# ADR-0001: AI-Native SDLC を骨格に、正本 spec と変更差分を分けて管理する

## Context

このリポジトリでは、題材ごとに設計ドキュメントと実装コードを置き、実装の大部分を AI エージェントが担う。エージェントに渡す文脈と、人間が判断する地点を、成果物として明確にしておく必要がある。

調べた主な手法は次のとおり。

- Anthropic AI-Native SDLC Playbook：intent → spec → plan
- Kiro：requirements / design / tasks、EARS
- GitHub Spec Kit
- OpenSpec：正本の specs と changes の差分
- AWS AI-DLC

一方で、成果物が多すぎるとレビューが辛くなり、実装と文書がずれていくという批判もある（Böckeler）。

## Options

1. **Kiro 型**：機能ごとに requirements / design / tasks の 3 ファイル
2. **AWS AI-DLC 型**：5 フェーズ・33 ステージの成果物をそのまま使う
3. **Anthropic 型を骨格にした組み合わせ**：intent → spec → plan を骨格にする。spec に Kiro の EARS と要件 ID を入れる。OpenSpec の正本／差分の分離を加える
4. **題材ごとに設計ドキュメント 1 枚**（初回コミットの形）

## Decision

3 を採用する。

- 段ごとに成果物が 1 つずつ（intent / spec / plan）で、成果物の数を抑えられる。要件と設計を spec 1 枚にまとめると、レビューの往復が減る。
- 既存製品の再構築は、機能を少しずつ積み上げる作業になる。正本と差分を分けると、差分だけをレビューすれば済み、正本は実装とずれない。
- EARS と要件 ID があると、要件からテスト・タスクまでを機械的に追える。
- 2 は、設計ドキュメントを中心とするこのリポジトリには重すぎる。4 は、実装を進めると文書が陳腐化する。

独自に、または調査した手法から次を加える。

- **品質を 2 層に分ける。** 題材ごとに、QA が持つ品質戦略 `quality.md` を置く。変更ごとのテスト設計は、原則として `spec.md` と `plan.md` の Proof に書く。ただし、リスクの高い変更に限り、変更単位の `quality.md` を作る。条件は process.md の「変更単位の quality.md を作る条件」にあり、当たるかどうかは Design 段で QA が判断する。すべての変更に作らないのは、レビューの負担を増やさないため。
- **「何が正しいか」は 3 つの形で `spec.md` に書く。**
  - シナリオ：代表例
  - 決定表：条件の組み合わせで結果が決まる規則
  - 正しさの性質：不変条件

  どれも仕様なので、アーカイブ時に正本へ積み上がる。決定表はテストが `spec.md` から直接読み込み、仕様とテストのずれを防ぐ。「どう確かめるか」（ジェネレーター、障害注入、負荷のモデル）は `plan.md` か、変更単位の `quality.md` に書く。
- **ロール（PM・Dev・QA・Ops）ごとに文書の持ち主を決める。** 1 つのファイルを複数のロールが日常的に編集しないよう、QA の `quality.md` と Ops の `runbooks/` を分ける。`spec.md` だけは PM と QA の二重承認にする。兼務は認めるが、同じ関門で作成者と承認者は別の人にする。
- **並行作業の衝突を仕組みで防ぐ。**
  - 変更フォルダを `YYMMDD-<slug>` で命名し、連番の衝突を避ける。
  - 変更の一覧を `roadmap.md` で手管理せず、frontmatter から集計する。
  - `MODIFIED` / `REMOVED` に変更前の本文を書かせ、アーカイブ時に正本と照合する（楽観ロック）。

## Consequences

- 良くなること：エージェントが読むべき文書が段ごとに決まる。追跡を CI で検査できる。
- 引き受けるコスト：
  - アーカイブ（差分を正本へ反映する作業）を忘れると、正本が古くなる。
  - 楽観ロックで失敗したら、差分を書き直し、承認を取り直す必要がある。
  - `CODEOWNERS` だけでは二重承認を強制できず、CI での補完が必要になる。

## Confirmation

- CI で、すべての ID（`REQ-*`・`PROP-*`・`DT-*`）がテストから参照されていることを検査する。
- CI で、ID の重複と、アーカイブ時の変更前の本文と正本との一致を検査する。
- `CODEOWNERS` と PR テンプレートで、文書ごとの承認者を確認する。
- QA の仕様レビューのチェックリスト（各題材の quality.md の 2.1 節）に、決定表の有無と、変更単位の quality.md の要否を含める。
- 変更の最後の PR で、`changes/` から `archive/` への移動と正本の更新が行われているかをレビューで確認する。
