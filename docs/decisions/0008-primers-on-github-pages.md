# ADR-0008: 題材ごとの前提知識の資料を、HTML で書き GitHub Pages で公開する

## Context

各題材の設計の文書は、その分野の知識を前提にしている。決済の台帳、WebRTC、CRDT、給与計算などである。分野に詳しくない読み手は、用語や業界の決まりでつまずく。

読み手が前提の知識を補える資料が要る。資料は、読み物として読めることに加えて、説明の場でスライドとしても使えるとよい。

## Options

1. **題材ごとに 1 つの HTML ファイルを書き、資料表示とスライド表示を切り替える。** `main` のルートから GitHub Pages で公開する。
2. **Markdown で書き、静的サイトの生成器でサイトにする。** Actions でビルドして公開する。
3. **スライドの道具（reveal.js など）で、スライドだけを作る。**

## Decision

1 を採用する。

- 置き場所：
  - 題材ごとの資料：`systems/<name>/docs/primer/index.html`
  - 共通の前提知識：`docs/primer/index.html`
  - 共通の CSS と JS：`docs/primer/assets/`
  - 入口：ルートの `index.html`
- 書き方の決まりは [docs/primer/AUTHORING.md](../primer/AUTHORING.md) に置く。
- 公開：GitHub Pages の公開元を `main` のルートにする。ルートに `.nojekyll` を置き、ファイルをそのまま配信する。ビルドの工程と CI は置かない。
- 外部から読むものは、図を描く Mermaid（jsdelivr）だけにする。
- 資料は設計の文書の要約ではなく、前提の知識を補うものにする。設計の正本は、これまでどおり Markdown の文書である。

他の案を退けた理由：

- 2 は、ビルドの工程と CI を、このリポジトリに持ち込む（[ADR-0005](0005-design-record-repository.md)）。
- 3 は、資料として順に読む使い方に向かない。

## Consequences

- 良くなること：
  - 分野に詳しくない読み手が、設計の文書へ入りやすくなる。
  - 同じファイルを、読み物とスライドの両方に使える。
- 引き受けるコスト：
  - 設計の文書を変えたとき、資料が古くなることがある。資料は前提の知識に絞り、設計の細部を書かないことで、古くなる範囲を小さくする。
  - Pages では Markdown が描画されない。資料から設計の文書へは、GitHub の URL でリンクする。
  - HTML・CSS・JS はリポジトリに置くが、資料を表示するためのもので、題材の実装のコードではない。ADR-0005 の「実装のコードを置かない」には当たらない。

## Confirmation

- 新しい題材を「設計済み」にするとき、前提知識の資料があることを確かめる。
- 資料を変える PR のレビューで、AUTHORING.md の決まりと、設計の文書との食い違いがないことを確かめる。
