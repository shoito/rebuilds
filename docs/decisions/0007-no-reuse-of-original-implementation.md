# ADR-0007: 題材の核に、本家の実装を使わない

## Context

このリポジトリは、既存のソフトウェアを「再構築するなら、どう設計し、どう作るか」を記録する。ところが、いくつかの題材の設計が、本家そのものの実装を核に据えていた。

- Kafka：本家の Apache Kafka のブローカーをそのまま動かし、その周りに管理の層を足していた。
- Cloudflare Workers：本家が公開しているランタイム workerd を土台にしていた。
- Chrome：本家の JavaScript エンジン V8 と、描画のライブラリ Skia を使っていた。

これでは、題材の中心の論点（ブローカーの複製と保存、isolate のランタイム、JS エンジンと描画）を設計していないことになる。本家の運用の形をなぞるだけでは、再構築の記録として価値が低い。

## Options

1. **本家の実装を核に使わない。** 核は自分で設計して作る。第三者の汎用の部品は使ってよい。
2. **部品として本家の実装を使うことを許す。** 核でなければよいとする。
3. **規則を置かない。** 題材ごとに判断する。

## Decision

1 を採用する。

- **本家の実装を、題材の核に使わない。** 「本家の実装」は、本家（またはその運営の組織）が作り、公開・提供している製品の本体・エンジン・ランタイムを指す。例：Apache Kafka のブローカー、workerd、V8、Skia。
- **核とは、その題材の主な論点を担う部分を指す。** 各題材の `README.md` の「主な論点」に挙げたものの実装である。
- **使ってよいもの：**
  - 本家と関係のない第三者の汎用の部品。データベース、言語の実行系、暗号のライブラリなどが当たる。
  - 公開の標準と、本家と互換のプロトコル。プロトコルの互換は振る舞いであり、実装の再利用ではない。
  - 本家が作った部品でも、題材の核から外れた、置き換えのきく部分。例：ビルドの道具やテストの道具。ただし、そうする理由を ADR に書く。
- **違反した題材は、作り直すか削除する。** 2026-09-28 に、Kafka、Cloudflare Workers、Chrome の 3 つを削除した。
- 2 は、何が核かの線引きがあいまいになり、同じ問題が繰り返される。
- 3 は、今回の 3 題材のように、題材ごとの判断で本家の再利用に流れやすい。

## Consequences

- 良くなること：
  - 各題材が、主な論点を自分で設計した記録になる。
- 引き受けるコスト：
  - 本家の実装を使うより、設計と実装の量が増える。成熟した実装に比べて、正しさと性能の検証が要る。
  - エンジンやランタイムを一から作る題材（ブラウザ、エッジのランタイムなど）は、題材として選びにくくなる。

## Confirmation

- 新しい題材の土台の ADR（技術の選定）のレビューで、核に本家の実装を使っていないことを確かめる。
- 設計の工程の最後の検証で、各題材の依存の一覧に、本家の実装が核として入っていないことを確かめる。
