# ADR-0006: 本家に寄せても、名前・接頭辞・ドメインは本家のものを使わない

## Context

各題材は、振る舞いを本家（Slack、Stripe、GitHub など）に寄せて設計している。その結果、設計の文書に、本家の名前を含む識別子がそのまま入りかけた。

- HTTP ヘッダー（`Stripe-Signature`、`X-GitHub-Api-Version`、`X-Hub-Signature-256` など）
- トークン・キーの接頭辞（`sk_live_`、`ghp_` など）
- ドメイン（`githubusercontent.com`、`js.stripe.com` など）

これには 2 つの問題がある。

- **識別子の衝突**：本家と同じ接頭辞のトークンは、GitHub などのシークレットスキャンで本家のトークンとして扱われ、誤った通報や失効の依頼が本家に届く。逆に、本家のトークンとの区別もつかない。
- **商標と誤認**：本家の名前を含むヘッダーやドメインを、別の事業者の製品に使うことは、商標の問題と、本家の製品との誤認を招く。

## Options

1. **振る舞いは本家に寄せ、名前・接頭辞・ドメインは独自のものにする**
2. **互換性のために、本家と同じ名前を使う**

## Decision

1 を採用する。

- 設計の文書では、ブランドの部分を `<Brand>`（ヘッダー名など）・`<brand>`（接頭辞・ドメインの一部）という置き換え用の名前で書く。実際の名前は、題材の開発リポジトリの作成時に決める。
  - 例：`<Brand>-Signature`、`X-<Brand>-Api-Version`、`<brand>_sk_live_...`、`<brand>p_...`、`<brand>usercontent.<domain>`
- 形式（署名の方式、ヘッダーの構造、接頭辞＋チェックサムの形式、バージョンの書式）は本家に寄せてよい。本家に寄せるのは振る舞いであって、名前ではない。
- トークン・キーの接頭辞は、他の既知のサービスの接頭辞と重ならないことを確かめ、GitHub のシークレットスキャンのパートナープログラムなどに、独自の形式として登録する。
- 本家の SDK やツール（Stripe の SDK、Octokit など）をそのまま使えることは、目標にしない。互換の層が必要になったら、別の ADR で扱う。

## Consequences

- 良くなること：
  - シークレットスキャンでの衝突と、本家との誤認を避けられる。
- 引き受けるコスト：
  - 本家の SDK やツールがそのまま使えない。題材ごとに公式の SDK を用意する（各題材の API の文書で扱う）。

## Confirmation

- 設計の文書のレビューで、本家の名前を含むヘッダー・接頭辞・ドメインが残っていないことを確かめる。出典の説明として本家の名前を書くのはよい。
