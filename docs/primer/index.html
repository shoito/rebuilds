このリポジトリは何か

既存の SaaS を「AI のコーディングエージェントを主な作り手として作り直すなら、どう設計するか」を記録しています。置いてあるのは設計の文書だけで、実装のコードはありません（ADR-0005）。

振る舞いは本家に寄せる

使い心地や API の形は本家を手本にします。

名前は本家のものを使わない

ヘッダー・トークンの接頭辞・ドメインは <brand> と書きます（ADR-0006）。

核に本家の実装を使わない

主な論点を担う部分は自分で設計します（ADR-0007）。

題材ごとの文書の地図

どの題材も systems/<name>/docs/ の下に同じ形の文書を持ちます。持ち主（承認する人）のロールも決まっています。

文書答える問い持ち主

architecture/どう作るか。全体像（README）と領域ごとの設計Dev

runbooks/本番でどう動かし続けるか。SLO・リリース・障害対応Ops

おすすめの読む順intent → architecture/README → 気になる領域の文書 → その領域の ADR → data-model。

開発の流れ（AI-Native SDLC）

各段は、次の段が読める成果物をコミットします。エージェントは草案と実装を担い、承認は人間のロールの持ち主がします。

  1. Plan：intent.md で問題と望む結果を書く。PM が受理する。
  2. Design：spec.md（差分）に要件を書く。必要なら ADR と quality.md。PM と QA が承認する。
  3. Build：plan.md を書き、承認されたら実装する。Dev がレビューする。
  4. Test：エージェントが自分で確認ループを回し、CI を通す。QA が受け入れる。
  5. Deploy：デプロイし、フィーチャーフラグで段階的にリリースする。Ops が本番を承認する。
  6. Maintain：監視と SLO。逸脱やインシデントは、新しい intent として起票する。

変更が小さければ、全部の成果物は要りません。typo は PR だけ、新しい Epic は intent・spec・plan・ADR・quality まで、と規模で重さを変えます。

ADR：決定の記録

アーキテクチャに影響する選択は、ADR に残します。形式は MADR で、次の節を持ちます。

何が問題で、何に縛られているか。

検討した選択肢。たいてい 2〜4 個。

どれを選んだか。選ばなかった案を退けた理由も書く。

良くなることと、引き受けるコスト。

決定が守られていることを、どう確かめるか。

決定を変えるとき確定した ADR の本文は書き換えず、日付つきの注記（> 2026-09-28 の注記：…）を足すか、新しい ADR で置き換えます。文書の中で「注記」を見かけたら、後から決定が補われた印です。

確定した ADR の決定を変えたくなりました。どうしますか？

過去の判断の理由を残すため、本文は書き換えません。いつ・なぜ変わったかが追えることが ADR の価値です。

要件の書き方：ID と EARS

要件には ID を振り、テストの名前にもその ID を入れて追跡します。

種類形式例
要件REQ-<CAP>-NNNREQ-MSG-001
正しさの性質PROP-<CAP>-NNNどんな入力でも成り立つべきこと
決定表DT-<CAP>-NNN条件の組み合わせで結果が決まる規則
非機能要件NFR-NNN遅延・可用性・規模の目標

文は EARS の型で書きます。例：「〈事象〉とき、システムは〈振る舞い〉しなければならない」。

規模の段階：S1・S2・S3

最初から最大の構成にはしません。題材ごとに、構成を変える地点を段階として決めています。

S1（MVP）

東京の 1 リージョン・3 AZ。DB は writer 1 台と reader。大阪に災害復旧の控えを置く。

S2

reader やキャッシュを増やし、検索などを専用の部品へ分ける。

S3

セルの構成。スタック一式を複製し、テナントをセルに割り当てる。

表の「S1 の規模」は、この S1 の段階で見込む行数や容量です。

マルチテナントと RLS

1 つの DB に多くの顧客（テナント）のデータが入ります。別の顧客のデータが見えることは、最も重い事故です。そこで DB 自身に、行ごとの読み書きの許可を判定させます（RLS）。

  1. リクエストが来たら、認証の結果からテナントの ID を決める。
  2. トランザクションの最初に SET LOCAL app.tenant_id = '…' を実行する。
  3. 各表のポリシーが tenant_id が設定の値と同じ行だけを通す。
  4. FORCE ROW LEVEL SECURITY で、表の持ち主のロールにもポリシーを効かせる。
  5. トランザクションが終わると設定は消え、次のリクエストに漏れない。
ALTER TABLE items ENABLE ROW LEVEL SECURITY;
ALTER TABLE items FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON items
  USING (tenant_id = current_setting('app.tenant_id')::uuid);
RLS の外テナントが決まる前に引く表（ログインの照合など）は RLS をかけられません。各題材の data-model に「RLS の外の表」として一覧があり、専用の関数やロールに限って読ませます。

ID：UUIDv7

主キーは多くの題材で UUIDv7 です。先頭 48 ビットが作った時刻（ミリ秒）なので、ほぼ作った順に並びます。

0192 3e4f-8a1b-7c3d-9e2f-1a2b3c4d5e6f
└── 時刻(48bit) ─┘ └ 版=7 ┘ └── ランダム ──┘
  • B-tree の索引の末尾に追記されるので、ランダムな UUIDv4 より書き込みが速い。
  • ID の範囲で時刻の範囲を表せるので、ID でパーティションを切れる。
  • PostgreSQL 18 は uuidv7() を標準で持つ。

パーティションに分けた表の主キーに、分割の鍵を含めなければならないのはなぜ？

そのため、多くの題材で「UUIDv7 の ID の範囲で分割する」か「主キーに日付を含める」という形を取っています。

正本と outbox

「DB に書いた」と「イベントを流した」を別々に行うと、片方だけ成功して食い違います。そこで outbox を使います。

flowchart LR
  API[API] -- "1 tx: 行 + outbox" --> DB[(Aurora)]
  DB -- "2 outbox を順に読む" --> R[Relay]
  R -- "3 配る" --> Q[SNS / SQS / Valkey]
  Q -- "4 処理" --> W[Worker・Gateway]
  1. 業務の行と、送るべきイベントの行を、同じトランザクションで書く。
  2. Relay が outbox を順に読み、キューや Pub/Sub に流す。
  3. 受け手は少なくとも 1 回届く前提で、重複を捨てる（冪等）。

配信の経路（Valkey など）が落ちても正本は失われず、クライアントは再接続のときに差分を取り直します。

冪等：同じ要求を 2 回送っても 1 回分

ネットワークが切れると、クライアントは「届いたか分からない」まま再送します。冪等にしておけば、再送しても二重にはなりません。

冪等でない

決済の API を再送 → 2 回請求される。

冪等

Idempotency-Key を付けて再送 → 1 回目の結果をそのまま返す。

DB では、キーに一意の制約を張り、同じキーの 2 回目は保存した応答を返します。キューの受け手も、イベントの ID で重複を捨てます。

デプロイとリリースを分ける

トランクベース開発で、main に毎日小さく入れます（ADR-0002）。未完成の機能はフィーチャーフラグの裏に置き、コードはデプロイしても、利用者には見せません。

  1. フラグを off のまま、コードを本番にデプロイする。
  2. 社内のテナントだけ on にする。
  3. 一部の顧客に広げ、指標を見る。
  4. 全体に on。問題があればフラグを off に戻す（再デプロイしない）。
  5. 定着したら、フラグとその分岐を消す。

ER 図の読み方

data-model の ER 図は Mermaid の erDiagram です。線の両端の記号が、相手が何件あるか（多重度）を表します。

erDiagram
  workspaces ||--o{ channels : "has"
  channels ||--o{ messages : "contains"
  users }o--o{ channels : "joins via members"
  workspaces {
    uuid id PK
    text name
  }
  channels {
    uuid id PK
    uuid workspace_id FK
    text name UK "unique per workspace"
  }
  messages {
    uuid id PK
    uuid channel_id FK
    bigint seq "order in channel"
  }
記号意味
||ちょうど 1 件
o{0 件以上
|{1 件以上
PK / FK / UK主キー / 外部キー / 一意

図には主な列だけを描き、全部の列・索引・CHECK は、図の下の表の一覧に書いています。

SLO と復旧の目標

非機能の目標は数字で書きます。よく出る略語です。

p99
遅い順に並べて上位 1% を除いた値。「p99 200ms」は、99% の要求が 200ms 以内に終わること。
SLO
目標とする信頼性（例：月間 99.9% 成功）。破りそうになったら機能の開発より安定を優先する。
RPO
障害で失ってよいデータの時間幅。RPO 0 は「成功を返したものは失わない」。
RTO
障害から復旧するまでの時間の目標。

用語集

ADR
Architecture Decision Record。設計の決定を、理由と退けた案と一緒に残す短い文書。
EARS
Easy Approach to Requirements Syntax。「〈条件〉とき、システムは〈振る舞い〉しなければならない」のような決まった型で要件を書く方法。
テナント
データを分けて持つ単位の顧客。題材によりワークスペース・組織・アカウントなどと呼ぶ。
RLS
Row Level Security。PostgreSQL の機能で、行ごとに読み書きの可否をポリシーで判定する。
UUIDv7
先頭に作成時刻を持つ UUID。時刻の順にほぼ並ぶ。
outbox
送るべきイベントを、業務のデータと同じトランザクションで DB の表に書き、後から別の処理が配る方式。
冪等
同じ操作を何回行っても、1 回行ったのと同じ結果になる性質。
Valkey
Redis から分かれたオープンソースのインメモリのデータストア。キャッシュ・Pub/Sub・レート制限に使う。
セル
サービスのスタック一式の複製。テナントをセルに割り当て、障害の影響を 1 つのセルに閉じ込める。
AZ
Availability Zone。同じリージョンの中で、電源やネットワークが独立したデータセンターの群。
Aurora Global Database
別のリージョンに読み取り用の複製を持つ Aurora の構成。災害のときに昇格させる。
