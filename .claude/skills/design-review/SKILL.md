# 設計の文書を横断して見直す

2026-10-10 の見直し（全題材の図の追加、README の整理、漏れている観点の追加につながったもの）の型。見直しは**読むだけ**で、直すのはユーザーが範囲を決めてからにする。

## 1. 定量の比較

```bash
node .claude/skills/design-review/scripts/scan.mjs
npm run check
```

`scan.mjs` は、題材ごとの規模・図の種類の数・固有の runbook、`architecture/README.md` の節とテンプレートとの差、観点（アクセシビリティ、多言語、移行、書き出し、運用者のアクセス、法務）の言及の数を、Markdown の表で出す。前回の結果があれば並べて比べる。観点の数が 0 のものは漏れの候補で、grep で中身を確かめてから漏れと言う。

## 2. 中身の見直し

題材を 4〜5 題材ずつのグループに分け、グループごとに読むだけのサブエージェントを並行して起動する。共通の文書にも 1 つ割り当てる。指示は [references/reviewer-prompt.md](references/reviewer-prompt.md) の雛形に、1 の結果のうちそのグループに関係する要点を埋めて作る（既に分かっていることを報告し直させないため）。

## 3. まとめて報告する

- サブエージェントの主な指摘は、自分で grep して確かめてから使う。
- 報告は「全体の傾向 → 図の不足 → 読みやすさ → 漏れている観点 → リポジトリ全体 → 進め方の提案」の順にする。進め方は、依存の順（テンプレートや規則のような土台を先に）で段階に分ける。
- **食い違い（本文と表、文書と文書）は直さない。** ファイル・行・内容の一覧にして報告する。設計の判断が要るためである（ルートの `AGENTS.md`）。
- ユーザーが望めば、食い違いと漏れを GitHub の Issue に起票する。外に出る操作なので、件数と題名の一覧を見せて承認を得てから行う。

## 4. 直すとき

ユーザーが範囲を決めたら、題材ごとにサブエージェントに分けて直す。指示は `new-subject` の Skill の `references/agent-brief.md` の「共通の約束」を使い、最後に `npm run check` を全体に通す。
