# 設計の文書を横断して見直す

2026-10-10 の見直し（全題材の図の追加、README の整理、漏れている観点の追加につながったもの）の型。見直しは**読むだけ**で、直すのはユーザーが範囲を決めてからにする。

## 1. 定量の比較（自分で行う）

題材ごとに次を数え、表にする。古い題材と新しい題材の差、手本との差が見える。

- 文書の数と行数、`architecture/README.md` の行数
- Mermaid の図の数を種類ごとに（`stateDiagram`・`sequenceDiagram`・`flowchart`・`gantt`・`erDiagram`）
- `architecture/README.md` の節の有無（コンテキスト、コンテナ、主要な流れ、本家の形、費用のモデル）が `docs/templates/architecture.md` と合っているか
- 題材に固有の runbook の有無
- 観点の言及の有無を grep で：アクセシビリティ（WCAG）、多言語、移行・取り込み、データの書き出し、運用者のアクセス、保持と削除、法務の確認待ち
- `npm run check` の結果

## 2. 中身の見直し（サブエージェントに分ける）

題材を 4〜5 題材ずつのグループに分け、グループごとに読むだけのサブエージェントを並行して起動する。共通の文書（`README.md`・`index.html`・`docs/`）にも 1 つ割り当てる。指示には次を入れる。

- 読むだけで、ファイルを編集しない。
- 1 の結果のうち既に分かっていることは報告し直さない（重複を避ける）。
- 題材ごとに、読み手（その分野に詳しくない Web の開発者）の立場で報告する：
  1. 図解の不足：ファイル・節・図の種類を挙げ、優先度順に。複数の者が絡む流れ、表や文章だけのステートマシン、失敗と回復の経路を特に見る。
  2. 理解の障害：定義のない用語、「なぜ」の欠け、詰め込みすぎ、リンクの欠け、primer と設計の文書の数値の食い違い（抜き取りで照らし合わせる）。
  3. 漏れている観点：grep で無いことを確かめてから挙げる。
  4. ほかの題材に広げたい良い点。
- ファイルと行の番号を付ける。最後に、上位 5 件の改善を優先度順に挙げる。

## 3. まとめて報告する

- サブエージェントの指摘は、主なものを自分で grep して確かめてから報告に使う。
- 報告は「全体の傾向 → 図の不足 → 読みやすさ → 漏れている観点 → リポジトリ全体 → 進め方の提案」の順にする。進め方は、依存の順（テンプレートや規則のような土台を先に）で段階に分けて提案する。
- **食い違い（本文と表、文書と文書）は直さない。** ファイル・行・内容の一覧にして報告する。設計の判断が要るためである（承認済みの内容を実装の都合で書き換えない、ルートの `AGENTS.md`）。
- ユーザーが望めば、食い違いと漏れを GitHub の Issue に起票する。起票は外に出る操作なので、件数と題名の一覧を見せて承認を得てから行う。

## 4. 直すとき

ユーザーが範囲を決めたら、題材ごとにサブエージェントに分けて直す。`new-subject` の Skill の「エージェントに任せるときの約束」を指示に入れ、最後に `npm run check` を全体に通す。
