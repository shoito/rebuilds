# ADR-0034: 住所の検索は自前の API の後ろに 1 社の提供者を置き、PoC の基準で選ぶ。乗降の座標は乗客が確かめたピンとして保存し、乗降の地点は運用が確かめたデータで出す

## Context

乗客は、乗車地と降車地を住所・建物・施設の名前で探す。日本の住所（番地、建物の名前、施設、駅の出口）の網羅は、OSM では足りないと見込み、商用の提供者を使う（[ADR-0005](0005-maps-and-routing.md)。候補はゼンリン、Google、Amazon Location Service）。

提供者の条件は、結果の保存と他の地図との併用を制限しうる（2026-09-27 に確認）。

- Google Maps Platform：Geocoding API の内容を Google 以外の地図と一緒に使ってはならない。緯度経度は 30 日まで一時にキャッシュできる。緯度経度と整形した住所は、要求したアプリの利用者向けの機能のためだけに、利用者ごとに分けて無期限に持てる（[Service Specific Terms](https://cloud.google.com/maps-platform/terms/maps-service-terms) の 6.2・6.3）。
- Amazon Location Service：保存（キャッシュを含む）には `IntendedUse=Storage` と高い料金が要り、自動補完は保存できない（[IntendedUse](https://docs.aws.amazon.com/location/latest/developerguide/places-intended-use.html)）。以前の版の API では、HERE の日本の結果を保存できない（[DataSourceConfiguration（previous）](https://docs.aws.amazon.com/location/previous/APIReference/API_DataSourceConfiguration.html)）。現行の版の条件は **未検証**。
- ゼンリン：保存と併用の条件は **未検証**。

一方で、乗車の記録には、乗降の地点が要る（運賃の根拠、領収書、問い合わせ、事故の調べ）。駅・空港・ホテルでは、決められた乗り場で乗せる必要がある。

## Options

窓口：

1. **自前の API（`/v1/places/*`）の後ろに提供者を置く**
2. **アプリから提供者の SDK を直接呼ぶ**

保存：

- a. **乗客が確かめたピンの座標を乗車の記録に持ち、提供者の内容（座標・名前・ID）は提供者ごとの期間だけ持つ**
- b. **提供者の結果をそのまま乗車の記録に持つ**

乗降の地点：

- i. **運用が確かめたデータ（施設の協定・運用の作成）と、実績から作る候補（運用の確認の後に公開）**
- ii. **実績から自動で作って公開する**
- iii. **持たない（ピンと道路への寄せだけ）**

## Decision

1、a、i を採用する。詳細は [maps-and-geodata.md](../architecture/maps-and-geodata.md) の 7・8 節。

- **窓口**：`places-service` が提供者の応答を自前の形にそろえる。鍵はサーバーだけに置く。入力の文字列をログに書かない。近くの位置は解像度 7 に丸めて提供者に送る。乗客 1 人あたり 1 秒に 5 回・1 日に 500 回の制限。
- **提供者の選定**：E4 の PoC で、的中の率（東京の 2,000 件で上位 1 件が 30 m 以内、必須 80%・目標 90%）、自動補完の p95 300 ms、保存の可否、乗客のアプリの地図・Valhalla の経路の線との併用の可否を必須の基準にし、表記の揺れ、料金、SLA、データの所在、推計走行距離の要件（[ADR-0017](0017-fare-distance-for-pre-fixed-fares.md)）と合わせて選ぶ。選んだ後、その提供者の条件を続きの ADR に写す。
- **保存**：乗車の記録には、乗客が地図の上で確かめたピン（`origin=rider_confirmed_pin`）を持つ。提供者の座標そのものは持たない。表示の名前と提供者の ID は、提供者の条件の期間だけ持つ。これが条件に反しないかは、PoC と法務の確認（L3）で確かめる。
- **乗降の地点**：`pickup_points` を運用が 2 人の確認で整える。乗客のピンから 80 m 以内の地点、なければ 50 m 以内の、高速道路・トンネル・橋を除いた道路の辺の上の点を、最大 3 つ提案する。施設の中では施設の地点だけ。実績（解像度 10、90 日、10 件以上・異なる乗客 5 人以上）から候補を作り、運用の確認の後に公開する。
- 2 を採らない理由：鍵がアプリに入り、提供者の替え・流量の制限・ログの規則を、アプリの配布なしに変えられない。
- b を採らない理由：提供者の保存の条件に反しうる。提供者を替えたときに、過去の記録の扱いが提供者ごとに分かれる。
- ii を採らない理由：私有地・規制の場所・特定の人の自宅の前が、乗降の地点として公開されうる。
- iii を採らない理由：駅・空港・大きな施設では、決められた乗り場を使わないと、到着から乗車までが延び、ETA の誤差（NFR-003）も増える。

## Consequences

- 良くなること：
  - 提供者を替えても、アプリと乗車の記録の形が変わらない。
  - 乗車の記録に残る座標は、乗客が確かめた値で、提供者の条件に左右されにくい。
  - 乗降の地点が運用の確認を経るので、誤った地点が公開されない。
- 引き受けるコスト：
  - 自前の API の分、自動補完の遅れが増える（数十 ms を見込む。**未検証**）。
  - PoC の正解の 2,000 件を作り、提供者の変更のたびに計り直す。
  - 乗降の地点のデータを運用が育て続ける。
  - Google を選ぶと、乗客のアプリの地図も Google にする必要があり、Valhalla の経路の線を重ねる設計（[ADR-0016](0016-valhalla-serving-traffic-and-eta-accuracy.md)）と衝突しうる。

## Confirmation

- 性質ベーステスト：PROP-MAP-003（提案は 80 m の地点か 50 m の許された辺だけ、施設の中は施設の地点だけ）、PROP-MAP-004（提供者の内容の型は期間つきのストアにだけ書け、乗車の記録の座標は `rider_confirmed_pin` だけ）。
- E4 の PoC の結果を、この ADR の続きの選定の ADR に添える。
- レビュー：アプリに提供者の鍵を置く変更、入力の文字列をログに書く変更、提供者の座標を乗車の記録に書く変更を差し戻す。
