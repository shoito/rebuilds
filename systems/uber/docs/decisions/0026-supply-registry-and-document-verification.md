# ADR-0026: 供給は事業者が登録し、この基盤が書類を確かめ、配車に出てよいかをバージョンつきの判定として出庫と提案の両方で確かめる

詳細は [supply-and-operators.md](../architecture/supply-and-operators.md) の 3〜5 節。

## Context

運送の主体はタクシー事業者で、ドライバーは事業者に属する。個人が事業者を通さずに客を運ぶ経路（白タク）は作らない（[intent.md](../intent.md)）。

ドライバーの要件は、サービスで違う（2026-09-27 に確認）。

- タクシーは第二種運転免許（[東北運輸局の資料](https://wwwtb.mlit.go.jp/tohoku/content/000338889.pdf)）。
- 日本版ライドシェアは、第一種（初心運転者期間を除く）か第二種の免許、従事の前 2 年間の無事故・無免停、事業者の研修と指導監督、運転者証明の携行。車両は定員 10 人以下で、対人 8,000 万円以上・対物 200 万円以上の任意保険（[関東の運輸支局長の公示](https://wwwtb.mlit.go.jp/kanto/content/000324077.pdf)、2024-03-29）。

書類には期限があり、期限の切れたドライバーを配車に出してはならない。一方、配車の熱い経路は索引の写しで候補を選ぶので、判定の変化が写しに届くまでに遅れがある。

## Options

### 登録の主体

1. **事業者が登録し、この基盤が確かめる**
2. **ドライバーが自分で登録し、事業者が承認する**

### 判定の持ち方

1. **書類・期限・停止・許可・運行枠から求めた判定を、バージョン（`eligibility_ver`）つきでセッションに持ち、索引へ配る。Trips の提案の検査でも同じ表を読む**
2. **索引の写しだけで判定する**
3. **提案のたびに、すべての書類を読み直す**

## Decision

登録は 1、判定は 1 を採用する。

- 登録の API は、事業者の管理画面の利用者のトークンでだけ呼べる。ドライバーのアプリのトークンでは呼べない。
- 書類の確認は、この基盤の審査の担当が行う。読み取り（OCR）は補助で、確定は人。無事故・無免停、研修、運転者証明、車両の表示は、事業者の証明（`driver_attestations`）として受ける。
- 出庫の可否は DT-SUP-002 で決め、許可したらセッションを作る。1 人のドライバー、1 台の車両に、同時に 1 つのオンラインのセッション（部分一意索引）。
- 判定が変わったら `eligibility_ver` を増やし、`supply.session_changed` を outbox で配る。判定が「出てはいけない」になっても、進行中の乗車は最後まで続け、新しいオファーだけを止める。
- Trips の提案の検査（[trips-lifecycle.md](../architecture/trips-lifecycle.md) の 4.3 節）は、同じ判定の表を同じ Aurora で読む。索引の写しが古くても、出てはいけないドライバーへのオファーは作られない。
- 書類の期限は、日次のジョブと出庫の時の検査の両方で確かめる。
- 登録の 2 を採らない理由：個人が登録できる入口ができると、事業者の管理の外のドライバーが生まれうる。白タクの禁止を仕組みで守れなくなる。
- 判定の 2 を採らない理由：写しの遅れの間、期限切れや停止のドライバーにオファーが届く。
- 判定の 3 を採らない理由：提案の検査が重くなり、配車の遅れ（NFR-001）に響く。

## Consequences

- 良くなること：
  - 白タクの経路が、API の権限の段階でない。
  - 判定が 1 か所で決まり、出庫・索引・提案の検査が同じ結果になる。
- 引き受けるコスト：
  - 書類の確認の担当と、待ちの管理が要る。
  - 事業者の証明に頼る項目（無事故・無免停など）は、この基盤が真正を確かめられない。事業者の責任として契約で定める。

## Confirmation

- 決定表：DT-SUP-001（書類の要否）、DT-SUP-002（出庫の可否）。
- 性質ベーステスト：PROP-SUP-002（期限切れ）、PROP-SUP-003（事業者の分離）、PROP-SUP-004（判定の収束）、PROP-SUP-005（白タクの経路がない）。
- レビュー：ドライバーのアプリのトークンで、登録・書類・事業者の API を呼べるようにする変更を差し戻す。
