# ADR-0036: 位置と個人の情報は種類ごとの KMS の鍵と保持の期間で分け、人が見る操作は理由・範囲・期限つきの許可と改ざんできない監査ログで行う

詳細は [security.md](../architecture/security.md) の 5〜7 節。

## Context

この基盤は、ドライバーの位置を 4 秒ごとに集め、乗車の軌跡、配車の判断の記録、緊急の通報の位置を持つ。位置の履歴は、個人の行動を強く表す。

- 乗客とドライバーの正確な位置は、乗車の相手にだけ、その乗車の間だけ見せる（NFR-009）。
- 位置の保存のストアと保持の既定案は [ADR-0010](0010-location-trails-map-matching-and-retention.md) が決めた（生の点 30 日、乗車の軌跡 1 年、ID を持たない集計 2 年）。配車の判断の記録は 180 日（[ADR-0015](0015-offer-protocol-decision-log-and-replay.md)）。
- 人が軌跡を見る操作は、理由の入力と監査ログを必須にする（[AGENTS.md](../../AGENTS.md)）。仕組み（鍵、許可、監査ログの保管、削除）は、この領域に残されていた。

事実（2026-09-27 に確認）：

- 個人情報保護委員会の FAQ は、位置情報を個人関連情報の例に挙げ、個人情報に当たる場合は個人関連情報に当たらないとする（[FAQ Q2-8](https://www.ppc.go.jp/all_faq_index/faq2-q2-8/)）。
- 電気通信事業のガイドラインの解説は、個人の位置情報がそれだけでは通常は個人情報に当たらないが、連続して蓄積されるなどして特定の個人を識別できる場合は個人情報に当たる、とする。電気通信事業者の位置情報は、同意などがある場合に限り取得・利用できる（第 41 条。[電気通信事業における個人情報等の保護に関するガイドラインの解説](https://www.ppc.go.jp/files/pdf/240312_telecom_GLs_description.pdf)、令和 6 年 3 月更新）。この基盤が電気通信事業者に当たるか、第 41 条が及ぶかは **法務の確認待ち**（[intent.md](../intent.md) の L4）。

## Options

### 鍵

1. **データの種類ごとの KMS の鍵（位置、個人の情報、お金、監査、一般）。鍵のポリシーで使える役割を絞る**
2. **環境ごとに 1 つの鍵**
3. **利用者ごとの鍵（削除を鍵の破棄で行う、crypto-shredding）**

### 人が見る操作

- a. **窓口を 1 つにし、理由・対象の範囲・期限つきの許可（grant）を発行して読む。監査ログは操作と同じトランザクションで書く**
- b. **役割があれば見られる。監査ログは後から集める**

## Decision

鍵は 1、人が見る操作は a を採用する。

- 鍵は `location`・`pii`・`biometric`・`money`・`audit`・`app` の 6 種類。東京で作り、大阪にレプリカを置くマルチリージョンの鍵にする。年 1 回の自動の入れ替え。
- `biometric` は、ドライバーの顔の画像（生体の情報）の専用の鍵で、使えるのは照合のサービスの役割と、安全の担当の監査つきの確認の役割だけ。`pii` と分けるのは、顔の画像が L4 の関門の裏の、最も機微な個人の情報で、鍵のポリシーで使える役割を最小にするため（統合の工程で足した。[safety-and-trust.md](../architecture/safety-and-trust.md) の 12 節）。
- `location` の鍵を使えるのは、位置のパイプラインの役割（loc-ingest、Firehose、trail-builder、配車の記録の書き手）と、監査つきの閲覧の窓口の役割だけ。分析の役割は、`driver_id` を HMAC に置き換えた写しだけを別のアカウントで読む（ADR-0010）。
- **位置の閲覧の許可（`location_access_grants`）**：理由（問い合わせ・インシデント・事故の ID）、対象（1 乗車の区間、または 1 つの `SafetyIncident` の追記の位置）、期限（30 分）を持つ。窓口は許可の範囲の外を返さない。
  - 複数の乗車、1 人の人の期間の軌跡、警察などの外部への提供は、法務の担当と運用の責任者の 2 人の承認を要する。外部への提供の条件は **法務の確認待ち**（L4・L7）。
- 監査ログは、操作と同じトランザクションで `audit_events` に書き、outbox で log-archive の S3（Object Lock のコンプライアンスモード）へ送る。保持は Aurora に 1 年、アーカイブに 7 年（既定案。法務の確認待ち）。形は Slack の題材の [ADR-0018](../../../slack/docs/decisions/0018-audit-log.md) を引き継ぐ。
- 保持の期間は、[security.md](../architecture/security.md) の 7 節の表を正本にし、Terraform の S3 のライフサイクル・DynamoDB の TTL・削除のジョブの値を、その表から生成する。
- 削除は東京と大阪の両方で行う。S3 の版を指定した削除とライフサイクルの動作は、複製で大阪に伝わらない（Figma の題材の [ADR-0045](../../../figma/docs/decisions/0045-audit-log-and-data-lifecycle.md) と同じ）。バックアップの期限（最大 35 日）を、どの削除でも最終の期限にする。
- 2 を採らない理由：位置を扱わないサービスの侵害で、位置のストアも読めてしまう。
- 3 を採らない理由：位置の点は多く（S1 で 1 日に数億点）、利用者ごとの鍵の管理と費用が重い。乗車の軌跡は運賃の根拠として事業者の記録と結びつき、利用者の削除だけで消せるとは限らない（L4）。
- b を採らない理由：後から集める監査ログは、欠けを見つけにくい。NFR-009 の「100% 残す」を仕組みで守れない。

## Consequences

- 良くなること：
  - 位置を読めるロールが、鍵のポリシーの一覧で数えられる。
  - 人が位置を見た記録が、閲覧の結果と必ず一緒に残る。
  - 法務の結論で期間が変わっても、表を直せば設定が生成し直される。
- 引き受けるコスト：
  - 許可の発行と 2 人の承認の画面を、サポートのツールに作る。
  - 鍵が 6 種類あり、サービスごとの鍵の権限の管理が増える。
  - 利用者の削除の依頼に、軌跡を保持の期間の前に消すかは、法務の結論待ち。消す場合は、軌跡の S3 のキーを乗車の ID から引く削除のジョブが要る。

## Confirmation

- IAM Access Analyzer と `checkov`：`location` の鍵を使える役割が、許可の一覧の外に増えたら PR を失敗させる。
- 毎日の照合：軌跡・位置の閲覧の API の呼び出しの件数と、`audit_events` の件数が一致する（ADR-0010 の Confirmation）。
- 性質ベーステスト：許可の範囲の外（別の乗車、期限の後）の位置を窓口が返さない（PROP-SEC-001）。
- PROP-LOC-005 と同じく、保持の表と Terraform のライフサイクルの値の一致をテストで確かめる。
