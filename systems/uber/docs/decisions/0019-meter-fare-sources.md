# ADR-0019: メーターの運賃は車載のメーターか認定ソフトメーターとの連携で受け取り、連携できない車はドライバーの入力を影の計算と照合する

詳細は [pricing-and-fares.md](../architecture/pricing-and-fares.md) の 5.4 節。

## Context

メーターの運賃（距離制運賃）の乗車では、降車のときにメーターが示した額が運賃になる。アプリで決済するには、その額をこの基盤が正しく受け取らなければならない。受け取り方で、運賃の正しさの保証が変わる（[architecture/README.md](../architecture/README.md) の 7 節）。

事実（2026-09-27 に確認）：

- 従来のタクシーメーターは計量法の特定計量器で、年に 1 度の検定で精度を担保する。国土交通省は、位置情報の推移から走行距離を推定して運賃を出すソフトメーターの認定制度を作った（[運賃・料金の多様化検討会 第 1 回説明資料](https://www.mlit.go.jp/jidosha/content/001758788.pdf)、2024-08）。
- 認定の要件は、GNSS が取れないときの走行信号での補正、距離の許容差（1 km 以下で −40 m〜0 m、1 km 超で −4.0%〜0%）、1 実車ごとの記録の 1 年の保存、乗務員の識別と改ざんへの対策、開発事業者の保守と不具合の収集の体制など（[特定運賃収受ソフトウェア認定要領](https://www.mlit.go.jp/jidosha/content/001860154.pdf)、令和 7 年 1 月）。
- 表示の方法は国土交通省告示第 63 号（2025-01-31）で定まり、認定を受けた製品は 4 つある（メーターの製造者 3 社と配車アプリの事業者 1 社。[認定事業者の一覧](https://www.mlit.go.jp/jidosha/content/001899200.pdf)、2026-09-27 に確認）。

## Options

1. **車載のメーター（または認定ソフトメーター）との連携だけ**
2. **連携を優先し、連携できない車はドライバーの入力を許す。入力は、軌跡から求めた影の計算と照合する**
3. **ドライバーの入力だけ**
4. **自前のソフトメーターを作り、認定を受ける**

## Decision

2 を採用する。

- 受け取り方は `integrated_meter`・`certified_soft_meter`・`driver_input` の 3 つ。乗車ごとに `meter_readings.source` に残す。
- 連携は、製造者に依らない口（`MeterAdapter`）にする。受け取る事象は、状態の変化（空車・迎車・実車・支払）と、支払の額・距離・時間。事象には機器の連番を持たせ、重複と抜けを検知する。製造者が署名を出せるなら検証する。
- 連携の中継（車内の機器からドライバーのアプリへ Bluetooth で送るか、製造者のサーバーから API で受けるか）は、1 社目の製造者に合わせて E7 で決める。
- **影の計算**：乗車の軌跡の当てはめた距離と時間から、事業者の距離制の規則でメーターの額を推定する。**影の計算の額で請求しない。** 使うのは、`driver_input` の照合と、連携の異常の検知だけ。
- `driver_input` は、影の計算との差が max(20%, 500 円) 以内なら確定する。超えたら確定を保留し、メーターの表示の写真と運用の確認を求める（DT-FARE-004）。
- 1 を採らない理由：最初の提携先の車に、連携できるメーターがそろうとは限らない。そろうまで配車できないのは、[intent.md](../intent.md) の MVP に合わない。
- 3 を採らない理由：入力の誤りや不正を検知できない。
- 4 を採らない理由：認定の要件（試験、1 年の記録、保守の体制、車内の表示の機器）を満たすには、機器とその保守まで持つことになる。この基盤の本質（配車と決済）から外れる。S2 で、連携できる製造者が足りないときに見直す。

## Consequences

- 良くなること：
  - 連携のある車では、運賃が機器から直接届き、入力の誤りがない。
  - 連携のない車でも配車でき、影の計算で大きな誤りを止められる。
- 引き受けるコスト：
  - 製造者ごとの連携の口を作り、保つ必要がある。
  - 保留の確認をする運用の担当が要る。保留が多いと、事業者への精算が遅れる。
  - 影の計算は、軌跡の欠け（トンネル、通信の切断）で外れる。照合の閾値は、実績で見直す。

## Confirmation

- 決定表：DT-FARE-004 を表駆動テストにする。
- 結合テスト：模擬のメーターの事象（連番の抜け、重複、支払の額なし）で、`driver_input` への切り替えと異常の記録を確かめる。
- 本番の計測：受け取り方ごとの割合、保留の割合、影の計算と連携のメーターの額の差の分布（quality.md）。
