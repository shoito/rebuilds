# ADR-0037: 利用者の種類ごとに認証を分け、ドライバーは出庫のときに端末の完全性を確かめる。不正は兆しの点数と人の確認で扱い、自動の処置は配車・特典から外すまでにする

詳細は [security.md](../architecture/security.md) の 3・4・9 節。

## Context

この基盤には、4 種類の利用者がいる。乗客、ドライバー、事業者の管理画面の利用者、この基盤の運用（サポート・安全・審査）。守るものと攻め方がそれぞれ違う。

- ドライバーは、事業者が登録した人だけが出庫できる（[ADR-0026](0026-supply-registry-and-document-verification.md)）。白タクの経路を作らない。
- 位置の偽装で配車の多い場所にいるように見せる不正がある（[location-ingestion.md](../architecture/location-ingestion.md) の 13 節）。
- 本家は、配車の不正として、払い戻しの要求、支払いの不正、アカウントの乗っ取り、ドライバーと乗客の共謀、特典の濫用、GPS の偽装を挙げ、教師なしの異常の検知と、処置の前の人の確認を組み合わせている（[Risk Entity Watch](https://www.uber.com/blog/risk-entity-watch/)、2023-09-28、2026-09-27 に確認）。
- 端末の完全性の仕組み（2026-09-27 に確認）：Android の Play Integrity API は、アプリの完全性、端末の完全性、アカウントの情報の判定を返し、既定の上限は 1 日 1 万回（[Overview](https://developer.android.com/google/play/integrity/overview)）。iOS は App Attest（DeviceCheck）で端末に結びつけた鍵でアプリを証明する。App Attest の鍵の証明（attestation）は、通常は利用者と端末ごとに 1 回で、Apple は、1 日 1,000 万人を超えない段階的な有効化と、全体で毎秒 100 回未満の呼び出しを勧める（[Preparing to use the App Attest service](https://developer.apple.com/documentation/devicecheck/preparing-to-use-the-app-attest-service)）。そこで、出庫のたびの確かめは、登録済みの鍵による assertion で行い、鍵の証明は端末の登録のときだけにする。S1 のドライバー 1 万台・1 日数回の出庫では、Play Integrity の既定の上限（1 日 1 万回）を超えうるので、E3 の前に引き上げを申請する。
- サービスの間の通信：ECS Service Connect は AWS Private CA の証明書で TLS 1.3 の暗号化を自動で行い、短い期限（7 日まで）の証明書を 5 日ごとに入れ替える。失効の仕組みは持たない（[Encrypt Amazon ECS Service Connect traffic](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/service-connect-tls.html)、2026-09-27 に確認）。同じ文書は、証明書の発行・入れ替え・配布と暗号化だけを説明し、呼び手の証明書による認証（相互の TLS）を説明しない（2026-09-27 に本文で確認）。そのため、呼び手の確かめは TLS に頼らず、サービスのトークンと RPC ごとの許可の一覧で行う（E1 の `service-identity-tokens`）。

## Options

### 認証

1. **利用者の種類ごとに発行者と鍵を分ける（乗客・ドライバー・事業者・運用）**
2. **1 つの認証の仕組みで、役割のクレームだけで分ける**

### 不正への処置

- a. **兆しの点数と規則で候補を出し、自動の処置は「配車の候補から外す」「特典を止める」「追加の確認を求める」までにする。利用の停止は人が決める**
- b. **点数が閾値を超えたら自動で利用を止める**

## Decision

認証は 1、処置は a を採用する。

- **乗客**：電話番号とワンタイムコード（[ADR-0031](0031-per-stream-sequence-redelivery-push-and-sms.md)）。パスキーを任意で足せる。アクセストークン 10 分、更新のトークン 30 日（使うたびに入れ替え、端末に結びつける）。
- **ドライバー**：事業者が登録した人に、事業者の管理画面から招待のコードを出す。ドライバーは招待のコードと、登録した電話番号へのワンタイムコードでアプリを有効にする。自分で登録する経路は作らない（ADR-0026）。出庫のたびに App Attest か Play Integrity の判定を確かめ、その日の最初の出庫では顔の照合も確かめる（ほかに 1 日 1 回の抜き打ち。[ADR-0029](0029-masked-communications-identity-and-ratings.md)。顔の照合は L4 の確認まで `legal.l4.driver_face_check` の裏で、その間は事業者の点呼に頼る）。通れば `driver_session_id` に結びつけたアクセストークン（10 分）を出す。入庫でセッションとトークンを無効にする。
- **事業者の管理画面**：メールとパスキーか TOTP の多要素を必須にする。大手の事業者には SAML の SSO を任意で出す。
- **運用**：IAM Identity Center の SSO と多要素。本番のデータを読む役割は、期限つきの承認（最長 4 時間）で得る。
- トークンの署名の鍵は種類ごとに分け（Ed25519、90 日ごとに入れ替え、`kid` で 24 時間並べる）、ある種類のトークンを別の API で使えないようにする。
- **サービスの間**：Service Connect の TLS で暗号化し、セキュリティグループで呼び手のサービスを絞る。呼び手の識別は、サービスごとの鍵で署名した 5 分のサービスのトークンを gRPC のメタデータに載せ、RPC ごとの許可の一覧（例：`FindNearby` は dispatch と eta だけ。[geospatial-index.md](../architecture/geospatial-index.md) の 9 節）で確かめる。
- **不正**：兆し（[security.md](../architecture/security.md) の 9 節）を 1 日 1 回と 10 分ごとに集計し、主体（ドライバー・乗客・端末・カードの指紋）ごとの点数にする。自動の処置は、位置の点を使わない、セッションを候補から外す、特典の適用を止める、カードの追加の認証（3-D セキュア）や電話番号の確認を求める、までにする。ドライバーの停止は事業者と運用が確かめてから（location-ingestion の 13 節と同じ）。乗客の停止は運用の 2 人の確認で行う。
- 2 を採らない理由：ドライバーの位置の API と、事業者の管理 API の間で、トークンの取り違えが権限の昇格になる。
- b を採らない理由：誤検知で、ドライバーの収入と乗客の移動を止める。本家も処置の前に人が確かめている。

## Consequences

- 良くなること：
  - ドライバーの位置と出庫が、事業者の登録・端末の完全性・顔の照合（1 日の最初と抜き打ち。L4 の後）の 3 つに結びつく。
  - 不正の処置の誤りが、利用の停止に直結しない。
- 引き受けるコスト：
  - 認証の発行者と鍵が 4 種類になる。
  - Play Integrity の 1 日の上限（既定 1 万回）は、S1 の出庫の回数（1 万台 × 1 日 1〜2 回）に近い。引き上げを申請する。
  - 不正の兆しの確認の担当が要る。

## Confirmation

- 結合テスト：乗客のトークンでドライバーの API、ドライバーのトークンで事業者の API を呼ぶと 401 になる。
- 結合テスト：端末の完全性の判定が失敗した端末は出庫できない。
- レビュー：不正の点数から、利用の停止を自動で行うコードを差し戻す。
- 本番の計測：出庫の完全性の失敗の率、不正の候補の件数と、人の確認で不正と判定した割合（誤検知の率）。
