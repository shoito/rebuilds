# ADR-0042: 配車と運賃の変更は、再生・シミュレーション・影の実行の関門を通し、都市とセルの単位の波で出す

詳細は [delivery.md](../architecture/delivery.md) の 3〜5 節。

## Context

配車と運賃の誤りは、エラーにならずに現れる。組が悪くなり迎車が延びる、運賃が 10 円ずれる、という形で。どちらも、単体のテストが通っても本番で初めて分かることがある。

- 配車は、記録した入力の再生、市場のシミュレーション、影の実行で比べると決めた（[ADR-0004](0004-batched-dispatch-and-offers.md)、[ADR-0015](0015-offer-protocol-decision-log-and-replay.md)）。関門の置き場所（CI・夜間・本番）と、設定の値の変更の扱いは、この領域に残された。
- 運賃の計算は、規則のバージョンを引数に取る純粋な関数で、見積もりと乗車にバージョンと入力のハッシュを残す（[ADR-0018](0018-versioned-fare-rules-and-integer-yen.md)）。コードの変更で過去の見積もりの額が変わらないことを、同じ方法で確かめられる。
- 規則のデータ（運賃の改定、係数）の変更は、デプロイではなく承認の流れで入る（ADR-0018）。
- 本家は、変更を小さな単位で少しずつ広げ、問題を見たら自動で戻す（[Up](https://www.uber.com/us/en/blog/up-portable-microservices-ready-for-the-cloud/)、2026-09-27 に確認）。

## Options

1. **変更の種類ごとに関門を決める（PR で再生・縮小のシミュレーション、本番で影の実行、都市・区域の単位のフラグで展開）**
2. **カナリアのデプロイ（一部のタスク）だけ**
3. **A/B テスト（乗客を分けて比べる）**

## Decision

1 を採用する。

| 変更 | PR の関門 | 本番に出す前 | 展開 |
| --- | --- | --- | --- |
| 配車の計算（`algorithm_version`） | 直近 7 日の再生、1 時間の縮小のシミュレーション。二重の割り当て 0 件 | 影の実行 1 週間（ADR-0015 の基準） | 区域単位の release フラグ：1 区域の 10% のバッチ → 100% → 他の区域 |
| 配車の設定（重み、周期、上限。AppConfig） | 直近 7 日の再生の結果を変更の要求に添える。AppConfig の検証の関数で範囲を確かめる | 影の実行は任意（重みの大きな変更は必須） | AppConfig の段階的な配備（区域ごと） |
| 候補の条件（営業区域、運行枠、商品の対応表） | 決定表のテスト（DT-DISP）、PROP-DISP-002・007 | — | データのバージョンの承認（2 人）と有効の日時 |
| 運賃の計算のコード | 公示の例のテスト、`fare-replay`：直近 30 日の見積もりを、同じ規則のバージョンで新しいコードで計算し直し、額の差 0 件（差を許す見積もりは PR に一覧で書く） | 影の計算 3 日（見積もりのたびに新旧を計算し、差を記録。乗客には出さない） | Pricing のデプロイ（カナリア） |
| 運賃の規則のデータ | 規則の型の検証、見本の乗車 100 件の試算を承認の画面に出す | — | 有効の日時（0 時の切り替え）。法務の確認待ちの規則は legal のフラグの裏（`legal_gate_records` の記録の範囲でだけ本番で有効。[ADR-0043](0043-flag-taxonomy-legal-gates-and-safety-defaults.md)） |
| Trips の遷移の表 | 決定表 DT-TRIP、性質ベーステスト、アプリの状態機械のベクター（[ADR-0006](0006-native-apps-contracts-vectors-and-release-train.md)） | — | 通常のデプロイ。アプリより先にサーバー |

- **S2 からの都市の波**：配備と設定の変更は、都市のセル（[ADR-0039](0039-city-cells-and-osaka-warm-standby.md)）の単位で、小さな都市 → 中の都市 → 東京の順に出す。各波の後 30 分、`dispatch_decision`・`offer_delivery`・成立率を見る（[ADR-0040](0040-per-city-slis-and-slos.md)）。
- **戻し**：配車の計算と設定は、フラグと AppConfig で 1 つ前のバージョンに戻す（デプロイを待たない）。運賃のコードは前のイメージで戻す。すでに確定した見積もりの額は変えない（見積もりはバージョンつき）。
- **凍結**：12/28〜1/3、予定の大きな催しの日、雨の予報で前もって広げた時間帯は、配車・運賃・Trips の変更を出さない（修正だけ）。ドライバーのアプリの段階の公開も、週末の夜は進めない（[rider-and-driver-apps.md](../architecture/rider-and-driver-apps.md) の 10.1 節）。
- 2 を採らない理由：配車は区域ごとに 1 つのタスクがバッチを解く（ADR-0011 のリース）。タスクの一部だけ新しくしても、区域の一部だけを比べられない。
- 3 を採らない理由：配車は同じ区域のドライバーを取り合うので、乗客を分けても 2 つの群れが干渉し、比べた結果が偏る。運賃を乗客ごとに変えることは、認可の運賃の外になりうる。

## Consequences

- 良くなること：
  - 配車と運賃の変更の効果と誤りが、本番の乗客に届く前に分かる。
  - 戻しがフラグと設定の単位で速い。
- 引き受けるコスト：
  - 再生・シミュレーション・`fare-replay` のために、記録（S3）を CI から読む権限と費用が要る。記録は位置を丸めたもので、個人の情報を含まない（ADR-0015）。
  - 影の実行のタスクの費用と、1 週間の待ち。

## Confirmation

- CI：配車の計算・設定・運賃のコードを変える PR で、再生・シミュレーション・`fare-replay` が動き、結果が PR に付く。二重の割り当てが 1 件、または許していない額の差が 1 件でもあれば失敗する。
- レビュー：影の実行の結果を添えずに、配車の計算の release フラグを本番で有効にする変更を差し戻す。
