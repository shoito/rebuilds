# Capacity: Uber

負荷のモデル（S1 の東京、雨・大晦日・台風・大雪）、部品ごとの必要量、受け入れの上限とパラメーター、負荷試験とシミュレーションの計画。台数と構成は [infrastructure.md](infrastructure.md) の 8 節、SLO は [observability.md](observability.md) の 6 節にある。

| ADR | 決定 |
| --- | --- |
| [0041](../decisions/0041-load-model-admission-control-and-prescaling.md) | 負荷は平常のピークに場面の倍率を掛けて見積もる。熱い経路は平常のピークの 2 倍を 1 AZ を失っても処理できる台数で常に持つ。依頼は都市ごとの未割り当ての上限で与信の前に断る。予定の催しと雨の予報で前もって広げる |

**ここの数値は、負荷試験（E3・E4・E5・E12）の前の初期見積もりである。** 仮定は表の中に書き、計測で置き換える。単価は [infrastructure.md](infrastructure.md) の 11 節。

## 1. 負荷のモデル（S1）

### 1.1 平常のピーク

[architecture/README.md](README.md) の 2 節の S1 の値から始める。

| 項目 | 値 | 仮定と根拠 |
| --- | --- | --- |
| オンラインの車両 | 1 万台 | README の S1 |
| 位置の受信 | 2,500 件/秒 | 1 万台 ÷ 4 秒 |
| 配車の依頼（受け付け） | 30 件/秒 | README の S1。**ピークに受け付ける依頼の数で、成立しない依頼（取り消し、`no_driver_found`、選び直し）を含む**（2026-09-27 の定義。2026-09-28 に確定） |
| 見積もり | 90 件/秒 | 依頼 1 件に見積もり 3 回（乗車地・降車地の選び直し。仮定） |
| 同時の有効な乗車（割り当て済み） | 5,000 | オンラインの車両の 5 割がアプリの乗車（残りは空車・流し・休憩。仮定） |
| 成立する乗車（受諾から完了まで進む乗車） | 約 3〜6 件/秒 | 同時の乗車 5,000〜1 万 ÷ 1 乗車の拘束の時間（迎車 7 分 ＋ 乗車 20 分 ＝ 約 1,620 秒。仮定）。リトルの法則。下限は 5 割がアプリの乗車、上限は全車がアプリの乗車 |
| 遷移のコミット | 約 180 件/秒 | 受け付け 30 件/秒 × 約 4 回（作成、与信の結果、`no_driver_found`・取り消し、タイマー）＋ 成立 6 件/秒 × 約 10 回（オファーの試み、受諾から完了までの遷移） |
| 常時の接続 | 約 3 万 | ドライバー 1 万＋乗客 2 万（[notifications-and-realtime-push.md](notifications-and-realtime-push.md) の 9 節） |
| 車の位置の配信 | 最大 5,000 件/秒 | 同上 |

- **2 つの量を分ける**（2026-09-27 の決定）：README の 30 件/秒は **受け付けの量**（組を作れない依頼を含む）である。1 万台で 1 乗車に約 27 分かかるので、**成立する乗車は約 3〜6 件/秒** になる。量ごとに使う値を次のように分ける。この定義は 2026-09-28 に確定した（[README.md](README.md) の 7 節）。提携先の車両の数が分かったら、量を見直す。

| 使う値 | 当てはまるもの |
| --- | --- |
| 受け付けの量（30 件/秒、常に持つ量で 60 件/秒） | 受け入れの上限、見積もり、与信（依頼のときに与信する）と与信の取り消し、配車のバッチの依頼、ETA の行列、Trips の作成と与信の遷移 |
| 成立の量（約 3〜6 件/秒、常に持つ量で 12 件/秒） | 受諾の時点の ETA、迎車中・乗車中の遷移、売上の確定、台帳の仕訳、乗車の軌跡、精算の明細の行 |

### 1.2 場面の倍率

| 場面 | 依頼の倍率 | 位置の倍率 | 根拠 |
| --- | --- | --- | --- |
| 平常のピーク（金曜の夜） | 1 | 1 | README |
| 雨 | 1.6 | 1.2（日本版ライドシェアの雨天の拡大、[ADR-0027](../decisions/0027-rideshare-operating-windows.md)） | 日本交通の広報は、雨の日は晴れの日より 5〜6 割増えると説明する（[ウェザーニュース](https://weathernews.jp/s/topics/201802/020165/)、2018-02-28、2026-09-27 に確認）。数えたものの定義は **未検証**（E12 の `prescale-schedules` で自前の実績に置き換える） |
| 大晦日（0〜3 時） | 2 | 1 | 本家の SRE は、ハロウィンと大晦日は 50〜100% 多いと説明する（[AWS Startups Blog](https://aws.amazon.com/blogs/startups/how-uber-survives-its-busiest-nights-of-the-year/)、2017-12-14、2026-09-27 に確認）。日本の大晦日に当てはまるかは **未検証**（E12 の `prescale-schedules` で自前の実績に置き換える） |
| 台風 | 9 | 0.8（出庫が減る。仮定） | 同じウェザーニュースの記事（2017 年 10 月の台風で通常の 9 倍） |
| 大雪 | 40 | 0.7（仮定） | 同じ記事（2014 年 2 月の大雪で通常の 30〜40 倍） |

- 倍率が効くのは、依頼の受け付け・見積もり・常時の接続（乗客）である。位置・索引・配車のバッチの量は、オンラインの車両の数で上限が決まる。
- 供給は増えないので、倍率の大きい場面は「組を作れない依頼の山」になる。受け入れの上限（4 節）で止める。

## 4. 受け入れの上限

[ADR-0041](../decisions/0041-load-model-admission-control-and-prescaling.md) による。

```
依頼（与信の前）
  ├─ 都市の未割り当ての数 < 上限 → 与信 → requested
  └─ それ以外 → 429「混み合っています」（Retry-After 60〜120 秒の揺らぎ）。需要として記録
```

| パラメーター | 既定 | 理由 |
| --- | --- | --- |
| 都市の未割り当ての依頼の上限 | オンラインの空車 × 0.5、最低 200、最大 5,000 | 3 分で組を作れる見込みのある量。上限の値は市場のシミュレーションで決める（**未検証**。E5 の `market-simulator` と `intake-admission-control`） |
| 1 回のバッチに入れる依頼 | `min(未割り当て, 空車 × 2, 500)`、待ちの長い順 | 最適化と ETA の量を抑える |
| 見積もりのキャッシュ | 同じ乗客・同じ乗降（`spot`）で 60 秒 | 選び直しの連打 |
| 乗客ごとの見積もり | 1 分 10 回 | 同上 |
| 推計走行距離の提供者の呼び出し | 都市ごとに毎秒 100 回（契約の上限の 80%。**未検証**。E4 の `fare-distance-provider-adapter` で契約から決める） | 超えたら事前確定運賃を出さず、メーターの目安だけを出す（[ADR-0017](../decisions/0017-fare-distance-for-pre-fixed-fares.md) の障害のときと同じ振る舞い） |
| 断らないもの | 進行中の乗車の操作、緊急の入口、ドライバーの出庫と位置 | — |

- 上限の数は Valkey `cache` の都市ごとの数で持ち、Trips の `requested` の数と 1 分ごとに照合する。
- 断った依頼は、需要の記録（都市・セル・時刻）として残し、需要の予測と成立率の分母の定義に使う（quality.md）。

## 6. 前もって広げる

| きっかけ | 時間 | 広げるもの | 量 |
| --- | --- | --- | --- |
| 大晦日 | 12/31 20:00〜1/1 04:00 | valhalla-eta、api、rt-gateway、trips | 平常のピークの 3 倍の台数 |
| 花火大会など予定の催し（運用が登録） | 開始の 2 時間前から終了の 2 時間後 | 同上 | 催しの規模で 2〜3 倍 |
| 1 時間 5 mm 以上の雨の予報（S1 は運用が手で、S2 で予報の取り込み） | 予報の時間の 2 時間前から | 同上 | 2 倍 |
| 台風・大雪の予報 | 前日 | 同上、受け入れの上限の確認 | 3 倍（受け入れの上限で断る前提） |

- Valhalla の起動は遅いと見込むので（**未検証**。E4 の `valhalla-pool-fargate` で計る）、自動の拡大に頼らない（[ADR-0038](../decisions/0038-compute-on-fargate-and-data-stores.md)）。
- 予定の拡大は ECS のスケジュールされた拡大で入れ、runbook `prescale-for-events.md`（[infrastructure.md](infrastructure.md) の 14 節）で確かめる。

## 7. 負荷試験とシミュレーションの計画

staging を本番と同じ台数に広げて行う。E12 のリリースの基準にする。

### 7.1 道具

| 道具 | 使いどころ |
| --- | --- |
| `loc-loadgen`（Go） | 合成のドライバー 1〜2 万台。Valhalla の経路の上を動き、4 秒ごとに `LocationBatch` を送る。通信の断・跳び・トンネル・模擬の位置・`backlog` を乱数で混ぜる（[location-ingestion.md](location-ingestion.md) の 14.3 節） |
| `rider-loadgen`（Go） | 合成の乗客。見積もり、依頼、常時の接続（gRPC）、取り消し。場面の倍率で依頼を出す |
| `driver-bot`（Go） | オファーを受け、受諾・辞退・時間切れを確率で返し、迎車・乗車・降車の遷移を送る |
| 市場のシミュレーション | [ADR-0015](../decisions/0015-offer-protocol-decision-log-and-replay.md) の仮の時計の都市。受け入れの上限とバッチの大きさの値を決める |
| PSP の模擬 | 遅れ・失敗・結果不明を注入する |
| AWS FIS | タスクの停止、AZ の切り離し、Aurora のフェイルオーバー |

- 実在の人の軌跡を使わない。需要は合成か、丸めて匿名化した記録だけ（[AGENTS.md](../../AGENTS.md)）。

### 7.2 シナリオ

| # | シナリオ | 負荷 | 合格の基準 |
| --- | --- | --- | --- |
| L1 | 平常の 2 倍の定常 | 位置 5,000/秒、依頼 60/秒、見積もり 180/秒、接続 6 万を 2 時間 | NFR-001（p95 3 秒、p99 5 秒）、NFR-002（p99 1 秒）、`trip_transition` 99.95%、Aurora `core` の CPU 60% 以下、Go の GC の停止を含む p99（ADR-0001） |
| L2 | 雨 | 依頼 ×1.6、位置 ×1.2、2 時間 | L1 と同じ |
| L3 | 大晦日の 0 時 | 23:59 に依頼を 30/秒から 60/秒へ段で上げる | 段の後 1 分で NFR-001 に戻る、429 は 0 |
| L4 | 大雪 | 依頼の受け付け 1,200/秒を 30 分 | 受け入れの上限が働く、断る応答の p99 100 ms、進行中の乗車の `trip_transition` 99.95%、緊急の入口の応答、推計走行距離の呼び出しが上限の中 |
| L5 | 再接続の殺到 | 1 万台が同時に切れて 15 分後に戻り、900 点ずつ `backlog` を送る | 平常の点の NFR-002、`backlog` の流し切り 30 分以内 |
| L6 | AZ の障害 | L1 の最中に 1 AZ を切り離す | `dispatch_decision` の悪い事象が 5 分で平常、乗車の記録の損失 0、二重の割り当て 0 |
| L7 | 索引の主と待機の停止 | L1 の最中に両方を止める | `READY` まで 15 秒、その間の依頼が失われない |
| L8 | Valhalla の遅れ | 行列に 300 ms の遅れを注入 | 概算への切り替え、NFR-001 の p99 5 秒 |
| L9 | PSP の障害 | 与信の 50% を時間切れにする | タクシーは車内払いへ案内、日本版ライドシェアは受けない、結果不明の照会、二重の請求 0 |
| L10 | デプロイ中の負荷 | L1 の最中に geo-index・dispatch・loc-ingest・rt-gateway を入れ替える | `dispatch_decision` の悪い事象の増加なし、リースの引き継ぎ 1 回で済む |
| L11 | 大阪への切り替え | L1 の半分の負荷で、Aurora の複製を止めて 30 秒後に切り替え | RPO 1 分、RTO 30 分、戻した乗車の数と食い違いを記録（[runbooks/disaster-recovery.md](../runbooks/disaster-recovery.md)） |

- 各シナリオで、見積もり（1〜5 節）と実測を並べ、この文書の数値を置き換える。
- 市場のシミュレーションは、夜間に平常・雨・大雪の 3 つの需要で 1 日分を流し、受け入れの上限あり・なしで成立率と迎車の時間を比べる。
