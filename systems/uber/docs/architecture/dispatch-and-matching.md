# Dispatch and matching: Uber

配車の依頼とドライバーを組み合わせる仕組み。区域ごとの 2 秒のバッチ、候補の絞り込み（車両の種類、事業者と営業区域、日本版ライドシェアの運行枠）、最小費用の割り当てと貪欲法への切り替え、1 人ずつのオファー（表示 15 秒、サーバーの期限 16.5 秒）、流しの乗車との両立、判断の記録と再生・シミュレーション・影の実行を決める。

前提となる決定は、割り当ての正本は Trips で fencing token（`assignment_epoch`）と DB の一意の制約が守る（[ADR-0003](../decisions/0003-trip-state-and-single-assignment.md)）、区域ごとの短いバッチと 1 人ずつのオファー（[ADR-0004](../decisions/0004-batched-dispatch-and-offers.md)）、索引の検索（[geospatial-index.md](geospatial-index.md)、[ADR-0012](../decisions/0012-geo-index-nearby-query-api.md)）、ETA の行列（[eta-and-routing.md](eta-and-routing.md)）、NFR-001（配車の判断の速さ）と NFR-005（割り当ての一意性）。この文書で決めたことは次の ADR にある。

| ADR | 決定 |
| --- | --- |
| [0013](../decisions/0013-batch-assignment-solver.md) | 区域ごとに 2 秒のバッチで、迎車の ETA を主にしたコストの最小の割り当てを、長方形の最短増加路法（Jonker–Volgenant 型）で解く。解けない依頼を表すダミーの列のコストは待ちとともに上がる。計算が 300 ms を超えたら貪欲法の結果を使う。同じ入力と種から同じ結果を出す |
| [0014](../decisions/0014-dispatch-eligibility-and-street-hails.md) | 候補の条件は、サービスの種類（日本版ライドシェアは乗客の承諾・事前確定運賃・キャッシュレス・降車地の確定が要る）、車両、席、営業区域（発地か着地が営業区域の中）、運行枠、鮮度、除外、迎車の ETA の上限を、版つきのデータで判定する。流しの実車はドライバーの操作かメーターで索引から外し、日本版ライドシェアのドライバーには流しの操作を置かない |
| [0015](../decisions/0015-offer-protocol-decision-log-and-replay.md) | オファーは Trips が作り、表示は 15 秒、サーバーの期限は 16.5 秒。5 秒で端末の受信の確認がなければ取り下げる。時間切れが 2 回続いたドライバーは休憩にする。バッチごとの入力と結果を記録し（位置は解像度 10 に丸め、180 日）、再生・市場のシミュレーション・影の実行で変更を比べる |

## 1. 目的と範囲

- 扱う：区域とバッチの周期、配車のプロセスの持ち主、候補の絞り込み、コストと最適化、貪欲法への切り替え、Trips への提案、オファーの手順と時間切れ、流しとの両立、判断の記録、再生、シミュレーション、影の実行。
- 扱わない：乗車の状態機械と割り当ての確定（`trips-lifecycle.md`。この文書は Trips に求める振る舞いだけを書く）、ETA の求め方（[eta-and-routing.md](eta-and-routing.md)）、運行枠と事業者の属性の登録（`supply-and-operators.md`）、オファーの端末への配信（`notifications-and-realtime-push.md`）、運賃（`pricing-and-fares.md`）、機能の展開のフラグと影の実行の基盤（`delivery.md`）。

- **日本版ライドシェア**：運送の主体はタクシー事業者。発着地が引受けの時点で決まっていること、利用者の事前の承諾、運賃はタクシーの事前確定運賃に準ずること、支払いは原則キャッシュレス。国土交通省が、不足する地域・時期・時間帯と台数を指定する（[東北運輸局の資料](https://wwwtb.mlit.go.jp/tohoku/content/000338889.pdf)、2024-11-21。[intent.md](../intent.md) の「日本の制度」）。

## 3. 構成と 1 回のバッチ

```
Trips ──（trip.requested・offer の結果・取り消し）──▶ dispatch（区域のリースを持つタスク）
                                                     │ 2 秒ごと
                                                     ├─ 1. 未割り当ての依頼の集合（Trips の写し）
                                                     ├─ 2. geo-index.FindNearby（依頼ごと、同じ写しの generation）
                                                     ├─ 3. 候補の条件（5 節、版つきのデータ）
                                                     ├─ 4. ETA（many-to-one、依頼ごと。eta-and-routing の 4.1 節）
                                                     ├─ 5. コストの行列と最小の割り当て（6 節）
                                                     ├─ 6. Trips.ProposeOffer（組ごと、並列）
                                                     └─ 7. 判断の記録（9 節）
```

| 段 | 予算（p99） | 超えたとき |
| --- | --- | --- |
| バッチの待ち | 最大 2,000 ms（平均 1,000 ms） | — |
| 2. 候補の検索 | 100 ms（待機への切り替えを含め 200 ms） | その依頼をこのバッチから外す |
| 4. ETA | 400 ms | 直線の距離からの概算（[eta-and-routing.md](eta-and-routing.md) の 4.1 節）。記録に印を付ける |
| 5. 最適化 | 300 ms | 貪欲法の結果（6.3 節） |
| 6. 提案 | 200 ms | その組を次のバッチに戻す |

- 合計の最悪は約 3.1 秒で、NFR-001（受付から最初のオファーの送信まで p95 3 秒、p99 5 秒）の p95 はバッチの待ちが平均 1 秒なので満たす見込み。
- 区域の未割り当ての依頼が 1 件だけで、前のバッチから 500 ms 以上たっていれば、次の締めを待たずに解く（ADR-0004）。

## 4. 区域と配車のプロセスの持ち主

- **区域**：S1 は東京（特別区・武三交通圏を含む）を 1 区域にする。1 回のバッチの依頼が 200 件を超えるようになったら、解像度 6 のセルの集まりで区域を分ける（S2）。区域の境目の依頼は、候補の検索の半径が隣の区域に及んでも、隣の区域のバッチとドライバーを取り合いうる。取り合いは Trips が epoch で片方を拒否して終わる（正しさは崩れない）。
- **持ち主**：区域ごとに 1 つのタスクが配車のリースを持つ。リースの仕組みは索引と同じ（DynamoDB の `geo_shard_leases` に `dispatch/<zone>` の項目。[geospatial-index.md](geospatial-index.md) の 5.2 節）。
- リースは正しさの前提ではない。2 つのタスクが同時にバッチを解いても、同じドライバーへの 2 つ目の提案は Trips で拒否される（ADR-0003）。リースは、無駄な提案と、ドライバーへの二重のオファーの試みを減らすためにある。
- 待機のタスクは、Trips の事象を読んで未割り当ての依頼の集合を温めておき、リースを取ったらすぐにバッチを始める。
- 依頼ごとの試したドライバーの一覧は、Trips のオファーの履歴を正本にする。配車のタスクは写しを持つだけで、引き継ぎのときは Trips から読み直す。

## 5. 候補の条件

索引の `FindNearby` は、車両・サービスの種類・事業者・席・除外の一覧で粗く絞る（[geospatial-index.md](geospatial-index.md) の 6.1 節）。配車は、残った候補に次の条件をすべて当てはめる。どれかに反した組は、コストの行列で解けない組（∞）にする。

| # | 条件 | 判定の元 |
| --- | --- | --- |
| E1 | **サービスの種類**：タクシーは常に可。日本版ライドシェアのドライバーは、(a) 乗客が日本版ライドシェアの車での運送を承諾している、(b) 運賃が事前確定運賃（またはそれに準ずる運賃）、(c) 支払いがキャッシュレス、(d) 降車地が依頼の時点で決まっている、のすべてを満たす依頼にだけ | 依頼、Pricing の見積もり |
| E2 | **車両の種類**：依頼の商品に合う車両（例：標準 → 標準・大型、UD（車いす対応）→ UD だけ） | 商品と車両の対応表（版つき） |
| E3 | **席と設備**：人数 ≤ 席の数。車いす → UD | 依頼、車両 |
| E4 | **営業区域**：ドライバーの事業者の営業区域が、乗車地か降車地を含む（道路運送法第 20 条）。降車地のない依頼（メーターの運賃）は、乗車地が営業区域の中であること | 営業区域の多角形（[maps-and-geodata.md](maps-and-geodata.md) の 9 節）、事業者の営業区域 |
| E5 | **日本版ライドシェアの運行枠**：オファーを作る時刻が、そのドライバーの事業者の運行枠（区域・曜日・時間帯）の中にあり、迎車の到着の見込みも枠の終わりより前 | 運行枠（`supply-and-operators.md` が版つきで持つ） |
| E6 | **鮮度と信頼**：位置が 15 秒以内、`LOCATION_UNTRUSTED` でない | 索引 |
| E7 | **除外**：この依頼で辞退・時間切れ・取り下げになったドライバー。乗客とドライバーの間の拒否の一覧（安全の通報など） | Trips のオファーの履歴、`safety-and-trust.md` の一覧 |
| E8 | **迎車の ETA の上限**：既定 15 分（区域ごとの設定） | ETA |
| E9 | **事業者の停止**：運行管理者が停止した車両・ドライバー、書類の期限切れ | 供給の属性（索引の `EligibilityVer`） |

- 条件の判定は、依頼・候補・データの版を引数に取る純粋な関数にする。使ったデータの版（商品の対応表、営業区域、運行枠）を判断の記録に残す。
- E1 の (a)〜(d) と E5 の中身（運行枠の時刻の境目の扱い、枠の終わりをまたぐ運行）は、日本版ライドシェアの制度に依る。法務の確認が済むまで、日本版ライドシェアのドライバーを候補に入れる経路は `legal.l2.rideshare_dispatch`・`legal.l5.rideshare_drivers` の裏に置く（[intent.md](../intent.md) の L2・L5、[delivery.md](delivery.md) の 6.2 節）。
- 運行枠の台数の上限（国土交通省が指定する台数）は、出庫（オンライン）の時点で供給の側が守る。配車はその結果（オンラインであること）だけを使う。

## 6. 最適化

### 6.1 コスト

依頼 i とドライバー j の組のコスト（秒）：

```
c[i][j] = eta[i][j] + p[j]          （E1〜E9 をすべて満たすとき）
        = ∞                          （それ以外）
u[i]    = U0 + γ · wait[i]           （依頼 i をこのバッチで割り当てないときのコスト。ダミーの列）
```

| 記号 | 意味 | 既定 |
| --- | --- | --- |
| `eta[i][j]` | 迎車の ETA（秒） | [eta-and-routing.md](eta-and-routing.md) |
| `p[j]` | ドライバーの罰則。直前 30 分の時間切れ 1 回ごとに 60 秒 | 60 |
| `U0` | 割り当てないことの基本のコスト | 900（E8 の上限と同じ） |
| `γ` | 待ちの重み | 1.0 |
| `wait[i]` | 依頼からの経過（秒） | — |

- `U0` を E8 の上限と同じにしたので、条件に合う空いたドライバーがいれば、依頼は必ず割り当てられる。ドライバーが足りないときは、待ちの長い依頼ほど `u[i]` が大きく、先に割り当てられる。
- ドライバーの空車の時間の公平さの項（空車の長いドライバーを優先する）は、S1 では重み 0 にする。再生とシミュレーションで効果を見てから入れる。
- 重みはすべて設定の値（AppConfig、区域ごと、版つき）。変えるときは 9 節の再生とシミュレーションを添える。

### 6.2 解き方

- 行 ＝ 依頼（n）、列 ＝ 候補のドライバーの和集合（m）＋ 依頼ごとのダミー（n）の長方形の割り当て問題を、行ごとに最短増加路を求める方式（Jonker–Volgenant 型、Dijkstra とポテンシャル）で解く。計算量は O(n² · (m + n)) 程度。
  - S1 のピーク：n ≒ 60（30 件/秒 × 2 秒）、m ≤ 600 で、数百万回の演算。数 ms を見込む（**未検証**。E5 の `solver-benchmark-500` で計る）。
- ∞ の組は辺を張らない（疎な行列として扱う）。
- 行と列は ID の順に並べ、同じコストの組は、バッチの種（`seed = hash(zone, batch_id)`）から作った順序で決める。同じ入力と同じ種から同じ結果を出す（[AGENTS.md](../../AGENTS.md)）。
- 時刻・乱数・ETA は引数で受け取り、関数の中で時計を読まない。

### 6.3 貪欲法への切り替え

- 最適化が 300 ms を超えた、または内部の誤り（数値の異常、パニック）が起きたら、同じコストで貪欲法の結果を使う：解ける組をコストの小さい順に並べ、依頼とドライバーの両方が空いていれば採る。
- 貪欲法に切り替えた割合を計り、1 時間に 1% を超えたら警告する。区域を分ける合図にする。
- バッチの計算の結果が得られなかったときは、そのバッチを飛ばす。依頼は次のバッチに残る。

### 6.4 Trips への提案

```proto
rpc ProposeOffer(ProposeOfferRequest) returns (ProposeOfferResponse);

message ProposeOfferRequest {
  string trip_id = 1;
  uint64 trip_version = 2;       // バッチが見た乗車の版
  string driver_id = 3;
  uint64 assignment_epoch = 4;   // 索引から読んだ値（ADR-0003）
  uint64 region_gen = 8;         // 索引から読んだ世代（ADR-0039）。比較は (region_gen, assignment_epoch)
  string decision_id = 5;        // <zone>/<batch_id>
  uint32 pickup_eta_s = 6;
  string eta_source = 7;         // valhalla:<tile_version> / fallback
}

message ProposeOfferResponse {
  oneof result {
    string offer_id = 1;
    RejectReason rejected = 2;   // EPOCH_MISMATCH、TRIP_STATE_CHANGED、DRIVER_NOT_AVAILABLE、NOT_ELIGIBLE、CONSTRAINT_VIOLATION
  }
}
```

- 提案は組ごとに並列に送る。拒否された組の依頼は次のバッチに戻る。ドライバーは、このバッチでは使わない。
- `CONSTRAINT_VIOLATION`（DB の一意の制約で止まった）は、配車の不具合か持ち主の二重を示す。1 件ごとに記録し、警告を出す。
- 条件の判定の正本は配車にある（ADR-0014）。Trips は割り当ての一意性と状態の遷移を守り、防御として提案の時に供給・営業区域・運行枠を確かめ直す（2026-09-27 の決定。[trips-lifecycle.md](trips-lifecycle.md) の 4.3 節）。落ちたら `NOT_ELIGIBLE` を返す。2 つの実装（Go と TypeScript）は、同じ版のデータと、共通のテストのベクター（12.2 節の DT-DISP-001）で食い違いを防ぐ。
- `NOT_ELIGIBLE` が出るのは、索引の写し（`eligibility_ver`）が古いか、2 つの実装が食い違ったときである。件数を理由ごとに数え、ベクターにない食い違いが見つかったら表に行を足す。

## 7. 流しの乗車との両立

タクシーは、アプリの配車の合間に、流しや乗り場で客を乗せる（ADR-0004）。空車・実車の状態がずれると、実車の車にオファーが届く。

| 場面 | 振る舞い |
| --- | --- |
| タクシーのドライバーが流しで客を乗せた | アプリの「実車」を押す（`HIRED_STREET`）。メーターと連携している事業者では、メーターの実車の信号で自動に切り替える。索引は空車から外す（[geospatial-index.md](geospatial-index.md) の 4.2 節） |
| 「実車」を押したときにオファーが出ていた | オファーを理由 `street_hail` で自動に辞退する。ドライバーの操作は 1 回で済む |
| 受諾の後（迎車中）に「実車」を押した | 押せない。流しの客を乗せるなら、先にドライバーが取り消す。取り消しは終端にならず、乗車は `requested` に戻って優先して再配車される（割り当ては `driver_cancelled` で解放。[trips-lifecycle.md](trips-lifecycle.md) の 3.3 節の行 22）。終端の `cancelled_by_driver` になるのは、理由が安全・乗客の迷惑行為のときだけ |
| 降車の後 | アプリの「空車」か、メーターの空車の信号で戻る |
| メーターが実車なのに、アプリは迎車中 | 配車の乗客を乗せたのか、別の客かを、アプリがドライバーに確かめる。確かめられなければ、運用の指標に数える |
| 「実車」の押し忘れ（実車なのに空車のまま） | オファーが辞退か時間切れになる。時間切れが 2 回続いたら自動で休憩にする（8.3 節） |
| 日本版ライドシェアのドライバー | 流しで客を乗せられない（発着地が引受けの時点で決まっている必要がある）。アプリに「実車」の操作を置かない。**流しの実車の切り替えはタクシーだけ** |

- 乗り場の待機場（空港のタクシープールなど）にいるドライバーを候補に入れるかは、事業者と乗り場の規則による。待機場の多角形（[maps-and-geodata.md](maps-and-geodata.md) の 9 節の `taxi_pool`）に入っているドライバーを除く設定を、区域ごとに持つ。既定は除く。
- メーターとの連携の方式（車載の機器から受け取るか）は未確定（[intent.md](../intent.md) の Open questions）。連携がない事業者では、ドライバーの操作だけに頼る。

## 8. オファーの手順

### 8.1 流れ

```
dispatch ──ProposeOffer──▶ Trips（offered、offer_id、期限 = 作成 + 16.5 秒、trip_timers）
Trips ──outbox──▶ リアルタイムの配信 ──▶ ドライバーのアプリ（OfferCreated）
ドライバーのアプリ ──OfferDelivered(offer_id)──▶ Trips（受信の確認。受信までの時間を記録）
ドライバーのアプリ ──AcceptOffer(offer_id, assignment_epoch) / DeclineOffer(offer_id, reason)──▶ Trips
Trips ──（accepted / 次のバッチへ）──▶ dispatch、両方のアプリ
```

| 事象 | Trips の振る舞い |
| --- | --- |
| 受諾（期限の中、epoch が一致） | `accepted`。同じ `offer_id` の受諾の送り直しには同じ結果を返す（冪等） |
| 受諾（期限の後・取り下げの後・epoch の不一致） | 拒否し、アプリに「このオファーは無効」と今の状態を返す |
| 辞退 | 依頼を次のバッチに戻す。ドライバーを E7 の除外に入れる |
| 5 秒たっても `OfferDelivered` がない | オファーを取り下げる（`undelivered`）。ドライバーの罰則にしない。依頼を次のバッチに戻す |
| 期限（16.5 秒） | 時間切れ。依頼を次のバッチに戻す。ドライバーに罰則（6.1 節の `p[j]`） |
| オファー中に乗客が取り消した | オファーを取り下げ、ドライバーに `OfferRevoked` を送る |
| 依頼から 3 分、または 10 回のオファーで成立しない | `no_driver_found`（ADR-0004） |

### 8.2 時間

- アプリは、受け取った時から 15 秒の残り時間を出す（端末の時計の時刻ではなく、受け取ってからの経過で数える）。
- サーバーの期限は 15 秒 ＋ 猶予 1.5 秒（配信の遅れと、受諾の送信の遅れの分）。期限は Trips の `trip_timers` の 1 行で、Trips が 1 か所で決める。
- 配信が遅れて 15 秒のうちの数秒を失うことがある。受信までの時間の p95 を計り（NFR-008 の 2 秒の範囲を見込む）、延びたら猶予を見直す。

### 8.3 自動の休憩

- 時間切れが 2 回続いたドライバーは、サーバーが休憩にする（供給の側の `paused_by_system`。索引から外れる）。アプリは「応答がなかったので休憩にしました」と出し、ドライバーが押すと空車に戻る。
- 目的は、アプリを開いたまま車を離れたドライバーや、実車の押し忘れに、オファーを送り続けないこと。

### 8.4 オファーに見せる中身

- 乗車地（正確な位置。受諾すれば迎車するので、相手としての範囲に入れる）、迎車の ETA、運賃の種類（メーター・事前確定運賃）、乗客の評価の要約。
- **降車地は、受諾の後に見せる（既定）。** タクシーには運送の引受けの義務があり、降車地を見て選ぶことが乗車の拒否に当たりうるため（道路運送法第 13 条は、約款によらない申込み、設備がない、法令に反するなど 6 つの場合を除いて、運送の引受けの拒絶を禁じる。[e-Gov 法令検索](https://laws.e-gov.go.jp/law/326AC0000000183)、2026-09-27 に本文を確認。降車地を見せることとの関係は法務の確認待ち（[intent.md](../intent.md) の L1））。日本版ライドシェアでは、発着地が引受けの時点で決まっていることが条件なので、降車地を見せる必要がありうる。扱いは法務の結論で決める。

## 9. 判断の記録・再生・シミュレーション・影の実行

### 9.1 判断の記録

バッチごとに 1 件の `DispatchBatchRecord` を書く。本番の判断を、同じ入力から再現できるようにする（ADR-0004）。

```proto
message DispatchBatchRecord {
  string zone = 1; string batch_id = 2; int64 started_at_ms = 3;
  uint64 seed = 4;
  string algorithm_version = 5; string config_version = 6;
  uint64 index_generation = 7; uint64 index_lease_epoch = 8;
  repeated DataVersion data_versions = 9;     // 商品の対応表、営業区域、運行枠、タイル
  repeated RequestInput requests = 10;        // trip_id、trip_version、created_at、乗車地・降車地の解像度 10 のセル、商品、条件の入力
  repeated CandidateInput candidates = 11;    // driver_id、解像度 10 のセル、epoch、属性、条件の判定の結果（理由のコード）
  repeated EtaValue etas = 12;                // (i, j, eta_s, source)
  repeated Pair result = 13;                  // 採った組とコスト
  bool greedy_fallback = 14;
  uint32 solve_ms = 15;
  repeated ProposalOutcome proposals = 16;    // offer_id か拒否の理由
}
```

- 位置は解像度 10 のセル（辺 約 76 m）に丸める。ETA の値を記録するので、配車の計算の再現には正確な位置は要らない。
- 置き場所：Firehose から S3 の `dispatch-decisions/`（位置の専用の KMS の鍵）。保持は 180 日。乗客の名前・電話番号を含めない（`trip_id` だけ）。
- 量：S1 で 1 秒に 0.5 件、1 件数十 KB。

### 9.2 再生（decision replay）

- `dispatch-replay --zone --from --to --algo <新しい版>`：記録した入力を、新旧の計算に流し、組の違いと指標を出す。ETA は記録の値を使う。ETA の変更を評価するときだけ、記録のセルの中心から ETA を求め直す。
- 指標：割り当ての数、迎車の ETA の合計と平均、貪欲法への切り替えの率、計算の時間の p99、1 人のドライバーへの二重の使用（0 件であること）。
- 配車の計算を変える PR には、直近 7 日の再生の結果を添える（[AGENTS.md](../../AGENTS.md)）。

### 9.3 市場のシミュレーション

再生は「同じ入力への判断」しか比べられない。判断が変わると、その後の需給（どのドライバーが空くか）も変わる。そこで、仮の時計で 1 日の都市を早回しで動かす。

| 部品 | 中身 |
| --- | --- |
| 需要 | 記録した依頼の時刻と乗降のセル（解像度 10）、または合成の需要 |
| 供給 | `supply-heat` の初期の分布、出庫・入庫・休憩の確率 |
| 動き | Valhalla の経路の上を、時間帯の速度で動かす |
| ドライバーの振る舞い | 迎車の ETA ごとの受諾の確率（実績から推定）、流しの乗車の発生（セル × 時間帯のポアソン過程、仮定の値） |
| Trips | 状態の遷移と一意の制約の模型。遷移は Trips の決定表のテストのベクター（[ADR-0001](../decisions/0001-platform-and-stack.md)）と一致させる |
| 障害 | 配車のタスクの二重、提案の重複、受諾の遅れ、取り消しとの競合、索引の遅れ |

- 同じ種から同じ結果を出す。CI では 1 時間分の縮小版を毎回、夜間に 1 日分を複数の種で流す。
- 指標：配車の成立率（3 分以内の受諾）、迎車の時間、ドライバーの空車の時間、辞退・時間切れの率、**二重の割り当ての件数（0 件でなければ失敗）**。

### 9.4 影の実行

- 新しい計算は、本番の区域で、同じ `DispatchBatchRecord` の入力（候補と ETA の後）を受け取る別のタスクで動かし、結果を記録するだけで提案しない。
- 比べる指標：組の一致の率、迎車の ETA の合計の差、計算の時間。1 週間の影の実行で指標が基準（下）を満たしたら、区域単位のフラグで一部のバッチに切り替える。展開の仕組みは `delivery.md`。
- 影のタスクは、本番のバッチの予算に影響しないよう、別のタスクにし、遅れても捨てる。

| 基準（変更の前と比べて） | 値 |
| --- | --- |
| 二重の割り当て | 0 件 |
| 配車の成立率 | −0.5 ポイントより悪くない |
| 迎車の ETA の平均 | +3% より悪くない |
| 計算の時間の p99 | 300 ms 以内 |

## 10. 障害のときの振る舞い

| 障害 | 起きること | 回復・影響の抑え方 |
| --- | --- | --- |
| 配車のタスクが落ちた | その区域のバッチが止まる | 待機がリースを取り（最大約 6.5 秒）、Trips から未割り当ての依頼と試したドライバーを読み直して続ける |
| 配車のタスクが 2 つ動く | 同じドライバーへの提案が 2 回 | Trips が epoch と一意の制約で片方を拒否する。`EPOCH_MISMATCH` の率で気づく |
| 索引が答えない（主も待機も） | 候補が出ない | バッチを飛ばす。依頼は 3 分まで残る。再構築を待つ（[geospatial-index.md](geospatial-index.md) の 5.4 節） |
| ETA が遅い・答えない | 行列が揃わない | 直線の距離からの概算で解き、記録に印を付ける。概算の割合が 10% を超えたら警告 |
| 最適化が遅い | 300 ms を超える | 貪欲法（6.3 節） |
| Trips が遅い・答えない | 提案が失敗する | 次のバッチで再び提案する。Trips の障害の間は、乗車の受付自体が止まる（`trips-lifecycle.md`） |
| オファーが端末に届かない | 5 秒で取り下げ | 依頼を次のバッチへ。届かない率を計る |
| 設定の値の誤り（重みの桁違い） | 組が悪くなる | 設定の変更にも再生の結果を求める。AppConfig の検証の関数で範囲を確かめる |

## 11. セキュリティと位置のプライバシー

- オファーの前のドライバーには、乗客の名前・電話番号を見せない。乗車地は見せる（8.4 節）。
- 判断の記録は、位置を解像度 10 に丸め、乗客の個人の情報を含めない。読めるのは配車の担当のロールと再生の仕組みだけ。
- 判断の記録とシミュレーションの需要は、本番の記録を使うときも丸めた値だけにする。テストのデータに入れるのは合成の需要か、丸めて匿名化した記録だけ（[AGENTS.md](../../AGENTS.md)）。
- 除外の一覧（E7 の拒否の一覧）の中身は、配車の記録に理由のコードとしてだけ残す。
- 配車の設定（重み、区域）の変更は、変更の記録と承認を残す（`delivery.md`）。

## 12. テスト

### 12.1 性質ベーステスト

- **PROP-DISP-001（1 対 1）**：任意の依頼・候補・コストで、バッチの結果は、1 人のドライバーを 2 つの依頼に使わず、1 つの依頼に 2 人を使わない（ADR-0004）。
- **PROP-DISP-002（条件）**：結果のすべての組は、E1〜E9 を満たす。判定は、配車のコードとは別に書いた参照の実装で確かめる。
- **PROP-DISP-003（決定性）**：同じ入力と同じ種から、同じ結果を出す。入力の並びを入れ替えても（ID で並べ直すので）同じ結果を出す。
- **PROP-DISP-004（最適性）**：6 × 6 までの問題で、結果のコストの合計が総当たりの最小と一致する。どの大きさでも、貪欲法の結果より大きくない。
- **PROP-DISP-005（二重の割り当てなし）**：任意の順序と重複の、提案・受諾・辞退・時間切れ・取り下げ・取り消し・配車のタスクの二重・索引の遅れの列の後で、どの時点でも、ドライバーごと・乗車ごとの有効な割り当ては高々 1 つ（ADR-0003 の性質を、配車の側の障害まで広げたもの）。
- **PROP-DISP-006（同じ人に 2 回送らない）**：1 つの依頼で、辞退・時間切れのドライバーに再びオファーしない。依頼は、3 分か 10 回のうちに受諾か `no_driver_found` になる。
- **PROP-DISP-007（日本版ライドシェア）**：日本版ライドシェアのドライバーへのオファーは、承諾・事前確定運賃・キャッシュレス・降車地あり・運行枠の中の依頼に限られる。

### 12.2 決定表

- **DT-DISP-001**：E1〜E9 の条件を、境界（運行枠の始まりと終わりの 1 秒前後、営業区域の境目の点、迎車の ETA の上限ちょうど）を含めて表駆動テストにする。表から作るベクター（`vectors/eligibility/`）を、配車（Go）と Trips の提案の確かめ直し（TypeScript）の両方の CI で通す。1 つでも違えばマージしない。
- 8.1 節のオファーの事象（期限の前後、取り下げの後の受諾、受諾の送り直し、取り消しとの競合）を、Trips の決定表と共通のベクターにする。

### 12.3 再生・シミュレーション・負荷

- 9.2 節の再生と 9.3 節のシミュレーションを、配車の計算・設定の変更の PR ごとに CI で流す。
- 負荷：S1 のピークの 2 倍（依頼 60 件/秒、オンライン 2 万台）で、バッチの各段の p99 と NFR-001 を計る。

## 14. 未解決の問い

### 決定（2026-09-27、既定案）

- **区域**：S1 は東京で 1 区域。1 回のバッチの依頼が 200 件を超えたら分ける。
- **バッチ**：2 秒。1 件だけのときは 500 ms で即時に解く。
- **コスト**：迎車の ETA ＋ 時間切れの罰則。割り当てないコストは `900 + 1.0 × 待ち`。
- **解き方**：Jonker–Volgenant 型の最短増加路法。300 ms で貪欲法。
- **オファー**：表示 15 秒、サーバーの期限 16.5 秒、5 秒で受信の確認がなければ取り下げ、時間切れ 2 回で自動の休憩。
- **降車地の表示**：受諾の後（法務の結論で見直す）。
- **待機場のドライバー**：既定で候補から除く。
- **判断の記録**：解像度 10、180 日。
- **Trips の確かめ直し**：Trips は提案の時に供給・営業区域・運行枠を確かめ直し、落ちたら `NOT_ELIGIBLE`。判定は DT-DISP-001 の共通のベクターで揃える（統合の決定）。
- **オファーの期限**：サーバーの期限 16.5 秒と、受信の確認の 5 秒の取り下げは、Trips の `trip_timers`（`offer_expiry`・`offer_delivery`）で持つ（[trips-lifecycle.md](trips-lifecycle.md) の 6 節。統合の決定）。
