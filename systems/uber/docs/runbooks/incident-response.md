# Runbook: インシデント対応

- Owner: Ops
- 対応するアラート: すべての呼び出し（page）のアラート（[observability.md](../architecture/observability.md) の 8 節）。個別の場面は「この題材に固有の場面」の節
- 最終確認日: 2026-09-27

個別の手順（[deploy-and-rollback.md](deploy-and-rollback.md)、[disaster-recovery.md](disaster-recovery.md)）の上に立つ、共通の進め方と、この題材に固有の場面（都市の配車の停止、位置の取り込みの遅れ、PSP の障害、緊急の通報の受け付けの失敗、二重の割り当て、位置の漏洩）。進め方の骨格は Slack・Figma の題材と同じ。

## 症状

次のどれかのときに、インシデントを宣言する。迷ったら宣言し、後で重さを下げる。

- 呼び出しのアラートが鳴った
- 乗客・ドライバー・事業者・社内から、「車が呼べない」「オファーが来ない」「二重に請求された」「知らない人に位置が見えた」「緊急のボタンを押したのに連絡がない」の報告が来た
- 不変条件の検査（二重の割り当て、二重の請求、台数の超過、位置の閲覧と監査ログの差）が 1 件でも見つけた

## 影響

### 重さ（severity）

| 重さ | 基準 | 例 | 最初の応答 | 告知 |
| --- | --- | --- | --- | --- |
| SEV1 | 乗客・ドライバーの安全に関わる。二重の割り当て・二重の請求。位置・個人の情報の漏洩。都市の全体で配車ができない（15 分以上） | 緊急の通報が運用に届かない、リージョンの障害、東京の配車の停止 | 5 分以内 | 30 分以内に利用者と事業者へ。以後 30 分ごと |
| SEV2 | 都市の一部・一部の機能が止まる。配車の SLO の速いバーンレート。支払いの与信・確定の障害 | 位置の取り込みの遅れ、PSP の障害、AZ の障害、事前確定運賃の停止 | 15 分以内 | 1 時間以内（影響があれば） |
| SEV3 | 劣化しているが、乗車と支払いは失われない。回避できる | ETA の精度の悪化、住所の検索の提供者の障害、通知の遅れ | 営業時間内 | 必要なら |
| SEV4 | 利用者への影響がない | 1 つのジョブの失敗の増加 | 営業時間内 | なし |

**安全（緊急の通報）、二重の割り当て・二重の請求、位置の漏洩の疑いは、範囲が 1 件でも SEV1 にする。**

## 確認

1. どのアラート・報告から始まったかを記録する。
2. 影響の範囲を見る：都市か、区域か、AZ か、事業者か、アプリのバージョン・OS か、決済の方法か。
3. 直近の変更を見る：デプロイ、配車の計算・設定（AppConfig）、運賃の規則の有効化、フラグ（release・ops・legal）、アプリの段階的な公開、インフラ、AWS Health、外部の提供者（PSP、地図、SMS、通話）の状態のページ。
4. お金・乗車・安全の損失の有無を見る：二重の割り当ての検査、二重の請求の検査、`pay_unknown_outcomes`、`trip_conflicts_total`、`safety_incident_unacked`。

## 対処

### 役割

| 役割 | 担う人 | 責任 |
| --- | --- | --- |
| 指揮者（IC） | 最初に応答したオンコール。SEV1 では Ops の責任者に引き継いでよい | 重さ、方針、大きな判断（都市の配車の停止、依頼の受け付けの停止、リージョンの切り替え） |
| 作業者 | オンコールの Ops、呼ばれた Dev | 調査と復旧 |
| 安全の担当 | 安全の責任者（当番） | 緊急の通報の受け付けを、障害の間も人の手で続ける |
| お金の担当 | お金の持ち主 | 二重の請求・結果不明・照合の評価 |
| 連絡係 | IC が指名する（PM が望ましい） | 乗客・ドライバー・事業者・社内への連絡。事業者の運行管理者への電話 |
| 記録係 | IC が指名する | 時刻つきの記録 |

SEV1 では、指揮者は手を動かさない。

### 進め方

1. **宣言する。** インシデント用の場を、このシステムと別の道具に作る。
2. **安全を最初に確かめる。** どの障害でも、緊急の通報の受け付けが動いているか（`safety_incident_unacked`、合成の緊急の通報）を最初に見る。動いていなければ、下の「緊急の通報の受け付けの失敗」を並べて進める。
3. **被害を止めることを、原因の特定より優先する。** 順番：
   - 直近の変更のフラグを切る、配車の計算を前のバージョンに固定する（`ops.dispatch.algo_pin.<zone>`）
   - 直近のデプロイ・アプリの段階的な公開を止める・戻す（[deploy-and-rollback.md](deploy-and-rollback.md)）
   - 都市の新しい依頼を断る（`ops.intake.reject.<city>`）、新しいオファーを止める（`ops.dispatch.pause.<city>`）。進行中の乗車は続く
   - 容量を増やす
4. **記録を消さない、書き換えない。** `trip_events`、`audit_events`、配車の判断の記録、台帳は、証拠であり、戻す材料である。直しは新しい遷移・仕訳・訂正として入れる。
5. **位置を見ない。** 調べるのは ID・数・時刻・`block` のセルだけ。個別の乗車の軌跡が要るときは、インシデントの ID を理由にした位置の閲覧の許可で見る（[security.md](../architecture/security.md) の 5.2 節）。
6. 30 分ごとに状況を更新する（SEV1・SEV2）。事業者には、運行管理者の連絡先に直接知らせる。
7. 回復を確かめてから閉じる：SLO が戻る、合成の監視（配車・緊急の通報）が成功する、不変条件の検査が 0。

## この題材に固有の場面

### 都市の配車の停止

**症状**：その都市の `dispatch_decision` の速いバーンレート、`disp_pending_requests` が増え続ける、成立率の急な低下、合成の配車の依頼の失敗、「車が呼べない」「オファーが来ない」の報告。

1. SEV1（15 分以上、都市の全体）か SEV2（一部）を宣言する。
2. **どの段で止まっているかを見る**（ダッシュボードの「配車の区域」、[observability.md](../architecture/observability.md) の 5 節）：
   | 見えること | 疑う原因 | 次に見る |
   | --- | --- | --- |
   | 区域のリースの持ち主がいない、バッチが走っていない | dispatch のタスクの停止、DynamoDB の障害 | `dispatch-zone-failover.md`。待機のタスクの状態 |
   | バッチは走るが候補が 0 | 索引の停止・遅れ、位置の取り込みの停止 | 下の「位置の取り込みの遅れ」、`geo-index-rebuild.md` |
   | 候補はあるが ETA が概算ばかり | Valhalla の劣化 | `valhalla-capacity.md` |
   | 最適化が貪欲法ばかり | バッチが大きすぎる | 受け入れの上限とバッチの上限（[capacity.md](../architecture/capacity.md) の 4 節） |
   | 提案が拒否される（`EPOCH_MISMATCH`、`CONSTRAINT_VIOLATION`） | 索引の遅れ、2 つの配車のタスク、Trips の事象の欠け | `trip_outbox_oldest_seconds`、索引の照合の差 |
   | 提案は通るがオファーが届かない（`undelivered`） | 常時の接続・プッシュの障害 | `offer-delivery-degraded.md` |
   | 受諾は来るが遷移が失敗 | Trips・Aurora `core` の障害 | Aurora のイベント、`trip_transition` |
   | 直前に配車の計算・設定・候補の条件のデータを変えた | 変更の不具合 | 前のバージョンに固定する |
3. **被害を抑える**：
   - 直前の変更があれば、`ops.dispatch.algo_pin.<zone>` と AppConfig の前のバージョンで戻す。
   - 未割り当ての依頼が溜まり、3 分で `no_driver_found` になる依頼が増えているなら、`ops.intake.reject.<city>` で新しい依頼を断り、乗客に「混み合っています」を出す（与信の前に断るので請求は起きない）。
   - 待っている乗客への案内（アプリの告知の帯）を連絡係が出す。
4. **索引・配車を作り直す**：geo-index と dispatch の主と待機がともに止まっていれば、両方のタスクを入れ替え、`READY`（35 秒の読み直し）を待つ。依頼は Trips に残っているので失われない。
5. **戻った後**：受け入れの上限を平常の 50% で開き、15 分ごとに上げる。その間の `no_driver_found` の件数を記録し、取り消し料が誤ってかかっていないかを確かめる（配車の停止による取り消しは、キャンセル料の対象にしない。運賃の持ち主と確かめる）。

**エスカレーション**：30 分たっても配車が戻らない → Dev のテックリード（配車の持ち主）と Ops の責任者を呼ぶ。リージョンの障害が疑われる → [disaster-recovery.md](disaster-recovery.md) の B。

### 位置の取り込みの遅れ

**症状**：`geo_apply_lag_seconds` の p99 が 3 秒（警告）・10 秒（page）、`geo_stale_drivers_ratio` の増加、候補の数の急な減少、loc-ingest の 5xx、Kinesis の `WriteProvisionedThroughputExceeded`。

1. SEV2 を宣言する（索引が 15 秒より古くなると、ドライバーが候補から消え、配車が止まる。都市の全体なら SEV1）。
2. **区間を切り分ける**（[location-ingestion.md](../architecture/location-ingestion.md) の 12 節の予算）：
   | 区間 | 見るもの | 対処 |
   | --- | --- | --- |
   | アプリ → loc-ingest | ALB の要求の数、4xx・5xx、`loc_ingest_seconds`、アプリのバージョンごとの送信の間隔 | loc-ingest のタスクを増やす。特定のアプリのバージョンなら段階的な公開を止める |
   | loc-ingest → Kinesis | `loc_kinesis_put_seconds`、`WriteProvisionedThroughputExceeded`、熱いシャード | シャードを分ける（`UpdateShardCount`）。すぐ効かなければ `ops.loc.interval_ms` を 8,000 に上げて量を半分にする |
   | Kinesis → geo-index | 拡張ファンアウトの `MillisBehindLatest`（主・待機ごと） | 片方だけ遅いなら、その索引のタスクを入れ替える（待機を先に） |
   | geo-index の適用 | 書き手の CPU、GC の停止、写しの公開の遅れ | `geo-index-lag.md`。タスクの CPU を上げる |
3. **再接続の殺到**（携帯の網の障害の復旧）なら、`backlog` の要求の別の流量の制限が働いているか（全体で 5,000 件/秒）を見る。平常の点が優先されていれば、`backlog` は待ってよい（`location-reconnect-storm.md`）。
4. `ops.loc.interval_ms` を上げた場合は、戻すのを忘れない。上げている間は、ドライバーの位置が 8 秒ごとになり、NFR-002 の 15 秒の古さに近づく。10,000 を超えて上げない。
5. 索引が壊れた疑い（照合の差が急増）なら、両方の索引のタスクを順に入れ替えて作り直す（`geo-index-rebuild.md`）。

**エスカレーション**：Kinesis・ALB のリージョンの障害 → AWS のサポート。30 分たっても遅れが 3 秒を下回らない → Dev のテックリードを呼ぶ。

### PSP の障害

**症状**：`payment_auth` の悪い事象の急増、PSP の 5xx・時間切れ、`payment_pending` から `payment_failed` への遷移の急増、`pay_unknown_outcomes` の増加、PSP の状態のページの障害の告知。

1. SEV2 を宣言する（新しいアプリの決済の依頼が通らない。進行中の乗車は続く）。お金の担当を呼ぶ。
2. **新しい依頼を守る**：`ops.payments.in_vehicle_only` を有効にする。タクシーの依頼は車内払い（`in_vehicle`）へ案内する。日本版ライドシェアはアプリの決済が必須なので受けない（アプリに理由を出す。[payments-and-payouts.md](../architecture/payments-and-payouts.md) の 13 節）。
3. **結果不明を増やさない**：PSP への新しい操作が時間切れになり続けるなら、確定と返金のキューを止める（`psp-outage.md`）。結果不明の操作は、照会で確定させるまで次を送らない（[ADR-0023](../decisions/0023-psp-authorize-at-request-capture-at-end.md)）。
4. **与信の期限**：未確定の支払いが与信の期限の 24 時間前に近づいていないかを見る（`capture-before-auth-expiry.md`）。障害が長引けば、期限の近いものから優先して確定する。
5. **復旧の後**：
   1. 照会のジョブで `unknown` を確定させる（`psp-unknown-outcomes.md`）。
   2. 確定のキューを再開し、`completed` から確定までの遅れが平常に戻るのを見る。
   3. `ops.payments.in_vehicle_only` を切る。
   4. 二重の売上の確定の検査を臨時に流す（0 件であること）。
   5. 照合（T+2 営業日）でブレイクを見る。
6. 車内払いに切り替えた乗車の手数料は、事業者の預り金と相殺する（payments の 4.1 節）。事業者へ知らせる。

**エスカレーション**：二重の請求が 1 件でも見つかった → SEV1。お金の持ち主と PM（乗客への連絡と返金）を呼ぶ。PSP の障害が 2 時間を超える → 経営の責任者へ報告し、事業者への精算の遅れを連絡する。

### 緊急の通報の受け付けの失敗

**症状**：`safety_incident_unacked` が 30 秒で 1 件以上、`safety_intake_queue_oldest_seconds` が 10 秒、合成の緊急の通報が 2 回続けて届かない、安全の担当の画面が開かない、「緊急のボタンを押したのに連絡がない」の報告。

端末の 110・119 の画面は、サーバーに依らず開く（[safety-and-trust.md](../architecture/safety-and-trust.md) の 4.1 節）。この場面は、運用への知らせ（`SafetyIncident`）が担当に届かない・受けられないことを扱う。

1. **SEV1 を宣言する。** 安全の責任者を呼ぶ（当番の呼び出しと電話の両方）。
2. **人の手の受け付けを先に立てる**：
   - 安全の担当の画面が開かないなら、safety-intake から当番の呼び出しの道具への直接の経路（SQS → 呼び出しの連携）で届いている通報を、呼び出しの道具の上で受ける（[safety-and-trust.md](../architecture/safety-and-trust.md) の 4.3 節）。
   - 呼び出しの連携も止まっているなら、作業者が SQS `safety-incidents` の最古のメッセージを読み（ID・乗車の ID・種類・時刻だけ）、安全の担当に電話で伝える。
3. **経路を切り分ける**（`safety-intake-outage.md`）：
   | 見えること | 疑う原因 | 対処 |
   | --- | --- | --- |
   | 合成の通報が api に届かない | 入口・api の障害 | 端末は送り直している。api を戻す。リージョンの障害なら [disaster-recovery.md](disaster-recovery.md) の B の 11 |
   | api には届くが SQS に入らない | safety-intake の障害 | タスクを入れ替える。前のデプロイを戻す |
   | SQS に溜まる | 受信の処理の停止 | 処理のタスクを増やす・入れ替える |
   | 担当の画面に出るが誰も受けない | 担当の人手、画面の音の不具合、当番の呼び出しの失敗 | `safety-queue-backlog.md`。応援を呼ぶ |
   | 特定のアプリのバージョンだけ届かない | アプリの不具合 | 段階的な公開を止める。緊急の入口の不具合なら、`required_min` を上げる判断を Dev と Ops で（緊急の入口は塞がない） |
4. **受けていない通報を確かめる**：戻った後、障害の間の `SafetyIncident` をすべて担当が受け、押した人に電話で安全を確かめる（[safety-and-trust.md](../architecture/safety-and-trust.md) の 4.2 節）。位置は、インシデントの ID を理由に閲覧の許可で見る。
5. 押した人の端末は、送れなかった通報を 5 秒ごとに送り直しているので、経路が戻ると一度に届く。受信の処理の数を上げて待つ。

**エスカレーション**：5 分たっても人の手の受け付けが立たない → 経営の責任者と法務へ報告する。通報を受けられなかった間に事故があった疑い → 法務（L7）と事業者に知らせ、記録を残す（`incident-packet-to-operator.md`）。

### 二重の割り当て

**症状**：1 分ごとの検査が、有効な割り当てを 2 つ持つドライバーか乗車を見つけた（[ADR-0003](../decisions/0003-trip-state-and-single-assignment.md)）。

1. SEV1 を宣言する。Dev のテックリードを呼ぶ。
2. 影響する都市の新しいオファーを止める（`ops.dispatch.pause.<city>`）。進行中の乗車は続く。
3. 手順は `double-assignment.md`（[trips-lifecycle.md](../architecture/trips-lifecycle.md) の 14 節）。直前の変更（Trips、マイグレーション、DR の切り替えの `region_gen`）を疑う。

### 位置の漏洩

**症状**：乗車の相手でない人に正確な位置が見えたという報告、位置の漏洩のテストの失敗、位置の閲覧と監査ログの件数の差、ログの緯度経度の検出。

1. SEV1 を宣言する（ログの緯度経度だけで、外に出ていなければ SEV3）。セキュリティの担当と法務を呼ぶ。
2. 経路を止める：該当の API・機能を release・ops のフラグで止める。直近のデプロイ・フラグを戻す。
3. 影響の範囲を、監査ログ・API のアクセスログ（ID と時刻）で調べる。位置の中身は見ない。
4. 報告の要否と期限（個人情報保護委員会と本人）は法務が判断する（**法務の確認待ち**、[intent.md](../intent.md) の L4）。手順は `personal-data-breach.md`（[security.md](../architecture/security.md) の 14 節）。
5. ログに緯度経度が入っていたなら、その期間のログを隔離し、法務の判断の後に消す（東京と大阪の両方）。

## エスカレーション

| 状況 | 連絡先 |
| --- | --- |
| SEV1 | Ops の責任者、Dev のテックリード、PM（告知） |
| 緊急の通報の受け付けの失敗 | 安全の責任者、法務（L7） |
| 二重の割り当て・二重の請求 | Dev のテックリード、お金の持ち主 |
| 位置・個人の情報の漏洩の疑い | セキュリティの担当、法務 |
| 日本版ライドシェアの台数の超過・運行枠の外の運行 | 事業者の運行管理者、法務（許可の条件の違反の疑い） |
| AWS のサービスの障害 | AWS のサポート（Business 以上のケース） |
| PSP・地図・SMS・通話の提供者の障害 | 提供者の窓口 |
| 1 時間たっても SEV1 が収まらない | 経営の責任者へ報告 |

## 事後

- SEV1・SEV2 は、5 営業日以内に事後の検討（責めない形）を行い、記録を残す。
- 調査結果と再発の防止を、`changes/` の新しい `intent.md` として起票する（Maintain 段）。
- 失った依頼、戻した乗車、誤った請求と返金、受けられなかった緊急の通報の件数を記録する。
- 事業者に影響の報告を出す（事業者ごとに閉じた形で）。
