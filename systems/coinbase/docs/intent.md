# Intent: Coinbase を AI エージェント主体で再構築する

- Author: shoito
- Status: draft（2026-11-15 に土台の設計と領域の文書を書き、統合の工程で領域から出た問い（L15〜L19、P5〜P14）を足した。PM の受理を待つ）
- Date: 2026-11-15

## Problem

個人が暗号資産を売り買いし、預けておくには、次のところで困る。

- **預けたものが盗まれる。** 交換業者のウォレットが破られると、利用者から預かった暗号資産が一度に流れ出る。2024 年 5 月には、国内の交換業者で、利用者から預かった約 482 億円相当の暗号資産が不正に流出した（金融庁の要請の文書。出典は末尾）。流れ出た暗号資産は、チェーンの上では取り戻せない。
- **約定が公正か分からない。** 注文の順序が入れ替わる、本人どうしの売りと買いがぶつかる、板に見せるだけの注文で価格が動く、といったことが起きても、利用者からは見えない。後から確かめる手段もない。
- **残高と約定が合わない。** 同じ残高で 2 つの注文が通る、約定したのに残高が動かない、取り消したのに拘束が戻らない、といった誤りは、エラーにならずに残高の違いとして残る。
- **入出金が遅く、取り返しがつかない。** 暗号資産の入金はチェーンの承認を待つので、いつ使えるようになるか分からない。出金の宛先を 1 文字でも誤れば、取り戻せない。チェーンが巻き戻る（reorg）と、一度見えた入金が消える。
- **販売所の値段が分かりにくい。** 交換業者が相手になる販売所では、提示の価格に含まれる差（スプレッド）が分かりにくい。取引所の板との違いも分かりにくい。
- **法令が動いている。** 暗号資産の規制は、2026 年 7 月に成立した改正法で、資金決済法から金融商品取引法へ移る途中にある。インサイダー取引の規制が新しく入る（出典）。

国内の交換業者の会員の合計で、2025 年 2 月末の稼働の口座は約 740 万、利用者から預かった暗号資産は約 3.49 兆円、同じ月の現物の取引高は約 1.92 兆円である（日本暗号資産等取引業協会の月次の統計。出典）。本家 Coinbase は米国を中心に交換所と保管を大きな規模で営むが、日本の事業は 2023 年 1 月に止めた（出典）。この題材では、日本の暗号資産交換業者として、小さなチームと AI エージェントで、どこまで作り直せるかを確かめる。核（マッチングエンジンと sequencer、注文の受付とリスクの確認、台帳、ウォレットの指揮と署名の方針）は自分で設計する（[リポジトリ共通の ADR-0007](../../../docs/decisions/0007-no-reuse-of-original-implementation.md)）。

## Proposed outcome

個人が、スマートフォンと Web で、日本円を入れて BTC と ETH を売り買いし、預けておき、自分のウォレットへ出せる交換所を作る。販売所（本システムが価格を示して相手になる）と取引所（利用者どうしの注文を板で突き合わせる）の両方を持つ。次の 7 つの価値を満たす。

1. **預かった資産を失わない**：利用者の暗号資産の大部分をネットワークにつながないコールドのウォレットに置き、ネットワークにつながるウォレットの額に上限を置く。誰も一人で資産を動かせない（NFR-007、NFR-014）。
2. **残高を超えて使えない**：注文・出金・販売所の購入は、使える残高を超えて通らない。どんな並行度でも（NFR-004）。
3. **約定が公正で、再現できる**：板の注文は価格・時間の優先で突き合わせ、本人どうしは約定しない。記録から再生すれば、同じ約定がビット単位で出る（NFR-003、NFR-012、NFR-013）。
4. **お金が合う**：台帳の仕訳は常に釣り合い、利用者の残高の和が、チェーンの上のウォレットの残高と、信託と銀行の口座の残高と、毎日一致する（NFR-005、NFR-006）。
5. **出金は正しい宛先に一度だけ**：出金は、許可した宛先に、承認した額で、一度だけ届く。同じ出金から 2 つの取引が確定しない（NFR-008）。
6. **入金は確定してから使える**：チェーンの承認・確定を待ってから残高に入れ、巻き戻りで消えた入金を使わせない（NFR-009）。
7. **速く、止まっても安全に戻る**：注文の受け付けは p99 20ms、板の配信は p99 50ms。止まるときは、板を止めてから、記録から元の状態に戻す（NFR-001、NFR-002、NFR-011）。

### MVP（S1）に含める

- **アカウントと本人確認**：個人の口座の開設、eKYC（提供者を通す。方式は法務の L4）、ログイン（パスキー、予備に TOTP）、セッション、端末の一覧と取り消し、取引の API キー（取引の権限だけ。出金の権限は PM の判断待ち P2）、退会。法人の口座とマーケットメイカーの口座は PM の判断待ち（P1）
- **日本円の入出金**：利用者ごとの振込先の口座番号（提携銀行）への振込による入金、本人の名義の口座への出金、着金と出金の照合
- **暗号資産の入金**：BTC と ETH（ETH 本体だけ。ERC-20 のトークンは持たない）、利用者ごとの入金のアドレス、承認の数・確定を待った記帳、入金のスクリーニング
- **暗号資産の出金**：宛先の許可の一覧（登録の後の待ち時間。PM の判断待ち P4）、手数料の表、スクリーニング（制裁、チェーン分析）、トラベルルールの通知（法務の L5）、額による承認の段、署名、放送、承認の追跡
- **取引所**：BTC/JPY と ETH/JPY の 2 つの板、指値（期限なし・即時の約定か取り消し・メイカーだけ）、成行（価格の帯つき）、取り消し、自己約定の防止、メイカー・テイカーの手数料、REST と WebSocket の API、板の配信（板の全体と差分、約定）、ローソク足
- **販売所**：BTC と ETH の買いと売り、価格の提示（期限つき）、提示の受け入れ、本システムの在庫の上限
- **台帳と残高**：複式簿記の台帳（日本円・BTC・ETH）、使える残高と拘束、約定の記帳、手数料、入出金、明細、年間の取引の報告書（法務の L10）
- **保管**：ホット・ウォーム・コールドのウォレット、ウォレットの間の移し替え、コールドの割合の監視（法務の L2）、履行保証暗号資産（法務の L2）、鍵の儀式
- **分別管理と照合**：利用者の日本円の信託（法務の L3）、台帳とチェーンの照合、台帳と銀行・信託の照合、日次の分別管理の報告
- **AML とトラベルルール**：入出金のスクリーニング、制裁の一覧との照合、取引の監視の規則、疑わしい取引の届出の案件の管理（法務の L4・L6）
- **不公正取引の監視**：見せ玉・仮装売買・相場操縦の兆しの検出、役職員の取引の制限（法務の L7）
- **運用の画面**：CS、出金の承認、鍵の儀式の記録、板の停止と再開、コンプライアンスの案件、監査ログ
- **通知**：入出金、約定、ログイン、宛先の登録の知らせ（メール、プッシュ）

### 守るべき振る舞い

- 利用者の各資産の使える残高（`available`）は、どの時点でも 0 以上。拘束（`hold`）の和は、拘束の種類（`source_type`）ごとに元の記録と一致する。未約定の注文の残りの必要額（`order`）、手続き中の暗号資産と日本円の出金（`withdrawal`・`fiat_withdrawal`）、巻き戻りと法令による拘束（`reorg`・`legal`。案件の記録と比べる）である（[ADR-0029](decisions/0029-hold-kinds-and-withdrawal-restrictions.md)）。販売所の提示の受け入れは 1 つのトランザクションで記帳し、拘束を残さない（[ADR-0010](decisions/0010-brokerage-quotes-and-inventory.md)）。
- 板の状態を変える入力は、sequencer が付けた通し番号の順にだけエンジンに入る。番号に抜けも重なりもない。
- エンジンは、同じスナップショットと同じ入力の列から、同じ出力の列を出す。本番のエンジンと、別の AZ の写しのエンジンの出力の要約（ハッシュ）は、入力の番号ごとに一致する。
- 板の注文は、価格の良い順、同じ価格なら受け付けの順に約定する。約定の価格は、板にあった注文の価格である。同じ利用者の売りと買いは約定しない。
- 1 つの約定は台帳に 1 回だけ記帳する。記帳の後、買い手と売り手と手数料の口座の増減の和は、資産ごとに 0。
- 台帳の各仕訳は、資産ごとに借方と貸方の和が等しい。利用者の口座の残高の和は、利用者用のウォレットの残高（チェーンの上）と、照合の時点で一致する。違いは仮勘定に置き、説明がつくまで消さない。
- 利用者の暗号資産のうち、ネットワークにつながる環境で管理する額は、`legal.hot_ratio_max` の割合を超えない。超えたら、自動でコールドへ移す依頼を出す。
- 1 つの出金から、チェーンの上で確定する取引は 0 か 1。出金の宛先は、登録して待ち時間を過ぎた宛先の許可の一覧の中にある。スクリーニングを通らない出金には署名しない。
- 入金は、承認の数（BTC）・確定（ETH）の閾値を満たすまで、使える残高に入れない。記帳の後も、出金に使える閾値（BTC の 6 承認）までは、その口座の暗号資産と日本円のすべての出金を止める（[ADR-0039](decisions/0039-deposit-state-machine-and-withdrawal-lock.md)）。記帳の後にチェーンが巻き戻ったら、その額を拘束し、仮勘定に置く。
- 一人の人も、一つのサービスも、方針の上限を超えて資産を動かせない。

## Affected users and systems

- **個人の投資家**：BTC・ETH を売り買いし、預けておく個人。スマートフォンが中心。初めて暗号資産を買う人と、取引所の板で頻繁に売り買いする人がいる。一部は API で自動の売買をする。
- **法人・マーケットメイカー**：板に指値を出し続けて流動性を出す事業者（MVP に入れるかは PM の判断待ち P1）。
- **運用者・CS**：問い合わせ、出金の承認、鍵の儀式、板の停止と再開、照合の差の調べ。
- **コンプライアンス**：本人確認の例外、取引の監視、疑わしい取引の届出、制裁の照合、トラベルルール、不公正取引の監視、当局への報告。
- **財務**：分別管理、信託、照合、履行保証暗号資産、税の書類。
- **外部のシステム**：Bitcoin と Ethereum のネットワーク（自前のノード）、HSM・MPC の提供者、提携銀行（入金の口座、出金）、信託銀行（利用者の日本円の信託）、eKYC の提供者、チェーン分析の提供者、トラベルルールの通知の提供者と相手の交換業者、参照の価格の提供者、メール・プッシュの送信、当局と自主規制団体。

## Constraints

- **核を自前で設計する。** マッチングエンジンと sequencer、注文の受付とリスクの確認、台帳、ウォレットの指揮と署名の方針、販売所の価格の提示、監視の規則は自分で作る。ブロックチェーンのノード、HSM・MPC、eKYC、銀行の API、チェーン分析、トラベルルールの通知の提供者は、核の外の汎用の部品・外部のサービスとして、理由を ADR に書いて使う（[ADR-0001](decisions/0001-platform-and-stack.md)、[ADR-0011](decisions/0011-external-providers-boundary.md)）。
- 実行基盤と技術は、rebuilds の他の題材の決定（AWS 東京・大阪、TypeScript・Hono、Aurora PostgreSQL、Valkey、S3、SQS・SNS、ECS Fargate、Terraform、OpenTelemetry、AppConfig のフラグ、FORCE RLS と `SET LOCAL`、UUIDv7、outbox）を引き継ぐ。外れるところ（マッチングエンジンを Rust で EC2 に置くこと、入力の記録に Amazon MSK を使うこと、ノードを EC2 に置くこと）は ADR に理由を書く（[ADR-0001](decisions/0001-platform-and-stack.md)、[ADR-0002](decisions/0002-sequencer-and-event-journal.md)）。
- **台帳を設計し直さない。** 複式簿記、冪等、3 者の照合、熱い口座の分け方は、Stripe の題材（[ADR-0003](../../stripe/docs/decisions/0003-double-entry-ledger.md)、[ADR-0017](../../stripe/docs/decisions/0017-three-way-reconciliation-with-suspense.md)）とメルカリの題材（[ADR-0003](../../mercari/docs/decisions/0003-escrow-and-double-entry-ledger.md)）を引き継ぐ。この題材は、複数の資産と拘束と約定の記帳とチェーンとの照合の差分を書く（[ADR-0005](decisions/0005-ledger-balances-and-trade-settlement.md)）。
- 本家の名前は識別子に使わない。ドメインは `<brand>.<domain>`、ヘッダーは `<Brand>-Signature`、API キーの接頭辞は `<brand>_live_` の形で書く（[リポジトリ共通の ADR-0006](../../../docs/decisions/0006-brand-neutral-identifiers.md)）。
- データは日本（東京、DR は大阪）に置く。コールドのウォレットの鍵の材料は、東京と大阪とその他の 1 か所の、別々の場所に分けて置く（[ADR-0006](decisions/0006-wallet-tiers-and-cold-ratio.md)）。
- 日本の法令への対応は、法務の確認を前提に設計する。結論は出さない（下の「法務の確認待ち」）。
- 規模は段階的に広げる（[architecture/](architecture/README.md) の 2 節）。

## Non-goals

| 機能 | 理由 |
| --- | --- |
| 証拠金取引、レバレッジ、先物・オプションなどのデリバティブ | 金融商品取引法の別の業の領域で、ロスカットと証拠金の設計が要る |
| ステーキング | 預かった暗号資産を運用に回すことになり、保管とお金の性質が変わる |
| NFT、ステーブルコイン（電子決済手段） | 改正法の対象の外で、別の法令の枠組みが要る |
| 自己管理のウォレットのアプリ | 鍵を利用者が持つ別の製品である |
| 日本の外の利用者と国 | 国ごとの登録とトラベルルールの設計が要る |
| 機関投資家向けのプライムブローカレッジ、カストディの単独のサービス | 別の顧客と契約の型である |
| 自前の eKYC、自前のブロックチェーンのクライアント、自前の暗号のライブラリ | 提供者と汎用の部品を使う（ADR-0007、ADR-0009、ADR-0011） |
| 本家の API・アプリとの互換、本家のデータの移し替え | 振る舞いは寄せるが、名前と形式は独自にする（リポジトリ共通の ADR-0006） |
