# Capacity: Coinbase

負荷のモデル、部品ごとの必要量、費用のモデルと単価、負荷試験。全体の規模の段階は [README.md](README.md) の 2 節、構成と台数の表と段階を上げる基準は infrastructure の領域にある。Stripe の [capacity.md](../../../stripe/docs/architecture/capacity.md) とメルカリの [capacity.md](../../../mercari/docs/architecture/capacity.md) の形と規則（接続数の上限、パラメーターを Terraform で持つこと）を引き継ぐ。

**ここの数値はすべて初期見積もりである。** E16 の `load-test-market-spike` と `cost-baseline` で確かめ、結果で置き換える。AWS の仕様と価格で確かめていないものは「未検証」と書く。

- 持たないもの：台数の表と配置、段階を上げる基準（infrastructure）、速さの上限の段の値（order-entry-and-risk）、配信の束ね方（market-data）、ノードのディスクと同期（chain-nodes-and-confirmations の `node-ops-poc`）。

## 4. 負荷のモデル（S1）

[README.md](README.md) の 2 節の値から作る。

| 項目 | 平均 | 最大（相場の急変の 10 分） | 根拠・前提 |
| --- | --- | --- | --- |
| 板の入力（注文と取り消し） | 約 104 件/秒（約 900 万件/日） | 3,000 件/秒（1 つの板に集中しうる） | README の 2 節 |
| うち新しい注文 | 約 52 件/秒 | 1,500 件/秒 | 入力の 9 割が取り消しと出し直しの組（quality.md の H）。新しい注文と取り消しを半々と置いた |
| うち取り消し | 約 52 件/秒 | 1,500 件/秒 | 同上 |
| 約定 | 約 3.5 件/秒（30 万件/日） | 300 件/秒 | README の 2 節 |
| 販売所の提示 | **未検証**（brokerage-quotes の領域で見積もる） | 平常の 10 倍 | quality.md の H |
| 配信の接続 | — | 2 万。全部が 2 つの板の差分を受ける | README の 2 節、quality.md の H |
| 暗号資産の入金・出金 | 5,000 件/日・4,000 件/日 | 1 時間に 1 日分の 1 割の集中 | README の 2 節 |
| 日本円の入金・出金 | 5,000 件/日・4,000 件/日 | 給料日と月末の朝に、1 時間に 1 日分の 2 割 | README の 2 節（暗号資産と同じほど） |
| 稼働の口座 | 30 万 | ログインの集中は急変の開始の 5 分 | README の 2 節 |

- 相場の急変は予告なく始まり、分の単位で最大に達する。最大を 10 分続け、その後 1 時間は平常の 5 倍が続くと置く。
- マーケットメイカーの口座（PM の判断待ち P1）は、入力の多くを出す。1 社の入力の上限は order-entry-and-risk の領域の速さの上限の段で決める。台帳の 1 つの残高の行の更新の速さの上限（行のロックの直列化）を超えない値にする（5.2 節）。

## 5. 部品ごとの必要量（S1 の最大）

### 5.1 注文の経路（`trading-api`・`order-gateway`）

- 最大 3,000 件/秒。1 vCPU あたり 250 件/秒の書き込みの要求（Stripe の [capacity.md](../../../stripe/docs/architecture/capacity.md) の 2.1 節の目安）と置き、12 vCPU。1 つの AZ を失っても受けるよう 3 AZ に 6 vCPU ずつ、計 18 vCPU を常設する（[ADR-0070](../decisions/0070-trading-path-provisioned-for-peak.md)）。
- 新しい注文は、拘束の 1 トランザクションを ledger の Aurora に書く（ADR-0004）。取り消しは拘束を書かない（戻しはエンジンの出力の後。[ledger-and-balances.md](ledger-and-balances.md) の 7 節）。

### 5.2 Aurora ledger の書き込み

| 処理 | 1 件あたりの行 | 最大の件数/秒 | 行/秒 |
| --- | --- | --- | --- |
| 注文の拘束（残高の行、拘束の行、仕訳 1 ＋ 行 2） | 5 | 1,500 | 7,500 |
| 取り消し・`done` の拘束の戻し（同上） | 5 | 1,500 | 7,500 |
| 約定の記帳（仕訳 1 ＋ 行 6、残高の行 4、拘束の行 2） | 13 | 300 | 3,900 |
| 販売所、入出金、その他 | — | — | 500 |
| **合計** | | | **約 1.9 万** |

- トランザクションは約 3,300 件/秒。Stripe の題材の見積もり（1.4 万行/秒を `db.r8g.4xlarge` の writer で CPU 50% 以下）より多いので、writer は `db.r8g.8xlarge` から始め、負荷試験で下げる（**未検証**）。
- 1 つの残高の行の更新は直列になる。1 回のロックの保持を 1〜2ms と置くと、1 行あたり 500〜1,000 件/秒が上限である（**未検証**）。マーケットメイカー 1 社の入力の上限は、この値の半分以下にする（order-entry-and-risk の領域に依頼する）。超えるなら S2 のスロットへ進む（[ADR-0004](../decisions/0004-order-entry-holds-and-idempotency.md)）。
- 接続数の規則は Stripe と同じ：オートスケールの上限まで増えたときの合計を `max_connections` の 50% 以下に保つ。

### 5.3 Aurora core

- 注文の行の作成（1,500 件/秒）と、エンジンの出力による状態の更新（約 3,000 件/秒）、outbox で、約 6,000 行/秒。`db.r8g.2xlarge` の writer から始める（**未検証**）。

### 5.4 MSK と、マッチングの EC2

- 入力の記録：最大 3,000 件/秒 × 1 件 約 300 バイト ＝ 約 1 MB/秒。出力の記録はその 2 倍と置く。3 ブローカーで、`acks=all` の遅れ（NFR-001）が先に効く（`engine-latency-poc`）。
- マッチング：板ごとに sequencer と engine の組 1 つ、写しの engine 1 つ。S1 は 2 つの板で、計算の最適化の型の EC2 を 4 台（本番 2、写し 2）。1 台は 1 つの板の最大の全部を受ける（README の 2 節）。

### 5.5 配信（`md-publisher`・`ws-gateway`）

- 送る回数は、配信の束ね方（market-data の領域）で大きく変わる。ここでは、板の差分を 10ms ごとに束ねると置く（NFR-002 の 50ms の中）。1 つの板あたり最大 100 回/秒 × 2 つの板 × 2 万の接続 ＝ 最大 400 万フレーム/秒。
- 1 タスク（2 vCPU）で 20 万フレーム/秒と置き（**未検証**）、20 タスク。3 AZ に分けて 1 AZ を失っても受けるよう、30 タスクを常設する。
- 外への転送：1 フレーム平均 200 バイトで最大 800 MB/秒（約 6.4 Gbps）。平常は束ねの中の差分が少なく、その 1 割以下と置く（**未検証**）。
- 再接続の嵐：`ws-gateway` の入れ替えや障害で 2 万の接続が 1 分で張り直す。全体の板の送り直しを、接続ごとに速さの上限で並べる（market-data の領域）。

### 5.6 入出金と提供者

- 入出金は 1 時間の集中でも 1 件/秒に届かない。部品の容量より、提供者の速さの上限（チェーン分析、トラベルルール、銀行の API）と人の承認が先に効く。提供者との契約の条件に、S1 の集中の 3 倍を入れる（**未検証**）。

## 6. データの増え方（S1）

| データ | 1 日 | 1 年 | 扱い |
| --- | --- | --- | --- |
| 拘束と戻しの仕訳と行（新しい注文 約 450 万件/日 × 2 回 × 3 行） | 約 2,700 万行 | 約 100 億行 | 最も大きい。月ごとのパーティションにし、13 か月より古いものを S3（Parquet）へ移す（Stripe の [ledger.md](../../../stripe/docs/architecture/ledger.md) の 3 節） |
| 約定の仕訳と行（30 万件 × 7 行） | 約 210 万行 | 約 8 億行 | 同上 |
| 明細の行 | 約 60 万行（約定の両側） | 約 2 億行 | 利用者ごとの索引。作り直せる |
| 入力と出力の記録 | 約 8 GB | 約 3 TB | MSK は 7 日、S3 に長く持つ（ADR-0002） |

- 1 行 150 バイトと置くと、ledger の Aurora は 1 年に約 1.6 TB 増える（**未検証**）。拘束の仕訳が大半なので、拘束の仕訳の形（[ADR-0004](../decisions/0004-order-entry-holds-and-idempotency.md)）を変える案（注文の拘束を仕訳にせず、残高の行と拘束の行だけで持つ）は、S2 の前に見直す候補にする。

### 8.1 約定あたりの原価と目標

- 1 約定の平均 1 万円（README の 2 節）で、テイカーの手数料は 10 円。目標はその 1 割の 1 円以下である。
- 基盤の月の費用 5.5 万 USD を、1 USD 150 円（本システムの置いた換算）で約 825 万円とする。約定は 25 万〜30 万件/日で、月 750 万〜900 万件。全部を約定に割り当てると、1 約定あたり 0.9〜1.1 円で、目標の境にある。
- 実際は、固定の原価の一部を入出金と口座に割り当てる（[README.md](README.md) の 2.1 節の式）。約定に割り当てる部分は、注文の経路、MSK、マッチング、ledger、配信で、表の約 6 割と置くと 0.5〜0.7 円である。
- 費用を下げる手段：ledger の拘束の仕訳の形の見直し（6 節）、配信の束ねの間隔、Savings Plans とリザーブド（**未検証**）。

## 9. 負荷試験

| 場面 | 内容 | 合格 |
| --- | --- | --- |
| LT-1 相場の急変 | quality.md の H のとおり。1 つの板に 3,000 件/秒を 10 分、その後 1 時間は 5 倍 | NFR-001・NFR-002・NFR-005。拘束の照合の不一致 0 |
| LT-2 急変と AZ の障害 | LT-1 の途中で 1 つの AZ のタスクを落とす | 同上。写しのエンジンへの切り替えは RTO 5 分（NFR-011） |
| LT-3 マーケットメイカーの集中 | 1 社が速さの上限まで入力を出す | 残高の行のロック待ち p99 が 5ms 以下。他の利用者の受け付けの p99 が変わらない |
| LT-4 配信の再接続の嵐 | 2 万の接続が 1 分で張り直す | 張り直しの間も NFR-002 を、張り直していない接続で満たす |
| LT-5 入出金の山 | 日本円と暗号資産の入出金を 1 時間に 1 日分の 2 割 | 入出金の受け付けの 5xx 0。提供者の速さの上限で待つだけ |

- 負荷は自前の注文の負荷の生成器（`order-load-generator`）と k6 で作る。検証の環境は本番と同じ型で作り、試験の後に消す。結果で 4〜8 節の値を置き換える。

## 10. キャパシティの運用

- 週次に、常設の部品の最大の使用率（CPU、DB の接続、ロック待ち、MSK の遅れ、配信の送り出しの遅れ）を見る。最大の時の使用率が 60% を超えたら、常設を増やす変更を起票する。
- 段階を上げる基準（S1 から S2）は infrastructure の領域で決める。capacity はその入力として、最大の時の使用率、ledger の行のロック待ち、データの増え方を毎月出す。
- 費用は毎月見直す（[runbooks/README.md](../runbooks/README.md) の 5 節）。

## 11. テスト

- 性質ではなく、負荷試験（9 節）と、本番の計測で確かめる。合否は QA が判定し、結果の解釈は Dev・QA・PM がレビューする（[roadmap.md](../roadmap.md) の「エージェントに任せないこと」）。
