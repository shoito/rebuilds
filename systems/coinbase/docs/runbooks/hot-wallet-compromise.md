# Runbook: ホットのウォレットの侵害の疑い、異常な出金

- Owner: セキュリティ、Ops（当番）、財務
- 対応するアラート: 方針の外の署名（2 か所の判定の食い違い。page、SEV1）、ホット・ウォームの残高の説明のつかない減り（page、SEV1）、自動の署名の累計の急増、同じ宛先への出金の急増、承認者の端末の異常、署名の境界の想定外の操作（CloudTrail）、入金のアドレスの検証の食い違い（`address-verifier`。page、SEV1 の候補）
- 最終確認日: 2026-11-15

前提の設計は [ADR-0006](../decisions/0006-wallet-tiers-and-cold-ratio.md)（段と上限）、[ADR-0007](../decisions/0007-signing-service-and-key-custody.md)（署名の境界と方針）、[ADR-0008](../decisions/0008-withdrawal-pipeline-and-approvals.md)（出金）、[ADR-0066](../decisions/0066-automatic-withdrawal-tripwires.md)（自動の停止）、[ADR-0071](../decisions/0071-aws-accounts-network-and-egress.md)（アカウントと経路）。流れ出た暗号資産はチェーンの上で取り戻せないので、**最初の 5 分で止める**。

## 症状

- 署名の境界が、オンラインの側が通した依頼を方針の外として拒んだ（オンラインの側が破られたか、方針のバージョンがずれた）。
- ホットかウォームのチェーンの上の残高が、台帳の出金と移し替えで説明できない額だけ減った。
- 自動の署名の累計が急に増えた。登録から間もない宛先、同じ宛先への出金が急に増えた。
- 承認者の端末・アカウントで、普段と違う承認が続いた。
- `address-verifier` が、`deposit_addresses` の行を境界の中の公開鍵から導き直した結果と食い違った（本体のアカウントの侵害で、攻撃者のアドレスを利用者に出している疑い。[deposits.md](../architecture/deposits.md) の 4.2 節）。

## 影響

- 損失の上限は、ホットの残高と、承認を通ってしまったウォームの額である。コールドはオンラインから署名できない。
- 止めている間、暗号資産の出金は止まる。取引所と販売所は止めなくてよい（残高は台帳の中で動く）。

## 確認

1. どの段・資産・鍵の残高が、いつから、いくら減ったか（自前のノードで、ウォレットのアドレスごとに）。
2. 減った分の取引が、出金の記録（`withdrawals`）と署名の境界の記録にあるか。
   - 記録にある：方針を通って署名された取引。承認者・方針のバージョン・宛先の登録を調べる。
   - 記録にない：鍵が境界の外で使われた疑い。最も重い。
3. 方針の判定の食い違いなら、`wallet-orchestrator` と `policy-verifier` の方針のバージョン、直近のデプロイ。
4. アドレスの検証の食い違いなら：食い違った行の数、いつ払い出された行か、その行のアドレスに届いた入金（台帳に記帳されたか、どのアドレスに届いたか）。新しい払い出しは「準備中」で止まっているか。
5. 調べの記録には、ID、額、取引の ID、アドレスだけを書く。利用者の氏名を書かない。

## 対処

1. **止める**（当番が一人でできる）：
   - すべての資産の `ops.hot_auto_signing_enabled.<asset>` と `ops.withdrawals_enabled.<asset>` を切る。
   - 署名の境界の受け付けを止める（境界の側の停止の操作。セキュリティ）。確かな兆しなら、境界の見張りがすでに止めている（移し替えのホット・ウォーム → コールドだけは受ける）。
   - 承認者の端末の鍵の疑いがあれば、その承認者を承認者の一覧から外す（セキュリティと Ops の責任者の 2 人）。
2. **残りを移す**：鍵が境界の外で使われた疑いがあれば、そのホット・ウォームの残りを、新しく作った鍵のウォレット（コールドの側の許可の一覧の宛先）へ移す。移す署名は、まだ破られていないと判断できる経路（コールドの儀式の手順に準じた、承認者 2 人以上の確認）で行う。どの鍵を信じるかは、セキュリティの責任者と IC が決める。
   - **放送の経路**：署名の境界（`custody`）はノードへの経路を持たない。逃がす取引も、境界の中で署名し、普段と同じ出力の経路（署名の依頼の応答）で `wallet-orchestrator` に渡し、`wallet-orchestrator` が放送する（[ADR-0071](../decisions/0071-aws-accounts-network-and-egress.md)、[ADR-0047](../decisions/0047-fee-estimation-and-broadcast-paths.md)）。本体のアカウントの侵害の疑いの中でも、署名済みの取引は中身（宛先、額）を変えられないので、本体の経路で流してよい。本体の側が流さない・遅らせる疑いがあれば、自前のノードと外部の見張りで mempool と取り込みを確かめ、見えなければ同じ取引を流し直す。
3. **入金のアドレス**：入金のアドレスの鍵が同じ根から導かれていれば、新しいアドレスへ切り替え、古いアドレスへの入金は記帳を止めて運用の待ち行列に入れる。
   - **アドレスの検証の食い違い**：新しいアドレスの払い出しを止め（「準備中」）、食い違った行を利用者の画面に出さない。食い違った行を払い出された利用者に、そのアドレスへ送らないよう知らせる（文言は法務）。境界の中の公開鍵から導き直したアドレスで払い出しを作り直し、`address-verifier` の確かめを通してから開ける。攻撃者のアドレスへ送られた入金は本システムに届いていないので、利用者の残高は変わらない。補填の扱いは財務・法務・経営が決める。
4. **追う**：流れた先のアドレスを、チェーン分析の提供者と、相手の交換業者（トラベルルールの経路や業界の連絡の経路）に知らせ、凍結を求める。捜査機関への届け出は法務とコンプライアンスが判断する。
5. **台帳**：流出した額を、利用者用のウォレットの口座から仮勘定（`suspense:wallet_loss`）へ移す仕訳を、財務の 2 人の承認で書く。利用者の残高は変えない（補填と、履行保証暗号資産の扱いは、財務・法務・経営の判断。法務の L2）。
6. **開ける**：原因を取り除き、新しい鍵・新しい方針のバージョン・承認者の一覧を入れ、試験の出金（見張りの口座）を通してから、承認だけの出金 → 自動の署名の順に開ける。開けるのは IC とセキュリティの責任者の 2 人の承認。

## エスカレーション

- 減りが確かめられたら、ただちに SEV1。IC、セキュリティの責任者、財務の責任者、コンプライアンス、法務、経営。
- 当局・自主規制団体への報告と、利用者への知らせの時期と文言は、法務とコンプライアンスが決める（法務の L1・L9・L13）。

## 事後

- 原因（オンラインの部品、方針、承認者、鍵）を `changes/` の `intent.md` に起票する。方針の決定表と性質ベーステストに、すり抜けた形の行と場面を足す（QA の承認）。
- 外部のフォレンジックの結果を記録する。鍵の儀式の手順と、承認者の端末の管理を見直す。
- 移した残り、仮勘定、補填の仕訳を財務が確かめる。
