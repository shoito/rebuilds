# Runbook: `legal.*` の値の変更

- Owner: Ops（適用）、法務・財務（承認）、Dev（PR）
- 対応するアラート: 定期作業（法務の結論の文書が出たとき）。カタログと実際の値の食い違い（日次の検査。チケット、承認の記録のない値は SEV2 の候補）、AppConfig の配布の検証の失敗
- 最終確認日: 2026-11-15

前提の設計は [ADR-0062](../decisions/0062-legal-config-catalog-and-approval.md)（カタログと承認）と [ADR-0075](../decisions/0075-signed-config-bundles-for-policies-and-rules.md)（署名した束。`legal.*` は AppConfig の検証の関数が束の署名を確かめる）。流れの図は [regulatory-compliance-japan.md](../architecture/regulatory-compliance-japan.md) の 4.4 節、例は 4.5 節。

**値の結論は法務が出す。** Dev とエージェントは PR の草案と検査の結果を作れるが、`prod_value` と `approval_ref` を決めない。**急ぎで止めるときは `ops.*` を使い、`legal.*` を書き換えない。**

## 症状

- 法務が結論の文書（L 番号、値、有効の始まり）を出した。
- 有効の期間の終わり（方式の終わりの日など）が近い。
- 日次の検査で、本番の値と `config/legal/` の内容が食い違った。

## 影響

- 値によって、出金の上限、ウォレットの割合、本人確認の方式、記録の保持の期間などが変わる。適用の前後で照合とウォレットの割合を回し、変化を確かめる。
- 1 回に適用するのは、1 つの結論の文書の鍵の束だけ。

## 確認

1. 結論の文書の ID、鍵、値、`effective_from`・`effective_to`。カタログの行（`l_ref`、`when_unset`、`ga_required`）があるか。
2. PR：`prod_value`、`approval_ref`、有効の期間。legal の組み合わせの検査（決定表 DT-REG-001 など）が緑。法務の承認（CODEOWNERS）と、お金に関わる鍵は財務の承認。
3. CI が作った束の署名が揃っているか（承認者の鍵）。
4. 適用の時間帯（平日の昼）。凍結の期間でないこと。

## 対処

1. **前**：照合（台帳とウォレット・銀行・信託）とウォレットの割合を回し、結果を記録する。
2. **適用**：Ops が AppConfig にマージしたバージョンを適用する。検証の関数が束の署名を確かめる。東京と大阪に同じ変更で入る。
3. **後**：照合とウォレットの割合をもう一度回す。値を使う領域の指標（たとえば `legal.hot_ratio_max` なら割合と P01 の拒否の数）を 1 時間見る。
4. **記録**：`legal_config_changes` に、鍵、前後の値、承認の記録、適用の者と時刻を書く。
5. **戻す**：戻すときも同じ手順で、承認の記録つきの次のバージョンとして入れる。値が誤っていて害が出ているときは、先に `ops.*` で止め、そのあと法務と戻す値を決める。

### 食い違いの検出のとき

1. 本番の値が `config/legal/` にない、または承認の記録がない：誰がいつ入れたかを AppConfig の記録と CloudTrail で確かめる。
2. 承認のない値が効いていれば、関わる機能を `ops.*` で止め、SEV2 の候補として IC に上げる。

## エスカレーション

- 検証の関数が束を受けない（署名の不足、バージョンの連続の誤り）：セキュリティ。改ざんの疑いなら SEV1 の候補。
- 適用の後に照合の差が出た：財務と [ledger-reconciliation-mismatch.md](ledger-reconciliation-mismatch.md)。

## 事後

- 適用の記録を、結論の文書の ID と結んで残す。カタログの `ga_required` の鍵が揃ったかを GA の判定の前に確かめる（PROP-REG-003）。
