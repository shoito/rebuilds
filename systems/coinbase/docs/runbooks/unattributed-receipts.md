# Runbook: 持ち主の分からない受け取りと対応しない資産の到着

- Owner: 財務、CS、Ops
- 対応するアラート: `unattributed_receipts` か `unsupported_receipts` に 7 日を超えた行が 1 件（チケット）、待ち行列の急増
- 最終確認日: 2026-11-15

前提の設計は [deposits.md](../architecture/deposits.md) の 7.3 節（例外の受け取り）と [ADR-0041](../decisions/0041-eth-deposit-detection-and-sweep.md)。どの受け取りも、台帳とチェーンの照合で「記帳していない既知の受け取り」として説明に使う（[segregation-and-reconciliation.md](../architecture/segregation-and-reconciliation.md)）。

| 受け取り | 入る表 | 扱い |
| --- | --- | --- |
| trace に出ない ETH の受け取り（契約の自己破壊による送金など） | `unattributed_receipts` | 持ち主を確かめ、財務の 2 人の承認で記帳する |
| 本システムのウォレット（ホット・ウォーム・コールド、本システムの財産）への直の受け取り | `unattributed_receipts` | 同上 |
| ERC-20 のトークン | `unsupported_receipts` | 記帳しない。返却は MVP で扱わない（PM の判断待ち） |
| 最小の額に満たない入金 | `below_minimum` | 記帳しない（CS が問い合わせに答える） |

## 症状

- 利用者から「送ったのに反映されない」の問い合わせがあり、入金の記録にない。
- 待ち行列に古い行が残っている。

## 影響

- 利用者の残高に入らない。照合では説明のつく差だが、溜まると説明の材料が古くなる。

## 確認

1. 行の受け取りの種類、チェーン、取引の ID、受け取ったアドレス、額、着いた時刻。
2. 受け取ったアドレスが利用者の入金のアドレスか、本システムのウォレットか。利用者の入金のアドレスなら、その口座の ID（記録に、アドレスと口座の ID を同じ行で書かない）。
3. 利用者からの申し出があるか（CS の案件の番号）。

## 対処

1. **持ち主の確かめ**：利用者の申し出（送った取引の ID、送り元、額、時刻）と、チェーンの上の取引を照らす。送り元が他の交換業者なら、トラベルルールの通知の有無も確かめる（[aml-and-travel-rule.md](../architecture/aml-and-travel-rule.md) の 7.2 節）。
2. **スクリーニング**：記帳の前に、通常の入金と同じ規則でスクリーニングする。`compliance_review` に当たれば、そちらで判断する。
3. **記帳**：持ち主が確かめられ、スクリーニングを通ったら、財務の 2 人の承認で記帳する（入金の仕訳と同じ型。冪等キーは取引の ID と出力の番号）。出金に使えるまでの止めは通常の入金と同じ（[ADR-0039](../decisions/0039-deposit-state-machine-and-withdrawal-lock.md)）。
4. **持ち主が分からない**：行を残し、30 日ごとに見直す。最終の扱い（本システムの財産にしない、保管を続ける）は法務の確認待ち（L14 に近い。新しい問いとして intent に足す候補）。
5. **ERC-20**：利用者に「対応していない資産で、今は返却できない」と答える（文言は法務の L12 の確認の後の型）。トークンは入金のアドレスに残し、集め直さない。

## エスカレーション

- 1 件が 100 万円相当を超える、同じ形が 1 日に 10 件を超える：財務の責任者と Ops（入金の検出の誤りでないかを Dev のテックリードと確かめる）。
- 本システムのウォレットへの大きな直の受け取り：攻撃の準備（アドレスの確かめ）や誤送金の可能性。セキュリティに知らせる。

## 事後

- 確かめた件数、記帳した件数と額、残る件数を毎月記録する。
- trace に出ない受け取りが続くなら、検出の方法を deposits の領域で見直す。
