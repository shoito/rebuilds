# Runbook: AZ とリージョンの障害（DR）

- Owner: Ops の責任者、IC
- 対応するアラート: 本番のエンジンの停止と写しへの切り替え（page）、MSK のブローカーの停止、Aurora Global Database の遅延、ノードの AZ の障害、東京のリージョンの障害、半年ごとの DR の訓練
- 最終確認日: 2026-11-15

目標は、AZ の障害で板の再開まで RTO 5 分、リージョンの障害で板を止めてから大阪で再開する RTO 4 時間、台帳の RPO 1 分（NFR-011）。構成の詳細は infrastructure の領域（工程 2 で書く）。

## 症状

- 1 つの AZ のエンジン・sequencer・MSK のブローカー・ノード・Fargate のタスクが同時に使えない。
- 東京のリージョンの複数の部品（Aurora、MSK、ECS、NLB）が同時に使えない。AWS の Health Dashboard にリージョンの障害が出ている。
- 大阪への複製の遅れが続く。

## 影響

- AZ の障害：数秒〜5 分、注文の受け付けが止まるか遅れる。受け付けを返した注文は MSK の他の AZ の写しにあり、失わない。
- リージョンの障害：取引所・販売所・入出金が止まる。板は止めたまま大阪で作り直す。入力の記録の大阪への写しの遅れの分（目標 1 秒）の入力は失いうる。

## 確認

1. AZ の障害か、リージョンの障害か。
2. AZ の障害なら：写しのエンジンが最後に処理した `seq` と、MSK の入力の最後の `seq`。sequencer の持ち主の記録（`sequencer_leases`）の epoch。
3. リージョンの障害なら：東京の回復の見込み。大阪の Aurora の二次の遅れ、S3 に写した入力の記録とスナップショットの最後の `seq`、大阪の待機のノードの同期。
4. 署名の境界（`custody` のアカウント）の大阪の待機の状態。

## 対処

**AZ の障害（多くは自動）**

1. 写しのエンジンが出力の書き手になり、sequencer は別の AZ のタスクが持ち主の記録を取って epoch を上げる（[ADR-0002](../decisions/0002-sequencer-and-event-journal.md)）。切り替えの記録と、エンジンの番号の連続の検査が緑であることを確かめる。
2. 自動の切り替えが 5 分で終わらなければ、板を止め（[market-halt.md](market-halt.md)）、手で切り替える。
3. MSK の `min.insync.replicas=2` を割った区画があれば、書き込みが止まる（受け付けを返さない）。ブローカーの回復を待つ。値を下げない。
4. ノードの片方が落ちたら、入金の記帳は 2 台の比べができずに止まる（[ADR-0009](../decisions/0009-deposits-confirmations-and-own-nodes.md)）。大阪の待機のノードを比べの相手に入れる（Ops の判断。手順は `node-ops-poc` の後に確定）。

**リージョンの障害（IC と Ops の責任者が決める。東京の回復の見込みが 1 時間を超えるとき）**

1. 板を止めたことを確かめる（東京のエンジンが止まっていれば入力は入らない）。大阪の AppConfig で `ops.trading_enabled.*`、`ops.brokerage_enabled.*`、`ops.withdrawals_enabled.*`、`ops.fiat_withdrawals_enabled`、`ops.deposit_crediting_enabled.*` を止める。
2. 切り替えの始まりの時刻を記録する。
3. Aurora の二次（core、ledger、kyc-vault）を昇格する。
4. 大阪の MSK とエンジンを起こし、S3 の最後のスナップショットと写した入力の記録から、板ごとに再生する。再生の最後の `seq` を記録する。
5. 失った入力の範囲（東京で受け付けて大阪に届かなかった `seq`）を、東京の `order-gateway` の受け付けの記録（Aurora core の注文の行）と比べて出す。失った注文は「取り消し」として利用者に知らせ、拘束を戻す。失った入力の後の約定は起きていない扱いにする（財務とコンプライアンスと合意する）。
6. 台帳と再生の結果の照合：エンジンの出力の約定と、台帳の約定の記帳を `trade_seq` で照らす。大阪に届いた記帳の後の約定がないことを確かめる。
7. 板を取り消しだけで開け、利用者が注文を確かめる時間（既定 30 分）を置いてから取引中にする（2 人の承認）。
8. 入出金は、ノードと署名の境界の大阪の待機を確かめ、照合が 0 になってから開ける。

**東京へ戻す**：計画作業として、板を止める時間帯を決め、同じ確かめをする。

## エスカレーション

- 再生の結果と台帳の照合が合わない：SEV1。Dev のテックリードと財務。
- 失った入力の扱い（利用者への知らせ、約定の扱い）：IC、PM、コンプライアンス、法務。

## 事後

- RTO・RPO の実測、失った入力の範囲、照合の結果を記録と振り返りに残す。
- 半年ごとの訓練では、staging で同じ手順を回し、再生の時間とエンジンの起動の時間を測る（`dr-drill-market-restart`）。
