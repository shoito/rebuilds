# Runbook: 規制の報告の書き出しと提出

- Owner: コンプライアンス、財務
- 対応するアラート: 定期作業（報告の定義の頻度ごと）。報告の材料の照合の差（提出を止める）、作り直しのハッシュの違い（チケット）、報告の実行の失敗
- 最終確認日: 2026-11-15

前提の設計は [ADR-0064](../decisions/0064-regulatory-report-exports.md)（報告の定義と実行、`as_of` の読み、2 人の確かめ、提出は人が行う）。定義の候補と例は [regulatory-compliance-japan.md](../architecture/regulatory-compliance-japan.md) の 6 節。**どの報告が要るか、様式、頻度、期限、提出の手段は法務の確認待ち（L1・L2・L3・L9・L10）で、提出の手段は未検証である。** 本システムは外へ自動で送らない。

## 症状

- 報告の期日が近い（`report_definitions` の頻度）。事象ごとの報告（`REP-INCIDENT`）が要ると法務が判断した。
- 作り直しの試しで、ハッシュが前と違った。

## 影響

- 期日を過ぎると、当局・協会への義務の違反になりうる（法務の判断）。誤った中身の提出は、訂正の報告を要する。

## 確認

1. 定義の ID とバージョン、`as_of`、宛先、期日。
2. 材料の照合：`as_of` の時点の台帳とウォレット・銀行・信託の照合の差が 0 か。開いた [ledger-reconciliation-mismatch.md](ledger-reconciliation-mismatch.md) の件がないか。
3. 個人の項目が要る報告（`REP-TAX` など）は、`kyc-vault` の `reportSubject()` で定義が求める項目だけを読んでいるか。

## 対処

1. **実行**：定義のバージョンと `as_of` で報告を作る。中身のハッシュを `report_runs` に記録する。出力は書き出し専用の S3 の場所に、報告ごとの鍵で暗号化して置かれる。
2. **確かめ**：作成者と別の 2 人（コンプライアンスの担当）が、前回との差と照合の結果を見て確かめる。お金の数を含む報告は、財務が前日の照合の差 0 を確かめる。
3. **提出**：担当が提出する（手段は法務の結論の後に書く）。受付の番号と提出の時刻を `report_runs` に書く。
4. **再現の試し**：提出の後に、同じ定義と `as_of` で作り直し、ハッシュが同じことを確かめる。

### ハッシュが違ったとき

1. 提出の前なら、提出を止める。`as_of` より後の行を読んでいる材料の問い合わせの誤りが多い。
2. 提出の後なら、財務とコンプライアンスに知らせ、どちらの中身が正しいかを確かめる。誤りが提出した側にあれば、訂正の要否を法務が判断する。
3. 材料の問い合わせを直し、定義のバージョンを上げる（`config/reports/` の PR。コンプライアンスと財務の CODEOWNERS）。

## エスカレーション

- 期日に間に合わない：コンプライアンスの責任者と法務（期限の延長の相談の要否）。
- 照合の差が期日の前日までに解けない：財務の責任者。差の説明を添えて出すかを法務と決める。

## 事後

- 実行、確かめ、提出、再現の試しの記録を残す（出力の保持は既定 1,826 日。法務の L9）。
- 様式の変化や項目の追加は、定義の新しいバージョンとして起票する。
