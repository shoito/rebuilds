# Runbook: 販売所の在庫の補充と処分

- Owner: 財務、Ops
- 対応するアラート: 作業。在庫の `|d|` が 0.5 を超えた状態が 1 営業日続いた（チケット）、`d` が ±1 で片方の向きの提示を止めた、日本円の在庫が 1,000 万円を下回った
- 最終確認日: 2026-11-15

前提の設計は [ADR-0025](../decisions/0025-brokerage-inventory-target-and-replenishment.md) と [brokerage-quotes.md](../architecture/brokerage-quotes.md) の 4.5 節。MVP の補充と処分は、本システムの財産の受け入れと払い出しだけで、取引所の板での在庫の調整とヘッジは持たない（PM の判断待ち P3、法務の確認待ち L7）。補充する暗号資産をどこから、どう得るかも法務の L7 の問いで、この手順はその結論の後に確定する。**利用者の財産を在庫に使わない。**

## 症状

- 在庫の暗号資産が目標 `T`（BTC 5 億円、ETH 2 億円の円換算）から大きく外れ、片方の向きのスプレッドが広がっている、または提示が止まっている。
- 日本円の在庫（目標は 2 つの資産の `T` の和の 1.5 倍）が、利用者の売りの 1 回の最大（1,000 万円）を下回った。

## 影響

- 在庫が偏ると、偏りを増やす向きの価格が不利になる。上限・下限で、その向きの提示が止まる。

## 確認

1. 資産ごとの在庫の円換算、`d`、日本円の在庫、24 時間の評価の損失。
2. 本システムの持ち分の精算の待ち（[house-settlement-stuck.md](house-settlement-stuck.md)）。精算が遅れて在庫が偏って見えていないか。
3. 補充・処分の元と先：暗号資産は本システムのウォレット（`house_wallet`）、日本円は本システムの口座（`bank:house`）。利用者用のウォレットと利用者の金銭の口座を使わない。

## 対処

1. **作る**：財務が運用の画面で補充・処分の依頼を作る（資産、額、向き、元と先、理由）。
2. **承認**：作成者と別の 2 人が承認する。
3. **暗号資産の受け入れ・払い出し**：`house_wallet` への受け入れ、または `house_wallet` からの払い出し。払い出しの宛先は本システムのウォレットの許可の一覧に限る（[ADR-0007](../decisions/0007-signing-service-and-key-custody.md)）。署名の方針の外なら署名されない。
4. **日本円**：本システムの口座との振り替え（[fiat-and-banking.md](../architecture/fiat-and-banking.md)）。
5. **仕訳を確かめる**：`house_inventory` と本システムの財産の口座の間の仕訳が、チェーンの取引・銀行の振り替えと一致することを確かめる。照合（[ledger-reconciliation-mismatch.md](ledger-reconciliation-mismatch.md)）が 0 であること。
6. `d` が戻り、止めていた向きの提示が自動で再開したことを確かめる。

## エスカレーション

- 補充の資金が足りない、在庫の目標の値を変えたい：財務の責任者、PM（目標と上限は承認の設定の変更）。
- 補充の取得の方法（法務の L7）に当たる判断：法務。結論までは本システムの財産の受け入れだけにする。

## 事後

- 依頼、承認者、取引の ID、仕訳の ID を `brokerage_inventory_ops` に残す。月ごとに、補充と処分の回数と額を財務が見直す。
