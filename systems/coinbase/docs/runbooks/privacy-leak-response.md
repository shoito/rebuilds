# Runbook: 個人のデータの漏れの疑い

- Owner: セキュリティ、Ops（当番）、法務、コンプライアンス
- 対応するアラート: ログの走査で個人のデータ・秘密の形（メールアドレス、電話番号、口座の番号、チェーンのアドレスと利用者の ID の組、API キーの形）を検出（page、SEV1 の候補）、CS の担当者の参照の上限・急増の知らせ、`kyc-vault` の見る操作の異常、外部からの届け（漏れたデータの売り出しの報告など）
- 最終確認日: 2026-11-15

前提の設計は [security.md](../architecture/security.md) の 8 節（データの区分とログに出してよいか）・11 節、[ADR-0054](../decisions/0054-kyc-vault-purpose-api-and-retention.md)（金庫の読む関数と監査）、[ADR-0065](../decisions/0065-operator-access-and-cs-view-scope.md)（CS の画面）、[ADR-0069](../decisions/0069-telemetry-schema-without-secrets.md)（秘密を持たない計測）。漏えい等の報告の要否、期限、本人への通知は法務が判断する（法務の確認待ち：L11）。この手順はその判断の材料を揃えるところまでを書く。

## 症状

- `app` のログに、出してはならない形の値が出た（[observability.md](../architecture/observability.md) の 5 節の走査）。
- CS の担当者、コンプライアンスの担当が、案件に結び付かない参照や上限を超える参照をした。
- 外部から、利用者のデータと思われるものの漏れの届けがあった。

## 影響

- 漏れたデータは戻らない。範囲を早く狭めるほど、本人への知らせと詐欺の被害が小さくなる。
- ログの行を消す間、調べに使うログが一部見えなくなる。

## 確認

1. **ログの検出**：どのサービスの、どの版（デプロイ）から、どのログ群の、どの時間の範囲か。形ごとの件数。ログを読める役割と、その範囲の読み出しの記録。
2. **人の参照**：担当者の ID、参照した口座の数と項目の種類、時刻（監査のアカウントの記録。ハッシュの鎖が続いているか）。
3. **外部の届け**：届いたデータの項目の種類と、本システムのどの区分に当たるか（金庫・本人・お金・チェーン）。項目の組み合わせから出どころの候補を絞る。
4. 調べの記録には、ID、件数、項目の種類、時刻だけを書く。漏れた値そのものを、調べの記録やチケットに貼らない。

## 対処

1. **止める**：
   - ログの検出：出したサービスを前のイメージに戻すか、その出力を止めるフラグを切る（[deploy-and-rollback.md](deploy-and-rollback.md)）。API キーの形なら、該当のキーを止め、利用者に作り直しを求める。
   - 人の参照：疑いのある担当者の権限を止める。委託先なら [vendor-access-suspend.md](vendor-access-suspend.md)。
2. **保全する**：監査の記録と、該当のログの範囲の写し（読める役割をセキュリティに限った場所）を、消す前に作る。
3. **消す**：該当の行の範囲を、ログの置き場所（CloudWatch Logs、S3 の保管）から消し、消した範囲・件数・者・時刻の記録を残す（セキュリティと Ops の 2 人）。
4. **範囲を数える**：影響した口座の数と、口座ごとの項目の種類の表を作る（ID だけ）。
5. **法務に渡す**：範囲の表、時間の範囲、原因、止めた時刻を法務とコンプライアンスに渡す。報告・通知の要否と時期は法務が決める（L11）。

## エスカレーション

- 金庫の区分（本人確認の書類、氏名・住所・生年月日、口座の番号）か、秘密（API キーの秘密、鍵の材料）が含まれる：SEV1。IC、セキュリティの責任者、法務、コンプライアンス、PM。
- 鍵の材料・承認の署名の中身の疑い：[hot-wallet-compromise.md](hot-wallet-compromise.md) を並べて行う。

## 事後

- 原因（ログの書き方、計測の属性、担当者の権限）を `changes/` の `intent.md` に起票する。漏れの経路の表（[quality.md](../quality.md) の 2.2.1 節 I）と走査の形に、すり抜けた形を足す（QA の承認）。
- 保全した写しは、法務の決める期間の後に消す。
