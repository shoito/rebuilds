# Runbook: 重要な情報の事象の取扱い

- Owner: コンプライアンス、監視の責任者
- 対応するアラート: 定期作業（重要な情報の候補が出たとき）、一覧の者の口座の止めの反映の失敗（チケット）、公表の後の `SUR-INSIDER-1` の兆し
- 最終確認日: 2026-11-15

前提の設計は [ADR-0061](../decisions/0061-staff-trading-and-material-information.md)（役職員の取引と重要な情報の台帳）。台帳の形は [market-surveillance.md](../architecture/market-surveillance.md) の 6.2 節。**何が重要事実に当たるか、売りをどこまで止めるか、家族を含めるかは法務の確認待ち（L7）。** この手順は、本システムの既定（新しい買いを止める）で、開く・公表する・閉じるの順を書く。

## 症状

公表の前の重要な情報の候補が出た。例：銘柄の取扱いの開始・終了の決定、流出などのセキュリティの事故、販売所の大きな在庫の処分、当局の処分。

## 影響

- 一覧の者（役職員と外部の関係者のうち口座を持つ者）の口座に `restricted`（`staff_blackout`）が立ち、新しい買いが止まる。
- セキュリティの事故のときは、事故の対応の人数が増えるほど一覧が長くなる。

## 確認

1. 事象の種類、知った時刻、持ち主（コンプライアンスの担当）。
2. 今知っている者の一覧（役職員の ID か外部の関係者の ID）。事象を画面で見た者は自動で一覧に足される。
3. 一覧の者の口座（`person_key` と `staff_registry` で結んだもの）と、立った止めの行。

## 対処

1. **開く**：コンプライアンスが `material_info_events` に事象を開く。セキュリティの事故なら、IC がまず開くよう求める（事故の対応と並べて行う。[hot-wallet-compromise.md](hot-wallet-compromise.md) など）。
2. **一覧を作る**：知っている者を `insider_lists` に足す（理由つき）。口頭で知らせた者も足す。外部の関係者（委託先、監査、弁護士）は外部の ID で足す。
3. **止める**：一覧の者の口座に `staff_blackout` が立つのを確かめる。反映の失敗があれば手で立てる（コンプライアンスと 2 人目）。
4. **知る者を増やさない**：事象の詳細は、一覧の者だけが見られる案件の画面に置く。チャットやチケットに中身を書かない。
5. **公表**：公表の時刻を事象に記録する。公表の前 30 日の、一覧の者と結び付いた口座の取引を `SUR-INSIDER-1` が調べる。兆しが出れば、監視の案件として扱う。
6. **閉じる**：公表の時刻の 1 営業日後に `staff_blackout` は自動で外れる（[account-restriction-release.md](account-restriction-release.md)）。公表しないで終わる事象（決定の取りやめ）は、コンプライアンスの責任者の判断で閉じ、閉じた時刻の 1 営業日後に外す。

## エスカレーション

- 公表の前に、一覧の者の取引の兆しが出た：監視の責任者とコンプライアンスの責任者。法務（L7）。
- 重要な情報が外に漏れた疑い（報道、SNS）：コンプライアンスの責任者と法務。公表を早めるかを経営と決める。

## 事後

- 事象、一覧の人数、止めた時間、公表の後の調べの結果を記録する（保存は `legal.surveillance_record_retention_days`）。
- 事象の種類の例を、法務の L7 の結論で直す。
