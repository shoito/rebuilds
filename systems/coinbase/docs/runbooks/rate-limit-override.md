# Runbook: 速さの上限の一時の引き上げ

- Owner: Ops、PM
- 対応するアラート: 作業（マーケットメイカーの口座からの引き上げの申請）。期限の切れた上書きが残っている（チケット）
- 最終確認日: 2026-11-15

前提の設計は [ADR-0020](../decisions/0020-rate-limit-tiers-and-cancel-budget.md) と [order-entry-and-risk.md](../architecture/order-entry-and-risk.md) の 4.8 節。値の一覧は [README.md](README.md) の 2 節。**段の値そのものは変えない。** 変えてよいのは、口座ごとの期限つきの上書きだけで、Ops と PM の 2 人の承認を要する。

## 症状

- マーケットメイカーの口座（または `api_standard` の口座）が、注文・取り消し・照会の上限の一時の引き上げを申請した（新しい銘柄の開始、相場の急変への備えなど）。
- または、期限の切れた上書きが計数の設定に残っている。

## 影響

- 引き上げた口座の注文が、板ごとの全体の上限（新しい注文 1 秒 5,000 件）の枠を多く使う。他の利用者の `market_busy` の率が上がりうる。
- 注文の山は、ledger の残高の行のロック待ちを増やす（[order-entry-degraded.md](order-entry-degraded.md)）。

## 確認

1. 口座の段（`app`・`api_standard`・`api_mm`）。`api_mm` の段は PM の判断待ち P1 の結論まで使わない（[intent.md](../intent.md)）。
2. 申請の理由、期間、求める値（注文・取り消し・照会、瞬間の値、板ごとの注文の数）。
3. その口座の直近の注文の数、取り消しの率、`market_busy` に当たった数。
4. 板ごとの全体の上限に対して、引き上げた後の余裕。相場の大きな変動の間（参照の価格が 1 時間で 10% 以上動いた）は受けない。

## 対処

1. 申請を運用の画面に記録する（口座、値、期限、理由）。期限は最長 7 日（本システムの値。Ops と PM で合意する）とし、期限のない上書きを作らない。
2. Ops と PM の 2 人（どちらも申請の作成者と別）が承認する。
3. 上書きを Valkey の計数の設定に入れ、`order-gateway` の各タスクが読んだことを確かめる。取り消しの枠は注文の 2 倍の関係を保つ（取り消せないことが最も危ない）。
4. 期間中、その口座の注文の速さ、全体の上限への寄与、残高の行のロック待ちを見る。他の利用者の `market_busy` が増えたら、上書きを取り消す（取り消しは Ops が 1 人でできる）。
5. 期限で上書きを消す。期限の切れた上書きは毎日の検査でチケットになる。

## エスカレーション

- 段の値そのものを変えたい：ADR-0020 の見直しとして Dev のテックリードと PM へ（運用で変えない）。
- 上書きの口座が不公正取引の兆しに当たった：コンプライアンス（[market-surveillance.md](../architecture/market-surveillance.md)）。

## 事後

- 上書きの記録（口座、値、期間、承認者）を残し、毎月の見直しで、繰り返す申請を段の見直しの材料にする。
