# ADR-0014: 出力の要約を SHA-256 の連鎖にし、スナップショットの点を seq で決める

## Context

[ADR-0002](0002-sequencer-and-event-journal.md) は、出力の各行が要約のハッシュの連鎖（`output_hash[seq]`）を持ち、10 万入力ごとと板の停止のたびにスナップショットを作ると決めた。次が決まっていない。

- 何をハッシュするか、どのハッシュの関数を使うか。
- スナップショットを作る点を、本番と写しで同じにできるか。点がずれると、写しは本番のスナップショットを確かめられない。
- スナップショットのファイルが壊れた・書き換えられたことを、読み込む側がどう見つけるか。

## Options

要約：

1. **`SHA-256(前の要約 ‖ seq ‖ その入力の出力の列の符号化)`**
2. 出力の件数と主な項目の和（チェックサム）
3. 状態の全体のハッシュを入力ごとに計算する

スナップショットの点と確かめ：

- a. **`seq` と入力の種類だけで点を決め、`engine-core` が状態のハッシュを `SnapshotMarker` として出力に出す。ファイルはそのハッシュで確かめる**
- b. `engine-host` が時間で点を決め、ファイルの中にだけハッシュを持つ

## Decision

1 と a を採用する。

- 要約の対象は、その入力の出力（`InputDigest` を除く）を [ADR-0012](0012-engine-io-encoding-and-ticks.md) の符号化で並べたバイト列である。ハッシュの関数は SHA-256 で、監査を受けた汎用の crate を使う（暗号の処理を自作しない。AGENTS.md）。
- `output_hash[0]` は、板の作成の時の固定の値（板の名前と設定のバージョンの SHA-256）にする。
- スナップショットの点は、`seq` が 100,000 の倍数の入力と `Halt` の入力の処理の後（ADR-0002）。`engine-core` は状態を正規の順（向き、価格、`seq`）で符号化し、その SHA-256 を `SnapshotMarker` に入れて出す。マーカーも要約の対象になる。
- ファイルは書き手のエンジンだけが S3 に書く（オブジェクトのロックで上書きと削除を禁じる）。読み込む側は、ファイルの状態のハッシュが記録の `SnapshotMarker` と一致するときだけ使い、合わなければ 1 つ前のスナップショットを使う。
- 日次の再生（ADR-0002）は、前日の最初のスナップショットから前日の全部の入力を流し、全部の `InputDigest` と `SnapshotMarker` を本番と比べる。

### 他の案を選ばなかった理由

- **2**：中身の違う出力（約定の相手の入れ替わり）で同じ値になりうる。
- **3**：100 万件の注文の板で、入力ごとに状態の全体を読むと 1 入力 100µs（NFR-002）に収まらない。出力の連鎖は、状態の違いが出力に現れた時点で食い違いを見つける。状態の全体はスナップショットの点で比べる。
- **b**：本番と写しで点がずれ、写しが本番のスナップショットを確かめられない。ファイルの中のハッシュだけでは、ファイルごと差し替えられたことを見つけられない。

## Consequences

- 良くなること：
  - 出力の 1 ビットの違いも、その `seq` で見つかる。
  - 出力に現れない状態の違いも、スナップショットの点で見つかる。
  - スナップショットの改ざんと壊れを、記録との照合で見つけられる。
- 引き受けるコスト：
  - 入力ごとの SHA-256 の計算（出力の数百バイトで 1µs 前後と見込む。`engine-latency-poc` で確かめる）。
  - 出力に現れない状態の違いは、最大 10 万入力の間、見つからない。

## Confirmation

- 性質（PROP-ME-2）：任意の列の任意の点のスナップショットから再生した要約が、通しの要約と一致する。
- 試験：スナップショットのファイルの 1 バイトを変えると、読み込みが拒む。
- 本番：写しの `SnapshotMarker` の比べと、日次の再生の結果を SLI にする（[runbooks/README.md](../runbooks/README.md) の 1 節のエンジンの決定性）。
