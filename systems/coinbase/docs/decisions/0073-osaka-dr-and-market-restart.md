# ADR-0073: 大阪で入力の記録を追い続け、再生の終わりを正として板を再開する

## Context

リージョンの障害では、板を止めてから大阪で再開する RTO 4 時間、台帳の RPO 1 分（Aurora Global Database）、入力の記録の RPO は写しの遅れ（目標 1 秒）とする（NFR-011）。失った入力は利用者に取り消しとして知らせる（[runbooks/disaster-recovery.md](../runbooks/disaster-recovery.md)）。

決めていないのは、次のことである。

- 入力と出力の記録（MSK）を、どう大阪に写すか。毎時の S3 への移し（[ADR-0002](0002-sequencer-and-event-journal.md)）では、RPO が 1 時間になる。
- 大阪のエンジンを、障害の後に起こすか、普段から動かしておくか。
- 台帳（Aurora ledger）と入力の記録は別の仕組みで写すので、大阪に届いた範囲が揃わない。大阪の台帳に、大阪の記録の再生では出てこない約定の記帳が残りうる。逆に、大阪の記録の再生で出る約定の記帳が、大阪の台帳にないこともある。
- 署名の境界、ノード、銀行の経路の大阪の待機。

## Options

入力の記録の写し方：

1. S3 への毎時の移しだけ
2. **MSK Replicator で、入力と出力のトピックを大阪の MSK に写し続ける**
3. 自前の写しの部品（MirrorMaker 2 を Fargate で動かす）

大阪のエンジン：

- a. 障害の後に起こし、スナップショットから再生する
- b. **大阪に 1 台を置き、写した入力を読み続けて板を追い、出力の要約を写した出力と比べ続ける（出力は書かない）**

台帳と記録の範囲の違い：

- x. 東京の `ledger-poster` が、約定の入力が大阪に写ったことを確かめてから記帳する
- y. **大阪の記録の再生の終わり（最後の `seq`）を正にし、その後の約定の記帳は打ち消しの仕訳で戻す。足りない記帳は、再生の出力から `ledger-poster` が足す**

## Decision

2、b、y を採用する。

### 大阪に常に置くもの（S1）

| 部品 | 大阪の形 |
| --- | --- |
| Aurora（core、ledger、kyc-vault） | Global Database の二次（reader 1 台） |
| MSK | 3 ブローカー。MSK Replicator で、東京の入力と出力のトピックを写す |
| マッチング | `match-osaka-1` の 1 台。写した入力を読み、両方の板を追い、要約を写した出力と比べる |
| S3 | スナップショットと記録の長期の保管を、リージョンをまたいで写す |
| ノード | BTC・ETH の待機の各 1 台（組）（[ADR-0009](0009-deposits-confirmations-and-own-nodes.md)） |
| 署名の境界 | `custody-prod` の大阪の待機。方式は `custody-signing-poc` の結論に従う |
| Fargate のサービス | 最小のタスク（各 1）。障害の時に広げる |
| AppConfig | 東京と同じフラグの値（`release.*`・`ops.*`・`legal.*`）を、同じ変更で両方に入れる |
| 銀行・提供者の出口 | 固定の IP を東京と同時に登録済み（[ADR-0071](0071-aws-accounts-network-and-egress.md)） |
| `watch` | 主を大阪に置く（[ADR-0068](0068-correctness-monitors-and-independent-watch.md)） |

- `match-osaka-1` の比べは、本番と写しの比べと同じ要約を使う。大阪で食い違えば、写しの仕組みか決定性の誤りで、チケットにする（本番の板は止めない。本番と写しの比べが正）。
- 写しの遅れ（MSK Replicator の遅れ、`match-osaka-1` が追った最後の `seq` と東京の最後の `seq` の差）を SLI にし、1 秒を目標に、10 秒を 5 分超えたら呼び出す。MSK Replicator の遅れの値は公式の資料で確かめていない（**未検証**）。`engine-latency-poc` と同じ時期に測り、1 秒に届かなければ 3 を比べる。

### 切り替えの手順の要点

1. IC と Ops の責任者が切り替えを決める（東京の回復の見込みが 1 時間を超えるとき）。大阪の AppConfig で `ops.*` を止める。
2. Aurora の二次を昇格する。
3. `match-osaka-1` が追った最後の `seq`（板ごとの `S_r`）を確定する。大阪の MSK の写した入力の最後と一致することを確かめる。
4. 板ごとに、新しい `epoch` で大阪の sequencer を起こし、`S_r + 1` から番号を付ける。東京で受け付けた `S_r` より後の入力は失ったものとして扱う。
5. **台帳と記録を揃える**：
   - 再生の出力にあって大阪の台帳にない約定は、`ledger-poster` が `(pair, trade_seq)` の冪等キーで記帳する（通常の処理）。
   - 大阪の台帳にあって、`S_r` までの再生の出力にない約定（`trade_seq` が再生の最後より大きい）は、打ち消しの仕訳で戻す。財務の 2 人の承認で、一覧と口座ごとの影響の和を先に出す（Stripe の [delivery.md](../../../stripe/docs/architecture/delivery.md) の 5.3 節の訂正の形）。
   - 失った入力の注文（core の注文の行にあり、`S_r` までの記録にない）は、取り消しにし、拘束を戻す。
6. 板を取り消しだけで開け、30 分の後に取引中にする（2 人の承認）。
7. 入出金は、照合が 0 になり、ノードと署名の境界の大阪の待機を確かめてから開ける。

- 打ち消しの対象の利用者への知らせ方と、約定の扱いの説明は、法務とコンプライアンスの確認を要する（失った約定を「なかったもの」とする扱いの整理）。結論まで、手順の 5 の第 2 項は、IC・財務・コンプライアンスの合意で 1 件ずつ行う。

### 他の案を選ばなかった理由

- **1**：RPO が 1 時間になり、NFR-011 の目標（写しの遅れ 1 秒）に届かない。
- **3**：運用の部品が増える。管理のサービスで足りるかを先に測る。
- **a**：再生にかかる時間（前のスナップショットから 10 万入力の内。S1 で数分の見込み）は RTO 4 時間に収まるが、大阪での比べがなく、写しが壊れていても切り替えの時まで分からない。
- **x**：記帳の遅れに、リージョンをまたぐ写しの遅れが入り、NFR-005（約定から記帳まで p99 1 秒）を満たせない。大阪の障害で東京の記帳が止まる。

## Consequences

- 良くなること：
  - 大阪の写しと再生を、障害の前から毎日確かめられる。
  - 切り替えの後の台帳と板の範囲が、再生の終わりという 1 つの点で決まる。
- 引き受けるコスト：
  - 大阪に MSK と EC2 を常に持つ（費用は capacity の領域）。
  - 切り替えの後に、記帳の打ち消しが出うる。利用者への説明が要る。
  - フラグの値を 2 つのリージョンに入れる手順が要る（delivery の領域）。

## Confirmation

- 半年ごとの DR の訓練（`dr-drill-market-restart`）で、staging で東京を止め、手順の 3〜6 を回し、RTO 4 時間の内であること、打ち消しと取り消しの一覧が再生の結果と一致することを確かめる。
- 性質ベーステスト（`chain-sim` と同じ枠の再生の模型）：任意の写しの遅れ（記録と台帳で別々）で、手順の 5 の後、台帳の約定の記帳の集合と、`S_r` までの再生の約定の集合が一致する。
- 写しの遅れの SLI を常に計る。
