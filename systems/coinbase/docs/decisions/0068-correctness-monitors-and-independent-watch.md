# ADR-0068: 正しさの見張りを別のアカウントの独立の経路で持つ

## Context

この題材で最も悪い障害は、止まることでなく、エラーにならずに残る誤りである（[quality.md](../quality.md) の冒頭）。方針の外の署名、二重の出金、写しのエンジンとの要約の食い違い、台帳とチェーンの差は、5xx にも遅れにも出ない。気づくのは、比べ（要約、照合）と、外からの見張り（`canary`）だけである。

- 比べと照合の結果は、本体のアカウントの部品（写しのエンジン、`reconcilers`、`rebalancer`）が出す。本体の可観測性の経路（ADOT → AMP → Alertmanager）が止まると、比べの結果が届かず、「アラートがない」が「誤りがない」に見える。
- 侵害の時、攻撃者は本体のアカウントの中の部品と、その見張りの両方に触れうる。ホットのウォレットの流出を、本体の中の見張りだけで見つけるのは弱い。
- 本家は 2026 年 5 月に、1 つの AZ の冷却の障害でマッチングエンジンの多数の節が止まり、数時間取引を止めた（報道。[observability.md](../architecture/observability.md) の 3 節）。外からの見張りは、内部の指標より先に利用者の側の止まりを示す。
- Datadog の題材は、監視のサービス自身を別のアカウントの経路で見張る形を決めている（[Datadog の ADR-0062](../../../datadog/docs/decisions/0062-independent-self-monitoring-path.md)）。

## Options

1. 比べ・照合・`canary` の結果を、本体の可観測性の経路だけで扱う
2. **比べ・照合の結果を、本体の経路に加えて、別のアカウント（`watch`）の独立の経路にも送る。`canary` と、チェーンの上のウォレットの残高の見張り、デッドマンスイッチを `watch` に置く**
3. 外部の監視の SaaS に、比べの結果と `canary` を任せる

## Decision

2 を採用する。

- **`watch` のアカウント**：本体（`prod`）と署名の境界（`custody`）と別の AWS アカウントに置く（[ADR-0071](0071-aws-accounts-network-and-egress.md)）。本体のアカウントのロールからは、`watch` の中の資源を変えられない（SCP で拒む）。
- **送るもの**：正しさの SLI（runbooks の 1 節で「品質の判定に使う」に○があるもの）の結果を、1 分ごとの心拍として、`watch` の取り込みの口（SQS のキュー。リソースポリシーで `prod` と `custody` の決めたロールだけ）に送る。中身は、SLI の名前、窓、件数、最後に確かめた `seq` か時刻、送り手のビルドのバージョン。個人のデータと秘密を含めない（[ADR-0069](0069-telemetry-schema-without-secrets.md)）。
- **デッドマンスイッチ**：`watch` は、心拍が 5 分届かない SLI を「確かめられていない」として呼び出す。確かめられない間は、その SLI を緑として扱わない。
- **`watch` が自分で確かめるもの**：
  - `canary`：見張りの口座の注文と取り消し（5 分ごと）、販売所の購入（15 分ごと）、板の配信の購読を、本体の公開の口（`api.<brand>.<domain>`、`ws.<brand>.<domain>`）から行う（[quality.md](../quality.md) の 4.2 節）。本番で約定させるか、入出金を見張るかは [observability.md](../architecture/observability.md) の 4.5 節の未決の問い。
  - チェーンの上のウォレットの残高：本システムのホットとウォームのアドレスの残高を、`watch` が持つ外部のノードの提供者（本体と別の契約）から 10 分ごとに読み、前の値からの減りを、本体が報告した出金と移し替えの和と比べる。説明のつかない減りを呼び出す（[runbooks/hot-wallet-compromise.md](../runbooks/hot-wallet-compromise.md)）。外部の結果は見張りにだけ使い、台帳と記帳に使わない（[ADR-0009](0009-deposits-confirmations-and-own-nodes.md)）。
- **呼び出しの経路**：`watch` のアラートは、本体の Alertmanager を通らず、`watch` の SNS から当番の呼び出しの提供者へ直接送る。

### 他の案を選ばなかった理由

- **1**：本体の経路の停止と、本体のアカウントの侵害の時に、正しさの見張りが一緒に止まる。
- **3**：外部の SaaS に、ウォレットのアドレスと出金の和を渡すことになる。利用者のデータの外への提供（法務の L11）と、外部への委託の管理（法務の L13）が増える。

## Consequences

- 良くなること：
  - 本体の可観測性の経路が止まっても、正しさの見張りが「確かめられていない」として呼び出す。
  - 本体のアカウントが破られても、ホットの残高の減りを別の経路で見つけられる。
- 引き受けるコスト：
  - アカウント、外部のノードの提供者の契約、呼び出しの経路を、もう 1 組持つ。
  - 心拍の送り忘れ（新しい SLI を足したとき）を、CI の検査で止める運用が要る。

## Confirmation

- CI：runbooks の 1 節の「品質の判定に使う」の行ごとに、心拍の送り手と `watch` の受け手の定義があることを検査する。
- 障害の注入（夜間、staging）：本体の ADOT と AMP を止め、5 分で `watch` が呼び出すことを確かめる。
- 半年ごとの DR の訓練で、`watch` の呼び出しが東京のリージョンの障害の間も届くことを確かめる（`watch` は大阪に置く。[ADR-0071](0071-aws-accounts-network-and-egress.md)）。
