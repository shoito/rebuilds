# ADR-0070: 取引の経路は急変の最大を常設で持ち、自動の拡大に頼らない

## Context

相場の急変では、板の入力が平常の 30 倍（S1 で 3,000 件/秒）に、分の単位で上がる（[architecture/README.md](../architecture/README.md) の 2 節、[quality.md](../quality.md) の 2.2.1 節 H）。

- 急変は予告がない。目標の追跡によるオートスケールは、計測・判断・タスクの起動で数分かかる。その間に受け付けの遅れ（NFR-001 の p99 20ms）と配信の遅れ（NFR-002）が崩れる。
- 急変の間こそ、利用者は注文と取り消しをしたい。取り消しが遅れると、利用者は意図しない約定を負う。
- Aurora の writer とマッチングの EC2 は、そもそも自動では大きくならない。
- 常設を大きくすると、平常の時の費用が増える（[architecture/capacity.md](../architecture/capacity.md) の 8 節）。

## Options

1. **取引の経路の部品は、S1 の最大を、1 つの AZ を失っても受ける量で常設する。自動の拡大は常設の上に足すだけにする**
2. 目標の追跡のオートスケールで、平常の量から広げる
3. 予定した拡大（時刻で広げる）と 2 の組み合わせ

## Decision

1 を採用する。

- 対象は `trading-api`、`order-gateway`、`ledger`、`ledger-poster`、`md-publisher`、`ws-gateway`、sequencer と engine、Aurora ledger と core の writer。
- 常設の量は、S1 の最大（板の入力 3,000 件/秒、約定 300 件/秒、配信の接続 2 万）を、3 つの AZ のうち 1 つを失っても受ける量（最大の 1.5 倍）にする。Aurora の writer は、最大で CPU 50% 以下の型にする。
- 自動の拡大は、常設の上に CPU の目標で足すだけにし、減らすのは常設の量までにする。
- 他の部品（`app-api`、通知、運用の画面、照合と入出金の Worker）は、目標の追跡で拡大する。
- 常設の量は、負荷試験（LT-1・LT-2）と週次の最大の使用率で見直し、最大の時に 60% を超えたら増やす。

### 他の案を選ばなかった理由

- **2**：急変の最初の数分を受けられない。急変は分の単位で始まる。
- **3**：急変は時刻で予定できない。予定できる山（指標の発表など）にだけ効く。

## Consequences

- 良くなること：
  - 急変の最初の数分も、NFR-001・NFR-002 を保てる。
  - AZ の障害と急変が重なっても受けられる。
- 引き受けるコスト：
  - 平常の時の使用率が低い。取引の経路の費用が、平常の量の何倍かになる（capacity の 8 節）。
  - 最大の見込みを超える急変（S1 の想定の外）は受けられない。速さの上限の段（order-entry-and-risk の領域）で入力を絞る。

## Confirmation

- 負荷試験：LT-1（急変）と LT-2（急変と AZ の障害）で、自動の拡大を止めた状態でも NFR-001・NFR-002・NFR-005 を満たす。
- Terraform の検査：対象の部品の最小のタスク数が、常設の量を下回らない。
- 週次の運用：最大の時の使用率の記録。
