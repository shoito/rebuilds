# ADR-0004: 注文は sequencer の前に台帳で拘束し、client_order_id で冪等にする

## Context

利用者は、同じ残高で同時に複数の注文・出金・販売所の購入を出せる。どの組み合わせでも、使える残高を超えて通ってはいけない（NFR-004）。

- エンジンは残高に触れない（[ADR-0002](0002-sequencer-and-event-journal.md)）。残高の確かめをエンジンに入れると、エンジンが板ごとに分かれているため、板をまたいだ同じ日本円の二重の使用を止められない（BTC/JPY と ETH/JPY の両方に同じ 100 万円で買いを出す）。
- 注文の送信は、利用者の端末・API・ネットワークの再送で重なる。同じ注文が 2 度板に入ってはいけない。
- 拘束を書いた後に、sequencer への送信が失敗することがある。拘束だけが残ると、利用者の残高が理由なく減って見える。

## Options

1. **注文の前に、台帳（Aurora ledger）の残高の行の条件つきの更新で拘束を書き、それから sequencer に送る**
2. 口座ごとに分けたメモリーのリスクの部品（自分の記録を持つ）が拘束を持ち、台帳には後から書く
3. 先に板に入れ、約定の後に台帳で確かめる（足りなければ約定を取り消す）

## Decision

1 を採用する。

### 拘束

- `order-gateway` は、注文の検査（刻み、最小の数量、価格の帯の目安、口座の状態、速さの上限）の後、`ledger` の拘束の API を呼ぶ。
- `ledger` は 1 つのトランザクションで次を書く（[ADR-0005](0005-ledger-balances-and-trade-settlement.md)）。
  - 残高の行の条件つきの更新：`UPDATE balances SET available = available - $a, hold = hold + $a WHERE account_id = $1 AND asset = $2 AND available >= $a`。1 行が更新できなければ「残高の不足」を返す。
  - 拘束の行（`holds`：`hold_id`、`source_type = order`、`source_id = order_id`、額、残り）。
  - 拘束の仕訳（`available:<asset>` から `hold:<asset>` への振り替え）。
- 拘束の額：

| 注文 | 拘束 |
| --- | --- |
| 指値の買い | `floor(指値 × 数量)` ＋ テイカーの手数料の上限（その額に率を掛けて切り上げ） |
| 指値の売り | 数量 |
| 成行の買い（金額の指定） | 指定の金額（手数料を含む） |
| 成行の買い（数量の指定） | `floor(価格の帯の上の端 × 数量)` ＋ 手数料の上限 |
| 成行の売り | 数量 |

- 約定・取り消し・期限切れのたびに、`ledger-poster` が拘束の残りを使うか戻す。注文が `done` になったら、拘束の残りは 0 になる。

### 冪等

- 利用者は `client_order_id`（API は必須、画面は端末が生成）を付ける。core の注文の表に `(account_id, client_order_id)` の一意の制約を置く。同じ値の再送には、最初の結果（`order_id`、状態）を返す。内容が違えば 409 を返す。
- `order_id`（UUIDv7）は拘束の前に決め、拘束の冪等キー（`order:<order_id>:hold`）と sequencer の入力に使う。sequencer は直近の `order_id` を板ごとに覚え（入力の記録から作り直せる）、同じ `order_id` の 2 度目の入力を板に入れずに、最初の `seq` を返す。

### 届かなかった注文

- 注文の行は `pending_submit` → `accepted`（`seq` を受けた）→ エンジンの状態（`open`、`done`）の順に進む。
- `reconcilers` は 5 秒ごとに、10 秒を超えて `pending_submit` の注文を拾い、同じ `order_id` で sequencer に送り直す。60 秒を超えても受け付けられないとき（板の停止など）は、取り消しの入力を送り、拘束を戻して利用者に知らせる。
- 5 分ごとに、拘束の残りの和と、エンジンの未約定の注文の必要額の和（出力の記録から作った写し）を口座と資産ごとに比べる（NFR-004）。

### S2 以降の熱い口座

- マーケットメイカーの口座は 1 秒に数百の注文と取り消しを出し、残高の行が熱くなる。S2 では、口座の残高をスロットに分ける（[Stripe の ADR-0016](../../../stripe/docs/decisions/0016-hot-accounts-and-ledger-sharding.md)）。それでも足りなければ、2 を口座の組に限って入れる ADR を書く（order-entry-and-risk の領域）。

### 他の案を選ばなかった理由

- **2**：拘束の正本が台帳の外にでき、出金・販売所と同じ残高の取り合いを 2 か所で見ることになる。部品の障害の時の作り直しの設計が S1 から要る。
- **3**：足りない注文が板で約定し、相手の利用者の約定を後から取り消すことになる。公正さを壊す。

## Consequences

- 良くなること：
  - 注文・出金・販売所の購入が、同じ残高の行の条件つきの更新で並ぶ。どの組み合わせでも二重に使えない。
  - 板をまたいだ同じ残高の使用を止められる。
  - 再送と送り直しで、同じ注文が 2 度板に入らない。
- 引き受けるコスト：
  - 注文の受け付けの遅れに、Aurora の 1 回の commit（数 ms）が入る（NFR-001 の 20ms の中）。
  - 取り消しの後の拘束の戻りは、エンジンの出力の記帳を待つ（p99 1 秒）。

## Confirmation

- 性質ベーステスト：任意の注文・取り消し・約定・出金・販売所の購入の並行の列で、`available >= 0`、拘束の和 ＝ 必要額の和。本物の PostgreSQL 18（Testcontainers）と並行度 2〜200 で回す。
- 性質：同じ `client_order_id` からの注文は板に 1 回だけ入る。
- 照合（5 分ごと）の不一致を SLI にし、1 件でチケット、口座の負の残高は 1 件で呼び出す。
