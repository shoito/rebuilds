# ADR-0075: 方針と規則の表を、承認者が署名した設定の束として出す

## Context

この題材は、お金・約定・署名の規則をフラグにせず、コードとバージョンの付いた設定として出す（AGENTS.md、[runbooks/README.md](../runbooks/README.md) の 3 節）。コードでない「バージョンの付いた設定」は、次の 5 つある。

| 設定 | 使う部品 | 承認（既存の決定） |
| --- | --- | --- |
| 署名の方針の決定表、承認者の公開鍵の一覧、本システムのウォレットの許可の一覧 | `wallet-orchestrator`、`policy-verifier`、`approval-verifier` | 2 人の承認の署名（[ADR-0007](0007-signing-service-and-key-custody.md)）。セキュリティと財務 |
| スクリーニングと取引の監視の規則の表 | `compliance` | コンプライアンスの承認（[ADR-0011](0011-external-providers-boundary.md)） |
| 資産の設定（入金の閾値など） | `deposit-watcher`、`wallet-orchestrator` | Dev とセキュリティ（[ADR-0009](0009-deposits-confirmations-and-own-nodes.md)） |
| 銘柄の設定（刻み、価格の帯、手数料の表の参照） | sequencer を通してエンジン | Dev と Ops の 2 人（[ADR-0003](0003-matching-rules-and-self-trade-prevention.md)） |
| `legal.*` の値 | 各部品（AppConfig） | 法務と財務の承認の記録（[roadmap.md](../roadmap.md) の `flags-and-legal-config`） |

承認の形はそれぞれ決まっているが、どう作り、どう届け、どう有効にするかは決めていない。特に署名の方針は、2 か所（`wallet-orchestrator` と `policy-verifier`）の判定が食い違えば署名しない（ADR-0007）ので、切り替えの途中で 2 か所のバージョンが違うと、正しい出金も止まる。逆に、届いた設定を受け手が確かめなければ、`prod` のアカウントが破られたときに、方針を書き換えた設定を `custody` に送り込まれる。

## Options

1. それぞれの設定を AppConfig のフラグと同じ経路で出し、承認は PR のレビューだけにする
2. **設定の種類ごとに、リポジトリの `config/<kind>/` から CI が束（内容、バージョン、ハッシュ）を作り、承認者がハッシュに署名する。受け手は署名とバージョンを自分で確かめてから有効にする**
3. 署名の方針だけを 2 にし、他は 1 にする

## Decision

2 を採用する。

### 束の作り方

1. 変更は `config/<kind>/` への PR で行う。CODEOWNERS は種類ごとの承認の持ち主（`config/signing-policy/` はセキュリティと財務、`config/legal/` は法務と財務、`config/compliance-rules/` はコンプライアンス、`config/assets/` と `config/instruments/` は Dev のテックリード。[roadmap.md](../roadmap.md) の `dev-repo-bootstrap`）。
2. CI は、表駆動のテスト（決定表の全行）と、束の検査（項目の型、値の範囲、`legal.*` の内側にあること）を回す。署名の方針の束は、`wallet-orchestrator` と `policy-verifier` の同じパッケージのバージョンで判定が一致することを確かめる。
3. マージの後、CI が束を作る。束は、種類、単調に増えるバージョン、前のバージョンのハッシュ、内容、内容のハッシュを持つ。
4. 承認者が、運用の画面で束の差分を見て、ハッシュに自分の鍵（端末のパスキーかハードウェアの鍵）で署名する。署名の数と役割は、種類ごとに上の表のとおり。作成者（PR の作者とマージした人）の署名は数えない。AI エージェントは署名者にならない。

### 受け手の確かめ

- 受け手は、束の署名が承認者の公開鍵の一覧の鍵で、数と役割を満たし、バージョンが今より大きく、前のバージョンのハッシュが今のものと一致することを確かめてから有効にする。どれかが欠けたら有効にせず、呼び出す。
- 承認者の公開鍵の一覧そのものは、署名の方針の束に入れ、前の一覧の鍵で署名する（一覧を変える束は、変える前の承認者が署名する）。
- `policy-verifier` は束を `custody-prod` の中に置き、`prod` からは束を「届ける」ことしかできない。届けた束を有効にするかは境界の中で決める。

### 有効にする手順

| 種類 | 手順 |
| --- | --- |
| 署名の方針 | `ops.hot_auto_signing_enabled.<asset>` を止める → 古いバージョンで判定した手続き中の依頼が署名か差し戻しで片付くのを待つ → `policy-verifier` で有効にする → `wallet-orchestrator` で有効にする → 試験の出金を通す → 2 人の承認で開ける。猶予の期間（新旧の両方を受ける時間）は置かない |
| 規則の表、資産の設定 | 束に有効の時刻を書き、受け手はその時刻から使う。判定の記録に規則のバージョンを残す |
| 銘柄の設定 | 束を、sequencer を通した銘柄の設定の変更の入力にする（ADR-0002）。板の停止の時間の中で入れる |
| `legal.*` | AppConfig の検証の関数（Lambda）が束の署名を確かめてから値を受ける。東京と大阪に同じ変更で入れる。平日の昼に Ops が適用し、前後で照合とウォレットの割合を回す |

### 他の案を選ばなかった理由

- **1**：PR のレビューの承認は、GitHub と CI の経路が破られれば越えられる。受け手が承認を確かめないので、`prod` のアカウントから方針を書き換えられる。
- **3**：規則の表と `legal.*` は資産を直接動かさないが、スクリーニングの規則を緩めた設定で制裁の対象に送金でき、`legal.hot_ratio_max` を大きくした設定でホットの額を増やせる。どちらも取り戻せない誤りにつながるので、同じ確かめにする。

## Consequences

- 良くなること：
  - 方針と規則の変更に、誰が承認したかが署名で残り、受け手がそれを確かめる。CI や `prod` が破られても、承認のない設定は有効にならない。
  - 束のバージョンとハッシュの鎖で、どの判定がどの設定で行われたかを後から辿れる。
- 引き受けるコスト：
  - 設定の変更のたびに、承認者の署名の手間がかかる。
  - 署名の方針の切り替えの間、ホットの自動の署名が止まる（数分を見込む）。
  - 承認者の鍵を失ったときの回復の手順が要る（custody-and-keys の領域）。

## Confirmation

- 性質ベーステスト：任意の束の列（署名の欠け、同じ人の 2 つの署名、作成者の署名、古いバージョン、前のハッシュの食い違い）で、受け手が有効にするのは、規則を満たす束だけ。
- 障害の注入（staging）：署名の方針の切り替えの途中で `wallet-orchestrator` と `policy-verifier` のバージョンが違う時間に、方針の外の署名 0。
- 毎週、署名の方針のバージョンと境界の記録を照らし合わせる（[runbooks/README.md](../runbooks/README.md) の 5 節）。
