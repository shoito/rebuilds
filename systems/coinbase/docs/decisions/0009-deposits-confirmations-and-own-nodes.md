# ADR-0009: 入金は自前のノード 2 台で確かめ、閾値の後に記帳する

## Context

暗号資産の入金は、本システムが作るものでなく、チェーンの上で起きたことを見つけて記帳するものである。

- ブロックは後から鎖から外れることがある（巻き戻り）。外れたブロックの入金は、なかったことになる。記帳した後に外れると、利用者はない資産を使える（K6）。
- BTC は、ブロックが積み重なる（承認の数）ほど外れにくくなる。ETH は、合意の仕組みでブロックが「確定（finalized）」すると、外れるには大量の掛け金を失う必要がある。
- 外部の提供者の API で入金を確かめると、提供者の誤りや侵害を、そのまま記帳する。
- 合意の規則（ブロックの検証）を自前で書くのは、題材の核ではなく、誤りの影響が大きい（AGENTS.md）。
- 入金は、利用者ごとに見分けられなければならない。

## Options

ノード：

1. **汎用のクライアント（Bitcoin Core、Ethereum の実行のクライアントと合意のクライアント）を自前で 2 台以上動かし、外部の提供者は見張りにだけ使う**
2. 外部のノードの提供者（RPC の提供）だけを使う
3. 自前のノードを 1 台にする

閾値：

- a. **BTC は 3 承認で記帳、6 承認で出金に使える。ETH は確定（finalized）で記帳**
- b. BTC は 1 承認で記帳。ETH は 12 ブロックで記帳
- c. BTC は 6 承認で記帳

入金のアドレス：

- x. **BTC は利用者ごとに導出したアドレス（監視だけの公開鍵から導く）。ETH は利用者ごとのアドレス（方式は PoC で決める）**
- y. 共有のアドレスと、利用者ごとの付記（タグ）

## Decision

1、a、x を採用する。

### ノード

- BTC は Bitcoin Core を 2 台、ETH は実行のクライアントと合意のクライアントの組を 2 組、別の AZ に置く。大阪に待機の 1 台（組）を置く。ETH のクライアントの種類（少数派のクライアントを選ぶか、2 組で違う種類にするか）は `node-ops-poc` で決める。
- ノードの RPC は、本体のアカウントの中の `deposit-watcher`・`wallet-orchestrator` と、署名の境界の放送の部品だけに開く。P2P の通信は、ノードの専用のサブネットから出す（infrastructure の領域）。

> 2026-11-15 の注記（統合）：「署名の境界の放送の部品」は置かない。署名の境界（`custody` のアカウント）はノードへの経路を持たず、放送はすべて `wallet-orchestrator` が行う（[ADR-0071](0071-aws-accounts-network-and-egress.md)、[ADR-0047](0047-fee-estimation-and-broadcast-paths.md) の注記）。下の「自前の頭が 3 ブロック・2 エポック以上遅れたら記帳を止める」は止めの閾値で、[runbooks/README.md](../runbooks/README.md) の SLO（2 ブロック・1 エポック以内）は目標である。食い違いではない。
- 外部のノードの提供者を 1 つ、見張りに使う。自前のノードの頭のブロックが外部より 3 ブロック（BTC）・2 エポック（ETH）以上遅れたら、入金の記帳を止めてアラートを出す。外部の結果で記帳しない。

### 記帳の規則

- 入金の状態は `detected` → `confirming` → `credited`、または `detected` → `reorged`（記帳の前に外れた）、`credited` → `reversed_suspense`（記帳の後に外れた）。
- 記帳の条件は、閾値に届いたこと、自前のノード 2 台（組）が同じブロックの ID と同じ入金（取引の ID、出力の番号、額、アドレス）を返したこと、入金のスクリーニングを通ったこと（[ADR-0011](0011-external-providers-boundary.md)）。2 台が食い違ったら、その資産の入金の記帳を止める。
- 記帳の冪等キーは `(deposit, <chain>, <txid>, <vout または log の番号>)`。
- BTC は 3 承認で記帳するが、6 承認までは、その額を出金に使えない（出金の拘束の対象から外す）。注文と販売所には使える。ETH は確定で記帳し、すぐに出金にも使える。

> 2026-11-15 の注記（統合）：6 承認の前の止めは、その額だけでなく口座の全部の出金（暗号資産と日本円）にする（[ADR-0039](0039-deposit-state-machine-and-withdrawal-lock.md)、[ADR-0029](0029-hold-kinds-and-withdrawal-restrictions.md) の注記）。入金した BTC を売った日本円や、その日本円で買った ETH で持ち出す経路を閉じるためである。
- 閾値は資産ごとの設定（バージョンつき）で持ち、相場と攻撃の費用で見直す（deposits と chain-nodes-and-confirmations の領域）。
- 記帳の後に入金のブロックが外れたら、その額をその利用者の `user_available` から拘束し（足りなければ負の分を `suspense` に置く）、その資産の入金の記帳を止める（[runbooks/chain-reorg.md](../runbooks/chain-reorg.md)）。

### 入金のアドレス

- BTC：利用者と資産ごとに、ネイティブ SegWit のアドレスを階層的な鍵の導出（BIP32・BIP84 の形）で払い出す。`deposit-watcher` は監視だけの公開鍵（xpub）だけを持ち、秘密鍵は署名の境界の中にだけある。
- ETH：利用者ごとのアドレスに入金を受け、利用者用のホットのウォレットへ集め直す。方式は 2 つを `eth-deposit-sweep-poc` で比べる。(i) 利用者ごとの通常のアドレス（鍵は署名の境界で導出。集め直しの手数料を本システムが送る）、(ii) 1 つの契約から決まった形で作る転送の契約（契約のコードの監査が要る）。結論までは (i) を既定にする。

> 2026-11-15 の注記（統合）：(i) の「集め直しの手数料を本システムが送る」は、ERC-20 のトークンを扱うときにだけ要る。ETH 本体の集め直しは、入金のアドレス自身の残高から手数料を払い、`network_fee_expense:ETH` に記帳する（[ADR-0041](0041-eth-deposit-detection-and-sweep.md)）。手数料を本システムが持つことは変えない。
- ERC-20 のトークンの入金は MVP で扱わない。トークンが ETH のアドレスに届いたら、記帳せず、運用の待ち行列に入れる。

### 他の案を選ばなかった理由

- **2**：入金の正しさを提供者に預ける。提供者の誤り・侵害・遅れがそのまま記帳になる。
- **3**：ノードの不具合・遅れ・分かれを見つけられない。更新の間に入金が止まる。
- **b**：BTC の 1 承認は、外れることが珍しくない。ETH の 12 ブロックは、確定の仕組みの後では根拠が弱い。
- **c**：入金の待ちが長くなる（およそ 1 時間）。3 承認で記帳し、出金を 6 承認まで止めれば、二重の使用の外への持ち出しを防げる。
- **y**：ETH の通常の送金に付記の欄がなく、付記を忘れた入金の持ち主を決められない。

## Consequences

- 良くなること：
  - 入金の正しさを、自前の 2 台のノードの一致で決める。外部の提供者の誤りを記帳しない。
  - BTC の入金は 3 承認（およそ 30 分）で注文に使え、外への持ち出しは 6 承認まで止める。
- 引き受けるコスト：
  - ノードの運用（同期、ディスク、クライアントの更新、分かれへの対応）を持つ。
  - ETH の集め直しの手数料がかかる。
  - ETH の確定は通常およそ十数分かかる（**未検証**。`node-ops-poc` で計る）。

## Confirmation

- 性質ベーステスト（`chain-sim`：任意の深さの巻き戻り、ノードの分かれ、遅れ、重複の通知）：記帳した入金のブロックが閾値の後に外れる場面以外で、`credited` の後の `reversed_suspense` 0。巻き戻りで消えた入金が出金に使われた件数 0。2 台が食い違う間の記帳 0。
- 結合の試験：bitcoind の regtest と Ethereum の開発用のチェーンで、巻き戻りを作って記帳の規則を確かめる。
- SLI：自前のノードと外部の見張りの頭の差、記帳の停止の時間。
