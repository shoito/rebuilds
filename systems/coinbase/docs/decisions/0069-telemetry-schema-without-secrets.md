# ADR-0069: 秘密と個人のデータを含まない計測の型を 1 か所で決める

## Context

ログ・メトリクス・トレースは、本番の調べに最もよく使われ、最も多くの人と道具が読む。この題材では、次のものが計測に混ざると、それ自体が事故になる。

- 本人確認の書類、氏名・住所・生年月日、口座の番号、メールアドレス、電話番号、API キー、鍵の材料、承認の証跡の中身（AGENTS.md、NFR-016）。
- チェーンのアドレスと取引の ID を、利用者の ID と同じ行に書くこと。チェーンは公開なので、行が漏れると、利用者の資産と取引の全履歴が誰にでも辿れる（AGENTS.md）。
- 本家の 2025 年の事故は、サポートの委託先の担当者が利用者のデータを引けたことで起きた（[architecture/README.md](../architecture/README.md) の 1.4 節）。ログを広く読める人が多いほど、同じ形の持ち出しの面が広がる。

加えて、計測そのものがエンジンの決定性を壊しうる。`engine-core` は壁の時計を使えない（[ADR-0001](0001-platform-and-stack.md)、[ADR-0002](0002-sequencer-and-event-journal.md)）。トレースの文脈を入力の記録に入れると、記録の形と再生の結果に計測が入り込む。

Stripe の題材は、カード番号を型・lint・流れの途中の走査で止める形を決めている（[Stripe の observability.md](../../../stripe/docs/architecture/observability.md) の 4.2 節）。

## Options

1. 各サービスが自由に構造化ログを書き、ログの基盤のマスキングで伏せる
2. **計測の項目を `packages/telemetry` の許可の一覧で 1 か所に決め、型と lint で一覧の外の項目を止める。チェーンの識別子は利用者の ID と別の流れに分ける。エンジンの計測は `engine-host` だけが行い、入力の記録にトレースの文脈を入れない**
3. 2 に加えて、チェーンのアドレスと取引の ID を、計測では常に鍵つきのハッシュにする

## Decision

2 を採用する。

### 項目の許可の一覧

- `packages/telemetry`（TypeScript）と `crates/telemetry`（Rust）に、ログの項目、メトリクスのラベル、スパンの属性を定数で定義する。両者は同じ一覧（Protocol Buffers の 1 つの定義）から生成する。
- 一覧にない項目、要求と応答の本文の全体、ヘッダーの全体をロガーに渡すコードを、CI の lint で拒む。
- 個人のデータと秘密は、専用の型（`Pii<T>`、`Secret<T>`）に入れる。ロガーとスパンの属性の関数は、その型を受け取ると型の検査で失敗する。`toString`・`toJSON` は伏せ字を返す。

### チェーンの識別子の分け方

- チェーンのアドレス、取引の ID、出力の番号は、**チェーンの流れ**（`chain` のロググループ）にだけ書く。この流れの行は `deposit_id`・`withdrawal_id`・`transfer_id`（本システムの内部の ID）を持てるが、`account_id`・`user_id` を持たない。
- 本体の流れ（`app` のロググループ）は `account_id` と `withdrawal_id` を持てるが、アドレスと取引の ID を持たない。
- 2 つをつなぐのは、内部の ID と core の表だけで、読むには期限つきの権限が要る（[Auth0 の ADR-0056](../../../auth0/docs/decisions/0056-operator-access.md)）。
- `chain` のロググループの読み手は、Ops とセキュリティの決めた役割だけにする。CS の役割は読めない。

### エンジンとトレース

- 入力と出力の記録（MSK）に、トレースの文脈（`traceparent`）を入れない。記録の形は決定性と再生の契約で、計測の都合で変えない。
- 注文の経路のスパンは `trading-api` → `order-gateway` → sequencer までで閉じ、sequencer のスパンに `pair`・`seq`・`epoch` を属性として付ける。エンジンの側（`engine-host`、`ledger-poster`、`md-publisher`）は、`(pair, seq)` を属性に持つ別のスパンを作り、同じ `(pair, seq)` でつなぐ。
- `engine-core` は計測の呼び出しを持たない。`engine-host` が、入力を渡す前と出力を受けた後に、単調な時計で処理の時間を測る。

### メトリクスの値

- 金額と数量のメトリクスは監視にだけ使い、正本にしない（正本は台帳。[ADR-0005](0005-ledger-balances-and-trade-settlement.md)）。Prometheus の値は浮動小数点で、wei の額は正確に表せない。照合の差は、`reconcilers` が整数で計算し、メトリクスには差の件数と、差の円換算の額（監視用、1 円未満を切り捨て）だけを出す。
- ラベルに `account_id`・`order_id`・`withdrawal_id`・アドレスを使わない。ラベルは `pair`、`asset`、`tier`（hot・warm・cold）、`service`、`az`、`outcome`、`reason_code` のような値の少ないものに限る。

### 他の案を選ばなかった理由

- **1**：伏せるのは基盤に届いた後で、届くまでの経路（エラーの応答、Collector の一時の保管、開発者の手元のログ）では伏せられない。伏せ方の規則の漏れを見つけられない。
- **3**：アドレスはチェーンの上で公開で、ハッシュの値は取引の調べ（入金の確かめ、放送の追跡）に使えない。鍵つきのハッシュの鍵の管理も増える。行を分けるほうが、調べに使え、漏れたときの害も小さい。

## Consequences

- 良くなること：
  - 漏れの経路が型と lint で止まり、エージェントの書き忘れも CI で落ちる。
  - ログが漏れても、利用者とチェーンの履歴がつながらない。
  - 計測を変えても、記録の形と再生の結果が変わらない。
- 引き受けるコスト：
  - 入金と出金の調べで、2 つの流れを内部の ID でつなぐ手間が増える。
  - 注文から約定までが 1 つのトレースにならず、`(pair, seq)` で 2 つをつなぐ道具（Grafana のリンク）が要る。

## Confirmation

- lint：ロガーとスパンの属性に、一覧の外の項目、`Pii<T>`・`Secret<T>`、本文とヘッダーの全体を渡すコードを拒む。
- 漏れの経路の表（[quality.md](../quality.md) の 2.2.1 節 I）の行ごとに、合成の利用者の値がログ・トレース・エラーの応答に出ないことを試験で確かめる（`pnpm test:leaks`）。
- 本番の `app` のロググループを、購読のフィルターで走査し、BTC と ETH のアドレスの形、API キーの接頭辞（`<brand>_live_`）を見つけたら呼び出す。
- lint：`engine-core` が `telemetry` の crate に依存しないこと。入力と出力の記録の Protocol Buffers の定義に、トレースの項目がないこと。
