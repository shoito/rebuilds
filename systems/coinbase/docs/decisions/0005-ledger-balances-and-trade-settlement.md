# ADR-0005: 台帳を引き継ぎ、資産ごとの釣り合いと拘束と約定の記帳を足す

## Context

お金の正本の一般の設計は、他の題材で決めている。

- 追記だけの複式簿記、残高は仕訳の和、誤りは打ち消しの仕訳（[Stripe の ADR-0003](../../../stripe/docs/decisions/0003-double-entry-ledger.md)）。
- すべての書き込みの冪等（[Stripe の ADR-0004](../../../stripe/docs/decisions/0004-idempotency.md)）。
- 台帳・提供者・銀行の 3 者の照合と仮勘定（[Stripe の ADR-0017](../../../stripe/docs/decisions/0017-three-way-reconciliation-with-suspense.md)）。
- 取引ごとの預かりと、一意の制約で 1 回だけの振り替え（[メルカリの ADR-0003](../../../mercari/docs/decisions/0003-escrow-and-double-entry-ledger.md)）。

この題材で違うのは次のところで、ここではその差分だけを決める。

- 資産が複数ある（日本円、BTC、ETH）。1 つの約定が 2 つの資産を同時に動かす。
- 使える残高と拘束を分けて持ち、注文・出金・販売所が同じ残高を取り合う（[ADR-0004](0004-order-entry-holds-and-idempotency.md)）。
- 約定はエンジンの出力から来る。台帳は約定を作らず、記帳するだけ。
- 照合の相手に、チェーンの上のウォレットの残高が入る。
- 利用者の財産と本システムの財産を分けて管理する（法務の L2・L3）。

## Options

1. **他の題材の台帳を引き継ぎ、資産の列、拘束の口座、約定の仕訳の型、ウォレットの口座を足す**
2. 資産ごとに別の台帳を持ち、約定ごとに 2 つの台帳を別々に書く
3. 残高の表だけを持ち、約定で直接増減する

## Decision

1 を採用する。

### 口座の種類（MVP）

| 口座の種類 | 持ち主 | 意味 |
| --- | --- | --- |
| `user_available:<asset>` | 利用者ごと | 使える残高 |
| `user_hold:<asset>` | 利用者ごと | 注文・出金・販売所の受け入れで拘束した残高 |
| `user_pending_deposit:<asset>` | 利用者ごと | 見つけたが閾値に届かない入金（記帳はしない。表示だけに使う写しで、台帳の口座にしない） |
| `wallet:<tier>:<asset>` | 本システムのウォレットごと | 利用者用のホット・ウォーム・コールドのウォレットに実際にある暗号資産 |
| `house_wallet:<asset>` | 本システムのウォレットごと | 本システムの暗号資産（手数料の収益の暗号資産、販売所の在庫、履行保証暗号資産）を置くウォレット |
| `house_inventory:<asset>` | 本システム | 販売所の在庫（[ADR-0010](0010-brokerage-quotes-and-inventory.md)） |
| `fee_revenue:<asset>` | 本システム | 取引の手数料、出金の手数料の収益 |
| `network_fee_expense:<asset>` | 本システム | 出金で実際に払ったチェーンの手数料 |
| `bank:<account>` | 本システムの銀行口座ごと | 入金の口座、出金の口座（日本円） |
| `trust:<account>` | 信託の口座ごと | 利用者の日本円を信託した額 |
| `fiat_in_transit` | 本システム | 出金の依頼の後、銀行の結果の前の日本円 |
| `suspense:<source>` | 本システム | 説明のつかない差。期限で人が確かめる |

- 仕訳の行は `(journal_id, account_id, asset, amount)` で、借方を正、貸方を負で持つ。**1 つの仕訳の行の和は、資産ごとに 0**（DB の遅延の制約のトリガーとコードの両方で検査する）。金額は `numeric(38,0)` の資産の最小の単位。
- 仕訳は追記だけ。`UPDATE`・`DELETE` は DB の権限で禁止する。
- 残高の行（`balances`：口座、資産、`available`、`hold`）は、仕訳と同じトランザクションで更新し、日次に仕訳から計算し直した値と突き合わせる。拘束は `available` から `hold` への振り替えの仕訳である（[ADR-0004](0004-order-entry-holds-and-idempotency.md)）。

### 約定の仕訳

1 つの約定（買い手 B、売り手 S、価格 p、数量 q、代金 n = `floor(p × q)`、買い手の手数料 fb、売り手の手数料 fs）を、1 つの仕訳で書く。手数料は、買い手は受け取る暗号資産から、売り手は受け取る日本円から引く（MVP の既定。端数は ledger-and-balances の領域）。

| 資産 | 残高が増える口座 | 残高が減る口座 |
| --- | --- | --- |
| JPY | `user_available:JPY`（S）n − fs、`fee_revenue:JPY` fs | `user_hold:JPY`（B）n |
| BTC | `user_available:BTC`（B）q − fb、`fee_revenue:BTC` fb | `user_hold:BTC`（S）q |

- 冪等キーは `(trade, <pair>, <trade_seq>)` で、一意の制約で 1 回に限る。`ledger-poster` が再実行しても 2 度書かない。
- 買い手の指値と約定の価格の差、手数料の上限と実際の手数料の差は、注文が `done` になったときに `user_hold` から `user_available` へ戻す（冪等キー `(order, <order_id>, release)`）。

> 2026-11-15 の注記（統合）：拘束に手数料の上限を含めない（[ADR-0004](0004-order-entry-holds-and-idempotency.md) の注記）。`done` で戻すのは、指値・帯の上の端と約定の価格の差と、約定しなかった残りだけになる。
- 約定の記帳の欠け（出力の記録にあって台帳にない約定）を、1 分ごとに出力の記録の `trade_seq` の連番と比べて見つける。

### 利用者の財産と本システムの財産

- 利用者用のウォレット（`wallet:*`）と本システムのウォレット（`house_wallet:*`）は、チェーンの上で別のアドレスにする。手数料の暗号資産は、日次に利用者用のウォレットから本システムのウォレットへ移す（同じ額の仕訳を同時に書く）。
- 照合の等式（資産ごと）：利用者の残高の和（`user_available` ＋ `user_hold`）＝ 利用者用のウォレットの口座の和 − 未精算の手数料。ウォレットの口座の和は、チェーンの上の残高と一致する（ホットとウォームは 1 時間ごと、コールドは毎日。NFR-006）。
- 日本円：利用者の日本円の残高の和を、毎営業日、`trust:*` の額と比べる。信託すべき額の計算（入金の途中・出金の途中の数え方）は法務の L3 の結論で決める。結論までは、計算の式を `legal.trust_amount_method` の設定にして、本番の値を有効にしない。

### 他の案を選ばなかった理由

- **2（資産ごとの台帳）**：1 つの約定の 2 つの資産の動きが別のトランザクションになり、片方だけが書かれた状態が生まれる。
- **3（残高の表だけ）**：照合でずれの原因を追えない。分別管理の説明に、仕訳の記録が要る。

## Consequences

- 良くなること：
  - 他の題材の台帳の不変条件と照合の道具を、そのまま使える。
  - 1 つの約定が 1 つの仕訳になり、2 つの資産の動きが必ず揃う。
  - 利用者の財産と本システムの財産が、口座とチェーンのアドレスの両方で分かれる。
- 引き受けるコスト：
  - 資産ごとの釣り合いの検査で、仕訳の検査が少し重くなる。
  - マーケットメイカーの口座の残高の行が熱くなる（S2 でスロット。[ADR-0004](0004-order-entry-holds-and-idempotency.md)）。

## Confirmation

- 性質ベーステスト：任意の注文・約定・取り消し・入出金・販売所の取引の列（重複、遅れ、順序の入れ替えを含む）で、仕訳の行の和は資産ごとに 0、全口座の残高の和は資産ごとに 0、`user_available >= 0`、約定の記帳は約定ごとに 1 回、参照の実装（`ledger-ref`）の残高と一致する。
- 照合（台帳とチェーン、台帳と銀行・信託、拘束と注文）の不一致を SLI にする（[runbooks/ledger-reconciliation-mismatch.md](../runbooks/ledger-reconciliation-mismatch.md)）。
- DB の権限の検査：`ledger` のサービスの役割だけが ledger のクラスタに書け、仕訳の表に `UPDATE`・`DELETE` できない。
