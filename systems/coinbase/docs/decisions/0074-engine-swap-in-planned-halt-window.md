# ADR-0074: エンジンを写しで先に確かめ、予定した板の停止の時間に入れ替える

## Context

`engine-core`・`engine-host`・`sequencer` の新しいビルドは、約定の規則と決定性に直接かかわる。Fargate のサービスのように、新旧を並べて利用者の一部に流す（段階のデプロイ）ことができない。1 つの板の入力は 1 つのエンジンだけが処理し、新旧のエンジンが同じ板に別の約定を出せば、どちらかが誤りになる（[ADR-0002](0002-sequencer-and-event-journal.md)）。

runbooks は、変更をまず写しのエンジンに入れて 24 時間比べ、予定した板の停止の時間（平日の早朝、既定 10 分）に本番を入れ替えると書く（[runbooks/README.md](../runbooks/README.md) の 3 節）。決めていないのは、次のことである。

- 日次の再生が、入れ替えをまたぐ日にどのビルドを使うか。前のビルドの出力を新しいビルドで再生すると、意図した違い（規則の変更）が食い違いに見える。
- 出力の形を変える変更（記録の形のバージョンを上げる）と、変えない変更の分け方。
- 写しで比べられない変更（約定の規則を意図して変える変更）の確かめ方。
- 板の停止と再開を、利用者にどう知らせるか。

## Options

1. 板を止めずに、写しを新しいビルドにしてから本番と写しを入れ替える（停止なし）
2. **写しに新しいビルドを入れて本番の入力で比べ、予定した板の停止の時間に、sequencer を通した入れ替えの入力で本番を入れ替える**
3. 毎回、板を止めて、スナップショットから新しいビルドで作り直す（写しで比べない）

## Decision

2 を採用する。

### 変更の種類

| 種類 | 例 | 写しでの比べ | 記録の形 |
| --- | --- | --- | --- |
| A：出力が変わらない | 速さの改善、計測、依存の更新 | 本番と同じ要約。24 時間、食い違い 0 | 変えない |
| B：規則を意図して変える | 新しい注文の種類、価格の帯の計算 | できない。`engine-ref` と再生の固定の列で、意図した違いの一覧を先に作る | 変えないか、上げる |
| C：記録の形を変える | 入力・出力の項目の追加 | B と同じ | 上げる。再生の道具が新旧の両方を読めるようにしたビルドを先に出す |

- 種類は PR の説明に書き、CODEOWNERS（テックリードと QA）が確かめる。

### 流れ（A）

1. 写しの `engine-host` を新しいビルドにする。本番の入力で 24 時間、入力ごとの要約が本番と一致することを確かめる。
2. 予定した板の停止の時間（平日の早朝。時刻は銘柄の設定で持つ。既定 10 分）の 2 営業日前までに、お知らせで停止を知らせる。
3. 時間になったら、運用の画面から板の停止（`halt`）の入力を sequencer に送る。エンジンは停止の入力でスナップショットを書く（ADR-0002）。
4. sequencer に **入れ替えの入力**（`engine_build_change`、新しいビルドの ID と、記録の形のバージョン）を送る。エンジンは状態を変えない。この入力の `seq` から後を新しいビルドで処理する。
5. 本番の `engine-host` を新しいビルドで起こし、停止のスナップショットから読み、要約が停止の時点と一致することを確かめる。
6. 取り消しだけ（既定 5 分）を経て取引中にする（2 人の承認。[ADR-0003](0003-matching-rules-and-self-trade-prevention.md)）。

- B と C は、1 の代わりに、staging で前日の本番の形の生成の列を新旧で再生し、違いが意図した違いの一覧と一致することを QA が確かめる。本番では 3〜6 を行い、写しは入れ替えの後に新しいビルドで比べを始める。

### 再生とビルド

- 再生の道具は、`engine_build_change` の入力の `seq` で、使うビルドを切り替える。どの範囲をどのビルドで再生するかは記録から決まり、人が選ばない。
- 過去の全部のビルドの成果物と SBOM を 7 年（本システムの値。記録の保存の期間は法務の L4・L7 の結論で見直す）保つ。

### 他の案を選ばなかった理由

- **1**：入れ替えの瞬間に、どの `seq` から新しいビルドが処理したかを記録に残せない。再生でビルドを選べなくなる。B・C の変更では、本番と写しが別の規則で同じ板を処理する時間ができる。
- **3**：写しでの 24 時間の比べがなく、A の変更の誤り（意図しない違い）を本番の入力で見つける機会を失う。

## Consequences

- 良くなること：
  - どの約定がどのビルドで作られたかが記録から分かり、日次の再生が入れ替えをまたいでも正しく比べられる。
  - A の変更の誤りを、利用者に影響する前に写しで見つけられる。
- 引き受けるコスト：
  - エンジンの変更は、週に 1 回ほどの停止の時間を待つ。急ぎの修正も同じ停止を要する（臨時の停止はお知らせの期間を縮める。IC の判断）。
  - 過去のビルドを長く保つ。

## Confirmation

- 再生の検査：入れ替えをまたぐ固定の列（`engine_build_change` を含む）で、再生の要約が本番と一致する。
- CI：`engine-core` の変更の PR に、種類（A・B・C）がない、または C で記録の形のバージョンが上がっていないものを落とす。
- 本番：入れ替えの後の 24 時間、写しとの比べの食い違い 0 を確かめてから、次のエンジンの変更を入れる。
