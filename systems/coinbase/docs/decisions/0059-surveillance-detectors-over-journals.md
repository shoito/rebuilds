# ADR-0059: 監視の検出器を記録の上の決定的な関数にし、閾値を承認つきの表に置く

## Context

- 取引所は、見せ玉、仮装売買、相場操縦の兆しを監視する（法務の L7）。協会の規則は、取引審査の部門、抽出の基準、価格の変動率と数量の定量の基準と定性の基準を社内規則に定めることを求め、自動にするときはパラメーターが無断で変更されていないことの確かめを求める（[規則とガイドライン](https://jvcea.or.jp/cms/wp-content/themes/jvcea/images/pdf/B10_jvcea202005.pdf)、2020-04-24 一部改正のときのもの。最新の改正は**未検証**）。
- 板の入力と出力は、`seq` と `ts` の付いた記録として MSK と S3 にある（[ADR-0002](0002-sequencer-and-event-journal.md)）。
- 不公正取引の監視の規則は核として自前で作る（AGENTS.md）。
- 検出が後から見落としと分かったとき、どの規則のどのバージョンで何を見たかを説明できなければならない。

## Options

1. **検出器を、記録を `seq` の順に読む決定的な関数にし、常時の読みと日次の再生で同じコードを使う。閾値はバージョンの付いた規則の表で、コンプライアンスの承認でだけ変わる**
2. 約定と注文を分析の基盤（データの倉庫）に移し、日次の SQL の集計で見つける
3. 監視の製品（外部の提供者）に記録を送り、製品の判定を使う

## Decision

1 を採用する。

- `surveillance` は板ごとに入力と出力の記録を読み、口座ごとの窓の状態を持つ。時刻は `ts` だけ。乱数・壁の時計・ハッシュの順序に依らない。
- 規則（`SUR-SPOOF-1`・`SUR-WASH-1`・`SUR-RAMP-1`・`SUR-SPIKE-1`・`SUR-HOUSE-1`・`SUR-INSIDER-1`・`SUR-STAFF-1`）の既定の閾値は [market-surveillance.md](../architecture/market-surveillance.md) の 4.2 節。閾値は過去 30 日の基準の値に対する倍率でも書ける。
- 規則の表は `config/surveillance/` に置き、コンプライアンスの CODEOWNERS と承認の記録の ID で変わる。兆しに規則のバージョンを残す。
- 兆しの冪等キーは `(rule_id, rule_version, pair, window_key)`。毎日、前日の記録を S3 から再生し、常時の検出器と兆しの集まりを比べる。差は見落としとして数え、案件にする。
- 口座の結び付き（`person_key`、端末、IP、宛先、出金の口座）は `identity` の信号の写しから読み、個人の項目そのものは読まない。
- 価格の急変で板を止めるのはエンジンの規則（[ADR-0003](0003-matching-rules-and-self-trade-prevention.md)）で、この検出器は板を止めない。

### 他の案を選ばなかった理由

- **2**：見つけるのが翌日になり、相場操縦の最中に措置を取れない。SQL の集計と再生の結果を比べる手段がなく、見落としが分からない。
- **3**：判定の基準が製品の中にあり、閾値の承認と変更の記録を本システムの手順で確かめられない。記録を外に送ると、口座と注文の情報の提供の論点が増える（法務の L11・L13）。協会の規則のパラメーターの確かめもしにくい。

## Consequences

- 良くなること：
  - 同じ記録と同じ規則のバージョンから同じ兆しが出るので、後から説明でき、試験のベクトルで確かめられる。
  - 常時の検出器の不具合を、日次の再生が見つける。
  - 閾値の変更が承認の記録とともに残る。
- 引き受けるコスト：
  - 検出器を自前で作り、閾値を相場に合わせて見直す運用が要る。
  - 長い窓（数日）の型は窓の状態が大きくなるので、再生の道具の調べに回す。

## Confirmation

- PROP-SUR-001（同じ記録の列から、どの点からの再生でも同じ兆しの集まり）、PROP-SUR-002（冪等）、PROP-SUR-004（承認の記録のないバージョンで判定した兆し 0）。
- DT-SUR-001 の表駆動のテストと、QA とコンプライアンスが持つ試験のベクトル。
- 本番：日次の再生の見落とし 0 を SLI にする。
