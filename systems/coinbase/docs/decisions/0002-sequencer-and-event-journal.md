# ADR-0002: 板ごとの sequencer が順序を決め、MSK の記録を板の正本にする

## Context

取引所の公正さと復旧は、板に入る入力の順序で決まる。

- 同じ価格の注文は受け付けの順に約定する（[ADR-0003](0003-matching-rules-and-self-trade-prevention.md)）。順序が後から変わったり、経路によって違ったりすると、公正でなくなる（NFR-013）。
- 受け付けを返した注文は、AZ の障害でも失ってはいけない（NFR-011）。
- 板の状態が壊れたとき、手で直すのでなく、確かな記録から作り直したい。
- エンジンの誤り（非決定性）は、エラーにならずに約定の違いとして残る。本番の出力を、別に計算した出力と比べ続けたい（NFR-003）。

板は銘柄ごとに独立している（1 つの注文は 1 つの板にしか入らない）。板をまたぐ順序は要らない。

## Options

順序を決める者：

1. **板ごとに 1 つの sequencer（単一の書き手）が通し番号と時刻を付ける**
2. 記録の仕組み（Kafka の区画の offset）だけで順序を決め、入口の各タスクが直接書く
3. エンジンが受けた順に処理し、記録は後から書く

入力の記録の置き場所：

- a. **Amazon MSK（板ごとに 1 つの区画、`acks=all`）**
- b. Aurora の表（追記の行）
- c. 自前の複製の記録（Raft など）

## Decision

1 と a を採用する。

### 入力の流れ

1. `order-gateway` が拘束を書いた注文（[ADR-0004](0004-order-entry-holds-and-idempotency.md)）、取り消し、運用の操作（板の停止・再開、銘柄の設定の変更）を、その板の sequencer に送る。
2. sequencer は板ごとに 1 つだけ動く。入力に `seq`（板ごとの 1 からの連番）と `ts`（sequencer の時計の時刻。エンジンはこれだけを時刻として使う）と `epoch` を付ける。
3. sequencer は入力を MSK の板ごとのトピック（区画 1 つ）に、トランザクションの producer（`transactional.id` を板ごとに固定）で書く。`acks=all`、`min.insync.replicas=2`、レプリカは 3 つの AZ に 3。書けたら受け付け（`seq`）を返す。書けなければ受け付けを返さない（呼び出し元は同じ `order_id` で送り直す）。
4. 小さな入力の束（既定 1ms か 64 件の早いほう）でまとめて書き、遅れと流量の釣り合いを取る（`engine-latency-poc` で値を決める）。

### 単一の書き手の保証

- sequencer の起動は、板ごとの持ち主の記録（core の `sequencer_leases` の行。期限 5 秒、更新 1 秒）を取ってから行い、`epoch` を 1 上げる。
- 古い sequencer は、MSK のトランザクションの producer の fencing（同じ `transactional.id` の新しい producer の開始で、古い producer の書き込みが拒まれる）で書けなくなる。
- エンジンは、`seq` が前の値 ＋ 1 でない入力、`epoch` が今の値より小さい入力を処理せずに板を止める（抜けと重なりを黙って通さない）。

### エンジンと出力

- `engine-host` は入力のトピックを `seq` の順に読み、`engine-core` を呼び、出力（注文の状態、約定、板の差分、入力ごとの要約）を出力のトピックに書く。出力は入力の `seq` を持つ。
- 出力の各行は、前の要約と今の出力から作るハッシュの連鎖（`output_hash[seq]`）を持つ。
- **写しのエンジン**：別の AZ の `engine-host` が同じ入力を読み、同じ要約を計算する。本番の要約と入力の番号ごとに比べ、食い違ったら両方の板を止める（[runbooks/market-halt.md](../runbooks/market-halt.md)）。
- **切り替え**：本番のエンジンが止まったら、写しが最後に処理した `seq` から出力を書く側になる。出力の書き込みも同じ fencing で単一の書き手にする。目標は 5 分以内（NFR-011）で、多くは数秒で済む見込み。

### スナップショットと再生

- エンジンは 10 万入力ごとと、板の停止のたびに、板の状態のスナップショット（`seq`、状態、要約）を S3 に書く。
- 再生は、スナップショット ＋ その後の入力から状態と出力を作り直す。日次に、前日の全部の入力を、前日の始めのスナップショットから再生し、出力の要約が本番と一致することを確かめる（NFR-003）。
- MSK の保持は 7 日にし、毎時、入力と出力のトピックを S3 に移す（長く持つ正本の記録。保存の期間は法務の L4・L7 の記録の要件で決める）。

### S3 の段階で見直すこと

- MSK の `acks=all` の p99 が NFR-001 を満たさないか、S3 の 10 万件/秒で区画の流量が足りないときは、入力の記録を自前の複製の記録（c）に替える ADR を書く。sequencer とエンジンの形（番号、epoch、要約）は変えない。

### 他の案を選ばなかった理由

- **2（offset だけ）**：入口のタスクが複数の書き手になり、時刻の付け方と抜けの検出をエンジンが持てない。切り替えの時の古い書き手を止める仕組みも別に要る。
- **3（後から記録）**：受け付けた入力がエンジンの停止で失われうる。再生の正本がない。
- **b（Aurora）**：1 入力ごとの commit の遅れと流量が、S2 以降の 3 万件/秒に足りない。板の記録と台帳が同じ DB の資源を取り合う。
- **c（自前の Raft）**：遅れは最も小さくできるが、複製と選出の誤りは、まれな障害の組み合わせでしか出ない。小さなチームとエージェントが最初から持つには重い。S3 で要るときに、MSK で固めた形を保ったまま替える。

## Consequences

- 良くなること：
  - 板の順序が 1 か所で決まり、どの入口からも同じ規則で並ぶ。
  - 受け付けた入力は 3 つの AZ のうち 2 つ以上に書かれてから返る。
  - 板を、手でなく記録とスナップショットから作り直せる。
  - 決定性の誤りを、本番で常に（写しの比べ）、毎日（再生）見つけられる。
- 引き受けるコスト：
  - 受け付けの遅れに MSK の書き込みの往復（数 ms と見込む）が入る。
  - 板ごとの sequencer は単一の書き手で、1 つの板の流量の上限になる。
  - MSK の運用（ブローカーの更新、区画の配置）を持つ。

## Confirmation

- 性質ベーステスト：任意の入力の列と、sequencer の切り替え・MSK の再送・重複の注入で、エンジンが処理する入力の `seq` は 1 から抜けなく 1 回ずつ（PROP-ME の候補。matching-engine の領域で ID を付ける）。
- 再生の検査：日次の全部の再生で、出力の要約が本番と一致する。
- 写しのエンジンの要約の食い違いを SLI にし、1 件で呼び出す（[runbooks/README.md](../runbooks/README.md)）。
- 障害の注入：sequencer の停止と二重の起動、MSK のブローカーの停止、エンジンの停止の場面を夜間に回す。
