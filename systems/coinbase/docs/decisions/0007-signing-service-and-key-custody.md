# ADR-0007: 署名の方針を自前で持ち、鍵を別のアカウントの署名の境界に閉じる

## Context

暗号資産の出金は、署名した取引をチェーンに流した時点で取り消せない。何に署名するかの判断の誤りと、鍵の漏れが、そのまま損失になる。

- 侵害の多くは、鍵そのものでなく、署名を依頼する側（オンラインの部品、承認者の端末、運用の権限）が破られて、正しい鍵で不正な取引に署名させる形で起きると考える。2024 年 5 月の国内の流出の原因は公表の資料で確かめていない（**未検証**）。
- 鍵の保管の方式には、HSM（鍵を機器の中に閉じる）、MPC（鍵を断片に分け、断片を持つ複数の者の計算で署名する）、チェーンの上の複数署名（BTC の複数の鍵の出力、ETH の複数署名の契約）がある。どれも利点と代償があり、BTC と ETH で対応も違う。提供者の能力と費用は確かめていない。
- 暗号の処理（署名、閾値の署名、鍵の導出）を自作すると、誤りを見つけにくい（AGENTS.md）。
- 法令は、システムのリスクの管理と外部への委託の管理を求める（法務の L13）。

鍵の方式と提供者は PoC で決めるが、方式に依らない境界と方針の形は、ほかの設計（出金、移し替え、入金のアドレス）の前提になるので、先に決める。

## Options

境界の形：

1. **方針の判定と依頼の流れを自前で作り、鍵は別の AWS アカウントの署名の境界に閉じる。境界の中でも方針と承認を確かめ直す**
2. 方針の判定をオンラインの部品（`wallet-orchestrator`）だけで行い、境界は来た依頼に署名する
3. 提供者の製品の方針の機能に、判定を任せる

鍵の保管の方式（PoC で比べる）：

- a. HSM（AWS CloudHSM、または専用の HSM の提供者）
- b. MPC の提供者
- c. チェーンの上の複数署名（BTC は複数の鍵の出力。ETH は複数署名の契約か、ETH だけ a・b）

## Decision

境界の形は 1 を採用する。鍵の保管の方式は、段（[ADR-0006](0006-wallet-tiers-and-cold-ratio.md)）ごとに、E6 の前の `custody-signing-poc` で a・b・c を比べてから決める（`decide_after`）。

### 署名の境界

- 署名の境界は、別の AWS アカウント（`custody`）に置く。本体のアカウントからは、決めた 1 つの API（署名の依頼）だけを通す。境界の外から鍵の材料に届く経路を作らない。
- 境界の中の部品：
  - `policy-verifier`：依頼が方針に合うかを確かめ直す。方針は、バージョンと 2 人の承認の署名の付いた設定で、境界の中に置く。
  - `approval-verifier`：承認者の署名（承認者ごとの端末のパスキー、またはハードウェアの鍵）を確かめる。承認者の公開鍵の一覧は、方針と同じ手順でだけ変わる。
  - `signer`：HSM・MPC の提供者のアダプター。上の 2 つを通った依頼にだけ署名する。
  - `nonce-and-utxo-guard`：同じ出金の ID、同じ入力（BTC の UTXO）、同じ nonce（ETH）に、別の取引で 2 度署名しない（[ADR-0008](0008-withdrawal-pipeline-and-approvals.md)）。
- 境界は、取引の中身（宛先、額、手数料、入力、nonce）を自分で解読してから方針に当てる。依頼に添えられた「要約」を信じない。

### 方針（自前）

- 方針は、決定表として書く。行の例：段、資産、宛先の種類（利用者の許可の一覧、本システムのウォレット、それ以外）、額の幅、24 時間の累計、承認の数と役割、宛先の登録からの時間。
- 方針の判定は純粋な関数（`packages/signing-policy`）にし、`wallet-orchestrator` と `policy-verifier` が同じパッケージの同じバージョンを使う。2 か所の判定が食い違ったら署名しない。
- ホットの自動の署名の 24 時間の累計の上限を、方針に必ず置く（S1 の既定はホットの目標の額の 50%）。超えたら自動の署名を止め、承認に回す。

### 承認

- 承認者は、運用とコンプライアンスと財務の決めた人で、作成者（依頼を作った人・サービス）と別である。1 つの依頼に、同じ人の承認を 2 度数えない。
- AI エージェントと Dev の役割は承認者にならない。本番の境界に経路を持たない（[Auth0 の ADR-0056](../../../auth0/docs/decisions/0056-operator-access.md)）。

### PoC で比べること

| 観点 | 見ること |
| --- | --- |
| 対応 | secp256k1 の ECDSA（BTC・ETH）、BTC の Schnorr（Taproot）、ETH の取引の型 |
| 方針の置き場所 | 方針の確かめを境界の中（本システムの `policy-verifier`）に置けるか。提供者の方針の機能と二重にできるか |
| 鍵の材料の場所 | 鍵の材料・断片が日本の中にあるか。提供者が単独で署名できないか |
| 復旧 | 提供者の終了・障害の時に、鍵を取り出すか、別の方式に移せるか |
| 速さと費用 | 1 署名の時間、署名あたりと固定の料金 |
| 監査 | 第三者の監査、認証、法務の L13 の外部への委託の要件 |

- 推奨の出発点（PoC で確かめる仮説）：コールドは BTC で複数の鍵の出力（鍵の機器は別々の場所）、ETH で MPC か HSM。ホットとウォームは、HSM か MPC のうち、方針を境界の中で確かめ直せるもの。

### 他の案を選ばなかった理由

- **2**：オンラインの部品が破られたら、境界は不正な依頼に正しく署名する。最も多い侵害の形を防げない。
- **3**：方針の判定が提供者の製品の中にあり、本システムの決定表とテストで確かめられない。提供者を替えると方針を書き直すことになる。

## Consequences

- 良くなること：
  - オンラインの部品が破られても、境界の中の方針と承認の確かめで、方針の外の取引に署名しない。
  - 方針が決定表とテストで確かめられ、提供者を替えても変わらない。
- 引き受けるコスト：
  - 方針の判定を 2 か所で動かし、同じバージョンを出し続ける運用が要る。
  - 取引の解読を境界の中で持つ（BTC と ETH の符号化のライブラリを境界に入れる）。
  - 方式の決定が PoC まで延び、E6 と E7 の spec がそれを待つ。

## Confirmation

- 方針の決定表を spec に置き、表駆動のテストで全行を確かめる。`wallet-orchestrator` と `policy-verifier` に同じ表を流し、判定が一致する。
- 性質：任意の依頼の列（承認の欠け、同じ人の 2 度の承認、要約と中身の食い違い、同じ UTXO・nonce の別の取引）で、方針の外の署名 0。
- 署名の境界の操作の全件を、別のアカウントの記録に残す（CloudTrail と境界の監査の記録）。外部のペンテストで、本体のアカウントから鍵の材料に届く経路がないことを確かめる。
