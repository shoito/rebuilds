# ADR-0035: 署名の方針を決定表の束にし、2 人の承認の署名で出す

## Context

[ADR-0007](0007-signing-service-and-key-custody.md) は、署名の方針を決定表として書き、`wallet-orchestrator` と境界の中の `policy-verifier` が同じ純粋な関数（`packages/signing-policy`）の同じバージョンで判定すると決めた。方針はバージョンと 2 人の承認の署名の付いた設定で、境界の中に置く。ここでは、次を決める。

- 決定表の列と、行の当て方（上から最初に当たる行か、すべての行か）。
- 方針の束（表と値）の形、署名、出し方、取り下げ。
- 2 か所のバージョンがずれたときの振る舞い。

方針の誤りは、取り戻せない署名になる（[quality.md](../quality.md) の 1 節の順位 1）。

## Options

1. **方針を「表（行の並び）＋値（額の段、累計）」の 1 つの束にし、上から最初に当たる行で決め、どの行にも当たらなければ拒む。束はハッシュで名前を付け、セキュリティと財務の 2 人が束のハッシュに署名する**
2. 規則をコードに書き、値だけを設定にする
3. 行ごとに独立に評価し、拒む行が 1 つでもあれば拒む（優先の順を持たない）

## Decision

1 を採用する。

### 決定表の列

| 列 | 値の例 |
| --- | --- |
| 依頼の種類 | `user_withdrawal`、`replacement`、`internal_transfer`、`deposit_sweep`、`house_transfer` |
| 送り元の段 | `hot`、`warm`、`cold`、`deposit_address` |
| 宛先の種類 | `user_allowlisted`（待ち時間を過ぎた宛先）、`house_cold`、`house_warm`、`house_hot`、`house_wallet`、`other` |

> 2026-11-15 の注記（統合）：`house_hot`・`house_warm`・`house_cold` は、本システムが管理する**利用者用の**ウォレットの段（台帳の `wallet:<tier>:<asset>`）のアドレスで、`house_wallet` は**本システムの財産の**ウォレット（台帳の `house_wallet:<asset>`。[ADR-0005](0005-ledger-balances-and-trade-settlement.md)）である。同じ `house_` の接頭辞で意味が違い、取り違えやすい。名前（たとえば `tier_hot`・`tier_warm`・`tier_cold`）はデータモデルの工程でそろえる。意味は変えない。
| 円換算の額の幅 | 依頼 1 件の額 |
| 累計 | 口座の 24 時間の累計、送り元の段の 24 時間の自動の署名の累計 |
| 状態の条件 | ネットワークにつながる額の割合が `legal.hot_ratio_max` を超えているか（[ADR-0006](0006-wallet-tiers-and-cold-ratio.md)） |
| 結果 | `auto`、`approve(役割の組)`、`ceremony`、`deny` |

- 行は上から順に当て、最初に当たった行の結果を使う。最後の行は必ず「すべて → `deny`」にし、CI が最後の行を検査する。
- 円換算の額は、依頼を作った時点の参照の価格で `wallet-orchestrator` が計算し、依頼に入れる。`policy-verifier` は境界の中の価格の写し（参照の価格の提供者 2 つからの値。[ADR-0011](0011-external-providers-boundary.md)）で計算し直し、差が 2% を超えたら拒む。
- 累計は、境界の中の署名の記録から `policy-verifier` が自分で数える。オンラインの側の数を信じない。

### 束の形と出し方

- 束は `config/signing-policy/` の 1 つのファイル（表と値）で、内容のハッシュを束の ID にする。バージョンは増える整数。
- 束を有効にするには、セキュリティの 1 人と財務の 1 人が、承認者の鍵（[ADR-0036](0036-approver-keys-and-approval-payload.md)）で束の ID に署名する。作成者（変更を書いた人）はどちらにもなれない。
- 境界の `policy-verifier` は、2 つの署名を確かめた束だけを読み込む。`wallet-orchestrator` は同じ束を読み、依頼に束の ID を入れる。境界は、自分の有効な束の ID と依頼の束の ID が違えば拒む。
- 切り替えは「新しい束を境界に入れる → `wallet-orchestrator` を新しい束に切り替える → 古い束を取り下げる」の順にし、切り替えの間は 2 つの束を有効にしてよい（最大 1 時間）。値を緩める変更（額の段を上げる、累計を広げる）は、入れてから 24 時間後に有効にする。厳しくする変更はすぐに有効にする。

> 2026-11-15 の注記（統合）：「切り替えの間は 2 つの束を有効にしてよい（最大 1 時間）」をやめ、[delivery.md](../architecture/delivery.md) の 4.9 節に合わせる。切り替えは、`ops.hot_auto_signing_enabled` を止め、古い束で判定した手続き中の依頼が片付くのを待ってから新しい束を境界に入れ、`wallet-orchestrator` を切り替え、見張りのウォレットへの試験の出金で判定の一致を確かめ、2 人の承認で自動の署名を開ける。境界が有効にする束は常に 1 つで、猶予の時間を持たない（[runbooks/signing-policy-rollout.md](../runbooks/signing-policy-rollout.md)）。値を緩める変更の 24 時間の待ちは変えない。Dev の確認待ち。
- 方針の変更は平日 10〜15 時、コールドの儀式の当日を除く（[runbooks/README.md](../runbooks/README.md) の 3.1 節）。

### 他の案を選ばなかった理由

- **2**：規則の変更がコードの変更になり、表駆動のテストと財務・セキュリティの承認の対象が分かれる。どの行で通ったかを記録に残しにくい。
- **3**：行の数が増えると、どの行の組み合わせで通るかが読めない。拒む既定の最後の行という単純な守りが使えない。

## Consequences

- 良くなること：
  - 署名ごとに、束の ID と当たった行の番号を記録でき、監査で「なぜ署名したか」を辿れる。
  - 緩める変更に 24 時間の待ちを置くので、乗っ取られた承認者 2 人でも、すぐに上限を上げて流せない。
- 引き受けるコスト：
  - 上限を急いで上げたいとき（相場の急変での大きな出金の集中）も 24 時間待つ。その間は承認の段で払う。
  - 境界の中に参照の価格の写しを持つ。

## Confirmation

- 決定表（DT-POL）を spec に置き、表駆動のテストで全行を、`wallet-orchestrator` と `policy-verifier` の両方に流して判定が一致することを確かめる（[ADR-0007](0007-signing-service-and-key-custody.md)）。
- 性質：任意の依頼で、最初に当たる行は 1 つに決まる。最後の行に当たる依頼は拒まれる。束の ID の違う依頼の署名 0。
- CI：最後の行が `deny` であること、緩める変更に 24 時間の有効の時刻が付いていること。
