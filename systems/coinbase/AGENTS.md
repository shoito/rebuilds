# AGENTS.md — Coinbase

Coinbase（暗号資産の交換所）の再構築の設計。日本の暗号資産交換業者として、BTC と ETH の販売所と取引所、日本円の入出金を最初の対象にする。リポジトリ共通のルールはルートの [AGENTS.md](../../AGENTS.md) にある。このリポジトリには設計だけを置き、実装は Coinbase の再構築の開発リポジトリで行う（[リポジトリ共通の ADR-0005](../../docs/decisions/0005-design-record-repository.md)）。

## この題材に固有の規則（開発リポジトリで守る）

### 本家の実装と名前

- **核を自前で作る。** マッチングエンジンと順序付け（sequencer）、注文の受付とリスクの確認、台帳と残高、ウォレットの指揮と署名の方針（policy）、入出金の状態の管理、販売所の価格の提示、不公正取引の監視の規則は自分で書く。本家のコード、本家の SDK・API のクライアント、本家が公開したライブラリ、本家から取り出したデータを、核にも依存にも使わない。本家の公開の資料（API の文書、技術ブログ、届出の書類）を読むのはよいが、設計の文書に出典を書く（[リポジトリ共通の ADR-0007](../../docs/decisions/0007-no-reuse-of-original-implementation.md)、ADR-0001）。
- **第三者の汎用の部品と外部のサービスは、ADR に理由を書いた範囲でだけ使う。** ブロックチェーンのノード（Bitcoin Core、Ethereum の実行のクライアントと合意のクライアント）、HSM・MPC の提供者、eKYC の提供者、銀行の API、チェーン分析（AML のスクリーニング）の提供者、トラベルルールの通知の提供者、参照の価格の提供者、Amazon MSK が当たる（ADR-0001、ADR-0002、ADR-0007、ADR-0009、ADR-0011）。
- **暗号の処理を自作しない。** 楕円曲線の署名、閾値の署名（MPC）、鍵の導出、ハッシュは、監査を受けた汎用のライブラリか、HSM・MPC の提供者のものを使う。自作するのは、何に署名してよいかを決める方針と、署名の依頼の流れだけである（ADR-0007）。
- **本家の名前を識別子に使わない。** ドメイン（`<brand>.<domain>`、API の `api.<brand>.<domain>`、板の配信の `ws.<brand>.<domain>`）、HTTP ヘッダー（`<Brand>-Signature`、`X-<Brand>-Client`）、API キーの接頭辞（`<brand>_live_`）、機能の名前は `<Brand>`・`<brand>` で書く（[リポジトリ共通の ADR-0006](../../docs/decisions/0006-brand-neutral-identifiers.md)）。銀行・提供者の名前は、相手先の名前としてそのまま書いてよい。

### 板とマッチングエンジン

- **板の状態を変える入力は、sequencer だけが順序を決める。** 注文、取り消し、板の停止と再開、銘柄の設定の変更は、板ごとの sequencer が通し番号（`seq`）を付け、MSK の記録に書けてから受け付けの応答を返す。sequencer を通らずにエンジンの状態を変える経路を作らない（ADR-0002）。
- **エンジンは決定的に作る。** エンジンの核（`engine-core`）は I/O・壁の時計・乱数・スレッド・ハッシュの順序に依存しない純粋な関数（状態と入力から、次の状態と出力）にする。時刻は sequencer が入力に付けた時刻だけを使う。同じスナップショットと同じ入力の列からは、ビット単位で同じ出力の列が出る（ADR-0002、ADR-0003）。
- **約定の規則は 1 か所に置く。** 価格・時間の優先、約定の価格（板にあった注文の価格）、自己約定の防止、価格の帯、刻みと最小の数量は `engine-core` にだけ書く。販売所・運用の画面・テストの道具が、別の規則で約定を作らない（ADR-0003）。
- **数量と価格は整数で持つ。** 資産ごとの最小の単位（BTC は satoshi、ETH は wei、日本円は 1 円）の整数で持つ。浮動小数点を使わない。Rust は `i128`・`u128`、TypeScript は `bigint`、DB は `numeric(38,0)` にする。桁あふれは検査つきの演算で止める。
- **板を直さない。** 板の状態がおかしいときは、エンジンを止め（`halt`）、スナップショットと記録から作り直す。メモリーの板・スナップショット・記録を手で書き換えない（[runbooks/market-halt.md](docs/runbooks/market-halt.md)）。

### お金と残高

- **お金の正本は追記だけの複式簿記の台帳にする。** 日本円・BTC・ETH のどれも仕訳で動かす。仕訳は資産ごとに借方と貸方の和が一致しなければ書けない（DB の制約とコードの両方）。残高は仕訳の和で、残高の列を直接書き換えない。台帳の一般の設計は Stripe とメルカリの題材にあり、設計し直さない（ADR-0005）。
- **使える残高を超えて拘束しない。** 注文・出金・販売所の購入は、Aurora の残高の行の条件つきの更新（`available >= $amount`）で拘束（hold）を書いてから先へ進む。拘束のない注文を sequencer に送らない（ADR-0004）。
- **約定の記帳は約定ごとに 1 回だけ。** エンジンの約定の出力は `(pair, trade_seq)` の冪等キーで 1 回だけ記帳する。記帳の再実行で残高が変わらない（ADR-0005）。
- **利用者の財産と本システムの財産を混ぜない。** 利用者の暗号資産は利用者用のウォレット、本システムの暗号資産（手数料の収益、販売所の在庫、履行保証暗号資産）は別のウォレットに置き、台帳の口座も分ける。利用者の日本円は信託の口座で管理する（ADR-0005、ADR-0006）。
- **法的に未決の値をコードに決め打ちしない。** コールドの割合、履行保証暗号資産の額の計算、信託の額の計算、トラベルルールの対象、取引時確認の方式、出金の上限は `legal.*` の設定で持つ。法務の結論（[intent.md](docs/intent.md) の L 番号）が出るまで、本番の値を有効にしない。

### ウォレットと署名

- **署名してよいものは方針が決める。** 署名の依頼は `wallet-orchestrator` だけが作り、署名の境界（signer）の中でも方針と承認を確かめ直してから署名する。方針の外の宛先・額・頻度の取引には、誰の指示でも署名しない（ADR-0007）。
- **一人でお金を動かせない。** ホットの自動の署名の上限を超える出金は作成者と別の人の承認を、大きな出金（ADR-0008 の最上の段）、ウォームとコールド**から出る**移し替え（ウォーム → ホット、コールド → ウォーム）、署名の方針の変更、本システムのウォレットの許可の一覧の変更は、作成者と別の 2 人以上の承認を要する。コールド**へ入る**移し替え（ホットとウォームの目標を超えた分を、許可の一覧のコールドへ）は、ネットワークにつながる額を減らすので自動にする（ADR-0006、ADR-0037）。運用者・Dev・エージェントのどの役割も、単独で署名の鍵を使えない（ADR-0007、ADR-0008）。
- **コールドの鍵をネットワークにつながない。** コールドの署名は、ネットワークにつながない機器での儀式（ceremony）で行う。オンラインの部品にコールドの鍵の材料を置かない（ADR-0006）。
- **同じ出金に 2 つの取引を作らない。** 手数料の引き上げは、同じ入力（BTC）・同じ nonce（ETH）で宛先と額を変えない置き換えだけにする。別の取引を作るのは、前の取引が確定しえないことをチェーンで確かめた後だけにする。結果が分からないときは作り直さずに確かめる（ADR-0008）。
- **入金は自前のノードで確かめてから残高に入れる。** 承認の数（BTC）・確定（ETH）の閾値を満たし、自前のノード 2 台が同じ結果を返したときだけ入金を記帳する。外部の提供者の結果だけで記帳しない（ADR-0009）。

### 個人のデータと運用

- **本人確認の書類を金庫の外に出さない。** 本人確認の書類と顔の画像、公的個人認証（JPKI）での確かめの結果、口座の番号は `kyc-vault` にだけ置く。個人番号（マイナンバー）は受け取らない（集めるかは [intent.md](docs/intent.md) の法務の L10 の確認待ち。集めるなら Workday の題材の保管庫の形にする）。設計は Workday の題材の[マイナンバーの保管庫](../workday/docs/architecture/my-number-vault.md)の形を引き継ぐ。
- **運用者は常設の権限を持たない。** 本番のデータの参照・書き込み、署名の承認の役割は、期限つきの権限と 2 人の承認で使う。Auth0 の題材の [ADR-0056](../auth0/docs/decisions/0056-operator-access.md) を引き継ぐ。サポートの担当が見られる項目は、問い合わせに要る最小の範囲にする（本家の 2025 年の事故。[intent.md](docs/intent.md) の出典）。
- **AI エージェントは本番に経路を持たない。** 本番のデータ、ログ、シェル、署名の承認、運用の画面に経路を持たない。
- **利用者のデータと秘密をログに出さない。** ログ・トレースに、氏名、住所、生年月日、本人確認の書類、口座の番号、メールアドレス、電話番号、API キー、鍵の材料、署名の承認の証跡の中身を書かない。ID と数と理由のコードだけを書く。チェーンのアドレスと取引の ID は、利用者の ID と同じ行に書かない。
- **お金・約定・署名の規則をフラグにしない。** マッチングの規則、台帳の仕訳の型、署名の方針はコードと、バージョンの付いた設定として出す。`release.*` のフラグで経路ごとに切り替えない。
- **フラグの名前**：`release.*` は kebab-case（`release.brokerage-quotes`）、`ops.*` は snake_case（`ops.trading_enabled.btc_jpy`、`ops.withdrawals_enabled.btc`）、`legal.*` は法務の結論を入れる値（`legal.hot_ratio_max`）。`ops.*` は止めるだけに使い、止めたものを開ける操作は 2 人の承認にする。
- **テストに本物の鍵とお金を使わない。** テストと検証の環境は、Bitcoin の regtest・testnet、Ethereum の開発用のチェーン・テストネットと、生成した鍵だけを使う。本番の鍵、本番のアドレス、実在の利用者のデータ、本家から取り出したデータを、テスト・フィクスチャーに入れない。

## このリポジトリでの規則

- ADR を追加・更新したら、`docs/decisions/README.md` の一覧を `npm run adr-index` で生成し直す。
- 領域の文書で ADR を起票するときは、[architecture/README.md](docs/architecture/README.md) の 7 節で領域に割り当てた番号の範囲の中で採番する。
- 本家の振る舞い・数値を書くときは、出典と確認日を付ける。確かめられないものは「未検証」と書く。本家と違う振る舞いを選んだら、[architecture/README.md](docs/architecture/README.md) の 1.4 節の「本家との意図した違い」に行を足す。
- 台帳の一般の設計（複式簿記、冪等、3 者の照合、熱い口座）は Stripe とメルカリの題材にある。この題材は、複数の資産、注文の拘束、約定の記帳、チェーンとの照合に合わせて、差分だけを書く。
- 法令に関わる項目は、枠組みだけを書き、結論を書かない。「法務の確認待ち」と書き、[intent.md](docs/intent.md) の L の番号を付ける。暗号資産の法令は、2026 年 7 月に成立した改正法で資金決済法から金融商品取引法へ移る途中にある（L1）。どちらの法令の言葉で書くかも、L1 の結論に合わせて直す。
