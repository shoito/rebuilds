# Runbook: 災害復旧（AZ の障害、リージョンの障害、データの破損、復元訓練）

- Owner: Ops
- 対応するアラート: AZ の障害（複数のサービスで 1 つの AZ が不健全）、大阪からの合成監視の連続失敗、`AuroraGlobalDBRPOLag` が 5 分を超える、訓練（四半期に 1 回）
- 最終確認日: 2026-09-26

構成と目標は [infrastructure.md](../architecture/infrastructure.md) の 8 節と [ADR-0029](../decisions/0029-disaster-recovery.md)。目標は NFR-008（AZ：RPO 0、RTO 5 分）と NFR-009（リージョン：RPO 15 分、RTO 4 時間）。Slack の [disaster-recovery.md](../../../slack/docs/runbooks/disaster-recovery.md) と同じ骨格で、物理クラスタが複数ある点と、クライアントの待ち行列がある点が違う。

## 症状

| 場面 | 見え方 |
| --- | --- |
| A. AZ の障害 | 1 つの AZ のタスク・Aurora のインスタンス・Valkey のノードが不健全。AWS Health Dashboard に東京の 1 つの AZ のイベント |
| B. リージョンの障害 | 東京の複数のサービスが応答しない。大阪からの合成監視がすべて失敗する |
| C. データの論理的な破損 | 誤ったマイグレーション・操作・不具合で、ブロックが消えた・壊れた。範囲は 1 ページから 1 シャードまでさまざま |
| D. 復元訓練 | 定期作業 |

## 影響

- A：数分、トランザクションの失敗と再接続が起きうる。クライアントは未確定のトランザクションを持ち続け、回復後に送る。コミット済みのデータは失わない。
- B：切り替えまで（最大 4 時間）全面的に使えない。オフラインで開いたことのあるページは閲覧・編集でき、回復後に統合される。確定済みのトランザクションを、最大で切り替えの時点の複製の遅延ぶん失いうる。
- C：範囲による。

## 確認

1. AWS Health Dashboard と、Grafana の AZ ごと・物理クラスタごとの内訳で、影響が 1 つの AZ か、リージョン全体か、特定のクラスタかを見分ける。
2. Aurora：物理クラスタごとに、フェイルオーバーの有無と writer の AZ を確かめる（S2 では数十のクラスタ。ダッシュボードの一覧で見る）。
3. 再シャーディングの途中なら、`shard_map` の状態（`frozen`・`fenced` のシャード）を記録する。
4. リージョンの障害を疑うときは、大阪の合成監視と、外部からの到達性の両方で確かめる。

## 対処

### A. AZ の障害

1. インシデントを SEV2 で宣言する（[incident-response.md](incident-response.md)）。
2. 全物理クラスタで、Aurora が別の AZ にフェイルオーバーしたことを確かめる。5 分たっても writer がないクラスタは、手動でフェイルオーバーする。
3. ECS が残る 2 AZ でタスクを起動しているか確かめる。足りなければ最小タスク数を上げる。
4. Sync Gateway への再接続と、差分の取得の負荷を見る。詰まっていれば api を増やす。
5. 再シャーディングの途中なら、手順を止める。論理レプリケーションのスロットが失われていたら、その群れを段 1 からやり直す（[ADR-0028](../decisions/0028-zero-downtime-resharding.md)）。
6. 回復したら、配置と台数を戻す。

### B. リージョンの障害（東京 → 大阪）

**切り替えの判断は IC が行い、Ops の責任者が承認する。** 1 時間以内に回復する見込みなら、待つことも選ぶ。

1. SEV1 で宣言し、利用者へ告知する。
2. 東京に書き込みが届いているなら止める（`ops.read_only_mode`）。
3. 各物理クラスタ（`global` を含む）の `AuroraGlobalDBRPOLag` を記録する（失うデータの範囲の目安）。
4. **DB を切り替える。** 「DR：Aurora の昇格」のワークフローで、全クラスタについて並列に行う。
   - 大阪の二次（headless）に writer と reader のインスタンスを足す。
   - 東京の writer が生きていれば switchover（RPO 0）、応答しなければ failover（`--allow-data-loss`）。
   - `global` を最初に昇格させる。シャードのクラスタは、その後に並列で。
5. 大阪のネットワークとアプリの基盤を Terraform で作る（ECS、ALB、Valkey、SQS。状態ファイルは大阪のバケット）。イメージは大阪の ECR。
6. CloudFront のオリジンを大阪の ALB に切り替える。
7. **突合する。** クラスタごとに昇格の時点がずれるので、次を確かめる。
   - `global.workspaces` にあって、シャードにワークスペースの初期の行がないもの（作成の途中で切れた）→ 作成のジョブを再実行する。
   - シャードにあって `global` にないもの → 記録し、Dev と判断する。
   - ワークスペースをまたぐジョブ（公開ページの複製など）は、切り替えの時点の前後 1 時間ぶんを再実行する。
8. 社内のワークスペースと合成監視で、編集・受信・検索・権限を確かめる。
9. 読み取り専用を解除し、段階的に開く。クライアントの未確定のトランザクションが一斉に届くので、api と Gateway の台数を多めにしておく。
10. 検索の索引を、切り替えの時点の 1 時間前から差分で再構築する。
11. 論理レプリケーションのスロット（CDC、再シャーディング）を作り直す。
12. 失ったデータの範囲（クラスタごとの複製の遅延）と、影響を受けたワークスペースを記録する。

**東京へ戻す（フェイルバック）**：別の計画作業として、東京に二次を作り直し、switchover（RPO 0）で戻す。

### C. データの論理的な破損

1. 被害を止める：原因の機能のフラグを切る、ジョブを止める。広い範囲なら、影響するシャードを `ops.read_only_mode` のシャード単位で止める。
2. 範囲を特定する：ワークスペース、ページ、時刻。監査ログと `page_ops` から。
3. **1 ページ〜数ページ**：利用者向けの履歴とゴミ箱で戻せるなら、それを使う（[block-model.md](../architecture/block-model.md) の 8・9 節）。
4. **1 つのワークスペース・シャード**：PITR で、破損の直前の時刻のクラスタを、prod のアカウントの中の隔離した VPC に復元する。該当するシャードのスキーマから、`workspace_id` で絞った行だけを取り出して本番に戻す。戻した行は、新しいトランザクションとして書き（`seq` を進める）、outbox から配信させる。本番の行を直接上書きしない。
5. **物理クラスタ全体**：本番のクラスタを復元したクラスタへ切り替えることを検討する。それ以降の書き込みを失うので、PM と Ops の責任者の承認が要る。
6. 検索の索引とデータレイクを、戻した範囲について作り直す。
7. 復元したクラスタを消す。

### D. 復元訓練（四半期に 1 回）

すべて prod のアカウントの中で行う。

1. 1 つの物理クラスタを、PITR で任意の時刻（例：24 時間前）に、隔離した VPC に復元する。時間を記録する。
2. 大阪にコピーしたスナップショットからも復元する。
3. 確かめる：行数がメトリクスと大きく違わない。抜き出したページで `page_ops` の `seq` に欠番がない。`app` ロールで RLS が効き、`search_path` なしでシャードのテーブルが読めない。
4. C の 4 の手順（1 つのワークスペースの行だけを取り出す）を、合成監視のワークスペースで行い、時間を記録する。
5. 年に 1 回、B の手順を staging で最後まで行い、RTO を計測する。S2 からは、複数の物理クラスタの並列の昇格を含める。
6. 復元したクラスタを消し、結果を下の記録に残す。

## エスカレーション

- A で 5 分たっても writer がないクラスタがある → SEV1 に上げ、Dev（テックリード）を呼ぶ。
- B の判断 → Ops の責任者。告知の文面は PM と合意する。
- 突合で、説明のつかないずれが見つかった → Dev（テックリード）。
- データの喪失が確定した → PM に報告し、顧客への連絡を決める。個人情報に関わるなら [security.md](../architecture/security.md) に従う。
- AWS 側の障害 → AWS サポートにケースを開く。

## 事後

- 調査結果を Intent の Issue として起票する（Maintain 段）。
- この手順で足りなかったことを、ここに反映する。
- 計測した RTO・RPO を記録し、目標を満たさなければ Intent を起票する。
