# Runbook: インシデント対応（重いシャード、同期の滞留を含む）

- Owner: Ops
- 対応するアラート: すべての呼び出し（page）のアラート。特に、同期の滞留（outbox の最古の行、クライアントの未確定の最古）、物理クラスタ・シャード・ワークスペースの占有、権限の監査の不一致
- 最終確認日: 2026-09-26

個別の手順（[deploy-and-rollback.md](deploy-and-rollback.md)、[disaster-recovery.md](disaster-recovery.md)）の上に立つ、共通の進め方。役割、重さ、告知、振り返りは Slack の [incident-response.md](../../../slack/docs/runbooks/incident-response.md) と同じにし、Notion に固有の 2 つの場面（重いシャード、同期の滞留）の手順を足す。

## 症状

次のどれかのときに、インシデントを宣言する。迷ったら宣言し、後で重さを下げる。

- 呼び出しのアラートが鳴った（[observability.md](../architecture/observability.md) の 5 節）
- 利用者や社内から、「保存されない」「他の人の変更が見えない」「見えてはいけないページが見える」という報告が来た
- 権限の監査で、不一致が 1 件でも出た

## 影響

### 重さ（severity）

| 重さ | 基準 | 例 | 最初の応答 | 告知 |
| --- | --- | --- | --- | --- |
| SEV1 | 権限のないページの中身が見えた。確定した編集が消えた。全体が使えない | 権限の監査の不一致、リージョンの障害 | 5 分以内 | 30 分以内。以後 30 分ごと |
| SEV2 | 編集・同期・ページの表示が、一部の利用者で使えない。SLO の速いバーンレート | 1 つの物理クラスタの過負荷、同期の滞留、AZ の障害 | 15 分以内 | 1 時間以内 |
| SEV3 | 劣化しているが回避できる。遅いバーンレート | 検索への反映の遅れ、通知の遅れ、1 つのワークスペースだけの遅さ | 営業時間内 | 必要なら |
| SEV4 | 影響がない、または非常に小さい | 1 つの Worker の失敗の増加 | 営業時間内 | なし |

権限の分離の破れ（NFR-010）は、1 件でも SEV1 とする。

## 確認

1. どのアラート・報告から始まったかを記録する。
2. 影響の範囲を見る：全体か、1 つの物理クラスタか、1 つの論理シャードか、1 つのワークスペース・ページか。Grafana の SLO ダッシュボードの、クラスタ・シャード・上位ワークスペースの内訳を使う。**範囲がシャード・クラスタに揃っていれば、DB 側を疑う。揃っていなければ、api・Gateway・Relay を疑う。**
3. 直近の変更を見る：デプロイ、フラグ、マイグレーションの群れの適用、バックフィル、再シャーディング、デスクトップの配布。

## 対処

### 役割と進め方

Slack の incident-response の「役割」「進め方」「オンコール」に従う（IC、作業者、連絡係、記録係。被害を止めることを原因の特定より優先する。連絡の場はこのシステムと別の道具に持つ）。被害を止める順番：

1. 直近の変更のフラグを切る
2. 直近のデプロイを戻す（[deploy-and-rollback.md](deploy-and-rollback.md)）。マイグレーションの群れの適用・バックフィル・再シャーディングを止める
3. 問題のワークスペースにレート制限をかける（[capacity.md](../architecture/capacity.md) の 3.5 節）
4. 容量を増やす

権限の分離の破れでは、原因の経路（検索、通知、API、埋め込み、リレーション、公開ページ、同期）を止めることを最優先にする。機能を止めてよい。証拠を消さない。手順は [security.md](../architecture/security.md) に従う。

### 重いシャード（ホットスポット）

アラート：物理クラスタの writer の CPU、1 シャード・1 ワークスペースの占有、1 ページへの集中（[observability.md](../architecture/observability.md) の 4 節）。

1. **粒度を特定する。** Grafana の「シャード」ダッシュボードで、クラスタ → 論理シャード → 上位ワークスペースの順に、DB 時間の内訳を見る。`pg_stat_statements` と遅いクエリのログを、SQL の注釈（論理シャード、ワークスペース）で絞る。
2. **原因の型を見分ける。**

   | 型 | 見え方 | 対処 |
   | --- | --- | --- |
   | 1 つのワークスペースの急増（インポート、連携の大量書き込み、スクリプト） | トランザクション数や API の呼び出しが急増 | そのワークスペース・連携のレート制限を一時的に下げる（ワークスペース単位の上書き。監査ログに残す）。インポートのジョブを止める |
   | 巨大なデータベースの重い問い合わせ | ビューの問い合わせのルートの DB 時間が大きい | 該当のビューの問い合わせを打ち切る上限を下げる。[databases.md](../architecture/databases.md) の上限を確かめる |
   | 1 ページへの集中（全社の告知ページの同時編集・閲覧） | ページの `seq` の行ロックの待ち、Gateway の配信の急増 | 在席の配信を間引く（`ops.presence_enabled` をワークスペース単位で切る）。閲覧だけの接続への配信を `page.head` に落とす（[collaboration.md](../architecture/collaboration.md) の 7.2 節） |
   | バックフィル・マイグレーション | migrator・backfill の DB 時間 | 止める（ops フラグ）。負荷の低い時間に再開する |
   | 実行計画の悪化 | 特定の SQL の時間が急に伸びる | `auto_explain` のログで計画を見る。統計の更新（そのシャードのスキーマの `ANALYZE`）を試す |
   | VACUUM が追いつかない | デッドタプルの増加、`age(datfrozenxid)` の上昇 | そのシャードのテーブルを手動で `VACUUM`。autovacuum の設定を見直す |

3. **容量で吸収する。** reader に回せる読み取りが多ければ reader を足す。writer が足りなければ、インスタンスを 1 段上げる（短いフェイルオーバーを伴う）。
4. **続くなら移す。** 1 つの論理シャードが恒常的に重いなら、空きのあるクラスタへ移す計画を立てる（[ADR-0028](../decisions/0028-zero-downtime-resharding.md)、`resharding.md`）。インシデントの最中には移さない。

### 同期の滞留

アラート：outbox の最古の行、クライアントの未確定の最古（[observability.md](../architecture/observability.md) の 2.1 節）。どの区間で詰まっているかで分ける。

1. **① クライアントの未確定だけが増える（outbox は正常）**：トランザクションが API で確定していない。
   - トランザクションの API の 5xx・遅延・429 を見る。429 ならレート制限に当たっている（どのワークスペースか）。
   - `shard_map` に `frozen` のシャードが残っていないか見る（再シャーディングの切り替えの途中で止まった）。残っていれば、[ADR-0028](../decisions/0028-zero-downtime-resharding.md) の手順で `active` に戻す。
   - 特定のシャード・クラスタに揃っていれば、「重いシャード」へ。
   - 特定のクライアントの版に揃っていれば、クライアントの不具合を疑う（[deploy-and-rollback.md](deploy-and-rollback.md) のデスクトップの配布の停止）。
2. **② outbox の最古の行が増える**：Relay が読んでいない。
   - Relay のタスクが動いているか、論理シャードのリースに持ち主のいないものがないかを見る。Relay を再起動し、リースが引き継がれることを確かめる。
   - 特定のシャードだけなら、そのシャードの outbox の読み取りのクエリが遅くないか（パーティションの肥大、VACUUM）を見る。
   - 滞留の間も、クライアントは確定の応答を受け取っているので、データは失われていない。他の人の画面への反映が遅れるだけで、再接続・差分の取得で追いつく。
3. **③ Gateway の送信が詰まる（outbox は正常）**：
   - Valkey の CPU・ネットワーク、Pub/Sub の出力バッファでの購読の切断を見る。
   - Gateway のタスクの送信の待ち、遅い受信者の切断を見る。巨大なページがあれば、上の「1 ページへの集中」の対処をする。
   - 接続数が上限に近ければ、Gateway を増やす。
4. **Worker 側（検索・通知・Webhook）だけが遅れる**：SQS のキューの最古のメッセージと DLQ を見る。編集の同期には影響しないので SEV3 にとどめる。
5. 収束の確認：3 つの区間の指標が戻り、合成監視の「編集 → 別のクライアントで受信」が 15 分成功し続けてから解決とする。

## エスカレーション

| 状況 | 連絡先 |
| --- | --- |
| SEV1 の宣言 | Ops の責任者、Dev（テックリード）、PM |
| 権限の分離の破れ、個人情報の漏洩の疑い | 上記に加えて、[security.md](../architecture/security.md) で定める責任者 |
| 確定した編集が消えた疑い（NFR-004） | SEV1。Dev（テックリード）と QA |
| リージョンの切り替えを考える | Ops の責任者。[disaster-recovery.md](disaster-recovery.md) |
| 再シャーディングの途中の障害 | Dev（テックリード）。手順を止める |
| AWS 側の障害 | AWS サポート |
| 1 時間たっても被害を止められない | 重さを 1 段上げる |

## 事後

- SEV1・SEV2 は、解決から 5 営業日以内に振り返りを行う（責任追及をしない。時系列、影響、検知までの時間、原因、再発防止）。
- 再発防止を Intent の Issue として起票する（Maintain 段）。
- 権限・データの喪失・同期の不整合に関わるものは QA に共有し、品質のリスクと対策を見直す。
- 重いシャードが原因なら、キャパシティの見直し（[capacity.md](../architecture/capacity.md) の 6 節）に、そのシャードの移動の要否を加える。
- この手順と個別の runbook で足りなかったことを反映する。アラートが鳴らなかった・遅かったなら、アラートを直す。
