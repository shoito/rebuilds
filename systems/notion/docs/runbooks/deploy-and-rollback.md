# Runbook: デプロイとロールバック

- Owner: Ops
- 対応するアラート: デプロイ中の自動ロールバック（api の blue/green のアラーム）、デプロイ後の SLO のバーンレート、マイグレーションの台帳の失敗・停滞
- 最終確認日: 2026-09-26

流れは [delivery.md](../architecture/delivery.md)、マイグレーションの群れは [ADR-0031](../decisions/0031-migration-rollout-by-shard-groups.md)、デプロイの方式は Slack の [ADR-0022](../../../slack/docs/decisions/0022-zero-downtime-deploy-and-migrations.md) にある。

## 症状

次のときに使う。

- 本番へデプロイするとき（通常の手順）
- マイグレーションが一部のシャードで失敗した・進まないとき
- デプロイの後に、編集の反映の遅延・トランザクションの成功率・同期の滞留が悪化したとき
- デスクトップアプリの新しい版で、クラッシュや不具合が増えたとき

## 影響

- 通常のデプロイ：利用者への影響はない。Sync Gateway の入れ替え中は、接続が順に再接続する（数秒の「保存中」の表示が出うる。入力は失われない）。
- 失敗したデプロイ：トランザクションの成功率と、編集の反映の遅延の SLO を消費する。
- マイグレーションの失敗：失敗したシャードのワークスペースだけが、新しい機能を使えない。適用済みのシャードと混在しても、アプリは動く（expand のため）。

## 確認

### デプロイの前

1. 対象のコミットが dev と staging へデプロイ済みで、E2E（同時編集、オフラインと再接続）とスモークが通っている。
2. staging でのデプロイ中に、k6 の編集と受信で、確定したトランザクションの消失が 0 件だった。
3. マイグレーションを確かめる。
   - expand だけか。contract を含むなら、古いものを参照するアプリが本番に残っていないこと、PITR の直近の復元可能な時刻が 5 分以内であることを確かめる。
   - 再シャーディングの期間中でないこと（期間中はマイグレーションを含むリリースを止める。[ADR-0028](../decisions/0028-zero-downtime-resharding.md)）。
   - RLS のポリシーを変えるなら、テナント境界の性質テストが新旧のアプリの両方で通っている。
4. **デプロイの関門**：`global.migration_ledger` で、このイメージが必要とする番号まで全 480 シャードに当たっている。当たっていなければ、先にマイグレーションだけを進める。
5. エラーバジェットが残っている。進行中のインシデントがない。

### デプロイの後（入れ替えが終わってから 15 分）

| 見るもの | 正常 | 異常 |
| --- | --- | --- |
| トランザクションの 5xx の割合 | デプロイ前と同じ | 0.1% を超える |
| 編集の反映の遅延 p99（サーバー） | 500ms 以内 | 500ms を超える |
| outbox の最古の行（全シャード） | 5 秒以内 | 30 秒を超えるシャードがある |
| クライアントの未確定の最古 | 30 秒を超える利用者が 1% 未満 | 1% 以上 |
| 欠損の検知 | Gateway の入れ替え中だけ一時的に上がる | 入れ替えの後も高い |
| 合成監視 | 成功 | 2 回続けて失敗 |

## 対処

### 通常のデプロイ

1. GitHub の `prod` の Environment で、作成者と別の Ops が承認する。
2. **マイグレーション（expand）**：migrator が群れ G0 → G1 → G2 → G3 の順に当てる。各群れの後に 30 分、そのシャードの SLI を見る。Grafana の「マイグレーションの台帳」で、未適用・失敗のシャードの数を見る。
3. デプロイの関門を通ったことを確かめる。
4. relay、workers：ローリング。Relay のリースが別のタスクに移り、outbox の最古の行が増え続けないことを見る。
5. api：blue/green のカナリア（10% → 100%）。
6. sync-gateway：10% ずつ入れ替える。再接続の速さと、差分の取得の API の負荷を見る。上限に近づいたら、1 回に入れ替える割合を下げる。
7. Web：静的ファイルを置いてから `index.html` を差し替える。
8. デスクトップ（新しい版があるとき）：更新の情報の API で 1% に配り、24 時間ごとにクラッシュ率と RUM を見て 10% → 50% → 100% に進める。
9. 「デプロイの後」の表を 15 分見て、異常がなければ終わる。

### マイグレーションが失敗した・進まない

1. 台帳で、失敗したシャードと、エラー（多くは `lock_timeout`）を確かめる。
2. **次の群れへ進めない。** migrator は、失敗したシャードがある群れで止まる。
3. `lock_timeout` なら、ロックを持っているセッション（長いトランザクション、VACUUM）を確かめ、負荷の低い時間に、そのシャードだけ再実行する。再実行は冪等である。
4. 同じシャードで 3 回失敗したら、Dev（テックリード）を呼ぶ。マイグレーションの中身に問題があるなら、前へ進める修正のマイグレーションを書く。途中まで当たったシャードを手で戻さない。
5. バックフィルが物理クラスタの負荷を上げたら、バックフィルの Worker を止める（ops フラグ）。止めても、アプリは expand の形で動く。

### 悪化したとき

1. **フラグで戻す。** 新しい機能のフラグを切る。新しいブロック・操作の種類が原因なら、その種類を作れなくするフラグを切る（既に作られたものは、読み取り専用で表示される）。
2. **アプリを戻す。** 1 つ前のイメージの digest で再デプロイする。Sync Gateway も同じ手順で 10% ずつ戻す。
3. **マイグレーションは戻さない。** expand は古いアプリでも動く。
4. **デスクトップの版が原因なら**、更新の情報の API で配布を止める。配った版は、中身を戻した新しい版で置き換える（前へ進めて戻す）。
5. contract でデータを失ったときは、[disaster-recovery.md](disaster-recovery.md) の C に進み、インシデントとして扱う。
6. 戻しても直らなければ、インシデントを宣言する（[incident-response.md](incident-response.md)）。

## エスカレーション

- 戻しても 15 分以内に SLO が回復しない → インシデントを宣言する。
- RLS のポリシーの変更の後に、権限・テナント境界の監査で不一致が出た → SEV1。
- マイグレーションが途中で止まり、どのシャードがどの状態か台帳でわからない → Dev（テックリード）。
- デスクトップの版で、ローカルの保存のデータが壊れた・未確定のトランザクションが消えた疑い → SEV2 以上。Dev と QA を呼ぶ。
