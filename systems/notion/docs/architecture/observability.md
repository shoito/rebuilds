# Observability: Notion

SLI の計測、シャードとワークスペースの偏りの検出、アラート。道具と経路は Slack の [ADR-0021](../../../slack/docs/decisions/0021-observability-stack.md) と [observability.md](../../../slack/docs/architecture/observability.md) を引き継ぐ（[ADR-0001](../decisions/0001-platform-and-stack.md)）。SLO の値の正本は Ops の [runbooks/README.md](../runbooks/README.md) に置き、ここにはそれを計測する仕組みと、NFR から導いた初期値を書く。

## 1. 引き継ぐもの

| 項目 | Slack と同じ | Notion での追加 |
| --- | --- | --- |
| 計装 | OpenTelemetry（`packages/telemetry`）、ADOT のサイドカー | 共通の属性に `db.shard.logical`（論理シャード）、`db.cluster`（物理クラスタ）を足す |
| 送り先 | メトリクスは AMP、トレースは X-Ray、ログは CloudWatch Logs、Grafana で横断 | 変わらない |
| トレースの伝播 | `traceparent`。outbox の行に `trace_context`、Relay はスパンリンク | トランザクション → outbox → Relay → Gateway → 他のクライアントまで 1 つのトレースで追う |
| ログ | 1 行 1 JSON、許可リスト方式で個人情報を出さない | ブロックの本文、ページのタイトル、データベースのプロパティの値、検索語を出さない。ブロックとページの ID は出してよい |
| サンプリング | 先頭で 10%。合成監視のワークスペースは 100% | 再シャーディング中の群れのワークスペースは 100%（照合の調査のため） |
| 保持・アクセス | 本番のログは prod のアカウントから出さない。AI エージェントは本番のログへの経路を持たない | 変わらない |

## 2. SLI

| SLI | 計測 | 初期の SLO（NFR） |
| --- | --- | --- |
| 編集の反映の遅延 | サーバー：トランザクションの受け付けから、Gateway が同じページの他の接続へ送り終えるまで（`edit_propagation_latency`、ヒストグラム）。クライアント：他人の変更を受け取ってから描画するまで（RUM） | サーバーの区間で 500ms 以内の割合 99%（NFR-001 の p99 500ms を比率の SLI にする） |
| トランザクションの成功率 | トランザクションの受け付けのルートの 5xx 以外の割合。429、権限による拒否、検証による拒否は成功として数える | 99.9%（NFR-007） |
| ページの表示 | RUM：ページを開いてから最初の 1 画面ぶんのブロックが描画されるまで。ローカルにある・ないで分ける | ないとき p75 1.5 秒、あるとき p75 300ms（NFR-002） |
| データベースのビューの問い合わせ | サーバー：ビューの問い合わせのルートの処理時間。行数の区分（〜1 千、〜1 万、それ以上）をラベルにする | 1 万行以下で p95 1 秒（NFR-003） |
| 同期の滞留 | 3 つの区間で測る（2.1 節） | outbox の最古の行 5 秒以内、クライアントの未確定の最古 30 秒以内（接続中の利用者のうち 99%） |
| 検索への反映 | 変更の確定から、検索の索引に反映されるまで（`search_index_lag`） | 30 秒以内の割合 99%（NFR-006） |
| 権限の監査の不一致 | 定期の監査（検索・通知・API の結果を、判定関数で判定し直す。[permissions-and-sharing.md](permissions-and-sharing.md)） | 0 件（NFR-010） |
| オフラインの統合の失敗 | クライアント：再接続時に、ローカルの変更の送信が恒久的に失敗した件数 | 0 件を目標。1 件でも QA に共有（NFR-005） |

- 遅延はすべてヒストグラムで持ち、パーセンタイルは Prometheus のクエリで出す。サーバーの区間はサーバーの時計で測る（Slack と同じ）。
- NFR-001 は「入力から他の利用者の画面まで」なので、クライアントの区間を含む。SLO の判定はサーバーの区間で行い、クライアントの区間は RUM で見る（時計がずれるため）。

### 2.1 同期の滞留の 3 つの区間

```
クライアント ──(未確定の待ち行列)──▶ API ──(outbox)──▶ Relay ──(Valkey)──▶ Gateway ──▶ 他のクライアント
     ①                                         ②                              ③
```

| 区間 | メトリクス | 何を疑うか |
| --- | --- | --- |
| ① クライアントの未確定 | RUM：待ち行列の件数と最古の経過時間。接続中のものだけを SLO に数える（オフラインは除く） | API の遅延・エラー、`frozen` のシャード、レート制限 |
| ② outbox | 論理シャードごとの未処理件数と最古の行の経過時間 | Relay の停止・リースの偏り、DB の負荷 |
| ③ Gateway の送信 | タスクごとの送信の待ち、遅い受信者の切断（4003 相当）の数 | Gateway の過負荷、巨大なページ |

## 3. メトリクス

| 種類 | 対象 | 主な指標 |
| --- | --- | --- |
| RED | api、sync-gateway、relay、workers | ルート・イベントごとの件数、エラー、処理時間 |
| USE | Aurora（クラスタごと）、Valkey、ECS、SQS、ALB | CPU、接続数、レプリカ遅延、キューの長さ |
| シャード | 論理シャード（480）と物理クラスタ | 2.1 節の outbox、トランザクション数、DB 時間、行数、`frozen` の時間 |
| 業務 | 全体 | トランザクション/秒、操作/秒、同時接続、開かれているページ数、ページの読み込み/秒、検索/秒 |
| DB の健全性 | Aurora | `age(datfrozenxid)`、デッドタプル、論理レプリケーションのスロットの遅延（保持している WAL の量）、`AuroraGlobalDBRPOLag`、マイグレーションの台帳（未適用のシャードの数） |
| 再シャーディング | reshard | 複製の遅延、影の読み取りの件数と不一致（遅延で説明できるもの・できないもの）、切り替えの書き込みの待ち時間 |
| クライアントの品質 | RUM | 欠損の検知（`seq` の飛び）、再接続の回数、統合の失敗、ローカルの保存の容量の不足 |

### 3.1 ラベルとカーディナリティ

- **論理シャード（`shard`）は常にラベルにしてよい。** 値は 480 に固定されている。ただし、ヒストグラムには付けない（バケット数 × 480 になるため）。シャードごとの遅延は、件数とエラーと DB 時間から見る。
- **物理クラスタ（`cluster`）** は、ヒストグラムを含むすべての DB の指標に付ける。数は最大でも数百。
- **ワークスペースは上位 N 件＋「その他」**（Slack の 3.2 節と同じ。N の初期値 50）。付けるのは、トランザクション数、エラー数、DB 時間、接続数、開いているページ数に限る。
- ページ・ブロック・利用者の ID は、メトリクスのラベルにしない。ログとトレースにだけ持たせる。

## 4. 偏り（ホットスポット）の検出

1 つのシャード・ワークスペース・ページが共有の資源を占有していないかを、3 つの粒度で見る。

| 粒度 | 見るもの | 検出の条件（初期値） | 対処 |
| --- | --- | --- | --- |
| 物理クラスタ | writer の CPU、DB 時間、レプリカ遅延 | CPU 50% を 15 分超える | [runbooks/incident-response.md](../runbooks/incident-response.md) の「重いシャード」 |
| 論理シャード | シャードごとの DB 時間の比率 | 1 シャードが、そのクラスタの DB 時間の 20% を 15 分超える（平均の約 100 倍。S1 で 480 シャードの場合） | 同上。原因のワークスペースを特定する |
| ワークスペース | 上位 N 件の DB 時間、トランザクション数 | 1 ワークスペースが、そのクラスタの DB 時間の 30% を 15 分超える | 同上。一時的にレート制限を下げる |
| ページ | Gateway の配信の件数（ページの ID はトレースから）、ページの `seq` の行ロックの待ち | 1 ページへのトランザクションが 1 秒に 50 件を超える | 同上。在席の配信を間引く |

- DB 時間をシャードごとに数えるため、ルーターは各トランザクションの SQL に論理シャードとワークスペースの注釈（SQL のコメント）を付け、`pg_stat_statements` と遅いクエリのログから集計できるようにする。スキーマが違えば同じ SQL でも別の行になるので、`pg_stat_statements` の行数は 480 倍になりうる（`pg_stat_statements.max` を上げる。値は負荷試験で決める）。
- 月次で、論理シャードの負荷の分布（上位 10 シャードの比率）を見て、移動の要否を判断する（[capacity.md](capacity.md) の 6 節）。

## 5. アラート

Slack と同じく、SLO はマルチウィンドウのバーンレート（1 時間・5 分で 14.4、6 時間・30 分で 6、3 日・6 時間で 1）で通知する。すべてのアラートに runbook の URL を付ける。

| アラート | 重さ | 手順 |
| --- | --- | --- |
| 編集の反映の遅延・トランザクションの成功率の速いバーンレート | 呼び出し | [incident-response.md](../runbooks/incident-response.md) |
| 合成監視の 2 回連続の失敗 | 呼び出し | 同上 |
| 権限の監査の不一致が 1 件以上 | 呼び出し（SEV1） | 同上 |
| 同期の滞留：outbox の最古の行が 30 秒を 5 分超える（どれかのシャード） | 呼び出し | 同上の「同期の滞留」 |
| 同期の滞留：クライアントの未確定の最古が 30 秒を超える利用者が 1% を超える | 呼び出し | 同上 |
| 物理クラスタの writer の CPU 50% が 15 分、1 シャード・1 ワークスペースの占有（4 節） | チケット（CPU 80% で呼び出し） | 同上の「重いシャード」 |
| 検索への反映の遅延の遅いバーンレート | チケット | `search-indexing.md`（E6） |
| `AuroraGlobalDBRPOLag` が 5 分を超える | 呼び出し | [disaster-recovery.md](../runbooks/disaster-recovery.md) |
| 論理レプリケーションのスロットが保持する WAL が閾値（初期値 100 GB）を超える | 呼び出し | `resharding.md`（E9）、`data-lake.md`（E9。S2 の CDC） |
| `age(datfrozenxid)` が 10 億を超える | 呼び出し | `db-maintenance.md`（E8） |
| マイグレーションの台帳で、失敗したシャードがある・30 分進まない | チケット | [deploy-and-rollback.md](../runbooks/deploy-and-rollback.md) |
| 影の読み取りの、遅延で説明できない不一致が 1 件以上 | チケット（再シャーディングを止める） | `resharding.md`（E9） |
| デプロイ中の自動ロールバック | 通知 | [deploy-and-rollback.md](../runbooks/deploy-and-rollback.md) |

呼び出しのアラートは、SLO か、利用者への影響が確実な症状と、放置すると全体が止まるもの（WAL の蓄積、トランザクション ID の周回）に限る。

## 6. 合成監視

CloudWatch Synthetics のカナリアを大阪から実行する（Slack と同じ）。prod の中の専用ワークスペースを、マイグレーションの群れ G0 のシャードに置く（[ADR-0031](../decisions/0031-migration-rollout-by-shard-groups.md)）。1 分ごとに次を行う。

1. クライアント A がページを開き、ブロックを 1 つ編集する。
2. 同じページを開いたクライアント B が、WebSocket で変更を受け取る（反映の遅延を記録する）。
3. データベースのビューを問い合わせる。
4. 30 秒以内に、編集した語で検索にヒットする。
5. 権限のない利用者 C が、そのページを検索・API で見つけられない。

S2 以降は、物理クラスタごとに合成監視のワークスペースを 1 つ置き、クラスタ単位の障害を見分けられるようにする。

## 7. 実ユーザー監視（RUM）

Slack の 6 節と同じ経路（`POST /telemetry` で API に送り、API が検証・間引きしてメトリクスに変換する）。Notion で送る指標：

- Web Vitals、JavaScript のエラー、デスクトップアプリのバージョン
- ページの表示の時間（ローカルにある・ない）
- 他人の変更を受け取ってから描画するまでの時間（`trace_id` 付き）
- 未確定の待ち行列の件数と最古の経過時間、オフラインの時間
- 再接続の回数、欠損の検知、統合の失敗
- ローカルの保存の使用量と、容量の不足による失敗
