# Comments and notifications: Notion

コメントとディスカッション、解決、メンション（人・ページ・日付とリマインダー）、受信箱、メール通知、ページの更新。通知のパイプラインは Slack の設計（Slack の read-state-and-notifications.md の 4 節）を先例にする。

## 1. 本家の振る舞い

本家のヘルプで確かめた（2026-09-26）。

| 機能 | 本家の振る舞い | 出典 |
| --- | --- | --- |
| コメント | ページ全体へのコメントと、本文の一部（テキストの範囲・ブロック）へのインラインのコメント。編集・削除・解決・再開・リアクション。コメントの一覧で人・状態で絞り込む。データベースのプロパティへのコメントもある | [Comments, mentions & reactions](https://www.notion.com/help/comments-mentions-and-reminders) |
| メンション | 人・グループ、ページ、日付。人のメンションは受信箱に通知する。**読めないページで人をメンションしても、その人には通知しない**。ページのメンションはバックリンクを作る | 同上 |
| リマインダー | `@remind` と日付、データベースの日付プロパティ。受信箱・デスクトップ・モバイルに通知する。他人に対しても設定できる。繰り返しはない | [Reminders](https://www.notion.com/help/reminders) |
| 受信箱 | メンションと返信、コメント、人のプロパティへの追加、リマインダー、招待、購読したページの変更。既読・未読・アーカイブ。ページごとに「すべての更新」「すべてのコメント」「返信と @メンション」を選ぶ | [Inbox & notifications](https://www.notion.com/help/updates-and-notifications) |
| メール | アプリで約 5 分見ていないときに送る。「常にメールを送る」の設定がある。ページの更新とワークスペースのダイジェストのメール | [Notification settings](https://www.notion.com/help/notification-settings) |
| 公開 API | コメントの取得・作成・更新・削除。ページ・ブロック・既存のディスカッションへの返信はできるが、テキストの範囲に新しいディスカッションは作れない。添付は 3 件まで | [Create a comment](https://developers.notion.com/reference/create-a-comment) |

## 2. コメントとディスカッション

### 2.1 データ

コメントはブロックにしない。ブロックの木（ADR-0002）に入れると、ページの本文の読み込み・エクスポート・同期の対象が膨らむため。権限はコメントが付いたページで判定する（ADR-0004）。

| 表 | 主な列 |
| --- | --- |
| `discussions` | `workspace_id`、`id`、`page_id`、`anchor_kind`（`page` / `block` / `text` / `property`）、`block_id`、`property_id`、`resolved_at`、`resolved_by`、`anchor_lost`、作成の情報 |
| `comments` | `workspace_id`、`id`、`discussion_id`、`author_id`（人か連携）、`rich_text`（JSON）、`attachments`（最大 3）、`edited_at`、`deleted_at`、作成の情報 |
| `comment_reactions` | `workspace_id`、`comment_id`、`member_id`、`emoji` |

- テキストの範囲へのディスカッションは、ブロックのリッチテキストに「コメントの印」（`discussion_id` を持つ装飾。[block-model.md](block-model.md) の `marks.comments`）として置く。印はテキストと同じ統合の方式（[collaboration.md](collaboration.md)）で動くので、周りの編集に追随する。
- 印のあるテキストがすべて消えたら、`anchor_lost` を立てる。ディスカッションは消さず、コメントの一覧に「削除された内容」として残す。元に戻す（undo・履歴の復元）で印が戻れば、`anchor_lost` を外す。
- ブロックごとページを削除しても、コメントは消さない。ページのゴミ箱からの復元で戻る。ページの完全な削除で消す。
- `property` はデータベースのプロパティへのコメント（本家の機能）。MVP の後に入れる。

### 2.2 操作と権限

コメントの操作は、ページのトランザクション（ADR-0005）の操作として送る。ページの `seq` を消費し、同じ経路で同時に開いている人へ配信する。オフラインで書いたコメントも、再接続時に送られる。

| 操作 | 必要な権限（ページに対して） |
| --- | --- |
| コメントを読む | 閲覧以上（本家と同じ。[permissions-and-sharing.md](permissions-and-sharing.md) の 4.2 節） |
| ディスカッションを始める・返信する | コメント可以上 |
| 自分のコメントの編集・削除 | コメント可以上、かつ作者 |
| 他人のコメントの削除 | 全権限 |
| 解決・再開 | コメント可以上 |
| リアクション | コメント可以上 |

- 閲覧だけの人もコメントを読める（本家と同じ。決定は [README.md](README.md) の「決定」）。書く・解決する・リアクションには、コメント可以上が要る。
- Web に公開したページ（公開サイト）では、コメントを描画しない（[permissions-and-sharing.md](permissions-and-sharing.md) の 8 節）。
- コメントの本文も、判定関数を通して返す。コメントの一覧の API、受信箱、メール、公開 API のどこでも同じ。

## 3. メンション

リッチテキスト（本文とコメント）の要素として持つ（[editor.md](editor.md)）。

| 種類 | 保存する値 | 表示 | 通知 |
| --- | --- | --- | --- |
| 人 | `member_id` | 表示の時点の名前 | 受信箱。メンションされた人がページを読めるときだけ |
| グループ | `group_id` | グループ名 | グループのメンバーのうち、ページを読める人だけ |
| ページ | `page_id` | 表示する人がそのページを読めればタイトル、読めなければ「アクセス権のないページ」 | なし。対象のページにバックリンクを作る |
| 日付 | 日付・時刻・タイムゾーン、任意でリマインダー | 表示する人のタイムゾーンで | リマインダーがあれば、その時刻に（4 節） |

- **読めない人へのメンション**：通知しない（本家と同じ）。エディタは入力の時点で、その人がページを読めないことを示し、共有を促す。共有するかは書いた人が決め、自動では共有しない。
- **ページのメンションのタイトル**：本文に保存するのは `page_id` だけで、タイトルは表示のたびに判定関数を通して解決する。読めないページのタイトルは、本文・エクスポート・API・通知のどこにも出さない（intent.md の「守るべき振る舞い」）。
- **バックリンク**：`backlinks (workspace_id, target_page_id, source_block_id, source_page_id)` を、メンションを含むブロックの変更のトランザクションで更新する。バックリンクの一覧は、元のページを読めるものだけを返す。
- メンションの記録：`mentions (workspace_id, block_id or comment_id, page_id, mentioned_member_id, created_by, created_at)`。編集で新しく増えたメンションにだけ通知する。消えたメンションの未読の通知は取り消す。

## 4. リマインダー

| 項目 | 設計 |
| --- | --- |
| 設定の場所 | 日付のメンション（`@remind`）と、データベースの日付プロパティ |
| 通知の時刻 | 当日の時刻、または「5 分前」「1 時間前」「1 日前」などの前倒し。日付だけの場合は、その日の 9:00（受け手のタイムゾーン） |
| 受け手 | 設定した本人。人のメンションを並べて書いたときは、その人（本家と同じ） |
| 保存 | `reminders (workspace_id, id, block_id or (page_id, property_id), member_id, fire_at（UTC）, tz, state)`。`(state, fire_at)` の部分インデックス |
| 発火 | 論理シャードごとのスケジューラーが、1 分ごとに `fire_at <= now()` の行を `FOR UPDATE SKIP LOCKED` で取り、通知の計画（5 節）に渡す |
| 変更・削除 | 日付の変更・メンションの削除・ブロックの削除のトランザクションで、行を更新・取り消す |
| 繰り返し | 持たない（本家と同じ） |

- 目標：`fire_at` から受信箱に届くまで p99 2 分（本家は 5 分以内）。
- 発火の時点で、受け手がまだページを読めるかを判定し、読めなければ捨てる。
- タイムゾーンは、設定した時点の設定者のもの（`tz`）を保存する。夏時間の切り替えでも壁時計の時刻を保つ。

## 5. 通知のパイプライン

```
API ─tx─▶ outbox ─▶ Relay ─▶ SQS notify-events ─▶ 通知の計画（planner）
                                                   │ 受け手を決め、判定関数で読めるか確かめる
                                                   ├──▶ inbox_items（DB）─▶ Sync Gateway（本人の購読）
                                                   ├──▶ SQS notify-push ─▶ デスクトップ・Web Push
                                                   └──▶ notification_pending_emails（DB）─▶ 1 分ごとにメール（SES）
リマインダーのスケジューラー ─────────────────────────┘
```

### 5.1 受け手の決め方

| きっかけ | 受け手 |
| --- | --- |
| 人・グループのメンション | メンションされた人 |
| ディスカッションへの返信 | そのディスカッションの参加者（書いた人、メンションされた人）。本人の返信は除く |
| 新しいコメント | ページを「すべてのコメント」以上で購読している人 |
| ページの変更 | ページを「すべての更新」で購読している人（6 節） |
| 人のプロパティへの追加 | 追加された人 |
| ページへの招待 | 招待された人 |
| リマインダー | 4 節の受け手 |

- 購読の既定：ページを作った人と、ページで人のメンションをされた人・コメントした人は、そのページを「返信と @メンション」で購読する。本家の既定の詳細は未検証。
- 購読の記録：`page_subscriptions (workspace_id, page_id, member_id, level)`。
- 変更した本人には通知しない。

### 5.2 権限の再確認

通知は、書いた人ではなく受け手の権限で中身を見せる経路なので、次の 3 か所で判定関数を通す。

| 時点 | 確かめること | 読めないとき |
| --- | --- | --- |
| 計画（受け手を決めるとき） | 受け手が `can(recipient, read, page)` | 通知を作らない |
| 受信箱の表示 | 表示のたびに同じ判定。タイトル・抜粋は、その時点で DB から読む | 項目を出さない（件数にも数えない） |
| メール・push の送信 | 送る直前に同じ判定 | 送らない。本文を含む push は、送る直前に内容を作る |

- `inbox_items` には ID（ページ・ブロック・コメント・操作した人）と種類だけを持ち、タイトルや本文の写しを持たない。共有を外された後に、古いタイトルが受信箱に残らない。
- 未読の数は、表示の判定を通った項目だけで数える。

### 5.3 受信箱

| 項目 | 設計 |
| --- | --- |
| 表 | `inbox_items (workspace_id, member_id, id, kind, page_id, block_id, comment_id, actor_ids, group_key, created_at, read_at, archived_at)` |
| まとめ | 同じページの同じ種類の通知は、`group_key`（ページ・種類・時間の窓）で 1 件にまとめ、操作した人を `actor_ids` に足す。ページの変更は 1 時間の窓、コメントはディスカッションごと |
| 操作 | 既読・未読、アーカイブ、「すべて既読」。絞り込み（未読・アーカイブ・種類） |
| リアルタイム | 項目の追加を、本人の購読（Sync Gateway）に流し、バッジを更新する |
| 保持 | 180 日。アーカイブ済みを含む |

### 5.4 メール

| 項目 | 設計 |
| --- | --- |
| 送る条件 | 受信箱の項目が 5 分たっても既読にならず、その人がどの端末でも操作していない（在席していない）とき。「常にメールを送る」がオンなら、在席に関係なく 5 分後に送る |
| まとめ | 送る時点で未読の項目を、ワークスペースごとに 1 通にまとめる |
| 中身 | ページのタイトル、操作した人、コメント・メンションの前後の短い抜粋。送る直前に判定を通した値から作る |
| リンク | ページの URL だけ。メールのリンクはログインを要し、アクセスの権限を与えない |
| 配信停止 | 種類ごとの配信停止のリンク（`List-Unsubscribe`） |
| 送信 | SES。バウンスと苦情で、その宛先への送信を止める |

- ゲストのメールにも同じ条件で送る。
- 「アクティビティ」「おすすめ」のマーケティングに近いメールは持たない。

### 5.5 push

- デスクトップアプリと Web（PWA）の通知。本家のデスクトップは約 10 秒後に通知する（[Inbox & notifications](https://www.notion.com/help/updates-and-notifications)）。同じく 10 秒待ち、その間に既読になれば送らない。
- モバイルのネイティブアプリは MVP の対象外（intent.md）。

### 5.6 通知の設定

| 範囲 | 設定 |
| --- | --- |
| アカウント | メール（オン・オフ、常に送る）、デスクトップ・Web の push、種類ごとのオン・オフ |
| ページ | 購読の水準（すべての更新 / すべてのコメント / 返信と @メンション / なし） |

- Slack・Microsoft Teams への通知（本家にある）は MVP の後。

## 6. ページの更新

### 6.1 更新の欄（ページごと）

ページの「更新」の欄に、そのページの変更・コメント・解決・プロパティの変更を新しい順に並べる。

- 元は操作のログ（ADR-0005）。操作を人と時間の窓（10 分）でまとめ、「〇〇 が 3 つのブロックを編集」などの要約にする。
- 要約の表 `page_activity (workspace_id, page_id, window_start, actor_id, kind, block_ids, counts)` を、操作のログから Worker が作る。操作のログがスナップショットに畳まれても、要約は残す（保持は履歴と同じ。[block-model.md](block-model.md)）。
- 表示は、ページを読める人だけ。子のページの変更を含めるときは、子のページごとに判定する。
- ページの履歴と復元は [block-model.md](block-model.md) にある。

### 6.2 購読したページの変更の通知

- 「すべての更新」で購読した人に、6.1 節の要約の単位で受信箱の項目を作る（5.3 節のまとめの窓は 1 時間）。
- データベースの行の、状態・担当者・期日の変更は、本家と同じく購読した人に通知する。

### 6.3 ダイジェストのメール

- ページの更新とワークスペースのダイジェストのメール（本家にある）は、MVP の後に入れる。入れるときも、送る直前に 1 件ずつ判定関数を通す。

## 7. 公開 API と Webhook

- コメントの API（取得・作成・更新・削除）は [api-and-integrations.md](api-and-integrations.md) にある。本家と同じく、API からはテキストの範囲に新しいディスカッションを作れない。
- 連携がコメントを書くと、作者は連携になり、画面に連携の名前を出す。連携が書いたメンションも、同じ条件で通知する。
- `comment.created`・`comment.updated`・`comment.deleted` の Webhook は、コメントの読み取りの能力を持つ連携にだけ送る（[ADR-0025](../decisions/0025-webhook-delivery.md)）。

## 8. 規模と運用

| 対象 | 見積もり（S1） |
| --- | --- |
| 受信箱の項目 | 1 人 1 日 20 件 × 10 万人 × 180 日 ≒ 3.6 億行。ワークスペースで分割（ADR-0003） |
| メール | 1 日 20 万通の見込み。SES の送信の上限を事前に引き上げる |
| リマインダー | 1 分あたり数百件 |

- 指標：計画の遅れ（コミット → 受信箱）の p99 10 秒、メールの送信の遅れ、判定で捨てた通知の件数、リマインダーの発火の遅れ。
- 大人数への通知（グループのメンション）は、500 人ずつに分けて処理する（Slack と同じ）。

## 9. テスト

- 漏洩テスト：共有されていないページでのメンション、通知の後に共有を外したページ、アクセス権のない親の下に移したページについて、受信箱・未読の数・メール・push・更新の欄に、タイトル・抜粋が出ない。
- 読めないページのメンションが、本文の表示・エクスポート・API で「アクセス権のないページ」になる。
- 性質ベーステスト：任意の共有の変更と通知の列で、受信箱が表示する項目は、すべて表示の時点で `can(recipient, read, page)` が真である。
- リマインダー：タイムゾーン・夏時間・日付の変更・ブロックの削除で、発火が正しく更新・取り消される。
- テキストの範囲のコメントの印が、同時の編集の後も正しい範囲に残る（[collaboration.md](collaboration.md) の性質とあわせて）。

## 10. 決定と持ち越し

2026-09-26 に、本家に寄せる既定案で次のとおり決めた（[README.md](README.md) の「決定」）。

- 閲覧だけの人もコメントを読める。公開サイトの閲覧者には、コメントを描画しない。
- 購読の既定は 5.1 節のとおり（ページを作った人、メンションされた人、コメントした人を「返信と @メンション」で購読する）。本家の既定の細部は未検証で、E6 の Story で本家を観察して揃える。
- ダイジェストのメールは MVP に入れない（[roadmap.md](../roadmap.md) の「後回しにしたもの」）。
