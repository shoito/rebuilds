# Collaboration: Notion

同時編集の方式、クライアントの待ち行列と統合、衝突の規則、在席とカーソル、変更の配信、再接続と差分取得、オフライン。

前提となる決定は、ブロック（[ADR-0002](../decisions/0002-everything-is-a-block.md)）、ワークスペースのシャード（[ADR-0003](../decisions/0003-workspace-sharding.md)）、権限の判定関数（[ADR-0004](../decisions/0004-inherited-page-permissions.md)）、トランザクションとページごとの `seq`（[ADR-0005](../decisions/0005-transactions-as-unit-of-change.md)）。この文書で決めたことは次の ADR にある。

| ADR | 決定 |
| --- | --- |
| [0010](../decisions/0010-text-crdt-with-server-ordered-structure.md) | テキストはブロックごとの CRDT（Fugue＋Peritext）で統合し、構造とプロパティはサーバーの順序で決める |
| [0011](../decisions/0011-structural-and-property-conflict-rules.md) | 構造とプロパティの衝突は、サーバーの順序と決まった規則で解き、負けた変更を記録して本人に見せる |
| [0012](../decisions/0012-child-order-by-sibling-anchors.md) | 子の並びは前後の兄弟をアンカーにした操作で表し、分数インデックスは使わない |
| [0013](../decisions/0013-offline-availability-policy.md) | オフラインで使うページを理由ごとに記録して決め、Web とデスクトップで SQLite に保存する |
| [0032](../decisions/0032-desktop-uses-wasm-sqlite-in-s1.md) | S1 のデスクトップも Web と同じ WASM の SQLite（OPFS）を使い、ネイティブの SQLite は S2 の候補にする |

配信の仕組み（Gateway、Valkey、背圧、再接続の殺到）は、Slack の [realtime.md](../../../slack/docs/architecture/realtime.md) をそのまま使う。Relay の担当の分け方は、論理シャードがあるため Slack と違う（7.3 節）。この文書には、Notion で違うところだけを書く。

## 1. 原則

- **正本はサーバーの操作のログと、ブロックの表である。** クライアントの画面は、確定した状態に、未確定の自分の変更を重ねたものである（Replicache と同じ考え方。[How Replicache works](https://doc.replicache.dev/concepts/how-it-works)）。
- **操作は「意図」で書く。** 位置は添字ではなく、ID（文字の ID、兄弟のブロックの ID）で指す。これにより、サーバーは古い版を基にした操作も、今の状態へそのまま当てられる。操作の変換（OT）のように、途中のすべての操作と突き合わせる必要がない。
- **テキストは CRDT で必ず合わさる。構造とプロパティはサーバーの順序で決まる。** テキストの入力は失わない。構造とプロパティの競合で捨てた値は、衝突の記録として残し、本人に見せる（6 節）。
- **配信はベストエフォート。** 欠けたものは、クライアントがページの `seq` の飛びで検知して取り戻す（Slack の [ADR-0001](../../../slack/docs/decisions/0001-per-channel-sequence.md)、[ADR-0002](../../../slack/docs/decisions/0002-db-as-source-of-truth-with-outbox.md)）。
- **権限は、操作を当てるときの権限で判定する。** オフラインの間に失った権限で書いた変更は、受け付けない（10 節）。

## 2. 本家の方式

| --- | --- | --- |
| 変更の単位 | 操作をトランザクションにまとめ、`/saveTransactions` でサーバーが検証して記録する。クライアントは `TransactionQueue` に保存してから送る（[The data model behind Notion's flexibility](https://www.notion.com/blog/data-model-behind-notion)） | 同じ（ADR-0005） |

| テキストの統合 | 2025 年 7 月から、RGA に Peritext の書式の操作を足した CRDT。ブロックの分割・結合に「text slice / text instance」を使う。以前は同じブロックへの同時の編集が LWW で失われた（[How Notion handles concurrent editing with CRDTs](https://www.notion.com/blog/how-notion-handles-concurrent-editing-with-crdts)） | Fugue＋Peritext の CRDT。分割・結合は本家の text slice に倣う（ADR-0010） |

| オフライン | デスクトップとモバイルのアプリだけ。明示したページ、有料プランでは最近のページとお気に入り。データベースは最初のビューの先頭 50 行。子ページは含めない。`offline_page` と、理由を持つ `offline_action` の表で管理する（[How we made Notion available offline](https://www.notion.com/blog/how-we-made-notion-available-offline)、ヘルプ） | Web（PWA）も含める。理由の表の考え方は同じ（ADR-0013） |
| 在席・カーソル | 実装の公開情報はない。CRDT の記事は、在席の表示の改善を今後の課題に挙げている（[How Notion handles concurrent editing with CRDTs](https://www.notion.com/blog/how-notion-handles-concurrent-editing-with-crdts)、2026-09-27 に確認） | Gateway の一時的なイベント（9 節） |

## 4. 操作

操作は、ADR-0005 のトランザクションに入れて送る。1 つのトランザクションは 1 つのワークスペースの中で閉じる。

| 操作 | 対象 | 統合 |
| --- | --- | --- |
| `block.insert { id, parent, after?, before?, type, props }` | ブロックの作成 | 並びはアンカー（ADR-0012）。ID はクライアントが UUIDv7 で振る |
| `block.move { id, parent, after?, before? }` | 移動（ページの間も） | 規則は ADR-0011 |
| `block.delete { id }` / `block.restore { id }` | 削除（`alive = false`。ページはゴミ箱へ）と復元 | 規則は ADR-0011 |
| `prop.set { id, path, value, base_version }` | 単一値のプロパティ、ブロックの種類、書式以外の属性 | サーバーの順序で LWW。負けた値を記録する |
| `prop.add / prop.remove { id, path, item }` | 複数選択、人、リレーション、ファイル | 集合として合わせる |
| `text.insert / text.delete / text.mark { instance, ... }` | ブロックのテキスト、ページのタイトル、テキストのプロパティ | CRDT（5 節） |
| `text.split / text.join` | 段落の分割（Enter）・結合（行頭の Backspace） | text slice（5.3 節） |

- エディタは、打鍵を 100ms ごとに 1 つのトランザクションにまとめる。ドラッグや貼り付けは 1 回の動作で 1 つにする。
- トランザクションは `device_id` と、端末ごとの連番 `tx_counter` を持つ。サーバーは端末ごとに適用済みの最大値（`device_cursors`）を持ち、それ以下は適用済みとして成功を返す。Replicache の `lastMutationID` と同じ考え方で、何日オフラインでも重複して当たらない。

## 5. テキストの CRDT

### 5.1 列

- 各ブロックのテキストは、Fugue の列 CRDT で持つ（[The Art of the Fugue](https://arxiv.org/abs/2305.00583)）。本家の RGA ではなく Fugue にするのは、2 人が同じ位置へ前向きに（左から右へ）長く書いたときに、互いの文が文字単位で交ざらないためである。RGA は、後ろ向きの挿入が重なると交ざりうる。交ざりを最小にする性質（maximal non-interleaving）が証明されているのは変種の FugueMax で、Fugue は実装が簡単な代わりに、後ろ向きの挿入で交ざる文字が少し多くなりうる（同じ論文、2026-09-27 に確認）。通常の入力は前向きなので、Fugue で足りるとする。オフラインの長い編集ほど効く。
- 文字の ID は `(replica_id, counter)`。`replica_id` は端末とセッションごとに振る。連続して入力した文字は 1 つの run にまとめて保存する。
- 削除は墓標（tombstone）にする。中身の文字列は消し、ID の範囲だけを run で残す。墓標は消さない。何か月も前の版を基にした操作でも、アンカーの ID が必ず見つかるようにするため。
- メンション（人・ページ・日付）とインラインの数式は、属性を持つ 1 文字として扱う。

### 5.2 書式

- 書式は Peritext に従う（[Peritext](https://www.inkandswitch.com/peritext/)）。`text.mark { start, end, type, value }` の両端は文字の ID と「前・後」の向きで指す。
- 太字・斜体・色などは、境界で入力したときに広がる。リンクとコメントの範囲は広がらない。
- 重なる書式（太字と斜体）は両方残る。排他的な値（色、リンク先）の競合は、操作の Lamport の時刻で後のものが勝つ。

### 5.3 ブロックの分割・結合

Peritext は段落をまたぐ構造を扱わない（論文の範囲外）。本家の text slice の考え方に倣う。

- テキストは「インスタンス」（最初に作ったブロックの ID で名付ける）に属する。分割は、後半の文字の範囲（slice）を新しいブロックへ移す操作である。文字の ID は変わらない。
- サーバーは「インスタンスと ID の範囲 → 今それを持つブロック」の索引（`text_slices`）を持つ。テキストの操作は、ブロックではなくインスタンスと文字の ID を指すので、分割・結合の後に届いた操作も、今の持ち主のブロックへ届く。
- 結合は、後ろのブロックの slice を前のブロックの末尾へ移し、後ろのブロックを削除する。
- 同じ位置での分割と入力が競合したら、入力は左のアンカーの文字を持つブロックに入る。

### 5.4 実装

- TypeScript で自前の実装を `packages/text-crdt` に持ち、クライアントとサーバーで同じものを使う。理由は ADR-0010。
- サーバーは、ブロックごとの CRDT の状態（`block_text_states`）と、読み取り用に展開したリッチテキスト（ブロックの `properties`）を同じトランザクションで書く。検索・API・エクスポートは展開した方を読む。

## 6. 構造とプロパティの衝突

規則の全体は ADR-0011 と ADR-0012。サーバーは、トランザクションを `seq` の順に、その時点の状態へ当てる。

| 競合 | 結果 | 本人への表示 |
| --- | --- | --- |
| 同じプロパティへの同時の設定 | サーバーに後に着いた方が勝つ | 負けた側に「上書きされた変更」を出し、値を戻せる |
| 複数値のプロパティへの追加と削除 | 両方の追加が残る。削除は、その要素があるときだけ効く | なし |
| 削除されたブロックのテキストの編集 | 編集は削除されたブロックに当たる（ゴミ箱・履歴から戻せる） | 「削除済みのブロックへの編集」と復元のボタン |
| 削除された親への挿入・移動（削除が先） | 挿入は削除された親の下に入る。移動は取り消す（元の場所に残す） | 挿入は復元のボタン、移動は取り消しの通知 |
| 同じブロックを別々の場所へ移動 | 後に着いた方が勝つ | なし |
| 循環になる移動（A を B の下へ、B を A の下へ） | 後に着いた方を取り消す | 取り消しの通知 |
| アンカーの兄弟が消えている | もう一方のアンカー、どちらもなければ親の末尾 | なし |
| プロパティがスキーマから消えた・型が変わった | 合わない値の設定を取り消す | 取り消しの通知と値 |
| 段落を見出しに変える操作とテキストの編集 | 独立に両方当たる | なし |

- 「取り消す」は、トランザクション全体を拒否するのではなく、その操作だけを当てない。ADR-0005 の「まとめて拒否」は、検証の失敗（権限、不正な値、木の不変条件）に使う。
- 捨てた値・取り消した操作は `sync_conflicts` に 30 日残し、該当する利用者に出す（11.5 節）。ページの履歴にも残る。

## 7. 変更の流れと配信

```
Client ──(WebSocket or POST /transactions)──▶ API
  API: page_seqs の行を page_id の順にロック → 権限（ADR-0004）→ 操作を当てる → 木の検証
       → blocks / block_text_states / page_ops（page_id, seq）/ outbox を 1 トランザクションで書く
                                   │ poll 25ms
                                   ▼
                                 Relay ──▶ Valkey  ws:{w}:pg:{page_id} ──▶ Sync Gateway ──▶ 購読中のクライアント
                                   └────▶ SQS（検索の索引、通知、Webhook）
```

- ページの `seq` は、`page_seqs (workspace_id, page_id, last_seq)` の行で採番する。この行のロックが、ページごとの書き込みの直列化になる。ブロックの行（大きい JSON）と分け、更新の多い小さな行にする（[capacity.md](capacity.md) の 3.1 節）。
- トランザクションが複数のページに触れる（ページの間の移動）ときは、触れた各ページで `seq` を 1 つ進める。ロックはページの ID の順に取り、デッドロックを避ける。
- 操作のログ `page_ops (workspace_id, page_id, seq, tx_id, actor_id, device_id, ops JSONB, client_created_at, committed_at)` は、差分取得の元にする。保持は 30 日。履歴はスナップショットで持つ（[block-model.md](block-model.md)）。
- Valkey・Gateway は Slack と同じ（[realtime.md](../../../slack/docs/architecture/realtime.md) の 7・8・11 節、Slack の [ADR-0013](../../../slack/docs/decisions/0013-gateway-scaling-and-presence.md)）。Relay は 7.3 節。

### 7.1 遅延の予算（NFR-001：p99 500ms）

| 区間 | 予算（p99） |
| --- | --- |
| 打鍵のまとめ | 100ms |
| 送信 → API のコミット | 150ms |
| コミット → Relay | 60ms |
| Relay → Valkey → Gateway → 送出 | 40ms |
| ネットワークと描画 | 150ms |

### 7.2 購読

| 対象 | Valkey のチャンネル | 条件 |
| --- | --- | --- |
| 開いているページ | `ws:{w}:pg:{page_id}` | 表示している間。1 接続あたり 20 ページまで（周辺のパネル、同期ブロックの元を含む） |
| メンバー | `ws:{w}:m:{member_id}` | 常に。権限の変更、セッションの失効 |
| 権限の変更 | `ws:{w}:acl` | 常に（Gateway がノードごとに 1 回） |

- 購読の開始時に、Gateway は ADR-0004 の判定関数で読めることを確かめ、そのページの祖先の鎖を覚える。
- 共有の設定の変更・ページの移動は `acl.changed { root_page_id }` として流す。Gateway は、祖先の鎖に `root_page_id` を含む購読を判定し直し、読めなくなった接続を外して `page.revoked` を送る。
- オフライン用に持っているページは購読しない。数が多いため、11.3 節の heads の照合で追う。
- 閲覧者が多いページ（公開ページ、全社の wiki。初期値 1,000 接続以上）は、Slack の大規模チャンネル（5.3 節）と同じく、編集しない接続には `page.head` を 1 秒に 1 回だけ送る。

### 7.3 Relay

[infrastructure.md](infrastructure.md) の 2 節の形にする。

- **物理クラスタごとに Relay の群れを 1 つ持ち、論理シャードごとのリースで担当を分ける。** outbox は各論理シャードのスキーマにある（[data-model.md](data-model.md)）。1 つの論理シャードの outbox は、リースを持つ 1 つのタスクだけが `id` の順に読むので、ページの中の順序が保たれる。
- リースは `global` の表ではなく、その物理クラスタの中で持つ（リースの表、期限 10 秒、5 秒ごとに更新）。タスクが止まったら、期限の後に同じ群れの別のタスクが引き継ぐ。デプロイでは、リースを手放してから止まる（[delivery.md](delivery.md) の 4.2 節）。
- S1 は物理クラスタ 1 つに Relay 2 タスクで、480 のリースを分け合う。1 タスクが止まっても、残りの 1 タスクが全シャードを引き継げる量にする（[capacity.md](capacity.md)）。
- 再シャーディングで論理シャードが別のクラスタへ移ったら、そのシャードのリースは移動先のクラスタの Relay の群れに移る（[ADR-0028](../decisions/0028-zero-downtime-resharding.md)）。移動元のスキーマはフェンスされるので、新しい行は増えない。移動元の Relay が残りを送り終えてから、リースを手放す。
- outbox の表は時間でパーティションを切り、送った後の古いパーティションを `DROP` する（[capacity.md](capacity.md) の 3.1 節）。

## 8. 再接続と差分取得

1. クライアントは、ページごとに「確定した `seq`」を持つ。
2. 受け取った操作の `seq` が `last + 1` でなければ欠損とみなし、`GET /pages/{id}/ops?after_seq=N` で取る（上限 1,000 件）。
3. 1,000 件を超える、または 30 日の保持より古いときは、ページのスナップショットを取り直す。
4. どちらの場合も、未送信の待ち行列は捨てない。操作が ID で書かれているので、新しい状態にもそのまま当てられる。
5. 取得の優先順位と同時数の制限は Slack と同じ（表示中のページを先に。同時 3 本）。

## 9. 在席とカーソル

- すべて一時的なイベントで、DB と Relay を通らない（Slack の typing と同じ経路）。
- **ページの在席**（顔アイコン）：`page.presence { page_id }` を 30 秒ごとに送り、Gateway が Valkey の `ws:{w}:pp:{page_id}` に TTL 90 秒で置く。
- **カーソルと選択**：`cursor { page_id, anchor, head }`。位置は文字の ID（5.1 節）で表し、相手の画面で文字が増減してもずれない。送信は 100ms に 1 回まで、変化があるときだけ。受け手は 10 秒来なければ消す。
- 1 ページで表示するカーソルは 50 人まで。閲覧者が多いページ（7.2 節）では送らない。
- 在席は `can(read)` を通った購読者にだけ届く。

## 10. 権限の変更

| 場面 | 振る舞い |
| --- | --- |
| 接続中に読めなくなった | `page.revoked` を受けたら、画面を閉じ、端末の写しと待ち行列のうちそのページの分を消す（未送信の自分の入力は 10.1 節へ） |
| 接続中に編集できなくなった | 送ったトランザクションが 403 で返る。未送信の分を 10.1 節へ移し、読み取り専用に切り替える |
| オフラインの間に権限が変わった | 再接続して送るときに、今の権限で判定する。拒否された分は 10.1 節へ。heads の照合（11.3 節）で読めなくなったページを知り、写しを消す |
| ワークスペースから外された | 認証が通らない。待ち行列は端末に残るが送れない。ログアウトで消える |

### 10.1 送れなかった変更

- 拒否されたトランザクションから、本人が入力したテキストと作ったブロックだけを取り出し、端末の「送れなかった変更」に置く。他人の書いた周りの内容は含めない。
- 本人は、コピーするか、自分のプライベートなページとして新しく保存できる。30 日で消える。

## 11. オフライン

方針は ADR-0013。

### 11.1 対象

| 理由 | 範囲 |
| --- | --- |
| 明示（「オフラインで使う」をオン） | そのページのすべてのブロック。子ページは含めない |
| 最近開いた | 直近 30 日に開いた 50 ページ |
| お気に入り | すべて |
| データベースから継承 | 最初のビューの先頭 50 行（本家と同じ） |

- 理由ごとに行を持ち（本家の `offline_page` / `offline_action` と同じ形）、最後の理由が消えたときだけページを外す。
- 上限は、ワークスペース・端末ごとに 2,000 ページ、合計 1GB（ファイルの写しを含む）。超えたら「最近開いた」から古い順に外す。明示とお気に入りは自動で外さず、警告を出す。
- 埋め込み、ファイルのプレビューのうち外部のもの、検索（ローカルの題名の検索だけはする）、共有の設定、公開 API は、オフラインでは使えない。

### 11.2 保存

- Web とデスクトップの両方で、WASM の SQLite を OPFS に置く（[ADR-0008](../decisions/0008-sqlite-wasm-opfs-local-store.md)）。本家と同じく、書き込みは Web Locks で選んだ 1 つのタブの専用ワーカーだけが行う（[How we sped up Notion in the browser with WASM SQLite](https://www.notion.com/blog/how-we-sped-up-notion-in-the-browser-with-wasm-sqlite)）。WebSocket と同期のエンジンは SharedWorker に置く（Slack の [ADR-0024](../../../slack/docs/decisions/0024-client-data-layer-and-offline.md)）。デスクトップ（Electron）も S1 は同じ実装を使い、ネイティブの SQLite は S2 の候補として計測で決める（[editor.md](editor.md) の 11 節、[ADR-0032](../decisions/0032-desktop-uses-wasm-sqlite-in-s1.md)）。
- 端末の表：`records`（ブロックなどのレコード、`version`、ページの確定した `seq`）、`text_states`（ブロックのテキストの CRDT の状態）、`transaction_queue`（未確定。FIFO）、`offline_pages`、`offline_actions`（理由）、`failed_changes`（10.1 節）、`meta`。名前と形の正は [editor.md](editor.md) の 10 節。データベースはアカウントごとに分け、キーに `workspace_id` を含める。
- `navigator.storage.persist()` を求める。Safari はホーム画面に追加していないサイトのデータを 7 日で消しうる（Slack の ADR-0024 の注記）。未送信があるのにデータが消えうる環境では、画面に警告を出す。
- OPFS が使えないブラウザでは、オフラインを無効にし、その旨を出す。

### 11.3 鮮度

- オンラインの間、10 分ごとと再接続時に、`POST /sync/heads` へ持っているページの `(page_id, seq)` を 500 件ずつ送る。サーバーは、変わったページ、削除されたページ、読めなくなったページを返す（本家の `lastDownloadedTimestamp` と `lastUpdatedTime` の比較に相当）。
- 変わったページは、差分取得か、スナップショットの取り直しで追いつく。

### 11.4 長時間のオフラインの統合

- 待ち行列は、期間の上限を設けない。上限は量で決め、1 ワークスペースあたり 5 万操作・50MB を超えたら、それ以上のオフラインの編集を止めて警告する。
- 再接続したら、待ち行列を FIFO で送る。1 回の送信は 500 操作まで。途中で失敗しても `tx_counter` で続きから再開できる。
- テキストはすべて合わさる。構造とプロパティは ADR-0011 の規則で決まる。
- セッションが切れていたら、ログインの後に送る。別のアカウントでログインしても、他のアカウントの待ち行列は送らない。

### 11.5 衝突の見せ方

- 再接続の後、`sync_conflicts` のうち自分の分があれば、ページの上部に「オフラインの変更のうち n 件が他の人の変更と重なりました」を出す。一覧から、前の値に戻す・取り消された操作をやり直すことができる（新しいトランザクションとして送る）。
- 上書きされた側（オンラインで先に書いた人）にも、ページの履歴で分かるようにする。通知は出さない。
- 同期の状態（未送信の件数、最後に同期した時刻）を、ページとサイドバーに出す。

## 12. 履歴との関係

- 履歴の各版は、確定の時刻（`committed_at`）で並べる。オフラインの編集は `client_created_at` も持ち、履歴に「オフラインで編集」と出す。
- 版の復元は、過去に戻すのではなく、今の状態から復元先への差分を新しいトランザクションとして当てる。復元の後に届いたオフラインのテキストの挿入は、アンカーの文字の位置（墓標を含む）に入る。復元で消えた文字の隣に入ることがあり、衝突の記録として出す。
- 操作のログは 30 日で畳み、履歴はスナップショットで持つ（[block-model.md](block-model.md)）。統合に古いログは要らない（1 節の「操作は意図で書く」）。

## 13. 規模

| 段階 | 同時接続 | 書き込み（ピークの目安） | 構成 |
| --- | --- | --- | --- |
| S1 | 1 万 | 1,000 tx/秒（接続の 20% が編集中、2 秒に 1 回） | Gateway 3 タスク（1 タスク 1 万接続、60% と AZ の障害の余裕）、Valkey 1 シャード、Relay 2 タスク（物理クラスタ 1 つ。480 の論理シャードのリースを分担。7.3 節） |
| S2 | 100 万 | 10 万 tx/秒 | Gateway は Slack の S2 と同じく Valkey の sharded pub/sub。Relay の群れを物理クラスタごとに置き、論理シャードのリースで分担する。閲覧者が多いページの経路を有効にする |
| S3 | 1,000 万 | 100 万 tx/秒 | セルごとに Gateway・Relay・Valkey を持つ（1 つのワークスペースは 1 つのセル） |

- 1 ページへの同時の書き込みは、ページの行のロックで直列になる。目標は 1 ページあたり 50 tx/秒。超えるページ（大人数の議事録）は、打鍵のまとめを 250ms に広げる。数値は負荷試験で確かめる（[capacity.md](capacity.md)）。
- CRDT の状態は、ブロックごとに小さい。墓標は run でまとめるので、ブロックの大きさは「消した回数」ではなく「編集の run の数」で増える。1 ブロックの状態が 1MB を超えたら、警告の指標にする。

## 14. 障害と振る舞い

Slack の [realtime.md](../../../slack/docs/architecture/realtime.md) の 14 節に加えて、次のとおり。

| 障害 | 起きること | 回復 |
| --- | --- | --- |
| 送信の途中で切れた | 適用されたか分からない | 同じ `device_id`・`tx_counter` で再送する。適用済みなら成功が返る |
| 端末の保存が消えた（Safari の追い出しなど） | 未送信が失われる | 警告で予防する。写しはスナップショットで取り直す |
| CRDT の状態が壊れた・展開と食い違う | 表示と正本がずれる | サーバーで CRDT の状態から展開し直すジョブ。クライアントはスナップショットを取り直す |
| 権限のキャッシュの無効化の遅れ | 読めなくなった人に操作が届く | `acl.changed` を操作と同じ経路で流し、Gateway が送る直前にも確かめる |
| リージョンの切り替え（[ADR-0029](../decisions/0029-disaster-recovery.md)）で、確定済みのトランザクションが失われた | 確定を受け取った後の編集が、昇格した DB にない | MVP では、クライアントは確定済みのトランザクションを保持しない。失った範囲（複製の遅延ぶん、NFR-009 の RPO 15 分以内）は戻らない。`device_cursors` が昇格した DB の時点に戻るので、確定済みを一定時間保持して再送すれば回復できる。入れるかは E8 の DR 訓練の結果で決める |

## 15. 監視する指標

- 入力 → 他者の画面の遅延（7.1 節の区間ごと）
- 欠損の検知率、スナップショットの取り直しの割合
- 衝突の記録の件数（種類ごと）、送れなかった変更の件数
- 再接続時の待ち行列の大きさと、送り終えるまでの時間
- 1 ページあたりの tx/秒の上位、ページの行のロック待ち
- CRDT の状態の大きさの分布、展開の食い違いの件数
