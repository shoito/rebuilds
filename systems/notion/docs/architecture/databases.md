# Databases: Notion

データベース、データソース、プロパティ、ビュー、フィルタ・並べ替え・グループ化、リレーション、ロールアップ、数式、問い合わせ。

本家の振る舞いに寄せる。本家の文書で確かめられなかった点は「未検証」と書く。主な決定は次の 4 つ。

- 問い合わせは、ワークスペースのシャードの中に置いた型付きの索引の表で行い、変更と同じ DB のトランザクションで更新する（[ADR-0014](../decisions/0014-database-query-index.md)）。
- 数式は、クライアントとサーバーで同じ評価器を使い、サーバーの値を正とする。同じ行の中の依存は書き込みと同時に、行をまたぐ依存は非同期に計算し直す（[ADR-0015](../decisions/0015-formula-evaluation-model.md)）。
- リレーションは、1 本の辺を正本にして両側の値を導く。両側は同じトランザクションで変わる（[ADR-0016](../decisions/0016-relation-edges-as-single-source.md)）。
- ロールアップと、リレーションをたどる数式は、見る人が読める行だけで計算する（[ADR-0017](../decisions/0017-rollups-over-readable-rows-only.md)）。

## 2. データモデル

```
ページ（ブロック）
 └─ database ブロック（インライン、または全画面のページ）
     ├─ data_source A（スキーマ）── 行（page ブロック）… ── 行の本文（ブロック）
     ├─ data_source B（スキーマ）── 行 …
     └─ view（表・ボード…）→ data_source を 1 つ指す
linked_database ブロック（別のページ）── view → 他のデータベースの data_source を指す
```

| レコード | 持つもの | 本家の対応 |
| --- | --- | --- |
| `database` ブロック | タイトル、アイコン、カバー、データソースの ID の並び、ビューの ID の並び、インラインかどうか | database |
| `data_source` | `workspace_id`、親（database ブロック）、名前、スキーマ（`properties`：プロパティ ID → 名前・種類・設定）、削除したプロパティ、行の数、行に固有の ACL を持つ行の数。ブロックではなく別の表（`data_source`）に持つ | data source（内部名 collection。未検証） |
| 行（`page` ブロック） | `parent_type = data_source`、`parent_id` がデータソースの ID。`properties` にプロパティ ID をキーとして値を持つ。本文は普通のブロックの木 | page |
| `view` | 親の database（またはリンクドビューのブロック）、対象の `data_source_id`、種類、設定（4 節） | view |
| `relation_edge` | リレーションの辺（6 節） | （未検証） |
| 索引の表 | 問い合わせ用の写し（3 節） | （未検証） |

- `data_source` と `view` は、ブロックと同じ操作・トランザクション・配信の仕組みに乗る（[ADR-0005](../decisions/0005-transactions-as-unit-of-change.md)）。レコードの種類が違うだけで、`seq`・履歴・権限の判定は共通。
- 権限の判定は、行 → `data_source` → `database` ブロック → 親のページ、と祖先をたどる（[ADR-0004](../decisions/0004-inherited-page-permissions.md)）。
- **行は `data_source` の `content` に並べない。** 行は数十万になり、並びは各ビューの並べ替えで決まるため。行の集合は索引の表で列挙する。ブロックの木の不変条件（[ADR-0002](../decisions/0002-everything-is-a-block.md)）は、行については「親の `data_source` がちょうど 1 つ」と読み替える（[ADR-0014](../decisions/0014-database-query-index.md)）。
- 手動の並び（ボードでのドラッグなど）は、ビューごとの並びのキー（分数の索引）として索引の表に持つ。

### 2.1 プロパティの種類

本家の 24 種（[Property object](https://developers.notion.com/reference/property-object)）。MVP は intent の範囲に、本家で基本となるものを加える。

| 種類 | MVP | 値の持ち方（`properties` の中） | 索引の列 |
| --- | --- | --- | --- |
| title、rich_text | ○ | リッチテキストの配列 | 平文（照合順序つき）、trigram |
| number | ○ | 数値。表示の書式はスキーマ | 数値 |
| select、status | ○ | 選択肢の ID。選択肢と、status のグループ（To-do・In progress・Complete）はスキーマ | 参照 ID |
| multi_select | ○ | 選択肢の ID の配列 | 参照 ID（複数行） |
| date | ○ | 開始・終了・時刻の有無・タイムゾーン | 時刻（開始・終了） |
| people | ○ | 利用者の ID の配列 | 参照 ID（複数行） |
| checkbox、url、email、phone_number | ○ | スカラー | 真偽・平文 |
| files | ○ | ファイルの参照の配列 | なし（空かどうかだけ） |
| relation | ○ | 持たない。`relation_edge` が正本（6 節） | 参照 ID（複数行） |
| rollup、formula | ○ | 持たない。計算の結果を索引に書く（7・8 節） | 結果の型の列 |
| created_time、created_by、last_edited_time、last_edited_by | ○ | ブロックの属性から導く | 時刻・参照 ID |
| unique_id | ○ | 接頭辞とデータソースごとの連番。採番はデータソースの行ロックで行う | 数値 |
| button、verification、place | × | MVP の後（ボタンとオートメーションは intent の対象外） | |

- プロパティの ID は、データソースの中で一意の短い文字列にし、名前の変更で変わらない。`title` の ID は固定の `title`（本家と同じ）。
- 種類の変更（例：text → select）は、値を変換する非同期のジョブで行い、終わるまでそのプロパティでのフィルタ・並べ替えは古い索引で答える。本家の変換規則の細部は未検証。
- プロパティの削除は論理削除にし、戻せるようにする（本家は削除したプロパティを 1.5MB まで保持する。[Optimize database performance](https://www.notion.com/help/optimize-database-load-times-and-performance)）。

## 3. 問い合わせ

### 3.1 索引の表（ADR-0014）

ワークスペースのシャードの中に、次の 2 つの表を持つ。変更のトランザクションと同じ DB のトランザクションで更新する。

| 表 | キー | 列 |
| --- | --- | --- |
| `dbx_row` | (`workspace_id`, `data_source_id`, `row_id`) | 作成・更新の時刻と人、ゴミ箱かどうか、行に固有の ACL を持つか、`version` |
| `dbx_value` | (`workspace_id`, `data_source_id`, `property_id`, `row_id`, `ord`) | `v_text`、`v_num`、`v_ts`、`v_ts_end`、`v_bool`、`v_ref`。型ごとに 1 列だけ使う。複数の値（multi_select・people・relation）は `ord` で複数行 |

- 索引は、`(workspace_id, data_source_id, property_id, v_num, row_id)` のように型ごとに持つ。`v_text` には照合順序つきの B-tree と、「含む」のための `pg_trgm` の GIN を置く（title と rich_text だけ）。
- 全表が `workspace_id` と RLS を持つ（[ADR-0003](../decisions/0003-workspace-sharding.md)）。
- 正本は行の `properties` と `relation_edge`。索引は写しで、整合の検査のジョブが定期的に突き合わせ、ずれたら作り直す。

### 3.2 実行

```
ビューの設定 ─▶ 計画 ─▶ SQL（押し下げられる条件） ─▶ 候補の行 ─▶ 評価器（残りの条件・権限・揮発する数式） ─▶ 並べ替え・グループ ─▶ ページ
```

- **押し下げ**：単純なプロパティ（数値・日付・選択・人・チェック・テキストの前方一致と完全一致・リレーションの有無）と、実体化した数式・ロールアップ（7・8 節）の条件は SQL にする。AND・OR の木（本家は 3 段まで）は、押し下げられる部分木だけを SQL にし、残りは評価器で判定する。
- **評価器**：フィルタ・並べ替えの意味を定める参照実装を 1 つ TypeScript で書き、サーバーの残りの判定、クライアントのオフラインの問い合わせ（ローカルの SQLite の写しに対して）、テストのオラクルの 3 つで共有する。
- **並べ替え**：先頭の並べ替えが索引の列 1 つで、条件がすべて押し下げられるときは、索引の順に読み、キーセット（並べ替えの値、`row_id`）でページ送りする。そうでないときは、候補の行の ID を並べ替えた結果を作り、`query_id` で 15 分キャッシュしてページ送りする（本家の API と同じ形）。キャッシュは、データソースの `version` が進んでも捨てず、画面は変更の配信で差分を当てる。
- **グループ化**：グループの一覧と件数は `GROUP BY` で求め、各グループの行はグループごとに別のページ送りで読む（ボードの列ごとの読み込み）。サブグループは 1 段まで（本家と同じ）。
- **カレンダー・タイムライン**：表示している期間で `v_ts`・`v_ts_end` の範囲を問い合わせる。
- **チャート**：集計（件数・合計・平均など）を SQL で求める。グループの数に上限を置く（200、本設計の値）。
- **読み込む行数**：ビューごとの最初の読み込みを 50 行にし、スクロールで続きを読む。本家のビューの「読み込み上限」の選択肢（10・25・50・100）は未検証。
- **行の権限**：データソースの「行に固有の ACL を持つ行の数」が 0 なら、データベースを読めることで全行を読める。1 以上なら、候補の行のうち固有の ACL を持つ行だけを判定の関数に通す（ADR-0004、10 節）。グループの件数とチャートの集計も、読める行だけで数える。

### 3.3 リンクドビュー

- `linked_database` ブロックは、他の場所の `data_source` を指すビューを持つ。行とスキーマは元のもので、ビューの設定だけが独立する。
- 行が見えるかは、元のデータソースの権限で決まる（本家と同じ）。リンクドビューを置いたページを読めても、元を読めなければ、タイトルを含めて何も返さない。
- 同じワークスペースの中のデータソースだけを指せる（ADR-0003）。

## 4. ビュー

| 種類 | 必須の設定 | MVP |
| --- | --- | --- |
| 表 | 列の表示・順・幅、固定する列、折り返し | ○ |
| ボード | グループ化のプロパティ（select・status・people など）、カードのプレビュー | ○ |
| リスト | 表示するプロパティ | ○ |
| カレンダー | 日付のプロパティ | ○ |
| ギャラリー | カードのプレビュー（本文・カバー・files）、カードの大きさ | ○ |
| タイムライン | 開始・終了の日付のプロパティ、目盛り | ○ |
| チャート | 縦棒・横棒・折れ線・ドーナツ、軸のプロパティと集計 | MVP の後 |
| フォーム・マップ・ダッシュボード | | MVP の後（intent の対象外、または本家でも新しい） |

- すべてのビューが、フィルタ（AND・OR、3 段まで）、並べ替え（複数、先のものが優先）、グループ化（とサブグループ 1 段）、行の開き方（サイドピーク・センターピーク・全画面）を持つ。
- フィルタ・並べ替えは「全員」と「自分だけ」を選べる（本家と同じ）。「自分だけ」は利用者ごとの上書きとして別の表（`view_member_overrides`）に持ち、他の人に配信しない。
- ビューの設定の変更は、ビューのレコードへの操作として同期する。

## 5. 書き込みの流れ

1. クライアントが、行のプロパティの変更をトランザクションで送る（ADR-0005）。
2. API は、権限・スキーマ（型・選択肢の存在・上限）を検証し、ブロックの表と索引の表（`dbx_row`・`dbx_value`）、同じ行の中の数式の結果を、1 つの DB のトランザクションで書く。
3. outbox から、行を開いている人と、そのデータソースのビューを購読している人へ配信する。
4. 行をまたぐ依存（ロールアップ、リレーションをたどる数式）は、Worker が計算し直して索引に書く（7 節）。

- 読み手は、自分の書き込みの直後のビューで、その変更を含む結果を得る（索引が同期のため）。
- ビューの購読者には、変わった行の ID と値を送り、クライアントがビューの条件で当てはめ直す。当てはめ直しが評価器でできない場合（押し下げの前提が崩れたときなど）は、問い合わせをやり直す。

## 6. リレーション（ADR-0016）

- 本家は、片方向と両方向（`single_property`・`dual_property`）、自分自身へのリレーション、関連できるページを「1 ページ」か「制限なし」に絞る設定を持つ（[Relations & rollups](https://www.notion.com/help/relations-and-rollups)、[Property object](https://developers.notion.com/reference/property-object)）。
- **正本は辺の表。** `relation_edge`（`workspace_id`、`from_property_id`、`from_row_id`、`to_row_id`、`from_pos`、`to_pos`）。両方向のリレーションは、1 本の辺を両側のプロパティから見る。A 側の値は `from_row_id = A` の辺、B 側の値は `to_row_id = B` の辺で、同じ辺から導くので、片側だけが変わる状態が起きない。
- 辺の追加・削除は 1 つの操作で、両側の行の購読者に配信し、両側の行の `last_edited_time` を進める（本家の細部は未検証）。
- **ワークスペースをまたぐリレーションは作れない。** 対象のデータソースは同じワークスペースに限る（ADR-0003）。本家も同じと見られるが、文書で明示されていない（未検証）。
- 「1 ページ」の制限は、辺の追加のときに同じトランザクションで検査する。
- 関連する行がゴミ箱に入っても辺は残し、表示と計算からは除く。行を戻せば元に戻る。行を完全に削除したら、辺も消す。
- 両方向のうち片側のプロパティを消したら、残った側は片方向になる（辺は残す）。本家の振る舞いは未検証。
- 上限：1 つの行の 1 つのリレーションのプロパティで、辺は 10,000 本まで。本家は、同じページへの参照が 10,000 を超えると両方向の同期をやめる（[Optimize database performance](https://www.notion.com/help/optimize-database-load-times-and-performance)）。本設計は同期をやめる代わりに、追加を拒否する（差異）。
- API の 1 リクエストで設定できる関連ページは 100 まで、ページのオブジェクトでは参照を 25 件で切り、続きはプロパティの取得で読む（本家と同じ。[Request limits](https://developers.notion.com/reference/request-limits)、[Retrieve a page property](https://developers.notion.com/reference/retrieve-a-page-property)）。

## 7. ロールアップ

- 関数は本家の一覧に合わせる（count、count_values、empty、not_empty、unique、show_unique、percent_*、sum、average、median、min、max、range、earliest_date、latest_date、date_range、checked、unchecked、percent_checked、percent_unchecked、count_per_group、percent_per_group、show_original。[Property object](https://developers.notion.com/reference/property-object)）。
- ロールアップのロールアップは作れない（本家と同じ。[Relations & rollups](https://www.notion.com/help/relations-and-rollups)）。数式を通した参照は、8 節の深さの上限で抑える。
- 計算と実体化：
  - 関連する行の値・辺・関連する行のゴミ箱の状態が変わったら、outbox のイベントから Worker が影響する行を求め、ロールアップを計算し直して `dbx_value` に書く。
  - 影響する行は辺の表の逆引きで求める。1 つの変更で計算し直す行が多いとき（10,000 行を超えるなど）は、バッチに分けて順に処理する。
  - 計算し直すまでの間、ビューには古い値を出す。目標は、変更からロールアップの反映まで p99 5 秒（S1）。
  - クライアントは、関連する行を読み込み済みなら、同じ評価器で楽観的に計算して先に出す。
- 権限との関係は 10 節。

## 8. 数式（ADR-0015）

### 8.1 言語

本家の Formulas 2.0 に合わせる（[Formula syntax](https://www.notion.com/help/formula-syntax)）。

- 型：テキスト、数値、真偽、日付、人、ページ、リスト。
- `prop("名前")`、`let`・`lets`、リストの関数（`map`・`filter`・`find`・`findIndex`・`some`・`every` など）と `current`。
- リレーションをたどる参照：`prop("Tasks").map(current.prop("Status"))`。
- 深さ：数式が他の数式・ロールアップを参照するたびに 1 層とし、15 層まで（本家と同じ。[Optimize database performance](https://www.notion.com/help/optimize-database-load-times-and-performance)）。
- 関数の一覧と各関数の細かな意味（日付の計算の丸め、空の値の扱い）は、本家の関数の文書に合わせて仕様で決める。コメントや複数行の書き方の可否は未検証。

### 8.2 解析と実行

- 自前の構文解析器で AST にし、AST を解釈する。`eval` や JavaScript への変換はしない。
- スキーマを保存するときに、型の検査と、依存のグラフ（同じ行のプロパティ、リレーションを通した他のデータソースのプロパティ）の循環と深さを検査し、違反は保存を拒否する。
- 実行は純粋な関数だけ。外部への入出力はなく、値の読み取りは評価器に渡した文脈（権限の判定を通した行の読み取り）からだけ行う。
- 1 回の評価に、手数（10 万ステップ）、リストの長さ（1 万要素）、テキストの長さ（10 万文字）、時間（50 ms）の上限を置き、超えたら数式のエラーの値にする（値は本設計の値）。

### 8.3 評価の場所と実体化

| 数式の種類 | 評価 | 結果の置き場 |
| --- | --- | --- |
| 同じ行のプロパティだけを参照 | 書き込みのトランザクションの中で、サーバーが評価 | `dbx_value`（押し下げできる） |
| リレーションをたどる、ロールアップを参照 | Worker が非同期に評価（7 節と同じ仕組み） | `dbx_value` |
| `now()` など時刻に依存（揮発） | 実体化しない。問い合わせのときに評価器で評価 | なし |

- クライアントは、同じ評価器で楽観的に表示し、サーバーの値が届いたら置き換える。
- 数式の定義を変えたら、データソースの全行を計算し直すジョブを起こす。終わるまで、そのプロパティでのフィルタ・並べ替えは古い値で答え、画面に「計算中」と出す。
- 揮発する数式でフィルタ・並べ替えるビューは、押し下げできないので、候補の行が多いと遅い。性能の目標（11 節）の対象外とし、ビューの設定の画面で知らせる。

## 9. 行の本文とテンプレート

- 行の本文は、普通のページのブロックの木。表示と共同編集は [block-model.md](block-model.md)・[collaboration.md](collaboration.md) に従う。
- データベースのテンプレート（新しい行の既定のプロパティと本文）は、`data_source` に紐づくテンプレートのページとして持つ。MVP には含めない（intent.md の MVP の範囲にないため。[roadmap.md](../roadmap.md) の「後回しにしたもの」）。

## 10. 権限との関係（ADR-0017）

- 行は、`data_source` と `database` ブロックを通して、データベースを置いたページの権限を継承する（ADR-0004）。行のページに固有の共有の設定を置くこともできる（本家と同じ）。
- データベースの「ページ単位の権限」の規則（作った人だけが編集できる、など。本家の詳細は [permissions-and-sharing.md](permissions-and-sharing.md)）がある場合は、行に固有の ACL がある場合と同じ扱いにする。
- **リレーションの値は、見る人が読める行だけを返す。** 読めない行は、タイトルも件数も「アクセスなし」の目印も出さない。本家は「No access」の表示を出す場合があるが（未検証）、intent の「リレーションのどこからも見えない」を優先する（差異）。
- **ロールアップと、リレーションをたどる数式の値は、見る人が読める関連行だけで計算する。**
  - 早い経路：見る人が対象のデータソースのすべての行を読める（データソースを読め、行に固有の ACL を持つ行がない）とき、実体化した値（全行で計算した値）をそのまま使う。
  - 遅い経路：それ以外のとき、読める関連行だけで評価器が計算し直す。このプロパティでのフィルタ・並べ替えは押し下げず、候補の行ごとに計算する。
  - 実体化した値を、遅い経路の人に返す経路を作らない。API・検索・通知・エクスポートも同じ関数を通す。
- 本家が、読めない関連行をロールアップの計算に含めるかは未検証。
- データソースを読めない人が、リンクドビュー・リレーション・メンションのどこから来ても、スキーマ（プロパティの名前・選択肢）も返さない。

## 12. 性能の目標

| 項目 | S1 の目標 |
| --- | --- |
| ビューの表示（1 万行、押し下げられる条件） | p95 1 秒以内（NFR-003） |
| ビューの表示（10 万〜25 万行、押し下げられる条件と索引の列での並べ替え） | p95 2 秒以内 |
| ビューの表示（押し下げられない条件、または遅い経路のロールアップ） | 目標の対象外。p95 を計測し、5 秒を超えるビューを数える |
| 行のプロパティの変更が、同じビューを開いた他の人に届く | p99 500ms 以内（NFR-001） |
| ロールアップ・行をまたぐ数式の反映 | p99 5 秒以内 |
| 数式の定義の変更の後の全行の計算し直し（25 万行） | 5 分以内 |

- 見積もりの前提：1 万行 × 表示するプロパティ 20 で、索引の表は 20 万行。押し下げた条件で候補を 1,000 行以下に絞れれば、1 秒に十分収まる。25 万行 × 20 プロパティで 500 万行の索引になり、索引の列の順に読む経路でだけ 2 秒を守れる。
- 索引の表は、ブロックの表の数倍の行数になる。必要量は [capacity.md](capacity.md) で見積もる。

## 13. 規模の段階

| 段階 | 構成 |
| --- | --- |
| S1 | 索引の表をシャードの中に置き、同期で更新する。行をまたぐ計算し直しは Worker |
| S2 | 論理シャードの物理のクラスタへの分散に、索引の表も一緒に乗る。読み取りの複製で問い合わせを受け、自分の書き込みの直後だけ主に送る。行をまたぐ計算し直しのキューをシャードごとに分ける |
| S3 | 25 万行に近いデータソースと、重い集計（チャート）のために、データソースの単位で列指向の写しをメモリに持つ問い合わせのノードを置くかを検討する。索引の表は正本の写しのまま残し、ノードは再構築できる写しにする。分析はデータレイクに回す |

## 14. リスクと未解決事項

- 行を `data_source` の `content` に並べない扱いは、ADR-0002 の不変条件の読み替え。[block-model.md](block-model.md) の 2・5 節（`parent_type = data_source`、T1・T3）に反映した。性質ベーステストで、行がどの `content` にも現れず、親の `data_source` がちょうど 1 つであることを確かめる（[quality.md](../quality.md)）。
- 索引の表の書き込みの増幅（1 行の変更で、プロパティの数だけ `dbx_value` を書く可能性）。変わったプロパティだけを書くことで抑えるが、インポートの大量の書き込みでの負荷は [capacity.md](capacity.md) で見る。
- 遅い経路のロールアップ（行に固有の ACL が多いデータソース）で、ビューが遅くなる。
- 揮発する数式でのフィルタ・並べ替えの性能。
- 複数のデータソースを持つデータベースの、上限の数え方（本家が未検証）。
