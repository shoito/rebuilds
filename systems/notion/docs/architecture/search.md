# Search: Notion

ワークスペースの中の全文検索、クイック検索、権限の適用。検索の基盤は S1 から OpenSearch にし、文書はページ単位で持ち、権限は「文書に持たせた権限キー」と「読み直しでの判定関数」の二重で効かせる（[ADR-0023](../decisions/0023-search-engine-and-permission-filtering.md)）。

## 1. 範囲

本家の検索に合わせる（[Search](https://www.notion.com/help/search)、2026-09-26 に確認）。

| 対象 | 扱い |
| --- | --- |
| ページのタイトル | 検索する。重みを本文より大きくする |
| ページの本文（テキストを持つブロック） | 検索する。見出し・リスト・ToDo・トグル・コード・引用・コールアウト・表のセル |
| データベースの行 | ページなので、タイトルと本文を検索する |
| プロパティの値（選択のタグなど） | 検索しない（本家と同じ）。データベースの中の絞り込みで扱う（[databases.md](databases.md)） |
| メンション（人・ページ）、コメント、ディスカッション | 検索しない（本家と同じ） |
| 添付ファイルの中身、埋め込み先の中身 | 検索しない。ファイル名は本文として扱う |
| ゴミ箱のページ | 既定では出さない。「ゴミ箱」の絞り込みで出す |

- 検索できるのは、検索した人がその時点で読めるページだけ（ADR-0004）。ゲストは、共有されたページとその子孫だけ。
- 同期ブロックの本文は、元のブロックがあるページの文書にだけ入れる。参照しているページでは検索にかからない。元のページの権限で判定するため、参照先の権限で本文が見えることを防ぐ（[block-model.md](block-model.md)）。
- 公開 API の検索（[api-and-integrations.md](api-and-integrations.md)）は、本家と同じくタイトルだけを対象にする。同じ索引の `title` フィールドを使う。

## 2. 本家との対応

| 観点 | 本家 | 本システム |
| --- | --- | --- |
| 検索エンジン | Elasticsearch（[Rebuilding Notion's lexical search reindexer](https://www.notion.com/blog/rebuilding-notions-lexical-search-reindexer)、2026-08） | Amazon OpenSearch Service |
| 文書の単位 | ブロック単位（同上） | **ページ単位**（3 節） |
| 権限 | 文書の生成時に、文書ごとの権限を解決して入れる（同上。詳細は非公開） | 権限キーを文書に入れ、読み直しで判定関数を通す（5 節） |
| 版の管理 | 外部バージョン（`version_type: external`）で新しい書き込みを優先（同上） | 同じ |
| 並べ替え | 最もよく一致（最近の編集とタイトルを優先）、最終編集、作成（[Search](https://www.notion.com/help/search)） | 同じ |
| 絞り込み | タイトルだけ、作成者、チームスペース、ページの中、日付 | 同じ |

## 3. 文書（ページ単位）

1 ページを 1 文書にする。ブロック単位にしないのは、権限の単位がページで、共有の変更や移動のたびに更新する文書の数を、ページの数に抑えるため（ブロックはページの数十〜数百倍）。一致したブロックへの移動（ハイライトとスクロール）は、読み直しの後に API で本文から探す（6.3 節）。

| フィールド | 型 | 中身 |
| --- | --- | --- |
| `workspace_id`、`page_id` | keyword | ID |
| `teamspace_id` | keyword | ページが属するチームスペース（なければ空） |
| `ancestor_ids` | keyword（配列） | 祖先のページの ID（「ページの中」の絞り込み） |
| `acl_source_id` | keyword | 最も近い「ACL を持つ祖先」のページの ID（ADR-0004）。自身が ACL を持てば自身 |
| `access_keys` | keyword（配列） | このページを読める主体のキー（5.1 節） |
| `created_by`、`created_at`、`last_edited_at` | keyword / date | 絞り込みと並べ替え |
| `in_trash` | boolean | ゴミ箱 |
| `is_database_row` | boolean | データベースの行か |
| `title` | text | タイトル（`normalizeForSearch` 済み） |
| `body` | text | 本文のブロックのテキストを、木の順に改行で連結したもの。先頭から 1 MB で切る |
| `index_version` | long | ページの `seq`（ADR-0005）。外部バージョンとして使う |
| `acl_version` | long | 権限キーを計算した時点の、ワークスペースの権限の版（5.3 節） |

- 1 MB を超えるページの残りは検索にかからない（既知の制限）。超えたページの数を指標にし、多ければ上限を見直す。
- 正規化（NFKC・小文字化）は、アナライザーではなくアプリの `normalizeForSearch` で行い、索引とクエリの両方にかける（Slack の search.md と同じ）。

## 4. 日本語の解析

Slack の S2 の設計（Slack の search.md の 5.2 節）をそのまま使う。

| フィールド | 解析 | 役割 |
| --- | --- | --- |
| `title.gram`、`body.gram` | 1〜2 文字の N-gram | **一致の判定**。語ごとに `match_phrase` で連続を要求する。未知語や語の途中でも取りこぼさない |
| `title`、`body` | Sudachi（形態素解析、表記の揺れの正規化） | **関連度のスコア**。`should` にだけ使う |
| `title.prefix` | edge N-gram（1〜20 文字） | クイック検索の前方一致（7 節） |

- Amazon OpenSearch Service は Sudachi を任意のプラグインとして提供する（[プラグインの一覧](https://docs.aws.amazon.com/opensearch-service/latest/developerguide/supported-plugins.html)）。辞書の差し替えは blue/green のデプロイで反映される。
- 英語などの空白で区切る言語も、同じ N-gram の判定で扱う。語幹の処理（英語の複数形など）は S1 では行わない。
- ひらがなとカタカナは同一視しない（Slack と同じ判断）。
- 1 文字の N-gram による索引の増え方は、代表的なワークスペースで測る（未検証）。

## 5. 権限の適用

### 5.1 権限キー

文書には「このページを読める主体」を、キーの配列として入れる。検索のたびに、検索した人の「主体のキー」を DB から求め、`terms` で照合する。

| キー | 意味 | 検索した人がこのキーを持つ条件 |
| --- | --- | --- |
| `ws:{workspace_id}` | ワークスペースの全メンバーが読める | ワークスペースのメンバー（ゲストでない） |
| `team:{teamspace_id}` | チームスペースのメンバーが読める | そのチームスペースのメンバー |
| `group:{group_id}` | グループに共有されている | そのグループのメンバー |
| `user:{member_id}` | 個人に共有されている（ゲストを含む） | 本人 |
| `bot:{integration_id}` | 連携に共有されている（[ADR-0024](../decisions/0024-integration-access-model.md)） | その連携のトークン |

- ページの ACL を、判定関数と同じ規則（[permissions-and-sharing.md](permissions-and-sharing.md)）でキーの集合に変換する関数 `accessKeysFor(page)` を、判定関数と同じパッケージに置く。
- Web への公開・リンクの共有は、キーにしない。ワークスペースの外の閲覧者は検索を使えない。
- 「アクセス権なし」の明示的な設定（継承を止める）は、キーを持たないことで表す。キーは「読める」ものだけを列挙し、拒否を表さない。
- 主体のキーは、リクエストの始めに読んだ `acl_version` をキーにしたキャッシュ（[permissions-and-sharing.md](permissions-and-sharing.md) の 5.1 節）か DB から求める。グループ・チームスペース・ワークスペースからの脱退は `acl_version` を上げるので、次の検索からすぐに効く。

### 5.2 二重の守り

| 層 | 何をするか | 何を防ぐか |
| --- | --- | --- |
| 1. クエリの条件 | `workspace_id` と `access_keys` の `terms` を必ず `filter` に入れる | 件数・ページング・並べ替えから、読めないページの存在が漏れること |
| 2. 読み直し | 結果の `page_id` を、判定関数 `can(actor, read, page)` と RLS の下で読み直す。タイトル・抜粋・パンくずは読み直した値から作る | 文書の権限キーが古い間（5.3 節）の漏洩。索引の値を画面に出さないので、古い文書のタイトルも出ない |

- 検索の応答に、索引の `title`・`body` の値を使わない。索引は `page_id` の一覧を得るためだけに使う。
- 読み直しで落ちた件数を `search_hydration_permission_drop` として計測する。権限の変更の直後（5.3 節の反映の間）以外で出たら、バグとして扱う。
- 1 ページの件数が要求より少なくなることは許容する（Slack と同じ）。合計の件数は返さない。

### 5.3 権限の変更と移動の反映

権限キーは、ページの ACL（ADR-0004）から決まる。変わる契機と、更新する文書は次のとおり。

| 契機 | 更新する文書 | 方法 |
| --- | --- | --- |
| ページの ACL の変更（共有の追加・削除、全般のアクセスの変更） | `acl_source_id` がそのページの文書すべて | `update_by_query`（`term: acl_source_id`）で `access_keys` を書き換える |
| ページの移動（親の変更） | 移動したページの部分木のうち、`acl_source_id` が変わる文書と、すべての `ancestor_ids`・`teamspace_id` | 部分木のページを DB から列挙し、一括で再索引する |
| ACL を持つページの継承の開始・停止 | そのページの部分木で、`acl_source_id` が変わる文書 | 同上 |
| チームスペースの設定の変更（公開・非公開） | そのチームスペースの文書すべて | `update_by_query`（`term: teamspace_id`） |
| グループ・チームスペースのメンバーの増減 | なし | 主体のキーの側で効く（5.1 節） |

- ACL の変更のトランザクションで、outbox に `acl.changed { page_id, acl_version }` を積む。専用のキュー `search-acl` に流し、本文の更新（`search-index`）に待たされないようにする。
- 目標：権限の変更から、検索のクエリの条件に反映されるまで p99 10 秒。それまでの間は 5.2 節の読み直しで守る。取り消しは即時に効き、付与は最大 10 秒遅れる。
- 部分木が大きい移動（1 万ページ超）は、分けて処理する。処理中も読み直しで守られる。
- 文書の `acl_version` と、ワークスペースの現在の権限の版を定期的に突き合わせ、古い文書を再計算する（取りこぼしの回収。1 時間ごと）。

### 5.4 クエリの組み立て

クエリは 1 つの関数 `buildSearchRequest` だけで作る。OpenSearch のクライアントを他の場所から使うことは lint で禁止する（Slack と同じ）。

```json
{
  "routing": "<workspace_id>",
  "query": { "bool": {
    "filter": [
      { "term":  { "workspace_id": "<workspace_id>" } },
      { "terms": { "access_keys": ["ws:…", "team:…", "user:…"] } },
      { "term":  { "in_trash": false } }
    ],
    "must":   [ { "multi_match": { "query": "<語>", "type": "phrase", "fields": ["title.gram", "body.gram"] } } ],
    "should": [ { "match": { "title": { "query": "<語>", "boost": 3 } } },
                { "match": { "body": "<語>" } } ]
  } }
}
```

- 性質ベーステスト：任意の検索の条件について、組み立てた要求が必ず `routing` と上の 3 つの `filter` を含む（ゴミ箱の検索では `in_trash: true`）。
- 1 人の主体のキーは、所属するグループとチームスペースの数で決まり、数百を超えない想定。`terms` の既定の上限（65,536）には届かない。

## 6. 検索の API と並べ替え

### 6.1 条件

| 条件 | 意味 |
| --- | --- |
| 語 | 部分一致。空白で区切った語はすべて含む（AND） |
| `"語 語"` | 連続する文字列 |
| タイトルだけ | `title.gram` だけで判定する |
| 作成者 | `created_by` |
| チームスペース | `teamspace_id` |
| ページの中 | `ancestor_ids` にそのページを含む |
| 日付 | `last_edited_at` または `created_at` の範囲。検索した人のタイムゾーンで解釈する |
| ゴミ箱 | `in_trash: true`。ゴミ箱のページは `can_edit` 以上の人にだけ見えるので、読み直し（5.2 節）で落ちる件数がある |

### 6.2 並べ替え

| 並べ替え | スコア |
| --- | --- |
| 最もよく一致（既定） | BM25（タイトルの重み 3）×最終編集の減衰（ガウス、30 日）×自分が最近開いたページの加点（直近 30 日の閲覧の履歴を、クエリの `should` に最大 50 件の `page_id` として渡す） |
| 最終編集 | `last_edited_at` の新しい順・古い順 |
| 作成 | `created_at` の新しい順・古い順 |

- 本家の「最もよく一致」は、最近の編集とタイトルを優先する（[Search](https://www.notion.com/help/search)）。重みの値は本家の公開の情報がないため、社内の評価のクエリの集合で決める。
- ページングは `search_after`（`_score`・`page_id`、または日付・`page_id`）。カーソルは不透明な文字列。1 ページ 20 件、深さは 1,000 件目まで。

### 6.3 結果

1. OpenSearch から `page_id` の一覧を得る。
2. 読み直し（5.2 節）で、タイトル・アイコン・パンくず（読める祖先だけ）・最終編集を得る。
3. 抜粋とハイライトは、読み直したページのブロックのテキストに対して API で付け、一致した最初のブロックの ID を返す。クライアントはそのブロックへスクロールする。

### 6.4 上限

- 1 人あたり 1 分に 60 回（クイック検索の入力ごとの呼び出しを含む）。超えたら 429。
- 1 回の検索は 3 秒で打ち切る。
- 検索語はログに平文で残さない。

## 7. クイック検索

`Cmd/Ctrl+P`・`Cmd/Ctrl+K` で開く検索（本家と同じ）。

| 入力 | 出すもの | 出どころ |
| --- | --- | --- |
| 空 | 最近開いたページ（最大 20） | クライアントのローカルの閲覧の履歴。表示前にサーバーで読めるか確かめる |
| 1 文字以上 | タイトルの前方一致を先に、続けて全文の一致 | `title.prefix` と全文の検索を 1 回の要求（`msearch`）で |
| オフライン | ローカルに写しのあるページのタイトルの部分一致 | クライアントのローカルの保存（[collaboration.md](collaboration.md)） |

- 目標：入力から候補の表示まで p95 300 ms（サーバーの処理は p95 150 ms）。入力は 150 ms で間引く。
- オフラインのローカルの検索は、写しを持っているページ（読めたことのあるページ）だけが対象なので、新たな漏洩の経路にはならない。権限を失ったページの写しは、次の同期で消す（[collaboration.md](collaboration.md)）。

## 8. 索引の更新と反映の遅れ（NFR-006）

```
API ─(tx)─▶ outbox ─▶ Relay ─▶ SQS search-index（本文）─▶ indexer ─▶ OpenSearch
                              └▶ SQS search-acl（権限・移動）─┘
```

- indexer はイベントを「きっかけ」として扱い、ページの現在の状態を DB（reader）から読んで文書を作る。テナントのコンテキストを設定してから読む。
- 同じページの編集は、5 秒の窓でまとめる（入力中の連続した変更で、同じ文書を何度も作らない）。
- 書き込みは `index_version` を外部バージョンにし、古い版で新しい版を上書きしない（本家と同じ）。
- ページの完全な削除は tombstone（本文を空にし `deleted`）で書き、7 日後に消す。ゴミ箱への移動は `in_trash` の更新。
- 失敗は SQS の再試行、5 回で DLQ とアラート。

| 区間 | 目安 |
| --- | --- |
| コミット → Relay → SQS | 1 秒 |
| まとめの窓 | 5 秒 |
| DB からの読み込みと文書の生成（1,000 ブロックのページ） | 2 秒 |
| 一括の書き込みと `refresh_interval` | 2 秒 |
| 合計（p99 の目標） | 15 秒（NFR-006 の 30 秒に対して余裕を持つ） |

- 指標 `search_index_lag`（コミット → 検索に見えるまで）の p99 が 30 秒を超える状態が 5 分続いたら、アラートを出す。
- 合成監視：「ページを編集 → 検索でヒット」と「共有を外す → 検索に出ない」を、5 分ごとに本番で確かめる。

## 9. 構成と規模

### 9.1 S1

- Amazon OpenSearch Service の 1 ドメイン。VPC の中、3 AZ、専用のマスターノード 3、データノードは負荷試験で決める。IAM で認証し、書き込みは indexer、読み出しは API のロールだけに許す。
- 索引は別名 `pages` の裏に置く（`pages-v1`）。ルーティングは `workspace_id`。`index.routing_partition_size` で大きいワークスペースの偏りを抑える（値は負荷試験で決める）。
- 見積もり（S1）：ページ 5,000 万（ブロック 10 億 ÷ 平均 20）、平均の文書 5 KB、N-gram を含めて索引は元の 5 倍（未検証）とすると、主シャードで約 1.2 TB、レプリカ 1 で約 2.5 TB。値は [capacity.md](capacity.md) で管理する。

### 9.2 S2

- 論理シャード（480。ADR-0003）の範囲ごとに、検索のドメインを分ける。`logical_shard → search_cluster` の割り当ての表を、DB の物理の割り当てと別に持つ。
- ワークスペースを別の検索のドメインへ移すときは、新しいドメインへの二重書き込み、バックフィル、読み出しの切り替えの順で行う（Slack の search.md の 5.4 節と同じ手順）。
- 非常に大きいワークスペースは、専用の索引にする。
- マッピングの変更による全体の再索引は、本家と同じく、DB のスナップショット（データレイク）から一括で文書を作り、その間の変更を二重書き込みで受ける。版の比較で新しい書き込みを優先する（[Rebuilding Notion's lexical search reindexer](https://www.notion.com/blog/rebuilding-notions-lexical-search-reindexer)）。

### 9.3 S3

- リージョンごとに検索のドメインを持つ。ワークスペースのデータと同じリージョンに置く。
- 意味検索（ベクトル）と AI による検索は、Notion AI の Epic で別に決める（intent.md の対象外）。

## 10. データの削除

- ページの完全な削除：tombstone にし、7 日後に消す。
- ワークスペースの削除：`routing` を付けた `delete_by_query`。削除の手順の一部として行う（[security.md](security.md)）。
- 利用者の削除：`access_keys` の `user:` は残っても、主体のキーに現れないので一致しない。定期の再計算（5.3 節）で消える。

## 11. テスト

- 日本語の部分一致、ひらがな・カタカナの混在、全角・半角、1 文字の語。
- 漏洩テスト（経路ごと）：別のワークスペース、共有されていないページ、共有を外した直後のページ、アクセス権のない親の下に移したページ、ゲストが共有されていない兄弟のページ、脱退した直後のチームスペース。いずれも検索の結果・件数・ハイライト・パンくずに出ない。
- 性質ベーステスト：任意の木・ACL・移動の列の後、indexer が落ち着いた状態で、各文書の `access_keys` を使った判定が、判定関数 `can` の結果と一致する。
- 性質ベーステスト：任意の木・ACL・移動の列の途中（indexer が遅れている状態を含む）で、検索の応答に含まれるページは、すべて `can(actor, read, page)` が真である。
- 版の比較：同じページのイベントを任意の順序・重複で indexer に与えても、最終的な文書が DB の最新の状態と一致する。
