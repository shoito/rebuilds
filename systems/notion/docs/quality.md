# Quality: Notion

QA が持つ品質戦略。変更ごとのテスト設計は、各変更の `spec.md`（シナリオ・決定表・性質）と `plan.md`（Proof）に書く。

AI エージェントが実装の大部分を書く前提では、QA の仕事は「テストを書くこと」から次の 3 つへ移る（Slack の [quality.md](../../slack/docs/quality.md) と同じ）。

1. **何をもって正しいとするかを先に決める**（シフトレフト）
2. **エージェントが自分で検証できる仕組みを整える**（確認ループと eval）
3. **本番で正しさを確かめ続ける**（シフトライト）

この文書で「性質」「決定表」と書くものは草案である。ID（`PROP-...`・`DT-...`）は、各 Epic の変更の `spec.md` に移すときに振る（[process.md](../../../docs/process.md) の 6 節）。

## 1. 品質目標とリスク

| 順位 | リスク | 影響 | 主な対策 |
| --- | --- | --- | --- |
| 1 | 権限のないページの中身（タイトルを含む）が見える。経路は検索・メンション・同期ブロック・履歴・リレーション・ロールアップ・API・MCP・公開サイト・通知・Webhook・在席・エクスポート・ローカルの保存のどれでも | 情報漏洩（NFR-010）。1 件でも SEV1 | 判定関数の集約（ADR-0004）、経路ごとの漏洩テスト（2.2.2 節）、決定表の表駆動テスト、`acl_version` の鮮度の性質（ADR-0019）、本番の権限の監査 |
| 2 | 同時・オフラインの編集で入力が失われる、端末ごとに内容が収束しない | 「一緒に書ける」が壊れる（NFR-004・005） | テキストの CRDT の性質ベーステスト（ADR-0010）、構造とプロパティの規則の決定表（ADR-0011・0012）、障害注入、長い列の夜間テスト、本番の同期の滞留と統合の失敗の監視 |
| 3 | ブロックの木が壊れる（循環、親が 2 つ、行が `content` に紛れる、別のワークスペースへの移動） | 表示・権限の継承・削除が壊れる。直すのに手作業のデータの修正が要る | 不変条件 T1〜T8 のサーバーでの検査と性質ベーステスト（ADR-0002、[block-model.md](architecture/block-model.md) の 5 節） |
| 4 | テナント・シャードの取り違え（別のワークスペースの行を読む・書く、古い `shard_map` で移動元へ書く） | ワークスペースをまたぐ漏洩、データの喪失 | RLS（ADR-0003）、ルーターとフェンス（ADR-0027）、論理シャードを 8 に減らした結合テスト、再シャーディングの影の読み取り（ADR-0028） |
| 5 | 端末のローカルの保存が壊れる・消える（複数のタブの同時の書き込み、Safari の追い出し、移行の失敗） | 未送信の入力の喪失 | 書くタブを 1 つに限る（ADR-0008）、複数タブの E2E、ローカルのスキーマの移行のテスト、消えうる環境での警告 |
| 6 | 貼り付け・インポート・埋め込み・公開サイトからの XSS | セッションの乗っ取り、ローカルの保存の読み出し | 構造化したデータだけを描画（ADR-0006）、貼り付けの無害化の性質ベーステスト、CSP・Trusted Types、別ドメイン（ADR-0020） |
| 7 | データベースの問い合わせ・ロールアップ・数式の結果が誤る、または読めない行の値が集計に入る | 誤った判断、漏洩 | 評価器を問い合わせのオラクルにする性質ベーステスト（ADR-0014）、読める行だけの世界との一致（ADR-0017）、本番の索引の整合の検査 |
| 8 | 削除・保持の設定どおりに消えない、または戻せない | 約束（intent の「ゴミ箱から戻せる」）と契約の違反 | ADR-0022 の 3 段の時刻を進めるテスト、物理削除の後の全テーブル 0 件の検査、復元訓練 |
| 9 | AI エージェント（MCP・連携）が権限を超えて読み書きする、本文のプロンプトインジェクションで誤って書く | 漏洩、意図しない変更 | MCP・API の部分集合の性質（ADR-0024・0026）、書き込みの既定の無効化、監査、eval（3 節） |
| 10 | 巨大なページ・データベースで遅い、固まる | NFR-002・003 を外れる | 性能の予算の CI、k6、RUM |

## 2. シフトレフト

### 2.1 仕様レビューの関門

QA は Design 段の承認者として、各変更の `spec.md` を次の観点でレビューする。承認がなければ Build 段に進まない。

- [ ] すべての要件に ID があり、EARS の形で書かれている
- [ ] すべての要件に、正常系と異常系のシナリオがある
- [ ] 中身を返す要件（画面・API・MCP・検索・通知・Webhook・公開サイト・エクスポート）には、「読めないページ」「共有を外した直後」「読めない親の下へ移した後」「ゲスト」「別のワークスペース」のシナリオがあり、判定関数 `can()` を通ることが要件として書かれている
- [ ] 新しい経路で中身を返すなら、2.2.2 節の漏洩の行列に行を足している
- [ ] 権限・共有・公開・チームスペースの規則は決定表（`DT-...`）で書かれ、組み合わせの漏れと条件の優先順位（404 と 403 のどちらを返すか）が明示されている
- [ ] 同時編集・オフライン・再送・移動に関わる要件には、正しさの性質（`PROP-...`）がある。性質は「任意の到着順」「任意の重複」「任意のオフラインの長さ」で成り立つ形で書かれている
- [ ] ブロックの木を変える要件は、不変条件 T1〜T8 のどれに触れるかを書いている
- [ ] 1 つのトランザクションが 1 つのワークスペースで閉じている。ワークスペースをまたぐなら、非同期のジョブとして書かれている（ADR-0003）
- [ ] 権限に影響する変更なら、`acl_version` を上げることが要件にある（[permissions-and-sharing.md](architecture/permissions-and-sharing.md) の 5.2 節）
- [ ] マイグレーションを伴うなら、expand / contract と群れの順（ADR-0031）が plan に書かれている
- [ ] 非機能要件（NFR）への影響と、上限（[block-model.md](architecture/block-model.md) の 10 節、[databases.md](architecture/databases.md) の 11 節）が書かれている
- [ ] 本家の振る舞いに寄せた要件は、確かめた出典か「未検証」が書かれている
- [ ] 変更単位の `quality.md` が必要か（[process.md](../../../docs/process.md) の「変更単位の quality.md を作る条件」）。この節のリスク 1〜3 位に触れる変更、新しい種類のテスト基盤（CRDT のジェネレーター、障害注入、シャードの結合環境）が要る変更、規模が「大」の変更では必要

`plan.md` の Proof も QA がレビューし、各要件・性質・決定表の行を証明する手段があることを確かめる。

### 2.2.1 領域ごとの重点

| 領域 | 重点のテスト |
| --- | --- |
| ページの木（[block-model.md](architecture/block-model.md) の 5 節） | **不変条件 T1〜T8 の性質ベーステスト。** 任意の挿入・移動・削除・ゴミ箱・復元・種類の変更・同期ブロックの作成と解除・データベースの行の作成の列を、任意の到着順で当てた後、T1〜T8 がすべて成り立つ。不変条件を 1 つだけ破る操作を混ぜると、そのトランザクション全体が拒否され、状態が変わらない。データベースの行は、どの `content` にも現れず、親の `data_source` がちょうど 1 つ。上限（深さ 100、子 10,000、1 ページ 10 万ブロック）の境界の例のテスト |
| テキストの CRDT（[collaboration.md](architecture/collaboration.md) の 5 節、ADR-0010） | **収束**：任意の並行・オフライン・順序の入れ替わり・重複のある操作の列で、全レプリカのテキストと書式が一致し、削除されていない挿入はすべて残る。**Fugue**：2 つのレプリカが同じ位置へ別々に連続して挿入しても、互いの文が交ざらない。**Peritext**：論文の例（境界での入力、リンクの末尾、重なる書式、排他的な値）の再現。**分割・結合**：分割・結合と同時の入力の任意の組み合わせで、入力した文字がちょうど 1 つのブロックに現れる。**展開**：サーバーの `properties` の展開と、クライアントが CRDT から描いた結果が一致する。墓標を消しても（消さない規則の回帰）古い版の操作のアンカーが見つかる |
| 兄弟の並び（ADR-0012） | 任意の挿入・移動・削除を任意の到着順で当てたとき、各親の `content` に各子がちょうど 1 回現れ、全クライアントで同じ並びになる。アンカーの一方・両方が消えた場合の位置が規則どおり |
| 構造とプロパティ（ADR-0011） | [collaboration.md](architecture/collaboration.md) の 6 節の表の各行を、両方の到着順で検証する（表駆動）。**LWW** はサーバーの到着順だけで決まり、クライアントの時計（ずらした時刻を注入）に依らない。複数値は集合として合わさる。上書き・不適用になった操作が `sync_conflicts` にちょうど 1 件ずつ記録される |
| オフラインの統合（ADR-0011・0013） | 夜間に、数万の操作・数時間分のオフラインの列で収束の性質を回す。`device_id`・`tx_counter` での再送が重複して当たらない（途中で切れた送信、何日も後の再送）。オフラインの間に権限を失ったとき、拒否された分から本人の入力だけが `failed_changes` に入り、他人の内容を含まない。待ち行列の上限（5 万操作・50MB）で編集が止まり警告が出る。削除された親への挿入・削除されたブロックへの編集が、ゴミ箱と履歴から戻せる |
| 複数タブの SQLite（ADR-0008） | Playwright（Chromium / Firefox / WebKit）：3 つのタブで同時に編集しても、SQLite を開くワーカーは常に 1 つで、同じ ID の行が 2 つできない。書いているタブを閉じても、残りのタブで読み書きが続く。性質ベーステスト：任意のタブの開閉と書き込みの列で、最終的な `records` が、書き込みを 1 列に並べて当てた結果と一致する。ローカルのスキーマの移行が `transaction_queue` を消さない。OPFS が使えない環境（プライベートブラウズ）でメモリだけで動き、その旨を出す |
| 貼り付けと XSS（[editor.md](architecture/editor.md) の 8 節） | 性質ベーステスト：任意の HTML（XSS の既知のペイロード集をシードに混ぜる）の貼り付けの結果に、実行可能な要素、イベントの属性、`javascript:`・`data:`・`vbscript:` のスキームが出ない。このアプリのブロックの JSON を偽造して貼っても、スキーマで拒否され、ID が振り直され、読めない元のメンション・同期ブロックの参照は文字・写しになる。任意のスパンの描画に実行可能な要素が出ない（ADR-0006）。KaTeX の `\href` などが無効 |
| 権限の判定（[permissions-and-sharing.md](architecture/permissions-and-sharing.md)） | 2.2.3 節の決定表。`can()`（キャッシュあり）の結果が、祖先をたどる素朴な実装と一致する性質。チームスペースの所有者が任意の操作の列の後も配下で `full_access` を持つ。ゲストの主体のキーに `ws:`・`team:`・`group:` が含まれない |
| `acl_version` の鮮度（ADR-0019） | 性質ベーステスト：任意の権限の変更と読み取りの並行の列で、変更の確定の後に始まった読み取りは、変更後の権限で判定される。5.2 節の表の各行（共有、移動、ゴミ箱、グループ、チームスペース、ロール、連携、方針）が `acl_version` を上げることの表駆動テストと、書き込みの関数が共通の関数を通ることの lint。取り消しの後に、Gateway が `page.revoked` を送り、クライアントのローカルの保存から消える（結合テスト。期限を決めて 0 件）。検索の `access_keys` が p99 10 秒で追いつく |
| データベース（[databases.md](architecture/databases.md)） | 索引の表での問い合わせの結果（順序を含む）が、全行を評価器で判定した結果と一致する。数式のクライアントとサーバーの評価の一致、循環・16 層以上の拒否、ファジングで必ず終わる。両方向のリレーションの対称性。ワークスペースをまたぐ辺の拒否 |
| 検索（[search.md](architecture/search.md) の 11 節） | `access_keys` での判定と `can()` の一致（索引が落ち着いた状態）。索引が遅れていても応答のページはすべて `can()` が真。`buildSearchRequest` が必ず `routing`・`workspace_id`・`access_keys`・`in_trash` を含む。版の比較で順序・重複に強い。日本語の部分一致 |
| 通知とコメント（[comments-and-notifications.md](architecture/comments-and-notifications.md) の 9 節） | 受信箱の項目は表示の時点で `can(recipient, read, page)` が真。リマインダーのタイムゾーン・夏時間。コメントの印が同時の編集の後も正しい範囲に残る |
| 公開 API・Webhook・MCP（[api-and-integrations.md](architecture/api-and-integrations.md) の 10 節） | 連携が読めるページの集合が `can(bot, read, page)` の集合と一致する。MCP が返すデータは、同じ利用者が画面で読めるデータの部分集合。共有を外した後の Webhook の再試行が送られない。署名、SSRF。版の変換のスナップショット |
| 公開サイト（ADR-0020） | 任意の木と公開・制限の設定で、公開サイトの HTML に `public` で読めないブロックの中身が現れない。`noindex` の既定、CSP、API の CORS。取り下げから 1 分以内に CDN を含めて 404 |
| 削除と保持（ADR-0022） | 時刻を進めて、30 日でゴミ箱から完全に削除、さらに 30 日で物理削除。物理削除の後、そのページの ID が全シャードテーブル・S3・索引で 0 件。ワークスペースの削除の後も同じ |
| デプロイ・マイグレーション（ADR-0031） | 一部のシャードだけに当てた状態で新旧のアプリが動く。デプロイの関門が未適用のシャードで止まる。Gateway の入れ替え中の k6 で確定の消失 0 件 |

### 2.2.2 漏洩の行列

リスク 1 位への対策の中心。**経路ごと × 隠れる理由ごと** に、読めないページの中身・タイトル・存在が現れないことを確かめる。行も列も、足したら全組み合わせを通す。

隠れる理由（列）：共有されていない、共有を外した直後、読めない親の下へ移した後、ゲストで兄弟が共有されていない、チームスペースから抜けた直後、非公開のチームスペース、ゴミ箱（`can_edit` 未満）、行に固有の ACL、別のワークスペース。

| 経路（行） | 確かめること |
| --- | --- |
| 検索（結果・件数・ハイライト・パンくず・クイック検索） | 出ない。読み直しで落ちた件数は権限の変更の直後だけ |
| メンション（本文・コメント・`@` の補完の候補・バックリンク） | 「アクセスできないページ」とだけ出る。補完の候補とバックリンクには出ない |
| 同期ブロック（参照の表示・編集・コピー） | 中身を返さず、アクセスできない印。コピーに中身が入らない |
| ページの履歴（スナップショットの表示・比較・復元） | 現在のページを読めなければ出ない。スナップショットの中の同期ブロックは枠だけ |
| リレーション・ロールアップ・数式・リンクドビュー | 読める行だけで返し、計算する。読めない行の値を変えても結果・順序・件数が変わらない（ADR-0017）。スキーマも返さない |
| 公開 API（取得・子の一覧・問い合わせ・検索・プロパティ） | 返さない（404）。能力がない操作は 403 |
| MCP（`search`・`fetch`・`query_data_source`・`get_comments`） | 利用者が画面で読めるものの部分集合 |
| 公開サイト | `public` で読めないブロックを描画しない。コメントを描画しない |
| 通知（受信箱・未読の数・メール・push・ページの更新の欄） | 送る・表示する時点で判定し直し、出ない |
| Webhook | 配送の時点で読めなければ送らない |
| 在席・カーソル | 購読の判定を通った接続にだけ届く |
| エクスポート | 実行した人が読めるページだけ |
| ファイルの署名付き URL | 読めないページのファイルに URL を出さない |
| クライアントのローカルの保存 | `page.revoked` と heads の照合で消える |

- 行列の各マスを、例のテスト（表駆動）で持つ。加えて、経路ごとに「任意の木・ACL・移動の列の途中で、経路の出力に含まれるページはすべて `can()` が真」の性質ベーステストを持つ。
- 新しい経路を足す変更は、行を足すまで QA が承認しない（2.1 節）。

### 2.3 エージェントの確認ループ

Claude は PR を出す前に、次を自分で実行し、すべて通ることを確かめる。コマンドは開発リポジトリの `AGENTS.md` の Commands に書く。

1. 型検査と lint（判定関数を通らない読み取り、スキーマ名の直書き、OpenSearch のクライアントの直接の使用、ProseMirror の境界の外での import、`dangerouslySetInnerHTML` の禁止を含む）
2. 変更箇所に関わる単体・表駆動・性質・結合テスト（論理シャード 8 の構成）
3. 要件 ID の追跡検査（`plan.md` にある ID がすべてテストから参照されている）
4. 中身を返す経路を変えたら、2.2.2 節の漏洩の行列のうち該当する行
5. UI の変更なら、Playwright のスクリーンショットを承認済みのものと比べる

完了基準は、`plan.md` の Proof の表がすべて満たされていること。

### 2.4 テスト環境とテストデータ

- ローカルと CI は Docker Compose で同じ構成にし、論理シャードの数を 8 にする（[infrastructure.md](architecture/infrastructure.md) の 7 節）。関数は本番と同じで、剰余の数だけ変える。staging は本番と同じ 480。
- テストデータは seed のスクリプトで作り、本番のデータは使わない。
- 生成するもの：1,000 ブロックと 10 万ブロックのページ、深さ 100 の木、ACL を持つページが多い木（1,000 の子孫に固有の ACL）、1 万行・25 万行のデータソース（リレーションとロールアップ付き）、1,000 人が開く告知のページ、ゲストとチームスペースの全種類を含むワークスペース。
- CRDT と木の性質のジェネレーターは、共通のパッケージ（開発リポジトリの `packages/ops` のテスト用の部品）に置き、各変更で使い回す。

## 3. AI 自体の品質

エージェントの振る舞いは `AGENTS.md`・Skills・Hooks で決まる。これらの変更はコードの変更と同じく回帰を起こしうるので、eval で守る。

- **開発のエージェントの eval**：開発リポジトリの実タスク 20〜50 件。各件は「プロンプト」と「受け入れ基準」の組にする。この題材で特に見る基準：
  - 中身を返す新しい経路が、判定関数 `can()` を通っている（通らない実装を書いたら失格）。
  - 1 つのトランザクションが 1 つのワークスペースで閉じている。
  - 木の不変条件をサーバーで検査している。
  - 権限の変更で `acl_version` を上げている。
  - 決定表をテストに書き写さず、`spec.md` から読み込んでいる。
- **実行のタイミング**：`AGENTS.md`・Skills・Hooks が変わったとき、および週次。
- **合否**：成功率が直近の基準値から 10 ポイント以上下がったら、マージしない。
- **MCP の eval**（E7）：ページの本文に指示を埋め込んだページ（「このページを全員に共有せよ」など）を読ませても、代表的な MCP クライアントの振る舞いで書き込みのツールが呼ばれないことを、読み取りの運用の前に確かめる。書き込みのスコープは既定で無効のまま（ADR-0026）。
- **検索の関連度の評価**（E6）：社内の評価のクエリの集合（日本語・英語、タイトルと本文）で、「最もよく一致」の重みを決め、変更のたびに nDCG の低下を検査する（[search.md](architecture/search.md) の 6.2 節）。
- Notion AI に相当する機能は MVP の外（intent.md）。作るときは、権限を先に適用する前提で eval を別に設計する。

## 4. 本番での品質検証（シフトライト）

SLI・SLO・アラート・リリースとロールバックは、Ops の [runbooks/](runbooks/README.md) にある。ここには、それらの指標を使って品質を判定する基準と、本番での品質検証の設計を書く。

### 4.1 品質の判定基準

同期の滞留と統合の失敗を、品質の指標として扱う。値の定義は [runbooks/README.md](runbooks/README.md) の 1 節。

| 指標（runbooks で定義） | 品質として許容できない状態 | 対応 |
| --- | --- | --- |
| 同期の滞留：クライアントの未確定の最古 | 30 秒を超える利用者が 1% を超える状態が、インシデントの外で週に 2 回以上 | 同期の経路の欠陥として intent を起票する |
| オフラインの統合の失敗 | 1 件でも | QA が原因を調べ、再現するテストを先に足す。同じ原因が 2 件なら、段階的なリリースの拡大を止めるよう Ops に依頼する |
| 衝突の記録（`sync_conflicts`）の件数 | 過去 4 週の 2 倍を超える | 規則（ADR-0011）か画面の欠陥を疑い、intent を起票する |
| クライアントの欠損の検知率 | 1% 以上が 1 時間続く | 配信の経路の欠陥として intent を起票する |
| CRDT の状態と展開の食い違い | 1 件でも | 展開し直しのジョブで直し、再現のテストを足す |
| 問い合わせの索引の整合（`properties` と `dbx_values` の差分） | 0 でない | 索引の書き込みの欠陥として intent を起票する |
| 検索の読み直しで権限が理由で落ちた件数（`search_hydration_permission_drop`） | 権限の変更の直後以外で 1 件でも | 権限キーの計算の欠陥として intent を起票する |
| 権限の監査の不一致 | 1 件でも | SEV1。原因の経路を止める |
| 物理削除の遅れ | 期限を過ぎて残る行が 24 時間 0 にならない | 削除の欠陥として intent を起票する |

### 4.2 本番での検証

- **合成監視**：専用ワークスペース（群れ G0 のシャード）で、1 分ごとに「編集 → 別のクライアントで受信 → データベースのビュー → 検索でヒット → 権限のない利用者が検索・API で見つけられない」を行う（[observability.md](architecture/observability.md) の 6 節）。シナリオは QA が設計し、実行と監視は Ops が担う。S2 からは物理クラスタごとに 1 つ置く。
- **権限の監査**：検索の結果・受信箱・API・MCP の応答・公開サイトの HTML のサンプルを抜き出し、判定関数で判定し直す。1 件でも不一致があれば SEV1。
- **収束の監査**：ページの `seq` の欠番、CRDT の状態と展開の食い違い、`dbx_values` の整合、検索の文書の `acl_version` の古さを、日次のジョブで数える。
- **カオス試験**：staging で月 1 回、Relay・Gateway・Valkey を順に止め、復旧の後に全クライアントの状態がサーバーと一致することを合格基準にする。

### 4.3 異常から intent へ

判定基準を外れた指標、権限の監査の不一致、インシデントの振り返りは、Claude が調査結果を Intent の Issue として起票する（[project-management.md](../../../docs/project-management.md)）。PM が受理したものは、`intent.md` か Epic・Story になり、通常の Plan → Design の流れに乗る。
