# ADR-0015: 数式は共通の評価器で解釈し、サーバーの値を正として実体化する

## Context

数式（Formulas 2.0）は、同じ行のプロパティ、リレーションをたどった他の行のプロパティ、ロールアップ、他の数式を参照する（[Formula syntax](https://www.notion.com/help/formula-syntax)）。本家は参照の深さを 15 層に限る（[Optimize database performance](https://www.notion.com/help/optimize-database-load-times-and-performance)）。数式の値で絞り込み・並べ替えができる必要があり（[Query a data source](https://developers.notion.com/reference/query-a-data-source)）、オフラインでも表示したい。利用者が書いた式を実行するので、サーバーを守る必要がある。本家がどこで評価しているかは未検証。

## Options

1. **TypeScript の 1 つの評価器（自前の構文解析と AST の解釈）をクライアントとサーバーで共有する。サーバーの値を正とし、索引に実体化する。同じ行の依存は書き込みと同時に、行をまたぐ依存は非同期に計算し直す**
2. **クライアントだけで評価し、サーバーは値を持たない**
3. **サーバーだけで評価し、すべての依存を書き込みと同時に計算し直す**
4. **数式を JavaScript に変換し、隔離した実行環境で動かす**

## Decision

1 を採用する。詳細は [databases.md](../architecture/databases.md) の 8 節にある。

- 同じ行だけを参照する数式は、書き込みのトランザクションの中で評価して `dbx_value` に書く。
- リレーションやロールアップをたどる数式は、outbox のイベントから Worker が計算し直す。目標は p99 5 秒。
- `now()` などの揮発する数式は実体化せず、問い合わせのときに評価する。
- スキーマの保存のときに、型・循環・深さ（15 層）を検査する。評価には手数・リストの長さ・テキストの長さ・時間の上限を置き、超えたらエラーの値にする。
- クライアントは同じ評価器で楽観的に表示し、サーバーの値で置き換える。
- 2 は、サーバーで絞り込み・並べ替え・API の値を返せない。
- 3 は、関連する行が多いとき（1 つの変更で数万行が影響する）に、書き込みが遅くなり、失敗する。
- 4 は、実行環境の隔離（脱出、資源の枯渇）を守る範囲が広く、クライアントとの意味の一致も難しい。

> 2026-09-27 の注記：Context の「本家は参照の深さを 15 層に限る」の値は正しいが、出典が違う。層の記述があるのは [Fix common formula errors](https://www.notion.com/help/common-formula-errors) で、数式が他の数式・ロールアップを参照するたびに 1 層増える（2026-09-27 に確認）。表の名前は複数形に揃えた（[data-model.md](../architecture/data-model.md) の冒頭の規約）。`dbx_value` は `dbx_values` と読む。

## Consequences

- 良くなること：
  - 数式の値で押し下げた絞り込み・並べ替えができる。
  - オフラインでも、同じ意味で数式を表示・問い合わせできる。
  - 評価器が純粋な関数なので、ファジングと参照実装との比較で確かめやすい。
- 引き受けるコスト：
  - 行をまたぐ数式は、数秒の間、古い値が見える。
  - 数式の定義の変更で、全行の計算し直しのジョブが要る。
  - 評価器の版の違い（古いクライアント）で、楽観的な表示がサーバーの値とずれることがある。サーバーの値で置き換える。

## Confirmation

- ファジング：ランダムな式・値で、構文解析器と評価器が上限の中で必ず終わり、例外で落ちない。
- 性質ベーステスト：同じ式・同じ入力で、クライアントとサーバーの評価の結果が一致する。
- 性質ベーステスト：任意の数式の定義の集合で、循環または 16 層以上の参照を含むものは保存を拒否する。
- 本番で、行をまたぐ計算し直しの遅れ（p99）を計測する。
