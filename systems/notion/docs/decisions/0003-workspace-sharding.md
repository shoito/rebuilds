# ADR-0003: ワークスペースで RLS と論理シャードを決める

## Context

ブロックは、S3 で数千億になる。本家は Postgres を、ワークスペースの ID で 480 の論理シャードに分け、物理のインスタンスの数を段階的に増やした（[Herding elephants](https://www.notion.com/blog/sharding-postgres-at-notion)、[The Great Re-shard](https://www.notion.com/blog/the-great-re-shard)）。

## Options

1. **ワークスペースをテナントにし、RLS で分け、ワークスペースの ID で 480 の論理シャードに割り当てる**（S1 は物理 1 つ）
2. **S1 は分割せず、必要になってから分割を設計する**
3. **ブロックの ID で分割する**

## Decision

1 を採用する。

- **テナントの分離は、Slack の ADR-0009 と同じにする。** 全テナントテーブルに `workspace_id` を持たせ、複合キーと `FORCE ROW LEVEL SECURITY` を使い、トランザクションごとにコンテキストを設定する。
- **論理シャードは 480 に固定する。** ワークスペースの ID のハッシュで論理シャードを決め、論理シャードを物理のクラスタに割り当てる表を持つ。S1 は物理 1 つに全論理シャードを置く。
- **1 つの操作は、1 つのワークスペース、つまり 1 つのシャードで閉じる。** ワークスペースをまたぐ機能（公開ページの複製など）は、非同期のジョブで行う。
- 2 は、後からの分割が、全表のキーの変更とデータの移動を伴い、本家も大きな作業になった。
- 3 は、ページの木がシャードをまたぎ、1 つのページの読み込みが複数のシャードに散る。

## Consequences

- 良くなること：
  - 物理のクラスタを増やすだけで、S2・S3 へ広げられる。論理シャードの移動で負荷を分けられる。
- 引き受けるコスト：
  - 巨大なワークスペース 1 つは、1 つのシャードに収まる前提になる。上限を超える場合の扱いを、S3 で検討する。
  - 論理シャードの割り当ての表と、移動の手順を運用する。

## Confirmation

- lint：テナントテーブルに `workspace_id`・RLS・シャードの鍵があることを検査する。
- 性質ベーステスト：任意の 2 ワークスペースで、一方のコンテキストで他方の行が読めない。
