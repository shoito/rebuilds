# ADR-0012: 子の並びは前後の兄弟をアンカーにした操作で表し、分数インデックスは使わない

## Context

ブロックの子の並びは、親の `content`（子の ID の並び）で持つ（ADR-0002）。ドラッグでの並べ替え、挿入、別の親への移動が同時に起き、オフラインの操作も後から届く。添字で位置を指すと、他の人の挿入・削除でずれる。

データベースのビューでの手動の並び（行の並べ替え）も同じ問題を持つ。

## Options

1. **添字**：`content` の n 番目に挿入する
2. **分数インデックス**：各子に並びの鍵（0〜1 の間の値、または文字列）を持たせ、並びは鍵の順とする。Figma が使う（[How Figma's multiplayer technology works](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)）
3. **兄弟のアンカー**：「X の後、Y の前」と前後の兄弟の ID で指し、サーバーが `seq` の順に `content` へ当てる。本家の操作（`listAfter` など）に近い（**未検証**。本家の操作の名前は公開の文書で確かめていない）
4. **子の並びも列の CRDT にする**

## Decision

3 を採用する。

- 操作は `after`（直前の兄弟）と `before`（直後の兄弟）の両方を持つ。サーバーは次の順に位置を決める。
  1. `after` が今の親の子にあれば、その直後
  2. なければ `before` が今の親の子にあれば、その直前
  3. どちらもなければ親の末尾
- サーバーが順序を決めるので、同じアンカーへの同時の挿入は、到着順で並ぶ（後に着いた方がアンカーのすぐ後）。どのクライアントも同じ結果になる。
- データベースのビューの手動の並びも、同じ形の操作で、ビューの並びの表に当てる。
- **2 を採らない理由**：鍵は、同時の挿入が同じ隙間に入ると、同じ値や長く伸びる値になり、対策（乱数を足す、鍵の振り直し）が要る。サーバーが順序を決める構成では、この複雑さが要らない。`content` の並びを持つ ADR-0002 の形も変えずに済む。
- **4 を採らない理由**：ブロックの並びで、同時の挿入が交ざることを避ける必要は薄い（ブロックは 1 回の動作で 1 つずつ入る）。CRDT の墓標を、並びにまで持つ意味がない。
- **1 を採らない理由**：同時の変更で位置がずれ、利用者の意図と違う場所に入る。

## Consequences

- 良くなること：
  - 並びの操作が小さく、`content` をそのまま正本にできる。
  - 古いバージョンを基にした操作も、アンカーがあれば意図した位置に入る。
- 引き受けるコスト：
  - 両方のアンカーが消えていると、末尾に入る。長いオフラインの後の挿入で、意図とずれうる。
  - 子の多い親（数千行のデータベースの手動の並び）では、`content` の配列の書き換えが大きい。大きさの上限と、並びの表の分け方を [databases.md](../architecture/databases.md) で決める。

## Confirmation

- 性質ベーステスト：任意の挿入・移動・削除の列を任意の到着順で当てたとき、各親の `content` に各子がちょうど 1 回現れ、全クライアントで同じ並びになる。
- 例のテスト：アンカーの一方・両方が消えた場合の位置が、上の 1〜3 の規則のとおりになる。
