# ADR-0018: 権限の水準を本家に合わせ、ACL は設定したページで継承を置き換える

## Context

[ADR-0004](0004-inherited-page-permissions.md) で、ACL は設定したページにだけ持ち、子は最も近い「設定のある祖先」の ACL を継承すると決めた。ここでは、どの水準を持つか、子のページで共有を変えたときに何を保存するかを決める。

本家の振る舞い（2026-09-26 に確認）：

- ページの水準は、フルアクセス・編集・内容の編集（データベース）・コメント・閲覧と、Business 以上の「作成」（[Sharing & permissions](https://www.notion.com/help/sharing-and-permissions)）。
- 子のページは親の権限を継承し、子で設定を変えられる。共有の画面の「Remove」で外せる（同じ文書）。
- 子で変えた後に、親の変更が子に届くかは、文書からは分からない（未検証）。

保存の仕方は、検索の権限キー（[ADR-0023](0023-search-engine-and-permission-filtering.md) の `acl_source_id`）、Gateway の購読の判定し直し、キャッシュの無効化のすべてに効く。

## Options

1. **置き換え**：子で何かを変えたら、子は継承元の ACL の写しに変更を加えたものを持ち、以後は継承元の変更を受けない（ADR-0004 の文面のまま）
2. **加算と制限**：子での追加は加算（継承元の変更は届き続ける）。継承した人を外す・下げるときだけ、写しを作って継承を切る
3. **加算と拒否の項目**：子に「拒否」の項目を置き、継承を切らない

## Decision

1 を採用する。詳細は [permissions-and-sharing.md](../architecture/permissions-and-sharing.md) の 4 節。

- **水準**：`none < can_view < can_comment < can_edit_content < can_edit < full_access` の全順序。`can_create` は全順序に入れず、データベースの行単位の権限と一緒に後で扱う。
- **実効の水準**：最も近い ACL を持つ祖先（自身を含む）の項目のうち、主体のキーに当たるものの最大。なければチームスペース（またはプライベートの領域）の暗黙の ACL。
- **例外**：チームスペースの所有者は、配下のページで常に `full_access`。ワークスペースの所有者は、ページの権限を迂回しない。
- **親の変更を子孫に届ける手段**：親で変えるとき、ACL を持つ子孫の数を画面に示し、「同じ変更を子孫にも加える」を選べる。選んだら、同じトランザクション（1,000 ページを超えたら非同期のジョブ）で子孫の項目にも加える。
- **移動**：実効の権限が変わるページの移動は `full_access` を要る。移動は共有の設定を変えるのと同じ効果を持つため。
- 2 は、1 つのページの実効の権限が、祖先の鎖の複数のページの ACL で決まる。検索の `acl_source_id` での一括の更新（ADR-0023）が成り立たず、親の変更のたびに部分木の文書を 1 つずつ計算し直すことになる。外すときに、他の祖先が同じ主体を許していないかを調べる必要もある。
- 3 は、拒否と許可の優先順位（グループで許可、個人で拒否など）が複雑になる。本家の画面にも拒否の概念はない。

## Consequences

- 良くなること：
  - ページの実効の権限が、1 つの ACL（か最上位）だけで決まる。判定・検索の権限キー・購読の判定し直しが単純になる。
  - ADR-0004 の文面と、ADR-0023 の索引の設計にそのまま合う。
- 悪くなること、引き受けるコスト：
  - 子に 1 人足しただけで、その子は親の後の変更を受けなくなる。「親と異なる」印と「子孫にも加える」の選択で補う。
  - 本家の振る舞いとずれる可能性がある（未検証）。

## Confirmation

- 表駆動テスト：permissions-and-sharing.md の 3.3・4.2・4.5・4.6 の表（spec.md に移したもの）。
- 性質ベーステスト：任意の木・共有の変更・継承に戻す・移動の列で、判定関数の結果が、祖先をたどる素朴な実装と一致する。
- 性質ベーステスト：チームスペースの所有者は、任意の操作の列の後も、配下のページで `full_access` を持つ。
