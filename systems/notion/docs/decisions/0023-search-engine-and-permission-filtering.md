# ADR-0023: 検索は S1 から OpenSearch でページ単位に索引し、権限キーと読み直しの二重で権限を効かせる

## Context

検索は、ワークスペースの中のページのタイトルと本文を対象にする（[search.md](../architecture/search.md)）。S1 でもブロックは 10 億あり、日本語の部分一致が要る。

権限はページの木を継承する（[ADR-0004](0004-inherited-page-permissions.md)）。読めないページの中身（タイトルを含む）が、検索の結果・件数・ハイライトのどこにも出てはならない（NFR-010）。一方、共有の変更や移動は、部分木の多くのページの権限を一度に変える。

本家は Elasticsearch でブロック単位に索引し、文書の生成時に文書ごとの権限を解決して入れている（[Rebuilding Notion's lexical search reindexer](https://www.notion.com/blog/rebuilding-notions-lexical-search-reindexer)、2026-08）。

Slack の先例は、S1 を PostgreSQL＋pg_bigm、S2 を OpenSearch にし、権限（読めるチャンネル）をクエリの時点で DB から得ている（Slack の ADR-0004、0027）。

## Options

検索の基盤：

1. **S1 から OpenSearch**
2. **S1 は PostgreSQL＋pg_bigm、S2 で OpenSearch**（Slack と同じ）

権限の適用：

- A. **ページごとの権限キーを文書に入れ、クエリの条件で絞り、結果を判定関数で読み直す**
- B. **クエリの時点で、読めるページの集合を DB から求めて条件に入れる**
- C. **検索の結果を、判定関数で後から除く**

## Decision

1 と A を採用する。文書はページ単位にする。

- **1 を採る理由**：S1 で 10 億ブロックを Aurora の GIN で索引すると、ブロックの正本と同じクラスタのストレージと書き込みを大きく使う。RLS の下では pg_bigm のインデックスが効かず、Slack と同じ RLS の例外（Slack の ADR-0027）も要る。関連度の並べ替え（本家の「最もよく一致」）も MVP に要る。2 は、S2 への移行（二重書き込み・バックフィル）を後で必ず行うことになる。
- **A を採る理由**：B は、読めるページの集合がワークスペースのページ数に比例し（数十万）、クエリの条件に入れられない。Slack はチャンネルの数が少ないので B が成り立つ。C は、件数・ページング・並べ替えから、読めないページの存在が漏れ、結果が空のページも生じる。
- **ページ単位の文書**：権限の単位はページなので、共有の変更と移動で更新する文書を、ブロックの数ではなくページの数に抑える。本家のブロック単位とは違う。一致したブロックへの移動は、読み直しの後に API で探す。
- **二重の守り**：
  1. 文書に `access_keys`（`ws:`、`team:`、`group:`、`user:`、`bot:`）と `acl_source_id` を入れる。検索した人の主体のキーを、リクエストごとに DB から求め、`terms` の条件にする。
  2. 結果の `page_id` を、判定関数と RLS の下で読み直し、タイトル・抜粋は読み直した値から作る。索引の値を画面に出さない。
- **権限の変更の反映**：ACL の変更は `acl_source_id` での `update_by_query`、移動は部分木の再索引で行い、専用のキューで p99 10 秒以内に反映する。その間の取り消しは、読み直しで即時に効く。メンバーの出入りは、主体のキーの側で即時に効く。
- 日本語は、一致の判定に N-gram、スコアに Sudachi を使う（Slack の search.md の 5.2 節と同じ）。

## Consequences

- 良くなること：
  - 件数・並べ替え・ページングが、権限で絞られた集合の上で決まり、存在が漏れない。
  - 取り消しは即時、付与は最大 10 秒遅れで効く。
  - S1 から関連度の並べ替えがあり、S2 への基盤の移行がない。
- 引き受けるコスト：
  - S1 から OpenSearch のドメインを運用する（費用、バージョンの更新、Sudachi のプラグイン）。
  - 権限キーの計算（`accessKeysFor`）が、判定関数と同じ規則を別の形で持つ。両者の一致を性質ベーステストで保つ必要がある。
  - 反映の間は、読み直しで落ちる件数があり、1 ページの件数が減りうる。
  - ページ単位の文書は、大きなページで文書が大きくなり、編集のたびに作り直す。5 秒の窓でまとめ、本文は 1 MB で切る。

## Confirmation

- 性質ベーステスト：任意の木・ACL・移動の列の後、索引が落ち着いた状態で、`access_keys` による判定と `can` が一致する。
- 性質ベーステスト：索引が遅れている状態を含め、検索の応答に含まれるページは、すべて `can(actor, read, page)` が真である。
- 性質ベーステスト：`buildSearchRequest` の要求が、必ず `routing`・`workspace_id`・`access_keys` の条件を含む。OpenSearch のクライアントの直接の使用を lint で禁止する。
- 指標 `search_hydration_permission_drop` と、合成監視「共有を外す → 検索に出ない」。
