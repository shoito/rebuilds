# ADR-0021: アカウントとメンバーを分け、ゲスト・連携もメンバーの行にし、チームスペースを最上位の暗黙の ACL にする

## Context

1 人が複数のワークスペースに属し、ワークスペースごとにロール・表示名・ゲストかどうかが違う。本家のロールは、ワークスペースの所有者・メンバーの管理者（Enterprise）・メンバー・ゲスト（[Who's who in a workspace](https://www.notion.com/help/whos-who-in-a-workspace)）。チームスペースは既定・公開・閉鎖・非公開の 4 種類で、チームスペースの所有者は既定で配下のページにフルアクセスを持つ（[Intro to teamspaces](https://www.notion.com/help/intro-to-teamspaces)）。いずれも 2026-09-26 に確認。

ページの ACL の主体と、ページの木の最上位（チームスペース）の権限をどう表すかを決める。テナントの分離（[ADR-0003](0003-workspace-sharding.md)）の下で、テナントの中のデータがテナントの外の ID に依存しないようにしたい。

## Options

主体：

1. **グローバルなアカウント＋ワークスペースごとのメンバー**（Slack の ADR-0010）。ゲストと連携もメンバーの行にする
2. ゲストを別の表（`guests`）にする
3. グローバルなユーザーだけを持ち、ワークスペースの中でも `account_id` を参照する

チームスペース：

- A. **チームスペースをブロックにせず、その設定を祖先の鎖の最上位の暗黙の ACL として扱う**
- B. チームスペースをページ（ブロック）にし、その ACL として持つ

## Decision

1 と A を採用する。詳細は [permissions-and-sharing.md](../architecture/permissions-and-sharing.md) の 2〜3 節。

- `members` は `account_id`（連携は NULL）、`kind`（`human` / `bot`）、`role`（`owner` / `membership_admin` / `member` / `guest`）を持つ。テナントの中のデータは `member_id` だけを参照する。
- ACL の主体は `user:`・`group:`・`team:`・`ws:`・`bot:`・`public`（[search.md](../architecture/search.md) の主体のキーと同じ形）。ゲストは `user:` だけを持ち、`ws:`・`team:`・`group:` を持たない。ゲストはチームスペースに入れない（本家で入れないかは未検証）。
- チームスペースの最上位の暗黙の ACL は、`team:` → チームスペースのメンバーの水準、既定・公開なら `ws:` → ワークスペースのメンバーの水準。プライベートの領域は本人だけ。
- 2 は、作成者・メンション・ACL の参照先が 2 つの表に分かれ、ゲストとメンバーの間の変更（本家にもある）が行の移し替えになる。3 は、テナントの中のデータが外の ID に依存する（Slack の ADR-0010 と同じ理由）。
- B は、チームスペースがページの一覧（サイドバー）の単位でもあり、ブロックの木に入れると、チームスペースの種類・参加の規則をブロックの属性で表すことになる。ページの親を「チームスペース」にしておけば、ブロックの木の不変条件（ADR-0002）を変えずに済む。

> 2026-09-27 の注記：「ゲストはチームスペースに入れない（本家で入れないかは未検証）」を確かめた。本家に「入れない」と明示した一文はないが、ゲストはページ単位で招待され、ワークスペース全体の権限やグループを持てず、チームスペースのページへもページ単位で共有される（[Who's who](https://www.notion.com/help/whos-who-in-a-workspace)、[Intro to teamspaces](https://www.notion.com/help/intro-to-teamspaces)、2026-09-27 に確認）。決定は本家の形と矛盾しない。本家には、チームスペースを作れず同じチームスペース・ページの人にだけ共有できる「制限付きメンバー」のロールもあるが、本システムの `role` には持たない（MVP の対象外）。

> 2026-09-28 の注記：上の「制限付きメンバー」を持たない決定を改めた。MVP の後、E10 で `role` に `restricted_member` を足す（[roadmap.md](../roadmap.md) の E10）。主体のキーの形は変えない。細部は E10 の Story で本家を観察して揃える。

## Consequences

- 良くなること：
  - テナントの中のデータがテナントの中だけで閉じ、ワークスペースの削除が `workspace_id` 単位で完結する。
  - 判定・検索の権限キー・購読が、同じ主体の形を使う。
- 悪くなること、引き受けるコスト：
  - 要求ごとに、アカウントとワークスペースからメンバーを解決する（認証ミドルウェアで行う）。
  - 判定の関数は、ページの ACL と、チームスペースの暗黙の ACL の 2 つの出どころを扱う。

## Confirmation

- マイグレーションの lint：テナントテーブルから `accounts` への外部キーは、`members.account_id` 以外にない。
- 表駆動テスト：permissions-and-sharing.md の 2.2・3.3 の表。
- 性質ベーステスト：ゲストの主体のキーに、`ws:`・`team:`・`group:` が含まれない。
