# ADR-0031: スキーマの変更は、論理シャードの群れの順に expand / contract で当てる

## Context

論理シャードは PostgreSQL のスキーマ `shard000`〜`shard479` として持つ（[ADR-0027](0027-shard-router.md)）。テーブルを 1 つ変えるには、同じ変更を 480 のスキーマに当てる必要がある。

Slack の設計では、マイグレーションを expand / contract に分け、アプリのデプロイの前に 1 回だけ実行する ECS タスクで当てる（Slack の [ADR-0022](../../../slack/docs/decisions/0022-zero-downtime-deploy-and-migrations.md)）。Notion では、次の点が違う。

- 480 回の適用は、途中で失敗しうる。一部のシャードだけが新しいスキーマになった状態が生じる。
- 1 つの誤った変更（長いロック、重いバックフィル）を、全シャードに一度に当てると、全顧客に同時に効く。
- 物理が複数（S2）になると、クラスタごとに負荷の余裕が違う。

## Options

1. **論理シャードを群れに分け、群れの順に当てる。アプリは、全シャードの適用が済んでから新しいスキーマに頼る**
2. 480 のスキーマに、1 つのトランザクションで一度に当てる
3. スキーマの変更を、各シャードで初めて使われたときに遅延して当てる

## Decision

1 を採用する。

### 群れ

| 群れ | 中身 | 次の群れへ進む条件 |
| --- | --- | --- |
| G0（カナリア） | 社内のワークスペースと合成監視のワークスペースがあるシャード（4〜8 個） | 適用が成功し、30 分、G0 のシャードの SLI が悪化しない |
| G1 | 5%（24 シャード） | 同上 |
| G2 | 25%（残りから 96 シャード） | 同上 |
| G3 | 残りすべて | — |

- 群れの割り当ては `global.shard_groups` で持ち、社内と合成監視のワークスペースを作るときに、G0 のシャードに入る ID を選んで作る（ID をサーバーで作る規則の中で、社内用に限って選ぶ。[ADR-0027](0027-shard-router.md)）。
- 同じ群れの中は、物理クラスタごとに並列度（初期値 4）を決めて当てる。writer の CPU と reader の遅延が閾値を超えたら、自動で待つ。

### 適用と台帳

- マイグレーションは、1 シャードずつ、それぞれ別のトランザクションで当てる。各シャードのスキーマに `schema_migrations` を持ち、どこまで当てたかを記録する。`global.migration_ledger` に、全シャードの状態を集める。
- 失敗したシャードは、止めて記録する。再実行は冪等にする（すでに当たっていれば何もしない）。
- `lock_timeout`、`statement_timeout`、`CREATE INDEX CONCURRENTLY` の規則は Slack の ADR-0022 と同じにする。`CONCURRENTLY` はトランザクションの外で実行するので、索引の作成は 1 シャードずつの別の段にする。

### アプリとの順序

| リリース | スキーマ | アプリ |
| --- | --- | --- |
| N（expand） | 群れの順に、全 480 シャードへ当てる | 新旧どちらのスキーマでも動く |
| デプロイの関門 | 台帳で、全シャードが N まで当たったことを確かめる | — |
| N+1 | — | 新しいスキーマに頼る。書き込みを新しい列に切り替える |
| バックフィル | Worker がシャードごとに、物理クラスタの負荷を見て小分けに埋める | — |
| N+2 以降（contract） | 群れの順に、古い列・テーブルを消す | 古いものを参照しない |

- **デプロイの関門：** 新しいスキーマに頼るアプリのリリースは、台帳で全シャードの適用が済んでいなければ、CI のデプロイのワークフローが止める。アプリのイメージに「必要なマイグレーションの番号」を埋め込み、関門で比べる。
- 新しい振る舞いの有効化は、別にフラグで行う（[delivery.md](../architecture/delivery.md) の 5 節）。群れの順とフラグの広げ方は独立である。
- 再シャーディングの間は、マイグレーションを凍結する（[ADR-0028](0028-zero-downtime-resharding.md)）。
- RLS のポリシーの変更は、Slack の ADR-0022 の規則（同じトランザクションで `DROP POLICY` と `CREATE POLICY`）に従い、各シャードで行う。

### 選ばなかった理由

- 2 は、480 のスキーマのロックを 1 つのトランザクションで取り、長いロックと失敗時の全体の巻き戻しになる。誤りも全顧客に同時に効く。
- 3 は、スキーマの状態がシャードごとに不定になり、アプリが常に両方の形を扱い続けることになる。

## Consequences

- 良くなること：
  - 誤ったマイグレーションの影響を、まず G0（社内）に閉じられる。
  - 途中で失敗しても、どのシャードがどこまで進んだかが台帳でわかる。
- 引き受けるコスト：
  - 1 つのマイグレーションが、全シャードに行き渡るまで時間がかかる（S1 で数十分〜数時間の見込み。初期見積もり）。
  - アプリは、expand の適用が全シャードに行き渡るまで、新しいスキーマに頼れない。
  - `schema_migrations` が 480 か所に分かれる。台帳の集約を監視する。

## Confirmation

- マイグレーションの lint（Slack の ADR-0022 の規則）に、次を足す：シャードのスキーマ名を直書きしない、1 シャード分の変更として書く。
- CI の結合テストで、480 シャードのうち一部だけに当てた状態で、新旧のアプリの両方が動くことを確かめる（シャードを数個に減らした構成で）。
- デプロイの関門が、未適用のシャードがあるときに止まることを、staging で確かめる。
