Google Calendar は何をするサービスか

個人と組織が、会議・面談・休暇・会議室の予定を管理し、他の人と調整するためのカレンダーです。主な使い手は、日本の中堅・大企業の社員です。社内の会議に人と会議室を招き、空きを探し、出欠を集めます。

個人

自分の予定、家族との共有、祝日。OS の標準のカレンダーやスマートフォンからも見る。

組織

部署やグループへの招待、会議室の予約、空き時間の共有。管理者が共有の方針と SSO を決める。

外部

取引先へメールで招待を送る。予約ページで、アカウントのない人から面談の予約を受ける。

再構築の intent が掲げる価値は 4 つです。時刻を間違えない、招待が食い違わない、空きをすぐ見つけて二重に取らない、どこからでも差分で同期する。規模は S1 で月間 60 万人、予定オブジェクト 3 億件を見込みます。識別子に本家の名前は使わず、calendar.<brand>.<domain> のように書きます（ADR-0006）。

設計の文書で効くところintent.md の「Proposed outcome」と「守るべき振る舞い」、architecture/README.md の 2 節（規模の段階）。

iCalendar の基本：VEVENT・UID・DTSTART

カレンダーの世界の共通語は iCalendar（RFC 5545）です。テキストの形式で、メールの招待・CalDAV・ICS のファイルのどれもこの形で予定を運びます。

BEGIN:VCALENDAR
VERSION:2.0
PRODID:-//<Brand>//Calendar//JA
BEGIN:VEVENT
UID:0192e4f0-…@<brand>.<domain>
DTSTAMP:20261004T010000Z
DTSTART;TZID=Asia/Tokyo:20261006T100000
DTEND;TZID=Asia/Tokyo:20261006T110000
RRULE:FREQ=WEEKLY;BYDAY=TU;COUNT=10
SUMMARY:週次の定例
SEQUENCE:0
END:VEVENT
END:VCALENDAR
  • VEVENT が予定 1 つ。UID が世界で一意の名前で、繰り返しの全回と例外は同じ UID を持ちます。
  • DTSTART は開始。TZID=Asia/Tokyo つきの壁時計の時刻で書けます（本来は同じファイルに VTIMEZONE も付けます）。
  • 長さは DTEND か DURATION のどちらかで書きます。DTEND は正確な長さ、DURATION:P1D のような日の単位は名目の長さです。夏時間をまたぐと、P1D は 23 時間にも 25 時間にもなります。
設計の文書で効くところdata-model.md の 2.5 節（iCalendar の往復）、events-and-recurrence.md の 4.5 節（長さ）。

繰り返し：RRULE・RDATE・EXDATE

繰り返しの予定は、回を 1 件ずつ保存せず、規則で持ちます。回の集合は「DTSTART ∪ RRULE の回 ∪ RDATE」から EXDATE を引いたものです（RFC 5545 の 3.8.5 節）。規則から回を作る処理を「展開」と呼びます。次の例で 1 段ずつ見ます。

DTSTART;TZID=Asia/Tokyo:20270131T100000
RRULE:FREQ=MONTHLY;BYMONTHDAY=31;COUNT=4
EXDATE;TZID=Asia/Tokyo:20270531T100000
RDATE;TZID=Asia/Tokyo:20270630T100000
  1. 周期ごとに候補を作る：月ごとに 31 日。1/31、2/31、3/31、4/31、5/31、6/31、7/31 …（まだ壁時計の時刻のまま）
  2. 無効な日付を捨てる：2/31、4/31、6/31 は存在しないので捨て、COUNT に数えない。
  3. COUNT を当てる：残った 4 回 → 1/31、3/31、5/31、7/31。DTSTART は最初の回として数える。
  4. TZID で UTC の瞬間にする：Asia/Tokyo の 10:00 → 01:00Z。
  5. RDATE を足す：6/30 を足す。
  6. EXDATE を引く：5/31 を引く。結果は 1/31、3/31、6/30、7/31 の 4 回。

設計では、MVP の FREQ を DAILY 以上に限り、RRULE は 1 本だけ受けます。BYSETPOS・WKST・2 月 29 日のような壊れやすい規則は、参照の実装（libical が第一の候補）との性質ベーステストで確かめます。

設計の文書で効くところevents-and-recurrence.md の 3.4 節（受け付けの検査）と 4 節（expand() の手順）、ADR-0008。

例外：RECURRENCE-ID と「これ以降」

繰り返しの 1 回だけを変えるときは、同じ UID の VEVENT をもう 1 つ作り、RECURRENCE-ID に「元の回の開始」を書きます。これが上書きです。規則を持つ VEVENT をマスターと呼びます。

flowchart TD
  A["回 R を変える"] --> B{"範囲"}
  B -->|この予定だけ| C["R の上書きを作る
RECURRENCE-ID = R の元の開始"]
  B -->|これ以降| D["系列を UNTIL で切り
新しい UID の系列を作る"]
  B -->|すべて| E["マスターを変える
上書きを付け替える"]
  • 「これ以降」：元の系列に UNTIL（または COUNT）を付けて終わらせ、R から先を新しい UID の系列にします。RELATED-TO で元を指します。標準の RANGE=THISANDFUTURE は使わず、外から届いたら 1 回分の上書きとして扱います（RFC との意図した違い）。
  • 回の取り消し：マスターの EXDATE に足す方法と、STATUS:CANCELLED の上書きを作る方法の 2 つが世の中にあります。

外のクライアントから、RECURRENCE-ID つきの STATUS:CANCELLED の上書きが届きました。本システムはどう保存しますか？

意味は同じ「その回がない」なので、保存の形を EXDATE の 1 つに揃えます。参加者へは CANCEL＋RECURRENCE-ID を送ります。なお参加者が自分の写しで回を消したときは、EXDATE にせず、その回の辞退にします。

設計の文書で効くところevents-and-recurrence.md の 5〜7 節、ADR-0009、ADR-0011。

タイムゾーン：壁時計の時刻と UTC の瞬間

「東京の 10:00」と「2026-10-06T01:00Z」は、今日は同じ瞬間でも、意味が違います。前者は人が決めた壁時計の時刻、後者は世界で 1 つの瞬間です。両者を結ぶのが、各地のオフセットと夏時間の規則を集めた IANA の tzdb です。

tzdb のリリース（2026b のような名前）に決まった予定はなく、ふつう数か月ごとに出ます。国が夏時間をやめる・始めるときは、短い予告で規則が変わります。規則が変われば、未来の予定の UTC の瞬間が変わります。

TZID つきの時刻。「東京の 10:00」。正本は壁時計の時刻と TZID。UTC は tzdata_version つきの派生の値で、tzdb が変われば作り直す。

UTC の瞬間だけ。TZID のないオフセットつきの時刻で、カレンダーの既定のゾーンと合わないもの。

浮動の時刻。TZID がなく、「どこにいてもその土地の 7:00」。ICS や CalDAV の取り込みで現れる。持ち主のカレンダーのゾーンで解く。

終日の予定。「2026-11-03」という日付で、終わりの日付を含まない。見る人のゾーンに関係なく同じ日付に出す。

「時刻はすべて UTC で保存し、表示の時だけ変換すればよい」。この設計で何が起きますか？

主催者が意図したのは「現地の 09:00」です。UTC だけを持つと、規則が変わった後も古いオフセットで計算した瞬間が残ります。そこで壁時計の時刻＋TZID を正にし、UTC をバージョンつきの派生にします（ADR-0002）。

設計の文書で効くところADR-0002、time-zones-and-holidays.md の 4〜6 節（tzdb のバージョンと更新の流れ）、runbooks/tzdb-update.md。

夏時間：存在しない時刻と 2 回ある時刻

日本に夏時間はありませんが、海外の拠点や参加者の予定で必ず出会います。切り替えの日には、壁時計の時刻が UTC の 1 つの瞬間に決まらないことがあります。例は America/New_York です。

日起きること02:30 や 01:30 は？
2027-03-14（日）02:00 に 03:00 へ進む（ギャップ）02:30 は存在しない
2027-11-07（日）02:00 に 01:00 へ戻る（重なり）01:30 が 2 回ある

毎週日曜 02:30 の予定を展開すると、次のようになります。

回解いた時刻UTC
03-07 02:3002:30 EST（−05:00）07:30Z
03-14 02:30存在しない。切り替えの前のオフセット −05:00 で解き、03:30 EDT07:30Z
03-21 02:3002:30 EDT（−04:00）06:30Z

2 回ある時刻は、先の回（切り替えの前のオフセット）にします。11-07 の 01:30 は EDT の 05:30Z です。どちらも RFC 5545 の 3.3.5 節の解き方で、展開・空き時間・リマインダー・画面が同じ関数 resolve を使います。

上の 03-14 の回について、RFC 5545 の 3.3.10 節（繰り返しの規則）は「存在しない時刻の回は捨て、数えない」としています。本システムは？

毎週の会議が夏時間の始まりの週だけ黙って消えると、利用者は欠けに気づけません。ずれた時刻で残せば気づいて直せます。これは RFC との意図した違い（ADR-0007 の D1）です。

設計の文書で効くところtime-zones-and-holidays.md の 5.1 節（resolve）、events-and-recurrence.md の 4.4 節、ADR-0007 の D1〜D6。

日本の祝日と和暦

日本の利用者は、祝日のカレンダーを重ねて使います。祝日は「国民の祝日に関する法律」で決まり、内閣府が 1955 年から 2027 年の一覧の CSV を公開しています。単純な固定の日付の表では表せない規則があります。

種類例
日付の固定元日 1/1、建国記念の日 2/11、天皇誕生日 2/23
第 n 月曜成人の日（1 月の第 2 月曜）、海の日、敬老の日、スポーツの日
春分の日・秋分の日法で日付を決めず、国立天文台が毎年 2 月に翌年の日を公表する
振替休日祝日が日曜なら、その後の最も近い祝日でない日。2026 年は 5/3 が日曜で、5/6 が休日
国民の休日前日と翌日が祝日の日。2026 年の 9/22（敬老の日と秋分の日の間）

設計では、規則の表からの生成を正本にし、内閣府の CSV は照合に使います。祝日は 1 日ずつ単発の終日の予定にし、transparent（空き時間を塞がない）にします。和暦（令和 8 年）は表示の書式だけで、保存は西暦のままです。

法務の確認待ち（L7）内閣府の CSV を取り込んで配信するときの利用の条件は、法務の確認待ちです。結論まで、祝日のカレンダーの公開の spec を承認しません。
設計の文書で効くところtime-zones-and-holidays.md の 9・10 節、free-busy-and-scheduling.md の 6.3 節（祝日を休みにする）。

招待：主催者の写しと iTIP

会議の予定は、主催者だけのものではありません。参加者それぞれのカレンダーにも同じ予定が載り、参加者は自分の出欠・リマインダー・色を持ちます。そこで参加者ごとに写しを持ち、主催者の写しを正にします。写しどうしを揃えるやりとりの意味を決めた標準が iTIP（RFC 5546）です。

flowchart LR
  O["主催者の写し（正）"] -->|"内部の iTIP REQUEST"| A1["参加者 A の写し"]
  O -->|"内部の iTIP REQUEST"| A2["参加者 B の写し（別の組織）"]
  O -->|"iMIP（メール）"| X["外部の参加者のカレンダー"]
  A1 -->|"REPLY（出欠）"| O
  X -->|"REPLY（メール）"| O
方法送り手 → 受け手意味
REQUEST主催者 → 参加者招待、または変更（予定の全体を送る）
REPLY参加者 → 主催者出欠（PARTSTAT：承諾・仮承諾・辞退）とコメント
CANCEL主催者 → 参加者取り消し。RECURRENCE-ID を付ければ 1 回分
COUNTER参加者 → 主催者別の時刻の提案。MVP は主催者に知らせるだけで、写しを変えない

本システムの中の参加者にも、外部と同じ意味のメッセージ（内部の iTIP）で配ります。参加者は写しの共有の項目（時刻・場所など）を直接書かず、変更は主催者の側への依頼として送ります。

設計の文書で効くところADR-0006、invitations-and-itip.md の 4・5 節（写しのモデルと当て方の決定表 DT-ITIP-001）。

SEQUENCE と iMIP：メールで招待を運ぶ

写しには新旧があります。どのメッセージが新しいかを決めるのが SEQUENCE です。主催者が日時・規則・状態などを変えたら 1 つ上げます。同じ SEQUENCE なら DTSTAMP の新しいほうが勝ちます。外部へは、iTIP を iMIP（RFC 6047）でメールに載せて運びます。

  1. 主催者が 10:00 の会議に A（外部）を招く。Content-Type: text/calendar; method=REQUEST のメールが届く。SEQUENCE:0。
  2. A が承諾する。A のカレンダーは REPLY を、ORGANIZER に書かれたアドレスへメールで返す。
  3. 主催者が 11:00 に動かす。SEQUENCE:1 の REQUEST を送り、A の出欠を「未回答」に戻す。
  4. メールの遅れで、A の古い返事（SEQUENCE:0 への辞退）が今ごろ届く。前の日時への返事なので捨て、A に最新の REQUEST を送り直す。
  5. 主催者が会議を取り消す。CANCEL を送り、SEQUENCE を上げる。

返事は ORGANIZER のアドレスへ届くので、設計では ORGANIZER を予定ごとの受け口のアドレス（o-<token>@imip.<brand>.<domain>）にします。RFC 6047 は送り手の認証に S/MIME を求めますが、設計は DKIM か SPF の揃いと From の一致で確かめます（RFC との意図した違い）。

主催者が会議のタイトルだけを変えました。参加者の出欠はどうなりますか？

SEQUENCE を上げるのは日時・規則・EXDATE・状態と、設計で足した場所・参加者の削除です。出欠を戻すのは日時と規則の変更だけです。タイトル・説明は同じ SEQUENCE の更新です（RFC 5546 の 2.1.4・3.2.2.2 節）。

設計の文書で効くところADR-0014、ADR-0015、invitations-and-itip.md の 5.3 節・6 節・11 節。

空き時間と日程の調整

空き時間（free/busy）は、予定の中身を見せずに「この時間は塞がっている」だけを返す仕組みです。同僚の予定の中身は見られなくても、空きは探せます。区間には種類があります（RFC 5545 の FBTYPE）。

予定空き時間での扱い
transparency = transparent（「空き」と表示する予定）、辞退した招待塞がない
不在（out_of_office）busy_unavailable
仮承諾・未回答の招待、tentative の予定busy_tentative
それ以外busy

「日程の調整」（find a time）は、必須の人・任意の人・会議室の空きを重ねて候補を出す機能です。設計では範囲を 5 分刻みのビットの列にし、累積の和で「この区間に予定があるか」を一定の時間で答えます。目標は 50 人＋会議室 20、2 週間で p95 1 秒です。勤務の時間と祝日は候補の並べ方にだけ使い、空き時間の結果には出しません。

設計の文書で効くところfree-busy-and-scheduling.md の 4.2 節（DT-FB-001）と 6 節、ADR-0017、ADR-0018。

会議室：二重予約を DB で防ぐ

会議室や設備は、予定の「参加者」として招きます。会議室は自動で出欠を返します。設定は「重ならなければ自動で承諾」か「管理者の承認」です。自動で承諾する会議室の二重予約は 0 件が目標です。

アプリで「重なりを探してから入れる」だけでは、同時の 2 つの要求が両方とも「空いている」と判断しえます。そこで PostgreSQL の排他の制約で、DB 自身に重なりを拒ませます。

-- resource_bookings：範囲の中の回ごとに 1 行
during tstzrange  -- [start_utc, end_utc)
EXCLUDE USING gist (tenant_id WITH =, room_id WITH =, during WITH &&)
  WHERE (status = 'accepted')

&& は「区間が重なる」、= は「同じ会議室」です。= と区間を 1 つの GiST の索引に入れるため、btree_gist の拡張を使います。繰り返しの予約は、重なる回が半分以下かつ 8 回以下なら系列を承諾してその回だけ辞退し、超えれば全体を辞退します（本家の説明に寄せた値）。

排他の制約は、範囲（未来 548 日）の中の回の行にしか効きません。終わりのない毎週の予約は、どう守りますか？

終わりのない系列の全回は作れません。範囲の端を進めるジョブが行を足し、端のジョブが止まった間は端より先の予約を受けません（ADR-0019）。

設計の文書で効くところrooms-and-resources.md の 4.2 節と 6.2 節（DT-ROOM-001）、ADR-0019、ADR-0020。

共有の段階と、中身を削る redact

カレンダーは、人・グループ・組織・公開の単位で共有します。ロールは 4 つの段で、上ほど強くなります。

ロールできること
free_busy_reader空き時間だけ見る（タイトルは見えない）
reader予定の中身を見る。ただし private の予定は区間だけ
writer予定を作る・変える。private の中身も見える（秘書・代理）
owner共有の設定を変える

予定ごとにも公開範囲（default・public・private・confidential）があります。見る人のロールと公開範囲から、返す形を 4 段で決めます：全体（FULL）、参加者を除く全体、区間だけ（BUSY）、返さない（NONE）。この削る処理が redact() です。

漏れは経路の数だけある画面だけでなく、API・CalDAV・ICS・検索・通知・Webhook のどれからも中身が漏れえます。だから「返す前に 1 つの関数で削る」を全経路に通します。組織の既定は「組織の中も外も空き時間だけ」です。
設計の文書で効くところsharing-and-acl.md の 4〜7 節（決定表 DT-ACL-001・002）、ADR-0021、ADR-0004（テナントは共通の資料の RLS）。

CalDAV の基本

iPhone・Mac のカレンダーや Thunderbird は、CalDAV（RFC 4791）でサーバーの予定を読み書きします。CalDAV は WebDAV の上の規約で、カレンダーは「コレクション（フォルダ）」、予定 1 つ（UID 1 つ）は「リソース（.ics のファイル）」です。

sequenceDiagram
  participant C as CalDAV のクライアント
  participant S as サーバー
  C->>S: GET /.well-known/caldav
  S-->>C: 301 → /dav/
  C->>S: PROPFIND（自分の主体はどこ？）
  S-->>C: 207 主体の URL
  C->>S: PROPFIND Depth 1（カレンダーの一覧、CTag、sync-token）
  S-->>C: 207 コレクションの一覧
  C->>S: REPORT sync-collection（前回のトークン）
  S-->>C: 207 変わった href と ETag、新しいトークン
  C->>S: PUT 予定.ics（If-Match: ETag）
  S-->>C: 204 または 412（他で変わっていた）
  • PROPFIND はプロパティを読む、REPORT は条件で問い合わせる WebDAV の拡張の方法です。
  • ETag はリソースのバージョンです。If-Match で「自分が見たバージョンのときだけ書く」を求め、違えば 412 にします。
  • CTag はコレクション全体のバージョン（標準の外の拡張）。sync-collection（RFC 6578）は前回からの差分を返します。
設計の文書で効くところsync-and-caldav.md の 6・7 節（PUT の判定 DT-DAV-001、暗黙のスケジュール）、ADR-0023、ADR-0024。

差分の同期：トークン・410・Webhook・ICS

端末は、毎回全件を取り直さず、前回からの差分だけを取ります。そのための目印が同期のトークンです。設計では、カレンダーごとに単調に増える番号 change_seq と変更のログを持ち、Web・公開 API・CalDAV・Webhook の共通の背骨にします。

トークン

「このカレンダーの seq N まで見た」。次の要求で N より後の変更（削除を含む）だけを返す。

410 Gone

トークンが使えない（30 日の期限切れ、共有の変化、DR の切り替え）。黙って欠けた差分を返さず、全件の取り直しを求める。CalDAV では 403 と valid-sync-token。

Webhook

「変わった」とだけ知らせる。本文はなく、受け手は差分の同期で中身を取る。期限（既定 7 日、最大 30 日）で切れ、自動で更新しない。

ICS の購読

外の URL の .ics を定期的に取り込む（既定 6 時間）。逆に、秘密のアドレスで自分のカレンダーを読み出し専用で公開もできる。

受け手のサーバーが落ちていて、Webhook の通知を 3 回取りこぼしました。変更は失われますか？

通知は「合図」で、正しさは変更のログとトークンが持ちます。「配信はベストエフォート、取り戻しは確実に」が設計の原則です。

設計の文書で効くところADR-0005、api-and-push.md の 4.6 節と 7 節（ADR-0028）、sync-and-caldav.md の 4 節と 8 節（ADR-0025）。

リマインダーの規模：毎時 0 分の集中

会議は 10:00・10:30 のような切りのよい時刻に集まり、リマインダーは「10 分前」「5 分前」に集まります。S1 の最悪で、毎時 50 分 00 秒の 1 秒に約 12 万件が来ます。平均ではなく、この瞬間の量で設計します。

1 秒 × 300 の枠"]

  • タイマーホイールは、時刻の枠を輪に並べ、1 秒ごとに針を進めて、その枠の仕事をまとめて出す仕組みです。何十万の個別のタイマーを持たずに済みます。
  • 送信の記録の一意の鍵（利用者、予定、回、方法、分、回の開始）で重複を捨てます。予定が動いたら計画を作り直し、送る直前に回の開始を確かめて古い時刻のものを捨てます。

予約ページ

予約ページは、自分の空いている枠を URL で外部に見せ、アカウントのない人（顧客・応募者）から面談の予約を受ける機能です。MVP は無料の予約だけです。

  1. 持ち主が設定する：長さ 30 分、受け付けは平日 10:00〜12:00（自分のタイムゾーンの壁時計）、間の時間 15 分、最短の予告 4 時間。
  2. 予約者がページを開く。受け付けの時間から、持ち主の予定あり（仮を含む）と既存の予約を前後の間の時間ごと引いて、枠を UTC で返す。予定の中身や理由は返さない。
  3. 予約者が枠を選び、名前とメールアドレスを送る（Idempotency-Key つき）。
  4. 1 つのトランザクションで確かめ直し、予約の区間を書く。区間の排他の制約で、同じ持ち主の予約どうしの重なりを 0 にする。
  5. 予約者は外部の参加者として、ICS つきの確認のメールを受ける。

会議室と同じ「区間の排他の制約」の考え方ですが、塞ぐのは予約どうしだけです。持ち主の普通の予定は重なってよいものなので、制約に入れず、確定の時に確かめ直します。冪等のキーは二重送信を防ぎます。

設計の文書で効くところbooking-pages.md の 5・6 節、ADR-0032・0033。

日本の法令の枠組み

ここは枠組みの説明だけです。設計の文書でも、次の論点はすべて法務の確認待ちで、結論を出していません。結論が出るまで、関係する Epic の spec を PM・QA が承認しません。

L1：予定のデータ（参加者の名前・メールアドレス、場所、説明）を組織からの委託として扱うか。外国にある第三者（メールの送信、Web Push の配信のサービス、外部の参加者への iMIP）への提供の扱い。漏えい等の報告の手順。L4：データを国外に出さないとどこまで約束するか。L5：変更のログ・受信したメール・監査ログなどの保持の期間。

L2：招待・コメント・予約の連絡の媒介が、電気通信事業法の届出の要る事業に当たるか。当たる場合の通信の秘密（迷惑な招待の検査など）。Web の画面の外部送信規律。L3：招待・リマインダーのメールが、特定電子メール法の広告宣伝のメールに当たらないことの整理と、迷惑な招待の大量の送信への責任。

L6：予約ページの予約者の個人情報の取得の通知・公表。L7：内閣府の祝日の CSV の利用の条件。L8：管理者が従業員の予定（private を含む）を見られる範囲。L9：委託の契約（DPA）とサブプロセッサー。L10：画面を本家に寄せる範囲（不正競争防止法・著作権）。

設計は、どの結論にも合わせられる形にしています。たとえば管理者による閲覧は、仕組みだけを作ってフラグの裏に置き、L8 の結論まで本番で有効にしません。

設計の文書で効くところintent.md の「法務の確認待ち」（L1〜L10）、security.md の法務の論点の整理、ADR-0037。

データモデルの読み方

中心は予定オブジェクト（event_objects）です。1 つの UID が 1 行で、マスターと、recurrence_id ごとの上書きを 1 つのまとまりとしてバージョンを持ちます。iCalendar・CalDAV の単位と同じです。記号の読み方は共通の資料にあります。

erDiagram
  calendars ||--o{ event_objects : "holds"
  event_objects ||--o{ event_overrides : "overrides"
  event_objects ||--o{ event_attendees : "attendees"
  event_objects ||--o{ occurrences : "expanded into"
  calendars ||--o{ calendar_changes : "change log"
  event_objects ||--o{ resource_bookings : "books rooms"
  calendars {
    uuid id PK
    bigint change_seq
  }
  event_objects {
    uuid id PK
    uuid calendar_id FK
    text uid "per calendar"
    text time_kind "zoned utc floating date"
    text rrule
    text copy_role "organizer attendee standalone"
    bigint version
    integer sequence
  }
  event_overrides {
    uuid event_object_id FK
    text recurrence_id "wall clock"
  }
  occurrences {
    uuid event_object_id FK
    text recurrence_id
    timestamptz start_utc "derived"
    text tzdata_version
  }
  calendar_changes {
    uuid calendar_id FK
    bigint seq
  }
  resource_bookings {
    uuid room_id FK
    tstzrange during "exclusion"
  }
  • マスター・上書き・回：マスターと上書きが正本です。回は expand() の結果で、occurrences（展開の索引）は過去 31 日から未来 548 日の回の写しです。捨てて作り直せます。範囲の外は、その場で同じ関数で展開します。
  • 回の名前：回は (event_object_id, recurrence_id) で特定します。recurrence_id は UTC ではなく壁時計の時刻で、系列の全体は '' です。
  • 写し：copy_role が主催者の写しか参加者の写しかを示します。参加者の写しは、テナントをまたいで主催者の写しを論理の参照で指します。
  • バージョンが 2 つ：version はどの変更でも上がる保存のバージョン（ETag の元）、sequence は iTIP のバージョンです。

用語集

iCalendar
RFC 5545。予定を運ぶテキストの形式。BEGIN:VCALENDAR から始まり、.ics のファイルやメールの添付になる。
VEVENT
iCalendar の中の、予定 1 つを表す構成要素。
UID
予定の世界で一意の名前。繰り返しの全回と上書きは同じ UID を持つ。
DTSTART
予定の開始。UTC・TZID つき・浮動・日付のどれかの形で書く。繰り返しでは最初の回になる。
RRULE
繰り返しの規則。FREQ=WEEKLY;BYDAY=TU;COUNT=10 のように書く。
RDATE
規則の外に足す回の日時の一覧。
EXDATE
回の集合から引く日時の一覧。回の取り消しに使う。
RECURRENCE-ID
上書きが、どの回（規則で決まる元の開始）を置き換えるかを示すプロパティ。
マスター
繰り返しの系列の規則と既定の中身を持つ VEVENT。
上書き
1 回分だけ時刻や中身を変えた VEVENT。同じ UID と RECURRENCE-ID を持つ。
回
繰り返しの規則から展開した 1 回分の予定。インスタンスとも呼ぶ。
予定オブジェクト
本システムの保存の単位。1 つの UID のマスターと上書きのまとまり。
展開の索引
一定の範囲の回を UTC の区間で写した表（occurrences）。範囲の表示・空き時間・会議室・リマインダーが読む。作り直せる写し。
壁時計の時刻
タイムゾーンのない「10:00」のような現地の時刻。TZID と組んで初めて瞬間が決まる。
tzdb
IANA が配る、世界のタイムゾーンのオフセットと夏時間の規則のデータベース。不定期に更新される。
TZID
タイムゾーンの名前。Asia/Tokyo のような tzdb の名前が多いが、iCalendar は形を決めていない。
VTIMEZONE
iCalendar の中に書くタイムゾーンの定義（オフセットと切り替えの規則）。
夏時間
DST（Daylight Saving Time）。季節で時計を 1 時間（地域により 30 分）進める制度。切り替えの日に時刻のギャップと重なりができる。
浮動の時刻
TZID も UTC の印もない時刻。見る場所のタイムゾーンで解く。
終日
時刻を持たず日付だけを持つ予定。終わりの日付は含まない。
iTIP
RFC 5546。招待・返事・取り消しなど、カレンダーどうしのやりとりの意味（方法）を決めた標準。
iMIP
RFC 6047。iTIP のメッセージをメールで運ぶ方法。text/calendar の部分に method を付ける。
主催者
ORGANIZER。予定を作り、参加者を招き、変更する人。主催者の写しが正になる。
PARTSTAT
参加者の出欠。NEEDS-ACTION・ACCEPTED・TENTATIVE・DECLINED など。
SEQUENCE
予定の iTIP のバージョンの番号。主催者が日時などの大事な項目を変えるたびに上げる。
DTSTAMP
iTIP のメッセージを作った時刻。同じ SEQUENCE の新旧を決めるのに使う。
DKIM
送信のドメインがメールに電子署名を付け、受け手が DNS の公開鍵で確かめる仕組み。SPF は送信元の IP をドメインの DNS の一覧で確かめる仕組み。
空き時間
free/busy。予定の中身を除き、塞がっている区間とその種類だけを示す情報。
排他の制約
PostgreSQL の EXCLUDE 制約。指定した演算子（区間の重なり && など）で衝突する 2 行の共存を、DB が拒む。
btree_gist
PostgreSQL の拡張。= で比べる普通の列を GiST の索引に入れられるようにし、「同じ会議室で、区間が重なる」の制約を作れる。
公開範囲
予定ごとの見せ方。private なら、参加者と writer 以上以外には区間だけを見せる。
redact()
見る人のロールと公開範囲から、返す形（全体・参加者を除く・区間だけ・返さない）を決めて中身を削る、本システムの 1 つの関数。
CalDAV
RFC 4791。WebDAV の上でカレンダーを読み書きする標準。OS の標準のカレンダーが使う。
WebDAV
HTTP を拡張し、サーバーの上のファイルとフォルダを読み書き・問い合わせする標準（RFC 4918）。
PROPFIND
WebDAV の方法。リソースやコレクションのプロパティ（名前、バージョン、子の一覧）を読む。
REPORT
WebDAV の拡張の方法。期間で絞る calendar-query、差分の sync-collection などの問い合わせに使う。
ETag
HTTP のリソースのバージョンの印。If-Match で、見たバージョンのときだけ書く条件つきの更新に使う。
CTag
コレクションの中身のどれかが変われば変わる印。RFC ではなく、広く使われる拡張（getctag）。
sync-collection
RFC 6578 の REPORT。前回のトークンを渡すと、その後に変わったリソースと消えたリソースを返す。
同期のトークン
「どこまで見たか」を表す不透明な値。次の要求で渡すと、その後の差分だけが返る。
タイマーホイール
時刻の枠を輪に並べ、針を一定の刻みで進めて、その枠に入れた仕事をまとめて発火させる仕組み。
予約ページ
空いている枠を外部の人に示し、予約を受けるページ。本家の appointment schedules にあたる。
