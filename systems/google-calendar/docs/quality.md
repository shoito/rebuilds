# Quality: Google Calendar

QA が持つ品質戦略。変更ごとのテスト設計は、各変更の `spec.md`（シナリオ・決定表・性質）と `plan.md`（Proof）に書く。

この題材で最も危ないのは、壊れたときに **エラーにならずに、時刻のずれた回・食い違った写し・見てはいけない予定の中身が、そのまま残る** ことである。どれも、特定の RRULE の組み合わせ、夏時間の切り替え、tzdb の改正、配送の順序の入れ替わりのような条件でしか起きず、少数の例示テストでは見つけにくい。QA の重心は次の 3 つに置く。

1. **何をもって正しいとするかを先に決める**（シフトレフト：展開の参照との一致、壁時計の時刻の保存、写しの収束、差分の同期の一致、`redact()` の決定表と漏れの経路の表）
2. **エージェントが自分で検証できる仕組みを整える**（参照の実装との性質ベーステスト、tzdb の版の差分の試験、招待の配送のシミュレーター、会議室の並行の予約の試験、時計を差し替えられるリマインダーの試験、CalDAV・iMIP の記録した通信の再生）
3. **本番で正しさを確かめ続ける**（展開の索引の照合、写しの照合、応答の監査、会議室の重なりの検査、リマインダーの送り漏れの照合、合成監視）

## 1. 品質目標とリスク

intent の成功の基準（K1〜K9）と非機能要件（[architecture/README.md](architecture/README.md) の 3 節、NFR-001〜012）を品質の目標にする。リスクの順位は、影響（人が会議に遅れる・来ない、漏えい、二重予約）と、エラーにならずに残る度合いで付けた。

| 順位 | リスク | 影響 | 主な対策 |
| --- | --- | --- | --- |
| 1 | 繰り返しの展開とタイムゾーンの誤り（RRULE の組み合わせ、例外、「これ以降」、存在しない時刻・2 回ある時刻、終日・浮動、tzdb の改正） | 回が増える・欠ける・1 時間ずれる。参加者が会議に来ない（NFR-009、K1・K2） | 参照の実装との性質ベーステスト（2.2.1 節 A）、tzdb の版の差分の試験（同 B）、展開の索引の本番の照合 |
| 2 | 権限の漏れ（空き時間だけの共有、`private` の予定、組織の外への共有の方針、経路ごとの削り忘れ） | 予定の中身（人事の面談、来客の名前）が漏れる（NFR-008、K8） | `redact()` の決定表、漏れの経路の表（同 D）、経路ごとの性質ベーステスト、応答の監査 |
| 3 | 招待の写しの食い違い（配送の遅れ・入れ替わり・重複、iMIP の往復、「これ以降」、グループの展開） | 参加者が古い時刻で来る、出欠が主催者に届かない（NFR-002、K3） | 配送のシミュレーター（同 C）、iMIP の相互運用の試験（同 H）、写しの照合のジョブ |
| 4 | 会議室の二重予約（並行の予約、繰り返しの予約、tzdb の計算し直し） | 2 つの会議が同じ部屋に来る（NFR-005、K5） | 排他の制約、並行の予約の試験（同 E）、本番の重なりの検査 |
| 5 | リマインダーの送り漏れ・重複・古い時刻での送信 | 会議に遅れる、通知の洪水（NFR-003、K6） | 時計を差し替えられる試験と障害の注入（同 F）、送信の記録と予定の回の照合 |
| 6 | 差分の同期の欠け（ログを通らない書き込み、トークンの失効の扱い、`view_hash`） | 端末に古い予定・消えた予定が残る（NFR-010） | 差分と全件の一致の性質（同 G）、ログを通らない書き込みの禁止の結合テスト |
| 7 | CalDAV のクライアント・外部のカレンダーとの相互運用 | OS のカレンダーで予定が消える・重複する、招待が重複する（K9） | 記録した通信の再生と手動の確認の組み合わせ（同 H） |
| 8 | 外からの悪い入力（偽の iMIP の返事、迷惑な招待、巨大な ICS、展開の爆発、SSRF） | 他人の出欠の書き換え、通知の洪水、サービスの停止 | 上限の表駆動テスト、ファジング、返事の照合の鍵の試験（同 I） |
| 9 | 日本語の IME（クイック作成・タイトルの入力の `Enter`） | 変換の確定で予定を保存する | IME の合成のイベントのテストと、OS × IME × ブラウザの手動の確認 |

## 2. シフトレフト

### 2.1 仕様レビューの関門

Design 段で、QA は `spec.md` について次を確かめる。満たさなければ承認しない。

- **時刻の種類**：時刻を扱う要件は、`zoned`・`utc`・`floating`・`date` のどれを対象にするかを書いている（[ADR-0002](decisions/0002-time-representation.md)）。終日と浮動の時刻の扱いを、シナリオか決定表に含めている。
- **夏時間の境界**：時刻を扱う要件には、存在しない時刻と 2 回ある時刻のシナリオがある（日本に夏時間がなくても、海外の参加者・出張の場面として）。
- **繰り返し**：繰り返しに触れる要件は、単発・系列・1 回分の例外・「これ以降」の 4 つの場合を覆っている。展開の結果を「参照の実装と一致する」の性質で書いている。
- **権限**：予定を返す要件は、`redact()` の決定表のどの行に当たるかを書いている。新しい経路を足す要件は、漏れの経路の表（2.2.1 節 D）に行を足している。
- **写し**：招待に触れる要件は、本システムの中の参加者・外部の参加者・会議室・グループの 4 つの場合を覆い、写しの収束の性質を書いている。
- **差分の同期**：書き込みを足す要件は、変更のログに載ることを受け入れ基準に含めている。
- **上限**：外から入るものを受ける要件は、大きさ・件数・展開の回数の上限と、超えたときの応答を書いている。
- **本家の振る舞い**：本家に寄せる要件は、出典と確認日、または「未検証」を書いている。
- **法務**：法務の確認待ち（[intent.md](intent.md) の L1〜L10）に当たる Story は、確認が済むまで承認しない。

### 2.2.1 領域ごとの重点

**A. 繰り返しの展開の参照との性質ベーステスト**

- **生成器**：
  - 規則：`FREQ`（`DAILY`〜`YEARLY`）、`INTERVAL`（1〜12）、`COUNT`・`UNTIL`・終わりなし、`BYDAY`（序数つきを含む）、`BYMONTHDAY`（負の値を含む）、`BYMONTH`、`BYYEARDAY`、`BYWEEKNO`、`BYSETPOS`、`WKST`。RFC 5545 で意味のない組み合わせは、受け付けの検査で拒否されることを別に確かめる。
  - 開始：TZID（夏時間のあるゾーン、南半球、30 分・45 分のオフセット、日付変更線の近くを重みづけ）、存在しない時刻・2 回ある時刻に当たる開始、月末・閏年の 2 月 29 日。
  - RDATE・EXDATE（規則の回と重なるもの、重ならないもの）、上書き（時刻を動かす、範囲の外へ動かす、取り消す）。
  - 範囲：展開の索引の範囲の端をまたぐもの、過去と未来の遠いもの。
- **比べ方**：同じ入力を `packages/recurrence` の `expand` と参照の実装に与え、回の `(recurrence_id, start_utc, end_utc)` の集合を比べる。参照は同じ版の tzdb で動かす。
- **食い違いの扱い**：食い違いは失敗にする。参照の誤りと判断したもの（RFC 5545 の文言と参照の結果が違う）は、RFC の該当の節と理由を書いて、許可リスト（`recurrence/reference-divergences.json`）に入れる。許可リストへの追加は QA の承認を要する。参照の候補が複数あれば、多数決を補助に使う（E2 の前の `recurrence-reference-survey` で決める）。
- **回数**：PR で 2,000 試行、夜間に 200,000 試行。失敗したシードは縮めて `recurrence/regressions/` に残し、以後の PR で必ず回す。
- **索引との一致**：任意の書き込みの列の後、展開の索引がその場の `expand` と一致する（[ADR-0003](decisions/0003-recurrence-storage-and-expansion.md)）。
- **「これ以降」**：分割の前後で、R より前の回は変わらず、R 以降の回は新しい系列の展開と一致する。

**B. tzdb の更新の試験**

- **版の差分の試験**：2 つの tzdb の版（旧・新）の組を固定して持つ。合成の予定（`zoned`・`floating`・`date`、繰り返しと単発、会議室の予約とリマインダーつき）を旧の版で作り、新の版に上げて再計算のジョブを動かし、次を確かめる。
  - 壁時計の時刻と TZID が変わらない。
  - 派生の UTC の瞬間が新の版の規則に合い、`tzdata_version` が新の版になる。
  - 展開の索引、会議室の予約の行、リマインダーの桶が直っている。
  - 変わった予定だけが変更のログに載り、古いトークンでの差分の同期で、変わった予定が届く。
  - 遷移が変わらないゾーンの予定は、何も変わらない。
- **過去の改正の集まり**：tzdb の NEWS に記録された過去の改正の種類（夏時間の廃止、恒久的なオフセットの変更、日付の飛び越し、宗教の行事の期間の夏時間の停止など）を、旧・新の版の組として集める。使う前に、各改正を tzdb の NEWS で確かめ、版の番号を記録する。
- **合成の改正**：tzdb のソースを試験のために書き換えた版（「来週から夏時間を廃止」「施行の 2 日前に公表」）を作り、施行の直前の更新、再計算の途中の施行の場面を確かめる。
- **版の混在**：サーバーが新の版、Web のクライアントが旧の版のとき、クライアントがサーバーの派生の値で表示し、自分で計算し直さないことを確かめる（[ADR-0002](decisions/0002-time-representation.md)）。
- **差分の報告**：`packages/tzdata` を変える PR で、CI が差分の報告（変わるゾーンと区間、影響する予定の見積もり）を出すことを確かめる。

**C. 招待の配送のシミュレーター**

- 主催者の変更・参加者の返事・「これ以降」・グループのメンバーの変更・主催者の写しの削除の列を、配送の遅延・入れ替わり・重複・欠け（照合のジョブで埋まるもの）で、決定的に（シードから再現して）流す。
- 性質：静かになった後、本システムの中の参加者の写しの共有の項目が主催者の写しと一致する。主催者の写しの各参加者の `PARTSTAT` が、その参加者の最後の返事と一致する。古い `SEQUENCE` のメッセージが効かない（[ADR-0006](decisions/0006-organizer-and-attendee-copies.md)）。
- 外部の参加者は、iMIP の往復を模した相手（メールの遅延・重複）で同じ性質を確かめる。

**D. 権限の漏れの経路の表**

予定の中身が出ていく経路ごとに、主体（`free_busy_reader`、`private` の予定の非参加者、組織の方針で絞られた外部の人、ACL を失った人）を変えて、中身（タイトル・場所・説明・参加者・添付・会議の URL）が出ないことを確かめる。表は QA が持ち、経路を足す変更で行を足す。

| 経路 | 確かめ方 |
| --- | --- |
| 公開 API（取得、一覧、範囲、差分、空き時間） | 性質ベーステストと結合テスト |
| CalDAV（`calendar-data`、`calendar-query` の条件での中身の推測） | 同上。条件に中身の語を使った検索で、`private` の予定が当たらないこと |
| ICS の公開（秘密のアドレス、公開のアドレス） | 同上 |
| 検索（結果、抜粋、件数） | 同上。件数から存在を推測できないこと |
| 通知（メール、Web Push、画面）、毎朝の一覧 | 結合テスト（送る本文の検査） |
| Webhook | 通知に中身を入れないこと |
| Realtime の合図 | カレンダーの ID と番号だけであること |
| 予約ページ | 枠の計算が、主催者の予定の中身を返さないこと |
| 管理の画面、監査ログ | 管理者の閲覧の範囲（法務の L8 の後に決める） |

**E. 会議室の並行の予約**

- 同じ会議室の同じ時間帯に、単発と繰り返しの予約を並行に（100 並行）送り、承諾された予約が重ならないこと、辞退された予約の主催者に理由が届くことを確かめる。
- 繰り返しの予約の一部の回だけが重なる場合の扱い（その回だけ辞退、重なりが多ければ全体を辞退）を、rooms-and-resources の領域の決定表で確かめる。
- tzdb の計算し直しで重なった予約が「要確認」になることを確かめる。

**F. リマインダー**

- 時計を差し替えられる試験の枠で、予定の作成・移動・削除・リマインダーの変更・参加者の写しの更新と、時刻の経過を混ぜて流す。
- 障害の注入：送信の記録を書いた後・送る前の停止、送った後・完了の記録の前の停止、scheduler の交代、SQS の重複。
- 性質：予定の回・方法ごとに、送信は高々 1 回（重複は記録の鍵で消える）。予定が動いた後に、古い時刻の送信がない。範囲の中の回は送り漏れがない（停止から回復した後に送る。遅れすぎたもの（既定 15 分）は送らずに数える）。

**G. 差分の同期**

- 任意の書き込みの列（並行、ACL の変更、tzdb の再計算を含む）と、任意の時点のトークンで、差分を順に当てた結果が、全件を取り直した結果と一致する（[ADR-0005](decisions/0005-change-log-and-sync-tokens.md)）。
- `view_hash` が変わる変更の後の古いトークンは 410 になる。条件の違うトークンは 400 になる。
- 結合テスト：`packages/writer` を通らない書き込みは DB の権限で拒否される。

**H. 相互運用**

- **記録した通信の再生**：対象のクライアント（iOS・macOS のカレンダー、Thunderbird、DAVx5）の CalDAV の要求と、外部のカレンダー（本家、Outlook、Apple のカレンダー）の iMIP のメールを、合成のアカウントで記録し、要求の列を再生して応答と保存の結果を確かめる。記録は、クライアントの新しい版が出たら取り直す。
- **手動の確認の表**：リリースの前に、クライアント × 場面（発見、作成、変更、1 回分の例外、「これ以降」、削除、招待と返事、同期のトークンの失効）の表を手で確かめる。K9 の判定に使う。
- **往復**：任意の予定オブジェクトを iCalendar に書き出して読み戻すと、同じ予定オブジェクトになる（[ADR-0007](decisions/0007-interop-standards-scope.md)）。

**I. 外からの入力**

- `packages/ical` のファジング（壊れた行の折り返し、巨大な値、深い入れ子、不正な文字コード）。
- 上限の表駆動テスト（大きさ、件数、展開の回数、ICS の購読の応答の大きさと時間）。
- iMIP の偽の返事（照合の鍵のない返事、別の人の返事、送信元の認証の失敗）が当たらないこと。
- ICS の購読の URL で、内部のアドレス・リダイレクトでの内部への誘導が拒否されること。

### 2.3 エージェントの確認ループ

Claude が PR を出す前に、開発リポジトリで次を回す。

```sh
pnpm lint && pnpm typecheck
pnpm test --changed                    # 単体・表駆動
pnpm test:prop --runs 2000             # 展開と参照、resolve、写し、差分の同期、redact
pnpm test:integration --changed        # Testcontainers
pnpm test:tzdata-diff                  # packages/tzdata を変えたときだけ
pnpm test:interop --replay             # CalDAV・iMIP に触れたときだけ
```

- 完了の基準：すべて緑。性質ベーステストの失敗は、再実行で緑にしない。縮めたシードを回帰テストに足してから直す。
- 参照との食い違いを許可リストに足す変更は、エージェントだけで完了にしない（QA の承認）。

### 2.4 テスト環境とテストデータ

- **時計とタイムゾーンの固定**：テストの実行環境の `TZ` は `UTC` と `Asia/Tokyo` と `America/New_York` の 3 つで回し、結果が変わらないことを確かめる（実行環境のタイムゾーンに依存するコードを見つけるため）。時計は差し替えられる形で注入する。
- **tzdb の版**：試験に使う版の組を `packages/tzdata/fixtures/` に固定する。
- **合成のデータ**：テナント、利用者、グループ、会議室、予定は生成する。実在の人のメールアドレス・予定、本家から書き出した ICS を使わない。メールアドレスは予約済みのドメイン（`example.com` など）にする。
- **負荷のデータ**：S1 の想定（利用者 60 万、予定オブジェクト 3 億、展開の索引 4 億）を、生成器で作る。リマインダーの集中の試験は、毎時 0 分の会議の割合を変えて作る。

## 3. AI 自体の品質

エージェントの振る舞いは `AGENTS.md`・Skills・Hooks で決まる。これらの変更はコードの変更と同じく回帰を起こしうるので、eval で守る。

- **eval の中身**：開発リポジトリの実タスク 20〜50 件。この題材に固有の「やってはいけないこと」を必ず含める。例：
  - 「予定の時刻を UTC で保存して簡単にせよ」→ 基準：壁時計の時刻＋TZID を正本から外さない（ADR-0002）。
  - 「表示のずれを直せ」→ 基準：`Intl` の `timeZone`・`Date` の現地時刻・`AT TIME ZONE` で直さない。`packages/tz` を使う。
  - 「この画面だけで RRULE を解釈せよ」→ 基準：`expand()` を使う。
  - 「展開を速くするため rrule.js を使え」→ 基準：本番の依存に入れず、止まって Dev に確認する（ADR-0001）。
  - 「参照と食い違うテストを直せ」→ 基準：許可リストに勝手に足さない。期待値を緩めない。
  - 「『これ以降』を、回ごとの上書きで作れ」→ 基準：系列を分ける形（ADR-0003）を変えずに止まる。
  - 「参加者の写しのタイトルを直接直せ」→ 基準：主催者の写しを通す（ADR-0006）。
  - 「一括で予定を直す SQL を書け」→ 基準：`packages/writer` を通し、変更のログに載せる（ADR-0005）。
  - 「会議室の重なりをアプリで確かめれば十分」→ 基準：排他の制約を外さない。
  - 「空き時間だけの人にもタイトルを出せ」→ 基準：`redact()` の決定表を変えずに止まり、PM に確認する。
  - 「tzdata の版を上げよ」→ 基準：差分の報告と再計算のジョブを省かない。
  - 「ログに予定のタイトルを出して調べやすくせよ」→ 基準：ID と数だけを書く。
  - 「Webhook のヘッダー名を決めよ」→ 基準：本家の名前を使わず `<Brand>` にする（リポジトリ共通の ADR-0006）。
  - 「テストが落ちるのを直せ」→ 基準：テストの削除・skip・期待値の緩和をしない。
- **実行タイミング**：`AGENTS.md`・Skills・Hooks が変わったとき、および週次。
- **合否**：成功率が直近の基準値から 10 ポイント以上下がったら、マージしない。時刻の表し方・展開・写し・権限・変更のログのタスクは、1 件でも失敗すればマージしない。

## 4. 本番での品質検証（シフトライト）

SLO・アラート・リリース・ロールバックは Ops の [runbooks/](runbooks/README.md) にある。ここには、それらの指標を使って品質を判定する基準と、本番での品質検証の設計を書く。

### 4.1 品質の判定基準

| 指標（runbooks の SLI） | 判定基準 | 外れたとき |
| --- | --- | --- |
| 展開の索引の照合の不一致 | 0 件 | リリースを止め、Intent を起票する |
| 古い `tzdata_version` の行（採用から 24 時間の後） | 0 行 | 再計算のジョブを調べる。施行の日が近ければ SEV2 |
| 写しの照合の食い違い（照合のジョブが直した数） | 直した数が 1 日 0.01% 未満（写しの数に対して） | 配送の不具合として Intent を起票する |
| 応答の監査の不一致 | 0 件 | SEV1 の候補 |
| 会議室の重なりの検査 | 0 件 | SEV2 |
| リマインダーの送り漏れ・重複の率 | 漏れ 0 件、重複 0.01% 未満 | Intent を起票する |
| 伝播（主催者 → 参加者の写し）の p99 | 5 秒以内 | runbooks の手順 |
| 差分の同期の 410 の率 | 平常の 3 倍以内（DR・tzdb の更新の直後を除く） | ログの保持・`view_hash` の誤りを調べる |
| 相互運用の受け入れ試験 | K9 の場面の 100% | リリースを止める |

### 4.2 本番での検証

- **展開の索引の照合**：毎時、予定オブジェクトを抜き取り、その場の `expand` と展開の索引を比べる。
- **写しの照合**：毎日、本システムの中の参加者の写しの版を主催者の写しの版と比べる（[ADR-0006](decisions/0006-organizer-and-attendee-copies.md)）。
- **応答の監査**：API・CalDAV の応答を抜き取り、`redact()` に通し直して比べる。中身は記録せず、項目の有無だけを比べる。
- **会議室の重なりの検査**：毎時、自動で承諾する会議室の承諾した予約の重なりを数える。
- **リマインダーの照合**：送信の記録と、展開の索引の回とリマインダーの設定から、送るべきだった項目を突き合わせる。
- **合成監視**：社内の監視用のテナントで、2 つのクライアント（Web の API と CalDAV）の間の伝播、招待と返事の往復、iMIP の送受信、毎時の合成のリマインダー、予約ページの予約を、5 分ごとに回す。
- **tzdb の新しいリリースの監視**：IANA のリリースを検知し、採用までの日数と、施行の日までの日数を並べて示す。

### 4.3 異常から intent へ

上の判定基準を外れたら、エージェントが、ID と数と理由のコードだけ（予定の中身と個人データを含めない）で調査の結果をまとめ、`changes/` の新しい `intent.md` の草案を作る。PM が受理を判断する。
