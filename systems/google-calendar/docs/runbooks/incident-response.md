# Runbook: インシデントへの対応（共通の進め方と最初の切り分け）

- Owner: Ops
- 対応するアラート: 予定の読み書きの SLO のバーンレート、書き込みの p99、変更のログの欠け、SLI の集計の欠け、ログの秘密の出力、監査ログのハッシュの連鎖の検証の失敗、個別の runbook のない呼び出しのアラート全部（[README.md](README.md) の 4 節）
- 最終確認日: 2026-10-04

## 共通の進め方

| 重さ | 目安 | 例 |
| --- | --- | --- |
| SEV1 | 見てはいけない予定の中身が届いた疑い。多くの利用者で予定の読み書きが止まる。リマインダーが広く送られない | 応答の監査の不一致、リージョンの障害、時計の全停止 |
| SEV2 | SLO を大きく消費。時刻・写し・同期の正しさが崩れる。会議室の二重予約 | 変更のログの欠け、会議室の重なり 1 件、施行まで 24 時間を切った古い `tzdata_version` の行 |
| SEV3 | 利用者の影響が小さい・迂回できる | 検索の更新の遅れ、ICS の購読の取得の失敗 |

1. インシデントの指揮者（IC）を決め、チャンネルを作り、時刻を記録し始める。
2. 影響の範囲（経路、テナントの数、利用者の数、期間）を決める。
3. 直前の変更を確かめる：デプロイ、フラグ（`release.*`・`ops.*`）、マイグレーション、Web の資産の段階、AppConfig の `tzdata.active_version`。疑わしければ [deploy-and-rollback.md](deploy-and-rollback.md) で戻す。展開・時刻・権限の不具合はフラグでなく前のイメージへ戻す（[README.md](README.md) の 3 節）。
4. 被害を止める → 原因を取り除く → 回復を確かめる、の順に進める。
5. 告知はステータスページで。権限の漏れと個人データの疑いは、法務と相談してから文面を決める（漏えい等の報告の要否は法務の L1）。
6. 調べるのは、中身と個人データを含まないログ・メトリクス・トレース・業務の記録（ID、数、理由のコード）だけ。予定の中身を見る必要があれば、顧客の明示の依頼（サポートのチケット）を確かめ、JIT（1 時間、2 人の承認）で入り、プラットフォームの監査に残す（[security.md](../architecture/security.md) の 8 節）。
7. エージェントは本番に経路を持たない。調査の結果（ID と数）を人から受け取り、`changes/` の新しい `intent.md` の草案を作る。

## 場面 1：予定の読み書きの SLO・書き込みの遅れ

### 症状

バーンレートのアラート。書き込みの p99 が 1 秒を 10 分超える。

### 確認

1. 経路（API・CalDAV・予約ページ）ごとの 5xx と時間の分布。CloudFront と `alb-dav` のどちらで出ているか。
2. Aurora の writer の CPU、ロックの待ち、`lock_timeout` の失敗。上位 50 のカレンダーのロックの待ち（`top_calendar_*`）。1 つのカレンダーに集中していれば `calendar-lock-contention.md`（予定）の内容で、`origin` ごとの枠を見る。
3. tzdb の再計算・大きな取り込み・方針の変更の一括の流れが同時に走っていないか（`maintenance`・`import` の枠の使用）。

### 対処

1. 背景の処理を絞る：`ops.tzdata_recompute_rate` を下げる、`ops.calendar_write_budget.maintenance`・`.import` を下げる。
2. 直前の変更が原因なら戻す。
3. writer の CPU が足りなければ、reader に逃がせる読み出し（照合のジョブ）を止める。writer の大きさを上げるのは計画作業にする。

## 場面 2：変更のログの欠け（`change_seq_gap_total`）

### 症状

あるカレンダーの `calendar_changes` の `seq` が連続していない。

### 影響

差分の同期で、そのカレンダーの変更がクライアントに届かない恐れ（NFR-010）。SEV2。

### 確認

1. 欠けたカレンダーと `seq` の範囲、その時刻の書き込みの経路（`origin`）とデプロイ。
2. `packages/writer` を通らない書き込みが DB の権限で拒否されているか（拒否の記録）。拒否されずに通った書き込みがあれば、そのロールを止める。
3. 分割を落とすジョブ（30 日）が、`floor_seq` を上げる前に分割を落としていないか。

### 対処

1. 欠けの範囲を含むトークンを 410 にするため、そのカレンダーの `epoch` を上げる（全クライアントが取り直す。番号の意味が変わるのを防ぐ）。
2. 原因の経路を止め、直すまで再開しない。
3. 直す変更に、PROP-SYNC-001（差分と全件の一致）の失敗のシードを回帰テストとして足す。

## 場面 3：SLI の集計の欠け

### 症状

`slo-aggregator` の出力が 5 分ない。SLO のダッシュボードが「データなし」。

### 確認と対処

1. `worker-slo-aggregator` のタスクとキュー、保守用のスキーマの業務の記録（`reminder_deliveries`・`itip_deliveries` など）への読み出しの権限（[ADR-0004](../decisions/0004-tenancy-and-rls.md) の X9）。
2. 集計を再開したら、欠けた時間の記録を後から集め直す（記録は全件あるので、SLI は後から正しく出せる）。
3. 欠けの間は、合成監視（[observability.md](../architecture/observability.md) の 6 節）で SLO を代わりに見る。

## 場面 4：秘密の出力・監査ログの連鎖の失敗

### 症状

ログの走査が `<brand>_ap_` などの接頭辞やメールアドレスの形を見つけた。監査ログのハッシュの連鎖の日次の検証が合わない。

### 確認と対処

1. 秘密の出力：出したサービスと版を特定し、ログの該当のストリームの読み出しを止め、出た秘密の種類を `credential-compromise.md`（予定）の手順で取り消す。直すまで、そのログの出力を止める。
2. 監査の連鎖：合わない日とテナントを特定し、log-archive の Object Lock の写しと Aurora の行を比べる。改ざんの疑いはセキュリティの担当へ上げる（SEV2）。

## エスカレーション

- SEV1：Ops の責任者、テックリード、セキュリティの担当、PM を 15 分以内に呼ぶ。権限の漏れは法務へ。
- リージョンの障害：[disaster-recovery.md](disaster-recovery.md)。切り替えの判断は IC と Ops の責任者だけ。
- tzdb・時刻の誤り：[tzdb-update.md](tzdb-update.md)。

## 事後

- 調査結果を `changes/` の新しい `intent.md` として起票する（Maintain 段）。中身と個人データを書かない。
- この手順で足りなかったことを、ここか個別の runbook に反映する。
