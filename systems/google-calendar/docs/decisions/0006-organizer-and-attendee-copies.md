# ADR-0006: 参加者ごとに写しを持ち、主催者の写しを正にする。本システムの中の参加者にも内部の iTIP のメッセージで配り、外部の参加者には同じ意味を iMIP で送る

## Context

1 つの会議には、主催者と参加者がいる。参加者は 3 種類である。

- 本システムの中の人（同じ組織、他の組織、個人のアカウント）
- 外部の人（本家・Outlook・Apple のカレンダーなどを使い、メールで招待を受ける）
- 会議室・設備（組織のディレクトリにあり、自動で承諾するか、管理者が承認する）

参加者は、同じ会議に対して、共有の項目（時刻、場所、参加者、繰り返し）と、自分だけの項目（出欠、リマインダー、色、空き・予定ありの表示）を持つ。主催者が変えた共有の項目は、全員に届く必要がある。参加者の出欠は、主催者に届く必要がある。

外部とのやりとりは、iTIP（RFC 5546）の意味（`REQUEST`・`REPLY`・`CANCEL` と、`SEQUENCE`・`DTSTAMP` による新旧の判定）を、iMIP（RFC 6047）でメールに載せる。

本家の API は、出欠を参加者ごとの `responseStatus`（`needsAction`・`declined`・`tentative`・`accepted`）で持つ（[Events resource](https://developers.google.com/workspace/calendar/api/v3/reference/events)、2026-10-04 に確認）。本家が参加者ごとに写しを持つかどうかの内部の形は、公開の資料にない（未検証）。グループの招待では、参加者の一覧がグループの変更に合わせて未来の予定で更新され、200 人を超える予定では 24 時間以内に反映される（[Invite groups to calendar events](https://support.google.com/calendar/answer/172013)、2026-10-04 に確認）。

テナントは RLS で分かれ（[ADR-0004](0004-tenancy-and-rls.md)）、S2 ではテナントごとに DB のクラスタが分かれる（[architecture/README.md](../architecture/README.md) の 2 節）。

## Options

1. **参加者ごとに写し（別の予定オブジェクト）を持ち、主催者の写しを正にする。** 本システムの中の参加者にも、内部の iTIP のメッセージで配る
2. 1 つの予定を全員で共有し、参加者ごとの項目を別の表に持つ
3. 本システムの中は 2 にし、外部の参加者にだけ iMIP を送る

## Decision

1 を採用する。

### 写し

- **主催者の写し**：主催者のカレンダーの予定オブジェクト。共有の項目の唯一の正本。参加者の一覧と、参加者ごとの出欠（`PARTSTAT`）、返事のコメントを持つ。
- **参加者の写し**：参加者の主のカレンダー（会議室なら会議室のカレンダー）の、同じ UID の別の予定オブジェクト。参加者のテナントに置く。
  - 共有の項目は、主催者の写しから届いたメッセージでだけ変える。参加者の写しに、共有の項目を直接書く API・CalDAV の要求は拒否する（403。CalDAV では RFC 6638 の `CALDAV:allowed-attendee-scheduling-object-change` の前提の違反として返す。sync-and-caldav の領域）。
  - 自分だけの項目（自分の出欠、リマインダー、色、`transparency`、自分から見た公開範囲）は、参加者が書ける。
  - 主催者の写しのバージョン（`organizer_sequence`、`organizer_version`）を持つ。
- **同じテナントの中でも写しを分ける。** 主催者と参加者が同じ組織でも、経路を 1 つにして、テナントをまたぐときと同じ処理で確かめる。

### 内部の iTIP のメッセージ

- 主催者の写しの変更は、`packages/writer` が、変更と同じトランザクションで、受け手ごとのメッセージ（`REQUEST`・`CANCEL`）を outbox に書く。参加者の返事は `REPLY` を書く。
- `SEQUENCE` は、RFC 5546 の 2.1.4 節が求める項目（DTSTART・DTEND・DURATION・RRULE・RDATE・EXDATE・STATUS。本システムでは TZID の変更も含める）に、場所の変更と参加者の削除を足した変更で上げる。出欠の変更だけでは上げない（一覧の正本は [ADR-0014](0014-itip-state-transfer-and-sequence.md)）。

> 2026-10-04 の注記：最初の設計の一覧は、RFC 5546 の 2.1.4 節が MUST とする DURATION と STATUS を欠いていた。[ADR-0014](0014-itip-state-transfer-and-sequence.md) に合わせて足した。
- `itip-delivery` が、受け手のテナントのコンテキストで、受け手の写しに当てる。当てる規則は iTIP と同じ。
  - 手元の写しより古いメッセージは捨てる。重複は同じ規則で 1 回だけ効く。新旧の鍵は、内部では `(SEQUENCE, 主催者のバージョン)`、外部（iMIP）では RFC 5546 の 2.1.5 節の `(SEQUENCE, DTSTAMP)` にする（[ADR-0014](0014-itip-state-transfer-and-sequence.md)。時計のずれで同点・逆転が起きないよう、内部は主催者のバージョンで決める）。
  - `REQUEST` は、回の単位（`RECURRENCE-ID` つき）と系列の単位の両方を受ける。
  - `REPLY` は、主催者の写しの、その参加者の `PARTSTAT` だけを変える。返事の `DTSTAMP` が手元より古ければ捨てる。
- 他の参加者の出欠の一覧は、主催者の写しが変わるたびではなく、受け手ごとに 30 秒にまとめて配る。出欠の一覧の遅れは NFR-002 の対象にしない。
- 配送は、受け手ごとに並行にし、受け手の写しの書き込みは受け手のカレンダーの `change_seq` を振る（[ADR-0005](0005-change-log-and-sync-tokens.md)）。S2 でテナントのクラスタが分かれても、メッセージは SQS で運ぶので同じ形で動く。
- **照合のジョブ**：毎日、本システムの中の参加者の写しのバージョンを、主催者の写しのバージョンと比べ、古いものに `REQUEST` を送り直す。食い違いの数を監視する（NFR-002 の補い）。

### 参加者の種類ごとの扱い

| 参加者 | 写し | 配送 | 出欠 |
| --- | --- | --- | --- |
| 本システムの中の人 | 参加者のテナントの主のカレンダー | 内部の iTIP のメッセージ | 写しで返事し、`REPLY` で主催者の写しへ |
| 外部の人 | 持たない | iMIP（SES）。`METHOD:REQUEST`・`CANCEL` の ICS をメールに付ける | iMIP の `REPLY` を `imip-inbound` が受け、返事の照合の鍵と送信元の認証を確かめてから当てる（invitations-and-itip の領域） |
| 会議室・設備 | 会議室のカレンダー | 予約の行（排他の制約）は主催者の書き込みのトランザクションで書く。会議室のカレンダーの写しは内部の iTIP で書く | 自動の承諾は、排他の制約の結果で決める。管理者の承認の会議室は `needsAction` のまま（rooms-and-resources の領域） |
| グループ | グループの項目を主催者の写しに残し、メンバーごとに写しを作る | メンバーに展開して内部の iTIP か iMIP | メンバーごと。グループの変更は未来の予定にだけ反映する |

- 外部の主催者から iMIP で招待を受けたときは、本システムの中の参加者の写しを作り、主催者は外部（`mailto:`）として持つ。返事は iMIP の `REPLY` で送る。
- 参加者の権限（他の参加者を見る・招待する・変更する）で参加者が共有の項目を変えるときは、主催者の写しへの書き込みとして `can()` で確かめ、主催者の写しを変えてから全員へ配る。参加者の写しを先に変えない。
- 参加者が自分の写しを消したら、辞退の `REPLY` を送り、写しを非表示にする（取り消しではない）。主催者の写しを消したら、全員へ `CANCEL` を送る。

### 他の案を選ばなかった理由

- **2（1 つの予定を共有）**：参加者のテナントから、主催者のテナントの行を読むことになり、テナントの分離（[ADR-0004](0004-tenancy-and-rls.md)）と S2 のクラスタの分割に合わない。参加者のカレンダーの変更のログ（[ADR-0005](0005-change-log-and-sync-tokens.md)）に、他のテナントの変更を載せる仕組みが別に要る。CalDAV で参加者のカレンダーに予定オブジェクトとして見せるときに、写しが要る。
- **3（中だけ共有、外は iMIP）**：外部との経路と中の経路で、新旧の判定・例外・「これ以降」の扱いが 2 通りになる。片方の誤りがもう片方の試験で見つからない。

## Consequences

- 良くなること：
  - 本システムの中の参加者と外部の参加者を、同じ iTIP の意味で扱える。外部との往復の試験が、中の配送の試験にもなる。
  - 参加者の写しが参加者のテナントにあるので、RLS・変更のログ・CalDAV・リマインダーが、写しをふつうの予定として扱える。
  - S2 のクラスタの分割をまたいで、同じ形で動く。
- 引き受けるコスト：
  - 参加者の数だけ写しを書く。大きな招待（グループで数千人）では、1 回の変更で数千の書き込みになる。配送のバッチと書き込みの枠で抑え、200 人を超える分の伝播を p99 60 秒にする（NFR-002）。
  - 写しが主催者の写しに追いつくまでの間、食い違いが見える。照合のジョブで直す。
  - 「これ以降」の分割（[ADR-0003](0003-recurrence-storage-and-expansion.md)）では、2 つの系列分のメッセージを送る。

## Confirmation

- 性質ベーステスト：任意の主催者の変更・参加者の返事の列を、任意の順序の入れ替え・重複・遅延で配ったとき、静かになった後、本システムの中のすべての参加者の写しの共有の項目が主催者の写しと一致し、主催者の写しの各参加者の `PARTSTAT` が、その参加者の最後の返事と一致する。
- 性質ベーステスト：同じ性質を、外部の参加者を模した iMIP の往復（メールの遅延・重複・欠け）を含めて確かめる。
- 結合テスト：参加者の写しの共有の項目を書き換える API・CalDAV の要求が拒否される。
- 相互運用の試験：本家・Outlook・Apple のカレンダーとの招待・返事・取り消し・「これ以降」の往復（[quality.md](../quality.md)）。
- 本番：照合のジョブの食い違いの数、配送の遅れ（主催者のコミットから参加者の写しのコミットまで）を監視する。
