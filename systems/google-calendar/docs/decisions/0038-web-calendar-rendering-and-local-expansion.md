# ADR-0038: Web の画面は、予定オブジェクトを窓つきの差分の同期で持ち、回は手元の `expand()` で作る。tzdb はサーバーのバージョンのゾーンのデータをバージョンつきの URL から取る。重なる予定は、日ごとの重なりの塊に貪欲に列を割り当てて右へ広げる決定的な配置で描く

## Context

Web の画面（日・週・月・予定リスト）は、複数のカレンダーの繰り返しの予定を、見る人のタイムゾーンで並べる。次の条件がある。

- 同じ予定の同じ回は、画面・API・CalDAV で同じ瞬間に出る（NFR-009）。展開は `packages/recurrence` の `expand()` だけで行う（[ADR-0001](0001-platform-and-stack.md)、[ADR-0003](0003-recurrence-storage-and-expansion.md)）。
- [ADR-0005](0005-change-log-and-sync-tokens.md) は、差分の同期のトークンを予定オブジェクトの単位にし、回の一覧はトークンを持たない範囲の問い合わせにして、Web のクライアントが手元で `expand` すると決めた。
- [ADR-0002](0002-time-representation.md) は、クライアントの tzdb のバージョンが古いときは、サーバーの派生の値で表示し、自分で計算し直さないと決めた。一方で、手元で `expand` するには、規則の回を UTC に解く tzdb のデータが要る。
- 週の表示では、同じ時間帯に多くの予定が重なる（会議の多い管理職で、同じ 1 時間に 5〜10 件）。配置が描くたびに変わると、ドラッグの最中に予定が跳ねる。
- ドラッグでの移動は、入力から描画まで p95 100ms（NFR-001）。

本家の画面の重なりの配置の規則は、公開の資料にない（**未検証**。2026-10-04 に確認）。

## Options

データの取り方：

1. **予定オブジェクトを窓（表示の範囲と、前後 4 週の手元の範囲）で取り、カレンダーごとのトークンで差分を取り続ける。回は手元の `expand()` で作る**
2. 表示のたびに、サーバーが展開した回の一覧を取る
3. カレンダーの全部の予定オブジェクトを取り、手元に持つ

tzdb のバージョン：

- a. **API の応答の `tzdata_version` と同じバージョンのゾーンのデータを、バージョンつきの URL（`/tzdata/<version>/<zone>`）から取る**
- b. Web の資産に tzdb を同梱し、資産のバージョンで決める
- c. バージョンが違えばサーバーの回の一覧に切り替える

重なりの配置：

- x. **日ごとに重なりの塊を作り、開始の順に最初に空いた列へ割り当て、右の空いた列へ広げる。並びの同点は `(event_object_id, recurrence_id)` で決める**
- y. 重なる予定を等しい幅に分ける
- z. 重なる予定を少しずつずらして重ねる（カスケード）

## Decision

1・a・x を採用する。

### データ

- 表示を開いたとき、見えるカレンダーごとに、まず今のトークン（その時点の `change_seq`。`POST /v1/sync` の `tokensOnly`）を取り、次に窓 `[表示の始まり − 4 週, 表示の終わり + 4 週]` に回が触れる予定オブジェクトを範囲の問い合わせで取る。トークンを先に取るので、間の変更は次の差分で重ねて届き、バージョンの比べで捨てる。差分の同期のトークンを `timeMin`・`timeMax` と一緒に使わない（[ADR-0026](0026-public-rest-api-shape.md)）。
- 以後は、Realtime の合図と 5 分ごとの確かめで、複数のカレンダーのトークンを `POST /v1/sync` の 1 回の要求で送って差分を取る（[api-and-push.md](../architecture/api-and-push.md) の 4.6 節）。差分のうち、窓に回が触れない予定オブジェクトは捨てる。窓の外へ移ると、もう一度範囲の問い合わせで取る。
- 回は `packages/recurrence` の `expand(object, window, tzdata)` で作る。画面の中で RRULE を解釈しない。
- 書き込みはオンラインのときだけ（[ADR-0039](0039-offline-read-cache-and-local-data.md)）。楽観的に描き、応答の予定オブジェクトで置き換える。412（バージョンの衝突）は、最新を取り直して利用者に示す。

### tzdb のバージョン

- `packages/tzdata` のゾーンのデータを、バージョンごとに変わらない URL `https://calendar.<brand>.<domain>/tzdata/<version>/<zone>.bin`（1 ゾーン 5 KiB 以下、`Cache-Control: immutable`）で配る（infrastructure.md の 2 節）。
- クライアントは、API の応答の `tzdata_version` と同じバージョンのゾーンを取り、そのバージョンで `expand` と `toLocal` を行う。手元のバージョンとサーバーのバージョンが違う間は、古いバージョンのデータで計算し直さない（[ADR-0002](0002-time-representation.md) の規則を、データの取り直しで満たす）。
- 取れないとき、オンラインなら範囲の問い合わせ（`singleEvents=true`）のサーバーの派生の値で描く（[sync-and-caldav.md](../architecture/sync-and-caldav.md) の 5 節）。オフラインで、まだ持っていないバージョンなら、手元にある派生の値（予定オブジェクトの `start_utc`・`end_utc` と、窓の中の上書き）だけで描き、繰り返しの回は「時刻を確かめられない」の印を付けて描く。
- tzdb のバージョンを上げても、Web の資産のデプロイは要らない（[ADR-0049](0049-tzdata-rollout-and-schema-change-ordering.md)）。

### 重なりの配置

- 時刻つきの予定を、表示のタイムゾーンの日の列ごとに、日をまたぐものは日ごとの区切りに分けて置く。終日の予定は、上の終日の帯に日付で置く（UTC に戻さない。[time-zones-and-holidays.md](../architecture/time-zones-and-holidays.md) の 5.2 節）。
- 配置は次の決定的な手順にする。
  1. 区切りを `(開始, −長さ, event_object_id, recurrence_id)` の順に並べる。15 分より短いものは、重なりの判定で 15 分として扱う。
  2. 重なりで連なる区切りを 1 つの塊にする。
  3. 塊の中で、開始の順に、終わりが自分の開始以前の最初の列へ入れる。なければ新しい列を作る。
  4. 塊の幅を列の数で分け、各区切りを、右の列で自分と重なる区切りがないところまで広げる。
  5. 列が画面の幅で 6 を超えたら（スマートフォンの幅では 3）、超えた分を「+N」にまとめる。
- 月の表示は、週の行ごとに、複数日の予定と終日の予定を最も低い空いた段に置き、段の数がセルの高さを超えたら「他 N 件」にする。
- ドラッグの最中は、動かしている区切り以外の配置を固定し、離したときに計算し直す。

### 他の案を選ばなかった理由

- **2（サーバーの回の一覧）**：表示を切り替えるたびに往復が要り、オフラインの閲覧（[ADR-0039](0039-offline-read-cache-and-local-data.md)）で回を作れない。[ADR-0005](0005-change-log-and-sync-tokens.md) の経路の決定にも合わない。
- **3（全部を取る）**：大きな共有のカレンダー（会議室、部署）は数万の予定オブジェクトを持つ。初めの読み込みが重い。
- **b（同梱）**：tzdb のバージョンを上げるたびに Web の資産の段階的な配布（4 時間 × 4 段）を待つことになり、バージョンの混ざる時間が長い。
- **c（サーバーに切り替え）**：バージョンが違う間、画面が往復に頼り、オフラインで描けない。
- **y（等しい幅）**：短い予定が隣の空いた場所を使えず、読みにくい。
- **z（カスケード）**：重なりが多いと下の予定をつかめない。ドラッグの対象を選びにくい。

## Consequences

- 良くなること：
  - 画面・API・CalDAV が同じ `expand()` と同じバージョンの tzdb で回を作る。
  - tzdb のバージョンの採用が、Web の資産の配布を待たない。
  - 同じ入力からは同じ配置になり、試験で比べられる。
- 引き受けるコスト：
  - トークンだけを取る口が要る。統合の工程で `POST /v1/sync` の `tokensOnly` として足した（[api-and-push.md](../architecture/api-and-push.md) の 4.6 節、2026-10-04）。
  - 窓の外の予定オブジェクトの差分も受けて捨てるので、大きな共有のカレンダーでは差分が無駄になる。1 回の差分が 1,000 件を超えるカレンダーは、窓の範囲の問い合わせを取り直す。
  - 6 列を超える重なりは「+N」になり、一目で全部は見えない。

## Confirmation

- 性質ベーステスト（PROP-CLI-001）：任意の予定オブジェクトと窓で、画面のデータ層が作る回の集合が、サーバーの範囲の問い合わせ（展開した回）と一致する。
- 性質ベーステスト（PROP-CLI-002）：任意の区切りの集合で、配置は入力の順に依らず同じで、同じ列の区切りは重ならず、どの区切りも幅が 0 にならない。
- 結合テスト：API の `tzdata_version` を新しいバージョンに変えると、クライアントがそのバージョンのゾーンを取り、古いバージョンで計算し直さない。
- lint：`apps/web` で RRULE の文字列を分解するコード、`Intl.DateTimeFormat` の `timeZone` の指定を禁止する（[ADR-0001](0001-platform-and-stack.md)）。
- ベンチマーク：週の表示（カレンダー 10、予定 300）の配置の計算 16ms 以下、ドラッグの入力から描画まで p95 100ms（[clients.md](../architecture/clients.md) の 9 節）。
