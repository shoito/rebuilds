# ADR-0036: 組織のドメインは DNS の TXT で確かめて毎日確かめ直す。SSO はドメインごとに SAML 2.0 か OIDC の IdP を 1 つ持ち、SP 起点だけ・署名を必須にし、必須にしても特権の管理者はパスキーで入れる。確認したドメインの個人のアカウントは本人の同意で組織へ移す。SCIM 2.0 は SSO の後に足す

## Context

[intent.md](../intent.md) は、組織（ドメインを持つテナント）、SSO（SAML・OIDC）、SCIM での利用者の同期を MVP に含める。[ADR-0004](0004-tenancy-and-rls.md) は、個人が後で組織に入るときにテナントを移す手続きを通すと決め、ACL の主体に「ドメイン（組織の全員）」を置いた。[ADR-0035](0035-accounts-auth-library-and-credentials.md) は、1 つのアカウントを 1 つのテナントに結ぶと決めた。

決めることは次である。

- ドメインの持ち主の確かめ方と、確かめが切れたときの扱い。
- SSO の受け方。SAML の応答の偽装・再送、IdP の障害での締め出し。
- 組織のドメインのメールアドレスで、すでに個人のアカウントを持つ人の扱い。データ（予定、他のテナントの参加者の写しの参照）が個人のテナントにある。
- SCIM をいつ・どこまで持つか。

本家のドメインの確認・SSO・SCIM の細部は、カレンダーの資料の範囲では確かめていない（未検証）。他の題材（Slack の identity-and-access.md）は、`@better-auth/sso` で OIDC と SAML を扱い、`InResponseTo` を検査し、IdP 起点を受けないと決めた。

## Options

ドメインの確認：

1. **DNS の TXT。毎日確かめ直す**
2. ドメインのメールアドレスへのメールの確認
3. Web のファイル（`/.well-known/…`）

個人のアカウント：

- a. **本人の同意で組織へ移す（データを移し、他のテナントの写しの参照を付け替える）。同意しなければ個人のまま**
- b. 組織が確認したら、自動で組織へ移す
- c. 移さない。個人のアカウントのメールアドレスを変えさせる

## Decision

1 と a を採用する。詳細は [accounts-and-orgs.md](../architecture/accounts-and-orgs.md) の 6〜8・12 節。

- **ドメイン**：`TXT "<brand>-domain-verification=<token>"`（128 ビット）。足した直後は 5 分ごとに 14 日まで、確認の後は毎日、DNSSEC の検証つきで確かめる。1 つのドメインは 1 つの組織だけが `verified`。サブドメインは追加の確認なし。7 日続けて見つからなければ `lapsed` にし、新しい JIT と移りの案内を止める。既存の利用者と SSO のログインは続ける。
- **SSO**：`@better-auth/sso`（SAML は samlify）。ドメインごとに IdP を 1 つ。SAML は SP 起点だけ、応答か主張の署名を必須、`InResponseTo`・`Audience`・`NotOnOrAfter`（ずれ 3 分）・`Destination`。OIDC は PKCE と `nonce`、`email_verified`。確認したドメインのメールアドレスだけ。IdP の属性で管理の役割を決めない。Single Logout は持たない。
- **ログインの規則**（DT-ACCT-001）：SSO を必須にしたら他の手段を拒むが、`super_admin` はパスキーで入れる（監査ログに残す）。JIT は既定で有効。
- **個人から組織へ**：組織がドメインを確認したら、同じドメインの個人のアカウントに「移るか、メールアドレスを変えるか」を案内する。同意したら `tenant-move` のジョブが、カレンダーごとのトランザクションで `tenant_id` を変え（ID は変えない）、そのカレンダーのトークンを 410 にする。他のテナントの参加者の写しへ新しい `organizer_ref` の `REQUEST`（`SEQUENCE` は上げない）を送り、古い参照への `REPLY` を 90 日回す。共有の ACL に組織の方針を当て直す。
- **SCIM**：SSO の後に、`release.scim` のフラグの裏で足す。`/scim/v2/<org_id>/` の Users・Groups、`<brand>_scim_` の Bearer。`active=false` は利用者の停止、削除も停止にする（引き継ぎは管理者が画面で）。1 回の要求で組織の 10% を超える停止は管理者の確認まで保留にする。

### 他の案を選ばなかった理由

- **2（メールの確認）**：メールアドレスの持ち主であって、ドメインの持ち主の確かめにならない。
- **3（Web のファイル）**：メールのドメインと Web のホストが別の組織が多い。
- **b（自動で移す）**：個人の予定（家族、副業）が本人の同意なしに組織の管理の下に入る（法務の L1・L8 の論点）。
- **c（移さない）**：同じ人が個人と組織の 2 つの主のカレンダーに分かれ、招待の宛先が割れる。

## Consequences

- 良くなること：
  - ドメインの持ち主だけが SSO と JIT を使える。確かめが切れても利用者を締め出さない。
  - SAML の偽装・再送の主な経路を閉じる。IdP の障害でも特権の管理者は入れる。
  - 個人の予定は、本人の同意なしに組織へ移らない。
- 引き受けるコスト：
  - `tenant-move` は、他のテナントの写しの参照の付け替えと、古い参照の回しを要する大きな処理である。E4 で試験を厚くする（PROP-ACCT-002）。
  - 同意しない人は、組織のドメインのメールアドレスのまま個人で残り、SSO を使えない。
  - SCIM は SSO より後になり、それまで利用者の作成は JIT と管理者の招待に頼る（[intent.md](../intent.md) は SCIM を MVP に含める。MVP の中の後段で出す）。
  - 部品の告知（SSO・SCIM の部品に Critical の告知があった。Linear の accounts-and-auth.md の 2.2 節）を追う。

## Confirmation

- 表駆動テスト：DT-ACCT-001（ログインの規則）、DT-ACCT-004（ドメインの状態）。
- 性質ベーステスト：PROP-ACCT-002（移りの前後で予定の集合と中身が同じ。他のテナントの写しが新しい主催者の写しに追いつく）。
- 結合テスト：SAML の IdP 起点・署名なし・`InResponseTo` の再利用の拒否、OIDC の `email_verified` が偽の拒否、TXT の確かめ、SCIM の `active=false` から停止、10% を超える停止の保留。
