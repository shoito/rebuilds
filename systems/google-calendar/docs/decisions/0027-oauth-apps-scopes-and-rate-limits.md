# ADR-0027: OAuth 2.0 は認可コードと PKCE（S256 を必須）で、アクセストークン 1 時間、リフレッシュトークンは使うたびに入れ替えて再利用で一式を取り消す。範囲は 4 つ。組織はアプリの認可を絞れる。レート制限は（アプリ, 利用者）1 分 600・（アプリ, テナント）1 分 10,000・利用者の書き込み 1 分 120 で、超えたら 429

## Context

[intent.md](../intent.md) は、公開 API を OAuth 2.0 で守ると決めた。[architecture/README.md](../architecture/README.md) の 6 節は、CalDAV の認証に OAuth 2.0 の Bearer とアプリ用のパスワードを使うと決めた。公開 API は社内のツール、予約・勤怠のシステムから使われ、CalDAV のクライアントも Bearer を使う。

決めることは次である。

- フローとトークンの寿命、入れ替え、取り消し。
- 範囲（scope）の分け方と、`can()` との重ね方（[ADR-0004](0004-tenancy-and-rls.md)）。
- 組織の管理者がアプリを絞る方法。
- レート制限の単位と値、超えたときの応答。1 カレンダーの書き込みは 1 秒 50 件が上限（[ADR-0005](0005-change-log-and-sync-tokens.md)）。

本家の割り当ては、プロジェクトごと 1 分 10,000、利用者ごと・プロジェクトごと 1 分 600 で、超えると 403 か 429 を返す（[Manage quotas](https://developers.google.com/workspace/calendar/api/guides/quota)、2026-10-04 に確認）。本家のトークンの寿命は確かめていない（未検証）。他の題材（Linear の ADR-0042）は、アクセストークン 24 時間、PKCE 必須、リフレッシュトークンの入れ替えと再利用の検出を決めた。

## Options

アクセストークンの寿命：

1. **1 時間**
2. 24 時間（Linear の題材と同じ）

範囲：

- a. **読み出し・予定・空き時間・管理の 4 つ**
- b. 資源ごとの細かい範囲（カレンダー、予定、ACL、設定、空き時間で読み書きを分ける）

レート制限の単位：

- x. **（アプリ, 利用者）と（アプリ, テナント）と、利用者の書き込みの合計**
- y. アプリだけ

## Decision

1、a、x を採用する。詳細は [api-and-push.md](../architecture/api-and-push.md) の 5・6 節。

- 認可 `https://auth.<brand>.<domain>/oauth/authorize`、トークン `…/oauth/token`。`response_type=code`、`state`、`code_challenge`（S256）を必須にし、戻りの URL は完全一致。コードは 60 秒・1 回限り。
- アクセストークン 1 時間。リフレッシュトークンは使うたびに入れ替え、入れ替えた古いものの再利用で同じ認可の一式を取り消す。90 日使わなければ切れる。RFC 7009 の取り消し。
- トークンは `<brand>_oat_`・`<brand>_ort_`・`<brand>_ocs_` の接頭辞とチェックサムの形で、SHA-256 だけを保存する。確かめは Valkey に 60 秒持ち、取り消しは 60 秒以内に効く。
- アプリは組織のアプリと個人のアプリ。他の組織へ配る公開のアプリは MVP の後。
- 範囲は `calendar.read`・`calendar.events`・`calendar.freebusy`・`calendar.manage`。許すかは `can() ∧ scopeAllows()` で、範囲の表を `packages/policy` に置く。管理の API は OAuth のアプリに開かない。
- 組織の `oauth_apps_policy`：`all`・`allowlist`・`none`。狭めたら方針の外のトークンを取り消し、Webhook の経路を止める。
- レート制限：（アプリ, 利用者）1 分 600、（アプリ, テナント）1 分 10,000、利用者の書き込みの合計 1 分 120、テナントの合計 1 分 30,000。Valkey のトークンバケット（落ちたらタスクのメモリーの厳しめの近似）。超えたら 429 と `Retry-After`。1 カレンダーの書き込みの上限は 429 `calendarWriteRateExceeded`。

### 他の案を選ばなかった理由

- **2（24 時間）**：トークンは CalDAV のクライアントの設定や社内のシステムに置かれ、漏れたときの影響の時間を短くしたい。リフレッシュの往復は 1 時間に 1 回で軽い。
- **b（細かい範囲）**：利用者が認可の画面で判断しにくい。カレンダーの連携の多くは「読む」か「予定を書く」かで足りる。
- **y（アプリだけ）**：1 つの組織の一括の処理が、同じアプリを使う他の組織の枠を食う。

## Consequences

- 良くなること：
  - 漏れたトークンの効く時間が短く、リフレッシュトークンの盗用を検出できる。
  - 組織が、従業員のカレンダーにつなぐアプリを絞れる。
  - 1 つの組織・利用者の大量の要求が、他を止めない。
- 引き受けるコスト：
  - アクセストークンの寿命が本家と違う可能性がある（本家の値は未検証）。連携の作り手はリフレッシュを実装する必要がある。
  - 本家は 403 と 429 の両方を返すが、本システムは 429 だけなので、本家向けの再試行の部品の一部は読み替えが要る。
  - 方針の変更で、利用者の連携が突然止まる。管理の画面で影響する利用者の数を示してから変える。

## Confirmation

- 表駆動テスト：DT-API-001（範囲 × 入口）。
- 結合テスト：PKCE のない要求の拒否、戻りの URL の不一致の拒否、リフレッシュトークンの再利用での一式の取り消し、方針の変更でのトークンの取り消し、レート制限の 429 と `Retry-After`。
- 負荷（E12）：（アプリ, 利用者）とテナントの合計の上限まで。
