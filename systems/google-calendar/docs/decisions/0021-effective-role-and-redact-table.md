# ADR-0021: 実際のロールは持ち主、ACL の行と暗黙の行の最大、組織の外への上限の最小の順で求める。`redact()` は「全体・参加者を除く全体・区間だけ・返さない」の 4 段で返し、区間だけの形は時刻の構造と見る人ごとの不透明な ID だけを持つ。公開範囲はマスターだけが持ち、テナントをまたぐ共有のカレンダーへの書き込みはカレンダーのテナントで `packages/writer` を通す

## Context

[ADR-0004](0004-tenancy-and-rls.md) は、5 つの ACL のロール、4 つの公開範囲、`can()` と `redact()` を 1 つのモジュールにすること、`redact()` の決定表の骨格（6 行）を決め、行と条件の全体をこの領域に残した。

決めることが残っている。

- **ロールの求め方**：利用者・グループ・ドメイン・公開の行が重なるとき、組織の方針の上限とどう組むか。本家の組織の外への共有の選択肢は、「空き時間だけ」から「カレンダーの管理を許す」まで 4 段ある（[Set Google Calendar sharing options](https://knowledge.workspace.google.com/admin/calendar/set-google-calendar-sharing-options)、2026-10-04 に確認）。
- **区間だけの形**：`reader` は `private` の予定を「見えるが詳細は隠す」（[Acl resource](https://developers.google.com/workspace/calendar/api/v3/reference/acl)、2026-10-04 に確認）。画面・CalDAV で予定の箱を描くには、何かの ID と時刻が要る。本当の ID を返すと、他の経路（検索、Webhook）の ID と結び付けて推測される。
- **公開範囲の単位**：本家は、繰り返しの 1 回の公開範囲を狭めると系列の全体に効く（[architecture/README.md](../architecture/README.md) の 1.4 節）。
- **テナントをまたぐ書き込み**：[ADR-0004](0004-tenancy-and-rls.md) は、テナントをまたぐ処理を、内部の iTIP の配送、空き時間の照会、共有されたカレンダーの読み出しの 3 つに限った。家族の個人のアカウントどうしの共有（それぞれ別の個人のテナント）や、組織の方針で外の人に変更を許した場合には、共有されたカレンダーへの書き込みが要る。

## Options

`redact()` の形：

1. **4 段（`FULL`・`FULL_NO_GUESTS`・`BUSY`・`NONE`）。`BUSY` は時刻の構造と不透明な ID**
2. 項目ごとに見せるかを決める（段を持たない）
3. 3 段（`FULL`・`BUSY`・`NONE`）。参加者を隠す設定は経路ごとに当てる

テナントをまたぐ書き込み：

- a. **読み出しと同じく、カレンダーのテナントのコンテキストで、専用のロールから `packages/writer` を通す**
- b. 認めない（組織の外・個人のテナントどうしの共有の上限を `reader` にする）
- c. 書き込みを、カレンダーのテナントへのメッセージにする（iTIP の `X-MODIFY` と同じ形）

## Decision

1 と a を採用する。詳細は [sharing-and-acl.md](../architecture/sharing-and-acl.md) の 4〜7 節。

- 実際のロール：持ち主なら `owner`。そうでなければ、一致する ACL の行（利用者、入れ子を含むグループ、ドメイン、公開）と暗黙の行（組織の中の共有の既定、会議室）の最大。見る人がカレンダーの組織の外なら、組織の外への上限との最小。ロールと効いた方針の組を `view_hash` にする（[ADR-0005](0005-change-log-and-sync-tokens.md)）。
- 組織の方針：組織の中の共有の既定（共有しない・空き時間だけ・すべて）、組織の外への上限（空き時間だけ・`reader`・`writer`・`owner`）、公開を許すか、ICS の秘密のアドレスを許すか。既定は「空き時間だけ」「空き時間だけ」「許さない」「許す」。
- `redact()` の決定表 DT-ACL-001（9 行）：`none` → `NONE`。持ち主以外が見る `hidden`・`cancelled` の写し → `NONE`。参加者 → `FULL`（参加者を隠す設定なら `FULL_NO_GUESTS`）。`owner`・`writer` → `FULL`。`reader` は `public` で `FULL`、`private` で `BUSY`。`free_busy_reader` は `transparent` で `NONE`、`opaque` で `BUSY`。管理者による閲覧は法務の L8 の後。
- `BUSY` は、開始・終了・TZID、RRULE・RDATE・EXDATE、上書きの時刻、`status` と、`HMAC(key, viewer_id || event_object_id)` の不透明な ID だけを持つ。
- 公開範囲は予定オブジェクトのマスターだけが持つ。1 回分への変更は系列に当てる。参加者の写しは自分の公開範囲を持てる。
- 外の主体が `writer` 以上を持つカレンダーへの書き込みは、カレンダーのテナントのコンテキストで、専用の DB のロール `shared_calendar_access` から `packages/writer` を通して行い、変更のログと outbox をカレンダーのテナントに書く。これは [ADR-0004](0004-tenancy-and-rls.md) の 3 つ目の処理（共有されたカレンダーの読み出し）を書き込みに広げる追補で、題材の `AGENTS.md` の規則（テナントをまたぐのは iTIP の配送と空き時間の照会だけ）の例外になる。テックリードの確認まで、`release.cross-tenant-shared-writes` のフラグの裏に置き、確認が得られなければ b に切り替える。

### 他の案を選ばなかった理由

- **2（項目ごと）**：経路ごとの削り方の組み合わせが増え、決定表で全部を確かめられない。
- **3（3 段）**：参加者を隠す設定を経路ごとに当てることになり、1 つの経路の漏れが漏えいになる（[ADR-0004](0004-tenancy-and-rls.md) の b を採らない理由と同じ）。
- **b（書き込みを認めない）**：家族の個人のアカウントどうしで予定を書き合う、本家にある使い方ができない（[intent.md](../intent.md) の個人の利用者）。
- **c（メッセージにする）**：書いた人の画面に、書き込みの結果がすぐに返らない。共有のカレンダーの書き込みは、参加者の写しと違って、そのカレンダーが正本なので、メッセージにする理由がない。

## Consequences

- 良くなること：
  - すべての経路が、同じ 4 段の形と同じ決定表を使う。
  - `BUSY` の ID から、他の経路の予定や他の見る人の画面と結び付けられない。
  - 個人のアカウントどうしの共有の書き込みができる。
- 引き受けるコスト：
  - `BUSY` で時刻の構造（RRULE）を返すので、系列の型から中身を推測される危険が残る。
  - テナントをまたぐ処理が 1 つ増え、監査の対象が広がる。[ADR-0004](0004-tenancy-and-rls.md) と題材の `AGENTS.md` との食い違いを、テックリードが確認するまで残す。
  - 組織の外への上限の既定を「空き時間だけ」にしたので、組織の外の人と予定を見せ合うには、管理者が方針を広げる必要がある。

## Confirmation

- 表駆動テスト：DT-ACL-001・002・003 を spec から読み込み、`packages/policy` と各経路で確かめる。
- 性質ベーステスト：PROP-ACL-001（中身の漏れなし、経路ごと）、PROP-ACL-002（ロールの単調）、PROP-ACL-003（取り消しの効き）、PROP-ACL-004（不透明な ID）、PROP-ACL-005（公開範囲は系列で 1 つ）。
- 結合テスト：テナントをまたぐ書き込みが、カレンダーのテナントの変更のログにだけ載る。
- 本番：応答の監査の不一致 0 件（NFR-008）。
