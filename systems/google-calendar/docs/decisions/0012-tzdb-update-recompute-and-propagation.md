# ADR-0012: tzdb の版の採用の後、会議室の予約の行を先に、次に施行の近い順に予定を計算し直す。版を上げて変更のログに載せるが `SEQUENCE` は上げない。外部の参加者には施行の後に回がある予定だけ同じ `SEQUENCE` の `REQUEST` を送り、会議室の重なりは「要確認」にする

## Context

[ADR-0002](0002-time-representation.md) は、壁時計の時刻＋TZID を正にし、tzdb の版を上げたら派生の UTC を計算し直すと決めた。次の 2 つはこの領域に残した。

- 計算し直しで会議室の予約が重なったときの扱い。
- 外部の参加者へ更新を送るか。

計算し直しには、次の性質がある。

- 予定の壁時計の時刻と TZID は変わらない。iTIP（RFC 5546 の 2.1.4 節）が `SEQUENCE` を上げるよう求める DTSTART・DTEND などのプロパティの値も変わらない。変わるのは、VTIMEZONE と、そこから求める UTC の瞬間である。
- 外部の参加者（CalDAV のクライアント、他社のカレンダー）は自分の tzdb を使う。相手の tzdb が新しければ何もしなくても合い、古ければ届いた VTIMEZONE を使うかどうかは相手次第である（未検証）。
- 影響の量は、変わったゾーンを使う予定の数で決まる。日本の利用者が主なので、多くの改正の影響は小さいが、`Asia/Tokyo` が変われば大半の予定が対象になる。
- 会議室の予約の行の排他の制約は、UTC の区間を比べる。計算し直しの途中は、新旧の版の区間が混ざる。

本家が tzdb の更新をどう扱うかは、公開の資料にない（未検証。2026-10-04 に確認）。

## Options

計算し直しの順序：

1. **会議室の予約の行を持つ予定を先に、次に施行の近い順**
2. テナントの順
3. 予定の作成の順

`SEQUENCE`：

- a. **上げない（同じ `SEQUENCE` の更新）**
- b. 上げる（日程の変更として扱う）

外部への知らせ：

- x. **施行の後に回がある予定だけ、同じ `SEQUENCE` の `REQUEST` を新しい VTIMEZONE つきで送る**
- y. 送らない
- z. 影響する予定のすべてに送る

会議室の重なり：

- p. **後から確定した予約を「要確認」にし、自動で辞退しない**
- q. 後から確定した予約を自動で辞退する

## Decision

1・a・x・p を採用する。詳細は [time-zones-and-holidays.md](../architecture/time-zones-and-holidays.md) の 6 節。

- `expander` の `tz-recompute` は、版の切り替えの完了を合図に、会議室の予約の行を持つ予定オブジェクトを先に、次に `changed_from` の近い順に処理する。
- 1 件ごとに `packages/writer` で、派生の値と `tzdata_version` を直し、版を上げ、索引・会議室の予約の行・リマインダー・`calendar_changes` を書く。`SEQUENCE` は上げない。
- 速さは全体 5,000 件/秒、1 テナント 500 件/秒まで。カレンダーの書き込みの上限を超えないよう、カレンダーごとに順に流す。
- 外部の参加者がいて、主催者の写しが本システムにあり、`changed_from` より後に回がある予定だけ、同じ `SEQUENCE` と新しい `DTSTAMP` の `REQUEST` を、新しい VTIMEZONE つきで送る。見積もりが 10 万通を超えたら Ops の承認を得てから送る。
- 本システムの中の参加者の写しには iTIP のメッセージを送らず、各テナントで同じジョブが計算し直す。
- 会議室の予約の行が重なったら、後から確定した（`accepted_at` が新しい）予約を「要確認」にし、主催者と会議室の管理者に知らせる（[ADR-0020](0020-room-approval-and-needs-review.md)）。

### 他の案を選ばなかった理由

- **2・3（テナント・作成の順）**：施行の近い改正の予定が、後回しになりうる。会議室の予約の行の新旧の版が混ざる時間が長くなる。
- **b（`SEQUENCE` を上げる）**：外部の参加者の出欠が戻り（RFC 5546 の 3.2.2.1 節の日程の変更）、全員に返事のやり直しを求める。壁時計の時刻は変わっていない。
- **y（送らない）**：tzdb が古く、届いた VTIMEZONE を使う相手（Outlook など。未検証）の時刻が、施行の後にずれたまま残る。
- **z（すべてに送る）**：施行の前に終わる予定にも送り、迷惑なメールになる。
- **q（自動で辞退）**：利用者の操作なしに、確定していた会議を外す。原因が本システムのデータの更新なので、人に判断を返す。

## Consequences

- 良くなること：
  - 施行の近い改正から直り、K2 の 24 時間に収まる見込み。
  - 外部の参加者の出欠を戻さずに、VTIMEZONE を届けられる。
  - 会議室の二重予約（承諾どうしの重なり）が、計算し直しでも 0 件のまま保たれる（NFR-005）。
- 引き受けるコスト：
  - `Asia/Tokyo` の改正のような最悪の場合、約 2 億件の計算し直しで 11 時間かかり、変更のログとクライアントの取り直しが集中する。
  - デプロイから会議室の予約の行の計算し直しまでの数分、排他の制約が新旧の版の区間を比べる（[ADR-0002](0002-time-representation.md) の原則を、短い幅で破る）。
  - 外部の主催者の予定は、主催者の tzdb が古ければずれたままになり、直せない。画面で示すだけである。

## Confirmation

- tzdb の版の差分の試験（[quality.md](../quality.md) の 2.2.1 節 B）：PROP-TZ-002〜004、会議室の予約の「要確認」、外部への `REQUEST` の `SEQUENCE` が変わらないこと。
- 結合テスト：計算し直しの順序（会議室の予約の行が先、施行の近い順）。
- 本番：採用から 24 時間の後の古い版の行の数 0、会議室の承諾どうしの重なり 0。
- E12 の `tzdata-update-drill` で、最悪の量の速さを測る。
