# ADR-0042: 監査ログは、テナントの監査（Aurora、既定 1 年）とプラットフォームの監査に分け、どちらも log-archive へハッシュの連鎖つきで写す。変更のログを監査ログの代わりにしない。保持の期間を 1 つの表（`retention_policies`）で持ち、時間で消えるものは分割を落とし、テナントの解約は 30 日の猶予の後に `tenant_id` で消す。値は法務の L5 の後に確定する

## Context

- 組織の管理者は、だれが共有を変えたか、だれが会議室の承認をしたか、管理者がだれの `private` の予定を見たか（法務の L8）、CalDAV のアプリ用のパスワードを作ったかを知る必要がある（[intent.md](../intent.md) の E11）。
- [ADR-0005](0005-change-log-and-sync-tokens.md) の変更のログ（`calendar_changes`）は、同期のためのもので、30 日で落ち、だれが変えたかを持たない。監査に使えない。
- 本システムは、外から来た生のデータ（iMIP のメール）、削除した予定の墓標、送信の記録、手元のキャッシュなど、保持の期間の違う多くのデータを持つ。保持の期間は法務の確認待ち（L5）である。
- 解約したテナントのデータを消す必要がある（L9 の DPA の雛形でも求められる見込み）。テナントは RLS で分けた共有のスキーマにあり（[ADR-0004](0004-tenancy-and-rls.md)）、消すのは行の削除になる。
- 他の題材（Linear の ADR-0047・0048）で同じ形の決定がある。

## Options

監査ログ：

1. **テナントの監査とプラットフォームの監査を分ける。どちらも Aurora の表に書き、log-archive の S3（Object Lock）へハッシュの連鎖つきで写す**
2. CloudWatch Logs に書き、そこから検索する
3. 変更のログを長く持ち、監査に使う

保持と削除：

- a. **保持の期間を 1 つの表で持ち、時間で消えるものは分割を落とす。テナントの解約は 30 日の猶予の後に消し、バックアップは 35 日で消える**
- b. 表ごとに削除のジョブを書く
- c. テナントごとの鍵を消して読めなくする（[ADR-0041](0041-encryption-keys-and-secret-storage.md) で持たないとした）

## Decision

1 と a を採用する。

### 監査ログ

| 種類 | 置き場所 | 書くもの | 読める人 |
| --- | --- | --- | --- |
| テナントの監査（`tenant_audit_events`） | Aurora、月で分割、RLS | 共有・ACL・方針の変更、管理者の操作、管理者の予定の閲覧、会議室の承認、アプリ用のパスワード・OAuth のアプリ・Webhook の作成と取り消し、ICS の秘密のアドレスの作り直し、未確認の返事の手での受け入れ、保留の招待の受け入れ、書き出し、SSO・SCIM の設定 | 組織の管理者（画面と書き出し）、個人のテナントは本人 |
| プラットフォームの監査（`platform_audit_events`） | Aurora の保守用のスキーマ（RLS の外） | 運用者の JIT のアクセス、break-glass、テナントをまたぐ関数の呼び出しの集計、tzdb のバージョンの採用、`sync_epoch` の更新、データの直接の修正（`packages/writer` の保守の経路） | セキュリティの担当 |

- 1 行は `(id, tenant_id, at, actor_kind, actor_id, action, target_kind, target_id, reason_code, request_id, ip_hash, prev_hash, row_hash)`。予定のタイトル・場所・本文は書かない（ID だけ）。
- `row_hash = SHA-256(prev_hash ‖ 行の正規化した形)`。テナントごと・日ごとに連鎖を作り、毎日の終わりの値を log-archive の S3（Object Lock のコンプライアンスモード）へ写す。行そのものも 1 時間ごとに写す。
- 監査ログの書き込みは、その操作と同じ DB のトランザクションで行う（`packages/writer` と管理の API）。書けなければ操作も失敗させる。
- 管理者の `private` の予定の閲覧（法務の L8 の結論で範囲を決める）は、必ず監査ログに残し、閲覧された人に知らせるかは L8 の後に決める。

### 保持の期間（既定。法務の L5 の後に確定）

| データ | 既定 | 消し方 |
| --- | --- | --- |
| `calendar_changes`（変更のログ） | 30 日 | 日の分割を落とす（[ADR-0005](0005-change-log-and-sync-tokens.md)） |
| 削除した予定（ごみ箱） | 30 日で消す。その後の墓標は変更のログの保持まで | `lifecycle` のジョブが `packages/writer` で消す |
| `occurrences`（展開の索引） | 過去 31 日 | 月の分割を落とす（[ADR-0003](0003-recurrence-storage-and-expansion.md)） |
| iMIP の受信の生のメール（S3） | 30 日 | S3 のライフサイクル |
| 保留の招待、未確認の返事 | 30 日 | 分割か日次のジョブ |
| iMIP の送信の記録 | 90 日 | 分割を落とす |
| 内部の配送の記録（`itip_deliveries`） | 14 日（その後は日ごとの集計だけを 90 日） | 分割を落とす。量が多い（S1 で 1 日 約 1.3 億行。[capacity.md](../architecture/capacity.md) の 5.1 節） |
| 差分の同期の使用の集計（`sync_token_uses`） | 90 日 | 分割を落とす |
| リマインダーの送信の記録 | 35 日 | 分割を落とす |
| ICS の取り込み・書き出しのファイル（S3） | 7 日 | S3 のライフサイクル |
| Web Push の購読 | 配信のサービスが 404・410 を返したら消す。90 日使われなければ消す | 日次のジョブ |
| テナントの監査（Aurora） | 1 年 | 月の分割を落とす |
| 監査ログの写し（log-archive） | 3 年 | Object Lock の期限 |
| アプリのログ | CloudWatch Logs 30 日、log-archive 13 か月 | 保持の設定 |
| Web の画面の手元の DB | 30 日使われなければ消す（[ADR-0039](0039-offline-read-cache-and-local-data.md)） | クライアント |
| バックアップ（Aurora の PITR、AWS Backup） | 35 日 | 期限で消える |

- 値の正本は `retention_policies` の表（データの種類 → 期間、根拠、L5 の結論のバージョン）と、Terraform の S3 のライフサイクルにする。CI が両者を比べる。
- 法的な保全（訴訟の保全の依頼）は、テナントごとに `legal_hold` を立て、`lifecycle` のジョブがそのテナントを飛ばす。分割を落とす表は、保全の間、そのテナントの行を保全の表へ写してから落とす。

### テナントの解約と削除

1. 解約の手続きで、テナントを `suspended` にする。利用者はログインできず、CalDAV・API・ICS の公開・Webhook・iMIP の受け口が止まる。外部への予定の取り消し（`CANCEL`）は送らない（組織の判断に任せ、書き出しを先に勧める）。
2. 30 日の猶予の間は、組織の管理者だけが書き出しと取り消しの撤回をできる。
3. 30 日の後、`tenant-purge` のジョブが、テナントの全部の表を `tenant_id` で消し（1 万行ずつ）、S3 の接頭辞を消し、Valkey の鍵を消す。他のテナントにある参加者の写しは、主催者が消えたものとして残す（外部の主催者と同じ扱い）。
4. 消した事実（テナントの ID、時刻、行の数）をプラットフォームの監査に残す。
5. バックアップの中のデータは、35 日の期限で消える。消すまでの期間を顧客に示す（L9）。

- 個人のアカウントの削除は、個人のテナントの解約と同じ手順で、猶予を 7 日にする。組織の利用者の削除は、accounts-and-orgs の領域で決める（予定の持ち主の付け替え）。

### 他の案を選ばなかった理由

- **2（CloudWatch Logs）**：組織の管理者の画面から、テナントで絞って検索させにくい。操作と同じトランザクションで書けず、欠けうる。
- **3（変更のログ）**：だれが変えたかを持たず、30 日で落ちる。同期の性能の都合と、監査の保持の都合を混ぜることになる。
- **b（表ごとのジョブ）**：保持の期間が散らばり、L5 の結論を当てる場所がわからなくなる。
- **c（鍵の消去）**：[ADR-0041](0041-encryption-keys-and-secret-storage.md) のとおり、テナントごとの鍵を持たない。

## Consequences

- 良くなること：
  - 監査ログが欠けず（同じトランザクション）、改ざんを連鎖で見つけられる。
  - L5 の結論を、1 つの表と S3 のライフサイクルに当てれば済む。
  - 解約したテナントのデータの消える時期を、顧客に示せる。
- 引き受けるコスト：
  - 監査ログの書き込みの分、管理の操作の書き込みが増える。
  - 猶予の 30 日とバックアップの 35 日の間、解約したテナントのデータが残る。
  - 他のテナントの参加者の写しは消さないので、主催者のテナントを消しても、相手の手元に予定が残る（iCalendar の写しと同じ性質）。

## Confirmation

- 結合テスト：上の監査の対象の操作が、監査の行を書けないときに失敗する。
- 日次のジョブ：ハッシュの連鎖の検証。合わなければ呼び出し（[observability.md](../architecture/observability.md) の 5 節）。
- 結合テスト：`tenant-purge` の後、テナントの ID でどの表・S3 の接頭辞・Valkey の鍵を探しても 0 件である（表の一覧は `tenant_id` の列を持つ表をスキーマから集める）。
- CI：`retention_policies` の表と、Terraform の S3 のライフサイクル・CloudWatch Logs の保持が一致する。
- 漏れの経路の表に「監査ログ（中身を書かない）」の行を足す。
