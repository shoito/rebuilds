# ADR-0002: 時刻つきの予定は壁時計の時刻＋TZID を正にし、UTC の瞬間は `tzdata_version` つきの派生の値にする。終日は日付、浮動は浮動のまま持つ。tzdb は版を固定してサーバーとクライアントに配る

## Context

カレンダーの予定の時刻には、意味の違う 3 つの種類がある（RFC 5545 の 3.3.4・3.3.5 節）。

- **TZID つきの時刻**：「東京の 10:00」。主催者が意図したのは現地の壁時計の時刻である。
- **浮動の時刻**：TZID のない時刻。「どこにいてもその土地の 7:00」。ICS や CalDAV の取り込みで現れる。
- **日付**：終日の予定。「2026-11-03」。見る人のタイムゾーンに関係なく、その日付である。

タイムゾーンの規則は変わる。IANA の tzdb には決まったリリースの予定がなく、ふつう数か月ごとに出る。規則は短い予告で変わることがある（[Time zone and daylight saving time data](https://data.iana.org/time-zones/tz-link.html)、2026-10-04 に確認）。UTC の瞬間だけを保存すると、規則が変わった国の未来の予定が、現地の時刻でずれる。

本家の API は、繰り返しの予定で開始のタイムゾーンを必須にし、展開に使う。終日の予定は日付で持つ（[Events resource](https://developers.google.com/workspace/calendar/api/v3/reference/events)、2026-10-04 に確認）。本家の内部の保存の形と、tzdb の更新の扱いは、公開の資料にない（未検証）。

日本は夏時間を持たないが、海外の参加者、出張、海外の拠点との会議で、夏時間のある地域の予定を扱う。

## Options

保存の正：

1. **壁時計の時刻＋TZID を正にし、UTC の瞬間を派生の値として持つ**
2. UTC の瞬間を正にし、TZID は表示のためにだけ持つ
3. 壁時計の時刻＋TZID だけを持ち、UTC の瞬間を読むたびに計算する

オフセットの計算の元：

- a. **tzdb の版を固定した自前のデータ（`packages/tzdata`）を、サーバーとクライアントで共有する**
- b. 実行環境の tzdata（Node.js・ブラウザの ICU、PostgreSQL の tzdata）を使う

## Decision

1 と a を採用する。

### 時刻の種類と保存の形

| 種類 | 正本 | 派生 | 例 |
| --- | --- | --- | --- |
| `zoned` | `start_local`・`start_tzid`、`end_local`・`end_tzid`（開始と終了で別のゾーンを持てる） | `start_utc`・`end_utc`、`tzdata_version` | 東京 10:00 から ロンドン 18:00 の移動 |
| `utc` | `start_utc`・`end_utc`（TZID は `UTC`） | なし | オフセットだけで指定された時刻（下の規則） |
| `floating` | `start_local`・`end_local`（TZID なし） | 写しの持ち主のカレンダーのタイムゾーンで解いた `start_utc`・`end_utc` | 取り込んだ ICS の「7:00 に薬」 |
| `date` | `start_date`・`end_date`（終わりを含まない） | 写しの持ち主のカレンダーのタイムゾーンで日付の境を解いた区間（空き時間・リマインダーのため） | 終日、複数日の休暇 |

- 派生の値は、展開の索引と予定の行の両方で `tzdata_version` と一緒に持つ。版の違う派生の値を、比べたり混ぜたりしない。唯一の例外は、tzdb の版の切り替えの直後に、会議室・予約の排他の制約が新旧の版の区間を比べる窓である（[ADR-0012](0012-tzdb-update-recompute-and-propagation.md) の「切り替えの窓」）。
- API で、TZID なしでオフセットだけの時刻（`2026-11-03T10:00:00+09:00`）を受けたら、カレンダーの既定のタイムゾーンでそのオフセットが合えば `zoned` に、合わなければ `utc` にする。繰り返しの予定は TZID を必須にする（本家と同じ）。
- `floating` と `date` の派生の値は、写しの持ち主のカレンダーのタイムゾーンで解く。カレンダーのタイムゾーンを変えたら、派生の値を作り直す（変更のログに載せる）。

### 解けない時刻

- 夏時間の切り替えで存在しない時刻と、2 回ある時刻は、RFC 5545 の 3.3.5 節の規則で解く。存在しない時刻は、切り替えの前のオフセットで解く（結果としてギャップの長さだけ後ろになる）。2 回ある時刻は、先の回（切り替えの前のオフセット）にする。
- 規則は `packages/tz` の `resolve(local, tzid, tzdata)` の 1 つにし、展開・空き時間・リマインダー・画面のすべてが使う。

### tzdb の版

- IANA の tzdb を zic で遷移の表にし、`packages/tzdata` に版（例：`2026b`）として固定する。サーバー・Worker・Web のクライアントで同じ版を使う。Web のクライアントは、使うゾーンのデータだけを遅延で読む。
- 実行環境の tzdata（`Intl`、`Date` の現地時刻、PostgreSQL の `AT TIME ZONE`）で、オフセットを計算しない。`Intl` は、月・曜日の名前、和暦の表示の書式にだけ使う。
- API の応答は `tzdata_version` を返す。クライアントの版が古いときは、サーバーの派生の値で表示し、自分で計算し直さない。クライアントの版の更新を促す。

### tzdb の更新

1. 新しい tzdb の版の PR に、CI が差分の報告を付ける。未来（今日から 10 年）の遷移が変わったゾーンと区間、影響する予定オブジェクトの数の見積もり。
2. 採用（AppConfig の `tzdata.active_version` の全サービスでの切り替え。[ADR-0049](0049-tzdata-rollout-and-schema-change-ordering.md)）の後、`expander` が、影響するゾーンを TZID に持つ予定（`zoned`）と、影響するゾーンのカレンダーの `floating`・`date` を探し、壁時計の時刻を保ったまま派生の値を計算し直す。展開の索引、会議室の予約の行、リマインダーの桶を直し、変わった予定を変更のログに載せる（[ADR-0005](0005-change-log-and-sync-tokens.md)）。
3. 計算し直しは、施行の日の近いゾーンから順に行い、採用から 24 時間以内に終える（NFR-009）。
4. 会議室の予約が、計算し直しで重なったときの扱い、外部の参加者へ更新を送るかは、time-zones-and-holidays の領域で決めた（[ADR-0012](0012-tzdb-update-recompute-and-propagation.md)）。

> 2026-10-04 の注記：最初の設計では、採用をデプロイで行うとした。delivery の領域で、版をイメージに入れて先にデプロイし、AppConfig の 1 つの値で全サービスを一度に切り替える形にした（[ADR-0049](0049-tzdata-rollout-and-schema-change-ordering.md)）。版の切り替えの窓での例外は、上の「時刻の種類と保存の形」の節に書いた。

### 他の案を選ばなかった理由

- **2（UTC の瞬間を正）**：規則が変わった国の未来の予定が、現地の時刻でずれる。終日の予定を UTC にすると、見る人のタイムゾーンで日付がずれる不具合の元になる。
- **3（派生の値を持たない）**：空き時間・会議室の排他の制約・リマインダーの桶は、UTC の区間の索引が要る。読むたびに計算すると、索引が作れない。
- **b（実行環境の tzdata）**：Node.js・ブラウザ・PostgreSQL・利用者の端末で版が揃わない。同じ予定の同じ回が、経路ごとに違う瞬間になりうる。tzdb の更新の時期を本システムで制御できない。

## Consequences

- 良くなること：
  - tzdb が変わっても、未来の予定が主催者の意図した現地の時刻に保たれる。
  - 本システムの中のすべての経路で、同じ版の同じ規則で時刻を解く。
  - tzdb の更新を、差分の報告つきのデータのリリースとして扱える。
- 引き受けるコスト：
  - 派生の値の計算し直しのジョブと、その運用が要る。計算し直しが変更のログを大量に流す（同期の負荷）。
  - Web のクライアントに tzdb のデータを配る分、資産が大きくなる。ゾーンごとの遅延の読み込みで抑える。
  - 外部（CalDAV のクライアント、iMIP の相手）は自分の tzdb を使うので、版の違いのずれは残る。VTIMEZONE を付けて送り、ずれの扱いを領域で決める。
  - 浮動と日付の時刻は、持ち主のカレンダーのタイムゾーンに依存する。カレンダーのタイムゾーンの変更が、派生の値の作り直しを起こす。

## Confirmation

- 性質ベーステスト：任意の壁時計の時刻・TZID・tzdb の版で、`resolve` の結果を `toLocal` で戻すと、存在しない時刻以外は元の壁時計の時刻に戻る。
- 性質ベーステスト：任意の 2 つの tzdb の版で、遷移が変わらないゾーンの予定は、派生の値が変わらない。
- tzdb の更新の試験：過去の tzdb の実際の改正（夏時間の廃止・新設、オフセットの変更）を、合成の予定に当て、計算し直しの後の壁時計の時刻が保たれ、UTC が新しい規則に合うことを確かめる（[quality.md](../quality.md) の 2.2.1 節）。
- lint：[ADR-0001](0001-platform-and-stack.md) の Confirmation の、`Intl` の `timeZone`・`Date` の現地時刻・`AT TIME ZONE` の禁止。
- CI：`packages/tzdata` の版を上げる PR に、差分の報告がなければ失敗させる。
- 本番：展開の索引の行の `tzdata_version` が、採用から 24 時間を過ぎて古い版のまま残っている数を監視する（0 を目標）。
