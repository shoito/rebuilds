# ADR-0033: 予約は持ち主の主のカレンダーの行をロックする 1 つのトランザクションで確かめ直して作り、`booking_reservations` の持ち主と区間の排他の制約で予約どうしの重なりを DB で 0 にする。メールの確認は 10 分の仮押さえで塞ぐ。予約者は外部の参加者として ICS つきのメールを受ける。ボットの対策は AWS WAF

## Context

予約ページは匿名の人から並行に予約を受ける。同じ枠に 2 人が同時に予約しうる。[architecture/README.md](../architecture/README.md) の 6 節は、会議室の二重予約を `btree_gist` の排他の制約で防ぐと決め、題材の `AGENTS.md` は、アプリの事前の確かめだけに頼らないと決めた。[quality.md](../quality.md) の 5 節は、E10 の合否基準を「並行の予約で二重の予約 0」とした。

決めることは次である。

- 予約どうしの重なりを、何で 0 にするか。
- 持ち主の予定との重なりを、どこまで防ぐか。
- 予約者のメールの確認（本家の「メールの確認を求める」）の間、枠をどう扱うか。
- 予約者を予定にどう入れ、どう知らせるか。
- ボットの対策の部品。

本家は「空きを確かめるカレンダー」で重なりを防ぎ、予約の書式で名・姓・メールアドレスを必須にし、メールの確認を選べる（[Create an appointment schedule](https://support.google.com/calendar/answer/10729749)、2026-10-04 に確認）。二重の予約の防ぎ方とボットの対策は公式の資料にない（未検証）。

## Options

予約どうしの重なり：

1. **`booking_reservations` に `(tenant_id, host_user_id, tstzrange)` の排他の制約。区間は `[開始, 終わり＋間の時間)`**
2. 持ち主のカレンダーの行のロックの中で、アプリが重なりを確かめるだけ
3. 枠ごとの一意の制約（開始の時刻の一意）

ボットの対策：

- a. **AWS WAF の Bot Control と、予約の送信への Challenge・CAPTCHA、レート制限**
- b. 第三者の CAPTCHA のサービス
- c. 予約者のメールの確認を必須にするだけ

## Decision

1 と a を採用する。詳細は [booking-pages.md](../architecture/booking-pages.md) の 6〜9 節。

- **トランザクション**：`packages/writer`（`origin = booking`）の 1 つのトランザクションで、持ち主の主のカレンダーの行をロックし（`change_seq`）、同じ持ち主の期限の切れた `held` を `released` にし、空きを確かめるカレンダーの予定ありを展開の索引で確かめ直し、1 日の上限を数え、`booking_reservations` に挿入し、`confirmed` なら予定オブジェクトと `calendar_changes` と outbox を書く。制約・予定ありの重なり・上限に当たれば 409 `slotUnavailable`。
- **排他の制約**：`EXCLUDE USING gist (tenant_id WITH =, host_user_id WITH =, span WITH &&) WHERE (status IN ('held', 'confirmed'))`。`span = [開始, 終わり + 間の時間)`。各予約が自分の後ろの間を持つので、前後の両方の間が守られる。取り消し・変更・期限切れは `released` にして行を残す。
- **予定との重なり**：持ち主の予定は制約に入れない（重なってよいもの）。主のカレンダーへの書き込みとは行のロックで直列になる。他の空きを確かめるカレンダーへの同時の書き込みとは直列にならず、重なりうることを引き受け、数を測る。
- **仮押さえ**：メールの確認を求めるページは、`held` と 10 分の期限で区間を塞ぎ、6 桁のコード（5 回まで）で `confirmed` にする。予定オブジェクトは `confirmed` の後に作る。
- **予定と予約者**：持ち主を主催者に、予約者を外部の参加者（`accepted`）にする。確認のメールに `METHOD:REQUEST` の ICS を付け、ORGANIZER は予定ごとの受け口のアドレス（[ADR-0015](0015-imip-addressing-and-trust.md)）。予約者の辞退の `REPLY` は取り消しとして扱う。管理のリンク（160 ビットの `token`、ハッシュを保存）で取り消しと変更を受ける。
- **冪等**：`Idempotency-Key` を 24 時間。
- **ボット**：予約ページだけの WAF の規則の組に Bot Control（共通の水準）と IP の評判の一覧、予約の送信に Challenge、疑わしい要求に CAPTCHA。予約の送信は 1 IP 1 時間 10 回、1 ページ 1 日 200 回、同じメールアドレスの未来の予約は 1 ページ 3 件まで。1 ページ 1 日 50 件を超えたらページを止めて持ち主に知らせる。
- **個人情報**：予約者の情報の通知・同意・本人確認・保持・請求は法務の L6 の結論を待ち、枠だけを持つ（[booking-pages.md](../architecture/booking-pages.md) の 10 節）。

### 他の案を選ばなかった理由

- **2（ロックの中のアプリの確かめだけ）**：ロックの取り忘れ・別の経路（管理の操作、移行のジョブ）の書き込みで重なりうる。題材の規則（DB の制約で拒む）に合わない。
- **3（開始の一意）**：長さ・間の時間の違うページの予約や、刻みのずれた予約の重なりを防げない。
- **b（第三者の CAPTCHA）**：予約者の端末の情報を新しい第三者へ送る（法務の L1・L2 の論点が増える）。まず AWS の中の機能で始める。
- **c（メールの確認だけ）**：捨てアドレスで仮押さえを繰り返し、枠を塞がれる。

## Consequences

- 良くなること：
  - 予約どうしの重なりが、どの経路の書き込みでも DB で 0 になる。
  - メールの確認の間も枠が塞がり、確認の後に取られることがない。
  - 予約者の手元のカレンダーに予定が入り、取り消しが返事で戻ってくる。
- 引き受けるコスト：
  - 持ち主の他のカレンダーとの同時の書き込みで、予定との重なりが残りうる。
  - `held` の仮押さえを捨てアドレスで繰り返されると、10 分ずつ枠を塞がれる（同じメールアドレス・IP の上限で抑える）。
  - WAF の機能だけでは突破されうる。E10 の後に測って見直す。
  - tzdb の再計算で予約の区間が動き、重なりうる（会議室と同じく「要確認」にする。[ADR-0012](0012-tzdb-update-recompute-and-propagation.md)）。

- 表駆動テスト：DT-BOOK-002（取り消しと変更）、DT-BOOK-003（組織の方針）。
- 性質ベーステスト：PROP-BOOK-001（任意の並行の予約・取り消し・変更・期限切れで区間が重ならない。100 並行）、PROP-BOOK-003（主のカレンダーだけのページで予定と重ならない）。
- 結合テスト：排他の制約の違反の 409、`held` の期限切れ、管理のリンク、辞退の `REPLY`。
- 本番：確定した予約と予定ありの重なりの数、409 の率、WAF で止めた要求の数。
