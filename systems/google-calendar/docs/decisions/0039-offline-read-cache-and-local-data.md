# ADR-0039: Web の画面のオフラインは読み出しだけにし、アカウントごとの IndexedDB に前後 4 週の予定オブジェクトとトークンとゾーンのデータを持つ。手元の DB は捨ててよい写しとし、版が変われば作り直す。ログアウト・セッションの取り消し・30 日の不使用で消し、共有の端末では保存しない

## Context

[architecture/README.md](../architecture/README.md) の 6 節は、Web の画面のオフラインを「最近の範囲（前後 4 週）の読み出しだけ」と決め、書き込みは MVP で持たないとした。ここでは、手元に何を、どう持ち、いつ消すかを決める。

- 手元のデータは、[ADR-0004](0004-tenancy-and-rls.md) の `redact()` を通した後の形である。見てよいものだけだが、端末の紛失・共有の端末・退職した人の端末に残ると漏えいになる（NFR-008）。
- 手元の保持の期間は、法務の確認待ちの L5 に入っている（[intent.md](../intent.md)）。
- 書き込みを持たないので、手元には送っていない変更（outbox）がない。手元の DB を消しても、失うものはない。
- 予定の画面は朝の通勤の電車、地下、機内で見られる。読めることの価値は高い。

本家の Web の画面のオフラインの範囲と保持は、公開の資料で確かめられなかった（**未検証**。2026-10-04 に確認）。

## Options

1. **アカウントごとの IndexedDB に、窓（前後 4 週）の予定オブジェクト・トークン・ゾーンのデータを持つ。手元の DB は捨ててよい写しにする**
2. Service Worker で API の応答をそのままキャッシュする
3. 手元に何も持たない（オンラインだけ）
4. 手元の DB をアプリの層で暗号化する（鍵はサーバーから受ける）

## Decision

1 を採用する。

### 持つもの

| ストア | 中身 | 大きさの目安 |
| --- | --- | --- |
| `calendars` | 見えるカレンダーの一覧、色、ロール、タイムゾーン | 数 KB |
| `objects` | 窓に回が触れる予定オブジェクト（`redact()` の後の形） | カレンダー 10 × 200 件 × 3 KB ≒ 6 MB |
| `tokens` | カレンダーごとの同期のトークン、窓の範囲、最後に確かめた時刻 | 数 KB |
| `tzdata` | 使うゾーンのデータ（版ごと） | 1 ゾーン 5 KiB |
| `prefs` | 表示のタイムゾーン、2 つ目のタイムゾーン、週の始まり、表示の種類 | 数 KB |
| `_meta` | 手元の DB の版（`cache_schema`）、アカウントの ID、作った時刻、最後に使った時刻 | — |

- DB の名前は `cal-<account_id>` にし、アカウントごとに分ける。アカウントを切り替えたら、別の DB を開く。
- Service Worker は、アプリの殻（ハッシュ付きの資産、`index.html`）と `/tzdata/<version>/*` だけをキャッシュする。API の応答をキャッシュしない。
- `navigator.storage.persist()` は求めない。ブラウザに消されても取り直せる写しなので、許可の表示を出さない。

### オフラインのときの振る舞い

- 画面の上に「オフライン。最後の同期 HH:MM」を出す。作成・移動・編集・出欠の操作を無効にし、押したら理由を示す。
- 窓の外へ移ったら「この期間はオフラインでは見られません」を示す。
- 回は手元の `expand()` で作る（[ADR-0038](0038-web-calendar-rendering-and-local-expansion.md)）。
- オンラインに戻ったら、トークンで差分を取る。410 なら窓を取り直す。

### 写しとしての扱い

- 手元の DB は捨ててよい写しである。`cache_schema` が今のコードの版と違えば、移行せず、消して取り直す。開けない・壊れているときも同じにする。
- 書き込みを持たないので、失う変更はない。手元の DB の版の変更を、機能の変更と同じリリースに含めてよい（[ADR-0049](0049-tzdata-rollout-and-schema-change-ordering.md)）。

### 消す

| きっかけ | 消すもの |
| --- | --- |
| ログアウト | そのアカウントの DB、Service Worker の殻以外のキャッシュ |
| セッションの取り消し、利用者の停止、組織からの除外（サーバーが 401 に `wipe` の理由を付ける） | 同上。次の起動か、次の要求の応答で消す |
| 30 日使われていない（`_meta` の最後に使った時刻） | 次の起動で消して取り直す。期間は法務の L5 の後に確定する |
| ACL を失ったカレンダー（差分の `acl` の変更、410） | そのカレンダーの `objects` と `tokens` |
| 「この端末に保存しない」でログインした | 手元の DB を作らない（メモリーだけ） |

- 組織の管理者は、組織の利用者に「この端末に保存しない」を強いる方針を持てる（accounts-and-orgs の領域）。
- アプリの層の暗号化はしない。OS のディスクの暗号化に任せる。

### 他の案を選ばなかった理由

- **2（API の応答のキャッシュ）**：応答の単位で残るので、ACL を失ったカレンダーの応答だけを消すのが難しい。差分を当てる形にならない。
- **3（持たない）**：電車・機内での閲覧ができない。[architecture/README.md](../architecture/README.md) の 6 節の決定に合わない。
- **4（暗号化）**：鍵をサーバーから受けるなら、オフラインで開けない。手元に鍵を置くなら、同じ端末の攻撃者に対して守りにならない。他の題材（Linear の ADR-0046）と同じ判断である。

## Consequences

- 良くなること：
  - 電車・機内で、前後 4 週の予定を見られる。
  - 手元の DB の移行を書かずに済む。版の変更が軽い。
  - 消すきっかけが決まり、退職した人・共有の端末の漏えいを抑えられる。
- 引き受けるコスト：
  - オフラインで書けない。会議の直前に場所を直すような操作は、オンラインに戻るまでできない。
  - ブラウザがデータを消すと、次のオンラインで取り直しになる。
  - 端末の OS のディスクの暗号化がなければ、手元の予定が読める。共有の端末は「この端末に保存しない」で避ける。

## Confirmation

- E2E（Playwright）：オフラインにして再読み込みし、窓の中の週を表示でき、作成の操作が無効になっている。
- E2E：ログアウト、`wipe` の 401、30 日を進めた時計で、そのアカウントの IndexedDB が消える。
- 性質ベーステスト（PROP-CLI-003）：任意の差分の列（ACL の変更を含む）を当てた後、手元の `objects` に、今の ACL で見てはいけないカレンダーの予定オブジェクトがない。
- 結合テスト：`cache_schema` を変えたコードで起動すると、手元の DB を消して取り直し、エラーにならない。
- 漏れの経路の表（[quality.md](../quality.md) の 2.2.1 節 D）に「Web の画面の手元の DB」の行を足す。
