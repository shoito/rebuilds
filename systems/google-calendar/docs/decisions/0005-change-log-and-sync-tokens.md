# ADR-0005: カレンダーごとに単調な `change_seq` と変更のログを持ち、Web・公開 API・CalDAV・Webhook の差分の同期の背骨にする。トークンは署名つきで、30 日を過ぎたら取り直しを求める

## Context

予定の変更を、次の相手に差分で届ける必要がある。

- **Web のクライアント**：表示しているカレンダーの変更を数秒で反映する（NFR-002）。
- **公開 API の利用者**：差分の同期のトークンで、前回からの変更だけを取る。
- **CalDAV のクライアント**：RFC 6578 の `sync-collection` の REPORT で、前回からの変更を取る。古いクライアントは CTag（コレクションのバージョン）と ETag で確かめる。
- **Webhook の受け手**：「変わった」の通知を受けて、差分を取りに来る。
- **社内の処理**：招待の配送、検索の表、リマインダーの付け替え。

本家の API は、`nextSyncToken` で差分を取り、トークンが失効したり ACL が変わったりすると 410 を返して全件の取り直しを求める。差分には削除が必ず含まれ、問い合わせの条件は最初の要求と同じにする。Push の通知は本文を持たず、一部は落ちうる（[Synchronize resources efficiently](https://developers.google.com/workspace/calendar/api/guides/sync)、[Push notifications](https://developers.google.com/workspace/calendar/api/guides/push)、2026-10-04 に確認）。トークンの有効の期間は、公式の資料に値がない（未検証）。

経路ごとに別の差分の仕組みを作ると、どれかの経路で変更が欠ける。

## Options

順序の単位：

1. **カレンダーごとに単調な `change_seq` を振る**
2. テナントごとに単調な番号を振る
3. 時刻（`updated_at`）で差分を取る
4. DB の論理レプリケーション（WAL）から変更を取る

## Decision

1 を採用する。

### 変更のログ

- `calendars` の行に `change_seq` を持つ。`packages/writer` は、書き込みのトランザクションの最初に、対象のカレンダーの行をロックし（`UPDATE ... SET change_seq = change_seq + n RETURNING`）、変更ごとに番号を振る。
- 番号を振った変更を `calendar_changes(tenant_id, calendar_id, seq, kind, event_object_id, object_version, committed_at)` に、予定の変更と outbox と同じ DB のトランザクションで書く。`kind` は `upsert`・`delete`・`calendar`（カレンダーの属性）・`acl`（共有の変更）。
- **ログを通らない書き込みを作らない。** 一括の修正、tzdb の更新の計算し直し（[ADR-0002](0002-time-representation.md)）、展開の範囲の端の移動で予定オブジェクトの見え方が変わるもの、方針の変更での ACL の無効化も、`packages/writer` を通して番号を振る。展開の索引の範囲の端の移動は予定オブジェクトを変えないので、ログに載せない。
- 1 つの予定オブジェクトを複数のカレンダーが持つことはない（参加者の写しは別の予定オブジェクト。[ADR-0006](0006-organizer-and-attendee-copies.md)）。
- ログは日で分割し、30 日を過ぎた分割を落とす（保持の期間は法務の L5 の後に確定する）。カレンダーごとに、保持の下限の番号（`floor_seq`）を持つ。
- 1 つのカレンダーの書き込みは、行のロックで直列になる。会議室と大きな共有のカレンダーで 1 秒 50 件を上限と見込み、E2 の前の `calendar-write-throughput-poc` で確かめる。

### 同期のトークン

- トークンは不透明な文字列で、中身は `{v, calendar_id, seq, epoch, filter_hash, view_hash}` に HMAC の署名を付けたもの。利用者が他のカレンダーのトークンを作れない。
  - `filter_hash`：問い合わせの条件（削除を含むか、など）。最初の要求と条件が違えば 400 を返す（本家と同じ）。
  - `view_hash`：トークンを出した時点の、主体のそのカレンダーへの見え方（ロールと方針の組）。`redact()` の結果が変わる共有の変更があれば、410 で取り直しを求める（本家の「ACL の変更で 410」と同じ考え方）。
  - `epoch`：DR の切り替え、時点への復元で上げる。古い `epoch` のトークンは 410。
- 差分の応答は、トークンの `seq` より後に変わった予定オブジェクトの、今の状態（`redact()` の後）と、削除の墓標。同じ予定オブジェクトが何度変わっても 1 件にまとめる。件数が多ければページに分け、最後のページで次のトークンを返す。
- トークンの `seq` が `floor_seq` より古ければ 410 を返す。最後の利用から 30 日は使える（NFR-010）。
- トークンは予定オブジェクトの単位で差分を返す。回に展開した一覧（範囲の表示）はトークンを持たない範囲の問い合わせにし、クライアントは手元で `expand` する（Web のクライアントは `packages/recurrence` を使う）。

### 経路ごとの使い方

| 経路 | 使い方 |
| --- | --- |
| Web のクライアント | 表示するカレンダーごとのトークンを持ち、複数のトークンを 1 回の要求で送る。Realtime の WebSocket で「カレンダー C が `seq` S になった」の合図を受け、手元のトークンが古ければ差分を取る。合図が落ちても、再接続と 5 分ごとの確かめで取り戻す |
| 公開 API | 差分の同期のトークン。410 で全件の取り直し |
| CalDAV | CTag はカレンダーの `change_seq`。RFC 6578 の `sync-token` は同じトークンを URI の形にしたもの。ETag は予定オブジェクトの `object_version` から作る |
| Webhook | Relay が変更のログの後に `push-sender` へ渡し、カレンダーの通知の経路ごとに 1 秒に 1 回へまとめて送る。通知に中身を入れない。受け手は差分の同期で取る（api-and-push の領域） |
| 社内の処理 | 変更のログではなく outbox から SNS・SQS で受ける。outbox は変更のログと同じトランザクションで書くので、両者は食い違わない |

### 他の案を選ばなかった理由

- **2（テナントごとの番号）**：大きな組織のすべての書き込みが 1 つの行のロックで直列になる。CalDAV と API の同期の単位（カレンダー）とも合わない。
- **3（時刻）**：同じ時刻の書き込みと、コミットの順序と時刻の入れ替わりで、差分が欠ける。削除を表せない。
- **4（WAL）**：権限で削った形（`redact()`）や、予定オブジェクトの単位のまとめを、行の変更から作り直す必要がある。DR の切り替えや分割の移動で、位置が引き継げない。

## Consequences

- 良くなること：
  - Web・API・CalDAV・Webhook が、同じ順序と同じ保持で差分を返す。ある経路だけ欠けることがない。
  - 合図や Webhook の通知が落ちても、トークンで取り戻せる。
  - トークンが署名つきで、条件と見え方を含むので、誤った差分を返さずに 410・400 で取り直しを求められる。
- 引き受けるコスト：
  - 1 つのカレンダーの書き込みが直列になる。会議室のような書き込みの多いカレンダーが上限に当たりうる。
  - tzdb の更新や方針の変更が、多くのカレンダーのログを流し、クライアントの取り直しを集中させる。計算し直しの速さを絞り、施行の近い順に流す。
  - 30 日を超えて同期しないクライアントは、全件を取り直す。

## Confirmation

- 性質ベーステスト：任意の書き込みの列（並行を含む）と、任意の時点で出したトークンで、差分を順に当てた結果が、全件を取り直した結果と一致する。
- 性質ベーステスト：任意の共有の変更の列で、`view_hash` が変わる変更の後に古いトークンで差分を取ると、410 になる。410 にならずに、見てはいけない予定の中身や、見てよくなった予定の欠けた差分を返さない。
- 結合テスト：`packages/writer` を通らない書き込み（`event_objects` への直接の `UPDATE`）を、DB のロールの権限で拒否する。
- CalDAV の相互運用の試験：対象のクライアントで、`sync-collection` の差分と、トークンの失効（RFC 6578 の `valid-sync-token` のエラー）からの取り直しが動く。
- 本番：変更のログの番号の欠け（カレンダーごとの連続）を監視する。合成監視の 2 つのクライアントで、確定から差分の到着までを測る（NFR-002）。
