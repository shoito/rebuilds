# ADR-0015: 外部への招待の ORGANIZER は予定ごとの受け口のアドレスにして返事を本システムで受け、人の返事は Reply-To で主催者へ向ける。受信は From と ATTENDEE・ORGANIZER の一致と DKIM か SPF の揃いで確かめ、満たさないものは当てない。外部からの招待は転送の受け口で受け、知らない送信元は保留にする

## Context

[ADR-0006](0006-organizer-and-attendee-copies.md) と [ADR-0007](0007-interop-standards-scope.md) は、外部の参加者と iMIP（RFC 6047）でやりとりし、送信は SES、受信は SES の受信 → S3 と決めた。返事の照合の鍵と送信元の認証は、この領域に残した。

本システムの利用者のメールは、本システムの外（組織のメールのサーバー、個人のメールのサービス）にある。そこで次が起きる。

- 外部のカレンダーは、返事を ICS の ORGANIZER のアドレスへ送る（RFC 6047 の 2.3 節）。ORGANIZER を主催者の本当のアドレスにすると、返事は主催者のメールのサーバーに届き、本システムは受けられない。
- 外部の主催者からの招待は、利用者のメールのサーバーに届く。本システムは、転送されなければ受けられない。
- RFC 6047 の 2.2.2 節は、認証を S/MIME で行うことを求める（MUST）。対象の外部のカレンダーが S/MIME で署名して送るかは確かめていない（未検証）。
- 偽の返事（他人の出欠の書き換え）と迷惑な招待は、[quality.md](../quality.md) のリスク 8 に当たる。

本家の ORGANIZER の形と返事の認証は、公式の資料で確かめられなかった（未検証）。本家は、招待を自動で追加する相手を「すべて」「知っている送信元だけ」「返事をしたときだけ」から選べる（[Choose who can add invitations to your calendar](https://support.google.com/calendar/answer/13159188)、2026-10-04 に確認）。

## Options

返事の受け方：

1. **ORGANIZER を予定ごとの受け口のアドレスにする**
2. ORGANIZER は主催者の本当のアドレスにし、組織にメールの転送の規則を設定してもらう
3. 返事を受けない（出欠は本システムの中の人だけ）

送信元の確かめ方：

- a. **From と ATTENDEE・ORGANIZER の一致と、DKIM か SPF の From のドメインへの揃い。S/MIME は必須にしない**
- b. S/MIME を必須にする（RFC 6047 のとおり）
- c. 確かめない

## Decision

1 と a を採用する。詳細は [invitations-and-itip.md](../architecture/invitations-and-itip.md) の 11 節。

- ORGANIZER は `mailto:o-<token>@imip.<brand>.<domain>`（`CN` は主催者の名前）。`token` は UID ごとに 128 ビットの乱数で、UID が生きている間変えない。
- 招待のメールの From は `invitations@mail.<brand>.<domain>`（DKIM で署名）、Reply-To は主催者の本当のアドレス。人の普通の返事は主催者へ直接届き、本システムは人のメールを転送しない。
- 本システムの参加者が外部の主催者へ返事をするときは、From は `replies@mail.<brand>.<domain>`、Reply-To と ATTENDEE は参加者のアドレスにする。
- 外部からの招待は、利用者の受け口（`u-<token>@imip.<brand>.<domain>`）か組織の受け口（`t-<token>@imip.<brand>.<domain>`）への転送で受ける。
- 受信の確かめ：返事は From が ATTENDEE（か `SENT-BY`）と同じ、招待・取り消しは From が ORGANIZER（か `SENT-BY`）と同じ。加えて DKIM の署名のドメインか SPF の MAIL FROM のドメインが From のドメインに揃って通る（SES の判定）。S/MIME の署名が付いて正しければ、それも通る。既存の写しと ORGANIZER が違う招待は拒否する。
- 確かめを通らない返事は当てず「未確認の返事」として主催者に示す。招待は保留、取り消しは当てない。
- 取り込みの方針は利用者が選ぶ（すべて・知っている送信元だけ・返事をしたときだけ）。既定は「知っている送信元だけ」。保留の招待はカレンダー・空き時間・同期に出さない。
- 送信の上限：主催者 24 時間で 2,000 の外部の受け手（本家の「参加者にメール」の機能の約 2,000 件に合わせた。本家の組織の外への招待の上限（短い期間に 10,000 件）より厳しい。[Avoid Calendar use limits](https://knowledge.workspace.google.com/admin/calendar/avoid-calendar-use-limits)、2026-10-04 に確認）、新しい個人のアカウント 200、組織 50,000（S1）。Bounce・Complaint の受け手を抑止する。

### 他の案を選ばなかった理由

- **2（組織の転送の規則）**：個人のアカウントでは設定できない。組織でも設定の誤りで返事が黙って欠ける。
- **3（返事を受けない）**：外部との会議の出欠がわからず、K9 の場面を満たせない。
- **b（S/MIME を必須）**：対象の外部のカレンダーからの返事のほとんどを受けられない見込み。RFC と違う判断として明記して引き受ける。
- **c（確かめない）**：受け口のアドレスは招待の全員に届くので、だれでも他人の出欠を書き換えられる。

## Consequences

- 良くなること：
  - 主催者のメールの環境に関係なく、外部の返事を本システムで受けられる。
  - 偽の返事は、送信元のドメインの認証がなければ当たらない。
  - 本システムは人のメールを転送せず、人の返事は主催者に直接届く。
- 引き受けるコスト：
  - 外部の参加者には、主催者が見慣れないアドレスに見える。外部のカレンダーが ORGANIZER の表示名（`CN`）を出すかは相互運用の試験で確かめる。
  - 外部からの招待を受けるには、利用者か組織が転送を設定する手間が要る。
  - RFC 6047 の S/MIME の要求に従わない（[ADR-0007](0007-interop-standards-scope.md) の「RFC との意図した違い」の D2）。送信元のドメインが DKIM も SPF も揃えていないと、返事は「未確認」になり、主催者の手で受ける。
  - 転送やメーリングリストで DKIM が壊れたメールは「未確認」になる。

## Confirmation

- 表駆動テスト：DT-ITIP-003（送信元の確かめ方）、DT-ITIP-004（取り込みの方針）。
- 性質ベーステスト：PROP-ITIP-006（確かめを通らない返事は主催者の写しを変えない）。
- 相互運用の試験：本家・Outlook・Apple のカレンダーが、受け口の ORGANIZER へ返事を送り、From・DKIM・SPF が揃うこと。
- 本番：未確認の返事の割合、保留の招待の数、Bounce・Complaint の率を監視する。
