# ADR-0008: `expand()` は規則を壁時計の時刻で求め、無効な日付は捨てる。存在しない時刻は捨てずに RFC 5545 の 3.3.5 節でずらす。DTSTART は最初の回として `COUNT` に数え、長さは DTEND なら正確な長さ、DURATION なら名目の長さで当てる

## Context

[ADR-0003](0003-recurrence-storage-and-expansion.md) は、`packages/recurrence` の `expand()` を唯一の展開の関数にした。その意味の細部は、RFC 5545 の中でも食い違いや未定義がある。

- 3.3.10 節は、規則が無効な日付（2 月 30 日）や存在しない現地の時刻を生んだら「その回は捨て、数えない」とする。
- 3.3.5 節は、値としての存在しない時刻を「切り替えの前のオフセットで解く」とする。[ADR-0002](0002-time-representation.md) の `resolve` はこれに従う。
- 3.8.5.3 節は、DTSTART を最初の回として `COUNT` に数えるが、DTSTART が規則に合わないときの回の集合を未定義にしている。
- 3.8.5.3 節は、DTEND で書いた長さは正確な長さで、DURATION で書いた長さは名目の長さで各回に当てるとする。

本家がこれらをどう扱うかは、公式の資料で確かめられなかった（未検証。[Events resource](https://developers.google.com/workspace/calendar/api/v3/reference/events)、2026-10-04 に確認）。展開の誤りは、エラーにならずに回が欠ける・ずれる形で残る（[quality.md](../quality.md) の 1 節のリスク 1）。決めずに実装すると、エージェントは手元のライブラリの振る舞いに合わせがちである。

## Options

存在しない時刻の回：

1. **3.3.5 節で解いてずらし、残す**
2. 3.3.10 節のとおり捨てる

DTSTART が規則に合わないとき：

- a. **DTSTART を最初の回として含め、`COUNT` に数える。新しい作成では拒否する**
- b. DTSTART を含めない（規則の回だけ）
- c. すべての経路で拒否する

## Decision

1 と a を採用する。手順の全体は [events-and-recurrence.md](../architecture/events-and-recurrence.md) の 4 節。

- 規則の回は、TZID に関係ない壁時計の暦の上で、RFC 5545 の 3.3.10 節の表（BYxxx の広げる・絞る）と `BYSETPOS` で作る。
- 無効な日付は捨て、`COUNT` に数えない（3.3.10 節のとおり）。
- 存在しない時刻の回は捨てずに、`resolve` で切り替えの前のオフセットで解く。`recurrence_id` は規則の名目の時刻のまま。2 回ある時刻は先の回。
- DTSTART は、規則に合わなくても最初の回として含め、`COUNT` に数える。API と画面での新しい系列の作成では、合わなければ 422 `dtstart_not_in_rule` にする。
- 長さは、DTEND で受けたら正確な秒を全回に足す。DURATION で受けたら名目の長さを各回の壁時計の開始に足してから解く。受けた形を保ち、書き出しで同じ形で返す。
- `UNTIL` は解いた UTC と比べ、等しい回を含める。RDATE と EXDATE が同じ回なら、EXDATE が勝つ。
- 計算の量は、1 回の展開で候補 200,000 個、空の周期 1,000 回までに制限する。
- 参照の実装が 1・a と違う答えを返したら、RFC の節と理由を書いて許可リストに入れる（QA の承認）。

### 他の案を選ばなかった理由

- **2（捨てる）**：毎週の会議が夏時間の始まりの週だけ消え、利用者は欠けに気づきにくい。展開とその他の経路（単発の予定の `resolve`）で、存在しない時刻の扱いが 2 通りになる。
- **b（DTSTART を含めない）**：利用者が作った最初の予定が画面から消える。CalDAV のクライアントの多くは DTSTART を最初の回として表示すると見込む（相互運用の試験で確かめる。未検証）。
- **c（すべて拒否）**：外部から来た招待を受けられなくなる。

## Consequences

- 良くなること：
  - 展開・空き時間・リマインダー・画面で、存在しない時刻の扱いが 1 つになる。
  - 回が黙って消えない。
  - 参照との性質ベーステストの食い違いの理由が、初めから 2 つに決まる。
- 引き受けるコスト：
  - RFC 5545 の 3.3.10 節の文言と違う（[ADR-0007](0007-interop-standards-scope.md) の「RFC との意図した違い」の D1）。3.3.10 節に従う外部のカレンダーとは、夏時間の始まりの回の有無が食い違う。相互運用の試験で、対象のクライアントの振る舞いを記録する。
  - 許可リストの管理が要る。

## Confirmation

- 性質ベーステスト：PROP-REC-001（参照との一致、許可リストつき）、PROP-REC-005（窓の分割）、PROP-REC-008（計算の量）。
- 例示テスト：[events-and-recurrence.md](../architecture/events-and-recurrence.md) の 4.2〜4.7 節の例。
- 相互運用の試験：夏時間の始まりの週をまたぐ毎週の予定を、対象のクライアントへ送り、回の有無と時刻を記録する。
