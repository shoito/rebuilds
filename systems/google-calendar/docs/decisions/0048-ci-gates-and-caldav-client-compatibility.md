# ADR-0048: CI の関門は変更のパスで足し、外すラベルを持たない。展開と参照の性質ベーステスト、tzdb の版の差分、`redact()` の経路の性質、記録した CalDAV・iMIP の通信の再生を PR の必須にする。CalDAV のクライアントとの互換は、PR の再生、夜間の実物のクライアントの試験場（macOS・iOS のシミュレーター・Android のエミュレーター）、リリースの前の手動の表の 3 段で確かめる

## Context

[quality.md](../quality.md) の 2.2 節は、テストのレベルと実行のタイミングを決めた。delivery の領域は、それを CI の関門に落とす。

- 展開・時刻・権限・写し・差分の同期の誤りは、エラーにならずに残る（[quality.md](../quality.md) の冒頭）。少数の例示テストでは見つからず、性質ベーステストの試行の数と、回帰のシードが頼りになる。
- 性質ベーステストの失敗を、再実行で緑にしたくなる。エージェントは期待値を緩めがちである（[quality.md](../quality.md) の 3 節の eval）。
- CalDAV のクライアント（iOS・macOS のカレンダー、Thunderbird、DAVx5）は、OS とアプリの更新で振る舞いが変わる。記録した通信の再生は、本システムの変更の後退を見つけるが、クライアントの新しい振る舞いは見つけない。
- 手動の確認は、リリースのたびには重い。

## Options

関門の足し方：

1. **変更のパスで関門を足し、外すラベルを持たない**
2. すべての PR ですべての関門を回す
3. 作成者がラベルで関門を選ぶ

CalDAV のクライアントとの互換：

- a. **PR の再生、夜間の実物のクライアントの試験場、リリースの前の手動の表の 3 段**
- b. PR の再生と、リリースの前の手動の表だけ
- c. 実物のクライアントの試験場だけ

## Decision

1 と a を採用する。

### パスで足す関門

| 区分 | パス（開発リポジトリ） | 足す関門 |
| --- | --- | --- |
| 展開 | `packages/recurrence`、`packages/ical` | 参照との性質ベーステスト 20,000 試行（既定の 2,000 に加えて）、回帰のシードの全部、iCalendar の往復 |
| 時刻 | `packages/tz`、`packages/tzdata` | tzdb の版の差分の試験（[quality.md](../quality.md) の 2.2.1 節 B）、差分の報告の生成（なければ失敗）、3 つの `TZ` |
| 権限 | `packages/policy` | `redact()`・`can()` の決定表の全行、漏れの経路の表の全行の性質ベーステスト |
| 書き込み | `packages/writer`、マイグレーション | 差分と全件の一致の性質（[quality.md](../quality.md) の 2.2.1 節 G）、ログを通らない書き込みの禁止、マイグレーションの比較 |
| 招待 | `packages/itip`、`services/itip-delivery`、`services/imip-*` | 配送のシミュレーター 2,000 の列、iMIP の再生 |
| CalDAV | `services/caldav` | CalDAV の再生の全部、表の外の入力の表駆動テスト |
| 画面の入力 | `apps/web/src/input`、`apps/web/src/views` | IME の決定表（DT-CLI-001）、配置の性質（PROP-CLI-002）、ドラッグの遅延のベンチマーク |
| セキュリティの機微 | 認証、トークン、KMS、WAF、`packages/ingress-limits` | `security:sensitive`（2 人の承認） |

- **性質ベーステストの失敗を、再実行で緑にしない。** 失敗したシードを縮めて `regressions/` に足す PR を先に出す（[quality.md](../quality.md) の 2.3 節）。
- **テストの削除・skip・期待値の緩和・参照との食い違いの許可リストへの追加**は、CI が差分から見つけ、QA の承認を求める。

### CalDAV のクライアントとの互換

| 段 | いつ | 中身 | 見つけるもの |
| --- | --- | --- | --- |
| 1. 再生 | PR（CalDAV・招待・`packages/ical` の区分） | 対象のクライアントの記録した要求の列を再生し、応答と保存の結果を確かめる（[quality.md](../quality.md) の 2.2.1 節 H） | 本システムの変更の後退 |
| 2. 実物の試験場 | 夜間（staging）、と OS・アプリの新しい版（ベータを含む）が出たとき | 実物のクライアントを自動で動かす（下の表）。場面は K9 の表の自動にできる分 | クライアントの新しい振る舞い、記録の古さ |
| 3. 手動の表 | リリースの前（CalDAV・招待に触れたリリース）と、月 1 回 | クライアント × 場面の表を人が確かめる（K9） | 自動にできない場面（通知、画面の表示、外部のカレンダーの iMIP） |

試験場の構成（staging の監視用のテナントに、合成のアカウントでつなぐ）：

| クライアント | 動かし方 | 備考 |
| --- | --- | --- |
| macOS のカレンダー | macOS のランナーで、構成プロファイルで CalDAV のアカウントを入れ、EventKit を使う小さな試験のアプリで作成・変更・削除し、サーバーの状態と比べる | 構成プロファイルでの CalDAV のアカウントの追加と、EventKit からの同期の起こし方は **未検証**（E8 の `caldav-client-lab` で確かめる） |
| iOS のカレンダー | 同じ macOS のランナーの iOS のシミュレーターで、同じ形 | シミュレーターで CalDAV のアカウントが同期するかは **未検証** |
| DAVx5 | Android のエミュレーター。DAVx5 にアカウントを入れ、CalendarContract のプロバイダーに書いて同期させる | DAVx5 の同期の起こし方（手動の同期の操作）を UI の自動化で行う |
| Thunderbird | 自動化の方法を E8 で調べる。見つからなければ段 3 だけ | **未検証** |

- 試験場の結果が段 1 の記録と違えば、記録を取り直す PR を作る（クライアントの振る舞いが変わった）。本システムの直しが要るかは Dev が判断する。
- 試験場の結果は、クライアントの種類と版ごとに保存し、K9 の判定と `caldav-client-regression.md` の調査に使う。

### 他の案を選ばなかった理由

- **2（すべての関門）**：性質ベーステストの夜間の量（200,000 試行）を PR ごとに回すと 1 時間を超える。
- **3（ラベル）**：エージェントも人も、遅い関門を外しがちである。
- **b（再生と手動だけ）**：OS の更新の振る舞いの変化が、利用者の報告まで見つからない。
- **c（試験場だけ）**：試験場は遅く不安定で、PR の関門にできない。自動にできない場面が残る。

## Consequences

- 良くなること：
  - 核に触れる PR は、必ず重い関門を通る。
  - OS のベータの段階で、CalDAV のクライアントの変化に気づける。
- 引き受けるコスト：
  - macOS のランナーと Android のエミュレーターの費用と保守。
  - 試験場の自動化の一部は未検証で、手動に残る場面がある。
  - 核に触れる PR の CI が 30 分を超えることがある。

## Confirmation

- CI の設定の検査：上の表のパスと関門の対応を、設定のファイルから機械で確かめる。関門を外すラベルの定義がない。
- 週次：夜間の性質ベーステストと試験場の結果の要約（新しい失敗のシード、記録の取り直しの数）を QA が見る。
- 指標：試験場で見つかった互換の問題のうち、利用者の報告より先に見つかった割合（目標 80%）。
