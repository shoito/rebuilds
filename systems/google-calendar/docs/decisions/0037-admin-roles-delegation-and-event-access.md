# ADR-0037: 管理の役割を 6 つにし、`super_admin` 以外はグループの範囲に委任できる。役割は予定の中身を見る権限を含まない。管理者による従業員の予定の閲覧は、法務の L8 の結論までフラグの裏に置き、理由と期間を書いた閲覧の許可・`can()` の入力・監査ログの記録の仕組みだけを作る

## Context

[intent.md](../intent.md) は、組織の管理（利用者、グループ、会議室、共有の方針）と監査ログを MVP に含め、法務の L8 として「組織の管理者・監査の担当が、従業員の予定（`private` を含む）を見られる範囲、就業規則・社内規程での周知の要否、監査ログでの閲覧の記録」を挙げる。L8 の結論まで、E11 の管理者の閲覧の機能の spec を承認しない。

日本の中堅・大企業では、部署ごとに管理の担当を分けることが多い（本システムの想定）。

本家は、特権の管理者と「カレンダーの管理」の権限を持つ管理者が、カレンダーの共有に関係なく、全員のカレンダーの予定の詳細を見られる（[Set Google Calendar sharing options](https://knowledge.workspace.google.com/admin/calendar/set-google-calendar-sharing-options)、2026-10-04 に確認）。本家の管理の役割の一覧と委任の細部は、カレンダーの資料の範囲では確かめていない（未検証）。

## Options

役割と委任：

1. **6 つの役割（`super_admin`・`user_admin`・`calendar_admin`・`resource_admin`・`auditor`・`helpdesk`）。`super_admin` 以外は、組織の全体かグループの範囲で付ける**
2. 管理者は 1 種類（全部ができる）
3. 操作ごとの権限を自由に組み合わせる独自の役割

予定の中身の閲覧：

- a. **役割に含めない。法務の L8 の結論までフラグの裏で、閲覧の許可（理由・期間・範囲）の仕組みだけを作る**
- b. 本家と同じく、カレンダーの管理の役割に全員の予定の閲覧を含める
- c. 管理者の閲覧を持たない

## Decision

1 と a を採用する。詳細は [accounts-and-orgs.md](../architecture/accounts-and-orgs.md) の 13・14 節。

- 役割：`super_admin`（全部）、`user_admin`（利用者・グループ・セッション）、`calendar_admin`（共有の方針・共有のカレンダー・引き継ぎ・予約ページの方針）、`resource_admin`（会議室・設備）、`auditor`（監査ログ）、`helpdesk`（セッションとアプリ用のパスワードの取り消し、ディレクトリの閲覧）。
- 委任の範囲：`super_admin` 以外は、組織の全体か、指定したグループ（入れ子を含む）の範囲。判定は `can(actor, "admin:<操作>", target)` で、役割と範囲の表を `packages/policy` に置く。最後の `super_admin` を外せない。
- 管理のすべての書き込みは、主体・役割・範囲・対象・変わった項目の名前を監査ログに書く。
- **役割は予定の中身を見る権限を含まない。**
- 予定の閲覧は、`admin_event_access` の能力（`super_admin` だけが付ける）を持つ管理者が、対象・理由・期間（最長 24 時間）・範囲（カレンダー、`private` を含めるか。既定は含めない）を書いた閲覧の許可（`admin_access_grants`）を作って行う。`redact()` は許可を入力に、範囲の中だけ全体を返す。許可と、読んだ予定の ID を、監査ログに必ず残す。2 人目の承認（`admin_event_access_approval`）と本人への通知（`admin_event_access_notify`）は方針として持ち、既定は L8 の後に決める。
- 機能は `release.admin-event-access` のフラグの裏に置き、L8 の結論まで本番で有効にしない。`redact()` の決定表への行の追加は sharing-and-acl の担当。

### 他の案を選ばなかった理由

- **2（1 種類）**：部署ごとの担当に全部の権限を渡すことになり、最小の権限にならない。
- **3（自由な組み合わせ）**：組み合わせの試験が膨らむ。MVP は固定の役割で始め、声があれば足す。
- **b（本家と同じ）**：法務の L8（労働者のプライバシー、周知、記録）の結論の前に、最も広い形を既定にすることになる。後から狭めるのは難しい。
- **c（持たない）**：内部の調査や退職の後の引き継ぎで要る場面がある（本システムの想定）。L8 の結論で持つと決まったときに、仕組みが後から足せない形になっているのを避ける。

## Consequences

- 良くなること：
  - 部署ごとに最小の権限で管理を任せられる。
  - 管理者の閲覧は、理由・期間・範囲を持ち、必ず記録される形でしか起きない。
  - L8 のどの結論（持たない、承認つき、通知つき、`private` を含む・含まない）にも、方針の値で合わせられる。
- 引き受けるコスト：
  - 本家の管理者に慣れた組織には、予定の中身が既定で見えないことが不便に見えうる。
  - 閲覧の許可の画面と、読んだ予定ごとの記録を作る費用。
  - L8 の結論までフラグの裏のコードを保つ。`release.*` は 100% の後 30 日で消す規則の例外として、[runbooks/README.md](../runbooks/README.md) の 3 節の「長く残すフラグの一覧」に載せる。
