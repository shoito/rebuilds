# Runbook: 災害復旧

- Owner: Ops
- 対応するアラート: AZ の障害（複数の Media Node の `dead`、ECS・Aurora・Valkey の AZ の異常）、東京のリージョンの障害、`AuroraGlobalDBRPOLag`、大阪の待機の構成の異常（[observability.md](../architecture/observability.md) の 6 節）
- 最終確認日: 2026-09-27

方針は [ADR-0050](../decisions/0050-disaster-recovery-and-edge-migration.md)、構成は [infrastructure.md](../architecture/infrastructure.md) の 8 節にある。

## 症状

| 場面 | 兆候 |
| --- | --- |
| A. AZ の障害 | 1 つの AZ の Media Node が一斉に `dead`、同じ AZ の TURN・ECS のタスクの異常、AWS Health の AZ の告知 |
| B. 東京のリージョンの障害 | 東京の API・シグナリングの合成の監視が全部失敗、大阪からの東京の監視の失敗、AWS Health の告知 |
| C. Aurora の障害・複製の遅延 | Aurora のフェイルオーバーのイベント、`AuroraGlobalDBRPOLag` が 60 秒を超える |
| D. Valkey の障害 | ElastiCache のフェイルオーバー、全会議の `epoch` の上昇 |
| E. 論理的な破損 | 誤ったマイグレーション・ジョブによる行の削除・書き換え |

## 影響

| 場面 | 影響 | 目標 |
| --- | --- | --- |
| A | その AZ の Media Node の会議の音声が一時的に止まり、別の AZ の Node へ付け替わる | 音声が 5 秒以内（p95。NFR-004） |
| B | 東京の全会議の制御が止まる。東京の Media Node が生きていればメディアは続く。新しい参加・予定・録画の参照ができない | 大阪で新しい会議を受けるまで 1 時間（RTO）。Aurora の RPO 1 分。**既定案** |
| C | 失ってはならない変更（退出させる、ロック、役割）が失敗する。ミュート・入室などは続く | Multi-AZ のフェイルオーバーで 1〜2 分 |
| D | 切り替えが 4.5 秒を超えると、全会議の Actor が止まり、取り直す（`epoch` が上がる）。メディアは続く | 制御が 10 秒〜数十秒で戻る |
| E | 行の欠け・誤り | 範囲による |

- B では、**進行中の会議は守らない**（ADR-0050）。待合室、チャット（会議の間のもの）、進行中の録画の未合成の区切りを失う。

## 確認

1. どの場面かを決める。AZ の障害を、リージョンの障害と取り違えない（1 つの AZ だけなら A）。
2. 影響の範囲：落ちた Media Node の数と AZ、付け替えの時間の分布、参加の成功、制御の回復。
3. AWS Health とサポートのケースで、AWS の側の見込みを確かめる。
4. B のとき：大阪の待機の構成の状態（Aurora の二次の遅延、ECS の最小のタスク、大阪の Media Node 3 台の自己診断、BYOIP の大阪の /24 の広告、KMS のレプリカ）。

## 対処

### A. AZ の障害

1. **付け替えが進んでいるかを見る。** 落ちた AZ の Node の会議は、別の AZ の予備の Node へ自動で付け替わる（[ADR-0013](../decisions/0013-media-node-failover-and-reattach.md)）。付け替えの時間の分布を見る。
2. **その AZ を新しい会議の候補から外す。** Media Assignment Service の AZ の重みを 0 にする。Auto Scaling が、残りの 2 つの AZ に台を足す（AZ ごとにピークの半分の容量を持っているので、足すまでの間も受けられる）。
3. **予備の Node の溢れを見る。** 残りの AZ の点が 0.85 を超える Node が多いなら、[incident-response.md](incident-response.md) の「Media Node の障害の波」の 2〜4 に従う。
4. **TURN**：クライアントは別の AZ の TURN を候補に持つ。落ちた AZ の TURN を参加の応答の一覧から外す。
5. **制御の側**：ECS のタスクは別の AZ で起動し直る。Aurora・Valkey のフェイルオーバーは C・D を見る。
6. **戻す**：AZ が回復したら、Media Node の自己診断を確かめてから、AZ の重みを段階的に戻す（25% → 100%。1 時間ずつ）。

### B. 東京のリージョンの障害（大阪への切り替え）

判断はインシデントの指揮者が行い、Ops の責任者が承認する。**自動では切り替えない。** 東京の部分的な障害（1 つのサービス、一時的な網の劣化）を、データを失う切り替えと取り違えないため。

1. **切り替えを決める。** 目安：東京の API・シグナリングの合成の監視が 15 分失敗し続け、AWS の側の見込みが 1 時間以内に立たない。
2. **受付を止める。** `ops.join_admission` を 0 にする（東京が部分的に生きている場合に、新しい書き込みを止める）。
3. **DB を昇格させる。** Aurora Global Database の大阪の二次を昇格させる。東京の writer が生きていれば switchover（RPO 0）、応答しなければ `failover-global-cluster --allow-data-loss`（大阪のリージョンで実行）。
4. **アプリを広げる。** 切り替えのワークフロー（大阪で実行できる GitHub Actions）で、大阪の ECS のサービスのタスク数を上げる。大阪の Valkey は空から始める（会議の状態は失われている）。
5. **メディアを広げる。** 大阪の Media Node（c6gn.16xlarge）と TURN の Auto Scaling の最大と最小を上げる。**大阪の EC2 の在庫は保証されない。** 起動の失敗が続くなら、予備の種類（c6in.32xlarge）を足し、受けられる同時の参加者の数（訓練で測った値）を運用の上限にする。
6. **入口を切り替える。** `global/edge` の変数（`active_region`）を大阪にして apply する（CloudFront のオリジンを大阪の ALB に）。シグナリングの WebSocket も同じ配信なので、同時に切り替わる。
7. **確かめる。** 社内の監視用の組織で、合成の監視の会議（参加、音声、画面共有、予定の作成）が大阪で成功する。
8. **受付を段階的に開く。** `ops.join_admission` を平常の 25% → 50% → 100% に、15 分ごとに上げる。**東京で会議に入っていた人が一斉に入り直す**ので、参加の集中（再接続の嵐と同じ形）を見ながら開く。
9. **組織へ告知する。** 進行中だった会議は入り直しが要ること、失われたもの（会議の間のチャット、待合室、進行中の録画の一部）、大阪で使えない・劣るもの（字幕は Transcribe の大阪での提供が**未検証**。使えなければ字幕を止める）。
10. **進行中の東京の会議**：東京の Media Node が生きていれば、メディアは続いている。クライアントはシグナリングが 60 秒戻らなければ入り直しの画面を出す。東京の Media Node は、東京が回復した後に会議が 0 になるのを待って片付ける。

**東京へ戻す（フェイルバック）**：東京の回復の後、Aurora が東京を二次として加え直す。複製が追いついたら、別の計画作業として、夜間に switchover（RPO 0）で戻し、入口を東京に戻す。大阪の会議は、自然に終わるのを待つ（大阪の Media Node はそのまま動く）。急がない。

### C. Aurora の障害・複製の遅延

1. **Multi-AZ のフェイルオーバー**：自動で進む。その間、Actor は失ってはならない変更に `err{code: unavailable, retryable: true}` を返し、他の操作は続く（[signaling-and-meetings.md](../architecture/signaling-and-meetings.md) の 12 節）。フェイルオーバーの後、書き込みの成功を確かめる。
2. **複製の遅延**（`AuroraGlobalDBRPOLag` が 60 秒超）：東京の writer の書き込みの量（朝の立ち上がりの参加・退出の行、outbox）と、リージョン間の回線を見る。10 分を超えて続くなら SEV3 にし、AWS サポートにケースを開く。

### D. Valkey の障害

1. フェイルオーバーの時間を見る。4.5 秒を超えたなら、全会議の Actor が止まり、取り直している（`epoch` が上がる）。メディアは続く。
2. 取り直しの集中で Actor Host の CPU が上がっていれば、Actor Host のタスクを足す。
3. スナップショットが失われた会議は、クライアントの申告と Aurora から戻る（[signaling-and-meetings.md](../architecture/signaling-and-meetings.md) の 10.2 節）。
4. 詳しい手順は `valkey-failover-meetings.md`（signaling の領域の提案）。

### E. 論理的な破損

1. 原因の機能のフラグを切る、原因のジョブを止める。
2. 破損の直前の時刻を、ログと監査ログから特定する。
3. Aurora の PITR で、隔離した VPC に新しいクラスタを復元する。本番のクラスタは上書きしない。
4. 失われた行だけを取り出して戻す。**退出させた人の ban、組織の鍵のかかった設定、削除した録画の記録を戻すときは、その後の変更を監査ログで確かめる。** 解除した ban、消した録画を戻さない。
5. 復元したクラスタを消す。

### F. 訓練

| 訓練 | 頻度 | 環境 | 確かめること |
| --- | --- | --- | --- |
| AZ の障害 | 四半期 | media-staging（負荷のボットで会議を載せる） | 1 つの AZ の Media Node を全部止め、全参加者の音声が 5 秒以内に戻る（p95）。残りの AZ の点 |
| 東京のリージョンの障害 | 四半期 | staging・media-staging | B の手順を最後まで行う。RTO 1 時間以内。大阪で受けられた同時の参加者の数（大阪の在庫の実測） |
| 本番の switchover | 年 1 回 | 本番（夜間） | 大阪で予定の作成と参加を受け、東京へ戻す |
| 大阪の待機の構成の確認 | 月次 | 本番 | [infrastructure.md](../architecture/infrastructure.md) の 8.4 節の項目 |
| PITR からの復元 | 四半期 | 本番の中の隔離した VPC | 復元の時間、行数、暗号文（パスコード、チャット）が復号できること |

結果（時間、受けられた参加者の数、問題点）を、この runbook の末尾の記録に残す。

## エスカレーション

- A で付け替えの時間の p95 が 10 秒を超える → SEV1 に上げ、メディアの Dev の当番を呼ぶ。
- B の判断 → Ops の責任者。告知の文面は PM と合意する。
- B で大阪の EC2 が起動できない → AWS サポート（容量の相談）、Ops の責任者（受けられる数の上限の判断）。
- E で ban や録画の削除の記録を戻す → セキュリティの担当の承認。
- AWS 側の障害 → AWS サポートにケースを開く。

## 事後

- 調査結果を Intent の Issue として起票する（Maintain 段）。
- 実際の切り替えと訓練で計測した RTO・RPO、付け替えの時間、大阪で受けられた参加者の数を記録し、目標を満たさなければ Intent を起票する。
- 大阪の在庫の実測が足りなければ、オンデマンドの容量の予約を持つかを Ops の責任者と PM が判断する（[ADR-0050](../decisions/0050-disaster-recovery-and-edge-migration.md) の見直し）。
- この手順で足りなかったことを、ここに反映する。
