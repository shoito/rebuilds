# ADR-0052: 音声の品質は E-model（G.107）の式で MOS を推定し、試験の ViSQOL で係数を合わせる。SLO は「良い参加者・分」の割合と、参加の成功率・脱落率・付け替えの時間で持つ

## Context

intent.md の成功の基準は、K1（遅れ）、K2（参加の速さと成功率）、K3（損失 20% で MOS 3.0 以上）、K4（意図しない脱落 0.5% 以下、付け替えで 5 秒以内に音声）、K5（体感の品質）である。K3 は試験の環境で ViSQOL を使って測る（[codecs-and-bandwidth-adaptation.md](../architecture/codecs-and-bandwidth-adaptation.md) の 11.2 節）。本番では、元の音声がないので ViSQOL（参照ありの評価）を使えない。

確かめたこと（いずれも 2026-09-27 に確認）：

- ITU-T G.107（06/2015、有効）は E-model で、遅れ・損失・符号器の劣化から評価値 R を計算し、R から MOS を推定する計画のためのモデルである（[G.107](https://www.itu.int/rec/T-REC-G.107)）。広帯域の版は G.107.1（06/2019）（[G.107.1](https://www.itu.int/rec/T-REC-G.107.1)）。
- ITU-T P.1203（10/2017）は、信頼できる伝送の上の、プログレッシブダウンロードと適応型のストリーミングの品質のモデルである（[P.1203](https://www.itu.int/rec/T-REC-P.1203)）。会議の実時間のメディアには合わない。
- ITU-T G.1070（06/2018）は、映像電話の意見のモデルである（[G.1070](https://www.itu.int/rec/T-REC-G.1070)）。符号器ごとの係数が要る。
- Opus の E-model の係数（`Ie`・`Bpl`）は、ITU-T G.113 の付録の値を確かめていない（**未検証**）。

webrtc-stats のフリーズの定義は [ADR-0051](0051-qos-telemetry-pipeline.md) の Context にある。

## Options

音声の推定：

1. **E-model の式を使い、`Ie`・`Bpl` などの係数を、試験の環境の ViSQOL の値に合わせる**
2. 損失の率と RTT の閾値だけで良し悪しを決める
3. 参照なしの機械学習のモデル（端末で音声を評価）

映像：

- a. **webrtc-stats のフリーズと、受けた解像度・fps で見る。映像の MOS は推定しない**
- b. G.1070 か P.1203 で映像の MOS を推定する

## Decision

1 と a を採用する。詳細は [observability.md](../architecture/observability.md) の 4・5 節。

- **音声の MOS の推定（`mos_est`）**：受けた音声の流れごと、10 秒の窓ごとに計算する。
  - 実効の損失 `Ppl` ＝（`concealedSamples` − `silentConcealedSamples`）の増分 ÷ `totalSamplesReceived` の増分 × 100。FEC と RED で直した分は含まれない（直した後に残った損失を見る）。
  - 片道の遅れ `Ta` ＝ RTT ÷ 2 ＋ ジッタバッファの遅れ（`jitterBufferDelay` ÷ `jitterBufferEmittedCount` の増分）＋ 固定の分（取り込みと再生、既定 60ms。試験で測って直す）。
  - `R = R0 − Idd(Ta) − Ie,eff`、`Ie,eff = Ie + (95 − Ie) × Ppl / (Ppl / BurstR + Bpl)`。`R0` と `Idd` の式は G.107 に従う。`BurstR` は 1（ランダム）とする。
  - `MOS = 1 + 0.035R + R(R − 60)(100 − R) × 7 × 10⁻⁶`（0 < R < 100）。狭帯域の尺度で出す（上限は約 4.4）。広帯域の尺度（G.107.1）には、係数を確かめてから移る。
  - `Ie`・`Bpl` は、`media-lab` の回線の劣化の試験（損失 0〜30%、揺らぎ 0〜100ms）で、同じ条件の ViSQOL の値との誤差が最小になるように決める。係数を変える PR は、QA の承認を要する。**推定は ViSQOL と同じではない。** 本番の値は、傾向と比較のために使う。
- **映像**：フリーズの回数と長さ（webrtc-stats の定義）、1 秒以上のフリーズ、受けた解像度と fps。映像の MOS は推定しない。G.1070 は係数を用意してから検討する。
- **SLI と SLO**（S1。**既定案**、Ops と PM の承認を要する）：

| SLI | 定義 | SLO（28 日） |
| --- | --- | --- |
| 参加の成功 | 参加のボタンから 10 秒以内に音声の送受信が始まった試行 ÷ 試行（待合室にいた時間を除く） | 99.5%（K2） |
| 参加の速さ | 参加のボタンから音声までの p95 | 3 秒（NFR-002） |
| 良い音声の分 | 受けた音声の `mos_est` が 3.6 以上で、隠しの率が 5% 未満だった参加者・分 ÷ 音声を受けた参加者・分 | 97% |
| フリーズのない分 | 1 秒以上のフリーズがなかった参加者・分 ÷ 映像を受けた参加者・分 | 95% |
| 意図しない脱落 | `leave_reason = dropped` の数 ÷ 参加者・時間 | 0.5% 以下（K4） |
| 付け替えの時間 | `media.reattach` から音声の最初のパケットまで 5 秒以内の割合 | 95%（NFR-004） |
| API | 参加・予定の API の成功（5xx でない）の割合 | 99.95%（NFR-005） |
| 制御の回復 | Actor の持ち主を失ってから、最初の `ack` まで 10 秒以内の割合 | 99%（NFR-004） |

- 良い音声の分とフリーズのない分は、利用者の回線に原因がある分も含む。原因の切り分けのため、Media Node の側の数（送り手の上りの損失、Node の転送の遅れ、ENA の超過）を同じ窓で並べる。**呼び出しのアラートは、サーバーの側の原因を示す数と組み合わせたときだけ鳴らす**（[observability.md](../architecture/observability.md) の 6 節）。
- 2 を採らない理由：損失と遅れの組み合わせの影響を 1 つの数にできず、閾値の意味を説明しにくい。
- 3 を採らない理由：端末の CPU を使う。音声の中身を端末の外に出さなくても、モデルの配布と検証の手間が大きい。
- b を採らない理由：P.1203 は実時間の会議に合わない。G.1070 は係数がない。

## Consequences

- 良くなること：
  - 本番でも、損失と遅れを 1 つの音声の品質の数で見られる。試験の値と同じ尺度に寄せられる。
  - SLO が、intent.md の K2・K3・K4 に直接つながる。
- 引き受けるコスト：
  - 係数の合わせ込みと、ブラウザの版ごとの見直し（NetEQ の振る舞いが変わる）。
  - 良い音声の分の SLO は、利用者の回線の悪さでも減る。SLO の違反を、そのままサーバーの障害とみなせない。

## Confirmation

- 回線の劣化の試験：`loss-5-random`・`loss-20-random`・`jitter-100` で、`mos_est` と ViSQOL の差の絶対値の平均が 0.3 以下。
- 性質ベーステスト：任意の `getStats` の列（カウンターのリセット、欠けた項目を含む）で、`mos_est` は 1〜4.5 の範囲で、損失が増えれば下がる（他が同じとき）。
- ダッシュボード：各 SLI に、[observability.md](../architecture/observability.md) の 6 節のアラートと runbook が付いている。
