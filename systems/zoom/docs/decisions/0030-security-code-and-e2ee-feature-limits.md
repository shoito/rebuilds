# ADR-0030: 会議のセキュリティのコードは MLS の epoch_authenticator から作り、E2EE で動かない機能は 3 か所で拒む。参加者の上限は S1 で 100 人

## Context

[ADR-0004](0004-encryption-and-e2ee.md) は、参加者が MLS のエポックから導いた「会議のセキュリティのコード」を見て、互いに読み上げて確かめられるようにすると決めた。AS（本システム）が偽の参加者を作る攻撃は、このコードの照合で見つける前提にした。E2EE の会議では、録画・字幕・電話からの参加・AI の機能を動かさず、参加者の上限を S1 で 100 人にした。

調べて分かったこと（いずれも 2026-09-27 に確認）。

- 本家は、リーダーの公開鍵から 39 桁の数字（約 129 ビット）を作り、リーダーが読み上げて全員が比べる。リーダーが替わると確かめ直しを促す（[Zoom Cryptography Whitepaper](https://github.com/zoom/zoom-e2e-whitepaper) v4.7 の 7.7 節）。
- MLS の `epoch_authenticator` は、鍵のスケジュールから導かれ、エポックの全員だけが知る。帯域外の確認に使える（[RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html) の 8.7 節）。OpenMLS は `epoch_authenticator()` を持つ（[docs.rs の MlsGroup](https://docs.rs/openmls/latest/openmls/group/struct.MlsGroup.html)）。
- 本家の E2EE の会議では、AI の機能、クラウド録画、ライブの文字起こしなどが使えず、参加者は 1,000 人まで（[End-to-end encryption for meetings](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0065408)）。

コードで何が分かるかを整理する。

- 全員のコードが一致すれば、全員が同じエポック（同じ名簿、同じ鍵）にいる。サーバーが参加者を別々のグループに分ける中間者の攻撃は見つかる。
- AS が偽の証明書で「幽霊の参加者」を正規の名簿に入れた場合、全員のコードは一致する。見つけるには、MLS の名簿そのものを画面に出す必要がある。

## Options

1. **コードは `epoch_authenticator` から 40 桁。参加者の一覧を MLS の名簿から作り、シグナリングの一覧と突き合わせる。E2EE で動かない機能は API・Actor・Media Node の 3 か所で拒む。上限は S1 で 100 人**
2. **本家に寄せ、1 人（主催者）の公開鍵からコードを作る**
3. **コードを出さず、名簿の表示だけにする**

## Decision

1 を採用する。

- **コード**：`Digits(SHA-256("<brand>-e2ee-security-code-v1" || group_id || epoch_authenticator))` から 40 桁の 10 進数を作り、5 桁ずつ 8 組で出す。エポックが変わると変わる。画面に「エポック N のコード」と、確かめた後に出入りした人の数を出し、人が入ったら確かめ直しを促す。
- **読み上げ**：主催者が読み上げ、他の人が自分の画面と比べる。合わなければ、主催者が会議を終えて作り直す。
- **名簿**：E2EE の会議の参加者の一覧は MLS の名簿から作り、シグナリングの一覧と突き合わせる。MLS にいてシグナリングにいない人は赤い警告、逆は「暗号化の準備中」、表示の名前の SHA-256 が合わない人は警告。各参加者の証明書の指紋の先頭 8 桁を出す。
- **動かない機能**：クラウド録画、ライブ字幕・文字起こし、電話からの参加、AI の機能、チャットの保存。次の 3 か所で拒む。
  - API：E2EE と、これらの機能の設定の組み合わせを受けない。
  - Meeting Actor：開始の命令を拒み、Recorder・Transcriber の参加を拒む。
  - Media Node：E2EE の開催で、Recorder・Transcriber の transport を作らない。
- E2EE の入り・切りは開催の前だけ。途中で変えない。
- **上限**：S1 は 100 人。コミットの作成と処理の時間を 300 人で測り、NFR-008 の予算に収まれば S2 で 300 人に上げる。
- 2 は、コードがエポックで変わらず読み上げの手間が少ない。ただし、主催者の鍵が正しいことしか確かめず、名簿の正しさは、主催者の署名した一覧を別に配る仕組みが要る。MLS では、全員の状態の一致を 1 つの値で確かめられる 1 のほうが単純。
- 3 は、中間者の攻撃（グループの分断）を見つけられない。

## Consequences

- 良くなること：
  - グループの分断と、幽霊の参加者の両方を、利用者が画面で見つけられる。
  - E2EE で動かない機能が、1 か所の抜けで動いてしまうことを防ぐ。
- 引き受けるコスト：
  - コードが人の出入りのたびに変わり、読み上げの手間が増える。
  - 名簿とシグナリングの一覧の突き合わせで、一時的な食い違い（参加の途中）を誤って警告しないよう、猶予（5 秒）が要る。
  - 100 人を超える E2EE の会議は、S1 では作れない。

## Confirmation

- 試験のベクトル：固定の `group_id` と `epoch_authenticator` から、Web とネイティブで同じ 40 桁のコードになる。
- 試験：Actor を改造して参加者を 2 つのグループに分けると、2 つのグループのコードが違う。偽の証明書で MLS にだけ参加者を足すと、全員の画面に警告が出る。
- 試験：E2EE の会議で、録画・字幕の開始の要求が、API・Actor・Media Node のそれぞれで拒まれる（1 か所ずつ無効にしても、残りで拒まれる）。
- 計測（E9）：300 人のグループで、コミットの作成と処理の時間を基準の端末で測り、記録する。
