# ADR-0039: 設定は組織・グループ・ユーザー・会議の順に 1 つの関数で解決し、上の鍵は下で変えられない。安全の項目は開催の開始で解決し直す

## Context

intent.md の MVP は「会議の既定の設定と強制」を求める。組織の管理者は、待合室・録画・チャットなどの既定を決め、利用者に変えさせないようにしたい。

本家は、組織・グループ・ユーザーの 3 段で設定し、上で鍵をかけると下で変えられない。組織の鍵はどのグループにも勝ち、複数のグループに属するときは優先度の高いグループの鍵を継ぐ（[Using tiered settings](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0065579)、細部は検索結果で確かめた。一次の本文は未検証）。鍵をかけていない設定は、利用者が無効にできる。パスコードの要件の変更は、既に予定した会議に効かない（[Managing Zoom Meetings passcodes](https://support.zoom.com/hc/en/article?id=zm_kb&sysparm_article=KB0063160)、2026-09-27 に確認）。

設定の解決は、API（会議の作成）、Actor（開催の開始）、カレンダーの連携、公開 API のすべてで同じでなければならない。どこか 1 か所でも違うと、待合室もパスコードもない会議ができうる（[ADR-0031](0031-waiting-room-and-passcode-rules.md)）。

## Options

1. **組織 → グループ → ユーザー → 会議の順に、1 つの純粋な関数で解決する。鍵は固定の形。安全の項目は開催の開始で解決し直す。ユーザーのグループは S1 で 1 つまで**
2. **1 と同じ。ただし、会議の作成の時点の値を最後まで使う（本家に近い）**
3. **組織の既定と会議の値だけ（グループとユーザーの階層なし）**

## Decision

1 を採用する。詳細は [accounts-and-admin.md](../architecture/accounts-and-admin.md) の 5 節。

- 項目は `settingsRegistry` の 1 つの表で定義する（型、既定、置ける階層、`security` の印）。
- 解決の順：組織の鍵 → グループの鍵 → 会議の値 → ユーザーの値 → グループの値 → 組織の値 → 既定。
- 解決の後に、システムの下限（待合室かパスコード）を当てる。どの階層の組み合わせでも破れない。
- 解決は `resolveSettings(org, group, user, meeting)` の 1 つの純粋な関数で行い、API・Actor・カレンダー・公開 API のすべてがこれを呼ぶ。
- `security: true` の項目（待合室、パスコード、主催者の前の参加、待合室を省く条件、E2EE の許可、外への録画の共有）は、開催の開始のときに解決し直す。既に配った招待のパスコードは作り直さない。
- 解決した値を `meeting_instances.effective_settings` に残す。
- ユーザーが属するグループは S1 で 0 か 1。複数のグループと優先度は S2。
- 2 を採らない理由：管理者が荒らしへの対策として鍵をかけても、既に予定した繰り返しの会議や PMI に何か月も効かない。
- 3 を採らない理由：部署ごとに録画やチャットの方針が違う組織（人事、営業）に応えられない。

## Consequences

- 良くなること：
  - どの経路から作った会議も、同じ規則で設定が決まる。
  - 管理者がかけた安全の鍵が、次の開催から必ず効く。
  - 「どの設定で開かれたか」を後から答えられる。
- 引き受けるコスト：
  - 主催者が予定したときの設定と、開催のときの設定が違うことがある。画面で「管理者の設定で変わりました」を示す必要がある。
  - 複数のグループに属する組織の構造を、S1 では表せない。
  - 項目を足すたびに、表と性質ベーステストの更新が要る。

## Confirmation

- 性質ベーステスト：組織の鍵の項目は常に組織の値（PROP-ADM-001）。解決した値が下限を破らない（PROP-ADM-002）。鍵のない階層の変更が、上の鍵の項目を変えない（PROP-ADM-003）。
- 決定表の試験：解決の表の各行（`DT-ADM-SET-*`）。
- lint：`meetings` の設定を読む処理が、`resolveSettings` を通らずに生の設定を使っていない。
- 本番：`effective_settings` と組織の鍵の不一致を毎日数え、0 でなければアラート。
