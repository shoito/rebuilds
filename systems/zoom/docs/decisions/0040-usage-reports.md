# ADR-0040: 利用状況のレポートは Aurora の参加の記録と毎日の集計の表から作り、S1 ではデータの倉庫を持たない

## Context

intent.md の MVP は「利用状況のレポート」を求める。組織の管理者は、会議の数と分、参加者、ユーザーごとの利用、会議ごとの参加者の一覧、録画の容量を見たい。

- 参加の記録（`meeting_participations`）と会議の開催（`meeting_instances`）は、Actor が Aurora に書く（[ADR-0005](0005-meeting-state-and-signaling.md)、[signaling-and-meetings.md](../architecture/signaling-and-meetings.md) の 17 節）。
- S1 の規模は、同時の会議 5,000、同時の参加者 3 万（[architecture/README.md](../architecture/README.md) の 2 節）。1 日の参加の行は数十万の見込み（**未検証**。E6 の `usage-reports` で E2 のベータの実績から見直す）。
- レポートの集計の問い合わせが、会議の開始と参加の書き込みを遅らせてはならない（NFR-002、NFR-005）。
- 参加の記録の保持の期間は、法務の確認待ち（L6・L8）。

## Options

1. **Aurora の参加の記録から、Worker が毎時・毎日の集計の表を作る。画面は集計の表と、会議ごとの詳細だけを読む。問い合わせは Aurora のリーダーに向ける**
2. **参加の記録を S3 に書き出し、Athena などで集計する（データの倉庫）**
3. **画面の要求のたびに、参加の記録を直接集計する**

## Decision

1 を採用する。詳細は [accounts-and-admin.md](../architecture/accounts-and-admin.md) の 6 節。

- Worker が毎時、終わった会議を `instance_id` ごとに 1 回だけ集計して、`usage_daily`・`usage_user_daily` に足す（冪等）。
- 画面は集計の表と、1 会議ずつの詳細だけを読む。期間は最大 1 年（詳細は 1 か月ごと）。
- 大きな書き出しは非同期で S3 に書き、署名付きの URL（24 時間）で渡す。ファイルは 7 日で消す。
- 問い合わせは Aurora のリーダーに向ける。
- 保持：参加の記録 12 か月、集計 36 か月（L6・L8 で見直す）。
- レポートに会議の中身（チャット、字幕、録画）を入れない。ゲストの IP を出さない。
- 2 を今は採らない理由：S1 の量では、Aurora と集計の表で足りる見込み。DWH の運用と、個人のデータの写しの置き場所が増える。S2 で、量と分析の要求が増えたら新しい ADR で足す。
- 3 を採らない理由：1 年の範囲の集計が、画面を開くたびに走り、Aurora の負荷と遅れが読めない。

## Consequences

- 良くなること：
  - 集計の負荷が本線から切り離され、時刻も読める（毎時）。
  - 集計が冪等なので、止まっても作り直せる。
- 引き受けるコスト：
  - 概要のレポートは最大 1 時間古い。
  - 自由な分析（任意の軸での集計）はできない。
  - 参加の記録の行が 12 か月分たまる。分割（月ごとのパーティション）が要る。

## Confirmation

- 性質ベーステスト：任意の参加の記録の列で、集計の表の合計が直接の計算と一致する。同じ会議を 2 回集計しても変わらない（PROP-ADM-004）。
- 負荷試験：1 万人の組織の 1 か月の CSV の書き出しが、本線の `POST /join` の p95 を悪くしない。
- レビュー：レポートの問い合わせがリーダーに向いている。レポートの項目に会議の中身が入っていない。
