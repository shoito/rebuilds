# ADR-0005: 会議の状態は会議ごとに 1 つの Meeting Actor が持ち、WebSocket のシグナリングと、会議を Media Node に割り当てるサービスで動かす

## Context

会議の中の状態は、次のようなものである。

- 参加者の一覧と、それぞれの役割（主催者、共同主催者、参加者）
- 待合室にいる人、会議のロック、退出させた人
- 誰がミュートか、誰が画面を共有しているか、誰が話しているか
- 誰の映像を、どの層で、誰に送るか（SFU への指示）
- チャットの順序、リアクション、挙手
- 録画・字幕が動いているか
- E2EE の会議では、MLS のメッセージの順序（[ADR-0004](0004-encryption-and-e2ee.md)）

この状態は、1 秒に何度も変わり、会議の全員に同じ順序で届く必要がある。「主催者がロックした直後に入ろうとした人」のように、競合の結果は 1 つに決まらなければならない。一方で、会議が終われば大半は捨ててよい。

他の題材（Slack）は、DB を唯一の正本にし、配信を outbox で行う（Slack の ADR-0002）。会議の中の状態の変化の頻度と遅れの要求（主催者の操作が p95 数百 ms で全員に届く）では、変化のたびに DB に書くのは重い。

MLS は、グループの更新（Commit）を 1 つの順序で配る DS を前提にする（[RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html)）。

## Options

1. **会議ごとに 1 つの Meeting Actor（1 つのノードの上のプロセスの中の状態）が正本になる。持ち主はリースで決め、フェンシングの番号で二重化を防ぐ**
2. **状態を Valkey や DB に置き、ステートレスなシグナリングのサーバーが読み書きする**
3. **状態を Media Node（SFU）に持たせる**

## Decision

1 を採用する。

- **Meeting Actor**：
  - 会議 1 つにつき、ある時点で 1 つの Actor だけが、その会議の状態を変えられる。すべての変更（主催者の操作、参加、チャット、MLS のメッセージ）は Actor に届き、Actor が順番を決めて連番（`seq`）を付け、全員に配る。
  - Actor は Signaling のノード（ECS の上の TypeScript のプロセス）の中で動く。1 つのノードが多数の会議の Actor を持つ。
  - 持ち主はリースで決める。リースは Valkey に置き、フェンシングの番号（`epoch`）を付ける。新しい持ち主は `epoch` を 1 つ上げる。Media Node と Signaling Gateway は、古い `epoch` の指示を拒否する。
  - 状態のスナップショットを、変化のたびに（間引いて）Valkey に書く。失っても、参加者の再接続の時の申告（自分の状態）から組み立て直せる形にする。
  - 残すべきもの（会議の開始と終了、参加の記録、録画の開始と終了、主催者の操作の監査）は、Aurora に outbox と同じトランザクションで書く。チャットの本文は、既定では会議の後に残さない（[ADR-0036](0036-in-meeting-chat-ordering-and-retention.md)）。
- **シグナリングのプロトコル**：
  - クライアントは WebSocket で Signaling Gateway に接続する。Gateway は状態を持たず、会議の ID で持ち主の Actor に中継する。Actor が替わっても、クライアントの WebSocket はそのまま使える。
  - メッセージは JSON にし、型を Zod のスキーマで定義する。スキーマにバージョンを付け、サーバーは Web には今と 1 つ前のバージョンを、ネイティブのアプリ（MVP の後）には 2 つ前のバージョンまでを受ける。最低のバージョン（`min_client_version`）より古いクライアントには更新を求める（[ADR-0008](0008-signaling-protocol.md) の注記）。
  - 状態の配信は「スナップショット＋連番付きの差分」にする。クライアントは最後に受けた `seq` を覚え、再接続の時に差分を求める。差分が古すぎたら、スナップショットを受け取り直す。
  - 参加には、API が発行する短命な参加のトークン（会議、利用者、役割、有効期限、署名）が要る。待合室やパスコードの判定は Actor が行う。
- **Media Assignment Service**：
  - 会議を始めるとき、Actor が、会議を置く Media Node を Assignment Service に求める。Service は Media Node の負荷（参加者の数、帯域、PPS）と、参加者の位置（リージョン）を見て選ぶ。
  - 大きな会議は、会議の途中で Node を足す（カスケード、[ADR-0002](0002-media-topology.md)）。
  - Media Node は、最後に受けた転送の指示のまま動き続ける。Actor が止まっても、メディアは流れ続ける。
- **障害の時**：
  - **Actor のノードが落ちた**：Gateway がリースの切れを検知し、別のノードが `epoch` を上げて Actor を立ち上げる。スナップショットと、クライアントの申告から状態を戻す。メディアは止まらない。目標は 10 秒以内（NFR-004）。
  - **Media Node が落ちた**：Actor は、会議の開始時に決めておいた予備の Node に router を作り、参加者に新しい transport（ICE と DTLS）での接続を指示する。別の Node へは ICE restart ではつなげない（ICE restart は同じ Node の同じ transport の経路を選び直すだけ。[ADR-0013](0013-media-node-failover-and-reattach.md)、[media-server-sfu.md](../architecture/media-server-sfu.md) の 9.3 節）。目標は、音声が 5 秒以内に戻ること（NFR-004）。
  - **Gateway が落ちた**：クライアントが別の Gateway に再接続し、`seq` から差分を受け取る。
- 2 は、シグナリングのサーバーを水平に増やしやすい。ただし、変化のたびに外部の記憶への往復と、競合の解決（楽観ロックの再試行）が要り、遅れが増える。MLS の順序付けとも相性が悪い。
- 3 は、構成が単純になる。ただし、カスケードで会議が複数の Node にまたがると、正本が決まらない。Media Node の障害で状態も失う。

## Consequences

- 良くなること：
  - 会議の中の競合の結果が、1 か所の順序で決まる。性質ベーステストで検証しやすい。
  - 制御とメディアの障害が、互いに伝わりにくい。
- 引き受けるコスト：
  - 1 つの会議の処理は、1 つのノードの 1 つのプロセスに収まる必要がある。1,000 人の会議（S3）の Actor の負荷を計測する。
  - リース、フェンシング、スナップショット、再同期を自分で作り、障害の注入の試験で確かめる必要がある。
  - Gateway から Actor への中継で、1 ホップ分の遅れが増える（同じリージョンの中で数 ms の見込み。**未検証**。E7 の `signaling-load-test` で測る）。

## Confirmation

- 性質ベーステスト：任意の操作の列（参加、退出、ロック、退出させる、再接続、重複した送信）で、全クライアントが最終的に見る状態は、Actor の `seq` 順の状態と一致する。ロックの後に許可された参加は 0 件。
- 障害の注入の試験：Actor のノードを止めても、会議のメディアが止まらず、10 秒以内に主催者の操作が効くようになる。同じ会議に 2 つの Actor を立てても、古い `epoch` の指示は Media Node に拒否される。
- 障害の注入の試験：Media Node を止めてから、全参加者の音声が戻るまでが 5 秒以内。
- 契約の試験：シグナリングのスキーマのバージョンを上げる PR で、受けるバージョン（Web は 1 つ前、アプリは 2 つ前）のクライアントの試験が通る。
