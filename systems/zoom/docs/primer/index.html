Zoom は何をするサービスか

Zoom Meetings は、離れた人どうしが音声・映像・画面共有で話すビデオ会議です。URL を開くと会議に入れ、主催者が参加者を管理します。社外の人も、アカウントなしでブラウザから入ります。

すぐに集まれる

URL を開くだけで、ブラウザから 3 秒程度で音声がつながる。

遅れず、途切れない

話してから届くまで p95 300ms 以内。損失 20% の回線でも音声で会話を続けられる。

安全

待合室とパスコードを既定にする。望めばサーバーも中身を見られない E2EE を選べる。

規模の感覚は、S1 で同時に 5,000 会議・3 万人、1 会議 100 人までです（S2 で 300 人、S3 で 1,000 人）。1 人あたりの帯域は、下り 2.5 Mbps（容量の前提）・上り 0.8 Mbps で見積もります。チャットの題材と違い、データの大半は DB を通らず、メディアサーバーを流れて消えていきます。

設計の文書で効くところintent.md の「Proposed outcome」と成功の基準（K1〜K8）、architecture/README.md の 2 節（規模の段階）。

会議・開催・参加者・役割

「会議」という言葉は 2 つの意味で使われます。設計では分けて呼びます。

言葉意味表
会議予定やリンクの単位。11 桁の会議の番号と URL を持つ。繰り返しの会議は全回で同じ番号meetings
開催実際に人が集まった 1 回。同じ会議で同時に動く開催は 1 つだけmeeting_instances
参加1 人が 1 回の開催に入っていた記録meeting_participations

会議の種類は、すぐの会議・予定の会議・繰り返しの会議・時刻のない繰り返し・PMI（個人に固定の 10 桁の番号）です。開催の中の役割は host（主催者。1 人）・cohost（共同主催者）・attendee の 3 つで、主催者はミュート・退出・ロック・待合室の操作ができます。ただし主催者でも、他人のミュートを本人の同意なしに外せません（解除を求めるだけ）。

設計の文書で効くところsignaling-and-meetings.md の 4・5・9 節、scheduling-and-calendar.md の 3〜5 節、ADR-0009。

遅れ・揺らぎ・損失：会話の物差し

人は音声の遅れに敏感です。ITU-T G.114 は、片道 150ms 以下なら会話がほぼ自然、400ms を超えると許容できないとしています。そこで設計は、音声の口から耳まで（mouth-to-ear）p95 200ms、映像の撮影から表示まで（glass-to-glass）p95 300ms を目標にします。

遅れ（RTT）

往復の時間。距離と経路で決まる。サーバーを日本に置く理由。

揺らぎ（ジッタ）

パケットの到着の間隔のばらつき。受け手はジッタバッファで溜めて均すが、溜めた分だけ遅れる。

損失

届かないパケット。Wi-Fi やモバイルで起きる。再送を待つと遅れるので、音声は再送しない工夫をする。

このため、メディアは TCP ではなく UDP の上の RTP で送ります。TCP は失ったパケットを必ず再送し、後続を止めて待ちます。会話では、古い音声が遅れて届くより、少し欠けても今の音声が届く方が良いのです。

設計の文書で効くところarchitecture/README.md の 3 節（NFR-001〜004）、signaling-and-meetings.md の 11 節（遅延の予算）。

WebRTC の部品

ブラウザどうし、またはブラウザとサーバーで、音声と映像をやり取りする標準が WebRTC です（W3C の WebRTC 1.0 と IETF の RFC 8825〜8835）。インストールなしで参加できるのは、ブラウザがこれを持っているからです。

flowchart TB
  A["getUserMedia・getDisplayMedia でマイク・カメラ・画面を取る"] --> B["符号器 Opus・VP8 などで圧縮"]
  B --> C["RTP にパケット化、RTCP で受信を報告"]
  C --> D["SRTP で暗号化、鍵は DTLS で交換"]
  D --> E["ICE で決めた経路、UDP がだめなら TCP・TURN"]
  • RTCP は、受け手が「どれだけ失ったか」「キーフレームが欲しい」を送り手へ返す制御の流れです。
  • DTLS-SRTP で、メディアは常に暗号化されます。ただし鍵を持つのは直接の相手（サーバー）です。
  • どの符号器を使い、どこへ送るかは SDP で交渉します。SDP を運ぶシグナリングの方式は標準の外で、各サービスが自分で作ります。
設計の文書で効くところADR-0003（本家の Web クライアントのような独自の伝送は採らない）、clients.md の 2 節（ブラウザの対応表）。

多人数の会議の形：P2P・MCU・SFU

N 人が互いの映像を見るとき、誰が何本を送るかで形が分かれます。

P2P：全員が全員へ直接送る。サーバーは要らないが、各自が N−1 本を送る。上りの帯域と CPU が人数とともに増え、4〜5 人が限度。この設計は 1:1 も SFU を通す（P2P は S2 で評価）。

MCU：サーバーが全員の映像を復号し、1 枚に合成して符号化し直す。受け手は 1 本だけ受ければよいが、サーバーの CPU の費用が大きく、復号と再符号化で遅れが増える。この設計は配信には使わず、録画の合成だけサーバーで行う。

SFU：各自は 1 本（または層を重ねた数本）だけを上げ、サーバーは復号せずに受け手ごとに選んで転送する。受け手ごとに解像度を変えられ、遅れも小さい。この設計の中心。

SFU の費用の大半は、サーバーからインターネットへの送出（egress）です。受け手 1 人に 25 本の映像を送ることもあるので、「誰に、どの品質を、何本送るか」の判断が、品質と費用の両方を決めます。

SFU が帯域の細い受け手に、720p ではなく 180p の映像を送りました。SFU は何をしましたか？

SFU は映像を復号しません。送り手が simulcast や SVC で複数の品質を同時に送り、SFU が受け手ごとに層を選びます（ADR-0002）。

設計の文書で効くところADR-0002、intent.md の Non-goals（MCU による配信）、capacity.md。

SFU の部品：mediasoup の言葉

Media Node は SFU のライブラリ mediasoup v3 で作ります。設計の文書は、その用語のまま書かれています。

言葉意味
workerC++ の子プロセス。CPU のコア 1 つで動く。Media Node は vCPU−2 個を持つ
router会議ごと・worker ごとの部屋。worker をまたぐときは pipeToRouter でつなぐ
transport参加者との 1 本の接続（ICE・DTLS）。1 人に送り用 1 本・受け用 1 本
producer参加者が上げる 1 本の流れ（マイク・カメラ・画面）
consumerある producer を、ある受け手へ流す 1 本。層の上限と優先度を持つ

参加の手順は、mediasoup-client の流れをシグナリングに写したものです。

  1. media.capabilities：router の対応する符号器を受け、ブラウザの Device に読み込む。
  2. media.transport.create：送り用と受け用の transport を作り、ICE と DTLS のパラメーターを受ける。
  3. media.transport.connect：DTLS を始める。ここで経路と暗号の鍵が決まる。
  4. media.produce：マイクやカメラを producer として上げる。ミュート中なら止めた状態で作る。
  5. 他の参加者の分は、サーバーが consumer を止めた状態で作って知らせる。
  6. media.consume.resume：受け手が準備できたら再開し、キーフレームを求める。
設計の文書で効くところmedia-server-sfu.md の 2〜4 節、signaling-and-meetings.md の 8 節、ADR-0010。

NAT を越える：ICE・STUN・TURN

家庭や会社の端末は NAT の内側にあり、外から直接は届きません。ICE は、通れそうな経路（候補）を集めて並行に試し、通った中で最も良いものを選ぶ手順です。

候補意味
host端末やサーバー自身のアドレス
server-reflexiveSTUN で知った、NAT の外側のアドレス
peer-reflexive接続の確認の中で相手から見えたアドレス
relayTURN のサーバーが中継するアドレス。最後の手段

Media Node は公開の IP を持つので ICE Lite で動き、host の候補だけを出します。そのため直接の経路に STUN のサーバーは要りません。UDP が閉じた会社の網のために、TURN を UDP・TCP 3478 と TLS 443 で待ちます。443 番しか通らない網でも、TLS の上で RTP を運べば参加できます（品質は最も悪い）。

参加者がつながっている Media Node が落ちました。別の Node へ移るには、どうしますか？

ICE restart は、同じ Node のまま参加者の網が変わったとき（Wi-Fi からモバイルへ）の手段です。Node が替わると DTLS の相手も変わるので、新しい transport が要ります（media-server-sfu.md の 9.3 節）。

設計の文書で効くところnetwork-traversal.md の 3〜8 節、ADR-0014・0015・0013。

音声：Opus と損失への備え

WebRTC の音声の標準の符号器は Opus です。設計では 20ms ごとに 1 パケット（毎秒 50 個）、約 32 kbps で送ります。損失には、再送ではなく「先に冗長を送っておく」方式で備えます。

DTX：黙っている間はほとんど送らない。100 人の会議の大半は黙っているので、帯域とパケットの数が大きく減る。

FEC：次のパケットの中に、前のフレームを低い品質で重ねる。1 個だけ失ったときに直せる。

RED（RFC 2198）：1 つのパケットに、今のフレームと前のフレームをそのまま並べる。ブラウザは冗長を 1 つ（distance 1）だけ作る。送出は最大約 2 倍。mediasoup に無いので、フォークで足す。

NACK：失ったパケットの再送を求める。音声では使わない。映像は NACK と RTX（再送）で直す。

大きな会議では、受け手に届ける音声を声の大きい 3 人までに絞ります。100 人を超える会議では、受け手ごとに 3 つの「音声の枠」を持たせ、話している人の音声を枠へ付け替えて送ります（ADR-0057）。

音声で NACK（再送の要求）を使わないのはなぜ？

20ms ごとの音声は、1 往復待つだけで遅れが増えます。FEC と RED で先回りして直し、直せない分は受け手の補間（隠す処理）に任せます（codecs-and-bandwidth-adaptation.md の 4.1 節）。

設計の文書で効くところcodecs-and-bandwidth-adaptation.md の 3・4 節、ADR-0017、ADR-0057。

映像：符号器・キーフレーム・層

映像の符号器は VP8・H.264（どのブラウザも必須）、VP9、AV1 です。映像は差分で圧縮するので、途中から見るには「それだけで描ける」キーフレームが要ります。受け手が欲しいときは RTCP の PLI で求めます。

simulcast（既定）

送り手が同じ映像を 3 本（180p・360p・720p）別々に符号化して送る。SFU は受け手ごとに 1 本を選ぶ。本を替えるときはキーフレームが要る。VP8 で使う。

SVC

1 本の流れの中に層を重ねる。L3T3_KEY は空間の層 3・時間の層 3。SFU は層を剥がすだけ。上りが少なく済む。全員が Chromium の会議だけ VP9 で使う。

  • 空間の層は解像度、時間の層はフレームの数（7.5・15・30 fps）。時間の層を落とすのにキーフレームは要らないので、まず時間の層から下げます。
  • 受け手が多いと、PLI が送り手に集まり、送出が 2〜3 倍になりえます。Media Node は要求を 1 秒（画面共有は 2 秒）にまとめます。
  • 画面共有は文字を読めることを優先し、解像度を保ってフレームの数を落とします（contentHint: "detail"、最大 5 fps）。
設計の文書で効くところcodecs-and-bandwidth-adaptation.md の 5・7 節、ADR-0018・0020、media-server-sfu.md の 7 節。

帯域の推定と層の選び方

回線の帯域は刻々と変わり、誰も正確な値を知りません。そこで送り手は、パケットの到着の遅れと損失から「いま送ってよい速さ」を推定します。この推定の方式が GCC で、受け手が到着の時刻を返す仕組みが transport-cc です。

上り（送り手 → Media Node）

ブラウザの GCC が推定し、simulcast の上の本から止める。Media Node は帰還を返すだけ。

下り（Media Node → 受け手）

Media Node が受け手ごとに推定し、優先度の順に層を配る。足りなければ低い優先度から層を下げ、最後は止めてアバターを出す。

何を誰に送るか（購読と上限の層）は Meeting Actor が決め、帯域の中でどの層を送るかは Media Node が決めます。優先度は画面共有 255、ピン留め・話者 200、ギャラリー 100・50 です。

  1. 受け手の下りが半分に落ちる。Media Node の推定が下がる。
  2. 割り当ての合計が推定を超えたので、すぐに下げる。まず時間の層、次に空間の層。
  3. 優先度の低いギャラリーの映像から下がり、載らない映像は止める。
  4. 音声は映像より先に守る。下り 150 kbps まで落ちても音声は続く（NFR-009）。
  5. 回線が戻ったら、1 つ上の層の 1.2 倍の推定が 3 秒続いたときに 1 段ずつ上げる。
設計の文書で効くところcodecs-and-bandwidth-adaptation.md の 6 節（mediasoup の priority は「高い順に満たす」ではない点に注意）、ADR-0019、ADR-0011。

シグナリングと Meeting Actor

メディアの経路とは別に、参加・ミュート・待合室などの「会議の状態」を扱う経路があります。これがシグナリングで、WebSocket の上の JSON です。状態の正本は、会議ごとに 1 つだけ動く Meeting Actor のメモリにあります。

sequenceDiagram
  participant C as ブラウザ
  participant API as API
  participant G as Gateway
  participant A as Meeting Actor
  participant N as Media Node
  C->>API: POST join（パスコード・参加の鍵）
  API-->>C: 参加のトークン（120 秒、1 回限り）
  C->>G: WebSocket hello{token}
  G->>A: join
  A-->>C: welcome{epoch, seq, snapshot}
  C->>A: media.transport.create など
  A->>N: epoch 付きの指示
  • 状態の変化は evt として (epoch, seq) 付きで配ります。音量や字幕のような落としてよいものは eph（seq なし）です。
  • Actor の持ち主は Valkey のリース（TTL 6 秒）で決め、取るたびに epoch を 1 増やします。
  • Actor が止まっても、Media Node は最後の指示のまま転送を続けます。制御が止まってもメディアは止めないのが原則です。

網の分断で、古い Actor（epoch 6）と新しい Actor（epoch 7）が同時に動きました。古い Actor の指示が Media Node に届くと？

epoch はフェンシングの番号です。Media Node・Gateway・Aurora は古い epoch の書き込みを拒みます。Media Node は制御の側に問い合わせません（ADR-0007）。

設計の文書で効くところsignaling-and-meetings.md の 5〜7・10 節、ADR-0005・0007・0008。

会議の荒らしと、待合室・パスコード

2020 年、会議の URL や番号が漏れて知らない人が入り込み、会議を荒らす事件が相次ぎました（「Zoombombing」）。本家は 2020-09-27 から、待合室かパスコードのどちらかを必ず有効にしています。設計も同じ規則を DB の CHECK で守ります。

  • 会議の番号は秘密ではない。画面に出し、電話でも読み上げます。11 桁の乱数でも、有効な番号が多ければ推測で当たります（S3 の見込みで 1 回あたり約 1/9,000）。だから番号だけでは入れない形にします。
  • 参加の鍵（128 ビット）は URL の #k= に置きます。フラグメントはサーバーへ送られないので、アクセスログや Referer に残りません。
  • パスコードは既定 6 桁の数字です（電話の押しボタンで入れるため）。弱いので、誤りの回数の流量の制限と組みます。
  • 主催者が退出させた人は、主催者が許すまで同じ会議に戻れません（ban）。荒らしには「活動の一時停止」で全員の映像・音声・共有・チャットを 1 回の操作で止めます。

参加の鍵の入った URL を持つ人は、何を省けますか？

URL は転送で漏れます。待合室を省けるのは、同じ組織のログインや主催者の招待など「身元」で判定できる人だけです（ADR-0031）。

設計の文書で効くところmeeting-security.md の 3〜8 節、ADR-0006・0031〜0033。

暗号化：ホップごとと E2EE

「暗号化している」には 2 つの意味があります。SFU を通す会議では、この違いが機能の可否を決めます。

ホップごと（既定）

DTLS-SRTP。端末と Media Node の間を暗号化する。Media Node は中身を平文で扱えるので、録画・字幕ができる。

E2EE（選べる）

端末が符号化の後のフレームを SFrame で暗号化し、さらに SRTP で包む。鍵は MLS で参加者だけが共有し、サーバーは持たない。

  • SFU は中身を読めなくても、RTP のヘッダーと拡張（rid、音量、Dependency Descriptor）で層を選び、話者を見分けます。誰がいつ話したかは、サーバーに見えます。
  • 参加者が抜けたら、2 秒以内に MLS の鍵を替え、抜けた人は以後のメディアを復号できません（NFR-008）。
  • 全員の画面の「セキュリティのコード」が一致すれば、サーバーによるすり替えが無いと確かめられます。

E2EE の会議で、使えるものはどれ？

録画・字幕・電話からの参加・個別のチャットは、サーバーが中身に触れるので使えません。話者の検出は平文の音量のヘッダー拡張で動きます（e2ee.md の 12 節）。

設計の文書で効くところe2ee.md の 3〜12 節、ADR-0004・0028〜0030。

録画・字幕と同意

録画と文字起こしの部品は、SFU から見ると「受け手の 1 人」です。参加者の一覧には出ませんが、動いている間は全員の画面に消せない表示を出します。

  1. 主催者が録画を始める。Actor が開始の判定（E2EE なら拒否、組織の設定、役割、容量）をする。
  2. 全員に「録画中」を表示する。同意していない人は、同意するまでマイク・カメラ・共有を始められない。
  3. Recorder が producer ごとの生の RTP を 10 秒の区切りで S3 に書く（会議の間は合成しない）。
  4. 会議の後に Composer が、復号・合成して 1 本の動画（mp4）にする。MCU の処理を、遅れの許される後処理に回した形。

字幕は Transcriber が音声を受け、ASR（S1 は Amazon Transcribe の ja-JP）へ話者ごとに流します。流れが話者ごとなので、話者の名前は必ず合います。日本語の正確さはCER（文字の誤り率）15% 以下を目標にしますが、まだ未検証です。

法務の確認待ち録画・文字起こしの同意の取り方と、同意しない人の扱い（L3）、サーバーが内容に触れてよい範囲（L2）、外部の音声認識の事業者への委託（L6）は結論が出ていません。設計は「同意するまで話せない」を既定にし、文言を差し替えられる形にしています。
設計の文書で効くところrecording-and-transcription.md の 3〜7 節、ADR-0025〜0027。

品質と費用の物差し

ビデオ会議の品質は「API が 200 を返したか」では測れません。ブラウザの getStats と RTCP から、損失・揺らぎ・RTT・フリーズを 10 秒ごとに集めます。

物差し意味
MOS音声の品質を 1〜5 で表す値。本番は E-model（ITU-T G.107）の式で推定し、試験の客観評価 ViSQOL で係数を合わせる
フリーズ映像が 1 秒以上止まること。映像は MOS を推定せず、フリーズと解像度で見る
良い参加者・分SLO の単位。利用者の回線の悪さでも減るので、サーバーの側の悪化と合わせて見る
pps1 秒あたりのパケットの数。映像 1 本で約 160、音声 1 本で 50。Media Node 1 台の上限は負荷試験で決める（初期の見積もりでは帯域より先に consumer の数と CPU で決まる）
K8参加者・分あたりのメディアの配信の費用。S1 で 0.20 円以下が目標

会議の費用の約 8 割は、SFU からインターネットへの送出です。クラウドの転送の料金が高いので、送出が一定の量（ピーク 4 週続けて 10 Gbps）を超えたら、自前の機器を置く Edge の構築を始めます。

設計の文書で効くところobservability.md の 3・4 節、capacity.md、ADR-0052・0050・0053。SLO の読み方は共通の資料へ。

本家と違うところ・法令の枠組み

振る舞いは本家に寄せますが、作り方と範囲は違います。本家の Web クライアントは独自の符号化と伝送を使うと報告されていますが、この設計は標準の WebRTC の上で作ります。本家のクライアントや SDK との互換は目指しません。アプリ（E13）、電話からの参加（E14）、ウェビナー（E15）、ブレイクアウトルーム（E16）は MVP の後です。識別子には本家の名前を使わず、URL は https://<brand>.<domain>/j/<meeting-id>、ヘッダーは X-<Brand>-… と書きます。

日本の法令に関わる次の問いは、すべて法務の確認待ちです。設計はどの結論にも対応できる形にし、結論が出るまで該当の spec を承認しません。

#枠組み問いの要点
L1電気通信事業法登録か届出か、その時期
L2通信の秘密SFU が平文のメディアを扱う。録画・字幕・診断で内容に触れてよい範囲
L3録画の同意・個人情報通知の方法、同意の記録、同意しない人の扱い
L4捜査機関への対応傍受・照会への応じ方。E2EE で応じられないことの扱い
L5外部送信規律端末の情報を外へ送るときの公表
L6〜L8個人情報保護法・電話番号・契約保持と委託、050 などの番号、DPA とサブプロセッサー
設計の文書で効くところintent.md の Constraints・Non-goals・「法務の確認待ち」、ADR-0006（リポジトリ共通）。

用語集

WebRTC
ブラウザで音声・映像・データをリアルタイムにやり取りするための W3C の API と IETF のプロトコルの一式。
RTP
Real-time Transport Protocol。音声・映像のパケットに連番と時刻を付けて運ぶ形式。ふつう UDP の上で使う。
RTCP
RTP の制御の流れ。受信の報告、損失、キーフレームの要求（PLI・FIR）、帯域の帰還を送る。
DTLS-SRTP
DTLS（UDP 版の TLS）で鍵を交換し、SRTP（暗号化した RTP）でメディアを送る方式。WebRTC では必須。
SDP
Session Description Protocol。符号器・暗号の指紋・経路の候補などを書いた、交渉用の文字列の形式。
シグナリング
メディアの前後の交渉と、会議の状態のやり取り。WebRTC の標準の外で、サービスごとに作る。
P2P
Peer to Peer。端末どうしが直接メディアを送り合う形。
MCU
Multipoint Control Unit。サーバーが全員の映像を復号・合成して送り直す形。
SFU
Selective Forwarding Unit。メディアを復号せず、受け手ごとに選んで転送するサーバー。
worker
mediasoup の C++ の子プロセス。CPU のコア 1 つで RTP を処理する。
router
mediasoup の中の、会議ごとの転送の部屋。producer と consumer をつなぐ。
transport
参加者と Media Node の間の 1 本の接続。ICE と DTLS の状態を持つ。
producer
参加者がサーバーへ上げる 1 本のメディアの流れ。
consumer
1 つの producer を 1 人の受け手へ流す、受け手ごとの 1 本。
NAT
Network Address Translation。内側の私的なアドレスを外側の公開のアドレスへ付け替える機器。外から内へは直接届かない。
ICE
Interactive Connectivity Establishment（RFC 8445）。経路の候補を集めて並行に試し、通る組を選ぶ手順。
ICE Lite
公開の IP を持つ側のための簡略な ICE。自分からは確認を送らず、相手の確認に答える。
STUN
NAT の外側から見た自分のアドレスを知るためのプロトコル（RFC 8489）。
TURN
直接つながらないときに、メディアを中継するサーバーのプロトコル（RFC 8656）。
ジッタバッファ
受け手が揺らぎを吸収するために、届いたパケットを少し溜めてから再生する仕組み。
glass-to-glass
カメラのレンズから相手の画面までの、映像の端から端の遅れ。
Opus
WebRTC の必須の音声の符号器（RFC 6716）。会話から音楽まで広く使える。
DTX
Discontinuous Transmission。無音の間の送出を止める仕組み。
FEC
Forward Error Correction。冗長を先に送り、損失を受け手の側で直す方式。Opus のインバンド FEC は前のフレームを低い品質で重ねる。
RED
Redundant Audio Data（RFC 2198）。1 つのパケットに過去のフレームを重ねて送る形式。
NACK
Negative Acknowledgement。受け手が失ったパケットの再送を求める RTCP。
キーフレーム
前のフレームに頼らず、それだけで描けるフレーム。大きいので頻繁には送らない。
PLI
Picture Loss Indication。受け手がキーフレームを求める RTCP。FIR も同じ目的。
simulcast
同じ映像を複数の解像度で別々に符号化し、同時に送る方式。
SVC
Scalable Video Coding。1 本の流れの中に、解像度（空間）とフレームの数（時間）の層を重ねる方式。
GCC
Google Congestion Control。到着の遅れの変化と損失から、送ってよい速さを推定する方式。
transport-cc
送り手が全パケットに連番を付け、受け手が到着の時刻をまとめて返す帰還。GCC を送り手の側で動かすのに使う。
Meeting Actor
会議ごとに 1 つだけ動き、会議の状態の正本を持つ処理。状態の変化に順番（seq）を付けて配る。
リース
期限つきの持ち主の権利。更新しなければ切れ、他の誰かが取れる。
epoch
Actor の持ち主が替わるたびに増える番号。減らない。
フェンシング
古い持ち主の書き込みを、番号（epoch）を比べて受け手の側で拒む仕組み。
待合室
参加者を会議に入れる前に留め置き、主催者が 1 人ずつ確かめて入れる仕組み。
参加の鍵
URL のフラグメント（#k=）に置く 128 ビットの乱数。パスコードの入力を省ける。
PMI
Personal Meeting ID。利用者ごとに固定の 10 桁の会議の番号。繰り返し使うので推測の対象になりやすい。
E2EE
End-to-End Encryption。送り手と受け手だけが鍵を持ち、途中のサーバーは中身を読めない暗号化。
SFrame
Secure Frame（RFC 9605）。符号化したフレームごとに暗号化する形式。SFU を通しても中身を守れる。
MLS
Messaging Layer Security（RFC 9420）。多人数のグループで鍵を共有・更新するプロトコル。抜けた人は以後の鍵を知らない。
Dependency Descriptor
フレームの層とキーフレームかどうかを示す、平文の RTP のヘッダー拡張。暗号化した中身を読まずに層を選べる。
ASR
Automatic Speech Recognition。音声を文字にする処理。
CER
Character Error Rate。文字の誤り率。日本語の音声認識は語の区切りが曖昧なので文字で測る。
MOS
Mean Opinion Score。品質を 1〜5 で表す値。もとは人の評価の平均で、式や客観評価で推定もする。
Edge
この設計で、コロケーションに自前のベアメタルの Media Node を置く構成。転送の費用を下げるため。
