Dropbox は何をするサービスか

個人とチームが、仕事のファイルと写真を、複数の PC とスマートフォンで同じ木として使うためのストレージです。主な利用者は、日本の中小・中堅企業の社員です。設計・映像・建設のように、大きなファイルを社外の取引先と共有する業種を想定しています。

同期のフォルダー

PC の ~/<Brand> に置いたファイルが、他の端末とサーバーへ自動でそろう。中身を手元に置かない「オンラインのみ」のファイルも選べる。

共有フォルダー

フォルダーに人やグループを招き、編集・閲覧の役割を付ける。招かれた人の木にもそのフォルダーが現れる。

共有リンク

URL を知る人に見せる。パスワード・期限・ダウンロードの禁止を付けられる。アカウントのない外部の人も開く。

バージョン履歴と巻き戻し

ファイルの前のバージョン、消したファイル、フォルダー全体を、プランの保持の期間の中で戻せる。

intent が掲げる価値は 4 つです。失わない・黙って上書きしない、すぐそろう、共有の範囲が分かる、戻せる。規模は S1 で 50 万アカウント、ノード 25 億、物理の保存 13 PB を見込みます。識別子に本家の名前は使わず、<brand>.<domain> のように書きます（ADR-0006）。

設計の文書で効くところintent.md の Problem・Proposed outcome・守るべき振る舞い、architecture/README.md の 2 節（規模の段階）と 3 節（NFR）。

ファイルシステムの基本：inode とパス

Unix のファイルシステムでは、ファイルの実体は inode で、フォルダーは「名前 → inode」の表です。パスは、ルートから名前をたどった道順にすぎません。Windows の NTFS では、同じ役目を File ID が担います。

  • 名前の変更と移動：同じボリュームの中なら、フォルダーの表の行を書き換えるだけです。inode は変わらず、中身も動きません。10 万ファイルのフォルダーの名前を変えても一瞬で済みます。
  • ボリュームをまたぐ移動：OS の中では「写して、元を消す」になります。同期のアプリからは「消えた」と「現れた」に見えます。
  • アプリの保存のしかた：多くのアプリは、一時のファイルに書いてから元の名前へ置き換えます（置き換えの保存）。同じパスでも inode が新しくなります。

設計は、ノードを UUIDv7 の ID で指し、親の ID と名前を持たせます。端末では inode・File ID でノードを結び、置き換えの保存は「同じノードの中身の変更」として扱います。こうしないと、バージョン履歴と共有リンクが切れます。

「ファイルはフルパスを主キーにすれば、ID の表が要らず単純だ」。この設計で何が起きますか？

パスは「今の置き場所」で、移動のたびに変わります。ID で指せば、名前の変更は 1 行の変更です。パスは表示と、API の入口での解決のためだけに使います（ADR-0008）。

設計の文書で効くところADR-0008、file-system-integration.md の 4・5 節（移動の検出、アプリの保存のしかた）、ADR-0015。

名前の落とし穴：大文字小文字・正規化・予約の名前

同じ名前に見えても、OS によって「同じ」の判定が違います。端末をまたぐと、1 つのファイルが 2 つに見えたり、消し合ったりします。

APFS の既定は、大文字小文字を区別しない（ただし保つ）。区別するボリュームも作れる。Unicode の正規化の形を保ったまま、形の違いを区別せずに引ける。古い HFS+ は NFD で持つ。アプリによって NFC と NFD のどちらの名前も現れる。

NTFS の既定は、大文字小文字を区別しない（保つ）。<>:"/\|?* と制御文字が使えない。CON・PRN・AUX・NUL・COM1・LPT1 などの予約の名前は、拡張子を付けても使えない。名前の末尾の空白とピリオドも使えない。

ext4 などは大文字小文字を区別する。名前はただのバイト列で、正規化しない。a.txt と A.txt は別のファイルとして並ぶ。MVP は Linux のクライアントを持たないが、Web や API から同じ問題が入る。

「が」は NFC で 1 文字（E3 81 8C）、NFD で「か」＋濁点の 2 文字（E3 81 8B E3 82 99）。見た目は同じでもバイト列が違う。全角の「カ」と半角の「ｶ」は NFC では別の文字で、NFKC では同じになる。

設計は、名前を NFC で持ち、同じフォルダーの中の一意を name_key（NFC → Unicode の case folding → NFC）で決めます。全角と半角は区別します。OS で表せない名前は、サーバーの名前を変えず、その端末だけ「同期できない名前」として示します。

macOS のアプリが が.txt を NFD の名前で保存しました。手元の名前を NFC に書き換えて揃えるべきですか？

手元の名前を書き換えると、アプリが NFD で書き戻し、名前の変更が端末の間で往復し続けます。比べるのは name_key だけにし、OS や SQLite の照合に任せません（ADR-0008、ADR-0017）。

設計の文書で効くところADR-0008・ADR-0017、file-system-integration.md の 7・8 節（大文字小文字だけの変更、NFC・NFD、表せない名前の例）、data-model.md の 3.5 節。

双方向の同期と 3 つの木

手元とサーバーの 2 つだけを比べると、「片方にだけあるファイル」が、片方で作ったのか、もう片方で消したのか決められません。時刻で決めようにも、端末の時計はずれます。そこで、最後にそろった状態を共通の祖先として持ち、3 方向のマージをします。Git のマージと同じ考え方です。

  • Remote：サーバーから差分で受けた木。Local：監視と走査で観測した手元の木。Synced：最後に両者が一致したと確かめた木。
  • Synced → Remote の差が「サーバーの変化」、Synced → Local の差が「手元の変化」です。

b.txtr1ないr1手元で消した → サーバーで消す
c.txtr1r1r2サーバーの変化 → 取る
d.txtないないr1サーバーで作った → 取る
2 つの木だけ

b.txt と d.txt は、どちらも「サーバーにだけある」。消すべきか取るべきか分からない。誤れば、他の端末のファイルを消す。

3 つの木

Synced にあれば「手元で消した」、なければ「サーバーで作った」と決まる。監視の取りこぼしで手元を走査し直しても、Synced を残すので判断を誤らない。

設計の文書で効くところADR-0006 の「クライアントの 3 つの木」、sync-engine.md の 5 節（木の形と進め方）と 6 節（計画）、ADR-0010（意図の記録）。

サーバーは、元にしたbase_rev などの条件つきの書き込みだけを受けます。先に届いた commit が通り、後の commit は 409 になります。後の側のクライアントが、決定表で次の手を決めます。

競合のコピーの名前は 見積 (A-PC の競合コピー 2026-10-09).xlsx の形です。本家は編集した人の名前を入れますが、設計は端末の名前を入れます。同じ人の 2 台の衝突が多いからです。

消しすぎの止め：手元からサーバーへ出す削除が、直近 5 分で 1,000 ファイルか木の 10% を超えたら、送る前に止めて利用者に確かめます。フォルダーを外付けのディスクへドラッグしただけでも、OS は「削除」に見せるからです。

端末 A がオフラインで 報告.docx を編集している間に、端末 B が同じファイルを削除しました。A が戻ったら、どうなりますか？

迷ったら中身が残るほうを選びます（決定表の 3）。逆の順でも、B の削除は base_rev の条件で 409 になり、B が A の中身を受けます（決定表の 4）。消した側の意図は、バージョン履歴から戻せるので失われません。

内容の番地：ハッシュを住所にする

中身の SHA-256 をそのまま保存の番地（キー）にする方式を、内容の番地（content-addressed storage）と呼びます。Git のオブジェクトも同じ考え方です。

  • 不変：中身が変われば番地も変わるので、ブロックは書き換えません。同じ番地への 2 回目の書き込みは、同じ中身です。
  • 確かめられる：受け取った中身のハッシュを計算し直せば、番地と一致するかが分かります。
  • 同じ中身は 1 回：同じブロックが何度出てきても、置くのは 1 つです（次の節の重複排除）。

ファイルのリビジョンは、ブロックのハッシュの並び（ブロックの一覧）を持つだけです。木の変更はメタデータの行の変更で、中身は動きません。アップロードは次の順です。

  1. クライアントがファイルを分割し、ブロックのハッシュの一覧を作って commit を送る。
  2. サーバーは確定せず、足りないブロックの一覧と、ブロックごとの署名つき URL（一時のキー incoming へ）を返す。
  3. クライアントが S3 へ直接 PUT する。S3 は SHA-256 のチェックサムを計算し直す。
  4. block-verifier が番地と大きさを確かめてから、正規のキーへ写し、ブロックの索引に入れる。
  5. クライアントが commit を送り直し、新しいリビジョンが確定する。中身はサーバーの ECS を通らない。
設計の文書で効くところADR-0002 の「番地とハッシュ」（content_sha256 と blocklist_hash）、architecture/README.md の 1.3 節 A、ADR-0018。

分割：固定の大きさと、内容で区切る分割

大きなファイルはブロックに分けます。4 MiB ごとの固定の分割は単純ですが、先頭に 1 バイト足すと、後ろの境界がすべて 1 バイトずれ、全部が新しいブロックになります。内容で区切る分割（CDC）は、境界を「位置」ではなく「中身」で決めるので、ずれが広がりません。

境界は回転のハッシュで探します。設計が使うギアのハッシュを 1 段ずつ見ます。

  1. 1 バイトずつ混ぜる：h = (h << 1) + G[byte]。G は 256 個の 64 ビットの値の表（ギアの表）。
  2. 古いバイトは押し出される：h は 64 ビットなので、左へ 64 回ずれたバイトの影響は消える。h は直近 64 バイトの中身だけで決まる（窓）。
  3. 境界を決める：h の下位のビットがマスクに一致した位置で切る。一致する確率で、ブロックの平均の大きさが決まる。位置ではなく中身で決まる。
  4. 大きさをそろえる：最小 1 MiB までは探さない。平均 4 MiB の前は厳しいマスク、後は緩いマスクで平均に寄せる。最大 16 MiB で必ず切る。
  5. 挿入に強い：途中に 1 バイト足すと、その近くの境界だけが動く。挿入点から 64 バイト過ぎれば h は元と同じ値の列に戻り、たいてい次の境界から後ろは同じブロック、同じハッシュになる。
  6. 規則はバージョンで固定：表と母数は chunker_version に結び付ける。同じバージョンなら、OS・CPU・ネイティブと WASM で同じ境界が出る。
設計の文書で効くところADR-0002 の「分割の規則」と「他の案を選ばなかった理由」（rsync の差分を選ばない理由）、block-storage.md の 4.5 節（公開 API の chunker_version 0）。

重複排除と、その横の漏れ

内容の番地なら、同じブロックは 1 回だけ置けます。さらに commit で「そのブロックはもうある」と答えれば、送る量も減ります。ところが、この答えは「誰かがその中身を持っている」ことを教えます。これが重複排除の横の漏れ（サイドチャネル）です。

  1. 攻撃者が、狙った中身（他社の文書の原稿、流出した名簿の候補）のファイルを作る。
  2. アップロードを試す。送らずに済めば、誰かがそのファイルを持っていると分かる。
  3. 給与の額のように一部だけ違う候補を総当たりで試せば、中身まで推測できる。
  4. 答えそのものを隠しても、送信の時間・容量の増え方・エラーの違いから漏れうる。

設計は、重複排除をテナントの中に閉じます。「送らなくてよい」と答えるのは、要求した人が既に読める名前空間がそのブロックを参照しているときだけです。それ以外は、テナントの中にあっても「送れ」と答え、受け取ってから保存だけを重ねます。容量は論理の大きさで数えます。

「全利用者で重複排除すれば、保存の量が最も減る。損はない」。何が問題ですか？

設計は案 3（全体の重複排除）を退けました（ADR-0003）。後半の穴は、索引にあるだけのブロックを commit で受けないことで塞ぎます。受けるのは have・copy・granted のブロックだけです（ADR-0018）。

設計の文書で効くところADR-0003 の commit の答えの表、ADR-0018、data-model.md の 5.1 節の 2 つ目の図と 6 節（横断の不変条件）。

参照の数と GC：共有したブロックを消すとき

1 つのブロックは、多くのリビジョンから参照されます。ファイルを 1 つ消しても、ブロックを消してよいとは限りません。そこで参照の数を数え、0 になったものだけを後から消します（GC）。

stateDiagram-v2
    [*] --> orphaned: 検証した（まだ参照なし）
    orphaned --> live: 最初の参照ができた
    live --> orphaned: 最後の参照が消えた
    orphaned --> deleting: 7 日の猶予の後、まだ 0
    deleting --> [*]: S3 から消して行を消す
  • なぜ猶予か：アップロードの途中で、まだ commit に載っていないブロックがあります。参照が 0 になった直後に、同じブロックを使う commit が来ることもあります。7 日待ち、ロックの下で 0 を確かめ直してから消します。
  • 消した後も戻せる：S3 のバージョニングで、消したオブジェクトを 30 日戻せます。数え違いに気づいたときの最後の網です。
  • 数え方の工夫：参照は名前空間ごとの ns_block_refs に持ち、blocks には「参照する名前空間の数」だけを持ちます。よく使われるブロックの行のロックが集中しないためです。
設計の文書で効くところADR-0019、ADR-0007 の「削除と GC」と「照合」、block-storage.md の 5・6 節。

ジャーナルとカーソル：差分で届ける

他の端末へ変更を届けるには、「前回からの差分」が要ります。時刻（updated_at）で差分を取ると、同じ時刻の書き込みやコミットの順序の入れ替わりで欠け、削除も表せません。そこで、名前空間ごとに単調に増える番号 ns_seq を振り、操作をジャーナルに順に書きます。

flowchart LR
  C["commit"] -->|"1 tx: ノード + ns_journal + outbox"| DB[("Aurora")]
  DB --> R["Relay"]
  R -->|"ns_seq が S になった"| N["Notify (WebSocket)"]
  N -->|"合図だけ"| D["端末"]
  D -->|"list/continue + カーソル"| API["API"]
  API -->|"seq より後の操作"| D
  • カーソルは「載せた名前空間ごとの、読み終えた番号」の組を署名した不透明な文字列です。端末は list/continue で続きを受けます。
  • 合図（WebSocket）が落ちても、端末は再接続のときと 60 秒ごとに確かめます。合図は速さのため、正しさはカーソルが担います。
  • ジャーナルは日で分割し 92 日で落とします。最後の利用から 90 日を過ぎたカーソル、DR の切り替えなどで epoch が変わったカーソルには、黙って欠けた差分を返さず、取り直し（409 reset）を求めます。取り直しでも Synced があるので手元の変更は失いません。

利用者が新しい共有フォルダーに参加しました。端末のカーソルはどうなりますか？

取り直しの理由は、期限切れ・floor_seq より古い・epoch の 3 つだけです（NFR-010）。参加は利用者のルートの名前空間に mount の操作として載り、外されたときは unmount として返ります。

設計の文書で効くところADR-0005（「他の案を選ばなかった理由」に時刻・WAL・利用者ごとのフィードとの比較）、metadata-and-journal.md の 5 節と 8 節、ADR-0023。共通の資料の outbox。

名前空間とマウント：共有フォルダーとチームのスペース

名前空間は、ノードの木と、順序（ns_seq）と、権限をまとめた単位です。共有フォルダーは 1 つの名前空間で、参加した人それぞれの木にマウントのノードとして載ります。1 回の書き込みはその名前空間のジャーナルに 1 回だけ載り、メンバーが 1 万人でも書き込みは増えません。

種類中身
user_root個人のルート。チームのメンバーでは「本人のフォルダー」
shared_folder共有フォルダー。作った人のテナントが持つ。他のテナントの人も参加できる
team_spaceチームのスペース。メンバーの端末の木のルート。最上位は管理者だけが変える
team_folderチームのフォルダー。中の制限したフォルダーも別の名前空間（深さ 4 まで）
flowchart TD
  TS["team_space: 全員 viewer"] --> H1["mount: 佐藤 (user_root)"]
  TS --> F1["mount: 営業 (team_folder)"]
  TS --> F2["mount: 全社共有 (team_folder)"]
  F1 --> R1["mount: 人事評価 (team_folder, 継承しない)"]
  H1 --> S1["mount: 取引先A (shared_folder, 他のテナント)"]

共有フォルダーの中に共有フォルダーは作れません。名前空間の中の移動は 1 行の変更ですが、名前空間をまたぐ移動（自分のフォルダーから共有フォルダーへ）は、移動先に子孫の数だけノードを作るバッチになります。権限は名前空間の単位で付け、can() の 1 つの関数で判定します（RLS は共通の資料）。

設計の文書で効くところADR-0004、ADR-0024・ADR-0025、namespaces-and-sharing.md の 4・5 節、ADR-0022。

オブジェクトストレージの基本：S3

S3 は、キーで中身（オブジェクト）を置いて取る保存の場所です。フォルダーの木や名前の変更はなく、オブジェクトは丸ごと置き換えるだけです。不変のブロックとの相性がよい理由です。

用語意味と、設計での使い方
耐久性置いたものを失わない確率。どの保存のクラスも 99.999999999%（11 個の 9）の設計
可用性今取り出せる確率。耐久性とは別の数字で、クラスによって違う
保存のクラス128 KiB 以上のブロックは Intelligent-Tiering、未満は Standard（監視の外で、低頻度のクラスの最小の課金 128 KB に当たるため）
CRR別のリージョンへの非同期の複製。東京から大阪へ。RTC を使うと 99.9% を 15 分以内に写す
署名つき URL期限つきで、特定のキーへの PUT・GET だけを許す URL。クライアントは一時のキー incoming にだけ書ける
チェックサムPUT のときに SHA-256 を指定すると、S3 が計算し直して合わなければ拒む

設計は、物理の耐久性（複製・消失訂正符号）を S3 に任せ、論理の耐久性（参照の数、削除の猶予、照合）を自分で持ちます。署名でチェックサムの指定を強制できるかは未検証で、PoC で確かめます。できなくても検証の工程で確かめるので、正しさは変わりません。

「S3 の耐久性は 11 個の 9 なので、ブロックの配信も止まらない」。正しいですか？

設計は NFR-005（耐久性）と NFR-006（可用性 月間 99.9%）を分けています。さらに、本システムの GC の誤りで消したものは S3 の耐久性の外なので、参照の数・7 日の猶予・バージョニングの 30 日で守ります。

設計の文書で効くところADR-0007（バケットとキー、保存のクラス、DR）、architecture/README.md の 2.1 節（保存の費用のモデル）、ADR-0048（中身の待ち）。

バージョン・復元・ランサムウェアからの巻き戻し

同期はバックアップではありません。手元で壊したものは、正しく全端末へ広がります。だから、サーバーに過去を持ち、戻せることが価値になります。

戻すものやり方
ファイルの前のバージョン古いリビジョンのブロックの一覧を写した、新しいリビジョンを作る
消したファイル・フォルダー墓石（deleted_at）の行を戻す（undelete）
フォルダー・名前空間の全体巻き戻し：時点 t の木と今の木の差を、普通の操作に直して流す

保持の期間は、無料と個人の有料で 30 日、チームの標準で 180 日、チームの上位で 365 日（本家の区分の既定）。ランサムウェアの典型の流れを見ます。

  1. 端末がランサムウェアに感染し、同期のフォルダーの数万のファイルを暗号化して書き換える。拡張子が変わることも多い。
  2. 同期は正しく働き、暗号化した中身が新しいリビジョンとして上がり、他の端末へも届く。
  3. サーバーの mass-change-detector が、名前空間 × 端末の 10 分の窓で、変更・削除の数、拡張子の変わった名前の変更の割合を数え、閾値を超えたら知らせる。中身は読まない。
  4. 通知は、巻き戻しの時点の候補（窓の始まりの 5 分前）と端末を示す。自動では止めない・巻き戻さない。
  5. 利用者や管理者が時点を選んで巻き戻す。1,000 操作ずつ commit し、途中で人が変えたファイルは条件で見つけて飛ばす。巻き戻しもまた巻き戻せる。
設計の文書で効くところversions-and-recovery.md の 4〜7 節、ADR-0029・ADR-0030・ADR-0031、runbooks/mass-change-response.md。

プレビュー：信用しないファイルを隔離して開く

サムネイルやプレビューを作るには、利用者のファイルを画像・PDF・Office・動画の部品で開きます。これらの部品は複雑な形式を解釈するので、脆弱性が見つかり続けています。悪意のあるファイル 1 つで、変換の処理を乗っ取られうるということです。

外へ出る道がない

変換は NAT もインターネットのゲートウェイもない区画の sandbox で動く。資格情報も URL も持たない。

使い捨て

変換のプロセスはジョブごとに作り直し、別の利用者 ID と資源の上限で動かす。タスクも 50 ジョブか 10 分で作り直す。

出力を作り直す

変換の出力をそのまま配らず、メモリー安全な復号器で読み直して WebP に作り直す。元の位置の情報も残さない。

別のドメインで返す

利用者の中身は <brand>usercontent.<domain> からだけ返す。本体のドメインの Cookie に届かせない。

プレビューはリビジョンごとに作り、同じ content_sha256 でも別のリビジョンでは作り直します。content_sha256 はクライアントの申告で、信用しないからです。

設計の文書で効くところADR-0032・ADR-0033、previews-and-thumbnails.md の 4・6 節、security.md の 3.4 節。

日本の法令の枠組み

ここは枠組みの説明だけです。設計の文書は、次のどれにも結論を出していません（法務の確認待ち）。結論まで、関係する Epic の spec を承認しません。

共有フォルダー・共有リンクで他人とやり取りする使い方が、届出の要る電気通信事業に当たるか。当たるなら、保存したファイルの中身が「通信の秘密」に当たり、プレビュー・本文の索引・マルウェアの検査のために中身を機械で読むことに同意が要るか。2023-06-16 に施行された外部送信規律（端末から外へ送る情報の通知・公表）が、端末の計測と Web の画面に当たるか。法務の確認待ち（L1）。一斉の変更の検知が中身を読まないのは、この論点のためです。

旧プロバイダ責任制限法を改めた法律で、2025-04-01 に施行。総務大臣が指定する大規模特定電気通信役務提供者に、削除の対応の迅速化と運用の透明化を求めます。本システムが対象に当たるか、共有リンクで公開されたファイルへの削除の請求の手順、違法な画像のハッシュの照合の範囲は法務の確認待ち（L2）。結論まで、anyone の共有リンクの公開はフラグの裏に置きます。

権利を侵害された人が、裁判所の手続きで発信者を特定する情報の開示を求める仕組みです。アップロードや共有リンクの作成の IP アドレス・時刻を、何を何日持つかは法務の確認待ち（L3）。

ファイルの中身をチームからの委託として扱うか（L4）、データの所在と CDN の国外のエッジ（L5）、保持の期間と解約の後の消去・リーガルホールド（L6）、管理者がメンバーのファイルを見る機能（L7）、電子帳簿保存法の要件をうたうか（L8）、契約の雛形（L9）、画面と競合のコピーの文言を本家に寄せる範囲（L10）。どれも法務の確認待ちです。

設計の文書で効くところintent.md の「法務の確認待ち」（L1〜L10 と承認を止める spec）、security.md、ADR-0046。

データモデルの読み方

中心は「名前空間 → ノード → リビジョン → ブロック」の鎖です。ファイルは次のように中身を指します。

flowchart LR
  F["ファイル (利用者のパス)"] --> N["nodes (ns_id, node_id, name_key)"]
  N -->|"今の rev_id"| R["revisions (content_sha256, blocklist_hash)"]
  R --> L["ブロックの一覧 (1,024 まで行の中、超えたら S3)"]
  L --> B["blocks (tenant_id, hash)"]
  B --> O["S3 のオブジェクト"]
erDiagram
  tenants ||--o{ namespaces : "owns"
  namespaces ||--o{ ns_grants : "grants"
  namespaces ||--|{ nodes : "contains"
  namespaces ||--o{ ns_journal : "orders"
  nodes ||--o{ revisions : "has"
  revisions }o--o{ blocks : "lists"
  namespaces ||--o{ ns_block_refs : "references"
  blocks ||--|{ ns_block_refs : "counted by"
  tenants ||--o{ blocks : "stores"
  namespaces {
    uuid ns_id PK
    uuid tenant_id FK
    text kind "user_root shared_folder team_space team_folder"
    bigint ns_seq
  }
  nodes {
    uuid ns_id PK
    uuid node_id PK
    uuid parent_id
    text kind "file folder mount"
    text name_key "unique per parent"
    uuid rev_id FK
    bigint node_ver
    timestamptz deleted_at "tombstone"
  }
  revisions {
    uuid ns_id PK
    uuid rev_id PK
    smallint chunker_version
    bytea blocklist_hash
    bytea content_sha256 "declared"
  }
  blocks {
    uuid tenant_id PK
    bytea hash PK
    text state "live orphaned deleting"
  }
  ns_journal {
    uuid ns_id FK
    bigint seq
    text op "upsert delete mount unmount purge"
  }
  • バージョンが 2 つ：rev_id は中身、node_ver は置き場所（親・名前・削除）。中身の変更と名前の変更を別々の条件で確かめるので、同時に起きても衝突にしません。
  • ハッシュの信用：ブロックの hash と blocklist_hash はサーバーが確かめます。ファイル全体の content_sha256 はクライアントの申告で、信用しません。
  • 名前を持つ列は限る：ファイルの名前・パスは nodes・node_versions・ns_journal などの決めた所だけに持ち、ログや監査に書きません。

用語集

inode・File ID
ファイルの実体を指す、ボリュームの中の番号。名前の変更・同じボリュームの中の移動では変わらない。Windows の NTFS では File ID。
置き換えの保存
一時のファイルに書いてから元の名前へ置き換える保存のしかた。同じパスでも inode・File ID が新しくなる。
NFC・NFD
Unicode の正規化の形。NFC は合成済みの文字（「が」1 文字）、NFD は分解した形（「か」＋濁点）。NFKC は互換の文字（全角と半角など）も同じにする。
case folding
大文字小文字の違いを無くすための Unicode の変換。小文字にするだけでは扱えない文字（ドイツ語の ß など）も含めて畳み込む。
name_key
本システムの名前の比べ方の鍵。NFC → case folding → NFC。同じフォルダーの中で一意にする。
予約の名前
Windows がデバイスに使う名前（CON・PRN・AUX・NUL・COM1〜・LPT1〜）。拡張子を付けても、ファイルの名前に使えない。
プレースホルダー
名前・大きさ・日時だけを持ち、中身を手元に置かないファイル。開いたときに中身を取り出す。
取り出し
hydration。プレースホルダーの中身をサーバーから受けて手元に置くこと。逆に中身を捨ててプレースホルダーに戻すことを追い出しと呼ぶ。
File Provider
macOS のクラウドのストレージのための OS の仕組み。同期のアプリは拡張として、OS からの呼び出しに応える。
Cloud Files API
Windows 10 1709 からの、プレースホルダーを使う同期のアプリのための API。中核のフィルターは NTFS だけで動く。
Synced の木
最後にサーバーと手元が一致したと確かめた木。3 方向のマージの共通の祖先になる。
3 方向のマージ
共通の祖先と 2 つの側を比べて、どちらで何が変わったかを決める方法。Git のマージと同じ考え方。
base_rev
書き込みの元にした中身のリビジョン。サーバーの今のリビジョンと違えば 409 で拒まれる。置き場所には base_node_ver を使う。
競合のコピー
2 つの編集がぶつかったとき、後に確定しようとした側の中身を残すために作る別の名前のファイル。
消しすぎの止め
手元からの削除が直近 5 分で 1,000 ファイルか木の 10% を超えたら、サーバーへ送る前に止めて利用者に確かめる仕組み。
内容の番地
content-addressed storage。中身のハッシュを保存のキーにする方式。中身が変われば番地も変わる。
リビジョン
ファイルの中身の 1 つのバージョン。ブロックの一覧とハッシュを持つ（revisions）。
ブロックの一覧
リビジョンの中身を表すブロックの（大きさ、SHA-256）の並び。1,024 ブロックまでは行の中、超えたら S3 に置く。
内容で区切る分割
CDC（content-defined chunking）。ファイルの中身から境界を決める分割。挿入・削除で境界がずれにくい。
回転のハッシュ
rolling hash。窓を 1 バイトずつ進めながら、少ない計算で窓の中身のハッシュを更新できるハッシュ。
ギアのハッシュ
バイトごとに表から 64 ビットの値を引き、左へずらして足す回転のハッシュ。直近 64 バイトだけで値が決まる。
重複排除
同じ中身のブロックを 1 回だけ保存すること。本システムではテナントの中だけで行う。
横の漏れ
サイドチャネル。答え・時間・容量の変化など、本来の出力でない手がかりから情報が漏れること。
参照の数
そのブロックを一覧に持つ、保持の期間の中のリビジョンの数。名前空間ごとに ns_block_refs に持つ。
GC
ガベージコレクション。参照のなくなったブロックを、猶予の後に消す処理（block-gc）。
名前空間
ノードの木・ns_seq・権限をまとめた単位。利用者のルート、共有フォルダー、チームのスペース、チームのフォルダー。
マウントのノード
別の名前空間を、木のある場所に載せることを表すノード（kind='mount'）。名前は載せる側ごとに持つ。
チームのスペース
チームのメンバーの端末の木のルートになる名前空間。最上位にチームのフォルダーと本人のフォルダーが載る。
ns_seq
名前空間ごとに、欠けも重なりもなく単調に増える操作の番号。
ジャーナル
名前空間の操作を ns_seq の順に書いた追記だけの表（ns_journal）。差分の取得の元になる。
カーソル
「どこまで読んだか」を表す署名つきの不透明な文字列。載せた名前空間ごとの番号の組を持つ。
取り直し
カーソルが使えないとき、木の全体を読み直すこと。409 reset で求める。
epoch
全体の 1 つの番号。DR の切り替えと、運用者が DB を時点へ戻したときだけ上がり、古いカーソルを取り直しにする。
耐久性
置いたデータを失わない度合い。S3 は 99.999999999% の設計。
可用性
求めたときに使える度合い。耐久性とは別の指標。
保存のクラス
S3 の置き方の種類。取り出しの速さ・単価・最小の課金の大きさと期間が違う（Standard、Standard-IA、Glacier Instant Retrieval など）。
Intelligent-Tiering
アクセスの頻度を見て、層を自動で移す S3 の保存のクラス。128 KB 未満のオブジェクトは監視せず、高頻度の層に置く。
CRR
Cross-Region Replication。S3 のオブジェクトを別のリージョンのバケットへ非同期に写す機能。RTC を有効にすると写す時間に目標が付く。
署名つき URL
期限と対象を決めて署名した URL。持っている人は、資格情報なしでそのキーへの PUT や GET だけができる。
チェックサム
中身から計算した短い値。S3 は指定された SHA-256 を計算し直し、合わなければ保存しない。
バージョニング
S3 のバケットの設定。上書き・削除の前のバージョンを残す。本システムは古いバージョンを 30 日で消す。
墓石
行を消さずに「削除した」の印（deleted_at）を付けて残すこと。復元と差分の配信に使う。
巻き戻し
フォルダーや名前空間の全体を、過去の時点の木へ戻す操作。本家の Rewind にあたる。
ランサムウェア
ファイルを暗号化して使えなくし、身代金を求める不正なプログラム。
sandbox
外へ出る道と権限を絞った隔離の環境。信用しない入力を処理する部品を閉じ込める。
利用者の中身のドメイン
本体と別の登録可能なドメイン（<brand>usercontent.<domain>）。利用者の中身を返し、本体の Cookie や画面に影響させない。
