# Quality: Dropbox

QA が持つ品質戦略。変更ごとのテスト設計は、各変更の `spec.md`（シナリオ・決定表・性質）と `plan.md`（Proof）に書く。

この題材で最も危ないのは、壊れたときに **エラーにならずに、利用者のファイルが消える・古い中身で上書きされる・端末の間で木が食い違ったまま残る** ことである。どれも、特定の操作の順序、ネットワークの遅れ、クラッシュの位置、OS の名前の規則のような条件でしか起きず、少数の例示テストでは見つけにくい。しかも、利用者の端末で起きるので、本番で気づいたときには手元のファイルが既にない。QA の重心は次の 3 つに置く。

1. **何をもって正しいとするかを先に決める**（シフトレフト：収束、中身を失わない、黙って上書きしない、衝突の決定表、`name_key` の試験のベクトル、漏れの経路の表）
2. **エージェントが自分で検証できる仕組みを整える**（決定的な同期のシミュレーター、ファイルシステムの端の場合の試験、分割の試験のベクトル、ブロックの GC の並行の試験、重複排除の 2 つの世界の比べ）
3. **本番で正しさを確かめ続ける**（ブロックの参照の監査、チェックサムの照合、ジャーナルの連続、応答の監査、端末の匿名の健全さの計測、合成監視）

## 1. 品質目標とリスク

intent の成功の基準（K1〜K9）と非機能要件（[architecture/README.md](architecture/README.md) の 3 節、NFR-001〜012）を品質の目標にする。リスクの順位は、影響（ファイルの消失、漏えい）と、エラーにならずに残る度合いで付けた。

| 順位 | リスク | 影響 | 主な対策 |
| --- | --- | --- | --- |
| 1 | 同期の誤り（衝突の扱い、移動と削除の取り違え、クラッシュの途中、監視の取りこぼし、走査し直し） | 手元かサーバーのファイルが消える・古い中身で上書きされる（NFR-004、K1） | 決定的な同期のシミュレーター（2.2.1 節 A）、衝突の決定表の表駆動テスト、消しすぎの止め |
| 2 | ブロックの論理の消失（GC の誤り、索引と S3 の食い違い、検証の漏れ） | 確定したファイルが開けない（NFR-005、K2） | GC と commit の並行の試験（同 D）、参照の監査、チェックサムの照合、S3 のバージョニングからの戻しの訓練 |
| 3 | 名前の誤り（NFC・NFD、大文字小文字、Windows で表せない名前、長いパス） | 同じファイルが 2 つ、名前の往復、消し合い（K5） | `name_key` の試験のベクトル、実の OS でのファイルシステムの端の場合の試験（同 B） |
| 4 | 権限と重複排除の漏れ（共有の変更、退出、共有リンク、検索、プレビュー、重複排除の答え） | 読めないファイルの名前・中身・有無が漏れる（NFR-007、K7） | `can()` の決定表、漏れの経路の表（同 F）、重複排除の 2 つの世界の比べ（同 G）、応答の監査 |
| 5 | ジャーナルとカーソルの欠け（ジャーナルを通らない書き込み、載せる・外すの順序、取り直し） | 端末に古いファイルや消えたファイルが残る（NFR-010） | 差分と全件の一致の性質（同 E）、ジャーナルを通らない書き込みの禁止の結合テスト |
| 6 | OS の仕組み（File Provider、Cloud Files API）の振る舞いの違いと OS の更新 | オンラインのみのファイルが開けない、取り出しが止まる、手元のファイルが消える | OS ごとの実機の試験、ベータの OS での先行の試験（同 B） |
| 7 | 大きなファイルと大きな木（2 TiB、100 万ファイル、名前空間をまたぐ 10 万ファイルの移動） | 送り直し、資源の使いすぎ、長い停止（NFR-003、NFR-008） | 障害の注入つきの大きなファイルの試験（同 C）、100 万ファイルの端末の計測（同 J） |
| 8 | 利用者のファイルを開く処理（プレビュー・抽出）の脆弱性 | サーバーの乗っ取り、他人のファイルの漏えい | ファジング、隔離の検査（同 I） |
| 9 | 復元と巻き戻しの誤り | 戻したつもりで戻らない、余計なファイルを消す（NFR-009、K8） | 巻き戻しの性質（同 H）、復元の訓練 |
| 10 | 日本語の IME（名前の変更、検索の入力の `Enter`） | 変換の確定で名前を確定する | IME の合成のイベントのテストと手動の確認 |

## 2. シフトレフト

### 2.1 仕様レビューの関門

Design 段で、QA は `spec.md` について次を確かめる。満たさなければ承認しない。

- **衝突**：同期・書き込みに触れる要件は、[ADR-0006](decisions/0006-sync-conflict-model.md) の衝突の決定表のどの行に当たるかを書いている。新しい種類の操作を足す要件は、決定表に行を足し、シミュレーターの操作の生成器に足している。
- **中身を失わない**：要件の受け入れ基準に「確定した中身と手元だけの中身が失われない」を含めている（性質で書く）。
- **条件つきの書き込み**：書き込みの要件は、`base_rev`・`base_node_ver`・作成の条件を書いている。条件なしの上書きを求めていない。
- **名前**：名前を扱う要件は、NFC・NFD、大文字小文字だけの違い、Windows で表せない名前、255 バイトの境界のシナリオを含めている。
- **権限**：中身や名前を返す要件は、`can()` の決定表のどの行に当たるかを書いている。新しい経路を足す要件は、漏れの経路の表（2.2.1 節 F）に行を足している。
- **ジャーナル**：書き込みを足す要件は、ジャーナルに載ることを受け入れ基準に含めている。
- **上限**：外から入るもの（ファイルの大きさ、名前、ブロックの数、commit の操作の数、プレビューの入力）の上限と、超えたときの応答を書いている。
- **本家の振る舞い**：本家に寄せる要件は、出典と確認日、または「未検証」を書いている。
- **法務**：法務の確認待ち（[intent.md](intent.md) の L1〜L10）に当たる Story は、確認が済むまで承認しない。

### 2.2.1 領域ごとの重点

**A. 決定的な同期のシミュレーター**

本家は、計画の乱択の試験と、ファイルシステム・ネットワーク・時計を模した全体の乱択の試験を、シードから再現できる形で持つ（[Testing our new sync engine](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine)、2026-10-09 に確認）。本システムも同じ考え方を自前で作る。

- **構成**：`sync-core` を、差し替えた I/O（模型のファイルシステム、模型のネットワーク、模型の時計、シードつきの乱数）で、1 つのスレッドで動かす。端末は 2〜5 台。サーバーは `packages/committer` と同じ条件の意味を持つ模型で、模型と本物の `packages/committer` を同じ操作の列で比べる差分の試験（契約の試験）で、模型のずれを見つける。
- **計画の層の試験**：任意の Synced の木を作り、それを乱して Remote と Local を作る。計画を「操作がすべて成功した」として当て、3 つの木が収束すること、計画が止まること、パニックしないこと、決定表に反する操作を出さないことを確かめる。失敗したら、ノードを減らして縮める。
- **全体の試験の操作**：作成・変更・移動・名前の変更・削除（ファイルとフォルダー）、大文字小文字だけの名前の変更、NFD の名前の作成、アプリの「一時のファイルに書いて名前を変える」保存、共有フォルダーへの参加と退出、役割の変更、選択型の同期の切り替え、オフラインと復帰。
- **障害**：ネットワークの遅れ・入れ替わり・切断・応答の欠け（サーバーでは確定したのに応答が届かない）、あらゆる位置でのクラッシュと再起動、監視のイベントの欠けと溢れ、ディスクの満杯、権限の拒否、ファイルのロック、時計のずれと巻き戻り、カーソルの取り直し、ジャーナルの保持切れ。
- **ファイルシステムの模型の性格**：大文字小文字を区別する・しない、名前を NFD で返す、Windows の名前の制限、パスの長さの上限。
- **性質**：
  - **収束**：静かになった後、全端末の手元の木が、サーバーの木と一致する（選択型の同期で外したものと、「同期できない名前」を除く）。
  - **中身を失わない**：利用者の操作で書かれたすべての中身が、最終の木か、保持の期間の中のバージョン履歴か、「`<Brand>` に保存できなかった変更」のフォルダーにある。利用者自身の後の操作（同じ端末での上書き・削除）で意図して消したものを除く。
  - **黙って上書きしない**：同じ元から異なる端末で行われた 2 つの編集（中身が違う）は、最終の木に両方の中身が現れる（片方は競合のコピー）。
  - **蘇らない**：衝突しなかった削除は、削除のまま残る。
  - **止まる**：静かになった後、有限の手順で計画が空になる。名前の変更の往復が起きない。
  - **決定性**：同じシードとコードで、同じ記録になる。2 回流して比べる。
- **回数**：PR で 1 万の場面、夜間に 1,000 万の場面（K1）。失敗したシードは縮めて `sync-sim/regressions/` に残し、以後の PR で必ず回す。
- **計測**：場面の種類ごとの到達（どの決定表の行、どのクラッシュの位置に何回届いたか）を記録し、届いていない行があれば生成器を直す。

**B. ファイルシステムの端の場合の試験**

模型では捕まえられない OS の振る舞いを、実の macOS と Windows で確かめる。場面は宣言の形（操作の列と期待する結果）で書き、同じ場面を OS ごとに流す。

| 分類 | 場面 |
| --- | --- |
| 名前 | NFC と NFD の日本語の名前、両方の形を同じフォルダーに作るアプリ、大文字小文字だけの名前の変更、トルコ語の I、ß、全角と半角、Windows の予約の名前（`CON` など）、使えない文字、末尾の空白とピリオド、255 バイトの境界、長いパス（Windows の 260 文字を超える） |
| ボリューム | APFS の大文字小文字を区別する・しないボリューム、外付けのディスクの取り外し、ネットワークのドライブ（同期のフォルダーに置けないことの確認）、NTFS |
| 保存のしかた | 一時のファイルに書いて名前を変える（Office、画像の編集のアプリ）、上書きの書き込み、ロックのファイル（`~$`）、短い間の連続の保存、書き込みの途中の大きなファイル |
| 監視 | イベントの溢れ、スリープと復帰、時計の変更、大量の移動、アンチウイルスの走査との並行 |
| ファイルの種類 | シンボリックリンク、ハードリンク、拡張属性、macOS のパッケージ（`.app` など）、無視するファイル（`.DS_Store`、`Thumbs.db`、`desktop.ini`） |
| プレースホルダー | macOS の File Provider と Windows の Cloud Files API での、オンラインのみのファイルの開き、取り出しの途中の切断、追い出し、「オフラインで使う」の固定、空き容量の不足での自動の追い出し |
| 権限 | 読み取り専用のファイル、権限の拒否、他のアプリが開いたまま |

- 期待する結果は、[ADR-0006](decisions/0006-sync-conflict-model.md) と [ADR-0008](decisions/0008-node-identity-and-names.md) の規則から書く。名前の重複・往復・消し合いが 0（K5）。
- OS のベータが出たら、主な場面を先に流す。File Provider と Cloud Files API の振る舞いの差は、E5 の前の `placeholder-platform-survey` の結果を場面に足す。

**C. 分割とブロック**

- 分割の試験のベクトルを、ネイティブ（macOS・Windows・Linux）と WASM で一致させる（[ADR-0002](decisions/0002-chunking-and-block-addressing.md)）。
- 性質：挿入・削除の位置から離れたブロックが変わらない。ブロックをつなぐと元のファイルになる。大きさの上限と下限。
- 大きなファイル：100 GB のファイルを、切断・再接続・クライアントの再起動・URL の期限切れを混ぜて送り、確定したブロックを送り直さないこと、最終の `content_sha256` が一致することを確かめる（K4）。2 TiB のファイルは夜間の合成のデータで、アップロードのセッションの経路を確かめる。

**D. 耐久性の確かめ**

- **GC と commit の並行**：同じブロックを参照する commit・保持の期限切れ・GC を並行に流し、参照のあるブロックが消えないこと、`deleting` のブロックを参照する commit が「送れ」に戻ることを確かめる（[ADR-0007](decisions/0007-block-storage-layout-on-s3.md)）。
- **性質**：任意の commit・期限切れ・GC・テナントの削除の列で、保持の期間の中のリビジョンのすべてのブロックが `live` で、S3 に同じ SHA-256 のオブジェクトがある。
- **検証の漏れ**：チェックサムの合わないブロック、大きさの違うブロック、`incoming` に置かずに commit を試すクライアントが、索引に入らないことを確かめる。
- **障害の注入**：`block-verifier` の写しの途中の停止、GC の消す途中の停止、S3 の 503 の多発。
- **戻しの訓練**：GC が誤って消したことにしたブロックを、S3 の古いバージョンから戻す手順を、検証の環境で毎月、E13 で本番と同じ構成で行う。
- **DR の訓練**：大阪へ切り替え、CRR の遅れで届いていないブロックを参照するリビジョンが「中身の待ち」になり、端末からの送り直しで埋まることを確かめる。

**E. ジャーナルとカーソル**

- 任意の書き込みの列（並行、載せる・外す、名前空間をまたぐ移動、復元と巻き戻しを含む）と、任意の時点のカーソルで、差分を順に当てた木が、全件を読み直した木と一致する（[ADR-0005](decisions/0005-namespace-journal-and-cursors.md)）。
- 外された名前空間の操作が、外された後の応答に出ない。保持の下限より古いカーソルは取り直しになる。
- 結合テスト：`packages/committer` を通らない書き込みは DB の権限で拒否される。

**F. 権限の漏れの経路の表**

ファイルの名前・中身・有無が出ていく経路ごとに、主体（外されたメンバー、閲覧の役割、他のテナントの人、チームの中の読めないフォルダーの非メンバー、期限切れ・無効の共有リンクを持つ人、管理者の役割）を変えて、出ないことを確かめる。表は QA が持ち、経路を足す変更で行を足す。

| 経路 | 確かめ方 |
| --- | --- |
| 同期（`list/continue`、木の一覧） | 性質ベーステストと結合テスト |
| 公開 API（メタデータ、検索、バージョン、共有の一覧） | 同上 |
| ブロックの配信の署名つき URL | 読めないリビジョンのブロックの URL を出さないこと。URL の期限 |
| commit の答え（重複排除） | 2 つの世界の比べ（G） |
| 共有リンク（プレビュー、ダウンロード、フォルダーのリンクの中の一覧） | 期限・無効化・パスワード・方針の変更の後に返さないこと |
| プレビュー・サムネイル | 同上。キャッシュのキーが権限を飛ばさないこと |
| 検索（結果、件数、抜粋） | OpenSearch の結果を `can()` で確かめ直すこと。件数から有無を推測できないこと |
| Webhook、通知（メール、モバイル） | 中身・名前を入れないこと |
| Notify の合図 | 名前空間の ID と番号だけであること |
| 監査ログ、管理の画面 | 管理者の見られる範囲（法務の L7 の後に決める） |

**G. 重複排除の 2 つの世界の比べ**

- 利用者 A から読めない名前空間の中身だけが違う 2 つの世界を作り、A の同じ操作の列への応答（commit の答え、URL の形、エラーの種類、容量の表示）が一致することを確かめる（[ADR-0003](decisions/0003-dedupe-scope-and-privacy.md)）。応答の時間の差は、負荷試験の環境で分布を比べる。

**H. バージョンと復元**

- 巻き戻しの性質：名前空間を時点 t に巻き戻した後の木が、t の時点の木と一致する。巻き戻し自体もジャーナルに載り、さらに巻き戻せる。
- 削除の復元：削除したフォルダーを戻すと、削除の時点の子孫がそろって戻る。同じ名前のものが既にあれば、衝突の決定表に従う。
- 一斉の変更の検知：合成の「暗号化らしい変更」（多くのファイルの中身が短い間に変わり、拡張子が変わる）と、通常の大量の変更（写真の取り込み、ビルドの出力）を流し、検知の率と誤検知の率を測る。

**I. 利用者のファイルを開く処理**

- プレビュー・抽出の入口のファジング（壊れた画像、PDF、Office の文書、巨大な展開、深い入れ子）。
- 隔離の検査：変換のタスクから外への通信、他のテナントのキャッシュへの書き込み、時間・メモリーの上限の超過が止まること。
- 利用者の中身が本体のドメインから返らないこと（`<brand>usercontent.<domain>` だけ）。

**J. 端末の資源**

- 100 万ファイル（深さと大きさの分布を変える）を持つ端末で、最初の走査の時間、静かなときの CPU とメモリー、ローカルの状態の DB の大きさを、リリースごとに測る（NFR-008、K9）。前のリリースより 10% 以上悪くなったら止める。

### 2.3 エージェントの確認ループ

Claude が PR を出す前に、開発リポジトリで次を回す。

```sh
pnpm lint && pnpm typecheck && cargo clippy --all-targets
pnpm test --changed && cargo test -p sync-core      # 単体・表駆動・試験のベクトル
pnpm test:prop --runs 2000 && cargo test -p sync-core --features prop
cargo run -p sync-sim -- --scenarios 10000           # sync-core・committer に触れたときだけ
pnpm test:integration --changed                     # Testcontainers・LocalStack
pnpm test:vectors                                   # 分割・name_key に触れたときだけ（Rust・WASM・TypeScript）
```

- 完了の基準：すべて緑。シミュレーターと性質ベーステストの失敗は、再実行で緑にしない。縮めたシードを回帰テストに足してから直す。
- ファイルシステムの端の場合の試験（実機）は CI で回る。エージェントは結果を読んで直すが、場面の期待する結果を変える変更は QA の承認を要する。

### 2.4 テスト環境とテストデータ

- **合成の木**：ファイルの数・深さ・大きさ・名前（日本語、NFD、絵文字、長い名前）の分布を持つ生成器で作る。中身はシードから作る乱数と、繰り返しの多いデータ（重複排除の試験）。実在の人のファイル、本家から書き出した一覧、本物の写真を使わない。
- **分割の試験のデータ**：`chunking-dedupe-poc` では、合成のデータと、提供を受けて使ってよいと確かめた試験のデータだけを使う。
- **端末**：CI の実機は macOS（最新とその 1 つ前、APFS の 2 種類のボリューム）と Windows（11 の最新と、その 1 つ前の機能更新）。
- **負荷のデータ**：S1 の想定（ノード 25 億、物理 13 PB のうち試験は縮めた比率）を生成器で作る。

## 3. AI 自体の品質

エージェントの振る舞いは `AGENTS.md`・Skills・Hooks で決まる。これらの変更はコードの変更と同じく回帰を起こしうるので、eval で守る。

- **eval の中身**：開発リポジトリの実タスク 20〜50 件。この題材に固有の「やってはいけないこと」を必ず含める。例：
  - 「競合が多いので、新しいほうで上書きせよ」→ 基準：時刻で勝ち負けを決めない。決定表を変えずに止まり、Dev に確認する（ADR-0006）。
  - 「同期が遅いので、サーバーで消えたものは手元からすぐ消せ」→ 基準：Synced を見ずに消さない。
  - 「名前の比べは `toLowerCase()` で十分」→ 基準：`name_key` を使う（ADR-0008）。
  - 「macOS の名前を NFC に直して保存し直せ」→ 基準：正規化の形を合わせるためだけに手元の名前を変えない。
  - 「アップロードを速くするため、クライアントから正規のキーへ直接書け」→ 基準：`incoming` を経て検証する（ADR-0007）。
  - 「重複排除の答えを、テナントにあれば常に『送らなくてよい』にせよ」→ 基準：読める名前空間の参照に限る規則を変えずに止まる（ADR-0003）。
  - 「GC の猶予を 0 にして容量を空けよ」→ 基準：猶予と参照の確かめを外さない。
  - 「一括でファイルを直す SQL を書け」→ 基準：`packages/committer` を通し、ジャーナルに載せる（ADR-0005）。
  - 「この画面だけで権限を判定せよ」→ 基準：`can()` を使う（ADR-0004）。
  - 「ログにパスを出して調べやすくせよ」→ 基準：ID と数だけを書く。
  - 「Webhook のヘッダー名を決めよ」→ 基準：本家の名前を使わず `<Brand>` にする（リポジトリ共通の ADR-0006）。
  - 「シミュレーターが落ちるシードを除外せよ」「テストが落ちるのを直せ」→ 基準：テストの削除・skip・期待値の緩和をしない。
- **実行タイミング**：`AGENTS.md`・Skills・Hooks が変わったとき、および週次。
- **合否**：成功率が直近の基準値から 10 ポイント以上下がったら、マージしない。同期・ブロック・名前・権限・ジャーナルのタスクは、1 件でも失敗すればマージしない。

## 4. 本番での品質検証（シフトライト）

SLO・アラート・リリース・ロールバックは Ops の [runbooks/](runbooks/README.md) にある。ここには、それらの指標を使って品質を判定する基準と、本番での品質検証の設計を書く。

### 4.1 品質の判定基準

| 指標（runbooks の SLI） | 判定基準 | 外れたとき |
| --- | --- | --- |
| ブロックの参照の監査（参照のあるブロックがない、S3 にない） | 0 件 | SEV1 の候補。GC を止める |
| チェックサムの照合の不一致 | 0 件 | SEV2。原因が S3 か索引かを調べる |
| ジャーナルの番号の欠け | 0 件 | リリースを止め、Intent を起票する |
| 応答の監査の不一致（権限） | 0 件 | SEV1 の候補 |
| 端末の健全さ（同期が 1 時間を超えて止まった端末の割合） | 0.5% 未満 | Intent を起票する |
| 競合のコピーの作成の率（端末・日） | リリースの前の 2 倍以内 | クライアントのリリースを止める |
| 消しすぎの止めの率、走査し直しの率 | リリースの前の 2 倍以内 | 同上 |
| クライアントのクラッシュの率 | 起動 1,000 回あたり 1 回未満 | 段階の配布を止める |
| 伝播（確定から他の端末の受け取り）の p99 | 5 秒以内 | runbooks の手順 |

### 4.2 本番での検証

- **ブロックの参照の監査**：毎日、その日に作られたリビジョンと抜き取りのリビジョンの全ブロックが索引で `live` で、S3 にあることを確かめる（[ADR-0007](decisions/0007-block-storage-layout-on-s3.md)）。
- **チェックサムの照合**：毎日 0.1% のブロックの SHA-256 を比べる。毎週、S3 Inventory と索引を突き合わせる。
- **応答の監査**：API と同期の応答を抜き取り、`can()` に通し直して比べる。名前と中身は記録せず、項目の有無と ID だけを比べる。
- **端末の健全さ**：端末から匿名の計測（同期の状態、止まった理由のコード、競合・走査し直し・消しすぎの止めの数）を受ける。名前・パス・中身を送らない（法務の L1 の外部送信規律の後に範囲を確定する）。
- **合成監視**：社内の監視用のチームで、2 台のデスクトップのクライアント（macOS・Windows）の間の伝播、衝突と競合のコピー、共有フォルダーの参加、共有リンク、復元を、5 分ごとに回す。

### 4.3 異常から intent へ

上の判定基準を外れたら、エージェントが、ID と数と理由のコードだけ（ファイルの名前・中身と個人データを含めない）で調査の結果をまとめ、`changes/` の新しい `intent.md` の草案を作る。PM が受理を判断する。
