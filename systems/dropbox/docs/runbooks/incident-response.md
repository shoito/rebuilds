# Runbook: インシデントへの対応（共通の進め方と最初の切り分け）

- Owner: Ops
- 対応するアラート: メタデータと同期の SLO のバーンレート、commit の p99、ジャーナルの欠け、SLI の集計の欠け（照合のジョブが動かなかった日を含む）、ログの秘密・名前の形の出力、個別の runbook のない呼び出しのアラート全部（[README.md](README.md) の 4 節）
- 最終確認日: 2026-10-09

## 共通の進め方

| 重さ | 目安 | 例 |
| --- | --- | --- |
| SEV1 | 確定した中身を失った疑い。読めない名前空間の名前・中身・有無が届いた疑い。多くの利用者で同期が止まる | ブロックの参照の監査の不一致、応答の監査の不一致、リージョンの障害、中身を消すクライアントの不具合 |
| SEV2 | SLO を大きく消費。同期の正しさが崩れるが、中身は残っている | ジャーナルの欠け、チェックサムの照合の不一致、伝播の p99 が 30 秒を超え続ける |
| SEV3 | 利用者の影響が小さい・迂回できる | 検索の索引の遅れ、Webhook の送信の失敗の増加 |

1. インシデントの指揮者（IC）を決め、チャンネルを作り、時刻を記録し始める。
2. 影響の範囲（経路、テナントの数、端末の数、期間）を決める。
3. 直前の変更を確かめる：サーバーのデプロイ、フラグ（`release.*`・`ops.*`）、マイグレーション、AppConfig の `client.*`、クライアントの段階の配布、`content_scan_policy`。疑わしければ [deploy-and-rollback.md](deploy-and-rollback.md) で戻す。同期・名前・分割・権限の規則の不具合は、フラグでなく前のイメージへ戻す（[README.md](README.md) の 3 節）。
4. 被害を止める → 原因を取り除く → 回復を確かめる、の順に進める。中身を失う恐れがあれば、最初に `ops.block_gc_enabled` を止める（止めても中身は失わない）。
5. 告知はステータスページで。権限の漏れと個人データの疑いは、法務と相談してから文面を決める（漏えい等の報告の要否は法務の L4）。
6. 調べるのは、中身と個人データを含まないログ・メトリクス・トレース・業務の記録（ID、数、理由のコード）だけ。ファイルの名前・パス・ハッシュはログにない前提で、ブロックは `block_id` で指す。中身を見る必要があれば、顧客の明示の依頼を確かめ、break-glass（2 人の承認、時間の上限）で入り、プラットフォームの事象に残す（[security.md](../architecture/security.md) の 9 節）。
7. エージェントは本番に経路を持たない。調査の結果（ID と数）を人から受け取り、`changes/` の新しい `intent.md` の草案を作る。

## 場面 1：メタデータと同期の SLO・commit の遅れ

### 症状

バーンレートのアラート。commit の p99 が 2 秒を 10 分超える。

### 確認

1. 経路（`api` の木の読み出し、commit、`list/continue`）ごとの 5xx と時間の分布。CloudFront と `api` のどちらで出ているか。
2. Aurora の writer の CPU、ロックの待ち。上位 50 の名前空間のロックの待ちと 429（`top_ns_*`）。1 つの名前空間に集中していれば `namespace-lock-contention.md`（予定）の内容で、自動の同期の道具やバッチを探す。
3. 復元・巻き戻し・名前空間をまたぐバッチ・保持の期限の処理・埋めのマイグレーションが同時に走っていないか（`maintenance` の枠の使用）。
4. Notify の再接続の殺到の後の `list/continue` の山か（[capacity.md](../architecture/capacity.md) の 3.2 節）。

### 対処

1. 背景の処理を絞る：`restore-runner` の commit の割合、`lifecycle` の速さ、`background` のアップロードの受け入れ（`ops.upload_admission_*`）。
2. 直前の変更が原因なら戻す。
3. writer の CPU が足りなければ、reader に逃がせる読み出しを確かめ、writer の大きさを上げるのは計画作業にする。

## 場面 2：ジャーナルの欠け（`journal_gap_total`）

### 症状

ある名前空間の `ns_journal` の `seq` が連続していない。

### 影響

端末と API の利用者に、その名前空間の変更が届かない恐れ（NFR-010）。SEV2。

### 確認

1. 欠けた名前空間と `seq` の範囲、その時刻の書き込みの経路とデプロイ。
2. `packages/committer` を通らない書き込みが DB のロールで拒否されているか。拒否されずに通った書き込みがあれば、そのロールを止める。
3. 分割を落とすジョブ（92 日）が、使われているカーソルの範囲を落としていないか。

### 対処

1. 原因の経路を止め、直すまで再開しない。
2. 欠けの範囲を読み飛ばしたかもしれない端末に取り直しをさせるため、その名前空間の `floor_seq` を今の `ns_seq` まで上げる（欠けの後まで読み進めたカーソルも含めて、その名前空間を載せたすべてのカーソルが取り直しになる。[ADR-0023](../decisions/0023-tree-listing-snapshot-and-journal-retention.md)。カーソルは 409 `reset`（`truncated`）になり、端末は Synced と比べて差を当てるので手元の変更を失わない）。`floor_seq` の更新はプラットフォームの事象に残す。
3. 欠けの原因を `changes/` に起票する。

## 場面 3：SLI の集計の欠け・照合のジョブが動かなかった

### 症状

`slo_minutely` に穴がある。`integrity_audit_runs` にその日の行がない（「不明」として呼び出す）。

### 確認と対処

1. `worker-slo-aggregator`・照合のジョブのタスクとキューを確かめる。
2. 照合のジョブが動かなかった日は、0 件と見なさない。直したら、その日の分を流し直す。参照の監査が 24 時間動かなければ、`ops.block_gc_enabled` を止める（[block-storage.md](../architecture/block-storage.md) の 5.2 節）。

## 場面 4：秘密・名前の形がログに出た

### 症状

ログの走査が、トークンの接頭辞（`<brand>_at_` など）、メールアドレス、64 桁の 16 進数（ハッシュ）、ホームのディレクトリのパスの形を見つけた。

### 確認と対処

1. 出したサービスとバージョン、期間、件数を決める。該当のロググループの読み出しを絞る。
2. トークンなら、そのトークンを取り消す（[ADR-0041](../decisions/0041-accounts-auth-and-device-credentials.md)）。
3. 出した呼び出しを直し、lint の型の印を足す。ログの消去の要否は法務と決める。

## エスカレーション

- SEV1：Ops の責任者、Dev のテックリード、セキュリティの担当をすぐに呼ぶ。権限の漏れ・個人データは法務も。
- 中身の消失の疑い：テックリードと [README.md](README.md) の 4 節の `block-integrity-incident.md` の担当。
- リージョンの障害：[disaster-recovery.md](disaster-recovery.md)。
- ランサムウェア・一斉の削除の疑い：[mass-change-response.md](mass-change-response.md)。
