# Runbook: デプロイとロールバック

- Owner: Ops
- 対応するアラート: デプロイ中の自動ロールバック、デプロイの直後の 5xx・commit の p99・409 と 4xx の率の急な上がり・参照の監査の不一致、クライアントの段階の配布の止める基準（[README.md](README.md) の 3 節、[delivery.md](../architecture/delivery.md)）
- 最終確認日: 2026-10-09

## 症状

- サーバーのデプロイの直後に、エラーや遅れが増えた。自動のロールバックが動いた。
- クライアントの新しいバージョンの端末で、異常終了・競合のコピー・消しすぎの止め・走査し直しの率が上がった。

## 影響

同期と API の SLO を消費する。同期・名前・権限の規則の不具合は、端末の手元のファイルや漏えいに及ぶ（SEV1 の候補）。

## 確認

1. 直前のデプロイのサービスとイメージ、マイグレーションの段（広げる・埋める・縮める・消す）、フラグと AppConfig の変更を並べる。
2. 新旧のタスクの数とヘルスチェック、CloudWatch のアラーム（5xx、commit の p99、409 と 4xx の率、参照の監査）。
3. クライアントなら、[observability.md](../architecture/observability.md) の 8 節の端末のダッシュボードで、新しいバージョンと古いバージョンを同じ期間で比べる。

## 対処

### サーバー

1. まずフラグで戻す（`release.*` を 0%）。同期・名前・分割・権限の規則はフラグにしていないので、次へ進む。
2. 1 つ前のイメージへ戻す。マイグレーションは広げる段だけを先に当てているので、前のイメージが今の DB で動く。縮める段の後は前へ戻さない（前へ直すリリースを出す）。
3. `block-gc` の新しいバージョンは止めた状態で入れ、参照の監査が 24 時間 0 のときだけ `ops.block_gc_enabled` を有効にする。疑いがあれば止める。
4. `notify` は 1 タスクずつ。抜く前に `reconnect` を送る（[capacity.md](../architecture/capacity.md) の 3.2 節）。
5. データの直接の書き換えはしない。直しは `packages/committer` の保守の経路だけ。

### クライアント

1. `client.rollout` の割合を 0 にし、目録を作り直す。既に入った端末はそのまま。
2. 中身を消す不具合なら、そのバージョンを `client.blocked_versions` に入れ、サーバーで commit と `list/continue` を 426 `client_blocked` にする。端末は同期を止め、手元のファイルを残す。
3. 古いバージョンへは戻さない。前のコードを新しい番号で出し直す（戻しのリリース）。社内の段は 24 時間に縮めてよいが、1% の段は省かない。
4. モバイルはストアの審査の時間が読めないので、`client.blocked_versions` を先に使う。

### マイグレーション

- 広げる段の失敗：失敗したマイグレーションを直して当て直す。前のイメージはそのまま動く。
- 埋めの遅れ：`maintenance` の枠（全体の commit の 10%）を超えない。急ぐために枠を広げない。
- 縮める・消す段は計画作業として平日 10〜15 時に行い、失敗したら前へ直す。

## リリースの前

- エラーバジェットの残り、凍結の期間（[README.md](README.md) の 3.1 節）を確かめる。
- 互換の関門（2 つ前までのクライアントの呼び出しの再生）、マイグレーションの比較、Terraform の plan の検査が緑。
- クライアントは、サーバーの対応が本番に出た後にだけ配布を始める。

## エスカレーション

- 同期・名前・権限の規則の不具合：Dev のテックリードと QA。漏えいの疑いはセキュリティの担当と法務。
- 戻しても直らない：[incident-response.md](incident-response.md) で IC を立てる。

## 事後

- 調査結果を `changes/` の新しい `intent.md` として起票する。
- 自動のロールバックの条件と、段階の配布の止める基準で足りなかったことを、ここと [delivery.md](../architecture/delivery.md) に反映する。
