# ADR-0044: 転送中は TLS 1.2 以上。保存時はデータの種類ごと・リージョンごとのカスタマー管理の KMS の鍵を使い、テナントごとの鍵を MVP で持たない。アプリの秘密は鍵の ID つきで 2 つを並べて回す。端末では資格情報を OS の鍵の保管庫に置き、モバイルのオフラインのファイルだけを暗号化する

## Context

- 中身は S3 に SSE-KMS とバケットキーで置くと決めた（[ADR-0007](0007-block-storage-layout-on-s3.md)）。鍵の分け方、メタデータ（Aurora）・索引（OpenSearch）・キャッシュの鍵、アプリの秘密の回し方、端末の上の扱いは決めていない。
- 物理 13 PB・ブロックの送信のピーク 2 GB/秒（[architecture/README.md](../architecture/README.md) の 2 節）。KMS の要求は、バケットキーで抑える前提である。
- 大阪へ S3 を CRR で、Aurora を Global Database で写す（[ADR-0007](0007-block-storage-layout-on-s3.md)）。
- 顧客の鍵（BYOK）とエンドツーエンドの暗号化は MVP の後（E16）で、重複排除・プレビュー・検索と両立しない（[intent.md](../intent.md)）。
- 社内の運用者が日常の権限で中身を読めないようにしたい（[security.md](../architecture/security.md) の 9 節）。
- 他の題材（Google Calendar の ADR-0041）は、テナントごとの鍵を持たず、データの種類ごとの鍵にした。

## Options

1. **データの種類ごと・リージョンごとのカスタマー管理の鍵。テナントごとの鍵を持たない**
2. テナントごとの鍵（暗号での消去を可能にする）
3. AWS 管理の鍵（`aws/s3` など）

## Decision

1 を採用する。

- **転送中**：エッジは TLS 1.2 以上（1.3 を優先）。S3 への直接の送受信は `aws:SecureTransport` を必須にする。Aurora・Valkey・OpenSearch・サービスの間も TLS。
- **保存時の鍵**：`kms-blocks`（`incoming`・`blocks`・`blocklists`）、`kms-previews`、`kms-audit`、`kms-aurora`、`kms-search`、`kms-cache`、`kms-secrets`、`kms-logs` を、東京と大阪でそれぞれ作る。マルチリージョンの鍵は使わない。写しは写し先のリージョンの鍵で暗号化する。
- **鍵の方針**：`kms:Decrypt` を決めたサービスのロールだけに許す。人のロールは break-glass を除いて復号できない。鍵の削除の予約・無効化は SCP で break-glass に限る。1 年で自動で回す。
- **テナントごとの鍵を持たない。** 解約・削除の消去は、行とオブジェクトを消すことで行う（[ADR-0045](0045-audit-log-and-data-lifecycle.md)）。
- **アプリの秘密**：Secrets Manager（大阪へレプリカ）に置く。カーソルの HMAC の鍵は鍵の ID をカーソルに入れ、1 年ごとに新しい鍵で署名し、古い鍵での確かめを 100 日残す。CloudFront の署名つき URL の鍵は 90 日ごとに、2 つを並べて回す。Webhook の秘密は Aurora に封筒の暗号化（`kms-secrets`）で置く。トークン類は DB に SHA-256 だけを持つ。
- **端末**：資格情報と端末の鍵は OS の鍵の保管庫に置く。ローカルの状態の DB とブロックの索引は暗号化しない。モバイルのオフラインのファイルは、鍵の保管庫の鍵で暗号化する。

### 他の案を選ばなかった理由

- **2（テナントごとの鍵）**：個人のテナントが S1 で 40 万、S3 で 2,000 万あり、KMS の鍵の数・費用・要求の上限が重い。バケットキーはバケットの鍵で効くので、テナントごとの鍵では効きにくい。テナントの中で重ねたブロック（[ADR-0003](0003-dedupe-scope-and-privacy.md)）の扱いは変わらないが、テナントをまたぐ写し（X1）が鍵をまたぐ。暗号での消去の利得は、法務の L6 の結論と BYOK（E16）で見直す。
- **3（AWS 管理の鍵）**：鍵の方針で人のロールの復号を拒めない。鍵の使用を CloudTrail で分けて見にくい。

## Consequences

- 良くなること：
  - 鍵の方針で、運用者の日常の権限から中身の復号を外せる。
  - 鍵の数が少なく、バケットキーで KMS の要求と費用を抑えられる。
- 引き受けるコスト：
  - 消去は本当に消すことに頼り、S3 のバージョニング（30 日）とバックアップ（35 日）の間は残る。
  - 端末の同期のフォルダーとローカルの DB は平文で、端末のディスクの暗号化は OS に任せる。

## Confirmation

- Terraform の plan の検査：すべてのバケット・Aurora・OpenSearch・Valkey・ロググループが決めた鍵を使う。鍵の方針で人のロールの `kms:Decrypt` がない。
- 結合テスト：古い鍵の ID のカーソルが、100 日の間は確かめられ、その後は取り直しになる。
- 本番：KMS の要求の数と拒否を監視する。人のロールの復号の試みを呼び出しにする。
