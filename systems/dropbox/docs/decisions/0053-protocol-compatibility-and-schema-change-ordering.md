# ADR-0053: サーバーは 2 つ前までのクライアントのリリースを受け、API は足すだけにする。`chunker_version` は読み出しを消さず、新しいバージョンはサーバーが受けると知らせてからクライアントが書く（フラグにしない）。`names_version` の更新は影の列で両方の鍵を持ってから切り替える。カーソルの形は新旧を受けてから古いものを `reset` にする。スキーマの変更は広げる・埋める・縮める・消すの順で、埋めは `packages/committer` の保守の経路と枠で流す

## Context

- クライアントは古いバージョンへ戻せず、段階の配布の間は複数のバージョンが同時に動く（[ADR-0052](0052-client-signing-staged-rollout-and-minimum-version.md)）。サーバーは 2 つ前までのクライアントを受ける（[runbooks/README.md](../runbooks/README.md) の 3 節）。
- 分割の規則は `chunker_version` で固定し、母数を変えるときは新しいバージョンを足して古いものの読み出しを消さない（[ADR-0002](0002-chunking-and-block-addressing.md)）。公開 API には `chunker_version` 0 がある（[ADR-0018](0018-upload-sessions-and-block-grants.md)）。
- `name_key` は `names_version` に結び付き、Unicode の更新は移行の作業になる（[ADR-0008](0008-node-identity-and-names.md)）。
- カーソルは形のバージョン `v` を持つ（[ADR-0005](0005-namespace-journal-and-cursors.md)）。
- 同期・名前・分割・権限の規則をフラグにしない（[AGENTS.md](../../AGENTS.md)）。
- ノードを変える書き込みはすべて `packages/committer` を通してジャーナルに載せる。直接の `UPDATE` は DB のロールで拒む（[ADR-0005](0005-namespace-journal-and-cursors.md)）。最大の表は `nodes`（25 億行）と `ns_journal`（約 400 億行、日の分割）（[capacity.md](../architecture/capacity.md) の 5.1 節）。
- 他の題材（Google Calendar の ADR-0049）は、広げる・移る・縮める・消すの順を決めた。

## Options

新しい分割・名前の規則の切り替え：

1. **サーバーが受けると知らせ（コードのバージョンで決まる）、クライアントがそれを見て書く**
2. AppConfig のフラグで、書くバージョンを切り替える
3. クライアントとサーバーを同時に切り替える

## Decision

1 を採用する。

### クライアントとの互換

- サーバーは 2 つ前までのデスクトップ・モバイルのリリースと、1 つ前の Web の資産を受ける。API は足すだけにし、意味を変えるものは新しい項目・操作として足す。古いものは、2 つ前のリリースが最低のバージョンより古くなってから消す。
- クライアントは `<Brand>-Client: <kind>/<version>` を送る。PR の CI で、2 つ前までのリリースの記録した呼び出しを再生する。
- ジャーナルの `op` を足すときは、知らない `op` を受けたクライアントが取り直しにする約束を、最初のリリースから持たせる。

### `chunker_version`

- サーバーが新しいバージョン N の検査を本番に出し、`GET /v1/config` で受けるバージョンの一覧に N を入れる。N を書けるクライアントは、一覧に N があるときだけ新しく書くファイルを N で分ける。古いバージョンの読み出しと試験のベクトルを消さない。

### `names_version`

- サーバーとクライアントに新旧の両方の鍵を計算するコードを出し、`nodes` に影の列 `name_key_next` を足して保守の枠で埋める。新しい鍵でぶつかる名前を数え、名前の変更（`packages/committer` を通す）で解く。一意の索引を新しい鍵へ切り替えて `names_version` を上げ、`GET /v1/config` で知らせる。最低のバージョンを 90 日以内に新しいリリースへ上げる。

### カーソル

- 新旧の両方の形を受けるコードを出してから新しい形を発行し、古い形の使用が 0 に近くなってから古い形を 409 `reset` にする。

### スキーマの変更の順序

| 段 | 中身 |
| --- | --- |
| 広げる | 表・列（NULL を許すか定数の既定）・索引（`CONCURRENTLY`）を足す。新しい表は `tenant_id`・`ns_id`・FORCE RLS |
| 埋めて移る | 書き込みは新旧の両方へ。埋めは `packages/committer` の保守の経路で、`maintenance` の枠（全体の commit の 10% まで）を通し、名前空間の単位で進める |
| 縮める | 古いものへの書き込みを止め、制約を外す |
| 消す | 縮める段の後、1 リリース以上空けて消す |

- 大きな表の書き換え（`ALTER TYPE`、関数の既定）をしない。`ns_journal` の形は新しい日の分割から変え、古い分割は保持の期間で落とす。
- 破壊の変更と、それを読むコードの削除を同じ PR に入れない（CI で確かめる）。
- クライアントのローカルの DB は、1 つのリリースの間は広げるだけ（[ADR-0052](0052-client-signing-staged-rollout-and-minimum-version.md) の戻しのリリース）。

### 他の案を選ばなかった理由

- **2（フラグ）**：分割の規則をフラグで切り替えることになり、規則に反する。フラグの値と、サーバーが本当に受けられるかがずれうる。
- **3（同時）**：段階の配布の間、新旧のクライアントが同時に動くので、同時の切り替えは成り立たない。

## Consequences

- 良くなること：
  - 段階の配布の間も、新旧のクライアントが同じサーバーで正しく動く。
  - 分割と名前の規則の切り替えが、サーバーのコードのバージョンで決まり、取り違えがない。
  - 大きな表の変更が、書き込みの上限と利用者の commit を押しのけない。
- 引き受けるコスト：
  - 古い項目と操作を、2 リリース分（約 1 か月）以上持ち続ける。
  - `chunker_version` を変えた後、変わったファイルは変わらないブロックも送り直す。
  - `names_version` の更新は、影の列と移行の作業で数週間かかる。

## Confirmation

- CI：2 つ前までのリリースの呼び出しの再生、マイグレーションの比較（破壊の変更と削除の同居の禁止、新しい表の RLS）。
- 試験のベクトル：すべての `chunker_version` の境界がネイティブと WASM で一致する。`name_key` の新旧の鍵が Rust と TypeScript で一致する。
- 性質ベーステスト：任意の新旧のクライアントの混ざった列で、シミュレーターの収束と中身を失わない性質が保たれる（[quality.md](../quality.md) の 2.2.1 節 A に、バージョンの混在を生成器に足す）。
