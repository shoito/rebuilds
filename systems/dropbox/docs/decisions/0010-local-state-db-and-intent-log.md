# ADR-0010: ローカルの状態の DB は SQLite（WAL）の 1 つのファイルで、3 つの木・意図の記録・送った commit を持つ。手元のファイルの操作は「意図を書く → 操作 → 結果を書く」の順にし、再起動では観測と期待の値を比べて進めるか捨てる。応答の届かない commit は、記録を残したまま差分を取り直してから計画し直す

## Context

同期の途中でクライアントが落ちる・電源が切れることは避けられない。落ちる位置によって、次の誤りが起きうる。

- 手元のファイルを置き換えたが、DB に記録していない。再起動で「手元が変わった」と見て、受けた中身をサーバーへ送り返す。
- DB に「消した」と記録したが、ファイルは消えていない。再起動で「手元で作った」と見て、上げ直す。
- commit がサーバーで確定したが、応答が届かない。同じ作成をもう一度送り、2 つにする。

[ADR-0006](0006-sync-conflict-model.md) は「操作の前に意図を書き、操作の後に結果を書く」と決め、形を sync-engine の領域に残した。ローカルの状態の DB は SQLite（[architecture/README.md](../architecture/README.md) の 4 節）。

## Options

1. **SQLite の 1 つのファイルに、3 つの木・意図・送った commit を持つ。意図は同期の書き込みで残す。再起動では観測と期待の値で解く**
2. 意図の記録を別の追記のファイル（ログ）に持つ
3. 意図を記録せず、再起動のたびに走査し直して Synced と比べる
4. commit に冪等のキーを付け、サーバーが 24 時間覚える

## Decision

1 を採用する。4 は採らない。詳細は [sync-engine.md](../architecture/sync-engine.md) の 7 節。

- DB は `sync.db`（WAL）。表は `remote_nodes`・`local_nodes`・`synced_nodes`・`intents`・`pending_commits`・`held_deletes`・`cursors`・`sync_meta`。
- 書き込みは制御のループだけが行う。`intents` の `prepared` の書き込みは `synchronous=FULL` で、操作の前に確実に残す。他の書き込みは `NORMAL`。
- 意図は、期待する前の観測と後の観測（`file_id`・`size`・`mtime`・`sha256`）を持つ。再起動では、操作ごとの表（置き換え・移動・削除・フォルダーの作成）で「済んだ」「済んでいない」「どちらでもない」に分け、済んだなら結果を書き、済んでいないなら Local が期待の前と同じときだけやり直し、どちらでもなければ捨てて計画し直す。
- 受けた中身は、同じボリュームの `.<brand>.cache/staging` に組み立て、ハッシュを確かめ、置き換えの直前に手元が計画の時と同じかを確かめる。
- commit を送る前に `pending_commits` に書く。応答がないまま再起動・時間切れになったら、その名前空間の差分を読み終えてから計画し直す。確定していれば、決定表の「そろった」の行で吸収される。
- DB が壊れたら、作り直す（Remote を番号 0 から、Local を走査で）。Synced がないので、中身の違うファイルはすべて競合のコピーとして残す。

### 他の案を選ばなかった理由

- **2（別のログ）**：木の更新と意図の完了を 1 つのトランザクションで書けない。2 つのファイルの食い違いを解く処理が増える。
- **3（記録しない）**：置き換えの途中（staging と元の両方がある）を判断できない。100 万ファイルの走査を再起動のたびに行うと NFR-008 の最初の走査の時間を毎回使う。
- **4（冪等のキー）**：サーバーに覚える表と期限が要る。期限を過ぎた再送は同じ問題になる。条件つきの書き込み（`base_rev`、「その名前がまだない」）と、差分を読んでからの計画し直しで、二重の確定は起きない。

## Consequences

- 良くなること：
  - どの位置で落ちても、二重の削除・二重の作成が起きない。
  - 木と意図が 1 つのトランザクションで進み、食い違わない。
  - サーバーに冪等のための状態を持たない。
- 引き受けるコスト：
  - `prepared` の同期の書き込みで、手元の操作 1 回ごとに fsync が 1 回増える。大量の取り出しでは、意図を 100 件ずつまとめて書く。
  - 100 万ファイルで DB は数百 MB になる（ディスク）。
  - 応答の届かない commit の後は、差分の読み出しを待つ分だけ遅れる。

## Confirmation

- 表駆動テスト：DT-SYNC-002（操作 × 観測）。
- 性質ベーステストとシミュレーター：PROP-SYNC-006（Synced は確かめた結果でしか進まない）、PROP-SYNC-007（意図の各位置でのクラッシュの後、二重の削除・作成がない）。応答の欠け（サーバーで確定、応答なし）の障害を生成器に入れる。
- 実機の試験：置き換えの途中で強制終了し、再起動の後にファイルの中身とサーバーのリビジョンが一致する（[quality.md](../quality.md) の 2.2.1 節 B）。
