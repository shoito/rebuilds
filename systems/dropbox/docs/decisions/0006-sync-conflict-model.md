# ADR-0006: クライアントは Remote・Local・Synced の 3 つの木で計画し、サーバーは `base_rev` つきの条件の書き込みだけを受ける。衝突は中身が残るほうを選び、編集どうしは競合のコピー、削除と編集は編集を残す

## Context

同期は、複数の端末とサーバーが、同じ木を別々に変える問題である。次の場面で、片方の変更が黙って失われやすい（[intent.md](../intent.md) の Problem）。

- 2 台が同じファイルを編集する。オフラインで編集して、後で戻る。
- 片方がフォルダーを消し、他方がその中にファイルを足す。
- 片方がファイルを移動し、他方が同じファイルを編集・移動する。
- 同期の途中でクライアントが落ちる。OS の監視のイベントが溢れて取りこぼす。
- 外付けのディスクが外れて、同期のフォルダーが丸ごと消えたように見える。

「手元にない」が「消した」なのか「まだ受けていない」なのかは、手元とサーバーの 2 つの状態だけでは決められない。最後にそろった状態（共通の祖先）が要る。

本家の同期エンジンは、Remote・Local・Synced の 3 つの木を持ち、Synced をマージの基準にして変わった側を決める（[Testing our new sync engine](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine)、2026-10-09 に確認）。本家は、食い違った編集で、編集した人の名前と「conflicted copy」と日付を付けたコピーを作り、後に保存されたほうをコピーにする（[Conflicted copy](https://help.dropbox.com/organize/conflicted-copy)、同日に確認）。本家の計画の規則と実装は公開されていない。この ADR は、3 つの木の考え方（バージョン管理の 3 方向のマージと同じ一般の考え方）を使い、規則は本システムで決める。

## Options

1. **3 つの木（Remote・Local・Synced）で 3 方向のマージをし、サーバーは条件つきの書き込みだけを受ける。衝突は中身が残るほうを選ぶ**
2. 2 つの木（手元とサーバー）に、ファイルごとの「手元で変えた」の印を足す
3. 最後に書いたほうが勝つ（時刻で決める）
4. 中身のマージ（行の単位の 3 方向のマージ、CRDT）

## Decision

1 を採用する。

### クライアントの 3 つの木

- `sync-core` は、ローカルの状態の DB（SQLite）に 3 つの木を持つ。ノードはサーバーの `node_id` で結ぶ。手元で作ってまだサーバーにないものは、仮の ID を持つ。
  - **Remote**：`list/continue` で受けたサーバーの木（[ADR-0005](0005-namespace-journal-and-cursors.md)）。
  - **Local**：監視と走査で観測した手元の木。ファイルの ID（inode・File ID）、大きさ、更新の時刻、必要なら `content_sha256` を持つ。
  - **Synced**：最後に Remote と Local が一致したと確かめた木。
- 計画は、Synced と Remote の差を「サーバーの変化」、Synced と Local の差を「手元の変化」とし、下の決定表で操作を決める。操作の結果を確かめたら、3 つの木を進める。
- 時刻で勝ち負けを決めない。更新の時刻は「変わったかもしれない」の手がかりにだけ使い、変わったかどうかはハッシュで確かめる。
- 監視のイベントが溢れた、クライアントが長く止まっていた、同期のフォルダーの持ち主の印が合わない、のときは、手元の全体を走査し直して Local を作り直す。Synced は残すので、走査し直しで手元の変更を失わない。
- **同期のフォルダーが丸ごと見えないとき**（外付けのディスクが外れた、フォルダーが移された）は、削除として扱わず、同期を止めて利用者に知らせる。

### サーバーの条件つきの書き込み

- ノードは、中身のリビジョン `rev` と、置き場所のバージョン `node_ver`（親と名前と削除の状態）を持つ（[ADR-0008](0008-node-identity-and-names.md)）。
- 中身の変更は `base_rev`、移動・名前の変更・削除は `base_node_ver`、作成は「その親にその `name_key` がまだない」を条件にする。条件が合わなければ 409 と今の状態を返す。
- 条件なしの上書きの API を持たない。公開 API の「上書き」の指定も、サーバーが今の `rev` を条件にする形に直す（api-and-webhooks の領域）。
- 循環（フォルダーを自分の子孫へ移す）は、サーバーが拒む。

### 衝突の決定表

上から順に評価し、最初に一致した行を採用する。「手元」「サーバー」は、Synced からの変化を指す。

| # | 手元の変化 | サーバーの変化 | 結果 |
| --- | --- | --- | --- |
| 1 | 中身の変更 | 中身の変更（`content_sha256` が手元と同じ） | 衝突にしない。サーバーのリビジョンを Synced にする |
| 2 | 中身の変更 | 中身の変更（違う） | サーバーの中身を元の名前に置き、手元の中身を競合のコピーとして作る |
| 3 | 中身の変更 | 削除（ファイルか、親のフォルダー） | 手元の中身を同じパスに作り直す（親のフォルダーも作り直す）。削除を取り消したことを知らせる |
| 4 | 削除 | 中身の変更 | サーバーの中身を受ける。手元の削除を取り消す |
| 5 | 削除 | 削除 | そろったとみなす |
| 6 | 移動・名前の変更 | 中身の変更 | 両方を当てる（移動を commit し、新しい中身を受ける） |
| 7 | 移動・名前の変更 | 移動・名前の変更（違う行き先） | サーバーの置き場所を採る。手元の移動は捨て、知らせる。中身は失わない |
| 8 | フォルダーの中への追加 | そのフォルダーの削除 | フォルダーを作り直し、足したものだけを残す。他の子は削除のまま |
| 9 | フォルダーの削除 | そのフォルダーの中への追加・変更 | サーバーで足された・変えられたものを残し、手元にフォルダーを作り直す。他の子の削除は commit する |
| 10 | 作成 | 同じ親に同じ `name_key` の作成（中身が同じ、またはどちらもフォルダー） | 1 つにまとめる |
| 11 | 作成 | 同じ親に同じ `name_key` の作成（違う） | サーバーのものを元の名前に置き、手元のものを競合のコピーにする |
| 12 | 変更・作成（書けない名前空間で） | 役割が閲覧に下がった・外された | 手元のものを利用者のルートの「`<Brand>` に保存できなかった変更」のフォルダーへ移して commit し、知らせる |
| 13 | 移動 | 移動先が循環になる | サーバーの置き場所を採り、手元の移動は捨てる |

- 「後に commit したほうがコピーになる」：サーバーは先に届いた commit を採り、後の commit を 409 にする。コピーを作るのは、後に届いた側のクライアントである。
- どの行も、確定した中身を消さない。手元だけにある中身は、サーバーに上げるか、手元に残すまで消さない。

### 競合のコピーの名前

- `<名前> (<端末の名前> の競合コピー <YYYY-MM-DD>).<拡張子>`。利用者の言語が英語なら `<name> (conflicted copy from <device> <YYYY-MM-DD>).<ext>`。日付は端末のタイムゾーン。同じ名前があれば末尾に ` 2`・` 3` を足す。
- 本家は編集した人の名前を入れるが、本システムは端末の名前を入れる。同じ人の 2 台の衝突が多く、人の名前では見分けられないため。文言は法務の L10 の後に確定する。

### 消しすぎの止め

- 1 回の計画で手元から消す数が 1,000 ファイル、または同期している木の 10% を超えたら、サーバーへ削除を commit する前に止め、利用者に確かめる（デスクトップの通知）。確かめるまで、他の変更の同期は続ける。
- サーバーからの削除で手元を消すときは、OS のゴミ箱へ移す（File Provider・Cloud Files の管理のファイルを除く）。

### クラッシュからの再開

- 手元のファイルの操作（置き換え、移動、削除）の前に、ローカルの状態の DB に意図を書き、操作の後に結果を書く。再起動したら、意図があって結果がない操作を、手元の観測から「済んだ」「済んでいない」を判断して進めるか捨てる（sync-engine の領域）。
- 受けた中身を置くときは、一時のファイルに組み立ててハッシュを確かめ、計画の時から手元のファイルが変わっていないことを確かめてから置き換える。変わっていれば、決定表の 2 に当たるとして計画し直す。

### 他の案を選ばなかった理由

- **2（2 つの木と印）**：印の付け忘れ・クラッシュで印を失うと、「手元にない」を削除か未受信か決められない。走査し直しのたびに危うい判断になる。
- **3（時刻で勝ち負け）**：端末の時計はずれる。負けた側の編集が黙って消える。
- **4（中身のマージ）**：多くのファイルは文書・画像・バイナリで、行のマージの意味がない。テキストだけマージしても、利用者に見えない形で中身を変える。

## Consequences

- 良くなること：
  - どの衝突でも、確定した中身と手元だけの中身が残る。
  - 走査し直し・カーソルの取り直し・クラッシュの後も、Synced があるので判断を誤らない。
  - 決定表で規則を 1 か所に書き、表駆動テストとシミュレーターで確かめられる。
- 引き受けるコスト：
  - 競合のコピーが増え、利用者が整理する手間が残る。
  - ローカルの状態の DB に 3 つの木を持つ容量（100 万ファイルで数百 MB の DB）。NFR-008 のメモリーとは別に、ディスクを使う。
  - 消しすぎの止めで、意図した一括の削除にも確かめが入る。

## Confirmation

- 決定表の表駆動テスト：上の表の全行を、`sync-core` の計画の単体テストで確かめる。表は spec から読み込む。
- 決定的な同期のシミュレーター（[quality.md](../quality.md) の 2.2.1 節 A）：任意の端末の数・操作・ネットワークの遅れ・クラッシュ・監視の溢れで、静かになった後の木が収束し、確定した中身と手元だけの中身が失われず、ぶつかった変更が競合のコピーとして残る。
- 結合テスト：サーバーの書き込みの API に、条件のない書き込みの経路がないこと（すべての操作に `base_rev`・`base_node_ver`・作成の条件がある）を、API の定義の検査で確かめる。
- 本番：競合のコピーの作成の率、消しすぎの止めの率、走査し直しの率を、端末の匿名の計測で見る。
