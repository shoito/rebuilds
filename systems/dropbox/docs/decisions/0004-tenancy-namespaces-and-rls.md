# ADR-0004: 個人とチームをテナントにし、名前空間（利用者のルート、共有フォルダー、チームのフォルダー）を持ち主のテナントに置く。名前空間の表は `app.ns_ids` の RLS で絞り、権限は `can()` の 1 つの関数で判定する

## Context

利用者は 2 種類いる。

- **個人**：無料・有料の個人のアカウント。家族や取引先とフォルダーを共有する。
- **チーム**：会社・団体。メンバー、グループ、チームのフォルダー、共有の方針、端末、監査ログを管理者が持つ。

ファイルの木には、テナントをまたぐ関わりが多い。

- 個人が、別の会社のチームのメンバーと共有フォルダーを持つ。共有フォルダーの中身は、全員の木に同じ場所として現れる。
- チームのフォルダーの中に、一部のメンバーだけが入れるフォルダーがある。
- 共有リンクで、アカウントを持たない人が読む。

木の単位で見ると、権限の境界は「テナント」ではなく「共有の単位（共有フォルダー、チームのフォルダー、利用者のルート）」である。この単位を**名前空間**と呼ぶ。ジャーナルとカーソルも名前空間ごとに持つ（[ADR-0005](0005-namespace-journal-and-cursors.md)）。本家の API にも名前空間の考え方（`ns:` で始まる名前空間の相対のパス）がある（[HTTP API documentation](https://www.dropbox.com/developers/documentation/http/documentation)、2026-10-09 に確認）が、内部の形は公開されていない（**未検証**）。

読めない名前空間の名前・中身・有無が、1 つの経路でも届けば漏えいである（NFR-007）。経路は多い：同期、API、Web、共有リンク、プレビュー、検索、Webhook、通知、重複排除の答え（[ADR-0003](0003-dedupe-scope-and-privacy.md)）。

## Options

分離の方式：

1. **共有スキーマ＋RLS。名前空間の表は `ns_id` の集合で、テナントの表は `tenant_id` で絞る**
2. 共有スキーマ＋RLS。すべての表を `tenant_id` だけで絞り、テナントをまたぐ共有フォルダーは専用の経路で読む
3. テナントごとのスキーマ・DB

権限の判定：

- a. **`can()`（許すか）を 1 つのモジュール（`packages/access`）にし、すべての経路が使う**
- b. 経路ごとに判定を書く
- c. DB の RLS のポリシーで、役割と方針まで判定する

## Decision

1 と a を採用する。

### テナントと名前空間

- **個人のアカウントを 1 人 1 つのテナント、チームを 1 つのテナントにする。** チームのメンバーの個人の領域（メンバーのルート）は、チームのテナントの名前空間にする。個人のアカウントとチームの間の移り方は accounts-and-teams の領域で決める。
- **名前空間の種類**：`user_root`（利用者のルート）、`shared_folder`（共有フォルダー）、`team_space`（チームのスペースの最上位）、`team_folder`（チームのフォルダー）。名前空間は持ち主のテナント（`tenant_id`）を 1 つ持つ。
- **名前空間は、別の名前空間の中に「載せる」（マウント）。** 利用者の木は、ルートの名前空間に、共有フォルダーやチームのフォルダーを載せたものである。載せる場所は `ns_mounts`（載せる側の名前空間、親のノード、名前、載せる名前空間）で表す。チームのフォルダーの中の、一部のメンバーだけのフォルダーも、別の名前空間として載せる。
- 権限は名前空間の単位（と共有リンクのノードの単位）で持つ。名前空間の中のファイルごとの ACL は持たない。

### RLS

- テナントのテーブルには `tenant_id`、名前空間のテーブルには `tenant_id` と `ns_id` を持たせ、主キーとインデックスの先頭に置く。ID は UUIDv7。`FORCE ROW LEVEL SECURITY` を設定する。
- **名前空間の表**（`nodes`、`revisions`、`ns_journal`、`ns_block_refs`、`ns_mounts`、`shared_links` など）のポリシーは `ns_id = ANY(app.ns_ids)`。`packages/access` が、要求ごとに操作する名前空間を決め、権限を確かめてから `SET LOCAL app.ns_ids` を設定する。1 回のトランザクションで扱う名前空間は 1,000 以下にし、超えたらバッチに分ける。
- **テナントの表**（`blocks`、`teams`、`members`、`groups`、`team_policies`、`audit_events` など）のポリシーは `tenant_id = app.tenant_id`。
- **トランザクションのテナントは、操作する名前空間の持ち主にする。** 利用者 A（テナント TA）が、テナント T の共有フォルダーに書くとき、`app.tenant_id` は T、`app.actor_id` は A にする。ブロックは T に置く（[ADR-0003](0003-dedupe-scope-and-privacy.md)）。
- **RLS の外の表**は次だけにし、ファイルの名前・パス・中身の列を持たせない。読めるのは専用の DB のロールだけにする。
  - `accounts`、`sessions`、`devices`、メールアドレスからアカウントの解決
  - `ns_access`（主体 → 名前空間、役割、持ち主のテナント）：A が読める名前空間の集合を引く
  - `ns_directory`（名前空間 → テナント、S2 ではクラスタ）
  - `link_tokens`（共有リンクのトークンのハッシュ → 名前空間、リンク）
  - outbox の読み出しの位置、SLI の集計
- **テナントをまたぐ処理は、次の経路だけにし、専用の DB のロールと関数を通す。** 一覧にない経路を足すときは、先にこの ADR を直す。
  - X1：重複排除の写し（読める他のテナントの名前空間のブロックを、書き込み先のテナントへ S3 の中で写す。[ADR-0003](0003-dedupe-scope-and-privacy.md)）
  - X2：共有リンクの解決（`link_tokens` から名前空間を引き、その名前空間の文脈で読む）
  - X3：システムの作業（GC、照合、容量の集計、保持の期限）。テナントを 1 つずつ文脈に設定して回す
  - X4：Relay の outbox の読み出し、SLI の集計
  - X5：共有の参加と退出の反映（共有フォルダーの持ち主が外したメンバーの、ルートの名前空間に「外す」の行とジャーナルを書く。参加は招かれた人が自分のテナントの文脈で書く。[ADR-0005](0005-namespace-journal-and-cursors.md)）

### 権限の判定

- **名前空間の役割**：`owner`・`editor`・`viewer`。主体は利用者、グループ、チーム（チームの全員）。
- **`can(actor, action, target)`**：読む、書く、共有を変える、リンクを作る、復元する、巻き戻す、管理する、を判定する。入力は、役割、名前空間の種類、チームの方針（チームの外への共有の可否、リンクの可否と必須の条件）、管理者の役割、端末の状態（切り離された端末を拒む）。
- 共有リンクの主体は「リンクを持つ人」で、`view` だけを持つ。パスワード・期限・方針は `can()` の入力にする（shared-links の領域）。
- **すべての経路が `can()` を通す。** 同期の `list/continue`、API、Web、Link、プレビューの配信、検索の結果（OpenSearch の結果を返す前に確かめ直す）、Webhook の送信、通知、重複排除の答え。
- c は、方針と役割の組み合わせ（チームの方針、管理者、リンク）を SQL のポリシーで書くと、検証と変更が難しい。RLS は「どの名前空間の行を読めるか」の最後の守りに限る。

### 他の案を選ばなかった理由

- **2（`tenant_id` だけ）**：共有フォルダーの読み書きが、ほとんどテナントをまたぐ。専用の経路が主な経路になり、RLS が守りにならない。逆に、同じテナントの中の読めない名前空間（人事のフォルダー）を RLS で守れない。
- **3（テナントごと）**：S3 で 2,000 万の個人のテナントに対して、スキーマの数とマイグレーションが重い。テナントをまたぐ共有フォルダーの読み書きが DB をまたぐ。

## Consequences

- 良くなること：
  - 共有フォルダーの読み書きが、テナントをまたいでも同じ経路（名前空間の RLS）で守られる。
  - 同じチームの中の読めないフォルダーも、RLS で守られる。
  - 名前空間が、権限・ジャーナル・S2 のシャードの単位としてそろう。
- 引き受けるコスト：
  - 要求ごとに読める名前空間の集合を決める手間が増える。`ns_access` を Valkey にキャッシュし、共有の変更で消す。
  - 名前空間をまたぐ操作（共有フォルダーへの移動）は、2 つの名前空間の書き込みになる（metadata-and-journal の領域）。
  - 名前空間の中のファイルごとの権限を持たない。一部だけを絞るには、別の名前空間（フォルダー）に分ける。

## Confirmation

- 結合テスト：名前空間の表とテナントの表のすべてに `FORCE ROW LEVEL SECURITY` とポリシーがあることを、スキーマの検査で確かめる。RLS の外の表の一覧を CI が上の一覧と照らす。
- 性質ベーステスト：任意の共有・退出・役割の変更・方針の変更の列で、利用者 A が読めない名前空間の名前・中身・有無が、どの経路（漏れの経路の表、[quality.md](../quality.md)）の応答にも出ない。
- 決定表の表駆動テスト：`can()` の決定表（namespaces-and-sharing・shared-links の領域で書く）の全行。
- lint：`packages/access` の外で、役割・方針の条件を書くコード（役割の文字列の比べ）を禁止する。
- 本番：API と同期の応答を抜き取り、`can()` に通し直して比べる（応答の監査）。
