# ADR-0018: 「送れ」と答えたら必ずアップロード（`upload_id`）を作り、検証したブロックをそのアップロードの許可（`block_grants`）として記録する。commit が受けるブロックは「読める名前空間の参照にある」か「この主体の許可がある」ものだけで、索引にあるだけでは受けない。1,024 ブロックを超えるファイルはアップロードのセッションで一覧を貯める。公開 API の利用者は固定 4 MiB の分け方（`chunker_version` 0）を使ってよい

## Context

[ADR-0003](0003-dedupe-scope-and-privacy.md) は、commit の答えを「読める名前空間の参照にあれば送らなくてよい、それ以外は送れ」と決めた。[ADR-0007](0007-block-storage-layout-on-s3.md) は、クライアントが `incoming` へ送り、`block-verifier` が確かめて正規のキーへ写し、commit は「一覧のすべてのブロックが索引で `live`」を確かめる、と決めた。

この 2 つを組み合わせると穴がある。

- 「索引で `live`」だけを確かめると、利用者 A は、読めない名前空間にあるブロックのハッシュを知っていれば、送らずに commit できる。確定したファイルを読めば、他人の中身が手に入る（ハッシュから中身を得る攻撃）。
- 送ったブロックを検証した後、commit の送り直しの時点で、そのブロックはまだどの名前空間からも参照されていない。「読める名前空間の参照」の規則だけでは、A が自分で送ったブロックも受けられない。

また、2 TiB のファイルは約 210 万ブロックで、1 回の commit で一覧を送れない（[ADR-0002](0002-chunking-and-block-addressing.md)）。公開 API の利用者に、内容で区切る分割の実装を求めるのも重い。

## Options

受けてよいブロックの決め方：

1. **「読める名前空間の参照」か「この主体が送って検証された許可」のどちらか**
2. 索引で `live` なら受ける（ADR-0007 の文言のまま）
3. commit のたびに、すべてのブロックを送らせる（重複排除の答えを使わない）

大きなファイル：

- a. **アップロードのセッションに、1,024 ブロックずつ一覧を貯め、`finish` で確定する**
- b. 一覧を S3 に先に置かせ、commit はその番地だけを送る
- c. ファイルを 1,024 ブロックごとの部分のファイルに分けて commit する

公開 API の分け方：

- x. **`chunker_version` 0（4 MiB の固定）を足す**
- y. 公開 API でも内容で区切る分割を必須にする

## Decision

1、a、x を採用する。詳細は [block-storage.md](../architecture/block-storage.md) の 4 節。

- commit の各ブロックを `have`（読める名前空間の参照）、`copy`（読める他のテナントの参照。X1 の写し）、`granted`（この主体の許可）、`need` に分ける。`need` の判定に、書き込み先のテナントの索引の有無を使わない。
- `need` が 1 つでもあれば、`uploads` の行を作り、ブロックごとに `incoming` の署名つきの PUT の URL（SHA-256 と大きさを署名に含む、15 分）を返す。
- 検証（`packages/blocks` の `verify`）が通ったら、`block_grants(tenant_id, actor_id, upload_id, hash, expires_at=7 日)` を書く。commit は送り直しで `upload_id` を付け、許可で受ける。
- commit は、許可のまだないブロックが `incoming` にあれば、同じ要求で 8 ブロック・1 秒まで `verify` を呼ぶ。残れば `blocks_pending` で待たせる。
- 1,024 ブロックを超えるファイルは `upload_session/start`・`blocks`・`status`・`finish` を使う。一覧は `upload_session_entries` に貯め、`finish` で `blocklist_hash` を計算して `blocklists/` に置く。セッションは活動から 7 日、作成から 30 日で切れる。セッションの検証済みのブロックは `pin_until` で GC から守る（[ADR-0019](0019-block-refcount-and-gc-protocol.md)）。
- `chunker_version` 0 は「4 MiB の固定、最後だけ短い」。公開 API の利用者が使ってよい。サーバーは、どのバージョンでも境界の正しさを確かめず、大きさの上限と一覧のハッシュだけを確かめる（ADR-0002 と同じ）。
- ADR-0007 の「一覧のすべてのブロックが索引で `live`」は、「`have`・`copy`・`granted` のどれかで、索引で `live` か `orphaned`（`deleting` でない）」と読み替える。

### 他の案を選ばなかった理由

- **2（索引で `live` なら受ける）**：ハッシュを知るだけで他人の中身を自分のファイルにできる。ADR-0003 の守りが commit の側で破れる。
- **3（毎回送らせる）**：自分のファイルの編集・移動・コピーで送る量が減らない。NFR-003 に合わない。
- **b（一覧を先に S3 へ）**：クライアントに `blocklists` への書き込みを許すことになり、ADR-0007 の「クライアントは `incoming` にだけ書く」に反する。一覧の各ブロックの区分を返す場もない。
- **c（部分のファイル）**：1 つのファイルが複数のリビジョンに分かれ、`content_sha256` とバージョン履歴の意味が崩れる。
- **y（CDC を必須）**：API の利用者の実装の負担が大きい。CDC で得られるのは重複の率の改善だけで、正しさには関わらない。

## Consequences

- 良くなること：
  - ハッシュを知るだけでは、他人の中身を得られない。
  - 再開は、検証済みの番号を引くだけで済み、送り直しが起きない。
  - 2 TiB のファイルも、要求の大きさを一定に保って送れる。
- 引き受けるコスト：
  - `uploads`・`upload_blocks`・`block_grants` の行が、新しいブロックごとに増える（7 日で消す）。
  - commit の答えが「送れ」の後、送り直しが 1 往復増える。
  - `chunker_version` 0 のブロックは、CDC のブロックと重ならない。

## Confirmation

- 性質ベーステスト：PROP-BLK-003（許可なしでは受けない）、PROP-BLK-004（2 つの世界）、PROP-BLK-005（再開）。
- 決定表：DT-BLK-001（commit の答え）、DT-BLK-002（検証）。
- 結合テスト：他人のブロックのハッシュだけを並べた commit が、URL を返して確定しない。許可の期限切れの後は `need` に戻る。
