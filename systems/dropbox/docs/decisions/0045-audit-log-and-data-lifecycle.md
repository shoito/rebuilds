# ADR-0045: 監査ログを、管理と安全の事象（Aurora、操作と同じトランザクション）、ファイルの活動の事象（Firehose → S3 の Object Lock、Athena で引く）、プラットフォームの事象に分け、名前を持たず ID で持ち、日ごとのハッシュの連鎖で改ざんを見つける。保持の期間を `retention_policies` の 1 つの表で持ち、解約・削除は猶予の後に `tenant_id` で消してブロックは GC の経路で消す。完全な削除は 24 時間の後に実行する。値は法務の L3・L6 の後に確定する

## Context

- チームの管理者は、誰が共有を変えたか、誰がどのファイルを消し・ダウンロードし・リンクで外へ出したかを追う必要がある（[intent.md](../intent.md) の価値 3、NFR-007）。
- ファイルの活動は量が多い。S1 で commit のピークは 5,000 件/秒（[architecture/README.md](../architecture/README.md) の 2 節）。これを監査の表として Aurora に重ねると、メタデータの書き込みと資源を取り合う。
- `ns_journal` は同期のためのもので、90 日で落ちる（[ADR-0005](0005-namespace-journal-and-cursors.md)）。ダウンロードと共有リンクのアクセスを持たない。
- ファイルの名前・パスをログに出さない規則がある（[AGENTS.md](../../AGENTS.md)）。監査の行に名前を持てば、名前の写しが保持の期間の違う場所に増える。
- 保持の期間と消去の期限は法務の L3・L6 の確認待ちで、値を 1 か所で変えられる形が要る。
- ブロックは参照 0 から 7 日の猶予の後に消し、S3 のバージョニングで 30 日戻せる（[ADR-0007](0007-block-storage-layout-on-s3.md)）。
- 乗っ取った資格情報でバージョン履歴まで消されると、戻せない（[security.md](../architecture/security.md) の 3.3 節）。

## Options

監査ログ：

1. **管理と安全の事象を Aurora に、ファイルの活動を Firehose → S3 に分ける。どちらも名前を持たない**
2. すべてを Aurora の監査の表に書く
3. すべてを CloudWatch Logs に書く
4. `ns_journal` を長く持ち、監査に使う

消去：

- a. **保持の期間を 1 つの表で持ち、猶予の後に `tenant_id` で消し、ブロックは GC の経路で消す**
- b. 表ごとに削除のジョブを書く

## Decision

1 と a を採用する。

### 監査ログ

| 種類 | 置き場所 | 書き方 |
| --- | --- | --- |
| 管理と安全の事象 `tenant_audit_events` | Aurora、月で分割、テナントの RLS | 操作と同じトランザクション。書けなければ操作も失敗 |
| ファイルの活動の事象 `activity_events` | Firehose → S3 `audit` のバケット（Parquet、テナントと日で分割、Object Lock）。Athena で引く | `activity-exporter` が outbox からジャーナルの操作を写し、Link と配信の URL の発行がアクセスを送る。チームのプランだけ |
| プラットフォームの事象 `platform_audit_events` | Aurora の保守用のスキーマ | 運用者・break-glass・直接の修正・`epoch`・検査の構成・保全 |

- 行は ID・主体・端末・操作・対象・理由のコード・要求の ID・IP アドレスを持ち、ファイルの名前・パス・中身を持たない。画面と書き出しで、`can()` で許した範囲の名前をその時に引く。
- テナントごと・日ごとに `row_hash = SHA-256(prev_hash ‖ 正規化した行)` の連鎖を作り、日の終わりの値を Object Lock のバケットへ写して毎日確かめる。
- 活動の事象の欠けは、名前空間ごとのジャーナルの番号と事象の数を日ごとに照らして見つける。

### 保持と消去

- 保持の期間の正本は `retention_policies`（データの種類 → 期間、根拠、法務の結論のバージョン）と Terraform の S3 のライフサイクル。CI が両者を比べる。既定の値は [security.md](../architecture/security.md) の 8.1 節。
- 解約・アカウントの削除は `suspended`（個人 7 日、チーム 30 日の猶予）→ `purging`。`tenant-purge` のジョブが、他のテナントのメンバーから共有フォルダーを外す書き込みをジャーナルに載せ、名前空間とテナントの表を `tenant_id` で 1 万行ずつ消し、ブロックの索引を `orphaned` にする。ブロックは `block-gc` の 7 日と S3 の 30 日の後に消える。
- 利用者による完全な削除は、再認証の後 24 時間待って、`packages/committer` の期限切れと同じ経路で実行する。待つ間は取り消せ、知らせる。
- 法的な保全は `legal_holds` で表し、保持・消去の処理が対象を飛ばす。MVP に入れるかは法務の L6。

### 他の案を選ばなかった理由

- **2（Aurora だけ）**：活動の事象がピークで commit の数倍になり、メタデータの writer を圧迫する。
- **3（CloudWatch Logs）**：操作と同じトランザクションで書けず欠けうる。テナントで絞った検索と書き出しを管理者の画面から出しにくい。
- **4（ジャーナルを長く）**：同期の保持と監査の保持が混ざる。ダウンロードと共有リンクのアクセスを持たない。
- **b（表ごとのジョブ）**：保持の値が散らばり、法務の結論を当てる場所が分からなくなる。

## Consequences

- 良くなること：
  - 管理と安全の事象が欠けず、改ざんを連鎖で見つけられる。
  - ファイルの活動の量がメタデータの DB に乗らない。
  - 名前の写しが監査ログに増えない。
  - 法務の結論を 1 つの表とライフサイクルに当てれば済む。
- 引き受けるコスト：
  - 活動の事象の検索は Athena で非同期になり、画面は数秒〜数十秒待つ。
  - 名前を引けなくなった古い事象は ID だけになる。
  - 消去の完了まで、チームで約 68 日かかる（猶予・GC・S3 のバージョン）。

## Confirmation

- 結合テスト：管理と安全の事象の対象の操作が、監査の行を書けないときに失敗する。
- 日次のジョブ：連鎖の検証と、活動の事象の欠けの照合。合わなければ呼び出し。
- 結合テスト：`tenant-purge` の後、テナントの ID でどの表・S3 の接頭辞・Valkey の鍵・OpenSearch の索引を探しても 0 件（GC の猶予の後のブロックを含む）。
- CI：`retention_policies` と Terraform の S3 のライフサイクル・ログの保持が一致する。
- lint：監査の行の型に名前・パスの列がない。
