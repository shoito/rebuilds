# ADR-0042: チームのドメインは DNS の TXT で確かめ、SSO は SAML 2.0 か OIDC の IdP を 1 つ持ち、必須にできる（`team_admin` だけはパスキーで入れる）。SCIM 2.0 で利用者とグループを受ける。チームへの参加は個人と別のアカウントにする。プランの機能と容量の上限を `plan_features` の 1 つの表で持ち、容量の超過とプランの変更で中身を消さない（容量の数え方は ADR-0026）

## Context

- チームの利用者は、日本の中小・中堅企業で、Microsoft Entra ID や Okta などの IdP を持つことが多い（[intent.md](../intent.md) の Affected users）。メンバーの入退社を IdP から反映したい。
- チームのテナントは、メンバーのルートの名前空間、チームのスペース、チームのフォルダーを持つ（[ADR-0004](0004-tenancy-namespaces-and-rls.md)）。個人のアカウントのテナントとは別である。
- 容量は、名前空間の持ち主のテナントに論理の大きさで数え、`packages/committer` が名前空間の `logical_bytes` を増減し、Worker が 1 分ごとにテナントの和を出す（[ADR-0026](0026-membership-lifecycle-and-quota.md)、[ADR-0003](0003-dedupe-scope-and-privacy.md)）。上限の値、プランごとの機能、超えたときの振る舞いは決めていない。
- 本家は、容量を超えると同期を止める（[Dropbox stopped syncing](https://help.dropbox.com/sync/files-not-syncing)、2026-10-09 に確認）。本家の SSO・SCIM の細部は確かめていない（**未検証**）。
- 他の題材（Google Calendar の ADR-0036）は、TXT のドメインの確認、IdP 1 つ、SSO の必須化と break-glass、SCIM の停止の写しを決めた。

## Options

個人とチームの関係：

1. **チームへの参加は別のアカウント。個人のデータは共有とコピーで移せる**
2. 個人のアカウントをチームのテナントへ移す（データも移す）
3. 1 つのアカウントが複数のテナントに属する

プランと容量の上限：

- a. **プランの機能と上限を 1 つの表（`plan_features`）にし、`can()` と各領域が読む。超過では増える操作だけを止める**
- b. プランの名前を各画面・各サービスで比べる
- c. 超過で同期を止め、長く超えたら古いファイルを消す

## Decision

1 と a を採用する。

### ドメインと SSO

- ドメインは `_<brand>-challenge.<ドメイン>` の TXT `<brand>-domain-verification=<token>` で確かめ、毎日確かめ直す。7 日見つからなければ `lapsed` にして知らせる。1 つのドメインは 1 つのチームだけが持つ。
- SSO はチームに IdP を 1 つ。SAML 2.0（SP 起点だけ、署名した主張を必須）か OIDC（認可コード＋PKCE）。メンバーは IdP の主体の ID とチームの組で結ぶ。メールアドレスの一致だけで結ばない。
- SSO を必須にできる。必須のとき、`team_admin` だけは登録したパスキーで入れる（break-glass。監査ログに残す）。
- JIT は、確認したドメインのメールアドレスで、席に空きがあり、チームが許すときだけ。

### SCIM

- SCIM 2.0 の `Users` と `Groups`。チームごとの Bearer のトークン（`<brand>_scim_`）。冪等にする。
- 停止（`active=false`）はメンバーを `suspended` にし、[ADR-0041](0041-accounts-auth-and-device-credentials.md) の取り消しを行う。チームの方針で端末の切り離しか、切り離しと消去を指示する（[ADR-0043](0043-admin-roles-device-wipe-and-member-access.md)）。`DELETE` は退出の手順を始め、データをすぐに消さない。

### 個人とチーム

- チームへの参加は、仕事のメールアドレスで別のアカウントを持つこと。個人のアカウントをチームのテナントへ移さない。
- 個人のファイルを移したい人には、個人のアカウントからチームのアカウントへフォルダーを共有し、チームの側で自分のフォルダーへコピーする流れを示す。読める名前空間からのコピーなので、ブロックは [ADR-0003](0003-dedupe-scope-and-privacy.md) の表の 2 行目（[ADR-0004](0004-tenancy-namespaces-and-rls.md) の X1）で S3 の中で写る。テナントをまたぐ新しい経路を足さない。
- メンバーの退出では、ルートの名前空間を引き継ぎ先のメンバーのルートに載せ、持ち主を付け替える（`ns_access` と `mount` だけ。中身を写さない）。

### プランと容量の上限

- プランの機能の可否と容量の上限は `plan_features`（プラン → 機能 → 値）の 1 つの表にし、`can()` と各領域が読む。画面とサービスでプランの名前を比べない。
- 容量の数え方と、commit での判定（上限＋余裕、507 `owner_quota_exceeded`）は [ADR-0026](0026-membership-lifecycle-and-quota.md) に従う。
- 容量を超えても、削除・移動・小さくなる変更・読み出し・共有は続ける。デスクトップは上げられない変更を手元に残し、受ける側の同期を続ける。**容量の超過とプランの変更（下げる）で中身を消さない。**

### 他の案を選ばなかった理由

- **2（個人をチームへ移す）**：テナントをまたぐブロックの移し（S3 のキーのテナントが変わる）、共有フォルダーの持ち主の付け替え、他のテナントのメンバーの載せる場所の書き直しが要り、テナントをまたぐ新しい経路になる。チームの管理者に、個人の過去のファイルが見えうる（法務の L4・L7）。
- **3（複数のテナント）**：`app.tenant_id` が要求ごとに変わり、メンバーの行・端末・容量・方針の判定が「どのテナントとして」を毎回持つ。共有フォルダーの名前空間と RLS で既にテナントをまたげるので、利得が小さい。
- **b（プランの名前を比べる）**：プランを足す・値を変えるたびに、経路ごとの条件を直すことになり、漏れる。
- **c（超過で消す）**：「失わない」（[intent.md](../intent.md) の価値 1）に反する。長く使われない無料のアカウントの扱いは法務の L9 で決める。

## Consequences

- 良くなること：
  - プランの値を 1 つの表で変えられる。
  - 退出の引き継ぎが中身を写さずに済む。
  - IdP からの停止が 60 秒以内に効く。
- 引き受けるコスト：
  - 容量を超えた利用者の中身を持ち続ける費用を引き受ける。
  - 個人とチームの両方を使う人は、2 つのアカウントを使い分ける。

## Confirmation

- 性質ベーステスト：任意のプランの変更と容量の超過の列で、中身とリビジョンが消えず、増えない操作が拒まれない。
- 結合テスト：SAML の署名なしの主張・範囲の外の主張・期限切れ・別の受け手を拒む。OIDC の `nonce`・`aud` を確かめる。SCIM の同じ要求を 2 回送って結果が同じ。
- 結合テスト：SSO の必須のチームで、`team_admin` 以外がパスキー・メールのコードで入れない。
- lint：`packages/access` と `plan_features` の読み出しの外で、プランの名前を比べるコードを禁止する。
