# ADR-0008: ノードは UUIDv7 の ID で指し、親と名前を持つ。名前は NFC で持ち、一意は `name_key`（NFC＋case folding）で決める。OS で表せない名前は、サーバーの名前を変えずに端末で「同期できない名前」として示す

## Context

ファイルとフォルダー（ノード）を、何で指し、名前をどう比べるかを決める。次の問題がある。

- **パスで指すと、移動が重い。** 10 万ファイルのフォルダーの名前を変えると、子孫のパスがすべて変わる。パスを主キーにすると、子孫の行をすべて書き換える。共有リンク、バージョン履歴、コメントの結び付きも切れる。
- **OS ごとに名前の規則が違う。**
  - macOS：APFS は名前の正規化の形を保ったまま、正規化の違いを区別せずに引ける。HFS+ は NFD で持つ。アプリによって NFC と NFD のどちらの名前も現れる（Apple の [APFS Guide の FAQ](https://developer.apple.com/library/archive/documentation/FileManagement/Conceptual/APFS_Guide/FAQ/FAQ.html)。Apple が古い文書としている。2026-10-09 に確認）。既定は大文字小文字を区別しない。
  - Windows：NTFS は既定で大文字小文字を区別せず、`<>:"/\|?*` と制御文字、`CON`・`NUL` などの予約の名前、末尾の空白とピリオドを使えない。Cloud Files API は NTFS だけで動く（[Build a Cloud Sync Engine](https://learn.microsoft.com/en-us/windows/win32/cfapi/build-a-cloud-file-sync-engine)、2026-10-09 に確認）。
  - 日本語：「が」は NFC で 1 文字、NFD で「か」＋濁点の 2 文字。全角の「カ」と半角の「ｶ」は、NFC では別の文字で、NFKC では同じになる。
- 本家は、パスの大文字小文字を区別せず、名前の大文字小文字はできるだけ保つ。ID は大文字小文字を区別する（[HTTP API documentation](https://www.dropbox.com/developers/documentation/http/documentation) の Path formats、2026-10-09 に確認）。本家の Unicode の正規化の扱いは、公式の資料で確かめられなかった（**未検証**）。

名前の比べ方が端末とサーバーで違うと、同じファイルが 2 つに見える、名前の変更が端末の間で往復し続ける、片方が他方を消す。

## Options

ノードの指し方：

1. **ID（UUIDv7）で指し、ノードは親の ID と名前を持つ。パスは引くときに作る**
2. パスを主キーにする
3. ID で指し、パスを各行に写して持つ（子孫の移動で書き換える）

名前の比べ方：

- a. **NFC で持ち、`name_key` = NFC＋Unicode の case folding で一意にする**
- b. バイトのまま比べる（大文字小文字・正規化を区別する）
- c. NFKC＋case folding で比べる（全角と半角も同じにする）
- d. 端末の OS の比べ方に任せる

## Decision

1 と a を採用する。

### ノード

- `nodes(tenant_id, ns_id, node_id, parent_id, name, name_key, is_folder, rev_id, node_ver, deleted_at)`。名前空間の最上位のノードは `parent_id` を持たない。
- `node_id` は UUIDv7 で、全体で一意。名前空間の中の移動・名前の変更で変わらない。名前空間をまたぐ移動でも同じ `node_id` を保ち、元の名前空間の `delete` と、移動先の名前空間の `upsert` として載せる（[ADR-0005](0005-namespace-journal-and-cursors.md)）。クライアントは同じ `node_id` から移動と分かる。
- 中身のリビジョン（`rev_id`）と、置き場所のバージョン（`node_ver`：親・名前・削除の状態が変わるたびに上がる）を分ける。中身の条件と置き場所の条件は別に確かめる（[ADR-0006](0006-sync-conflict-model.md)）。
- 移動と名前の変更は、そのノードの行の `parent_id`・`name`・`name_key`・`node_ver` を変えるだけ。子孫の行を書き換えない。
- パスは、親をたどって作る。API がパスで指されたときは、最上位から `name_key` で 1 段ずつ引く。深さは 256 段までにする。パスの写しを持つ表は作らない（検索の索引は写しとして持つ。search の領域）。

### 名前

- **持つ名前**：受けた名前を NFC に正規化して持つ。大文字小文字は保つ。
- **`name_key`**：NFC に正規化し、Unicode の case folding（完全な畳み込み）をかけ、もう一度 NFC にしたもの。同じ親の中で、削除されていないノードの `name_key` を一意にする（`UNIQUE (ns_id, parent_id, name_key) WHERE deleted_at IS NULL`）。
- 全角と半角、NFKC で同じになる文字は区別する（c を採らない）。macOS と Windows も区別するため。
- 正規化と case folding の表は、固定した Unicode のバージョンで `names_version` に結び付け、Rust（クライアント）と TypeScript（サーバー）で同じ規則にする（[ADR-0001](0001-platform-and-stack.md)）。Unicode のバージョンを上げるときは、`name_key` を作り直し、新しくぶつかる名前を数えて扱いを決める移行の作業にする。
- 大文字小文字だけの名前の変更（`report.xlsx` → `Report.xlsx`）は、同じノードの名前の変更として受ける。
- **サーバーが拒む名前**：空、`.`、`..`、`/` か NUL を含む、制御文字（U+0000〜U+001F、U+007F）を含む、NFC で 255 バイトを超える、不正な UTF-8。
- それ以外は受ける。Windows で使えない文字・予約の名前・末尾の空白とピリオドも、サーバーでは受ける（macOS や Web で作られうるため）。

### クライアントでの名前の対応

- クライアントは、手元の名前（OS が返すバイト列）と、サーバーの名前の対応をローカルの状態の DB に持つ。比べるのは `name_key` だけで、OS や SQLite の照合順序に任せない。
- 手元の名前の NFC がサーバーの名前と同じなら、同じ名前とみなす。正規化の形を合わせるためだけに、手元の名前を変えない（変えると、他のアプリとの間で往復する）。
- サーバーから新しく作るファイルは、NFC の名前で手元に書く。
- **その OS で表せない名前**（Windows の使えない文字・予約の名前・末尾の空白とピリオド、手元のパスの長さの上限を超えるもの）は、手元に作らず、サーバーの名前も変えずに「同期できない名前」として状態の表示に出す。利用者が Web か手元で名前を変えれば同期する。
- 手元で、同じ親に `name_key` が同じ 2 つの名前ができた（大文字小文字を区別するボリューム、NFC と NFD の両方の名前を作るアプリ）ときは、片方だけを同期し、他方を「同期できない名前」として示す。黙って片方を消さない。

### 他の案を選ばなかった理由

- **2（パスを主キー）**：大きなフォルダーの移動で子孫をすべて書き換える。共有リンク・バージョン履歴の結び付きが名前の変更で切れる。
- **3（パスの写し）**：移動の書き込みが子孫の数に比例し、名前空間のロックを長く持つ（[ADR-0005](0005-namespace-journal-and-cursors.md)）。
- **b（バイトで比べる）**：macOS と Windows で同じに見える 2 つのファイルがサーバーにでき、手元で消し合う。
- **c（NFKC）**：OS が区別する全角と半角を同じにし、手元に 2 つあるファイルを同期できなくする。
- **d（OS に任せる）**：端末ごとに比べ方が違い、サーバーの一意と合わない。

## Consequences

- 良くなること：
  - 大きなフォルダーの移動・名前の変更が 1 行の変更で済む。
  - macOS・Windows・Web で、同じ名前の扱いが 1 つの規則になる。
  - 表せない名前があっても、サーバーの名前を勝手に変えず、他の端末に影響しない。
- 引き受けるコスト：
  - パスでの読み出しは、深さの分だけ索引を引く。よく使うパスの解決をキャッシュする（metadata-and-journal の領域）。
  - Unicode のバージョンの更新が、`name_key` の作り直しの移行になる。
  - Windows の利用者には、macOS で作られた名前が「同期できない名前」として残ることがある。

## Confirmation

- 共通の試験のベクトル：名前の集まり（NFC・NFD の日本語、合成済みと分解の混在、大文字小文字の各言語の特殊な例（ドイツ語の ß、トルコ語の I）、全角・半角、Windows の予約の名前、絵文字と結合文字、255 バイトの境界）で、Rust と TypeScript の `name_key` と受け付けの判定が一致する。
- 性質ベーステスト：任意の名前について、`name_key(name_key(x)) = name_key(x)`、`name_key(NFD(x)) = name_key(x)`。
- ファイルシステムの端の場合の試験（[quality.md](../quality.md) の 2.2.1 節 B）：実の macOS（APFS の大文字小文字を区別する・しないボリューム）と Windows（NTFS）で、上の集まりの作成・名前の変更・大文字小文字だけの変更を行い、名前の重複・往復・消し合いが起きない。
- DB の制約：`(ns_id, parent_id, name_key)` の一意の索引があることを、スキーマの検査で確かめる。
