# ADR-0002: ファイルを内容で区切って分割し（最小 1 MiB・平均 4 MiB・最大 16 MiB、`chunker_version` で固定）、ブロックを SHA-256 で番地付けする。ファイルのハッシュはブロックの一覧から作る。最大 2 TiB、大きな一覧は S3 に置く

## Context

ファイルの中身は、ブロックに分けて保存し、送る（[architecture/README.md](../architecture/README.md) の 1.2 節の原則）。分け方は、次のすべてに効く。

- **差分の送信**：大きなファイルの一部を変えたとき、変わったブロックだけを送る（NFR-003）。
- **重複排除**：同じ中身のブロックを、テナントの中で 1 回だけ保存する（[ADR-0003](0003-dedupe-scope-and-privacy.md)）。
- **再開**：途切れたアップロード・ダウンロードを、ブロックの単位で続ける。
- **保存の費用**：S3 のオブジェクトの数と要求の数（[ADR-0007](0007-block-storage-layout-on-s3.md)）。

本家の API の `content_hash` は、ファイルを 4 MB（4,194,304 バイト）の固定のブロックに分け、各ブロックの SHA-256 をつないでさらに SHA-256 を取る（[Content hash](https://docs.dropboxapi.com/dropbox-api/docs/technical-reference/content-hash)、2026-10-09 に確認）。本家の保存の層は、最大 4 MB のブロックを SHA-256 で名付ける（[Inside the Magic Pocket](https://dropbox.tech/infrastructure/inside-the-magic-pocket)、同日に確認）。本家のファイルの上限は 2 TB（[Upload limitations](https://help.dropbox.com/sync/upload-limitations)、同日に確認）。

固定の大きさのブロックは単純だが、ファイルの途中に 1 バイトを挿入すると、その後ろのブロックの境界がすべてずれ、全部が新しいブロックになる。日本のチームの利用者には、動画の編集の素材、CAD・BIM のファイル、仮想のディスク、データベースのファイルなど、途中を書き換える大きなファイルが多い。

## Options

1. **内容で区切る分割（CDC）。ギアのハッシュで境界を探し、最小・平均・最大の大きさを持つ**
2. 固定の 4 MiB（本家の `content_hash` と同じ）
3. 固定の大きさのブロックに、rsync のような回転のチェックサムでの差分を足す
4. ファイルの大きさに応じて固定の大きさを変える（小さいファイルは小さく、大きいファイルは大きく）

## Decision

1 を採用する。

### 分割の規則（`chunker_version` = 1）

- 境界は、ギアのハッシュ（バイトごとに 64 ビットの値を表から引いて、左へずらして足す回転のハッシュ）で探す。最小 1 MiB の位置から探し始め、ハッシュの下位のビットがマスクに一致した位置を境界にする。平均の近く（4 MiB）より前は厳しいマスク、後は緩いマスクを使い、ブロックの大きさを平均に寄せる（正規化した分割）。最大 16 MiB に達したら、そこで切る。
- ギアの表（256 個の 64 ビットの値）は、固定の文字列から SHA-256 で決定的に作り、`chunker_version` の一部として固定する。表と母数（最小・平均・最大・マスク）は、この ADR の範囲で変えない。
- 1 MiB 未満のファイルは 1 つのブロックにする。空のファイルはブロックを持たない。
- 同じ `chunker_version` で、同じ入力から必ず同じ境界が出る。境界は、OS・CPU・ネイティブと WASM で変わらない（共通の試験のベクトルで確かめる）。
- 母数を変えるときは、新しい `chunker_version` を足す。古いバージョンで分けたリビジョンは、そのまま読める。クライアントは、新しく書くファイルだけを新しいバージョンで分ける。
- 母数（1 MiB・4 MiB・16 MiB）は、E2 の前の `chunking-dedupe-poc` で、合成のデータと提供を受けた試験のデータで、重複の率・ブロックの数・分割の速さを測って確かめる。変えるなら、この ADR を直す（最初の設計の間の例外。[process.md](../../../../docs/process.md) の 9 節）。

### 番地とハッシュ

- **ブロックの番地は、平文のブロックの SHA-256（32 バイト）とテナントの組。** S3 がアップロードの時に SHA-256 のチェックサムを計算し直して確かめられる（[Checking object integrity](https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity.html)、2026-10-09 に確認）ので、サーバーの ECS で中身を読まずに番地と中身の一致を確かめられる（[ADR-0007](0007-block-storage-layout-on-s3.md)）。BLAKE3 は速いが、この確かめを S3 に任せられない。
- **リビジョンは 2 つのハッシュを持つ。**
  - `content_sha256`：ファイル全体の SHA-256。分割と関係なく、中身が同じかを比べる値。公開 API にも返す。
  - `blocklist_hash`：`SHA-256("<brand>-blocklist-v1" ‖ chunker_version ‖ 各ブロックの（大きさ（u32、ビッグエンディアン）‖ SHA-256）)`。ブロックの一覧の同一性。
  - クライアントは 1 回の読み出しで、分割、ブロックのハッシュ、全体のハッシュを同時に計算する。
- 本家の `content_hash` と同じ値は出さない。公開 API で互換の値を求められたら、api-and-webhooks の領域で、別の値として足すかを決める。

### ブロックの一覧

- 1,024 ブロック以下（平均で約 4 GiB）の一覧は、リビジョンの行に持つ。
- それを超える一覧は、S3 の `blocklists/` に `blocklist_hash` を番地にして置き、リビジョンの行は番地を持つ（[ADR-0007](0007-block-storage-layout-on-s3.md)）。
- ファイルの上限は 2 TiB（本家と同じ）。最大のブロックの数は、最小の大きさで割って約 210 万。2 TiB のファイルの commit は、アップロードのセッションに検証済みのブロックを貯めてから行う。1 回の commit の要求で、ブロックの一覧の全体を送らない（block-storage の領域）。

### 差分の送信と受信

- ファイルが変わったら、全体を読み直して分割する。ブロックのハッシュが既にあるもの（[ADR-0003](0003-dedupe-scope-and-privacy.md) の規則で「送らなくてよい」と答えられたもの）は送らない。
- 受信では、手元のブロックの索引（ハッシュから手元のファイルと位置）にあるブロックは、手元から写して組み立てる。ないものだけを取る（block-storage の領域）。
- 大きなファイルの読み直しの時間（1 GB/秒の分割とハッシュで、100 GB で約 100 秒）は引き受ける。書き込みの途中のファイルを分けないよう、大きさと更新の時刻が落ち着くのを待つ（sync-engine の領域）。

### 他の案を選ばなかった理由

- **2（固定の 4 MiB）**：途中への挿入・削除で、後ろのブロックがすべて新しくなる。動画の素材や仮想のディスクで、送る量と保存の量が増える。本家の `content_hash` と同じ値を出せる利点は、互換を目標にしない（[intent.md](../intent.md) の Non-goals）ので小さい。
- **3（rsync の差分）**：差分の計算に、送る側と受ける側の両方に古いバージョンの中身が要る。サーバーは中身を読まない（S3 へ直接送る）ので合わない。重複排除にも効かない。
- **4（大きさに応じた固定）**：ブロックの数は抑えられるが、挿入でずれる問題は残る。

## Consequences

- 良くなること：
  - 途中を書き換える大きなファイルで、変わった近くのブロックだけを送り、保存する。
  - 番地と中身の一致を S3 のチェックサムで確かめられ、サーバーが中身を通さない。
  - `content_sha256` で、分割のバージョンをまたいでも中身の同一性を比べられる。
- 引き受けるコスト：
  - 分割の実装と、境界の決定性（ネイティブと WASM で同じ）の試験が要る。
  - ブロックの大きさがそろわないので、ブロックの数とオブジェクトの数の見積もりに幅が出る。
  - 小さなファイルは 1 ファイル 1 ブロックで、S3 のオブジェクトの数が多くなる。パックは S2 の前に決める（[ADR-0007](0007-block-storage-layout-on-s3.md)）。
  - 本家の `content_hash` と互換の値を出さない。

## Confirmation

- 共通の試験のベクトル：決まった入力（乱数のシードから作る 0 バイト〜64 MiB のファイル、挿入・削除・追記を加えたもの）の境界とハッシュを JSON に持ち、Rust のネイティブ（macOS・Windows・Linux の CI）と WASM で一致を確かめる。
- 性質ベーステスト：任意のファイルと、任意の位置への挿入・削除で、変更の位置から離れたブロックの境界とハッシュが変わらない。
- 性質ベーステスト：すべてのブロックが最大の大きさ以下、最後のブロック以外は最小の大きさ以上。ブロックをつなぐと元のファイルになる。
- サーバーの検査：commit で受けたブロックの一覧の各ブロックの大きさが最大以下で、`blocklist_hash` が一覧から計算し直した値と一致することを確かめる。
