# ADR-0052: デスクトップのクライアントは `release` のアカウントで 2 人の承認のもとに OS のコード署名（macOS は公証も）をし、Ed25519 で署名した更新の目録で配る。段階の配布は社内 → 1% → 10% → 50% → 100%（各 48 時間以上）で、品質の基準を外れたら止める。古いバージョンへ戻さず、前のコードを新しい番号で出し直す。サーバーは最低のバージョンより古いクライアントの書き込みを 426 で拒んで読み出しだけにし、モバイルはストアの段階の公開を使う

## Context

- デスクトップのクライアントは常駐し、利用者のファイルを読み書きする。誤ったリリースは、利用者の手元のファイルを消しうる（[quality.md](../quality.md) の 1 節のリスク 1）。端末で起きるので、気づいたときには手元のファイルが既にない。
- 配布の経路が乗っ取られると、全端末へ任意のコードを配れる（[security.md](../architecture/security.md) の 3.9 節）。
- [runbooks/README.md](../runbooks/README.md) の 3 節は、社内 → 1% → 10% → 50% → 100%（各 48 時間以上）、クライアントは古いバージョンへ戻せない前提、サーバーは 2 つ前までのクライアントを受ける、止めたバージョンは AppConfig で同期を止めて読み出しだけにする、と決めた。その仕組みを決める。
- デスクトップの受け取り（6 時間ごと、Ed25519 の目録、`device_id` のハッシュでの段階）は [desktop-client.md](../architecture/desktop-client.md) の 9 節。
- App Store の段階的なリリースは 7 日で 1%〜100% の決まった段で、止めるのは合計 30 日まで（[Release a version update in phases](https://developer.apple.com/help/app-store-connect/update-your-app/release-a-version-update-in-phases)、2026-10-09 に確認）。Play の段階的な公開は割合を選び、止めて再開できる（[Release app updates with staged rollouts](https://support.google.com/googleplay/android-developer/answer/6346149)、同日に確認）。
- 本家は、サポートの外の OS で同期を止めてログアウトさせる（[Dropbox no longer supports my operating system](https://help.dropbox.com/installs/computer-os-not-supported)、同日に確認）。

## Options

署名と配布：

1. **`release` のアカウントの鍵で 2 人の承認のもとに署名し、Ed25519 の目録で配る**
2. CI のジョブが署名の鍵を直接使う
3. OS のストア（Mac App Store、Microsoft Store）だけで配る

不具合の扱い：

- a. **古いバージョンへ戻さず、戻しのリリースと、サーバーでの同期の停止を使う**
- b. クライアントに古いバージョンへの自動の戻しを持たせる

## Decision

1 と a を採用する。

- 成果物は CI でビルドし（SBOM つき）、未署名のまま `release` のアカウントへ置く。2 人の承認で署名のジョブが動き、macOS は Developer ID の署名と Apple の公証、Windows は鍵を書き出せない署名のサービスでコード署名する。その後に、バージョン・OS・アーキテクチャ・割合・URL・SHA-256 の目録を Ed25519 で署名し、`dl.<brand>.<domain>` に置く。
- クライアントは目録の署名、成果物の SHA-256、OS のコード署名を確かめてから入れ替える。
- 段階は社内 → 1% → 10% → 50% → 100%、各 48 時間以上。割合は AppConfig の `client.rollout` から目録を作り直して変える。異常終了の率・端末の健全さ・競合・消しすぎの止め・走査し直しの率が基準を外れたら、割合を 0 にする。
- 古いバージョンへ戻さない。前のコードを新しい番号で出し直す（戻しのリリース）。そのため、ローカルの DB のスキーマの変更は、1 つのリリースの間は広げるだけにする。
- 中身を消す不具合のバージョンは `client.blocked_versions` に入れ、サーバーは commit と `list/continue` を 426 `client_blocked` で拒む。クライアントは同期を止め、手元のファイルを残し、更新を促す。
- `client.min_supported_version` より古いクライアントの書き込みを 426 `client_too_old` で拒み、読み出しだけにする。最低のバージョンは 2 つ前のリリースより新しくしない。上げる 30 日前から更新を促す。OS のサポートの外になった端末も、ログアウトさせずに読み出しだけにする（本家と違う）。
- モバイルは、iOS は App Store の 7 日の段階的なリリース、Android は Play の段階的な公開（1% → 10% → 50% → 100%）を使い、同じ基準で止める。審査の時間が読めないので、深刻な不具合は `client.blocked_versions` を先に使う。

### 他の案を選ばなかった理由

- **2（CI が鍵を使う）**：CI の資格情報や依存が乗っ取られたとき、署名つきの悪意のあるリリースを作れる。
- **3（ストアだけ）**：File Provider・Cloud Files の殻と常駐の形がストアの配布の制約に合うか確かめていない（**未検証**）。段階の割合と止め方を本システムで決められない。企業の端末の配布（MDM）にも合わない。
- **b（自動の戻し）**：ローカルの状態の DB と手元のファイルの状態が新しいバージョンで進んでおり、古いバージョンが読み違えると、手元のファイルを消しうる。

## Consequences

- 良くなること：
  - 署名の鍵が CI と本番の作業の権限から離れる。
  - 不具合のバージョンの影響を、段階で 1% に止め、サーバー側で同期を止められる。
  - 古いクライアントが新しいサーバーと食い違って書き込むことを防げる。
- 引き受けるコスト：
  - リリースのたびに 2 人の承認が要る。
  - 戻しのリリースは、配布の全段をもう一度通る（ホットフィックスの扱いで社内の段を縮める）。
  - iOS の段階の割合は Apple の決まった段になる。

## Confirmation

- 結合テスト：署名の検査に失敗した目録・成果物を、クライアントが入れ替えない。
- 結合テスト：`client.blocked_versions` と `client.min_supported_version` で、該当の `<Brand>-Client` の commit が 426 になり、読み出しは通る。
- 段階の配布の訓練（staging の合成監視の端末）：割合 0 で新しい端末に配られないこと、戻しのリリースが壊れたリリースの DB を読めること。
- Terraform の検査：CI のロールが `release` のアカウントの署名の鍵を使えない。
