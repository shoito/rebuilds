# ADR-0048: 大阪のウォームスタンバイへ人の判断で切り替え、書き込みを止めてから昇格し、`epoch` を上げる。切り替えの前 60 分に確定したリビジョンのブロックを大阪で確かめ、欠けたものを「中身の待ち」にして、持つ端末に送り直しを求める。戻すときは計画の switchover で、`epoch` を上げない

## Context

- NFR-005：リージョンの障害で、メタデータ RPO 1 分・RTO 1 時間、中身 RPO 15 分。欠けたブロックは、まだ持つ端末から送り直しを求める（[architecture/README.md](../architecture/README.md) の 3 節）。
- メタデータは Aurora Global Database、中身は S3 の CRR（Replication Time Control、15 分を目標）で大阪へ写す（[ADR-0007](0007-block-storage-layout-on-s3.md)）。2 つの写しは独立に遅れ、大阪のメタデータが大阪にまだないブロックを指しうる。
- Global Database の計画外のフェイルオーバーは、複製の遅れの分の commit を失いうる。失った番号は大阪で別の操作に振り直される。カーソルは `epoch` を持ち、DR の切り替えで上げると決めている（[ADR-0005](0005-namespace-journal-and-cursors.md)）。
- 端末は手元のファイルとそのハッシュを持つ。Synced の木があるので、木を読み直しても手元の変更を失わない（[ADR-0006](0006-sync-conflict-model.md)）。
- 他の題材（Google Calendar の ADR-0044）は、人の判断の切り替え、書き込みの停止、`sync_epoch` の更新を決めた。

## Options

1. **人の判断で切り替え、`epoch` を上げ、切り替えの前 60 分のブロックを確かめて、欠けたものを中身の待ちにして端末に送り直しを求める**
2. 自動で切り替える
3. 中身の CRR が追いつくまで切り替えを待つ
4. 中身の確かめをせず、読めないブロックは読み出しの時に見つける

## Decision

1 を採用する。

- 切り替えは IC と Ops の責任者が決める。ワークフローは、東京の入口と `ops.writes_enabled`・`ops.uploads_enabled` を止め、Aurora を大阪で昇格させ、`epoch` を上げて `dr_failover_at` を記録し、`dr-content-check` を始め、大阪のサービスを広げ、CloudFront のオリジンを切り替え、書き込みを開く。
- 古い `epoch` のカーソルはすべて 409 `reset`（ADR-0005 のとおり）。端末は木を読み直して Synced と比べる。
- `dr-content-check` は、`dr_failover_at` の前 60 分（RTC の目標の 4 倍）に確定したリビジョンのブロックを、大阪の `blocks` で確かめる。欠けたものを `content_pending_blocks` に入れ、リビジョンを `content_state = pending` にする。
- `pending` のリビジョンのダウンロードは 503 `content_pending`。読み直しの応答で印を付け、手元のファイルのハッシュが合う端末が欠けたブロックを通常のアップロードで送る。そろえば `ready` に戻す。
- 東京が戻れば、東京から残りを写す。どこにもない中身は `lost` にし、前のリビジョンを残して持ち主に知らせ、数を報告する。
- `content` の CloudFront は `/b/*` に大阪の写しを第 2 のオリジンとして持つ（組み合わせの可否は E1 で確かめる）。
- 戻すときは Aurora の switchover（RPO 0）で、`epoch` を上げない。大阪で受けたブロックは、平常から設定した大阪 → 東京の CRR で写る。
- outbox は大阪で未送信の行から流し直し、受け手の冪等で重複を吸う。

### 他の案を選ばなかった理由

- **2（自動）**：東京の一時の不調で切り替えると、失う commit と `epoch` の取り直しの費用（全端末の木の読み直し）が大きい。判断は人がする。
- **3（CRR を待つ）**：東京の S3 が読めないリージョンの障害では、待っても追いつかない。RTO 1 時間を守れない。
- **4（読み出しで見つける）**：端末は「サーバーに確定した」と思い、手元のファイルを送り直さない。誰かが開くまで欠けに気づかず、その間に端末が手元を消す（[ADR-0006](0006-sync-conflict-model.md) の受信の置き換え）と中身を失う。

## Consequences

- 良くなること：
  - 中身の欠けを切り替えの直後に数え、まだ持つ端末から埋められる。
  - 失う中身を、どの端末も持たないものだけに絞り、数を報告できる。
- 引き受けるコスト：
  - `epoch` の更新で、全端末が木を読み直す（[capacity.md](../architecture/capacity.md) の 3.3 節）。
  - 60 分の窓の外で CRR が遅れていたブロックは、毎週の照合まで見つからない。CRR の遅れが 15 分を超えたら呼び出すことで、窓の外の遅れを防ぐ。
  - 双方向の CRR と、オリジンのフェイルオーバーの組み合わせの確かめが要る。

## Confirmation

- DR の訓練（staging、四半期）：CRR を止めた状態で切り替え、`pending` の数が止めた間のブロックと一致し、合成監視の端末からの送り直しで `ready` に戻り、メタデータ RPO 1 分・RTO 1 時間を満たす。
- 性質ベーステスト（模型）：任意の CRR の遅れと切り替えの時刻で、切り替えの前 60 分のブロックのうち大阪にないものが、すべて `pending` になる。
- 結合テスト：`pending` のリビジョンのダウンロードが 503 `content_pending` を返し、署名つき URL を出さない。
