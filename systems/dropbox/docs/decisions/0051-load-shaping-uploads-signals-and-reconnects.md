# ADR-0051: 負荷の集中を 4 つの仕組みでならす。アップロードの署名つき URL の発行をテナントと全体のトークンバケットで絞り、`background` の優先度を先に待たせる。合図は端末と名前空間の組ごとに 1〜3 秒の窓でまとめ、購読の多い名前空間はジャーナルの末尾を Valkey に持つ。再接続は端末が乱数で散らし、`notify` は 1 タスク 1 秒 500 の接続まで受ける。取り直しはサーバーが端末ごとの待ちの時間を割り当てる

## Context

- S1 のピークは commit 5,000 件/秒、送信 2 GB/秒、配信 4 GB/秒（[architecture/README.md](../architecture/README.md) の 2 節）。負荷は平日の業務の時間、月曜の朝、夜のカメラのアップロード、行事の後に集まる（[capacity.md](../architecture/capacity.md) の 1.2 節）。
- 合図は名前空間ごとで、載せたすべての端末に届く（[ADR-0005](0005-namespace-journal-and-cursors.md)）。最大のチームでは、1 つのチームのフォルダーを 4.5 万の端末が載せる。1 秒 10 件の commit が続くと、まとめなければ 1 秒 45 万の `list/continue` になる。
- `notify` の停止・デプロイ・AZ の喪失で、数万〜20 万の端末が一斉に戻る。DR の `epoch` の更新では 40 万台が木を読み直す（[ADR-0048](0048-disaster-recovery-and-content-pending.md)）。
- カメラのアップロード（元日の 0 時など）は、送信のピークの 60% に達しうる。デスクトップの同期の遅れ（NFR-002）を押しのけたくない。
- S3 は接頭辞ごとの要求の上限を、負荷に合わせて徐々に広げ、その間は 503 を返す（[optimizing Amazon S3 performance](https://docs.aws.amazon.com/AmazonS3/latest/userguide/optimizing-performance.html)、2026-10-09 に確認）。
- 名前空間の中のファイルごとの権限を持たない（[ADR-0004](0004-tenancy-namespaces-and-rls.md)）。同じ名前空間のジャーナルの行は、読めるどの端末にも同じである。

## Options

1. **発行の絞り（優先度つき）、窓でまとめる合図と末尾のキャッシュ、端末の乱数の再接続と受け入れの上限、サーバーの割り当ての取り直しを組み合わせる**
2. 台数を最大の集中に合わせて常に持つ
3. 合図に変更の中身を入れ、`list/continue` を省く

## Decision

1 を採用する。

### アップロードの受け入れ

- 署名つきの PUT の URL の発行を、全体（既定 2.5 GB/秒）とテナント（個人 100 MB/秒、チーム 1 GB/秒）のトークンバケットで絞る。値は `ops.upload_admission_global_bps`・`ops.upload_admission_tenant_bps`。
- アップロードに `priority`（`interactive`：デスクトップの同期と Web、`background`：カメラのアップロード・公開 API の一括・復元の写し）を持たせる。全体のバケットが 80% を超えるか、`block-verifier` の最古が 30 秒を超えるか、S3 の 503 の率が 1% を超えたら、`background` に 429 と `Retry-After` を先に返す。

### 合図

- `notify` は合図に `seq` を入れ、端末と名前空間の組ごとに窓の間の合図を最後の 1 つにまとめる。窓は購読の端末 1,000 以下で 1 秒、1 万以上で 3 秒。端末ごとに窓の中の乱数の位置で送る。
- 購読が 1,000 を超える名前空間は、`api` がジャーナルの末尾（最大 1 万行）を Valkey に持ち、`list/continue` はそこから読んで、端末ごとに `can()` と載せた場所のパスへの直しだけを行う。
- `list/continue` は、カーソルの位置を Valkey の `ns_head` と比べ、変わっていなければ DB を読まずに返す。

### 再接続

- 端末は、サーバーが切った（`reconnect`）ときは 0〜30 秒、失敗のときは 0〜60 秒の乱数で待ち、失敗が続けば指数の後退（最大 5 分）。
- `notify` は 1 タスク 1 秒 500 の新しい接続まで受け、超えたら 503 と `Retry-After`。

### 取り直し

- `reset` の応答に `retry_after` を付け、端末の ID のハッシュで窓（DR の後は 2 時間、平常は 10 分）に散らす。木の一覧は reader の専用のエンドポイントで読む。

### 他の案を選ばなかった理由

- **2（最大に合わせて持つ）**：最大の集中（DR の後の取り直し、元日のカメラ）は年に数回で、常に持つ費用に見合わない。端末の側が散らなければ、台数を足しても最初の数秒の山を受けきれない。
- **3（合図に中身）**：合図の経路（Valkey、WebSocket）に名前と中身が乗り、権限の確かめが `notify` に要る。合図が落ちたときの取り戻しはカーソルのままなので、仕組みが 2 つになる（[ADR-0005](0005-namespace-journal-and-cursors.md)）。

## Consequences

- 良くなること：
  - 購読の多い名前空間の負荷が、端末の数ではなく窓と末尾のキャッシュで決まる。
  - カメラの集中がデスクトップの同期を押しのけない。
  - 再接続と取り直しの山が、端末とサーバーの両方で散る。
- 引き受けるコスト：
  - 購読の多い名前空間では、伝播が最大 3 秒遅れる（NFR-002 の中に収める）。
  - DR の後、全端末の読み直しに最大 2 時間（その間も手元のファイルは使える）。
  - `background` のアップロードは、集中の間に遅れる。

## Confirmation

- 負荷試験（[capacity.md](../architecture/capacity.md) の 8 節）：4.5 万端末の名前空間で伝播の p99 5 秒、20 万の再接続の後 10 分で伝播が戻る、カメラの集中の間に `interactive` の commit の p99 が変わらない。
- 性質ベーステスト：任意の合図の欠け・重複・まとめの列で、端末の木が、合図なしで 60 秒ごとに確かめた場合と同じ木に収束する。
- 結合テスト：末尾のキャッシュから返した `list/continue` が、DB から返したものと同じ（権限とパスの直しを含む）。
