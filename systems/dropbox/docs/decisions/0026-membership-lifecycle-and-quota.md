# ADR-0026: 自分で抜けるときと、外されるときを分ける。外されたら、まず読めなくし、その後に、持ち主が許した場合だけ外した時点の写しを外された人のルートへ作る。容量は名前空間の持ち主のテナントだけに論理の大きさで数え、メンバーには数えない。持ち主の移し替えは同じテナントの中だけで、テナントをまたぐ移し替えは写しで行う

## Context

共有フォルダーから抜ける・外されるとき、そのメンバーの端末の手元のファイルと、サーバーの中身をどう扱うかを決める必要がある。[ADR-0005](0005-namespace-journal-and-cursors.md) は、外されたらまず `ns_access` を消して読めなくし、次に `unmount` を書くと決め、手元の扱い（変えていないファイルは消し、変えたファイルは残す）を sync-engine の領域に預けた。[ADR-0006](0006-sync-conflict-model.md) の行 12 は、書けなくなった手元の変更を「`<Brand>` に保存できなかった変更」へ移す。

決めることは次である。

- 外された人に中身の写しを残すか。誰が決めるか。いつ作るか。
- 容量を誰に数えるか。本家の数え方は公式の資料で確かめられなかった（**未検証**。[intent.md](../intent.md)）。
- 持ち主を、別のテナントの人に移せるか。名前空間の持ち主のテナントは、RLS の `tenant_id` とブロックの S3 のキーに入っている（[ADR-0004](0004-tenancy-namespaces-and-rls.md)、[ADR-0007](0007-block-storage-layout-on-s3.md)）。

## Options

写し：

1. **抜けるときは本人が選び、外されるときは持ち主が許したときだけ。読めなくした後に、外した時点の写しを作る**
2. 常に写しを残す
3. 写しを残さない

容量：

- a. **名前空間の持ち主のテナントだけに数える**
- b. 載せたメンバー全員に数える
- c. 書いた人に数える

持ち主の移し替え：

- x. **同じテナントの中だけ。テナントをまたぐのは写し**
- y. テナントをまたいで移し、行とブロックの `tenant_id` を書き換える

## Decision

1、a、x を採用する。詳細は [namespaces-and-sharing.md](../architecture/namespaces-and-sharing.md) の 7〜9 節。

- 抜ける（`leave`）：本人が「写しを残す」を選び、チームの方針 `allow_keep_copy`（既定 持てない。個人の名前空間は常に可）が許すとき写しを作る。
- 外す（`remove_member`）・共有の解除：持ち主が「写しを残すことを許す」（既定 なし）を選び、方針が許すときだけ写しを作る。方針で無効にしたときは作らない。
- 順序：付与を消す → `access_version` を上げる → `unmount` → 写しの作業。写しは外した時点の `ns_seq` の木を、名前空間をまたぐコピーのバッチで作り、写し先の容量に数える。許した人を監査ログに残す。
- 容量は、名前空間の持ち主のテナントに、削除していないファイルの今のリビジョンの大きさの和で数える。バージョン履歴と削除したファイルは数えない。`packages/committer` が名前空間の `logical_bytes` を差分で直し、Worker が 1 分ごとにテナントの和を出す。commit は上限 + 余裕（min(1 GiB, 1%)）で、大きさを増やす操作を 507 で拒む。
- 名前空間の持ち主のテナントは変えない。`transfer_owner` は同じテナントの `editor` へだけ。テナントをまたぐのは、新しい名前空間への写しと付け直しで行う。

### 他の案を選ばなかった理由

- **2（常に写し）**：会社の共有フォルダーから外した社外の人が、中身の写しを持ち続ける。外す理由の多くと合わない。
- **3（写しなし）**：個人どうしの共有で、抜けた人が自分の書いたファイルまで失う。
- **b（全員に数える）**：1 万人のグループに付与すると 1 万のテナントの容量が動き、容量の変化から他人の共有フォルダーの大きさが分かる。書き込みごとに数を配る増幅も起きる。
- **c（書いた人）**：同じ名前空間の容量が人ごとに割れ、移動・削除・別の人の上書きで、誰の容量を減らすかが決まらない。
- **y（テナントの書き換え）**：数百万行と S3 のキーを書き換える。途中の状態で RLS と重複排除の守りが崩れる。

## Consequences

- 良くなること：
  - 外す人が写しを制御でき、外すことの意味（中身を渡さない）を守れる。
  - 容量の数え方が名前空間ごとに 1 つで、メンバーの数に比例しない。
  - 名前空間のテナントが一生変わらず、RLS と S3 のキーが安定する。
- 引き受けるコスト：
  - 無料の利用者が、他人の大きな共有フォルダーに容量を使わずに書ける（持ち主の容量で止まる）。
  - 写しの作業は大きなフォルダーで数分かかり、その間、外された人の手元は空きうる。
  - 個人の共有フォルダーは持ち主を移せない。
