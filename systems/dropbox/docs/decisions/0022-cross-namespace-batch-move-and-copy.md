# ADR-0022: 名前空間をまたぐ移動とコピーは、バッチの操作にする。移動先の名前空間の隠した入れ物に 2,000 ノードずつ写し、最後に 1 つのトランザクションで、移動先へ出す（子孫の一覧を読ませる印つき）と、元の削除（`moved_to` つき）を書く。移動の間、元の部分木への書き込みを 409 `subtree_locked` で待たせる。写した行のジャーナルは利用者に返さない

## Context

名前空間の中の移動は 1 行の変更で済む（[ADR-0008](0008-node-identity-and-names.md)）。名前空間をまたぐ移動（自分のフォルダーから共有フォルダーへ）は、移動先の名前空間に子孫のすべての行が要り、2 つの名前空間の書き込みになる（[ADR-0004](0004-tenancy-namespaces-and-rls.md)）。[ADR-0008](0008-node-identity-and-names.md) は、同じ `node_id` を保ち、元の `delete` と移動先の `upsert` として載せると決めた。[architecture/README.md](../architecture/README.md) の 6 節は、10 万ファイルの移動をバッチの非同期の操作にし、途中の状態を端末に見せない形をこの領域に残した。

条件：

- 1 回の commit は 1,000 操作まで。名前空間の行のロックを長く持たない（[ADR-0005](0005-namespace-journal-and-cursors.md)）。
- テナントをまたぐと、ブロックを移動先のテナントへ写す（[ADR-0003](0003-dedupe-scope-and-privacy.md) の表の 2、[ADR-0004](0004-tenancy-namespaces-and-rls.md) の X1）。
- 本家の内部の手順は公開されていない（**未検証**）。

## Options

1. **隠した入れ物に写し、最後に 1 回で出す。元の部分木を lock する**
2. 1,000 ずつ普通の commit で移動先に作り、元から消す（途中が見える）
3. 隠した入れ物に写し、元を lock せず、出す前に差分を追いかける
4. 名前空間をまたぐ移動を許さず、コピーと削除を利用者に任せる

## Decision

1 を採用する。詳細は [metadata-and-journal.md](../architecture/metadata-and-journal.md) の 6 節。

- 状態：`accepted` → `copying` →（テナントが違えば `blocks_pending`）→ `revealing` → `purging` → `done`。中止は `aborting` → `aborted`。
- 写すときは、移動先の名前空間の、`hidden_batch_id` を持つ隠した入れ物の下に、同じ `node_id` で 2,000 ノードずつ書く。保持の期間の中のリビジョンも写す。ジャーナルには `batch_id` つきの行を書き、利用者に返さない。
- 出すときは、2 つの名前空間の行を `ns_id` の順にロックし、移動先に根の `upsert`（`subtree_listing`、`moved_from_ns`）、元に根の `delete`（`deleted_reason = moved`、`moved_to_ns`、`moved_to_seq`）を書く。名前がふさがっていれば ` 2` を足す。
- 移動の間、元の部分木への commit は 409 `subtree_locked`（`Retry-After`）。30 分を超えたら中止する。
- 後始末で元の子孫の行とリビジョンを消し、`batch_id` つきの `purge` を書く。
- コピーは新しい `node_id` で、`snapshot_seq` の時点の木（`node_versions`）から写す。元を lock しない。
- クライアントは、`moved_to` つきの削除を受けたら移動先を `moved_to_seq` まで読むまで手元の削除を保留し、同じ `node_id` なら手元の移動にする（[sync-engine.md](../architecture/sync-engine.md) の 9.2 節）。

### 他の案を選ばなかった理由

- **2（途中が見える）**：他の端末が半分だけの木を受け、元と先の両方に同じファイルが見える。途中で失敗すると、半分の状態が残る。
- **3（差分を追いかける）**：待たせないが、元の部分木の変化を先へ写し直す処理と、その終わらない場合の扱いが要る。MVP では、移動の時間（10 万ファイルで約 8 分）の待ちを引き受ける。
- **4（許さない）**：共有フォルダーへの整理は主な使い方で、バージョン履歴と共有リンクが切れる。

## Consequences

- 良くなること：
  - 途中の状態が、どの端末・一覧・差分にも見えない。
  - 同じ `node_id` なので、両方を載せた端末では手元の移動だけで済み、中身を取り直さない。
  - バージョン履歴がファイルに付いていく。
- 引き受けるコスト：
  - 移動の間、元の部分木への保存が待たされる。
  - 移動先にリビジョンとブロックの参照を写す分、書き込みが増える。テナントをまたぐとブロックの写しで数分かかる。
  - ジャーナルの行の種類（利用者に返さない行）と、`subtree_listing` の読み方が増える。

## Confirmation

- 性質ベーステスト：PROP-META-005（どの段でも途中の行が見えない。移動の後、先の部分木が元と同じ形と中身）、PROP-META-001（差分と全件の一致。移動とコピーを含む）。
- 表駆動テスト：DT-META-003（中止の遷移）。
- 負荷試験：10 万ファイルの移動（同じテナント、違うテナント）で p95 10 分。
- シミュレーター：名前空間をまたぐ移動を生成器に入れ、両方を載せた端末で中身の取り直しが起きないことを数える。
