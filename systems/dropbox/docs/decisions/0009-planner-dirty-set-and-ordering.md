# ADR-0009: 計画は、汚れたノードだけを Synced と比べて変化を分類し、決定表で操作を決め、依存のグラフで並べる。1 回の計画は 3 つの木の 1 つの読み取りの写しに対して決定的で、出した操作の結果を確かめてから木を進める

## Context

[ADR-0006](0006-sync-conflict-model.md) は、3 つの木（Remote・Local・Synced）と 13 行の衝突の決定表を決めた。計画の手順（何を比べ、どの順に操作を出すか）は sync-engine の領域に残した。

条件は次のとおり。

- 100 万ファイルの端末で、静かなときの CPU 1% 未満・メモリー 300 MB 以下（NFR-008）。木の全体を毎回比べられない。
- サーバーの変化から計画まで短く（NFR-002）。
- 操作の間に依存がある。親を作ってから子、名前を空けてから使う、名前の入れ替え、子を外へ出してから親を消す。
- 決定的な同期のシミュレーターで、同じシードから同じ記録を出す（[quality.md](../quality.md) の 2.2.1 節 A）。
- 本家は 3 つの木を持つが、計画の規則は公開していない（[Testing our new sync engine](https://dropbox.tech/infrastructure/-testing-our-new-sync-engine)、2026-10-09 に確認。規則は**未検証**）。

## Options

1. **汚れたノードだけを分類し、決定表で操作を決め、依存のグラフで並べる**
2. 毎回、3 つの木の全体を比べる
3. OS のイベントを順に当てる（イベントの再生）。木の比べはしない
4. 操作を 1 つずつ出し、結果を見てから次を決める（グラフを作らない）

## Decision

1 を採用する。詳細は [sync-engine.md](../architecture/sync-engine.md) の 6 節。

- Remote・Local の更新で、変わったノードに `dirty` を付ける。計画は `node_key` の順に最大 50,000 件を取る。
- 各ノードの変化を、Synced との差で `none`・`create`・`content`・`place`・`content+place`・`delete` に分ける。中身の変化は `content_sha256` で決め、時刻は「ハッシュを取り直す」の手がかりにだけ使う。
- 決定表の結果を、条件つきの操作（`create`・`update`・`move`・`delete`・`undelete`）と手元の操作に直す。
- 依存の規則 O1〜O8（親が先、名前を空けるのが先、入れ替えは 1 つの commit、外へ出すのが先、手元の削除は子から、競合のコピーへの移動が先、ブロックの送信が先、名前空間をまたぐ移動は単独）で辺を張り、トポロジカルの順に並べる。同じ順位は `node_key` の順。
- 解けない循環が残ったら、成分の最小の `node_key` を仮の名前へ移す操作だけを出し、次の計画に回す。
- 計画は SQLite の 1 つの読み取りのトランザクションの写しの上で行い、同じ入力から同じ操作の列を出す。Synced は、操作の結果を確かめてから進める。
- サーバーへの操作は名前空間ごとに commit にまとめる（既定 100、最大 1,000）。1 つの名前空間の commit は 1 本ずつ送る。
- ファイルの `delete` に `base_rev` を、フォルダーの `delete` に `base_seq` を条件として付ける。削除の後に確定した中身の変更や子孫の変更を、削除が黙って巻き込まないため（[metadata-and-journal.md](../architecture/metadata-and-journal.md) の 4.2 節）。

### 他の案を選ばなかった理由

- **2（全体の比べ）**：100 万ノードの比べは 1 回で数秒の CPU と数百 MB を使い、NFR-008 に収まらない。走査し直しのときだけ全体を汚す形で、同じ手順に含められる。
- **3（イベントの再生）**：イベントは溢れ、順序が入れ替わり、移動が削除と作成に分かれる。Synced を見ない判断になる（[ADR-0006](0006-sync-conflict-model.md) が退けた形）。
- **4（1 つずつ）**：名前の入れ替えや親子の順を表せない。往復を起こしやすい。

## Consequences

- 良くなること：
  - 計画の量が変化の量に比例し、静かなときは計画を回さない。
  - 順序の規則が表になり、シミュレーターで行ごとの到達を測れる。
  - 計画の決定性で、失敗のシードを縮めて再現できる。
- 引き受けるコスト：
  - `dirty` の付け忘れが、変化の見落としになる。走査し直しと、夜間のシミュレーターの「全体を汚した計画と結果が同じ」の性質で守る。
  - ファイルの削除が `base_rev` を求めるので、他の端末の中身の変更の直後の削除は 409 になり、計画し直しが増える。

## Confirmation

- 表駆動テスト：DT-SYNC-001（決定表の 13 行と前段の 2 行）。
- 性質ベーステスト：PROP-SYNC-004（止まる）、PROP-SYNC-005（決定性。汚れの取り出しの順を変えても同じ操作の列）。夜間に「全体を汚した計画」と「汚れたノードだけの計画」の結果の一致。
- シミュレーター：O1〜O8 の各規則と循環の解きに届いた回数を記録し、0 回なら生成器を直す。
