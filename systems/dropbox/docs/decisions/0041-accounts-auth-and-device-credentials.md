# ADR-0041: 認証の部品に Better Auth を使い、`packages/auth` で包む。ログインはパスキー・メールのコード・Google・Apple・チームの SSO で、パスワードを持たない。1 つのアカウントは 1 つのテナントに属する。デスクトップとモバイルは認可コード＋PKCE で端末を登録し、端末の鍵に結んだ回転する更新トークンを持つ。停止と切り離しを 60 秒以内に効かせ、危ない操作は 10 分以内の再認証を求める

## Context

- 利用者は、Web・デスクトップ（macOS・Windows）・モバイル（iOS・Android）・公開 API から使う（[intent.md](../intent.md)）。デスクトップとモバイルは常駐し、数か月ログインし直さずに同期を続ける。
- デスクトップは利用者の PC のファイルを読み書きする。端末の資格情報が盗まれると、同期の経路から全ファイルを読まれ、消される。乗っ取りからの一括の削除は、この題材の主なリスクの 1 つである（[security.md](../architecture/security.md) の 3.3 節）。
- 端末を切り離したら、その端末の同期をすぐ止め、選べば手元の中身を消す必要がある（本家の遠隔の消去。[accounts-and-teams.md](../architecture/accounts-and-teams.md) の 3 節）。
- テナントは個人とチームで、名前空間を持ち主のテナントに置く（[ADR-0004](0004-tenancy-namespaces-and-rls.md)）。アカウントとセッションと端末は RLS の外の表にする（同 ADR の一覧）。
- 他の題材（Google Calendar の ADR-0035）は Better Auth を `packages/auth` で包み、パスワードを持たない形にした。
- iOS のアプリで他社のログイン（Google）を出すなら、名前とメールアドレスだけを集め、メールアドレスを隠せるログインを同等の選択肢として出す必要がある（[App Store Review Guidelines](https://developer.apple.com/app-store/review/guidelines/) の 4.8、2026-10-09 に確認）。

## Options

認証の部品：

1. **Better Auth を `packages/auth` で包む（他の題材と同じ）**
2. マネージドの認証のサービス（Amazon Cognito など）
3. 自前で書く

端末の資格情報：

- a. **OAuth 2.0 の認可コード＋PKCE で登録し、端末の鍵に結んだ回転する更新トークンと 1 時間のアクセストークン**
- b. 長い期限のアクセストークン 1 つ
- c. Web と同じクッキーのセッションを端末にも持たせる

## Decision

1 と a を採用する。

### ログイン

- 手段はパスキー（推す）、メールのコード（6 桁・10 分）、Google、Apple、チームの SSO（[ADR-0042](0042-teams-sso-scim-and-plans.md)）。パスワードを持たない。
- 外部のアカウントは `email_verified` が真のときだけ既存のアカウントに結ぶ。Apple の中継のメールアドレスは、そのまま主のメールアドレスにする。
- 新しい端末・新しい場所のログインは、本人にメールで知らせる。

### アカウントとテナント

- 1 つのアカウントは 1 つのテナント（個人のテナントかチーム）に属する。チームへの参加は、別のアカウントを持つこと（[ADR-0042](0042-teams-sso-scim-and-plans.md)）。
- アカウント、メールアドレスの解決、Web のセッション、端末、端末の資格情報は RLS の外の `auth` スキーマに置く。ファイルの名前・パス・中身の列を持たせない（[ADR-0004](0004-tenancy-namespaces-and-rls.md)）。

### Web のセッション

- HttpOnly・`Secure`・`SameSite=Lax` のクッキーを `www`・`api` の親のドメインに付ける。`<brand>usercontent.<domain>` には付かない。使わないまま 30 日で切れる。チームは 1〜30 日に絞れる。

### 端末の資格情報

| 項目 | 決定 |
| --- | --- |
| 登録 | 認可コード＋PKCE（S256）。デスクトップは 127.0.0.1 のループバック（RFC 8252）、モバイルは OS の認証のシートとアプリに結んだ `https` の戻り先 |
| 端末の鍵 | 登録で Ed25519 の鍵の組を作り、秘密鍵を OS の鍵の保管庫（キーチェーン、DPAPI、Android Keystore）に置く。公開鍵を `devices` に持つ |
| アクセストークン | `<brand>_at_`、不透明、1 時間。SHA-256 だけを保存 |
| 更新トークン | `<brand>_rt_`、不透明、使うたびに入れ替える。更新の要求に端末の鍵の署名を求める。古いものの再使用でその端末の資格情報をすべて取り消す。90 日使わなければ切れる |
| チームの方針 | 端末の最長の期間 1〜180 日。過ぎたら SSO で入り直すまで同期を止める |
| 端末の数 | 無料のプランは 3 台 |

- トークンの接頭辞は、他の既知のサービスと重ならないことを確かめ、シークレットスキャンに登録する（[リポジトリ共通の ADR-0006](../../../../docs/decisions/0006-brand-neutral-identifiers.md)）。公開 API の OAuth のアプリのトークン（[ADR-0039](0039-oauth-apps-scopes-and-rate-limits.md)）と同じ接頭辞・形・保存のしかたにし、期限（アプリは 4 時間、端末は 1 時間）だけを分ける。

### 取り消し

- 取り消しは `auth_epoch` を上げるか行を無効にし、Valkey の取り消しの一覧に 30 日置き、pub/sub で合図する。サービスはトークンの検証の結果を最大 30 秒だけ持ち、合図で捨てる。Notify は 5 秒以内に WebSocket を切る。停止から 60 秒以内に、どの経路でも効かなくする。
- Valkey が使えないときは DB を引く。取り消しが効かない状態を作らない。

### 危ない操作の再認証

- 資格情報の変更、他の端末の切り離しと消去、1,000 を超えるノードの一括の削除（Web・API）、保持の期間の前の完全な削除、アカウント全体の巻き戻し、全体の書き出し、全体のスコープのアプリの許可、Webhook の作成、チームの SSO・SCIM・役割・共有の方針を緩める変更は、10 分以内の認証（`recent_auth`）を求める。SSO のチームは IdP で認証し直す。
- 対象の操作は決定表として spec に書き、`packages/auth` の `requireRecentAuth()` だけで判定する。

### 他の案を選ばなかった理由

- **2（Cognito など）**：他の題材と道具がずれる。端末の鍵に結んだ更新トークン、`auth_epoch` での一括の取り消しを、マネージドのサービスの外で組み直すことになる。
- **3（自前）**：WebAuthn、OIDC、SAML を自前で書くと、検証の量が題材の核に見合わない。
- **b（長い期限のトークン 1 つ）**：盗まれたときに気づけず、使われ続ける。取り消しの確かめのたびに DB を引くことになる。
- **c（クッキー）**：OS のネイティブのクライアントで、クッキーの保管と CSRF の対策が要り、端末ごとの切り離しと消去の手がかりにならない。

## Consequences

- 良くなること：
  - パスワードを持たず、漏えいと総当たりの対象が減る。
  - 端末ごとに切り離せ、盗まれた更新トークンの再使用を見つけられる。
  - 切り離した端末にも、端末の鍵で消去の指示を安全に渡せる（[ADR-0043](0043-admin-roles-device-wipe-and-member-access.md)）。
- 引き受けるコスト：
  - Better Auth の脆弱性の告知を追い、使う部品だけを依存に入れる。
  - 端末の鍵の保管庫は OS ごとに作り分ける。鍵を失った端末（OS の入れ直し）は登録し直す。
  - 1 アカウント 1 テナントなので、個人とチームの両方を使う人は 2 つのアカウントを持つ。

## Confirmation

- 性質ベーステスト：任意の停止・切り離し・方針の変更の列で、模型の時計で 60 秒を過ぎた後、取り消した主体と端末の要求がどの経路でも通らない。
- 性質ベーステスト：更新トークンの再使用で、その端末のすべての資格情報が無効になる。
- 決定表の表駆動テスト：再認証の対象の操作の全行。
- lint：`packages/auth` の外で、トークンの検証と `recent_auth` の判定を書くコードを禁止する。
- シークレットスキャン：ログ・トレースに `<brand>_at_`・`<brand>_rt_` の形が現れたら呼び出す（[observability.md](../architecture/observability.md) の 2.1 節）。
