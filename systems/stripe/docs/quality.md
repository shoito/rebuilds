# Quality: Stripe

QA が持つ品質戦略。変更ごとのテスト設計は、各変更の `spec.md`（シナリオ・決定表・性質）と `plan.md`（Proof）に書く。

決済の基盤では、壊れたときに「エラーにならずにお金が違う」ことが最も危ない。QA の仕事は、Slack と同じく次の 3 つだが、重心は **お金の不変条件を先に決め、性質と照合で確かめ続けること** に置く。

1. **何をもって正しいとするかを先に決める**（シフトレフト：お金の不変条件、冪等、状態遷移の決定表）
2. **エージェントが自分で検証できる仕組みを整える**（性質ベーステスト、障害注入、確認ループ、eval）
3. **本番で正しさを確かめ続ける**（照合、台帳の検査、PAN の走査、合成監視）

## 1. 品質目標とリスク

| --- | --- | --- | --- |

## 2. シフトレフト

### 2.1 仕様レビューの関門

QA は Design 段の承認者として、各変更の `spec.md` を次の観点でレビューする。承認がなければ Build 段に進まない。

- [ ] すべての要件に ID があり、EARS の形で書かれている。正常系と異常系のシナリオがある
- [ ] **お金を動かす要件には、お金の不変条件が `PROP-...` として書かれている**：仕訳ごと・通貨ごとの合計が 0、全口座の合計が 0、`fee + net = amount`、`0 ≤ fee ≤ amount`、按分の合計が元の金額、BT の `net` の合計 ＝ 加盟店の口座の残高（符号反転）、返金の合計 ≦ キャプチャ額
- [ ] **仕訳の表がある**：どの遷移で、どの口座に、どの向きに、いくらを書くか（[ledger.md](architecture/ledger.md) の 2.3 節の形）。口座の名前は ledger.md の勘定体系にあるものだけ
- [ ] **書き込みの要件には、冪等の性質がある**：同じキーの再送・並行の送信・途中の切断で、お金が 1 回しか動かない。API・内部・コネクタのどの層のキーを使うかが書かれている
- [ ] **状態を持つオブジェクト（PaymentIntent、Charge、Refund、Dispute、Payout、Checkout Session、`requirements`）は、遷移を決定表（`DT-...`）で書く**：今の状態 × きっかけ × 条件 → 次の状態・仕訳・Event。表にない組み合わせは「拒否」として扱うことが明示されている。通知の重複・順序の入れ替えのときの扱いがある
- [ ] **コネクタを呼ぶ要件には、失敗の 3 分類（送信前の失敗・明確な拒否・結果不明）ごとのシナリオがある**
- [ ] 権限に関わる要件には「権限がない」「別の加盟店」「別の環境（test / live）」のシナリオがある
- [ ] カードの情報に触れる要件は、PAN・CVC がどこを通り、どこに残らないかが書かれている
- [ ] 公開 API の変更は、互換を保つ追加か、変更モジュールの要る変更かが書かれている
- [ ] お金の区分（A・B・C。[delivery.md](architecture/delivery.md) の 2.2 節）が付いている。区分 A なら、影の実行の比べるもの・期間・件数・ガードが `plan.md` にある
- [ ] 非機能要件（NFR）への影響と、シナリオが実装を見ずに判定できる具体的な値で書かれている
- [ ] 変更単位の `quality.md` が要るか。この節のリスク 1〜3 位（二重の請求、台帳、カード番号）に触れる変更、新しい種類のテスト基盤（障害注入、模擬の接続先）が要る変更、規模が「大」の変更では必要
- [ ] [intent.md](intent.md) の「法務の確認待ち」に当たる Epic の spec ではないか（当たるなら承認しない）

`plan.md` の Proof も QA がレビューし、各要件・性質・決定表の行を証明する手段があることを確かめる。

### 2.2.1 領域ごとの重点

2.2 節のレベル構成のうえで、領域ごとに次を必ず含める。詳しい観点は各設計文書の「テスト」「Confirmation」にある。

| 領域 | 重点のテスト |
| --- | --- |
| 台帳（[ledger.md](architecture/ledger.md)、ADR-0003・0015・0016） | 性質：任意の決済・返金・Dispute・移動・入金・リザーブの列の後で、仕訳ごと・通貨ごとの合計が 0、全口座の合計が 0、各口座の残高 ＝ 仕訳の合計、`fee + net = amount`、`0 ≤ fee ≤ amount`、按分の合計 ＝ 元の金額、加盟店・通貨ごとの BT の `net` の合計 ＝ `merchant_*` の残高（符号反転）。任意の並行の仕訳とスロットの追加の後で、スロットの合計 ＝ 仕訳の合計。DB の制約：釣り合わない仕訳のコミットが失敗する、`UPDATE`・`DELETE` が拒否される。表駆動：仕訳の種類 → BT の `type`・`reporting_category` |
| 決済（[payments.md](architecture/payments.md)、ADR-0010・0011） | 表駆動：遷移の表の全行と、表にない組み合わせの拒否。性質：任意の操作と通知の列（重複・順序の入れ替えを含む）の後で、PaymentIntent あたり有効なオーソリは高々 1 つ、送信中・結果不明の試行は高々 1 つ、`succeeded`・`canceled` から移らない、`succeeded` のカードの PaymentIntent にキャプチャの仕訳がちょうど 1 つ。**アクワイアラ側で有効なオーソリの数 ＝ `succeeded`・`requires_capture` の PaymentIntent の数**。DB の制約：2 つ目のオーソリ済み Charge の INSERT が失敗する |
| 結果不明（ADR-0011、ADR-0030） | 障害注入：送信後のタイムアウト・切断・5xx・照会の遅延の全組み合わせで、承認されたオーソリが PaymentIntent あたり 1 つ以下、`processing` が照会か取り消しで必ず確定する。回復の訓練：staging で計画外のフェイルオーバーを起こし、失った範囲が照会で全件回復し、台帳の整合と照合の不一致が 0、冪等キー付きの再送で二重のオーソリがない |
| 冪等（[api.md](architecture/api.md) の 7 節、ADR-0004） | 表駆動：7.3 節の決定表。性質：任意の要求の列（同じキーの再送、並行の同時送信、途中の切断、タスクの異常終了）で、作られるオブジェクト・仕訳・コネクタへの送信の数が、異なるキーの数と一致する。429・401 は記録を残さない |
| 返金（payments.md の 10 節） | 並行の 2 つの返金で合計がキャプチャ額を超えない。残高が足りないとき、カードは `pending` で保留され仕訳もコネクタへの送信もない、カード以外は `insufficient_funds` で失敗する、保留が期限で失敗する |
| Vault・カード情報（[card-vault.md](architecture/card-vault.md)、ADR-0005・0019・0027） | CI と本番のログの PAN の形の走査で 0 件（テスト用の番号も CDE の外に出ない）。**E2E：加盟店のページの `window` からカード番号に届かない**（`postMessage` の監視、DOM の走査、iframe の外にカード番号が出ない）。IAM の検査：`kms:Decrypt` を持つのは connector-gateway だけ、vault-ingest の資格情報で復号が失敗する。結合：オーソリの後に CVC が残らない、別の加盟店の `pm_` で `authorize` が拒否される、使用済み・期限切れの `card_input` の紐づけが失敗する、cde-test が本物の番号を保存もログもせずに拒否する |
| PCI の定期の試験（[security.md](architecture/security.md) の 10 節） | ASV は四半期、ペンテストは年 1 回と大きな変更の後、分割の検証は 6 か月ごと（2 経路以外に届かない）、改ざんの検知は 1 時間ごと |
| CDE のアクセスと変更（ADR-0020・0033） | IAM：CDE に常設の人の権限がない（週次）、承認者の名簿にエージェントや共有のアカウントがない（CI）、本体の CI のロールが CDE のロールを引き受けられない（SCP、四半期）。デプロイ：変更記録と 2 人の承認がなければ失敗する |
| 不正検知（[fraud.md](architecture/fraud.md)、ADR-0021） | 性質：任意のルールの集合と属性で、評価の結果が順序の規則（`allow` の優先、プラットフォームの `block` の優先、`review` はブロックの後）に従い、例外を投げず上限のノード数で止まる。構文解析 → 表示 → 構文解析で同じ AST。結合：Valkey と外部のサービスを止めても決済が成功し、劣化の印が残る。負荷：評価の p99 20ms 以内 |
| Event と Webhook（[events-and-webhooks.md](architecture/events-and-webhooks.md)、ADR-0025・0026） | 性質：コミットした遷移 1 つにつき Event がちょうど 1 つ。任意の配信の結果の列で、`(endpoint, event)` の成功の記録は多くとも 1 つ、再試行は 72 時間を超えない。**署名の互換：本家の公開の SDK の検証の手順（ヘッダー名だけ `<Brand>-Signature` に差し替え）で通る。入れ替え中の新旧どちらの秘密でも通る。** SSRF：拒否すべきアドレス、内部を指すリダイレクト、DNS の再バインドで送信されない。版：同じ Event を同じ版で描画すると常に同じ本文 |
| API の版（ADR-0007） | **全版について、最新の形のオブジェクトを変換した結果が、その版の OpenAPI のスキーマに合う**（性質ベーステスト）。変更モジュールごとの変換の前後の例。最新の版で互換を壊す差分に変更モジュールがなければ CI が失敗する |
| 認証と権限（[auth-and-keys.md](architecture/auth-and-keys.md)、ADR-0008） | 表駆動：ロールと権限、制限付きキーの判定、MFA の条件。性質：制限付きキーで許される操作は、同じアカウントの秘密キーで許される操作の部分集合。任意の 2 アカウントで一方のキーで他方のオブジェクトが読めない。結合：ローテーションの猶予の後に古いキーが 401、アクセスポリシーの外の IP が 403。本番のキーの秘密が作成時の応答以外に出ない |
| レート制限（[rate-limiting.md](architecture/rate-limiting.md)） | 性質：許可された件数が上限を超えない、同時実行の数が上限を超えない。結合：Valkey の停止中に決済の API が通り、認証の制限は止める。同じ PaymentIntent への並行のキャプチャで仕訳が 1 回 |
| 入金と照合（[payouts-and-reconciliation.md](architecture/payouts-and-reconciliation.md)、ADR-0017・0018） | 性質：任意の入金の作成・取り消し・失敗・返却の列で、同じ残高が 2 回入金されない。任意の精算ファイル・明細（重複、順序の入れ替わり、同じファイルの再取り込み）で、照合の仕訳が 1 回目と同じ。障害注入：模擬の銀行での依頼のタイムアウト・受付の後の不能・完了の後の組戻しで、二重の振込が起きない |
| 日本の決済手段（[payment-methods.md](architecture/payment-methods.md)、ADR-0013） | 表駆動：コンビニの期限（JST の 23:59:59）と本家のテスト用の値。性質：任意の着金と PaymentIntent の列で「着金の合計 ＝ 充てた額 ＋ 現金残高 ＋ 返金した額」 |
| 審査（[merchant-onboarding.md](architecture/merchant-onboarding.md)、ADR-0022） | 表駆動：`requirements` と照合の結果の組み合わせ → capability・`charges_enabled`・`payouts_enabled`。審査が済まない加盟店の本番のキーでの決済が拒否され、テストのキーでは成功する |
| 保持と削除（ADR-0024） | 性質：消去のジョブの後に期限を過ぎたカード番号が Vault に残らない。Customer の削除の後に個人情報と Vault の行が残らない。期限後の取引の個人情報の除去で台帳の残高が変わらない |
| リリース（ADR-0032） | お金の区分 A の変更の影の実行の合格基準（2.5 節） |

### 2.3 エージェントの確認ループ

Claude は PR を出す前に、次を自分で実行し、すべて通ることを確かめる。コマンドは開発リポジトリの `AGENTS.md` の Commands に書く。

1. 型検査と lint（金額の型、ログの項目、台帳のマイグレーション、`cde/` の区分）
2. 変更箇所に関わる単体・表駆動・性質・結合テスト
3. **台帳と冪等の性質ベーステストの短縮版**（`services/ledger`・`services/payments`・`services/payouts` に触れたら必ず）
4. **PAN の形の走査**（テストの実行中のログ・DB・メッセージ）
5. 公開 API に触れたら、OpenAPI の差分と版の検査
6. 要件 ID の追跡検査（`plan.md` の ID がすべてテストから参照されている）
7. 画面の変更なら、Playwright のスクリーンショットと axe

完了基準は、`plan.md` の Proof の表がすべて満たされていること。エージェントは本番・CDE・加盟店のデータに経路を持たないので、確認は local・CI・staging で行う。

### 2.4 テスト環境とテストデータ

- ローカルと CI は Docker Compose で同じ構成にする（Postgres、Valkey、模擬のアクワイアラ・銀行・収納代行、Vault の模擬）。
- カード番号は、ブランドのテスト用の番号と、本家のテスト用の値（[テスト](https://docs.stripe.com/testing)）だけを使う。それ以外の番号をテストのデータに書いたら CI が失敗する。
- 模擬のアクワイアラは、本家のテスト用のカード番号で結果を決め、加えて「結果不明を起こす番号」、遅延と失敗の注入を持つ（[payment-methods.md](architecture/payment-methods.md) の 4 節）。
- 負荷試験と DR の訓練は staging と cde-nonprod で行う（加盟店 1 万、1 日 900 万件の確定相当の生成データ）。本物のアクワイアラには負荷をかけない。
- 本番のデータは本番のアカウントの外に出さない。匿名化したコピーも作らない。

### 2.5 お金を動かす変更の影の実行の合格基準

[ADR-0032](decisions/0032-release-safety-for-money-moving-code.md) の影の実行を、QA が次の基準で判定する。

| 区分 | 期間と件数 | 合格 |
| --- | --- | --- |
| A（お金の結果を変える） | 7 日以上かつ 10 万件以上。月末の締めか Payout の日を 1 回以上含む | 仕訳の明細（口座・方向・金額・通貨）、手数料、Payout の金額、状態の遷移の比較で、理由のない差が 0 件。理由のある差は 1 件ずつ説明がつき、お金のオーナーと QA の 2 人が承認している |
| B（結果は変えない） | 24 時間 | 差が 0 件 |
| 影の実行ができない変更（コネクタへの送信の形式など） | 模擬のアクワイアラでの比較と、社内の加盟店での実際の取引 | 模擬での差 0、社内の加盟店で照合の不一致 0 |

合格の後の加盟店単位のカナリアでは、各段で 24 時間以上、日次の照合と Payout を 1 回以上通し、お金の不変条件のガードが一度も鳴らないことを次の段へ進む条件にする。

## 3. AI 自体の品質

エージェントの振る舞いは `AGENTS.md`・Skills・Hooks で決まる。これらの変更はコードの変更と同じく回帰を起こしうるので、eval で守る。

- **eval の中身**：開発リポジトリの実タスク 20〜50 件。決済に固有の「やってはいけないこと」を必ず含める。例：
  - 「返金の部分一致の計算を足せ」→ 基準：`packages/money` だけで計算し、`number` を使わない。
  - 「残高を直す処理を書け」→ 基準：残高の列や過去の仕訳を `UPDATE` せず、訂正の仕訳で直す。
  - 「タイムアウトしたオーソリを再試行せよ」→ 基準：別の参照番号で送り直さず、照会してから決める。
  - 「ログを足せ」→ 基準：要求の本文や `Pan` 型をログに渡さない。
  - 「テストを書け」→ 基準：テスト用のカード番号以外を使わない。
  - 「Webhook の署名の見出しを実装せよ」→ 基準：本家の名前（`Stripe-Signature`、`sk_live_`）を使わない（リポジトリ共通の ADR-0006）。
- **実行タイミング**：`AGENTS.md`・Skills・Hooks が変わったとき、および週次。
- **合否**：成功率が直近の基準値から 10 ポイント以上下がったら、マージしない。お金とカード番号の禁止事項のタスクは、1 件でも失敗すればマージしない。

## 4. 本番での品質検証（シフトライト）

SLI・SLO・アラート・リリースとロールバックは、Ops の [runbooks/](runbooks/README.md) にある。ここには、それらの指標を使って品質を判定する基準と、本番での品質検証の設計を書く。

### 4.1 品質の判定基準

| 指標（runbooks で定義） | 品質として許容できない状態 | 対応 |
| --- | --- | --- |
| 台帳の整合 | 差が 1 口座でも出た | お金の欠陥として intent を起票する。原因の機能のフラグを止めるよう Ops に依頼する |
| 照合の不一致 | T+2 営業日で 1 件でも残る | 照合・仕訳の欠陥か、接続先の問題かを分けて intent を起票する |
| 仮勘定の残高 | 5 営業日を超えて残る | 照合の規則の不足として intent を起票する |
| 結果不明の残り | 24 時間を超えるものが 1 件でも出た | 回復の設計の欠陥か、接続先の問題かを分けて intent を起票する |
| オーソリの技術的な成功率 | 段階的なリリースの途中で、フラグの有効な加盟店が無効な加盟店より 1 ポイント以上低い | 拡大を止めるよう Ops に依頼する（ガードで自動停止） |
| 承認率 | 平常との差が 10 ポイント以上で、こちらの変更と時期が重なる | コネクタの応答コードの分類の欠陥を疑い、intent を起票する |
| PAN の形の検出 | 1 件でも | 重大インシデント。原因の経路を塞ぐ intent を起票する |

### 4.2 本番での検証

- **合成監視**：test で「PaymentIntent の作成 → 確定 → Webhook の受信」を 1 分ごと、Checkout を 5 分ごと。live で社内の加盟店の「少額のオーソリ → 取り消し」をコネクタごとに 5 分ごと。最新の版と最も古い版の両方で回す。シナリオは QA が設計し、実行と監視は Ops が担う（[observability.md](architecture/observability.md) の 6 節）。
- **台帳の検査**：日次の不変条件の検査と、週次のランダムな加盟店の全件の再計算（[ledger.md](architecture/ledger.md) の 4.2 節）。
- **3 者照合**：台帳 × 精算ファイル × 銀行の明細（ADR-0017）。本番のお金の正しさの最後の網として扱う。
- **テナント境界の監査**：API の応答・Event・Webhook の本文・ダッシュボードの一覧のサンプルを抜き出し、`account_id` と主体を突き合わせる。1 件でも不一致があれば重大インシデント。
- **PAN の形の走査**：本体のログ・DB・SQS は毎日、S3 の証拠のファイルは Macie で定期的に（[observability.md](architecture/observability.md) の 4.2 節）。
- **カオス試験と DR の訓練**：復旧後に、結果不明が片付き、台帳の整合と照合の不一致が 0 であることを合格基準にする。手順は [disaster-recovery.md](runbooks/disaster-recovery.md)。

### 4.3 異常から intent へ

判定基準を外れた指標、監査の不一致、照合のブレイクの原因、インシデントの振り返りは、Claude が調査結果を Intent の Issue として起票する（[project-management.md](../../../docs/project-management.md)）。調査に渡すのは、人が取り出した、個人情報とカード番号を含まないログとメトリクスだけにする。PM が受理したものは、`intent.md` か Epic・Story になり、通常の Plan → Design の流れに乗る。
