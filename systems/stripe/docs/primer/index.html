Stripe は何をするサービスか

Stripe は、事業者（加盟店）が数行のコードでオンラインの代金を受け取れるようにする決済の API です。カード会社や銀行との接続、カード情報の保護、返金やチャージバック、売上の入金までを肩代わりします。

加盟店の開発者

API キーで PaymentIntent を作り、Webhook で結果を受け取ります。

加盟店の運用担当

ダッシュボードで売上・返金・Dispute・入金を見ます。

加盟店の顧客

決済ページ（Checkout）や埋め込みの入力欄（Elements）でカードを入力し、3D セキュアで本人認証をします。

規模の感覚：S1 で決済の確定のピークが 500 件/秒・加盟店 1 万、S3 で 50,000 件/秒・100 万です。可用性の目標は月間 99.99% です。

設計で効くところ：3 つの価値（すぐ組み込める・お金が必ず合う・安全で止まらない）は intent.md、規模は architecture/README.md の 2・3 節。

カード決済の登場人物

カード決済には、加盟店と顧客のほかに、お金と情報を中継する事業者がいます。このシステムは自分ではカードブランドの会員にならず、決済代行・アクワイアラと接続します（intent.md の Constraints）。

設計で効くところ：コネクタの共通の操作と能力は payment-methods.md の 3 節と ADR-0011。

オーソリ・キャプチャ・精算

カード決済は、1 回の操作に見えて、時間をずらした複数の段からできています。

  1. オーソリ：イシュアに「この額を使えるか」を問い合わせ、枠を押さえる。お金はまだ動かない。
  2. キャプチャ：押さえた枠のうち、実際に請求する額を確定する。ここで売上になる。
  3. 取り消し（void）：キャプチャの前なら、オーソリを取り消して枠を解放できる。
  4. 精算：決済代行が、手数料を引いた額を後日まとめて振り込み、明細（精算ファイル）を送る。
  5. 入金（Payout）：このシステムが、加盟店の残高から加盟店の銀行口座へ振り込む。

オーソリには有効期限があります。たとえば Visa の CIT は 7 日、日本の加盟店の JPY 取引は最長 30 日です（接続先が許す場合）。

オーソリが承認された時点で、台帳に売上の仕訳を書きますか？

オーソリは枠を押さえるだけでお金を動かしません。設計でも、仕訳を書くのはキャプチャが確定したときです（payments.md の 1・9 節）。

設計で効くところ：キャプチャの方式とオーソリの期限は payments.md の 5 節。

PaymentIntent：1 回の支払いの意図

本家の API では、1 回の支払いを PaymentIntent（pi_）で表し、確定（confirm）1 回ごとの試行を Charge（ch_）で表します。状態の名前は本家と同じ 7 つです。

stateDiagram-v2
  [*] --> requires_payment_method
  requires_payment_method --> requires_confirmation : 決済手段を付ける
  requires_confirmation --> requires_action : 3DS・支払い待ち
  requires_confirmation --> processing : 結果待ち
  requires_confirmation --> requires_capture : 手動キャプチャ
  requires_confirmation --> succeeded : 自動キャプチャ
  requires_action --> succeeded : 認証・入金
  processing --> succeeded : 照会で承認
  requires_capture --> succeeded : capture
  requires_action --> requires_payment_method : 失敗
  processing --> requires_payment_method : 取り消しが確定
  requires_capture --> canceled : cancel・期限切れ
  succeeded --> [*]
  canceled --> [*]

オーソリの承認で succeeded を返し、キャプチャは後ろで行う。本家の最新のバージョンの既定で、最初のバージョンの既定もこれ。

承認に続けて同じ要求の中でキャプチャし、succeeded を返す。

オーソリだけで requires_capture に止め、加盟店が後で capture する（在庫を確かめてから請求する、など）。

設計で効くところ：遷移の表と不変条件は payments.md の 3 節、ADR-0010。図は主な遷移だけです。

3D セキュアと不正検知

3D セキュア（EMV 3-D セキュア、3DS2）は、イシュアが顧客本人かを確かめる仕組みです。リスクが低ければ顧客の操作なしで通り（frictionless）、高ければパスワードなどを求めます（チャレンジ）。

  • 日本の「クレジットカード・セキュリティガイドライン」（現行 6.1 版）は、EC 加盟店に EMV 3-D セキュアの導入と、原則として決済の都度の認証を求めています。
  • 設計は、日本で発行されたカードの CIT で常に 3DS を要求します。事前に認証した MIT は免除です。
  • 3DS Server は自前で持たず、コネクタが提供するものを使います（EMVCo の認定が要るため）。
  • 不正検知は、本家の Radar に寄せたルール（allow・block・review、3DS の要求）を決済の経路の中で評価します。機械学習は MVP の範囲外です。

3DS の認証に成功した決済は、チャージバックで加盟店が負けることはない？

本家も保証しないと明言しています。設計も画面・文書で「保証」と書かないと決めています（payments.md の 6.2 節）。

設計で効くところ：ADR-0012、fraud.md の 2・5 節。本システムへの法的な当てはめは法務の確認待ちです。

結果不明：最大の難所

オーソリを送った後にタイムアウトすると、アクワイアラ側で承認されたかが分かりません。「失敗」と返して顧客が払い直すと二重請求になり、「成功」と見なすと受け取っていない代金で発送させてしまいます。

  1. 送る前に、試行（Charge）と参照番号を DB に記録してコミットする。
  2. 送信後のタイムアウト・5xx は unknown。PaymentIntent を processing にする。
  3. 回復のジョブが、参照番号でコネクタに照会する（5 秒・30 秒・2 分…）。
  4. 見つかれば、その結果（承認・拒否）を反映する。
  5. 見つからなければ、整合性の時間を待ってから同じ参照番号で取り消しを送り、確定してから失敗として返す。
  6. 最後の網：精算ファイルとの照合で、記録にない売上を見つけたら取り消す。

コネクタ A へのオーソリがタイムアウトしました。コネクタ B に送り直してよいのはいつ？

結果が分からないうちに別の試行を作ると、二重オーソリになります。設計は「送信中・結果不明の試行は同時に 1 つまで」を DB の制約で守ります（payments.md の 8.1 節）。

設計で効くところ：payments.md の 7・8 節、ADR-0011、コネクタからの通知は ADR-0014。

開発者向け API の約束

本家の API の使い心地は、加盟店の開発者との 3 つの約束からできています。

公開可能キー（ブラウザーに置いてよい）、秘密キー（全権限）、制限付きキー（権限を絞る）の 3 種類。接頭辞で本番とテストを分けます：<brand>_sk_live_・<brand>_sk_test_。本番とテスト（サンドボックス）は DB のクラスタごと分かれます。

POST に Idempotency-Key を付けると、同じキーの再送には最初の結果（500 を含む）を 24 時間返します。仕組みは共通の資料。設計は API・内部（仕訳）・コネクタ（参照番号）の 3 層で冪等にします。

バージョンは YYYY-MM-DD.<名前>。最初の要求の時点のバージョンがアカウントに固定され、互換性を壊す変更は新しいバージョンにだけ入ります。古いバージョンの形は「変更モジュール」で最新の形から変換して作ります。

金額の表し方金額は通貨ごとの最小単位の整数（bigint）と ISO 4217 の通貨コードで持ちます。JPY は小数がないので 1,000 円は 1000、USD は 10.00 ドルが 1000 です。浮動小数点は使いません。

設計で効くところ：api.md の 6・7・11 節、ADR-0004、ADR-0007、ADR-0008。

複式簿記の台帳

お金の正本は複式簿記の台帳です。1 つの仕訳は 2 行以上からなり、借方（+）と貸方（−）の合計が必ず 0 になります。お金は消えも湧きもせず、口座の間を移るだけです。

口座区分（自社から見て）10,000 円のカード決済の確定
connector_receivable資産：決済代行からの未収金+10,000
merchant_pending負債：加盟店に払うべき、まだ使えない売上−9,640
fee_revenue収益：決済手数料（3.6%）−360

加盟店の残高は、自社から見ると預かっている負債です。だから貸方（負）が普通の状態で、加盟店に見せるときは符号を反転します。

返金の処理で、加盟店の残高を減らすにはどうしますか？

台帳は追記だけで、UPDATE・DELETE はトリガーで拒否します。誤りも逆の仕訳で直します（ledger.md の 3 節）。

設計で効くところ：ledger.md の 2・3 節、ADR-0003、ADR-0015。

保留中・利用可能・リザーブ

本家の加盟店の残高（Balance）は、pending（まだ使えない）と available（入金・返金に使える）に分かれます。残高を動かす 1 件ごとの記録が BalanceTransaction で、設計では仕訳の射影です。

available_on

売上が利用可能になる日。確定日＋売上処理のタイミング（日本の既定は初回 7 暦日、以後 4 営業日）。確定時に固定します。

リザーブ

リスクに応じて残高の一部を留め置く。固定（指定日に解放）とローリング（決済から N 日後に解放）があります。

マイナス残高

Dispute の引き落としは残高が足りなくても行います。以後の売上で相殺します。

書き込みの集中大口の加盟店では、1 つの残高の行に毎秒数百件の書き込みが集まり、行ロックで直列になります。設計は集計をスロット（16〜64 行）に分け、プラットフォームの口座は即時に集計しません。

設計で効くところ：ledger.md の 4〜8 節、ADR-0016。

返金とチャージバック

どちらもお金が顧客に戻りますが、誰が始め、誰が決めるかが違います。

返金（Refund）

加盟店が自分の判断で行う。利用可能な残高から引く。足りなければカードは最長 30 日保留し、他の手段は失敗にする。決済手数料は戻らない。

チャージバック（Dispute）

顧客がイシュアに異議を申し立てて始まる。通知の時点で額と手数料（1 件 1,500 円）を引き、加盟店は証拠を1 回だけ提出できる。勝てば額は戻るが、手数料は戻らない。

本家の Dispute の状態は 8 つです。warning_ が付くもの（照会）はお金を動かさず、付かないもの（needs_response → under_review → won / lost）が正式なチャージバックです。

Dispute の勝ち負けを決めるのは誰？

設計は自分で勝ち負けを決めず、証拠をアクワイアラへ届けるだけです（disputes.md の 1 節）。

設計で効くところ：disputes.md の 3・5 節、返金は payments.md の 10 節。

入金と 3 者照合

台帳が正しくても、外の世界と合っているとは限りません。そこで、台帳・決済代行の精算ファイル・銀行の入出金明細の 3 つを突き合わせます（3 者照合）。

flowchart LR
  L["台帳
(未収金・入金の仕訳)"] -- "参照番号で" --- S["精算ファイル
(決済代行)"]
  S -- "純額・日付で" --- B["銀行の明細
(着金・出金)"]
  B -- "振込の依頼番号で" --- L
  B -. "相手が分からない入金" .-> X["仮勘定
(suspense)"]
  • 説明のつかない差は「ブレイク」として記録し、T+2 営業日までに 0 件にします（NFR-005）。
  • お金が実際に動いたのに相手が分からないときは、まず仮勘定に置きます。
  • 加盟店への入金は、提携銀行の API で振り込み、予備に全銀フォーマットのファイルを持ちます。日本の本家の既定は手動入金で、週次・月次も選べます。

設計で効くところ：payouts-and-reconciliation.md、ADR-0017、ADR-0018。入金の Epic は法務の確認待ち（L1）です。

日本の決済手段：コンビニ払いと銀行振込

どちらも顧客が後から払う「非同期」の手段です。PaymentIntent は requires_action で支払いを待ちます。

  • 収納代行の事業者が支払い番号を発行し、顧客が店頭で現金で払う。120 円〜300,000 円、期限の既定は 3 日。
  • 支払うと「速報」が届き、後日「確報」と精算ファイルが届く。設計は速報で succeeded にし、確報で照合する。
  • チャージバックはない。返金は顧客の銀行口座への振込。
  • Customer ごとにバーチャル口座（振込専用の口座番号）を割り当てる。
  • 振込はまず Customer の現金残高に入り、そこから PaymentIntent に充てる。過不足が起きうる。
  • 顧客のお金を預かる形になるため、資金決済法の上の扱いが法務の確認待ち（L1）。

設計で効くところ：payment-methods.md の 5・6 節、ADR-0013。

PCI DSS とカード情報の隔離

PCI DSS は、カード番号（PAN）を扱う事業者が守る業界の基準です。カード番号に触れる範囲（CDE）がすべて審査の対象になるので、範囲を小さく閉じ込めることが設計の要になります。

  1. 顧客のカード番号は、CDE が配る iframe に入力され、CDE（別の AWS アカウント）へ直接送られる。
  2. CDE は番号を暗号化して保存し、使い捨ての card_input を返す。
  3. 本体は card_input と引き換えに pm_（トークン）を得る。手に入るのはブランド・下 4 桁などの表示用の情報だけ。
  4. オーソリのときだけ、CDE の Connector Gateway が番号を復号してアクワイアラへ送る。
  5. CVC はオーソリの後に一切残さない（オーソリ後の機密認証データの保存は禁止）。

加盟店は番号に触れないので、最も軽い自己評価（SAQ A）で済みます。目標は v4.0.1 のサービスプロバイダー レベル 1 です。

設計で効くところ：card-vault.md の 2・3 節、ADR-0005、ADR-0029、ADR-0020（AI エージェントは CDE に入れない）。

Event と Webhook

決済の結果は、非同期に決まることが多い（3DS・結果不明・コンビニの入金）ため、加盟店は Webhook で知ります。Event は状態の変化と同じトランザクションで outbox に書きます（共通の資料）。

  • 少なくとも 1 回・順序なし：加盟店は Event の id で重複を捨てる。
  • 失敗は 3 日間、指数的に再試行：2xx 以外はすべて失敗。
  • HMAC で署名：<Brand>-Signature: t=…,v1=…。v1 は「時刻.本文」の HMAC-SHA256。加盟店は生の本文で検証し、時刻の差で再送の攻撃を防ぐ。
  • 隔離された経路から送る：加盟店の URL への送信は、内部に届かない egress VPC の固定 IP から。

payment_intent.succeeded の後に payment_intent.created が届きました。何が起きた？

本家も設計も順序を保証しません。1 つの遅いエンドポイントで全体を詰まらせないためです（events-and-webhooks.md の 1・5.3 節）。

設計で効くところ：events-and-webhooks.md、ADR-0025、ADR-0026。

加盟店の審査と日本の法令の枠組み

決済の基盤は、誰にでも使わせてよいわけではありません。本番で決済を受ける前に、本人確認（KYC）、反社会的勢力・制裁の照合、業種と Web サイトの審査をし、通れば charges_enabled・payouts_enabled が開きます。

法令論点（設計は結論を出していない）
資金決済法代金を受け取って後で渡す流れが、収納代行か資金移動業か（L1）
割賦販売法締結事業者の登録の要否、加盟店調査の項目（L2）
犯罪収益移転防止法特定事業者に当たるか、取引時確認の義務（L3）
個人情報保護法顧客の情報を委託で扱うか、外国の提供者への提供（L4）
電気通信事業法端末の情報を不正検知へ送ることの外部送信規律（L5）
帳簿・税保存期間（L6）、留保の期間（L7）、手数料の消費税（L8）
法務の確認待ち上の L1〜L8 はすべて法務の確認待ちです。確認が済むまで、関係する Epic の spec は承認しません。この資料は枠組みの紹介で、法的な判断ではありません。

設計で効くところ：intent.md の「法務の確認待ち」、merchant-onboarding.md、ADR-0022。

中心は「支払い」と「お金」の 2 つの系です。支払いの系（PaymentIntent → Charge → Refund・Dispute）が状態を持ち、お金の系（仕訳 → 行 → 口座）が金額の正本を持ちます。BalanceTransaction は両者をつなぐ射影です。

用語集

加盟店
代金を受け取る事業者。このシステムのテナント（acct_）。
決済代行
加盟店とカード会社などの間をつなぐ事業者（PSP）。
アクワイアラ
加盟店の契約を持ち、カードブランドの網に取引を送るカード会社。
イシュア
顧客にカードを発行した会社。オーソリの承認と、チャージバックの判断をする。
コネクタ
決済代行・アクワイアラ・収納代行・銀行ごとの差を吸収する、このシステムの部品。共通の操作と「能力」を持つ。
オーソリ
与信の確認。イシュアに利用可能かを問い合わせ、枠を押さえる。お金は動かない。
キャプチャ
オーソリした枠のうち請求する額を確定すること。日本では「売上確定」「実売上」とも呼ぶ。
精算
決済代行が、取引の代金から手数料を引いてまとめて振り込むこと。明細が精算ファイル。
CIT
Customer-Initiated Transaction。顧客がその場にいて始める取引。
MIT
Merchant-Initiated Transaction。保存したカードで、加盟店が顧客の不在時に始める取引。
3D セキュア
EMV 3-D セキュア（3DS2）。イシュアがカード会員本人かを認証する仕組み。
frictionless
3DS で、イシュアがリスクを低いと見て、顧客の操作なしに認証を通すこと。逆がチャレンジ。
参照番号
コネクタへの要求ごとの一意の番号。再送・照会・取り消しを同じ番号で行い、重複を防ぐ。
チャージバック
顧客の異議を受けて、イシュアが加盟店から代金を取り戻す仕組み。API では Dispute（du_）。
照会（inquiry）
チャージバックの前の段階の問い合わせ。お金は動かない。
複式簿記
1 つの取引を、借方と貸方の 2 つ以上の口座の動きとして、合計が釣り合うように記録する方法。
仕訳
台帳への 1 回の記録（journal_entries）。行（ledger_postings）の合計は通貨ごとに 0。
BalanceTransaction
加盟店の残高を動かす 1 件ごとの記録（txn_）。amount・fee・net・available_on を持つ。
3 者照合
台帳・決済代行の精算・銀行の明細の 3 つが一致することを確かめる処理。
仮勘定
実際に動いたが行き先・出どころが分からないお金を一時的に置く口座（suspense:*）。
全銀フォーマット
全国銀行協会が定めた、総合振込や入出金明細のファイルの固定長の形式。
収納代行
コンビニでの支払いを受け付け、事業者に代金を渡す事業者。
バーチャル口座
振込の受け取り専用に割り当てる口座番号。番号で振込人（Customer）を特定する。
PCI DSS
カードブランドが作った PCI SSC の、カード情報を守るための基準。v4.0.1 が現行。
PAN
Primary Account Number。カード番号。
CDE
Cardholder Data Environment。カード会員データを扱う、またはそれに接続する範囲。
トークン
カード番号の代わりに使う、番号を復元できない値。ここでは pm_。
SAQ A
カード情報の処理を全面的に外部へ任せた加盟店向けの、最も短い自己評価の質問票。
HMAC
共有の秘密の鍵とハッシュ関数で作る、改ざん検知用の署名。
KYC
Know Your Customer。事業者の本人確認と審査。オンラインで行うものを eKYC と呼ぶ。
ISO 4217
通貨コードの国際規格（JPY・USD など）。通貨ごとの小数の桁数も定める。
