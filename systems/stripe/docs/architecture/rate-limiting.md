# Rate limiting: Stripe

レート制限、同時実行の制限、オブジェクトのロック待ちの共通の設計。方式は [ADR-0009](../decisions/0009-rate-limiting.md) にある。Slack の [rate-limiting.md](../../../slack/docs/architecture/rate-limiting.md)（層・GCRA・Valkey・障害時の振る舞い）を引き継ぎ、単位と数値を本家 Stripe に合わせる。

各領域の文書にある上限は、この文書の枠組みに従う。数値の一覧は 4 節にまとめ、ここを正とする。本家の振る舞いは、2026-09-26 に [Rate limits](https://docs.stripe.com/rate-limits) で確かめた。

## 1. 本家の仕組み（確かめたこと）

| 項目 | 本家 |
| --- | --- |
| 単位 | Stripe のアカウントごとの 1 秒あたりの要求の数。全体の制限に加え、一部のエンドポイントに個別の制限がある |
| エンドポイント | 名前の付いた操作ごとに 1 つ（`POST /v1/payment_intents` と `GET /v1/payment_intents/{id}` は別）。ID が違っても同じ操作は同じ制限 |
| 全体 | 本番 1 秒に 100、サンドボックス 1 秒に 25 |
| エンドポイントの既定 | 1 秒に 25（個別に書かれていないもの） |
| 個別 | PaymentIntent：1 つのオブジェクトにつき 1 時間に 1,000 回の更新。Files：読み取り 1 秒 20、書き込み 1 秒 20。Payouts：作成 1 秒 15、同時 30。Search：1 秒 20（本番とテストで別）。Connect のアカウントの作成：本番 1 秒 30、サンドボックス 1 秒 5 |
| 同時実行 | レートとは別に、同時に処理中の要求の数を制限する。一覧や `expand` を含む重い要求で当たりやすい。値は公開していない |
| 応答 | 429 と `Stripe-Rate-Limited-Reason`（`global-rate`・`endpoint-rate`・`global-concurrency`・`endpoint-concurrency`・`resource-specific`） |
| ロック待ち | 同じオブジェクトへの並行の操作で、ロックを時間内に取れないと 429（`code: lock_timeout`）。この 429 には `Stripe-Rate-Limited-Reason` が付かず、要求は処理されない。SDK はこれを自動で再試行する |
| 読み取りの割当 | 読み取り（`GET`）の数を、直近 30 日の取引 1 件あたり平均 500 以下にする。月に最低 10,000 件は割り当てる。書き込みには割当がない |
| 緩和 | サポートに申請する。大きな緩和は 6 週間前までに |
| 負荷試験 | サンドボックスは制限が低く、決済の遅延も本番と違うので、本家への負荷試験を勧めず、呼び出しを模擬することを勧めている |
| プラン | 料金のプランで制限が変わるという記述はない |

`Retry-After` を 429 に付けるかは、文書に書かれていない。**未検証**（サンドボックスで 1 秒 25 件を超えて送り、応答の見出しを確かめる）。

## 2. 原則

| 原則 | 内容 |
| --- | --- |
| 本家の単位と値に寄せる | アカウント × 環境ごとの全体の制限と、エンドポイントごとの制限の 2 段を基本にする。値は本家の公開値を初期値にする |
| 決済を止めない | 決済の経路（PaymentIntent の作成・確定・キャプチャ、Refund の作成）は、エンドポイントの既定（1 秒 25）で絞らず、全体の制限だけにかける（4.2 節） |
| プランで変えない | すべてのアカウントに同じ値をかける。緩和はアカウント単位の上書き（6 節）だけで行う（Slack の ADR-0033 と同じ） |
| 同期は早く断り、非同期は遅らせる | Slack と同じ。Webhook の配信は捨てずに遅らせる（[events-and-webhooks.md](events-and-webhooks.md)） |
| 予測できる | 上限は契約の一部として文書にし、429 の理由を見出しで知らせる |

## 3. 層と方式

### 3.1 層

| 層 | 場所 | 単位 | 目的 |
| --- | --- | --- | --- |
| L1 エッジ | AWS WAF | IP | 洪水・総当たりの粗い遮断 |
| L2 認証 | api・ダッシュボード | IP、メールアドレス | キーの検証の失敗、ログイン・OTP の総当たり |
| L3 全体のレート | api のミドルウェア | アカウント × 環境 | `global-rate` |
| L4 エンドポイントのレート | api のミドルウェア | アカウント × 環境 × 操作 | `endpoint-rate` |
| L5 同時実行 | api のミドルウェア | アカウント × 環境（全体・操作ごと） | `global-concurrency`・`endpoint-concurrency` |
| L6 リソースに固有 | ドメイン層 | オブジェクト、アカウント | `resource-specific`（PaymentIntent の更新の回数、Payout の作成） |
| L7 ロック | ドメイン層（DB） | オブジェクト | `lock_timeout` |
| L8 割当 | 日次のジョブ | アカウント × 環境 | 読み取りの割当（30 日） |
| L9 非同期 | Worker | 送信先 | Webhook の配信の速さ（[events-and-webhooks.md](events-and-webhooks.md)） |

- L3〜L5 は、キーの認証の直後、冪等の層の前で判定する（本家と同じ順。[api.md](api.md) の 2 節）。
- 判定は L3 → L4 → L5 の順に行い、最初に超えたものの理由を返す。
- 単位にキーを含めない。本家と同じく、アカウントの中の全キーで枠を共有する。

### 3.2 計数

- **GCRA を Valkey の Lua スクリプトで実行する**（Slack の rate-limiting.md の 3.1 節と同じ）。1 つの対象につきキー 1 つ、1 往復で判定と更新をする。
- キーの形は `rl:{acct_xxx:live}:<limit>:<subject>`。`{acct_xxx:live}` をハッシュタグにし、S2 のクラスタでもアカウント × 環境の計数を同じシャードに置く。
- 1 秒あたりの制限は、バーストを 1 秒ぶん（100 なら 100）にする。本家の「1 秒あたり」を、瞬間の集中をある程度許す形で表す。
- 同時実行（L5）は、Valkey のソート済み集合に処理中の要求を期限付き（30 秒。API のタイムアウトと同じ）で入れて数え、応答の後に消す。
- PaymentIntent の更新の回数（L6）は、`rl:{acct:env}:pi_update:{pi_id}` に 1 時間 1,000 回の GCRA をかける。

### 3.3 ロック待ち（L7）

- PaymentIntent・Refund・Payout など、状態を持つオブジェクトの変更は、行ロック（`SELECT ... FOR UPDATE`）で直列にする。ロック待ちの上限は `SET LOCAL lock_timeout = '2s'`（初期値。負荷試験で決め直す）。
- 時間切れは 429、`type: invalid_request_error`、`code: lock_timeout`、`<Brand>-Should-Retry: true`。`<Brand>-Rate-Limited-Reason` は付けない（本家と同じ）。
- 本家はロック待ちの 429 に要求の ID を付けないが、本システムは追跡のために `Request-Id` を付ける。処理はしていないので、冪等の記録は残さない（[api.md](api.md) の 7.3 節の 1 段目で止まる）。
- ロックはコネクタの呼び出しの間は持たない。コネクタを呼ぶ前に状態を「処理中」にしてコミットし、結果を反映するときに取り直す（[payments.md](payments.md)）。長い処理で他の要求を 2 秒以上待たせないため。

### 3.4 応答

| 超えたもの | 状態 | `<Brand>-Rate-Limited-Reason` | 本文 |
| --- | --- | --- | --- |
| L3 | 429 | `global-rate` | `{"error": {"type": "invalid_request_error", "code": "rate_limit", "message": "..."}}` |
| L4 | 429 | `endpoint-rate` | 同上 |
| L5 | 429 | `global-concurrency` / `endpoint-concurrency` | 同上 |
| L6 | 429 | `resource-specific` | 同上 |
| L7 | 429 | なし | `code: lock_timeout` |
| L1・L2 | 429（WAF は 403） | なし | 認証の制限は、成功と区別できない文面にする（Slack と同じ） |

- 429 には、理由の見出しに加えて `Retry-After`（秒、GCRA が求めた次に許される時刻まで。最低 1）と `<Brand>-Should-Retry: true` を付ける。本家が `Retry-After` を付けるかは未検証だが、付けても本家の SDK と互換を損なわない。
- `code: rate_limit` の名前は、本家の [Error codes](https://docs.stripe.com/error-codes) にあることを確かめた。`type` の値は本家の応答で**未検証**。
- Slack の外部公開 API で付けた `RateLimit`・`RateLimit-Policy`（IETF の草案）は付けない。本家も付けておらず、値の公開の粒度（アカウントごとの残り）を契約にしないため。

### 3.5 Valkey が使えないとき

Slack の rate-limiting.md の 3.4 節と同じ。

| 対象 | 振る舞い |
| --- | --- |
| L3〜L6 | 通す側に倒す。各タスクの中で、上限をタスク数で割った簡易な制限を続ける。**決済の API を、Valkey の障害で止めない** |
| L2（キーの検証の失敗、ログイン、OTP） | 止める側に倒す。タスクの中の厳しい制限と WAF で守る |
| L7 | Valkey に依らない（DB のロック） |

## 4. 上限の一覧（S1）

数値は初期値で、負荷試験と運用で見直す。本家の公開値があるものは、それを初期値にする。

### 4.1 エッジと認証

| 対象 | 単位 | 上限 |
| --- | --- | --- |
| `api.<domain>` のすべての要求 | IP | 5 分に 30,000 件（WAF）。決済の API は加盟店のサーバーの少数の IP から集中して来る。アカウントの全体の上限（1 秒に 100 ＝ 5 分に 30,000）と同じ量を 1 つの IP から受けられるようにする。大口の加盟店は 6 節の上書きで WAF の除外に加える |
| `vault.<domain>`・`checkout.<domain>` のすべての要求 | IP | 5 分に 1,000 件（WAF）。カードテスティングを入口で抑える（[fraud.md](fraud.md) の 7 節）。急増時は Challenge |
| ダッシュボード（`dashboard.<domain>`） | IP | 5 分に 2,000 件（WAF。Slack と同じ） |
| API キーの検証の失敗 | IP | 1 分に 20 回 |
| ダッシュボードのログインの開始 | IP | 1 分に 30 回 |
| OTP の送信 | メールアドレス / IP | 1 時間に 5 回 / 20 回 |
| 2 要素目の検証 | ログインの途中 | 5 回。15 分に 3 回やり直したら、IP とアカウントの組を 15 分止める |
| ダッシュボードの内部 API | セッション | 1 分に 600 回（バースト 100） |

認証の値は Slack の identity-and-access.md の 11 節と同じにする（[auth-and-keys.md](auth-and-keys.md) の 3 節）。

### 4.2 全体とエンドポイント（L3・L4）

| 対象 | 本番 | サンドボックス | 本家 |
| --- | --- | --- | --- |
| 全体（アカウント） | 1 秒に 100 | 1 秒に 25 | 同じ |
| エンドポイントの既定 | 1 秒に 25 | 1 秒に 25 | 同じ |
| 決済の経路（PaymentIntent の作成・確定・キャプチャ・取り消し、Refund の作成） | 全体の枠だけ（エンドポイントの制限なし） | 全体の枠だけ | 本家がこれらに個別の値を持つかは**未検証**（下記） |
| 公開可能キーの操作（PaymentMethod の作成、PaymentIntent の確定） | 全体の枠に数える。加えて IP ごとに 1 分に 60 回 | 同じ | 未検証 |
| Search（全エンドポイントの合計） | 1 秒に 20 | 1 秒に 20 | 同じ |
| Files（読み取り / 書き込み） | 1 秒に 20 / 20 | 同じ | 同じ |
| Payouts の作成 | 1 秒に 15 | 1 秒に 15 | 同じ |

- 本家の表の「エンドポイントの既定 1 秒 25」をそのまま決済の作成にかけると、1 つの加盟店が 1 秒に 25 件しか決済できない。本家がこれで運用しているのか、決済の経路に高い値を持っているのかは、文書から読み取れない。本システムは、全体の 100 を決済の上限とし、決済の経路にはエンドポイントの制限をかけない。本家の値はサポートへの問い合わせか、サンドボックスでの計測（ただしサンドボックスは全体が 25 なので、本番の値は分からない）で確かめる。
- S1 の規模（ピーク 500 件/秒、1 万加盟店。[README.md](README.md) の 2 節）では、1 秒に 100 件を超える加盟店は、大規模な販売のときの少数に限られる。これらは 6 節の上書きで事前に上げる。

### 4.3 同時実行（L5）

本家は値を公開していない。本システムの初期値を決める。

| 対象 | 本番 | サンドボックス |
| --- | --- | --- |
| 全体（アカウント） | 同時に 50 | 同時に 15 |
| 一覧のエンドポイント、`expand` を含む要求 | 操作ごとに同時に 10 | 同時に 5 |
| Payouts の作成 | 同時に 30（本家と同じ） | 同時に 30 |

### 4.4 リソースに固有（L6）

| 対象 | 単位 | 上限 |
| --- | --- | --- |
| PaymentIntent の更新（確定・キャプチャ・更新・取り消しを含むすべての書き込み） | オブジェクト | 1 時間に 1,000 回（本家と同じ） |

### 4.5 読み取りの割当（L8）

- 本家と同じく、直近 30 日の読み取りの要求の数を、同じ期間の取引の数で割り、1 件あたり 500 を超えないようにする。最低は月 10,000 件。
- MVP は計測と通知だけにする。超えたアカウントに、ダッシュボードとメールで知らせ、一覧の代わりに Webhook を使うよう案内する。止める運用（読み取りの 429）は E11 で、計測の結果を見て決める。
- 取引の数の定義（決済の成功だけか、返金を含むか）は、本家の文書に書かれていない。**未検証**。本システムでは、成功した決済と返金の数とする。

### 4.6 非同期（L9）

Webhook の配信の速さは [events-and-webhooks.md](events-and-webhooks.md) で決める。1 つの送信先が遅くても、他の加盟店の配信を遅らせないこと（送信先ごとの同時実行の上限）を、その文書の要件にする。

## 5. サンドボックスと負荷試験

- サンドボックスの全体の制限は、本番の 1/4（1 秒 25）にする（本家と同じ）。模擬のアクワイアラを使うサンドボックスが、本番のコネクタの容量を圧迫しないため。
- 本家と同じく、サンドボックスへの負荷試験を加盟店に勧めない。文書で、加盟店の側で API の呼び出しを模擬する方法を案内する。
- 本システム自身の負荷試験は、専用の試験用アカウントに 6 節の上書きをかけて行い、本番の加盟店と同じ上限の判定の経路を通す。

## 6. 上書きと運用

- **緩和は、アカウント × 環境の上書きだけで行う。** テーブル `rate_limit_overrides`（`account_id`、環境、制限の名前、値、理由、期限、承認者）に置き、Ops が変更する。変更は監査ログ（[auth-and-keys.md](auth-and-keys.md) の 9 節）に残す。コードに特定のアカウントを書かない。
- 加盟店からの申請はダッシュボードかサポートで受ける。本家と同じく、大きな緩和（全体を 2 倍以上）は 6 週間前までに申請してもらい、容量（[capacity.md](capacity.md)）を確かめてから承認する。
- 障害時には、特定のアカウントの上限を一時的に下げられる。上げる・下げるの手順は runbook の `rate-limit-override.md`（E10 で作る。[runbooks/README.md](../runbooks/README.md)）に置く。
- 合成監視のアカウントは上限の対象から外さない。

## 7. 観測

- メトリクス：`ratelimit_limited_total{limit, reason, livemode}`、`ratelimit_backend_errors_total`、同時実行の使用率、`lock_timeout_total{resource}`、読み取りの割当の比率の分布。
- アカウントのラベルは上位 N 件と「その他」に丸める。
- アラート：
  - 特定の制限の 429 が急増した（攻撃か、加盟店の不具合か）
  - Valkey の計数が失敗している
  - `lock_timeout` の急増（同じオブジェクトへの並行の操作、または内部の処理との競合）
  - 決済の経路での 429 の率が 0.1% を超えた（正当な決済を断っている疑い）
- 加盟店向けに、ダッシュボードで 429 の件数と理由を、要求のログ（[auth-and-keys.md](auth-and-keys.md) の 9.2 節）から見られるようにする（E7）。

## 8. テスト

- 性質ベーステスト：任意の要求の列について、許可された件数が、上限（平均の速さ × 時間＋バースト）を超えない。同時実行の制限で、任意の時点の処理中の数が上限を超えない。
- 表駆動テスト：3.4 節の応答の表（理由の見出しの値、`<Brand>-Should-Retry`、`Retry-After`）。
- 結合テスト：
  - Valkey の停止中、決済の API は通り、キーの検証の失敗の制限は止める。
  - 同じ PaymentIntent への並行のキャプチャで、1 つが成功し、他は `lock_timeout` か状態の衝突になり、仕訳が 1 回だけ（ADR-0003・0004）。
  - 429 の要求を同じ `Idempotency-Key` で再送すると、制限が解けた後に処理される（429 は冪等の記録を残さない）。
- 負荷試験：上限の付近で、429 の判定が DB の負荷を増やさない（判定は Valkey の 1 往復だけ）。

## 9. 段階ごとの変化

| 段階 | 変化 |
| --- | --- |
| S2 | Valkey をクラスタにする。ハッシュタグでアカウント × 環境の計数を同じシャードに置く。読み取りの割当を止める運用を検討する |
| S3 | アカウントの制限はセルの中で閉じる。IP とログインの制限は、セルの外のアイデンティティ面で数える。大口の加盟店の専用のセルでは、上書きの値を大きくできる |

## 10. 決定と持ち越し（2026-09-26、既定案）

- **決済の経路の制限**：本家の値が分からないまま、全体の枠（1 秒に 100）だけをかける（4.2 節）で確定する。本家の値の確認は行わない（分かっても、正当な決済を断らない方針は変えない）。
- **`Retry-After`**：付ける（3.4 節）。本家が付けるかにかかわらず、本家の SDK との互換を損なわない。429 の本文の `type` は `invalid_request_error` とする。
- **エッジの IP の上限**：api は 5 分に 30,000、Vault・Checkout は 5 分に 1,000（4.1 節）。
- 持ち越し：同時実行の上限の値（4.3 節）は E10 の負荷試験で決める。読み取りの割当を超えたときに止めるか（4.5 節）は、E11 で計測の結果を見て決める。
