## 2. 部品ごとの必要量

### 2.1 API

- 確定の要求は、API の中でコネクタの応答を待つ。**同時に処理中の要求の数**（リトルの法則：到着率 × 滞在時間）が効く。
  - 平常：500 件/秒 ×（内部の処理 0.1 秒＋コネクタ 0.8 秒の平均）＝ 約 450 件。
  - コネクタが遅くなり全件がタイムアウト（20 秒）まで待つと：500 × 20 ＝ 1 万件。
- Node.js は、待っている要求を安く保持できる（1 要求あたり数十 KB）。CPU で効くのは、内部の処理（認証、冪等、検証、台帳の仕訳、JSON）で、1 vCPU あたり約 250 件/秒の書き込みの要求と見る。
- ピークの書き込みの要求（作成 600＋確定 500＋キャプチャ 150＋返金 25 ≒ 1,300 件/秒）と読み取り（1,500 件/秒、1 vCPU あたり 500 件/秒）で、約 8 vCPU。余裕と AZ の障害を見て、2 vCPU × 12 タスク（平常）、最大 40 タスク。
- **コネクタが遅くなったときの守り**（隔壁）：
  - connector-gateway は、コネクタごとに同時に送る要求の上限（初期値：1 コネクタ 1 リージョンあたり 2,000）を持つ。上限に達したら、待たずに失敗を返し、振り分けの規則（[payment-methods.md](payment-methods.md)）で別のコネクタに回すか、`processing_error` を返す。
  - api は、1 タスクあたりの同時の確定の要求に上限（初期値 1,000）を置き、超えたら 503 を返す（加盟店は冪等キーで安全に再送できる）。1 つのコネクタの遅れが、読み取りの API まで止めないようにする。

### 2.2 Aurora（live）の書き込み

| 処理 | 1 件あたりの行 | ピークの件数/秒 | 行/秒 |
| --- | --- | --- | --- |
| 確定（冪等キー、PaymentIntent、試行の記録と結果、Charge、仕訳 1＋明細 4、残高の集計、outbox 2、Event 2） | 約 15 | 500 | 7,500 |
| 作成（冪等キー、PaymentIntent、outbox、Event） | 4 | 600 | 2,400 |
| 手動のキャプチャ | 10 | 150 | 1,500 |
| 返金 | 12 | 25 | 300 |
| Webhook の試行の記録 | 1 | 1,500 | 1,500 |
| コネクタの結果の反映、結果不明の照会、その他 | — | — | 500 |
| **合計** | | | **約 1.4 万** |

- トランザクションの数は、約 3,500 件/秒（確定は「試行の記録」と「結果の反映」の 2〜3 回に分かれる）。
- `db.r8g.4xlarge`（16 vCPU、128 GiB）の writer で、CPU 50% 以下を目標にする。超えるなら `db.r8g.8xlarge` へ上げ、並行して S2 の準備（台帳の分割、Webhook の分離）を始める。
- **大口の加盟店の残高の集計の行**が、書き込みのホットスポットになりうる。集計をスロット（既定 1、最大 64）に分け、ロック待ちの p99 が 20ms を超えた口座を Ops が増やす（[ADR-0016](../decisions/0016-hot-accounts-and-ledger-sharding.md)、[ledger.md](ledger.md) の 8 節）。
- ストレージ：1 年で約 6 TB（仕訳が大半）。台帳は月ごとのパーティションで持ち、13 か月より古いパーティションは S3 の Parquet（Iceberg）へ移す（[ledger.md](ledger.md) の 3 節）。

### 2.3 DB の接続数

規則は Slack と同じ：**オートスケールの上限まで増えたときの合計を、`max_connections` の 50% 以下に保つ。** `db.r8g.4xlarge` の既定の `max_connections` は `LEAST({DBInstanceClassMemory/9531392}, 5000)` で 5,000 になる（[AWS のドキュメント](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/AuroraPostgreSQL.Managing.html#AuroraPostgreSQL.Managing.MaxConnections)）。

| 利用者 | タスクあたりのプール | 最大タスク数 | 最大の接続数 |
| --- | --- | --- | --- |
| api | 20 | 40 | 800 |
| dashboard、checkout | 10 | 12 | 120 |
| workers | 5 | 30 | 150 |
| relay | 3 | 2 | 6 |
| connectors | 5 | 6 | 30 |
| migrator、運用、照合のバッチ | — | — | 50 |
| **合計** | | | **約 1,160** |

- **コネクタを待つ間は、DB の接続を持たない。** 試行の記録のトランザクションをコミットしてから呼ぶ（[infrastructure.md](infrastructure.md) の 3.1 節）。これを破ると、コネクタの遅れで api のプールが枯れ、読み取りまで止まる。lint では防げないので、結合テストで「コネクタの呼び出し中に、そのプロセスが開いたトランザクションを持たない」ことを確かめる。
- CDE のサービスは、本体の DB に接続しない（Vault DB だけを使う）。webhook-sender は、署名の秘密を読むために接続する（上の表の workers に含める）。webhook-egress の Lambda は DB に接続しない。
- RDS Proxy は使わない（テナントのコンテキストの `SET LOCAL` で接続が固定されるため。Slack の capacity.md の 2.2 節）。

### 2.4 Vault（CDE）

| 処理 | ピーク | KMS の呼び出し |
| --- | --- | --- |
| カードの受け取り（トークン化） | 550 件/秒 | 1 件ごとにデータキーを作る（`GenerateDataKey`）：550 回/秒 |
| オーソリのための復号 | 500 件/秒 | `Decrypt`：500 回/秒 |
| 合計 | | 約 1,050 回/秒 |

- KMS の対称鍵の暗号操作の上限は、アカウント・リージョンごとの共有で、東京は既定 20,000 回/秒、大阪は既定 10,000 回/秒（2026-09-26 に確認。[AWS のドキュメント](https://docs.aws.amazon.com/kms/latest/developerguide/requests-per-second.html)）。S1 は十分に収まる。
- **大阪へ切り替えたとき**も、S1 の負荷は大阪の上限の約 10% に収まる。
- S3（50,000 件/秒）では、全体で約 11 万回/秒になる。セルごとに cde-live のアカウントを分けるので、上限はセルごとにかかる（1 セル 5,000 件/秒なら約 1.1 万回/秒）。大阪の既定値を超えるので、データキーのキャッシュ（Encryption SDK）か、上限の引き上げを S3 の前に決める。

### 2.5 connector-gateway と、コネクタへの同時接続

- 同時に待つ要求：平常 約 400、コネクタの劣化時は隔壁の上限（2,000/コネクタ/リージョン）まで。
- 1 タスク（2 vCPU / 4 GB）で同時 1,000 件の待ちと、約 300 件/秒の要求の組み立て（復号、署名、電文の変換）を見込む。平常 6 タスク、最大 24 タスク。
- HTTP の接続はコネクタごとに keep-alive のプールを持つ（1 タスクあたりの上限 `maxSockets` 256）。TLS の接続を毎回張らない。
- NAT ゲートウェイは、1 つの IPv4 アドレスあたり、同じ宛先（IP・ポート・プロトコル）へ同時 55,000 接続まで。IP を 8 個まで足して上限を上げられる（[AWS のドキュメント](https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateway-basics.html)）。keep-alive のプールを使えば S1 では届かないが、アクワイアラの宛先が 1 つの IP のときに S2 以降で効く。
- **アクワイアラ側の上限**（契約上の毎秒の件数、同時接続数）が、最も先に効く見込み。S1 のピークの 1.5 倍（750 件/秒）を、最初の接続先との契約の条件にする。

### 2.6 SQS と Worker

| キュー | ピークの流量 | 処理時間 p99 | タスク数（最小 / 最大） |
| --- | --- | --- | --- |
| connector-results（CDE → 本体。コネクタの結果と、カード番号を除いた通知。通知は [ADR-0014](../decisions/0014-connector-inbox.md) の受信箱へ） | 700 件/秒 | 50 ms | 2 / 6 |
| event-build（outbox → Event と配信の予定） | 1,500 件/秒 | 30 ms | 2 / 6 |
| webhook-delivery | 1,500 件/秒＋再送 | 加盟店の応答に依存（タイムアウトは接続 5 秒・全体 15 秒。[events-and-webhooks.md](events-and-webhooks.md) の 5.1 節） | webhook-sender 3 / 12。送信は webhook-egress の Lambda（予約済みの同時実行 500） |
| unknown-outcome（結果不明の照会） | 平常 数件/秒、コネクタの障害時 数百件/秒 | 照会の応答に依存 | 1 / 6 |
| settlement-import、recon（精算ファイルの取り込みと照合） | 日次のバッチ（1 ファイル 数百万行） | — | 1 / 4 |
| payout | 日次のバッチ（加盟店 1 万） | — | 1 / 2 |

- Webhook の再送は 3 日間の指数的な間隔で行う（NFR-006）。SQS の遅延の上限は 15 分なので、15 分より先の再送は DB の予定の表に置き、スケジューラーが時刻になったものを SQS に積む（[events-and-webhooks.md](events-and-webhooks.md)）。
- webhook-sender は、送信先ごとに同時の送信の上限（初期値 10）と、アカウントごとの 1 秒あたりの送信数の上限（初期値 100 件/秒）を持つ（正本は [events-and-webhooks.md](events-and-webhooks.md) の 5.3 節）。応答の遅い加盟店が、他の加盟店の配信を遅らせないようにする。失敗が続く送信先は、別の再送のキューに移す。
- 1 タスク（1 vCPU）で、同時 1,000 件の送信の待ちを見込む（平常の応答 0.3 秒なら 1 タスク約 2,000 件/秒）。

## 4. 余裕の方針

- **1 つの AZ を失っても足りる**ことを、すべての部品の前提にする。平常時の使用率を上限の 2/3 以下に保つ。
- **大阪へ切り替えても足りる**こと。大阪の待機の構成は小さいが、オートスケールの上限とクォータは東京と同じにしておく。切り替えの後、上がりきるまでの数分は、レート制限（[rate-limiting.md](rate-limiting.md)）で受け付けを絞る。
- DB の writer は CPU 50% を上限とみなす。
- 大型セール（年末、ブラックフライデー相当）は、ピークの 2 倍（1,000 件/秒）を 1 時間さばけることを、年 1 回の負荷試験で確かめる。

## 5. キャパシティの運用

| 活動 | 頻度 | 担当 |
| --- | --- | --- |
| 実際の負荷（確定/秒、同時に待つ要求、DB の CPU、残高の集計のロック待ち、KMS の使用率）と、1 節のモデルの比較 | 月次 | Ops |
| モデルの更新と 3 か月先の予測。大口の加盟店の契約・大型セールの予定を反映する | 四半期 | Ops、PM |
| 負荷試験（k6）：モデルの 1 倍・2 倍、AZ の喪失、コネクタの遅延の注入（p99 20 秒）、大口の加盟店への集中、大阪への切り替えの直後 | リリース前、四半期 | QA、Ops |
| パラメーターの見直し（遅いクエリ、VACUUM、プールの待ち、ロック待ち） | 月次 | Dev、Ops |
| 段階を上げる判断（[infrastructure.md](infrastructure.md) の 8 節） | 月次の比較の結果で | Ops、Dev |

負荷試験の結果は、この文書と [infrastructure.md](infrastructure.md) の 4 節に反映する。見積もりと 30% 以上ずれた項目は、原因を調べて記録する。負荷試験は staging と cde-nonprod で行い、模擬のアクワイアラ（遅延と失敗を注入できる）を使う。本物のアクワイアラには負荷をかけない。
