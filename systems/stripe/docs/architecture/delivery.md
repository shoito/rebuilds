# Delivery: Stripe

ブランチ、CI、デプロイ、リリースの流れ。Slack の [delivery.md](../../../slack/docs/architecture/delivery.md) を引き継ぎ、決済に固有の 2 つを足す：**お金を動かすコードのリリースの安全策**と、**CDE の分かれたデプロイの経路**。

| 対象 | 方針 |
| --- | --- |
| ブランチモデル | リポジトリ共通の [ADR-0002](../../../../docs/decisions/0002-trunk-based-development.md)（トランクベース開発） |
| デプロイとマイグレーション、フラグ | Slack の ADR-0022・0026 を引き継ぐ |
| お金を動かすコードのリリース | [ADR-0032](../decisions/0032-release-safety-for-money-moving-code.md) |
| CDE のデプロイの経路と変更管理 | [ADR-0033](../decisions/0033-cde-pipeline-and-change-control.md) |
| AWS の CI/CD の構成 | [infrastructure.md](infrastructure.md) の 6 節 |
| 手順 | [runbooks/deploy-and-rollback.md](../runbooks/deploy-and-rollback.md) |

原則は 3 つ。

- **`main` は常にデプロイできる状態に保つ。**
- **デプロイ（コードを置くこと）とリリース（機能を有効にすること）を分ける。** デプロイは Ops が承認し、リリースは PM が判断する。
- **お金の結果を変えうる変更は、本番のお金を動かす前に、本番のデータで比べる。** 比べ方は 5 節。

## 1. 変更からマージまで

Slack と同じ。

```
changes/YYMMDD-<slug>/ の spec・plan が承認済み
   ▼
ブランチ stripe/YYMMDD-<slug>（エージェントは worktree ごとに 1 本）
   ▼
PR ─▶ PR の CI（2 節）─▶ レビュー（CODEOWNERS、作成者と別の人）
   ▼
merge queue ─▶ squash で main へ
```

- 未完成の振る舞いは release フラグの裏に置く。
- PR の説明には、変更フォルダ、規模、使うフラグに加えて、**お金の区分**（2.2 節）と、**CDE に触れるか**を書く。

### 1.1 リポジトリの中の区分

開発リポジトリは 1 つ（モノレポ）で、CDE のコードを `cde/` に分ける（[ADR-0033](../decisions/0033-cde-pipeline-and-change-control.md)）。

| パス | 中身 | コードオーナー |
| --- | --- | --- |
| `cde/` | vault-ingest、vault-core、connector-gateway、Elements の iframe、CDE の Terraform | CDE のオーナー（Dev のテックリード＋セキュリティの担当） |
| `packages/`（CDE が使うもの） | `money`、コネクタの電文の型、トークンの形式 | 各パッケージのオーナー＋CDE のオーナー |
| `services/ledger`、`services/payments`、`services/payouts` | お金を動かすコード | お金のオーナー（Dev のテックリード）＋ QA |
| その他 | 本体 | 各領域のオーナー |

GitHub のルールセットで、`cde/` と CDE が使うパッケージへの変更に、CDE のオーナーの承認を必須にする。エージェントは `cde/` の PR を作れるが、CDE のアカウントへの経路と、CDE の本番のデータには触れない。

## 2. CI

### 2.1 PR の CI

Slack の delivery.md の 2.1 節の段をすべて持ち、次を足す。目標は 20 分以内。

| 段 | 内容 | 失敗の条件 |
| --- | --- | --- |
| 金額の型 | `Money` 以外で金額を `number` として扱うコードの lint（[ADR-0001](../decisions/0001-platform-and-stack.md)） | 1 件でも |
| 台帳の性質 | 性質ベーステスト：任意の操作の列で、全口座の残高の合計が 0、各口座の残高が仕訳の合計と一致（[ADR-0003](../decisions/0003-double-entry-ledger.md)） | 1 件でも |
| 冪等の性質 | 性質ベーステスト：再送・並行・途中の切断を含む列で、決済と仕訳の数が異なるキーの数と一致（[ADR-0004](../decisions/0004-idempotency.md)） | 1 件でも |
| コネクタの障害注入 | 模擬のアクワイアラで、タイムアウト、応答の欠落、二重の応答、遅延を注入し、結果不明の処理と照会が 1 回だけお金を動かすこと | 1 件でも |
| カード番号の流出 | テストの実行中のログ・DB・メッセージを走査し、Luhn を満たす 13〜19 桁の列がないこと（テスト用のカード番号を含めて、CDE の外に出ていないこと） | 1 件でも |
| ログの項目 | ロガーに許可リスト外の項目、`Pan` 型、要求の本文の全体を渡すコード（[observability.md](observability.md) の 4.2 節） | 1 件でも |
| API の版 | 公開 API の OpenAPI の差分が、版の規則（[api.md](api.md)）に沿う。固定した版の応答が変わらない | 規則の違反 |
| お金の区分 | お金の区分 A（2.2 節）の変更に、5 節の比較の計画が `plan.md` にある | 計画がない |
| CDE（`cde/` の変更時） | 上記に加えて、CDE の SAST、依存の脆弱性、コンテナの検査を厳しい基準（Medium 以上）で行う | Medium 以上 |

### 2.2 お金の区分

変更がお金の結果を変えうるかで、区分を付ける。区分は PR の作成者が付け、お金のオーナーがレビューで確かめる。

| 区分 | 例 | 求めること |
| --- | --- | --- |
| A：お金の結果を変える | 仕訳の規則、手数料の計算、丸め、通貨、Payout の金額の計算、返金・Dispute の計上、コネクタの応答コードの分類、状態遷移 | 5 節の比較（影の実行）と、加盟店単位のカナリア。承認は、お金のオーナーと QA の 2 人 |
| B：お金の流れに触れるが結果は変えない | 性能の改善、ログ、リファクタリング（仕訳の出力が同じ） | 5 節の比較を短く（24 時間）行う。承認は通常どおり |
| C：お金に触れない | ダッシュボードの表示、ドキュメント | 通常どおり |

### 2.3 夜間の CI

- E2E の全件、障害注入の完全版、見た目の回帰（Slack と同じ）。
- staging と cde-nonprod に対する負荷試験と DAST。
- **台帳の再計算**：staging の全仕訳から残高を再計算し、集計と比べる。

夜間の CI が 2 日続けて失敗している間は、release フラグを広げない。

## 3. ビルドと成果物

- `main` へのマージごとに、1 回だけビルドする（Slack と同じ）。
- 本体のイメージは shared の ECR へ、CDE のイメージは **CDE 用のワークフローだけが** cde-shared の ECR へ push する。CDE のイメージには、ベースイメージの固定（digest）、SBOM、ビルドの来歴（provenance）を必須にし、デプロイの前に署名を検証する。
- リリースの識別子は `<日付>-<コミットの短いハッシュ>`。

## 4. デプロイ

### 4.1 環境の昇格

```
本体：main ─▶ dev（自動）─▶ staging（自動、E2E・スモーク・デプロイ中の k6）─▶ prod（Ops の承認）
CDE ：main ─▶ cde-nonprod（自動）─▶ cde-test（CDE の承認）─▶ cde-live（CDE の承認、cde-test で 24 時間後）
```

- prod のデプロイは、平日の 10〜17 時。金曜の 15 時以降、月末・月初の 2 営業日（Payout と締めの集中）、年末年始と大型セールの前後は、修正以外のデプロイをしない。
- CDE のデプロイは、平日の 10〜16 時。変更記録の番号と、2 人の承認を必須にする（6 節）。
- エラーバジェットを使い切っている間は、修正以外のデプロイをしない。

### 4.2 デプロイの順序

本体と CDE の間の API（PrivateLink の呼び出しと `connector-results` のメッセージ）は、**新旧の両方と互換を保つ**。どちらを先にデプロイしても壊れないようにし、順序への依存を作らない。

| 順 | 対象 | 方式 |
| --- | --- | --- |
| 1 | マイグレーション（expand） | 1 回だけ実行する ECS タスク（`migrator`）。台帳のテーブルへの変更は、5.3 節の追加の規則に従う |
| 2 | relay、workers、webhook-router・sender・scheduler、connectors。webhook-egress の Lambda は新しい版を発行して別名を切り替える | ローリング（`minimumHealthyPercent` 100%） |
| 3 | api | ECS のネイティブな blue/green のカナリア（10% → 100%）。アラームで自動ロールバック |
| 4 | dashboard、checkout | blue/green |
| 5 | CDE（別の経路。6 節） | vault-core → vault-ingest → connector-gateway。それぞれ blue/green。Elements の iframe の静的ファイルは最後に差し替える |

- **デプロイの切り替えで、処理中の決済を落とさない。** api の登録解除の遅延を 60 秒、`stopTimeout` を 120 秒にし、コネクタを待っている要求を終えてから止める（[capacity.md](capacity.md) の 3.3 節）。それでも途中で止まった試行は、結果不明として照会で片付く。
- api の blue/green の自動ロールバックのアラームには、5xx の率に加えて、**オーソリの技術的な成功率と、結果不明の発生率**を入れる。新しいコードがコネクタとのやり取りを壊したとき、5xx が出なくても止められる。

## 5. リリース（お金を動かす変更の安全策）

[ADR-0032](../decisions/0032-release-safety-for-money-moving-code.md) の要点。

### 5.1 流れ

```
デプロイ済み（フラグ無効）
   │ QA：staging でフラグを有効にし、Proof を満たすことを確認
   ▼
影の実行（区分 A・B）：本番の実際の取引で、新しい計算を並べて実行し、結果を比べる
   │ 差 0 件（または説明がつく差だけ）で、決めた期間・件数を満たす
   ▼
社内の加盟店（live、社内のカード）─▶ 選んだ加盟店（同意を得た低リスクの加盟店）
   ─▶ 加盟店の 1% ─▶ 10% ─▶ 50% ─▶ 100%
   各段で 24 時間以上、かつ 1 回以上の日次の照合と Payout を通す
   ▼
100% で 2 週間 ─▶ 古いコードとフラグを消す
```

### 5.2 影の実行（dual-run）

- 新しい計算（仕訳の規則、手数料、Payout の金額など）を、本番の実際の取引に対して、**古い計算と並べて実行する。** 新しい計算の結果は、台帳に書かず、比較用の表（`shadow_results`）に書く。
- 比べるもの：仕訳の明細（口座、方向、金額、通貨）、手数料、Payout の金額、状態の遷移。
- 差があれば、比較のダッシュボードに出し、1 件ずつ理由を付ける。理由のない差が 1 件でもあれば、先へ進めない。
- 期間の目安：区分 A は 7 日かつ 10 万件以上、区分 B は 24 時間。月末の締めや Payout の日を 1 回以上含める。
- 影の実行は、要求の処理時間に効かないよう、outbox から非同期に行う。
- 影の実行ができない変更（コネクタへの送信の形式の変更など、外部に副作用があるもの）は、模擬のアクワイアラでの比較と、社内の加盟店での実際の取引で代える。

### 5.3 台帳とお金のデータの変更

- 台帳は追記のみ（[ADR-0003](../decisions/0003-double-entry-ledger.md)）。**過去の仕訳を書き換えるマイグレーションとバックフィルは作らない。** 誤りは、訂正の仕訳（逆の仕訳＋正しい仕訳）で直す。
- 訂正の仕訳を大量に作るときは、専用の「台帳の訂正」のジョブで行う：
  1. 訂正の一覧を、乾いた実行（dry-run）で作り、口座ごとの影響の合計を出す。
  2. お金のオーナーと経理の担当の 2 人が承認する。
  3. 冪等キー（訂正の ID）付きで追記する。途中で止まっても、再実行で二重にならない。
  4. 実行の後に、全口座の再計算を行い、影響の合計が 1. と一致することを確かめる。

### 5.4 加盟店単位のカナリア

- **割り当ての単位は加盟店のアカウントにする。** 要求ごとの割合で振り分けない。同じ加盟店の取引が新旧の計算に分かれると、その加盟店の照合と問い合わせの説明がつかなくなる。
- 判定は `hash(flag_name + account_id) mod 100` をアプリで計算する（Slack の ADR-0026 と同じ方式で、単位を加盟店にする）。
- 社内の加盟店と、個別に指定した加盟店の許可リスト、除外リスト（大口の加盟店は最後にする）を持つ。
- live と test は別に広げる。test（テスト環境）を先に 100% にし、加盟店の統合の不具合を先に見つける。

### 5.5 お金の不変条件のガード（自動で止める）

各段の間、次のどれかが起きたら、フラグを自動で切り、PM と Ops に知らせる。AppConfig のデプロイ戦略のアラームに、次を入れる。

| ガード | 条件 |
| --- | --- |
| 台帳の整合 | 日次・時間ごとの再計算で差が出た |
| 影の実行の差 | 理由のない差が 1 件以上 |
| オーソリの技術的な成功率 | フラグの有効な加盟店で、無効な加盟店より 1 ポイント以上低い |
| 結果不明の発生率 | フラグの有効な加盟店で、平常の 2 倍 |
| 照合の不一致 | フラグの有効な加盟店に、T+1 で新しい不一致が出た |
| 返金・Dispute の失敗 | フラグの有効な加盟店で増えた |

### 5.6 判断

| 判断 | 誰が |
| --- | --- |
| staging での受け入れ | QA |
| 影の実行の結果の承認（区分 A） | お金のオーナーと QA |
| 社内 → 選んだ加盟店 → 1% に進める | PM（QA の受け入れと影の実行の承認が前提） |
| 10% → 100% に進める | PM。Ops が指標とガードに問題がないことを確かめる |
| 止める・戻す | 誰でもよい。切ったら、インシデントの要否を Ops が判断する |

## 6. CDE のデプロイと変更管理

[ADR-0033](../decisions/0033-cde-pipeline-and-change-control.md) の要点。PCI DSS の要件 6.5（変更の管理）に沿う。

- **変更記録**：CDE の本番（cde-test・cde-live）へのデプロイごとに、PR に変更記録を付ける。中身は、変更の理由、セキュリティへの影響、承認者、テストの証跡（CI の結果、cde-nonprod での確認）、戻し方。変更記録は GitHub の Issue（Type：Task、ラベル `pci:change`）とし、デプロイのワークフローが番号を検査する。
- **承認**：Dev のテックリードと、セキュリティの担当の 2 人。どちらも作成者と別の人。GitHub の Environments（`cde-test`、`cde-live`）の必須のレビュー担当者にする。人が 1 人しかいないときの事後確認（[ADR-0004](../../../../docs/decisions/0004-agent-prs-via-github-app.md)）は、CDE では使わない。2 人がそろわない間は、CDE の本番へデプロイしない。
- **役割の分離**：CDE のコードを書く人と、CDE の本番の権限を持つ人を、同じ変更で兼ねない。本番と本番前の環境で、役割を分ける（PCI DSS 要件 6.5.4）。
- **ホットフィックス**：セキュリティの修正は、時間帯の制限を受けない。ただし、2 人の承認と cde-nonprod での自動の検査は省かない。
- **重要な変更の後の確認**：ネットワーク・鍵・認証に関わる変更の後は、該当する PCI DSS の統制が働いていることを確かめ、変更記録に残す（要件 6.5.2）。
- **ロールバック**：1 つ前のイメージの digest で再デプロイする。フラグは、CDE の中では ops フラグ（コネクタの無効化など）だけを使い、release フラグで振る舞いを切り替えない（CDE の振る舞いの組み合わせを増やさない）。

## 7. ホットフィックス

Slack と同じく、まずフラグで止め、修正は `main` への PR で入れる（forward fix）。フラグで止められず修正も間に合わないときは、1 つ前のイメージで再デプロイする。マイグレーションは戻さない。お金の結果を誤らせた修正は、修正のデプロイとは別に、5.3 節の訂正の仕訳で過去の分を直す。

## 8. 指標

DORA の 4 指標（Slack と同じ目標）に加えて、次を見る。

| 指標 | 目標 |
| --- | --- |
| お金の区分 A の変更のうち、影の実行で差が見つかった割合 | 記録する（目標は置かない。影の実行が役に立っていることの確認） |
| 5.5 節のガードで自動で止まった回数 | 記録し、振り返る |
| CDE のデプロイの頻度とリードタイム | 週 1 回以上、マージから 3 営業日以内 |
| CDE の変更記録の不備（監査での指摘） | 0 件 |
