# ADR-0004: すべての書き込みを冪等にする

## Context

決済の API では、ネットワークの切断やタイムアウトのあとに、加盟店が要求を再送することがよくある。再送で二重に請求すれば、そのまま顧客の損失になる。

本家 Stripe は `Idempotency-Key` ヘッダーで、同じキーの要求に 24 時間のあいだ最初の結果を返す（[Stripe の文書](https://docs.stripe.com/api/idempotent_requests)）。

冪等であるべきなのは、加盟店からの要求だけではない。内部の再試行（SQS の再配送）や、コネクタへの再送でも、お金が 2 回動いてはならない。

## Options

1. **API・内部・コネクタの 3 層で、それぞれ冪等キーを持つ**
2. **API の入口だけで冪等にする**

## Decision

1 を採用する。

| 層 | キー | 保存と振る舞い |
| --- | --- | --- |
| API | 加盟店の `Idempotency-Key`（アカウント × 環境 × キー） | 最初の要求の本文の要約と、応答（状態コード・本文）を 24 時間保存する。同じキーで本文が違えば 400 を返す。処理中の同じキーには 409 を返す |
| 内部 | 操作ごとに決まる ID（例：`capture:{payment_intent_id}:{attempt}`） | 仕訳と状態の遷移を、その ID の一意制約で 1 回に限る |
| コネクタ | アクワイアラに送る取引の参照番号 | 再送のときは同じ参照番号を使い、アクワイアラ側でも重複を拒否させる。結果が不明のときは、参照番号で照会してから次の手を決める |

- `Idempotency-Key` のない書き込みの要求も受け付ける（本家と同じ）。SDK は、既定でキーを付けて送る。
- 2 は、内部の再試行とコネクタの再送での二重の処理を防げない。

## Consequences

- 良くなること：
  - どの層で再試行が起きても、お金は 1 回しか動かない。
- 引き受けるコスト：
  - 冪等キーの保存に、書き込みの要求ごとに 1 行が要る。24 時間で消す（パーティションを日ごとに切り、`DROP` する）。

## Confirmation

- 性質ベーステスト：任意の要求の列（同じキーの再送、並行の同時送信、途中での切断を含む）で、仕訳の数と決済の数が、異なるキーの数と一致する。
- 結合テスト：同じキーで本文が違う要求に 400、処理中の同じキーに 409 を返す。
