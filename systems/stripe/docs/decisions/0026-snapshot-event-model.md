# ADR-0026: Event は作成時点のスナップショットとして不変に保存し、MVP は snapshot events だけを出す

## Context

本家の Event には 2 種類ある（[イベントとの連携](https://docs.stripe.com/event-destinations)、2026-09-26 に確認）。

- **snapshot events（v1）**：`data.object` に、作成の時点のリソースの全体を含む。Event の `api_version` は作成の時点のアカウントの既定の版で固定され、Event は作成後に変わらない。エンドポイントが版を指定すれば、その版で描画して送る。
- **thin events（v2）**：リソースの ID と種類だけの軽い通知。受け手は API で最新の状態を取り直す。版に依存しない。v2 の API のリソースが出すもので、v1 のリソースへの対応はプライベートプレビュー。

本システムの公開 API は本家の v1 の形に寄せる（[api.md](../architecture/api.md)）。Event をどう保存し、版ごとの形をどう作るかを決める必要がある。

- 版ごとに描画した本文をすべて保存すると、容量が版の数だけ増える。
- 描画を後から行うと、変換のコードの変更で、過去の Event の本文が変わりうる。

## Options

1. **正規形（内部の最新の型）と `api_version` を保存し、送信と取得のたびに版の変換で描画する**
2. **作成の時点で、必要な版すべてで描画した本文を保存する**
3. **thin events だけにする**
4. **snapshot と thin の両方を MVP で出す**

## Decision

1 を採用し、MVP では snapshot events だけを出す。

- `events` には、状態の遷移と同じトランザクションで、リソースの正規形・`previous_attributes`・`api_version`（作成の時点のアカウントの既定の版）を書く。
- 送信と API での取得のときに、[api.md](../architecture/api.md) の版ごとの変換で、エンドポイントの版（なければ Event の版）へ描画する。
- **公開した版の変換は書き換えない。** 誤りを直すときは、新しい版として出す。これで、同じ Event を同じ版で描画すると、いつでも同じ本文になり、「Event は作成後に変わらない」という本家の約束を守れる。
- 2 は、アカウントが版の違うエンドポイントを持つと（本家の上限で最大 4 種類の版）、容量が数倍になる。
- 3 は、v1 の形の API を使う加盟店にとって、本家の既定の体験（`data.object` で処理できる）と違う。
- 4 は、thin の需要（版に依存しない通知、v2 の API）が MVP にない。エンドポイントに `event_payload`（`snapshot` / `thin`）を後から足せるよう、配信の表の設計を分けておく。

## Consequences

- 良くなること：
  - 容量は版の数に比例しない。
  - 本家と同じく、加盟店は `data.object` だけで多くの処理ができ、`previous_attributes` で変更点を見られる。
- 引き受けるコスト：
  - 版の変換の不変性を、テストとレビューで守り続ける必要がある。
  - 送信のたびに描画の CPU がかかる（同じ Event を複数のエンドポイントへ同じ版で送るときは、描画の結果をその送信の処理の中で使い回す）。
  - `data.object` は作成の時点の値なので、処理の時点では古いことがある。加盟店には、必要なら API で取り直すよう案内する（本家と同じ）。

## Confirmation

- スナップショットテスト：公開した各版について、代表的な Event の描画の結果を固定し、変換のコードの変更で結果が変わったら CI を失敗させる。
- 性質ベーステスト：任意の状態の遷移の列で、コミットした遷移 1 つにつき Event がちょうど 1 つあり、`data.object` がコミットの時点の状態と一致する。
- レビューの観点：公開済みの版の変換を変える PR は、Dev の承認を必須にする（CODEOWNERS）。
