# ADR-0033: CDE のコードは同じリポジトリの `cde/` に置き、ビルドとデプロイの経路と承認を本体から分ける

## Context

CDE（[ADR-0005](0005-pci-scope-segmentation.md)、[ADR-0029](0029-multi-account-and-cde-layout.md)）のシステムへの変更は、PCI DSS の要件 6.5 の変更管理（変更の記録、承認、テスト、戻し方、本番と本番前の役割の分離）に従う必要がある。

一方で、本体は 1 日に何度もデプロイし、エージェントが多くの PR を作る（リポジトリ共通の ADR-0002・0004）。CDE の統制を本体にまで広げると、本体の開発が遅くなる。本体の経路から CDE に触れられると、CDE の統制に穴があく。

CDE は、本体と共通の型（`packages/money`、コネクタの電文の型、トークンの形式）を使う。

## Options

1. **同じリポジトリ（モノレポ）の `cde/` に置き、ワークフロー・ECR・デプロイのロール・承認を分ける**
2. CDE のコードを別のリポジトリに分ける
3. 同じリポジトリ・同じ経路で、CDE のデプロイにだけ承認を足す

## Decision

1 を採用する。流れは [delivery.md](../architecture/delivery.md) の 1.1・3・4・6 節、構成は [infrastructure.md](../architecture/infrastructure.md) の 6 節にある。

- **コードの置き場所**：`cde/` に CDE のサービスと Terraform を置く。GitHub のルールセットで、`cde/` と CDE が使うパッケージへの変更に、CDE のオーナー（Dev のテックリードとセキュリティの担当）の承認を必須にする。
- **ビルド**：CDE 用のワークフロー（`cde-build.yml`・`cde-deploy.yml`）だけが、cde-shared の ECR へ push できる。ベースイメージの固定、SBOM、来歴、署名を必須にし、デプロイの前に署名を検証する。
- **デプロイのロール**：CDE のアカウントのデプロイ用のロールは、OIDC の条件で、`environment:cde-*` かつ `job_workflow_ref` が `cde-deploy.yml` のときだけ引き受けられる。本体の CI のロールからは、SCP で CDE のロールを引き受けられない。
- **承認と変更記録**：cde-test と cde-live へのデプロイには、作成者と別の 2 人（Dev のテックリード、セキュリティの担当）の承認と、変更記録（理由、セキュリティへの影響、テストの証跡、戻し方）を必須にする。人が足りないときの事後確認（リポジトリ共通の ADR-0004）は、CDE には使わない。
- **役割の分離**：同じ変更で、CDE のコードを書く人と CDE の本番の権限を使う人を兼ねない。エージェントは CDE の PR を作れるが、承認と CDE の本番への経路を持たない。
- **Terraform**：CDE のルートモジュールの状態ファイルは cde-shared のバケットに置き、apply のロールも CDE 専用にする。
- 2 は、アクセス権の分離が最も明確になる。ただし、共通の型を別のリポジトリへ公開する手間と、本体と CDE の契約のテストが別々のリポジトリに分かれる不便がある。1 でも、ルールセット・ワークフロー・OIDC の条件で、書き込みとデプロイの権限は分けられる。題材ごとに開発リポジトリを 1 つ持つ方針（リポジトリ共通の ADR-0005）にも合う。
- 3 は、本体のロールが CDE に届く構成を残す。

## Consequences

- 良くなること：
  - 本体のデプロイの頻度を落とさずに、CDE の変更だけを PCI DSS の変更管理に従わせられる。
  - 本体と CDE の契約（PrivateLink の API、`connector-results` のメッセージ）を、同じ PR でテストできる。
- 引き受けるコスト：
  - CDE の変更は、2 人の承認がそろうまで本番に出ない。人が少ない間は、CDE のリードタイムが延びる（目標：マージから 3 営業日以内）。
  - CDE が使うパッケージを変えると、CDE の承認と CDE の経路のデプロイが要る。CDE が使うパッケージを最小に保つ。
  - モノレポのルールセットと OIDC の条件の設定を誤ると、分離が崩れる。設定自体を Terraform（GitHub のプロバイダ）で管理し、変更を CDE の承認の対象にする。

## Confirmation

- CI：`cde/` と CDE が使うパッケージを変える PR に、CDE のオーナーの承認がなければマージできない（ルールセットの設定を、四半期ごとに確認する）。
- IAM：CDE のデプロイ用のロールの信頼ポリシーに、`job_workflow_ref` と `environment` の条件があることを、IAM Access Analyzer のカスタムの検査で確かめる。
- デプロイのワークフロー：変更記録の番号と、2 人の承認がなければ失敗させる。
- 監査：CDE の本番へのデプロイの一覧と変更記録を、四半期ごとに突き合わせ、記録のないデプロイが 0 件であることを確かめる。
