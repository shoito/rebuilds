# ADR-0007: API のバージョンは日付で持ち、アカウントに固定し、変更モジュールで古いバージョンの形を保つ

## Context

intent.md は「API のバージョンを固定した加盟店は、そのバージョンの振る舞いを受け続ける」を守るべき振る舞いにしている。決済の組み込みは、一度動いたら加盟店が長く触らないことが多く、互換性を壊す変更を強いると、決済が止まる。

本家 Stripe の仕組み（2026-09-26 に確かめた）：

- バージョンは `YYYY-MM-DD.<名前>`。2024-09-30.acacia から、毎月の互換性を保つバージョンと、年 2 回の互換性を壊す大きなリリース（acacia、basil、clover、dahlia）を出している。現在は 2026-08-26.dahlia（[Versioning](https://docs.stripe.com/api/versioning)、[Changelog](https://docs.stripe.com/changelog)）。
- アカウントの既定のバージョンは、最初の API 要求の時点のバージョンに固定される。`Stripe-Version` 見出しで要求ごとに上書きでき、SDK はリリース時点のバージョンを送る（[API upgrades](https://docs.stripe.com/upgrades)）。
- Webhook のエンドポイントは、作成時のバージョンでイベントを描く。
- 内部では、互換性を壊す変更ごとに「バージョンの変更モジュール」を持ち、応答を最新の形から要求のバージョンまで遡って変換する（[APIs as infrastructure](https://stripe.com/blog/api-versioning)）。

Slack の再構築は URL の大きなバージョン（`/v1`、`/v2`）を選び、日付のバージョンを「今の規模に合わない」として採らなかった（Slack の ADR-0030）。

## Options

1. URL の大きなバージョン（`/v1`、`/v2`）。古いバージョンは期限を決めて止める
2. 日付のバージョンをアカウントに固定し、変更モジュールで変換する（本家と同じ）
3. バージョンを持たず、互換性を壊す変更をしない

## Decision

2 を採用する。詳細は [api.md](../architecture/api.md) の 6 節にある。

- **バージョンは `YYYY-MM-DD.<名前>`。** 名前は本システムの大きなリリースごとに付け、本家の名前（acacia など）は使わない。同じ名前だと、本家の同じバージョンと互換だと誤解されるため。
- **アカウントの既定のバージョンは、最初の API 要求で固定する。** `<Brand>-Version` で要求ごとに上書きできる。SDK はリリース時点のバージョンを送る。Webhook のエンドポイントは作成時にバージョンを持つ。
- **互換性を壊す変更だけがバージョンを作る。** 項目・エンドポイント・列挙値の追加は全バージョンに出す。月ごとの定期のリリースは持たず、変更がある月にだけバージョンを切る。
- **ハンドラーとサービス関数は最新の形だけを扱う。** 応答は変更モジュールを新しい順に当てて古いバージョンの形にする。形で表せない振る舞いの違いは、モジュールの ID で参照する分岐にし、日付の比較をコードに散らさない。
- **Event は最新の形で保存し、配信・取得のときにバージョンへ変換する。**
- **古いバージョンは止めない。** 止めるなら新しい ADR で決める。
- 1 は、決済の組み込みに大きな移行を強い、止めた日に加盟店の決済が止まる。本家に寄せる題材の目的にも合わない。Slack で 1 を選んだ理由（変換の層のコスト）は、この題材では製品の価値そのものなので引き受ける。
- 3 は、誤った設計を直せなくなる。

## Consequences

- 良くなること：
  - 加盟店は、自分の都合でバージョンを上げられる。古いバージョンの加盟店の決済が、本システムの変更で止まらない。
  - 新しい機能の開発では、古いバージョンをほぼ意識しなくてよい（変更モジュールに閉じる）。
- 悪くなること、引き受けるコスト：
  - 変更モジュールの保守と、全バージョンにわたるテストのコスト。モジュールの数に比例して、応答の変換の時間が増える。
  - 振る舞いの分岐（`sideEffects: true`）は、変換だけで済まず、サービス関数を複雑にする。互換性を壊す振る舞いの変更は、Dev（テックリード）の承認を要する。
  - バージョンごとの OpenAPI と変更履歴を生成する道具を作る。

## Confirmation

- 性質ベーステスト：全バージョンについて、最新の形のオブジェクトを変換した結果が、そのバージョンの OpenAPI のスキーマに合う。
- CI：最新のバージョンの OpenAPI で互換性を壊す差分が出たとき、対応する変更モジュールがなければ失敗させる。
- lint：`packages/api-versions` の外で、バージョンの日付の文字列を比較するコードを禁止する。
- 合成監視：最新のバージョンと、最も古いバージョンの両方で、決済の一連の流れを回す。
