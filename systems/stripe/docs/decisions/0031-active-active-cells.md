# ADR-0031: S3 で、加盟店をセルに固定し、セルごとに主のリージョンを東京か大阪に置いて active-active にする

S3（確定 50,000 件/秒、加盟店 100 万）に向けた計画。S2 を運用して得た数字で見直し、S3 への移行を始めるときに accepted にする。

## Context

S1・S2 は、東京で決済を受け、大阪を待機に置く（[ADR-0030](0030-payments-disaster-recovery.md)）。S3 では次の問題が出る。

- **可用性の目標**：NFR-001 は S3 で 99.995%（30 日で約 2 分）。リージョンの切り替えの 1 時間を、全加盟店が同時に受けることはできない。
- **縦に伸ばす限界**：台帳を加盟店のハッシュで分割しても（S2）、アプリの群れ・CDE・デプロイの失敗の影響範囲は全体のまま。
- **大阪の待機の構成**が、使わない費用として大きくなる。
- **大口の加盟店**が、共有の資源を占有しうる。

Slack は S3 でセル構成を提案している（Slack の ADR-0023）。決済では、1 つの加盟店のお金（台帳の口座、冪等キー、残高）を 2 つの場所で同時に書くと、一貫性を守るのが難しい。

## Options

1. **マルチライターの DB**：Aurora DSQL のマルチリージョンのクラスタ（東京・大阪・ソウルの組で提供。[AWS の発表](https://aws.amazon.com/about-aws/whats-new/2026/07/amazon-aurora-dsql-adds-multi-region-clusters-four-more-regions/)）で、同じデータを両方のリージョンで書く
2. **セル構成。加盟店を 1 つのセルに固定し、セルごとに主のリージョンを持つ。** 東京を主とするセルと大阪を主とするセルを並べ、全体として両方のリージョンで決済を受ける
3. S2 の構成のまま、縦に伸ばし続ける

## Decision

2 を採用する（提案）。構成の概要は [infrastructure.md](../architecture/infrastructure.md) の 10 節。

- **セルの中身**：本体（api、workers、Webhook の配信など、Aurora）と CDE（Vault、Connector Gateway）の一式。セルごとに prod と cde-live の AWS アカウントの組を持つ。
- **加盟店のアカウントを 1 つのセルに固定する。** 台帳の口座、残高、冪等キー、Payout は、セルの中で閉じる。1 つの加盟店の書き込みは、常に 1 つのリージョン（そのセルの主）で行う。
- **セルの主のリージョンを、東京と大阪に半分ずつ置く。** 各セルの Aurora Global Database の二次は、相手のリージョンに置く。
- **リージョンの障害**では、止まったリージョンを主とするセルだけを、相手のリージョンへ切り替える。失った範囲の回復は ADR-0030 と同じ手順を、セルごとに行う。もう一方のリージョンを主とするセル（全体の約半分）は、影響を受けない。
- **各リージョンは、相手のセルを引き受ける余裕を持つ**（平常時の使用率 50% 以下）。待機の構成の費用は、S1・S2 の「使わない大阪」から「両方で使う余裕」に変わる。
- **セルの外（Global）**：API キー → アカウント → セルの対応表、ダッシュボードのログインとセッション、審査の状態。両方のリージョンで読めるようにする。セルは自分が持たないアカウントの要求に 421 を返し、ルーターは対応表を取り直す。
- **大口の加盟店**には専用のセルを割り当てる。
- **デプロイはセルを順に進める**：社内の加盟店のセル → 小さなセル → 残り。お金の区分 A の変更（[ADR-0032](0032-release-safety-for-money-moving-code.md)）は、1 つのセルで影の実行と照合を 1 日以上通してから、次のセルへ進める。
- 1 は、1 つの加盟店を両方のリージョンで書ける点で勝る。ただし、台帳が頼る PostgreSQL の機能（遅延制約のトリガー、RLS）との互換と、ソウルの witness に置かれるデータの扱いが **未検証** である。台帳の正しさを DB の新しい一貫性のモデルに預けるのは、S2 の運用の実績の後に再評価する。
- 3 は、影響範囲と可用性の目標を解決しない。

## Consequences

- 良くなること：
  - リージョンの障害の影響が、約半分のセルに限られる。
  - セルの追加で規模を伸ばせる。1 つのデプロイの失敗が、1 つのセルにとどまる。
  - 大阪の資源を、待機ではなく実際の処理に使う。
- 引き受けるコスト：
  - Global（対応表）が全体の単一障害点になりうる。セルとルーターは対応表をキャッシュし、Global が止まっても既存の加盟店の決済を続けられるようにする。新規の加盟店の登録と、セル間の移動は止まってよい。
  - セルごとに CDE を持つので、PCI DSS の範囲のアカウントがセルの数だけ増える。監査の証跡の集め方を、セルをまたいで自動化する必要がある。
  - 1 つの顧客のカードが、複数のセルに別々に保存される。加盟店をまたいでカードを共有する機能（本家の Link に相当）は、MVP の範囲外で、S3 でも扱わない。
  - セル間の加盟店の移動は、結果不明の試行が残っていないこと、台帳の残高が移動の前後で一致することを条件にする。手順は S3 の前に runbook にし、staging で訓練する。
  - KMS の暗号操作の上限はセル（アカウント）ごとにかかるが、大阪の既定値（10,000 回/秒）を超えうる（[capacity.md](../architecture/capacity.md) の 2.4 節）。

## Confirmation

S3 に入る前に、staging に 2 つのセル（主：東京、主：大阪）と Global を作り、次を確かめる。

- 大阪を止めたとき、大阪を主とするセルだけが切り替わり、東京を主とするセルの合成監視が成功し続ける。
- 切り替えたセルで、失った範囲の決済が照会で回復し、台帳の整合と照合の不一致が 0 件になる。
- Global を止めても、既存の加盟店の決済が続く。
- 加盟店の移動の訓練で、書き込みの停止が 1 分以内に収まり、移動の前後で残高が一致する。

本番では、セルごとの SLO をダッシュボードで並べて見る（[observability.md](../architecture/observability.md)）。
