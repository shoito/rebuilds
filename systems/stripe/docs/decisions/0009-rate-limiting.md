# ADR-0009: レート制限は本家の単位と値に寄せ、Slack の層と GCRA の仕組みで行う

## Context

共有の API と DB（ADR-0002 の共有スキーマ）で、1 つの加盟店の急増や不具合が、他の加盟店の決済を遅らせてはならない。一方で、正当な決済を 429 で断れば、そのまま加盟店の売上の損失になる。

本家 Stripe は、アカウントごとに全体の制限（本番 1 秒 100、サンドボックス 1 秒 25）、エンドポイントの既定（1 秒 25）、個別の制限（PaymentIntent の更新はオブジェクトごとに 1 時間 1,000 回、Search は 1 秒 20、Payouts の作成は 1 秒 15・同時 30 など）、同時実行の制限を持ち、429 に `Stripe-Rate-Limited-Reason` を付ける。同じオブジェクトへの並行の操作は `lock_timeout` の 429 になる（[Rate limits](https://docs.stripe.com/rate-limits)、2026-09-26 に確かめた）。

Slack の再構築では、層・主体・テナントの枠組みを決め、Valkey の GCRA で数え、Valkey の障害時は一般の制限を通し、認証の制限を止めるとした（Slack の ADR-0029）。

## Options

1. 本家の単位と値を初期値にし、Slack の仕組み（層、Valkey の GCRA、障害時の振る舞い）で実装する
2. Slack の tier（読み取り・書き込みなど）とトークンごとの制限をそのまま使う
3. API Gateway（AWS）の使用量プランに任せる

## Decision

1 を採用する。詳細は [rate-limiting.md](../architecture/rate-limiting.md) にある。

- **単位はアカウント × 環境。** キーごとには分けない（本家と同じ）。全体 → エンドポイント → 同時実行 → リソースに固有、の順に判定する。
- **値は本家の公開値を初期値にする。** ただし、決済の経路（PaymentIntent の作成・確定・キャプチャ・取り消し、Refund の作成）には、エンドポイントの既定（1 秒 25）をかけず、全体の枠だけにする。本家がこれらにどの値をかけているかは未検証で、正当な決済を断る危険を避ける。
- **同時実行の値は本家が公開していないので、本システムで決める**（本番は同時 50、一覧と `expand` は操作ごとに同時 10）。
- **応答は本家に合わせる。** 429 と `<Brand>-Rate-Limited-Reason`。ロック待ちは `lock_timeout` の 429 で、理由の見出しを付けない。加えて `Retry-After` と `<Brand>-Should-Retry: true` を付ける。
- **レート制限を冪等の層の前に置く**（本家と同じ）。429 は冪等の記録を残さない。
- **計数は Valkey の GCRA、キーはアカウント × 環境のハッシュタグ**（Slack と同じ）。Valkey の障害時は、決済の API を止めない側（fail-open）に倒し、認証の制限は止める側に倒す。
- **プランで変えない。** 緩和はアカウント × 環境の上書きだけで、Ops が承認し、監査ログに残す。
- **読み取りの割当（取引 1 件あたり 500）は、MVP では計測と通知だけ。**
- 2 は、本家の文書と加盟店の期待に合わない。3 は、アカウント × 環境の単位、同時実行、ロック待ち、Valkey の障害時の振る舞いを表せない。

## Consequences

- 良くなること：
  - 加盟店が本家で得た知識（上限の値、理由の見出し、`lock_timeout` の再試行）がそのまま通じる。
  - Slack の実装と運用を使い回せる。
- 悪くなること、引き受けるコスト：
  - 決済の経路にエンドポイントの制限をかけないので、1 つの加盟店が全体の 100 まで決済の作成に集中できる。容量（[capacity.md](../architecture/capacity.md)）はこれを前提にする。
  - 判定のたびに Valkey へ 1 往復する。NFR-002 の遅延の予算に含める。
  - Valkey の障害中は、一般の制限が緩くなる。

## Confirmation

- 性質ベーステスト：許可された件数が上限を超えない。同時実行の数が上限を超えない。
- 表駆動テスト：理由の見出し・`<Brand>-Should-Retry`・`Retry-After` の表。
- 結合テスト：Valkey の停止中に決済の API が通る。同じ PaymentIntent への並行のキャプチャで、仕訳が 1 回だけ。
- レビュー：各領域の文書の上限の値が、rate-limiting.md の 4 節と一致している。
