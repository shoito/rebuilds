# ADR-0014: コネクタからの通知は受信箱に記録してから、重複と順序を解決して反映する

## Context

決済の状態の多くは、コネクタからの非同期の通知で進む。

- 3D セキュアの認証の結果、非同期のキャプチャ・返金の結果
- コンビニの入金の速報・確報、期限切れ
- 銀行振込の着金の明細
- Dispute（照会・チャージバック・決定）、早期の不正警告（EFW）

通知は Webhook・日次のファイル・照会の応答など、コネクタごとに違う手段で届く。同じ通知が重複して届き、順序が入れ替わり、こちらの記録にない取引を指すことがある。受けた通知をその場で状態に反映すると、次のことが起きる。

- 処理の途中で落ちると、通知を失う（コネクタが再送しない場合）。
- 重複した通知で、お金が 2 回動く。
- 後から届いた古い通知で、状態が戻る。

## Options

1. **受信箱（`connector_inbox`）に生のまま記録してから、ワーカーが重複を除き、順序を解決して反映する**
2. **受けた HTTP の要求の中で、そのまま状態を更新する**
3. **通知を使わず、定期的な照会（ポーリング）だけで状態を進める**

## Decision

1 を採用する。

- **受けたらまず記録する。** Webhook の受信口は、署名（コネクタごとの方式）を検証し、`connector_inbox` に生のデータを INSERT してから 2xx を返す。ファイルは S3 に置き、行ごとに受信箱へ展開する。反映は受信口で行わない。
- **重複を除く。** `(connector, livemode, 通知の ID)` に一意制約を付ける。通知の ID がないコネクタは、内容の要約（ハッシュ）を使う。
- **反映は、SQS 経由のワーカーが遷移関数を通して行う**（[ADR-0010](0010-payment-intent-state-machine.md)）。遷移・仕訳・Event を 1 トランザクションで書き、受信箱の行に反映済みの印を付ける。同じ通知が 2 回反映されても、遷移関数の冪等（同じ結果への遷移は何もしない）で 1 回になる。
- **順序を解決する。** 表にない遷移になる通知（前の通知がまだ来ていない）は保留にし、前の通知の反映の後に再び試す。一定時間（既定 24 時間）解決しなければ運用に回す。
- **対象が見つからない通知は保留にする。** アクワイアラの取引 ID・参照番号で Charge が見つからない通知は、SEV3 として運用が確かめる。結果不明の回復（[ADR-0011](0011-connector-abstraction-and-unknown-outcome.md)）の途中の取引であれば、照会の結果として扱う。
- **テナントの特定**：受信箱は、通知を受けた時点では加盟店が分からない。受信箱のテーブルは RLS の例外（システムのテーブル）とし、反映のときに Charge から `account_id` を特定してから、テナントのコンテキストで書く。例外は [security.md](../architecture/security.md) の一覧に載せる。
- **保存期間**：生の通知は、照合と監査のために 13 か月保存する（PCI DSS の監査ログの 12 か月に余裕を持たせた値。[security.md](../architecture/security.md) の 13 節）。カード番号を含む通知は CDE の中で受け、カード番号を除いてから本体の受信箱に渡す。
- 2 は、処理の途中の障害で通知を失い、重複と順序の問題を各ハンドラーが個別に扱うことになる。
- 3 は、ファイルでしか来ない通知（精算・一部の Dispute）に対応できず、コネクタの照会の API の負荷も大きい。照会は、結果不明の回復と、通知が来ないときの補助にだけ使う。

## Consequences

- 良くなること：
  - 受けた通知を失わない。後から再び反映できる（バグの修正後の再処理）。
  - 重複・順序の入れ替えに、すべての通知の種類で同じ方式で対処できる。
- 悪くなること、引き受けるコスト：
  - 通知の受け取りから反映まで、キューの分だけ遅れる（目標は p95 5 秒以内。[observability.md](../architecture/observability.md) の SLO に載せる）。
  - RLS の例外のテーブルが 1 つ増える。受信箱を読むのはワーカーだけに限る。

## Confirmation

- 性質ベーステスト：任意の通知の列（重複、順序の入れ替え、欠落の後の到着を含む）を反映した後の状態と仕訳が、正しい順序で 1 回ずつ反映した場合と同じになる。
- 結合テスト：受信口がデータを記録する前に落ちたら 2xx を返さない（コネクタが再送する）。
- メトリクス：未反映・保留の受信箱の行の数と経過時間。24 時間を超えたものがあればアラート。
