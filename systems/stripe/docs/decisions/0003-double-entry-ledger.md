# ADR-0003: お金の正本は、追記のみの複式簿記の台帳にする

## Context

決済の基盤では、次のようなお金の動きが絡み合う。

- 決済、返金、チャージバック
- 手数料、通貨の両替
- 加盟店への入金（Payout）
- 決済代行からの精算

状態のテーブル（`payment_intents.amount_captured` など）の数値を足し合わせて残高を出すと、不具合や並行更新で数字がずれ、どこでずれたかを後から追えなくなる。

## Options

1. **追記のみの複式簿記の台帳を正本にする**
2. **残高の列を、各操作で更新する**
3. **外部の台帳サービスを使う**

## Decision

1 を採用する。詳細は [ledger.md](../architecture/ledger.md) にある。

- **すべてのお金の動きを、1 つ以上の仕訳（journal entry）として記録する。**
  - 各仕訳は、同じ通貨の中で、借方の合計と貸方の合計が一致する明細（posting）の組である。
  - 一致しない仕訳は、DB の制約（遅延制約のトリガー）で拒否する。
- **仕訳は追記のみ。** 更新・削除はしない。誤りは、逆の仕訳（取り消し）で直す。
- **残高は仕訳から求める。** 性能のために残高の集計を持つ場合も、仕訳と同じトランザクションで更新し、日次で仕訳から再計算した値と突き合わせる。
- **状態の遷移と仕訳は、同じトランザクションで書く。** 例：決済のキャプチャの成功と、「加盟店の未入金残高」への計上。
- 2 は、ずれの原因を追えない。
- 3 は、お金の正本を社外に置くことになり、PCI の範囲や障害時の振る舞いを自分で決められない。

## Consequences

- 良くなること：
  - どの時点の残高でも、仕訳から再現できる。
  - 精算・会計の照合が、仕訳の単位でできる。
- 引き受けるコスト：
  - 仕訳のテーブルが大きくなる（S1 で 1 日数百万行）。月ごとのパーティションで持つ。
  - 大口の加盟店の残高の口座に、書き込みが集中しうる。集計の持ち方は [ledger.md](../architecture/ledger.md) で扱う。

## Confirmation

- DB の制約：借方と貸方が一致しない仕訳のコミットが失敗する。
- 性質ベーステスト：任意の操作の列の後で、全口座の残高の合計が 0 になり、各口座の残高が仕訳の合計と一致する。
- 日次の照合のジョブ：集計の残高と、仕訳から再計算した残高の差が 0 であることを確かめる。差があれば SEV2 とする。
