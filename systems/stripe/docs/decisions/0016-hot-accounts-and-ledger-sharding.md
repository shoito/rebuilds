# ADR-0016: 加盟店の残高の集計をスロットに分け、プラットフォームの口座は集計しない。S2 では加盟店のハッシュで台帳を分ける

ADR-0003 の「残高の集計を持つ場合は、仕訳と同じトランザクションで更新する」を具体化する。詳細は [ledger.md](../architecture/ledger.md) の 4・8・9 節。

## Context

- 残高の集計を 1 行で持つと、同じ口座への書き込みが行ロックで直列になる。
- 大口の加盟店は、1 つの `merchant_pending` に毎秒数百件の決済が書き込みうる（S1 のピークは全体で 500 件/秒、S2 で 5,000 件/秒）。
- プラットフォームの口座（`fee_revenue`、`connector_receivable`）は、全加盟店の決済が書き込む。1 行の集計なら、全体のスループットの上限になる。
- 一方で、Balance API と入金の判定には、加盟店の残高を速く正しく読む必要がある。
- S2 では、台帳の書き込みを 1 つの writer に収められなくなる。

## Options

### 集計

1. 1 口座 1 行の集計を、仕訳と同じトランザクションで更新する
2. 集計を持たず、読むたびに仕訳を合計する
3. outbox から非同期に集計する（結果整合）
4. **口座の集計を N 行（スロット）に分け、仕訳と同じトランザクションで 1 行だけ更新する。読むときは合計する**
5. 加盟店の口座自体を N 個の台帳の口座に分ける（サブアカウント）

### S2 の分け方

A. **加盟店の `account_id` のハッシュで分ける**
B. 口座の種類で分ける（加盟店の口座とプラットフォームの口座を別のクラスタに）

## Decision

4 と A を採用する。

- **加盟店の口座は `slotted`。** `ledger_balance_slots (ledger_account_id, slot)` を持ち、仕訳の ID のハッシュでスロットを選ぶ。既定は 1 スロット。行ロックの待ちの p99 が 20ms を超えた口座を、Ops が 16〜64 に増やす。増やすだけで、減らさない。
- **プラットフォームの口座は `snapshot_only`。** 仕訳のときに集計を更新しない。残高は日次のスナップショット＋その後の行の合計で求め、照合と会計でだけ読む。
- **残高を確かめる処理を、入金の作成と返金の作成に限る。** そのときだけ全スロットを `FOR UPDATE` で読む。返金は本家と同じく利用可能な残高を確かめ、足りなければカードの返金は残高が足りるまで保留し、他の決済手段の返金は失敗にする（[payments.md](../architecture/payments.md) の 10.2 節）。Dispute は残高を確かめず、マイナスを許す。
- **S2 では `account_id` のハッシュで、台帳と、同じトランザクションで書く状態のテーブル（決済・返金・入金）を同じシャードに置く。** 1 つの仕訳は 1 つの加盟店に属するので（ADR-0015）、仕訳はシャードの中で閉じる。プラットフォームの口座はシャードごとに持ち、全体は日次に合計する。仮想のシャード（1,024）→ 物理のクラスタの 2 段にする。
- 1 を採らない理由：大口の加盟店とプラットフォームの口座で詰まる。
- 2 を採らない理由：大口の加盟店の残高の読み取りが、行の数に比例して遅くなる。
- 3 を採らない理由：入金の判定で古い残高を使うと、残高を超える入金を作りうる。集計の遅れの監視も増える。
- 5 を採らない理由：スロットと効果は同じだが、勘定体系と BT・レポートの集計が口座の分割を意識する必要がある。分割を集計の層に閉じ込めるほうが単純。
- B を採らない理由：1 つの仕訳が 2 つのクラスタにまたがり、分散トランザクションが要る。

## Consequences

- 良くなること：
  - 大口の加盟店の書き込みの競合が、スロットの数で割られる。
  - プラットフォームの口座が、全体のスループットの上限にならない。
  - S2 で分散トランザクションが要らない。
- 引き受けるコスト：
  - 残高の読み取りが N 行の合計になる。N は最大 64 に抑える。
  - プラットフォームの口座の即時の残高が見えない。必要なら、日次のスナップショット＋行の合計を計算する（数秒〜数十秒）。
  - 精算・銀行の明細など、複数の加盟店にまたがる照合の仕訳は、シャードごとに分けて書く必要がある。
  - Connect のように加盟店の間でお金を動かす機能は、2 つのシャードにまたがる。入れるときに別の ADR で扱う。

## Confirmation

- 日次のジョブ：`slotted` の口座で、スロットの合計＝スナップショット＋締め以降の行の合計。シャードごとと全体で、通貨ごとの全口座の合計が 0。
- 負荷試験：1 加盟店に 500 件/秒の決済を集中させ、スロット 32 で API の p99 が NFR-002（300ms）に収まる（[capacity.md](../architecture/capacity.md)）。
- 性質ベーステスト：任意の並行の仕訳の列と、途中でのスロットの追加の後で、スロットの合計が仕訳の合計と一致する。
- lint：台帳のシャードの鍵（`account_id`）を持たない、台帳のテーブルへの問い合わせを禁止する（照合・会計の専用のロールを除く）。
