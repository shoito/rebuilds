# ADR-0005: カード情報は CDE（別の AWS アカウント）に閉じ込め、本体はトークンだけを扱う

## Context

カード会員データ（カード番号など）を保存・処理・伝送するシステムは、PCI DSS の対象になる。対象が広いほど、統制と監査の範囲が広がる。

本家 Stripe は、カード番号を加盟店のサーバーに通さない入力部品（Elements）を提供し、加盟店の PCI の負担を減らしている。

## Options

1. **CDE を別の AWS アカウントに分け、本体はトークンだけを扱う**
2. **同じアカウントの中で、ネットワークで分ける**
3. **外部のトークン化サービス（カード情報の保管の代行）を使う**

## Decision

1 を採用する。詳細は [card-vault.md](../architecture/card-vault.md) にある。

- **CDE は専用の AWS アカウントにする。** Vault（受け取り・トークン化・保管）と Connector Gateway（アクワイアラへの送信）だけを置く。本体のアカウントとは、決まった API（トークンを渡す）でだけつなぐ。
- **カード番号は、顧客のブラウザ（Elements・Checkout）から Vault へ直接送る。** 加盟店のサーバーと本体を通さない。
- **本体が持つのはトークン（`pm_...`）と、表示用の情報（ブランド、下 4 桁、有効期限）だけ。**
- **CDE の中のカード番号は、CDE 専用の KMS の鍵で暗号化して保存する。** 復号できるのは Connector Gateway の役割だけにする。
- **CDE へのアクセスは、人もエージェントも、常設の権限を持たない。** 期限つきの承認を経てだけ入れる。
- 2 は、IAM・ログ・運用の境界が本体と混ざり、PCI の対象が広がる。
- 3 は、決済の中核を社外に依存させる。本家に寄せる題材の目的にも合わない。

## Consequences

- 良くなること：
  - PCI DSS の対象を、CDE の少ない部品に絞れる。
  - 本体の変更の多くが、PCI の統制の対象外になる。
- 引き受けるコスト：
  - CDE のアカウント・ネットワーク・デプロイの経路を、別に運用する。
  - 決済の経路に、アカウントをまたぐ呼び出しが 1 回増える（遅延の予算に含める）。

## Confirmation

- データの流れの検査：本体のログ・DB・メッセージに、カード番号の形（Luhn を満たす 13〜19 桁）が出ないことを、CI と本番のログの走査で確かめる。
- IAM：CDE のアカウントに、常設の人の権限がないことを週次で確かめる。
