# ADR-0008: API キーは本家と同じ 3 種類にし、ダッシュボードは Better Auth と必須の MFA で守る

## Context

加盟店が API を呼ぶ資格情報（API キー）と、ダッシュボードに入る利用者の認証・権限を決める。キーが漏れると、他人の決済・返金・入金を操作される。ダッシュボードは入金先の口座を変えられる。

本家 Stripe の仕組み（2026-09-26 に確かめた。[API keys](https://docs.stripe.com/keys)、[Restricted API keys](https://docs.stripe.com/keys/restricted-api-keys)、[User roles](https://docs.stripe.com/get-started/account/teams/roles)）：

- キーは公開可能キー（`pk_`）、秘密キー（`sk_`）、制限付きキー（`rk_`。リソースごとに None・Read・Write）の 3 種類で、環境ごとに別。新しい用途には制限付きキーを勧めている。
- 本番のキーは作成時に 1 回だけ表示する。ローテーションでは古いキーを最大 7 日動かせる。キーごとにアクセスポリシー（IP、ASN、国など）を付けられる。
- ダッシュボードの利用者は、アカウントごとにロール（Administrator、Developer、Analyst、View Only など）を持つ。管理者はチーム全員に 2 段階認証を必須にできる。

Slack の再構築では、ログインを Better Auth で自前でホストし、パスワードを持たない方式にした（Slack の ADR-0012）。

## Options

### API キー

1. 本家と同じ 3 種類（公開可能・秘密・制限付き）
2. 制限付きキーだけ（秘密キーを持たない）
3. OAuth のクライアント資格情報で短命のトークンを出す

### ダッシュボードの認証

A. Slack と同じ Better Auth。MFA は管理者の選択
B. Better Auth で、MFA を全員に必須にする
C. マネージドの IdP（Cognito など）

## Decision

1 と B を採用する。詳細は [auth-and-keys.md](../architecture/auth-and-keys.md) にある。

- **キーは本家と同じ 3 種類（1）。** 形は `<brand>_{pk|sk|rk}_{live|test}_{本体}` で、本体にキーの ID と秘密を持つ。接頭辞の `<brand>_` は、本家の `sk_live_` などと重ならないようにするためのもので、リポジトリ共通の [ADR-0006](../../../../docs/decisions/0006-brand-neutral-identifiers.md) に従う。実際の名前は開発リポジトリの作成時に決め、GitHub のシークレットスキャンのパートナープログラムに独自の形式として登録する。環境の接頭辞でクラスタを選ぶ（ADR-0002）。本番の秘密キー・制限付きキーは秘密のハッシュだけを持ち、作成時に 1 回だけ表示する。サンドボックスのキーは KMS で暗号化して、いつでも表示できる。
  - 2 は本家の推奨の方向だが、本家の文書・SDK の例が秘密キーを前提にしており、移行の手間が大きい。秘密キーを残し、ダッシュボードで制限付きキーを先に勧める。
  - 3 は、キー 1 つで呼べる本家の手軽さを失う。
- **キーは人に属さず、アカウントと環境に属する。** 作った人が辞めても動く。
- **制限付きキーの権限は「リソース × None・Read・Write」。** `GET` は Read、`POST`・`DELETE` は Write。各エンドポイントの必要な権限は OpenAPI の `x-permission` に持つ。ダッシュボードのロールも同じ権限の語彙で定義し、判定は 1 つの `authorize()` に集める。
- **ローテーションは、古いキーを最大 7 日動かす。** 期限切れは即時。180 日使われない本番のキーは、お金を動かす操作を止める（本家と同じ）。
- **アクセスポリシーは、MVP では IP（IPv4・CIDR）だけ。** 詳細な条件は E11。
- **ダッシュボードは Better Auth（Slack の ADR-0012 の使い方の規則をそのまま引き継ぐ）で、MFA を全員に必須にする（B）。** パスキーか、1 つ目の要素＋TOTP（かバックアップコード）を満たさないセッションは入れない。Better Auth の `twoFactor` は OTP・ソーシャル・パスキーのサインインに 2 要素目を求めないので、必須の検査は自前のミドルウェアで行う。A は、お金を動かす画面として弱い。C は Slack の ADR-0012 で採らなかった理由がそのまま当てはまる。
- **利用者とロールは live のクラスタに置き、サンドボックスでも同じものを使う。**
- **サンドボックスは、test のクラスタの中の独立したアカウントとして作り、設定を本番と共有しない。** MVP はアカウントごとに 1 つ、E11 で最大 5 つ（本家の一般のサンドボックスと同じ）。
- **ロールは本家の名前に合わせる。** MVP は範囲外の製品に属さないもの（Owner、Super Administrator、Administrator、IAM Administrator、Developer、Analyst、Dispute Analyst、Refund Analyst、Support Specialist、View Only）。

## Consequences

- 良くなること：
  - 本家の知識（キーの種類、ローテーション、ロール）がそのまま通じる。
  - 制限付きキーとロールが同じ権限の語彙で判定され、面ごとの判定のずれが起きにくい。
  - ダッシュボードの乗っ取りの危険を、全員の MFA で下げられる。
- 悪くなること、引き受けるコスト：
  - 全権の秘密キーが残る。漏洩の検知（シークレットスキャン）とローテーションの手順を運用で持つ。
  - MFA の必須は、要素を失った利用者の回復をサポートの手作業にする。
  - 本家の SDK は、キーの形の検査があればそのままでは使えない（ADR-0006 のとおり、本家の SDK との互換は目標にしない）。

## Confirmation

- 表駆動テスト：ロールと権限の表、制限付きキーの判定の表、MFA の条件の表。
- 性質ベーステスト：制限付きキーで許される操作は、同じアカウントの秘密キーで許される操作の部分集合である。
- CI：すべてのエンドポイントが `x-permission` を持つ。
- ログの走査：本番のキーの秘密が、作成時の応答以外に出ない。
- 結合テスト：MFA を満たさないセッションがダッシュボードの API で 403。ローテーションの猶予の後に古いキーが 401。
