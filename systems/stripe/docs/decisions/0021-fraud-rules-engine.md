# ADR-0021: 不正検知は Radar に寄せたルールの言語を決済の経路の中で同期に評価し、外部のサービスはシグナルの 1 つにする

## Context

intent.md で、MVP の不正検知は「ルールと外部の不正検知サービスの連携」で行い、機械学習は作らないと決めた。決める必要があるのは次の点である。

- 加盟店が書くルールの形と、評価の順序。
- 決済の経路のどこで、どう評価するか（遅延の予算、NFR-002）。
- 速度（同じカード・メール・IP の直近の件数）をどこで数えるか。
- 部品の障害のときに、決済を止めるか通すか（NFR-001）。

本家の Radar は、`{action} if {条件}` のルール、4 つの動作（3DS の要求、許可、ブロック、レビュー）、リスト、ルールの試験と段階的な適用（0% の影の評価を含む）を持つ（[Radar のルール](https://docs.stripe.com/radar/rules)、[リスト](https://docs.stripe.com/radar/lists)）。

## Options

1. **Radar に寄せた独自の小さな言語**を、Payments のプロセスの中で評価する。速度は Valkey の時間のバケットで数える
2. 汎用のルールエンジン（JSON Logic、CEL など）をそのまま加盟店に見せる
3. 評価を外部の不正検知サービスに任せ、ルールも外部で書かせる
4. 別のサービス（Fraud API）にして、Payments からネットワーク越しに呼ぶ

## Decision

1 を採用する。詳細は [fraud.md](../architecture/fraud.md) にある。

- **言語**：`{action} if {predicate}`。属性（`:name:`）、メタデータ（`::key::`）、リスト（`@alias`）、比較と論理の演算子、`is_missing()` だけを持つ。属性の名前は本家に合わせる。保存時に AST に構文解析して型を検査し、評価は副作用のない関数で行う。
- **順序**：段 1 で `request_3ds`、段 2（オーソリの前）で `allow` → `block` → `review`、段 3（オーソリの後）で発行会社の照合の結果を使うルール。`allow` は加盟店と既定のルールに優先するが、プラットフォームの `block` には優先しない。
- **場所**：ルールの評価は Payments のプロセスの中のライブラリで行う。外に出るのは速度の読み取りと外部のサービスへの問い合わせだけ。評価の時間の目標は p99 20ms 以内。
- **速度**：ElastiCache（Valkey）に時間のバケット（1 分・1 時間・1 日）を持ち、決済の結果の Event から Worker が冪等に更新する。同期の経路では読むだけ。
- **外部のサービス**：`risk_score`・`risk_level` の属性を返すアダプタにする。時間の予算は 150ms。PAN を渡さない。
- **障害のとき**：速度・外部のサービス・個々のルールの失敗は、属性の欠損として扱い、決済を続ける（fail-open）。プラットフォームのブロックリストはプロセスのキャッシュで評価し続ける。劣化した評価の決済は、閾値を超える金額ならレビューに回す。
- 2 は、加盟店に見せる言語が本家から離れ、本家のルールを移しにくい。内部の AST の表現には、似た構造を使ってよい。
- 3 は、外部のサービスの障害と遅延が決済の API を直接止める。ルールの試験と監査も外部に依存する。
- 4 は、決済ごとにネットワークの往復が 1 回増える。ルールの評価は CPU だけで済み、分ける利点が小さい。S2 で評価の負荷が大きくなれば分ける。

## Consequences

- 良くなること：
  - 加盟店は本家と同じ書き方でルールを書け、本家のルールを移しやすい。
  - ルールの評価が純粋な関数なので、性質ベーステストと過去の決済への試験（バックテスト）が同じ関数でできる。
  - 不正検知の部品の障害で、決済の API が止まらない。
- 引き受けるコスト：
  - 言語の構文解析器・型検査・評価器と、その互換性を自分で持つ。
  - fail-open の間は、速度に頼るルールが効かない。カードテスティングは別に同期のレート制限で防ぐ。
  - 速度の更新が非同期なので、数秒の遅れがある。
  - ルールの集合をプロセスにキャッシュするので、変更の反映に最大 10 秒かかる。

## Confirmation

- 性質ベーステスト：任意のルールの集合と属性で、評価の結果が順序の規則（`allow` の優先、プラットフォームの `block` の優先、`review` はブロックの後）に従う。評価が例外を投げず、上限のノード数で止まる。
- 性質ベーステスト：構文解析 → 表示 → 構文解析で同じ AST になる。
- 結合テスト：Valkey と外部のサービスを止めても決済が成功し、劣化の印が記録される。
- 負荷試験：S1 のピーク（500 件/秒）で、評価の時間の p99 が 20ms 以内。
