# ADR-0002: 加盟店のアカウントをテナントにし、共有スキーマと RLS で分ける

## Context

加盟店どうしのデータの分離は、決済の基盤で最も重い要件の 1 つである。本家 Stripe では、同じアカウントに「テスト」と「本番」の 2 つの環境があり、API キーで切り替わる。

## Options

1. **共有スキーマ＋RLS。** テナントは加盟店のアカウント（`account_id`）。テストと本番は `livemode` の列で分ける
2. **テストと本番を別のデータベース（別のスタック）に分ける**
3. **加盟店ごとに DB を分ける（silo）**

## Decision

1 を基本にし、テストと本番は **DB のクラスタを分ける**。

- **テナントの分け方は Slack の ADR-0009 に倣う。**
  - 全テナントテーブルに `account_id` を持たせ、複合キーを使う。
  - `FORCE ROW LEVEL SECURITY` を設定し、トランザクションごとに `SET LOCAL app.account_id` を設定する。
- **テスト環境と本番環境は、別の Aurora のクラスタに置く。**
  - API キーの接頭辞（`sk_test_` / `sk_live_`）で、要求を振り分ける。
  - テストのデータが本番の台帳・入金に混ざる余地を、構成の段階でなくす。
  - テスト環境は、コネクタの代わりに模擬のアクワイアラ（テスト用のカード番号で結果が決まる）につなぐ。
- 2 の「別のスタック」までは分けない。API・Dashboard のコードは共通で、接続先の DB とコネクタだけを切り替える。
- 3 は加盟店の数（S1 で 1 万）に対して運用が重い。大口の加盟店の分離は、S3 のセル構成で行う。

## Consequences

- 良くなること：
  - テストのデータと本番のお金が、構成として分かれる。
  - RLS により、加盟店のデータの分離をアプリのコードだけに頼らない。
- 引き受けるコスト：
  - DB のクラスタが 2 つになる。テスト側は小さな構成にし、費用を抑える。
  - 同じ加盟店の設定（ブランド、Webhook の送信先）を、環境ごとに持つ必要がある。

## Confirmation

- 性質ベーステスト：任意の 2 加盟店で、一方のコンテキストで他方の行が読めない。
- 結合テスト：`sk_test_` のキーの要求が、本番のクラスタに接続しない。
