# ADR-0030: S1 から大阪にウォームスタンバイを持ち、失った決済はコネクタへの照会で回復する

## Context

NFR-008 は、リージョンの障害で RPO 1 分以内・RTO 1 時間以内を求める。Slack の S1 はパイロットライト（大阪の DB は headless、アプリは切り替え時に作る）で RTO 4 時間だった。決済では 2 つの点が違う。

- **止まっている間、加盟店は売上を失う。** RTO 4 時間は許容されない。
- **失ったデータの中に、外で起きたお金の動きがある。** Aurora Global Database の計画外のフェイルオーバーでは、複製の遅延ぶん（通常は秒単位）の書き込みを失う（[AWS のドキュメント](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-global-database-disaster-recovery.html)）。その間にアクワイアラで成立したオーソリ・キャプチャは、大阪の DB にはないが、顧客のカードには請求されている。加盟店には成功を返し、Webhook も送っているかもしれない。

Aurora PostgreSQL の Global Database には `rds.global_db_rpo` があり、二次の遅れが指定の秒数（20 秒以上）を超えると、一次のコミットを止めて RPO の上限を守る（同上）。

## Options

大阪の構成：

1. パイロットライト（Slack と同じ）
2. **ウォームスタンバイ**：DB の二次に reader を置き、アプリを最小の台数で常に動かし、接続先の登録と専用線も済ませておく
3. S1 から active-active

RPO の守り方：

A. `rds.global_db_rpo` で、一次のコミットを止めてでも RPO の上限を守る
B. **設定せず、遅れを監視し、失った範囲をコネクタへの照会で回復する**

## Decision

2 と B を採用する。手順は [infrastructure.md](../architecture/infrastructure.md) の 5 節と [runbooks/disaster-recovery.md](../runbooks/disaster-recovery.md) にある。

### 大阪の構成

- live と Vault の Global Database の二次に、reader を 1 台置く。切り替えのときにインスタンスを作る時間を省く。test は headless にし、RTO 4 時間とする（お金が動かないため）。
- 本体と CDE の各サービスを、大阪で最小のタスク数で動かす。ALB、NAT、Network Firewall、VPC エンドポイント、SQS、KMS のマルチリージョンキー、Secrets Manager のレプリカ、ECR のレプリカを常に置く。
- アクワイアラへの接続は、大阪の送信元の IP の登録と、大阪のロケーションの専用線（使う場合）まで済ませておく。
- 1 は、切り替えのときの作成（DB のインスタンス、ECS、ALB、接続先の許可）に時間がかかり、RTO 1 時間に届かない。3 は、1 つの加盟店の台帳を 2 つのリージョンで書くことになり、S1 の構成では台帳の一貫性を守れない。active-active は、加盟店をセルに固定したうえで S3 で行う（[ADR-0031](0031-active-active-cells.md)）。

### RPO と、失った決済の回復

- **`rds.global_db_rpo` は設定しない。** A は、東京と大阪の間の回線の劣化だけで、東京の決済をすべて止める。NFR-001（99.99%）を、リージョンの障害より頻度の高い事象で損なう。2 リージョンだけの Global Database では、二次の側で既定のままにすることを AWS も勧めている（同上）。
- 代わりに `AuroraGlobalDBRPOLag` を監視し、10 秒を超えたら呼び出す。
- 失った範囲は、次の仕組みで回復する。
  1. **コネクタの参照番号に、PaymentIntent の ID と試行の番号を入れる。** ID は乱数を含む形式にし、連番にしない。照会の結果から、元の ID で作り直せる。
  2. **`Idempotency-Key` 付きの作成と確定では、コネクタの参照番号をキーから決める。** 大阪が冪等キーの記録を失い、加盟店の再送を新しい決済として処理しても、アクワイアラの重複の検査で二重の請求を防ぐ。
  3. **切り替えの直後に、失った範囲（複製の遅延の記録＋前後 5 分）について、アクワイアラへ照会する。** 照会 API、古い一次の障害時点のスナップショット（取れた場合）、翌日の精算ファイルの順に使う。
  4. **成立していた決済は、元の ID で状態と仕訳を作り直し、元の ID の Event を発行する。** 加盟店が作成の応答を受け取っていないオーソリは、取り消す。
  5. **照合が終わるまで、失った範囲にかかる加盟店の Payout を保留する。**
- NFR-008 の「RPO 1 分」は、DB の複製の遅延（通常は秒単位）で失う範囲が 1 分以内であり、かつその範囲をこの照会で回復できることを指す、と解釈する。

## Consequences

- 良くなること：
  - RTO 1 時間の見込みが立つ（DB の昇格は通常数分。アプリは動いている）。
  - 東京と大阪の回線の劣化で、東京の決済が止まらない。
  - 失った範囲の決済を、加盟店と顧客への影響（二重の請求、成功したのに記録がない）なしに回復する道がある。
- 引き受けるコスト：
  - 大阪の待機の構成の費用が、常にかかる（[infrastructure.md](../architecture/infrastructure.md) の 9 節）。
  - 参照番号の形式と冪等キーからの導出を、コネクタごとに実装し、接続先の重複の扱い（拒否か、元の結果を返すか）を確かめる必要がある。**未検証**：最初の接続先が決まったら E3 で確かめる。照会 API がない接続先では、回復が翌日の精算ファイルまで遅れる。
  - 回復の間、影響を受けた加盟店の Payout が遅れる。
  - 作り直した PaymentIntent の Event は、加盟店に 2 回届きうる（同じ Event の ID なので、加盟店の側で重複として捨てられる前提。[events-and-webhooks.md](../architecture/events-and-webhooks.md) で加盟店への案内を書く）。

## Confirmation

- 四半期：staging で、東京の書き込みを続けたまま計画外のフェイルオーバーを行い、次を確かめる。
  - RTO（切り替えの判断から、大阪での決済の再開まで）が 1 時間以内。
  - 失った範囲の決済が、模擬のアクワイアラへの照会で全件回復し、台帳の整合と照合の不一致が 0 件になる。
  - 冪等キー付きの再送が、二重のオーソリにならない。
- 年 1 回：本番で計画的な切り替え（switchover、RPO 0）を行い、大阪で決済を受け、東京へ戻す。
- 監視：`AuroraGlobalDBRPOLag` のアラート、大阪の待機の構成の健全性（合成監視を大阪の構成に対しても行う）。
