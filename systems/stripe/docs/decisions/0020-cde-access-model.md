# ADR-0020: CDE へのアクセスは、人は期限つきの承認（JIT）だけとし、AI エージェントには与えない

## Context

ADR-0005 で、CDE へは人もエージェントも常設の権限を持たないと決めた。具体的な仕組みを決める必要がある。

- PCI DSS は、CDE へのすべてのアクセスに MFA を求め（要件 8.4.2）、アクセスの権限を 6 か月ごとに見直すことを求める（要件 7.2.4）。
- 本家は、CDE へのアクセスを特別な訓練を受けた少数のエンジニアに限り、四半期ごとに見直す（[Stripe のセキュリティ](https://docs.stripe.com/security)）。
- rebuilds では、AI エージェントは本番に一切アクセスしない（Slack の security.md の 7.3 節）。CDE はそれ以上に厳しくしたい。
- 障害の対応では、CDE の中を見る必要が出る。そのときの経路がないと、手作業の抜け道が生まれる。

## Options

1. **JIT**：申請 → 2 人目の承認 → 期限つきの権限セットの割り当て。セッションは SSM Session Manager で記録する
2. 少数のエンジニアに常設の読み取り権限を与え、書き込みだけ承認制にする
3. CDE に人が入る経路を一切作らない（すべて自動化とデプロイだけで直す）

## Decision

1 を採用する。

- **申請と承認**：申請者は理由と対象（インシデントの ID など）を書く。申請者以外の、CDE の承認者の名簿にある人が承認する。承認なしで入る経路はない。
- **期限**：最長 4 時間。延長は申請し直す。
- **権限の払い出し**：IAM Identity Center の権限セットを、承認のワークフローが一時的に割り当て、期限で外す。仕組みは AWS の TEAM（Temporary Elevated Access Management）などを候補にし、着手時に決める（未検証）。
- **入り方**：SSM Session Manager だけ。SSH の鍵、踏み台、コンソールでの手作業は使わない。セッションの入出力を log-archive に残す。
- **MFA** はフィッシングに強い方式（パスキー、セキュリティキー）に限る。
- **見られないもの**：PAN の平文を人に見せる機能を作らない。調査は `card_ref`、指紋、下 4 桁で行う。
- **AI エージェント（コーディング・運用）は、JIT の対象にもしない。** 承認者の名簿にも入れない。
- **見直し**：承認者の名簿と、JIT の利用の記録を四半期ごとに見直す（本家に合わせる。PCI の 6 か月より短い）。
- 2 は、常設の権限が乗っ取られたときの影響が大きい。本家の「少数・四半期の見直し」は、常設か JIT かを公表していない。
- 3 は理想だが、アクワイアラとの接続の障害などで、ネットワークや設定の状態を見る必要が出る。経路がないと、手順外の抜け道が作られる。

## Consequences

- 良くなること：
  - CDE への人のアクセスが、すべて申請・承認・記録に紐づく。
  - 権限の乗っ取りの影響が、期限の内に限られる。
- 引き受けるコスト：
  - 深夜の障害で、承認者がつかまらないと入れない。承認者の当番を置く（runbook の `cde-access`）。
  - 承認のワークフローの仕組みを運用する。
  - PAN を人が見られないので、アクワイアラとの食い違いの調査は、参照番号と下 4 桁で行う必要がある。

## Confirmation

- 週次の検査：CDE のアカウントに、人の常設の権限（ユーザー、恒久的な権限セットの割り当て）がない（ADR-0005 の Confirmation と同じ）。
- 期限を過ぎた割り当てが残っていたら、アラートにする。
- JIT の利用ごとに、申請・承認・セッションの記録がそろっていることを、月次で突き合わせる。
- 承認者の名簿に、エージェントのロールや共有のアカウントがないことを CI（IaC の検査）で確かめる。
