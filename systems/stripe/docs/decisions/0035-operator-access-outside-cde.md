# ADR-0035: CDE の外での運用者のアクセスと、加盟店のデータの閲覧

## Context

CDE へのアクセスは [ADR-0020](0020-cde-access-model.md) で決めた（人は JIT だけ、AI エージェントは対象外、PAN を人に見せない）。CDE の外（本体の prod のアカウント）については、[security.md](../architecture/security.md) の 4 節に「本体は最小権限と break-glass」とあるだけで、次が決まっていない。

- 平常時に持つ権限と、期限つきで得る権限の境目
- サポートが加盟店のデータ（決済、顧客の個人情報、入金先の口座）を見る条件。いまは「閲覧の理由の入力と監査ログ、加盟店のセキュリティの履歴に表示」（security.md の 3.5 節）だけがある
- 運用者が、加盟店のダッシュボードの利用者になりすませるか

本体の DB には、加盟店の顧客の個人情報と、お金を動かす操作がある。Auth0 の題材は同じ問いを [ADR-0056](../../../auth0/docs/decisions/0056-operator-access.md) で決め、テナントのデータの参照にテナントの許可を求めた。ただし、この題材では、審査・不正・Dispute・照合を運用者が自ら行う（[ADR-0022](0022-merchant-onboarding-and-kyc.md)、犯収法の扱いは L3）。加盟店の許可を待つと、プラットフォームの義務を果たせない。

## Options

1. Auth0 の ADR-0056 の形に寄せる。ただし、加盟店のデータの閲覧は加盟店の許可を求めず、業務の役割と理由で絞り、加盟店に見せる
2. **Auth0 と同じく、加盟店のデータの閲覧に加盟店の許可を求める（審査・不正・Dispute の業務は例外にする）**
3. いまのまま（Ops の常設の読み取り権限と break-glass）

## Decision

2 を採用する。

> 2026-10-25 の注記：最初の案は 1（加盟店の許可を求めない）だった。レビューで、Slack・GitHub・Auth0 と同じく加盟店の許可を前提にし、運用者自身の業務だけを例外にする形に改めた。

- **常設の権限**：ダッシュボード、メトリクス、トレース、許可リストのフィールドだけのログ（[observability.md](../architecture/observability.md)）の読み取り。運用者の画面（社内のツール）での、加盟店のアカウントの設定と状態（有効・停止・審査中など）のメタデータの閲覧。
- **加盟店のデータの閲覧は、加盟店の許可を前提にする。** サポートが、決済・返金・入金の詳細、Webhook の配信の記録の中身、顧客の個人情報を運用者の画面で見るには、加盟店の owner か admin が、ダッシュボードで問い合わせを指定して許可する。許可は期限つき（既定 72 時間）で、加盟店はいつでも取り消せる。
- **例外（許可を求めない業務）**：運用者自身の業務で、加盟店の許可を待つと義務を果たせないもの。どれも案件の ID を必須にする。

  | 業務 | 見られるもの | 必須の案件の ID |
  | --- | --- | --- |
  | 審査（オンボーディングと継続の審査、本人確認） | 審査の資料、本人確認の結果、アカウントの設定と状態 | 審査の ID |
  | 不正の調査 | 決済と不正のシグナル | 調査の ID |
  | Dispute の対応 | 対象の決済と、提出する証拠 | Dispute の ID |
  | 照合（経理） | 照合と入金の記録、仮勘定。顧客の個人情報を含まない | `recon` の業務の ID |

- **伏せ字と記録**：顧客の個人情報は、許可がある場合も例外の業務でも既定で伏せ、開くたびに理由を求める。運用者の画面の閲覧は、許可によるものも例外によるものも、加盟店の `audit_events`（運用者による閲覧）に残し、ダッシュボードのセキュリティの履歴に出す（ADR-0023）。
- **期限つきの権限（最長 4 時間。ADR-0020 と同じ仕組み）**：

  | 権限 | 承認 | 使う場面 |
  | --- | --- | --- |
  | 本番の DB の読み取り（RLS の対象のロール。`SET LOCAL app.account_id` で加盟店を指定する） | Ops の責任者（依頼者と別） | 障害の調査 |
  | 本番の DB の書き込み、ECS Exec | Ops の責任者と Dev のテックリードの 2 人 | データの修復。お金を動かす修復は台帳の仕訳で行い、残高を直接書かない（ADR-0003） |

- **なりすましの機能を作らない。** 運用者が、加盟店のメンバーとしてダッシュボードにログインする機能、API キーを作る・表示する機能は作らない。運用者の画面からお金を動かす操作（返金、入金の再実行）は、運用者の名前で、2 人の承認を経て行い、監査ログに運用者として残す。
- **AI エージェントは本番に経路を持たない。** CDE に加えて、本体の DB・ログ・シェル・運用者の画面にも経路を持たない（security.md の 9 節）。
- **レビュー**：四半期ごとに、役割の割り当て、期限つきの権限の使用、例外の業務による閲覧の件数と理由を見直す（ADR-0020 と同じ周期）。例外が許可の代わりの平常の経路になっていないかを確かめる。
- 1 は、許可なしの閲覧が平常になり、Slack・GitHub・Auth0 と運用の決まりが揃わない。サポートの閲覧の大半は問い合わせに伴うもので、加盟店の許可を得られる。3 は、1 人のアカウントの乗っ取りで全加盟店の顧客の個人情報が読める。

## Consequences

- 良くなること：
  - サポートの閲覧は加盟店の許可を前提にし、例外の業務を含めて、すべて加盟店から見える。
  - 運用者のアクセスの決まりが、Slack・GitHub・Auth0 の題材と揃う。
  - 本体と CDE で、期限つきの権限の仕組みが 1 つになる。
- 引き受けるコスト：
  - 加盟店のダッシュボードに、許可の画面（問い合わせの指定、期限、取り消し）を作る。運用者の画面で、伏せ字と理由の入力を作る。
  - 許可を待つ分、サポートの返答が遅れうる。
  - 例外の業務の閲覧は許可で抑止できないので、案件の ID と記録と四半期のレビューに頼る。

## Confirmation

- IAM の静的検査（Terraform の CI）：本体の prod のアカウントに、期限つきの権限の仕組み以外から DB・ECS Exec の権限を持つ人のロールがない。
- 結合テスト：加盟店の許可がなく、例外の業務の案件の ID もない閲覧は拒否する。許可の期限が切れたら閲覧できない。
- 結合テスト：運用者の画面のどの閲覧も、加盟店の `audit_events` に 1 件ずつ残る。顧客の個人情報を開くと、理由がない限り拒否する。
- 結合テスト：運用者の画面の API に、加盟店のメンバーのセッションや API キーを作る操作がない（ルートの一覧の検査）。
- 四半期：アクセスレビューの記録。
