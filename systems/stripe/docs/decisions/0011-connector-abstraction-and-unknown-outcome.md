# ADR-0011: コネクタを共通の操作と能力で抽象し、結果不明の取引は照会と取り消しで確定させてから次の手を打つ

## Context

決済は、ライセンスを持つ決済代行・アクワイアラに接続して行う（[intent.md](../intent.md)）。接続先は 1 社から始め、後で増やす。接続先ごとに、要求の形、応答コード、仮売上・実売上の扱い、照会の有無が違う。

最大の難所は、オーソリの要求を送った後にタイムアウトや切断が起きたときである（[architecture/README.md](../architecture/README.md) の 6 節）。

- 「失敗」と返すと、顧客が払い直したときに、先のオーソリが実は通っていれば二重に請求する。
- 「成功」と見なすと、受け取っていないお金で商品を発送させる。
- 別のコネクタに送り直すと、二重請求の危険がさらに高い。

[ADR-0004](0004-idempotency.md) で、コネクタの層では参照番号で冪等にし、結果が不明なら照会してから次の手を決めると決めた。その具体的な規則を決める。

## Options

1. **共通の操作と能力の宣言でコネクタを抽象する。結果不明は `processing` で待ち、参照番号での照会と取り消しで確定させる。振り分けは送信前の失敗に限る**
2. **結果不明を、一定時間後に失敗とみなす**（タイムアウト＝失敗）
3. **結果不明のとき、すぐに別のコネクタへ送り直す**（可用性を優先）
4. **コネクタごとに Payments の中で分岐を書く**（抽象を作らない）

## Decision

1 を採用する。詳細は [payments.md](../architecture/payments.md) の 7・8 節と [payment-methods.md](../architecture/payment-methods.md) の 3 節にある。

- **コネクタは共通の操作を持つ**：`authorize`、`capture`、`void`、`refund`、`inquire`、`verify`、`authenticate_*`、`parse_notification`、`parse_settlement`。すべて参照番号で冪等にする。
- **能力を宣言する**：手動キャプチャ、オーソリの有効期限、照会とその整合性の時間、3DS Server、口座確認、EFW、ネットワークトークンなど。Payments は能力を見て振る舞いを変え、コネクタの名前で分岐しない。
- **応答コードを本家の拒否コードに正規化する。** 生のコードは `network_decline_code` に残す。
- **送信の前に記録する。** 試行を `pending_send` でコミットしてから送る。
- **失敗を 3 つに分ける**：送信前の失敗（確実に送っていない）、明確な拒否、結果不明。区別できない失敗は結果不明とする。コネクタの HTTP クライアントは自動で再送しない。
- **結果不明のときは次の手順で確定させる。**
  1. PaymentIntent を `processing` にし、加盟店と顧客に失敗と言わない。
  2. 参照番号で照会する（5 秒・30 秒・2 分・10 分・1 時間）。見つかれば、その結果を反映する。
  3. 照会の整合性の時間を過ぎても見つからなければ、同じ参照番号で取り消しを送る。取り消しが受理されてから、失敗（`processing_error`）として `requires_payment_method` に戻す。
  4. 照会も取り消しもできなければ待つ。24 時間で SEV2 とし、runbook の手順で確かめる。
  5. 精算ファイルとの照合で、成功の記録のない売上を見つけたら、自動で取り消し・返金する。
- **振り分けの規則**：別のコネクタへ送ってよいのは、前の試行が送信前の失敗のとき、または取り消しが確定したときだけ。キャプチャ・取り消し・返金は、オーソリしたコネクタにだけ送る。カード発行会社の拒否を自動で別のコネクタに送り直さない。
- 2 は、タイムアウトの後に実はオーソリが通っていたとき、顧客の再試行で二重請求になる。取り消しを送らずに失敗とするのは危険である。
- 3 は、決済の成功率は上がるが、二重オーソリを構造的に招く。決済の基盤の信用（[intent.md](../intent.md) の「守るべき振る舞い」）に反する。
- 4 は、2 社目を足すたびに Payments の変更が要り、結果不明の扱いがコネクタごとにずれる。

## Consequences

- 良くなること：
  - どのコネクタでも、結果不明の取引が二重請求にならない。
  - 2 社目のコネクタを、Payments を変えずに足せる。
- 悪くなること、引き受けるコスト：
  - 結果不明のあいだ、顧客は「処理中」の画面で待つ。まれだが、コネクタの障害時には多数の取引が `processing` に溜まる。
  - 照会の API を持たないコネクタでは、取り消しと精算の照合だけが頼りになる。そのようなコネクタは本番で使わない（能力 `inquiry` を必須とする）。照会がないことが接続先の選定で避けられない場合は、この ADR を見直す。
  - 本家の Adaptive Acceptance のような、拒否の後の自動の再試行は作らない。

## Confirmation

- 故障注入のテスト：模擬のアクワイアラで、送信後のタイムアウト・切断・5xx・照会の遅延を起こし、どの組み合わせでも承認されたオーソリが PaymentIntent あたり 1 つ以下であることを確かめる。
- 性質ベーステスト：任意の故障の列の後で、「アクワイアラ側で有効なオーソリ（取り消されていないもの）」の数が「`succeeded`・`requires_capture` の PaymentIntent」の数と一致する。
- 結合テスト：コネクタごとに、同じ参照番号の 2 回目の要求が重複として扱われる。
- メトリクス：`processing` の PaymentIntent の数と経過時間。24 時間を超えたものが 1 件でもあればアラート。
