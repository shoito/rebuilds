# ADR-0032: お金を動かすコードは、影の実行で比べてから、加盟店単位のカナリアで広げる

## Context

Slack の ADR-0022・0026 は、デプロイとリリースを分け、フラグをワークスペース単位で 5% → 25% → 100% と広げる。決済では、これだけでは足りない。

- **誤りの影響が、後から見える。** 手数料の計算や仕訳の規則の誤りは、エラーにならない。数日後の照合や Payout、月末の締めで初めて見つかり、そのときには多くの取引に広がっている。
- **戻しても、動いたお金は戻らない。** フラグを切れば新しい取引は正しくなるが、誤った仕訳と、誤った額の Payout はそのまま残る。台帳は追記のみなので（[ADR-0003](0003-double-entry-ledger.md)）、訂正の仕訳で直すことになる。
- **要求ごとの割合で振り分けると、1 つの加盟店の取引が新旧の計算に分かれる。** 照合と、加盟店への説明がつかなくなる。

## Options

1. Slack と同じ（フラグで段階的に広げ、エラー率と遅延で判断する）
2. **影の実行（dual-run）で本番の取引の結果を比べてから、加盟店単位のカナリアで広げ、お金の不変条件のガードで自動で止める**
3. すべての変更で、長期間の並行稼働と手作業の突合を行う

## Decision

2 を採用する。流れと判断者は [delivery.md](../architecture/delivery.md) の 2.2・5 節にある。

- **お金の区分を付ける。** A（お金の結果を変える）、B（お金の流れに触れるが結果は変えない）、C（触れない）。A と B だけに、以下の手間をかける。3 のようにすべての変更に長い並行稼働を求めると、デプロイの頻度が落ち、変更を溜めて 1 回の危険を大きくする。
- **影の実行**：新しい計算を、本番の実際の取引に対して古い計算と並べて実行し、結果を比較用の表に書く（台帳には書かない）。仕訳の明細、手数料、Payout の金額、状態の遷移を比べ、理由のない差が 1 件でもあれば先へ進めない。区分 A は 7 日かつ 10 万件以上、月末または Payout の日を含める。区分 B は 24 時間。
- **加盟店単位のカナリア**：割り当ての単位は加盟店のアカウント。社内の加盟店（live、社内のカード）→ 同意を得た低リスクの加盟店 → 1% → 10% → 50% → 100%。各段で 24 時間以上、かつ 1 回以上の日次の照合と Payout を通す。大口の加盟店は最後にする。
- **お金の不変条件のガード**：台帳の整合、影の実行の差、フラグの有効・無効の加盟店の間でのオーソリの技術的な成功率と結果不明の発生率の差、照合の新しい不一致。どれかが起きたら、AppConfig のアラームでフラグを自動で切る。
- **台帳を書き換えない。** 過去の仕訳を変えるマイグレーションとバックフィルを禁止する。誤りは「台帳の訂正」のジョブ（乾いた実行 → 2 人の承認 → 冪等な追記 → 再計算での確認）で直す。
- **承認**：区分 A は、お金のオーナー（Dev のテックリード）と QA の 2 人がレビューし、影の実行の結果も 2 人が承認する。
- 1 は、エラーにならない誤りを見つけられない。

## Consequences

- 良くなること：
  - お金の誤りの多くを、本番のお金を動かす前に見つけられる。
  - 誤りが出ても、影響が一部の加盟店に限られ、照合で範囲を特定しやすい。
- 引き受けるコスト：
  - 区分 A の変更は、リリースまでに最短でも 7 日＋段階的な展開の日数がかかる。
  - 影の実行の仕組み（比較用の表、差のダッシュボード、非同期の実行）を作って保守する。影の実行の分だけ、DB の書き込みが増える。
  - 外部に副作用がある変更（コネクタへの送信の形式）は影の実行ができない。模擬のアクワイアラでの比較と、社内の加盟店での実際の取引で代える。
  - 区分の付け間違いが起こりうる。お金のオーナーがレビューで確かめ、`services/ledger` など決まったパスの変更は、CI で区分 A か B を必須にする。

## Confirmation

- CI：区分 A の変更の `plan.md` に、影の実行の計画（比べるもの、期間、件数、ガード）がなければ失敗させる。`services/ledger`・`services/payments`・`services/payouts` の変更で、区分が C なら失敗させる。
- CI：台帳のテーブルへの `UPDATE`・`DELETE` を含むマイグレーションを拒否する。
- リリースの記録：区分 A のフラグごとに、影の実行の結果（件数、差、理由）を Story の Issue に残し、QA が受け入れの判定に使う。
- 振り返り：ガードで自動で止まった事例と、照合で後から見つかったお金の誤りを四半期ごとに見直し、ガードの条件を直す。
