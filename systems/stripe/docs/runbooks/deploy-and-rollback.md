# Runbook: デプロイとロールバック

- Owner: Ops
- 対応するアラート: api の blue/green の自動ロールバック、デプロイ後の SLO のバーンレート、お金の不変条件のガードによるフラグの自動停止
- 最終確認日: 2026-09-26

流れは [delivery.md](../architecture/delivery.md)、CI/CD の構成は [infrastructure.md](../architecture/infrastructure.md) の 6 節、お金を動かす変更のリリースは [ADR-0032](../decisions/0032-release-safety-for-money-moving-code.md)、CDE の経路は [ADR-0033](../decisions/0033-cde-pipeline-and-change-control.md) にある。

## 症状

次のときに使う。

- 本番（prod）または CDE の本番（cde-test・cde-live）へデプロイするとき
- デプロイの後に、API の 5xx、オーソリの技術的な成功率、結果不明の発生率が悪化したとき
- お金の不変条件のガードが、フラグを自動で切ったとき

## 影響

- 通常のデプロイ：加盟店への影響はない。
- 失敗したデプロイ：決済の API の可用性（99.99%）とオーソリの成功率を消費する。お金の区分 A の誤りは、エラーにならずに誤った仕訳・Payout を生む。

## 確認

### デプロイの前

1. 対象のコミットが staging（CDE は cde-nonprod）へデプロイ済みで、E2E・スモーク・デプロイ中の k6 が通っている。
2. デプロイできる時間帯である（本体：平日 10〜17 時。CDE：平日 10〜16 時。月末・月初の 2 営業日、凍結期間は修正だけ）。
3. マイグレーションが expand だけか。contract を含むなら、1 つ前のリリースで参照をやめていること、PITR の直近の復元可能な時刻が 5 分以内であることを確かめる。**台帳のテーブルへの `UPDATE`・`DELETE` を含むマイグレーションは、CI で拒否されているはずである。含まれていたら止める。**
4. SLO のダッシュボードで、エラーバジェットが残っている。
5. 進行中のインシデントと、結果不明の滞留がない。照合の不一致が T+1 で残っていない。
6. CDE のデプロイなら、変更記録（`pci:change` の Issue）があり、2 人の承認がそろっている。

### デプロイの後（入れ替えが終わってから 15 分）

| 見るもの | 正常 | 異常 |
| --- | --- | --- |
| 決済の API の 5xx の割合 | デプロイ前と同じ | 0.05% を超える |
| 処理時間（コネクタの待ちを除く）p99 | 300ms 以内 | 超える |
| オーソリの技術的な成功率（コネクタ別） | デプロイ前と同じ | 0.5 ポイント以上下がる |
| 結果不明の発生率 | デプロイ前と同じ | 2 倍以上 |
| outbox の最古の行、Webhook の最初の配信の p95 | 30 秒以内、10 秒以内 | 超える |
| 合成監視（test と live） | 成功 | 2 回続けて失敗 |
| カード番号の走査 | 0 件 | 1 件以上（直ちにインシデント） |

## 対処

### 通常のデプロイ（本体）

1. GitHub の `prod` の Environment で、Ops が承認する（作成者と別の人）。
2. マイグレーションのタスクの成功を確かめる。失敗したら、アプリのデプロイは自動で止まる。
3. relay、workers、webhook-router・sender・scheduler、connectors がローリングで入れ替わる。webhook-egress の Lambda は新しいバージョンの別名に切り替わる。
4. api：blue/green のカナリア（10%）。5xx、オーソリの技術的な成功率、結果不明の発生率のアラームが鳴らなければ 100% に切り替わる。
5. dashboard、checkout：blue/green。
6. 「デプロイの後」の表を 15 分見る。

### 通常のデプロイ（CDE）

1. cde-nonprod で自動の検査が通っていることを確かめる。
2. `cde-test` の Environment で 2 人が承認する。vault-core → vault-ingest → connector-gateway の順に blue/green で入れ替わり、Elements の iframe の静的ファイルを最後に差し替える。
3. test の合成監視（1 分ごと）が 24 時間成功し続けたら、`cde-live` の Environment で 2 人が承認する。
4. cde-live を同じ順に入れ替える。connector-gateway の入れ替え中は、コネクタ別の技術的な成功率と、live の社内の加盟店の合成監視（オーソリ → 取り消し）を見続ける。
5. 変更記録に、デプロイの時刻、確認の結果、承認者を書き、閉じる。

### 悪化したとき

1. **フラグで戻す。** 新しい機能のフラグが原因なら、AppConfig で切る。お金の不変条件のガードで自動で切れていれば、切れていることを確かめる。
2. **フラグで戻せないとき、アプリを戻す。** 1 つ前のイメージの digest で再デプロイする（「前のリリースを再デプロイ」のワークフロー）。CDE も同じだが、CDE の経路のワークフローで、2 人の承認を得て行う（ロールバックでも省かない。承認者はオンコールで呼ぶ）。
3. **マイグレーションは戻さない。** 前へ進める修正を書く。
4. **お金の誤りが出ていたら**（誤った仕訳・手数料・Payout の金額）：
   - 影響を受けた加盟店と期間を、フラグの有効化の記録と照合の結果から特定する。
   - その加盟店の Payout を保留する（ops フラグ `ops.payout_hold` を加盟店単位で）。
   - 訂正は「台帳の訂正」のジョブで行う（[delivery.md](../architecture/delivery.md) の 5.3 節）。過去の仕訳を直接書き換えない。
   - インシデントとして扱う（[incident-response.md](incident-response.md)）。
5. 戻しても直らなければ、インシデントを宣言する。

## エスカレーション

- 戻しても 15 分以内に SLO が回復しない → インシデントを宣言する。
- お金の誤り、台帳の整合の検査の失敗 → SEV2 以上。お金のオーナー（Dev のテックリード）と経理の担当を呼ぶ。
- CDE のデプロイの後にカード番号の走査で検出 → SEV1。セキュリティの担当を呼ぶ。
- マイグレーションが途中で止まり状態がわからない → Dev のテックリードを呼ぶ。

## 事後

- 調査結果を Intent の Issue として起票する（Maintain 段）。
- デプロイの失敗を CI で防げたなら、CI の検査（障害注入、影の実行の条件、ガードの条件）を足す提案を Dev と QA に出す。
- CDE の変更なら、変更記録に事後の結果を追記する。
- この手順で足りなかったことを、ここに反映する。
