# Runbook: インシデント対応

- Owner: Ops
- 対応するアラート: すべての呼び出し（page）のアラート。個別の場面は「決済に固有の場面」の節
- 最終確認日: 2026-09-26

個別の手順（[deploy-and-rollback.md](deploy-and-rollback.md)、[disaster-recovery.md](disaster-recovery.md)）の上に立つ、共通の進め方と、決済に固有の場面（コネクタの障害、結果不明、照合の不一致、カード番号の漏洩の疑い）。進め方の骨格は Slack の [incident-response.md](../../../slack/docs/runbooks/incident-response.md) と同じ。

## 症状

次のどれかのときに、インシデントを宣言する。迷ったら宣言し、後で重さを下げる。

- 呼び出しのアラートが鳴った（[observability.md](../architecture/observability.md) の 5.2 節）
- 加盟店や社内から、障害・お金の不一致の報告が来た
- テナント境界の監査で不一致が出た、カード番号の走査で検出した

## 影響

### 重さ（severity）

| 重さ | 基準 | 例 | 最初の応答 | 告知 |
| --- | --- | --- | --- | --- |
| SEV1 | 他の加盟店のデータが見えた。カード番号の漏洩が確定した。成功を返した決済・返金・入金が失われた。二重の請求が起きた。決済を全体で受けられない | テナント境界の破れ、リージョンの障害、全コネクタの停止 | 5 分以内 | 30 分以内に加盟店へ。以後 30 分ごと |
| SEV2 | 決済の一部が失敗する（1 つのコネクタ・ブランド）。結果不明が滞留する。台帳の整合の検査の失敗。カード番号の漏洩の疑い。SLO の速いバーンレート | 1 つのコネクタの障害、AZ の障害 | 15 分以内 | 1 時間以内に加盟店へ（影響があれば） |
| SEV3 | 劣化しているが、お金は正しい。回避できる | Webhook の遅れ、照合の不一致（T+1）、ダッシュボードの遅れ | 営業時間内 | 必要なら |
| SEV4 | 加盟店への影響がない | 1 つの Worker の失敗の増加 | 営業時間内 | なし |

お金の正しさ（台帳、二重の請求）と、カード番号とテナント境界に関わるものは、範囲が 1 件でも SEV2 以上にする。

## 確認

1. どのアラート・報告から始まったかを記録する。
2. 影響の範囲を見る：全体か、特定のコネクタ・ブランド・加盟店・AZ か。live か test か。
3. 直近の変更を見る：デプロイ（本体と CDE）、フラグ、マイグレーション、インフラ、**コネクタの側の変更の告知**（接続先の保守の予定）。
4. お金への影響を見る：結果不明の件数、台帳の整合、照合の不一致、Payout の状態。

## 対処

### 役割

| 役割 | 担う人 | 責任 |
| --- | --- | --- |
| 指揮者（IC） | 最初に応答したオンコール。SEV1 では Ops の責任者に引き継いでよい | 重さ、方針、大きな判断（コネクタの切り離し、Payout の保留、リージョンの切り替え） |
| 作業者 | オンコールの Ops、呼ばれた Dev | 調査と復旧 |
| お金の担当 | お金のオーナー（Dev のテックリード）、経理の担当 | お金への影響の評価、回復・訂正の承認 |
| 連絡係 | IC が指名する（PM が望ましい） | 加盟店、社内、接続先への連絡 |
| 記録係 | IC が指名する | 時刻付きの記録 |

SEV1 では、指揮者は手を動かさない。

### 進め方

1. **宣言する。** インシデント用の場を、このシステムと別の道具に作る。
2. **被害を止めることを、原因の特定より優先する。** 順番：
   - 直近の変更のフラグを切る
   - 直近のデプロイを戻す（[deploy-and-rollback.md](deploy-and-rollback.md)）
   - 問題のコネクタを切り離し、振り分けを変える（「コネクタの障害」）
   - お金の誤りが広がるなら、Payout を保留する（`ops.payout_hold`）
   - 問題の加盟店にレート制限をかける、容量を増やす
3. **お金の記録を消さない、書き換えない。** 台帳、試行の記録、ログは証拠であり、回復の材料である。訂正は追記で行う。
4. **告知する。** 何が起きているか、どの決済に影響するか（新しい決済、返金、入金）、次の更新はいつか。原因の推測は書かない。
5. **収束を確かめる。** SLO の指標が戻り、合成監視が成功し、結果不明が片付き、15 分たってから解決とする。お金の回復（照会、訂正、照合）が残るときは、インシデントを閉じず、SEV を下げて続ける。

### 決済に固有の場面

#### コネクタの障害

アラート：コネクタの技術的な成功率の低下、承認率の低下、コネクタの応答時間の悪化。

1. **接続先の障害か、こちらの障害かを見分ける。**
   - 1 つのコネクタだけ → 接続先か、その経路（NAT、Network Firewall、専用線、証明書）。
   - 全コネクタ → connector-gateway、CDE の KMS、PrivateLink、`connector-results` のキュー、本体の api。
   - 接続先の状態のページ、接続先のサポート窓口、証明書の期限、Network Firewall のログ（拒否の増加）、Direct Connect の BGP の状態を見る。
2. **切り離す。** 振り分けの規則（[payment-methods.md](../architecture/payment-methods.md)）で別のコネクタに回せるなら、ops フラグでそのコネクタを無効にする。回せないなら、そのコネクタの新しい試行を止め、`processing_error` を早く返す（タイムアウトまで待たせて結果不明を増やさない）。
3. **結果不明の増加に備える。** 障害の間に送った試行は、結果不明になっている。次の「結果不明」の手順で片付ける。
4. **接続先に連絡する。** 契約上の連絡先へ、時刻と影響の範囲（試行の件数、参照番号の例）を伝える。
5. 回復したら、コネクタを社内の加盟店だけで有効にし、live の合成監視が成功してから全体に戻す。

#### 結果不明（unknown outcome）の滞留

アラート：結果不明の最古が 15 分を超える、件数が平常の 5 倍。

結果不明は、コネクタへ送ったが結果がわからない試行である（タイムアウト、接続の切断、デプロイ・フェイルオーバーでの中断）。**再送で解決しない。** 参照番号で照会し、アクワイアラの記録に合わせる（[ADR-0004](../decisions/0004-idempotency.md)、[payments.md](../architecture/payments.md)）。

1. 件数、コネクタ、最古の時刻、原因（コネクタの障害、デプロイ、AZ の障害）を確かめる。
2. unknown-outcome のキューの処理が進んでいるかを見る。照会自体が失敗しているなら（接続先の照会 API も止まっている）、照会の間隔を広げ、接続先の回復を待つ。**照会できない間に、同じ決済を別の参照番号で送り直さない**（二重のオーソリになる）。
3. 加盟店への見え方：PaymentIntent は `processing` のまま。加盟店に、処理中の決済が最終的に確定し Webhook で通知されることを告知する。
4. 1 時間を超えて照会できないものが残るなら、SEV2 に上げ、接続先に参照番号の一覧で確認を依頼する。
5. 照会の結果で、成立していたものは成功に、していなかったものは失敗にする（仕訳と Event が出る）。オーソリの有効期限が近いもので、加盟店の意図がわからないものは、取り消す判断をお金の担当が行う。
6. 最終確認は翌営業日の精算ファイルの照合で行う。

#### 照合の不一致（reconciliation breaks）

アラート：T+1 営業日で残る不一致（チケット）、T+2 営業日で残る不一致（呼び出し）、台帳の整合の検査の失敗（呼び出し、SEV2）。

| 段階 | 誰が | すること |
| --- | --- | --- |
| T+0〜T+1 | 照合のジョブ（自動） | 精算ファイル・銀行の明細と台帳を突き合わせ、既知の型（タイミングのずれ、手数料の端数、通貨の換算）を自動で解消する |
| T+1 に残る | Ops（営業時間） | 不一致を型で分ける：こちらにない取引、接続先にない取引、金額の違い、状態の違い。結果不明の照会の漏れ、失った範囲（DR）でないかを先に見る |
| T+2 に残る | Ops → お金の担当（呼び出し） | NFR-005 の違反。影響する加盟店の Payout を保留するか判断する。原因がコードなら、インシデントとして扱い、訂正の仕訳を計画する |
| 台帳の整合の検査の失敗 | お金の担当（即時、SEV2） | 仕訳の追記を伴う新機能のフラグを切る。差の出た口座と、最初に差が出た時刻を特定する |
| 1 週間を超えて残る、または金額が大きい | お金の担当 → 経理の責任者、PM | 会計上の扱い（仮勘定）と、加盟店・接続先への連絡を決める |

- 不一致の解消は、台帳の訂正の仕訳（[delivery.md](../architecture/delivery.md) の 5.3 節）か、接続先への問い合わせで行う。**集計の値や状態のテーブルを手で直して、不一致を消さない。**
- 詳細な型と手順は [payouts-and-reconciliation.md](../architecture/payouts-and-reconciliation.md) にあり、E4 で `reconciliation-break.md` として個別の runbook にする（[README.md](README.md) の 4 節）。

#### カード番号の漏洩の疑い

アラート：カード番号の走査で検出（[observability.md](../architecture/observability.md) の 4.2 節）、外部からの報告。

1. SEV2 で宣言し、セキュリティの担当を呼ぶ。漏洩が確定したら SEV1 に上げる。
2. **広げない。** 検出したロググループ・バケットへの読み取りを、調査の担当だけに絞る。原因の経路（ログの出力、エラーの報告、Dispute の証拠のファイル）を、フラグかデプロイで止める。
3. 証拠を保全する（検出の記録、該当の行の場所、時刻の範囲）。**カード番号そのものを、チケット・チャット・この記録に写さない。** 場所と件数だけを書く。
4. 範囲を特定する：どのカード番号が、どこに、いつから、誰が読めたか（CloudTrail のログの読み取りの記録）。
5. 該当のデータを、PCI DSS の手順に従って消去し、消去の記録を残す。バックアップ・アーカイブ（log-archive の Object Lock）にも及ぶかを確かめる。Object Lock のコンプライアンスモードは期間内に消せないので、アクセスの制限と記録で扱い、QSA と相談する。
6. 法務・PM と、カードブランド・アクワイアラ・監督官庁への報告の要否を決める（[security.md](../architecture/security.md)）。

#### KMS のスロットリング（CDE）

1. どの操作（`GenerateDataKey`・`Decrypt`）が、どのサービスから増えたかを見る。
2. 攻撃（カードテスティングで vault-ingest への要求が急増）なら、WAF のレート制限を強め、[fraud.md](../architecture/fraud.md) の手順につなぐ。
3. 正常な増加なら、上限の引き上げを申請し（[capacity.md](../architecture/capacity.md) の 3.7 節）、その間は vault-ingest の受け付けを絞る。

### オンコール

- 一次は Ops、二次は Dev（週替わり）。一次が 5 分（SEV1）・15 分（SEV2）で応答しなければ、二次を呼ぶ。
- **お金の担当と、CDE の承認者（CDE のロールバックに 2 人の承認が要る）も、当番を持つ。**
- 呼び出しの道具と当番の表は、E10 で決める。個別の runbook の一覧と作る Epic は [README.md](README.md) の 4 節にある。

## エスカレーション

| 状況 | 連絡先 |
| --- | --- |
| SEV1 の宣言 | Ops の責任者、Dev のテックリード、PM |
| お金の誤り、二重の請求、台帳の整合の失敗、T+2 の照合の不一致 | 上記に加えて、お金の担当と経理の責任者 |
| カード番号の漏洩の疑い、テナント境界の破れ | 上記に加えて、セキュリティの担当と法務（報告の要否を判断する） |
| コネクタの障害 | 接続先の契約上の窓口（連絡係が行う） |
| リージョンの切り替えを考える | Ops の責任者（承認）。[disaster-recovery.md](disaster-recovery.md) |
| AWS 側の障害 | AWS サポートにケースを開く |
| 1 時間たっても被害を止められない | 重さを 1 段上げる |

## 事後

- **振り返り**を、SEV1・SEV2 では必ず、解決から 5 営業日以内に行う（責任追及をしない）。書くこと：時系列、影響（時間、加盟店数、失敗した決済の件数と金額、結果不明の件数、消費したエラーバジェット）、お金の回復の結果（照会・訂正・照合の完了日）、検知までの時間、原因、再発防止の対策。
- **再発防止を Intent にする。** Claude が調査結果から Intent の Issue を起票する（Maintain 段）。
- お金・カード番号・テナント境界に関わるものは、QA にも共有し、[quality.md](../quality.md) のリスクと対策を見直す。PCI DSS に関わるものは、セキュリティの担当が年次の評価の記録に加える。
- この手順と、関係した個別の runbook で足りなかったことを反映する。
