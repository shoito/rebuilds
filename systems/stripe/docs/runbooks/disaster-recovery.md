# Runbook: 災害復旧（AZ の障害、リージョンの障害、失った決済の回復、訓練）

- Owner: Ops
- 対応するアラート: AZ の障害（複数のサービスで 1 つの AZ のターゲットが不健全）、大阪からの合成監視の連続失敗、`AuroraGlobalDBRPOLag` の超過、訓練（四半期に 1 回）
- 最終確認日: 2026-09-26

構成と目標は [infrastructure.md](../architecture/infrastructure.md) の 5 節、方針は [ADR-0030](../decisions/0030-payments-disaster-recovery.md) にある。目標は NFR-007（AZ：RPO 0、RTO 5 分）と NFR-008（リージョン：RPO 1 分、RTO 1 時間。失った範囲はコネクタへの照会で回復する）。

## 症状

| 場面 | 見え方 |
| --- | --- |
| A. AZ の障害 | 1 つの AZ のタスク・Aurora のインスタンスが不健全になる。AWS Health Dashboard に、東京の 1 つの AZ のイベント |
| B. リージョンの障害 | 東京の本体と CDE が同時に応答しない。大阪からの合成監視がすべて失敗する |
| C. 複製の遅延 | `AuroraGlobalDBRPOLag` が 10 秒を超え続ける（東京は正常） |
| D. 論理的な破損 | 誤ったマイグレーション・操作で、状態のテーブルのデータが消えた・壊れた |
| E. 訓練 | 四半期に 1 回（staging）、年 1 回（本番の switchover） |

## 影響

- A：数十秒〜数分、決済の失敗と結果不明が増える。コミット済みのデータは失わない。
- B：切り替えまで（目標 1 時間以内）、決済を受けられない。複製の遅延ぶんの書き込みを失い、照会で回復するまで、一部の決済の記録が欠け、影響を受けた加盟店の Payout が遅れる。
- C：この状態でリージョンの障害が起きると、失う範囲が広がる。

## 確認

1. AWS Health Dashboard と Grafana の AZ ごとの内訳で、1 つの AZ か、リージョン全体かを見分ける。
2. Aurora（live と Vault）のクラスタのイベントで、フェイルオーバーの有無と現在の writer の AZ を確かめる。
3. リージョンの障害を疑うときは、大阪の合成監視と、別の回線からの到達性の両方で確かめる。
4. **`AuroraGlobalDBRPOLag` の直近の値（live と Vault）を記録する。** 失った範囲の目安になる（B の手順で使う）。

## 対処

### A. AZ の障害

基本は自動で回復する。

1. インシデントを宣言する（SEV2 から。[incident-response.md](incident-response.md)）。
2. Aurora（live、Vault）が別の AZ へ自動でフェイルオーバーしたことを確かめる。5 分たっても writer がなければ、手動でフェイルオーバーする。
3. ECS が残る 2 AZ でタスクを起動しているか確かめる。足りなければ最小タスク数を上げる。
4. 結果不明の滞留を見る。フェイルオーバー中の試行は、照会のキューで片付く。滞留が 15 分を超えたら [incident-response.md](incident-response.md) の「結果不明」に進む。
5. AZ が回復したら、台数を平常に戻す。

### B. リージョンの障害（東京 → 大阪）

**切り替えの判断は、インシデントの指揮者（IC）が行い、Ops の責任者が承認する。** AWS の見込みで 30 分以内に回復しそうなら、待つことも選ぶ（RTO 1 時間の内に収まるなら、データを失わない待機のほうがよい）。

1. SEV1 を宣言し、加盟店へ告知する（ステータスページ）。
2. **東京への書き込みを止める。** 東京の API に届くなら、`ops.read_only_mode` を有効にする。届かなくても、CloudFront のオリジンの切り替え（手順 7）までは大阪へ流さない。
3. **失った範囲を記録する。** 手順「確認」の 4 の `AuroraGlobalDBRPOLag`（live と Vault）と、東京が応答しなくなった時刻を、インシデントの記録に書く。
4. **DB を切り替える。** live、Vault（cde-live）の順に、Aurora Global Database の大阪の二次を昇格させる。
   - 東京の writer が生きていれば、switchover（RPO 0）を使う。
   - 応答しなければ、マネージドなフェイルオーバー（`aws rds failover-global-cluster --allow-data-loss`、大阪のリージョンで実行）を使う。
   - RDS のイベントで、write fencing の成否を確かめる。
5. 大阪の reader を writer に昇格させた後、reader を 1 台足す。test の DB（headless）は、後回しにする（RTO 4 時間）。
6. **アプリを広げる。** 「DR：大阪を有効化」のワークフローで、大阪の各サービスの最小・最大のタスク数を東京と同じにする（本体と CDE。CDE は CDE の経路のワークフローで、2 人の承認を得る）。状態ファイルは大阪のバケットにある。
7. **入口を切り替える。** `global/edge` の変数 `active_region` を大阪にして apply する（本体の CloudFront と、CDE の `vault.<domain>` の CloudFront の両方）。
8. **決済の受け付けを、段階的に再開する。**
   1. 社内の加盟店で、live の合成監視（オーソリ → 取り消し）がコネクタごとに成功することを確かめる。**接続先が大阪の送信元 IP を受け付けているか**を、ここで確かめる。
   2. 読み取り専用を解除する。レート制限を平常の 50% にして開き、15 分ごとに上げる（[rate-limiting.md](../architecture/rate-limiting.md)）。
9. **失った決済を回復する**（次の節「失った決済の回復」）。受け付けの再開と並行して進める。
10. 加盟店へ、再開と、影響（一部の決済の記録の遅れ、Payout の遅れ）を告知する。

**東京へ戻す（フェイルバック）**：東京の回復後、Aurora が東京を二次として自動で加え直す。複製が追いついたら、別の計画作業として switchover（RPO 0）で戻す。月末・月初は避ける。急がない。

### 失った決済の回復（B の後）

目的：東京で成功し、大阪に届かなかった決済・返金・仕訳を、元の ID で作り直し、二重の請求をなくす。

1. **範囲を決める。** 開始 ＝ 東京が応答しなくなった時刻 − 記録した複製の遅延 − 5 分。終了 ＝ 大阪の昇格の時刻 ＋ 5 分。
2. **Payout を保留する。** 範囲の中で決済・返金のあった加盟店に、`ops.payout_hold` を加盟店単位で有効にする。範囲の特定が遅れるなら、全加盟店の当日の Payout を保留する。
3. **古い一次のスナップショットを確かめる。** RDS のスナップショットに `rds:unplanned-global-failover-...` があれば、手動のスナップショットにコピーして保全する（保持期間で消えないように）。東京が回復したら、隔離した VPC に復元して、範囲の行を取り出せる。
4. **アクワイアラへ照会する。** 「DR：失った範囲の照会」のジョブ（workers の unknown-outcome のキューを使う）に範囲を渡す。ジョブは、コネクタごとに次の順で照会する。
   - 取引の照会 API（時間の範囲、または参照番号）
   - 大阪の DB に残っている試行の記録（`pending_send`）
   - 3 のスナップショット（取れていれば）
5. **ジョブの結果を確かめる。** ジョブは、見つかった取引を次のどれかに分け、一覧を出す。
   | 分類 | 処理 |
   | --- | --- |
   | 大阪にある | 何もしない |
   | 大阪になく、アクワイアラで成立（オーソリ・キャプチャ・返金） | 参照番号から元の ID を復元し、状態と仕訳を作り直し、元の ID の Event を発行する |
   | 大阪になく、オーソリだけで、加盟店に作成の応答を返した記録もない | 取り消す（void） |
   | 同じ冪等キーの決済が大阪で新しく作られ、アクワイアラが重複として扱った | 新しい決済を、アクワイアラの結果に合わせる。二重の請求がないことを確かめる |
   | 判断できない | 手作業の確認の一覧に入れる |
6. **作り直しはお金のオーナーが承認する。** 件数と、通貨ごとの金額の合計を確かめてから、実行を承認する。作り直しは冪等（元の ID が一意制約になる）なので、途中で止まっても再実行してよい。
7. **精算ファイルで最終確認する。** 翌営業日の精算ファイルの照合で、範囲の不一致が 0 件になったら、`ops.payout_hold` を解除する。
8. 手作業の確認の一覧は、経理の担当とサポートが加盟店ごとに片付ける。

### C. 複製の遅延

1. `AuroraGlobalDBRPOLag` と、東京の writer の書き込み量、リージョン間の回線の状態を確かめる。
2. 書き込みの急増（大型セール）なら、遅延が収まるのを待つ。10 分を超えて続くなら、SEV3 のインシデントにし、AWS サポートにケースを開く。
3. `rds.global_db_rpo` は設定しない（東京の決済を止めるため。[ADR-0030](../decisions/0030-payments-disaster-recovery.md)）。

### D. 論理的な破損

1. 原因の機能のフラグを切る、原因のジョブを止める。
2. 破損の直前の時刻を、ログと監査ログから特定する。
3. Aurora の PITR で、隔離した VPC に新しいクラスタを復元する。本番のクラスタは上書きしない。
4. 状態のテーブルは、失われた行だけを取り出して戻す。**台帳は、欠けた仕訳の追記として戻す。** 既存の仕訳を上書きしない。
5. 戻した行について、Event を積み直す。
6. 台帳の整合の検査と、該当する期間の照合をやり直す。
7. 復元したクラスタを消す。

### E. 訓練

| 訓練 | 頻度 | 環境 | 確かめること |
| --- | --- | --- | --- |
| PITR からの復元 | 四半期 | prod の中の隔離した VPC | 復元の時間、行数、RLS が有効であること、台帳の残高の再計算が一致すること |
| 計画外のフェイルオーバーと失った決済の回復 | 四半期 | staging・cde-nonprod（模擬のアクワイアラ） | 書き込みを続けたまま東京を止め、B の手順を最後まで行う。RTO 1 時間以内、回復の後の台帳の整合と照合の不一致が 0 件、冪等キー付きの再送で二重のオーソリがない |
| 本番の switchover | 年 1 回 | 本番 | 大阪で決済を受け、東京へ戻す。接続先が大阪の送信元 IP を受け付けること |
| 大阪の待機の構成の確認 | 月次 | 本番 | 大阪の合成監視（test）、大阪の Terraform の plan に差分がない、ECR・Secrets・KMS のレプリカの同期 |

結果（時間、問題点）を、この runbook の末尾の記録に残す。

## エスカレーション

- A で 5 分たっても DB の writer がない → SEV1 に上げ、Dev のテックリードを呼ぶ。
- B の判断 → Ops の責任者。告知の文面は PM と合意する。
- 失った決済の回復で、判断できない取引が残る、または金額の合計が合わない → お金のオーナーと経理の担当。
- 回復の結果、二重の請求が顧客に起きていた → SEV1。PM に報告し、返金と顧客・加盟店への連絡を決める。
- AWS 側の障害 → AWS サポートにケースを開く。

## 事後

- 調査結果を Intent の Issue として起票する（Maintain 段）。
- 実際の切り替えと訓練で計測した RTO・RPO、失った決済の件数と回復にかかった時間を記録し、目標を満たさなければ Intent を起票する。
- 照会 API で回復できなかった接続先があれば、[ADR-0030](../decisions/0030-payments-disaster-recovery.md) の前提を見直す。
- この手順で足りなかったことを、ここに反映する。
