# Runbook: インシデント対応

- Owner: Ops
- 対応するアラート: すべての呼び出し（page）のアラート（[observability.md](../architecture/observability.md) の 8 節）。個別の場面は「Kafka に固有の場面」の節
- 最終確認日: 2026-09-27

個別の手順（[deploy-and-rollback.md](deploy-and-rollback.md)、[disaster-recovery.md](disaster-recovery.md)）の上に立つ、共通の進め方と、Kafka に固有の場面（AZ の喪失、オフラインのパーティション、うるさい隣人、耐久性の監査の不一致、テナントの境界の破れ、エッジの不調）。進め方の骨格は他の題材（Stripe の [incident-response.md](../../../stripe/docs/runbooks/incident-response.md)）と同じ。

## 症状

次のどれかのときに、インシデントを宣言する。迷ったら宣言し、後で重さを下げる。

- 呼び出しのアラートが鳴った
- 利用者や社内から、書き込みの失敗・データの欠け・他の組織のデータが見えるという報告が来た
- カナリア・耐久性の監査・隣のテナントの確認で不一致が出た

## 影響

### 重さ（severity）

| 重さ | 基準 | 例 | 最初の応答 | 告知 |
| --- | --- | --- | --- | --- |
| SEV1 | `acks=all` で成功を返した書き込みの喪失（疑いを含む）。他のテナントの資源・データが見えた。1 つの物理クラスタ以上で produce・fetch ができない。オフラインのテナントのパーティション | カナリアの抜け、監査の不一致、`tenant_boundary_violation`、リージョンの障害、KRaft のクォーラムの喪失 | 5 分以内 | 30 分以内に利用者へ。以後 30 分ごと |
| SEV2 | 一部の利用者の produce・fetch が失敗・遅延する。SLO の速いバーンレート。1 つの AZ の喪失 | AZ の喪失、1 つのブローカーの劣化、うるさい隣人による背圧、min ISR を下回るパーティション | 15 分以内 | 1 時間以内に影響する利用者へ |
| SEV3 | 劣化しているが、データは正しい。回避できる | 管理 API の遅れ、メトリクスの遅れ、反映の遅れ、階層型の上げの遅れ | 営業時間内 | 必要なら |
| SEV4 | 利用者への影響がない | 1 つのエージェントのレプリカの失敗 | 営業時間内 | なし |

受け付けた書き込みの喪失とテナントの分離に関わるものは、範囲が 1 件でも SEV1 にする（[intent.md](../intent.md) の守るべき振る舞い）。

## 確認

1. どのアラート・報告から始まったかを記録する。
2. 影響の範囲を見る：全体か、1 つの物理クラスタか、1 つの AZ か、1 つのブローカーか、1 つの論理クラスタか。Basic か Standard か。
3. 直近の変更を見る：ブローカーのロール（`broker_rollouts`）、データ面の部品のデプロイ、運用のフラグ（`ops_flags`）、再配置（`reassignment_jobs`）、cordon・降格（`broker_states`）、制御面のデプロイ、Terraform の apply。
4. データへの影響を見る：カナリア（AUD-7）、直近の監査（AUD-1〜6）、URP・min ISR・オフラインのパーティション、unclean な選出の記録。

## 対処

### 役割

| 役割 | 担う人 | 責任 |
| --- | --- | --- |
| 指揮者（IC） | 最初に応答したオンコール。SEV1 では Ops の責任者に引き継いでよい | 重さ、方針、大きな判断（物理クラスタの変更の凍結、降格、リージョンの切り替え、unclean な選出の承認の依頼） |
| 作業者 | オンコールの Ops、呼ばれた Dev | 調査と復旧 |
| 耐久性の担当 | Dev のテックリード | データの喪失・テナントの分離の評価、壊れた複製の扱い、利用者への説明の中身 |
| 連絡係 | IC が指名する（PM が望ましい） | 利用者、社内、AWS への連絡 |
| 記録係 | IC が指名する | 時刻付きの記録 |

SEV1 では、指揮者は手を動かさない。

### 進め方

1. **宣言する。** インシデント用の場を、このシステムと別の道具に作る。
2. **被害を止めることを、原因の特定より優先する。** 順番：
   - 同じ物理クラスタへの変更を止める（`rollout.pause`、再配置の取り消し、Argo CD の同期の停止）
   - 直近の変更のフラグを切る、直近のデプロイを戻す（[deploy-and-rollback.md](deploy-and-rollback.md)）
   - 劣化したブローカーを降格する（リーダーを外す）
   - データを消しうる処理を止める（`tiered.delete.pause`、保持の削除の停止）
   - 問題の論理クラスタのクォーラムを上書きで厳しくする
3. **データを消さない。** ログのセグメント、S3 のオブジェクト、監査の事象、KRaft のスナップショットは証拠であり、回復の材料である。壊れた疑いのある複製も、調べ終わるまで消さない（ボリュームを外して残す）。
4. **告知する。** 何が起きているか、どの操作に影響するか（produce、fetch、管理の操作）、次の更新はいつか。原因の推測は書かない。
5. **収束を確かめる。** SLO の指標が戻り、合成監視が成功し、URP が 0 になり、15 分たってから解決とする。データの回復・監査の照合が残るときは、インシデントを閉じず、重さを下げて続ける。

### Kafka に固有の場面

#### AZ の喪失

アラート：合成監視の連続失敗（AZ）、1 つの AZ の全ブローカーの登録の喪失、NLB の zonal health、AWS Health Dashboard。

1. SEV2 を宣言する。1 つの AZ だけか、を確かめる（2 つ以上なら SEV1。リージョンの障害として [disaster-recovery.md](disaster-recovery.md) も見る）。
2. **期待される状態を確かめる**（[replication-and-durability.md](../architecture/replication-and-durability.md) の 3.2 節）：
   - 全てのパーティションで ISR が 2。`acks=all` の書き込みは成功している。
   - `UnderMinIsrPartitionCount` と `OfflinePartitionsCount` が 0。0 でなければ、その AZ の前から別の AZ の複製が落ちていた。「オフラインのパーティション」へ。
   - リーダーは残る 2 つの AZ へ移っている（1 分以内。NFR-009）。
   - コントローラーは 2 台で過半数を保っている。
3. **入口**：その AZ の NLB の EIP 宛ての接続は失敗する（その AZ のブローカーも止まっているので影響は小さい）。NLB の zonal shift で、ブートストラップからその AZ を外す。
4. **負荷**：残る 2 つの AZ のブローカーの送信と EBS が、基準の帯域の 90% 以内か。超えそうなら、背圧が効いていることを確かめ、うるさい隣人の手順と同じくクォータを見る。
5. **しないこと**：
   - 残りの 2 つの AZ に 3 つ目の複製を作らない（[replication-and-durability.md](../architecture/replication-and-durability.md) の 4 節）。AZ の不変条件を保つ。
   - その AZ のブローカーを退役させない。AZ が戻れば、同じボリュームで追いつく。
   - コントローラーの入れ替えをしない（S1 の 3 台では、もう 1 台の失敗に耐えない）。この間は他の変更を全て止める。
6. **長く戻らないとき**（AWS の見込みで数時間を超える）：Dev のテックリードと、(a) 待つ、(b) 別の AZ ID（apne1-az3 は使わない方針）への移し替えを検討する、のどちらかを決める。S1 では (a) を基本にする。耐久性は ISR 2 で保たれているが、もう 1 つの失敗で書き込みが止まることを利用者に告知する。
7. **戻ったとき**：その AZ のブローカーが追いつき、ISR が 3 に戻るまで、再配置やロールをしない。追いつきの間は、戻ったブローカーの EBS と送信が高くなる。優先リーダーへの戻りを確かめる。

#### オフラインのパーティション

アラート：`OfflinePartitionsCount` > 0、`UnderMinIsrPartitionCount` > 0。

1. `OfflinePartitionsCount` > 0 でテナントのパーティションなら SEV1、内部のトピック（`__consumer_offsets` など）なら影響が全テナントに及ぶので SEV1。
2. 対象のパーティションを特定し（エージェントの表示、KRaft のメタデータ）、ISR と ELR と複製のブローカーを見る。
3. **ISR か ELR の複製のブローカーを戻すことを最優先にする。**
   - 止まったブローカーの再起動（ログの回復を待つ。目標 5 分）。
   - ノードの喪失なら、同じ AZ の新しいノードにボリュームを付け替える。
   - ELR の複製が戻れば、それがリーダーになる（KIP-966）。
4. **unclean な選出をしない。** `unclean.leader.election.enable=false` は固定（[ADR-0012](../decisions/0012-durability-settings-and-elr.md)）。ISR と ELR の外の複製をリーダーにすると、成功を返した書き込みを失う。
5. 最後の手段（ISR と ELR の複製が全て戻らない見込み。ボリュームの喪失など）：
   - Dev のテックリードの承認と、影響するテナントへの事前の連絡を要件にする（[replication-and-durability.md](../architecture/replication-and-durability.md) の 5.2 節）。
   - 選ぶ複製の最後のオフセットと、失う範囲（高水位との差）を記録する。
   - `unclean_elections` に、パーティション、承認者、理由、失った範囲の見積もり、連絡の時刻を残す（AUD-6 で照合される）。
   - 行う前に、失う範囲が S3 に上がっていないか（階層型の保存の前の部分なら残る）を確かめる。
6. `UnderMinIsrPartitionCount` > 0 でオフラインでないとき：書き込みは失敗しているが、データは失っていない。複製のブローカーを戻す。ディスクの逼迫・遅いブローカーが原因なら、その手順（`broker-disk-pressure.md`・`slow-broker-demotion.md`。E3）へ。

#### うるさい隣人

アラート：背圧が 1 分以上続く、クォータの中で絞られたテナントの割合の上昇、1 つのブローカーの遅延の急増。

1. SEV2（影響が 1 つのテナントに留まるなら SEV3）。
2. **どの資源か**を見る：書き込み・読み取りの帯域、要求の処理時間（CPU）、接続の試み、パーティションの作成・削除、InitProducerId、リバランス、リモートの読み取りの待ち行列、圧縮のトピック（[multi-tenancy-and-quotas.md](../architecture/multi-tenancy-and-quotas.md) の 11.3 節の N1〜N10 の型）。
3. **加害のテナントを特定する**：運用のダッシュボード（テナント）の上位 100 の論理クラスタの、要求・バイト・throttle の時間・接続。該当するブローカーで、背圧の直前に増えた論理クラスタ。
4. **期待される振る舞いか**を確かめる：クォータを超えた分は throttle され、ブローカーの合計が安全な上限の 90% を超えると、全テナントが割り当ての比で下がる（背圧。[ADR-0027](../decisions/0027-dynamic-quota-coordinator-and-backpressure.md)）。クォータの中の被害者が絞られていれば、配分か背圧の値が合っていない。
5. **止める**：
   - 加害のテナントの論理クラスタに、上書き（`logical_cluster_limits`）で厳しいクォータを掛ける。理由と期限を書く（監査ログに残る）。
   - クォータのコーディネーターが止まっていれば、`quota-coordinator-down.md`（E7）へ。静的な等分に戻っているかを見る。
   - 特定のブローカーに負荷が偏っているなら（熱いパーティション）、再配置を依頼する（[metadata-and-control.md](../architecture/metadata-and-control.md) の 4 節）。物理クラスタ全体が高ければ、ブローカーを足す（`broker-scale-out.md`）。
6. **連絡**：加害のテナントには、上限と使い方（接続の再利用、バッチ、`linger.ms`）を案内する。攻撃や不正の疑い（接続の嵐、認証の失敗の急増）なら、Envoy の RBAC で送信元を拒否し、セキュリティの担当を呼ぶ。
7. 上書きは期限を過ぎたら外す。外し忘れを `tenant-limit-override.md`（E7）の手順で確かめる。

#### 耐久性の監査の不一致（カナリアの抜けを含む）

アラート：カナリア（AUD-7）の抜け、AUD-1〜6 の不一致、階層型の監査の重大な破れ（[tiered-and-object-storage.md](../architecture/tiered-and-object-storage.md) の 6.7 節）。

1. **SEV1 を宣言する。** 監査の誤りの可能性があっても、喪失として扱って始める。
2. **消す処理を止める**：その物理クラスタで `tiered.delete.pause` を立て、保持による削除と S3 の削除を止める（データを救える可能性を残す）。同じ物理クラスタへの変更（ロール、再配置、cordon、降格、Strimzi の同期）を止める。
3. **範囲を特定する**：
   - どの不変条件か（AUD-1：説明できない `log-start-offset` の前進、AUD-2：高水位以下の切り詰め、AUD-3：複製の CRC の不一致、AUD-4：階層型の抜け、AUD-5：設定と AZ の配置、AUD-6：unclean な選出の記録の欠け、AUD-7：カナリア）。
   - 対象のパーティション・複製・ブローカー・時刻。監査の事象（`__<brand>_durability_audit` と S3）の前後を読む。
4. **データを救う**（Kora の監査の考え方。複製があるので、早く気づけば救えることがある。[Kora](https://vldb.org/pvldb/vol16/p3822-povzner.pdf) の 4.6.3 節）：
   - 壊れたのが 1 つの複製（リーダーのストレージの破損による切り詰めなど）なら、その複製のブローカーを降格・停止し、正しい複製からリーダーを選び直す。壊れた複製のボリュームは外して残す。
   - 階層型のメタデータの食い違いなら、RLMM の各複製の見え方と `_rlmm/` のスナップショット、S3 のオブジェクトを突き合わせ、有効なセグメントを特定する。
   - 保持の設定の誤りなら、設定の変更の記録（`retention_config_changed`）と、変えた主体を特定する。
5. **確かめる**：救ったパーティションで、カナリアや監査の照合を、その場で回し直す。
6. **テナントへの連絡**：喪失が確定したら、影響したテナント（論理クラスタ、トピック、オフセットの範囲、時刻）に、耐久性の担当が確かめた内容で連絡する。推測を書かない。
7. **監査の誤りだったとき**：監査の規則の不具合として記録し、同じ誤りが出ないよう規則を直す（QA と一緒に）。インシデントは SEV を下げて閉じる。
8. `durability_incidents` に、不変条件、範囲、原因、救ったか、連絡の時刻を残す。

#### テナントの境界の破れ

アラート：`tenant_boundary_violation`、隣のテナントの確認の失敗。

1. SEV1。セキュリティの担当と Dev のテックリードを呼ぶ。
2. 該当する物理クラスタで、直近の名前空間のパッチ・TenantAuthorizer の変更を戻す（[deploy-and-rollback.md](deploy-and-rollback.md) の C）。原因の API が特定できれば、その API を名前空間の表で「拒否」に替える（運用のフラグ）。
3. Envoy のアクセスログとブローカーの監査の事象で、他のテナントの資源に届いた要求（主体、API、資源、時刻）を特定する。
4. 以降は `tenant-boundary-violation.md`（E8）。個人データを含みうるので、法務（intent.md の L4）に連絡する。

#### エッジの不調（NLB・Envoy・sni-router）

アラート：合成監視の失敗（ブートストラップ・AZ ごと）、NLB の健全なターゲットが 0、Envoy の上流への接続の失敗の急増、xDS の更新が 10 分ない。

1. 1 つの AZ か、全体かを見る。ブローカーの JMX が正常で、合成監視だけが失敗するなら、エッジを疑う。
2. 1 つの AZ の Envoy が全て止まった：Envoy を戻す。戻らなければ、その AZ のブローカーを降格してリーダーを他の AZ へ移す（読み取りは AZ をまたぐが、止まらない）。
3. sni-router が止まった：既存の経路は続く。新しい論理クラスタと、入れ替えたブローカーの Pod に届かない。sni-router を戻す。その間、ブローカーのロール・論理クラスタの作成を止める。
4. 証明書の期限切れ：全テナントの接続が失敗する。SEV1。`tls-certificate-renewal.md`（E12）の手動の更新。
5. 未知の SNI の急増（`edge` の拒否）：古いクライアントの設定か、走査の試み。送信元を見て、必要なら RBAC で拒否する。

#### KMS のスロットリング

1. どの操作か（S3 の SSE-KMS、EBS の付け替え）と、S3 Bucket Keys が有効かを見る（[ADR-0030](../decisions/0030-encryption-and-audit-logs.md)）。
2. 上限の引き上げを AWS に依頼する。続くなら、データ面のアカウントの分割を前倒しする（[infrastructure.md](../architecture/infrastructure.md) の 1 節）。

## エスカレーション

- SEV1 → Ops の責任者、Dev のテックリード（耐久性・分離）、PM（告知）。テナントの分離と個人データ → セキュリティの担当、法務。
- データの喪失が確定 → Dev のテックリードの承認で、テナントへの連絡の内容を決める。SLA の返金の対象か（法務、intent.md の L6）。
- AWS の障害（AZ、NLB、S3、KMS） → AWS のサポートにケースを開き、ケースの番号を記録する。
- 本家の不具合の疑い → Dev のテックリードが、本家の Jira に報告するか、既知の問題かを判断する。

## 事後

- ポストモーテムを 5 営業日以内に書く（非難しない形）。SEV1 は必須、SEV2 は IC が判断する。
- 調査結果を `changes/` の新しい `intent.md` として起票する（Maintain 段）。
- 耐久性・分離のインシデントは、Jepsen の形の試験・性質ベーステスト・監査の規則に、同じ型を再現する試験を足す（QA と Dev のテックリード）。
- 足りなかった個別の手順を、runbooks/README.md の候補に足す。
- この手順で足りなかったことを、ここに反映する。
