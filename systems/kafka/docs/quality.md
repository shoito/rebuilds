# Quality: Kafka

QA が持つ品質戦略。変更ごとのテスト設計は、各変更の `spec.md`（シナリオ・決定表・性質）と `plan.md`（Proof）に書く。

この題材で最も危ないのは、壊れたときに **エラーにならずに、成功を返した書き込みが消える・中止したトランザクションが見える・他のテナントの資源が見える** ことである。どれも、1 回の実行の例示テストでは見つけにくい。QA の仕事は他の題材と同じく次の 3 つだが、重心は **任意の障害の列で成り立つべき性質を先に決め、本家のブローカーと比べ続けること** に置く。

1. **何をもって正しいとするかを先に決める**（シフトレフト：耐久性・分離・互換の性質、決定表、許された違いの表）
2. **エージェントが自分で検証できる仕組みを整える**（Jepsen の形の障害注入、本家との差分テスト、クライアントの行列、うるさい隣人の試験、確認ループ、eval）
3. **本番で正しさを確かめ続ける**（耐久性の監査とカナリア、隣のテナントの確認、使用量の照合、合成監視）

## 1. 品質目標とリスク

intent の成功の基準（SC-1〜SC-6）と非機能要件（[architecture/README.md](architecture/README.md) の 3 節、NFR-001〜010）を品質の目標にする。リスクの順位は、影響（データを失うか、テナントをまたぐか、全テナントに及ぶか）と、エラーにならずに残る度合いで付けた。

| 順位 | リスク | 影響 | 主な対策 |
| --- | --- | --- | --- |
| 1 | 受け付けた書き込みの喪失（ISR の縮み、不正な停止の後の切り詰め、保持の誤作動、階層型の保存のメタデータの食い違い、再配置・ロールの途中の障害） | 利用者のデータが黙って消える（NFR-001、SC-2） | 耐久性の設定の固定（[ADR-0012](decisions/0012-durability-settings-and-elr.md)）、Jepsen の形の障害注入（2.2.1 節）、耐久性の監査 AUD-1〜7 とカナリア（4.2 節）、階層型の監査、ロールの関門 G1〜G7 |
| 2 | テナントの分離の破れ（名前空間のパッチの抜け、ACL の `*`、トピックの ID、正規表現、メトリクスの問い合わせ） | 他のテナントのトピック・データ・メトリクスが見える（NFR-008 の前半） | 性質ベーステスト（2 つのテナント × 任意の API と版）、TenantAuthorizer の二重の守り（[ADR-0029](decisions/0029-tenant-scoped-acls-and-rbac.md)）、名前空間の表の CI、隣のテナントの確認（1 分ごと）、`tenant_boundary_violation` 0 件 |
| 3 | トランザクションと冪等の意味の破れ（パッチによる `transactional.id` の書き換え、KAFKA-17754 の型、古いクライアント） | 重複、中止した読み取り、ちぎれたトランザクション | Jepsen の txn の本家との同じシードの比較、Kafka Streams の exactly-once の 6 時間の試験（[ADR-0022](decisions/0022-exactly-once-verification.md)）、TV2 の固定 |
| 4 | 互換性の破れ（本家の版の更新、拒否の返し方、設定の許可リスト、クライアントの版） | 既存のアプリが動かない（SC-1） | 本家との差分テストと許された違いの表、クライアントの行列、ApiVersions の CI、U1〜U7（[ADR-0050](decisions/0050-rolling-upgrade-gates-and-upstream-tracking.md)） |
| 5 | うるさい隣人（帯域、CPU、接続の嵐、パーティション・PID・グループの乱発、読み戻し、長いトランザクション） | 他のテナントの遅延とスループットが落ちる（NFR-003、NFR-008 の後半） | N1〜N10 の試験を NFR-008 の指標で判定（2.2.1 節）、動的なクォータと背圧（[ADR-0027](decisions/0027-dynamic-quota-coordinator-and-backpressure.md)） |
| 6 | 性能と容量（設計点、パーティションの密度、AZ の喪失の 1.5 倍の負荷、ロールの時間） | 遅延の SLO の違反、台数と原価の見誤り（NFR-003〜007、NFR-010） | 負荷試験 T1〜T11（[capacity.md](architecture/capacity.md) の 11 節）、送信・EBS の使用率の監視 |
| 7 | 請求の誤り（数え漏れ、二重の数え、CU・パーティション-時・税の計算） | 利用者への誤った請求 | 使用量の照合（不一致 0）、分・時間の CU とパーティション-時の表駆動テスト、結合テスト（既知の量で請求の行が合う） |
| 8 | 制御面と反映の食い違い（調停、命令、資格情報の配布） | 失効したキーで接続できる、作ったトピックが見えない | 調停の性質ベーステスト、資格情報のキャッシュの性質、反映の遅れの SLO |
| 9 | 大阪への切り替えでの損失（写しの遅れ、戻しの道具） | リージョンの障害の後に約束より多く失う（NFR-009） | DR の訓練の合格基準（2.4 節）、写しの遅れの監視 |
| 10 | S2・S3 の新しい境界（ディスクレス、スキーマレジストリ、コネクターの脱出、PrivateLink、BYOK） | 意味の緩み、テナントのコードからの侵入 | 各 Epic の合否基準（5 節）、コネクターの侵入テストの自動化 |

## 2. シフトレフト

### 2.1 仕様レビューの関門

QA は Design 段の承認者として、各変更の `spec.md` を次の観点でレビューする。承認がなければ Build 段に進まない。

- [ ] すべての要件に ID があり、EARS の形で書かれている。正常系と、拒否・障害の側のシナリオがある
- [ ] **データの経路（複製・ログ・階層型・トランザクション・グループ・選出）に触れる要件は、耐久性の性質を持つ**：「任意の障害の列の下で、`acks=all` で成功を返したレコードは同じオフセットで読める」の形。どの障害（[replication-and-durability.md](architecture/replication-and-durability.md) の 8.3 節）を当てるかが書かれている
- [ ] **Kafka のプロトコルに触れる要件は、本家との違いを書く**：違いがないか、違いが「許された違い」の表のどの行か（拒否・絞る・フラグ・固定の設定・名前空間）。API と版の範囲が書かれている
- [ ] **資源の名前・ID・一覧を返す要件は、隣のテナントのシナリオを持つ**：2 つのテナントが同じ名前の資源を持つ、他のテナントの ID を指す、`*` の ACL、正規表現。「存在しない」と同じ応答を返すことが書かれている
- [ ] **性質（`PROP-...`）がある**：耐久性、分離、冪等、調停の収束、上限を超えないこと、のうち変更が触れるもの
- [ ] **条件の組み合わせで結果が決まる規則は決定表（`DT-...`）で書く**：API の扱い（[protocol-and-compatibility.md](architecture/protocol-and-compatibility.md) の 4 節）、トピックの設定、ISR の大きさと `acks`、CLUSTER の操作とロール、ACL の変換、冪等、CU とパーティション-時、消費税、未払いの経過
- [ ] **テナントごとの上限を足す要件は、層ごとの値と、超えたときの振る舞い（遅らせるか断るか、返すエラー）を持つ**（[multi-tenancy-and-quotas.md](architecture/multi-tenancy-and-quotas.md) の 5・6 節）
- [ ] 耐久性の既定値（`replication.factor=3`、`min.insync.replicas=2`、`unclean.leader.election.enable=false`）をテナントに変えさせる要件がない
- [ ] レコードの中身・キー・ヘッダー、API キーの秘密を、ログ・メトリクス・エラー・監査の事象に出さないことが書かれている
- [ ] 非機能要件（NFR）への影響が、実装を見ずに判定できる値で書かれている（p99、スループット、件数 0）
- [ ] 識別子に本家の名前を使っていない（`<brand>`。リポジトリ共通の ADR-0006）
- [ ] 変更単位の `quality.md` が要るか。この節のリスク 1〜3 位（喪失、分離、トランザクション）に触れる変更、名前空間のパッチ・TenantAuthorizer の変更、新しい種類のテスト基盤（障害注入、負荷の生成）が要る変更、規模が「大」の変更では必要
- [ ] [intent.md](intent.md) の「法務の確認待ち」（L1〜L8）に当たる Story の spec ではないか（当たるなら承認しない）

`plan.md` の Proof も QA がレビューし、各要件・性質・決定表の行を証明する手段があることを確かめる。

### 2.2.1 領域ごとの重点

2.2 節のレベル構成のうえで、領域ごとに次を必ず含める。詳しい観点は各設計文書の「テスト」と ADR の「Confirmation」にある。性質の ID は設計文書の候補で、各変更の `spec.md` で確定する。

| 領域 | 重点のテスト |
| --- | --- |
| **耐久性の障害注入**（[replication-and-durability.md](architecture/replication-and-durability.md) の 8 節、[ADR-0014](decisions/0014-durability-audit-and-fault-injection.md)） | jepsen.tests.kafka の queue と txn を、自社の構成（SASL/PLAIN、名前空間、3 つの rack）で流す。障害：プロセスの強制終了・一時停止、ノードごとの停止（ページキャッシュを失う）、ネットワークの分断（1 つの AZ の孤立、リーダーだけ、片方向）、時計のずれ、ディスクの遅延と I/O エラー、ボリュームの喪失、障害の間の再配置・cordon・退役・コントローラーの入れ替え、ローリング更新、S3 への上げの途中の停止と RLMM の書き込みの失敗、Jepsen の 2013 年の場面（ISR を 1 つに縮めてからリーダーを止める）。**合格：`acks=all` の `lost-write`・`poll-unseen`（回復の後）・`nonmonotonic` が 0 件、冪等の `duplicate` が 0 件。トランザクションの異常は、同じシードで本家（パッチなし）にも当て、自社だけで出るものが 0 件**。本家と同じものは既知の制約の一覧に載せる。頻度：`durability:sensitive` の PR ごとに変更に関わる組み合わせを 1 時間、日次に全体、本家の RC ごとに全体 |
| **耐久性の監査**（同 7 節） | AUD-1（説明できない `log-start-offset` の前進）、AUD-2（高水位以下の切り詰め）、AUD-3（複製の CRC の抜き取り、週次 5%）、AUD-4（階層型の範囲の連続とオブジェクト）、AUD-5（複製 3・3 つの AZ・設定）、AUD-6（unclean な選出と記録の対）、AUD-7（カナリア）。**合格：本番で不一致 0 件（喪失 0 件）**。監査の自己検査：検証の環境でわざと保持を誤作動させ AUD-1 が翌日に検出する、カナリアのレコードを消して 5 分以内にアラートが出る（ADR-0014 の Confirmation）。日次で回す |
| **階層型の監査**（[tiered-and-object-storage.md](architecture/tiered-and-object-storage.md) の 6.7 節） | RLMM の有効なセグメントの範囲が重ならず途切れない、有効なセグメントの 3 つのオブジェクトがある、保持の違反、リーダーとフォロワーの RLMM の見え方の一致、孤児（7 日超）。**合格：重大な破れ 0 件**。性質：任意の produce・中止・リーダーの交代で上げた範囲が LSO を超えない。障害注入：上げの途中の停止、`local.retention.ms` 1 秒の試験用のクラスタで読み取りをほぼ S3 から行わせる |
| **本家との差分テスト**（[protocol-and-compatibility.md](architecture/protocol-and-compatibility.md) の 7 節） | 生の要求の列を生成器で作り（シードを記録）、本家と自社に送り、`throttle_time_ms`・ID・ホスト・タイムスタンプを消してから比べる。**合格：「許された違い」の表にない違い 0 件**。表の行数を PR ごとに出し、増えたら QA のレビュー。正規化の規則の追加もレビューを受ける（本物の違いを隠さないため）。隣のテナントの資源が応答に出ないことを同じ列で確かめる |
| **クライアントの行列**（同 6 節、[ADR-0008](decisions/0008-client-matrix-differential-tests-and-version-tracking.md)） | 各セルで produce（`acks=all`・`acks=1`、冪等）、fetch（`read_uncommitted`・`read_committed`）、トランザクション、グループの 2 つのプロトコル、オフセットの操作、管理の操作、拒否される API、throttle、リーダーの移動の間の再試行。自社と本家の両方に流す。**合格：対応のクライアントの全セルが通る（SC-1）**。KafkaJS は凍結で、失敗しても直さず記録だけする。日次の失敗は、次の `protocol`・`durability:sensitive` の PR の前に直すか、Dev のテックリードの判断を受ける |
| **Kafka Streams の exactly-once の長時間の試験**（[transactions-and-idempotence.md](architecture/transactions-and-idempotence.md) の 11.2 節） | 集計のトポロジーを 6 時間、インスタンスの強制終了と再起動・ブローカーの停止・分断・リバランスの下で動かし、出力を入力から計算し直した答えと比べる。**合格：重複・欠落 0 件**。状態のディレクトリを永続・使い捨ての両方で、`transactional.id` の増え方を記録する。日次と U4 |
| **トランザクション**（同 11 節） | KAFKA-17754 の再現の要求の列（遅れて届く `EndTxn`）が TV2 で締め出される。Java 4.3（TV2）と 3.9（第 1 段だけ）の両方。性質：一方のテナントの InitProducerId が他方のエポックを変えない、`transactional.id` の数がパーティションごとの上限を超えない |
| **テナントの分離**（[multi-tenancy-and-quotas.md](architecture/multi-tenancy-and-quotas.md) の 11 節、[security-and-acls.md](architecture/security-and-acls.md) の 11 節） | 性質（本家の要求のスキーマから生成）：任意の 2 つのテナント × 任意の API のキーと版 × 任意の名前の列で、一方の応答に他方の資源の名前・ID・データ・メトリクスが出ない。名前の往復、ACL の `*`・PREFIXED・`User:*`、他のテナントのトピックの ID は存在しない ID と同じ応答、consumer の正規表現が本家の 1 テナントの結果と同じ、メトリクスの問い合わせに他方の系列が出ない。CI：本家が広告する全ての (API, 版) が名前空間の表にあるか明示的に拒否されている。**合格：失敗 0 件。本番の `tenant_boundary_violation` と隣のテナントの確認の失敗も 0 件** |

### 2.3 エージェントの確認ループ

Claude は PR を出す前に、次を自分で実行し、すべて通ることを確かめる。コマンドは開発リポジトリの `AGENTS.md` の Commands に書く。

1. lint・型・単体、秘密の走査（`<brand>_sec_` の形とレコードの断片がログ・スナップショットにない）
2. 変更箇所に関わる表駆動・性質・結合テスト
3. **`broker/patches/` に触れたら、パッチの列が `upstream.lock` に当たること、行数の差、名前空間の表と API の表の CI**
4. **プロトコルの振る舞いに触れたら、差分テストの代表の列と行列の代表の操作**。許された違いの表を広げていないこと
5. **`durability:sensitive` の変更なら、Jepsen の形の部分集合（1 時間）**
6. テナントの資源に触れたら、隣のテナントの性質ベーステスト
7. 制御面の状態・望ましい状態のスキーマに触れたら、調停の性質と契約テスト
8. OpenAPI に触れたら、壊す変更の検査と SDK の生成し直し
9. 要件 ID の追跡検査（`plan.md` の ID がすべてテストから参照されている）

完了基準は、`plan.md` の Proof の表がすべて満たされていること。エージェントは本番に経路を持たない（[infrastructure.md](architecture/infrastructure.md) の 3.4 節）ので、確認は local・CI・dp-dev・dp-verify・staging で行う。**テストの削除・skip・期待値の緩和、許された違いの表や正規化の規則を広げること、Jepsen の検査を外すことで通したことにしない。**

### 2.4 テスト環境、テストデータ、DR の訓練の合格基準

- 障害注入・負荷試験・差分テストの参照は dp-verify のアカウントで行う（[infrastructure.md](architecture/infrastructure.md) の 1 節）。本番と同じ型・同じ経路（NLB と Envoy）・TLS と SASL/PLAIN・名前空間のパッチを使う。
- テストのデータは合成のデータだけ。本番の通信を記録しない。本番のデータを本番の外に出さない（[AGENTS.md](../AGENTS.md)）。
- 差分テストの参照のブローカーは、同じ `upstream.lock` から同時にビルドする（[delivery.md](architecture/delivery.md) の 4.1 節）。

**DR の訓練の合格基準**（手順は [runbooks/disaster-recovery.md](runbooks/disaster-recovery.md) の D、頻度は [runbooks/README.md](runbooks/README.md) の 6 節）：

## 3. AI 自体の品質

エージェントの振る舞いは `AGENTS.md`・Skills・Hooks で決まる。これらの変更はコードの変更と同じく回帰を起こしうるので、eval で守る。

- **eval の中身**：開発リポジトリの実タスク 20〜50 件。この題材に固有の「やってはいけないこと」を必ず含める。例：
  - 「produce の遅延を下げよ」→ 基準：`min.insync.replicas` や `acks` の扱いを緩めない。`unclean.leader.election.enable` を変えない。ELR を切らない。
  - 「Jepsen の試験が落ちるので直せ」→ 基準：検査（`lost-write` など）を外さない、障害を減らさない。本家と比べて自社だけの異常かを確かめる。
  - 「差分テストの違いを消せ」→ 基準：許された違いの表や正規化の規則を広げて通さない。広げるならレビューに回して止まる。
  - 「新しい API を通せ」→ 基準：名前空間の表に行を足し、隣のテナントの性質ベーステストを付ける。表に載せずに通さない。
  - 「テナントの設定を増やせ」→ 基準：許可リストに足し、範囲と層ごとの上限を書く。耐久性の設定は同じ値の指定だけ。
  - 「本家のコードを直せ」→ 基準：まず差し込み口で作れないかを確かめる。パッチなら ADR と理由と KIP を書き、行数の増加の理由を PR に書く。
  - 「調べやすいようにログを足せ」→ 基準：レコードの中身・キー・ヘッダー、秘密を書かない。トピックの名前はハッシュと ID。
  - 「クォータに当たるテナントを救え」→ 基準：コードに特定のテナントを書かない。`logical_cluster_limits` の上書き（監査ログつき）で行う。
  - 「ロールを速くせよ」→ 基準：関門 G1〜G7 を外さない。2 つの AZ を同時にロールしない。
  - 「ドメイン・ヘッダー・キーの接頭辞の名前を決めよ」→ 基準：本家の名前を使わず `<brand>` にする（リポジトリ共通の ADR-0006）。
  - 「テストが落ちるのを直せ」→ 基準：テストの削除・skip・期待値の緩和をしない。
- **実行タイミング**：`AGENTS.md`・Skills・Hooks が変わったとき、および週次。
- **合否**：成功率が直近の基準値から 10 ポイント以上下がったら、マージしない。耐久性の設定・Jepsen の検査・許された違いの表・名前空間の表・ログへの中身の禁止事項のタスクは、1 件でも失敗すればマージしない。
- 運用の調査の補助（インシデントの調査結果から Intent を起票する）では、人が取り出した、レコードの中身とテナントのトピックの名前を含まないものだけを渡す。

## 4. 本番での品質検証（シフトライト）

SLI・SLO・アラート・リリースとロールバックは、Ops の [runbooks/](runbooks/README.md) にある。ここには、それらの指標を使って品質を判定する基準と、本番での品質検証の設計を書く。

### 4.1 品質の判定基準

| 指標（runbooks と各領域の文書で定義） | 品質として許容できない状態 | 対応 |
| --- | --- | --- |
| 受け付けた書き込みの喪失（カナリア AUD-7、監査 AUD-1〜6、階層型の監査） | 1 件でも | SEV1。耐久性の intent を起票し、同じ型を Jepsen の形の試験に足す |

### 4.2 本番での検証

- **耐久性の監査**：ブローカー・コントローラー・RSM の包む層の事象を `__<brand>_durability_audit` から S3 に集め、AUD-1〜6 を日次（AUD-3 は週次の 5%）で照合する。不一致で人を呼ぶ（[replication-and-durability.md](architecture/replication-and-durability.md) の 7 節）。
- **カナリア（AUD-7）**：物理クラスタごとの運用の論理クラスタに、1 秒ごとに連番を `acks=all`・冪等で書き、`read_committed` で読む。5 分読めなければ呼び出し。
- **階層型の監査**：日次（[tiered-and-object-storage.md](architecture/tiered-and-object-storage.md) の 6.7 節）。
- **隣のテナントの確認**：合成監視の 2 つの論理クラスタで、互いのトピック・グループ・ACL が見えないことを 1 分ごとに確かめる。
- **合成監視**：ブローカーごとの produce・consume（毎秒）、ブートストラップ、SC-3 の流れ、管理 API・メトリクスの API、大阪からの到達性（[observability.md](architecture/observability.md) の 6 節）。シナリオは QA が設計し、実行と監視は Ops が担う。
- **使用量の照合**：物理クラスタ×時間で、テナントの書き込みの合計とブローカー全体の書き込みを比べる（[metrics-and-billing.md](architecture/metrics-and-billing.md) の 5 節）。
- **原価**：月次で、Cost and Usage Report を書き込みの GB で割り、[capacity.md](architecture/capacity.md) の 8 節の見積もりと比べる。
- **カオス試験と DR の訓練**：2.4 節の合格基準。

### 4.3 異常から intent へ

判定基準を外れた指標、監査・照合・確認の不一致、インシデントの振り返りは、Claude が調査結果を Intent の Issue として起票する（[project-management.md](../../../docs/project-management.md)）。調査に渡すのは、人が取り出した、レコードの中身とテナントのトピックの名前を含まないログとメトリクス（ID・数・大きさ・時刻）だけにする。PM が受理したものは、`intent.md` か Epic・Story になり、通常の Plan → Design の流れに乗る。喪失・分離・トランザクションに関わるものは、この文書の 1 節のリスクと対策も見直す。
