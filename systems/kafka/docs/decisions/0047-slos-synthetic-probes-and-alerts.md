# ADR-0047: 可用性と遅延の SLI は、外からブローカーごとに流す合成の produce・consume で測り、層ごとの SLO とバーンレートで呼び出す

詳細は [observability.md](../architecture/observability.md) の 6〜9 節。

## Context

- NFR-002：可用性は、外からの合成監視の produce・fetch の成否で測る。Standard は 99.95%（S1）、Basic は 99.5%（[architecture/README.md](../architecture/README.md) の 3 節）。
- NFR-003・NFR-004：produce の p99 50ms、端から端の p99 100ms。
- Kora は、内部のネットワークの外に健康の確認のエージェント（HC）を置き、ロードバランサーとプロキシを通して、ブローカーごとに毎分 100 回の produce と consume を送る。リーダーの固定された内部のパーティションを使う。分ごとにブローカーの p99 を出し、全ブローカーの最悪を、その分の値にする。週の値はその p99。サーバーのメトリクスは、ロードバランサーとプロキシの失敗を見落とす（[Kora](https://vldb.org/pvldb/vol16/p3822-povzner.pdf) の 3.1・4.4.1・4.4.2 節、2026-09-27 に確認）。
- 本家のサーバーのエラーコードには、クライアントの誤り（認可、設定）と、サービスの失敗（`NOT_ENOUGH_REPLICAS` など）が混ざる。throttle は失敗ではない。
- 他の題材は、マルチウィンドウのバーンレートで呼び出す（Stripe の [observability.md](../../../stripe/docs/architecture/observability.md) の 5.1 節）。

## Options

可用性の SLI：

1. **外からの合成の要求（ブローカーごと）の成功の割合**
2. テナントの実際の要求のうち、サーバーの失敗でないものの割合
3. 分ごとの「悪い分」（失敗の割合が閾値を超えた分）の割合

## Decision

1 を採用し、2 を補助の指標にする。

- 合成監視は、probe のアカウントの東京の 3 つの AZ（`client.rack` を設定）と、大阪から流す。物理クラスタごとの運用の論理クラスタに、ブローカーごとにリーダーを固定したパーティション（`probe-b<broker-id>`）を置き、ブローカーごとに毎秒 1 回、`acks=all`・冪等の produce と、`read_committed` の consume を行う。
- 1 回の要求は、5 秒で成功しなければ失敗。throttle は失敗にしない（合成監視の論理クラスタの上限に当たったら、それ自体を異常にする）。
- 可用性の SLI：層・物理クラスタごとの、合成の produce と consume の成功の割合（30 日）。
- 遅延の SLI：分ごとにブローカーの p99 を出し、物理クラスタの最悪のブローカーの値をその分の値にする（Kora と同じ）。30 日の分の値の p99 が目標以内。
- SLO（S1）：

| SLI | Basic | Standard |
| --- | --- | --- |
| 可用性（produce・consume） | 99.5% | 99.95% |
| produce の p99（1 KB、`acks=all`） | 100ms | 50ms |
| 端から端の p99 | 200ms | 100ms |
| 受け付けた書き込みの喪失 | 0（予算なし） | 0（予算なし） |

- 呼び出し：可用性の SLO に、1 時間・5 分で 14.4 倍、6 時間・30 分で 6 倍のバーンレート。3 日・6 時間で 1 倍はチケット。耐久性・テナントの分離・監査の不一致は、予算を使わず 1 件で呼び出す。
- すべてのアラートは runbook の URL を注釈に持つ。CI で検査する。
- 2 を主にしない理由：テナントの誤った使い方（存在しないトピック、古いクライアント）で値が揺れ、SLO の判断に使えない。NLB・Envoy・DNS の失敗は、テナントの要求がブローカーに届かないので数えられない。
- 3 を選ばない理由：SLA の文言の候補としては残す（法務の確認、intent.md の L6）。運用の予算は 1 のほうが細かく測れる。

## Consequences

- 良くなること：
  - NLB・Envoy・DNS・証明書を含めた、クライアントから見た可用性を測れる。
  - 遅いブローカーが 1 台あっても、SLI に出る（最悪のブローカーの値）。
- 引き受けるコスト：
  - 合成の要求は、ブローカーあたり毎秒 2 回（produce と consume）× 3 AZ。S1 の 150 台で毎秒約 900 回。負荷は小さいが、合成監視の論理クラスタのパーティションを、再配置と降格の対象から外す必要がある（リーダーを固定するため）。
  - 大阪からの合成監視は、リージョンをまたぐ遅延を含むので、遅延の SLI には使わず、到達性だけに使う。

## Confirmation

- 合成監視の自己検査：試験の物理クラスタで、1 つの AZ の Envoy を止めたとき、その AZ のブローカーの合成の要求が失敗として数えられ、バーンレートのアラートが 5 分以内に鳴る。
- CI：アラートの規則のファイルに、runbook の URL がない規則があれば失敗にする。
- 月次：SLO の報告（層・物理クラスタごとの達成、予算の残り、主な消費の原因）を Ops がまとめる。
