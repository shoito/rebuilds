# ADR-0038: 使用量はブローカーで分ごとに数えて S3 を正本にし、テナントのメトリクスは専用の AMP を条件付きの問い合わせで使う

## Context

請求（使った分）と、テナント向けのメトリクスの API（intent.md の MVP）の、数え方・経路・保存を決める。

- 本家のブローカーのメトリクスには、テナントの次元がない。テナントは、名前空間のパッチが付けた論理クラスタの ID でしか分からない（[ADR-0004](0004-logical-clusters-on-shared-physical-clusters.md)）。
- クォータの経路（`__<brand>_quota_usage`）は、5 秒の窓の速さで、配分のための近似である（[multi-tenancy-and-quotas.md](../architecture/multi-tenancy-and-quotas.md) の 7 節）。
- データの経路は制御面に依存しない（[ADR-0003](0003-kraft-metadata-and-cluster-placement.md)）。

事実（いずれも 2026-09-27 に確認）：

- Confluent Cloud の Metrics API は、`query`・`descriptors`・Prometheus の形の `export` を持ち、粒度は `PT1M`〜`P1D`、データは 3 分以内に問い合わせられ、IP ごとに毎分 300 回の上限がある（[Metrics API reference](https://api.telemetry.confluent.cloud/docs)）。

## Options

請求の使用量：

1. **ブローカーが、テナント×分の累計の数を内部のトピックに書き、エージェントが S3 に送る。S3 の生の記録を正本にし、時間ごとに集計する**
2. クォータの経路（5 秒の窓の速さ）を積分して使う
3. 運用のメトリクス（Prometheus）から請求を作る

テナントのメトリクス：

- A. **テナント専用の AMP のワークスペース。管理 API が JSON の問い合わせを PromQL に組み立て、テナントの条件を必ず付ける**
- B. 運用のメトリクスと同じ AMP を使う
- C. Aurora か時系列の DB に自前で持つ

## Decision

1 と A を採用する。詳細は [metrics-and-billing.md](../architecture/metrics-and-billing.md) の 4〜6 節にある。

- **数える場所**：名前空間のパッチの出口（書き込み・読み取りのバイト、要求）と、資格情報のコールバック（接続、接続の試み、キーごとの認証の成功）。フォロワーの複製、内部の主体、失敗した produce は数えない。
- **記録**：`__<brand>_usage` に、`(logical_cluster_id, broker_id, broker_incarnation, minute)` で一意の記録を書く。同じ記録の重複は 1 回と数える。ブローカーの停止で失う分は、少なく数える側（利用者に有利）。
- **経路**：エージェント → Firehose → S3（Parquet、請求の根拠の正本）→ 制御面の時間ごとの集計（Aurora の `usage_hourly`）。時間は 2 時間後に確定し、月の締めまでは集計し直せる。
- **照合**：物理クラスタ×時間で、テナントの書き込みの合計と、ブローカー全体の書き込みを比べ、1% を超えたら請求を保留する。
- **保持の量**：S3 の有効なセグメントとローカルの上がっていない部分の合計（複製の前）を 5 分ごとに計り、GB-時にする。
- **メトリクスの API**：テナント専用の AMP のワークスペース。管理 API の `/v1/metrics/query`・`descriptors`・`export`。問い合わせはサーバーが組み立て、`logical_cluster_id` の条件を必ず付ける。パーティションのラベルは保存せず、遅れのパーティションごとの値は問い合わせのときに計算する。KIP-714 は使わない。

2 を選ばない理由：窓の速さの積分は、窓の抜けや配分の揺れで誤差が出る。請求は、累計の正確な数と、重複を捨てられる一意の鍵が要る。

3 を選ばない理由：運用のメトリクスは、欠けても運用の判断には足りる設計（収集の間引き、保持の短さ）で、請求の根拠に向かない。

B を選ばない理由：テナントの問い合わせの条件に誤りがあると、運用のメトリクス（他のテナントを含む）に届く。負荷の分離もできない。

C を選ばない理由：時系列の保存と間引きを自前で作ることになる。

## Consequences

- 良くなること：
  - 請求の根拠が S3 に残り、集計を何度でも作り直せる。
  - 照合で、数え漏れを請求の前に見つけられる。
  - テナントのメトリクスの問い合わせが、運用と他のテナントに届かない。
- 引き受けるコスト：
  - ブローカーのパッチの出口に、数える処理を足す（名前空間のパッチの行数が増える。ADR-0001 の CI でパッチの行数を見る）。
  - 使用量の経路と、メトリクスの経路の 2 つを保つ。
  - 保持の量の精度は、階層型の保存のメタデータに依存する（E4 で確かめる）。

## Confirmation

- 性質ベーステスト：任意の分の記録の列（重複・順序の入れ替え・遅れ）で、時間の集計が正しい列の集計と同じ。
- 性質ベーステスト：任意の 2 つのテナントの問い合わせで、一方の結果に他方の系列が出ない。
- 結合テスト：既知の量の produce・fetch で、使用量とメトリクスが誤差 0.1% 以内。
- 本番：照合の不一致の件数（目標 0）。
