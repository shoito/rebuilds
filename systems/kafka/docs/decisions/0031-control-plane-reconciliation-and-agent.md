# ADR-0031: 制御面の状態は合図と取得による調停で反映し、KRaft が正本の資源は命令で扱う。データ面のエージェントは Java で書く

## Context

[ADR-0003](0003-kraft-metadata-and-cluster-placement.md) は、制御面の状態の変更を outbox → SQS → データ面のエージェントで届け、エージェントが望ましい状態と KRaft の実際の状態の差を冪等に埋めると決めた。この領域では、次を決める。

- SQS のメッセージに何を載せるか（状態の全体か、変更か、合図だけか）
- トピックや ACL のように、テナントが Kafka のプロトコルでも作れる資源を、制御面の API からどう変えるか
- エージェントを何の言語で書くか。[ADR-0001](0001-upstream-brokers-and-stack.md) は TypeScript を既定にし、Admin API のクライアントの選定をこの領域に任せた

事実（いずれも 2026-09-27 に確認）：

- KafkaJS の最後の版は v2.2.4（2023-02-27）。[ADR-0008](0008-client-matrix-differential-tests-and-version-tracking.md) は KafkaJS を凍結にし、エージェントのクライアントの見直しをこの領域に求めた。
- confluent-kafka-javascript（MIT、v1.10.1、2026-09-10）の管理のクライアントは「限られた部分」だけを持ち、移行の文書に ACL と設定の変更の API がない（[MIGRATION.md](https://github.com/confluentinc/confluent-kafka-javascript/blob/master/MIGRATION.md)）。
- 本家の Java の AdminClient は、ブローカーと同じ版で、管理の API をすべて持つ。

## Options

反映の方式：

1. **SQS は合図（論理クラスタの ID と世代）だけ。エージェントは毎回、望ましい状態の全体を制御面から取り、実際の状態と比べて埋める（レベルで動く調停）。10 分ごとに全体を再同期する**
2. SQS に変更の本文（差分）を載せ、エージェントが順に適用する（エッジで動く）
3. エージェントが制御面を定期的に読むだけ（SQS を使わない）

テナントも作れる資源（トピック、ACL）：

- A. **命令にする。制御面は命令を記録し、エージェントが AdminClient で実行し、結果を返す。一覧は KRaft の写しから見せる**
- B. 望ましい状態に含め、調停する

エージェントの言語：

- X. **Java 21 と本家の AdminClient**
- Y. TypeScript と confluent-kafka-javascript（足りない API は自前で足す）
- Z. Go と franz-go の管理のクライアント

## Decision

1、A、X を採用する。詳細は [control-plane-and-provisioning.md](../architecture/control-plane-and-provisioning.md) の 3〜6 節にある。

- **合図と取得**：状態の行の更新、`generation` の加算、outbox の行を 1 つのトランザクションで書く。relay が物理クラスタごとの SQS FIFO に `lc_id:generation` の合図を送る。エージェントは internal-api から望ましい状態の全体を取り、差を埋め、`observed_generation` を返す。内部のトピックの記録は `generation` を持ち、古い値で上書きしない。
- **命令**：トピック、パーティション、トピックの設定、ACL の変更は、`commands` の行と SQS FIFO（論理クラスタごとのグループ）で届け、エージェントが実行して結果を返す。管理 API は最長 5 秒待ち、終わらなければ 202 と操作の URL を返す。命令は冪等にし、10 分で期限切れにする。
- **写し**：エージェントは 30 秒ごとと命令の後に、KRaft の資源の一覧を制御面に送る。一覧の応答には `as_of` を付ける。
- **向き**：通信はデータ面から制御面へ出るだけ。制御面は物理クラスタの Kafka のリスナーに直接つながない。
- **エージェント**：Java 21 と本家の AdminClient。望ましい状態のスキーマの正本は制御面の Zod で、CI で JSON Schema を出し、Java の型を生成する。2 つのレプリカを Lease で主と副にする。

2 を選ばない理由：メッセージの抜け・重複・順序の入れ替えのたびに、状態がずれる。ずれを直す再同期が結局要る。

3 を選ばない理由：変更の反映が、読み取りの周期（数十秒〜数分）まで遅れる。SC-3（5 分で最初のメッセージ）の内訳を圧迫する。

B を選ばない理由：テナントが Kafka のプロトコルで作ったトピックを、制御面の「望ましい一覧」にないとして消してしまう。正本を KRaft とした ADR-0003 と合わない。

Y を選ばない理由：ACL・設定・クォータの API を Node.js で自前に作ると、本家のプロトコルの版の追従を 2 つ目の言語で抱える。Z は、同じ理由に加え、エージェントとブローカーの差し込み口で型（内部のトピックの記録）を共有できない。

これは ADR-0001 の「データ面のエージェントを TypeScript で書く」を改める。制御面・コンソールのバックエンドは TypeScript のまま。

## Consequences

- 良くなること：
  - 合図が失われても、10 分以内に最終の状態がそろう。調停を性質ベーステストで確かめやすい。
  - テナントが Kafka のプロトコルで行った変更と、管理 API の変更が衝突しない。
  - 管理の API をすべて、本家と同じ版のクライアントで扱える。
- 引き受けるコスト：
  - 言語が Java のサービスを 1 つ増やす（ADR-0001 の 4 つの言語の範囲の中）。スキーマの生成と契約テストを CI に置く。
  - 管理 API の一覧は最長 30 秒古い。`as_of` で見せる。
  - 命令の待ち（5 秒）の間、api のタスクの接続を使う。同時の命令の数を、組織ごとに制限する（管理 API のレート制限）。

## Confirmation

- 性質ベーステスト：任意の望ましい状態の列を、任意の順序・重複・抜けで合図しても、再同期の後の実際の状態が最後の望ましい状態と同じ。
- 性質ベーステスト：同じ命令を任意の回数だけ実行しても、結果が 1 回と同じ。
- 契約テスト：制御面が出す望ましい状態の文書を、エージェントの生成した型で読める。
- 結合テスト：制御面を止めても、既存の論理クラスタの produce・fetch が続く。
