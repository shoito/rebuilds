# ADR-0003: 物理クラスタのメタデータは KRaft を正本にし、制御面は望ましい状態を反映する

## Context

メタデータには 2 つの層がある。

- **物理クラスタの中のメタデータ**：トピック、パーティションの配置、ISR、リーダー、ACL、クォータ、設定。本家の Apache Kafka は、4.0 から KRaft（Raft で複製するメタデータのログ）だけで持つ（KIP-500、KIP-595、KIP-631。[4.0.0 の発表](https://kafka.apache.org/blog/2025/03/18/apache-kafka-4.0.0-release-announcement/)、2026-09-27 に確認）。3.9 で、コントローラーのクォーラムを止めずに入れ替えられるようになった（KIP-853。[Kafka 3.9 の紹介](https://www.confluent.io/blog/introducing-apache-kafka-3-9/)、2026-09-27 に確認）。
- **制御面のメタデータ**：組織、利用者、論理クラスタ、どの物理クラスタに載っているか、API キー、請求。

Kora は、制御面が HTTP の API で要求を受け、物理クラスタの設定（クォータ、API キー）を Kafka のプロトコルで物理クラスタへ送り、内部のトピックに保存する（[Kora](https://vldb.org/pvldb/vol16/p3822-povzner.pdf) の 3.1 節）。論理クラスタの物理クラスタへの配置と、セル（物理クラスタの中のブローカーの部分集合）も論文にある（5.3 節）。

決めることは 3 つある。

- 2 つの層のどちらを、どの情報の正本にするか
- 制御面から物理クラスタへ、どう反映するか
- 論理クラスタを、物理クラスタにどう配置するか

## Options

正本と反映：

1. **KRaft を物理クラスタの中の正本、Aurora を制御面の正本にし、制御面は望ましい状態を Admin API で反映する（調停のループ）**
2. **Aurora をすべての正本にし、ブローカーが Aurora を読む**
3. **KRaft をすべての正本にし、制御面は KRaft を読むだけにする**

配置：

- A. **論理クラスタを 1 つの物理クラスタに載せる。移すときは複製して切り替える**
- B. **1 つの論理クラスタを、複数の物理クラスタにまたがらせる**

## Decision

1 と A を採用する。

### 正本の分担

| 情報 | 正本 | もう一方での扱い |
| --- | --- | --- |
| トピック、パーティション、ISR、リーダー、トピックの設定 | KRaft | 制御面は Admin API で読んで表示する。トピックはクライアントからも作れるので、制御面に写しを持つときは、KRaft から定期的に取り込む |
| ACL | KRaft（StandardAuthorizer） | 制御面の API・コンソール・Terraform からの変更は、命令として Admin API で反映する（[ADR-0031](0031-control-plane-reconciliation-and-agent.md)）。クライアントからの CreateAcls・DeleteAcls は、本家の CLUSTER の ALTER の代わりに、論理クラスタの管理の権限（資格情報の `cluster_role=admin`）で許し、資源は自分の論理クラスタの TOPIC・GROUP・TRANSACTIONAL_ID に限る（[ADR-0029](0029-tenant-scoped-acls-and-rbac.md)、security-and-acls の 5.3 節） |
| テナントのクォータ | 制御面（層と CU から決める） | データ面のクォータのコーディネーターが、ブローカーごとの値を配る（[ADR-0027](0027-dynamic-quota-coordinator-and-backpressure.md)） |
| API キー | 制御面（ハッシュだけを保存） | ブローカーの認証のコールバックが、内部のトピック `__<brand>_credentials` で配られたハッシュで確かめる（[ADR-0028](0028-service-accounts-api-keys-and-sasl-plain.md)） |
| 論理クラスタ、配置、組織、請求 | 制御面（Aurora） | 物理クラスタは知らなくてよい。テナントの名前空間の ID だけを持つ |

- 制御面の状態の変更は、outbox → SQS の合図 → データ面のエージェントの取得の順に届ける。エージェントは、望ましい状態と KRaft の実際の状態の差を埋める（冪等に何度でも回せる）。詳しい方式は [ADR-0031](0031-control-plane-reconciliation-and-agent.md)。
- 反映が遅れても、データの経路（produce・fetch）は止まらない。制御面が落ちても、既存の論理クラスタは動き続ける。

### KRaft のクォーラム

- 物理クラスタごとに、専用のコントローラーを 3 台、AZ ごとに 1 台置く。ブローカーと同じノードに同居させない（Kora の論文も、コントローラーを別のプロセスに分けた利点を書いている。3.3 節）。
- 1 つの AZ を失っても、残りの 2 台で過半数を保つ。
- コントローラーの入れ替えは、KIP-853 の動的なクォーラムで行う。
- S2 で 5 台（2・2・1）にする（[ADR-0015](0015-kraft-dynamic-quorum-and-controller-sizing.md)）。

### 配置

- 論理クラスタは、1 つの物理クラスタに載せる（A）。1 つのリージョンの中で、トピック・グループ・トランザクションのコーディネーターがすべて 1 つの KRaft の下にあり、本家の意味がそのまま成り立つ。
- 新しい論理クラスタは、物理クラスタを 2 つ無作為に選び、負荷の低い方に置く。Kora はセルの選び方にこの方法を使っている（論文の 5.3 節）。作成の時点ではテナントの負荷が分からないので、最も空いた 1 つに集中させないためである。負荷は、CU の割り当ての合計と、実際の使用量の両方で見る（得点と受け入れの条件は [ADR-0033](0033-logical-cluster-placement.md)）。
- 論理クラスタが物理クラスタに収まらなくなったら、別の物理クラスタへ移す。移し方（クラスタの間の複製と、ブートストラップの切り替え）は S2 の control-plane-and-provisioning の領域で決める。S1 では、物理クラスタにブローカーを足して対応する。
- B は、1 つの論理クラスタのパーティションが複数の KRaft に分かれ、トランザクションやグループの意味を本家から変えることになるので採らない。

### 識別子

- 論理クラスタ：`lc-<ランダムな英数字>`。ブートストラップのホスト名は `<lc-id>.<region>.<brand>.<domain>`（[リポジトリ共通の ADR-0006](../../../../docs/decisions/0006-brand-neutral-identifiers.md)）。
- 物理クラスタ：`pc-<ランダムな英数字>`。テナントには見せない。

## Consequences

- 良くなること：
  - データの経路が制御面に依存しない。制御面の障害は、作成・変更の操作だけを止める。
  - KRaft の意味（トピック、ACL、トランザクション）は本家のまま。
- 引き受けるコスト：
  - 正本が 2 か所に分かれるので、表示（コンソール）と実際（KRaft）の食い違いが一時的に起きる。調停のループと、食い違いの監視が要る。
  - 1 つの論理クラスタの上限は、1 つの物理クラスタの大きさで決まる。

## Confirmation

- 結合テスト：制御面を止めても、既存の論理クラスタの produce・fetch・グループ・トランザクションが続く。
- 調停のテスト：望ましい状態を任意の順序で与え、エージェントを任意の回数だけ再実行しても、KRaft の最終の状態が同じになる（性質ベーステスト）。
- 監視：制御面の望ましい状態と KRaft の実際の状態の差の件数と、反映の遅れを、メトリクスにする。
