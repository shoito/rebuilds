# ADR-0027: クォータのコーディネーターを物理クラスタごとにデータ面に置き、使用量に応じて配り直し、ブローカーは背圧で全体を守る

詳細は [multi-tenancy-and-quotas.md](../architecture/multi-tenancy-and-quotas.md) の 7 節。

## Context

- 本家のクォータはブローカーごとの値である。テナントのクォータを静的にブローカーの数で割ると、熱いパーティションのあるテナントは、全体では余裕があるのに一部のブローカーで絞られる。Kora は、静的な配分から、共有のクォータのコーディネーターによる動的な配分に替え、帯域の SLO（週に絞られる時間 5 分以内）を満たすテナントの割合を 99% から 99.9% 超にした。値の揺れによる細かい throttle を避けるため、テナント全体の使用量が閾値を超えるまで throttle を遅らせる。ブローカーは、資源の安全な上限を超えると、テナントのクォータを割り当ての比で下げる（背圧）。CPU は要求の待ち行列の閾値で背圧を掛ける（[Kora](https://vldb.org/pvldb/vol16/p3822-povzner.pdf) の 5.2 節、2026-09-27 に確認）。
- NFR-008 は Kora と同じ指標（週 5 分以内のテナントを 99.9% 以上）を目標にする。
- [architecture/README.md](../architecture/README.md) の 1 節の図は、クォータのコーディネーターを制御面に置いている。一方、[ADR-0003](0003-kraft-metadata-and-cluster-placement.md) は「データの経路は制御面に依存しない」とした。
- [ADR-0004](0004-logical-clusters-on-shared-physical-clusters.md) は、S1 を静的な等分から始め、E7 で動的にするとした。

## Options

置き場所：

1. **物理クラスタごとに、データ面の中に置く（3 つ、Kafka のコンシューマーグループでテナントを分け合う）**
2. 制御面に 1 つ置く
3. コーディネーターを置かず、ブローカーどうしで使用量を交換する

配分の伝え方：

- A. **内部トピック（`__<brand>_quota_usage`・`__<brand>_quota_assignments`）**
- B. KRaft のクライアントのクォータの記録（AlterClientQuotas）
- C. 制御面の HTTP の API

## Decision

1 と A を採用する。

- ブローカーは 5 秒ごとに、テナントごとの使用量と throttle の時間を `__<brand>_quota_usage` に書く。
- コーディネーターは 10 秒ごとに、担当のテナントのブローカーごとの値を計算し、`__<brand>_quota_assignments`（圧縮）に書く。ブローカーは自分の分を読み、`ClientQuotaCallback` の値を差し替える。
- 配分：需要 d_b = max(u_b × (throttled ? 1.5 : 1.1), Q × 0.05 ÷ |B|)、q_b = Q × d_b ÷ Σ d。全体の使用量が Q の 50% 未満なら静的な等分より絞らない。全体の使用量が Q の 90% 未満の間、ブローカーは q_b の 2 倍まで許す（遅らせる throttle）。係数は初期値。
- 背圧：ブローカーの資源の使用量が安全な上限の 90% を超えたら、そのブローカーの全テナントの値を割り当ての比で下げる。要求の待ち行列が 80% に達したら、要求の処理時間のクォータを同じく下げる。1 分以上続いたら、再配置と拡張の判断に渡す。
- コーディネーターが止まったら、ブローカーは最後の値を使い、5 分を過ぎるか、対象のブローカーが変われば、静的な等分に戻る。
- 制御面は、テナントのクォータの総量（層、CU、上書き）を、望ましい状態としてデータ面へ渡すだけにする。データ面のエージェントが内部トピック `__<brand>_tenants` に書き（[ADR-0031](0031-control-plane-reconciliation-and-agent.md)）、コーディネーターとブローカーが読む。
- 2 を選ばない理由：制御面の障害で、配分が止まる。ブローカーと制御面の間の往復が、物理クラスタの数だけ増える。
- 3 を選ばない理由：ブローカーの数の 2 乗の通信になり、計算が分散して調べにくい。
- B を選ばない理由：数千のテナント × ブローカーの値を 10 秒ごとに書くと、KRaft のメタデータのログを膨らませ、コントローラーを重くする。
- C を選ばない理由：2 と同じく、データの経路の配分が制御面に依存する。

## Consequences

- 良くなること：
  - 偏ったワークロードのテナントが、全体では余裕があるのに絞られる時間を減らせる。
  - 制御面が止まっても、配分と背圧が続く。
- 引き受けるコスト：
  - データ面に、状態を持つ新しい部品（コーディネーター）と、2 つの内部トピックが増える。
  - 遅らせる throttle の間、テナントの全体の使用量が一時的に Q を超えうる（最大 2Q、最大 15 秒）。背圧で全体は守る。
  - README の 1 節の図と、コーディネーターの置き場所が変わる（統合の工程で README の図を直した）。

## Confirmation

- 性質ベーステスト：任意の使用量の列で、配分の合計は Q に等しく、最低の分を下回らない。
- 負荷試験：熱いパーティションを持つテナントで、静的な等分と比べて、クォータの中で絞られた時間が減る。うるさい隣人の試験（N1〜N10）が通る。
- 障害注入：コーディネーターをすべて止めても produce・fetch が続き、5 分後に静的な等分へ戻る。
