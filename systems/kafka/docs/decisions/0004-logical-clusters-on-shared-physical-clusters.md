# ADR-0004: テナントは、共有の物理クラスタの上の論理クラスタにする

## Context

マネージドのストリーミング基盤のテナントの分け方には、2 つの型がある（いずれも 2026-09-27 に確認）。

- **テナントごとに物理クラスタを作る**：Amazon MSK の Provisioned、Confluent Cloud の Dedicated。分離は強いが、小さなテナントにも最低限のブローカーとコントローラーが要り、費用と作成の時間がかかる。
- **物理クラスタを共有し、論理クラスタで分ける**：Confluent Cloud の Basic・Standard・Enterprise（Kora）。Kora の多数のテナントの物理クラスタには、数千のテナントが載る（[Kora](https://vldb.org/pvldb/vol16/p3822-povzner.pdf) の 5.2 節）。Kora は、論理クラスタを分離の単位にし、専用のクラスタは「テナントが 1 つだけの共有のクラスタ」として扱う（5.1 節）。

Kora の分け方（論文の 5 節）：

- 資源（トピック、グループ、`transactional.id` など）に論理クラスタの ID を付け、ブローカーの中の割り込みの処理で、要求ごとに ID を付けて、他のテナントの資源に触れないようにする。
- テナントごとのクォータ：書き込み・読み取りの帯域、CPU（要求の処理の時間）、接続の数と接続の頻度、メモリーを使う振る舞い、パーティションの作成・削除の頻度。
- ブローカーが限界に近づくと、テナントのクォータを割り当ての比で自動的に下げて、ブローカー全体を守る（背圧）。
- テナントのクォータを、使用量に応じてブローカーの間で配り直す（動的なクォータ）。

intent.md は、MVP を「サーバーレス（容量が伸び縮みする）」としている。1,000 の論理クラスタ（S1）に物理クラスタを 1 つずつ作ると、費用が合わない。

## Options

1. **共有の物理クラスタの上の論理クラスタ（Kora の型）。名前空間はブローカーのパッチで作る**
2. **1 と同じ。ただし名前空間は、Kafka のプロトコルを理解するプロキシで作る**（Kroxylicious など。資源の名前に接頭辞を付け外しするフィルターがある。未検証）
3. **1 と同じ。ただし名前空間を作らず、トピックの名前の接頭辞と、接頭辞の ACL で分ける**（テナントに接頭辞が見える）
4. **テナントごとに物理クラスタを作る**

## Decision

1 を採用する。専用の物理クラスタ（Dedicated）は、S2 で「論理クラスタが 1 つだけの物理クラスタ」として足す。

### 名前空間

- ブローカーの中で、認証した主体（principal）から論理クラスタの ID を決め、要求の中の資源の名前（トピック、グループ、`transactional.id`、ACL の資源）に内部で接頭辞を付け、応答では外す。テナントからは、接頭辞のない名前に見える。
- Metadata・DescribeCluster・ListTopics・ListGroups などの一覧の応答は、そのテナントの資源だけを返す。ブローカーの一覧は、そのテナントのパーティションを持つブローカーだけにできるかを、multi-tenancy-and-quotas の領域で決める。
- これは本家の差し込み口では作れないので、ブローカーのパッチにする（[ADR-0001](0001-upstream-brokers-and-stack.md)）。パッチは要求の出入口の 1 か所に集め、API ごとの資源の名前の場所を表で持つ。新しい API・版が本家に入ったら、表を更新しないと、その API は拒否される（安全な側に倒す）。

### 2・3・4 を選ばない理由

- 2 は、本家のブローカーに手を入れずに済む。ただし、すべての要求をプロキシで解釈するので、経路が 1 つ増え、遅延と CPU を使う。クォータ・ACL・メトリクスにもテナントの ID が要るので、結局ブローカーにもテナントを伝える必要がある。E1 の PoC で、パッチの量が想定より大きければ、2 を再評価する。
- 3 は、テナントに接頭辞が見え、トピックの名前を決め打ちしている既存のアプリ（Kafka Streams の内部トピックなど）が、そのまま動かない。intent.md の「クライアントは変更なしで動く」に反する。
- 4 は、小さなテナントに費用が合わず、作成に時間がかかる（SC-3 の 5 分に届かない見込み）。

### クォータと背圧

- Kora と同じ種類のクォータを、テナントの単位で掛ける：書き込み・読み取りの帯域、要求の処理時間、接続の数と頻度、パーティションの数と作成・削除の頻度。
- 本家のクォータの仕組み（ClientQuotaCallback と、応答の throttle の時間）を使う。クライアントには、本家と同じ throttle の応答で伝わる。
- ブローカーごとの値は、制御面のクォータのコーディネーターが、テナントの使用量から計算して配る（動的なクォータ）。S1 は静的な等分から始め、E7 で動的にする。
- ブローカーの資源が限界に近づいたら、テナントのクォータを割り当ての比で下げる（背圧）。同時に、再配置と拡張の判断に使う。

### 層

| 層 | 物理クラスタ | 可用性の目標 | 用途 | 段階 |
| --- | --- | --- | --- | --- |
| Basic | 共有（Basic 専用の物理クラスタ群） | 99.5% | 開発、検証 | S1 |
| Standard | 共有（Standard 専用の物理クラスタ群。マルチ AZ） | 99.95%（S1）→ 99.99%（S2） | 本番 | S1 |
| Dedicated | 1 テナントだけ | 99.99% | 大きな本番、分離の要件が強いもの。PrivateLink | S2 |

- Basic と Standard は、物理クラスタを分ける。Basic の無料・安価な利用の負荷が、Standard に及ばないようにする。
- どの層も、複製 3・3 つの AZ にする（[ADR-0002](0002-replicated-log-with-tiered-storage.md)）。Basic でも耐久性の既定値を下げない。1 つの AZ だけの安い層（Kora にはある）は、MVP では提供しない。
- セル（物理クラスタの中のブローカーの部分集合に、論理クラスタを閉じ込める）は S2 で入れる。Kora は、セルで接続の数を減らし、クラスタの負荷が 73% から 53% に下がったと書いている（論文の 5.3 節）。

## Consequences

- 良くなること：
  - 小さなテナントを安く、すぐに作れる。容量の伸び縮みの多くを、クォータの変更だけで行える。
  - 専用のクラスタも同じ仕組みで作るので、分離の実装は 1 つで済む。
- 引き受けるコスト：
  - ブローカーのパッチを維持する。本家の新しい API を、名前空間の表に足すまで使えない。
  - うるさい隣人の危険を、クォータと背圧と監視で抑え続ける必要がある。
  - 物理クラスタの障害は、載っているすべてのテナントに及ぶ。セル（S2）で範囲を絞る。

## Confirmation

- 性質ベーステスト：任意の 2 つのテナントと、任意の API・版の要求の列で、一方の要求の応答に、他方の資源の名前・データ・メトリクスが出ない。
- CI：本家の ApiVersions が広告するすべての API について、名前空間の表に載っているか、明示的に拒否しているかを確かめる。載っていない API があれば失敗にする。
- 負荷試験：1 つのテナントがクォータの 10 倍を送っても、他のテナントの produce の p99 と、クォータの中のスループットが、NFR-003・NFR-008 を満たす。
