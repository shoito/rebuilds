# ADR-0015: KRaft は作成時から動的なクォーラムにし、S1 は 3 台、S2 は 5 台の専用のコントローラーにする

詳細は [metadata-and-control.md](../architecture/metadata-and-control.md) の 3 節。

## Context

[ADR-0003](0003-kraft-metadata-and-cluster-placement.md) は、物理クラスタごとに専用のコントローラーを 3 台（AZ ごとに 1 台）置き、入れ替えは KIP-853 の動的なクォーラムで行い、5 台にするかは S2 でこの領域が決めるとした。

事実（2026-09-27 に確認）：

- 本家は 3 か 5 台を勧め、N 個の同時の失敗には 2N＋1 台が要る。普通のクラスタでは、メモリー 5 GB とディスク 5 GB で足りる（[KRaft](https://kafka.apache.org/43/operations/kraft/)）。
- 動的なクォーラム（`kraft.version` 1）では、`add-controller`・`remove-controller` で投票者を変えられる。変更は一度に 1 つ。`kraft.version` は 1 から 0 に戻せない（[KIP-853](https://cwiki.apache.org/confluence/display/KAFKA/KIP-853%3A+KRaft+Controller+Membership+Changes)）。
- Kora は、コントローラーを別のプロセスにし、ブローカーを全てロールしてもコントローラーを安定させている（[Kora](https://vldb.org/pvldb/vol16/p3822-povzner.pdf) の 3.3 節）。

## Options

1. **S1 から 5 台（2・2・1）**
2. **S1 は 3 台、S2 で 5 台（2・2・1）。作成時から動的なクォーラム**
3. **3 台、静的なクォーラム（`controller.quorum.voters`）**

## Decision

2 を採用する。

- 作成時から `--initial-controllers` で動的なクォーラムにし、ブローカーは `controller.quorum.bootstrap.servers` で見つける。
- コントローラーは専用のノードに置き、ブローカーと同居させない。ノードは 16 GiB（ヒープ 8 GiB）、EBS gp3 50 GiB（仮。本家の目安の上に余裕を取る）。
- 入れ替えは「新しい台を同じ AZ に作る → 追いつく → 足す → 古い台を外す」の順。足してから外すまでを数分に抑える。
- 最新のスナップショットを 1 時間ごとに S3 に写す（過半数のボリュームを失ったときの調査と、最後の手段の材料）。
- S1 の 3 台の間は、コントローラーのローリング更新を、3 台が健全で遅れがないときだけ行う。
- 1 は、S1 の小さな物理クラスタに費用がかかる。ただし、コントローラーは小さいので差は小さい。E3 の運用の実績で前倒しを判断する。
- 3 は、入れ替えのたびに全てのノードの設定を変えて再起動する必要があり、動的なクォーラムへの移行も後で要る。

## Consequences

- 良くなること：
  - コントローラーを止めずに入れ替えられる。台の型の変更、ボリュームの喪失に対応できる。
  - S2 で、ローリング更新と 1 台の故障の重なりに耐える。
- 引き受けるコスト：
  - S1 では、1 つの AZ の喪失の間、コントローラーの失敗にもう耐えられない。
  - 入れ替えの途中の 4 台の窓では、同じ AZ に 2 台の投票者がいて、その AZ を失うと過半数を割る。

## Confirmation

- 障害注入：入れ替えの各段で、コントローラーとブローカーを止めても、メタデータを失わず、クォーラムが戻る。
- 監視：投票者の一覧の変化、活動中のコントローラーの数、観測者と投票者の遅れ。
- 訓練：スナップショットの写しからの復旧を、検証の環境で年 2 回試す。
