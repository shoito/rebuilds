# AGENTS.md — Mercari

Mercari の再構築の設計。リポジトリ共通のルールはルートの [AGENTS.md](../../AGENTS.md) にある。このリポジトリには設計だけを置き、実装は Mercari の開発リポジトリで行う（[リポジトリ共通の ADR-0005](../../docs/decisions/0005-design-record-repository.md)）。

## この題材に固有の規則（開発リポジトリで守る）

### 本家の実装と名前

- **核を自前で作る。** 取引の状態の機械、台帳、検索の順位付け、保存した検索の照合、T&S のパイプライン（規則のエンジン、分類器の学習と評価、審査の待ち行列）、配送の指揮は自分で書く。本家のコード、本家の SDK・API のクライアント、本家から取り出したデータ・モデル・重みを、核にも依存にも使わない。本家の技術ブログやヘルプの考え方を読むのはよいが、設計の文書に出典を書く（[リポジトリ共通の ADR-0007](../../docs/decisions/0007-no-reuse-of-original-implementation.md)、ADR-0001）。
- **第三者の汎用の部品は、ADR に理由を書いた範囲でだけ使う。** 検索のエンジン（OpenSearch と Sudachi）、画像の変換（sharp）、機械学習の枠組み（PyTorch など）、決済の提供者、運送会社の API、eKYC の提供者、SMS・プッシュ・メールの送信が当たる（ADR-0001、ADR-0005、ADR-0006、ADR-0008、ADR-0009）。
- **カード処理を設計し直さない。** カード情報の保管、アクワイアラへの接続は Stripe の題材の論点である。この題材は提供者の API を使う側として書く。ただし、本システムの台帳（預かり、手数料、売上金）は自前で設計する（ADR-0003、ADR-0005）。
- **本家の名前を識別子に使わない。** ドメイン（`<brand>.<domain>`、画像の `static.<brand>.<domain>`）、HTTP ヘッダー（`X-<Brand>-Client`、`<Brand>-Signature`）、配送の商品の名前（`<Brand>便`）、ポイントの名前、ID の接頭辞は `<Brand>`・`<brand>` で書く（[リポジトリ共通の ADR-0006](../../docs/decisions/0006-brand-neutral-identifiers.md)）。運送会社の名前は、相手先の名前としてそのまま書いてよい。

### 一品は一回だけ売る

- **出品の売れた状態の正本は Aurora の行にする。** 購入は、出品の行の条件つきの更新（`status = 'on_sale' AND version = $expected`）と、取引の行の挿入を同じトランザクションで書く。取引の表に「進行中の取引は出品ごとに 1 つ」の部分一意の索引を置く。Valkey の先着の印は流量を絞るだけで、正本にしない（ADR-0002）。
- **購入は 1 つの関数を通す。** 通常の購入、ポイント・売上金での購入、値下げの後の購入のどれも `purchaseListing` を通す。別の経路で取引を作らない（ADR-0002）。
- **表示した価格で売る。** 購入の要求は、買い手が見た価格と出品のバージョンを持つ。出品の価格・バージョンが違えば、取引を作らずに 409 を返す。

### 取引の状態と期限

- **状態の遷移は 1 つの遷移の関数だけが書く。** 遷移は決定表（ADR-0002 の DT-TXN-001 の草案）に従い、`transaction_events` に行を足す。画面・ジョブ・運送会社の Webhook・運用の操作のどれも、この関数を呼ぶ（ADR-0002）。
- **期限は DB に書いた時刻で動かす。** 支払いの期限、発送の期限、受取評価の自動の完了、評価の期限は、取引の行の期限の列と、期限の処理（1 分ごと）で動かす。プロセスのメモリーのタイマーに頼らない。紛争の間は期限を止める（ADR-0002）。
- **運送会社の事象は、状態を前にだけ進める。** 運送会社の Webhook は inbox で重複を除き、事象の順位（引き受け < 輸送中 < 配達済み）で古い事象を無視する。配達済みの事象で受取評価を代わりにしない（ADR-0006）。

### お金

- **お金の正本は追記だけの複式簿記の台帳にする。** 仕訳は借方と貸方の和が一致しなければ書けない（DB の制約とコードの両方）。残高は仕訳の和で、残高の列を直接書き換えない（ADR-0003）。
- **売上金への振り替えは取引ごとに 1 回だけ。** 預かりから売上金への振り替え（release）と、返金（refund）は、`(source_type, source_id, event)` の一意の冪等キーで 1 回に限る。release と refund は同じ取引で両方は起きない（ADR-0003）。
- **金額は整数の円で持つ。** 浮動小数点を使わない。手数料の端数の規則は 1 か所（`packages/fees`）に置き、手数料の表はバージョンで固定する。
- **売上金・残高・ポイントの法的な扱いを、コードに決め打ちしない。** 期限、本人確認の要否、使い道、保全は、`legal.*` の設定とバージョンの付いた残高の種類で持つ。法務の結論（L1）が出るまで、本番の値を有効にしない（ADR-0004）。
- **カード番号を扱わない。** カード番号は提供者のホストした入力部品で受ける。本システムのサーバー・ログ・DB に、カード番号とセキュリティコードが入る経路を作らない（ADR-0005）。

### 個人のデータと可視性

- **住所を相手に見せない。** 匿名の配送では、配送先と差出人の住所・氏名・電話番号を、取引の相手・メッセージ・画面・通知のどこにも出さない。住所は `shipping` のサービスだけが封筒の暗号化を解いて運送会社に渡す（ADR-0006、ADR-0007）。
- **見える範囲は DB と 1 つの関数で決める。** 本人だけの表は FORCE RLS と `SET LOCAL app.actor_id`、取引の表は買い手と売り手の 2 者の RLS にする。出品の公開の判定は `listingVisible(viewer, listing)` の 1 か所で行い、検索・おすすめ・通知・共有のページはこれを通す（ADR-0007）。
- **利用者のデータをログに出さない。** 本システムのログ・トレースに、住所、氏名、電話番号、メールアドレス、本人確認の書類、メッセージとコメントの本文、検索の語、口座の番号を書かない。ID と数と理由のコードだけを書く。

### T&S と ML

- **ML の出力は信号であり、決定ではない。** 分類器（文字・画像・行動）の点は、規則のエンジンの入力にする。出品の停止、アカウントの制限、取引の取り消しは、規則のエンジンと人の審査が、根拠を `moderation_actions` に書いてから効かせる（ADR-0009）。
- **価格の提案は助言だけ。** 価格の提案は、出品の画面に出す参考の値で、出品の価格を自動で変えない。手数料・送料・売上金の計算に使わない（ADR-0010）。
- **措置は記録してから効かせる。** 措置の記録、出品の状態の変更、outbox を同じトランザクションで書き、その後に検索の索引と通知を直す。

### 運用と入力

- **お金・取引の状態・期限の規則をフラグにしない。** 取引の状態の機械、台帳の仕訳の型、手数料の計算はコードのバージョンとして出す。`release.*` のフラグで経路ごとに切り替えない。手数料の表と送料の表は、バージョンの付いた設定にする。
- **フラグの名前**：`release.*` は kebab-case（`release.offers`）、`ops.*` は snake_case（`ops.purchase_enabled`）、`legal.*` は法務の結論を入れる値（`legal.proceeds_expiry_days`）。`release.*` は 100% の後 30 日で消す。
- **テストに本物のデータを使わない。** 実在の利用者の出品・写真・住所・メッセージ、本家から取り出したデータを、テスト・フィクスチャー・学習のデータに入れない。偽ブランドの評価の集まりは、権利者と合意した素材と、生成した素材だけで作る（[quality.md](docs/quality.md) の 2.2.1 節 F）。

## このリポジトリでの規則

- ADR を追加・更新したら、`docs/decisions/README.md` の一覧を生成し直す。
- 領域の文書で ADR を起票するときは、[architecture/README.md](docs/architecture/README.md) の 7 節で領域に割り当てた番号の範囲の中で採番する。
- 本家の振る舞い・数値を書くときは、出典と確認日を付ける。確かめられないものは「未検証」と書く。本家と違う振る舞いを選んだら、[architecture/README.md](docs/architecture/README.md) の 1.4 節の「本家との意図した違い」に行を足す。
- 決済のカード処理と、加盟店の台帳の一般の設計は Stripe の題材にある。この題材の台帳は、そこの考え方（複式簿記、冪等、3 者の照合）を参照し、C2C の預かりと売上金に合わせて自前で書く。
- 法令に関わる項目は、枠組みだけを書き、結論を書かない。「法務の確認待ち」と書き、[intent.md](docs/intent.md) の L の番号を付ける。
