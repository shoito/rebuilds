# ADR-0008: 検索は Amazon OpenSearch Service に、販売中と売れた品の出品を入れ、Sudachi の形態素と 2-gram の欄で日本語を引く。順位付けは自前の決めた式。索引は出品のバージョンを外部のバージョンにして順序を守る。保存した検索の照合は OpenSearch でなく自前の逆索引で行う

## Context

- 買い手は、題名・説明・ブランド・カテゴリを日本語で引き、カテゴリ・ブランド・価格・状態・配送料の負担・販売の状態で絞る。件数の集計を出す。
- 売れた品も引けることが、相場を調べる人と、価格を決める売り手に役立つ。売れた品は 1 年残すと販売中の 1〜2 倍ある。
- 出品から検索に出るまで p95 10 秒、検索 p95 200ms（NFR-001、NFR-010）。S3 で索引 8.5 億件（最初の設計では 30 億件と見積もった）、検索 10 万件/秒（[architecture/README.md](../architecture/README.md) の 2 節）。
- 保存した検索は、新しい出品ごとに「どの保存した検索に一致するか」を引く、逆向きの検索である。S3 で 5 億件の保存した検索に、1 秒あたり平均 35 件（最大はその数倍）の新しい出品を当てる。
- 日本語は単語の区切りがなく、表記の揺れ（全角・半角、かな・カナ、長音、ブランドの英字とカナ）が多い。
- 本家の検索の基盤は Elasticsearch と採用の募集にある（**未検証**）。Shopify の題材は、OpenSearch と Sudachi と 2-gram を決めた（[Shopify の ADR-0052](../../../shopify/docs/decisions/0052-search-index-per-pod-and-japanese-analysis.md)）。

## Options

検索のエンジン：

1. **Amazon OpenSearch Service（Sudachi の解析器、ICU の正規化、2-gram の欄）**
2. PostgreSQL の全文検索（pg_bigm などの拡張）
3. 自前の検索のエンジン

保存した検索の照合：

- a. **自前の逆索引（照合の鍵で候補を引き、条件を全部当てる）**
- b. OpenSearch の percolator
- c. 保存した検索を定期に実行する（ポーリング）

## Decision

1 と a を採用する。

### 索引

- 1 つの論理の索引（別名つき）に、販売中・取引中・売り切れの出品を入れる。`status` の欄で分け、既定の検索は販売中だけ。売れた品は、売れた日から保持の期間（S1 は 1 年。search-and-discovery の領域で決める）だけ残す。S2 で、販売中と売れた品を別の索引に分け、売れた品の索引のシャードと複製を少なくする。
- 欄：題名・説明（Sudachi の分割の B と C の単位、ICU の正規化、かな・カナの揃え）、題名の 2-gram（短い語と、辞書にない語）、ブランド（正規化した ID と、表記の揺れの辞書の展開）、カテゴリ（木の全祖先の ID）、価格、状態、配送料の負担、配送の方法、出品の時刻、売れた時刻、いいねの数、売り手の評価の段、措置と見える範囲の写し。
- 書き込み：`search-indexer` が outbox の事象（`listing.*`）から書く。出品のバージョンを OpenSearch の外部のバージョン（`version_type=external`）にし、古い事象が新しい内容を上書きしない。

> 2026-10-10 の注記：書き込みは `version_type=external_gte` にした。いいねの数を同じバージョンで直すため（[ADR-0018](0018-search-index-layout-and-japanese-analysis.md)）。売れた品の保持は 365 日。Context の「S3 で索引 30 億件」と「売れた品は販売中の数倍」は、売れた品を取引の完了 × 365 日で数え直し、S1 約 7,000 万・S2 約 2.8 億・S3 約 8.5 億にした（[architecture/README.md](../architecture/README.md) の 2 節）。売れた品の検索は、相場のデータの持ち出しを抑えるため、ログインした利用者だけにした（[search-and-discovery.md](../architecture/search-and-discovery.md) の 5.6 節）。

- 措置・売り切れ・停止は、通常の事象より先に処理する別の待ち行列で流す（NFR-001 の p99 60 秒）。
- 索引の作り直しは、新しい索引に全件を流して別名を付け替える。作り直しの間の変更は、両方に書く。

### 検索と順位付け

- 検索は `packages/search` の 1 つの関数だけが組み立てる。必ず見える範囲の写しの絞り込みを付け、返す前に `listingVisible()` を通す（[ADR-0007](0007-single-tenant-and-party-visibility.md)）。
- 並べ替えの既定は「新しい順」（フリマの買い手の主な見方。本家の既定は**未検証**）。「おすすめ順」の順位は、欄ごとの重みの BM25 に、新しさの減衰、いいねの数（`log1p`）、売り手の評価の段、写真の質の点を掛ける決めた式にする。同じ得点は出品の ID の順にする。式と重みは search-and-discovery の領域で決め、バージョンで出す。
- ML の順位付け（学習した順位の式）は MVP の後。入れるときは、この式の後の並べ替えとして、見える範囲と絞り込みを変えない（[ADR-0010](0010-ml-boundary-for-pricing-and-recommendations.md)）。
- 集計（カテゴリ・ブランド・価格の帯ごとの件数）は、OpenSearch の集計で出す。件数は「おおよそ」と表示してよい（search-and-discovery の領域で決める）。

### 保存した検索の照合

- 保存した検索は content の表に正規化した条件で置く。照合の鍵を条件から作る：カテゴリ（最も深い指定）× ブランド、ブランドだけ、カテゴリだけ、語だけの場合は語の主な語幹（Sudachi の正規化した形）。
- 照合の鍵ごとの逆索引（鍵 → 保存した検索の ID の一覧）を content の表に持ち、Valkey に写す。
- `saved-search-matcher` は、新しい出品・値下げの事象で、出品の鍵（カテゴリの祖先 × ブランド、題名の語幹）から候補を引き、各候補の条件を全部当てる（語は同じ解析器の結果で比べる）。一致を通知の依頼にする（saved-searches-and-alerts の領域）。
- 照合の鍵が広すぎる保存した検索（語だけの短い語など）は、候補の上限と、利用者へのまとめで抑える。

### 他の案を選ばなかった理由

- **2（PostgreSQL）**：日本語の形態素の解析がなく、8.5 億件の集計と 10 万件/秒の検索を、取引の DB と同じ資源で受けられない。
- **3（自前のエンジン）**：検索のエンジンの本体は汎用の部品で、作る価値が小さい。題材の核は、順位付けの式と保存した検索の照合に置く。
- **b（percolator）**：5 億件の保存した検索を 1 つの索引に入れ、新しい出品ごとに全シャードで照合する。費用と遅れが S3 で大きい。条件の正規化と、利用者ごとのまとめの規則を、どのみち自前で持つ。
- **c（ポーリング）**：5 億件を数分ごとに引くと、検索の負荷が 10 万件/秒を大きく超える。

## Consequences

- 良くなること：
  - 日本語の検索と集計を、汎用のエンジンで素直に作れる。
  - 売れた品の検索が、同じ仕組みで作れる。
  - 保存した検索の照合が、出品の数に比例し、保存した検索の数に比例しない。
- 引き受けるコスト：
  - OpenSearch の運用（シャードの数、索引の作り直し、Sudachi の辞書の更新）。
  - 逆索引の鍵の設計を誤ると、通知の取りこぼしが起きる。取りこぼしの試験（定期の実行との比べ）を持つ。

## Confirmation

- 試験のベクトル：日本語の表記の揺れ（全角・半角、かな・カナ、長音、ブランドの英字とカナ）で、同じ出品が引けること。
- 性質ベーステスト：任意の出品の事象の列（作成、編集、値下げ、措置、売り切れの順序の入れ替えと重複）で、索引の最後の内容が DB の最後の内容と一致する。保存した検索の照合の結果が、条件を全件に素直に当てた結果（参照の実装）と一致する（[quality.md](../quality.md) の 2.2.1 節 E）。
- 本番：見える範囲の抜き取りの監査（検索の結果の出品の状態を core で確かめる）と、出品から検索に出るまでの合成監視（NFR-001）。
