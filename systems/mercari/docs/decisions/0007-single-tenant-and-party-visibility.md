# ADR-0007: テナントは 1 つ。本人だけの表は FORCE RLS、取引の表は買い手と売り手の 2 者の RLS にする。出品の見える範囲は `listingVisible(viewer, listing)` の 1 つの関数で決める。運用者は監査つきの JIT の権限で見る

## Context

- 他の題材の多くは、ワークスペースやショップを単位に `tenant_id` と FORCE RLS で分ける。この題材は X・YouTube の題材と同じく、全利用者が 1 つの公開の場にいる（[X の ADR-0004](../../../x/docs/decisions/0004-single-tenant-and-visibility.md)、[YouTube の ADR-0009](../../../youtube/docs/decisions/0009-single-tenant-and-playable.md)）。
- ただし、見てよい人が決まったデータがある。
  - **本人だけ**：住所、売上金と明細、口座、本人確認、閲覧の履歴、検索の履歴、保存した検索、いいね、通知、端末、セッション、下書きの出品。
  - **取引の 2 者だけ**：取引、取引のメッセージ、配送の状態、評価の前の状態、問題の報告。
  - **公開**：販売中・売り切れの出品、公開のプロフィール、商品のコメント、評価の集計。
- 出品の見える範囲は、出品と閲覧者で決まる：出品の状態（下書き、公開、停止、取引中、売り切れ、措置、削除）、売り手のアカウントの状態（停止、退会）、閲覧者と売り手のブロック、措置の範囲。
- 検索、おすすめ、保存した検索の通知、値下げの通知、共有のページ、いいねの一覧のどこかで判定がずれると、措置した出品や停止した売り手の出品が漏れる。

## Options

1. **テナントの RLS は置かない。本人だけの表に持ち主の RLS、取引の表に 2 者の RLS を置き、公開の判定は 1 つの関数 `listingVisible()` にする**
2. 利用者をテナントとみなし、全表に `user_id` の RLS を置く
3. 見える範囲を RLS のポリシーで表す

## Decision

1 を採用する。

### RLS

- **本人だけの表**：`owner_id` と `FORCE ROW LEVEL SECURITY`。トランザクションごとに `SET LOCAL app.actor_id`。`actor_id` はセッションからだけ決め、要求の本文から取らない。
- **取引の 2 者の表**（`transactions`、`transaction_events`、`transaction_messages`、`shipments` の相手に見せる列、`disputes`）：`buyer_id`・`seller_id` を持ち、`app.actor_id` がどちらかの行だけを読める。住所は 2 者の表に置かず、金庫（本人だけ）に置く（[ADR-0006](0006-shipping-orchestration-via-carriers.md)）。
- **公開の表**（出品、写真の参照、公開のプロフィール、商品のコメント、評価の集計）：RLS を置かず、`listingVisible()` で絞る。RLS の外の表の一覧は data-model の領域で持ち、CI で検査する。
- **サービスの役割**：Worker（期限の処理、照合、配送）は `app.actor_id` を持たない。代わりに、行を絞る役割（`app.service = 'deadline-runner'` と、触れてよい表の許可リスト）で動く。RLS を外す役割（`BYPASSRLS`）はマイグレーションだけが持つ。
- **ledger**：利用者の口座の読み出しは `ledger` のサービスの API を通し、API が `actor_id` と口座の持ち主を照らす。ledger の DB にも口座の持ち主の RLS を置く。

### `listingVisible(viewer, listing)`

- 入力：閲覧者（利用者か匿名、ブロックの一覧、運用者の役割）、出品（状態、措置、売り手のアカウントの状態）、文脈（検索、詳細、通知、共有、いいねの一覧、取引の画面）。
- 出力：`visible`、`visible_readonly`（売り切れ・取引中。購入できない）、`hidden`（理由のコード）。
- 判定は決定表で定め、上から最初に一致した行を使う。措置（削除、偽ブランドの確定）と売り手の停止は、文脈と役割より先に評価する。取引の 2 者は、措置した出品でも取引の画面では題名と写真を見られる（理由の表示つき）。
- 呼ぶ経路：出品の詳細、検索の結果、おすすめ、保存した検索の通知、値下げ・いいねの通知、共有のページ、いいねの一覧、プロフィールの出品の一覧。
- `listingVisible()` は `packages/visibility` の 1 か所に置く。検索は、索引の時の写し（状態、措置、売り手の状態）で絞った上で、返す前に Valkey の写し（outbox で 60 秒以内に更新）でもう一度通す。

### 運用者

- 運用者は RLS を外す役割を持たない。`ops-api` が案件（問い合わせ、紛争、審査）に結び付けた JIT の権限を発行し、権限の範囲の行だけを、理由の入力と監査ログつきで読む（security の領域）。
- 住所・本人確認・口座の番号は、権限の種類を分け、通常の CS の権限では見えない。

### 他の案を選ばなかった理由

- **2（利用者をテナント）**：出品・コメントは公開で、検索は全利用者をまたぐ。公開の読み出しに RLS をかけても守るものがない。
- **3（RLS で見える範囲）**：検索（OpenSearch）、通知の fan-out、Valkey の写しに効かない。全経路で同じ判定にするには、1 つの関数のほうが確かめやすい。

## Consequences

- 良くなること：
  - 本人と 2 者のデータの漏れを DB で防げる。
  - 出品の見える範囲の判定を 1 か所で試験できる。
- 引き受けるコスト：
  - 全経路が `listingVisible()` を呼ぶことを、lint と試験で守り続ける。
  - 写しの遅れ（60 秒）の間、措置の前の状態で判定されうる（NFR-016）。購入は core の出品の状態で必ず確かめるので、措置した出品は買えない。

## Confirmation

- 決定表の全行を表駆動テストで確かめる。
- 漏れの経路の表（[quality.md](../quality.md) の 2.2.1 節 G）の全行で、本人・2 者のデータと、措置・停止の出品が出ないことを確かめる。
- RLS の検査：FORCE RLS の表の一覧と、RLS の外の表の許可リストを CI で確かめ、別の利用者・取引の行が読めないことを性質ベーステストで確かめる。
