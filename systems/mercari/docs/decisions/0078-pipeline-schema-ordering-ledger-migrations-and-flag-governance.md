# ADR-0078: デプロイの順を、広げる段のマイグレーション → Worker → ドメインのサービス（`ledger` は最後に単独）→ 入口 → Web にする。スキーマは広げる・移す・縮めるの 3 段で、守る物に触れる変更はテックリードの承認を要る。台帳のマイグレーションは別の流れで、足すだけの DDL、仕訳の表の書き換えの禁止（権限とトリガー）、前後の不変条件と照合、参照の実装の再生、2 人の承認で行う。`legal.*` は別の AppConfig のアプリケーションにし、承認の記録の付いた PR だけで変える

## Context

- [runbooks/](../runbooks/README.md) の 3 節は、デプロイの順（マイグレーション → Worker → ドメインのサービス（`ledger` は最後に単独）→ 入口 → Web）と、マイグレーションは広げる段だけ、縮める段の後は戻さない、を決めた。スキーマの段の条件と、検査の仕組みは決めていない。
- 二重の販売と振り替えの一回性は、DB の部分一意の索引・一意の制約・トリガーが最後の守りである（[ADR-0002](0002-transaction-state-machine-and-single-purchase.md)、[ADR-0003](0003-escrow-and-double-entry-ledger.md)）。マイグレーションでこれを誤って外すと、エラーにならずに壊れる。
- 台帳は追記だけで、過去の仕訳を書き換えない。マイグレーションの埋め直しも例外にしない。
- `legal.*` の値は法務の結論を入れるもので、誤って本番で失効・交換を有効にすると利用者のお金が消える（[ADR-0004](0004-proceeds-model-under-payment-services-act.md)、[quality.md](../quality.md) のリスク 10）。
- アプリの古いバージョンは、数か月残る（[ADR-0079](0079-app-release-trains-min-versions-and-model-releases.md)）。縮める段は、古いバージョンが古い欄を読まなくなってからでなければならない。

## Options

スキーマ：

1. **広げる・移す・縮めるの 3 段と、守る物の一覧の CI の検査。台帳は別の流れ**
2. 通常のマイグレーション（同じ PR で変更と削除）と、レビューだけ
3. 台帳もほかと同じ流れ

`legal.*`：

- a. **別の AppConfig のアプリケーション、承認の記録の付いた PR、CI の禁じた値の検査**
- b. `ops.*` と同じ構成で、Ops が運用の画面から変える
- c. コードの定数にして、変えるたびにリリース

## Decision

1 と a を採用する。詳細は [delivery.md](../architecture/delivery.md) の 3〜5 節。

- 順序：広げる段のマイグレーション（クラスタごと）→ Worker → ドメインのサービス（`ledger` は最後に単独の日）→ `app-api`・`ops-api` → Web。新しい事象は消費者を先に、新しい API の欄はサービスを先に出す。
- 段：広げる（足すだけ、`CONCURRENTLY`、`NOT VALID` と後の `VALIDATE`）→ 移す（両方を書き、1,000 行のバッチで埋める）→ 縮める（2 回のリリースと 7 日、古いバージョンが最小のバージョンより古くなってから）。`lock_timeout = 2s`。型の変更はその場でしない。
- 守る物：`transactions` の部分一意の索引、出品の条件つきの更新の列、仕訳の冪等の一意、`escrow_settlements` の一意、釣り合いのトリガー、負でない CHECK、FORCE RLS のポリシー、サービスの役割の許可リスト、金庫の表。触れるマイグレーションを CI が見つけ、テックリード（ledger は財務も）の承認を求める。
- 事象の形：`packages/events` の型と `schema_version`。足すだけが互換。互換でない変更は新しいバージョンを両方出す。CI で前のリリースと比べる。
- 台帳のマイグレーション：仕訳の表の持ち主は `ledger_owner`（ログインなし）。`ledger_migrator` は仕訳の表の `UPDATE`・`DELETE`・`TRUNCATE` を持たず、仕訳の表にそれを拒むトリガーを置く。足すだけの DDL。前に不変条件と照合が緑、staging の合成の 1 億行で試し、`ledger-ref` の 100 万の場面を再生。テックリードと財務の承認。平日 10〜15 時、月末・月初と企画の日の前後を除く。後に不変条件と照合。DDL は戻さず、誤りは打ち消しの仕訳。
- `legal.*`：AppConfig の別のアプリケーション `legal`。値は `config/legal/<env>.json`（JSON Schema、`value`・`effective_from`・`approval_ref`）。CODEOWNERS は法務と財務。本番の禁じた値（失効、交換、移し替え、期限切れ、未成年の上限）を既定から変える PR は、承認の記録（法務と財務、L の番号）がなければ CI が失敗にする。適用は Ops が平日 10〜15 時に一度にすべて行い、前後に台帳の照合を回す。仕訳に構成のバージョンを記録する。

### 他の案を選ばなかった理由

- **2（通常のマイグレーション）**：同じリリースで列を消すと、古いタスク・古いアプリのバージョンが壊れる。守る物の削除がレビューで見落とされうる。
- **3（台帳も同じ流れ）**：台帳の埋め直し（`UPDATE`）が、ほかのマイグレーションと同じ気軽さで入る。お金の正本の変更の手続きを他と分けるのが 3 クラスタにした理由の 1 つである（[ADR-0001](0001-platform-and-stack.md)）。
- **b（運用の画面から）**：法務と財務の承認の記録と、値の履歴が、コードのレビューの外に出る。誤操作で本番の失効が有効になる。
- **c（定数）**：法務の結論の値の変更に、全サービスのリリースが要る。値と承認の記録が結び付かない。

## Consequences

- 良くなること：
  - 二重の販売・振り替えの守りを、マイグレーションで誤って外せない。
  - 台帳の過去の仕訳が、どの経路でも書き換わらない。
  - `legal.*` の本番の値が、承認の記録なしに変わらない。
- 引き受けるコスト：
  - 列の削除まで最短で 2 週間かかる。
  - 台帳のマイグレーションは月に数回の窓に限られる。
  - 法務の結論を本番に入れるのに、PR と承認の記録の手間が要る。

## Confirmation

- CI の自己の試験：悪い例のマイグレーション（列の削除、守る物の変更、`CONCURRENTLY` でない索引）と、承認の記録のない `legal.*` の変更が失敗する。
- 結合テスト：`ledger_migrator` で仕訳の表の `UPDATE`・`DELETE` が失敗する。
- 本番：台帳のマイグレーションの前後の不変条件と照合の結果を `schema_migrations` に記録する。
