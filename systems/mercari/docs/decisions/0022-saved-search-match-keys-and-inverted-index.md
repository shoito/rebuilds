# ADR-0022: 保存した検索ごとに、出品の流量の見込みが最も小さい照合の鍵の組を 1 つ選ぶ。語の鍵は問い合わせの B の単位の語のうち最もまれなもの。出品は全欄の C と B の単位の語・祖先のカテゴリ・ブランドから鍵を全部出す。逆索引の正本は Aurora content、Valkey は鍵ごとに分けた hash で、Worker のメモリーにバージョンつきでキャッシュする。毎晩、全件の素直な照合と比べる

詳細は [saved-searches-and-alerts.md](../architecture/saved-searches-and-alerts.md) の 5・7 節。

## Context

- [ADR-0008](0008-search-engine-and-index.md) は、保存した検索の照合を自前の逆索引（照合の鍵 → 保存した検索の ID の一覧。content の表と Valkey の写し）で行い、出品の鍵から候補を引いて条件を全部当てる、と決めた。鍵の作り方・選び方・置き方はこの領域に任せた。
- S1 で保存した検索 2,000 万、新しい出品 30 万件/日。S3 で 5 億と 300 万件/日（[architecture/README.md](../architecture/README.md) の 2 節）。
- 鍵の設計を誤ると、通知の取りこぼしがエラーにならずに起きる。E6 の合否は、夜間の参照の実装との比べが 7 日続けて緑であること（[quality.md](../quality.md) の 5 節）。
- 一致の意味は `match_v1` の語の一致（[ADR-0018](0018-search-index-layout-and-japanese-analysis.md)）。

## Options

鍵の選び方：

1. **取りうる鍵の組のうち、出品の流量の見込みの和が最も小さい組を 1 つ選ぶ**
2. 全部の鍵に登録する（出品の側で重複を除く）
3. 決めた順（カテゴリ × ブランド > ブランド > カテゴリ > 語）で選ぶ

写しの置き方：

- a. **Valkey の鍵ごとの hash（2,000 件で分ける）に条件を詰めて置き、Worker の LRU にバージョンつきでキャッシュする**
- b. Worker のメモリーに全件を持つ（各タスクが全件を読み込む）
- c. Aurora を直接引く

## Decision

1 と a を採用する。

- 鍵：`cb:{category}:{brand}`、`b:{brand}`、`c:{category}`、`t:{語}`。語の鍵は、問い合わせの全部の語を `ja_b` で分けた語のうち、流量の最も小さい 1 つ。ブランドが複数なら、ブランドごとの鍵の組。
- 出品の鍵：祖先の 3 つのカテゴリ × ブランド、ブランド、祖先の 3 つのカテゴリ、全欄の `ja_c` と `ja_b` の語。語の鍵で取りこぼさないことは、`match_v1` の定義から言える（C の単位の語が出品にあれば、同じ文字の列の B の単位の語も出品の鍵に入る）。
- 流量の見込みは `ss_key_rates`（直近 7 日の平均、日次）。月に 1 回、全部の鍵を選び直す。選び方は正しさに影響しない。
- 正本：`saved_searches`（本人の RLS）と `saved_search_keys`（サービスの役割だけ）。保存・変更・削除は 1 つのトランザクションで両方と outbox を書き、`ss-index-writer` が Valkey を直して `active_from` を書く。
- 写し：`ss:k:{key}:{shard}`（`ss_id` → MessagePack の条件、語は 64 ビットのハッシュ）。2,000 件を超えたら分ける数を倍にする。`ss:kv:{key}` のバージョンで Worker の LRU（1 GB）を使う。
- Valkey を失ったら照合を止めて SQS に溜め、正本から作り直してから再開する（取りこぼしでなく遅れにする）。
- 毎晩、その日の出品 200 件を、全保存した検索に素直な判定（`saved-search-ref`）で当て、`alert_matches` と比べる。目標は取りこぼし 0・余り 0。

### 他の案を選ばなかった理由

- **2（全部の鍵）**：語の多い保存した検索が何倍もの候補を作り、照合の費用が増える。
- **3（決めた順）**：「ブランドだけ」の鍵が人気のブランドで巨大になる。流量で選べば、まれな語のほうを選べる。
- **b（全件をメモリー）**：S3 で 5 億件・65 GB を各タスクに持てない。
- **c（Aurora）**：1 秒数万の候補の読み出しを content の DB に掛けられない。

## Consequences

- 良くなること：照合の費用が保存した検索の数でなく、鍵の流量の和に比例する。取りこぼしを毎晩、本番の断面で確かめられる。
- 引き受けるコスト：出品 1 件で 180 前後の鍵を引く。Valkey の読み出しが主な費用（S1 の山で 1 秒 28 MB の見込み）。解析器の変更のたびに全保存した検索を解析し直す。

## Confirmation

- PROP-SS-001・002・007（参照の実装との一致、出品の鍵が選んだ鍵を含む、分け直しの間も同じ）。
- 夜間の比べ（7 日続けて緑が E6 の合否）。
- `saved-search-matcher-poc` で、候補の数・Valkey の量を合成の分布で測る。
