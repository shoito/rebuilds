# ADR-0063: 通知を種類の一覧で定め、種類ごとに級（`security`・`transactional`・`engagement`・`announcement`）を持たせる。級ごとに SQS のレーンと消費者を分ける。プッシュの中身は、種類のコード、不透明な ID、決まった文の鍵と、許可した公開の欄だけにする

## Context

- 通知の量は、取引の通知（S1 で 1 日 100 万通前後）より、値下げ・保存した検索の新着（1 日 600 万前後の候補。統合の工程で保存した検索の一致を直した）が大きい（[capacity.md](../architecture/capacity.md) の 1 節）。大型の企画の日は、値下げと新着が数倍になる。
- 取引の通知は p95 10 秒、値下げ・新着は p95 5 分（NFR-008）。量の多い方が少ない方を待たせてはならない。
- プッシュは APNs・FCM（国外の事業者）を通り、端末のロック画面に出る。住所・氏名・電話番号を出さない（NFR-014、[ADR-0006](0006-shipping-orchestration-via-carriers.md)）。取引のメッセージの本文は 2 者のデータで、機械で扱う範囲は法務の確認待ち（L11）。国外への渡し方も法務の確認待ち（L5）。
- 本家は、取引関連の通知をプッシュかメールのどちらかで必ず受けさせ、事務局の個別の連絡は切れない（[ヘルプの記事 239](https://help.jp.mercari.com/guide/articles/239/)、2026-10-10 に確認）。プッシュの中身の作り方は公開されていない（**未検証**）。
- Gmail の題材は、プッシュに中身を入れず、端末が API で取る形にした（[Gmail の ADR-0045](../../../gmail/docs/decisions/0045-push-payload-without-content.md)）。メールの件名と違い、フリマの通知の多くは公開の情報（出品の題名、価格）で足りる。

## Options

レーン：

1. **級ごとに SQS のキューと消費者を分ける**
2. 1 つのキューに優先度の欄を持たせる
3. 取引の通知だけ同期で送り、他を非同期にする

中身：

- a. **許可した公開の欄（題名、価格、ニックネーム、件数、期限）だけを入れる**
- b. 中身を入れず、端末が API で取る
- c. 文をサーバーで作り、そのまま入れる（本文を含む）

## Decision

1 と a を採用する。詳細は [notifications.md](../architecture/notifications.md) の 4・5 節。

- 種類（`kind`）の一覧を `packages/notifications/kinds.ts` の 1 か所に置き、事象 → 種類 → 宛先 → 級 → 既定の経路 → 文の鍵を表で持つ。
- 級：`security`（アカウントの安全、振込。切れない）、`transactional`（取引、自分の出品へのコメント、措置）、`engagement`（いいね、値下げ、保存した検索）、`announcement`（企画。同意した人だけ）。
- 級ごとに SQS のキュー（`ntf-security`・`ntf-transactional`・`ntf-engagement`・`ntf-announcement`）と `notifier-decide` の消費者のプールを分ける。`notifier-send` は級の順に送る。
- 中身に入れてよいのは、種類のコード、対象の ID、通知の ID、文の鍵と、許可の一覧の欄（出品の題名 40 文字、価格、相手のニックネーム、件数、期限の日時）だけ。メッセージ・コメントの本文、住所、本名、電話番号、メールアドレス、残高、口座、本人確認、措置の詳しい理由は入れない。`notifier-send` が型で検査し、外れたら送らない。
- メールは本人の取引の金額を入れてよいが、残高・口座・住所・本名は入れず、ログインの鍵を含むリンクを入れない。
- まとめの鍵（`thread-id`・`collapse_key`）は、利用者ごとの鍵の HMAC にし、取引の ID をそのまま出さない。

### 他の案を選ばなかった理由

- **2（1 つのキューと優先度）**：SQS の標準のキューは優先度で取り出せない。溜まった値下げの後ろに取引の通知が並ぶ。
- **3（取引の通知を同期）**：取引の遷移の関数が APNs の遅れと障害を待つ。遷移と通知の一貫は outbox で十分に取れる。
- **b（中身なし）**：取引の通知の大半は端末の拡張の取得の成否で文が変わり、取れないと「お知らせがあります」になる。フリマの通知の欄は公開のもので足りるので、拡張に頼らずに意味のある文を出せる。
- **c（本文を含む）**：取引のメッセージの本文に電話番号や外の連絡先が入りうる。ロック画面と国外の事業者に流れる（L5・L11）。

## Consequences

- 良くなること：
  - 値下げ・新着の嵐が、取引の通知の p95 10 秒を崩さない。
  - 中身の漏れの範囲が、型の許可の一覧で決まり、試験しやすい。
- 引き受けるコスト：
  - 級ごとに消費者の数と拡大の規則を持つ（[capacity.md](../architecture/capacity.md) の 4 節）。
  - 出品の題名とニックネームは APNs・FCM に渡る。その整理は法務の確認待ち（L5）で、結論によっては題名を外す（文の鍵を替えるだけで済む形にする）。

## Confirmation

- 性質ベーステスト：全種類の中身が許可の一覧の欄だけを持ち、住所・名前・電話番号・本文の形が現れない（PROP-NTF-002、[quality.md](../quality.md) の 2.2.1 節 G）。
- 負荷試験：`ntf-engagement` に 100 万件を溜めた状態で、取引の通知の p95 10 秒（[capacity.md](../architecture/capacity.md) の 7 節）。
- 本番：級ごとの遅れの SLI（[observability.md](../architecture/observability.md) の 3 節）。
