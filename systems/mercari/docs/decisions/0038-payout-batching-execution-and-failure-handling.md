# ADR-0038: 振込は 1 人 1 件ずつ申請し、銀行の営業日の 08:30〜14:30 に 30 分ごとにまとめて、提携銀行の総合振込の API で依頼する。API が 30 分使えなければ全銀の形式のファイルに切り替える。依頼の番号を先に保存し、結果が不明なら再依頼せず照会する。依頼の時点の不能は手数料ごと戻し、完了の後の組戻しは振り込んだ額を戻す

## Context

- 最初の設計で、振込は提携銀行の API、予備に全銀の形式のファイル、手数料は 1 回 200 円と決めた（[architecture/README.md](../architecture/README.md) の 6 節）。振込の申請の受け付けから提携銀行への依頼まで、営業日の 1 時間以内（NFR-006）。
- 本家の振込の申請の手数料は 200 円（[ヘルプの記事 96](https://help.jp.mercari.com/guide/articles/96/)、2026-10-10 に確認）。最低額と着金の日は確かめられなかった（**未検証**）。
- 銀行への依頼が時間切れになると、受け付けられたかがわからない。再依頼すると二重に振り込みうる。
- 振込は、依頼の時点で不能（口座なし、名義の不一致）になることも、完了の後に資金が返ることもある。
- Stripe の題材は、銀行の API を主、全銀の形式のファイルを予備にし、依頼の番号を先に保存して不明なら照会する、と決めた（[Stripe の ADR-0018](../../../stripe/docs/decisions/0018-payout-execution-via-banking-partner.md)）。この題材は考え方を参照し、C2C の売上金のロットと手数料に合わせて自前で書く。

## Options

依頼の単位：

1. **申請を時刻でまとめ、総合振込で依頼する**
2. 申請ごとに即時の振込の API で依頼する

予備への切り替え：

- a. **Ops の承認で切り替える**
- b. 自動で切り替える

## Decision

1 と a を採用する。詳細と例は [payouts-and-points.md](../architecture/payouts-and-points.md) の 5・6 節。

- 1 人の同時の申請は 1 件。最低の申請額は 201 円。手数料 200 円は申請の仕訳で手数料の収益にする。
- まとめは銀行の営業日の 08:30〜14:30 に 30 分ごと、払出口座ごとに 1,000 件まで。営業時間の外と休業日の申請は次の営業日の 08:30。まとめの前に払出口座の残高を確かめ、足りなければ止めて page。
- 依頼の番号（`bank_request_ref`）と申請ごとの参照の番号（`payout_ref`、EDI 情報に載せる 20 文字）を先に保存してから依頼する。再送は同じ番号を使う。結果が不明なら再依頼せず照会し、分からなければ Ops に回す。
- API が 30 分続けて使えないとき、Ops の承認で全銀の形式の総合振込のファイルに切り替える（1 日 2 回の締め）。API で依頼した可能性のあるまとめは、照会で確かめてからファイルに入れる。
- 依頼の時点の不能（`failed`）は、手数料も含めて申請の額を元のロットへ戻す。完了の後の組戻し・資金返却（`returned`）は、振り込んだ額だけを戻す。口座の不能の理由で口座を `unusable` にする。
- 口座の変更などの後 72 時間の待ち（[ADR-0067](0067-account-takeover-step-up-and-payout-holds.md) の `payoutHoldUntil(user)`）と、T&S・運用の `payout_blocks` は、申請を受け付けたまま、まとめに入れない。

### 他の案を選ばなかった理由

- **2（申請ごとの即時の振込）**：銀行の手数料と API の呼び出しが申請の数に比例する。即時の振込の API と 24 時間の振込の可否は銀行ごとに違い（**未検証**）、選定の幅を狭める。30 分のまとめで NFR-006 を満たせる。
- **b（自動の切り替え）**：API で受け付けられたかわからないまとめを、ファイルでもう一度出す危険がある。

## Consequences

- 良くなること：
  - 二重の振込を、依頼の番号の先の保存と照会で防げる。
  - 銀行の API の障害の間も、ファイルで振込を続けられる。
- 引き受けるコスト：
  - 営業時間の外の申請は翌営業日になる。画面に依頼の見込みの時刻を出す。
  - ファイルの切り替えは人の手順で、`payout-failure.md` の手順に書く。
  - 依頼の時点の不能で手数料を戻すので、誤った口座の繰り返しの費用を本システムが持つ。不能の多い利用者を T&S の信号にする。

## Confirmation

- 性質ベーステスト：PROP-PAYOUT-001（不明のときに再依頼しない、成功は 1 回）、PROP-PAYOUT-002（状態と仕訳の一致）。
- 試験のベクトル：全銀の形式のファイルのレコード。
- 結合テスト：銀行の模型で、時間切れ、名義の不一致、組戻し、払出口座の不足を起こし、第 3 段の照合（E3）で外れが残らない。
