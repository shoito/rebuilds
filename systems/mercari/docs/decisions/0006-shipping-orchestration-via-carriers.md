# ADR-0006: 配送は運送会社の API を包むアダプターで扱い、匿名の配送の受け付け・QR・追跡・状態の Webhook を自前で指揮する。住所は `shipping` の金庫に封筒の暗号化で置き、相手に出さない。運送会社の事象は順位で前にだけ進める

## Context

個人どうしの取引では、売り手と買い手が互いの住所・氏名・電話番号を知らずに送りたい。本家は、運送会社 2 社と組んだ専用の配送の商品で匿名の配送を行い、サイズの段ごとに全国一律の料金（160 円〜2,500 円）を置く。専用でない方法は匿名でなく、専用でない方法へ変えるには本人確認が要る（[公式のコラム](https://jp-news.mercari.com/contents/954)、2026-02-17、2026-10-10 に確認）。運送会社との接続の方式（API の形、QR の作り方）は公開されていない（**未検証**）。

この題材では、次を守る（NFR-013、NFR-014）。

- 匿名の配送で、相手に住所・氏名・電話番号が出ない。
- 運送会社の事象から取引の状態まで p95 60 秒。どんな順序・重複でも状態は後ろに戻らない。
- 偽の発送（運送会社に渡していないのに発送の通知をする）を防ぐ。

運送会社の API の能力（匿名の配送の受け付け、QR の発行、Webhook の有無と形、照会）は、契約の前で確かめられない（選定の Story）。

## Options

1. **運送会社ごとのアダプターと、自前の配送の指揮（受け付け、状態の正規化、inbox、照会）。住所は金庫に置き、運送会社へだけ渡す**
2. 配送の集約の外部サービス（複数の運送会社をまとめる業者）に任せる
3. 匿名の配送を持たず、送り状の情報を売り手に出す

## Decision

1 を採用する。

### 配送の方法とサイズと料金

- 配送の方法（`<Brand>便` の運送会社 × サイズの段、匿名でない方法）と料金は、バージョンの付いた表（`shipping_rate_tables`）で持つ。取引は作成の時の表のバージョンを記録し、送料の差し引きに使う（[ADR-0003](0003-escrow-and-double-entry-ledger.md)）。
- 出品の時に売り手が配送の方法を選ぶ。発送の手続きの時にサイズを変えられる（料金の差は売り手の負担。本システムの値）。
- 匿名でない方法に変えるには、売り手の本人確認を求める（本家に寄せる）。

### 運送会社のアダプター

| 操作 | 内容 |
| --- | --- |
| `createShipment` | 匿名の配送の受け付け。配送先・差出人（金庫から）、サイズ、取引の参照の番号を渡し、受け付けの番号と QR（または番号）を受け取る。冪等キー `<transaction_id>:ship:<attempt>` |
| `cancelShipment` | 引き受けの前の取り消し |
| `getTracking` | 追跡の状態の照会 |
| `parseWebhook` | 運送会社の通知の検証（署名・送り元）と、正規の事象への写し |

- 正規の事象と順位：`label_created`（0）< `accepted`（引き受け、1）< `in_transit`（2）< `out_for_delivery`（3）< `delivered`（4）。例外の事象：`returned_to_sender`、`lost`、`damaged`、`held_at_office`（順位の外で、運用の待ち行列へ）。
- 運送会社の Webhook は、inbox の表に（運送会社、事象の ID か追跡の番号＋状態＋時刻）で一度だけ入れる。処理は、配送の行の `max_rank` より高い順位の事象だけで状態を進める。低い・同じ順位は記録だけして捨てる。
- 取引の遷移：`accepted` で取引を `shipped`（`auto_receive_at` を設定）、`delivered` で `delivered`。どちらも遷移の関数を通す（[ADR-0002](0002-transaction-state-machine-and-single-purchase.md)）。
- Webhook がないか遅いときは、照会のジョブが、受け付けの後 6 時間ごと、引き受けの後 6 時間ごとに `getTracking` を呼び、同じ処理に入れる。
- **偽の発送の防止**：匿名の配送では、売り手の「発送の通知」だけでは `shipped` にしない。運送会社の `accepted` を条件にする。匿名でない配送では、追跡の番号の形の検査と照会で `accepted` を確かめられたら `shipped`、確かめられなければ `shipped` にして信用の印を付け、T&S の規則の入力にする。

> 2026-10-10 の注記：「運送会社の `accepted` を条件にする」は、「順位 1 以上の運送会社の事象を条件にする」と読む。`accepted` の通知が欠けて `in_transit`・`delivered` が先に届いたら、`accepted` を補って（`implied`）から進める。売り手の操作だけでは補わない（[ADR-0042](0042-carrier-event-ranking-and-implied-acceptance.md)）。`delivered` の後の例外（`lost` など）は取引に渡さず、運用の待ち行列にだけ入れる。例外に `refused` を足した。下の Confirmation の「`accepted` のない匿名の配送」も同じに読む。

### 住所の金庫

- 住所・氏名・電話番号は、core の `address_vault` の表に、KMS の鍵での封筒の暗号化の列で置く。行は利用者の FORCE RLS（[ADR-0007](0007-single-tenant-and-party-visibility.md)）。
- 復号は `shipping` のサービスの IAM の役割だけが行える。`createShipment` で運送会社へ渡すときだけ復号する。
- 取引の相手・画面・通知・メッセージ・検索・データレイクに住所を流さない。相手の画面には、都道府県（匿名でない配送の時の送り元の表示に使うかは shipping-integrations の領域で決める）も出さない。
- 運用者の閲覧は、案件に結び付けた JIT の権限と理由の入力と監査でだけ（security の領域）。
- 運送会社へ渡すことの整理（委託か第三者提供か）は法務の確認待ち（L5）。

### 他の案を選ばなかった理由

- **2（集約の外部サービス）**：住所が第三者を一段多く通る。偽の発送の防止と状態の順位の規則は、どのみち自前で持つ。配送の指揮は題材の核なので自前にする。
- **3（匿名なし）**：本家の主な価値の 1 つを失う。

## Consequences

- 良くなること：
  - 運送会社の差をアダプターに閉じ、運送会社を足せる。
  - 状態が順位で前にだけ進み、Webhook の乱れに強い。
  - 住所の出口が `shipping` の 1 つに絞られ、漏れの経路を試験しやすい。
- 引き受けるコスト：
  - 運送会社の API の能力が足りない（Webhook がない、QR を返さない）と、照会と運用の手間が増える。選定で確かめる。
  - 照会のジョブが、S3 で 1 日数百万件の呼び出しになりうる。運送会社の上限と費用を capacity の領域で見積もる。

## Confirmation

- 性質ベーステスト：任意の順序・重複・遅れの運送会社の事象の列で、配送と取引の状態の順位は単調に増え、`accepted` のない匿名の配送は `shipped` にならない（[quality.md](../quality.md) の 2.2.1 節 D）。
- 漏れの経路の表（同 G）：取引の相手の画面・API の応答・通知・メッセージ・ログに、住所・氏名・電話番号が出ないこと。
- IAM の検査：`address_vault` の鍵の復号の権限が `shipping` の役割だけにあること。
