# ADR-0005: 決済は外部の提供者に任せ、本システムはカード番号に触れない。カードは購入の時に売上を確定し、預かりは本システムの台帳で持つ。冪等キー、Webhook の inbox、照会で結果を確かめる。Stripe の題材は提供者の 1 つとして使い、設計し直さない

## Context

買い手は、カード・コンビニ払い・売上金・ポイントで払う。カード処理（カード情報の保管、アクワイアラへの接続）は Stripe の題材の論点である。この題材では、提供者の API を使う側として設計する。

- 取引は、購入から受取評価まで最長で数週間かかる（自動の完了は発送の 9 日後。発送の期限と紛争で延びる）。
- カードのオーソリ（与信の確保）には期限がある（ブランドと提供者による。値は提供者ごとに確かめる）。
- 決済の結果は、提供者の応答・Webhook・照会のどれから来るかわからず、重なり、遅れる。
- チャージバックは、取引の完了と売上金の振込の後にも来る。

Shopify の題材は、提供者のアダプターの契約、冪等キー、Webhook の inbox を決めた（[Shopify の ADR-0006](../../../shopify/docs/decisions/0006-payments-via-providers.md)）。Uber の題材は、依頼で与信し、乗車の終わりに確定する（[Uber の ADR-0023](../../../uber/docs/decisions/0023-psp-authorize-at-request-capture-at-end.md)）。

## Options

カードの確定の時点：

1. **購入の時にオーソリと同時に売上を確定し、預かりは本システムの台帳で持つ**
2. 購入の時にオーソリだけ、受取評価の時に確定する
3. 提供者の預かり（エスクロー）の機能を使う

## Decision

1 を採用する。

### 提供者のアダプター

- `packages/payments` に提供者ごとのアダプターを置く。契約は、支払いの作成（カード、コンビニ払い）、照会（本システムの参照の番号で）、返金（全額・一部）、Webhook の検証と正規化、精算の一覧の取得。
- 提供者への要求には、必ず冪等キーを付ける：`<transaction_id>:capture`、`<transaction_id>:refund:<n>`。
- 支払いの試行（`payment_attempts`）の行を、提供者を呼ぶ前に書いてコミットする。試行の ID を提供者への参照の番号にする。結果が不明（時間切れ）なら、照会で確かめる（5 秒、30 秒、2 分、5 分、その後 30 分ごとに 24 時間）。
- 提供者の Webhook は、署名を確かめて inbox の表に提供者のイベント ID で一度だけ入れ、200 を返す。処理のジョブが inbox を読み、照会で確かめた結果で取引の遷移の関数を呼ぶ（[ADR-0002](0002-transaction-state-machine-and-single-purchase.md)）。
- 照会の API を持たない提供者は選ばない。
- **カード番号を扱わない**：カード番号は提供者のホストした入力部品（アプリの SDK、Web の iframe）で受け、本システムは提供者のトークンだけを持つ。本システムのサーバー・ログ・DB に、カード番号とセキュリティコードが入る経路を作らない（PCI DSS の範囲は security の領域で確かめる）。
- Stripe の題材の再構築したものは、提供者の候補の 1 つとして、このアダプターの契約の後ろに置く。

### 手段ごとの流れ

| 手段 | 購入の時 | 確定 | 取り消しの時 |
| --- | --- | --- | --- |
| カード | オーソリと売上の確定を同時に依頼。3-D セキュアは提供者の流れで | 購入の時 | 返金（全額） |
| コンビニ払い | 支払いの番号を発行。取引は `created`（支払い待ち） | 入金の Webhook・照会 | 入金の前は番号の取り消し、後は返金（返金の方法は提供者による。payments-and-escrow の領域） |
| 売上金・ポイント | 台帳で引き当て（[ADR-0003](0003-escrow-and-double-entry-ledger.md)） | 取引の作成と同時 | 台帳で戻す |
| 組み合わせ（ポイント＋カード） | ポイントを先に引き当て、残りをカードで | 両方の確定で `paid` | 両方を戻す |

### チャージバック

- 提供者のチャージバックの事象を inbox で受け、取引に結び付ける。取引が完了の前なら、取引を `disputed` にし、預かりを動かさない。
- 完了の後なら、売り手の売上金から回収する仕訳（`chargeback_receivable`）を書き、売上金が足りなければ不足を記録する。売り手の責任か（偽の発送など）を T&S と CS が判断し、補償するかを決める（disputes-and-customer-support の領域）。
- チャージバックの率を、売り手・買い手・端末の不正の兆しに入れる（[ADR-0009](0009-trust-and-safety-pipeline-boundary.md)）。

### 他の案を選ばなかった理由

- **2（受取評価の時に確定）**：オーソリの期限を、発送の遅れ・紛争の取引が超える。期限切れで確定できないと、売り手に払うお金がない。延長の再オーソリは失敗しうる。
- **3（提供者の預かりの機能）**：預かりの期間、売上金での購入、ポイント、手数料の表が提供者の形に縛られる。台帳を題材の核として自前に持つ方針（[ADR-0003](0003-escrow-and-double-entry-ledger.md)）と合わない。

## Consequences

- 良くなること：
  - 取引がどれだけ長引いても、お金はすでに本システムの側にあり、売り手への振り替えが確実にできる。
  - 提供者の差をアダプターに閉じ、提供者を替えられる。
- 引き受けるコスト：
  - 取り消しのたびに返金になる（オーソリの取り消しより、提供者の手数料が戻らないことがある）。提供者の手数料の扱いは capacity の領域の費用のモデルに入れる。
  - 預かりの期間、本システムが代金を持つ。その法的な整理は法務の確認待ち（L1、[ADR-0004](0004-proceeds-model-under-payment-services-act.md)）。
  - 照会と inbox の処理、提供者ごとの契約の試験を持ち続ける。

## Confirmation

- 契約の試験：提供者ごとに、アダプターの契約（冪等、照会、Webhook の検証、返金）を満たすこと。
- 提供者の模型（`psp-sim`）で、結果の不明・Webhook の重複・遅れ・順序の入れ替えの場面を回し、取引の状態と台帳が釣り合うこと（[quality.md](../quality.md) の 2.2.1 節 B）。
- カード番号の不在の検査：ログ・DB・トレースの抜き取りで、カード番号の形の文字列がないこと（security の領域）。
