# Runbook: 振込の失敗と銀行の障害

- Owner: Ops（当番）、財務
- 対応するアラート: 振込の失敗の率の急増、提携銀行の API の 5xx・時間切れ、`accepted` のまま 2 営業日を超えた振込、払出口座の残高の不足（page）
- 最終確認日: 2026-10-10

振込の流れは [payouts-and-points.md](../architecture/payouts-and-points.md) の 5・6 節（[ADR-0038](../decisions/0038-payout-batching-execution-and-failure-handling.md)）。乗っ取りの後の振込の待ちは [account-takeover.md](account-takeover.md)。

## 症状

- まとめ（銀行の営業日の 08:30〜14:30、30 分ごと）の依頼が時間切れ・5xx になる。
- 結果の照会で不能（`failed`）が急に増えた。
- まとめの前の払出口座の残高が、振り込む額の合計に足りない。
- 振込の状態が `unknown` のまま、照会でも受付の有無が分からない。

## 影響

- 売り手の振込が遅れる（NFR-006 の「営業日の 1 時間以内に依頼」）。申請は受け付け続け、`requested` のまま待つ。
- 二重の振込は、依頼の番号（`bank_request_ref`）の先の保存と照会で防ぐ。結果が不明なときに再依頼すると二重になりうる。

## 確認

1. 振込の状態ごとの数（`requested`・`batched`・`submitted`・`unknown`・`accepted`・`failed`）と、不能の理由のコード（`account_closed`、`name_mismatch` など）の分布。
2. 提携銀行の API の応答（5xx・時間切れの率）と、銀行の障害の知らせ。
3. 払出口座の残高と、その回の振り込む額の合計。
4. 不能が特定の口座・利用者に集まっていないか（乗っ取り・運び屋の口座の兆し。口座の HMAC で数える）。

## 対処

1. **結果が不明（`unknown`）**：再依頼しない。`bank_request_ref` で照会する。照会でも分からなければ、そのまとめを止め、銀行に問い合わせる（二重の振込を防ぐことを優先する）。
2. **API が 30 分続けて使えない**（5xx・時間切れが 3 回続く）：Ops の承認で、その回からのまとめを全銀の形式の総合振込のファイルに切り替える。API で依頼した可能性のあるまとめは、照会で確かめてからファイルに入れる。ファイルの締めは 09:00 と 13:00。渡した記録（誰が、いつ、どのファイル）を `payout_batches` に残す。
3. **払出口座の不足**：まとめを止める（自動）。財務が資金を移す。移した後に止めたまとめを流す。
4. **不能の急増**：口座の不能は `payout_failed` の仕訳で申請の額と手数料（200 円）を元のロットへ戻し、口座を `unusable` にして利用者に更新を求める（自動）。特定の利用者・口座に集まるなら、T&S の `fraud` の待ち行列に回し、必要なら `payout_blocks` をかける（人の判定）。
5. **全体を止める**：銀行の障害が長いとき、または台帳の照合の異常のときは `ops.payouts_enabled` を止める（申請は受け付け続ける）。
6. **組戻し・資金返却**：銀行の明細の入金を `payout_ref` で見つけ、`returned` にし、`payout_returned` で振り込んだ額だけ戻す（手数料は戻さない）。額が違えば外れ（`recon_breaks`）にして財務が決める。

## エスカレーション

- 二重の振込の疑い：SEV1。財務の責任者、Dev のテックリード、銀行の窓口。
- 銀行の障害が営業日をまたぐ：SEV2。PM に利用者への知らせを依頼する。

## 事後

- 依頼の遅れ（申請から依頼まで）と、ファイルへの切り替えの時間を記録する。
- 第 3 段の照合（E3）で、振込の仕訳と銀行の明細が 1 対 1 で合うことを確かめる。
- 不能の理由の分布を、口座の登録の確かめ（名義の照会）の改善の材料にする。
