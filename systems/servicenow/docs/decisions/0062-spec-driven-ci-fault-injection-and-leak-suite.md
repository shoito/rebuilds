# ADR-0062: CI は `spec.md` の決定表を直接読み込んで動かし、性質ベーステスト・障害注入・出口ごとの漏れの試験を、PR（変更に関わるもの、短いバージョン）と夜間（全体）の 2 段で必須にする

詳細は [delivery.md](../architecture/delivery.md) の 2 節。

## Context

[process.md](../../../../docs/process.md) の 6・7 節は、決定表を `spec.md` から直接読む表駆動テストにし、要件・性質・決定表の ID をテストの名前に含めて CI で追跡を検査すると決めた。[AGENTS.md](../../AGENTS.md) は、この題材に、ACL の決定表、計時の性質、ワークフローの障害注入、CMDB の性質、出口ごとの漏れの試験を求める。各領域の文書は、数十の決定表（`DT-ACL-*`、`DT-SLA-*`、`DT-FLOW-*` など）と性質（`PROP-*`）を置いた。

この題材の誤りの多くは、個々の例示のテストでは見つからない：条件の組み合わせの抜け、並行と障害の組み合わせでの二重の遷移、出口の 1 つからの値の漏れ。

## Options

### 決定表

1. **`spec.md` の表を読み込む道具（`spec-table-loader`）で、各行を 1 ケースにする**
2. 表をテストのコードに書き写す

### 重い試験の置き場所

- a. **PR は変更に関わるものの短いバージョン、夜間は全体**
- b. すべてを PR で全体
- c. 夜間だけ

## Decision

1 と a を採用する。

- PR：決定表（最後の網羅の行のケースを必須）、否定の表、変更に関わる性質（200 回、種と縮めた反例を PR に出す）、障害注入（engine・Record Service・ingest に触れるとき、障害の点ごとに 20 回）、漏れの試験（触れた出口）、テナントの分離、ID の追跡（`REQ`・`PROP`・`DT`・`SEC`）、計時の参照の実装との比較（計時の関数に触れるとき）、検索の評価（解析器に触れるとき）、組み込みの定義の検査、純粋さの lint。
- 夜間：性質 1 万回、障害注入の全体（障害の点 × 200、接続の切断、DB の再起動）、漏れの試験の全体（16 の出口 × 組み込みのテーブル × 組み込みのロール）、E2E の全体、DAST、短い負荷試験。夜間が 2 日続けて失敗したら、フラグを広げない。
- 性質・障害注入で見つけた反例は、`quality/regressions/` に固定のケースとして残す。
- 障害の点はテストのビルドにだけ入る名前付きの呼び出しで、本番のビルドには入れない。

2 を採らない理由：仕様とテストがずれる（process.md の 6 節）。表を直す人が、テストの直しを忘れる。

b を採らない理由：障害注入と漏れの試験の全体は数十分〜数時間かかり、PR の待ちが長くなる。関わるパスに絞れば、PR で大事なものを見られる。

c を採らない理由：遷移の二重や漏れの誤りが、マージの後に見つかり、`main` を壊す。

## Consequences

- 良くなること：
  - 仕様の表と性質が、そのまま CI の合否になる。
  - 並行と障害の組み合わせの誤りを、マージの前に見つけやすい。
- 引き受けるコスト：
  - CI の時間と費用が増える（PR の目標 25 分）。
  - `spec-table-loader` の保守（Markdown の表の形の約束）。表の形の誤りは CI で知らせる。

## Confirmation

- CI の追跡の検査：すべての ID がテストから参照される。表の最後の行のケースがある。
- 夜間の CI の結果を quality の指標にする（[delivery.md](../architecture/delivery.md) の 8 節）。
