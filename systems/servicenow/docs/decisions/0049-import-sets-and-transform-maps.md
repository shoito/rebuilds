# ADR-0049: 一括の取り込みは取り込みの行の表に原本を置いてから、版付きの変換の対応で 1 行ずつ Record Service を通して書く。一致のキーは索引のあるフィールドに限り、キーごとの助言ロックで重複を防ぎ、2 つ以上に一致したら行のエラーにする。CI への取り込みは CMDB の入口を通す

詳細は [api-and-integrations.md](../architecture/api-and-integrations.md) の 5 節。

## Context

[intent.md](../intent.md) は、取り込みの API と CSV の取り込み（社員・組織、資産管理、本家からのデータの移行）を求める。CI の作成・更新は識別と調整の 1 つの入口だけを通す（[ADR-0005](0005-cmdb-identification-and-reconciliation.md)、[ADR-0037](0037-ci-ingest-entry-point-and-ambiguity-hold.md)）。人事の一括の取り込みは `acl_version` を取り込みの単位で 1 回だけ上げる（[access-control.md](../architecture/access-control.md) の 7 節）。

本家は、取り込みの表に置き、変換の対応で対象の表に写す。一致のキー（coalesce）が既存のレコードと一致すれば更新、なければ作成する。複数のキーはすべて一致したときだけ更新する（[Import set coalesce](https://www.servicenow.com/docs/bundle/zurich-integrate-applications/page/administer/import-sets/concept/c_ImportSetCoalesce.html)、2026-09-28 に確認。本文は未検証で、解説の記事と検索の結果の抜粋で確認）。キーが複数のレコードに一致したときの本家の振る舞いは未検証（本家の振る舞いで、この決定の前提ではない。本システムは推測で選ばず失敗にする）。

## Options

### 段の数

1. **原本を取り込みの行の表に置き、その後に変換する（2 段）**
2. ファイルを読みながら直接対象の表に書く（1 段）

### 並行の重複

- a. **一致のキーの値ごとの助言ロック（`pg_advisory_xact_lock`）と、キーの区画ごとの順の処理**
- b. 対象の表の一意の索引だけに頼る
- c. 取り込みの実行を 1 テナントで 1 つに直列にする

### あいまいな一致

- x. **行のエラーにし、推測しない**
- y. 最も新しい（または最初の）行を更新する

## Decision

1、a、x を採用する。

- 取り込みの実行（`run_key` で 7 日一意）と、原本の写しの `import_row`（30 日）。変換の対応はメタデータで、公開で不変の版。実行は開始の時の版に固定する。
- 変換は Engine の `bulk_job` で、1 行 1 トランザクション、Record Service の保存（`channel = import`、`run_as` の主体）。主体の表（利用者・グループ・所属）は 1,000 行ずつにまとめ、まとまりごとに `acl_version` を 1 回上げる。
- 一致のキーは索引のあるフィールドだけ（公開の時に確かめる）。行のトランザクションの始めにキーの値のハッシュで助言ロックを取る。同じ実行の同じキーの行は、区画の中で `row_no` の順に処理する。
- 行の判定は DT-IMP-001：空のキー・2 つ以上の一致はエラー。一致の検索は `run_as` の ACL で行い、見つからなければ存在だけを確かめ、読めない行があれば `coalesce_target_not_readable` のエラーにする（重複を作らない）。
- CSV の文字コードは UTF-8（BOM）→ 厳格な UTF-8 → Shift_JIS の順に試し、どれも失敗なら実行を失敗にする（化けたまま保存しない）。
- 上限：100 MB、50 万行、1 テナントの同時の変換 2。最初の 1,000 行でエラーが 50% を超えたら止める。
- CI のクラスを対象にする変換は作れない。対象を `cmdb_payload` にして、CMDB の入口にペイロードとして送る。

2 を採らない理由：変換の対応の誤りを直して同じ原本でやり直せない。行ごとの結果を原本と並べて見せられない。途中の失敗の続きの位置を、ファイルの読み取りの位置で持つことになる。

b を採らない理由：テナントのフィールドの一致のキーには、一意の索引がない（`ext_index` は一意の制約を持たない）。組み込みのフィールドでも、一意でない列（メールアドレスなど）を一致のキーにしたい。

c を採らない理由：人事と資産管理の取り込みが、互いを待たせる。キーの単位のロックで足りる。

y を採らない理由：誤った行を更新すると、戻しにくい（社員の情報の上書き）。CMDB と同じく、あいまいなら止める。

## Consequences

- 良くなること：
  - 並行の取り込みでも、同じキーの重複を作らない。
  - 結果がファイルの順で決まり、同じ原本と版でやり直すと同じになる。
  - CI は取り込みでも識別と調整の入口を通る。
- 引き受けるコスト：
  - 原本の写しの分、書き込みと保存が増える（30 日で消す）。
  - 1 行 1 トランザクションで、1 秒の行の数に上限がある（E11 で計測）。
  - あいまいな一致の行は、人が直してやり直す。

## Confirmation

- 決定表 DT-IMP-001。
- 性質ベーステスト PROP-IMP-001（並行でも重複しない）、PROP-IMP-002（決定性）。
- 公開の検証のテスト：CI のクラスを対象にする変換の対応、索引のない一致のキーを拒否する。
- 障害注入：変換の途中でプロセスを落とし、済んだ行をやり直さず、残りの行から続く。
