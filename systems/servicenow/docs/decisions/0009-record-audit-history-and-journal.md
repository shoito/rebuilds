# ADR-0009: 監査の履歴は保存ごとに 1 行、変更と同じトランザクションで追記だけの表に書く。日ごとのハッシュの鎖を S3 Object Lock に置く

詳細は [data-dictionary-and-tables.md](../architecture/data-dictionary-and-tables.md) の 7 節。

## Context

[intent.md](../intent.md) は、監査の対象のテーブルの変更が、変更と同じトランザクションで履歴に残り、利用者が消したり書き換えたりできないことを求める。NFR-010 は、履歴の欠けを 0 件にする。顧客は J-SOX の証跡として、変更の記録・承認・権限の変更の履歴を使う。保持の年数は法務の確認待ち（L4）である。

本家は、フィールドの値の変更を監査の表に、作業メモ・コメントを別の表に持ち、テーブル・フィールドの単位で監査を止められる（監査の表と、作業メモ・履歴の別の表、辞書の監査の印でのテーブルの単位の有効は [Viewing Sys Audit and Audit Relationship Change tables](https://www.servicenow.com/docs/r/platform-security/c_UnderstandingTheSysAuditTable.html)、2026-09-28 に確認。フィールドの単位で外す方法は [コミュニティの記事](https://www.servicenow.com/community/developer-blog/servicenow-things-to-know-55-how-to-activate-deactivate-auditing/ba-p/2774658) だけで、未検証）。

## Options

### 行の単位

1. **保存ごとに 1 行。変えたフィールドを JSON にまとめる**
2. フィールドの変更ごとに 1 行

### 書き方

- a. **Record Service が同じトランザクションで書く**
- b. DB のトリガーで書く
- c. outbox から非同期で書く

### 改ざんの防止

- x. **DB の権限で追記だけにし、日ごとのハッシュの鎖を S3 Object Lock に置く**
- y. DB の権限だけ

## Decision

1、a、x を採用する。

- `record_change` に、保存ごとに 1 行（操作、バージョン、実行した主体と本人、経路、原因、`changes`、削除のときの全体の値）を書く。月ごとのパーティション。
- `journal_entry` に作業メモ・コメントを書く。編集・削除しない。
- アプリの DB のロールは `INSERT` と `SELECT` だけを持つ。保持の期間を過ぎたパーティションだけを、保守のロールが外して消す。
- 日次で、テナント・日ごとの行のハッシュの鎖を計算し、S3 Object Lock（compliance モード）に置く。
- 組み込みのテーブルの監査は止められない。テナントのテーブルは既定で対象にし、止めた操作も履歴に残す。
- 既定の保持は 7 年（延長は 10 年まで、短縮はできない）。L4 の結論で見直す。L4 が済むまで E2 の監査の `spec.md` を承認しない。

2 を採らない理由：1 回の保存で平均数フィールドが変わり、行の数が数倍になる。S1 の 20 万件/日の作成と、その数倍の更新で、書き込みと索引が重い。

b を採らない理由：実行した主体・本人・経路・原因は、アプリのコンテキストにあり、トリガーに渡すにはセッションの変数が要る。Record Service が唯一の入口なので、そこで書くほうが試しやすい。

c を採らない理由：変更と履歴が別のトランザクションになり、欠けが起こりうる（NFR-010 に反する）。

y を採らない理由：DB の特権（運用者・保守のロール）による書き換えを、外から確かめる手段がない。監査の担当が自分で確かめられるようにする。

## Consequences

- 良くなること：
  - 履歴の欠けが起きないことを、同じトランザクションで説明できる。
  - 改ざんのないことを、監査の担当が S3 のハッシュと突き合わせて確かめられる。
- 引き受けるコスト：
  - フィールドの履歴の画面は、JSON を展開して読む。1 つのレコードの履歴が多い（数千回の更新）と遅くなる。画面はページに分ける。
  - 7 年の保持で、履歴の表が大きくなる。古いパーティションを安い置き場所へ移すかを S2 で検討する。
  - 個人の削除の請求との関係は、法務の確認（L1・L4）の後に決める。

## Confirmation

- 性質ベーステスト PROP-DICT-003（監査の完全）。
- 障害注入：コミットの直前にプロセスを落とし、行と履歴のどちらも残らない。
- DB の権限の検査（CI）：アプリのロールが `record_change`・`journal_entry` に `UPDATE`・`DELETE` を持たない。
- 日次のハッシュの鎖の検証のジョブ：食い違い 0 件。
