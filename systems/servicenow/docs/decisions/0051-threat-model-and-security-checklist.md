# ADR-0051: 脅威は信頼境界と部品ごとの STRIDE で洗い出し、対策を `SEC-NNN` のチェックリストにして各行に拒否の側のテストを持たせる。ACL・テナントの分離・監査・承認に触れる変更は `security:sensitive` にする

詳細は [security.md](../architecture/security.md) の 2〜4 節。

## Context

この題材で最も重い障害は、テナントをまたいだ漏えい（NFR-009）、ACL で読めない値の漏えい（NFR-010、K6）、監査の証跡の改ざん・欠け、なりすましの承認、外への送信の踏み台である。対策は多くの領域の文書に散らばる（access-control、workflow-engine、notifications-and-email-ingest、search、reports、api-and-integrations）。散らばったままだと、1 つの抜けに気づけない。

他の題材は、脅威モデルと標準（Auth0 は RFC 9700）のチェックリストを持ち、各行に拒否の側のテストを付けている（Auth0 の ADR-0053）。この題材には、1 つの標準に対応する形のチェックリストがない。

## Options

1. **信頼境界と部品ごとの STRIDE から、本システムの `SEC-NNN` のチェックリストを作る。各行に拒否の側のテストと、決める領域を持たせる**
2. OWASP ASVS の要件をそのままチェックリストにする
3. チェックリストを持たず、各領域の文書のテストに任せる

## Decision

1 を採用する。

- 信頼境界は 7 つ（エッジ、テナント、ACL、外向き、メールの受信、管理の面、開発の環境）。部品ごと（エッジとルーター、App、Record Service と Engine、Ingest、Notifier、Indexer とレポート、データの置き場所、CI/CD）に STRIDE の表を持つ。
- 対策を `SEC-NNN` の行にし、「決める領域」と「拒否の側のテストの例」を持たせる。テストの名前に `SEC-NNN` を含め、すべての行がテストから参照されていることを CI で確かめる。
- ASVS 5.0 の Level 2 を全体の目標にし、要件の番号との照合は E1 で行う（チェックリストの行は ASVS の要件を満たすための本システムの対策の索引である）。
- `security:sensitive` のパス（ACL の判定と述語のコンパイラ、保存の流れ、RLS とマイグレーション、監査の履歴、承認、成り代わり、SSO、差出人の信頼、Webhook の送信、KMS・IAM・WAF の Terraform）の変更は、作成者と別の 2 人の人の承認を要る（[delivery.md](../architecture/delivery.md) の 3 節）。
- テナントの分離の破れ、ACL の迂回、監査の改ざん、承認の偽りにつながる脆弱性は、CVSS にかかわらず Critical とする。

2 を採らない理由：ASVS は汎用で、この題材に固有の脅威（読めない値の推測、承認の二重の反映、メールのなりすましによるチケットの操作）を行として持たない。ASVS は目標の段として使い、行は本システムの対策で書く。

3 を採らない理由：出口が 16 あり、新しい出口（検索、レポート、Webhook）を足す領域が、他の領域の約束を知らずに抜けを作りうる。1 つの表と CI の参照の検査で、抜けを見える形にする。

## Consequences

- 良くなること：
  - 対策の抜けが、テストのない行として CI で見える。
  - 外部のペンテストの範囲を、表から決められる。
- 引き受けるコスト：
  - 新しい出口・部品を足す変更は、この表の更新とテストの追加を要る。
  - `security:sensitive` の 2 人の承認で、レビューの待ちが増える。

## Confirmation

- CI：`SEC-` の行のすべてがテストの名前から参照されている。
- CI：`security:sensitive` のパスの PR に 2 人の承認がなければマージさせない。
- E12 の外部のペンテストの範囲に、表の STRIDE の重い行を入れる。
