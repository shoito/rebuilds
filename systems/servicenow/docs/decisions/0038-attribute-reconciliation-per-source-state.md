# ADR-0038: 属性の調整は CI・取り込み元ごとの最新の観測の状態を max の結合で持ち、値をその状態の集合から純粋な関数で選ぶ。鮮度はその属性の最新の観測の時刻から測る。関係の有無も取り込み元ごとの状態から決める

詳細は [cmdb-and-reconciliation.md](../architecture/cmdb-and-reconciliation.md) の 6・7 節。

## Context

[ADR-0005](0005-cmdb-identification-and-reconciliation.md) は、CI の属性ごとに最後に書いた取り込み元と時刻（来歴）を持ち、新しいペイロードを次の決定表で書くか決めるとした：来歴がないか同じ取り込み元なら書く（古ければ書かない）、優先度が高ければ書く、低くても高い取り込み元の値が鮮度の期限を過ぎていれば書く、それ以外は書かない。そして、属性の最終の値が到着の順序によらず決まることを性質として確かめるとした。

この決定表は、来歴に最後に書いた 1 つの取り込み元しか持たないため、到着の順で結果が変わる場合がある。例：強い取り込み元 H が 1 日目に x、弱い取り込み元 L が 40 日目に y を観測し、鮮度が 30 日とする。H → L の順では「H の値は L の時刻から見て古い」で y を書く。L → H の順では、L が先に書き、H は「優先度が高い」で x を書く。

本家は、属性の最新の観測の時刻と、取り込み元の新しさの時刻で値を選ぶ（[Identification and Reconciliation engine (IRE)](https://www.servicenow.com/docs/r/servicenow-platform/configuration-management-database-cmdb/ire.html)、2026-09-28 に確認）。本家のデータの更新の規則と動的な調整の規則の細部は未検証。

## Options

1. **CI・取り込み元ごとの最新の観測の状態を持ち、状態の集合から値を選ぶ**
2. ADR-0005 の決定表のまま、最後に書いた来歴だけを持つ
3. すべての観測を追記で持ち、値を選ぶたびに全体から計算する

## Decision

1 を採用する。ADR-0005 の調整の原則（属性ごと、優先度と鮮度、ペイロードの時刻、到着の順序によらない）は変えず、その細部をこの形に決める。

- `ci_source_state(tenant_id, ci_id, source_id, attrs, last_seen_at)`。`attrs` は属性ごとの `{v, t}`。更新は属性ごとに `t` の大きいほう（同じなら正準の値の順）を採る max の結合。明示の空は `v = null` の観測、ペイロードにない属性は観測なし。
- 値の選び方（DT-CMDB-002）：`T` = その属性の観測の最新の時刻、`live` = `t ≥ T − staleness(s)` の観測、`live` の中で優先度、時刻、正準の値、取り込み元の ID の順で最初のもの。現在の時刻を読まない。
- 優先度と鮮度は `ci_precedence(class, attr | *, source)` で、子のクラスの規則が親に勝つ。既定は `asset_mgmt` 10、`manual`・`cloud_api` 20、`api` 30、`csv` 40、鮮度 30 日。
- 選んだ値が変われば `ci` を更新し、選ばれた取り込み元と時刻を `provenance` に持ち、監査の履歴に残す。
- 関係は `ci_relation_source_state(relation, source, present | absent, t)` の max の結合で、どれかの取り込み元の最新が `present` なら `present`。関係の全体の印は、その取り込み元が観測した関係にだけ `absent` を入れる。
- 統合も同じ max の結合で、2 つの CI の状態を合わせる。

2 を採らない理由：上の Context の例で、到着の順で結果が変わる。性質（順序によらない）が成り立たない。

3 を採らない理由：取り込み元は同じ CI を毎日送る。観測をすべて持つと、1 秒 1,000 CI × 属性 20 の行が溜まり続ける。取り込み元ごとの最新だけで、選ぶのに要る情報は足りる（古い観測は、同じ取り込み元の新しい観測に負けるので、結果に影響しない）。

## Consequences

- 良くなること：
  - 状態の更新が半束の結合（交換・結合・冪等）なので、順序によらないこと・冪等なことが構造から言え、性質ベーステストで確かめられる。
  - 「この値はどの取り込み元から来て、他の取り込み元は何と言っているか」を画面に出せる。
- 引き受けるコスト：
  - CI・取り込み元ごとに 1 行の状態を持つ（取り込み元 3 なら CI の 3 倍の行）。1 行の JSONB の更新で、属性ごとの行より書き込みは少ない。
  - 取り込み元の時計が大きく未来にずれると、その観測が長く勝つ。5 分より未来の観測を入口で拒む（ADR-0037）。
