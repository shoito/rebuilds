# ADR-0032: 評価は利用者・版ごとに 1 件にし、旗は理由を必須にして持ち主のタスクにまとめる。自己解決は仮名のセッションの事象から、明示と推定を分けて数える

詳細は [knowledge.md](../architecture/knowledge.md) の 7 節。

## Context

[intent.md](../intent.md) の K8 は、ポータルでナレッジを見て申請をやめた割合（自己解決の率）を計測できることを求める。目標の値は E9 で決める。記事の持ち主は、古い・誤った記事を知りたい。

本家は、「役に立ったか」と星の評価、理由が必須の旗を持ち、旗や低い評価からフィードバックのタスクを作る（コミュニティの記事で確認。未検証）。本家は、ポータルのフォームで記事の閲覧を計測の表に残す（KB0712999 の抜粋。未検証）。

自己解決は、そもそも「申請しなかった」ことの計測で、直接には観測できない。どこまで推定に頼るかを決める必要がある。ポータルの利用者の行動の記録は個人の情報になりうる（[intent.md](../intent.md) の L1）。

## Options

### 低い評価のタスク

1. **割合と件数のしきい値でタスクにし、旗は 1 件でタスクにする。開いているタスクにまとめる**
2. 低い評価の 1 件ごとにタスクを作る

### 自己解決の数え方

- a. **明示（「解決した」の押下）と推定（記事の閲覧の後 30 分に申請がない）を分けて数える**
- b. 明示だけを数える
- c. 推定だけを数える

### 事象の記録

- x. **仮名のセッションの ID で持ち、利用者の ID と検索の語を入れない**
- y. 利用者の ID で持つ

## Decision

1、a、x を採用する。

- `kb_rating` は `(version_id, user_id)` で一意、送り直しは上書き。記事の合計は同じトランザクションで差分を足す。
- 旗は理由とコメントが必須。開いているフィードバックのタスクがあれば足し込む。低い評価は、直近 30 日の「役に立たない」の割合 50% 以上かつ 5 件以上でタスクにする。
- 事象（`portal.search`、`kb.suggested`、`kb.viewed`、`kb.resolved`、`form.started`、`form.submitted`）を `portal_event` に仮名のセッションで書き、90 日保つ。
- 機会（フォームの開始）ごとに、30 分の事象の集合から DT-KB-003 で判定する純粋な関数を、日次のジョブで動かす。率は明示と推定の和と、明示だけの両方を出す。

2 を採らない理由：持ち主のグループのタスクが、少数の評価で溢れる。タスクが多いと、重要な旗が埋もれる。

b を採らない理由：押さずに去る利用者が多く、率を大きく過小に見積もる。改善の比較に使いにくい。

c を採らない理由：別の理由で去った利用者（会議に呼ばれた）も自己解決に数える。明示の率と並べれば、推定の幅を示せる。

y を採らない理由：ポータルの閲覧の行動を個人に結ぶ必要がない。個人の情報の扱い（L1）を増やさない。

## Consequences

- 良くなること：
  - 自己解決の率を、推定の幅とともに示せる。
  - 事象の記録が個人の追跡にならない。
- 引き受けるコスト：
  - 推定の判定の時間（30 分）の値で率が変わる。E9 の計測で決め直す。
  - 利用者ごとの自己解決の分析（部署ごとなど）はできない。
