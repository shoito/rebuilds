# ADR-0030: 依頼者は自分が依頼した・自分のための・見守りに入った要求だけを見る。変数ごとに依頼者への公開を持ち、他人のための申請は品目の許可と関係があるときだけ許す。フォームからのレコードの作成も依頼者の主体で保存する

詳細は [service-catalog-and-requests.md](../architecture/service-catalog-and-requests.md) の 6・7 節。

## Context

社員（`requester` のロールだけの利用者）は、ポータルで申請し、自分の要求の状況を見る。担当者の作業メモや、担当者だけが使う変数（払い出した機器の管理の番号など）は、依頼者に見せたくない。秘書やサービスデスクが、他人のために申請することもある。インシデントの報告のフォームは、要求を作らずにインシデントを作る。

[access-control.md](../architecture/access-control.md) は、ポータルの自分のチケットの出口を、リストと同じ判定で扱い、ポータル用の抜け道を作らないと決めた（6.2 節の 16 行）。本家の「利用できる人の条件」の意味は、公式の本文で確かめられなかった（未検証）。

## Options

### 依頼者の範囲

1. **組み込みの ACL の規則で、依頼した・自分のための・見守りの 3 つの関係の要求だけを読める。変数ごとに依頼者への公開の印を持つ**
2. ポータルの専用の API で、要求の一部の項目だけを返す

### 他人のための申請

- a. **品目の許可と、上長（3 段まで）・代理・サービスデスクの関係を要る**
- b. 品目の許可だけで、誰のためにでも申請できる

### フォームからのレコードの作成

- x. **依頼者の主体で Record Service の保存を通し、マップの先のフィールドを依頼者が書けることを公開の時に検査する**
- y. システムの主体で作り、依頼者の ACL を通さない

## Decision

1、a、x を採用する。

- 依頼者の組み込みの規則は DT-REQ-002。作業メモ、実行のタスクの担当者、`visible_to_requester = false` の変数は読めない。
- 品目の `audience` は `include` と `exclude` を持ち、除くほうが勝つ。`include` が空なら誰も使えない。主体の属性だけで評価し、見える品目の集合を `acl_version`・`meta_version` のキーでキャッシュする。
- 他人のための申請は DT-REQ-003。対象者にも品目が使えることを確かめる。
- フォームからのレコードの作成は、依頼者の主体で保存する。マップしなかった回答は、依頼者に見せる変数はコメント、見せない変数は作業メモに残す。

2 を採らない理由：出口ごとの判定を作ることになり、リスト・件数・検索・通知で漏れが起きうる（[AGENTS.md](../../AGENTS.md) の「1 つの判定の関数」に反する）。

b を採らない理由：任意の社員のために申請でき、承認の依頼が対象者の上長に届く。なりすましの申請になりうる。

y を採らない理由：フォームの定義の誤りで、依頼者が本来書けないフィールド（優先度、担当者）を書けてしまう。

## Consequences

- 良くなること：
  - ポータルの画面・API・通知が、同じ ACL の規則で依頼者の範囲を守る。
  - 他人のための申請の証跡（どの関係で許したか）が残る。
- 引き受けるコスト：
  - 依頼者に見せない変数の設定を、品目の管理者が正しく付ける必要がある。既定は「見せる」なので、機微な変数は明示で外す。
  - 上長の関係を 3 段まで読むので、組織の取り込み（E3）の上長の正しさに頼る。

## Confirmation

- 決定表 DT-REQ-002、DT-REQ-003。
- 性質ベーステスト PROP-REQ-003（依頼者の範囲。リスト・件数・検索の出口）。
- 出口ごとの漏れの試験に、依頼者に見せない変数の「漏れの印」を加える（[access-control.md](../architecture/access-control.md) の 12.3 節）。
