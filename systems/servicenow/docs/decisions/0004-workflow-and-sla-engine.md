# ADR-0004: ワークフロー・承認・SLA は Aurora の上の自前の耐久性のあるエンジンで動かし、遷移をレコードと同じトランザクションで 1 回だけ行う

## Context

ITSM の業務は、長く続く処理の組み合わせである。

- 承認：変更の CAB の承認、要求の上長の承認。数時間から数日、応答を待つ。期限切れと代理がある。
- フロー：レコードの作成・更新・時刻をきっかけに、条件・承認・タスクの作成・通知・待ち・外部の呼び出しを進める。管理者がノーコードで作る。
- SLA：業務カレンダーの上で時間を数え、期限の前に警告し、期限で違反にする。一時停止・再開・リセットがある。

本家の Flow Designer は、トリガー・アクション・サブフロー・条件でフローを組み、承認のアクションで規則の組を書ける（[Flows, subflows, and actions reference](https://www.servicenow.com/docs/bundle/yokohama-build-workflows/page/administer/flow-designer/reference/flow-designer-reference.html)、2026-09-28 に確認）。本家の SLA の定義は、開始・一時停止・停止・リセットの条件、スケジュールの取り方、タイムゾーンの取り方（呼び出し元、SLA の定義、CI の場所、タスクの場所、呼び出し元の場所）、さかのぼりの開始を持つ（[Create an SLA definition](https://www.servicenow.com/docs/bundle/zurich-it-service-management/page/product/service-level-management/task/t_CreateAnSLADefinition.html)、2026-09-28 に確認）。本家は SLA の計時を、違反までの近さで分けた複数の定期のジョブで更新する（例：「1 時間以内に違反」のものを 10 分ごと）とされる（[SLA 関連のコミュニティの記事](https://www.servicenow.com/community/in-other-news/understanding-my-slas-part-i-scheduled-jobs-and-the-task-sla/ba-p/2272370)、2026-09-28 に検索の結果の抜粋で確認。未検証）。

守るべきことは次のとおり（intent の「守るべき振る舞い」）。

- 1 つの承認の回答は 1 回だけ反映される。
- SLA の計時は障害で失われず、期限は入力から一意に決まる。
- 受け付けたフローのステップとタイマーは失われない（NFR-004）。

## Options

ワークフローの実行の基盤として、次を比べた。

1. **Aurora の上の自前のエンジン。** フローの実行の状態とタイマーを、テナントのレコードと同じ DB の表に持つ
2. **Temporal（自前のクラスタ、または Temporal Cloud）。** 1 つの汎用の「DSL の解釈の」ワークフローで、テナントのフローの定義を解釈する
3. **AWS Step Functions。** テナントのフローを、ステートマシンの定義に変換する

SLA の計時として、次を比べた。

- a. **期限の時刻をカレンダーから計算し、タイマーとして登録する**
- b. 本家のように、定期のジョブで動いている計時をまとめて更新する

## Decision

1 と a を採用する。

### 実行のモデル

- **フローの定義は、版付きの不変の文書にする。** 管理者が公開すると新しい版になる。実行は、開始したときの版に固定する。
- **フローの実行は、DB の行（`flow_run`）と、ステップの状態の行（`flow_step`）で持つ。** 実行の状態は明示の状態機械にする（`running`・`waiting`・`completed`・`failed`・`cancelled`）。
- **タイマーは 1 つの表（`timer`）に持つ。** `(cell, due_at)` の索引の上で、Engine のワーカーが `FOR UPDATE SKIP LOCKED` で期限の来たものを取る。フローの待ち、承認の期限、SLA の警告と違反を、同じ表で扱う。
- **1 つの遷移は、1 つのトランザクションで行う。** 次をまとめてコミットする。
  - 対象のレコードの更新（版の番号の条件付き）
  - ステップの状態の更新
  - 次のタイマーの登録と、消化したタイマーの削除
  - outbox へのイベント
- 途中で落ちたら、トランザクションは巻き戻り、タイマーは再び取られる。コミットの後に落ちたら、タイマーはもうないので、2 回目は起きない。これを「状態の遷移を 1 回だけ行う」の定義にする。
- **外への呼び出し（Webhook、外部の API）は、少なくとも 1 回にする。** outbox から送り、`(flow_run, step, attempt)` から作った冪等のキーを付ける。受け手が冪等でないときの重複は、利用者に明示する（workflow-engine の領域）。
- **レコードの版の番号で、並行の更新を守る。** 承認の回答は、承認のレコードの版の番号を条件に更新する。同じ承認への 2 つの回答は、先にコミットしたほうだけが効き、後のほうは「すでに回答済み」になる。
- **公平性と上限**：テナントごとに、同時に動く実行の数・1 実行のステップの数・フローの入れ子の深さ・1 ステップで更新するレコードの数に上限を置く。値は workflow-engine の領域で決める。

> 2026-09-28 の注記：
> - 冪等のキーの `(flow_run, step, attempt)` の `attempt` は、ノードの実行の回（`iteration`。`for_each` の中の何回目か）の意味である。配送の再試行の回数を含めない。再試行の回数を入れると、同じ依頼の送り直しが別のキーになり、受け手が重複を見分けられないためである（[ADR-0015](0015-flow-execution-and-timers.md)、[workflow-engine.md](../architecture/workflow-engine.md) の 5.5 節）。
> - タイマーの索引は `(cell, due_at)` ではなく `(shard, due_at)` にした。タイマーの表はセルの DB にあるので、セルの列は要らない（[workflow-engine.md](../architecture/workflow-engine.md) の 5.1 節）。
> - 期限の来たタイマーの候補は、テナントをまたいで表を読まない。`engine_scheduler` のロールの関数 `claim_due_timers` が識別子（`timer_id`、`tenant_id`）だけを返し、ワーカーはテナントのコンテキスト（RLS の下）で 1 件ずつ `FOR UPDATE SKIP LOCKED` で取り直す（[ADR-0054](0054-shared-reference-rows-and-cross-tenant-roles.md)）。

### SLA の計時

- **計時の核は、純粋な関数にする。**
  - `addBusinessTime(start, duration, calendar) → deadline`
  - `businessTimeBetween(from, to, calendar) → duration`
  - カレンダーは、営業時間の週の型、IANA のタイムゾーン、祝日の表の版、会社の休日を持つ。現在の時刻・DB を関数の中で読まない。
- **計時の行（`task_sla`）には、開始の時刻、一時停止の累計、カレンダーの版、期限の時刻（UTC）を持つ。** 開始・一時停止・再開・停止・リセットは、タスクのレコードの更新と同じトランザクションで評価し、期限を計算し直して、警告と違反のタイマーを登録し直す。
- **期限は、カレンダーの版を固定して計算する。** 祝日の表が更新されたら、動いている計時の期限を、新しい版で計算し直す（ジョブで行い、変更を履歴に残す）。
- **日本の祝日は、内閣府の CSV から取り込んだ版付きの表にする**（[国民の祝日について](https://www8.cao.go.jp/chosei/shukujitsu/gaiyou.html)、2026-09-28 に確認）。振替休日・国民の休日を含める。会社の休日（年末年始、創立記念日）は、テナントが足す。
- b を採らない理由：定期のジョブでは、警告と違反の時刻の精度が、ジョブの間隔に左右される。NFR-003（期限から p99 60 秒以内の発火）を、動いている計時の数によらず満たすには、期限の時刻をタイマーに登録するほうがよい。表示の残り時間は、画面が期限の時刻から計算する。

### 2・3 を選ばなかった理由

- **2（Temporal）**：耐久性のある実行・タイマー・再試行を、既製の仕組みで得られる。ただし、次の理由で採らない。
  - 遷移の正本が 2 つになる。レコードの更新（Aurora）と、ワークフローの状態（Temporal）を、1 つのトランザクションで書けない。承認の反映とレコードの状態の遷移を 1 回だけにするには、outbox と冪等の処理を両側に作ることになる。
  - テナントのフローはノーコードの DSL で、コードのワークフローの決定性の利点が小さい。1 つの解釈のワークフローで DSL を動かすと、DSL の版の管理を結局自前で持つ。
  - クラスタを自前で運用するか、外部の SaaS にテナントのデータ（フローの入力）を置くことになる。後者はデータの所在（intent の L3）に関わる。
  - Uber の題材も、同じ理由で乗車の状態機械を DB に持った（Uber の ADR-0003）。
- **3（Step Functions）**：テナントのフローごとにステートマシンを作ると、数と更新の管理が重く、遷移ごとの費用がかかる。レコードの更新と同じトランザクションで遷移できない点は、2 と同じである。

## Consequences

- 良くなること：
  - レコード・フロー・タイマー・outbox が同じトランザクションにあり、「1 回だけ」を DB の保証で説明できる。
  - SLA の期限がカレンダーから一意に決まり、性質ベーステストで確かめられる。
  - 部品が増えない（Aurora と SQS だけ）。
- 引き受けるコスト：
  - 耐久性のある実行の仕組み（タイマーの取得、再試行、止まった実行の回収、フローの版の管理）を自前で作り、試験する。障害注入の試験を必須にする（[AGENTS.md](../../AGENTS.md)）。
  - タイマーの表が、セルの Aurora の書き込みの負荷になる。9 時の集中で、取得の遅れが NFR-003 を超えうる。E4 の計測で、取得の間隔と件数、表の分け方を決める。
  - 長く続く実行（数か月の変更）の行が残り続ける。完了した実行の保持と移動を workflow-engine の領域で決める。

## Confirmation

- 障害注入の試験（E4 の必須のチェック）：遷移のトランザクションの途中、コミットの直前と直後、タイマーの取得の後でプロセスを落とす。遷移の欠落と二重の反映が 0 件であること。
- 性質ベーステスト：
  - 任意の開始の時刻・長さ・カレンダーで、`businessTimeBetween(start, addBusinessTime(start, d, cal), cal) = d`。
  - `d1 ≤ d2` なら、`addBusinessTime(start, d1, cal) ≤ addBusinessTime(start, d2, cal)`。
  - 一時停止の区間をどう分割しても、累計の経過時間は変わらない。
  - 任意の同じ承認への並行の回答で、反映は 1 回だけ。
- 本番の突き合わせのジョブ：期限を過ぎて発火していないタイマーと、期限の時刻と発火の時刻の差を計測する（observability の領域）。
