# ADR-0056: 専用のセルは 1 つの顧客のための共有のセルと同じ形のセルにし、同じコード・同じバージョンで動かす。テナントのセル間の移動は、写し・差分・短い停止・ルーターの切り替え・索引の作り直しの手順で行う

詳細は [infrastructure.md](../architecture/infrastructure.md) の 4 節。

## Context

[ADR-0002](0002-tenancy-and-isolation.md) は、大口の企業に専用のセルを出し、専用のセルは DB・キャッシュ・検索の索引・暗号の鍵を他の顧客と共有しない（NFR-009）と決めた。専用のアカウントに置くかは infrastructure の領域に残した。セルの間のテナントの移動の手順を、S1 の 2 つの共有のセルの間で E12 の前に通すとした。

## Options

### 専用のセルの形

1. **共有のセルと同じ形（同じ Terraform のモジュール）を、専用のアカウントに置く**
2. 共有のセルのアカウントの中に、専用の DB と索引だけを足す
3. 顧客の AWS アカウントの中に置く

### 移動の手順

- a. **テナントの行の論理の写し → 差分 → 短い書き込みの停止 → 切り替え → 索引の作り直し**
- b. セル全体の DB のスナップショットから新しいセルを作り、他のテナントを消す
- c. 論理レプリケーション（テナントで絞った出版）で追いつき、切り替える

## Decision

1 と a を採用する。

- 専用のセル：専用のアカウント・VPC・Aurora・Valkey・OpenSearch のドメイン・S3・KMS の鍵・受信のサブドメイン（`<cell>.in.<brand>.<domain>`）。最小の構成から始め、顧客の規模で大きさを決める。デプロイは共有のセルの後の段。
- 移動：写し（`platform` のロールで表ごと、S3 は Batch Operations）→ 差分 → 「移動中」で書き込みを止める（目標 5 分以内）、タイマーの取得から外し、メールを溜める → 最後の差分と件数・ハッシュの突き合わせ → 台帳・KeyValueStore・受信の対応表の切り替え → 新しいセルでタイマーの取得の再開、溜めたメールを流す → 索引の作り直し → 古いセルの行を 7 日の後に消す。
- 番号の数の行、`meta_version`・`acl_version`、タイマー、SLA の計時の行も写す。タイマーの `due_at` は絶対の時刻なのでそのまま。

2 を採らない理由：セルのアカウントの中に、他の顧客と共有する部品（VPC、ECS のサービス、SQS）が残り、「専用」の説明が部品ごとになる。

3 を採らない理由：顧客のアカウントの中のセルを、本システムのデプロイと運用で同じバージョンに保つ仕組み（権限の委任、ネットワーク）が重い。顧客の管理する鍵で得たい性質は、S2 の前に別に検討する。

b を採らない理由：大きな共有のセルのスナップショットの復元と、他のテナントの削除に時間がかかり、1 つのテナントを移すたびにセルを作ることになる。

c を採らない理由：RLS の表ごとの行のフィルターでの論理レプリケーションの出版と、DDL のない JSONB の拡張の扱いの確かめが要る。MVP の移動の回数（年に数回）では、停止の短い a で足りる。停止の時間が問題になれば見直す。

## Consequences

- 良くなること：
  - 専用のセルの分離を、アカウントの単位で説明できる。
  - 移動の手順が、同じ部品（`platform` のロール、索引の作り直し、ルーターの切り替え）の組み合わせで済む。
- 引き受けるコスト：
  - 移動の間、そのテナントは数分書き込めない。業務の少ない時間に行い、事前に告知する。
  - 専用のセルは最小の構成でも固定の費用がかかる（月 約 8,000〜10,000 USD。初期見積もり）。

## Confirmation

- 訓練（E12）：S1 の 2 つの共有のセルの間で、`task` 数百万行のテナントを移し、停止の時間と突き合わせの結果を記録する。
- 移動のジョブの結合テスト：移動の後、古いセルでそのテナントのホスト名が 421、新しいセルで同じ件数・同じハッシュ。
