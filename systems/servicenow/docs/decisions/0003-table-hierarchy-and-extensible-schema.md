# ADR-0003: テーブルはクラスの継承の階層として辞書に持ち、組み込みのクラスは型付きの列、テナントの拡張は JSONB と型付きの索引の表で持つ

## Context

ITSM の記録は、共通の部分と種類ごとの部分を持つ。インシデント・問題・変更・要求の品目・実行のタスクは、どれも「担当のグループ」「担当者」「状態」「期限」「作業メモ」を持つ。担当者の「自分の作業の一覧」は、種類をまたいで 1 つのリストに並ぶ。SLA・承認・割り当ての規則も、共通の部分に対して書きたい。

本家は、テーブルの継承でこれを表す。タスクのテーブルが親で、インシデント・問題・変更が子である。子は親のフィールドと規則を継承する。物理の配置には 3 つの型がある（[Table extension and classes](https://www.servicenow.com/docs/r/platform-administration/table-administration-and-data-management/table-extension-and-classes.html)、2026-09-28 に確認）。

- 階層ごとに 1 つの表（table per hierarchy）：タスクの階層は、親と子のレコードを 1 つの物理の表に持ち、クラスの名前の列で見分ける。
- クラスごとの表（table per class）：子の表のレコードを、同じ ID で親の表に複製する。
- パーティションごとの表（table per partition）：CMDB の基底の CI の表は、上限に達すると物理の区画を足していく。

テナントは、フィールドとテーブルを足す。S1 で 300 テナント、S3 で 3 万テナントを、共有のセルに置く（[ADR-0002](0002-tenancy-and-isolation.md)）。

テナントの拡張の保存の方法として、次を比べる。

- **実の表**：テナントのフィールドを `ALTER TABLE` で列として足し、テーブルを `CREATE TABLE` で作る。
- **JSONB**：拡張の値を 1 つの JSONB の列に入れる。
- **汎用の列（flex columns）**：`value0`〜`valueN` の文字列の列を持つ表に、テナントごとに列の意味を割り当てる。絞り込みには、別の型付きの索引の表を使う。メタデータ駆動の SaaS でよく知られた方式である。

## Options

1. **組み込みのクラスは型付きの列、テナントの拡張は JSONB と型付きの索引の表**
2. **すべてを実の表にする。** テナントのフィールドも列として足し、テナントのテーブルも実の表として作る
3. **すべてを汎用の列にする。** 組み込みのクラスも含め、値を汎用の列に割り当てる
4. **すべてを JSONB にする。** 組み込みのフィールドも JSONB に入れる

## Decision

1 を採用する。

### 論理のモデル：クラスの継承

- **データ辞書に、テーブル（クラス）とフィールドを持つ。** クラスは親を 1 つ持てる（単一の継承）。子は親のフィールド・ACL・レコードのルール・SLA の定義の対象を継承する。
- 組み込みのクラスの階層の例：
  - `task` → `incident`、`problem`、`change`、`request`、`request_item`、`catalog_task`、`problem_task`、`change_task`
  - `ci` → `hardware` → `server` → `linux_server` など（CI のクラスは [ADR-0005](0005-cmdb-identification-and-reconciliation.md)）
- 内部の名前は本システムのものにする。本家のテーブル名・システムのフィールドの名前は写さない（[リポジトリ共通の ADR-0006](../../../../docs/decisions/0006-brand-neutral-identifiers.md)、[ADR-0007](../../../../docs/decisions/0007-no-reuse-of-original-implementation.md)）。
- テナントは、組み込みのクラスを継承した子のクラスと、親を持たない独立のテーブルを作れる。組み込みのクラスのフィールドの型は変えられない。

### 物理の配置

- **タスクの階層は、1 つの物理の表 `task` に置く（階層ごとに 1 つの表）。** 共通のフィールドと、組み込みの子のクラスのフィールドを型付きの列で持つ。`class` の列でクラスを見分ける。種類をまたぐリスト（自分の作業、グループの滞留）と、SLA・承認・割り当ての結合が 1 つの表で済む。PostgreSQL は NULL の列を行の NULL のビットマップで持つので、使わない列の費用は小さい。
- **CI の階層は、1 つの物理の表 `ci` に置く。** 共通の属性（名前、クラス、状態、所有のグループ、場所、識別の値など）は型付きの列にする。CI のクラスは数百に及ぶので、クラスに固有の属性は、組み込みのものも JSONB に入れる（この ADR の例外）。
- ほかの組み込みのテーブル（ユーザー、グループ、ナレッジの記事、カタログの品目など）は、それぞれの型付きの表にする。
- **テナントのフィールド**は、その行の `ext`（JSONB）の列に、フィールドの ID をキーにして入れる。フィールドの名前をキーにしない（名前の変更で移し替えが要らないようにする）。
- **テナントのテーブル**は、共通の物理の表 `custom_record`（`tenant_id`、`table_id`、`id`、共通のシステムの列、`ext`）に置く。組み込みのクラスを継承したテナントのクラスは、親の物理の表（`task` など）に行を置き、固有のフィールドを `ext` に入れる。
- **絞り込み・並べ替えに使うテナントのフィールドは、型付きの索引の表に写す。** 管理者がフィールドに「索引を付ける」を選ぶと、値を `(tenant_id, field_id, value_text | value_number | value_time, record_id)` の表に、レコードの書き込みと同じトランザクションで書く。テーブルごとの索引の数に上限を置く（値は E2 の計測で決める）。索引のないフィールドでの絞り込みは、件数の上限の中で行うか、検索の索引（OpenSearch）で行う。
- 型の検証は、辞書から組み立てた Zod のスキーマで、Record Service が書き込みの前に行う。DB は JSONB の中の型を検証しない。

### メタデータの版

- テナントの辞書（テーブル・フィールド・選択肢・ACL・ルール）は、変更ごとに版の番号を上げる。App と Engine は、版ごとにコンパイルしたスキーマと判定をキャッシュし、版の通知で入れ替える。
- フィールドの削除は、まず非表示にし、値を保持の期間の後に消す（data-dictionary-and-tables の領域）。

### 2・3・4 を選ばなかった理由

- **2（実の表）**：共有のセルで、テナントごとの DDL が要る。3 万テナント × 数十のテーブル・列で、PostgreSQL のカタログが大きくなり、`ALTER TABLE` のロックと、テナントごとのマイグレーションの失敗が運用の負担になる。RLS の共有のスキーマ（[ADR-0002](0002-tenancy-and-isolation.md)）とも合わない。
- **3（汎用の列）**：型の変換、列の数の上限、列の割り当ての管理が自前になる。PostgreSQL 18 には JSONB があり、汎用の列の利点（固定のスキーマで任意の値を持つ）を、JSONB でより簡単に得られる。索引は、1 と同じく型付きの索引の表で持てる。
- **4（すべて JSONB）**：組み込みのフィールド（状態、担当、期限）は、ほぼすべての問い合わせで使う。型付きの列のほうが、索引・統計・制約（参照の整合、NOT NULL）で速く安全である。

## Consequences

- 良くなること：
  - 種類をまたぐリスト・SLA・承認が、1 つの表の上で速く動く。
  - テナントのフィールドとテーブルの追加が、DDL なしに即時に反映される。
  - 組み込みのフィールドは、DB の制約で守れる。
- 引き受けるコスト：
  - テナントのフィールドの値には、DB の制約（参照の整合、型）が効かない。Record Service の検証と、定期の整合の検査で補う。
  - 索引の表の書き込みで、保存の費用が増える。索引の数の上限で抑える。
  - 集計（レポート）で JSONB の値を使うと遅い。reports の領域で、集計の置き場所を決める。
  - `task` の表が大きくなる（S1 で年 7,000 万行程度の見込み）。`tenant_id` を先頭にした索引と、完了したレコードの分け方（パーティション）を data-dictionary-and-tables の領域で決める。

## Confirmation

- lint：Record Service の外で、テナントテーブルの `ext` の列を直接読み書きすることを禁止する。
- 性質ベーステスト：任意の辞書の定義と値の組で、「保存して読み出すと、辞書の型に合った同じ値が返る」。索引の表の値が、`ext` の値と常に一致する。
- 結合テスト：テナントのフィールドの追加・名前の変更・削除が、DDL を発行せずに反映される（マイグレーションの記録が増えない）。
- 計測：E2 で、索引の数・テーブルの行の数を変えたリストの応答時間を測り、NFR-001 を満たす上限を決める。
