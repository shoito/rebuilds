# ADR-0057: DR はセルごとに大阪のウォームスタンバイを持ち、人の判断で切り替える。検索の索引は複製せず切り替えの後に DB から作り直し、失った範囲の受信のメールは S3 の原本から冪等に取り込み直す

詳細は [infrastructure.md](../architecture/infrastructure.md) の 6 節。

## Context

NFR-008 は、リージョンの障害で RPO 1 分以内・RTO 1 時間以内（S2 で 15 分）を求める。[architecture/README.md](../architecture/README.md) の 2 節は、S1 から大阪にウォームスタンバイ（Aurora Global Database）を持つと決めた。データの所在は国内（東京・大阪）に留める（L3）。

Aurora Global Database の計画外のフェイルオーバーは、複製の遅れの分（通常は秒の単位）を失う。switchover は RPO 0（Auth0 の infrastructure.md の 6.3 節で 2026-09-27 に確認した AWS の文書による）。

この題材に固有の事情：

- 検索の索引（OpenSearch）は DB の写しで、作り直せる（[ADR-0044](0044-acl-aware-search-and-index-freshness.md)）。
- 受信のメールは、原本を S3 に置き、`(tenant_id, ses_message_id)` の一意で冪等に取り込む（[ADR-0034](0034-inbound-email-threading-and-sender-trust.md)）。
- SLA の違反の時刻は期限の時刻で、発火の遅れの影響を受けない（[ADR-0021](0021-sla-definitions-and-timers.md)）。

## Options

### 範囲

1. **セルごとのウォームスタンバイ（制御の面と mail-ingress も）**
2. 全体を 1 つの単位で切り替える
3. パイロットライト（DB の二次だけ、タスクを持たない）

### 検索の索引

- a. **複製せず、切り替えの後に DB から作り直す（小さな索引を先に）**
- b. OpenSearch のクラスタ間のレプリケーションで大阪に複製する

### 失った範囲

- x. **受信のメールは S3 の原本から冪等に取り込み直す。ほかは告知と送り直し**
- y. 失った範囲を扱わない（告知だけ）

## Decision

1、a、x を採用する。

- 大阪に、セルごとに Aurora の二次（reader 1 台）、各サービスの最小のタスク、S3 のレプリケーションの先、空の小さな OpenSearch と Valkey、SES の受信・送信の設定、KMS のレプリカを置く。
- 切り替えはインシデントの指揮者が判断し、Ops の責任者が承認する。東京が生きていれば switchover、応答しなければ `--allow-data-loss` の failover。ルーターはセルのオリジンを大阪の ALB に向け、MX を大阪へ切り替える。
- 索引は、`kb`・`catalog` を先に（数分）、`task`・`ci`・`record` を後から（数時間）DB で作り直す。その間、全体の検索は使えず、リスト・フォームは動く。
- 失った範囲：東京の障害の時刻の前 10 分の受信の原本（大阪に複製済みのもの）を Ingest に流し直す。承認の回答は承認者に再回答を依頼し、タイマーは大阪で発火し直す（違反の通知が 2 回届きうることを告知する）。監査のハッシュの鎖の欠けは「DR による欠け」として範囲をプラットフォームの監査に残す。
- `AuroraGlobalDBRPOLag` が 10 秒を超えたら呼び出す。

2 を採らない理由：1 つのセルの障害（AZ を超える部品の障害を含む）で、全セルを切り替えることになる。S3 のセルごとの主のリージョンの形にも移りにくい。

3 を採らない理由：切り替えの後のタスクの起動と台数の拡大に時間がかかり、RTO 1 時間の中の余裕が小さい。9 時の山と重なると、タイマーの遅れが大きい。

b を採らない理由：索引の複製の費用（大阪にも同じ大きさのドメイン）が、作り直しの時間（全体の検索が数時間使えない）の不便に見合わない。ポータルの自己解決に要る `kb`・`catalog` は小さく、数分で作り直せる（未検証。E12 `search-rebuild-drill` で測る）。

y を採らない理由：メールからのチケットは受け付けの主な入口で、原本がすでに大阪にあるのに失うのは避けられる。冪等の仕組みがそのまま使える。

## Consequences

- 良くなること：
  - 失ったメールの多くを、人の手なしに取り戻せる。
  - 索引の複製の費用がない。
- 引き受けるコスト：
  - 切り替えの後の数時間、全体の検索が使えない。
  - S3 のレプリケーションの遅れの分の原本は取り戻せない（RTC を使うかは E12 で費用と決める）。
  - 違反の通知・Webhook が 2 回届きうる。

## Confirmation

- 訓練：staging で四半期に 1 回（計画外のフェイルオーバーと失った範囲の取り込み直し、索引の作り直しの時間）、本番で年 1 回の switchover。
- 本番の監視：大阪の ALB への合成監視、大阪の Terraform の plan の差分、KMS のレプリカ。
- 結合テスト：同じ原本の取り込み直しで、レコードが増えない（`(tenant_id, ses_message_id)` の一意）。
