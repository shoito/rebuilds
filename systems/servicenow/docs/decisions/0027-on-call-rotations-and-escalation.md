# ADR-0027: 当番表は不変の版の層と差し替えで持ち、当番を純粋な関数で求める。呼び出しは専用の状態機械とタイマーで進め、本人の受け付けで止める。経路は差し込み口にし、MVP はメールとプッシュだけにする

詳細は [assignment-and-on-call.md](../architecture/assignment-and-on-call.md) の 5・6 節。

## Context

[intent.md](../intent.md) は、当番表（ローテーション）とエスカレーションを MVP に含め、オンコールの通知を MVP ではメールとアプリのプッシュに限るとした。SMS・音声は、通信の事業者との契約と法令の確認（L8）の後にする。

本家の当番のエスカレーションは、応答がないと次の段へ進み、SMS・音声・メールで受け付けを求め、最後の受け手を持つ（[Escalations in On-Call Scheduling](https://www.servicenow.com/docs/r/it-service-management/on-call-scheduling/escalations-oncall.html)、2026-09-28 に確認。内部のモデルと、段の間の時間の既定の値は未検証。本家の振る舞いで、この決定の前提ではない）。

要ることは次のとおり。

- 夜中の呼び出しが、障害やプロセスの停止で失われず、二重にもならない。
- 「その時刻に誰が当番だったか」を後から説明できる。
- 海外の拠点を含むタイムゾーンと夏時間で、引き継ぎの時刻がずれない。

## Options

### 当番表

1. **層（ローテーション）と差し替え。層は不変の版で、当番は純粋な関数で求める**
2. シフトの行（誰が、いつからいつまで）を並べて持つ

### 呼び出しの実行

- a. **専用の状態機械（`page`）と、`timer` の表の専用の種類**
- b. フローの DSL（通知・待ち・分岐）で組み込みのフローとして書く

### 受け付け

- x. **本人のログインを要る（プッシュのセッション、またはメールのリンクからのログイン）**
- y. メールのリンクのトークンだけで受け付ける

## Decision

1、a、x を採用する。

- 当番表は `layers`（メンバーの順、日・週・n 時間の周期、現地の引き継ぎの時刻、起点、制限の区間）と `effective_from` を持つ版。差し替えは版の外の行。
- `onCall(version, overrides, t)` は、差し替え → 上の層から順、で当番を返す。周期は現地の暦の日・週で数え、夏時間は ADR-0019 と同じ規則にする。
- 版は過去に効かせない。差し替えも過去に作れない。
- 方針は段（受け手、待ちの時間）、繰り返し、最後の受け手、経路を持つ。
- 呼び出しは `page` の行で、`notifying` → `acknowledged` / `resolved` / `exhausted` / `cancelled`。段の進みは `page_escalation` のタイマー（優先度 0）で、版の条件付きで 1 回だけ行う。`(task, group)` ごとに開いている呼び出しは 1 つ。
- 受け付けは本人の確認の後に、`page` の行のロックと版の条件で 1 回だけ反映する。
- 経路は `PagerChannel` の差し込み口にし、MVP は `email` と `push` だけを実装する。

2 を採らない理由：ローテーションの規則が行の列に展開され、規則の変更（メンバーの追加）のたびに先の行を作り直す。「どの規則でその人が当番だったか」を説明しにくい。

b を採らない理由：受け付けの反映（外からの事象で待ちを解く）、繰り返し、当番の解決をフローのノードで表すと、ループの禁止（[ADR-0014](0014-flow-dsl-and-versioning.md)）に合わない。呼び出しは組み込みの 1 つの動きなので、専用の状態機械のほうが決定表で網羅できる。

y を採らない理由：メールの転送で他人が受け付けると、当番の記録と割り当てが誤る。承認と同じく、メールの本人性に頼らない（[ADR-0016](0016-approvals.md)）。

## Consequences

- 良くなること：
  - 当番の解決が純粋な関数で、夏時間を含む性質ベーステストで確かめられる。
  - 呼び出しの段の進みと受け付けが、タイマーと版の条件で 1 回だけ起きる。
  - SMS・音声を後から経路として足せる。
- 引き受けるコスト：
  - 夜中の受け付けにログインが要る。アプリのセッションを長く保つ（`portal-and-ui.md` と `security.md` で決める）。
  - `timer` の種類と優先度を増やす（workflow-engine の表への追加）。
