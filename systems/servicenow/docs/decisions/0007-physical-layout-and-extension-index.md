# ADR-0007: `task`・`ci` を階層ごとに 1 つの表に置き、S1 ではパーティションに分けない。参照のフィールドは必ず索引の表に写す

詳細は [data-dictionary-and-tables.md](../architecture/data-dictionary-and-tables.md) の 4 節。

## Context

[ADR-0003](0003-table-hierarchy-and-extensible-schema.md) は、タスクと CI をそれぞれ 1 つの物理の表に置き、テナントの拡張を `ext`（JSONB）と型付きの索引の表に置くと決めた。`task` が大きくなる（S1 で年 7,000 万行程度）ことに対し、完了したレコードの分け方（パーティション）を data-dictionary-and-tables の領域で決めるとした。

本家のタスクの階層は 1 つの表、CI の基底の表は上限で区画を足す配置である（[Table extension and classes](https://www.servicenow.com/docs/r/platform-administration/table-administration-and-data-management/table-extension-and-classes.html)、2026-09-28 に確認）。

決めることは次のとおり。

- `task` をパーティションに分けるか。分けるなら何で分けるか。
- `ext` の参照のフィールドの整合（参照先の削除）をどう守るか。
- 上限。

## Options

### パーティション

1. **S1 では分けない。進行中のレコードは部分索引で速くする**
2. 完了（`active = false`）かどうかで分ける
3. テナントのハッシュで分ける
4. 作成の年・月で分ける

### `ext` の参照

- a. **参照のフィールドを必ず索引の表に写す**
- b. 索引を付けたものだけ写し、参照先の削除のときは全件を走査する

## Decision

1 と a を採用する。

- `task`・`ci` は S1 でパーティションに分けない。主な問い合わせ（担当・グループの進行中の一覧）は `WHERE active` の部分索引で受ける。監査の履歴と作業メモだけを月ごとに分ける。
- すべての `reference` のフィールドを `ext_index` に写す。参照先の削除のとき、`value_ref` の索引で参照元を探し、`on_delete`（`restrict` / `clear` / `cascade`）に従う。
- 行は `version` を持ち、更新はバージョンの条件付きで行う。
- 上限（S1 の既定）：テナントのフィールド 300、索引を付けたフィールド 20（参照を除く）、参照のフィールド 50、テナントのテーブル 500、`ext` 64 KB、深さ 6。値は E2 の計測で見直す。
- 索引のないテナントのフィールドでの絞り込みは、索引のある条件で 10,000 行以下に絞ったときだけ許す。

2 を採らない理由：再オープンのたびに行が区画をまたいで動く（PostgreSQL では削除と挿入になる）。一覧の多くは進行中のレコードだけを見るので、部分索引で同じ効果を得られる。

3 を採らない理由：1 つのテナントの問い合わせは 1 つの区画に入るが、S1 の問題（表と索引の大きさ）はテナントごとには小さくならない。大きなテナントの偏りは残る。

4 を採らない理由：一覧の問い合わせに作成の時刻の条件がなく、すべての区画を走査する。

b を採らない理由：削除のたびに、テナントの `task` の全件を走査することになる。

## Consequences

- 良くなること：
  - 行の移動がなく、再オープンや状態の変更が安い。
  - 参照の整合を、DB の制約がない `ext` でも、索引で速く守れる。
- 引き受けるコスト：
  - `task` の vacuum と索引の大きさを、E12 の規模で確かめ、S2 の前に分け方を決め直す。
  - 参照のフィールドの分、保存のときの `ext_index` の書き込みが増える。
