# ADR-0026: 割り当ての規則は順序付きで最初に一致した 1 つだけを使い、人が入れた割り当てを上書きしない。担当者はメンバーの行を SKIP LOCKED で取って選ぶ

詳細は [assignment-and-on-call.md](../architecture/assignment-and-on-call.md) の 3・4 節。

## Context

インシデント・要求・変更のタスクを、カテゴリ・CI・場所などから担当のグループへ自動で振り分けたい。グループの中では、順番・負荷・スキルで担当者を決めたい要望がある。

本家は、条件でグループを入れる割り当ての規則と、完全一致の表で値を入れるデータの参照の規則を持ち、保存の前のエンジンとして動かす。2 つの順序は決まっていない（[Precedence between data lookup, assignment, and business rules](https://www.servicenow.com/docs/bundle/xanadu-platform-administration/page/administer/task-table/concept/c_PrecBetweenAssignmentAndBusRules.html)、2026-09-28 に確認）。担当者の選び方は、別の機能（作業の割り当て）で「最後に割り当てた」「最も余裕がある」とスキルの一致を持つ（コミュニティの記事。未検証）。

同じグループへの割り当ては、メールの一斉の受信で並行に起きる。素朴に「最後に割り当てた時刻の古い人」を読んで選ぶと、並行の保存が同じ人を選ぶ。

## Options

### 規則の適用

1. **順序付き、最初に一致した 1 つだけ。人が入れたグループは上書きしない**
2. 一致したすべての規則を順に適用し、後の規則が上書きする
3. 本家と同じく、割り当ての規則とデータの参照の規則を別に持つ

### 並行の選択

- a. **候補のメンバーの行を、選ぶ順に `FOR UPDATE SKIP LOCKED LIMIT 1` で取る**
- b. グループごとの順番の数の行を 1 つ持ち、`FOR UPDATE` で直列にする
- c. 読んで選び、偏りは受け入れる

## Decision

1 と a を採用する。

- 規則は `order`、子のクラスが先、`stable_key` の順に評価し、最初に一致した規則だけを適用する。一致しなければテーブルの既定のグループ。
- 評価は、作成の時と、グループが空で規則のきっかけのフィールドが変わった更新の時だけ。この保存で人・API・メールがグループを入れたら評価しない。
- 規則のグループが無効なら、その規則は一致しなかったものとする。
- 選び方は `none`・`round_robin`・`least_loaded`・`skills`。候補は `active`・`assignable`・不在でない人。`least_loaded` と `skills` は 200 人以下のグループだけ。スキルで 0 人なら選ばない。
- 選んだ人の `group_member.last_assigned_at` を同じトランザクションで更新する。

2 を採らない理由：どの規則が効いたかを説明しにくく、規則の並べ替えで結果が黙って変わる。

3 を採らない理由：完全一致の表は、同じ規則の条件（等しいの AND）で書ける。仕組みを 2 つにすると、順序の決まらない問題（本家の形）を持ち込む。

b を採らない理由：同じグループへの割り当てが、保存の終わりまで直列になる。メールの一斉の受信で、1 グループあたり毎秒数件で詰まる。

c を採らない理由：メールの一斉の受信のような、並行の割り当ての多いときほど偏る。

## Consequences

- 良くなること：
  - 割り当ての結果が、規則の順序から一意に説明できる。
  - 並行の割り当てが、直列にならずに散らばる。
- 引き受けるコスト：
  - 候補の全員がロック中なら、担当者を空のまま（キュー）にする。
  - `least_loaded` の数えの費用のため、大きなグループでは使えない。
