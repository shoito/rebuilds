# ADR-0063: デプロイは制御の面 → カナリアのセル → 共有のセル → 専用のセルの段で行い、振る舞いはフラグで社内 → サブプロダクション → 本番の段で広げる。業務の振る舞いの変更は、顧客が最大 60 日の中で有効にする時期を選べる

詳細は [delivery.md](../architecture/delivery.md) の 5・6 節。

## Context

[ADR-0002](0002-tenancy-and-isolation.md) は、全セルで同じコード・同じバージョンを動かし、振る舞いの変更を AppConfig のフラグでテナント・セルの単位で段階的に広げ、繁忙期を避けたい顧客には振る舞いの変更の切り替えの時期を決めた期間の中で選ばせる（コードのバージョンは選ばせない）と決めた。本番とサブプロダクションは別のテナントである。

日本の企業は、期末・年度の替わり・年末年始に変化を嫌う。タイマーの山は平日 9 時にある（[capacity.md](../architecture/capacity.md)）。

## Options

### デプロイの単位

1. **セルごとの段（カナリアのセルから）**
2. 全セルに同時にデプロイし、フラグだけで段を作る

### リリースの段

- a. **社内 → サブプロダクションの 100%（7 日）→ 本番をカナリアのセルから広げる → 専用のセル**
- b. 本番のテナントの割合だけで広げる

### 顧客の時期の選択

- x. **業務の振る舞いの変更に「選べる変更」の印を付け、最大 60 日の中で有効にする日を選ばせる**
- y. 選ばせない

## Decision

1、a、x を採用する。

- デプロイ：control と mail-ingress → cell-s01（カナリアのセル）→ 60 分の観察 → ほかの共有のセル → 専用のセル。各段で Ops が承認する。平日の 13〜17 時。9 時の山（8:30〜10:30）、月末の最後の 2 営業日、期末、年末年始は修正だけ。
- リリース：社内・監視用のテナント → サブプロダクションの 100%（最低 7 日）→ cell-s01 の 10%・100% → 全共有のセルの 50%・100%（各段 24 時間以上）→ 専用のセル → 2 週間で古いコードとフラグを消す。
- ガード：保存の 422・403 の率、期限を過ぎた未発火の違反、本番の漏れの合成監視、5xx、フォームの p99。差が続けば AppConfig のアラームで自動で切る。
- 選べる変更：業務の画面・流れ・通知の文面が変わるもの。本番の段に入ってから最大 60 日、テナントの管理者が有効にする日を選べる。セキュリティと正しさの修正は選べる変更にしない。

2 を採らない理由：コードの誤り（フラグの外の変更、依存の更新）が全セルに同時に出る。セルに分けた意味（障害の影響を限る）がデプロイで失われる。

b を採らない理由：顧客の開発・検証の環境（サブプロダクション）で先に気づく機会を使えない。

y を採らない理由：期末に画面や承認の流れが変わると、顧客の業務と監査の手順に影響する。ADR-0002 の約束でもある。

## Consequences

- 良くなること：
  - コードの誤りはカナリアのセルで、振る舞いの誤りはサブプロダクションで、先に見つかる。
  - 顧客が繁忙期を避けられる。
- 引き受けるコスト：
  - デプロイが全セルに届くまで時間がかかる（S2 でセルが増えると段を 25% ずつに分ける）。
  - 選べる変更の間、同じ機能の新旧の振る舞いを最大 60 日保つ。

## Confirmation

- デプロイのワークフローが、段の順と観察の時間と承認を強制する。
- フラグの定義の lint：選べる変更の印のフラグに期限（60 日）がある。セキュリティの修正のフラグに選べる変更の印がない。
- ガードで止まったフラグの記録（[delivery.md](../architecture/delivery.md) の 8 節）。
