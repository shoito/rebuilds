# ADR-0012: 行の規則の条件は SQL の述語にコンパイルできる式に限り、読めないフィールドの値は利用者にとって NULL として扱う。判定の材料は `acl_version` をキーにキャッシュする

詳細は [access-control.md](../architecture/access-control.md) の 4.5・6・7 節。

## Context

[intent.md](../intent.md) は、ACL で読めないレコードとフィールドの値も件数も、フォーム・リスト・API・レポート・検索・エクスポート・通知のどこからも漏らさないことを求める（NFR-010、K6）。[AGENTS.md](../../AGENTS.md) は、並べ替えや絞り込みで値を推測できる経路も含めて確かめることを求める。

一覧の件数と集計は、行ごとに判定の関数を呼んで後から絞ると、次の問題がある。

- ページ送りで、読めない行を除いた後のページが短くなり、総数が合わない。
- 総数を出すために全行を読むと、NFR-001（リストの p99 500ms）を満たせない。
- 読めないフィールドで並べ替えると、読める値の並びの位置から読めない値の範囲が分かる。

## Options

### 行の判定の実行の場所

1. **条件を SQL の述語にコンパイルし、問い合わせに押し込む。コンパイルできない条件は規則に書かせない**
2. DB から多めに読み、アプリで判定して絞る
3. 読める行の ID の一覧を事前に計算して持つ

### 読めないフィールドの扱い

- a. **その利用者にとって NULL として扱う。絞り込み・並べ替え・集計もその値で行う**
- b. 読めないフィールドでの絞り込み・並べ替えをエラーにする
- c. 表示だけ隠し、問い合わせは元の値で行う

### キャッシュ

- x. **テナントの `acl_version` を権限の変更と同じトランザクションで上げ、キャッシュのキーに含める**
- y. 時間で切れるキャッシュ

## Decision

1、a、x を採用する。

- 行の規則の条件は、行のフィールド・1 段の参照のたどり・主体の属性・`now` の相対の比較に限る。規則の保存の時にコンパイルし、できなければ 422。
- 読み取りの問い合わせは、行の述語を `WHERE` に入れ、各フィールドを `CASE WHEN フィールドの述語 THEN f END` で読む。件数・集計・グループ化・並べ替え・絞り込みは、この値で行う。
- 16 の出口（access-control.md の 6.2 節）は、同じ `decide` と同じ述語のコンパイラを使う。
- `acl_version` は、規則・ロール・グループの所属・主体の属性の変更で上がる。要求の始めに読み、主体と規則のキャッシュのキーに含める。

2 を採らない理由：件数とページ送りが合わず、大きなテナントで遅い。

3 を採らない理由：主体の数 × 行の数の表になり、レコードの更新のたびに計算し直す。S1 の 100 万人・年 7,000 万行で持てない。

b を採らない理由：エラーになったこと自体は推測に使えないが、画面の保存したフィルター・レポートが、見る人によって壊れる。a なら同じフィルターが見る人ごとに正しい結果を返す。

c を採らない理由：並べ替えの位置と件数から値が推測できる。

y を採らない理由：権限を外した直後に、キャッシュの残りの時間だけ読める。

## Consequences

- 良くなること：
  - 件数・集計・並べ替えからの推測を、1 つの規則（NULL として扱う）で閉じられる。
  - 一覧の判定が DB の索引の上で動く。
- 引き受けるコスト：
  - 条件の表現が本家より狭い（本家はスクリプトで何でも書ける）。2 段以上のたどりが要るときは、辞書に写しのフィールドを作り、レコードのルールで保つ。
  - `CASE` の式で、読めないフィールドでの並べ替えに索引が効かない。画面で選ばせないことで頻度を下げる。
  - 人事の一括の取り込みで `acl_version` が上がると、テナントのキャッシュがまとめて外れる。取り込みの単位で 1 回だけ上げる。

## Confirmation

- 性質ベーステスト PROP-ACL-003（述語と関数の一致）、PROP-ACL-004（推測できない）、PROP-ACL-005（キャッシュの鮮度）。
- 出口ごとの漏れの試験（「漏れの印」を 16 の出口で探す）。
- 計測（E3）：規則を 50 持つテーブルで、リストの p99 が NFR-001 を満たす。
