# ADR-0045: 集計は S1 ではセルの Aurora のレポート用の reader で問い合わせの時に行い、推移のための過去の状態は日次の事実の表（行の写し）に持つ。集計の結果を事前に計算せず、S2 で PostgreSQL と互換の分析のクラスタへ移す

詳細は [reports.md](../architecture/reports.md) の 4・6 節。

## Context

[architecture/README.md](../architecture/README.md) は、レポートの集計の置き場所（Aurora の reader か、分析の専用の置き場所か）を E11 の計測で決め、S2 で分析の専用の置き場所へ移すとした。セルの Aurora は writer 1 台と reader 2 台を持つ（同じ文書の 2 節）。

集計の結果は、見る人ごとに違う（[ADR-0012](0012-acl-enforcement-at-every-exit.md)、[access-control.md](../architecture/access-control.md) の 6.2 節の 5 行）。「未解決の件数の推移」は、今の行からは作れず、過去の状態が要る。

Aurora の reader の遅れは通常 100ms を大きく下回り、書き込みが多いと増える（[Replication with Amazon Aurora](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Replication.html)、2026-09-28 に確認）。本家は、指標の値（スコア）を時点ごとに集める仕組みと、写しを取って問い合わせの時に計算する仕組みを持つ（コミュニティの記事、2026-09-28 に確認。公式の本文は未検証）。

## Options

### 実行の場所（S1）

1. **レポート用の reader（カスタムのエンドポイント）で、問い合わせの時に計算する**
2. writer と同じ既定の reader で計算する
3. 事前の計算の置き場所（集計の結果の表、または列指向の DWH）

### 過去の状態

- a. **日次の事実の表：毎日 0 時の時点の進行中の行の写し**
- b. 集計の結果（グループごとの件数）を毎日記録する
- c. 監査の履歴から、問い合わせの時に過去の状態を組み立てる

## Decision

1 と a を採用する。

- 2 台の reader のうち 1 台をレポート用のカスタムのエンドポイントにし、定期の配信・ダッシュボード・エクスポートをここで動かす。フェイルオーバーの優先度は画面用の reader を先にする。
- 上限：画面 10 秒、定期 120 秒、テナントの同時の実行 5（画面）・2（定期）、セル 40、見積もりの走査 1,000 万行、グループの結果 1,000 行。
- `task_daily_fact` に、テナントのタイムゾーンの 0 時の時点の進行中の `task` の行（状態、優先度、担当、経過の日数など）を写す。13 か月保つ。ACL は今の `task` の行に対して評価する。
- S2 の基準（reader B の CPU の p95 60%、画面の p95 5 秒、1 テナントの `task` 2,000 万行）に当たったら、PostgreSQL と互換の分析のクラスタへ移す（既定案。Redshift は S2 の前に比べる）。

2 を採らない理由：月初の定期の配信とダッシュボードの一斉の読み込みが、画面の読み取り（NFR-001）と検索の確かめ直しを遅くする。

3 を採らない理由：集計の結果は見る人の ACL で変わるので、見る人ごとに持つことになる。列指向の DWH は、ACL の述語のコンパイラ（SQL）を別の方言で持つことになる。S1 の規模は reader で足りる見込み（E11 で計測）。

b を採らない理由：a と同じく、見る人ごとに違う結果を持てない。グループ化の軸も事前に決め打ちになる。

c を採らない理由：監査の履歴は保存ごとの JSON の差分で（[ADR-0009](0009-record-audit-history-and-journal.md)）、13 か月の推移を組み立てるには、全レコードの履歴の再生が要る。

## Consequences

- 良くなること：
  - 1 つの述語のコンパイラで、リスト・レポート・推移が同じ ACL で動く。
  - 重い集計が画面を遅くしない。
- 引き受けるコスト：
  - reader B の分の費用。S1 の既定の構成（reader 2 台）の中なので、足さない。
  - 日次の事実の表の書き込み（全体で 1 日 約 50 万行。初期見積もり）。
  - 事実の表は日の単位で、時の単位の推移は出せない。

## Confirmation

- 計測（E11・E12）：月初の 9 時の負荷で、画面のレポートの p95 と reader B の CPU。
- 性質ベーステスト PROP-RPT-002（集計と掘り下げの一致）。
- lint：レポートの実行のモジュールが writer のエンドポイントに接続しないこと。
