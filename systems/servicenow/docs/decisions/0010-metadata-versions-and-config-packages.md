# ADR-0010: メタデータの変更はテナントの版の番号を上げる 1 つのトランザクションで行う。設定の移送は、安定したキーと元の版のハッシュを持つパッケージで行う

詳細は [data-dictionary-and-tables.md](../architecture/data-dictionary-and-tables.md) の 9・10 節。

## Context

[ADR-0003](0003-table-hierarchy-and-extensible-schema.md) は、テナントの辞書を版付きにし、版ごとにコンパイルした判定をキャッシュすると決めた。[ADR-0002](0002-tenancy-and-isolation.md) は、本番とサブプロダクションを別のテナントにし、同じ顧客のテナントを同じセルに置き、設定の移送（開発 → 本番）を data-dictionary-and-tables の領域で決めるとした。

本家の更新のセットは、更新の記録の名前と更新の時刻で衝突を見つけ、一部の表は一意の列の組で同じレコードを見つけ、移送のときに参照の ID を書き換える（[Update set collision resolution](https://www.servicenow.com/docs/r/application-development/system-update-sets/update-set-collisions.html)、2026-09-28 に確認）。取り込んだ更新のセットはプレビューで問題（衝突、欠けた依存など）を見つけ、取り込むか飛ばすかを決めてからコミットする（[Preview a remote update set](https://www.servicenow.com/docs/r/application-development/system-update-sets/t_PreviewARemoteUpdateSet.html)、2026-09-28 に確認）。本家の更新のセットの形式との互換は目標にしない（[intent.md](../intent.md) の Non-goals）。

## Options

### 版

1. **テナントに 1 つの `meta_version` を持ち、メタデータの変更ごとに同じトランザクションで上げる**
2. オブジェクトごとの版だけを持ち、キャッシュは時間で切る

### 移送

- a. **変更したオブジェクトの内容と元の版のハッシュを持つパッケージ。移送先でも同じ ID を使う。衝突は内容のハッシュで判定する。適用は 1 つのトランザクション**
- b. 本家に近い形：更新の記録の列を順に再生し、名前と時刻で衝突を見つけ、参照の ID を書き換える
- c. テナントの設定の全体を写す（差分でなく、丸ごと置き換える）

## Decision

1 と a を採用する。

- メタデータの変更のトランザクションで、オブジェクトの行、`tenant_meta.meta_version += 1`、`meta_change`、outbox を書く。要求の始めに `meta_version` を読み、手元の版が古ければ読み直す。キャッシュのキーは `(tenant_id, meta_version)`。
- パッケージは、「作業のパッケージ」を開いている間の変更を記録し、閉じるときに固める。項目は `stable_key`、`id`、操作、`base_hash`、内容、`content_hash`、依存を持つ。署名する。
- 移送先では DT-PKG-001 で項目ごとに判定し、衝突は人が決める。適用は 1 つのトランザクションで、`meta_version` を 1 回だけ上げる。1 パッケージ 5,000 項目まで。
- 取り消しは、適用の前の内容から作った逆のパッケージで行う。
- 移すのはメタデータだけ。レコード・利用者・秘密の値は移さない。
- 本番への適用は、既定で別の人の承認を要る。

2 を採らない理由：キャッシュの切れる前の要求が、古い検証・ACL で保存しうる。ACL の変更の直後に古い判定で読める経路ができる（NFR-010）。

b を採らない理由：

- 時刻の比較は、時計のずれと、同じ内容の二重の適用で誤った衝突を出す。
- 参照の書き換えは、書き換えの漏れで壊れた参照を作る。移送先でも同じ ID を使えば、書き換えが要らない（主キーは `(tenant_id, id)` なので衝突しない）。
- 記録の列の再生の途中で失敗すると、中途半端な設定が残る。

c を採らない理由：本番で先に直した設定（緊急の対応）を、黙って上書きする。

## Consequences

- 良くなること：
  - メタデータの変更の直後から、全プロセスが新しい版で判定する。
  - パッケージの適用は全部か無しかで、二重の適用は何もしない。
- 引き受けるコスト：
  - 同じテナントのメタデータの変更は直列になる。大きなパッケージの適用の間、そのテナントの他の設定の変更を待たせる（5,000 項目の上限で抑える）。
  - 本番で手で作ったオブジェクトと、開発で作ったオブジェクトの `id` が違うと、毎回衝突になる。画面で「移送先のオブジェクトをパッケージの ID に合わせる」操作（衝突の解決の 1 つ）を用意する。

## Confirmation

- 性質ベーステスト PROP-PKG-001（冪等）、PROP-PKG-002（取り消しで戻る）、PROP-PKG-003（原子性）。
- 決定表 DT-PKG-001。
- 結合テスト：メタデータの変更のコミットの直後に別のプロセスで始めた保存が、新しい版の検証を使う。
