# Runbook: デプロイとロールバック

- Owner: Ops
- 対応するアラート: app の blue/green の自動のロールバック、デプロイの後の SLO のバーンレート、フラグのガードによる自動の停止、メタデータのコンパイルの検査の失敗（[observability.md](../architecture/observability.md) の 7.2 節）
- 最終確認日: 2026-09-28

流れは [delivery.md](../architecture/delivery.md)、セルの段は [ADR-0063](../decisions/0063-flags-and-staged-release-per-cell.md)、メタデータの互換の検査は [ADR-0064](../decisions/0064-migrations-and-metadata-compatibility-check.md)、CI/CD と Terraform の構成は [infrastructure.md](../architecture/infrastructure.md) の 7 節にある。

## 症状

次のときに使う。

- 本番（prod）へデプロイするとき（アプリ、Terraform、セルの追加）
- デプロイの後に、可用性、保存の 422・403 の率、タイマーの遅れ、フォームの時間が悪化したとき
- 本番の漏れの合成監視が、デプロイの直後に検出したとき
- フラグのガードが、フラグを自動で切ったとき
- メタデータのコンパイルの検査が、セルのデプロイを止めたとき

## 影響

- 通常のデプロイ：利用者への影響はない。
- 失敗したデプロイ：セルの可用性（99.95%。30 日のエラーバジェット 約 21.6 分）を消費する。**判定・遷移・計時の誤りは、5xx にならずに現れる**（保存の 422・403 の増加、期限を過ぎた未発火の違反、読めない値の表示）。
- ACL の出口の誤りは、読めない値の漏れ（NFR-010）になる。SEV1 として扱う（[incident-response.md](incident-response.md) の「ACL の漏れの疑い」）。

## 確認

### デプロイの前

1. 対象のコミットが staging の 2 つのセルへデプロイ済みで、E2E、スモーク、k6 の短い負荷、メタデータのコンパイルの検査が通っている。夜間の CI（性質・障害注入・漏れの試験の全体）が直近で通っている。
2. デプロイできる時間帯である（平日 13〜17 時）。**平日 8:30〜10:30（9 時の山）、月末の最後の 2 営業日、期末（3 月 25 日〜4 月 5 日、9 月 25 日〜10 月 5 日）、年末年始は、修正だけ。** 専用のセルの顧客が知らせた繁忙の時間帯でない。
3. マイグレーションが expand だけか。contract を含むなら、1 つ前のリリースで参照をやめていること、PITR の直近の復元できる時刻が 5 分以内であることを確かめる。
4. フローの意味を変える変更なら、`engine_schema` を上げていること（古いバージョンの実行を新しい意味で進めない）。
5. SLO のダッシュボードで、対象のセルのエラーバジェットが残っている。
6. 進行中のインシデント、タイマーの遅れの警告、`AuroraGlobalDBRPOLag` の超過がない。
7. `security:sensitive` の PR を含むなら、2 人の承認がそろっている（GitHub の記録で確かめる）。

### デプロイの後（各セル、入れ替えが終わってから 60 分。カナリアのセル cell-s01 は必ず 60 分）

| 見るもの | 正常 | 異常 |
| --- | --- | --- |
| 可用性（エッジ、セル別） | デプロイの前と同じ | 5xx が 0.1% を超える |
| 保存の 422・403 の率 | デプロイの前と同じ | 2 倍以上 |
| フォームのサーバーの p99、リストの p99 | 300ms・500ms 以内 | 超える |
| タイマーの遅れ（優先度 0 の p99）、期限を過ぎた未発火の違反 | 60 秒以内、0 | 超える、1 件以上 |
| 止まった実行の回収 | 0 | 1 件以上 |
| 本番の漏れの合成監視 | 検出 0 | 1 件でも（直ちに SEV1） |
| 合成監視（ログイン・フォーム・保存、ポータルの申請、API、メール、SLA、検索） | 成功 | 2 回続けて失敗 |
| ACL の条件の評価の失敗 | デプロイの前と同じ | 急増 |

## 対処

### 通常のデプロイ（アプリ）

各セルで、次の順に行う（セルの順は control・mail-ingress → cell-s01 → ほかの共有のセル → 専用のセル）。

1. GitHub の `prod-<cell>` の Environment で、Ops が承認する（作成者と別の人）。
2. **メタデータのコンパイルの検査のタスク**が動く。失敗なら、ワークフローが止まる（下の「検査で止まったとき」）。
3. マイグレーションのタスク（`migrator`）の成功を確かめる。失敗したら、アプリのデプロイは自動で止まる。
4. relay、indexer、notifier、notifier-egress、ingest がローリングで入れ替わる。
5. engine がローリングで入れ替わる。平日 8:50 の予定の台数の拡大と重ならないこと（時間帯の制限で重ならないはず）。
6. app：blue/green のカナリア（要求の 10%）。5xx、保存の 422・403、タイマーの遅れ、漏れの合成監視のアラームが鳴らなければ 100% に切り替わる。
7. 「デプロイの後」の表を 60 分（カナリアのセル）または 15 分（それ以降のセル）見てから、次のセルへ進む。

### Terraform（`cell/*`、`global/edge`、KMS・IAM・WAF）

1. plan の差分を 2 人（作成者と別）で読む。KMS・IAM・WAF・ルーターの関数は `security:sensitive`。
2. セルのモジュールの変更は、cell-s01 から 1 セルずつ apply する。
3. ルーターの関数の変更は、まず staging の配信で、未知のホスト名が 404、既知のホスト名が正しいセルへ行くことを確かめる。本番の反映の後、ルーターの 404・421 の件数を 15 分見る。
4. WAF の新しい Block のルールは、まず Count で 24 時間出し、誤検知を見てから Block にする。

### 新しいセルの追加

1. `infra/cells.yaml` に 1 行を足す PR（Ops の承認）。
2. `org/` でアカウントを作り、`cell/<id>/{ap-northeast-1,ap-northeast-3}` を apply する。
3. 制御の面にセルを登録し、ルーターの配信にオリジンを足す（テナントはまだ割り当てない）。
4. 監視用のテナントを作り、合成監視を 24 時間通してから、新しいテナントの割り当ての先に加える。

### 検査で止まったとき

1. 検査の結果（テナントの ID、オブジェクトの ID、エラーのコード）を見る。値は出ていない。
2. コードの誤り（新しいコードが正しいメタデータを読めない）なら、デプロイを止めたまま修正の PR を出す。
3. 意図した非互換（古いメタデータの形を新しいコードが受けない）なら、移行のジョブをリリースに含めるか、古い形を読む互換のコードを残す。Dev のテックリードが判断する。
4. **テナントのメタデータを手で書き換えて検査を通さない。**

### 悪化したとき

1. **フラグで戻す。** 新しい振る舞いのフラグが原因なら、AppConfig で切る（セル・テナントの単位で切れる）。ガードで自動で切れていれば、切れていることを確かめる。
2. **フラグで戻せないとき、アプリを戻す。** そのセルで、1 つ前のイメージの digest で再デプロイする（「前のリリースを再デプロイ」のワークフロー。セルを選ぶ）。app の blue/green の途中なら、ロールバックのボタンで旧い側に戻す。まだデプロイしていないセルへは進めない。
3. **マイグレーションは戻さない。** 前へ進める修正を書く。
4. **engine の誤り（遷移・タイマー）で、誤った状態の遷移が起きていたら**：戻した後、誤った遷移の範囲を監査の履歴（`record_change` の `actor_kind = flow`、`channel`、時刻の範囲）で特定する。直すのは、Dev のテックリードの判断で、修正のジョブ（Record Service を通す、`channel = system`、理由付き）で行う。**DB を直接書き換えない**（監査の履歴が欠ける）。
5. **ACL・出口の誤りで値が漏れた疑い**：戻したうえで、[incident-response.md](incident-response.md) の「ACL の漏れの疑い」に移る。
6. **SLA の計時の誤り（期限の誤り）**：戻した後、誤った期限の計時の行を、計算し直しのジョブ（[sla-and-calendars.md](../architecture/sla-and-calendars.md) の 8 節）で直す。違反の事実は取り消さない（`breach_disputed` が残る）。
7. 戻しても直らなければ、インシデントを宣言する（[incident-response.md](incident-response.md)）。

## エスカレーション

- 戻しても 15 分以内に SLO が回復しない → インシデントを宣言する。
- 本番の漏れの合成監視の検出、テナントの分離の疑い → SEV1。セキュリティの担当と Dev のテックリードを呼ぶ。
- 誤った状態の遷移・承認の反映が起きた → SEV2。Dev のテックリードと QA を呼ぶ（修正の範囲と、監査の担当への説明）。
- マイグレーションが途中で止まり状態がわからない → Dev のテックリードを呼ぶ。
- 検査で止まった原因が特定のテナントのメタデータの壊れ → テナントの管理者への連絡を PM と決める。

## 事後

- 調査結果を Intent の Issue として起票する（Maintain 段）。
- デプロイの失敗を CI で防げたなら、CI の検査（決定表の行、性質、障害の点、漏れの試験の出口、メタデータの検査の対象）を足す提案を Dev と QA に出す。
- この手順で足りなかったことを、ここに反映する。
