# Runbook: 災害復旧（AZ の障害、リージョンの障害、失った範囲の取り込み直し、訓練）

- Owner: Ops
- 対応するアラート: AZ の障害（複数のサービスで 1 つの AZ のターゲットが不健全）、大阪からの合成監視の連続失敗、`AuroraGlobalDBRPOLag` の超過、大阪の待機の構成の異常、訓練（staging は四半期に 1 回、本番の switchover は年 1 回）
- 最終確認日: 2026-09-28

構成と目標は [infrastructure.md](../architecture/infrastructure.md) の 6 節、方針は [ADR-0057](../decisions/0057-disaster-recovery-per-cell.md) にある。目標は NFR-007（AZ：RPO 0、RTO 5 分）と NFR-008（リージョン：RPO 1 分、RTO 1 時間）。**DR はセルごとに行う。** 制御の面と mail-ingress も同じ形で切り替える。

## 症状

| 場面 | 見え方 |
| --- | --- |
| A. AZ の障害 | 1 つの AZ のタスク・Aurora のインスタンス・Valkey のノード・OpenSearch のノードが不健全。AWS Health Dashboard に東京の 1 つの AZ のイベント |
| B. リージョンの障害 | 東京のセルが応答しない。大阪からの合成監視がすべて失敗。CloudFront の 502・504 の増加。SES の受信が止まる（顧客のメールサーバーは再送を続ける） |
| C. 複製の遅延 | `AuroraGlobalDBRPOLag` が 10 秒を超え続ける（東京は正常） |
| D. 論理的な破損 | 誤ったマイグレーション・操作・修正のジョブで、レコード・メタデータが消えた・壊れた |
| E. 訓練 | 計画した日時 |

## 影響

- A：数十秒、保存が 503。タイマーの発火が止まり、復旧の後に期限の古い順に発火する。SLA の違反の時刻は期限の時刻なので正しい。コミット済みのデータは失わない。
- B：切り替えまで（目標 1 時間以内）、そのセルの全テナントの画面・API・ポータル・メールの受け付けが止まる。**タイマー（SLA の違反の通知、承認の期限、当番の呼び出し）も止まる。** 切り替えの後、複製の遅れの分の書き込みを失う（下の表）。全体の検索は、索引の作り直しまで数時間使えない。
- C：この状態でリージョンの障害が起きると、失う範囲が広がる。

| 失った書き込み | 切り替えの後に起きること | 回復 |
| --- | --- | --- |
| 受信のメールから作ったレコード・追記 | ない | 「失った範囲の取り込み直し」の 1（冪等） |
| 画面・API の作成・更新 | 失う | テナントへ告知（時刻の範囲）。API の連携は送り直せる |
| 承認の回答 | 回答の前に戻る | 承認者へ再回答の依頼 |
| タイマーの発火（SLA の警告・違反、フローのステップ、当番の呼び出しの段） | 発火の前に戻る | 大阪で発火し直す。通知が 2 回届きうる（告知に含める） |
| 番号の取得 | 数の行が戻る | 番号は一意の索引で守られる。失った範囲の番号が再び使われうる（失ったレコードの番号を、テナントが控えていたら食い違う。告知に含める） |
| 監査のハッシュの鎖 | その日の鎖と大阪の DB が合わない | 「DR による欠け」の注記 |

## 確認

1. AWS Health Dashboard と Grafana の AZ ごとの内訳で、1 つの AZ か、リージョン全体かを見分ける。1 つのセルだけか、全セルかも見る。
2. Aurora のクラスタのイベントで、フェイルオーバーの有無と、今の writer の AZ を確かめる。
3. リージョンの障害を疑うときは、大阪の合成監視と、別の回線からの到達性の両方で確かめる。
4. **`AuroraGlobalDBRPOLag` の直近の値と、東京が応答しなくなった時刻を、セルごとに記録する。** 失った範囲の目安になる。
5. S3 のレプリケーションの遅れ（`ReplicationLatency`）を記録する。取り込み直せるメールの原本の範囲の目安になる。

## 対処

### A. AZ の障害

基本は自動で回復する。

1. インシデントを宣言する（SEV2 から。[incident-response.md](incident-response.md)）。
2. Aurora が別の AZ（reader A を優先）へ自動でフェイルオーバーしたことを確かめる。5 分たっても writer がなければ、手動でフェイルオーバーする。
3. ECS が残る 2 AZ でタスクを起動しているか確かめる。app と engine が足りなければ、最小のタスク数を上げる。
4. 復旧の後、タイマーの遅れ（優先度 0 の p99）と期限を過ぎた未発火の違反が 0 に戻るのを見る（[incident-response.md](incident-response.md) の「タイマーの遅れ」）。
5. AZ が回復したら、台数を平常に戻す。

### B. リージョンの障害（東京 → 大阪）

**切り替えの判断は、インシデントの指揮者（IC）が行い、Ops の責任者が承認する。** AWS の見込みで 30 分以内に回復しそうなら、待つことも選ぶ（RTO 1 時間の内に収まるなら、データを失わない待機のほうがよい）。ただし、タイマーが止まっているので、SLA の違反の通知と当番の呼び出しが遅れていることを、待つ判断の材料に入れる。

1. SEV1 を宣言し、テナントへ告知する（ステータスのページ `status.<brand>.<domain>`。本システムの外）。
2. **東京への書き込みを止める。** 東京のセルに届くなら、ops フラグ `ops.read_only_mode` をセルに有効にする（保存を 503 にし、engine のタイマーの取得を止める）。
3. **失った範囲を記録する**（「確認」の 4・5）。
4. **制御の面と mail-ingress を先に切り替える**（テナントの台帳が要る）。
   1. 制御の面の Aurora Global Database を大阪へ（switchover か `--allow-data-loss` の failover）。
   2. mail-ingress：Route 53 の `in.<brand>.<domain>` の MX を大阪の SES の受信へ（TTL 300 秒）。`mail-router` を大阪で起動する。
5. **セルごとに切り替える**（「DR：セルを大阪で有効化」のワークフロー。大阪で実行できるもの）。
   1. Aurora Global Database の大阪の二次を昇格させる。東京の writer が生きていれば switchover（RPO 0）、応答しなければ `aws rds failover-global-cluster --allow-data-loss`（大阪のリージョンで実行）。
   2. 大阪の Aurora に reader を 2 台足す（reader B はレポート用）。
   3. ECS の台数を東京の平常へ上げる（engine は 9 時の山の近くなら 6 タスク）。
   4. OpenSearch の大阪のドメインのノードを増やし、索引の作り直しのジョブを始める（`kb`・`catalog` を先に）。
   5. SES の送信を大阪のセルのアカウントへ（送信の設定、DKIM）。
   6. `global/edge` の変数 `active_region`（そのセル）を大阪に替えて apply し、ルーターのオリジンを大阪の ALB に向ける。
   7. `ops.read_only_mode` を切る。engine のタイマーの取得を始める（期限の古い順、優先度 0 から）。
6. 合成監視（大阪）で、ログイン・フォーム・保存、ポータル、API、メール、SLA が成功することを確かめる。
7. 「失った範囲の取り込み直し」を行う。
8. テナントへ、失った時刻の範囲と、再回答の要る承認、2 回届きうる通知、検索が戻るまでの見込みを告知する。

### 失った範囲の取り込み直し

1. **受信のメール**：失った範囲（東京が応答しなくなった時刻の前 10 分から）の、大阪の S3 に複製済みの原本を一覧にし、Ingest の再処理のキューへ流す（「DR：受信の再処理」のジョブ。セルごと）。`(tenant_id, ses_message_id)` の一意で、大阪にすでにあるものは飛ばされる。件数（再処理・飛ばし・失敗）を記録する。
2. **承認**：失った範囲に回答の記録（監査の履歴の東京の最後の日次の写しと比べられないので、承認の依頼の通知の送信の記録 `email_outbound` と、承認者の画面の操作の報告から）がありうる承認に、「もう一度回答してください」の通知を送る。承認の行は版で守られるので、二重には反映されない。
3. **監査のハッシュの鎖**：切り替えの日の鎖の検証に、失った範囲（時刻）を「DR による欠け」としてプラットフォームの監査に残す。
4. **Webhook の受け手**：同じ事象が 2 回届きうることは、配達の ID で見分けられる（同じ事象から同じ ID）。告知に含める。

### C. 複製の遅延

1. 東京の writer の書き込みの量（9 時の山、CMDB の一括の取り込み、`bulk_job`）と、大阪の二次の状態を確かめる。
2. 一括の処理が原因なら、そのテナントの取り込みの同時の実行を下げる（[api-and-integrations.md](../architecture/api-and-integrations.md) の 7 節、[cmdb-and-reconciliation.md](../architecture/cmdb-and-reconciliation.md)）。
3. 大阪の二次のインスタンスが小さすぎるなら、東京の reader と同じ型に上げる。
4. 30 分以上続くなら SEV3 のインシデントにし、その間にリージョンの障害が起きたときの失う範囲を IC に知らせる。

### D. 論理的な破損

1. 破損の範囲（テナント、表、時刻）を監査の履歴（`record_change`、`meta_change`）で特定する。
2. **メタデータ**（辞書・ACL・フロー）なら、`meta_change` から前の版の内容で逆のパッケージを作って適用する（[data-dictionary-and-tables.md](../architecture/data-dictionary-and-tables.md) の 10.5 節）。ACL の誤りで管理者も読めなくなったときは `break_glass` の管理者で行う。
3. **レコード**なら、監査の履歴の `changes` と削除のときの `snapshot` から、修正のジョブ（Record Service を通す、`channel = system`、理由付き）で戻す。
4. 監査の履歴で戻せない範囲（監査から外したテナントのテーブル）は、Aurora の PITR で隔離した VPC に新しいクラスタを復元し、そのテナントの行だけを取り出して、修正のジョブで戻す。**本番のクラスタを PITR で上書きしない**（他のテナントの書き込みを失う）。
5. 戻した操作は、すべて監査の履歴とプラットフォームの監査に残る。

### E. 訓練

| 訓練 | 頻度 | 場所 | 確かめること |
| --- | --- | --- | --- |
| 計画外のフェイルオーバー（`--allow-data-loss`）と失った範囲の取り込み直し | 四半期 | staging | RTO、RPO の実測、メールの再処理の件数、索引の作り直しの時間 |
| switchover（東京 → 大阪 → 東京） | 年 1 回 | 本番（1 つのセル。業務の少ない休日） | RPO 0、ルーターと MX の切り替え、タイマーの再開 |
| AZ の障害（Aurora のフェイルオーバー、ECS の 1 AZ の停止）を 9 時の山の負荷の中で | 四半期 | staging | タイマーの遅れ、遷移の欠落・二重 0 |
| セルの移動 | E12 の前、その後は年 1 回 | staging（本番は必要なときだけ） | [infrastructure.md](../architecture/infrastructure.md) の 4.2 節 |

## エスカレーション

- リージョンの切り替えの判断 → Ops の責任者（承認）。PM（テナントへの告知の文面）。
- 失った範囲の承認に、変更の承認（J-SOX の証跡）が含まれる → QA と PM（顧客の監査の担当への説明）。
- 論理的な破損が複数のテナントに及ぶ、原因がわからない → Dev のテックリード。セキュリティの疑いがあればセキュリティの担当。
- 大阪のクォータ（Fargate、OpenSearch、SES）が足りない → AWS のサポートに緊急で引き上げを依頼する。

## 事後

- 調査結果を Intent の Issue として起票する（Maintain 段）。
- 訓練と本番の切り替えの実測（RTO、RPO、索引の作り直し、メールの再処理）を quality の指標に残す。
- この手順で足りなかったことを、ここに反映する。
