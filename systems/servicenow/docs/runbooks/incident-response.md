# Runbook: インシデント対応

- Owner: Ops
- 対応するアラート: すべての呼び出し（page）のアラート（[observability.md](../architecture/observability.md) の 7.2 節）。個別の場面は「この題材に固有の場面」の節
- 最終確認日: 2026-09-28

個別の手順（[deploy-and-rollback.md](deploy-and-rollback.md)、[disaster-recovery.md](disaster-recovery.md)）の上に立つ、共通の進め方と、この題材に固有の場面（タイマーの遅れ、ACL の漏れの疑い、テナントの分離の破れの疑い、メールのループ、CMDB の誤った統合）。各 Epic で個別の runbook（`timer-lag.md`、`mail-loop-detected.md`、`cmdb-wrong-merge.md` など）ができたら、場面をそちらへ移す（[ADR-0060](../decisions/0060-alerts-and-runbook-mapping.md)）。進め方の骨格は他の題材（Slack・Auth0 の incident-response.md）と同じ。

## 症状

次のどれかのときに、インシデントを宣言する。迷ったら宣言し、後で重さを下げる。

- 呼び出しのアラートが鳴った
- テナントや社内から、障害・見えるはずのないデータ・SLA の通知の遅れ・メールの洪水の報告が来た
- 正しさの監視（承認なしの実施、監査の鎖、漏れの合成監視）が 0 でない値を出した

## 影響

### 重さ（severity）

| 重さ | 基準 | 例 | 最初の応答 | 告知 |
| --- | --- | --- | --- | --- |
| SEV1 | セルの全体が使えない。他のテナントのデータが見えた。ACL で読めない値が漏れた（確定、または合成監視の検出）。監査の証跡の改ざん | リージョンの障害、テナントの分離の破れ、出口の漏れ | 5 分以内 | 30 分以内にテナントへ。以後 30 分ごと |
| SEV2 | 一部の機能が使えない、または約束（SLA の計時、承認の 1 回）が破れうる | タイマーの遅れ（優先度 0 の p99 60 秒超）、承認なしの実施の検出、監査の鎖の食い違い、メールの取り込みの停止、AZ の障害 | 15 分以内 | 1 時間以内に影響のあるテナントへ |
| SEV3 | 劣化しているが回避できる。1 テナントに閉じる | メールのループ（1 テナント）、CMDB の誤った統合、索引の遅れ、止まった実行の回収 | 営業時間内（夜間は翌朝） | 影響のあるテナントへ必要なら |
| SEV4 | テナントへの影響がない | 1 つのジョブの失敗の増加 | 営業時間内 | なし |

**テナントの分離・ACL の漏れ・監査の改ざん・承認の偽りに関わるものは、範囲が 1 件でも SEV2 以上にする**（漏れが確定したら SEV1）。

## 確認

1. どのアラート・報告から始まったかを記録する。
2. 影響の範囲を見る：全体か、特定のセル・テナント・テーブル・出口・AZ か。本番のテナントか、サブプロダクションのテナントか。
3. 直近の変更を見る：デプロイ（セルの段のどこまで）、フラグ、マイグレーション、Terraform、テナントの設定の変更（ACL の規則、フロー、受信の規則、識別の規則）、パッケージの適用。
4. 正しさの監視の値を見る（[observability.md](../architecture/observability.md) の 5 節）。
5. セキュリティへの影響を見る：漏れの合成監視、ログの走査、GuardDuty、運用者の権限の使用、ACL の判定のログ。

## 対処

### 役割

| 役割 | 担う人 | 責任 |
| --- | --- | --- |
| 指揮者（IC） | 最初に応答したオンコール。SEV1 では Ops の責任者に引き継いでよい | 重さ、方針、大きな判断（リージョンの切り替え、テナントの機能の停止、フラグの全体の停止） |
| 作業者 | オンコールの Ops、呼ばれた Dev | 調査と復旧 |
| セキュリティの担当 | セキュリティの当番 | 漏れ・分離・改ざんの判断、証拠の保全、法務への連絡 |
| 連絡係 | IC が指名する（PM が望ましい） | テナント、社内、AWS への連絡 |
| 記録係 | IC が指名する | 時刻付きの記録 |

SEV1 では、指揮者は手を動かさない。

### 進め方

1. **宣言する。** インシデント用の場を、このシステムと別の道具に作る（本システムが止まっていても使える場所。本システムの ITSM でインシデントを管理しない）。
2. **被害を止めることを、原因の特定より優先する。** 順番：
   - 直近の変更のフラグを切る（セル・テナントの単位で切れる）
   - 直近のデプロイを戻す（[deploy-and-rollback.md](deploy-and-rollback.md)。まだのセルへ進めない）
   - 問題のテナントの機能を止める（フローの無効化、受信の規則の停止、取り込み元の停止、レート制限の一時の引き下げ）
   - 容量を増やす（engine・app・ingest の台数）
3. **証拠を消さない。** 監査の履歴、ACL の判定のログ、アプリのログ、テナントの監査ログ、プラットフォームの監査は、調査と説明の材料である。**レコードの値・メールの本文・秘密を、チケット・チャット・この記録に写さない。** テナント・テーブル・レコードの ID と件数だけを書く。
4. **告知する。** 何が起きているか、どの操作に影響するか（画面、ポータル、メールの受け付け、SLA の通知、承認）、データは失われたか、次の更新はいつか。原因の推測は書かない。
5. **収束を確かめる。** SLO の指標と正しさの監視が戻り、合成監視が成功し、15 分たってから解決とする。セキュリティの調査（範囲の特定、報告）が残るときは、インシデントを閉じず、SEV を下げて続ける。

### この題材に固有の場面

#### タイマーの遅れ

アラート：タイマーの遅れ（優先度 0 の p99 が 60 秒を 5 分超える、または期限を 60 秒過ぎた優先度 0 のタイマーが 100 件を超える）、期限を過ぎた未発火の違反（1 件以上が 5 分）。個別の runbook `timer-lag.md`・`sla-breach-lag.md`（E4・E5）ができるまでこの場面を使う。

影響：SLA の警告と違反の通知、当番の呼び出しの段の進み、承認の期限、フローのステップが遅れる。**違反の時刻そのものは期限の時刻で記録される**（遅れても SLA の達成率は変わらない）が、担当者が違反に気づくのが遅れる。NFR-003 を消費する。

1. **どの優先度が遅れているか**を見る（タイマーのダッシュボード）。優先度 0 が遅れていれば SEV2。優先度 2・3 だけで、9 時の山（8:55〜9:15）の中なら、5 分までは想定の内（[capacity.md](../architecture/capacity.md) の 2.2 節）。
2. **engine が動いているか**：タスクの数、取得の件数（1 回の取得の件数と取り分）、ワーカーの例外。タスクが 0 か、取得が 0 なら、engine の障害（デプロイ、設定、DB の接続）を疑う。
3. **DB が詰まっているか**：writer の CPU、ロックの待ち、`timer` の表の取得の問い合わせの時間。
   - CPU が高い → 1 テナントの一括の処理（`bulk_job`、大量のトリガー）を疑う。テナント別の「期限を過ぎた」の数と、フローの作成の件数の上位を見る。
   - ロックの待ちが多い → 同じレコードに多くのタイマー（1 つの変更に数千の子）を疑う。
4. **対処**：
   - engine の台数を上げる（最大 24。DB の CPU が 70% を超えているなら上げても速くならない）。
   - 1 テナントのフローの暴走なら、そのフローを無効にし、抑えた実行の数を管理者に知らせる（`flow-runaway.md` の手順。E4）。上限（[ADR-0018](../decisions/0018-flow-limits-and-tenant-fairness.md)）の一時の引き下げは、Dev のテックリードの判断で。
   - `bulk_job` の続き（優先度 3）が多ければ、そのテナントの `bulk_job` を一時止める。
   - engine が落ちている・取得が止まっているなら、直近のデプロイを戻す。
5. **回復の確かめ**：期限を過ぎた未発火の違反が 0、優先度 0 の p99 が 60 秒以内に戻る。回復の後、遅れた違反の通知がまとめて出る（期限の古い順）。影響のあるテナントに「SLA の通知が何時から何時まで遅れた。違反の時刻の記録は正しい」を告知する。
6. **止まった実行の回収**（INV-FLOW-001）が同時に出ていたら、原因（タイマーの消し忘れ、待ちの行の欠け）を Dev のテックリードと調べる。本来は起きない。

#### ACL の漏れの疑い

アラート・報告：本番の漏れの合成監視の検出、テナントからの「見えるはずのないものが見える」報告、出口の漏れの試験の夜間の失敗が本番のコードに当たる、ACL の条件の評価の失敗の急増。access-control の領域の `suspected-acl-leak.md` の提案をこの場面で受ける。

影響：ACL で読めない値・レコードの存在が、どれかの出口（フォーム、リスト、件数、並べ替え、集計、参照の表示、関連リスト、検索、エクスポート、通知、API、Webhook、履歴、添付、ポータル）から見えた可能性。NFR-010・K6 の破れ。

1. **SEV2 で宣言し、セキュリティの担当を呼ぶ。** 漏れが確定したら SEV1 に上げる。
2. **出口と範囲を決める。**
   - 合成監視の検出なら、どの出口のどのシナリオか（監視の結果に出る）。
   - テナントの報告なら、見えた利用者・画面・レコードの ID・時刻を聞く（値は聞かない）。`acl-explain`（同じ `decide` の説明）で、その利用者がそのレコード・フィールドを読めるはずかを確かめる。読めるはず（規則どおり）なら、テナントの ACL の設定の問題で、本システムの漏れではない（テナントの管理者に規則を案内する。SEV を下げる）。
   - 読めないはずなのに見えたなら、漏れである。
3. **被害を止める。**
   - 直近のデプロイ・フラグが原因なら、そのフラグを切る・デプロイを戻す（全セル）。
   - 1 つの出口の誤りで、戻せないなら、その出口を止める（ops フラグ：検索の停止、エクスポートの停止、レポートの停止、Webhook の配達の停止、通知の停止）。止めた機能を告知する。
   - テナントの規則のコンパイルの誤り（新しいコードで古い規則が意図と違う述語になる）なら、そのテーブルを「すべて拒否」に倒す（[access-control.md](../architecture/access-control.md) の 10 節の既定の振る舞いと同じ側）。
4. **証拠を保全する。** ACL の判定のログ（拒否のサンプリング）、アプリのログ（要求の ID・利用者・ルート）、CloudFront のログ、エクスポートの記録、通知の送信の記録（`notification_message`、`email_outbound`）、Webhook の配達の記録。保持の期限の短いもの（通知 30 日、配達 7 日）は、先に写す。
5. **誰が何を見たかの範囲を決める。** 出口ごとに：
   - 画面・API・検索・レポート：その期間の要求のログから、影響のテーブルを読んだ利用者と要求の数。
   - エクスポート・通知・Webhook：送った先（利用者、メールアドレス、Webhook の URL）と件数。**外へ出たもの（メール、Webhook、エクスポートのダウンロード）は取り消せない。**
6. **法務へ連絡する。** 個人データの漏えい等に当たるか、報告の主体（テナントか本システムか）、個人情報保護委員会への報告（速報は速やか、概ね 3〜5 日以内。確報は 30 日以内、不正の目的のおそれがあるときは 60 日以内）と本人への通知の要否を法務が判断する（[security.md](../architecture/security.md) の 13 節、L1）。
7. **テナントへ告知する。** 影響のテナントの管理者に、出口、期間、見えた可能性のある利用者の範囲（件数）、外へ出たかを知らせる。
8. **直す。** 修正は `security:sensitive` の 2 人の承認で、漏れの試験の出口とケースを足してから入れる（時間帯の制限を受けない。[delivery.md](../architecture/delivery.md) の 7 節）。本番の漏れの合成監視のシナリオも足す。

#### テナントの分離の破れの疑い

報告・検知：あるテナントの利用者に、別のテナントのレコード・添付・検索の結果・通知が見えた。SQS のメッセージのテナントと読んだ行のテナントの食い違い（SEV2 の自動の停止。[security.md](../architecture/security.md) の 10.1 節）。

1. **SEV1 で宣言し、セキュリティの担当と Dev のテックリードを呼ぶ。**
2. 経路を決める：RLS のコンテキストの設定漏れ（ルーターの誤り、`SET LOCAL` の抜け、テナントをまたぐロールの誤用）、検索の `tenant_id` の絞り込みの抜け、S3 の接頭辞の誤り、Valkey のキーの接頭辞の誤り、通知の受け手の解決の誤り。
3. 被害を止める：直近のデプロイを全セルで戻す。検索・通知・Webhook を止める。原因のセルのルーターを止める（メンテナンスの応答）ことも IC が判断する。
4. 以後は「ACL の漏れの疑い」の 4〜8 と同じ（証拠、範囲、法務、告知、修正）。範囲は 2 つのテナントの両方に告知する。

#### メールのループ

アラート：メールのループの疑い（流量の上限に当たった件数が 1 テナントで 10 分に 20 件、同じ差出人の保留が 1 時間に 50 件）、テナントからの「同じ通知が何十通も届く」報告。個別の runbook `mail-loop-detected.md`（E6）ができるまでこの場面を使う。

影響：依頼者・担当者に大量の通知が届く。レコードに追記が溜まる。SES の送信の評判（苦情の率）が下がり、セルの送信が止まる危険。

1. **相手を特定する。** 保留の一覧（`inbound_email.classification`、`sender_trust`、流量の上限の記録）で、差出人、テナント、レコード、受信の分類（`human` なのに実は自動の応答、など）を見る。
2. **往復を止める**（上から順に試す）：
   - 流量の上限は効いているか（保留になっているか）。効いていれば、往復はすでに止まっている。
   - 相手の自動の応答が本システムの印（`<Brand>-Loop`、`Auto-Submitted`）を見ていない古い道具なら、その差出人をテナントの受信の規則で一時的に遮断する（24 時間。テナントの管理者に知らせる）。
   - 本システムの判定の誤り（不在の返信の見分けの語の抜け、分類の誤り）なら、その差出人を遮断し、判定の語の一覧の修正を E6 の Story にする。
   - 通知の規則の誤り（コメントのたびに依頼者に送る規則と、依頼者の自動の転送の組み合わせ）なら、テナントの管理者に規則の見直しを案内し、その規則を一時無効にする（管理者の同意を得て）。
3. **溜まったものを片付ける。** 保留のメールは、担当者が一括で「破棄」できる（レコードに追記しない）。すでにレコードに追記された自動の応答は、作業メモとして残る（消さない。監査の履歴）。
4. **送信の評判を見る。** SES のバウンス・苦情の率。上がっていれば、そのテナントの送信を一時止める（テナントのバケットの上限を 0 に）。`sending-reputation.md`（E6）。
5. SEV3（1 テナント）。複数のテナントで同時に起きたら、本システムの判定の誤りを疑い SEV2 に上げる。

#### CMDB の誤った統合

検知・報告：統合の後の保留の急増（統合の先の CI を候補に含む保留が 24 時間に 5 件）、テナントからの「別のサーバーが 1 つの CI になった」報告、影響の範囲・変更の衝突の誤り。個別の runbook `cmdb-wrong-merge.md`（E10）ができるまでこの場面を使う。

影響：2 つの機器の関係・チケットの履歴・識別の値が 1 つの CI に混ざる。変更の影響の範囲と衝突の検知、インシデントの影響を受けるサービスの表示が誤る。統合は人（`cmdb_admin`）の操作なので、本システムの自動の誤りではない（ADR-0037）が、戻す手段が MVP にない（[cmdb-and-reconciliation.md](../architecture/cmdb-and-reconciliation.md) の 5.6 節）。

1. **統合の記録を見る。** `ci_merge_log`（統合の先 `s`、統合された側 `d`、操作した人、理由、時刻、統合の前の `d` の識別の値・観測の状態・関係）。
2. **被害を止める。**
   - 統合の先 `s` に、`d` から来た識別の値が付いている。取り込み元は、`d` の機器の観測を `s` に書き続ける。その取り込み元の、その CI への書き込みを止めるため、`s` を候補にした保留を作らせる（`s` の識別の値のうち `d` から来たものを、除外の一覧に一時的に入れる。`cmdb_admin` の「別の機器である」の操作と同じ効果）。
   - 変更の評価（影響の範囲の写し `change_impact_snapshot`）で、`s` を含む進行中の変更を一覧にし、担当に「影響の範囲が誤っている可能性」を知らせる。
3. **手で戻す**（`cmdb_admin` とテナントの管理者が行い、Ops が手順を案内する）。
   1. 新しい CI `d'` を、`ci_merge_log` の `d` のクラスと属性で作る（識別と調整の入口を `manual` の取り込み元で通す）。
   2. `d` から来た識別の値を `s` から外し、`d'` に登録する（入口の操作で。DB を直接書き換えない）。
   3. `d` から来た関係を `d'` に付け替える。
   4. 統合で `s` に付け替えた進行中のタスク（`bulk_job` の記録）を、`d'` に付け替え直す。
   5. 取り込み元の次の観測で、`s` と `d'` のそれぞれの属性が選び直されることを確かめる（保留が出なければよい）。
   6. `d`（`retired`、`merged_into_id = s`）はそのまま残す（履歴）。
4. **完了したタスクの履歴**（統合の前に `d` を指していたもの）は `d` のまま残っている。付け替えない。
5. SEV3。同じテナントで繰り返すなら、統合の画面の確認の手順（候補の比較の表示）を E10 の Story として見直す。統合を戻す操作を MVP の後に作るかは、この場面の回数で PM が決める。

## エスカレーション

- SEV1 → Ops の責任者、セキュリティの担当、Dev のテックリード、PM（告知）。
- 個人データの漏えい等のおそれ → 法務（報告の要否と主体の判断）。
- 承認・変更の証跡（J-SOX）に影響 → QA と PM（顧客の監査の担当への説明）。
- AWS の障害 → AWS のサポート（ビジネス以上のプラン）に、影響のサービスとリージョンを添えて。
- 2 時間たっても SEV1・SEV2 の原因が特定できない → Dev のテックリードを追加で呼び、対応の人を交代する。

## 事後

- SEV1・SEV2 は 5 営業日以内に事後の振り返り（責めない形）を書く。時系列、影響（テナント・件数・時間）、原因、検知の遅れ、対処、再発の防止。
- 調査結果を Intent の Issue として起票する（Maintain 段）。
- 再発の防止を、テスト（決定表の行、性質、障害の点、漏れの試験の出口）、合成監視のシナリオ、アラートの条件、この runbook のどれかに落とす。
- 個別の runbook ができた場面は、この文書から移し、ここにはリンクだけを残す。
- この手順で足りなかったことを、ここに反映する。
