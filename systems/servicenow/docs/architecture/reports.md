# Reports: ServiceNow

レポート（一覧・集計・推移・表）、ダッシュボード、定期の配信、集計を動かす場所（reader か事前の計算の置き場所か）、ACL を効かせた集計（読めないフィールドの NULL の意味）、SLA の達成率のレポートと `breach_disputed` の扱いを決める。

前提の決定は、読めない値をその利用者にとって NULL として扱い、件数・集計・並べ替え・グループ化もその値で行うこと（[ADR-0012](../decisions/0012-acl-enforcement-at-every-exit.md)）、集計の出口は見る人の主体で計算し、定期の配信は受け手ごとに受け手の主体で計算すること（[access-control.md](access-control.md) の 6.2 節の 5 行）、SLA の違反の事実は計算し直しで取り消さず `breach_disputed` を残し、その扱いをレポートで決めること（[ADR-0021](../decisions/0021-sla-definitions-and-timers.md)）、大きなテナントの集計は S2 で分析の専用の置き場所へ移すこと（[architecture/README.md](README.md) の 2・6 節）である。この文書で決めたことは次の ADR にある。

| ADR | 決定 |
| --- | --- |
| [0045](../decisions/0045-report-execution-on-reader-and-daily-facts.md) | 集計は S1 ではセルの Aurora の「レポート用の reader」で、見る人の問い合わせの時に行う。推移のための過去の状態は日次の事実の表（行の写し）として Aurora に持ち、集計の結果そのものは事前に計算しない。S2 で、PostgreSQL と互換の分析の専用のクラスタへ移す |
| [0046](../decisions/0046-acl-aware-aggregation-and-per-recipient-delivery.md) | 集計は見る人の主体の行の述語と `visible(f)` の上で行い、読めない値は空の値のグループにまとめる（区別しない）。結果のキャッシュは主体を当てはめた後の問い合わせのハッシュで共有する。定期の配信は受け手ごとに計算し、受け手はテナントの有効な利用者に限る |
| [0047](../decisions/0047-sla-attainment-and-breach-disputed.md) | SLA の達成率は、期間の中に停止した計時の行を母数にし、達成 ÷（達成＋違反）で求める。`breach_disputed` の行は、厳格（違反に数える）と調整（新しい期限で判定する）の両方の値と件数を出し、既定の表示は厳格にする。契約の報告でどちらを使うかは PM が E11 で決める |

この文書の決定表・性質は設計の草案である。ID は E11 の各変更の `spec.md` に移すときに確定する。

## 1. 目的と範囲

- 扱う：レポートの定義、実行の場所と上限、日次の事実の表、ACL の効かせ方、結果のキャッシュ、ダッシュボード、定期の配信、SLA の達成率・滞留・担当ごとの件数の組み込みのレポート、レポートのエクスポート。
- 扱わない：一覧の画面（[portal-and-ui.md](portal-and-ui.md) の 4.5 節）、SLA の計時（[sla-and-calendars.md](sla-and-calendars.md)）、通知の配信（[notifications-and-email-ingest.md](notifications-and-email-ingest.md)）、自己解決の率の集計（[knowledge.md](knowledge.md) の 7.4 節。結果の表 `deflection_daily` をレポートの元にできる）。

## 3. レポートの定義

| 列 | 意味 |
| --- | --- |
| `id`、`stable_key`、`owner_id`、`name`（翻訳の対象） | |
| `kind` | `list`（一覧）/ `aggregate`（棒・円・1 つの値）/ `pivot`（2 つのグループ化の表）/ `trend`（時系列） |
| `source` | `table`（テーブルとその子のクラス）/ `daily_fact`（6 節の日次の事実）/ `sla`（`sla_clock` と `task`。8 節）/ 組み込みの集計の表（`deflection_daily` など） |
| `condition` | 式の言語の条件（リストのフィルターと同じ形） |
| `group_by` | 最大 2 つのフィールド（参照のたどりは 1 段まで） |
| `measure` | `count`、または数・長さのフィールドの `sum`・`avg`・`min`・`max` |
| `trend` | 日付のフィールドと、`day`・`week`・`month`、期間（最大 13 か月）、タイムゾーン（既定はテナントの既定） |
| `visibility` | `private`（作った人）/ `groups`（指定のグループ）/ `roles`（指定のロール） |

- レポートの定義はテナントのデータ（利用者が作る）で、メタデータではない。テナントの管理者が「設定として移す」（`packaged = true`）の印を付けたレポートとダッシュボードだけを、設定のパッケージで移す（統合で決めた。[data-dictionary-and-tables.md](data-dictionary-and-tables.md) の 10.1 節）。印を付けられるのは `tenant_admin` で、印の付いた定義は `stable_key` を持つ。
- **定義を共有しても、データは共有しない。** 共有されたレポートを開くと、開いた人の主体で計算する（7 節）。
- 集計に使えるフィールドは、索引のある列（型付きの列と `ext_index` のフィールド）だけにする。索引のないテナントのフィールドでのグループ化・集計は、定義の保存の時に 422 にする（[ADR-0007](../decisions/0007-physical-layout-and-extension-index.md) の上限の考えと同じ）。

## 4. 実行の場所（[ADR-0045](../decisions/0045-report-execution-on-reader-and-daily-facts.md)）

### 4.1 S1：レポート用の reader

```
セルの Aurora クラスタ（architecture/README.md の 2 節：writer 1 台＋reader 2 台）
  writer   … 保存、フロー、タイマー
  reader A … 画面・API の読み取り、検索の確かめ直し（既定の reader のエンドポイント）
  reader B … レポート用のカスタムのエンドポイント（report）。定期の配信、ダッシュボード、エクスポート
  ※ フェイルオーバーの優先度は A を先、B を後にする
```

- **レポートの問い合わせは reader B だけで動かす。** 重い集計が、画面の読み取り（NFR-001）と writer を遅くしないようにする。reader B が落ちたら、レポートは reader A を使い、同時の実行の上限を半分に下げる。
- Aurora の reader は、書き込みの後の遅れが通常 100ms を大きく下回る。書き込みが多いと遅れは増える（[Replication with Amazon Aurora](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Replication.html)、2026-09-28 に確認）。レポートは「数秒前の値」でよいとし、画面に集計の時刻を出す。

### 4.2 上限

| 項目 | 上限（S1 の既定。E11 の計測で見直す） | 超えたとき |
| --- | --- | --- |
| 画面からの 1 回の問い合わせの時間 | 10 秒（`statement_timeout`） | 打ち切り、「条件を絞るか、定期の配信にしてください」 |
| 定期の配信・エクスポートの 1 回の時間 | 120 秒 | 失敗にし、持ち主に知らせる |
| テナントの同時の実行（画面） | 5 | 待たせる（最大 30 秒）、その後 429 |
| テナントの同時の実行（定期・エクスポート） | 2 | 列で待つ |
| セルの reader B の同時の実行 | 40 | 待たせる |
| 走査する行（見積もり） | 1,000 万 | 実行の前に `EXPLAIN` の見積もりで止める |
| グループ化の結果の行 | 1,000（`pivot` は 100 × 100） | 上位を出し「その他」にまとめる |
| エクスポートの行 | 10 万（DT-ACL-003 の 10 行と同じ） | 打ち切り、打ち切ったことを示す |

- テナントの同時の実行の上限は、1 つのテナントのダッシュボードの一斉の読み込み（朝の会議）が、他のテナントを待たせないためである。

### 4.3 S2 の置き場所

- 次のどれかに当たったら、分析の専用のクラスタへ移す（[infrastructure.md](infrastructure.md) の 9 節の段階の基準に入れる）。
  - reader B の CPU のピークの p95 が 60% を超える
  - 画面のレポートの p95 が 5 秒を超える
  - 1 テナントの `task` が 2,000 万行を超える
- **移す先は、PostgreSQL と互換のクラスタにする（既定案）。** レポートの問い合わせは、ACL の述語のコンパイラ（[ADR-0012](../decisions/0012-acl-enforcement-at-every-exit.md)）が作る SQL で動く。別の方言の置き場所（列指向の DWH）に移すと、コンパイラを 2 つ持つことになる。
- 候補：(a) 別の Aurora のクラスタへ論理レプリケーションで必要な表だけを写す、(b) Amazon Redshift への zero-ETL（写す単位はデータベース・スキーマ・テーブルで、行や列では絞れない。[Aurora zero-ETL integrations](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/zero-etl.html)、2026-09-28 に検索の結果の抜粋で確認）。(b) は RLS とテナントの分離を Redshift の側で作り直すことになる。S2 の前に E11 の計測で決める（持ち越し）。

## 5. 実行の流れ

```
レポートを開く（主体 P）
 1. 定義を読み、P が定義を見られるか（visibility）を確かめる
 2. 問い合わせを組み立てる：
      source の表 ＋ 行の read の述語（P）＋ 定義の condition（visible(f) の上で評価）
      グループ化・集計は visible(f) の上（7 節）
 3. キャッシュのキー = hash(主体を当てはめた後の SQL と引数) ＋ meta_version ＋ 集計の時刻の 5 分の枠
      あれば返す（7.3 節）
 4. reader B で実行（4.2 節の上限）
 5. 結果に「集計の時刻」「打ち切りの有無」を付けて返す
掘り下げ（グループの 1 つを押す）
 6. 同じ condition ＋ そのグループの値の条件で、リストの出口（portal-and-ui.md の 4.5 節）を開く
```

- 掘り下げは、集計と同じ述語と同じ `visible(f)` を使うので、集計の件数と掘り下げの一覧の件数が一致する（キャッシュの時刻の差を除く）。

## 6. 日次の事実の表（[ADR-0045](../decisions/0045-report-execution-on-reader-and-daily-facts.md)）

「毎日の未解決の件数の推移」「グループごとの滞留の推移」は、今の行からは作れない（過去の状態が要る）。

```
task_daily_fact（tenant_id, day, task_id, class_id, state, active, priority,
                 assignment_group_id, assigned_to_id, age_days, sla_breached_any）
  - 毎日、テナントのタイムゾーンの 0 時の時点の active な task の行を写す
  - 月ごとのパーティション、13 か月保つ
```

- **写すのは行の値で、集計の結果ではない。** 集計の結果（「グループ A の未解決 12 件」）を事前に計算すると、見る人ごとに違う ACL の結果を持てない。行の写しなら、問い合わせの時に見る人の述語で絞れる。
- 事実の表の ACL：行の述語は、**今の `task` の行**に対して評価する（`task_daily_fact` と `task` を `task_id` で結合する）。フィールドの `visible(f)` も今の行の述語で判定し、その判定を事実の表の値に当てる。過去の値を、今の権限で見せる（読めなくなった人には見せない）。
- 削除した `task` は結合で落ちる（事実の表に残っても出ない）。事実の表の行は 13 か月で消える。
- 写しのジョブは Engine の日次のジョブで、テナントごとに `INSERT ... SELECT`（writer で、夜間に 1 テナントずつ）。S1 の見込みで、1 日の写しは全体で約 50 万行（進行中の `task` の数。初期見積もり）。
- 事実の表は、レポートの推移の元にだけ使う。画面の一覧・SLA の計時の正本にしない。

## 7. ACL を効かせた集計（[ADR-0046](../decisions/0046-acl-aware-aggregation-and-per-recipient-delivery.md)）

### 7.1 規則

| 要素 | 扱い |
| --- | --- |
| 母数の行 | 見る人の行の `read` の述語を満たす行だけ（DT-ACL-003 の 3 行） |
| 条件（`condition`） | `visible(f)` の上で評価する。読めないフィールドの条件は NULL との比較になる |
| グループ化 | `visible(f)` の値でグループにする。読めない値と本当に空の値は、同じ「（空）」のグループになる |
| 集計（`sum`・`avg`・`min`・`max`） | `visible(f)` の上。読めない値は NULL として集計から外れる（SQL の集計の関数の NULL の扱い） |
| 件数（`count`） | 行の数。読めない値でも行は数える（行は読めるため） |
| 参照のグループの表示の名前 | 参照先の行と表示のフィールドが読めるときだけ名前を出す。読めなければ「（表示できないレコード）」にまとめる（DT-ACL-003 の 6 行） |
| 掘り下げ | 同じ規則のリスト |

- **読めない値と空の値を区別しない**（決定）。「（読めない値）」のグループを別に出すと、その件数から「このフィールドが読めない行が何件あるか」が分かる。フィールドの読み取りがレコードの条件で決まるとき（例：「人事の部署の依頼だけ隠す」）、その件数はレコードの条件に合う行の数を漏らす（PROP-ACL-004 の集計の版）。
- 画面は、読めないフィールドをグループ化・集計の選択肢に出さない（[access-control.md](access-control.md) の 6.1 節）。共有されたレポートで、見る人に読めないフィールドでグループ化しているときは、グループがすべて「（空）」になる。画面に「このレポートには、あなたが見られない項目が含まれます」と出す。どの項目かは出さない。

DT-RPT-001（レポートを開いたときの振る舞い）：

| # | 定義を見られる（visibility） | 元のテーブルの行の `read` の規則が主体にある | グループ化・集計のフィールドが主体に読める | 結果 |
| --- | --- | --- | --- | --- |
| 1 | いいえ | - | - | 404（定義の存在を知らせない） |
| 2 | はい | ない（どの行も読めない） | - | 空の結果（0 件）。エラーにしない |
| 3 | はい | ある | すべて読める | 通常の結果 |
| 4 | はい | ある | 読めないものがある | 読めない値を「（空）」にまとめた結果と、7.1 節の注意の文 |
| 5 | - | - | - | 拒否（網羅の確かめ） |

- 2 行を 403 にしないのは、定義は見られることを 1 行で確かめ済みで、「行が 0 件」と「行を読めない」を見分けさせないためである。

### 7.2 全体の集計のロール

- 「部門の管理者に、全社の件数だけを見せたい」要望がある。行の `read` を与えずに件数だけを見せると、条件の組み合わせで個々の行の存在を推測できる（件数が 1 のグループ）。
- MVP では、件数だけの権限を作らない。全体の件数を見る人には、そのテーブルの行の `read` を与える（フィールドの ACL で機微な値は隠せる）。
- 小さなグループの伏せ（k-匿名の考え）での件数だけの権限は、持ち越し。

### 7.3 結果のキャッシュ

- キャッシュのキーは、**主体を当てはめた後の SQL と引数のハッシュ**にする。行の述語が同じになる主体（同じロール・同じグループ・述語に使う同じ属性の人）は、同じキーになり、結果を共有する。見る人が違っても、述語が同じなら結果は同じだからである。
- キーに `meta_version` と 5 分の時刻の枠を入れる。ロール・グループの変化は、当てはめた SQL の変化としてキーに現れる。規則の変更は `meta_version` に現れる。
- 置き場所は Valkey（セルの中、テナントの接頭辞）。失われてもよい。1 件 1 MB まで、テナントあたり 200 MB まで。

## 8. SLA の達成率（[ADR-0047](../decisions/0047-sla-attainment-and-breach-disputed.md)）

### 8.1 母数と判定

期間 P（テナントのタイムゾーンの暦の半開区間 `[開始, 終わり)`）、SLA の定義 D（`stable_key`。版をまたいで同じ定義として数え、版ごとの内訳も出す）について：

```
母数 = sla_clock のうち、定義が D、stage = completed、stop_at ∈ P の行
達成 = 母数のうち breached = false
違反 = 母数のうち breached = true
達成率 = 達成 ÷（達成 ＋ 違反）         … 母数が 0 なら「—」
```

- 取り消し（`cancelled`）の行は母数に入れない。件数は別に出す（リセットで取り消した行も含む。`cancel_reason` 別）。
- 進行中（`in_progress`・`paused`）の行は母数に入れない。「期間の終わりの時点で違反中の件数」と「進行中の件数」を別に出す。停止した期間の母数に入る。
- 期間は停止の時刻で数える。開始の時刻で数えると、長い SLA の達成率が期間の終わりの後まで確定しないためである。
- ACL：母数は、見る人が読める `task` の計時の行だけ（計時の行の `read` はタスクの `read` に従う。[sla-and-calendars.md](sla-and-calendars.md) の 10 節）。

### 8.2 `breach_disputed`

- `breach_disputed` は、カレンダー・祝日の計算し直しで期限が後ろに動き、すでに違反した行の新しい期限がまだ来ていなかったときに、`sla_clock_event` に残る事象である（[sla-and-calendars.md](sla-and-calendars.md) の 8 節）。違反の事実（`breached = true`）は取り消されない。
- 停止の後、その行は次のどれかになる。

DT-RPT-002（停止した行の分類）：

| # | `breached` | `breach_disputed` の事象がある | `stop_at` ≤ 今の `planned_end`（計算し直しの後の期限） | 分類 |
| --- | --- | --- | --- | --- |
| 1 | false | - | - | 達成 |
| 2 | true | ない | - | 違反 |
| 3 | true | ある | はい | 争いのある違反（新しい期限では達成） |
| 4 | true | ある | いいえ | 違反（新しい期限でも違反。争いは解けた） |
| 5 | - | - | - | 網羅の確かめ（ここに来ない） |

- 3 行の「争いのある違反」を、次の 2 つの値で出す。

| 値 | 3 行の扱い | 使いどころ |
| --- | --- | --- |
| 厳格の達成率 | 違反に数える | 違反の通知・エスカレーションが実際に動いた事実と一致する |
| 調整の達成率 | 達成に数える | 祝日の追加（法の改正）で期限が延びたことを、契約の評価に反映したいとき |

- **既定の表示は厳格の達成率にし、調整の達成率と争いのある件数を並べて出す**（決定）。どちらを契約の報告に使うかは PM が E11 で決める（[sla-and-calendars.md](sla-and-calendars.md) の 13 節の持ち越し）。テナントは、レポートの設定で既定の表示を選べる（選んだことを監査に残す）。
- `breach_disputed` は事象の表にしかないので、毎回 `sla_clock_event` を探すと遅い。**`sla_clock` に `breach_disputed_at` の列を足し、事象と同じトランザクションで入れる**（統合で決めた。[sla-and-calendars.md](sla-and-calendars.md) の 6.2・8 節）。DT-RPT-002 の「`breach_disputed` の事象がある」は、この列が空でないことで判定する。

## 9. ダッシュボード

- ダッシュボードは、レポートの部品の配置（行と列、最大 12 の部品）と、共通のフィルター（期間、担当のグループ）を持つ。
- 各部品は独立に計算し、1 つの失敗・打ち切りが他を止めない。部品ごとに「集計の時刻」を出す。
- ダッシュボードの共有は、定義の共有である（7 節）。
- 画面の自動の更新は 5 分ごと（キャッシュの枠と同じ）。それより速くしない。

## 10. 定期の配信（[ADR-0046](../decisions/0046-acl-aware-aggregation-and-per-recipient-delivery.md)）

| 列 | 意味 |
| --- | --- |
| `report_id` または `dashboard_id` | |
| `schedule` | 毎日・毎週・毎月（曜日・日・時刻、テナントのタイムゾーン）。業務カレンダーの営業日だけ、を選べる |
| `recipients` | 利用者・グループ（展開の後 500 人まで） |
| `format` | メールの本文の表（上位 50 行）＋ CSV の添付 |

- **受け手ごとに、受け手の主体で計算する。** 同じ述語になる受け手は、7.3 節のキャッシュで 1 回の計算を共有する。
- **受け手はテナントの有効な利用者だけ。** 外部のメールアドレスには送らない（決定）。外部の人に送るには、誰の主体で計算するか（作った人か）を決める必要があり、作った人の権限で読める値を外に出す経路になるためである。
- 送るのは Notifier で、通知の 1 通として `notification_message` の一意で 1 回にする（[ADR-0033](../decisions/0033-notification-rules-and-outbound-email.md)）。
- 実行の時刻は、指定の時刻から 0〜10 分のばらつき（テナント・配信の ID のハッシュで決まる値）を足す。月初の 9 時に全テナントの配信が一斉に reader B に来るのを避ける（[capacity.md](capacity.md) の 1 節）。
- 画像（PNG のグラフ）と PDF は MVP で送らない（画面の描画の仕組みを Notifier に持たない。持ち越し）。

## 11. エクスポート

- レポートの一覧・集計の結果の CSV は、リストのエクスポートと同じ出口（DT-ACL-003 の 10 行）で、10 万行まで。`auditor` は含まない。成り代わりの間はできない（[ADR-0013](../decisions/0013-impersonation-and-tenant-sso.md)）。
- CSV は UTF-8（BOM 付き。表計算ソフトでの文字化けを避ける）。値が `=`・`+`・`-`・`@` で始まるセルは先頭に `'` を付ける（CSV の式の注入の対策）。
- エクスポートは非同期で作り、S3 に 24 時間置き、署名付き URL（5 分）で渡す。エクスポートの操作は監査ログに残す。

## 12. 障害のときの振る舞い

| 障害 | 振る舞い |
| --- | --- |
| reader B の障害 | reader A で動かし、同時の実行の上限を半分にする。定期の配信は遅らせてよい |
| reader の遅れの増加 | 集計の時刻を出しているので、そのまま出す。10 秒を超えたら、画面に「数値が遅れています」を出す |
| 日次の事実の表のジョブの失敗 | その日の点を欠けとして推移に出す（0 と区別する）。翌日に前日の分を作り直せないときは欠けのままにする |
| 定期の配信の失敗 | 3 回まで再試行し、失敗なら持ち主に知らせる |
| キャッシュ（Valkey）の障害 | 毎回計算する。同時の実行の上限で守る |

## 13. セキュリティ

- 集計は、行の述語と `visible(f)` の上でだけ行う。レポートのための抜け道の問い合わせを作らない。
- 読めない値と空の値を区別しない（7.1 節）。件数だけの権限を作らない（7.2 節）。
- キャッシュのキーに主体を当てはめた SQL を使うので、違う述語の人が同じ結果を受け取ることはない。
- 定期の配信は受け手の主体で計算し、外部に送らない（10 節）。
- CSV の式の注入の対策（11 節）。
- reader B で動かす DB のロールは、アプリのロールで RLS の対象にする（`BYPASSRLS` を持たない）。

## 14. テスト

### 14.1 決定表

- DT-RPT-001（レポートを開いたとき）、DT-RPT-002（停止した行の分類）を、`spec.md` から読む表駆動テストにする。

### 14.2 性質ベーステスト

- **PROP-RPT-001（集計は推測させない）**：任意のテーブル・ACL・主体で、読めないフィールド f の値だけが違う 2 つのデータの集合に対し、任意のレポート（条件・グループ化・集計）の結果は同じ（PROP-ACL-004 のレポートの版）。
- **PROP-RPT-002（集計と掘り下げの一致）**：任意のレポートとグループで、グループの件数は、掘り下げのリストの行の数と等しい（同じデータの時点で）。
- **PROP-RPT-003（キャッシュの共有は正しい）**：任意の 2 主体で、主体を当てはめた SQL が等しければ、2 人が直接計算した結果は等しい。
- **PROP-RPT-004（達成率の分け方）**：任意の計時の行の集合で、母数 ＝ 達成 ＋ 違反 ＋ 争いのある違反（DT-RPT-002 の分類）で、厳格の達成率 ≤ 調整の達成率。
- **PROP-RPT-005（期間の加法）**：任意の期間の分け方で、隣り合う期間の母数の和は、合わせた期間の母数と等しい（半開区間）。

### 14.3 結合テスト

- 漏れの試験の集計の出口（[access-control.md](access-control.md) の 12.3 節）：読めないフィールドに「漏れの印」を入れ、グループ化・集計・掘り下げ・CSV・定期の配信のメールに出ないこと。
- 上限（4.2 節）の打ち切りと、reader B の障害のときの切り替え。
