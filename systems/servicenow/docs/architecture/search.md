# Search: ServiceNow

全体の検索（テーブルを横断する検索）、ナレッジの検索、カタログの検索、OpenSearch の索引と反映、日本語の解析器、ACL を効かせた検索、索引の鮮度を決める。

前提の決定は、検索に Amazon OpenSearch Service を使い、索引をセルごとに持ち、文書に `tenant_id` を入れて問い合わせに必ず付けること（[ADR-0001](../decisions/0001-platform-and-stack.md)、[ADR-0002](../decisions/0002-tenancy-and-isolation.md)）、検索の出口は「索引の ACL の属性で絞った後、返す直前に各結果を判定の関数で確かめ直す。読めないフィールドの一致の強調を出さない」こと（[access-control.md](access-control.md) の 6.2 節の 9 行、[ADR-0012](../decisions/0012-acl-enforcement-at-every-exit.md)）、ナレッジは公開中の版だけを索引に入れること（[knowledge.md](knowledge.md) の 6 節）である。この文書で決めたことは次の ADR にある。

| ADR | 決定 |
| --- | --- |
| [0043](../decisions/0043-japanese-analyzer-and-index-layout.md) | 日本語の解析器は Sudachi を既定にし、正規化の形（表記の揺れの吸収）と、未知の語のための 2 文字の n-gram の副フィールドを併せて持つ。索引はセルの OpenSearch のドメインに種類ごとの共有の索引を置き、`tenant_id` で経路を決める。テナントのフィールドは入れ子のフィールドの枠に入れ、フィールドの数を増やさない。辞書の更新は新しい索引への入れ直しと別名の切り替えで行う |
| [0044](../decisions/0044-acl-aware-search-and-index-freshness.md) | 検索は、行の ACL の述語のうち索引で表せる部分を OpenSearch の絞り込みにし、返す直前に DB で行の述語とフィールドの読み取りを確かめ直す。一致させるフィールドと強調は、見る人が読めるフィールドに限る。OpenSearch の総数を出さない。索引は outbox から、レコードの版を外部の版として反映し、遅れを計測する |

この文書の決定表・性質は設計の草案である。ID は E9 の各変更の `spec.md` に移すときに確定する。

## 1. 目的と範囲

- 扱う：索引に入れるもの、索引の配置、日本語の解析、問い合わせの形、ACL の絞り込みと確かめ直し、強調、並べ替え、索引への反映と鮮度、索引の作り直し、検索の語の扱い。
- 扱わない：ナレッジの公開の範囲の規則（[knowledge.md](knowledge.md) の 6 節）、カタログの見える品目の集合（[service-catalog-and-requests.md](service-catalog-and-requests.md) の 6.1 節）、画面の検索の箱（[portal-and-ui.md](portal-and-ui.md)）、ACL の規則（[access-control.md](access-control.md)）。
- **検索は DB の代わりではない。** 正本は Aurora で、索引はいつでも DB から作り直せる写しである。リストの絞り込み（索引のある列）は DB で行い、全文と曖昧な一致だけを検索で行う。

## 3. 索引に入れるもの

| 索引（種類） | 文書 | 入れるフィールド | 使う画面 |
| --- | --- | --- | --- |
| `task` | `task` の全クラスのレコード（進行中と完了。削除は除く） | 番号、短い説明、説明、状態、クラス、担当のグループ・担当者・依頼者の ID、CI の ID、作成・更新の時刻、索引の対象のテナントのフィールド、作業メモ・コメントの本文（下の注） | 全体の検索、担当者の類似のチケットの候補 |
| `kb` | 公開中の版（`published`）だけ | 題名、本文（Markdown を文字列にしたもの）、キーワード、`kb_base_id`、`audience_id`、カテゴリ、評価の合計 | ナレッジの検索、ポータルの候補（[knowledge.md](knowledge.md)） |
| `catalog` | 公開中の品目の版 | 名前、説明、キーワード、カテゴリ、`audience_id` | ポータルのカタログの検索 |
| `ci` | `ci`（`retired` を含む。既定では出さない） | 名前、クラス、識別の値のうち表示してよいもの（シリアル番号、ホスト名、IP）、場所、所有のグループ | 全体の検索、参照の候補 |

- **作業メモとコメントは、`journal` の読み取りの規則（組み込み：作業メモは `agent` 以上）が違うので、文書の中で種類ごとに別のフィールドの枠に入れる**（4.3 節）。依頼者の検索で作業メモの語に一致させない。
- 添付ファイルの本文は MVP で索引に入れない（持ち越し）。
- 監査の履歴は入れない（履歴の検索は DB で行う）。
- テナントのテーブル（`custom_record`）は、管理者が「検索に入れる」を選んだテーブルだけを `task` と同じ形の索引 `record` に入れる。

## 4. 解析器（[ADR-0043](../decisions/0043-japanese-analyzer-and-index-layout.md)）

### 4.1 選定

| 観点 | Sudachi | kuromoji |
| --- | --- | --- |
| OpenSearch Service での扱い | 任意のプラグイン。関連付けが要る。「日本語に勧める」とされる | すべてのドメインに入っている |
| 表記の揺れ | 正規化の形（例：「サーバー」と「サーバ」、「問い合わせ」と「問合せ」を揃える。辞書の正規化の情報による） | 基本の形・読みのフィルターはあるが、表記の揺れの正規化の仕組みはない（未検証） |
| 分割の単位 | A・B・C を選べる。索引は C（複合語を保つ）＋ A（短い単位）の併用ができる | `search` の方式で複合語を分け、元の語も持つ |
| 辞書 | 公式の辞書（小・中・大）。利用者の辞書 | IPADIC。利用者の辞書 |
| 辞書の更新 | 次の blue/green まで効かない。新しい索引への入れ直しで効かせる | 利用者の辞書の更新も入れ直しが要る（未検証） |
| エンジンの版との結び付き | プラグインのパッケージが OpenSearch の版ごと。エンジンの版を上げるときに、同じ版のパッケージが要る | 同梱 |

- **Sudachi を既定にする**（決定）。ITSM の文章は「サーバー／サーバ」「ログイン／ログオン」「問合せ／問い合わせ」のような表記の揺れが多く、正規化の形の効果が大きいと見込む。
- ただし、効果は E9 の評価で確かめる。評価のデータ（架空の社内のナレッジ 2,000 本と、実際の問い合わせを模した検索の語 300 と、正解の記事の組）で、Sudachi と kuromoji の nDCG@10 と再現率@20 を比べる。**Sudachi が kuromoji より低ければ、この決定を新しい ADR で置き換える**（[ADR-0043](../decisions/0043-japanese-analyzer-and-index-layout.md) の Confirmation）。
- 評価のデータに本物の社員の名前や本物の社内の文書を使わない（[AGENTS.md](../../AGENTS.md)）。

### 4.2 解析の組み立て

```
文字の前処理：ICU の正規化（NFKC、大文字・小文字を揃える）… 全角・半角の英数字の揺れを揃える
本文のフィールド（text）：
  ja     … Sudachi（分割 C）→ 正規化の形 → 品詞で助詞・助動詞を落とす → 止め語（組み込み＋テナント）
  ja_a   … Sudachi（分割 A）→ 正規化の形 → 同じ    … 複合語の部分での一致（「パスワード再設定」→「再設定」）
  bigram … CJK の 2 文字の n-gram               … 辞書にない語（製品の型番、社内の略語、誤字）の拾い上げ
  en     … 英語の標準の解析（語幹）             … 英語の文章
番号・識別の値（keyword）：大文字・小文字を揃えた完全一致と前方一致
```

- 問い合わせは `ja` と `ja_a` を主にし、`bigram` は重みを下げて足す（再現率の補い）。`en` は検索の語に英字が多いときに重みを上げる。
- 番号（`INC0001234`）と識別の値（ホスト名、シリアル番号）の完全一致は、最も高い重みにする（担当者は番号で探すことが多い）。
- 同義語は、テナントごとの同義語の一覧を問い合わせの時に展開する（索引の時に展開しない）。索引の解析器はセルで共通なので、テナントごとの索引の時の同義語を持てない。

### 4.3 辞書の更新

- Sudachi の辞書の更新（公式の辞書の新しい版、組み込みの利用者の辞書の追加）は、新しいパッケージを作り、新しい索引（`task_v{n+1}`）に DB から入れ直し、別名（`task`）を切り替えてから古い索引を消す（5.4 節の作り直しと同じ手順）。
- テナントの利用者の辞書は MVP で持たない。テナントの語は同義語の一覧と `bigram` で拾う（持ち越し）。

## 5. 索引の配置（[ADR-0043](../decisions/0043-japanese-analyzer-and-index-layout.md)）

### 5.1 ドメインと索引

```
セルごとに 1 つの OpenSearch のドメイン（3 AZ、専用のマスター 3）
  索引：task_v{n}、kb_v{n}、catalog_v{n}、ci_v{n}、record_v{n}（別名で task などを指す）
  すべての文書：_routing = tenant_id、フィールド tenant_id（keyword）
専用のセル：専用のドメイン（他の顧客と共有しない。NFR-009）
```

- **テナントごとに索引を分けない。** S1 で 300 テナント、S3 で 3 万テナントに、種類ごとの索引を持つと、シャードの数が 1 ドメインの上限と JVM のヒープの目安（1 GiB あたり 25 シャード）を大きく超える（2 節）。
- `_routing = tenant_id` で、1 つのテナントの文書を 1 つのシャードに集める。問い合わせは同じ `routing` を付け、そのシャードだけを読む。大きなテナント（CI 500 万）が 1 つのシャードを大きくしすぎるときは、索引の設定 `routing_partition_size` で数シャードに広げる（E9・E10 の計測で決める）。
- **すべての問い合わせに `tenant_id` の絞り込みを付ける。** 問い合わせを組み立てる関数は 1 つで、`tenant_id` を引数に必須にする（型で強制する）。`routing` だけに頼らない（同じシャードに他のテナントもいる）。
- OpenSearch の細かなアクセス制御（文書の単位の権限）は使わない。Indexer と App の検索のロールは、そのセルの索引だけを読み書きする IAM の権限を持つ。テナントの分離は、上の必須の絞り込みと 6 節の DB での確かめ直しの 2 つで行う。

### 5.2 テナントのフィールド

- テナントのフィールドを索引のフィールドにすると、テナントの数 × フィールドの数で、索引のフィールドの数が OpenSearch の既定の上限（1 索引 1,000）を超える。
- **テナントのフィールドは、入れ子の枠に入れる。**

```
fields: nested [
  { fid: "<field_id>", kind: "text" | "keyword" | "journal_work_note" | "journal_comment",
    text: 解析する本文（ja / ja_a / bigram の副フィールド）, kw: 完全一致の値 }
]
```

- 組み込みの本文（短い説明、説明）と、作業メモ・コメントも同じ枠に入れる（`fid` は組み込みのフィールドの ID）。これで、6.3 節の「読めるフィールドだけに一致させる」を 1 つの形で書ける。
- 入れるのは、`string`・`text` の型で、管理者が「検索に入れる」を選んだテナントのフィールドだけ（1 テーブル 20 まで）。数・日付・参照のフィールドは索引に入れない（絞り込みは DB で行う）。

### 5.3 大きさ（S1、1 セル。初期見積もり）

| 索引 | 文書の数 | 1 文書 | 主の大きさ | シャード（主） |
| --- | --- | --- | --- | --- |
| `task` | 3,500 万（1 年分。セルに S1 の半分） | 約 3 KB（本文と作業メモの一部） | 約 110 GB | 6 |
| `ci` | 2,500 万 | 約 1 KB | 約 25 GB | 2 |
| `kb` | 10 万 | 約 8 KB | 約 1 GB | 1 |
| `catalog`、`record` | 数万 | — | 1 GB 未満 | 1 |

- 作業メモは、1 つのレコードの最新の 50 件、合計 32 KB までを入れる（長いレコードで文書を大きくしない）。それより古い作業メモの検索は、レコードの画面の中の検索で行う（DB）。
- レプリカ 1 で合計 約 280 GB。ノードの構成は [infrastructure.md](infrastructure.md) の 5 節。完了から 2 年を過ぎた `task` は索引から外す（DB には残る。持ち越し：古いレコードの検索の要望を見て）。

## 6. ACL を効かせた検索（[ADR-0044](../decisions/0044-acl-aware-search-and-index-freshness.md)）

### 6.1 流れ

```
検索（主体 P、語 q、種類 kind）
 1. 主体を解く（access-control の 3.4 節。acl_version でキャッシュ）
 2. 行の read の述語を、索引の絞り込みにコンパイルする（6.2 節）
      表せる部分 F_os と、表せない部分 R（なければ真）に分ける
 3. 読めるフィールドの集合 V を決める（ロールだけで決まる field の read。6.3 節）
 4. OpenSearch：tenant_id = T AND kind AND F_os AND nested(fields.fid ∈ V かつ語に一致)
      上位 N 件（N = 1 ページの件数 × 3、最大 150）の ID と版と、V の中の強調を取る
 5. DB で確かめ直す（6.4 節）：
      SELECT id FROM <table> WHERE tenant_id = T AND id = ANY($ids) AND <行の read の述語（全体）>
      一致したフィールドについて、行ごとの field の read（レコードの条件を含む）を確かめる
 6. 確かめを通った行だけを、OpenSearch の順位の順に返す。強調は 3 と 5 を通ったフィールドだけ
 7. 1 ページに足りなければ、4 を次の N 件で繰り返す（最大 3 回）。それでも足りなければ、そこで止め「さらに探す」を出す
```

- **OpenSearch の総数（`hits.total`）を画面にも API にも出さない。** 総数は 5 の確かめの前の数で、読めない行を含む。出すのは「このページの結果」と「さらにあるか」だけにする。
- 集計（ファセット：状態ごとの件数など）は、OpenSearch の集計を使わない。必要なら、DB のリストの出口で数える（[portal-and-ui.md](portal-and-ui.md) の 4.5 節の上限付きの件数）。

### 6.2 行の述語のコンパイル

行の規則の条件は、SQL の述語にコンパイルできる形に限られている（[access-control.md](access-control.md) の 4.5 節）。そのうち索引で表せる部分を OpenSearch の絞り込みにする。

| 条件の要素 | OpenSearch での扱い |
| --- | --- |
| 索引に入れた型付きの列（クラス、状態、担当のグループ・担当者・依頼者の ID、CI の ID、`kb_base_id`、`audience_id`）と定数・主体の属性の比較 | `term`・`terms` の絞り込みに写す |
| `active`、時刻の `now` の相対の比較 | `term`・`range` に写す（`now` は要求の開始の時刻に固定） |
| 論理の結合（AND・OR・NOT） | `bool` に写す。ただし、表せない要素を含む枝は下の扱い |
| 1 段の参照のたどり（`assignment_group.manager = me`）、索引に入れていない列 | 表せない。AND の中なら R に回す（索引では真として扱い、DB で確かめる）。OR・NOT の中なら、その枝を含む式全体を R に回し、索引では `tenant_id` とクラスだけで絞る |

- 索引では「真として扱う」（広めに取る）方向にだけ近似する。狭める方向の近似はしない（読める行を落とさないため）。読めない行が 4 で混ざっても、5 で落ちる。
- 近似が大きい（R が主な絞り込みになる）テーブルでは、5 で多くの行が落ち、7 の繰り返しが増える。落ちた割合を計測し（quality の項目）、多ければ、その列を索引に入れる。
- 行の ACL の規則の変更は、索引を作り直さない。規則は問い合わせの時にコンパイルするからである（`acl_version` のキャッシュ）。

### 6.3 フィールドと強調

- **一致させるフィールドを、見る人が読めるフィールドに限る。** 3 の V は、フィールドの `read` の判定のうち、ロールだけで決まる（真の定数になる）フィールドの ID の集合である。V の外のフィールドの語には一致させない（入れ子の問い合わせの `fid ∈ V`）。
- レコードの条件で読めるかが変わるフィールド（例：「依頼者の会社が同じなら読める」）は、V に入れて一致させ、5 で行ごとに確かめる。読めない行では、そのフィールドの一致だけで結果に入った行を落とす（そのフィールド以外にも一致していれば残し、強調から外す）。
- こうするのは、「読めないフィールドにだけ一致した行が結果に出る」ことで、読めない値に語が含まれることを推測させないためである（PROP-ACL-004 の検索の版）。
- 強調（ハイライト）は、入れ子の一致のうち、最終的に読めるフィールドの断片だけを返す。断片の長さは 150 文字まで。

### 6.4 DB での確かめ直し

- 確かめ直しは、リストの出口と同じ述語のコンパイラで作った SQL を、Aurora の reader で行う。1 回の検索で 1〜3 回の問い合わせ（ID の集合で引くので、索引の上で速い）。
- **索引の遅れと削除にも効く。** 索引に残っている削除済みのレコード、権限を外された後のレコード、索引の版の古いレコードは、DB の今の値で判定されるので、結果に出ない。
- 強調の断片は、索引の時点の本文から作る。レコードの本文が索引の後に変わったとき、古い断片が出うる。断片を出すのは、索引の版（6.5 節の外部の版）が DB の `version` と等しい行だけにし、違えば断片を出さずに題名だけを出す。

### 6.5 ポータルとナレッジ

- ポータルの依頼者は、`requester` の組み込みの規則（DT-REQ-002、ナレッジの公開の範囲）で同じ流れを通る。ポータル用の別の検索を作らない。
- ナレッジの `audience` は主体の属性だけで評価できる（[service-catalog-and-requests.md](service-catalog-and-requests.md) の 6.1 節）。主体ごとに読める `audience_id` の集合をキャッシュし、`terms` の絞り込みにする。`kb` は 6.2 節の近似がほぼ要らない。
- カタログの検索は、見える品目の ID の集合（キャッシュ）を `terms` にする。

## 7. 索引への反映と鮮度（[ADR-0044](../decisions/0044-acl-aware-search-and-index-freshness.md)）

### 7.1 流れ

```
Record Service の保存 → outbox：record.changed（record_id, version, 変わったフィールドの ID）
   → Relay → SQS（セルごと。テナントの公平のため tenant_id をメッセージのグループの鍵にはしない）
   → Indexer：
       1. 変わったフィールドが索引の対象でなければ捨てる
       2. DB の reader から今の行を読む（version も）。reader の遅れで version が古ければ、少し待って読み直す（最大 3 回。なお古ければ writer から読む）
       3. OpenSearch に index（version_type = external、version = 行の version）
          削除なら delete（同じく外部の版）
```

- **外部の版で、順序の逆転を防ぐ。** SQS の標準のキューは順序を保たず、同じレコードの 2 つの事象が逆に届きうる。OpenSearch は、今の文書の版より小さい版の書き込みを拒む（`version_conflict`）ので、古い版で新しい版を上書きしない。拒まれたら成功として捨てる。
- 事象の本文を索引に入れず、DB の今の行を読んで入れる。事象の重複・欠け・逆転があっても、最後の事象の処理で今の行になる。
- ナレッジは、版の状態が `published` になった・外れたことを事象にし、記事ごとに今の公開中の版を入れる（なければ消す）。
- 一括の処理（取り込み、`bulk_job`）の大量の事象は、Indexer が `_bulk`（最大 500 件・5 MB）でまとめる。テナントごとの取り分（1 回の `_bulk` の中の 1 テナントの割合を 50% まで）で、1 テナントの大量の更新が他のテナントの反映を待たせないようにする。

### 7.2 鮮度の目標

| 指標 | 定義 | 目標（案。正本は runbooks） |
| --- | --- | --- |
| 索引の遅れ | コミットの時刻から OpenSearch の反映（`refresh` の後、検索できる）まで | p95 5 秒、p99 30 秒 |
| 公開の遅れ（ナレッジ） | 版の公開のコミットから検索できるまで | p99 30 秒 |

- `refresh_interval` は 1 秒（既定）にする。書き込みが多い時間帯でも、検索できるまでの遅れを短くする。取り込みの一括の間は変えない（テナントの数が多く、1 テナントのための変更をしない）。
- 遅れは、Indexer が事象の中のコミットの時刻と、反映の完了の時刻の差を計測する（[observability.md](observability.md) の 3.2 節）。

### 7.3 突き合わせと作り直し

- **日次の突き合わせ**：テナントごとに、DB の `(id, version)` の抜き取り（1%、最大 1 万件）と、索引の同じ ID の外部の版を比べる。違いがあれば、その ID を入れ直し、件数を記録する。違いが 0.1% を超えたら SEV3。
- **作り直し**：新しい索引 `*_v{n+1}` を作り、DB から全件を入れ、その間の事象は両方の索引に書く（Indexer は別名ではなく、2 つの具体の索引に書く）。全件の入れ直しが済み、突き合わせで違いがなければ、別名を切り替え、古い索引を消す。
- 作り直しの速さは、1 セルで 1 秒 5,000 文書を目安にする（`task` 3,500 万件で約 2 時間。未検証。E9 で計測）。

## 8. 検索の語

- 検索の語は、運用のログに残さない（個人の情報や機微な語を含みうる）。ポータルの事象にも語を入れない（[knowledge.md](knowledge.md) の 7.3 節）。
- 「よく検索されるのに記事がない語」の分析は、語を集計した形（テナント・日ごとに、結果が 0 件だった語の上位 100 と回数。5 回未満の語は捨てる）で持つ。個人に結び付けない（持ち越し：E9 の後。法務の L1 の結論を見て）。

## 9. 障害のときの振る舞い

| 障害 | 振る舞い |
| --- | --- |
| OpenSearch のドメインの障害 | 検索は 503 にし、画面は「検索は一時的に使えません。番号での検索とリストの絞り込みは使えます」を出す。番号の完全一致は DB で引く。リスト・フォームは影響を受けない。SEV2 |
| Indexer の停止・SQS の滞留 | 検索の結果が古くなる。6.4 節の確かめ直しで、削除・権限の変更は結果に出ない。遅れが 5 分を超えたら SEV3 |
| DB の reader の遅れ | 確かめ直しは reader で行うので、reader が遅れると、直前に権限を与えられた行が出ないことがある（読めない行は出ない側に倒れる）。reader の遅れが 1 秒を超えたら、確かめ直しを writer で行う |
| AZ の障害 | 3 AZ のドメインで、残る 2 AZ のレプリカで続ける |
| リージョンの障害 | 大阪には小さな待機のドメインだけを置き、索引は複製しない。切り替えの後、`kb` と `catalog` を先に DB から作り直し（数分。ポータルの自己解決を先に戻す）、`task`・`ci`・`record` は後から作り直す（数時間。未検証）（[infrastructure.md](infrastructure.md) の 6 節）。作り直しの間は全体の検索が使えない |

## 10. セキュリティ

- テナントの分離は 2 重にする：問い合わせの必須の `tenant_id` の絞り込み（型で強制）と、DB（RLS の下）での確かめ直し。どちらか 1 つの誤りでは、他のテナントの行は返らない。
- ACL は、索引の近似の絞り込み（広めに取る）と、DB での確かめ直しの 2 段で効かせる。索引に ACL の規則を焼き込まない。
- 総数・ファセット・一致したフィールドの存在からの推測を閉じる（6.1・6.3 節）。
- 強調の断片は、今の版の本文だけから出す（6.4 節）。
- OpenSearch のドメインは VPC の中に置き、アクセスのポリシーで Indexer と App のタスクのロールだけに限る。保存の暗号化はセルの KMS の鍵（[security.md](security.md) の 5 節）。
- 検索の語を記録しない（8 節）。

### 11.2 性質ベーステスト（fast-check、Testcontainers の OpenSearch と PostgreSQL）

- **PROP-SRCH-001（検索は ACL を広げない）**：任意の ACL の規則・主体・レコード・語で、検索の結果の行の集合は、同じ主体のリストの出口で読める行の集合に含まれる。
- **PROP-SRCH-002（近似は読める行を落とさない）**：任意の行の述語で、索引の絞り込み F_os に合う行の集合は、行の述語に合う行の集合を含む。
- **PROP-SRCH-003（読めないフィールドだけの一致は出ない）**：任意のデータで、語が読めないフィールドの値にだけ含まれる行は、結果にも強調にも出ない。語が読めないフィールドにだけある 2 つのデータの集合で、結果は同じ。
- **PROP-SRCH-004（反映の順序）**：任意の保存の列と事象の重複・逆転・欠け（最後の事象は届く）で、最終の索引の文書の版は DB の行の版と等しい。
- **PROP-SRCH-005（テナントの分離）**：任意の 2 テナントで、一方の主体の検索が他方の文書を返さない（索引の絞り込みを外したビルドでも、DB の確かめ直しで返らない）。

- 4.1 節の解析器の評価（nDCG@10、再現率@20）。評価のデータは開発リポジトリに固定の版で置く。解析器の設定を変える PR は、評価の値が下がらないことを CI で確かめる（[delivery.md](delivery.md) の 2 節）。
