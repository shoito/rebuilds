# Delivery: ServiceNow

ブランチ、CI（決定表・性質・障害注入・漏れの試験の CI）、`security:sensitive` の変更、デプロイ（セルごとの段階）、リリースとフラグ（テナント・セルの単位の段階的なリリース）、DB とメタデータのマイグレーション、リリースの前の全テナントのメタデータのコンパイルの検査を決める。Slack・Auth0 の delivery.md を引き継ぎ、この題材に固有の 4 つを足す：**仕様（決定表・性質）から直接動く CI**、**障害注入の CI**、**セルを単位にしたデプロイ**、**テナントの設定（メタデータ）との互換の検査**。

| 対象 | 方針 |
| --- | --- |
| ブランチモデル | リポジトリ共通の [ADR-0002](../../../../docs/decisions/0002-trunk-based-development.md)（トランクベース開発） |
| 仕様から動く CI、障害注入、漏れの試験 | [ADR-0062](../decisions/0062-spec-driven-ci-fault-injection-and-leak-suite.md) |
| フラグとセル・テナントの段階的なリリース | [ADR-0063](../decisions/0063-flags-and-staged-release-per-cell.md) |
| マイグレーションとメタデータの互換の検査 | [ADR-0064](../decisions/0064-migrations-and-metadata-compatibility-check.md) |
| `security:sensitive` の変更 | [ADR-0051](../decisions/0051-threat-model-and-security-checklist.md) |
| AWS の CI/CD と Terraform の構成 | [infrastructure.md](infrastructure.md) の 7 節 |
| 手順 | [runbooks/deploy-and-rollback.md](../runbooks/deploy-and-rollback.md) |

原則は 4 つ。

- **`main` は常にデプロイできる状態に保つ。**
- **デプロイ（コードを置くこと）とリリース（振る舞いを有効にすること）を分ける。** デプロイは Ops が承認し、リリースは PM が判断する。全テナントは同じバージョンで動き、振る舞いの変更はフラグで出す（[ADR-0002](../decisions/0002-tenancy-and-isolation.md)）。
- **仕様の表と性質を、テストに書き写さずに CI で動かす**（[process.md](../../../../docs/process.md) の 6・7 節）。
- **テナントの設定を壊さない。** 新しいコードは、全テナントの今のメタデータ（辞書・ACL・フロー・画面の規則）をコンパイルできることを確かめてから出す。

## 1. 変更からマージまで

```
changes/YYMMDD-<slug>/ の spec・plan が承認済み
   ▼
ブランチ servicenow/YYMMDD-<slug>（エージェントは worktree ごとに 1 本）
   ▼
PR ─▶ パスで security:sensitive のラベルを自動で付ける（3 節）
   ▼
PR の CI（2 節）─▶ レビュー（CODEOWNERS、作成者と別の人。security:sensitive は 2 人）
   ▼
merge queue ─▶ squash で main へ
```

- 未完成の振る舞いは release フラグの裏に置く。
- PR の説明には、変更フォルダ、規模、使うフラグ、**`security:sensitive` に当たるか**、**マイグレーション（DB・組み込みの辞書・`engine_schema`）を含むか**、**ACL の出口を足すか**（足すなら漏れの試験と合成監視の対象を足したか）を書く。

### 1.1 リポジトリの中の区分

開発リポジトリは 1 つ（モノレポ）。

| パス | 中身 | コードオーナー |
| --- | --- | --- |
| `packages/record-service/`、`packages/acl/`、`packages/expr/`（式の言語） | 保存の流れ、判定と述語のコンパイラ、評価器 | Dev のテックリード＋セキュリティの担当（2 人） |
| `packages/sla-time/`、`packages/calendar/` | 計時の純粋な関数 | 領域のオーナー＋QA |
| `services/engine/`、`packages/flow/` | フロー・承認・タイマー | 領域のオーナー＋QA |
| `services/ingest/`（メール・CMDB・取り込み） | 差出人の信頼、識別と調整 | 領域のオーナー（差出人の信頼はセキュリティの担当も） |
| `services/notifier/`（Webhook の送信を含む） | 通知、署名、SSRF の検査 | 領域のオーナー＋セキュリティの担当 |
| `builtin/`（組み込みの辞書・ACL の規則・状態のモデル・配置・文言の辞書） | コードのバージョンの定義 | 領域のオーナー＋QA |
| `migrations/` | DB のマイグレーション | Dev のテックリード |
| `infra/` の KMS・IAM・WAF・ルーターの関数 | 鍵と境界の IaC | Ops＋セキュリティの担当 |
| `infra/`（その他） | IaC | Ops |

## 2. CI（[ADR-0062](../decisions/0062-spec-driven-ci-fault-injection-and-leak-suite.md)）

### 2.1 PR の CI

Slack・Auth0 の delivery.md の段（lint、型、単体、結合、E2E のスモーク、依存・イメージ・IaC の検査）をすべて持ち、次を足す。目標は 25 分以内。

| 段 | 内容 | 失敗の条件 |
| --- | --- | --- |
| 決定表のテスト | `specs/` と進行中の `changes/` の `spec.md` の決定表（`DT-*`）を読み込み、各行を 1 ケースとして動かす。テストの名前は `DT-XXX-NNN #行` | 1 行でも失敗。表の最後の行（既定の拒否・網羅の確かめ）のケースがない |
| 否定の表 | 状態の遷移の表（DT-INC-001、DT-FLOW-002 など）にない組をすべて作り、状態が変わらないこと | 1 件でも |
| 性質ベーステスト（PR） | 変更に関わる `PROP-*` を fast-check で 200 回。失敗の種（seed）と縮めた反例を PR に出す | 1 件でも |
| 障害注入（短） | 変更が `services/engine/`・`packages/record-service/`・`services/ingest/` に触れるとき、名前付きの障害の点（[workflow-engine.md](workflow-engine.md) の 12.3 節）で `SIGKILL` を入れ、遷移の欠落・二重 0 を確かめる（障害の点ごとに 20 回） | 1 件でも |
| 漏れの試験（変更した出口） | 変更が ACL の出口（16 の出口、[access-control.md](access-control.md) の 6.2 節）に触れるとき、その出口の漏れの試験 | 「漏れの印」が 1 件でも |
| テナントの分離 | 任意の 2 テナントの性質ベーステスト、NULL の行の書き込みの拒否（[ADR-0054](../decisions/0054-shared-reference-rows-and-cross-tenant-roles.md)） | 1 件でも |
| 追跡 | `specs/`・進行中の `changes/` のすべての `REQ-*`・`PROP-*`・`DT-*` と、[security.md](security.md) の `SEC-*` が、どこかのテストの名前から参照されている。ID の重複がない | 参照の漏れ、重複 |
| 計時の参照の実装 | 計時の関数を変えたとき、1 分ごとの素朴な参照の実装と、10 万の生成したケースで秒の単位で一致（[ADR-0019](../decisions/0019-business-calendar-and-pure-time-functions.md)） | 1 件でも |
| 検索の評価 | 解析器・問い合わせの組み立てを変えたとき、評価のデータの nDCG@10・再現率@20 が下がらない（[search.md](search.md) の 11.3 節） | 下がる |
| 組み込みの定義の検査 | `builtin/` の変更で、組み込みの ACL の規則がすべて述語にコンパイルでき、`deny_unless` の規則が消えていない。文言の辞書の `ja`・`en` のキーが等しい | 違反 |
| 純粋さの lint | 計時・衝突・識別・当番の関数のモジュールが、時計・DB・キャッシュを読み込まない。式の評価器に副作用のある組み込みの関数がない | 違反 |
| マイグレーション | 新しいテーブルに `tenant_id` と RLS のポリシー（NULL の行の許可の一覧の外は NOT NULL）、時間で消える表は時間のパーティション、追記だけの表にアプリのロールの `UPDATE`・`DELETE` がない | 違反 |
| テストのデータ | テスト・フィクスチャー・シードに、本物の個人情報の形（許可したテスト用のドメインの外のメールアドレス、実在の機器のシリアル番号の形の一覧） | 1 件でも |
| インフラ（`infra/` の変更時） | `fmt`、`validate`、tflint、Checkov、`plan`、plan のポリシー検査、`cells.yaml` と台帳の突き合わせ | 違反、状態を持つリソースの削除・置き換え |

- **決定表をテストに書き写さない。** 表の読み込みの道具（`spec-table-loader`）が `spec.md` の Markdown の表を読み、条件の列と結果の列を型付きのケースにする（[AGENTS.md](../../AGENTS.md)）。
- 性質ベーステストの失敗は、種と縮めた反例を `quality/regressions/` に固定のケースとして残す（次から常に動く）。

### 2.2 夜間の CI

- 性質ベーステストの長いバージョン（`PROP-*` ごとに 1 万回）。
- 障害注入の全体：すべての障害の点 × 200 回、DB の接続の切断、Testcontainers の PostgreSQL の再起動（Aurora のフェイルオーバーの代わり）。
- 漏れの試験の全体：16 の出口 × 組み込みのテーブル × 組み込みのロール。
- E2E の全体（`ja`・`en`、アクセシビリティの自動の検査）。
- staging に対する DAST と、負荷試験の短いバージョン（タイマーの山の 1/10）。

夜間の CI が 2 日続けて失敗している間は、release フラグを広げない。

### 2.3 staging の検証（デプロイの前）

- staging の 2 つのセルへデプロイし、E2E、スモーク、k6 の短い負荷、Aurora の実際のフェイルオーバー（週 1 回）を通す。
- リリースの前のメタデータのコンパイルの検査（4 節）を staging で通す。

## 3. `security:sensitive` の変更

[ADR-0051](../decisions/0051-threat-model-and-security-checklist.md) の要点。

| 項目 | 規則 |
| --- | --- |
| パス | ACL の判定と述語のコンパイラ、式の評価器、Record Service の保存の流れ、RLS とマイグレーションの検査、監査の履歴、承認、成り代わり、SSO、メールの差出人の信頼、Webhook の送信と SSRF の検査、KMS・IAM・WAF・ルーターの関数の Terraform。`.github/security-sensitive-paths.yml` に書く |
| 承認 | Dev のテックリードとセキュリティの担当の 2 人。どちらも作成者と別。エージェントの PR でも同じ |
| 事後の確認の例外 | 使わない（リポジトリ共通の [ADR-0004](../../../../docs/decisions/0004-agent-prs-via-github-app.md) の例外を当てない） |
| 追加の CI | 漏れの試験の全体、テナントの分離の長いバージョン |
| リリース | release フラグの裏に置き、テナントのカナリア（6 節）で広げる。権限を広げる方向の変更は、フラグの既定を旧い振る舞いにし、PM とセキュリティの担当が広げる |

## 4. マイグレーションとメタデータの互換（[ADR-0064](../decisions/0064-migrations-and-metadata-compatibility-check.md)）

### 4.1 DB のマイグレーション

- 他の題材と同じく、expand → 移行 → contract の 3 つのリリースに分ける。contract は、前のリリースで参照をやめた後だけ。
- マイグレーションは 1 回だけ実行する ECS タスク（`migrator`）で、セルごとに行う（デプロイの段の順。5 節）。
- 大きな表（`task`、`record_change`、`ci`）への列の追加は、既定値のない NULL の列だけを expand で行う。索引の追加は `CREATE INDEX CONCURRENTLY`。値の埋め戻しは `bulk_job` で、テナントごとに分けて行う。

### 4.2 組み込みの定義の変更

組み込みの辞書・ACL の規則・状態のモデル・配置・文言は、コードのバージョンに持つ（[ADR-0006](../decisions/0006-data-dictionary-and-field-types.md)、[ADR-0022](../decisions/0022-process-state-machines.md)）。

| 変更 | 扱い |
| --- | --- |
| 組み込みのフィールドの追加 | 列の追加（expand）と定義の追加を同じリリースで。画面・API に出すのはフラグで |
| 組み込みのフィールドの削除・型の変更 | しない（新しいフィールドを足し、古いものを非表示にして、2 つ後のリリースで消す） |
| 組み込みの ACL の規則の変更 | 権限を狭める方向は、フラグの裏でテナントのカナリアで広げる。広げる方向は `security:sensitive` |
| 状態のモデルの辺の追加 | フラグの裏で。辺の削除は、その辺を通る動いているレコードがないことを確かめてから |
| 組み込みの文言の変更 | `ja`・`en` を同じ PR で |

### 4.3 リリースの前のメタデータのコンパイルの検査

新しいコードのバージョンで、全テナントの今のメタデータが読めることを、デプロイの前に確かめる。読めないと、そのテーブルの全操作が拒否になる（ACL の規則。[access-control.md](access-control.md) の 10 節）か、既定の配置になる（[portal-and-ui.md](portal-and-ui.md) の 9 節）。

```
各セル（本番を含む）で、新しいイメージの「検査のタスク」を 1 つ動かす（トラフィックを受けない）
  1. 全テナントの今の meta_version のメタデータを読む（reader、テナントごとにコンテキストを設定）
  2. 新しいコードで、辞書・ACL の規則（述語へのコンパイル）・画面の規則・配置・フロー（DT-FLOW-001）・
     SLA の定義・カレンダー・変換の対応・通知のテンプレートをコンパイルする
  3. 結果（テナント・オブジェクトの ID・エラーのコード。値は出さない）を報告する。何も書かない
失敗が 1 件でもあれば、そのセルのデプロイを止める
```

- 本番のメタデータを本番のアカウントの外に出さない（[infrastructure.md](infrastructure.md) の 8 節）ので、検査は各セルの中で行う。
- 失敗は、(1) コードの誤り（直す）、(2) 古いメタデータを新しいコードが読めない意図した変更（移行のジョブをリリースに含める）、のどちらか。(2) は `engine_schema` のように古い意味を残すか、移行のジョブで直す。

### 4.4 フローの意味の変更

- フローのノードの振る舞いを変える変更は、`engine_schema` を上げ、古い `engine_schema` のバージョンは古い意味で動かす（[ADR-0014](../decisions/0014-flow-dsl-and-versioning.md)）。コードは両方の意味を持つ。
- 古い `engine_schema` のコードを消すのは、そのバージョンで動いている実行が 0 になり、そのバージョンのフローのバージョンが公開の対象でなくなった後（数か月の変更の実行があるので、長く残る）。

## 5. デプロイ

### 5.1 セルの段

```
main ─▶ dev（自動）─▶ staging（自動。E2E・スモーク・k6・メタデータのコンパイルの検査）
   ─▶ prod：
      1. control（制御の面）、mail-ingress
      2. cell-s01（カナリアのセル。監視用のテナントと、社内のテナントを多く置く）
      3. 60 分の観察 ─▶ cell-s02 ...（共有のセル。S2 からは 25% ずつ）
      4. 専用のセル（最後。顧客の知らせた繁忙の時間を避ける）
   各段で Ops が承認する。1 つの段で 5 節の 3 の指標が悪化したら、次の段へ進まない
```

- **デプロイの時間帯**：平日の 13〜17 時。平日 8:30〜10:30（9 時の山）、月末の最後の 2 営業日、期末（3 月 25 日〜4 月 5 日、9 月 25 日〜10 月 5 日）、年末年始は、修正以外のデプロイをしない。
- エラーバジェットを使い切っている間は、修正以外のデプロイをしない。

### 5.2 セルの中の順序

| 順 | 対象 | 方式 |
| --- | --- | --- |
| 1 | メタデータのコンパイルの検査（4.3 節） | 検査のタスク。失敗なら止める |
| 2 | マイグレーション（expand） | `migrator` のタスク |
| 3 | relay、indexer、notifier、notifier-egress、ingest | ローリング（`minimumHealthyPercent` 100%） |
| 4 | engine | ローリング。古いタスクは処理中のトランザクションを終えてから止まる（タイマーは `SKIP LOCKED` なので、新旧が並んでも二重にならない） |
| 5 | app | ECS の blue/green のカナリア（要求の 10% → 100%）。アラームで自動のロールバック |

- engine の新旧が並ぶ間、同じフローの実行を新旧のタスクが続けて進めうる。フローの意味の変更は `engine_schema` で分けるので、同じバージョンの実行を新旧のコードが違う意味で進めない。
- app の blue/green の自動のロールバックのアラームには、5xx の率に加えて、**保存の 422・403 の率（遷移・ACL の誤りの兆し）、タイマーの遅れ、本番の漏れの合成監視の検出**を入れる。新しいコードが判定を壊したとき、5xx が出なくても止められる。
- 新旧の画面の束と API の互換を 1 つ前のバージョンまで保つ（[portal-and-ui.md](portal-and-ui.md) の 3 節）。

## 6. リリース（[ADR-0063](../decisions/0063-flags-and-staged-release-per-cell.md)）

### 6.1 フラグの段

```
デプロイ済み（フラグ無効）
   │ QA：staging でフラグを有効にし、Proof を満たすことを確かめる
   ▼
社内のテナント・監視用のテナント（全セル）
   ▼
サブプロダクションのテナントの 100%（最低 7 日。顧客の開発・検証の環境で先に気づく）
   ▼
本番のテナント：cell-s01 の 10% → cell-s01 の 100% → 全共有のセルの 50% → 100%（各段で最低 24 時間）
   ▼
専用のセルの本番のテナント（顧客の選んだ時期。6.2 節）
   ▼
100% で 2 週間 ─▶ 古いコードとフラグを消す
```

- 判定は `hash(flag_name + tenant_id) mod 100`。同じテナントの要求は常に同じ側。フラグは AppConfig で、セルとテナントの両方の条件を持てる（[architecture/README.md](README.md) の 4 節）。
- 同じ顧客の本番とサブプロダクションのテナントは、サブプロダクションを先にする（上の段の順で自然にそうなる）。

### 6.2 顧客が時期を選べる振る舞いの変更

- 業務の画面・流れ・通知の文面が変わる振る舞いの変更（[ADR-0002](../decisions/0002-tenancy-and-isolation.md) の「振る舞いの変更のフラグの切り替えの時期を、決めた期間の中で選ばせる」）は、**「選べる変更」**の印を付ける。
- 選べる変更は、本番の段に入ってから最大 60 日、テナントの管理者が有効にする日を選べる（既定は段の予定どおり）。60 日を過ぎると全テナントで有効にする。
- 選べるのは有効にする時期だけで、コードのバージョンは選べない。セキュリティの修正と、正しさの修正（SLA の計算の誤りなど）は選べる変更にしない。

### 6.3 ガード

フラグの有効なテナントと無効なテナントを比べ、差が続いたら AppConfig のアラームでフラグを自動で切る。

| ガード | 条件 |
| --- | --- |
| 保存の失敗 | 保存の 422・403 の率が無効な側の 2 倍、15 分 |
| タイマー | 期限を過ぎた未発火の違反が有効な側で 1 件以上 |
| 正しさの監視 | 本番の漏れの合成監視の検出（フラグによらず即時。デプロイの段を止める） |
| 可用性 | フラグの有効なテナントの 5xx が 0.1% を超える |
| 画面 | フォームのサーバーの p99 が無効な側の 1.5 倍、15 分 |

| 判断 | 誰が |
| --- | --- |
| staging での受け入れ | QA |
| 社内 → サブプロダクション → cell-s01 の 10% | PM |
| cell-s01 の 100% → 全体 | PM と Ops |
| 権限を広げる方向の変更の各段 | PM とセキュリティの担当 |
| 止める・戻す | 誰でもよい |

## 7. ホットフィックス

- まずフラグで止め、修正は `main` への PR で入れる（forward fix）。フラグで止められず修正も間に合わないときは、1 つ前のイメージで再デプロイする（セルごと）。マイグレーションは戻さない。
- **テナントの分離の破れ・ACL の漏れ・監査の改ざん・承認の偽り**の修正は、デプロイの時間帯の制限を受けない。ただし、2 人の承認、漏れの試験、テナントの分離の試験は省かない。セルの段は、カナリアのセルの観察を 15 分に縮めてよい。
- 脆弱性の修正は、公開の前に PR の説明とコミットメッセージに攻撃の詳細を書かない。
