ServiceNow は何をするサービスか

ServiceNow は、企業の IT 部門が受ける障害の報告と依頼を 1 つの記録にまとめ、誰が・いつまでに・何をするかを管理する SaaS です。この分野を ITSM（IT サービス管理）と呼びます。

サービスデスク

電話・メール・ポータルで受けた障害と依頼を、分類し、担当のグループに割り当て、解決する。

運用・開発のチーム

繰り返す障害の原因を調べ、本番の変更を計画し、承認を得て実施する。

社員（依頼者）

ポータルで PC やアカウントを申請し、自分のチケットの状況を見る。IT に詳しくない前提。

ほかに、変更を承認する人、設定をする管理者、証跡を確かめる監査の担当がいます。再構築の S1 の規模は、テナント 300（本番 100）、社員 100 万人、担当者 3 万人、チケットの作成 20 万件/日です。平日の 9 時に SLA の期限とタイマーが一斉に来る、という偏りも設計の前提です。

設計の文書で効くところintent.md の「Affected users and systems」と MVP の範囲、architecture/README.md の 2 節「規模の段階」。

アプリの下にある「記録の基盤」

ServiceNow の特徴は、ITSM のアプリが汎用の記録の基盤の上に載っていることです。インシデントも変更も、基盤から見れば「テーブルの 1 行」にすぎません。

記録の基盤

データ辞書（テーブルとフィールドの定義）、フォームとリスト、ACL、ワークフロー、通知、レポート、REST API、監査の履歴。

ITSM のアプリ

インシデント・問題・変更・要求・ナレッジ・CMDB・SLA。基盤の上の「テーブルの定義 ＋ 状態の流れ ＋ 既定の設定」の束。

管理者は、画面でフィールド・テーブル・フォーム・承認・SLA を足します。つまり振る舞いの多くがコードではなくメタデータで決まります。本家はここにスクリプト（サーバーで動くコード）も書かせますが、再構築ではテナントに任意のコードを書かせず、ノーコードの設定だけにします。

要点設計の文書の「メタデータが振る舞いを決める」「Record Service がすべての書き込みの唯一の入口」は、この 2 層の構造を自前で作るための原則です。
設計の文書で効くところarchitecture/README.md の 1.2 節の原則、ADR-0001（スクリプトの API と互換にしない）。

ITIL：インシデント・問題・変更・要求の違い

ITIL は IT サービス管理の実務の型をまとめた枠組みです。ITIL 4 は 34 のプラクティスを持ち、この題材はそのうちインシデント・問題・変更・サービス要求などの業務を作ります。言葉が日常語と少し違うので、まずここをそろえます。

計画外のサービスの中断や品質の低下。例：「メールが送れない」。目的は早く元に戻すことで、原因の究明ではありません。再起動での回復も立派な解決です。

1 つ以上のインシデントの原因（または原因になりうるもの）。例：「メールサーバーのディスクが毎週あふれる」。根本原因を調べ、恒久の対策につなげます。原因が分かり回避策がある状態を既知のエラーと呼びます。

サービスに影響しうるものの追加・修正・削除。例：「メールサーバーのディスクを増設する」。リスクを評価し、権限のある人の承認を得てから実施します。

障害ではない、決まった手順で応える依頼。例：「新しい PC がほしい」「パスワードを再設定したい」。カタログから選んで申請し、承認と作業で応えます。

flowchart LR
  I1[インシデント] --> P[問題]
  I2[インシデント] --> P
  P -- 恒久の対策 --> C[変更]
  P -- 回避策 --> K[既知のエラーの記事]
  R[サービス要求] -.別の流れ.-> F[実行のタスク]

同じ VPN の切断が今週 5 回起き、そのたびに再接続で直しています。原因を調べる作業は、どの記録で追いますか？

インシデントは「戻すこと」が目的で、再接続で解決済みです。原因の調査は問題として起票し、インシデントを結びます。対策でルーターの設定を変えるなら、それは問題から作る変更です。

設計の文書で効くところitsm-processes.md の 1 節（扱う範囲）、intent.md の Constraints（ITIL 4 の用語を使う）。

インシデントの流れと優先度

インシデントは、受け付けから完了まで決まった状態を進みます。「解決」と「完了」を分けるのが ITSM の習慣です。

  1. 新規：ポータル・メール・API・担当者の入力で受け付ける。割り当ての規則が担当のグループを決める。
  2. 対応中：担当者が着手する。
  3. 保留：依頼者の回答待ち・ベンダー待ちなど、理由を付けて止める。理由で SLA を止めるかが変わる。
  4. 解決：担当者が直した。依頼者の確認を待つ。一定の期間（既定 7 日）がたつと自動で完了。
  5. 完了：終わり。再オープンはしない（新しく起票して結ぶ）。

優先度は人が選ぶ値ではありません。影響度（どれだけ広く効くか）と緊急度（どれだけ急ぐか）の表から導きます。

影響度＼緊急度1 高2 中3 低
1 高1 緊急23
2 中234
3 低344

この 3 × 3 は本家の既定と同じ形です。優先度を直接書き換えるには、専用のロールと理由が要ります（上書き）。

設計の文書で効くところitsm-processes.md の 4 節（DT-INC-001）と 5 節（DT-PRIO-001・002）、ADR-0022、ADR-0023。

メジャーインシデント・問題・既知のエラー

メジャーインシデント

全社のメールが止まった、のような重大な障害。宣言すると当番の呼び出し・経営への連絡・定期の状況の更新が始まる重い判断なので、規則は候補を作るだけで、昇格は人が決めます。

親子のインシデント

同じ障害の報告が何百件も来たら、1 件を親にして残りを子に結ぶ。親を解決すると子もまとめて解決します。

問題と RCA

問題は「評価 → 根本原因の分析 → 修正中 → 解決」と進む。根本原因の分析の結果、恒久の対策は変更として実施します。

回避策が分かったら、原因が不明でも既知のエラーにでき、その記事をナレッジに公開してサービスデスクが使います。

根本原因を調査中ですが、回避策は分かりました。再構築の設計で、この問題はどう表しますか？

既知のエラーを状態にすると「修正中だが既知のエラー」を表せません。そのため状態ではなく印（known_error）にし、条件は回避策があることだけです。本家の今のモデルも状態に持ちません。

設計の文書で効くところitsm-processes.md の 6・7 節、knowledge.md の 5 節（既知のエラーの記事）。

変更：種類・リスク・CAB

本番の変更は障害の大きな原因なので、ITIL は種類ごとに承認の重さを変えます。

手順が決まり、リスクの低い、繰り返す変更（例：決まった手順のパッチ）。雛形を一度承認すれば、個々の変更は承認を通らない。雛形の承認が証跡になります。

リスクを評価し、技術の承認（担当のグループの管理者）と、リスクに応じて変更の管理者または CAB の承認を経て実施します。

障害の復旧などで待てない変更。ECAB の承認で進め、実施の後に CAB の事後の承認を完了の条件にします。

  1. 新規：対象の CI、予定の時刻、実施・切り戻し・テストの計画を書く。
  2. 評価：リスクを規則と質問票で求め、高いほうを採る。
  3. 承認：種類 × リスクの決定表で、誰の何段の承認かが決まる。
  4. 予定済み：禁止期間や他の変更との衝突を確かめる。
  5. 実施 → 振り返り → 完了：結果（成功・失敗）を残す。振り返りと完了は取り消せない。

深夜の障害で、緊急の変更をすぐ実施したい。CAB は朝まで集まれません。設計ではどうなりますか？

intent の「変更の記録は、承認のないまま実施に進まない」を守るため、どの種類も承認なしに実施へ入れません。変更のテーブルでは期限切れの自動の承認も選べません。

設計の文書で効くところitsm-processes.md の 8・9 節（DT-CHG-001〜003、DT-RISK-001）、ADR-0024、ADR-0025。

サービスカタログ・要求・ナレッジ

社員はポータルのカタログから品目を選び、変数（入力の項目）に答えて申請します。1 回の申請（カート）は、3 段の記録になります。

flowchart LR
  REQ["要求（request）
1 回の申請"] --> RI1["要求の品目
ノート PC × 1"]
  REQ --> RI2["要求の品目
モニター × 2"]
  RI1 -- 実行のフロー --> T1["実行のタスク
キッティング"]
  RI1 -- 実行のフロー --> T2["実行のタスク
配送"]
  RI2 -- 実行のフロー --> T3["実行のタスク"]
  • 品目ごとに承認とタスクの流れ（実行のフロー）が違うので、要求の品目が単位になる。
  • 要求の状態は自分では持たず、子の要求の品目の状態から導く。
  • 申請の前に、入力に合うナレッジの記事を見せて自分で解決してもらう（自己解決）。その割合が K8 の指標。

ナレッジの記事はバージョンを持ち、レビューと承認を経て公開します。承認者が見た本文と公開する本文を同じにするため、レビューに出したバージョンの本文は変えません。

SLA・OLA・UC と計時

SLA は「この種類のインシデントには 4 業務時間以内に応答する」のような約束です。誰との約束かで呼び名が変わります。

種類約束の相手例
SLAサービスの利用者（社員・顧客）P1 の解決は 4 時間
OLA社内のチーム どうしネットワークのチームは 2 時間で調査
UC外部の事業者保守のベンダーが翌営業日に部品交換

1 つのインシデントに、応答・解決・OLA など複数の計時が並行して動きます。計時は開始・一時停止・停止の条件で進みます。

stateDiagram-v2
  [*] --> in_progress : 開始の条件
  in_progress --> paused : 一時停止の条件
  paused --> in_progress : 再開
  in_progress --> completed : 停止の条件
  paused --> completed : 停止の条件
  in_progress --> cancelled : 取り消し・リセット
  paused --> cancelled : 取り消し・リセット

期限を過ぎると「違反」の印が立ちますが、計時は停止まで続きます。期限の 50%・75% で警告を出すのが既定です。

担当者がインシデントを「保留（ベンダー待ち）」にしました。組み込みの既定で、依頼者向けの解決の SLA と、担当のグループの OLA はどうなりますか？

ベンダー待ちは IT の側の都合なので、依頼者との約束（SLA）は止めません。SLA を止めるのは依頼者の回答待ちと解決だけです。担当のグループの OLA は、ベンダー待ちがグループの責任の外なので止めます。

設計の文書で効くところsla-and-calendars.md の 6・7 節（DT-SLA-001・002）、itsm-processes.md の 4.4 節、ADR-0021。

業務カレンダーと日本の祝日

SLA の「4 時間」は、たいてい業務時間で数えます。期限は業務カレンダー（営業時間・タイムゾーン・祝日・会社の休日）から計算します。

  1. カレンダー：平日 9:00〜18:00、Asia/Tokyo、国民の祝日、会社の休日 12/29〜1/3（テナントの既定）。
  2. 2026-09-18（金）17:00 に、業務時間 4 時間の SLA が始まる。金曜に 1 時間を使う。
  3. 19・20 日は週末。21 日は敬老の日、23 日は秋分の日、その間の 22 日は国民の休日。
  4. 残り 3 時間を 24 日（木）の 9:00 から数え、期限は 24 日 12:00。カレンダーなしなら 18 日 21:00。
  • 祝日が日曜に当たると、後の平日が振替休日になる。内閣府の CSV では、振替休日も国民の休日も名称が「休日」。
  • 内閣府の CSV は翌年の分までを収録し、翌々年の分は前年の 2 月ごろに載る。収録の外の日付は祝日なしで計算し、後で計算し直す。
  • 計算し直しで期限が後ろに動いても、すでに起きた違反は取り消さない（breach_disputed として別に数える）。
法務の確認待ち（L9）内閣府の祝日の CSV を全テナントの SLA の計算に使い、原本を保存してよいか（公共データ利用規約の当てはめ、出典の表示の仕方）。確認が済むまで E5 の祝日の取り込みの spec を承認しません。
設計の文書で効くところsla-and-calendars.md の 3〜5・8 節、ADR-0019（純粋な関数 addBusinessTime）、ADR-0020。

CMDB：CI・関係・サービスのモデル

CMDB は、サーバー・PC・ネットワーク機器・クラウドの資源・アプリ・サービスの台帳です。1 つ 1 つを CI（構成アイテム）と呼び、CI どうしを関係で結びます。

flowchart TB
  BS["ビジネスのサービス
経費精算"] -- contains --> BSO["サービスの提供
経費精算・本社向け"]
  BSO -- depends_on --> SI["サービスのインスタンス
経費精算・本番"]
  SI -- depends_on --> DB["DB のインスタンス"]
  APP["アプリのサーバー"] -- runs_on --> SV["Linux のサーバー"]
  SI -- depends_on --> APP
  DB -- runs_on --> SV
  • 影響の範囲：Linux のサーバーが落ちると、関係を逆にたどって「経費精算」が影響を受けると分かる。変更のリスクやメジャーインシデントの判断に使う。
  • CI にはクラスの階層がある（ci → hardware → computer → server → linux_server）。
  • サービスの形は、本家の CSDM の考え方に寄せる（ビジネスのサービス・その提供・サービスのインスタンス）。名前と範囲は再構築のもの。
設計の文書で効くところcmdb-and-reconciliation.md の 3・7〜9 節、ADR-0039。

識別と調整：取り込み元が食い違うとき

CI の情報は、手入力・CSV・クラウドの API・資産管理のツールなど複数の取り込み元から届きます。同じサーバーが別の名前で届くこともあります。そこで 2 段で処理します。

  1. 識別：届いたものが既存のどの CI かを、クラスごとの規則で探す。例：シリアル番号 ＋ メーカー → BIOS の UUID → MAC → FQDN の順。値は正規化する（00:1A:2B… と 001a2b… を同じに）。
  2. 一致がなければ新しい CI を作る。2 つ以上の CI に一致したら推測で選ばず、保留にして人が統合する。
  3. 調整：一致した CI の属性ごとに、どの取り込み元の値を採るかを、取り込み元の優先度と鮮度で決める。

強い取り込み元 H が 1 日目に値 x、弱い取り込み元 L が 40 日目に値 y を観測しました（鮮度 30 日）。L の報告が先に、H の報告が後に届きました。属性の値は？

鮮度は届いた時刻ではなく、観測の時刻で測ります。取り込み元ごとの最新の観測を持ち、その集合から純粋な関数で選ぶので、届く順によらず y になります（NFR-005）。

設計の文書で効くところcmdb-and-reconciliation.md の 4〜6 節（DT-CMDB-002）、ADR-0037、ADR-0038（ADR-0005 の調整の表を置き換えた）。

継承するテーブルとデータ辞書

ServiceNow のテーブルは、オブジェクト指向のクラスのように親を継承します。インシデント・問題・変更・要求は、どれも task（作業）の子です。

flowchart TB
  task --> incident
  task --> problem
  task --> change
  task --> request
  task --> request_item
  task --> catalog_task
  task --> change_task
  task --> c_facilities_request["c_facilities_request
（テナントのクラス）"]
  • 子は親のフィールド・ACL・ルール・SLA の対象を引き継ぐ。「担当のグループ」「番号」「状態」はすべての作業に共通。
  • テナントはフィールドや子のクラスを足せる。名前は c_ で始める。
  • 再構築では、task の階層を 1 つの物理の表に置き、組み込みのフィールドは型付きの列、テナントのフィールドは JSONB の ext に入れる。DDL は発行しない。
  • レコードのクラスは作成の後に変えない。番号（INC… など）は一意だが欠番はありうる。
設計の文書で効くところdata-dictionary-and-tables.md の 3・4 節、ADR-0003、ADR-0006、ADR-0007。

ロールと ACL：テーブル・行・フィールド

ITSM では、同じインシデントでも見せてよい範囲が人で違います。依頼者には作業メモを見せない、人事の案件は人事のグループだけ、などです。ACL はこれをテーブル × 操作（作成・読み取り・書き込み・削除）の規則で書きます。

行の規則

そのレコードを読めるか。例：「依頼者は自分が依頼したものだけ」。

フィールドの規則

その項目を読めるか。行が読めても、作業メモや原価は読めないことがある。

  • 規則は 2 種：deny_unless（満たさなければ拒否）と allow_if（満たせば許可）。
  • クラスの継承に沿って探す。拒否は親のすべての段で効き、許可は最も近い段の規則を使う。
  • 許可の規則がなければ拒否（既定の拒否）。本家は規則がなければ許可が既定で、設定で拒否に変える。
  • 読めない値は、その人にとって NULL として扱う。並べ替えや件数からも推測させない。出口（フォーム・リスト・レポート・検索・通知・API など）は 16 あり、すべて同じ判定を通す。

ある人が読めないフィールド「原価」で、リストを並べ替えようとしました。どうなりますか？

本当の値で並べると、並び順から値を推測できます。絞り込み・並べ替え・集計はすべて visible(f) の上で行います（ADR-0012）。

設計の文書で効くところaccess-control.md の 4・6 節（DT-ACL-001〜003）、ADR-0011、ADR-0012。テナントの分離は共通の資料へ。

ワークフロー・承認・タイマー

管理者は「レコードが作られたら → 条件 → 承認 → タスク → 通知 → 待ち」をノーコードのフローとして組みます。承認には決まった規則があります。

規則承認に決まる条件
any誰か 1 人が承認
all全員が承認（1 人の却下で却下）
all_responded_any_approves全員が回答し、1 人以上が承認
percent(p) / count(k)p% 以上 / k 人以上が承認（CAB は 50%）
  • 代理：不在の承認者の代わりに答えられる人。誰が答えたかは記録に残す。
  • 職務の分離：依頼した本人は承認できない。変更のテーブルでは外せない。
  • メールの返信での承認は受けない（差出人の本人性を保証できないため）。
「ちょうど 1 回」2 人が同時に最後の承認を押しても、SLA の違反のタイマーが障害の後に再実行されても、状態は 1 回だけ進みます。遷移・タイマー・outbox を 1 つのトランザクションで書き、行のバージョンで守ります（NFR-004、K3）。
設計の文書で効くところworkflow-engine.md の 3・5・7 節（DT-APR-001）、ADR-0004、ADR-0015、ADR-0016。

受け付け：メール・割り当て・当番

日本の企業では、今も多くの依頼がメールで来ます。サービスデスクの宛先に届いたメールから起票し、返信を同じチケットに追記します。

  • スレッドの紐付け：In-Reply-To・References のヘッダー → 送ったメールに入れた推測できない参照の印 → 件名の番号（関係者だけ）の順で探す。
  • ループの防止：不在の返信や監視のアラートに自動の返信を返すと、メールが往復し続ける。Auto-Submitted などのヘッダー（RFC 3834）で見分け、応答しない。
  • 文字コード：ISO-2022-JP・Shift_JIS・ラベルのない 8 ビットの本文を復号する。送るメールは UTF-8。

起票すると、割り当ての規則（カテゴリ・CI・場所などの条件）が担当のグループを決め、必要なら順番・受け持ちの少ない順・スキルで担当者を選びます。人が入れた割り当ては上書きしません。業務時間の外の P1 などでは、当番を呼び、応答がなければ次の段へエスカレーションします（MVP の経路はメールとプッシュ）。

法務の確認待ち（L2・L8）メールの受信と自動の処理が電気通信事業法の「他人の通信の媒介」に当たるか（L2、E6 の spec を止める）。SMS・音声での呼び出しの契約と法令（L8、MVP の後）。
設計の文書で効くところnotifications-and-email-ingest.md の 5〜7 節、assignment-and-on-call.md の 3〜6 節、ADR-0034、ADR-0035。

監査と法令の枠組み

ITSM の記録は、顧客の内部統制の証跡にもなります。設計の文書が前提にしている枠組みだけを示します。法的な判断はしません。

J-SOX と IT 全般統制

上場企業の財務報告に関わる内部統制の制度。IT 全般統制では、本番の変更が承認されてから行われたか、権限を誰に与えたかの証跡を監査人が確かめます。

監査の履歴

フィールドごとに「誰が・いつ・何を何に」を、変更と同じトランザクションで追記だけの表に残す。利用者は消せない。

個人データ

チケットには社員の氏名・連絡先・端末・本文が入る。削除の請求と、消せない監査の履歴が衝突しうる。

法務の確認待ち個人情報保護法での立場（委託かどうか）と漏えいの報告（L1）、データを国外に出さない約束の範囲（L3）、監査の履歴の保持の期間（既定案 7 年）と出力の形式（L4）、契約（L5）、「ITIL」の名前の使い方（L6。ITIL は AXELOS Limited の登録商標）、本家からの移行の道具（L7）。結論が出るまで、関係する spec を承認しません。
設計の文書で効くところintent.md の「法務の確認待ち」L1〜L9、ADR-0009、ADR-0053、security.md の 9・14 節。

用語集

ITSM
IT Service Management。IT を「サービス」として利用者に提供し、障害・依頼・変更などを管理する実務。
ITIL
IT サービス管理の実務の枠組み。ITIL 4 は 34 のプラクティスを持つ。ITIL は AXELOS Limited の登録商標。
インシデント
計画外のサービスの中断や品質の低下。早く元に戻すことが目的。
問題
1 つ以上のインシデントの原因、または原因になりうるもの。
既知のエラー
分析が済み、回避策が分かっているが、まだ恒久に解決していない問題。再構築では問題の印として持つ。
回避策
原因を取り除かずに、インシデントの影響を減らす・なくす手段。
根本原因の分析
RCA（Root Cause Analysis）。問題の本当の原因を突き止める調査。
変更
サービスに影響しうるものの追加・修正・削除。標準・通常・緊急の 3 種がある。
サービス要求
障害ではない、決まった手順で応える利用者の依頼（PC の申請、パスワードの再設定など）。
影響度
インシデントがどれだけ広い範囲（人数・業務）に及ぶか。1（高）〜3（低）。
緊急度
どれだけ早く対応しなければならないか。1（高）〜3（低）。影響度と組み合わせて優先度を導く。
メジャーインシデント
影響が大きく、通常と別の体制（当番の呼び出し、経営への連絡）で扱うインシデント。
CAB
Change Advisory Board。変更のリスクを見て承認を判断する会議・グループ。
ECAB
Emergency CAB。緊急の変更をすぐに判断する少人数の CAB。
禁止期間
決算の期間など、通常の変更を予定してはならない時間帯。逆に変更を予定すべき時間帯を保守の時間帯と呼ぶ。
ポータル
社員が申請・報告・ナレッジの検索・承認をする、IT の担当者向けの画面とは別のセルフサービスの画面。
変数
カタログの品目の申請で答える入力の項目（機種、数量、理由など）。
要求の品目
1 回の申請（要求）に含まれる品目ごとの記録。承認と実行のフローの単位。
実行
fulfillment。承認された要求に応えて、実際に作業すること。その作業を実行のタスクと呼ぶ。
自己解決
deflection。ポータルでナレッジを見て、申請・報告をやめて自分で解決すること。
SLA
Service Level Agreement。サービスの提供者と利用者の間の、応答・解決の時間などの約束。
OLA
Operational Level Agreement。社内のチームどうしの約束。SLA を守るための内訳。
UC
Underpinning Contract。外部の事業者との契約上の約束。
業務カレンダー
営業時間・タイムゾーン・祝日・会社の休日の定義。SLA の業務時間を数える物差し。
振替休日
国民の祝日が日曜日に当たったとき、その後の最も近い祝日でない日を休日にするもの（祝日法 第 3 条第 2 項）。
国民の休日
前日と翌日が祝日である、祝日でない日を休日にするもの（祝日法 第 3 条第 3 項）。
CMDB
Configuration Management Database。CI とその関係の台帳。
CI
Configuration Item。サーバー・PC・ネットワーク機器・アプリ・サービスなど、管理の対象の構成要素。
CSDM
Common Service Data Model。ServiceNow が示す、サービスと CI の表し方の標準の型。
取り込み元
CI の情報を送ってくる元（手入力、CSV、API、クラウド、資産管理のツール）。属性ごとに優先度を持つ。
識別
届いた CI の情報が、既存のどの CI を指すかを決めること。
調整
複数の取り込み元の値が食い違うとき、属性ごとにどの値を採るかを決めること。
鮮度
取り込み元の観測が「まだ有効」とみなせる期間。古くなった強い取り込み元より、新しい弱い取り込み元の値を採る。
データ辞書
テーブル・フィールド・型・選択肢・参照の定義を持つメタデータ。
メタデータ
振る舞いを決める設定のデータ（辞書・ACL・フロー・SLA・フォームの配置など）。テナントごとにバージョンを持つ。
クラス
継承の階層の中のテーブル。例：task の子の incident。
ACL
Access Control List。テーブル・行・フィールドごとに、誰が何の操作をできるかの規則。
フロー
きっかけ・条件・承認・タスク・通知・待ちを組み合わせたノーコードの業務の流れ。公開すると不変のバージョンになる。
代理
期間を決めて、本人の代わりに承認や申請をする人を指定すること。
職務の分離
依頼した人と承認する人を分け、1 人で不正を完結できないようにする内部統制の原則。
参照の印
送ったメールに入れる推測できない文字列。返信を元のチケットに結ぶ手がかりで、権限ではない。
当番
オンコール。業務時間の外も含めて、呼び出しに応じる担当者。当番表とローテーションで決まる。
エスカレーション
応答がない・期限が近いときに、次の担当や上位の人へ引き上げること。
IT 全般統制
ITGC。システムの開発・変更・運用・アクセスの管理についての内部統制。変更の承認と権限の付与の証跡が対象になる。
