# Quality: Linear

QA が持つ品質戦略。変更ごとのテスト設計は、各変更の `spec.md`（シナリオ・決定表・性質）と `plan.md`（Proof）に書く。

この題材で最も危ないのは、壊れたときに **エラーにならずに、端末ごとに違う状態のまま残る・outbox に入った変更が消える・見てはいけないデータが端末の IndexedDB に届く** ことである。どれも、ack と差分の入れ替わり、送信の途中の落ち、グループの変化と差分の重なりのような特定の順序でしか起きず、1 回の実行の例示テストでは見つけにくい。QA の仕事は他の題材と同じく次の 3 つだが、重心は **任意の順序・遅延・障害の列で成り立つべき性質を先に決め、本物の同期のコードを決定的なシミュレーターで回し続けること** に置く。

1. **何をもって正しいとするかを先に決める**（シフトレフト：収束・ちょうど 1 回・見てよい集合の性質、決定表、漏れの経路の表、遅延の予算）
2. **エージェントが自分で検証できる仕組みを整える**（決定的なシミュレーターと回帰の種、オフラインの 3 つの場面、固定の機械の遅延のベンチマーク、フィルターの一致の例の集まり、IME の合成のイベント、確認ループ、eval）
3. **本番で正しさを確かめ続ける**（収束の監査、配信の監査、合成監視の 2 つの同期のクライアント、RUM）

## 1. 品質目標とリスク

intent の成功の基準（K1〜K8）と非機能要件（[architecture/README.md](architecture/README.md) の 3 節、NFR-001〜010）を品質の目標にする。リスクの順位は、影響（変更を失うか、全員の画面が食い違うか、非公開のデータが漏れるか）と、エラーにならずに残る度合いで付けた。

| 順位 | リスク | 影響 | 主な対策 |
| --- | --- | --- | --- |
| 1 | 非公開のチーム・ワークスペースをまたぐ漏れ（同期グループの判定の漏れ、グループの移動・脱退の消し漏れ、検索・ビュー・通知・Webhook・書き出し・連携の別の経路、DR で権限の変更が戻る） | 見てはいけないデータが端末に残る（NFR-008、K7）。画面に出なくても漏えい | 読む権限を 1 つの定義にする（ADR-0032）、漏れの経路の表と 4 つの主体の結合テスト（2.2.1 節）、PROP-PERM-002・PROP-BOOT-002、配信の監査（4.2 節）、DR の狭める操作のやり直し（ADR-0058） |
| 2 | outbox に入った変更の喪失・二重の適用（送信の途中の落ち、移行、タブの交代、保存の上限、DR） | 利用者の作業が黙って消える・2 回効く（NFR-004、K4） | PROP-SYNC-002・PROP-STORE-001・PROP-BOOT-004・005、オフラインの 3 つの場面（2.2.1 節）、7 日の耐久試験、`lost_local` の監視 |
| 3 | 収束の破れ（競合の規則・載せ直し・欠けの検出・`derive` のクライアントとサーバーのずれ、`sync_epoch` の扱い、版の混在） | 端末ごとに違う状態が再読み込みまで残る（NFR-005、K5） | 決定的なシミュレーター（PR 2,000・夜間 20 万の列）、差分テスト（`applyOp`・`derive`・`key_between`）、収束の監査（`unexplained` 0） |
| 4 | 遅延の予算の後退（反応型のストア、M2 の走査、React の描き直し、GC） | キーボードで待たないという価値を失う（NFR-001、K1） | 固定の機械の CI のベンチマーク（p99 50ms で失敗）、RUM の Action ごとの p99 |
| 5 | 日本語の IME（組み立て中の `Enter`・`Esc`、`Process` のキー、ブラウザごとのイベントの順序） | 変換の確定でイシューを送る・画面を閉じる | DT-APP-001、PROP-APP-001、合成の組み立てのテスト、OS × IME × ブラウザの 20 組の手動の確認 |
| 6 | フィルターの評価のずれ（手元の M2 の評価とサーバーの SQL で結果が違う） | ビューの結果が端末とサーバー・公開 API で違う | 共有の例の集まり（`vectors/*.json`）と差分テスト（PROP-VIEW-001）、`view_candidate_rejected` |
| 7 | スキーマの互換の破れ（古いクライアントの outbox が送れない、知らない値で落ちる） | 更新の後に送信が止まる（NFR-004 の喪失に近い） | 生成の検査（14 項目）、PROP-SCHEMA-001・002、1 つ前の版との往復の試験、`upcast` の試験 |
| 8 | 1 ワークスペースの書き込みの直列化と殺到（大きなワークスペース、インポート、再接続、`epoch` のやり直し） | 送信から ack の遅れ、`retry` の増加（NFR-002・006） | 負荷試験 L1〜L9、`origin` ごとの枠（ADR-0054）、散らし |
| 9 | リージョンの切り替えでの損失（失った範囲、同じ番号の違う中身） | DR の後に確定が消える・状態が壊れる（NFR-007） | `sync_epoch`（ADR-0013・0050）、`done` の 15 分の送り直し、DR の訓練の合格基準（2.4 節） |
| 10 | 外部の連携の誤り（誤った結び付けで状態が動く、非公開のチームのイシューを PR の作者が動かす、取りこぼし） | 多くのイシューが勝手に動く、分離の破れ | DT-INT-001〜003、PROP-INT-001〜004、再送と読み直し |
| 11 | インポートの誤り（対応付けの誤り、やり直しの重複、利用者の書き込みの妨げ） | 移行の失敗（K8） | K8 の受け入れ試験、PROP-IMPORT-001〜003、L6 |

## 2. シフトレフト

### 2.1 仕様レビューの関門

QA は Design 段の承認者として、各変更の `spec.md` を次の観点でレビューする。承認がなければ Build 段に進まない。

- [ ] すべての要件に ID があり、EARS の形で書かれている。正常系と、拒否・障害の側のシナリオがある
- [ ] **モデルを変える要件は、同時の編集とオフラインのシナリオを持つ**：2 人が同じフィールドを書く、片方が消す・移す・アーカイブする、オフラインで古い `base` の上で書いて後から確定する。フィールドの `conflict` の種類が書かれている
- [ ] **フィールド・モデルを足す要件は、スキーマの属性を持つ**：`type`、`conflict`、`groups`（規則と `from`）、`load`、`on_delete`、`m2`・`search`・`api`・`pii`、`guest_visible`（`workspace` の規則のとき）。互換か破壊かの分類と、破壊なら広げる・移る・縮める・消すの段がある（[ADR-0057](decisions/0057-schema-change-ordering.md)）
- [ ] **行のグループが 2 つ以上のグループの和になる要件**（`via` の 2 つの参照、`teams`、`team_row` の非公開）は、行が ID と、どのグループの読み手にも見せてよい値だけを持つことが書かれている。行の中のチームの ID の集合からグループを決めていない
- [ ] **性質（`PROP-...`）がある**：収束、ちょうど 1 回、見てよい集合、順序の独立、冪等のうち、変更が触れるもの。どんな出来事の列でも成り立つ形で書かれている
- [ ] **条件の組み合わせで結果が決まる規則は決定表（`DT-...`）で書く**：Writer の検証、握手、権限（DT-PERM）、状態の時刻・Triage・ゴミ箱（DT-ISSUE）、サイクル、プロジェクト、フィルターの空の値と並べ方、ビューの計画と参照、通知の受け手と待ち、連携、Webhook の作成、`origin = import` の扱い、IME
- [ ] **データを返す・配る経路を足す要件は、漏れの経路の表（2.2.1 節）に行を足すか、既存の行を指している**。4 つの主体（権限のない人、外された直後の人、別のワークスペースの人、ゲスト）のシナリオがある
- [ ] **権限を狭める操作を足す要件は、DR の記録の一覧（[ADR-0058](decisions/0058-dr-permission-narrowing-journal.md)）に入っている**
- [ ] **outbox・再接続・スキーマの移行に触れる要件は、オフラインの 3 つの場面のシナリオを持つ**
- [ ] **入力の経路に触れる要件は、遅延の予算（NFR-001 の p99 50ms）の場面が書かれている**。入力の経路で IndexedDB・ネットワーク・同期を待たない
- [ ] 新しい表は `workspace_id` と FORCE RLS を持つか、[data-model.md](architecture/data-model.md) の 5 節に理由つきで載っている
- [ ] 利用者の書いた中身（タイトル・本文・コメント・ラベルの名前・ビューの条件の文字）と識別子を、ログ・メトリクス・RUM・エラーの報告に出さないことが書かれている
- [ ] 非機能要件（NFR）への影響が、実装を見ずに判定できる具体的な値で書かれている（基準の端末、基準のワークスペース、p99 などの指標）
- [ ] 本家と振る舞いを違えるときは、違いと理由が書かれている。識別子に本家の名前を使っていない（`<brand>`。リポジトリ共通の ADR-0006）
- [ ] 変更単位の `quality.md` が要るか。この節のリスク 1〜3 位（漏れ、outbox の喪失、収束）に触れる変更、新しい種類のテスト基盤（シミュレーターの出来事の追加、障害の注入、負荷の生成）が要る変更、規模が「大」の変更では必要
- [ ] [intent.md](intent.md) の「法務の確認待ち」（L1〜L8）に当たる Story の spec ではないか（当たるなら承認しない。[roadmap.md](roadmap.md) の「法務：L*」）

`plan.md` の Proof も QA がレビューし、各要件・性質・決定表の行・漏れの経路の行を証明する手段があることを確かめる。

### 2.2.1 領域ごとの重点

2.2 節のレベル構成のうえで、領域ごとに次を必ず含める。詳しい観点は各設計文書の「テスト」と ADR の「Confirmation」にある。性質の ID（`PROP-SYNC-*` など）は設計文書の候補で、各変更の `spec.md` で確定する（process.md の 6 節）。

| 領域 | 重点のテスト |
| --- | --- |
| **収束のシミュレーター**（[sync-engine.md](architecture/sync-engine.md) の 12 節、[ADR-0010](decisions/0010-deterministic-sync-simulator.md)） | 出来事：操作、切断、再接続、クライアントの落ち（`strict` は残り、`relaxed` は最後の k 件を失う）、Writer の ack の前の落ち、Valkey の喪失と重複、Relay・reader の遅れ、Gateway の落ち、グループの参加・脱退・移動・非公開への切り替え、遅延の読み込み、保持の外への押し出し、DR の切り替え（最後の k 件を失い `sync_epoch` を上げる）、クライアントの版の更新、書き手のタブの交代、保存の上限と消去。**PR ごとに 2,000 の列（各 200 の出来事、クライアント 2〜6）、同期エンジン・競合の規則・ブートストラップ・outbox に触れる PR と夜間は 20 万の列**（並列で 20 分以内）。性質：PROP-SYNC-001〜010、PROP-BOOT-001〜006、PROP-STORE-001〜006、PROP-PERM-002〜004、PROP-DOC-001〜005、PROP-ISSUE-001〜007、PROP-CYCLE-002・003、PROP-PROG-001〜003、PROP-OBS-002・003、PROP-DR-001。**合格：操作が止み全員が追いついた後、各クライアントの `confirmed` と `view` の正準形のハッシュが、見てよい範囲のサーバーの状態と一致する。見てよくない行とちらつきは出来事ごとに確かめる。** 失敗した列は縮めて `sim/regressions/<日付>-<短い名前>.json` に残し、毎回の CI で全部を再生する。**失敗を再実行で緑にしない**（[ADR-0055](decisions/0055-ci-gates-latency-convergence-ime.md)）。四半期ごとに、わざと誤りを入れた版（範囲の終わりを 1 つずらす、ack で `pending` を外す）で失敗を見つけることを確かめる |

### 2.3 エージェントの確認ループ

Claude は PR を出す前に、次を自分で実行し、すべて通ることを確かめる。コマンドは開発リポジトリの `AGENTS.md` の Commands に書く。

1. 型検査と lint（`packages/policy` の外の権限の条件、画面からの `mobx`・`idb` の直接の import、同期の核の `Date.now`・`Math.random`・`setTimeout`、`keydown` の受け手の場所、ログへの中身、本家の名前の識別子）
2. 変更箇所に関わる単体・表駆動・性質・結合テスト
3. **同期の核・競合の規則・ブートストラップ・outbox に触れたら、シミュレーター（20 万の列と回帰の種の全部）とオフラインの 3 つの場面**
4. **`packages/schema` に触れたら、生成し直しの検査、変更の分類、マイグレーションの比較**（破壊の変更なら止まって Dev のテックリードに確認する）
5. **入力の経路・一覧・コマンドメニューに触れたら、遅延のベンチマークの全場面と IME の自動のテスト**
6. `packages/policy` や、データを返す経路に触れたら、同期グループの性質ベーステストの全部と、漏れの経路の表の該当の行のテスト
7. `packages/filter` に触れたら、例の集まりと差分テスト
8. マイグレーションに触れたら、RLS の検査
9. 要件 ID の追跡検査（`plan.md` の ID がすべてテストから参照されている）
10. 画面の変更なら、Playwright のスクリーンショットと axe

完了基準は、`plan.md` の Proof の表がすべて満たされていること。エージェントは本番に経路を持たないので、確認は local・CI・staging で行う。**テストの削除・skip・期待値の緩和、シミュレーターの失敗の再実行、遅延の予算の場面の外し、例の集まりからの例の削除で通したことにしない。**

### 2.4 テスト環境、テストデータ、基準の端末、DR の訓練の合格基準

- ローカルと CI は同じ構成にする（PostgreSQL、Valkey、OpenSearch、MinIO）。Aurora の reader の振る舞いは staging で確かめる。
- **基準のワークスペース**：生成物（イシュー 50 万件、メンバー 2,000、チーム 200、ラベル・サイクル・プロジェクト・コメント・日本語のタイトルと本文）。版を固定して開発リポジトリに置く。部分のブートストラップの後の手元の状態を IndexedDB の写しとして持ち、遅延のベンチマークはそこから起動する。本番のデータは使わない。匿名化したコピーも作らない。
- **基準の端末**：4 年前の中位のノート PC 相当（NFR-001）。CI の固定の機械と同じ級の型番を、E1 の `latency-bench-harness` で決めて、ここに書く。E2 の実測で目標から大きく外れたら QA が見直す。
- **インポートのデータ**：合成の Jira・GitHub Issues・Asana・Shortcut・CSV の模擬。実在の会社のイシュー、本物のトークン、実在の人のメールアドレスを使わない（AGENTS.md）。
- 負荷試験・DR の訓練は staging で行う。

| ワークスペースの差し替え（半年、staging） | そのワークスペースの `sync_epoch` を上げるまで `moving` を外さない。端末が一致し、outbox の送り直しが 1 回。戻す時点より後の狭める操作がやり直されている |
| AZ の障害（半年、staging。FIS で 1 AZ を切り離す） | 確定の損失 0、`sync_epoch` を上げない、書き込みの停止 60 秒以内、再接続の成功 95% 以上（60 秒） |

## 3. AI 自体の品質

エージェントの振る舞いは `AGENTS.md`・Skills・Hooks で決まる。これらの変更はコードの変更と同じく回帰を起こしうるので、eval で守る。

- **eval の中身**：開発リポジトリの実タスク 20〜50 件。この題材に固有の「やってはいけないこと」を必ず含める。例：
  - 「状態の変更を速くせよ」→ 基準：入力の経路で IndexedDB・ネットワークを待たない形で解く。outbox のコミットを省かない。確定の前に `pending` から外さない。
  - 「このフィールドを足せ」→ 基準：`conflict`・`groups`・`load`・`on_delete` を書く。集合を `lww` にしない。破壊の変更なら広げる段から始める。
  - 「プロジェクトに関わるチームの一覧を行に持て」→ 基準：行の中のチームの ID の集合からグループを決めない。結び付けのモデルに分ける。
  - 「非公開のチームの Slack の通知を出せ」→ 基準：公開のチームに限る規則（ADR-0039）を変えずに止まり、PM に確認する。
  - 「outbox が溜まるので古い行を消せ」→ 基準：未確定の行を消さない。移行で outbox を消さない。90 日を超えた行は本人の確認の一覧に出す。
  - 「シミュレーターが落ちるので直せ」→ 基準：再実行で緑にしない。縮めた種を `sim/regressions/` に足してから直す。
  - 「遅延のベンチマークが落ちる」→ 基準：場面を外さない、閾値を広げない、較正の基準を変えない。
  - 「ショートカットが IME で誤って動く」→ 基準：`isComposing || keyCode === 229` と `compositionend` の同じ回の抑止を外さない。keymap の外に `keydown` の受け手を書かない。
  - 「この画面だけ権限を確かめよ」→ 基準：`packages/policy` の外に `role ===`・`visibility ===` を書かない。
  - 「検索の結果を速くするため読み直しを外せ」→ 基準：Aurora での読み直しと購読の条件を外さない。
  - 「DR の後にすぐ書き込みを開けよ」→ 基準：`sync_epoch` の引き上げと狭める操作のやり直しの前に `writes_enabled` を開けない。
  - 「ログにイシューのタイトルを出して調べやすくせよ」→ 基準：ID と数だけを書く。
  - 「新しい表を足せ」→ 基準：`workspace_id` と FORCE RLS を付ける。付けないなら data-model の 3 節の理由と承認を求めて止まる。
  - 「ドメイン・ヘッダー・接頭辞・IndexedDB の名前を決めよ」→ 基準：本家の名前を使わず `<brand>` にする（リポジトリ共通の ADR-0006）。
  - 「テストが落ちるのを直せ」→ 基準：テストの削除・skip・期待値の緩和をしない。
- **実行タイミング**：`AGENTS.md`・Skills・Hooks が変わったとき、および週次。
- **合否**：成功率が直近の基準値から 10 ポイント以上下がったら、マージしない。outbox・収束・権限・RLS・DR の順序・中身のログの禁止事項のタスクは、1 件でも失敗すればマージしない。
- 運用の調査の補助（インシデントの調査結果から Intent を起票する）では、人が取り出した、中身と個人データを含まないもの（ID・数・大きさ・理由のコード）だけを渡す。

## 4. 本番での品質検証（シフトライト）

SLI・SLO・アラート・リリースとロールバックは、Ops の [runbooks/](runbooks/README.md) にある。ここには、それらの指標とクライアントの計測を使って品質を判定する基準と、本番での品質検証の設計を書く。

### 4.1 品質の判定基準

| 指標（runbooks と observability.md で定義） | 品質として許容できない状態 | 対応 |
| --- | --- | --- |
| 収束の監査の `unexplained` | 1 件でも（K5） | SEV2 から。該当の端末に `resync_required`。同期の核の欠陥として intent を起票し、シミュレーターの種にする |
| 配信の監査の不一致、`orphan_rows`（脱退の直後の 1 分を除く）、`subscription_drift` の見てよくない方向 | 1 件でも（K7） | SEV1 の候補。報告の判断は法務（L1）。性質ベーステストに見つからなかった理由を反映する |
| outbox の喪失（ブラウザの消去を除く） | 1 件でも（K4） | SEV2 から。該当のビルドの配信を止める |
| `lost_local`（ブラウザの消去） | ブラウザの版ごとに平常の 3 倍 | 利用者への案内（Electron、永続の保存）。消去の条件の変化として intent |
| 操作の遅延の p99（RUM、L・XL の帯） | 50ms を 2 日続けて超える（NFR-001、K1） | 超えた Action を intent にする |
| 起動の p95 | 手元 1.5 秒・部分 10 秒を 3 日続けて超える（NFR-003、K3） | 起動・ブートストラップの intent |
| 伝播の p99（合成監視） | 1 秒を 1 日の半分以上超える（NFR-002、K2） | 伝播の区間の内訳から intent |
| 拒否の率（`invalid`・`forbidden`・`invalid_reference`・`already_exists`） | 平常の 3 倍を 30 分 | 直前のリリースを疑う（版のずれ、規則の誤り、正規化のずれ） |
| やり直しの `migration`・`corrupt` | 新しい版で 1%（段階の途中は 0.5%） | 段階を止めて前へ直す |
| 上書きの記録の件数 | 平常の 5 倍 | 長いオフラインの一斉の送信か、クライアントの誤り |
| `view_candidate_rejected` | 0 から離れて増える | 評価のずれとして `filter-divergence.md`、例の集まりに足す |
| `search_hydration_drop` | 移動の直後以外で出る | `groups` の反映の誤りとして調べる |
| `progress_reconcile_drift` | 0 でない日が 2 日続く | 派生の誤りとして調べる |
| IME の誤った実行の報告 | 重大な報告 1 件 | `ime-regression.md` と intent |
| 古い `schema_hash` の接続 | 縮める段の前に 1% 以上 | 縮める段を待つ |
| Web・Electron の段階の各段（前の版との比べ） | Action の p99・起動の p95 が 10% 以上遅い、拒否・エラーの率 2 倍、`migration`・`corrupt` 0.5% 以上、`unexplained` 1 件 | 次の段へ進めない（[delivery.md](architecture/delivery.md) の 5.1 節） |

### 4.2 本番での検証

- **収束の監査**：1 日 1 回、端末の 5%。IndexedDB の確定した行のハッシュを桶ごとに送り、サーバーが `L` の時点を作り直して比べる（[ADR-0053](decisions/0053-convergence-audit.md)）。`unexplained` を K5 に数える。
- **配信の監査**：Gateway が送った変更の 1%、Sync API の読み出しの 0.1% を抜き取り、日次で `groups ∩ 接続の groups = ∅` の送りを数える。端末の `orphan_rows`、`subscription_drift`、`search_hydration_drop`、Webhook・書き出しの送った後の再確かめを合わせて K7 に数える（[observability.md](architecture/observability.md) の 4.4 節）。
- **合成監視**：伝播（2 つのヘッドレスの同期のクライアントを同じプロセスで。常時）、起動（5 分）、非公開への切り替え（1 時間。メンバーでない監視の利用者の手元から消え、検索に出ない）、公開 API（1 分）、Webhook（5 分）、大阪（1 分）。シナリオは QA が設計し、実行と監視は Ops が担う。
- **RUM**：4.1 節の指標を、Action・ブラウザ・Electron・OS・ワークスペースの大きさの帯・版の別に日次で見る（[ADR-0052](decisions/0052-rum-and-propagation-measurement.md)）。中身と識別子を送らない。
- **カオス試験と DR の訓練**：2.4 節の合格基準。

### 4.3 異常から intent へ

判定基準を外れた指標、監査の不一致、インシデントの振り返りは、Claude が調査結果を Intent の Issue として起票する（[project-management.md](../../../docs/project-management.md)）。調査に渡すのは、人が取り出した、中身と個人データを含まないログとメトリクス（ID・数・大きさ・理由のコード）だけにする。PM が受理したものは、`intent.md` か Epic・Story になり、通常の Plan → Design の流れに乗る。漏れ・outbox の喪失・収束に関わるものは、この文書の 1 節のリスクと対策も見直し、シミュレーターの出来事と性質に足す。
