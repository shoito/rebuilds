Linear は何をするサービスか

Linear は、ソフトウェアのチームのための課題管理のツールです。開発者・PM・デザイナーが、やること（イシュー）を登録し、状態を進め、期間（サイクル）やプロジェクトにまとめて計画します。本家の料金のページには「40,000 社以上」が使うとあります。

待たない

状態・優先度・担当の変更は、入力から描画まで p99 50ms 以内。サーバーの応答を待たない（NFR-001）。

全員が同じものを見る

他の人の変更は 1 秒以内に届き、切断や同時の編集の後も全員が同じ状態に収束する（NFR-002・005）。

失わない

オフラインの変更は再起動をまたいでも失わず、つながったら 1 回だけ効く（NFR-004）。

使われ方の特徴は、キーボードだけで、何百件ものイシューを素早く整理することです。一覧で P を押して優先度を変え、次の行へ移り、また変える。1 回ごとにサーバーを待つと、この使い方が成り立ちません。規模は S1 で 5,000 ワークスペース、同時接続 6 万、最大のワークスペースでメンバー 2,000 人・イシュー 50 万件を想定しています。

設計の文書で効くところintent.md の Problem と Proposed outcome、architecture/README.md の 2〜3 節（規模の段階と NFR）。

ワークスペース・チーム・識別子

顧客の組織 1 つが 1 つのワークスペースで、これがテナントの単位です（共通の資料）。その中をチームに分けます。チームは、ワークフロー・サイクル・識別子の接頭辞を持つ、課題管理の基本の単位です。

  • 人が読む識別子：イシューは ENG-123 のように「チームの接頭辞 − 番号」で呼びます。番号はチームごとの連番で、サーバーの Writer が確定の時に振ります。確定するまで画面は ENG-… と仮に出します。
  • ID は別にある：イシューの本当の ID は、クライアントが振る UUIDv7 です（共通の資料）。サーバーを待たずに、作ったイシューへの参照を作れます。チームを移ると番号は振り直され、古い識別子は別名として残ります。
  • 公開と非公開のチーム：公開のチームはワークスペースの全メンバーが見て参加できます。非公開のチームは、そのチームのメンバーだけが中身を見られます。
ロールできること（概要）
owner管理者のすべてに加えて、請求・セキュリティの設定・ワークスペースの削除
adminメンバーの招待・停止、チームの作成と公開の切り替え、連携
member見てよいチームで読み書き。チームを作る、公開のチームに参加する
guest参加させられたチームだけ。MVP の後

イシューのワークフローと属性

各チームは、イシューの状態を自分で定義します（「In Review」など）。ただし、どの状態も決まった種類のどれかに属し、種類の順は変えられません。集計や自動化は、名前ではなく種類で判断します。

flowchart LR
  T[triage] --> B[backlog] --> U[unstarted] --> S[started] --> C[completed]
  S --> X[canceled]
  D["duplicate（システムだけが付ける）"]

状態はどこからどこへも移せます。例外は 2 つで、duplicate へは「重複の関連を作る」操作でだけ入り、Triage は連携やチーム外の人が作ったイシューの受け皿です。削除は 30 日のゴミ箱で、すぐには消えません。

なし・Urgent・High・Medium・Low の 5 つ。並べ替えでは「なし」が最後です。Urgent にすると担当に通知し、メールでも知らせます。

ワークスペースのラベルとチームのラベル。グループの中からは 1 つだけ付けられます（例：「種別」の中の Bug か Feature）。

点数で持ち、尺度は表示の形だけを決めます。指数（1・2・4・8・16）、フィボナッチ（1・2・3・5・8）、線形（1〜5）、T シャツ（XS〜XL）。親の見積もりに子の合計は足しません。

サブイシューの深さの上限を本家は書いていません。この設計は 10 段までです。関連は blocks・related・duplicate。設定により、子が全部閉じたら親を閉じる、親を閉じたら子を閉じる、という自動の処理があります。

設計の文書で効くところissues-and-workflow.md の 4〜10 節の決定表、ADR-0023、ADR-0024。

サイクル：チームの短い期間

サイクルはスクラムのスプリントにあたる、チームごとの 1〜8 週の期間です。決めた曜日から自動で繰り返し、先のサイクルを最大 15 個まで用意します。サイクルの間に任意のクールダウンを置けます。クールダウンにはイシューを割り当てられません。

  • 境界はチームのタイムゾーンで決まる。同じワークスペースでも、東京のチームとロンドンのチームでは、サイクルの始まりの時刻が違います。
  • 繰り越し：サイクルが終わると、未完了のイシューは次のサイクルへ自動で移ります。
  • 成功の割合：完了を 1、着手中（started）を 1/4 と数えます。完了 5・着手中 4・手つかず 1 なら (5 + 4/4) / 10 = 60% です。

サイクルが終わり、次のサイクルが始まりました。残っていたイシューのうち、この設計で次のサイクルへ自動で移るのは？

Triage・Backlog は「まだ計画していない」ものなので、元のサイクルに残します（DT-CYCLE-001）。繰り越しは次のサイクルの始まりに行うので、クールダウンの間に Backlog へ戻したものも移りません。

設計の文書で効くところcycles-and-projects.md の 4 節（境界の計算、繰り越し、遅れた割り当て）、ADR-0026。

プロジェクト・イニシアチブ・進捗

サイクルが「チームの時間の区切り」なら、プロジェクトは「成果の単位」です。複数のチームにまたがり、リーダー・状態・期日・マイルストーンを持ちます。リーダーは定期的に進捗の更新を書き、健康状態（On track・At risk・Off track）を示します。複数のプロジェクトを束ねるのがイニシアチブ（識別子は I- と連番）です。

イシューの種類範囲（scope）進捗への寄与
triage・backlog・unstarted入る0
started入る1/4
completed入る1
canceled・duplicate・ゴミ箱入らない—

点は見積もりの値です。見積もりのないイシューは、設定により 1 点か 0 点と数えます。進捗はチームごとの行に分けて持ちます。プロジェクトが非公開のチームにまたがると、そのチームの件数を、他のチームの人に見せてはいけないからです。

設計の文書で効くところcycles-and-projects.md の 3・5〜7 節、ADR-0027。

ローカルファーストとは

この題材の核です。ローカルファーストでは、ワークスペースのデータを端末の DB に持ち、画面はそれを読みます。

よくある Web アプリ

操作 → API に送る → 応答を待つ → 描く。数百ミリ秒かかり、回線が切れると何もできない。他の人の変更は再読み込みまで見えない。

ローカルファースト

操作 → 手元のモデルに楽観的に当てて描く → 後で送る。サーバーが順序を決めて確定し、他の人の変更は差分で届く。

ただし、これは P2P ではありません。正本はサーバーの 1 本の順序です。クライアントは「確定した状態」の上に「自分の未確定の変更」を重ねて見せているだけで、最後はサーバーの順序に合わせます。似た系統に Replicache・Zero があります。本家の文書は、オフラインを「完全な機能ではなく失敗への備え」と書き、この設計はそれより強い保証（7 日のオフライン、上書きの記録）を目標にしています。

あなたはオフラインで優先度を High にしました。その後、同僚がオンラインで Low にしました。あなたが再接続すると、どうなりますか？

端末の時刻は順序に使いません。サーバーで確定した順に後が勝ちます（LWW）。作った時点のバージョン（base）より後に他の人が変えていれば、上書きとして履歴に残し、古い操作なら本人にも知らせます（ADR-0008）。

設計の文書で効くところADR-0002（同期のモデル）、sync-engine.md の 2 節（本家の形と他の方式との比較）。

sync_id：ワークスペースの 1 本の順序

サーバーは、ワークスペースの中のすべての変更に、1 つずつ増える番号 sync_id を欠けなく振ります。クライアントの手元のバージョンは「どの sync_id まで当てたか」の 1 つの数（L）で表せます。

  • なぜ DB のシーケンスを使わないか。シーケンスは、番号の順とコミットの順がずれます。ワークスペースの行をロックして数を増やすと、番号の順とコミットの順が一致し、「x より後」を読んで取りこぼすことがなくなります。代わりに、1 ワークスペースの書き込みは直列になります（S1 で 1 秒 300 変更の見込み）。
  • 絞ると番号が飛ぶ。非公開のチームの変更は、見てよくない人に送りません。すると受け手から見た番号は飛び飛びになり、番号の連続では欠けを判定できません。
  • そこで範囲の証明。差分は {from: a, to: b} の形で送り、「(a, b] のうち、あなたが見てよい変更はこれで全部」を表します。中身が 0 件の範囲も知らせます。

手元の L は 100 です。届いたパケットは {from: 120, to: 130} でした。クライアントはどうしますか？

from > L は欠けです。配信（Valkey の pub/sub）は落ちてよいものとして作り、正しさは範囲の連続と取り戻しが持ちます。取り戻せないほど古い（ログの保持の外、5 万件より先）ときだけ、やり直しになります。

設計の文書で効くところADR-0007、sync-engine.md の 7 節（sync_actions、Gateway での絞り込み、欠けの検出）。

トランザクションの一生と載せ直し

1 回の入力（キーの操作 1 回、ドラッグ 1 回）が 1 つのトランザクションになります。中身は「priority を 2 にする」「label を 1 つ足す」のような意図の操作の列で、行の全体ではありません。

  1. トランザクションを作り、メモリーのオブジェクトプールの未確定（pending）に積んで、すぐ描く。ネットワークも IndexedDB も待たない。
  2. 端末の outbox に保存する。ここが「失わない」の起点。
  3. WebSocket で Sync Gateway に送る。client_tx_id（UUIDv7）が冪等の鍵になる（共通の資料）。
  4. Writer がワークスペースの行をロックし、権限・参照・ワークフローの規則を確かめ、モデルの表と sync_actions を 1 つの DB のトランザクションで書く。
  5. 送り手に ack（確定の sync_id = s）が返る。まだ pending から外さない。
  6. s までの差分が届き、手元に保存したら pending から外す。ack と差分の順が揺れても、画面は自分の値から動かない。
  7. 拒否されたら、pending から外して画面を作り直し、理由を本人に示す。

他の人の差分が来たら、確定した値に当ててから、自分の未確定の操作を当て直します。これが載せ直しです。ある変更から決まる別の変更（状態の時刻、親の自動で閉じるなど）は、共有のコードの derive で求め、クライアントは同じコードで予測します。

設計の文書で効くところsync-engine.md の 4〜6 節、ADR-0006、ADR-0025。

競合の規則：フィールドの型ごとに決める

課題管理では、同じフィールドを同時に編集することはまれです。そこで、全部を CRDT にはせず、フィールドの型ごとに単純な規則を決めます。規則はスキーマの 1 か所に書き、規則のないフィールドはコードの生成で失敗させます。

タイトル・状態・優先度・担当など。確定の順で後が勝ちます。フィールドごとに独立なので、Aさんが状態、Bさんが担当を同時に変えても両方残ります。

ラベルなどの集合。「足す」「除く」の操作で送り、集合の全体を置き換えません。2 人が別のラベルを同時に足せば、両方残ります。

手動の並び。分数インデックスの文字列の鍵で、「a0 と a1 の間」に a0V を作って入れます。兄弟の番号を振り直さないので、1 件の移動が 1 行の変更で済みます。

counter は加算（進捗の数）。server_only は Writer だけが書く値（イシューの番号、作成の時刻）。

イシューとプロジェクトの説明（本文）だけ。複数の人が同時に打っても文字が混ざって合わさるよう、Yjs の更新をそのまま足します。コメントは作った人だけが直すので LWW です。

集合の規則だけでは、ラベルの「グループの中から 1 つだけ」が崩れます（2 人が同時に別のラベルを足すと両方残る）。そこで、足す操作の派生として同じグループの他のラベルを除き、後に確定した方だけを残します。

設計の文書で効くところsync-engine.md の 8 節、ADR-0008、ADR-0021。

ブートストラップと遅延の読み込み

手元に何もない初回は、サーバーから見てよいデータをまとめて受け取ります。これがブートストラップです。2 回目からは手元の DB から画面を出し、その後で WebSocket の握手をして続きを受けます。

起動の時に全部を取るモデル。チーム、メンバー、状態、ラベルなど、画面の骨格に要る小さなもの。

条件に合うものだけを取るモデル。イシューは「未完了か、30 日以内に閉じたもの」。見てよいモデルが 5 万件（E3 の PoC で決める仮の値）を超えるワークスペースでは、この部分のブートストラップになります。

開いたときに読むモデル。コメント・履歴・本文・アーカイブしたもの。読んだ範囲を被覆の鍵（例：Comment:issue_id=…）として記録し、二度読まない。

握手の結果いつすること
resume手元が最新そのまま差分を受ける
catch_up手元が少し古いHTTP で (L, head] を取り戻す
resetログの保持（30 日）の外、5 万件より先、sync_epoch が違う手元のモデルを捨て、outbox は残して取り直す
設計の文書で効くところbootstrap-and-partial-sync.md の 3〜6・8 節、ADR-0003、ADR-0009 の握手の決定表。

同期グループ：配る単位 = 権限の単位

手元に持たせるということは、届いたデータは全部見られるということです。画面に出さなくても、端末の IndexedDB に入れば漏えいです。そこで、各行に同期グループを付け、利用者が購読するグループの行だけを配ります。

グループ購読する人例
workspace全員（ゲストを含む）ワークスペース、利用者
membersゲストを除くメンバー設定、イニシアチブ
team:<id>公開：ゲスト以外の全員と、そのチームのゲスト。非公開：そのチームのメンバーイシュー、状態、サイクル
user:<id>本人通知、個人のビュー
role:adminowner・admin連携の設定、招待

読む権限は「行のグループと購読が交わる」という 1 つの定義で、差分・ブートストラップ・検索・API・Webhook・通知が同じ関数を使います。チームへの参加・脱退も同期のログに載るので、どの sync_id から送り始め、どこで止めるかが一意に決まります。脱退したら、手元の行をまとめて消します。

非公開のチームのイシューを全員の端末に配り、メンバーでない人の画面では隠す。この設計の問題は？

クライアントに届いたデータは、見てよいデータだけでなければなりません（NFR-008）。だから配る前に Gateway で絞ります。

設計の文書で効くところADR-0004、ADR-0032、permissions-and-teams.md の 5〜7 節、bootstrap-and-partial-sync.md の 7 節。

ブラウザの保存とオフライン

手元の DB はブラウザの IndexedDB です。アカウント × ワークスペースごとに 1 つの DB を持ちます。ブラウザの保存には、サーバーの DB にない癖があります。

  • 書けたかの強さを選べる。IndexedDB のトランザクションの durability は、strict（ディスクに書けてから完了）と relaxed（OS に渡したら完了）を選べます。Chrome 121 から既定が relaxed です。この設計は outbox だけを strict にし、差分は relaxed にします（失っても取り戻せるため）。
  • ブラウザに消されうる。空きが少ないと、永続でないオリジンのデータは丸ごと消されます。Safari は追跡の防止で、7 日操作のないサイトのデータを消します。永続の保存（persist()）を求め、デスクトップのアプリ（Electron）を勧めます。
  • タブが複数ある。Web Locks で書き手のタブを 1 つ選び、そのタブだけが WebSocket を持って送ります。他のタブは outbox に書いて BroadcastChannel で知らせます。

outbox の上限は 5 万件・100 MiB です。7 日のオフラインは上限の内に収まる見積もりです。90 日より古い未送信は、自動では送らず本人に選ばせます。

設計の文書で効くところclient-store-and-offline.md の 2〜5・8〜9 節、ADR-0014、ADR-0015、ADR-0016。

キーボード・コマンドメニュー・IME

Linear の使い心地の要はキーボードです。C で作成、P で優先度、X で選択、Cmd/Ctrl+K でコマンドメニュー、G の後のキーで移動、のように 1〜2 打で操作します。設計では、操作を 1 つの Action の登録にまとめ、ショートカット・コマンドメニュー・メニューが同じ登録を使います。

50ms の予算：入力 → トランザクション → プールへの適用 → 変わった行だけの描き直し、の経路で何も待ちません。一覧は固定の高さで仮想化し、50 万件でも見えている行だけを描きます。予算を超えた PR は、CI の固定の機械で失敗させます。

日本語の入力：IME で変換している途中の Enter や Esc は、確定や取り消しのためのキーです。これをショートカットとして扱うと、意図しないイシューが送られます。変換中は event.isComposing が真か、keyCode が 229 になるので、そのキーはどのショートカットにも使いません。

法務の確認待ち画面の見た目とショートカットを本家にどこまで寄せてよいか（不正競争防止法・著作権の観点。intent.md の L8）。見積もりのキーは本家の Shift+E でなく E のまま、L8 の後に見直します。
設計の文書で効くところclient-app.md の 4〜6・9 節、ADR-0017、ADR-0018。

フィルターとビュー：手元とサーバーで同じ答え

Linear の一覧は、条件を AND・OR で組み合わせたフィルター、グループ化、並べ方で作ります。保存したビューは個人・チーム・ワークスペースの範囲を持ちます。ビューのリンクを共有しても、見る権限は与えません。

この題材では、同じフィルターをクライアントの手元でもサーバーの SQL でも評価します。手元にないイシュー（古い完了）を含む条件は、サーバーに問い合わせて補うからです。両者がずれると、同じビューで結果が変わります。そこで、フィルターを型の付いた JSON の木で持ち、1 つの定義から両方の評価を生成します。手元だけで答えられるかは、被覆の鍵から「手元だけ」「手元とサーバー」「サーバー」を選びます。

フィルター「担当が Alice でない」に、担当のいないイシューは入りますか？

SQL の三値の論理に任せると、手元の評価とずれます。空の値の扱いを言語の側で真か偽に決め、SQL は IS DISTINCT FROM などで同じ意味に訳します（DT-FILTER-001）。

設計の文書で効くところviews-and-filters.md の 3.4 節と 6 節、ADR-0028、ADR-0029。

連携：Git のホスティング・Slack・Webhook

ソフトウェアのチームの課題管理は、コードの変更とつながって初めて楽になります。GitHub・GitLab の連携では、PR（GitLab では MR）とイシューを、次の手がかりで結びます。

  • ブランチ名に識別子を入れる（eng-123-fix-login）。タイトルに識別子を書く。
  • 本文に閉じる語と識別子を書く（Fixes ENG-123）。ref・part of などは閉じない結び付け、skip・ignore は結ばない。
  • PR が開くと started、マージされると completed へ、チームの設定に従って前へだけ進めます。複数の PR があれば、全部が終わってから進めます。

GitHub の組織の誰でも PR のタイトルに識別子を書けるので、非公開のチームのイシューは、書く権限のある人の PR のときだけ状態を動かします。Slack からはメッセージでイシューを作れ、チャンネルへの通知は公開のチームに限ります。外部へ送る Webhook は時刻を含む <Brand>-Signature で署名し、失敗したら 1 分・1 時間・6 時間後に送り直します。

設計の文書で効くところintegrations.md の 4〜5 節（DT-INT-001〜003）、ADR-0038、ADR-0043。

全部で 86 表（うち同期するモデル 45）ありますが、核は次の数個です。テナントの中の表は、主キーの先頭に workspace_id を持ちます（ER 図の記号は共通の資料）。

  • モデルの表は共通の列を持ちます。updated_sync_id（最後に変えた番号。手元では _u）、sync_groups（同期グループ。手元では _g）、archived_at、trashed_at。

  • project_teams は、プロジェクトがどのチームのグループに属すかを決める結び付けの表です。行の中の配列から決めると、非公開のチームの ID が他の人に届くからです。
  • 正本は Aurora だけです。Valkey・OpenSearch・端末の IndexedDB は写しで、作り直せます（端末の outbox は例外で、送るまでは端末が正本）。

本家と違うところ・名前・法務

振る舞いは本家に寄せていますが、意図して変えたところ、MVP で作らないもの、法務の結論を待つものがあります。

本家この設計
番号（lastSyncId）は全ワークスペースで共通（第三者の解析）ワークスペースごとの sync_id
送った後に落ちると 2 回効きうる（第三者の解析）client_tx_id で 1 回だけ
オフラインは失敗への備え7 日のオフライン、上書きを履歴に残す
アーカイブは自動だけ手動のアーカイブも持つ
サイクルは 0 時 1 分に始まる0 時 0 分（隙間を作らない）
オーナーは Enterprise だけMVP からオーナーを置く

MVP の後：ゲスト、サブチーム、AI の機能、モバイルのアプリ、SAML・SCIM、ロードマップとインサイト、トリアージの自動化。作らない：自前のホストでの提供、本家の API・SDK との完全な互換、P2P の同期、汎用のプロジェクト管理。

本家の名前は識別子に使いません。閉じる語の linear issue は <brand> issue、トークンは <brand>_api_…、署名のヘッダーは <Brand>-Signature と書きます。

設計はどの結論にも対応できる形にし、結論は出していません。確認が済むまで、関わる Epic の spec を承認しません。

  • L1 個人情報保護法：ワークスペースのデータを委託として扱うか、外国の第三者（GitHub・Slack・メールの送信事業者）への提供
  • L2 電気通信事業法：コメントや通知での媒介が届出の要る事業に当たるか、外部送信規律
  • L3 インポートが他社のツールの規約に反しないか
  • L4 データの所在、L5 保持の期間（同期のログの 30 日を含む）、L6 AI の機能、L7 顧客との契約（DPA）
  • L8 画面とショートカットを本家にどこまで似せてよいか
設計の文書で効くところintent.md の Non-goals と「法務の確認待ち」、architecture/README.md の 1.3 節と 6 節、ADR-0006（リポジトリ共通）。

用語集

イシュー
課題管理の 1 件のやること。状態・優先度・担当・ラベル・見積もりなどを持つ。
ワークスペース
1 つの組織の Linear の単位。契約とデータの単位で、テナントにあたる。
チーム
ワークスペースの中の作業の単位。ワークフロー・サイクル・識別子の接頭辞（ENG）を持ち、権限の範囲にもなる。
非公開のチーム
そのチームのメンバーだけが中身を見られるチーム。メンバーでない人の端末には行が届かない。
ワークフローの状態
チームが定義するイシューの状態。triage・backlog・unstarted・started・completed・canceled・duplicate のどれかの種類に属す。
Triage
連携やチーム外の人が作ったイシューを、受け入れる・却下する・重複にする前に置く受け皿の状態。
ゴミ箱
削除したイシューを 30 日置く場所。アーカイブと trashed_at の組で表し、期限の後に本当に消す。
サイクル
チームごとに繰り返す 1〜8 週の作業の期間。スプリントにあたる。
クールダウン
サイクルとサイクルの間の、イシューを割り当てない期間。
繰り越し
サイクルの終わりに残った未完了のイシューを、次のサイクルへ移すこと。
プロジェクト
期日のある成果の単位。複数のチームにまたがれる。イシューは 1 つのプロジェクトにだけ属す。
マイルストーン
プロジェクトの中の区切り。任意の目標日を持ち、結び付いたイシューの完了の割合を示す。
イニシアチブ
複数のプロジェクトを束ねる、より大きな目標の単位。
ローカルファースト
データを端末に持ち、操作をまず手元で反映し、後でサーバーや他の端末と合わせる作り方。
楽観的な更新
サーバーの確定を待たずに、成功する前提で画面に反映すること。拒否されたら取り消す。
差分
delta。サーバーで確定した変更を、sync_id の範囲ごとにクライアントへ送るもの。
sync_id
ワークスペースの中のすべての変更に、確定の順に欠けなく振る番号。手元のバージョンを 1 つの数で表せる。
範囲の証明
差分のパケットに付ける (from, to]。その範囲で受け手が見てよい変更はこれで全部、という宣言。
sync_epoch
sync_id の世代。DR の切り替えや時点の復元で上げ、全クライアントに取り直させる。
トランザクション
1 回の入力で生まれる、意図の操作の列。全体が確定するか、全体が拒否されるか。
オブジェクトプール
クライアントのメモリーにあるモデルの集まり。確定の値と未確定の操作の 2 層を持ち、画面はその重ね合わせを読む。
outbox（クライアント）
送る前のトランザクションを保存する端末の IndexedDB の store。確定を差分で確かめてから消す。サーバー側の outbox とは別物。
Writer
すべての書き込みを検証し、モデルの表と同期のログに書き、sync_id を振るサーバーの部品。
載せ直し
rebase。確定した状態に他の人の差分を当ててから、自分の未確定の操作を当て直すこと。
derive
ある変更から決まる別の変更（派生）を求める共有のコード。Writer が書き、クライアントが同じコードで予測する。
LWW
Last Writer Wins。後に確定した値が勝つ規則。この設計の「後」は端末の時刻でなく確定の順。
CRDT
Conflict-free Replicated Data Type。どの順で何回当てても同じ状態に合わさるように作ったデータ構造。
Yjs
テキストの同時編集のための CRDT のライブラリ。エディタの ProseMirror とは y-prosemirror でつなぐ。
分数インデックス
並びを「2 つの鍵の間の新しい鍵」で表す方法。挿入や移動で他の行の鍵を書き換えずに済む。
ブートストラップ
初回やり直しのときに、見てよいデータをサーバーからまとめて受け取ること。
部分のブートストラップ
大きなワークスペースで、条件に合うイシュー（未完了と直近 30 日）だけを最初に受け取る形。
被覆の鍵
「この条件の行は手元にすべてある」を表す記録。例：Comment:issue_id=…。
同期グループ
行を配る宛先の単位（workspace・members・team:<id>・user:<id>・role:admin）。権限の単位と同じ。
IndexedDB
ブラウザに組み込まれた、キーと値のトランザクションつきのデータベース。
durability
IndexedDB のトランザクションの完了をいつとみなすかの指定。strict はディスクへの書き込みの後、relaxed は OS に渡した後。
Web Locks
同じオリジンのタブの間で使えるロックの API。タブが閉じると自動で外れる。
BroadcastChannel
同じオリジンのタブの間でメッセージを送り合う API。
コマンドメニュー
Cmd/Ctrl+K で開く、名前で操作を探して実行する入力欄。
IME
Input Method Editor。かなを漢字に変換するなど、文字の組み立てを助ける入力の仕組み。
ビュー
フィルター・グループ化・並べ方を保存した一覧。個人・チーム・ワークスペースの範囲がある。
PR
Pull Request。コードの変更をレビューしてから取り込むための依頼。GitLab では MR（Merge Request）。
閉じる語
PR の本文で識別子の前に書く fixes・closes などの語。マージでイシューを完了へ進める。
Webhook
イベントが起きたときに、利用者が登録した URL へ HTTP で知らせる仕組み。
