# ADR-0029: ビューは計画の関数が被覆の鍵から「手元だけ」「手元とサーバー」「サーバー」を決める。サーバーの問い合わせは同期グループで絞った行を返し、クライアントはそれを候補として手元に足して同じ関数で評価する。保存したビューは範囲ごとの同期グループに属し、フィルターが参照する ID はビューの読み手全員が見てよいものに限る

## Context

大きなワークスペースは部分のブートストラップで、未完了と 30 日以内に閉じたイシューだけを手元に持つ（[ADR-0003](0003-bootstrap-and-partial-sync.md)）。部分のブートストラップは、読んだ範囲を被覆の鍵（`Issue:team_id=<T>:active`）として記録する（[ADR-0012](0012-lazy-loading-coverage-and-tombstones.md)）。ADR-0012 は、被覆の鍵を「ビューが手元だけで答えられるかの判定」に使えると書いている。

残る問いは次のとおり。

- どのビューを手元だけで答え、どれをサーバーに問い合わせるかを、誰がどう決めるか。
- サーバーの結果と手元の結果をどう合わせるか。問い合わせの後にも差分は届く。
- 保存したビューの定義（名前、フィルターの ID）は、誰に届くか。非公開のチームを参照するワークスペースのビューは、そのチームの存在を漏らす。

本家は、ワークスペース・チーム・個人のビューを持ち、リンクを共有しても権限を与えない（[Custom views](https://linear.app/docs/custom-views)、2026-09-28 に確認）。ゲストはワークスペースのビューを見られない（[Members and roles](https://linear.app/docs/members-roles)、2026-09-28 に確認）。

## Options

経路の決め方：

1. **計画の関数が、フィルターの構文と被覆の鍵から保守的に決める。決められないときは手元の結果を出しつつサーバーで補う**
2. 常に手元とサーバーの両方で評価する
3. 利用者が「古いものも含める」を選んだときだけサーバーに問い合わせる

組み合わせ：

- a. **サーバーの行は候補として手元に足し、画面の結果は手元の評価だけで決める**
- b. サーバーの結果の集合と並びを、そのまま画面に出す

ビューの定義の漏れ：

- x. **ワークスペースのビューが、非公開のチームの ID を参照することを Writer が拒否する**
- y. 許し、見る人の画面で「非公開」と描く

## Decision

1・a・x を採用する。詳細は [views-and-filters.md](../architecture/views-and-filters.md) の 6・7 節。

- `planView` は DT-VIEW-001 で決める。サーバーだけのフィールド、アーカイブを含む → `server`。範囲の全チームに `:all` の被覆 → `local`。範囲の全チームに `:active` の被覆があり、条件が「開いている、または 30 日以内に閉じた」を構文で含意する → `local`。それ以外 → `hybrid`。
- 既定の完了の窓（月）を 30 日にし、部分のブートストラップの条件と同じ長さにする。既定のビューは手元だけで答えられる。
- `POST /sync/query` は、ADR-0028 の SQL を `sync_groups && $groups` で絞り、行の全体を 200 行ずつ返す。クライアントは遅延の読み込みと同じ規則（`_u`、墓標）で手元に書き、被覆は記録しない。
- 画面の結果は、手元の行を手元の評価の関数で評価したもの。サーバーの結果に続きがあれば、最後の行の並びの値（境）より後の手元の行を隠す。
- `View` の同期グループは `scope` で決める：個人 `user:<id>`、チーム `team:<id>`、ワークスペース `members`（`workspace_members` の規則。ゲストを除く）。
- フィルターが参照する ID は、`actor` が見てよく、かつ参照先の読み手がビューの読み手を含むものに限る（DT-VIEW-003）。
- 2 を採らない理由：手元で答えられるビュー（大部分）でもサーバーを叩き、負荷とオフラインの表示が悪くなる。
- 3 を採らない理由：利用者が被覆の範囲を知らないと、結果が欠けたことに気づかない。
- b を採らない理由：問い合わせの後に届いた差分が画面に反映されない。サーバーとクライアントの評価の違いが画面に出る。
- y を採らない理由：ビューの名前と条件から、非公開のチームの存在と中身の見当が付く。

## Consequences

- 良くなること：
  - 大部分のビューが手元だけで答えられ、NFR-001 とオフラインを満たす。
  - 手元にないデータを含むビューも、欠けたまま「完全」と見せない。
  - 画面の結果の規則が 1 つ（手元の評価）で、サーバーの結果との食い違いが画面に出ない。
- 引き受けるコスト：
  - 構文の含意の判定は保守的で、手元で答えられるビューを `hybrid` にすることがある（余計な問い合わせ）。
  - サーバーから足した行が M2 を大きくする。被覆のない行は、ビューを閉じて 10 分で M2 から外す。
  - 非公開のチームを条件に使うビューは、チームのビューか個人のビューにしか作れない。

## Confirmation

- 性質ベーステスト：PROP-VIEW-003（計画の安全）、PROP-VIEW-004（問い合わせの絞り込み）、PROP-VIEW-005（組み合わせの収束）。
- 表駆動テスト：DT-VIEW-001、DT-VIEW-003。
- 本番：経路ごとの割合、`hybrid` が完全になるまでの時間、`/sync/query` の p99 と打ち切りの率。
