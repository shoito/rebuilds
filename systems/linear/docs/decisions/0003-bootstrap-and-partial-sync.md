# ADR-0003: 小さなワークスペースは全体のブートストラップ、大きなワークスペースは部分のブートストラップと遅延の読み込み。差分は同期グループで絞って配る

## Context

クライアントは、ワークスペースのデータを手元に持って動く（[ADR-0002](0002-sync-model.md)）。最初にそのデータを取る処理を**ブートストラップ**と呼ぶ。

- 小さなワークスペース（イシュー数千件）は、全部を取っても数 MB で、数秒で終わる。
- 最大のワークスペース（S1 でイシュー 50 万件、モデルの合計 500 万件）は、全部を取ると数百 MB になり、初回の起動（NFR-003：p95 10 秒）もブラウザのメモリーも持たない。
- 非公開のチームのデータは、メンバー以外のクライアントへ送ってはならない（[ADR-0004](0004-tenancy-and-permissions.md)）。

本家の形は、第三者の解析から次のように分かっている（[reverse-linear-sync-engine](https://github.com/wzhudev/reverse-linear-sync-engine)、[Reverse engineering Linear's sync magic](https://marknotfound.com/posts/reverse-engineering-linears-sync-magic/)、どちらも 2026-09-28 に確認。本家の保証ではない）。

- `type=full` のブートストラップでモデルの大部分を取り、`type=partial` でコメントや履歴などを後から取る。
- 同期グループ（利用者、チーム、ロール）を購読し、そのグループのモデルと差分だけを受ける。グループに加わると、そのグループのモデルを取りに行く。
- 遅延の読み込みは「部分の索引」（例：あるイシューのコメント）を記録し、同じものを二度取らない。
- 手元のデータがあれば、そこから起動し、`lastSyncId` の後の差分だけを取る。

本家の講演は、データが大きくなったときに「いつ、どれをメモリーに読み込むか」が課題になったと述べている（[Scaling the Linear Sync Engine](https://linear.app/now/scaling-the-linear-sync-engine)、2023-06-29、2026-09-28 に確認）。

## Options

1. **ワークスペースの大きさで、全体と部分のブートストラップを切り替える。** 部分では、最初に要るモデルだけを取り、残りを遅延で読む。差分は同期グループで絞る
2. **常に全体のブートストラップ**（すべてのモデルを手元に持つ）
3. **常に画面ごとの問い合わせ**（手元には開いたものだけを持つ。Replicache・Zero の問い合わせの単位に近い）

## Decision

1 を採用する。詳細は bootstrap-and-partial-sync の領域で決める。

### モデルの読み込みの方針

モデルの定義（スキーマ）に、モデルごとの読み込みの方針を書く。

| 方針 | 意味 | 例 |
| --- | --- | --- |
| `instant` | ブートストラップで必ず取る | 利用者、チーム、ワークフローの状態、ラベル、サイクル、プロジェクト、イニシアチブ、保存したビュー、自分の通知（直近） |
| `partial` | 全体のブートストラップでは取る。部分のブートストラップでは、条件に合うものだけ取り、残りは遅延で読む | イシュー（部分では、未完了のものと、30 日以内に完了・取り消したもの） |
| `lazy` | ブートストラップでは取らない。部分の索引の単位で、要るときに取る | コメント、イシューの履歴、添付の情報、アーカイブしたモデル、本文の CRDT の状態 |

- 条件（30 日など）は仮の値にし、E3 の PoC で決める。

### ブートストラップの種類

| 種類 | いつ | 何をする |
| --- | --- | --- |
| 全体 | 手元にデータがなく、見てよい範囲のモデルの数が閾値以下（仮に 5 万件） | `instant` と `partial` のすべてを取る |
| 部分 | 手元にデータがなく、閾値を超える | `instant` のすべてと、`partial` の条件に合うものを取る。残りは遅延で読む |
| 手元から | 手元に使えるデータがある | IndexedDB から起動し、手元の `last_sync_id` の後の差分だけを取る。サーバーを待たずに画面を出す |
| やり直し | 手元の `last_sync_id` が同期のログの保持の外、または取り戻す差分が多すぎる（仮に 5 万件超）、または手元の DB のスキーマを移行できない | 手元のモデルを捨て、全体か部分のブートストラップをする。**outbox は残す**（[ADR-0005](0005-client-persistence-and-offline.md)） |

- **一貫した写し**：Sync API は、1 つの読み取りのスナップショット（`REPEATABLE READ`）の中で、ワークスペースの `last_sync_id`（= `S`）とモデルを読む。クライアントは写しを当てた後、`S` の後の差分を受ければよい。Aurora の reader から読んでも、`S` が同じスナップショットから来るので、遅れは問題にならない。
- **ストリーム**：応答は、1 行 1 モデルの JSON の列（NDJSON）を圧縮して流す。最初の行に `S`・購読する同期グループ・スキーマの版を置く。クライアントは届いた順に IndexedDB へ書き、全部そろう前でも `instant` のモデルがそろったら画面を出す。
- ブートストラップの応答は、ワークスペースと `S` の組でキャッシュしない（権限で中身が変わるため）。負荷は capacity の領域で見積もる。デプロイの後に全クライアントが一斉にやり直すことがないよう、サーバーの版の更新ではやり直しを起こさない。

### 遅延の読み込みと部分の索引

- 遅延の読み込みは、`(モデル, 索引のフィールド, 値)` の単位で求める（例：`Comment` の `issue_id = X`）。応答は、行と、読んだ時点の `sync_id`（`as_of`）を返す。
- クライアントは、読み込んだ単位を**部分の索引**として IndexedDB に記録し、次からはサーバーへ求めない。
- 遅延の読み込みの行と、同時に届く差分の行がぶつかったら、行ごとの `updated_sync_id`（その行を最後に変えた `sync_id`）が大きい方を残す。差分と読み込みの順序に頼らない。
- 購読している同期グループの差分は、遅延のモデルのものも含めて、すべて受けて IndexedDB に書く。部分の索引がそろっていない単位は、「一部だけ手元にある」として扱い、画面ではサーバーから読み込むまで読み込み中と示す。

### 同期グループ

- モデルの各行は、1 つ以上の同期グループに属する。グループは、モデルの定義に書いた規則で決まる（例：イシューはチームのグループ、コメントはそのイシューのチームのグループ）。
- グループの種類は次の 4 つ。

| グループ | 購読する人 | 含むもの |
| --- | --- | --- |
| `workspace` | ワークスペースの全メンバー | 利用者、公開のチームの一覧、ワークスペースの設定のうち全員が見てよいもの |
| `team:<id>` | 公開のチームは全メンバー。非公開のチームはそのチームのメンバーだけ | チームのイシュー、状態、ラベル、サイクル、コメントなど |
| `user:<id>` | その人だけ | 通知、個人のビュー、下書き、個人の設定 |
| `role:admin` | 管理者とオーナー | 連携の設定、請求、招待の管理 |

- 購読するグループは、サーバーが権限から決める（[ADR-0004](0004-tenancy-and-permissions.md)）。クライアントが指定したグループは信じない。
- **グループをまたぐ移動**（イシューを別のチームへ移す）：Writer は、変更の行に移動の前と後のグループを両方付ける。Gateway は、後のグループを購読する接続には行の全体を、前のグループだけを購読する接続には「手元から消す」操作を送る。
- **グループへの参加**：参加は `user:<id>` のグループの差分として届く（`sync_id = M`）。Gateway は、その接続の購読に新しいグループを足し、`M` の後の差分を送り始める。クライアントは、そのグループの部分のブートストラップ（写しの `S' ≥ M`）をする。重なった行は `updated_sync_id` で決める。
- **グループからの脱退**（非公開のチームから外された、チームが非公開になった）：クライアントは、そのグループだけに属するモデルを、メモリーと IndexedDB から消す。そのモデルへの未確定のトランザクションは、拒否されるので outbox から外し、本人に示す。オフラインの間に外された場合に備え、再接続の握手でサーバーが今の購読の一覧を返し、クライアントは一覧にないグループのモデルを消す。

### 同期のログの保持

- `sync_actions` は、仮に 30 日持つ。30 日より古い `last_sync_id` のクライアントは、やり直しのブートストラップをする。期間は法務の L5 と、やり直しの頻度（ブートストラップの負荷）を見て、E3 で決める。

- 2 を採らない理由：最大のワークスペースで NFR-003 と、ブラウザのメモリーを満たせない。
- 3 を採らない理由：一覧・ボード・フィルターの切り替えのたびにサーバーを待ち、NFR-001 を満たせない。オフラインで開いていない画面が使えない。
- 1 は、小さなワークスペースでは 2 と同じ単純さを保ち、大きなワークスペースだけに遅延の読み込みの複雑さを払う。

## Consequences

- 良くなること：
  - 小さなワークスペースは、全部を手元に持ち、すべての操作が即座で、オフラインでも全部見える。
  - 大きなワークスペースでも、初回の起動が一定の時間に収まる。
  - 権限の絞り込みを、差分・ブートストラップ・遅延の読み込みで同じ同期グループの判定にまとめられる。
- 引き受けるコスト：
  - 部分のブートストラップでは、オフラインで見えないデータ（古い完了のイシュー、読んでいないコメント）がある。画面で「手元にない」ことを示す必要がある。
  - フィルターとビューは、手元にないデータを含むことがある。手元の評価とサーバーの評価の組み合わせが要る（views-and-filters の領域）。
  - グループの移動・参加・脱退の処理は、漏れがそのまま情報の漏えいになる。性質ベーステストで確かめる。
  - 同期のログの保持の外に出たクライアントのやり直しは、大きなワークスペースでは重い。

## Confirmation

- 性質ベーステスト（シミュレーター）：
  - 任意のグループの参加・脱退・移動の列の後、各クライアントの手元（メモリーと IndexedDB）のモデルが、その時点で見てよいモデルの集合と一致する。脱退したグループだけに属するモデルが残らない。
  - 全体・部分・手元から・やり直しのどの経路で起動しても、同じ差分を受けた後の状態が一致する。
  - 遅延の読み込みと差分の到着の順序を入れ替えても、結果が変わらない。
- 結合テスト：写しの読み取りの途中で書き込みがあっても、`S` の後の差分を当てた結果がサーバーと一致する。
- 計測（CI と RUM）：基準のワークスペース（イシュー 50 万件）で、部分のブートストラップの操作できるまでの時間が p95 10 秒以内（NFR-003）。
