# ADR-0020: モデルの ID はクライアントが振る UUIDv7。人が読む番号はチームごとの数から Writer が確定の時に振り、再利用しない。チームを移したイシューは番号を振り直し、古い識別子は別名の表で引く

## Context

[ADR-0002](0002-sync-model.md) で、モデルの ID はクライアントが UUIDv7 で振り、人が読む番号（`ENG-123`）は Writer がチームごとの数で確定の時に振ると決めた。残る問いは次のとおり。

- チームの識別子（`ENG`）の形と、変えたときの古い識別子の扱い。
- イシューを別のチームへ移したときの番号。
- 番号の再利用。
- 番号が決まる前（オフラインを含む）の参照と表示。

本家の公式の文書は次のように書いている（いずれも 2026-09-28 に確認）。

- 番号は、作った順に続く（[Create issues](https://linear.app/docs/creating-issues)）。
- 別のチームへ移すと、新しい識別子と URL になる。古い URL は転送され、古い識別子で検索しても今のイシューが出る。本文の中の古い識別子の参照は、見た目は古いままで、押せば転送される（[Edit issues](https://linear.app/docs/editing-issues)）。

チームの識別子の長さ・文字の制約と、識別子を変えたときの古い識別子の扱いは、公式の資料で確かめられなかった（未検証）。

## Options

移動の番号：

1. **移った先のチームで番号を振り直し、古い `(チーム, 番号)` を別名の表に残す**（本家と同じ振る舞い）
2. 番号を変えず、元のチームの識別子のまま持ち続ける
3. ワークスペースで 1 つの番号にする（チームの接頭辞は表示だけ）

本文の中の参照：

- a. **ID で持ち、描く時に今の識別子にする**
- b. 識別子の文字列で持つ

## Decision

1 と a を採用する。詳細は [data-model-and-schema.md](../architecture/data-model-and-schema.md) の 5 節。

- ID はすべて UUIDv7。Writer は版と変種を確かめ、時刻が 1 日以上先のものを拒否する。過去の側は制限しない。
- チームの識別子は `^[A-Z][A-Z0-9]{0,6}$`、ワークスペースの中で一意（大文字・小文字を区別しない）。変えたら古い識別子を `team_key_aliases` に残し、他のチームに使わせない。
- 番号は `teams.next_issue_number` から Writer が `create` の適用の時に振る。`server_only`。ワークスペースの行のロックの中なので、番号の順は確定の順である。番号は再利用しない。
- クライアントは ack の `server_ops` で番号を受ける。それまでは `ENG-…` と示し、URL は ID の形（`/issue/<uuid>`）で開ける。
- 移動では、Writer が同じトランザクションで移った先の番号を振り、前の `(team_id, number)` を `issue_aliases` に書く。別名の行は今のイシューの同期グループに入れる。
- 本文の中のメンション・参照は ID で持ち、描く時に今の識別子にする。本家は古い識別子の見た目が残るが、ID で持てば移動の後も今の識別子で描ける。
- 2 を採らない理由：移った先のチームの一覧で、接頭辞の違うイシューが混ざり、チームの番号の意味（そのチームの何番目か）が崩れる。本家の振る舞いとも違う。
- 3 を採らない理由：大きなワークスペースで番号が大きくなり、チームごとの番号という本家の慣れた形から離れる。番号の行がワークスペースで 1 つになるのは今と同じだが、表示の利点を失う。
- b を採らない理由：移動と識別子の変更のたびに、本文の文字列が古くなる。CRDT の本文を書き換える操作が要る。

## Consequences

- 良くなること：
  - 番号の振り方がワークスペースのロックの中で決まり、重なりがない。
  - 移動・識別子の変更の後も、古い識別子・URL・本文の参照が今のイシューに届く。
  - オフラインで作ったイシューも、参照を先に作れる。
- 引き受けるコスト：
  - 別名の表と、解決の順の分だけ、識別子の解決が複雑になる。
  - 仮の番号の間、利用者が識別子をコピーできない（URL の形を使う）。
  - 別名が見てよくない人へ漏れない規則（今のイシューのグループに入れる）を守る必要がある。

## Confirmation

- 性質ベーステスト：PROP-SCHEMA-003（番号の一意と `resolve`）、PROP-SCHEMA-004（別名の権限）。
- 結合テスト：同じチームに 2 つの Writer のタスクから同時に作っても、番号が重ならず、確定の順に並ぶ。
- 表駆動テスト：`resolve` の順（今の識別子 → チームの別名 → 番号 → イシューの別名）。
- DB：`(workspace_id, team_id, number)` の一意の索引。
