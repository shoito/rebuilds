# ADR-0044: 取り込みは段置きと対応付けと試しの実行の後に、Writer（`origin = import`）へ 200 変更の束で、ワークスペースの枠（1 秒 100 変更、ロックの待ちで半分）で書く。ID は元の記録から決まる UUIDv7 にし、やり直しを冪等にする。取り消しは 7 日、人が触れていない行だけ

## Context

intent は、Jira・GitHub Issues・Asana・Shortcut・CSV からの取り込みを MVP に含め、K8 で「Jira のイシュー 1 万件を 30 分以内、対応付けの誤り 0 件」を求める。

1 つのワークスペースの書き込みは、`sync_id` を振る行のロックで直列になり、上限は 1 秒 300 変更ほど（[ADR-0002](0002-sync-model.md)、[ADR-0054](0054-per-workspace-write-admission.md)）。README の 6 節は、インポートが他の利用者の書き込みを待たせうることを挙げ、束ね方をこの領域で決めるとしている。[sync-engine.md](../architecture/sync-engine.md) の 5.2 節は、インポートの 1 回の DB のトランザクションを 200 件までと置いた。

本家は、取り込み済みのイシューを飛ばすやり直しと、期間を限った取り消しを持つ（[Import issues](https://linear.app/docs/import-issues)、2026-09-28 に確認）。

## Options

書き込みの経路：

1. **Writer を通す（検証・派生・`sync_actions`・差分を普通と同じにする）**
2. 別の一括の経路（DB への直接の `COPY` と、`sync_actions` のまとめての生成）

流量：

- a. **ワークスペースの `import` の枠（既定 1 秒 100 変更）と、ロックの待ちでの自動の調整**
- b. 固定の流量
- c. 流量を制御しない（夜間に流す）

冪等：

- x. **元の記録から決まる UUIDv7 のモデルの ID と `client_tx_id`、`import_items` の対応表**
- y. `import_items` の対応表だけ（ID は毎回乱数）

## Decision

1・a・x を採用する。詳細は [import-export.md](../architecture/import-export.md) の 3〜6 節。

- ジョブは `fetching` → `mapping` → `planned` → `committing` → `done` の状態を持つ。取り出した記録は S3 に正規化して段置きし（30 日）、管理者が対応付けを決め、試しの実行で件数の表を確かめてから書く。
- 1 つのイシューとその依存を 1 つのトランザクションにし、1 回の Writer の呼び出しを 200 変更までにする。枠は既定 1 秒 100 変更、直近 30 秒のロックの待ちの p99 が 50ms か、利用者の送信から ack の p99 が 300ms を超えたら半分にし、落ち着いたら少しずつ戻す。1 つのクラスタで同時に書くジョブは 3 まで。
- `origin = import` だけに、`created_at`・作者・完了の時刻を操作の値で受けることを許す（DT-IMPORT-002）。通知・Slack・連携の自動化は起こさず、Webhook は `include_import` のものだけ、検索は `search-bulk`。
- モデルの ID は、元の作成の時刻を上位のビットに、`(workspace_id, source_key, 種類, source_id)` のハッシュを残りに入れた UUIDv7。`client_tx_id` は同じ作り方で、時刻の部分は取り込みを始めた時刻にする。
- 取り消しは 7 日以内。取り込みの後に `import` 以外の変更を受けた行とその子は残す。
- 2 を採らない理由：検証・派生・同期グループ・履歴を別に作ることになり、同期の正しさ（収束、NFR-008）の試験を 2 つの経路に持つ。Writer のロックを取らない書き込みは `sync_id` の順を壊す。
- b を採らない理由：大きなワークスペースで利用者が多い時間に、利用者の操作を待たせる。小さなワークスペースでは遅すぎる。
- c を採らない理由：取り込みはワークスペースの始めに行い、利用者がすぐに使いたい。
- y を採らない理由：落ちた束の送り直しで、`import_items` を書く前に落ちると重複の行ができる。

## Consequences

- 良くなること：
  - 取り込みの行が、普通の行と同じ規則で検証・配信される。
  - 落ちても、やり直しても、重複しない。
  - 利用者の操作を待たせない。
- 引き受けるコスト：
  - 取り込みの速さは 1 秒 100 変更ほどに縛られる。イシュー 10 万件の取り込みは 2 時間ほどかかる。
  - Writer に `origin = import` の例外（DT-IMPORT-002）を持つ。
  - オフラインのクライアントが戻った時に、`too_far` でやり直しになりうる。

## Confirmation

- 性質ベーステスト：PROP-IMPORT-001（冪等）、PROP-IMPORT-002（取り消しの安全）、PROP-IMPORT-003（対応付けの保存）。
- 受け入れ試験（E11）：K8。取り込みの間の利用者の送信から ack の p99 300ms。
- E11 のインポートの spec は、法務の L3 の結論まで承認しない。
