# ADR-0028: フィルターは型の付いた JSON の木で持ち、共有のパッケージの 1 つの定義から、クライアントの評価の関数と SQL の生成を作る。空の値・文字の正規化・並びの比較を言語の側で決め、共有のテストの例の集まりと差分テストで一致を確かめる

## Context

ビューとフィルターは、クライアントの手元とサーバーの両方で評価する。

- 一覧の切り替えとフィルターは、手元の詰めた索引（M2）だけで答える（NFR-001、[ADR-0016](0016-memory-tiers-quota-and-offline-ux.md)）。
- 手元にないデータ（古い完了のイシュー）を含むビューは、サーバーで問い合わせる（[ADR-0003](0003-bootstrap-and-partial-sync.md) の Consequences）。
- 公開 API と、進捗の数え直し（[ADR-0027](0027-progress-stats-per-team-via-derive.md)）も、同じ条件を SQL で評価する。

2 つの評価の結果が違うと、サーバーから来た行が手元で消えたり、同じビューが人や経路で違う結果になったりする。違いの出やすいところは次のとおり。

- SQL の三値の論理（`NULL`）。`assignee <> 'A'` は担当なしの行を含まない。
- 文字の正規化と比較。PostgreSQL の照合と JavaScript の `<`（UTF-16 の単位）は順が違う。
- 「今日」「今のサイクル」の決め方（時計、タイムゾーン）。

本家は、フィルターを AND・OR の入れ子で組み、URL に反映する（[Filters](https://linear.app/docs/filters)、2026-09-28 に確認）。本家の評価の実装は公開されていない（未検証）。

## Options

1. **型の付いた JSON の木。共有のパッケージの 1 つの登録から、クライアントの評価と SQL の生成を作る。意味（空の値、正規化、順）を言語の側で決める**
2. 文字の問い合わせの言語（`assignee:me priority:>2` のような）を定義し、構文解析する
3. クライアントとサーバーで別々に実装し、結合テストで合わせる
4. サーバーだけで評価する（手元の評価をしない）

## Decision

1 を採用する。詳細は [views-and-filters.md](../architecture/views-and-filters.md) の 3・4 節。

- 文法は `and`・`or`・`not` と条件 `{f, op, v}`。深さ 5、条件 50、8 KiB まで。保存の前に正準の形にする。
- フィールドは `packages/filter` に登録する（型、M2 の列、SQL の式）。M2 にないフィールドは「サーバー」の印を持ち、手元では評価しない。
- 空の値：`neq`・`nin`・`none`・`not_contains` は空を含み、比較は空を含まない。SQL は比較の式をすべて `COALESCE(式, false)` で包み、`IS DISTINCT FROM` を使う。
- 文字：共有の `normalizeForSearch`（NFKC、小文字、カタカナをひらがなへ）。サーバーは Writer が同じ関数で `title_norm` を書き、SQL は `strpos` で比べる。PostgreSQL の正規化の関数を使わない。
- 並び：文字は Unicode の符号位置の順（SQL は `COLLATE "C"`、クライアントは `cmpCodepoint`）。空は最後。最後に `id` を足す。
- 動的な値（`me`、今のサイクル、今日、相対の時刻）は、評価の前の解決の段で具体の値にする。サーバーの問い合わせには、クライアントが解決した木と文脈（`now`・`tz`・`me`）を送る。
- 一致の確認：`vectors/*.json` の例の集まりを、クライアントの評価と PostgreSQL の SQL の両方で走らせる。文法から無作為に作ったフィルターで差分テストを回し、失敗した例を集まりに足す。
- 2 を採らない理由：構文解析の誤りと、日本語の値（ラベルの名前）の引用の規則が増える。画面は条件を部品で組むので、文字の言語は要らない。後で検索の窓に文字の条件を足すなら、この木へ変換する。
- 3 を採らない理由：意味の違い（空の値、順）が、例で見つけた分しか合わない。
- 4 を採らない理由：NFR-001 を満たせない。オフラインでビューが使えない。

## Consequences

- 良くなること：
  - 同じビューが、手元・サーバー・公開 API で同じ結果になる。違いは差分テストで機械的に見つかる。
  - 空の値と順の意味が、SQL の癖でなく、文書に書いた規則で決まる。
- 引き受けるコスト：
  - SQL の式が素直な形より長くなり（`COALESCE`、`IS DISTINCT FROM`）、索引が効きにくい条件がある。サーバーの問い合わせは reader で行い、2 秒で打ち切る。
  - `title_norm` のサーバーの列を Writer が保つ。
  - 名前の並びは読みの順にならない（漢字の名前は符号位置の順）。

## Confirmation

- CI：共有のテストの例の集まりを、クライアント（Vitest）と PostgreSQL 18（Testcontainers）の両方で走らせる。
- 性質ベーステスト：PROP-VIEW-001（評価の一致）、PROP-VIEW-002（増分と全件）。
- lint：並べ方のコードで、文字の `<` と `localeCompare` を禁止する。
- 本番：`view_candidate_rejected` が 0 に近い。
