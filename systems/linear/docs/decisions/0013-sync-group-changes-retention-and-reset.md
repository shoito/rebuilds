# ADR-0013: 同期グループの参加・脱退は `SyncSubscription` の差分で表し、参加は部分のブートストラップ、脱退は 1 つの IndexedDB のトランザクションでの消去にする。ログは 30 日持ち、DR の切り替えと復元では `sync_epoch` を上げて、直近 15 分に確定した outbox を送り直す

## Context

[ADR-0003](0003-bootstrap-and-partial-sync.md) で、同期グループの参加・脱退・移動の扱いの方針と、`sync_actions` を仮に 30 日持つことを決めた。[ADR-0004](0004-tenancy-and-permissions.md) で、非公開への切り替えを 1 つのトランザクションで行うと決めた。残る問いは次のとおり。

- 参加・脱退を差分の中でどう表し、Gateway の絞り込みの切り替わりの位置をどう決めるか。
- 脱退の消去の単位と、消し漏れを防ぐ方法。
- ログの保持の境（`floor`）の管理と、保持の外のクライアントの扱い。
- リージョンの切り替え（NFR-007：RPO 1 分）や時点の復元で、同じ `sync_id` が別の変更に振り直されること。ADR-0002・0003 はこれを扱っていない。クライアントが確定を確かめて outbox から消した変更は、切り替えで失われても送り直されない。

第三者の解析によれば、本家は差分の G・S でグループの変化を知らせ、新しいグループのモデルを取りに行ってから残りの差分を当て、外れたグループのモデルを IndexedDB から消す（[reverse-linear-sync-engine](https://github.com/wzhudev/reverse-linear-sync-engine)、2026-09-28 に確認。本家の保証ではない）。本家のログの保持の期間は**未検証**。

## Options

グループの変化の表し方：

1. **`SyncSubscription` モデル（`user:<id>` のグループ）の `insert`・`delete`**
2. 専用の差分の種類（本家の G・S のような）

番号の世代：

- a. **ワークスペースに `sync_epoch` を持ち、DR の切り替えと時点の復元で上げる。上がったらクライアントはやり直し、確定して 15 分以内の outbox の行も送り直す**
- b. DR の後に `last_sync_id` を大きく飛ばして、番号の重なりを避ける
- c. 扱わない（RPO の範囲の喪失を受け入れる）

## Decision

1 と a を採用する。詳細は [bootstrap-and-partial-sync.md](../architecture/bootstrap-and-partial-sync.md) の 7・8 節。

- Writer は、メンバーシップ・ロール・チームの公開の状態を変えるトランザクションの中で、`can()` から購読を計算し直し、差を `sync_subscriptions` の `insert`・`delete` として書く。Gateway は、絞る前の列を順に処理し、その `sync_id` の直後から接続の購読を変える。
- 参加（`sync_id = M`）：クライアントはそのグループのブートストラップを `min_sync_id = M` で求め、`_u` と墓標の規則で書く。一斉の参加（非公開 → 公開）は 0〜30 秒の乱数で散らす。
- 脱退：1 つの IndexedDB のトランザクション（`strict`）で、`_g` の multiEntry の索引から、残りの購読に属さない行・被覆の鍵・`_meta.groups` を消し、墓標を書く。未確定のトランザクションは残し、サーバーの拒否を待つ。
- 握手の `welcome.groups` を正とし、手元との差を差分の前に処理する。
- 移動：Writer はイシューと依存の行の `sync_groups` を同じトランザクションで変え、`groups_before` 付きの `update` を書く。依存の行が 1 万を超えたら、残りを Worker が 1,000 行ずつ移す。
- ワークスペースから除外されたら、手元の DB を outbox ごと消し、件数を示す。
- `sync_actions` は 30 日（法務の L5 と E3 で確定）。保持のジョブは `floor_sync_id` を先に上げてからパーティションを落とす。`tx_results` は 90 日。
- やり直しの理由は `too_old`・`too_far`・`epoch`・`ahead`・`migration`・`corrupt`。どれでも `_outbox`・`_rejected`・`_blobs` を残す。`epoch` の一斉のやり直しは 0〜10 分に散らし、その間は古い手元のデータを示し、書き込みは outbox に入れる。
  > 2026-09-28 の注記：散らしの幅は既定 10 分のまま、DR の切り替えの後に大阪の reader と Sync API が広がりきらないときは、Ops のフラグ `ops.epoch_reset_spread_min` で 30 分まで伸ばせることにした（[capacity.md](../architecture/capacity.md) の 4.2 節、[runbooks/disaster-recovery.md](../runbooks/disaster-recovery.md) の B）。30 分にすると、全端末のやり直しの同時の数は約 330 になる。
- `sync_epoch` は、リージョンの切り替えと時点の復元で上げる。
  > 2026-09-28 の注記：`sync_epoch` を上げた後、書き込みを受ける前に、失った範囲の権限を狭める操作を別の記録からやり直す（[ADR-0058](0058-dr-permission-narrowing-journal.md)）。やり直しのブートストラップが、正しい購読で行われるようにするため。
- S2 のクラスタの移動は番号を保つので上げない。クライアントは outbox の行を確定の後 15 分 `done` で残し、`epoch` のやり直しで送り直す。生き残った変更は `tx_results` で前の結果が返り、失われた変更は 1 回だけ当たる。
- 2 を採らない理由：購読の変化は権限の変化から導かれる普通のデータで、モデルとして持てば、ブートストラップ・差分・監査が同じ仕組みで扱える。
- b を採らない理由：番号の重なりは避けられても、切り替えで失われた範囲の変更をクライアントが持っていたかどうかを確かめられない。クライアントの手元が、サーバーにない変更を含んだ状態のまま続く。
- c を採らない理由：NFR-005（収束）が、DR の後に崩れる。

## Consequences

- 良くなること：
  - 参加・脱退の位置が `sync_id` で決まり、Gateway・取り戻し・ブートストラップで同じ結果になる。
  - DR の切り替えの後も、全クライアントがサーバーと一致し、直近 15 分に確定した自分の変更は取り戻される（それより前の失われた変更は RPO の範囲として受け入れる）。
- 引き受けるコスト：
  - 非公開 → 公開の切り替えで、多数のクライアントが同時にブートストラップする。
  - `epoch` の一斉のやり直しは、Sync API と reader に大きな負荷をかける。散らす間、利用者は古いデータを見る。
  - outbox の行を 15 分長く持つ。

## Confirmation

- 性質ベーステスト（[ADR-0010](0010-deterministic-sync-simulator.md)）：PROP-BOOT-002（見てよい集合）、PROP-BOOT-004（やり直しで失わない）、PROP-BOOT-005（世代）、PROP-BOOT-006（保持の境）。
- DR の訓練（E12）：大阪への昇格の後、`sync_epoch` を上げ、合成監視のクライアントが一致し、直近の確定の送り直しが 1 回だけ当たることを確かめる。
- 本番：配信の監査で不一致 0 件（NFR-008）。やり直しの理由ごとの回数を監視する。
