# ADR-0002: ワークスペースごとに、サーバーが全順序を決める変更のログと単調な `sync_id` を持つ。クライアントは楽観的に当て、差分の上に載せ直す。競合はフィールドの型ごとの規則で解く

## Context

この題材は、ワークスペースのデータ（イシュー、コメント、サイクル、プロジェクト、ラベル、ビューなど数十種のモデル）を、多数のクライアントの手元に持たせる。クライアントは操作を即座に反映し（NFR-001）、オフラインでも書き（NFR-004）、最終的に全員が同じ状態に収束しなければならない（NFR-005）。

本家の形は、公開の講演と第三者の解析から次のように分かっている（[architecture/README.md](../architecture/README.md) の 1.3 節）。

- 変更はトランザクションとしてサーバーへ送り、サーバーが `lastSyncId` という 1 つの整数で順序を決める。
- クライアントは、確定の `lastSyncId` を受け、その差分が届くまで自分の変更を保持して載せ直す。
- 競合は大部分が LWW で、CRDT はイシューの本文にだけ使う（講演の要約。第三者）。
- 本家の文書は、オフラインの編集が他の人の変更を上書きしうると書いている（[Download Linear](https://linear.app/docs/get-the-app)、2026-09-28 に確認）。

課題管理のデータでは、同じフィールドへの同時の編集はまれである。一方で、権限（非公開のチーム）、参照の整合（削除したラベル、存在しない親）、ワークフローの規則（Duplicate はシステムだけが付ける）をサーバーで守る必要がある。

## Options

1. **サーバーが全順序を決めるログ（ワークスペースごと）＋クライアントの楽観的な適用と載せ直し＋フィールドの型ごとの競合の規則**
2. **すべてのモデルを CRDT で持つ**（Automerge・Yjs の文書、またはモデルごとの CRDT）。サーバーは中継と保存だけ
3. **中央の権威のプロセスがメモリーで状態を持つ**（Figma の形。ワークスペースごとに 1 つのプロセスが順序を決め、ジャーナルに書く）
4. **操作の変換（OT）**

`sync_id` の範囲として、次も比べた。

- a. **ワークスペースごとの数**
- b. 全ワークスペースで共通の 1 つの数（第三者の解析は、本家がこの形だと推定している。[reverse-linear-sync-engine](https://github.com/wzhudev/reverse-linear-sync-engine)、2026-09-28 に確認。本家の保証ではない）

## Decision

1 と a を採用する。詳細は sync-engine の領域で決める。

### 順序と `sync_id`

- **ワークスペースごとに、単調に増える `sync_id`（64 ビットの整数）を持つ。** Writer は、1 つの DB のトランザクションの中で、ワークスペースの行の `last_sync_id` を増やし（`UPDATE ... SET last_sync_id = last_sync_id + n RETURNING`）、モデルの表の変更と、変更ごとの `sync_actions` の行を書く。
- 行のロックがコミットまで続くので、**`sync_id` の順とコミットの順が一致する。** 読み手が「`sync_id` が x より大きい行」を読んでも、後から小さい `sync_id` の行がコミットされて見落とす、ということが起きない。PostgreSQL のシーケンスは、コミットの順と番号の順がずれるので使わない。チャンネルの行で数を振る Slack の ADR-0001 と同じ形である。
- b を採らない理由：全体で 1 つの数は、全ワークスペースの書き込みを 1 か所で直列にするか、番号の順とコミットの順のずれを別の仕組みで扱う必要がある。ワークスペースは互いに独立で、S2 でクラスタに分ける単位でもある（[ADR-0004](0004-tenancy-and-permissions.md)）。
- 1 つのワークスペースの書き込みは直列になる。S1 の上限を 1 秒 300 件と見込み、E2 の PoC で測る。足りなければ、ワークスペースごとに順序を振る単一の書き手（Writer のタスクへの割り当て）に替える ADR を書く。

> 2026-09-28 の注記：この ADR は、同じ `sync_id` が別の変更に振り直される場面（リージョンの切り替えで直近の確定を失う、ワークスペースを時点へ戻す）を扱っていなかった。[ADR-0013](0013-sync-group-changes-retention-and-reset.md) で、ワークスペースに番号の世代 `sync_epoch` を足し、その場面で上げて全クライアントをやり直させると決めた。クライアントの手元の版は `(sync_epoch, last_sync_id)` の組で表す（[ADR-0050](0050-disaster-recovery-and-sync-epoch-bump.md)）。

### 変更の形（トランザクション）

- クライアントは、操作を**トランザクション**にまとめる。種類は `create`・`update`・`delete`・`archive`・`unarchive` と、フィールドの型ごとの操作（下の表）。1 回の入力（1 つのキーの操作、1 回のドラッグ）が 1 つのトランザクションになる。
- 各トランザクションは、クライアントが振る `client_tx_id`（UUIDv7）と、作った時点でクライアントが知っていた `base_sync_id` を持つ。
- **冪等**：Writer は `(workspace_id, client_tx_id)` を記録し、同じトランザクションの再送には、前の結果（確定の `sync_id` か、拒否の理由）を返す。記録は同期のログの保持の期間より長く持つ。
- **検証はサーバーで行う。** 権限、型と範囲、参照の存在、ワークフローの規則を、クライアントと同じモデルの定義のコードで Writer が確かめる。拒否したトランザクションは、送り手にだけ理由を返し、ログに載せない。1 回の送信にまとめた複数のトランザクションは、1 つずつ独立に確定か拒否になる。
- モデルの ID は、クライアントが UUIDv7 で振る。サーバーを待たずに参照を作れる。人が読む識別子（`ENG-123` の番号）は、Writer がチームごとの数で確定の時に振る。確定まで、クライアントは仮の表示（`ENG-…`）を出す。

### 差分と配信

- `sync_actions` の 1 行は、`(workspace_id, sync_id, model, model_id, action, data, sync_groups)` を持つ。`action` は `insert`・`update`・`archive`・`unarchive`・`delete` と、同期グループの変化（[ADR-0003](0003-bootstrap-and-partial-sync.md)）。
  > 2026-09-28 の注記：同期グループの変化は、専用の `action` を足さず、`SyncSubscription` モデルの `insert`・`delete` で表すことにした。本文の CRDT の更新は `append` の `action` で運ぶ（[ADR-0007](0007-sync-actions-and-range-proof-deltas.md)）。
- Sync Gateway は、ワークスペースの差分を `sync_id` の順に受け、接続の同期グループで絞ってから送る。
- **絞った後の差分は、`sync_id` が飛び飛びになる。** 番号の連続では欠けを判定できない。そこで、Gateway は差分をパケットにまとめ、各パケットに「`(from, to]` の範囲のうち、この接続が見てよい変更は、これで全部」という範囲を付ける。変更が 1 つもない範囲も、空のパケットとして知らせる。クライアントは、受けた範囲がつながっているかで欠けを判定し、欠けたら Sync API から範囲を指定して取り戻す。
- 配信（Valkey の pub/sub）はベストエフォートにする。欠けは上の範囲で必ず見つかり、取り戻せる。

### 楽観的な適用と載せ直し（rebase）

- クライアントのモデルの状態は、次の 2 層で決まる。
  1. **確定した状態**：受けた差分を `sync_id` の順に当てたもの。IndexedDB に保存する。
  2. **未確定のトランザクションの列**：outbox にあり、確定を差分で確かめていないもの。
- 画面に出す状態は、確定した状態の上に、未確定の列を順に当てたものである。
- 差分が届いたら、確定した状態に当て、その上に未確定の列を当て直す。同じフィールドに自分の未確定の変更があれば、画面では自分の値のままにする（自分の変更が確定すれば、どのみちサーバーでも後に来る）。
- 自分のトランザクションの確定の応答（`sync_id = s`）を受けても、すぐには未確定の列から外さない。`s` までの差分を受けた時点で外す。応答と差分の間の順序の揺れで、画面が一瞬古い値に戻ること（ちらつき）を防ぐ。
- 拒否されたトランザクションは、未確定の列から外し、画面を当て直し、理由を本人に示す。

### 競合の規則（フィールドの型ごと）

どれも「サーバーに確定した順」で決まる。規則はモデルの定義（スキーマ）に書き、クライアントとサーバーが同じコードで当てる。スキーマに規則のないフィールドは、コードの生成で失敗させる。

| フィールドの型 | 例 | 操作 | 競合の解き方 |
| --- | --- | --- | --- |
| 単一値 | タイトル、状態、優先度、担当、見積もり、期日、サイクル、プロジェクト、親 | `set(field, value)` | LWW（後に確定した方が勝つ）。フィールドごとに独立で、別のフィールドへの変更は競合しない |
| 集合 | ラベル、購読者、関連 | `add(field, item)`・`remove(field, item)` | 要素ごとに後に確定した操作が勝つ。配列全体を LWW にしない。同時に別のラベルを足した 2 人の変更は、両方残る |
| 並び | 一覧・ボードの手動の並び（`sort_key`）、サブイシューの並び | `set(sort_key, key)` | 分数インデックスの文字列の鍵（base-62、可変長）。鍵は LWW。同じ鍵が重なったら、Writer が後の方の鍵を振り直し、差分として配る。鍵が 48 バイトを超えたら、兄弟の鍵をまとめて振り直す（Figma の ADR-0010 と同じ考え方） |
| 数の加算 | 手動で数える値（まれ） | `increment(field, n)` | 加算は可換なので、すべて足す。集計の値（完了したイシューの数、見積もりの合計）はフィールドに持たず、クライアントとサーバーが計算する |
| 採番 | イシューの番号 | サーバーだけが振る | 競合しない |
| 本文 | イシューの説明、プロジェクトの説明 | CRDT の更新（不透明なバイト列）を `append` する | 更新は可換で、すべて合わさる。同期のログには更新をそのまま載せ、順序は他の変更と同じ `sync_id` で決める。CRDT の部品と保存の形は editor-and-descriptions の領域で決める |

> 2026-09-28 の注記：当初は「本文」の行に「コメントの本文」を含め、CRDT にするとしていた。[ADR-0022](0022-comments-anchors-mentions-attachments.md) で、コメントの本文は ProseMirror の JSON を LWW で持つ（書けるのは作った人だけ）と決めたので、コメントを外した。CRDT はイシューとプロジェクトの説明だけに使う。

> 2026-09-28 の注記：「並び」の行の「兄弟の鍵をまとめて振り直す」は、[ADR-0008](0008-conflict-rules-and-fractional-keys.md) で、鍵の前後の窓（65 個から最大 1,024 個）だけを振り直し、足りなければ Worker が範囲の全体を振り直す形に細かくした。チームの手動の並び（数十万件）で、1 回の書き込みが大きくならないようにするためで、方針は変えない。

- **削除とアーカイブ**：削除したモデルへの `update` は拒否する。アーカイブしたモデルへの `update` は受け付ける（本家の自動のアーカイブの後にも戻せるため。規則の詳細は issues-and-workflow の領域の決定表にする）。削除した親・ラベル・サイクルを参照する変更は拒否する。親を削除したときの子の扱いはモデルの定義に書く（連鎖の削除か、参照を外すか）。
- **親子の循環**：親の変更で循環ができる場合、Writer が拒否する。
- **上書きの記録**：`update` の `base_sync_id` より後に、同じフィールドが他の人に変えられていた場合、LWW のまま当てるが、イシューの履歴に「上書き」として前の値を残す。オフラインの時間が長い（`base_sync_id` が 1 時間以上前）トランザクションで上書きが起きたら、本人に知らせる。本家の文書が述べる上書きの問題（上の Context）に、記録と通知で備える。

### 他の題材との比較

| 項目 | この ADR（Linear） | Notion（Notion の ADR-0005・0010〜0012） | Figma（Figma の ADR-0002） |
| --- | --- | --- | --- |
| 順序を決める場所 | ワークスペースごとの `sync_id` を DB の行のロックで振る | ページごとの `seq` を DB で振る（Slack の ADR-0001 と同じ考え方） | ファイルごとのプロセスがメモリーで `seq` を振る |
| 順序の範囲 | ワークスペース全体（数十種のモデル） | ページ | ファイル |
| 手元に持つもの | ワークスペースの見てよい範囲（部分の同期を含む） | 開いた・オフラインに指定したページ | 開いたファイル |
| 単一値の競合 | フィールドごとの LWW | 同じ（負けた値を記録） | プロパティごとの LWW |
| テキスト | 本文だけ CRDT | ブロックごとの CRDT（Fugue＋Peritext） | プロパティとして LWW |
| 並び | 分数インデックス | 前後の兄弟のアンカー | 分数インデックス |
| オフライン | 長いオフラインの編集を送り直す（7 日） | 長いオフラインの編集を統合する | 短い切断だけ |

- **2（すべて CRDT）を採らない理由**：
  - CRDT は定義上どの変更も受け入れるので、サーバーが権限・参照・ワークフローの規則に反する変更を拒否できない。
  - 非公開のチームのデータを、権限のない人へ送らない部分の同期（[ADR-0004](0004-tenancy-and-permissions.md)）と、全員が同じ文書を複製する CRDT の前提が合わない。
  - 課題管理のフィールドは単一値が多く、同時の編集がまれである。墓標とメタデータの費用に見合わない。長いオフラインからの取り戻しも、1 つの整数（`sync_id`）の後を求めるだけで済む。
  - ただし、同時の編集が起きやすく、失うと痛い本文だけは CRDT にする（Notion がテキストだけ CRDT にしたのと同じ判断）。
- **3（中央のメモリーの権威）を採らない理由**：Figma は 1 つのファイルの中で、多数のプロパティが秒間に何度も変わる。そこでは、メモリーの権威が DB の往復を避ける利点が大きい。課題管理では、ワークスペースの変更は 1 人あたり数秒に 1 回で、DB のトランザクションで順序を振っても間に合う。ワークスペース全体（最大で 1,000 万件のイシュー）をメモリーの権威に載せる費用と、プロセスの割り当て・障害の引き継ぎの複雑さに見合わない。
- **4（OT）を採らない理由**：フィールドの置き換えが大部分で、変換の関数が要らない。本文は CRDT で扱う。

## Consequences

- 良くなること：
  - 順序が 1 本なので、欠けの検出、取り戻し、収束の確かめが単純になる。長いオフラインの後も、`sync_id` の後を求めるだけで追いつける。
  - Writer が全変更を検証するので、権限と整合をサーバーで守れる。
  - 競合の規則がスキーマに書かれ、クライアントとサーバーで同じコードになる。
- 引き受けるコスト：
  - 1 つのワークスペースの書き込みが直列になり、大きなワークスペースの書き込みの上限になる（[architecture/README.md](../architecture/README.md) の 6 節）。
  - 単一値の LWW では、オフラインの古い変更が新しい変更を上書きしうる。記録と通知で見えるようにするが、防ぎはしない。
  - 同期グループで絞るため、Gateway が接続ごとに範囲付きのパケットを作る処理が要る。
  - `sync_actions` が大きく増える。保持の期間と、期間の外のクライアントのやり直しを決める必要がある（[ADR-0003](0003-bootstrap-and-partial-sync.md)）。

## Confirmation

- 性質ベーステスト（決定的なシミュレーター。fast-check でシードから操作・切断・並べ替え・重複・再起動の列を作る）：
  - 変更が止んだ後、全クライアントの見てよい範囲のモデルが、サーバーの状態と一致する（収束）。
  - 同じ `client_tx_id` のトランザクションは、何回送っても 1 回だけ効く（冪等）。
  - クライアントが受けた範囲がつながっていれば、見てよい変更を 1 つも落としていない（欠けの検出の完全さ）。
  - 分数インデックスの鍵は、振り直しの後も全クライアントで同じ並びになる。
  - 集合の操作は、同時の `add` を失わない。
- 結合テスト：2 つの Writer のタスクで同じワークスペースに同時に書いても、`sync_id` の順とコミットの順が一致する（読み手の見落としが 0 件）。
- CI：スキーマの定義で、競合の種類のないフィールドがあれば、コードの生成を失敗させる。
- 本番：収束の監査（クライアントのモデルのハッシュを抜き取りでサーバーと突き合わせる）で、説明のつかない不一致を 0 件に保つ（NFR-005）。
