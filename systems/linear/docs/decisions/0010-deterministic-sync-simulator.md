# ADR-0010: 収束は、本物の同期のコードを 1 つのプロセスで動かす、シードから再現できる決定的なシミュレーターで確かめる。PR ごとに 2,000 の列、夜間に 20 万の列を回し、失敗したシードを回帰テストに残す

## Context

同期エンジンの誤りは、収束しない・データを失う・見てはいけないデータが届く、の形で現れる。どれも、特定の順序（ack と差分の入れ替わり、送信の途中の落ち、グループの変化と差分の重なり）でしか起きず、例示のテストや E2E のテストでは見つけにくい。[ADR-0002](0002-sync-model.md)・[ADR-0003](0003-bootstrap-and-partial-sync.md)・[ADR-0005](0005-client-persistence-and-offline.md) の Confirmation は、どれも決定的なシミュレーターでの性質ベーステストを求めている。AGENTS.md は、失敗したシードを回帰テストとして残すことを求めている。

決めることは次のとおり。

- シミュレーターで動かすコードを、本物にするか、模型にするか。
- 非決定性（時刻、乱数、ネットワーク、非同期の順序）をどう抑えるか。
- 回す回数と、CI での扱い。

## Options

1. **本物の同期のコード（クライアントの核、Writer の検証と適用、Gateway の絞り込みと範囲の証明、Sync API の取り戻しとブートストラップ）を、差し替えた I/O（メモリーの DB と IndexedDB、仮想の時計、経路ごとの待ち行列）の上で 1 つのプロセスで動かす**
2. 同期の方式の模型（TLA+ など）を別に書いて検査する
3. 本物の構成（Aurora、Valkey、ブラウザ）で、障害注入の E2E を多く回す

## Decision

1 を採用する。3 は障害注入の試験（E12）として補いに使う。詳細は [sync-engine.md](../architecture/sync-engine.md) の 12 節、[bootstrap-and-partial-sync.md](../architecture/bootstrap-and-partial-sync.md) と [client-store-and-offline.md](../architecture/client-store-and-offline.md) のテストの節。

- **I/O の境を作る。** 同期の核のコードは、時刻・乱数・タイマー・ネットワーク・IndexedDB・Web Locks・BroadcastChannel を、注入されたインターフェースだけから使う。本番とシミュレーターで実装を差し替える。lint で、核のパッケージから `Date.now`・`Math.random`・`setTimeout`・`indexedDB`・`WebSocket` を直接使うことを禁止する。
- **決定性**：乱数は 1 つのシードから分けて作る。時刻は仮想の時計。非同期の処理は、シミュレーターの待ち行列が順番を決める。接続の中の順序は保ち、経路の間（ack と差分、取り戻しと生の差分、タブの間の通知）の順序は揺らす。
- **模したメモリーの IndexedDB**：トランザクションの原子性を守る。クライアントの落ちでは、`strict` でコミットしたものは残り、`relaxed` でコミットしたものは最後の k 件を失いうる（電源の喪失の模擬）。
- **出来事**：操作、切断、再接続、クライアントの落ちと再起動、書き手のタブの交代、Writer の ack の前の落ち、Valkey の喪失と重複、Relay・reader の遅れ、Gateway の落ち、グループの参加・脱退・移動・非公開への切り替え、遅延の読み込み、保持の外への押し出し、DR の切り替え（`sync_epoch`）、クライアントの版の更新、保存の上限と消去。
- **判定**：操作が止み、全員が追いついた後に、各性質（PROP-SYNC-*・PROP-BOOT-*・PROP-STORE-*）を確かめる。途中でも確かめる性質（見てよくないデータが手元にない、ちらつきなし）は、出来事ごとに確かめる。
- **回数**：PR ごとに 2,000 の列（各 200 の出来事、クライアント 2〜6）。同期エンジン・競合の規則・ブートストラップ・outbox に触れる PR は、夜間と同じ 20 万の列を必須にする。夜間は 20 万の列。
- **回帰**：fast-check で失敗した列を縮め、`sim/regressions/<日付>-<短い名前>.json`（シード、出来事の列、期待）に残す。CI は毎回すべてを再生する。削除や期待の緩和でテストを通さない（AGENTS.md）。
- 2 を採らない理由：模型と本物のコードのずれが残り、実装の誤り（範囲の終わりの計算、IndexedDB の保存の順）を見つけられない。方式の検討に模型を使うことは妨げない。
- 3 だけにしない理由：遅く、失敗を再現できない。

## Consequences

- 良くなること：
  - まれな順序の不具合を、PR の段階で再現できる形で見つけられる。
  - 失敗したシードが回帰テストとして増え、同じ誤りを繰り返さない。
- 引き受けるコスト：
  - 同期の核の I/O をすべて注入にする設計の制約と、lint の維持。
  - メモリーの DB と Aurora の違い（ロックの挙動、reader の遅れ）は、結合テストと障害注入で別に確かめる必要がある。
  - CI の時間。PR ごとの 2,000 の列を 5 分以内に収めるよう、並列に回す。

## Confirmation

- CI：シミュレーターの性質ベーステストと回帰の再生を、同期の核に触れる PR の必須のチェックにする。
- lint：核のパッケージから、時刻・乱数・タイマー・ネットワーク・保存の API の直接の使用を禁止する。
- 定期の確かめ：わざと誤りを入れた版（範囲の終わりを 1 つずらす、ack で `pending` を外す）で、シミュレーターが失敗を見つけることを、四半期ごとに確かめる（ミューテーションの試験）。
