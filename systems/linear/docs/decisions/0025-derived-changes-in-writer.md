# ADR-0025: ある変更から決まる別の変更は、共有のコードの `derive` で求める。Writer は同じトランザクションで書き、クライアントは同じコードで予測して画面に重ねる

## Context

イシューの規則には、利用者が送った変更から、別の変更が決まるものが多い。

- ラベルのグループの中から 1 つだけ付けられる（[Issue labels](https://linear.app/docs/labels)、2026-09-28 に確認）。ラベルは `set` の競合（[ADR-0002](0002-sync-model.md)）なので、同時に同じグループの別のラベルを足すと、両方が残る。
- 状態を変えると、完了・取り消しの時刻が決まる。
- 重複にすると、状態が Duplicate になる（[ADR-0024](0024-hierarchy-relations-duplicates-and-triage.md)）。
- 子がすべて完了すると親も完了する設定がある。
- 担当やメンションされた人が購読者になる。
- 履歴と上書きの記録を残す（[ADR-0008](0008-conflict-rules-and-fractional-keys.md)）。
- チームを移すと、チームのラベルやプロジェクトが外れる。

どれも、オフラインで作った変更が、他の人の変更の後に確定の順で当たる場面で、正しく決まる必要がある。画面は、サーバーを待たずに結果を見せたい（NFR-001）。

## Options

1. **共有のコードの `derive(state_before, tx) → ops` で求める。Writer は同じ DB のトランザクションで派生の変更を当てて `sync_actions` に書き、クライアントは同じ関数で予測して `pending` に重ねる**
2. クライアントが派生の変更もトランザクションに入れて送り、Writer は確かめるだけ
3. Writer がコミットの後に、Worker で派生の変更を別のトランザクションとして当てる
4. 派生の値を保存せず、読み出しの時に計算する

## Decision

1 を採用する。詳細は [issues-and-workflow.md](../architecture/issues-and-workflow.md) の 4.3・6.1・8・9.3・11 節。

- 派生の関数は `packages/model` にモデルごとに登録する（定義の `derive`。[ADR-0019](0019-schema-definition-and-codegen.md)）。入力は、そのトランザクションを当てる直前の確定の状態（クライアントでは手元の `view`）と、トランザクションの操作。出力は操作の列。
- Writer は、トランザクションの操作を当てた後、同じ savepoint の中で派生の操作を当て、`sync_actions` に書く（行ごとに `sync_id` を振る。[ADR-0007](0007-sync-actions-and-range-proof-deltas.md)）。派生の操作は、利用者の送ったトランザクションの一部として確定か拒否になる。派生の操作が検証に落ちたら、トランザクション全体を拒否する。
- クライアントは、トランザクションを作る時に `derive` を呼び、派生の操作を `pending` に重ねる（送らない）。確定の差分で `confirmed` が正されるので、予測と違っても収束する（[ADR-0002](0002-sync-model.md) の載せ直し）。
- 派生の操作は、時刻（`now`）と ID（履歴の行）を除いて決定的にする。時刻と ID は Writer の値が正で、クライアントの予測の値は差分で置き換わる。
- 派生の連なり（派生が派生を生む）は、1 回の派生の中で同じイシューを 2 度変えない。1 トランザクションの派生が 500 操作を超えたら、残りを Worker のシステムのトランザクションに回す。
- 派生の関数は、`actor` の権限ではなく、元の変更が許されたことを根拠に当てる。ただし、購読者を足すなど人に結び付く派生は、`can()` で見てよい人に絞る。
- 2 を採らない理由：オフラインで作った時点の状態で派生を決めることになる。後に確定する時には、他の人の変更で状態が変わっていて、派生が古い（例：同じグループのラベルを消し忘れる）。Writer がそれを検証で拒否すると、正しい意図の変更が拒否になる。
- 3 を採らない理由：派生が確定するまでの間、サーバーと全クライアントに規則の破れた状態（グループに 2 つのラベル）が見える。Worker の遅れや失敗で破れたままになる。
- 4 を採らない理由：履歴、状態の時刻、重複の状態は、後から計算で作れない（いつ変わったかが要る）。フィルター（views-and-filters）と公開 API で同じ計算を 3 か所に持つことになる。

## Consequences

- 良くなること：
  - 規則は確定の順で決まり、オフラインの変更でも破れない。
  - 画面はサーバーを待たずに派生の結果を見せられる。
  - 規則が 1 つの関数にあり、クライアントとサーバーでずれない。
- 引き受けるコスト：
  - Writer のロックの中の処理が、派生の分だけ伸びる。1 ワークスペースの書き込みの上限（ADR-0002、ADR-0006）に効くので、E5 で測る。
  - 派生の関数は、手元にない行（遅延のモデル）を読めないクライアントでも動く必要がある。手元にない行に触れる派生（重複の元の元のつなぎ直し）は、予測をあきらめ、差分を待つ。
  - 派生で `sync_actions` の行が増える。

## Confirmation

- 性質ベーステスト（[ADR-0010](0010-deterministic-sync-simulator.md)）：PROP-ISSUE-001（グループの排他）、PROP-ISSUE-002（派生の一致）、PROP-ISSUE-005（連なりの停止）、PROP-ISSUE-007（履歴）。
- 差分テスト：同じ入力で、クライアントの `derive` と Writer の `derive` が同じ操作を返す（時刻と ID を除く）。同じパッケージから使うことを依存の検査で確かめる。
- lint：Writer の中で、`derive` の外にイシューの派生の規則を書かない（モデルの表への直接の書き込みを、適用の層だけに限る）。
