# ADR-0033: 同期グループに `members`（ゲストを除くメンバー）を足し、ゲストに届けないワークスペースの行をそこに置く。チームの行は公開なら `workspace`、非公開なら `team:<id>` と `role:admin`。非公開への切り替えは、同期に加えて、担当・購読者・通知・ビューの後始末を行う。管理者は非公開のチームに自分で参加でき、監査に残す

## Context

[ADR-0003](0003-bootstrap-and-partial-sync.md) の同期グループは `workspace`・`team:<id>`・`user:<id>`・`role:admin` の 4 つで、`workspace` はワークスペースの全員が購読する。ゲストは MVP の後だが（[intent.md](../intent.md)）、本家のゲストは次のようである（[Members and roles](https://linear.app/docs/members-roles)、2026-09-28 に確認）。

- 指定したチームだけを見る。
- ワークスペースのビュー、イニシアチブ、顧客の要望を見ない。

イニシアチブとワークスペースのビューは、ワークスペース全体の行である。今の 4 つのグループでは `workspace` に入るので、ゲストが `workspace` を購読すると届いてしまう。後からモデルのグループを変えるのは破壊の変更で、全行の `sync_groups` の計算し直しが要る（[data-model-and-schema.md](../architecture/data-model-and-schema.md) の 6.2 節）。

非公開への切り替えは、[ADR-0004](0004-tenancy-and-permissions.md) と [ADR-0013](0013-sync-group-changes-retention-and-reset.md) で、同期の側（購読の削除、手元の消去、担当と購読の外し）を決めた。この後に作った領域（プロジェクトのつながり、ビュー、通知、検索）で、切り替えの時に何をするかが残っていた。

本家は、管理者は非公開のチームの存在が見え、イシューを見るには参加が要り、参加の前に警告を出す（[Private teams](https://linear.app/docs/private-teams)、2026-09-28 に確認）。

## Options

ゲストに届けない行：

1. **`members` のグループを足し、ゲストに届けないワークスペースの行を MVP から置く**
2. ゲストを出す時に、該当のモデルのグループを変える（破壊の変更）
3. ゲストに `workspace` を購読させず、ゲストが要る行（利用者、ラベル）を別の手段で配る

非公開への切り替えの後始末：

- a. **同期の側は同じトランザクションで、担当・購読者は同じトランザクション（多ければ Worker）、通知の行の削除とビューの知らせは Worker で行う**
- b. 全部を同じトランザクションで行う

## Decision

1 と a を採用する。詳細は [permissions-and-teams.md](../architecture/permissions-and-teams.md) の 5〜7 節。

- `members`：`active` の `owner`・`admin`・`member` が購読する。`workspace_members` の規則のモデル（`Initiative`、ワークスペースの `View`）の行がここに入る。新しいワークスペースの行のモデルは既定で `members` にし、ゲストに要るもの（`User`、ワークスペースのラベル・テンプレート、`ProjectStatus`、公開の `Team`）だけを `workspace` にして、理由の注記を必須にする。
- `Team`・`TeamMembership` は `team_row` の規則：公開なら `workspace`、非公開なら `team:<id>` と `role:admin`。管理者は非公開のチームの存在・名前・メンバーを見るが、イシューは見ない。
- 管理者は非公開のチームに自分で参加できる。参加は監査の記録（`admin_joined_private_team`）に残し、チームのメンバーに知らせる。
- 非公開への切り替え（DT-PERM-004）：Writer は同じトランザクションで、チームの行のグループの移動、メンバーでない人の購読の削除、担当と購読者の外し（1 万件を超えたら残りを Worker）を行う。Worker が、メンバーでない人の、そのチームのイシューを主題とする通知の行を消し、そのチームを参照するワークスペースのビューの持ち主に知らせる。プロジェクトのつながり（`ProjectTeam`）と検索は、グループの定義から自動で絞られるので何もしない。
- 非公開のチームから抜けた人も、切り替えと同じく、担当と購読者から外す。
- ゲストのロールを付ける操作は、MVP の後までフラグの裏に置く。
- 2 を採らない理由：ゲストを出すたびに、大きなワークスペースで全行の計算し直しと移動の差分が要る。
- 3 を採らない理由：配りの経路が 2 つになり、同期グループの試験の外で漏れる。
- b を採らない理由：通知の行とビューの検索は、ワークスペースの全員に広がりうる。Writer のロックの保持が長くなりすぎる。通知の行は中身を持たない（ID と種類だけ）ので、消すまでの遅れは漏れにならない。

## Consequences

- 良くなること：
  - ゲストを出すときに、行のグループを変えずに済む。
  - 非公開への切り替えで、プロジェクトの進捗・つながり・検索が、追加の処理なしに絞られる。
- 引き受けるコスト：
  - 購読のグループが 1 つ増え、全メンバーの購読の行が 1 つ増える。
  - 新しいモデルのたびに、`workspace` か `members` かを判断する。既定を `members` にし、生成の検査で注記を求める。
  - 公開のチームの一覧とメンバー（とメールアドレス）はゲストにも届く。本家の見え方は未検証で、ゲストの Epic の前にセキュリティのレビューで見直す。

## Confirmation

- 性質ベーステスト（[ADR-0010](0010-deterministic-sync-simulator.md)）：PROP-PERM-002（手元の集合。ゲストと `members` を含む）、PROP-PERM-004（切り替えの後始末）。
- 表駆動テスト：DT-PERM-004 の各行。
- 生成の検査：`workspace` の規則のモデルに `guest_visible` の注記がなければ失敗させる。
- 結合テスト：メンバー 2,000・イシュー 5 万のチームの非公開への切り替えが、`lock_timeout` 10 秒の中で確定する。
