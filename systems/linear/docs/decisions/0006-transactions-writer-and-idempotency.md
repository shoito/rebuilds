# ADR-0006: トランザクションは意図の操作の列で、全体が確定か拒否。Writer はワークスペースの行を最初にロックし、1 つの DB のトランザクションで書き、結果を 90 日持って再送に同じ結果を返す

## Context

[ADR-0002](0002-sync-model.md) で、変更をトランザクションとして送り、Writer が検証してワークスペースの `sync_id` を振ると決めた。残る問いは次のとおり。

- トランザクションの形と、原子性の単位。
- Writer が、検証と適用と番号の振り方を、どの順で 1 つの DB のトランザクションにするか。
- 冪等性の記録の形と、拒否の扱い。
- クライアントが、自分のトランザクションをいつ未確定の列から外すか。

第三者の解析によれば、本家はトランザクションをまとめて 1 つの GraphQL の mutation で送り、応答の `lastSyncId` の差分が届くまで保持する。送った後、応答の前にクライアントが落ちると、同じ変更が 2 回効きうることを、まれとして受け入れている（[reverse-linear-sync-engine](https://github.com/wzhudev/reverse-linear-sync-engine)、2026-09-28 に確認。本家の保証ではない）。この題材は「確定したトランザクションは 1 回だけ効く」を必須の性質にしている（NFR-004、AGENTS.md）。

## Options

形と原子性：

1. **意図の操作（`set`・`add`・`remove`・`incr`・`append`・`create`・`delete`・`archive`・`unarchive`）の列。トランザクション全体が確定か拒否**
2. 行の全体の置き換え（変更後の行を送る）
3. 操作ごとに独立に確定・拒否

Writer の順序：

- a. **最初にワークスペースの行をロックし、ロックの中で検証・適用・番号を振る**
- b. ロックの前に検証し、ロックの中で読んだ行のバージョンが変わっていないかを確かめる（楽観的な検証）
- c. 検証と適用の後に、番号だけを別に振る

冪等性：

- x. **`(workspace_id, client_tx_id)` の結果（確定の `sync_id` か拒否の理由）を記録し、再送に同じ結果を返す**
- y. 本家と同じく、記録しない

## Decision

1・a・x を採用する。詳細は [sync-engine.md](../architecture/sync-engine.md) の 4〜6 節。

- トランザクションは `{id: client_tx_id, fv, base, at, ops[]}`。1 回の入力が 1 つのトランザクションで、全体が確定か拒否のどちらか。操作は 500、大きさは 256 KiB まで。一括の編集は 500 操作ずつに分ける。
- 1 回の `submit`（最大 100 トランザクション）を、Writer は 1 つの DB のトランザクションで処理する。最初に `workspace_sync` の行を `FOR UPDATE` で取り、トランザクションごとに savepoint を切って、検証・適用・`sync_actions` の書き込み・`tx_results` の書き込みを行う。拒否したものは savepoint まで戻し、拒否を `tx_results` に書く。
- 再試行できる失敗（ロックの時間切れ、フェイルオーバー）は拒否にせず `retry` を返す。クライアントは同じ `client_tx_id` で送り直す。
- `tx_results` は 90 日持つ（[ADR-0005](0005-client-persistence-and-offline.md) と同じ）。
- クライアントは、ack の `sync_id = s` を受けても、`s` までの差分を保存するまで未確定の列から外さない。拒否は列から外し、`_rejected` に理由を残す。依存する後のトランザクションを先回りして捨てず、サーバーの拒否を待つ。
- 検証はクライアントと同じモデルの定義のコードで行い、決定表（sync-engine.md の 5.3 節）の順で最初に当たった行で決める。
- 2 を採らない理由：フィールドごとの LWW と集合の追加・削除（ADR-0002）を表せない。同時に別のフィールドを変えた 2 人の変更が、行の全体で打ち消し合う。
- 3 を採らない理由：1 回の操作（イシューを作ってラベルを付ける）が半分だけ当たる状態が画面に出る。
- b は、ロックの保持を短くできるが、読んだ行の集合の追跡が要り、誤りが収束の不具合になる。E2 の PoC で a が上限（1 ワークスペース 1 秒 300 件）に届かないときの代案として残す。
- c は、番号の順とコミットの順がずれる（ADR-0002 がシーケンスを退けた理由と同じ）。
- y は、NFR-004 の「1 回だけ効く」を満たせない。

## Consequences

- 良くなること：
  - 送信の途中で落ちても、再送で重複しない。拒否も同じ理由で返るので、画面の説明が安定する。
  - 検証と適用がロックの中にあるので、削除された親・循環・並びの鍵の重なりを確実に判定できる。
  - 1 回の操作の原子性が、画面・サーバー・ログで一致する。
- 引き受けるコスト：
  - ロックの保持が検証の時間だけ伸び、1 ワークスペースの書き込みの上限を下げる。
  - `tx_results` が書き込みごとに 1 行増える。90 日分を日ごとのパーティションで持つ。
  - 90 日より古い未送信のトランザクションは、重複を見分けられないので、自動では送れない。

## Confirmation

- 性質ベーステスト（[ADR-0010](0010-deterministic-sync-simulator.md) のシミュレーター）：PROP-SYNC-002（ちょうど 1 回）、PROP-SYNC-005（直列）、PROP-SYNC-006（ちらつきなし）、PROP-SYNC-007（拒否の見せ方）。
- 表駆動テスト：sync-engine.md の 5.3 節の決定表の全行を、クライアントの検証と Writer の検証の両方で確かめる。
- 結合テスト：Writer がコミットした後、ack の前に落ちる場面で、再送が前の結果を返し、`sync_actions` が増えない。
- 計測（E2 の PoC）：1 ワークスペースに 1 秒 300 件を書き、ロックの待ちの p99 と送信から ack の p99（300ms）を測る。
