# ADR-0026: サイクルはチームごとの行で、Worker がチームのタイムゾーンで先の分を作る。クールダウンは行のない隙間で表し、繰り越しは次のサイクルの始まりに Worker のシステムのトランザクションで行う。終わったサイクルへの遅れた割り当ては、派生で繰り越し先へ付け替える

## Context

本家のサイクルは次のように動く（[Cycles](https://linear.app/docs/use-cycles)、2026-09-28 に確認）。

- 長さは 1〜8 週。チームのタイムゾーンで、選んだ曜日の 0 時 1 分に始まる。
- 任意のクールダウンがあり、クールダウンにはイシューを割り当てられない。
- 先のサイクルは最大 15 まで作れる。
- 未完了のイシューは次のサイクルへ自動で移る。クールダウンの間に Backlog・Triage・Canceled・Completed へ移したものは移らない。
- 設定で、サイクルのない Started のイシューを次のサイクルへ自動で足す。

この題材では、クライアントはオフラインで変更を作り、後でサーバーの順序で確定する（[ADR-0002](0002-sync-model.md)）。すると、次のことが起きる。

- オフラインで「今のサイクル」に入れた変更が、サイクルの終わりと繰り越しの後に確定する。
- クライアントの時計は信じられない。境界の判定をクライアントに任せると、端末ごとに結果が違う。

## Options

サイクルの表し方：

1. **行として持ち、Worker が先の分を作る。境界の時刻は行に持つ**
2. チームの設定から、境界をその都度計算する（行を持たない。サイクルは「番号」だけ）

繰り越しの時刻：

- a. **次のサイクルの始まり（クールダウンの後）**
- b. 今のサイクルの終わり（クールダウンの前）

遅れた割り当て（終わったサイクルへの `set cycle_id`）：

- x. **派生で繰り越し先へ付け替える**
- y. 拒否する（`workflow_violation`）
- z. そのまま受ける

## Decision

1・a・x を採用する。詳細は [cycles-and-projects.md](../architecture/cycles-and-projects.md) の 4 節。

- `Cycle` はチームの同期グループの行。Worker の `cycle-scheduler` が 1 時間ごとに、先の分を `cycle_upcoming`（1〜15、既定 3）まで作る。利用者は名前だけを変えられる。
- 境界はサーバーの共有の関数 `cycleBounds` だけで計算し、`starts_at`・`ends_at` に書く。チームのタイムゾーン（IANA）の日付の 00:00 を基準にする。本家の 0 時 1 分ではなく 0 時 0 分にし、終わりと次の始まりを同じ時刻にする。
- クールダウンは行を作らない。割り当てる先の行がないので、本家の「クールダウンに割り当てられない」が成り立つ。
- 繰り越しは、次のサイクルの `starts_at` に、Worker の `cycle-rollover` が 500 件ずつのシステムのトランザクションで行う。対象は `unstarted`・`started` の種類。`triage`・`backlog` は元のサイクルに残す。最後のトランザクションで元のサイクルを完了にし、`rolled_to_id` を書き、写し（`snapshot`）を残す。
- 終わったサイクルへの `set cycle_id` は、繰り越し先があり、イシューが `unstarted`・`started` なら、派生（[ADR-0025](0025-derived-changes-in-writer.md)）で繰り越し先へ付け替える。
- 設定の変更は、今のサイクルを変えず、先のサイクルの境界を同じ ID のまま計算し直す。
- 2 を採らない理由：繰り越しの「済み」、写し、名前、先のサイクルへの割り当ての参照先を持てない。参照の検証（`invalid_reference`）とビューの絞り込みが、ID でなく計算になる。
- b を採らない理由：本家の「クールダウンの間に移したものは移らない」を表せない。
- y を採らない理由：オフラインで正しい意図（今のサイクルでやる）で作った変更が、繰り越しの時刻をまたいだだけで拒否になる。
- z を採らない理由：繰り越しのジョブが先に当たるか、割り当てが先に当たるかで、イシューの行き先が変わる（収束はしても、意図と違う）。

## Consequences

- 良くなること：
  - 境界の判定がサーバーの 1 か所になり、端末の時計に左右されない。
  - 繰り越しとオフラインの割り当ての順序にかかわらず、未完了のイシューは次のサイクルに入る。
  - サイクルは普通のモデルなので、ブートストラップ・差分・ビューの参照がそのまま使える。
- 引き受けるコスト：
  - Worker のジョブが止まると、先のサイクルが作られず、繰り越しが遅れる。先を 3 つ持って猶予を作り、監視する。
  - 多くのチームが同じ曜日・時刻に境界を迎えると、繰り越しの書き込みが重なる。1 ワークスペースの `worker` の枠（[ADR-0054](0054-per-workspace-write-admission.md)）で散らし、E12 で測る。
    > 2026-09-28 の注記：当初は「ワークスペースごとの間隔（100ms に 1 回）で散らす」としていた。ADR-0023 の注記と同じく、`worker` の枠（1 秒 50 変更）に揃えた。1 チーム 5,000 件の繰り越し（1 件 約 2 変更）は約 3 分半で終わり、[cycles-and-projects.md](../architecture/cycles-and-projects.md) の 4.4 節の目標（10 分）に収まる。
  - Backlog を繰り越さない判断は、本家の文書で確かめられない（未検証）。

## Confirmation

- 表駆動テスト：DT-CYCLE-001（繰り越し）、DT-CYCLE-002（割り当て）、DT-CYCLE-003（設定の変更）の全行を、クライアントの予測と Writer の両方で。
- 例示テスト：`cycleBounds` を夏時間のあるタイムゾーンを含めて確かめる。
- 性質ベーステスト（[ADR-0010](0010-deterministic-sync-simulator.md)）：PROP-CYCLE-001（隙間と重なり）、PROP-CYCLE-002（繰り越しの順序の独立）、PROP-CYCLE-003（冪等）。
- 本番：境界から繰り越しの完了までの p95 10 分以内。先のサイクルが 1 つ以下のチームが 0。
