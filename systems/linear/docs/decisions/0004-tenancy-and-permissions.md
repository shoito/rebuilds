# ADR-0004: ワークスペースをテナントにし、FORCE RLS で分ける。チームを権限の範囲にし、非公開のチームは同期グループで差分から外す

## Context

本家では、ワークスペースが契約・メンバー・データの単位である。1 人が複数のワークスペースに属せる。ワークスペースの中にチームがあり、チームごとにワークフロー・サイクル・識別子の接頭辞を持つ。

非公開のチームについて、本家の文書は次のように書いている（[Private teams](https://linear.app/docs/private-teams)、2026-09-28 に確認）。

- Business と Enterprise のプランで使える。
- チームのメンバーでない人は、そのチームのイシューを見られない。ワークスペースのオーナーと管理者は、管理の設定でチームの存在は見えるが、イシューを見るには参加する必要がある。
- 公開のチームを非公開にすると、メンバーでない人はイシューの担当から外され、購読も外れる。
- メンバーでない人を、そのチームのイシューでメンションできない。
- 一部の連携（Google Sheets、Intercom、Sentry、Zendesk）は、非公開のチームのデータに触れられない。

この題材では、データをクライアントの手元へ送る（[ADR-0002](0002-sync-model.md)、[ADR-0003](0003-bootstrap-and-partial-sync.md)）。サーバーの画面で隠すだけでは足りない。**見てはいけないデータが、クライアントの IndexedDB に一度でも届けば漏えいである。**

## Options

分離の方式：

1. **共有スキーマ＋RLS。** 全ワークスペースのテーブルに `workspace_id` を持たせる
2. ワークスペースごとのスキーマ
3. ワークスペースごとの DB（silo）

非公開のチームの扱い：

- a. **同期グループで、配る前に絞る。** 権限の判定を 1 つの関数にまとめ、同期グループの購読・差分・ブートストラップ・遅延の読み込み・API・検索・Webhook・通知のすべてがそれを使う
- b. 全データを配り、クライアントの画面で隠す
- c. 非公開のチームを、別のワークスペースのように分けて扱う

## Decision

1 と a を採用する。

### ワークスペースの分離

- **分け方は、他の題材（Slack の ADR-0009、Auth0 の ADR-0002）に倣う。**
  - 全ワークスペースのテーブルに `workspace_id` を持たせ、主キーとインデックスの先頭に置く。ID は UUIDv7。
  - `FORCE ROW LEVEL SECURITY` を設定し、トランザクションごとに `SET LOCAL app.workspace_id` を設定する。
  - RLS を外すのは、ワークスペースをまたぐ処理（アカウントの解決、請求の集計、S2 のクラスタの移動）だけにし、別の DB のロールで行う。
- **`sync_actions` と、ワークスペースの `last_sync_id` の行も、ワークスペースに属する。** 順序はワークスペースの中で閉じる（[ADR-0002](0002-sync-model.md)）。
- **アカウントはワークスペースの外に置く。** 1 人のアカウント（メールアドレス、ログインの手段）は、複数のワークスペースのメンバーシップを持つ。アカウントの表は RLS の外の別のスキーマに置き、認証のサービスのロールだけが読む。本家も、アカウントとワークスペースの対応を全体のサービスに置き、ワークスペースのデータはリージョンに置いている（[How we built multi-region support for Linear](https://linear.app/now/how-we-built-multi-region-support-for-linear)、2026-09-28 に確認）。S3 で海外のリージョンを足すときも、同じ分け方にする。
- **要求のワークスペースは、セッションと URL（`<brand>.<domain>/<workspace-slug>/...`）から決める。** そのアカウントがメンバーでないワークスペースの要求は、ワークスペースの存在を明かさずに 404 を返す。
- **手元の DB もワークスペースごとに分ける。** クライアントは、ワークスペースごと・アカウントごとに別の IndexedDB のデータベースを持つ（[ADR-0005](0005-client-persistence-and-offline.md)）。
- 2 は、S3 で 30 万のワークスペースに対してスキーマの数とマイグレーションが重い。3 は、S1 の 5,000 でも運用が重い。大口のワークスペースは、S2 でワークスペースを単位に専用のクラスタへ移し、S3 でセルに固定する（infrastructure の領域）。

### 権限の範囲

- **ワークスペースのロール**：オーナー・管理者・メンバー。ゲストは MVP の後（[intent.md](../intent.md)）。
- **チームを権限の範囲にする。**
  - 公開のチーム：ワークスペースの全メンバーが見られ、書ける。チームへの参加は、サイドバーや通知の既定を変えるだけで、見える範囲は変えない。
  - 非公開のチーム：チームのメンバーだけが見られ、書ける。オーナーと管理者は、管理の画面でチームの存在と名前だけを見られる。
- **権限の判定を 1 つの関数にまとめる。** `can(actor, action, model)` と、そこから導いた「この人が購読する同期グループ」の計算を、Writer・Sync API・Sync Gateway・Public API・検索・Webhook・通知が共有する。他の場所で権限の条件を書かない（Slack の ADR-0005 と同じ考え方）。
- **非公開のチームのモデルは、`team:<id>` の同期グループにだけ入れる。** そのチームのメンバーだけが購読する（[ADR-0003](0003-bootstrap-and-partial-sync.md)）。差分・ブートストラップ・遅延の読み込みは、同期グループで絞ってから送る。
- **グループをまたぐ参照は、ID だけを持つ。** 公開のチームのイシューが、非公開のチームのイシューを関連として参照するとき、参照の行は公開の側のグループに入るが、相手のタイトルや状態は含めない。権限のない人の画面は「非公開のイシュー」と示す。
- **非公開への切り替え**：公開のチームを非公開にすると、Writer は 1 つのトランザクションで、メンバーでない人の担当と購読を外し（本家と同じ）、同期グループの変化を記録する。メンバーでない人のクライアントは、グループからの脱退として、そのチームのモデルを手元から消す（[ADR-0003](0003-bootstrap-and-partial-sync.md)）。
- **公開 API・Webhook・連携**：API キーと OAuth のアプリは、発行した人の権限を超えない。Webhook は対象のチームを持ち、非公開のチームを対象にできるのは、そのチームのメンバーの管理者だけにする（詳細は api-and-webhooks の領域）。
- b を採らない理由：画面で隠しても、手元の DB と開発者のツールから読める。漏えいである。
- c を採らない理由：非公開のチームと公開のチームの間の関連、プロジェクト、ビューが、ワークスペースの中で自然につながらなくなる。

## Consequences

- 良くなること：
  - ワークスペースの分離を、アプリのコードだけに頼らない。
  - 非公開のチームの絞り込みが、どの経路でも同じ関数と同じ同期グループで行われる。
- 引き受けるコスト：
  - 権限の変化（非公開への切り替え、メンバーの追加・削除、ロールの変更）が、同期グループの変化になり、クライアントの手元のデータの追加・消去を伴う。処理が重く、漏れがそのまま漏えいになる。
  - グループをまたぐ参照で、相手の情報を出せない場面が画面に出る。
  - 大きなワークスペースが共有の DB を占有しうる。ワークスペース単位のレート制限と、S2 のクラスタの分割で抑える。
  - RLS のコンテキストの設定漏れは「データがない」という形で現れ、クライアントの同期では「消えた」ように見える。結合テストで全経路のコンテキストの設定を確かめる。

## Confirmation

- 性質ベーステスト：任意の 2 ワークスペースで、一方のコンテキストで他方の行が読めない。
- 性質ベーステスト（シミュレーター）：任意のメンバーシップ・非公開への切り替え・イシューの移動の列の後、どのクライアントの手元（メモリー、IndexedDB）にも、その時点で見てよくないモデルがない。
- 表駆動テスト：`can` の決定表（ロール × チームの種類 × メンバーか × 操作）を、spec から読み込んで全行を確かめる（permissions-and-teams の領域で書く）。
- CI：新しいテーブルに `workspace_id` と RLS のポリシーがないマイグレーションを失敗させる（例外は許可リストで管理する）。
- CI：モデルの定義で、同期グループの規則のないモデルがあれば、コードの生成を失敗させる。
- 本番：配信の監査（Gateway が送った行の同期グループと、接続の購読の突き合わせの抜き取り）で、不一致 0 件（NFR-008）。
