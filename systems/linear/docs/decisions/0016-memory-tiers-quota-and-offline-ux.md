# ADR-0016: メモリーは 3 層にし、観測可能なモデルは 5 万個まで。保存の上限を見張って遅延のモデルの写しだけを退かし、ブラウザに消された未送信の件数はサーバーのクッキーの端末の ID で本人に示す

## Context

最大のワークスペース（イシュー 50 万件）を手元に持つと、ブラウザのメモリーと起動の時間が重い（[architecture/README.md](../architecture/README.md) の 6 節）。[ADR-0003](0003-bootstrap-and-partial-sync.md) は部分のブートストラップで手元の量を抑えるが、部分でも十数万件のイシューと、遅延の読み込みで増える行が残る。一方、一覧の切り替えとフィルター（NFR-001：p99 50ms）は、IndexedDB を待てない。

保存について、MDN は次のように説明する（[Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)、2026-09-28 に確認）。

- 上限は Chrome でディスクの最大 60%、Firefox は既定でディスクの 10% か 10 GiB の小さい方、Safari（macOS 14・iOS 17 以降）はブラウザのアプリで約 60%。
- 空きが少ないと、永続でないオリジンを、最も長く使っていない順に、オリジンごと全部消す。
- Safari は、追跡の防止が有効なとき、7 日間操作のないオリジンのスクリプトが作ったデータを消す。サーバーが設定したクッキーは消さない。
- `persist()` は Firefox では利用者に尋ね、Chrome・Edge・Safari は利用の度合いで自動で決める。

[ADR-0005](0005-client-persistence-and-offline.md) は、永続の保存を求め、上限に近づいたら警告し、消去されたらやり直すと決めた。ブラウザの上限の具体と、消去で失った未送信を本人にどう示すかは残っていた。

## Options

メモリー：

1. **3 層：M1 観測可能なモデル（`instant` と画面で使うもの、5 万個まで）、M2 行の多いモデルの詰めた索引（フィルター・並べ替えのフィールドの列の配列）、M3 IndexedDB だけ**
2. 手元のすべての行を観測可能なモデルにする
3. 画面ごとに IndexedDB から読む

消去の知らせ：

- a. **サーバーが HttpOnly のクッキーで端末の ID を配り、Gateway が端末ごとに最後に報告された未送信の件数を持つ。手元がない状態の握手で、失った件数を返す**
- b. 知らせない（手元が消えたら、やり直すだけ）

## Decision

1 と a を採用する。詳細は [client-store-and-offline.md](../architecture/client-store-and-offline.md) の 7・9 節。

- 一覧・フィルター・並べ替えは M2 だけで答える。行の詳細は M1 になければ IndexedDB から戻す（NFR-001 の対象外）。差分は M2 と M1 にある行に当て、M3 だけの行は保存で済ませる。
- M1 は `instant` を除いて 5 万個まで。観測されていないものから古い順に外す。ヒープの目標は、最大のワークスペースで p95 500 MB、モデル 5 万件以下で p95 250 MB（E2・E3 で測る）。
- 保存は `persist()` を最初に開いた時に求め、`estimate()` を起動・ブートストラップの後・10 分ごとに読む。70% で遅延のモデルの写しを被覆の鍵と一緒に古い順に退かし、85% で警告する。outbox の書き込みが `QuotaExceededError` なら、退かしてから 1 回書き直し、だめなら読み取りの専用にする。`_outbox`・`_rejected`・`_meta`・未送信の `_blobs`・`instant`・被覆のある `partial` は退かさない。
- 端末の ID のクッキー `<brand>_cid`（HttpOnly・Secure・SameSite=Lax）を配り、`client_devices` に最後に報告された未送信の件数を持つ。手元がない状態の握手で `welcome.lost_local` を返し、件数を示す。
- オフラインの表示は 1 か所にまとめ、状態（同期済み・同期中・オフライン・再接続中・再同期を待つ・更新が必要・空きが少ない・保存できない・未送信を失った）と未送信の件数を出す。本家の「Syncing」と件数の表示（[Download Linear](https://linear.app/docs/get-the-app)、2026-09-28 に確認）と同じ考え方にする。
- 2 を採らない理由：十数万個の観測可能なオブジェクトのメモリーと GC の停止が、遅延の予算を脅かす。
- 3 を採らない理由：一覧の切り替えのたびに IndexedDB を待ち、NFR-001 を満たせない。
- b を採らない理由：「失わない」（NFR-004）の保証の外で失ったことを、本人が知る手段がなくなる。

## Consequences

- 良くなること：
  - 大きなワークスペースでも、一覧とフィルターを同期の処理だけで答えられる。
  - 保存の上限で失うのは取り直せる写しだけで、未送信は守られる。
  - ブラウザに消されたとき、失った件数だけは本人に示せる。
- 引き受けるコスト：
  - M2 の列の配列と M1 の間の整合を、差分の適用で 2 か所に保つ必要がある。
  - 端末の ID の表を持ち、握手と `status` の度に件数を書く。
  - 未送信の中身は取り戻せない。

## Confirmation

- 性質ベーステスト（[ADR-0010](0010-deterministic-sync-simulator.md)）：PROP-STORE-005（退かし）、PROP-SYNC-001（M1 から外して戻しても `view` が変わらない）。
- CI のベンチマーク（E2・E3）：基準の端末と基準のワークスペースで、一覧の切り替え・フィルターの p99 50ms（NFR-001）と、ヒープの目標。
- 結合テスト：手元の DB を消して握手すると、`lost_local` が前に報告した件数を返す。
