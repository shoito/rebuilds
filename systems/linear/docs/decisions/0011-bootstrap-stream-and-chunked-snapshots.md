# ADR-0011: ブートストラップは NDJSON のストリームで、ID の範囲のチャンクごとに 1 つの写しで読む。クライアントは最も小さい `as_of` から差分を当て、チャンクの境を先に決めて途中から再開できるようにする

## Context

[ADR-0003](0003-bootstrap-and-partial-sync.md) で、全体・部分・手元から・やり直しの 4 つのブートストラップと、「1 つの読み取りのスナップショット（`REPEATABLE READ`）の中でワークスペースの `last_sync_id` とモデルを読む」「NDJSON を圧縮して流す」ことを決めた。残る問いは次のとおり。

- 最大のワークスペース（部分でも十数万行）を 1 つのスナップショットで読むと、Aurora の reader で長い読み取りになる。PostgreSQL のホットスタンバイでは、長い問い合わせが複製の適用と衝突して取り消されうる（Aurora の reader での条件は**未検証**）。
- 途中で切れたとき（タブを閉じた、回線が落ちた）、最初からやり直すと、大きなワークスペースで NFR-003（p95 10 秒）を何度も払う。
- 画面を早く出すための、モデルの順序。

第三者の解析によれば、本家の全体のブートストラップはモデルの列をストリームで返し、メタデータに `lastSyncId` と購読のグループを持つ（[reverse-linear-sync-engine](https://github.com/wzhudev/reverse-linear-sync-engine)、2026-09-28 に確認。本家の保証ではない）。途中からの再開の有無は**未検証**。

## Options

1. **ID の範囲のチャンク（2 万行）ごとに 1 つの写しで読み、各チャンクに `as_of` を付ける。クライアントは全チャンクの `as_of` の最小（`s_min`）から差分を当て、行の `updated_sync_id` で古い差分を退ける。チャンクの境を最初に返し、途中から残りのチャンクだけを求められるようにする**
2. 1 つの写しで全部を読む（ADR-0003 の文言どおり）
3. PostgreSQL の `pg_export_snapshot()` で 1 つの写しを複数の接続で共有する

## Decision

1 を採用する。詳細は [bootstrap-and-partial-sync.md](../architecture/bootstrap-and-partial-sync.md) の 4 節。

- 応答は NDJSON（br か gzip）。行は `head`（種類、`sync_epoch`、スキーマ、購読のグループ、チャンクの境の一覧）、`chunk`（`as_of`）、`rows`（1,000 行まで。各行に `_u` と `_g`）、`chunk_end`、`covered`（被覆の鍵）、`end`（`s_min`）。
- モデルは `instant` を依存の順に、その後に `partial`。`instant` がそろえば画面を出す。
- 1 つのチャンクは ID の範囲で 2 万行、読み取り 10 秒以内。`REPEATABLE READ, READ ONLY` の中で `workspace_sync.last_sync_id` と行を読む。
- クライアントは行を 2,000 行ずつ `relaxed` で書き、`chunk_end` で `_meta.bootstrap.done` に記録する。行は `_u` の大きい方を残し、墓標より古い行を書かない。
- 全チャンクの後、`L = s_min` とし、`s_min` の後の差分を順にすべて当てる。これで、チャンクごとに写しが違っても、サーバーの状態に一致する（行の作成と更新は `_u` で退けられ、写しの後の変更は差分で当たり、写しの前に消えた行は後の `delete` で消える）。
- 中断したら、`_meta.bootstrap` の境と `done` から、残りのチャンクだけを `POST /sync/bootstrap/chunks` で求める。`sync_epoch` か購読が変わっていれば、サーバーは `409 restart` を返し、最初からやり直す。
- 全体か部分かは Sync API が見てよいモデルの数で決める（`kind=auto`。閾値は ADR-0003 の仮の 5 万件）。
- 2 を採らない理由：大きなワークスペースで長い読み取りになり、reader で取り消されうる。途中から再開できない。
- 3 を採らない理由：書き出したスナップショットは、書き出したトランザクションが生きている間しか使えず、タブの中断をまたいだ再開には使えない。長い読み取りの問題も残る。

## Consequences

- 良くなること：
  - 1 回の読み取りが短く、reader の負荷と取り消しの危険が小さい。
  - 中断しても、残りのチャンクだけで続けられる。
  - 写しの正しさの規則（`s_min` と `_u`）が、遅延の読み込みやグループのブートストラップと同じになる。
- 引き受けるコスト：
  - `s_min` から差分を当てるので、写しの時点より前の差分も少し当て直す。多くは `_u` で退けられる。
  - チャンクの境を決めるための ID の範囲の計算（モデルごとの ID の分位点）が要る。

## Confirmation

- 性質ベーステスト（[ADR-0010](0010-deterministic-sync-simulator.md)）：PROP-BOOT-001（全体・部分・手元から・やり直し・中断からの再開のどれでも、同じ差分の後に一致する）。チャンクの間に書き込み・削除・移動を挟む。
- 結合テスト：写しの読み取りの途中で書き込みがあっても、`s_min` の後の差分を当てた結果がサーバーと一致する。
- 計測（E3 の PoC）：基準のワークスペースで、部分のブートストラップの操作できるまでの時間 p95 10 秒（NFR-003）。Aurora の reader で 10 秒の読み取りが取り消されないこと。
