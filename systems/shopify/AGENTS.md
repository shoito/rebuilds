# AGENTS.md — Shopify

Shopify の再構築の設計。リポジトリ共通のルールはルートの [AGENTS.md](../../AGENTS.md) にある。このリポジトリには設計だけを置き、実装は Shopify の開発リポジトリで行う（[リポジトリ共通の ADR-0005](../../docs/decisions/0005-design-record-repository.md)）。

- [docs/intent.md](docs/intent.md) — 何を、なぜ作るか
- [docs/architecture/](docs/architecture/README.md) — 全体像、規模の段階、非機能要件、領域の計画
- [docs/decisions/](docs/decisions/README.md) — ADR。特に 0002（ポッドとショップの置き場所）、0004（在庫の引き当て）、0005（チェックアウトの状態の機械と注文の一回性）、0007（テーマの言語）、0008（拡張の砂場）
- [docs/quality.md](docs/quality.md)・[docs/roadmap.md](docs/roadmap.md)・[docs/runbooks/](docs/runbooks/README.md) — 品質の戦略、Epic と Story、SLO とフラッシュセールの運用

## この題材に固有の規則（開発リポジトリで守る）

### 本家の実装と名前

- **核を自前で作る。** チェックアウト、在庫の引き当て、テーマの言語とレンダラー、関数の砂場の設計、ポッドとショップの移し替え、割引のエンジン、Admin API の費用の計算は自分で書く。本家のコード（Liquid の実装、本家の SDK・CLI・テーマ・アプリのひな形、内部の形式）を、核にも依存にも使わない。本家の技術ブログや開発者の文書の考え方を読むのはよいが、設計の文書に出典を書く（[リポジトリ共通の ADR-0007](../../docs/decisions/0007-no-reuse-of-original-implementation.md)、ADR-0001）。
- **第三者の汎用の部品は、ADR に理由を書いた範囲でだけ使う。** WebAssembly の実行系（Wasmtime）、GraphQL の参照の実装（graphql-js）、検索のエンジン（OpenSearch）、AWS WAF などが当たる（ADR-0001、ADR-0008、ADR-0009）。
- **公開の標準には合わせてよい。** GraphQL、OAuth 2.0、OpenID Connect、WebAssembly、HTTP のキャッシュ（`Cache-Control`、`stale-while-revalidate`）、schema.org の構造化データは、標準として受ける。
- **本家の名前を識別子に使わない。** ドメイン（`admin.<brand>.<domain>`、ショップの既定のドメイン `<shop>.<brand>.<domain>`）、HTTP ヘッダー（`X-<Brand>-Access-Token`、`X-<Brand>-Hmac-Sha256`、`X-<Brand>-Webhook-Id`、`X-<Brand>-Storefront-Access-Token`）、トークンの接頭辞（`<brand>_at_`、`<brand>_sf_`）、グローバル ID（`gid://<brand>/Product/...`）、テンプレートの言語の拡張子は `<Brand>`・`<brand>` か独自の名前で書く（[リポジトリ共通の ADR-0006](../../docs/decisions/0006-brand-neutral-identifiers.md)）。

### 在庫を売り越さない

- **在庫の正本は Aurora の行にする。** 「売り越さない」設定（`inventory_policy = deny`）の品目は、引き当ての行と在庫の行を同じトランザクションで書き、`available >= 0` の CHECK 制約で守る。Valkey・待合室・キャッシュの数は目安で、正本にしない（ADR-0004）。
- **引き当てと確定を分ける。** 引き当て（reservation）は期限つきで、注文の作成と同じトランザクションで確定（commit）に変える。期限切れの引き当ては掃除の処理だけが戻す。確定した数を、引き当ての掃除で戻さない（ADR-0004）。
- **熱い品目は行を分ける。** フラッシュセールの品目は、在庫を複数の枠（slot）の行に分けて持つ。1 つの行に全員の更新を集めない。枠の数の変更と枠の間の移し替えは、合計を変えない操作だけで行う（ADR-0004）。

### 注文はちょうど 1 回

- **1 つのチェックアウトから作る注文は 1 つ。** `orders.checkout_id` に一意の制約を置く。注文の作成は、リダイレクトの戻り・決済の提供者の Webhook・掃除の処理のどれから呼ばれても、同じ関数（`completeCheckout`）を通す。別の経路で注文を作らない（ADR-0005）。
- **決済の提供者への要求には、必ず冪等キーを付ける。** キーはチェックアウトの試行と操作から決める（`<checkout_id>:<attempt>:<op>`）。提供者の Webhook は inbox の表で重複を除いてから処理する（ADR-0006）。
- **「決済だけ済んで注文がない」状態を放置しない。** 照合の処理（`checkout-reconciler`）が 1 分ごとに探し、注文を作るか、オーソリを取り消す・返金する。どちらにするかは決定表（cart-and-checkout の領域）に従う（ADR-0005）。
- **カード番号を扱わない。** カード番号は提供者のホストした入力部品か、提供者の決済ページで受ける。本システムのサーバー・ログ・DB に、カード番号とセキュリティコードが入る経路を作らない（ADR-0006）。

### お金と税の計算

- **金額は整数の最小単位で持つ。** 円は 1 円、米ドルはセント。浮動小数点を使わない。通貨ごとの小数の桁は ISO 4217 の表から取る。
- **税の端数は、税率ごとに 1 回だけ処理する。** 1 つの注文（インボイス）の中で、税率（10%・8%）ごとに対価の合計から税額を計算し、ショップの設定の方法（既定は切り捨て）で丸める。品目ごとに丸めて足さない（taxes-and-invoices の領域。法務の確認待ち L4）。
- **割引の計算は決定的にする。** 同じカート・同じ割引の集まりから、同じ結果（適用の順序、按分、端数の割り振り）を出す。ハッシュの表の順序・壁の時計・乱数に依らせない（discounts-engine の領域）。

### テナントとポッド

- **ショップがテナントである。** Aurora の表は `shop_id` を持ち、`FORCE ROW LEVEL SECURITY` と `SET LOCAL app.shop_id` で絞る。`shop_id` は、ホスト名・アクセストークン・セッションから決める。要求の本文やクエリの引数から取らない（ADR-0003）。
- **1 つの要求・1 つのジョブは 1 つのポッドだけに触れる。** ポッドをまたぐ処理は、ADR-0002 の一覧の経路 P1〜P5（ディレクトリ、移し替え、集計、スタッフの所属、全体の定義の写し）だけにする。
- **キャッシュの鍵には、必ずショップを入れる。** エッジ（CloudFront）・Valkey・アプリのメモリーのどのキャッシュも、鍵の先頭にショップ（とテーマ・通貨・言語）を持つ。Valkey の鍵は `{<shop_id>}:<種類>:…` で始める。S3 のキーは `shops/<shop_id>/…` で、ポッドを入れない（[data-model.md](docs/architecture/data-model.md)）。ショップの区別のない鍵を作る関数を書かない（storefront-api-and-caching の領域）。

### テーマと拡張の安全

- **テーマの言語は副作用を持たない。** テンプレートは、許可した値（drop）の読み出しと、決めたフィルターだけを使える。外部への通信、ファイル、任意のコードの評価（`eval`、`new Function`）を持たない。テンプレートを JavaScript のソースに変換して実行しない（ADR-0007）。
- **テンプレートの実行には上限を付ける。** 実行の歩数、出力の大きさ、ループの回数、部品の入れ子の深さ、データの読み出しの回数に上限を置く。上限は運用の値で、コードで外さない（ADR-0007）。
- **出力は既定でエスケープする。** HTML の文脈で値を出すときは、既定でエスケープする。エスケープを外すフィルター（`raw`）の使用は、テーマのチェックで警告にする（ADR-0007）。
- **利用者のコード（関数）は WebAssembly の砂場でだけ動かす。** 燃料（命令の数）とメモリーの上限を付け、WASI の機能（時計・乱数・通信・ファイル・環境変数）を渡さない。輸入は自前の殻の入出力の関数だけにする。失敗・上限の超過は、関数の種類ごとに決めた「効果なし」の結果にする（ADR-0008）。
- **Admin API の費用の上限を外さない。** 1 つのクエリの費用の上限、アプリとショップごとのバケットは、管理の画面（自社のアプリ）にも同じに当てる。内部の近道の API を作らない（ADR-0009）。

### 運用と入力

- **買い手の個人のデータをログに出さない。** 本システムのログ・トレースに、氏名、住所、電話番号、メールアドレス、決済の情報を書かない。ID と数と理由のコードだけを書く。
- **お金・在庫・税の規則をフラグにしない。** 引き当ての状態の遷移、チェックアウトの状態の機械、税の計算の規則、割引の適用の順序はコードのバージョンとして出す。`release.*` のフラグで経路ごとに切り替えない。
- **フラグの名前**：`release.*` は kebab-case（`release.checkout-konbini`）、`ops.*` は snake_case（`ops.checkout_enabled`）。`release.*` は 100% の後 30 日で消す。
- **テストに本物のデータを使わない。** 実在のショップの商品・注文・買い手のデータ、本家から書き出したデータを、テスト・フィクスチャー・シードに書かない。データは生成器で作る。

## このリポジトリでの規則

- ADR を追加・更新したら、`docs/decisions/README.md` の一覧を生成し直す。
- 領域の文書で ADR を起票するときは、[architecture/README.md](docs/architecture/README.md) の 7 節で領域に割り当てた番号の範囲の中で採番する。
- 本家の振る舞い・数値を書くときは、出典と確認日を付ける。確かめられないものは「未検証」と書く。本家と違う振る舞いを選んだら、[architecture/README.md](docs/architecture/README.md) の 1.4 節の「本家との意図した違い」に行を足す。
- 決済のカード処理そのもの（カード情報の保管、アクワイアラへの接続、台帳）は Stripe の題材の論点である。この題材では設計し直さず、提供者の API の利用者として書く（ADR-0006）。
- 法令に関わる項目は、枠組みだけを書き、結論を書かない。「法務の確認待ち」と書き、[intent.md](docs/intent.md) の L の番号を付ける。
