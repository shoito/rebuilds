# Runbook: インシデントへの対応（全般）

- Owner: Ops
- 対応するアラート: 個別の手順のないアラートの全部。SEV の判断、連絡、振り返り
- 最終確認日: 2026-10-10

SLO とアラートの一覧は [README.md](README.md) の 1・4 節、計測は [observability.md](../architecture/observability.md)、セキュリティの事象の最初の動作は [security.md](../architecture/security.md) の 10 節にある。

## 症状

- 呼び出し（page）かチケットが来たが、[README.md](README.md) の 4 節に「草案」の手順がない。
- 複数のアラートが同時に出て、どの手順から入るか分からない。

## 影響

アラートによる。ストアフロント・チェックアウトの停止は、その時間の事業者の売上が消える。フラッシュセールの間は、事業者の 1 年の山場を壊しうる。

## 確認

1. **範囲**：1 つのショップか、1 つのポッドか、全体の面か、エッジか、リージョンか。Grafana の全体のダッシュボードで、ポッドごとのチェックアウトの可用性と p99、ストアフロントの 5xx、`edge-router` の中継の数を見る。
2. **正しさ**：正しさの見張り（[observability.md](../architecture/observability.md) の 5 節）の R・P・M・I・S に 0 でない値があるか。あれば SEV1・SEV2 の候補で、可用性より先に扱う。
3. **直近の変更**：デプロイ（`deployments`）、AppConfig のフラグ、WAF の規則、ショップの移し替え（`shop_moves`）、予定したセール（`flash_sales`）。
4. **外からの見張り**：`canary`（大阪）の購入・表示・反映の結果。observability のアカウントが止まっていても、`canary` は直接呼び出す。

### SEV の目安

| SEV | 例 |
| --- | --- |
| SEV1 | 売り越し（在庫の照合の不一致）、重複の注文、他のショップのデータの露出の疑い、チェックアウトのスクリプトの目録の不一致、全ポッドのチェックアウトの停止 |
| SEV2 | 決済済みで注文なしの 15 分超、1 つのポッドのチェックアウトの停止、フラッシュセールのショップの停止、CHECK の違反の急増、リージョンの障害の兆候 |
| SEV3 | 1 つのショップの劣化、Webhook の遅れ、キャッシュの無効化の遅れ、検索の遅れ |

## 対処

1. **IC を決める**（SEV1・SEV2）。IC は判断と連絡、別の人が作業する。記録の場（課題の管理のチャンネル）を開く。
2. **被害を止める**（原因の調査より先）：
   - 正しさの問題：該当の品目の販売を止める（`ops.inventory_item_sales_enabled`）か、ショップ・ポッドのチェックアウトを止める（`ops.checkout_enabled`）。止めるのは Ops の判断で即時、開けるのは IC が確かめてから。
   - デプロイの直後：まずフラグで戻し、次に 1 つ前のイメージへ（[deploy-and-rollback.md](deploy-and-rollback.md)）。
   - 1 つのショップの急増：待合室を有効にする（`ops.waiting_room_admit_rate` を下げる）、ショップの上限を下げる（`ops.shop_limit_overrides`）。
   - 悪用したアプリ：`ops.app_suspended`。
   - 分離の疑い：エッジのキャッシュの全消去（全ショップの世代を上げる）と、該当の経路のフラグを止める。
3. **個別の手順へ**：原因の領域が分かったら、[README.md](README.md) の 4 節の手順に移る。手順が「計画」なら、この手順で続け、足りなかったことを記録する。
4. **事業者への知らせ**：状況のページで、影響のあるショップと時間を知らせる。個人のデータ・他のショップの名前を書かない。文言は法務の確認の後のひな形を使う。
5. **回復の確かめ**：SLI が SLO に戻り、正しさの見張りの照合をやり直して 0 を確かめる（決済と注文、在庫）。

## エスカレーション

- SEV1：Ops の責任者、Dev のテックリード、PM。分離・漏えいの疑いはセキュリティの担当と法務（漏えいの報告の要否は法務の確認待ち L3）。
- 決済の提供者・AWS の障害：提供者・AWS のサポートへ。
- 1 時間で被害を止められない：Ops の責任者が、リージョンの切り替え（[disaster-recovery.md](disaster-recovery.md)）を含めて判断する。

## 事後

- SEV1・SEV2 は 5 営業日の中で振り返りを書く（時刻の並び、検知までの時間、止めるまでの時間、失った範囲、根の原因、直すこと）。個人のデータを書かない。
- 調査結果を `changes/` の新しい `intent.md` として起票する（Maintain 段）。
- この手順と、[README.md](README.md) の 4 節の計画の手順で足りなかったことを反映する。
