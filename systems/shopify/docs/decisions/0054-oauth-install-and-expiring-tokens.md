# ADR-0054: アプリの導入は OAuth 2.0 の認可コードの流れで行い、導入の要求と戻りに本システムが署名した JWT（ES256）を付ける。アクセストークン（`<brand>_at_`）は 1 時間で切れ、リフレッシュトークン（`<brand>_rt_`、90 日、使うたびに入れ替え、再利用で一式を取り消し）で更新する。トークンはポッドの DB にハッシュで置く。埋め込みのアプリは、セッションのトークン（ES256、60 秒）を RFC 8693 のトークンの交換でアクセストークンに替える

## Context

- アプリは Admin API でショップのデータを読み書きする。トークンが漏れると、ショップの注文・顧客のデータが漏れる。
- `shop_id` はアクセストークンから決める（[ADR-0003](0003-tenancy-and-rls.md)）。トークンの照合はポッドで行う。
- 全体の面（`app-registry`）はショップのデータを持たない（[ADR-0002](0002-pods-and-shop-placement.md)）。アプリの秘密を各ポッドに配りたくない。
- 埋め込みのアプリは、サードパーティの Cookie の制限で Cookie に頼れない。
- 本家の OAuth の細部（導入の要求の署名の形、トークンの寿命）は確かめていない（未検証）。

## Options

トークン：

1. **期限つきのアクセストークン（1 時間）と、入れ替えるリフレッシュトークン**
2. 期限のないオフラインのアクセストークン（削除まで有効）

導入の要求と戻りの真正性：

- a. **本システムの鍵の JWT（ES256、公開鍵は JWKS）**
- b. アプリの client secret での HMAC のクエリの署名

## Decision

1 と a を採用する。詳細は [app-platform-and-apis.md](../architecture/app-platform-and-apis.md) の 4・7 節。

- 認可コードは 1 回だけ・60 秒。再利用でそのコードからのトークンを全部取り消す。`redirect_uri` は登録と完全一致。
- アクセストークン 1 時間、リフレッシュトークン 90 日・使うたびに入れ替え・再利用で一式を取り消す。オンラインのトークン（スタッフごと）はスコープとスタッフの権限の交わり。
- トークンはポッドの `app_tokens` に SHA-256 のハッシュ、Valkey に 60 秒の写し。削除で 5 秒以内に効かなくする。
- `client_secret` の確かめは、ポッドに写したハッシュで定数時間に比べる。アプリの定義は全体からポッドへの読み出しの写しで配る（ADR-0002 の経路の一覧への追加が要る）。
- 導入の要求（`install_token`）・戻り（`return_token`）・埋め込みのセッションのトークンは、本システムの ES256 の鍵で署名し、`https://<brand>.<domain>/.well-known/jwks.json` で公開鍵を出す（90 日で入れ替え、2 つを同時に載せる）。
- 埋め込みのアプリは、セッションのトークンを `grant_type=urn:ietf:params:oauth:grant-type:token-exchange` で替える。

### 他の案を選ばなかった理由

- **2（期限なし）**：漏れたトークンが削除まで使え、漏れに気づく手段がない。リフレッシュトークンの再利用の検出で盗難を見つけられる 1 の方が安全（RFC 9700 の推奨に沿う）。
- **b（HMAC）**：本システムの側で各アプリの秘密を平文で使う必要があり、全体の面と各ポッドに秘密を配ることになる。

## Consequences

- 良くなること：漏れたトークンの効く時間が 1 時間に限られ、盗難を検出できる。秘密をポッドに配らない。
- 引き受けるコスト：アプリはトークンの更新を実装する。オフラインの処理の長いアプリは、更新の失敗の扱いが要る。

## Confirmation

- 性質ベーステスト PROP-APP-003（一式の取り消し）、PROP-APP-004（ショップの一致）。
- 結合テスト：コードの再利用、`redirect_uri` の不一致、期限切れ、削除の 5 秒の効き、JWKS の鍵の入れ替え。
