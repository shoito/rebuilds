# ADR-0075: デプロイは staging → 見張りのポッド `p00` → 共有のポッド 1 つ → 残りを 25% ずつの波で出し、各波 30 分の自動のロールバックの条件を見る。スキーマの変更は広げる段と縮める段に分け、`pod-migrator` が波の順で全ポッドに当てる。縮める段は全ポッドの全サービスが新しい形だけを使ってから 7 日の後にだけ行う。移し替えは元と先のスキーマのバージョンが同じときだけ動く

## Context

- [runbooks/](../runbooks/README.md) の 3 節は、ポッドごとの段階のデプロイ（検証 → 見張りのショップのポッド → 本番のポッド 1 つ → 残りを 25% ずつ）、自動のロールバックの条件、マイグレーションは広げる段だけをデプロイで当てることを決めた。実装（移行の当て方、縮める段の時期、移し替えとの関係）は決めていない。
- ポッドは S1 で 6、S3 で 300。全ポッドの DB は同じスキーマを持つが、同じ時刻に同じバージョンである保証はない。
- ショップの移し替えは、元のポッドの行を先のポッドの同じ表に当てる（[ADR-0012](0012-shop-mover-logical-decoding-and-cutover.md)）。バージョンが違うと当てられない。
- お金・在庫・税の規則はフラグでなくコードのバージョンで出す（[AGENTS.md](../../AGENTS.md)）。壊れたら波で止めて戻すしかない。

## Options

1. **波のデプロイ、`pod-migrator` が波の順で広げる段を当て、縮める段は 7 日の後。移し替えは同じバージョンの間だけ**
2. 全ポッドに同時に出す
3. ポッドごとに独立に出す（バージョンの揃いを求めない）

## Decision

1 を採用する。詳細は [delivery.md](../architecture/delivery.md) の 4・5 節。

- 波：staging → `p00`（60 分）→ 共有のポッド 1 つ → 25% → 50% → 75% → 100%（各 30 分）。隔離のポッドは最後の波で、予定したセールの前後 24 時間は外す。
- 自動のロールバック：チェックアウトとストアフロントの 5xx の 2 倍かつ 0.1% 以上、確定の p99 2 秒、在庫・重複・決済済みで注文なしの不一致 1 件、テンプレートの上限の超過の 2 倍、関数の失敗（本システムの原因）0.01%、鍵の材料の不一致 1 件。当たれば、その波を戻して後の波を止める。
- 移行：広げる段（追加、`CONCURRENTLY` の索引、`NOT VALID` の制約）だけをデプロイで当てる。埋めるのは `workers` の作業。縮める段は、全ポッドの全サービスが新しい形だけを使い 7 日たってから。`lock_timeout = 2s`。
- `pod-migrator`（全体）が、移行のロールで、波の順に全ポッドに当て、`pod_schema_versions` に記録する。アプリのロールは DDL を持たない。
- `shop-mover` は、元と先のバージョンが同じときだけ始め、移し替えの間は両方のポッドの移行を止める。
- 全体の面は、ポッドの波の前に出す（読む側が先）。全体とポッドの間の事象と API は 1 つ前のバージョンと互換に保つ。

### 他の案を選ばなかった理由

- **2（同時）**：壊れたバージョンが全ポッド・全ショップに同時に届く。
- **3（独立）**：バージョンの違うポッドの間で移し替えができず、全体の面とポッドの間の互換の範囲が広がる。

## Consequences

- 良くなること：
  - 壊れたバージョンの影響が、見張りのポッドか 1 つのポッドで止まる。
  - 前のバージョンが今の DB で動くので、イメージの戻しで足りる。
- 引き受けるコスト：
  - 1 回のデプロイが S1 で 4〜5 時間かかり、ポッドの数が増えると波の中の並行が要る。
  - 縮める段が 7 日以上遅れ、古い列がしばらく残る。
  - 移し替えと移行の時間の取り合いを `pod-migrator` と `shop-mover` で調整する。

## Confirmation

- 性質ベーステスト：PROP-DLV-001（1 つ前のバージョンの結合テストが、広げる段の後の DB で緑）。
- CI：移行の形の検査（縮める段の変更を、7 日の条件の記録なしに拒む）、表の目録の検査。
- staging の波の試験：わざと壊したイメージで、波 0 で止まり戻る。
