# ADR-0062: 本文はポッドの `workers` が作り、本文を含む配信の依頼を暗号化した SQS で全体の `webhook-dispatcher` に渡す。`webhook-dispatcher` は本文を保存せず、結果（状態のコード、時間）だけをポッドへ返す。送り先は HTTPS・443・公開の IP だけで、名前の解決の結果を確かめて固定し、リダイレクトを追わない。送信は固定の IP の隔離した egress から行い、IP の一覧を公開する

## Context

- [ADR-0001](0001-platform-and-stack.md) は `webhook-dispatcher` を全体の面に置き、[ADR-0002](0002-pods-and-shop-placement.md) は全体の面がショップのデータを持たないと決めた。Webhook の本文は注文・顧客のデータを含む。
- 送り先の URL はアプリの開発者が決める。内部の網・クラウドのメタデータへの要求（SSRF）に使われうる。
- 受け手は、送り元の IP で許可したいことがある。
- 1 つのアプリの遅い受け口が、他のアプリの配信を遅らせてはならない（NFR-008）。

## Options

本文の置き場所：

1. **ポッドで作り、暗号化した SQS で運び、全体は保存しない**
2. 全体の面に本文を保存し、送り直しに使う
3. ポッドごとに送り手を持つ（全体の `webhook-dispatcher` を持たない）

## Decision

1 を採用する。詳細は [webhooks.md](../architecture/webhooks.md) の 6 節。

- ポッドの fanout が購読を引き、本文を作り、`webhook_deliveries`（状態だけ）を書いてから、依頼を全体の SQS（SSE-KMS、アプリのハッシュで 16 本）に入れる。`pending` の行は 1 分ごとのジョブが入れ直す。
- `webhook-dispatcher` は秘密を KMS で開き（5 分の写し）、署名して送り、結果を SNS でポッドへ返す。本文と URL のクエリをログに書かない。
- アプリごとに同時の送り 50。（ショップ、アプリ）1 秒 50。
- 送り先：`https`、443、公開の CA、TLS 1.2 以上。送るたびに名前を解決し、私的・ループバック・リンクローカル・CGNAT・メタデータ・ULA・本システムの範囲を拒み、確かめた IP に固定して接続する。リダイレクトを追わない。応答は 64 KiB まで読んで捨てる。
- egress は固定の IP の NAT（AZ ごと）。一覧を公開し、変更は 30 日前に知らせる。dispatcher は内部の網に届かないサブネットに置く。
- 「全体の面はショップのデータを持たない」を「保存しない（運ぶだけ）」と読む。ADR-0002 への注記の要否は Dev（テックリード）に確認する。

### 他の案を選ばなかった理由

- **2（全体に保存）**：全体の面にショップのデータが溜まり、ADR-0002 の分け方と、ショップの移し替え・削除の範囲が崩れる。
- **3（ポッドごと）**：ポッドの数だけ egress の固定の IP が増え、受け手の許可の一覧が長くなる。ポッドの網から外へ出る経路が増える。

## Consequences

- 良くなること：本文は SQS の保持の間だけ全体の面を通り、保存されない。SSRF の経路が 1 つの送り手に閉じる。
- 引き受けるコスト：依頼の大きさ（256 KiB）が SQS の上限に縛られる。結果の返りの経路（全体 → ポッド）を持つ。

## Confirmation

- 結合テスト：私的な IP、DNS の再束縛、リダイレクト、メタデータの IP への送り先が拒まれる。遅い受け口のアプリが他のアプリを遅らせない。
- IaC の検査：dispatcher のサブネットから内部の網へ届かない。全体の面の保存（S3、DB）に本文がない。
- 性質ベーステスト PROP-HOOK-004（分離とスコープ）。
