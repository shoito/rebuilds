# ADR-0016: 条件のコレクションの所属は保存した所属の表（`collection_products`）にする。商品の変更ではその商品だけを全条件で評価して同期で直し、条件の変更では非同期のジョブで全商品を評価し直す。カタログの変更は、商品ごとに単調に増える `catalog_version` を持つ outbox の事象にし、キャッシュ・検索・Webhook が同じ事象を使う

## Context

- 条件のコレクション（タグ、価格、ベンダーなどの条件）は、ストアフロントのコレクションのページ、検索の絞り込み、割引の対象、関数の入力（`inCollection`）で使う。
- 1 ショップに 5,000 コレクション・10 万商品を見込む。ページの描画のたびに条件を評価すると、DB の負荷が大きい。
- カタログの変更は、エッジのキャッシュ（NFR-011）、検索の索引（NFR-014）、Webhook（NFR-010）の 3 つに伝える。事象は順序が入れ替わり、重複する。

## Options

所属：

1. **保存した所属の表。商品の変更は同期、条件の変更は非同期のジョブ**
2. 読み出しの時に条件を SQL にして評価する
3. 検索の索引（OpenSearch）で評価する

事象：

- a. **商品ごとの `catalog_version` を持つ 1 つの事象の流れを、3 つの使い手が共有する**
- b. 使い手ごとに別の事象を出す

## Decision

1 と a を採用する。詳細は [catalog-and-pricing.md](../architecture/catalog-and-pricing.md) の 5・12 節。

- 商品の保存のトランザクションで、ショップの条件のコレクションの条件（保存の時に比べの列にしたもの）を、その商品だけで評価し、`collection_products` を直す。
- 条件の変更は `rebuilding` にしてジョブで 1,000 件ずつ直す。新しい変更はジョブの世代を上げ、古いジョブを止める。
- 在庫の数は条件に使えない。
- 商品・バリエーション・オプション・メディア・公開・所属を変えるトランザクションは、商品の `catalog_version` を 1 上げ、outbox に事象を 1 つ書く。事象は変わった項目の種類（`display`・`price`・`publication`・`inventory_policy`・`internal`）を持つ。
- 使い手は `catalog_version` が自分の値以下の事象を捨て、事象の中身でなく正本を読み直す（検索）か、世代を上げる（キャッシュ）。

### 他の案を選ばなかった理由

- **2（読み出しの時）**：条件の組み合わせで索引の効かない SQL になり、ページの描画の p95 を守れない。
- **3（検索の索引）**：索引の遅れ（p95 30 秒）が所属の遅れになり、割引の対象の判定に使えない。
- **b（別の事象）**：同じ変更の事象が使い手ごとに分かれ、片方の欠けを見つけにくい。

## Consequences

- 良くなること：
  - コレクションのページは表の読み出しで済む。
  - 順序の入れ替えと重複に、`catalog_version` で強くなる。
- 引き受けるコスト：
  - 商品の保存が、ショップの条件の数に比例して重くなる（5,000 × 60 で 10ms 未満の見込み。E3 で測る）。
  - 条件の変更の直後は、所属が数分混ざる。

## Confirmation

- 性質ベーステスト PROP-CAT-002（ジョブの後、所属が素直な評価と一致）、PROP-CAT-004（`catalog_version` の単調）。
- 負荷：5,000 コレクション・60 条件のショップで、商品の保存 p99 1.5 秒。
