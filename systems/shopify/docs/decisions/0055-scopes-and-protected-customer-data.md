# ADR-0055: スコープは `read_<資源>`・`write_<資源>` の形で、フィールドごとに要るスコープをスキーマの指示で持つ。顧客の個人のデータは、通常のスコープに加えて「保護のデータ」の段階（段階 1：買い手を識別する ID、段階 2：氏名・メール・電話・住所を項目ごとに）の承認を要し、公開のアプリは審査で理由を確かめる。承認のない項目は `null` と注記で返し、Webhook の本文と関数の入力からも除く

## Context

- [ADR-0009](0009-admin-api-graphql-and-cost-limits.md) は、フィールドごとに要るスコープを持ち、顧客の個人のデータには別の保護のスコープを要ると決め、細部を app-platform-and-apis の領域に任せた。
- 買い手の個人のデータのアプリへの提供は、第三者提供か委託か、外国の開発者への提供の扱いが法務の確認待ち（L3）。どの結論でも、提供の範囲を項目ごとに絞れる形が要る。
- アプリの古いクエリが、承認の変更で全体のエラーになると、アプリが止まる。

## Options

1. **通常のスコープ＋保護のデータの 2 段階（項目ごと）。未承認は `null` と注記**
2. `read_customers` だけで全項目を読める
3. 未承認の項目を選んだクエリを全体のエラーにする

## Decision

1 を採用する。詳細は [app-platform-and-apis.md](../architecture/app-platform-and-apis.md) の 5.2・6 節。

- スキーマのフィールドに `@requiresScope` と `@protectedData(field: …)` を書き、実行の前に確かめる。スコープの不足は `ACCESS_DENIED`。
- 段階 0：ID、金額、行、配送の都道府県。段階 1：顧客のタグ、注文の数、会員の区分。段階 2：`NAME`・`EMAIL`・`PHONE`・`ADDRESS` を項目ごと。
- 段階 1・2 は申請（理由）と事業者の承認。段階 2 の公開のアプリは審査（保持の期間、削除への対応、暗号化の宣言）。
- 未承認の保護の項目は `null` で返し、`extensions.redactedFields` に道を出す。Webhook の本文（`<brand>_redacted_fields`）と関数の入力も同じ判定。
- 既定で読める注文は直近 60 日（`read_all_orders` で全部）。
- 段階 2 の承認は `release.protected-data-level2` の裏に置き、L3 の確認まで公開のアプリに出さない運用にできる。

### 他の案を選ばなかった理由

- **2（1 つのスコープ）**：在庫の連携のアプリにまで買い手の住所が渡る。L3 のどの結論にも絞り込みの手段が要る。
- **3（全体のエラー）**：承認の取り消しでアプリが止まり、事業者の業務に響く。

## Consequences

- 良くなること：アプリに渡る個人のデータが項目ごとに絞られ、全経路（API、Webhook、関数）で同じ判定になる。
- 引き受けるコスト：スキーマの全フィールドに指示を書き続ける（lint で確かめる）。審査の人手が要る。
