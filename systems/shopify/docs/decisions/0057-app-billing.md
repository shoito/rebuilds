# ADR-0057: アプリの課金（定額の購読、従量、1 回）は Admin API の課金のミューテーションで作り、事業者が管理画面で承認して有効にする。代金は本システムが事業者への月次の請求に載せて受け取り、開発者の取り分を台帳（`app_earnings`）に記録する。開発者への支払いの実行は、法務の L5 の確認まで自動にしない

## Context

- MVP にアプリの課金（定額と従量）がある（[intent.md](../intent.md)）。
- 本システムが事業者から代金を受け取ってアプリの開発者に渡すことが、収納代行か資金移動業かは法務の確認待ち（L5）。
- 事業者は、知らない請求を承認なしに受けてはならない。
- 本システムは事業者にプランの料金を請求する仕組みを持つ（`merchant-admin-and-staff.md`）。

## Options

1. **本システムの請求に載せて受け取り、台帳に記録。支払いは L5 まで手で**
2. アプリの開発者が自分の決済の仕組みで事業者に直接請求する
3. 本システムが受け取り、開発者への支払いも初めから自動にする

## Decision

1 を採用する。詳細は [app-platform-and-apis.md](../architecture/app-platform-and-apis.md) の 8 節。

- 種類：定額の購読（30 日）、従量（期間の上限の額つき、冪等キー）、1 回。
- 状態：`pending` → `active`・`declined`・`expired`（48 時間）、`active` → `frozen`・`cancelled`。
- 承認の画面は本システムの画面で、`apps_billing` の権限のスタッフだけが承認する。
- 金額は JPY の整数。税の扱いは L4。
- 取り分の台帳は全体の Aurora（ショップの ID と額だけ）。月次で締める。支払いの実行は L5 の後に設計する。

### 他の案を選ばなかった理由

- **2（直接）**：事業者が多くの請求の相手を持ち、承認の画面が統一できない。アプリの削除と課金の停止が結び付かない。
- **3（自動の支払い）**：L5 の結論によっては登録・許可が要る。確認の前に送金の仕組みを作らない。

## Consequences

- 良くなること：事業者の請求が 1 つにまとまり、承認と停止を本システムが守れる。
- 引き受けるコスト：L5 の結論まで、開発者への支払いが手の作業になる。

## Confirmation

- 表駆動テスト DT-APP-002（課金の状態 × 事象）。
- 結合テスト：従量の上限を超える記録の拒否、同じ冪等キーの 2 回の記録が 1 回、アプリの削除で `cancelled`。
