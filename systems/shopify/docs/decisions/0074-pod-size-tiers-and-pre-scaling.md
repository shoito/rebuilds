# ADR-0074: ポッドの大きさを段（`p-min`・`p-std`・`x-min`・`x-std`・`x-large`、S3 の `d-xl`）で持ち、Terraform の変数で切り替える。共有のポッドは 2 AZ でピークを受けられる最小の数と CPU の自動の拡大で動かす。隔離のポッドは、セールの登録から段を決め、4 日前（ショップを移す前）に Aurora を上げ、開始の 60 分前に ECS の最小の数を予定の拡大で上げる。急増は自動の拡大を待たず、ショップの同時実行の上限と待合室で受ける

## Context

- S1 の 1 ショップの最大は 100 件/秒の注文、チェックアウトの段の要求 1,000 件/秒（[capacity.md](../architecture/capacity.md) の 3 節）。共有のポッドの平常の山は注文 1 件/秒の桁で、隔離のポッドとの差が 2 桁ある。
- Aurora の書き込みのインスタンスの型の変更は、フェイルオーバー（書き込みの数十秒の停止）を伴う。セールの最中や直前にはできない。
- Fargate の自動の拡大は分の単位で、フラッシュセールの開始の秒の単位の急増に間に合わない（速さは**未検証**）。
- 隔離のポッドは、セールのない間は空に近い。大きいまま持つと費用が大きい（[capacity.md](../architecture/capacity.md) の 6 節）。
- ポッドの追加は Terraform の 1 つのモジュールから行う（[ADR-0002](0002-pods-and-shop-placement.md)）。

## Options

1. **決めた段を変数で切り替え、隔離のポッドはセールの予定から前もって上げる。急増は上限と待合室で受ける**
2. Aurora Serverless v2 と Fargate の自動の拡大だけで受ける
3. 隔離のポッドを常に最大の段で持つ

## Decision

1 を採用する。詳細は [capacity.md](../architecture/capacity.md) の 4・5 節。

- 段：`p-min`（`db.r8g.large`）、`p-std`（`db.r8g.2xlarge`）、`x-min`（`db.r8g.large`）、`x-std`（`db.r8g.4xlarge`）、`x-large`（`db.r8g.8xlarge`）、`d-xl`（`db.r8g.16xlarge`、S3、**未検証**）。各段は Valkey・OpenSearch・ECS の最小と最大の数の組を持つ。
- 共有のポッドの ECS の最小は、1 つの AZ を失っても平常の山を受けられる数。拡大は CPU 60%（`workers` はキューの年齢）。
- 隔離のポッド：セールの登録で段を決める（受け入れ 100 人/秒以下は `x-std`、同時のセール 2 か 100 人/秒を超えるなら `x-large`）。4 日前に大きい型の読み出しを足してフェイルオーバーで書き込みにし（ショップを移す前）、Valkey を上げる。60 分前に ECS の最小を予定の拡大で上げ、終わりの 2 時間後に戻す。ショップを戻したら `x-min` へ下げる。
- 予定にない急増は、ショップの同時実行の上限（[ADR-0003](0003-tenancy-and-rls.md)）・作成の速さ（[ADR-0031](0031-checkout-admission-limits.md)）・自動の待合室（[ADR-0027](0027-flash-sale-preparation-and-surge-auto-queue.md)）で受け、自動の拡大はその後ろで追いつく。

### 他の案を選ばなかった理由

- **2（Serverless v2）**：容量の上がり方が秒の急増に追いつく保証がなく、書き込みの熱い行（在庫の枠）の振る舞いを PoC なしに信用できない。費用の見積もりが負荷の形に強く依る。
- **3（常に最大）**：隔離のポッドの費用が、セールのない月の大半で無駄になる（`x-large` の Aurora だけで月 約 1 万 USD）。

## Consequences

- 良くなること：
  - セールの前に、書き込みの停止を伴う変更を、ショップのいない時に済ませられる。
  - 段が少ない数の組で、負荷試験と費用の見積もりを段ごとに持てる。
- 引き受けるコスト：
  - 隔離のポッドの上げ下げの作業が、セールごとに Ops の承認を要る。
  - 予定にない急増の初めの数分は、上限と待合室で買い手を待たせる。

## Confirmation

- 負荷試験（E18）：段ごとに、[capacity.md](../architecture/capacity.md) の 8 節の場面の合否。
- 結合テスト（staging）：段の変更の手順（読み出しの追加 → フェイルオーバー）の停止の時間と、予定の拡大の効きの時刻。
- 本番：セールごとの振り返りで、段の選び方と実際の負荷を比べる（[runbooks/](../runbooks/README.md) の 5.3 節）。
