# ADR-0011: ポッドに種類（共有・隔離・見張り・専用）を持たせ、容量を「ポッドの単位（PU）」で数える。新しいショップは受け入れ中の共有のポッドのうち使用率の最も低いものへ置き、70% で受け入れを止め、85% で偏りの直しを計画する。隔離のポッドはセールの前に大きさを上げてからショップを移す

## Context

- [ADR-0002](0002-pods-and-shop-placement.md) は、S1 でポッド 4 つと隔離のポッド 1 つを持ち、ポッドの大きさの上限と増やす基準を領域の文書に任せた。
- ショップの重さは、書き込み、ストアフロントと API の要求、データの大きさの 3 つで偏る。ショップの数だけで置くと、重いショップが同じポッドに集まる。
- 予定したフラッシュセールのショップは、前もって隔離のポッドへ移す（[runbooks/](../runbooks/README.md) の 5 節、[ADR-0027](0027-flash-sale-preparation-and-surge-auto-queue.md)）。
- デプロイの段（[runbooks/](../runbooks/README.md) の 3 節）は「見張りのショップのポッド」を要る。

## Options

1. **PU（書き込み・要求・大きさの比の最大）で数え、使用率の最も低いポッドへ置く。閾値で受け入れを止め、移し替えで直す**
2. ショップの数で均等に置く
3. ショップ ID のハッシュで置く（一貫したハッシュ）

## Decision

1 を採用する。詳細は [shops-and-pods.md](../architecture/shops-and-pods.md) の 4・7 節。

- 種類：`shared`（`p01`〜）、`isolation`（`x01`〜）、`canary`（`p00`、見張りと社内のショップ）、`dedicated`（`d01`〜、S2 から）。S1 は共有 4、隔離 1、見張り 1（最小の大きさ）。
- ショップの PU：`max(書き込みの行/時 ÷ ポッドの容量, 要求/分 ÷ ポッドの容量, 大きさ ÷ ポッドの容量)`。直近 7 日の最大の値を日次で数える。新しいショップは最初の 30 日 0.01%。容量の初期値は [capacity.md](../architecture/capacity.md) の 4 節。
- 新しいショップは `accepting` の共有のポッドのうち使用率の最も低いものへ。70% で `full`。全部が `full` なら新しいポッドを作る作業を起こし、作る間は 85% まで受ける。
- 偏りの直し：週次に、85% を超えたポッドから PU の大きい順に移す候補を作り、Ops が承認する。1 回に 1 ポッドから移す PU は 15% まで。
- 隔離のポッド：セールの登録から大きさの段を決め、4 日前までに大きさを上げ、3 日前までにショップを移し、後 7 日で戻す。同時に 4 ショップ、同じ時刻のセールは 2 まで。足りなければ `x02` を作る。
- 共有のポッドの容量の 25% を 4 週超え続けるショップは、専用のポッドの候補にする（S2 から）。

### 他の案を選ばなかった理由

- **2（数）**：重さの偏りを見ない。重いショップが同じポッドに集まる。
- **3（ハッシュ）**：置き場所を選べず、隔離のポッドへの前もっての移し替えと、偏りの直しができない。ポッドを足したときに多くのショップが動く。

## Consequences

- 良くなること：
  - 1 つの数でポッドの空きを判断でき、新しいポッドを作る時期が読める。
  - 隔離のポッドの大きさを、セールの規模に合わせて前もって上げられる。
- 引き受けるコスト：
  - ショップの重さの日次の数え上げ（`shop_load`）を持つ。
  - PU の容量の値は初期見積もりで、負荷試験と本番の計測で直し続ける。
  - 見張りのポッドの分、ポッドの最小の費用が 1 つ増える。

## Confirmation

- 単体：PU の計算と、置き場所の選び方の表駆動テスト（使用率の同じとき、`full` のとき、全部が `full` のとき）。
- 夜間：生成したショップの重さの分布で、1 年分の作成と成長を模擬し、どのポッドも 85% を超える期間が 2 週を超えない。
- 本番：ポッドの使用率と PU の推移を週次で見る（[capacity.md](../architecture/capacity.md) の 7 節）。
