# ADR-0006: 決済は外部の提供者に任せ、本システムはカード番号に触れない。提供者の差を吸収するアダプターの契約、冪等キー、Webhook の inbox を持つ。Stripe の題材は提供者の 1 つとして使い、設計し直さない

## Context

ショップの買い手は、カード、コンビニ払い、銀行振込、キャリア決済、後払いで払う。

- カード番号を扱うと、PCI DSS の範囲と、割賦販売法のカード情報の保護の扱い（法務の確認待ち L7）が本システム全体に広がる。
- 決済の基盤（カード情報の保管、アクワイアラへの接続、3D セキュア、台帳、入金）は、rebuilds の Stripe の題材の主な論点で、そこで設計している（[Stripe の intent](../../../stripe/docs/intent.md)）。この題材で同じものを設計し直すと、論点がぶれる。
- 日本の決済手段は、提供者ごとに流れが違う（リダイレクト、番号の発行と後の入金の通知、キャリアの認証）。
- 提供者への要求は、時間切れで結果が不明になりうる。提供者の Webhook は重複し、順序が入れ替わる。

## Options

1. **本システムは提供者の API の利用者になる。アダプターの契約で差を吸収し、カード番号は提供者のホストした入力部品・決済ページで受ける**
2. 自前のカード情報の保管とトークン化を持ち、複数の提供者へ振り分ける
3. 1 つの提供者に固定し、その API を直接呼ぶ

## Decision

1 を採用する。

### 範囲

- **本システムが持つもの**：決済の試行（`payment_attempts`）、提供者の参照の ID、金額、状態、冪等キー、Webhook の inbox、返金の依頼、照合。
- **提供者が持つもの**：カード番号・セキュリティコード、3D セキュア、アクワイアラ・コンビニ・銀行・キャリアへの接続、提供者の台帳と入金。
- カードの入力は、提供者のホストした入力部品（iframe）か、提供者の決済ページへのリダイレクトだけで受ける。本システムのページの DOM・サーバー・ログに、カード番号が入る経路を作らない。チェックアウトのページの CSP で、入力部品の配信元を提供者のドメインに絞る。

### アダプターの契約

各提供者のアダプター（`packages/payments/adapters/<provider>`）は、次の操作を実装する。

| 操作 | 意味 |
| --- | --- |
| `createSession(attempt, amount, method, returnUrl, idempotencyKey)` | 決済のセッションを作る。リダイレクトの URL か、入力部品のための値を返す |
| `getResult(providerRef)` | 結果を照会する（成功・オーソリ・支払い待ち・失敗・処理中）。必須 |
| `capture(providerRef, amount, idempotencyKey)` | 売上の確定（一部を含む） |
| `void(providerRef, idempotencyKey)` | オーソリの取り消し |
| `refund(providerRef, amount, idempotencyKey)` | 返金（一部を含む） |
| `verifyWebhook(headers, body)` | Webhook の署名の検証と、イベントの ID・種類・参照の ID の取り出し |

> 2026-10-10 の注記：`findByReference(merchantRef)`（加盟店の参照の番号＝試行の ID で照会し、`providerRef` と正規の結果を返す）を必須の操作に足した。`createSession` の時間切れで `providerRef` が分からないときに確定するため（[ADR-0035](0035-payment-attempt-states-and-result-normalization.md)）。照会の API は `providerRef` と加盟店の参照の番号の両方で引けることを、提供者の選定の条件にする。

- **冪等キー**：`<checkout_id>:<attempt>:<op>`（返金は `<refund_id>:refund`）。提供者が冪等キーを受けない場合は、アダプターが参照の番号（加盟店の注文の番号）の重複の拒否で同じ効果を作る。どちらも持たない提供者は選ばない。
- **照会の API を持たない提供者は選ばない。** 結果が不明のときに確定できないため（[ADR-0005](0005-checkout-state-machine-and-exactly-once-orders.md)）。
- **Webhook の inbox**：提供者の Webhook は、署名を確かめ、（提供者、イベントの ID）を一意の鍵として `payment_webhook_inbox` に入れてから 200 を返す。処理は inbox を読むジョブが行い、照会の API で結果を確かめてから `completeCheckout` を呼ぶ。
- 提供者のアダプターは、事業者ごとの認証の情報（API キー、加盟店の ID）を、ポッドの DB に KMS の封筒の暗号（`kms-pod-<id>-secrets`）で置き、平文で置かない。

> 2026-10-10 の注記：最初は「Secrets Manager の参照で持つ」としたが、ショップの数だけの秘密の月額の費用と取得の API の速さの上限のため、[ADR-0066](0066-encryption-and-key-layout.md) の DB の封筒の暗号に置き換えた。Secrets Manager はシステムの秘密（全体の DB の資格情報、提供者のプラットフォームの鍵など）だけに使う。

### 日本の決済手段

| 手段 | 流れ | 注文の作成 |
| --- | --- | --- |
| カード | 入力部品か決済ページ、3D セキュアは提供者 | オーソリの成功で作成。売上の確定は既定で同時 |
| コンビニ払い | 提供者が支払いの番号を発行、後で入金の通知 | 番号の発行で「支払い待ち」の注文を作成。期限切れで取り消し |
| 銀行振込 | 提供者が振込先（バーチャル口座）を発行、後で入金の通知 | 同上。過不足の入金は提供者の通知に従い事業者に示す |
| キャリア決済 | キャリアの認証へリダイレクト | 認証の成功で作成 |
| 後払い | 提供者の与信へリダイレクト・同期の与信 | 与信の成功で作成 |

- 手段ごとの細かい流れ、提供者の選定（候補の例：Stripe の題材の再構築したもの、日本の決済代行 2 社。能力は未確認）、手数料の扱いは payments-integration の領域で決める。

### Stripe の題材との関係

- Stripe の題材は、提供者の 1 つとして、このアダプターの契約で使う。Stripe の題材の PaymentIntent・Checkout・Webhook の形は、その題材の文書を正とし、この題材では写さない。
- この題材の台帳は持たない。事業者の売上と入金は、提供者の管理画面と精算のファイルで見る。本システムは注文と返金の金額の記録と、照合の結果を持つ。

### 他の案を選ばなかった理由

- **2（自前の保管）**：PCI DSS の範囲が本システムに入り、Stripe の題材の論点を作り直すことになる。
- **3（1 社に固定）**：日本の決済手段を 1 社で網羅できる保証がなく、提供者の障害のときに切り替えられない。

## Consequences

- 良くなること：
  - カード番号が本システムに入らず、PCI DSS の範囲が小さくなる（範囲の確定は security の領域と QSA の確認、法務の L7）。
  - 提供者を足すことが、アダプターの追加で閉じる。
- 引き受けるコスト：
  - 提供者ごとの差（冪等の効き方、Webhook の再送、照会の API の速さ）をアダプターで吸収し、契約の試験を提供者ごとに持つ。
  - 決済の体験（入力部品の見た目、3D セキュアの画面）は提供者に依る。

## Confirmation

- 契約の試験：アダプターごとに、同じ冪等キーの 2 回の `createSession`・`capture`・`refund` が 1 回の効果になること、`getResult` が全状態を返すことを、提供者の試験の環境（なければ模型）で確かめる。
- 検査：チェックアウトのページの CSP と、サーバーの要求のログの走査で、カード番号の形（Luhn の検査を通る 13〜19 桁）が現れないこと（夜間と本番の抜き取り）。
- 性質ベーステスト：Webhook の重複・順序の入れ替え・リダイレクトとの競合で、`completeCheckout` の結果が 1 回だけ（[ADR-0005](0005-checkout-state-machine-and-exactly-once-orders.md)）。
