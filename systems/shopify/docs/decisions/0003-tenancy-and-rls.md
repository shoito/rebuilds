# ADR-0003: ショップをテナントにし、ポッドの DB の全表に `shop_id` と FORCE RLS を置く。`shop_id` はホスト名・トークン・セッションからだけ決める。ポッドの中で、ショップごとの同時実行と速さの上限を置く

## Context

1 つのポッドには、S1 で 1.25 万のショップが同居する（[ADR-0002](0002-pods-and-shop-placement.md)）。ショップのデータ（商品、在庫、注文、買い手の住所）が他のショップに 1 件でも出れば漏えいである。

- データの出口は多い：ストアフロントの HTML、Storefront API、Admin API、管理画面、Webhook、検索、エッジのキャッシュ、書き出し、メールの通知。
- 主体も多い：買い手、スタッフ（複数のショップに属しうる）、アプリ（ショップごとに入れられ、スコープを持つ）、社内のサポート。
- 同じポッドの 1 つのショップのフラッシュセールや、アプリの重いクエリで、他のショップが遅くなってはならない（NFR-008）。

## Options

1. **ポッドの DB の全表に `shop_id` を持たせ、FORCE RLS と `SET LOCAL app.shop_id` で絞る**
2. ショップごとに PostgreSQL のスキーマを分ける
3. アプリの層の条件（`WHERE shop_id = ?`）だけで絞る

## Decision

1 を採用する。

### 表と RLS

- ポッドの DB の表は、`shop_id`（UUIDv7）を持ち、主キーと索引の先頭に置く。`FORCE ROW LEVEL SECURITY` を設定し、ポリシーは `shop_id = current_setting('app.shop_id')::uuid` だけにする。
- アプリは、要求・ジョブごとにトランザクションを開き、最初に `SET LOCAL app.shop_id` を実行する。接続のプールで値が残らないように、`SET` ではなく `SET LOCAL` だけを使う。
- アプリの DB のロールは、表の持ち主でなく、`BYPASSRLS` を持たない。
- **RLS の外の表**はポッドの DB では次だけにし、ショップのデータの列を持たせない。
  - `shop_freeze`（移し替えの停止の印）
  - outbox の読み出しの位置
  - スキーマの移行の記録
- 全体の Aurora は、ショップのデータを持たない。ショップの表（`shops`）、スタッフのアカウント、アプリの登録は、それぞれの所有者の条件で RLS を付ける（領域の文書で書く）。

### `shop_id` の決め方

| 入口 | 決め方 |
| --- | --- |
| ストアフロント、Storefront API、チェックアウト | ホスト名 → `shop-directory`（エッジのヘッダーをポッドで検証し、ポッドの DB の `domains` で引き直す） |
| Admin API | アクセストークン → 導入（installation）の行 → `shop_id`。URL のショップと一致しなければ 401 |
| 管理画面 | スタッフのセッション＋選んだショップ。スタッフがそのショップに属することを確かめる |
| 提供者・運送会社の Webhook | URL のショップの ID と、署名の検証に使う、そのショップの秘密 |
| ジョブ | ジョブのメッセージの `shop_id`（outbox で書いたもの）。ジョブは 1 つのショップだけを扱う |

- 要求の本文、GraphQL の引数、クエリの文字列に `shop_id` を書いても使わない。グローバル ID（`gid://<brand>/Order/...`）は、RLS の中でだけ引く。

### ショップをまたぐ処理

ポッドの中でショップをまたぐ処理は、次だけにし、専用の DB のロールを通す。一覧にない経路を足すときは、先にこの ADR を直す。

- X1：システムの作業（引き当ての期限の掃除、決済の照合、保持の削除）。ショップを 1 つずつ `SET LOCAL` して回す
- X2：`relay` の outbox の読み出し
- X3：`shop-mover` の読み出し（[ADR-0002](0002-pods-and-shop-placement.md)）

### ポッドの中のうるさい隣人の抑え

| 対象 | 仕組み |
| --- | --- |
| ストアフロント | エッジのキャッシュ。元への要求はショップごとのトークンバケット（プランから）。超えたら古いキャッシュを返す（`stale-if-error`） |
| チェックアウト | ショップごとの同時実行の上限（既定 50、隔離のポッドでは 500）と、作成の速さの上限。待合室と組む（flash-sales-and-queueing の領域） |
| Admin API | アプリとショップの組ごとの費用のバケット（[ADR-0009](0009-admin-api-graphql-and-cost-limits.md)）と、ショップごとの全アプリの合計の上限 |
| DB | ショップごとの DB の接続の同時の数の上限（アプリの層のセマフォ）、文の時間切れ（ストアフロント 2 秒、Admin API 10 秒、ジョブ 60 秒） |
| ジョブ | ショップごとの公平なキュー（SQS のメッセージ グループ、ショップごとの同時の数の上限） |
| Webhook | ショップとアプリごとの送信の速さの上限 |

### 他の案を選ばなかった理由

- **2（スキーマ）**：ポッドあたり 1 万を超えるスキーマは、移行の時間とカタログの大きさで運用できない。
- **3（アプリの条件だけ）**：条件の書き忘れが 1 件で漏えいになる。エージェントが書くコードの量を考えると、DB で止める層が要る。

## Consequences

- 良くなること：
  - 条件の書き忘れが DB で止まる。
  - 他の題材と同じ形で、エージェントが扱いやすい。
- 引き受けるコスト：
  - すべての索引の先頭に `shop_id` を置くので、索引が大きくなる。
  - エッジのキャッシュ・検索・Valkey は RLS で守れない。鍵の先頭のショップと試験で守る（storefront-api-and-caching、search-and-recommendations の領域）。

## Confirmation

- 結合テスト：ポッドの DB のすべての表に `FORCE ROW LEVEL SECURITY` とポリシーがあることを、スキーマの検査で確かめる。RLS の外の表の一覧を CI が上の一覧と照らす。
- 性質ベーステスト：任意の 2 つのショップのデータと操作の列で、ショップ A の主体（買い手、スタッフ、アプリ）の応答・Webhook・検索・キャッシュに、ショップ B の値が出ない（漏れの経路の表、[quality.md](../quality.md) の 2.2.1 節 G）。
- lint：`SET`（`LOCAL` なし）の `app.shop_id` を禁止する。要求の本文・GraphQL の引数から `shop_id` を読むコードを禁止する。
- 負荷試験：同じポッドの 1 ショップに割り当ての 10 倍をかけ、他のショップの NFR-001・NFR-003 を確かめる（E18）。
