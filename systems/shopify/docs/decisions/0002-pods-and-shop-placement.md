# ADR-0002: ショップを単位に、Aurora・Valkey・SQS・アプリのサービスを持つポッド（完全なセル）へ置く。エッジが KeyValueStore でショップ → ポッドを引く。ショップの移し替えは、コピー・論理デコードでの追いかけ・10 秒以内の書き込みの停止・ディレクトリの切り替えで行う

## Context

S3 で 500 万のショップ、注文の最大 5,000 件/秒を見込む（[architecture/README.md](../architecture/README.md) の 2 節）。1 つの DB では書き込みも障害の範囲も足りない。

- ショップの間でデータを共有しない。注文・在庫・カタログはショップの中で閉じる。
- ショップの大きさの差が大きい。ほとんどは小さいが、限定品の発売の日だけ 1 秒数百件の注文を受けるショップがある。
- 本家は、ショップの集まりを完全に分けたデータストアに置くポッドを持ち、アプリのサーバーは共有する。1 つの要求は 1 つのポッドだけに触れる（[Pods Architecture](https://shopify.engineering/a-pods-architecture-to-allow-shopify-to-scale)、2026-10-10 に確認）。
- フラッシュセールのショップを、前もって空いたポッドへ移したい。ショップの成長で、ポッドの偏りを直したい。

## Options

分け方：

1. **ポッド＝DB・Valkey・SQS・アプリのサービスを持つ完全なセル。エッジで振り分ける**
2. ポッド＝DB だけ。アプリのサービスは全体で共有（本家の形）
3. 1 つの分散 SQL の DB（Aurora DSQL など）にショップの鍵で分けて置く

移し替え：

- a. **自前の `shop-mover`（ショップの行のコピー、PostgreSQL の論理デコードで変更を追いかけ、短い書き込みの停止で切り替え）**
- b. 書き込みを長く止めて、書き出しと取り込みで移す
- c. 両方へ書き込み（二重の書き込み）、後で読み出しを切り替える

## Decision

1 と a を採用する。

### ポッド

- **ポッド**は、Aurora PostgreSQL のクラスタ（書き込み 1、読み出し 1 以上）、Valkey、SQS のキューの組、`storefront-renderer`・`storefront-api`・`checkout`・`admin-api`・`workers`・`relay` の ECS のサービス、ALB を持つ。Terraform の 1 つのモジュールから作る。
- S1 はポッド 4 つと、フラッシュセールの隔離のポッド 1 つ。S2 で 40、S3 で 300 を見込む。ポッドの大きさの上限（ショップの数、書き込みの量）と増やす基準は infrastructure・capacity の領域で決める。
- **全体の面**（`shop-directory`、`identity`、`app-registry`、`waiting-room`、`shop-mover`、`webhook-dispatcher`）はポッドの外に置き、ショップのデータ（商品、注文、買い手）を持たない。

### 振り分け

- `shop-directory`（全体の Aurora）が、ショップ・ドメイン → `shop_id`・`pod_id`・状態（`active`・`moving`・`frozen`）の正本を持つ。変更を CloudFront の KeyValueStore に配る。
- CloudFront Functions がホスト名で KeyValueStore を引き、ポッドの入口（ALB）を選び、`x-<brand>-shop-id`・`x-<brand>-pod-id` のヘッダーを付ける。ポッドのサービスは、自分のポッドの ID と違う要求を 421 で拒む（古い振り分けの検出）。

> 2026-10-10 の注記：KeyValueStore は 1 つの保存が 5 MB で、全ホストは入らない（S1 の登録 10 万ショップで足りない）。KeyValueStore には要求の多いホストだけを「熱い集まり」（4 MB まで）として置き、集まりにないホストは、関数が全体の面の `edge-router` を元に選び、`edge-router` が `shop-directory` で引いてポッドへ中継する形にした（[ADR-0010](0010-shop-routing-hot-set-and-custom-domains.md)）。状態の `moving`・`frozen` は KeyValueStore に出さない。移し替えの停止はポッドの DB の印、ライフサイクルは [ADR-0013](0013-shop-lifecycle-and-data-deletion.md) の状態で表す。
- Admin API（`<shop>.<brand>.<domain>/admin/api/...`）と Webhook の受け口（提供者から）も同じ振り分けを通す。提供者の Webhook の URL にはショップの ID を入れる。
- **1 つの要求・1 つのジョブは 1 つのポッドだけに触れる。** ポッドをまたぐ経路は次だけにし、一覧にない経路を足すときは、先にこの ADR を直す。
  - P1：`shop-directory` の読み出し（振り分け）
  - P2：`shop-mover`（移し替え）
  - P3：全体の集計（請求の利用量、SLI）。各ポッドが SNS へ出したものを全体で集める
  - P4：スタッフのアカウント（`identity`）から、属するショップの一覧を引く
  - P5：全体の面からポッドへの読み出しの写し。アプリの定義、プランの上限、言語と通貨の表を全体の面が SNS で配り、各ポッドが自分の DB の写しの表（`*_replica`、RLS の外、ショップのデータの列を持たない）に当てる。ポッドの要求は写しだけを読み、全体の Aurora を直接読まない（[ADR-0010](0010-shop-routing-hot-set-and-custom-domains.md)）

> 2026-10-10 の注記：統合の工程で P5 を足した（ADR-0010）。また、全体の `webhook-dispatcher` は、ポッドが作った Webhook の本文を暗号化した SQS で受けて送るが、本文を保存しない（SQS の保持の中だけ）。「全体の面はショップのデータを持たない」は「保存しない（運ぶだけ）」と読む（[ADR-0062](0062-webhook-egress-and-payload-custody.md)）。

> 2026-10-10 の注記：データモデルの工程で、P3 に待合室への受け渡しを含めた。ポッドの `workers` は、フラッシュセールの設定（開始・終わり、`rate_cap`、`k`・`q`、許可証の期限）を `sale/config` の事象で、在庫の予算の材料（`U = Σavailable`、`R = Σreserved`）を `sale/budget` の事象で 5 秒ごとに SNS へ出す。全体の `waiting-room` は、それを全体の `waiting_room_sales` と Valkey の `wr:{<sale_id>}:budget` に当てる。運ぶ値はセール・ショップの ID と数だけで、全体の面はショップのデータを持たない。`waiting-room` はポッドの DB を直接読まない（[data-model.md](../architecture/data-model.md) の D-16）。

### ショップの移し替え

1. **コピー**：移す先のポッドに、ショップの `shop_id` の行を表ごとにコピーする。コピーの開始の LSN を記録する。
2. **追いかけ**：元のポッドの論理デコードのスロット（`pgoutput`、表の公開を絞る）から、そのショップの行の変更だけを選び、先へ当てる。遅れが 1 秒未満になるまで続ける。
3. **停止と照合**：`shop-directory` の状態を `moving` にし、元のポッドの `shop_freeze` の表に印を書く。印のあるショップへの書き込みのトランザクションは、RLS のポリシーと同じ関数で拒まれる（503 と `Retry-After: 5`）。残りの変更を当て、表ごとの行の数とチェックサムを比べる。目標は停止 10 秒以内（NFR-015）。
4. **切り替え**：`shop-directory` を新しいポッドに変え、KeyValueStore に配る。伝わる前に古いポッドへ来た要求は、古いポッドが 15 分（最大 24 時間）の間、新しいポッドへ中継する（1 段だけ。データに触れるのは新しいポッドだけ）。元のポッドの行は 7 日の後に消す（その間は読み出しの専用で残す）。

> 2026-10-10 の注記：最初は「伝わる前に古いポッドへ来た要求は 421 で再送させる」としたが、ブラウザは 421 で別の経路へ送り直さないので、[ADR-0012](0012-shop-mover-logical-decoding-and-cutover.md) の 15 分の中継の窓に置き換えた。`x-<brand>-pod-id` が自分と違う要求の 421 は残す。
5. 照合が合わなければ、切り替えずに `active` に戻し、先のポッドの行を消す。
- 進行中の引き当て・チェックアウトもそのまま移る（同じ表の行）。期限の掃除は、移し替え中のショップを飛ばす。
- 本家の Ghostferry（MySQL）は使わない。DB が違い、移し替えは核の論点である。

### うるさい隣人

- ポッドの中では、ショップごとの同時実行と速さの上限を置く（[ADR-0003](0003-tenancy-and-rls.md)）。
- 予定したフラッシュセールのショップは、Ops の手順で前もって隔離のポッドへ移す（[runbooks/](../runbooks/README.md) の 5 節）。予定にない急増は、待合室を自動で有効にして流量を絞る（flash-sales-and-queueing の領域）。

### 他の案を選ばなかった理由

- **2（本家の形）**：アプリのサービスを共有すると、各タスクがすべてのポッドの DB に接続を持ち、ポッドが増えるほど接続の数が掛け算で増える。1 つのショップの急増がアプリの層で他のポッドのショップと資源を取り合う。Fargate なら小さなサービスをポッドごとに持つ費用は小さい。
- **3（分散 SQL）**：在庫の熱い行と、ショップの中の大きなトランザクションの振る舞いを、PoC なしに信用できない。障害の範囲が全ショップになる。
- **b（長い停止）**：大きなショップは書き出しと取り込みに数十分かかり、その間売れない。
- **c（二重の書き込み）**：アプリのすべての書き込みの経路に二重の書き込みを入れることになり、在庫の行で食い違う。

## Consequences

- 良くなること：
  - 障害の範囲がポッドに閉じる。DB の接続の数がポッドの中で決まる。
  - フラッシュセールのショップを前もって隔離できる。
  - ポッドの形が 1 つのモジュールで、増やすのが機械的になる。
- 引き受けるコスト：
  - ポッドの数だけ Aurora と Fargate のサービスの最小の費用がかかる。
  - 移し替えの仕組み（論理デコード、照合、停止の印）を持ち、表を足すたびに対象に含める。
  - ショップをまたぐ機能（全ショップの検索、マーケットプレイス）は作りにくい。必要なら全体の面に読み出しの写しを作る。

## Confirmation

- 結合テスト：ポッドのサービスが、自分のポッドでない `x-<brand>-pod-id` を 421 で拒む。
- lint：ポッドのサービスのコードが、全体の Aurora の表のうち P1〜P4 の経路の外を読まない。
- 移し替えの試験：負荷（書き込み 1 秒 100 件）をかけたまま、任意のショップを移し、移した後の行の数・チェックサム・在庫の数が一致し、停止が 10 秒以内（E2 の `shop-move-poc` と夜間の試験）。
- 表の目録の検査：ポッドの DB のすべての表が `shop_id` を持ち、移し替えの対象の一覧にある（CI がスキーマと一覧を比べる）。
