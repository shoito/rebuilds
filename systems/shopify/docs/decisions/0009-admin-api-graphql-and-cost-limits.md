# ADR-0009: Admin API は GraphQL だけにし、日付のバージョン（`YYYY-MM`、四半期）を持つ。クエリの費用を実行の前に計算し、アプリとショップの組ごとのリーキーバケット（Valkey）で絞る。重い読み出しは一括の操作（S3 の JSONL）

## Context

アプリと事業者の自動化は、Admin API で商品・在庫・注文・顧客を読み書きする。管理画面も同じ API を使う。

- アプリの要求は、件数では重さが測れない。1 回のクエリで、商品 250 件 × バリエーション 100 件 × 在庫の拠点を読める。
- 1 つのアプリの重い読み出しが、同じポッドのチェックアウトの DB を食いつぶしてはならない（NFR-008）。
- アプリの開発者は、残りの量を見て速さを調整したい。
- API の形を変えると、配ったアプリが壊れる。
- 本家は、計算した費用のリーキーバケットで絞る。回復の速さはプランごとに 1 秒 100〜2,000、1 つのクエリの上限は 1,000、オブジェクト 1、ミューテーション 10、コネクションは `first`・`last` で決まる（[GraphQL Admin API rate limits](https://shopify.dev/docs/apps/build/apis/graphql-admin/rate-limits)、2026-10-10 に確認）。配列の入力は 250 件まで（[API usage limits](https://shopify.dev/docs/api/usage/limits)）。

## Options

API の形：

1. **GraphQL だけ**
2. GraphQL と REST の両方
3. REST だけ

上限の単位：

- a. **計算した費用（実行の前に見積もり、実行の後に実際の費用で返す）のリーキーバケット。アプリとショップの組ごと**
- b. 要求の件数のバケット
- c. 同時実行の数だけ

## Decision

1 と a を採用する。

### API の形

- 入口：`https://<shop>.<brand>.<domain>/admin/api/<version>/graphql.json`。認証は `X-<Brand>-Access-Token`（`<brand>_at_` の接頭辞、ハッシュで保存）。
- **バージョン**：`YYYY-MM`（1・4・7・10 月）。各バージョンを 12 か月支える。古いバージョンの要求には、`X-<Brand>-Api-Version-Deprecated` のヘッダーを付ける。バージョンの間の違いは、スキーマの変換の層（`packages/admin-schema/versions`）で吸収する。
- 構文解析と検証は graphql-js（GraphQL の参照の実装）を使う。費用の計算、実行の計画（データの先読み）、権限の判定は自前で書く。
- ID はグローバル ID（`gid://<brand>/<Type>/<uuid>`）。ページングはカーソル（`first`・`last` は 250 まで）。
- ミューテーションは任意の `Idempotency-Key` のヘッダーを受け、24 時間、同じ結果を返す。
- **スコープ**：`read_products`・`write_products`・`read_orders`・`write_orders`・`read_customers`・`write_inventory` などの形。フィールドごとに要るスコープをスキーマの指示で持ち、実行の前に検査する。顧客の個人のデータのフィールドは、別の保護のスコープを要る（法務の L3。app-platform-and-apis の領域）。

### 費用

- 既定の費用：スカラー・列挙 0、オブジェクト 1、インターフェースとユニオンは選んだ型の最大、コネクションは `2 + first（または last）× 子の選択の費用`、ミューテーション 10。重いフィールドは、スキーマの指示で費用を手で付ける。
- **見積もり（requested cost）**を実行の前に計算する。1 つのクエリの上限 1,000 を超えたら、実行せずに `MAX_COST_EXCEEDED` を返す。
- 実行の後に**実際の費用（actual cost）**を数え、見積もりとの差をバケットに返す。
- 応答の `extensions.cost` に `requestedQueryCost`・`actualQueryCost`・`throttleStatus`（`maximumAvailable`・`currentlyAvailable`・`restoreRate`）を入れる。形は本家に寄せる。

### バケット

| プラン | 回復（1 秒あたり） | 容量 |
| --- | --- | --- |
| ベーシック | 100 | 1,000 |
| アドバンス | 200 | 2,000 |
| プラス | 1,000 | 10,000 |

- バケットは（アプリ、ショップ）の組ごと。ポッドの Valkey に置き、取り出しと回復を 1 つの Lua のスクリプトで行う。
- 見積もりが残りを超えたら、実行せずに `THROTTLED` のエラー（HTTP は 200、本家に寄せる）と、回復までの秒数を返す。
- 加えて、ショップごとの全アプリの合計の回復の上限（プランの回復の 5 倍）と、ポッドの DB の負荷による一時の引き下げ（`ops.admin_api_restore_factor`、下げるだけ）を置く。
- **Valkey の障害のとき**は、各タスクの局所のバケット（容量 ÷ タスクの数）に落とす。上限を外さない（閉じる側に倒す）。
- 管理画面（自社のアプリ）も、同じ費用と、自社のアプリとしてのバケットを使う。内部の近道の API を作らない。

### 一括の操作

- 費用の上限を超える読み出しは、一括の操作（`bulkOperationRunQuery`）で受ける。ワーカーが RLS の中でページを辿り、結果を JSONL で S3 に書き、期限つきの URL を返す。完了は Webhook（`bulk_operations/finish`）で知らせる。
- 一括の操作は、アプリとショップの組ごとに同時に 1 つ。読み出しの DB は、ポッドの読み出しの写しを使う。
- 一括の書き込み（JSONL を受けてミューテーションを繰り返す）も同じ形で持つ（app-platform-and-apis の領域）。

### 他の案を選ばなかった理由

- **2（GraphQL と REST）**：2 つの形の上限・バージョン・権限の検査を持つことになる。
- **3（REST だけ）**：必要な値だけを 1 回で読めず、アプリが多くの要求を出す。
- **b（件数）**：重いクエリと軽いクエリを同じに数え、DB の負荷を表さない。
- **c（同時実行）**：速いクエリを連打するアプリを止められない。補助として、アプリとショップごとの同時実行 10 は別に置く。

## Consequences

- 良くなること：
  - DB の負荷に近い量で絞れ、アプリの開発者が残りを見て調整できる。
  - 管理画面と外部のアプリが同じ API で、API の品質が管理画面で常に試される。
- 引き受けるコスト：
  - 費用の計算とスキーマの費用の指示を保守する。費用と実際の DB の負荷のずれを、本番の計測で見直す。
  - 四半期ごとのバージョンと、12 か月のバージョンの変換の層を持つ。

## Confirmation

- 性質ベーステスト：任意のクエリで、見積もりが実際の費用以上になる（返すことはあっても、足りなくならない）。1,000 を超える見積もりのクエリは実行されない。
- 結合テスト：バケットの取り出しと回復が、並行の要求で残りを負にしない。Valkey を止めると局所のバケットに落ち、上限を超えない。
- 契約の試験：バージョンごとのスキーマの写し（SDL）を固定し、支えている間に壊す変更がないことを CI で比べる。
- 本番：見積もりの費用と、DB の時間の相関を週ごとに見る（observability の領域）。
