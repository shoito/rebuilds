# ADR-0063: スタッフのアカウントは `identity` に 1 つだけ持ち、2 段階の認証（パスキーか TOTP、SMS なし）を全員に必須にする。ショップへの入場は、`identity` が署名した 60 秒の入場の主張を、ショップのポッドが所属を確かめて 15 分の管理のトークンに替える。SSO は確かめたドメインを持つ組織の単位で、協力者はパートナーの組織のアカウントが事業者の承認で期限つきの所属を得る

## Context

- スタッフは複数のショップに属しうる。アカウントは全体の面の `identity`、ショップの中の権限は各ポッドが持つ（[architecture/README.md](../architecture/README.md) の 1.2 節）。全体の面はショップのデータを持たない（[ADR-0002](0002-pods-and-shop-placement.md)）。
- 管理画面は Admin API だけを使う（[ADR-0009](0009-admin-api-graphql-and-cost-limits.md)）。Admin API の `shop_id` はトークンかセッションから決める（[ADR-0003](0003-tenancy-and-rls.md)）。
- 事業者のアカウントの乗っ取りは、売上の口座・顧客のデータ・テーマ（チェックアウトへの不正なスクリプト）に直結する（[security.md](../architecture/security.md) の 3 節）。
- 制作会社・運用代行が、多くのショップを代わりに操作する。事業者のスタッフの枠を使わず、期限と範囲を絞りたい。
- 大きな事業者は、自社の IdP で社員を管理したい。

## Options

入場：

1. **`identity` の短い入場の主張を、ポッドが所属を確かめて管理のトークンに替える**
2. `identity` がショップの権限まで持ち、トークンを出す
3. ポッドごとにログインする

2 段階の認証：

- a. **全員に必須（パスキーか TOTP）**
- b. 任意（所有者だけ必須）

## Decision

1 と a を採用する。詳細は [merchant-admin-and-staff.md](../architecture/merchant-admin-and-staff.md) の 4 節。

- アカウントの方法は、パスキー、メールとパスワード（Argon2id、漏えいした値の拒否）、SSO。2 段階の認証はパスキーか TOTP で全員に必須。SMS は使わない。回復のコード 10 個。
- 入場の主張：JWT（ES256）、60 秒、`sub`・`aud`（ショップ）・`amr`・`auth_time`・`sid`。ポッドは JWKS の写し（P5、[ADR-0010](0010-shop-routing-hot-set-and-custom-domains.md)）で署名を確かめ、自分の DB の所属・ショップの状態・SSO の強制を確かめて、自社のアプリのオンラインのトークン（15 分）を出す。所属の変更は Valkey の写しを消して 60 秒以内に効かせる。
- 所属の一覧（`account_shops`）は、ポッドの outbox から `identity` へ写す（P4 の写し）。判定には使わない。
- 再確認（直近 5 分の 2 段階の認証）を、権限の変更・所有者の移転・ドメインと決済の設定・顧客の書き出し・アプリの導入と課金・閉店に要る。
- SSO：組織がドメインを DNS の TXT で確かめ、SAML 2.0 か OIDC（PKCE）の IdP を結ぶ。「SSO を必須」では、対象のアカウントはパスワードで入れない。所有者は非常の入口（パスワード＋2 段階の認証、使用を通知と監査）を持つ。JIT で既定の役割。SCIM は MVP の後。
- 協力者：パートナーの組織のメンバーが依頼し、事業者が承認して `kind = collaborator` の所属を作る。所有者だけの操作と、顧客の個人のデータの読み出し・書き出しは、事業者が明示に選ばない限り与えない。期限 180 日、未使用 90 日で外す。スタッフの数に数えない。

### 他の案を選ばなかった理由

- **2（`identity` が権限を持つ）**：ショップの権限が全体の面に移り、ショップのデータの境界（ADR-0002）がぼやける。権限の判定にポッドをまたぐ同期が要る。
- **3（ポッドごとのログイン）**：複数のショップに属する人が、ショップの数だけ認証の情報を持つ。移し替えでログインが壊れる。
- **b（任意）**：乗っ取りの影響が大きく、スタッフの 1 人の弱いパスワードがショップ全体の危険になる。

## Consequences

- 良くなること：
  - 権限の判定がポッドの DB の所属で閉じ、全体の面の写しの遅れで権限を広げない。
  - 協力者の範囲と期限を事業者が管理できる。
- 引き受けるコスト：
  - 管理のトークンの 10 分ごとの入場のやり直しの往復。
  - 2 段階の認証の喪失の回復の手順（人の確認）を持つ。
  - SAML の検証の実装は、汎用の部品（ライブラリ）の選定と、署名の包み替えの攻撃の試験が要る。

## Confirmation

- 表駆動テスト：DT-PERM-001 の 2・3・6 行（所属、SSO の強制、再確認）。
- 性質ベーステスト：PROP-STAFF-003（取り消しの 60 秒）。
- 結合テスト：期限切れ・他のショップの `aud`・再利用した入場の主張が拒まれる。SAML の署名の包み替え・`InResponseTo` の欠けが拒まれる。
- E2E：招待から入場、協力者の依頼と承認、SSO（模型の IdP）。
