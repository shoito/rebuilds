# ADR-0031: チェックアウトの入口に、ショップごとの同時実行のセマフォ（既定 50、隔離のポッド 500）と、作成の速さのトークンバケット（既定 1 ショップ 20 件/秒、セール中は待合室の受け入れの速さの 1.2 倍）を置く。超えたら 429 と `Retry-After` を返し、待合室を持つショップは待合室へ送る

## Context

- [ADR-0003](0003-tenancy-and-rls.md) は、ショップごとのチェックアウトの同時実行の上限（既定 50、隔離のポッド 500）と、作成の速さの上限を置くと決めた。速さの値と、超えたときの応答は決めていない。
- 待合室を通らない経路から来る要求も、ポッドに届く前に絞る必要がある（[architecture/README.md](../architecture/README.md) の 6 節）。
- 本家は、Storefront API で 1 分あたりのチェックアウトの作成を絞り、超えると `200 Throttled` を返す（[Storefront API](https://shopify.dev/docs/api/storefront)、2026-10-10 に確認）。

## Options

1. **同時実行のセマフォと作成の速さのバケットを、ショップごとに Valkey で持つ。Valkey の障害ではタスクの中の局所の値に落とす**
2. エッジの WAF の速さの上限だけで絞る
3. DB の接続の数の上限だけで絞る

## Decision

1 を採用する。詳細は [cart-and-checkout.md](../architecture/cart-and-checkout.md) の 9 節。

- セマフォ：送信と `completeCheckout` を含む、DB のトランザクションを持つ段の要求に掛ける。Valkey の有限の期限つきの数え上げ（30 秒で自動に戻る）。
- バケット：チェックアウトの作成に掛ける。既定 1 ショップ 20 件/秒・溜め 100。セールの `open` の間は、待合室の `rate_cap` の 1.2 倍。
- 超えたら 429 と `Retry-After`（1〜5 秒の揺らぎ）。待合室を持つショップは、待合室のページへの転送を返す。
- `completeCheckout` の Webhook と照合の経路は、セマフォを取らない別の上限（ポッドの照合の同時実行 20）で動く。買い手の要求の混雑で、決済済みのチェックアウトの完了が遅れない。
- Valkey の障害では、各タスクが `上限 ÷ タスクの数` の局所のセマフォに落ちる。

### 他の案を選ばなかった理由

- **2**：WAF の上限は IP の単位で、ショップの単位の同時実行を数えられない。
- **3**：接続の数で詰まると、他のショップの要求も待つ。

## Consequences

- 良くなること：1 つのショップの急増で、同じポッドの他のショップの DB の接続が尽きない。
- 引き受けるコスト：セールでない急増の始めに 429 を返す。自動の待合室（[ADR-0027](0027-flash-sale-preparation-and-surge-auto-queue.md)）が 30 秒で引き継ぐ。

## Confirmation

- 負荷試験：1 ショップに割り当ての 10 倍をかけ、他のショップの NFR-001 を満たす（[quality.md](../quality.md) の 2.2.1 節 H）。
- 結合テスト：Valkey を止めて、局所のセマフォに落ちる。
