# ADR-0036: 提供者の Webhook は inbox に入れて 200 を返し、処理のジョブは inbox を 1 秒ごとと SQS の合図で読む。結果が `processing` の試行は、5 秒・30 秒・2 分・5 分・10 分、その後 30 分ごとに 24 時間まで照会する。提供者と手段の組ごとに失敗の率で遮断器を持ち、開いたら最終確認の前の手段の一覧から隠す

## Context

- [ADR-0006](0006-payments-via-providers.md) は inbox を決めた。処理の速さと、照会の間隔は決めていない。
- 決済が済んで注文がない状態を 15 分以内に閉じる（NFR-006）。照合の処理は 1 分ごと（[ADR-0005](0005-checkout-state-machine-and-exactly-once-orders.md)）。
- 提供者の障害で、ある手段（例：キャリア決済）だけが失敗し続けることがある。買い手が失敗を繰り返すと、引き当てが長く残る。

## Options

1. **inbox を短い間隔で読み、照会は段階の間隔で行う。手段ごとの遮断器を持つ**
2. Webhook の受け口で、その場で `completeCheckout` を呼ぶ
3. 照会を一定の間隔（1 分）だけで行う

## Decision

1 を採用する。詳細は [payments-integration.md](../architecture/payments-integration.md) の 6・7 節。

- 受け口：URL のショップの ID とそのショップの秘密で署名を確かめ（[ADR-0003](0003-tenancy-and-rls.md)）、`payment_webhook_inbox` に（提供者、イベントの ID）の一意で入れ、200 を返す。重複は 200 を返して捨てる。本文は 64 KB まで。
- 処理のジョブ：outbox を経ずに SQS に合図を送り、合図がなくても 1 秒ごとに `processed_at IS NULL` の行を `FOR UPDATE SKIP LOCKED` で 100 行ずつ取る。照会（`getResult`）で結果を確かめ、`completeCheckout` などを呼ぶ。失敗は 1 分後に再試行。
- 照会の予定（`processing` と結果不明）：5 秒、30 秒、2 分、5 分、10 分、以後 30 分ごと。24 時間で `payment-order-mismatch` の呼び出し。
- 遮断器：（ショップ、提供者、手段）ごとに、直近 1 分の失敗（`failed` のうち提供者の障害の理由と、時間切れ）が 20 件以上かつ 50% 以上で開く。開いたら、その手段を手段の一覧から隠す。5 分後に半開きにし、試行の 10% だけ通す。
- 遮断器は、提供者の障害の理由のコードだけで数え、カードの拒否（残高の不足など）は数えない。

### 他の案を選ばなかった理由

- **2**：Webhook の受け口の応答が遅れ、提供者の再送が増える。受け口の障害で取りこぼす。
- **3**：多くの決済は数秒で結果が決まる。1 分の間隔は買い手の待ちを延ばす。

## Consequences

- 良くなること：Webhook の受け付けが軽い。結果の多くが 1 分以内に確定する。
- 引き受けるコスト：照会の要求が増える。提供者の照会の API の速さの上限を、提供者の選定で確かめる。

## Confirmation

- 性質ベーステスト：PROP-PAY-002（Webhook の重複・順序の入れ替えで、効果は 1 回）。
- 障害の注入：照会の API の時間切れが続く場面で、24 時間で呼び出しになり、その前に誤って失敗にしない。
