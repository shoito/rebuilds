# ADR-0019: 登録番号（`T`＋13 桁）は、形と検査の数字を確かめた後、国税庁の公表サイトの照会で事業者の名前と状態を確かめてから有効にする。月に 1 回確かめ直し、失効したら文書への記載を止めて事業者に知らせる

## Context

- 適格請求書には売手の登録番号を書く。誤った番号・失効した番号を出すと、買い手の仕入税額控除に影響しうる（扱いは法務の確認待ち L4）。
- 国税庁は適格請求書発行事業者の公表サイトを持ち、照会の Web-API がある（利用の条件と速さの上限は未検証）。
- 登録は取り消し・失効がありうる。

## Options

1. **形と検査の数字 → 公表サイトの照会 → 有効。月次で確かめ直す**
2. 形の検査だけで有効にする（事業者の責任）
3. 照会を文書の発行のたびに行う

## Decision

1 を採用する。詳細は [taxes-and-invoices.md](../architecture/taxes-and-invoices.md) の 7.5 節。

- 状態：`unverified` → `verified`・`rejected`、`verified` → `revoked`（月次）。
- 照会の名前とショップの文書の名前を NFKC と空白の除去で比べ、違えば事業者に確かめさせる。
- `verified` になるまで、文書に番号を出さず、適格でないレシートにする。
- 公表サイトの障害では `unverified` のまま 24 時間ごとに試す。発行済みの文書は変えない。

### 他の案を選ばなかった理由

- **2（形だけ）**：打ち間違い・他人の番号を見つけられない。
- **3（毎回）**：注文の数だけ外部に問い合わせ、外部の障害が文書の発行を止める。

## Consequences

- 良くなること：誤った番号の記載を減らせる。失効を 1 か月以内に見つけられる。
- 引き受けるコスト：外部の API の利用の条件に依る。条件が合わなければ、公表サイトの全件のデータの取り込みに替える（E4 で確かめる）。

## Confirmation

- 結合テスト：照会の模型で、一致・不一致・失効・障害の各場合の状態の遷移。
- 本番：`revoked` の件数と、知らせの送信を数える。
