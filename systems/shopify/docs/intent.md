# Intent: Shopify を AI エージェント主体で再構築する

- Author: shoito
- Status: draft（2026-10-10 に統合と検証を終えた。PM の受理を待つ）
- Date: 2026-10-10

## Problem

日本の中小の事業者が自分のネットショップを持ち、続けて売るには、次のところで困る。

- **作るのも続けるのも重い。** 商品の登録、在庫、決済、送料、税、配送、返品、法令の表示を、自前のサイトで全部そろえるのは重い。モールに出すと、顧客と見せ方を自分で持てない。
- **売れた瞬間に壊れる。** 限定品の発売やテレビの紹介で、数分に数万人が来る。サイトが落ちる、在庫より多く売れる（売り越し）、二重に注文が入る、決済だけ済んで注文がない、が起きる。売り越しは、謝罪と返金と信用の損失になる。
- **ボットに買い占められる。** 限定品は自動の購入のボットに先に買われ、転売される。本当のファンが買えない。
- **お金と税が合わない。** 日本の消費税は 10% と 8%（軽減税率）が混ざる。インボイス制度では、税率ごとに端数を処理した税額を書いた領収書が要る。割引・送料・返品が入ると、税額と按分が合わなくなる。
- **日本の買い方に合わない。** コンビニ払い、銀行振込、キャリア決済、配送の日時の指定、都道府県ごとの送料、特定商取引法の表示と最終確認画面への対応が要る。
- **拡張が危ない。** アプリやテーマで機能を足すと、他人のコードがチェックアウトで動く。遅いコードがチェックアウトを止め、悪いコードが買い手のデータを抜く。

本家 Shopify は、これらを大きな規模で解いている。ショップをポッドに分けた構成（[A Pods Architecture To Allow Shopify To Scale](https://shopify.engineering/a-pods-architecture-to-allow-shopify-to-scale)）、GraphQL の Admin API と費用による上限、WebAssembly で動く Functions、待合室とボット対策を持つ。2025 年の BFCM では、売上の最大が 1 分 510 万 USD、エッジの要求の最大が 1 分 4.89 億件だった（出典は末尾）。この題材では、日本の市場を最初の対象に、小さなチームと AI エージェントで、これをどこまで作り直せるかを確かめる。核（チェックアウト、在庫のエンジン、テーマの言語、関数の砂場、ポッドへの分け方）は自分で設計する（[リポジトリ共通の ADR-0007](../../../docs/decisions/0007-no-reuse-of-original-implementation.md)）。

## Proposed outcome

事業者が、数分でショップを開き、商品を並べ、日本の買い手に売り、配送と返品までを 1 か所で回せる EC の基盤を作る。次の 6 つの価値を満たす。

1. **売り越さない**：「在庫切れで売らない」品目は、どんな並行度でも、確定した数が在庫を超えない（NFR-004）。
2. **注文はちょうど 1 回**：1 つのチェックアウトから注文は 1 つだけできる。決済が済んだのに注文がない状態は、15 分以内に必ず解消する（NFR-006）。
3. **売れた瞬間に落ちない**：1 つのショップに 1 秒 100 件の注文（S1）が来ても、チェックアウトの p99 を守り、同じポッドの他のショップの SLO を消費しない（NFR-002、NFR-008）。
4. **速いストアフロント**：キャッシュに当たれば TTFB p95 80ms、外れても p95 500ms（NFR-003）。商品の更新は p95 10 秒で表示に出る（NFR-011）。
5. **お金と税が合う**：税額・割引の按分・返金の額が、参照の計算と 1 円も違わない（NFR-013）。
6. **安全に拡張できる**：アプリの関数とテーマは上限の中でしか動かず、チェックアウトを止められず、許可した範囲のデータしか読めない（NFR-012）。

### MVP（S1）に含める

- **ショップと管理**：ショップの開設、プラン、ドメイン（既定のドメインと独自のドメイン、TLS の自動の発行）、スタッフと権限、監査ログ、管理画面（Web）
- **カタログ**：商品、バリエーション（オプション 3 つまで）、コレクション（手動と条件）、メディア（画像、動画）、メタフィールド、販売の公開の設定、CSV の取り込みと書き出し
- **価格と通貨**：税込みの価格（日本の総額表示）、比較の価格（通常の価格）、ショップの基本の通貨（JPY）、表示と支払いの通貨の仕組み（マーケットごとの固定の価格か換算と丸めの規則）。**仮の決定（2026-10-10、PM の判断待ち）**：外貨のマーケットは海外への販売を伴い、越境の税（法務の L4）と E22 の設計が要る。MVP では仕組みを作って試験し、外貨のマーケットの有効化は `release.markets-foreign-currency` の裏に置く。MVP で買い手が使える通貨は JPY だけ（[architecture/README.md](architecture/README.md) の 6 節の「決定（2026-10-10、統合）」）
- **税**：消費税の標準税率（10%）と軽減税率（8%）、品目ごとの税の区分、税率ごとの端数処理、適格簡易請求書（レシート）の発行、適格請求書発行事業者の登録番号の表示
- **在庫**：拠点（倉庫、店舗）、拠点ごとの在庫の数と状態、「売り越さない」と「在庫切れでも売る」の設定、引き当てと確定、移動と調整の履歴
- **フラッシュセール**：セールの予定の登録、待合室、購入の許可証、ボット対策（チャレンジ、速さの上限、1 人あたりの数の上限）、熱い品目の在庫の枠の分割
- **カートとチェックアウト**：カート、チェックアウト（1 ページ）、配送先、配送の方法と送料（都道府県ごと、重さ・サイズ、無料の閾値）、配送の日時の指定、割引のコード、自動の割引、最終確認画面
- **割引**：金額・率・送料無料・まとめ買い（Buy X Get Y）、対象（商品、コレクション、注文の全体）、組み合わせの規則、使用の回数の上限、期間
- **決済**：外部の決済の提供者の連携（リダイレクト、提供者のホストした入力部品）、オーソリと売上の確定、取り消しと返金、提供者の Webhook。日本の決済手段（カード、コンビニ払い、銀行振込、キャリア決済、後払い）は提供者を通す
- **注文と配送**：注文、配送の指示（fulfillment order）、配送と追跡の番号、運送会社（ヤマト運輸・佐川急便・日本郵便）の送り状の CSV と、選んだ 1 社の API の連携、キャンセル
- **返品と返金**：返品の受け付け、返金（全額・一部・送料）、在庫への戻し、返金の税の扱い（返還インボイス）
- **ストアフロント**：自前のテーマの言語とレンダラー、既定のテーマ 2 つ、テーマの編集（セクションとブロック）、エッジのキャッシュと無効化、Storefront API（GraphQL、ヘッドレス）、SEO（サイトマップ、構造化データ、正規の URL、リダイレクト）
- **検索とおすすめ**：商品の検索（日本語）、絞り込み、並べ替え、予測の検索、関連の商品（基本）
- **アプリの基盤**：アプリの登録、OAuth 2.0 とスコープ、Admin API（GraphQL、費用による上限、一括の操作）、Webhook、管理画面への埋め込み、関数（割引・送料・決済の手段の並べ替え・カートの検証）、アプリの課金（定額と従量）
- **通知**：買い手へのメール（注文の確認、発送、返金）、事業者への通知

### MVP の後の Epic で扱う

| 機能 | 理由 |
| --- | --- |
| ギフトカード、ストアクレジット、ポイント | 前払式支払手段として資金決済法の扱いを、法務の L5 で確かめてから設計する |
| 定期購入（サブスクリプション） | 特定商取引法の定期購入の表示の規則（法務の L1）と、繰り返しの決済の設計が要る |
| 実店舗の POS | 端末と、店舗の在庫の即時の同期の設計が要る |
| 海外への販売（越境）、外貨のマーケットの有効化、海外のリージョン | 関税、海外の税（法務の L4）、データの所在（法務の L3）の設計が要る。外貨のマーケットの仕組みは MVP で作り、フラグの裏に置く |
| B2B（卸の価格、掛け売り） | 価格の表と与信の設計が要る |
| モール・SNS などの販売のチャネルの連携 | チャネルごとの在庫の配り方の設計が要る |
| 機械学習のおすすめ | MVP は共起と人気の基本のおすすめ |

### 守るべき振る舞い

- 「売り越さない」品目で、確定した数（注文に入った数）が、拠点の手元の数を超えない。待合室・キャッシュ・Valkey が壊れても超えない。
- 1 つのチェックアウトから作られる注文は 0 か 1。決済の Webhook とリダイレクトの戻りが同時に来ても 1。
- 決済の売上を確定した買い手は、必ず注文を持つか、全額の返金を受ける。どちらでもない状態が 15 分を超えて続かない。
- 最終確認画面に出した金額（商品、送料、手数料、割引、税、合計）と、注文に記録した金額と、決済の金額が一致する。
- 1 つの注文の税額は、税率ごとに対価の合計から計算し、税率ごとに 1 回だけ丸める。
- 同じカートと同じ割引の集まりからは、何度計算しても同じ割引の結果になる。
- 事業者・スタッフ・アプリは、自分のショップの、許された範囲のデータだけを見られる。エッジのキャッシュ・検索・Webhook を含め、どの経路でも他のショップのデータが出ない。
- テーマとアプリの関数は、決めた上限（歩数・燃料・メモリー・出力）を超えて動かない。超えたら決めた「効果なし」の結果になり、チェックアウトは続く。
- 価格・在庫の表示が変わってから、ストアフロントに古い価格が出続けない（p99 60 秒以内に新しい価格）。チェックアウトでは常に最新の価格で計算する。

### 成功の基準

| # | 基準 | 目標 | 測り方 |
| --- | --- | --- | --- |
| K1 | 売り越し | 「売り越さない」品目の売り越し 0 件（NFR-004） | 在庫の照合（確定の数と手元の数）、性質ベーステスト |
| K2 | 注文の一回性 | 重複の注文 0 件。決済済みで注文のない状態が 15 分を超えた件数 0（NFR-006） | 決済と注文の照合 |
| K3 | チェックアウトの速さ | 確定の要求 p99 1.5 秒（提供者の時間を除く）、その他の段 p99 500ms（NFR-001） | サーバーの計測 |
| K4 | フラッシュセール | 1 ショップ 100 件/秒、全体 200 件/秒の注文を S1 で処理する。その間、他のショップの SLO を満たす（NFR-002、NFR-008） | 負荷試験、本番の指標 |
| K5 | ストアフロント | TTFB：キャッシュに当たれば p95 80ms、外れれば p95 500ms（NFR-003） | 合成監視、実ユーザーの計測 |
| K6 | 金額の正しさ | 税額・割引の按分・返金の額の、参照の計算との差 0 円（NFR-013） | 性質ベーステスト、本番の抜き取りの再計算 |
| K7 | 可用性 | チェックアウトとストアフロント 月間 99.95%、管理画面と Admin API 月間 99.9%（NFR-007） | 合成監視、5xx の割合 |
| K8 | 分離 | 他のショップのデータが出た事象 0 件（NFR-008） | 性質ベーステスト、応答の監査 |
| K9 | 拡張の安全 | 砂場の外への到達 0 件。関数の上限の超過でのチェックアウトの失敗 0 件（NFR-012） | 脱出の試験、本番の指標 |
| K10 | 開店の速さ | 新しいショップが、登録から最初の商品の公開まで 10 分以内（中央値） | 製品の計測 |

## Affected users and systems

- **事業者（ショップの持ち主）**：日本の中小の事業者、D2C のブランド、アーティストやメーカーの直販。限定品の発売をする事業者を含む。
- **スタッフ**：ショップの中の担当者（商品の登録、注文の処理、配送、問い合わせ）。持ち主が権限を与える。
- **買い手**：日本の消費者。スマートフォンが中心。会員の登録をせずに買う人が多い。
- **アプリの開発者**：アプリとテーマを作り、事業者に配る外部の開発者。Admin API・Webhook・関数・Storefront API を使う。
- **ヘッドレスの開発者**：自前のフロントエンドから Storefront API を使う、事業者の開発者。
- **社内の運用**：サポート、不正の対応、フラッシュセールの運用、法令の照会への対応。
- **外部のシステム**：決済の提供者（カード、コンビニ払い、銀行振込、キャリア決済、後払い）、運送会社（ヤマト運輸、佐川急便、日本郵便）、メールの送信、DNS と TLS の証明書、検索のエンジン（Google など）のクローラー。

## Constraints

- **核を自前で設計する。** チェックアウト、在庫のエンジン、テーマの言語、関数の砂場の設計、ポッドへの分け方は自分で作る。本家の Liquid の実装、本家の SDK・CLI・テーマ・内部の形式を使わない。WebAssembly の実行系（Wasmtime）、GraphQL の参照の実装、検索のエンジンは、核の外の汎用の部品として、理由を ADR に書いて使う（[リポジトリ共通の ADR-0007](../../../docs/decisions/0007-no-reuse-of-original-implementation.md)、[ADR-0001](decisions/0001-platform-and-stack.md)、[ADR-0008](decisions/0008-extension-sandbox-wasm.md)）。
- 実行基盤と技術は、rebuilds の他の題材の決定（AWS 東京・大阪、TypeScript・Hono、Aurora PostgreSQL、Valkey、S3、SQS・SNS、ECS Fargate、Terraform、OpenTelemetry、AppConfig のフラグ、FORCE RLS と `SET LOCAL`、UUIDv7、outbox）を引き継ぐ。外れるところ（関数の砂場のホストを Rust で書くこと、検索のエンジン）は ADR に理由を書く。
- **カード処理を設計し直さない。** カード情報の保管、アクワイアラへの接続、台帳は、Stripe の題材の論点である。この題材は、決済の提供者（Stripe の題材の再構築したもの、日本の決済代行など）の API を使う側として設計する（[ADR-0006](decisions/0006-payments-via-providers.md)）。
- 本家の名前は識別子に使わない。ドメインは `<brand>.<domain>`、ヘッダーは `X-<Brand>-Access-Token`、トークンの接頭辞は `<brand>_at_` の形で書く（[リポジトリ共通の ADR-0006](../../../docs/decisions/0006-brand-neutral-identifiers.md)）。本家の API・テーマ・アプリとそのまま互換にすることは目標にしない。
- データは日本（東京、DR は大阪）に置く。
- 日本の法令への対応は、法務の確認を前提に設計する。結論は出さない（下の「法務の確認待ち」）。
- 規模は段階的に広げる（[architecture/](architecture/README.md) の 2 節）。

## Non-goals

| 機能 | 理由 |
| --- | --- |
| カード情報の保管、アクワイアラへの直接の接続、自前の決済の台帳 | Stripe の題材の論点。提供者を通す（[ADR-0006](decisions/0006-payments-via-providers.md)） |
| 本家の API・テーマ・Liquid の文法・アプリとの完全な互換 | 振る舞いは寄せるが、名前と言語は独自にする（リポジトリ共通の ADR-0006、[ADR-0007](decisions/0007-theme-language-design.md)） |
| テーマやアプリに任意のサーバーのコード（JavaScript など）を本システムの中で動かさせること | 安全の上限を守れない。関数は WebAssembly の砂場で、決めた入口だけ（[ADR-0008](decisions/0008-extension-sandbox-wasm.md)） |
| 自前の物流（倉庫の運営） | 運送会社と外部の倉庫の連携までにする |
| 事業者の会計・在庫の管理のソフトの代わり | 書き出しと API で連携する |
| オンプレミスでの提供 | 運用の形が別になる |

## Open questions

### 法務の確認待ち

### 選定・計測で決めるもの（法務以外）

- 熱い品目の在庫の枠の数と、Aurora の 1 行・1 枠あたりの更新の上限：E5 の前の `inventory-hot-row-poc`（[ADR-0004](decisions/0004-inventory-reservation-model.md)）。
- ショップの移し替えの書き込みの停止の時間（目標 10 秒以内）と、論理デコードでショップの変更を拾う方法：E2 の前の `shop-move-poc`（[ADR-0002](decisions/0002-pods-and-shop-placement.md)）。
- テーマのレンダラーの速さ（1 ページあたりの CPU の時間、歩数の上限の値）：E11 の前の `theme-renderer-poc`（[ADR-0007](decisions/0007-theme-language-design.md)）。
- 関数の実体化と実行の時間、燃料の上限の値：E15 の前の `wasm-function-poc`（[ADR-0008](decisions/0008-extension-sandbox-wasm.md)）。
- エッジのキャッシュの世代の番号と熱い集まりを CloudFront KeyValueStore で配るときの、伝わるまでの時間：E12 の前の `edge-cache-generation-poc`（[ADR-0010](decisions/0010-shop-routing-hot-set-and-custom-domains.md)、[ADR-0050](decisions/0050-edge-cache-keys-and-generations.md)）。
- 決済の提供者、運送会社の API、ボット対策のチャレンジの提供者の選定：各 Epic の選定の Story。候補の名前は例で、能力は未確認である。
- 本家の振る舞いのうち、チェックアウトで在庫を引き当てる時点、関数の失敗のときのチェックアウトの振る舞い、待合室の並びの規則、Webhook の再送の間隔は、公式の資料で確かめられなかった（**未検証**）。本システムの値を使う。

- Shopify Engineering, [A Pods Architecture To Allow Shopify To Scale](https://shopify.engineering/a-pods-architecture-to-allow-shopify-to-scale)（2018-03-02）：ポッドは、完全に分けたデータストアの上のショップの集まり。アプリのサーバー・ジョブの実行・ロードバランサーは共有し、1 つの要求・ジョブは 1 つのポッドだけに触れる。ロードバランサーの Sorting Hat が規則で要求をポッドに振る。ポッドは 2 つのデータセンター（稼働と復旧）を持ち、Pod Mover で 1 分ほどで移せる
