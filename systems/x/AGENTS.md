## この題材に固有の規則（開発リポジトリで守る）

### 本家の実装と名前

- **タイムライン・推薦・カウンター・検索の核を自前で作る。** 本家が公開したアルゴリズムのコード（`twitter/the-algorithm`（AGPL-3.0）、`xai-org/x-algorithm`（Apache-2.0））、本家の文字数の数え方のライブラリ（`twitter-text`）、本家の ID の生成器（Snowflake）を、核にも依存にも使わない。コードの写し、設定の値（重み・閾値）、学習済みのモデルの重みも持ち込まない。考え方を読むのはよいが、設計の文書に「本家の公開の資料による」と出典を書く（[リポジトリ共通の ADR-0007](../../docs/decisions/0007-no-reuse-of-original-implementation.md)、ADR-0001）。
- **本家の名前を識別子に使わない。** ドメイン（`<brand>.<domain>`）、短縮 URL のドメイン、HTTP ヘッダー、API のパス、トークンの接頭辞（`<brand>_`）、アプリのバンドル ID、URL のスキームは `<Brand>`・`<brand>` で書く。投稿・リポスト・フォローのような一般の語はそのまま使ってよい（[リポジトリ共通の ADR-0006](../../docs/decisions/0006-brand-neutral-identifiers.md)）。

### 投稿とタイムライン

- **投稿の ID は `packages/tid` だけで振る。** 時刻の順に並ぶ 64 ビットの ID（ADR-0002）。DB の連番、UUIDv7、乱数で投稿・利用者・DM のメッセージの ID を作らない。時計が戻ったら、ID を振らずに待つか失敗させる。生成器の番号は貸し出しで得て、リージョンごとに範囲を分ける。
- **ID は API と JSON では文字列で返す。** JavaScript の `number` に 64 ビットの ID を入れない（53 ビットを超えると壊れる）。TypeScript の中では `bigint` か、ブランド型の文字列で扱う。
- **タイムラインの写しは正本にしない。** Valkey のホームのタイムラインは、投稿とフォローの表から作り直せる写しである。写しにしかない状態を作らない。写しが消えても、作り直しで同じ結果になる（ADR-0003）。
- **見える範囲は読み出しの時に 1 つの関数で決める。** ブロック・ミュート・鍵アカウント・削除・法的な措置・モデレーションの制限は、`packages/visibility` の `visible(viewer, post)` で判定する。`viewer` は読み出しの面（`surface`）を持ち、面で変わるのはミュートの当て方と警告の出し方だけにする。fan-out の時に決めた結果を、読み出しの時の判定の代わりにしない。タイムライン・検索・通知・API・埋め込み・メディアの配信のどの経路でも、この関数を通らない読み出しを作らない（ADR-0004）。
- **fan-out の方式の閾値（フォロワーの数）を、コードに書かない。** AppConfig の `ops.fanout.*` で持ち、変えたら記録を残す。閾値をまたいだ利用者の扱いは、プッシュとプルの両方の結果を合わせて重ならないことを、性質ベーステストで確かめる（ADR-0003）。

### カウンターと出来事

- **数は正本の関係から数え直せる形にする。** いいね・リポスト・フォローの数は、関係の表（`likes`・`reposts`・`following`・`followers`）が正本で、表示の数はその写しである。写しを直接 `UPDATE` で書き換えない。照合のジョブで、写しと正本の差を測る（ADR-0005、ADR-0023）。
- **出来事は outbox から流す。** 投稿・フォロー・いいねなどの確定した変更は、同じ DB のトランザクションで outbox に書き、Relay がイベントのログ（Kinesis Data Streams）へ流す。アプリから直接イベントのログへ書いて、DB と食い違う経路を作らない。例外は表示の数（閲覧）の取り込みだけで、これは失ってよい出来事として別の口から入れる（ADR-0005）。
- **出来事の消費者は冪等にする。** 同じ出来事を 2 回以上受けても、結果が変わらないようにする。出来事の ID で重複を落とす。

### ランキングと推薦

- **ML の出力は「並べる順」だけに使う。** 見える範囲の判定、法的な措置、ブロック・ミュート、年齢の制限を、モデルのスコアで上書きしない。安全のための固い絞り込みは、スコアの後に必ず通す（ADR-0006）。
- **ランキングの部品は、決まった口の後ろに置く。** 候補の取り出し・特徴の付加・スコア・絞り込み・混ぜ合わせを、`packages/ranking` の型の口で分ける。スコアの部品が落ちたり遅れたりしたら、時刻の順の並びに戻す。
- **ランキングの変更は、オフラインの評価と A/B を通す。** 重み・特徴・モデルの入れ替えは、記録した出来事での再生の評価を CI に置き、本番では `experiment.ranking.*` のフラグで割合を広げる。人の目で決めた重みも同じ扱いにする。
- **推薦の理由を残す。** 「おすすめ」に出した投稿ごとに、どの候補の源から来たか、理由のコードを記録し、利用者に示せるようにする。

### トラスト＆セーフティと法令

- **措置は記録してから効かせる。** 削除・表示の制限・アカウントの凍結は、`moderation_actions` に、根拠（規約の条項か、法令の申出）と判断した人（または規則）を書いてから効かせる。措置は取り消せる形で持ち、物理の削除は保持の期間の後のジョブだけが行う。
- **法令の申出の期限を、仕組みで守る。** 削除の申出（情報流通プラットフォーム対処法）には、受け付けた時刻から期限を計算して持ち、期限の前に警告を出す。期限の値は法務の確認の後に決める（[intent.md](docs/intent.md) の L1）。
- **発信者情報の開示に使うログを、勝手に消さない・増やさない。** 投稿・ログインの時の IP アドレス・時刻などの保存の期間と範囲は、法務の確認（L2）で決めた値だけにする。調査のために保存を延ばすときは、保全の手順を通す。
- **DM の中身を、モデレーションや推薦の特徴に使わない。** DM は通信の秘密に当たりうる（L3）。スパムの判定で DM の中身を機械で読むかは、法務の確認が済むまで実装しない。DM の中身を、ログ・メトリクス・トレース・分析の出力に書かない。

### テストのデータ

- **テストに本物の投稿・利用者を使わない。** 本家の投稿・利用者名・メディア、実在の人の名前・電話番号・メールアドレスを、テスト・フィクスチャー・シード・負荷試験に入れない。日本語の本文は合成する（生成器と、権利の問題のない文の集まり）。
- **有害なメディアの検出の試験に、本物の有害なメディアを使わない。** 試験は、ハッシュの照合の仕組みが提供する試験用のハッシュと、合成の画像で行う。

## このリポジトリでの規則

- ADR を追加・更新したら、`docs/decisions/README.md` の一覧を生成し直す。
- 領域の文書で ADR を起票するときは、[architecture/README.md](docs/architecture/README.md) の 7 節で領域に割り当てた番号の範囲の中で採番する。
- 本家の振る舞い・数値を書くときは、出典と確認日を付ける。確かめられないものは「未検証」と書く。本家の公開のアルゴリズムの説明は、公式の資料（ブログ、公開のリポジトリの README）と、第三者の解説を分けて書く。
- 法令の解釈は結論を出さず、[intent.md](docs/intent.md) の「法務の確認待ち」に載せる。
- フラグと設定の名前空間を次に限る（[architecture/README.md](docs/architecture/README.md) の 6 節の統合の決定）。振る舞いを切り替えるフラグは `release.*`（未完成・法務の確認待ちの振る舞いを隠す）・`ops.*`（運用の止め・絞り・閾値）・`experiment.*`（A/B。ランキングは `experiment.ranking.*`）。決めた値の設定は `policy.*`（製品の規則）・`retention.*`（保持）・`legal.*`（法令の期限と基準の値）・`ts.*`（T&S の閾値）。
