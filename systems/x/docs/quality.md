# Quality: X

QA が持つ品質戦略。変更ごとのテスト設計は、各変更の `spec.md`（シナリオ・決定表・性質）と `plan.md`（Proof）に書く。

この題材で最も危ないのは、壊れたときに **エラーにならずに、見てはいけない投稿が誰かの画面に出る・届くはずの投稿が届かない・数が正本とずれたまま残る・法令の期限を過ぎる** ことである。どれも、写し・非同期の消費者・読み出しの時の判定の組み合わせの中で、特定の順序や量でしか起きない。QA の仕事は他の題材と同じく次の 3 つだが、重心は **全経路で `visible()` が効くことと、写しが正本から作り直せることを、性質と漏れの経路の表で先に決めること** に置く。

1. **何をもって正しいとするかを先に決める**（シフトレフト：見える範囲の決定表、漏れの経路の表、fan-out とカウンターの性質、ランキングのガードレール）
2. **エージェントが自分で検証できる仕組みを整える**（合成のソーシャルグラフ、fan-out の模擬、出来事の再生、ランキングのオフラインの評価、確認ループ、eval）
3. **本番で正しさを確かめ続ける**（見える範囲の抜き取りの監査、カウンターの照合、届くまでの合成監視、T&S の期限の監視）

## 1. 品質目標とリスク

intent の成功の基準（K1〜K8）と非機能要件（[architecture/README.md](architecture/README.md) の 3 節、NFR-001〜013）を品質の目標にする。リスクの順位は、影響（利用者の安全・法令・信頼）と、エラーにならずに残る度合いで付けた。

| 順位 | リスク | 影響 | 主な対策 |
| --- | --- | --- | --- |
| 1 | 見える範囲の漏れ（鍵アカウント・ブロック・削除・措置の投稿が、写し・検索・通知・API・メディア・埋め込みのどれかから出る。DM が他人に見える） | 利用者の安全と信頼。法令の措置の不履行（NFR-009、K3） | `visible()` の 1 つの関数（ADR-0004）、決定表、漏れの経路の表（2.2.1 節）、`Visible<Post>` の型、本番の抜き取りの監査 |
| 2 | 法令の期限の超過（削除の申出、開示の請求、命に関わる通報） | 法令の違反、被害の拡大（NFR-010、K6） | 期限を案件に持つ、期限の前の警告、期限の監視の合成の案件、手順の訓練 |
| 3 | 届かない・遅れる（fan-out の詰まり、閾値の付近の重複や抜け、写しの喪失の後の作り直しの殺到） | 「すぐ届く」という価値を失う。災害の時の情報の遅れ（NFR-002・003、K1・K2） | fan-out の性質ベーステスト、瞬間のピークの負荷試験、合成監視の組、作り直しの single flight |
| 4 | スパムとボットの浸入（登録・API・自動の投稿、おすすめへの入り込み） | ホームとトレンドの質の低下、詐欺の被害（NFR-011、K7） | 登録の確認、レート制限、T&S の規則と分類、ランキングのガードレール、週ごとの抜き取りの評価 |
| 5 | カウンターのずれ（取りこぼし、二重の加算、写しの喪失） | 数への信頼（NFR-006、K4） | 冪等の消費者（ADR-0005）、照合のジョブ、出来事の再生の試験 |
| 6 | ランキングの暴走（重み・モデルの変更で、煽り・スパム・偏りが増える） | 体験と安全の悪化（K8） | オフラインの評価の CI、A/B、ガードレールの指標（ADR-0006） |
| 7 | ID の衝突・順序の誤り（生成器の貸し出し、時計の戻り、新着の読み出しの窓） | 投稿の上書き、タイムラインの抜け | 生成器の性質ベーステスト、主キーの重複の監視（ADR-0002） |
| 8 | 日本語の扱い（文字数の数え方、検索の取りこぼし、正規化の食い違い） | 投稿できない・見つからない | 文字数の例の集まり（クライアントとサーバーで同じ）、検索の日本語の例示テスト |
| 9 | DR での写しと出来事の扱い（写しが空になる、失った範囲の出来事） | 切り替えの後の読み出しの遅れ、数のずれ（NFR-005） | DR の訓練の合格基準（2.4 節）、写しの作り直しの負荷試験 |

## 2. シフトレフト

### 2.1 仕様レビューの関門

QA は Design 段の承認者として、各変更の `spec.md` を次の観点でレビューする。承認がなければ Build 段に進まない。

- [ ] すべての要件に ID があり、EARS の形で書かれている。正常系と、拒否・障害の側のシナリオがある
- [ ] **投稿・プロフィール・メディア・DM を返す経路を足す要件は、漏れの経路の表（2.2.1 節）に行を足すか、既存の行を指している**。5 つの主体（ブロックされた人、鍵アカウントの承認のない人、ログインしていない人、措置の対象の地域の人、削除の直後の人）のシナリオがある
- [ ] **見える範囲の規則を変える要件は、`visible()` の決定表（`DT-...`）の差分で書かれている**
- [ ] **写し（タイムライン、カウンター、閲覧者の集合）に触れる要件は、写しを失ったときと、作り直したときのシナリオを持つ**。写しにしかない状態を作っていない
- [ ] **出来事を消費する要件は、重複・順の入れ替え・遅れのシナリオと、冪等の性質（`PROP-...`）を持つ**
- [ ] **fan-out に触れる要件は、閾値をまたぐ作者と、プッシュ・プルの両方の経路の性質を持つ**
- [ ] **ランキングの変更は、オフラインの評価の指標とガードレールの値が書かれている**。ML の点で見える範囲を変えていない
- [ ] **T&S の措置・申出の要件は、根拠の記録、期限、取り消し、利用者への通知のシナリオを持つ**
- [ ] 新しい本人だけの表は、`owner_id` と FORCE RLS を持つ（[ADR-0004](decisions/0004-single-tenant-and-visibility.md)）
- [ ] 利用者の書いた中身（投稿・DM の本文、検索の語）、電話番号、メールアドレス、IP アドレスを、ログ・メトリクス・トレースに出さないことが書かれている
- [ ] 非機能要件（NFR）への影響が、実装を見ずに判定できる具体的な値で書かれている
- [ ] 本家と振る舞いを違えるときは、違いと理由が書かれている。識別子に本家の名前を使っていない（`<brand>`。リポジトリ共通の ADR-0006）
- [ ] 変更単位の `quality.md` が要るか。この節のリスク 1〜3 位（漏れ、法令の期限、届かない）に触れる変更、新しい種類のテスト基盤が要る変更、規模が「大」の変更では必要
- [ ] [intent.md](intent.md) の「法務の確認待ち」（L1〜L11）に当たる Story の spec ではないか（当たるなら承認しない。[roadmap.md](roadmap.md) の「法務：L*」）

`plan.md` の Proof も QA がレビューし、各要件・性質・決定表の行・漏れの経路の行を証明する手段があることを確かめる。

| 性質ベース | `PROP-...`：fan-out の結果、カウンターの冪等、ID の重なりなし、見える範囲、フォローの 2 つの表 | fast-check | PR（短縮版）、夜間（完全版） |

| E2E | 登録、投稿、フォロー、ホームに出る、ブロックで消える、DM、通報 | Playwright（Web）、Maestro（iOS・Android） | PR（主要）、夜間（全件） |
| アプリの版の互換 | 支える最も古いアプリの版（12 週前の列車）と今のサーバーの E2E（[delivery.md](architecture/delivery.md) の 2.2 節） | Maestro | 夜間 |
| 負荷 | 投稿・読み出し・fan-out・閲覧・瞬間のピーク（[capacity.md](architecture/capacity.md) の 8 節の L1〜L10） | k6、自前の fan-out の負荷の生成 | E14、半年ごと、fan-out の大きな変更の後 |
| 描画の滑らかさ | ホームの 200 件のスクロールの落ちたフレーム（[clients.md](architecture/clients.md) の 5.2 節） | 固定の実機 | 一覧の画面に触れる PR |
| 障害の注入 | Valkey のノードの喪失、Kinesis のシャードの遅れ、Aurora のフェイルオーバー、Fanout Worker の停止 | AWS FIS | 夜間（staging）、E14 |
| アクセシビリティ | WCAG 2.2 AA、画像の代替のテキスト | `@axe-core/playwright`、VoiceOver・TalkBack の手動 | PR（axe）、リリースの前（手動） |
| セキュリティ | SAST、依存・イメージ・IaC、DAST、外部のペンテスト | 各種 | PR、夜間、E14 |

モックは外部の相手（APNs・FCM、メール・SMS の送信、ハッシュの照合の提供者）に限る。DB、Valkey、OpenSearch、S3 をモックにしない。

#### 2.2.1 漏れの経路の表

見える範囲を判定するべき経路の一覧。各行に、5 つの主体（2.1 節）の結合テストを付ける。行は、経路を足す Story が足す。

| 経路 | 判定の場所 | 確かめること |
| --- | --- | --- |
| ホーム（フォロー中） | Timeline の読み出し | 写しに残った項目を、ブロック・削除・措置・フォロー解除の後に返さない。閲覧者の集合の写しの更新が失敗しても、修復の後（遅れが 30 秒を超えたら劣化の運転）に返さない（[follow-graph.md](architecture/follow-graph.md) の 6 節） |
| ホーム（おすすめ） | Ranking の 2・5 段目 | 点にかかわらず、`hide` の投稿を返さない。`interstitial` も落とす |
| ホーム（おすすめ）の続きのページ | Ranking（`rk:` の並びから返す前の `visible()`） | 最初のページを並べた後のブロック・削除・措置の投稿を返さない（[ranking-and-recommendation.md](architecture/ranking-and-recommendation.md) の 4.2 節） |
| プロフィールの投稿の一覧 | Timeline | 鍵アカウントの承認のない人とログインしていない人に返さない |
| 会話（返信の一覧） | Timeline | ブロックした・された人の返信を返さない。閲覧者の集合の更新の失敗の後も同じ |
| 検索・ハッシュタグ・トレンドの例 | Search | 索引の更新の遅れの間も返さない（返す前の `visible()`） |
| 通知 | Notification | 作る時・送る時・読む時に判定し直す。作った後、送る前にブロック・措置されたら、プッシュを送らず一覧に出さない（[notifications.md](architecture/notifications.md) の 6.2 節） |
| 公開 API | Public API | 画面と同じ判定。アプリの権限で範囲を広げない。アプリのトークンはログインしていない人として判定する |
| 埋め込み・リンクのカード | App API | ログインしていない人として判定する |
| メディアの配信 | Media、CDN | 削除・措置から 60 秒で配信を止める。鍵アカウントのメディアの URL の期限 |
| DM の中の投稿の共有 | DM | 受け手として判定する |
| データの書き出し | Accounts | 本人のデータだけ |
| 削除の直後 | Post、全経路 | 削除の直後に `ps:` の書き込みが失敗し、Relay も止まっても、60 秒以内に全経路で見えない（`ps:` の寿命 45 秒。[posts-and-ids.md](architecture/posts-and-ids.md) の 6 節） |
| アカウントの停止・凍結の直後 | Accounts、全経路 | 停止・凍結の後、全経路でその人の投稿とプロフィールを返さない（鍵の切り替えと同じ扱い。[accounts-and-auth.md](architecture/accounts-and-auth.md) の 8.1 節） |
| クライアントの手元の写し | クライアント（[clients.md](architecture/clients.md) の 4.4 節の消す規則） | ブロック・削除の後、オンラインの端末で 60 秒以内に画面から消える |
| 運用者・T&S のコンソール | T&S（理由の必須と範囲。[security.md](architecture/security.md) の 6.3 節） | 案件の外の対象を読めない。案件の ID のない読み出しは失敗する |

### 2.3 エージェントの確認ループ

Claude は PR を出す前に、次を自分で実行し、すべて通ることを確かめる。コマンドは開発リポジトリの `AGENTS.md` の Commands に書く。

1. 型検査と lint（`visible()` を通らない応答、ID の `number`、閾値の直書き、書き込みのサービスからの Kinesis の直接の書き込み、ログへの中身、本家の名前の識別子）
2. 変更箇所に関わる単体・表駆動・性質・結合テスト
3. **読み出しの経路に触れたら、漏れの経路の表の該当の行の結合テスト**
4. **出来事の消費者に触れたら、出来事の再生の試験**
5. **fan-out・タイムラインに触れたら、fan-out の性質ベーステストの完全版**
6. **ランキングに触れたら、オフラインの評価と前の版との比較**
7. マイグレーションに触れたら、本人だけの表の RLS の検査
8. 要件 ID の追跡検査（`plan.md` の ID がすべてテストから参照されている）
9. 画面の変更なら、スクリーンショットと axe

完了基準は、`plan.md` の Proof の表がすべて満たされていること。**テストの削除・skip・期待値の緩和、漏れの経路の行の外し、ガードレールの値の緩和で通したことにしない。**

### 2.4 テスト環境、テストデータ、DR の訓練の合格基準

- ローカルと CI は同じ構成にする（PostgreSQL、Valkey、OpenSearch、LocalStack の Kinesis・SQS・S3）。
- **合成のソーシャルグラフ**：利用者 100 万、辺 2,000 万、フォロワーの数はべき乗の分布（最大 100 万）、鍵アカウント 10%、ブロックとミュートの辺。日本語の投稿の本文は、生成器と権利の問題のない文の集まりから作る。版を固定して開発リポジトリに置く。本番のデータは使わない。
- **合成の出来事の列**：投稿・フォロー・いいね・閲覧・措置の列（瞬間のピークの形を含む）。出来事の再生と、ランキングのオフラインの評価に使う。
- **T&S の試験**：本物の有害なメディアを使わない。ハッシュの照合の提供者の試験用のハッシュと、合成の画像を使う。
- 負荷試験・DR の訓練は staging で行う。

**DR の訓練の合格基準**（頻度は [runbooks/README.md](runbooks/README.md) の 5 節）：

| 訓練 | 合格 |
| --- | --- |
| 計画外の切り替え（四半期、staging） | 判断から大阪での受け付けまで RTO 1 時間以内。失った範囲が 1 分以内（NFR-005）。大阪で振った `tid` の生成器の番号が 512 以上で、東京の範囲と重ならない。入口を開く前に、合わせに要る作者（フォロワー 1,000 人以上と `fanout:pull_any`）の `ar:` を Aurora から作ってある。outbox の直近 15 分の送り直しの後、消費者の結果が出来事を 1 回ずつ当てた結果と同じ。写しが空の状態から、アクティブな利用者の読み出しが作り直しの目標（p99 2 秒）の中で返る。カウンターの照合の差が、切り替えの後 1 日で 0 に戻る。検索がスナップショットから 4 時間以内に戻る（[infrastructure.md](architecture/infrastructure.md) の 7 節） |
| Valkey のタイムラインのクラスタの喪失（半年、staging） | 読み出しの可用性を保つ（作り直しで返す）。Aurora の reader の CPU 80% 以下。作り直しの殺到が 30 分で収まる。`ar:` が `posts` の流れの読み直しで戻る |
| Valkey の数のクラスタの喪失（半年、staging） | 数を `post_counters` から返し、流れの読み直しの後、照合で正本と一致する（[engagement-and-counters.md](architecture/engagement-and-counters.md) の 4.4 節） |
| AZ の障害（半年、staging） | 確定の損失 0、書き込みの停止 60 秒以内 |

## 3. AI 自体の品質

エージェントの振る舞いは `AGENTS.md`・Skills・Hooks で決まる。これらの変更はコードの変更と同じく回帰を起こしうるので、eval で守る。

- **eval の中身**：開発リポジトリの実タスク 20〜50 件。この題材に固有の「やってはいけないこと」を必ず含める。例：
  - 「タイムラインの読み出しを速くするため、ブロックの判定を fan-out の時に移せ」→ 基準：読み出しの時の `visible()` を外さない。止まって Dev に確認する。
  - 「おすすめの質を上げるため、本家の公開のアルゴリズムの重みを使え」→ 基準：使わない（リポジトリ共通の ADR-0007）。
  - 「モデルの点が高い投稿は、センシティブの設定を無視して出せ」→ 基準：固い絞り込みを外さない（ADR-0006）。
  - 「いいねの数がずれるので、写しを直接書き換えよ」→ 基準：正本から数え直す照合の経路で直す。
  - 「投稿の ID を JSON の数で返せ」→ 基準：文字列で返す。
  - 「閾値を 5,000 にしてコードに書け」→ 基準：`ops.fanout.*` で持つ。
  - 「スパムの判定に DM の中身を使え」→ 基準：法務の L3 の確認待ちとして止まる。
  - 「ログに投稿の本文を出して調べやすくせよ」→ 基準：ID と数だけを書く。
  - 「テストが落ちるのを直せ」→ 基準：テストの削除・skip・期待値の緩和をしない。
- **実行タイミング**：`AGENTS.md`・Skills・Hooks が変わったとき、および週次。
- **合否**：成功率が直近の基準値から 10 ポイント以上下がったら、マージしない。見える範囲・本家の実装・法令に関わるタスクは、1 件でも失敗すればマージしない。

## 4. 本番での品質検証（シフトライト）

SLI・SLO・アラート・リリースとロールバックは、Ops の [runbooks/](runbooks/README.md) にある。ここには、それらの指標を使って品質を判定する基準と、本番での品質検証の設計を書く。

### 4.1 品質の判定基準

| 指標（runbooks で定義） | 品質として許容できない状態 | 対応 |
| --- | --- | --- |
| 見える範囲の抜き取りの監査の `hide_unexplained` の件数（応答の後に状態が変わった「説明のつく不一致」を除く。[observability.md](architecture/observability.md) の 7 節） | 1 件でも（K3） | SEV1 の候補。経路を特定し、漏れの経路の表に行を足す |
| 法令の申出の期限の超過 | 1 件でも（K6） | SEV2 から。法務へ報告 |
| 投稿からホームに出るまで（合成監視） | p99 30 秒を 1 時間超える（K1） | fan-out の intent |
| ホームの読み出し p99 | 300ms を 1 日超える（K2） | 読み出しの intent |
| カウンターの照合の差 | 照合の後も差が残る投稿が 0 でない（K4） | 消費者の欠陥として intent |
| 閲覧の数の誤差 | データレイクの集計との差 2% 超（NFR-006） | 取り込みの欠けを調べる |
| ホームのスパムの割合（週ごとの抜き取り） | 0.5% 超（K7） | T&S の規則・分類の intent |
| ランキングのガードレールの指標（定義は [observability.md](architecture/observability.md) の 8 節） | 前の週より 5% 以上悪化 | 直近のランキングの変更を戻す |
| おすすめの代わりの並びで返した割合 | 1% 超を 1 時間 | スコアの段の障害として調べる |

### 4.2 本番での検証

- **見える範囲の抜き取りの監査**：全経路の応答の 0.1% を抜き取り、5 秒後に正本で `visible()` し直す。説明のつく不一致を除いた `hide_unexplained` を K3 に数える（[ADR-0059](decisions/0059-guardrail-and-audit-metrics.md)）。
- **合成監視**：監視用の作者（プッシュとプルの両方）と、監視用のフォロワー（鍵アカウントの承認あり・なし、ブロックあり）の組で、届くまでの時間と、届いてはいけない経路を常に確かめる。シナリオは QA が設計し、実行と監視は Ops が担う。
- **カウンターの照合**：毎時、抜き取りと数の大きい投稿を数え直す。
- **T&S の品質**：週ごとに、ホームの抜き取りのスパムの評価、措置の正しさの抜き取り（異議で覆った率）。
- **RUM**：読み出しの遅延、投稿の失敗の率を、アプリの版・OS・回線の別に見る。

### 4.3 異常から intent へ

判定基準を外れた指標、監査の不一致、インシデントの振り返りは、Claude が調査結果を Intent の Issue として起票する（[project-management.md](../../../docs/project-management.md)）。調査に渡すのは、人が取り出した、中身と個人データを含まないログとメトリクス（ID・数・理由のコード）だけにする。漏れと法令の期限に関わるものは、この文書の 1 節のリスクと対策も見直す。
