X の設計を読む前に

公開型の SNS は「短い文を保存して見せる」だけに見えますが、届ける・選ぶ・数える・守るのそれぞれに、分野に固有の考え方があります。設計の文書が前提にしている知識を、ここで先に押さえます。共通の前提知識（RLS、outbox、冪等、UUIDv7、ER 図の記号など）は共通の資料にあります。

X は何をするサービスか

X（旧 Twitter）は、誰でも短い文を投稿し、誰でもそれを読める公開型の SNS です。宛先を選んで送るのではなく、自分の投稿を公開し、自分をフォローしている人のホームに届きます。ニュースの速報、災害の情報、テレビの実況が、同じ流れの上で起きます。

おすすめ（For you）

フォローしていない人の投稿も含めて、1 人ひとりに合わせて並べ替えたホーム。ランキングで作ります。

フォロー中（Following）

フォローしている人の投稿だけを、新しい順に並べたホーム。順は時刻だけで決まります。

読む人が圧倒的に多い

多くの利用者は読むだけです。S1 でもタイムラインの読み出しのピークは 1 万件/秒で、投稿の 300 件/秒の 30 倍以上です。

再構築の intent は、難しさを 4 つに絞っています。届ける（数千万人のフォロワーに数秒で）、選ぶ（おすすめ）、数える（いいね・表示の数）、守る（スパム・違法な情報・日本の法令の期限）です。この資料も、この 4 つに沿って進みます。

設計の文書で効くところintent.md の Problem と「成功の基準」（K1〜K8）、architecture/README.md の 2 節（規模の段階）。

投稿・返信・引用・リポスト

X の「投稿」には 4 つの種類があります。設計では、どれも posts の 1 行で、kind の列で区別します。

kind何か本文指す先の列
postふつうの投稿あり—
reply返信。会話にぶら下がるありin_reply_to_post_id、conversation_id
quote引用。元の投稿を埋め込んでコメントするあり（空でもよい）quoted_post_id
repostリポスト。元の投稿を自分のフォロワーにそのまま広めるなしrepost_of_id
  • 会話は返信の木です。conversation_id は根の投稿の ID で、返信は親の値を写します。
  • スレッドは、作者が自分の投稿に続けた返信の列です。別の表はありません。
  • 文字数は「重み付きで 280」です。日本語・中国語・韓国語の文字は 2 と数えるので、全角だけなら 140 文字です。URL は短縮して 23 と数えます。
設計の文書で効くところposts-and-ids.md の 4 節（種類、文字数、引用とリポストの規則）、ADR-0008（書き込みの経路）。

フォロー・鍵アカウント・ブロック・ミュート

フォローは片向きの関係です。相手の承認は要りません。ただし、相手が鍵アカウントなら申請になり、承認されるまで投稿は読めません。

する側からの辺です。相手が公開なら active、鍵アカウントなら pending で始まります。設計は、する側から引く following と、される側から引く followers の 2 つの向きの表を、同じトランザクションで書きます。

承認したフォロワーと本人だけが投稿を読めます。リポストはできません（本人も）。承認したフォロワーの外に広がるためです。引用は書けますが、引用の中の元の投稿は、見えない人には「表示できません」になります。

相手は自分の投稿を読めず、フォロー・返信・DM ができません。ブロックした瞬間に、両向きのフォローと申請が外れます。

自分のホーム・通知から相手の投稿を消すだけです。相手には知られません。そのため、ミュートした人を、された側から引く逆向きの表を持ちません。語のミュートもあります。

設計の文書で効くところfollow-graph.md の 4 節（辺の状態と決定表）、ADR-0007・ADR-0011。

見える範囲は「読む時に」決める

この題材は、Slack のようなテナントの壁を持ちません。全員が 1 つの空間にいて、投稿は原則として公開です。そのかわり、誰に見せてはいけないかが、投稿と閲覧者の組ごとに変わります。

  • ブロックの関係、鍵アカウント、削除、法的な措置、規約の措置、年齢の制限、地域の制限。
  • これらは、投稿の後にも変わります（あとからブロックする、措置が入る）。

そこで設計は、見える範囲を読み出しの時に、1 つの関数 visible(viewer, post) で決めます。タイムライン・検索・通知・API・埋め込み・メディアの配信のどの経路も、この関数を通ります。配った時の判断を、読む時の判定の代わりにしません。

配る時に決める

配った後にブロックや削除が起きると、写しに古い判断が残り、見えてはいけない人に出る。

読む時に決める

写しには ID だけを持ち、読むたびに最新の状態で判定する。措置から 60 秒以内に全経路で消える（NFR-009）。

テナントがないので、共通の資料のテナントの RLS は使いません。RLS は DM・通知・ブックマークなど「本人だけの表」にだけ張ります。

設計の文書で効くところADR-0004、data-model.md の 3.2 節（本人だけの表）と 3.5 節（visible() に渡す列）。

fan-out：書く時に配るか、読む時に集めるか

「フォロー中」のホームは、フォローしている全員の投稿を新しい順に並べたものです。作り方は大きく 2 つあります。

投稿したら、フォロワー 1 人ひとりのホームの写し（受信箱）に ID を書き込みます（fan-out on write）。読む時は自分の写しを読むだけなので、読み出しが速い。かわりに、フォロワーが 100 万人なら 1 件の投稿で 100 万回の書き込みになります。

読む時に、フォローしている人の最近の投稿をそれぞれ取ってきて、合わせて並べます（fan-out on read）。書き込みは 1 回で済みます。かわりに、500 人をフォローしている人は、読むたびに 500 人分を合わせることになり、読み出しが重い。

flowchart LR
  P[投稿] --> L[(出来事のログ)]
  L --> F[Fanout Worker]
  F -- "フォロワーごとに書く" --> T1[(A のホームの写し)]
  F --> T2[(B のホームの写し)]
  F --> T3[(C のホームの写し)]
  R[A が読む] --> T1

読み出しは書き込みの 30 倍以上あるので、基本はプッシュが有利です。設計では、写しを Valkey に持ち、最近 30 日に読んだ人（アクティブな人）にだけ配ります。写しは正本ではなく、投稿とフォローの表から作り直せます。

設計の文書で効くところADR-0003、timeline-fanout.md の 4〜6 節（写しの形、fan-out の流れ、読み出し）。

セレブリティの問題と組み合わせの方式

フォロワーが数百万〜数千万人いる人（芸能人、報道機関、自治体）が投稿すると、プッシュでは 1 件で何千万回もの書き込みになり、キューが詰まります。これをセレブリティの問題と呼びます。本家も、2012 年の講演で「書く時に配り、フォロワーの多い作者は読む時に合わせる」形を説明しています。

  1. 作者のフォロワーが閾値 T 未満ならプッシュ。S1 の既定は T = 10,000（ops.fanout.pull_threshold）。
  2. T 以上の作者はプル。投稿は作者ごとの最近の投稿の写し（ar:）にだけ入れる。
  3. 読む人は、自分の写し（tl:）と、フォローしているプルの作者の ar: を、ID の順に合わせる。重複は ID で落とす。
  4. 地震の直後のような瞬間のピークでは、キューの遅れを見て閾値を一時的に下げ、より多くの作者をプルに回す（burst の状態）。
  5. 写しが消えても（Valkey の障害、久しぶりの利用者）、正本から作り直す。作り直しは利用者ごとに 1 回にまとめる（single flight）。

フォロワー 1,000 万人の作者が投稿しました。この設計で、フォロワーのホームにはどう届きますか？

閾値（既定 1 万）以上の作者はプルです。書き込みの量は閾値とアクティブなフォロワーの数で上限が決まり、大きな作者の投稿で爆発しません。それでも p95 5 秒（NFR-002）は守ります。

設計の文書で効くところADR-0015（瞬間のピーク）、ADR-0016（作り直し）、timeline-fanout.md の 5.4・5.5・7 節。

時刻の順に並ぶ 64 ビットの ID

共通の資料の UUIDv7 と同じく「ID の大小が時刻の順」になる ID ですが、この題材は 64 ビットの tid を使います。本家が 2010 年に公開した方式（Snowflake）と同じ考え方で、コードは自前で書きます。

 0 | ミリ秒 41 ビット（起点 2026-01-01） | 生成器 10 ビット | 連番 12 ビット
符号  └── 約 69 年もつ ──────────────┘   └ 0〜1023 ─┘   └ 1 ms に 4096 ─┘
  • なぜ 64 ビットか：ホームの写しは 1 項目に ID を 3 つ持ちます。UUIDv7（128 ビット）だと写しの記憶が倍になります。
  • 調整なしで振れる：生成器の番号さえ重ならなければ、DB の連番を通さずに各サーバーで振れます。番号は DB で貸し出し、東京は 0〜511、大阪は 512〜1023 です。
  • おおむね時刻の順（k-sorted）：生成器の時計のずれの分、後で振った ID が小さいことがあります。新着の読み出しは 10 秒ぶん重ねて読みます。
  • 時計が戻ったら振らない：5ms までは待ち、それ以上は失敗させます。

API の JSON で、tid を数値ではなく文字列で返すのはなぜ？

number は倍精度の浮動小数点数で、253 を超える整数は丸められ、別の投稿の ID になってしまいます。TypeScript の中では bigint かブランド型の文字列で持ちます。作成の時刻は公開の情報なので、隠しません。

設計の文書で効くところADR-0002、posts-and-ids.md の 8 節（生成器の貸し出しと時計）、data-model.md の 3.1 節（どの表が tid か）。

推薦のパイプラインの基本

「おすすめ」は、全部の投稿に点を付けるのではなく、段を踏んで数を絞るのが業界の定石です。本家も公開の README で、候補を集めて軽いランク・重いランクで並べ、絞り込んで混ぜる構成を説明しています。

flowchart LR
  S["候補の源 5 つ"] -- "800 件" --> PF["前の絞り込み"]
  PF --> LR["軽いランク"]
  LR -- "200 件" --> HR["重いランク"]
  HR --> QF["後の絞り込み"]
  QF --> MX["混ぜ合わせ"]
  MX -- "20 件" --> U["画面"]
段何をするか
候補の取り出しフォロー中、フォロー中の人のいいね、2 歩先の作者、話題、人気、の 5 つの源から集める
軽いランク手元にある値だけで安く点を付け、800 件を 200 件に減らす
重いランク行動（いいね・返信など）ごとの確率 × 重みの和。S1 は式、S2 から学習済みのモデル
後の絞り込みvisible() をもう一度通し、スパムや表示の制限を落とす。時間が足りなくても飛ばさない

境界ML の出力は「並べる順」にだけ使います。ブロック・鍵アカウント・法的な措置・年齢の制限を、スコアで上書きしません。スコアの部品が落ちたら、時刻の順の並びに戻します。
設計の文書で効くところADR-0006、ADR-0018、ranking-and-recommendation.md の 4〜11 節。

A/B テストとガードレール

推薦の良し悪しは、コードを読んでも分かりません。実際の利用者の行動で比べるしかありません。そのための道具が A/B テストとガードレールです。

  1. オフラインの評価：過去の配信と行動の記録を再生し、新しいバージョンで並べ直して比べる（NDCG など）。CI の足切りに使う。
  2. 割り当て：利用者の ID のハッシュで、新旧のどちらを見せるかを固定する。同じ人は毎回同じ側になる。
  3. 少しずつ広げる：1% → 5% → 50% → 100%。各段 7 日以上（曜日の偏りを除く）。
  4. 主な指標で良くなったかを見る：1 回の訪問の中のいいね・返信・リポストの率（K8）、7 日の再訪の率。
  5. ガードレールで悪くなっていないかを見る：通報・ミュート・ブロックの率、スパムの表示、遅延。悪化が出たら広げずに止める。

主な指標が上がっても、通報が増えていれば採用しません。「伸ばしたい数」と「悪化させてはいけない数」を分けて持つのが、ガードレールの考え方です。100% に広げる判断は人（PM）が行います。

新しい重みで、いいねの率が 8% 上がりました。ただし通報の率も 6% 上がりました（信頼区間の上端で）。どうしますか？

設計では、ガードレールの指標が信頼区間の上端で 5% 以上悪化したら止めます。主な指標の改善と引き換えにしません。

設計の文書で効くところADR-0020、ADR-0059、ranking-and-recommendation.md の 12.3 節。フラグは共通の資料のデプロイとリリースを分ける。

大規模なカウンターと結果整合

人気の投稿には、1 秒に何千ものいいねが付きます。全員が同じ行の like_count を +1 すると、その行のロックに行列ができます。そこで、正本と表示の数を分けます。

  1. いいねは likes(post_id, user_id) に 1 行を足す。主キーが利用者ごとなので、行の取り合いがない。同じトランザクションで outbox に出来事を書く。
  2. Relay が出来事を Kinesis の engagement の流れへ送る。
  3. Counter Aggregator が 1 秒ぶんを投稿ごとにまとめ、Valkey の写し（pc:{post_id}）に 1 回で足す。同じ出来事を 2 回足さないよう、連番を覚えておく。
  4. 60 秒ごとに、写しの値を DB の post_counters へ書き戻す。
  5. 静かになった投稿を、likes の行を数え直して照合する。差があれば正本の値で直す。

表示の数は、確定から p95 5 秒遅れて追いつきます。この「いずれ正本に揃う」性質を結果整合と呼びます。自分の操作だけは、画面が楽観的に ±1 して見せます。表示の数（閲覧）は桁が大きいので、Aurora を通さずに受け、概算で数え、減らない形で見せます。

いいねの数の写し（Valkey）と post_counters が食い違いました。正しい値はどれですか？

正本は関係の表（likes・reposts・followers）で、表示の数はどちらも写しです。写しを直接 UPDATE で直さず、照合の経路だけが正本の値で上書きします。

設計の文書で効くところADR-0023、ADR-0024、engagement-and-counters.md の 4・5 節。outbox は共通の資料。

トレンドと急上昇の検出

トレンドは「いま、いつもより急に多く語られている語」です。多く語られている語ではありません。「おはよう」は毎朝多いですが、トレンドではありません。だから、基準（ふだんの量）との差で決めます。

  1. 投稿からハッシュタグと名詞の並びを、1 件あたり最大 10 語取り出す。
  2. 5 分の区切りごとに、語ごとの数を数える。1 人の作者は 1 つの語を区切りに 1 回だけ数える（連投で水増しできない）。
  3. 作者に重みを付ける。登録 7 日未満、スパムの点の高い人、未確認の人は 0。
  4. 直近 15 分の数 c と、ふだんの量 e（指数移動平均）を比べ、z = (c − e) / √(e + β) の大きい語を出す。
  5. ボットの群れ・同じ文の貼り付けが多い語は出さず、T&S の待ち行列へ送る。

4 の式は、数がポアソン分布で揺れるとき、揺れの大きさが平均の平方根になることを使っています。ふだん 100 の語が 120 になっても珍しくありませんが、ふだん 1 の語が 21 になるのは珍しい、という判断を 1 つの式で表します。このような検出をバースト検出と呼びます。

設計の文書で効くところADR-0027、search-and-trends.md の 9 節（数え方、急上昇の検出、操作への強さ）。

日本語の全文検索：N-gram と形態素解析

英語は空白で語が区切れますが、日本語は区切れません。「東京都庁に行く」を語に分ける方法が 2 つあります。

文字列を機械的に N 文字ずつずらして切ります（N-gram）。2 文字なら「東京・京都・都庁・庁に…」。辞書が要らないので、新語・固有名詞・語の途中でも取りこぼしません。かわりに「京都」で「東京都」が当たるような誤りが出て、索引も大きくなります。

辞書を使って意味のある語に分けます（形態素解析。kuromoji・Sudachi など）。「東京都庁 / に / 行く」。誤りが少なく、関連度の点を付けやすい。かわりに、辞書にない新語やネットの言い回しを、分け方の違いで取りこぼします。

設計は 2 つを組み合わせます。当たるかどうかは 1〜2 文字の N-gram で判定し、並べる順の点は kuromoji で付けます。英字は語の単位で当てます。索引と問い合わせには、同じ正規化の関数（NFKC、小文字、長音の揃え）をかけます。

昨日生まれたばかりのネットの流行語で検索しました。取りこぼしにくいのはどちら？

形態素解析は辞書にない語を予想外の位置で分け、問い合わせ側と本文側で分け方が食い違うことがあります。N-gram は文字の並びだけを見るので、新語でも部分一致で当たります。

設計の文書で効くところADR-0025、ADR-0026（索引にも visible()）、search-and-trends.md の 5・6 節。

メディアの配信：HLS と CDN

動画を 1 本の大きなファイルで配ると、回線の遅い人は再生が止まります。そこで動画は HLS で配ります。

短く切る

動画を 6 秒ずつの区切り（セグメント）に分ける。

画質を何段も作る

240p〜1080p の 5 段を作り、一覧（master.m3u8）に並べる。

端末が選ぶ

再生する側が回線の速さを見て、区切りごとに段を切り替える（ABR）。

画像も動画も、CDN（CloudFront）の端のサーバーから配ります。公開のメディアは推測できない 128 ビットのキーの URL にし、中身が変わらないので 1 年キャッシュします。鍵アカウントと DM のメディアは、visible() を通った人にだけ、15 分で切れる署名付きの URL を出します。

キャッシュと削除1 年キャッシュしたものを、措置で数秒のうちに止める必要があります。設計は、CDN の端で読める拒否の一覧（CloudFront KeyValueStore）にキーを書き、451 か 404 を返させます。キャッシュの無効化と、元のファイルの隔離も重ねます。
設計の文書で効くところADR-0032、ADR-0033、media.md の 6・8 節。

モデレーションと T&S

T&S（Trust & Safety）は、スパム・ボット・誹謗中傷・違法な情報から利用者を守る仕事と仕組みの総称です。公開型の SNS では、ここが製品の中心の 1 つです。

  1. 見つける：利用者の通報、スパムの規則と危険の点、既知の違法な画像のハッシュの照合、法令の申出。
  2. まとめて並べる：同じ対象への通報を 1 つの案件にし、重さ・広がり・速さで P0〜P3 の待ち行列に入れる。命に関わるものは P0 で当番を呼ぶ。
  3. 判断して記録する：措置を、根拠（規約の条項か法令）と判断した人と一緒に、追記だけの表に書く。
  4. 効かせる：措置の要約（mod_flags）と状態のバージョンを上げ、visible() が 60 秒以内に全経路で隠す。
  5. 知らせる・覆す：措置を受けた人に、根拠と異議の申立ての方法を示す。異議は別の担当が見る。

措置は「消す」だけではありません。ラベル（注意の印）、表示の制限（フォロワーには出すが、検索・おすすめ・トレンドから外す）、地域の制限、メディアだけの停止、アカウントの読み取りだけ・凍結、と段階があります。

設計の文書で効くところADR-0038〜0040、trust-and-safety.md の 4〜8 節、data-model.md の 3.5 節（mod_flags のビット）。

日本の法令の枠組み

ここは枠組みの説明だけです。具体の期限・基準・手順は、設計の文書でも法務の確認待ちで、結論を出していません。

プロバイダ責任制限法を改正・改称した法律で、2025-04-01 に施行されました。利用者の多い SNS などを総務大臣が大規模特定電気通信役務提供者に指定し、削除の申出の窓口、申出への判断と通知、削除の基準の公表、運用の状況の公表などを求めます。2025-04-30 に本家の運営の会社を含む 5 社が指定されました。判断と通知の期限は「7 日」とされますが、省令の条文は未検証で、設計は仮置きです。

法務の確認待ち（L1）：どの規模で指定に当たるか、指定の前から同じ水準で対応するか、期限の数え方、通知の具体。

匿名の投稿で権利を侵害された人が、裁判所の手続きで、投稿した人を特定する情報（IP アドレス、時刻、電話番号など）の開示を求める仕組みです。開示の命令のほか、別の事業者の情報を得るための提供の命令、ログを消させない消去の禁止の命令があります。だから、投稿・ログインの時の IP アドレスなどを、決めた期間だけ持つ必要があります。

法務の確認待ち（L2）：何を何日持つか、意見の照会の手順。確認まで、該当のログは物理の削除を止めています。

DM は電気通信事業法の「通信の秘密」に当たりうるため、スパムの判定などで DM の中身を機械で読むかは法務の確認待ち（L3）です。確認まで作りません。ほかに、推薦と個人情報（L4）、青少年の保護（L5）、著作権（L6）、捜査機関への対応（L7）、保持の期間（L8）、選挙（L9）が確認待ちです。

削除の申出への判断の期限「7 日」は、設計でどう扱われていますか？

受け付けの時刻から期限を計算して案件に持ち、期限の前に警告を出す仕組みは先に作ります。値と数え方は L1 の確認の後に決め、AppConfig の legal.l1.takedown_deadline に入れます。

設計の文書で効くところintent.md の「法務の確認待ち」（L1〜L11）、ADR-0041、trust-and-safety.md の 10・11 節。

データモデルの読み方

中心は users と posts です。関係（フォロー・いいね・リポスト）は、2 人（または人と投稿）の組を主キーにした表で、行があること＝関係があることです。記号の読み方は共通の資料にあります。

erDiagram
  users ||--o{ posts : "writes"
  posts ||--o{ posts : "reply, quote, repost of"
  users ||--o{ following : "follows"
  users ||--o{ followers : "followed by"
  posts ||--o{ likes : "liked"
  posts ||--o{ reposts : "reposted"
  posts ||--o| post_counters : "counted by"
  posts ||--o{ moderation_actions : "acted on"
  users {
    bigint id PK "tid"
    text handle_lower UK
    boolean protected
    text state
  }
  posts {
    bigint id PK "tid"
    bigint author_id FK
    text kind "post, reply, quote, repost"
    bigint conversation_id
    smallint mod_flags
    bigint state_version
  }
  following {
    bigint src_id PK
    bigint dst_id PK
    text state "active, pending"
  }
  followers {
    bigint dst_id PK
    bigint src_id PK
    text state
  }
  likes {
    bigint post_id PK
    bigint user_id PK
  }
  reposts {
    bigint post_id PK
    bigint user_id PK
  }
  post_counters {
    bigint post_id PK
    bigint likes "copy of likes rows"
    bigint views "approx"
  }
  moderation_actions {
    uuid action_id PK
    text target_kind "post, media, account"
    bigint target_id
    text kind
    text basis_kind
  }
  • following と followers は同じ辺の 2 つの向きです。「A がフォローしている人」と「B のフォロワー」をどちらも主キーの範囲で速く引くためです。
  • post_counters は写しです。正本は likes・reposts です（views だけは正本の表がなく、概算です）。
  • moderation_actions は対象を target_kind と target_id で指す論理の参照で、DB の外部キーではありません。
  • 投稿は消さずに状態を変えます（墓石）。state_version は写しが古い状態で上書きしないためのバージョンです。
設計の文書で効くところdata-model.md の 3 節（規約）と 4 節（全体の ER 図）、data-model/ の領域ごとのファイル。

用語集

返信
ある投稿への応答の投稿。返信の木が会話になる。
引用
元の投稿を埋め込み、自分のコメントを付けた投稿。
リポスト
元の投稿を、本文を付けずに自分のフォロワーへ広める操作。旧称はリツイート。
鍵アカウント
承認したフォロワーと本人だけが投稿を読めるアカウント。フォローは申請と承認になる。
visible()
閲覧者と投稿の組から、見せるか・隠すか・警告を挟むかを決める 1 つの関数。全部の読み出しの経路が通る。
fan-out
1 件の投稿を、フォロワーごとのホームの写しへ複製して配ること。書く時に配る（プッシュ）と読む時に集める（プル）がある。
セレブリティの問題
フォロワーの非常に多い作者の投稿で、プッシュの書き込みの量が爆発する問題。
瞬間のピーク
年明けの 0 時、番組の山場、地震の直後などに、数秒〜数分だけ投稿が集中すること。設計ではピークの 10 倍と置く。
tid
この設計の 64 ビットの ID。ミリ秒の時刻・生成器の番号・連番からなり、ID の大小がおおむね作られた順になる。
Snowflake
本家が 2010 年に公開した、調整なしで時刻の順の 64 ビットの ID を振る方式。この設計はコードを使わない。
k-sorted
完全ではないが、ずれが一定の幅に収まる並び。tid は時計のずれの分だけ順が入れ替わりうる。
ランキング
候補の投稿に点を付け、並べる順を決めること。この設計では見える範囲の判定には使わない。
候補の取り出し
推薦の最初の段。膨大な投稿から、点を付ける価値のありそうな数百件を、いくつかの源から集める。
混ぜ合わせ
点の順に並べた後、作者の偏りやフォロー外の割合などの規則で、1 ページの並びを整える段。
フォロー外
閲覧者がフォローしていない作者の投稿。英語では out-of-network。
A/B テスト
利用者を無作為に分け、新旧のバージョンを同じ期間に見せて、指標の差で採否を決める実験。
ガードレール
実験で「悪化させてはいけない」指標。通報・ブロックの率や遅延など。悪化したら止める。
Kinesis Data Streams
AWS の出来事のログ。複数の消費者が同じ流れを独立に読み、読み直せる。
結果整合
更新の直後は写しが古いことがあるが、時間がたてば正本と同じ値に揃う性質。
照合
写しの数と、正本の関係の表を数え直した値を比べ、差を正本の値で直すジョブ。
表示の数
投稿が画面に出た回数。この設計では投稿の 50% 以上が 500ms 以上出たら 1 回。概算で、減らない。
バースト検出
ある語の出現が、ふだんの量に比べて統計的に珍しいほど増えたことを見つける処理。
N-gram
文字列を N 文字ずつずらして切った断片。1 文字なら unigram、2 文字なら bigram。
形態素解析
辞書を使って文を意味のある最小の語に区切る処理。kuromoji・Sudachi など。
HLS
HTTP Live Streaming。動画を短い区切りと画質の段に分け、プレイリスト（.m3u8）で配る方式。
ABR
Adaptive Bitrate。再生する側が回線の速さに合わせて、画質の段を切り替えること。
CDN
利用者に近い端のサーバーにコンテンツを置いて配る仕組み。この設計では CloudFront。
T&S
Trust & Safety。プラットフォームの安全と信頼を守る仕事と仕組み。モデレーション、スパム対策、法令の対応を含む。
通報
利用者が、規約の違反と思う投稿・アカウントを知らせること。法令の「申出」とは別の経路で扱う。
措置
規約や法令に基づく、削除・表示の制限・凍結などの対応。根拠と判断した人を記録してから効かせる。
異議の申立て
措置を受けた人が、判断の見直しを求めること。
ハッシュの照合
画像の知覚ハッシュ（PDQ など）を、既知の違法な画像の一覧と比べる仕組み。少し加工した画像も当たる。
大規模特定電気通信役務提供者
情報流通プラットフォーム対処法で、利用者の規模などから総務大臣が指定し、削除の申出への迅速な対応などの義務を負う事業者。
発信者情報の開示
権利を侵害された人が、投稿した人を特定する情報の開示を、裁判所の手続きなどで求める仕組み。
墓石
tombstone。行を消さずに「削除済み」の状態だけを残すこと。物理の削除は保持の期間の後のジョブが行う。
