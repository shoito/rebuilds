# ADR-0004: テナントは 1 つ。本人だけの表に FORCE RLS をかけ、公開の表の見える範囲は 1 つの関数 `visible()` で読み出しの時に決める

## Context

rebuilds の他の題材は、ワークスペースやテナントを契約とデータの単位にし、全テーブルに `tenant_id`（`workspace_id`）を持たせ、`FORCE ROW LEVEL SECURITY` と `SET LOCAL` で分けている（Linear の ADR-0004、Slack の ADR-0009）。

この題材は違う。

- **テナントがない。** 全利用者が 1 つの公開の空間にいる。誰でも誰をフォローでき、公開の投稿は誰でも（ログインしていなくても、検索エンジンからも）読める。
- **見える範囲は、閲覧者と投稿の関係で決まる。** 同じ投稿が、ある人には見え、別の人には見えない。
  - 鍵アカウント：承認したフォロワーと本人だけが読める。
  - ブロック：ブロックした人・された人の間で互いに見えない。
  - ミュート：ミュートした人のタイムラインと通知から消える（投稿そのものは見られる）。
  - 削除、規約の措置（削除・表示の制限・年齢の制限）、法令の措置（削除の申出への対応、地域での非表示）。
  - センシティブなメディアの設定、返信できる人の制限。
- **本人だけが読むデータがある。** DM、ブックマーク、下書き、通知、設定、ミュートの語、ログインの記録。
- 読み出しは S3 で 80 万件/秒。1 回のタイムラインの読み出しで、数十〜数百件の投稿の見える範囲を判定する。

## Options

テナント：

1. **テナントは 1 つ。テナントの列と RLS を置かない**
2. 利用者をテナントとみなし、全テーブルに `owner_id` と RLS を付ける
3. 地域や利用者のハッシュでテナントを作り、セルに分ける

見える範囲：

- a. **公開の表は、読み出しの時に 1 つの関数 `visible(viewer, post)` で決める。** 本人だけの表は FORCE RLS で守る
- b. 見える範囲を RLS のポリシーで表す（閲覧者の ID を `SET LOCAL` し、ポリシーでブロック・鍵アカウントを結合する）
- c. 書き込みの時（fan-out の時）に、見えてよい人にだけ配る

## Decision

1 と a を採用する。

### テナント

- テナントの列（`tenant_id`）を置かない。テナントの RLS も置かない。全利用者が 1 つの空間にいるのが、この題材の本質である。
- 2 は、公開の投稿・フォローの辺・いいねが「誰のものか」を 1 人に決められない（フォローの辺は両端の 2 人に関わる）。全テーブルの RLS は、公開の読み出しの性能を下げるだけで、守るものがない。
- 3 は、利用者の間に境がないため、セルをまたぐ読み出しが常に起きる。S3 の分割は、テナントでなく、機能と鍵で行う（infrastructure の領域）。

### 本人だけの表：FORCE RLS

- **本人だけが読む表** に `owner_id` を持たせ、`FORCE ROW LEVEL SECURITY` を設定する。トランザクションごとに `SET LOCAL app.actor_id = '<利用者の tid>'` を設定し、ポリシーは `owner_id = current_setting('app.actor_id')::bigint` にする。
  - 対象：ブックマーク、下書き、予約の投稿、通知、ミュートの語、設定、ログインの記録、データの書き出しの依頼。
  - DM：会話の参加者の表を通して、参加者だけが読めるポリシーにする（`EXISTS` で `dm_participants` を引く）。
- **運用と T&S の読み出し** は、別の DB のロール（`ts_reader` など）で行い、RLS を通さない代わりに、読み出しの理由（案件の ID）を必ず記録する。DM の中身を人が読む手順は、法務の確認（L3）が済むまで作らない。
- バッチとストリームの処理（fan-out、集計、索引）は、本人だけの表を読まない。読む必要がある処理（通知の送信）は、受け手ごとに `SET LOCAL` して読む。

### 公開の表：`visible()`

- 投稿・プロフィール・フォローの一覧・メディアの見える範囲は、`packages/visibility` の純粋な関数で決める。

  ```ts
  visible(viewer: ViewerContext, post: PostState): Visibility
  // Visibility = { kind: "show" } | { kind: "hide", reason } | { kind: "interstitial", reason }
  ```

  - `ViewerContext`：閲覧者の ID（ログインしていなければ匿名）、ブロックした・された集合、ミュートの集合と語、承認されているフォロー先の鍵アカウント、年齢の区分、センシティブの設定、地域。
  - `PostState`：作者、作者の鍵の状態、削除、措置（種類、範囲、地域）、センシティブの印、返信の制限。
- **全経路がこの関数を通る。** タイムライン（フォロー中・おすすめ）、プロフィール、会話、検索、トレンドの例、通知、公開 API、埋め込み、メディアの配信の確認、DM の中の投稿の共有、データの書き出し。この関数を通らない読み出しの経路を作らない。
- **読み出しの時に毎回判定する。** fan-out の時や、検索の索引に入れた時の判定を、読み出しの判定の代わりにしない（[ADR-0003](0003-timeline-fanout-hybrid.md)）。写しに入った後に、ブロック・削除・措置が起きるため。
  - 費用は、投稿の状態の写し（Valkey）と、閲覧者の集合の写し（ブロック・ミュート・承認済みの鍵アカウント）で抑える。集合は変更の出来事で無効にする。
- **検索の索引には、粗い絞り込みの印を入れる。** 削除・措置・鍵アカウントの印を文書に入れ、問い合わせの条件で先に落とす。その上で、返す前に `visible()` で判定し直す（索引の更新の遅れの間の漏れを防ぐ）。
- **メディア**：公開の CDN で配る。鍵アカウントの投稿のメディアは、推測できない URL と、短い期限の署名付きの URL で配る。措置・削除のときは、元の S3 のオブジェクトの公開を止め、CDN を無効にする。具体は media の領域で決める（NFR-009 の 60 秒）。
- b を採らない理由：ブロック・鍵アカウント・措置の判定を、全ての読み出しの SQL に結合として乗せることになり、タイムラインの読み出し（Valkey の写しから始まる）にはそもそも効かない。検索（OpenSearch）にも効かない。全経路で同じ判定にするには、アプリの 1 つの関数のほうが確かめやすい。
- c を採らない理由：配った後に状態が変わる（ブロック、削除、措置）。配った時の判定は古くなる。

## Consequences

- 良くなること：
  - 公開の空間という題材の本質に合う。公開の読み出しに RLS の費用がかからない。
  - 見える範囲の規則が 1 つの関数にまとまり、表駆動テストと性質ベーステストで確かめられる。
  - 本人だけのデータ（DM、ブックマーク、通知）は、アプリの誤りがあっても DB で守られる。
- 引き受けるコスト：
  - 公開の表の見える範囲は DB で守られない。`visible()` を通らない経路が 1 つでもあれば漏れる。漏れの経路の表（[quality.md](../quality.md) の 2.2.1 節）と、本番の抜き取りの監査で確かめる。
  - 読み出しのたびの判定の費用。閲覧者の集合が大きい人（ブロックを数万件持つ人）の扱いを、follow-graph の領域で決める。
  - 共通の基盤の「全テーブルに RLS」の規則から外れる。どの表が本人だけの表かを、データモデルの規約で 1 か所に書き、マイグレーションの検査で強制する。

## Confirmation

- 表駆動テスト：`visible()` の決定表（閲覧者の関係 × 鍵 × ブロック × 削除 × 措置 × センシティブ × 年齢）を、spec から読み込んで全行を確かめる（trust-and-safety・follow-graph の領域で書く）。
- 性質ベーステスト：任意のフォロー・承認・ブロック・削除・措置の列の後、どの経路（タイムライン、検索、通知、API、会話）の読み出しも、`visible()` が `show` を返す投稿だけを返す。
- CI：本人だけの表の一覧にある表に、`owner_id`（DM は参加者のポリシー）と FORCE RLS がないマイグレーションを失敗させる。
- lint：投稿・プロフィール・メディアを返す API の処理で、`visible()` を通さずに応答へ投稿を入れるコードを検出する（応答の型を `Visible<Post>` にし、`visible()` だけがその型を作れるようにする）。
- 本番：読み出しの抜き取りの監査（返した投稿を、その時点の正本で `visible()` し直し、`hide` の件数を数える。0 であるべき）。
