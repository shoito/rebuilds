# ADR-0006: おすすめは自前の段のパイプラインにし、ML はスコアと取り出しだけに使う。安全と法令の判定を上書きしない

## Context

「おすすめ」のタイムラインは、フォローしている人の投稿と、フォローしていない人の投稿を混ぜ、1 人ひとりに合わせて並べる。本家は次の形を公開している（[architecture/README.md](../architecture/README.md) の 1.3 節。2026-10-04 に確認）。

- 2023 年（[twitter/the-algorithm](https://github.com/twitter/the-algorithm)）：候補の源（フォロー中の投稿の索引、関係のグラフの辿り、埋め込みの近さ）から集め、軽いランク、重いランク（ニューラルネットワーク）、見える範囲の絞り込み、混ぜ合わせの順に通す。フォロー中とそれ以外は平均で半々。
- 今（[xai-org/x-algorithm](https://github.com/xai-org/x-algorithm)）：Home Mixer が段を回し、Thunder がフォロー中の最近の投稿をメモリーに持ち、Phoenix（transformer）が取り出しとランクを行う。行動（いいね、返信、リポストなど）ごとの確率を重みで足し、作者の偏りを減らし、フォロー外を割り引く。

この題材で決めたいのは、次の境界である。

- **何を ML に任せ、何を任せないか。** モデルの誤りや、学習のデータの偏りで、ブロックした人の投稿や、措置した投稿が出てはならない（NFR-009）。
- **S1 でどこまでやるか。** S1 は出来事のログが少なく、学習済みのモデルの質が出ない。学習の基盤も重い。
- **壊れたときにどうするか。** おすすめが落ちても、ホームを空にしない（NFR-004）。
- **変更をどう安全に出すか。** 重みの小さな変更が、利用者の体験と安全の指標を大きく動かす。

## Options

1. **自前の段のパイプライン。** 段の口を固定し、ML はスコアの段と取り出しの段の中だけに置く。S1 は規則と軽いスコア、S2 から学習済みのモデル
2. **最初から学習済みのモデルで端から端まで**（取り出しからランクまで 1 つのモデル）
3. **規則だけ**（ML を使わない）
4. **外部の推薦のサービス**（Amazon Personalize など）

## Decision

1 を採用する。

### 段

`packages/ranking` に、次の段を型の口で分ける。各段は、前の段の出力だけを入力にする。

| 段 | 役目 | ML を使うか |
| --- | --- | --- |
| 1. 候補の取り出し（candidate sources） | 源ごとに候補を集める。S1 の源：フォロー中の写し（[ADR-0003](0003-timeline-fanout-hybrid.md)）、フォロー中の人がいいね・リポストした投稿、話題（トレンド）の人気の投稿、フォロー中の人がフォローしている人の人気の投稿。S3 で埋め込みの近さを足す | S3 から（埋め込みでの取り出し） |
| 2. 固い絞り込み（前） | `visible()`（[ADR-0004](0004-single-tenant-and-visibility.md)）、既読、古さ（既定 48 時間）、重複 | 使わない |
| 3. 特徴の付加（hydration） | 投稿の特徴（経過時間、エンゲージメントの率、メディアの有無、言語）、作者との関係（やりとりの回数、相互フォロー）、閲覧者の特徴 | 使わない（特徴は決まった定義から作る） |
| 4. スコア | 候補ごとに点を付ける。S1：手で決めた式（行動の率と関係の強さと時間の減衰の積）。S2：学習済みのモデル（行動ごとの確率）と重みの和 | 使う |
| 5. 固い絞り込み（後）と安全のガードレール | `visible()` を **もう一度** 通す。通報・措置の候補、スパムの点の高い作者、センシティブの設定に合わない投稿を落とすか、順位を下げる | 使わない（スパムの点は T&S の分類の結果を入力として使うが、落とす判断は規則） |
| 6. 混ぜ合わせ（mixer） | 作者の偏りを減らす（同じ作者の連続を避ける）、フォロー外の割合の上限、会話のまとめ、広告の枠（MVP の後） | 使わない |

### 境界の規則

- **ML の出力は順位だけ。** 見える範囲（ブロック、鍵、削除、措置、年齢、センシティブ）を ML の点で変えない。2 段目と 5 段目の絞り込みは、点の後でも必ず通す。モデルが「見せたほうがよい」と言っても、`visible()` が `hide` なら出さない。
- **段の口を固定する。** 候補は `(post_id, source, source_reason)`、点は `(post_id, score, model_version)`。モデルを入れ替えても、他の段は変わらない。
- **時間の予算**：おすすめの最初のページの p99 800ms（NFR-003）を、段ごとに割り振る（取り出し 200ms、特徴 150ms、スコア 250ms、絞り込みと混ぜ合わせ 100ms、残りは余裕）。段が予算を超えたら、その段の結果を部分で使うか、飛ばす。
- **代わりの並び**：スコアの段が落ちたか予算を超えたら、フォロー中の時刻の順に、人気の投稿を少し混ぜた並びで返す。可用性に数える（NFR-004）。どちらで返したかを記録する。
- **理由の記録**：返した投稿ごとに、源と理由のコード（「フォロー中の○○さんがいいね」など）と、モデルのバージョンを記録する。利用者に「なぜ表示されるか」を示す。推薦に使う履歴の説明の範囲は法務の L4 の後に決める。

### 段階

| 段階 | スコア | 取り出し | 学習 |
| --- | --- | --- | --- |
| S1 | 手で決めた式。重みは AppConfig で持ち、A/B で決める | 規則の源（フォロー中、フォロー中の人の行動、話題、2 歩先） | なし。出来事をデータレイクに貯める |
| S2 | 学習済みのモデル（勾配ブースティング。行動ごとの確率）を ONNX Runtime で動かす | S1 と同じ | Python でオフラインに学習。週ごとに作り直す |
| S3 | ニューラルネットワークのランク | 埋め込み（2 つの塔）と近傍の探索を足す | 同上。学習の基盤は ranking-and-recommendation の領域で決める |

### 変更の出し方

- 重み・特徴・モデルの変更は、すべて「ランキングの変更」として同じ手順を通す。手で決めた重みも例外にしない。
  1. **オフラインの評価**：記録した出来事（データレイク）で再生し、決まった指標（行動の予測の正しさ、多様さ、フォロー外の割合、ガードレールの指標）を前のバージョンと比べる。CI で回す。
  2. **A/B**：`experiment.ranking.*` のフラグで、1% → 5% → 50% → 100% と広げる。
  3. **ガードレール**：通報の率、ミュート・ブロックの率、「興味がない」の率、スパムの点の高い投稿の表示の割合が、前のバージョンより決まった幅（既定 5%）以上悪くなったら、広げずに止める。
- 本家の公開のアルゴリズムの重み・特徴の定義・モデルを持ち込まない（[ADR-0001](0001-platform-and-stack.md)）。

### 他の案を選ばなかった理由

- **2（端から端まで 1 つのモデル）**：S1 では学習のデータが足りない。見える範囲の絞り込みをモデルの外に確実に置く境界が曖昧になる。
- **3（規則だけ）**：S1 の出発点としては同じだが、K8（フォロー中の時刻の順より 20% 高い）を S2 以降で伸ばす道がない。
- **4（外部のサービス）**：題材の主な論点を設計しないことになる。見える範囲の絞り込みを、サービスの中で強制できない。

## Consequences

- 良くなること：
  - 安全と法令の判定が、ML の変更に左右されない。
  - S1 は小さく始め、モデルを段の中で差し替えて育てられる。
  - おすすめが落ちても、ホームは時刻の順で出る。
- 引き受けるコスト：
  - S1 のおすすめの質は、本家より低い。K8 の基準と A/B で評価する。
  - 段ごとの予算と代わりの並びの経路が増え、試験が要る。
  - 学習（Python）と推論（TypeScript）の特徴のずれを防ぐ仕組みが要る（S2 の前に ranking-and-recommendation の領域で決める）。
  - 推薦に閲覧の履歴を使うことの説明と同意は、法務の確認（L4）待ち。

## Confirmation

- 性質ベーステスト：任意の候補・点（悪意のある点、NaN、無限大を含む）に対して、返した投稿はすべて `visible()` が `show` を返す。点がどう変わっても、ブロック・鍵・措置の投稿が出ない。
- 結合テスト：スコアの段を落とす・遅らせると、代わりの並びが予算の中で返る。
- CI：ランキングの変更の PR は、オフラインの評価の結果（前のバージョンとの比較）を添えないと失敗する。
- lint：`packages/ranking` の段の外で、`visible()` の結果を上書きする処理を禁止する。混ぜ合わせの段の後に `visible()` を呼んでいない経路を、型（`Visible<Post>`）で防ぐ。
- 本番：代わりの並びで返した割合、段ごとの遅延、ガードレールの指標を計測し、アラートにする。
