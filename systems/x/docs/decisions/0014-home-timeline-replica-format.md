# ADR-0014: ホームの写しは、32 バイトの項目を ID の降順に詰めた Valkey の文字列にし、挿入・合わせ・除去を Valkey Functions で行う。返信の項目は 4 つ目の欄に返信先の利用者を入れる

## Context

[ADR-0003](0003-timeline-fanout-hybrid.md) は、ホームの写しを利用者ごとに最大 800 件、項目を `(post_id, author_id, repost_of_id, flags)` の 4 つの 64 ビットとし、形（ソート済みの集合か、詰めたバイナリの列か）をこの領域に任せた。

- 記憶の量：S1 でアクティブな利用者 100 万人、S3 で 4,000 万人。800 件の写しの記憶が Valkey の大部分を占める。
- 書き込み：S1 の瞬間のピークで 1 秒 30 万件の挿入。仕事の順は前後し、同じ項目が 2 回来る。
- 読み出し：ID の降順に 20〜200 件を、`max_id` から読む。
- ホームに出す返信は、返信先の利用者で決める（[timeline-fanout.md](../architecture/timeline-fanout.md) の 6.4 節）。項目に返信先がないと、読み出しのたびに投稿の本体を引く必要がある。

## Options

1. **詰めた文字列。** 頭 16 バイト＋項目 32 バイト × 800。ID の降順。Valkey Functions で二分探索の挿入、切り詰め、合わせ、除去を行う
2. **ソート済みの集合（Sorted Set）。** 要素は 24 バイトの詰めた値、点は `post_id`
3. **リスト（List）。** 先頭に足し、順はクライアントの側で直す

## Decision

1 を採用する。`fanout-poc` で、1 が CPU か遅延の点で目標に届かなければ 2 に替える（この ADR を更新する）。

- 項目は `post_id`・`author_id`・`ref_id`・`flags`（各 64 ビット、ビッグエンディアン）。`ref_id` は、リポストなら元の投稿の ID、返信なら返信先の利用者の ID。投稿はリポストと返信を兼ねないので、1 つの欄で足りる。
- 頭は形の版、状態（`ready`・`building`・`partial`）、件数、作った時刻。
- Functions：`tl_insert`（鍵があるときだけ）、`tl_begin`、`tl_merge`、`tl_remove`、`tl_remove_author`、`tl_read`。どれも同じ `post_id` を 1 つにまとめ、ID の降順と 800 件の上限を保つ。
- 形の版を頭に持ち、形を変えるときは、読み手が両方の版を読めるようにしてから書き手を替える。
- 2 を採らない理由：Sorted Set は要素ごとに数十バイトの上乗せ（スキップリストと辞書）があり、800 件で 2〜3 倍の記憶になる見込み（**未検証**。PoC で測る）。S3 の写しの記憶（1 の形で約 1 TB）が倍以上になる。
- 3 を採らない理由：順の前後する挿入と重複を、読み出しのたびに直す必要がある。

## Consequences

- 良くなること：
  - 記憶の量が項目の大きさにほぼ等しい（S1 で約 26 GB）。
  - 挿入・合わせ・除去が 1 回の呼び出しで原子的に済む。
  - 返信の規則を、投稿の本体を引かずに判定できる。
- 引き受けるコスト：
  - Functions のコード（Lua）を持ち、Valkey の版の更新のたびに試験する。Functions の読み込みを、クラスタの全ノードへの配備の手順に入れる（`delivery.md`）。
  - 挿入は 25.6 KB の中の移動を伴う。1 秒 30 万件で Valkey の CPU が足りるかを PoC で測る。
  - 写しの中身を Valkey の道具で直接読めない。調べる道具（読み出しの関数）を用意する。

## Confirmation

- 性質ベーステスト：PROP-TL-004（降順、重複なし、800 件以下）を、メモリーの実装と本物の Valkey の Functions の両方で、同じ列に対して同じ結果になることで確かめる。
- 負荷試験（`fanout-poc`）：1 と 2 で、1 秒 30 万件の挿入の CPU、記憶の量、`tl_read` の p99 を比べ、結果を記録する。
- lint：`tl:` の鍵に Functions 以外の命令で書くことを禁止する。
