# ADR-0053: データを種類ごとの保持の方針の表で管理し、法令に関わる種類は法務の値が入るまで物理の削除を止める。削除は墓石から後始末を経て物理の削除へ進み、法的な保全で止まる

## Context

- 保持の期間（削除した投稿・DM・凍結したアカウント・措置・通報・出来事のログ・閲覧の履歴）は法務の確認待ち（[intent.md](../intent.md) の L8）。開示に使うログは L2。
- 発信者情報の開示に使うログを、勝手に消さない・増やさない（AGENTS.md）。消去の禁止の命令への対応も要る（L2）。
- 措置は取り消せる形で持ち、物理の削除は保持の期間の後のジョブだけが行う（AGENTS.md）。
- 削除の後も、写し・検索の索引・CDN・データレイク・バックアップに残りうる。

## Options

1. **種類ごとの保持の方針の表と、墓石 → 後始末 → 物理の削除の流れ。法務の値が未定の種類は物理の削除を止める。法的な保全で止める**
2. 削除の時にすぐ物理の削除をする
3. 何も消さない（法務の値が出るまで設計しない）

## Decision

1 を採用する。詳細は [security.md](../architecture/security.md) の 7 節。

- `retention_policies` に種類ごとの値・根拠・決めた日を持ち、値は `retention.*` で読む。法務の確認待ちの種類は `retention.<種類>.enabled = false` にしておき、値が決まったらその種類だけを有効にする。
- 技術で決まる種類は値を決める：アプリのログ 30 日、Kinesis 7 日、写しは TTL。
- 削除は、墓石（`deleted_at` と outbox）→ `visible()` が即座に `hide` → 消費者が写し・索引・通知・CDN・数を後始末 → 保持の期間の後に物理の削除のジョブ。
- `legal_holds` のある対象は、墓石までで止め、物理の削除をしない。保全の作成と解除は監査ログに書く。
- バックアップは 35 日で切れる。これを削除の説明に含める（文言は法務の確認）。バックアップから戻すときは、墓石を当て直す。
- 2 を採らない理由：開示の請求・保全の要請に応えられない。取り消せる措置の規則にも反する。
- 3 を採らない理由：削除の流れを後から足すと、写し・索引・データレイクの全部に手を入れ直すことになる。

## Consequences

- 良くなること：
  - 法務の値が決まっても、設定の値と有効の印を変えるだけで済む。
  - 開示・保全の手続きと、本人の削除の求めが 1 つの流れの上で両立する。
- 引き受けるコスト：
  - 値が決まるまで、法令に関わる種類のデータが溜まる（保存の量と、漏えいの時の影響）。
  - 削除の後始末の消費者が、各領域に要る。

## Confirmation

- 表駆動テスト：DT-SEC-001（種類 × 方針 × 保全 → 消すか）。
- 性質ベーステスト：PROP-SEC-001（保全のかかった対象は物理の削除をされない）。
- 本番：`retention.*.enabled` の一覧を四半期に法務の確認の記録と突き合わせる。
