# ADR-0007: フォローの関係は、向きの違う 2 つの隣接の表を正本にし、同じトランザクションで書く。グラフ DB を使わない

## Context

フォローの関係は、この題材の多くの読み出しの元になる。

| 読み出し | 向き | 量 |
| --- | --- | --- |
| fan-out：作者のフォロワーを全部たどる | される側 → する側 | 作者のフォロワーの数（最大 S3 で 5,000 万） |
| 写しの作り直し、プルの作者の一覧 | する側 → される側 | 1 人のフォローの数（多くて数千） |
| 「A は B をフォローしているか」（鍵アカウントの判定、返信の制限、DM の申請） | 1 本の辺 | 読み出しのたびに多数 |
| フォロー中・フォロワーの一覧（ページング） | 両方 | 画面と API |
| フォロワーの数・フォローの数 | 両方 | 表示のたび |
| おすすめの特徴（相互フォロー、2 歩先） | 両方 | ランキングのたび |

辺の数は、S1 で 6,000 万、S3 で 100 億（[architecture/README.md](../architecture/README.md) の 2 節）。ブロックとミュートも、同じ形の辺である。

本家は、フォローの関係を専用のグラフの保存の仕組みで持ってきた（具体は公式の資料で確かめておらず未検証）。

## Options

1. **Aurora に、向きの違う 2 つの隣接の表を持つ。** `following(src, dst)` と `followers(dst, src)` を同じトランザクションで書く。S2 で利用者の ID で分割する
2. **Aurora に 1 つの表と、逆向きの索引**（`follows(src, dst)` に `(dst, src)` の索引）
3. **グラフ DB**（Amazon Neptune）
4. **キーと値の保存**（DynamoDB の隣接の項目）

## Decision

1 を採用する。

### 形

- `following(src_id, dst_id, state, created_at)`：主キー `(src_id, dst_id)`。する側から見た辺。
- `followers(dst_id, src_id, state, created_at)`：主キー `(dst_id, src_id)`。される側から見た辺。
- `state` は `active`・`pending`（鍵アカウントへの申請）。ブロックとミュートは別の表（`blocks`・`mutes`）で同じ 2 つの向きを持つ（ミュートは本人だけの表。[ADR-0004](0004-single-tenant-and-visibility.md)）。
- **2 つの表を同じトランザクションで書く**（S2 で分割した後は下の「分割」）。outbox にも同じトランザクションで出来事を書く（[ADR-0005](0005-event-log-and-outbox.md)）。
- 一覧は `(src_id, created_at DESC)`・`(dst_id, created_at DESC)` の順でページを送る。
- **数は写し**：`user_counters(user_id, followers, following)` を出来事から集計して持つ。照合のジョブで数え直す（カウンターと同じ扱い）。

### 「A は B をフォローしているか」

- 読み出しのたびに DB を引かない。閲覧者ごとの「承認済みのフォロー先の鍵アカウントの集合」「ブロックの集合」を Valkey に写しとして持つ（[ADR-0004](0004-single-tenant-and-visibility.md)）。
- 1 本の辺の確かめは `following` の主キーで引く。Valkey の写しは出来事で無効にする。

### 分割（S2・S3）

- `following` は `src_id`、`followers` は `dst_id` で分割する。どちらの向きの読み出しも、1 つの分割で済む。
- 分割の後は、2 つの表が別の DB にありうる。書き込みは、**`following` を正本** にして先に書き（outbox を含む）、`followers` は出来事から非同期に作る。`followers` は遅れうるが、fan-out の遅れ（NFR-002）の中に収める。照合のジョブで 2 つの表の差を測る。
- 分割の数と方式は follow-graph の領域で、S1 の計測の後に決める。

### 他の案を選ばなかった理由

- **2（1 つの表と逆向きの索引）**：S1 では同じ働きをするが、S2 で分割すると、逆向きの索引が全分割にまたがる。最初から 2 つの表にしておけば、分割の時に形を変えずに済む。
- **3（グラフ DB）**：この題材の読み出しの大部分は「1 歩の隣接の一覧」と「1 本の辺の有無」で、グラフ DB の深い辿りは要らない。2 歩先（おすすめ）は、オフラインの集計で足りる。運用する DB の種類が増える。
- **4（DynamoDB）**：大きな作者のフォロワーの一覧（数千万件）のページングと、出来事の outbox を同じトランザクションで書くことが難しい。他の題材と同じ Aurora で、型・マイグレーション・試験の道具を揃える。

## Consequences

- 良くなること：
  - fan-out も写しの作り直しも、1 つの分割を順に読むだけで済む。
  - 共通の基盤（Aurora、outbox）の中で作れる。
- 引き受けるコスト：
  - 辺を 2 回書く。保存の量が倍になる（S3 で辺 100 億 × 2）。
  - S2 で分割した後、`followers` が遅れる。フォローの直後に、相手のフォロワーの一覧に出ない時間がある。
  - 大きな作者のフォロワーの一覧の読み出し（fan-out）が、1 つの分割に集中する。プル（[ADR-0003](0003-timeline-fanout-hybrid.md)）で fan-out の対象から外すので、集中は閾値 `T` 未満の作者に限られる。

## Confirmation

- 性質ベーステスト：任意のフォロー・解除・申請・承認・ブロックの列の後、`following` と `followers` が互いの逆になる（S2 の非同期の後は、出来事を全部当てた後に）。
- 結合テスト：同じ 2 人の間の同時のフォローと解除で、辺が 1 本か 0 本に定まる。
- 本番：照合のジョブで、2 つの表の差と、数の写しの差を測る。
