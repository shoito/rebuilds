# ADR-0050: タイムラインの一覧は、アプリは FlashList、Web は自前の仮想化で描き、落ちたフレームを固定の端末と RUM で測る。基準を 2 回の改善で満たせない画面だけ、ネイティブの一覧の部品にする

## Context

- [ADR-0001](0001-platform-and-stack.md) は、React Native のタイムラインのスクロールの滑らかさが足りないときは、該当の画面だけネイティブの部品にし、clients の領域で ADR を書くとした。
- タイムラインは、本文の長さ、画像の枚数、動画、引用、リポストで項目の高さが大きく変わる。高さが描画の後に決まると、スクロールの位置が跳ねる。
- 日本の利用者には、数年前の中位の Android の端末が多い（**未検証**。RUM で確かめる）。

## Options

1. **アプリは FlashList（項目の部品の使い回し）、Web は自前の仮想化。高さは投稿の形から先に見積もる。基準を決め、満たせない画面だけネイティブ**
2. 最初からタイムラインの一覧をネイティブの部品（Swift・Kotlin）で作る
3. React Native の標準の `FlatList`

## Decision

1 を採用する。詳細は [clients.md](../architecture/clients.md) の 5 節。

- 項目の種類（本文だけ、画像 1 枚、2〜4 枚、動画、引用、リポスト、返信の連なり）で部品を使い回す。高さは本文の重み付きの長さとメディアの縦横の比から計算し、画像の枠を先に取る。
- 基準：基準の端末（Android の 4 年前の中位の機種、iOS の 3 つ前の世代）で、200 件のスクロールの落ちたフレームが p75 1% 以下・p95 5% 以下。CI の固定の端末と、RUM（端末の 10%）で測る。
- 基準を外した画面に、項目の部品の軽量化と、画像の取り込み・高さの見積もりの見直しの 2 回の改善をしても満たせないとき、その画面の一覧だけを Expo の module で包んだネイティブの一覧の部品にする。置き換えは ADR を足して記録する。
- 2 を採らない理由：同じ画面を 3 回（Web、iOS、Android）作ることになり、ADR-0001 の判断に反する。必要になってから、必要な画面だけにする。
- 3 を採らない理由：部品を使い回さず、長い一覧で記憶と描画の負荷が大きい。

## Consequences

- 良くなること：
  - 画面の作りを Web とアプリで近く保ち、ネイティブの作業を本当に要る所に限る。
  - 滑らかさが数で判定でき、置き換えの判断が人の感覚に寄らない。
- 引き受けるコスト：
  - 固定の端末の CI の運用（[delivery.md](../architecture/delivery.md) の 2.3 節）。
  - 高さの見積もりの誤りで位置が跳ねる不具合の試験。

## Confirmation

- CI：一覧の画面に触れる PR で、固定の端末の落ちたフレームを測り、基準を超えたら失敗。
- 本番：RUM の `client.scroll_dropped_frames` を版・機種の帯ごとに見る。
