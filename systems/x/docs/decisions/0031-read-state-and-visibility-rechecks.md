# ADR-0031: 通知の既読は受け手ごとの 1 本の位置で持ち、未読の数は Valkey の写しで数えて Realtime Gateway で届ける。見える範囲は、作る時・送る時・読む時の 3 回判定する

## Context

通知の一覧には、未読の数（バッジ）と既読の表示が要る。利用者は複数の端末を持つ。通知の行は、殺到の受け手で 1 分に数千件増える。

見える範囲は読み出しの時に判定する（[ADR-0004](0004-single-tenant-and-visibility.md)）。通知には 3 つの時点がある。

- 作る時：作らないほうがよいもの（ブロックした人からのいいね）を作らない。行の数を減らす。
- 送る時：プッシュは取り消せない（[ADR-0030](0030-push-and-email-delivery.md)）。
- 読む時：作った後に削除・措置・ブロックが起きる。

## Options

既読：

1. **受け手ごとの 1 本の位置（`last_seen_at`）。位置より新しい行が未読**
2. 行ごとの既読の印

未読の数：

- a. **Valkey の写し（`nu:`）を足し引きし、なければ Aurora で数え直す（100 件で打ち切り）**
- b. 毎回 Aurora で数える

見える範囲：

- x. **作る時・送る時・読む時の 3 回**
- y. 読む時だけ

## Decision

1、a、x を採用する。詳細は [notifications.md](../architecture/notifications.md) の 4.2・6.2・7 節。

- 位置はクライアントが一覧の先頭の時刻を送って進める。戻さない。全端末で共通。
- 未読の数の変化は Valkey の pub/sub で Realtime Gateway に送る。
- 読む時は、元の投稿に `visible()`（`surface = notifications`）、行為者にブロック・ミュート・凍結を判定し、出さない行のうち恒久の理由のものを `hidden` にする。
- 2 を採らない理由：殺到の受け手で、行ごとの既読の更新が行の数だけ要る。本家の画面の形（一覧を開くと全部が既読）にも合わない（本家の形は未検証）。
- b を採らない理由：未読の数はアプリの起動と画面の切り替えのたびに読まれ、Aurora の数え上げが重い。
- y を採らない理由：作る時の判定がないと、ブロックした人の通知の行が溜まり、未読の数に入る。送る時の判定がないと、取り消せないプッシュが漏れる。

## Consequences

- 良くなること：
  - 既読の更新が 1 行で済む。
  - 未読の数が速く、端末の間でそろう。
  - どの時点の変化でも、見てはいけない通知が出ない。
- 引き受けるコスト：
  - 個々の通知を「未読に戻す」ことはできない。
  - 未読の数の写しは、読む時の判定で出さない行を含みうる（数が実際の行より多い）。一覧を開いたときに位置を進めて 0 に戻る。差は計測する。
  - 3 回の判定の費用（写しの読み出し）。

## Confirmation

- 性質ベーステスト：PROP-NOTIF-003（位置が減らない、未読の数の再計算の一致）。
- 結合テスト：漏れの経路の表の「通知」の行を、作る時・送る時・読む時のそれぞれの直前に、ブロック・削除・措置を入れて確かめる。
- 本番：未読の数の写しと再計算の差、読む時に出さなかった行の数（理由ごと）を計測する。
