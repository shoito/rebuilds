# ADR-0023: `engagement` の流れの鍵を「投稿の ID と利用者の ID の下 3 ビット」にし、数の写しは Valkey の投稿ごとのハッシュに部分ごとの最後の連番を持って Function で冪等に足す。返信・引用の数も投稿の書き込みが `engagement` の流れへ出す。書き戻しは 60 秒、照合は静かな投稿で数え直す

## Context

[ADR-0005](0005-event-log-and-outbox.md) は、数の写しを Counter Aggregator が作り、結果とシャードの読み終わりの位置を「同じ `MULTI` で書く」と決め、細部（殺到する投稿の分割など）をこの領域に任せた。詰めると次の問題がある。

- **Valkey のクラスタでは、`MULTI` は同じスロットの鍵にしか使えない。** 投稿ごとの数の鍵と、シャードの位置の鍵は別のスロットにある。1 つのシャードは多くの投稿の出来事を運ぶので、「結果と位置を同じ `MULTI`」は、全部の鍵を 1 つのスロットに寄せない限りできない（寄せると Valkey を分けられない）。
- **殺到する投稿**：ADR-0005 の鍵（投稿の ID）では、1 つの投稿の出来事が 1 つのシャードに集まる。Kinesis のシャードの書き込みは 1,000 レコード/秒・1 MB/秒が上限（[AWS の文書](https://docs.aws.amazon.com/streams/latest/dev/service-sizes-and-limits.html)、2026-10-04 に確認）。
- **返信・引用の数**：`posts` の流れは作者の ID で分けるので、1 つの投稿への返信の出来事が多くのシャードから届く。投稿ごとの位置で冪等にできない。
- Relay は少なくとも 1 回届けるので、送信の後に落ちると、同じ出来事が新しい連番で届く。

## Options

1. **鍵を `"{post_id}:{sub}"`（`sub = user_id mod 8`）にし、投稿ごとのハッシュに `sub` ごとの最後の連番を持って、Function で「連番が新しいときだけ足す」。返信・引用の数の出来事も `engagement` の流れに同じ鍵で出す。Relay の重複は照合で直す**
2. 出来事の ID ごとの重複の印を、数の鍵と同じスロットに持つ（`{post_id}` のハッシュタグ）
3. 全ての数の鍵を、シャードごとに 1 つのスロットに寄せ、ADR-0005 のとおり `MULTI` で書く
4. 数を Aurora で直接足す（`UPDATE ... SET likes = likes + n`）

## Decision

1 を採用する。詳細は [engagement-and-counters.md](../architecture/engagement-and-counters.md) の 4 節。ADR-0005 の「同じ `MULTI`」と、`engagement` の鍵（投稿の ID）を、この ADR で置き換える。

- `pc:{post_id}` に、数・`l0`〜`l7`（`sub` ごとの最後の連番）・`s0`〜`s7`（シャードの ID）・`t`（最後の更新）を持つ。`cnt_apply` は、同じシャードで連番が `l{sub}` 以下なら何もしない。シャードが変わったら受ける（親のシャードを読み終えてから子を読む順に頼る）。
- Aggregator は 1 秒ぶんを投稿と `sub` ごとにまとめてから `cnt_apply` を呼び、全部が済んでからシャードの位置を記録する。
- Relay は同じ分ける鍵の出来事を 1 レコードに最大 50 件束ねる。1 投稿の上限はおよそ 4 万件/秒。
- 投稿の書き込みは、返信・引用のときに `reply.added`・`quote.added` を `engagement` の流れに書く（[ADR-0008](0008-post-write-path-and-idempotency.md) のトランザクションの中）。
- 書き戻しは 60 秒ごとに絶対の値と連番を `post_counters` へ。Valkey を失ったら、`post_counters` から入れ、最後の書き戻しの 2 分前から読み直す。
- 照合は、静かな投稿（5 分）を毎時の抜き取りと上位 1,000 件、週ごとの全件で数え直し、差を `cnt_set` で直して記録する。
- 2 を採らない理由：重複の印が出来事ごとに要り、S1 のいいねだけで 1 日 5,000 万件 × 7 日の印になる。
- 3 を採らない理由：数の鍵がシャードの数のスロットに集まり、Valkey を分けられない。
- 4 を採らない理由：人気の投稿の行に更新が集中し、行のロックで待つ。

## Consequences

- 良くなること：
  - 消費者の再起動・持ち主の交代・読み直しで 2 回足さない。
  - 1 つの投稿の出来事が最大 8 シャードに分かれ、殺到に耐える。
  - 数の出来事がすべて 1 つの流れ（`engagement`）にそろう。
- 引き受けるコスト：
  - Relay の重複（まれ）は照合まで残る。K4 の「照合の後、差 0」は満たすが、照合の前は一時的に多い。
  - ADR-0005 の鍵の表と「同じ `MULTI`」の記述から外れる。ADR-0005 の更新は Dev（テックリード）の判断に回す。
  - シャードの分割の後の連番の扱いに、KCL の順への依存が入る（AWS の保証の書き方は未検証）。

## Confirmation

- 性質ベーステスト：PROP-CNT-001（冪等と収束）、PROP-CNT-002（照合で戻る）、PROP-CNT-003（書き戻しの冪等と Valkey の喪失）。
- 結合テスト：LocalStack の Kinesis でシャードを分けた後、数が正本と一致する。
- 負荷試験：1 投稿へのいいね 1 万件/秒を 1 分。
- lint：`pc:`・`uc:` に `cnt_apply`・`cnt_set` 以外で書くことを禁止する。`post_counters` に書き戻しと照合のジョブ以外が書くことを、DB のロールで禁止する。
