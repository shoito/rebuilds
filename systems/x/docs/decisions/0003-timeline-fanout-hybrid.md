# ADR-0003: ホームのタイムラインは、フォロワーの少ない作者はプッシュ、多い作者はプルで作る

## Context

ホーム（フォロー中）は、フォローしている人の投稿を新しい順に並べる。読み出しは書き込みよりずっと多い（S1 で読み出しのピーク 1 万件/秒に対し、投稿のピーク 300 件/秒。[architecture/README.md](../architecture/README.md) の 2 節）。読み出しを p99 300ms で返す（NFR-003）。投稿は p95 5 秒・p99 30 秒でフォロワーのホームに出す（NFR-002）。

作り方には 2 つの極がある。

- **プッシュ（書くときに配る）**：投稿のたびに、全フォロワーのタイムラインの写しへ書く。読み出しは写しを読むだけで速い。フォロワーが 1,000 万人の作者の 1 件の投稿で、1,000 万件の書き込みになる。
- **プル（読むときに集める）**：読み出しのたびに、フォローしている全員の最近の投稿を集めて並べる。書き込みは 1 件で済む。2,000 人をフォローする人の読み出しで、2,000 人ぶんを集めることになる。

フォロワーの数の分布は大きく偏る。大部分の作者のフォロワーは数百人以下で、ごく一部が数百万人を持つ。本家は、書くときにフォロワーのメモリーの中のタイムラインへ配り、フォロワーの多い作者は読むときに合わせる形を説明している（2012 年の講演 [Timelines at Scale](https://www.infoq.com/presentations/Twitter-Timeline-Scalability)。具体の数値は本文で確かめておらず未検証。2026-10-04 に確認）。

もう 1 つの偏りは、読む人の側にある。登録した利用者の多くは、毎日は読まない。読まない人の写しへ配る書き込みは、無駄になる。

## Options

1. **すべてプッシュ**（全フォロワー、読まない人を含む）
2. **すべてプル**
3. **組み合わせ：フォロワーの少ない作者はアクティブなフォロワーへプッシュ、多い作者はプル。** 読む人は、写しと、フォローしているフォロワーの多い作者の最近の投稿を合わせる
4. **組み合わせ（3）に加えて、フォロワーの多い作者の投稿を、とくにアクティブなフォロワーにだけ遅れてプッシュする**

## Decision

3 を採用する。4 は、3 の上で必要になったら足す（timeline-fanout の領域で、計測の後に ADR を書く）。

### 写しの形

- **ホームのタイムラインの写し**（`tl:{viewer_id}`）：Valkey に、利用者ごとに最大 800 件の項目を、投稿の `tid` の降順で持つ。項目は `(post_id, author_id, repost_of_id, flags)` の 4 つの 64 ビット（`flags` は返信・リポスト・引用の印）。投稿の本文は持たない。
  - 形（ソート済みの集合か、詰めたバイナリの列を Valkey Functions で挿入するか）は、記憶の量を測って timeline-fanout の領域で決める。
- **作者の最近の投稿**（`ar:{author_id}`）：全作者に、直近 7 日・最大 200 件の項目を持つ。プルの合わせ、写しの作り直し、プロフィールの一覧に使う（[ADR-0015](0015-fanout-pipeline-and-burst-control.md)、[ADR-0016](0016-timeline-rebuild-single-flight.md)）。
- どちらも **写しであり、正本ではない。** 正本は Aurora の投稿の表と、フォローの表（[ADR-0007](0007-follow-graph-storage.md)）である。写しが消えても、正本から作り直して同じ並びになる。

### プッシュとプルの分け方

- 作者のフォロワーの数が **閾値 `T` 未満ならプッシュ、`T` 以上ならプル**。S1 の既定は `T = 10,000`。値は AppConfig の `ops.fanout.pull_threshold` で持つ。
- 切り替えのばたつきを防ぐため、プルからプッシュへ戻すのは `0.8 T` を下回ったときにする（履歴の効果）。作者の方式は `users.fanout_mode` に持ち、Graph が数の変化で更新する。
- 切り替えの時に、過去の投稿を配り直したり消したりしない。読み出しで、写しとプルの結果を合わせ、投稿の ID で重複を落とす。どちらの方式の時の投稿も、必ずどちらかの経路で見つかる（下の性質）。

### プッシュ（Fanout Worker）

1. Post が投稿を確定し、outbox から出来事のログへ流れる（[ADR-0005](0005-event-log-and-outbox.md)）。
2. Fanout の振り分け役が投稿の出来事を読み、作者がプッシュなら、フォロワーの一覧を 1,000 人ずつのページに分けて、ページごとに SQS の仕事を作る。
3. Fanout Worker は、ページの中の **写しを持っている利用者（アクティブな利用者）にだけ** 書く。写しは最後の読み出しから 30 日で期限が切れるので、写しがあることがアクティブの印になる。読まない人へは書かない。
4. 書き込みは、Valkey へのパイプラインで束ね、挿入の後に 800 件へ切り詰める。項目は ID の順の位置に入れるので、仕事の順が前後しても並びは正しい。
5. 仕事は冪等にする。同じ投稿の同じページを 2 回処理しても、同じ項目は 1 つにまとまる。

### プル（Timeline）

- 読み出しの時に、写し（最大 800 件）と、その利用者がフォローしているプルの作者の `ar:{author_id}` を、ID の降順で合わせる（k 個の列の合併）。
- 利用者ごとの「フォローしているプルの作者」の一覧は、Graph から得て短い時間の写しに持つ。プルの作者は少数（S1 で数百人）なので、1 人がフォローするプルの作者は多くても数百人である。
- プルの作者の投稿は、確定の後すぐ `ar:` に入るので、次の読み出しで見える（NFR-002 の中に収まる）。

### 読み出し（フォロー中）

1. 写しとプルの列を合わせる。写しがなければ作り直す（下）。
2. 投稿の本文と状態を、投稿の写し（Valkey、なければ Aurora）から付ける。
3. **`visible(viewer, post)` で絞る**（[ADR-0004](0004-single-tenant-and-visibility.md)）。削除・措置・ブロック・ミュート・鍵アカウントの判定は、ここで毎回行う。写しに入った時の判定に頼らない。フォローを外した作者の項目も、ここで落とす。
4. 絞った後で 20 件に足りなければ、続きを読む。1 ページのために読む項目の上限を決め（既定 200）、超えたらそこまでで返す。

### 写しの作り直し

- 写しがない（30 日以上読んでいない、Valkey のノードを失った、DR で切り替えた）ときは、フォローしている作者の `ar:` を合わせ、`ar:` のない作者だけ Aurora の `(author_id, id DESC)` の索引から集めて、800 件を作る（詳細は [ADR-0016](0016-timeline-rebuild-single-flight.md)）。
- 同じ利用者の作り直しは 1 回にまとめる（single flight）。フォローが多い利用者（2,000 人超）は、直近 3 日に絞る。
- 作り直しの目標は p99 2 秒（NFR-003）。作り直しが殺到したら（DR の後など）、作り直しの範囲を狭めて先に返し、残りを後で埋める。

### 後始末

| 出来事 | 写しへの扱い |
| --- | --- |
| 投稿の削除・措置 | 読み出しの `visible()` で即座に落とす。写しからの除去は、出来事から遅れて行う（後始末であって、正しさの条件ではない） |
| フォローの解除・ブロック | 読み出しで落とす。写しから作者の項目を遅れて除く |
| 新しいフォロー | 新しく追った作者の直近 50 件を、遅れて写しへ入れる（プッシュの作者のとき） |
| 閾値をまたいだ作者 | 何もしない。読み出しの合わせで重複を落とす |

### 他の案を選ばなかった理由

- **1（すべてプッシュ）**：フォロワー 1,000 万人の作者の 1 件で 1,000 万件の書き込み。瞬間のピークに重なると、キューが溜まって NFR-002 を外す。読まない利用者への書き込みも無駄になる。
- **2（すべてプル）**：読み出しのたびに数百〜数千の作者の列を集める。読み出しのピーク（S3 で 80 万件/秒）に、作者ごとの読み出しが掛け算で乗る。NFR-003 の p99 300ms を守れない。

## Consequences

- 良くなること：
  - 書き込みの量の上限が、閾値 `T` とアクティブなフォロワーの数で決まる。フォロワーの多い作者の投稿で爆発しない。
  - 読み出しは、写しと少数のプルの列の合わせで済む。
  - 写しは作り直せるので、Valkey の障害がデータの喪失にならない。
- 引き受けるコスト：
  - 読み出しの経路が、写し・プル・作り直しの 3 つになり、試験の組み合わせが増える。
  - `T` の付近の作者で、読み出しのプルの列が増える。`T` は、書き込みの量と読み出しの遅れの釣り合いで決める必要があり、E5 の PoC で測る。
  - 久しぶりの利用者の最初の読み出しが遅い（作り直し）。
  - 写しに入った時から読み出しまでに状態が変わるので、読み出しで毎回 `visible()` の費用を払う。投稿の写しと、閲覧者ごとのブロック・ミュートの集合の写しで抑える。

## Confirmation

- 性質ベーステスト：任意の投稿・フォロー・解除・閾値の変更（またぎを含む）・写しの喪失の列に対して、フォロー中の読み出しは「その時点でフォローしていて、見てよい作者の投稿」を、ID の降順で、重複なく、抜けなく（800 件と 7 日の範囲の中で）返す。作り直した写しと、プッシュで作った写しは、同じ並びになる。
- 結合テスト：Fanout Worker の仕事の重複・順の入れ替え・途中の失敗の後で、写しが同じになる。
- 負荷試験：瞬間のピーク（S1 で投稿 3,000 件/秒、うちフォロワー 100 万人の作者の連投を含む）で、NFR-002 の p99 30 秒。
- 本番：合成監視の組（監視用の作者と、プッシュ・プルの両方の監視用のフォロワー）で、投稿からホームに出るまでの時間を常に測る。
- lint：閾値の数値をコードに書くことを禁止する（`ops.fanout.*` から読む）。
