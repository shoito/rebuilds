# ADR-0002: 投稿・利用者・DM のメッセージに、時刻の順に並ぶ 64 ビットの `tid` を振る

## Context

投稿の ID は、この題材のほとんどの部品が使う。

- **タイムラインの写し**：ホームのタイムラインは、利用者ごとに投稿の ID の並びを Valkey に持つ（[ADR-0003](0003-timeline-fanout-hybrid.md)）。S1 でアクティブな利用者 100 万人 × 800 件、S3 で 4,000 万人 × 800 件になる。ID の大きさが、そのまま記憶の量になる。
- **時刻の順**：フォロー中のタイムラインは時刻の順に並べる。プッシュの写しと、プルの作者の最近の投稿を合わせるとき、ID で並べられれば、時刻の列を別に持たなくてよい。
- **ページング**：「これより新しい」「これより古い」を ID の範囲で表せる。本家の公開 API も、ID の範囲でページを送る引数（`since_id`・`until_id`）を持つとされる（公式の文書の該当の箇所は確かめておらず**未検証**）。
- **書き込みの速さ**：瞬間のピークで S3 は 1 秒 15 万件の投稿を受ける（[architecture/README.md](../architecture/README.md) の 2 節）。ID の採番に、1 か所の DB の連番を通すと、そこが詰まる。
- 共通の基盤は ID を UUIDv7 にしている。UUIDv7 も時刻の順に並ぶが、128 ビットである。

本家は、41 ビットのミリ秒の時刻、10 ビットの機械の番号、12 ビットの連番の 64 ビットの ID を、調整なしで振る方式を 2010 年に公開した（[snowflake（2010 年の版）](https://github.com/twitter-archive/snowflake/tree/snowflake-2010)、2026-10-04 に確認）。今の実装は未検証。

## Options

1. **64 ビットの時刻の順の ID（`tid`）を、サービスの中で振る。** 生成器の番号は DB の貸し出しで得る
2. **UUIDv7**（共通の基盤のまま）
3. **DB の連番**（Aurora の `bigserial`）
4. **64 ビットの ID の中に、分割の番号を入れる**（時刻 41 ビット＋分割 13 ビット＋連番 10 ビット。分割ごとの DB の連番で振る）

## Decision

1 を採用する。

### 形

```
 63  62                                    22 21          12 11          0
 ┌──┬────────────────────────────────────────┬──────────────┬─────────────┐
 │ 0│ ミリ秒（41 ビット、起点 2026-01-01T00:00:00Z）│ 生成器（10）   │ 連番（12）    │
 └──┴────────────────────────────────────────┴──────────────┴─────────────┘
```

- 符号のビットは 0 にし、PostgreSQL の `bigint` と、他の言語の符号付きの 64 ビットの整数で正の数になるようにする。
- 時刻は独自の起点からのミリ秒。41 ビットで約 69 年もつ。
- 生成器の番号は 0〜1023。**0〜511 を東京、512〜1023 を大阪** に割り当てる。DR で大阪に切り替えても、東京で振った ID と重ならない。
- 連番は、同じ生成器・同じミリ秒の中で 0〜4095。足りなければ次のミリ秒まで待つ（1 生成器で 1 秒 409 万件まで）。
- 形とビットの配分は公開の考え方に寄せたが、生成器のコードは自前で書く（[ADR-0001](0001-platform-and-stack.md)）。

### 対象

| 対象 | ID | 理由 |
| --- | --- | --- |
| 投稿（リポストの行を含む） | `tid` | タイムラインの写し、時刻の順、公開の URL |
| 利用者 | `tid` | タイムラインの写しの作者、フォローの辺の両端。公開の ID |
| DM のメッセージ | `tid` | 会話の中の時刻の順とページング |
| メディア | `tid` | 公開の ID。投稿と同じ扱い |
| その他（通報、措置、通知、セッション、アップロードの作業、会話など） | UUIDv7（共通のまま） | 量が少ないか、写しに並べないため |

### 振り方

- **生成器は、サービスの中のライブラリ**（`packages/tid`）。別の採番のサービスを置かない。ネットワークの往復をなくし、採番のサービスの障害で投稿が止まらないようにする。
- **生成器の番号は、Aurora の `tid_generator_leases` で貸し出す。** 行は `(generator_id, region, holder, expires_at)`。期限は 60 秒、20 秒ごとに延ばす。延ばせないまま `expires_at` の 5 秒前になったら、ID を振るのを止める。
- **前の持ち主と時刻が重ならない。** 新しい持ち主は、前の持ち主の `expires_at` より後のミリ秒からしか振らない。前の持ち主は `expires_at` の前に止まるので、同じ生成器の番号でも、時刻の範囲が重ならない。
- **時計**：Amazon Time Sync Service に合わせる。時計が前の ID のミリ秒より戻ったら、5ms までは待ち、それより大きければ失敗させてアラートを出す。ID を振らないことで重なりを防ぐ。
- **ID の重なりの検出**：投稿の表の主キーで重複を拒否し、拒否はアラートにする（起きてはいけない事象）。

### 順序の保証と、その限界

- `tid` は、生成器の間で **おおむね** 時刻の順である（k-sorted）。生成器の時計のずれ（数 ms）の範囲で、後で振った ID が小さいことがある。
- 確定の順と ID の順も一致しない。小さい ID の投稿が、後から確定することがある。
- したがって、**「最新の ID より新しいもの」を取る読み出しは、重なりの窓を持つ。** フォロー中のタイムラインの新着の確かめは、クライアントの最新の ID から 10 秒ぶん戻した位置（`since − (10,000 << 22)`）から読み、クライアントで重複を落とす。窓の値は timeline-fanout の領域で計測して決める。
- 全体の厳密な順序が要る処理（同じ会話の中の DM の既読の位置など）は、ID ではなく、その処理の中の順序（会話の連番など）で決める。direct-messages の領域で扱う。

### 表に出す形

- 公開 API・画面の API・JSON では **10 進の文字列** で返す（`"id": "1844…"`）。JavaScript の `number` は 53 ビットまでしか正確に持てない。
- TypeScript の中では `bigint` か、ブランド型の文字列（`type PostId = string & { __brand: "PostId" }`）で扱う。
- URL は `https://<brand>.<domain>/<handle>/posts/<id>`。
- ID から作られた時刻が分かる。投稿の作成の時刻は公開の情報なので、隠さない。利用者の ID からは登録の時刻が分かる。これも公開のプロフィールに出す情報と同じ扱いにする。

### 他の案を選ばなかった理由

- **2（UUIDv7）**：16 バイトで、タイムラインの写しの記憶が倍になる（写しの 1 件を投稿・作者・リポストの元の 3 つの ID とすると、24 バイトが 48 バイト）。S3 で 4,000 万人 × 800 件の写しは、64 ビットで約 770 GB、UUIDv7 で約 1.5 TB（Valkey の上乗せを除く）。URL も長くなる。
- **3（DB の連番）**：瞬間のピークで 1 か所に集中し、S2 で表を分けると連番を保てない。
- **4（分割の番号を ID に入れる）**：ID から分割の場所が分かるのは便利だが、分割の数を ID の形に固定し、DB の連番の方式では DR の切り替えで失った範囲の連番を再び振りうる（外の写しや検索の索引に残った ID と重なる）。S2 で投稿の表を分ける鍵は、別に決める（下の「持ち越し」）。

## Consequences

- 良くなること：
  - タイムラインの写しが小さく、ID の大小で並べ、ページを送れる。
  - 採番が投稿のサービスの中で済み、瞬間のピークでも DB の連番に集中しない。
  - DR で大阪に切り替えても、ID が重ならない。
- 引き受けるコスト：
  - 共通の UUIDv7 と、2 種類の ID が混ざる。どの表がどちらかを、データモデルの規約で 1 か所に書く（data-model の領域）。
  - 生成器の番号の貸し出しと時計の監視を運用する。生成器の上限（リージョンごとに 512）が、投稿のサービスのタスクの数の上限になる。足りなくなる前に、1 タスクで複数の番号を持つか、ビットの配分を見直す ADR を書く。
  - ID の順が確定の順と一致しないので、新着の読み出しに重なりの窓が要る。

### 持ち越し

- S2 で投稿の表を分ける鍵（投稿の ID のハッシュと作者ごとの索引の表、作者のハッシュ）：posts-and-ids の領域で、S1 の読み出しの型（ID で 1 件、作者の一覧、会話）の比率を測って決める。

## Confirmation

- 性質ベーステスト：任意の生成器の数・貸し出しの交代・時計の揺れ（戻りを含む）の列に対して、振った ID が重ならない。同じ生成器の中では単調に増える。
- 単体テスト：ビットの配分、起点、リージョンの範囲、10 進の文字列への変換と戻し。
- lint：画面と API の型で、ID を `number` にすることを禁止する。投稿・利用者・DM のメッセージの表に UUIDv7 や連番の既定値を付けることを、マイグレーションの検査で禁止する。
- 本番：主キーの重複による拒否の件数（0 であるべき）と、時計の戻りによる採番の失敗を、アラートにする。
