# ADR-0037: DM のエンドツーエンドの暗号化は MVP の後に入れる。MVP では本文を中身の分からない入れ物として扱い、サーバーが本文を読む機能を作らない。方式の第一の候補は MLS

詳細は [direct-messages.md](../architecture/direct-messages.md) の 11 節。

## Context

- [architecture/README.md](../architecture/README.md) の 6 節は、MVP の DM の暗号化をサーバーの側の保存の暗号化（KMS）だけにし、エンドツーエンドの暗号化は MVP の後（L3 とあわせて決める）とした。[intent.md](../intent.md) は E18 に置いた。
- 本家は 2025 年に、鍵を PIN で守る方式のエンドツーエンドの暗号化を持つ「Chat」へ移ったと報じられている（第三者の報道。本家の文書は**未検証**）。
- MVP の機能が「サーバーが本文を読めること」に頼ると、後で暗号化を入れるときに、その機能を壊すか、暗号化を弱めることになる。
- 暗号化はモデレーション（通報、照合）と両立させる必要がある。

## Options

1. **MVP の後に入れる。MVP では、本文を `body_ct` と `enc_scheme` の入れ物にし、サーバーが本文を読む機能を作らない。通報はクライアントが平文を送る形にしておく**
2. MVP から入れる
3. 入れない（サーバーの側の暗号化だけ）

## Decision

1 を採用する。

- MVP で作らないもの：DM の検索（サーバー）、サーバーでのリンクのカードの生成、中身による迷惑の判定、サーバーでの翻訳・要約。リンクのカードはクライアントで作る。
- `dm_messages.body_ct` と `dm_conversations.enc_scheme`（`server_dek_v1`）を持つ。E18 で `mls_v1` を足し、会話ごとに方式を持つ。
- 通報は、通報する人のクライアントが選んだ平文を送る形（[ADR-0036](0036-dm-consent-requests-and-reporting.md)）。暗号化の後も同じ形で続く。
- 方式の第一の候補は MLS（RFC 9420）。50 人のグループで鍵の更新が速い。鍵の保管（PIN と HSM での預かり）、端末の追加、過去のメッセージの扱い、L3 との両立は E18 で別の ADR に書く。
- 2 を採らない理由：鍵の管理・端末の追加・復旧・通報の両立を MVP で設計しきれない。DM の可用性と配信の速さ（NFR-008）の確認を先にしたい。
- 3 を採らない理由：本家と利用者の期待から離れる。運営が本文を読める状態を続ける理由がない。

## Consequences

- 良くなること：
  - 暗号化を後で入れても、壊れる機能がない。
  - MVP の DM を早く出せる。
- 引き受けるコスト：
  - DM の検索とサーバーのリンクのカードを MVP で出さない。
  - MVP の間は、運営（DM のサービスと KMS の権限）が技術的には本文を復号できる。復号の記録（CloudTrail）と権限の限定で抑える（[ADR-0035](0035-dm-conversation-model-and-storage.md)）。

## Confirmation

- lint：DM のサービスの外で `body_ct` を復号する道を禁止する。DM の本文を入力にする処理（検索の索引、リンクのカードの取得、分類）の追加を、レビューの観点に入れる。
- E18 の着手のときに、この ADR の「作らないもの」が守られていることを確かめる。
