# ADR-0011: フォロー・申請・ブロックの辺を 1 つのステートマシンで扱い、2 人の組ごとの勧告ロックで直列にする。ブロックは同じトランザクションで両向きのフォローと申請を外し、鍵を外したら待っている申請をすべて承認する

## Context

フォローの関係は、`following`・`followers`・`blocks`・`blocked_by` の 4 つの表にまたがる（[ADR-0007](0007-follow-graph-storage.md)）。同じ 2 人の間で、次の操作が同時に起きうる。

- A のフォローと、B の A へのブロック
- A のフォローと解除の連打（二重のタップ、クライアントの再送）
- B の承認と、A の申請の取り消し
- B の鍵の解除と、届いている申請の承認・拒否

行ごとのロックだけでは、4 つの表のうち、まだ行がない表（新しいフォロー、新しいブロック）をロックできない。順序が乱れると、ブロックの後にフォローの辺が残る（`visible()` で隠れるが、数と fan-out の配り先に残る）。

## Options

1. **2 人の組ごとの勧告ロック（`pg_advisory_xact_lock`。鍵は小さい ID と大きい ID の組のハッシュ）を、辺を変える全てのトランザクションの最初に取る**
2. 利用者の行（`users`）を、ID の小さい順に `FOR UPDATE` でロックする
3. 楽観的に書き、一意の制約と再試行に任せる

鍵の解除の時の申請：

- a. **待っている申請をすべて承認する**
- b. 待っている申請をすべて消す
- c. そのまま残す（鍵がないのに申請が残る）

## Decision

1 と a を採用する。詳細は [follow-graph.md](../architecture/follow-graph.md) の 4 節と 5 節。

- 状態は「辺なし」「`pending`」「`active`」の 3 つ。ブロックは別の辺で、ある間は両向きのフォローの辺を持てない。
- フォロー・解除・承認・拒否・取り消し・フォロワーの削除・ブロック・ブロックの解除は、どれも最初に組の勧告ロックを取り、4.3 節の決定表で判定してから書く。
- 同じ状態への書き込み（フォロー済みへのフォロー）は何もせず、出来事も出さない。クライアントの再送が安全になる。
- 辺を変えたら、関わる利用者の `users.graph_version` を上げる（[ADR-0012](0012-viewer-sets-cache.md)）。
- 鍵の解除で、待っている申請を `active` にする。1,000 件を超えるときは 1,000 件ずつのジョブに分ける（ジョブの各回も組のロックを取る）。
- S2 で表が分割された後は、ロックをする側の分割で取り、逆向きの表の変更は出来事から行う（[ADR-0013](0013-graph-partitioning.md)）。
- 2 を採らない理由：利用者の行は、プロフィールの更新や数の書き戻しでも触れる。フォローの殺到する人の行に全員の書き込みが集中し、待ちが長くなる。
- 3 を採らない理由：行のない表の組み合わせ（ブロックとフォローの同時）を一意の制約だけで防げない。
- b を採らない理由：申請した人の意図（フォローしたい）を、相手の設定の変更で無にする。
- c を採らない理由：鍵のない利用者に `pending` の辺が残り、ステートマシンに意味のない状態が増える。

## Consequences

- 良くなること：
  - どの同時の操作でも、結果がどれかの直列の順と等しい。
  - クライアントの再送が冪等になる。
- 引き受けるコスト：
  - 人気の利用者へのフォローの殺到でも、組は別々なのでロックは競合しない。ただし、勧告ロックの表（共有メモリー）の大きさを負荷試験で確かめる。
  - 鍵の解除の一括の承認で、フォロワーの数と fan-out の配り先が一度に増える。ジョブの速さを抑える（1 秒 1,000 件）。

## Confirmation

- 性質ベーステスト：PROP-GRAPH-002（ブロックの排他）、PROP-GRAPH-003（同時の操作）、PROP-GRAPH-005（鍵の承認）。
- 結合テスト：同じ組への同時のフォロー・ブロックを 1,000 回重ね、ブロックの後にフォローの辺が残らない。
- lint：`following`・`followers`・`blocks`・`blocked_by` に書く SQL を、Graph のリポジトリの関数（ロックを取るもの）の外で書くことを禁止する。
