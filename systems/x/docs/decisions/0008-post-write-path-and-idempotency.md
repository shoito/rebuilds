# ADR-0008: 投稿の書き込みは、検証の後に `tid` を振り、投稿の行・抜き出した要素・冪等の記録・outbox を 1 つの DB のトランザクションで確定する。再送は `(author_id, client_request_id)` で同じ投稿を返す

## Context

投稿の API は、NFR-001（p99 300ms、確定を返した投稿を失わない）を満たす必要がある。スマートフォンの回線は切れやすく、クライアントは応答を受け取れずに再送する。再送で同じ投稿が 2 件できると、フォロワーのホームに重なって届き、消すのも利用者の手間になる。

投稿は、メンション・ハッシュタグ・URL・メディアの参照を伴う。これらと投稿の行が食い違うと、通知・検索・トレンドがずれる。出来事は outbox から流す（[ADR-0005](0005-event-log-and-outbox.md)）。ID は `tid`（[ADR-0002](0002-post-ids-and-ordering.md)）。

リポストは、タイムラインの項目として自分の `tid` を持つ（ADR-0002 の表）。1 人 1 回の制約は、関係の表 `reposts` が持つ（AGENTS.md の「カウンターと出来事」）。

## Options

書き込みの形：

1. **1 つの DB のトランザクションで、投稿の行・抜き出し・冪等の記録・outbox を書く**
2. 投稿の行と outbox だけを同期で書き、抜き出し（メンション・ハッシュタグ）は出来事から非同期に作る
3. 投稿を先に Kinesis に書き、消費者が DB に書く（ログを正本にする）

冪等性：

- a. **`(author_id, client_request_id)` の記録を同じトランザクションで書く**
- b. 本文のハッシュで重複を判定する
- c. 冪等にしない（クライアントの再送を許さない）

リポストの形：

- x. **リポストも `posts` の行（`kind = repost`、本文なし）。1 人 1 回は `reposts` の主キーで守り、同じトランザクションで書く**
- y. リポストは `reposts` の行だけにし、タイムラインの項目は `reposts` から作る

## Decision

1、a、x を採用する。詳細は [posts-and-ids.md](../architecture/posts-and-ids.md) の 4〜5 節。

- 検証は安い順（利用者の状態 → レート制限 → 本文の形 → 文字数 → メディア → 返信先・引用先 → T&S の同期の規則）に行い、全部が通ってから `tid` を振る。
- トランザクションで `posts`・`post_mentions`・`post_hashtags`・`post_urls`・`post_media`・`post_requests`・`outbox` を書く。
- `post_requests(author_id, client_request_id)` を主キーにし、24 時間持つ。同時の再送は主キーの重複で後の方が失敗し、既存の投稿を返す。
- 出来事（`post.created`）に本文を載せない。本文が要る消費者は正本を読む。
- リポストは Engagement が書く（[engagement-and-counters.md](../architecture/engagement-and-counters.md)）。S1 では `reposts` と `posts` のリポストの行と outbox を同じトランザクションで書く。S2 で両者が別のクラスタになるときの扱いは [ADR-0010](0010-post-table-partitioning-s2.md)。
- 2 を採らない理由：抜き出しが遅れると、メンションの通知と検索の結果が投稿の後にずれて出る。抜き出しの行は投稿ごとに数行で、同期で書いても予算（DB の区間 80ms）に収まる。
- 3 を採らない理由：確定の判断が非同期になり、「確定を返した投稿を失わない」を DB の耐久性で守れない。他の正本と同じ Aurora の規則（[ADR-0005](0005-event-log-and-outbox.md)）から外れる。
- b を採らない理由：同じ本文を意図して続けて投稿する利用者（定時の告知など）を拒んでしまう。重複の連投の抑止は T&S の規則で別に扱う。
- y を採らない理由：作者の一覧・写しの作り直し・会話が `posts` の索引 1 つで済まなくなり、全ての読み出しに 2 つ目の表の合わせが要る。

## Consequences

- 良くなること：
  - 再送で投稿が重ならない。クライアントは同じ ID で安全に再送できる。
  - 投稿の行と抜き出しと出来事が食い違わない。
- 引き受けるコスト：
  - 冪等の記録の表の保守（24 時間の削除のジョブ）。
  - 投稿 1 件あたりの書き込みの行が増える（平均 4〜6 行）。瞬間のピーク（S1 で 3,000 件/秒）で writer の負荷を負荷試験で確かめる。
  - 本文を出来事に載せないので、検索の索引と T&S の消費者が正本を読む往復が増える。

## Confirmation

- 性質ベーステスト：PROP-POST-001（冪等）、PROP-POST-002（確定と出来事）。
- 結合テスト：トランザクションの途中の失敗で、どの行も残らない。同時の再送で 1 件だけ確定する。
- lint：出来事の形の型に本文の列を入れることを禁止する。
- 本番：`post_requests` による再送の件数と、主キーの重複の件数を計測する。
