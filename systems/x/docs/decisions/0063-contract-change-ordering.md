# ADR-0063: 契約の変更は、広げる → 読む側を新旧に対応 → 書く側を移す → 縮める、の順にする。DB の縮めは別のリリース、出来事は共通の頭と版を持ち、公開 API は同じ版の中で足すだけ、画面の API は 12 週前のアプリが読める形を保つ

## Context

- 出来事の形（スキーマ）は版で管理し、消費者は 1 つ前の版を読めるようにする（[ADR-0005](0005-event-log-and-outbox.md) の Consequences）。runbooks は、出来事の形を変えるときは消費者が新旧の両方を読めるようにしてから作る側を変える、とした（[runbooks/README.md](../runbooks/README.md) の 3 節）。
- 出来事は Kinesis に 7 日残り、DR では outbox の行を 1 時間ぶん送り直す（[ADR-0056](0056-disaster-recovery-osaka.md)）。古い版の出来事が、新しい消費者に後から届く。
- 公開 API は同じ版の中で足す変更だけ（[ADR-0046](0046-public-api-shape-and-oauth.md)）。アプリは 12 週前の版まで支える（[ADR-0062](0062-mobile-release-and-min-version.md)）。
- 大きな表（投稿、関係、通知）の DB の変更は、表の書き換えと長いロックを避けたい。

## Options

1. **広げる → 読む側 → 書く側 → 縮める。DB の縮めは別のリリース。出来事は共通の頭と `version`**
2. 1 回のリリースで DB とコードを一緒に変える
3. 出来事の形を固定し、変えるときは新しい `type` を作る

## Decision

1 を採用する。詳細は [delivery.md](../architecture/delivery.md) の 7 節。

- DB：広げる段（列・表・索引の追加、`NOT VALID` の制約）は読むコードと同じリリースでよい。縮める段は、全サービスのデプロイの後 7 日以上たち、古い列を読むコードがないことを確かめた別のリリース。表の書き換えになる型の変更をしない。`tid` の主キーの型を変えない。
- 出来事：共通の頭 `{ type, version, event_id, committed_at, traceparent, partition_key }`。消費者が新しい `version` を読めるようにしてデプロイ → 作る側を変える → Kinesis の 7 日と送り直しの 1 時間を過ぎてから古い読み方を消す。同じ `version` の型は任意のフィールドの追加しか許さない（CI）。
- 公開 API：`/v1/` の中では足すだけ。OpenAPI の差分で検査する。
- 画面の API：版をパスに持たず、12 週前のアプリが読めなくなる変更をしない。壊す変更は新しいエンドポイントを足し、`min_supported_build` が超えた後に古いものを消す。
- 2 を採らない理由：デプロイの途中で古いタスクと新しいタスクが並ぶ間に、どちらかが壊れる。戻せない。
- 3 を採らない理由：小さな変更のたびに `type` が増え、消費者の分岐が増える。

## Consequences

- 良くなること：
  - デプロイの途中、DR の送り直し、古いアプリのどの組み合わせでも壊れない。
- 引き受けるコスト：
  - 1 つの変更が 2〜3 回のリリースに分かれる。
  - 古い読み方を消す時期の管理。

## Confirmation

- CI：マイグレーションの検査（縮める段と、それを読むコードの同じリリースを拒む）、出来事の形の互換の検査、OpenAPI の差分。
- 夜間の E2E：12 週前のアプリの版。
- 出来事の再生の試験に、1 つ前の版の出来事を混ぜる。
