# ADR-0060: 各部品は AZ を 1 つ失っても S1 のピークをさばける大きさにし、fan-out は瞬間のピークの 2/3 を続けて書ける大きさにする。超えるときに削る順を決め、投稿の書き込みと `visible()` は削らない

## Context

- 瞬間のピーク（年が変わる 0 時、番組の山場、地震の直後）はピークの 10 倍で、S1 で投稿 3,000 件/秒、fan-out の書き込み 30 万件/秒（[architecture/README.md](../architecture/README.md) の 2 節）。
- NFR-002 は瞬間のピークの間も p99 30 秒。NFR-004 は、おすすめの代わりの並びを可用性に数える。
- 災害の時の自治体・報道機関の投稿は遅れが許されない（[intent.md](../intent.md)）。
- 瞬間のピークに合わせて全部を常に用意すると、平常の費用が大きい。

## Options

1. **平常のピークで 2/3 以下、fan-out は瞬間の 2/3、残りはキューと削る順で受ける**
2. 瞬間のピークに合わせて全部を用意する
3. 平常のピークに合わせ、瞬間はオートスケールだけで受ける

## Decision

1 を採用する。詳細は [capacity.md](../architecture/capacity.md) の 2・7 節。

- 各部品は平常のピークで使用率 2/3 以下（1 つの AZ を失っても残りで受ける）。
- fan-out は S1 で 20 万件/秒を続けて書ける大きさ（`fanout-worker` 20 タスク、`vk-timeline` 6 シャード）。残りは SQS で受け、`burst`（[ADR-0015](0015-fanout-pipeline-and-burst-control.md)）で量を減らす。
- `posts` の流れは温めた量（warm throughput）を 20 MB/秒にしておく。
- 削る順：(1) 閲覧の取り込み、(2) おすすめ（代わりの並びに固定）、(3) 作り直しの範囲、(4) 公開 API の全体の天井、(5) fan-out の量（`burst`、閾値の一時の引き下げ）。投稿の書き込み、`visible()`、措置の反映、法令の期限の処理は削らない。
- 2 を採らない理由：年に数回の数分のために、平常の何倍もの費用を払う。
- 3 を採らない理由：Fargate のタスクの起動は分の単位で、数十秒の殺到に間に合わない。Valkey のシャードはすぐには足せない。

## Consequences

- 良くなること：
  - 費用を抑えつつ、瞬間のピークで「届く」と「見せない」を守る。
  - 殺到の時の判断が、事前に決めた順で速い。
- 引き受けるコスト：
  - 殺到の間、おすすめと表示の数の質が下がる。
  - `burst` の間、読み出しの合わせが増える。

## Confirmation

- 負荷試験 L4（年が変わる 0 時の形）で NFR-002 の p99 30 秒（[capacity.md](../architecture/capacity.md) の 8 節）。
- L7（`vk-timeline` の喪失）で読み出しの可用性を保つ。
- 削る順の各段の仕組みを staging で動かし、戻す条件を確かめる。
