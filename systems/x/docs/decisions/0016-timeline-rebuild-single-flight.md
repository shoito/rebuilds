# ADR-0016: 写しの作り直しは、空の「作り直し中」の写しを先に置いてから、フォローしている作者の最近の投稿の写しを合わせて作る。single flight は Valkey の鍵で行い、全体の作り直しの速さに上限を置き、超えたら範囲を狭めて返す

## Context

写しがない利用者（30 日以上読んでいない、Valkey のノードを失った、DR で切り替えた）の読み出しは、写しを作り直す（[ADR-0003](0003-timeline-fanout-hybrid.md)）。目標は p99 2 秒（NFR-003）。

- 作り直しの最中に確定した投稿の扱い：プッシュは写しがある人にだけ書く。作り直しが正本を読んだ後、写しを置く前に配られた投稿は、どちらにも入らず抜ける。
- Aurora の reader は writer より遅れるので、正本の読み出しだけでは直前の投稿を欠く。
- Valkey のクラスタを失う・DR で切り替えると、全員の読み出しが作り直しになり、Aurora に集中する（[architecture/README.md](../architecture/README.md) の 6 節）。

## Options

1. **空の `building` の写しを先に置き、その後で `ar:` と正本を読んで合わせる。`ar:` はプッシュの前に書かれる（[ADR-0015](0015-fanout-pipeline-and-burst-control.md)）。single flight は Valkey の鍵。全体の速さに上限、超えたら範囲を狭める**
2. 正本を読んでから写しを置き、その間の投稿は次の読み出しの新着の窓で拾う
3. 作り直しを writer から読む

## Decision

1 を採用する。詳細は [timeline-fanout.md](../architecture/timeline-fanout.md) の 7 節。

- 手順：`tlb:` を `SET NX PX 5000` で取る → `tl_begin`（`building`）→ `following` を読む → フォロー先の `ar:` を束ねて読む → `ar:` のない作者だけ Aurora の `(author_id, id DESC)` から直近 7 日の上位 50 件 → 合わせて 800 件 → `tl_merge`（`ready`）→ `pl:` を作る。
- `tlb:` を取れない読み出しは、50ms ごとに写しを待つ（最大 2 秒）。
- フォローが 2,000 人を超える利用者は 3 日に絞る。
- 全体の上限は毎秒 `ops.timeline.rebuild_rate`（S1 は 500）。超えたら 24 時間・200 件に狭めて `partial` で返し、残りを低い優先度の仕事で埋める。
- Valkey のノードの喪失で `ar:` も失ったときは、`posts` の流れを喪失の 5 分前から読み直して `ar:` を作り直す。それまでは Aurora の作者の索引を使う。
- 2 を採らない理由：新着の窓は 10 秒で、作り直しの時間（最大 2 秒）とプッシュの遅れ（p99 30 秒）の和を覆えない。
- 3 を採らない理由：作り直しの殺到を writer で受けることになり、投稿の書き込みを巻き込む。

## Consequences

- 良くなること：
  - 作り直しの開始の前後のどの時点の投稿も抜けない（`building` の写しか `ar:` のどちらか）。
  - reader の遅れが作り直しの結果に出ない。
  - 殺到の時も Aurora の負荷に上限がある。
- 引き受けるコスト：
  - `partial` の写しの利用者は、しばらく古い投稿が少ない。
  - `tlb:` の待ちで、同じ利用者の複数の端末の最初の読み出しが遅れる。
  - `ar:` を Kinesis から作り直す手順を運用する。

## Confirmation

- 性質ベーステスト：PROP-TL-002（作り直しの一致）、PROP-TL-003（作り直しの最中の投稿）を、作り直しの各段の間に投稿とプッシュを差し込む列で確かめる。
- 障害の注入：Valkey のタイムラインのクラスタの喪失で、読み出しの可用性を保ち、Aurora の負荷が上限の中、殺到が 30 分で収まる（[quality.md](../quality.md) の 2.4 節）。
- 本番：作り直しの回数、`partial` の割合、作り直しの p99、`tlb:` の待ちの時間を計測する。
