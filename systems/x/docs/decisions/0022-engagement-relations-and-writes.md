# ADR-0022: いいねは投稿の側と利用者の側の 2 つの向きの表を正本にし、リポストは `reposts` を正本にする。状態が変わったときだけ出来事を出す。ブックマークは本人だけの表。いいねした人の一覧は投稿の作者だけ、利用者のいいねの一覧は本人だけが見られる

## Context

いいね・リポスト・ブックマークの数の正本は関係の表である（AGENTS.md、[ADR-0005](0005-event-log-and-outbox.md)）。読み出しは 2 つの向きがある。

- 投稿の側：数の数え直し（照合）、いいねした人の一覧。
- 利用者の側：本人のいいねの一覧、おすすめの特徴（その人が最近いいねした投稿）。

S2 ではエンゲージメントの表を投稿の ID で分割する。利用者の側の読み出しは、全ての分割にまたがってしまう。フォローの表と同じ問題である（[ADR-0007](0007-follow-graph-storage.md)）。

いいね・取り消しの連打、クライアントの再送が多い。そのたびに出来事を出すと、数の出来事と通知が無駄に増える。

いいねの一覧を誰に見せるかは、利用者の安心に関わる。本家は 2024 年に利用者のいいねの一覧を本人だけにしたと報じられている（第三者の報道。本家の文書は未検証）。ブックマークは本人だけのデータ（[ADR-0004](0004-single-tenant-and-visibility.md)）。

## Options

表の形：

1. **いいねは `likes(post_id, user_id)` と `user_likes(user_id, post_id)` の 2 つ。S1 は同じトランザクション、S2 は `likes` を正本にして `user_likes` を出来事から作る**
2. `likes` 1 つと、`(user_id, created_at)` の索引

出来事：

- a. **行を足した・消したときだけ出す（`INSERT ... ON CONFLICT DO NOTHING` の結果で判定）**
- b. 要求ごとに出し、消費者で重複を落とす

一覧の範囲：

- x. **いいねした人の一覧は投稿の作者だけ。利用者のいいねの一覧は本人だけ。リポストした人と引用は投稿を見られる人。ブックマークの数は作者だけ**
- y. すべて公開

## Decision

1、a、x を採用する。詳細は [engagement-and-counters.md](../architecture/engagement-and-counters.md) の 3 節。

- 見えない投稿（`visible()` が `hide`）には、いいね・リポスト・ブックマークできない（`404`）。取り消しは見えなくなった後もできる。
- リポストは `reposts` と、リポストの `posts` の行と、outbox を同じトランザクションで書く（[ADR-0008](0008-post-write-path-and-idempotency.md)）。
- ブックマークの出来事は `post_id` と `sub` だけを持ち、`owner_id` を含めない。
- 2 を採らない理由：S2 の分割の後、利用者の側の読み出しが全分割にまたがる。最初から 2 つの表にしておけば、分割の時に形を変えずに済む（ADR-0007 と同じ理由）。
- b を採らない理由：連打と再送の分の出来事が、数・通知・特徴の全消費者に流れる。
- y を採らない理由：誰が何にいいねしたかは、利用者の関心と人間関係を推測させる。作者が反応を知る必要は認め、それ以外には数だけを見せる。

## Consequences

- 良くなること：
  - 照合と本人の一覧が、それぞれ 1 つの分割で済む。
  - 連打・再送で出来事が増えない。
  - いいねの一覧から、他人の関心を集められない。
- 引き受けるコスト：
  - いいねを 2 回書く。保存の量が倍。
  - S2 では `user_likes` が出来事の分だけ遅れる。
  - 本家の振る舞い（一覧の公開の範囲）と違いうる。差は spec に書く。

## Confirmation

- 性質ベーステスト：PROP-CNT-005（2 つの表が互いの逆、出来事の数と行の数の一致）。
- 結合テスト：見えない投稿への操作が `404`。一覧の範囲を 5 つの主体（[quality.md](../quality.md) の 2.1 節）で確かめる。
- lint：出来事の形の型に、ブックマークの `owner_id` を入れることを禁止する。
