# ADR-0058: タイムラインの届く速さは合成監視を正解にし、出来事に運ぶ確定の時刻からの区間の内訳と、読み出しの抜き取りで補う

## Context

- NFR-002：投稿の確定から、アクティブなフォロワーのホーム（フォロー中）に出るまで p95 5 秒、p99 30 秒。プルの作者も同じ。
- runbooks は、fan-out の遅延の SLI を「合成監視の組（プッシュとプルの両方）」で数えると決めている（[runbooks/README.md](../runbooks/README.md) の 1 節）。
- 合成監視は少数の組で、本物の利用者の遅れの分布（フォロワーの多い作者、閾値の付近、`burst` の間）を表さない。
- 遅れの原因は、Relay、消費者、SQS、Worker、Valkey、読み出しの合わせのどこにもありうる。

## Options

1. **合成監視を正解にし、出来事の確定の時刻からの区間の内訳と、読み出しの抜き取りで補う**
2. 合成監視だけ
3. 全部の読み出しで、入っているべき投稿を正本と比べる

## Decision

1 を採用する。詳細は [observability.md](../architecture/observability.md) の 4 節。

- 合成監視：監視用の作者（プッシュとプル）とフォロワー（写しあり、写しなし、鍵の承認あり・なし、ブロック）を東京と大阪に置き、1 分ごとに投稿し、出るまでの時間と、出てはいけない人に出ないことを測る。SLO はこの値。
- 内訳：Post が `committed_at` を outbox と出来事に入れ、Relay・消費者・Worker・`ar:` の挿入の時刻との差を出す。fan-out はページの中の書いた人数で重みを付け、「フォロワー 1 人にとっての遅れ」を `follower_band` ごとに出す。
- 抜き取り：ホームの読み出しの 0.1% で、入っているべき最新の投稿が最初のページにあるかを、応答の後に非同期で正本と比べ、抜けを理由のコードで数える（reader への上限 1 秒 20 回）。
- 時計は全部 Amazon Time Sync。ずれは E1 で測る。
- 2 を採らない理由：遅れの原因の場所と、本物の分布が分からない。
- 3 を採らない理由：全部の読み出しで正本を引くと、reader の負荷が読み出しと同じだけ増える。

## Consequences

- 良くなること：
  - SLO の値と、原因の場所の両方が分かる。抜けの理由のコードで、写しの切り詰めと遅れを分けられる。
- 引き受けるコスト：
  - 出来事の共通の頭に `committed_at` が要る（[delivery.md](../architecture/delivery.md) の 7.2 節）。
  - 抜き取りの問い合わせの reader の負荷。
  - 合成監視のアカウントを、T&S・おすすめ・トレンド・数から外す印が要る。

## Confirmation

- 合成監視のシナリオが staging で通る。
- 人為的に遅らせた Worker（staging）で、内訳のメトリクスと合成監視が同じ方向に動く。
- 抜けの理由のコードの `unknown` が 0 であることを週ごとに見る。
