# ADR-0013: 関係の表を利用者の ID のハッシュで 1,024 の論理の分割に分け、物理のクラスタへの対応表で置く。S2 は 4 クラスタから。分割の後は `following` と `blocks` を正本にし、逆向きの表は出来事から作る

## Context

フォローの辺は S1 で 6,000 万、S2 で 15 億、S3 で 100 億（[architecture/README.md](../architecture/README.md) の 2 節）。[ADR-0007](0007-follow-graph-storage.md) は、S2 で `following` を `src_id`、`followers` を `dst_id` で分割し、分割の後は `following` を正本にして `followers` を出来事から作ると決め、分割の数と方式をこの領域に任せた。

分割の数は、後から変えると全ての辺を動かすことになる。物理のクラスタの数は、S2 から S3 にかけて増える。

## Options

1. **論理の分割を 1,024 に固定し、論理の分割 → 物理のクラスタの対応表で置く。クラスタを増やすときは論理の分割を丸ごと移す**
2. 物理のクラスタの数で直接ハッシュの余りを取る（クラスタを増やすと再配置）
3. 一貫したハッシュ（仮想のノード）
4. 利用者の ID の範囲で分ける（`tid` の時刻の範囲）

## Decision

1 を採用する。詳細は [follow-graph.md](../architecture/follow-graph.md) の 9 節。

- 論理の分割は `xxHash64(user_id) mod 1024`。`following`・`blocks` は `src_id`、`followers`・`blocked_by` は `dst_id` の論理の分割に置く。
- 対応表 `graph_shard_map` を Aurora の小さな表に持ち、サービスは 60 秒ごとと、移動の出来事で読み直す。
- S2 の初めは 4 クラスタ。1 クラスタの書き込みか保存の量が上限の 6 割を超えたら、論理の分割を新しいクラスタへ移す。
- 分割の後の書き込み：組の勧告ロックと、`following`・`blocks` と outbox は、する側の分割で 1 つのトランザクション。`followers`・`blocked_by` と、ブロックで消す逆向きのフォローは、出来事から冪等に作る。
- 同じ形（1,024 の論理の分割と対応表）を、投稿の表の分割（[ADR-0010](0010-post-table-partitioning-s2.md)）にも使う。
- 2 を採らない理由：クラスタを足すたびに、ほぼ全ての辺が動く。
- 3 を採らない理由：移動の単位が細かく、どの辺がどこにあるかを運用で追いにくい。1,024 の固定の分割で、移動の単位として十分に細かい。
- 4 を採らない理由：新しい利用者が新しい分割に集まり、書き込みが偏る。

## Consequences

- 良くなること：
  - クラスタの追加が、論理の分割の移動の繰り返しで済む。
  - 投稿の表と同じ運用の手順を使える。
- 引き受けるコスト：
  - 逆向きの表が出来事の遅れの分だけ遅れる（ADR-0007 の Consequences）。
  - 移動の間、その論理の分割の書き込みが数秒止まる。
  - 大きな作者の `followers` は 1 つの論理の分割に集まる。fan-out の対象はフォロワー 1 万人未満の作者なので、読み出しの集中は限られる（[ADR-0003](0003-timeline-fanout-hybrid.md)）。

## Confirmation

- 性質ベーステスト：PROP-GRAPH-001（出来事を全部当てた後の 2 つの表の一致）と PROP-GRAPH-002 を、分割の後の非同期の経路で確かめる。
- 結合テスト：論理の分割の移動の最中の書き込みが、失敗して再送されるか、移動の先で確定し、失われない。
- 本番（S2）：照合のジョブで `following` と `followers`、`blocks` と `blocked_by` の差を測る。逆向きの作成役の遅れの p99 を計測する。
