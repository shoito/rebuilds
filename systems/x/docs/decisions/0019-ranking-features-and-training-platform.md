# ADR-0019: ランキングの特徴の定義を 1 か所に置き、配信の時の特徴を記録して学習に使う。学習は SageMaker と Step Functions、推論は ONNX Runtime をサービスの中で動かす

詳細は [ranking-and-recommendation.md](../architecture/ranking-and-recommendation.md) の 7・13 節。

## Context

[ADR-0006](0006-ranking-boundary.md) は、S2 から学習済みのモデル（勾配ブースティング）を ONNX Runtime で動かし、学習は Python でオフラインに行うと決めた。そのうえで次を決める必要がある（[architecture/README.md](../architecture/README.md) の 6 節の持ち越し「学習の基盤」）。

- **学習と推論の特徴のずれ**：学習は Python、推論は TypeScript。同じ特徴を 2 つの言語で別々に書くと、値がずれる。ずれはエラーにならず、並びの質だけが静かに落ちる。
- **過去の時点の特徴**：学習のデータには、投稿を表示した時点の特徴の値が要る。データレイクから後で計算し直すと、その時点より後の情報（後で付いたいいね）が混ざる。
- **学習の基盤**：S2 は週ごとに数億行の学習。S3 はニューラルネットワークで GPU が要る。
- **個人データ**：特徴に使ってよいものと、使わないもの（DM、IP アドレス、要配慮個人情報を推定しうるもの）を、仕組みで分ける。

## Options

特徴：

1. **定義を `packages/ranking/features` の 1 か所に置き、TypeScript の計算はそのまま、Python には定義から生成した仕様（`feature-spec.json`）を渡す。配信の時の特徴の値を記録し、学習はその記録で行う**
2. 学習の側（Python）で特徴を計算し、推論の側（TypeScript）で書き直す
3. マネージドの特徴の保存（SageMaker Feature Store）

学習の基盤：

- a. **SageMaker の学習ジョブを Step Functions で回す**
- b. ECS の上のバッチ（自前のコンテナ）
- c. 学習も推論も外部のサービス

## Decision

1 と a を採用する。

- 特徴の定義は、名前・バージョン・型・既定の値・計算の源（出来事の流れの名前か、写しのキー）・更新の周期・個人データの区分を持つ。区分が `prohibited`（DM、IP アドレス、電話番号、メールアドレス、正確な位置）の源を参照する定義は、CI で拒む。
- 推論（TypeScript）は定義をそのまま使う。学習の側で特徴を作り直さない。学習のデータは、配信の記録（`ranking_served`）に残した特徴の値と、24 時間以内の行動のラベルを結合して作る。最初の学習（記録が溜まる前）だけは、データレイクから時点を合わせて計算し、`backfill` の印を付ける。
- 特徴の計算の一致の試験を CI に置く（同じ入力で TypeScript と Python の差 1e-6 以内）。Python の計算は、評価と最初の学習のためだけに使う。
- 本番では、配信の記録と学習のデータの分布の PSI を毎日測り、0.2 を超えたらチケット。
- 学習は SageMaker の学習ジョブ（LightGBM のコンテナ）を、Step Functions で週ごとに回す。同じデータのバージョン・設定・乱数の種から同じモデルを作る。出力は ONNX にし、`ranking_models` に `registered` で登録する。`approved` にするのは人。
- 推論は Ranking のサービスの中で ONNX Runtime（Node.js の束縛）で行う。別の推論のサービスを熱い経路に入れない。
- 2 を採らない理由：2 つの実装の差が、そのまま学習と推論のずれになる。
- 3 を採らない理由：オンラインの読み出しの遅れと費用が**未検証**で、写し（Valkey）と配信の記録で同じことができる。S3 の前に見直してよい。
- b を採らない理由：S3 の GPU の学習と、実験の記録・再現の仕組みを自前で持つことになる。S2 の勾配ブースティングだけなら b でも足りるが、S3 で移る手間を避ける。
- c を採らない理由：[ADR-0001](0001-platform-and-stack.md) と同じ（題材の核を外に出す）。

## Consequences

- 良くなること：
  - 学習と推論の特徴が同じ定義から作られ、ずれが入りにくく、入っても PSI で気づける。
  - 配信の時の値で学習するので、後の情報が混ざらない。
  - 使ってはいけない個人データが、定義の検査で特徴に入らない。
- 引き受けるコスト：
  - 配信の記録に特徴の値を書くので、データレイクの量が増える（S1 で、おすすめの表示 1 件あたり特徴 50 個として 1 日数億行）。保持は L8 の結論に従う。
  - 新しい特徴は、配信で記録が溜まるまで学習に使えない（2〜4 週）。
  - SageMaker と Step Functions の運用が加わる。

## Confirmation

- CI：特徴の定義の検査（`prohibited` の源の参照の拒否、バージョンの付け忘れ）。特徴の一致の試験。
- 性質ベーステスト：PROP-RANK-006（DM の出来事・中身が特徴の入力に現れない）。
- 本番：PSI、特徴の欠けの割合、`approved` でないモデルが配信されていないこと（Ranking の起動の時に登録の状態を検査）。
