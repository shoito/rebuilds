# ADR-0064: 本人のデータの書き出しの範囲と形

## Context

- 書き出しの入れ物は決まっている。重い操作の確かめ（[accounts-and-auth.md](../architecture/accounts-and-auth.md) の 5.4 節）、`data_export_requests` の表（[data-model/users-and-accounts.md](../architecture/data-model/users-and-accounts.md) の 4.5 節）、S3 の `exports` のバケット（7 日。[data-model/stores.md](../architecture/data-model/stores.md) の 4 節）、監査ログへの記録（[ADR-0052](0052-audit-and-operator-access.md)）、`visible()` を通すこと（[ADR-0004](0004-single-tenant-and-visibility.md)）。
- 決まっていないのは、何を入れて何を入れないか、どの形で渡すか、乗っ取りの疑い・凍結の間に許すか、法令に基づく開示の求め（個人情報保護法の保有個人データの開示の請求）とどう分けるか、である。
- 範囲を決めずに作ると、表を足すたびに「入れ忘れ」か「他人のデータの混入」が起きる。DM には相手の書いたメッセージがあり、相手の同意なく本人に渡してよいかは法務の確認が要る（[intent.md](../intent.md) の L3・L12）。
- 推薦に使う本人の特徴や、スパムの危険の点（[ADR-0040](0040-spam-and-bot-defense.md)）を渡すと、検出の回避に使われうる。一方で、開示の請求の対象に当たるかは法務の確認が要る（L4・L12）。
- 書き出しを MVP に入れるかは PM の判断である（[intent.md](../intent.md) の「PM が決めるもの」）。この ADR は、入れるときの形を決める。

## Options

1. **本人に結び付くデータの種類を 1 か所の一覧（書き出しの目録）に持ち、機械で読める JSON と閲覧用の HTML の ZIP で、セルフサービスで渡す。法令の開示の求めのうち書き出しで足りないものは、T&S の法令の窓口で受ける**
2. 画面で見られるものだけを、閲覧用の HTML だけで渡す
3. 書き出しを作らず、すべてを法令の開示の求めの手続き（本人確認と人の確認）で受ける

## Decision

1 を採用する。詳細は [security.md](../architecture/security.md) の 7.5 節。

> 2026-10-25 の注記：PM が範囲を決めた。MVP（E14 の `data-export`、GA の前）に入れる。法務の確認待ちの種類（L12）は、結論まで `release.export.*` のフラグで止める。

- **書き出しの目録**：`packages/export` に、本人に結び付く表・置き場所ごとに「入れる（列の一覧）」「入れない（理由）」「法務の確認待ち（`release.export.<種類>` のフラグで止める）」のどれかを書く。本人だけの表の一覧（[data-model.md](../architecture/data-model.md) の規約）にある表が、目録に 1 つ残らず載っていることを CI で確かめる。新しい表は、目録に載せるまで CI を通らない。
- **入れる**：プロフィール、本人の投稿とメディアの原本（削除したものは入れない）、リポスト・いいね・ブックマーク、フォロー・フォロワー・ブロック・ミュートの一覧（相手は ID とハンドルだけ）、設定、連絡先（平文に戻す）、本人のアカウントと投稿への措置とその根拠と異議（利用者への通知と同じ範囲。[ADR-0038](0038-moderation-action-model.md)）、おすすめの理由の記録（[ADR-0020](0020-ranking-evaluation-experiments-and-transparency.md)）、認可したアプリの一覧。
- **法務の確認待ち（既定は入れない）**：DM の相手が書いたメッセージ（本人が送ったメッセージと会話の参加者の ID は入れる。L3・L12）、ログインの記録と投稿の時の IP（L2・L12）、推薦に使う特徴の値（L4・L12）。
- **入れない**：他人の本人だけのデータ、通報した人の身元、T&S の内部のメモ、検出の規則と危険の点、データレイクの仮名の行動の記録。開示の請求でこれらを求められたときは、下の窓口で個別に判断する（法務の確認待ち。L12）。
- **形**：ZIP の中に `manifest.json`（書き出しの形のバージョン、作った時刻、目録のバージョン）、種類ごとの `data/<種類>.jsonl`（ID は文字列。ADR-0002）、メディアの原本、オフラインで開ける `index.html` を入れる。2 GB を超えたら分ける。
- **作り方と渡し方**：Worker のジョブが本人の権限（`app.actor_id`）で読む。RLS が本人の行に限り、公開の表も `visible()` を通す。準備ができたらアプリの通知とメールで知らせ、ダウンロードは重い操作の確かめの後、15 分の署名付きの URL で渡す。要求とダウンロードを監査ログに書く。要求の間隔は `policy.export.min_interval_days`（既定 7）。
- **状態ごとの可否**：`locked`（乗っ取りの疑い）では受け付けず、作りかけの書き出しも取り消す（乗っ取った人の持ち出しを防ぐ）。`suspended` と `deactivated` の猶予の間は受け付ける（措置で本人のデータの取り出しを妨げない）。`suspended` の扱いは法務の確認で変えうる（L12）。
- **法令の開示の求め**：書き出しで足りない求め（第三者提供の記録、開示の方法の指定、訂正・利用停止など）は、T&S の法令の案件（[ADR-0041](0041-legal-requests-and-transparency.md)）の種類として受ける。本人確認の方法、期限、手数料は法務の確認待ち（L12）。
- 2 を採らない理由：機械で読めないため、他のサービスへの持ち出しに使えない。目録がないため入れ忘れを検出できない。
- 3 を採らない理由：求めの数が増えると人の確認が回らない。本人が自分の投稿を取り出すたびに T&S が関わる必要はない。

## Consequences

- 表を足す変更に、目録の 1 行が増える。入れるか入れないかの判断が PR のレビューに現れる。
- 法務の確認待ちの種類は既定で入れないので、確認の後に入れると、それより前の書き出しには入らない。目録のバージョンを `manifest.json` に残して区別する。
- 書き出しの形は外へ出る契約になる。形を変えるときは `manifest.json` のバージョンを上げ、足すだけにする（[ADR-0063](0063-contract-change-ordering.md) の公開 API と同じ扱い）。
- メディアの多い利用者の書き出しは大きく、Worker と S3 の費用がかかる。要求の間隔で抑える。

## Confirmation

- CI：本人だけの表の一覧と書き出しの目録の突き合わせ（載っていない表があれば失敗）。
- 性質ベーステスト（PROP-SEC-003）：任意の利用者の組と書き込みの列で、利用者 A の書き出しに、A 以外の本人だけの表の行と、A から見えない公開の行が入らない。
- 結合テスト：`locked` で要求が拒まれ、`locked` に入ると作りかけの書き出しが取り消される。署名付きの URL が 15 分で切れる。
- [quality.md](../quality.md) の 2.2.1 節の「データの書き出し」の行。
