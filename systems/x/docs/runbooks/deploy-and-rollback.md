# Runbook: デプロイと戻し（サーバー、アプリ、OTA）

- Owner: Ops
- 対応するアラート: デプロイの止める条件（5xx の率が前のバージョンの 2 倍、遅延の p99 が SLO の 1.5 倍、消費者の遅れ 60 秒）、アプリの止める条件（クラッシュのないセッションの割合が 0.5 ポイント低下、投稿の失敗の率が 2 倍）、定期作業（週 1 回のアプリの列車）
- 最終確認日: 2026-10-04

理由は [delivery.md](../architecture/delivery.md)、方針は [ADR-0062](../decisions/0062-mobile-release-and-min-version.md)・[ADR-0063](../decisions/0063-contract-change-ordering.md)、時間帯と凍結は [README.md](README.md) の 3 節にある。

## 症状

| 場面 | 見え方 |
| --- | --- |
| A. サーバーのデプロイの悪化 | デプロイの段の後の 10 分の観察で、止める条件に当たる。ECS のサーキットブレーカーが止める |
| B. アプリのバージョンの悪化 | 段階の配布の途中で、クラッシュの率や投稿の失敗の率が上がる |
| C. OTA の束の悪化 | OTA の段階（1% → 10% → 100%）の途中で同じ |
| D. 出来事の形の変更の失敗 | 消費者が新しい `version` を読めず、`stream.consumer_lag` が伸びる |

## 影響

- A：該当のサービスの経路のエラーと遅延。書き込みのサービスなら、投稿・フォローの失敗（クライアントは再送する）。
- B・C：該当のバージョンの利用者のクラッシュ、投稿の失敗。
- D：fan-out・通知・検索などの遅れ。正本は失わない。

## 確認

1. 概要のダッシュボードの「デプロイとフラグの変更の印」で、悪化の始まりと変更の時刻を合わせる。
2. 直前の変更の種類を見分ける：イメージ、フラグ（`release.*`・`ops.*`・`experiment.*`）、マイグレーション、アプリのバージョン、OTA の束。
3. アプリは `app_version_band` の次元で、悪化が新しいバージョンだけかを確かめる。

## 対処

### A. サーバー

1. **まずフラグで戻す。** 新しい振る舞いが `release.*` の裏なら割合を 0 にする。ランキングは `experiment.ranking.*` を止める。
2. 次に 1 つ前のイメージへ戻す（ECS のデプロイの戻し）。デプロイの順（マイグレーション → 書き込み → Relay → 消費者 → 読み出し → Gateway）の、悪化した段から逆の順で戻す。
3. **マイグレーションは戻さない。** 広げる段だけなので、古いコードがそのまま動く。縮める段で問題が出たら、列を足し直す新しいマイグレーションを出す。
4. Gateway を戻すときは、接続を 1 タスクずつ逃がし、10 分かけて再接続を散らす。

### B. アプリ

1. iOS は段階的リリースを一時停止する（合計 30 日まで止められる）。Android は段階的公開を止める。
2. JS だけの不具合なら、OTA で 1 つ前の JS の束に戻す（C）。
3. ネイティブの不具合なら、臨時の列車を出す（ストアの審査の早期の依頼）。ストアではバージョンを戻せない。
4. 支える最も古いバージョン（12 週）を下回る強制（`min_supported_build` の引き上げ）は、セキュリティと API の互換の理由に限る。上げる前に、そのバージョンの利用者の割合が 1% 未満でなければ 2 週の告知を挟む。

### C. OTA

1. 更新のサーバーで、その束の配布を止める。
2. 1 つ前の束を有効にする（`runtimeVersion` が同じ組の端末だけに配る）。
3. 束の作成は CI だけが行う。手元で作った束を出さない。

### D. 出来事の形

1. 作る側を古い `version` に戻す（フラグかイメージ）。
2. 消費者が新旧の両方を読めるバージョンになっているかを確かめてから、作る側を出し直す（[delivery.md](../architecture/delivery.md) の 7.2 節）。

## エスカレーション

- 戻しても悪化が続く：[incident-response.md](incident-response.md) で SEV を宣言する。
- 署名の鍵・OTA の配布の異常：セキュリティの担当（`security:sensitive`）。
- アプリの列車が月に 2 回以上遅れる：PM と Dev に報告する。

## 事後

- 原因を `changes/` の新しい `intent.md` として起票する（Maintain 段）。
- 止める条件に当たらずにすり抜けた悪化は、条件の見直しを [delivery.md](../architecture/delivery.md) の 4.3 節に反映する。
