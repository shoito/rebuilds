# Runbook: インシデントへの対応（共通の進め方と最初の切り分け）

- Owner: Ops
- 対応するアラート: SLO のバーンレート（タイムラインの読み出し・投稿・DM・公開 API）、見える範囲の監査の `hide_unexplained`（個別の手順 `visibility-leak.md` ができるまで）、個別の runbook のない呼び出しのアラート全部（[README.md](README.md) の 4 節）
- 最終確認日: 2026-10-04

## 共通の進め方

| 重さ | 目安 | 例 |
| --- | --- | --- |
| SEV1 | 見てはいけない投稿・DM が見えた疑い。多くの利用者で投稿・読み出しが止まる。法令の期限の超過が確実 | `hide_unexplained` の 1 件、リージョンの障害 |
| SEV2 | SLO を大きく消費。届かない・遅れる。数のずれが広く残る | fan-out の p99 が 30 秒を超え続ける、照合の差が消えない |
| SEV3 | 利用者の影響が小さい・迂回できる | トレンドの更新の遅れ、検索の索引の遅れ（タイムラインは正常） |

1. インシデントの指揮者（IC）を決め、チャンネルを作り、時刻を記録し始める。
2. 影響の範囲（経路、利用者の数、期間）を決める。
3. 直前の変更（デプロイ、フラグ、マイグレーション、アプリの版、AppConfig の `ops.*`）を確かめる。疑わしければ [deploy-and-rollback.md](deploy-and-rollback.md) で戻す。
4. 被害を止める → 原因を取り除く → 回復を確かめる、の順に進める。
5. 告知はステータスページで。見える範囲の漏れと個人データの疑いは、法務と相談してから文面を決める。
6. 調査に使うのは、中身と個人データを含まないログ・メトリクス・トレース（ID・数・理由のコード）だけ。データを見る必要があれば T&S のコンソールか break-glass（2 人の承認）を使う（[security.md](../architecture/security.md) の 6 節）。

## 場面 1：見てはいけない投稿が見えた疑い

### 症状

見える範囲の抜き取りの監査の `hide_unexplained` が 1 件以上。合成監視で「届いてはいけない人」に出た。利用者・報道からの通報。

### 確認

1. `visibility_audit_findings` で、経路（漏れの経路の表の行）、理由（ブロック・鍵・削除・措置）、どの写しから来たか（`tl:`、`ar:`、索引、通知、`rk:`）を見る。
2. 同じ経路の直近のデプロイとフラグの変更を確かめる。
3. 閲覧者の集合の修復の遅れ（`graph-cache-repair` の最古の仕事）と、投稿の状態の写しの書き込みの失敗を見る。

### 対処

1. 経路が特定できたら、その経路を止めるか、劣化の運転に切り替える（閲覧者の集合は `ops.graph.viewer_sets_bypass`、おすすめは `ops.ranking.fallback`）。
2. 直前の変更が原因なら戻す。
3. 漏れた範囲（閲覧者と投稿の ID、期間）を監査の記録から特定し、法務へ報告する（個人データの漏えいに当たるかは法務の L4）。
4. 漏れの経路の表（[quality.md](../quality.md) の 2.2.1 節）に行かシナリオを足す変更を起票する。

## 場面 2：届かない・遅れる

### 症状

fan-out の合成監視の p99 が 30 秒を超える。outbox の最古の行・消費者の遅れが伸びる。

### 確認と対処

1. 区間の内訳（`outbox.relay_lag`、`stream.consumer_lag`、`fanout.page_lag`、`ar.insert_lag`）で、どこで溜まっているかを見る（[observability.md](../architecture/observability.md) の 4.1 節）。
2. Relay：待機の Relay が引き継いだか。outbox の流れごとの溜まり（`engagement` の殺到が他を待たせていないか）。
3. Fanout：`burst` に入ったか。入らないなら `ops.fanout.pull_threshold` を一時に下げる。Worker を増やす。
4. Valkey：`vk-timeline` の記憶と命令の数。ノードの喪失なら作り直しの殺到の手順へ。

## 場面 3：数が正本とずれる

### 症状

照合の後も差が残る。表示の遅れが p95 5 秒を超え続ける。

### 確認と対処

1. `counter_reconcile_log` で、差のある数の種類（いいね、リポスト、返信、閲覧）と投稿の分布を見る。
2. Aggregator の遅れ（`IteratorAge`）と、シャードの分割の直後かを確かめる（分割の後の連番の扱いは未検証。[engagement-and-counters.md](../architecture/engagement-and-counters.md) の 4.2 節）。
3. 照合の経路で正本の値に直す。写しを `UPDATE` で直接書き換えない。

## エスカレーション

- SEV1：Ops の責任者、テックリード、セキュリティの担当。見える範囲の漏れは法務、法令の期限は T&S のリードと法務。
- 30 分で被害を止められないとき：Ops の責任者が追加の人を呼ぶ。

## 事後

- 振り返りを 5 営業日以内に書く。調査結果を `changes/` の新しい `intent.md` として起票する（Maintain 段、[quality.md](../quality.md) の 4.3 節）。
- 見える範囲・法令の期限に関わるものは、[quality.md](../quality.md) の 1 節のリスクと対策も見直す。
