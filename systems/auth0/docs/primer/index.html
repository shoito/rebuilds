Auth0 は何をするサービスか

Auth0 は、アプリの利用者（顧客）のログインを肩代わりする認証基盤です。この分野を CIAM と呼びます。アプリはログインの画面もパスワードも持たず、本システムへリダイレクトして、戻ってきた結果をトークンとして受け取ります。

テナントの開発者

テナントを作り、アプリと API を登録し、標準の OIDC のライブラリでつなぐ。主な利用者。

テナントの管理者

ダッシュボードと Management API で、設定・ユーザー・ログを扱う。

エンドユーザー

テナントのアプリにログインする人。ホスト型の画面で、パスワード・パスキー・ソーシャルログインを使う。

規模の感覚は、S1 でテナント 1 万（うち本番 3,000）、エンドユーザー合計 2,000 万、パスワードを照合するログインのピーク 500 件/秒、トークンの発行のピーク 3,000 件/秒です。ログインが止まると、テナントのアプリの全機能が止まるので、認証の経路は月間 99.99% を目標にしています。

設計の文書で効くところintent.md の「Proposed outcome」と「守るべき振る舞い」、architecture/README.md の 2 節（規模の段階）。

登場人物：OAuth と OpenID Connect

OAuth 2.0 は「API を呼ぶ許可を、パスワードを渡さずに委ねる」ための認可の標準です。OpenID Connect（OIDC）は、その上に「誰がログインしたか」を伝える認証の層を足したものです。

flowchart LR
  U["エンドユーザー（リソースオーナー）"] -- "ログイン・同意" --> AS["本システム（認可サーバー・OP）"]
  C["テナントのアプリ（クライアント・RP）"] -- "認可の要求" --> AS
  AS -- "トークン" --> C
  C -- "アクセストークン" --> RS["テナントの API（リソースサーバー）"]
  RS -. "JWKS で署名を検証" .-> AS

リソースオーナー（利用者）、クライアント（アプリ）、認可サーバー、リソースサーバー（API）。RFC 6749。

OP（OpenID Provider、ID を証明する側）と RP（Relying Party、その証明を信じる側）。外から見ると本システムは IdP です。

クライアントは「アプリケーション」（clients）、リソースサーバーは「API」（resource_servers）。本家の画面の呼び方に合わせています。

設計の文書で効くところauthentication-flows.md の 1・4 節、tenants-and-applications.md の 4・5 節。

3 つのトークンと JWT

トークン何を表すか宛先（aud）形
ID トークン誰が、いつ、どう認証したかアプリ（client_id）JWT
アクセストークンどの API を、どの スコープで呼んでよいか1 つの APIJWT（RFC 9068、typ: at+jwt）
リフレッシュトークンログインし直さずに新しいトークンを得る権利本システムだけ不透明な乱数（<brand>_rt_…）

JWT は「ヘッダー.中身.署名」の 3 つを base64url でつないだものです。中身は誰でも読めます。受け手は、公開鍵で署名を確かめるだけで、本システムに問い合わせずに検証できます。だから API は本システムが落ちても動き続けます。その代わり、発行済みの JWT は期限まで止められません。

管理者がユーザーをブロックしました。そのユーザーが持っているアクセストークン（JWT、残り 40 分）はどうなりますか？

本システムは JWT の失効の一覧を持ちません（ADR-0003）。止めたいテナントには、短い有効期間とリフレッシュトークンの失効を勧めます。/oauth/revoke にアクセストークンを渡すと unsupported_token_type を返し、止められないことを明示します。

設計の文書で効くところADR-0003、ADR-0008、authentication-flows.md の 8 節（有効期間とクレーム）。

認可コード＋PKCE の流れ

本システムが受ける認可の要求は、この 1 つの形だけです。トークンをブラウザの URL に載せず、短命の「コード」をいったん返してから、裏で交換します。

  1. アプリが乱数の code_verifier を作り、その SHA-256 を code_challenge にする。state と nonce も乱数で作る。
  2. ブラウザを /authorize へ送る（client_id・redirect_uri・scope=openid …・code_challenge・state・nonce）。
  3. 本システムが redirect_uri を登録と完全一致で照合し、ログインの画面を出す。有効なセッションがあれば画面を省く（SSO）。
  4. ログインが済むと、redirect_uri へ code・state・iss を付けて戻す。コードは 60 秒、1 回限り。
  5. アプリは state が自分の送った値かを確かめる（CSRF の防御）。iss で発行者の取り違え（mix-up 攻撃）を防ぐ。
  6. アプリが /oauth/token へ code と code_verifier を送る。本システムは SHA-256(code_verifier) が code_challenge と一致するかを確かめる。
  7. ID トークン・アクセストークン（・リフレッシュトークン）を返す。アプリは ID トークンの署名・aud・nonce を確かめる。
要点PKCE は、コードを盗んだ人がトークンに交換できないようにする仕組みです。秘密を持てないアプリ（SPA・ネイティブ）で必須で、本システムは S256 だけを受け、機密のアプリでも既定で必須にします。2 回目のコードの使用を検知したら、そのコードから出したリフレッシュトークンの系列を失効させます。
設計の文書で効くところADR-0006、authentication-flows.md の 5 節（パラメーター・照合の決定表・シーケンス）。

アプリの種類と、その他のフロー

アプリが秘密を安全に持てるかどうかで、公開クライアントと機密クライアントに分かれます。種類が、クライアントの認証の方式と使えるグラントの上限を決めます。

app_type公開・機密使えるグラント
spa公開（ブラウザの JS は秘密を隠せない）認可コード、リフレッシュ
native公開（配った実行ファイルは解析できる）認可コード、リフレッシュ、デバイス
regular_web機密（サーバーで秘密を持つ）認可コード、リフレッシュ、クライアントクレデンシャル
m2m機密クライアントクレデンシャル

利用者のいないサーバー同士の呼び出しです。アプリが自分の秘密か private_key_jwt で名乗り、client_credentials でトークンを得ます。出せるスコープは「アプリ × API」の許可（client_grants）の範囲だけ。sub は <client_id>@clients の形です。

テレビなど入力の限られた端末向けの デバイス認可グラント（RFC 8628）。端末が XXXX-XXXX のコードを表示し、利用者がスマートフォンで /activate を開いて入力・承認します。端末は 5 秒ごとに問い合わせます。遠隔のフィッシングを防ぐため、確認の画面で「許可」を押すまで承認しません。

暗黙フローとパスワードのグラント（ROPG）は出しません。OAuth 2.0 のセキュリティの BCP である RFC 9700 が非推奨にしているためです。

登録した redirect_uri は https://app.example.com/callback。要求に https://app.example.com/callback/（末尾にスラッシュ）が来ました。どうなりますか？

正規化はせず、文字列の完全一致だけで照合します。ワイルドカードも許しません。照合に失敗した URL へエラーを送ると、コードやエラーを攻撃者の URL へ流すオープンリダイレクトになるためです。例外は、ネイティブアプリのループバックのポートだけ（RFC 8252）。

設計の文書で効くところADR-0031、ADR-0007、ADR-0009、tenants-and-applications.md の 4〜6 節。

署名鍵・JWKS・Signer

トークンは秘密鍵で署名し、受け手は公開鍵で確かめます。公開鍵の一覧が JWKS（/.well-known/jwks.json）で、JWT のヘッダーの kid でどの鍵かを選びます。エンドポイントの一覧は discovery の文書にあります。

stateDiagram-v2
  direction LR
  [*] --> next : 生成
  next --> current : ローテーション
  current --> previous : ローテーション
  previous --> revoked : 失効
  current --> revoked : 緊急のローテーション
  • 次の鍵を先に配る。RP は JWKS を数分キャッシュします。next を JWKS に載せて 15 分たってから切り替えるので、新しい鍵の署名を知らない RP が出ません。
  • 秘密鍵は Signer の中だけ。秘密鍵は エンベロープ暗号化で DB に置き、KMS で復号できるのは Signer だけです。外からの要求を受ける Auth は秘密鍵を持ちません。
  • 失効しても、発行済みのトークンは消えない。失効が効くのは、RP が新しい JWKS を読んだとき（キャッシュ 5 分＋エッジ 1 分）からです。
設計の文書で効くところkeys-and-secrets.md の 3・5・7 節、ADR-0046、ADR-0047、ADR-0059。

セッション・SSO・ログアウト

ログインの状態は 3 か所にあります。ログアウトが難しいのはこのためです。

アプリのセッション

アプリが自分の Cookie で持つ。本システムからは見えない。

本システムのセッション

__Host-<brand>_session の Cookie と DB の sessions。SSO の元。使われない期間 3 日・最終 7 日。

外部の IdP のセッション

Google などに残るもの。MVP ではここまでログアウトさせない。

SSO は、同じホスト名で /authorize を呼ぶアプリの間で効きます。prompt=none（画面を出さない）、prompt=login・max_age（再認証させる）で、アプリが振る舞いを選べます。別サイトの iframe で行う「サイレント認証」は、ブラウザのサードパーティの Cookie の制限で動かないことが多いので、SPA にはリフレッシュトークンを勧めます。

アプリがブラウザを /oidc/logout へ送り、本システムのセッションを終えます。id_token_hint がないか合わないときは、ログアウトの CSRF を防ぐため確認の画面を出します。戻り先は登録と完全一致。

本システムのサーバーが、各アプリの登録した URL へ署名したログアウトトークン（sid・sub・events を持つ JWT）を直接 POST します。ブラウザを経由しないので、閉じたタブのアプリにも届きます。再試行のたびにトークンを作り直します。

ブラウザの iframe で各アプリのログアウトの URL を開く方式。サードパーティの Cookie に頼るので、持ちません。

設計の文書で効くところsessions-and-sso.md の 3・4・6 節、ADR-0027、ADR-0028。

リフレッシュトークンのローテーション

SPA やモバイルでは、長くログインを保ちたい一方、トークンが盗まれる危険も高くなります。そこで、使うたびに新しいトークンに替え（ローテーション）、古いトークンの再使用を盗用の印とみなします。1 回のログインから続くトークンの列を系列と呼びます。

  1. ログインで系列 F を作り、RT1 を出す。
  2. アプリが RT1 を使う → RT2 と新しいアクセストークンを出し、RT1 を使用済みにする。
  3. 攻撃者が盗んでいた RT1 を使う。使用済みなので「再利用」と判定する。
  4. 系列 F をすべて失効させる（正規の利用者の RT2 も）。結び付いたセッションも終える。
  5. 正規の利用者は次の更新で失敗し、ログインし直す。この不便が、盗用を見つける代わりの費用。

系列はアプリの設定でセッションに結び付けます（binding）。session（SPA・Web の既定）はログアウトで一緒に止まり、independent（ネイティブ・デバイスの既定）はログアウトの後も使えます。

2 つのタブが同じリフレッシュトークンで同時に更新を送りました（猶予は既定の 0 秒）。遅れた方はどうなりますか？

行のロックで順に処理し、遅れた方は使用済みのトークンを送ったことになります。テナントは猶予を 0〜60 秒で設定でき、SDK には更新を 1 つのタブに寄せるよう文書で勧めます（authentication-flows.md の 7.2 節）。

設計の文書で効くところauthentication-flows.md の 7.2 節の決定表、ADR-0029、sessions-and-sso.md の 7 節。

Universal Login とログインのトランザクション

Universal Login は、本システムのドメインで出すホスト型のログインの画面です。アプリの画面にログインの部品を埋め込む方式は持ちません。

埋め込み型

パスワードがアプリのページを通る。偽の画面と見分けにくい。アプリごとに CSP や MFA の画面を作り直す。

ホスト型

パスワードは本システムにしか渡らない。パスキーの RP ID が 1 つにそろう。厳しい CSP をかけられる。

画面はサーバーで組み立てる HTML で、JavaScript は最小です。/authorize で検証を通った要求は、ログインのトランザクション（login_transactions の 1 行、有効 60 分）に保存し、__Host-<brand>_tx の Cookie と結び付けます。ブランディングはテーマの変数と文言の上書きだけで、テナントの任意の HTML や JavaScript は入れません。

ログインの画面の URL /u/login?state=… の state は何ですか？

本家と同じ形で、トランザクションの handle（256 ビットの乱数）を state の名前で運びます。アプリの state はトランザクションの中に保存し、最後に redirect_uri へそのまま返します（authentication-flows.md の 5.4 節）。

設計の文書で効くところuniversal-login.md の 3〜5 節、ADR-0011、ADR-0012。

接続・ユーザー・ID のリンク

接続は「資格情報を確かめて、外部の ID を返す部品」です。MVP はデータベース接続（メールアドレスとパスワード）と、ソーシャル接続（Google・Apple・LINE・GitHub）を持ちます。1 人のユーザーは、接続ごとの ID を複数持てます。

  • user_id は接続から独立。usr_ ＋乱数で、そのままトークンの sub になります。接続の種類を含めず、削除しても再利用しません（OIDC Core が sub の再割り当てを禁じるため）。
  • メールアドレスの「確認済み」は IdP ごとに違う。Google・Apple は ID トークンの email_verified を使い、LINE はそのクレームがないので確認済みにしません。
  • 同じ人の ID をつなぐのがリンク。つなぐと、どちらでログインしても同じ sub になります。

Google でログインした人の確認済みのメールアドレスが、既存のパスワードのユーザーと同じでした（テナントの設定は prompt）。どうしますか？

メールアドレスの一致だけでつなぐと、IdP の確認の甘さを突いたアカウントの乗っ取りの経路になります。両方の ID で本人が認証してからつなぎます（ADR-0019）。設定の既定は off で、提案せずに新しいユーザーを作ります。

設計の文書で効くところconnections.md の 3・5 節、users-and-profiles.md の 3・5 節、ADR-0014、ADR-0018、ADR-0019。

パスワードを守る：保存・ポリシー・列挙

パスワードの扱いは、米国の NIST SP 800-63B-4 が事実上の基準です。昔の常識と逆になっている点があります。

昔の常識

SHA-256 で保存（速すぎて総当たりされる）。記号を必須にする。定期的に変えさせる。

この設計

Argon2id ＋ pepper で保存。組み合わせの規則は持たず、長さ（既定 15 文字）と、よく使われる・漏えいしたパスワードの一覧で拒否する。

  • 漏えいの照合は k-匿名性。パスワードの SHA-1 の先頭 5 文字だけで範囲を問い合わせ、残りは手元で比べます。データセットの自前のホストは法務の確認待ちで、それまでは公式の API を使います。
  • アカウントの列挙を防ぐ。登録の有無で画面・文言・時間を変えません。ユーザーがいなくてもダミーのハッシュで同じ計算をし、再設定は「登録があれば送りました」と返します。
  • Argon2id は重い。攻撃の判定をハッシュの前に置き、同時に計算する数に上限を置きます（超えたら 503）。
設計の文書で効くところADR-0004、ADR-0015、ADR-0025、connections.md の 4 節。

MFA の要素と保証の水準（AAL）

MFA は、知っているもの（パスワード）・持っているもの（端末の鍵）・本人の特徴（生体）のうち、異なる 2 つを確かめることです。どれだけ確かかを、NIST は AAL の 3 段階で表します。

使った手段amrAAL（acr）
パスワードだけpwdAAL1
パスワード＋TOTPpwd otp mfaAAL2
パスキー（UV あり）swk/hwk user …AAL2（フィッシングに強い）
パスワード＋メールの OTPpwd email mfaAAL1

amr は「使った手段」（RFC 8176）、acr は「達成した水準」です。amr に mfa があっても AAL2 とは限りません。アプリが acr_values や max_age で高い水準を求め、足りなければ追加の要素だけを求めることを step-up と呼びます。

パスワードの後にメールの OTP を通しました。ID トークンの acr はどれですか？

メールの OTP は、TOTP かパスキーを登録した人の予備に限り、AAL2 に数えません（ADR-0021）。本家との互換のため amr には mfa を入れるので、水準は acr で判断します。

設計の文書で効くところmfa-and-passkeys.md の 3・6 節（対応の表と step-up の決定表）、ADR-0021、ADR-0023。

WebAuthn とパスキー

WebAuthn は、ブラウザと端末の認証器で公開鍵暗号のログインをする標準です。端末が秘密鍵を持ち、サーバーは公開鍵だけを持ちます。署名は RP ID とページの origin に結び付くので、偽のドメインでは使えず、フィッシングに強いのです。

  1. 識別子の画面を出すときに、サーバーが 1 回限りのチャレンジを作り、ブラウザで条件付きの UI（mediation: "conditional"）を待たせる。
  2. 利用者が入力欄の自動入力の候補からパスキーを選び、端末の生体認証か PIN で本人を確かめる（UV）。
  3. 認証器が、チャレンジ・origin・RP ID のハッシュに秘密鍵で署名して返す。
  4. サーバーが公開鍵で署名を確かめ、チャレンジ・origin・RP ID・UP/UV のフラグを照合する。
  5. セッションに amr と AAL2 を記録する。UV 付きのパスキーは、所持と本人の確認を 1 回で済ませるので、単独で MFA を満たす（本家は既定で追加の MFA を求める）。
  • 同期するパスキーと端末に固定の鍵。クラウドで複製されうるものは BE フラグが立ちます。NIST は同期するパスキーを AAL2 までとし、MVP は AAL3 を主張しません。
  • RP ID は後から変えられない。テナントで最初にパスキーを有効にしたときのホスト名に固定し、後から足したカスタムドメインは Related Origin Requests で受けます。
設計の文書で効くところmfa-and-passkeys.md の 5.2 節、ADR-0022、connections.md の 4.1.1 節（パスキーだけのユーザー）。

攻撃の防御

ログインの画面は、常に自動化された攻撃を受けます。代表は 2 つです。

ブルートフォース

1 つのアカウントに、多くのパスワードを試す。

クレデンシャルスタッフィング

他のサービスから漏れたメールアドレスとパスワードの組を、多くのアカウントに 1 回ずつ試す。使い回しを突く。

  1. エッジ：WAF が IP の評判とレートで明らかな攻撃を落とす。
  2. 段 1・不審な IP：IP ごとのトークンのバケツ。ログインの失敗は既定で 1 日 100 回。空になったら 429。
  3. 段 2・ボット：リスクの点数が高ければ、自前の proof-of-work のチャレンジをブラウザに解かせる（画像のパズルなし）。
  4. 段 3・ブルートフォース：「識別子 × IP」の失敗が既定 10 回でブロック。ユーザーがいなくても同じに数え、同じ画面を返す。
  5. ここまで通ってから、初めて Argon2id で照合する。成功したら漏えいしたパスワードを調べる。
日本の携帯回線CGNAT では、多くの利用者が 1 つの IP を共有します。IP だけで止めると正規の利用者を締め出すため、ログインに成功したことのあるブラウザには「既知の端末」の Cookie を出し、別に数えます。目標は、攻撃の 99% 以上を止め、誤ブロックを 0.1% 以下にすることです（K5）。新しい防御は「監視」のモードで件数を見てから有効にできます。
設計の文書で効くところattack-protection.md の 3〜6 節、ADR-0024、ADR-0026。

テナント・ホスト名・止まらない認証の経路

テナントは環境（開発・ステージング・本番）ごとに作り、ユーザー・鍵・セッションを共有しません。その上に、請求と契約の単位の「アカウント」を置きます。テナントは <tenant>.jp.<brand>.<domain> のホスト名を持ち、これがトークンの iss になります。

  • ホスト名からテナントを決めてから DB を読む。対応表は各プロセスのメモリーに持ちます。テナントの分け方そのもの（RLS）は共通の資料へ。
  • テナントの名前は再利用しない。別の顧客が同じ名前を取ると、iss が同じなので、古いアプリがそのトークンを信じてしまいます。
  • カスタムドメインは別の iss と別の Cookie。標準のホスト名と混ぜると、SSO が効きません。
flowchart LR
  E["CloudFront + WAF"] -- "認証の経路" --> A["Auth"]
  A -- "相互 TLS" --> S["Signer"]
  E -- "管理の経路" --> M["Management API"]
  A --> DB[("Aurora")]
  M --> DB
  A -. "失われてもよい" .-> V[("Valkey")]

認証の経路と管理の経路は、入口から DB の接続まで分けます。依存先ごとに縮退を決めておき、たとえば Valkey が落ちたらセッションを DB から読み、KMS が落ちてもメモリーの鍵で署名を続けます。

設計の文書で効くところADR-0002、ADR-0005（縮退の表）、ADR-0039、tenants-and-applications.md の 3 節。

法令の枠組み（法務の確認待ち）

認証基盤は、テナントのエンドユーザーの個人データを大量に預かります。設計の文書は法的な結論を出さず、どの結論にも対応できる形にし、確認が済むまで関係する spec を承認しません。

法令論点の枠組み状態
個人情報保護法テナントからの委託か、自ら取得か。海外の IdP・送信事業者などの「外国にある第三者」への提供。漏えい等の報告を誰が行うか（L1）。ログの保持（L5）、データの所在（L6）、委託の契約（L7）法務の確認待ち
電気通信事業法ログインの画面が端末の情報を外部へ送るときの外部送信規律の公表を誰が負うか（L2）。メールの送信の代行が「他人の通信の媒介」に当たるか（L3）法務の確認待ち
SMS の送信送信事業者との契約、送信元の表示、関係する法令（L4）法務の確認待ち（MVP の後）
規約の同意同意を誰の責任で、どう記録するか。未成年の扱い（L8）法務の確認待ち

ほかに、漏えいしたパスワードのデータセットの利用の条件と、署名鍵の失効の権限を契約にどう書くかも、法務の確認待ちです。

設計の文書で効くところintent.md の「法務の確認待ち」の表（承認を止める spec の列）、security.md の 13 節、ADR-0055。

データモデルの読み方

全部で 92 表（MVP 73）ありますが、核は次の数個です。テナントの中の表は、主キーの先頭に tenant_id を持ちます。

erDiagram
  tenants ||--o{ clients : "has"
  tenants ||--o{ connections : "has"
  tenants ||--|{ signing_keys : "signs with"
  users ||--|{ user_identities : "has"
  connections ||--o{ user_identities : "authenticates"
  users ||--o{ authenticators : "enrolls"
  users ||--o{ sessions : "signs in"
  sessions |o--o{ refresh_token_families : "binds"
  clients ||--o{ refresh_token_families : "holds"
  refresh_token_families ||--|{ refresh_tokens : "rotates"
  users {
    uuid tenant_id PK
    uuid id PK
    text user_id UK "sub"
  }
  user_identities {
    uuid user_pk FK
    uuid connection_id FK
    text provider_user_id
  }
  sessions {
    uuid user_pk FK
    bytea secret_hash "SHA-256 of cookie"
    text sid
  }
  refresh_token_families {
    uuid session_id
    text binding
    timestamptz revoked_at
  }
  refresh_tokens {
    bytea token_hash PK
    uuid family_id FK
    int seq
    timestamptz used_at
  }
  signing_keys {
    text kid PK
    text state
  }
  • 内部の結合は user_pk（users.id）、外に出すのは user_id（sub）。UUIDv7 は作成の時刻を含むので外に出しません。
  • 秘密は平文で持ちません。*_hash は SHA-256（高エントロピーの秘密）、パスワードは Argon2id、戻す必要のある秘密は暗号文です。
  • refresh_tokens は再利用の検知のため、使用済みの行も系列が消えるまで残します。
  • ホスト名の対応表や outbox など、テナントの外（RLS の外）の表は data-model.md の 3 節に全部並んでいます。
設計の文書で効くところdata-model.md の 2〜4 節と、data-model/ の領域ごとの定義。ER 図の記号は共通の資料へ。

本家と違うところ・名前の置き換え

振る舞いは本家に寄せていますが、標準の指針（RFC 9700・NIST）を優先して変えたところがあります。

本家この設計
暗黙フロー・パスワードのグラントを出せる認可コード＋PKCE（S256）だけ
コールバックにワイルドカードを許す完全一致だけ
HS256 で署名できる。クライアントシークレットをいつでも表示HS256 なし。シークレットは作成時に 1 回だけ表示し、ハッシュで持つ
user_id に接続の種類を含む接続から独立した usr_…
パスキーの後も既定で MFA を求めるUV 付きのパスキーは単独で MFA を満たす
埋め込み型のログイン（Lock）、プッシュの認証アプリ（Guardian）、SMS持たない（SMS は MVP の後）

ドメイン・ヘッダー・Cookie・クレームの名前空間・トークンの接頭辞には本家の名前を使わず、<brand>・<Brand> と書きます（例：__Host-<brand>_session、<Brand>-RateLimit-Reason）。本家から移るテナントの既存の user_id は、顧客のデータとしてそのまま受け取ります。

設計の文書で効くところintent.md の Non-goals、各領域の文書の「本家の振る舞い」の節、ADR-0006（リポジトリ共通）。

用語集

CIAM
Customer Identity and Access Management。自社のサービスの利用者（顧客）のログインと認可を扱う分野。社員向けの IdP とは利用者の数と使われ方が違う。
OAuth 2.0
パスワードを渡さずに、アプリへ API を呼ぶ許可を委ねる認可の標準（RFC 6749）。
OpenID Connect
OAuth 2.0 の上に、ログインした人を ID トークンで伝える認証の層を足した標準。
認可サーバー
利用者を認証し、トークンを発行するサーバー。本システムそのもの。
OP
OpenID Provider。OIDC で ID を証明する側。認可サーバーと同じもの。
RP
Relying Party。OP の証明（ID トークン）を信じてログインさせるアプリ。
IdP
Identity Provider。利用者の ID を確かめて証明するサービス。本システムも、Google・LINE なども IdP。
JWT
JSON Web Token。ヘッダー・中身・署名を base64url でつないだトークン。中身は誰でも読め、署名で改ざんを検知する。
ID トークン
誰が・いつ・どの手段でログインしたかをアプリに伝える JWT。API の呼び出しには使わない。
アクセストークン
API を呼ぶ許可を表すトークン。宛先の API（aud）とスコープを持つ。
リフレッシュトークン
ログインし直さずに新しいアクセストークンを得るための、長命で不透明なトークン。
スコープ
トークンで許す操作の範囲を表す名前（openid、read:orders など）。
PKCE
Proof Key for Code Exchange（RFC 7636）。認可の要求でハッシュを送り、交換のときに元の値を見せて、コードの横取りを防ぐ。
state
アプリが認可の要求に付け、戻りで同じ値かを確かめる乱数。CSRF を防ぐ。
nonce
アプリが要求に付け、ID トークンに入って戻る乱数。ID トークンの使い回しを防ぐ。
redirect_uri
認可の結果（コード）をアプリへ返す URL。事前に登録したものだけを使える。
公開クライアント
秘密を安全に持てないアプリ（SPA、ネイティブ）。クライアントの認証は none で、PKCE が必須。
機密クライアント
サーバーで秘密や秘密鍵を持てるアプリ。トークンのエンドポイントで自分を認証する。
デバイス認可グラント
入力の限られた端末のための OAuth のフロー（RFC 8628）。別の端末でコードを入力して承認する。
暗黙フロー
トークンを URL のフラグメントで直接返す旧来のフロー。漏えいしやすく、非推奨。
ROPG
Resource Owner Password Credentials Grant。アプリが利用者のパスワードを受け取ってトークンに替える旧来のグラント。非推奨。
RFC 9700
OAuth 2.0 Security Best Current Practice。OAuth の安全な使い方の現行の指針。
JWKS
JSON Web Key Set。署名を確かめるための公開鍵の一覧。
kid
Key ID。JWT がどの鍵で署名されたかを示す値。本システムは公開鍵の thumbprint（RFC 7638）。
discovery
/.well-known/openid-configuration にある、エンドポイントと対応する機能の一覧。ライブラリはここから設定を読む。
Signer
本システムで、テナントの署名鍵を復号して署名する唯一のサービス。外からの要求を受けない。
エンベロープ暗号化
データをデータキー（DEK）で暗号化し、DEK を KMS の鍵で暗号化して一緒に保存する方式。
SSO
Single Sign-On。1 回のログインで、同じ IdP を使う複数のアプリに入れること。
ローテーション
リフレッシュトークンを使うたびに新しいものに替え、古いものを使用済みにすること。
系列
1 回のログインから、ローテーションで続くリフレッシュトークンの列。再利用を検知したら全体を失効させる。
Universal Login
本家の呼び名で、IdP のドメインで出すホスト型のログインの画面。
トランザクション
ここでは、/authorize から認可の応答までのログインの途中の状態（login_transactions の 1 行）。DB のトランザクションとは別。
接続
資格情報を確かめて外部の ID を返す部品。データベース・ソーシャル・（後に）エンタープライズの種類がある。
ID（identity）
接続ごとの利用者の ID（user_identities の 1 行）。1 人のユーザーが複数持てる。
ID のリンク
別々の接続の ID を、同じ 1 人のユーザーにまとめること。
NIST SP 800-63B-4
米国の国立標準技術研究所のデジタル ID の指針のうち、認証を扱う巻。パスワード・MFA・AAL を定める。
Argon2id
計算とメモリーを多く使う、パスワードのハッシュの方式。総当たりを遅くする。
pepper
パスワードのハッシュに加える秘密の鍵。DB と別に保管し、DB だけが漏れても総当たりできなくする。
k-匿名性
ここでは、ハッシュの先頭だけで範囲を問い合わせ、同じ範囲の多数の候補に紛れさせて、照会の中身を相手に知らせない方式。
アカウントの列挙
応答の違いから、あるメールアドレスが登録済みかを探る攻撃。
MFA
多要素認証。種類の違う 2 つ以上の要素で本人を確かめること。
TOTP
Time-based One-Time Password（RFC 6238）。共有した種と時刻から、30 秒ごとに 6 桁のコードを作る。
AAL
Authentication Assurance Level。NIST の認証の確かさの 3 段階。AAL2 は 2 要素、AAL3 はさらに強い認証器を求める。
amr
Authentication Methods References。使った認証の手段の一覧のクレーム（RFC 8176）。
acr
Authentication Context Class Reference。達成した認証の水準を表すクレーム。
step-up
より高い水準が要る操作の前に、足りない要素だけを追加で求めること。
WebAuthn
ブラウザから端末の認証器を使い、公開鍵暗号でログインする W3C の標準。
パスキー
発見可能で、本人の確認（UV）付きの WebAuthn の資格情報。識別子もパスワードも入れずにログインできる。
RP ID
WebAuthn の資格情報が結び付くドメイン。違うドメインのページからは使えない。
UV
User Verification。認証器が生体認証や PIN で本人を確かめたことを示すフラグ。UP（User Presence）は触れただけ。
ブルートフォース
1 つのアカウントに対し、パスワードを総当たりで試す攻撃。
クレデンシャルスタッフィング
他で漏れた ID とパスワードの組を、別のサービスで大量に試す攻撃。
proof-of-work
ブラウザに一定の計算をさせてから送信を受け付ける仕組み。1 回は軽く、大量の自動化には重い。
CGNAT
Carrier-Grade NAT。携帯の事業者などが、多くの利用者に同じグローバル IP を共有させる仕組み。
issuer（iss）
トークンの発行者を表す URL。受け手は、信じる発行者かを iss で確かめる。
委託
個人情報保護法で、個人データの取り扱いを他の事業者に任せること。任せた側が監督の責任を負う。
外部送信規律
電気通信事業法の規律で、利用者の端末の情報を外部へ送らせるときに、送る内容や送り先の公表などを求めるもの。
