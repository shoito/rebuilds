# Runbook: 災害復旧（AZ の障害、リージョンの障害、失った範囲のやり直し、訓練）

- Owner: Ops
- 対応するアラート: AZ の障害（複数のサービスで 1 つの AZ のターゲットが不健全）、大阪からの合成監視の連続失敗、`AuroraGlobalDBRPOLag` の超過、大阪の待機の構成の異常、訓練（四半期に 1 回）
- 最終確認日: 2026-09-27

構成と目標は [infrastructure.md](../architecture/infrastructure.md) の 6 節、方針は [ADR-0060](../decisions/0060-disaster-recovery-and-stages.md) と [ADR-0005](../decisions/0005-authentication-path-availability.md) にある。目標は NFR-005（AZ：RPO 0、RTO 5 分）と NFR-006（リージョン：RPO 1 分、RTO 1 時間）。

## 症状

| 場面 | 見え方 |
| --- | --- |
| A. AZ の障害 | 1 つの AZ のタスク・Aurora のインスタンス・Valkey のノードが不健全になる。AWS Health Dashboard に、東京の 1 つの AZ のイベント |
| B. リージョンの障害 | 東京の認証の経路が応答しない。大阪からの合成監視がすべて失敗する。CloudFront の 502・504 が増える（JWKS・discovery は大阪の S3 から返り続ける） |
| C. 複製の遅延 | `AuroraGlobalDBRPOLag` が 10 秒を超え続ける（東京は正常） |
| D. 論理的な破損 | 誤ったマイグレーション・操作で、設定・ユーザー・資格情報のデータが消えた・壊れた |
| E. 訓練 | 四半期に 1 回（staging）、年 1 回（本番の switchover） |

## 影響

- A：数十秒、ログインとリフレッシュが 503（`Retry-After`）になる。クライアントクレデンシャル、JWKS、発行済みのトークンの検証（テナントの側）は続く。コミット済みのデータは失わない。
- B：切り替えまで（目標 1 時間以内）、ログインとトークンの発行ができない。**発行済みのアクセストークンは、テナントの API で有効のまま**（JWKS はエッジから配り続ける）。切り替えの後、複製の遅延ぶんの書き込みを失う（下の表）。
- C：この状態でリージョンの障害が起きると、失う範囲が広がる。

| 失った書き込み | 切り替えの後に起きること | 回復 |
| --- | --- | --- |
| リフレッシュトークンのローテーション | 利用者の手元の新しいトークンが `invalid_grant` になる | 再ログイン（テナントへ告知） |
| サインアップ、ソーシャルの初回のリンク、MFA の登録 | ユーザー・要素が消える | 再登録（テナントへ告知） |
| **パスワードの変更・再設定、MFA の要素の削除、ログアウト、リフレッシュトークンの失効、ユーザーのブロック・削除** | **古い状態に戻る** | 下の「失った範囲のやり直し」 |
| **署名鍵の失効、クライアントシークレットのローテーション** | **失効したものが有効に戻る** | 同上 |

## 確認

1. AWS Health Dashboard と Grafana の AZ ごとの内訳で、1 つの AZ か、リージョン全体かを見分ける。
2. Aurora のクラスタのイベントで、フェイルオーバーの有無と、現在の writer の AZ を確かめる。
3. リージョンの障害を疑うときは、大阪の合成監視と、別の回線からの到達性の両方で確かめる。
4. **`AuroraGlobalDBRPOLag` の直近の値と、東京が応答しなくなった時刻を記録する。** 失った範囲の目安になる（B で使う）。
5. KMS（東京）の到達性を確かめる。東京の KMS だけの障害なら、リージョンの切り替えではなく、ADR-0005 の KMS の縮退（キャッシュの鍵で続ける）で対処する（[incident-response.md](incident-response.md)）。

## 対処

### A. AZ の障害

基本は自動で回復する。

1. インシデントを宣言する（SEV2 から。[incident-response.md](incident-response.md)）。
2. Aurora が別の AZ へ自動でフェイルオーバーしたことを確かめる。5 分たっても writer がなければ、手動でフェイルオーバーする。
3. ECS が残る 2 AZ でタスクを起動しているか確かめる。auth と signer が足りなければ、最小のタスク数を上げる（signer は 1 AZ ずつ。KMS の読み込みの速さを守る）。
4. Valkey のレプリカの昇格を確かめる。昇格の間は、攻撃の防御の数がタスクごとになる（ADR-0005）。
5. AZ が回復したら、台数を平常に戻す。

### B. リージョンの障害（東京 → 大阪）

**切り替えの判断は、インシデントの指揮者（IC）が行い、Ops の責任者が承認する。** AWS の見込みで 30 分以内に回復しそうなら、待つことも選ぶ（RTO 1 時間の内に収まるなら、データを失わない待機のほうがよい）。発行済みのトークンは有効なので、テナントのアプリは、リフレッシュとログインだけが止まっている。

1. SEV1 を宣言し、テナントへ告知する（ステータスページ）。
2. **東京への書き込みを止める。** 東京の auth・mgmt に届くなら、ops フラグ `ops.read_only_mode` を有効にする（ログイン・リフレッシュを 503 にし、書き込みをやめる）。
3. **失った範囲を記録する。** 「確認」の 4 の値をインシデントの記録に書く。
4. **DB を切り替える。**「DR：大阪を有効化」のワークフロー（大阪で実行できるもの）を起動する。ワークフローは次を順に行う。
   1. Aurora Global Database の大阪の二次を昇格させる。東京の writer が生きていれば switchover（RPO 0）、応答しなければ `aws rds failover-global-cluster --allow-data-loss`（大阪のリージョンで実行）。RDS のイベントで write fencing の成否を確かめる。
   2. 古い一次の障害時点のスナップショット（`rds:unplanned-global-failover-...`）があれば、手動のスナップショットにコピーして保全する（保持の期間で消えないように）。
   3. 大阪の reader を 1 台足す。
5. **アプリを広げる。** 同じワークフローで、大阪の各サービスの最小・最大のタスク数を東京と同じにする。**signer は段階的に広げる**（1 回に 3 タスクずつ。KMS の大阪の上限 1 秒 10,000 回を守る。[capacity.md](../architecture/capacity.md) の 2.7 節）。
6. **大阪の Signer が鍵を復号できることを確かめる**（大阪の KMS のレプリカ。鍵の読み込みの成功のメトリクス）。できなければ、切り替えを進めない（ログインを受けてもトークンを出せない）。
7. **入口を切り替える。** `global/edge` の変数 `active_region` を大阪にして apply する（CloudFront のオリジンを大阪の ALB に。POST はオリジングループで切り替わらないため。[ADR-0058](../decisions/0058-edge-and-custom-domains.md)）。
8. **失った範囲のやり直しを行う**（次の節）。**受け付けの再開の前に終える。** 失効した鍵・変えたパスワードが有効な状態でログインを受けない。
9. **受け付けを段階的に再開する。**
   1. 社内の監視用のテナントで、合成監視（ログイン、リフレッシュ、クライアントクレデンシャル、JWKS）が成功することを確かめる。
   2. `ops.read_only_mode` を解除する。レート制限を平常の 50% にして開き、15 分ごとに上げる。**全クライアントのリフレッシュが集中する**ので、auth のタスク数とハッシュの待ち行列を見ながら開く（[capacity.md](../architecture/capacity.md) の L8）。
10. テナントへ、再開と影響（一部の利用者の再ログイン・再登録、パスワードの再設定の依頼）を告知する。

**東京へ戻す（フェイルバック）**：東京の回復後、Aurora が東京を二次として自動で加え直す。複製が追いついたら、別の計画作業として switchover（RPO 0）で戻す。急がない。大きなイベントの日を避ける。

### 失った範囲のやり直し（B の後）

目的：失った範囲の、セキュリティを強める操作を、大阪の DB にやり直す（[ADR-0060](../decisions/0060-disaster-recovery-and-stages.md)）。

1. **範囲を決める。** 開始 ＝ 東京が応答しなくなった時刻 − 記録した複製の遅延 − 5 分。終了 ＝ 大阪の昇格の時刻。
2. **記録を取り出す。**「DR：失った範囲の取り出し」のジョブに範囲を渡す。ジョブは、log-archive（大阪へのレプリケーション）の監査ログと認証のイベントから、次を取り出す。古い一次のスナップショットが取れていれば、東京の回復後にそれも使う。
   | 記録 | やり直し |
   | --- | --- |
   | パスワードの変更・再設定の完了 | そのユーザーのパスワードを無効にし、次のログインで再設定を求める |
   | MFA の要素の削除 | 同じ要素を削除する |
   | ユーザーのブロック・削除 | 同じ操作をする |
   | ログアウト、リフレッシュトークン・系列の失効、セッションの失効 | 同じ操作をする |
   | 署名鍵の失効・緊急のローテーション | 同じ操作をする（[emergency-key-rotation.md](emergency-key-rotation.md)。大阪で新しい鍵を作る） |
   | クライアントシークレットのローテーション | 旧いシークレットを失効させる。新しいシークレットは大阪にないので、テナントに再ローテーションを依頼する |
   | 接続の秘密・攻撃の防御の設定の変更 | テナントに確かめてもらう（一覧を渡す） |
3. **件数を確かめてから実行する。** Ops の責任者とセキュリティの担当が、種類ごとの件数を確かめて承認する。実行は冪等（同じ操作を 2 回しても同じ結果）なので、途中で止まっても再実行してよい。記録は `dr_replay_runs` に残す。
4. **S3 のレプリケーションも非同期なので、取り出せない記録がありうる。** 東京が回復したら、東京の log-archive と古い一次のスナップショットで、もう一度同じ範囲を取り出し、差分をやり直す。
5. **失効の漏れの疑いが残るテナント**には、緊急のローテーションを勧める（署名鍵）。

### C. 複製の遅延

1. `AuroraGlobalDBRPOLag` と、東京の writer の書き込みの量、リージョン間の回線の状態を確かめる。
2. 書き込みの急増（イベントの集中、クレデンシャルスタッフィングの波の失敗の記録）なら、遅延が収まるのを待つ。10 分を超えて続くなら、SEV3 のインシデントにし、AWS サポートにケースを開く。
3. `rds.global_db_rpo` は設定しない（東京のログインを止めるため。ADR-0060）。
4. この間に署名鍵の失効を行うと、完了の確認（大阪への複製）が遅れる。失効の操作が「完了の確認中」のまま 30 秒を超えたら、[emergency-key-rotation.md](emergency-key-rotation.md) の「完了の確認」に従う。

### D. 論理的な破損

1. 原因の機能のフラグを切る、原因のジョブを止める。
2. 破損の直前の時刻を、ログと監査ログから特定する。
3. Aurora の PITR で、隔離した VPC に新しいクラスタを復元する。本番のクラスタは上書きしない。
4. 失われた行だけを取り出して戻す。**資格情報の表（パスワード、MFA、署名鍵）を戻すときは、戻す行が、その後に削除・変更・失効されていないことを監査ログで確かめる。** 削除したユーザー、変えたパスワード、失効した鍵を戻さない。
5. テナントの設定を戻したら、`tenant_config_versions` を進め、各タスクのキャッシュを更新させる。署名鍵を戻したら、JWKS を書き出し直す。
6. 復元したクラスタを消す。

### E. 訓練

| 訓練 | 頻度 | 環境 | 確かめること |
| --- | --- | --- | --- |
| PITR からの復元 | 四半期 | prod の中の隔離した VPC | 復元の時間、行数、RLS が有効であること、資格情報の暗号文が復号できること |
| 計画外のフェイルオーバーと失った範囲のやり直し | 四半期 | staging | 書き込み（ログイン、パスワードの変更、鍵の失効）を続けたまま東京を止め、B の手順を最後まで行う。RTO 1 時間以内。失った範囲に入れたパスワードの変更・鍵の失効が、やり直しで反映され、古いパスワード・失効した鍵が使えない |
| 本番の switchover | 年 1 回 | 本番 | 大阪でログインとトークンの発行を受け、東京へ戻す。発行済みのトークンが切り替えの前後で検証できる |
| 大阪の待機の構成の確認 | 月次 | 本番 | [infrastructure.md](../architecture/infrastructure.md) の 6.5 節の表 |
| KMS の鍵のレプリカからの復旧 | 年 1 回 | staging | 東京の KMS を使えない状態で、大阪のレプリカだけで Signer と auth が起動する |

結果（時間、問題点）を、この runbook の末尾の記録に残す。

## エスカレーション

- A で 5 分たっても DB の writer がない → SEV1 に上げ、Dev のテックリードを呼ぶ。
- B の判断 → Ops の責任者。告知の文面は PM と合意する。
- 失った範囲のやり直しで、署名鍵の失効・パスワードの変更が含まれる → セキュリティの担当を呼ぶ（承認者）。
- 大阪の Signer が鍵を復号できない → SEV1。セキュリティの担当と Dev のテックリード。AWS サポートにケースを開く。
- AWS 側の障害 → AWS サポートにケースを開く。

## 事後

- 調査結果を Intent の Issue として起票する（Maintain 段）。
- 実際の切り替えと訓練で計測した RTO・RPO、失った範囲の件数（種類別）、やり直した件数と時間を記録し、目標を満たさなければ Intent を起票する。
- この手順で足りなかったことを、ここに反映する。
