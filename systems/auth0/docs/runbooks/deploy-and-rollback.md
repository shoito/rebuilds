# Runbook: デプロイとロールバック

- Owner: Ops
- 対応するアラート: auth の blue/green の自動のロールバック、デプロイの後の SLO のバーンレート、テナントのカナリアのガードによるフラグの自動の停止（[observability.md](../architecture/observability.md) の 5.2 節）
- 最終確認日: 2026-09-27

流れは [delivery.md](../architecture/delivery.md)、CI/CD と Terraform の構成は [infrastructure.md](../architecture/infrastructure.md) の 7 節、テナントのカナリアは [ADR-0066](../decisions/0066-tenant-canary-release.md)、`security:sensitive` の変更は [ADR-0065](../decisions/0065-security-sensitive-change-flow.md) にある。

## 症状

次のときに使う。

- 本番（prod）へデプロイするとき（アプリ、Signer、Terraform）
- デプロイの後に、認証の経路の失敗の率、ログインの成功率、`invalid_grant` の率、Signer の呼び出しの失敗が悪化したとき
- テナントのカナリアのガードが、フラグを自動で切ったとき

## 影響

- 通常のデプロイ：利用者への影響はない。
- 失敗したデプロイ：認証の経路の可用性（99.99%。月のエラーバジェット 約 4.3 分）を消費する。**照合・トークン・セッションの誤りは、5xx にならずにログインの失敗として現れる**（テナントのアプリのログインが止まる）。セッションや Cookie の形の誤りは、SSO の切断（再ログイン）として広く現れる。

## 確認

### デプロイの前

1. 対象のコミットが staging へデプロイ済みで、適合試験（対象のすべてのプロファイル）、E2E、スモーク、デプロイ中の k6 が通っている。
2. デプロイできる時間帯である（平日 10〜17 時。金曜の 15 時以降と年末年始は修正だけ）。テナントから知らされた大きなイベント（チケットの発売、テレビの放送）の時間帯でない。
3. マイグレーションが expand だけか。contract を含むなら、1 つ前のリリースで参照をやめていること、PITR の直近の復元できる時刻が 5 分以内であることを確かめる。
4. **セッション・Cookie・ログインのトランザクション・トークンの形を変える変更なら、新旧の両方を読めるコードが先に本番にあること**（[delivery.md](../architecture/delivery.md) の 5.2 節）。なければ止める。
5. SLO のダッシュボードで、エラーバジェットが残っている。
6. 進行中のインシデント、クレデンシャルスタッフィングの波、`AuroraGlobalDBRPOLag` の超過がない。
7. `security:sensitive` の PR を含むなら、2 人の承認がそろっている（GitHub の記録で確かめる）。
8. Signer の変更を含むなら、同じ日に他のサービスの変更を出さない。

### デプロイの後（入れ替えが終わってから 15 分）

| 見るもの | 正常 | 異常 |
| --- | --- | --- |
| 認証の経路の失敗の率（エッジ） | デプロイの前と同じ | 0.05% を超える |
| ログインの成功率（全体・接続別） | デプロイの前と同じ | 2 ポイント以上下がる |
| `invalid_grant` の率、リフレッシュトークンの再利用の検知 | デプロイの前と同じ | 2 倍以上 |
| `/oauth/token` の p99 | 150ms 以内 | 超える |
| ログインの送信の p99 | 500ms 以内 | 超える |
| Signer の呼び出しの失敗、KMS の `ThrottlingException` | 0 に近い | 増える |
| 合成監視（ログイン、リフレッシュ、クライアントクレデンシャル、JWKS、カスタムドメイン） | 成功 | 2 回続けて失敗 |
| 秘密の出力の走査 | 0 件 | 1 件以上（直ちにインシデント） |

## 対処

### 通常のデプロイ（アプリ）

1. GitHub の `prod` の Environment で、Ops が承認する（作成者と別の人）。
2. マイグレーションのタスクの成功を確かめる。失敗したら、アプリのデプロイは自動で止まる。
3. relay、worker、worker-egress がローリングで入れ替わる。
4. mgmt：blue/green。
5. auth：blue/green のカナリア（要求の 10%）。5xx、ログインの成功率、`invalid_grant` の率、Signer の呼び出しの失敗のアラームが鳴らなければ 100% に切り替わる。
6. 「デプロイの後」の表を 15 分見る。

### Signer のデプロイ（別の日）

1. `security:sensitive` の 2 人の承認を確かめる。
2. 1 AZ ずつローリングで入れ替える。1 AZ ごとに、KMS の `Decrypt` の件数（1 タスク 500 回/秒の上限の内）、`ThrottlingException`、鍵のキャッシュのヒット率、`/oauth/token` の p99 を見る。
3. 3 AZ を終えたら、「デプロイの後」の表を 15 分見る。

### Terraform（`global/edge`、`regional/keys`、WAF）

1. plan の差分を 2 人（作成者と別）で読む。`regional/keys` と WAF のルールは `security:sensitive`。
2. WAF のルールの新しい Block は、まず Count で 24 時間出し、誤検知を見てから Block にする。
3. CloudFront の配信の変更は、反映に数分かかる。反映の後に合成監視（カスタムドメインを含む）を確かめる。

### 悪化したとき

1. **フラグで戻す。** 新しい振る舞いのフラグが原因なら、AppConfig で切る。ガードで自動で切れていれば、切れていることを確かめる。
2. **フラグで戻せないとき、アプリを戻す。** 1 つ前のイメージの digest で再デプロイする（「前のリリースを再デプロイ」のワークフロー）。auth の blue/green の途中なら、ロールバックのボタンで旧い側に戻す。
3. **Signer を戻す**ときも同じ手順で、1 AZ ずつ行う。`security:sensitive` の承認は、ロールバックでは事後でよい（オンコールの二次が確認する）。
4. **マイグレーションは戻さない。** 前へ進める修正を書く。
5. **セッション・Cookie の形の誤りで、利用者のセッションが壊れていたら**：戻しても、壊れた Cookie は残る。旧い形も読めるなら自然に回復する。読めないなら、テナントへ「再ログインが必要になる」と告知する。セッションの一括の失効はしない（被害を広げる）。
6. **トークンのクレームの誤りで、テナントの API が検証に失敗していたら**：戻した後に発行したトークンで回復する。誤ったトークンの有効期間の間、テナントに影響が残ることを告知する（JWT は取り消せない。[ADR-0003](../decisions/0003-token-formats-and-signing-keys.md)）。
7. 戻しても直らなければ、インシデントを宣言する（[incident-response.md](incident-response.md)）。

## エスカレーション

- 戻しても 15 分以内に SLO が回復しない → インシデントを宣言する。
- 秘密の出力の走査で検出 → SEV2 以上。セキュリティの担当を呼ぶ（[incident-response.md](incident-response.md) の「秘密の出力」）。
- 認証の迂回・テナントの分離の疑い（他のテナントのユーザーでログインできた、別のテナントの `kid` で署名された）→ SEV1。セキュリティの担当と Dev のテックリードを呼ぶ。
- マイグレーションが途中で止まり状態がわからない → Dev のテックリードを呼ぶ。

## 事後

- 調査結果を Intent の Issue として起票する（Maintain 段）。
- デプロイの失敗を CI で防げたなら、CI の検査（適合試験のプロファイル、拒否の側のテスト、ガードの条件）を足す提案を Dev と QA に出す。
- この手順で足りなかったことを、ここに反映する。
