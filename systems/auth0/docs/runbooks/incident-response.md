# Runbook: インシデント対応

- Owner: Ops
- 対応するアラート: すべての呼び出し（page）のアラート（[observability.md](../architecture/observability.md) の 5.2 節）。個別の場面は「認証に固有の場面」の節
- 最終確認日: 2026-09-27

個別の手順（[deploy-and-rollback.md](deploy-and-rollback.md)、[disaster-recovery.md](disaster-recovery.md)、[emergency-key-rotation.md](emergency-key-rotation.md)）の上に立つ、共通の進め方と、認証に固有の場面（署名鍵の漏えいの疑い、クレデンシャルスタッフィングの波、秘密の出力、テナントの分離の破れ、依存先の障害）。進め方の骨格は他の題材（Slack・Stripe の incident-response.md）と同じ。

## 症状

次のどれかのときに、インシデントを宣言する。迷ったら宣言し、後で重さを下げる。

- 呼び出しのアラートが鳴った
- テナントや社内から、ログインの障害・不正なログイン・データの漏えいの報告が来た
- 秘密の走査で検出した、署名鍵の KMS の鍵の異常な操作を検知した、シークレットスキャンのパートナーから通知が来た

## 影響

### 重さ（severity）

| 重さ | 基準 | 例 | 最初の応答 | 告知 |
| --- | --- | --- | --- | --- |
| SEV1 | 全体でログインかトークンの発行ができない。他のテナントのデータが見えた。他人としてログインできた（認証の迂回）。署名鍵の漏えいが確定した・Signer の侵害の疑い。資格情報の大量の漏えい | リージョンの障害、Signer の全停止、テナントの分離の破れ | 5 分以内 | 30 分以内にテナントへ。以後 30 分ごと |
| SEV2 | 一部のログインが失敗する（1 つの接続、1 つの AZ、一部のテナント）。1 テナントの署名鍵の漏えいの疑い。秘密の出力の検出。大規模なクレデンシャルスタッフィングの波。SLO の速いバーンレート | ソーシャル IdP の障害、AZ の障害、メールの送信の停止 | 15 分以内 | 1 時間以内にテナントへ（影響があれば） |
| SEV3 | 劣化しているが、回避できる | ログの反映の遅れ、Management API の遅れ、1 テナントへの攻撃 | 営業時間内 | 必要なら |
| SEV4 | テナントへの影響がない | 1 つの Worker の失敗の増加 | 営業時間内 | なし |

**署名鍵、秘密、テナントの分離、認証の迂回に関わるものは、範囲が 1 件でも SEV2 以上にする。**

## 確認

1. どのアラート・報告から始まったかを記録する。
2. 影響の範囲を見る：全体か、特定のテナント・接続・AZ・エンドポイントか。本番のテナントか、開発の環境のテナントか。認証の経路か、管理の経路か。
3. 直近の変更を見る：デプロイ（アプリ、Signer、Terraform の WAF・KMS）、フラグ、マイグレーション、テナントの設定の変更（攻撃の防御の設定、接続の秘密）、外部の IdP の変更の告知。
4. セキュリティへの影響を見る：秘密の走査、KMS の操作（CloudTrail）、攻撃の防御のメトリクス、GuardDuty。

## 対処

### 役割

| 役割 | 担う人 | 責任 |
| --- | --- | --- |
| 指揮者（IC） | 最初に応答したオンコール。SEV1 では Ops の責任者に引き継いでよい | 重さ、方針、大きな判断（鍵のローテーション、リージョンの切り替え、テナントのトークンの発行の停止） |
| 作業者 | オンコールの Ops、呼ばれた Dev | 調査と復旧 |
| セキュリティの担当 | セキュリティの当番 | 鍵・秘密・攻撃・分離に関わる判断、証拠の保全、法務への連絡 |
| 連絡係 | IC が指名する（PM が望ましい） | テナント、社内、外部の IdP・AWS への連絡 |
| 記録係 | IC が指名する | 時刻付きの記録 |

SEV1 では、指揮者は手を動かさない。

### 進め方

1. **宣言する。** インシデント用の場を、このシステムと別の道具に作る（本システムのダッシュボードの管理者のログインが止まっていても使える場所）。
2. **被害を止めることを、原因の特定より優先する。** 順番：
   - 直近の変更のフラグを切る
   - 直近のデプロイを戻す（[deploy-and-rollback.md](deploy-and-rollback.md)）
   - 問題の接続を無効にし、画面で他の方法を案内する（ソーシャル IdP の障害）
   - 攻撃の送信元を WAF で止める、攻撃の防御を強める（「クレデンシャルスタッフィングの波」）
   - 問題のテナントにレート制限をかける、容量を増やす
3. **証拠を消さない。** 監査ログ、認証のイベント、ログ、Signer のタスクの状態（止める前にメトリクスとログを保全する）は、調査と回復の材料である。**秘密の値を、チケット・チャット・この記録に写さない。** 場所と件数と識別子だけを書く。
4. **告知する。** 何が起きているか、どの操作に影響するか（ログイン、リフレッシュ、M2M のトークン、管理の画面）、発行済みのトークンは有効か、次の更新はいつか。原因の推測は書かない。
5. **収束を確かめる。** SLO の指標が戻り、合成監視が成功し、15 分たってから解決とする。セキュリティの調査（範囲の特定、報告）が残るときは、インシデントを閉じず、SEV を下げて続ける。

### 認証に固有の場面

#### 署名鍵の漏えいの疑い

アラート：署名鍵の KMS の鍵の操作（キーポリシーの変更、Signer 以外の `Decrypt`）、テナントからの報告（見知らぬ `kid` の正当なトークン）、Signer のイメージ・依存の Critical の脆弱性。

1. SEV2 で宣言し（Signer の侵害・KMS の権限の異常なら SEV1）、セキュリティの担当を呼ぶ。
2. **範囲を決める。** [emergency-key-rotation.md](emergency-key-rotation.md) の「症状」の場面 1〜4 のどれか。CloudTrail の `Decrypt` の主体、Signer のタスクのログ、`signing_keys` の読み取りの記録（期限つきの権限の使用）を確かめる。
3. **原因を止める。** Signer の侵害なら Signer を確かなイメージで入れ替える。KMS の権限の異常なら、キーポリシーを戻す。
4. **鍵を入れ替える。** [emergency-key-rotation.md](emergency-key-rotation.md) に従う。
5. **テナントへの支援**：テナントの API のログで、失効した `kid` のトークンの使用（特に、ログインの記録と合わない `sub`）を探すよう依頼する。本システムの側でも、その `kid` で署名した記録（認証のイベント）と、テナントから受け取ったトークンの `jti` を照合できるようにする。
6. **法務へ連絡する。** 不正なトークンで利用者のデータが読まれたおそれがあるなら、個人データの漏えい等に当たるか、報告の主体（テナントか本システムか）を法務が判断する（[security.md](../architecture/security.md) の 12・13 節）。

#### クレデンシャルスタッフィングの波

アラート：クレデンシャルスタッフィングの兆候（ログインの試行が全体で平常の 5 倍、または 1 テナントで 20 倍かつ失敗の率 80% 超）、ハッシュの待ち行列の飽和、WAF のレート制限の急増。防御の仕組みは [attack-protection.md](../architecture/attack-protection.md) にある。

1. SEV2 で宣言する（正規のログインに影響が出ていなければ SEV3 でよい）。セキュリティの担当を呼ぶ。
2. **形を見る。** 対象（1 テナントか、多くのテナントか）、送信元（IP の数、ASN、国、匿名の IP のラベル）、ユーザーエージェントの偏り、成功の率（成功が出ているなら、漏えいした資格情報が当たっている）。
3. **エッジで落とす**（安い順）：
   1. 送信元が少数の ASN・IP に偏るなら、WAF の IP の集合か ASN の一致のルールで Block する（Terraform の緊急の変更。2 人の承認は事後でよい）。
   2. 分散しているなら、ログインの送信のレート制限のルールを Block から Challenge に切り替え、しきい値を下げる（[infrastructure.md](../architecture/infrastructure.md) の 4.3 節のルール 5）。
   3. 攻撃が大きいテナントは、テナントの全体を WAF の Challenge に切り替える（attack-protection の手順）。
4. **アプリで強める**：
   - 対象のテナントのボットの検知を `always`（ログインの送信で常にチャレンジ）にする。テナントの管理者に知らせる。
   - プラットフォームのバケツ（全テナントの IP ごとの失敗の数）の値を一時的に引き締める。
   - 防御が `monitor` のテナントで被害が出ているなら、テナントの管理者に `enforce` を勧める（本システムが勝手に変えない。ただし、テナントの利用者の乗っ取りが続いているときは、セキュリティの担当の判断で一時的に `enforce` にし、プラットフォームの監査に残す）。
5. **正規の利用者を守る**：
   - ハッシュの待ち行列の上限で 503 が出ていたら、auth のタスクを増やす。ただし、Argon2id に届く攻撃の試行を増やすだけなので、先に 3・4 で落とす。
   - 誤ブロックの報告（特定の携帯の回線、企業の NAT）を見て、IP の許可リストの追加をテナントに案内する。
6. **成功したログインへの対処**：攻撃の中で成功したログイン（漏えいした資格情報が当たったもの）を、認証のイベントから一覧にする（`user_id`、テナント）。
   - 漏えいしたパスワードの検知の対象ならパスワードの再設定を求める（テナントの設定に従う）。
   - テナントの管理者に一覧を渡し、利用者への通知とセッション・リフレッシュトークンの失効を勧める。
7. **収束の後**：WAF の緊急のルールを外すか、恒久のルールにするかを決める。Challenge の費用（[attack-protection.md](../architecture/attack-protection.md)）を記録する。

#### 秘密の出力

アラート：秘密の走査の検出（[observability.md](../architecture/observability.md) の 4.3 節）、テストの CI ではなく本番のログでの検出。

1. SEV2 で宣言し、セキュリティの担当を呼ぶ。
2. **広げない。** 検出したロググループ・バケットの読み取りを、調査の担当だけに絞る。原因の経路（新しいログのイベント、例外の出力、アクセスログの設定）を、フラグかデプロイで止める。
3. **種類と範囲を確かめる。** どの種類の秘密（リフレッシュトークン、認可コード、パスワード、クライアントシークレット、セッション）が、どこに、いつから、何件、誰が読めたか（CloudTrail のログの読み取りの記録）。
4. **秘密を無効にする**：
   | 秘密 | 無効にする方法 |
   | --- | --- |
   | リフレッシュトークン | 該当の系列を失効させる |
   | 認可コード | 期限（60 秒）で失効済み。確かめるだけ |
   | アクセストークン・ID トークン | 取り消せない。期限まで待つ。長いものが含まれるなら、テナントに知らせる |
   | セッション | 該当のセッションを失効させる |
   | パスワード | 該当のユーザーに再設定を求める。テナントに知らせる |
   | クライアントシークレット、接続の秘密 | テナントにローテーションを依頼する（本システムの側で旧いものを失効させる期限を決める） |
   | 署名の秘密鍵、pepper | 「署名鍵の漏えいの疑い」、pepper のローテーション（[keys-and-secrets.md](../architecture/keys-and-secrets.md)） |
5. **ログの該当の行を消す。** CloudWatch Logs は該当のログストリームを消す。log-archive（Object Lock）は期間内に消せないので、アクセスの制限と記録で扱う。
6. 法務と、報告の要否を決める（パスワードの漏えいは個人データの漏えい等に当たりうる）。

#### テナントの分離の破れ、認証の迂回

アラート：テナントからの報告（他のテナントのユーザー・設定が見えた、他人としてログインできた）、テナントの分離の監査の不一致。

1. **SEV1** で宣言する。セキュリティの担当、Dev のテックリード、PM を呼ぶ。
2. 原因の機能を止める。フラグで止められなければ、直近のデプロイを戻す。どちらも効かないなら、影響のエンドポイントを WAF で一時的に止める（ログインが止まるが、他人としてのログインを続けさせない）。判断は IC とセキュリティの担当。
3. 範囲を特定する：認証のイベントと監査ログで、`tenant_id` と要求のホスト名、`client_id` のテナントが合わない記録、発行したトークンの `iss` と `sub` の組み合わせを探す。
4. 誤って発行したトークンの系列を失効させる。署名鍵の取り違えなら、[emergency-key-rotation.md](emergency-key-rotation.md) の場面 4。
5. 法務へ連絡する。

#### 依存先の障害

[ADR-0005](../decisions/0005-authentication-path-availability.md) の縮退の表のとおりに動いているかを確かめる。

| 依存先 | 見るもの | すること |
| --- | --- | --- |
| Aurora の writer | ログイン・リフレッシュの 503、フェイルオーバーのイベント | 自動のフェイルオーバーを待つ。5 分を超えたら手動（[disaster-recovery.md](disaster-recovery.md) の A） |
| Valkey | 攻撃の防御がタスクごとの近似の数になっている | 攻撃の波と重なっていないか確かめる。重なっていれば WAF を強める |
| KMS | Signer の鍵のキャッシュのミスで 503 のテナント | Signer と auth を縮小しない（オートスケールの縮小を止める）。キャッシュにない鍵のテナントを一覧にし、影響を告知する。鍵の生成・ローテーションは止まる |
| Signer | `/oauth/token` の 503 | タスクの状態、相互 TLS の証明書の期限（Private CA の更新の失敗）、KMS を確かめる。代わりに署名する経路は作らない |
| ソーシャル IdP | 接続の種類別の成功率 | 外部の状態のページを見る。画面で他の方法を案内する。テナントへ告知する |
| メールの送信 | 送信の失敗・遅れ | メールの OTP だけのユーザーの MFA が失敗する。送信事業者に連絡する |
| 漏えいしたパスワードの照合 | サインアップ・パスワードの変更・再設定の 503、`ap_breached_check_skipped` の件数 | 照合を飛ばさない（ADR-0005）。法務の確認までは公式の range API への外部の依存なので、提供者の状態を確かめ、テナントへ告知する。自前のホストに移った後は、前の版のデータで動かせるか確かめる（[attack-protection.md](../architecture/attack-protection.md) の 5 節） |
| Actions の実行の基盤（E13 の後） | Action を使うテナントのログイン・M2M の失敗、Lambda のスロットリング | `on_platform_error` が `deny` のテナントを一覧にして告知する。手順は `actions-platform-degraded.md`（E13 で作る） |

### オンコール

- 一次は Ops、二次は Dev（週替わり）。一次が 5 分（SEV1）・15 分（SEV2）で応答しなければ、二次を呼ぶ。
- **セキュリティの担当も当番を持つ**（鍵のローテーションの判断、`security:sensitive` の緊急の変更の承認、法務への連絡）。
- 呼び出しの道具と当番の表は、E12 で決める。

## エスカレーション

| 状況 | 連絡先 |
| --- | --- |
| SEV1 の宣言 | Ops の責任者、Dev のテックリード、PM |
| 署名鍵、秘密、テナントの分離、認証の迂回 | 上記に加えて、セキュリティの担当と法務（報告の要否を判断する） |
| 外部の IdP・メールの送信事業者の障害 | 各社の窓口（連絡係が行う） |
| リージョンの切り替えを考える | Ops の責任者（承認）。[disaster-recovery.md](disaster-recovery.md) |
| AWS 側の障害 | AWS サポートにケースを開く |
| 1 時間たっても被害を止められない | 重さを 1 段上げる |

## 事後

- **振り返り**を、SEV1・SEV2 では必ず、解決から 5 営業日以内に行う（責任追及をしない）。書くこと：時系列、影響（時間、テナント数、失敗したログインの件数、消費したエラーバジェット）、セキュリティの影響（無効にした秘密の件数、ローテーションした鍵の数、報告の有無）、検知までの時間、原因、再発防止の対策。
- **再発防止を Intent にする。** Claude が調査結果から Intent の Issue を起票する（Maintain 段）。調査に Claude を使うときは、人が取り出した、秘密と個人データを含まないものだけを渡す（[ADR-0056](../decisions/0056-operator-access.md)）。
- 鍵・秘密・分離・攻撃に関わるものは、QA にも共有し、[quality.md](../quality.md) のリスクと対策を見直す。`security.md` の `SEC-` の行とテストを足すかを、セキュリティの担当が判断する。
- この手順と、関係した個別の runbook で足りなかったことを反映する。
