# Runbook: 署名鍵の緊急のローテーション

- Owner: Ops（判断はセキュリティの担当と共同）
- 対応するアラート: 署名鍵の KMS の鍵の操作（キーポリシーの変更、無効化、削除の予約、Signer 以外のプリンシパルの `Decrypt` の試み）、テナントからの鍵の漏えいの報告、JWKS の書き出しの遅れ、訓練（四半期に 1 回。[ADR-0046](../decisions/0046-signing-key-lifecycle.md) の Confirmation）
- 最終確認日: 2026-09-27

署名鍵の状態と遷移は [keys-and-secrets.md](../architecture/keys-and-secrets.md) の 5 節（[ADR-0046](../decisions/0046-signing-key-lifecycle.md)）、Signer の API は [ADR-0047](../decisions/0047-signer-api-and-jwks-publishing.md)、Signer の隔離は [ADR-0059](../decisions/0059-signer-isolation.md)、DR の後の失効のやり直しは [ADR-0060](../decisions/0060-disaster-recovery-and-stages.md) にある。署名鍵の漏えいの疑いの全体の進め方（封じ込め、調査、報告）は [incident-response.md](incident-response.md) の「署名鍵の漏えいの疑い」にあり、この runbook は鍵の操作の手順を書く。

## 症状

次のときに使う。

| 場面 | 範囲 |
| --- | --- |
| 1. テナントの鍵の漏えいの疑い（テナントからの報告、そのテナントの `kid` の見知らぬトークンの報告） | 1 テナント |
| 2. Signer の侵害の疑い（Signer のタスクの異常な振る舞い、Signer のイメージ・依存の脆弱性で鍵が読まれた可能性） | Signer のキャッシュにあったすべてのテナント（実質的に全テナント） |
| 3. 署名鍵の KMS の鍵の権限の異常（Signer 以外のプリンシパルの `Decrypt` の成功、キーポリシーの不正な変更） | 暗号文を読めた範囲（DB の読み取りの権限と合わせて判断） |
| 4. 本システムの誤り（誤った鍵で署名した、別のテナントの鍵が JWKS に載った） | 影響のテナント |
| 5. 訓練 | staging |

## 影響

- **失効しても、発行済みのトークンは取り消せない。** 失効が効くのは、テナントの API・RP が新しい JWKS を読んだ時点から（CloudFront のキャッシュ 約 1 分、RP のキャッシュ 約 5 分。RP のライブラリによってはもっと長い。[keys-and-secrets.md](../architecture/keys-and-secrets.md) の 5.3 節）。
- 緊急のローテーションで `current` を失効させると、その鍵で署名した**有効な ID トークン・アクセストークンも、テナントの API で検証に失敗する**。テナントの利用者は、トークンの更新（リフレッシュ）か再ログインが要る。リフレッシュトークン（不透明、DB で照合）は鍵の失効の影響を受けない。
- 場面 2 は全テナントの鍵を入れ替えるので、全テナントの利用者の、有効なアクセストークンが一斉に無効になり、リフレッシュが集中する。
- ローテーションの間も、認証の経路の SLO は消費しない（ログインとトークンの発行は続く）。

## 確認

1. **範囲を決める。** 場面、対象のテナント（`tenant_id`）、対象の `kid`、疑いの始まりの時刻。
2. **鍵の状態を見る。** ダッシュボード（運用者の画面）か `signing_keys` の読み取り（期限つきの権限。[ADR-0056](../decisions/0056-operator-access.md)）で、対象のテナントの `next`・`current`・`previous` の `kid` と、`last_used_at` を確かめる。
3. **KMS の状態を見る。** 東京と大阪の署名鍵の KMS の鍵（`<brand>-signing-keys`）が有効で、`GenerateDataKey` が使えること。KMS が使えないと新しい鍵を作れない（5 の「KMS が使えないとき」）。
4. **CloudTrail で、署名鍵の KMS の鍵の `Decrypt` の主体を確かめる**（場面 2・3）。Signer のタスクのロール以外の成功が 1 件でもあれば、場面 3 として扱う。
5. **複製の遅延を見る。** `AuroraGlobalDBRPOLag`。10 秒を超えていたら、失効の完了の確認が遅れる（5 の「完了の確認」）。

## 対処

**判断**：場面 1・4 はセキュリティの担当が、場面 2・3 はセキュリティの担当と Ops の責任者の 2 人が、ローテーションを決める。テナントの同意を待たずに本システムの判断で行うかは、契約の扱いが法務の確認待ちである（[security.md](../architecture/security.md) の 13 節）。確定までは、場面 1 はテナントの管理者に連絡して同意を得てから行い、連絡がつかない・場面 2・3 のときは本システムの判断で行い、プラットフォームの監査に理由を残す。

### 1. 1 テナントの緊急のローテーション（場面 1・4）

1. インシデントを宣言する（SEV2。場面 4 でテナントの分離に関わるなら SEV1）。
2. **緊急のローテーションを実行する。** 運用の手順（2 人の承認）で、Management API の緊急のローテーション（[keys-and-secrets.md](../architecture/keys-and-secrets.md) の 5.2 節の 7：`next`→`current`、`current`→`revoked`、新しい `next` を生成）を呼ぶ。`previous` も漏えいの疑いがあれば、続けて失効させる（5.2 節の 4）。
3. **Signer の停止を確かめる。** 全 Signer のタスクが `keys:invalidate` に応答し、失効した `kid` で署名しないこと（署名の件数のメトリクスで、その `kid` が 0 になる）。応答しないタスクは、2 秒のポーリングで追いつく。追いつかないタスクは停止する。
4. **JWKS の反映を確かめる。**
   1. `signing_key_operations` の状態が `published` になる（Worker が S3 に書き出した）。
   2. CloudFront のキャッシュの無効化を出す（`/.well-known/jwks.json`。テナントのホスト名とカスタムドメインの両方）。
   3. エッジから JWKS を取得し、失効した `kid` がないことを確かめる（テナントのホスト名とカスタムドメインの両方）。
5. **完了の確認。** 操作が `completed` になる（大阪への複製の確認を含む。[ADR-0060](../decisions/0060-disaster-recovery-and-stages.md)）。30 秒を超えて `published` のままなら、`AuroraGlobalDBRPOLag` を見て、遅延が解けるのを待つ。解けないまま大阪へ切り替えることになったら、[disaster-recovery.md](disaster-recovery.md) の「失った範囲のやり直し」の対象に入れる。
6. **テナントへ知らせる。** 知らせること：失効した `kid`、時刻、テナントの API と RP で JWKS のキャッシュを捨てること、失効した鍵で署名されたトークンを受け付けないように API の側で `kid` を拒否すること（キャッシュを捨てられない場合）、利用者の再ログイン・リフレッシュが起きること。
7. **追加の封じ込めを判断する**（[keys-and-secrets.md](../architecture/keys-and-secrets.md) の 5.3 節）：
   - テナントのリフレッシュトークンの系列の失効：鍵の漏えいだけではリフレッシュトークンは作れないので、既定では行わない。攻撃者がセッションも得た疑いがあるときだけ行う。
   - テナントのトークンの発行の一時停止（キルスイッチ）：新しい鍵を作れないとき（KMS の障害）だけ。

### 2. 全テナントの緊急のローテーション（場面 2・3）

1. SEV1 を宣言する。セキュリティの担当、Dev のテックリード、PM を呼ぶ。
2. **原因を先に止める。** Signer の侵害なら、疑わしいイメージのタスクを止め、1 つ前の確かなイメージで Signer を入れ替える（[deploy-and-rollback.md](deploy-and-rollback.md)）。KMS の権限の異常なら、キーポリシーを正しい状態に戻し、不正な主体のロールを無効にする（2 人の承認）。**原因を止める前に鍵を入れ替えると、新しい鍵も漏れる。**
3. **Signer のタスクを増やす。** 最大（24）まで広げる。鍵の生成（RSA 2048 の生成の CPU）が律速になる（[keys-and-secrets.md](../architecture/keys-and-secrets.md) の 5.4 節。S1 で数分と見込む。未検証）。
4. **本番のテナントから順に、緊急のローテーション（全部。5.2 節の 8）を実行する。** バッチのジョブ（`emergency-rotate-all`）に、テナントの一覧（本番 → ステージング → 開発の順）を渡す。KMS の `GenerateDataKey` は 1 秒 500 回に絞る。
5. 進みをダッシュボードで見る：完了したテナントの数、`ThrottlingException`、`/oauth/token` の p99、Signer の CPU。**トークンの発行を止めない。** 未完了のテナントは古い鍵で署名を続ける（原因を止めた後なので、新しい漏えいは起きない前提）。
6. 全テナントの JWKS の書き出しと、CloudFront のキャッシュの無効化（ワイルドカード）を確かめる。
7. **リフレッシュの集中に備える。** 全テナントのアクセストークンが無効になるので、リフレッシュが集中する。auth のタスク数を広げ、レート制限の値を確かめる。
8. 全テナントへ告知する（1 の 6 と同じ内容）。

### 3. KMS が使えないとき

新しい鍵を作れない（[keys-and-secrets.md](../architecture/keys-and-secrets.md) の縮退の表）。

1. 漏えいした鍵を**失効だけ**させる（`previous` の失効はできる。`current` は、`next` がすでにあるなら `next` への切り替えで外せる。`next` はキャッシュにあれば署名できる）。
2. `next` もない・使えないテナントは、トークンの発行を一時停止する（キルスイッチ）。漏えいした鍵で署名を続けるより、止めるほうを選ぶ。判断はセキュリティの担当。
3. KMS の回復を待ち、1 の手順で新しい鍵を作る。

### 4. 訓練（場面 5）

| 訓練 | 頻度 | 確かめること |
| --- | --- | --- |
| 1 テナントの緊急のローテーション | 四半期（staging の監視用のテナント） | 操作から、エッジの JWKS に失効が反映されるまでの時間（目標 2 分以内）。失効した `kid` の署名が 0 件 |
| 全テナントの緊急のローテーション | 年 1 回（staging、テナント 1 万） | 完了までの時間、KMS のスロットリング 0 件、`/oauth/token` の p99 |
| KMS が使えないときの失効とキルスイッチ | 年 1 回 | 3 の手順が回る |

## エスカレーション

- 場面 2・3 → SEV1。セキュリティの担当、Dev のテックリード、PM、法務（報告の要否。[security.md](../architecture/security.md) の 12 節）。
- 失効の完了が確認できない（Signer のタスクが止まらない、JWKS がエッジで更新されない）→ Dev のテックリード。
- 鍵で作られた不正なトークンで、テナントの利用者の被害が確かめられた → SEV1 に上げ、PM と法務。

## 事後

- 漏えいの原因と、鍵で署名された不正なトークンの有無（テナントからの情報）を記録する。
- 調査結果を Intent の Issue として起票する（Maintain 段）。
- 1 テナントの失効の反映の時間、全テナントのローテーションの時間を記録し、目標に届かなければ Intent を起票する。
- この手順で足りなかったことを、ここに反映する。
