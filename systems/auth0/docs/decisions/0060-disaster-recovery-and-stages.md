# ADR-0060: 大阪のウォームスタンバイへ人の判断で切り替え、失った範囲のセキュリティを強める操作をやり直す。S3 でテナントをセルに固定する

## Context

[ADR-0005](0005-authentication-path-availability.md) は、S1 から大阪にウォームスタンバイを置き（Aurora Global Database、マルチリージョンの KMS の鍵）、切り替えは人の判断で行い、手順を自動化すると決めた。目標は NFR-006（リージョン：RPO 1 分以内、RTO 1 時間以内。S2 で RTO 15 分）。

Aurora Global Database の計画外のフェイルオーバーでは、その時点の複製の遅延ぶんの書き込みを失う（通常は秒単位）。計画的な switchover は RPO 0（[Using switchover or failover in Amazon Aurora Global Database](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-global-database-disaster-recovery.html)、2026-09-27 に確認）。

認証の基盤で、失った書き込みは次の問題になる。

| 失った書き込み | 切り替えの後に起きること |
| --- | --- |
| リフレッシュトークンのローテーション | 利用者の手元の新しいトークンを大阪が知らない。更新が `invalid_grant` になり、再ログインになる |
| サインアップ、ソーシャルの初回のリンク | ユーザーが消える。再登録か再リンクになる |
| **パスワードの変更・再設定、MFA の要素の削除、セッションのログアウト、リフレッシュトークンの失効、ユーザーのブロック・削除** | **古い状態に戻る。** 漏えいを受けてパスワードを変えたのに、古いパスワードでログインできる |
| **署名鍵の失効、クライアントシークレットのローテーション** | **失効した鍵・シークレットが有効に戻る** |
| 認可コード | 交換が失敗する（有効 60 秒なので影響は小さい） |

後の 2 行は、セキュリティを弱める方向の喪失で、放置できない。

本家の Private Cloud は RPO 1 分未満・RTO 15 分未満で、フェイルオーバーは自動（手動でも起動できる）とされる（[The Architect's View of Auth0's New Private Cloud Platform](https://auth0.com/blog/the-architect-s-view-of-auth0-s-new-private-cloud-platform/)、2026-09-27 に確認）。

## Options

失った範囲の扱い：

1. **失った範囲の、セキュリティを強める操作を、log-archive の監査ログと認証のイベントからやり直す。署名鍵の失効は、大阪への複製を確かめてから完了とする**
2. `rds.global_db_rpo` を設定し、大阪の遅れが上限を超えたら東京の書き込みを止める
3. 失った範囲を受け入れ、テナントへ知らせるだけにする

切り替えの起動：

- a. **人の判断で起動し、手順はワークフローで自動化する（S1・S2）**
- b. 自動で切り替える

## Decision

1 と a を採用する。

### 大阪の構成（S1・S2）

- Aurora Global Database の二次に reader を 1 台（東京の writer と同じ大きさ）。Valkey は大阪に別のクラスタを置く（複製しない。失ってよい）。
- `auth`・`signer`・`mgmt`・`worker` を最小のタスク数で動かす。ALB、VPC エンドポイント、SQS、ECR・Secrets Manager のレプリカ、Private CA、KMS のマルチリージョンの鍵のレプリカ（署名鍵・資格情報・pepper・データ）を常に置く。
- S3（discovery・JWKS、静的な資産）は東京 → 大阪へレプリケーションする。
- **`rds.global_db_rpo` は設定しない。** 大阪との回線の劣化だけで東京のログインが止まり、NFR-001 を損なう。2 リージョンだけの Global Database では、二次の側で既定のままにすることを AWS も勧めている（同上）。`AuroraGlobalDBRPOLag` を監視し、10 秒を超えたら呼び出す。

### 失った範囲のやり直し（1）

- **監査ログと認証のイベントを、log-archive（S3、大阪へレプリケーション）にも送っておく。** 切り替えの後、失った範囲（東京が応答しなくなった時刻 − 複製の遅延 − 5 分 から、昇格の時刻まで）の次の記録を取り出し、大阪の DB に対してやり直す。
  - パスワードの変更・再設定：該当のユーザーのパスワードを無効にし、再設定を求める（新しいハッシュは S3 に送らないので、戻せない）。
  - MFA の要素の削除、ユーザーのブロック・削除、セッションのログアウト、リフレッシュトークンの失効：同じ操作をやり直す。
  - 署名鍵の失効、クライアントシークレットのローテーション：同じ操作をやり直す。
- S3 のレプリケーションも非同期なので、上のやり直しは完全ではない。**署名鍵の失効は、大阪への複製を確かめてから、テナントに「完了」と返す。** 失効の操作は、Global Database の複製の位置が操作のコミットを越えるまで待つ（上限 30 秒。越えなければ「完了の確認中」を返し、runbook の手順で確かめる）。複製の位置を操作ごとに確かめる方法（`aurora_global_db_status()` などの関数で LSN を比べられるか）は未検証。E1 で確かめ、できなければ「コミットの後、`AuroraGlobalDBRPOLag` の 2 倍の時間を待つ」で代える。回数が少ない操作なので、待ちを許す。
- リフレッシュトークンのローテーションとサインアップの喪失は、再ログイン・再登録で回復する。テナントへ告知する。
- 2 は上の理由で採らない。3 は、失効した署名鍵が有効に戻るのを放置する。

### 切り替えの起動（a）

- 判断はインシデントの指揮者が行い、Ops の責任者が承認する。手順は [runbooks/disaster-recovery.md](../runbooks/disaster-recovery.md)。
- 切り替えのワークフロー（GitHub Actions、大阪で実行できるもの）が、Aurora のフェイルオーバー、大阪のタスク数の拡大、CloudFront のオリジンの切り替え（`active_region`）を順に行う。
- b は、東京の部分的な障害（1 つのサービス、ネットワークの一時的な劣化）を、データを失う切り替えと取り違える危険がある。S2 で RTO 15 分を目指すときに、判断の自動化（自動の検知と、1 クリックの承認）を再評価する。

### 段階を上げる基準と S3 のセル

- 段階を上げる基準は [infrastructure.md](../architecture/infrastructure.md) の 9 節に置く。
- **S3 でセル構成にする。** テナントを 1 つのセルに固定し、セルごとに主のリージョン（東京か大阪）を持つ。セルの外（Global）に置くのは、ホスト名 → テナント → セルの対応表、ダッシュボードの管理者の管理用のテナント、課金の集計だけ。
- 署名鍵と資格情報はセルの中に閉じる。1 つのテナントの鍵が 2 つのセルに存在しない。
- 大口のテナントに専用のセル（本家の Private Cloud の代わり。[intent.md](../intent.md) の Non-goals）。
- 複数リージョンで書ける DB（Aurora DSQL など）は、RLS を持たないため候補から外す（Stripe の ADR-0031 と同じ判断。DSQL の SQL の対応は Stripe の infrastructure.md の 10 節を参照）。

## Consequences

- 良くなること：
  - 計画外の切り替えの後も、失効した鍵・変えたパスワードが有効に戻ったままにならない。
  - 東京と大阪の回線の劣化で、東京のログインが止まらない。
- 引き受けるコスト：
  - 署名鍵の失効が、複製を待つぶん遅くなる（通常は 1 秒未満、最大 30 秒）。
  - 失った範囲のやり直しのジョブと、その訓練が要る。
  - 失った範囲のサインアップ・ローテーションは戻らず、一部のエンドユーザーに再ログイン・再登録を求める。
  - 大阪の待機の構成の費用が常にかかる（[infrastructure.md](../architecture/infrastructure.md) の 10 節）。

## Confirmation

- 四半期（staging）：書き込みを続けたまま計画外のフェイルオーバーを行い、次を確かめる。
  - RTO（判断から大阪でのログインの再開まで）が 1 時間以内。
  - 失った範囲に入れたパスワードの変更・鍵の失効が、やり直しのジョブで反映され、古いパスワード・失効した鍵が使えない。
- 年 1 回（本番）：switchover で大阪へ切り替え、ログインとトークンの発行を受け、東京へ戻す。
- 結合テスト：署名鍵の失効の API が、複製の位置を確かめてから完了を返す。
