# ADR-0054: 管理と運用の操作の監査ログは、認証のイベントのログと分け、操作と同じトランザクションで書いて改ざんできない保管庫へ送る

## Context

このシステムには、性質の違う 2 種類の記録がある。

| 記録 | 例 | 量（S1） | 読む人 |
| --- | --- | --- | --- |
| 認証のイベントのログ | ログインの成功・失敗、トークンの交換、MFA、ブロック | ピーク 数千件/秒 | テナントの管理者（Management API のログの検索、ログストリーム） |
| 管理と運用の監査ログ | 設定の変更、署名鍵のローテーション・失効、アプリのシークレットの再発行、メンバーとロールの変更、ユーザーの削除、社内の運用者の操作 | 1 日 数万件 | テナントの管理者、本システムのセキュリティの担当、監査 |

本家は、両方をテナントのログ（`type` のコードで区別）として見せる。保持はプランで 1〜30 日（[Auth0 Pricing](https://auth0.com/pricing)、2026-09-27 に確認）。

認証のイベントは量が多く、少なくとも 1 回の配信でよい（NFR-010）。監査ログは量が少ないが、欠けてはならず、改ざんを検知できる必要がある。署名鍵の失効の記録は、鍵の漏えいの調査の証拠になる。

他の題材は、監査ログを操作と同じトランザクションで `audit_events` に書き、log-archive の Object Lock のバケットへハッシュの連鎖で送っている（Slack の ADR-0018、Stripe の ADR-0023）。

## Options

1. **監査ログを認証のイベントのログと分ける。** 操作と同じトランザクションで `audit_events` に追記し、log-archive の Object Lock のバケットへハッシュの連鎖で送る
2. 1 つのログの系統にまとめ、`type` で区別する（本家と同じ）
3. CloudTrail とアプリのログだけで追う

## Decision

1 を採用する。他の題材の方式を引き継ぐ。

- **系統を 3 つにする。**

  | 系統 | テーブル | 書く時点 | 保管 |
  | --- | --- | --- | --- |
  | テナントの監査 | `audit_events`（テナントテーブル、RLS） | 操作と同じトランザクション | Aurora に 1 年 → log-archive（Object Lock）に 7 年（既定案。法務の L5） |
  | プラットフォームの監査 | `platform_audit_events`（RLS の外） | 同上 | 同上 |
  | 認証のイベント | logs-and-streams の領域のテーブル | outbox 経由で非同期 | logs-and-streams の領域で決める |

- **テナントの監査に書くもの**：テナントの設定、アプリケーション・API・接続の作成・変更・削除、クライアントシークレットの発行とローテーション、署名鍵のローテーション・失効、カスタムドメイン、メンバー・ロール・招待、攻撃の防御の設定、ログストリームの変更、ユーザーの削除・ブロック・MFA のリセット・一括の操作、Management API の M2M の許可の変更。
- **プラットフォームの監査に書くもの**：運用者の本番へのアクセス（[ADR-0056](0056-operator-access.md)）、サポートによるテナントのデータの参照、緊急の鍵の失効（本システムの判断で行うもの）、テナントの停止、break-glass の使用、ダッシュボードの管理用のテナントの非常用の経路の使用。
- **記録の形**：誰が（主体の種類と ID。M2M ならクライアントの ID）、いつ、何を、対象、成否、どこから（IP、ユーザーエージェント）、要求の ID、変更の前後の差分。**差分に秘密を入れない。** クライアントシークレットや接続の秘密は「変更した」とだけ書く。
- **改ざんの検知**：Relay が行ごとに前の行のハッシュを含めて log-archive へ送る。日次のジョブで連鎖を検証する。
- **テナントの管理者は、自分のテナントの監査ログを見られる。** ダッシュボードの「監査ログ」と Management API で、プランによらず 90 日を見せる（本家より長い。既定案）。
- 2 は、認証のイベントの量に監査の記録が埋もれ、保持と改ざんの防止の要件を分けられない。3 は、テナントの側の操作（Management API の呼び出し）が CloudTrail に出ない。

## Consequences

- 良くなること：
  - 署名鍵の失効や、シークレットの再発行の記録が、欠けずに残る。鍵の漏えいの調査で、いつ誰が何をしたかを確かめられる。
  - 監査の記録を、ログストリームの遅れや障害から切り離せる。
- 引き受けるコスト：
  - 書き込みが 1 行増える（管理の経路だけなので、量は小さい）。
  - 認証のイベントと監査ログで、ダッシュボードの見せ方が 2 つになる（dashboard の領域で扱う）。

## Confirmation

- 結合テスト：上に挙げた管理の操作のそれぞれで、同じトランザクションに `audit_events` の行があり、操作が失敗したら行も残らない。
- 性質ベーステスト：任意の設定の変更の差分に、秘密の値（シークレット、秘密鍵、TOTP の種）が含まれない。
- 日次：ハッシュの連鎖の検証。失敗したら呼び出す（[observability.md](../architecture/observability.md)）。
