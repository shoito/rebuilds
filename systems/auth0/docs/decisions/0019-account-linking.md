# ADR-0019: ID のリンクは両方の ID での本人の認証を必須にし、メールアドレスの一致だけでは自動にリンクしない

## Context

同じ人が、データベース接続とソーシャル接続（Google、Apple、LINE、GitHub）で別々にログインすると、別のユーザーになる。テナントは 1 人にまとめたい。

まとめ方を誤ると乗っ取りになる。たとえば、攻撃者が被害者のメールアドレスで、メールアドレスを確かめない IdP のアカウントを作り、そのメールアドレスの一致だけで被害者のユーザーにリンクされると、攻撃者は被害者としてログインできる。

本家 Auth0 は、主と従のリンクを持つ。リンクの前に両方のアカウントで認証を求めるべきで、手動のリンクでは毎回資格情報を入れさせるよう求めている。従のメタデータは捨てられ、主を消すと従も消える（[User Account Linking](https://auth0.com/docs/manage-users/user-accounts/user-account-linking)、2026-09-27 に確認）。

[ADR-0014](0014-connection-abstraction.md) で、ユーザーの特定は `(tenant_id, connection_id, provider_user_id)` の組でだけ行い、メールアドレスでは特定しないと決めた。

## Options

1. **リンクは、両方の ID で本人が認証したときだけ行う。ログインの途中の提案の画面と、アプリ・管理者の Management API の 3 つの経路を持つ。メールアドレスの一致だけで黙ってリンクしない**
2. 確認済みのメールアドレスが一致すれば、自動でリンクする（テナントの設定で有効にできる）
3. リンクを提供せず、アプリの側で対応表を持たせる

## Decision

1 を採用する。

- 提案の画面は、新しい ID の `email_verified` が真で、同じ確認済みのメールアドレスのユーザーがちょうど 1 人いて、テナントが `account_linking: prompt` にしたときだけ出す。既定は `off`。
- 既存のユーザーの認証には、テナントの MFA の方針をそのまま適用する。
- 従のユーザーの MFA の要素とパスキーは主へ移さない。従のセッションとリフレッシュトークンは失効させる。
- 従の `user_metadata`・`app_metadata` は捨てる（本家と同じ）。Management API の応答で 1 回だけ返す。
- 主の `user_id` は変えない。従の `user_id` は墓標に入れる（[ADR-0018](0018-user-identifier-and-profile-store.md)）。
- ブロック中のユーザーへのリンクと、ブロック中のユーザーと同じ確認済みのメールアドレスでの新しいユーザーの作成を止める（ブロックの回避を防ぐ。テナントの設定で外せる）。
- 管理者のリンクは本人の認証を伴わない。ダッシュボードで危険を示し、監査ログに残す。
- 2 は、IdP の `email_verified` の正しさに全面的に依存する。IdP の実装や、メールアドレスの再利用（退職者のアドレスの再割り当てなど）で乗っ取りになる。
- 3 は、テナントの多くが同じ処理を自前で作り、同じ誤りを繰り返す。

## Consequences

- 良くなること：
  - メールアドレスの一致だけによる乗っ取りの経路がない。
  - リンクの判断が決定表で書け、テストできる。
- 引き受けるコスト：
  - ユーザーは、リンクのときに既存のアカウントでもう一度ログインする手間がある。
  - 「自動でまとめてほしい」テナントの要望に、既定では応えない。

## Confirmation

- 決定表のテスト：[users-and-profiles.md](../architecture/users-and-profiles.md) の 5.3 と 12.1 の各行。
- 性質ベーステスト：任意の ID の作成とリンクの操作の列で、本人の認証（または管理者の操作）を経ずに、2 つの ID が同じユーザーになることがない。
- 結合テスト：従のユーザーの MFA の要素が、リンクの後に主のユーザーの要素の一覧に現れない。
