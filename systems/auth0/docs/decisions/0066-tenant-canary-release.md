# ADR-0066: 認証の経路の振る舞いの変更は、テナントを単位に、社内・開発の環境・本番の順で広げ、認証の成功率のガードで自動で止める

## Context

他の題材は、AWS AppConfig のフラグで release・ops・experiment・permission の種類を持ち、利用者やワークスペースの割合で広げる（Slack の ADR-0026）。Stripe は、割り当ての単位を加盟店にし、お金の不変条件のガードで自動で止める（Stripe の ADR-0032）。

認証の経路には次の事情がある。

- **テナントには環境（`development`・`staging`・`production`）がある**（[ADR-0002](0002-tenancy-and-isolation.md)）。開発の環境のテナントは SLO の対象外で、テナントの開発者が本番の前に振る舞いを試す場所である。
- **1 つのテナントの中で、要求ごとに振る舞いが変わると困る。** 例えば、トークンのクレームの形が要求ごとに違うと、テナントの API の検証が不安定になる。セッションの Cookie の形が変わると、SSO がつながらない。
- **失敗は、5xx より「ログインの成功率の低下」として現れる。** 誤ってすべてのパスワードを拒否しても、応答は 400 で、可用性の SLI（[ADR-0062](0062-sli-and-synthetic-monitoring.md)）は下がらない。

## Options

1. **割り当ての単位をテナントにし、社内のテナント → 開発の環境のテナント → 本番のテナントの 1%・10%・50%・100% の順で広げる。認証の成功率のガードを AppConfig のアラームにつなぐ**
2. 要求の割合で広げる（ECS の blue/green のカナリアだけ）
3. テナントの管理者に選ばせる（オプトイン）

## Decision

1 を採用する。

- **判定**：`hash(flag_name + tenant_id) mod 100` をアプリで計算する（Slack の ADR-0026 と同じ方式で、単位をテナントにする）。許可リスト（社内のテナント、同意を得たテナント）と除外リスト（大口のテナントは最後にする）を持つ。
- **順番**：
  1. 社内のテナント（ダッシュボードの管理用のテナント、合成監視のテナント、社内のアプリ）
  2. 開発・ステージングの環境のテナントの 100%（テナントの開発者が本番の前に気づく期間。最低 7 日）
  3. 本番のテナントの 1% → 10% → 50% → 100%。各段で最低 24 時間
- **ガード**（フラグの有効なテナントと、無効なテナントを比べる。差が続いたらフラグを自動で切る）：
  | ガード | 条件 |
  | --- | --- |
  | ログインの成功率 | パスワードのログインの成功の割合が、無効な側より 2 ポイント以上低く、15 分続く |
  | トークンの交換の失敗 | `/oauth/token` の `invalid_grant` の割合が、無効な側の 2 倍 |
  | リフレッシュトークンの再利用の検知 | 系列の失効の件数が、無効な側の 3 倍（ローテーションの誤りは、再利用の誤検知として現れる） |
  | 可用性 | フラグの有効なテナントの 5xx の割合が 0.05% を超える |
  | 秘密の出力 | 走査の検出が 1 件（[ADR-0061](0061-secret-free-telemetry.md)）。フラグによらず即時に止める |
- **デプロイの blue/green のカナリアは別に持つ。** コードの入れ替えの失敗（起動しない、5xx）は、ECS のネイティブな blue/green（要求の 10% → 100%）のアラームで止める。振る舞いの変更は、テナントのフラグで広げる。
- **プロトコルの形を変える変更**（トークンのクレーム、エラーの形、discovery の値）は、テナントの設定のバージョン（テナントが選べる互換のバージョン）として出すかを、各領域で決める。フラグで全テナントに広げてよいのは、標準の範囲の中の変更だけ。
- **判断**：staging での受け入れは QA、社内 → 開発の環境 → 本番の 1% に進めるのは PM、10% 以降は PM と Ops。`security:sensitive` の認証を弱める方向の変更は、セキュリティの担当も判断に加わる（[ADR-0065](0065-security-sensitive-change-flow.md)）。止めるのは誰でもよい。
- 2 は、1 つのテナントの中で振る舞いが混ざる。3 は、多くのテナントが選ばず、100% にする時点で初めて問題が見つかる。

## Consequences

- 良くなること：
  - テナントの開発者が、開発の環境のテナントで先に変化に気づける。
  - エラーにならない失敗（ログインの成功率の低下）で、自動で止められる。
- 引き受けるコスト：
  - 本番の 100% まで、最低で 7 日＋4 日かかる。緊急の修正は、フラグを使わない（修正は forward fix で、[delivery.md](../architecture/delivery.md) の 7 節）。
  - 比べる相手（フラグの無効な側）が、1% の段ではテナントの構成の偏りで比べにくい。成功率は、テナントごとの平常との差でも見る。

## Confirmation

- 結合テスト：同じテナントの要求は、フラグの判定が常に同じ。
- AppConfig のデプロイ戦略のアラームに、上のガードのメトリクスが入っていることを、Terraform の検査で確かめる。
- 月次：ガードで自動で止まった回数と理由を振り返る。
