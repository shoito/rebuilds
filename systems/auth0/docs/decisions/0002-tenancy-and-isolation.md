# ADR-0002: テナントを分離と設定の単位にし、共有スキーマと RLS で分ける

## Context

本家 Auth0 では、テナントが設定・ユーザー・鍵・ドメインの単位である。開発・ステージング・本番は、別のテナントとして作る。テナントのドメインは `<tenant>.<region>.auth0.com` の形で、リージョン（米国、EU、豪州、日本、英国、カナダ）はテナントを作るときに選ぶ（[Public Cloud Service Endpoints](https://auth0.com/docs/troubleshoot/customer-support/operational-policies/public-cloud-service-endpoints)、2026-09-27 に確認）。本家の基盤は、利用者の識別子でデータを分ける共有の区画と、必要に応じた専用の区画を組み合わせている（[Multi-Subscriber Deployment on Converged Architecture](https://auth0.com/blog/multi-subscriber-public-cloud-deployment-on-converged-architecture/)、2026-09-27 に確認）。

テナントの分離が破れると、他の事業者のユーザーの情報が見える、他のテナントの鍵でトークンが作れる、といった致命的な事故になる。S1 で 1 万、S3 で 100 万のテナントを扱う。

## Options

1. **共有スキーマ＋RLS。** 全テナントテーブルに `tenant_id` を持たせる
2. **テナントごとのスキーマ**
3. **テナントごとの DB（silo）**

環境の分け方として、次も比べた。

- a. **環境ごとに別のテナント**（本家と同じ）
- b. 1 つのテナントの中で、Stripe のように `livemode` の列で分ける

## Decision

1 と a を採用する。

- **テナントの分け方は、他の題材（Slack の ADR-0009、Stripe の ADR-0002）に倣う。**
  - 全テナントテーブルに `tenant_id` を持たせ、主キーとインデックスの先頭に置く。ID は UUIDv7。
  - `FORCE ROW LEVEL SECURITY` を設定し、トランザクションごとに `SET LOCAL app.tenant_id` を設定する。
  - RLS を外すのは、テナントをまたぐ管理の処理（テナントの作成、課金の集計）だけにし、別の DB のロールで行う。
- **テナントの解決を、DB を読む前に行う。** 要求のホスト名（`<tenant>.jp.<brand>.<domain>` か、カスタムドメイン）から `tenant_id` を決める。ホスト名の対応表はプロセスの中にキャッシュする（[ADR-0005](0005-authentication-path-availability.md)）。解決できない要求は、どのテナントのデータにも触れずに 404 を返す。
- **環境ごとに別のテナントにする。** テナントに `environment`（`development`・`staging`・`production`）の属性を持たせる。本番のテナントだけを SLO の対象にし、レート制限の値も属性で変える。環境の間でユーザー・鍵・セッションを共有しない。b は、同じテナントの中で本番の鍵とテストの鍵が並び、取り違えの余地が残るので採らない。
- **テナントはリージョンに固定する。** テナントの作成時に `region` を決め、後から変えない。S1 は `jp`（東京、DR は大阪）だけにする。テナントの名前は、リージョンの中で一意にする。
- **カスタムドメインはテナントに属する。** S1 は 1 テナントに 1 つ。複数のカスタムドメインは S2 以降に扱う（custom-domains の領域）。
- **鍵もテナントに属する。** 署名鍵はテナントごとに持ち、他のテナントの鍵で署名できないことを Signer でも確かめる（[ADR-0003](0003-token-formats-and-signing-keys.md)）。
- **ダッシュボードの管理者（テナントのメンバー）と、エンドユーザーを分ける。** 管理者は複数のテナントに属しうる。エンドユーザーはテナントに属し、テナントをまたがない。
- 2 は、テナントの数（S3 で 100 万）に対してスキーマの数とマイグレーションが重い。
- 3 は、S1 の 1 万テナントで運用が重い。大口のテナントの分離は、S2 のシャードと S3 のセルで行う（infrastructure の領域）。

## Consequences

- 良くなること：
  - テナントの分離を、アプリのコードだけに頼らない。
  - 本番と開発のテナントが構成として分かれ、開発のテナントの負荷や設定の誤りが本番に及ばない。
- 引き受けるコスト：
  - 1 つの顧客（組織）が複数のテナントを持つ。請求と管理者の権限は、テナントの上の「アカウント」でまとめる必要がある（tenants-and-applications の領域）。
  - 大きなテナント（数百万のユーザー）が共有の DB を占有しうる。テナント単位のレート制限（management-api-and-rate-limiting の領域）と、S2 のシャードで抑える。
  - RLS のコンテキストの設定漏れは「ユーザーが見つからない」という形で現れ、ログインの失敗として見える。認証の経路の結合テストで、全エンドポイントのコンテキストの設定を確かめる。

## Confirmation

- 性質ベーステスト：任意の 2 テナントで、一方のコンテキストで他方の行が読めない。
- 結合テスト：未知のホスト名の要求が、DB に問い合わせずに 404 になる。
- 結合テスト：テナント A の要求で、テナント B の `kid` を指定して署名を求めると、Signer が拒否する。
- CI：新しいテーブルに `tenant_id` と RLS のポリシーがないマイグレーションを失敗させる（例外は許可リストで管理する。一覧は [data-model.md](../architecture/data-model.md) の 3 節）。
