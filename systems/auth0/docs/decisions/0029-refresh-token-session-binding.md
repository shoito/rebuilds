# ADR-0029: リフレッシュトークンの系列は、アプリの設定でセッションに結び付けるか独立にするかを決める

詳細は [sessions-and-sso.md](../architecture/sessions-and-sso.md) の 7 節。

## Context

ログアウトした後も、アプリがリフレッシュトークンで新しいアクセストークンを得られるなら、ログアウトの意味が薄れる。一方、モバイルアプリやテレビは、ブラウザのセッションと関係なく長くログインを保ちたい。

- OIDC Back-Channel Logout 1.0 は、`offline_access` なしで出したリフレッシュトークンをログアウトで失効させ（SHOULD）、`offline_access` 付きのものは通常は失効させない（SHOULD NOT）とする。
- 本家 Auth0 は、リフレッシュトークンを出す条件に `offline_access` を求める（[Refresh Tokens](https://auth0.com/docs/secure/tokens/refresh-tokens)、2026-09-27 に確認）。ログアウトでリフレッシュトークンを失効させるかは、資料で確かめられなかった（未検証）。
- [ADR-0003](0003-token-formats-and-signing-keys.md) は、系列（family）の単位で失効と再利用の検知を行うと決めた。

本システムもリフレッシュトークンに `offline_access` を求めるので、仕様の考え方をそのまま当てると、すべての系列がログアウトの後も残る。

## Options

1. **系列に `session_id` と `binding`（`session`・`independent`）を持たせ、アプリの設定で既定を決める**
2. すべての系列を、ログアウトで失効させる
3. すべての系列を、ログアウトの後も残す（仕様の字面どおり）

## Decision

1 を採用する。

- 既定：SPA と機密の Web アプリは `session`。Native とデバイスのフローは `independent`。アプリで変えられる。
- `session`：
  - セッションが終わる（ログアウト、取り消し、期限）と、系列も使えない。ログアウトの操作で、同じトランザクションで系列に `revoked_at` を書く。
  - 系列の利用はセッションの「使われた」に数える（最終の期限は延びない）。
  - 系列の最終の期限は、セッションの最終の期限を超えない。
  - 再利用を検知したら、系列に加えてセッションも終える。
- `independent`：失効、再利用の検知、系列の期限、ユーザーのブロック・削除、「すべての端末からログアウト」で止まる。Back-Channel Logout の対象にしない。
- デバイスのフローの系列は、承認に使ったスマートフォンのセッションに結び付けない。
- 2 は、モバイルアプリとテレビで、ブラウザのログアウトのたびに再ログインを強いる。3 は、ブラウザのアプリでログアウトが効かない。

## Consequences

- 良くなること：
  - ブラウザのアプリでは、ログアウトがトークンの更新まで止める。
  - ネイティブのアプリは、仕様の `offline_access` の考え方どおりに続く。
- 引き受けるコスト：
  - `session` の系列のリフレッシュで、セッションの読み込みが 1 回増える（Valkey か DB）。
  - SPA のリフレッシュトークンが、SSO のセッションの期限（既定 7 日）より長く使えない。長く保ちたい SPA は `independent` を選ぶ必要がある。

## Confirmation

- 性質ベーステスト：任意の操作の列で、`session` の系列は、結び付いたセッションが `active` でない間、リフレッシュに成功しない。`independent` の系列は、ログアウトの後もリフレッシュに成功する。
- 結合テスト：`session` の系列の再利用で、セッションが `refresh_reuse` で終わり、Back-Channel Logout が送られる。
