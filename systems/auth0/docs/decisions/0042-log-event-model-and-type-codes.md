# ADR-0042: 認証のイベントは本家の公開のスキーマと種類のコードに寄せ、`log_id` はテナントの中でコミットの順に単調にする

詳細は [logs-and-streams.md](../architecture/logs-and-streams.md) の 3 節。

## Context

テナントは、認証のイベントのログで、ログインの失敗の調査、攻撃の把握、SIEM への取り込みをする。本家から移るテナントは、本家の種類のコード（`s`、`fp`、`seacft` など）で検索やアラートを組んでいる。

本家は、ログのスキーマと種類のコードを公開している（[auth0/auth0-log-schemas](https://github.com/auth0/auth0-log-schemas)、2026-09-27 に確認）。ログを Management API で順に取り出すチェックポイントは、生成の時刻ではなく `log_id` の順で、件数の上限がない（[Retrieve Logs](https://auth0.com/docs/deploy-monitor/logs/retrieve-log-events-using-mgmt-api)、2026-09-27 に確認）。

本システムでは、ログは outbox → SQS → Worker で非同期に取り込む（[ADR-0005](0005-authentication-path-availability.md)）。複数の Worker が並行して書くと、イベントの時刻や UUIDv7 で `log_id` を付けたとき、小さい `log_id` が後からコミットされ、チェックポイントとストリームのカーソルが取りこぼす。

## Options

イベントの形：

1. **本家の公開のスキーマのフィールドと種類のコードに寄せる。`details` は種類ごとの許可リストのスキーマ**
2. 本システム独自の形（`event.type = "login.succeeded"` など）

`log_id`：

- a. **テナントをシャードに割り当て、シャードの唯一の書き手が取り込みの時点に採番する**
- b. イベントの発生の時点の UUIDv7
- c. 読み出しで「今から 1 分前まで」だけを返す水位線で、遅れて入るものを待つ

## Decision

1 と a を採用する。

- フィールドの名前と種類のコードは本家に寄せる。コードは本家の名前を含む識別子ではないので、リポジトリ共通の ADR-0006 に触れない。
- `details` は種類ごとの Zod のスキーマで検証し、知らないフィールドを落とす。秘密はスキーマに存在させない。認可コードの一部の表示も出さない（本家は出す）。
- `$event_schema.version` を持ち、足す変更だけをする。
- `log_id` は、`hash(tenant_id) mod 64` のシャードの唯一の書き手（DB の advisory lock を持つ Worker）が、`ingest_ms｜shard｜連番｜乱数` を base32 の 26 文字にして採番する。テナントの中で、コミットの順に単調に増える。
- `date` は発生の時刻で、`log_id` の順と一致しないことがある。文書に書く。
- 2 は、本家から移るテナントの検索・アラート・SIEM の設定を全部書き換えさせる。
- b は、並行の取り込みで小さい `log_id` が後からコミットされ、チェックポイントとカーソルが取りこぼす。
- c は、水位線より遅れた取り込み（Worker の停止、SQS の滞留）で、やはり取りこぼす。遅れの上限を保証できない。

## Consequences

- 良くなること：
  - 本家の利用者の知識と、SIEM の設定がそのまま使える。
  - チェックポイントとストリームのカーソルが、取りこぼしなしで前へ進む。
- 引き受けるコスト：
  - シャードごとに書き手が 1 つで、取り込みの並列度はシャードの数（64）で決まる。S1 のピーク 4,000 件/秒で 1 シャード約 60 件/秒。S2 でシャードを増やすときは、テナントのシャードの移し替えの手順（移す前の `log_id` より大きい値から始める）が要る。
  - 本家のコードの意味の一部は、名前から推したもの（未検証）。

## Confirmation

- 性質ベーステスト：任意の取り込みの順と書き手の交代について、テナントの中の `log_id` がコミットの順に単調に増える。
- 性質ベーステスト：任意の `details` の入力について、出力に秘密のフィールドの名前と秘密の形が現れない。
- CI：種類ごとのスキーマの変更が、足す変更だけであることを検査する。
- レビュー：新しい種類のコードを足すとき、本家のスキーマに同じ意味のコードがあればそれを使う。
