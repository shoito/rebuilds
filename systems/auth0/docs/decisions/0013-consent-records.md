# ADR-0013: 規約への同意は、文書の版ごとに追記だけの表に記録し、記録の成功をサインアップの完了の条件にする

## Context

サインアップの画面で、テナントの利用規約とプライバシーポリシーへの同意を取りたいテナントが多い。日本の B2C では、同意の有無と、どの版に同意したかを後から示せることが求められやすい。一方、誰の責任で、何を、どれだけの期間記録するかは、法務の確認待ちである（[intent.md](../intent.md) の L8）。

本家 Auth0 の New Universal Login は、サインアップの画面に規約への同意のチェックボックスを置く手段を、ページのテンプレートの部分（partials）や Forms で提供している。同意の記録そのものは、ユーザーのメタデータに書く例が示されているだけで、専用の記録の仕組みは資料で確かめられなかった（未検証。[Customize Signup and Login Prompts](https://auth0.com/docs/customize/login-pages/universal-login/customize-signup-and-login-prompts)、2026-09-27 に確認）。

OAuth の同意（第三者のアプリにスコープを許すこと）は、これとは別のものである。その記録（grant）は authentication-flows の領域が持ち、この ADR は扱わない。

## Options

1. **テナントが文書（規約・ポリシー）と版を登録し、同意を `consent_records` に追記だけで記録する。記録の書き込みを、ユーザーの作成と同じトランザクションで行う**
2. 本家の例のように、ユーザーのメタデータに同意の日時を書く
3. 同意の取得と記録はテナントのアプリに任せ、本システムは何もしない

## Decision

1 を採用する。

- **文書の登録**：`legal_documents` に、種類（`terms`・`privacy`・`custom`）、版（テナントが付ける文字列）、言語ごとの URL、発効の日時、`requires_reconsent`（新しい版で同意を取り直すか）を持つ。版は作ったら変えない（新しい版を足す）。
- **同意の方式**：テナントが接続ごとに選ぶ。
  - `checkbox`：チェックを必須にする。チェックなしの送信は、サーバーの側で拒否する（画面の `required` だけに頼らない）。
  - `notice`：「登録すると規約に同意したものとみなします」の文言を出す。記録の `method` に `notice` と残す。
  - `none`：出さない。記録もしない。
- **記録**：`consent_records` に、`tenant_id`・`user_id`・`document_id`・`version`・`locale`・`method`・`accepted_at`・`client_id`・`transaction_id`・`ip`・`user_agent` を持つ。追記だけにし、更新と削除を DB のロールで禁じる（ユーザーの削除のときの扱いは下の「持ち越し」）。
- **トランザクション**：`checkbox`・`notice` のときは、ユーザーの作成と同意の記録を同じ DB のトランザクションで書く。記録に失敗したら、ユーザーを作らない。
- **ソーシャル接続での初回のログイン**：ユーザーを作る前に、同じ同意の画面を 1 回出す（テナントが有効にした場合）。
- **版の更新**：`requires_reconsent` の版が発効したら、次のログインで同意の画面を出す。同意しないとログインを完了しない（テナントの設定で「通知だけ」も選べる）。
- **未成年**：年齢の確認や保護者の同意は、MVP では作らない。テナントは `custom` の文書で確認の文言を足せる。扱いは L8 の結論で決める。
- 2 は、メタデータがアプリから書き換えられ、版と時刻の証拠にならない。
- 3 は、ホスト型の画面でサインアップを行う以上、テナントが同意を取る場所がなくなる。

## Consequences

- 良くなること：
  - どの版に、いつ、どのアプリから同意したかを、Management API とログで示せる。
  - 記録のないユーザーが作られない。
- 引き受けるコスト：
  - 追記だけの表が、ユーザーの数×版の数で増える。保持の期間は L5・L8 の結論で決め、それまでは消さない。
  - ユーザーの削除（個人データの削除の請求）と、同意の証拠を残すことが衝突しうる。削除のときに `user_id` を仮名の値に置き換えて残すか、消すかは、法務の確認（L7・L8）の後に決める（users-and-profiles の領域）。
  - `ip`・`user_agent` は個人データになりうる。記録するかをテナントの設定にするかは L8 で決める。既定は記録する。

## Confirmation

- 結合テスト：`checkbox` の接続で、チェックのない送信がサーバーで拒否され、ユーザーも記録も作られない。
- 性質ベーステスト：任意のサインアップの要求の列で、`checkbox`・`notice` の接続で作られたユーザーには、必ず 1 件以上の `consent_records` がある。
- DB のテスト：アプリのロールで `consent_records` の `UPDATE`・`DELETE` が拒否される。
