# Quality: Slack

QA が持つ品質戦略。変更ごとのテスト設計は、各変更の `spec.md`（シナリオ・性質）と `plan.md`（Proof）に書く。

AI エージェントが実装の大部分を書く前提では、QA の仕事は「テストを書くこと」から次の 3 つへ移る。

1. **何をもって正しいとするかを先に決める**（シフトレフト）
2. **エージェントが自分で検証できる仕組みを整える**（確認ループと eval）
3. **本番で正しさを確かめ続ける**（シフトライト）

## 1. 品質目標とリスク

| 順位 | リスク | 影響 | 主な対策 |
| --- | --- | --- | --- |
| 1 | 権限外のメッセージが見える（API・配信・検索・通知のいずれか） | 情報漏洩。信頼を失う | 判定関数の集約（ADR-0005）、経路ごとの漏洩テスト、本番での監査ログ照合 |
| 2 | 成功を返したメッセージが消える | データ喪失 | DB を正本にする（ADR-0002）、障害注入テスト、バックアップの復元訓練 |
| 3 | メッセージの順序が端末ごとに違う、または欠ける | 会話が成り立たない | `seq`（ADR-0001）、性質ベーステスト、本番での欠損検知率の監視 |
| 4 | 重複投稿 | 混乱と不信 | 冪等キー、再送テスト |
| 5 | 送信から表示までが遅い | 「速い会話」が損なわれる | 負荷試験、SLO 監視（runbooks） |
| 6 | 未読数・メンションの数がずれる | 取りこぼしへの不安 | 性質ベーステスト、クライアントとサーバーの突合 |

## 2. シフトレフト

### 2.1 仕様レビューの関門

QA は Design 段の承認者として、各変更の `spec.md` を次の観点でレビューする。承認がなければ Build 段に進まない。

- [ ] すべての要件に ID があり、EARS の形で書かれている
- [ ] すべての要件に、正常系と異常系のシナリオがある
- [ ] 権限に関わる要件には、「権限がない場合」のシナリオがある
- [ ] 並行処理・再送・切断に関わる要件には、正しさの性質（`PROP-...`）がある
- [ ] 条件の組み合わせで結果が決まる規則（特に権限）は決定表（`DT-...`）で書かれ、組み合わせの漏れと条件の優先順位が明示されている
- [ ] 非機能要件（NFR）への影響が書かれている
- [ ] シナリオが、実装を見なくても判定できる具体的な値で書かれている
- [ ] 変更単位の `quality.md` が必要か（[process.md](../../../docs/process.md) の「変更単位の quality.md を作る条件」）。リスク 1〜3 位に触れる E2・E4・E7 の変更では、原則として必要

`plan.md` の Proof も QA がレビューし、各要件・性質を証明する手段があることを確認する。

### 2.2 テストのレベル構成

| レベル | 対象 | 道具 | 実行タイミング |
| --- | --- | --- | --- |
| 単体 | ドメインロジック（権限判定、AST 変換、未読計算） | Vitest | 保存時、PR |
| 表駆動 | `DT-...`：`spec.md` の決定表を直接読み込み、各行を 1 ケースにする | Vitest | PR |
| 性質ベース | `PROP-...`：順序、冪等性、権限、XSS | fast-check | PR |
| 契約 | API とイベントが契約（Zod / OpenAPI）に一致する | 契約から生成したテスト | PR |
| 結合 | API ＋ 実 DB ＋ Redis | Testcontainers | PR |
| 障害注入 | Redis 停止、Gateway 再起動、遅延・重複 | Toxiproxy | PR（短縮版）、夜間（完全版） |
| E2E | 複数ブラウザでの会話シナリオ | Playwright（ブラウザ 2〜3 個を同時に使う） | PR（主要シナリオ）、夜間（全件） |
| 負荷 | NFR-001〜003 | k6 | 夜間、リリース前 |

モックは外部サービス（メール送信など）に限る。DB と Redis はモックにしない。

### 2.3 エージェントの確認ループ

Claude は PR を出す前に、次を自分で実行し、すべて通ることを確認する。コマンドは `systems/slack/AGENTS.md` の Commands に書く。

1. 型検査と lint
2. 変更箇所に関わる単体・性質・結合テスト
3. 要件 ID の追跡検査（`plan.md` にある ID がすべてテストから参照されている）
4. UI の変更なら、Playwright のスクリーンショットを承認済みのモックと比べる

完了基準は、`plan.md` の Proof の表がすべて満たされていること。

### 2.4 テスト環境とテストデータ

- ローカルと CI は Docker Compose で同じ構成にする。
- テストデータは seed スクリプトで生成し、本番データは使わない。
- 負荷試験用に、5,000 人規模のワークスペースを生成するスクリプトを用意する。

## 3. AI 自体の品質

エージェントの振る舞いは `AGENTS.md`・Skills・Hooks で決まる。これらの変更はコードの変更と同じく回帰を起こしうるので、eval で守る。

- **eval の中身**：このリポジトリの実タスク 20〜50 件。各件は「プロンプト」と「受け入れ基準」の組にする。例：「REQ-MSG-004 を実装せよ」→ 基準は、テストが通る、`seq` の採番を別の方法で書いていない、など。
- **実行タイミング**：`AGENTS.md`・Skills・Hooks が変わったとき、および週次。
- **合否**：成功率が直近の基準値から 10 ポイント以上下がったら、マージしない。

## 4. 本番での品質検証（シフトライト）

SLI・SLO・アラート・リリースとロールバックは、Ops の [runbooks/](runbooks/README.md) にある。ここには、それらの指標を使って品質を判定する基準と、本番での品質検証の設計を書く。

### 4.1 品質の判定基準

| 指標（runbooks で定義） | 品質として許容できない状態 | 対応 |
| --- | --- | --- |
| クライアントの欠損検知率 | 1% 以上が 1 時間続く | 配信経路の欠陥として intent を起票する |
| 未読数の不一致率 | 0.1% 以上 | 未読計算の欠陥として intent を起票する。段階的リリースの途中なら、拡大を止めるよう Ops に依頼する |

### 4.2 本番での検証

- **合成監視**：専用ワークスペースで、1 分ごとに「投稿 → 別クライアントで受信 → 検索でヒット」を実行する。シナリオは QA が設計し、実行と監視は Ops が担う。
- **権限の監査**：配信・検索結果のサンプルを抜き出し、`channel_members` と突合する。1 件でも不一致があれば重大インシデントとして扱う。
- **カオス試験**：復旧後に、全クライアントの状態が DB と一致することを合格基準にする。実施手順は runbooks にある。

### 4.3 異常から intent へ

判定基準を外れた指標、権限監査の不一致、インシデントの振り返りは、Claude が調査結果を `changes/` 配下の新しい `intent.md` として起票する。PM が受理したものは、通常の Plan → Design の流れに乗る。

## 5. テスト計画

| Epic | 重点 | リリースの合否基準 |
| --- | --- | --- |
| E1 Walking skeleton | 投稿・履歴の冪等性と順序 | PROP-MSG-001, 002 が通る |
| E2 チャンネルと権限 | 権限のテーブル駆動テスト | 権限の全組み合わせが通る |
| E3 会話機能 | 編集・削除・スレッドのイベント整合 | E2E の会話シナリオが通る |
| E4 リアルタイム同期 | 障害注入のもとでの収束 | PROP-SYNC-001 が夜間の完全版で通る |
| E5 既読・通知 | 未読数の突合 | 不一致率 0.1% 未満（ステージング） |
| E6 検索とファイル | 経路ごとの漏洩テスト、日本語検索 | 漏洩テストの全件が通る |
| E7 負荷と運用 | NFR-001〜006 | k6 で目標を満たす。Runbook がある |
