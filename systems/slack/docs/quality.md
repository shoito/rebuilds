# Quality: Slack

QA が持つ品質戦略。変更ごとのテスト設計は、各変更の `spec.md`（シナリオ・性質）と `plan.md`（Proof）に書く。

AI エージェントが実装の大部分を書く前提では、QA の仕事は「テストを書くこと」から次の 3 つへ移る。

1. **何をもって正しいとするかを先に決める**（シフトレフト）
2. **エージェントが自分で検証できる仕組みを整える**（確認ループと eval）
3. **本番で正しさを確かめ続ける**（シフトライト）

## 1. 品質目標とリスク

| 順位 | リスク | 影響 | 主な対策 |
| --- | --- | --- | --- |
| 1 | 別のワークスペース、または権限外のチャンネルのデータが見える（API・配信・検索・通知・ファイルのいずれか） | 情報漏洩。信頼を失う | RLS による分離の強制（ADR-0009）、判定関数の集約（ADR-0005）、経路ごとの漏洩テスト、本番での監査 |
| 2 | 成功を返したメッセージが消える | データ喪失 | DB を正本にする（ADR-0002）、障害注入テスト、バックアップの復元訓練 |
| 3 | メッセージの順序が端末ごとに違う、または欠ける | 会話が成り立たない | `seq`（ADR-0001）、性質ベーステスト、本番での欠損検知率の監視 |
| 4 | 重複投稿 | 混乱と不信 | 冪等キー、再送テスト |
| 5 | 送信から表示までが遅い | 「速い会話」が損なわれる | 負荷試験、SLO 監視（runbooks） |
| 6 | 未読数・メンションの数がずれる | 取りこぼしへの不安 | 性質ベーステスト、クライアントとサーバーの突合 |
| 7 | 通知が届かない、重複する、権限外の内容を含む | 取りこぼし、情報漏洩 | 冪等性の性質ベーステスト、通知の経路の漏洩テスト（[read-state-and-notifications.md](architecture/read-state-and-notifications.md)） |
| 8 | AI エージェント（MCP）が、メンバーの権限を超えて読み書きする、または誤って投稿する | 情報漏洩、混乱 | MCP の性質ベーステスト、書き込みの既定の無効化、監査（ADR-0028） |
| 9 | 削除・保持の設定どおりにデータが消えない、または消えすぎる | 法令・契約の違反 | 削除の結合テスト（全テナントテーブルで 0 件）、リーガルホールドの優先（ADR-0019） |

## 2. シフトレフト

### 2.1 仕様レビューの関門

QA は Design 段の承認者として、各変更の `spec.md` を次の観点でレビューする。承認がなければ Build 段に進まない。

- [ ] すべての要件に ID があり、EARS の形で書かれている
- [ ] すべての要件に、正常系と異常系のシナリオがある
- [ ] 権限に関わる要件には、「権限がない場合」と「別のワークスペースの場合」のシナリオがある
- [ ] 並行処理・再送・切断に関わる要件には、正しさの性質（`PROP-...`）がある
- [ ] 条件の組み合わせで結果が決まる規則（特に権限）は決定表（`DT-...`）で書かれ、組み合わせの漏れと条件の優先順位が明示されている
- [ ] 非機能要件（NFR）への影響が書かれている
- [ ] シナリオが、実装を見なくても判定できる具体的な値で書かれている
- [ ] 変更単位の `quality.md` が必要か（[process.md](../../../docs/process.md) の「変更単位の quality.md を作る条件」）。Epic によらず、この節のリスク 1〜3 位に触れる変更、新しい種類のテスト基盤が要る変更、規模が「大」の変更では必要

`plan.md` の Proof も QA がレビューし、各要件・性質を証明する手段があることを確認する。

### 2.2 テストのレベル構成

| レベル | 対象 | 道具 | 実行タイミング |
| --- | --- | --- | --- |
| 単体 | ドメインロジック（権限判定、AST 変換、未読計算） | Vitest | 保存時、PR |
| 表駆動 | `DT-...`：`spec.md` の決定表を直接読み込み、各行を 1 ケースにする | Vitest | PR |
| 性質ベース | `PROP-...`：順序、冪等性、テナント分離、権限、XSS | fast-check | PR |
| RLS | `app` ロールで、コンテキストなし・別テナントのコンテキストでは行が読めず書けない。マイグレーションの lint | Testcontainers、SQL | PR |
| 契約 | HTTP：Hono RPC のクライアント型のスナップショットに差分がない。WebSocket：送受信するイベントが Zod スキーマに一致する | tsc、Vitest | PR |
| 結合 | API ＋ 実 DB ＋ Valkey | Testcontainers | PR |
| 障害注入 | Valkey 停止、Gateway 再起動、遅延・重複 | Toxiproxy | PR（短縮版）、夜間（完全版） |
| E2E | 複数ブラウザでの会話シナリオ | Playwright（ブラウザ 2〜3 個を同時に使う） | PR（主要シナリオ）、夜間（全件） |
| 負荷 | NFR-001〜003、NFR-006（負荷のもとでの `search_index_lag`）、NFR-010 | k6 | 夜間、リリース前 |

モックは外部サービス（メール送信など）に限る。DB と Valkey はモックにしない。

非機能要件のうち、次の 2 つは検証の経路を決めておく。

| NFR | 検証の経路 |
| --- | --- |
| NFR-005（成功を返したメッセージを失わない） | 障害注入（Valkey・Gateway・Relay の停止、Aurora のフェイルオーバー）のもとで、成功を返した `client_msg_id` がすべて DB にあることを確かめる（PR の短縮版、夜間の完全版）。本番では、カオス試験と復元の訓練で同じ基準を使う（4.2 節） |
| NFR-006（投稿から 10 秒以内に検索へ反映） | 結合テストで反映の経路を確かめ、k6 の負荷のもとで `search_index_lag` の p99 を測る。本番では、合成監視の「検索でヒット」と `search_index_lag` のアラート（runbooks の 4 節）で見る |

### 2.2.1 領域ごとの重点

2.2 節のレベル構成のうえで、領域ごとに次を必ず含める。詳しい観点は各設計文書の「テスト」の節にある。

| 領域 | 重点のテスト |
| --- | --- |
| 認証と権限（[identity-and-access.md](architecture/identity-and-access.md)） | 権限の決定表の表駆動テスト。Better Auth の許可リスト外のパス（例：`/api/auth/sso/register`）が 404 になる。セッションの取り消しが WebSocket に届くまでの時間。SAML の外部ペンテスト |
| リアルタイム（[realtime.md](architecture/realtime.md)） | 退出の直後のメッセージが外された人に届かない。Valkey のフェイルオーバーと `resync`、再接続の殺到の障害注入 |
| 通知（[read-state-and-notifications.md](architecture/read-state-and-notifications.md)） | 1 人に最大 1 回の性質。通知の適用順序の表駆動テスト。SQS の送信失敗の障害注入。メンション数の突合 |
| 検索（[search.md](architecture/search.md)） | TypeScript の判定関数と SQL の `readable_channel_ids()` が同じ集合を返す性質。検索の関数が他テナントの ID を返さない性質（ADR-0027）。読み直しで権限が理由で落ちた件数が 0。インデックスの版の比較 |
| ファイル・プレビュー（[files.md](architecture/files.md)、ADR-0016） | EICAR のテストファイルでのスキャンと隔離。SSRF のテスト（内部の IP、DNS の再バインド、リダイレクト） |
| クライアント（[client.md](architecture/client.md)） | 同期エンジンの性質ベーステスト（SharedWorker とタブ単体の両方）。送信キューの性質（`client_msg_id` ごとに 1 件）。3 エンジンの E2E（3 タブで WebSocket が 1 本、送信中の再読み込み、IME）。axe で違反 0。見た目の回帰。性能の予算 |
| MCP（[mcp.md](architecture/mcp.md)） | MCP が返すデータは、同じメンバーが API で読めるデータの部分集合である性質。`aud`・ワークスペース・取り消しの検証。仕様の適合（Protected Resource Metadata、401、古い版への 405） |
| 公開 API・アプリ（[public-api.md](architecture/public-api.md)、[apps.md](architecture/apps.md)） | 配信がボットの読める範囲の部分集合である性質。`ui_blocks` を任意に生成しても XSS にならない性質。署名のテストベクター。配信先の SSRF。インストールの判定の決定表。OpenAPI の破壊的変更の検査 |
| レート制限（[rate-limiting.md](architecture/rate-limiting.md)） | 許可された件数が上限を超えない性質。Valkey の停止中の振る舞い（一般は通す、認証は止める） |
| 利用状況の計測（ADR-0025） | 送信されるリクエストに本文・名前・ID が含まれない。計測を無効にしたワークスペースで gtag.js が読み込まれない |
| フィーチャーフラグ（ADR-0026） | release・migration のフラグの両方の状態でのテスト |
| セキュリティ（[security.md](architecture/security.md) の 10・11 節） | SAST、依存の検査、DAST、定期のペンテスト。脆弱性の期限（Critical は 24 時間で緩和、7 日で修正） |
| 削除と保持（ADR-0019） | ワークスペースの削除の後に、全テナントテーブルで該当の行が 0 件。復元の訓練で、削除の再適用が行われる |
| デプロイ（ADR-0022） | デプロイ中の k6 で、投稿のエラーが 0 件、最終状態が DB と一致 |

### 2.3 エージェントの確認ループ

Claude は PR を出す前に、次を自分で実行し、すべて通ることを確認する。コマンドは `systems/slack/AGENTS.md` の Commands に書く。

1. 型検査と lint
2. 変更箇所に関わる単体・性質・結合テスト
3. 要件 ID の追跡検査（`plan.md` にある ID がすべてテストから参照されている）
4. UI の変更なら、Playwright のスクリーンショットを承認済みのモックと比べる

完了基準は、`plan.md` の Proof の表がすべて満たされていること。

### 2.4 テスト環境とテストデータ

- ローカルと CI は Docker Compose で同じ構成にする。
- テストデータは seed スクリプトで生成し、本番データは使わない。
- 負荷試験用に、5,000 人規模のワークスペースを生成するスクリプトを用意する。

## 3. AI 自体の品質

エージェントの振る舞いは `AGENTS.md`・Skills・Hooks で決まる。これらの変更はコードの変更と同じく回帰を起こしうるので、eval で守る。

- **eval の中身**：開発リポジトリの実タスク 20〜50 件。各件は「プロンプト」と「受け入れ基準」の組にする。例：「REQ-MSG-004 を実装せよ」→ 基準は、テストが通る、`seq` の採番を別の方法で書いていない、など。
- **実行タイミング**：`AGENTS.md`・Skills・Hooks が変わったとき、および週次。
- **合否**：成功率が直近の基準値から 10 ポイント以上下がったら、マージしない。

## 4. 本番での品質検証（シフトライト）

SLI・SLO・アラート・リリースとロールバックは、Ops の [runbooks/](runbooks/README.md) にある。ここには、それらの指標を使って品質を判定する基準と、本番での品質検証の設計を書く。

### 4.1 品質の判定基準

| 指標（runbooks で定義） | 品質として許容できない状態 | 対応 |
| --- | --- | --- |
| クライアントの欠損検知率 | 1% 以上が 1 時間続く | 配信経路の欠陥として intent を起票する |
| 未読数の不一致率 | 0.1% 以上 | 未読計算の欠陥として intent を起票する。段階的リリースの途中なら、拡大を止めるよう Ops に依頼する |

### 4.2 本番での検証

- **合成監視**：専用ワークスペースで、1 分ごとに「投稿 → 別クライアントで受信 → 検索でヒット」を実行する。シナリオは QA が設計し、実行と監視は Ops が担う。
- **テナント境界と権限の監査**：配信・検索結果・ファイル取得のサンプルを抜き出し、`workspace_id` と `channel_members` と突合する。1 件でも不一致があれば重大インシデントとして扱う。
- **カオス試験**：復旧後に、全クライアントの状態が DB と一致することを合格基準にする。実施手順は runbooks にある。

### 4.3 異常から intent へ

判定基準を外れた指標、権限監査の不一致、インシデントの振り返りは、Claude が調査結果を Intent の Issue として起票する（[project-management.md](../../../docs/project-management.md)）。PM が受理したものは、`intent.md` か Epic・Story になり、通常の Plan → Design の流れに乗る。
