Slack は何をするサービスか

Slack は、会社やチームの中の会話を話題ごとの部屋（チャンネル）に分けて行うチャットです。メールと違い、宛先を選んで送るのではなく、部屋に書き込み、部屋にいる人が読みます。

速い会話

送ったメッセージが、相手の画面に 1 秒以内に、正しい順で出る。

取りこぼさない

未読・メンション・スレッドで、どこで何が起きたかを後から追える。

積み上がる知識

過去のやり取りを検索でき、チームの記録として残る。

この 3 つが、再構築の intent が掲げる価値です。規模の感覚は、S1 で 1 ワークスペース最大 5,000 人、全体で同時接続 5 万です。1 人が 1 日に何十ものチャンネルを開き、タブを開いたまま何時間も過ごす、という使われ方が設計の前提になっています。

設計の文書で効くところintent.md の「Proposed outcome」と「守るべき振る舞い」。

ワークスペース・アカウント・メンバー

顧客の組織 1 つが 1 つのワークスペースです。これがテナントの単位です。1 人の人間は、ログインのためのアカウントを 1 つ持ち、所属するワークスペースごとに別のメンバーになります。表示名・アイコン・ロールはワークスペースごとに違ってよいのです。

ロールできること（概要）
ownerすべて。主たる所有者（1 人）だけが所有権の移転とワークスペースの削除をできる
adminメンバーの管理、SSO などの設定
memberチャンネルを作る・参加する・投稿する
guest_multi招かれた複数のチャンネルだけに参加できるゲスト
guest_single1 つのチャンネルだけに参加できるゲスト

ボットと AI エージェントも、アカウントを持たないメンバーとして表します（account_id が NULL）。人と同じ権限の表で判定し、トークンのスコープで上限をかけます。

設計の文書で効くところADR-0010（テナントの中は member_id だけを参照する）、identity-and-access.md の 6 節。

会話の場：チャンネルと DM

メッセージはすべて、どれかの「会話の場」に属します。データモデルでは、4 種類をまとめて channels の 1 つの表で持ち、kind と is_private で区別します。

kind = channel、is_private = false。ゲスト以外のメンバーは、参加していなくても読め、検索でき、自分で参加できます。#general のように全員が入る既定のチャンネルが 1 つあります。

kind = channel、is_private = true。招かれた人だけが存在を知り、読めます。owner や admin でも、入っていなければ読めません。

DM（1:1）。kind = dm。名前を持たず、参加者の組（dm_key）で一意です。

少人数の DM。kind = group_dm。参加者の組が同じなら、同じ場を使い回します。

チャンネルは削除せずアーカイブします。アーカイブ済みのチャンネルは読めますが、投稿できません。

設計の文書で効くところdata-model/conversations.md の channels、identity-and-access.md の 6.4 節の決定表。

メッセージ・スレッド・リアクション

Slack のメッセージには、メールや掲示板にない決まりがいくつかあります。

  • スレッドは 1 段だけ。返信への返信はありません。「チャンネルにも送信」を選ぶと、返信がチャンネルの一覧にも出ます。
  • 編集は投稿者だけ。管理者も他人の本文は直せません（削除はできます）。前の本文は残しません。
  • 削除しても行は残る。本文を消したtombstone にします。返信のある親は「このメッセージは削除されました」と出し続けます。
  • リアクションは絵文字で 1 人 1 回ずつ。同じ絵文字をもう一度押すと外れます。ただし API はトグルにせず、付ける（PUT）と外す（DELETE）を分けます。再送で結果が反転しないためです。
  • 本文は HTML でも Markdown でもない。独自の軽い構文木（AST）を JSON で持ち、メンションは表示名ではなく member_id で持ちます。
設計の文書で効くところmessaging.md の「編集」「削除」「スレッド」「リアクション」、ADR-0006。

メンションと一斉通知

メンションは「この人に気づいてほしい」という印です。Slack には、人を指すものと、まとめて知らせるもの（一斉通知）があります。

書き方知らせる相手使える場所・人
@名前その人誰でも
@hereチャンネルの参加者のうち、いまアクティブな人ゲスト以外
@channelチャンネルの参加者全員ゲスト以外
@everyoneワークスペースの全員既定のチャンネルで、owner・admin

本家に合わせて、参加者が 6 人以上のチャンネルで一斉通知を送るときは確認を出し、スレッドの返信の中の一斉通知は通知しません。一斉通知は、メンバーごとの行に展開せず、メッセージの属性として 1 回だけ記録します。

投稿を編集して @佐藤 を書き足しました。佐藤さんにはどうなりますか？

編集で増えたメンションに通知を送ると、「後から大量に通知を送る手段」になるためです。メンション一覧とバッジには反映します（messaging.md の「編集」）。

設計の文書で効くところmessaging.md の「メンション」、architecture/README.md の 6 節の決定。

なぜ「順序」が難しいのか

チャンネルの全員が同じ順でメッセージを見る必要があります。時刻で並べればよさそうですが、うまくいきません。

時刻（created_at）や ID で並べる

サーバーごとに時計がずれる。同じミリ秒の投稿は順が決まらない。そして「間が抜けている」ことを判定できない。

チャンネル内の連番 seq

チャンネルの行の last_seq を、投稿と同じトランザクションで 1 増やして採番する。1, 2, 3… と欠番なく並ぶ。

連番なら「受け取った seq が直前 + 1 か」だけで欠けを見つけられます。既読の位置・未読数・差分取得も、すべて seq で表せます。編集・削除・リアクションも seq を 1 つ消費する「イベント」にします。代わりに、チャンネルの行のロックが採番のたびに起きます。書き込みが集中するチャンネルでの待ちは、負荷試験で確かめる項目です。

メッセージに付いたリアクションを外しました。チャンネルの seq はどうなりますか？

状態を変える操作は 1 つずつ seq を消費します。メッセージ本体の seq（作成時の値）は変わりません。付いていないリアクションを外すなど、状態が変わらない操作は消費しません。

設計の文書で効くところADR-0001、data-model.md の不変条件 I-2〜I-4。

リアルタイム配信の基本

相手の画面にすぐ出すには、サーバーから押し出す（push）経路が要ります。ブラウザとは WebSocket の接続を張りっぱなしにし、その接続を専門に持つ Gateway が配ります。

sequenceDiagram
  participant S as 送信者
  participant A as API
  participant D as DB
  participant R as Relay
  participant V as Valkey Pub/Sub
  participant G as Gateway
  participant B as 受信者
  S->>A: POST messages
  A->>D: 1 tx で message と outbox を書く
  A-->>S: seq を返す
  R->>D: outbox を 25ms ごとに読む
  R->>V: チャンネルへ publish
  V->>G: 購読している Gateway へ
  G->>B: WebSocket で push

書き込みの経路（API → DB）と配信の経路（Relay → Gateway）は分かれています。配信は落としてもよいものとして作り、正しさは DB と次の節の差分取得が持ちます（outbox）。1 投稿を参加者全員の接続へ配ることをファンアウトと呼び、Pub/Sub の購読は Gateway のノードごとに 1 回にまとめます。

設計の文書で効くところrealtime.md の 2 節と 5 節、ADR-0002、ADR-0013。

接続・切断・差分取得

ノート PC を閉じる、電車でトンネルに入る、サーバーをデプロイする。WebSocket は頻繁に切れます。切れても欠けないようにするのが、この設計の要です。

  1. API が短命で 1 回限りのチケットを発行する。ブラウザの WebSocket はヘッダーを付けられないため、Cookie や Bearer の代わりにこれで認証する。
  2. Gateway に接続し、hello でチケットを渡す。Gateway は読めるチャンネルを購読してから各チャンネルの last_seq を読む（逆順だと間のイベントを取りこぼす）。
  3. ready でチャンネルごとの最新の seq（heads）を受け取り、自分の持つ値と比べる。
  4. 受け取ったイベントの seq が「直前 + 1」でなければ欠けとみなす。
  5. GET …/events?after_seq=N で差分を取り、seq の順に当てる。重複は seq で捨てる。
  6. 差分が 1,000 件を超えたら、差分をあきらめて最新のページを取り直す。

途中の経路が詰まっても、Gateway はイベントを溜め込まず、その接続を切ります（遅い受信者）。クライアントが差分を取れば追いつけるからです。一斉の再接続に備え、待ち時間にはランダムな揺らぎ（ジッター）を入れます。

Valkey が数秒止まり、その間のイベントが Gateway に届きませんでした。メッセージはどうなりますか？

DB だけが正本で、Valkey は失われてよい配信のバスです。Gateway は状態を作らず、DB にも書きません。

設計の文書で効くところrealtime.md の 3 節・6〜8 節、client.md（クライアントの同期エンジン）。

在席と入力中：消えてよい情報

チャットには、保存しない種類の情報があります。

在席

名前の横の緑の点。active・away・offline の 3 状態。Valkey に TTL 付きで置き、端末が消えれば 90 秒以内に自然に消える。DB には保存しない。

入力中（typing）

「○○さんが入力中…」。3 秒に 1 回まで送り、5 秒で消える。DB も seq も通らず、取りこぼしても取り戻さない。

端末の操作状態

いまどの端末で何を見ているか。「見ている人にはプッシュ通知を送らない」の判定に使う。

在席は「誰が誰を見るか」の組み合わせが多く、全員分を配ると重くなります。そこで、画面に出している人（最大 500 人）だけを購読します。

設計の文書で効くところrealtime.md の 4 節「ストリームの種類」と 9〜10 節。

既読・未読とバッジ

チャンネルごとに「どこまで読んだか」を 1 つの数（last_read_seq）で持ちます。メッセージごとに既読の行を作るのではありません。

未読数 ≒ channels.last_seq − channel_members.last_read_seq

差で出すので、自分の投稿・スレッドの返信・リアクションなどのイベントも数に混ざります。「太字にするかどうか」が大事なので、近似で許容しています。

赤いバッジの数は正確に数えます。見落とすと「取りこぼさない」を損なうからです。last_read_seq より後の、自分へのメンションと一斉通知を数えます。DM は未読のすべてをメンションとして数えます。

スレッドは購読（フォロー）した人ごとに別の既読位置を持ちます。親の投稿者・返信した人・メンションされた人は自動で購読します。

既読の位置は後退しません（GREATEST で更新）。古い端末が遅れて既読を送っても、新しい位置を上書きしません。既読の変化は自分の他の端末にだけ配ります。

設計の文書で効くところread-state-and-notifications.md の 1〜3 節、intent.md の Open questions（未読数の正確さ）。

通知：誰に、どの経路で

通知の経路は、アプリ内（開いているタブ）、Web Push、メールの 3 つです。1 つのメッセージについて、受け手ごとに「通知するか」「どの経路か」を次の順に決めます。

  1. 投稿者本人、チャンネルを読めない人、無効化された人には送らない（送る直前に権限を確かめ直す）。
  2. チャンネルをミュートしていれば送らない。
  3. 通知レベル（すべて / メンションのみ / なし）で許されない理由なら送らない。
  4. おやすみモードの間は、メールだけを終了後に予定する。
  5. どこかの端末でそのチャンネルを見ていれば、何も送らない。
  6. どこかの端末を操作中なら、アプリ内だけ。
  7. それ以外は Web Push を送り、メールを 15 分後（設定による）に予定する。

Web Push は、ブラウザの提供元が運営する Push サービスを経由します。送り手は VAPID の鍵で名乗り、中身は暗号化します。端末に届くまでの時間は Push サービス次第なので、NFR-010 は「送信まで」を測ります。

設計の文書で効くところread-state-and-notifications.md の 4〜8 節、ADR-0014。

日本語の全文検索

日本語は語の間に空白がないので、「どこで語を区切るか」を決めないと索引を作れません。方法は 2 つあります。

文字を機械的に 2 文字ずつ（N-gram）切る。「東京都庁」→「東京」「京都」「都庁」。辞書が要らず、未知語や語の途中でも見つかる。ただし「京都」でも当たってしまうなど、関係のない一致が混ざる。S1 の pg_bigm はこちら。

辞書で意味のある語に切る（形態素解析。Sudachi、Kuromoji）。関連度の順位付けに向く。ただし辞書にない語や語の途中は取りこぼす。S2 の OpenSearch では、一致の判定は N-gram、順位付けは Sudachi と使い分ける。

もう 1 つの要は権限です。読めるチャンネルの集合を、検索の条件の中に入れます。PostgreSQL では、RLS のある表に LIKE をかけると pg_bigm の索引が使われません。そこで検索用の表だけ RLS を外し、関数を通してしか読めないようにしています（ADR-0027）。

検索の結果を取ってから、読めないチャンネルのものを API で除く。この方式の問題は？

後から除くと「20 件のはずが 17 件」のような形で存在が漏れます。だから条件に入れ、さらに読み直しで落ちた件数を 0 件であるべき指標として測ります。

設計の文書で効くところsearch.md の 3〜5 節、ADR-0004、ADR-0027。

権限：「見えない」は「存在しない」

チャットの権限は、ワークスペースのロールと、チャンネルの種別と、そのチャンネルに入っているかの組み合わせで決まります。この判定を1 つの関数にまとめ、API・WebSocket の購読・検索・通知のすべてが同じ関数を使います（ADR-0005）。経路ごとに判定を書くと、どこか 1 つが漏れるからです。

0 主体の解決 → 1 テナント → 2 メンバー → SET LOCAL
→ 3 ワークスペースの操作 → 4 チャンネル → 5 操作・スコープ

読めないプライベートチャンネルには、403 ではなく 404 を返します。403 は「そこに何かある」と教えてしまうからです。

admin が、自分の入っていないプライベートチャンネルの履歴を API で取ろうとしました。結果は？

owner や admin でも、入っていないプライベートチャンネルと DM は読めません。管理者が中身を見る経路（コンプライアンスのエクスポート）は、別の経路と監査ログで設計します。

設計の文書で効くところidentity-and-access.md の 6 節、ADR-0005。テナントの分離は共通の資料へ。

プラン・アプリ・AI エージェント

Slack のような SaaS は、料金のプランで容量と機能を変えます。設計では、プランから決まる値をentitlement としてワークスペースに持たせます。価格と課金はこの題材では扱いません。

FreeProBusiness+Enterprise
閲覧・検索できる履歴90 日無制限無制限無制限
アプリの数10無制限無制限無制限
SAML の SSO・SCIM——ありあり
監査ログ・リーガルホールド———あり

本家に合わせ、レート制限はプランで変えません。外の世界とのつながりは 3 つあります。MCP サーバー（AI エージェント向け。E9）、版付きの公開 API とアプリ（MVP の後、E12）です。アプリのボットの投稿は、人間の投稿と別の枠で制限します。

設計の文書で効くところADR-0033（ADR-0032 の初期値を改めたもの）、mcp.md、apps.md。

保持・削除・エクスポートの枠組み

会社のチャットは、業務の記録でもあります。企業の顧客は早い段階で次の機能を求めます。

  • 保持ポリシー：一定の期間を過ぎたメッセージを自動で消す。
  • リーガルホールド：訴訟や調査に備え、特定の人や場のデータを、削除の操作や保持ポリシーより優先して残す。
  • エクスポート：ワークスペースのデータを書き出す。プライベートチャンネルや DM を含むものは上位のプランだけ。
  • 削除の流れ：論理削除で即座に見えなくし、本文を消す。行は非同期の Worker が物理削除する。バックアップの期限が、削除の最終的な期限になる。

日本の個人情報保護法では、ワークスペースの中身は顧客から委託を受けて扱うデータ、アカウントの情報は自ら取得するデータ、という整理で設計しています。

法務の確認待ち全データのエクスポートで、メンバーへ自動で通知しないこと（本家と同じ既定案）が、個人情報保護法の扱いとして問題ないか。確認が済むまで E8 の workspace-export の spec を承認しません。
設計の文書で効くところADR-0019、security.md の 13〜14 節、intent.md の Open questions。

データモデルの読み方

全部で 83 表ありますが、核は次の数個です。テナントの中の表は、主キーの先頭に workspace_id を持ちます。

erDiagram
  accounts ||--o{ members : "has membership"
  workspaces ||--|{ members : "has"
  workspaces ||--o{ channels : "has"
  channels ||--o{ channel_members : "has"
  members ||--o{ channel_members : "joins"
  channels ||--o{ messages : "contains"
  messages ||--o{ messages : "thread root of"
  messages ||--o{ reactions : "has"
  messages ||--o{ mentions : "mentions"
  channels {
    uuid workspace_id PK
    uuid id PK
    text kind
    bigint last_seq
  }
  channel_members {
    uuid channel_id PK
    uuid member_id PK
    bigint last_read_seq
  }
  messages {
    uuid id PK
    uuid channel_id FK
    bigint seq
    uuid thread_root_id FK
    jsonb body
  }
  • channels.last_seq と channel_members.last_read_seq の差が、未読数の元です。
  • messages の自己参照（thread_root_id）がスレッドです。返信もチャンネルの seq を持ちます。
  • テナントの外にあるのは accounts など認証の表だけで、中の表は member_id を参照します。
  • DB の外のストア（Valkey、S3、検索）は正本ではなく、DB から作り直せます。
設計の文書で効くところdata-model.md の 3〜5 節。ER 図の記号は共通の資料へ。

用語集

ワークスペース
1 つの組織の Slack の単位。テナントにあたる。
アカウント
ログインのための、人ごとのグローバルな ID。テナントの外にある。
メンバー
ワークスペースの中での人（またはボット）。表示名とロールを持ち、テナントの中のデータはこれを参照する。
ゲスト
招かれたチャンネルだけに参加できる外部の人。複数のチャンネル用と 1 チャンネル用がある。
DM
Direct Message。1:1 または少人数の、名前のない会話の場。
スレッド
1 つのメッセージにぶら下がる返信の列。Slack では 1 段だけ。
tombstone
「削除済み」の印だけを残し、中身を消した行。順序や一意性を保つために使う。
AST
Abstract Syntax Tree。本文を段落・リンク・メンションなどの節の木として持つ形。
メンション
@名前 で特定の人に気づかせる印。通知とバッジの対象になる。
一斉通知
@here・@channel・@everyone。チャンネルやワークスペースの多くの人にまとめて知らせる。
seq
チャンネルの中で、状態を変える操作ごとに 1 ずつ増える連番。順序・欠けの検知・既読の位置に使う。
WebSocket
ブラウザとサーバーの間で、双方向に送り合える張りっぱなしの接続。
Gateway
WebSocket の接続を持ち、購読に応じてイベントを配るサーバー。書き込みはしない。
Pub/Sub
送り手が名前付きの経路に流し、その経路を購読している受け手全員に届く仕組み。保存はしない。
ファンアウト
1 つのイベントを多数の受け手へ複製して配ること。
在席
presence。メンバーがいま接続して操作しているかの状態。
おやすみモード
DND（Do Not Disturb）。指定した時間帯に通知を止める設定。
Web Push
ブラウザを閉じていても通知を届ける標準の仕組み。ブラウザの提供元の Push サービスを経由する。
VAPID
Voluntary Application Server Identification。Web Push で送り手のサーバーを鍵で名乗る方式（RFC 8292）。
N-gram
文字列を N 文字ずつずらして切った断片。2 文字なら bigram。
pg_bigm
PostgreSQL の拡張。2 文字の断片で全文検索の索引（GIN）を作り、LIKE の部分一致を速くする。
形態素解析
辞書を使って文を意味のある語に区切る処理。Sudachi・Kuromoji など。
entitlement
プランや個別の契約から決まる、ワークスペースが使える容量と機能の値。
SSO
Single Sign-On。会社の認証基盤（SAML・OIDC）でログインさせる仕組み。
SCIM
会社の人事・ID の台帳から、メンバーの作成・無効化を自動で反映する標準の API。
リーガルホールド
訴訟や調査のために、対象のデータを削除から守って残すこと。
MCP
Model Context Protocol。AI エージェントが外部のツールやデータを使うための標準のプロトコル。
