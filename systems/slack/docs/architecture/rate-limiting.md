# Rate limiting: Slack

レート制限、同時実行の制限、テナント単位の上限の共通設計。方式は [ADR-0029](../decisions/0029-rate-limiting.md)、ワークスペース単位の上書きと容量の上限の持ち方は [ADR-0032](../decisions/0032-plans-and-entitlements.md)、レート制限をプランで変えないことは [ADR-0033](../decisions/0033-slack-aligned-platform-and-plan-decisions.md) にある。

各領域の文書にある個別の上限は、この文書の枠組みに従う。数値の一覧は 4 節にまとめ、ここを正とする。

## 1. 目的と原則

| 目的 | 守るもの |
| --- | --- |
| 共有資源の保護 | 1 つのワークスペースや 1 つのアプリが、DB・Gateway・Worker を占有しない（ADR-0009 の pool モデルの前提） |
| 濫用の防止 | 総当たり、スパム、スクレイピング、AI エージェントのループ |
| 公平さ | プランによらず、すべてのワークスペースを同じ上限で扱う（ADR-0033） |
| 予測できること | 外部公開 API とアプリにとって、上限は契約の一部である。文書化し、応答で残りを知らせる |

- **制限は「誰が」と「どのテナントで」の 2 つの軸でかける。** 主体（IP、アカウント、メンバー、トークン、アプリ）ごとの上限と、ワークスペース全体の上限の両方を確かめ、どちらかを超えたら止める。
- **非同期の処理は、捨てずに遅らせる。** 通知の push や、イベントの配信などが対象。
- **同期の処理は、早く断る。** 429 を返し、いつ再試行してよいかを知らせる。

## 2. 層

| 層 | 場所 | 単位 | 目的 |
| --- | --- | --- | --- |
| L1 エッジ | AWS WAF | IP | 洪水・総当たりの粗い遮断（[security.md](security.md) の 6 節） |
| L2 接続 | Gateway | タスク、IP、アカウント | 接続の受け付けの速さ、同時接続の数、クライアントからのフレームの速さ（[realtime.md](realtime.md)） |
| L3 リクエスト | api・mcp・公開 API のミドルウェア | 主体、ワークスペース | tier ごとのレート |
| L4 資源 | ドメイン層 | チャンネル、メンバー | チャンネルへの投稿の速さなど、資源に固有の上限 |
| L5 同時実行 | ドメイン層 | ワークスペース、主体 | 重い処理（検索、エクスポート、一括処理）の同時実行数 |
| L6 非同期 | Worker | ワークスペース、送信先 | 通知の push、メール、イベントの配信の速さ |
| L7 容量 | ドメイン層 | ワークスペース | ストレージ、履歴、アプリの数などの上限（プランで決まる）。メンバー数は、規模の段階による技術的な上限で、プランでは決まらない（ADR-0033） |

## 3. 方式

### 3.1 計数

- **GCRA（Generic Cell Rate Algorithm）を Valkey で実行する。**
  - 1 つの制限の対象につき、キーを 1 つ（次に許される時刻 `TAT`）だけ持つ。
  - Lua スクリプトで、判定と更新を 1 回の往復で原子的に行う。
  - トークンバケットと同じ振る舞い（平均の速さ＋バースト）を、少ないメモリで表せる。
- キーの形は `rl:{workspace_id}:<limit>:<subject>` にする。`{workspace_id}` をハッシュタグにし、S2 の Valkey クラスタで、同じワークスペースのキーを同じシャードに置く。ワークスペースに属さない制限（IP、アカウント）は `rl:{global}:...` にする。
- 同時実行の制限（L5）は、Valkey のソート済み集合に「実行中の要求」を期限付きで入れて数える。処理の終わりに消し、異常終了しても期限で消える。

### 3.2 tier

外部公開 API とアプリのメソッドは、次の tier のどれかに属する。tier の名前は [public-api.md](public-api.md) と [apps.md](apps.md) から参照する。

| 名前 | 対象の例 |
| --- | --- |
| `tier-read` | 軽い読み取り（1 件の取得、チャンネルの情報） |
| `tier-read-heavy` | 重い読み取り（履歴、検索、一覧の全件） |
| `tier-write` | 書き込み（投稿、リアクション、編集） |
| `tier-admin` | 管理・設定の操作 |
| `limit-post-per-channel` | 1 つのチャンネルへの投稿（主体によらず、チャンネル単位） |
| `concurrency-bulk` | エクスポート・一括処理の同時実行 |

### 3.3 応答

| 経路 | 超えたとき |
| --- | --- |
| HTTP（内部 API・外部公開 API） | `429`。`Retry-After`（秒）を必ず付ける。本文は `{"error": {"code": "rate_limited", "limit": "<名前>", "retry_after": <秒>}}` |
| 外部公開 API だけ | 上に加えて、すべての応答に `RateLimit-Policy` と `RateLimit` ヘッダーを付ける。IETF の草案（draft-ietf-httpapi-ratelimit-headers-11、2026 年 5 月）に基づく。RFC になるまでは書式が変わりうることを、利用者向けの文書に明記する |
| WebSocket | 受け付けの制限は `4029`、クライアントからの送信が多すぎるときは `4008` で切る（[realtime.md](realtime.md)） |
| MCP | JSON-RPC のエラーで `retry_after` を返す（[mcp.md](mcp.md)） |
| 非同期（L6） | 捨てずに、SQS の遅延か再投入で遅らせる。期限（push の TTL など）を過ぎたら諦める |

### 3.4 Valkey が使えないとき

| 対象 | 振る舞い |
| --- | --- |
| 一般の制限（L3〜L5） | **通す側に倒す（fail-open）。** ただし、各タスクの中で、上限をタスク数で割った値の簡易な制限を続ける。Valkey の障害で、サービス全体を止めない |
| 認証の制限（OTP の送信、ログイン） | **止める側に倒す（fail-closed）。** 各タスクの中の厳しい制限と、WAF のルールで守る。OTP の送信の上限は、タスクの中で既定の 1/5 にする |

どちらの場合も、`ratelimit_backend_errors_total` を計数し、アラートを出す。

### 3.5 クライアントの振る舞い

- Web クライアントは、`Retry-After` の間は同じ要求を送らない。送信キュー（[client.md](client.md) の 3.6 節）は、`Retry-After` に従って再送する。利用者には「送信が混み合っています」と表示する。
- 公式の SDK（公開 API）は、`Retry-After` に従う再試行を既定で持つ。

## 4. 上限の一覧（S1）

**数値は初期値**で、負荷試験と運用で見直す。本家 Slack と同じく、**レート制限はプランで変えない**（[ADR-0033](../decisions/0033-slack-aligned-platform-and-plan-decisions.md)）。プランで変わるのは容量と機能だけで、大口の顧客への緩和は、ワークスペース単位の上書き（ADR-0032）で行う。

### 4.1 エッジ・接続・認証

| 対象 | 単位 | 上限 | 定義元 |
| --- | --- | --- | --- |
| すべての要求 | IP | 5 分に 2,000 件 | WAF（[capacity.md](capacity.md) の 3.5 節） |
| ログインの開始 | IP | 1 分に 30 回 | [identity-and-access.md](identity-and-access.md) の 11 節 |
| OTP の送信 | メールアドレス / IP | 1 時間に 5 回 / 20 回 | 同上 |
| WebSocket のチケットの発行 | セッション | 1 分に 10 回 | 同上 |
| WebSocket の受け付け | Gateway のタスク | 1 秒に 200 | [capacity.md](capacity.md) の 3.4 節 |
| 同時の WebSocket 接続 | メンバー（ワークスペースごと） | 10 本。超えたら古い接続から `4000` で切る | [realtime.md](realtime.md) の 12 節 |
| 同時の WebSocket 接続 | アカウント（ワークスペースをまたいだ合計） | 20 本 | ここで定める |
| クライアントからの送信（ping 以外） | 接続 | 1 秒に 10 フレーム、1 フレーム 16 KB まで | ここで定める |
| API トークンの検証の失敗 | IP | 1 分に 20 回 | [identity-and-access.md](identity-and-access.md) の 11 節 |

### 4.2 内部 API（Web クライアント）

| 対象 | 単位 | 上限 |
| --- | --- | --- |
| すべての API | メンバー | 1 分に 600 回（バースト 100） |
| 投稿 | メンバー | 1 秒に 1 件（バースト 5） |
| 投稿（人間） | ワークスペース | 1 秒に 200 件。アプリの投稿は含めない（4.3 節の別の枠。ADR-0033） |
| 投稿 | チャンネル（`limit-post-per-channel`） | 1 秒に 5 件（バースト 20） |
| 検索 | メンバー | 1 分に 30 回 |
| 検索の同時実行 | ワークスペース | 20 |
| ファイルのアップロード | メンバー | 1 分に 20 件 |
| 招待の送信 | ワークスペース | 1 日に 500 件 |

### 4.3 外部公開 API・アプリ（E12、MVP の後）

| tier | 単位 | 上限 |
| --- | --- | --- |
| `tier-read` | トークン | 1 分に 100 回 |
| `tier-read-heavy` | トークン | 1 分に 20 回 |
| `tier-write` | トークン | 1 分に 50 回 |
| `tier-admin` | トークン | 1 分に 10 回 |
| `limit-post-per-channel` | チャンネル | 1 秒に 1 件（アプリからの投稿。短いバーストを許す） |
| `tier-read-heavy` の履歴・スレッドの取得（未審査の配布型のアプリ） | インストール | 1 分に 1 回、1 回 15 件まで（ADR-0033） |
| `concurrency-bulk` | ワークスペース | 1 |
| すべての tier の合計 | ワークスペース | 1 分に 5,000 回 |

### 4.4 MCP

| 対象 | 単位 | 上限 |
| --- | --- | --- |
| 読み取り | トークン | 1 分に 60 回 |
| 書き込み | トークン | 1 分に 10 回 |
| すべて | ワークスペース | 1 秒に 50 回 |

### 4.5 非同期

| 対象 | 単位 | 上限 | 超えたとき |
| --- | --- | --- | --- |
| Web Push の送信 | ワークスペース | 1 秒に 200 件 | 遅らせる |
| push | 受け手 × チャンネル | 10 秒に 1 件 | まとめて「N 件の新着」にする（[read-state-and-notifications.md](read-state-and-notifications.md)） |
| 通知の planner の処理 | ワークスペース | 同時に処理するジョブの数を全体の 20% まで | 後回しにする（同上） |
| SES の送信 | 全体 | アカウントのクォータの 80% | 遅らせる |
| アプリへのイベントの配信 | アプリの送信先 | 1 秒に 30 件 | 遅らせる。失敗が続いたら配信を止める（[apps.md](apps.md)） |

### 4.6 容量（L7）

容量の上限（ストレージ、履歴、アプリの数）は、プランで決まる。値は [ADR-0033](../decisions/0033-slack-aligned-platform-and-plan-decisions.md) の表にある。メンバー数はプランで制限せず、規模の段階による技術的な上限（S1 は 5,000 人。[README.md](README.md) の 2 節）を全プランに共通でかける。

## 5. 例外と運用

- **上限を緩める例外は、ワークスペース単位の上書き（ADR-0032）だけで行う。** 変更は Ops が行い、監査ログに残す。コードに特定のワークスペースを書かない。
- **障害時には、特定のワークスペースやアプリの上限を一時的に厳しくできる。** 手順は、runbooks の「テナント間の負荷の偏り」に置く。
- 合成監視のワークスペースは、上限の対象から外さない。上限に当たったら、それ自体を異常として扱う。

## 6. 観測

- メトリクス：
  - `ratelimit_limited_total{limit, subject_type}`
  - `ratelimit_backend_errors_total`
  - 同時実行の使用率
- ワークスペースとアプリのラベルは、上位 N 件と「その他」に丸める（[observability.md](observability.md)）。
- アラート：
  - 特定の制限の 429 が急増した（攻撃か、クライアントの不具合か）
  - Valkey の計数が失敗している
- 外部公開 API の利用者向けに、アプリの管理画面で、tier ごとの消費と 429 の件数を見られるようにする（E12）。

## 7. テスト

- 性質ベーステスト：任意の要求の列について、許可された件数が、上限（平均の速さ × 時間＋バースト）を超えない。
- 結合テスト：
  - Valkey の停止中は、一般の制限は通し、認証の制限は止める。
  - `Retry-After` と、外部公開 API のヘッダーの値が正しい。
- 負荷試験：上限の付近で、429 の判定が DB と Gateway の負荷を増やさない（判定は Valkey の 1 往復だけ）。

## 8. 段階ごとの変化

| 段階 | 変化 |
| --- | --- |
| S2 | Valkey をクラスタにする。キーのハッシュタグで、ワークスペースの計数を同じシャードに置く |
| S3 | ワークスペース単位の制限は、セルの中で閉じる。アカウント・IP の制限（認証）は、セルの外のアイデンティティ面で数える（ADR-0023） |
