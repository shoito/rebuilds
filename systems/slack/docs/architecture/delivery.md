# Delivery: Slack

ブランチ、CI、デプロイ、リリースの流れ。関係する方針は次のとおり。

| 対象 | 方針 |
| --- | --- |
| ブランチモデル | リポジトリ共通の [ADR-0002](../../../../docs/decisions/0002-trunk-based-development.md)（トランクベース開発） |
| AWS の CI/CD の構成 | [infrastructure.md](infrastructure.md) の 6 節 |
| IaC | [ADR-0020](../decisions/0020-infrastructure-as-code-with-terraform.md) |
| デプロイとマイグレーション | [ADR-0022](../decisions/0022-zero-downtime-deploy-and-migrations.md) |
| フィーチャーフラグ | [ADR-0026](../decisions/0026-feature-flags.md) |
| 手順 | [runbooks/deploy-and-rollback.md](../runbooks/deploy-and-rollback.md) |

原則は 2 つ。

- **`main` は常にデプロイできる状態に保つ。**
- **デプロイ（コードを置くこと）とリリース（機能を有効にすること）を分ける。** デプロイは Ops が承認し、リリースは PM が判断する。

## 1. 変更からマージまで

```
changes/YYMMDD-<slug>/ の spec・plan が承認済み
   │
   ▼
ブランチ slack/YYMMDD-<slug>（エージェントは worktree ごとに 1 本）
   │  エージェントが確認ループを回す（quality.md の 2.3 節）
   ▼
PR ─▶ PR の CI（2 節） ─▶ レビュー（CODEOWNERS、作成者と別の人）
   │
   ▼
merge queue（最新の main と合わせて CI をもう一度） ─▶ squash で main へ
```

- 1 つの変更フォルダに、複数の PR があってよい。ただし、どの PR も単独で `main` を壊さない。未完成の振る舞いは、release フラグの裏に置く。
- PR の説明には、変更フォルダ、規模、使うフラグを書く（`.github/pull_request_template.md`）。
- エージェントは PR を作れるが、承認とマージの判断はしない。

## 2. CI

### 2.1 PR の CI

変更のあったパッケージと、それに依存するパッケージだけを検査する（pnpm と Turborepo の依存グラフで絞る）。目標は 15 分以内。

| 段 | 内容 | 失敗の条件 |
| --- | --- | --- |
| 静的検査 | 型検査、lint、フォーマット | 1 件でも |
| 単体・性質・表駆動 | Vitest、fast-check、`spec.md` の決定表 | 1 件でも |
| 結合 | Testcontainers（PostgreSQL、Valkey）、RLS のテスト | 1 件でも |
| 契約 | Hono RPC のクライアント型のスナップショット、WebSocket のイベントスキーマ（ADR-0008） | 差分があるのに、契約の変更の承認がない |
| フラグ | release・migration のフラグの両方の状態で、結合テストを実行する（ADR-0026） | 1 件でも |
| 追跡 | 要件・性質・決定表の ID が、テストから参照されている。ID が重複していない | 漏れ・重複 |
| マイグレーション | マイグレーションの lint（ADR-0022） | 規則の違反 |
| E2E（主要シナリオ） | Playwright（Chromium）で、2 人の会話、切断と再接続 | 1 件でも |
| Web | バンドルの大きさ、axe による a11y の検査（[client.md](client.md) の 11・12 節） | 予算の超過、違反 |
| セキュリティ | SAST（CodeQL）、依存の脆弱性、秘密情報の混入（[security.md](security.md)） | High 以上 |
| インフラ（`infra/` の変更時） | `fmt`、`validate`、tflint、Checkov、`plan`、plan のポリシー検査（ADR-0020） | 違反、状態を持つリソースの削除・置き換え |
| エージェントの eval（`AGENTS.md`・Skills・Hooks の変更時） | quality.md の 3 節 | 成功率の低下 |

### 2.2 夜間の CI

- E2E の全件を、3 つのブラウザエンジンで実行する。
- 障害注入の完全版を実行する（quality.md の 2.2 節）。
- 見た目の回帰を検査する。
- staging に対して、負荷試験と DAST を行う。

失敗したら、翌営業日に Dev と QA が確認する。夜間の CI が 2 日続けて失敗している間は、release フラグを広げない。

## 3. ビルドと成果物

- `main` へのマージごとに、1 回だけビルドする。
- サーバーの成果物は、コンテナイメージ（api、gateway、relay、workers、migrator）にする。ECR に不変のタグで push し、digest で参照する。
  - イメージには、SBOM と、ビルドの来歴（provenance）を付ける。
- Web の成果物は、ハッシュ付きのファイル名の静的ファイル一式にする。ビルドのたびに、S3 の新しいパスに置く。
- リリースの識別子は、`<日付>-<コミットの短いハッシュ>` にする（例：`2026-09-26-a1b2c3d`）。ログ・トレース・Web クライアントの計測に、この識別子を付ける。

## 4. デプロイ

### 4.1 環境の昇格

```
main へのマージ ─▶ dev（自動） ─▶ staging（自動、E2E・スモーク・デプロイ中の k6）
                               ─▶ prod（Ops の承認）
```

- prod へのデプロイは、平日の 10〜17 時（日本時間）に行う。金曜の 15 時以降と、年末年始などの凍結期間は、修正以外のデプロイをしない。
- エラーバジェットを使い切っている間は、修正以外のデプロイをしない（[runbooks/README.md](../runbooks/README.md) の 1 節）。
- 目安の頻度は、1 日 1 回以上。変更を溜めないほうが、1 回のデプロイの危険が小さい。

### 4.2 デプロイの順序

| 順 | 対象 | 方式 |
| --- | --- | --- |
| 1 | マイグレーション（expand） | 1 回だけ実行する ECS タスク（`migrator` ロール） |
| 2 | relay、workers | ローリング |
| 3 | api | blue/green のカナリア（10% → 100%）。アラームで自動ロールバック |
| 4 | gateway | ローリングで 10% ずつ。接続を少しずつ移す |
| 5 | Web | 新しい静的ファイルを置いてから、`index.html` を差し替える |

### 4.3 新旧の混在

デプロイ中や、古いタブを開いたままの利用者がいるため、新旧のバージョンが同時に動く。

- **サーバーは、1 つ前のバージョンのクライアントと互換を保つ。** API の入出力と WebSocket のイベントは、項目の追加だけを行う。削除や意味の変更は、expand/contract と同じく 2 回以上のリリースに分ける。
- **クライアントは、起動時と再接続時に、自分のバージョンを送る。** サーバーが対応する最小のバージョンを下回っていたら、クライアントは再読み込みを促す。未送信のキューは IndexedDB に残るので、再読み込みで失われない（[client.md](client.md) の 3.6 節）。
- Service Worker は、新しい版を見つけたら待機させる。次にタブを開き直したときに切り替える。

## 5. リリース（機能を有効にする）

```
デプロイ済み（フラグ無効）
   │ QA：staging でフラグを有効にし、Proof を満たすことを確認
   ▼
社内のワークスペース ─▶ 5% ─▶ 25% ─▶ 100%
   各段で 24 時間以上、runbooks の 1 節の指標と quality.md の 4.1 節の基準を見る
   │
   ▼
100% で 2 週間 ─▶ フラグをコードから消す（plan.md の削除のタスク）
```

| 判断 | 誰が |
| --- | --- |
| staging での受け入れ | QA |
| 社内 → 5% に進める | PM（QA の受け入れが前提） |
| 5% → 25% → 100% に進める | PM。Ops が指標に問題がないことを確認する |
| 止める・戻す | 誰でもよい（ops フラグ・release フラグを切る）。切ったら、インシデントの要否を Ops が判断する |

- 企業向けのプランのワークスペースは、100% の段の最後に有効にする。企業顧客への告知が要る変更は、PM が事前に告知する。
- リリースノートは、Conventional Commits の `feat` と、100% に達したフラグから作る。利用者向けの文面は PM が書く。

## 6. ホットフィックス

- 本番の問題は、まずフラグで止める（ops・release フラグ）。
- 修正は、通常と同じく `main` への PR で入れる（forward fix）。リリースのためのブランチは作らない。
- 急ぐときは、次の短縮を認める。
  - 承認者は、変更の作成者と別の人 1 人でよい。
  - prod へのデプロイは、時間帯の制限を受けない。
  - staging での自動の検査は省略しない。
- フラグで止められず、修正も間に合わないときは、1 つ前のイメージの digest で再デプロイする（[runbooks/deploy-and-rollback.md](../runbooks/deploy-and-rollback.md)）。マイグレーションは戻さない。

## 7. 指標

DORA の 4 指標を月次で見る。

| 指標 | 目標 |
| --- | --- |
| デプロイの頻度 | 1 日 1 回以上 |
| 変更のリードタイム（マージ → prod） | 1 日以内 |
| 変更の失敗率（ロールバック・フラグでの停止・修正のデプロイが必要になった割合） | 15% 未満 |
| 復旧までの時間 | 1 時間未満 |

このほかに、次の 3 つも見る。

- エージェントが作った PR のうち、差し戻しなしでマージされた割合
- merge queue の待ち時間
- 残っているフラグの数
