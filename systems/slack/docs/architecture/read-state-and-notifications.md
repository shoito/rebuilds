# Read state and notifications: Slack

既読・未読、メンションのバッジ、通知（Web Push、メール）、通知設定。Relay と Worker の間のキューと通知の配送は [ADR-0014](../decisions/0014-sqs-worker-queues-and-notification-delivery.md) で決めた。リアルタイムのイベントの流れは [realtime.md](realtime.md) にある。

## 1. 既読と未読数

- 未読数は `channels.last_seq - channel_members.last_read_seq` を基本とする。自分の投稿やスレッド返信など、本来は数えないものが含まれても近似として許容する（正確な数よりもバッジの有無が重要なため）。
- 既読更新は `POST /workspaces/{ws}/channels/{id}/read {seq}` で行い、`GREATEST(last_read_seq, :seq)` で後退しないようにする。
- 既読イベントは、同じメンバーの他端末にだけ配信する。

### 補足

- **既読の送り方**：クライアントは、表示中のチャンネルの最新の `seq` を、1 秒の間引き（debounce）と、タブが背面に回ったときに送る。スクロールのたびに送らない。
- **他端末への配信**：API は既読を更新したトランザクションで outbox に `read.updated { channel_id, last_read_seq }` を積み、Relay がメンバーのストリーム（`ws:{w}:m:{member_id}`）に流す。チャンネルの `seq` は消費しない。
- **未読の要約**：`GET /workspaces/{ws}/unreads` が、参加しているチャンネルごとの `last_seq`・`last_read_seq`・メンション数と、未読のスレッド数を返す。クライアントは起動時・再接続時・タブが前面に戻ったときにこれを取り、それ以外はイベントで更新する。
- **ミュート**したチャンネルは、未読があっても強調しない。メンションのバッジだけは出す。

## 2. スレッドの既読

スレッドの返信はチャンネルのメッセージとして `seq` を持つ。スレッドの既読は、[messaging.md](messaging.md) の `thread_subscriptions`（`subscribed`、`last_read_seq`）で持つ。自動で購読する条件もそちらにある（親の投稿者、返信した人、スレッドでメンションされた人）。

- **未読の判定**：親メッセージの最後の返信の `seq`（`messages.last_reply_seq`。親に非正規化する。[data-model/conversations.md](data-model/conversations.md) に反映済み）が `last_read_seq` より大きく、`subscribed` が真なら未読。
- **既読の更新**：`POST /workspaces/{ws}/threads/{root_id}/read {seq}`。チャンネルと同じく後退させない。他の端末へは `thread_subscription.updated` で知らせる（チャンネルの `seq` は消費しない）。
- **未読の一覧**：「スレッド」画面は、購読中で未読のスレッドを最後の返信の新しい順に並べる。`(workspace_id, member_id, subscribed)` で絞れるインデックスを持つ。
- チャンネルの未読数には、スレッドの返信を数えない形を目指すが、MVP では 1 節の近似のままにする。「チャンネルにも送信」した返信は、チャンネルのメッセージとしても数える。

## 3. メンションのバッジ

メンションの数は、チャンネルの未読数と違い **正確に** 数える。見落とすと「取りこぼさない」（intent.md）を損なうため。

| 種類 | 記録の仕方 | バッジの対象 |
| --- | --- | --- |
| @メンバー | `mentions` にメンバーごとに 1 行 | 本人 |
| @channel / @here / @everyone | メッセージの属性（`messages.broadcast_mention`）として 1 回だけ記録する。全員分の行を作らない（[messaging.md](messaging.md)） | チャンネルの参加者全員。@here も、バッジは全員に出す（通知は在席している人だけ。5 節） |
| DM・グループ DM | 記録しない | すべての未読のメッセージをメンションとして数える |
| キーワード | 記録しない | バッジの対象にしない（通知だけ） |

- **数え方**：`last_read_seq` より大きい `seq` を持つ、自分へのメンションと @channel / @here のメッセージの数。`mentions` に `seq` を持たせ、`(workspace_id, member_id, channel_id, seq)` のインデックスで数える（[data-model/conversations.md](data-model/conversations.md) に反映済み）。
- **リアルタイムの更新**：`message.created` の本体にはメンションの一覧（メンバー ID と @channel / @here）が入っている。クライアントは、自分が含まれていて、投稿者が自分でなければバッジを増やす。大規模チャンネルで本体を受け取らない接続には、`channel.head` の `has_mention_for_you` で知らせる（[realtime.md](realtime.md) の 5.3 節）。
- **編集・削除**：編集でメンションが増えたらバッジは増やすが、通知はしない（[messaging.md](messaging.md)）。メッセージが削除されたら、そのメンションは数えない。
- **正本との突合**：クライアントが数えた値と、未読の要約 API の値を再接続時に比べ、ずれを不一致率の指標として送る（[runbooks](../runbooks/README.md) の SLI）。

## 4. 通知のパイプライン

```
API ─tx─▶ outbox ─▶ Relay ─▶ SQS notify-events ─▶ 通知の計画（planner）
                                                     │ 受け手を決める。大人数なら分割する
                                                     ├──▶ SQS notify-fanout ─▶ planner（分割した受け手の続き）
                                                     ├──▶ SQS notify-push ───▶ push の送信 ─▶ Web Push サービス
                                                     └──▶ notification_pending_emails（DB）
                                                                   │ 1 分ごと
                                                                   ▼
                                                              メールの送信 ─▶ SES
```

- Relay は `message.created`、`message.deleted`（未送信の通知の取り消し）、`channel.member_left` を `notify-events` へ送る。`message.edited` は送らない（編集で増えたメンションには通知しない。[messaging.md](messaging.md)）（[realtime.md](realtime.md) の 11 節）。
- **planner** は、ジョブの `workspace_id` でテナントのコンテキストを設定してから処理する（ADR-0009）。メッセージの本体・受け手の候補・設定を DB から読み、受け手ごとに「通知するか、どの経路で」を決める（5〜6 節）。
- 受け手が 500 人を超えるとき（@channel など）は、500 人ずつに分けて `notify-fanout` に積み、1 回の処理を短く保つ。`notify-fanout` は `notify-events` と別のキューにし、大人数の通知が DM やメンションの通知を待たせないようにする。
- **push の送信** は 1 受け手 1 ジョブにする。受け手の push の購読（端末）ごとに送る。
- **メール** は遅らせて送るので、SQS ではなく DB に「送る予定」として置く（7 節）。SQS の遅延は最大 15 分で、1 時間などの遅延を表せないため。
- 各キューにはデッドレターキューを付ける（10 節）。

## 5. 誰に通知するか

1 つのメッセージについて、受け手ごとに **理由を 1 つ** に決める。複数に当たるときは、上の行を優先する。

| 優先 | 理由 | 候補になる人 |
| --- | --- | --- |
| 1 | DM・グループ DM | 投稿者以外の参加者 |
| 2 | @メンバー | メンションされたメンバー |
| 3 | スレッドの返信 | スレッドをフォローしている人（2 節） |
| 4 | キーワード | 本文のテキストに、本人が登録したキーワードを含むチャンネルの参加者 |
| 5 | @channel / @everyone | チャンネルの参加者全員（@everyone は既定のチャンネルでだけ使える） |
| 5 | @here | チャンネルの参加者のうち、その時点で在席が `active` の人（[realtime.md](realtime.md) の 9 節） |
| 6 | すべてのメッセージ | 通知レベルが「すべて」の参加者 |

- 候補の全員について、**送る直前に ADR-0005 の判定関数で、チャンネルを読めるかを確かめ直す。** 投稿から処理までの間に外された人や、無効化されたメンバーには送らない。投稿者本人にも送らない。
- キーワードは、本文の AST から作ったテキスト（ADR-0006）を NFKC で正規化し、大文字・小文字を区別せずに部分一致で探す。1 人 50 語まで。ワークスペースごとに全員のキーワードから照合器（Aho-Corasick）を作ってキャッシュし、設定の変更で作り直す。
- @channel / @here を使える条件は、本家に寄せて決めた（[messaging.md](messaging.md) の「誰が使えるか」）。スレッドの返信の中の @channel / @here / @everyone は、理由 5 にしない（通知しない）。

## 6. 通知設定と抑制

### 6.1 設定

| 設定 | 単位 | 値 | 既定 |
| --- | --- | --- | --- |
| 通知レベル | メンバー（既定値）とチャンネル（`channel_members.notify_level`） | すべて / メンションのみ / なし | DM は「すべて」、チャンネルは「メンションのみ」 |
| ミュート | チャンネル | オン / オフ | オフ |
| @channel / @here を無視 | チャンネル | オン / オフ | オフ |
| キーワード | メンバー | 最大 50 語 | なし |
| おやすみモード（DND） | メンバー | 曜日ごとの時間帯（本人のタイムゾーン）、または「〜まで一時停止」 | なし |
| Web Push | メンバー | オン / オフ、本文のプレビューを含めるか | オン、プレビューあり |
| メール | メンバー | 送らない / 15 分後 / 1 時間後 | 15 分後 |

メンバー単位の設定は `member_notification_prefs`（テナントテーブル）に置く。変更は `prefs.updated` で他の端末に知らせる。

### 6.2 適用の順序

受け手ごとに上から順に評価し、最初に一致した行を採用する。「アプリ内」は、接続中のクライアントが WebSocket のイベントから自分で出す通知（ブラウザの Notification API）を指す。

| # | 条件 | アプリ内 | Web Push | メール |
| --- | --- | --- | --- | --- |
| 1 | 投稿者が本人、チャンネルを読めない、または無効化されている | なし | なし | なし |
| 2 | チャンネルがミュート | なし | なし | なし |
| 3 | 理由がチャンネルの通知レベルで許されない（「なし」、または「メンションのみ」で理由が 6、または @channel / @here を無視していて理由が 5） | なし | なし | なし |
| 4 | DND の間 | なし | なし | DND の終了後に予定する |
| 5 | いずれかの端末が操作中で、そのチャンネル（スレッド）を表示している | なし | なし | なし |
| 6 | いずれかの端末が操作中（直近 2 分以内に操作がある） | あり | なし | なし |
| 7 | 上のどれでもない（接続がない、またはすべての端末が操作していない） | あり（接続があれば） | あり | 予定する |

- 5・6 の判定には、Gateway が置く端末ごとの `activity`（`ws:{w}:act:{member_id}`）を使う（[realtime.md](realtime.md) の 9 節）。Valkey から読めないときは、7 として扱う（通知が重なる方に倒す。取りこぼすよりよい）。
- クライアントは、自分の画面でそのチャンネルを表示しているときは、アプリ内の通知を出さない。
- バッジ（3 節）は、この表と関係なく数える。

## 7. 配送

### 7.1 Web Push（VAPID）

- ブラウザの Push API で購読し、`push_subscriptions (workspace_id, member_id, id, endpoint, p256dh, auth, user_agent, created_at, last_success_at)` に保存する。同じブラウザが複数のワークスペースで購読してよい。
- 送信は Web Push のプロトコル（VAPID による送信者の認証、ペイロードの暗号化）に従う。VAPID の鍵は Secrets Manager に置く。鍵を替えると既存の購読が使えなくなるので、原則として替えない。替えるときは、クライアントが購読し直す流れを先に用意する。
- **ペイロード**：通知 ID、ワークスペース、チャンネル、投稿者の表示名、本文のプレビュー（最大 100 文字。本人の設定で省ける）、遷移先。ペイロードは暗号化されるが、端末のロック画面に出ることを前提に、プレビューはワークスペースの管理者が一括で無効にできるようにする。
- **ヘッダー**：`TTL` は 1 時間（それより古い通知は届いても役に立たない）。DM と @メンバーは `Urgency: high`、それ以外は `normal`。
- **まとめ**：通知の `tag` をチャンネル（スレッド）単位にし、同じチャンネルの通知は端末の上で置き換える。短時間に同じチャンネルから続いたら「N 件の新着」にまとめる（9 節）。
- **応答ごとの扱い**：

  | 応答 | 扱い |
  | --- | --- |
  | 201 | 成功。`last_success_at` を更新する |
  | 404 / 410 | 購読が失効している。行を消す |
  | 413 | ペイロードが大きすぎる。プレビューを省いて 1 回だけ送り直す |
  | 429 / 5xx | `Retry-After` か指数バックオフで再試行する。`TTL` を過ぎたら諦める |

### 7.2 メール（SES）

未読のメンションと DM を、遅らせてまとめて送る。

1. planner は、メールの対象になった通知を `notification_pending_emails (workspace_id, member_id, message_id, channel_id, seq, reason, due_at)` に積む。`due_at` は本人の設定（15 分後 / 1 時間後）。DND の間なら、DND の終了時刻以降にする。
2. メールの送信 Worker は 1 分ごとに（advisory lock で 1 台だけが）`due_at` を過ぎた行をメンバーごとにまとめて取り出す。
3. 送る直前に、行ごとに確かめる：まだ未読か（`seq > last_read_seq`。スレッドなら `thread_subscriptions` の `last_read_seq`）、メッセージが削除されていないか、チャンネルを読めるか。どれかに外れた行は捨てる。
4. 残った行を 1 通のメールにまとめる（最大 20 件。超えた分は件数だけ書く）。1 人に送るメールは、設定した遅延の間に 1 通まで。
5. SES で送り、行を消す。

- メールには、`List-Unsubscribe` と `List-Unsubscribe-Post`（ワンクリックでの配信停止）を付ける。
- バウンスと苦情は、SES のイベントを SNS 経由で受け取り、該当するアカウントのメールを止める。SES のアカウント単位の抑制リストも使う。
- メールの宛先はアカウントのメールアドレスだが、中身はワークスペースごとに分け、別のワークスペースの内容を 1 通に混ぜない（ADR-0009）。
- 本文のプレビューは、Web Push と同じく管理者が無効にできる。

## 8. 冪等性と重複の排除

SQS の標準キューは、同じメッセージを 2 回以上渡しうる（ADR-0014）。どの段も、同じ入力を 2 回処理しても結果が変わらないようにする。

- **通知の記録**：`notification_log (workspace_id, member_id, message_id, reason, push_state, email_state, created_at, PRIMARY KEY (workspace_id, member_id, message_id))`。planner は `INSERT ... ON CONFLICT DO NOTHING` で受け手ごとの行を作り、挿入できた受け手にだけジョブを出す。1 つのメッセージで、1 人に通知は 1 回だけになる（5 節の「理由を 1 つに決める」）。
- **push の送信**：送信の前に `push_state` を確かめ、成功したら `sent` にする。送信後、記録の前に落ちると 2 回送りうるが、同じ `tag` で端末の上では置き換わるので許容する。
- **メール**：`notification_pending_emails` の行を、送信と同じ単位で消す。SES への送信後、消す前に落ちると 2 通送りうる。メールのヘッダーにまとめの ID を入れ、送信済みの ID を記録して、再実行時に送らない。
- **編集・削除**：`message.deleted` を受けたら、そのメッセージの `notification_pending_emails` の行を消す。送信済みの push は取り消さない。
- `notification_log` は 30 日で消す（月ごとのパーティションを落とす）。

## 9. テナント単位と受け手単位の制限

| 対象 | 上限（S1 の初期値） | 超えたとき |
| --- | --- | --- |
| 1 ワークスペースの push の送信 | 1 秒に 200 件 | 遅らせる（捨てない）。遅れが `TTL` を超えたものは捨てる |
| 1 ワークスペースの planner の処理 | 同時に処理するジョブの数を全体の 20% まで | 残りは後回しにする |
| 1 受け手・1 チャンネルの push | 10 秒に 1 件 | まとめて「N 件の新着」にする |
| 1 受け手のメール | 設定した遅延の間に 1 通 | まとめる（7.2 節） |
| SES の送信レート | アカウントのクォータの 80% | 全体で遅らせる |

- 制限の計数は Valkey の共通の制限（GCRA）で行う（キーは `rl:{workspace_id}:...`。[rate-limiting.md](rate-limiting.md) の 3.1 節）。Valkey が使えないときは、制限なしで送る（通知を止めない）。
- 上限値は [runbooks](../runbooks/README.md) の「テナント単位の上限と負荷」に載せる（Ops への依頼事項）。

## 10. 失敗の扱い

| 失敗 | 扱い |
| --- | --- |
| Worker の処理中の例外 | メッセージを消さず、可視性タイムアウトの後に再び受け取る。キューごとに可視性タイムアウトを処理時間の 6 倍にする |
| 5 回失敗した（`maxReceiveCount` = 5） | デッドレターキューへ移る。1 件でも入ったらアラートを出す |
| デッドレターキューの再処理 | 原因を直した後、SQS の再処理（redrive）で元のキューへ戻す。冪等なので、重複しても問題ない |
| Web Push サービスの障害 | 指数バックオフで再試行し、`TTL` を過ぎたら諦める。メールの予定は別に進む |
| SES のスロットリング | 指数バックオフ。`notification_pending_emails` に残るので失われない |
| Relay から SQS へ送れない | outbox の行を消さずに再送する（ADR-0014）。通知は遅れるが、失われない |
| planner が止まる | `notify-events` が溜まる。最古のメッセージの経過時間でアラートを出す |

- 通知の遅延の目標：DM と @メンバーの push は、投稿から p95 5 秒以内に送信する（NFR-010。2026-09-26 に NFR として追加）。
- 通知で「別のワークスペースや権限外のチャンネルの内容が出ない」ことは、経路ごとの漏洩テストの対象に含める（ADR-0005）。

## 11. 監視する指標

- 各キューの可視メッセージ数と最古のメッセージの経過時間、デッドレターキューの件数
- 投稿から push の送信までの遅延（理由ごと）
- Web Push の応答コードごとの件数（404 / 410 の急増は、鍵やクライアントの不具合を疑う）
- SES のバウンス率と苦情率
- 未読数・メンション数の不一致率（クライアントとサーバーの突合）

## リマインダー

E5 の `reminders` で作る。本家 Slack の `/remind` と「後で読む」のリマインドに相当する。

- `reminders (workspace_id, id, member_id, text, remind_at, recurrence, message_id NULL, state)`。`message_id` があれば、そのメッセージへのリマインドになる。
- 1 分ごとに動く Worker が、`remind_at` を過ぎた行を取り、本人への通知（アプリ内の通知と Web Push）を送る。繰り返し（毎日・毎週など）は、次の `remind_at` を計算して行を更新する。
- 時刻の解釈は、メンバーのタイムゾーン（プロフィール）で行う。
- 本人だけが一覧・編集・取り消しできる。スラッシュコマンド（`/remind`）での作成は、E12 のアプリの基盤の組み込みのコマンドとして足す。
