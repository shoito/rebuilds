## 1. 目標と前提

- **目標水準は OWASP ASVS 5.0 の Level 2** とする。ASVS 5.0 は 2025 年 5 月に公開され、Level 2 が標準的な既定の水準とされている。Level 3 の要件のうち、テナント分離・暗号鍵・監査ログに関わるものは個別に取り込む。
- **最も重い障害は、ワークスペースをまたいだ漏洩**（[quality.md](../quality.md) のリスク 1 位、NFR-009）。どの統制も、まずこれを防ぐことを優先する。
- **AI エージェント（コーディング）は本番に一切アクセスしない。** 本番のデータ・認証情報・操作の経路を持たない（7.3 節）。
- 本番の変更は、すべて PR・CI・IaC を通す。コンソールでの手作業は禁止し、AWS Config で逸脱を検知する（ADR-0011）。

## 2. 信頼境界

```
  ┌──────────────────── インターネット（信頼しない）─────────────────────┐
  │ Browser（メンバー）  攻撃者  外部サイト（プレビュー対象）  IdP（SSO） │
  └──────┬─────────────────────────────────────────────▲───────────────┘
         │ TLS                                          │ 取得（外向きのみ）
  ═══════╪══════ B1: エッジ（CloudFront＋WAF＋Shield）══╪═════════════════
         │                                              │
  ┌──────▼──────── VPC：アプリ層（private subnet）──────┼──────────────┐
  │  ALB ─▶ API ──────┐      Gateway（WS）              │              │
  │          │        │         ▲                       │              │
  │  ════ B2: テナントのコンテキスト（SET LOCAL）════   │              │
  │          ▼        ▼         │                 ┌─────┴────────┐     │
  │  ┌────────────┐  ┌──────────┴─┐  ┌─────────┐  │ Unfurler     │     │
  │  │  Aurora    │  │ ElastiCache│  │  SQS    │  │ 隔離サブネット│     │
  │  │（RLS）     │  │ （Valkey） │  │         │  │ DB/内部へ到達 │     │
  │  └─────▲──────┘  └────────────┘  └────┬────┘  │ 不可          │     │
  │        │ Relay / Workers ◀────────────┘       └──────────────┘     │
  └────────┼──────────────────────────────────────────────────────────┘
           │                          ┌──────────────────────────────┐
  ═════ B3: 管理プレーン ═════════════│ S3（ファイル・監査・バックアップ）│
  CI/CD（GitHub Actions → OIDC）       │ KMS / Secrets Manager          │
  運用者（SSO＋MFA、break-glass）       └──────────────────────────────┘
  ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─
  B4: 開発環境（AI コーディングエージェント）… 本番への経路なし
```

| 境界 | 越えるもの | 主な統制 |
| --- | --- | --- |
| B1 エッジ | すべての外部リクエスト | TLS、WAF（マネージドルール＋レート制限）、Shield Standard、ALB は CloudFront からのみ受け付ける |
| B2 テナント | API・Worker から DB への全アクセス | `SET LOCAL app.workspace_id`、FORCE RLS、判定関数（ADR-0005） |
| B3 管理プレーン | デプロイ、鍵、秘密情報、運用者の操作 | OIDC による短命な認証情報、最小権限の IAM、人間の承認、監査ログ |
| B4 開発環境 | コード（PR としてのみ） | 本番の認証情報を置かない。ブランチ保護と CODEOWNERS |
| unfurler | 外部サイトからの取得 | 隔離したサブネット、内部アドレスへの到達を禁止（ADR-0016） |

## 3. 脅威モデル（STRIDE）

S＝なりすまし、T＝改ざん、R＝否認、I＝情報漏洩、D＝サービス妨害、E＝権限昇格。主要な脅威と対策だけを書く。

### 3.1 Browser（Web クライアント）

| 種類 | 脅威 | 対策 |
| --- | --- | --- |
| S | セッションの窃取・固定 | `__Host-` 接頭辞の Cookie（`HttpOnly`、`Secure`、`SameSite=Lax`）、ログイン時のセッション ID の再発行 |
| T | 悪意ある本文・ファイル名・表示名による XSS | 本文は AST から React の要素として描画（ADR-0006）、`dangerouslySetInnerHTML` を lint で禁止、厳格な CSP（5 節） |
| I | 共有端末に残るデータ、外部画像を使ったデータの持ち出し | ログアウト時にキャッシュと IndexedDB を消す。CSP の `img-src` で外部画像を直接読まない（プレビューの画像は自ドメイン経由） |
| E | CSRF、クリックジャッキング、WebSocket の乗っ取り（CSWSH） | 5 節 |

### 3.2 CloudFront / ALB（エッジ）

| 種類 | 脅威 | 対策 |
| --- | --- | --- |
| S | ALB へ直接アクセスして WAF を迂回する | ALB のセキュリティグループを CloudFront のマネージドプレフィックスリストに限定し、CloudFront が付ける秘密のヘッダーも検査する |
| T | 盗聴・改ざん | TLS 1.2 以上、HSTS（`includeSubDomains; preload`）（ADR-0017） |
| D | L7 の洪水、認証エンドポイントへの総当たり | WAF のレートベースルール、Bot Control・CAPTCHA は必要になった時点で有効にする。Shield Standard |
| I | エラーページやヘッダーからの内部情報の露出 | 汎用のエラー応答、`Server` などのヘッダーを削る |

### 3.3 API server

| 種類 | 脅威 | 対策 |
| --- | --- | --- |
| S | 認証の迂回、トークンの推測 | 全ルートに認証ミドルウェアを既定で掛け、除外は明示リストにする。トークンは 128 bit 以上の乱数で、DB にはハッシュだけを保存する |
| T | 入力の改ざん、一括代入 | Zod のスキーマで入出力を検証（ADR-0008）。未知のフィールドは拒否する |
| R | 操作の否認 | 監査ログ（ADR-0018） |
| I | 別テナント・権限外のデータ（IDOR） | パスの `workspace_id` とセッションからメンバーを解決、RLS、判定関数（ADR-0005、0009）。存在しないものと権限がないものは同じ 404 を返す |
| D | 重いクエリ、巨大なリクエスト | 本文とリクエストの上限、ページングの上限、ステートメントのタイムアウト、レート制限（6 節） |
| E | ロールの昇格、ゲストの越権 | 権限の決定表（E2）、ロール変更は owner / admin のみで監査対象 |

### 3.4 Gateway（WebSocket）

| 種類 | 脅威 | 対策 |
| --- | --- | --- |
| S | 他人の接続としての購読 | 接続時に短命なチケット（API が発行、1 回限り、有効 30 秒）で認証し、`Origin` を検査する |
| I | 権限外チャンネルの購読、退出後の受信 | Gateway は DB に触れないため、購読できるチャンネルは API が判定関数で決めたものに限る（方式は [realtime.md](realtime.md)）。メンバーの除外・無効化のイベントで購読を切る |
| D | 接続の大量確立、購読の爆発 | IP・アカウントごとの接続数の上限、1 接続あたりの購読数の上限、受信フレームのサイズとレートの上限 |
| T | 不正なイベントの送信 | 受信イベントを Zod で検証する（ADR-0008）。Gateway は書き込まない |

### 3.5 Relay / Workers

| 種類 | 脅威 | 対策 |
| --- | --- | --- |
| I | ジョブの `workspace_id` の取り違えによる別テナントへの書き込み・送信 | ジョブの `workspace_id` でコンテキストを設定してから処理する（ADR-0009）。通知の宛先は処理時に再度判定関数で確かめる |
| T | キューへの偽のジョブの投入 | SQS のキューポリシーで送信元の IAM ロールを限定する |
| E | Relay の権限の悪用 | `relay` ロールは `outbox` の読み取りと削除だけ（ADR-0009） |
| D | 毒入りのメッセージによる無限の再試行 | 再試行の上限と DLQ |

### 3.6 DB（Aurora PostgreSQL）

| 種類 | 脅威 | 対策 |
| --- | --- | --- |
| I | RLS の抜け、`BYPASSRLS` を持つロールの誤用 | FORCE RLS、マイグレーションの lint、`app` が所有者でないことの CI 検査（ADR-0009） |
| I | SQL インジェクション | Drizzle のパラメーター化されたクエリだけを使う。生の SQL は lint で検出し、レビュー必須 |
| T | 運用者による直接の改ざん | 本番 DB への人間のログインは break-glass に限り、監査ログとセッション記録を残す |
| I | スナップショットの持ち出し | KMS のカスタマー管理キーで暗号化し、キーポリシーで共有先を限定する（ADR-0017） |

### 3.7 Redis（ElastiCache Valkey）

| 種類 | 脅威 | 対策 |
| --- | --- | --- |
| I | 別テナントのチャンネルの購読 | チャンネル名に `workspace_id` を含め（ADR-0009）、購読の判断は Gateway の判定関数で行う |
| S | 未認証の接続 | 転送中の暗号化と、RBAC のユーザー（サービスごと）。セキュリティグループで API・Gateway・Relay 以外を拒否する |
| D | メモリの枯渇 | キーの TTL、`maxmemory` の方針。失われても正しさは保たれる（ADR-0002） |

### 3.8 S3（ファイル・エクスポート・監査・バックアップ）

| 種類 | 脅威 | 対策 |
| --- | --- | --- |
| I | バケットの公開、署名付き URL の使い回し | Block Public Access をアカウント単位で有効にする。配信は CloudFront の短命な署名付き URL だけ。キーに `workspace_id` を含める |
| T | アップロードしたファイルによる攻撃（マルウェア、HTML による XSS） | スキャン（[files.md](files.md)）、ユーザーのファイルは別ドメインから `Content-Disposition: attachment` と `X-Content-Type-Options: nosniff` で配信する |
| R | 監査ログの削除 | 監査用バケットは Object Lock（コンプライアンスモード）（ADR-0018） |

### 3.9 Unfurler（リンクのプレビュー）

| 種類 | 脅威 | 対策 |
| --- | --- | --- |
| I | SSRF（メタデータエンドポイント、VPC の内部、DB） | 隔離したサブネット、名前解決後の IP の検査（プライベート・リンクローカル・ループバックを拒否）、リダイレクトごとの再検査（ADR-0016） |
| T | 悪意あるページのメタデータによる XSS | 取り出した値はプレーンテキストとして AST に入れる。画像は再エンコードして自ドメインから配信する |
| D | 巨大な応答、遅い応答 | サイズとタイムアウトの上限、ドメインごとの同時実行数の上限 |
| I | プレビューの取得によるプライベートチャンネルの URL の外部への露出 | プライベートチャンネル・DM ではプレビューを既定で有効にし、ワークスペースの設定で無効化できるようにする（PM が決める） |

### 3.10 CI/CD

| 種類 | 脅威 | 対策 |
| --- | --- | --- |
| T | 依存パッケージ・GitHub Actions の乗っ取り（サプライチェーン） | 8 節 |
| E | ワークフローの改ざんによる本番の認証情報の取得 | AWS へは OIDC で入る。本番のロールの信頼ポリシーを `main` ブランチと `production` 環境に限定し、`production` 環境は Ops の承認を必須にする。`pull_request_target` を使わない |
| I | ログへの秘密情報の出力 | 秘密情報は Secrets Manager から実行時に取得し、CI には置かない。シークレットスキャン |
| R | 誰が何をデプロイしたか不明 | デプロイは PR と承認に紐づき、成果物に来歴（provenance）を付ける |

| 種類 | 脅威 | 対策 |
| --- | --- | --- |
| E | コーディングエージェントが本番の認証情報・データに触れる | 7.3 節。本番への経路を持たせない |
| T | コーディングエージェントが、指示に紛れた命令（Issue、依存パッケージの README など）に従い、悪意あるコードを入れる | 人間のレビューと CODEOWNERS、CI のセキュリティ検査。エージェントが承認しない（process.md） |

### 3.12 リモート MCP サーバー

設計は [mcp.md](mcp.md)、方針は [ADR-0028](../decisions/0028-remote-mcp-server.md)。

| 種類 | 脅威 | 対策 |
| --- | --- | --- |
| S | 悪意あるクライアントが、正規のクライアントを装って同意を得る | CIMD の `client_id` の URL とドメインを同意の画面に示す。管理者がクライアントの許可リストを持てる。DCR を提供しない |
| E | トークンの横流し・混乱した代理（confused deputy） | トークンの `aud` を mcp に束縛する。mcp は受け取ったトークンを他のサービスへ渡さない |
| I | エージェントがメンバーより多くを読む、別のワークスペースを読む | トークンを 1 つのワークスペースとメンバーに束縛し、api と同じ判定関数と RLS を通す |

### 3.13 公開 API とアプリ（E12）

脅威と対策の詳細は [apps.md](apps.md) の 14.1 節と [public-api.md](public-api.md) にある。要点は次のとおり。

| 種類 | 脅威 | 対策 |
| --- | --- | --- |
| I | アプリへのイベントの配信・インタラクティブの呼び出しを使った SSRF | 外向き送信用の VPC に接続しない Lambda（ADR-0016 と同じ方式）、名前解決後の IP の検査 |

## 5. Web のセキュリティ

### CSP とヘッダー

Web クライアントは CloudFront から配る静的な SPA なので、nonce は使わず、インラインスクリプトを持たない構成にする。

```
Content-Security-Policy:
  default-src 'none';
  script-src 'self';
  style-src 'self';
  img-src 'self' blob: https://<files-domain>;
  media-src 'self' blob: https://<files-domain>;
  font-src 'self';
  connect-src 'self' wss://<gateway-domain>;
  manifest-src 'self';
  worker-src 'self';
  frame-ancestors 'none';
  form-action 'self';
  base-uri 'none';
  object-src 'none';
  require-trusted-types-for 'script';
  report-to csp
```

- 利用状況の計測（[ADR-0025](../decisions/0025-product-analytics-with-ga4.md)）を有効にしたワークスペースでは、GA の送信先のドメインだけを `script-src`・`connect-src`・`img-src` に加えた別のポリシーを返す。Google Tag Manager はアプリでは使わない。第三者のスクリプトを読み込む危険は、[ADR-0025](../decisions/0025-product-analytics-with-ga4.md) の Consequences に書いた。
- `X-Frame-Options: DENY`、`X-Content-Type-Options: nosniff`、`Referrer-Policy: strict-origin-when-cross-origin`、`Cross-Origin-Opener-Policy: same-origin`、`Permissions-Policy` で不要な機能を止める。
- CSP の違反報告を集め、`report-only` で新しいポリシーを試してから有効にする。

### XSS

- 本文は AST（ADR-0006）を React の要素に変換して描画する。HTML の文字列を組み立てない。
- リンクの `href` はスキームを許可リスト（`https`、`http`、`mailto`）で検査する。`javascript:` などは描画しない。
- 表示名・チャンネル名・ファイル名・プレビューのタイトルも、すべてテキストとして描画する。
- ユーザーがアップロードしたファイルは、アプリとは別の登録可能ドメイン（例：`*-usercontent`）から配る。同じサイトの Cookie が送られないようにするため。

### CSRF

- セッション Cookie は `SameSite=Lax` とする。
- 状態を変える API は `Content-Type: application/json` だけを受け付け、`Origin` ヘッダーを許可リストで検査する。単純リクエストでは届かないため、CSRF トークンは使わない。
- CORS は自ドメインだけを許可する。

### クリックジャッキング

- `frame-ancestors 'none'` と `X-Frame-Options: DENY`。埋め込みの需要が出たら、個別の画面だけを許可する。

### WebSocket

- アップグレード時に `Origin` を許可リストで検査し、短命なチケットで認証する（3.4 節）。Cookie だけで認証しない。

### その他

- オープンリダイレクト：ログイン後の遷移先は相対パスだけを許可する。
- エラー応答にスタックトレースや SQL を含めない。

## 6. レート制限と濫用対策

| 層 | 対象 | 方式 |
| --- | --- | --- |
| エッジ | IP ごとの総量、認証エンドポイント | WAF のレートベースルール、マネージドルール（既知の悪性 IP など） |
| アプリ | メンバー・ワークスペースごとの投稿（[runbooks/README.md](../runbooks/README.md) の 2 節） | Valkey のトークンバケット。429 と `Retry-After` を返す |
| 認証 | ログイン、マジックリンク、パスワードリセット、MFA | アカウントと IP の両方で制限。失敗の連続でロックではなく遅延を掛ける（ロックによる妨害を避ける） |
| 招待 | ワークスペースごとの招待数 | 1 日あたりの上限。作成直後のワークスペースは低く始め、実績に応じて上げる |
| メール | SES の送信 | バウンスと苦情を SNS で受け、宛先を抑止リストに入れる。送信の評判を監視する |
| Gateway | 接続数、購読数、受信フレーム | 3.4 節 |
| ボット・AI エージェント | API の呼び出し | 人間と別の枠（7.2 節） |

- **スパムとワークスペースの濫用**：新規ワークスペースの作成数を IP・アカウントごとに制限する。明らかな濫用には、エッジで WAF の CAPTCHA / Challenge を掛ける。
- **通報と対応**：メンバーはメッセージを管理者に通報できる。運用者によるワークスペースの停止・コンテンツの削除は、理由を付けて監査ログに残す。
- 上限の値はテナントの規模・プランで変える。値の管理は Ops が持つ。

## 7. AI に固有のリスク

### 7.1 将来の AI 機能（要約、質問応答など）

roadmap の「後回しにしたもの」を作るときの前提を先に決めておく。

- **権限を先に適用する。** LLM に渡すのは、依頼したメンバーが判定関数で読めるものだけにする。検索のベクトルインデックスでも、権限の条件を検索の段階で入れる（ADR-0005）。
- **テナントを混ぜない。** 1 回の呼び出し・キャッシュ・埋め込みのインデックスに、複数のワークスペースのデータを入れない。
- **本文は命令ではなくデータとして扱う。** 間接的なプロンプトインジェクション（メッセージやファイルに紛れた命令）を前提に設計する。
  - LLM の出力も AST として描画する。外部画像の自動読み込みやリンクの自動取得をしない（持ち出しの経路を断つ）。
  - LLM によるツール呼び出しは、依頼したメンバーの権限の範囲に限る。書き込み（投稿、招待、設定変更）は、メンバーの確認を経てから行う。
- **LLM の提供者**：顧客データを学習に使わない契約を前提にする。処理する地域（東京リージョンで使えるモデル）は 未検証。
- AI 機能の評価に、プロンプトインジェクションと越権のケースを含める。

### 7.2 ボット・AI エージェントのメンバー

ADR-0010 により、ボット・AI エージェントは `account_id` が NULL のメンバーとして表す。

- 人間と同じ判定関数・同じ RLS を通る。特別な抜け道を作らない。
- ロールは `member` 以下に限る。`owner` / `admin` にはできない。
- 参加できるのは、招待されたチャンネルだけ。ワークスペース全体の読み取り権限を持たせない。
- 認証はメンバーごとのトークン（スコープ付き、有効期限付き、DB にはハッシュだけ）。発行・失効は owner / admin だけが行い、監査ログに残す。
- 人間と別のレート制限の枠を持つ。
- 監査ログとメッセージに、行為者の種類（`human` / `bot` / `agent`）を残す。

### 7.3 コーディングエージェント

- **本番へのアクセスは持たない。** 本番の AWS アカウント、DB、秘密情報、ログ、顧客データのいずれにも経路がない。
- 開発環境には本番の認証情報を置かない。テストデータは seed で生成する（quality.md 2.4）。
- 変更は PR としてのみ入る。承認は人間が行い、エージェントは承認しない（process.md）。
- `.github/workflows/`、`CODEOWNERS`、IaC、認証・認可のコードの変更は、Dev（テックリード）と Ops の承認を必須にする。
- 障害の調査にエージェントを使うときも、人間が取り出した、個人情報を除いたログやメトリクスだけを渡す。
- エージェントが読む外部の内容（Issue、依存パッケージ、Web）は命令として扱わない。

## 8. サプライチェーン

| 対象 | 統制 |
| --- | --- |
| npm の依存 | ロックファイルをコミットし、CI では固定インストール（`--frozen-lockfile` 相当）だけを行う。インストール時のスクリプトは既定で無効にし、必要なものだけ許可する |
| 依存の更新 | Renovate。公開から一定期間（例：3 日）経ったバージョンだけを提案させる。メジャー更新は人間がレビューする |
| GitHub Actions | サードパーティの Action はコミット SHA で固定する。`GITHUB_TOKEN` の権限は既定で読み取りのみ |
| コンテナイメージ | ベースイメージをダイジェストで固定する。ECR のスキャン |
| SBOM | ビルドごとに SBOM（CycloneDX か SPDX）を作り、成果物と一緒に保存する |
| 来歴 | ビルドの来歴（SLSA の provenance）を付け、デプロイ時に検証する。目標は SLSA Build L2 以上 |
| 秘密情報 | シークレットスキャンとプッシュ保護 |

## 9. 秘密情報の管理

詳細は ADR-0017。

- 秘密情報（DB の認証情報、セッションの署名鍵、SES・外部サービスの鍵）は Secrets Manager に置く。リポジトリ・環境変数ファイル・CI の変数に置かない。
- ECS のタスクロールで、サービスごとに読める秘密情報を限定する。
- DB の認証情報は自動でローテーションする。アプリはローテーションに追従できるよう、接続の確立時に秘密情報を取り直す。
- 署名鍵は、新旧の鍵を同時に受け付ける期間を設けて入れ替える。
- 漏洩の疑いがあれば、即座にローテーションする（runbook の `key-rotation`、E7 で作成）。

| 種類 | 道具（候補） | 実行タイミング | 合否 |

## 11. 脆弱性の管理

深刻度は CVSS を基準に、悪用の可能性とテナント分離への影響で補正する。テナント分離を破る脆弱性は、CVSS にかかわらず Critical とする。

| 深刻度 | 緩和の期限 | 修正の期限 |
| --- | --- | --- |
| Critical | 24 時間以内（WAF のルール、フラグでの停止など） | 7 日以内 |
| High | 7 日以内 | 30 日以内 |
| Medium | — | 90 日以内 |
| Low | — | 180 日以内、または次の定期更新 |

- 期限を守れないときは、Dev（テックリード）と Ops がリスクの受容を記録する。
- 期限と件数は、Ops のダッシュボードで追う。

## 12. セキュリティインシデントへの対応

- 手順は runbook の `security-incident`（E7 で作成）に書く。検知・封じ込め・根絶・復旧・事後の振り返りの流れ、連絡先、証拠の保全を含む。
- 検知の源：GuardDuty、Security Hub、アプリのセキュリティイベント（認証の失敗の急増、権限の拒否の急増、テナント境界の監査の不一致）、外部からの報告。
- テナント境界の監査で不一致が 1 件でも見つかれば、重大インシデントとして扱う（quality.md 4.2）。
- 法令上の報告の期限（13 節）を、対応の手順に組み込む。影響を受けたワークスペースの特定には、監査ログと `workspace_id` を使う。

## 14. データのライフサイクル

方針は ADR-0019、監査ログは ADR-0018 にある。ここには全体の一覧を書く。

| データ | 保持 | 削除のされ方 |
| --- | --- | --- |
| メッセージ・リアクション・メンション | ワークスペースの保持ポリシー（既定は無期限）。チャンネルごとに上書きできる | 論理削除 → hard delete の Worker が物理削除 |
| ファイル | メッセージと同じ保持ポリシー | S3 のオブジェクトとサムネイルを削除 |
| 検索インデックス | 元のデータに従う | 削除のイベントで同時に消す |
| outbox、SQS | 処理後すぐ。DLQ は最大 14 日 | 自動 |
| Valkey | 揮発（TTL） | 自動 |
| 監査ログ | DB に 1 年、アーカイブに 400 日 | ADR-0018 |
| アプリのログ | 30 日（本文・トークンを含めない） | 期限で自動削除 |
| エクスポートの成果物 | 7 日 | S3 のライフサイクルで削除 |
| バックアップ（Aurora、AWS Backup、大阪へのコピー） | 35 日 | 期限で消える。**これが削除の最終的な期限になる** |

- **リーガルホールド**は、保持ポリシーとメンバーの削除操作に優先する。
- **ワークスペースの削除**は、30 日の猶予期間のあと、`workspace_id` 単位で消去する。
- **アカウントの削除**は、アカウントの個人情報を消し、各ワークスペースのメンバーは「削除されたユーザー」として匿名化する。メッセージはワークスペースのデータとして残る。
- **削除の完了**：物理削除から、最長 35 日でバックアップからも消える。顧客には、メッセージ・ファイルは削除から最長 45 日、ワークスペースは依頼から最長 75 日で、バックアップを含めて消えると説明する（ADR-0019）。例外は監査ログのアーカイブ（400 日）。
- 手順は runbook の `data-deletion`（E7 で作成）に書く。
