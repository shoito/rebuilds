## 2. テスト設計

### 2.1 RLS による分離

- `app` ロールで、次の 3 つのコンテキストについて、テナントテーブル（`workspaces` を除く全部）に `SELECT`・`INSERT`・`UPDATE`・`DELETE` を試す：コンテキストなし、別のワークスペースのコンテキスト、正しいコンテキスト。前の 2 つで、読める行が 0 件、書き込みがすべて拒否されること。
- テーブルの一覧はマイグレーションから取り、テストに書き写さない。テーブルを足したら自動で対象になる。
- `SET LOCAL` の残留：同じプールの接続で、ワークスペース A のトランザクションの直後に、コンテキストを設定せずに読むと 0 件になること。
- API の経路：別のワークスペースのチャンネルへの投稿・履歴取得が 404 になり、応答の本文と時間で存在が区別できないこと（DT-MSG-001 の 1 行）。

### 2.2 `seq` の順序

- PROP-MSG-001 のジェネレーター：チャンネル 1〜3 個、メンバー 1〜5 人（非メンバーを含む）、投稿 1〜200 件。各投稿の本文は有効・無効を 9:1 で混ぜ、再送を 2 割含める。
- 並行度は 1〜50 から生成し、`Promise.all` で同時に送る。試行は PR で 100 回、夜間で 1,000 回。
- 判定：チャンネルごとに、保存された `seq` の集合が 1〜N と一致する。拒否（400・404）と再送（200）で `seq` が進まない。

### 2.3 冪等性

- PROP-MSG-002 のジェネレーター：同じ（メンバー, `client_msg_id`）を 1〜10 回、同時と逐次を混ぜて送る。別のメンバーが同じ `client_msg_id` を使う組を含める。
- 判定：保存数が、異なる（メンバー, `client_msg_id`）の組の数と一致する。同じ組への応答は、すべて同じメッセージ（ID と `seq`）を返す。一意制約の違反で 500 を返さない。

| ID | 観点 | 条件 | 期待結果 | 要件 / 性質 |
| --- | --- | --- | --- | --- |
| Q-1 | 分離 | コンテキストなしで `messages` を読む | 0 件 | ADR-0009 |
| Q-2 | 分離 | 別のワークスペースのチャンネルへ投稿 | 404、`seq` を消費しない | REQ-MSG-003、DT-MSG-001 #1 |
| Q-3 | 順序 | 50 並行で 200 件を投稿 | `seq` が 1〜200 | PROP-MSG-001 |
| Q-4 | 冪等 | 同じ `client_msg_id` を 10 並行で送る | 1 件だけ保存。全応答が同じメッセージ | REQ-MSG-002、PROP-MSG-002 |
| Q-5 | 冪等 | 同じ `client_msg_id` で本文を変えて再送 | 200 で既存を返す | DT-MSG-001 #3 |

## 3. テスト環境とテストデータ

- Testcontainers の PostgreSQL（本番と同じメジャー版）。マイグレーションを当ててから、`app` ロールで接続する。
- seed：ワークスペース 2 つ、各 3 チャンネル、各 5 メンバー（うち 1 人は非メンバー）。

## 4. 合否の判定基準

- 2.1 の全テーブル・全操作で、分離のテストが通る。1 件でも失敗したら不合格。
- PROP-MSG-001・002 が、夜間の 1,000 回で反例なく通る。
- DT-MSG-001 の全行の表駆動テストが通る。
- テストの削除・skip・期待値の緩和がない。

## 5. リリース後の品質の確認

- E1 は本番に出さない。E4 以降、クライアントの欠損検知率（runbooks の 1 節）と、テナント境界の監査（[quality.md](../../quality.md) の 4.2 節）で見る。

## 6. 題材の quality.md へ反映する知見

- マイグレーションからテナントテーブルの一覧を取り、全操作の分離を試す RLS のテストの型。
- 並行投稿の性質ベーステストのジェネレーター（`seq` を扱う後続の変更で使い回す）。
