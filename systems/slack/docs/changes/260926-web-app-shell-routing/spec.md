# Spec: Web クライアントの骨格とルーティング

## 概要

Web クライアント（`apps/web`）の骨格を作る。ルートの定義、認証の状態による転送、ワークスペースの切り替え、チャンネル一覧のサイドバー、「見つかりません」とエラーの画面、API の呼び出し口、CSP に合う構成、国際化と a11y の土台、フラグとリリースの識別子の受け取りを含む。

- チャンネルの中身（メッセージの一覧と入力欄）は [260926-web-channel-view](../260926-web-channel-view/spec.md) で作る。この変更では、チャンネルのルートに枠だけを置く。
- 認証は E1 の簡易方式（[260926-post-and-list-messages](../260926-post-and-list-messages/spec.md) の Design にある開発用トークン）に合わせる。本来のサインイン（Better Auth、OTP、OAuth）は E2 の `auth-email-otp-and-oauth` で入れる。境界は Design の「認証の境界」に書く。
- 翻訳の全面的な整備（`i18n-ja-en`）と a11y の全面的な整備（`a11y-baseline`）は E7 で行う。この変更では、後から足せる土台と、骨格の画面が満たす最低限だけを定める。
- リアルタイム同期（WebSocket、SharedWorker）は E4 で入れる。

## ADDED Requirements

### REQ-WEB-001: ルートの定義

システムは、Design の「E1 のルート」の表にあるパスだけを画面に対応させ、それ以外のパスでは「見つかりません」の画面（REQ-WEB-011）を出さなければならない。

#### Scenario: 定義したパス

- Given 認証済みで、ワークスペース W1 に属し、W1 のチャンネル C1 に参加しているアカウント
- When `/w/W1/c/C1` を開く
- Then チャンネルの画面の枠が出る。左端にワークスペースの一覧、その右にチャンネル一覧、主領域にチャンネルの中身が出る

#### Scenario: 定義していないパス

- Given 認証済みのアカウント
- When `/w/W1/search?q=hello`（E1 では未定義）を開く
- Then 「見つかりません」の画面が出る

### REQ-WEB-002: 未認証のときのサインインへの転送

認証の状態が「未認証」のときに `/signin` 以外のパスを開いた場合、システムは `/signin?next=<開こうとしたパスとクエリ>` へ転送しなければならない。認証の状態は、DT-WEB-001 に従って決める。

#### Scenario: 未認証でチャンネルを開く

- Given セッションのないブラウザ
- When `/w/W1/c/C1` を開く
- Then URL が `/signin?next=%2Fw%2FW1%2Fc%2FC1` に置き換わり（履歴に残さない）、サインインの画面が出る

#### Scenario: 操作中にセッションが切れる

- Given `/w/W1/c/C1` を表示中で、セッションが無効になった
- When 次の API の呼び出しが 401 を返す
- Then `/signin?next=%2Fw%2FW1%2Fc%2FC1` へ転送される

### REQ-WEB-003: サインイン後の転送先の検証

サインインが完了したとき、システムは `next` が DT-WEB-004 で有効と判定される場合にだけそのパスへ転送し、それ以外は `/` へ転送しなければならない。

#### Scenario: 自サイトのパス

- Given `/signin?next=%2Fw%2FW1%2Fc%2FC1` を表示中
- When サインインが完了する
- Then `/w/W1/c/C1` へ転送される

#### Scenario: 外部のオリジン

- Given `/signin?next=https%3A%2F%2Fevil.example%2F` を表示中
- When サインインが完了する
- Then `/` へ転送され、`evil.example` へは遷移しない

### REQ-WEB-004: E1 の開発用サインイン

開発用の認証が有効なビルドのとき、システムは `/signin` に開発用のサインインの画面を出し、API が発行する HttpOnly の Cookie でセッションを確立しなければならない。開発用の認証が無効なビルド（本番のビルド）には、開発用のサインインの画面とその呼び出しを含めてはならない。

#### Scenario: 開発用のビルドでのサインイン

- Given 開発用の認証が有効なビルドと、seed の開発用トークン
- When `/signin` で開発用トークンを入力して送信する
- Then API が Cookie を発行し、アプリは `GET /api/me/workspaces` が 200 を返すことを確かめてから、REQ-WEB-003 の転送先へ移る。入力したトークンは、画面の状態から消える

#### Scenario: 誤ったトークン

- Given 開発用の認証が有効なビルド
- When 存在しない開発用トークンで送信する
- Then 「サインインできませんでした」を出し、`/signin` にとどまる。トークンの値は画面にもコンソールにも出さない

#### Scenario: 本番のビルド

- Given 開発用の認証が無効なビルド
- When ビルドした成果物（JS・HTML）を調べる
- Then 開発用のサインインの画面の部品と、開発用のサインインの API の経路が含まれていない。`/signin` は「サインインは準備中です」を出す

### REQ-WEB-005: 認証情報を端末に保存しない

システムは、トークン・セッションの値を `localStorage`・`sessionStorage`・IndexedDB・URL・Cookie（JavaScript から書くもの）に保存してはならない。

#### Scenario: サインインの後の保存領域

- Given 開発用のサインインを完了したブラウザ
- When `localStorage`・`sessionStorage`・IndexedDB の全キーと値、`document.cookie`、現在の URL を調べる
- Then 開発用トークンの値も、セッションの Cookie の値も見つからない（セッションの Cookie は HttpOnly なので `document.cookie` に現れない）

### REQ-WEB-006: `/` の転送

認証済みで `/` を開いたとき、システムは DT-WEB-002 に従って、最後に開いたワークスペースへ転送するか、ワークスペースの選択の画面を出さなければならない。

#### Scenario: 最後に開いたワークスペースがある

- Given W1 と W2 に属し、この端末で最後に開いたワークスペースが W2
- When `/` を開く
- Then `/w/W2` へ転送される（履歴に残さない）

#### Scenario: 最後に開いたワークスペースから外されている

- Given この端末で最後に開いたのは W3 だが、W3 はもう一覧にない。W1 と W2 に属する
- When `/` を開く
- Then ワークスペースの選択の画面に W1 と W2 が出る。W3 の ID も名前も出ない

#### Scenario: どのワークスペースにも属さない

- Given 所属するワークスペースが 0 件
- When `/` を開く
- Then 「参加しているワークスペースがありません」が出る

### REQ-WEB-007: `/w/{workspace_id}` の転送

認証済みで、所属するワークスペースの `/w/{workspace_id}` を開いたとき、システムは DT-WEB-002 に従って、そのワークスペースで最後に開いたチャンネル、またはチャンネル一覧の先頭へ転送しなければならない。

#### Scenario: 最後に開いたチャンネルへ

- Given W1 で最後に開いたチャンネルが C2 で、C2 はチャンネル一覧にある
- When `/w/W1` を開く
- Then `/w/W1/c/C2` へ転送される

#### Scenario: チャンネルに参加していない

- Given W1 のチャンネル一覧が 0 件
- When `/w/W1` を開く
- Then 「参加しているチャンネルがありません」が出る

### REQ-WEB-008: ワークスペースの切り替え

利用者がワークスペースの一覧から別のワークスペースを選んだとき、システムは URL を `/w/{選んだ workspace_id}` に変えるだけで切り替え、以後の画面をそのワークスペースのデータで描かなければならない。一覧では、表示中のワークスペースを `aria-current="page"` で示さなければならない。

#### Scenario: 切り替え

- Given `/w/W1/c/C1` を表示中で、W2 にも属する
- When 一覧で W2 を選ぶ
- Then URL が `/w/W2` になり、DT-WEB-002 により W2 のチャンネルへ転送される。サイドバーには W2 のチャンネルだけが出る。W2 の項目に `aria-current="page"` が付く

#### Scenario: ブラウザの戻る

- Given W1 から W2 へ切り替えた
- When ブラウザの「戻る」を押す
- Then `/w/W1/c/C1` に戻り、W1 のデータで描かれる

### REQ-WEB-009: ワークスペースごとのデータの分離

システムは、ワークスペースに属するデータ（チャンネル一覧、フラグ、メッセージ、「最後に開いた」の記憶）を、`workspace_id` を含むキーで保持し、URL の `workspace_id` と異なるワークスペースのデータを画面に出してはならない。

#### Scenario: 遅れて届いた前のワークスペースの応答

- Given W1 のチャンネル一覧の取得が遅れている間に、W2 へ切り替えた
- When W1 のチャンネル一覧の応答が届く
- Then W2 のサイドバーには W1 のチャンネルが出ない。W1 の応答は W1 のキーに保存されるだけである

### REQ-WEB-010: チャンネル一覧のサイドバー

ワークスペースの画面を表示している間、システムはそのワークスペースで利用者が参加しているチャンネルの一覧をサイドバーに出し、表示中のチャンネルを `aria-current="page"` で示さなければならない。

#### Scenario: 一覧の表示

- Given W1 で C1（`general`）と C2（`random`）に参加している
- When `/w/W1/c/C1` を開く
- Then サイドバーに `general` と `random` がこの API の返す順で出て、`general` に `aria-current="page"` が付く。各項目は `/w/W1/c/{channel_id}` へのリンクである

#### Scenario: 一覧の取得に失敗する

- Given チャンネル一覧の API が 503 を返し続ける
- When `/w/W1/c/C1` を開く
- Then サイドバーに「チャンネルを読み込めませんでした」と「再試行」のボタンが出る。主領域のチャンネルの中身は、サイドバーの失敗と関係なく表示される

### REQ-WEB-011: 「見つかりません」の画面

ワークスペースまたはチャンネルが「存在しない」「権限がない」「別のワークスペースのもの」「ID の形式が不正」のいずれかの場合、システムはどれでも同じ「見つかりません」の画面を出さなければならない。画面には、要求した ID に対応する名前・種別・件数など、存在を示す情報を含めてはならない。

#### Scenario: 権限のないプライベートチャンネル

- Given W1 のプライベートチャンネル C9 に参加していない（履歴の API は 404 を返す）
- When `/w/W1/c/C9` を開く
- Then 「見つかりません」の画面が出る。`document.title` は「見つかりません」の画面の既定の題名で、C9 の名前を含まない

#### Scenario: 存在しないチャンネルと比べる

- Given 存在しないチャンネルの ID `C0`
- When `/w/W1/c/C0` と `/w/W1/c/C9` をそれぞれ開く
- Then 両者の画面は、アクセシビリティツリーのテキスト、`document.title`、URL 以外の DOM の構造が一致する（PROP-WEB-001）

#### Scenario: 所属しないワークスペース

- Given W2 に属さない
- When `/w/W2/c/C1` を開く
- Then 同じ「見つかりません」の画面が出る。W2 の名前はどこにも出ない

### REQ-WEB-012: API の応答の扱い

API の呼び出しが失敗した場合、システムは DT-WEB-003 に従って、転送・画面・再試行を決めなければならない。エラーの画面には、スタックトレース・SQL・応答の本文をそのまま出してはならない。

#### Scenario: サーバーのエラー

- Given チャンネル一覧の API が 500 を返す
- When 自動の再試行（DT-WEB-003）がすべて失敗する
- Then 「問題が発生しました」と「再試行」のボタン、リリースの識別子（REQ-WEB-018）が出る。応答の本文は出ない

#### Scenario: 429

- Given `GET /api/me/workspaces` が `429` と `Retry-After: 3` を返す
- When アプリがこれを受け取る
- Then 3 秒が経つまで同じ要求を送らず、3 秒後に 1 回だけ再試行する

### REQ-WEB-013: API の呼び出し口

システムは、HTTP の API を `packages/api-client` だけを通して呼ばなければならない。`apps/web` のコードで `fetch`・`XMLHttpRequest`・`hono/client` を直接使ってはならない（ADR-0008）。

#### Scenario: 直接の fetch

- Given `apps/web/src` のどこかに `fetch("/api/...")` を書いた変更
- When lint を実行する
- Then lint が失敗する

#### Scenario: 共通の設定

- Given `packages/api-client` を包む `apps/web/src/api/` の呼び出し口
- When 任意の API を呼ぶ
- Then 要求は同一オリジンに送られ、Cookie は同一オリジンだけに付き（`credentials: "same-origin"`）、本文を持つ要求は `Content-Type: application/json` で、リリースの識別子のヘッダー（REQ-WEB-018）が付く

### REQ-WEB-014: CSP に合う構成

システムは、[security.md](../../architecture/security.md) の 5 節の CSP（`script-src 'self'`、`style-src 'self'`、`require-trusted-types-for 'script'` を含む）のもとで、CSP の違反を 1 件も起こさずに動かなければならない。`index.html` と配布するファイルに、インラインのスクリプト・インラインのスタイル・`eval` 相当の実行を含めてはならない。

#### Scenario: 本番のビルドを CSP 付きで配る

- Given 本番のビルドを、security.md の CSP のヘッダーを付けて配るサーバー
- When サインイン → `/` → ワークスペースの切り替え → チャンネル → 「見つかりません」の順に操作する
- Then `securitypolicyviolation` のイベントが 0 件で、コンソールに CSP のエラーが出ない

### REQ-WEB-015: 国際化の土台

システムは、骨格の画面のすべての文言を、ICU MessageFormat のメッセージ ID を通して表示し、ja と en の両方の文言を持たなければならない。表示の言語は DT-WEB-005 に従って決め、`<html lang>` をその言語にしなければならない。

#### Scenario: 英語の環境

- Given `navigator.languages` が `["en-US", "en"]` のブラウザ
- When 「見つかりません」の画面を開く
- Then 英語の文言が出て、`<html lang="en">` になる

#### Scenario: ja と en のキーの不一致

- Given en にだけメッセージ ID `shell.notFound.title` がある
- When i18n のキーの検査を実行する
- Then 検査が失敗し、ja に欠けているキーの名前を出す

### REQ-WEB-016: アクセシビリティの土台

システムは、骨格の画面に次を備えなければならない。ワークスペースの一覧・チャンネル一覧・主領域のランドマーク、主領域へ飛ぶリンク（skip link）、ルートごとの `document.title`、ルートが変わったときの主領域の見出しへのフォーカスの移動と読み上げ。骨格の画面は、axe の検査（WCAG 2.2 AA のルール）で違反 0 件でなければならない。

#### Scenario: ルートの移動

- Given `/w/W1/c/C1` を表示中
- When サイドバーで C2 を選ぶ
- Then `document.title` が C2 の名前とワークスペースの名前を含むものに変わり、フォーカスが主領域の見出しに移り、画面の読み上げ用の領域（`aria-live="polite"`）に C2 の名前が入る

#### Scenario: axe

- When サインイン、ワークスペースの選択、チャンネルの枠、「見つかりません」、エラーの各画面を、ja と en で axe にかける
- Then 違反が 0 件である

### REQ-WEB-017: フラグの受け取り

`packages/flags`（`feature-flags-appconfig`）が使えるとき、システムはワークスペースのブートストラップの API を提供し、`feature-flags-appconfig` の REQ-FLAG-009 の一覧を、そのワークスペースのメンバーにだけ返さなければならない（メンバーでなければ 404）。Web はワークスペースを開くたびにそのワークスペースの評価済みのフラグを取得し、`packages/flags` の型付きの定義を通してだけ画面に渡さなければならない。取得に失敗した場合、または 3 秒以内に応答がない場合、システムは `packages/flags` の既定値を使わなければならない。

#### Scenario: ワークスペースごとの値

- Given `release.web_channel_view` が W1 では有効、W2 では無効
- When W1 から W2 へ切り替える
- Then W2 の画面では `release.web_channel_view` が無効として扱われる

#### Scenario: メンバーでないワークスペース

- Given W2 に属さないアカウント
- When W2 のブートストラップの API を呼ぶ
- Then 404 が返り、W2 のフラグの名前も値も含まれない

#### Scenario: 取得の失敗

- Given フラグの API が 503 を返す
- When W1 を開く
- Then すべてのフラグが `packages/flags` の既定値で扱われ、画面はエラーにならない

### REQ-WEB-018: リリースの識別子

システムは、ビルド時に決まるリリースの識別子（[delivery.md](../../architecture/delivery.md) の 3 節の `<日付>-<コミットの短いハッシュ>`）を持ち、API への全要求のヘッダーと、エラーの画面と、エラーの報告に付けなければならない。

#### Scenario: API の要求

- Given リリースの識別子 `2026-09-26-a1b2c3d` でビルドしたアプリ
- When 任意の API を呼ぶ
- Then 要求のヘッダーに `2026-09-26-a1b2c3d` が付く（ヘッダー名は Open questions）

#### Scenario: 描画中の例外

- Given チャンネルの枠の描画中に例外が起きる
- When エラー境界がそれを捕まえる
- Then 「問題が発生しました」の画面に `2026-09-26-a1b2c3d` が出て、エラーの報告口（E1 ではコンソール、E7 で RUM）に同じ識別子とルートの種類（ID を伏せたパス）が渡る。例外のメッセージやスタックは画面に出ない

### REQ-WEB-019: サインアウト

利用者がサインアウトしたとき、システムはサーバーのセッションを終わらせ、そのアカウントの画面の状態・クエリのキャッシュ・メッセージの保持・「最後に開いた」の記憶を消し、`/signin` へ転送しなければならない。

#### Scenario: サインアウト

- Given W1 の C1 を表示し、W1 のチャンネル一覧をキャッシュしている
- When サインアウトする
- Then `/signin` に移り、ブラウザの「戻る」で `/w/W1/c/C1` に戻っても、キャッシュからチャンネル名やメッセージが出ず、DT-WEB-001 により `/signin` へ転送される

## Decision Tables

### DT-WEB-001: ルートの判定

上から順に評価し、最初に一致した行を採用する。認証の状態は `GET /api/me/workspaces` の結果で決める（200：認証済み、401：未認証、それ以外の失敗：確認に失敗）。

| # | 認証の状態 | ルート | → 表示 | → 転送先 |
| --- | --- | --- | --- | --- |
| 1 | 確認中 | - | 読み込み中の骨格（ワークスペース・チャンネルの名前を出さない） | なし |
| 2 | 確認に失敗（5xx・ネットワーク、DT-WEB-003 の再試行の後） | - | エラーの画面（再試行のボタン付き） | なし |
| 3 | 未認証 | `/signin` | サインインの画面 | なし |
| 4 | 未認証 | `/signin` 以外（未定義のパスを含む） | - | `/signin?next=<現在のパスとクエリ>` |
| 5 | 認証済み | `/signin` | - | `next`（DT-WEB-004 の結果） |
| 6 | 認証済み | `/` | - | DT-WEB-002 |
| 7 | 認証済み | `/w/{ws}` で始まり、`ws` が所属するワークスペースの一覧にない（形式が不正な ID を含む） | 「見つかりません」 | なし |
| 8 | 認証済み | `/w/{ws}` | - | DT-WEB-002 |
| 9 | 認証済み | `/w/{ws}/c/{ch}` | チャンネルの枠（中身と 404 の扱いは web-channel-view） | なし |
| 10 | 認証済み | それ以外 | 「見つかりません」 | なし |

- 転送はすべて履歴を置き換える（`replace`）。「戻る」で転送の前のパスに戻り、再び転送される繰り返しを避けるため。

### DT-WEB-002: `/` と `/w/{ws}` の転送先

上から順に評価し、最初に一致した行を採用する。「記憶」は、この端末でアカウントごとに保存した「最後に開いたワークスペース」と、ワークスペースごとの「最後に開いたチャンネル」である。

| # | パス | 一覧の取得 | 記憶した転送先が一覧にある | 一覧の件数 | → 表示 | → 転送先 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | `/` | - | はい | - | - | `/w/{記憶したワークスペース}` |
| 2 | `/` | - | いいえ | 1 件以上 | ワークスペースの選択（一覧の順） | なし |
| 3 | `/` | - | いいえ | 0 件 | 「参加しているワークスペースがありません」 | なし |
| 4 | `/w/{ws}` | 失敗 | - | - | ワークスペースの枠と、主領域にエラー（再試行付き） | なし |
| 5 | `/w/{ws}` | 成功 | はい | - | - | `/w/{ws}/c/{記憶したチャンネル}` |
| 6 | `/w/{ws}` | 成功 | いいえ | 1 件以上 | - | `/w/{ws}/c/{一覧の先頭}` |
| 7 | `/w/{ws}` | 成功 | いいえ | 0 件 | 「参加しているチャンネルがありません」 | なし |

- `/` の一覧はワークスペースの一覧、`/w/{ws}` の一覧はそのワークスペースのチャンネル一覧である。`/` でワークスペースの一覧の取得に失敗した場合は DT-WEB-001 の 2 行目になる。
- 記憶は、チャンネルの中身（web-channel-view）の履歴の取得が 200 を返したときにだけ更新する。「見つかりません」になったチャンネルは記憶しない。

### DT-WEB-003: API の応答の扱い

上から順に評価し、最初に一致した行を採用する。ここに当たらない個別の扱い（メッセージの送信）は、web-channel-view の DT-WEB-010 が優先する。

| # | 応答 | 要求の種類 | → 動作 | → 画面 |
| --- | --- | --- | --- | --- |
| 1 | 2xx | - | 成功として扱う | - |
| 2 | 401 | - | 認証の状態を「未認証」にする | DT-WEB-001 の 4 行目で `/signin` へ |
| 3 | 404 | ワークスペースまたはチャンネルの経路 | 再試行しない | 「見つかりません」（REQ-WEB-011） |
| 4 | 403 | - | 再試行しない | 「アクセスできません」。エラーのコード（`member_deactivated` など）ごとの文言は E2 で足す |
| 5 | 429 | `GET` | `Retry-After` の秒数（HTTP 日付も解釈する）だけ待って再試行。ヘッダーがない・不正なら 7 行目の間隔。最大 3 回 | 待っている間は読み込み中 |
| 6 | 400、その他の 4xx | - | 再試行しない。不具合としてエラーの報告口へ送る | 「問題が発生しました」とリリースの識別子 |
| 7 | 5xx、ネットワークエラー、30 秒のタイムアウト | `GET` | 指数バックオフ（1 秒、2 秒、4 秒。±20% のゆらぎ）で最大 3 回再試行 | 再試行が尽きたら、その領域にエラーと再試行のボタン |
| 8 | 429、5xx、ネットワークエラー、タイムアウト | `GET` 以外 | 呼び出し元に任せる（自動で再試行しない） | 呼び出し元が決める |

### DT-WEB-004: `next` の検証

上から順に評価し、最初に一致した行を採用する。`next` は URL のデコードを 1 回行った後の文字列で判定する。

| # | `next` | → 転送先 |
| --- | --- | --- |
| 1 | ない、または空 | `/` |
| 2 | `/` で始まらない（`https://...`、`javascript:...`、`w/W1` など） | `/` |
| 3 | `//` または `/\` で始まる | `/` |
| 4 | 制御文字（U+0000〜U+001F、U+007F）または `\` を含む | `/` |
| 5 | 現在のオリジンを基準に URL として解決したとき、オリジンが現在のオリジンと異なる | `/` |
| 6 | パスが `/signin` で始まる | `/` |
| 7 | それ以外 | `next` のパス・クエリ・フラグメント |

### DT-WEB-005: 表示の言語

上から順に評価し、最初に一致した行を採用する。

| # | アカウントの設定の言語 | `navigator.languages` | → 言語 |
| --- | --- | --- | --- |
| 1 | `ja` または `en`（E2 以降。E1 には設定がない） | - | 設定の言語 |
| 2 | なし | 先頭から見て、主言語の部分（`ja-JP` なら `ja`）が `ja` か `en` に最初に一致するもの | その言語 |
| 3 | なし | どれも一致しない、または取得できない | `ja` |

## Correctness Properties

### PROP-WEB-001: 「見つかりません」は理由で区別できない

任意のワークスペースの ID とチャンネルの ID の組（存在しない・権限がない・別のワークスペースのもの・形式が不正、のいずれか）に対して、表示される画面のアクセシビリティツリーのテキスト、`document.title`、URL 以外の DOM の構造は同一であり、要求した ID に対応する名前を含まない。

### PROP-WEB-002: 画面のデータは URL のワークスペースのものだけ

ワークスペースの切り替え、戻る・進む、API の応答の遅延と順序の入れ替わりの任意の列に対して、どの時点でも、画面に出ているワークスペースに属するデータ（チャンネル一覧、フラグ、メッセージ）は、その時点の URL の `workspace_id` のものだけである。

### PROP-WEB-003: 転送先は自サイトのパスだけ

任意の文字列 `next` に対して、DT-WEB-004 の結果は `/`、または `/` で始まり `//` で始まらず、現在のオリジンを基準に解決したときのオリジンが現在のオリジンと一致するパスである。

### PROP-WEB-004: フラグは表示中のワークスペースのもの

ワークスペースの切り替えと、フラグの API の応答（遅延・順序の入れ替わり・失敗を含む）の任意の列に対して、画面に渡るフラグの値は、URL の `workspace_id` のブートストラップの応答の値か、`packages/flags` の既定値のどちらかであり、別のワークスペースの応答の値ではない。

## Design

### E1 のルート

[client.md](../../architecture/client.md) の 2.2 節のうち、E1 で作るものだけを定義する。ルーターは TanStack Router を使い、パスの引数を型で検査する。

| パス | 画面 | 備考 |
| --- | --- | --- |
| `/` | DT-WEB-002 で転送、またはワークスペースの選択 | |
| `/signin?next=` | サインイン | E1 は開発用（REQ-WEB-004）。E2 で中身を差し替える |
| `/w/{workspace_id}` | DT-WEB-002 で転送 | |
| `/w/{workspace_id}/c/{channel_id}` | チャンネルの枠 | 中身は web-channel-view |
| その他 | 「見つかりません」 | `/m/{seq}`（E3）、`/t/...`（E3）、`search`（E6）、`settings`（E2 以降）は、それぞれの変更で足す |

- パスの ID は UUID の形式を型で検査し、形式が不正なら API を呼ばずに「見つかりません」を出す。API を呼んだ場合と同じ画面にする（PROP-WEB-001）。
- URL に入れるのは UUID だけにする（client.md の 2.2 節）。チャンネル名をパスに入れない。

### 画面の構成

```
┌──────────┬──────────────┬──────────────────────────────────┐
│ nav      │ nav          │ main                             │
│ ワーク    │ チャンネル    │  <h1>チャンネル名</h1>              │
│ スペース  │ 一覧          │  （web-channel-view の中身）        │
│ の一覧    │              │                                  │
└──────────┴──────────────┴──────────────────────────────────┘
 skip link（先頭） / aria-live="polite" のルートの読み上げ領域（末尾）
```

- エラー境界は、アプリ全体・ワークスペースの枠・主領域の 3 段に置く。主領域の例外でサイドバーを消さない。
- 部品は `packages/ui`（React Aria、CSS Modules）を使う。`packages/ui` がまだないときは、この変更で最小の部品（ボタン、リンクの一覧、エラーの枠）だけを作る。

### 認証の境界（E1 と E2）

| 項目 | E1（この変更） | E2（`auth-email-otp-and-oauth` など） |
| --- | --- | --- |
| セッションの確立 | 開発用のサインインの API が、開発用トークンを受けて HttpOnly の Cookie を発行する（API の追加が必要。Open questions） | Better Auth のサインインが Cookie を発行する |
| `/signin` の中身 | 開発用のビルドだけ、開発用トークンの入力欄。本番のビルドは「準備中」 | OTP、Google・Microsoft、SSO への誘導 |
| 認証の状態の判定 | `GET /api/me/workspaces` の 200 / 401 | 同じ |
| 401 の扱い、`next` の検証、ルートの判定 | DT-WEB-001、DT-WEB-003、DT-WEB-004 | 変えない |
| 403 のコード（`sso_required`、`mfa_required`、`member_deactivated`） | 「アクセスできません」だけ | コードごとの画面と誘導を足す（MODIFIED） |
| サインアウト | 開発用の API でセッションを消す | Better Auth のサインアウト |

- アプリのコードは、`src/app/auth/` の小さな口（`probeSession`、`signOut`、サインインの画面の部品）だけを通して認証に触れる。E2 はこの口の中身と `/signin` の画面を差し替え、ルートの判定には触れない。
- 開発用のサインインの部品は、ビルド時の定数で分岐して読み込む。本番のビルドでは、その分岐ごと取り除かれることを成果物の検査で確かめる（REQ-WEB-004）。

### API とクエリのキー

| 用途 | API | 状態 |
| --- | --- | --- |
| 認証の確認とワークスペースの一覧 | `GET /api/me/workspaces` | [identity-and-access.md](../../architecture/identity-and-access.md) の 2.3 節にあるが、どの変更にもまだない（Open questions） |
| チャンネル一覧（参加しているもの） | `GET /api/workspaces/{ws}/channels` | どの変更にもまだない（Open questions） |
| フラグ | `GET /api/workspaces/{ws}/flags`（[feature-flags-appconfig](../260926-feature-flags-appconfig/spec.md) の REQ-FLAG-014） → `{ flags: { [name]: boolean } }` | **この変更で作る**（`feature-flags-appconfig` は範囲外としている）。REQ-FLAG-009 の関数を呼ぶ。認証ミドルウェアのメンバーの解決を通す |
| 開発用のサインイン・サインアウト | 開発用の API | どの変更にもまだない（Open questions） |

- TanStack Query のキーは、ワークスペースに属するものを必ず `["ws", workspace_id, ...]` で始める。キーはキーを作る関数（`queryKeys`）だけから作り、lint で文字列の直書きを禁じる（PROP-WEB-002）。
- 「最後に開いた」の記憶は `localStorage` に置く。キーは `slack:last:{account を表す値}`、値は ID だけにする（名前を保存しない）。アカウントを表す値は `GET /api/me/workspaces` の応答に含まれる前提で、ない場合は Open questions。サインアウトで消す。

### CSP

- Vite の本番のビルドは、インラインのスクリプトを出さない構成にする（`index.html` にはハッシュ付きのファイルの `<script type="module" src>` だけ）。`build.modulePreload.polyfill` がインラインのスクリプトを出さないことは 未検証 で、出るなら無効にする。
- スタイルは CSS Modules で、実行時に `<style>` を差し込むライブラリを使わない（client.md の 7 節）。
- 開発サーバー（HMR）はインラインのスクリプトを使うので、CSP の検査は本番のビルドを `vite preview` などで配って行う。CSP のヘッダーの本番での付与（CloudFront）は E7 の `security-headers-csp` で行う。

### 国際化

- FormatJS（`react-intl`）と ICU MessageFormat を使う（client.md の 9 節）。文言は `src/i18n/messages/{ja,en}/<機能>.json` に機能ごとに置く。
- CI で、ja と en のキーの一致と、使われていないキーを検査する。
- 日時・数は `Intl` で整形する。E1 ではタイムゾーンをブラウザのものにする。

### フラグとリリースの識別子

- フラグの取得は、ワークスペースの枠のローダーで行い、キーは `["ws", workspace_id, "flags"]` にする。取得中は主領域を読み込み中の骨格にし、フラグが決まる前に機能を一瞬だけ出すことを避ける。
- リリースの識別子は、CI がビルド時に環境変数で渡し、Vite の `define` で埋め込む。ローカルのビルドでは `local-<コミットの短いハッシュ>`、取れなければ `local`。`<meta name="app-release">` にも出す（スクリプトではないので CSP に影響しない）。
- サーバーが対応する最小のバージョンを下回ったときの再読み込みの強制（[delivery.md](../../architecture/delivery.md) の 4.3 節）は、API の側の規約が決まってから入れる。この変更ではバージョンを送るだけにする。

### 非機能要件への影響

- 骨格の初回の JS は、client.md の 11 節の予算（gzip で 200KB 以内）に収める。ルートごとに分割し、開発用のサインインとチャンネルの中身は別のチャンクにする。
- NFR-009（テナント分離）：分離の強制は API と RLS が行う。クライアントは PROP-WEB-002 で、別のワークスペースのデータを画面に混ぜないことを守る。
- NFR-001〜008 への影響はない。

## Open questions

- **開発用トークンの渡し方（Dev）**：推奨は、開発用の API が HttpOnly の Cookie を発行する方式（E2 と同じ経路になり、Web がトークンを持たない）。代わりに、ローカルの開発サーバーのプロキシがヘッダーを付ける方式もある（UI は不要だが、staging では Web を使えない）。
- （決定）既定の言語は `ja` にする。DT-WEB-005 の 3 行目（PM、2026-09-26）。
- **リリースの識別子のヘッダー名（Dev・Ops）**：仮に `X-Client-Release` とする。API のログ・トレースに載せるのは `telemetry-package` の範囲。
- **骨格の release フラグ（PM・Ops）**：フラグはワークスペース単位で評価するため、ワークスペースを選ぶ前の骨格そのものは release フラグで隠せない。E1 では本番の利用者がいない前提で、骨格にはフラグを置かない。本番の CloudFront で Web をいつから配るかを決める必要がある（未検証）。
- **「最後に開いた」の記憶のキー（Dev）**：アカウントを表す値（`account_id` そのものか、その派生値か）を `GET /api/me/workspaces` の応答に含めるか。

## 決定（2026-09-26、PM・QA、既定案）

上の Open questions は、次のとおり決めた。

- 不足していた API（`GET /api/me/workspaces`、`GET /api/workspaces/{ws}/channels`、開発用のサインイン・サインアウト）は、`dev-session-and-workspaces` と `channel-list` で作る。
- 内部 API のパスの接頭辞は `/api` にする（`packages/api-client` もこれを基準にする）。
- 開発用の認証は、開発用の API が HttpOnly の Cookie を発行する方式にする（`dev-session-and-workspaces`）。
- リリースの識別子のヘッダー名は `X-Client-Release` にする。
- E1 の間は、Web を本番に公開しない（staging までにとどめる）。そのため、骨格に release フラグは置かない。
- 「最後に開いたワークスペース」は、`GET /api/me/workspaces` が返す `account_id` をキーにして記憶する。
