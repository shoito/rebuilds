# Spec: チャンネルの画面（E1、リアルタイムなし）

## 概要

チャンネルのメッセージの一覧と入力欄を作る。[260926-post-and-list-messages](../260926-post-and-list-messages/spec.md) の API（`POST` / `GET /api/workspaces/{ws}/channels/{ch}/messages`、REQ-MSG-001〜006）を、[260926-web-app-shell-routing](../260926-web-app-shell-routing/spec.md) のチャンネルの枠の中で使う。

- **リアルタイムの同期は含めない（E4）。** 他の人の投稿は、チャンネルを開いたとき、自分の送信が確定したとき、タブが前面に戻ったときに、最新ページを取り直して併合することで出す（REQ-WEB-026）。
- Timeline ストア（[ADR-0024](../../decisions/0024-client-data-layer-and-offline.md)）は、E1 に要る分だけを作る。E4 以降で足すものは Design の「Timeline ストアの範囲」に書く。
- 入力欄は平文の `<textarea>` とし、送るときに本文の AST（[ADR-0006](../../decisions/0006-message-body-ast.md)）へ変換する。ProseMirror の入力欄・補完は E3 の `composer-prosemirror-ast` で入れる。
- 未送信のメッセージはメモリにだけ持つ。再読み込みで失われる。IndexedDB の送信キューは E4 の `send-queue-indexeddb` で入れる。
- 未読の線と既読の更新（E5）、指定したメッセージへの移動（E3、`around_seq`）、編集・削除・リアクション・スレッド（E3）は含めない。
- 要件は `release.web_channel_view` が有効な状態の振る舞いを定める（ADR-0026）。無効な状態は plan の Proof に書く。

以下、「窓」はメモリに持つ確定済みのメッセージの連続した範囲、「最新ページ」は `before_seq` なしの `GET`（`limit` = 50）、「前のページ」は `before_seq` = 窓の最小の `seq` の `GET`（`limit` = 50）を指す。

## ADDED Requirements

### REQ-WEB-020: チャンネルを開いたときの最新ページの表示

利用者がチャンネルを開いたとき、システムは最新ページを取得し、メッセージを `seq` の昇順（古いものが上）で表示し、一覧を最下部までスクロールした状態にしなければならない。

#### Scenario: 120 件のチャンネル

- Given `seq` 1〜120 のメッセージがあるチャンネル C1 のメンバー
- When `/w/W1/c/C1` を開く
- Then `GET .../messages?limit=50` が 1 回送られ、`seq` 71〜120 が昇順で表示され、`seq` 120 の行が画面の最下部に見えている

#### Scenario: キャッシュのあるチャンネルに戻る

- Given C1 を開いた後に C2 へ移り、C1 の窓がメモリに残っている
- When C1 に戻る
- Then 残っている窓をすぐに表示し、同時に最新ページを取り直して DT-WEB-011 で併合する

### REQ-WEB-021: 前のページの読み込み

一覧の先頭から 10 行以内が描画の範囲に入ったとき、窓より前にメッセージがある（`has_more` が真だった）場合、システムは前のページを取得して窓の前に足さなければならない。同じチャンネルで前のページの取得を同時に 2 つ以上行ってはならない。

#### Scenario: 上へスクロール

- Given C1 の窓が `seq` 71〜120 で、`has_more` が真
- When 上へスクロールし、`seq` 80 の行が描画の範囲に入る
- Then `GET .../messages?before_seq=71&limit=50` が 1 回だけ送られ、応答の `seq` 21〜70 が窓の前に足される

#### Scenario: 取得中にさらにスクロール

- Given 前のページを取得中
- When さらに上へスクロールする
- Then 2 つ目の取得は送られない。取得が終わって条件をまだ満たしていれば、次の前のページを取得する

### REQ-WEB-022: チャンネルの始まり

前のページの応答の `has_more` が偽のとき、システムは窓の先頭に「チャンネルの始まり」の表示を出し、それ以上前のページを取得してはならない。

#### Scenario: 先頭まで読んだ

- Given 窓が `seq` 21〜120 で `has_more` が真
- When 前のページの応答が `seq` 1〜20、`has_more` が偽
- Then 窓の先頭に「チャンネルの始まり」が出て、さらに上へスクロールしても `GET` は送られない

### REQ-WEB-023: 一覧の仮想化

システムは、メッセージの一覧を仮想化し、画面に見えている行とその前後だけを DOM に置かなければならない。一覧の DOM の行は、同時に 150 行以下でなければならない。

#### Scenario: 1,000 件の窓

- Given 窓に 1,000 件のメッセージがある
- When 一覧の任意の位置までスクロールする
- Then 一覧の中の `article` 要素は 150 個以下である

### REQ-WEB-024: スクロール位置の保持

窓の前にメッセージを足したとき、システムは足す前に見えていた先頭の行の画面上の位置を保たなければならない。最下部にいる（一覧の下端まで 40px 以内）間に窓の後ろにメッセージが加わったときは、最下部に追従しなければならない。最下部にいないときは、見えている行の位置を保たなければならない。スクロールの動作は DT-WEB-013 に従う。CSS の `overflow-anchor` に頼ってはならない（client.md の 4.2 節）。

#### Scenario: 前のページを足す

- Given `seq` 75 の行が一覧の上端から 12px の位置に見えている
- When 前のページ（`seq` 21〜70、高さがまちまち）が足される
- Then `seq` 75 の行は上端から 12px（±1px）の位置のままである

#### Scenario: 最下部で他の人の投稿が加わる

- Given 最下部にいて、最新は `seq` 120
- When 取り直した最新ページに `seq` 121、122 が含まれる
- Then `seq` 122 の行が最下部に見える

#### Scenario: 過去を読んでいる間に加わる

- Given 最下部から 2,000px 上を読んでいて、`seq` 90 の行が上端から 100px にある
- When 取り直した最新ページに `seq` 121 が含まれる
- Then `seq` 90 の行は上端から 100px（±1px）のままである

### REQ-WEB-025: 窓の上限と「最新へ移動」

窓が 1,000 件を超えた場合、システムは DT-WEB-012 に従って、見えている側と反対の端から捨てなければならない。窓が最新を含まなくなったときは、一覧の下端に「最新へ移動」のボタンを出し、押されたら最新ページで窓を置き換えて最下部を表示しなければならない。

#### Scenario: 過去へ読み進めて上限を超える

- Given 窓が `seq` 101〜1,100（1,000 件、最新を含む）で、上端付近を見ている
- When 前のページ `seq` 51〜100 が足される
- Then 窓は `seq` 51〜1,050 になり、`seq` 1,051〜1,100 は捨てられ、下端に「最新へ移動」が出る

#### Scenario: 最新へ移動

- Given 「最新へ移動」が出ている
- When それを押す
- Then 最新ページを取得して窓を置き換え、最新の行が最下部に見え、ボタンが消える

### REQ-WEB-026: 最新ページの取り直しと併合

次のいずれかのとき、システムは最新ページを取り直し、DT-WEB-011 に従って窓に併合しなければならない。(a) チャンネルを開いた、(b) 自分の送信が確定した（DT-WEB-010 の 1 行目）、(c) タブが前面に戻った（`visibilitychange` で `visible`）。同じチャンネルで最新ページの取得が進行中のあいだは、新しい取得を始めず、進行中の取得が終わった後に 1 回だけ取り直さなければならない。

#### Scenario: 他の人の投稿を取り込む

- Given 窓が `seq` 71〜120 で最下部にいる。サーバーでは他の人が `seq` 121〜123 を投稿済み
- When タブが前面に戻る
- Then 最新ページ（`seq` 74〜123）が併合され、窓は `seq` 71〜123 になる。`seq` 71〜120 の行は重複しない

#### Scenario: 間が空きすぎた

- Given 窓が `seq` 71〜120 で最下部にいる。サーバーでは他の人が `seq` 121〜300 を投稿済み
- When タブが前面に戻る
- Then 最新ページ（`seq` 251〜300、`has_more` が真）は窓とつながらないので、窓を `seq` 251〜300 で置き換え、最下部を表示する。`seq` 121〜250 を欠いたまま 120 と 251 を隣に並べることはない

### REQ-WEB-027: 入力欄

利用者が入力欄で送信の操作をしたとき、システムは DT-WEB-014 に従って送信するかを決め、送信する場合は入力の文字列を `message-body-ast-v1` の `parsePlainText`（DT-MSG-004）で本文の AST（`v: 1`）にし、新しい `client_msg_id`（UUIDv7）を付けて送信の列（REQ-WEB-029）に入れ、入力欄を空にしなければならない。空と長さは、同じ Story の `isBlankBody` と `countBodyChars`（REQ-MSG-012）で判定しなければならない。

#### Scenario: Enter で送信

- Given 入力欄に「hello」
- When `Enter` を押す
- Then 本文が `hello` のテキストノード 1 つを持つ AST（`v: 1`）で、新しい UUIDv7 の `client_msg_id` を付けた送信が列に入り、入力欄が空になる

#### Scenario: 日本語の変換の確定

- Given IME で「こんにちは」を変換中
- When 変換を確定する `Enter` を押す（`isComposing` が真、または `keyCode` が 229）
- Then 送信されず、入力欄に「こんにちは」が残る

#### Scenario: 空白だけ・上限超え

- Given 入力欄が空白と改行だけ、または 40,001 文字
- When `Enter` を押す
- Then 送信されない。40,001 文字のときは「40,000 文字までです」を出す。送信のボタンは無効になっている

### REQ-WEB-028: 送信中の表示（楽観表示）

送信を列に入れたとき、システムはサーバーの応答を待たずに、そのメッセージを「送信中」として一覧の末尾に表示しなければならない。未確定のメッセージは、確定したメッセージのすべての後ろに、送信の操作をした順で並べなければならない。

#### Scenario: 送信中

- Given 窓が `seq` 71〜120 で最下部にいる
- When 「hello」を送信する
- Then 応答の前に、`seq` 120 の後ろに「hello」が「送信中」の印付きで出て、最下部に見える

#### Scenario: 続けて 2 件

- When 「a」、「b」の順に送信する
- Then 確定したメッセージの後ろに「a」、「b」の順で「送信中」が並ぶ

### REQ-WEB-029: 送信の直列化

システムは、チャンネルごとに送信の列を持ち、列の先頭から 1 件ずつ送り、同じチャンネルで `POST` を同時に 2 件以上送ってはならない。再送では、同じ `client_msg_id` を使わなければならない。

#### Scenario: 先頭が終わるまで待つ

- Given 「a」の `POST` の応答を待っている
- When 「b」を送信する
- Then 「b」の `POST` は、「a」の応答（DT-WEB-010 の結果が確定か失敗）を受けるまで送られない

#### Scenario: チャンネルごとに独立

- Given C1 の「a」が再試行を待っている
- When C2 で「x」を送信する
- Then C2 の「x」はすぐに送られる

### REQ-WEB-030: 送信の自動の再試行

送信がネットワークエラー・タイムアウト（30 秒）・5xx・429 で失敗した場合、作成から 10 分未満であれば、システムは同じ `client_msg_id` で自動で再送しなければならない。429 のときは `Retry-After` の時間が経つまで、そのチャンネルの `POST` を送ってはならない。待ちの時間は DT-WEB-010 に従う。

#### Scenario: 429

- Given 「a」の `POST` が `429`、`Retry-After: 5` を返した
- When 時間が進む
- Then 5 秒が経つまで C1 の `POST` は送られず、5 秒後に「a」が同じ `client_msg_id` で再送される。その間、「a」には「送信が混み合っています」が出る

#### Scenario: 応答が失われたが保存されていた

- Given 「a」の `POST` がサーバーで保存されたが、応答がタイムアウトした
- When 再送する
- Then サーバーは 200 と既存のメッセージ（REQ-MSG-002）を返し、一覧には「a」が 1 件だけ出る

### REQ-WEB-031: 送信の失敗と利用者の操作

送信が DT-WEB-010 で「失敗」または「未送信」になった場合、システムはそのメッセージに理由を表示し、「失敗」には「編集」と「破棄」を、「未送信」には「再送」と「破棄」を出さなければならない。自動では再送してはならない。

#### Scenario: 400

- Given 「a」の `POST` が 400 を返した
- When 応答を受ける
- Then 「a」は「送信できませんでした」になり、「編集」を押すと「a」が入力欄に戻って一覧から消え、「破棄」を押すと一覧から消える

#### Scenario: 10 分を超えた

- Given 「a」がネットワークエラーで再試行を続け、作成から 10 分が経った
- When 次の再試行の時刻になる
- Then 再送せずに「未送信」になり、後ろに並ぶ「b」も「未送信」になる。「a」の「再送」を押すと、同じ `client_msg_id` で再送が始まり、10 分の起点を押した時刻にする

#### Scenario: 404

- Given 送信中に、チャンネルから外された
- When 「a」の `POST` が 404 を返す
- Then 「a」とその後ろの C1 の未確定のメッセージは、すべて「送信できませんでした（チャンネルが見つかりません）」になり、C1 の画面は「見つかりません」（REQ-WEB-011）になる

### REQ-WEB-032: 重複の除去

システムは、同じ `seq` のメッセージと、同じ `client_msg_id` のメッセージを、一覧に 2 つ以上出してはならない。確定したメッセージ（`POST` の応答か、取得したページ）が未確定のメッセージと同じ `client_msg_id`、または未確定のメッセージの受け取った `seq` と同じ `seq` を持つとき、システムは同じ更新の中で、未確定のメッセージを消して確定したメッセージを置かなければならない。

#### Scenario: 取り直しに自分の投稿が含まれる

- Given 「a」の `POST` が 201（`seq` 121）を返し、「a」は確定を待っている（DT-WEB-010 の 1 行目）
- When 最新ページ（`seq` 72〜121）が併合される
- Then 「a」は `seq` 121 の確定したメッセージとして 1 件だけ出て、「送信中」の印が消える

#### Scenario: 同じページが 2 回届く

- Given 窓が `seq` 71〜120
- When 同じ内容の最新ページの応答が 2 回併合される
- Then 窓は `seq` 71〜120 のままで、各行は 1 件ずつである

### REQ-WEB-033: 本文の描画

システムは、メッセージの本文を `message-body-ast-v1` の `MessageBody`（`packages/ui`）だけで描画し、表示名を引く関数とチャンネル名を引く関数を渡さなければならない。チャンネル名を引く関数は、骨格のチャンネル一覧（REQ-WEB-010）にあるチャンネルの名前だけを返さなければならない。`apps/web` で本文を独自に描画してはならず、`dangerouslySetInnerHTML`・`innerHTML`・`outerHTML`・`insertAdjacentHTML`・`eval`・`new Function` を使ってはならない。描画の規則そのもの（要素・属性・リンクの検査）は REQ-MSG-014 と PROP-MSG-005 に従う。

#### Scenario: 一覧の中の HTML の文字列

- Given `seq` 100 の本文のテキストが `<img src=x onerror=alert(1)>`
- When 窓に `seq` 71〜120 を表示する
- Then `seq` 100 の行にはその文字列がそのまま文字として出て、一覧の中に `img` 要素は作られない

#### Scenario: 一覧にないチャンネルへのリンク

- Given 本文に、骨格のチャンネル一覧にない C9 への `channel_link` がある
- When 描画する
- Then 「プライベートチャンネル」と表示され（REQ-MSG-014）、C9 の ID もリンクも出ない

### REQ-WEB-034: 表示できない本文があるときの再読み込みの案内

窓の中に、`MessageBody` が「このメッセージは表示できません」と描いた本文（REQ-MSG-015）のうち、版（`v`）が 1 より大きいものがある場合、システムは一覧の上部に「新しいバージョンがあります。再読み込みしてください」と再読み込みのボタンを 1 つだけ出し、他のメッセージの表示と入力欄を使える状態に保たなければならない。

#### Scenario: 未知のバージョン

- Given `seq` 100 と `seq` 110 の本文が `{ v: 2, ... }`
- When 窓に `seq` 71〜120 を表示する
- Then 2 つの行は「このメッセージは表示できません」になり、他の 48 件は通常どおり表示され、再読み込みの案内は 1 つだけ出る

#### Scenario: 版は 1 だが検証に通らない

- Given `seq` 100 の本文が `{ v: 1, blocks: [] }`
- When 窓を表示する
- Then `seq` 100 の行は「このメッセージは表示できません」になり、再読み込みの案内は出ない

### REQ-WEB-035: 空の状態

最新ページの応答が 0 件で `has_more` が偽のとき、システムは「まだメッセージはありません」を出し、入力欄を使える状態にしなければならない。

#### Scenario: 空のチャンネル

- Given メッセージ 0 件のチャンネル C3
- When C3 を開く
- Then 「まだメッセージはありません」と入力欄が出る。「hello」を送信すると、空の表示が消えて「hello」が「送信中」で出る

### REQ-WEB-036: 履歴の取得の失敗

履歴の取得が失敗した場合、システムは DT-WEB-015 に従って表示を決めなければならない。404 のときは、骨格の「見つかりません」（REQ-WEB-011）と同一の画面を出し、そのチャンネルの窓・未確定のメッセージ・「最後に開いた」の記憶をメモリから消さなければならない。

#### Scenario: 権限のないチャンネル

- Given 参加していないプライベートチャンネル C9
- When `/w/W1/c/C9` を開き、履歴の `GET` が 404 を返す
- Then 「見つかりません」の画面が出て、入力欄は出ない。PROP-WEB-001 の比較で、存在しないチャンネルの画面と区別できない

#### Scenario: 前のページの失敗

- Given 窓が `seq` 71〜120 で、前のページの取得が再試行の後も 503
- When 失敗が確定する
- Then 窓の先頭に「読み込めませんでした」と「再試行」が出て、`seq` 71〜120 の表示と入力欄はそのまま使える

### REQ-WEB-037: 投稿者と時刻の表示

システムは、各メッセージに投稿者と投稿の時刻を表示しなければならない。投稿者は `member_id` からメンバーの Query で表示名を引き、引けないときは「メンバー」と `member_id` の先頭 8 文字を出さなければならない。時刻は `Intl.DateTimeFormat` で表示の言語に合わせて整形しなければならない。並べ替えに時刻を使ってはならない（ADR-0001）。

#### Scenario: 表示名を引けない

- Given メンバーの API がまだない（E1）
- When `member_id` が `0192f7a0-...` のメッセージを表示する
- Then 投稿者は「メンバー 0192f7a0」と出る

### REQ-WEB-038: メッセージ一覧のアクセシビリティ

システムは、メッセージの一覧を `role="feed"` の要素とし、各メッセージを `article` にし、仮想化のため `aria-setsize="-1"` を付け、読み込み中は `aria-busy="true"` にしなければならない。入力欄にはラベルを付け、送信中・失敗の状態は文字でも表さなければならない（色だけで表さない）。一覧と入力欄は、axe の検査で違反 0 件でなければならない。

#### Scenario: axe

- When 窓を表示した一覧、空の状態、失敗のメッセージを含む一覧を、ja と en で axe にかける
- Then 違反が 0 件である


### REQ-WEB-039: 未送信のメッセージがあるときの離脱の確認

送信キューに未送信（送信中・失敗）のメッセージがある間に、利用者がページを閉じる・再読み込みする・別のサイトへ移ろうとしたとき、システムはブラウザの確認（`beforeunload`）を出さなければならない。未送信のメッセージがないときは、確認を出してはならない。

#### Scenario: 送信中に閉じようとする

- Given 送信中のメッセージが 1 件ある
- When タブを閉じようとする
- Then ブラウザの確認が出る

#### Scenario: すべて送信済み

- Given 未送信のメッセージがない
- When タブを閉じようとする
- Then 確認は出ない

## Decision Tables

### DT-WEB-010: 送信の結果

上から順に評価し、最初に一致した行を採用する。「後続」は、同じチャンネルの列で、このメッセージの後ろにある未確定のメッセージを指す。

| # | 応答 | 作成（または手動の再送）からの経過 | → このメッセージの状態 | → このメッセージの次の送信 | → 後続 |
| --- | --- | --- | --- | --- | --- |
| 1 | 201、200 | - | 確定待ち（`seq` を記録）。最新ページを取り直す（REQ-WEB-026 の b） | なし | 列の先頭を次へ進める |
| 2 | 401 | - | 未送信 | なし（手動） | すべて未送信。認証の状態を未認証にする（DT-WEB-001） |
| 3 | 404 | - | 失敗（チャンネルが見つかりません） | なし | すべて同じ失敗。画面は「見つかりません」 |
| 4 | 403 | - | 失敗（アクセスできません） | なし | すべて同じ失敗 |
| 5 | 400、その他の 4xx（429 を除く） | - | 失敗（送信できませんでした） | なし（編集か破棄） | 列の先頭を次へ進める |
| 6 | 429、5xx、ネットワークエラー、タイムアウト | 10 分以上 | 未送信 | なし（手動） | すべて未送信 |
| 7 | 429 で、`Retry-After` が解釈できる | 10 分未満 | 待機（「送信が混み合っています」） | `Retry-After` の後（秒数、または HTTP 日付） | 待つ |
| 8 | 429（`Retry-After` がない・不正）、5xx、ネットワークエラー、タイムアウト | 10 分未満 | 待機 | 指数バックオフ：`min(30, 2^(n-1))` 秒（n は失敗の回数）、±20% のゆらぎ | 待つ |

- 「確定待ち」のメッセージは、併合したページにその `seq` か `client_msg_id` が現れた時点、または窓の最大の `seq` がその `seq` 以上になった時点で消え、確定したメッセージに置き換わる（REQ-WEB-032）。
- 最新ページの取り直しが失敗しても、確定待ちのメッセージは一覧に残る。取り直しは DT-WEB-003 の 7 行目の再試行に従う。

### DT-WEB-011: 取得したページの併合

上から順に評価し、最初に一致した行を採用する。「つながる」は、ページに窓の最大の `seq` 以下のメッセージが含まれる、またはページの `has_more` が偽であることを指す。`seq` の値の連続（`+1`）では判定しない（E3 以降、履歴に出ない `seq` があるため）。

| # | ページ | 窓 | 条件 | → 窓の操作 | → 窓が最新を含むか |
| --- | --- | --- | --- | --- | --- |
| 1 | 前のページ | 空、または要求の `before_seq` が今の窓の最小の `seq` と違う | - | 捨てる（古い応答） | 変えない |
| 2 | 前のページ | 要求の `before_seq` が窓の最小の `seq` と一致 | - | 前に足す。`has_more` をページの値にする | 変えない |
| 3 | 最新ページ | 空 | - | ページで窓を作る | 含む |
| 4 | 最新ページ | 最新を含まない | きっかけがタブの復帰 | 捨てる | 変えない |
| 5 | 最新ページ | 最新を含まない | きっかけがタブの復帰以外 | ページで窓を置き換える | 含む |
| 6 | 最新ページ | 最新を含む | つながる | 和集合で併合する（同じ `seq` はページの値にする） | 含む |
| 7 | 最新ページ | 最新を含む | つながらない | ページで窓を置き換える。`has_more` をページの値にする | 含む |

### DT-WEB-014: 入力欄のキー操作

## Correctness Properties

### PROP-WEB-010: 一覧は seq 順で重複がない

チャンネルを開く、前のページの読み込み、タブの復帰、送信、サーバーの応答（201・200・400・404・429・5xx・ネットワークエラー・応答の喪失）、他の人の投稿、応答の遅延と順序の入れ替わりの任意の交互の列に対して、どの時点でも、描画された一覧のうち `seq` を持つメッセージは `seq` の狭義の昇順に並び、同じ `seq` も同じ `client_msg_id` も 2 回以上現れない。この性質は、メッセージの応答が `client_msg_id` を含むことを前提にする（Open questions）。

### PROP-WEB-011: 窓はサーバーの列の区間と一致する

上と同じ任意の列に対して、どの時点でも、窓の確定したメッセージの列は、サーバーに保存されたそのチャンネルのメッセージの列を、窓の最小の `seq` から最大の `seq` までの区間に絞ったものと一致する（欠けも余りもない）。

### PROP-WEB-012: 送った順に 1 件ずつ投稿される

送信・破棄・手動の再送と、サーバーの応答（応答の喪失、5xx、429 を含む）の任意の列に対して、次がすべて成り立つ。(1) 同じチャンネルで同時に送られている `POST` は常に 1 件以下である。(2) 1 回の送信の操作は、再送を含めて 1 つの `client_msg_id` だけを使う。(3) すべての応答が届き再試行が終わった後、サーバーに保存されたメッセージは、破棄されず失敗にならなかった送信の操作ごとにちょうど 1 件で、同じチャンネルの中の `seq` の順は送信の操作の順と一致する。

### PROP-WEB-013: 未確定のメッセージは確定したものの後ろにある

上と同じ任意の列に対して、どの時点でも、描画された一覧で、すべての未確定のメッセージ（送信中・待機・確定待ち・失敗・未送信）は、すべての確定したメッセージより後ろにあり、送信の操作の順に並ぶ。

### PROP-WEB-014: Retry-After を守る

`POST` の応答の任意の列（`Retry-After` の値が 0〜120 秒の 429 を含む）に対して、429 を受けた時刻から `Retry-After` の時間が経つまでに、同じチャンネルの `POST` は 1 件も送られない。

### PROP-WEB-015: 前に足してもスクロールの位置が保たれる

任意の行の高さ（20〜400px）の窓と、任意の件数（1〜50）の前のページに対して、前に足す前に見えていた先頭の行の、一覧の上端からの位置は、足した後に 1px 以内の差で保たれる。

## Design

### Timeline ストアの範囲

[client.md](../../architecture/client.md) の 3.3 節の Timeline ストアのうち、E1 で作るものと、後の Epic で足すもの。ストアは React に依存しない TypeScript のモジュールにし、画面は `useSyncExternalStore` で読む。メッセージの取得は TanStack Query の `queryFn` 経由で行い、結果をストアへ流し込む（ADR-0024）。メッセージのクエリへ `setQueryData` で書き込むのはストアだけにする（lint）。

| 項目 | E1（この変更） | 後で足すもの |
| --- | --- | --- |
| `messages` | `seq` → メッセージ。連続した 1 つの窓、最大 1,000 件 | E3：編集・削除・リアクションの反映 |
| `window` | 最小・最大の `seq`、`has_more`（前）、最新を含むか | E3：`around_seq` で作った窓（最新とつながらない窓の取り直し） |
| `pending` | `client_msg_id` → 本文・状態・失敗の回数・作成の時刻・次の送信の時刻・受け取った `seq`。**メモリだけ** | E4：IndexedDB の `outbox`、SharedWorker での処理、再読み込み後の 10 分の規則 |
| `applied_seq`、`sync`（`stale` / `catching_up` / `live`） | 持たない | E4：イベントの適用、欠損の検知、差分取得（`after_seq`） |
| 新着の取り込み | 最新ページの取り直しと併合（REQ-WEB-026） | E4：WebSocket のイベントに置き換え、取り直しは差分取得にする |
| チャンネルの保持 | メモリに最大 10 チャンネル（LRU）。追い出したら次に開いたときに取り直す | E4：IndexedDB の読み取りキャッシュから戻す |
| ワークスペース | ストアのキーを `[workspace_id, channel_id]` にする（PROP-WEB-002） | 変えない |

- 送信の列（`src/features/composer/send-queue.ts`）は、DT-WEB-010 の状態遷移を純関数で持ち、時刻とネットワークを外から渡す。E4 で SharedWorker へ移すとき、この状態遷移をそのまま使う。
- `release.web_channel_view` が無効なワークスペースでは、チャンネルの枠に「準備中」を出し、メッセージの API を呼ばない。

### 送信の状態

```
          送信の操作
              │
              ▼
          送信中 ──201/200──▶ 確定待ち ──併合に現れる──▶ （確定したメッセージに置き換わる）
           ▲  │
   時刻が来る  │429/5xx/ネットワーク（10 分未満）
           │  ▼
           待機
              │ 10 分以上 / 401            400・その他 4xx / 403 / 404
              ▼                               ▼
           未送信 ──再送──▶ 送信中            失敗 ──編集・破棄──▶ （消える）
              └──破棄──▶ （消える）
```

### API

| 用途 | API | 状態 |
| --- | --- | --- |
| 履歴 | `GET /api/workspaces/{ws}/channels/{ch}/messages?before_seq&limit` → `{ messages, has_more }`（`seq` の降順） | REQ-MSG-004。クライアントは昇順に並べ直す |
| 投稿 | `POST /api/workspaces/{ws}/channels/{ch}/messages` `{ client_msg_id, body }` → 201 / 200 | REQ-MSG-001、002 |
| メンバーの表示名 | メンバーの Query | E1 にはない。REQ-WEB-037 の代わりの表示を使う |

- メッセージの応答に次が含まれることを前提にする。含まれるかは 260926 の契約で確定していない（Open questions）。`seq`、`client_msg_id`、`author_member_id`（名前は仮）、`body`、`created_at`。
- `client_msg_id` が応答にない場合も、確定待ちのメッセージは `seq` で重複を除ける。ただし応答を失った送信中のメッセージは、再送の 200 が届くまで、取り直したページの同じメッセージと一時的に二重に見える。

### 入力欄

- `<textarea>` にラベルを付け、`Enter` と `Shift+Enter` を DT-WEB-014 で扱う。設定での入れ替え（client.md の 5.1 節）は E3 で入れる。
- 文字列から AST への変換は `message-body-ast-v1` の `parsePlainText` を使い、この変更で独自に書かない。改行は段落の区切りになる（DT-MSG-004 の 1 行目）。入力した `<@UUID>` はメンションになる（E1 では補完がないため、実際には使われない想定）。
- 下書きの保存（client.md の 5.3 節）は E3 以降。チャンネルを切り替えると、入力欄の内容はチャンネルごとにメモリに残す。

### 非機能要件への影響

- NFR-002（送信 → 他者の画面に表示）は E1 では満たさない。他者の画面には、その人の取り直し（開く・送信・タブの復帰）で出る。E4 で満たす。
- client.md の 11 節の予算のうち、チャンネルの切り替え（キャッシュなし p75 500ms 以内、キャッシュあり 100ms 以内）と、一覧の DOM 150 行以下を、この変更で計測する。チャンネルの中身は骨格と別のチャンクにし、骨格の初回の JS の予算を圧迫しない。
- 投稿のレート制限（[rate-limiting.md](../../architecture/rate-limiting.md) の 4.2 節：メンバーあたり 1 秒に 1 件、バースト 5）に当たったときの扱いは DT-WEB-010 の 7 行目。取り直し（開く・送信・復帰）は 1 チャンネルにつき同時に 1 つなので、全 API の上限（1 分に 600 回）には通常届かない。

## Open questions

- **メッセージの応答の項目（Dev・PM）**：260926 の spec は応答に含める項目を定めていない。`client_msg_id`（重複の除去）、`created_at`（REQ-WEB-037）、投稿者の `member_id` を契約に含めるよう、260926 に足すか。
- **`after_seq`（Dev）**：窓が最新を含まないとき（DT-WEB-012 の 2 行目）、下へ読み進める手段がなく、「最新へ移動」で最新ページに戻るしかない。`after_seq`（または `around_seq`）は E3 の `jump-to-message` と E4 の差分取得で入る予定で、E1 ではこの制限を受け入れてよいか。
- **メンバーの表示名（PM）**：E1 に表示名の API がないため、投稿者は「メンバー」と ID の先頭で出る。walking skeleton としてこれでよいか、E1 にメンバーの取得を足すか。
- **未送信のメッセージの喪失（PM）**：E1 では再読み込みで未送信のメッセージが消える。確認の画面（`beforeunload`）を出すか。出すなら要件を足す。
- **自動の再試行の 10 分（PM・QA）**：client.md の 3.6 節の 10 分は、再読み込みの後の扱いとして書かれている。E1 では、同じ画面の中での自動の再試行の上限にも同じ 10 分を使った。
- **`limit` の値（Dev）**：最新ページ・前のページとも 50 にした。前のページを 100 にして取得の回数を減らすかは、性能の計測の後に決める。

## 決定（2026-09-26、PM・QA、既定案）

上の Open questions は、次のとおり決めた。

- メッセージの応答の項目は、`post-and-list-messages` の Design で定めた（反映済み）。
- `after_seq`・`around_seq` は、E3 の `jump-to-message` で足す。E1 は「最新へ移動」で戻る。
- E1 では、投稿者を「メンバー」と ID の先頭で表示する。表示名は E2 で足す。
- 未送信のメッセージがあるときは、ページを離れる前に確認を出す（REQ-WEB-039 を追加）。
- 自動の再試行は、同じ画面の中でも 10 分で打ち切る。
- `limit` は、最新ページ・前のページとも 50 にする。性能の計測の後に見直す。
