## 2. テスト設計

### 2.1 サーバーのモデル（`apps/web/test/support/fake-messages-server.ts`）

性質ベーステストで、ストアと送信の列を実 API なしで検査するための、260926 の API の振る舞いのモデル。

- 状態：チャンネルごとのメッセージの列（`seq` は 1 から欠けなく採番）、（メンバー, `client_msg_id`）→ メッセージの対応。
- `POST`：REQ-MSG-001、REQ-MSG-002 と DT-MSG-001 のとおり。201 / 200 を返す。
- `GET`：REQ-MSG-004 のとおり。`seq` の降順、`limit`、`before_seq`、`has_more`。
- 障害の注入（生成器が選ぶ）：応答の遅延（0〜5 秒）、応答の順序の入れ替わり、保存した後の応答の喪失（タイムアウト）、保存しない 5xx、429（`Retry-After` 0〜120 秒、欠けた値・不正な値を含む）、404（チャンネルから外す）。
- モデルそのものの正しさは、260926 の結合テストと同じシナリオをモデルに流して確かめる（モデルの単体テスト）。

### 2.2 生成器と試行回数

| 性質 | 生成するもの | 試行回数（PR / 夜間） | 各試行の長さ |
| --- | --- | --- | --- |
| PROP-WEB-010、PROP-WEB-011、PROP-WEB-013 | 操作の列：開く、前のページ、タブの復帰、送信（本文は短い文字列）、他の人の投稿（1〜200 件をまとめて）、応答の配送（どの保留中の応答を次に届けるか）、時間の経過 | 200 / 2,000 | 操作 1〜80 個 |
| PROP-WEB-012 | 送信・破棄・手動の再送と、障害の注入の列 | 200 / 2,000 | 送信 1〜20 件 |
| PROP-WEB-014 | 429 の列（`Retry-After` 0〜120 秒）と 5xx・成功の混在 | 500 / 5,000 | 応答 1〜30 個 |
| PROP-WEB-015 | 行の高さ（20〜400px）、窓の件数（1〜200）、前に足す件数（1〜50）、見えている位置 | Chromium 50・他 20 / 各 200 | — |

- 時間は偽のタイマーで進め、実時間に依存させない。
- 失敗した例は fast-check の縮小の結果（seed と path）を CI のログに出し、再現のテストとして固定する。
- 各時点の検査は、ストアの選択関数（描画に渡す列）に対して行う。DOM を使う検査は PROP-WEB-015 だけにし、他は Node で速く回す。

## 3. テスト環境とテストデータ

- 単体・表駆動・性質（DOM なし）：Vitest（Node）。
- 部品：Vitest の browser mode、Playwright のプロバイダで Chromium・Firefox・WebKit。CI の段（`test:browser`）は骨格の変更（260926-web-app-shell-routing）が足す。スクロールの位置の性質ベーステストを browser mode で回すのは、この変更が最初になる。
- E2E：Docker Compose の API と PostgreSQL に seed を入れ、Playwright（PR は Chromium、夜間は 3 エンジン）。
- seed：`seq` 1〜120 のチャンネル、0 件のチャンネル、1,200 件のチャンネル、`v: 2` の本文の行、参加していないプライベートチャンネル、同じワークスペースの 2 人目のメンバー（他の人の投稿用）。
- IME の手動確認：macOS の日本語入力で、Safari・Chrome・Firefox。リリース前に 1 回。
