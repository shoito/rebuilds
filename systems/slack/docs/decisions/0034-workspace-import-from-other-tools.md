# ADR-0034: 他のチャットツールからの取り込み（移行）の範囲と方式

## Context

チームが乗り換えるとき、過去のやり取り（チャンネル、メッセージ、スレッド、ファイル）とメンバーを持ち込めないと、「積み上がる知識」（intent の価値の 3）がゼロから始まる。取り込みは、intent の MVP にも Non-goals にも入っておらず、設計もない。

取り込みは、既存の決定と次の点でぶつかる。

- **順序**：`seq` はチャンネルの中で投稿のたびに採番する（[ADR-0001](0001-per-channel-sequence.md)）。既存のチャンネルに過去のメッセージを差し込むと、`seq` の順と時刻の順が食い違い、既読位置と差分取得が壊れる。
- **配信と通知**：取り込んだメッセージを通常の投稿の経路に流すと、リアルタイム配信・メンション・通知が大量に走る（[ADR-0002](0002-db-as-source-of-truth-with-outbox.md)、[ADR-0014](0014-sqs-worker-queues-and-notification-delivery.md)）。
- **メンバー**：取り込み元のユーザーが、まだこのシステムのアカウントを持たない。メンバーはアカウントと分けて持つ（[ADR-0010](0010-accounts-and-workspace-members.md)）。
- **本文とファイル**：本文は HTML ではなく AST で持ち（[ADR-0006](0006-message-body-ast.md)）、ファイルはスキャンを通す（[ADR-0015](0015-file-upload-scan-and-delivery.md)）。

本家は、Slack のエクスポートのファイルや CSV からの取り込みを手引きで案内している（[Guide to Slack import and export tools](https://slack.com/help/articles/204897248-Guide-to-Slack-import-and-export-tools)。対応する形式と範囲の細部は、着手時に確かめる）。取り込む形式は公開されたファイルの形であり、本家の実装の再利用にはあたらない（リポジトリ共通の [ADR-0007](../../../../docs/decisions/0007-no-reuse-of-original-implementation.md)）。

## Options

1. **取り込みを提供しない**（Non-goal にする）。移行は顧客が手で行う
2. **本家 Slack のエクスポートの ZIP（パブリックチャンネル）だけを取り込む。MVP の後、E8 で提供する**
3. 2 に加えて、汎用の CSV（チャンネル名、投稿者、時刻、本文）と、他のツール（Teams、Chatwork など）の形式も取り込む

範囲（どれを、いつ提供するか）は PM が決める（[intent.md](../intent.md) の Open questions）。推奨は 2。

## Decision

**推奨案は 2**（PM の判断待ち）。2 か 3 を採る場合の方式は次のとおりとする。

- **取り込みは新しいチャンネルにだけ行う。** 既存のチャンネルへの差し込みは提供しない。取り込みのジョブが、元の時刻の順に `seq` を 1 から採番し、終わったらチャンネルを公開する。こうすれば `seq` の順と時刻の順が一致し、ADR-0001 を崩さない。同名のチャンネルがあれば、別名（例：`general-imported`）を提案する。
- **通常の投稿の経路を通さない。** 取り込みの Worker が DB に直接まとめて書き、outbox にイベントを積まない。リアルタイム配信・メンション・通知・リンクのプレビューを出さない。検索のインデックスは、取り込みの後にバックフィルする。既読位置は、取り込んだチャンネルの末尾に置く（未読にしない）。
- **ユーザーの対応づけ**：取り込み元のユーザーを、メールアドレスで既存のメンバーに対応づける。管理者は取り込みの前に、対応づけの一覧を確かめて直せる。対応しないユーザーは、アカウントを持たない「取り込んだユーザー」のメンバー（`account_id` が NULL、無効化した状態）として作る。後でそのメールアドレスのアカウントが参加したら、管理者の操作でそのメンバーに結び付ける。
- **本文**：取り込み元の書式（mrkdwn など）を AST に変換する。変換できない要素はプレーンテキストとして残す。HTML を受け取って保存しない。
- **ファイル**：取り込みの ZIP の中のファイルも、通常のアップロードと同じスキャン（ADR-0015）を通す。スキャンを通らないファイルは取り込まず、結果の報告に載せる。容量はワークスペースの上限（[ADR-0032](0032-plans-and-entitlements.md)）に数える。
- **プライベートチャンネルと DM は、2 では取り込まない。** 取り込み元のエクスポートに含まれていても、範囲を広げるかは PM が決める。
- **実行と記録**：実行できるのは owner だけ。依頼・対応づけの確定・完了・失敗を監査ログに残す（[ADR-0018](0018-audit-log.md)）。ZIP はアップロードから 7 日で消す（エクスポートの成果物と同じ。[security.md](../architecture/security.md) の 14 節）。
- **ジョブ**：ZIP の検査（パスの走査、展開後のサイズの上限、件数の上限）を先に行い、取り込みはチャンネル単位で冪等にする。途中で失敗したら、そのチャンネルを消してやり直せる。
- 1 は、乗り換えの障壁が残る。3 は、形式ごとに変換と試験が要り、E8 の負担が大きい。2 で需要を確かめてから広げる。

## Consequences

- 良くなること：
  - 乗り換えたチームが、過去のやり取りを検索できる状態で始められる。
  - 取り込みが `seq`・配信・通知の既存の決定を崩さない。
- 引き受けるコスト：
  - 既存のチャンネルへ過去のメッセージを足せない。
  - 取り込み元の形式が変わると、変換を直す必要がある。形式ごとの固定のサンプルで回帰を試す。
  - 取り込み元の他人の発言と個人情報を預かる。扱いは法務の確認待ち（intent の Open questions）。

## Confirmation

- 性質ベーステスト：任意の取り込みデータで、取り込んだチャンネルの `seq` が欠番・重複なく、元の時刻の順と一致する（PROP-MSG-001 と同じ形）。
- 結合テスト：取り込みの間に、outbox・通知・Web Push が 1 件も発生しない。
- 結合テスト：ZIP のパスの走査（`../`）と、展開後のサイズの上限を超えるファイルを拒否する。
- 取り込みの後、別のワークスペースから取り込んだデータが見えない（NFR-009 の経路ごとの漏洩テストに加える）。
