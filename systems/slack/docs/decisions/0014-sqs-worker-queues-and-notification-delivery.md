# ADR-0014: Relay と Worker の間に SQS の標準キューを置き、通知は冪等な多段の処理で配送する

ADR-0002（transactional outbox）の、Worker 側の受け渡しを具体化する。詳細は [read-state-and-notifications.md](../architecture/read-state-and-notifications.md)。

## Context

Relay は outbox を読み、リアルタイム配信（Valkey）と、Worker（通知、検索インデックス、サムネイルなど）へイベントを渡す。Valkey の配信は失われてもよいが（ADR-0002）、Worker への受け渡しは失われてはならない。通知や検索への反映が、黙って欠けるためである。

通知には次の性質がある。

- 1 つのメッセージが、DM なら 1 人、@channel なら数万人への通知になる。
- 受け手ごとに、設定・DND・他の端末での操作・権限で結果が変わる。
- Web Push とメールは外部のサービスで、失敗・遅延・重複がありうる。
- メールは「15 分後にまだ未読なら送る」のように、遅らせて送る。

## Options

### Relay と Worker の間

1. **SQS の標準キュー**を Worker ごとに置き、Relay が直接送る
2. **SQS の FIFO キュー**（チャンネル単位の順序を保つ）
3. **SNS → SQS** のファンアウト、または EventBridge
4. **Kinesis Data Streams / MSK**（順序付きのログ）
5. **DB をキューにする**（Worker が outbox や専用のテーブルを直接読む）

### 通知の配送

A. 1 つの Worker が、受け手の決定から送信までを 1 回の処理で行う
B. **段を分ける**：計画（受け手を決める）→ 大人数の分割 → 経路ごとの送信。メールは DB に予定として置き、定期的に送る

## Decision

1 と B を採用する。

### SQS

- Worker の種類ごとに標準キューを置き、それぞれにデッドレターキュー（`maxReceiveCount` = 5）を付ける。Relay は `event_type` の対応表で宛先のキューを選び、`SendMessageBatch` で送る。
- Relay は、SQS への送信に成功するまで outbox の行を消さない。Valkey への配信は 1 回試して諦めるのと対照的に、SQS への受け渡しは確実に行う。
- メッセージには ID と小さな属性だけを入れ、本体は Worker が DB から読む。メッセージの大きさの上限と、権限の確認し直しの両方のため。
- Worker は、SQS のメッセージを「少なくとも 1 回」受け取り、順序も保証されない前提で作る。どの処理も冪等にし、順序が要る処理（検索インデックスの更新など）は、バージョン（`seq` や更新時刻）を比べて古いものを捨てる。
- 2 を採らない理由：通知には順序が要らない。FIFO はメッセージグループあたりのスループットに制約があり、1 つのチャンネルに通知が集中すると詰まる。
- 3 を採らない理由：受け手が 2〜3 種類のうちは、Relay から直接送るほうが構成が少ない。Worker の種類が増えて Relay の対応表が扱いにくくなったら、SNS か EventBridge を挟む。
- 4 を採らない理由：順序と再生が得られるが、運用とコストが重い。順序と再生は、`seq` と `channel_events` で DB がすでに持っている。
- 5 を採らない理由：Worker の処理が writer に負荷をかけ、ロックの設計も必要になる。

### 通知

- **計画（planner）**：受け手ごとに理由を 1 つに決め、設定・DND・他の端末での操作を適用し、送る直前に ADR-0005 の判定関数で読めるかを確かめ直す。
- **分割**：受け手が 500 人を超えたら分けて別のキューに積み、大人数の通知が DM やメンションを待たせないようにする。
- **Web Push**：VAPID で送る。1 受け手 1 ジョブ。失効した購読（404 / 410）は消す。`TTL` は 1 時間。
- **メール**：SQS の遅延は最大 15 分なので使わない。送る予定を DB（`notification_pending_emails`）に置き、1 分ごとに期限が来たものをメンバーごとにまとめ、まだ未読か・読めるかを確かめてから SES で送る。
- **冪等性**：受け手ごとの通知の記録（`notification_log`、主キーは `(workspace_id, member_id, message_id)`）を先に作り、作れたときだけ送る。外部への送信と記録の間で落ちたときの重複は、Web Push の `tag` による置き換えと、メールのまとめの ID で抑える。
- **テナント単位の制限**：ワークスペースごと・受け手ごとの上限を Valkey のトークンバケットで数える。超えたら遅らせるか、まとめる。
- A を採らない理由：@channel の 1 件が数万人分の処理になり、キューの可視性タイムアウトの中で終わらない。途中で失敗すると、全員分をやり直すことになる。

## Consequences

- 良くなること：
  - Worker への受け渡しが失われない。Worker が止まっても、キューに溜まるだけで、復旧後に追いつく。
  - キューごとに Worker をスケールでき、遅れを「最古のメッセージの経過時間」で見られる。
  - 大人数の通知と、少人数の通知の遅れが分かれる。
- 引き受けるコスト：
  - すべての Worker を冪等に作る必要がある。重複と順序の入れ替わりのテストが要る。
  - SQS が止まると、outbox が伸びる。Relay は SQS に送れない行を残したまま、Valkey への配信だけを先に進める必要がある。
  - Valkey と SQS の中身は、リージョンの切り替えで失われる。切り替え後は outbox の残りから再開し、通知の一部の欠落を許容する（[infrastructure.md](../architecture/infrastructure.md)）。
  - メールの予定のテーブルが増え、定期的な掃き出しの処理を 1 台だけで動かす仕組み（advisory lock）が要る。

## Confirmation

- 性質ベーステスト：任意の重複・順序の入れ替わりを含む `notify-events` の列に対して、1 つのメッセージで 1 人に送られる push とメールは、それぞれ最大 1 回である。
- 表駆動テスト：通知の適用の順序（[read-state-and-notifications.md](../architecture/read-state-and-notifications.md) の 6.2 節）の各行。spec に決定表として取り込んだあとは、spec から読み込む。
- 漏洩テスト：チャンネルから外されたメンバー、別のワークスペースのメンバーに、通知（push、メール）が届かないこと。
- 障害注入テスト：SQS への送信を失敗させても outbox の行が消えず、復旧後にすべての通知が 1 回ずつ送られること。
- 運用：デッドレターキューに 1 件でも入ったらアラートを出す（runbooks）。
