# ADR-0010: グローバルなアカウントと、ワークスペースごとのメンバーを分ける

## Context

1 人が複数のワークスペースに属する。ワークスペースごとに、表示名・アイコン・ロール・ゲストかどうか・無効化の状態が異なる。

それまでの設計では `users` が 1 つのグローバルなテーブルで、表示名もそこにあった。このままだと、次の 2 つの問題がある。

- ワークスペースごとのプロフィールを表せない。
- メッセージが、テナントの外にある ID を参照してしまう。

## Options

1. **グローバルなユーザー**を、全ワークスペースで共有する
2. **ワークスペースごとに完全に別のユーザー**（ログインもワークスペースごと）
3. **グローバルなアカウント＋ワークスペースごとのメンバー**：ログインはアカウントで 1 回だけ。ワークスペースの中ではメンバーとして別の ID を持つ（本家 Slack に近い形）

## Decision

3 を採用する。

| テーブル | テナント | 中身 |
| --- | --- | --- |
| `accounts` | 外（グローバル） | 認証のためだけの情報：メールアドレス、認証手段 |
| `members` | 内（`workspace_id` を持つ） | `account_id`、表示名、本名、アイコン、ロール（owner / admin / member / guest）、無効化日時 |

- **テナントの中のデータは、すべて `member_id` を参照する。** `account_id` は参照しない。メッセージ、チャンネルのメンバー、リアクション、メンションが対象で、テナントの中のデータがテナントの外の ID に依存しなくなる。
- 1 つのアカウントは、1 つのワークスペースに最大 1 人のメンバーを持つ（`UNIQUE (workspace_id, account_id)`）。
- `members.account_id` は NULL を許す。ボットや AI エージェントは、アカウントを持たないメンバーとして表す（roadmap の「エージェントを第一級のメンバーにする」）。
- ワークスペースを退出・無効化しても、`members` の行は消さない。過去のメッセージの投稿者として残す。
- 1 は、ワークスペースごとのプロフィールを表せない。2 は、ワークスペースを行き来するたびにログインが要り、体験が悪い。

## Consequences

- 良くなること：
  - テナントの中のデータが、テナントの中だけで閉じる（ADR-0009 の RLS と相性が良い）。
  - ワークスペースの削除が `workspace_id` 単位で完結する。
- 引き受けるコスト：
  - API で「今どのメンバーとして操作しているか」を、アカウントとワークスペースから毎回解決する必要がある（認証ミドルウェアで行う）。
  - 同じ人をワークスペース横断で扱う機能（Enterprise Grid 相当）は、アカウントを経由して別途設計する必要がある（MVP の範囲外）。

## Confirmation

- マイグレーションの lint：テナントテーブルから `accounts` への外部キーは、`members.account_id` 以外に存在しない。
- 結合テスト：同じアカウントが 2 つのワークスペースで別の表示名を持ち、それぞれのワークスペースの中でだけ見える。
