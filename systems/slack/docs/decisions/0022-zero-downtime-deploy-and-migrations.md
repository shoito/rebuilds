# ADR-0022: 無停止でデプロイし、スキーマは expand / contract で変える

## Context

NFR-004（月間 99.9%）のもとで、1 日に何度もデプロイしたい。無停止にするうえで、次の 3 つが課題になる。

- **Gateway は WebSocket を長く保持する。** 古いタスクを止めると、その接続がすべて切れる。S1 の 5 万接続が一斉に再接続すると、API の差分取得と DB に負荷が集中する。
- **スキーマの変更と、アプリの新旧の混在。** デプロイ中は新旧のアプリが同時に動く。どちらでも動くスキーマでなければならない。
- **RLS のポリシーの変更**（[ADR-0009](0009-pooled-tenancy-with-rls.md)）。ポリシーの誤りは、テナントの分離の破れ（quality.md のリスク 1 位）か、データが見えなくなる障害になる。

runbooks の 3 節で「ロールバックはデプロイではなくフラグで行う」と決めている。この ADR は、デプロイそのものの安全性を扱う。

## Options

デプロイの方式：

1. ECS のローリング更新（全サービス）
2. ECS のネイティブな blue/green（2025 年 7 月から ECS が単独で提供。カナリアと線形も選べる）（全サービス）
3. サービスごとに選ぶ：状態を持たないサービスは blue/green、Gateway はローリング＋穏やかな接続の移し替え

スキーマの変更：

A. デプロイと同時に、そのまま変更する
B. expand / contract：互換性を保つ追加（expand）と、古いものの削除（contract）を別のリリースに分ける

## Decision

3 と B を採用する。

### デプロイの方式

| サービス | 方式 | 理由 |
| --- | --- | --- |
| api | ECS のネイティブな blue/green（カナリア：10% → 100%）。CloudWatch アラームで自動ロールバック | 新旧を並べて、切り替えと戻しが速い |
| workers、relay | ローリング（`minimumHealthyPercent` 100%） | ALB を持たない。SQS と outbox から処理を再開できる |
| gateway | ローリング（1 回に全体の 10% 程度ずつ）＋穏やかな接続の移し替え | blue/green で一斉に切り替えても、古い接続は古いタスクに残り、結局止めるときに切れるため |

**Gateway の接続の移し替え**（詳細は [realtime.md](../architecture/realtime.md) の 3.5 節）：

1. ECS がタスクをターゲットグループから外し、新しい接続を送らなくなる。登録解除の遅延は 180 秒にする。ECS は、この遅延が過ぎてから SIGTERM を送る。
2. Gateway は、自分が登録解除されたことに気づいたら、接続を 150 秒かけて少しずつ `4000 reconnect` で切る。気づく方法（ECS のタスクメタデータ）は **未検証**。
3. クライアントは、ジッターを入れて再接続し、`seq` による差分取得で追いつく。データは失われない（[ADR-0002](0002-db-as-source-of-truth-with-outbox.md)）。
4. 残った接続は、遅延の終わりに ALB が切る。SIGTERM の後は、Fargate の `stopTimeout` の上限（120 秒）の中で終了する。

Gateway の登録解除の検知ができなかった場合も、ALB の切断とクライアントの再接続で吸収できる。ただし、そのときは再接続が一度に集中するので、1 回に入れ替える割合を小さく保つ。

### スキーマの変更（expand / contract）

1 回のリリースで行うのは、新旧のアプリの両方が動く変更だけにする。

| リリース | スキーマ | アプリ |
| --- | --- | --- |
| N（expand） | 列・テーブル・インデックスを足す。NULL 許容か既定値付き | 新旧の両方を書く（必要なら） |
| N と N+1 の間 | 既存の行を埋める（バックフィル）。Worker が小分けに実行する。マイグレーションの中ではしない | — |
| N+1 | — | 新しいほうだけを読む |
| N+2 以降（contract） | 古い列・テーブルを消す。バックアップと PITR の時点を確かめてから | — |

- マイグレーションは、アプリのデプロイの前に、1 回だけ実行する ECS タスクで行う。`migrator` ロールを使う。
- 各マイグレーションは `lock_timeout`（例：3 秒）と `statement_timeout` を設定し、長いロックを取らない。インデックスは `CREATE INDEX CONCURRENTLY` で作る。
- **RLS のポリシー：**
  - 新しいテナントテーブルは、テーブルの作成と同じマイグレーションで、`ENABLE`・`FORCE ROW LEVEL SECURITY` とポリシーを付ける。
  - 既存のポリシーを変えるときは、`DROP POLICY` と `CREATE POLICY` を同じトランザクションで行う。permissive なポリシーは OR で結合されるため、新しいポリシーを足してから古いものを消す手順にすると、その間だけ許可が広がる。
  - ポリシーの変更は、新旧のアプリの両方で PROP-WS-001 を通してからリリースする。

### マイグレーションの lint

CI で、次のどれかに当たるマイグレーションを失敗させる。

- expand のリリースで、列・テーブルの削除、列名の変更、型の変更、`NOT NULL` の追加（既定値なし）を行う
- `CONCURRENTLY` なしのインデックスの作成、`lock_timeout` の設定がない
- テナントテーブルに `workspace_id`、`FORCE ROW LEVEL SECURITY`、ポリシーのどれかがない（ADR-0009 の lint）
- `app` ロールへの `BYPASSRLS` の付与、テーブルの所有者の変更

### フィーチャーフラグ

種類・評価の場所・テスト・削除の規則は [ADR-0026](0026-feature-flags.md) で詳しくした。


- 新しい振る舞いは、すべてフラグの裏に置く（runbooks の 3 節）。デプロイ（コードを置くこと）とリリース（機能を有効にすること）を分ける。
- フラグは AWS AppConfig の機能フラグで持つ。`workspace_id` を単位に、社内 → 5% → 25% → 100% と広げる。割合での振り分けを `workspace_id` で安定させられるか（同じワークスペースが常に同じ側になるか）は **未検証**。できなければ、アプリで `workspace_id` のハッシュから判定する。
- フラグの変更は、AppConfig のデプロイ戦略（段階的な反映とアラームでの自動ロールバック）で行い、変更の履歴を残す。
- 100% にして 2 週間たったフラグは、コードから消す。残っているフラグの数を毎月見る。

## Consequences

- 良くなること：
  - 状態を持たないサービスは、切り替えと戻しが速い。
  - Gateway のデプロイが、再接続の嵐を起こさない。
  - スキーマの変更が、デプロイ中の新旧の混在で壊れない。アプリのロールバックもスキーマに縛られない。
- 引き受けるコスト：
  - スキーマの変更 1 つに、リリースが 2〜3 回かかる。
  - Gateway のデプロイは、全台の入れ替えに時間がかかる（1 回あたり数分 × 10 回程度）。
  - サービスごとにデプロイの方式が違う。手順を runbook にまとめて補う。

## Confirmation

- マイグレーションの lint（上記）を CI で実行する。
- staging で、デプロイ中に k6 で投稿と受信を続け、投稿 API のエラーが 0 件で、クライアントの最終状態が DB と一致することを確かめる（PROP-SYNC-001）。リリース前の確認に含める。
- Gateway のデプロイ中の再接続の速さ（1 秒あたりの再接続数）と、差分取得の API の負荷を計測し、上限を超えないことを確かめる。
- 手順は [runbooks/deploy-and-rollback.md](../runbooks/deploy-and-rollback.md)。
