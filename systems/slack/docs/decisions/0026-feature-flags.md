# ADR-0026: フィーチャーフラグの種類と運用を決める

[ADR-0022](0022-zero-downtime-deploy-and-migrations.md) の「フィーチャーフラグ」の節を、この ADR で詳しくする。

## Context

トランクベース開発（リポジトリ共通の ADR-0002）では、未完成の機能も `main` に入る。そのため、次の 2 つを分ける必要がある。

- **デプロイ**：コードを本番に置くこと
- **リリース**：機能を有効にすること

ADR-0022 では、フラグを AWS AppConfig で持ち、ワークスペース単位で広げ、2 週間で消すことだけを決めていた。フラグの種類、評価する場所、仕様との結びつけ、テスト、消し忘れの防止が決まっていない。

## Options

1. **AWS AppConfig の機能フラグ**
2. **フラグの SaaS**（LaunchDarkly など）
3. **自前**（DB のテーブルと管理画面）

## Decision

1 を採用する。

- AWS の中で完結し、変更は AppConfig のデプロイ戦略で段階的に反映される。アラームによる自動ロールバックと、変更の履歴も得られる。
- 2 は、割り当ての条件や実験の機能で勝る。ただし、ワークスペースの ID を社外に送ることになり、費用も接続数に比例して増える。
- 3 は、フラグの基盤そのものの可用性を自分で持つことになる。

### 種類

| 種類 | 目的 | 寿命 | 例 |
| --- | --- | --- | --- |
| release | 未完成・段階的な機能を隠す | 100% にして 2 週間で削除 | `release.thread_replies` |
| ops | 障害時に機能を止める（キルスイッチ） | 常設 | `ops.link_unfurl_enabled`、`ops.read_only_mode` |
| migration | データの移行や二重書き込みを切り替える | 移行の完了で削除 | `migration.search_read_opensearch` |
| entitlement | プランや契約で使える機能を分ける | 常設。ただし、プランの仕組みができたら DB へ移す | `entitlement.sso` |

> entitlement の種別は、[ADR-0032](0032-plans-and-entitlements.md) と [ADR-0033](0033-slack-aligned-platform-and-plan-decisions.md) の DB の entitlement に置き換えたため、使わない。

- 名前は `<種類>.<名前>` にする。種類ごとに、既定値と期限の規則を変える。
- 実験（A/B テスト）には使わない。必要になったら、別の ADR で決める。

### 割り当ての単位

- **割り当ての単位はワークスペースにする。** 同じワークスペースのメンバーは、同じ機能を見る。会話の相手どうしで見える機能が違うと、混乱を生むため。
- 割合で広げるときは、`hash(flag_name + workspace_id) mod 100` をアプリで計算して判定する。AppConfig の多変量フラグの `split` も、渡した値の一貫したハッシュで振り分ける（`seed` を渡せばフラグをまたいでもそろう。[AppConfig の文書](https://docs.aws.amazon.com/appconfig/latest/userguide/appconfig-creating-multi-variant-feature-flags-rules.html)、2026-09-26 に確認）が、判定を API・Gateway・Worker で同じ関数にそろえるため、アプリで計算する。
- 社内のワークスペースと、個別に指定したワークスペースの許可リストを持てるようにする。

### 評価する場所

| 場所 | 方法 |
| --- | --- |
| API・Worker・Relay | AppConfig Agent（サイドカー）から、ローカルで取得して評価する。取得できないときは、最後に取得した値を使う。起動時に取得できなければ、コードの既定値（安全側）を使う |
| Gateway | API と同じ。ワークスペースごとに、接続時に評価した結果を持つ |
| Web クライアント | 起動時の API（ブートストラップ）で、評価済みのフラグの一覧を受け取る。ワークスペースを切り替えたら取り直す。クライアントは AppConfig に直接触れない |

- フラグの定義（名前、種類、既定値、期限、持ち主）は、`packages/flags` に型付きで置く。コードからは、この定義を通してだけ参照する。
- **権限の判定をフラグで置き換えない。** フラグが有効でも、権限の判定（ADR-0005）は必ず通す。

### 仕様・計画との結びつけ

- 振る舞いを変える変更の `plan.md` には、使うフラグと、段階的なリリースの計画、削除のタスクを書く。
- `spec.md` の要件は、フラグが有効な状態の振る舞いを定める。無効な状態で既存の振る舞いが変わらないことは、`plan.md` の Proof に書く。

## Consequences

- 良くなること：
  - デプロイとリリースを分けられる。問題が起きたらフラグで止められ、デプロイで戻すより速い。
  - 障害時に止める手段（ops フラグ）を、あらかじめ用意できる。
- 引き受けるコスト：
  - フラグの組み合わせの数だけ、振る舞いが増える。テストと消し忘れの管理が必要になる。
  - AppConfig が使えないときは、最後に取得した値で動く。フラグの変更が反映されるまでに遅れが出る。

## Confirmation

- CI で、release と migration のフラグは、両方の状態でテストを実行する。テストの対象は、そのフラグを参照するパッケージの結合テストと E2E の主要シナリオ。
- CI で、期限を過ぎた release・migration のフラグがコードに残っていたら警告する。期限を 30 日過ぎたら失敗させる。
- `packages/flags` に定義のないフラグ名をコードから参照したら、型検査で失敗させる。
- フラグの変更は AppConfig の履歴と監査ログ（[ADR-0018](0018-audit-log.md)）に残す。
