# ADR-0013: Gateway を水平に増やし、購読をノードごとに集約する。在席は TTL と必要な分だけの購読で扱う

ADR-0003（Redis Pub/Sub）の使い方を具体化する。詳細は [realtime.md](../architecture/realtime.md)。

## Context

Gateway は WebSocket を保持し、Relay が Valkey に流したイベントを接続へ配る。規模は S1（同時接続 5 万、最大 5,000 人のワークスペース）から S3（100 万、10 万人）まで広げる。

決めることは 3 つある。

- 接続をどう Gateway のタスクに分け、Valkey のチャンネルをどう購読するか。
- 巨大なチャンネルと、再接続の殺到にどう耐えるか。
- 在席（オンライン / 退席）と入力中を、どこに置き、どう配るか。

前提として、配信はベストエフォートでよい（ADR-0002）。欠けたものはクライアントが `seq` で検知して差分を取る。

## Options

### 接続と購読

1. **全 Gateway が全イベントを受け取る**（ワークスペースやシステム全体の 1 つのチャンネル）。各ノードが自分の接続に関係するものを選ぶ
2. **接続ごとに Valkey を購読する**
3. **ノードごとに集約して購読する**：ノードが「チャンネル → 自分の接続の集合」を持ち、Valkey にはノードあたり 1 チャンネル 1 回だけ購読する
4. **チャンネルごとに担当ノードを決める**（一貫性ハッシュで振り分け、接続をそのノードへ寄せる）

### 在席

A. DB に保存し、変化をイベントとして流す
B. 各接続の心拍をワークスペース全体に流す
C. **Valkey に TTL 付きで置き、画面に出すメンバーの分だけ購読する**

## Decision

接続と購読は 3、在席は C を採用する。

### 接続と購読

- Gateway は ALB の後ろで水平に増やし、スティッキーセッションを使わない。どのノードにつないでも同じように動く。スケールの指標はタスクあたりの接続数にする（1 タスク 1 万接続を上限とみなす。負荷試験で見直す）。
- 1 つの接続は 1 つのワークスペースに属する。認証は API が発行する 1 回限りのチケットで行う。
- ノードは、接続が必要とするチャンネルを参照カウントで管理し、最初の 1 本で SUBSCRIBE、最後の 1 本がいなくなって 30 秒後に UNSUBSCRIBE する。受け取ったイベントは 1 回だけシリアライズして配る。
- Valkey のチャンネルは、チャンネルのストリーム `ws:{w}:ch:{c}` に加えて、メンバーのストリーム `ws:{w}:m:{member_id}` と在席の `ws:{w}:pr` を使う。どれも `ws:{workspace_id}:` で始める（ADR-0009）。
- 接続時は「購読してから `last_seq` を読む」。この順を守れば、接続の途中で来たイベントを落とさない。
- チャンネルからの退出は、同じチャンネルのストリームに `seq` を消費するイベントとして流す。同じ Valkey のチャンネルの上で順序が保たれるので、外された人に後続のメッセージが届かない。
- 1 と 4 を採らない理由：
  - 1 は、全ノードが全イベントを受け取るので、ノードを増やしても 1 ノードあたりの受信量が減らない。
  - 4 は、1 つの接続が数百のチャンネルに属するので、接続をチャンネルの担当ノードに寄せられない。
  - 2 は、同じチャンネルの購読がノードの中で接続の数だけ重なり、Valkey の購読数と配信量が接続数に比例する。
- **巨大チャンネル**：参加者が 1,000 人以上のチャンネルは、S2 で専用の経路にする。Relay のパーティションを分け、表示していない接続には「最新の `seq`」だけを間引いて送り、差分取得を Valkey のキャッシュから返す。
- **S2** では Valkey をクラスタモードにし、sharded pub/sub（`SPUBLISH` / `SSUBSCRIBE`）を使う。通常の PUBLISH はクラスタの全ノードに伝わるので、シャードを増やしても配信の負荷が分散しない。
- **S3** ではセルごとに Gateway と Valkey を持ち、セルをまたぐ購読を作らない。

### 在席と入力中

- Gateway が接続ごとに Valkey のソート済み集合へ失効時刻付きで登録し、30 秒ごとに延長する（90 秒で失効）。複数の端末の状態は、メンバー単位にまとめる。
- 状態の変化は、ワークスペースの在席チャンネルへ 1 秒ごとにまとめて流す。クライアントは画面に出すメンバー（最大 500 人）だけを Gateway に伝え、Gateway はノード単位で和集合を持って関係するものだけを配る。
- Gateway は 30 秒ごとに、見ているメンバーの在席を読み直す。Gateway が落ちたときの `offline` は、この照合で最大 90 秒遅れて反映される。
- 入力中は、Gateway がチャンネルのストリームへ `seq` なしで流す。3 秒に 1 回までに間引き、保存しない。大規模チャンネルでは流さない。
- A を採らない理由：在席は数十秒で変わり、失っても害が小さい。DB に書くと、書き込みの大半が在席になる。
- B を採らない理由：10 万人のワークスペースでは、心拍だけで大量のイベントになり、誰も見ていないメンバーの分まで配ることになる。

## Consequences

- 良くなること：
  - Valkey の購読数と受信量が、接続数ではなく「ノード数 × そのノードが必要とするチャンネル数」に比例する。
  - Gateway は状態を作らないので、いつでも落として入れ替えられる。
  - 在席が DB に負荷をかけない。
- 引き受けるコスト：
  - 接続時に、読めるチャンネルの一覧と `last_seq` を DB（reader）から読む。再接続が殺到すると DB に集中するので、受け付けの制限・ジッター・差分取得の優先順位が必要になる。
  - Gateway が落ちたときの `offline` は、最大 90 秒遅れる。
  - Fargate の停止猶予は最大 120 秒で、ALB は登録解除の遅延が過ぎると残った接続を切る。デプロイ時の切り替えは、Gateway が登録解除を検知して少しずつ切る方式に頼る。検知の方法（タスクメタデータ）は未検証。
  - 巨大チャンネルの経路は、通常の経路と別の振る舞いになる。テストの組み合わせが増える。

## Confirmation

- 負荷試験（k6）：S1 の規模で NFR-002 を満たすこと。1 投稿あたりの Valkey からの受信が、Gateway のノード数以下であること。
- 障害注入テスト：Gateway の再起動・Valkey のフェイルオーバー・再接続の殺到のあとで、全クライアントの状態が DB と一致すること（PROP-SYNC-001）。
- 経路ごとの漏洩テスト：チャンネルから外されたメンバー、別のワークスペースの接続に、イベントが届かないこと（ADR-0005）。
- レビュー観点：Gateway が DB に書き込んでいないこと、`channel_members` を判定関数を通さずに参照していないこと、Valkey のチャンネル名が `ws:{workspace_id}:` で始まること。
