# ADR-0035: 運用者の本番へのアクセスと、ワークスペースの参照の許可

## Context

運用者（Ops、サポート、Dev）の本番へのアクセスは、[security.md](../architecture/security.md) の 4 節の統制の表に 1 行（SSO＋MFA、最小権限、break-glass、四半期のレビュー）があるだけで、次が決まっていない。

- 平常時に持つ権限と、期限つきで得る権限の境目
- サポートが顧客のワークスペースの中身（メッセージ、ファイル）を見るときの条件
- 運用者がメンバーになりすませるか

監査ログには「サポートのためのワークスペースへのアクセス」を記録する分類と、運用者の操作をそのワークスペースの監査ログにも出す決定がある（[ADR-0018](0018-audit-log.md)）。記録はあるが、アクセスそのものの条件がない。

Auth0 の題材は、同じ問いを [ADR-0056](../../../auth0/docs/decisions/0056-operator-access.md) で決めた。ワークスペースの中身は、顧客から委託を受けて扱うデータであり（security.md の 13 節）、同じ形が合う。本家に、owner がサポートの参照を許可する機能があるかは未検証。

## Options

1. **Auth0 の ADR-0056 と同じ形にする。** 常設の権限は秘密と本文を含まない観測だけ。本番の DB・シェルは期限つきの権限（JIT）で得る。ワークスペースの中身の参照は、owner の許可を前提にする
2. Ops に本番の読み取りの常設の権限を与え、監査ログで追う
3. 本番のすべてを JIT にし、承認を常に 2 人にする（Stripe の CDE と同じ）

## Decision

1 を採用する（2026-10-25 に承認）。

- **常設の権限**：Grafana のダッシュボード、メトリクス、アラート、トレース、アプリのログ（本文・トークンを含めない。security.md の 14 節）の読み取り。サポートの管理ツールでの、ワークスペースの設定・プラン・メンバー数などのメタデータの参照（本文を含まない）。
- **期限つきの権限（最長 4 時間）**：

  | 権限 | 承認 | 使う場面 |
  | --- | --- | --- |
  | 本番の DB の読み取り（RLS の対象のロール `ops_read`。`SET LOCAL app.workspace_id` でワークスペースを 1 つ指定する） | Ops の責任者（依頼者と別） | 障害の調査、顧客からの問い合わせ |
  | 本番の DB の書き込み | Ops の責任者と Dev のテックリードの 2 人 | データの修復 |
  | ECS Exec、タスクへのシェル | 同上 | 障害の調査 |
  | KMS の鍵の管理 | セキュリティの担当と Ops の責任者の 2 人 | 緊急の鍵の操作 |

- **`ops_read` は `BYPASSRLS` を持たない。** ADR-0009 のロールの表に足す。テナントをまたぐ読み取りは、break-glass の場合だけにする。
- **ワークスペースの中身の参照は、owner の許可を前提にする。** owner（Enterprise では admin も）が、管理画面でサポートの参照を期限つき（既定 72 時間）で許可する。許可は `workspace_settings` に期限と範囲（メタデータだけ／チャンネルを指定して本文まで）を持たせる。許可のない参照は、セキュリティインシデントと法令に基づく要請への対応に限り、事後に owner へ知らせる（法令が禁じる場合を除く）。
- **記録**：許可・取り消し・期限つきの権限の付与・参照を、`platform_audit_events` と、そのワークスペースの監査ログの両方に残す（`actor_type = operator`。ADR-0018）。owner は管理者の監査ログの画面で見られる。
- **なりすましの機能を作らない。** 運用者が、メンバーとしてセッションやトークンを作る機能、メンバーとして投稿する機能は作らない。
- **AI エージェントは本番に経路を持たない。** security.md の 7.3 節のとおり。サポートの調査でも、人が取り出した本文と個人情報を含まないものだけを渡す。
- **レビュー**：四半期ごとに、権限の割り当てと期限つきの権限の使用の記録を見直す。週次で、期限を過ぎて残る割り当てを検出する。
- 2 は、1 人のアカウントの乗っ取りで全ワークスペースの本文が読める。3 は、障害の調査が遅くなり、NFR-004（月間 99.9%）の障害の対応に合わない。

## Consequences

- 良くなること：
  - 運用者のアカウントが乗っ取られても、常設の権限で本文は読めない。
  - 顧客は、サポートがいつ何を見たかを自分の監査ログで確かめられる。
- 引き受けるコスト：
  - owner の許可を待つ間、問い合わせへの回答が遅れる。
  - 障害の調査で、期限つきの権限を得る手間（数分）がかかる。SEV1 では、承認をオンコールの二次が行ってよい。

## Confirmation

- IAM の静的検査（Terraform の CI）：本番のアカウントに、期限つきの権限の仕組み以外から DB・ECS Exec・KMS の管理の権限を持つ人のロールがない。
- DB の検査（CI）：`ops_read` が `BYPASSRLS` を持たず、テーブルの所有者でもない（ADR-0009 の `app` と同じ検査）。
- 結合テスト：owner の許可がない、または期限を過ぎたワークスペースを、サポートの管理ツールで本文まで開けない。参照がそのワークスペースの監査ログに出る。
- 四半期：アクセスレビューの記録。
