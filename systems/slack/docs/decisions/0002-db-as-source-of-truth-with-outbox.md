# ADR-0002: DB を唯一の正本とし、配信はベストエフォートにする。連携は transactional outbox で行う

## Context

リアルタイム配信（WebSocket）は、切断・遅延・重複を避けられない。配信経路に正しさの責任を持たせると、配信系が複雑になる。

## Options

1. Kafka などによる exactly-once 配信で、配信経路自体を信頼できるものにする
2. API がコミット後に直接 publish する
3. DB を正本とし、outbox 経由でベストエフォートに配信する。欠損はクライアントが差分取得で回復する

## Decision

3 を採用する。

- 正しさの責任を DB とクライアントの差分取得の 2 か所に集め、配信系を単純に保つ。
- 2 は、コミットと publish の間で落ちると取りこぼしが起き、順序が入れ替わると存在しないメッセージを参照する「幽霊メッセージ」が出る。outbox なら同じトランザクションに載る。

## Consequences

- 良くなること：Redis や Gateway が落ちてもデータは失われない。配信系を気軽に再起動できる。
- 引き受けるコスト：Relay というコンポーネントが増える。outbox テーブルの掃除が必要になる。

## Confirmation

- 障害注入テストで、Redis の停止・Gateway の再起動のあとも、全クライアントの最終状態が DB と一致することを検証する（PROP-SYNC-001）。
