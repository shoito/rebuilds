# ADR-0031: アプリの基盤を、インストール単位のボット、署名付きの HTTPS の配送、宣言的な UI で作る

## Context

intent.md は、アプリ / Bot のプラットフォームを MVP の対象外にしていた。MVP の後の E12 で、本家の Slack App に相当する基盤（マニフェスト、ワークスペースへのインストール、ボット、スコープ、Events API、インタラクティブ機能、アプリのホーム、Incoming Webhook、管理者の承認、配布）を出すことが決まった。公開のディレクトリは範囲外とする。

決めることは次のとおり。どれも後から変えるコストが高い。

- アプリとボットを、テナントのモデル（[ADR-0009](0009-pooled-tenancy-with-rls.md)、[ADR-0010](0010-accounts-and-workspace-members.md)）にどう載せるか
- ボットのトークンとインストールの認可を、何で作るか（[ADR-0012](0012-self-hosted-auth-with-better-auth.md)）
- イベントを、どうアプリへ届けるか
- アプリの出す UI を、どう安全に描画するか（[ADR-0006](0006-message-body-ast.md)）
- アプリの URL への送信（SSRF の危険）を、どこから出すか（[ADR-0016](0016-isolated-link-unfurling.md)）

## Options

### アプリとボットのモデル

1. アプリの定義はグローバル、インストールはテナントの中。インストールごとに `account_id IS NULL` のボットのメンバーを作る
2. アプリ自体を、ワークスペースをまたぐ 1 つの主体にする

### イベントの届け方

A. 署名付きの HTTPS の `POST`（再試行、無効化）だけ
B. A に加えて、WebSocket での受け取り（本家の Socket Mode）
C. アプリにポーリングさせる

### UI

a. 宣言的な JSON のブロックを、クライアントが自前の部品で描画する
b. アプリの HTML を iframe（サンドボックス）で表示する

### 外向きの通信

i. 既存の unfurler（ADR-0016）の関数を共用する
ii. ADR-0016 と同じ方式（VPC に接続しない、権限のない Lambda）で、アプリ用の関数を分ける
iii. VPC の中の Worker から、Network Firewall の許可リストで出す

## Decision

1・A・a・ii を採用する。設計の詳細は [apps.md](../architecture/apps.md) にある。

- **インストール単位のボット（1）。** ボットはインストールごとのメンバーで、人間と同じ判定関数と RLS を通る。ワークスペースをまたぐデータを持つ主体を作らない。2 は、テナントの分離の前提（ADR-0009）を崩す。
  - [identity-and-access.md](../architecture/identity-and-access.md) の 9 節のボットは、アプリのインストールに一本化する。`members` に種類の列（`human` / `bot` / `agent`）を加える。
  - アンインストールでは、ボットを無効化してチャンネルから外し、トークンを失効させる。過去の投稿は残す（[ADR-0019](0019-data-retention-and-deletion.md)）。
- **認可は Better Auth の oauth-provider、ボットのトークンは自前。** インストールの同意・認可コード・ユーザーのトークンは、MCP（[ADR-0028](0028-remote-mcp-server.md)）と同じ Better Auth の oauth-provider で行い、アプリは機密クライアントとして登録する。ボットのトークン（`slk_bot_...`）は、アカウントを持たないメンバーのものなので、本システムが発行する（ADR-0012 の方針どおり）。ボットのスコープはマニフェストの版に固定し、追加は再同意とする。
- **スコープの語彙は MCP と共通にする。** `channels:read`、`messages:read`、`messages:write`、`search:read`、`members:read`、`reactions:write` に、`channels:join`、`channels:manage`、`reactions:read`、`files:read`、`files:write`、`members:read.email`、`commands`、`incoming-webhook` を加える。機微なスコープは、ワークスペースの方針にかかわらず管理者の承認を要する。
- **HTTPS の配送だけ（A）。** 配送は「少なくとも 1 回」で、順序は保証せず、`channel_id` と `seq` と `event_id` を付ける。中身は送る時点の DB から作り、再試行の間に消されたデータを出さない。失敗が続けば宛先を無効にする。署名は Standard Webhooks の形式（HMAC-SHA256、時刻、ID）。
  - B は、確実な配送の責務を持つ、状態のある新しい接続のサービスが要る。Gateway（[ADR-0013](0013-gateway-scaling-and-presence.md)）はベストエフォートの配信のためのもので、流用できない。需要が続けば別の ADR で検討する。
  - C は、イベントの遅延と無駄な呼び出しが増える。
- **宣言的な UI（a）。** UI ブロックは Zod で検証した JSON で、クライアントが自前の React の部品で描画する。HTML・スクリプト・外部の画像を受け付けず、アプリの出したものに必ず「アプリ」の印を付ける。本文（リッチテキスト）を必須にし、通知と検索は本文だけを使う。b は、CSP を広げ、クリックジャッキングとフィッシングの面を増やす。
- **インタラクティブ機能は、3 秒以内の ack を求める。** 本システムの側の予算を含め、アプリの応答を待つのは 2.5 秒まで。後の応答は `response_url` と公開 API で受ける。`trigger_id` は 10 秒・1 回限り。
- **外向きの通信は、ADR-0016 と同じ方式で関数を分ける（ii）。** Events API 用と、インタラクティブ用（プロビジョニング済みの同時実行）の 2 つ。署名は VPC の中で行い、Lambda は秘密も権限も持たない。i は、アプリの遅い宛先がリンクのプレビューを止める。iii は、宛先が任意の URL なので許可リストを作れない。送信元の IP は固定しない。
- **管理者の統制と配布。** ワークスペースは `open` / `approval_required` の方針と、アプリごとの許可・拒否を持つ。他のワークスペースへ配る「配布型」のアプリは、運用者の審査とドメインの確認を通したものだけが、一般のワークスペースに入る。

## Consequences

- 良くなること：
  - ボットが人間と同じ権限のモデルに載り、テナントの分離に抜け道を作らない。
  - アプリの遅延・障害・悪意が、投稿の経路とリンクのプレビューに波及しにくい。
  - UI の描画が、本文と同じく XSS の面を持たない。
  - 管理者が、インストール・スコープ・停止を統制できる。
- 悪くなること、引き受けるコスト：
  - 配送の Worker、スケジューラー、2 つの Lambda、開発者コンソール、審査の運用が増える。
  - Socket Mode がないので、公開の URL を持てない環境ではアプリを動かしにくい。送信元の IP を固定しないので、IP で絞るアプリの側の要望に応えられない。
  - Better Auth の oauth-provider の、ワークスペースへの結び付け・トークンの応答への項目の追加・`client_secret` の入れ替え（旧い秘密が即座に無効になる）は、未検証か制約がある。合わなければ、トークンのエンドポイントを自前のハンドラーで包む。
  - 審査の担当（ロール）を新しく決める必要がある。
  - アプリの側に渡ったデータは、アンインストール後も本システムでは消せない。規約と審査で扱う。

## Confirmation

- 性質ベーステスト：アプリに配送されるイベントは、配送の時点でボットが読めて、スコープが許すものの部分集合である。別のワークスペースのインストールに配送されない。
- 表駆動テスト：インストールの判定、アプリの応答ごとの扱い、ボットのライフサイクル（[apps.md](../architecture/apps.md) の 6.4 節・7.4 節・5.2 節）。
- 性質ベーステスト：任意の UI ブロックの描画結果に、実行可能な要素と外部の画像が含まれない。
- SSRF のテスト：ADR-0016 の Confirmation の宛先の一覧で、アプリ用の Lambda が送信しない。IaC の検査で、アプリ用の Lambda に VPC の設定がなく、実行ロールの権限がログの書き込みだけであることを確かめる。
- 署名：公開するテスト用のベクターで、SDK と本システムの署名が一致する。
- アンインストールの結合テスト：トークン・ボット・コマンド・Webhook・ビュー・未配送のイベントが、[apps.md](../architecture/apps.md) の 15 節の表どおりになる。
- lint：`members.kind = 'bot'` のメンバーを特別に通す分岐を、`authorization.ts` の外に書かない。
