# ADR-0018: 監査ログは操作と同じトランザクションで DB に書き、改ざんできないアーカイブへ送る

## Context

次の 3 つの目的で、「誰が、いつ、何をしたか」の記録が必要になる。

- ワークスペースの管理者が、自分のワークスペースで起きた管理操作を確かめる（企業顧客の要求）。
- 運用者がセキュリティインシデントを調査し、影響の範囲を特定する（[security.md](../architecture/security.md) の 12 節）。
- SOC 2 などの監査に、証跡として出す。

監査ログには次の性質が要る。

- 操作が成功したのに記録がない、という状態を作らない。
- 運用者を含め、あとから書き換え・削除できない。書き換えられたら検知できる。
- テナントの分離を守る。管理者が見られるのは自分のワークスペースの記録だけ。

## Options

1. **アプリのログ（CloudWatch Logs）に構造化ログとして出す**
2. **操作と同じトランザクションで、DB のテナントテーブル（`audit_events`）に追記する。** 別のプロセスが改ざんできないアーカイブ（S3 の Object Lock）へ送り、ハッシュの連鎖で改ざんを検知できるようにする
3. **専用の別ストア**（別の DB クラスタ、CloudTrail Lake のカスタムイベントなど）に、API から直接書く

## Decision

2 を採用する。

- 1 は、ログの送信が失敗しても操作は成功するため、記録の欠落を防げない。テナントごとの検索にも向かない。
- 3 は、操作とのトランザクションを共有できず、1 と同じ欠落が起きる。構成要素も増える。
- 2 は、transactional outbox（ADR-0002）と同じ考え方で、欠落をなくせる。アーカイブで改ざんへの耐性を持たせる。

### 何を記録するか

| 分類 | 例 |
| --- | --- |
| 認証 | ログインの成功・失敗、MFA・パスキーの登録・解除、セッションの失効、SSO の設定の変更 |
| メンバー | 招待、参加、ロールの変更、無効化・再有効化、ボット・AI エージェントの作成とトークンの発行・失効 |
| 権限・チャンネル | プライベート ⇄ パブリックの変更、アーカイブ、管理者によるメンバーの追加・除外、チャンネルの削除 |
| 管理設定 | ワークスペースの設定、セキュリティの設定、保持ポリシーの変更 |
| データの持ち出し | エクスポートの依頼・完了・ダウンロード |
| 削除 | 管理者によるメッセージ・ファイルの削除、保持ポリシーによる削除の実行（件数の要約）、ワークスペースの削除の依頼・取り消し・消去の完了 |
| リーガルホールド | 作成・対象の変更・解除 |
| 運用者のアクセス | サポートのためのワークスペースへのアクセス、break-glass による本番へのアクセス、運用者によるワークスペースの停止 |

- **記録しないもの**：通常のメッセージの投稿・閲覧、既読の更新。量が多く、メッセージ自体が記録になっている。
- **権限による拒否**は、管理操作の拒否だけを記録する。それ以外はセキュリティのメトリクス（[observability.md](../architecture/observability.md)）で扱う。
- **本文を記録しない。** 削除されたメッセージは `message_id` だけを残す。設定の変更は、変更前と変更後の値を残す。秘密情報とトークンは残さない。

### 形

```sql
audit_events (workspace_id, id,                  -- UUIDv7
              occurred_at,
              actor_type,                        -- human / bot / agent / operator / system
              actor_member_id NULL,              -- テナントの中は member_id（ADR-0010）
              actor_operator_id NULL,            -- 運用者（社内の SSO の ID）
              action,                            -- 例：member.role_changed
              target_type, target_id,
              result,                            -- success / denied
              ip, user_agent, request_id,
              metadata JSONB,                    -- 変更前後の値など
              PRIMARY KEY (workspace_id, id))
```

- テナントテーブルとして RLS を掛ける（ADR-0009）。
- **追記のみ**：`app` ロールには `INSERT` と `SELECT` だけを与え、`UPDATE`・`DELETE` を与えない。トリガーでも更新と削除を拒否する。
- ワークスペースに属さない記録（アカウントのログイン、ワークスペースを特定しない運用者の操作）は、テナントの外の `platform_audit_events` に同じ形で書く。アカウントのログイン履歴は、本人だけが見られる。

### アーカイブと改ざんの検知

```
API（操作＋audit_events を同じトランザクションで INSERT）
  └─▶ Aurora の audit_events
        └─▶ Audit exporter（専用の DB ロール audit_exporter。audit_events の読み取りだけ）
              ├─ ワークスペースごとに、直前のバッチのハッシュを含めてバッチを作る（ハッシュの連鎖）
              ├─ S3 の監査用バケット（Object Lock コンプライアンスモード、KMS の audit キー）へ書く
              └─ 1 時間ごとに、全バッチのハッシュをまとめたダイジェストを KMS の非対称キーで署名して置く
```

- `audit_exporter` ロールは、テナントをまたいで `audit_events` だけを読める専用のポリシーを持つ。ほかのテーブルは読めない。
- コミットの順と ID の順はずれうるため、エクスポーターは遅延を持たせた透かし（watermark）で読み、取りこぼしを防ぐ。詳しい方式は実装の `plan.md` で決める。
- 監査用バケットは、本番のアプリとは別の AWS アカウント（[infrastructure.md](../architecture/infrastructure.md) の log-archive）に置く。本番のアカウントの管理者でも削除できない。
- 検証のツールで、ハッシュの連鎖と署名を定期的に検証する。不一致はセキュリティインシデントとして扱う。
- AWS の API 操作は CloudTrail（組織の証跡）で記録し、同じアーカイブ用のアカウントに置く。

### テナントから見える監査ログ

- ワークスペースの `owner` と `admin` が、Web の管理画面と API で見られる。
- 期間・行為者・操作・対象で絞り込める。CSV / JSON でエクスポートできる（そのエクスポート自体も記録する）。
- 運用者が顧客のワークスペースにアクセスした記録も、そのワークスペースの監査ログに出す。
- 読み取りは DB の `audit_events` から行う（直近 1 年）。

### 保持

| 場所 | 期間 | 期限後 |
| --- | --- | --- |
| DB の `audit_events` | 1 年 | 削除の Worker が消す（専用のロールで行い、その実行自体を `platform_audit_events` に残す） |
| S3 のアーカイブ | 400 日（Object Lock で固定） | ライフサイクルで削除 |
| CloudTrail | [observability.md](../architecture/observability.md) の 7 節に従う | 同上 |

- ワークスペースの削除後も、アーカイブの監査ログは期限まで残る。個人に関わる項目は `member_id`・IP・User-Agent に限り、本文を含めないことで、残すことの影響を小さくする（ADR-0019）。
- 保持期間を契約で延ばす（企業向け）ときは、ワークスペースごとの保持の設定を加える。今は作らない。

## Consequences

- 良くなること：
  - 操作が成功すれば、必ず記録が残る。
  - テナントの分離を、ほかのデータと同じ RLS で守れる。
  - 運用者でも、記録を消したり、気づかれずに書き換えたりできない。
- 引き受けるコスト：
  - 管理操作のトランザクションに INSERT が 1 件増える。
  - エクスポーター、別の AWS アカウント、署名の検証ツールを持つことになる。
  - Object Lock のコンプライアンスモードは、期間を短くできない。期間を誤って長くすると、費用と削除の約束の両方に響く。設定は IaC のレビューで守る。
  - ワークスペースの削除後も、監査ログが最長 400 日残る。顧客への説明が要る。

## Confirmation

- 監査の対象の操作ごとに、「操作が成功したら `audit_events` に 1 件ある」「操作が失敗・ロールバックしたら記録がない」を結合テストで確かめる。対象の一覧を表にし、表駆動テストにする。
- `app` ロールで `audit_events` を `UPDATE`・`DELETE` できないことを、RLS のテストと同じ場所で確かめる。
- 監査用バケットの Object Lock の設定と、別アカウントであることを IaC の検査で確かめる。
- ハッシュの連鎖と署名の検証を毎日実行し、失敗したらアラートにする。
- 本文・トークンが `metadata` に入っていないことを、テストのデータで検査する。
