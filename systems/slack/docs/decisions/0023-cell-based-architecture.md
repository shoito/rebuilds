# ADR-0023: S3 でセル構成に移る

S3（同時接続 100 万）に向けた計画。S2 を運用して得た数字で見直し、S3 への移行を始めるときに accepted にする。

## Context

S1・S2 の構成は、1 つの Aurora クラスタ、1 つの Valkey、1 つの Gateway の群れをすべてのワークスペースで共有する。規模が大きくなると、次の問題が出る。

- **縦に伸ばす限界。** Aurora の writer は 1 台で、最大のインスタンスクラスを超えられない。
- **障害の影響範囲。** 1 つの障害（誤ったマイグレーション、DB の過負荷、設定の誤り）が、全顧客を同時に止める。S3 の可用性の目標（NFR-004 の 99.95%）を守りにくい。
- **テナント間の負荷の偏り。** 大口のワークスペース（10 万人）が、共有の資源を占有しうる。

[ADR-0009](0009-pooled-tenancy-with-rls.md) は、この段階で「ワークスペース → DB の対応表」を置き、セルか専用の DB へ移れる形を残している。

## Options

1. **縦に伸ばし続ける**：Aurora のインスタンスを上げ、reader を増やし、Valkey のシャードを増やす
2. **DB だけを分割する（シャーディング）**：アプリの群れは共有のまま、ワークスペースごとに DB を振り分ける
3. **セル構成**：スタック一式（api、gateway、relay、workers、Aurora、Valkey、検索）をセルとして複製し、ワークスペースをセルに割り当てる。アカウントと認証など、ワークスペースをまたぐものだけをセルの外（Global）に置く

## Decision

3 を採用する（提案）。

- 1 は、writer 1 台の上限と、障害の影響範囲の問題を解決しない。
- 2 は DB の上限を解決するが、Gateway・Valkey・デプロイの失敗の影響範囲は全体のまま残る。アプリがすべての DB への接続を持つことになり、接続の管理も複雑になる。
- 3 は、規模と影響範囲の両方をセルの単位で閉じる。セルの中の設計は S1・S2 と同じなので、アプリのコードの変更は、Global との境界に限られる。

### 要点

構成の詳細は [infrastructure.md](../architecture/infrastructure.md) の 10 節にある。

- **セルの中身**：S1〜S2 のスタック一式。セルの中のコードは、自分がどのセルかを知らなくてよい。
- **Global（セルの外）**：アカウントと認証（[ADR-0010](0010-accounts-and-workspace-members.md)）、workspace → cell の対応表、アカウント → ワークスペースの一覧、課金。
- **ルーティング**：ログイン後に、Global がクライアントへセルのエンドポイントを返す。セルは自分が持たないワークスペースへのリクエストに 421 を返し、クライアントは対応表を取り直す。
- **セルの大きさ**：同時接続 15 万以下、Aurora の writer のピーク CPU 50% 以下を目安にする。大口のワークスペースには専用のセルを割り当てる。
- **セルごとに AWS アカウントを分ける。** クォータ、権限、障害の影響範囲をセルに閉じる。
- **デプロイはセルを順に進める**：カナリアのセル（社内と合成監視のワークスペースを置く）→ 小さなセル → 残り。1 つのセルで問題が出たら、残りのセルへ進めない。
- **ワークスペースの移動**：`workspace_id` 単位のコピー、変更の追従、短時間の書き込みの停止、対応表の切り替え、再接続と差分取得。`seq` と ID は移動しても変わらない。
- **災害復旧**：各セルが、大阪にウォームスタンバイを持つ（Aurora Global Database。RPO 1 分、RTO 1 時間）。
- **Global が止まったときのセッション**（2026-09-28 に決定）：キャッシュの切れたセッションも、セルが最後に得た検証の結果を延長して受け入れる。拒否すると、Global の停止が全員のログアウトになり、Global が単一障害点に戻るため。次の制限を付ける。
  - 延長は、Global の停止中だけ、最長 4 時間とする。超えたら拒否する。
  - 絶対タイムアウトと、ワークスペースごとの最大有効期間は、キャッシュした作成時刻で検査し続ける。
  - 再認証を要する重要な操作と、新しいログインは受け付けない。
  - 停止中の取り消しは、Global が戻ってから反映する。延長して受け入れた要求は監査ログに印を付ける。

## Consequences

- 良くなること：
  - 規模をセルの追加で伸ばせる。
  - 1 つの障害やデプロイの失敗が、1 つのセルの顧客にとどまる。
  - 大口の顧客を専用のセルに隔離できる。
- 引き受けるコスト：
  - Global という新しい部品が増え、それ自体が全体の単一障害点になりうる。ログイン済みのクライアントが Global なしで動き続けられるよう、セルでのセッションの検証結果と、対応表をキャッシュする。セッションは DB を正本とする不透明なトークンなので（[identity-and-access.md](../architecture/identity-and-access.md)）、キャッシュの切れたセッションは、Global の停止中に最長 4 時間まで延長して受け入れる（要点を参照）。その間に取り消したセッションが使われうることを受け入れる。
  - セルの数だけ、運用の対象（DB、キャッシュ、デプロイ）が増える。IaC（[ADR-0020](0020-infrastructure-as-code-with-terraform.md)）とデプロイの自動化が前提になる。
  - ワークスペースをまたぐ機能（Enterprise Grid 相当、組織間チャンネル）は、セルをまたぐ設計が必要になる。どちらも MVP の範囲外。
  - セルごとの固定費がかかり、小さなセルでは 1 接続あたりの費用が上がる。

## Confirmation

- S3 に入る前に、staging に 2 つのセルと Global を作り、次を確かめる。
  - ワークスペースの移動の訓練で、書き込みの停止が 1 分以内に収まり、移動の前後でメッセージの件数と各チャンネルの `last_seq` が一致する。
  - 1 つのセルを止めても、他のセルの合成監視が成功し続ける。
  - Global を止めても、ログイン済みのクライアントが投稿と受信を続けられる。
- 本番では、セルごとの SLO をダッシュボードで並べて見る（[observability.md](../architecture/observability.md)）。
