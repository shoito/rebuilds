# ADR-0029: レート制限を、層・主体・テナントの共通の枠組みで行う

## Context

レート制限の値が、認証・投稿・検索・MCP・WAF・Gateway の各文書に散らばっていて、次の点が決まっていなかった。

- 計数の方式
- 制限をかける単位
- 応答の形式
- Valkey の障害時の振る舞い

外部公開 API とアプリ（E12）を設計するにあたり、上限は利用者との契約の一部になる。共有スキーマのマルチテナント（ADR-0009）では、1 つのテナントが資源を占有しないことも、上限で守る必要がある。

## Options

1. **アプリで、Valkey の GCRA を使う**（主体とワークスペースの両方の軸）
2. **API Gateway（AWS）の使用量プランに任せる**
3. **各サービスのメモリの中だけで数える**

## Decision

1 を採用する。詳細は [rate-limiting.md](../architecture/rate-limiting.md) にある。

- **層を分ける。** エッジ（WAF）、接続（Gateway）、リクエスト、資源、同時実行、非同期、容量の 7 層で、それぞれの単位で制限する。
- **2 つの軸で判定する。** 主体ごとの上限と、ワークスペース全体の上限の両方を確かめる。
- **計数は GCRA を Valkey の Lua スクリプトで行う。** 1 つの対象につき 1 キー、1 往復で判定する。キーはワークスペースのハッシュタグで、S2 のクラスタでも同じシャードに置く。
- **応答をそろえる。**
  - すべての 429 に `Retry-After` を付ける。
  - 外部公開 API には、IETF の草案の `RateLimit-Policy`・`RateLimit` も付ける。草案の段階であることを利用者に明記する。
- **非同期は遅らせ、同期は断る。**
- **Valkey の障害時の振る舞いを、対象ごとに分ける。** 一般の制限は通す側に倒し、タスク内の簡易な制限で守る。認証の制限は止める側に倒す。
- **上限の値は、プランと、ワークスペース単位の上書きで決める**（[ADR-0032](0032-plans-and-entitlements.md)）。
- 2 は、ALB と WebSocket、MCP、内部 API を同じ仕組みで扱えない。テナントと主体の 2 軸の判定もできない。
- 3 は、タスクの数に応じて実際の上限がぶれ、オートスケールで緩くなる。

## Consequences

- 良くなること：
  - 上限の値と振る舞いが 1 か所で決まり、外部の利用者に説明できる。
  - 1 つのテナントやアプリの暴走が、他に波及しにくい。
- 引き受けるコスト：
  - 判定のたびに Valkey へ 1 往復する。遅延の予算に含める。
  - Valkey の障害中は、一般の制限が緩くなる。

## Confirmation

- 性質ベーステスト：許可された件数が、上限を超えない。
- 結合テスト：Valkey の停止中の振る舞い（一般は通す、認証は止める）と、応答のヘッダー。
- 各領域の文書の上限の値が、rate-limiting.md の 4 節と一致していることを、レビューで確かめる。
