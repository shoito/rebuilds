# ADR-0009: テナントは共有スキーマ（pool）で持ち、PostgreSQL の RLS で分離を強制する

ADR-0005（権限判定の集約）を拡張する。判定の起点に、テナント境界を加える。

## Context

ワークスペースが 1 つのテナントである。テナントをまたいだデータの漏洩は、最も重い障害になる（quality.md のリスク 1 位）。

一方、それまでの設計には次の問題があった。

- 多くのテーブル（`messages`、`channel_members`、`reactions` など）が、`workspace_id` をチャンネル経由の間接的な形でしか持っていない。
- 分離をアプリのクエリだけに頼っている。

## Options

1. **silo**：テナントごとに DB（またはスキーマ）を分ける
2. **pool**：共有スキーマ。分離はアプリのクエリで行う
3. **pool ＋ RLS**：共有スキーマ。全テナントテーブルに `workspace_id` を持たせ、PostgreSQL の Row Level Security で DB 側でも分離を強制する

## Decision

3 を採用する。

- 1 は、テナント数に比例して運用対象が増え、スキーマ移行も全テナントに必要になる。小規模テナントが大多数の SaaS には重い。
- 2 は、クエリ 1 つの書き忘れで漏洩する。エージェントが大量のクエリを書く前提では、レビューだけで防ぎきれない。
- 3 は、アプリのバグがあっても DB が行を返さない。多層防御になる。

### 規則

- **テナントテーブルは、すべて `workspace_id` を直接持つ。**
  - 主キーは `(workspace_id, id)` とする。
  - 外部キーも `workspace_id` を含む複合キーにし、別テナントの行を参照できないようにする。
- **RLS を全テナントテーブルで有効にする。**
  - `ENABLE ROW LEVEL SECURITY` と `FORCE ROW LEVEL SECURITY` の両方を設定する。
  - ポリシーは `workspace_id = current_setting('app.workspace_id')::uuid` を `USING` と `WITH CHECK` の両方に書く。
- **DB ロールを分ける。**

  | ロール | 使う主体 | 権限 |
  | --- | --- | --- |
  | `migrator` | マイグレーション | テーブルの所有者 |
  | `app` | API・Gateway・Worker | RLS の対象。`BYPASSRLS` を持たない |
  | `relay` | Relay | `outbox` の読み取りと削除だけを持つ |

- **テナントのコンテキストは、トランザクションの中で設定する。**
  - API はリクエストごとに、トランザクションの先頭で `SET LOCAL app.workspace_id` と `SET LOCAL app.member_id` を設定する。
  - `SET LOCAL` は、トランザクションの終了とともに消える。コネクションプール（トランザクションモード）でも、前のリクエストの値が残らない。
  - Worker はジョブごとに、ジョブが持つ `workspace_id` で同じことをする。
- **テナントをまたぐ正当な読み取りは、個別に扱う。**
  - 例：ログイン後に自分が属するワークスペースの一覧を出す。
  - この読み取りだけは、`account_id` で絞る専用のポリシー（または `SECURITY DEFINER` 関数）で許可し、テナントテーブル全体の抜け道にしない。
- **ID は UUIDv7 にする。** 連番と違って他テナントの ID を推測されにくい。時刻順に並ぶので、B-tree インデックスの局所性も保てる。PostgreSQL 18 の `uuidv7()` で生成する。
- **テナントの外に出るものにも `workspace_id` を含める。**

  | 対象 | 形 |
  | --- | --- |
  | オブジェクトストレージのキー | `ws/{workspace_id}/files/{file_id}` |
  | Redis のチャンネル名 | `ws:{workspace_id}:ch:{channel_id}` |
  | 検索インデックス | 検索クエリに `workspace_id` を必ず含める |

- **権限判定の順序（ADR-0005 の拡張）**：テナントが一致するか → チャンネルのメンバーか → その操作が許されるか。具体的な規則は、E2 で決定表として定義する。

### 将来の拡張

データベースの前段に、「どのワークスペースがどの DB にいるか」を引く対応表（ルーティング）を置ける形にしておく。規模が大きくなったら、次のどちらかへ移る。

- 複数のテナントをまとめた単位（セル）ごとに DB を分ける
- 大口のテナントだけを専用の DB に置く

どちらでも `workspace_id` の規則はそのまま使える。

## Consequences

- 良くなること：
  - テナント境界の保証が、アプリのコードだけに依存しなくなる。
  - エージェントが書いたクエリに絞り込みの漏れがあっても、漏洩しない。
- 引き受けるコスト：
  - すべての DB アクセスが、テナントのコンテキストを設定したトランザクションの中で行われる必要がある。設定を忘れると、`current_setting` がエラーになるか 0 件になる（安全側に倒れる）。
  - RLS のポリシーはクエリの条件に加わるため、インデックスの先頭を `workspace_id` にしないと遅くなる。
  - 複合キーのため、スキーマと ORM の定義が冗長になる。
  - テナントをまたぐ集計（運用のダッシュボードなど）は、専用のロールと読み取り専用のレプリカで行う必要がある。

## Confirmation

- マイグレーションの lint：テナントテーブルに `workspace_id` の列、`FORCE ROW LEVEL SECURITY`、ポリシーがなければ失敗させる。
- 性質ベーステスト（PROP-WS-001）：任意の 2 テナントと任意の操作列について、一方のコンテキストで他方の行が 1 件も読めず、書けない。
- `app` ロールが `BYPASSRLS` を持たず、テーブルの所有者でもないことを、CI で検査する。
- 本番では、テナント境界の監査を行う（quality.md）。
