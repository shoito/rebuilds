# ADR-0016: リンクのプレビューは、VPC の外で権限を持たない取得器で行う

ADR-0011（Worker は ECS Fargate で動かす）の例外として、外部の URL の取得だけを Lambda で行う。

## Context

メッセージ中の URL のプレビュー（タイトル、説明、画像）を出したい。これには、利用者が指定した任意の URL をサーバーから取得する必要があり、SSRF の典型的な入口になる。

- 社内のサービス（DB、Valkey、内部の管理画面）に届く。
- ECS のタスクは、`169.254.170.2` からタスクロールの認証情報を得られる。取得器がこれを取得して返すと、認証情報が漏れる。
- DNS の再バインドやリダイレクトで、検査をすり抜けられる。
- 取得した HTML や画像の解析そのものが、攻撃面になる。

## Options

1. API が投稿時に同期で取得する
2. VPC の中の Worker（ECS）が、アプリの検査（IP の拒否リストなど）だけで取得する
3. 専用の VPC（内部へのルートなし）に置いた ECS タスクで取得する
4. VPC に接続しない Lambda を、権限を持たないロールで動かし、取得と解析をさせる
5. 外部のプレビューサービスに URL を渡す

## Decision

4 を採用し、アプリの検査を重ねる。

- **ネットワークで隔離する。** VPC に接続しない Lambda は、VPC 内の資源に届かない。検査に漏れがあっても、DB や Valkey には到達できない。
- **盗まれる権限を持たせない。** 実行ロールには、ログの書き込み以外の権限を与えない。ECS のタスクのような認証情報のエンドポイントがない（Lambda の認証情報は環境変数で渡る。未検証：取得器のコードから到達できる HTTP の経路がないこと）。
- **呼び出しを 1 方向にする。** VPC 内の unfurl Worker（ECS）が Lambda を同期で呼び、結果を受け取って DB と S3 に書く。Lambda はキューにも DB にも触れない。
- **解析も隔離の中で行う。** HTML からは、タイトル・説明・サイト名だけを取り出し、長さを切り詰めて返す。画像は Lambda の中で WebP に再エンコードしてから返す。
- 1 は投稿 API を外部サイトの遅延に巻き込む（NFR-003）。2 は、検査の漏れがそのまま内部への到達になる。3 は 4 と同じ隔離を得られるが、VPC と NAT を別に持つ費用と運用がかかる。5 は、秘密を含みうる URL を第三者に渡す。

### アプリの検査（多層防御）

| 対象 | 規則 |
| --- | --- |
| スキーム・ポート | `http` / `https`、80 / 443 だけ。URL 中の認証情報（`user:pass@`）は拒否 |
| 宛先の IP | 名前解決したすべてのアドレスを検査する。ループバック、プライベート（RFC 1918）、リンクローカル（`169.254.0.0/16`）、CGNAT（`100.64.0.0/10`）、`0.0.0.0/8`、マルチキャスト、予約済み、IPv6 の `::1`・`fc00::/7`・`fe80::/10`・IPv4 射影（`::ffff:0:0/96`）・NAT64（`64:ff9b::/96`）を拒否する |
| DNS の再バインド | 検査したアドレスに直接接続する（名前を引き直さない）。TLS の SNI と `Host` は元の名前にする |
| リダイレクト | 自動で追わない。最大 3 回まで、毎回スキームと IP を検査し直す |
| 自分たちのドメイン | アプリ・API・ファイル配信のドメインは取得しない |
| 時間 | 接続 2 秒、全体 5 秒 |
| 大きさ | HTML は先頭 512 KB だけ読む。画像は 5 MB まで。展開後の大きさにも上限を設ける |
| 種類 | HTML（`text/html`）と画像だけ。それ以外は失敗として扱う |
| 要求 | Cookie・認証ヘッダーを送らない。専用の User-Agent を名乗る |
| 出力 | Zod で検証する。テキストから HTML を除く。画像は再エンコード済みのものだけ |

### 濫用の抑制

- Lambda の予約済み同時実行数で、全体の取得の速度に上限を設ける。
- 取得先のホストごとに、Worker 側で速度を絞る（Valkey で数える）。
- 結果はワークスペースごとに 24 時間キャッシュし、同じ URL を何度も取得しない。キャッシュはワークスペースをまたがない（ADR-0009）。

詳細は [messaging.md](../architecture/messaging.md) の「リンクのプレビュー」。

## Consequences

- 良くなること：
  - 検査の漏れが、内部への到達や認証情報の漏洩に直結しない。
  - 外部サイトの遅延や失敗が、投稿 API に影響しない。
  - 閲覧者の IP を外部サイトに渡さない（画像を置き直して配るため）。
- 引き受けるコスト：
  - 実行基盤が ECS と Lambda の 2 種類になる。デプロイ・監視・IaC の対象が増える。
  - Lambda の送信元 IP は固定されない。取得先のサイトに許可リストを案内できず、拒否されることがある。
  - プライベートチャンネルに貼った URL も、外部サイトから見れば取得される。ワークスペースの設定で、プレビューを無効にできるようにする。
  - プレビューは投稿の数秒後に出る。

## Confirmation

- SSRF のテスト：拒否すべきアドレス（`127.0.0.1`、`169.254.169.254`、`169.254.170.2`、`10.0.0.1`、`[::1]`、`[::ffff:127.0.0.1]`、10 進表記の IP など）、内部を指すリダイレクト、DNS の再バインドのそれぞれで、取得されないこと。
- IaC の検査：取得器の Lambda に VPC の設定がなく、実行ロールの権限がログの書き込みだけである。
- unfurl Worker 以外に、取得器を呼ぶ権限（`lambda:InvokeFunction`）がない。
