# Runbook: デプロイとロールバック

- Owner: Ops
- 対応するアラート: デプロイ中の自動ロールバック（api の blue/green のアラーム）、デプロイ後の SLO のバーンレート
- 最終確認日: 2026-09-26

方針は [ADR-0022](../decisions/0022-zero-downtime-deploy-and-migrations.md)、CI/CD の構成は [infrastructure.md](../architecture/infrastructure.md) の 6 節、ブランチからリリースまでの流れは [delivery.md](../architecture/delivery.md) にある。機能の段階的なリリースとフラグでのロールバックは [README.md](README.md) の 3 節に従う。

## 症状

次のときに使う。

- 本番へデプロイするとき（通常の手順）
- デプロイの後に、エラー率・遅延・欠損検知率が悪化したとき

## 影響

- 通常のデプロイ：ユーザーへの影響はない。Gateway の入れ替え中は、接続が順に再接続する（数秒の再接続が見える場合がある）。
- 失敗したデプロイ：投稿 API の成功率と、送信 → 表示の遅延の SLO を消費する。

## 確認

### デプロイの前

1. GitHub Actions で、対象のコミットが dev と staging へデプロイ済みで、staging の E2E とスモークテストが通っている。
2. staging へのデプロイ中に、k6 の投稿・受信が失敗 0 件だった（ADR-0022 の Confirmation）。
3. リリースに含まれるマイグレーションを確認する。
   - expand だけか。contract（削除）を含むなら、次を確かめる。
     - 古い列・テーブルを参照するアプリが、本番に残っていない（1 つ前のリリースで参照をやめている）。
     - Aurora の PITR が有効で、直近の復元可能な時刻が 5 分以内である。
   - RLS のポリシーを変えるなら、PROP-WS-001 が新旧のアプリの両方で通っている。
4. Grafana の SLO ダッシュボードで、エラーバジェットが残っている。バジェットを使い切っているときは、修正のデプロイ以外は行わない（README.md の 1 節）。
5. 進行中のインシデントがない。

### デプロイの後（各サービスの入れ替えが終わってから 15 分）

| 見るもの | 正常 | 異常 |
| --- | --- | --- |
| 投稿 API の 5xx の割合 | デプロイ前と同じ | 0.1% を超える |
| 送信 → 表示の遅延 p99 | 500ms 以内 | 500ms を超える |
| クライアントの欠損検知率 | 1% 未満（Gateway の入れ替え中は一時的に上がってよい） | 入れ替えが終わっても 1% 以上 |
| 合成監視 | 成功 | 2 回続けて失敗 |
| relay の outbox の未処理件数 | 増え続けない | 増え続ける |

## 対処

### 通常のデプロイ

1. GitHub の `prod` の Environment で、Ops がデプロイを承認する。承認する人は、そのリリースの作成者と別の人にする。
2. マイグレーションのタスクが成功したことを確かめる。失敗したら、アプリのデプロイは自動で止まる。マイグレーションは `lock_timeout` で失敗しているだけのことが多いので、原因を見てから再実行する。
3. api：blue/green のカナリア（10%）で、アラームが鳴らなければ 100% に切り替わる。
4. workers、relay：ローリングで入れ替わる。
5. gateway：ローリングで 10% ずつ入れ替わる。Grafana で、再接続の速さと差分取得の API の負荷が上限の内にあることを見る。上限に近づいたら、Terraform の変数で 1 回に入れ替える割合を下げる。
6. 「デプロイの後」の表を 15 分見て、異常がなければ終わる。

### 悪化したとき

1. **フラグで戻す。** 新しい機能のフラグが原因なら、AppConfig でフラグを切る。デプロイより速く、確実である。
2. **フラグで戻せないとき、アプリを戻す。** 1 つ前のイメージの digest で再デプロイする（GitHub Actions の「前のリリースを再デプロイ」のワークフロー）。api は blue/green なので、切り替えの直後なら ECS が自動でロールバックしている場合がある。
3. **マイグレーションは戻さない。** expand のマイグレーションは古いアプリでも動くので、アプリだけを戻す。スキーマに問題があれば、前へ進める修正のマイグレーションを書く。
4. **contract のマイグレーションでデータを失ったとき**は、[disaster-recovery.md](disaster-recovery.md) の「PITR での復元」に進み、インシデントとして扱う（[incident-response.md](incident-response.md)）。
5. 戻しても直らなければ、インシデントを宣言する。

## エスカレーション

- 戻しても 15 分以内に SLO が回復しない → インシデントを宣言し、[incident-response.md](incident-response.md) に従う。
- RLS のポリシーの変更の後に、テナント境界の監査で不一致が出た → SEV1 として扱う。
- マイグレーションが途中で止まり、状態がわからない → Dev（テックリード）を呼ぶ。

## 事後

- 調査結果を Intent の Issue として起票する（Maintain 段。[project-management.md](../../../../docs/project-management.md)）。
- この手順で足りなかったことを、ここに反映する。
- デプロイの失敗の原因が CI で防げたなら、CI の検査（マイグレーションの lint、E2E）を足す提案を Dev と QA に出す。
