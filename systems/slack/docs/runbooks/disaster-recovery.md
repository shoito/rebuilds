# Runbook: 災害復旧（AZ の障害、リージョンの障害、復元訓練）

- Owner: Ops
- 対応するアラート: AZ の障害（複数のサービスで 1 つの AZ のターゲットが不健全）、合成監視の連続失敗（大阪から東京が見えない）、訓練（四半期に 1 回）
- 最終確認日: 2026-09-26

構成と目標は [infrastructure.md](../architecture/infrastructure.md) の 5 節にある。目標は NFR-007（AZ：RPO 0、RTO 5 分）と NFR-008（リージョン：S1 で RPO 15 分、RTO 4 時間）。

## 症状

| 場面 | 見え方 |
| --- | --- |
| A. AZ の障害 | 1 つの AZ のタスク・Aurora のインスタンス・Valkey のノードが不健全になる。AWS Health Dashboard に、東京の 1 つの AZ のイベントが出る |
| B. リージョンの障害 | 東京の複数のサービスが同時に応答しない。大阪からの合成監視がすべて失敗する。AWS Health Dashboard に、東京のリージョン全体のイベントが出る |
| C. データの論理的な破損 | 誤ったマイグレーションや操作で、データが消えた・壊れた |
| D. 復元訓練 | 定期作業（四半期に 1 回） |

## 影響

- A：数分の間、投稿の失敗と再接続が起きうる。コミット済みのデータは失わない。投稿 API の成功率と遅延の SLO を消費する。
- B：切り替えまでの間（最大 4 時間）、全面的に使えない。最大 15 分ぶんの投稿を失いうる。通知の一部と、検索への反映が欠けうる。
- C：影響はデータの範囲による。復元の時点より後の書き込みを失いうる。

## 確認

1. AWS Health Dashboard と、Grafana の AZ ごとの内訳（ターゲットの健全性、エラー率）で、影響が 1 つの AZ か、リージョン全体かを見分ける。
2. Aurora：クラスタのイベントで、フェイルオーバーの有無と、現在の writer の AZ を確かめる。
3. Valkey：プライマリの切り替えの有無を確かめる。
4. リージョンの障害を疑うときは、大阪の合成監視と、外部からの到達性（別の回線から）の両方で確かめる。東京のコンソールや API が使えないこともある。

## 対処

### A. AZ の障害

基本は自動で回復する。人は確認と、回復が遅いときの補助をする。

1. インシデントを宣言する（SEV2 から始める。[incident-response.md](incident-response.md)）。
2. Aurora が別の AZ に自動でフェイルオーバーしたことを確かめる。5 分たっても writer がなければ、手動でフェイルオーバーする。
3. ECS が残る 2 AZ でタスクを起動しているか確かめる。容量が足りなければ、各サービスの最小タスク数を一時的に上げる。
4. 障害の AZ のサブネットに、タスクが起動を繰り返していれば、そのサービスの配置から外す。
5. Gateway への再接続の嵐を見る。差分取得の API が詰まっていれば、api のタスクを増やす。
6. AZ が回復したら、配置を元に戻し、台数を平常に戻す。Aurora の writer の AZ は、元に戻さなくてよい。

### B. リージョンの障害（東京 → 大阪）

**切り替えの判断は、インシデントの指揮者（IC）が行い、Ops の責任者が承認する。** 切り替えにはデータの損失（最大 15 分）と、戻すための作業が伴う。AWS の見込みで 1 時間以内に回復しそうなら、待つことも選ぶ。

1. インシデントを SEV1 で宣言し、利用者へ告知する（[incident-response.md](incident-response.md)）。
2. 東京に書き込みが届いているなら、止める（メンテナンスのフラグで、API を読み取り専用にする）。
3. **DB を切り替える。** Aurora Global Database の大阪の二次クラスタを昇格させる。
   - 東京の writer が生きていれば、計画的な切り替え（switchover）を使う（RPO 0）。
   - 東京が応答しなければ、計画外のフェイルオーバーを使う。昇格の直前に、二次クラスタの複製の遅延を記録する（失ったデータの範囲の目安になる）。
4. 大阪の二次クラスタに、writer と reader のインスタンスを作る（S1 では headless のため）。
5. **アプリの基盤を作る。** GitHub Actions の「DR：大阪にデプロイ」のワークフローで、Terraform の `prod/ap-northeast-3/compute` を apply し、ECS、ALB、Valkey、SQS を大阪に作る。状態ファイルは大阪のバケットにあるので、東京が使えなくても実行できる（ADR-0020）。イメージは、大阪にレプリケーション済みの ECR から取る。
6. CloudFront のオリジンを、大阪の ALB に切り替える（`global/edge` の変数 `active_region` を大阪にして apply する）。
7. 大阪の合成監視と、社内のワークスペースで、投稿・受信・検索を確かめる。
8. 読み取り専用を解除し、段階的に全体へ開く。
9. 検索インデックスの差分の再構築を、切り替えの時点の 1 時間前からやり直す。
10. 失ったデータの範囲（切り替えの時点の複製の遅延）を記録し、影響を受けたワークスペースを特定する。

**東京へ戻す（フェイルバック）：** 東京が回復してから、別の計画作業として行う。東京に Global Database の二次クラスタを作り直し、計画的な切り替え（RPO 0）で戻す。急がない。

### C. データの論理的な破損（PITR での復元）

1. 被害を止める：原因の機能のフラグを切る、原因のジョブを止める。
2. 破損の直前の時刻を、ログと監査ログから特定する。
3. Aurora の PITR で、その時刻の新しいクラスタを、prod のアカウントの中の隔離した VPC に復元する。本番のクラスタは上書きしない。
4. 復元したクラスタから、失われた行だけを取り出して本番に戻す。範囲が広く、行単位で戻せない場合は、本番のクラスタを復元したクラスタへ切り替えることを検討する（それ以降の書き込みを失うので、PM と Ops の責任者の承認が要る）。
5. 戻した行について、outbox へのイベントを積み直し、クライアントへ反映させる。
6. 復元したクラスタを消す。

### D. 復元訓練（四半期に 1 回）

本番のデータを使うので、すべて prod のアカウントの中で行う（[infrastructure.md](../architecture/infrastructure.md) の 7 節）。

1. Aurora の PITR で、任意の時刻（例：24 時間前）を隔離した VPC に復元する。かかった時間を記録する。
2. 大阪にコピーしたスナップショットから、大阪にも復元する。かかった時間を記録する。
3. 両方について、次を確かめる。
   - 行数が、本番の同じ時刻の値（メトリクス）と大きく違わない
   - 抜き出したチャンネルで、`seq` に欠番がない
   - `app` ロールで接続し、RLS が有効で、コンテキストなしでは行が読めない
4. 年に 1 回は、B の手順を staging で最後まで行い（大阪へ切り替え、東京へ戻す）、RTO を計測する。
5. 復元したクラスタを消す。結果（時間、問題点）をこの runbook の末尾の記録に残す。

## エスカレーション

- A で 5 分たっても DB の writer がない、またはエラー率が下がらない → SEV1 に上げ、Dev（テックリード）を呼ぶ。
- B の判断 → Ops の責任者。利用者への告知の文面は PM と合意する。
- データの喪失が確定した → PM に報告し、影響を受けた顧客への連絡を決める。個人情報に関わるなら [security.md](../architecture/security.md) の手順に従う。
- AWS 側の障害が原因 → AWS サポートにケースを開く。
