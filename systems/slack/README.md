# Slack を AI で再構築する

> 一行要約：ワークスペース単位で閉じた「チャンネル型メッセージング」を、順序保証付きのイベントストリームとして作り直す。

## 1. 本質

1. **速い会話** — 送ったメッセージが、相手の画面に 1 秒以内に、正しい順序で出る。
2. **取りこぼさない** — 未読・メンション・スレッドにより、どこで何が起きたかを後から確実に追える。
3. **積み上がる知識** — 過去のやり取りが検索でき、チームの記録として残る。

絵文字や連携機能の多さは価値を増幅するものであって、本質ではない。MVP では上の 3 つだけを確実に作る。

## 2. スコープ

### MVP に含める

- ワークスペース、メンバー、招待（メールリンク）
- パブリック / プライベートチャンネル、DM（1:1 と少人数グループ）
- メッセージの投稿・編集・削除、スレッド返信、リアクション、@メンション
- 既読位置と未読数、メンション数のバッジ
- ファイル添付（画像プレビューまで）
- 全文検索（日本語対応）
- Web クライアント

### 含めない（理由付き）

| 機能 | 理由 |
| --- | --- |
| 音声・ビデオ通話（Huddle） | WebRTC / SFU は別の製品と言えるほど大きい。後から別の題材として扱う |
| Slack Connect（組織間チャンネル） | テナント境界をまたぐ権限モデルが必要になり、MVP の単純さを壊す |
| アプリ / Bot プラットフォーム | 外部公開 API の互換性を維持する負担が大きい。内部イベントが安定してから公開する |
| Enterprise Grid（複数ワークスペースの束ね） | 需要が大企業に限られる。データモデル上の拡張余地だけ残す |
| モバイルネイティブアプリ | Web（PWA）で代替。API とイベント仕様を先に固める |

## 3. 要件

### 機能要件

- メッセージはチャンネル内で **全メンバーが同じ順序** で見る。
- クライアントが切断・再接続しても、欠けたメッセージを自動で補完する。
- 同じメッセージの二重送信（再送・ボタン連打）で重複投稿しない。
- 編集・削除・リアクションも、接続中の全クライアントにリアルタイムで反映する。
- 権限のないチャンネルの内容は、検索・通知・API のどこからも見えない。

### 非機能要件

| 項目 | 目標 |
| --- | --- |
| 規模（MVP 想定） | 1 ワークスペース最大 5,000 人、全体で同時接続 5 万 |
| 送信 → 他者の画面に表示 | p99 500ms 以内（同一リージョン） |
| メッセージ投稿 API | p99 200ms 以内 |
| 可用性 | 月間 99.9% |
| 耐久性 | 投稿 API が成功を返したメッセージは失わない |
| 検索への反映 | 投稿から 10 秒以内 |

## 4. アーキテクチャ

```
                ┌──────────────┐
  Browser ──────┤  CDN / LB    │
   │  ▲         └──────┬───────┘
   │  │ WebSocket      │ HTTPS
   │  │                ▼
   │  │         ┌──────────────┐   write (tx: message + outbox)   ┌────────────┐
   │  │         │  API server  │ ───────────────────────────────▶ │ PostgreSQL │
   │  │         └──────────────┘                                   └─────┬──────┘
   │  │                                                                  │ outbox
   │  │         ┌──────────────┐   subscribe ch:{id}  ┌───────────┐     ▼
   │  └─────────┤   Gateway    │ ◀─────────────────── │   Redis   │ ◀── Relay
   │            │ (WS 常時接続)│                       │  Pub/Sub  │     │
   │            └──────────────┘                       └───────────┘     │
   │                                                                     ▼
   │ upload (presigned URL)                             ┌──────────────────────┐
   └──────────────────────────▶ Object Storage (S3)     │ Workers              │
                                                        │  - search indexer    │
                                                        │  - notification      │
                                                        │  - thumbnail         │
                                                        └──────────────────────┘
```

| コンポーネント | 責務 |
| --- | --- |
| API server | 認証・認可、書き込みのすべて、履歴取得。**状態を持たない** |
| Gateway | WebSocket 接続の保持、購読管理、イベントのファンアウト。書き込みはしない |
| Relay | outbox テーブルを順に読み、Redis と各 Worker 向けキューに流す |
| Workers | 検索インデックス更新、通知（メール / Web Push）、サムネイル生成 |
| PostgreSQL | 唯一の正本（source of truth） |
| Redis | リアルタイム配信用のバス。**失われてもよい**（クライアントが差分取得で回復する） |

ポイントは **書き込み経路（API → DB）と配信経路（Relay → Gateway）を分ける** こと。配信が落ちてもデータは失われず、クライアントは再接続時の差分取得で追いつく。

## 5. データモデル

```sql
workspaces      (id, name, created_at)
users           (id, email, name, created_at)
memberships     (workspace_id, user_id, role)                 -- owner / admin / member / guest

channels        (id, workspace_id, kind, name, is_private,    -- kind: channel / dm / group_dm
                 last_seq, created_at)
channel_members (channel_id, user_id, last_read_seq, notify_level, joined_at)

messages        (id, channel_id, seq, user_id,
                 thread_root_id NULL,                         -- スレッド返信なら親メッセージ
                 body, body_format,
                 client_msg_id,                               -- 冪等キー
                 reply_count, last_reply_at,                  -- スレッド親に非正規化
                 edited_at, deleted_at, created_at,
                 UNIQUE (channel_id, seq),
                 UNIQUE (channel_id, user_id, client_msg_id))

reactions       (message_id, user_id, emoji, created_at, PRIMARY KEY (message_id, user_id, emoji))
mentions        (message_id, user_id, channel_id, created_at) -- メンション一覧・バッジ用
files           (id, workspace_id, uploader_id, storage_key, mime, size, created_at)
message_files   (message_id, file_id)

outbox          (id BIGSERIAL, channel_id, event_type, payload JSONB, created_at)
```

- **`seq`（チャンネル内の連番）が設計の中心。** 表示順、欠損検知、既読位置、差分取得のすべてを `seq` で表す。
- `channels.last_seq` を `UPDATE ... SET last_seq = last_seq + 1 RETURNING last_seq` で採番し、メッセージの INSERT と同じトランザクションで行う。チャンネル単位の行ロックになるが、1 チャンネルへの投稿頻度は低いので問題にならない。
- 編集・削除・リアクションも `seq` を消費するイベントとして outbox に積む。メッセージ本体の `seq` は変わらない。
- 全テーブルに `workspace_id` を直接または間接に持たせ、将来はワークスペース単位でシャードできるようにする。

## 6. 主要フロー

### 6.1 投稿

1. クライアントが `client_msg_id`（UUID）を生成し、画面に「送信中」で仮表示する。
2. `POST /channels/{id}/messages` を送る。
3. API は 1 トランザクションで次を行う。
   - メンバーであることを確認する
   - `last_seq` を採番する
   - `messages` に INSERT する（`client_msg_id` の一意制約に当たったら、既存の行を返す）
   - `mentions` と `outbox` に INSERT する
4. コミット後、`seq` 付きのメッセージを返す。クライアントは仮表示を確定させる。
5. Relay が outbox を読み、Redis の `ch:{channel_id}` に publish する。
6. 購読中の Gateway が、接続中のメンバーへ WebSocket で push する。

### 6.2 再接続と差分取得

1. クライアントはチャンネルごとに「最後に受け取った `seq`」を保持する。
2. WebSocket で受け取ったイベントの `seq` が `last + 1` でなければ、欠損とみなす。
3. 再接続時・欠損検知時は `GET /channels/{id}/events?after_seq=N` で差分を取得し、`seq` 順に適用する。
4. 差分が多すぎる場合（例：1,000 件超）は差分を諦め、最新ページを取り直す。

これにより **Redis や Gateway の配信を「ベストエフォート」にしても正しさが保たれる**。

### 6.3 既読と未読数

- 未読数 = `channels.last_seq - channel_members.last_read_seq` を基本とし、自分の投稿やスレッド返信など数えないものは近似として許容する（正確な数よりもバッジの有無が重要なため）。
- 既読更新は `POST /channels/{id}/read {seq}` で行い、`GREATEST(last_read_seq, :seq)` で後退しないようにする。
- 既読イベントは同じユーザーの他端末にだけ配信する。

## 7. 設計判断

| 論点 | 採用 | 捨てた選択肢 | 理由 |
| --- | --- | --- | --- |
| 順序付け | チャンネル内連番 `seq` | タイムスタンプ、Snowflake ID | 欠損検知と差分取得が単純な整数比較になる |
| 配信の信頼性 | DB が正本、配信はベストエフォート＋差分取得 | Kafka 等による exactly-once 配信 | 配信系を単純に保てる。正しさの責任を 1 か所に集める |
| DB → 配信の連携 | Transactional outbox | API から直接 publish | コミットと publish のずれによる幽霊メッセージや取りこぼしを防ぐ |
| Pub/Sub | Redis Pub/Sub | NATS、Kafka | MVP 規模で十分。消えてもよい用途なので永続化は不要 |
| 検索 | PostgreSQL＋pg_bigm で始め、規模に応じて OpenSearch へ | 最初から OpenSearch | 運用コンポーネントを減らす。インデクサーを Worker に分けておけば移行できる |
| 権限の適用 | 検索・通知・配信のすべてで `channel_members` を参照 | 各所で個別に実装 | 情報漏洩はいちばん重い障害。判定関数を 1 つにしてテストを集中させる |
| 本文フォーマット | 独自の軽量 AST（JSON） | HTML、Markdown 文字列 | メンション・リンク・絵文字を構造として扱える。XSS の面が小さい |

## 8. 技術スタック

| 層 | 選定 | AI エージェント視点での理由 |
| --- | --- | --- |
| 言語 | TypeScript（フロント・バック共通） | 型を API 契約として共有でき、エージェントが境界をまたいでも整合を保ちやすい |
| API | Hono＋Zod | スキーマから型と OpenAPI を生成できる。仕様と実装のずれを機械的に検出できる |
| Gateway | Node.js＋`ws` | 同じ言語・同じイベント型を使える |
| DB | PostgreSQL 17＋Drizzle | SQL に近く、生成されるクエリが読みやすい。マイグレーションをレビューしやすい |
| Web | React＋TanStack Query＋Vite | 学習データが多く、エージェントの出力品質が安定する |
| テスト | Vitest、Testcontainers、Playwright | 実 DB・実ブラウザで検証でき、モックで誤魔化せない |
| ローカル環境 | Docker Compose（Postgres、Redis、MinIO） | エージェントが 1 コマンドで起動・破棄できる |

## 9. AI による構築プラン

### 進め方の原則

- **契約を先に固定する。** OpenAPI とイベントスキーマ（`packages/contract`）は人間がレビューして確定し、以降のフェーズではエージェントが勝手に変えられないようにする（CI で差分を検知する）。
- **検証手段を先に作る。** 各フェーズで、実装より前に「通れば完了」と言えるテストを用意する。エージェントには「このテストを通せ」という形で渡す。
- **1 タスク 1 PR、差分は小さく。** 並列に動かすエージェント同士が同じファイルを触らないよう、パッケージ境界でタスクを切る。
- **リポジトリに `AGENTS.md` を置く。** コマンド（`pnpm test`、`pnpm db:reset`）、ディレクトリの責務、禁止事項（契約の変更、テストの削除・skip）を明記する。

### フェーズ

| フェーズ | 成果物 | エージェントへの渡し方 | 完了条件（検証） | 人間の判断点 |
| --- | --- | --- | --- | --- |
| 0. 契約 | データモデル、OpenAPI、WS イベントスキーマ、`AGENTS.md` | 本ドキュメントを入力に草案を作らせる | スキーマから型生成が通る | **契約の確定**（ここがいちばん重要） |
| 1. ドメインと API | 投稿・編集・スレッド・既読・権限の API | エンドポイント単位でタスク化し、並列で実装 | Testcontainers 上の結合テスト。権限テーブル駆動テストが全件通る | 権限判定のロジックを読む |
| 2. リアルタイム | Relay、Gateway、差分取得 | 「6.2 のシナリオを満たせ」と渡す | 性質テスト：ランダムな切断・遅延・重複のもとで、全クライアントの最終状態が DB と一致する | 障害注入のシナリオが十分か |
| 3. Web クライアント | チャンネル一覧、タイムライン、スレッド、入力欄 | 画面単位でタスク化。デザインはワイヤーを渡す | Playwright で 2 ブラウザを使ったシナリオテスト | 触って体験を確認する（自動化できない） |
| 4. 周辺機能 | 検索、ファイル、通知 | Worker 単位で並列に実装 | 検索結果に権限外のメッセージが混ざらないテスト。日本語の検索ケース | 通知の頻度・既定値 |
| 5. 負荷と運用 | k6 シナリオ、ダッシュボード、Runbook | 非機能要件の表を渡す | 同時接続 5 万、送信 → 表示 p99 500ms | ボトルネック対策の優先順位 |

### エージェントに任せない・任せにくいところ

- **契約（API・イベント・スキーマ）の確定** — 後から変えるコストがいちばん高い。
- **権限モデルの最終確認** — テストが通っていても、テストケースの漏れはエージェント自身では気づきにくい。
- **体験の良し悪し** — スクロール位置の保持、未読線の位置、入力中のラグなど、触らないとわからない品質。
- **負荷試験結果の解釈** — 数字は出せるが、どこに投資するかはプロダクト判断。

## 10. AI 時代に作り直すなら変えること

- **「未読を全部読む」をやめる。** 未読が溜まったチャンネルは、要約と「あなたに関係あるもの」の抽出を既定の表示にする。`seq` 範囲を指定して要約できるよう、差分取得 API をそのまま流用する。
- **スレッドを後から整理する。** 流れてしまった議論を、AI が決定事項・未解決事項・担当者に構造化して、チャンネルに固定する。
- **検索を質問応答にする。** 全文検索のインデックスに加えてベクトルインデックスを持つ。ただし権限フィルタは必ず検索の前段で適用する（後段で除外すると漏れる）。
- **エージェントを第一級のメンバーにする。** Bot を特殊扱いせず `users` の一種として扱い、人間と同じ権限モデル・同じイベントストリームに載せる。

## 11. リスクと未解決事項

- **巨大チャンネル（数千人）のファンアウト** — 1 投稿あたり数千件の push になる。Gateway 側で購読をチャンネル単位にまとめ、Redis からの受信は Gateway 1 台につき 1 回にする設計で足りるかは、負荷試験で確認する。
- **`last_seq` 採番のホットスポット** — 全社アナウンスのように書き込みが集中するチャンネルでは、行ロックの待ちが発生しうる。現実的には書き込み頻度が低いため問題になりにくいと見込むが、計測する。
- **未読数の正確さ** — 近似で許容したが、「未読 3 件と出ているのに見当たらない」はユーザーの不信を招く。どこまで正確にするかは要検討。
- **データ保持と削除** — 保持期間ポリシーや法的保全（リーガルホールド）は MVP に含めていないが、企業利用では早い段階で要求される。
