# Intent: Workday を AI エージェント主体で再構築する

- Author: shoito
- Status: accepted
- Date: 2026-09-28

## Problem

日本の企業の人事・給与の業務は、多くのシステムと表計算に分かれている。

- 人事の記録（所属、役職、等級、給与）が「今の値」だけで持たれ、いつ何が変わったかを後から正しく追えない。4 月 1 日付の異動を 3 月に入力する、過去の入社日を直す、といった操作で履歴が壊れる。
- 異動・昇給・退職の申請と承認が、メールや紙で回る。誰がいつ承認したかが残らない。
- 給与計算は、法令と料率の変更が毎年ある。源泉徴収税額表（令和 8 年分は基礎控除の見直しで改正）、健康保険と介護保険の料率（令和 8 年度は 3 月分から）、子ども・子育て支援金（令和 8 年 4 月分から）、雇用保険の料率（4 月から）が、別々の時期に変わる。反映の漏れと端数の処理の誤りが、そのまま従業員への支払いの誤りになる。
- 勤怠は、36 協定の上限（月 45 時間・年 360 時間、特別条項でも単月 100 時間未満など）を超えそうなことに、月末まで気づけない。
- マイナンバーが、給与のシステムや表計算に平文で混ざり、誰が見たかを追えない。

本家 Workday は、人事の全データを有効日付つきのオブジェクトとして持ち、すべての変更を業務プロセスで承認し、同じ権限の仕組みで画面・レポート・連携を守る。1 つのコードラインを全顧客が使う。その考え方を借りつつ、日本の給与計算と労務の規則を中心に、小さなチームと AI エージェントでどこまで作り直せるかを確かめる。

## Proposed outcome

人事・給与の担当者が、組織と従業員の記録を有効日付つきで持ち、承認を経て変え、そこから日本の法令に沿った給与を毎月誤りなく計算して支払えるシステムを作り直す。次の 3 つの価値を満たす。

1. **履歴を失わない**：すべての人事のデータに、いつから有効か（有効日）と、いつそう記録したか（記録日時）を持つ。将来日付の変更、過去の訂正、取消を区別し、任意の時点の状態を再現できる。
2. **給与を誤らない**：給与計算は、入力と規則表の版から決まる純粋な計算にする。ゴールデンデータセットで誤り 0 件、現行のシステムとの並行稼働で差異がすべて説明できることを、本番の切り替えの条件にする。
3. **権限と個人情報を守る**：ドメインとロールの権限、職務分掌、マイナンバーの隔離を、画面・API・レポート・一括の出力のすべてに同じく効かせる。

### MVP に含める

- **Core HR**
  - 従業員（worker）、ポジション、職務、組織の階層（監督組織、会社、コストセンター、事業所）
  - 入社、異動、昇格・降格、所属の変更、休職・復職、退職
  - すべて有効日付つき。完全な履歴、将来日付の変更、訂正、取消、任意の時点の問い合わせ
- **業務プロセス**
  - 起票、承認、差し戻し、却下、ルーティングの規則（上長、人事の担当、組織の階層、条件）、代理（委任）、期限と督促、取消（rescind）と訂正（correct）
  - テナントが定義を変えられる。定義は版を持ち、進行中の案件は起票時の版で進む
- **従業員とマネージャーのセルフサービス**
  - 従業員：自分の情報の確認と変更の申請（住所、通勤経路、扶養、振込先の口座）、打刻、休暇の申請、給与明細の閲覧
  - マネージャー：部下の一覧、承認の受信箱、部下の勤怠と残業の状況、異動・昇給の起票
- **勤怠**
  - 打刻（Web、モバイル Web、打刻機からの取り込み）、勤務体系（固定、シフト、フレックス、変形労働時間制の 1 か月単位）、労働時間の計算（法定内・法定外の残業、深夜、休日、月 60 時間超）
  - 36 協定の設定と、上限に近づいたときと超えたときの警告（本人、上長、人事）
  - 月次の締め（上長の確認、人事の確定）と、給与計算への連携
- **休暇**
  - 年次有給休暇の付与（継続勤務 6 か月・出勤率 8 割の要件、勤続年数による日数、所定労働日数による比例付与）、繰越と 2 年の時効、年 5 日の取得義務の管理、年次有給休暇管理簿
  - 特別休暇（会社が定義）、半日・時間単位の休暇、休職
- **日本の給与計算**
  - 月次の給与と賞与
  - 支給項目（基本給、手当、残業代などの割増賃金）と控除項目（テナントが定義できる。法定の計算はシステムが持つ）
  - 源泉所得税（月額表の甲欄・乙欄、賞与の算出率の表、電子計算機等による計算の特例）
  - 社会保険料（健康保険、介護保険、厚生年金保険、子ども・子育て支援金）と雇用保険料
  - 住民税の特別徴収（6 月から翌年 5 月の月割り）
  - 日割り、欠勤控除、遡及の差額、随時改定の候補の検知
- **給与明細**：Web での閲覧と PDF。電子交付の同意の記録
- **振込ファイル**：全銀協の規定形式（給与・賞与振込）のファイル
- **会計の仕訳の出力**：給与計算の結果から、勘定科目の対応表で仕訳を作り、会計システム向けに出力する
- **権限**：ドメイン（機能の領域）とロールによる権限、業務プロセスごとの権限、組織で絞る権限、職務分掌の規則、権限の変更の承認
- **マイナンバーの保管庫**：収集、本人確認の記録、利用の目的の制限、アクセスの記録、保存期間の後の削除
- **監査**：すべての変更の記録（誰が、いつ、何を、前後の値）、権限の変更、マイナンバーへのアクセス、改ざんの検知、保存期間の管理
- **レポート**：人員の一覧、組織図、異動の履歴、残業の集計、休暇の取得状況、給与の集計、賃金台帳。任意の時点で出せる
- **連携**：一括の取り込み・出力（表計算の雛形でデータを入れ、同じ検証と業務プロセスを通す。本家の EIB に相当）、現行のシステムからの移行、API

### 守るべき振る舞い

- 有効日付つきのデータで、同じ従業員の同じ項目の有効期間は重ならない。
- 訂正・取消をしても、過去の記録（「その時点でシステムが何を知っていたか」）は消えない。任意の有効日と記録日時の組で、当時の状態を再現できる。
- 業務プロセスを経ずに、人事のデータは変わらない。同じ人が、同じ案件で起票と承認をしない。
- 確定した給与の結果は書き換わらない。同じ入力・同じ規則表の版・同じエンジンの版で再計算すると、1 円も違わない結果になる。
- 給与の仕訳は、給与の計算ごとに借方と貸方が一致する。
- マイナンバーの平文は、保管庫の外に出ない。例外は、法令で決まった書類に書くときだけで、そのときも保管庫の中で書類を作る。アクセスはすべて記録される。
- テナントは、他のテナントの従業員・給与・設定を一切見られない。

### 成功の基準

| # | 基準 | 目標 | 測り方 |
| --- | --- | --- | --- |
| K1 | 給与計算の正しさ | ゴールデンデータセットで計算誤り 0 件（NFR-001） | CI で全件を比べる。期待値は社労士・税理士が確かめたもの |
| K2 | 並行稼働 | 本番の切り替えの前に、現行のシステムと 3 か月（うち賞与の月を 1 回以上）並行して計算し、差異がすべて説明済み | 従業員 × 項目ごとの差異の報告。説明のない差異が 0 件 |
| K3 | 有効日付の一貫性 | 性質ベーステストと本番の検査で、期間の重なり・時点の問い合わせの不一致が 0 件（NFR-002） | fast-check と、夜間の整合性の検査 |
| K4 | 給与計算の時間 | 1 万人の月次の計算が 15 分以内（NFR-003） | 本番とステージングでの計測 |
| K5 | 36 協定の警告 | 上限を超える前に、本人・上長・人事に警告が届く割合 100%（打刻が入力されている場合） | 模擬のデータでの E2E と、本番の日次の検査 |
| K6 | マイナンバーの保護 | 保管庫の外に平文が出た件数 0 件。アクセスの記録の欠け 0 件（NFR-007） | CI とログの走査、保管庫の監査 |
| K7 | テナントの分離 | 他のテナントのデータが見える事象 0 件（NFR-009） | 性質ベーステストと本番の監査 |
| K8 | セルフサービス | 従業員の申請（住所の変更、休暇）が、説明なしで 3 分以内に終わる割合 90% 以上 | 利用者の試験と、画面の計測 |

## Affected users and systems

- **人事の担当者**（主な利用者）：組織と従業員の記録、業務プロセスの定義、権限、レポートを扱う。
- **給与の担当者**（主な利用者）：給与計算の準備・確認・確定、振込、仕訳、住民税、社会保険の手続き。マイナンバーの事務取扱担当者を兼ねることが多い。
- **マネージャー**：部下の勤怠・休暇・異動・昇給の起票と承認。
- **従業員**：自分の情報、打刻、休暇、給与明細。
- **テナントの管理者**：権限の設定、職務分掌の規則、連携の設定。
- **監査人**（社内監査、監査法人）：変更の記録と権限の確認。
- **外部のシステム**：銀行（全銀協の形式のファイル）、会計システム（仕訳）、打刻機、ID 基盤（SAML・OIDC の SSO）、現行の人事・給与のシステム（移行と並行稼働）。後の Epic で、e-Tax、eLTAX、e-Gov（電子申請）。
- **社内の運用**：サポート、法令と料率の更新、障害の対応。

最初の対象は、従業員 300〜3 万人の日本の企業（単一の国、日本の法人）とする。

## Constraints

- **本家の実装を使わない。** オブジェクトモデル、業務プロセスのエンジン、給与計算は自分で設計して作る（[リポジトリ共通の ADR-0007](../../../docs/decisions/0007-no-reuse-of-original-implementation.md)）。本家の振る舞い（有効日付、業務プロセス、ドメインの権限）は考え方として参考にする。
- **本家の名前は識別子に使わない**（[リポジトリ共通の ADR-0006](../../../docs/decisions/0006-brand-neutral-identifiers.md)）。一括の取り込みの形式、API のパス、ヘッダーは `<Brand>`・`<brand>` で書く。本家の API・連携の形式との互換は目標にしない。
- 実行基盤と技術は、rebuilds の他の題材の決定（AWS 東京・大阪、TypeScript、Aurora PostgreSQL、Terraform、OpenTelemetry）を引き継ぐ（[ADR-0001](decisions/0001-platform-and-stack.md)）。
- **法令**：労働基準法（労働時間、割増賃金、年次有給休暇、記録の保存）、所得税法、地方税法（特別徴収）、健康保険法、厚生年金保険法、雇用保険法、介護保険法、子ども・子育て支援法、番号法（行政手続における特定の個人を識別するための番号の利用等に関する法律）、個人情報保護法、電子帳簿保存法。解釈の結論は、法務・社労士・税理士の確認を前提にする。
- **料率と表の改正の周期**：源泉徴収税額表は暦年（1 月）、協会けんぽの料率は 3 月分から、子ども・子育て支援金は 4 月分から、雇用保険の料率は 4 月から、厚生年金の標準報酬月額の上限は 2027 年 9 月から段階的に引き上げ（出典は下の「参考」）。規則表の更新を、法令の公表から適用までの間に出せる形にする。
- データは日本の国内（東京、DR は大阪）に置く。
- 規模は段階的に広げる（[architecture/](architecture/README.md) の「規模の段階」）。

## Non-goals

| 機能 | 理由 |
| --- | --- |
| 本家のメタデータで画面とロジックを組み立てる開発の環境（本家の XpressO に相当）、テナントが書くコードでの拡張 | 題材の論点から外れる。テナントの設定（項目、業務プロセス、計算式の限られた形）で足りる範囲に絞る |
| テナントごとのカスタマイズの版（テナントごとのコードの分岐） | 本家と同じく、全テナントが 1 つのコードラインを使う。違いは設定と規則表で表す |
| 本家の Web サービス・一括の取り込みの形式との互換 | リポジトリ共通の ADR-0006 |
| 給与の支払いの代行（資金を預かって振り込む） | 資金移動業や銀行との契約の論点が別になる。振込ファイルを作り、送信は企業の銀行の仕組みで行う |
| 労務の判断の代行（36 協定の締結、就業規則の作成） | 設定を受け取り、警告するまで。判断は企業と社労士が行う |
| 給与計算の結果の「自動の修正」 | 計算の誤りの候補は検知して示すが、直すのは担当者が業務プロセスで行う |

### 選定・計測で決めるもの（法務以外）

- 源泉所得税の計算の方式：月額表の表引きと、電子計算機等による計算の特例の両方を持ち、会社ごとの有効日付の設定で選ぶ。既定は表引き。特例の端数は告示の別表で確かめた（**決定**。[ADR-0031](decisions/0031-income-tax-withholding.md)）。
- 雇用保険の料率の改定は、賃金の締日で選ぶ（**決定**。[ADR-0033](decisions/0033-employment-insurance-and-resident-tax.md)）。一次の資料の確認は L37 に残す。
- 協会けんぽと健康保険組合の料率の持ち方：協会けんぽの都道府県別の料率は規則表、健康保険組合の料率はテナントが入力する表（**決定**。[payroll-jp-rules.md](architecture/payroll-jp-rules.md) の 2.1 節）。
- 給与計算の時間（NFR-003）と、S2 の 10 万人のテナントでの計算の分割の単位：E12 の負荷試験で決める。
- 打刻機の連携の形式：対象の機種と形式を E6 の着手前に決める（未検証。E6 の `clock-terminal-integration` の PoC で確かめる）。
- 銀行への振込データの締め切り（支給日の何営業日前か）は、銀行ごとに違う（未検証。E10 の `zengin-file-generation` の前に確かめる）。既定は支払元の口座の設定の 3 営業日前（[payments-and-accounting.md](architecture/payments-and-accounting.md) の 3.5 節）。銀行ごとの値は E10 の着手の前に対象のテナントの銀行の仕様書で確かめる。
