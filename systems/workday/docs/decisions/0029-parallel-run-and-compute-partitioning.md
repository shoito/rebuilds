# ADR-0029: 計算を決まった束ごとに ECS のタスクで行い、並行稼働は許容の幅なしで差を分類して切り替えを判定する

詳細は [payroll-engine.md](../architecture/payroll-engine.md) の 9・10 節。

## Context

- NFR-003：1 万人の月次の計算が 15 分以内、3 万人が 45 分以内、1 人の再計算が 5 秒以内。S2 は 10 万人で 60 分以内。支給日の前の 5 日に S1 の 7 割のテナントが集中する。
- [ADR-0004](0004-payroll-engine.md) は、Payroll Compute が DB を直接読まず、従業員の束ごとに並列に計算すると決め、束の大きさとタスクの数を E12 の負荷試験で決めるとした。
- NFR-001 と K2：本番の切り替えの前に、現行のシステムと 3 か月（賞与の月を 1 回以上）並行して計算し、差がすべて説明済みであること。比較は本番の環境の中だけで行い、報告に個人を特定できる値を出さない（[AGENTS.md](../../AGENTS.md)）。
- タスクの異常終了と再試行で、結果が二重になったり欠けたりしてはならない。

## Options

分割：

1. **雇用の ID の順の決まった束（既定 250 人）。束の中身を記録して再試行でも変えない。束の結果をファイルにし、取り込みで 1 束 1 トランザクション**
2. タスクが共有の待ち行列から 1 人ずつ取る
3. 1 つのタスクで全員を計算し、worker threads だけで並列にする

並行稼働の差：

- a. **許容の幅なし（1 円の差も差）。差を分類し、説明を担当が付けて QA が承認する。`our_bug` は直して差が消えるまで閉じない**
- b. 1 人あたり数円の許容の幅を置く

## Decision

1 と a を採用する。

- 束（`payroll_chunks`）は入力の固定のときに作り、中身と `manifest_hash` を記録する。SQS で束の ID を配り、ECS のタスク（worker threads つき）が S3 から入力を読み、結果の束のファイル（JSONL と SHA-256）を S3 に書く。
- 取り込み（Worker の Loader）は、束のファイルのハッシュを確かめて 1 トランザクションで入れる。`(run_id, employment_id)` の一意で二重の取り込みは何もしない。
- 1 人の評価の例外はその人を `error` にし、束は成功にする。タスクの異常終了は束ごとに 3 回まで再試行する。
- 同時のタスクは、テナントごと（既定 20）と全体に上限を置き、支給日の近い実行を先にする。束の大きさ・タスクの数は E12 で決め直す。
- 並行稼働は `run_type = parallel` の実行で行い、確定しない。現行の結果を項目の対応表（`legacy_item_map`）で取り込み、従業員 × 項目 × 月の差（`parallel_diffs`）を `our_bug`・`legacy_bug`・`config_diff`・`rounding_rule_diff`・`input_diff`・`timing_diff` に分ける。
- 切り替えの条件は、3 か月続けて（賞与の月を 1 回以上）説明のない差が 0 件。月ごとの判定を `parallel_run_gates` に記録する。報告の外への出力は、テナントの鍵の HMAC の仮の ID と、件数・分類・項目だけにする。
- 2 を採らない理由：1 人ごとの取り出しと書き込みで、待ち行列と DB への要求が人数分に増える。どの人がどのタスクで計算されたかの記録も散らばる。
- 3 を採らない理由：1 つのタスクの CPU とメモリーの上限で、3 万人・10 万人の時間の目標に届かない。1 つの失敗で全体をやり直すことになる。
- b を採らない理由：許容の幅の中に、端数の規則の誤りや、特定の条件でだけ出る誤りが隠れる。1 円の誤りも許されない（[ADR-0001](0001-platform-and-stack.md)）。

## Consequences

- 良くなること：
  - 束の分け方・再試行・タスクの数によらず、同じ結果の集合になる。
  - 切り替えの判定が、件数と承認の記録で説明できる。
- 引き受けるコスト：
  - 束の結果のファイルと取り込みの段が 1 つ増える。
  - 並行稼働の説明の作業が重い。`rounding_rule_diff` を減らすため、端数の設定（[ADR-0034](0034-overtime-premiums-and-proration.md)）を現行に合わせる支援が要る。
  - 現行の結果の取り込みの契約の扱いは法務の確認待ち（[intent.md](../intent.md) の L11）。

## Confirmation

- 性質ベーステスト：PROP-PAY-001（束の分け方によらず同じ）、PROP-PAY-007（取り込みに重複・欠けがない）。
- 障害注入：タスクの途中終了、Loader の途中の失敗、同じ束の 2 回の完了の通知。
- 負荷試験（E12）：合成の 3 万人・10 万人で NFR-003。
- 本番：並行稼働の月ごとの説明のない差の件数と、`our_bug` の件数。
