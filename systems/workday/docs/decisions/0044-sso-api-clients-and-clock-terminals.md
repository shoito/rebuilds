# ADR-0044: ログインと SSO は Better Auth で持って本システムは SP・RP だけになり、API の利用者と打刻機は専用の資格情報で同じ権限の判定を通す

詳細は [integrations-and-bulk.md](../architecture/integrations-and-bulk.md) の 6〜8 節。

## Context

- 利用者は企業の ID 基盤から SAML 2.0・OIDC の SSO で入る（intent）。企業の IdP を持たない従業員（工場・店舗）もいる。
- 人事・給与・保管庫の操作は重く、振込ファイルの取り出しや番号の表示には再認証が要る（[ADR-0035](0035-bank-transfer-files.md)）。
- 認証の実装は、rebuilds の他の題材で 2 つの前例がある。
  - Slack の題材は Better Auth を自前でホストし、SSO（OIDC・SAML）はプラグインで、管理の経路は自前の API から呼ぶ（[Slack の ADR-0012](../../../slack/docs/decisions/0012-self-hosted-auth-with-better-auth.md)、2026-09-26 に確定）。Uber・Notion の題材も同じ先例に従う。
  - Auth0 の題材は、IdP そのものを作り直す設計で、まだ開発リポジトリがない。
- 連携（API）と打刻機は人でない主体で、人と同じ権限の判定を通す必要がある（[ADR-0005](0005-security-and-my-number.md)）。打刻機は再送で打刻を二重にしてはならない（[ADR-0021](0021-clock-events-corrections-and-objective-records.md)）。

## Options

利用者の認証：

1. **Better Auth を API のプロセスの中で使う。本システムは SP・RP だけ**
2. Auth0 の題材を IdP にし、本システムはその RP になる
3. マネージドの IdP（Cognito など）

API の利用者：

- a. **OAuth 2.0 のクライアントクレデンシャル（`private_key_jwt` 既定）。連携用の利用者に結び、セキュリティグループで権限を与える**
- b. テナントごとの長命の API キー

打刻機：

- i. **端末ごとの鍵で送る直接の経路と、ファイルの取り込みの経路。打刻の ID は端末の連番から決める**
- ii. 打刻機に人のログインをさせる

## Decision

1、a、i を採用する。

- Better Auth の版を固定し、許可した経路だけを Hono から渡す。SSO の接続の登録は、本システムの管理 API で `security.admin` を確かめてから、サーバーの側で呼ぶ。
- SSO の初回のログインで従業員を作らない。属性で既にいる従業員に結び、結べなければ拒む。アカウントの有効化・無効化は入社・退職の発効のタイマーで行う。
- 企業の IdP を持たない利用者は、メールの OTP かパスキー。パスワードは使わない。SSO を使わない人事・給与・管理者は MFA を必須にする。重い操作は 5 分以内の再認証を要する。
- API の利用者は連携用の利用者（人でない利用者）に結び、`get`・`put`・`initiate` を与える。`approve` は与えない。トークンは 15 分。
- 打刻機は端末ごとの鍵（`<brand>_tk_`、ハッシュで保存）で `POST` するか、管理のソフトの CSV を列の対応で取り込む。`client_event_id = UUIDv5(terminal_id, terminal_seq)`。
- 2 を採らない理由：Auth0 の題材は設計だけで、本番で動く IdP がない。動いたとしても、別の題材のサービスの可用性がログインの可用性を決め、運用とテナントの対応表を二重に持つ。本システムに要るのは SP・RP の側だけで、Better Auth で足りる。Auth0 の題材が本番になれば、テナントの SSO の接続の 1 つ（OIDC）として使える。
- 3 を採らない理由：テナントごとの SSO の接続と、従業員の結び（人事の記録が正本）を IdP の側の利用者のモデルと二重に持つ。利用者の数に比例する費用になる（Slack の ADR-0012 と同じ理由）。
- b を採らない理由：漏れたときの影響が長く、鍵の持ち主の区別（どの連携か）が付けにくい。
- ii を採らない理由：共有の端末で個人のセッションを持つと、なりすましと、ログアウトの忘れが起きる。

## Consequences

- 良くなること：
  - 他の題材と同じ認証の部品と知見を使える。
  - 人・連携・打刻機のすべてが、同じ権限の判定と監査の記録を通る。
  - 打刻機の再送と同じファイルの再取り込みで二重にならない。
- 引き受けるコスト：
  - Better Auth の SAML の相互運用と脆弱性の対応を自分たちで追う（Slack の ADR-0012 の見直しの条件を引き継ぐ）。
  - SCIM がないので、IdP の側でだけ無効にした利用者は、退職の発効までセッションを持てる。人事・給与のロールのアイドル 30 分と絶対 12 時間で抑える。
  - 打刻機の機種ごとの CSV の列の対応をテナントが作る。

## Confirmation

- 結合テスト：テストの IdP で、SAML の署名の誤り・古い応答・IdP 起点・属性の欠けを拒む。SSO の初回のログインで従業員が作られない。
- 決定表のテスト：DT-INT-004。
- 性質ベーステスト：PROP-INT-003（打刻機の再送で件数が変わらない）、PROP-INT-004（API と画面の結果の一致）。
- lint：Better Auth の管理の経路（`/api/auth/sso/register` など）を Hono のルートに渡すコードを禁じる。
