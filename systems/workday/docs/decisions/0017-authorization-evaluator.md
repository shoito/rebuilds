# ADR-0017: 権限の判定を自前の評価器で行い、利用者ごとの権限の表と、閉包を使う SQL の条件で絞る

詳細は [security-model.md](../architecture/security-model.md) の 4・7 節。

## Context

[ADR-0005](0005-security-and-my-number.md) は、ドメインと業務プロセスの権限、組織で絞るロール、職務分掌で守り、判定を 1 か所にまとめると決めた。判定の方式（自前の評価器か、汎用のポリシーエンジンか）は、この領域で E4 の着手の前に決めるとした（[architecture/README.md](../architecture/README.md) の 6 節）。

条件は次のとおり。

- 判定はすべての読み取りに入る。画面の 1 件だけでなく、一覧・レポート・一括の出力で、数千〜数万行を組織の範囲で絞る。行ごとに外部のエンジンを呼べない。
- 範囲は組織の階層の下位を含む。階層は有効日付で変わる（[ADR-0011](0011-effective-dated-org-hierarchy-closure.md)）。
- テナントの管理者と監査人に「誰が何を見られるか」を説明できなければならない。
- 本家は、絞られたグループと絞らないグループの両方に属する人に和を与える（[Security Group Configuration and Constraints](https://doc.workday.com/workday-education/en-us/course-manuals/security-for-administrators/security-group-configuration-and-constraints.html)、2026-09-28 に確認）。

## Options

1. **自前の評価器。有効な方針のバージョンとグループの所属から、利用者ごとの権限（ドメイン、操作、範囲の根の組織）を畳んだ表を作る。1 件は関数で、一覧は閉包を使う SQL の条件で絞る**
2. Cedar（[Cedar](https://www.cedarpolicy.com/)、2026-09-28 に確認）。方針を Cedar の言語に変換し、評価する
3. OPA（[Open Policy Agent](https://www.openpolicyagent.org/docs)、2026-09-28 に確認）。Rego で方針を書き、サイドカーで評価する
4. 関係に基づく認可（Zanzibar の考え方。[Zanzibar](https://research.google/pubs/zanzibar-googles-consistent-global-authorization-system/)、SpiceDB など。2026-09-28 に確認）。組織の階層と所属を関係の組として別のサービスに持つ

## Decision

1 を採用する。

- 判定のコードは `packages/authz` に 1 つだけ置く。`can`（1 件）、`scopeFilter`（一覧の SQL の条件）、`project`（項目の射影）、`canBp`（業務プロセスの操作）。
- 権限は和で決まる。既定は拒否。明示の拒否の規則は持たない。例外はシステムの固定の規則（本人の案件の承認の禁止、要配慮の既定の不付与、マイナンバーは保管庫の判定）。
- `security_effective_grants` に、利用者ごと・方針のバージョンごと・所属のバージョンごとの権限の行（ドメインまたは業務プロセス、操作、範囲の種類、根の組織）を持つ。`self` の権限は行にしない。方針の有効化・所属の変更・発効の日に、影響を受けた人だけ作り直す。
- 範囲は根の組織の ID で持ち、下位は判定のときに閉包で展開する。一覧は `EXISTS (SELECT 1 FROM org_closure ...)` の条件を SQL に入れる。
- Valkey に権限の表をキャッシュする。鍵にバージョンを含め、無効化の漏れを構造上なくす。判定の結果はキャッシュしない。
- 判定は許した権限の ID か拒否の理由を返す。監査と説明の報告に使う。
- 2 を採らない理由：1 件の判定は表せるが、一覧を SQL で絞るには、Cedar の方針から SQL の条件を作る層を別に持つことになる（部分評価の仕組みはあるが、閉包の結びを含む条件を作るのは自前になる）。組織の階層をエンティティとして毎回渡すか、評価器の外で展開する必要もある。
- 3 を採らない理由：2 と同じく一覧の絞り込みが評価器の外に出る。要求ごとにサイドカーを呼ぶ遅れと運用が増える。
- 4 を採らない理由：組織の階層と所属は、すでに Aurora の有効日付のテーブルが正本である。関係の組を別のサービスに写すと、2 つの正本の整合（有効日付を含む）が要る。一覧の絞り込みも、関係のサービスへの問い合わせと DB の結びを往復する。
- 選ばなかった汎用のエンジンの利点（方針の言語の検証の道具）は、方針を JSON のデータにし、決定表と性質ベーステストで確かめることで代える（Figma の題材も、同じく自前の小さな評価器を選んだ）。

## Consequences

- 良くなること：
  - 1 件の判定と一覧の絞り込みが、同じ方針から、同じコードで作られる。経路の食い違いが起きにくい。
  - 組織の再編で権限の表を作り直さなくてよい。
  - 判定に理由を付けられる。
- 引き受けるコスト：
  - 評価器、権限の表の作り直し、キャッシュを自前で持つ。
  - `scopeFilter` を使わずに一覧を読むコードを、lint とレビューで止める必要がある。

## Confirmation

- 性質ベーステスト：PROP-SEC-001（経路の一致）、PROP-SEC-003（単調）、PROP-SEC-005（キャッシュの有無で同じ）、PROP-SEC-007（再編の後の範囲）。
- 決定表のテスト：DT-SEC-001（範囲）、DT-SEC-003（項目の射影）。
- lint：`packages/authz` の外で、方針・グループ・権限の表を読んで権限を決めるコード、`scopeFilter` を通さない人事のテーブルの一覧の問い合わせを禁止する（例外は許可リスト）。
- 性能のテスト：`can` の p99 1ms 以内。
