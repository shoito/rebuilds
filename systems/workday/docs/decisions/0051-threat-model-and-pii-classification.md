# ADR-0051: 個人情報を 5 つの区分に分けて列ごとに宣言し、脅威は部品ごとの STRIDE の表と拒否の側のテストで持つ

詳細は [security.md](../architecture/security.md) の 3・4 節。

## Context

- 人事・給与のデータは、同じテナントの中でも重さが大きく違う。組織の名前、表示の名前、給与の額、口座、健康の情報、マイナンバー。
- 規則は重さごとに違う：ログに出してよいか、分析用の基盤に出してよいか、閲覧を記録するか、項目の暗号が要るか。[AGENTS.md](../../AGENTS.md) は、氏名・住所・生年月日・口座・給与・健康・扶養をログに出さないと決めている。
- 規則を文書にだけ書くと、新しい facet や列で漏れる。facet は宣言から生成する（[ADR-0006](0006-temporal-table-triplet-and-fold.md)）ので、宣言に区分を足せば機械で守れる。
- 他の題材（Auth0）は、RFC のチェックリストの行を `SEC-` の ID で拒否の側のテストに結んだ。この題材に RFC はないが、脅威の表の行を同じようにテストに結べる。

## Options

区分：

1. **P0 業務・P1 個人・P2 機微・P3 要配慮・P4 特定個人情報の 5 区分。列ごとに宣言し、区分ごとの規則を CI と実行時の型で守る**
2. 「個人情報か否か」の 2 区分
3. 区分を持たず、ドメインの権限（[ADR-0005](0005-security-and-my-number.md)）だけで扱う

脅威：

- a. **部品ごとの STRIDE の表。行に `THR-NNN` の ID を振り、拒否の側のテストの名前に入れ、CI で参照の漏れを検査する**
- b. 文書だけ

## Decision

1 と a を採用する。

- 区分ごとの規則（保存の暗号、ログ・トレース、分析用の出力、閲覧の記録）は [security.md](../architecture/security.md) の 4 節の表。P4 は保管庫にだけ置く。P3 は MVP では持たない。
- 列の区分は `FacetSpec` とマイグレーションの注記（`pii_class`）で持つ。区分のない列を CI で拒む。ログのイベントの型は P0・P1 の ID だけを受ける。
- 区分とドメインは別の軸：ドメインは「誰が見られるか」、区分は「どこに出してよいか」。機微なドメインの列は P2 以上にする。
- 脅威の表の行は `THR-NNN`。テストの名前に ID を入れ、表のすべての行がどこかのテストから参照されていることを CI で確かめる。
- 2 を採らない理由：表示の名前（組織図に出る）と給与の額が同じ扱いになり、ログから表示の名前まで消すか、給与まで出すかのどちらかになる。
- 3 を採らない理由：ドメインの権限は、ログ・トレース・分析の出力・テストのデータの規則を決めない。
- b を採らない理由：脅威の対策の実装の漏れを、ペンテストまで見つけられない。

## Consequences

- 良くなること：
  - 新しい列を足すたびに、どこに出してよいかが決まる。
  - 脅威の対策の抜けを、テストの参照の漏れとして CI で見つけられる。
- 引き受けるコスト：
  - すべての列に区分を付ける手間。既定の区分（P2）を置かず、明示させる。
  - 脅威の表の保守。新しい部品・経路を足す変更は、表の行を足す（`security:sensitive` のレビューで確かめる）。

## Confirmation

- CI：`pii_class` のない列を持つマイグレーションを拒む。`THR-` の行を参照しないテストの漏れを拒む。
- CI：ログのイベントの型に P2 以上の列の型が入ったら拒む。
- 本番：ログ・トレースの個人情報の形の走査で検出 0 件（[observability.md](../architecture/observability.md) の 4 節）。
