# ADR-0035: 振込は支払の指示から決定的に作る全銀協の形式のファイルにし、承認はファイルのハッシュに結ぶ

詳細は [payments-and-accounting.md](../architecture/payments-and-accounting.md) の 3 節。

## Context

- 賃金は労働者の同意を得れば、指定の預金口座への振込で払える（[労働基準法施行規則](https://laws.e-gov.go.jp/law/322M40000100023) 7 条の 2、e-Gov で 2026-09-28 に確認）。同意の取り方は社労士の確認待ち（[intent.md](../intent.md) の L4）。
- intent は、資金を預からず、全銀協の規定形式（給与・賞与振込）のファイルを作り、送信は企業の銀行の仕組みで行うと決めた。
- 形式は 120 バイトの固定長で、ヘッダー・データ・トレーラー・エンドの 4 種、種別コードは給与 11・賞与 12、コード区分は JIS か EBCDIC、給与の預金種目は普通・当座だけ、0 円のレコードは入れない（[三井住友銀行の仕様](https://www.smbc.co.jp/hojin/eb/firm/manual/resources/pdf/sougoufurikomi_kyuyofurikomi.pdf)、2026-09-28 に確認。全銀協の原本は未取得）。レコードの区切りや使える文字の細部は銀行ごとに違いうる（未検証。E10 の `zengin-file-generation` の前に、テナントの銀行の仕様書で確かめる）。
- 振込ファイルは口座番号の平文を含み、改ざんされれば架空の口座への送金になる。振込先の変更と振込ファイルの承認は職務分掌の対象（[security-model.md](../architecture/security-model.md) の 5 節の S2）。
- Stripe の題材は、銀行の API を主、全銀のファイルを予備にした（[payouts-and-reconciliation.md](../../../stripe/docs/architecture/payouts-and-reconciliation.md) の 4.1 節）。この題材は資金を預からないので、企業の口座からの送信になる。

## Options

1. **確定のときに支払の指示（1 人 × 口座の額）を作り、支払元の口座 × 種別 × 振込指定日ごとに、指示だけから決まるバイト列のファイルを作る。承認はファイルの SHA-256 に結ぶ**
2. 承認の後に、その時点の振込先でファイルを作る
3. 銀行の API で本システムから送信する

## Decision

1 を採用する。

- 指示（`payment_instructions`）は `finalized` のときに、確定の結果と、実行の `known_at` の振込先から作る。配分は `fixed` → `percent`（`round_down_yen`）→ `remainder` の順。口座番号は暗号文のまま持つ。
- ファイル（`bank_files`）は指示だけから作る。並びは銀行・支店・雇用・順。コード区分・レコードの区切りは支払元の口座の設定。受取人名は全角→半角、英小文字→大文字、小書きのカナ→大書きに変換し、使えない文字があれば作らずに一覧を出す。検査は DT-PMT-001。
- 承認は `payroll_payment_release` で、承認の対象はファイルの SHA-256。ファイルが変われば承認は無効。取り出しは承認者と指定の担当だけ、ステップアップの再認証、15 分の 1 回限りの URL、すべて記録する。
- 同意（`wage_payment_consents`）のない人は振込から外し、振込以外の支払いの一覧に出す。
- 振込の不能は担当が記録し、`off_cycle` か再支払いの指示で扱う。
- 2 を採らない理由：承認と支給の間に振込先が変わると、承認していない口座に送ることになる。承認の対象が曖昧になる。
- 3 を採らない理由：企業ごとに銀行と契約が違い、本システムが企業の口座の送金の権限を持つことになる。資金の移動の論点と責任が変わる（intent の Non-goals）。

## Consequences

- 良くなること：
  - 承認したバイト列と銀行に渡るバイト列が同じであることを、ハッシュで確かめられる。
  - 振込先の変更の攻撃（承認の後にすり替える）が効かない。
- 引き受けるコスト：
  - 銀行ごとの細部（区切り、文字、名前の長さ、締め切り）を設定で持ち、E10 の前に対象の銀行の仕様書で確かめる。
  - 振込の結果の自動の取り込みがないので、不能の記録は担当の入力に頼る。
  - ファイルの取り出しの後の扱い（担当の端末、銀行への受け渡し）はシステムの外。runbooks で手順にする。

## Confirmation

- 決定表のテスト：DT-PMT-001・002。
- 性質ベーステスト：PROP-PMT-001（配分の合計）、PROP-PMT-002（120 バイトとトレーラー）、PROP-PMT-003（同じ指示から同じバイト列）。
- 結合テスト：承認の後にファイルを作り直して違うハッシュになると、取り出しが拒まれる。
- 決定表のテスト（権限）：S2 の組を持つ利用者の `payroll_payment_release` の承認が拒まれる。
