# ADR-0005: ドメインと業務プロセスの権限と職務分掌で守り、マイナンバーは別アカウントの保管庫に置く

## Context

人事・給与のデータは、同じテナントの中でも、見てよい人が細かく分かれる。

- 従業員は自分の情報だけ。マネージャーは部下の情報のうち勤怠・休暇・職務だけで、給与は見せないことが多い。人事の担当は担当の組織だけ。給与の担当は給与と口座を見るが、評価は見ない。
- 同じ人に、給与のマスタの変更と給与の確定、振込先の口座の変更と振込ファイルの承認を、両方させてはならない（職務分掌）。
- 権限は、画面・API・レポート・一括の出力・連携のすべてで同じでなければならない。

本家は、機能の領域（ドメイン）ごとの権限（View・Modify、連携の Get・Put）と、業務プロセスの種類ごとの権限（起票、承認、取消、訂正など）を持つ。セキュリティグループには、ユーザー、ロール（組織で絞る・絞らない）、職務、組織・勤務地、集約・交差、階層などの種類がある。権限の変更は「有効化」まで保留され、編集と有効化を別の人に分けられる（[Security](https://doc.workday.com/workday-education/en-us/course-manuals/financial-management-for-administrators/security.html)、2026-09-28 に確認）。レポート・モバイル・API・業務プロセスのすべてに、同じロールの権限が効く（[ホワイトペーパー](https://www.workday.com/content/dam/web/en-us/documents/whitepapers/whitepaper_workday_technology_platform_devt_process.pdf)、2026-09-28 に確認）。

マイナンバー（個人番号）には、番号法と個人情報保護委員会のガイドラインの規律がある（[特定個人情報の適正な取扱いに関するガイドライン（事業者編）](https://www.ppc.go.jp/legal/policy/my_number_guideline_jigyosha/)、令和 7 年 6 月の一部改正の版。2026-09-28 に確認）。

> 2026-09-28 の注記：最初は令和 6 年 5 月の一部改正の版を引いていた。今の最新は令和 7 年 6 月の一部改正の版で、[my-number-vault.md](../architecture/my-number-vault.md) の 2 節でその本文を確かめたので、引く版を直した。下の要点（利用の制限、安全管理措置、保存期間の後の廃棄、継続的な保管）は、新しい版でも同じで、決定は変えない。

- 利用は、社会保障・税・災害対策の決められた事務に限る。
- 取り扱う事務、特定個人情報の範囲、事務取扱担当者を明確にする。
- 組織・人・物理・技術の安全管理措置（アクセスの制御、利用の状況の記録など）を講じる。
- 事務に要らなくなり、所管の法令の保存期間を過ぎたら、できるだけ速やかに廃棄・削除する。例：扶養控除等申告書は、提出の期限の属する年の翌年 1 月 10 日の翌日から 7 年の保存で、過ぎたら記載の個人番号を廃棄する。
- 雇用の契約が続く間は、翌年以降の源泉徴収票の作成のために保管し続けてよい。

## Options

権限のモデル：

1. **ドメインと業務プロセスの権限、組織で絞るロール、職務分掌の規則表**（本家と同じ考え方を自前で作る）
2. 単純な RBAC（テナントの中のロールだけ）
3. 属性ベース（ABAC）のポリシーを、テナントが自由に書く

マイナンバーの置き場所：

- a. **別の AWS アカウントの保管庫（専用のサービス、DB、KMS の鍵）。人事の DB には参照の ID だけ**
- b. 人事の DB の中で、項目ごとに暗号化する
- c. 外部のマイナンバーの管理のサービスに任せる

テナントの分け方：

- i. **共有スキーマ＋RLS**（他の題材と同じ）
- ii. テナントごとの DB

## Decision

1、a、i を採用する。

### 権限のモデル

| 概念 | 内容 |
| --- | --- |
| ドメイン | 機能の領域。データの項目の群と操作をまとめたもの。例：`worker.personal`、`worker.job`、`worker.compensation`、`worker.payment_election`、`worker.dependents`、`time.records`、`absence`、`payroll.results`、`payroll.run`、`my_number`、`security.admin`、`audit` |
| 権限 | ドメインごとの `view`・`modify`。連携では `get`・`put` |
| 業務プロセスの権限 | 業務プロセスの種類ごとの `initiate`・`approve`・`cancel`・`rescind`・`correct`・`view` |
| セキュリティグループ | 権限を持たせる単位。種類は、ユーザー（直接の割り当て）、ロール（組織ごとの割り当て。例：組織 A の上長）、職務（職務・等級から自動）、自分（対象が自分）、交差（2 つのグループの両方に属する） |
| 範囲 | ロールのグループは、割り当てた組織と、その下位の組織に絞る（下位を含むかは割り当てごとに決める） |

- ドメインの一覧と、項目・操作のドメインへの割り当ては、システムが持つ。テナントは変えられない。テナントは、どのグループにどのドメインの権限を与えるかを決める。
- ロールの割り当ては有効日付で持つ（[ADR-0002](0002-effective-dated-data-model.md)）。権限の判定は、要求の時点の割り当てで行う。
- **権限の判定は 1 か所にまとめる。** API、画面、レポートの実行、一括の出力、連携、Webhook の送信の前に、同じ判定のライブラリを通す。項目の単位で、見えない項目を落とす。判定の方式（自前の評価器か、汎用のポリシーエンジンか）は security-model の領域で決める。
- **権限の変更は、保留と有効化に分ける。** 編集した人と有効化した人を別にできる。有効化も記録する。

### 職務分掌

- 同じ人が、同じ業務プロセスの案件で、起票と承認をしない。委任を経た場合も、実際の操作者で判定する（[ADR-0003](0003-business-process-engine.md)）。
- システムが既定の職務分掌の規則表（両立しない権限の組）を持ち、テナントが足せる。例：

| 権限 A | 権限 B | 理由 |
| --- | --- | --- |
| `worker.compensation` の `modify` | `payroll_finalize` の `approve` | 自分で上げた給与を自分で確定しない |
| `worker.payment_election` の `modify`（本人以外） | 振込ファイルの承認 | 振込先を書き換えて送金しない |
| `security.admin` の `modify` | 権限の変更の有効化 | 自分に権限を与えない |
| `payroll.results` の `modify`（個別の調整） | `payroll_finalize` の `approve` | 調整と確定を分ける |

- 規則表に反する割り当ては、権限の変更の有効化のときに拒む。規則表の変更の前からある違反は、報告に出す。
  - > 2026-09-28 の注記：上の表は例である。規則表の正本は [security-model.md](../architecture/security-model.md) の 5.1 節（S1〜S8）で、ドメインの名前もそこに揃えた（権限の変更の編集は `security.config`、有効化は `security.activation`、給与の個別の調整は `payroll.input`。`security.admin` は SSO の接続・API の利用者・代理のログインなどの管理に使う）。検査点は [ADR-0019](0019-segregation-of-duties-checks.md) の 4 か所に広げた。決定は変えない。

- 本人が自分の情報を変える申請（住所、口座）は、本人の起票として扱い、承認は他の人が行う。

### マイナンバーの保管庫（a）

- **置き場所**：保管庫（Vault）は、別の AWS アカウントに、専用の ECS のサービスと、専用の Aurora と、専用の KMS の鍵で置く。人事の側のサービスは、相互 TLS の API で、参照の ID（`mn_ref`）を使って呼ぶ。人事の DB には `mn_ref` と「登録済みか」だけを置く。
- **暗号化**：番号はレコードごとのデータの鍵で暗号化し、データの鍵を KMS の鍵で暗号化する（エンベロープ暗号化）。検索のための値（重複の登録の検知）は、テナントごとの秘密の鍵の HMAC で持つ。
- **利用の目的**：保管庫の API は、目的（源泉徴収票の作成、給与支払報告書の作成、社会保険の届出、雇用保険の届出など）を必須の引数にする。目的ごとに、呼べるロール（事務取扱担当者）と、返す形を決める。
- **平文を外に出さない**：画面での確認は、保管庫が描画するマスクした表示（末尾 4 桁など）と、事務取扱担当者の明示の操作での一時の表示に限る。法定の書類（源泉徴収票など）は、保管庫の中で作り、完成した書類を保管庫の中に置く。書類の取り出しも記録する。
- **アクセスの記録**：登録、表示、書類の作成・取り出し、変更、削除のすべてに、誰が・いつ・どの従業員（またはその扶養の親族）の・どの目的で、を追記のみのログに記録する。ログはハッシュの連鎖と S3 の Object Lock で改ざんを検知できる形にする（audit-and-retention の領域）。
- **収集**：従業員のセルフサービスで、番号と本人確認の書類を受け取る。本人確認の方法と結果を記録する。扶養の親族の番号も同じ形で受ける。
- **削除**：書類の種類ごとの保存期間を規則表で持ち、退職などで事務が要らなくなり、保存期間を過ぎた番号を削除する。削除は日次の処理で候補を作り、事務取扱担当者の確認の後に実行する。削除の記録（いつ、誰の、何を、誰の承認で）は残し、番号そのものは残さない。書類ごとの保存期間は、税理士・社労士の確認待ち（[intent.md](../intent.md) の L2）。
- **運用者**：本システムの運用者は、通常の運用で保管庫のデータを見られない。障害の対応での例外の手順は、security の領域で決める。
- b を選ばなかった理由：人事の DB の中に置くと、人事の DB の読み取りの権限、バックアップ、分析用の出力、ログの経路のすべてが、特定個人情報の安全管理の範囲に入る。範囲を保管庫に絞るため、アカウントから分ける。
- c を選ばなかった理由：法定の書類の作成を本システムの中で行う必要があり、外部のサービスと書類の生成を往復させると、平文の経路が増える。委託の関係（[intent.md](../intent.md) の L1）も複雑になる。

### その他の個人情報

- 口座番号は、項目ごとにエンベロープ暗号化して持ち、`worker.payment_election` の権限でだけ復号する。
- 要配慮個人情報（健康の情報、障害、労災）は、専用のドメインに置き、既定でどのロールにも与えない。扱いは法務の確認待ち（[intent.md](../intent.md) の L10）。
- ログ・トレースには、許可リストのスキーマを通した値だけを出す。個人情報はマスクする。

### テナント（i）

- 全テナントテーブルに `tenant_id` を持たせ、主キーとインデックスの先頭に置く。ID は UUIDv7。
- `FORCE ROW LEVEL SECURITY` を設定し、トランザクションごとに `SET LOCAL app.tenant_id` を設定する。Payroll Compute と BP Worker も、ジョブのテナントを設定してから読む。
- テナントの解決は、ログインのセッション（SSO の結果）と、ホスト名（`<tenant>.<brand>.<domain>`）で行い、両方が一致しない要求は拒む。
- RLS を外すのは、テナントをまたぐ運用の処理（規則表の配布、課金の集計）だけにし、別の DB のロールで行う。規則表（税額表、料率）は全テナントに共通のデータとして、テナントの外に置く。
- 保管庫もテナントで分ける（`tenant_id` と RLS、テナントごとの HMAC の鍵）。
- ii は、S1 の 600 テナントなら運用できるが、S3 の 2 万テナントで重い。大口のテナントの分離は、S2 のクラスタの分割と S3 のセルで行う（infrastructure の領域）。
- 2 を選ばなかった理由：組織で絞る権限と、職務分掌と、業務プロセスごとの権限を表せない。
- 3 を選ばなかった理由：テナントが自由に書くポリシーは、誤りの検証と、監査人への説明が難しい。本システムは、決まった概念の組み合わせで表し、組み合わせの結果を「誰が何を見られるか」の報告として出せる形にする。

## Consequences

- 良くなること：
  - 画面・API・レポート・連携で権限が食い違わない。
  - 特定個人情報の安全管理の範囲が、保管庫のアカウントに絞られる。
  - 職務分掌の違反を、権限の有効化の時点で止められる。
- 引き受けるコスト：
  - 権限の判定が、すべての読み取りの経路に入る。レポートや一覧で、行と項目の絞り込みの性能が要る。判定の結果のキャッシュ（ロールの割り当ての変更で無効化）を security-model の領域で設計する。
  - 保管庫が別のアカウントになり、ネットワーク、デプロイ、監視、DR を別に持つ。
  - テナントの管理者が、権限の設定を理解できる画面と報告（「この人は何を見られるか」「この項目を誰が見られるか」）が要る。

## Confirmation

- 性質ベーステスト：任意の 2 テナントで、一方のコンテキストで他方の行が読めない。
- 性質ベーステスト：任意のロールの割り当てと要求で、API・レポート・一括の出力の結果が、同じ判定の関数の結果と一致する（経路による差がない）。
- 決定表のテスト：職務分掌の規則表の各行で、両立しない割り当ての有効化が拒まれる。
- CI：人事の側のパッケージのコード・ログ・フィクスチャーに、個人番号の形（12 桁の数字で、チェックデジットが合うもの）が現れたら失敗させる。保管庫のパッケージ以外からの KMS の保管庫の鍵の利用を、IAM と lint の両方で禁止する。
- 監査：保管庫のアクセスの記録と、保管庫の API の呼び出しの記録（ロードバランサーのログ）を日次で突き合わせ、記録の欠けが 0 件であることを確かめる。
- CI：新しいテーブルに `tenant_id` と RLS のポリシーがないマイグレーションを失敗させる（例外は許可リストで管理する）。
