# ADR-0004: 給与計算を、入力のスナップショットと規則表のバージョンから決まる純粋な計算にする

## Context

日本の給与計算は、次のものから決まる。

- 従業員の情報（所属、雇用区分、基本給、手当、扶養の人数、税の区分、社会保険の等級、住民税の月額）。有効日付つき（[ADR-0002](0002-effective-dated-data-model.md)）
- 勤怠の結果（残業、深夜、休日、欠勤）と休暇
- 規則表：
  - 源泉徴収税額表（月額表の甲欄・乙欄、日額表、賞与の算出率の表、電子計算機等による計算の特例）。令和 8 年分は、基礎控除の見直しにより改正され、令和 8 年 1 月に支払う給与から使う（[国税庁](https://www.nta.go.jp/publication/pamph/gensen/zeigakuhyo2026/01.htm)、2026-09-28 に確認）
  - 健康保険・介護保険の料率（協会けんぽは都道府県別で、令和 8 年度は 3 月分から）、子ども・子育て支援金率（令和 8 年 4 月分から 0.23%）（[協会けんぽ](https://www.kyoukaikenpo.or.jp/about/business/insurance_rate/rate_prefectures/r08/index.html)、[子ども・子育て支援金率](https://www.kyoukaikenpo.or.jp/about/business/insurance_rate/003/index.html)、2026-09-28 に確認）
  - 厚生年金の料率と標準報酬月額の等級表
  - 雇用保険の料率（令和 8 年度の一般の事業は、労働者の負担 5/1000。[厚生労働省](https://www.mhlw.go.jp/content/001692566.pdf)、2026-09-28 に確認）
- 端数の規則：社会保険料の被保険者負担分は、給与から控除するとき 50 銭以下を切り捨て、50 銭を超えると切り上げる。特約があればそれに従う。事業主の負担は、納入告知の額から被保険者の負担の合計を引いた額になる（[日本年金機構](https://www.nenkin.go.jp/service/kounen/hokenryo/nofu/20121026.html)、2026-09-28 に確認）。
- 料率の「何月分」と、控除する給与の月のずれ：事業主は前月の標準報酬月額に係る保険料を報酬から控除できる（[厚生年金保険法](https://laws.e-gov.go.jp/law/329AC0000000115) 84 条、[健康保険法](https://laws.e-gov.go.jp/law/211AC0000000070) 167 条）。協会けんぽの令和 8 年度の料率は「3 月分（4 月納付分）」から、支援金は「4 月分（5 月納付分）」から（[東京支部の額表](https://www.kyoukaikenpo.or.jp/assets/R8_13tokyo.pdf)）。前月分を控除する会社では、新しい料率は 4 月支給から、支援金は 5 月支給から控除に現れる。いずれも 2026-09-28 に確認。控除の月の慣行はテナントの設定。

本家は、給与計算のような重い計算を、別の計算のサービスで、メモリーの中のデータのスナップショットから行う（[ホワイトペーパー](https://www.workday.com/content/dam/web/en-us/documents/whitepapers/whitepaper_workday_technology_platform_devt_process.pdf)、2026-09-28 に確認）。本家が日本の給与計算を自社の機能として提供しているかは、公開の資料で確かめられなかった。日本は、給与計算のパートナーとの連携（Global Payroll Connect）で扱う形と見られる（[Workday のグローバル給与計算](https://www.workday.com/ja-jp/products/payroll/global-payroll.html)、2026-09-28 に確認。日本の扱いは未検証）。

## Options

計算の形：

1. **純粋な計算。** 計算の前に入力のスナップショットを作り、規則表のバージョンとエンジンのバージョンを固定して計算する。結果は追記のみ
2. **DB を読みながら計算する手続き。** 計算の中で必要な値をその都度読む
3. **テナントが規則を書くルールエンジン（汎用の DSL）**

遡及の扱い：

- a. **遡及の差額を、次の計算の項目として出す**（確定した結果は変えない）
- b. 確定した過去の結果を再計算して置き換える

## Decision

1 と a を採用する。

### 計算の実行

給与計算の実行（payroll run）は、次の段を持つ。段の移動は、業務プロセス（[ADR-0003](0003-business-process-engine.md)）で行い、確定には承認を要する。

| 段 | すること | 取り消し |
| --- | --- | --- |
| 準備 | 対象の従業員、期間（締日・支給日）、種類（月次・賞与）を決める | できる |
| 入力の固定 | 入力のスナップショットを作る（下） | できる（捨てて作り直す） |
| 計算 | Payroll Compute が、従業員の束ごとに計算する | できる |
| 確認 | 前月との差、異常値（差引の支給額が負、急な増減）、並行稼働の差異を示す。1 人ずつの再計算ができる | できる |
| 確定 | 結果を固定する。仕訳を作る。以後、結果は変わらない | 支払の前なら、取消の業務プロセスで取り消し、作り直す |
| 支払 | 振込ファイル、明細の公開 | できない。誤りは次の計算の差額で直す |

### 入力のスナップショットと再現性

- 入力の固定の時刻を `known_at` として、対象の従業員の有効日付のデータを、期間の各日について読み（[ADR-0002](0002-effective-dated-data-model.md)）、勤怠の締めの結果、休暇、個別の調整の入力と合わせて、1 人ずつの入力の文書（JSON）にする。
- 入力の文書は、正規の形（キーの順序、数の表記を固定）にしてハッシュを取り、S3 と DB に保存する。
- 結果には、入力のハッシュ、規則表のバージョンの ID の一覧、エンジンのバージョン（コンテナのイメージのダイジェスト）、テナントの計算の設定のバージョンを記録する。
- **計算の関数は純粋にする。** 入力の文書・規則表・設定だけから結果を決める。現在時刻、乱数、DB、環境変数を使わない。Payroll Compute は、入力を渡して結果を受け取るだけで、DB を直接は読まない。
- 同じ入力・同じ規則表のバージョン・同じエンジンのバージョンで、何度計算しても 1 円も違わない。確定した結果は、記録したバージョンで再計算して一致することを、定期に抜き取りで確かめる。
- エンジンの古いバージョンで計算した結果を再現するため、エンジンのイメージは保存期間の間残す（保存期間は [intent.md](../intent.md) の L5）。

### 規則表

- 法定の値は、規則表としてデータで持ち、コードに書き写さない。

| 規則表 | 適用の単位 | 主なキー |
| --- | --- | --- |
| 源泉徴収税額表（月額表、日額表） | 支払の日の属する年 | 社会保険料等の控除後の給与の額の区分、扶養親族等の数、甲欄・乙欄 |
| 賞与の算出率の表 | 同上 | 前月の社会保険料等の控除後の給与の額、扶養親族等の数、甲欄・乙欄 |
| 電子計算機等による計算の特例 | 同上 | 給与所得控除の額などの式の係数 |
| 健康保険の料率 | 保険料の「何月分」 | 保険者（協会けんぽの都道府県、健康保険組合） |
| 介護保険の料率、子ども・子育て支援金率 | 同上 | 保険者 |
| 厚生年金の料率 | 同上 | — |
| 標準報酬月額の等級表 | 同上 | 報酬月額の区分（健康保険と厚生年金で別） |
| 雇用保険の料率 | 適用の区切り（payroll-jp-rules の領域で確かめる） | 事業の種類 |

- 規則表は、公的な資料（国税庁の Excel、協会けんぽの保険料額表など）から取り込む。取り込みの記録に、出典の URL、取得日、ファイルのハッシュ、取り込んだ人と確かめた人を残す。2 人で確かめる。
- 規則表は、適用開始の日付（または「何月分」）でバージョンを持つ。有効期間は重ならない。
- テナントが入力する値（健康保険組合の料率、特約の端数の規則）も、同じ形でバージョンを持つ。
- 規則表のリリースは、コードのリリースと分ける。法令の公表から適用までに、規則表だけを出せる（delivery の領域）。

### 計算の構造

- 1 人の計算は、項目（支給、控除、途中の値）の依存のグラフを、決まった順序で評価する。循環する依存は、定義の保存のときに拒む。
- 法定の計算（源泉所得税、社会保険料、雇用保険料、住民税の月割り、割増賃金の最低の率）は、システムのコードに持つ。テナントは変えられない。
- テナントが定義できる項目は、限られた式（定額、率 × 基礎、時間 × 単価、表引き、日割り）の宣言だけにする（[ADR-0001](0001-platform-and-stack.md)）。
- 条件の組み合わせで決まる規則（甲欄・乙欄、介護保険の対象の年齢の判定、雇用保険の加入、端数の規則の選択、割増率）は、`spec.md` の決定表に書き、表駆動テストで確かめる。
- 金額は `packages/money` の型で扱い、丸めは名前付きの関数で行う（[ADR-0001](0001-platform-and-stack.md)）。
  - 例：社会保険料の被保険者負担分 ＝ 標準報酬月額 × 料率 ÷ 2 を固定小数点で求め、`roundSocialInsuranceEmployeeShare` で円にする。料率の合計（健康保険＋子ども・子育て支援金など）を先に足すか、項目ごとに丸めるかは、payroll-jp-rules の領域で保険者の資料から決める。

### 遡及（a）

- 確定した期間にかかる変更（過去日付の変更、訂正、取消。[ADR-0002](0002-effective-dated-data-model.md)）が入ったら、遡及の候補として記録する。
- 次の計算の入力の固定のときに、確定した各期間を、新しい `known_at` の入力で再計算し、確定した結果との差を項目ごとに求める。差を、当期の遡及の差額の項目として出す。確定した過去の結果は変えない。
- 差額に関わる税と保険の扱い（遡及の差額を支払月の給与として源泉徴収する、社会保険の随時改定の候補の検知）は、payroll-jp-rules の領域の決定表で決める。随時改定は候補を示すだけで、届出の判断は担当者が行う。
- b は、支払済みの額と明細、振込、仕訳、税と保険の届出が変わってしまうので採らない。

### お金の記録

- 確定した結果から、給与の実行ごとに仕訳を作る。仕訳は借方と貸方が一致することを、コミットの時に DB のトリガーで確かめる（Stripe の台帳の方式に倣う。[systems/stripe の ledger.md](../../../stripe/docs/architecture/ledger.md)）。
- 仕訳は追記のみ。取消は逆仕訳で行う。
- 勘定科目の対応（給与手当、賞与、法定福利費、預り金の各種、未払金）は、テナントの設定で持つ。預り金と法定福利費の扱いは、税理士の確認待ち（[intent.md](../intent.md) の L9）。

### 並行稼働

- 本番の切り替えの前に、現行のシステムの計算の結果（従業員 × 項目 × 月）を取り込み、本システムの結果と比べる。
- 差異は、従業員と項目ごとに、分類（本システムの誤り、現行のシステムの誤り、設定の差、端数の規則の差、入力の差）と説明を付ける。説明は担当者が付け、QA が承認する。
- 切り替えの条件は、3 か月（賞与の月を 1 回以上含む）続けて、説明のない差異が 0 件であること（NFR-001）。
- 並行稼働の比較は本番の環境の中だけで行い、差異の報告の外への出力は、個人を特定できる値を除く。

### ゴールデンデータセット

- 合成の従業員（雇用区分、扶養、年齢の境界（40 歳・65 歳・70 歳・75 歳）、保険者、等級の境界、乙欄、月の途中の入退社、休職、残業の境界（月 60 時間）、賞与、遡及）と、期待値の組を持つ。
- 期待値は、社労士・税理士、または現行の検証済みの給与システムで確かめたものにする。確かめた人と方法を記録する。
- 給与計算に触れる PR では、ゴールデンデータセットの全件一致を必須のチェックにする。期待値を実装に合わせて書き換えない。

### 2・3 を選ばなかった理由

- **2（DB を読みながら計算）**：計算の途中でデータが変わると、結果が読む時刻に依存する。再計算で同じ結果になる保証がなく、遡及の差の計算の土台にならない。
- **3（汎用のルールエンジン）**：法定の計算をテナントの規則として書かせると、法令の改正を全テナントに届けられない。テナントの規則の正しさの検証も難しい。本家も含め、1 つのコードラインで法定の計算を配る考え方と合わない。

## Consequences

- 良くなること：
  - 給与の結果を、いつでも同じ入力・バージョンで再現できる。監査と、従業員からの問い合わせへの説明ができる。
  - 遡及の差が、確定した結果と新しい知識の差として機械的に出る。
  - 法令の改正が、規則表のバージョンの追加として、全テナントに同じく届く。
- 引き受けるコスト：
  - 入力のスナップショットの保存（1 人 1 回の計算で数 KB〜数十 KB。S1 で月に数十 GB）と、エンジンのイメージの長期の保存。
  - 遡及の再計算で、過去の期間の数だけ計算が増える。遡及の範囲の上限（例：過去 24 か月）を payroll-engine の領域で決める。
  - 規則表の取り込みと 2 人の確認の運用が、改正のたびに要る。
  - 年末調整は、1 年分の結果と申告から計算する別の計算になる。MVP の後の Epic で、同じ純粋な計算の形で足す。

## Confirmation

- CI：ゴールデンデータセットの全件一致。決定表（`DT-*`）の全行の表駆動テスト。
- 性質ベーステスト：
  - 任意の入力で、同じ入力を 2 回計算した結果が一致する。
  - 任意の入力で、差引の支給額 ＝ 支給の合計 − 控除の合計。
  - 任意の給与の実行で、仕訳の借方と貸方が一致する。
  - 任意の遡及で、「確定した結果＋遡及の差額」が「新しい知識で計算し直した結果」と一致する（税・保険で差額の扱いが別の規則になる項目を除く）。
- lint：`packages/payroll` の中で、`Date.now`、`new Date()`（引数なし）、`Math.random`、DB のクライアント、`process.env` の使用を禁止する。
- 本番：確定した結果の抜き取りの再計算で、不一致が 0 件。
