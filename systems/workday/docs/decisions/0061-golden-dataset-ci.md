# ADR-0061: ゴールデンデータセットを事例ごとの入力・規則表のバージョン・期待値・確認の出所で持ち、分類の網羅を検査し、期待値の変更とコードの変更を別の PR にする

詳細は [delivery.md](../architecture/delivery.md) の 4 節。

## Context

- NFR-001 と K1 は、ゴールデンデータセットで計算誤り 0 件を求める。[ADR-0004](0004-payroll-engine.md) と [AGENTS.md](../../AGENTS.md) は、給与計算に触れる PR でゴールデンデータセットの全件一致を必須のチェックにし、期待値を実装に合わせて書き換えず、期待値の変更は QA が承認し、法令の解釈に関わるものは社労士・税理士の確認を記録すると決めた。
- 形（どこに、何を、どう置くか）と、網羅の確かめ方と、期待値の変更の手順は決まっていない。
- 同じ PR で、エンジンのコードと期待値の両方を変えると、「実装に合わせた期待値の書き換え」と「正しい修正」を、レビューで見分けにくい。エージェントは、失敗するテストの期待値を直しがちである。
- 期待値は、支払日によって違う規則表のバージョンに依存する（令和 7 年 12 月と令和 8 年 1 月の支払いなど）。

## Options

形：

1. **事例ごとに、正規の入力の文書・規則表のバージョン・設定・期待値（項目ごとの円）・確認の出所を置く。分類の一覧（境界の一覧）を持ち、すべての分類に事例があることを CI で確かめる**
2. 表計算の 1 つのファイルに、人と期待値を並べる
3. 現行のシステムの出力をそのまま期待値にする

期待値の変更：

- a. **期待値の変更とコードの変更を別の PR にする。期待値の PR は QA の承認と確認の記録を要し、一時に外す事例は 5 営業日で期限を切る**
- b. 同じ PR で、QA の承認だけを足す

## Decision

1 と a を採用する。

- `golden/cases/<id>/` に `input.json`（RFC 8785）・`rules.yaml`・`settings.json`・`expected.json`・`provenance.yaml` を置く。入力は合成の人だけ。
- `manifest.yaml` の分類：ADR-0004 の境界の一覧と、各領域の決定表の境界の行。CI は分類ごとに 1 件以上を確かめる。
- 比較は項目ごとの完全一致。許容の幅はない。
- 実行の条件：依存のグラフで給与の計算に届く PR で必須。夜間は全件。
- 期待値の変更は `golden:expected-change` のラベルで、QA の承認を要し、解釈に関わるものは社労士・税理士の確認の記録（役割、日、記録の ID）を `provenance.yaml` に足す。
- 期待値の PR を先に出し、`pending_fix` の印でその事例だけを一時に外し、コードの PR で戻す。`pending_fix` は 5 営業日まで。
- 事例の削除も QA の承認を要し、分類の網羅の検査を通す。
- 本番の監視用のテナントの合成の給与の実行（[ADR-0059](0059-payroll-run-slo-and-synthetic-run.md)）は、この事例の代表を使う。
- 2 を採らない理由：バージョンの管理と差の読みが難しい。規則表のバージョンと設定を事例ごとに持てない。
- 3 を採らない理由：現行のシステムの誤りを正解にしてしまう。現行との比較は並行稼働（[ADR-0029](0029-parallel-run-and-compute-partitioning.md)）で行い、差を分類する。
- b を採らない理由：実装に合わせた書き換えを、レビューで見分けにくい。

## Consequences

- 良くなること：
  - 期待値の出所（誰が、何で確かめたか）が事例ごとに残る。
  - 分類の漏れ（ある境界の事例がない）を CI で見つけられる。
  - 期待値の書き換えが、コードの変更と切り離されて見える。
- 引き受けるコスト：
  - 事例の作成と、社労士・税理士の確認の手間。規則表の改正ごとに、新しい期間の事例を足す（[ADR-0062](0062-rule-table-release-calendar.md)）。
  - 期待値の変更に 2 つの PR が要り、修正のリードタイムが延びる。

## Confirmation

- CI：分類の網羅、期待値の完全一致、`pending_fix` の期限、`golden:expected-change` の PR の QA の承認と `provenance.yaml` の記録の有無。
- 指標：`main` での失敗 0 件、確認の記録のない期待値の変更 0 件（[delivery.md](../architecture/delivery.md) の 10 節）。
