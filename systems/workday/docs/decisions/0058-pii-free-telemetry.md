# ADR-0058: 個人情報を出さない計装を型・Collector・URL の規則・走査の 4 層で守り、保管庫のテレメトリーは保管庫のアカウントに閉じる

詳細は [observability.md](../architecture/observability.md) の 2・4 節。

## Context

- [AGENTS.md](../../AGENTS.md) は、個人番号をログ・エラーの本文・トレースの属性・メトリクスのラベルに書かないこと、氏名・住所・生年月日・口座・給与・健康・扶養をログに出さないことを求める。NFR-008 はログ・トレースに個人情報が出た件数を 0 件にすることを求める。
- 個人情報の区分は P0〜P4 で、ログに出してよいのは P0・P1 の ID とコードだけ（[ADR-0051](0051-threat-model-and-pii-classification.md)）。
- 他の題材（Auth0 の ADR-0061）は、秘密を出さない計装を型・Collector・AWS のアクセスログ・走査の 4 層で守った。
- 名前や住所は正規表現で見つけにくい。個人番号は形（12 桁とチェックデジット）で見つけられるが、他の 12 桁の数と区別しにくい。
- ALB・CloudFront のアクセスログは URL のクエリを残す。API の URL に個人情報が入れば、ログに残る。
- 給与の額は、テナントやグループの合計でも、少人数なら個人の額になる。

## Options

1. **型（`Pii<T>`、型付きのイベント）、Collector の属性の許可リスト、URL に個人情報を入れない API の規則、ログの走査（個人番号の形と既知の鍵の名前）。走査を印つきの合成の番号で毎日確かめる。保管庫のテレメトリーは保管庫のアカウントに閉じ、外へはメトリクスだけ**
2. ログの出力の直前に、正規表現で個人情報を伏せる
3. 走査だけで見つけて消す

## Decision

1 を採用する。

- ロガーは型付きのイベントだけを受け、項目は P0・P1 の ID とコード。`Pii<T>` は文字列化で `[REDACTED]` になる。
- 給与の額は、個人のものも合計もメトリクス・ログに出さない。件数と時間だけ。
- API のパスの引数は ID だけ。検索の条件は `POST` の本文。lint で確かめる。
- 走査：個人番号の形（12 桁、チェックデジット、文脈の鍵）と、既知の鍵の名前に値が付いたもの。個人番号の形は SEV2。
- 走査の生存の確認：毎日、合成の生成器の番号を専用のロググループに書き、検出を確かめる。
- 保管庫のログとトレースは保管庫のアカウントの中に置き、shared の Grafana へはメトリクスだけを出す。
- 2 を採らない理由：伏せる規則に合わない形（名前、全角の数字）が漏れる。伏せる処理の誤りで、ログがまるごと消えることもある。出さない形にするほうが確か。
- 3 を採らない理由：見つけた時点で、ログは複数の場所（CloudWatch、Firehose、log-archive の Object Lock）に写っている。Object Lock の上のものは消せない。

## Consequences

- 良くなること：
  - 個人情報がテレメトリーに入る経路が、型と Collector の 2 か所で止まる。
  - 走査が止まったことに気づける。
- 引き受けるコスト：
  - 障害の調査で、個人を ID でしか引けない。額の調査はテナントの許可の参照で行う（[ADR-0053](0053-operator-access-and-vault-break-glass.md)）。
  - 個人番号の形の走査は、無関係な 12 桁の数を拾う。文脈の鍵で確度を分け、低い確度はチケットにする。
  - log-archive の Object Lock に入った漏れは消せない。アクセスの制限と記録で扱う（[runbooks/incident-response.md](../runbooks/incident-response.md)）。

## Confirmation

- CI：テストの実行中のログ・スパン・スナップショットを走査し、個人番号の形・既知の鍵の名前の値が 0 件。ログのイベントの型に P2 以上の型がない。パスの引数が ID でないルートがない。
- 本番：走査の検出 0 件、合成の番号の毎日の検出 100%。
