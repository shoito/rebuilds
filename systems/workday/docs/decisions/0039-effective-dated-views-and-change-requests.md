# ADR-0039: 画面は時点を URL に持ち、将来の変更と保留中の案件を重ねて示し、変更の申請は有効日を必須にする

詳細は [self-service-ui.md](../architecture/self-service-ui.md) の 5 節。

## Context

- 人事のデータは有効時間と記録時間の 2 軸を持つ（[ADR-0002](0002-effective-dated-data-model.md)）。API は `effective_on` と `known_at` を受ける（[ADR-0008](0008-point-in-time-queries-and-activation-timers.md)）。
- 画面が「今日の値」しか見せないと、次の誤りが起きる。
  - 3 月に 4 月 1 日付の異動が入っているのに、マネージャーが気づかずに別の異動を起票する。
  - 本人が住所の変更を申請中なのに、もう一度申請する。
  - 担当が、過去の日付の変更と訂正を取り違える（意味と社会保険の届出が違う。[ADR-0007](0007-change-correction-rescind-semantics.md)）。
- 「今日」を有効日の既定にすると、将来日付・過去日付の申請で誤った日付が黙って入る。
- 過去の知識（`known_at`）は監査の権限を要する（ADR-0008）。

## Options

1. **時点を URL の `asOf` に持ち、見出しに常に示す。将来の変更と保留中の案件を今の値に重ねて示す。有効日を必須にし、訂正を別の操作にする**
2. 今日の値だけを示し、履歴は別の画面にする
3. 時点を利用者の設定（セッション）に持つ

## Decision

1 を採用する。

- 時点は `asOf=YYYY-MM-DD`（既定は今日）。`knownAt` は `audit` の権限の利用者にだけ出し、出すときは画面に帯を出す。
- 項目ごとに、完了した将来の差分（「4 月 1 日から：…」）と、保留中の案件（「申請中：…」）を重ねる。API は、項目ごとの将来の差分と保留中の案件の要約を、権限の射影を通して返す。
- 変更の申請の画面は有効日を必須にする。候補をボタンで出す。過去の日付は差額の注意を出し、90 日より前は権限を要する。
- 訂正は履歴の差分の行から始める別の操作にする。本人のセルフサービスには出さない。
- 起票の画面は読んだ版の ID を案件に持たせる。
- 2 を採らない理由：上の誤りが防げない。履歴の画面まで行く人は少ない。
- 3 を採らない理由：共有したリンクで時点が変わる。画面ごとに時点が違うことが見えにくい。

## Consequences

- 良くなること：
  - 将来日付の変更と保留中の案件の見落としが減る。
  - 有効日の入力の誤りが、既定の値のせいで起きない。
- 引き受けるコスト：
  - 画面の API が、項目ごとの将来の差分と保留中の案件を返す分、応答が大きくなる。1 人の画面に限る（一覧には出さない）。
  - 有効日の入力が 1 手増える。K8（3 分以内）の計測で見る。

## Confirmation

- 決定表のテスト：DT-UI-001（有効日の扱い）。
- 性質ベーステスト：PROP-UI-002（画面の表示は同じ `effective_on` の API の応答と一致する）。
- E2E：将来日付の異動がある従業員の画面で、今日と 4 月 1 日の `asOf` の表示が違い、将来の変更の表示が出る。
