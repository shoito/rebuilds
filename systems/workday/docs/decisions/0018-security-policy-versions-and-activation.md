# ADR-0018: 権限の方針をバージョンで持って別の人が有効化し、所属とロールの変更は業務プロセスで効かせる

詳細は [security-model.md](../architecture/security-model.md) の 4.4・8 節。

## Context

[ADR-0005](0005-security-and-my-number.md) は、権限の変更を保留と有効化に分け、編集した人と有効化した人を別にできると決めた。

本家は、ドメイン・業務プロセスの方針の変更を有効化まで保留し、有効化の時刻を記録し、前の時刻を有効化して戻せる。方針の編集と有効化は別のドメインで、別のグループに持たせられる。一方、グループの定義と所属の変更は有効化を待たずにすぐ効き、時刻の戻しの影響を受けない（[Security Policy Configuration and Activation](https://doc.workday.com/workday-education/en-us/course-manuals/security-for-administrators/security-policy-configuration-and-activation.html)、2026-09-28 に確認）。

決めることは次のとおり。

- 方針のバージョンの持ち方と戻し方。
- 所属・ロールの割り当ての変更を、どう統制するか。すぐ効く所属の変更は、職務分掌の検査と承認の抜け道になりうる。

## Options

方針：

1. **バージョン（下書き → 有効化の業務プロセス → 有効）。編集者と承認者を別にする。戻しは前のバージョンの写しを有効化する**
2. 変更をすぐ効かせ、監査ログで後から確かめる

所属・ロールの変更：

- a. **業務プロセス（承認つき）で変え、完了で効く。有効化は待たない**
- b. 本家と同じく、すぐ効かせる（承認なし）
- c. 方針のバージョンに含め、有効化で効かせる

## Decision

1 と a を採用する。

- `security_policy_versions` に、グループへの権限の付与と職務分掌の規則表を 1 つのバージョンとして持つ。下書きはテナントに 1 つ。
- 有効化は `security_policy_activation` の業務プロセス。承認者は `security.activation` の権限を持ち、編集者と別（職務分掌の規則 S3）。委任できない。
- 承認の前に、新しいバージョンの権限の表を背景で作り、職務分掌の検査（方針の有効化の検査点）を行い、前のバージョンとの差（権限を得る・失う利用者）を示す。
- 完了のトランザクションで有効なバージョンの指し先を切り替える。進行中の要求は、要求の始めのバージョンで判定を終える。
- 戻しは、前のバージョンの中身を写した新しい下書きを同じ手順で有効化する。有効化したバージョンは書き換えない。
- ロールの割り当て（有効日付）とグループの所属は、それぞれの業務プロセスで変える。完了で職務分掌の検査を行い、影響を受けた人の権限の表を作り直す。
- 2 を採らない理由：誤った権限の付与（全社の給与の閲覧など）が即時に効き、後から気づいても見られた後になる。編集と有効化の分離もできない。
- b を採らない理由：所属の変更だけで権限を得られ、承認と職務分掌の検査の抜け道になる。
- c を採らない理由：入社・異動・上長の交代のたびにロールが変わる。これを方針の有効化の単位に入れると、日常の人事の操作がすべて権限の管理者の有効化を待つことになる。

## Consequences

- 良くなること：
  - 権限を広げる変更は、必ず 2 人を経て、差を見たうえで効く。
  - 戻しが、バージョンの写しの有効化という 1 つの手順になる。
- 引き受けるコスト：
  - 管理者が 1 人のテナントは、方針を変えられない（持ち越し。security-model の 16 節）。
  - 下書きがテナントに 1 つなので、複数の管理者の並行の編集は楽観ロックで衝突する。

## Confirmation

- 性質ベーステスト：PROP-SEC-006（下書きは有効化まで判定を変えない。写しの有効化で前のバージョンの判定に戻る）。
- 決定表のテスト：DT-SEC-004（方針の状態の遷移）。
- 結合テスト：編集者が自分の下書きの有効化を承認しようとすると拒まれる。
