# ADR-0063: 給与に効くフラグとエンジンのイメージを実行ごとに固定し、テナントには影の比較の後に期間の境目で広げ、支給日の前は給与の経路のデプロイを凍結する

詳細は [delivery.md](../architecture/delivery.md) の 5・8 節。

## Context

- 給与の結果は、入力の文書・規則表の版・エンジンの版・テナントの計算の設定の版から決まり、再計算で 1 円も違わない（[ADR-0004](0004-payroll-engine.md)、[ADR-0026](0026-payroll-run-stages-and-input-snapshot.md)）。フラグは、この 4 つのどれにも入っていない。フラグで計算の振る舞いを変えると、再現の前提が崩れる。
- 実行は数日にわたる（固定、計算、確認、確定）。途中でフラグやエンジンのイメージが変わると、同じ実行の中の人によって計算が違いうる。
- 遡及は、元の入力を今のエンジンで再現できることを前提にする（[ADR-0028](0028-retro-deltas-and-bonus-runs.md)）。
- 他の題材（[Auth0 の ADR-0066](../../../auth0/docs/decisions/0066-tenant-canary-release.md)）は、テナントを単位にしたカナリアで広げる。給与は月に 1 回しか結果が出ないので、要求の率のガードでは誤りに気づくのが遅い。
- 支給日の直前の給与の経路の障害は、振込の締め切りに直結する（NFR-004、NFR-006）。

## Options

1. **給与に効くフラグの値とエンジンのイメージのダイジェストを、入力の固定のときに実行の設定の版に記録し、実行の最後まで固定する。テナントで有効にする前に、直近の確定した期間をフラグあり・なしで計算し直す影の比較を行い、給与の期間の境目で有効にする。本番の従業員の 20% 以上が 3 営業日以内に支給日を迎える日は、給与の経路のデプロイを凍結する**
2. 給与の計算にフラグを使わない（新しい計算はすべて規則表かテナントの設定の版で表す）
3. 他の振る舞いと同じく、フラグを要求ごとに評価する

## Decision

1 を採用する。2 は原則として目指し（法令の値は規則表、テナントの選択は設定の版）、フラグは新しい計算の方式を段階的に広げるときだけに使う。

- 給与に効くフラグは `payroll` の種類で登録し、値を実行の設定の版のハッシュに含める。結果の記録から、どのフラグの値で計算したかが分かる。
- Payroll Compute のタスクは、実行に記録したイメージのダイジェストで起こす。新しいイメージは次に入力を固定する実行から使う。
- 影の比較：`parallel` の実行で、直近の確定した期間をフラグあり・なしで計算し、差を給与の担当と QA が確かめる。説明できない差があれば有効にしない。
- 有効にする時期は、テナントの次の実行の入力の固定の前（期間の途中では変えない）。カナリアの各段で最低 1 回の支給を経る。
- 凍結の日は、支給日の予定から毎晩計算して暦に出す。凍結の日の給与の経路（`payroll:calc`、振込ファイル、明細、Payroll Compute のイメージ、給与の DB のスキーマの contract）のデプロイは、Ops の責任者と QA の承認の例外だけ。脆弱性の Critical の修正は凍結の対象外。
- 3 を採らない理由：同じ実行の中で人によって計算が違いうる。記録から再現できない。

## Consequences

- 良くなること：
  - 実行の結果が、フラグとエンジンの変更に影響されず、記録から再現できる。
  - 新しい計算の方式の影響を、テナントの実データの上で、支払いの前に見られる。
  - 支給日の直前の障害の危険を減らす。
- 引き受けるコスト：
  - 給与に効くフラグの広がりは遅い（各段で 1 か月）。
  - 凍結の日が多い月末に、給与の経路の修正が溜まる。凍結の外の日に計画して出す。
  - 影の比較の説明の作業が、給与の担当と QA に要る。

## Confirmation

- 結合テスト：実行の途中でフラグを切り替えても、同じ実行の中の再計算の結果が変わらない。記録したダイジェストと違うイメージのタスクは、束を拒む。
- CI：凍結の日に、給与の経路のパスを含む本番のデプロイのワークフローが、例外の承認なしに止まる。
- 指標：影の比較をせずに有効にした件数 0 件、凍結の期間の給与の経路のデプロイ 0 件（例外を除く）。
