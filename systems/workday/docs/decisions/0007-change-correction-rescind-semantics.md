# ADR-0007: 変更・訂正・取消を差分の種類で区別し、取消は依存の決定表で拒む

詳細は [object-model-and-effective-dating.md](../architecture/object-model-and-effective-dating.md) の 6 節。

## Context

[ADR-0002](0002-effective-dated-data-model.md) は、訂正を「元の差分を置き換える差分」、取消を「差分に取消の印を付けて畳み込み直す」とし、取消は後の差分が依存しているとき拒むと決めた。依存の判定の規則は、この領域で決定表にするとした。

残っている論点は次のとおり。

- 訂正で有効日を動かしてよいか。動かした先が、同じ項目の別の変更をまたぐと、前後が入れ替わる。
- 「依存」を何で判定するか。同じ項目に触れる後の変更を全部依存とすると、取消がほぼできなくなる。何も依存としないと、昇格を取り消したのに、その昇格を前提にした昇給が残る。
- 本家では、確定した案件の取消は元に戻せず、取消・訂正は承認に回らない（大学の利用の手引き [Correct, Cancel, and Rescind](https://it.tamus.edu/workdayservices/training/job_aid/correct-cancel-and-rescind/)、2026-09-28 に確認。二次資料）。後の取引から順に取り消す運用の案内もある（二次資料。未検証）。

## Options

依存の判定：

1. **起票の時に見ていた版（`based_on_version_ids`）と、項目の重なりと、業務プロセスの種類の `depends_on` の宣言を組み合わせる**
2. 同じ主体・facet の、後の有効日の差分をすべて依存とする
3. 依存を判定せず、取消を常に受ける。結果は担当が確かめる

訂正の有効日：

- a. **同じ項目の別の差分をまたがない範囲で動かせる**
- b. 動かせない（取消して入れ直す）
- c. 自由に動かせる

## Decision

1 と a を採用する。

- 差分は `kind`（`change`・`correction`・`end`）を持つ。訂正は、元の差分に取消の印を付け、`corrects_change_id` を持つ新しい差分を同じトランザクションで足す。
- 訂正（DT-TEMP-003）：値だけの訂正は受ける。有効日の訂正は、古い日と新しい日の間（両端を含む）に同じ項目の生きている差分がなければ受ける。触れる項目を増やす訂正は拒む。入社の差分の有効日の訂正は、coverage の子の最初の差分も同じ日に動かす。
- 取消（DT-TEMP-004）：取り消す差分 R より後（有効日が同じか後）の生きている差分 L について、上から評価する。
  1. R が入社・再雇用なら、L があれば依存（後から取り消す）。
  2. L が退職・終わりなら依存しない（警告だけ）。
  3. L の `based_on_version_ids` が R の作った版を含み、項目が重なれば依存。
  4. 含むが項目が重ならなければ依存しない。
  5. 含まなければ依存しない。
  6. 業務プロセスの種類が `depends_on` を宣言していれば、その相手は依存。
- 依存で拒むときは、依存する案件の一覧を返す。連鎖をまとめて取り消す操作は MVP では持たない。
- どの操作も、差分の追記と印の埋め込みだけで行い、過去の知識を変えない。
- 取消・訂正の承認の要否は業務プロセスの定義で決める（[ADR-0003](0003-business-process-engine.md)。給与・口座の訂正は既定で承認）。
- 2 を採らない理由：住所の変更の後の給与の変更のように、関係のない後の変更で取消が止まる。担当が関係のない案件まで取り消して入れ直すことになり、誤りが増える。
- 3 を採らない理由：昇格の取消の後に、昇格を前提にした等級の手当が残るなど、矛盾した状態を黙って作る。
- b を採らない理由：入社日の 1 日の誤りのような、よくある訂正のたびに、後の案件をすべて取り消して入れ直すことになる。
- c を採らない理由：またいだ変更との前後が入れ替わり、訂正の意味（「もともと誤っていた」）を越えて履歴の意味が変わる。

## Consequences

- 良くなること：
  - 取消が、本当に前提にしている後の変更があるときだけ止まる。
  - 訂正と過去日付の変更を区別して記録でき、社会保険の届出の訂正と監査に使える。
- 引き受けるコスト：
  - 起票の画面・API が、読んだ版の ID を案件に持たせる必要がある。版が完了までに変わったら、確かめ直しの手順が要る（[business-process-engine.md](../architecture/business-process-engine.md) の 6.3 節）。
  - 業務プロセスの種類の `depends_on` の宣言を、既定の定義で持ち、保守する。

## Confirmation

- 決定表のテスト：DT-TEMP-003・004 の全行。
- 性質ベーステスト：PROP-TEMP-003（過去の知識は変わらない）、PROP-TEMP-007（許される順で全部取り消すと差分のない状態に戻る）。
- 結合テスト：依存で拒んだ応答が、依存する案件の一覧を返す。
