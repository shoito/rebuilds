# ADR-0020: 機微なドメインの閲覧を記録し、判定に理由を付けて説明の報告を出し、本番の代理のログインを読み取りに限る

詳細は [security-model.md](../architecture/security-model.md) の 6・9・10 節。

## Context

NFR-008 は、権限のない利用者に給与・口座・健康・扶養の情報が見えた事象を 0 件にすることを求める。NFR-010 は、人事・給与・権限のすべての変更の記録を求める。変更の記録は業務プロセスのイベントと有効日付の差分で残る。閲覧は残らない。

- 権限の設定の誤りで機微な情報が見えてしまったとき、誰が何を見たかを調べられなければならない。個人情報の漏えいの報告の判断にも要る（[intent.md](../intent.md) の L10）。
- テナントの管理者と監査人は、「この人は何を見られるか」「この項目を誰が見られるか」を確かめたい（[ADR-0005](0005-security-and-my-number.md) の Consequences）。
- 権限の管理者が、ある利用者の見え方を確かめる手段（代理のログイン）が要る。本家の代理のログインの条件は確かめられなかった（未検証）。代理のログインは、他人の権限で機微な情報を見る経路になる。

## Options

閲覧の記録：

1. **機微なドメイン（給与、口座、扶養、住所、個人の全氏名・生年月日、休職の種類、退職の理由、要配慮、`known_at`）の閲覧だけを、要求ごとに記録する。拒否はまとめて記録する**
2. すべての閲覧を記録する
3. 閲覧を記録しない

代理のログイン：

- a. **検証用の環境では操作も可。本番では読み取りだけ・30 分・理由つき・機微なドメインを見せない。運用者は使わない**
- b. 本番でも操作を許す
- c. 代理のログインを持たず、説明の報告だけにする

## Decision

1 と a を採用する。

- 機微なドメインの閲覧を、要求ごとに（利用者、実際の操作者、対象、ドメイン、経路、許した権限の ID）記録する。一覧・レポート・一括の出力は、要求ごとに条件と件数と対象の一覧のハッシュを記録する。値は記録しない。拒否は利用者・ドメイン・1 時間ごとの件数にまとめる。
- 記録は監査ログの経路に書く（保管と改ざんの検知は [audit-and-retention.md](../architecture/audit-and-retention.md)）。
- 判定は許した権限の ID か拒否の理由を返す。これを使い、「この人は何を見られるか」「この項目を誰が見られるか」「バージョンの差」「職務分掌の違反」「1 件の判定の説明」の報告を出す。報告はデータを出さない。報告の出力も記録する。
- 代理のログイン：検証用の環境では、`security.admin` の人が理由つきで 2 時間、操作も可。本番では、`security.admin` と `audit` の両方を持つ人が、読み取りだけ・30 分・理由つきで使える。機微なドメインと `my_number` は見せない。開始と終了をテナントの監査の担当に通知する。本システムの運用者は代理でログインしない。
- 2 を採らない理由：組織図や勤怠の一覧まで記録すると、量が大きく（S1 で 1 日数千万件の見込み）、調べたい機微な閲覧が埋もれる。
- 3 を採らない理由：設定の誤りによる漏えいの範囲を特定できない。
- b を採らない理由：他人の名前での操作が、業務プロセスの起票者・承認者の記録と職務分掌の判定を曖昧にする。
- c を採らない理由：画面の見え方（メニュー、ボタン、項目の伏せ方）は、報告だけでは確かめにくい。問い合わせの対応が遅れる。

## Consequences

- 良くなること：
  - 機微な情報の閲覧の範囲を、事後に特定できる。
  - 権限の設定を、データを見ずに説明できる。
- 引き受けるコスト：
  - 閲覧の記録の量（S1 で 1 日数百万件）を監査ログの容量に入れる。
  - 本番の代理のログインでは機微なドメインが見えないので、その部分の見え方は説明の報告で確かめる。

## Confirmation

- 結合テスト：機微なドメインを読む API・レポート・一括の出力のすべての経路で、閲覧の記録が 1 件以上できる（経路の一覧を CI で列挙し、記録のない経路を失敗させる）。
- 結合テスト：本番の代理のログインで、書き込みの操作と機微なドメインの読み取りが拒まれる。
- 本番：代理のログインの件数と理由を月次で監査の担当が確かめる。
