# ADR-0002: 人事のデータを有効時間と記録時間の 2 軸で持ち、変更の差分を有効日の順に畳み込む

## Context

人事のデータは「いつから有効か」を持つ。次の操作が日常的にある。

- **将来日付の変更**：3 月に、4 月 1 日付の異動・昇給を入力する。3 月の間は旧の値が有効で、4 月 1 日から新の値になる。
- **過去日付の変更（遡及）**：6 月に、4 月 1 日付の昇給を入力する。確定した 4 月・5 月の給与に差額が出る。
- **訂正**：入社日や等級を誤って入力していた。値そのものを直す。
- **取消**：異動の発令そのものを無かったことにする。
- **時点の問い合わせ**：「4 月 1 日時点の組織図」「5 月の給与計算のときに、システムは 4 月の等級を何と知っていたか」。

本家は、すべてのデータを有効日付つきのオブジェクトとして持つ。変更は非破壊で、有効日と入力日を分け、前後の値・変更者・時刻を監査の記録に残す（[Concept: Auditing](https://doc.workday.com/admin-guide/en-us/manage-workday/tenant-configuration/auditing/dan1370797846272.html)、2026-09-28 に確認）。保存は、少数の汎用のテーブル（インスタンス、属性、関係）に追記で書き、アプリはメモリーの中のオブジェクトのグラフで動く（[ホワイトペーパー](https://www.workday.com/content/dam/web/en-us/documents/whitepapers/whitepaper_workday_technology_platform_devt_process.pdf)、2026-09-28 に確認。汎用のテーブルの数と追記の方式は [DBMS2, 2010](https://www.dbms2.com/2010/08/22/workday-technology-stack/) による古い第三者の記事で、現在の実装は未検証）。

この題材では、給与計算の再現性（[ADR-0004](0004-payroll-engine.md)）と遡及の検知のために、「ある時点で、システムが何を知っていたか」を正確に答える必要がある。

## Options

1. **有効時間だけ（effective-dated）。** 各行に有効期間を持ち、過去の値の変更は上書きする。変更の前後は監査ログに残す
2. **有効時間と記録時間の 2 軸（bitemporal）。** 現在の知識のテーブルと、追記のみの版のテーブルを持つ
3. **本家に近い汎用のオブジェクトの保存。** 型のない属性・関係のテーブルに、有効日付つきで追記し、メモリーの中のグラフで読む
4. **イベントソーシングだけ。** 業務のイベントを正本にし、状態は読むたびにイベントから作る

## Decision

2 を採用する。変更は、業務プロセスのイベントが持つ差分として記録し、主体と項目のまとまりごとに、有効日の順に畳み込んで期間を作る（4 の考え方を、書き込みの時点で使う）。

### 2 つの時間の軸

| 軸 | 意味 | 型 | 例 |
| --- | --- | --- | --- |
| 有効時間（valid time） | 現実の世界で、その値が有効な期間 | `daterange`（日単位。`[開始日, 終了日)`。終了がなければ上限なし） | 2026-04-01 から等級 3 |
| 記録時間（transaction time） | システムがその値を正しいと記録していた期間 | 版の `recorded_at`（`timestamptz`）と、置き換えられた時刻 | 2026-03-15 10:00 に記録し、2026-06-02 9:00 に訂正で置き換えた |

- 有効時間は日単位にする。人事の発令と給与の期間は日で決まる。日付はテナントの暦（S1 は日本時間）で解釈する。
- 本家の「有効日」と「入力日」に当たる。

### テーブルの形

データを、一緒に変わる項目のまとまり（facet）ごとのテーブルに分ける。例：`worker_job`（ポジション、職務、等級、所属、勤務地、雇用区分）、`worker_compensation`（基本給、手当）、`worker_personal`（氏名、住所）、`worker_payment_election`（振込先）。各 facet に、次の 3 つのテーブルを持つ。

```sql
-- 変更の差分（業務プロセスのイベントごと）。追記のみ
worker_job_changes (tenant_id, id, worker_id,
                    effective_on,            -- 有効日
                    event_id,                -- 業務プロセスのイベント（ADR-0003）
                    delta jsonb,             -- 変えた項目だけ（Zod のスキーマで検証）
                    seq,                     -- 同じ有効日の中の順序
                    recorded_at,
                    rescinded_at, rescinded_by_event_id,   -- 取消の印（ここだけ後から書く）
                    corrects_change_id)      -- 訂正なら、訂正された差分

-- 版（畳み込んだ結果の期間）。追記のみ
worker_job_versions (tenant_id, id, worker_id, valid daterange,
                     position_id, job_id, grade, org_id, ...,
                     recorded_at, superseded_at, superseded_by_event_id)

-- 現在の知識（superseded_at が空の版と同じ内容）。読み取りと制約のため
worker_job (tenant_id, worker_id, valid daterange, position_id, ..., version_id,
            PRIMARY KEY (tenant_id, worker_id, valid WITHOUT OVERLAPS),
            FOREIGN KEY (tenant_id, org_id, PERIOD valid)
              REFERENCES organization (tenant_id, id, PERIOD valid))
```

> 2026-09-28 の注記（名前の対応）：上の例の列の名前は、データモデルの正本（[data-model.md](../architecture/data-model.md) の 6 節の DM-8、[data-model/temporal.md](../architecture/data-model/temporal.md)）で次のとおり読み替える。`worker_id` → `subject_id`（facet によらず主体の ID）、`event_id` → `case_id`（業務プロセスの案件）、`rescinded_by_event_id` → `rescinded_by_case_id`、`superseded_by_event_id` → `superseded_by_case_id`、`job_id` → `job_profile_id`、`grade` → `grade_id`、参照先の `organization (tenant_id, id, ...)` → `organization (tenant_id, subject_id, ...)`。決定の中身は変えていない。例は起票の時の記録として残す。

- **差分を畳み込む。** 変更が入ったら、その主体・facet の差分のうち取消されていないものを、有効日と `seq` の順に並べ、影響を受ける日付から後の期間を作り直す。作り直した期間のうち、前と違うものだけを新しい版として追記し、古い版に `superseded_at` を書く。
  - 例：4 月 1 日付の等級の変更（将来日付）が入っている状態で、3 月 1 日付の所属の変更を後から入れる。所属の差分は 3 月 1 日から効き、4 月 1 日の等級の差分は所属に触れないので、4 月 1 日以降の期間も新しい所属になる。期間を丸ごと複製して持つ方式では、ここで 4 月以降の所属が古いまま残る誤りが起きやすい。
- **現在の知識のテーブル**は、版のうち置き換えられていないものと同じ内容を持つ。PostgreSQL 18 の時間の制約（`WITHOUT OVERLAPS` の主キー、`PERIOD` の外部キー）で、期間の重なりと、参照先（組織、ポジション）が存在しない期間への所属を DB で拒む。Aurora で使えなければ、`EXCLUDE USING gist` と、トリガーでの包含の検査で代える（E1 の PoC）。
- **追記のみ。** 差分と版のテーブルは、アプリのロールから `UPDATE`・`DELETE` の権限を外す。例外は、取消の印（`rescinded_at`）と、置き換えの印（`superseded_at`）を空から埋める更新だけで、トリガーで他の列の変更と、埋めた後の変更を拒む。
- 有効日付を持たないデータ（打刻の生の記録、給与の結果、監査ログ）は、ただの追記のテーブルにする。

### 操作の意味

| 操作 | 何をするか | 過去の知識 | 給与への影響 |
| --- | --- | --- | --- |
| 将来日付の変更 | 有効日が今日より後の差分を追記 | 変わらない（新しい版を足すだけ） | その日から効く |
| 過去日付の変更（遡及） | 有効日が今日以前の差分を追記 | 変わらない | 確定した給与の期間にかかれば、遡及の候補（[ADR-0004](0004-payroll-engine.md)） |
| 訂正 | 元の差分を置き換える差分を追記（`corrects_change_id`）。元の差分は取消の印を付ける | 変わらない | 同上 |
| 取消 | 差分に取消の印を付け、畳み込み直す | 変わらない | 同上 |

- 「過去日付の変更」と「訂正」は、データの上ではどちらも新しい版になる。違いは意味（「その日から変わった」か「もともと誤っていた」か）で、監査と、業務プロセスの権限（[ADR-0005](0005-security-and-my-number.md)）と、社会保険の届出（訂正は届出の訂正になりうる）で区別する。
- 取消は、後の差分がその差分に依存しているとき（例：取り消す昇格を前提にした後の昇給）に拒む。後の差分から順に取り消す。依存の判定の規則は、object-model-and-effective-dating の領域で決定表にする。
- 同じ主体・facet の畳み込みは、行ロック（主体の ID での `SELECT ... FOR UPDATE`）で直列にする。

### 時点の問い合わせ

| 問い | 読むもの | 条件 |
| --- | --- | --- |
| 今日の値 | 現在の知識 | `valid @> 今日` |
| 有効日 D の値（今の知識で） | 現在の知識 | `valid @> D` |
| 有効日 D の値を、時刻 T の知識で | 版 | `valid @> D AND recorded_at <= T AND (superseded_at IS NULL OR superseded_at > T)` |
| 主体の履歴 | 版または現在の知識 | 期間の順 |

- API は、問い合わせに `effective_on`（有効日。既定は今日）と `known_at`（記録時刻。既定は今）を受ける。
- 給与計算は、計算の開始時刻を `known_at` として入力のスナップショットを作る（[ADR-0004](0004-payroll-engine.md)）。後で同じ `known_at` で問い合わせれば、同じ入力が得られる。
- 将来日付の変更は、問い合わせの日付で自然に見え方が変わる。発効の日に要る副作用（アカウントの作成、通知、権限の付け替え）は、BP Worker のタイマーで行う（[ADR-0003](0003-business-process-engine.md)）。

### 1・3・4 を選ばなかった理由

- **1（有効時間だけ）**：過去の値を上書きするので、「5 月の給与計算のとき何を知っていたか」に、監査ログからの再構成でしか答えられない。再構成のロジックが別に要り、給与の再現性と遡及の検知の土台として弱い。
- **3（本家に近い汎用の保存）**：型と DB の制約（重なり、参照）を失う。速く読むには本家のようなメモリーの中のグラフが要り、それ自体が大きな設計になる。レポートと SQL での調査も難しくなる。本家の方式をなぞることにもなる（[リポジトリ共通の ADR-0007](../../../../docs/decisions/0007-no-reuse-of-original-implementation.md)）。
- **4（イベントソーシングだけ）**：読むたびに畳み込むと、組織図・一覧・レポートが重い。本システムは、書き込みの時点で畳み込み、結果を版として持つ。差分のテーブルがイベントの記録の役を果たす。

## Consequences

- 良くなること：
  - 任意の有効日と記録時刻の組で、当時の状態を再現できる。給与の再現性、遡及の検知、監査の土台になる。
  - 期間の重なりと参照の整合を DB が守る。
  - 後から入った過去日付の変更が、将来日付の変更の項目を壊さない。
- 引き受けるコスト：
  - 1 つの facet に 3 つのテーブルがあり、書き込みが増える。書き込みは `packages/temporal` にまとめ、アプリのコードで直接書かない。
  - 版のテーブルが大きくなる。S2 で、記録時刻での月ごとのパーティションと、古い版の分析用の基盤への移動を検討する。
  - facet の分け方を誤ると、関係のない変更で版が増える。分け方は core-hr の領域で決め、変える時は ADR にする。
  - 組織の再編のような、多くの主体を一度に変える操作は、主体ごとの畳み込みが多数になる。一括の業務プロセス（[ADR-0003](0003-business-process-engine.md)）で分割して実行する。

## Confirmation

- 性質ベーステスト（fast-check）：任意の差分・訂正・取消の列を任意の順で入れても、
  - 現在の知識の期間が重ならず、隙間の扱いが決定表どおりである。
  - 現在の知識が、取消されていない差分を有効日の順に畳み込んだ結果と一致する。
  - 任意の過去の時刻 T の問い合わせの結果が、T より後の操作で変わらない。
  - 有効日と同じ日の中の順序（`seq`）が同じなら、差分を入れた順序によらず、同じ現在の知識になる。
- CI：有効日付のテーブルへの `UPDATE`・`DELETE` を `packages/temporal` の外で書くコードを、lint で禁止する。新しい有効日付のテーブルが、3 つのテーブルと時間の制約を持たないマイグレーションを失敗させる。
- 夜間の検査：本番で、現在の知識と版の突き合わせ、期間の重なりの検査をし、不一致を警告する（NFR-002）。
