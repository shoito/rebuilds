# ADR-0003: 業務プロセスを、バージョンつきの定義と Aurora に永続する状態機械で自前に作る

## Context

人事のデータの変更（入社、異動、昇給、退職、住所の変更、休暇の申請、給与の確定）は、承認を経て反映する。次の条件がある。

- **テナントが定義を変える**：承認者の並び、条件（例：昇給率が 10% を超えたら人事部長の承認を足す）、通知、期限を、テナントの人事が設定する。
- **ルーティング**：承認者は、起票の対象の従業員の所属の組織の階層と、組織ごとのロール（上長、人事の担当）から決まる。組織とロールの割り当ても有効日付で持つ（[ADR-0002](0002-effective-dated-data-model.md)）。
- **委任**：休暇中の上長が、期間を決めて承認を他の人に任せる。
- **取消と訂正**：完了した案件を取り消す（rescind）、完了した案件の値を直す（correct）、進行中の案件を止める（cancel）。
- **監査**：誰が、いつ、どのステップで、何をしたか。権限は案件の種類ごとに決まる（[ADR-0005](0005-security-and-my-number.md)）。
- **長く続く**：案件は数日から数週間続く。将来日付の発令は、有効日に副作用（アカウントの作成など）を起こす。

本家の業務プロセスは、起票・承認・アクション（To Do）・サービス（アカウントの作成、ファイルの送信など）・通知・完了のステップを持ち、ステップごとに担当のセキュリティグループを決める。条件の規則は、入る時・検証・進行中・出る時の 4 種がある。委任は、開始日と終了日を決めて、起票と受信箱の操作を他の人に任せる（[Approval Step](https://doc.workday.com/admin-guide/en-us/manage-workday/business-processes/business-process-step-types/dan1370797855296.html)、[Setup Considerations: Delegation](https://doc.workday.com/admin-guide/en-us/manage-workday/business-processes/delegate-business-processes/cxi1568047444210.html)、どちらも 2026-09-28 に確認。ステップの種類と条件の規則の種類は、検索の結果の要約と講座の資料による）。取消は完了した案件に、キャンセルは進行中の案件に使い、どちらも元に戻せない。訂正は完了した案件を直し、承認には回らない（大学の利用の手引き [Correct, Cancel, and Rescind](https://it.tamus.edu/workdayservices/training/job_aid/correct-cancel-and-rescind/)、2026-09-28 に確認。二次資料で、設定で変えられるかは未検証）。

この実装は使わない（[リポジトリ共通の ADR-0007](../../../../docs/decisions/0007-no-reuse-of-original-implementation.md)）。業務プロセスのエンジンは、この題材の主な論点の 1 つである。

## Options

1. **自前の状態機械。** 定義はテナントのデータ（バージョンつき）。案件の状態とイベントを Aurora に永続し、ステップの実行を SQS と BP Worker で行う
2. **汎用のワークフローエンジン（Temporal）の上に作る。** 定義をワークフローのコードの入力にする
3. **AWS Step Functions。** 定義をテナントごとのステートマシンに変換する
4. **BPMN のエンジン（Camunda など）**

## Decision

1 を採用する。

### 定義

- 業務プロセスの種類（例：`hire`、`job_change`、`compensation_change`、`terminate`、`time_off_request`、`payroll_finalize`）ごとに、テナントが定義を持つ。システムが既定の定義を持ち、テナントはそれを写して変える。
- **定義はバージョンを持つ。** 定義の変更は新しいバージョンになり、それ自体が承認を要する（権限の変更と同じく、編集と有効化を別の人にできる）。**進行中の案件は、起票した時点のバージョンで最後まで進む。**
- 定義は、ステップの有向グラフ（MVP は直列と、条件つきの分岐・並列の承認まで）で、Zod のスキーマで検証する。保存の前に、到達できないステップ、承認者が決まらないステップ、終わらない差し戻しの循環を検査して拒む。
- ステップの種類：

| 種類 | 内容 |
| --- | --- |
| 起票 | 案件の種類の起票の権限を持つ人が作る。対象（従業員、組織）と有効日を持つ |
| 承認 | 承認・差し戻し・却下。担当はロールで決める |
| アクション | 人の作業（書類の確認、口座の確認など）。完了の操作で進む |
| サービス | システムの処理（アカウントの作成、帳票の生成、外部への通知）。冪等にする |
| 通知 | メール・画面の通知。進行を止めない |
| 完了 | 人事のデータへの反映。この時点で差分を書く（[ADR-0002](0002-effective-dated-data-model.md)） |

- 条件は、定義の中の限られた式（案件の項目・対象の従業員の属性・組織の比較と論理演算）で書く。任意のコードは書かせない。

### ルーティング

- 担当は、ロール（例：`manager`、`hr_partner`、`payroll_admin`）と、起点（対象の従業員の所属の組織）と、階層をたどる方向で決める。例：「対象の所属の上長。いなければ、1 つ上の組織の上長」。
- 担当の決定は、ステップに入った時点の、有効日が今日の組織とロールの割り当てで行う。決まった担当は案件に記録し、後で組織が変わっても自動では付け替えない（付け替えは人事の操作で行い、記録を残す）。
- 担当が決まらないときは、テナントが決めた予備の担当（人事の管理者）に回し、警告を出す。

### 委任

- 利用者は、期間と、任せる業務プロセスの種類と、任せる相手を決めて委任する。委任の設定も記録する。
- 委任された人が操作した記録には、本人と代理の両方を残す。
- 職務分掌（[ADR-0005](0005-security-and-my-number.md)）は、委任の後の実際の操作者で判定する。起票者に委任された承認は、起票者本人は行えない。

### 状態機械と永続

```sql
bp_definitions (tenant_id, id, process_type, version, body jsonb, status, activated_at, activated_by)
bp_cases       (tenant_id, id, process_type, definition_id, subject_type, subject_id,
                effective_on, state,            -- in_progress / completed / cancelled / rescinded / denied
                initiated_by, initiated_at, completed_at, lock_version)
bp_steps       (tenant_id, id, case_id, step_key, state, assignee_*, due_at, acted_by, acted_on_behalf_of, acted_at)
bp_events      (tenant_id, id, case_id, seq, type, payload jsonb, actor, on_behalf_of, recorded_at)   -- 追記のみ
bp_timers      (tenant_id, id, case_id, fire_at, kind, fired_at)   -- 期限・督促・発効
```

- **案件の状態の変化は、イベントの追記と同じトランザクションで行う。** 案件の現在の状態は `bp_cases`・`bp_steps` に持ち、`bp_events` を監査の正本にする。楽観ロック（`lock_version`）で、同じ案件への同時の操作を 1 つにする。
- **完了の反映は、最後のステップと同じトランザクションで行う。** 人事のデータの差分、案件の完了、outbox のイベントを 1 つのトランザクションで書く。途中で失敗したら全体を戻す。
- ステップの実行（サービス、通知、担当の決定）は、outbox から SQS を経て BP Worker で行う。少なくとも 1 回の実行なので、サービスのステップは冪等キー（案件 ID＋ステップ）で重複を防ぐ。
- タイマー（期限、督促、将来日付の発効の副作用）は `bp_timers` に持ち、BP Worker が期限の来たものを `FOR UPDATE SKIP LOCKED` で取って実行する。
- 大量の案件（組織の再編、一括の取り込み）は、親の案件の下に子の案件を作り、束に分けて実行する。

### 取消・訂正・キャンセル

| 操作 | 対象 | すること | 承認 |
| --- | --- | --- | --- |
| キャンセル | 進行中の案件 | 案件を `cancelled` にする。データは変わっていない | 案件の種類の権限。承認には回さない |
| 取消（rescind） | 完了した案件 | 案件が書いた差分に取消の印を付け、畳み込み直す（[ADR-0002](0002-effective-dated-data-model.md)）。後の案件が依存していれば拒む | 取消の権限。テナントの定義で承認を足せる |
| 訂正（correct） | 完了した案件 | 案件の値を直す差分を書く（訂正の差分）。元の案件と結び付ける | 訂正の権限。**給与・口座に関わる項目の訂正は、既定で承認に回す** |
| 差し戻し | 承認のステップ | 前のステップ（既定は起票）に戻す | — |

- 取消と訂正は、元の案件を書き換えず、新しいイベントとして記録する。
- 本家は訂正を承認に回さない（上の二次資料。未検証）。本システムは、給与・口座のように職務分掌の対象になる項目では、訂正でも承認を既定にする。承認なしの訂正は、テナントが定義で明示したときだけ許し、監査の報告に出す。
- 確定した給与の期間にかかる取消・訂正は、遡及の候補として給与の担当に示す（[ADR-0004](0004-payroll-engine.md)）。

### 2〜4 を選ばなかった理由

- **2（Temporal）**：永続の実行と再試行は優れている。ただし、定義はテナントのデータで、バージョンごとにワークフローのコードの決定性を保つ工夫が要る。案件の完了と人事のデータの差分を 1 つのトランザクションで書けず、2 つの状態の整合を取る仕組みが別に要る。状態を持つクラスタの運用も増える。
- **3（Step Functions）**：テナントごと・バージョンごとのステートマシンが数万になり、定義の変換と管理が重い。承認の待ちが長い案件の数と、人事のデータとのトランザクションの問題は 2 と同じ。
- **4（BPMN のエンジン）**：表現力は高いが、MVP の定義（直列、条件の分岐、並列の承認）には過剰で、Java の運用と、BPMN のモデルとテナントの画面の対応を持つことになる。

## Consequences

- 良くなること：
  - 案件の完了と人事のデータの反映が 1 つのトランザクションになり、「承認されたのに反映されていない」状態が起きない。
  - 監査の記録（`bp_events`）と、権限と職務分掌の判定を、エンジンの中で一貫して扱える。
  - 定義のバージョンで、進行中の案件の振る舞いが定義の変更に影響されない。
- 引き受けるコスト：
  - 永続の状態機械、タイマー、再試行、冪等を自前で作る。性質ベーステスト（任意の操作の列で、案件の状態が決定表の遷移に従う）で確かめる。
  - 定義の表現力を限る。複雑な分岐や、外部のシステムの応答を待つステップは、MVP の後に ADR で足す。
  - 定義の検証と、テナントの人事が定義を試す仕組み（模擬の実行）が要る。business-process-engine の領域で扱う。

## Confirmation

- 性質ベーステスト：任意の起票・承認・差し戻し・委任・キャンセル・取消・訂正の列で、案件の状態の遷移が決定表どおりで、完了した案件の数と、反映された差分の数が一致する。
- 結合テスト：完了のトランザクションの途中で失敗させても、案件の状態と人事のデータが食い違わない。
- 結合テスト：同じ人が、同じ案件で起票と承認をしようとすると拒まれる（委任を経由しても）。
- CI：業務プロセスを経ずに人事のデータの差分を書くコードを、`packages/temporal` の書き込みの API の呼び出し元の検査で拒む（例外は許可リストで管理する）。
