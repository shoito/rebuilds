# ADR-0056: S1 は 1 つの Aurora のクラスタ、S2 はテナントの対応表でクラスタを分け、S3 は保管庫を含むセルにする

詳細は [infrastructure.md](../architecture/infrastructure.md) の 8・9 節。

## Context

- [architecture/README.md](../architecture/README.md) の 2 節は、S1（テナント 600、従業員 100 万）、S2（6,000、1,000 万、最大のテナント 10 万人）、S3（2 万、3,000 万、30 万人）を置き、段階を上げる基準を infrastructure の領域で決めるとした。
- 負荷の集中は支給日の前（全テナントの 7 割が 5 日に集中）と始業の前（打刻）にある。
- 人事のデータの書き込みは、テナントの中の主体の行ロックで直列になるが、テナントの間は独立している。テナントをまたぐ問い合わせは、規則表の配布と課金の集計だけ（[ADR-0005](0005-security-and-my-number.md)）。
- 他の題材（Slack・Auth0）は、S2 でテナントのハッシュでクラスタを分け、S3 でセルにした。

## Options

1. **S1 は 1 つのクラスタ。S2 はテナントの対応表（テナント → クラスタ）で分け、大口のテナントを専用のクラスタへ。S3 は保管庫を含むスタック一式のセル**
2. S1 からテナントごとの DB
3. S2 から水平に分散する DB（Aurora Limitless など）

## Decision

1 を採用する。

- 段階を上げる目安は、本番のテナントの数、最大のテナントの従業員、支給日の前の writer の CPU、給与計算の時間、レポートの reader、打刻のピーク、RTO の契約（[infrastructure.md](../architecture/infrastructure.md) の 8 節の表）。どれかが上限の 70% に届き、戻らない見込みになったら移行を始める。
- S2 の対応表 `tenant_directory` はテナントの外に置き、要求の始めに 1 回引いて接続のプールを選ぶ（タスクのメモリーにキャッシュ）。ハッシュではなく対応表にするのは、大口のテナントを個別に動かすため。
- S3 のセルは prod と vault-prod の両方を含む。テナントをセルに固定し、ホスト名でセルを決める。規則表はセルの外から各セルへ配る。
- 2 を採らない理由：S1 の 600 テナントなら運用できるが、S3 の 2 万テナントで接続・マイグレーション・監視が重い（ADR-0005 の ii と同じ）。
- 3 を採らない理由：有効日付の時間の制約（`WITHOUT OVERLAPS`、`PERIOD`）と RLS が、分散の DB で同じく使えるか確かめられていない（未検証）。テナントの間が独立しているので、クラスタの分割で足りる。

## Consequences

- 良くなること：
  - S1 は単純な構成のまま始められる。
  - 大口のテナントの支給日の集中を、専用のクラスタで他のテナントから切り離せる。
- 引き受けるコスト：
  - S2 で、テナントの移動（クラスタ間）の手順とツールが要る。
  - S3 のセル間のテナントの移動（保管庫の記録の連鎖を結ぶことを含む）は、S3 の前に別の ADR で決める。

## Confirmation

- 月次：8 節の指標をダッシュボードで見て、70% に届いたものを Ops が PM に知らせる。
- S2 の前：テナントの移動の訓練（staging で、合成の 3 万人のテナントをクラスタ間で動かし、給与の再現の抜き取りが一致する）。
