# ADR-0026: 給与の実行を状態機械にし、入力を RFC 8785 の正規の形と SHA-256 で固定して内容のアドレスで置く

詳細は [payroll-engine.md](../architecture/payroll-engine.md) の 3〜5 節。

## Context

[ADR-0004](0004-payroll-engine.md) は、給与の実行の段（準備、入力の固定、計算、確認、確定、支払）と、入力のスナップショットを正規の形にしてハッシュを取ることを決めた。[ADR-0008](0008-point-in-time-queries-and-activation-timers.md) は、`known_at` を安定の境界（今 − 10 秒）より前に限ると決めた。残っている論点は次のとおり。

- 段の移動の単位と、同じ期間に並ぶ実行の数。確認の途中で 1 人だけ直したいときの扱い。
- 正規の形の規則（キーの順序、数の表記、文字列のエスケープ）。自前の規則にすると、別の言語の検証の道具で同じハッシュを出せない。
- 入力の文書に何を入れるか。マイナンバー・口座・氏名を入れると、スナップショットの保存の全体が機微な情報の範囲に入る。
- 営業日の暦の持ち主（[business-process-engine.md](../architecture/business-process-engine.md) の持ち越し）。

## Options

正規の形：

1. **RFC 8785（JSON Canonicalization Scheme）。金額は整数、率は 10 進の文字列**
2. 自前の規則（キーの辞書順、独自の数の表記）
3. バイナリの形（CBOR の決定的な符号化など）

入力の中身：

- a. **計算に要る事実だけ。氏名・住所・口座・マイナンバーを入れない**
- b. 明細や振込にも使えるよう、人事のデータを丸ごと入れる

## Decision

1 と a を採用する。

- 実行は `payroll_runs`（給与のグループ × 期間 × 種類）で、`draft → frozen → computing → computed → in_review → finalized → released`、取り消しは `cancelled`（DT-PAY-001）。`finalized` は `payroll_finalize`、`released` は `payroll_payment_release`、確定の後の取り消しは `payroll_cancel` の業務プロセスで行う。同じグループ・期間の `regular` は `cancelled` 以外に 1 つ。
- `in_review` の中で、1 人の入力を新しい `known_at` で固定し直して計算し直せる。人ごとの `known_at` を記録する。
- 入力の固定は、`known_at` ＝ 開始 − 10 秒で、1 人ずつ期間の各日の事実を区間の列にし、勤怠の集計の版、休暇、個別の調整、住民税の月割額、前の結果から要る値、規則表の版、設定の版を入れる。RFC 8785 で正規にし、SHA-256 を取る。S3 の `payroll-inputs/{tenant}/{sha256}.json`（テナントの KMS の鍵）に置き、`payroll_inputs` に記録する。
- 結果は、入力のハッシュ・規則表の版の一覧のハッシュ・エンジンのイメージのダイジェスト・設定の版を持つ。確定の後はアプリのロールから書き換えられない。
- 夜間に確定した結果の 1% を記録した版で計算し直し、不一致を SEV1 にする。エンジンのイメージは保存の期間の間消さない。
- 営業日の暦（`business_calendars`）はこの領域が持ち、業務プロセスの期限と共有する。
- 2 を採らない理由：規則の細部（数の指数表記、Unicode の扱い）を自分で決めて保守することになる。監査人や別の道具が同じハッシュを再計算できない。
- 3 を採らない理由：人が読めない。調査と監査の説明のたびに変換が要る。入力は数 KB〜数十 KB で、大きさの利点は小さい。
- b を採らない理由：スナップショットの保存・ログ・計算のタスクのすべてが、口座やマイナンバーの安全管理の範囲に入る。明細と振込は、結果と人事のデータをそれぞれの領域で結べば足りる。

## Consequences

- 良くなること：
  - どの入力で計算したかがハッシュで一意に決まり、同じハッシュの文書は 1 回だけ置く。
  - 計算の側に口座・マイナンバーが流れない。
  - 営業日の数え方が給与と業務プロセスで一致する。
- 引き受けるコスト：
  - JSON の正規化の実装の正しさを、RFC の付録の例と性質ベーステストで確かめる必要がある。
  - 1 人の再計算で、同じ実行の中に `known_at` の違う人が混ざる。監査の画面で人ごとの `known_at` を示す。
  - 入力の固定（DB の読み取り）が実行の時間の主になる見込み。雇用の束ごとに並列にする。

## Confirmation

- 決定表のテスト：DT-PAY-001。
- 性質ベーステスト：PROP-PAY-001（再計算の一致）、PROP-PAY-003（正規の形とハッシュ）。
- CI：入力の文書のスキーマに、氏名・住所・口座・マイナンバーの項目がないことを検査する。人事の側の個人番号の形の検査（[ADR-0005](0005-security-and-my-number.md)）を入力の文書のフィクスチャーにも当てる。
- 本番：夜間の抜き取りの再計算の不一致 0 件。
