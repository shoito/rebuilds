# ADR-0059: 給与の実行を支給日から逆算した里程標の遅れで監視し、本番の監視用のテナントで合成の給与を毎日計算して期待値と比べる

詳細は [observability.md](../architecture/observability.md) の 3.3・3.5 節。

## Context

- 給与の実行は数が少なく（テナント × 月に数回）、要求の成功の率のような SLI では、1 つの実行の遅れや誤りが埋もれる。
- 支給日と振込の締め切り（`lead_business_days`）は動かせない。遅れの影響は、締め切りに間に合うかで決まる（[payroll-engine.md](../architecture/payroll-engine.md) の 4.2 節、[payments-and-accounting.md](../architecture/payments-and-accounting.md) の 3.5 節）。
- 実行の遅れには、本システムの原因（計算の遅れ、失敗）と、テナントの原因（担当の確認・承認の待ち）がある。後者は SLO にすべきでない。
- NFR-003 は、1 万人の計算を 15 分以内、3 万人を 45 分以内、1 人の再計算を 5 秒以内とする。
- 計算の正しさは、ゴールデンデータセット（CI）と夜間の再現の抜き取り（本番）で見る（[ADR-0004](0004-payroll-engine.md)、[ADR-0026](0026-payroll-run-stages-and-input-snapshot.md)）。再現の抜き取りは「同じ入力で同じ結果か」を見るが、「本番の規則表とエンジンの組み合わせで正しい額か」は見ない。規則表の公開やエンジンのデプロイの誤りは、本番のテナントの確定まで気づけない。

## Options

1. **里程標（勤怠の締め、入力の固定、計算の完了、確定、振込ファイルの承認）の予定と実際を記録し、原因を `system` と `tenant` に分け、`system` の原因の遅れを SLI にする。本番の監視用のテナントで、合成の従業員の給与を毎日と変更の直後に計算し（確定しない）、ゴールデンデータの期待値と比べる**
2. 要求の成功の率と計算の時間だけを SLI にする
3. 本番のテナントの結果を、前月との差の検査（確認の段）だけで見る

## Decision

1 を採用する。

- 里程標の予定は、支給日と営業日の暦から、実行を作るときに決める。実際の時刻は段の遷移で記録する。段の中で人の操作を待った時間は `tenant` の原因にする。
- SLI：`system` の原因で里程標に遅れなかった実行の割合（99.9%）、人数で正規化した計算の時間（NFR-003）、1 人の再計算の p99、振込ファイルの生成の成功、再現の抜き取りの不一致 0 件、合成の給与の実行の一致 100%。
- 合成の給与の実行：監視用のテナント（`environment = internal`）の約 100 人の合成の従業員。`run_type = parallel` で確定しない。毎日 6 時と、エンジンのデプロイ・規則表の公開の直後に走らせる。期待値は、その支払日に当たる規則表の版のゴールデンデータ。不一致は SEV2。
- 2 を採らない理由：締め切りへの近さが見えない。テナントの待ちで遅れた実行まで障害に数えてしまう。
- 3 を採らない理由：前月との差の検査は、全員に同じく効く誤り（料率の取り込みの誤り）を「料率の改正」と区別できない。

## Consequences

- 良くなること：
  - 支給日に間に合うかを、実行ごとに先回りして見られる。
  - 本番の規則表とエンジンの組み合わせの誤りを、本番のテナントの確定の前に見つけられる。
- 引き受けるコスト：
  - 監視用のテナントの合成の従業員と期待値を、ゴールデンデータセットと同じく保守する（[ADR-0061](0061-golden-dataset-ci.md)）。
  - 原因の分け方（段の中の人の待ち）の規則を実装し、誤りを見直す。

## Confirmation

- 結合テスト：段の遷移で里程標の実際の時刻が記録され、人の待ちが `tenant` に数えられる。
- 本番：合成の給与の実行の毎日の結果が記録され、デプロイ・規則表の公開の直後にも走っている（デプロイの記録と突き合わせる）。
