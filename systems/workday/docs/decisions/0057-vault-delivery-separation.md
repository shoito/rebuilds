# ADR-0057: 保管庫の Terraform の状態・デプロイのパイプライン・承認者・デプロイの日を人事の側と分ける

詳細は [infrastructure.md](../architecture/infrastructure.md) の 10 節と [delivery.md](../architecture/delivery.md) の 5 節。

## Context

- 保管庫は別のアカウントに置く（[ADR-0054](0054-accounts-network-and-vault-boundary.md)）。アカウントを分けても、同じ CI のロールと同じ Terraform の状態で人事の側と保管庫の両方を apply できるなら、CI の乗っ取りや誤った変更で両方に届く。
- Terraform の状態のファイルには、リソースの属性（DB のエンドポイント、場合によっては秘密）が入る。
- 保管庫の変更は `security:sensitive`（[AGENTS.md](../../AGENTS.md)）。他の題材（[Auth0 の ADR-0065](../../../auth0/docs/decisions/0065-security-sensitive-change-flow.md)）は、Signer のイメージを他のサービスと別の日に本番へ出した。

## Options

1. **保管庫の Terraform の状態は vault-prod の中の専用のバケット。保管庫のパイプラインは別の GitHub の環境と別の OIDC のロールで、承認はセキュリティの担当と Ops の責任者。人事の側と同じ日に本番へ出さない**
2. 同じパイプラインで、承認だけを足す
3. 同じリポジトリの中で、保管庫を別のリポジトリに分ける

## Decision

1 を採用する。3 は採らず、同じモノレポの中でパスとパイプラインを分ける。

- 保管庫のコード（`services/vault-*`、`packages/vault-*`）と `infra/vault/*` は、別のコードオーナー（Dev のテックリードとセキュリティの担当）。
- 保管庫のパイプラインの OIDC のロールは vault-prod にだけ信頼を持つ。人事の側のパイプラインのロールは vault-prod を引き受けられない。
- 保管庫の本番のデプロイは、人事の側のデプロイと別の日。人事の側と保管庫の間の API（PrivateLink の上）は、新旧の両方と互換を保つ。
- 保管庫のイメージは、署名（ECR の署名の検証）とダイジェストで固定する。
- 2 を採らない理由：1 つのロールの乗っ取りで両方に届く。承認の段は、ロールの権限の広さを減らさない。
- 3 を採らない理由：人事の側と保管庫の間の型（主張の形、書類の元のデータのスキーマ）を 2 つのリポジトリで持つことになる。パスとパイプラインの分離で足りる。

## Consequences

- 良くなること：
  - 人事の側の CI の乗っ取りや誤った変更が、保管庫に届かない。
  - 保管庫の変更と人事の側の変更が同じ日に重ならず、障害の原因の切り分けがしやすい。
- 引き受けるコスト：
  - パイプラインと承認者が 2 系統になり、保管庫の変更のリードタイムが延びる。
  - 両側の API の互換（新旧）を保つ規律が要る。

## Confirmation

- IAM の静的検査：人事の側のパイプラインのロールの信頼の方針に、vault-prod のロールの引き受けがない。
- CI：`infra/vault/*` と保管庫のパスの PR に、セキュリティの担当の承認がないとマージできない。
- デプロイの記録：保管庫と人事の側の本番のデプロイが同じ日にない（月次に確かめる）。
