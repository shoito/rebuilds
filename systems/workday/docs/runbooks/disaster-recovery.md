# Runbook: 災害復旧（AZ の障害、リージョンの障害、支給日の DR、論理的な破損、訓練）

- Owner: Ops
- 対応するアラート: AZ の障害（複数のサービスで 1 つの AZ のターゲットが不健全）、大阪からの合成監視の連続失敗、`AuroraGlobalDBRPOLag` の超過、大阪での振込ファイルの作り直しのハッシュの不一致、大阪の待機の構成の異常、訓練（四半期に 1 回）
- 最終確認日: 2026-09-28

構成と目標は [infrastructure.md](../architecture/infrastructure.md) の 6 節、方針は [ADR-0055](../decisions/0055-disaster-recovery-and-payday-continuity.md) にある。目標は NFR-006（AZ：RPO 0・RTO 15 分以内。リージョン：RPO 5 分以内・RTO 4 時間以内。支給日の前の 5 営業日にリージョンが落ちても、振込ファイルを当日中に出す）。

## 症状

| 場面 | 見え方 |
| --- | --- |
| A. AZ の障害 | 1 つの AZ のタスク・Aurora のインスタンス・Valkey のノードが不健全。AWS Health Dashboard に東京の 1 つの AZ のイベント |
| B. リージョンの障害 | 東京の画面・API が応答しない。大阪からの合成監視がすべて失敗。CloudFront の 502・504 が増える |
| C. 複製の遅延 | `AuroraGlobalDBRPOLag` が 60 秒を超え続ける（東京は正常） |
| D. 論理的な破損 | 誤ったマイグレーション・操作・保存の期間の削除で、データが消えた・壊れた |
| E. 支給日の DR | B が支給日の前の 5 営業日に起きた。または大阪での振込ファイルの作り直しのハッシュが一致しない |
| F. 保管庫 | vault-prod の東京が応答しない（人事の側は正常なこともある） |
| G. 訓練 | 半年〜四半期に 1 回（staging）、年 1 回（本番の switchover）。合格基準は [quality.md](../quality.md) の 2.4 節 |

## 影響

- A：数十秒、書き込みが失敗・再試行になる。打刻は端末に貯まる。給与の計算の束は再試行で続く。コミット済みのデータは失わない。
- B：切り替えまで（目標 4 時間以内）、画面・API・打刻の受付が止まる。打刻は端末と打刻機に貯まる。切り替えの後、複製の遅延ぶんの書き込みを失う（下の表）。
- E：B に加えて、振込の締め切りに間に合わないと、従業員への給与の支払いが遅れる（賃金の支払いの期日に関わる）。
- F：番号の提出と書類の生成が止まる。給与の計算と振込ファイルは影響を受けない。

| 失った書き込み（B） | 切り替えの後に起きること | 回復 |
| --- | --- | --- |
| 業務プロセスの起票・承認・完了 | 案件が前の状態に戻る | 監査の記録から一覧にし、担当にやり直しを依頼する |
| 有効日付の差分（完了した案件の反映） | 反映が消える | 同上（案件ごと戻るので、差分だけが残ることはない。[ADR-0003](../decisions/0003-business-process-engine.md)） |
| 打刻 | サーバーの記録が消える | 端末・打刻機は送信済みで消している。**消えた打刻は、監査の記録ではなくアプリのログ（打刻の受付の件数）で範囲だけ分かる。** 本人・上長の訂正（`time_correction`）で入れ直す |
| 給与の実行の段の遷移（確定、振込ファイルの承認） | 前の段に戻る | E の手順 |
| 振込ファイルの取り出し | 取り出しの記録が消える | E の手順（二重の提出の防止） |
| 権限の方針の有効化、所属の変更 | 前の版に戻る | 監査の記録から一覧にし、やり直す |

## 確認

1. AWS Health Dashboard と Grafana の AZ ごとの内訳で、1 つの AZ か、リージョン全体かを見分ける。
2. Aurora のクラスタのイベントで、フェイルオーバーの有無と、現在の writer の AZ を確かめる。
3. リージョンの障害を疑うときは、大阪の合成監視と、別の回線からの到達性の両方で確かめる。
4. **`AuroraGlobalDBRPOLag` の直近の値と、東京が応答しなくなった時刻を記録する。** 失った範囲の目安になる。
5. **今後 5 営業日の支給日の予定**（給与の実行のダッシュボードのヒートマップ）を見る。当日・翌営業日に振込の締め切りがあるテナントがあれば、E を並行で始める。
6. KMS（東京）の到達性を確かめる。KMS だけの障害なら、リージョンの切り替えではなく、KMS の復旧を待つ（新しい暗号・復号が止まるので、給与の入力の固定・振込ファイルの生成・口座の表示が止まる）。

## 対処

### A. AZ の障害

基本は自動で回復する。

1. インシデントを宣言する（SEV2 から。[incident-response.md](incident-response.md)）。
2. Aurora が別の AZ へ自動でフェイルオーバーしたことを確かめる。5 分たっても writer がなければ、手動でフェイルオーバーする。
3. ECS が残る 2 AZ でタスクを起動しているか確かめる。api が足りなければ、最小のタスク数を上げる。
4. 給与の実行の束の失敗の率を見る。3 回の再試行で失敗した束があれば、束を再投入する（[payroll-engine.md](../architecture/payroll-engine.md) の 13 節）。
5. AZ が回復したら、台数を平常に戻す。

### B. リージョンの障害（東京 → 大阪）

**切り替えの判断は、インシデントの指揮者（IC）が行い、Ops の責任者が承認する。** AWS の見込みで 1 時間以内に回復しそうで、今後 2 営業日に振込の締め切りがなければ、待つことも選ぶ（データを失わない）。締め切りがあれば、E の判断を先にする。

1. SEV1 を宣言し、テナントへ告知する（ステータスページ）。
2. **東京への書き込みを止める。** 東京の api・worker に届くなら、ops フラグ `ops.read_only_mode` を有効にする。
3. **失った範囲を記録する。** 「確認」の 4 の値をインシデントの記録に書く。
4. **DB を切り替える。**「DR：大阪を有効化」のワークフロー（大阪で実行できるもの）を起動する。
   1. 人事の Aurora Global Database の大阪の二次を昇格させる。東京の writer が生きていれば switchover（RPO 0）、応答しなければ `failover-global-cluster --allow-data-loss`（大阪のリージョンで実行）。
   2. 古い一次の障害の時点のスナップショットがあれば、手動のスナップショットにコピーして保全する。
   3. 大阪の reader を足す（一般用、支給日の前なら給与の用）。
5. **アプリを広げる（順序を守る。[infrastructure.md](../architecture/infrastructure.md) の 6.3 節）。**
   1. api と、振込ファイル・明細の worker を、東京と同じ台数にする。人事・給与の担当の経路を先に開く（ops フラグ `ops.payroll_first`：セルフサービスの経路を 503 にしたまま、給与・人事の担当の画面だけを受ける）。
   2. 次に、セルフサービスの画面と打刻の受付を開く。**端末と打刻機に貯まった打刻が一度に届く**ので、api の台数とテナントごとのレート制限（200 件/秒）を見ながら開く。
   3. 次に、bp-worker（タイマーと発効を `fire_at` の順に追いつく）、レポート、egress-worker、audit-archiver。
6. **入口を切り替える。** `global/edge` の変数 `active_region` を大阪にして apply する（CloudFront のオリジンを大阪の ALB に）。
7. **失った範囲の一覧を作る**（次の節）。
8. **受け付けを段階的に再開する。** 監視用のテナントで合成監視が成功することを確かめ、`ops.read_only_mode` を解除する。
9. テナントへ、再開と影響（失った範囲の案件のやり直し、打刻の訂正の依頼）を告知する。
10. 保管庫は F の手順で、人事の側の後に行う。

**東京へ戻す（フェイルバック）**：東京の回復後、Aurora が東京を二次として加え直す。複製が追いついたら、別の計画作業として switchover（RPO 0）で戻す。**支給日の前の 5 営業日と凍結の日を避ける。**

### 失った範囲の一覧（B の後）

1. **範囲を決める。** 開始 ＝ 東京が応答しなくなった時刻 − 記録した複製の遅延 − 5 分。終了 ＝ 大阪の昇格の時刻。
2. **記録を取り出す。**「DR：失った範囲の取り出し」のジョブに範囲を渡す。ジョブは、log-archive（大阪へ複製）の監査のセグメントから、範囲の中の `bp_events`（書き出されていれば）と `audit_events` を取り出し、大阪の DB にない事象を一覧にする。監査のセグメントは 10 秒〜1 分遅れて書き出すので、最後の 1〜2 分は取り出せない。
3. **テナントごとに一覧を渡す**（案件の ID、種類、操作、時刻。値は含めない）。やり直しは担当が業務プロセスで行う。システムは自動でやり直さない（承認は人の判断のため）。
4. **権限の変更**（方針の有効化、所属の変更）は、セキュリティの担当が一覧を確かめ、テナントの管理者にやり直しを依頼する。職務分掌の違反の状態に戻っていないかを、夜間の走査を手で走らせて確かめる。
5. 東京が回復したら、東京の log-archive と古い一次のスナップショットで、もう一度同じ範囲を取り出し、差分を一覧に足す。

### C. 複製の遅延

1. `AuroraGlobalDBRPOLag` と、東京の writer の書き込みの量（給与の取り込み、打刻の集中、閲覧の記録）、リージョン間の回線の状態を確かめる。
2. 給与の取り込み（loader）の集中なら、loader の同時の上限を下げて待つ。10 分を超えて続くなら、SEV3 のインシデントにし、AWS サポートにケースを開く。
3. 支給日の前の 5 営業日に 5 分を超えたら SEV2 にする（NFR-006 の RPO を超えうる）。

### D. 論理的な破損

1. 原因の機能のフラグを切る、原因のジョブ（保存の期間の削除、一括の取り込み、再編）を止める。
2. 破損の直前の時刻を、ログと監査の記録から特定する。
3. Aurora の PITR で、隔離した VPC に新しいクラスタを復元する。本番のクラスタは上書きしない。
4. 失われた行だけを取り出して戻す。
   - **有効日付の差分・版**：戻す行の後に書かれた差分・版と矛盾しないことを、参照のモデルでの畳み込み直し（[ADR-0009](../decisions/0009-temporal-reference-model-testing.md)）で確かめる。戻したら `rebuild_current` で現在のテーブルを作り直す。
   - **給与の結果**：戻すのではなく、入力の文書（S3）から、記録したエンジンと規則表の版で計算し直し、失われた結果のハッシュ（監査のセグメント・実行の記録）と一致することを確かめてから入れる。
   - **仕訳**：逆仕訳と矛盾しないことを確かめる。
   - **保存の期間の削除の誤り**：`retention_executions` の範囲を戻す。
5. 復元したクラスタを消す。

### E. 支給日の DR（振込ファイルを当日中に出す）

**最優先は、支給日の振込に間に合わせることと、同じ振込を 2 回出さないこと。**

1. IC は、給与の支援の担当を連絡係に指名し、今後 2 営業日に振込の締め切りがあるテナントの一覧（実行、支給日、支払元の口座、振込指定日、`lead_business_days`）を作る。一覧は給与の実行のダッシュボード（大阪の DB を読む）から出す。
2. B の手順の 4〜6 を、`ops.payroll_first` で行う（支払の経路を先に開く）。
3. **大阪の二次の昇格の前の最後の毎日の確認**（大阪での作り直しのハッシュの一致）の結果を確かめる。一致していれば、大阪で同じファイルを作れる。
4. テナントの実行ごとに、大阪の DB の状態で分ける。

| 大阪での実行の状態 | 監査の記録（log-archive）に | すること |
| --- | --- | --- |
| `released`（承認済み）で、取り出しの記録がある | — | **テナントに、東京で取り出したファイルを銀行に渡したかを確かめる。** 渡していれば何もしない。渡していなければ、大阪の S3 の複製のファイルを取り出す（ファイルの SHA-256 が承認の記録のハッシュと一致することを確かめる） |
| `released` で、取り出しの記録がない | 取り出しの事象がある（大阪の DB で失った） | 同上（渡したかを必ず確かめる） |
| `released` で、取り出しの記録がない | 取り出しの事象もない | 大阪の S3 の複製のファイルを、ハッシュを確かめて取り出してもらう |
| `finalized` | 承認の事象がある（失った） | **大阪で支払の指示から振込ファイルを作り直す。** 作ったファイルの SHA-256 が、監査の記録の承認の事象のハッシュと一致することを確かめる。一致すれば、`payroll_payment_release` の承認を大阪でやり直してもらう（承認者の再認証） |
| `finalized` | 承認の事象がない | 大阪でファイルを作り、通常どおり承認してもらう |
| `in_review`・`computed` | 確定の事象がある（失った） | 確定の業務プロセスをやり直す。入力の文書は S3 の複製にあり、結果は計算し直して元の結果のハッシュと一致を確かめる |
| `frozen`・`computing` | — | 大阪で計算を続ける（入力の文書は S3 の複製。束を再投入）。確定と承認を担当に依頼する |
| `draft`（入力の固定の前） | — | 大阪で入力の固定から行う。勤怠の締めが失った範囲にかかるなら、先に締めをやり直す |

5. **締め切りに間に合わない見込みの実行**は、支払元の口座の銀行との当日の扱い（締め切りの延長、別の送信の手段）を、テナントが銀行と相談する。本システムは、ファイルを作れる時刻の見込みを連絡係からテナントに伝える。銀行ごとの締め切りの扱いは未検証。
6. **本システムは、仮の金額（前月と同じ額など）での支払いのファイルを勝手に作らない。** テナントが仮払いを選ぶときは、テナントの給与の担当が `off_cycle` の実行に金額を入れて、通常の承認を経る。仮払いの後の精算の扱いは社労士の確認待ち（下の「事後」）。
7. ファイルを渡した実行ごとに、テナントから「銀行へ渡した」確認を受け、インシデントの記録に残す。**同じ振込指定日・同じ支払元の口座のファイルを、2 回渡さない。**
8. 明細の公開は、振込の後でよい。公開の時刻を過ぎた明細は、大阪の worker が PDF を作り直して公開する（同じ文書から同じバイト列。[ADR-0036](../decisions/0036-payslips-wage-ledger-and-e-delivery-consent.md)）。

### F. 保管庫（vault-prod）

1. 保管庫の東京だけが落ちたなら、人事の側は止めない。番号の提出と書類の生成を止めた旨を、テナントの事務取扱責任者に知らせる。
2. 切り替えは、保管庫のワークフロー（保管庫のアカウントのロール。セキュリティの担当と Ops の責任者の承認）で、保管庫の Aurora の大阪の二次を昇格させ、vault-api・vault-web を大阪で広げ、大阪の PrivateLink のエンドポイントに人事の側を向ける。
3. 大阪の保管庫の KMS のレプリカで復号できることを、監視用の `mn_ref` の `status` と、監視用の担当者の表示の操作（合成の番号）で確かめる。
4. 失った範囲の保管庫の操作（登録、確認、削除）は、log-archive の保管庫の記録から一覧にし、テナントの事務取扱担当者にやり直しを依頼する。**削除のやり直しを落とさない**（消したはずの番号が戻る）。

### G. 訓練

| 訓練 | 頻度 | 環境 | 確かめること |
| --- | --- | --- | --- |
| AZ の障害 | 半年 | staging | FIS で 1 AZ を切り離す。コミット済みのデータの損失 0、書き込みの回復まで 15 分以内、給与の束が再試行で完了する |
| リージョンの切り替え（計画外） | 年 2 回 | staging | B の手順。失った範囲 5 分以内、RTO 4 時間以内、切り替えの順序、失った範囲の一覧 |
| PITR からの復元 | 四半期 | prod の中の隔離した VPC | 復元の時間、RLS が有効、テナントの鍵で S3 の物体が読める、給与の結果の計算し直しでハッシュが一致 |
| 支給日の DR | 四半期 | staging | 支給日の 1 営業日前を模して、書き込み（確定、承認、取り出し）を続けたまま東京を止め、E の手順で大阪から振込ファイルを出すまで。RTO（振込ファイルまで）2 時間以内。ハッシュの一致。二重の取り出しの確認の手順が動く |
| 本番の switchover | 年 1 回 | 本番 | 支給日の前の 5 営業日と凍結の日を避ける。大阪で画面と給与の担当の操作を受け、東京へ戻す |
| 保管庫の切り替え | 年 1 回 | vault-staging | 大阪で復号でき、アクセスの記録の連鎖が切り替えの前後でつながる |
| 大阪の待機の構成の確認 | 月次 | 本番 | [infrastructure.md](../architecture/infrastructure.md) の 6.6 節の表 |

合格基準は [quality.md](../quality.md) の 2.4 節（QA が判定する）。結果（時間、問題点）を、この runbook の末尾の記録に残す。

## エスカレーション

- A で 5 分たっても DB の writer がない → SEV1 に上げ、Dev のテックリードを呼ぶ。
- B の判断 → Ops の責任者。告知の文面は PM と合意する。
- E（支給日）→ PM と給与の支援の担当を必ず呼ぶ。テナントの給与の担当への連絡は連絡係が行う。締め切りに間に合わない見込みのテナントは、1 時間ごとに状況を伝える。
- 大阪で振込ファイルのハッシュが承認の記録と一致しない → 作り直したファイルを渡さない。SEV1。Dev のテックリードと QA を呼ぶ（入力・指示・生成の順に調べる）。
- 保管庫の切り替え・削除のやり直し → セキュリティの担当。
- AWS 側の障害 → AWS サポートにケースを開く。

## 事後

- 調査結果を Intent の Issue として起票する（Maintain 段）。
- 実際の切り替えと訓練で計測した RTO・RPO、失った範囲の件数（種類別）、振込ファイルを出すまでの時間を記録し、目標を満たさなければ Intent を起票する。
- 仮払い（E の 6）を選んだテナントがあれば、精算の扱い（過払い・不足の調整、24 条の協定との関係）を社労士の確認に回す（[payroll-engine.md](../architecture/payroll-engine.md) の L28 と同じ論点）。
- この手順で足りなかったことを、ここに反映する。
