# Runbook: インシデント対応

- Owner: Ops
- 対応するアラート: すべての呼び出し（page）のアラート（[observability.md](../architecture/observability.md) の 5.2 節）。個別の場面は「この題材に固有の場面」の節
- 最終確認日: 2026-09-28

個別の手順（[deploy-and-rollback.md](deploy-and-rollback.md)、[disaster-recovery.md](disaster-recovery.md)）の上に立つ、共通の進め方と、この題材に固有の場面（マイナンバーの漏えいの疑い、個人情報の出力、給与の計算の誤り（支給日の後）、テナントの分離の破れ・権限の迂回、依存先の障害）。進め方の骨格は他の題材（Slack・Stripe・Auth0 の incident-response.md）と同じ。

## 症状

次のどれかのときに、インシデントを宣言する。迷ったら宣言し、後で重さを下げる。

- 呼び出しのアラートが鳴った
- テナントや社内から、障害・給与の誤り・個人情報やマイナンバーの漏えいの報告が来た
- 個人情報・個人番号の形の走査で検出した、保管庫の鍵・主張の署名の鍵の想定外の使用を検知した、監査・保管庫の記録の連鎖の検証が失敗した

## 影響

### 重さ（severity）

| 重さ | 基準 | 例 | 最初の応答 | 告知 |
| --- | --- | --- | --- | --- |
| SEV1 | 全体で画面・API が使えない。支給日の振込に間に合わない恐れ。他のテナントのデータが見えた。マイナンバーの外部への漏えいが確定した・保管庫の侵害の疑い。多くのテナントに及ぶ給与の計算の誤り | リージョンの障害、テナントの分離の破れ、規則表の誤りの確定の後の発見 | 5 分以内 | 30 分以内にテナントへ。以後 30 分ごと |
| SEV2 | 一部の機能・テナントが使えない。支給日の前の給与の経路の劣化。個人番号の形が保管庫の外で見つかった。1 テナントの給与の計算の誤り。再現の抜き取りの不一致・合成の給与の実行の不一致。監査の連鎖の検証の失敗 | AZ の障害、Payroll Compute の失敗、ログへの番号の出力 | 15 分以内 | 1 時間以内にテナントへ（影響があれば） |
| SEV3 | 劣化しているが、回避できる | レポートの遅れ、発効の遅れ（4 月以外）、1 つの Webhook の停止 | 営業時間内 | 必要なら |
| SEV4 | テナントへの影響がない | 1 つの Worker の失敗の増加 | 営業時間内 | なし |

**マイナンバー、テナントの分離、権限の迂回、支給日の振込、給与の誤りに関わるものは、範囲が 1 件でも SEV2 以上にする。**

## 確認

1. どのアラート・報告から始まったかを記録する。
2. 影響の範囲を見る：全体か、特定のテナント・AZ・機能か。本番のテナントか、sandbox か。**今後 5 営業日に支給日のあるテナントか。**
3. 直近の変更を見る：デプロイ（アプリ、Payroll Compute のイメージ、Terraform）、規則表の公開、フラグ、マイグレーション、テナントの設定の変更（権限の方針、業務プロセスの定義、給与の設定）。
4. セキュリティへの影響を見る：走査の結果、KMS の操作（CloudTrail）、保管庫の記録の突き合わせ、GuardDuty。

## 対処

### 役割

| 役割 | 担う人 | 責任 |
| --- | --- | --- |
| 指揮者（IC） | 最初に応答したオンコール。SEV1 では Ops の責任者に引き継いでよい | 重さ、方針、大きな判断（リージョンの切り替え、給与の確定の保留、保管庫の停止） |
| 作業者 | オンコールの Ops、呼ばれた Dev | 調査と復旧 |
| セキュリティの担当 | セキュリティの当番 | 個人情報・マイナンバー・分離に関わる判断、証拠の保全、法務への連絡 |
| 給与の支援の担当 | 給与の当番（支給日の前と、給与の誤り） | テナントの給与の担当との連絡、締め切りの確認 |
| 連絡係 | IC が指名する（PM が望ましい） | テナント、社内、AWS への連絡 |
| 記録係 | IC が指名する | 時刻付きの記録 |

SEV1 では、指揮者は手を動かさない。

### 進め方

1. **宣言する。** インシデント用の場を、このシステムと別の道具に作る。
2. **被害を止めることを、原因の特定より優先する。** 順番：
   - 直近の変更のフラグを切る
   - 直近のデプロイを戻す（[deploy-and-rollback.md](deploy-and-rollback.md)）
   - 給与の確定を保留する（ops フラグ `ops.payroll_finalize_hold`。テナントを指定できる）
   - 原因の機能を ops フラグで止める（レポートの非同期、一括の取り込み、Webhook）
   - 問題のテナントにレート制限をかける、容量を増やす
3. **証拠を消さない。** 監査の記録、保管庫の記録、ログ、CloudTrail は調査の材料である。**個人情報とマイナンバーの値を、チケット・チャット・この記録に写さない。** ID（`tenant_id`、`worker_id`、`mn_ref`、`run_id`）と件数だけを書く。
4. **告知する。** 何が起きているか、どの操作に影響するか（画面、打刻、給与の確定、振込ファイル、明細）、打刻は端末に貯まっているか、次の更新はいつか。原因の推測は書かない。
5. **収束を確かめる。** SLO の指標が戻り、合成監視と合成の給与の実行が成功し、15 分たってから解決とする。セキュリティの調査・給与の訂正が残るときは、インシデントを閉じず、SEV を下げて続ける。

### この題材に固有の場面

#### マイナンバーの漏えいの疑い

アラート：保管庫の外での個人番号の形の検出（[observability.md](../architecture/observability.md) の 4.3 節）、保管庫の鍵（`vault-mn`）・主張の署名の鍵（`<brand>-hr-vault-assertion`）の想定外の主体の使用、保管庫の記録の欠け・連鎖の検証の失敗、担当者の `reveal` の急増、テナントからの報告、事務取扱担当者の端末の紛失の連絡。

1. **SEV2** で宣言する（外部への持ち出しの確定、保管庫の侵害の疑いなら **SEV1**）。セキュリティの担当と法務を呼ぶ。
2. **広げない。**
   - 保管庫の外（人事の側のログ・S3）で番号の形が見つかった：検出したロググループ・バケットの読み取りを、調査の担当だけに絞る。原因の経路（新しいログのイベント、例外の本文、取り込みのファイル）を、フラグかデプロイで止める。
   - 保管庫の侵害の疑い：保管庫の操作を止める。順に、(a) vault-web を WAF で止める（番号の入力と表示を止める）、(b) `<brand>-hr-vault-assertion` の鍵を無効にする（人事の側からの保管庫の呼び出しがすべて止まる）、(c) 保管庫の PrivateLink のエンドポイントの接続を拒む。止めても、人事・勤怠・給与の計算と振込ファイルは続く（[my-number-vault.md](../architecture/my-number-vault.md) の 13 節）。判断は IC とセキュリティの担当。
   - 担当者のアカウントの乗っ取りの疑い：その担当者の `mn_handlers` の指定をテナントの事務取扱責任者に止めてもらい、セッションを失効させる。
3. **範囲を確かめる**（値を写さない）：
   - どこに（ロググループ、S3 の接頭辞、保管庫の外への応答）、いつから、何件、どのテナントの、どの `mn_ref`（または行の位置）か。
   - 誰が読めたか（CloudTrail のログ・S3 の読み取りの記録、保管庫の `mn_access_log` と ALB の記録）。
   - 持ち出されたのは平文か暗号文か。暗号文なら、鍵（`vault-mn`）の使用に異常がないか。高度な暗号化の措置が講じられていれば報告を要しないとされる（[ガイドライン](https://www.ppc.go.jp/legal/policy/my_number_guideline_jigyosha/) の別添 2）。当てはまるかは法務が判断する。
   - 本人の数（100 人を超えるか）、不正の目的か（報告の対象の事態の判断の材料。別添 2）。
4. **テナントへ知らせる。** 本システムが委託先に当たるなら、委託元（テナント）への通知で報告の義務を免れ、通知の目安は、事態を知った時点から概ね 3〜5 日以内とされる（同じ別添 2。委託の関係は [intent.md](../intent.md) の L1 の確認待ち）。**迷ったら早く知らせる。** 通知には、事態の概要、対象の項目（「個人番号」）、件数、原因（わかった範囲）、二次の被害の有無、対策を書く。個人番号そのものは書かない。
5. **テナントの報告と本人への通知を支援する。** 個人情報保護委員会への報告（速報・確報）と本人への通知はテナント（個人番号関係事務実施者）が行う。本システムは、対象の `mn_ref` の一覧（テナントの画面で人に結べる形）と、アクセスの記録の抜き出しを出す。
6. **記録を消す。** CloudWatch Logs は該当のログストリームを消す。Object Lock のない S3 は該当の物体と版を消す。log-archive（Object Lock のコンプライアンスモード）は期間の中は消せないので、アクセスの制限と、読み取りの記録の監視で扱う。消した・消せなかったものと理由を、インシデントの記録に残す（番号は書かない）。
7. **原因を直す。** 番号が保管庫の外に出た経路を、CI の検査（[ADR-0058](../decisions/0058-pii-free-telemetry.md)）で次から止められるようにする。

#### 個人情報の出力

アラート：個人情報の形（既知の鍵の名前の値、トークンの接頭辞）の検出、テナントからの報告（通知のメールに額が書いてあった、別の人の明細が見えた）。

1. SEV3 から（給与・口座・扶養・健康の値なら SEV2）。セキュリティの担当を呼ぶ。
2. 広げない：原因の経路をフラグかデプロイで止める。ログの読み取りを絞る。
3. 範囲を確かめる：どの区分（[security.md](../architecture/security.md) の 4 節）の値が、どこに、何件、誰に見えたか。別の人の明細・給与が見えたなら、次の「テナントの分離の破れ・権限の迂回」も行う。
4. ログの該当の行を消す（上の 6 と同じ）。
5. 法務と、個人データの漏えい等の報告の要否を決める（個人情報保護法。[security.md](../architecture/security.md) の 10 節）。

#### 給与の計算の誤り（支給日の後）

アラート：再現の抜き取りの不一致、`ENGINE_DRIFT`、合成の給与の実行の不一致、テナントからの報告（控除の額がおかしい）、規則表の誤りの発見、ゴールデンデータの事例の追加で過去の誤りが分かった。

1. **SEV2** で宣言する（多くのテナント、全員に効く誤り（規則表・エンジン）なら **SEV1**）。QA、Dev のテックリード、給与の支援の担当を呼ぶ。
2. **新しい確定を止める。** `ops.payroll_finalize_hold` を、影響の見込みのあるテナント（規則表・エンジンの誤りなら全テナント）に有効にする。振込の締め切りが近いテナントは、給与の支援の担当が個別に状況を伝え、保留を解く条件（原因の範囲の外と確かめられた実行）を IC が決める。
3. **原因を分ける。**

   | 原因 | 見分け方 | 直し方 |
   | --- | --- | --- |
   | 規則表の誤り | 誤った規則表の版を使った実行だけに出る。元の資料との照合で分かる | 訂正の版を公開する（[ADR-0030](../decisions/0030-rule-table-ingestion-and-verification.md)）。遡及の候補が自動で作られる |
   | エンジンの誤り | 特定のエンジンのダイジェストの実行に出る。ゴールデンデータの事例で再現できる | ゴールデンデータの事例を先に足し、エンジンを直す（[delivery.md](../architecture/delivery.md) の 9 節）。過去の期間の扱いは 5 |
   | テナントの設定の誤り | 特定のテナントの設定の版に出る | テナントが設定の新しい版を有効にする。過去の期間は遡及の候補か手の調整 |
   | 入力の誤り | 特定の人・項目に出る。入力の文書を見て分かる | 人事・勤怠のデータを業務プロセスで直す。遡及の候補が作られる（[ADR-0028](../decisions/0028-retro-deltas-and-bonus-runs.md)） |

4. **範囲を決める。** 結果の記録（入力のハッシュ、規則表の版の一覧、エンジンのダイジェスト、設定の版。[ADR-0026](../decisions/0026-payroll-run-stages-and-input-snapshot.md)）から、影響を受けた実行・人・項目の一覧を作る。一覧は ID と件数で、テナントの画面で人に結べる形にする。
5. **正しい額を出す。** 影響を受けた期間を、直した規則表・エンジン・設定で計算し直す（`parallel` の実行。確定しない）。人・項目ごとの差を、不足（払い足りない）と過払いに分ける。
   - エンジンの誤りでは、遡及の再現の確認が `ENGINE_DRIFT` で止まる（[ADR-0028](../decisions/0028-retro-deltas-and-bonus-runs.md)）。これは意図した動きで、エンジンの修正の影響は遡及に混ぜず、この手順の差の一覧として扱う。差の一覧を QA が確かめ、エンジンの修正の判断（対象の項目と期間）を記録してから、遡及の窓の再現の確認を新しいダイジェストで通す手順は、[payroll-engine.md](../architecture/payroll-engine.md) の runbook（`payroll-reproducibility-mismatch.md`）で決める（持ち越し）。
6. **直す（テナントが判断し、担当が業務プロセスで行う。システムは自動で直さない。[intent.md](../intent.md) の Non-goals）。**
   - 不足：`off_cycle` の実行で差を払う。できるだけ早く払う。支払いの遅れの扱いは社労士の確認に回す。
   - 過払い：次の給与から自動では差し引かない（24 条の協定と本人の同意が要る。[payroll-engine.md](../architecture/payroll-engine.md) の L28）。テナントが本人と相談して決める。
   - 源泉所得税・社会保険料の差：遡及の扱いの決定表（DT-PAY-003）と年末調整での精算、届出の訂正の要否を、給与の担当と税理士・社労士が決める。
   - 明細：差の支払いの明細（遡及の行と期間を示す）を出す。確定した明細は書き換えない。
   - 仕訳：直す仕訳を足す（逆仕訳と調整。[ADR-0037](../decisions/0037-payroll-journal-export.md)）。出力した束は作り直さない。
   - 振込ファイルを銀行に渡した後、振込指定日の前に誤りが分かった：テナントが銀行と組戻し・差し替えを相談する。本システムは、取消（`payroll_cancel`）と作り直しを支える（支払の前の取消。[ADR-0004](../decisions/0004-payroll-engine.md)）。
7. **テナントへ知らせる。** 原因の種類、影響を受けた実行・人数・項目、直し方の案、本システムの側の修正の予定。個人の額は書かない（テナントの画面で見てもらう）。
8. **保留を解く。** 原因を直し、合成の給与の実行とゴールデンデータの全件が通り、影響の範囲の外と確かめられたテナントから、`ops.payroll_finalize_hold` を解く。

#### テナントの分離の破れ、権限の迂回

アラート：テナントからの報告（他のテナント・範囲の外の人のデータが見えた）、レポートと API の判定の突き合わせの不一致、テナントの分離の性質の本番の抜き取りの不一致。

1. **SEV1** で宣言する（1 テナントの中の範囲の外の閲覧だけなら SEV2）。セキュリティの担当、Dev のテックリード、PM を呼ぶ。
2. 原因の機能を止める。フラグで止められなければ、直近のデプロイを戻す。どちらも効かないなら、影響の経路（特定のレポート、一括の出力、API）を ops フラグか WAF で一時に止める。
3. 範囲を特定する：機微なドメインの閲覧の記録（[ADR-0020](../decisions/0020-sensitive-read-audit-and-access-explanations.md)）で、誰が、どの人の、どのドメインを、どの経路で見たか。要求のテナントと行のテナントが合わない記録を探す。
4. 権限の方針の誤りなら、前の版の写しを有効化して戻す（`security-policy-rollback.md`。[security-model.md](../architecture/security-model.md) の 17 節）。
5. 法務へ連絡し、個人データの漏えい等に当たるか、報告の主体を判断してもらう。

#### 依存先の障害

| 依存先 | 見るもの | すること |
| --- | --- | --- |
| Aurora の writer | 書き込みの 503、フェイルオーバーのイベント | 自動のフェイルオーバーを待つ。5 分を超えたら手動（[disaster-recovery.md](disaster-recovery.md) の A）。打刻は端末に貯まる |
| Valkey | 権限の表を DB から読んでいる（遅い） | 画面の p95 を見る。悪化していれば api を増やす |
| SQS・Relay | outbox の遅れ | 業務プロセスのステップ、通知、束の配布が遅れる。支給日の前なら、給与の実行の里程標を見る |
| KMS | 暗号・復号の失敗、`ThrottlingException` | 給与の入力の固定（S3）、振込ファイル、口座の表示、保管庫が止まる。支給日の前なら SEV2 に上げる。AWS サポート |
| 保管庫 | 保管庫の呼び出しの失敗 | 人事・給与は続く。番号の提出と書類の生成が止まる旨をテナントに知らせる |
| テナントの IdP | SSO のログインの失敗（接続別） | テナントに知らせる。非常用の管理者のログインを案内する（`idp-outage.md`） |
| メールの送信 | 通知の失敗 | 受信箱は画面で見られる。支給日の前の明細の公開の通知の遅れを告知する |
| 公的な資料の頁（規則表の監視） | 頁の変化の検知の失敗 | 改正の暦の手の確認に切り替える（`statutory-rate-calendar.md`） |

### オンコール

- 一次は Ops、二次は Dev（週替わり）。一次が 5 分（SEV1）・15 分（SEV2）で応答しなければ、二次を呼ぶ。
- **セキュリティの担当**も当番を持つ（マイナンバー・個人情報・分離の判断、`security:sensitive` の緊急の変更の承認、法務への連絡）。
- **給与の当番**を、支給日の前の 5 営業日と、毎月の支給日の翌営業日に置く（給与の支援の担当と QA）。
- 呼び出しの道具と当番の表は、E12 で決める。

## エスカレーション

| 状況 | 連絡先 |
| --- | --- |
| SEV1 の宣言 | Ops の責任者、Dev のテックリード、PM |
| マイナンバー、個人情報、テナントの分離、権限の迂回 | 上記に加えて、セキュリティの担当と法務（報告と通知の要否） |
| 給与の計算の誤り、支給日の振込 | 上記に加えて、QA と給与の支援の担当。解釈に関わるものは社労士・税理士 |
| リージョンの切り替えを考える | Ops の責任者（承認）。[disaster-recovery.md](disaster-recovery.md) |
| AWS 側の障害 | AWS サポートにケースを開く |
| 1 時間たっても被害を止められない | 重さを 1 段上げる |

## 事後

- **振り返り**を、SEV1・SEV2 では必ず、解決から 5 営業日以内に行う（責任追及をしない）。書くこと：時系列、影響（時間、テナント数、人数、消費したエラーバジェット、遅れた支払い）、セキュリティの影響（番号・個人情報の件数、通知・報告の有無）、給与の影響（誤った実行・人数・項目、不足と過払いの件数、直した方法）、検知までの時間、原因、再発防止の対策。
- **再発防止を Intent にする。** Claude が調査結果から Intent の Issue を起票する（Maintain 段）。調査に Claude を使うときは、人が取り出した、個人情報とマイナンバーを含まないものだけを渡す（[ADR-0053](../decisions/0053-operator-access-and-vault-break-glass.md)）。
- 給与の誤りは、ゴールデンデータの事例・決定表の行を足したかを QA が確かめる。マイナンバー・個人情報は、`THR-` の行と CI の検査を足すかをセキュリティの担当が判断する。
- この手順と、関係した個別の runbook で足りなかったことを反映する。
