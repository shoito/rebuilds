# Runbook: デプロイとロールバック

- Owner: Ops
- 対応するアラート: api の blue/green の自動のロールバック、デプロイの後の SLO のバーンレート、フラグのガードによる自動の停止、デプロイの直後の合成の給与の実行の不一致（[observability.md](../architecture/observability.md) の 5.2 節）
- 最終確認日: 2026-09-28

流れは [delivery.md](../architecture/delivery.md)、CI/CD と Terraform の構成は [infrastructure.md](../architecture/infrastructure.md) の 10 節、給与に効くフラグと凍結は [ADR-0063](../decisions/0063-payroll-flags-pinning-and-freeze-windows.md)、規則表のリリースは [ADR-0062](../decisions/0062-rule-table-release-calendar.md)、保管庫のパイプラインは [ADR-0057](../decisions/0057-vault-delivery-separation.md) にある。

## 症状

次のときに使う。

- 本番（prod・vault-prod）へデプロイするとき（アプリ、Payroll Compute のイメージ、マイグレーション、Terraform）
- 規則表を本番に公開するとき
- 給与に効くフラグをテナントで有効にするとき
- デプロイの後に、エラーの率・業務プロセスの完了の失敗・打刻の失敗・合成の給与の実行の不一致が出たとき
- フラグのガードが、フラグを自動で切ったとき

## 影響

- 通常のデプロイ：利用者への影響はない。
- 失敗したデプロイ：画面・API の可用性（99.9%）を消費する。支給日の前は、給与の経路の可用性（99.95%）を消費する。
- **給与の計算の誤りは 5xx にならない。** 合成の給与の実行、確認の検査の警告の増加、夜間の再現の抜き取りで現れる。確定・支払の後に見つかると、[incident-response.md](incident-response.md) の「給与の計算の誤り（支給日の後）」になる。
- 打刻の受付の誤りは、端末に貯まった打刻として後から届く（失われない）が、36 協定の警告が遅れる。

## 確認

### デプロイの前

1. 対象のコミットが staging へデプロイ済みで、E2E、スモーク、k6、**ゴールデンデータセットの全件、合成の給与の実行**が通っている。
2. デプロイできる時間帯である（平日 10〜17 時。金曜の 15 時以降と年末年始は修正だけ）。
3. **支給日の前の凍結の日でないか**を、凍結の暦で確かめる。凍結の日に給与の経路（`payroll:calc`、振込ファイル、明細、Payroll Compute のイメージ、給与の DB のスキーマの contract）を含むなら止める。例外は Ops の責任者と QA の承認を記録してから。
4. 月初の 3 営業日（4 月 1 日の発効、1 月の源泉の切り替えの直後を含む）は、業務プロセスと有効日付のパッケージの変更を避ける。
5. マイグレーションが expand だけか。contract を含むなら、1 つ前のリリースで参照をやめていること、PITR の直近の復元できる時刻が 5 分以内であることを確かめる。
6. SLO のダッシュボードで、エラーバジェットが残っている。
7. 進行中のインシデント、`AuroraGlobalDBRPOLag` の超過、給与の実行の里程標の遅れ（`system`）がない。
8. `security:sensitive` の PR を含むなら、2 人の承認がそろっている。
9. 保管庫の変更なら、同じ日に人事の側の本番のデプロイがない（あれば日をずらす）。

### デプロイの後（入れ替えが終わってから 15 分）

| 見るもの | 正常 | 異常 |
| --- | --- | --- |
| 画面・API の失敗の率（エッジ） | デプロイの前と同じ | 0.1% を超える |
| 画面の操作の p95・p99 | 500ms・1.5 秒以内 | 超える |
| 打刻の p99、打刻の失敗 | 300ms 以内、0 に近い | 超える・増える |
| 業務プロセスの完了の失敗、`SAME_DAY_CONFLICT` の急増 | デプロイの前と同じ | 2 倍以上 |
| 権限の拒否の件数 | デプロイの前と同じ | 2 倍以上（判定の誤りか設定） |
| 合成の給与の実行（デプロイの直後に自動で走る） | 期待値と全件一致 | 1 件でも違う |
| 合成監視 | 成功 | 2 回続けて失敗 |
| 個人情報・個人番号の形の走査 | 0 件 | 1 件以上（直ちにインシデント） |

## 対処

### 通常のデプロイ（アプリ）

1. ワークフロー「prod へデプロイ」を、コミットのイメージのダイジェストを指定して起動する（Ops の承認）。
2. 順序は [delivery.md](../architecture/delivery.md) の 5.2 節：マイグレーション（expand）→ relay・worker・loader・egress-worker・audit-archiver → bp-worker → api（blue/green のカナリア 10% → 100%）→ Payroll Compute のイメージの登録。
3. api のカナリアの間、「デプロイの後」の表を見る。自動のロールバックのアラームが鳴れば、ロールバックが終わったことを確かめて止める。
4. 入れ替えの後 15 分、「デプロイの後」の表を見る。

### Payroll Compute のイメージ

1. 新しいイメージは、次に**入力を固定する**実行から使われる。進行中の実行（`frozen`〜`in_review`）は、記録したダイジェストで続く。切り替えで進行中の実行は変わらない。
2. 登録の直後の合成の給与の実行が全件一致することを確かめる。
3. 一致しなければ、「現在のエンジンのダイジェスト」の設定を前のダイジェストに戻す（次の実行から前のイメージを使う）。その間に新しいダイジェストで入力を固定した実行があれば、一覧にし、給与の担当に固定し直しを依頼する（確定の前なら `in_review` の中で固定し直せる。[payroll-engine.md](../architecture/payroll-engine.md) の 4 節）。確定の後なら [incident-response.md](incident-response.md) の「給与の計算の誤り」。
4. 夜間の CI の「前のリリースのエンジンとの比較」で説明のない差が出ていたら、デプロイを止める。

### マイグレーション

1. expand は通常のデプロイの最初に行う。追記のみの表と有効日付の 3 つのテーブルの権限（アプリのロールに `UPDATE`・`DELETE` がない）を、マイグレーションの後に検査のスクリプトで確かめる。
2. contract（列・表の削除）は、凍結の日と月初の 3 営業日を避け、別のリリースで行う。
3. **マイグレーションは戻さない。** 失敗したら前へ進める修正を書く。

### 規則表の公開

1. 束の署名、SHA-256、照合の記録（`verified_by ≠ imported_by`）を確かめる（ワークフローが自動で検査する）。
2. staging で公開し、ゴールデンデータセットの全件と合成の給与の実行が通っていることを確かめる。
3. 本番の公開（`rules.publish`。Ops の承認）。公開は `published` にする 1 トランザクション。
4. 直後の合成の給与の実行が全件一致することを確かめる。
5. 誤りが分かったら、公開を戻さない（戻すと、その版で計算した実行の再現が崩れる）。訂正の版を同じ流れで出し、遡及の候補を確かめる（`rule-table-correction.md`。[payroll-jp-rules.md](../architecture/payroll-jp-rules.md) の 16 節）。まだその版で確定した実行がなく、適用の日より前なら、訂正の版を急いで公開し、新しい版で入力を固定し直してもらう。

### 給与に効くフラグの有効化

1. そのテナントの直近の確定した期間で、フラグあり・なしの影の比較（`parallel` の実行）が済み、差の説明を給与の担当と QA が承認していることを確かめる。
2. 有効にするのは、テナントの次の実行の入力の固定の前。期間の途中の実行があるなら、その実行の確定の後にする。
3. 有効にした後、次の実行の確認の検査の警告の件数（1 人あたり）を見る。

### Terraform

1. plan の差分を 2 人（作成者と別）で読む。`regional/keys`、WAF、IAM、`vault/*` は `security:sensitive`。
2. 状態を持つリソース（Aurora、S3、KMS の鍵）の削除・置き換えは CI で拒まれる。拒まれたら止めて Dev のテックリードに相談する。
3. WAF の新しい Block は、まず Count で 24 時間出してから Block にする。

### 保管庫（vault-prod）

1. 保管庫のパイプライン（別の承認者：セキュリティの担当と Ops の責任者）で行う。人事の側と同じ日にしない。
2. 人事の側と保管庫の間の API は新旧の両方と互換を保つ。互換を壊す変更は、受ける側（保管庫）を先に出す。
3. デプロイの後、保管庫の `status` の合成監視と、アクセスの記録の書き込み（監視の呼び出しで 1 行増える）を確かめる。

### 悪化したとき

1. **フラグで戻す。** 新しい振る舞いのフラグが原因なら、AppConfig で切る。給与に効くフラグは、進行中の実行には効かない（値は実行に固定されている）。次の実行から前の振る舞いになる。
2. **フラグで戻せないとき、アプリを戻す。** 1 つ前のイメージのダイジェストで再デプロイする（「前のリリースを再デプロイ」のワークフロー）。api の blue/green の途中なら、旧い側に戻す。
3. **Payroll Compute は上の「Payroll Compute のイメージ」の 3。**
4. **マイグレーションは戻さない。**
5. **有効日付の書き込みの誤りで、差分・版がおかしくなったら**：戻した後、夜間の整合の検査を手で走らせ、`temporal-consistency-mismatch.md`（[object-model-and-effective-dating.md](../architecture/object-model-and-effective-dating.md) の 15 節）に従う。誤った差分は、取消・訂正の業務プロセスで直す（テーブルを直接直さない）。
6. 戻しても直らなければ、インシデントを宣言する（[incident-response.md](incident-response.md)）。

## エスカレーション

- 戻しても 15 分以内に SLO が回復しない → インシデントを宣言する。
- 合成の給与の実行の不一致、夜間の再現の抜き取りの不一致 → SEV2 以上。QA と Dev のテックリードを呼ぶ。本番のテナントの確定を止めるか（ops フラグ `ops.payroll_finalize_hold`）を IC が判断する。
- 個人情報・個人番号の形の検出 → SEV2 以上。セキュリティの担当を呼ぶ（[incident-response.md](incident-response.md)）。
- テナントの分離・権限の迂回の疑い → SEV1。セキュリティの担当と Dev のテックリード。
- マイグレーションが途中で止まり状態がわからない → Dev のテックリード。
- 凍結の日の例外のデプロイが必要 → Ops の責任者と QA の承認。

## 事後

- 調査結果を Intent の Issue として起票する（Maintain 段）。
- デプロイの失敗を CI で防げたなら、CI の検査（ゴールデンデータの分類、決定表の行、`THR-` の行、ガードの条件）を足す提案を Dev と QA に出す。
- この手順で足りなかったことを、ここに反映する。
