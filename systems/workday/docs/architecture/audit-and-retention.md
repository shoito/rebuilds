# Audit and retention: Workday

監査の記録と保存を決める。監査ログ（変更、閲覧、権限、ログイン、出力、運用者の操作）、改ざんの検知（ハッシュの連鎖、Object Lock、日次の署名）、保存の期間の規則表、削除と保全（リーガルホールド）、監査人の画面、電子帳簿保存法の要件への対応を扱う。

前提の決定は、人事のデータの変更を業務プロセスのイベントと有効日付の差分で残すこと（[ADR-0002](../decisions/0002-effective-dated-data-model.md)、[ADR-0003](../decisions/0003-business-process-engine.md)）、機微なドメインの閲覧を記録すること（[ADR-0020](../decisions/0020-sensitive-read-audit-and-access-explanations.md)）、マイナンバーの記録を保管庫の中で連鎖にすること（[ADR-0046](../decisions/0046-purpose-bound-vault-api-and-access-log.md)）。保管の場所（log-archive のアカウント）は [infrastructure.md](infrastructure.md)、鍵は [security.md](security.md) にある。この文書で決めたことは次の ADR にある。

| ADR | 決定 |
| --- | --- |
| [0048](../decisions/0048-audit-log-hash-chain-and-anchoring.md) | 監査ログは、操作と同じトランザクション（閲覧は応答の前）で Aurora の追記のみの表に書く。書き出しの処理が、安定の境界（10 秒）を過ぎた行をテナントごとのハッシュの連鎖の区切り（セグメント）にし、log-archive のコンプライアンスモードの Object Lock に置く。日ごとに連鎖の頭を KMS の非対称の鍵で署名して残す。DB と保管の突き合わせと連鎖の検証を日次に行う |
| [0049](../decisions/0049-retention-rules-table-and-legal-hold.md) | 保存の期間を、データの種類・根拠・起算の事象・期間・確認の状態を持つ規則表（データ）で持つ。確認待ちの間は、候補のうち長いほうを既定にする。期限の計算と削除はデータの種類ごとのジョブで行い、保全が優先する。追記のみの表の削除は専用のロールだけが行い、削除も監査に残す |
| [0050](../decisions/0050-electronic-books-act-readiness.md) | 電子帳簿保存法の対象になりうる記録（源泉徴収簿に当たる給与の記録、給与の仕訳の出力）に、最低限の要件（システムの概要書などの備付け、見読、ダウンロードの求めへの対応）と、優良な電子帳簿に相当する機能（訂正・削除の履歴、相互の関連、検索）を持たせる。対象になるかの判断はテナントと税理士が行い、システムは結論を出さない |

## 1. 目的と範囲

- 扱う：監査の記録の系統と中身、書き込みの経路、改ざんの検知、保管、監査人の画面と出力、保存の期間の規則表、期限の計算と削除、保全、電子帳簿保存法の要件への対応。
- 扱わない：閲覧の記録の対象のドメインの決め方（[security-model.md](security-model.md) の 10 節）、保管庫の記録の中身（[my-number-vault.md](my-number-vault.md) の 8 節）、アプリのログとテレメトリー（[observability.md](observability.md)）、帳簿の出力の形（[reporting.md](reporting.md) の 5.1 節）。
- 法令の保存の期間の解釈は結論を出さない（[intent.md](../intent.md) の L2・L5）。

## 3. 監査の記録の系統

| 系統 | 記録するもの | 正本 | 書く時点 |
| --- | --- | --- | --- |
| 人事のデータの変更 | 差分、版、取消・訂正の印 | `<facet>_changes`・`<facet>_versions`（[object-model-and-effective-dating.md](object-model-and-effective-dating.md) の 4 節） | 業務プロセスの完了と同じトランザクション |
| 業務プロセス | 起票、承認、差し戻し、却下、委任、取消、訂正、担当の差し替え | `bp_events`（[business-process-engine.md](business-process-engine.md) の 6 節） | 状態の変化と同じトランザクション |
| 給与・支払・仕訳 | 実行の段、確定、取消、振込ファイルの承認、仕訳 | `payroll_runs` の遷移、`bp_events`、仕訳（追記のみ） | 同上 |
| テナントの監査（`audit_events`） | 下の 3.1 節 | Aurora の追記のみの表 | 操作と同じトランザクション。閲覧は応答の前 |
| プラットフォームの監査（`platform_audit_events`） | 運用者の本番へのアクセス、break-glass、テナントの停止・作成・削除、規則表の公開、保存の期間の削除の実行、保全の設定 | Aurora（RLS の外）の追記のみの表 | 同上 |
| マイナンバー | 保管庫のすべての操作 | 保管庫の `mn_access_log` | 同上（保管庫の中） |
| AWS の操作 | CloudTrail（組織の証跡）、KMS の操作 | log-archive | AWS |

- 人事のデータの変更の「前後の値」は、版の表の前後の版から出す。`audit_events` に値を写さない（二重に持たない）。
- 監査の画面（6 節）は、これらの系統を 1 つの時系列に並べて見せる。

### 3.1 `audit_events` の事象

| 群 | 事象の例 |
| --- | --- |
| 権限 | 方針の下書きの編集・有効化・戻し、所属とロールの変更の完了、職務分掌の違反（止めた・警告・夜間の走査）、代理のログインの開始・終了・全要求（[security-model.md](security-model.md) の 10.1 節） |
| 閲覧 | 機微なドメインの閲覧（要求ごと）、拒否のまとめ（1 利用者・1 ドメイン・1 時間）、`known_at` の問い合わせ（[ADR-0020](../decisions/0020-sensitive-read-audit-and-access-explanations.md)） |
| 出力 | レポートの実行と取り出し、一括の出力、明細の閲覧、振込ファイルの取り出し、賃金台帳などの帳簿の出力 |
| 設定 | 業務プロセスの定義の有効化、項目・勘定の対応の版の有効化、テナントの規則表（健康保険組合の料率）の公開、保存の期間の延長、保全 |
| 認証 | ログインの成功・失敗、再認証、SSO の接続の変更、API の利用者・打刻機の鍵の発行と取消、セッションの失効 |
| 連携 | 一括の取り込みの確定、移行の実行、Webhook の登録 |

- 記録の形：`tenant_id`、`id`（UUIDv7）、`recorded_at`、`event_type`、`actor_type`（`worker`・`integration`・`terminal`・`system`・`operator`）、`actor_id`、`on_behalf_of`、`target_type`・`target_id`、`result`、`reason_code`、`request_id`、`client_ip_prefix`（/24）、`details`（許可リストのスキーマ。値を入れない）。
- **記録に個人情報の値を入れない。** 氏名・住所・額・口座・番号は入れず、ID だけを入れる。変更の前後の値は版の表を参照する。

## 4. 改ざんの検知（[ADR-0048](../decisions/0048-audit-log-hash-chain-and-anchoring.md)）

```
操作のトランザクション ──▶ Aurora audit_events（追記のみ。アプリのロールは INSERT だけ）
                              │ 書き出し（audit-archiver。1 分ごと）
                              │  recorded_at ≤ 今 − 10 秒 の行を、テナントごとに id の順に取る
                              ▼
         セグメント（テナント × 1 分）：行の正規の形（RFC 8785）の列
         seg_hash = SHA-256(prev_seg_hash || SHA-256(各行) の列)
                              ▼
   log-archive S3 audit/{tenant}/{yyyy}/{mm}/{dd}/{seq}.jsonl.gz（Object Lock コンプライアンス、保存の期間）
                              ▼ 毎日 0 時（日本時間）
   日の署名：全テナントのその日の最後の seg_hash の Merkle 根を、KMS の非対称の鍵 audit-anchor で署名し、
            anchors/{yyyy-mm-dd}.json に置く（別の接頭辞、同じ Object Lock）
```

- 書き込みのトランザクションは 5 秒で打ち切る（[ADR-0008](../decisions/0008-point-in-time-queries-and-activation-timers.md)）ので、10 秒の境界の後に古い `recorded_at` の行が現れない。境界の後に見つかった行（時計のずれなど）は「遅れの行」として次のセグメントに入れ、印を付ける。
- 行の順序は id（UUIDv7）の順で、テナントの中の連鎖だけを持つ。テナントをまたぐ直列の点を作らない。
- `prev_seg_hash` と各セグメントのハッシュを `audit_segments`（Aurora）にも置き、検証を速くする。
- 日次の検証（`audit-verifier`）：
  1. Object Lock の上のセグメントの連鎖を、テナントごとに頭から確かめる（前日の続きから）。
  2. 日の署名を確かめる。
  3. Aurora の `audit_events` の前日の行と、セグメントの行を突き合わせる（DB の行の消去・書き換えの検知）。
  4. 失敗は SEV2 で呼び出す（[runbooks/incident-response.md](../runbooks/incident-response.md)）。
- 保管庫の `mn_access_log` も同じ形で、保管庫の専用の接頭辞に置く（[my-number-vault.md](my-number-vault.md) の 8 節）。
- 業務プロセスのイベント（`bp_events`）と差分・版の表も、同じ書き出しの処理でセグメントにする（監査の正本の保全）。量が多いので、行の本体ではなく行のハッシュの列だけを連鎖にし、本体は Aurora とバックアップに置く案を E11 で決める（持ち越し）。
- テナントは、自分のテナントの日の連鎖の頭（ハッシュ）を画面から取り出して、手元に残せる。後で本システムが連鎖を書き換えていないことを、テナントが確かめられる。

## 5. 保存の期間の規則表（[ADR-0049](../decisions/0049-retention-rules-table-and-legal-hold.md)）

### 5.1 形

```sql
retention_rules (rule_id, version, data_kind text, legal_basis text, start_event text,
                 period_months int, period_basis text,        -- e.g. 'from_start_event' | 'from_next_jan_10_plus_1'
                 status text,                                   -- confirmed | pending_review
                 candidates jsonb,                              -- alternatives while pending
                 source_url, checked_on date, reviewed_by,
                 PRIMARY KEY (rule_id, version))
tenant_retention_overrides (tenant_id, rule_id, extend_months, reason, set_by, set_at)  -- extend only
legal_holds (tenant_id, id, scope jsonb, reason, set_by, set_at, released_by, released_at)
retention_executions (id, tenant_id, rule_id, data_kind, cutoff, rows_deleted, objects_deleted,
                      started_at, finished_at, approved_by)
```

- 規則表はテナントの外の共通のデータ（規則表の版と同じく、取り込み・確認・公開の手順を持つ。[ADR-0030](../decisions/0030-rule-table-ingestion-and-verification.md) の考え方）。
- テナントは延ばせる（`tenant_retention_overrides`）。短くはできない。
- `pending_review` の行は、`candidates` のうち最も長い期間で動く。

### 5.3 期限の計算と削除

- 日次のジョブが、データの種類ごとに、起算の事象（退職の日、支払期日など）と規則から `expires_on` を求め、候補を作る。
- 削除の方式：

| データ | 方式 |
| --- | --- |
| 時間で並ぶ表（打刻、監査ログ、閲覧の記録、実行の結果の行） | 月ごとのパーティションを、期限を過ぎ、保全がなければ `DROP` する |
| 主体で並ぶ表（退職者の facet の差分・版・現在） | 専用のロール `retention_purger` が、主体ごとに行を消す。追記のみのトリガーは、このロールと `retention_executions` の行のあるトランザクションだけを通す |
| S3 のオブジェクト | ライフサイクルと Object Lock の保存の期限。Object Lock の期限は規則の既定（長いほう）で置くので、確認で短くなっても、それより前には消せない（5.4 節） |

- 削除の実行は、テナントごとに件数の予覧を出し、本システムの運用の担当（2 人）が承認する（`platform_audit_events` に残す）。テナントの管理者には、削除の予定と結果を知らせる。
- 削除した主体を指す監査の記録の ID は残る（値は入っていない）。ID から人をたどれる表が消えれば、記録は個人を指さない。
- 保全（`legal_holds`）はすべての削除に優先する。保全の範囲は、テナント全体・従業員・期間で指定する。S3 は Object Lock のリーガルホールドを付ける。

### 5.4 Object Lock の期間と、期間の変更

- log-archive の Object Lock は、コンプライアンスモード（根のユーザーも消せない。期間を短くできない。[S3 Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)、2026-09-28 に確認）で、既定の期間（長いほう）を置く。
- 確認で期間が短くなっても、置いた Object Lock の期間は縮められない。短くなる見込みのあるデータ（振込ファイル、閲覧の記録）は、コンプライアンスモードではなく、ガバナンスモードか、Object Lock なしの暗号化と版の管理で持つ（[infrastructure.md](infrastructure.md) の 6 節）。
- 監査ログ（連鎖と日の署名）は、改ざんの検知が目的なのでコンプライアンスモードにする。

## 6. 監査人の画面と出力

- 権限は `audit` のドメイン（[security-model.md](security-model.md) の 3.1 節）。監査人（社内監査、監査法人）には、期限つきの利用者として `audit` を与える運用を勧める。
- 画面：
  - 従業員ごとの変更の履歴（差分、版、業務プロセスの案件、承認者、`known_at` の切り替え）
  - 業務プロセスの案件の全イベント
  - 権限の変更の履歴と説明の報告（[security-model.md](security-model.md) の 10.2 節）
  - 機微なドメインの閲覧の記録の検索（利用者別、対象別）
  - 出力と取り出しの記録
  - 連鎖の検証の結果（日ごと）と、テナントの連鎖の頭の取り出し
- 13 か月より古い記録は、log-archive のセグメントを Athena で読む非同期の実行（[reporting.md](reporting.md) の 4.3 節と同じ仕組み）。
- 監査人の画面の操作も記録する。

## 7. 電子帳簿保存法（[ADR-0050](../decisions/0050-electronic-books-act-readiness.md)）

### 7.1 確かめたこと

[国税庁 電子帳簿保存法一問一答【電子計算機を使用して作成する帳簿書類関係】](https://www.nta.go.jp/law/joho-zeikaishaku/sonota/jirei/pdf/03-2.pdf)（令和 7 年 6 月）を 2026-09-28 に確かめた。

- 電子計算機で一貫して作る国税関係帳簿書類は、一定の要件の下で電磁的記録で保存できる（法 4 条 1 項・2 項）。
- 電子取引の取引情報の保存の義務（法 7 条）は、所得税（**源泉徴収に係る所得税を除く**）と法人税の保存義務者が対象とされる（問 1）。
- 要件の概要（規則 2 条・5 条）：
  - すべての帳簿・書類：電子計算機処理システムの概要書などの備付け、見読可能装置の備付け。
  - 優良以外の帳簿と書類：ダウンロードの求め（電磁的記録の提示・提出の要求）に応じること（書類は検索の機能の確保に相当する要件を満たせば不要）。
  - 優良な電子帳簿：訂正・削除・追加の事実と内容を確認できるシステム、帳簿間の記録事項の相互関連性、検索の機能（日付・金額・取引先、範囲の指定、2 つ以上の項目の組み合わせ）。優良の要件をすべて満たせば、ダウンロードの求めの要件は不要。
- 保存の期間は、それぞれの税法の期間（問 3。法人の帳簿書類は 7 年、欠損金の生じた年度は 10 年）。

### 7.2 対象になりうる記録

| 記録 | 国税関係帳簿書類に当たるか | システムの対応 |
| --- | --- | --- |
| 源泉徴収簿に当たる給与の記録（支給額、社会保険料、源泉所得税の月ごと・人ごと） | 源泉徴収簿が法定の帳簿かは未検証。テナントが帳簿として扱うかを税理士と決める | 7.3 節の要件を満たす形で持つ |
| 給与の仕訳の出力 | テナントの会計システムの仕訳帳が正本。本システムの出力は入力の元 | 7.3 節の相互関連性（仕訳 ↔ 実行 ↔ 結果の行） |
| 扶養控除等申告書などの申告書 | 国税関係書類。電子の提出と保存の要件は E13 で確かめる | E13（保管庫の中） |
| 給与明細 | 所得税法の支払明細書。電子帳簿保存法の電子取引には当たらないと見られる（未検証） | [payments-and-accounting.md](payments-and-accounting.md) の 4 節の変わらない文書 |

### 7.3 システムが持つ機能

| 要件 | 本システムの形 |
| --- | --- |
| システムの概要書・操作説明書の備付け | リリースごとに、給与の計算と記録の流れの概要書と操作説明書を公開し、版を残す（[delivery.md](delivery.md) の 7 節） |
| 見読可能 | 画面と PDF の出力（[reporting.md](reporting.md)） |
| ダウンロードの求めへの対応 | 期間・従業員・項目の条件で、給与の記録と仕訳を CSV で出す一括の出力（[integrations-and-bulk.md](integrations-and-bulk.md) の 3.5 節）。税務の調査のための出力の手順を操作説明書に書く |
| 訂正・削除・追加の事実と内容 | 確定した結果は書き換えない。取消・遡及の差額・逆仕訳の記録で直す（[ADR-0004](../decisions/0004-payroll-engine.md)、[ADR-0028](../decisions/0028-retro-deltas-and-bonus-runs.md)、[ADR-0037](../decisions/0037-payroll-journal-export.md)）。履歴は監査の画面で見られる |
| 帳簿間の相互関連性 | 仕訳の行 → 実行と段 → 結果の行 → 入力の文書のハッシュをたどれる |
| 検索（日付・金額・取引先、範囲、組み合わせ） | 給与の記録は支給日・金額・従業員（取引先に当たる）で、範囲と組み合わせの条件で検索できる。仕訳は会計の日・金額・勘定で |

- どの要件で保存するか（優良か、そうでないか）の判断と、事務処理の規程はテナントが持つ。システムは要件の対応表（上の表）と、規程の雛形を出す。

## 8. 規模

- `audit_events`：S1 で 1 日数百万件（機微な閲覧が主。[security-model.md](security-model.md) の 11 節）。1 件 0.5 KB で 1 日 1〜2 GB。Aurora に 13 か月（月ごとのパーティション）。
- セグメント：テナント × 1 分。S1 の 600 テナントで 1 日最大 約 86 万個（活動のない分は作らない）。小さな物体が多いので、1 時間ごとにまとめた物体を作り、連鎖はセグメント単位で保つ案を E11 で測って決める。
- log-archive の量：S1 で 1 年 1 TB 未満（圧縮の後。初期見積もり）。

## 9. 障害のときの振る舞い

| 障害 | 振る舞い |
| --- | --- |
| `audit_events` の書き込みの失敗 | 操作ごと失敗させる。閲覧も、機微なドメインは記録できなければ返さない（fail closed） |
| 書き出しの処理の停止 | Aurora に行が残る。遅れ（最古の未書き出しの行の経過時間）が 15 分で警告、1 時間で呼び出す。追いつくときも id の順で連鎖を保つ |
| 連鎖の検証の失敗・DB とセグメントの不一致 | SEV2。原因（バグか改ざん）を調べる。書き出しを止めず、以後のセグメントに「検証の失敗の後」の印を付ける |
| 保存の期間の削除の誤り（消しすぎ） | 削除は予覧と 2 人の承認を経る。消したものは PITR（35 日）で隔離した復元から戻す（[runbooks/disaster-recovery.md](../runbooks/disaster-recovery.md) の論理的な破損） |
| 日の署名の鍵が使えない | 署名を遅らせ、使えるようになったら前の日の分から署名する。連鎖そのものは続く |

## 10. セキュリティとプライバシー

- `audit_events` の表は、アプリのロールに `INSERT` と `SELECT`（`audit` の権限の経路だけ）を与え、`UPDATE`・`DELETE` を与えない。削除は `retention_purger` だけ。
- log-archive のバケットは log-archive のアカウントの鍵で暗号化し、prod のアカウントの主体が消せない・読めないようにする（[security.md](security.md) の 5 節）。
- `audit-anchor` の鍵の `Sign` は `audit-verifier` のロールだけ。
- 監査の記録の検索も記録する。
- 記録に個人情報の値を入れないことを、許可リストのスキーマと性質ベーステストで確かめる。

## 13. 未解決の問い

### 決定

- **監査の記録に個人情報の値を入れない。** 変更の前後の値は版の表を参照する。
- **連鎖はテナントごと。安定の境界の 10 秒の後に書き出す。日ごとに署名する。**
- **保存の期間は規則表のデータで持ち、確認待ちの間は長いほうで動く。テナントは延ばすだけ。**
- **期間が短くなりうるデータにコンプライアンスモードの Object Lock を使わない。**
- **電子帳簿保存法の対象になるかの判断はテナントと税理士。システムは要件に相当する機能を持つ。**
