# AGENTS.md — Workday

Workday の再構築の設計。リポジトリ共通のルールはルートの [AGENTS.md](../../AGENTS.md) にある。このリポジトリには設計だけを置き、実装は Workday の開発リポジトリで行う（[リポジトリ共通の ADR-0005](../../docs/decisions/0005-design-record-repository.md)）。

- [docs/intent.md](docs/intent.md) — 何を、なぜ作るか
- [docs/architecture/](docs/architecture/README.md) — 全体像、規模の段階、非機能要件、領域ごとの設計
- [docs/decisions/](docs/decisions/README.md) — ADR。特に 0002（有効日付のデータモデル）、0004（給与計算エンジン）、0005（権限とマイナンバー）

## この題材に固有の規則（開発リポジトリで守る）

### 給与計算

- **金額は `packages/money` の型だけで扱う。** 円は `bigint`、率や途中の値は固定小数点の型で持つ。`number` と浮動小数点で金額を計算しない。丸めは、法令ごとに名前を付けた関数（例：社会保険料の被保険者負担分の「50 銭以下切り捨て」）だけで行う。`Math.round` などの汎用の丸めを金額に使わない（ADR-0001、ADR-0004）。
- **税額表と保険料率は、データとしてバージョンを管理する。** 源泉徴収税額表、社会保険の料率、標準報酬月額の等級表、雇用保険の料率は、公的な資料から取り込んだ規則表として、適用開始日つきで持つ。値をコードに書き写さない。取り込んだ表は、出典の URL・取得日・ハッシュを記録し、2 人で確かめる（ADR-0004）。
- **規則は決定表で書き、表駆動テストで確かめる。** 税の区分（甲欄・乙欄）、保険の加入の要否、介護保険の対象年齢、端数の処理、割増率のような条件の組み合わせは、`spec.md` の決定表（`DT-*`）に書く。テストは表を `spec.md` から直接読む。
- **ゴールデンデータセットを通す。** 給与計算に触れる PR は、ゴールデンデータセット（合成の従業員と、社労士・税理士が確かめた期待値の組）の全件一致を必須のチェックにする。期待値を実装に合わせて書き換えない。期待値の変更は QA が承認し、法令の解釈に関わるものは社労士・税理士の確認を記録する。
- **計算は純粋関数にする。** 給与計算の関数は、入力のスナップショット・規則表のバージョン・エンジンのバージョンだけから結果を決める。現在時刻、乱数、DB の直接の読み取り、環境変数を計算の中で使わない。同じ入力で同じ結果になることを、再計算のテストで確かめる（ADR-0004）。
- **確定した給与の結果を書き換えない。** 誤りは、次の計算での遡及の差額か、取消と再計算で直す。仕訳は追記だけで、逆仕訳で直す。

### 有効日付と業務プロセス

- **有効日付のテーブルを直接 `UPDATE`・`DELETE` しない。** 変更は、有効日付のライブラリ（`packages/temporal`）を通して、新しいバージョンとして書く。履歴のテーブルは追記だけにする（ADR-0002）。
- **有効日付には性質ベーステストを付ける。** 期間が重ならないこと、任意の時点の問い合わせが履歴から再現できること、訂正と取消の後でも過去の時点の見え方（知っていたこと）が変わらないことを、fast-check で確かめる（ADR-0002）。
- **人事のデータは業務プロセスを通して変える。** 入社・異動・退職・給与の変更などは、業務プロセスのイベントとして記録し、承認を経て反映する。一括の取り込みも同じ業務プロセスを通す。管理の画面や SQL で、業務プロセスを迂回して変えない（ADR-0003）。

### 権限と個人情報

- **マイナンバーは保管庫の外で扱わない。** 個人番号の平文は、保管庫のサービスの中でだけ扱う。人事の DB には参照の ID だけを置く。個人番号をログ・エラーの本文・トレースの属性・メトリクスのラベル・スナップショット・分析用の出力に書かない。保管庫への変更は `security:sensitive` とする（ADR-0005）。
- **個人情報をログに出さない。** 氏名、住所、生年月日、口座番号、給与の額、健康の情報、扶養の情報は、許可リストのスキーマを通したログにだけ、マスクして出す。
- **権限の判定を迂回しない。** 画面・API・レポート・一括の出力・連携のすべてで、同じ権限の判定（ドメインと業務プロセスの権限）を通す。レポートのために別の経路で DB を読まない（ADR-0005）。
- **職務分掌を崩さない。** 同じ人が、同じ業務プロセスで起票と承認をしない。職務分掌の規則表にある組み合わせ（例：振込先の口座の変更と振込ファイルの承認）を、1 人のロールに持たせない。
- **テナントテーブルには `tenant_id` と RLS を付ける。** 給与計算の worker も、テナントのコンテキストを設定してから読む（ADR-0005）。
- **セキュリティに関わる変更は、追加のレビューを受ける。** 権限の判定、職務分掌、保管庫、暗号、テナントの分離、給与の計算、振込ファイル、監査ログに触れる PR には `security:sensitive` のラベルを付ける。Dev のテックリードに加え、セキュリティの担当の承認を必須にする。エージェントは承認しない。

### テストのデータ

- **テストに実在の人のデータを使わない。** 実在の人の氏名・住所・生年月日・口座・給与・マイナンバーを、テスト・フィクスチャー・シード・ゴールデンデータセットに入れない。現行のシステムの本番のデータを、開発・テストの環境に持ち込まない。
- 個人番号は、合成の生成器（チェックデジットは正しく、実在の番号と区別できる印を持つもの）だけで作る。口座は、テスト用の銀行コードと支店コードを使う。
- 並行稼働の比較は、本番の環境の中だけで行い、結果の差異の報告にも個人を特定できる値を出さない。

### 本家の名前

- **本家の名前を識別子に使わない。** ドメイン、ヘッダー、API のパス、ファイルの形式の名前、トークンの接頭辞は `<Brand>`・`<brand>` で書く（[リポジトリ共通の ADR-0006](../../docs/decisions/0006-brand-neutral-identifiers.md)）。
- **本家の実装を使わない。** オブジェクトモデル、業務プロセスのエンジン、給与計算は自分で設計して作る（[リポジトリ共通の ADR-0007](../../docs/decisions/0007-no-reuse-of-original-implementation.md)）。

## このリポジトリでの規則

- ADR を追加・更新したら、`docs/decisions/README.md` の一覧を生成し直す。
- 領域の文書で ADR を起票するときは、[architecture/README.md](docs/architecture/README.md) の 7 節で領域に割り当てた番号の範囲の中で採番する。
- 本家の振る舞い・数値と、日本の法令・料率を書くときは、出典と確認日を付ける。確かめられないものは「未検証」と書く。法令の解釈は結論を出さず、[intent.md](docs/intent.md) の「法務・社労士・税理士の確認待ち」に載せる。
