# Runbook: デプロイとロールバック（ランタイムの段階的な配信）

- Owner: Ops
- 対応するアラート: ランタイムの配信の関門で停止・自動の戻し（配信の制御役）、V8 の Critical・High の修正の検知、AMI の入れ替えの停止、基盤の設定の検証の失敗
- 最終確認日: 2026-09-27

流れは [delivery.md](../architecture/delivery.md) の 5〜8 節、波と関門は [ADR-0055](../decisions/0055-staged-runtime-rollout-by-cordon-and-region.md)、基盤の設定は [ADR-0056](../decisions/0056-platform-config-staging-and-flags.md)、V8 の緊急の経路は [ADR-0012](../decisions/0012-v8-24-hour-patch-pipeline.md) と [sandbox-and-security.md](../architecture/sandbox-and-security.md) の 8 節にある。**利用者の関数の**デプロイとロールバックは利用者の操作で、この手順では扱わない（[deployment-and-config-distribution.md](../architecture/deployment-and-config-distribution.md)）。

## 症状

次のときに使う。

- 週 1 回のランタイムの取り込みを本番へ出すとき（水曜の W1 から）
- V8 の Critical・High の修正を 24 時間以内に配るとき
- 配信の制御役が、関門の外れで波を止めた、または自動で戻したとき
- ランタイムの配信の後に、プロセスの落ち・OOM・seccomp の違反・`exceededCpu` の増加が出たとき
- ノードの AMI（Rust の部品、OS、カーネル）の入れ替えが止まったとき
- 基盤の器（`egress_policy`・`platform_flags` など）の変更を配る・戻すとき

## 影響

- 通常の波：利用者への影響は小さい。プロセスの入れ替えで、そのプロセスの温かい isolate が冷たくなる（冷たい起動が増える。NFR-001 の予算を使う）。WebSocket と長い要求は 30 秒で切れる（休止できる DO の WebSocket は切れない。[ADR-0032](../decisions/0032-do-alarms-hibernation-and-rpc.md)）。
- 退行した版：プラットフォームが原因の失敗が増え、関数の実行の可用性（99.99%）の予算を使う。1 つの cordon の中にとどまる（波が cordon で切れているため）。
- 戻し：約 10 分で全ノードが前の版になる。その間、冷たい起動が増える。
- V8 の修正の遅れ：NFR-007（24 時間）の破れは、K6 の違反としてインシデントにする。

## 確認

### 波を始める前（W1、水曜の朝）

1. `runtime_releases` の対象の版が `staging` で 2 日動き、次を満たす：性能の退行の門（起動の p99 10%、CPU 時間の中央値 5%。ADR-0006）、WPT の門（ADR-0014）、ステージングの毎晩の脱出のテストの成功、seccomp の監査のモードの記録が空。
2. 成果物の署名と `artifact_sha256`・来歴・SBOM がある。
3. 本番の全リージョンで、エラーの予算が残っている（[observability.md](../architecture/observability.md) の 6.2 節）。予算を使い切ったリージョンは、そのリージョンの波を飛ばす。
4. 凍結の期間でない。V8 の緊急の経路が進行中でない。
5. `runtime_rollouts` に計画の行を作り、Dev のテックリードが承認する。

### 波の間

| 見るもの | 正常 |
| --- | --- |
| 配信の制御役の画面（波ごとの関門） | 全ての関門が「前の版の比」の中 |
| `runtime_version` ごとのプロセスの落ち・OOM・seccomp の違反 | 0 |
| 冷たい起動の率 | 5% 未満（入れ替えの直後の一時の増加を除く） |
| 合成監視・各 cordon の探りの関数 | 成功 100% |
| ノードの版の分布 | 範囲に入ったノードのプロセスが新しい版を報告している |

## 対処

### A. 関門で止まった（自動の停止）

1. 止まった関門を見る。**seccomp の違反で止まったなら、C に進む**（セキュリティの事象）。
2. 新しい版の cordon だけに出ているか（前の版の同じ cordon と比べる）を確かめる。前の版にも出ていれば、配信と関係のない障害として [incident-response.md](incident-response.md) へ。
3. 新しい版だけなら、戻す（B）。原因の調べは戻した後に行う。
4. 関門の誤り（閾値が厳しすぎる、比べる母数が少ない）と判断したら、Dev のテックリードの承認で、その波だけ再開する。判断を `runtime_rollouts.gate_results` に書く。

### B. ランタイムを戻す

1. 配信の制御役で、対象の `runtime_rollout` を `rollback` にする。範囲の cordon のプロセスが、ノードの前の版で起動し直る（25% ずつ 2 分おき）。
2. 全ノードの報告で、範囲のプロセスが前の版になったことを確かめる（約 10 分）。
3. 前の版に既知のセキュリティの欠陥（V8 の修正の前など）がある場合は、戻さない。代わりに、当番と Dev のテックリードが、V8 のフラグで該当の機能を止める・範囲を狭めるなどを選ぶ（ADR-0012 の「間に合わないとき」）。
4. 新しい版の最大の互換の日付を、デプロイで受け付けないように戻す（delivery の 5.3 節）。その日付で作った版があれば、その利用者への影響を調べる。
5. `upstream-rebase-blocked` の判断：次の週の取り込みで直すか、パッチを足すか、上流へ報告するかを Dev のテックリードが決める。

### C. seccomp の違反・脱出の探りの失敗で止まった

1. 波を止めたまま（戻すかは次の 2 の後）、セキュリティの当番を呼ぶ。
2. 上流の取り込みで許可リストの外のシステムコールが入ったか（正当な動作）を、ステージングの監査のモードで再現する（[sandbox-and-security.md](../architecture/sandbox-and-security.md) の 10 節）。
   - 正当な動作なら：戻し（B）、許可リストを直した版を次の波で出す。
   - 再現しない、または特定の関数の読み込みの直後なら：脱出の試みの疑い。[incident-response.md](incident-response.md) の「サンドボックスの脱出の疑い」へ。

### D. V8 の緊急の配信

時間の予算は ADR-0012（T+0 は最初に観測した時刻）。

| 時刻 | すること | 誰が |
| --- | --- | --- |
| T+0 | 検知のジョブが当番を呼ぶ。`v8_security_patches` に行ができる | 自動 |
| T+1h | いまの本番の V8 に影響するか、重さ、上流の workerd の修正のタグの有無を判断。進行中の通常の波を止める | セキュリティの当番 |
| T+4h | 修正の版：上流のタグが T+3h までにあればそれを土台に、なければいまの本番の土台に cherry-pick。ビルド（90 分以内）、署名 | Dev の当番 |
| T+8h | 速い試験（上流の単体テストの一部、WPT の核、脱出のテスト、再現コード（security-lab）） | 自動、確認は Dev の当番 |
| T+10h | カナリア（`scope.node_pct = 1`。リージョンごとに 1 台、全 cordon）、1 時間。**承認 1 回目**（セキュリティの当番と Dev のテックリード） | 承認は人。エージェントは承認しない |
| T+12h | 大阪（`scope.regions = [apne3]`） | 当番 |
| T+16h | 全リージョン。**承認 2 回目** | 同上 |
| T+24h | 全ノードの報告を確かめ、`fleet_complete_at` を書く | 当番 |

- 関門は 5.2 節と同じ値。外れたら、戻すのではなく原因を調べ、修正の版を作り直す（戻すと脆弱な版に戻るため）。
- **間に合わないとき**：V8 のフラグで該当の機能・最適化を止める、`c0-untrusted`・`c1-free` の新しい isolate の作成を止める、などを当番とテックリードが選び、SEV1 のインシデントにする（[incident-response.md](incident-response.md) の「V8 の 0-day」）。

### E. 毎週の空の実行と四半期の訓練

- 毎週：いまの本番の土台に何もしないパッチを当て、T+4h〜T+10h の手前（ビルド、試験、署名、カナリアへの配置の準備）を回す。失敗したら、その週のうちに直す（経路が腐っている）。
- 四半期：過去の実際の修正を 1 つ選び、全ノードへの配信まで 24 時間以内に終える。本番で行い、`v8_security_patches` に `drill` として記録する。経路を壊しうる変更（ビルド、配信、ノードの版の切り替え）は、この訓練を通してからマージする（[AGENTS.md](../../AGENTS.md)）。

### F. AMI の入れ替えが止まった

1. ASG のインスタンスの入れ替えの状態を見る。新しいノードが健全にならない理由（起動の自己検査：PMU・PKU・IMDSv2・署名、スナップショットの追いつき、KMS）を、ASG のライフサイクルのフックの記録で見る。
2. 自己検査の失敗なら、入れ替えを取り消し（前の AMI の起動テンプレートへ）、AMI を直す。
3. カーネルの重大な修正（72 時間）の入れ替えなら、失敗の原因の修正を最優先にし、Ops の責任者へ上げる。

### G. 基盤の設定を配る・戻す

1. 変更を `platform_config_changes` に作り、2 人が承認する。
2. 段 1（ステージング）から段 5（全リージョン）へ、30 分ずつ（delivery の 7 節）。関門は A と同じ。
3. 戻しは、前の値を同じ範囲に書く新しい変更（速い経路でなく、同じ段階を短い待ちで）。緊急のときは、Ops の責任者の承認で全範囲に一度に書いてよい。
4. ノードの検証の失敗（スキーマに合わない値）の警報が出たら、ノードは前の値で動いている。変更を取り消し、値を直す。

## エスカレーション

| 状況 | 連絡先 |
| --- | --- |
| 関門で止まり、原因が 1 時間で分からない | Dev のテックリード |
| seccomp の違反、脱出の探りの失敗 | セキュリティの当番（即時） |
| V8 の緊急の経路が T+12h で大阪に届いていない | Dev のテックリード、Ops の責任者 |
| 24 時間に間に合わない見込み | Ops の責任者、PM（利用者への告知の判断） |
| 戻しで前の版にも問題がある | Dev のテックリード、Ops の責任者（インシデントを宣言） |

## 事後

- 戻した配信・関門で止まった配信は、原因を `changes/` の新しい `intent.md` として起票する（Maintain 段）。
- 関門の閾値の誤り（誤った停止、見逃し）は、[ADR-0055](../decisions/0055-staged-runtime-rollout-by-cordon-and-region.md) の初期値の見直しとして記録する。
- V8 の修正ごとに、T+0 から全ノードの報告までの時間を記録し、24 時間を超えた件数を K6 に報告する。
- この手順で足りなかったことを、ここに反映する。
