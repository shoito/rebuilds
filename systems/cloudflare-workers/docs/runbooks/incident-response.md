# Runbook: インシデント対応

- Owner: Ops
- 対応するアラート: すべての呼び出し（page）のアラート（[observability.md](../architecture/observability.md) の 7 節）。個別の場面は「この基盤に固有の場面」の節
- 最終確認日: 2026-09-27

個別の手順（[deploy-and-rollback.md](deploy-and-rollback.md)、[disaster-recovery.md](disaster-recovery.md)）の上に立つ、共通の進め方と、この基盤に固有の場面（サンドボックスの脱出の疑い、V8 の 0-day、リージョンの退避、設定の伝搬の停止、耐久性の違反）。進め方の骨格は他の題材（[kafka の incident-response.md](../../../kafka/docs/runbooks/incident-response.md)）と同じ。

## 症状

次のどれかのときに、インシデントを宣言する。迷ったら宣言し、後で重さを下げる。

- 呼び出しのアラートが鳴った
- 利用者・社内・報奨金の制度の研究者から、他のテナントのデータが見える、関数が動かない、デプロイが届かない、という報告が来た
- 脱出の探り・DO のカナリア・監査の突き合わせで不一致が出た
- V8 の Critical・High の修正が公開された（それ自体をインシデントとして扱う）

## 影響

### 重さ（severity）

| 重さ | 基準 | 例 | 最初の応答 | 告知 |
| --- | --- | --- | --- | --- |
| SEV1 | テナントの隔離の破れ（疑いを含む）。成功を返した書き込みの喪失（疑いを含む）。1 つのリージョン以上で関数が動かない。V8 の修正が 24 時間に間に合わない見込み | 脱出の探りの失敗、他のテナントのデータの報告、DO の二重の持ち主、東京の全体の障害、`msg_id` の喪失 | 5 分以内 | 30 分以内に状況の頁。以後 30 分ごと |
| SEV2 | 一部の利用者・一部の cordon で関数が失敗・遅延。SLO の速いバーンレート。デプロイの伝搬の停止。監査の鎖の食い違い | 1 つの cordon のプロセスの落ちの繰り返し、設定の伝搬の停止、1 つの AZ の喪失、KV の古さの SLO の破れ | 15 分以内 | 1 時間以内に影響する利用者へ |
| SEV3 | 劣化しているが、データと隔離は正しい。回避できる | 管理 API の遅れ、ログの取り込みの遅れ、証明書の更新の失敗（期限まで余裕） | 営業時間内 | 必要なら |
| SEV4 | 利用者への影響がない | 1 台の中継の障害 | 営業時間内 | なし |

**隔離と耐久性に関わるものは、範囲が 1 件でも SEV1 にする**（intent の守るべき振る舞い、NFR-006・NFR-010）。

## 確認

1. どのアラート・報告から始まったかを記録する。
2. 影響の範囲を見る：全体か、1 つのリージョンか、1 つの AZ か、1 つの cordon か、1 台のノードか、1 つの関数・アカウントか。
3. 直近の変更を見る：ランタイムの配信（`runtime_rollouts`）、AMI の入れ替え（`ami_rollouts`）、基盤の器の変更（`platform_config_changes`）、制御プレーンの配信、Terraform の apply、`region_flags`。
4. データと隔離への影響を見る：脱出の探り、`sandbox_violations`、`quarantine_events`、DO のカナリア、KV の版の戻り、キューの `msg_id` の検査、監査の突き合わせ。

## 対処

### 役割

| 役割 | 担う人 | 責任 |
| --- | --- | --- |
| 指揮者（IC） | 最初に応答した当番。SEV1 では Ops の責任者に引き継いでよい | 重さ、方針、大きな判断（配信の凍結、`drain`、cordon の新しい isolate の停止、DR の切り替え） |
| 作業者 | 当番の Ops、呼ばれた Dev | 調べと復旧 |
| セキュリティの担当 | セキュリティの当番 | 隔離の破れ・脱出・V8・鍵の評価、証拠の保全、`quarantine` の操作 |
| 耐久性の担当 | Dev のテックリード | データの喪失の評価、利用者への説明の中身 |
| 連絡係 | IC が指名する（PM が望ましい） | 利用者、社内、AWS、法務への連絡 |
| 記録係 | IC が指名する | 時刻付きの記録 |

SEV1 では、IC は手を動かさない。エージェントは調べの補助（人が渡したログ・指標の解析、手順の案内）だけを行い、本番の操作と承認はしない（[ADR-0046](../decisions/0046-control-plane-privilege-separation-and-operator-access.md)）。

### 進め方

1. **宣言する。** インシデント用の場を、この基盤と別の道具に作る（この基盤の障害で連絡の道具が止まらないように）。
2. **被害を止めることを、原因の特定より優先する。** 順番：
   - 変更を止める：ランタイムの配信の波（`rollout.pause`）、AMI の入れ替え、基盤の器の変更の段
   - 直近の変更を戻す：ランタイム（[deploy-and-rollback.md](deploy-and-rollback.md) の B）、基盤の器（同 G）、制御プレーン（blue/green の戻し）
   - 範囲を狭める：リージョンの `drain`、ノードの退避、cordon の新しい isolate の作成の停止、関数・アカウントの停止（優先の印）
3. **証拠を消さない。** 侵害の疑いのノードは、捨てる前に `quarantine` へ写す。ログ・監査・`sandbox_violations` の記録を保全する。
4. **法務への連絡**：隔離の破れ・個人情報の漏えいの疑い・データの喪失は、SEV1 の最初の 1 時間に法務へ知らせる（報告の義務の判断。[security.md](../architecture/security.md) の 9 節の S-L2・S-L3）。
5. **収束**：SLI が戻り、1 時間安定したら収束を宣言する。止めた配信の再開は、原因が分かってから。

## この基盤に固有の場面

### サンドボックスの脱出の疑い

**症状**：脱出の探りの失敗（届いてはいけない先に届いた）、seccomp の違反（上流の取り込みの直後でない）、同じ関数の読み込みの直後のプロセスの落ちが 3 回続く、外向きのプロキシの拒否の急増（IMDS・内部のアドレスへ）、研究者・利用者からの報告。

1. **SEV1 を宣言し、セキュリティの当番を呼ぶ。**
2. **関数とアカウントを特定する**：`sandbox_violations` の `scripts_in_process`、探りの失敗のノードとプロセス、プロセスの落ちの直前に読み込んだ関数。
3. **被害を止める**（セキュリティの担当と IC で決める）：
   - 疑いの関数・アカウントを停止する（優先の印。全ノードへ p99 10 秒）。
   - 範囲が 1 つの cordon なら、そのリージョンのその cordon の新しい isolate の作成を止める（`cordon_policy` の緊急の変更。[delivery.md](../architecture/delivery.md) の 7 節のセキュリティの修正の扱い）。
   - 同じプロセスにいたテナント（`scripts_in_process`）を記録する。これらは、同じプロセスのメモリに届きえた（cordon の中の被害の範囲。[sandbox-and-security.md](../architecture/sandbox-and-security.md) の 3.3 節の②）。
4. **ノードを隔離する**：該当のノードを `drain`（ノードの退避）にし、NLB から外す。EBS のスナップショットとメモリの写し（取れれば）を `quarantine` のアカウントへ写す。**写し終えるまでノードを終了しない。** 写した後に終了し、ASG が新しいノードを起こす。
5. **ホストへの到達の疑い**（L2 を越えた兆候：プロセスの外のファイル、別の UID のプロセス、IMDS への到達）があれば：
   - そのリージョンのノードの役割の資格情報を失効させる（インスタンスのプロファイルの付け替え、`edge-<r>` の STS のセッションの失効）。
   - そのリージョンの RSK・RDK の入れ替えを前倒しで行う（`kms-key-compromise`）。そのリージョンで動いた関数のシークレットの利用者に、入れ替えを勧める連絡を準備する（法務と PM の判断）。
   - 同じ AMI の全ノードを疑い、AMI とカーネルを調べる。
6. **調べ**：`quarantine` で、バンドル（内容のハッシュで固定。再現できる）を security-lab で再現する。V8 の欠陥なら「V8 の 0-day」へ。カーネルの欠陥なら、カーネルの修正を 72 時間の経路で。
7. **連絡**：影響を受けうるテナント（同じプロセス・同じノード）への連絡の範囲と時期を、法務・PM と決める。報告者が研究者なら、報奨金の制度の手順（`vulnerability-report-triage`）で連絡する。

### V8 の 0-day（公開済みの修正、または修正のない既知の攻撃）

**症状**：V8 の修正の検知のジョブ、Chrome の緊急の更新、野生での悪用の報告。

1. **修正が公開されている**：[deploy-and-rollback.md](deploy-and-rollback.md) の D（24 時間の経路）。T+0 を記録する。進行中の通常の波を止める。
2. **修正がまだない、または 24 時間に間に合わない**（SEV1）：
   - 影響する機能を V8 のフラグで止められるか（該当の JIT の段、Wasm の機能など）を Dev のテックリードとセキュリティの担当が判断し、`platform_flags` の緊急の変更で配る（全範囲、2 人の承認）。互換の日付の約束を破る場合は、[ADR-0008](../decisions/0008-bundle-format-and-compatibility-dates.md) の例外として記録し、事前に知らせられない理由を残す。
   - `c0-untrusted`・`c1-free` の新しい isolate の作成を止める（新しいアカウントからの攻撃を止める。既存の温かい isolate は動く）。止める範囲と時間を PM と決める（無料の利用者の関数の冷たい起動が失敗する）。
   - 性能カウンターの検知の閾値を一時的に厳しくする（`pmu_thresholds`）。
   - 悪用の兆候（外向きの拒否、seccomp の違反、プロセスの落ち）を 1 時間ごとに見る。
3. 修正が出たら D の経路で配り、止めた機能とフラグを戻す。

### リージョンの退避（`drain`）

**症状**：リージョンの灰色の障害（一部の関数だけ失敗、遅い）、リージョンのサービス（KV・DO・中継）の障害で関数が広く失敗、AWS の告知。

1. **判断**：合成監視と実際の要求の SLI で、そのリージョンだけが悪いことを確かめる。GA の健全性の検査で自動で迂回していないか（ノードの局所の故障でないため、健全性は落ちない）。
2. **同時に退かせているリージョンの数を確かめる。2 つまで**（3 つ目は中継が拒む。GA の fail open を避ける。[ADR-0017](../decisions/0017-global-accelerator-and-regional-nlb.md)）。
3. **東京と大阪を同時に退かせない**。どうしても要るときは Dev と Ops の 2 人の承認と、PM・法務への連絡（国内の要求が海外で処理される。L3）。
4. **退かせる**：`region_flags/<r>.drain = true` を配る（優先の印）。制御プレーンが止まっていれば、そのリージョンの中継に直接書く手順（`region-drain`）を使う。
5. **確かめる**：そのリージョンの全ノードの `/healthz` が 503、NLB の全ターゲットが不健全、GA が新しい接続を近いリージョンへ（約 30 秒の見込み。GA の反映の時間は未検証で、T5（E4 の `load-test-t5-t6-t9`）の実測で置き換える）。受ける側のリージョンの CPU が 70% 以下、ホームの断りの率が 20% 以下。
6. **ストレージ**：そのリージョンのホームの DO は使えないまま（自動で移さない）。長く続くなら `do-region-evacuate` の判断（[disaster-recovery.md](disaster-recovery.md) の 5 と同じ条件）。
7. **戻す**：原因が直ったら `drain = false`。GA のダイヤルで段階的に戻すかは、そのリージョンの台数と冷たい起動の見込みで決める。

### 設定の伝搬の停止

**症状**：設定の伝搬の SLO（p99 10 秒）の逸脱、全体の古さ（中継の先頭が 5 分進まない）、取りこぼし（60 秒で埋まらない抜け）、局所の遅れのノードの増加、利用者の「デプロイが反映されない」。

1. **どこで止まっているかを分ける**（[deployment-and-config-distribution.md](../architecture/deployment-and-config-distribution.md) の 9・10 節）：
   - outbox に採番していない行が溜まっている → 採番器（リースの持ち主、Aurora の遅延、1 万項目を超える変更の保留）
   - `config_log` は進むが中継の先頭が進まない → 配信の元、リージョンの間の経路（TGW）
   - 1 つのリージョンの中継だけ遅れる → そのリージョンの中継
   - 中継は進むがノードが遅れる → 局所の遅れ（ノードの受け手、LMDB）
2. **関数は動き続けていることを確かめる**（静的な安定）。`/healthz` が全体の古さで 503 になっていないか（なっていれば、それ自体が設計の破れ。SEV1 に上げる）。
3. **対処**：
   - 採番器：リースの持ち主のタスクを確かめ、止まっていれば別のタスクがリースを取る（10 秒）。取れなければ `config-origin-down` の手動のリーダーの交代。
   - 1 万項目を超える変更の保留：`bulk-change-approval` で中身を確かめ、承認か取り消し。
   - 配信の元・経路：中継は他のリージョンの中継から受けられる。TGW の障害なら AWS へ。
   - 局所の遅れのノード：60 秒で自動で NLB から外れる。戻らなければ `node-lmdb-rebuild`（スナップショットから作り直す）。
   - `db_id` の不一致・CRC の失敗が続く：取り違え・破損の疑い。SEV1 に上げ、そのリージョンの中継を作り直す（`relay-rebuild`）。
4. **緊急の停止（不正な利用）が届かない**：アカウントの停止は優先の印で配るが、経路が止まれば届かない。そのリージョンで直接止める手段（中継への直接の書き込み）を使う。
5. **利用者への連絡**：デプロイが届かない間は、利用者の新しいデプロイが古い版のまま動く。ノードは受けていない版を名乗らない（呼び出しの記録の `config_lag_ms`）。状況の頁で「デプロイの反映が遅れている」と知らせる。
6. **基盤の器の誤りが原因**（誤った値を配った）：[deploy-and-rollback.md](deploy-and-rollback.md) の G で戻す。

### 耐久性の違反（DO の二重の持ち主、KV の版の戻り、キューの喪失）

1. SEV1。耐久性の担当（Dev のテックリード）を呼ぶ。
2. 該当の実体・名前空間・キューへの変更を止める（DO は `unavailable` にする、キューはディスパッチャーのシャードを止める）。
3. **データを消さない。** DO の WAL・スナップショット、ログのノードのログ、SQS のメッセージ、DynamoDB の PITR を保全する。
4. 一意性の違反は、リースとフェンシング（[ADR-0030](../decisions/0030-do-leases-and-fencing.md)）の欠陥として、Jepsen の形の試験で再現する。直るまで、そのリージョンの配置のサービスの変更を凍結する。
5. 失われた・食い違ったデータの範囲を記録し、PM・法務と利用者への説明を決める。

### テナントをまたぐデータの報告（ログ・KV・オブジェクト）

1. SEV1。報告の証拠（`<Brand>-Ray`、時刻、アカウント）を受け取る。
2. 経路を特定する：ゲートウェイの `account_id` の二重の検査の記録、ClickHouse の問い合わせの条件、キャッシュのキー。
3. 該当の経路（例：KV の L2、ログの問い合わせ）を止めるか、正本だけで返すようにする。
4. 影響を受けたアカウントの範囲を記録し、法務へ。

## エスカレーション

| 状況 | 連絡先 |
| --- | --- |
| SEV1 | Ops の責任者、Dev のテックリード、セキュリティの当番、PM（連絡係） |
| 隔離の破れ・個人情報の漏えいの疑い | 法務（最初の 1 時間）、セキュリティの責任者 |
| AWS の障害が原因 | AWS のサポート（エンタープライズ）。東京の全体なら [disaster-recovery.md](disaster-recovery.md) |
| 上流（workerd・V8）の欠陥 | 上流のセキュリティの窓口（非公開の報告）。公開の Issue にしない |
| 30 分で収束の見込みが立たない SEV2 | SEV1 に上げるかを IC が判断 |

## 事後

- 5 営業日以内に振り返りを行う（責めない形）。時刻の記録、検知までの時間、被害を止めるまでの時間、原因、直すこと。
- 原因と改善を `changes/` の新しい `intent.md` として起票する（Maintain 段）。隔離・耐久性の事象は、脅威モデル（[sandbox-and-security.md](../architecture/sandbox-and-security.md) の 3 節、[security.md](../architecture/security.md) の 3 節）の見直しに入れる。
- 見つかった欠陥は、回帰テスト（脱出のテスト、ファズの種、Jepsen の形の試験）にしてから直す（[AGENTS.md](../../AGENTS.md)）。
- この手順で足りなかったことを、ここに反映する。
