# Runbook: 災害復旧（東京の全体の障害と、大阪への切り替え）

- Owner: Ops
- 対応するアラート: 東京の全体の障害（東京の合成監視・制御プレーン・ストレージの同時の失敗が 5 分）、複製の遅れ（`AuroraGlobalDBRPOLag`、S3 の `ReplicationLatency`・`OperationsFailedReplication`、DynamoDB の `ReplicationLatency`）、DR の訓練（半期）
- 最終確認日: 2026-09-27

方針は [ADR-0051](../decisions/0051-disaster-recovery-and-honest-rpo.md)、構成と RPO の表は [infrastructure.md](../architecture/infrastructure.md) の 7 節にある。製品ごとの細かい切り替えは、各領域が挙げた個別の手順（`kv-region-failover`、`object-region-failover`、`do-region-evacuate`、`cron-region-failover`、`control-plane-dr-epoch`。各 Epic で作る。[README.md](README.md) の 5.2 節）で、この手順はその順と判断をまとめる。作るまでは、この手順の 2〜6 で対応する。

## 症状

- 東京のリージョンの複数のサービス（EC2、Aurora、DynamoDB、S3）が同時に失敗し、AWS の Health Dashboard に東京の障害が出ている。
- 東京のエッジのノードの合成監視が全て失敗し、GA が新しい接続を大阪・他へ迂回させている。
- 管理 API・デプロイが失敗し、KV の書き込み・オブジェクトの読み書き・東京の DO・キュー・cron が失敗している。
- 複製の遅れのアラートだけが出ている（障害の前触れ、または複製の不調）→ 「確認」の 4 だけを行う。

## 影響

| 対象 | 切り替えの前 | 切り替えの後 |
| --- | --- | --- |
| 関数の実行 | GA の迂回で大阪・他が受ける（自動、約 30 秒）。大阪は国内の全量を受ける台数を持つ（[ADR-0054](../decisions/0054-capacity-design-point-and-region-sizing.md)） | 同じ |
| デプロイ済みの関数の設定 | 各ノードの写しで動く（全体の古さの警報） | 新しいエポックの後に更新が再開 |
| 新しいデプロイ・設定の変更・停止 | 止まる | 大阪の制御プレーンで再開 |
| KV | 読み込みは各リージョンのキャッシュ（古くても返す段）。書き込みは失敗 | 大阪の正本で読み書き。RPO は複製の遅れ（通常は秒） |
| オブジェクトストレージ | 止まる | 大阪の写しで再開。RPO は CRR の遅れ（通常は秒、上限の約束は 15 分） |
| Durable Objects（東京の実体） | 使えない | 大阪へ退避した後、要求の来た実体から復元。RPO は最大 10 秒＋CRR の遅れ |
| キュー | 送信・配送が止まる | **切り替えない**。東京の回復の後に配る |
| cron | 止まる | 大阪の待機で再開。2 重の起動がありうる |
| 保存するログ・tail | 止まる | tail は大阪のハブで再開。保存は東京の回復まで大阪の S3 に貯める |
| 使用量 | ノードの spool に貯まる | 大阪の集計で再開（束は冪等） |

- NFR-010 は、統合の工程（2026-09-27）で「RPO 1 分」から ADR-0051 の製品ごとの値に改めた（[architecture/README.md](../architecture/README.md) の 3 節。PM・Ops の確認事項）。KV の大きな値・オブジェクト・Durable Objects は、99.9% で 15 分以内の書き込みを失いうる。

## 確認

1. **範囲を確かめる**：AWS の Health Dashboard、東京の各サービスの合成監視、`probe` の東京の外からの監視。1 つの AZ だけの障害なら、この手順を使わない（Multi-AZ で吸収する。[incident-response.md](incident-response.md) へ）。
2. **関数の実行が迂回しているか**：GA のエンドポイントの健全性、大阪の要求の数と CPU（70% 以下か）、ホームの断りの率。迂回していなければ、東京を `drain` にする（[incident-response.md](incident-response.md) の「リージョンの退避」）。**東京と大阪を同時に `drain` にしない**（2 人の承認が要る。L3）。
3. **切り替えの判断の条件**：東京の障害が 30 分続き、AWS の告知で回復の見込みが 1 時間を超える。判断は Ops の責任者と Dev のテックリードの 2 人。記録係が時刻を残す。
4. **失うものを先に見積もる**（切り替えの前に、最後の値を記録する）：
   - `AuroraGlobalDBRPOLag`（大阪の副から見る）
   - DynamoDB の `ReplicationLatency`（`kv_entries`、`cron_fires`、`do_directory`）
   - S3 の `ReplicationLatency`・`OperationsPendingReplication`（KV の値、オブジェクト、DO の WAL）
   - 中継が持つ最大の `seq`（全リージョン）

## 対処

順番は、依存の少ないものから。各段の終わりに、記録係が時刻と結果を残す。

### 1. 関数の実行を守る（自動のはず）

1. GA の迂回を確かめる。大阪の CPU が 70% を超えるなら、大阪の ASG の最大を上げる（warm pool から）。
2. 海外のリージョンへの国内の要求の迂回が起きていないかを見る（東京と大阪が同時に落ちたときだけ起こる。L3 の論点。起きたら PM と法務へ知らせる）。

### 2. 制御プレーンを大阪へ（`control-plane-dr-epoch`）

1. Aurora Global Database の管理された切り替え（`failover-global-cluster --allow-data-loss`）で、大阪の副を主にする（数分）。書き込みの囲い込み（write fencing）の事象を確かめる。
2. 大阪の ECS のサービスを増やす（API、採番器、配信の元、cert-manager、tail ハブ、使用量の集計、配信の制御役）。東京のタスクが生きていても、採番器のリースが東京で取れないことを確かめる（2 つの採番器を動かさない）。
3. 採番器を**新しいエポック**で始める（[ADR-0022](../decisions/0022-sequenced-change-log-relays-and-lmdb.md)、[deployment-and-config-distribution.md](../architecture/deployment-and-config-distribution.md) の 5.3 節）：
   1. 全リージョンの中継に、持っている最大の `seq` と、失われた範囲の項目を尋ねる。
   2. 新しいエポックの最初の `seq` を、その最大 ＋ 1 にする。
   3. 失われた範囲のキーを、大阪の正本のいまの値で書き直す補正を最初に流す。
   4. 失われた変更の持ち主の一覧を、監査ログから作る。
4. 中継が大阪の配信の元へつながり、全ノードの `applied_seq` が進むことを確かめる（全体の古さの警報が消える）。
5. 管理 API の合成監視が通ることを確かめる。`cp-adk-wrap` の大阪の複製で、シークレットの受付ができることを確かめる（[ADR-0047](../decisions/0047-kms-key-hierarchy.md)）。

### 3. KV を大阪へ（`kv-region-failover`）

1. 大阪の KV の書き込みサービスを起動し、全リージョンのゲートウェイの書き込みの宛先を大阪にする（基盤の器の変更。緊急として Ops の責任者の承認で全範囲へ）。
2. `kv_entries` の大阪の複製を正本として使う。4 KiB を超える値で、項目はあるが S3 の本体（大阪の CRR の写し）がないものを、読み込みで `NoSuchKey` として検知したら、**失われた値**として記録する（ADR-0051 の Consequences）。
3. 1 秒に 1 回の書き込みの制限の時計が、大阪の書き込みサービスの時計に移ることを確かめる。

### 4. オブジェクトストレージを大阪へ（`object-region-failover`）

1. 大阪のゲートウェイを起動し、`*.storage.<brand>.<domain>` を向けた S3 の API の口の GA のエンドポイントを大阪にする（予備として持つ。[object-storage.md](../architecture/object-storage.md) の 4 節）。
2. 関数のバインディングの宛先を大阪のゲートウェイにする。
3. `OperationsPendingReplication` の最後の値から、失いうるオブジェクトの数を記録する。

### 5. Durable Objects を大阪へ（`do-region-evacuate`）

1. **東京の DO のホストが止まっていることを確かめる。** 確かめられないときは、東京の DO のホストの IAM の権限（S3・DynamoDB）を外し、リースの更新をできなくする。**それも確かめられないときは、退避しない**（二重の実体を作らない。[durable-objects.md](../architecture/durable-objects.md) の 10.2 節）。
2. 名前の台帳の `region` と `region_epoch` を更新する（2 人の承認）。一意の ID の「リージョンの読み替えの表」に東京 → 大阪を載せる（設定の配信で届く）。
3. 大阪で、DR の写し（WAL とスナップショット）から、要求の来た実体から復元する。
4. 管轄 `jp` の実体は、大阪（日本の中）だけに退避する。

### 6. cron を大阪へ（`cron-region-failover`）

1. 大阪の待機のスケジューラーを起動する。`cron_fires` の大阪の複製を使う。
2. 複製に届いていなかった起動の記録の分だけ、2 重の起動がありうる。切り替えの時刻の前後 5 分の起動を記録する。

### 7. キュー・ログ

- キューは切り替えない。利用者に「東京の回復の後に配る」と知らせる。送信は失敗し続ける（利用者の再試行）。
- 保存するログは、大阪の S3 に貯め、東京の回復の後に ClickHouse へ入れ直す。

### 8. 利用者への連絡

- 連絡係が、30 分以内に状況の頁で知らせ、以後 30 分ごとに更新する。
- 製品ごとの影響（ADR-0051 の表）と、失いうる範囲（4 の見積もり）を書く。
- 失われた設定の変更（エポックの補正）の持ち主には、監査ログから作った一覧でメールで知らせる。

### 9. 戻す（東京の回復の後）

1. Aurora：東京が副として自動で戻るのを待ち、計画の切り替え（switchover。RPO 0）で東京を主にする。採番器は、さらに新しいエポックで始める（番号は巻き戻さない）。
2. KV・オブジェクト：大阪で書いた分を東京へ戻す（グローバルテーブルは両方向。S3 は大阪 → 東京の CRR を一時的に作り、終わってから宛先を東京に戻す）。
3. DO：大阪へ退避した実体は、S1 では大阪に残す（場所を変えない原則）。東京へ戻すかは、durable-objects の領域の判断。
4. cron・キュー：東京のスケジューラーとディスパッチャーを戻す。キューのバックログの配送を見守る。
5. 東京のエッジの `drain` を外し、GA のダイヤルで 10 → 50 → 100 と戻す。

## エスカレーション

| 状況 | 連絡先 |
| --- | --- |
| 切り替えの判断（30 分の条件を満たした） | Ops の責任者と Dev のテックリード（2 人の判断） |
| 東京の DO のホストの停止を確かめられない | Dev のテックリード（退避しない判断の記録） |
| 失われた書き込みがある（KV の値、オブジェクト、DO、設定の変更） | PM（利用者への説明）、法務（個人情報を含むなら。security の 9 節の S-L2） |
| 国内の要求が海外で処理された | PM、法務（L3） |
| AWS への問い合わせ | Ops の責任者（エンタープライズのサポート） |

## 事後

- 実際の RPO と RTO を製品ごとに `dr_drills`（本番の障害は `kind = incident`）に記録し、ADR-0051 の表と比べる。
- 失われたデータの一覧と、利用者への連絡の記録を残す。
- 原因と改善を `changes/` の新しい `intent.md` として起票する（Maintain 段）。
- この手順で足りなかったことを、ここに反映する。

## 訓練（半期）

staging の東京・大阪で、東京の全体の障害を模す（東京の VPC の経路を切る、Aurora の管理された切り替え、各製品の切り替え）。合成のテナントのデータで、製品ごとの RPO（最後に確定した書き込みと、大阪で読めた最後の書き込みの差）と RTO を測る。結果を `dr_drills` に残し、手順の各段の時間をこの文書に書き戻す。
