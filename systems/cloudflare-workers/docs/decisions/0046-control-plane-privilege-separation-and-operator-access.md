# ADR-0046: 全ノードへ届く 3 つの権限（ランタイムの配布、設定のログ、鍵の復号）を別の役割とアカウントに分け、人の本番の権限は期限付き・2 人の承認にする

詳細は [security.md](../architecture/security.md) の 3 節と 5 節。

## Context

利用者のコードに対する脅威モデルは [sandbox-and-security.md](../architecture/sandbox-and-security.md) の 3 節にある。制御プレーンには、それとは別の脅威がある。

この基盤では、制御プレーンの一部の権限が、全リージョンの全ノードへ一度に届く。

- **ランタイムの配布**：署名したランタイムの版を配ると、全ノードのすべてのテナントのプロセスが入れ替わる（[ADR-0012](0012-v8-24-hour-patch-pipeline.md) の署名）。
- **設定のログの書き込み**：`config_outbox` に書ける役割は、全ノードのルート・証明書・アカウントの停止・`egress_policy` を変えられる（[ADR-0022](0022-sequenced-change-log-relays-and-lmdb.md)）。
- **鍵の復号**：ADK を包む KMS の鍵を使える役割は、全アカウントのシークレットを開ける（[ADR-0023](0023-code-and-secret-distribution.md)）。

本家は、設定の配信（Quicksilver）の誤った変更で、全網を数秒で止めた。2025-11-18 の障害は約 2 時間 10 分、2025-12-05 の障害は約 25 分で、どちらも設定の変更が数秒で世界へ広がったことが原因だった（[Code Orange: Fail Small](https://blog.cloudflare.com/fail-small-resilience-plan/)、2025-12-19、2026-09-27 に確認）。悪意のある内部者や、奪われた運用者の資格情報でも、同じ経路が使われうる。

## Options

1. **3 つの権限を、別の役割・別の AWS アカウント・別の承認に分ける。人は常設の本番の権限を持たず、期限付きの権限を 2 人の承認で得る。エージェントには本番の経路を与えない**
2. 制御プレーンのアカウントに 3 つをまとめ、IAM の役割だけで分ける
3. 人の運用者に常設の管理者の役割を与え、操作を監査ログで事後に見る

## Decision

1 を採用する。

| 権限 | 持つ役割 | 置き場所 | 承認 |
| --- | --- | --- | --- |
| ランタイムとノードの AMI の署名 | `release-signer`（KMS の非対称の鍵で署名だけ） | `build-release` のアカウント | 本番の段へ進むたびに Dev のテックリードの承認。V8 の緊急の経路は ADR-0012 の 2 回 |
| 設定のログの書き込み | 制御プレーンの API のサービスの役割と、採番器 | `cp-prod` | 利用者の変更は API の認可。基盤の設定（`egress_policy`・`region_flags`・ランタイムのフラグ）は [ADR-0056](0056-platform-config-staging-and-flags.md) の段階と 2 人の承認 |
| ADK を包む鍵の復号 | 制御プレーンのシークレットのサービスの役割（暗号化の文脈に `account_id` を必須） | `cp-prod` の KMS | 人は break-glass だけ |

- 人の本番の権限：IAM Identity Center の期限付きの権限（最長 4 時間）。本番の書き込みの権限は、別の人の承認で出す。常設の人の管理者を置かない。
- break-glass：`management` の外の封をした資格情報と、`log-archive` への記録。使ったら 24 時間以内に振り返る。
- エージェント：本番の AWS・ノード・Aurora への経路を与えない。CI の役割（OIDC）で、承認済みの計画だけを適用する。
- ノードへの対話的なログインは止める。調査は SSM Session Manager の記録つきの break-glass だけにし、疑わしいノードは `quarantine` のアカウントへ証拠を写してから捨てる（[ADR-0049](0049-aws-accounts-and-network.md)）。
- 2 を採らない理由：1 つのアカウントの管理者の資格情報で、3 つの権限すべてに届く。IAM の誤設定 1 つで境界が消える。
- 3 を採らない理由：事後の監査では、全ノードへ一度に届く変更を止められない。

## Consequences

- 良くなること：
  - 1 つの役割・1 つの資格情報が奪われても、全ノードの任意のコードの実行と、全シークレットの復号の両方には届かない。
  - 運用者の操作は、承認と期限で範囲が限られ、記録が残る。
- 引き受けるコスト：
  - 障害の対応で、権限を得るまでの待ちが増える（承認者の呼び出し）。当番に 2 人を置く。
  - アカウントと役割の数が増え、Terraform とアクセスの設計の手間が増える。

## Confirmation

- IAM Access Analyzer と CI の検査：`release-signer` の鍵の `kms:Sign` を持つ主体が 1 つだけ。ADK の鍵の `kms:Decrypt` を持つ主体に人の役割がない。
- 四半期ごとに、break-glass の手順を訓練し、記録が `log-archive` に残ることを確かめる。
- 権限の申請の記録と、実際の操作（CloudTrail）の突き合わせを週次で行う。
