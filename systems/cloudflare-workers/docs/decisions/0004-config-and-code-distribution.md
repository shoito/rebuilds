# ADR-0004: 設定とコードは、順序付きの変更のログを全ノードの読み込み用の写しへ押し出して配る

## Context

エッジのノードは、1 つの要求ごとに多くの設定を読む。

- ホスト名とパスから、どの関数のどの版を動かすか（ルート、段階的なデプロイの割合）
- TLS の証明書、関数のバインディング、シークレット、制限、アカウントの状態（停止中かどうか）

これをリクエストの処理のたびに制御プレーンへ問い合わせると、遅延（NFR-002）と可用性（NFR-004）の両方を満たせない。一方で、デプロイや設定の変更は、全ノードへ速く届く必要がある（NFR-008）。

本家は、設定の配信に Quicksilver を使っている（[Introducing Quicksilver](https://blog.cloudflare.com/introducing-quicksilver-configuration-distribution-at-internet-scale/)、2020-03-30、2026-09-27 に確認）。

- 以前の Kyoto Tycoon は、書き込みの排他のロックで読み込みの遅延が悪化したので置き換えた。
- 各ノードの保存は LMDB。複数のプロセスが同じ保存を同時に読め、読み込みの遅延を優先した設計。
- 変更は単調に増える番号の付いたログで、500ms ごとにまとめて送る。番号で取りこぼしを検知する。
- ノードは中継のノードに、中継のノードは最上位のノードに、最新の変更を問い合わせる木の形で広がる。
- 200 都市に「数秒で」届き、1 日に 2.5 兆の読み込みと 3,000 万の書き込みを扱う（当時の値）。

## Options

1. **Quicksilver に近い仕組みを自前で作る。** 正本（Aurora）の変更を、番号の付いた変更のログにし、リージョンの中継を経て全ノードの LMDB へ押し出す。コードの本体は、内容のハッシュで S3 に置き、ノードがキャッシュする
2. **DynamoDB のグローバルテーブルを、ノードから直接読む**（ノードに短い TTL のキャッシュを持つ）
3. **S3 の設定ファイルを、ノードが定期的に取りに行く**
4. **etcd・Consul などの分散の設定の保存を、リージョンをまたいで組む**

## Decision

1 を採用する。

- **正本は制御プレーンの Aurora。** デプロイ・ルート・証明書・シークレット・制限の変更は、同じトランザクションで outbox に変更の記録を書く。
- **変更のログは、全体で単調に増える番号を持つ。** 配信の器（キーの空間）は、ルート・関数の版・証明書・シークレット・アカウントの状態に分ける。番号は全体で 1 本にし、ノードは「どの番号まで適用したか」だけを持つ。
- **配信は木の形。** 制御プレーン（東京）の配信の元 → 各リージョンの中継（2 台以上）→ ノード。ノードは中継からログを長いポーリングか、ストリームで受け、番号の抜けを検知したら取り直す。中継が落ちたら、別の中継か、配信の元から直接取る。
- **ノードの保存は LMDB。** 入口のプロキシ、スーパーバイザー、ランタイムが、同じ保存を読み込みだけで共有する。書き込むのは、ノードの受け手の 1 プロセスだけ。
- **コードの本体は、内容のハッシュ（SHA-256）で S3 に置く。** 設定には、関数の版からハッシュへの対応だけを入れる。ノードは、要求が来たとき、またはデプロイの時点の先読みで、リージョンの S3（または中継のキャッシュ）から取り、ハッシュを確かめてからノードのディスクに置く。S3 は、各リージョンへ複製する。
- **シークレットは、アカウントごとの鍵で暗号化したまま配る。** 復号の鍵は、ノードの受け手が KMS で取り出し、メモリにだけ置く。詳細は security の領域で決める。
- **伝搬の SLO**：デプロイ（版の切り替え）は p99 30 秒以内、ルート・シークレット・設定は p99 10 秒以内に全ノードへ届く（NFR-008）。ノードは、適用済みの番号を定期的に報告する。報告の番号と、各変更の番号・受付の時刻から、伝搬の遅れを計測する。
- **版と段階的なデプロイ**：関数の各デプロイは、変えられない版（コードのハッシュ、設定、互換の日付、バインディング）を作る。ルートは「版 A に x%、版 B に 100−x%」を指す。ロールバックは、前の版を指す設定の変更として配る。本家は、段階的なデプロイに直近 100 の版を使えるとしている（[Gradual deployments](https://developers.cloudflare.com/workers/configuration/versions-and-deployments/gradual-deployments/)、2026-09-27 に確認）。
- **静的な安定**：配信が止まっても、ノードは最後に適用した設定で処理を続ける。古さが閾値（既定 5 分）を超えたら、ノードの健全性を下げて警報を出すが、要求は止めない。アカウントの停止（不正利用）だけは、古さに関わらず、届いた時点で反映する。
- **緊急の停止**：特定の関数・アカウントの停止は、通常の変更と同じログで、優先の印を付けて配る。
- 2 を採らない理由：
  - 要求の処理の経路に、ネットワークを越えた読み込みが入る。キャッシュが切れた瞬間の遅延と、DynamoDB の障害の影響を受ける。
  - グローバルテーブルは、ノードの側で「どこまで適用したか」を持てず、伝搬の計測と取りこぼしの検知が難しい。
- 3 を採らない理由：取りに行く間隔が、そのまま伝搬の遅れになる。細かく取りに行くと、ノードの数に比例して S3 の要求が増える。
- 4 を採らない理由：合意のプロトコルを、リージョンをまたいで組むと書き込みが遅く、S3 の段階のノードの数（数万）に広げにくい。ノードは読むだけでよく、合意は要らない。

## Consequences

- 良くなること：
  - 要求の処理は、ノードの手元の LMDB を読むだけになり、遅延が小さく予測しやすい。
  - 制御プレーンが止まっても、デプロイ済みの関数は動き続ける。
  - 番号で、どのノードがどの変更まで適用したかを正確に言える。
- 引き受けるコスト：
  - 配信の仕組み（ログ、中継、ノードの受け手、取り直し）を自前で作り、運用する。
  - 全体で 1 本の番号は、書き込みの量が増えると配信の元が詰まる。本家の当時の書き込みは 1 日 3,000 万だった。S3 の段階で詰まるなら、器ごとに番号を分ける（そのとき、器をまたぐ変更の順序を別に保つ必要がある）。
  - ノードのディスクに全テナントの設定の写しを持つ。S3 の段階の大きさ（関数 500 万）での容量は capacity の領域で見積もる（未検証）。

## Confirmation

- 伝搬の SLO を、ノードの報告から常に計測し、ダッシュボードとアラートにする（runbooks）。
- 障害の注入：中継を落とす、配信の元を落とす、ノードを長く切り離して戻す、の各場合で、取りこぼしがなく、番号の順に適用されることを確かめる。
- 性質ベーステスト：任意の変更の列と、任意の配信の遅れ・重複・並べ替えに対し、ノードの最終的な状態が、正本の同じ番号の時点の状態と等しい。
- lint とレビュー：入口のプロキシとランタイムの要求の処理の経路から、制御プレーンの API・Aurora を呼ぶコードを禁止する（[AGENTS.md](../../AGENTS.md)）。
