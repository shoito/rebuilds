# ADR-0020: 入口と外向きのプロキシは Pingora の上に別々のプロセスとして作り、外向きは専用のリゾルバーとアカウントごとの接続で出す

詳細は [edge-network-and-routing.md](../architecture/edge-network-and-routing.md) の 10 節。

## Context

intent は、エッジの入口の HTTP のプロキシの実装（Rust の自作か、既存の OSS か）を、この領域で決めるとした。[ADR-0001](0001-runtime-build-vs-reuse.md) は、ノードの自前の部品を Rust で作ると決めた。

[ADR-0010](0010-process-sandbox-and-egress-invariants.md) は、外向きのプロキシが守る不変条件を決めた。

- ランタイムのプロセスの外への経路は、受け継いだソケットで外向きのプロキシへ渡すものだけ。
- 名前の解決の後に IP を検査し、検査した IP にだけ接続する。リダイレクトは 1 回ごとに検査する。
- 内部・IMDS・予約・自分たちの anycast の IP を拒否する。止まったら閉じる。
- バインディングの呼び出しも同じプロキシを通り、isolate の中から届く識別子を信じない。

使える部品（2026-09-27 に確認）：

- Pingora：本家の Rust のプロキシのフレームワーク。Apache-2.0。HTTP/1・HTTP/2、gRPC・WebSocket、TLS は BoringSSL などを選べる。無停止の再読み込み。本家で毎秒 4,000 万要求以上を数年扱う（[pingora](https://github.com/cloudflare/pingora)）。
- Envoy：C++。設定と拡張（Wasm・Lua・C++ のフィルター）で作る。
- hyper と rustls で自作する。

## Options

1. **Pingora の上に、入口のプロキシと外向きのプロキシを別々のプロセスとして作る。TLS は BoringSSL**
2. Envoy を入口と外向きに使い、判断をフィルターで書く
3. hyper・rustls で自作する
4. 入口と外向きを 1 つのプロセスにする

## Decision

1 を採用する。

- 入口のプロキシ：TLS の終端（BoringSSL の証明書の選択のコールバック）、HTTP の解析と上限（URL 16KB、ヘッダー 128KB、本文 100MB）、ヘッダーの削除と付与、ルートの解決、ホームのノードへの転送。
- 外向きのプロキシ：ノードに 1 つ、専用の Linux の利用者で動かす。
  - ランタイムのプロセスごとのソケットで受け、要求に付いた呼び出しの ID を、スーパーバイザーの「そのプロセスで進行中の呼び出し」の表と照合する。違えば拒否する。
  - 呼び出しの ID から、アカウント・関数・版・制限を引き、サブリクエストの数と同時の接続の数を強制する。
  - 名前の解決は、リージョンごとの専用の再帰のリゾルバー（私的なホストゾーンに結び付けない）で行う。VPC の既定のリゾルバーは使わない。応答のアドレスに拒否の範囲が 1 つでもあれば、その名前への接続をすべて拒否する。
  - 接続のプールは `(account_id, scheme, host, port, IP)` ごとにし、テナントの間で共有しない。
  - すべてのサブリクエストに `<Brand>-Worker: <送り元の関数のホスト名>` を付ける。
  - この基盤のホスト名への要求は、インターネットへ出さず入口のプロキシへ内部の経路で渡す（ADR-0019）。
  - オリジンへの転送（ADR-0019）も同じ検査を通す。
- 入口と外向きは別のプロセスにする。入口だけが TLS の秘密鍵を読め、外向きだけが外への網に出られる。
- 2 を採らない理由：要求ごとの判断（ルートの解決、呼び出しの ID の照合、テナントごとの数の強制）をフィルターで書くと、C++ か Wasm の拡張が要り、ノードの他の部品（Rust）と言語が分かれる。
- 3 を採らない理由：接続の管理、HTTP/2、無停止の再読み込みを作り直すことになる。Pingora はそれを持ち、本番の実績がある。
- 4 を採らない理由：片方の欠陥で、TLS の秘密鍵と外への網の両方に届く。

## Consequences

- 良くなること：
  - 本番の実績のある部品の上で、判断の部分だけを Rust で書ける。
  - TLS の実装が、ランタイム（workerd）と同じ BoringSSL の系統になる。
  - SSRF の対策が、名前の解決から接続まで 1 か所に集まる。
- 引き受けるコスト：
  - Pingora の版の追従（MSRV は半年ごとに上がる）と、上流の変更への合わせ込み。
  - アカウントごとの接続のプールで、外への接続の数が増える。容量は capacity で見積もる。
  - 呼び出しの ID は、同じプロセスの中の乗っ取りには効かない。被害の範囲は cordon（[ADR-0011](0011-cordon-tiers-and-placement.md)）で限る。
  - 専用のリゾルバーを各リージョンに運用する。

## Confirmation

- 結合テスト：拒否の一覧の全範囲、IPv6 の IMDS、DNS の再束縛、拒否の範囲を混ぜた応答、私的な IP へのリダイレクト、自分たちの anycast の IP、別のプロセスの呼び出しの ID の拒否、`<Brand>-Worker` を利用者が消せないこと。
- ファズ：入口の HTTP の解析、内部の要求の形。
- 本番の探り：[sandbox-and-security.md](../architecture/sandbox-and-security.md) の脱出のテストの探りに、外向きの拒否を含める。
- レビュー：外向きのプロキシが VPC の既定のリゾルバーを使う変更、テナントの間で接続を共有する変更を拒む。
