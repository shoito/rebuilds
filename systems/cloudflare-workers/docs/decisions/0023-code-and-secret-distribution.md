# ADR-0023: バンドルは版の確定の前に全リージョンの S3 へ置き、シークレットはリージョンの鍵で包んだアカウントの鍵で配る

詳細は [deployment-and-config-distribution.md](../architecture/deployment-and-config-distribution.md) の 4.2 節、7 節、8 節。

## Context

[ADR-0004](0004-config-and-code-distribution.md) は、コードの本体を内容のハッシュ（SHA-256）で S3 に置き、各リージョンへ複製し、ノードが取って確かめると決めた。シークレットはアカウントごとの鍵で暗号化したまま配り、詳細は後で決めるとした。

- デプロイの伝搬は p99 30 秒（NFR-008）。コードがノードにないときの起動は p99 50ms（NFR-001）。
- S3 の複製は、RTC でも 99.9% を 15 分以内という約束で、数秒の約束はない（[S3 Replication Time Control](https://docs.aws.amazon.com/AmazonS3/latest/userguide/replication-time-control.html)、2026-09-27 に確認）。
- KMS のマルチリージョンキーは、同じ素材で別のリージョンで復号できる（[Multi-Region keys](https://docs.aws.amazon.com/kms/latest/developerguide/multi-region-keys-overview.html)、2026-09-27 に確認）。
- 静的な安定：KMS などが止まっても、デプロイ済みの関数は動き続ける（ADR-0004）。
- どのノードもどの関数も動かしうる（リージョンの中のホームのノードは温めのためで、隔離のためではない）。

## Options

コード：

1. **版の作成で、全リージョンのバケットへ同期で PUT し、終わってから版を `ready` にする。ノードへは中継のキャッシュと先読みで届ける**
2. 東京に 1 回置き、S3 の複製（RTC）で各リージョンへ広げる
3. コードを変更のログに入れて、全ノードへ押し出す

シークレット：

- a. **アカウントの鍵（ADK）で値を暗号化し、ADK をリージョンの秘密の鍵（RSK。KMS で包む）で包んで配る。ノードは RSK を起動時に 1 回開く**
- b. ADK を KMS（マルチリージョンキー）で直接包んで配り、ノードがアカウントごとに KMS で開く
- c. 平文のシークレットを、ノードの間の mTLS の経路でだけ配る

## Decision

1 と a を採用する。

- バンドルのキーは `bundles/sha256/<hex>`。版の作成で、制御プレーンが 5 つのリージョンのバケットへ並行に `If-None-Match: *` で PUT し、全部の成功で `ready` にする。30 秒失敗し続けるリージョンは `pending_regions` にして `ready` にし、そのリージョンのノードは東京から取る。
- ノードは、同じ AZ の中継（HTTP/2、mTLS、ディスクの LRU 200GB）から取り、なければリージョンの S3、最後に東京。取った後に SHA-256 を確かめる。
- デプロイが中継に届いたら、中継がバンドルをキャッシュへ取る。ホームのノードも先に取る。デプロイの伝搬の SLI に、中継のキャッシュへの到着を含める。
- 参照されなくなったバンドルは、印を付けて 30 日後に消す。
- シークレットの値は、受付の時点で ADK で AES-256-GCM で暗号化する（追加の認証データにアカウント・関数・名前・値の ID）。ADK は制御プレーンで KMS に包んで持ち、各リージョンの RSK で包み直して配る。
- ノードのスーパーバイザーは、起動時に自分のリージョンの RSK を KMS で開く（暗号化の文脈つき）。isolate の読み込みのとき、ADK を開き、値を開き、読み込みの指示でランタイムへ渡す。平文をディスク・ログに出さない。入口と外向きのプロキシは RSK を持たない。
- RSK は毎月入れ替え、全 ADK を包み直して配る。
- 2 を採らない理由：複製の時間の約束が 15 分で、30 秒の SLO に入らない。
- 3 を採らない理由：全ノードが全関数のコードを持つことになり、S1 でも数百 GB（5 万関数×最大 10MiB）になりうる。使われない関数のコードまで配る。
- b を採らない理由：冷たい isolate の読み込みごとに、アカウントの KMS の呼び出しが要りうる。KMS の障害・スロットリングが、そのまま関数の起動の失敗になる（静的な安定を崩す）。どのノードもどのアカウントを開けるので、アカウントごとの KMS の呼び出しは隔離を強めない。
- c を採らない理由：平文が中継とノードの間を流れ、中継のディスク・メモリにも平文が残りうる。

## Consequences

- 良くなること：
  - 版が `ready` なら、全リージョンにコードがある。デプロイの時間にコードの複製が入らない。
  - KMS の呼び出しは、ノードの起動時のリージョンの鍵 1 つ（証明書の鍵と合わせて 2 つ）で、関数の起動の経路にない。
  - シークレットの平文は、スーパーバイザーの一時のメモリと isolate の中だけにある。
- 引き受けるコスト：
  - 版の作成の時間に、5 つのリージョンへの PUT（最大 10MiB）が入る（東京からフランクフルトで 1〜2 秒の見込み。未検証。E5 の `bundle-multi-region-put` で測る）。
  - RSK が漏れると、そのリージョンの全アカウントのシークレットを開ける。ノードの侵害で同じことが起きる前提は変わらないので、ノードのロールの最小の権限とエッジのフリートの別のアカウントで守る。
  - 鍵の階層の全体（ADK を包む制御プレーンの鍵、入れ替えの方針）は security の領域で確定させる。

## Confirmation

- 結合テスト：1 リージョンのバケットを拒否にしたとき、版が `pending_regions` で `ready` になり、そのリージョンのノードが東京から取る。
- 結合テスト：シークレットの平文が、ノードのディスク・ログ・コアダンプ・中継に出ない。入口のプロキシのプロセスの資格情報で RSK を開けない。
- 障害の注入：KMS を拒否にしても、動いているノードの関数（シークレットあり）が冷たい起動を含めて動く。新しいノードは健全にならない。
- 監視：`pending_regions` の数、中継のキャッシュの当たりの率、コードの取得の p99。
