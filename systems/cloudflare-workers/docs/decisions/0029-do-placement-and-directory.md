# ADR-0029: Durable Objects の実体の場所は作成時に決めて変えない。名前の ID は東京の台帳で調停し、一意の ID は場所を ID に埋め込む

詳細は [durable-objects.md](../architecture/durable-objects.md) の 4 節。

## Context

ADR-0005 は、実体を最初の要求に近いリージョンに置き、作成後は場所を変えないと決めた。場所のヒントとデータの所在の指定（`jp` など）を持つ。名前から実体の場所への対応の置き方は、durable-objects の領域で決める。

本家（2026-09-27 に確認）：

- 実体は最初の要求の近くに置かれ、作成後は移らない。場所のヒント（`wnam`・`enam`・`sam`・`weur`・`eeur`・`apac`・`apac-ne`・`apac-se`・`oc`・`afr`・`me`）は最善の努力で、最初の `get()` だけに効く。管轄（`eu`・`us`・`fedramp`）は実行と保存をその中に限る（[Data location](https://developers.cloudflare.com/durable-objects/reference/data-location/)）。
- ID は名前空間に結びつき、別の名前空間の ID は使えない。

名前の ID は、2 つのリージョンの関数が同時に同じ名前の最初の要求を出しうる。どちらのリージョンに作るかを 1 つに決める調停が要る。

## Options

1. **名前の ID は東京の DynamoDB の台帳で条件付きの作成により調停し、グローバルテーブルで全リージョンへ読み込み用に複製する。一意の ID は作成のリージョンを ID に埋め込み、台帳を使わない**
2. **名前のハッシュでリージョンを決め打ちする**（台帳なし）
3. **各リージョンに台帳を持ち、リージョンの間の合意で調停する**

## Decision

1 を採用する。

- ID は 32 バイト（版、管轄、リージョンの番号、乱数または名前の HMAC、名前空間の鍵によるタグ）。`idFromString` はタグを検証する。
- 名前の台帳 `do_directory` は東京の DynamoDB。作成は `attribute_not_exists(pk)` の条件付きの書き込みで、先に確定した方が勝つ。項目は作成後に変えない（手動のリージョンの退避の `region_epoch` を除く）ので、ルーターは無期限にキャッシュする。
- 作成のリージョンは、管轄 → 場所のヒント（S1 のリージョンへの対応の表）→ 呼び出した関数のリージョンの順で決める。
- 管轄は S1 で `jp`（東京と大阪だけ）。`eu` は EU に 2 つ目のリージョンを持つ S2 で足す。
- 2 を採らない理由：利用者に近い場所に置けない。日本の利用者の名前が海外のリージョンに決まりうる。
- 3 を採らない理由：リージョンをまたぐ合意の遅延が、名前の最初の要求ごとに入る。作成の調停だけなら、1 つの正本の条件付きの書き込みで足りる。

## Consequences

- 良くなること：
  - 名前の実体の場所が 1 つに決まり、以後はキャッシュだけで経路が決まる。
  - 一意の ID は、東京の障害の間も作れて、経路も決まる。
  - ID の偽造で別の名前空間に届かない。
- 引き受けるコスト：
  - 東京の DynamoDB の障害の間は、新しい名前の実体を作れない。
  - 名前の最初の要求は、東京への往復（海外から 100ms 以上の見込み。未検証。E9 の `do-directory` で測る）が入る。
  - 場所のヒントの値は本家の地域の名前を使うが、対応するリージョンは S1 の 5 つだけで、本家より粗い。

## Confirmation

- 性質ベーステスト：任意のリージョンからの同じ名前の同時の最初の要求で、台帳の場所が 1 つに決まり、全ての要求が同じ実体に届く。
- 結合テスト：別の名前空間の ID、タグを変えた ID の拒否。管轄 `jp` の実体が日本のリージョンだけに置かれる。
