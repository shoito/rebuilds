# ADR-0039: 使用量は仕事をした部品が数え、冪等の ID の束で東京へ送り、重複を捨てて集計する

詳細は [limits-and-billing.md](../architecture/limits-and-billing.md) の 5 節。

## Context

intent の MVP は、要求の数と CPU の時間（ミリ秒）で数える従量の課金を含む。ストレージ（KV、オブジェクト、Durable Objects、キュー）の操作と保存、外向きの転送も課金する（[ADR-0040](0040-jpy-pricing-invoices-and-spend-controls.md)）。

- 使用量は 5 つのリージョンの多数のノードと、ストレージのサービスで生まれる。
- 利用者のコードは悪意があるものとして扱う（[AGENTS.md](../../AGENTS.md)）。isolate の中の数は信じられない。
- ランタイムは呼び出しごとの記録（`cpu_us`、`outcome` など）をスーパーバイザーへ送り、「記録が届かなかった呼び出しは課金しない」と決めている（[runtime-and-isolates.md](../architecture/runtime-and-isolates.md) の 6.3 節）。
- 期間の枠と費用の上限（[ADR-0038](0038-plan-limits-and-edge-enforcement.md)）は、数十秒の遅れで集計を必要とする。

## Options

1. **仕事をした部品が数え、ノードで 10 秒ごとの束にまとめ、spool → リージョンの Kinesis → 東京の集計。`usage_batches` の主キーで重複を捨て、時間ごとに Aurora に足す**
2. 呼び出しごとの記録をそのまま中央へ送り、課金を保存するログ（ClickHouse）から集計する
3. 各リージョンで集計し、月末にリージョンの合計を東京へ送る

## Decision

1 を採用する。

- 数える部品：要求と CPU 時間はスーパーバイザー（呼び出しの記録から）、利用者への応答の転送は入口のプロキシ、サブリクエストの転送は外向きのプロキシ、ストレージの操作と保存は各ストレージのサービス。
- ノードの使用量の送り手が、10 秒の窓ごとに `(account_id, script_id, resource_id, metric)` で足した束を作り、ローカルのディスクの spool に書いてから送る。束の ID は `<部品の種類>:<部品の ID>:<起動の ID>:<番号>`。
- 東京の集計は、1 つのトランザクションで `usage_batches` に束の ID を入れ、入れられたときだけ `usage_hourly`（と、枠のあるアカウントの `usage_daily_counters`）に足す。
- 生の束は S3 に 13 か月置き、再計算に使う。
- 課金しないもの：基盤の都合の失敗（`internalError`・`evicted`）、止めた要求、記録の届かない呼び出し、月の締めの後に届いた前の月の束、費用の上限を超えた遅れの分。
- 入口の要求の数と呼び出しの記録、サブリクエストの数を 1 時間ごとに突き合わせ、差が 0.5% を超えたら警報を出す。
- 2 を採らない理由：保存するログは標本（`head_sampling_rate`）と日ごとの上限で間引かれ、利用者が無効にできる。課金の正本にできない。呼び出しごとに中央へ送る量も大きい。
- 3 を採らない理由：期間の枠と費用の上限は、アカウント全体の数を数十秒で知る必要がある。

## Consequences

- 良くなること：
  - 再送・重複・並べ替えに対し、合計が正しい。
  - 利用者のコードが数を変えられない。
  - 期間の枠の判定と、請求の元が同じ数になる。
- 引き受けるコスト：
  - 束の ID の表が大きくなる（90 日で消す）。
  - S2 で量が 10 倍になると、Aurora での加算が詰まりうる。そのときは `usage_hourly` を列の保存へ移す（別の ADR）。
  - spool のディスクが満ちると束を捨てる（課金しない側に倒れる）。

## Confirmation

- 性質ベーステスト：任意の束の列と、任意の再送・並べ替えで、`usage_hourly` の合計が重複を除いた束の合計と等しい。
- 結合テスト：呼び出しの記録を落とすと、突き合わせの警報が出て、請求は少ない側になる。
- 本番の探り：探りのアカウントで決まった数の要求と転送を毎時送り、`usage_hourly` の値が合う。
