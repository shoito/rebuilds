# ADR-0048: 監査ログはハッシュの鎖と WORM の写しで改ざんを検知できるようにし、アカウントのデータは削除から 30 日の猶予の後に消し、写しは各保存の保持の期間で消える

詳細は [security.md](../architecture/security.md) の 6 節と 8 節。

## Context

[ADR-0042](0042-api-tokens-roles-and-audit-log.md) は、利用者の監査ログ（`audit_events`）を変更と同じトランザクションで Aurora に書き、18 か月持つと決めた。改ざんの検知と長期の保存は security の領域に預けた。

- Aurora の行は、制御プレーンの DB の管理者の権限で書き換えられる。運用者の操作（停止、ログの閲覧、break-glass）の記録が、同じ運用者に消されると、調べられない。
- S3 Object Lock のコンプライアンスのモードでは、保持の期間の中は、ルートの利用者を含めて誰も上書き・削除できない（[Object Lock](https://docs.aws.amazon.com/AmazonS3/latest/userguide/object-lock.html)、2026-09-27 に確認）。
- 各領域は、データの写しを別々の期間で持つ：DynamoDB の PITR 35 日（[ADR-0024](0024-kv-central-store-dynamodb.md)）、Durable Objects の WAL 30 日（[ADR-0031](0031-do-sqlite-replication-and-pitr.md)）、ログ 3・7 日（[ADR-0037](0037-tail-sessions-and-tenant-logs.md)）、使用量の生の束 13 か月（[ADR-0039](0039-usage-metering-pipeline.md)）。
- アカウントの削除のとき、どこまで・いつまでに消すかは、利用者との約束と法令（intent の L7）に関わる。

## Options

1. **監査の行をアカウントごとのハッシュの鎖にし、1 時間ごとの要約を WORM（Object Lock のコンプライアンスのモード）に置く。削除は 30 日の猶予の後に正本から消し、写しは各保存の保持の期間で自然に消える**
2. 監査ログを最初から WORM の S3 にだけ書く（Aurora に持たない）
3. 削除の時点で、写し（PITR、WAL、S3 の旧い版）まで能動的に消す

## Decision

1 を採用する。

**監査ログ**：

- `audit_events` の各行に `prev_hash`・`row_hash`（SHA-256。アカウントごとの鎖）を足す。鎖はアカウントごとに行を直列にする（同じアカウントの監査の書き込みは行のロックで順に並ぶ）。
- `outbox` と同じ形で、監査の行を Kinesis Data Firehose で `log-archive` のアカウントの S3（Object Lock、コンプライアンスのモード、18 か月）へ写す。1 時間ごとに、アカウントごとの鎖の先頭の要約（ダイジェスト）を別のファイルに置き、`log-archive` の署名の鍵で署名する。
- 基盤の監査（運用者の権限の申請と承認、break-glass、CloudTrail、鍵の操作、`quarantine` への証拠の写し）は、`log-archive` に 3 年置く（法務の確認待ち。値は仮）。
- 毎日、Aurora の鎖と WORM の写しを突き合わせ、食い違いを SEV2 のインシデントにする。

**データのライフサイクル**：

| 段 | 期間 | 起きること |
| --- | --- | --- |
| 削除の予約（`deletion_scheduled`） | 30 日 | 関数は止まる（ルートは 404）。データは残り、利用者は戻せる。既定のサブドメインは確保したまま |
| 正本の削除 | 30 日目 | 関数・版・バンドルの参照、KV の名前空間、バケット、Durable Objects の名前空間、キュー、ログ、シークレット（ADK を捨てる）を消す |
| 写しの自然な消滅 | 正本の削除から最長 35 日 | DynamoDB の PITR、S3 の旧い版（7 日）、DO の WAL（30 日）、CRR の写し、ClickHouse の TTL で消える |
| 残すもの | 各期間 | 監査ログ（18 か月）、請求書と使用量（法令の保存の期間。法務・経理の確認待ち）、基盤の監査（3 年。仮） |

- ADK を捨てると、写しに残るシークレットの暗号文も開けなくなる（暗号的な削除）。
- 利用者への約束は「削除の予約から 65 日以内に、写しを含めて消える」にする。
- 2 を採らない理由：画面の絞り込みと CSV（ADR-0042）を S3 の上で作ることになり、変更と同じトランザクションで書く約束を守れない。
- 3 を採らない理由：PITR と WAL は運用の誤りから戻すための保険で、利用者ごとに部分を消す API がない（DynamoDB の PITR は表の単位で新しい表へ戻す機能で、戻せる期間を 1〜35 日で短くする以外に、中の項目を消す手段は文書にない。[Point-in-time backups](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Point-in-time-recovery.html)、2026-09-27 に確認）。能動的に消すと、全体の復旧の手段を壊す。

## Consequences

- 良くなること：
  - 運用者が Aurora の監査の行を書き換えても、WORM の写しと鎖の突き合わせで見つかる。
  - 削除の約束が、保存ごとの保持の期間から導ける値になる。
- 引き受けるコスト：
  - アカウントごとの鎖で、同じアカウントの監査の書き込みが直列になる（同じアカウントの同時の変更が少し遅くなる）。
  - Object Lock のコンプライアンスのモードは、誤って長い期間を設定すると、アカウントを消す以外に消せない。期間の変更は 2 人の承認にする。
  - 削除から完全な消滅まで最長 65 日かかる。

## Confirmation

- 性質ベーステスト：任意の監査の行の列で、途中の 1 行を変えると、鎖の検証がその行から失敗する。
- 日次の突き合わせのジョブの成功と、食い違い 0 件（SLI）。
- 結合テスト：削除の予約の 30 日後に、各保存から正本が消え、ADK が捨てられる。削除の予約の中の戻しで、全てが元に戻る。
