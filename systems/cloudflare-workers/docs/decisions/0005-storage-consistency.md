# ADR-0005: ストレージの一貫性は製品ごとに決め、利用者に明示する

## Context

関数は世界の複数のリージョンで動くが、状態を持つ保存は、速さ・一貫性・可用性を同時に最大にできない。本家は、用途ごとに別の製品を用意し、一貫性の約束を製品ごとに変えている（2026-09-27 に確認）。

- **KV**：結果整合。少数の中央のデータセンターに保存し、読まれた拠点でキャッシュする。書き込んだ拠点ではすぐ見えることが多いが、他の拠点では、キャッシュの期限が切れるまで最大 60 秒以上かかりうる。キャッシュの TTL の既定は 60 秒、最小は 30 秒。同じキーへの書き込みは 1 秒に 1 回、値は 25MiB まで（[How KV works](https://developers.cloudflare.com/kv/concepts/how-kv-works/)、[KV limits](https://developers.cloudflare.com/kv/platform/limits/)）。
- **R2（オブジェクトストレージ）**：強い整合。書き込み・更新・削除の結果は、直後に世界のどこからでも見え、一覧も最新になる。同じキーへの同時の書き込みは、最後に終わったものが勝つ。ただし、カスタムドメインでキャッシュを有効にすると、キャッシュの分だけ緩む（[R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/)）。S3 の API の主な操作に対応し、リージョンの値は `auto` を使う（[R2 S3 API](https://developers.cloudflare.com/r2/api/s3/api/)）。
- **Durable Objects**：名前ごとに世界で 1 つの実体。単一のスレッドで協調的に処理する。最初の要求の近くに置かれ、作成後は場所を変えない。場所のヒントは最善の努力で、保証ではない。EU などの管轄の指定ができる（[What are Durable Objects](https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/)、[Data location](https://developers.cloudflare.com/durable-objects/reference/data-location/)）。
  - 入力のゲート：保存の操作の実行中は、保存の完了以外のイベントを渡さない。
  - 出力のゲート：書き込みが確定するまで、新しい外向きの通信を止める（[Durable Objects: Easy, Fast, Correct — Choose three](https://blog.cloudflare.com/durable-objects-easy-fast-correct-choose-three/)、2021-08-03）。
  - SQLite の保存では、変更のログを別のデータセンターの 5 台の follower に送り、3 台の確認で書き込みを確定する。ログは 10 秒か 16MB ごとにまとめてオブジェクトの保存に置き、30 日の時点の復旧ができる（[Zero-latency SQLite storage in every Durable Object](https://blog.cloudflare.com/sqlite-in-durable-objects/)、2024-09-26）。
- **Queues**：既定で少なくとも 1 回の配信。重複がありうるので、利用者の側で冪等にすることを勧める（[Delivery guarantees](https://developers.cloudflare.com/queues/reference/delivery-guarantees/)）。

この題材は、S1 で 5 リージョン、中央は東京に置く（[ADR-0003](0003-edge-locations.md)）。本家の「世界の拠点」を「AWS のリージョンと AZ」に読み替えて、各製品の約束を決める必要がある。

## Options

1. **製品ごとに一貫性を変える**（本家と同じ考え方）。KV は結果整合、オブジェクトストレージは強い整合、Durable Objects は 1 つの実体と強い整合、キューは少なくとも 1 回
2. **すべてを強い整合にする**（すべての読み書きを中央のリージョンへ送る）
3. **すべてを結果整合にする**（各リージョンに複製し、非同期に収束させる）

## Decision

1 を採用する。製品ごとの約束は次のとおり。実装の具体（保存先の選定など）は、各領域の文書と ADR で決める。

| 製品 | 約束 | S1 の構成の方針 |
| --- | --- | --- |
| KV | 結果整合。書き込みは中央の正本に確定してから成功を返す。読み込みは、ノード・リージョンのキャッシュから返し、TTL（既定 60 秒、最小 30 秒）で古さを抑える。TTL が既定の 60 秒のとき、全リージョンで読めるまで p99 70 秒以内（NFR-009）。同じキーの同時の書き込みは、最後の書き込みが勝つ。同じキーへの書き込みは 1 秒に 1 回まで | 正本は東京（候補は DynamoDB。kv-store の領域で決める）。各リージョンに読み込みのキャッシュの層を置く。書き込んだリージョンのキャッシュは、書き込みの時点で更新する |
| オブジェクトストレージ | バケットにホームのリージョンを持つ（S1 は東京だけ。S2 で選べるようにする）。成功を返した書き込み・上書き・削除は、直後のすべての読み込み・一覧に反映する（どのリージョンの関数から読んでも）。同じキーへの同時の書き込みは、最後に確定したものが勝つ。公開の配信でキャッシュを有効にした場合だけ、キャッシュの TTL の分だけ緩む | 本体とメタデータはホームのリージョンに置く。他のリージョンの関数からの読み書きは、ホームのリージョンへ送る（遅延は増える）。本体は S3（S3 は書き込みの直後の読み込みで強い整合）、S3 互換の API とアカウントの認証は自前の層で作る |
| Durable Objects に相当するもの | 名前ごとに同時に 1 つの実体。1 つの実体の中では要求を直列に処理し、保存の操作は直列化可能。入力のゲートと出力のゲートを持つ。書き込みは、別の AZ の複製の過半数の確認で確定する。確定する前に、その結果に依存する応答・外向きの通信を出さない | 実体は、最初の要求に近いリージョンに置き、作成後は場所を変えない（本家と同じ）。場所のヒントとデータの所在の指定（`jp` など）を持つ。保存は SQLite。変更のログを同じリージョンの別の AZ の 2 台へ送り、3 台のうち 2 台で確定する。ログはまとめて S3 へ置き、30 日の時点の復旧に使う |
| キュー | 少なくとも 1 回。確定したメッセージは失わない。重複はありうる。再試行の上限を超えたら、デッドレターのキューへ移す | queues-and-cron の領域で決める |

**Durable Objects の配置と障害の移動**：

- 名前から実体の場所への対応は、リージョンごとの配置の台帳に置く。実体を動かすホストは、期限付きのリース（フェンシングの番号付き）を持つ。
- ホストが落ちたら、リースの期限の後、同じリージョンの別のホストが、複製済みのログから SQLite を戻して実体を作り直す。古いホストの書き込みは、フェンシングの番号で拒否する。
- リージョン全体の障害では、S1 は自動でリージョンを移さない（データの所在の約束と、複製の遅れのため）。そのリージョンの実体は、復旧まで使えない。手動でのリージョンの移動の手順と、その場合の RPO は durable-objects の領域と runbooks で決める。
- この一意性（同時に 1 つの実体）は、可用性より優先する。

**KV の読み込みの近さ**：S1 で、東京から遠いリージョンのキャッシュのミスは、100ms 以上かかりうる（未検証）。S2 で、正本の読み込みの複製を海外のリージョンに置く。

2 を採らない理由：KV の主な用途（読み込みの多い設定、フラグ）で、遠いリージョンの関数の読み込みが毎回中央へ往復し、エッジで動かす意味がなくなる。

3 を採らない理由：オブジェクトの上書きと削除、Durable Objects のような調整（カウンター、在庫、共同編集）を、正しく書けなくなる。利用者に衝突の解決を押し付ける。

## Consequences

- 良くなること：
  - 利用者は、用途（読み込みの多い設定、ファイル、調整の要る状態）で製品を選び、それぞれの約束に頼って書ける。
  - 本家と約束が近いので、本家向けの設計の知識をそのまま使える。
- 引き受けるコスト：
  - 製品ごとに、別の保存の仕組みと運用を持つ。
  - オブジェクトストレージの強い整合は、ホームのリージョンから遠い関数からの読み書きを遅くする。本家は「世界のどこからでも強い整合」を約束しているが、この設計はホームのリージョンへの往復で同じ約束を守るので、遅延は本家より大きくなりうる（本家の内部の方式は未検証）。
  - Durable Objects は、リージョン全体の障害で使えなくなる（S1）。本家は別のデータセンターへ複製しているが、この設計は同じリージョンの AZ への複製にとどめる。データの所在の約束と釣り合わせた結果である。
  - KV の結果整合は、利用者の誤解を生みやすい。ドキュメントと CLI の警告で、書き込みの直後の読み込みが古い値を返しうることを示す。

## Confirmation

- KV：書き込みから各リージョンで新しい値が読めるまでの時間を、合成の書き込みで常に計測する（NFR-009）。
- オブジェクトストレージ：書き込み・上書き・削除の直後の読み込み・一覧を、全リージョンの関数から確かめる線形化可能性の検査（Jepsen に近い試験）を、E8 の受け入れで行う。
- Durable Objects：
  - 性質ベーステストと障害の注入で、ホストの停止・網の分断・リースの期限切れの任意の組み合わせで、1 つの名前に同時に 2 つの実体が書き込みを確定しないこと。
  - 出力のゲート：書き込みの確定の前に、その結果を含む応答が外へ出ないこと。
  - E9 の受け入れで、線形化可能性の検査を行う。
- キュー：確定したメッセージが、ブローカーの停止の後も必ず配信されること（重複は許す）。
