# ADR-0019: ルートはホスト名の表と制限した文法で解決し、リージョンの中はランデブーハッシュでホームのノードへ 1 回だけ転送する

詳細は [edge-network-and-routing.md](../architecture/edge-network-and-routing.md) の 8 節と 9.1 節。

## Context

入口のプロキシは、ホスト名とパスから、どの関数を動かすかを決める。本家のルートの文法は、ワイルドカード `*` だけを持ち、ホスト名の先頭とパスの末尾に置ける。複数が当たると「最も具体的なもの」が勝ち、関数のないルートは弱いパターンを打ち消す。`*example.com` は `myexample.com` にも当たる（[Routes](https://developers.cloudflare.com/workers/configuration/routing/routes/)）。カスタムドメインは関数をオリジンにし、同じホスト名のルートが先に動く（[Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/)）。どちらも 2026-09-27 に確認した。

本家は利用者の DNS（ゾーン）を持つので、ルートに当たらない要求はゾーンの DNS のオリジンへ行く。この題材は DNS の製品を持たない。

isolate を温かく保つため、リージョンの中で同じ関数の版を同じノードへ寄せる（[runtime-and-isolates.md](../architecture/runtime-and-isolates.md) の 5.4 節、[ADR-0007](0007-isolate-lifecycle-and-dynamic-loading.md)）。転送の実装はこの領域で決める。

## Options

ルート：

1. **本家の文法から `*example.jp`（ドットのない先頭の `*`）を除き、順位を決定表で固定する。ルートに当たらない要求は、ホスト名に設定したオリジンへ転送する**
2. 本家の文法をそのまま受ける
3. 正規表現を受ける

ホームのノード：

- a. **ランデブーハッシュ（HRW）。ノードの一覧はリージョンの中継が配る**
- b. 一貫性ハッシュの環（仮想のノード）
- c. GA のカスタムルーティングで、利用者を直接ホームのノードへ

## Decision

1 と a を採用する。

- ホスト名の表（`host/`）と、ホスト名ごとの並べ替え済みのルートの一覧（`routes/`、`routes_wild/`）をノードの LMDB に持つ。
- 順位：ホスト名の完全一致 ＞ `*.` のワイルドカード（親が長い方が上）＞ パスの前方が長い方 ＞ 同じ長さなら完全一致 ＞ スキームの指定あり ＞ 作成の早い方。
- 解決の順は決定表 `DT-ROUTE-001`（停止 → ACME のトークン → HTTPS への転送 → ルート → ワイルドカードのルート → 既定の関数 → オリジン → 404）。
- ホスト名に `origin` を設定できる。ルートに当たらない要求と、ルートで動く関数の同じホスト名への `fetch` はオリジンへ行く。オリジンへの転送は外向きのプロキシを通し、内部のアドレスを拒否する。
- この基盤のホスト名への `fetch` は、インターネットへ出さず内部の経路で扱う（`DT-ROUTE-002`）。深さは 16 まで。
- ホームのノードは `(script_id, version_id)` の鍵で HRW により決める。ノードの一覧は、リージョンの中継がノードの心拍から作って配る。転送は内部のポートの mTLS の HTTP/2 で 1 回だけ。ホームが断る（CPU 70% 以上、メモリの hard の段、50ms で応答の頭がない）と、受けたノードで動かす。
- 2 を採らない理由：`*example.jp` は他人のドメイン（`myexample.jp`）にも当たり、本家も注意書きを置いている。所有の確認と組み合わせると誤りの元になる。
- 3 を採らない理由：照合の時間が読めず（ReDoS）、順位も決められない。
- b を採らない理由：HRW は仮想のノードの調整が要らず、ノードの増減で動く鍵が最小になる。S1 のリージョンあたりのノードの数（数十）なら、1 要求あたりの計算も小さい。
- c を採らない理由：ADR-0017 のとおり。

## Consequences

- 良くなること：
  - 順位が表で決まり、利用者に説明できる。表駆動と性質ベーステストで検証できる。
  - ルートの一部だけに関数を置き、残りを既存のサーバーへ流す使い方ができる。
  - 要求の多い関数を除き、同じ版の要求が同じノードに集まる。
- 引き受けるコスト：
  - 本家のパターンのうち `*example.jp` の形は移せない。CLI が 2 つのパターンへの書き換えを示す（developer-tooling）。
  - オリジンへの転送は、この基盤が利用者のサーバーの前に立つリバースプロキシになる。キャッシュは持たない（intent の範囲の外）。
  - ノードの間の転送で、同じリージョンの中の往復（AZ をまたげば 1ms 程度。未検証）が 1 回増える。

## Confirmation

- 表駆動テスト：`DT-ROUTE-001` と `DT-ROUTE-002` の全行。
- 性質ベーステスト：任意のパターンの集合と URL で、結果が集合の並べ順によらず、当たったものより具体的で同じ URL に当たるパターンが集合にない。
- 性質ベーステスト：ノードを 1 台足す・抜くと、動く鍵は約 1/N で、抜けたノード以外の鍵は動かない。
- 結合テスト：オリジンに私的な IP・IMDS を設定しても届かない。自分のホスト名への `fetch` の深さ 17 で 508。
