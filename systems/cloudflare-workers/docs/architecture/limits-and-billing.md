## 1. 目的と範囲

- 目的：利用者が、どこまで使えて、いくらかかるかを、事前に円で知れる。基盤は、原価を下回る料金で使われない（intent の K8）。1 つのテナントの使いすぎが、他のテナントに響かない。

| 範囲に含む | 範囲に含まない（担当の領域） |
| --- | --- |
| 計画（無料・有料・専用）ごとの制限の値の表 | 制限を強制する仕組みの実装（各領域） |
| 日ごとの枠と費用の上限の止め方、エラーの番号 | エラーの頁の見た目（edge-network-and-routing） |
| 使用量の計測の点、束の形、集計、突き合わせ | 基盤の運用のメトリクス（observability） |
| 円の料金、無料の枠、原価の見積もり | ノードの台数と原価の詳細の見積もり（capacity） |
| 請求書、消費税、支払い、未払い | 決済の代行の事業者の画面（dashboard-and-api の請求の画面） |
| 予算の警告、費用の上限 | 不正な利用の停止（abuse-and-trust-safety） |

## 4. 制限の強制とエラーの番号

[ADR-0038](../decisions/0038-plan-limits-and-edge-enforcement.md)。

### 4.1 2 つの種類

| 種類 | 例 | 止め方 | 遅れ |
| --- | --- | --- | --- |
| 要求ごとの制限 | CPU 時間、メモリ、サブリクエスト、大きさ | 処理する部品がその場で止める | なし |
| 期間の枠と費用 | 無料の 1 日の要求、転送、ストレージの操作の枠、費用の上限 | 集計がアカウントの状態を変え、変更のログで全ノードへ配る | 最大約 30 秒（4.2 節） |

- 要求ごとの制限の値は、版の `limits`（計画の上限と `limits.cpu_ms` の小さい方）とアカウントの状態（計画）から、ノードの手元で決める。制御プレーンを呼ばない（ADR-0004）。

### 4.2 期間の枠の止め方

```
ノードの使用量の送り手（10 秒ごとの束）──▶ 東京の集計（5 節）
                                              │ 無料のアカウントの日ごとの数を足す
                                              │ 枠の 100% を超えた
                                              ▼
                              config_outbox：account_state/<account_id>
                                { quota_block: { kind: "requests_daily", until: "翌日 0:00 JST" } }（優先）
                                              │ p99 10 秒
                                              ▼
                              入口のプロキシ：該当のアカウントの要求を 1027 で返す（関数を呼ばない）
```

- **遅れの見積もり**：束の間隔 10 秒＋送りと集計 5 秒＋配信 p99 10 秒 ＝ 約 25〜30 秒。その間の超過は許し、**枠を超えた分は課金しない**（無料の計画はもともと課金しない）。
- 80% を超えたら、メールとダッシュボードで知らせる。
- ストレージの操作の枠（KV の書き込み 1 日 1,000 など）は、バインディングの呼び出しを受けるストレージの部品が、アカウントの状態の `quota_block` を見て、その操作だけを失敗させる（KV の書き込みなら例外。関数は動き続ける）。
- 日ごとの枠は JST の 0 時に戻す。集計は 0 時に `quota_block` を消す変更を書く（`until` を過ぎた印は、ノードも無視する。消す変更が遅れても止まり続けない）。

### 4.3 エラーの番号

本家と同じ意味のものは同じ番号にする（番号は名前ではないので、[リポジトリ共通の ADR-0006](../../../../docs/decisions/0006-brand-neutral-identifiers.md) の対象外と判断する）。この基盤だけのものは 1200 番台にする。

| 番号 | HTTP | 意味 | 出す所 |
| --- | --- | --- | --- |
| 1101 | 500 | 関数が例外を投げた（`exception`） | ランタイム。本家の同じ番号の意味は未検証 |
| 1102 | 503 | 資源の上限を超えた（`exceededCpu`・`exceededMemory`・`exceededStartup`） | ランタイム |
| 1027 | 429 | 無料の 1 日の枠を超えた | 入口のプロキシ |
| 10021 | —（管理 API の 400） | 起動の時間を超えた（デプロイの拒否） | 検証のフリート |
| 1201 | 503 | 費用の上限に達した（8 節） | 入口のプロキシ |
| 1202 | 503 | 基盤の都合で処理できない（`evicted`、コードの取得の失敗、`internalError`） | ノード |
| 1203 | 403 | 関数・アカウントが停止されている（不正な利用、未払い）。理由は出さない | 入口のプロキシ（[abuse-and-trust-safety.md](abuse-and-trust-safety.md) の 6 節） |

- エラーの頁は、`<Brand>-Ray` と番号だけを出す。関数の持ち主の情報、停止の理由は出さない。
- 1202 は利用者の責めではないので、課金しない（5.4 節）。

## 5. 使用量の計測

[ADR-0039](../decisions/0039-usage-metering-pipeline.md)。

### 5.1 数える場所

**課金の量は、その仕事をした部品が数える。** isolate の中の数を信じない。

| 量 | 数える部品 | 元 |
| --- | --- | --- |
| 要求（`fetch`・cron・キューの束・アラーム・WebSocket のメッセージの受信） | スーパーバイザー | 呼び出しの記録（[runtime-and-isolates.md](runtime-and-isolates.md) の 6.3 節）の件数 |
| CPU 時間 | スーパーバイザー | 呼び出しの記録の `cpu_us` |
| 外向きの転送（利用者への応答） | 入口のプロキシ | 応答のヘッダーと本文のバイト数（圧縮の後、TLS の前）。WebSocket はサーバーから利用者へのフレーム |
| 外向きの転送（サブリクエスト） | 外向きのプロキシ | インターネットへ送った要求のヘッダーと本文のバイト数。自分たちのホスト名への内部の経路は数えない |
| ログの件数 | スーパーバイザー | 保存の対象にした呼び出しの数 |
| KV の操作と保存 | KV の書き込みのサービス、読み込みの段 | 操作の数。保存は正本の項目の大きさの合計を 1 時間ごとに |
| オブジェクトの操作・保存・転送 | オブジェクトのゲートウェイ | 書き込み系・読み込み系の数、保存（日次）、S3 の API の口からの転送 |
| Durable Objects | 実体のホスト | 要求、GB-s（実体のメモリの割り当て 128MB × 動いていた時間）、行の読み書き、保存 |
| キュー | ブローカー | 操作（書き込み・読み込み・削除を 64KB ごとに 1。本家の数え方に寄せる。細部は queues-and-cron） |

- 受けた転送（利用者からの要求の本文、サブリクエストの応答）は課金しない。
- TLS と TCP の上乗せ（AWS はこれも数える）は課金しない。差は原価に含める（割合は未検証。E11 で実測する）。

### 5.2 束の形と経路

```
UsageBatch {
  batch_id:   "<source_kind>:<source_id>:<boot_id>:<seq>"   // idempotency key
  region:     "ap-northeast-1"
  window:     [start_ms, end_ms)        // 10 seconds, aligned
  records:    [ { account_id, script_id?, resource_id?, metric, quantity (u64), unit } ]
  sent_at_ms: u64
}
```

```
ノードの部品 ──(Unix ドメインソケット)──▶ ノードの使用量の送り手（Rust、ノードに 1 つ）
   10 秒ごとに束を作り、ローカルのディスクの spool に書いてから送る（落ちても失わない）
   ──▶ リージョンの Kinesis Data Streams（usage-<region>）
   ──▶ 東京の集計（ECS。リージョンごとの流れを読む）
         1 トランザクションで：
           INSERT INTO usage_batches(batch_id, …) ON CONFLICT DO NOTHING
           挿入できたら usage_hourly に加算（(account_id, hour_jst, metric, script_id)）
           無料・上限のあるアカウントは usage_daily_counters にも加算
   ──▶ S3（Firehose で生の束を保存。13 か月。監査と再計算）
```

- **重複を捨てる**：送り手は、Kinesis の受け取りの確認が来るまで同じ束を同じ `batch_id` で送り直す。集計は `usage_batches` の主キーで 2 回目を捨てる。
- **遅れて届いた束**：月の締め（翌月 3 日の JST 0 時）までに届いたものは、その月に入れる。締めの後に届いた前の月の束は課金せず、数だけ記録する（利用者に不利にしない）。
- ストレージのサービス（KV、オブジェクト、Durable Objects、キュー）も同じ形の束を同じ流れに送る。

### 5.3 保存の量

- 保存（GB-月）は、1 時間ごとの標本の平均にする：`GB-月 = Σ(1 時間ごとの保存の量[GB]) ÷ その月の時間の数`。
- KV は書き込みのサービスが名前空間ごとの合計を持ち、1 時間ごとに束で送る。オブジェクトは S3 Inventory（日次）とゲートウェイの増減の足し引きで出す（[object-storage.md](object-storage.md) の担当）。

### 5.4 課金しないもの

| 場合 | 理由 |
| --- | --- |
| `outcome` が `internalError`・`evicted`、1202 | 基盤の都合 |
| 1027・1201・1203 で止めた要求 | 関数を呼んでいない |
| 呼び出しの記録が届かなかった呼び出し | 利用者に不利にしない（runtime-and-isolates の 6.3 節） |
| 締めの後に届いた前の月の束 | 同上 |
| 費用の上限を超えた分（8 節の遅れの間） | 上限を約束として守る |

- `exception`・`exceededCpu`・`exceededMemory`・`canceled` は課金する（利用者のコードが資源を使った）。

### 5.5 突き合わせ

- 1 時間ごとに、入口のプロキシが数えた「関数に渡した要求」の数と、呼び出しの記録の数を、アカウントごとに比べる。差が 0.5% を超えたら警報を出す。請求は呼び出しの記録の数を使う。
- 外向きのプロキシのサブリクエストの数と、呼び出しの記録の `subrequests` の合計も同じく比べる。
- 月ごとに、請求した外向きの転送の合計と、AWS の請求（EC2 の外向きの転送と DT-Premium）を比べ、原価の差を出す（capacity と経理へ）。

### 6.1 決め方

- 単価は円で決める。ドルの価格を為替で換算しない（毎月の請求が為替で揺れないように）。

### 6.4 K8（採算）の式

```
最小の関数の 100 万要求の基盤の費用
  = ノードの費用の按分 + 入口のプロキシの費用の按分 + 使用量とログの経路の按分
ノードの費用の按分 = (ノードの 1 時間の費用 ÷ ノードの 1 時間の処理件数) × 100 万
目標（K8）：上の値 ≤ 25 円（要求の単価 50 円の 50%）
```

- 例（未検証）：c7i.24xlarge（[ADR-0050](../decisions/0050-runtime-fleet-instance-types.md)、東京 5.3928 ドル/時）が最小の関数を 1 秒に 3 万件処理するなら、利用率 100% で 100 万要求あたり約 0.050 ドル（約 7.5 円）、設計点の利用率 50% で約 15 円（[capacity.md](capacity.md) の 8 節）。処理件数の実測（capacity、E2・E4）で置き換える。
- 外向きの転送と Global Accelerator の DT-Premium は、別の行で課金するので K8 の式に入れない。アクセラレーターの固定の費用（2 つで 1 か月約 36 ドル）は基盤の費用に入れる。

### 6.5 CPU 時間の単価の計算（2026-09-27、統合の工程）

既定案の 3 円（本家と同じ値）は、原価を下回っていた（[capacity.md](capacity.md) の 8 節）。**PM の確認事項**として、次の式で 7 円にした（[ADR-0040](../decisions/0040-jpy-pricing-invoices-and-spend-controls.md) の注記）。

```
c7i.24xlarge（東京）       = 5.3928 ドル/時、96 vCPU
1 vCPU-ms の原価（利用率 100%）= 5.3928 ÷ 96 ÷ 3,600,000 ≒ 1.56 × 10⁻⁸ ドル
100 万 vCPU-ms（100%）      ≒ 0.0156 ドル ≒ 2.34 円（1 ドル 150 円）
設計点の利用率 50%（ADR-0054） ≒ 4.68 円
× 1.3                      ≒ 6.09 円 → 切り上げて 7 円
```

- 課金の CPU 時間はスレッドの CPU 時計（`CLOCK_THREAD_CPUTIME_ID`。[ADR-0009](../decisions/0009-cpu-and-memory-metering.md)）で、vCPU の時間と同じ単位として扱う。基盤の CPU（1 要求あたり 0.8ms の仮定）は要求の単価で回収する。
- S1 の東京の平常の利用率（約 23%）では原価が約 10.2 円で、7 円でも下回る。国内の 2 リージョンが互いの全量を受ける台数を持つためで、K8 と同じく S2 の利用率で評価する。月ごとの原価と請求の比（5.5 節）で見続ける。
- 月額 800 円と含む量（3,000 万 ms）は変えない。平均の関数（利用者の CPU 2.2ms）の 100 万要求の請求は、50 円 ＋ 2.2 × 7 円 ＝ 65.4 円になる（原価は利用率 50% で約 28 円）。

## 7. 請求

[ADR-0040](../decisions/0040-jpy-pricing-invoices-and-spend-controls.md)。

### 7.1 計算

```
rated_usage(account, hour, metric) = max(0, 数量 − 残りの含む量) × 単価     -- numeric(20,6) の円
月の行の金額 = Σ rated_usage を行ごとに合計し、1 円未満を切り捨て（利用者に有利な側）
小計 = 月額（日割り）＋ Σ 行の金額
課税の対象 = 小計 − 値引き（販促のクレジット、SLA の返金）
消費税 = floor(課税の対象 × 10%)                                         -- 1 つの請求書で 1 回
合計 = 課税の対象 ＋ 消費税
```

- 含む量は、月の初めから時間の順に消費する（どの時間が有料になったかを説明できるように）。
- 「今月の見込み」は 1 時間ごとに更新し、ダッシュボードと API で見せる。
- 月の途中の有料への変更は、月額を日割り（JST の日の単位）にし、変更の日から有料の含む量を日割りで与える。無料への変更は月末に効く。

### 7.2 請求書

- 締め：JST の月末。翌月 3 日（JST）までに確定する（遅れて届く束を 2 日待つ。5.2 節）。
- 形：適格請求書の記載事項（2 節の①〜⑥）を持つ PDF と、管理 API の JSON。宛名は、アカウントの請求先の名称。登録番号は、会社の適格請求書発行事業者の登録の後に入れる（経理の確認待ち）。
- 消費税は 10%。**1 つの請求書につき、税率ごとに 1 回だけ端数を処理する。** 方法は切り捨て（国税庁 Q&A 問 57。2 節）。
- 請求書の番号は `INV-YYYYMM-<連番>`。確定した請求書は変えない。誤りは、赤の請求書（取り消し）と新しい請求書で直す。
- PDF と JSON は、電子の取引の記録として保存する。保存の期間（7 年を既定案とする）と、検索の要件の満たし方は経理の確認待ち（未検証）。
- 海外の利用者（国外の事業者・個人）への消費税の扱い（電気通信利用役務の提供の区分と、内外の判定）は、法務・税務の確認待ち（[intent.md](../intent.md) の L5）。確認までは、請求先の住所が日本のアカウントだけに有料の計画を売る（15 節）。

```
invoices
  account_id, id, number, period (2026-09), status (draft | finalized | paid | overdue | void),
  bill_to_name, bill_to_address, registration_number,
  subtotal_jpy, discounts_jpy, taxable_jpy, tax_rate (0.10), tax_jpy, total_jpy,
  issued_at, due_at, pdf_s3_key, supersedes_invoice_id
invoice_lines
  invoice_id, line_kind (plan_fee | requests | cpu_ms | egress_gb | logs | kv_reads | …),
  quantity (numeric), included_quantity (numeric), unit_price_jpy (numeric(20,6)), amount_jpy (bigint)
```

### 7.3 支払い

| 方法 | 対象 | 流れ |
| --- | --- | --- |
| カード | 全ての有料 | 決済の代行の事業者のトークンだけを持つ（カードの番号を持たない）。請求書の確定のときに引き落とす |
| 銀行振込（請求書払い） | 月の見込みが 10 万円以上で、与信の審査を通ったアカウント | 月末締め・翌月末払い。振込の突き合わせは入金の明細で行う |

- 決済の代行の事業者の選定は E11 で行う。

### 7.4 前払いのクレジット（L5）

| 案 | 中身 | 法令の上の論点 |
| --- | --- | --- |
| A | 前払いのクレジットを売らない。販促のクレジット（無償）だけを配る | 無償で配るものが前払式支払手段に当たらないか（法務の確認待ち） |
| B | 自家型の前払いのクレジットを売る | 基準日の未使用残高が 1,000 万円を超えたら届出と発行保証金。払い戻しの制限 |
| C | 有効期限を短く（6 か月以内）して売る | 適用の除外に当たるか（未検証） |

- **S1 は A にする**（ADR-0040）。後払い（月末締め）で、前払いの必要がない。
- 販促のクレジットは、課税の対象から引く値引きとして扱い、有効期限を 12 か月にする。値引きとしての税の扱いは経理の確認待ち。
- 設計は B・C に移れる形にしておく：クレジットの残高を `credit_grants` と `credit_ledger`（付与・消費・失効の台帳）で持ち、基準日（3 月 31 日・9 月 30 日）の未使用残高を出せるようにする。

## 8. 予算の警告と費用の上限

[ADR-0040](../decisions/0040-jpy-pricing-invoices-and-spend-controls.md)。

### 8.1 予算の警告

- アカウントごとに、円の額の警告を複数作れる。1 時間ごとに、今月の累計と、月末の予測（直近 7 日の平均から）を比べる。
- 累計が額を超えたら 1 回、予測が額を超えそうになったら 1 回、知らせる（メールとダッシュボード）。同じ期間に同じ警告を 2 回出さない。
- 有料に変えたアカウントには、1,000 円の警告を既定で作る（本家の 10 ドルの既定に寄せる。消せる）。
- 警告は知らせるだけで、止めない（本家と同じ）。

### 8.2 費用の上限

- アカウントごとに、月の費用の上限（円、税抜の従量の分）を任意で決められる。**既定は切る。**
- 上限に達したら、集計がアカウントの状態に `spend_capped: true` を書く（4.2 節と同じ経路）。

| 止まるもの | 止まらないもの |
| --- | --- |
| `fetch` の呼び出し（1201）、cron、キューの consumer、アラーム | 保存の課金（データを消さない） |
| バインディングの操作（KV・オブジェクト・Durable Objects・キュー）。関数からも S3 の口からも | 管理 API、ダッシュボード、データの取り出し（S3 の口の読み込みは止める。取り出しは上限を上げてから） |

- キューのメッセージは止まる間も保持する（保持の期限は延ばさない）。
- 上限の 50%・80%・100% で知らせる。100% の知らせには、止めたものと、上限の上げ方を書く。
- 遅れ（約 30 秒）の間の超過は課金しない（5.4 節）。
- 利用者は上限を上げるか外すと、30 秒以内（配信の p99 10 秒）に再開する。
- 上限で止めるのは、利用者のサービスを止めるということ。設定の画面でこれを明示し、既定で有効にしない理由にする。

## 9. 未払いと停止

| 経過 | 動き |
| --- | --- |
| 支払いの失敗 | カードを 1・3・7 日後に再試行。メールで知らせる。アカウントの状態に `payment_failed` を書き、cordon を `c1-free` に下げる（ADR-0011 の信頼を下げる変更。`c0-untrusted` には下げない。`risk_level` が `high` なら `c0-untrusted`。ADR-0011 の注記） |
| 期限から 14 日 | 管理者に、計画を下げる予告を知らせる |
| 期限から 30 日 | 無料の計画の制限に下げる（CPU 10ms、1 日 10 万要求など）。関数は動くが、制限を超える関数は失敗する |
| 期限から 60 日 | アカウントを停止する（関数は 1203、ストレージの操作は拒否）。データは保持する |
| 期限から 90 日 | 削除の予告（30 日前） |
| 期限から 120 日 | データを削除する（security の領域のデータのライフサイクル） |

- 停止と削除の条件は利用規約に書く（法務の確認待ち）。停止の間の保存の課金は続けない案を既定にする（未回収を増やさない）。

## 10. 障害の型

| 障害 | 検知 | 振る舞い |
| --- | --- | --- |
| ノードの送り手が落ちる | 束の届かないノード | spool から再送。spool のディスクが満ちたら古い束から捨て、捨てた数を記録（課金しない側に倒れる） |
| Kinesis の遅れ | `IteratorAge` | 5 分で警報。期間の枠の止めが遅れる（その間の超過は課金しない） |
| 集計の停止 | 取り込みの遅れ | 期間の枠と費用の上限が効かない。15 分で当番。回復後に Kinesis（保持 7 日）から読み直す |
| 二重の計上 | `usage_batches` の主キー | 2 回目を捨てる。重複の数を指標にする |
| 突き合わせの差が 0.5% を超える | 5.5 節 | 当番へ。原因が分かるまで請求の確定を保留できる（手動） |
| 月の締めの誤り | 確定の前の検査（前の月との比、急な増加） | 前の月の 5 倍を超えるアカウントは、確定の前に人が見る |
| 誤った `quota_block` で止めた | 利用者の申し出、枠と実数の比べ | 印を消す変更を優先で書く。止めた時間の月額を返す（SLA の扱い） |
| 決済の代行の障害 | 引き落としの失敗の急増 | 再試行を遅らせる。支払いの失敗として扱わない（cordon を下げない） |

## 11. セキュリティ

| 脅威 | 対策 |
| --- | --- |
| 使用量の改ざん（利用者のコードから数を減らす） | 数は isolate の外の部品が数える。束はノードの部品から mTLS で送り、`source_id` はノードの証明書と照合する |
| 他のアカウントへの計上 | 束の `account_id` は、ノードが設定の写しから引いた値。集計は、`script_id` と `account_id` の組が正本と合うかを 1 時間ごとに標本で確かめる |
| 請求書・支払いの情報の漏れ | 請求の表は RLS。カードの番号を持たない。請求書の PDF は署名付きの URL（5 分）で渡す |
| 費用の上限・予算の設定の乗っ取り | `billing:edit` の権限と、ステップアップの MFA（[dashboard-and-api.md](dashboard-and-api.md) の 5 節） |
| 無料の枠の使い回し（アカウントを大量に作る） | abuse-and-trust-safety の新しいアカウントのリスクの点数（[abuse-and-trust-safety.md](abuse-and-trust-safety.md) の 8 節） |
| 盗んだカードで有料にし、大量に使う | 与信のない新しい有料のアカウントに、月の見込みの一時の上限（10 万円）を置き、超えたら人が見る（abuse-and-trust-safety と合わせる） |

## 12. テスト

| 種類 | 対象 | 確かめること |
| --- | --- | --- |
| 性質ベース | 束の重複 | 任意の束の列と、任意の再送・並べ替えで、`usage_hourly` の合計が、重複を除いた束の合計と等しい |
| 性質ベース | 請求の計算 | 任意の使用量の列で、含む量の消費が時間の順で、行の金額の合計が単価×超過量の合計の切り捨てと等しい。消費税が 1 回だけの切り捨て |
| 表駆動 | 課金しないもの | 5.4 節の各場合 |
| 表駆動 | 計画の制限 | 3 節の各値の境目（ちょうどで通り、1 つ超えで失敗） |
| 表駆動 | 請求書 | 適格請求書の記載事項がそろう。赤の請求書と新しい請求書 |
| 結合 | 期間の枠 | 無料の 1 日 10 万を超えて 30 秒以内に 1027。JST の 0 時に戻る |
| 結合 | 費用の上限 | 上限で 1201。上げると 30 秒以内に再開。遅れの間の超過が請求に入らない |
| 結合 | 突き合わせ | 呼び出しの記録を故意に落とすと、差の警報が出て、請求は少ない側 |
| 負荷 | 集計 | S1 のピーク（5 万件/秒）の 10 倍の束の量で、集計の遅れが 60 秒以内 |
| 本番の探り | 計上 | 探りのアカウントで、決まった数の要求と転送を毎時送り、`usage_hourly` の値が合う |

テスト名には要件 ID（開発リポジトリの `REQ-BILLING-*`・`PROP-BILLING-*`）を含める。

## 15. 未解決の問い

- 1 ドルの換算の仮定（150 円）と、各行の単価の確定。原価の実測。
- オブジェクトストレージの大阪への複製の有無（原価が約 2 倍変わる）。
- 本家の日ごとの枠の戻る時刻。この基盤は JST の 0 時でよいか。
- 無料の外向きの転送の枠（1 日 500MB）は、無料の利用に足り、不正な利用の費用を抑えられるか。
- 海外の利用者への消費税の扱いと、有料の計画を海外に売る時期（L5）。
- 無償の販促のクレジットの法令の上の扱い。前払いのクレジットを売るか（L5）。
- 電子の請求書の保存の期間と要件。
- 費用の上限で止めるものの範囲（S3 の口の読み込みを止めるか）。
- 専用の契約の料金の形（最低の月額と含む量）。

### 決定

2026-09-27 の既定案。

- 換算は 150 円を仮定に使い、単価は 6.3 節の表で始める。E11 の着手の前に、capacity の原価の実測で各行を 1.3 倍の規則に照らして直し、PM が承認する。
- オブジェクトの単価は複製ありの原価で決める。object-storage が複製なしを選んだら、単価を下げる。
- 日ごとの枠は JST の 0 時に戻す（日本の利用者に分かりやすい）。
- 無料の転送の枠は 1 日 500MB で始め、無料のアカウントの分布を見て S2 の前に見直す。
- L5 の確認までは、請求先が日本のアカウントだけに有料の計画を売る。無料の計画は海外にも開く。
- 前払いのクレジットは売らない（案 A）。販促のクレジットの扱いは法務の確認を E11 の spec の承認の条件にする。
- 請求書の保存は 7 年を既定にし、経理の確認で直す。
- 費用の上限は、S3 の口の読み込みも止める（課金の対象だから）。上限を上げれば、すぐ取り出せる。
- 専用の契約は S1 で個別の見積もり。S2 で形を決める。

## 16. quality.md・runbooks・data-model に載せるもの

**quality.md**

- リスク：二重の計上・取りこぼしで請求が誤る。束の重複の性質ベーステスト、突き合わせ、本番の探り。
- リスク：原価割れ（特に転送と KV の書き込み）。月ごとの原価と請求の比べ、K8 の計測。
- リスク：期間の枠・費用の上限の止めの遅れ。結合テストと、止めまでの時間の SLI（p99 30 秒）。
- リスク：誤った停止（`quota_block` の誤り）。印の `until` での自然な解除と、解除の runbook。
- 本番での検証：集計の遅れ、突き合わせの差、月の締めの前の急な増加の検査。

**runbooks**

- `usage-pipeline-lag`：Kinesis・集計の遅れ。読み直しと、期間の枠の止めの影響の確認。
- `usage-reconciliation-mismatch`：突き合わせの差の調査。請求の確定の保留の判断。
- `invoice-close`：月の締めの手順（遅れた束の確認、急な増加の人の確認、確定、PDF の発行）。
- `invoice-correction`：赤の請求書と新しい請求書の発行。
- `quota-block-release`：誤った `quota_block`・`spend_capped` の解除と、返金。
- `payment-failure-wave`：決済の代行の障害での引き落としの失敗の急増。
- SLI の追加の依頼（Ops へ）：束の遅れ（ノードの窓の終わりから集計まで p99）、期間の枠の止めまでの時間、突き合わせの差、spool で捨てた束の数、重複の数。
