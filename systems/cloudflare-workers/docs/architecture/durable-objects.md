# Durable Objects: Cloudflare Workers

名前ごとに 1 つだけの実体（アクター）と、強い整合の SQLite の保存（本家の Durable Objects に相当するもの）の設計。配置と場所のヒント、リースとフェンシング、入力と出力のゲート、AZ をまたぐ同期の複製、S3 への WAL の転送と時点の復旧（PITR）、アラーム、WebSocket の休止、RPC の API、制限、障害の移動、データの所在を決める。

| 関連 | 決定 |
| --- | --- |
| [ADR-0005](../decisions/0005-storage-consistency.md) | 名前ごとに同時に 1 つの実体。書き込みは別の AZ の複製の過半数で確定。確定の前に結果を外へ出さない。S1 はリージョンを自動で移さない |
| [ADR-0011](../decisions/0011-cordon-tiers-and-placement.md) | cordon（信頼の段階）ごとにランタイムのプロセスを分ける |
| [ADR-0029](../decisions/0029-do-placement-and-directory.md) | 場所は作成時に決めて変えない。名前の ID は東京の台帳で調停し、一意の ID は場所を ID に埋め込む |
| [ADR-0030](../decisions/0030-do-leases-and-fencing.md) | 持ち主はホストのリースと実体ごとのエポックで決める。複製の側でエポックを検査し、古い持ち主の確定を拒む |
| [ADR-0031](../decisions/0031-do-sqlite-replication-and-pitr.md) | SQLite の WAL を持ち主と 2 台の複製の 3 台のうち 2 台（2 つの AZ）で確定し、10 秒か 16 MiB ごとに S3 へ置いて 30 日の PITR を持つ |
| [ADR-0032](../decisions/0032-do-alarms-hibernation-and-rpc.md) | WebSocket はランタイムの外の接続の保持役で持ち、休止を支える。アラームはリージョンの索引で起こす。呼び出しは RPC を基本にする |

ランタイムの isolate とプロセスの入れ替えは [runtime-and-isolates.md](runtime-and-isolates.md)、cordon とサンドボックスは [sandbox-and-security.md](sandbox-and-security.md)、WebSocket の API は [web-apis-and-compat.md](web-apis-and-compat.md) にある。キューは Durable Objects の上に作らない（[queues-and-cron.md](queues-and-cron.md)）。

## 3. 原則

- **一意性は可用性より優先する**（ADR-0005）。1 つの名前に 2 つの実体が同時に確定する可能性があるなら、その実体を止める。
- **正しさは時計に頼らない。** 2 つの持ち主の同時の確定は、複製の側のエポックの検査で防ぐ。リースの時間は、可用性（早い引き継ぎ）と読み込みの古さの防止にだけ使う。
- **出力は確定の後。** 書き込みの結果に依存する応答・外への通信は、2 つの AZ で確定するまで出さない。
- **読み込みは手元の SQLite から。** 同期の API（`sql.exec`、`storage.kv`）は、ネットワークを越えない。
- **実体の場所は変えない。** 作成時に決め、S1 ではリージョンを自動で移さない。リージョンの中のホストは変わりうる。
- **要求の処理の経路で制御プレーンを呼ばない**（ADR-0004）。名前空間（クラス）の定義は、設定の配信で届く。

## 4. ID と配置

[ADR-0029](../decisions/0029-do-placement-and-directory.md)。

### 4.1 ID の形

ID は 32 バイト（16 進で 64 文字。本家と同じ長さ）。

```
一意の ID（newUniqueId）
  [0]      版 = 0x01
  [1]      管轄（0 = なし、1 = jp。S2 で eu など）
  [2]      リージョンの番号（作成時に決めたリージョン）
  [3..15]  乱数 13 バイト
  [16..31] タグ = HMAC-SHA256(namespace_key, bytes[0..15]) の先頭 16 バイト

名前の ID（idFromName(name)）
  [0]      版 = 0x02
  [1]      管轄
  [2]      0（リージョンは台帳で引く）
  [3..15]  HMAC-SHA256(namespace_key, name) の先頭 13 バイト
  [16..31] タグ（同上）
```

- `namespace_key` は名前空間（クラス）ごとの秘密の鍵。設定の配信で、KMS で暗号化したまま届き、DO のルーターとホストがメモリに持つ。
- `idFromString()` はタグを検証し、別の名前空間の ID を拒む。利用者が ID を偽っても、他の名前空間の実体に届かない。
- 一意の ID はリージョンを ID に埋め込むので、台帳を引かずに経路が決まる。名前の ID は、最初の要求まで場所が決まらないので台帳を使う。

### 4.2 名前の台帳

```
表 do_directory（東京の DynamoDB。グローバルテーブルで S1 の全リージョンへ読み込み用に複製）
  pk             Binary  = object_id（32B）
  namespace_id   String
  account_id     String
  region         String  （作成時に決めたリージョン）
  jurisdiction   String
  region_epoch   Number  （手動のリージョンの退避で増える。通常は 1）
  created_at     Number
```

- 作成は東京への条件付きの `PutItem`（`attribute_not_exists(pk)`）。先に確定した方が勝つ。負けた側は勝った側の値を読む。
- 引くのは、まずリージョンの複製（結果整合）。なければ東京へ強い読み込み。それでもなければ作成する。
- 項目は作成の後に変わらない（手動の退避を除く）ので、引いた値をルーターが無期限にキャッシュしてよい。`region_epoch` が上がったら、10 節の手順で無効にする。
- 東京が止まっている間は、新しい名前の実体を作れない（既存の名前は、リージョンの複製で引ける）。

### 4.3 場所の決め方

作成のリージョンは、次の順で決める。

1. 管轄が `jp` なら、東京か大阪（場所のヒントが `apac-ne` 以外でも日本の中に限る）。
2. 場所のヒントがあれば、下の表で対応するリージョン。
3. なければ、最初の要求を出した関数が動いているリージョン。

| 本家のヒント | S1 のリージョン |
| --- | --- |
| `apac-ne` | 東京 |
| `apac`・`apac-se`・`oc` | シンガポール |
| `wnam`・`enam`・`sam` | オレゴン |
| `weur`・`eeur`・`afr`・`me` | フランクフルト |

- ヒントは最善の努力（本家と同じ）。リージョンの容量が足りないときは、同じ管轄の中の最も近いリージョンに置き、指標に出す。
- S1 の海外のリージョンの候補は ADR-0003 のもの。確定したら、この表を更新する。

### 4.4 要求の経路

```
関数（リージョン X）
  │ env.NS.get(id).method(args)  ─ RPC（Cap'n Proto）
  ▼
外向きのプロキシ：isolate の鍵 → バインディング → namespace_id。ID のタグを検証
  ▼
DO のルーター（リージョン X）
  │ リージョン R を決める：一意の ID は ID から、名前の ID は台帳（キャッシュ）
  │ R ≠ X なら、リージョンの間の mTLS の経路で R のルーターへ
  ▼
DO のルーター（リージョン R）
  │ 割り当ての表（キャッシュ）から持ち主のホストとエポックを引く
  │ 割り当てがなければ、配置のサービスに割り当てを求める（5.3 節）
  ▼
DO のホスト：自分が有効なリースと、そのエポックの割り当てを持つかを確かめる
  │ 持たなければ NotOwner(epoch) を返す → ルーターは表を引き直して再送（1 回）
  ▼
ランタイム（DO の cordon のプロセス）の中の実体
```

- ホストは、リージョンごとの専用の群（DO のホスト）。ランタイムは関数と同じ workerd を元にしたもので、同じ cordon の規則（ADR-0011）でプロセスを分ける。
- 同じスタブからの呼び出しは、送った順に届く（workerd の RPC の順序の保証に従う）。
- 段階的なデプロイの間も、1 つの名前空間の実体は同時に 1 つの版だけで動く（本家と同じ。[deployment-and-config-distribution.md](deployment-and-config-distribution.md)）。版が変わると、ホストは実体を作り直す（8.2 節）。クラスの変更（名前の変更・削除）を含む版への切り替えと戻しの規則は E9 で決める（16 節）。

## 5. 持ち主の決定：リースとフェンシング

[ADR-0030](../decisions/0030-do-leases-and-fencing.md)。

### 5.1 2 つの表

```
表 do_host_leases（リージョンごとの DynamoDB）
  pk            host_id
  az            String
  lease_seq     Number  （ホストが 2 秒ごとに条件付きで 1 増やす）
  state         "active" | "draining" | "dead"

表 do_assignments（リージョンごとの DynamoDB）
  pk            object_id
  host_id       String
  epoch         Number   （持ち主が変わるたびに 1 増える。単調）
  replicas      List     [{node_id, az}, {node_id, az}]  （2 台の複製。持ち主と別の AZ）
  config_seq    Number   （複製の組の変更の番号）
  state         "active" | "recovering" | "unavailable"
```

### 5.2 時間の規則（S1 の既定）

| 値 | 意味 |
| --- | --- |
| 2 秒 | ホストがリースを更新する間隔（`lease_seq` を条件付きで増やす） |
| 7 秒 | ホストが、最後に成功した更新の**送信**の時刻から、自分の単調な時計で 7 秒たっても次の更新が成功しなければ、自ら止まる（全実体の新しい要求を断り、出力を出さない） |
| 10 秒 | 配置のサービスが、自分の単調な時計で 10 秒 `lease_seq` の変化を見なければ、そのホストを `dead` にする |
| 3 秒 | 上の 2 つの差。2 台の時計の進みの速さの違い（同期のずれではない）が 30% を超えない限り、古い持ち主は新しい持ち主より先に止まる |

- 時計の同期（壁の時計の一致）は仮定しない。仮定するのは、単調な時計の進む速さの違いが小さいことだけ。
- この時間の規則は、**読み込みの古さ**を防ぐためのもの（古い持ち主が、分断の中で古い手元の状態から応答し続けないように）。書き込みの二重の確定は、5.4 節のエポックの検査で、時計によらず防ぐ。

### 5.3 割り当てと引き継ぎ

```
配置のサービス（リージョンごと、3 台。自身の主は DynamoDB の条件付きの書き込みで決める）

新しく割り当てる / dead のホストの実体を引き継ぐ：
  1) ホスト H' を選ぶ（容量、cordon、AZ。複製の 2 台と別の AZ を優先）
  2) do_assignments を条件付きで更新：epoch = e+1, host_id = H'（条件：epoch = e）
  3) H' へ Activate(object_id, e+1) を送る

H' の起動（Activate）：
  4) 複製の組 {旧持ち主の手元, r1, r2} のうち、生きている 2 台（旧持ち主が死んでいれば r1 と r2）へ
     Fence(object_id, e+1) を送る。各複製は promised_epoch = max(promised_epoch, e+1) を
     ディスクに書いてから、自分の最後の LSN とエポックを返す
     → 2 台から返らなければ state = unavailable（待つ。可用性より一意性）
  5) 返った中で最も進んだログ（エポック、LSN の順で比べる）を正とする
  6) SQLite を戻す：手元にあれば手元、なければ S3 の最新のスナップショット＋S3 の WAL＋複製のログの末尾
  7) 最も進んだログの末尾まで適用し、エポック e+1 の最初の記録（持ち主の交代）を 2 つの AZ で確定する
  8) 実体を動かし始める（state = active）
```

- ホストの計画的な停止（`draining`）では、ホストが自ら実体を手放し（処理中の要求の完了を最大 30 秒待つ）、配置のサービスがすぐ引き継ぐ。リースの期限を待たない。
- 割り当ては粘り強くする（sticky）。無活動で実体をメモリから外しても、割り当てと手元の SQLite は残し、次の要求で同じホストが使う。手元の SQLite の置き場所は、ホストの gp3 のキャッシュ（容量で古いものから消す。DO のホストの m7i はローカルの NVMe を持たない。[ADR-0050](../decisions/0050-runtime-fleet-instance-types.md)）。

### 5.4 フェンシング（正しさの要）

- 複製は、実体ごとに `promised_epoch` を持つ。**`promised_epoch` より小さいエポックの記録を拒む。**
- 確定には、2 つの AZ にまたがる 2 台の保存が要る（7.2 節）。新しい持ち主は、起動のときに 2 台から約束（Fence）を得る。3 台のうち 2 台の集まりは必ず重なるので、古い持ち主が新しい約束の後に確定を得ることはできない。
- したがって、ネットワークの分断・長い一時停止（GC、SIGSTOP）・時計のずれの任意の組み合わせで、1 つのエポックの中で確定できる持ち主は 1 つだけになる。これは ADR-0005 の「同時に 2 つの実体が書き込みを確定しない」そのものである。
- 古い持ち主が確定できなかった書き込みの結果は、出力のゲートで止まっているので、外へは出ない（6 節）。その実体は、書き込みの失敗として作り直され、ホストが `NotOwner` を知って捨てる。

## 6. 入力と出力のゲート

- workerd の実装（入力のゲート、出力のゲート、`await` を挟まない書き込みのまとめ）をそのまま使う。本家と同じ意味にする。
- 変えるのは「確定」の意味だけ。上流の手元の SQLite では手元のディスクへの書き込みで確定するが、この設計では 7.2 節の 2 つの AZ での確定を待つ。出力のゲートは、この確定の約束（promise）が解決するまで閉じる。
- `put(..., {allowUnconfirmed: true})` は、出力のゲートを待たない（本家と同じ）。複製はする。確定に失敗したら、実体を作り直す。
- 確定の失敗（2 つの AZ に届かない、エポックで拒否された）のときは、閉じていた出力を捨ててエラーに替え、実体を最初から作り直す（本家と同じ）。
- 同期の SQL（`sql.exec`）の読み込みは、手元の SQLite から返す。書き込みは手元に適用し、WAL の記録を複製へ送る。確定の前の手元の状態は、同じ実体の後続の処理から見える（本家と同じ）。外へ出るのは確定の後だけ。

## 7. SQLite の保存と複製

[ADR-0031](../decisions/0031-do-sqlite-replication-and-pitr.md)。

### 7.1 取り方

- 自前の SQLite の VFS（workerd への自前のパッチ。分類 `multitenant`）で、WAL のフレームを取る。本家の Storage Relay Service と同じ考え方。
- 1 回の確定の単位は、SQLite のトランザクション（自動のまとめを含む）。記録は `{object_id, epoch, lsn, commit_time_ms, frames[], checksum}`。
- LSN は実体ごとに単調に増える 64 ビットの番号。

### 7.2 確定の規則

```
持ち主のホスト（AZ-a）                 複製 r1（AZ-b）        複製 r2（AZ-c）
  │ 手元の WAL に書く（fsync）  ─────┐
  │ 記録を r1・r2 へ並列に送る ───────┼──▶ epoch を検査          epoch を検査
  │                                   │     ログに追記（fsync）  ログに追記（fsync）
  │                                   │◀── ack(lsn)            ◀── ack(lsn)
  │ 確定：3 台のうち 2 台が保存し、その 2 台が 2 つの異なる AZ にある
  ▼
出力のゲートを開く
```

- 通常は「持ち主の手元＋最初に返った複製 1 台」で確定する。AZ の間の往復（同じリージョンで 1〜2ms の見込み。未検証。E9 の `do-commit-and-output-gate` で測る）と fsync の時間が、確定の遅延になる。
- 持ち主と複製 1 台が同じ AZ にいる場合（AZ の障害の後の引き継ぎで起こる）は、別の AZ の複製の保存を待つ。
- 複製は、リージョンの各 AZ に置くログのノードの群（ローカルの NVMe を持つ i4i.2xlarge。ADR-0050）。多数の実体のログを 1 台で持ち、グループでの fsync でまとめる。
- 複製の 1 台が落ちたら、持ち主と残りの 1 台（別の AZ）で確定を続ける。配置のサービスが新しい複製を選び、S3 と残りの複製から追いつかせてから、組の変更（1 台ずつ）をログの記録として確定する（`config_seq` を増やす）。
- 持ち主と複製の 1 台が同時に落ちたら、残りの 1 台だけでは Fence の 2 台を得られない。その実体は、どちらかが戻るまで `unavailable`（一意性を優先）。

### 7.3 S3 への転送

- 持ち主が、10 秒か 16 MiB の早い方ごとに、確定済みの記録をまとめて 1 つのオブジェクトとして S3 に置く（本家と同じ値）。
  - `s3://<brand>-do-{region}/{jurisdiction}/{namespace_id}/{object_id}/wal/{timeline:04}-{start_lsn:016x}-{end_lsn:016x}.zst`
- 置けたら、`archived_lsn` を複製に知らせ、複製はそこまでのログを捨ててよい。置けない間（S3 の障害）は、複製がログを持ち続ける。ログのノードのディスクの使用率を監視する。
- 持ち主が置く前に落ちたら、新しい持ち主が、複製のログから置く。
- **スナップショット**：最新のスナップショットの後のログの合計が、DB の大きさを超えたら、SQLite のバックアップの API で一貫した写しを作り、`snap/{timeline:04}-{lsn:016x}.sqlite.zst` に置く。保存量を DB の約 2 倍に抑える（本家と同じ）。
- 保存時の暗号化は SSE-S3。S3 のバケットはリージョンごとで、リージョンの外へは 10.3 節の DR の写しだけが出る。

### 7.4 PITR

- **ブックマーク**は `{timeline, lsn}` を、実体ごとの HMAC で認証した不透明な文字列。別の実体では使えない。
- `getCurrentBookmark()`：確定済みの最新の LSN。
- `getBookmarkForTime(ts)`：`commit_time_ms <= ts` の最後の確定の LSN。30 日より前は例外。
- `onNextSessionRestoreBookmark(bm)`：次に実体が作り直されたとき（`ctx.abort()`、デプロイ、引き継ぎ）に、その時点へ戻す。戻す前の状態のブックマークを返す（戻したことも戻せる）。
- 戻す手順：`bm.lsn` 以前の最新のスナップショットを取り、WAL を `bm.lsn` まで適用し、**新しい timeline** として続ける（PostgreSQL の timeline と同じ考え方）。古い timeline の WAL は 30 日残す。
- 保持：30 日。掃除のジョブが、30 日より古い WAL を消す。ただし、30 日前の時点へ戻すのに要るスナップショット（30 日前より前の最新のもの）と、その後の WAL は残す。
- `deleteAll()`：手元の SQLite を空にする確定の記録を書く。過去の WAL とスナップショットは、30 日で消える（それまでは PITR で戻せる）。本家の PITR も過去 30 日の任意の点へ戻せ、SQLite の保存の `deleteAll()` は全部か無かの操作とされる。`deleteAll()` の前へ戻せるとは明記されていない（[SQLite storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)、2026-09-27 に確認）。名前空間の削除のときのデータの消去は security の領域で決める。

## 8. アラーム、WebSocket の休止、RPC

[ADR-0032](../decisions/0032-do-alarms-hibernation-and-rpc.md)。

### 8.1 アラーム

- 正本は、実体の SQLite の中のアラームの時刻（workerd の保存の中のメタデータ）。確定の規則は他の書き込みと同じ。
- 実体がメモリにいない間も起こすため、リージョンごとの索引を持つ。

```
表 do_alarms（リージョンごとの DynamoDB）
  pk   = "{shard:03}"                 -- xxhash(object_id) mod 256
  sk   = "{due_ms:013}#{object_id}"
  namespace_id, account_id
```

- `setAlarm(t)`：先に索引へ `(t, object_id)` を足し（冪等）、その後にアラームの時刻を SQLite に書いて確定する。索引への書き込みが確定より先なので、確定したアラームは必ず索引にある。確定しなかった場合の索引の項目は、起こしたときに空振りする。
- `deleteAlarm()`・時刻の変更：SQLite の確定を先にし、古い索引の項目は後で消す（残っても空振りするだけ）。
- **起こす役**：リージョンの中の 256 のシャードを、アラームのスケジューラー（3 台以上）がシャードごとのリースで分担し、1 秒ごとに期限の来た項目を読み、ルーター経由で実体に「アラームの時刻」を届ける。
- 実体は、SQLite のアラームの時刻が今以前のときだけ `alarm()` を動かす（空振りを除く）。入力のゲートの規則で、他のイベントと同時には動かない。
- 実体がメモリにいて、手元の時計でアラームの時刻が来たら、ホストが先に動かす。後から届いたスケジューラーの起こしは空振りになる。
- 成功したら、アラームを消す確定をしてから、索引の項目を消す。例外なら、2 秒から倍にして最大 6 回まで再試行する（本家と同じ）。`alarmInfo.retryCount`・`isRetry` を渡す。
- 保証は少なくとも 1 回（本家と同じ）。引き継ぎの途中で、同じアラームが 2 回動くことがある。

### 8.2 WebSocket の休止

- 利用者の WebSocket は、利用者に近いリージョンの入口のプロキシで終端し、内部のストリームで実体のホストへ届く。
- 実体のホストでは、**接続の保持役**（スーパーバイザーの Rust の部品。ランタイムのプロセスの外）が接続を持つ。実体が `acceptWebSocket(ws, tags)` で受けた接続は、保持役が持ち続ける。
  - タグ、`serializeAttachment()` の値（16,384 バイトまで）、自動の応答の組（`setWebSocketAutoResponse`）を、保持役が持つ。
  - ping・pong と自動の応答は、実体を起こさずに保持役が返す。
  - メッセージが来たら、実体を（必要なら作り直して）起こし、`webSocketMessage()` を呼ぶ。
- 休止の条件（処理中の要求・外への接続・`setTimeout` がない）を満たして 10 秒たったら、実体をメモリから外す（本家と同じ）。休止中の時間は課金しない。
- **ランタイムのプロセスの毎日の入れ替え**（[sandbox-and-security.md](sandbox-and-security.md) の 6.4 節）では、保持役がプロセスの外にいるので、休止できる接続は切れない。休止できない接続（`accept()` で受けたもの）は、30 秒の猶予の後に切る。
- **コードのデプロイ**では、全実体を作り直し、全 WebSocket を切る（本家と同じ）。
- **持ち主のホストの障害・引き継ぎ**では、接続は切れる（コード 1012。利用者のクライアントは再接続する）。
- 休止できない実体は、70〜140 秒の無活動でメモリから外す（本家と同じ）。

### 8.3 RPC と `fetch`

- 互換の日付 2024-04-03 以降は、クラスの公開のメソッドを RPC で呼べる（本家と同じ）。それより前の日付と、`stub.fetch(request)` も受ける。
- ルーターとホストの間、リージョンの間は、Cap'n Proto の RPC を mTLS で運ぶ。公開の workerd の RPC を、機械をまたいで運べるかは未検証（E9 の `do-storage-poc` で確かめる）。
- スタブの作り方：`idFromName`、`newUniqueId({jurisdiction})`、`idFromString`、`get(id, {locationHint})`、`getByName(name)`。
- エラー：
  - `.retryable = true`：経路の障害、持ち主の交代、確定の失敗で作り直したとき。利用者の処理が冪等なら再試行してよい。
  - `.overloaded = true`：実体の待ちの列が 1,000 件を超えたとき、または最も古い待ちが 30 秒を超えたとき（仮）。再試行しない。
  - `.remote = true`：利用者のコードが投げた例外。

## 10. 障害と移動

### 10.1 障害ごとの振る舞い

| 障害 | 起きること | 回復までの見込み |
| --- | --- | --- |
| 持ち主のホストの停止 | 10 秒でリースが切れ、配置のサービスが別のホストに割り当てる。新しい持ち主が Fence と復元をして再開する | 検知 10 秒＋復元。手元にない DB は S3 から取る（100 MiB で数秒、10 GiB で数分の見込み。未検証。E9 の `do-wal-archive` の復元の試験で測る） |
| 持ち主のホストの一時停止（長い GC、SIGSTOP） | 7 秒で自ら止まる。戻ったとき、エポックで拒否され、実体を捨てる | 上と同じ |
| 持ち主とリースの表の分断（複製とはつながる） | 自ら止まる。新しい持ち主の Fence の後は、古い持ち主の確定は拒否される | 上と同じ |
| 複製 1 台の停止 | 持ち主と残りの 1 台で確定を続ける。新しい複製を足す | 利用者への影響なし（確定の遅延が少し増えうる） |
| 持ち主と複製 1 台の同時の停止 | Fence の 2 台が得られない。`unavailable` | どちらかが戻るまで。一意性を優先する |
| 1 つの AZ の喪失 | その AZ の持ち主の実体は引き継がれる。その AZ の複製は入れ替える | NFR-010（RPO 0、RTO 5 分）。多数の実体の同時の復元で S3 と容量が混むので、次の要求が来た実体から復元する（遅延の少ない順ではなく需要の順） |
| S3 の障害 | WAL を置けない。複製がログを持ち続ける。確定は続く | ログのノードのディスクが 70% を超えたら警報、90% で新しい書き込みを 503（確定できないより止める） |
| リージョンの配置のサービス・DynamoDB の障害 | 新しい割り当て・引き継ぎができない。割り当て済みで有効なリースのホストの実体は続く | リースの更新もできないので、7 秒で全ホストが止まる。DynamoDB の障害はリージョンの DO の全停止になる（16 節の問い） |
| 東京の DynamoDB（名前の台帳）の障害 | 新しい名前の実体を作れない。既存の名前は各リージョンの複製で引ける | 東京の回復まで |
| リージョン全体の障害 | そのリージョンの実体は使えない。S1 は自動で移さない | 10.2 節の手動の退避 |

### 10.2 リージョンの手動の退避

runbooks の `do-region-evacuate`。S1 で自動にしない理由は ADR-0005（データの所在と、複製の遅れ）。

1. 古いリージョンの DO のホストを止める。届かないときは、古いリージョンのホストの IAM の権限（S3・DynamoDB）を外し、リースの更新をできなくする。**古いリージョンが分断されているだけで生きている場合、ここで止められないと二重の実体が生まれる。止めたことを確かめられないときは、退避しない。**
2. 退避先を選ぶ（管轄の中。`jp` は東京と大阪の間だけ）。
3. 名前の台帳の `region` と `region_epoch` を更新する（手動の操作。2 人の承認）。一意の ID は ID にリージョンを持つので、ルーターの「リージョンの読み替えの表」（設定の配信で届く）に古いリージョン → 新しいリージョンを載せる。
4. 退避先で、DR の写し（10.3 節）から実体ごとに復元する（次の要求が来た実体から）。
5. RPO は、S3 に置く前の WAL（最大 10 秒）＋ CRR の遅れ。NFR-010 の RPO 1 分は保証できない（16 節）。

### 10.3 DR の写し

- WAL とスナップショットの S3 のバケットを、別のリージョンへ S3 CRR で写す。東京 ↔ 大阪。海外のリージョン（管轄なし）は東京へ。
- 管轄 `jp` の実体の写しは、日本の中（東京・大阪）だけに置く。

## 11. データの所在

- 管轄 `jp` の名前空間・ID の実体は、実行（ホスト）、保存（SQLite、複製、S3）、DR の写しをすべて東京と大阪に置く。ほかのリージョンの関数から呼べるが、実体は日本から出ない（本家の管轄と同じ考え方）。
- ID、名前空間、アカウント、要求の数・時間の計量は、課金と調査のため管轄の外（東京の制御プレーン）にも残る。本家も ID を管轄の外に残すとしている。`jp` では、そもそも制御プレーンが東京にある。
- 管轄のない実体は、4.3 節の規則で置く。日本の利用者の個人情報を扱う利用者には、`jp` を勧める。法令の上の扱い（外国にある第三者への提供）は法務の L3 の確認待ちで、E9 の配置の spec はそれまで承認しない（intent）。
- S2 で `eu` を足す（EU の中に 2 つ目のリージョンが要る）。

## 12. セキュリティ（テナントの分離）

- 実体のコードは、関数と同じ cordon の規則でプロセスを分ける（ADR-0011）。1 つの実体は 1 つの isolate で、別のアカウントの実体と isolate を共有しない。
- ID はタグで名前空間に結びつく。外向きのプロキシとルーターは、isolate の鍵から許された名前空間のバインディングだけを通し、ID のタグを検証する。
- 複製とログのノードは、記録の `object_id` と `namespace_id` を持ち、持ち主のホストの mTLS の証明書（ホストの ID）と `do_assignments` の組の一致を確かめる。割り当てのない実体の記録を拒む。
- 手元の SQLite のファイルは、ホストの gp3 に実体ごとに置き、ランタイムのプロセスには VFS を通してだけ見せる（ファイルシステムの系のシステムコールの禁止を崩さない。[sandbox-and-security.md](sandbox-and-security.md)）。
- S3 の WAL とスナップショットは、ホストとログのノードのロールだけが書ける。ホストのロールは、自分のリージョンのバケットだけに届く。アカウントごとの暗号化の鍵は 16 節の問い。
- PITR のブックマークは HMAC で実体に結びつき、別の実体の過去の状態を読む手段にならない。
- WebSocket の添付とタグは利用者のデータなので、ログに出さない。

## 13. テスト

### 13.1 性質ベーステスト

| 対象 | 性質 |
| --- | --- |
| 確定の規則 | 任意の複製の応答の順・欠け・遅れで、確定と判定したとき、2 つの異なる AZ の 2 台に保存がある |
| フェンシング | 任意の Fence と追記の交互の順で、複製は `promised_epoch` より小さいエポックの追記を受けない |
| 復元 | 任意の書き込みの列と任意の切れ目（スナップショット、WAL のまとめ）で、スナップショット＋WAL の適用の結果が、切れ目なしに適用した結果と一致する |
| PITR | 任意の書き込みの列と任意の時刻で、`getBookmarkForTime` への復元の結果が、その時刻の直前の確定の状態と一致する |
| アラームの索引 | 任意の `setAlarm`・`deleteAlarm`・確定の失敗の列で、確定したアラームは必ず索引にある |

### 13.2 Jepsen の形の試験

ADR-0005 の E9 の受け入れ。専用の検証の環境（1 リージョン、3 AZ に見立てた 3 つのネットワークの区画、ホスト 5 台、ログのノード 6 台）で行う。

| 項目 | 内容 |
| --- | --- |
| ワークロード | (a) list-append：RPC のメソッドが SQL のトランザクションで複数のリストに追記し、読む（Elle で厳密な直列化可能性を検査する。実体ごと）。(b) 登録簿：1 つの値の読み書きと比較と交換（Knossos で線形化可能性）。(c) 出力のゲート：書き込みの後に、外の観測者へ `fetch` で LSN を送る |
| 障害 | 持ち主のホストの SIGKILL、SIGSTOP（15 秒。リースより長い）と再開、持ち主と複製の分断、持ち主とリースの表だけの分断、ルーターとホストの分断、1 つの AZ の孤立、複製のディスクの fsync のエラーと満杯、時計の跳び（`libfaketime`）と進みの速さの違い、S3 の障害、DynamoDB のスロットリング、障害の最中のデプロイ（全実体の作り直し） |
| 検査 | Elle：G0・G1a・G1b・G1c・G-single・G2 が 0 件。確定を返した書き込みの喪失が 0 件。Knossos：線形化可能性の違反が 0 件。計装のログから「1 つのエポックで確定した持ち主が 2 つ」が 0 件。観測者が受けた LSN が、障害の後の状態に必ず含まれる（出力の後に失われた書き込みが 0 件） |
| 頻度 | 保存・複製・リース・ルーターに触れる PR ごとに 1 時間。毎晩すべての障害の組み合わせ。workerd の取り込みのたび |

## 16. 未解決の問い

- 公開の workerd の Durable Objects の実装に、確定の約束を外から差し込めるか。差し込めないと、パッチが大きくなる（ADR-0006 のパッチの行数の目標に響く）。
- リージョンの DynamoDB の障害で、リースを更新できず全ホストが止まる。リースを DynamoDB でなく、ログのノードの群の中の合意（Raft）で持つか。
- 手元にない大きな DB（10 GiB）の復元の時間。複製を暖かい写し（SQLite を適用し続ける）にするか。費用は 3 倍に近くなる。
- アカウントごとの暗号化の鍵を、手元の SQLite と S3 の WAL に使うか。
- NFR-010 の「ホームのリージョンの全体の障害で RPO 1 分」を、S3 CRR で保証できない。約束の値を変えるか、WAL を別のリージョンへ同期で送るか。
- 管轄 `jp` の実体を、東京と大阪の 2 リージョンにまたがって同期で複製するか（リージョンの障害に自動で耐えるが、確定の遅延が増える）。
- 1 実体の WebSocket の数とタグの上限の本家の値。
- クラスの名前の変更・削除（移行）を含む版のデプロイと、その版からのロールバックの規則。

### 決定

2026-09-27 の既定案。

- E9 の最初に PoC を行う。差し込めないときは、Durable Objects の保存の層（`ActorSqlite` に相当する部分）を自前のパッチで持ち、パッチの一覧に理由を書く。
- リースは S1 で DynamoDB。DynamoDB の障害でリージョンの DO が止まることを、既知の制約として quality.md に載せる。S2 の前に見直す。
- 暖かい写しは持たない。復元は需要の順にし、10 GiB の実体の RTO を 5 分以内にする（試験で確かめる）。
- 暗号化は S1 で SSE-S3 とホストのディスクの暗号化。アカウントごとの鍵は security の領域で決める。
- NFR-010 の RPO 1 分は、DO について S1 で保証しない（通常は 10 秒＋CRR の遅れ）。PM・Ops に諮る（矛盾として報告する）。→ 統合の工程（2026-09-27）で、NFR-010 を ADR-0051 の製品ごとの値に改めた（[README.md](README.md) の 3 節。PM・Ops の確認事項）。
- リージョンをまたぐ同期の複製は S1 でしない（ADR-0005 のまま）。
- WebSocket とタグの上限は仮の値で始め、E9 で本家の値を確かめて揃える。

## 17. quality.md・runbooks・data-model に載せるもの

**quality.md**

- リスク：1 つの名前に 2 つの実体が確定する（リースとフェンシングの誤り）。性質ベーステストと Jepsen の形の試験を、保存・複製・リース・ルーターの変更ごとに回す。合格の基準は 13.2 節の検査で 0 件。
- リスク：確定の前に出力が出る（出力のゲートの配線の誤り）。出力のゲートのワークロード。
- リスク：S3 の障害でログのノードのディスクが満ちる。ディスクの使用率の監視と、90% での書き込みの停止。
- リスク：DynamoDB の障害でリージョンの DO が止まる（既知の制約）。
- 本番での検証：各リージョンに合成の実体を置き、1 秒ごとに連番を書いて読み、抜け・戻りを検査する（カナリア）。四半期ごとに 1 つの AZ のホストを外す訓練。

**runbooks**

- `do-host-failure-storm`：多数のホストの同時の停止（AZ の障害）。復元の待ちの列、S3 の速さ、容量の確認。
- `do-unavailable-objects`：`unavailable` の実体がある。持ち主と複製の状態、戻せる複製の特定。データを失う手段（1 台だけの複製からの強制の復元）は、Dev のテックリードの承認がなければ使わない。
- `do-log-node-disk-pressure`：ログのノードのディスクの使用率が 70% を超えた。S3 への転送の遅れの確認。
- `do-region-evacuate`：10.2 節。
- `do-pitr-restore-support`：利用者からの復元の依頼の支援（利用者の API で戻せない場合）。
- SLI の追加の依頼（Ops へ）：確定の遅延（p50・p99）、引き継ぎの数と時間、`unavailable` の実体の数、`overloaded` の率、WAL の転送の遅れ、ログのノードのディスクの使用率、アラームの遅れ、カナリアの抜け。
