# ADR-0083: アプリは週 1 回の列車と段階のリリースで出し、最小と強制の 2 つのバージョンを持つ。PMS の API は `/v1` と日付のバージョン（`X-<Brand>-Api-Version: YYYY-MM`）で持ち、アプリごとに固定し、各バージョンを次の公開から 12 か月支え、使われているバージョンは止めない。ML のモデルと T&S の規則は関門 → 影 → 5% → 100% で出し、設定で戻す

## Context

- アプリ（iOS・Android）はストアの審査と利用者の更新を経るので、古いバージョンが長く残る。安全の窓口のボタン、総額と確認の画面の表示（法務の L7）の不具合は、古いバージョンを止める理由になる。
- PMS は本システムの API に空室を書き続ける。API の壊す変更で PMS の書き込みが止まると、外部との二重の予約につながる（NFR-003、NFR-005）。PMS の開発者は本システムの外にいて、更新の速さを本システムが決められない。
- 本家の PMS の API のバージョンの方式は確かめられなかった（**未検証**）。Shopify の題材は四半期の日付のバージョンを決めた（[Shopify の ADR-0009](../../../shopify/docs/decisions/0009-admin-api-graphql-and-cost-limits.md)）。
- ML と T&S の規則は、影の評価の後に予約の 5% → 100% で出し、戻しは設定の切り替え（[runbooks/](../runbooks/README.md) の 3 節、[ADR-0009](0009-trust-and-safety-and-ml-boundary.md)）。
- Mercari の題材は、アプリの列車と最小のバージョン、モデルの出し方を決めた（[Mercari の ADR-0079](../../../mercari/docs/decisions/0079-app-release-trains-min-versions-and-model-releases.md)）。

## Options

PMS の API：

1. **道の大きなバージョンと日付のバージョン、アプリごとの固定、12 か月の支え、使われていれば止めない**
2. 道のバージョンだけ（`/v1`、`/v2`）
3. バージョンを持たず、互換の変更だけを続ける

## Decision

1 を採用する。詳細は [delivery.md](../architecture/delivery.md) の 6〜8 節。

- **アプリ**：週 1 回の列車。App Store の段階のリリース（7 日）と Google Play の段階の公開。クラッシュのない率 99.5% 未満と API の誤りで止める。`ops.app_min_version_<platform>`（促す）と `ops.app_force_version_<platform>`（426）。支えるのは直近 26 の列車。強制の引き上げは安全、お金と法令の表示、API の契約の削除のときだけで、予約の確認の経路は引き上げの後 24 時間受ける。
- **PMS の API**：`/v1` と `X-<Brand>-Api-Version: YYYY-MM`（年 4 回まで。最初は `2026-10`）。アプリの登録の時に最新を固定し、見出しのない要求は固定のバージョン。同じバージョンの中は互換の変更（欄・任意の入力・選んだときだけの事象の追加）だけ。壊す変更は新しいバージョンだけ。各バージョンを次の公開から 12 か月支え、6 か月前に知らせ、`Deprecation`（RFC 9745）と `Sunset`（RFC 8594）を付ける。止める前の 30 日に使った審査済みのアプリがあれば止めずに延ばす。Webhook の本文は購読のバージョンの形。バージョンごとの OpenAPI を固定し、全バージョンの契約の試験を PR で回す。
- **ML と規則**：署名した成果物、評価の集まりの関門（公平さの比 1.25 以下を含む）、7 日の影、予約の 5%、100%。審査の量が 1.5 倍を超える変更は Ops と合意。戻しは `models.*`・`rules.*` の設定の切り替え。

### 他の案を選ばなかった理由

- **2（道のバージョンだけ）**：小さな壊す変更のたびに道のバージョンを上げることになり、PMS の移行の手間が大きい。上げるのをためらって、同じバージョンの中で壊す変更をしたくなる。
- **3（バージョンなし）**：誤った設計を直せず、欄が増え続ける。直すときに全 PMS が同時に壊れる。

## Consequences

- 良くなること：
  - PMS は自分の速さでバージョンを上げられ、本システムは壊す変更を出せる。
  - 使われているバージョンを止めないので、API の変更が外部との二重の予約の原因にならない。
  - アプリとモデルの戻しが速い。
- 引き受けるコスト：
  - 同時に最大 5 つ前後のバージョンの変換の層と契約の試験を持つ。
  - 移行しない PMS のために古いバージョンを延ばす運用が要る。

## Confirmation

- CI：全バージョンの契約の試験、`Deprecation`・`Sunset` の見出し、最小のバージョンの 426 と予約の経路の 24 時間の表駆動。
- 本番：バージョンごとの要求の数とアプリの数、止める 30 日前の要求の率 0（[observability.md](../architecture/observability.md)）。
- モデル：評価の集まりの関門と影の評価の記録（[quality.md](../quality.md) の 2.2.1 節 I）。
