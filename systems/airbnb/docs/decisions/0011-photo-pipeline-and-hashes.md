# ADR-0011: 写真は署名つきの URL で S3 に直接上げ、`media-processor` が sharp で検査・向きの補正・メタデータの全部の除去・4 つの幅の WebP と JPEG への変換を行い、出力を読み直して位置情報がないことを確かめてから使う。知覚ハッシュは 64 ビットの pHash と dHash。1 件 50 枚、公開には 5 枚

詳細は [listings-and-content.md](../architecture/listings-and-content.md) の 6 節。

## Context

- 写真の EXIF の GPS は、物件の正確な位置を漏らす。位置の秘匿（NFR-016）は、写真の 1 枚の漏れで崩れる。
- 他の物件の写真の使い回しは、偽のリスティングの主な手口である（[ADR-0009](0009-trust-and-safety-and-ml-boundary.md)）。
- S1 で 250 万枚、地図と一覧で何度も表示する。端末の幅に合わせた大きさが要る。
- Mercari の題材は、同じ形の写真の処理と、帯に分けた pHash の索引を決めた（[ADR-0012](../../../mercari/docs/decisions/0012-photo-pipeline-and-perceptual-hashes.md)、[ADR-0013](../../../mercari/docs/decisions/0013-photo-reuse-index.md)）。

## Options

1. **S3 に直接上げ、Worker で変換し、メタデータの除去を出力の読み直しで確かめる。pHash と dHash**
2. API のサーバーが受けて変換する
3. 画像の変換の外部のサービス（要求の時に変換する CDN の機能）を使う

## Decision

1 を採用する。

- 署名つきの PUT の URL（5 分、`Content-Length` と `Content-Type` を固定）。形式は JPEG・PNG・HEIC・WebP を中身で確かめる。1 枚 25 MB、1 億画素まで。
- sharp で復号、向きの補正、sRGB、幅 320・640・1,280・2,048 の WebP（品質 80）と JPEG（品質 82）。メタデータを残す関数は lint で禁じる。
- 8 つの出力を読み直し、EXIF・XMP・IPTC・GPS の塊がないことを確かめる。1 つでも残れば `failed` で、警告を出す。
- 原本は受け付けの桶から 1 日で消し、配らない。
- pHash と dHash は Mercari の題材の作り方を参照し、本システムのコードで書く。距離 0 は禁止の一覧の一致、1〜6 は他のホストのアカウントとの使い回しの信号。同じホストのアカウントの中の一致は信号にしない。
- 1 リスティング 50 枚、公開に 5 枚以上。

### 他の案を選ばなかった理由

- **2**：25 MB の写真を API のタスクが受けると、メモリと時間を食い、検索・予約の要求と資源を取り合う。
- **3**：要求の時の変換は、原本を残す必要があり、原本のメタデータが配る経路の近くに残る。除去の確かめを本システムで持てない。

## Consequences

- 良くなること：
  - 配る写真に位置情報がないことを、出力ごとに確かめられる。
  - 使い回しの信号が Mercari の題材と同じ考え方で、閾値の確かめの方法も共有できる。
- 引き受けるコスト：
  - 8 つの出力を持つ保存の費用（1 枚 平均 1.5 MB 前後と見込み、S1 で 4 TB 前後。capacity の領域）。
  - 宿泊の写真は同じ建物で似るため、使い回しの信号に誤りが出る。規則のエンジンの重みで抑える。
