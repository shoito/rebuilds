# ADR-0067: 宿泊者名簿は予約ごと・宿泊者ごとの行を vault に、（届出住宅、年度）の主体の鍵の封筒の暗号化で持ち、旅券の画像は同じ鍵で S3 に置く。読めるのはホストのアカウントの名簿の権限と、法令の照会の手順（2 人の承認）だけ。入力はゲストがチェックインの 24 時間前までに行う。保存の期間は `legal.guest_registry_retention_days`（開発・検証の既定 1,095 日）で、本番の値は法務の L3 の後

## Context

- 宿泊者名簿は本人確認のうえ作り、作成日から 3 年保存する。日本に住所のない外国人は国籍と旅券の番号（観光庁の資料、2026-10-10 に確認）。本家はホストに旅券の写しの保存を求める（[ヘルプの記事 2274](https://www.airbnb.com/help/article/2274)）。
- 名簿と旅券の画像は vault に閉じ、ホストの名簿の画面と法令の照会の手順からだけ読む（[AGENTS.md](../../AGENTS.md)）。
- 鍵は用途ごと・主体ごとで、名簿と旅券の主体は（届出住宅、年度）（[ADR-0073](0073-key-layout-and-vault-envelope-encryption.md)）。保持は名簿と旅券を作成から 3 年を下限にし、自動の削除は法務の結論の後（[ADR-0075](0075-data-classes-and-retention.md)）。
- 作成の義務者、本人確認の方法、項目、保存、照会への提出は法務の L3（越境と保存は L8）。

## Options

1. **vault の行、主体の鍵、ゲストが事前に入れる、名簿の権限と 2 人の承認の照会**
2. ホストが自分で名簿を持ち、本システムは持たない
3. 名簿を予約の表（core）に暗号化の列で持つ

## Decision

1 を採用する。詳細は [regulatory-compliance-japan.md](../architecture/regulatory-compliance-japan.md) の 8 節。

- 項目は `legal.guest_registry_fields`。旅券は eKYC の提供者の部品で撮影と読み取り（identity-verification の領域）。
- 入力の期限 `registry_due_at = check_in_at − 24h`。案内は確定の時、72 時間前、24 時間前。入り方の情報は名簿の完了の後（`legal.registry_gate_arrival_info`）。
- 読める主体：ホストのアカウントの `owner`・`full`・`registry` の権限の共同ホスト。運用者は照会の手順（記録、JIT、2 人の承認）だけ。読み出しごとに監査ログ（内容は書かない）。
- 消去は年度の主体の鍵の破棄（自動の破棄は法務の結論の後）。
- 書き出しは再認証の後、署名つきの URL（15 分）。

### 他の案を選ばなかった理由

- **2**：ホストの多くは電子の名簿を持たず、旅券の写しが個人の端末やメッセージに流れる。
- **3**：core の読み手が多く、名簿だけを鍵の破棄でまとめて消せない。

## Consequences

- 良くなること：
  - 名簿の読み手が限られ、年度ごとにまとめて消せる。
- 引き受けるコスト：
  - L3 の結論まで、本番の保存の期間・項目・門の値が決まらない。
  - 名簿を入れないゲストの問い合わせが増える。
