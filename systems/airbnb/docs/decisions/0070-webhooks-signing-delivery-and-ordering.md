# ADR-0070: PMS への Webhook は購読ごとに少なくとも 1 回配り、`<Brand>-Signature`（時刻つきの HMAC-SHA256）で署名し、リスティングごとに 1 件ずつ送って順序を守る。72 時間まで再送して止め、7 日分の事象の一覧で取り直せるようにする。本文に個人のデータを載せない

## Context

- PMS は本システムの予約・変更・キャンセルを早く知り、他の掲載先を閉じる必要がある。本システムの変化から Webhook の送信まで p95 10 秒（NFR-003）。
- 受け手は止まり、遅れ、重複を嫌う。同じリスティングの「確定」と「キャンセル」が逆に届くと、PMS は開いた夜を閉じたままにするか、閉じた夜を開ける。
- 宛先の URL は開発者が決めるので、送信は SSRF の経路になる（[security.md](../architecture/security.md) の T8）。
- Webhook の秘密が漏れると、偽の事象を受け手に送れる。本文に個人のデータがあると、受け手の側の漏れが本システムの漏れになる（NFR-016）。

## Options

1. **少なくとも 1 回、リスティングごとの直列の送信、時刻つきの HMAC の署名、72 時間の再送、事象の一覧の API、最小の本文**
2. 順序を持たない並列の送信と、受け手の側での並べ替え
3. Webhook を持たず、PMS に事象の一覧を引かせる（ポーリング）

## Decision

1 を採用する。詳細は [host-tools-and-api.md](../architecture/host-tools-and-api.md) の 7 節。

- **事象**：`reservation.*`、`availability.changed`（そのアプリ自身の書き込みの分は送らない）、`calendar.conflict_detected`、`message.created`、`listing.*`、`bulk_job.completed`、`grant.revoked`。outbox から `webhook-fanout` が購読と範囲で宛先を決める。
- **本文**：ID、種類、資源のバージョン、日付・状態などの最小の欄。ゲストの名前、連絡先、メッセージの本文、住所を載せない。受け手は範囲を確かめる API で取る。
- **署名**：`<Brand>-Signature: t=<unix>,v1=<hex>`。`v1` は購読の秘密での `t.本文` の HMAC-SHA256。秘密は購読ごと 256 ビット、`kms-pms-secrets` で包む。入れ替えの間は新旧の 2 つの `v1` を付ける。受け手には 5 分より古い `t` を拒むよう求める。`X-<Brand>-Event-Id` で重複を除かせる。
- **順序**：（購読、リスティング）ごとに送っている事象を 1 つに限る。各事象に `listing_seq` を付ける。
- **再送**：30 秒から倍にして最大 1 時間の間隔、揺らぎ ±20%、最初から 72 時間。接続 3 秒・全体 10 秒、2xx の外は失敗、転送を辿らない。72 時間、成功のない購読は `disabled` にし、開発者と `owner` に知らせる。
- **取り直し**：`GET /v1/events?since=` で同意の範囲の事象を 7 日分返す。
- **送信の経路**：`webhook-sender` だけが送り、信用しない宛先への egress の経路（私的なアドレスの拒否、固定の送り元の IP）を使う（[ADR-0076](0076-accounts-network-and-egress-with-ssrf-controls.md)）。

### 他の案を選ばなかった理由

- **2（並列）**：受け手は全員が並べ替えを正しく作らなければならず、作らない受け手で開け閉めが逆になる。1 つのリスティングの事象は多くないので、直列でも NFR-003 の p95 10 秒に収まる。
- **3（ポーリングだけ）**：PMS が多くのホストを短い間隔で引くと、本システムの負荷が Webhook より大きく、知るまでの遅れも長い。事象の一覧は取り直しの手段として残す。

## Consequences

- 良くなること：
  - 受け手は `listing_seq` で順序と飛びを確かめられる。
  - 秘密が漏れても個人のデータは漏れない。
  - 長い障害の後も、7 日の中なら取り直せる。
- 引き受けるコスト：
  - 1 つの遅い受け手の 1 つのリスティングの事象が、そのリスティングの後の事象を待たせる（時間切れ 10 秒と再送の間隔の分）。
  - 受け手は詳しい中身のために API を呼ぶ必要があり、要求が増える（速さの上限に含める）。

## Confirmation

- 性質ベーステスト：任意の失敗・時間切れの列で、各事象が `delivered` か `dead` になり、（購読、リスティング）の中で `listing_seq` の順に配られる（PROP-HST-004。`webhook-sim` と仮想の時計）。
- 試験のベクトル：署名、古い `t`、新旧の秘密。
- 本番：送信までの遅れ（p95 10 秒）、再送の率、`disabled` の購読の数（[observability.md](../architecture/observability.md)）。
