# ADR-0008: リスティングの価格はホストの通貨の整数で持つ。表示と支払いはゲストの通貨にでき、換算は見積もりの時の相場の写し（ID つき）で 1 回だけ行う。台帳の仕訳は 1 つの通貨に閉じ、通貨の間は為替の口座で結ぶ。ホストへは自分の通貨で送る

## Context

日本の物件に海外のゲストが泊まる。ゲストは自分の通貨（米ドル、ユーロ、ウォン、台湾ドル、人民元、香港ドル、豪ドルなど）で総額を見て、払いたい。ホストは円で料金を決め、円で受け取りたい。S2 以降は日本の外のホストも加わる。次を守る（NFR-007、NFR-015）。

- 見積もりの総額と請求の額が、通貨を含めて一致する。
- キャンセルの返金は、ゲストが払った通貨と額をもとに計算する。為替の動きで、ゲストに払った額より多く・少なく返さない。
- 台帳は通貨ごとに釣り合う。為替の差が説明できる。

本家は通貨の異なる予約で、ゲストのサービス料を高くしている（分担の型で 14.1〜16.5% の上の値。[ヘルプの記事 1857](https://www.airbnb.com/help/article/1857)、2026-10-10 に確認）。相場の出どころと換算の時期は公開されていない（**未検証**）。

関係する題材：Shopify の題材は、基本の通貨の価格と、日次の相場の写し（ID つき）での換算と丸めを決めた（[ADR-0015](../../../shopify/docs/decisions/0015-markets-currencies-and-rounding.md)）。Stripe の題材は、複数の通貨の残高と送金を持つ（[ADR-0015](../../../stripe/docs/decisions/0015-chart-of-accounts-and-balance-transactions.md)）。

## Options

請求の通貨：

1. **ゲストの通貨（提供者が対応する通貨）で請求する。対応しなければリスティングの通貨**
2. 常にリスティングの通貨で請求し、ゲストのカードの発行者に換算を任せる

換算の時期：

- a. **見積もりの時に 1 回。相場の写しの ID を見積もりに固定する**
- b. 売上の確定の時の相場で換算し直す

## Decision

1 と a を採用する。

### 価格の正本

- リスティングの料金の規則は、ホストのアカウントの通貨（MVP は円）の最小単位の整数で持つ。
- 見積もりは、まずリスティングの通貨で全部の行（泊、割引、料金、サービス料、税）を計算し、丸める（pricing-and-fees、taxes の各領域）。

### 換算

- `packages/fx` の `convert(amount, from, to, rate_snapshot)` だけが換算する。相場の写し（`fx_rate_snapshots`：ID、通貨の組、仲値、上乗せ、取得の時刻、提供者）は、為替の相場の提供者から 1 時間ごとに取り込む。
- 見積もりの時に、その時点の最新の写しの ID を見積もりに固定する。表示の額 = 各行をリスティングの通貨で計算した後、**合計だけ** を換算し、通貨の最小単位で丸める（端数は四捨五入。ISO 4217 の小数の桁）。行ごとの換算額は、合計から按分して出す（大きい行から 1 単位ずつ割り振る決定的な規則）。
- 上乗せ（為替の手数料）は相場の写しに含め、見積もりの明細に「為替の手数料」として出すかは法務の L7・L13 の後（既定は総額に含め、明細の注で示す）。
- 見積もりの期限（15 分）の間、相場は固定される。

### 請求と台帳

- 請求の通貨（`charge_currency`）は、ゲストの選んだ表示の通貨が提供者の対応の一覧にあればそれ、なければリスティングの通貨。
- 台帳は、仕訳を 1 つの通貨に閉じる。ゲストの通貨で受けた額は、その通貨の `psp_receivable` と `guest_funds_held` に入れる。
- 決着（release・settle）の時に、ゲストの通貨の預かりを、見積もりに固定した相場でリスティングの通貨に換える仕訳を書く：「借方 `guest_funds_held`（ゲストの通貨）／貸方 `fx_clearing:<ゲストの通貨>`」と「借方 `fx_clearing:<リスティングの通貨>`／貸方 `host_payable`・`service_fee_revenue`（リスティングの通貨）」。ホストの受け取りは見積もりの時の円の額で決まり、為替の動きの影響を受けない。
- 提供者の精算の通貨と相場の差（本システムの固定の相場と、実際の換算の相場の差）は、`fx_clearing` の残高として残り、日次に `fx_gain_loss`（収益・費用）へ振り替える。
- 返金は、ゲストが払った通貨と額で計算する（見積もりの各行の、ゲストの通貨の按分の額をもとに、返金の割合を当てる）。

### 送金

- ホストへは、ホストのアカウントの通貨（MVP は円）で送る。日本の外のホストと国際送金は、ledger-and-payouts の領域で、法務の L6 の後に足す。

### 他の案を選ばなかった理由

- **2（リスティングの通貨だけ）**：ゲストは請求の額を事前に知れない（カードの発行者の相場と手数料による）。総額の一致（NFR-015）をゲストの側で守れない。
- **b（確定の時の相場）**：見積もりと請求の額が変わり、NFR-015 を守れない。

## Consequences

- 良くなること：
  - ゲストは自分の通貨の総額を見て、その額で払える。
  - ホストの受け取りは円で確定し、為替の動きを本システムが持つ。
  - 換算と丸めが 1 か所で、見積もりから再現できる。
- 引き受けるコスト：
  - 見積もりから決着までの為替の動き（最長 1 年以上）を本システムが負う。上乗せでまかなえるかを財務が見る。大きな動きには、上乗せの値の見直しで応じる。
  - 通貨ごとの口座と為替の口座で、台帳の照合が増える。

## Confirmation

- 性質ベーステスト：任意の行の額・通貨・相場で、表示の行の和が表示の総額と一致する。返金の額は払った額を超えない。決着の後の `guest_funds_held` は通貨ごとに 0（[quality.md](../quality.md) の 2.2.1 節 C）。
- 試験のベクトル：通貨ごとの小数の桁（円 0、米ドル 2、クウェート・ディナールのような 3 の通貨は MVP で扱わない）、丸めの境。
- 本番：`fx_clearing` の日次の残高と、為替の損益の月次の確認（財務）。
