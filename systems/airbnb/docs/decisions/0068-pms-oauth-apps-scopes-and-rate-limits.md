# ADR-0068: PMS は登録して審査した OAuth のアプリとして、ホストのアカウントの `owner` の同意で動く。認可コードと PKCE、1 時間のアクセストークンと入れ替える 90 日のリフレッシュトークン、同意で範囲とリスティングを絞り、（アプリ、ホスト）とアプリ全体のトークンバケットで速さを絞る

## Context

- PMS・チャネルマネージャーは、多くのホストのリスティングの空室・料金・予約・メッセージを 1 か所で動かす（[intent.md](../intent.md)）。ホストは同じ物件を他の掲載先にも出し、PMS の書き込みが遅れると外部との二重の予約になる（NFR-003）。
- [ADR-0007](0007-tenancy-host-accounts-and-rls.md) は、PMS を OAuth のアプリとし、ホストのアカウントの範囲で動かし、トークンの接頭辞を `<brand>_pms_` にすると決めた。PMS の書き込みも `stay_claims` の排他の制約を通る。
- PMS のトークンは、多くのホストの予約とゲストの名前を読める。漏れや悪用（読み集め、書き込みの連打）は、多くのホストに同時に効く（[security.md](../architecture/security.md) の T6）。
- 本家の PMS の API の公開の範囲と形は、公式の資料で確かめられなかった（**未検証**）。Shopify の題材はアプリの導入を OAuth と入れ替えるトークンで設計した（[Shopify の ADR-0054](../../../shopify/docs/decisions/0054-oauth-install-and-expiring-tokens.md)）。

## Options

1. **登録と審査のある OAuth のアプリ。認可コードと PKCE、短いアクセストークンと入れ替えるリフレッシュトークン、同意で範囲とリスティングを絞る**
2. ホストが画面で作る長い寿命の API の鍵（個人のアクセストークン）
3. 1 つの PMS に 1 つの全体の鍵を渡し、ホストの ID を要求ごとに指定させる

## Decision

1 を採用する。詳細は [host-tools-and-api.md](../architecture/host-tools-and-api.md) の 5 節。

- **アプリ**：開発者の組織がアプリを登録する。状態は `development`（試験のホストだけ、10 まで）→ `review` → `approved`（全ホスト）→ `suspended`。本番のホストに接続できるのは、運用の審査（範囲が用途に合う、冪等と署名の検証が試験の環境で通る）を通したアプリだけ。
- **同意**：ホストのアカウントの `owner` だけが、直近 10 分の強い確認（[ADR-0072](0072-sensitive-operations-payout-holds-and-account-deletion.md)）の後に許す。範囲と、リスティングの全部か一部を選ぶ。
- **流れ**：認可コード（60 秒、1 回）と PKCE（`S256` だけ）。`redirect_uri` は登録の一覧と完全一致。
- **トークン**：アクセストークン `<brand>_pms_at_…`（1 時間）、リフレッシュトークン `<brand>_pms_rt_…`（90 日、使うたびに入れ替え、再使用で同じ同意の一式を取り消す）。どちらもハッシュで core に置き、末尾にチェックサムを付けてシークレットスキャンに独自の形式として登録する。
- **主体**：`partner-api` は要求ごとに `SET LOCAL app.host_account_id`、`app.host_role = 'pms'`、`app.pms_grant_id` を置く。RLS のポリシーは同意のリスティングの集合で行を絞り、経路の `requiredScopes` と応答の欄の許可の一覧で範囲を守る。
- **範囲**：`listings:read|write`、`calendar:read|write`、`pricing:read|write`、`reservations:read|write`、`messages:read|write`、`guest_registry:read`（`legal.pms_registry_scope_enabled`、既定 `false`。法務の確認待ち：L3・L8）、`webhooks:manage`。住所・位置・届出住宅・公開の状態の変更、予約の作成、ホストのキャンセルは API に出さない。
- **速さの上限**：（アプリ、ホストのアカウント）ごとに 1 秒 20 単位・瞬間 100 単位、アプリ全体で 1 秒 500 単位（S1。審査で 2,000 まで）。書き込みは 1 + 泊の数 ÷ 31 の切り上げの単位。Valkey が使えなければタスクごとの上限で絞り、緩めない。
- **取り消し**：同意の取り消し・アプリの停止（`ops.partner_api_enabled.<app>`）で、トークンを 5 秒以内に失効させる。書き込みは同じトランザクションで同意の有効を確かめる。そのアプリの `api_block` の行は残す。
- **越境**：アプリはデータの置き場所の国を申告する。日本の外のアプリにゲストの個人のデータを渡すかは法務の確認待ち（L8）で、結論まで `legal.pms_cross_border_guest_data = deny`。

### 他の案を選ばなかった理由

- **2（長い寿命の API の鍵）**：漏れたときの効く期間が長く、ホストが PMS の会社に鍵を手で渡す運用になる。範囲とリスティングの絞りを同意の画面で見せられない。
- **3（全体の鍵）**：1 つの鍵の漏れが全ホストに効く。ホストの同意の記録がなく、[ADR-0007](0007-tenancy-host-accounts-and-rls.md) の「ホストが許した範囲でだけ動く」を守れない。

## Consequences

- 良くなること：
  - PMS の行える範囲が、ホストの同意と RLS で二重に閉じる。
  - トークンの漏れの効く期間が 1 時間で、入れ替えの再使用で盗難に気づける。
  - アプリごとに止められる。
- 引き受けるコスト：
  - 審査の人手と、開発者の試験の環境（試験のホスト）の運用。
  - PMS はリフレッシュトークンの入れ替えを正しく実装する必要があり、誤ると一式の取り消しで接続が切れる（開発者の文書と試験の環境で確かめる）。

## Confirmation

- 性質ベーステスト：任意の同意と要求の列で、同意の外の行と範囲の外の欄が出ない（PROP-HST-001。[quality.md](../quality.md) の 2.2.1 節 H の PMS の行）。
- 結合：リフレッシュトークンの再使用で一式が取り消され、取り消しから 5 秒の後に 401。
- CI：`requiredScopes` のない `partner-api` の経路を拒む。
- E20 の外部のペンテストで、PMS の API の範囲の越え、トークンの扱い、速さの上限を確かめる。
