# ADR-0020: 1 リスティングの複数の同じ部屋（S2）は、部屋（`listing_units`）ごとの `stay_claims` の行にし、排他の制約の鍵を `unit_id` にする。部屋の割り当ては予約のトランザクションの中で先に空いた部屋から決める

## Context

- [ADR-0002](0002-availability-representation-and-double-booking.md) の排他の制約は、1 リスティング = 1 つの在庫の前提で、複数の同じ部屋（ホテルの部屋の種類）には使えない。S2 で決めるとした。
- 複数の同じ部屋でも、二重の予約を DB で 0 にしたい（NFR-005）。日程の変更・準備の日・ブロックも同じ形で扱いたい。
- 本家の扱いは**未検証**。

## Options

1. **部屋ごとの行。`unit_id` を鍵にした同じ排他の制約。割り当ては予約のトランザクションの中で先に空いた部屋**
2. 泊ごとの数の在庫（リスティング × 日の残り数）を条件つきの更新で減らす
3. 部屋ごとに別のリスティングを作り、検索でまとめる

## Decision

1 を採用する（S2）。形は [availability-and-calendars.md](../architecture/availability-and-calendars.md) の 10 節。

- `listing_units` を持ち、`stay_claims.unit_id` を NOT NULL にする。1 部屋のリスティングは既定の部屋を 1 つ持つ。排他の制約は `(unit_id, claim_group, block_span)`。
- `claimStay` はリスティングの行のロックの下で、部屋を `unit_id` の順に試し、最初に入った部屋に割り当てる。日程の変更は同じ部屋を先に試す。
- ゲストは部屋を選ばない。ホストの部屋の交換は `swapUnits`（1 つのトランザクション）。
- 届出住宅の数えは部屋に依らず、届出住宅 × 日で 1 日（[ADR-0006](0006-regulatory-night-cap-enforcement.md)）。

### 他の案を選ばなかった理由

- **2**：準備の日と、滞在の全部の夜を同じ部屋で泊まれることを表せない（日ごとには空いていても、部屋を移る必要が出る）。
- **3**：ホストの料金と規則の管理が部屋の数だけ増え、検索で同じ部屋が並ぶ。

## Consequences

- 良くなること：
  - 1 部屋と複数の部屋で、制約と関数が同じになる。
- 引き受けるコスト：
  - 先に空いた部屋の割り当てで、日程の細切れ（部屋の入れ替えをすれば入る予約が入らない）が起きる。ホストの `swapUnits` と、S2 の後の割り当ての改善で補う。
  - 検索の写しの形が変わる（search-and-ranking の領域で決める）。

## Confirmation

- 性質ベーステスト：任意の部屋の数・並行の操作で、同じ部屋の異なる組の有効な `block_span` は重ならず、成功した予約の数は `avail-ref`（部屋ごとの配列に直列に先に空いた部屋で書く）と一致する。
