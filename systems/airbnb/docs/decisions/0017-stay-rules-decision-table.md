# ADR-0017: 滞在の規則を DT-AVL-001 の 12 行で確定する。最短・最長はチェックインの日の値、締め切りは「N 日前の HH:MM」の 1 つの形、予約できる期間はチェックアウトの日で判定する。泊数の上限は MVP で 27 泊。判定は物件の現地の日付と時刻で、`checkStayRules` の 1 つの純粋な関数が行う

## Context

- [ADR-0002](0002-availability-representation-and-double-booking.md) は、排他の制約に入れない規則（最短・最長の泊数、曜日、締め切り、予約できる期間、定員）を `checkStayRules` の 1 つの純粋な関数で判定すると決め、表の草案を置いた。
- 予約、日程の変更、検索のステージ 2、ホストの画面の 4 か所が同じ判定を要る（[ADR-0003](0003-search-for-date-range-availability.md)）。
- 草案では、滞在の途中の日の上書きを見るか、締め切りの形（「当日の HH:MM」と「N 日前」）、予約できる期間をチェックインとチェックアウトのどちらで測るか、泊数の上限が決まっていなかった。
- 28 泊以上の滞在は、月ごとの請求と送金、借地借家法との関係（法務の L7）が要り、MVP の後にした（intent の「MVP の後」）。
- 本家の判定の細部は公開されていない（**未検証**）。

## Options

1. **12 行の決定表。上書きはチェックインの日だけ。締め切りは「N 日前の HH:MM」。期間はチェックアウトの日。MVP の上限 27 泊**
2. 滞在の全部の日の上書きの最大の最短の泊数を使う
3. 締め切りを「当日の HH:MM」と「N 日前」の 2 つの形で持つ
4. 泊数の上限を持たず、28 泊以上も予約させる

## Decision

1 を採用する。表と例は [availability-and-calendars.md](../architecture/availability-and-calendars.md) の 6 節。

- 評価の順：範囲 → 過去 → 27 泊 → 定員 → 予約できる期間 → 締め切り → チェックインの曜日 → チェックアウトの曜日 → 最短 → 最長 → 設定の誤り → 通す。最初に一致した行の理由のコードを返す。
- 締め切りの瞬間 = `toInstant(check_in − cutoff_days_before, cutoff_local_time, time_zone)`。`cutoff_days_before = 0` が「当日の HH:MM」。
- 予約できる期間：`check_out ≤ add_months(today_local, booking_window_months)`（月末を丸める）。
- 最短・最長は `calendar_days` のチェックインの日の上書き、なければリスティングの既定。
- `now` は引数。関数は DB と時計に触れない。

### 他の案を選ばなかった理由

- **2**：ホストが特定の日（催しの日）に最短 3 泊を付けると、その日をまたぐ全部の滞在に効き、意図より広く塞ぐ。ホストの画面で説明しにくい。
- **3**：2 つの形は「0 日前の HH:MM」と「N 日前の 23:59」で 1 つの形に表せる。形が 2 つだと検索の写しと決定表の行が増える。
- **4**：28 泊以上の送金と法的な整理が決まっていない。予約だけ受けると、後の送金の設計が既存の予約に縛られる。

## Consequences

- 良くなること：
  - 4 か所の判定が 1 つの関数と 1 つの表で一致する。
  - 締め切りの判定がゲストのタイムゾーンに依らない。
- 引き受けるコスト：
  - 28 泊以上を求めるゲストを受けられない（本家との違い。[README.md](../architecture/README.md) の 1.4 節に足す提案）。
  - 途中の日の上書きを見ないので、ホストが特定の夜だけを長い滞在に限る使い方はできない。

- 仮想の時計：締め切りの境（17:59:59・18:00:00）、月末と閏日。
