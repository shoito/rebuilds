# Runbook: デプロイとロールバック

- Owner: Ops（当番）
- 対応するアラート: デプロイ中の自動ロールバック、デプロイの後の SLO の悪化、手のロールバックの判断
- 最終確認日: 2026-10-10

方針は [README.md](README.md) の 3 節、仕組みは [delivery.md](../architecture/delivery.md) の 4・5 節（[ADR-0082](../decisions/0082-pipeline-schema-ordering-and-config-governance.md)）。

## 症状

- 段階のデプロイ（検証 → 見張りの利用者 → 5% → 25% → 100%、各 30 分）の途中で、自動のロールバックが働いた。
- デプロイの後に、予約の 5xx・p99、照合の不一致、検索の混入の率が上がった。

## 影響

- 新しい組に送った割合の利用者が誤りを受ける。正しさの指標（`stay_claims`・180 日・決着・台帳の照合）は組で分けられないので、1 件でも全体の問題として扱う。

## 確認

1. デプロイの記録（`deployments`：サービス、イメージのダイジェスト、段、ロールバックの理由）。
2. 新旧の組の指標の比べ：予約の 5xx と p99、見積もりと請求の差、検索の 5xx と混入の率。新しい組が古い組の 2 倍を 5 分超えたか。
3. 照合（`stay_claims`、180 日、予約と台帳、台帳の不変条件）が段の中で 1 件でも出たか。
4. 同じ時刻のマイグレーション（広げる段だけのはず）、フラグ、`legal.*`、設定の表の変更がないか。

## 対処

1. **フラグで戻せるなら先に戻す**（`release.*` を 0%）。
2. **サービス**：新しい組への重みを 0 にし、タスクを止める（自動のロールバックと同じ操作）。Worker は 1 つ前のタスクの定義に戻す。`ledger`・`reconcilers`・`deadline-runner` は単独で戻し、照合を回す。
3. **マイグレーションは戻さない。** 広げる段だけなので、前のイメージが今の DB で動く。縮める段を出した後は前へ戻さず、前へ直して出す。
4. **設定の表**：誤ったバージョンを消さない。新しいバージョンで直し、誤ったバージョンで作った見積もり・予約の一覧を出す（[delivery.md](../architecture/delivery.md) の 3.4 節）。
5. **`legal.*`**：承認の記録のある前の値に戻す PR を出し、平日の昼に適用する。過去の記録は書き換えない。
6. **ML のモデル・T&S の規則**：`models.*`・`rules.*` の `active_version` を 1 つ前に切り替える（デプロイなし）。

## エスカレーション

- 正しさの指標が出た：SEV1 として [incident-response.md](incident-response.md)。テックリードを呼ぶ。
- 凍結の中の修正（[README.md](README.md) の 3.1 節）：Ops の承認（作成者と別の人）。

## 事後

- ロールバックの理由を `deployments` に残す。自動のロールバックで止まらなかった誤りは、条件に足す。
- 原因を直す変更は、通常の段で出す（段の 30 分は Ops の判断で 10 分に縮めてよい）。
