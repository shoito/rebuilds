## この題材に固有の規則（開発リポジトリで守る）

### 本家の実装と名前

- **核を自前で作る。** 空室の判定（`stay_claims` と滞在の規則）、検索の候補の絞り込みと順位付け、料金の計算（`quoteStay`）、予約のステートマシン（`reserveStay`）、台帳、T&S の規則のエンジンと審査は自分で書く。本家のコード、本家が公開したライブラリ・ツール、本家の SDK・API のクライアント、本家から取り出したデータ・モデル・重みを、核にも依存にも使わない。本家の技術ブログやヘルプの考え方を読むのはよいが、設計の文書に出典を書く（[リポジトリ共通の ADR-0007](../../docs/decisions/0007-no-reuse-of-original-implementation.md)、ADR-0001）。
- **第三者の汎用の部品は、ADR に理由を書いた範囲でだけ使う。** 検索のエンジン（OpenSearch）と日本語の解析（Sudachi、ICU）、PostgreSQL の `btree_gist`、地図のタイルと住所の検索の提供者、機械学習の枠組み、決済の提供者、為替の相場の提供者、提携銀行と国際送金の提供者、eKYC の提供者、翻訳の提供者が当たる（ADR-0001、ADR-0003、ADR-0005、ADR-0008、ADR-0009）。
- **公開の標準には合わせてよい。** iCalendar（RFC 5545）の取り込みと書き出し、OAuth 2.0、ISO 4217、IANA の tz データベースは標準として受ける。
- **カード処理を設計し直さない。** カード情報の保管、アクワイアラへの接続は Stripe の題材の論点である。この題材は提供者の API を使う側として書く。台帳（預かり、手数料、ホストへの支払い、税の預かり、為替）は自前で設計する（ADR-0005）。
- **本家の名前を識別子に使わない。** ドメイン（`<brand>.<domain>`、写真の `img.<brand>.<domain>`、カレンダーの書き出しの `cal.<brand>.<domain>`）、HTTP ヘッダー（`X-<Brand>-Client`、`<Brand>-Signature`）、iCalendar の `PRODID`（`-//<Brand>//Calendar//EN`）と `UID`（`<id>@<brand>.<domain>`）、API のトークンの接頭辞（`<brand>_pms_`）、機能の名前（即時予約、料金の提案、ホストの保護の仕組み）は、`<Brand>`・`<brand>` か一般の言葉で書く（[リポジトリ共通の ADR-0006](../../docs/decisions/0006-brand-neutral-identifiers.md)）。

### 同じ夜を二度売らない

- **空室の正本は Aurora の `stay_claims` の行にする。** 予約・仮押さえ・予約のリクエスト・ホストのブロック・取り込んだ外部の予定は、どれも `stay_claims` の行として持つ。重なりは `EXCLUDE USING gist (listing_id WITH =, claim_group WITH <>, block_span WITH &&) WHERE (status = 'active')` の排他の制約で DB が拒む（同じ予約の組の行どうしは、日程の変更の間だけ重なってよい）。アプリの事前の確かめだけに頼らない（ADR-0002）。
- **日付は物件の現地の日付で持つ。** 泊は `daterange`（チェックインの日を含み、チェックアウトの日を含まない）で、時刻やタイムゾーンを持たない。チェックインの時刻・締め切り・期限は、物件の IANA のタイムゾーン（`listings.time_zone`）で現地の時刻から UTC の瞬間に直す。この計算は `packages/stay-time` の 1 か所に置く（ADR-0002）。
- **予約を作るのは `reserveStay` だけ。** 即時予約、予約のリクエストの承認、日程の変更、運用の代わりの予約のどれも、`reserveStay`・`alterReservation` を通す。別の経路で `stay_claims` の `reservation` の行を作らない（ADR-0004）。
- **検索の結果は約束ではない。** 検索の索引と Valkey の空室の写しは候補を絞るだけで、予約の判定は必ず DB の排他の制約と滞在の規則の関数（`checkStayRules`）で行う（ADR-0003）。

### 法令の上限

- **180 泊の上限は、予約と同じトランザクションで数える。** 住宅宿泊事業の届出住宅は、`regulated_properties` の行をロックし、`regulated_nights`（届出住宅 × 日）を挿入し、年度の数を CHECK 制約で守る。仮押さえと予約のリクエストも数える。後から数え直して超過を見つける方式にしない（ADR-0006）。
- **上限は物件（届出住宅）ごと。** 同じ届出住宅の複数のリスティング・部屋は、1 つの数を分け合う。同じ夜に 2 室が埋まっても 1 日と数える（ADR-0006）。
- **自治体の規則はデータにする。** 曜日・期間・区域の制限は、バージョンの付いた `municipal_rule_sets` で持ち、コードに自治体の名前を書かない。法令の解釈に当たる値（数え方、他の掲載先の泊の扱い）は `legal.*` に置き、法務の結論（[intent.md](docs/intent.md) の L1）まで本番の値を有効にしない。

### お金

- **お金の正本は追記だけの複式簿記の台帳にする。** 仕訳は通貨ごとに借方と貸方の和が一致しなければ書けない。残高は仕訳の和で、残高の列を直接書き換えない（ADR-0005）。
- **預かりは予約ごとに 1 回だけ決着する。** ホストへの支払いへの振り替え（release）、キャンセルの精算（settle）、全額の返金（refund）は、`(reservation_id, settlement_seq)` の一意の冪等キーで 1 回に限る。日程の変更は新しい `settlement_seq` の差分の仕訳で表す（ADR-0005）。
- **見せた額で請求する。** 予約の要求は `quote_id` を持ち、見積もりの写し（料金の規則・手数料・税・為替の相場の ID とバージョン）と金額が一致しなければ、予約を作らずに 409 を返す。見積もりの有効期限は 15 分（ADR-0004、ADR-0008）。
- **金額は通貨の最小単位の整数で持つ。** 浮動小数点を使わない。為替の換算と丸めは `packages/fx` の 1 か所で、見積もりにつき 1 回だけ行う（ADR-0008）。
- **キャンセルの返金は、予約の時のキャンセルポリシーのバージョンで計算する。** ポリシーの表を変えても、既存の予約の計算は変わらない（cancellations-and-changes の領域）。
- **カード番号を扱わない。** カード番号は提供者のホストした入力部品で受ける。本システムのサーバー・ログ・DB に、カード番号とセキュリティコードが入る経路を作らない（ADR-0005）。

### 個人のデータと可視性

- **正確な住所と位置は、確定した予約のゲストにだけ出す。** 検索・地図・リスティングの画面・メッセージの自動の文には、ずらした位置（`approx_point`）だけを使う。検索の索引にも正確な位置を入れない。地図の範囲を細かく変える問い合わせで位置を割り出せないようにする（location-and-geo の領域）。
- **見える範囲は DB と 1 つの関数で決める。** 本人だけの表は FORCE RLS と `SET LOCAL app.actor_id`、ホストの表はホストのアカウント（共同ホストを含む）の RLS、予約の表はゲストとホストのアカウントの 2 者の RLS にする。リスティングの公開の判定は `listingVisible(viewer, listing)` の 1 か所で行う（ADR-0007）。
- **宿泊者名簿と旅券の画像は金庫に閉じる。** 名簿の項目と旅券の画像は封筒の暗号化で持ち、ホストの名簿の画面と、法令の照会の手順からだけ読める。保存の期間と扱いは法務の L3・L8 の結論まで `legal.*` の値で持つ。
- **利用者のデータをログに出さない。** ログ・トレースに、住所、正確な位置、氏名、電話番号、メールアドレス、旅券の番号、本人確認の書類、メッセージの本文、検索の語、口座の番号を書かない。ID と数と理由のコードだけを書く。

### T&S と ML

- **ML の出力は信号であり、決定ではない。** 不正の点、パーティーの危険の点、偽のリスティングの点は、規則のエンジンの入力にする。予約の拒否、アカウントの停止、リスティングの停止は、規則のエンジンと人の審査が、根拠を `moderation_actions` に書いてから効かせる（ADR-0009）。
- **料金の提案は、ホストが決めた範囲でだけ効く。** 料金の提案は、ホストが有効にし、最低と最高の値を決めたときだけ、カレンダーの料金を書き換える。書き換えは主体 `pricing_suggestion` の通常のカレンダーの書き込みで、範囲の外の値を書けない（ADR-0009）。
- **差別をしない。** 順位付け・不正の点・パーティーの危険の点の特徴に、国籍・人種・宗教・性別などの保護される属性と、その代わりになる値（氏名、顔の写真）を使わない。予約の確定の前に、ホストにゲストの顔の写真を見せない（trust-and-safety の領域）。

### 運用と入力

- **空室・予約の状態・お金・法令の上限の規則をフラグにしない。** 排他の制約、滞在の規則、予約のステートマシン、仕訳の型、キャンセルの精算の計算はコードのバージョンとして出す。料金の規則の表、キャンセルポリシーの表、税の表、自治体の規則の表は、バージョンの付いた設定にする。
- **フラグの名前**：`release.*` は kebab-case（`release.flexible-dates`）、`ops.*` は snake_case（`ops.booking_enabled`）、`legal.*` は法務の結論を入れる値（`legal.minpaku_count_external_nights`）。`release.*` は 100% の後 30 日で消す。
- **外部のカレンダーは信用しない入力として扱う。** 取り込む iCalendar は、大きさ・件数・期間の上限、URL の許可（私的なアドレスへの接続を拒む）、文字の正規化を通してから `stay_claims` に入れる（calendar-sync の領域）。
- **テストに本物のデータを使わない。** 実在の利用者・リスティング・住所・旅券・メッセージ、本家から取り出したデータを、テスト・フィクスチャー・学習のデータに入れない。

## このリポジトリでの規則

- ADR を追加・更新したら、`docs/decisions/README.md` の一覧を生成し直す。
- 領域の文書で ADR を起票するときは、[architecture/README.md](docs/architecture/README.md) の 7 節で領域に割り当てた番号の範囲の中で採番する。
- 本家の振る舞い・数値を書くときは、出典と確認日を付ける。確かめられないものは「未検証」と書く。本家と違う振る舞いを選んだら、[architecture/README.md](docs/architecture/README.md) の 1.4 節の「本家との意図した違い」に行を足す。
- 他の題材の設計を参照し、設計し直さない。地理の格子と配車は Uber、空き時間・タイムゾーン・予約の排他の制約・ICS の購読は Google Calendar、預かり・台帳・T&S・評価は Mercari、決済・複数の通貨・送金は Stripe、熱い在庫と売上の確定の時期は Shopify にある（[architecture/README.md](docs/architecture/README.md) の 5 節）。
- 法令に関わる項目は、枠組みだけを書き、結論を書かない。「法務の確認待ち」と書き、[intent.md](docs/intent.md) の L の番号を付ける。
