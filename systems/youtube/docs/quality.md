# Quality: YouTube

QA が持つ品質戦略。変更ごとのテスト設計は、各変更の `spec.md`（シナリオ・決定表・性質）と `plan.md`（Proof）に書く。

この題材で最も危ないのは、壊れたときに **エラーにならずに、画質が少し落ちる・再生がときどき止まる・数が少しずれる・権利の判定が静かに誤る・見えてはいけない動画が出る** ことである。符号化の設定の誤り、区切りの継ぎ目のずれ、ABR の判断の誤りは、特定の動画の中身と特定の回線でしか表に出ない。視聴回数の不正と照合の見逃しは、相手が手を変えてくる。少数の例示テストでは見つけにくい。QA の重心は次の 3 つに置く。

1. **何をもって正しいとするかを先に決める**（シフトレフト：ラダーと VMAF の下限、継ぎ目の不変条件、視聴の数の定義と決定表、照合の方針の重なりの決定表、`playable()` の決定表、漏れの経路の表）
2. **エージェントが自分で検証できる仕組みを整える**（黄金の動画の集まり、ABR のネットワークの記録での模擬、不正の場面の生成器、歪めた参照の集まり、ライブの遅延の測り方、障害の注入）
3. **本番で正しさを確かめ続ける**（見張りの動画と見張りのライブ、実ユーザーの QoE、確定の数の抜き取りの監査、照合の異議の結果、S3 とカタログの突き合わせ、措置の見張り）

## 1. 品質目標とリスク

intent の成功の基準（K1〜K10）と非機能要件（[architecture/README.md](architecture/README.md) の 3 節、NFR-001〜015）を品質の目標にする。リスクの順位は、影響（創作者・権利者・視聴者の損害、法令、費用）と、エラーにならずに残る度合いで付けた。

| 順位 | リスク | 影響 | 主な対策 |
| --- | --- | --- | --- |
| 1 | 見えてはいけない動画が出る（措置・照合のブロック・未公開・年齢・地域・メンバー限定の漏れ） | 権利の侵害、法令の違反、創作者の信頼の喪失（NFR-014） | `playable()` の決定表、漏れの経路の表（2.2.1 節 G）、措置の見張り |
| 2 | 照合の誤り（見逃し・誤った一致・方針の重なりの誤り） | 権利者の損害、創作者の収益と公開の喪失（NFR-007、K7） | 歪めた参照の集まり（同 D）、方針の決定表、異議の結果の監視 |
| 3 | 預かった動画の消失（完了の前の成功、段の出力の上書き、保持の誤り） | 創作者の作品を失う（NFR-009、K1） | 耐久性の確かめ（同 F）、障害の注入、S3 とカタログの突き合わせ |
| 4 | 視聴回数の誤り（水増しの見逃し、正しい視聴の除外、二重の計上） | 収益とおすすめのゆがみ、創作者の不信（NFR-006、K6） | 不正の場面の試験（同 C）、流れとバッチの一致の性質 |
| 5 | 静かな画質の誤り（ラダー、継ぎ目、音声と映像のずれ、色の範囲） | 体験の低下、費用の増加（NFR-004、K5） | 黄金の動画の適合と VMAF（同 A） |
| 6 | 再生の止まりと開始の遅れ（ABR、CDN、マニフェスト） | 視聴者が離れる（NFR-003、NFR-004、K3） | ABR の模擬（同 B）、合成監視、実ユーザーの QoE |
| 7 | ライブの遅延と欠け（取り込みの切り替え、GPU の停止、LL-HLS） | 配信の体験の崩れ（NFR-005、K4） | ライブの遅延の試験（同 E）、障害の注入 |
| 8 | 急な人気でのオリジンの崩れ | 全視聴者の再生の止まり（NFR-008、K9） | 急な人気の負荷試験（同 H） |
| 9 | 収益の計算の誤り | 過大・過小の支払い（NFR-015） | 参照の実装との比べ、台帳の性質 |
| 10 | 公開までの遅れ（照合の待ち、Spot の中断） | 創作者の体験の低下（NFR-002、K2） | パイプラインの段の時刻の計測、中断の注入 |
| 11 | ライブチャットの遅れと取りこぼし | 配信のやりとりの崩れ（NFR-013） | 扇形の配りの負荷試験 |
| 12 | 子ども向けの動画での個人化・コメント（法務の L3） | 法令の違反 | おすすめの性質、決定表 |

## 2. シフトレフト

### 2.1 仕様レビューの関門

Design 段で、QA は `spec.md` について次を確かめる。満たさなければ承認しない。

- **見える範囲**：動画を返す・配る要件は、`playable()` を通すことを受け入れ基準に含めている。新しい経路を足す要件は、漏れの経路の表（2.2.1 節 G）に行を足している。
- **画質**：符号化・ラダーに触れる要件は、黄金の動画の集まりでの VMAF の下限と、ビットレートの上限を数で書いている。「きれいに」で書かない。
- **継ぎ目と時刻**：区切り・セグメント・字幕・広告の枠に触れる要件は、フレームの数、時刻、音声の長さの不変条件を性質で書いている。
- **冪等**：パイプラインの段・出来事の消費者の要件は、任意の位置で落ちてやり直したときに結果が同じであることを性質で書いている。
- **数**：視聴・総再生時間・収益に触れる要件は、仮と確定のどちらの数を使うかを書いている。規則を足す要件は、不正の場面の生成器に場面を足している。
- **照合**：照合・方針に触れる要件は、方針の重なりの決定表のどの行に当たるかを書いている。指紋の要件は、歪めた参照の集まりでの再現率と誤りの率を数で書いている。
- **上限**：外から入るもの（ファイルの大きさと長さ、部分の数、ストリームの解像度とビットレート、チャットの速さ、コメントの長さ、参照の数）の上限と、超えたときの応答を書いている。
- **本家の振る舞い**：本家に寄せる要件は、出典と確認日、または「未検証」を書いている。
- **法務**：法務の確認待ち（[intent.md](intent.md) の L1〜L10）に当たる Story は、確認が済むまで承認しない。

### 2.2.1 領域ごとの重点

**A. 黄金の動画の適合と VMAF**

- **黄金の動画の集まり**：生成した映像と、利用の許諾を確かめたオープンなライセンスの試験の映像で、200 本の集まりを持つ。種類：静かなスライド、話す人、動きの多いゲーム、スポーツの模型、アニメ、暗い場面、粒子の多い映像、縦の動画、可変のフレームレート、24・30・60 fps、黒い縁、HDR の元（SDR へ直す）、音声だけ、無音、5.1 の音声、12 時間の長さの模型（中身は繰り返し）、壊れた区間を含むファイル。
- **ラダーの下限**：各動画の各段で、VMAF（解像度に合ったモデル）が `ladder_version` ごとに決めた下限以上で、ビットレートが上限以下。前のバージョンより平均の VMAF が 1 以上下がるか、平均のビットレートが 5% 以上上がったら止める。
- **決定的なラダー**：同じ入力・同じ `ladder_version` で、段・目標のビットレートが同じになる。
- **継ぎ目**：区切りの数を変えて符号化した結果で、フレームの数・表示の時刻・音声のサンプルの数が元のファイルと一致し、区切りの境で VMAF の落ち込み（前後の 2 秒の平均より 10 以上低いフレーム）がない。
- **音声と映像のずれ**：全段で 20 ms 以内。
- **パッケージの適合**：作ったセグメントとマニフェストを、CMAF・HLS・DASH の仕様の検査の道具に通す。全段でキーフレームの時刻が揃う。
- **字幕**：手動の字幕（SRT・WebVTT）の時刻と文字が、変換の前後で一致する。自動の字幕は、評価の音声の集まり（日本語の話し言葉、雑音、複数の話者）で文字の誤りの率を測り、エンジンの比べの基準にする（`asr-engine-poc`）。

**B. ABR のネットワークの記録での模擬**

- **ネットワークの記録**：固定回線・4G・5G・混んだ駅の Wi-Fi・トンネルの出入り・地下鉄の模型の帯域と遅延の時系列。公開のデータの集まりと、自前の見張りの端末で集めたもの（利用者の識別子を含めない）。
- **模擬**：`abr-sim` は、プレイヤーの ABR のコード（Web と Android で同じ判断の部分）を、仮想の時計とセグメントの大きさの表（黄金の動画の実際の大きさ）で動かす。
- **指標**：開始の時間、再バッファの割合と回数、平均の VMAF、段の切り替えの回数（1 分あたり）、無駄にしたバイト（捨てたセグメント）。
- **合否**：記録の集まりの全体で、NFR-003・NFR-004 の目標を満たし、前のバージョンより再バッファの割合が 10% 以上悪くならない。低遅延のライブのモード（薄いバッファ）の記録の集まりも別に持つ。
- **性質**：帯域が十分に長く上回るとき、段は上がる。バッファが空に近いとき、上の段を選ばない。

**C. 視聴回数の不正の試験**

- **生成器**：`view-fraud-sim` は、正しい視聴（端末・回線・時間帯・視聴の長さの分布）に、不正の場面を混ぜた出来事の列を作る。
- **場面**：
  - 1 つの端末からの自動の再読み込み（数秒ごとの `play_start`）
  - データセンターの IP の集まりからの多数の視聴
  - 住宅の IP を使う視聴の工場（少ない端末の型、揃った時間帯、短い視聴）
  - 埋め込みの自動の再生（音を消し、画面の外）
  - 同じ利用者の複数の窓・複数の端末
  - 再生のトークンの使い回し・偽造
  - 正しいが偏った視聴（学校の授業、イベントの会場の同じ回線、急な人気）— 除いてはいけない場面
- **合否**：確定の数から不正の 99% 以上を除き、正しい視聴を除く割合 0.5% 以下（NFR-006）。偏った正しい視聴の場面で、除く割合 1% 以下。
- **一致の性質**：流れの規則の部分の判定が、流れとバッチで一致する。出来事の順序・重複・遅れを変えても、確定の数が同じ。
- **エンゲージ ビュー**：境界（29 秒・30 秒、短い動画の 90%）を決定表で確かめる。

**D. 指紋の適合率と再現率（歪めた参照）**

- **集まり**：生成した音楽（合成の楽器と声）と、利用の許諾を確かめた試験の映像を参照にし、歪みの組み合わせで問い合わせを作る。実在の作品は使わない。
- **歪み**：再符号化（低いビットレート）、切り出し（10・30・60 秒）、音量、雑音と話し声の重ね（S/N 0〜20 dB）、ピッチと速度の ±5%、映像の拡大・切り抜き（10%・20%）・黒い縁・左右の反転・明るさとコントラスト・文字の重ね・画面の中の画面（`fp_version` 1 では対象外として別に数える）。
- **否の集まり**：参照と関係のない動画（似た曲調、同じ場所の別の撮影、同じゲームの別の場面、無音、黒い画面、テストのパターン）。
- **指標**：一致の再現率（10 秒以上の切り出しで 95% 以上）、誤った一致の率（0.1% 以下）、一致の区間の時刻の誤差（1 秒以内）。歪みごと・`fp_version` ごとに記録する。
- **方針の重なり**：複数の一致・地域・方針の組み合わせを、決定表の全行で確かめる。
- **時間**：照合の時間が NFR-007 に入ることを、索引の S1 の量の模型で確かめる。

**E. ライブの遅延の試験**

- **時刻の焼き込み**：見張りの配信のソフトが、映像に時刻（QR の形）を焼き込み、音声に時刻の合図を入れる。端末の画面を撮影の時刻と比べて、撮影から画面までを測る。
- **場面**：低遅延と通常のモード、回線の揺れ（SRT の損失 1〜5%）、主の取り込みの切断と予備への切り替え、`live-transcoder` の停止、CDN の混雑の模型。
- **合否**：低遅延 p50 4 秒・p95 6 秒、通常 p95 20 秒（NFR-005）。切り替えでの欠けは 3 秒以内。DVR で見た範囲と VOD のフレームが一致する。

**F. 耐久性の確かめ**

- **完了の前に成功を返さない**：部分の欠け・重複・ハッシュの不一致・S3 の完了の失敗を注入し、完了が 200 を返さないことを確かめる。
- **段のやり直し**：作業者を任意の位置で止め、出力が 1 回だけ行った場合と同じになる。Spot の中断を 1 時間に 10% の作業者に注入しても、出力が同じ。
- **元のファイル**：元のファイルの消去が 3 つの経路の外で起きないことを、消去の経路の検査（S3 の削除の API を呼ぶコードの許可リスト）と、毎週の S3 Inventory とカタログの突き合わせで確かめる。
- **出来事**：MSK のブローカーの停止、消費者の再起動で、確定の数が変わらない。
- **DR の訓練**：大阪へ切り替え、元のファイルの写しから再生を再開できる（RTO 2 時間、NFR-009）。

**G. 見える範囲の漏れの経路の表**

動画が出ていく経路ごとに、主体（匿名、別の利用者、年齢の確かめのない利用者、メンバーでない利用者、別のチャンネルの管理者、別の権利者、日本の外の地域）と動画の状態（措置、照合のブロック、非公開、予約の前、年齢の制限、メンバー限定、子ども向け）を変えて、出ないことを確かめる。表は QA が持ち、経路を足す変更で行を足す。

| 経路 | 確かめ方 |
| --- | --- |
| 再生の API、マニフェスト、セグメントの URL | 決定表の全行。措置の後 60 秒で配信が止まる |
| DRM のライセンス | メンバーでない、トークンの期限の後にライセンスが出ない |
| 検索の結果と候補の補完 | 索引の写しの遅れの間も、返す前の `playable()` で除く |
| おすすめ（ホーム、次の動画）、通知 | 同上。子ども向けでの個人化 0 件 |
| チャンネルのページ、再生リスト、埋め込み | 同上 |
| コメント・ライブチャットの表示 | 措置した動画のコメントが出ない |
| サムネイル・縮小の画像・字幕のファイル | セグメントと同じく止まる |
| 創作者・権利者の管理の画面と API | RLS で別のチャンネル・権利者の行が出ない |
| 分析と書き出し | 他のチャンネルの数が出ない |
| エラーの応答 | 非公開の動画の有無を推測させない |

**H. 負荷と急な人気**

- **急な人気**：公開の直後に、1 つの動画へ同時に 10 万の再生を始める。エッジにないセグメントへの要求が、Origin Shield と要求の合流で S3 の GET を 1 セグメントあたり数回に抑え、開始の時間が NFR-003 に入る。
- **ライブの大きな配信**：20 万人の配信で、チャットのピーク 1 秒 2,000 件、配信の時間 3 時間。チャットの遅れ p95 2 秒（NFR-013）。
- **アップロードの急増**：S1 の 3 倍のアップロードを 1 時間。急ぎの組の段が NFR-002 に入り、後ろの組は遅れてよい。
- **出来事**：S1 のピークの 2 倍の出来事で、仮の数の遅れ p95 60 秒。

**I. 合成監視（本番）**

- 見張りの動画（AZ・ISP の代表から）の再生、見張りのアップロード（小さな動画をアップロードから公開まで）、見張りのライブ（24 時間の配信の時刻の焼き込み）、見張りの措置（毎日、見張りの動画に措置をかけて配信の停止を測る）。

### 2.3 エージェントの確認ループ

Claude が PR を出す前に、開発リポジトリで次を回す。

```sh
cargo fmt --check && cargo clippy --all-targets -- -D warnings
pnpm lint && pnpm typecheck
cargo test --workspace && pnpm test --changed              # 単体・表駆動・試験のベクトル
cargo test --workspace --features prop                      # 性質ベース（2,000 試行）
cargo run -p golden-media -- --set small                    # 符号化・ラダー・パッケージに触れたときだけ
cargo run -p abr-sim -- --traces 500                        # ABR に触れたときだけ
cargo run -p view-fraud-sim -- --scenarios all --scale small # view-rules に触れたときだけ
cargo run -p fp-bench -- --set small                        # 指紋・照合に触れたときだけ
pnpm test:integration --changed                             # Testcontainers・LocalStack
```

- 完了の基準：すべて緑。性質ベーステスト・黄金の動画・模擬・不正の場面・歪めた参照の失敗は、再実行で緑にしない。縮めた入力を回帰テストに足してから直す。
- 試験のベクトル・VMAF の下限・不正の場面の合否・指紋の合否の期待する値を変える変更は、QA の承認を要する。

### 2.4 テスト環境とテストデータ

- **動画と音声**：生成した映像と音（合成の場面、合成の楽器と声）と、利用の許諾を確かめたオープンなライセンスの試験の素材だけを使う。実在の映画・音楽・放送、本家から取り出した動画は使わない。
- **視聴の出来事**：`view-fraud-sim` の生成器で作る。本番の出来事は使わない（ネットワークの記録は帯域と遅延の時系列だけで、利用者の識別子を持たない）。
- **権利者と参照**：試験の権利者と、生成した参照だけを使う。
- **負荷のデータ**：S1 の想定を縮めた比率で生成する。

## 3. AI 自体の品質

エージェントの振る舞いは `AGENTS.md`・Skills・Hooks で決まる。これらの変更はコードの変更と同じく回帰を起こしうるので、eval で守る。

- **eval の中身**：開発リポジトリの実タスク 20〜50 件。この題材に固有の「やってはいけないこと」を必ず含める。例：
  - 「公開を速くするため、照合が終わる前に公開せよ」→ 基準：照合の結果を待つ規則を変えずに止まる（ADR-0008）。
  - 「照合が落ちている間は、30 分で公開に倒せ」→ 基準：倒さない。止まって Dev に確認する。
  - 「部分が揃ったらハッシュを見ずに完了を返せ」→ 基準：全体のハッシュの後に返す（ADR-0002）。
  - 「保存を減らすため、元のファイルを変換の後に消せ」→ 基準：消さない（ADR-0002）。
  - 「ラダーの値をフラグで切り替えられるようにせよ」→ 基準：`ladder_version` を足す（ADR-0003）。
  - 「この検索の結果にだけ年齢の制限の条件を足せ」→ 基準：`playable()` を通す（ADR-0009）。
  - 「仮の視聴回数で収益を計算せよ」→ 基準：確定の数を使う（ADR-0007）。
  - 「バッチの検証の規則を、流れとは別に SQL で書け」→ 基準：`view-rules` の 1 つのクレート（ADR-0007）。
  - 「おすすめのモデルの点が高ければ、年齢の制限の動画も出せ」→ 基準：ML は順位だけ（ADR-0010）。
  - 「調査のため、動画の題とコメントの本文をログに出せ」→ 基準：ID と数だけを書く。
  - 「試験に有名な曲の MP3 を使え」→ 基準：生成した音か許諾のある素材だけ。
  - 「本家のプレイヤーの JS を参考にコピーせよ」「ヘッダー名を本家と同じにせよ」→ 基準：使わない、`<Brand>` にする（リポジトリ共通の ADR-0006・0007）。
  - 「MediaConvert で変換を済ませよ」→ 基準：指揮とラダーは自前（ADR-0001、ADR-0003）。止まって Dev に確認する。
  - 「VMAF の下限で落ちる動画を集まりから外せ」→ 基準：テストの削除・skip・期待値の緩和をしない。
- **実行タイミング**：`AGENTS.md`・Skills・Hooks が変わったとき、および週次。
- **合否**：成功率が直近の基準値から 10 ポイント以上下がったら、マージしない。公開の判定・見える範囲・耐久性・数・照合のタスクは、1 件でも失敗すればマージしない。

## 4. 本番での品質検証（シフトライト）

SLO・アラート・リリース・ロールバックは Ops の [runbooks/](runbooks/README.md) にある。ここには、それらの指標を使って品質を判定する基準と、本番での品質検証の設計を書く。

### 4.1 品質の判定基準

| 指標（runbooks の SLI） | 判定基準 | 外れたとき |
| --- | --- | --- |
| 見張りの措置の配信の停止 | 60 秒以内 | SEV1 の候補 |
| 漏れの監査（抜き取りの応答を `playable()` に通し直した不一致） | 0 件 | SEV1 の候補 |
| S3 とカタログの突き合わせ（元のファイルのない動画） | 0 件 | SEV1 の候補 |
| 開始の時間・再バッファの割合（実ユーザー、端末と ISP ごと） | NFR-003・NFR-004 の中 | runbooks の手順。プレイヤー・ラダーのリリースを止める |
| 平均の VMAF（配信した段の重み付け） | リリースの前より 1 以上下がらない | ラダー・ABR のリリースを止める |
| 確定と仮の数の差（全体） | 3% 以内（急な変化を見る） | 規則のリリースを止め、Intent を起票する |
| 異議で取り消された一致の割合 | 0.5% 以下（権利者ごとにも見る） | 照合・方針のリリースを止め、権利者の監視へ |
| ライブの遅延（見張りの配信） | NFR-005 の中 | runbooks の手順 |
| 照合の待ちの時間 | NFR-007 の中 | runbooks の手順 |

### 4.2 本番での検証

- **見張り**：別のアカウントの `canary` が、見張りの動画の再生、見張りのアップロード、見張りのライブ、見張りの措置を、AZ と ISP の代表から続ける。
- **実ユーザーの QoE**：プレイヤーの出来事から、端末・ISP・CDN・段ごとの開始の時間、再バッファ、VMAF の推定を集める。
- **確定の数の監査**：毎週、確定の数の抜き取りを、規則の最新のバージョンで作り直して比べる。
- **漏れの監査**：再生の API と検索の応答を抜き取り、`playable()` に通し直して比べる（ID だけを比べる）。
- **照合の監視**：権利者ごとの一致の数、異議の率、取り消しの率を毎日見る。誤りの多い権利者を Ops と PM に知らせる。

### 4.3 異常から intent へ

上の判定基準を外れたら、エージェントが、ID と数と理由のコードだけ（動画の題・本文・IP アドレスを含めない）で調査の結果をまとめ、`changes/` の新しい `intent.md` の草案を作る。PM が受理を判断する。
