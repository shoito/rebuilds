# ADR-0069: 負荷のモデルは平常のピーク・大きな催し・急な人気の 3 つの重ねで作り、部品は平常のピークを 60% の使用で受け、AZ を 1 つ失っても催しのピークを 90% で受ける台数にする。負荷試験は CDN を通すものを 10% の規模、オリジンの部品は直接の模型で全規模にする

## Context

- [architecture/README.md](../architecture/README.md) の 2 節の S1 は、同時の視聴 15 万・配信 0.3 Tbps と、1 配信の最大 20 万人のライブを並べる。20 万人の LL-HLS は 0.6 Tbps・120 万件/秒（[live-streaming.md](../architecture/live-streaming.md) の 6.5 節）で、平常のピークより大きい。
- 急な人気（[cdn-and-delivery.md](../architecture/cdn-and-delivery.md) の 8 節）は量より同時の外れの形が問題になる。
- 自動の拡大は、再生の API の 1 分の急増、`origin-cache` のキャッシュの温まり、GPU の起動に間に合わない。
- CDN を通す全規模の試験（0.3 Tbps）は、転送の費用だけで 1 時間 約 8,000 USD（公開の価格）かかる。

## Options

1. **3 つの重ねのモデル、60%・90% の余裕、CDN は 10%・オリジンは全規模の試験**
2. S1 の表の値をそのまま 1 つのピークとして扱う
3. すべてを全規模で CDN を通して試験する

## Decision

1 を採用する。詳細は [capacity.md](../architecture/capacity.md) の 2・7・9 節。

- **重ね**：平常のピーク（夜、15 万・0.3 Tbps）、大きな催し（20 万人の LL-HLS を上乗せし、催しの日の山を 0.9 Tbps）、急な人気（1 動画へ 10 万の開始を 60 秒）。
- **余裕**：平常のピークで CPU・メモリー・ネットワーク・MSK・CDN の上限の使用を 60% 以下。AZ を 1 つ失った状態で催しのピークを 90% 以下（`origin-cache`、`live-origin`、Gateway、MSK、`match-engine`）。
- **常に持つもの**：再生の API（平常のピークの 2 倍）、急ぎの組の On-Demand の下限、GPU のキャパシティの予約の下限、`origin-cache`。Spot の群れには台数の上限を置く。
- **負荷試験**：E15 と段階を上げる前。CDN を通す VOD とライブは staging のディストリビューションで 10%（同時 1.5 万、2 万人の LL-HLS）。`origin-cache`（60 Gbps の外れ）と `live-origin`（20 万人の合流の後の要求）は直接の模型で全規模。急な人気、アップロードの急増（3 倍 × 1 時間）、出来事（2 倍）、チャット（20 万人・2,000 件/秒）、照合、再生の API を全規模。

### 他の案を選ばなかった理由

- **2（1 つのピーク）**：催しの日の 0.9 Tbps と 120 万件/秒を見落とし、CDN の上限の申請とライブの部品の台数が足りなくなる。
- **3（全規模の CDN）**：試験の費用が大きく、事業者への事前の連絡も要る（**未検証**）。オリジンの部品の振る舞いは直接の模型で全規模を確かめられる。

## Consequences

- 良くなること：
  - CDN の上限、GPU の予約、Gateway の台数を、催しの模型から前もって決められる。
  - 試験の費用を抑えつつ、オリジンの側を全規模で確かめる。
- 引き受けるコスト：
  - 常に持つ部品の空きの費用。
  - CDN の全規模の振る舞い（エッジの拠点の偏り）は本番の催しで初めて見える。

## Confirmation

- E15 の `load-tests` と `viral-spike-tests` の合否（[capacity.md](../architecture/capacity.md) の 9 節）。
- 大きな催しの 2 週間前の確認（`event-capacity-plan`）で、3.2 節の表を埋めて上限と台数を確かめる。
