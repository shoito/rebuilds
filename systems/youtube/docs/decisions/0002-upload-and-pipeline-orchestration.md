# ADR-0002: アップロードは S3 のマルチパートの上の自前の再開できるセッションにし、全体のハッシュが合ってから完了を返す。パイプラインは自前の段の状態の機械で、段は冪等にし、元のファイルを保持する

## Context

- 創作者は、数 GB〜256 GB、最長 12 時間のファイルを上げる（本家の上限。[Upload videos longer than 15 minutes](https://support.google.com/youtube/answer/71673)、2026-10-10 に確認）。家庭とモバイルの回線では、途中で何度も切れる。
- アップロードの後、検査、指紋と照合、ラダーの決定、複数の段の符号化、字幕、サムネイルを、決まった順序と並びで進める。どこかで落ちても、動画を失わず、最初からやり直さずに済ませたい。
- 公開までの時間（NFR-002）と、照合が終わるまで公開しない規則（[ADR-0008](0008-fingerprinting-and-match-engine.md)）を両立させる。
- X の題材は、短いメディアを S3 の署名つきの URL へ分割で直接上げ、MediaConvert で HLS にした（[X の media.md](../../../x/docs/architecture/media.md)）。長い動画では、セッションの期限・再開・段の多さが違う。

## Options

アップロード：

1. **自前のセッションの API（作成・部分・位置の問い合わせ・完了）。裏は S3 のマルチパートのアップロードで、部分は署名つきの URL へ直接送る**
2. tus のプロトコル（公開の仕様）のサーバーを置き、本体をサーバーで中継する
3. S3 のマルチパートの署名つきの URL を、クライアントの SDK にそのまま扱わせる（セッションの層なし）

パイプラインの指揮：

- a. **自前の段の状態の機械（Aurora の状態の行と SQS の作業の配り）**
- b. AWS Step Functions
- c. 汎用のワークフローのエンジン（Temporal など）

## Decision

1 と a を採用する。

### アップロードのセッション

- `POST /v1/uploads`（大きさ、MIME、任意の全体の SHA-256）→ `video_id`（UUIDv7）、`upload_id`、部分の大きさ（既定 16 MiB、回線に合わせて 8〜64 MiB）、期限（7 日）。
- 部分は、`upload-service` が出す署名つきの URL（部分ごと、15 分）へ直接 PUT する。本体はサーバーを通さない。部分ごとに `Content-MD5` を付け、S3 が確かめる。
- `GET /v1/uploads/{upload_id}` は、受け取り済みの部分の番号と ETag の一覧を返す（S3 の `ListParts` と自前の記録を突き合わせる）。クライアントはこれで続きから送る。
- `POST /v1/uploads/{upload_id}/complete` は、すべての部分が揃い、部分の ETag の並びが記録と合い、クライアントが全体の SHA-256 を出していればサーバーの計算と合ったときだけ、S3 の完了を行い、`video_upload_completed` を outbox に書いて 200 を返す。合わなければ 409 と、足りない・合わない部分の番号を返す。
- 期限を過ぎたセッションは、S3 の未完了のマルチパートを消す（ライフサイクルの規則と、自前の掃除の両方）。
- アプリは OS の背景の転送（iOS の背景の URL セッション、Android の WorkManager）で部分を送る。

> 2026-10-10 の注記：S3 はマルチパートで SHA-256 の全体の値を照合しない（全体のチェックサムは CRC64NVME・CRC32・CRC32C だけ）。[ADR-0011](0011-upload-session-protocol-and-checksums.md) で「全体の CRC64NVME を必須にし S3 に照合させる。SHA-256 は任意で、完了の前に読み直す」と具体にした。部分の署名つきの URL に `Content-MD5` と CRC64NVME を含める形は `presigned-part-checksum-poc` で確かめる。「全体のハッシュが合ってから完了を返す」は変えない。


### 段の状態の機械

| 段 | 入力 | 出力 | 並び |
| --- | --- | --- | --- |
| `probe` | 元のファイル | コンテナ・符号化・長さ・壊れた区間・既知の違法なメディアのハッシュの結果 | 最初 |
| `segment_plan` | `probe` | GOP に揃えた区切り（既定 20 秒）の一覧 | `probe` の後 |
| `fingerprint` | 元のファイル | 音声と映像の指紋（`fp_version`） | `segment_plan` と並べる |
| `match` | 指紋 | 一致と方針 | `fingerprint` の後 |
| `fast_encode` | 区切り | H.264 の 360p・720p | `segment_plan` の後 |
| `complexity` | 区切りの抜き取り | ラダー（`ladder_version`）| `fast_encode` と並べる |
| `publish_gate` | `fast_encode`、`match`、公開の設定 | 公開・ブロック・予約 | 両方の後 |
| `full_encode` | 区切り、ラダー | H.264 の全段 | `complexity` の後（公開を待たない） |
| `captions`、`thumbnails`、`storyboard` | 音声・区切り | 自動の字幕、サムネイル、シークの縮小の画像 | `probe` の後 |
| `av1_encode` | 区切り、ラダー | AV1 の全段 | 人気のしきい値の後（[ADR-0003](0003-codecs-and-per-title-ladder.md)） |

- 状態は Aurora の `pipeline_runs`（動画ごと）と `pipeline_tasks`（段・区切りごと）に持つ。遷移は条件つきの `UPDATE`（前の状態を条件に）で行う。
- 作業は段の種類と優先度ごとの SQS に出す。作業者は貸し出し（見えなくする時間）で受け、心拍で延ばす。落ちたら別の作業者が同じ作業を最初からやり直す。
- **段は冪等にする。** 出力の S3 のキーを（`video_id`、段、入力のハッシュ、設定のバージョン、区切りの番号）から決め、同じ作業を 2 回しても同じキーに同じ中身を書く。出力の確定は、Aurora の行の遷移を 1 回だけ成功させることで行う。
- 区切りの符号化の継ぎ目（区切りの境のフレームの数、時刻、音声の連続）を、`full_encode` の後の `stitch_check` で確かめる。合わなければその区切りだけをやり直す。
- 優先度：`fast_encode`・`fingerprint`・`match` は急ぎの組（On-Demand の小さなプールも使う）。`full_encode`・`captions` は通常の組。`av1_encode` と作り直しは後ろの組（Spot だけ）。

### 元のファイルの保持

- 元のファイルを、動画が残る間は保持する。新しいコーデック・ラダー・指紋のバージョンで作り直すために要る。公開の後 90 日で Glacier Deep Archive へ移す（[architecture/README.md](../architecture/README.md) の 2.1 節）。
- 消す経路は、創作者の削除（猶予の後）、保持の期限、法的な削除の手続きの 3 つだけにする。
- 大阪へは元のファイルを CRR で写す（レンディションは元のファイルから作り直せるので写さない。人気の動画のレンディションは S2 で写すかを infrastructure の領域で決める）。

> 2026-10-10 の注記：S1 から、熱い集まり（直近 7 日の確定の総再生時間の 90% を占める動画と、登録者 10 万以上のチャンネルの公開から 30 日の動画）の H.264 のレンディションも大阪へ写す（[ADR-0066](0066-osaka-dr-stage-up-and-multi-cdn-timing.md)）。全部を作り直していては再生の再開 RTO 2 時間を満たせないため。

### 他の案を選ばなかった理由

- **2（tus）**：本体をサーバーで中継すると、転送の費用とサーバーの帯域が重い。S3 の直接の PUT で足りる。プロトコルの形（位置の問い合わせ、期限）は参考にする。
- **3（セッションなし）**：完了の条件（全体のハッシュ）、期限、アプリの再開を、クライアントごとに作ることになる。
- **b（Step Functions）**：区切りごとの数百〜数千の作業の扇形の展開と、人気での後からの段の追加（数日後の AV1）を、状態の遷移の課金と上限の中で表しにくい。指揮は題材の核である。
- **c（Temporal など）**：成り立つが、新しい状態を持つ部品を運用することになる。Aurora の行と SQS で足りる。

## Consequences

- 良くなること：
  - 切れても受け取り済みの部分を送り直さない。本体がサーバーを通らない。
  - 段のどこで落ちても、その段から同じ結果でやり直せる。
  - 新しいコーデックやラダーを、元のファイルから後で足せる。
- 引き受けるコスト：
  - 元のファイルの保存の費用（1 時間あたり 3 GB）。
  - 状態の機械と作業の配りを自前で保守する。段を足すたびに状態の遷移の決定表を直す。

## Confirmation

- 性質ベーステスト：任意の部分の順序・重複・欠け・再送で、完了は「全部が揃い、ハッシュが合う」ときだけ成功する。
- 障害の注入：作業者を任意の位置（S3 の PUT の前後、行の遷移の前後）で止めても、出力が 1 回だけ行った場合と同じになる。
- 継ぎ目の検査：区切りの数を変えて符号化しても、フレームの数・時刻・音声の長さが元のファイルと合う（[quality.md](../quality.md)）。
- 状態の遷移の決定表の全行を、表駆動テストで確かめる。
