# ADR-0005: S1 は CloudFront と Origin Shield と自前の中間のキャッシュで配り、S2 から複数の CDN と計測による振り分けを足す。セグメントは署名つきの URL で、措置は拒否の一覧で 60 秒以内に止める

## Context

- 配信は原価の最も大きい部分で、S1 で月 27 PB、ピーク 0.3 Tbps、S2 でピーク 8 Tbps と見込む（[architecture/README.md](../architecture/README.md) の 2 節）。
- 視聴は少数の人気の動画に偏るが、保存の大部分はほとんど見られない動画（ロングテール）である。ロングテールのセグメントはエッジに残らず、オリジンの読み出しが増える。
- 急な人気（公開の直後や、外のサイトでの拡散）では、エッジにないセグメントへの要求が同時に集まる。
- 1 つの CDN の障害・混雑は、全視聴者の再生を止める。
- 措置・削除・ブロックの方針の後、キャッシュに残ったセグメントを配ってはいけない（NFR-014）。

## Options

1. **CloudFront（S1）→ 複数の CDN（S2）→ ISP の中の自前のキャッシュの検討（S3）。オリジンの前に Origin Shield と自前の中間のキャッシュ**
2. 最初から複数の CDN
3. 自前の CDN（エッジの拠点を持つ）
4. CloudFront だけを全段階で

## Decision

1 を採用する。

### 層

```
プレイヤー → CDN のエッジ → Origin Shield（東京）→ origin-cache（自前、NVMe、AZ ごと）→ S3
                                                   └→ manifest-service（マニフェスト）
```

- **CDN のエッジ**：セグメントは長くキャッシュする（1 年。URL は中身が変わらない）。マニフェストは短く（[ADR-0004](0004-cmaf-packaging-and-drm-scope.md)）。
- **Origin Shield**：エッジの外れを東京の 1 か所にまとめる。
- **`origin-cache`**：セグメントの URL を S3 の範囲の読み出しに直す。NVMe に最近のセグメントを持つ。同じセグメントへの同時の要求を 1 つの S3 の読み出しにまとめる（要求の合流）。人気の動画の最初のセグメントを、急な人気の兆しで先に読み込む（事前の配置）。
- キャッシュの外れの割合（バイト）の目標は 5% 以下（NFR-008）。

### 署名とアクセス

- セグメントとマニフェストの URL は、再生の API が出す短い期限（6 時間。ライブは配信の間）の署名つきの URL か、署名つきの cookie にする。署名の鍵は 2 つを並べて回す。
- 公開の動画のセグメントは、署名の確かめをエッジで行い、オリジンへは通さない。メンバー限定の動画は DRM で守る（[ADR-0004](0004-cmaf-packaging-and-drm-scope.md)）。
- 配信のドメインは `<brand>video.<domain>`（利用者の中身を管理の画面と別のドメインにする）。

### 措置と配信の停止

- 措置・削除・ブロックの方針の決定は、記録を書いた後に outbox で `delivery_block` を出す（[ADR-0009](0009-single-tenant-and-playable.md)）。
- エッジの関数（CloudFront Functions と KeyValueStore）の拒否の一覧に `video_id` を入れ、署名の確かめの後に一覧を引いて 403 を返す。X の題材の形（[X の ADR-0033](../../../x/docs/decisions/0033-media-delivery-and-takedown.md)）に寄せる。
- 同時に CDN の無効化を出し、再生の API とマニフェストも `playable()` で止める。決定から新しいセグメントの配信が止まるまで 60 秒以内（NFR-014）。
- 地域の制限（照合の方針の地域）は、再生の API とマニフェストで判定する。セグメントの URL の署名に地域を入れ、エッジで国の情報と照らす（日本の外は S1 の対象外なので、最小の形で持つ）。

### 複数の CDN（S2）

- 2 つ目の CDN を足し、プレイヤーの計測（開始の時間、再バッファ、スループット）を CDN ごと・ISP ごとに集め、振り分けの重みを 5 分ごとに決める。
- 振り分けは再生の API が CDN のホストを返す形にし（DNS の振り分けではなく）、プレイヤーはセグメントの失敗が続いたら他の CDN へ移る。
- 1 つの CDN の障害で 5 分以内に他へ移す（NFR-008）。
- 費用は CDN ごとの約定の量と単価で振り分けの上限を付ける。

### ISP の中のキャッシュ（S3 で検討）

- S3 の規模（ピーク 250 Tbps）では、ISP の網の中に自前のキャッシュの機器を置く形を検討する。人気の動画を夜間に先に置く。cdn-and-delivery の領域で、S2 の計測から判断の基準を決める。

### 他の案を選ばなかった理由

- **2（最初から複数）**：S1 の量では、振り分けの計測と、2 つの CDN の署名・拒否の一覧の運用が、得る可用性に見合わない。
- **3（自前の CDN）**：小さなチームの S1・S2 の範囲を超える。
- **4（CloudFront だけ）**：S2 以降で 1 つの事業者の障害と単価の交渉力に縛られる。

## Consequences

- 良くなること：
  - ロングテールのセグメントを、S3 の GET を増やさずに配れる。
  - 急な人気で、オリジンへの同時の読み出しを抑えられる。
  - 措置の後の配信を 60 秒以内に止められる。
- 引き受けるコスト：
  - `origin-cache` を運用する（NVMe のインスタンス、AZ ごと）。
  - S2 で振り分けの計測と、CDN ごとの署名・拒否の一覧・無効化の差を吸収する層が要る。

## Confirmation

- 合成監視：AZ ごと・ISP ごとに見張りの動画を再生し、開始の時間とセグメントの成功を測る。
- 措置の試験：見張りの動画に措置をかけ、エッジでの配信が 60 秒以内に止まることを、毎日確かめる。
- 急な人気の試験：公開の直後に同時に 10 万の再生を始める模型で、S3 の GET が要求の合流で抑えられることを確かめる（[quality.md](../quality.md)）。
