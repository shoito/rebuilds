# ADR-0071: 符号化器の組み立てを `enc_build` の番号に固定して段の出力のキーの設定のハッシュに入れ、上げても既存の動画は作り直さない。作り直しは欠陥の修正・新しいラダーの損益・各 ADR の条件の 3 つに限る。マニフェストの出力のバイトを変える変更は URL の `mf` を上げ、2 つ前の `mf` まで作れるままにする

## Context

- [ADR-0003](0003-codecs-and-per-title-ladder.md) は `ladder_version` でラダーの段・ビットレート・符号化の設定を固定した。FFmpeg のライブラリ・x264・SVT-AV1・libvmaf のバージョンと組み立ての旗、命令セットは、同じ設定でも出力を変えうるが、固定の仕組みが決まっていない。
- 段の出力のキーは（`video_id`、段、入力のハッシュ、設定のハッシュ）から決まり、最初の書き込みを採る（[ADR-0014](0014-pipeline-task-leases-and-idempotent-outputs.md)）。組み立てが違う出力が同じキーに書かれると、どちらが残るかが決まらない。
- 全動画の作り直しは、元のファイルの多くが Deep Archive にあり（戻し 12〜48 時間、アカウントに 1 日 1〜2 PB）、費用も大きい（[infrastructure.md](../architecture/infrastructure.md) の 6.2・11.3 節）。
- マニフェストは能力の組ごとに CDN で 1 時間キャッシュされ、利用者の間で共有される（[ADR-0020](0020-manifest-generation-and-capability-classes.md)）。生成のコードを変えると、同じ URL に古い中身と新しい中身が混ざる。古いアプリは新しいタグを読めないことがある。
- 形式とラダーと規則はフラグにしない（AGENTS.md）。

## Options

符号化器：

1. **`enc_build` の番号で固定し、設定のハッシュに入れる。上げても作り直さず、作り直しは決めた 3 つに限る**
2. 作業者のイメージのバージョンに任せる（番号を持たない）
3. `enc_build` を上げるたびに全動画を作り直す

マニフェスト：

- a. **URL に `mf` を入れ、2 つ前まで作れる**
- b. 生成のコードを変えたら、マニフェストの cache tag を全部無効にする

## Decision

1 と a を採用する。詳細は [delivery.md](../architecture/delivery.md) の 6 節。

- `enc_build` は、FFmpeg のライブラリのバージョンとコミットと組み立ての旗（許す復号器の一覧を含む）、x264 のコミット、SVT-AV1 のバージョン、libvmaf のバージョンと VMAF のモデル、命令セットの組、作業者の殻のバージョンを含む。`enc_builds` に記録し、`renditions` に `enc_build` を持つ。
- 上げるとき：黄金の動画の全集まりで、前との差（平均の VMAF ±0.5、平均のビットレート ±2%、継ぎ目と決定性が全部通る）を確かめ、QA が新しい試験のベクトルを承認する。出力のバイトが変わらない復号の側だけの修正は、上げずに出してよい。
- 作り直し：(1) 欠陥の修正は、欠陥のある `enc_build`・`ladder_version` で作り条件に当たるものだけ、視聴の多い順。(2) 新しい `ladder_version` は、配信の節約が作り直しの費用を 90 日で上回る動画だけ。(3) 各 ADR の条件（AV1 など）。Deep Archive の戻しは大量にし、1 日の戻しをアカウントの上限の 30% までにする。`reencode_campaigns` に量と費用を記録する。
- マニフェスト：URL に `mf` を入れる（`/t/{token}/m/{mf}/...`）。出力のバイトを変える変更（`EXT-X-VERSION`、タグの追加、段の並びの規則、DASH の profile）で `mf` を上げる。`manifest-service` は今と 2 つ前までを作れる。再生の API はデプロイのバージョンの既定の `mf` を返す（フラグではない）。読む側を端末の試験で確かめてから出し、古いアプリが読めない変更は `min_supported` を先に上げる（[ADR-0070](0070-ci-cd-golden-media-gates-and-player-rollout.md)）。

### 他の案を選ばなかった理由

- **2（番号なし）**：どの組み立てで作ったかが記録に残らず、欠陥の影響の範囲を引けない。違う組み立ての出力が同じキーに混ざる。
- **3（全部作り直し）**：Deep Archive の戻しと符号化の費用が、得る画質に見合わない。見られない動画の作り直しは無駄になる。
- **b（全部無効にする）**：無効にした直後に全マニフェストの外れが集まる。古いアプリが新しい形を受けて壊れる。

## Consequences

- 良くなること：
  - 欠陥の影響の範囲を記録から引き、必要な動画だけを作り直せる。
  - 符号化器の更新が、既存の動画の作り直しを伴わない。
  - マニフェストの形式の変更を、キャッシュの混ざりなく、前のバージョンへ数分で戻せる。
- 引き受けるコスト：
  - 動画ごとに違う `enc_build` のレンディションが混ざる（同じ動画の中は世代でそろう）。
  - マニフェストの URL の形の変更を packaging-and-drm の担当と合わせる（[packaging-and-drm.md](../architecture/packaging-and-drm.md) の 4.4 節）。

## Confirmation

- PROP-DLV-001（`cfg_hash` が違えば出力のキーが違う）、PROP-DLV-002（同じ `mf` の URL の応答はどのバージョンでも同じバイト）、PROP-DLV-003（作り直しの対象の選び方）。
- 試験のベクトル：`enc_build` ごとの黄金の動画の出力のハッシュ、`mf` ごとのマニフェストの黄金の出力。
