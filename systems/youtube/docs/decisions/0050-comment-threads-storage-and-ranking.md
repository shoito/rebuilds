# ADR-0050: コメントは最上位と返信の 2 段の木にし、Aurora の `comments` を `video_id` のハッシュで 16 に分ける。「評価順」は高評価・返信した人・創作者のハートと経過時間の式で付け、上位 2,000 の候補を Valkey に持つ

## Context

- コメントは動画ごとに読まれ、人気の動画には数十万件が付く。投稿は p99 500 ms（NFR-013）。
- 深い木は画面で読みにくく、並べ方と措置の後始末が複雑になる。本家の木の深さは公式の資料で確かめられなかった（**未検証**）。
- 「評価順」は、古くて高評価の多いコメントが永く先頭を占めないようにしたい。

## Options

木：

1. **2 段（返信への返信は最上位の下に並べ、返信先の利用者を持つ）**
2. 任意の深さの木

並べ方の置き場：

- a. **点の候補を Valkey のソート済みの集合に持ち、正本は Aurora**
- b. 読み出しの度に Aurora で点を計算する

## Decision

1 と a を採用する。詳細は [comments-and-moderation.md](../architecture/comments-and-moderation.md) の 4・5 節。

- 木：`parent_id` は最上位の ID だけ。返信への返信は `reply_to_user_id` を持つ。最上位の下の返信は 500 件まで。返信は古い順。
- 保存：`comments` を `video_id` のハッシュで 16 に分け、主キー `(video_id, comment_id)`、UUIDv7。数は Valkey に積み 1 分ごとに書き戻す。
- 評価順：`(likes + 2 · distinct_repliers + 10 · creator_heart + 1) / (age_hours + 2)^0.8`。スパムの点が 0.5〜0.95 の作者は 0.3 倍。ピン留めが先頭。候補は `ct:{video_id}` に上位 2,000、2,000 件より後は新しい順。
- 係数は本システムの値で、A/B で決め直す。

### 他の案を選ばなかった理由

- **2（任意の深さ）**：画面と API が複雑になり、措置で枝ごと隠す判定が要る。動画のコメントの使われ方に見合わない。
- **b（毎回 Aurora）**：人気の動画で 1 回の読み出しに数十万行の点の計算が要る。

## Consequences

- 良くなること：
  - 人気の動画でも評価順の最初のページを Valkey の 1 回の読み出しで返せる。
  - 返信の扱いが単純で、措置の後始末が行の状態だけで済む。
- 引き受けるコスト：
  - Valkey を失うと評価順の候補を作り直すまで新しい順に近い並びになる。
  - 深い議論は 1 つの最上位の下に平らに並ぶ。

## Confirmation

- PROP-CMT-001・004。
- 結合テスト：Valkey の喪失の後、Aurora から `ct:` を作り直して同じ並びになる。
