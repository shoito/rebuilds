# ADR-0007: 視聴回数は、流れの中の仮の数と、Parquet のバッチで確かめる確定の数の 2 段で出す。検証の規則は 1 つのクレートに置く。公開の数は再生の開始で数え、収益はエンゲージ ビュー（30 秒）で数える

## Context

- 視聴回数は、創作者の収益、収益化の条件、広告の値段、おすすめ、人気のランキング、AV1 に上げる時機（[ADR-0003](0003-codecs-and-per-title-ladder.md)）を決める。水増しされると、全部がゆがむ。
- 本家は 2026-08-24 から、Shorts・長い動画・ライブの視聴を、再生の開始で数える。人の視聴であることを確かめるのに時間がかかり、数を遅らせ・止め・直すことがある。複数の端末・窓での同じ動画の再生など、質の低い再生を除く。収益は「エンゲージ ビュー」と「エンゲージ視聴時間」で決まる（[How video views are counted](https://support.google.com/youtube/answer/2991785)、2026-10-10 に確認）。エンゲージ ビューのしきい値と、検証の規則の中身は公開されていない（**未検証**）。
- 創作者は、公開の直後に数が動くことを見たい。正しさのための検証（端末と回線の集団の偏り、視聴の工場の型）は、多くの出来事を集めてからでないとできない。
- 量：S1 でピーク 5,000 件/秒、S3 で 500 万件/秒（[architecture/README.md](../architecture/README.md) の 2 節）。

## Options

1. **2 段：流れの中の仮の数（明らかなものだけ除く）と、遅れたバッチの確定の数。規則は 1 つのクレートを両方で使う**
2. 流れの中だけで判定し、数を確定させる
3. バッチだけで判定し、確定するまで数を見せない
4. 流れとバッチで別々に規則を書く（ラムダ型の典型）

## Decision

1 を採用する。

### 出来事

- プレイヤーは、再生の API が出した再生のトークン（`video_id`、視聴者、端末の識別子のハッシュ、時刻、署名。10 時間の期限）を付けて、次を送る：`play_start`（最初のフレームの描画）、心拍（最初の 1 分は 10 秒ごと、その後 30 秒ごと。再生した区間）、`seek`、`quality_change`、`rebuffer`、`ad_*`、`end`。
- `event-collector` は、署名と期限を確かめ、IP アドレスを粗くした値（/24、/48）と ASN を足し、MSK の `watch-events`（`video_id` でパーティション）に書く。IP アドレスの生の値は、流れの中の判定（1 時間）の後に捨てる（保持は法務の L5）。

### 数の定義

| 数 | 定義 | 使い道 |
| --- | --- | --- |
| 視聴（公開の数） | 有効な `play_start`。同じ視聴者（ログインしていれば利用者、していなければ端末の識別子）と同じ動画の組で、24 時間に数える回数に上限（既定 4 回）を置く | 公開の視聴回数、人気の順位 |
| エンゲージ ビュー | 有効な視聴のうち、30 秒以上（30 秒未満の動画は 90% 以上）再生したもの。30 秒は本システムの値 | 収益の分配、収益化の条件、AV1 の時機 |
| 総再生時間 | 心拍の区間の和（同じ区間の重なりを 1 回にし、速度の倍率で割り戻さない） | 分析、収益化の条件 |
| 維持率 | 動画の時刻ごとの、再生した視聴の割合 | 分析 |

### 2 段の判定

- **仮の段（`view-validator`）**：`view-rules` の「流れの規則」（署名、重複の出来事、同じ組の上限、明らかなボットの端末の型、速すぎる繰り返し、データセンターの ASN）で判定し、Valkey に動画ごとの仮の数を積む。公開の数に p95 60 秒で出す（NFR-006）。
- **確定の段（`view-verifier`）**：出来事は 5 分ごとに S3 の Parquet（Iceberg の表）にまとまる。1 時間ごとと 1 日ごとに、`view-rules` の全部の規則（流れの規則に加え、端末・ASN・時間帯の集団の偏り、視聴の工場の型、埋め込みの自動の再生、ボットの点、広告の無効なトラフィック）で判定し、確定の数を Aurora に書く。確定は 24 時間以内（p99）。
- **公開の数** = 確定した時間までの確定の数 ＋ それより後の仮の数。確定の数が仮の数より少なければ、数は減る。減った数と理由のコード（規則の ID）を `view_adjustments` に記録し、創作者の分析で見せる。
- **同じ規則**：`view-rules` は Rust のクレート 1 つで、流れの判定（1 件ずつ）とバッチの判定（DataFusion の上の集団の計算）の両方で使う。規則には ID とバージョンを付け、確定の行に使った規則のバージョンを持つ。
- **再計算**：規則を変えたら、過去 30 日の確定の数を新しいバージョンで作り直せる（Parquet から）。収益の締めた月は作り直さず、調整の行で直す（monetization-and-payouts の領域）。

### 収益と公開の数の分け方

- 収益の分配、収益化の条件、AV1 の時機、人気の順位の確定は、確定の数だけを使う。
- 仮の数は、公開の数の表示と、急な人気の検知（[ADR-0005](0005-cdn-and-origin-strategy.md)）だけに使う。

### 他の案を選ばなかった理由

- **2（流れだけ）**：集団の偏りと視聴の工場の型は、1 件ずつでは見えない。
- **3（バッチだけ）**：公開の直後に数が動かず、創作者の体験が悪い。急な人気の検知にも使えない。
- **4（別々の規則）**：2 つの経路で判定がずれ、仮の数と確定の数の差が規則の違いから生まれる。どちらが正しいか確かめられない。

## Consequences

- 良くなること：
  - 公開の直後に数が動き、正しさは後から確かめられる。
  - 規則の変更を過去の出来事で再生して確かめられる。
- 引き受けるコスト：
  - 公開の数が減ることがあり、創作者に説明が要る（画面の文言と調整の記録）。
  - 出来事の保存（S3 の Parquet。S1 で約 1.2 億件/日）と、MSK の運用。

## Confirmation

- 不正の試験：生成した不正の場面（ボット、視聴の工場、自動の再読み込み、埋め込みの自動の再生、複数の窓）を正しい視聴に混ぜ、確定の数から 99% 以上を除き、正しい視聴を除く割合 0.5% 以下（NFR-006、[quality.md](../quality.md)）。
- 一致の性質：同じ出来事の集まりを、流れとバッチで判定したとき、流れの規則の部分の結果が一致する。
- 再生の試験：出来事を任意の順・重複・遅れで流しても、確定の数が同じになる。
