# ADR-0029: ライブの変換は GPU のプールに配信を詰めて置き、AZ ごとに空きを「GPU 2 枚か 10% の大きいほう」持つ。予想の視聴が 1 万を超える配信には別の AZ に同時に動く予備を置く。セグメントの番号と IDR の位置は入力の時刻から決める

## Context

- [ADR-0006](0006-live-ingest-and-latency.md) は、配信ごとに 1 つの `live-transcoder`（GPU、NVENC の H.264）を割り当て、予備を別の AZ に用意すると決めた。予備の形（同時に動かすか、空きで受けるか）は決めていない。
- GPU 1 枚（L4）で 1080p のラダーを 6 配信と見込む（[architecture/README.md](../architecture/README.md) の 2.1 節）。すべての配信に同時に動く予備を置くと、GPU が 2 倍要る。
- 視聴の多い配信の欠けは影響が大きい。小さな配信の数秒の欠けは許せる。
- 2 つの変換器の出力を切り替えるには、セグメントの番号と境が同じでないといけない。

## Options

1. **空きで受ける（小さな配信）＋同時に動く予備（大きな配信）。番号と IDR は入力の時刻から決める**
2. すべての配信に同時に動く予備
3. 予備を持たず、空きで受けるだけ

## Decision

1 を採用する。詳細は [live-streaming.md](../architecture/live-streaming.md) の 6.1・6.2 節。

- 配信を空きのある GPU に詰めて置く。AZ ごとの空きは「GPU 2 枚か、使っている枚数の 10% の大きいほう」。
- 予想の視聴が 1 万を超える配信（登録者 10 万以上のチャンネル、または視聴が 1 万を超えた時点から）には、別の AZ で同じ入力から同時に作る予備を置く。`live-origin` は主の停止で次のセグメントの境から予備に切り替える。
- 予備のない配信の変換器が止まったら、空きの GPU に新しい変換器を置き、`live-ingest` の入力のバッファから直前のセグメントの境で作り直す。
- `msn = floor((入力の時刻 − 配信の開始の時刻) / 2 秒)`。IDR は入力の時刻が 2 秒の倍数を越えた最初のフレーム。全段で同じ。
- 低遅延のモードは B フレームなし・先読みなし。
- 2 つの変換器の SPS・PPS が同じかは**未検証**。違えば切り替えで `EXT-X-DISCONTINUITY` を入れる（`ll-hls-poc`）。

### 他の案を選ばなかった理由

- **2（すべてに予備）**：S1 のピーク（2,000 配信）で GPU が約 334 枚から約 668 枚になる。小さな配信の欠けに見合わない。
- **3（予備なし）**：20 万人の配信で、変換器の停止のたびに数秒の欠けと、全視聴者のプレイヤーのやり直しが起きる。

## Consequences

- 良くなること：
  - GPU の費用を、空きの 10% と大きな配信の予備だけに抑える。
  - 番号が入力の時刻だけで決まり、変換器の入れ替えで番号が飛ばない。
- 引き受けるコスト：
  - AZ の 1 つ分の再配置には空きが足りない。AZ の停止では小さな配信の戻しが遅れる。
  - 大きな配信の判定（予想の視聴）が外れると、予備なしで大きくなる。視聴が 1 万を超えた時点で予備を足す。

## Confirmation

- 性質ベーステスト：PROP-LIVE-001。
- 障害の注入：予備あり・なしの配信で変換器を止め、欠け 3 秒以内（[quality.md](../quality.md) の 2.2.1 節 E）。
- `ll-hls-poc`：GPU 1 枚の配信の数、SPS の一致。
