# Runbook: 急な人気（バイラル）

- Owner: Ops
- 対応するアラート: 1 つの動画の仮の数の急な上がり、同時の視聴が 5 万を超えた、キャッシュの外れの急増、外のサイトからの参照の急増
- 最終確認日: 2026-10-10

設計は [cdn-and-delivery.md](../architecture/cdn-and-delivery.md) の 6・8 節、[capacity.md](../architecture/capacity.md) の 3 節、[ADR-0026](../decisions/0026-origin-cache-routing-admission-and-coalescing.md)、[ADR-0016](../decisions/0016-av1-promotion-rule-and-cost.md)。

## 症状

- 公開の直後や外のサイトでの拡散で、1 つの動画へ数万〜10 万の再生が数分で始まる。
- エッジにないセグメントの外れが `origin-cache` と S3 に集まる（キャッシュの群れ）。
- 再生の API と出来事の受け口に急増が来る。

## 影響

開始の時間（NFR-003）とキャッシュの外れ（NFR-008）。オリジンが詰まると、他の動画の外れの応答も遅れる。

## 確認

1. `origin-cache` の要求の合流の割合、S3 の GET の数（1 セグメントあたり 3 回以下が目安）と 503、外れの応答の p95。
2. 開始の時間（その動画と全体）、再生の API の p99 と 5xx。
3. 出来事：その動画の分割の消費の遅れ（`view-validator`）。
4. ライブなら、`live-origin` の保留の要求の数と、`live` のディストリビューションの上限の使用の割合。

## 対処

1. **自動の備えが動いたか**（`viral-prewarm`）：3 つの AZ の輪に H.264 の上位 4 段と音声の最初の 8 セグメントを読み込む。`av1_encode` が後ろの組の先頭に上がる（仮の数で始めた AV1 は取り消さない）。動いていなければ手で出す。
2. **`origin-cache` を増やす**：NVMe の温まりに時間がかかるので早めに。rendezvous のハッシュで動く鍵は増やしたノードの分だけ。
3. **再生の API**：平常のピークの 2 倍を常に持っている。足りなければタスクを足す。
4. **オリジンが詰まりそう**：その動画の最上段をマニフェストから一時に外す（画質を下げて配信を守る）。`release.*` のフラグではなく、運用の記録つきの手順で行い、戻す時刻を決める。
5. **出来事**：分割の遅れが続けば、その動画を熱い動画の桶（`vh:{video_id}`）にする（[view-counting-and-analytics.md](../architecture/view-counting-and-analytics.md) の 4.3 節）。
6. **ライブの急な人気**：チャットの低速モードを強制し、上位のチャットに切り替える。`live-transcoder` の同時の予備があるかを確かめ、なければ足す。`live` の上限が足りなければ [cdn-incident.md](cdn-incident.md) の 5。

## エスカレーション

- 他の動画の開始の時間まで悪化した：SEV2。Ops の責任者。
- `live` の上限に届きそう：AWS のサポート。PM に大きな配信の通常のモードへの切り替えを知らせる。

## 事後

- 急な人気は不正の場面と似ることがある。24 時間後に、確定の段で正しい視聴を除いていないか（`view_adjustments` の B01・B02 の量）を確かめる。
- 事前の配置のきっかけと量の見直しを `changes/` の `intent.md` に起票する。
