# Runbook: インシデントへの対応（全般）

- Owner: Ops
- 対応するアラート: 個別の手順のないアラートの全部。SEV の判断、連絡、振り返り
- 最終確認日: 2026-10-10

SLO とアラートの一覧は [README.md](README.md) の 1・4 節、計測は [observability.md](../architecture/observability.md)、運用者の権限は [security.md](../architecture/security.md) の 8 節にある。

## 症状

- 呼び出し（page）かチケットが来たが、[README.md](README.md) の 4 節の手順が「計画」のままである。
- 複数のアラートが同時に出て、どの手順から入るか分からない。

## 影響

アラートによる。配信と再生の API の停止は、全視聴者に数分で見える。措置の停止の遅れ、漏れの監査の不一致、元のファイルの消失は、エラーにならずに権利と信頼を損なう。

## 確認

1. **範囲**：全体か、1 つの AZ か、1 つの ISP か、1 つの動画・配信か、1 つの面（配信・パイプライン・ライブ・数・照合）か。大阪の `selfmon` の Grafana の配信・パイプライン・ライブのダッシュボードで見る。
2. **正しさ**：措置の停止、漏れの監査、ストレージの突き合わせに 0 でない値があるか。あれば SEV1・SEV2 の候補で、可用性より先に扱う。
3. **直近の変更**：デプロイ（作業者のプール、`manifest-service`、エッジの関数）、AppConfig のフラグ、`ladder_version`・`fp_version`・`ruleset_version`・`mf` の更新、CloudFront の設定。
4. **外からの見張り**：`canary`（東京・大阪の EC2 と見張りの端末 6 拠点）の再生・措置・ライブの結果。本番の計測が止まっていても、`canary` は大阪から呼び出す。

### SEV の目安

| SEV | 例 |
| --- | --- |
| SEV1 | 措置・照合のブロック・非公開の動画の配信（漏れの監査の不一致）、完了を返した元のファイルの消失、照合を待たない公開、全体の再生の停止 |
| SEV2 | 措置の停止が 120 秒を超えた、CDN の 1 つの地域・ISP の停止、20 万人級の配信の停止、照合の待ちの溜まり（30 分超）、リージョンの障害の兆し |
| SEV3 | 1 つの ISP の再バッファの悪化、仮の数の遅れ、通知の遅れ、検索の遅れ |

## 対処

1. **IC を決める**（SEV1・SEV2）。IC は判断と連絡、別の人が作業する。記録の場を開く。
2. **被害を止める**（原因の調査より先）：
   - 漏れ・措置の遅れ：[takedown-propagation.md](takedown-propagation.md)。拒否の鍵とパスの無効化を手で足す。
   - デプロイの直後：まずフラグで戻し、次に 1 つ前のイメージへ（[deploy-and-rollback.md](deploy-and-rollback.md)）。
   - 消失の疑い：消去の作業を止める（`ops.retention_delete_enabled` を切る）。S3 の古いバージョン（30 日）から戻せることを確かめる。
   - 受け付けの急増・障害：`ops.upload_enabled`・`ops.live_ingest_enabled` で新しい受け付けを止める。止めても受け取り済みの部分と配信中のライブは残る。
   - 照合の停止：公開に倒さない。`ops.publish_gate_enabled` は止めるだけで、公開に倒すスイッチはない。
3. **個別の手順へ**：原因の領域が分かったら、[README.md](README.md) の 4 節の手順に移る。手順が「計画」なら、この手順で続け、足りなかったことを記録する。
4. **創作者・視聴者への知らせ**：状況のページで、影響と時間を知らせる。動画の題・利用者の名前を書かない。
5. **回復の確かめ**：SLI が SLO に戻り、漏れの監査とストレージの突き合わせをやり直して 0 を確かめる。

## エスカレーション

- SEV1：Ops の責任者、Dev のテックリード、PM。漏れ・権利の侵害の疑いは法務（法務の確認待ち：L1）。
- CDN・AWS の障害：事業者・AWS のサポートへ。
- 1 時間で被害を止められない：Ops の責任者が、大阪への切り替え（[disaster-recovery.md](disaster-recovery.md)）を含めて判断する。

## 事後

- SEV1・SEV2 は 5 営業日の中で振り返りを書く（時刻の並び、検知までの時間、止めるまでの時間、失った範囲、根の原因、直すこと）。ID と数と理由のコードだけを書く。
- 調査結果を `changes/` の新しい `intent.md` として起票する（Maintain 段）。
- この手順と、[README.md](README.md) の 4 節の計画の手順で足りなかったことを反映する。
