## この題材に固有の規則（開発リポジトリで守る）

### 本家の実装と名前

- **時系列の保存のエンジン（TSDB）、ログの保存と検索、トレースの組み立て、モニターの評価のエンジンを自前で作る。** 本家のエージェント・ライブラリ・SDK のコード、本家の内部の保存の形式を、核にも依存にも使わない。本家の技術ブログの考え方を読むのはよいが、設計の文書に出典を書く。Kafka（MSK）、S3、Aurora は、核の外の汎用の部品として ADR に理由を書いた範囲でだけ使う（[リポジトリ共通の ADR-0007](../../docs/decisions/0007-no-reuse-of-original-implementation.md)、ADR-0001、ADR-0002）。
- **公開の標準には合わせてよい。** OTLP、W3C Trace Context、StatsD の形式（タグの拡張を含む）、OpenTelemetry の指数のヒストグラムは、プロトコルとして受ける。互換は振る舞いであって、実装の再利用ではない。
- **本家の名前を識別子に使わない。** ドメイン（`app.<brand>.<domain>`、`intake.<brand>.<domain>`）、HTTP ヘッダー（`<Brand>-Api-Key`、`<Brand>-Application-Key`、`<Brand>-Signature`）、キーの接頭辞（`<brand>_ik_`、`<brand>_ak_`）、エージェントの名前（`<brand>-agent`）、自社の指標の名前空間（`<brand>.`）、`tracestate` のキー（`<brand>`）は `<Brand>`・`<brand>` で書く（[リポジトリ共通の ADR-0006](../../docs/decisions/0006-brand-neutral-identifiers.md)）。

### 受け取ったデータを失わない

- **202 を返すのは、取り込みのログ（MSK）が書き込みを確定してからにする。** `acks=all`、`min.insync.replicas=2` の確定の前に成功を返さない。確定できなければ 503 か 429 を返し、エージェントに送り直させる（ADR-0002）。
- **取り込みのログが WAL である。** インジェスターは、S3 に置いたブロックと、そこまでのオフセットを同じ記録で確定する。オフセットを先に進めて、ブロックを後で書く順序にしない。読み直しで同じ点が二重に入っても結果が変わらないように、同じ系列・同じ時刻の点は「後に取り込んだもの」で決める（ADR-0004）。
- **圧縮は可逆にする。** 浮動小数点の値はビットで同じに戻す。コーデックは `codec_id` で固定し、変えるときは新しい ID を足す。古い ID の読み出しを消さない（ADR-0004）。
- **ロールアップは生の点から決まる値だけを持つ。** 合計・個数・最小・最大・最後の値と、分布のスケッチ。平均は合計と個数から求める。ロールアップどうしを平均して作らない（ADR-0004）。
- **遅れたデータの扱いを、受け付けの窓で決める。** メトリクスは過去 1 時間・未来 10 分、ログは過去 18 時間まで受ける。窓の外は拒み、拒んだ数を利用者に見せる。黙って捨てない（ADR-0004、ADR-0005）。

### テナントと分離

- **データの鍵の先頭に `tenant_id` を置く。** MSK のメッセージ、系列の鍵、ブロック・セグメントのパス、キャッシュの鍵、クエリの計画は、すべて `tenant_id` を持つ。`tenant_id` は認証の文脈からだけ取り、要求の本文やクエリの文字列から取らない（ADR-0003）。
- **管理の DB は FORCE RLS にする。** Aurora の表は `tenant_id` と `FORCE ROW LEVEL SECURITY`、`SET LOCAL app.tenant_id` で絞る。RLS の外の表は ADR-0003 の一覧だけにする。
- **データのアクセスの制限は、クエリの計画で必ず足す。** 役割に付いた制限（例：`team:payments`）は、クエリのコンパイラが AND の条件として足す。画面や API の側で条件を足さない。制限を外す経路を作らない（tenancy-and-rbac の領域）。
- **うるさい隣人を、取り込み・保存・クエリ・評価の各段で抑える。** テナントごとの割り当て（トークンバケット）、シャッフルシャーディング、重み付きの公平なキューを使う。1 つのテナントの急増で、他のテナントの SLO を消費させない（ADR-0003）。

### カーディナリティと費用

- **新しい系列には上限を付ける。** テナントと指標ごとの有効な系列の上限、新しい系列の作成の速さの上限を超えたら、系列を作らずに溢れの系列（`<brand>.cardinality_overflow:true`）へ数え、利用者に知らせる。上限を外す変更をコードで入れない。上限の値は運用のパラメーター（ADR-0006）。
- **利用量は取り込んだ時点で数える。** ホスト、カスタムメトリクス（指標の名前とタグの値の組）、ログの GB、スパンの GB の計測は、間引く前の量を、取り込みの段で数える。課金の数字を、サンプリングした値から推定しない（usage-and-billing の領域）。

### クエリとモニター

- **クエリは型付きの中間表現（IR）を通す。** クエリの言語、画面の組み立て、モニター、SLO、ダッシュボードは、同じ IR にコンパイルし、同じエンジンで実行する。経路ごとに別の集計のコードを書かない（ADR-0007）。
- **モニターの評価は決定的にする。** 評価は「モニターの定義のバージョン、入力のデータ、前の状態、評価の時刻」の純粋な関数にし、壁の時計・乱数・処理の順序に依らせない。状態の遷移には入力の写しを残し、再生で同じ結果になることを CI で確かめる（ADR-0008）。
- **本システムの遅れを、利用者の「データなし」にしない。** 取り込みの水位が評価の時刻に届くまで評価を待つ。待ちの上限を超えたら「不完全」として評価し、データなしの通知を出さない（ADR-0008）。

### 自己監視

- **本システムの監視を、本システムに頼らない。** 本番のアラートと呼び出しは、別の AWS アカウントの独立した経路（CloudWatch と Amazon Managed Service for Prometheus と、呼び出しのサービスへの直接の連携）で行う。自社のモニターのエンジンと通知の経路を、自社の障害の検知に使わない。社内の利用（ドッグフーディング）は、調査のためだけに使う（[runbooks/](docs/runbooks/README.md) の 5 節）。

### 運用と入力

- **利用者のデータをログに出さない。** 本システム自身のログ・トレースに、利用者のログの本文、タグの値、クエリの文字列、キーを書かない。ID と数と理由のコードだけを書く。
- **PII のマスクは取り込みの段で、索引と保存の前に行う。** マスクした後の値だけを、索引・保存・アーカイブ・ライブテールに流す。マスクの規則の変更は、過去のデータに遡らないことを利用者に示す（logs-pipeline の領域）。
- **保存の形式・圧縮・ロールアップ・評価の規則をフラグにしない。** `codec_id`、ブロックとセグメントの形式、ロールアップの定義、モニターの状態の遷移はコードのバージョンとして出す。`release.*` のフラグで経路ごとに切り替えない。
- **フラグの名前**：`release.*` は kebab-case（`release.log-rehydration`）、`ops.*` は snake_case（`ops.intake_enabled`）。`release.*` は 100% の後 30 日で消す。
- **テストに本物のデータを使わない。** 実在の組織のメトリクス・ログ・トレース、本家から書き出したデータを、テスト・フィクスチャー・シードに書かない。データは生成器で作る。

## このリポジトリでの規則

- ADR を追加・更新したら、`docs/decisions/README.md` の一覧を生成し直す。
- 領域の文書で ADR を起票するときは、[architecture/README.md](docs/architecture/README.md) の 7 節で領域に割り当てた番号の範囲の中で採番する。
- 本家の振る舞い・数値を書くときは、出典と確認日を付ける。確かめられないものは「未検証」と書く。本家と違う振る舞いを選んだら、[architecture/README.md](docs/architecture/README.md) の 1.4 節の「本家との意図した違い」に行を足す。
- 標準（OTLP、W3C Trace Context、OpenTelemetry のデータモデル）と本家の振る舞いが違うときは、両方を書き、本システムがどちらに寄せるかを明記する。
