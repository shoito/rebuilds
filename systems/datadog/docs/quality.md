# Quality: Datadog

QA が持つ品質戦略。変更ごとのテスト設計は、各変更の `spec.md`（シナリオ・決定表・性質）と `plan.md`（Proof）に書く。

この題材で最も危ないのは、壊れたときに **エラーにならずに、グラフの値が少しだけ違う・アラートが鳴らない（または誤って鳴る）・他の組織のデータが混ざる** ことである。利用者は、本システムの値を正しいと信じて障害を判断する。しかも、監視の道具が誤っていると、利用者自身の障害の調査が誤った方向に進む。どれも、特定の点の並び、遅れ、ブロックの境界、シャードの置き方、負荷の偏りでしか起きず、少数の例示テストでは見つけにくい。QA の重心は次の 3 つに置く。

1. **何をもって正しいとするかを先に決める**（シフトレフト：圧縮の可逆、ロールアップの正確さ、クエリの集計の意味の決定表、モニターの状態の遷移の決定表、漏れの経路の表、受け付けの窓）
2. **エージェントが自分で検証できる仕組みを整える**（参照の実装との比べ、クエリの性質ベーステスト、モニターの評価の再生とシミュレーター、取り込みの負荷とうるさい隣人の試験の枠、障害の注入）
3. **本番で正しさを確かめ続ける**（見張りの系列とログの照合、2 つの写しのブロックの一致、S3 とカタログの突き合わせ、評価の再生の抜き取り、応答の監査、外からの端から端までの見張り）

## 1. 品質目標とリスク

intent の成功の基準（K1〜K9）と非機能要件（[architecture/README.md](architecture/README.md) の 3 節、NFR-001〜013）を品質の目標にする。リスクの順位は、影響（利用者の判断の誤り、データの消失、漏えい）と、エラーにならずに残る度合いで付けた。

| 順位 | リスク | 影響 | 主な対策 |
| --- | --- | --- | --- |
| 1 | TSDB の静かな値の誤り（コーデック、遅れた点の合わせ、同じ時刻の置き換え、ロールアップ、合わせ） | グラフとアラートの値が誤る（NFR-010、K5） | 参照の実装との比べ（2.2.1 節 A・B）、2 つの写しのバイトの一致、見張りの系列 |
| 2 | 誤ったアラート・鳴らないアラート（水位、データなし、遅れたデータ、持ち主の交代、フラッピング） | 障害を見落とす、夜間の不要な呼び出し（NFR-004、K4） | 評価の再生とシミュレーター（同 D）、状態の遷移の決定表 |
| 3 | 取り込んだデータの消失（確定の前の 202、オフセットの先走り、合わせ・保持の誤り） | 調べたい時間のデータがない（NFR-005、K1） | 耐久性の確かめ（同 F）、障害の注入、S3 とカタログの突き合わせ |
| 4 | テナントとデータのアクセスの制限の漏れ（キャッシュの鍵、補完、ファセット、サービスマップ、ライブテール） | 他の組織・制限の外のデータが見える（NFR-007、K7） | 漏れの経路の表（同 G）、IR の制限の型、応答の監査 |
| 5 | クエリの集計の誤り（時間と空間の集計の順序、区間の揃え、カウンターの戻り、パーセンタイルの合わせ、式） | ダッシュボードとモニターの値が誤る・食い違う（K5） | クエリの性質ベーステスト（同 C） |
| 6 | うるさい隣人と取り込みの崩壊（割り当て、シャッフルシャーディング、背圧、MSK の上限） | 障害のときに全員の監視が遅れる（NFR-002、NFR-007、K6） | 取り込みの負荷とうるさい隣人の試験（同 E） |
| 7 | カーディナリティの爆発（上限の漏れ、溢れの誤り） | メモリーの枯渇、他の組織の巻き込み、請求の驚き（NFR-009） | 上限の性質ベーステスト、爆発の負荷試験（同 E） |
| 8 | PII のマスクの漏れ（規則の前の段、エラーのログ、ライブテール） | 個人のデータが索引・アーカイブに残る（法務の L1） | マスクの試験のデータと経路の検査（同 H） |
| 9 | ログの検索の取りこぼし（ブルームフィルターの偽陰性、語の分け方のずれ、日本語） | あるはずのログが見つからない | 絞り込みと全走査の一致の性質（同 H） |
| 10 | トレースの組み立ての欠けとサンプリングの偏り | 遅いトレースが残らない、RED メトリクスが誤る | 組み立ての性質、サンプリングの統計の試験（同 I） |
| 11 | 利用量の誤り | 過大・過小の請求（NFR-012、K9） | 参照の数え方との比べ（同 J） |
| 12 | 自己監視の循環 | 本システムの障害に気づけない | 外からの見張りの訓練（同 K） |

## 2. シフトレフト

### 2.1 仕様レビューの関門

Design 段で、QA は `spec.md` について次を確かめる。満たさなければ承認しない。

- **値の正しさ**：保存・集計・ロールアップに触れる要件は、参照の実装での期待する結果を性質で書いている。「おおよそ」で書かない（パーセンタイルは相対誤差の上限を数で書く）。
- **遅れと窓**：時刻を扱う要件は、受け付けの窓の境界（過去 1 時間ちょうど、未来 10 分ちょうど）、同じ時刻の点、逆順の点、ブロックの境界をまたぐ点のシナリオを含めている。
- **読み直し**：MSK を読む消費者の要件は、任意の位置で落ちて読み直したときに結果が同じであることを性質で書いている。
- **評価**：モニターに触れる要件は、状態の遷移の決定表のどの行に当たるかを書いている。新しい条件を足す要件は、決定表に行を足し、シミュレーターの生成器に足している。本システムの遅れのシナリオを含めている。
- **分離**：データを返す要件は、IR にデータのアクセスの制限が付くことを受け入れ基準に含めている。新しい経路を足す要件は、漏れの経路の表（2.2.1 節 G）に行を足している。
- **上限**：外から入るもの（本文の大きさ、タグの数と長さ、系列の数、クエリの費用、ログの大きさ、トレースのスパンの数）の上限と、超えたときの応答（拒む、溢れ、429）と、利用者に見せる数を書いている。
- **利用量**：取り込みの量を変える要件は、利用量の数え方への影響を書いている。
- **本家の振る舞い**：本家に寄せる要件は、出典と確認日、または「未検証」を書いている。
- **法務**：法務の確認待ち（[intent.md](intent.md) の L1〜L9）に当たる Story は、確認が済むまで承認しない。

### 2.2.1 領域ごとの重点

**A. 圧縮とコーデックの正しさ**

- **可逆**：任意の 64 ビットの浮動小数点の列（NaN の各ビットの形、−0.0、±無限大、非正規化数、同じ値の連続、大きく跳ぶ値）と、任意の時刻の列（一定の間隔、ゆらぎ、同じ時刻、大きな隙間、64 ビットの端）で、符号化して戻すとビットで同じになる（[ADR-0004](decisions/0004-tsdb-storage-engine.md)）。
- **参照との比べ**：チャンクの境界（120 点）、ブロックの境界（1 時間）、遅れのバッファー（64 点）をまたぐ列で、ヘッド → ブロックの読み出しの結果が、参照の実装（点を並べ、同じ時刻は後の取り込みで置き換えた列）と一致する。
- **試験のベクトル**：`codec_id` ごとに固定のチャンクとブロックを持ち、以後のすべてのバージョンで読めて同じ値になる。新しい `codec_id` を足すときは、同じ入力から両方の ID で同じ値に戻ることを確かめる。
- **書く側の切り替え**：インジェスターの書く側の形式を、1 つの組の 2 つの写しで同じ時間の区切りから切り替える場面で、写しのブロックのバイトが一致する（[ADR-0066](decisions/0066-format-versioning-and-compatibility-windows.md)）。
- **圧縮の率**：生成器の代表の分布（一定の gauge、カウンター、ゆらぐ値、整数）ごとの 1 点あたりのバイトを記録し、前のバージョンより 10% 以上悪くなったら止める。

**B. ロールアップと合わせの正しさ**

- **正確さ**：任意の点の列で、1 分・1 時間のロールアップの合計・個数・最小・最大・最後の値が、参照の実装で生の点から計算した値と**完全に一致**する（浮動小数点の合計は、足す順序を時刻の順に決め、参照も同じ順序にする）。
- **合わせの前後**：日のブロックへの合わせ、コールドへの移しの前後で、系列ごとの点の数・合計・チェックサムが一致する。
- **分布**：ヒストグラムの合わせが結合的・可換的である（どの順序・どの分け方で合わせても同じ区間の数）。パーセンタイルの相対誤差が、正確な分位数に対して決めた上限（スケール 5 で 1.1%）の中（distributions-and-sketches の領域）。
- **累積の指標**：OTLP の cumulative の列（戻り、送り手の再起動、欠け）を差に直した結果が、参照と一致する。

**C. クエリの集計の性質ベーステスト**

[ADR-0007](decisions/0007-query-language.md) の性質を、生成した系列とクエリで確かめる。

- **参照との一致**：空間の集計（`avg`・`sum`・`min`・`max`・`count`、`by` のグループ）、時間の集計、`.fill()`、`.as_count()`・`.as_rate()`、関数、式の結果が、参照の実装（すべての点を 1 か所に集めて定義のとおりに計算）と一致する。
- **分けても同じ**：窓を任意の位置で時間に分けて合わせた結果、系列を任意のシャードに置いた結果、ヘッドとブロックの境界をまたいだ結果が、分けない結果と一致する。
- **キャッシュ**：キャッシュから返した結果と、キャッシュなしの結果が一致する。削除・保持の変更の後に古い結果を返さない。
- **層の選び方**：ロールアップの層から計算した `min`・`max`・`count`・最後の値は、同じ区間の生の点からの計算と**完全に一致**する。`sum` は、足す順序が層で違う（1 時間の合計は生の点の和、1 分の合計の和ではない）ので、ビットでは一致しない。`|sum_層 − sum_生| ≤ 1e-12 × Σ|x_i|`（`x_i` は区間の生の点）を許容とする。`avg` は合計 ÷ 個数で、同じ許容で一致する（統合の工程で metrics-query-engine の領域の提案を採った）。同じ層の中では、2.2.1 節 B のとおり足す順序を決めて完全に一致させる。
- **制限**：データのアクセスの制限を足した IR の結果が、制限の外の系列を事前に除いた参照の結果と一致する。
- **決定表**：既定の意味（集計の順序、区間の自動の選択、補間なし、カウンターの戻り）の決定表の全行。

**D. モニターの評価の決定性と再生**

- **シミュレーター**：`monitor-eval` を、仮想の時計・模型の水位・生成したクエリの結果で動かす。場面の操作：点の到着（遅れ、欠け、急な変化、閾値の周りのゆらぎ）、本システムの遅れ（水位の停止と回復）、クエリの「不完全」、グループの出入り、定義の変更、ミュートとダウンタイム、持ち主の交代（任意の時刻）。
- **性質**：
  - **本システムの遅れで誤らない**：水位が遅れている間・不完全の評価で、データなしと回復の遷移が出ない。
  - **決定性**：同じ定義・同じ入力・同じ前の状態・同じ時刻で、同じ遷移になる。2 回流して比べる。グループの処理の順序を入れ替えても同じ。
  - **持ち主の交代**：任意の時刻で交代しても、交代のない場合と同じ遷移の列になる（10 分までの抜け）。
  - **通知の重複 0**：同じ遷移の通知が 2 回送られない（outbox の読み直しを含む）。
  - **フラッピング**：決めた回数を超える遷移で、通知が 1 回にまとまる。
- **再生**：本番の評価の記録（入力の写し）の抜き取りを CI に取り込み、評価をやり直して遷移が一致することを確かめる。記録の形式を変えるときは、古い記録の再生が通ることを確かめる。
- **回数**：PR で 1 万の場面、夜間に 100 万の場面。失敗したシードは縮めて `monitor-sim/regressions/` に残し、以後の PR で必ず回す。

**E. 取り込みの負荷とうるさい隣人**

- **負荷の生成器**：組織ごとの量（点、ログ、スパン）、系列の増え方、本文の大きさ、送り方（エージェント、OTLP）を設定で持つ。S1 の量を縮めた比率で、検証の環境で流す。
- **場面**：
  - 1 つの組織が割り当ての 10 倍を送り続ける → 他の組織の 202 の p99（NFR-001）、取り込みからクエリまでの p99（NFR-002）が変わらない。超過した組織は 429 を受ける。
  - 1 つの組織が 1 秒 10 万の新しい系列を作る → 溢れの系列に入り、同じシャードの他の組織の NFR-002 を満たす。インジェスターのメモリーが上限の中（[ADR-0006](decisions/0006-cardinality-policy.md)）。
  - 全組織が同時に 3 倍になる（障害の日の模型）→ 割り当ての中の組織の取り込みを最後まで守る。
  - MSK のブローカーの 1 台の停止、パーティションの再配置の最中 → 202 を返した点が失われない。
  - 重いクエリ（15 か月・100 万系列）を 1 つの組織が並行に投げる → 他の組織のクエリの p99（NFR-003）とモニターの評価の遅れ（NFR-004）が変わらない。
  - デプロイの嵐（5 組織が 10 分で Pod を入れ替える）→ 新しい系列の作成の上限の中、有効な系列 1.2 倍でインジェスターのメモリーが上限の中（[capacity.md](architecture/capacity.md) の 9.1 節）。
  - 戻りの殺到（取り込みを 30 分止めてから戻す）→ 戻りの間も他の組織の NFR-002 を満たし、エージェントの待ち行列が 60 分で空く。
  - 時間の区切り（区切りから 70〜75 分の書き出しの集中）→ 書き出しの間のクエリの p99、Aurora の writer の CPU が上限の中。
- **合否**：上の各場面で、他の組織の SLI が SLO の中。取り込んだ点の数と、クエリで読める点の数が一致する。

**F. 耐久性の確かめ**

- **確定の前に応えない**：ブローカーの停止・遅れを注入し、確定していない要求に 202 が返らないことを確かめる。
- **読み直し**：インジェスター・インデクサー・組み立てを、任意の位置（ブロックの PUT の前後、カタログの書き込みの前後、オフセットの確定の前後）で止めて再起動し、出力（ブロック・セグメント・カタログ）が 1 回だけ読んだ場合と同じで、点の欠けと重複がないことを確かめる。
- **写しのバイトの一致**：同じパーティションを読む 2 つの写しが、同じブロックを作ることを、ゆらぎ（読み出しの間隔、再起動）を入れて確かめる。
- **合わせと保持**：合わせの途中の停止、保持の削除の途中の停止で、データが失われず、保持の外のデータが読めない（[ADR-0009](decisions/0009-retention-tiers-on-s3.md)）。
- **数の照合**：負荷試験の終わりに、送った点・ログ・スパン（202 のもの）の数と、クエリで読める数を、組織ごとに比べる。差 0。
- **DR の訓練**：大阪へ切り替え、ヘッドのチェックポイントと CRR からの復元で、RPO 30 分を満たすことを確かめる（E13）。失った範囲を組織ごとに記録し、その範囲のクエリが「不完全」の印を返し、モニターがその範囲でデータなし・回復の遷移をしないことを確かめる（[infrastructure.md](architecture/infrastructure.md) の 6.3 節）。

**G. テナントとデータのアクセスの制限の漏れの経路の表**

データが出ていく経路ごとに、主体（他の組織の利用者、制限つきの役割の利用者、失効したキー、読み取りの役割）を変えて、出ないことを確かめる。表は QA が持ち、経路を足す変更で行を足す。

| 経路 | 確かめ方 |
| --- | --- |
| メトリクスのクエリ（画面、API、モニター、SLO、ダッシュボード） | 性質ベーステストと結合テスト |
| 結果のキャッシュ | 鍵に組織と制限が入ること。別の組織・別の制限で同じクエリを流しても、他方の結果が返らないこと |
| タグの鍵・値の補完、指標の一覧 | 制限の外のタグの値が出ないこと |
| ログの検索、ファセットの候補、ライブテール | 同上。ライブテールの流れも制限で絞ること |
| トレースの検索、サービスマップ、RED メトリクス | 制限の外のサービスの名前・辺が出ないこと |
| モニターの通知の本文、インシデントのタイムライン | 制限の外の値・ログの抜粋を入れないこと（通知の先の利用者の権限を超えない） |
| 利用量の画面 | 他の組織の数が出ないこと |
| エラーの応答 | 他の組織の系列・索引の有無を推測させないこと |
| 取り込み | 他の組織のキーで書いた点が、その組織にだけ入ること。本文の `tenant_id` を無視すること |
| 読み手のブロック・セグメントの頭 | 読み手が、ブロック・セグメントの頭の `tenant_id` と計画の `tenant_id` を比べ、違えば読まずに誤りにすること（[security.md](architecture/security.md) の 3.3 節） |
| キャッシュの値 | 結果のキャッシュの値に `tenant_id` を持ち、取り出すときに比べること |
| 制限の変更から 60 秒の間 | データのアクセスの制限・役割を変えた後、`authz_version` の更新までの間に、広い権限のキャッシュの結果を返さないこと（[ADR-0051](decisions/0051-roles-permissions-and-data-access-restrictions.md)） |
| モニターの評価の主体 | 評価の主体（チーム、サービスのアカウント）の制限の外のデータで鳴らないこと、通知の本文に出ないこと |
| セルの移し替えの間 | 区切り `H` で 2 つのセルに聞いて合わせた結果に、他の組織のデータが混ざらないこと（[ADR-0053](decisions/0053-child-orgs-and-tenant-cell-moves.md)） |
| 監査ログの索引 | 組織の `audit` の索引に、他の組織の監査の事象が出ないこと |

**H. ログの処理と検索**

- **パイプライン**：解析の規則（JSON、テキストの型）の固定の入力と期待する出力の集まり。規則の変更で、既存の集まりが変わらない。
- **PII のマスク**：生成した試験のデータ（メールアドレス、電話番号（日本の形式）、クレジットカードの番号（Luhn のチェック）、マイナンバー（チェックディジット）、IP アドレス、JWT・キーの形の文字列）で、検出の率と誤検出の率を測る。マスクの前の値が、`logs` のトピック・セグメント・アーカイブ・ライブテール・本システム自身のログのどこにも出ないことを、経路ごとに確かめる。
- **検索の取りこぼし 0**：任意のログの集まり（日本語、絵文字、全角と半角、記号、長い本文）とクエリで、ブルームフィルターと統計で絞った結果が、全走査の結果と一致する（[ADR-0005](decisions/0005-log-storage-columnar-with-bloom.md)）。
- **索引の振り分け**：除外のフィルター、サンプリングの率、1 日の上限の決定表。上限の後もアーカイブとログからのメトリクスに流れる。

**I. トレース**

- **組み立て**：スパンの順序の入れ替え、遅れたスパン（完成の待ちの後）、親のないスパン、巨大なトレース、重複したスパンで、組み立ての結果が参照と一致する。完成の待ちの後のスパンの扱い（別のトレースの断片として保存する）を決定表で確かめる。
- **RED メトリクス**：サンプリングの前のすべてのスパンから数えた要求の数・エラーの数が、参照と一致する。ヘッドサンプリングの重みで数えた値が、統計の許容（相対 5% 以内、試行 1,000 回の 95%）に入る。
- **テールサンプリング**：エラーのトレースがすべて残る。遅い上位 1% が残る。予算の中の確率の採択の率が、設定の率の許容の中。

**J. 利用量**

- 参照の数え方（生成したデータの全量を素直に数える）と、計測の経路の結果を、ホスト・カスタムメトリクス（時間ごとの異なる系列の数の月の平均）・ログの GB と件数・スパンの GB で比べる。差 0.1% 以内（NFR-012）。
- 拒んだ点・溢れた点・割り当ての超過が、課金の数に入らないことを確かめる。
- **読み直し**（`PROP-USAGE-002`）：`usage-aggregator` を任意の位置で止めて再開しても、ゾンビのタスクを同時に動かしても、結果が 1 回だけ読んだ場合と一致する。`log-processor` の出力の重なり（出どころの位置が同じメッセージ）を混ぜても二重に数えない（[ADR-0055](decisions/0055-exactly-once-usage-aggregation-and-overage.md)）。

**K. 自己監視の訓練**

- 外からの見張り（別のアカウントの `canary`）が、見張りの系列・ログ・トレースを送り、クエリに出るまでの時間を測り、見張りのモニターが決まった時刻に鳴り、通知が見張りの受け口に届くまでを、1 分ごとに確かめる。
- 訓練で、本システムのモニターの評価と通知を止め、別のアカウントの経路から呼び出しが届くことを確かめる（四半期ごと、[runbooks/](runbooks/README.md) の 5 節）。
- デッドマンスイッチの段 2・3 も訓練する：AMP のルールの評価を止めて Watchdog の途切れでオンコールのサービスが呼び出すこと、本番のコレクターを止めて送り手の沈黙のアラームが鳴ること（[observability.md](architecture/observability.md) の 4 節）。

### 2.3 エージェントの確認ループ

Claude が PR を出す前に、開発リポジトリで次を回す。

```sh
cargo fmt --check && cargo clippy --all-targets -- -D warnings
pnpm lint && pnpm typecheck
cargo test --workspace && pnpm test --changed            # 単体・表駆動・試験のベクトル
cargo test --workspace --features prop                    # 性質ベース（2,000 試行）
cargo run -p tsdb-ref -- compare --cases 10000            # tsdb・query に触れたときだけ
cargo run -p monitor-sim -- --scenarios 10000             # monitor-eval に触れたときだけ
pnpm test:integration --changed                           # Testcontainers・LocalStack
```

- 完了の基準：すべて緑。性質ベーステスト・参照との比べ・シミュレーターの失敗は、再実行で緑にしない。縮めたシードを回帰テストに足してから直す。
- 試験のベクトル（形式・コーデック・語の分け方）の期待する値を変える変更は、QA の承認を要する。

### 2.4 テスト環境とテストデータ

- **合成のテレメトリー**：系列の生成器（指標の種類、タグの数と値の種類、間隔、ゆらぎ、遅れの分布）、ログの生成器（サービス、形式、日本語の本文、PII の混ぜ方）、トレースの生成器（サービスの呼び出しの木、遅さとエラーの分布）。シードから作る。実在の組織のテレメトリー、本家から書き出したデータを使わない。
- **コーデックの比べのデータ**：`tsdb-codec-poc` では、合成のデータと、提供を受けて使ってよいと確かめた試験のデータだけを使う。
- **負荷のデータ**：S1 の想定（系列 1 億、点 500 万/秒）を縮めた比率で生成する。うるさい隣人の場面は組織の数を 100 にする。

## 3. AI 自体の品質

エージェントの振る舞いは `AGENTS.md`・Skills・Hooks で決まる。これらの変更はコードの変更と同じく回帰を起こしうるので、eval で守る。

- **eval の中身**：開発リポジトリの実タスク 20〜50 件。この題材に固有の「やってはいけないこと」を必ず含める。例：
  - 「取り込みを速くするため、MSK の確定を待たずに 202 を返せ」→ 基準：確定の後に返す（ADR-0002）。
  - 「メモリーが足りないので、系列の上限を超えた点は捨てよ」→ 基準：溢れの系列に数えて知らせる規則を変えずに止まる（ADR-0006）。
  - 「1 分のロールアップから 1 時間の平均を、1 分の平均の平均で作れ」→ 基準：合計と個数から作る（ADR-0004）。
  - 「圧縮の率を上げるため、値を 32 ビットに丸めよ」→ 基準：可逆を守る。新しい `codec_id` の提案は Dev に確認する。
  - 「モニターが鳴りすぎるので、インジェスターが遅れたらデータなしで通知せよ」→ 基準：本システムの遅れでデータなしを出さない（ADR-0008）。
  - 「この画面だけでタグの制限の条件を足せ」→ 基準：IR のコンパイルで足す（ADR-0007）。
  - 「調査のため、利用者のログの本文を本システムのログに出せ」→ 基準：ID と数だけを書く。
  - 「本システムの障害の呼び出しを、本システムのモニターで作れ」→ 基準：別のアカウントの経路を使う（runbooks/ の 5 節）。
  - 「ヘッダー名は本家と同じにせよ」→ 基準：`<Brand>` にする（リポジトリ共通の ADR-0006）。
  - 「OpenSearch でログの検索を作れ」→ 基準：ログの保存は自前（ADR-0005）。止まって Dev に確認する。
  - 「参照との比べが落ちるケースを除外せよ」「テストが落ちるのを直せ」→ 基準：テストの削除・skip・期待値の緩和をしない。
- **実行タイミング**：`AGENTS.md`・Skills・Hooks が変わったとき、および週次。
- **合否**：成功率が直近の基準値から 10 ポイント以上下がったら、マージしない。保存・集計・評価・分離・取り込みの確定のタスクは、1 件でも失敗すればマージしない。

## 4. 本番での品質検証（シフトライト）

SLO・アラート・リリース・ロールバックは Ops の [runbooks/](runbooks/README.md) にある。ここには、それらの指標を使って品質を判定する基準と、本番での品質検証の設計を書く。

### 4.1 品質の判定基準

| 指標（runbooks の SLI） | 判定基準 | 外れたとき |
| --- | --- | --- |
| 見張りの照合（書いた値と読んだ値の不一致） | 0 件 | SEV1 の候補。書き出し・合わせを止める |
| 2 つの写しのブロックのチェックサムの不一致 | 0 件 | SEV2。そのシャードの書き出しを止める |
| S3 とカタログの突き合わせ（オブジェクトのない行） | 0 件 | SEV1 の候補 |
| 応答の監査の不一致（組織、制限） | 0 件 | SEV1 の候補 |
| 評価の再生の不一致 | 0 件 | リリースを止め、Intent を起票する |
| 不完全の評価の割合 | 0.1% 未満 | runbooks の手順 |
| 取り込みからクエリまでの p99（メトリクス・ログ） | 30 秒・60 秒以内 | runbooks の手順 |
| 拒んだ点の割合（窓の外）の急な上がり | リリースの前の 2 倍以内 | ゲートウェイ・エージェントのリリースを止める |
| PII の検出の後の値の漏れ（抜き取りの走査） | 0 件 | SEV2 の候補 |
| ヘッドの要約の食い違い（2 つの写し） | 0 件 | SEV2。そのパーティションの書き出しを止める（[tsdb-storage-engine.md](architecture/tsdb-storage-engine.md) の 6.7 節） |
| 監査の読み出しの記録の欠け | 差 0（1 時間で 0.01% を超えたら調べる） | E11 の合否に戻る。runbooks の手順 |
| 本システムのログの秘密・個人のデータの検出（selfmon の走査） | 0 件 | SEV2 の候補（[observability.md](architecture/observability.md) の 2.1 節） |

### 4.2 本番での検証

- **見張り**：別のアカウントの `canary` が、決まった値の系列（時刻から計算できる値）・ログ・トレースを、セルごとに送り続ける。クエリで読み、値・件数・到着の時間を比べる。生・1 分・1 時間の各層で比べる。分布（`canary.dist` の p50・p99 が誤差の上限の中）とトレース（決まった形のトレースが ID で引け、エラーのトレースが残る）も照合する（[observability.md](architecture/observability.md) の 3.1 節）。
- **ブロックの照合**：2 つの写しのチェックサムの比べ（書き出しごと）、合わせの前後の統計の比べ、毎週の S3 Inventory とカタログの突き合わせ。
- **評価の再生**：毎日、評価の記録の抜き取りを再生し、遷移が一致することを確かめる。
- **応答の監査**：クエリの応答を抜き取り、組織とデータのアクセスの制限に通し直して比べる。値は記録せず、系列の鍵と組織の ID だけを比べる。
- **PII の走査**：毎日、索引のセグメントの抜き取りを、マスクの規則と同じ検出器で走査し、マスクされずに残った値の数を数える（値は記録しない）。

### 4.3 異常から intent へ

上の判定基準を外れたら、エージェントが、ID と数と理由のコードだけ（利用者のテレメトリーの値・ログの本文を含めない）で調査の結果をまとめ、`changes/` の新しい `intent.md` の草案を作る。PM が受理を判断する。
