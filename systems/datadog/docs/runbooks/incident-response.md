# Runbook: インシデントへの対応（共通の進め方と最初の切り分け）

- Owner: Ops
- 対応するアラート: 個別の手順のない呼び出しのアラート全部（[README.md](README.md) の 4 節）。見張りの照合・ストレージの突き合わせ・分離の不一致（SEV1 の候補）の最初の対応
- 最終確認日: 2026-10-09

## 共通の進め方

| 重さ | 目安 | 例 |
| --- | --- | --- |
| SEV1 | 202 を返したデータを失った疑い。他の組織・制限の外のデータが届いた疑い。多くの組織で取り込み・評価・通知が止まる | 見張りの照合の不一致、カタログの行に S3 のオブジェクトがない、応答の監査の不一致、リージョンの障害 |
| SEV2 | SLO を大きく消費する。値の正しさが崩れる恐れがあるが、データは残っている | ブロックの写しの不一致、ヘッドの要約の食い違い、取り込みからクエリまでの p99 が 2 分を超え続ける、評価の遅れ |
| SEV3 | 利用者の影響が小さい・迂回できる | 利用量の遅れ、1 つのチャネルの通知の失敗、エージェントの一部のバージョンの失敗 |

1. インシデントの指揮者（IC）を決め、チャンネルを作り、時刻を記録し始める。
2. **調査は selfmon のアカウントの Grafana から始める**（本番の画面や本システムのモニターに頼らない。[README.md](README.md) の 5 節）。社内の組織のダッシュボードは補助にだけ使う。
3. 影響の範囲を決める：セル、信号（メトリクス・ログ・トレース）、段（取り込み・保存・クエリ・評価・通知）、組織の数、期間。
4. 直前の変更を確かめる：デプロイ（データの面・管理の面・エージェントの配布）、フラグ（`release.*`・`ops.*`）、形式の書く側の切り替え、Terraform。疑わしければ [deploy-and-rollback.md](deploy-and-rollback.md) で戻す。形式・コーデック・評価の規則の不具合はフラグでなく前のイメージに戻す（[README.md](README.md) の 3 節）。
5. 被害を止める → 原因を取り除く → 回復を確かめる、の順に進める。値の誤り・消失の疑いがあれば、最初に `ops.compaction_enabled` と `ops.retention_delete_enabled` を止める（止めてもデータは失わない。古いブロック・セグメントが消えなくなるだけ）。
6. 利用者への告知は公表のページで行う。本システムの障害は「利用者の監視の欠け」なので、影響する信号・期間・「この間のデータなしのアラートは本システムの遅れの可能性」を書く。文言は法務の L7 の後に雛形を決める。分離の疑いと個人のデータの疑いは、法務と相談してから文面を決める（L1・L6）。
7. 調べるのは、ID と数と理由のコード（組織の ID、ブロック・セグメントの ID、パーティション、オフセット、件数）だけ。利用者のテレメトリーの値・ログの本文・タグの値を見る必要があれば、組織のサポートの許可・JIT・監査を通す（[security.md](../architecture/security.md) の 8 節）。
8. エージェント（AI）は本番に経路を持たない。調査の結果（ID と数）を人から受け取り、`changes/` の新しい `intent.md` の草案を作る。

## 場面 1：取り込みの SLO・202 の遅れ

### 症状

取り込みの可用性のバーンレート、202 の p99 が 1 秒を 10 分超える。

### 確認

1. NLB とゲートウェイの 5xx・時間切れの割合。AZ ごとか、全体か。
2. MSK の確定の遅れ（`acks=all` の p99）、ISR の縮み、Express の絞り。MSK が原因なら `msk-broker-incident.md`（予定）の内容で進める。
3. セルの混雑の段（[ADR-0012](../decisions/0012-intake-quota-coordination.md)）と、429 の急増が特定の組織か。特定の組織なら [noisy-neighbor.md](noisy-neighbor.md)。
4. キーの確かめの失敗（Aurora の reader、Valkey）の急増。

### 対処

1. 1 つの AZ が原因なら、その AZ の NLB のアドレスを DNS から外す。
2. 特定の組織の急増なら、割り当てを一時に下げる（記録つき）。
3. セルの全体が詰まっているなら、割り当てを超えている組織から 429 を返す段に上げる（混雑 2）。割り当ての中の組織は最後まで受ける。
4. 最後の手として `ops.intake_enabled` でセルの取り込みを止める（エージェントはディスクに 2 GB まで溜めて待つ。止めた時間を記録する）。

## 場面 2：見張りの照合・ストレージの突き合わせの不一致（SEV1 の候補）

### 症状

`canary` が書いた値と読んだ値が違う。カタログの行に S3 のオブジェクトがない。

### 確認と対処

1. `ops.compaction_enabled`・`ops.retention_delete_enabled` を止める。
2. どの層（生・1 分・1 時間）、どのセル・パーティション・時間か。ヘッド（直近）かブロックか。
3. ブロックなら、写しの比べ（`metric_block_verifications`）と合わせの前後の統計を見る。S3 の古いバージョン（7 日）から戻せるかを確かめる。
4. `data-integrity-incident.md`（予定）の担当と Dev のテックリードを呼ぶ。

## 場面 3：分離の疑い（応答の監査の不一致。SEV1 の候補）

### 確認と対処

1. 不一致の経路（クエリ、キャッシュ、補完、ファセット、サービスマップ、ライブテール、通知）、組織の ID、時刻を決める。
2. キャッシュが疑わしければ、関わる組織の `query_cache_generation` と `authz_version` を上げてキャッシュを捨てる（[tenancy-and-rbac.md](../architecture/tenancy-and-rbac.md) の 5.3 節）。
3. 直前のデプロイを戻す。`access-leak-response.md`（予定）の担当、セキュリティの担当、法務を呼ぶ。

## 場面 4：評価の遅れ・抜け・不完全の評価の急増

### 確認と対処

1. 水位の遅れか（インジェスター・インデクサーの消費の遅れ）、クエリの遅れ（評価の組の読み手）か、評価器のシャードの持ち主の交代か。
2. 水位の遅れなら、消費者の遅れを先に直す。評価は水位を待つので、遅れても誤ったデータなしは出ない（[ADR-0008](../decisions/0008-monitor-evaluation-model.md)）。
3. 抜け（10 分を超えて追わなかった時刻）は記録に残る。利用者への告知に、抜けの時間を書く。

## エスカレーション

- SEV1：Ops の責任者、Dev のテックリード、セキュリティの担当をすぐに呼ぶ。分離・個人のデータは法務も。
- データの消失・値の誤りの疑い：`data-integrity-incident.md`（予定）の担当とテックリード。
- リージョンの障害：[disaster-recovery.md](disaster-recovery.md)。
- 自己監視の経路の停止：[self-monitoring-path-failure.md](self-monitoring-path-failure.md)。
