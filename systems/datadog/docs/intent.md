# Intent: Datadog を AI エージェント主体で再構築する

- Author: shoito
- Status: draft
- Date: 2026-10-09

## Problem

日本の企業のシステムは、クラウドとコンテナとマネージドのサービスに分かれ、1 つの障害の原因が多くの部品にまたがる。運用の担当者と開発者は、次のところで困る。

- **道具が分かれている。** メトリクスは監視の道具、ログはログの基盤、トレースは APM の道具に分かれ、障害のときに時刻とホストとサービスを手で突き合わせる。
- **アラートが信用できない。** 閾値の監視が、データの遅れ・欠け・一時の揺れで誤って鳴る（フラッピング）。逆に、データが来なくなったことに気づかない。夜間の呼び出しの多くが対応の要らないものになり、本当の障害の呼び出しを見落とす。
- **量と費用が読めない。** コンテナの ID やリクエストの ID をタグに入れた途端に系列の数（カーディナリティ）が数百倍になり、保存の費用とクエリの速さが崩れる。ログは全部を索引に入れると高く、捨てると調べられない。
- **大きな利用者の急増が、周りを巻き込む。** 障害のときこそデータが急増するが、取り込みの基盤が詰まると、関係のない利用者のデータまで遅れ、監視が最も要るときに見えなくなる。
- **個人のデータと所在。** ログとトレースには、利用者の顧客の個人のデータ（メールアドレス、電話番号、IP アドレス）が混ざる。日本の企業は、データを国内に置き、取り込みの段で消す（マスクする）ことを求める。

本家 Datadog は、これらを大きな規模で解いている。エージェントと OTLP の取り込み、メトリクス（カスタムメトリクスと分布）、ログ（索引とアーカイブ、再水和）、APM（サンプリングと保持の規則）、モニター、ダッシュボード、SLO、インシデント管理を 1 つの製品で提供し、日本のサイト（AP1）を持つ（出典は末尾）。この題材では、これを日本の市場を最初の対象に、小さなチームと AI エージェントでどこまで作り直せるかを確かめる。核（時系列の保存のエンジン、ログの保存と検索、トレースの組み立て、モニターの評価のエンジン）は自分で設計する（[リポジトリ共通の ADR-0007](../../../docs/decisions/0007-no-reuse-of-original-implementation.md)）。

## Proposed outcome

利用者が、自社のシステムのメトリクス・ログ・トレースを 1 か所に送り、数十秒で調べられ、信用できるアラートで障害に気づける可観測性の SaaS を作る。次の 5 つの価値を満たす。

1. **受け取ったものを失わない**：取り込みが成功（202）を返したデータは、保持の期間の中で失わない（NFR-005）。遅れて届いたデータも、受け付けの窓の中なら正しく集計に入る（NFR-008）。
2. **すぐ見える**：メトリクスは受け取ってから p99 30 秒で、ログは p99 60 秒でクエリに出る（NFR-002）。ダッシュボードのウィジェットは p99 1 秒で返る（NFR-003）。
3. **アラートを信用できる**：モニターは同じ入力から同じ結果を出し、本システムの遅れで誤ってデータなしを鳴らさない。評価の遅れは p99 30 秒（NFR-004）。フラッピングを抑え、通知を重ねない。
4. **量と費用を制御できる**：系列の上限、索引に入れるログの選び方、トレースのサンプリングを利用者が決め、利用量を時間ごとに見られる（NFR-009、NFR-012）。
5. **隣の利用者に巻き込まれない**：あるテナントが割り当ての 10 倍のデータを送っても、他のテナントの取り込みとクエリの SLO を消費しない（NFR-007）。

### MVP（S1）に含める

- **取り込み**：自前のエージェント（Linux と Windows のホスト、Docker、Kubernetes。ホストとコンテナのメトリクス、ファイルのログの追跡、StatsD の受け口、OTLP の受け口）、OTLP（gRPC・HTTP）の直接の受け口、HTTP の API（メトリクス・ログ）、取り込みのキー、テナントごとの割り当てと背圧
- **メトリクス**：指標の名前とタグの組の時系列、gauge・count・rate・分布、自前の TSDB（圧縮、1 時間のブロック、1 分・1 時間のロールアップ、S3 の保持の層、15 か月の保持）、クエリの言語とエンジン（タグをまたぐ集計、時間の集計、関数、式）、パーセンタイル、カーディナリティの上限と、索引に入れるタグの選択
- **ログ**：パイプライン（JSON とテキストの解析、属性の付け替え、PII のマスク）、索引（除外のフィルター、1 日の上限、保持の期間）とアーカイブ（すべてのログ）、自前のログの保存と検索、ファセット、ライブテール、アーカイブからの再水和、ログから作るメトリクス
- **トレース**：OpenTelemetry の SDK と Collector からの OTLP のスパン（自前の言語ごとの SDK は持たない）、W3C Trace Context、ヘッドサンプリングとテールサンプリング、トレースの組み立て、サービスマップ、スパンから作る RED メトリクス（要求の数・エラー・所要時間）、トレースとログの結び付け
- **モニターとアラート**：メトリクス・ログ・APM・複合のモニター、データなしと遅れたデータの扱い、タグのグループごとのアラート（マルチアラート）、回復の閾値とフラッピングの抑え、再通知、ミュートとダウンタイム
- **通知と連携**：メール、チャット（Slack・Microsoft Teams の受信の Webhook）、汎用の Webhook（署名つき）、オンコールのサービス（PagerDuty・Opsgenie など）への連携
- **ダッシュボード**：時系列・数値・上位・表・ヒートマップ・ログの一覧のウィジェット、テンプレートの変数、ライブの更新、共有のリンク（組織の中）
- **SLO とインシデント**：メトリクスとモニターの SLO、エラーバジェット、バーンレートのアラート。軽いインシデント管理（宣言、重さ、担当、タイムライン、通知、振り返りの雛形）
- **テナントと権限**：組織、利用者、チーム、役割（管理者・標準・読み取り）と独自の役割、SSO（SAML・OIDC）と SCIM、タグによるデータのアクセスの制限、監査ログ
- **利用量の計測**：ホスト、カスタムメトリクス、ログ（取り込みの GB と索引の件数）、スパン（取り込みの GB と保持の件数）を時間ごとに数え、画面と API で見せる。課金の請求の仕組みは外部に渡す

### MVP の後の Epic で扱う

| 機能 | 理由 |
| --- | --- |
| ブラウザ・モバイルの RUM（実ユーザーの計測） | 利用者のサイトの閲覧者の端末から送る。電気通信事業法の外部送信規律と cookie の扱いを、法務の L4 で確かめてから設計する |
| 合成監視（Synthetics） | 外からの監視の拠点と、利用者の認証の情報の預かりの設計が要る |

| PromQL の互換のクエリ、Prometheus の remote write の受け口 | 標準ではないが広く使われる。MVP は自前のクエリの言語（[ADR-0007](decisions/0007-query-language.md)） |

| 履歴のメトリクスの取り込み（1 時間より古い点） | 書き出したブロックへの後からの合流（バックフィル）の設計が要る |
| プロファイリング、セキュリティの監視、データベースの監視 | 別の製品の論点 |
| 海外のリージョン | テナントをリージョンに固定する形で足す |

### 守るべき振る舞い

- 取り込みが 202 を返したデータは、保持の期間の中で、どのクエリからも同じ値で読める。圧縮とロールアップで値が変わらない（合計・個数・最小・最大は正確、パーセンタイルは決めた相対誤差の中）。
- 同じ系列・同じ時刻の点を 2 回送ると、後に取り込んだ値になる。取り込みのログの読み直しで、結果は変わらない。
- 受け付けの窓の外のデータ（メトリクスは過去 1 時間より古い・未来 10 分より先、ログは過去 18 時間より古い）は拒み、拒んだ数を利用者が見られる。黙って捨てない。
- クエリの結果は、データがどのシャード・どのブロック・どのキャッシュから来ても同じである。
- モニターは、同じ定義・同じ入力・同じ前の状態から、同じ状態の遷移と通知を出す。本システムの取り込みの遅れを、データなしとして通知しない。
- 利用者は、自分の組織のデータと、役割のデータのアクセスの制限の中のデータだけを見られる。キャッシュ・サービスマップ・候補の補完（タグの値の一覧）を含め、どの経路でも他の組織のデータの有無が分からない。
- 系列の上限を超えたデータは、溢れの系列に数え、利用者に知らせる。上限の超過で、他の系列のデータを失わない。
- PII のマスクの規則に当たる値は、索引・保存・アーカイブ・ライブテールのどこにもマスクの前の形で残らない。

## Affected users and systems

- **運用の担当者・SRE**（主な利用者）：日本の中堅・大企業、SaaS の事業者、ゲーム・EC・金融の事業者。オンコールで呼び出しを受け、ダッシュボードで調べる。
- **アプリケーションの開発者**：トレースとログでエラーと遅さを調べる。SDK や OpenTelemetry で計測を入れる。
- **組織の管理者**：利用者・役割・SSO・キー・データのアクセスの制限・利用量と費用を管理する。
- **財務・購買の担当**：利用量と請求を見る。
- **外部のシステム**：エージェントと OTLP の送り手（利用者のホスト、コンテナ、Kubernetes、OpenTelemetry Collector）、通知の先（メール、チャット、オンコールのサービス）、IdP（Microsoft Entra ID、Okta など）、課金のシステム。
- **社内の運用**：自社の障害の対応、利用者のサポート、開示の請求への対応。

## Constraints

- **核を自前で設計する。** TSDB、ログの保存と検索、トレースの組み立て、モニターの評価のエンジンは、自分で作る。本家のエージェント・ライブラリのコードと内部の形式を使わない。Kafka（Amazon MSK）、S3、Aurora は、核の外の汎用の部品として、理由を ADR に書いて使う（[リポジトリ共通の ADR-0007](../../../docs/decisions/0007-no-reuse-of-original-implementation.md)、[ADR-0001](decisions/0001-platform-and-stack.md)、[ADR-0002](decisions/0002-intake-log-on-msk.md)）。
- 実行基盤と技術は、rebuilds の他の題材の決定（AWS 東京・大阪、TypeScript・Hono、Aurora PostgreSQL、Valkey、S3、SQS・SNS、ECS Fargate、Terraform、OpenTelemetry、AppConfig のフラグ）を、管理の側（制御の面）で引き継ぐ。データの面（取り込み、保存、クエリ、評価）は、量が桁違いに多いので外れる。外れるところは [ADR-0001](decisions/0001-platform-and-stack.md) から [ADR-0009](decisions/0009-retention-tiers-on-s3.md) に理由を書く。
- 本家の名前は識別子に使わない。ドメインは `<brand>.<domain>`、キーの接頭辞は `<brand>_ik_`、ヘッダーは `<Brand>-Api-Key` の形で書く（[リポジトリ共通の ADR-0006](../../../docs/decisions/0006-brand-neutral-identifiers.md)）。本家のエージェント・SDK・API とそのまま互換にすることは目標にしない。公開の標準（OTLP、W3C Trace Context、StatsD）は受ける。
- データは日本（東京、DR は大阪）に置く。
- 日本の法令（個人情報保護法、電気通信事業法など）への対応は、法務の確認を前提に設計する。結論は出さない（下の「法務の確認待ち」）。
- 規模は段階的に広げる（[architecture/](architecture/README.md) の 2 節）。

## Non-goals

| 機能 | 理由 |
| --- | --- |
| 自前のホスト（オンプレミス）での提供 | 運用の形が別になる |
| 本家のエージェント・SDK・API・クエリの文法との完全な互換 | 振る舞いは寄せるが、名前と識別子は独自にする（リポジトリ共通の ADR-0006）。クエリの言語は本システムの設計（[ADR-0007](decisions/0007-query-language.md)） |
| 汎用のデータウェアハウス、任意の SQL | 可観測性のクエリに絞る。データの書き出しは API で行う |
| 汎用の全文検索のエンジンを核に据えること（OpenSearch など） | ログの保存と検索は題材の核。自前で作る（[ADR-0005](decisions/0005-log-storage-columnar-with-bloom.md)） |
| 請求書の発行と決済 | 利用量の計測までを持ち、請求は外部の課金のシステムに渡す |
| 利用者の障害の自動の修復（実行の自動化） | 通知と連携までにする |

| L9 | 画面とクエリの言語を本家に寄せる範囲：不正競争防止法（商品等表示、商品の形態の模倣）と著作権の観点で、画面の配置、ウィジェットの見た目、クエリの文法をどこまで似せてよいか | dashboards、metrics-query-engine の各領域 | E4 のクエリの文法の確定、E9 の画面の Story |

### 選定・計測で決めるもの（法務以外）

- 時系列の圧縮のコーデック：`codec_id` 1 は Gorilla の形（時刻の差分の差分、値の XOR）。ALP などの浮動小数点の圧縮と SIMD の差分の詰め込みを、E3 の前の `tsdb-codec-poc` で、合成のデータと提供を受けた試験のデータで比べる（[ADR-0004](decisions/0004-tsdb-storage-engine.md)）。
- MSK のブローカーの構成とパーティションの数、1 GB/秒あたりの費用：E2 の前の `msk-throughput-poc`（[ADR-0002](decisions/0002-intake-log-on-msk.md)）。
- インジェスターの 1 系列あたりのメモリー（ヘッドの 2 時間分と系列の索引）：E3 の前の `ingester-memory-poc`。S1 で有効な系列 1 億を見込む（[ADR-0004](decisions/0004-tsdb-storage-engine.md)）。
- ログのセグメントのブルームフィルターの誤検出の率と大きさ、日本語の 2-gram の効き：E5 の前の `log-bloom-poc`（[ADR-0005](decisions/0005-log-storage-columnar-with-bloom.md)）。
- テールサンプリングの待ちの窓（既定 30 秒）と、組み立てのメモリー：E6 の前の `tail-sampling-memory-poc`。
- 本家の利用量の数え方のうち、ホストの数え方（時間ごとの最大の扱い）、ログの索引の保持の期間の選択肢、トレースの保持の規則、本家のサービスの SLA：公式の資料で確かめられなかった（**未検証**）。本システムの値は usage-and-billing、log-storage-and-search、traces-and-sampling の各領域で決める。
