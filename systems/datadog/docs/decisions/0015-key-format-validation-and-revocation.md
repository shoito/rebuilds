# ADR-0015: 取り込みのキーは `<brand>_ik_` ＋ 32 文字の base62 の乱数 ＋ 6 文字の CRC32 のチェックサム。SHA-256 のハッシュだけを持つ。ゲートウェイは、形とチェックサムを手元で確かめてから、プロセスのキャッシュ → Valkey → Aurora の順で引く。正のキャッシュの期限は Aurora から読んだ時刻から 60 秒で、失効は通知と期限で 60 秒以内に効く。Aurora が使えない間は既知の有効なキーを 15 分まで受け、知らないキーには 503 を返す。アプリケーションキーは `<brand>_ak_` ＋ 組織の参照 ＋ 秘密で、組織を RLS の外の表なしで決め、実効の権限はスコープと持ち主の役割の積にする

## Context

取り込みのキーは、エージェントと OpenTelemetry の送り手が `<Brand>-Api-Key` で送る。ゲートウェイは S1 でピーク 1,000 万点/秒を受け、要求ごとにキーを確かめる（[ADR-0011](0011-intake-gateway-pipeline-and-watermark-ticks.md)）。

- `tenant_id` はキーからだけ決める（[ADR-0003](0003-tenancy-cells-and-isolation.md)）。キーの確認は RLS の外の `intake_keys_index` を X1 の経路で引く。
- 要求ごとに Aurora を引けない。キャッシュが要るが、キャッシュは失効を遅らせる。roadmap の `intake-keys` は失効の伝わりを 60 秒にしている。
- Aurora の停止で取り込みを止めると、NFR-006（取り込み 99.95%）を Aurora の可用性に縛る。逆に、知らないキーを 403 にするとエージェントは送り直さず、データを失う。
- キーの値をそのまま保存すると、DB の漏えいがキーの漏えいになる。
- キーはリポジトリに誤って置かれやすい。シークレットスキャンで見つけられる形が要る（[リポジトリ共通の ADR-0006](../../../../docs/decisions/0006-brand-neutral-identifiers.md)）。
- アプリケーションキーは利用者に属し、スコープを持つ（本家に寄せる。[API and Application Keys](https://docs.datadoghq.com/account_management/api-app-keys/)、2026-10-09 に確認）。管理の面（`api`）で確かめるが、組織を決めるためにキーから組織を引く表を RLS の外に置くと、ADR-0003 の一覧が増える。

## Options

キーの保存：

1. **高い乱数と SHA-256 のハッシュだけ**
2. 遅いハッシュ（bcrypt・Argon2）と塩
3. 暗号化して保存（取り出せる）

キャッシュと失効：

- a. **Aurora から読んだ時刻から 60 秒の期限と、失効の通知。Aurora の停止の間は既知のキーを 15 分まで**
- b. 長い期限（10 分）と通知だけ
- c. キャッシュなし（毎回 Aurora）

アプリケーションキーの組織の決め方：

- x. **キーに組織の参照（`tenant_id` の base62）を入れる**
- y. RLS の外に `application_keys_index` を足す

## Decision

1、a、x を採用する。詳細は [otlp-and-api-keys.md](../architecture/otlp-and-api-keys.md) の 7・8 節。

- 取り込みのキーの形は `<brand>_ik_` ＋ base62 の乱数 32 文字（約 190 ビット）＋ CRC32 の base62 6 文字。保存は `SHA-256(キー)` と最後の 4 文字だけ。作成のときに 1 回だけ見せる。
- ゲートウェイの確かめ：形とチェックサムの誤りは引かずに 403 → 負のキャッシュ（10 秒）→ L1（プロセス、100 万件）→ Valkey → Aurora の読み手（single flight）。正のキャッシュは `fetched_at`（Aurora から読んだ時刻）から 60 秒で切れ、写しても延びない。
- 失効は、`intake_keys` と `intake_keys_index` を 1 つのトランザクションで更新し、Valkey の鍵を消して `ik-revoked` を publish する。通知は速さのため、期限が正しさを守る。
- Aurora が使えない間は、L1 の有効なキーを `fetched_at` から 15 分まで受ける。知らないキーは 503（`Retry-After: 30`）。
- アプリケーションキーの形は `<brand>_ak_<tenant_ref>_<乱数 32><チェックサム 6>`。`api` は `tenant_ref` で `SET LOCAL app.tenant_id` を決め、RLS の中で引く。実効の権限はスコープと持ち主の今の役割の積（[ADR-0052](0052-identity-sso-scim-keys-and-audit-trail.md) と同じ）。持ち主が無効ならキーも無効。期限と送り元の IP の範囲は ADR-0052 に従う。
- シークレットスキャンの通報での失効の時期（取り込みのキーは 24 時間の後、アプリケーションキーはすぐ）は security.md の 3.1 節に従う。

### 他の案を選ばなかった理由

- **2（遅いハッシュ）**：190 ビットの乱数には総当たりが成り立たず、遅いハッシュは要求ごとの CPU（ミス時）を増やすだけ。塩があると、ハッシュで直接引けない。
- **3（暗号化）**：取り出せる形で持つ理由がない。漏えいの影響が大きい。
- **b（長い期限）**：通知を失うと失効が 10 分遅れる。60 秒の目標に合わない。
- **c（キャッシュなし）**：Aurora に毎秒数十万の問い合わせが行き、Aurora の停止がそのまま取り込みの停止になる。
- **y（RLS の外の表）**：ADR-0003 の RLS の外の表を増やす。組織の参照は秘密ではなく、キーに入れても漏れるものはない。

## Consequences

- 良くなること：
  - 失効が 60 秒以内に効き、通知の喪失にも強い。
  - Aurora の停止の間も、既知の送り手の取り込みが続く。
  - DB の漏えいでキーは漏れない。形とチェックサムでシークレットスキャンに載せられる。
  - アプリケーションキーのために RLS の外の表を足さない。
- 引き受けるコスト：
  - Aurora の停止の間の失効は、最悪 15 分遅れる（書き込みだけのキーなので受け入れる。[security.md](../architecture/security.md) の 3.1 節）。
  - 作ったばかりのキーは、負のキャッシュで最大 10 秒拒まれうる。
  - アプリケーションキーから組織の ID が読める（秘密ではないが、利用者に説明する）。

## Confirmation

- 表駆動テスト：DT-KEY-001（確かめの全組み合わせ）。
- 性質ベーステスト：PROP-KEY-001（失効の 60 秒）、PROP-KEY-002（組織の取り違えなし）、PROP-KEY-003（実効の権限）。
- lint：キーの値・ハッシュをログ・指標・トレースの属性に書くコードを禁止する（`key_id` だけ）。
- 結合テスト：Testcontainers の PostgreSQL 18 と Valkey で、通知を落とした場合の失効の伝わりを測る。
