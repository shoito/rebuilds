# ADR-0063: 「取り込みからクエリに出るまで」と「通知まで」の SLI は `canary` の端から端までの計測を正にし、クエリの速さと評価の遅れはサーバーのヒストグラムを正にする。組織ごとの「隣人の影響」は、パーティションの水位と今の時刻の差を組織ごとに標本にして近似し、`canary` の実測と比べて確かめる

## Context

- runbooks の SLI（[runbooks/](../runbooks/README.md) の 1 節）は、見張りの系列・ログで「202 からクエリで読めるまで」を測ると書いた。QA は品質の判定に、取り込みからクエリまで、評価の遅れ、見張りの照合などを使う。
- 本システムの遅れの多くは、取り込みの後（消費者の遅れ、セグメントの書き出しの間隔、組み立ての待ち）にあり、サーバーの片側の計測では、どこかの部品の計測の抜けで実際より良く見える。
- 一方、`canary` は 1 セルに 1 つの組織しか測れない。「隣人の影響」は、割り当ての中の組織ごとに取り込みからクエリまでの p99 を見る必要がある（NFR-007、K6）。
- 消費者はパーティションごとの水位を出し、`query-frontend` は組織ごとに合わせる（[ADR-0008](0008-monitor-evaluation-model.md)、[ADR-0011](0011-intake-gateway-pipeline-and-watermark-ticks.md)）。
- クエリの速さ（NFR-003）と評価の遅れ（NFR-004）は、利用者の要求とモニターの数に比例する分布で、`canary` の少数の標本では p99 が測れない。

## Options

1. **端から端は `canary`、速さと遅れはサーバーのヒストグラム、組織ごとは水位の近似**
2. すべてサーバーの計測
3. すべて `canary`（組織を増やす）

## Decision

1 を採用する。

| SLI | 正 |
| --- | --- |
| メトリクス・ログ・トレースがクエリに出るまで | `canary`（202 からクエリ・検索・ID の引きで読めるまで。1 秒ごとに読む。トレースは完成の待ちを引いた値も出す） |
| 通知まで（評価と通知の可用性の一部） | `notifier` の「遷移から送信まで」のヒストグラム。端から端の確かめとして `canary.flip` のモニターの通知が見張りの受け口に届くまで |
| 取り込みの応答、クエリの速さ、評価の遅れ | ゲートウェイ・`query-frontend`・`monitor-evaluator` のヒストグラム |
| 見張りの照合 | `canary` が時刻から計算した値と、生・1 分・1 時間の層の値の比べ |
| 隣人の影響 | 組織ごとの `今 − 水位` を 10 秒ごとに標本にした 5 分の p99（`svc_tenant_freshness_seconds`）。`canary` の組織で実測との差が 5 秒を超えたら近似を直す |

- バーンレートは 1 時間（＋5 分の確かめ）14.4 倍、6 時間 6 倍、3 日 1 倍。
- `canary` の組織はセルごとに 1 つで、SLO・利用量・課金から除く。公開の入口と公開の API だけを使う。

### 他の案を選ばなかった理由

- **2（すべてサーバー）**：部品の間の受け渡し（セグメントの書き出しの間隔、カタログの確定、キャッシュ）の遅れを取りこぼす。計測の抜けが「良い」に見える。
- **3（すべて `canary`）**：組織を増やすほど、取り込みと費用と `canary` のキーの管理が増える。クエリの p99 は少数の標本で測れない。

## Consequences

- 良くなること：
  - 利用者の体験に最も近い SLI（端から端）を正にできる。
  - 組織ごとの隣人の影響を、全組織で見られる。
- 引き受けるコスト：
  - 組織ごとの値は近似で、近似と実測の差を見続ける。
  - `canary` は 1 秒ごとに読むので、本番のクエリの負荷になる（セルあたり 1 秒 10 件前後）。

## Confirmation

- `canary` の照合の関数を、生成した値の列で参照と比べる（`PROP-OBS-001`）。
- `canary` の組織の実測と近似の差を指標にし、5 秒を超えたらチケット。
- runbooks の 1 節の SLI と、この ADR の表が 1 対 1 であることを、SLI の定義の変更のたびに QA と Ops が確かめる。
