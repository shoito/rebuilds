# ADR-0050: インシデントは Aurora の行と、追記だけの出来事の列（タイムライン）で持つ。状態は `active` → `stable` → `resolved` → `completed`（振り返りの済み）、`resolved` から `active` に戻せる。出来事は書き換えず、直すときは直しの出来事を足す。モニターの遷移・通知は写さず参照する。通知は outbox を通す

## Context

- MVP に軽いインシデント管理（宣言、重さ、担当、タイムライン、通知、振り返りの雛形）を含め、オンコールの当番の表は外部のサービスに渡すと決めている（[architecture/README.md](../architecture/README.md) の 6 節）。
- タイムラインは振り返りの元になり、「誰がいつ何をしたか」の記録として後から直されては困る。一方で、メモの誤りは直したい。
- タイムラインにはモニターの遷移と通知が並ぶ。値を写すと、見る人の権限（データのアクセスの制限）を超えて値が残りうる（[quality.md](../quality.md) の 2.2.1 節 G のインシデントのタイムラインの行）。
- 通知は、モニターと同じ経路で重ねずに送りたい（[ADR-0045](0045-notification-delivery-model.md)）。
- 本家のインシデント管理の状態と重さの段は確かめなかった（**未検証**）。

## Options

1. **行と追記だけの出来事の列。直しは新しい出来事。参照で持つ**
2. インシデントの 1 つの文書（JSON）を書き換える
3. 外部のサービス（オンコールのサービスのインシデントの機能）に任せる

## Decision

1 を採用する。詳細は [slos-and-incidents.md](../architecture/slos-and-incidents.md) の 7 節。

- `incidents`：組織ごとの連番、題、重さ（`SEV-1`〜`SEV-5`）、状態、指揮者、対応者、影響するサービス、顧客への影響、結び付け。
- 状態：`active` ⇄ `stable` → `resolved` → `completed`。`resolved` → `active`（再開）。
- `incident_events`：追記だけ。`occurred_at`・`recorded_at`・行為者を持つ。直しは `note_corrected` が元を参照し、元を残す。モニターの遷移と通知は ID で参照し、表示のときに見る人の権限で確かめる。
- 宣言・状態・重さの変更の通知は、出どころ＝インシデントの通知の依頼として outbox に書く。重ねない鍵は（インシデント、出来事の ID）。オンコールのサービスへは `dedup_key = <tenant>:incident:<番号>`。
- `resolved` で振り返りの Markdown の雛形を作り、バージョンを付けて保存する。

### 他の案を選ばなかった理由

- **2（1 つの文書）**：同時に複数の対応者が書くと衝突し、上書きで記録が消える。
- **3（外部に任せる）**：本システムのモニター・ダッシュボード・SLO とタイムラインを結べない。外部のサービスを使わない利用者が使えない。

## Consequences

- 良くなること：
  - 記録が消えず、振り返りの元として信頼できる。
  - 複数の対応者が同時に書いても衝突しない。
  - 制限の外の値がタイムラインに残らない。
- 引き受けるコスト：
  - 表示のたびに参照の先を引き、権限を確かめる。
  - 誤って書いた個人のデータを消すには、直しではなく削除の手順（管理者の操作、監査ログ）が要る（[security.md](../architecture/security.md) と合わせる）。

## Confirmation

- 性質ベーステスト：PROP-INC-001（タイムラインを書き換えない）。
- 漏れの経路：見る人が見られないモニターの値がタイムラインに出ない。
- 表駆動：状態の遷移の全組（許す・拒む）。
