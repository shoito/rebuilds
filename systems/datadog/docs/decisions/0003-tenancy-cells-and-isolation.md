# ADR-0003: 組織をテナントにし、共有のセルに置く（大きな組織は専用のセル）。データの鍵の先頭に `tenant_id`、管理の DB は FORCE RLS。取り込み・保存・クエリ・評価の各段に、割り当て、シャッフルシャーディング、重み付きの公平なキューを置く

## Context

利用者は組織（会社、事業部）で、組織の中に利用者・チーム・役割がある。組織どうしでデータを共有しない。

- 組織の大きさの差が大きい。S1 で 1,000 組織、最大の組織はホスト 5,000・有効な系列 1,000 万を見込む。
- 量は障害のときに急に増える。ある組織の障害（ログの急増、リトライの嵐でのスパンの急増、新しいタグでの系列の急増）で、他の組織の取り込み・クエリ・アラートが遅れれば、監視が最も要るときに見えなくなる（NFR-007）。
- 他の組織のデータ（値、タグの値、ログの本文、サービスの名前）が、1 つの経路でも届けば漏えいである。経路は多い：クエリ、結果のキャッシュ、タグの値の補完、ファセット、サービスマップ、ライブテール、通知、利用量。
- 組織の中でも、役割によって見られるデータを絞る（データのアクセスの制限。例：`team:payments` のデータは決済のチームだけ）。
- データの面の保存は Aurora ではなく、S3 のブロック・セグメントとインジェスターのメモリーにある。RLS で守れるのは管理の面だけである。

## Options

置き方：

1. **共有のセル（多くの組織が同じデータの面を使う）。大きな組織は専用のセル**
2. 組織ごとに専用のデータの面
3. 1 つの大きな共有のデータの面（セルを持たない）

分離の方式（データの面）：

- a. **`tenant_id` を、すべての鍵・パス・メッセージ・クエリの IR の先頭に置き、認証の文脈からだけ入れる。各段に割り当てと公平なキュー**
- b. 組織ごとに S3 のバケット・MSK のトピックを分ける

## Decision

1 と a を採用する。

### セル

- **セル**は、1 組の MSK のクラスタ、データの面のサービス、S3 の接頭辞、Valkey を持つ単位。管理の面（Aurora、`api`）はリージョンで 1 つにし、組織からセルを引く表（`tenant_cells`）を持つ。
- S1 は東京に 1 つのセル。S2 で 4〜8 つに分け、新しい組織は空きのあるセルに置く。ホスト 2 万以上か有効な系列 1 億以上の組織は、専用のセルの候補にする（基準は infrastructure の領域）。
- 組織のセルの移し替えは、新しいセルへの二重の書き込み、保持の期間の後の読み出しの切り替えで行う（infrastructure の領域）。

### 鍵とパス

- **`tenant_id`（UUIDv7）を、次のすべての先頭に置く。** MSK のメッセージの頭、系列の鍵のハッシュの入力、系列の索引の鍵、S3 のパス（`<cell>/<tenant_id>/metrics/...`）、ログのセグメントのカタログの行、キャッシュの鍵、評価のシャードの鍵、クエリの IR。
- **`tenant_id` は認証の文脈からだけ入れる。** 取り込みはキーから、画面と API はセッションとアプリケーションキーから決める。要求の本文、タグ、クエリの文字列に `tenant_id` を書いても使わない。
- ブロック・セグメントは 1 つの組織のデータだけを持つ。複数の組織の点を同じファイルに混ぜない（小さな組織が多いと小さなファイルが増える。合わせで抑える）。
- S3 のキーの暗号化は、共有の KMS キー（バケットキー）にする。組織ごとの鍵（BYOK）は MVP の後。

### 管理の DB

- Aurora の表には `tenant_id` を持たせ、主キーとインデックスの先頭に置く。ID は UUIDv7。`FORCE ROW LEVEL SECURITY` を設定し、要求ごとに `SET LOCAL app.tenant_id` で絞る。
- **RLS の外の表**は次だけにし、テレメトリーの値・タグの値・ログの本文を持たせない。
  - `tenant_cells`（組織 → セル）
  - `intake_keys_index`（キーのハッシュ → 組織。キーの確認の入口）
  - `users`、`sessions`、メールアドレスから利用者の解決（利用者は複数の組織に属しうる）
  - outbox の読み出しの位置、SLI の集計
- **組織をまたぐ処理は、次の経路だけにし、専用の DB のロールを通す。** 一覧にない経路を足すときは、先にこの ADR を直す。
  - X1：キーの確認（`intake_keys_index`）
  - X2：システムの作業（保持の期限、合わせ、利用量の集計）。組織を 1 つずつ文脈に設定して回す
  - X3：Relay の outbox の読み出し、SLI の集計
  - X4：セルの割り当てと移し替え

### うるさい隣人の抑え

| 段 | 仕組み |
| --- | --- |
| 取り込み | 組織ごとのトークンバケット（点/秒、バイト/秒、ログの件数/秒、スパン/秒）。ゲートウェイごとの局所のバケットに、全体の割り当てを 10 秒ごとに配り直す（調整は Valkey）。超過は 429。MSK のパーティションは組織ごとの組（[ADR-0002](0002-intake-log-on-msk.md)） |
| 保存 | インジェスターのシャードごとに、組織ごとのメモリーの割り当て（系列の数）と新しい系列の作成の速さの上限（[ADR-0006](0006-cardinality-policy.md)）。ログのインデクサーは組織ごとに書き出しのバッファーを分ける |
| クエリ | 組織ごとの並行の上限と、重み付きの公平なキュー（重みは契約の量）。費用の見積もり（読む系列 × 点、読むバイト）で受け付けを決め、上限を超えるクエリは拒むかロールアップの層に落とす（[ADR-0007](0007-query-language.md)） |
| 評価 | モニターの評価は、ダッシュボードと別のクエリの読み手の組で実行する。組織ごとの評価の量の上限 |
| 通知 | 組織ごとの送信の速さの上限、チャネルごとの待ち行列 |

- 全体が溢れたとき（MSK の書き込みの上限に近い）は、割り当てを超えている組織から先に 429 を返す。割り当ての中の組織の取り込みは最後まで守る。

### データのアクセスの制限

- 役割に、信号ごとの制限の条件（タグの条件。例：`team:payments`）を付けられる。クエリのコンパイラが、IR に AND の条件として必ず足す。画面・API・モニター・ダッシュボード・エクスポートで同じにする（tenancy-and-rbac の領域）。
- タグの値の補完、ファセットの候補、サービスマップも、制限を足した IR で作る。

### 他の案を選ばなかった理由

- **2（組織ごとに専用）**：小さな組織が多く、データの面の最小の構成（MSK、インジェスターの 2 つの写し）の費用が組織の数に比例する。
- **3（セルなし）**：障害の範囲が全組織になる。S2 以降でパーティション・シャードの数が 1 つのクラスタの上限を超える。
- **b（バケット・トピックを組織ごとに）**：S3 のバケットの数と MSK のトピックの数の上限に当たり、小さな組織の多いこの題材に合わない。分離は鍵の先頭とテストで守る。

## Consequences

- 良くなること：
  - 障害の範囲がセルに閉じる。大きな組織を専用のセルに移せる。
  - 各段に割り当てと公平なキューがあり、1 つの組織の急増が他の組織の SLO を消費しにくい。
  - 管理の面は他の題材と同じ RLS の形で守られる。
- 引き受けるコスト：
  - データの面の分離は RLS に頼れない。鍵の先頭の `tenant_id` と、テスト・lint で守る。
  - 小さな組織の小さなファイルが増える。合わせ（[ADR-0009](0009-retention-tiers-on-s3.md)）の負荷が増える。
  - セルの割り当てと移し替えの仕組みを持つ。

## Confirmation

- 結合テスト：管理の DB のすべての表に `FORCE ROW LEVEL SECURITY` とポリシーがあることを、スキーマの検査で確かめる。RLS の外の表の一覧を CI が上の一覧と照らす。
- 性質ベーステスト：任意の 2 つの組織のデータとクエリの列で、組織 A のクエリ・補完・ファセット・サービスマップ・キャッシュの結果に、組織 B の値・タグの値が出ない（漏れの経路の表、[quality.md](../quality.md)）。
- lint：データの面で、`tenant_id` を要求の本文・タグ・クエリの文字列から読むコードを禁止する。S3 のパス・キャッシュの鍵を作る関数は、`TenantId` の型を最初の引数に取るものだけにする。
- 負荷試験：割り当ての 10 倍を送る組織と、通常の組織を同じセルに置き、通常の組織の NFR-002・NFR-003 を確かめる（E13）。
- 本番：クエリの応答を抜き取り、組織とデータのアクセスの制限に通し直して比べる（応答の監査）。
