# ADR-0043: ミュートとダウンタイムは、評価の入力（組織のダウンタイムの設定のバージョン）として扱い、状態は進め、通知だけを抑える。繰り返しは RRULE と時間帯で展開する。終わったときに通知の要る状態が続いていれば知らせる。抑えた遷移も記録する

## Context

- 計画の作業（デプロイ、保守）の間の通知を止めたい。本家は、ダウンタイムの間も状態を変え、通知だけを抑え、終わったときに通知の要る状態なら知らせる。繰り返しは RRULE（[Downtimes](https://docs.datadoghq.com/monitors/downtimes/)、2026-10-09 に確認）。
- 評価は決定的でなければならない（[ADR-0008](0008-monitor-evaluation-model.md)）。ダウンタイムの作成・取り消しは壁の時計で起き、評価器への届き方で、同じ `t` の評価がダウンタイムを見たり見なかったりしうる。
- 日本の利用者は日本時間で予定を作る。夏時間はないが、利用者が海外の時間帯を使うこともある。

## Options

1. **組織のダウンタイムの集まりをバージョンにし、評価の入力として記録する。状態は進め、通知を抑える**
2. 評価そのものを止める
3. 通知の段（`notifier`）で、送る時に止める

## Decision

1 を採用する。詳細は [monitors-and-alerting.md](../architecture/monitors-and-alerting.md) の 9 節。

- ダウンタイム：モニターの選び方（ID かモニターのタグの条件）、グループの範囲（タグの条件）、予定（1 回か RRULE＋長さ＋時間帯、既定 `Asia/Tokyo`）、終わりの通知の対象、間の回復の通知。ミュートは同じ表の 1 つの形。
- 変更のたびに `downtime_set_version` を上げ、outbox で評価器に配る。評価器は `t` の評価に使ったバージョンを遷移の記録に書き、再生は同じバージョンで行う。
- 間の遷移は `muted = true` で記録し、通知の依頼を `suppressed` で書く。再通知も抑える。
- 終わりの最初の評価で、状態が対象（既定 ALERT・WARN・NO_DATA）で未通知なら知らせる。前に知らせた ALERT が間に回復したら、最初の回復だけ知らせる（既定）。

### 他の案を選ばなかった理由

- **2（評価を止める）**：終わったときに今の状態が分からず、終わりの通知とモニターの SLO が誤る。
- **3（送る時に止める）**：どの遷移が抑えられたかが評価の記録に残らず、再生と「なぜ鳴らなかったか」の説明ができない。終わりの通知を作れない。

## Consequences

- 良くなること：
  - ダウンタイムの間も状態が正しく、終わりに必要な通知が出る。
  - 再生で、同じダウンタイムのバージョンを使って同じ結果になる。
- 引き受けるコスト：
  - ダウンタイムの作成から効くまで、評価器への配布の遅れ（数秒）がある。作成の画面に「次の評価から効く」と示す。
  - RRULE の展開を評価器で行う（時間帯のデータベースのバージョンを固定して持つ）。

## Confirmation

- 性質ベーステスト：PROP-MON-006（間の通知が出ない、終わりに 1 回、状態の列はダウンタイムのない場合と同じ）。
- 試験のベクトル：RRULE と時間帯の展開（月の第 3 月曜、月末、年をまたぐ）。
- 再生：ダウンタイムのバージョンを含めた記録の再生。
