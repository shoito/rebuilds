# ADR-0030: 組織のパイプラインの設定を、Rust の `log-pipeline` で検証して実行の形にコンパイルし、バージョンを付けて配る。正規表現は線形の時間のものだけにし、1 件あたりの処理の予算を持つ。予算や規則の誤りでは、ログを捨てずに元のまま流す。`logs-raw` から `logs` への処理は、Kafka のトランザクションで 1 回だけにする

## Context

`log-processor` は、組織が書いた規則（解析、付け替え、マスク、振り分け）を、S1 でピーク 1.5 GB/秒のログに当てる（[architecture/README.md](../architecture/README.md) の 2 節）。

- 規則は組織が書く。遅い正規表現（破局的なバックトラック）や、大きな本文への重い規則が、同じタスクの他の組織を遅らせうる（NFR-007）。
- 規則の誤りで、受け取ったログを失ってはいけない（NFR-005）。
- 消費者は読み直しで同じ結果を作る（[ADR-0002](0002-intake-log-on-msk.md)）。`log-processor` の出力は S3 ではなく MSK の `logs` のトピックで、出力と読んだ位置を同じ記録で確定する方法を決める必要がある。
- 規則は変わる。読み直しの途中で規則が変わると、同じログが違う結果になりうる。
- 本家は処理器を順に当て、遅い規則を本家が止めることがあると説明している（[Log Pipelines](https://docs.datadoghq.com/logs/log_configuration/pipelines/)、2026-10-09 に確認）。本家の実装は使わない。

## Options

実行の形：

1. **設定の束を検証してコンパイルし、線形の時間の正規表現と手順の予算で実行する**
2. 設定をそのまま解釈し、時間切れ（壁の時計）で止める
3. 組織ごとに WASM の利用者の関数を動かす

1 回だけの確定：

- a. **Kafka のトランザクション（`logs-raw` のオフセットと `logs`・`derived-partials` への書き込みを 1 つに）**
- b. 少なくとも 1 回で書き、下流で `log_id` で重複を除く

## Decision

1 と a を採用する。詳細は [logs-pipeline.md](../architecture/logs-pipeline.md) の 6・7 節。

- パイプライン・処理器・マスクの規則・索引・ログから作るメトリクスを、組織ごとに 1 つの設定の束にし、変更のたびにバージョンを上げる。`api` が Rust の `log-pipeline` を WASM で呼んで検証・コンパイルし、結果を S3 に置く。`log-processor` は次のバッチの区切りで切り替える。
- 正規表現は線形の時間のもの（後方参照・先読みなし）だけにする。grok の形の規則も同じ正規表現にコンパイルする。
- 1 件あたりの予算は手順の数で数える（既定 200 万手順。マスクは別に 100 万手順）。壁の時計で止めない（読み直しで結果が変わらないため）。
- 処理器の失敗と予算の超過では、残りの処理器を飛ばして流す。`pipeline.errors` に理由のコードだけを書く。マスクは飛ばさない（[ADR-0031](0031-pii-scrubbing-before-routing.md)）。
- `logs-raw` を読み、`logs` と `derived-partials` に書き、オフセットを確定するまでを Kafka のトランザクションにする。下流は `read_committed` で読む。バッチで使った設定のバージョンを記録し、読み直しでは同じバージョンで処理する。
- 同じログで 3 回落ちたら、本文なしで `poison` として流してオフセットを進める。

### 他の案を選ばなかった理由

- **2（時間切れ）**：壁の時計で止めると、同じログが負荷によって違う結果になり、読み直しで同じにならない。バックトラックの正規表現は時間切れまで CPU を使い切る。
- **3（WASM の関数）**：表現は広いが、利用者のコードの隔離・審査・費用の見積もりが要り、MVP の範囲を超える。本家の振る舞い（決まった処理器）にも寄らない。
- **b（少なくとも 1 回）**：`logs` を読む消費者（インデクサー、アーカイブ、ライブテール、`derived-metrics-aggregator`）すべてに重複の除去が要る。ログから作るメトリクスの部分の値は、重複すると数が増える。

## Consequences

- 良くなること：
  - 規則の誤りでログを失わない。重い規則の影響が、その組織の 1 件の予算の中に収まる。
  - 読み直しで、振り分け・マスク・メトリクスの部分の値が同じになる。
  - 画面の「試す」と本番が同じコードで動く。
- 引き受けるコスト：
  - Kafka のトランザクションの費用（調整役への往復、`read_committed` の遅れ）。`msk-throughput-poc` で測る。
  - 正規表現の表現が制限される（後方参照を使う既存の規則は書き直しが要る）。
  - 設定の束の全体を変更のたびにコンパイルする。

## Confirmation

- 性質ベーステスト：PROP-LOGP-001（任意の位置での停止・再開で、1 回だけ処理した結果と一致）。
- 単体：破局的なバックトラックの形を受け付けない。最悪の入力（1 MB）で 1 件の手順が予算の中。
- ファジング：規則のコンパイル、JSON の展開、日付の解析。
- lint：`crates/log-pipeline` で、壁の時計と乱数を使うコードを禁止する。
