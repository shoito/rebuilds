# ADR-0068: 他の監視の道具からの移行の取り込み

## Context

- 主な利用者（[intent.md](../intent.md) の「Affected users and systems」）は、すでに何かの監視の道具（本家、Grafana と Prometheus、他の SaaS、自前の監視）を使っている。乗り換えの費用の大半は、ダッシュボードとモニター（数百〜数千）の作り直しと、新旧の結果を比べる並行の運転である。
- テレメトリーの送り方は標準に寄せている（OTLP、StatsD、OpenTelemetry の Collector。[ADR-0014](0014-otlp-mapping-and-resource-attributes.md)）。Collector は複数の送り先に同時に送れるので、テレメトリーの移行は「2 重に送って並行に運転する」で足りる。1 時間より古いメトリクスの取り込みは MVP の後（E18）。
- 設定の移行は決めていない。本家の API・クエリの文法との完全な互換は Non-goal で（[intent.md](../intent.md)）、PromQL を IR にコンパイルするのは MVP の後（E17、[ADR-0007](0007-query-language.md)）。Grafana と Prometheus の規則の多くは PromQL で書かれている。
- 本家の書き出した設定の形式を読む変換器を持つこと、画面に他社の名前を出すことの扱いは、法務の確認が要る（[intent.md](../intent.md) の L9・L10）。
- テストに本家から書き出したデータを使わない（AGENTS.md）。変換器の試験の入力も合成する必要がある。
- 移行の道具を MVP に入れるかは PM の判断である（[intent.md](../intent.md) の「PM が決めるもの」）。この ADR は、作るときの形を決める。

## Options

1. 移行の道具を持たない。2 重の送信の手順書と、公開 API・Terraform での作り直しの案内だけを用意する
2. **利用者が他の道具から書き出したファイルを上げると、変換器がダッシュボードとモニターの定義に変換し、通知を止めた下書きとして作る。変換できない部分は報告する。変換元は段階で足す**
3. 本家の API と同じ形の受け口を持ち、利用者の今の Terraform・スクリプトをそのまま向けられるようにする

## Decision

2 を提案する。詳細は [dashboards.md](../architecture/dashboards.md) の 11 節。

- **入力はファイルだけ**：利用者が上げた JSON・YAML（1 回 20 MiB まで）を読む。他社のサービスの API キーを預かって取りに行く形にしない（他社の秘密を持たない。[ADR-0058](0058-untrusted-senders-egress-and-operator-access.md) の egress を増やさない）。
- **変換器は口の後ろに置く**：`crates/import` に変換元ごとの変換器（`Importer`）を置き、出力は公開 API と同じ定義の JSON（[dashboards.md](../architecture/dashboards.md) の 4.1 節）にする。クエリは変換元の言語から IR へ変換し、IR に表せない関数・パネルの種類・テンプレートは変換せず、項目ごとの理由のコードで報告する。黙って近い意味に置き換えない（集計の意味が変わるため。[ADR-0024](0024-query-ir-default-semantics.md)）。
- **変換元の順**：PromQL の IR へのコンパイル（E17）の後に、Grafana のダッシュボードの JSON と Prometheus の警告の規則（YAML）から始める。本家の書き出した JSON の変換は、法務の確認（L10）の後に決める。
- **下書きとして作る**：取り込んだモニターは「移行の待ち」のダウンタイムを付けて作り、評価は進めて通知だけを止める（[ADR-0043](0043-downtimes-as-evaluation-input.md)）。利用者は並行の運転の間、遷移の記録を旧い道具のアラートと比べ、モニターごとに有効にする。ダッシュボードは移行の印（`imported_from`、取り込みの ID）を付けて作る。
- **報告**：取り込みごとに、項目（ダッシュボード・ウィジェット・モニター）ごとの結果（変換した・一部・できない）と理由のコードを `import_runs` に持ち、画面と API で見せる。同じファイルを 2 回上げても、取り込みの ID で重ねない。
- **テレメトリー**：2 重の送信の手順書（OpenTelemetry の Collector の設定例、本システムのエージェントと旧い道具のエージェントの並行の動かし方）を用意する。履歴のメトリクスは移さない（E18 の後に改めて決める）。
- **権限**：ダッシュボードは `dashboards.write`、モニターは `monitors.write` を持つ人だけが取り込める。取り込みは組織の監査ログに書く。
- 1 を採らない理由：数百のモニターを手で作り直す費用が、乗り換えの最大の障害として残る。
- 3 を採らない理由：本家の API との互換は Non-goal で、名前と識別子を独自にする規則（リポジトリ共通の ADR-0006）と、法務の L9 に触れる。互換の受け口は、本家の振る舞いの変化を追い続ける費用もかかる。

## Consequences

- 変換元の形式の変化を追う保守がかかる。変換元ごとに、確かめた形式のバージョンを変換器に書く。
- 変換の質は、IR に表せる範囲で決まる。PromQL の範囲のベクトルの意味のように、本システムのロールアップと意味がずれるものは「一部」として報告され、利用者が直す。
- 取り込んだモニターが通知を止めたまま放置されうる。移行の待ちのダウンタイムに期限（既定 30 日）を付け、期限の前に作った人へ知らせる。

## Confirmation

- 試験のベクトル：変換元ごとに、公開の形式の資料から合成した入力ファイルと、期待する定義・報告の組を持つ。実在の組織・本家から書き出したファイルを使わない。
- 性質ベーステスト（PROP-DSH-005）：任意の入力で、変換器は「変換した」と報告した項目の IR が入力のクエリと同じ意味（参照の実装で同じ結果）になり、意味の違うものを「変換した」と報告しない。
- 結合テスト：取り込んだモニターは、移行の待ちの間に遷移を記録し、通知を 1 件も送らない。
