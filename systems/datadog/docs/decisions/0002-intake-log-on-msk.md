# ADR-0002: 取り込みのログに Amazon MSK を使い、MSK の確定の後に 202 を返す。信号ごとのトピック、テナントごとのパーティションの組、保持 24 時間。MSK はデータの面の WAL で、消費者は読み直しで同じ結果になるように作る

## Context

取り込みは、S1 でピーク 1,000 万点/秒のメトリクス、1.5 GB/秒のログ、200 万/秒のスパンを受ける（[architecture/README.md](../architecture/README.md) の 2 節）。量は、利用者の障害のときに急に増える。

- 受け取ったデータを失わない（NFR-005）。202 を返したら、保存の側が落ちても残る必要がある。
- 取り込みの応答は速く（NFR-001）、保存・索引・組み立ての遅れに引きずられない。
- 同じデータを、複数の消費者（インジェスター、ログの処理、組み立て、利用量の計測、ライブテール）が読む。
- 消費者が落ちたら、落ちた位置から読み直す。インジェスターのヘッド（直近 2 時間）は、メモリーにだけある間、何かから作り直せる必要がある（[ADR-0004](0004-tsdb-storage-engine.md)）。
- 共通の基盤の非同期は SQS・SNS だが、SQS は消費者ごとの読み直しの位置・順序・複数の消費者を持たない。

本家も、取り込みを Kafka のパーティションから読む形で説明している（[Rust timeseries engine](https://www.datadoghq.com/blog/engineering/rust-timeseries-engine/)、[Introducing Husky](https://www.datadoghq.com/blog/engineering/introducing-husky/)、2026-10-09 に確認）。Kafka は本家（Datadog）の実装ではなく、第三者の汎用の部品である。この題材の核は保存・クエリ・評価で、取り込みのバスは核ではない（[リポジトリ共通の ADR-0007](../../../../docs/decisions/0007-no-reuse-of-original-implementation.md)）。

## Options

1. **Amazon MSK（Kafka のプロトコル）**
2. Amazon Kinesis Data Streams
3. 自前の WAL（取り込みのゲートウェイが S3 に小さなファイルを書く）
4. SQS・SNS（共通の基盤）
5. 取り込みのゲートウェイがインジェスターへ直接送り、インジェスターが自前の WAL を持つ

## Decision

1 を採用する。

### 確定と応答

- `intake-gateway` は、MSK のプロデューサーの `acks=all` で、`min.insync.replicas=2`（複製 3、3 AZ）の確定を受けてから 202 を返す。
- 確定できない（時間切れ、ブローカーの障害）ときは 503 と `Retry-After` を返す。部分の成功は返さない（1 つの要求の点を 1 つのバッチで書く）。
- 割り当ての超過は MSK に書かずに 429 を返す（[ADR-0003](0003-tenancy-cells-and-isolation.md)）。
- エージェントは 429・503 でディスクの待ち行列に溜め、指数の待ちとゆらぎで送り直す（intake-and-agent の領域）。

### トピック

| トピック | 中身 | パーティションの鍵 | 消費者 |
| --- | --- | --- | --- |
| `metrics` | 系列の点（系列の鍵、タグ、時刻、値・ヒストグラム） | テナントの組の中で、系列の鍵のハッシュ | `metrics-ingester`、`usage-aggregator` |
| `logs-raw` | 受け取ったままのログ | テナントの組の中で、ばらす | `log-processor`、利用量 |
| `logs` | 処理（マスク）の後のログと振り分けの結果 | テナントの組の中で、ばらす | `log-indexer`、アーカイブの書き手、ライブテール |
| `spans` | スパン | テナントの組の中で、`trace_id` のハッシュ | `trace-assembler`、利用量 |
| `usage` | ゲートウェイが数えた利用量（ホスト、バイト数） | テナント | `usage-aggregator` |

- メッセージは内部の Protobuf にし、先頭に `tenant_id`・形式のバージョン・取り込みの時刻を持つ。本文は zstd で圧縮する。
- 保持は 24 時間（`logs-raw` も 24 時間。マスクの前の値を長く持たない）。インジェスターのブロックの書き出し（区切りから 70 分）と、消費者の障害からの回復に足りる。
- 同じ系列の点は同じパーティションに入るので、同じ系列・同じ時刻の点の「後に取り込んだもの」はオフセットの順で決まる。読み直しても同じ結果になる。

### テナントのパーティションの組（シャッフルシャーディング）

- 各トピックのパーティション（S1 で `metrics` 1,024、`logs` 512、`spans` 512 を仮に置く。`msk-throughput-poc` で決める）から、テナントごとに k 個の組をハッシュで選ぶ。k はテナントの割り当ての量に比例し、最小 4。
- 大きなテナントの急増は、組の重なるパーティションにだけ及ぶ。2 つのテナントの組が全部重なる確率を、k と全体の数で小さくする（[ADR-0003](0003-tenancy-cells-and-isolation.md)）。
- テナントの k を変えると、系列のパーティションが変わり、同じ系列の点が 2 つのパーティションに分かれうる。k の変更は 1 時間の区切り（ブロックの区切り）でだけ有効にし、区切りの前後で同じ時刻の点が混ざらないようにする（tsdb-storage-engine の領域）。

### 消費者の決まり

- 消費者は、自分の出力（S3 のブロック・セグメント、Aurora のカタログ）を確定した後でだけ、オフセットを進める。出力とオフセットを同じ記録（ブロックのマニフェスト、カタログの行）に書き、読み直したときに同じ出力を作るか、既にあるものを見て飛ばす。
- 消費者の遅れは利用者への応答を遅らせない。遅れは水位（取り込みの時刻で表した「ここまで反映した」）として計測し、モニターの評価が使う（[ADR-0008](0008-monitor-evaluation-model.md)）。

### 他の案を選ばなかった理由

- **2（Kinesis）**：1 シャードの書き込みの上限（1 MB/秒）で、S1 のピークに数千のシャードが要る。GB/秒の量での費用、保持の延長の費用、消費者の数の扱いが MSK より重い。
- **3（自前の WAL を S3 に）**：S3 の PUT の遅れ（数十〜数百 ms）と要求の費用で、202 の遅れと費用が合わない。小さなファイルの合わせと順序の保証を自前で作ることになり、核ではない部分に作る量が増える。
- **4（SQS・SNS）**：読み直しの位置、パーティションの順序、複数の消費者の独立した位置を持たない。
- **5（直接送る）**：インジェスターの障害がそのまま取り込みの障害になる。消費者を足すたびにゲートウェイを直す。

## Consequences

- 良くなること：
  - 取り込みと保存を切り離し、保存の側の障害・デプロイ・遅れで、取り込みが止まらない。
  - 消費者を足しても、ゲートウェイを変えない。
  - インジェスターのヘッドを、MSK の読み直しで作り直せる。
- 引き受けるコスト：
  - MSK の運用（ブローカーの大きさ、パーティションの数、再配置、バージョンの更新）が増える。共通の基盤からの外れ。
  - データが MSK を通る分、転送と保存の費用が増える（取り込みの量 × 複製 3 × 24 時間）。
  - リージョンの障害では、MSK にだけあるデータ（S3 に書く前）を失いうる。インジェスターのヘッドの checkpoint を 5 分ごとに S3 に置き、テレメトリーの RPO を 30 分にする（NFR-005、[ADR-0009](0009-retention-tiers-on-s3.md)）。

## Confirmation

- 結合テスト（Testcontainers の Kafka）：ブローカーを止めた状態で 202 が返らないこと。確定の後に消費者を任意の位置で落として読み直しても、ブロック・セグメントの中身が同じになること。
- 性質ベーステスト：任意の点の列と読み直しの位置で、インジェスターの結果が、1 回だけ読んだ場合と一致する。
- 負荷試験：`msk-throughput-poc` と E13 で、S1 のピークの 2 倍の書き込みで 202 の p99 が NFR-001 の中。
- lint：`intake-gateway` で、MSK の確定の前に応答を書くコードを禁止する（応答の関数を、確定の結果の型からだけ呼べるようにする）。
