# ADR-0055: `usage-aggregator` は、データのトピックのメッセージの頭と `usage` のトピックを読み、増分とオフセットを Aurora の 1 つのトランザクションで、前の位置を条件に書く。系列の数と保持の件数はカタログの行から ID で 1 回だけ取り込む。時間は 3 時間で確定し、後の訂正は調整の行にする。契約の超過は止めずに数え、止めるのは組織の費用の上限と試用だけ

## Context

- 利用量の差は参照との比べで 0.1% 以内（NFR-012）。MSK を読む消費者は、任意の位置で落ちて読み直しても同じ結果になる必要がある（[ADR-0002](0002-intake-log-on-msk.md)）。Kafka の消費者は、少なくとも 1 回の読み出しが基本で、オフセットの確定と出力の確定を別にすると、二重に数えるか欠ける。
- ADR-0002 は、`metrics`・`logs-raw`・`spans` の消費者に利用量の計測を、`usage` のトピックに「ゲートウェイが数えた利用量」を置いた。
- カスタムメトリクスの系列の数は、時間の中で異なる系列を数える必要があり、点の流れから数えると、系列の集合を時間ごとに持つことになる。インジェスターは、ブロックを書き出すときに、その時間の系列を正確に知っている（[ADR-0004](0004-tsdb-storage-engine.md)）。
- 利用者は、監視が止まることを最も嫌う（[intent.md](../intent.md)）。一方、契約を大きく超える量は原価と他の組織への影響を生む。

## Options

1 回だけの集計：

1. **データのトピックの頭と `usage` を読み、増分とオフセットを条件つきで 1 トランザクションに書く。系列の数・保持の件数はカタログの行から**
2. ゲートウェイが Kafka のトランザクションで、データと利用量のメッセージを同時に書く。集計は `usage` だけを読む
3. 時間ごとに S3 のブロック・セグメントを走査して数える

超過の扱い：

- a. **止めずに数えて知らせる。止めるのは組織が決めた費用の上限と試用だけ**
- b. 契約の量で止める

## Decision

1 と a を採用する。

- `usage-aggregator` はメッセージの頭（`tenant_id`、`host_key`、`raw_bytes`、件数、振り分けの結果）だけを読む。組織・時間・単位ごとの増分を溜め、10 秒か 10 万メッセージごとに、`usage_offsets` を `WHERE next_offset = $start` の条件で進めるのと同じトランザクションで `usage_hourly` に足す。条件に合わなければ捨てる（ゾンビのタスクの二重の加算を防ぐ）。

> 2026-10-09 の注記：この「1 回だけ」は Aurora の条件つきの更新で作るもので、MSK の 1 回だけの読み出しには頼らない。`logs` は `read_committed` で読むが、`logs` のメッセージの出どころ（`src_partition`、`src_offset`）も `usage_offsets` と同じトランザクションで覚え、折り込み済みの位置以下を飛ばす。`log-processor` が Kafka のトランザクションをやめても（[ADR-0030](0030-log-pipeline-execution-model.md) の注記）、二重に数えない（[ADR-0002](0002-intake-log-on-msk.md) の注記）。

- ホストは `(tenant_id, hour, host_key)` の一意の行の集合として足す。
- 系列の数（`metric_blocks`、貸し出しの持ち主のマニフェスト、`origin = ingest`）とスパンの保持の件数（`trace_segments`）は、行の ID を一意の鍵で記録するのと同じトランザクションで足す。
- 時間は `H + 3 時間` に、水位を確かめて確定する。確定の後に来た増分は `usage_adjustments` に入れる。暫定の値は区切りから 2 時間以内に見せる。月は翌月 1 日の 03:00 JST に確定する。
- 契約の超過は止めない。日割りで 80%・100%・150% で知らせる。組織の費用の上限は、ログは索引への振り分けを止め、スパンは保持をエラーのトレースだけに下げ、メトリクスは止めない。試用の組織は、ログの索引とスパンの保持を止め、メトリクスは系列の上限で溢れにする。
- 課金のシステムへは、確定した値を冪等の鍵 `(tenant_id, period, unit, version)` で日ごとに送り、毎日突き合わせる。

### 他の案を選ばなかった理由

- **2（Kafka のトランザクション）**：ゲートウェイの 202 の経路に、トランザクションの開始と確定の往復が足され、遅れ（NFR-001）と調整の費用が増える。`logs-raw` から `logs` への処理は既に Kafka のトランザクションを使う（[ADR-0030](0030-log-pipeline-execution-model.md)）が、それは消費者の側で、202 の経路ではない。`logs` は `read_committed` で読む。
- **3（S3 の走査）**：取り込みのバイト（パイプラインの前）は S3 に残らない。読み出しの費用が大きい。
- **b（止める）**：契約の量に達した瞬間に、利用者の監視とアラートが止まる。超過の請求で調整できる。

## Consequences

- 良くなること：
  - 集計の正しさが、他の消費者と同じ規則（出力とオフセットを同じ記録で確定する）で守られる。
  - 系列の数が、ブロックのマニフェストから正確に出る。
  - 契約の超過で監視が止まらない。
- 引き受けるコスト：
  - `usage-aggregator` が、データのトピックのバッチを展開して読む（ブローカーからの読み出しと CPU）。
  - 系列の数は区切りから 70〜75 分（書き出しのずらしを含む）たたないと出ない。確定を 3 時間にする。
  - 超過の請求の驚きを、知らせで抑える必要がある。

## Confirmation

- 性質ベーステスト：`usage-aggregator` を任意の位置で止めて再開しても、ゾンビのタスクを同時に動かしても、結果が 1 回だけ読んだ場合と一致する。
- 参照との比べ：差 0.1% 以内（[quality.md](../quality.md) の 2.2.1 節 J）。
- 結合テスト：確定の後の増分が調整の行になる。`billing-export` を 2 回送っても課金のシステムの値が変わらない。
- 本番：課金のシステムとの毎日の突き合わせの差を指標にする。
