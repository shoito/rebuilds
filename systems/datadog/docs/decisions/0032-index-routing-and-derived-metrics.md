# ADR-0032: 索引の振り分けは最初に当たった索引、除外のサンプリングは `log_id` のハッシュで決める。1 日の上限は Valkey の予算の前借りで数える。ログから作るメトリクスは、振り分けの前のすべてのログから、10 秒の桶の部分の値を `derived-partials` のトピックで系列ごとに集め直し、1 系列を 1 つの書き手で出す。遅れた分は同じ時刻の点を書き直して直す

## Context

- 組織は複数の索引を持ち、索引ごとにフィルター・除外のフィルター（率つき）・1 日の上限・保持を持つ（[ADR-0005](0005-log-storage-columnar-with-bloom.md)、[Log Indexes](https://docs.datadoghq.com/logs/log_configuration/indexes/)、2026-10-09 に確認）。
- 除外の率で間引くとき、乱数を使うと読み直しで違うログが選ばれる（[ADR-0002](0002-intake-log-on-msk.md)）。
- 1 日の上限は組織の全パーティションの合計で数える。1 つの数えを毎件で更新すると、S1 のピークで Valkey が詰まる。
- ログから作るメトリクスは、除外・上限で索引に入らないログも数える。ログは組織の組の中でばらして置くので、同じ系列が複数のプロセッサーで数えられる。TSDB は同じ系列・同じ時刻の点を「後に取り込んだもの」で決める（[ADR-0004](0004-tsdb-storage-engine.md)）ので、各プロセッサーが点を出すと互いに上書きする。
- スパンから作る RED メトリクスとサービスマップの辺にも、同じ問題がある（`trace_id` でばらすため）。

## Options

ログから作るメトリクス：

1. **部分の値を系列の鍵で集め直す段（`derived-partials` と `derived-metrics-aggregator`）を置き、1 系列を 1 つの書き手にする。遅れは同じ時刻の点の書き直しで直す**
2. プロセッサーごとのタグ（`src_partition`）を付けて別の系列にし、クエリで合計する
3. TSDB に「同じ時刻の count は足す」の意味を足す

1 日の上限：

- a. **Valkey から 1,000 件ずつ前借りする**
- b. 毎件で Valkey を数える
- c. 上限をパーティションの数で割って、流れごとに数える

## Decision

1 と a を採用する。詳細は [logs-pipeline.md](../architecture/logs-pipeline.md) の 9・10 節。

- 振り分け：索引の並びで最初にフィルターに合った索引。除外は最初に合った除外のフィルターの率 `r` で、`xxh3_64(tenant_id ‖ index_id ‖ rule_id ‖ log_id) / 2^64 < r` なら残す。結果（`indexed`・`excluded`・`over_quota`・`unrouted`）を `logs` のメッセージに書く。どの結果でもアーカイブとライブテールに流れる。
- 1 日の上限：Valkey の `quota:{tenant}:{index}:{day}` から 1,000 件ずつ前借りする。日の区切りの時刻と時間帯は索引ごと（既定 `Asia/Tokyo` の 0 時）。超過は最大で「1,000 × 組織のパーティションの流れの数」。Valkey が落ちたら、上限をパーティションの数で割って流れごとに数える。

> 2026-10-09 の注記（データモデル）：取り込みの割り当ての `quota:{cell}:{tenant}:{window}` と紛れないように、鍵の名前を `idxq:{tenant}:{index}:{day}` にした（[data-model.md](../architecture/data-model.md) の D-23）。決定は変えていない。
- ログから作るメトリクス：マスクの後・振り分けの前のすべてのログから、10 秒の桶の部分の値を作り、`derived-partials`（パーティションの鍵は系列の鍵、保持 24 時間）へ書く。`derived-metrics-aggregator` が桶の終わり＋20 秒で合計を `metrics` へ書き、遅れた部分の値が来たら同じ系列・同じ時刻の点を新しい合計で書き直す。桶の状態は 65 分持つ。
- `derived-partials` と `derived-metrics-aggregator` は、スパンから作る RED メトリクスとサービスマップの辺でも使う（[ADR-0039](0039-red-metrics-and-service-map-before-sampling.md)）。

### 他の案を選ばなかった理由

- **2（プロセッサーごとの系列）**：系列の数が組織のパーティションの数（4〜数十）倍になり、カーディナリティの上限と利用量（[ADR-0006](0006-cardinality-policy.md)）を食う。パーティションの組を変えると系列が入れ替わる。
- **3（足す意味）**：「後に取り込んだもの」の規則（読み直しで二重に入っても変わらない）と矛盾し、TSDB の読み直しの性質が崩れる。
- **b（毎件）**：S1 のピークで Valkey の操作が毎秒数百万になる。
- **c（割るだけ）**：組織のログが特定のパーティションに偏ると、上限の前に止まる流れと余る流れができる。

## Consequences

- 良くなること：
  - 振り分けが決定的で、読み直しで同じ。
  - ログから作るメトリクスが、ばらして置いたログでも正しい合計になる。TSDB の意味を変えない。
  - RED メトリクスと同じ仕組みを使える。
- 引き受けるコスト：
  - トピックと状態を持つ部品が 1 つずつ増える（data-model と infrastructure の領域に足す）。
  - ログから作るメトリクスの遅れが、桶の 10 秒と閉じの 20 秒だけ増える。
  - 1 日の上限が数千件の幅で超えうる。

## Confirmation

- 性質ベーステスト：PROP-LOGP-003（決定的なサンプリング）、PROP-LOGP-004（ログから作るメトリクスが参照と一致）。
- 決定表：索引のフィルター × 除外 × 上限 × 索引なしの全行（[quality.md](../quality.md) の 2.2.1 節 H）。
- 障害の注入：`derived-metrics-aggregator` を任意の位置で止めて、チェックポイントから作り直した値が一致する。
