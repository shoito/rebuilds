# ADR-0040: 残したトレースのスパンを `LSEG` のセグメントに置き、時ごとに `trace_id` の並べた索引（フェンスつき）と時のブルームフィルターを書く。ID での引きは、時刻の手がかりの前後の時から、時のブルームフィルター → 索引 → 行のブロックの順に探す

## Context

- 残したトレースを 15 日持つ（[ADR-0009](0009-retention-tiers-on-s3.md)）。スパンはログと同じ列指向の形式で持つ（[ADR-0005](0005-log-storage-columnar-with-bloom.md)、[ADR-0033](0033-log-segment-format-and-tokenizer.md)）。
- トレースの表示は `trace_id` で引く。NFR-003 は ID で引く p99 1 秒を求める。
- `trace_id` は乱数で、時刻を含まない。ログからの移動では時刻の手がかりがあるが、利用者が ID だけを貼ることもある。
- セグメントのブルームフィルターだけで 15 日を探すと、大きな組織では数万のセグメントのフッターを読むことになる。
- 遅れたスパンは、元のトレースと別のセグメントに入る（[ADR-0037](0037-trace-assembly-and-completion.md)）。

## Options

1. **セグメント＋時ごとの並べた ID の索引と時のブルームフィルター**
2. セグメントのブルームフィルターだけ
3. `trace_id` → セグメントの鍵と値の表（DynamoDB など）

## Decision

1 を採用する。詳細は [traces-and-sampling.md](../architecture/traces-and-sampling.md) の 9 節。

- 残したトレースのスパンを組織ごとのバッファーから 10 秒か 64 MiB で `LSEG` 1 にする。`trace_id`・`span_id` を ID の属性としてブルームフィルターに入れる。カタログは `trace_segments`。
- 確定：セグメントの ID は（パーティション、最初のトレースの完成の刻み、組織）で決め、`If-None-Match` で二重を防ぐ。確定の位置を `assembler_offsets` にカタログの行と同じトランザクションで書く。
- 合わせのときに（組織、時）ごとに `tidx`（`trace_id` の順に並べた組、4,096 件ごとのフェンス）と時のブルームフィルターを書き、`trace_hours` に載せる。
- 引き：手がかりがあればその前後 1 時間から、なければ 15 日を新しい順に。合わせていない直近の時はセグメントのブルームフィルター、合わせた時は時のブルームフィルター → `tidx` の範囲の GET → 行のブロック。同じ `trace_id` の遅れた断片を合わせて返す。
- 削除の請求の書き直しで `tidx` と時のブルームフィルターを作り直す。

### 他の案を選ばなかった理由

- **2（セグメントだけ）**：手がかりのない引きで、15 日分のフッターを読む。
- **3（鍵と値の表）**：残すトレース 1 秒 1 万件の書き込みと 15 日の保持の費用が、S3 の索引より重い。正本が 2 か所に分かれる。

## Consequences

- 良くなること：
  - 手がかりがあれば数回の GET で引ける。手がかりがなくても時のブルームフィルターで候補の時を絞れる。
  - 正本は S3 のセグメントだけで、索引は作り直せる。
- 引き受けるコスト：
  - 合わせのときに索引を書く仕事が増える。
  - 時のブルームフィルターを読み手にキャッシュする（大きな組織で 15 日 数百 MB）。

## Confirmation

- 性質ベーステスト：PROP-TRC-006（任意の残したトレースが、手がかりあり・なしで遅れた断片を含めて引ける）。
- 負荷試験：ID で引く p99 1 秒（E13）。
- 試験のベクトル：`tidx` の固定のファイル。
