# ADR-0052: 利用者は組織をまたいで 1 人で、SSO（SAML 2.0・OIDC）と SCIM 2.0 は組織ごとに持つ。アプリケーションキーの効く権限は「スコープ ∩ 持ち主の今の権限」にする。監査ログは、変更を outbox で、読み出しを `query-frontend` から MSK の `audit` に流し、組織の特別な索引として自前のログの保存に置く

## Context

- 利用者は複数の組織に属しうる（[ADR-0003](0003-tenancy-cells-and-isolation.md) の RLS の外の `users`）。企業の利用者の多くは IdP（Microsoft Entra ID、Okta など）で入り、利用者とグループを SCIM で配る（[intent.md](../intent.md)）。
- 公開 API と Terraform はアプリケーションキーで呼ぶ。キーは人に属し、スコープで絞れる（[API and Application Keys](https://docs.datadoghq.com/account_management/api-app-keys/)、2026-10-09 に確認）。人の役割が変わったり、退職したりしたときに、キーが古い権限で残ると危ない。
- 監査ログは、組織の管理者が「誰が何を変え、誰が何を見たか」を調べるのに使う。本家は既定 90 日の保持で、API の要求と製品ごとの変更を記録する（[Audit Trail](https://docs.datadoghq.com/account_management/audit_trail/)、同日に確認）。読み出しまで記録すると、量はクエリの数（S1 のピーク 1 秒 3,000）に比例する。保持の期間は法務の L6。
- 監査ログの欠けは E11 の合否基準で 0 件（[quality.md](../quality.md) の 5 節）。

## Options

監査ログの置き場所：

1. **自前のログの保存に、組織の特別な索引 `audit` として置く。変更は outbox、読み出しは MSK へ直接**
2. Aurora の表に置く
3. AWS の別のサービス（CloudWatch Logs、Firehose と Athena）に置く

アプリケーションキーの権限：

- a. **スコープ ∩ 持ち主の今の権限**
- b. 作ったときの権限の写しを持つ

## Decision

1 と a を採用する。

- SSO は組織ごとの SAML 2.0・OIDC。JIT の作成、IdP のグループ → 役割・チームの対応表、「SSO だけ」の設定と指名した管理者の非常の入口を持つ。IdP の不変の ID で利用者を結ぶ。
- SCIM 2.0 の `Users`・`Groups` で同期し、停止から 60 秒以内にセッションと本人が持ち主のアプリケーションキーを止める。1 時間に利用者の 20% を超える停止は保留して確かめる。
- アプリケーションキーは利用者かサービスのアカウントに属し、効く権限はスコープと持ち主の今の権限の積。制限の述語も持ち主のもの。既定の期限 1 年。
- 監査ログ：変更は変更と同じトランザクションで outbox に書き、`relay` が MSK の `audit` へ送る。読み出しは `query-frontend` がローカルのディスクの待ち行列を経て `audit` に書き、溢れたら新しいクエリを拒む。`log-indexer` が組織の索引 `audit` のセグメントにする。値（クエリの文字列、タグの値、ログの本文）は持たず、ID と数と理由のコードを持つ。保持は既定 90 日（仮。法務の L6）。`audit-archiver` が組織・日ごとのハッシュの連鎖を log-archive のアカウントの Object Lock に写す。

### 他の案を選ばなかった理由

- **2（Aurora）**：読み出しの記録は 1 日 2 億件を超えうる。管理の DB の書き込みと保存を圧迫する。検索と書き出しを別に作ることになる。
- **3（AWS の別のサービス）**：組織ごとの分離（RLS 相当）、データのアクセスの制限、検索の文法を別に作る。組織に見せる画面がログの検索と別になる。
- **b（権限の写し）**：役割を減らしても、退職しても、キーが古い権限で残る。

## Consequences

- 良くなること：
  - 監査ログを、ログと同じ検索・ファセット・書き出しで見られる。保存の費用が GB あたりで安い。
  - 人の権限の変更が、その人のキーにすぐ効く。
- 引き受けるコスト：
  - 監査ログの表示が、本システムのログの保存の可用性に依る（変更の記録は outbox に残るので失わない）。
  - 読み出しの記録の欠けは、待ち行列と照合で抑えるが、変更の記録ほど強くない。
  - 持ち主の役割を変えると、その人のキーで動く自動化が止まりうる。サービスのアカウントを勧める。

## Confirmation

- 結合テスト：SCIM の停止から 60 秒以内にセッションとキーが効かない。SAML・OIDC の署名・期限・宛先・`InResponseTo` の誤りを拒む（試験のベクトル）。
- 経路の検査：変更の API の全経路で監査の事象が 1 件ずつ出ることを、経路の一覧と照らす（CI）。
- 本番：返したクエリの数と、`audit` の読み出しの事象の数を、組織・時間ごとに照合し、差を SLI にする。
