# ADR-0031: PII のマスクは、パイプラインの後、振り分け・ログから作るメトリクス・ライブテールの前に、すべての文字列の値に当てる。動作は伏せる・一部を残す・組織の鍵での HMAC の 3 つ。終わらない値は全体を伏せる（fail closed）。規則はバージョンを持ち、過去に遡らない。既定の有効化は法務の L1 の後に決める

## Context

ログには、利用者の顧客のメールアドレス、電話番号、IP アドレス、カードの番号、マイナンバーが混ざる（[intent.md](../intent.md)）。intent の守るべき振る舞いは「マスクの規則に当たる値は、索引・保存・アーカイブ・ライブテールのどこにもマスクの前の形で残らない」。

- パイプラインの解析で、本文の中の値が属性に移る（grok で `usr.id` を取り出す）。解析の前にだけマスクすると、属性に移った値を見落とすことはないが、解析の規則が `[REDACTED]` を前提に書けず、解析が合わなくなる。
- 解析の後にだけマスクすると、解析の途中の値はプロセスのメモリーの中にだけあり、外へ出なければ漏れではない。
- マスクが失敗・時間切れのときに値を流すと、漏れになる。
- どの種類を既定で有効にするかは、委託の扱い（法務の L1）で変わる。
- 本家の Sensitive Data Scanner の既定の規則と動作は、確かめなかった（**未検証**）。

## Options

位置：

1. **パイプラインの後、振り分けの前に、すべての文字列の値に当てる**
2. パイプラインの前に、本文にだけ当てる
3. 前と後の 2 回当てる

失敗のとき：

- a. **値の全体を伏せる（fail closed）**
- b. 値をそのまま流し、数を数える

## Decision

1 と a を採用する。詳細は [logs-pipeline.md](../architecture/logs-pipeline.md) の 8 節。

- 対象は本文とすべての文字列の属性の値。検出の種類は `email`、`phone_jp`、`credit_card`（Luhn）、`my_number`（チェックディジット）、`ipv4`・`ipv6`、`jwt`、`secret_key`、組織の独自の規則。
- 動作は `redact`（既定）、`partial`、`hash`（組織ごとの鍵の HMAC-SHA256 の先頭 64 ビット）。
- マスクにも手順の予算を持ち、超過・誤りでは値の全体を `[REDACTED:scrub_error]` にする。
- 規則は設定の束のバージョンで配り、各ログに `scrub_rules_version` を書く。規則の変更は、これから取り込むログにだけ効く。過去は削除の請求で消す（[ADR-0036](0036-personal-data-deletion-tombstones.md)）。
- マスクの前の値は `log-processor` のメモリーと `logs-raw`（24 時間）にだけある。エラー・パニックのメッセージに値を入れない。
- 既定の有効化は決めない（**法務の確認待ち：L1**）。組織の設定 `scrub_default_profile` で、全種類・一部・なしのどれにも切り替えられる形にする。
- スパンの属性にも同じ `pii-scrub` の crate と組織の規則を使う（[traces-and-sampling.md](../architecture/traces-and-sampling.md)）。

### 他の案を選ばなかった理由

- **2（前に本文だけ）**：属性で届く値（JSON のログ、OTLP の属性）を見落とす。解析が `[REDACTED]` を前提にすることになる。
- **3（2 回）**：処理が倍になる。1 の位置で、解析で作った属性を含むすべての値を見られるので足りる。
- **b（流す）**：失敗が漏れになる。誤検出で伏せすぎる損より、漏れの損が大きい。

## Consequences

- 良くなること：
  - 索引・アーカイブ・ライブテール・ログから作るメトリクスのタグに、マスクの前の値が出ない。
  - 解析の規則は元の値を前提に書ける。
  - 法務の結論がどれでも、既定の切り替えだけで対応できる。
- 引き受けるコスト：
  - すべての文字列の値を走査する CPU。E5 の負荷試験で測る。
  - 誤検出で調査に要る値が伏せられることがある（`partial`・`hash` で補う）。
  - マスクは戻せない。規則の誤りで伏せすぎた値は戻らない。
