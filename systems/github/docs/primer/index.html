GitHub は何をするサービスか

Git のリポジトリを預かり、その上でレビュー・課題の管理・CI を回す場です。使うのは、開発者・Organization の管理者・外部のツール、そして API で操作する AI エージェントです。

  1. リポジトリを git clone で手元に取る。
  2. ブランチを切ってコミットし、git push でサーバーに送る。
  3. Pull Request（PR）を開き、取り込みを提案する。
  4. CI が走り、レビュアーが差分を読んで承認する。
  5. 保護の規則を満たしたら、既定のブランチにマージする。
  6. マージの事象が Webhook・通知・CI に伝わり、デプロイなどが続く。

公開のリポジトリはだれでも読め、非公開のリポジトリは権限のある人だけが読めます。この 2 つが同じ基盤に混ざっていることが、設計の難しさの多くを生みます。規模は S1 で 100 万リポジトリ、1 日 10 万人、Git の要求はピークで 2,000 件/秒を見込みます。

設計の文書のどこで効くか3 つの価値と「守るべき振る舞い」は intent.md、規模は architecture/README.md の 2 節にあります。規模の段階の考え方は共通の資料を見てください。

Git のしくみ：オブジェクトと ref

Git の中身は、中身のハッシュを名前にしたオブジェクトの集まりです。名前が中身で決まるので、一度書いたオブジェクトは変わりません。

flowchart LR
  R["ref: refs/heads/main"] --> C3["commit C3"]
  C3 -- "parent" --> C2["commit C2"]
  C2 -- "parent" --> C1["commit C1"]
  C3 --> T["tree: ディレクトリ"]
  T --> B1["blob: README.md"]
  T --> B2["blob: main.go"]
  • blob（ファイルの中身）、tree（ディレクトリ）、commit（tree と親と作者）、tag の 4 種類があります。名前は SHA です。
  • ref は「名前 → コミットの SHA」の対応だけです。ブランチは ref の 1 つにすぎません。
  • オブジェクトは packfile にまとめて圧縮し、やり取りします。
要点push で変わるのは、新しいオブジェクトの追加と ref の付け替えだけです。だから「ref をどう安全に動かすか」が保存の設計の中心になります。
設計の文書のどこで効くか中身の正本を Git に置く決定（ADR-0005）と、SHA の組で差分をキャッシュできる理由（ADR-0010）の前提です。

push と fetch でサーバーがすること

Git のクライアントは HTTPS か SSH でサーバーと話します。いまの既定はプロトコル v2 です。HTTPS では、パスワードではなくトークンで認証します。

  1. 認証し、そのリポジトリに書き込めるかを判定する。
  2. クライアントが「ref・旧い SHA・新しい SHA」の一覧を送る。
  3. packfile を受け、検疫の領域で壊れていないかを検査する。
  4. 大きさ・ref の名前・ブランチの保護の規則を検査する。
  5. ref を「旧い値のときだけ新しい値へ」更新する。
  6. ref ごとに ok か理由つきの ng を返す。
  1. ls-refs：サーバーが ref の一覧を返す。
  2. クライアントが欲しいコミット（want）と、持っているコミット（have）を伝える。
  3. サーバーが差分のオブジェクトを数え、packfile を作って流す。

3 の「数える」が重い処理です。clone は全履歴を数えるので、とくに重くなります。

新しいコミットが旧いコミットの子孫なら、ref を前に進めるだけで済みます。これが fast-forward です。子孫でない更新は履歴を書き換えるので、--force が要ります。保護の規則はこれを禁止できます。

設計の文書のどこで効くか検査の順序と時間の予算は git-protocols.md の 5 節、フロントエンドが状態を持たない理由は ADR-0004 です。

3 つの複製と ref の更新の合意

リポジトリは、別々の AZ にある 3 台のストレージのノードに、普通の Git のリポジトリとして置きます。ディスクはノードのローカルの NVMe で、ノードは使い捨てです。だから過半数（2 つ）に書けたときだけ成功を返します。

sequenceDiagram
  participant C as 調整役
  participant R as 複製 A・B・C
  participant D as Aurora
  C->>R: 1 PREPARE ref をロックし旧い値を確かめる
  R-->>C: 票 ok と前後のチェックサム
  C->>D: 2 version を CAS で予約
  C->>R: 3 COMMIT
  R-->>C: ack
  C->>D: 4 checksum と version を確定し outbox に書く
  C-->>C: 5 クライアントに成功を返す

複製が同期しているかは、全 ref の「名前と値」のハッシュの XOR であるチェックサムで判定します。同じリポジトリへの push は、DB の version の CAS で 1 列に並びます。

3 つの複製のうち 1 つにしか書けなかったとき、push はどうなりますか？

成功を返した push を失わないため、2 つ以上の ack と DB の確定の後にだけ成功を返します。同じ push を再送しても、ref がすでに新しい値なら「最新」として扱われます。

設計の文書のどこで効くか手順と回収は git-storage.md の 5 節、決定は ADR-0003 と ADR-0006 です。outbox は共通の資料を見てください。

fork とネットワーク

fork は、他人のリポジトリを自分のアカウントの下に写したものです。権限のない人も、fork に push してから元のリポジトリへ PR を出せます。これが OSS への貢献の普通の形です。

元のリポジトリと全ての fork を、1 つのネットワークにまとめます。オブジェクトはネットワークで 1 か所に集め、各リポジトリは alternates でそこを参照します。fork の作成は ref を写すだけで、コピーはありません。

共有の副作用ある fork に push したコミットは、同じネットワークの他のリポジトリから SHA を指定すると見ええます。Git のプロトコル v2 の fetch は、広告していない want も弾かないためです。公開のネットワークでは本家と同じく仕様として受け入れ、非公開のネットワークでは到達できるかを検査します（本家との違い）。

公開のリポジトリを非公開に変えました。その公開の fork はどうなりますか？

1 つのネットワークに公開と非公開を混ぜると、非公開のオブジェクトが公開の側から SHA で引けてしまいます。そこで切り離し、ネットワークの公開の種類を常に 1 つに保ちます。

設計の文書のどこで効くかADR-0007、git-storage.md の 7 節、identity-and-permissions.md の 6 節です。

clone を速く・安くする道具

clone は「送るオブジェクトを数えて pack を作る」計算と、帯域を食います。Git の本体にある道具と、配り方の工夫を組み合わせます。

push のたびに小さな pack が増えます。repack でまとめ、到達できないオブジェクトは猶予の後に消します。消すのが早すぎると、進行中の push が参照するオブジェクトを壊します。

到達可能性のビットマップは、あるコミットから届くオブジェクトの集合を前もって計算したものです。clone で履歴を歩かずに済みます。commit-graph は、merge base の計算や fetch の交渉を速くします。

CI やボットは同じ clone を短い間に繰り返します。同じ要求の pack をノードで使い回します。人気の公開リポジトリは、bundle-uri で CDN から配ります（クライアントの既定では無効）。

partial clone は blob を後で取り、shallow clone は古い履歴を取りません。CI は shallow が既定です。

Git LFS は、大きなファイルを Git の外に置き、リポジトリには小さな「指し先」だけを入れます。本体は S3 に、presigned URL で直接やり取りします。

設計の文書のどこで効くかADR-0008、ADR-0009、git-storage.md の 8 節、git-protocols.md の 6・7 節です。

Pull Request：base・head・三点の差分

PR は「head の ref の変更を、base の ref に取り込む提案」です。head は同じリポジトリか、同じネットワークの fork のブランチです。

flowchart LR
  M["merge base"] --> B1["base の新しいコミット"]
  M --> H1["head のコミット 1"]
  H1 --> H2["head のコミット 2"]

画面の差分は merge base から head までの三点の差分です。「PR が持ち込む変更」だけが見えます。

base のリポジトリに refs/pull/{number}/head（head の最新）と refs/pull/{number}/merge（試しにマージした結果）を持ちます。fork が消えても PR を読め、CI は merge の方を対象に走ります。

merge：親が 2 つのマージのコミットを作る。squash：変更を 1 つのコミットにまとめる。rebase：head の各コミットを base の上に載せ直す（SHA が変わる）。

衝突の有無は裏で計算し、終わるまで mergeable は null です。入力の SHA が決まれば結果も決まるので、SHA の組でキャッシュできます。

PR を開いた後、base のブランチに他の人の変更がマージされました。PR の画面の差分はどうなりますか？

三点の差分は、base が進んでも変わりません。ただし、マージ可能かの計算は base と head の現在の SHA でやり直します。

設計の文書のどこで効くかpull-requests.md の 1・3・6 節と ADR-0010 です。

レビューとブランチの保護（ruleset）

既定のブランチは、だれでも書き換えてよいものではありません。「承認が 2 件」「CI が成功」などの条件を、ruleset で表します。

レビュー

結論は承認・変更の依頼・コメント。数に入るのは、書き込み権限を持つ人の、レビュアーごとの最新の結論だけ。新しい push で古い承認を取り消せる。

CODEOWNERS

パスごとのオーナーを書いたファイル。base 側のファイルを使い、後に書いた一致が優先する。詳しく

ステータスチェック

CI の結果はコミットの SHA に付く。送り手の App を指定し、名前のなりすましを防ぐ。詳しく

ruleset

対象の ref のパターン、規則、バイパスできる主体を持つ。複数が重なれば、最も厳しいものが効く。

要点規則は「git push」と「PR のマージ」の 2 つの経路で効きます。片方だけで判定すると、もう片方から迂回されます。だから 1 つの評価関数を両方から呼び、判定の材料が読めないときは拒否します（fail closed）。
設計の文書のどこで効くかADR-0011、pull-requests.md の 4・5 節です。

merge queue

「最新の base で CI が通ったものだけ入れる」とすると、だれかがマージするたびに、他の全ての PR が base を取り込み直して CI をやり直します。PR の多いリポジトリでは進みません。merge queue はこれを解きます。

  1. 承認などの条件を満たした PR を、キューに入れる。
  2. 「最新の base ＋ 前に並ぶ PR ＋ その PR」を合わせた一時的なブランチを作る。
  3. CI に merge_group の事象を送り、必須のチェックを走らせる。
  4. 通ったら、base をそのブランチの SHA へ fast-forward で進める。検査した SHA と取り込む SHA が同じになる。
  5. 失敗した PR は外し、後ろのグループを作り直して続ける。

一時的なブランチの名前は <brand>-readonly-queue/… です。CI のワークフローが merge_group を契機に持たないと、キューでチェックが走りません。

設計の文書のどこで効くかADR-0012、pull-requests.md の 8 節です。

権限：公開の種類とロールの合成

リポジトリの公開の種類は public・private・internal（E10 から）です。ロールは本家と同じ 5 つです。

read < triage < write < maintain < admin

権限の元与えるロール
個人のリポジトリの持ち主、Organization の owneradmin
直接のコラボレーター付けたロール
チーム（親チームのロールは子に引き継ぐ）チームのロール
基本の権限（メンバーだけ。外部のコラボレーターには効かない）既定は read
公開の種類が publicだれでも read

実効のロールは、これらの最大値です。「拒否」の規則はありません。

権限のない人が、非公開のリポジトリの URL を開きました。何を返しますか？

403 を返すと「そこにリポジトリがある」ことが漏れます。読めない資源には 404 を返し、存在を明かしません。403 は、読めるが書けないときだけです。

設計の文書のどこで効くかなぜ RLS（共通の資料）ではなく判定関数 can() にするかは ADR-0002 です。1 人が多数の持ち主の公開リポジトリを読むので、持ち主はテナントになりません。合成の規則は ADR-0018 です。

API と Webhook

外部のツールと AI エージェントは、REST と GraphQL の API で操作します。REST は日付のバージョンをヘッダー X-<Brand>-Api-Version で選びます。互換を壊す変更は新しいバージョンだけに入れ、追加は全てのバージョンに入れます。

Webhook は逆向きで、事象が起きたらサーバーが相手の URL へ POST します。受け手は、次の順で確かめます。

  1. 本文の生のバイト列と、共有の秘密で HMAC-SHA256 を計算する。
  2. X-<Brand>-Signature-256 の sha256=… と、定数時間で比べる。
  3. X-<Brand>-Delivery の GUID で重複を捨てる（再送でも同じ値）。
  4. 順序は保証されないので、本文の状態で冪等に処理する。

送る側は、送る直前に権限を確かめ直し、宛先が社内のアドレスでないかを検査します（SSRF の対策）。送信は本体とつながらない隔離した環境から出します。

設計の文書のどこで効くかADR-0021、ADR-0022、api-and-webhooks.md の 4・9 節です。冪等は共通の資料を見てください。

CI（Actions）：だれのコードを、どの秘密で動かすか

ワークフローは .<brand>/workflows/*.yml に書き、push や PR などの事象で起動します。1 つの実行は複数のジョブ、ジョブは複数のステップからなり、ジョブはランナーで動きます。

前提公開のリポジトリには、だれでも PR を出せます。ジョブのコードは常に悪意があるものとして扱います。ホストのランナーは 1 ジョブ 1 つの microVM で、使ったら壊します。
起動シークレット<BRAND>_TOKEN
同じリポジトリのブランチからの PR渡すワークフローの permissions の範囲
fork からの PR（pull_request）渡さない読み取りだけ
pull_request_target渡す公開のリポジトリでは既定で止める

クラウドへのデプロイには、長命の鍵の代わりに OIDC の短命の ID トークンを使います。クラウドの側は sub などの claim で「どのリポジトリのどのブランチか」を確かめます。

fork からの PR で動くジョブが、デプロイ用のシークレットを読めないのはなぜですか？

PR のワークフローやテストのコードは、PR を出した人が自由に書き換えられます。そこで秘密を渡さず、トークンも読み取りだけにします。

設計の文書のどこで効くかactions.md の 6・7・8 節、ADR-0023、ADR-0025、ADR-0026 です。

信頼できない内容を安全に見せる

README、Issue の本文、SVG、ノートブックは、だれでも書けます。アプリと同じオリジンで描くと、利用者の書いたスクリプトが閲覧者のセッションで動きます（XSS）。

危ない

生のファイルをアプリのサブドメインから HTML として返す。サブドメインは同じサイトなので、Cookie が送られ、上書きもされうる。

安全

利用者の内容は別の登録可能ドメイン（<brand>usercontent.<domain>）から、text/plain・nosniff・CSP の sandbox 付きで返す。

  • Markdown は、サーバーで HTML にしてから許可リストで無害化します。
  • SVG は <img> で読み、スクリプトを動かしません。
  • ノートブックや Mermaid は、allow-same-origin を付けない sandbox の iframe で描きます。
  • 利用者の内容のドメインは Public Suffix List に登録し、サブドメインどうしも別のサイトにします。
設計の文書のどこで効くかADR-0013、web.md の 4・5 節です。

検索と通知：権限を前段で効かせる

コードを部分一致で探すには、全文検索の単語の索引では足りません。Zoekt は、3 文字ずつの断片（trigram）の索引で候補を絞ってから、本文を照合します。索引するのは既定のブランチだけです。Issue・PR・リポジトリの検索は OpenSearch に置きます。

結果を取った後に権限で除くと、件数やページの欠けから、読めないリポジトリの存在が漏れます。そこで「読めるリポジトリ」の条件を、クエリの中に入れて前段で絞ります。公開の種類を変えたリポジトリは、索引を直すまで除外の表で全ての検索から外します。

リポジトリの watch と、スレッドへの「参加」（作った・コメントした・メンションされた・レビューを頼まれた）で受け手が決まります。権限は事象のときと送るときで変わりうるので、送る直前に確かめ直します。

設計の文書のどこで効くかADR-0014、ADR-0015、ADR-0016、search.md の 4 節、notifications.md の 2・3 節です。

  • 各表には権限の区分（R・A・O・U・S・P）があります。R の表は必ず repo_id を持ち、can() を通して読みます。
読み違えやすい点「S3」は、規模の段階の S3 と、AWS の Amazon S3 の両方の意味で出てきます。前後の文脈で見分けてください。
設計の文書のどこで効くかdata-model.md の 2・3・4 節と、ADR-0017 です。記号は共通の資料を見てください。

用語集

オブジェクト
Git が保存する単位。blob・tree・commit・tag の 4 種類。中身のハッシュが名前になる。
SHA
オブジェクトの名前に使うハッシュ。多くのリポジトリは SHA-1（20 バイト）で、SHA-256 のリポジトリもある。
ref
名前からコミットの SHA への対応。ブランチ（refs/heads/*）やタグ（refs/tags/*）。
packfile
多数のオブジェクトを差分で圧縮して 1 つにまとめたファイル。転送と保存に使う。
プロトコル v2
Git の通信の新しいバージョン。ls-refs で要る ref だけを聞き、fetch で pack を取る。
検疫
push で届いたオブジェクトを、検査が終わるまで本体と分けて置く領域。
fast-forward
新しいコミットが旧いコミットの子孫で、ref を前に進めるだけで済む更新。
チェックサム
この設計では、全 ref の「名前と値」のハッシュの XOR。複製が同期しているかの判定に使う。
CAS
Compare-and-swap。「今の値が期待どおりのときだけ書き換える」操作。
ネットワーク
元のリポジトリとその全ての fork の集まり。オブジェクトを共有し、同じノードに置く。
alternates
Git の仕組み。別の場所のオブジェクトの置き場も、自分のものとして読む。
repack
pack をまとめ直す保守の作業。不要なオブジェクトは cruft pack に移し、猶予の後に消す。
到達可能性のビットマップ
あるコミットから届くオブジェクトの集合を、ビット列で前もって持つ索引。
commit-graph
コミットの親子と世代を持つファイル。履歴の走査を速くする。
bundle-uri
clone の前に、サーバーが案内する URL から bundle（履歴の固まり）を取らせる Git の仕組み。
partial clone
blob などを一部だけ取り、要るときに後から取る clone。
Git LFS
大きなファイルを別の保存先に置き、リポジトリには指し先（pointer）だけを入れる拡張。
merge base
2 つのコミットの共通の祖先のうち、最も新しいもの。
三点の差分
base...head。merge base から head までの差分。PR が持ち込む変更だけを表す。
ruleset
ref のパターンに掛ける保護の規則の集まり。本家の旧来の branch protection rule の後継。
CODEOWNERS
パスのパターンごとにオーナーを書くファイル。該当するファイルの変更に、オーナーのレビューを求められる。
ステータスチェック
コミットの SHA に付く外部の検査の結果。commit status と check run の 2 つの形がある。
fail closed
判定に要る情報が得られないとき、許可ではなく拒否の側に倒すこと。
merge queue
PR を順に並べ、まとめて検査してから取り込む仕組み。
基本の権限
Organization のメンバー全員に、その Organization の全リポジトリへ与えるロール。
PAT
Personal Access Token。ユーザーが作るトークン。細粒度のものとクラシックのものがある。
App
本家の GitHub App に相当する連携の形。アカウントに「インストール」し、自分の bot として権限の範囲で動く。
インストールのトークン
App がインストールの範囲で API を呼ぶための、1 時間で切れるトークン。
デプロイキー
1 つのリポジトリにだけ結び付いた SSH の鍵。
Webhook
事象が起きたとき、登録した URL へサーバーから HTTP で知らせる仕組み。
HMAC
共有の秘密とハッシュで作る署名。送り手と改ざんのなさを確かめる。
SSRF
サーバーに内部のアドレスへ要求を出させる攻撃。
ワークフロー
CI の定義の YAML。起動の事象、ジョブ、ステップを書く。
ランナー
ジョブを受け取って実行する環境とエージェント。ホストのものとセルフホストのものがある。
microVM
起動の速い軽量の仮想マシン。この設計は Firecracker を使う。
pull_request_target
base のリポジトリのワークフローを、秘密と書き込みのトークン付きで動かす起動の事象。PR のコードを実行すると危ない。
OIDC
OpenID Connect。ジョブが署名付きの短命の ID トークンを得て、クラウドに身元を示す。
無害化
HTML から、許可した要素と属性以外を落とすこと。
Public Suffix List
ブラウザが「どこまでが 1 つのサイトか」を決めるのに使う公開の一覧。
Zoekt
オープンソースのコード検索のエンジン。trigram の索引を使う。
trigram
連続する 3 文字の断片。部分一致の検索の候補を絞るのに使う。
watch
リポジトリの活動の通知を受け取る設定。参加とメンションだけ、全て、無視などの水準がある。
