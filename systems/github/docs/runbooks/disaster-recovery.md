# Runbook: 災害復旧（AZ の障害、リージョンの障害、リポジトリの復元、訓練）

- Owner: Ops
- 対応するアラート: AZ の障害（複数の部品で 1 つの AZ のターゲット・ストレージのノードが不健全）、合成監視の連続失敗（大阪から東京が見えない）、複製が 1 つしかないリポジトリの発生、訓練（四半期）
- 最終確認日: 2026-09-26

構成と目標は [infrastructure.md](../architecture/infrastructure.md) の 5 節と [ADR-0032](../decisions/0032-disaster-recovery-strategy.md) にある。目標は NFR-008（AZ：RPO 0、RTO 5 分）と NFR-009（リージョン：RPO 15 分、RTO 4 時間。範囲は ADR-0032）。DB とアプリの切り替えは Slack の [disaster-recovery.md](../../../slack/docs/runbooks/disaster-recovery.md) と同じ部分が多い。

## 症状

| 場面 | 見え方 |
| --- | --- |
| A. AZ の障害 | 1 つの AZ のストレージのノード・タスク・Aurora のインスタンスが不健全になる。AWS Health に、東京の 1 つの AZ のイベントが出る |
| B. リージョンの障害 | 東京の複数の部品が同時に応答しない。大阪からの合成監視がすべて失敗する |
| C. リポジトリの複製の喪失 | ソフトウェアの誤り・複数のノードの喪失で、あるリポジトリの健全な複製が 1 つ以下になった。チェックサムの検査で 3 つの複製がそろって壊れていた |
| D. DB の論理的な破損 | 誤ったマイグレーション・操作でメタデータが壊れた |
| E. 訓練 | 定期作業 |

## 影響

- A：数十秒〜数分、Git の操作の失敗と、進行中の clone の切断が起きる。成功を返した push は失わない。AZ を失っている間は、別のノードの喪失に対する余裕がない。
- B：切り替えまで全面的に使えない。最大 15 分の push を失いうる。4 時間以内に戻るのは、Web・API と直近 7 日に使われたリポジトリ。残りは 24 時間以内。Actions とコード検索は後回し。
- C：そのリポジトリの書き込みが止まる。バックアップの時点より後の push を失いうる。
- D：Slack と同じ。

## 確認

1. AWS Health と、Grafana の AZ ごとの内訳（ターゲット、ストレージのノードの健全性、エラー率）で、1 つの AZ か、リージョン全体かを見分ける。
2. ストレージの制御のダッシュボードで、次を見る。
   - 複製が 2 つのリポジトリの数、1 つのリポジトリの数
   - 喪失・退避中のノード
   - 修復の待ちと最古の経過時間
3. Aurora の writer の AZ と、フェイルオーバーの有無。
4. バックアップの遅れ（最新の p99）。リージョンの切り替えで失う範囲の目安になる。
5. リージョンの障害を疑うときは、大阪の合成監視と、外部からの到達性の両方で確かめる。

## 対処

### A. AZ の障害

基本は自動で続く（Git は残る 2 つの複製、Aurora はフェイルオーバー）。人は確認と、長引いたときの補助をする。

1. インシデントを SEV2 で宣言する（[incident-response.md](incident-response.md)）。
2. **ストレージの列車・Git の版の更新・保守（repack）の大きなものを止める。** 余裕のない間に、他のノードを止めない。
3. ストレージの制御が、障害の AZ のノードを「喪失の疑い」にし、修復を**まだ始めていない**ことを確かめる。AZ の一時的な障害で数十 TB の修復を始めると、戻ったときに無駄になり、残る AZ の帯域を使う。
4. Aurora が別の AZ にフェイルオーバーしたことを確かめる。5 分たっても writer がなければ、手動でフェイルオーバーする。
5. Git フロントエンド、Web・API のタスクが残る 2 つの AZ で足りているかを見る。足りなければ最小タスク数を上げる。
6. **1 時間たっても AZ が戻らないとき**：ストレージの制御で「AZ を分ける規則の一時的な緩和」を有効にし、書き込みの多いリポジトリ（直近 24 時間に push のあったもの）から順に、残る 2 つの AZ の中に 3 つ目の複製を作る。帯域の上限は [capacity.md](../architecture/capacity.md) の 3.2 節のまま。
7. AZ が戻ったら：
   - 戻ったノードを 1 台ずつ検査し（チェックサム）、遅れた ref を追いつかせて、ルーティングに戻す。
   - データが失われたノード（再起動ではなく入れ替えられたもの）は、喪失として扱い、修復で作り直す。
   - 緩和で作った一時の複製を、配置の規則に戻す（AZ の複製が戻った後に消す）。
   - 規則の緩和を無効にする。

### B. リージョンの障害（東京 → 大阪）

**切り替えの判断は、IC が行い、Ops の責任者が承認する。** 最大 15 分の push を失い、全リポジトリが戻るまで 24 時間かかる。AWS の見込みで数時間以内に回復しそうなら、待つことも選ぶ。

1. インシデントを SEV1 で宣言し、利用者へ告知する。
2. 東京に書き込みが届いているなら止める（`ops.read_only_mode` を全体に）。
3. **DB を切り替える。** Slack の手順と同じ（Aurora Global Database の大阪の二次クラスタを昇格し、インスタンスを作る）。昇格の直前に、複製の遅延を記録する。
4. **大阪の基盤を作る。** GitHub Actions の「DR：大阪にデプロイ」のワークフローで、Terraform の大阪のルートモジュールを apply する。状態ファイルは大阪のバケットにある。
   - ストレージのノード：まず AZ ごとに 14 台（S1 の台数）。`i8g` の在庫がなければ、ワークフローの変数で `i7i`・`i4i`、または EBS（gp3）の構成を選ぶ（ADR-0032）。
   - Git フロントエンド、Web・API、Worker（ECS）。
5. **Git を復元する。** ストレージの制御の「バックアップからの復元」を、次の優先度で始める。
   1. 合成監視のリポジトリ、社内の Organization
   2. 直近 7 日に push か fetch のあったリポジトリ（DB の記録から一覧を作る）
   3. 残り（アクセスされたものを先に）
   - 最初は複製を 1 つで戻し、全体が戻ってから 3 つにそろえる。1 つの間は、書き込みを受けない（読み取りだけ）。優先度 2 までが 3 つにそろったら、そのリポジトリの書き込みを開く。
6. **DB と Git の食い違いを直す。** 復元したリポジトリごとに、ref の写し（DB）を Git から作り直す（[ADR-0005](../decisions/0005-git-as-source-of-truth.md)）。push の Event の記録のうち、復元した ref より新しいもの（失った push）を一覧にして保存する。
7. CloudFront のオリジンと、SSH の NLB の DNS を大阪に切り替える。
8. 大阪の合成監視（clone、push、PR の表示、権限の確認）が通ることを確かめ、読み取り専用を解除する（リポジトリ単位で、復元済みのものから）。
9. Webhook と通知は、DB の outbox から再開する。コード検索の索引は作り直す。Actions は止めたままにし、利用者に告知する。
10. 失った push の一覧をもとに、影響を受けたリポジトリの管理者へ、再 push を頼む連絡を出す（文面は PM と合意する）。
11. 4 時間の時点と 24 時間の時点で、戻ったリポジトリの割合を記録する。

**東京へ戻す（フェイルバック）**：東京が回復してから、別の計画作業として行う。東京のストレージのノードを作り、大阪から全リポジトリを複製してから、DB を計画的な切り替え（RPO 0）で戻し、ルーティングを切り替える。急がない。戻るまでの間、バックアップは大阪の別のバケット（または東京が回復していれば東京）に書く。

### C. リポジトリの複製の喪失

1. 健全な複製が 1 つ残っているなら、それを正として修復を最優先にする（ストレージの制御で、そのリポジトリの修復の優先度を最高にする）。修復が終わるまで、そのリポジトリを読み取り専用にする。
2. 健全な複製がないなら、そのリポジトリを読み取り専用にし、大阪のバックアップから復元する。
   - 最新の完全なバンドルと、その後の差分を順に適用し、ref を最新の ref の一覧に合わせる。
   - 復元したリポジトリのチェックサムを記録し、3 つの複製に配る。
3. バックアップより後の push（push の Event の記録で分かる）を一覧にし、SEV1 としてリポジトリの管理者へ連絡する（成功を返した push を失ったため）。
4. 原因がソフトウェアの誤りなら、同じ誤りで他のリポジトリも壊れていないか、チェックサムの検査を全体に走らせる。

### D. DB の論理的な破損

Slack の手順と同じ（PITR で隔離した VPC に復元し、失われた行を戻す）。ref の写しが壊れた場合は、PITR ではなく Git から作り直す。

### E. 訓練

| 訓練 | 頻度 | 場所 | 見ること |
| --- | --- | --- | --- |
| ストレージのノード 1 台の終了と修復 | 月 1 回 | staging（四半期に 1 回は prod で、事前に退避したノードを使う） | 修復が 2 時間以内。チェックサムの一致 |
| バックアップからのリポジトリの復元 | 毎日（自動、1,000 件） | prod の隔離した環境 | ref とチェックサムの一致 |
| AZ の分断 | 四半期 | staging | push が失われない。RTO 5 分 |
| 大阪への切り替え | 四半期（staging）、年 1 回（prod のバックアップの 20% を大阪へ復元） | staging、prod | 7 日のアクティブなリポジトリが 4 時間以内。全体の復元の速さ |
| Aurora の PITR | 四半期 | prod の隔離した VPC | Slack と同じ |

結果（かかった時間、問題点）を末尾の記録に残す。目標を満たさなければ intent を起票する。

## エスカレーション

- A で 5 分たっても Git の操作の成功率が戻らない → SEV1 に上げ、Dev（テックリード）を呼ぶ。
- A の間に、複製が 1 つしかないリポジトリが出た → SEV1。Dev を呼ぶ。
- B の判断 → Ops の責任者。告知の文面は PM と合意する。
- 成功を返した push の喪失が確定した → PM に報告し、影響を受けた利用者への連絡を決める。
- AWS 側の障害 → AWS サポートにケースを開く。
