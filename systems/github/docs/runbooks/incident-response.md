# Runbook: インシデント対応

- Owner: Ops
- 対応するアラート: すべての呼び出し（page）のアラート。個別の場面：ストレージのノードの喪失、修復の遅れ、複製の不足、ホットなリポジトリ、バックアップの遅れ
- 最終確認日: 2026-09-26

進め方（宣言、役割、被害を止める順、告知、振り返り）は Slack の [incident-response.md](../../../slack/docs/runbooks/incident-response.md) と同じ。ここには、重さの基準の GitHub での読み替えと、GitHub に固有の場面の手順を書く。個別の手順は [deploy-and-rollback.md](deploy-and-rollback.md) と [disaster-recovery.md](disaster-recovery.md)。

## 症状

次のどれかのときに、インシデントを宣言する。迷ったら宣言し、後で重さを下げる。

- 呼び出しのアラートが鳴った（SLO のバーンレート、合成監視の連続失敗、[observability.md](../architecture/observability.md) の 5.2 節の GitHub に固有のアラート）
- 利用者や社内から、障害の報告が来た
- 権限の合成監視・漏洩テストの失敗、非公開のリポジトリの中身が見えたという報告

## 影響

### 重さ（severity）

| 重さ | 基準 | 例 |
| --- | --- | --- |
| SEV1 | 非公開のリポジトリの中身が権限のない人に見えた（NFR-010）。成功を返した push を失った・失う恐れがある。全体が使えない。CI のジョブが他のジョブ・リポジトリのシークレットに触れた | 合意なしの成功、健全な複製が 1 つ以下のリポジトリ、権限の合成監視の失敗、リージョンの障害 |
| SEV2 | Git の操作・PR・ログインが一部の利用者で使えない。速いバーンレート | 1 つの AZ の障害、ストレージのノードの喪失で修復が 2 時間を超えた、デプロイ後の悪化 |
| SEV3 | 一部の劣化。回避できる。遅いバーンレート | Webhook・検索・Actions の開始の遅れ、1 つのホットなリポジトリの遅さ |
| SEV4 | 利用者への影響がない、または非常に小さい | 修復が予定どおり進んでいるノードの喪失 |

最初の応答と告知の時間は Slack と同じ（SEV1：5 分以内、30 分以内に利用者へ告知）。

## 確認

1. どのアラート・報告から始まったかを記録する。
2. 影響の範囲を見る：全体か、特定のリポジトリ・持ち主か、特定のストレージのノード・AZ か。上位のリポジトリの内訳（[observability.md](../architecture/observability.md) の 3.2 節）を使う。
3. 直近の変更を見る：アプリの列車、ストレージの列車、Git の版、フラグ、インフラの変更。

## 対処

### 共通

Slack と同じ順で被害を止める（フラグを切る → デプロイを戻す → 上限をかける → 容量を増やす）。GitHub で加わるもの：

- **ストレージの列車・Git の版の更新・大きな保守を止める。** 何が原因でも、調査の間に複製を止める作業を重ねない。
- **書き込みを止めるのは最後の手段。** `ops.read_only_mode` はリポジトリ単位でかけられる。全体にかけるのは SEV1 で、データの喪失の拡大を止めるときだけ。
- インシデントの連絡の場と runbook は、このシステムの外に持つ（[delivery.md](../architecture/delivery.md) の 6.2 節）。

### ストレージのノードの喪失

ノードが応答しない、EC2 のステータスチェックの失敗、NVMe の故障、AWS Health の停止・退役の予定。

1. **予定（停止・退役のイベント）のとき**は、急がない。ストレージの制御でそのノードの「退避」を始める。複製を同じ AZ の他のノードへ移し終えたら、ノードを退役させ、新しいノードを足す。予定の時刻に間に合わない見込みなら、書き込みの多いリポジトリから先に移す。SEV4。
2. **突然の喪失のとき**：
   1. ストレージの制御が、そのノードを「喪失の疑い」にし、ルーティングから外したことを確かめる。そのノードのリポジトリは 2 つの複製で動いている。
   2. **一時的か（再起動で戻るか）を 15 分だけ見る。** インスタンスが再起動しただけならデータは残っている。15 分で戻れば、検査（チェックサム）と追いつきをして戻す。
   3. 戻らない、またはインスタンスが停止・終了していたら（データは消えている）、「喪失」にする。ストレージの制御が修復を始める（同じ AZ の他のノードへ、書き込みの多いリポジトリから）。SEV4 から始め、修復の見込みが 2 時間を超えたら SEV2 にする。
   4. 同じ AZ に代わりのノードを足す（Terraform）。充填率が 70% を超えるノードがあれば、急ぐ。
   5. 同時期に別の AZ でもノードを失ったら、両方のノードに複製を持つリポジトリ（複製が 1 つになったもの）を一覧にし、それを最優先に修復する。SEV1。
3. 喪失したノードのインスタンスを、調査のために残さない（データはすでに消えている）。ログは CloudWatch に残っている。

### 修復の遅れ（replica repair backlog）

アラート：修復の待ちの最古が 2 時間を超えた。

1. 修復が進んでいるか（毎分の完了件数）を見る。
2. 進んでいない：
   - 受け入れ側のノードの充填率が高すぎる（75% 超）→ ノードを足す。修復の配置先から、充填率の高いノードを外す。
   - 送り側のノード（他の AZ の健全な複製）が負荷で詰まっている → 修復の帯域を一時的に下げ、利用者の読み取りを優先する。ホットなリポジトリが原因なら、次の節。
   - 特定のリポジトリで失敗を繰り返している（壊れたオブジェクト、巨大なリポジトリ）→ そのリポジトリを除外の一覧に入れて他を先に進め、個別に調べる。健全な複製がどれかをチェックサムで決める。
3. 進んでいるが遅い：`ops.repair_bandwidth_gbps` を上げる（利用者の clone の遅れと引き換え。fetch の開始 p95 を見ながら）。
4. 待ちの間に、複製が 1 つのリポジトリが出たら SEV1 にする。

### 複製の不足・合意なしの成功

- 複製が 1 つしかないリポジトリ：そのリポジトリを読み取り専用にし、修復を最優先にする（[disaster-recovery.md](disaster-recovery.md) の C）。
- 合意なしの成功（合意した複製が 2 未満で成功を返した）：設計上起きないはずの事象。SEV1。
  1. ストレージの列車を止め、直近のデプロイを戻す。
  2. 対象の push（アクセスログの `replicas_acked`）を一覧にし、それぞれのリポジトリで ref が 2 つ以上の複製にあるかを確かめ、なければ直ちに複製する。
  3. Dev（テックリード）を呼ぶ。

### ホットなリポジトリ

アラート・チケット：1 つのリポジトリがノードの CPU の 20% 以上を使い続ける、1 つのリポジトリへの要求が上限（[capacity.md](../architecture/capacity.md) の 4 節）に達し続ける。

1. 上位のリポジトリの内訳で、どのリポジトリ・どの主体（認証の主体、IP の範囲、`git.client`）からかを見る。
2. 正当な利用の集中（リリースの直後の clone、話題の OSS）なら：
   - パックの生成のキャッシュが効いているかを見る（ヒット率）。
   - そのリポジトリに読み取り専用の追加の複製を作る（[git-storage.md](../architecture/git-storage.md)）。
3. 1 つの主体からの過剰な利用（CI の設定の誤り、収集）なら、その主体に上限をかける。濫用の疑いがあれば [security.md](../architecture/security.md) の手順に従う。
4. 巨大なリポジトリの保守（repack）が原因なら、保守を低負荷の時間帯へ移す。

### バックアップの遅れ

アラート：バックアップの遅れ p99 が 12 分を超えた。

1. backup のキューの最古と Worker の数、S3（大阪）への PUT のエラー（503・スロットリング）を見る。
2. Worker を増やす。S3 のスロットリングなら、プレフィックスの分散を確かめ、リトライの間隔を広げる。
3. 大阪のリージョンの障害なら、東京の一時のバケットへ書く設定に切り替え、大阪の回復後に移す（この間はリージョンの障害への備えがない。SEV3 として告知は不要、Ops の責任者に報告）。

### 権限の漏洩（NFR-010）

Slack のテナント境界の破れと同じく、範囲が 1 件でも SEV1。原因の経路（Git、API、検索、通知、Webhook、Actions のログ）を止めることを最優先にする。機能を止めてよい。証拠を消さない。手順は [security.md](../architecture/security.md) に従う。

## エスカレーション

| 状況 | 連絡先 |
| --- | --- |
| SEV1 の宣言 | Ops の責任者、Dev（テックリード）、PM |
| 権限の漏洩、シークレットの漏洩の疑い | 上記に加えて、[security.md](../architecture/security.md) で定める責任者 |
| 成功を返した push の喪失 | 上記に加えて、PM（利用者への連絡） |
| リージョンの切り替えを考える | Ops の責任者（承認）。[disaster-recovery.md](disaster-recovery.md) |
| AWS 側の障害、インスタンスの予定のイベントの時刻の変更 | AWS サポート |
| 1 時間たっても被害を止められない | 重さを 1 段上げる |

## 事後

- 振り返りを、SEV1・SEV2 では必ず 5 営業日以内に行う（Slack と同じ。責任追及をしない）。
- 再発防止を Intent の Issue にする（Maintain 段）。
- 複製・権限に関わるものは QA に共有し、[quality.md](../quality.md) のリスクと対策を見直す。
- この手順で足りなかったことを反映する。アラートが鳴らなかった・遅かったなら、アラートを直す。
