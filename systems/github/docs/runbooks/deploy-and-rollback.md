# Runbook: デプロイとロールバック

- Owner: Ops
- 対応するアラート: デプロイ中の自動ロールバック（Web・API の blue/green のアラーム）、ストレージの列車の自動停止、デプロイ後の SLO のバーンレート
- 最終確認日: 2026-09-26

流れは [delivery.md](../architecture/delivery.md)、ストレージのノードの更新の方針は [ADR-0033](../decisions/0033-rolling-storage-node-upgrades.md)、CI/CD の構成は [infrastructure.md](../architecture/infrastructure.md) の 6 節にある。アプリの部分（マイグレーション、blue/green、フラグでの戻し）は Slack の [deploy-and-rollback.md](../../../slack/docs/runbooks/deploy-and-rollback.md) と同じで、ここでは GitHub に固有の部分を中心に書く。

## 症状

次のときに使う。

- 本番へデプロイするとき（アプリの列車、ストレージの列車、Git の本体の版の更新）
- デプロイの後に、Git の操作の成功率・push の時間・Web の表示が悪化したとき

## 影響

- 通常のデプロイ：利用者への影響はない。Git フロントエンドの入れ替えで、15 分を超える転送は切れうる（クライアントのやり直し）。
- ストレージの列車の間：更新中のノードの複製は一時的に使われず、そのノードのリポジトリは 2 つの複製で動く。
- 失敗したデプロイ：Git の操作の成功率、fetch の開始の時間、push の時間の SLO を消費する。

## 確認

### デプロイの前（共通）

1. 対象が dev と staging にデプロイ済みで、staging の E2E・スモーク・Git の互換のマトリクスが通っている。
2. 夜間の CI（障害注入、負荷試験、復元）が直近 2 日で通っている（ストレージの列車の前提）。
3. Grafana の SLO ダッシュボードで、エラーバジェットが残っている。
4. 進行中のインシデントがない。
5. **ストレージの列車の前に、複製の健全性を見る。**

   | 見るもの | 始めてよい | 始めない |
   | --- | --- | --- |
   | 複製が 3 つそろっていないリポジトリ | 0 件、または修復中で最古が 30 分以内 | 修復の最古が 30 分を超える |
   | 退避中・喪失のノード | 0 台 | 1 台以上（別の作業と重ねない） |
   | ストレージの充填率 | 全ノードで 75% 未満 | 75% 以上のノードがある（退避の受け入れができない） |
   | AWS Health の予定のイベント | 当日にない | 当日にある |

### デプロイの後（各段の後に 15 分）

| 見るもの | 正常 | 異常 |
| --- | --- | --- |
| Git の操作の成功率（サーバーの原因の失敗を除く） | 99.95% 以上 | 下回る |
| fetch の開始 p95 | 1 秒以内 | 超える |
| push の成功までの時間 p95 | デプロイ前と同じ | 1.5 倍を超える |
| 合意なしの成功 | 0 件 | 1 件以上（SEV1） |
| 更新したノードの子プロセスのエラー、trace2 の異常終了 | デプロイ前と同じ | 増える |
| 合成監視（clone・push・権限の確認） | 成功 | 2 回続けて失敗 |

## 対処

### アプリの列車（Web・API、Worker、Git フロントエンド）

Slack の手順と同じ（Ops の承認、マイグレーション、Web・API の blue/green、ローリング）。Git フロントエンドは、ローリングで 1 回に 1 AZ の 1/3 ずつ入れ替わる。停止の猶予 15 分の間、進行中の clone を見届ける。

### ストレージの列車

1. GitHub の `prod-storage` の Environment で、Ops が承認する。
2. デプロイのワークフローが、カナリアの 1 台（AZ-1）を更新する。ワークフローは、ストレージの制御に「退避 → 再起動 → 検査 → 追いつき → 復帰」を 1 台ずつ依頼する（[delivery.md](../architecture/delivery.md) の 4.2 節）。
3. 1 時間、「デプロイの後」の表を見る。問題がなければ、ワークフローを「続ける」にする。
4. AZ-1、AZ-2、AZ-3 の順に 1 台ずつ進む。AZ の区切りごとに表を確かめる。17 時を過ぎたら、AZ の区切りで止め、翌日に続ける。
5. 全台が終わったら、ノードごとの版が 1 つにそろっていることを Grafana で確かめる。

**ワークフローが自動で止まったとき**は、止まった理由（SLI の悪化、退避の時間切れ、健全性の検査の失敗、他の複製の不健全）を見る。

- 退避の時間切れ（進行中の処理が 10 分で終わらない）：大きな clone の集中が多い。時間をずらして再開する。
- 健全性の検査の失敗：そのノードを「退避中」のまま残し、下の「ロールバック」を行う。
- 他の複製の不健全：修復が終わるのを待つ。[incident-response.md](incident-response.md) の「修復の遅れ」を見る。

### Git の本体の版の更新

ストレージの列車と同じ手順で、パッケージの Git の版だけが変わる。違いは次のとおり。

- カナリアの 1 台で 24 時間待つ。
- 新しいディスクの形式に関わる migration フラグは、全台の更新の 1 週間後まで有効にしない。フラグを有効にした後は、古い版へ戻せない。
- **脆弱性の修正の短縮の経路**：Ops の責任者の承認で、カナリアを 1 時間、AZ の中の同時の台数を 3 台にする。時間帯の制限を受けない。目標は公開から 48 時間以内に全台。

### ロールバック

1. **フラグで戻す。** 新しい機能のフラグ、ops フラグ（`ops.clone_cache_enabled` など）で止められるなら、まずそれを使う。
2. **アプリを戻す。** 1 つ前のイメージの digest で再デプロイする（Slack と同じ）。
3. **ストレージのサービス・Git の本体を戻す。** 各ノードに残した 1 つ前のパッケージへ、同じ 1 台ずつの手順で戻す。
   - 更新した順と逆に（最後に更新した AZ から）戻す。
   - 戻す間も、同時に止めるのは 1 つの AZ だけ。急いで全台を同時に戻さない。複製が 2 つ止まると、書き込みが止まる。
   - ディスクの形式の migration フラグを有効にした後なら、戻せない。前へ進める修正を入れる。
4. **マイグレーションは戻さない**（expand / contract。Slack と同じ）。
5. 戻しても 15 分で回復しなければ、インシデントを宣言する。

## エスカレーション

- 合意なしの成功が 1 件でも出た → SEV1。ストレージの列車を止め、[incident-response.md](incident-response.md) に従う。Dev（テックリード）を呼ぶ。
- ロールバックの途中で、複製が 1 つしかないリポジトリが出た → 作業を止め、修復を優先する。Dev を呼ぶ。
- 権限の合成監視が失敗した → SEV1（NFR-010）。

## 事後

- 調査結果を Intent の Issue として起票する（Maintain 段。[project-management.md](../../../../docs/project-management.md)）。
- この手順で足りなかったことを、ここに反映する。
- ストレージの列車の所要時間と止まった理由を記録し、1 回の列車が 2 日を超えるようになったら、AZ の中の同時の台数を増やすことを提案する。
