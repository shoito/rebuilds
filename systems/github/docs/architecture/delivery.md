# Delivery: GitHub

ブランチ、CI、デプロイ、リリースの流れ。Slack の流れ（[Slack の delivery.md](../../../slack/docs/architecture/delivery.md)）を基本に、GitHub に固有のもの（ストレージのノード、Git の本体の版、自分自身をホストすること）を足す。

| 対象 | 方針 |
| --- | --- |
| ブランチモデル | リポジトリ共通の [ADR-0002](../../../../docs/decisions/0002-trunk-based-development.md)（トランクベース開発） |
| AWS の CI/CD の構成 | [infrastructure.md](infrastructure.md) の 6 節 |
| ストレージのノードの更新 | [ADR-0033](../decisions/0033-rolling-storage-node-upgrades.md) |
| フィーチャーフラグ | Slack の [ADR-0026](../../../slack/docs/decisions/0026-feature-flags.md) を引き継ぐ（AWS AppConfig。release・ops・migration・entitlement の 4 種類） |
| 無停止のデプロイとスキーマの変更 | Slack の [ADR-0022](../../../slack/docs/decisions/0022-zero-downtime-deploy-and-migrations.md) を引き継ぐ（expand / contract） |
| 手順 | [runbooks/deploy-and-rollback.md](../runbooks/deploy-and-rollback.md) |

原則は Slack と同じく 2 つ。`main` は常にデプロイできる状態に保つ。デプロイ（Ops が承認）とリリース（PM が判断）を分ける。GitHub では 3 つ目を足す。

- **ストレージのノードの更新は、どのリポジトリについても、同時に 2 つ以上の複製を止めない。**

## 1. 変更からマージまで

Slack と同じ（`github/YYMMDD-<slug>` のブランチ、エージェントは worktree ごとに 1 本、PR の CI、CODEOWNERS のレビュー、merge queue、squash）。

- CODEOWNERS で、次の変更には Dev（テックリード）と QA のレビューを必須にする。
  - 権限の判定の関数（ADR-0002）
  - 複製の合意と修復（ADR-0003）
  - Git の本体の版と、Git の設定（[capacity.md](capacity.md) の 3.1 節）
  - RPC の契約（`.proto`）

## 2. CI

### 2.1 PR の CI

Slack の段（静的検査、単体・性質・表駆動、結合、契約、フラグ、追跡、マイグレーション、E2E、セキュリティ、インフラ、エージェントの eval）に加えて、次を行う。目標は 20 分以内。

| 段 | 内容 | 失敗の条件 |
| --- | --- | --- |
| Go | `go vet`、staticcheck、`go test -race` | 1 件でも |
| RPC の契約 | `.proto` の後方互換の検査（フィールドの削除・番号の変更を禁止）。TypeScript と Go のコードの生成の差分 | 互換を壊す変更、生成物の差分 |
| Git の互換 | 主要な Git のクライアントの版（直近 4 つの minor と、配布で多い古い版）、libgit2、JGit、go-git で、clone・fetch・push・部分的な clone・LFS を実行する | 1 件でも |
| 複製 | 3 つのノードを立てた結合テスト。push の途中で 1 つを止め、成功を返した push が失われず、修復後にチェックサムが一致する（ADR-0003 の Confirmation） | 1 件でも |
| 権限の漏洩 | 権限の判定の性質ベーステストと、経路ごと（Git、API、検索、通知、Webhook、Actions のログ）の漏洩テスト（ADR-0002） | 1 件でも |

### 2.2 夜間の CI

- Git の互換のマトリクスの全件。
- 障害注入の完全版（ノードの停止、ディスクの満杯、AZ の分断、合意の途中の遅延）を staging で行う。
- staging で、[capacity.md](capacity.md) の負荷のモデルの 1 倍の負荷試験。
- バックアップからの復元（無作為の 100 リポジトリ）。

夜間の CI が 2 日続けて失敗している間は、release フラグを広げない。ストレージのノードのデプロイも止める。

## 3. ビルドと成果物

| 成果物 | 内容 | 識別子 |
| --- | --- | --- |
| コンテナイメージ | Web・API、Worker、Git フロントエンド、migrator | Slack と同じ（ECR、digest で参照） |
| ストレージのパッケージ | ストレージのサービス（Go）と、Git の本体を 1 つにした tar。署名と SBOM を付けて S3 に置く | `<日付>-<コミット>+git<版>`（例：`2026-09-26-a1b2c3d+git2.51.0`） |
| Git の本体 | 上流の公開の版を、CI で再現可能にビルドする。自前のパッチは原則持たない | 上流の版 |
| AMI | ストレージのノード、実行環境のホスト | Image Builder の版 |

- Git の本体の版は、ストレージのパッケージと同じ tar に入れる。ただし、**版の変更は、サービスの変更と別の PR・別のデプロイにする**（4.3 節）。1 回のデプロイで両方を変えると、問題の原因を切り分けられない。
- Git フロントエンドは Git の本体を使わない（Go で SSH・HTTP を話し、ストレージの RPC へつなぐ）。

## 4. デプロイ

### 4.1 デプロイの順序

RPC の契約は、1 つ前の版と互換に保つ（項目の追加のみ）。そのうえで、呼ばれる側から先に入れ替える。

| 順 | 対象 | 方式 |
| --- | --- | --- |
| 1 | マイグレーション（expand） | 1 回だけ実行する ECS のタスク |
| 2 | ストレージのサービス | 1 台ずつ、プロセスの再起動（4.2 節）。全台で数時間かかる |
| 3 | Git フロントエンド | ローリング。停止の猶予 15 分で進行中の転送を終える |
| 4 | Worker | ローリング |
| 5 | Web・API | blue/green のカナリア（10% → 100%）。アラームで自動ロールバック |

- ストレージのサービスは全台の入れ替えに時間がかかるので、他の部品と同じ日に 1 つのリリースとして流さない。**ストレージの列車（週 2 回）と、アプリの列車（毎日）を分ける。** アプリの列車は、ストレージの N−1 の版と互換であることを CI で確かめる。

### 4.2 ストレージのノードのローリング更新

ADR-0033 のとおり。

```
カナリア：AZ-1 の 1 台 ─▶ 1 時間、SLI とそのノードのエラーを見る
   ─▶ AZ-1 の残り（1 台ずつ）─▶ AZ-2（1 台ずつ）─▶ AZ-3（1 台ずつ）
各台で：
   1. ルーティングで、そのノードを「退避中」にする（新しい読み取りを他の複製へ、書き込みの合意はそのノードを除いた 2 つで）
   2. 進行中の処理を終える（最大 10 分。超えたら切る）
   3. プロセスを入れ替えて起動し、健全性の検査（自分の複製のチェックサムを 100 件検査）
   4. 退避中の間に遅れた ref を追いつかせる（修復）
   5. ルーティングに戻す
```

- **ある AZ のノードを更新している間、他の AZ のノードを更新しない。** どのリポジトリも 1 つの AZ に 1 つの複製しか持たないので、同じ AZ の中なら何台を同時に止めても、1 つのリポジトリで止まる複製は 1 つに限られる。S1 では安全のため 1 台ずつにし、全体で約 42 × 15 分 ≒ 10 時間。S2 で台数が増えたら、AZ の中の同時の台数を増やす。
- **複製がすでに欠けているリポジトリがあるノードは止めない。** 更新の前に、そのノードが持つリポジトリで、他の複製が不健全なものがないかを確かめる。あれば、修復を待つ。
- プロセスの再起動では、インスタンスストアのデータは残る。OS のカーネルの更新による再起動でも残る（[AWS のドキュメント](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instance-store-lifetime.html)）。
- **AMI・インスタンスの種類の変更は、ノードの入れ替えになる。** 停止すると NVMe のデータが消えるので、新しいノードを作り、複製を移してから古いノードを退役させる（1 台あたり数時間）。月 1 回の AMI の更新は、急ぎのセキュリティの修正を除き、カーネルのライブパッチと再起動で済ませ、入れ替えは四半期に 1 回にまとめる。
- 途中で SLI が悪化したら、自動で止まる。戻すときは、各ノードに残した 1 つ前のパッケージで同じ手順を逆に行う。

### 4.3 Git の本体の版の更新

Git の本体の更新は、Git の中身（ディスクの形式、プロトコル）に触れるので、サービスの更新より慎重に行う。

| 段 | 内容 | 期間 |
| --- | --- | --- |
| 1 | CI：互換のマトリクス、上流のリリースノートの確認（ディスクの形式・既定値の変更） | — |
| 2 | staging の全ノード。夜間の障害注入と負荷試験を 2 回通す | 3 日 |
| 3 | prod のカナリアの 1 台 | 24 時間 |
| 4 | 4.2 節の順で全台 | 数日 |

- **新しい版でしか読めないディスクの形式を、全台がそろうまで使わない。** 新しい形式（ref の保存形式、索引の形式など）は、Git の設定で有効にするので、migration フラグ（`migration.git_<機能>`）で制御する。全台が新しい版になり、1 週間問題がなければフラグを有効にする。有効にした後は、古い版へ戻せない（expand / contract と同じ考え方）。
- 複製の間で Git の版が混ざっても、合意とチェックサムは ref の値で比べるので、パックのバイト列の違いは問題にならない（ADR-0003）。
- **脆弱性の修正は短縮の経路で入れる。** Git の本体の重大な脆弱性（Critical・High）が公開されたら、段 2 を半日、段 3 を 1 時間に縮め、AZ の中の同時の台数を 3 台に上げる。目標は、公開から 48 時間以内に全台。ノードごとの版を監視し（ADR-0001 の Confirmation）、古い版が残っていたらアラートを出す。

### 4.4 環境の昇格と時間帯

Slack と同じ（dev → staging → prod、prod は平日 10〜17 時、エラーバジェットを使い切ったら修正以外を止める）。ストレージの列車は、夜間の CI が通った日の午前に始め、夕方に AZ の区切りで止め、翌日に続きを行う。AZ の途中で夜を越さない。

## 5. リリース（機能を有効にする）

Slack の段（社内 → 5% → 25% → 100%）を引き継ぐ。広げる単位は、リポジトリの持ち主（ユーザー・Organization）にする。

- 社内の段は、自分たちの Organization（6 節）と、合成監視の Organization にする。
- Git のプロトコルの振る舞いを変える機能（新しい能力の広告など）は、クライアントの互換を確かめるため、5% の段を 1 週間にする。
- ops フラグ（キルスイッチ）の例：`ops.clone_cache_enabled`、`ops.mergeability_on_push`、`ops.repair_bandwidth_gbps`、`ops.read_only_mode`（全体・リポジトリ単位）。

## 6. 自分自身をホストする（ドッグフーディング）と、起動の順序

このシステムの開発リポジトリを、このシステムに置くかどうか。置けば、Pull Request・レビュー・merge queue・Actions を、日々の開発で最も厳しく使うことになる。一方で、**このシステムが止まると、それを直すための変更をマージ・ビルド・デプロイできない**という循環が生まれる。

### 6.1 段階

| 段階 | 開発リポジトリの正本 | CI | このシステムでの利用 |
| --- | --- | --- | --- |
| E1〜MVP の前 | 外部のホスティング（現在の GitHub.com） | 外部（GitHub Actions） | なし |
| MVP の社内の段 | 外部 | 外部 | 開発リポジトリの読み取りの複製を置き、閲覧・検索・PR のレビューの試用に使う |
| MVP の後、SLO を 3 か月満たしたら | このシステム | このシステムの Actions と、外部の CI の二重 | 正本を移す。外部には、push のたびに複製（ミラー）を送る |

正本を移す判断は、PM・Ops・Dev（テックリード）が行う。

### 6.2 循環を断つための規則

- **デプロイの経路は、このシステムに依存しない。** 本番へのデプロイに使うもの（成果物の ECR・S3、Terraform の状態ファイル、デプロイのワークフローの実行の場）は、このシステムの外に持つ。正本を移した後も、外部のミラーから、外部の CI でビルド・デプロイできる経路（緊急の経路）を保ち、四半期に 1 回試す。
- **成果物は、このシステムが止まっていても取れる。** 直近の 10 リリースの成果物を ECR・S3 に残す。1 つ前の版への再デプロイは、Git を読まずにできる。
- **runbook とインシデントの連絡の場は、このシステムの外にも置く。** runbook は、この設計のリポジトリ（外部）を正本とし、オンコールの端末にも複製を持つ。
- **Actions の実行環境の AMI・microVM のイメージのビルドは、Actions に依存しない。** EC2 Image Builder で作る。
- **認証の循環を避ける。** 本番の AWS への人のアクセス（IAM Identity Center）と、デプロイの OIDC の信頼は、このシステムのアカウントや Actions の OIDC に依存させない。正本を移した後に、このシステムの Actions からのデプロイを加える場合も、外部の CI の信頼を残す。

### 6.3 最初の構築（ブートストラップ）の順序

1. 基盤のアカウントと Terraform の状態（Slack の foundation と同じ）
2. prod のネットワーク、KMS、S3（バックアップ、LFS）、Aurora
3. ストレージのノード 3 台（各 AZ に 1 台）とストレージの制御。空のルーティングの表
4. Git フロントエンド、Web・API、Worker
5. 合成監視のリポジトリを作り、5.3 節（[observability.md](observability.md)）の合成監視が通ることを確かめる
6. ストレージのノードを S1 の台数へ増やす（配置の再調整）
7. 実行環境のアカウントと PrivateLink

## 7. 指標

Slack と同じ DORA の 4 指標に加えて、次を見る。

- ストレージの列車の所要時間と、途中で止まった回数
- Git の本体の脆弱性の公開から、全台への反映までの時間（目標 48 時間）
- ノードごとの版のばらつき（ストレージのサービス、Git の本体）
