# ADR-0003: リポジトリは、アプリケーションの層で 3 つのノードに複製する

## Context

リポジトリの中身を失うことは、最も重い障害である。一方、Git のリポジトリは、小さなファイルと大きなパックファイルが混ざり、ブロックストレージや共有ファイルシステムの上では性能と運用が難しい。

本家 GitHub は、Spokes（旧 DGit）で、各リポジトリを 3 つのサーバーに、Git のプロトコルで同期した独立した Git のリポジトリとして持つ（[Introducing DGit](https://github.blog/engineering/architecture-optimization/introducing-dgit/)）。

## Options

1. **アプリケーションの層で 3 つの複製を持つ（Spokes に倣う）**
2. **共有ファイルシステム（EFS など）に 1 つだけ置く**
3. **オブジェクトストレージ（S3）にオブジェクトを置き、必要時に組み立てる**

## Decision

1 を採用する。詳細は [git-storage.md](../architecture/git-storage.md) にある。

- **リポジトリごとに 3 つの複製を持つ。** 異なる AZ の 3 つのストレージのノード（EC2 とローカルの NVMe、または EBS）に置く。
- **書き込み（push の ref の更新）は、3 つの複製で合意してから成功を返す。**
  - 3 つのうち 2 つ以上で書けたら成功とする。
  - 遅れた複製は、あとから Git のプロトコルで修復する。
- **どの複製にあるかは、ルーティングの表（DB）で管理する。** ノードの追加・故障時は、複製を別のノードへ作り直す。
- **ref の更新の順序は、リポジトリごとのチェックサム（全 ref の要約）で揃っていることを確かめる。**
- 2 は、共有ファイルシステムの遅延と一貫性が、Git の大量の小さな読み書きに合わない。単一障害点にもなる。
- 3 は、Git の読み取りの経路（パックの生成）で、毎回組み立て直す費用が大きい。バックアップと、大きな LFS のオブジェクトの置き場としては S3 を使う。

## Consequences

- 良くなること：
  - 1 つのノード・1 つの AZ を失っても、読み書きが続く。
  - 複製は通常の Git のリポジトリなので、Git の道具で調べて直せる。
- 引き受けるコスト：
  - 保存の容量が 3 倍になる。
  - ref の更新の合意と、複製の修復の仕組みを、自分で作って保つ必要がある。

## Confirmation

- 障害注入：push の途中で複製のノードを 1 つ止めても、成功を返した push が失われず、修復後に 3 つの複製のチェックサムが一致する。
- 定期の検査：全リポジトリの 3 つの複製のチェックサムを比べ、不一致を修復する。
