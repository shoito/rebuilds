# ADR-0038: 運用者の本番へのアクセスと、非公開のリポジトリの参照

## Context

運用者（Ops、サポート、Dev）の本番へのアクセスは、[security.md](../architecture/security.md) の 4 節の統制の表に 1 行（SSO＋MFA、最小権限、break-glass、四半期のアクセスレビュー）があるだけで、次が決まっていない。

- 平常時に持つ権限と、期限つきで得る権限の境目
- サポートが非公開のリポジトリの中身（コード、Issue、PR）を見る条件
- 運用者が利用者になりすませるか

このシステムは RLS を使わず、権限は判定関数に集約している（[ADR-0002](0002-repository-permission-model.md)）。DB に直接入る運用者には、判定関数が効かない。ストレージのノードに入れる運用者は、平文の Git の中身を読める（[ADR-0028](0028-encryption-and-key-management.md)）。

Auth0 の題材は、同じ問いを [ADR-0056](../../../auth0/docs/decisions/0056-operator-access.md) で決め、テナントのデータの参照にテナントの許可を求めた。本家は、社員が非公開のリポジトリの中身にアクセスする場面を、持ち主の同意、セキュリティ、法令などに限ると規約で説明している（[GitHub Terms of Service](https://docs.github.com/en/site-policy/github-terms/github-terms-of-service) の Private Repositories。場面の一覧の細部は着手時に確かめる）。

## Options

1. **Auth0 の ADR-0056 と同じ形にする。** 常設の権限は中身を含まない観測だけ。DB・ストレージのノード・シェルは期限つきの権限（JIT）で得る。非公開のリポジトリの中身の参照は、持ち主の同意を前提にする
2. Ops に本番の読み取りの常設の権限を与え、監査ログで追う
3. 本番のすべてを JIT にし、承認を常に 2 人にする

## Decision

1 を採用する（proposed。Dev と Ops の承認待ち）。

- **常設の権限**：Grafana のダッシュボード、メトリクス、トレース、アプリのログ（本文・トークンを含めない）の読み取り。運用者の画面（社内のツール）での、アカウント・リポジトリのメタデータ（名前、公開範囲、大きさ、状態）と公開のリポジトリの参照。6 節の措置（無効化、非表示、停止）は、理由とケースの ID を付けて行う。
- **期限つきの権限（最長 4 時間）**：

  | 権限 | 承認 | 使う場面 |
  | --- | --- | --- |
  | 本番の DB の読み取り（読み取り専用のロール。クエリを pgaudit で記録する） | Ops の責任者（依頼者と別） | 障害の調査 |
  | 本番の DB の書き込み、ECS Exec | Ops の責任者と Dev のテックリードの 2 人 | データの修復 |
  | ストレージのノードへのシェル（SSM Session Manager だけ。入出力を記録する） | Ops の責任者と Dev のテックリードの 2 人 | 複製の修復、障害の調査 |
  | 内部のアクセスログの検索（[ADR-0029](0029-audit-log.md)） | Ops の責任者 | トークンの漏洩の影響の特定 |

- **非公開のリポジトリの中身の参照は、持ち主の同意を前提にする。** サポートの依頼の中で、持ち主（Organization の owner、個人は本人）がリポジトリを指定して同意し、期限（既定 72 時間）を付ける。運用者の画面は、同意のあるリポジトリだけを、判定関数に「運用者（同意つき）」の主体を足して読む。同意のない参照は、セキュリティの事象、濫用の調査（6 節）、法令に基づく要請に限り、事後に持ち主へ知らせる（法令が禁じる場合を除く）。
- **記録**：同意・取り消し・期限つきの権限の付与・参照を、`platform_audit_events` と、Organization の `audit_events` の両方に残す（`actor_type = operator`）。
- **なりすましの機能を作らない。** 運用者が、利用者としてセッション・トークンを作る機能、利用者として push・コメントする機能は作らない。
- **AI エージェントは本番に経路を持たない。** security.md の 1 節と 7 節のとおり。調査に使うときも、人が取り出した、コードと個人情報を含まないものだけを渡す。
- **レビュー**：四半期ごとに、権限の割り当てと期限つきの権限の使用の記録を見直す。週次で、期限を過ぎて残る割り当てを検出する。
- 2 は、1 人のアカウントの乗っ取りで全員の非公開のリポジトリのメタデータと Issue が読める。3 は、障害の調査が遅くなり、NFR-001（月間 99.95%）の障害の対応に合わない。

## Consequences

- 良くなること：
  - 運用者のアカウントが乗っ取られても、常設の権限で非公開の中身は読めない。
  - 持ち主は、サポートがいつ何を見たかを監査ログで確かめられる。
- 引き受けるコスト：
  - 持ち主の同意を待つ間、問い合わせへの回答が遅れる。
  - DB に直接入る期限つきの権限では、判定関数が効かない。範囲は承認と pgaudit の記録で守る。
  - ストレージのノードのシェルは、平文の Git の中身に届く。2 人の承認と記録で守る。

## Confirmation

- IAM の静的検査（Terraform の CI）：本番のアカウントに、期限つきの権限の仕組み以外から DB・ECS Exec・ストレージのノードの SSM の権限を持つ人のロールがない。
- 結合テスト：同意がない、または期限を過ぎた非公開のリポジトリを、運用者の画面で開けない。参照が Organization の監査ログに出る。
- 結合テスト：運用者の画面の API に、利用者のセッション・トークンを作る操作がない（ルートの一覧の検査）。
- 四半期：アクセスレビューの記録。
