# ADR-0033: ストレージのノードは、1 つの AZ の中で 1 台ずつ退避して更新し、AZ をまたいで同時に止めない

## Context

ストレージのノード（[ADR-0031](0031-storage-nodes-on-instance-store.md)）では、次の 4 種類の更新がある。

| 種類 | 頻度 | データ |
| --- | --- | --- |
| ストレージのサービス（Go）の更新 | 週 2 回 | プロセスの再起動。データは残る |
| Git の本体のバージョンの更新 | 月 1 回前後。脆弱性の修正は随時 | 同上 |
| OS のカーネルの更新 | 月 1 回 | 再起動。インスタンスストアのデータは再起動では残る（[AWS のドキュメント](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instance-store-lifetime.html)） |
| AMI・インスタンスの種類の変更 | 四半期 | 停止・終了でデータが消えるので、ノードの入れ替えになる |

push は 3 つの複製のうち 2 つの合意で成功を返す（[ADR-0003](0003-replicated-git-storage.md)）。あるリポジトリの複製を同時に 2 つ止めると、そのリポジトリは書き込めなくなる。

## Options

1. **1 つの AZ の中で、1 台ずつ退避してから更新する。AZ をまたいで同時に止めない**
2. **AZ ごとにまとめて更新する（AZ の全台を同時に止める）**
3. **新しいノードを作って複製を移す（ブルー/グリーン）を、すべての更新で行う**

## Decision

1 を採用する。

- **どのリポジトリも、1 つの AZ に 1 つの複製しか持たない**（ADR-0003 の配置の規則）。したがって、同じ AZ の中のノードだけを止めている間は、どのリポジトリでも止まる複製は 1 つ以下になる。**更新中の AZ は常に 1 つに限る。**
- **1 台ずつの手順。**
  1. ノードを「退避中」にする。読み取りは他の複製へ、書き込みの合意は残る 2 つで行う。
  2. 進行中の処理を最大 10 分待って終える。
  3. プロセス（またはカーネルの更新なら OS）を再起動し、健全性を検査する。
  4. 退避中に遅れた ref を、他の複製から追いつかせる。
  5. ルーティングに戻す。
- **止める前に、そのノードが持つリポジトリの他の複製が健全かを確かめる。** 修復の待ちがあるリポジトリを含むノードは、修復が終わるまで止めない。
- **S1 では 1 台ずつ。** AZ の中の同時の台数は、ストレージの制御の設定で変えられる（脆弱性の修正では 3 台）。ただし、AZ の中で同時に止める台数を増やすと、残る 2 つの AZ に読み取りの負荷が寄るので、[capacity.md](../architecture/capacity.md) の使用率の余裕の内に収める。
- **AMI・種類の変更だけ、入れ替え（3 の方式）にする。** 新しいノードを同じ AZ に作り、複製を移してから古いノードを退役させる。
- **自動で止まる。** 各台の後に、SLI（Git の操作の成功率、push の時間、複製の不足）を見て、悪化していれば次の台へ進まない。
- 2 は速いが、更新中の AZ の全台が止まる間、全リポジトリの複製が 2 つになり、他の AZ でノードを 1 台失うだけで、そのノードのリポジトリの書き込みが止まる。更新のたびに AZ の障害と同じ状態を作ることになる。
- 3 は、毎回数 TB の複製の移動を伴い、週 2 回のサービスの更新には重すぎる。

## Consequences

- 良くなること：
  - 更新中も、どのリポジトリも 2 つ以上の複製で読み書きできる。
  - 更新は、ノードの喪失と同じ仕組み（退避と修復）を毎週使うことになり、その仕組みが錆びない。
- 引き受けるコスト：
  - 全台の更新に時間がかかる（S1 で約 10 時間。[delivery.md](../architecture/delivery.md) の 4.2 節）。ストレージのサービスと、アプリの列車を分ける必要がある。RPC の契約は N−1 のバージョンと互換に保つ。
  - 更新中は、ストレージのサービスの 2 つのバージョンが混ざる。Git の本体のバージョンも混ざるので、新しいディスクの形式は全台がそろうまで有効にしない（[delivery.md](../architecture/delivery.md) の 4.3 節）。

## Confirmation

- ストレージの制御の単体・性質ベーステスト：任意のノードの状態（健全、退避中、喪失）と更新の計画で、同時に止まる複製が 1 つのリポジトリで 2 つ以上にならない。
- staging の週 1 回の障害注入：更新中に、別の AZ のノードを 1 台止め、成功を返した push が失われないことを確かめる。
- 更新のたびに、各ノードのバージョンと、止まっていた時間、進まなかった理由を記録し、Grafana に出す。
