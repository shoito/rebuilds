# ADR-0027: 成果物・キャッシュ・ログは S3 にリポジトリ単位で置き、キャッシュは ref の単位で分ける

詳細は [actions.md](../architecture/actions.md) の 10 節。

## Context

Actions は、ジョブの間で大きなデータを受け渡す。

- **成果物（artifact）**：ビルドの結果。実行の単位。人がダウンロードする。
- **キャッシュ**：依存のディレクトリなど。実行をまたいで再利用する。
- **ログ**：ステップごとの出力。実行中はライブで見せ、完了後に保存する。

どれも非公開のリポジトリの中身を含みうるので、権限のない人から見えてはならない（NFR-010）。キャッシュは実行をまたいで読まれるので、信頼の低い実行（PR）が書いたものを、信頼の高い実行（デフォルトブランチ）が読むと、汚染の経路になる。本家は、キャッシュの読める範囲を「自分の ref、デフォルトブランチ、PR ならベースのブランチ」に限り、PR が書いたものはマージの ref の範囲に閉じる（[Dependency caching](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching)）。

## Options

### 置き場所

1. **S3 に置き、ランナーは署名付き URL で直接読み書きする**
2. **専用のサービスを通して S3 に読み書きする（データがサービスを通る）**
3. **Git のストレージのノードに置く**

### キャッシュの範囲

A. **リポジトリと ref の組（本家と同じ）**
B. リポジトリ全体で 1 つの範囲

## Decision

置き場所は 1、キャッシュの範囲は A を採用する。

- **S3 のキーはリポジトリの ID で始める**（`artifacts/{repo_id}/...`、`caches/{repo_id}/...`、`logs/{repo_id}/...`、`actions/{repo_id}/{sha}.tar.gz`）。リポジトリの削除は前方一致で消せる。SSE-KMS、パブリックアクセスの遮断。
- **ランナーには、キーを 1 つに限った署名付き URL（15 分）を出す。** Artifact・Cache service は、ジョブトークンの範囲（そのジョブのリポジトリ・実行、キャッシュの読める ref と書ける ref）を照合してから出す。ランナーの申告を信じない。
- **利用者のダウンロード**は、ADR-0002 の `can(actor, read, repo)` を通してから署名付き URL を出す。
- **キャッシュ**：
  - 読める範囲は、自分の ref・デフォルトブランチ・（PR なら）ベースのブランチ。書ける範囲は自分の ref だけ。PR の実行はマージの ref に書く。
  - エントリは不変。バージョンは `path` と圧縮の方式から作る。
  - リポジトリあたり 10 GB、古い順に消す。7 日使われないものは消す。流量の上限はアップロード 200 件/分、ダウンロード 1,500 件/分、削除 400 件/分（本家と同じ。[Actions limits](https://docs.github.com/en/actions/reference/limits)）。
  - エントリに、書いた実行の `run_id`・イベント・コミットを記録し、汚染の調査で辿れるようにする。
- **成果物**：実行の単位、1 ジョブ 500 まで、不変（本家の `upload-artifact@v4` と同じ。[actions/upload-artifact](https://github.com/actions/upload-artifact)）。保持の既定は 90 日、公開リポジトリは 1〜90 日、非公開は 1〜400 日（本家と同じ）。
- **ログ**：実行中は Valkey のストリームでライブに見せ、1 MB ごとのブロックで S3 に確定する。保持は成果物と同じ設定に従う。
- **保持期間の削除**は、DB の期限から削除のジョブで行う。S3 のライフサイクルの規則は、削除の漏れに備える上限（401 日）として置く。
- 2 を採らない理由：大きな転送がサービスを通り、帯域と費用が 2 倍になる。認可はサービスで行い、転送だけを S3 に任せれば足りる。
- 3 を採らない理由：Git のストレージは 3 つの複製の Git のリポジトリ用で、大きな一時的なファイルの置き場に向かない（ADR-0003）。
- B を採らない理由：PR（fork を含む）が書いたキャッシュを、デフォルトブランチの実行が読める。汚染がすべての実行に広がる。

## Consequences

- 良くなること：
  - 大きな転送がサービスを通らない。S3 の耐久性と容量をそのまま使える。
  - キャッシュの範囲が本家と同じなので、本家のワークフローがそのまま動き、汚染の性質も同じに説明できる。
- 引き受けるコスト：
  - 署名付き URL は、期限の間は持ち主以外でも使える。期限を短くし、キーを 1 つに限り、ログに URL を出さない。
  - デフォルトブランチの上で動く秘密を持つ実行（`pull_request_target`、`workflow_run` など）が PR のコードを実行すると、デフォルトブランチのキャッシュが汚染される。範囲の規則だけでは防げず、ADR-0025 の既定の遮断とドキュメントに頼る。
  - 保持期間の削除のジョブが遅れると、保存の費用と、削除の約束の両方に響く。削除の遅れを監視する。

## Confirmation

- 性質ベーステスト：任意の (ref, イベント) の実行の列で、キャッシュの読み取りが、本家の範囲の規則（自分の ref・デフォルトブランチ・ベースのブランチ）の外のエントリを返さない。PR の実行の書き込みが、デフォルトブランチの範囲に入らない。
- 漏洩のテスト：権限のない利用者・他のリポジトリのジョブトークンで、成果物・キャッシュ・ログの署名付き URL が得られない。
- 定期の検査：保持期間を過ぎた成果物・ログが S3 に残っている件数が 0。
- レビュー観点：S3 のキーがリポジトリの ID で始まること。署名付き URL をログ・トレースに出していないこと。
