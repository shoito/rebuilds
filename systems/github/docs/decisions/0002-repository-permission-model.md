# ADR-0002: 権限はリポジトリの単位の判定関数に集約し、テナントの RLS は使わない

## Context

Slack と Stripe では、ワークスペースや加盟店をテナントにして、RLS で分けた。GitHub では事情が違う。

- 公開リポジトリは、誰でも（ログインしていない人も）読める。
- fork は、別の持ち主のリポジトリと、オブジェクトを共有する。
- 1 人のユーザーが、多数の Organization とリポジトリにまたがって作業する。

テナントの境界で行を分ける RLS は、この「またいだ読み取り」の本質と合わない。

## Options

1. **リポジトリの単位で権限を判定する 1 つの関数に集約し、RLS は使わない**
2. **持ち主（ユーザー・Organization）をテナントにして RLS を使い、公開の読み取りは例外にする**
3. **リポジトリごとに DB を分ける**

## Decision

1 を採用する。詳細は [identity-and-permissions.md](../architecture/identity-and-permissions.md) にある。

- **判定の関数は 1 つにする。** `can(actor, action, resource)` に集約し、Web・API・Git のフロントエンド・検索・通知・Webhook・Actions のすべての経路がこれを通る。
  - `actor`：ユーザー、App、トークン
  - `action`：read、write、admin など
  - `resource`：リポジトリと、その中の Issue・Pull Request など
- **判定の材料を明確にする。**
  - リポジトリの公開の種類（public・internal・private）
  - 持ち主（ユーザーか Organization か）
  - コラボレーター、チームとロール、Organization の基本の権限
  - トークンのスコープ
- **一覧や検索の結果は、判定を通したものだけを返す。** 検索では、索引の段階で公開の種類とリポジトリの ID を持たせ、クエリの前段で絞る。後から除く方式にしない（Slack の ADR-0005 と同じ考え方）。
- **非公開のリポジトリのメタデータ（Issue・Pull Request）のテーブルでも、リポジトリの ID を必ず持たせ、判定を経ない読み取りを lint で禁止する。**
- 2 は、公開の読み取りが例外ではなく主な使われ方なので、例外が本体になってしまう。
- 3 は、リポジトリの数（S1 で 100 万）に対して現実的でない。

## Consequences

- 良くなること：
  - 公開・非公開・fork・Organization が絡む権限を、1 か所で検証できる。
- 引き受けるコスト：
  - DB の層での多層防御（RLS）がない。判定の関数と、経路ごとの漏洩テストに頼る。判定の関数の変更は、Dev と QA のレビューを必須にする。
  - 判定の結果のキャッシュが要る（1 つの画面で多数のリポジトリを判定する）。権限の変更時に、キャッシュを確実に消す。

## Confirmation

- 性質ベーステスト：任意の権限の設定と操作で、判定の関数が「読めない」とした非公開のリポジトリの中身が、Web・API・検索・通知・Webhook のどの経路からも返らない。
- lint：リポジトリのデータを読むクエリが、判定の関数の結果（リポジトリの ID の集合）を条件に含まない場合に失敗させる。
