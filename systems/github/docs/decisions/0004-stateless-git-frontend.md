# ADR-0004: Git の要求は、状態を持たないフロントエンドで受けて、複製へ振り分ける

## Context

Git のクライアントは、SSH（22 番）と HTTPS で接続する。どちらも、認証・認可のあとで、リポジトリの複製のあるストレージのノードへ要求を届ける必要がある。

## Options

1. **状態を持たない Git のフロントエンド（SSH と HTTPS）を置き、認証・認可のあとでストレージの RPC へつなぐ**
2. **ストレージのノードに、直接 SSH・HTTPS を受けさせる**

## Decision

1 を採用する。詳細は [git-protocols.md](../architecture/git-protocols.md) にある。

- フロントエンドは、SSH の鍵・トークンで認証し、[ADR-0002](0002-repository-permission-model.md) の判定関数で認可する。そのうえで、ルーティングの表から複製のノードを選び、`upload-pack`（読み取り）・`receive-pack`（書き込み）をストリームでつなぐ。
- 読み取りは、3 つの複製のうち負荷の低いものへ振り分ける。書き込みは、合意の手順（ADR-0003）を経る。
- フロントエンドは状態を持たないので、水平に増やせる。長時間の接続（大きな clone）を持つので、接続の数でスケールさせる。
- 2 は、認証・認可のロジックが、ストレージのノードに散らばる。ノードが外部に直接さらされる。

## Consequences

- 良くなること：
  - 認証・認可が 1 か所に集まる。
  - ストレージのノードを、外部から隔離できる。
- 引き受けるコスト：
  - 大きな転送が、フロントエンドを通って 2 回流れる。フロントエンドと同じ AZ の複製を優先して、帯域を抑える。

## Confirmation

- 結合テスト：権限のない SSH の鍵・トークンで、非公開のリポジトリの `upload-pack` が拒否される。
- 負荷試験：フロントエンドのタスクを入れ替えても、進行中の clone の失敗が許容の範囲に収まる（クライアントの再試行を含む）。
