# ADR-0031: Git のストレージのノードは、EC2 のローカル NVMe（インスタンスストア）に置く

## Context

[ADR-0003](0003-replicated-git-storage.md) で、リポジトリを異なる AZ の 3 つのノードに複製すると決めた。ノードのディスクを「EC2 とローカルの NVMe、または EBS」のどちらにするかは決めていなかった。

Git のストレージには次の性質がある。

- 小さなランダムな読み取り（オブジェクト、索引、ref）と、大きな順次の読み書き（パック、repack）が混ざる。
- よく読まれるパックがページキャッシュに載ることが、fetch の開始の速さ（NFR-003）に効く。
- S1 の保存量は、3 つの複製で約 150 TB（充填率 60%）。台数は CPU ではなく容量で決まる（[capacity.md](../architecture/capacity.md) の 2.1・2.2 節）。

AWS の仕様で確かめたこと：

- インスタンスストアのデータは、再起動では残るが、停止・休止・終了・インスタンスの種類の変更・下のディスクの故障では残らない。AWS の予定されたイベントのうち、停止と退役でも消える（[AWS のドキュメント](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/instance-store-lifetime.html)）。
- EBS の耐久性は、gp3 で 99.8〜99.9%（年間の故障率 0.1〜0.2%）、io2 Block Express で 99.999%（[AWS のドキュメント](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-volume-types.html)）。gp3 は 1 ボリュームで最大 80,000 IOPS・2,000 MiB/s。
- `i8g.4xlarge` は 16 vCPU、128 GiB、NVMe 3,750 GB × 1、読み 600,000 / 書き 330,000 IOPS、ネットワーク最大 25 Gbps、EBS 最大 10 Gbps（[AWS の仕様](https://docs.aws.amazon.com/ec2/latest/instancetypes/so.html)）。東京で使える（[AWS の発表](https://aws.amazon.com/about-aws/whats-new/2025/10/amazon-ec2-i8g-instances-available-in-additional-aws/)）。

## Options

1. **インスタンスストア（`i8g` のローカル NVMe）。** 耐久性は 3 つの複製と S3 へのバックアップで持つ
2. **EBS（gp3）を汎用のインスタンスに付ける。** ノードが壊れたら、ボリュームを別のインスタンスへ付け替える
3. **EBS（io2 Block Express）**

## Decision

> 2026-09-26 の注記：東京のオンデマンドの料金（Linux）は、`i8g.4xlarge`（16 vCPU・128 GiB・NVMe 3,750 GB）が 1.6128 ドル/時、`m8g.4xlarge`（16 vCPU・64 GiB）が 0.92752 ドル/時、gp3 が 0.096 ドル/GB・月（[On-Demand Pricing](https://aws.amazon.com/ec2/pricing/on-demand/)、[EBS pricing](https://aws.amazon.com/ebs/pricing/)）。月 730 時間で、`i8g.4xlarge` は約 1,177 ドル、`m8g.4xlarge` と gp3 3,750 GB は約 677 ＋ 360 ＝ 1,037 ドルで、差は約 14%（しかも `m8g` はメモリが半分で、gp3 の既定の 3,000 IOPS・125 MB/秒は NVMe に遠く及ばず、IOPS と帯域の追加で差はさらに縮む）。「費用はおおむね同じ」は確かめられた。下の「東京の料金での比較は未検証」は解消した。

1 を採用する。

- **耐久性は、ディスクではなく複製で持つ。** ADR-0003 の 3 つの複製（異なる AZ）と、大阪の S3 へのバックアップ（[ADR-0032](0032-disaster-recovery-strategy.md)）があれば、1 台の NVMe の喪失はデータの喪失にならない。EBS を使っても、AZ の障害には複製が要ることは変わらない。EBS の耐久性に払う費用は、3 つの複製と二重になる。
- **速さ。** ローカル NVMe の遅延と IOPS は、ネットワーク越しの EBS より有利で、EBS の帯域の上限（`i8g.4xlarge` で 10 Gbps）もかからない。repack と修復の大きな読み書きが、利用者の読み取りと帯域を取り合わない。
- **費用はおおむね同じ。** 容量あたりの費用は、`i8g` の同じ CPU・メモリの汎用のインスタンスとの差額と、gp3 の容量の料金が近い（東京の料金での比較は **未検証**。E3 で見積もり直す）。
- **ノードの扱いの規則を決める。** インスタンスストアの性質から、次を守る。
  - **ストレージのノードを停止しない。** 停止はデータの消去と同じである。Terraform・運用の手順で `stop` を使わない。IAM で、ストレージのノードへの `ec2:StopInstances` と `ec2:ModifyInstanceAttribute`（種類の変更）を Ops の break-glass だけに限る。
  - **Auto Scaling グループを使わない。** ヘルスチェックの誤判定による入れ替えで、複製を失わない。ノードの追加・退役は、ストレージの制御が複製を移してから行う。
  - **終了の保護（termination protection）を有効にする。** OS からのシャットダウンは保護できないので、ノードの OS からシャットダウンのコマンドを実行できる権限を絞る。
  - **AWS の停止・退役の予定を受けたら、予定の前に退避する。** AWS Health のイベントを EventBridge で受け、ストレージの制御に退避を始めさせる。
  - **ノードの喪失を、例外ではなく日常として扱う。** 修復（AZ の中で 2 時間以内。[capacity.md](../architecture/capacity.md) の 2.8 節）を常に動く仕組みにし、定期的に訓練する。
- **ノードを小さめ（`i8g.4xlarge`）にする。** 1 台の喪失で作り直す量を約 2.2 TB に抑える。
- 2 は、ノードが壊れたときにボリュームを付け替えれば修復がいらない点で勝る。ただし、付け替えにも検知と手順が要り、ボリューム自体の故障（年 0.1〜0.2%）には結局複製からの修復が要る。容量あたりの費用が近く、性能で劣るので採らない。**災害復旧で大阪に `i8g` がないときの代わりとしては使う**（ADR-0032）。
- 3 は、耐久性で最も優れるが、3 つの複製の上にさらに費用を払うことになる。

## Consequences

- 良くなること：
  - Git の読み書きの遅延が小さく、ページキャッシュとローカル NVMe で NFR-003 を満たしやすい。
  - EBS の帯域の上限と、ボリュームの管理がない。
- 引き受けるコスト：
  - ノードの停止・種類の変更ができない。OS・AMI の更新は、再起動か、ノードの入れ替え（複製の移動、1 台数時間）になる（[ADR-0033](0033-rolling-storage-node-upgrades.md)）。
  - ノードの喪失のたびに、数 TB の修復が走る。修復が遅れている間に別の AZ で同じリポジトリの複製を持つノードを失うと、そのリポジトリの書き込みが止まる。3 台を同時に失えば、バックアップの時点まで戻る。
  - ストレージの容量を増やすには、ノードを足すしかない（ディスクだけは増やせない）。

## Confirmation

- IAM のポリシーの検査：ストレージのノードの停止・種類の変更が、break-glass 以外に許されていない（CI のポリシー検査）。
- Terraform のポリシー検査：ストレージのノードに Auto Scaling グループを使っていない。終了の保護が有効である。
- 月 1 回の訓練：staging で 1 台を終了させ、修復が 2 時間以内に終わり、全リポジトリの 3 つの複製のチェックサムが一致する。四半期に 1 回は prod で、事前に退避したノードを使って同じことを行う。
- AWS Health の停止・退役のイベントから、退避の開始までを自動化し、その経路を staging で試す。
