# ADR-0034: S3 では、リポジトリにホームのリージョンを割り当て、他のリージョンに非同期の読み取りの複製を置く

## Context

S3（リポジトリ 1 億、Git の要求 20 万件/秒）では、次の理由で 1 つのリージョンに収まらない。

- **容量と台数。** S1 の 100 倍の保存量で、ストレージのノードが数千台になる。1 つのリージョンの在庫と、ストレージの制御の規模の限界に近づく。
- **障害の範囲。** リージョンの障害で全利用者が止まり、復元に 24 時間かかる（[ADR-0032](0032-disaster-recovery-strategy.md)）ことは、S3 の規模では許容できない。目標は RPO 1 分、RTO 1 時間（[infrastructure.md](../architecture/infrastructure.md) の 5.2 節）。
- **遠い利用者の遅延。** 海外の利用者の clone・fetch が、東京まで往復する。

一方で、Git の push の合意（[ADR-0003](0003-replicated-git-storage.md)）をリージョンをまたいで行うと、書き込みのたびにリージョン間の往復（数十〜百数十 ms）が加わる。

## Options

1. **リポジトリ（fork のネットワーク）ごとにホームのリージョンを 1 つ決める。** 書き込みの合意はホームの 3 つの AZ で行い、他のリージョンには非同期の読み取りの複製を置く
2. **3 つの複製を 3 つのリージョンに置き、リージョンをまたいで合意する**
3. **リージョンごとに独立したシステムにする（利用者・Organization をリージョンに割り当てる）**

## Decision

1 を提案する。S2 の間に staging で試し、S3 に入る前に accepted にするかを決める。

- **ホームのリージョン。** fork のネットワーク（オブジェクトを共有する単位）ごとに 1 つ。書き込み（push、ref の更新）はホームへ届け、ホームの 3 つの AZ で合意する。書き込みの遅延は S1 と変わらない。
- **読み取りの複製。** 他のリージョン（1 つ以上）に、非同期の複製を 1 つ置く。ref の更新の Event の順序で追いかける。fetch・clone は、利用者に近いリージョンの複製が十分に新しければ（ref がホームと一致していれば）そこから返す。古ければホームへ回す。
- **リージョンの障害。** ホームが失われたら、読み取りの複製を昇格させる。遅れていた分（目標 1 分以内）を失いうる。昇格は、リポジトリ単位で自動で行える。
- **ルーティング。** リポジトリ → ホームのリージョンの対応表を、グローバルな DB（Aurora Global Database か Aurora DSQL などを比べる。未決定）に持つ。Git フロントエンドは全リージョンに置き、どのリージョンで受けても、ホームへ転送できる。
- **メタデータ。** PR・Issue もリポジトリのホームのリージョンに置くかどうかは、未決定（Slack の [ADR-0023](../../../slack/docs/decisions/0023-cell-based-architecture.md) のセルの考え方と比べる）。
- **ホームの移動。** 利用者の多いリージョンへ、リポジトリのホームを移せるようにする（読み取りの複製を昇格させ、旧ホームを複製に下げる）。
- 2 は、リージョンの障害でも RPO 0 だが、すべての push にリージョン間の往復が加わり、東京・大阪のように近い組でなければ遅すぎる。近い組では、同時に被災する範囲の独立性が下がる。
- 3 は、Organization がリージョンをまたいで fork・参照・検索することを妨げる。公開リポジトリは全世界から読まれる。

## Consequences

- 良くなること：
  - リージョンの障害の RPO・RTO を、リポジトリ単位の昇格で大きく縮められる。
  - 遠い利用者の読み取りが速くなる。
- 引き受けるコスト：
  - 読み取りの複製の分だけ、保存量が 4/3 以上になる。
  - 「読み取りの複製が古い」ことを、クライアントが気づかないように扱う必要がある（push の直後に別のリージョンから fetch する CI など）。
  - グローバルなルーティングの表が、新しい単一障害点になりうる。

## Confirmation

（proposed のため、accepted にするときに確定する）

- staging で 2 つのリージョンを使い、ホームの喪失と読み取りの複製の昇格を行い、RPO 1 分・RTO 1 時間を計測する。
- 性質ベーステスト：任意の push と昇格の列で、昇格した複製の ref が、ホームの ref の過去のある時点と一致する（途中の状態を作らない）。
