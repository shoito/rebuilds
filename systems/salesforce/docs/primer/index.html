Salesforce は何をするサービスか

Salesforce は、B2B の営業チームが顧客・見込み客・商談・活動を記録し、チームで共有して、売上の見込みを管理する CRM です。同時に、会社ごとに項目・画面・自動化を変えられる「業務アプリの基盤」でもあります。

業務に合わせて変えられる

管理者が画面の操作で、オブジェクト・項目・画面・自動化を足す。コードは書かない。

見せてよい人にだけ見せる

上司は部下の商談を見られるが、他の支店の商談は見えない、を設定で決める。

安全に変える

Sandbox で試し、検証してから本番へ全部か無しかでデプロイする。

公平で止まらない

ある会社の重い処理が、他の会社を遅くしない。

顧客の会社 1 つが 1 つの組織（org）で、これがテナントです。使う人は、営業の担当者・管理職・組織の管理者・連携の開発者です。S1 の規模は、組織 5,000（本番 1,000）、利用者 5 万、レコード 5 億です。

設計の文書で効くところintent.md の「Proposed outcome」と「Affected users」、architecture/README.md の 2 節（規模の段階）。

CRM の基本の登場人物

営業の記録は、決まった数個の標準オブジェクト（表のようなもの）に入れます。名前が似ていて混同しやすいので、先に区別します。

オブジェクト何を表すか例
リード（lead）まだ確かめていない見込み客。会社名と人が 1 件にまとまっている展示会で名刺を交換した人
取引先（account）取引の相手の会社株式会社〇〇
取引先責任者（contact）取引先に属する人〇〇社の購買部の佐藤さん
商談（opportunity）売れるかもしれない 1 件の案件。金額と完了予定日を持つ2026 年度の 100 ライセンスの導入
活動（task・event）ToDo と行動（予定）。誰と・何について、を持つ来週の提案の訪問

活動の「誰と」（who）は取引先責任者かリード、「何について」（what）は取引先や商談です。1 つの項目が複数の種類のオブジェクトを指せるので、多態の参照と呼びます。日本向けに、会社名のカナ、13 桁の法人番号、6 項目の日本の住所を持ちます。

設計の文書で効くところsales-objects.md の 3 節（標準オブジェクトの項目）。

商談とパイプライン

商談はフェーズを順に進みます。全ての進行中の商談を並べたものがパイプラインで、管理職はこれを見て「今期いくら売れそうか」を判断します。フェーズの名前は組織が決めます。

flowchart LR
  L["リード"] -->|変換| O["商談"]
  O --> S1["見込み"] --> S2["提案"] --> S3["交渉"]
  S3 --> W["成立 (完了)"]
  S3 --> X["不成立 (完了)"]

フェーズの値ごとに、既定の確度（default_probability）、完了か（is_closed）、成立か（is_won）、売上予測の分類（pipeline・best_case・commit・closed・omitted）を持ちます。フェーズを変えると、保存の手順 2 でこれらを入れ直します。フェーズ・金額・確度・完了予定日などが変わるたびに opportunity_history に 1 行残り、パイプラインの推移のレポートの元になります。

MVP で、利用者が商談の画面で直接書き換えられるのはどれですか？

確度はフェーズの既定値が入りますが、利用者が変えられます。売上予測の分類と is_closed・is_won はフェーズから決まり、利用者は書けません（sales-objects.md の 3.5 節）。

設計の文書で効くところsales-objects.md の 3.5 節。売上予測そのもの（フォーキャスト）は MVP の後です（intent.md）。

リードの変換と重複

見込み客が本物の商機だと分かったら、リードを変換します。1 件のリードから、取引先・取引先責任者・（任意で）商談を作るか、既存のものに合わせます。

  1. リードを読み、まだ変換していないこと、権限（convert_leads など）を確かめる。
  2. 変換済みを表す状態の値を選ぶ。キューが持つリードなら、新しい所有者を指定する。
  3. 取引先を作る（既存なら、空の項目にだけ値を入れる）。
  4. 取引先責任者を作り、その取引先に付ける。
  5. 商談を作るなら、取引先に付け、主の取引先責任者の役割を 1 件作る。
  6. リードの活動を、できた取引先責任者・商談に付け替える。
  7. リードを「変換済み」にする。以後は読むだけになる。1 件の変換は全部か無しか。

変換や登録の時に、同じ会社や人の二重登録を重複の規則で見つけます。日本語では、全角と半角、カナの表記の揺れ、「株式会社」の有無などを正規化してから比べます。

API でリードの status を「変換済み」の値に更新しました。どうなりますか？

本家と同じく、状態を書き換えるだけでは変換できません。変換を元に戻す操作もありません（sales-objects.md の 3.4 節と 5 節）。

設計の文書で効くところADR-0021、ADR-0022、sales-objects.md の 5〜6 節。

メタデータ駆動：オブジェクトも項目も「データ」

Salesforce の一番の特徴は、会社ごとの違いをコードや DB の構造ではなくメタデータとして持つことです。管理者がカスタムオブジェクト「契約」や、取引先の項目「地域」を足すと、メタデータの表に行が増えるだけです。

  • 名前の決まり：標準は接頭辞なしの小文字のスネーク（account、close_date）、カスタムは x_ の接頭辞（x_region）。本家の __c は使いません。
  • 項目の型：テキスト、数値、通貨、日付、選択リスト、参照、主従、数式、積み上げ集計など。
  • バージョン：メタデータを変えるたびに組織のバージョン（metadata_version）が 1 つ上がる。1 つの要求は 1 つのバージョンに固定して動く。
  • コンパイル：バージョンごとのメタデータを部品に分けてコンパイルし、キャッシュする。問い合わせや保存は、それを使って SQL を作る。

目標は「カスタム項目を足してから、画面と API で使えるまで p95 5 秒」で、他の組織を遅くしないことです（K2）。

設計の文書で効くところADR-0003、ADR-0007、metadata-and-runtime.md の 3〜4 節。

1 つの表に全部入れる：records とピボット

組織ごとにオブジェクトが違うのに、DB の構造は全組織で同じです。全てのレコードを 1 つの records の表に入れ、項目の値は JSONB の data に入れます。キーは項目の番号 field_no（再利用しない連番）です。

flowchart LR
  F["md_fields: x_region は field_no 12"] -.-> R["records.data: 12 は 関東"]
  R --> P["record_index_values: field_no 12 の v_text"]
  R --> U["record_unique_values: 一意の値"]
  R --> RL["record_relationships: 参照と主従"]

JSONB の中には型付きの索引を張りにくいので、索引の要る項目だけ、型付きのピボットの表へ同じトランザクションで写して引きます。本家も、型のない値の列と、型付きの索引の表という形を公開しています。値の検索が「どの索引で絞れるか」に左右されるので、問い合わせには選択性の見積もりが要ります。

ある組織が、取引先にカスタム項目 x_region を足しました。DB では何が起きますか？

カスタムオブジェクトや項目を足しても DDL は走りません（architecture/README.md の原則）。名前の変更もメタデータだけで済み、値を書き換えません。

設計の文書で効くところADR-0002、ADR-0006、data-storage.md の 3 節、ADR-0019。

保存の順序（DML の手順）

レコードを 1 件保存すると、検証・自動化・集計・共有が決まった順に動きます。この順は本家の「Order of Execution」に寄せたもので、多くの設計の文書が「手順 3a」「手順 10」のように番号で参照します。

  1. 1–2：元のレコードを読み、要求の値を当てる。権限・FLS・型・参照先を確かめる（システムの検証）。
  2. 3a・3b：保存の前のフロー、before トリガー（MVP の後）。同じレコードの項目だけを変えられる。
  3. 4–5：入力規則と、重複の規則。
  4. 6：書く（未確定）。一意の違反はここで分かる。
  5. 7a・7b：after トリガー、保存の後のフロー。他のレコードの保存は入れ子になる。
  6. 8：積み上げ集計。親の値が変われば、親も入れ子で保存する。
  7. 9–11：項目の変更の履歴、共有の評価、変更のイベントの outbox。最上位で 1 回だけ。
  8. 12–13：確定。その後に、非同期の処理・メール・Webhook・検索の索引。

手順 12 までは 1 つの DB のトランザクションです。どこかで上限を超えたら全体を巻き戻します。1 つの DML は 200 件ずつの塊で、この手順を塊ごとにまとめて行います。

設計の文書で効くところADR-0008、metadata-and-runtime.md の 6 節、ADR-0026。

ガバナ制限と割り当て

全組織が同じ DB とサーバーを共有するので、1 つの組織の重い処理が他を遅くします（騒がしい隣人）。そこで 2 種類の上限を置きます。

ガバナ制限は 1 つのトランザクションの上限です。超えたら全体を巻き戻し、フローの例外の経路でも捕まえられません。エディションで変えません。

上限同期非同期
問い合わせの数100200
取得の行50,00050,000
DML の数・行150・10,000150・10,000
CPU 時間10 秒60 秒

割り当ては組織ごとの 24 時間・1 時間の量です。例：API の要求は Enterprise で「100,000＋ライセンスの数 × 1,000」。超えたら 429 を返します。値はエディションで変わります。

エディション（starter・pro・enterprise・unlimited・developer）は、割り当て・機能・カスタムオブジェクトの数・Sandbox の数を変えます。ライセンス（full・platform・integration）は、利用者ごとの権限の上限です。

上の数は本家の公開の値に寄せた初期値で、確定の値は E12 の負荷試験で決めます。上限の正本は 1 つの登録簿にあり、CI で文書と照合します。

設計の文書で効くところgovernor-limits.md の 4 節と 8 節、ADR-0005、ADR-0042。テナントの分離は共通の資料へ。

アクセスの 2 つの層

「誰が何を見られるか」は、オブジェクトと項目の層と、レコードの層の 2 段で決まります。両方を通ったものだけが見えます。

オブジェクトごとに read・create・edit・delete・view_all・modify_all。view_all（すべて参照）と modify_all（すべて変更）は、共有の設定に関わらず全レコードに届く強い権限です。

FLS は項目ごとの read・edit。読めない項目は「存在しない項目」と同じに扱い、条件・並べ替え・集計・数式・レポート・イベントのどこからも値を漏らしません。

権限は全て権限セットで与え、割り当てた全ての権限セットの和になります。プロファイルは 1 人に 1 つで、レイアウトの割り当て・使えるレコードタイプ・ログインの制限などの既定値の入れ物にします。

レコードごとの水準（none・read・edit・full）。次の節の OWD・ロール階層・共有ルールで決まります。

ある利用者は項目 x_salary を FLS で読めません。その項目で WHERE を書いた問い合わせはどうなりますか？

読めない項目で絞れると、件数の差から値を推し量れます。だから存在しない項目と同じエラーにします（sharing-and-record-access.md の 3.4 節）。

設計の文書で効くところADR-0013、sharing-and-record-access.md の 3 節、ADR-0045（システムの権限 25）。

共有のモデル：OWD から広げる

レコードの層は「既定でどこまで見せるか」を決め、そこから広げるだけの仕組みです。狭める道具はありません。

  1. OWD（組織の共有設定）：オブジェクトごとの既定。private・public_read・public_read_write・controlled_by_parent（親に連動）。
  2. ロール階層：上司は、部下が所有するレコードを見られる（grant_via_hierarchy）。
  3. 共有ルール：「グループ A が所有するもの」か「条件 C を満たすもの」を、グループ B に共有する。
  4. 手動の共有・チーム：レコードごとに人やグループへ与える。所有者が変わると手動の共有は消える。
  5. 暗黙の共有：商談を見られる人は親の取引先を読める。取引先の所有者は子を見られる。
flowchart TB
  CEO["社長"] --> E["東日本 営業部長"]
  CEO --> W["西日本 営業部長"]
  E --> T["東京 担当"]
  E --> S["仙台 担当"]
  W --> O["大阪 担当"]

OWD が public_read の商談を、共有ルールで「西日本の部からは見えない」ようにできますか？

複数の付与があれば最も強いものが勝ちます（決定表 DT-SHR-001）。見せたくない人がいるなら、OWD を狭くして広げる設計にします。

設計の文書で効くところsharing-and-record-access.md の 4〜6 節（DT-SHR-001・002）、ADR-0014、ADR-0015。

事前計算・閉包・再計算・スキュー

読むたびに共有を全て計算すると、ページの表示の目安 300ms に収まりません。本家も、設定が変わった時に計算して保存しています。この設計は、何を行に持ち、何を問い合わせの時に結ぶかを分けています。

行に持つ（事前計算）

レコードの条件の共有ルール・手動・チームは record_shares に、暗黙の親は子ごとの行に持つ。条件のルールの追加は、全レコードを評価し直す再計算になる。

問い合わせの時に結ぶ

所有者・ロール階層・所有者の条件のルール・OWD は、owner_id と閉包の表を結んで判定する。OWD の変更はバージョンの切り替えだけで、行を書き直さない。

再計算の間は、古い構成で判定し続け、できたらバージョンを 1 つ上げて一度に切り替えます（新しいルールのバージョン、閉包の新しい世代）。「古い設定と新しい設定が混ざった判定をしない」は intent の約束です。また、1 人が 1 万件を超えて所有する、1 つの親に 1 万件を超える子を置く、というスキューは、本家も避けるよう勧めており、この設計でも警告します。

設計の文書で効くところADR-0004（注記を必ず読む）、ADR-0016、sharing-and-record-access.md の 7〜8 節、NFR-005。

宣言的な自動化

管理者はコードを書かずに業務の決まりを設定します。どれも保存の手順のどこかで動きます。

処理の手順を図で組むもの。保存の前（3a）・保存の後（7b）・スケジュール・画面・イベントで起動します。200 件の塊を「足並みをそろえて」1 歩ずつ進め、同じフローは同じレコードに 1 トランザクションで 1 回だけ動きます。

数式で書いた条件が真なら保存を断ります（手順 4）。例：「成立のフェーズなのに金額が空」。

主従の親に、子の件数・合計・最小・最大を持たせる項目（手順 8）。例：取引先の「成立した商談の合計金額」。子の変更から差分で直します。

承認の段（30 まで）と承認者（25 まで）を決め、申請から承認・却下・取り消しまでを状態で持ちます。申請中のレコードはロックされます。承認者にアクセスを与えません。

フローの要素の実行も、ガバナ制限で数えます。本家は要素の数の上限をなくしましたが、この設計は残します（本家との差）。

設計の文書で効くところautomation-flows.md、ADR-0025〜0028。

画面・レポート・検索：見えない行を数えない

営業の担当者は、ページレイアウトの画面でレコードを開き、リストビューで一覧を見て、レポートとダッシュボードで集計を見ます。どれも見る人の権限で毎回コンパイルします。

  • レイアウトは狭めるだけ。FLS で読めない項目は、レイアウトにあっても出ない。レイアウトの必須は画面の保存だけに効く。
  • レポート：表形式・サマリー・マトリックス。件数・合計・平均のどれにも、見えない行を入れない。
  • ダッシュボード：本家の「指定した実行ユーザー」（全員が特定の人の権限で見る）は持たない。
  • 検索：日本語は形態素と 2-gram で索引し、結果は候補として共有を後で確かめる。件数の合計は返さない。

営業部長が、ダッシュボードを部下 S の視点に切り替えました。集計に入る行は？

視点の切り替えは「絞る」道具で、広げる道具になりません（DT-DSH-001）。PM が確認済みの決定です。

設計の文書で効くところADR-0029、ADR-0030、ADR-0023、ADR-0032。

API・一括・変更のイベント・Webhook

CRM は、基幹システム・名刺管理・MA（マーケティングの自動化）とつながって使われます。連携の道具は 4 つです。

REST API と問い合わせの言語

レコードの CRUD と、SQL に寄せた独自の問い合わせの言語。親へは account.name のようにドットでたどる。

一括の API

大量の登録・更新・削除・問い合わせのジョブ。200 行ずつ処理し、行ごとに成否を返す（部分の成功）。upsert は外部 ID で既存を探す。

変更のイベント

レコードの変更を確定の順に配り、3 日は replay_id の位置から取り直せる。少なくとも 1 回届く。

Webhook

外のサーバーへ署名付きで送る。宛先は検査し、本番と別の送信の網から送る（SSRF の守り）。

変更のイベントの購読は、オブジェクトの view_all が要り、レコードの共有では絞りません（読めない項目は落とします）。本家の変更のイベントも、共有の設定を無視して配ります。

設計の文書で効くところquery-language-and-api.md、bulk-and-import.md、events-and-integrations.md（ADR-0033〜0037）。

Sandbox とデプロイ

本番で設定を直接いじると営業が止まります。そこで、本番の複製のSandbox（別の組織）で作って試し、メタデータを本番へデプロイします。

種類写すものデータの容量再作成の間隔
developerメタデータ200MB1 日
developer_proメタデータ1GB1 日
partialメタデータ＋選んだデータの標本（伏せる）5GB5 日
fullメタデータ＋全てのデータ（伏せる）本番と同じ29 日
  • 検証だけの実行：本番を一切変えずに、差分・型・依存・データへの影響を調べて計画を作る。
  • 全部か無しか：計画を 1 つのバージョンで当てる。途中で失敗すれば何も変わらない。
  • 戻し：バージョンを巻き戻さず、逆の差分を新しいデプロイとして当てる。

日本の法令の枠組み

取引先責任者やリードは、個人の名前・メール・電話を持つ個人データです。設計は、次の法令の論点に、どの結論にも対応できる形にしてあります。結論は出していません。

  • 個人情報保護法：組織が登録した個人データを、本システムが委託を受けて扱うのか（L1）。外国の事業者（メールの送信、Webhook の宛先、IdP）への提供（L2）。Sandbox への本番の個人データの複製と、マスキングを必須にするか（L3）。漏えいの報告の主体と期限（L10）。
  • 電気通信事業法：Web からのリードのフォームなどでの外部送信規律、BCC でのメールの取り込みが「他人の通信の媒介」に当たるか（L4）。
  • 特定電子メール法：MVP の後の一括のメールでの同意の記録と送信者の表示（L8）。
  • 保持と削除：監査の履歴の日数、本人の削除の請求、解約時の返却と削除（L5・L7）、データの所在（L6）。
法務の確認待ちL1〜L11 は全て確認待ちです。確認が済むまで、intent の表に挙げた spec（E2 の組織の作成、E5 の取引先責任者とリード、E8 の Webhook、E10 のデータを含む Sandbox など）を承認しません。
設計の文書で効くところintent.md の「法務の確認待ち」、security.md の 6・7・11 節。

データモデルの読み方

全部で 171 表ありますが、核は次の数個です。組織の表は、主キーと全ての索引の先頭に org_id を持ち、レコードの系の表は末尾に shard_no を持ちます。

erDiagram

  orgs ||--o{ md_objects : "defines"
  md_objects ||--o{ md_fields : "has"
  md_objects ||--o{ records : "typed rows"
  records ||--o{ record_index_values : "pivot rows"
  records ||--o{ record_relationships : "child of"
  records ||--o{ record_shares : "shared by"
  groups ||--o{ record_shares : "grantee"
  groups ||--o{ group_members_closure : "expanded to"
  users ||--o{ group_members_closure : "member of"
  records {
    uuid org_id PK
    uuid object_id PK
    uuid id PK
    uuid owner_id
    uuid parent_id
    jsonb data
  }
  md_fields {
    uuid field_id PK
    uuid object_id FK
    smallint field_no
    text api_name
    text type
  }
  record_shares {
    uuid record_id
    uuid grantee_group_id
    text access_level
    text row_cause
  }
  group_members_closure {
    bigint generation
    uuid user_id
    uuid group_id
    boolean via_hierarchy
  }
  • 標準オブジェクトの取引先や商談も、専用の表を持たず、records の 1 行です。項目の値は data の field_no のキーで引きます。
  • 利用者のグループの ID は利用者の ID と同じです。だから records.owner_id をそのまま閉包の group_id と結べます。
  • records.parent_id は、主従の親か活動の主の親で、「親に連動」の判定に使います。
  • 変更のイベント（events）と項目の変更の履歴（history）は、主と別のクラスタにあります。

本家と違うところ・名前の置き換え

振る舞いは本家に寄せますが、本家の言語との互換は持たず、作らないものと変えるものがあります。

本家この設計
Apex・SOQL・SOSL・本家のメタデータの XML受け付けない。問い合わせ・数式の言語とメタデータの形式（YAML）は独自
利用者のコード（トリガー）MVP の後（E13）。TypeScript を WASM の砂場で動かす
新しいカスタムオブジェクトの OWD の既定本家より狭い private
ダッシュボードの指定した実行ユーザー持たない。見る人の権限だけで集計
Service Cloud・Marketing Cloud・Experience Cloud作らない。Sales Cloud と基盤に絞る
CPQ・売上予測・AI（Einstein・Agentforce）MVP の後の Epic

識別子に本家の名前を使いません。カスタムの接尾辞 __c は x_ の接頭辞に、組織のドメインは <org>.my.<brand>.<domain>、上限の見出しは <Brand>-Limit-Info、Webhook の署名は <Brand>-Signature と書きます。

設計の文書で効くところintent.md の Constraints と Non-goals、ADR-0006・ADR-0007（リポジトリ共通）、architecture/README.md の 6 節の「本家との差」。

用語集

CRM
Customer Relationship Management。顧客との関係（会社、人、案件、やり取り）を記録して管理する仕組み。
組織（org）
顧客の会社 1 つ分の環境。テナントにあたる。本番の組織と Sandbox の組織がある。
リード
まだ確かめていない見込み客。会社と人の情報を 1 件に持ち、確かめた後に変換する。
取引先
取引の相手の会社。account。
取引先責任者
取引先に属する人。contact。
商談
売上になるかもしれない 1 件の案件。金額・完了予定日・フェーズを持つ。opportunity。
活動
ToDo（task）と行動（event）。誰と（who）・何について（what）を持つ。
多態の参照
1 つの参照の項目が、複数の種類のオブジェクトのどれかを指せるもの。値はレコードの ID とオブジェクトの組。
法人番号
国税庁が法人に指定する 13 桁の番号。取引先の一意の鍵や外部 ID に使える。
フェーズ
商談の進み具合を表す選択リストの値。値ごとに既定の確度・完了・成立・売上予測の分類を持つ。
パイプライン
進行中の商談の集まり。フェーズごとの件数や金額で、売上の見込みを見る。
売上予測の分類
商談を売上予測でどう数えるか（パイプライン、最善、確約、完了、除外）。フェーズから決まる。
リードの変換
リードから取引先・取引先責任者・商談を作る（または既存に合わせる）操作。変換したリードは読むだけになる。
重複の規則
作成・更新の時に、照合の規則で重複の候補を探し、知らせるか止めるかを決める設定。
メタデータ
オブジェクト・項目・画面・自動化・権限などの「設定」。本システムではバージョンを持ち、コンパイルして使う。
カスタムオブジェクト
組織が自分で足すオブジェクト。API の名前は x_ で始まる。
選択リスト
決まった値から選ぶ項目。値は ID で持ち、ラベルを変えてもレコードを書き換えない。
参照
他のレコードを指す項目（lookup）。親を消しても子は残せる。
主従
master-detail。子の所有と共有が親に従う強い関係。親を消すと子も消える。
数式
他の項目から値を計算する項目。値は保存せず、読む時に計算する。
積み上げ集計
主従の子の件数・合計・最小・最大を、親の項目に持つもの。
ピボットの表
JSONB の中の値を、型付きの列に写して索引を張るための表。正本の写しで、同じトランザクションで書く。
選択性
条件が全体のうちどれだけの行に絞れるか。十分に絞れる条件だけが索引から進める。
フロー
コードを書かずに組む自動化。レコードの保存・スケジュール・画面・イベントで動く。
入力規則
数式の条件が真なら保存を断る設定。
承認のプロセス
レコードを申請し、決めた承認者が段ごとに承認・却下する流れ。申請中はレコードをロックする。
ガバナ制限
1 つのトランザクションで使える資源の上限。超えると全体を巻き戻す。
割り当て
組織ごとの一定の時間あたりの量（API の要求、一括の行、イベントの配信など）。
騒がしい隣人
共有の基盤で、ある組織の重い処理が他の組織を遅くすること。
エディション
組織の契約の段。割り当て・機能・カスタムオブジェクトや Sandbox の数を変える。トランザクションの上限は変えない。
ライセンス
利用者ごとの契約の種類。使えるオブジェクトと権限の上限を決める。
FLS
Field-Level Security。項目ごとの読み・編集の権限。
権限セット
オブジェクト・項目・システムの権限の束。利用者の権限は、割り当てた権限セットの和。
プロファイル
利用者に 1 つ必ず付く既定値の入れ物（レイアウト、レコードタイプ、ログインの制限）。基本の権限セットを 1 つ持つ。
OWD
Organization-Wide Defaults。オブジェクトごとに、既定で誰がレコードを見られるかの設定。
ロール階層
組織の上下関係の木。上司は部下が所有するレコードを見られる。
共有ルール
所有者のグループか、レコードの条件で、別のグループにレコードを共有する設定。広げるだけ。
暗黙の共有
設定せずに起きる共有。子の商談を見られれば親の取引先を読め、取引先の所有者は子を見られる。
閉包の表
入れ子のグループとロール階層を展開し、「利用者 U はグループ G に属する」を全て行にした表。
共有の再計算
共有の設定の変更に合わせて、共有の行を作り直すこと。終わるまで古い構成で判定する。
スキュー
1 人の所有者や 1 つの親に、レコードが極端に集まること。ロックの待ちと再計算が重くなる。
ページレイアウト
レコードの画面の項目の並びと関連リスト。アクセスは与えず、狭めるだけ。
リストビュー
条件・列・並び順を保存した一覧。見る人の権限で毎回コンパイルする。
一括の API
大量のレコードを、非同期のジョブで登録・更新・削除・問い合わせする API。
upsert
鍵で既存のレコードを探し、あれば更新、なければ作成する操作。
外部 ID
他のシステムの ID を入れる、一意で索引のある項目。upsert の鍵に使う。
変更のイベント
レコードの作成・更新・削除を、確定の順に購読者へ配るイベント。本家の Change Data Capture にあたる。
Sandbox
本番の組織の複製の、開発・試験用の別の組織。
デプロイ
メタデータのパッケージを、他の組織へ全部か無しかで当てること。
