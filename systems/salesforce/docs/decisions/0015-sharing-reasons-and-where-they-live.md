# ADR-0015: 所有者の条件のルールと暗黙の子は問い合わせの時に、レコードの条件のルール・手動・チーム・暗黙の親は行に持つ。暗黙の親は子ごとの行にする

詳細は [sharing-and-record-access.md](../architecture/sharing-and-record-access.md) の 5 節と 6.3 節。

## Context

[ADR-0004](0004-record-access-model.md) は、所有者と所有者の条件の共有ルールを問い合わせの時に結び、それ以外の理由（手動、チーム、レコードの条件の共有ルール、暗黙の共有）を `record_shares` に持つとした。暗黙の共有の持ち方は決めていなかった。

本家（[Record-Level Access: Under the Hood](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_record_access_under_the_hood.pdf)、[Best Practices for Deployments with Large Data Volumes](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_large_data_volumes_bp.pdf)、2026-09-28 に確認）：

- 暗黙の付与：子の商談・ケース・取引先責任者を見られれば、親の取引先を見られる。親の取引先を見られれば、子を見られる。
- 所有者が変わると、手動の理由の行を消す。
- 1 つの親に 1 万件を超える子を置かないよう勧めている（親のスキュー）。

暗黙の共有を素直に行にすると、次のことが起きる。

- 暗黙の子（取引先の所有者が子を見る）を行にすると、取引先の所有者の変更が子の数だけの書き直しになる。
- 暗黙の親を「親 × 相手」の数の行にすると、同じ親に多くの子を同時に作る時に、同じ行を奪い合う。

## Options

1. **理由ごとに持ち方を決める。暗黙の子は問い合わせの時に親の所有者と結び、暗黙の親は子ごとの行（親、子、相手）にする**
2. 暗黙の共有を全て `record_shares` に「親 × 相手」の行で持つ
3. 暗黙の共有を全て問い合わせの時に評価する

## Decision

1 を採用する。

| 理由 | 持ち方 |
| --- | --- |
| 所有者本人・キュー・階層 | 問い合わせの時（`owner_id` と閉包） |
| 所有者の条件の共有ルール | 問い合わせの時（`owner_rule_grants` はメタデータ） |
| レコードの条件の共有ルール | `record_shares`（`rule`、`rule_id`） |
| 手動の共有 | `record_shares`（`manual`）。所有者の変更で消す |
| チーム | `record_shares`（`team`）。所有者の変更では消さない |
| 親に連動 | 問い合わせの時（`records.parent_id` の親の判定） |
| 暗黙の親 | `implicit_parent_grants`（子ごと。相手は子の所有者のグループと、子の行の付与の相手） |
| 暗黙の子 | 問い合わせの時（親の `owner_id` と、そのロールの `child_access`） |

- 暗黙の共有は、MVP では標準の「取引先 ← 商談」「取引先 ← 取引先責任者」だけにする。
- 所有者の条件のルールで子を見る利用者には、暗黙の親を与えない。行にすると、ルールの変更が子の数だけの書き直しになるため。本家の振る舞いは未検証で、差として残す。
- レコードの条件のルールの条件は、同じレコードの項目だけで決まる式（数式の分類 A）に限る。
- 2 は、取引先の所有者の変更と、親のスキューでのロックが重い。3 は、暗黙の親の判定が「読める子が 1 件でもあるか」の問い合わせになり、子のアクセスの判定を入れ子で評価することになる。

## Consequences

- 良くなること：
  - 取引先の所有者の変更が、子の数に依らない。
  - 同じ取引先に多くの子を同時に作っても、共有の行を奪い合わない。
- 引き受けるコスト：
  - 商談・取引先責任者の問い合わせに、親の取引先との結合が 1 つ増える。
  - 暗黙の親の行は、子の数 ×（1＋子の行の付与の数）になる。
  - 本家と違い、所有者の条件のルールで子を見る利用者に親を見せない。

## Confirmation

- 決定表：`DT-SHR-001` の「行の付与」と「所有者」の列を、理由ごとの持ち方と対応させた表駆動テストにする。
- 性質ベーステスト：任意の子・親・所有者・共有の操作の列で、暗黙の親・子の判定が参照の評価器と一致する。
- 性能テスト（E5）：1 つの取引先に 1 万件の商談を並行で作っても、行ロックの待ちが増えない。取引先の所有者の変更が子の数に依らず一定の時間で終わる。
