# ADR-0064: Web からのリードのフォームの公開の受け口

## Context

- 組織は、自社の Web サイトの問い合わせ・資料請求のフォームから、リードを直接作りたい（本家の Web-to-リードに相当）。[intent.md](../intent.md) の L4 はこのフォームを前提に外部送信規律を問うが、MVP の一覧にも設計にもない。MVP に入れるかは PM の判断（[intent.md](../intent.md) の「PM の判断待ち」）。この ADR は、作るときの形を決める。
- 本システムの入口は、どれも認証した利用者か OAuth のトークンを前提にしている（[security.md](../architecture/security.md) の 2 節、B1〜B3）。フォームは、認証のない、インターネットの誰からでも届く初めての書き込みの入口になる。ボット・スパム・大量の送信・注入の的になる。
- 書き込みは、データ層を通す（直接の SQL を書かない。AGENTS.md）。DML の手順（[ADR-0008](0008-dml-order-of-execution.md)）、重複の規則（[ADR-0022](0022-duplicate-rules-and-japanese-matching.md)）、フロー、入力規則は、フォームからの作成にも効く必要がある。
- 重複の規則の応答（`DUPLICATE_DETECTED`）をそのまま返すと、匿名の送り手に「このメールのリードがある」ことを漏らす（[security.md](../architecture/security.md) の 4 節の `existence`）。
- 送り手の端末の情報（IP、利用者のエージェント）と、外部のボット判定の事業者に送る情報の扱いは、法務の確認が要る（L4・L12）。
- 本家の 1 日の受け付けの上限とスパムの対策の細部は確かめていない（未検証。E5 の着手の時に確かめる）。

## Options

1. フォームの受け口を持たない。組織は自分のサーバーから REST API を呼ぶ（OAuth の資格を組織のサーバーに置く）
2. **専用のホストの公開の受け口に、メタデータで定めたフォームを置き、受け付けは待ち行列に入れて、フォームごとの実行の利用者の権限で非同期にデータ層へ書く。守りを層に重ねる**
3. 組織のホスト（`<org>.my.<brand>.<domain>`）の上に公開の受け口を置き、受け付けた要求の中で同期に DML を実行する

## Decision

2 を提案する。詳細は [sales-objects.md](../architecture/sales-objects.md) の 9 節。

- **フォームの定義はメタデータ**（`web_lead_form`。バージョンを上げる。ADR-0003）：対象のオブジェクト（MVP はリードだけ）、受ける項目の許可の一覧（一覧にない名前は捨てる）、必須、固定の既定値（`source = web` など）、所有者（キューか利用者）、許す送り元のオリジン、送信の後に戻す URL の許可の一覧、組織のプライバシーの方針の URL（必須）、同意の確認の項目の有無、実行の利用者。
- **実行の利用者**：フォームごとに、組織の「フォームの利用者」（ログインできない、ライセンスを消費しない統合の利用者）を 1 人結ぶ。権限セットで、対象のオブジェクトの `create` と許可した項目の FLS だけを渡す。書き込みは、この利用者の権限でデータ層を通す。フォームの定義の許可の一覧と FLS の両方を通った項目だけが書かれる。
- **専用のホスト**：`forms.<brand>.<domain>/f/<form_key>`。組織のホストと分け、利用者のセッションのクッキーが届かないようにする（CSRF とクッキーの漏れを構造で防ぐ）。`form_key` は 128 ビットの乱数で、組織の ID を出さない。
- **受け付けと書き込みを分ける**：`form-intake`（DB に書かない小さなサービス）が、本文の大きさ（32KB）、形、許可の一覧、項目の型の検査をして、受け付けを SQS に入れ、常に同じ 202（または戻す URL への 303）を返す。Worker が実行の利用者の権限で、通常の DML の手順（重複の規則・入力規則・フロー）で作る。公開の流量の波を DB に直接当てない。
- **守りの層**：(1) WAF の IP ごとのレート制限、(2) フォームの埋め込みの小さなスクリプトが渡す署名付きの時刻の token（入力の時間が短すぎる・token のない・古い送信を落とす）と、見えない罠の項目、(3) 組織とフォームごとの 1 日の受け付けの割り当て（`alloc.web_form_submissions`）、(4) 内容の規則（URL の数、禁止の語、同じ送り元の繰り返し）、(5) 外部のボット判定（`ChallengeVerifier` の口の後ろ。事業者の選定と既定は法務の L4・L12 の後）。落とした送信も、送り手には同じ応答を返す（落としたことを教えない）。
- **隔離**：規則に当たった送信と、`block` の重複の規則に当たった送信は、リードを作らず「隔離した送信」（`web_form_submissions`、14 日）に入れ、管理者が Setup で見て、作るか捨てる。重複の有無を送り手に返さない。
- **記録**：送信ごとに、受け付けの時刻、結果、理由のコード、組織ごとの鍵の HMAC にした IP を 30 日持つ（調査と繰り返しの判定のため）。リードのレコードに IP・利用者のエージェントを書かない。外部へ送る情報は、既定ではない。
- 1 を採らない理由：多くの組織は自分のサーバーを持たず、静的なサイトのフォームから送りたい。OAuth の資格を Web のページに置かれる事故を招く。
- 3 を採らない理由：公開の流量とボットの波が、組織のホストと DB の書き込みに直接当たる。組織のホストのクッキーが届く経路になる。

## Consequences

- 認証のない書き込みの入口が増える。漏えいの経路の登録簿に行を足し（`LEAK-031`）、ペンテストの範囲に入れる。
- 非同期なので、送り手に入力規則の失敗を返せない。フォームの側の検査（必須・形）は受け口で行い、入力規則・フローでの失敗は隔離に入れて管理者に知らせる。
- 「フォームの利用者」の権限が広すぎると、フォームが組織への書き込みの穴になる。権限セットの付与を `security:sensitive` の変更にし、Setup で警告する。
- 本家のフォームの HTML をそのまま使う組織は、項目の名前と送り先を書き換える必要がある。移行の文書に書く（[bulk-and-import.md](../architecture/bulk-and-import.md) の 15 節）。

## Confirmation

- 決定表 `DT-WLF-001`（検査の結果 × 重複の規則 × 割り当て → 作成・隔離・捨てる、と送り手への応答）を表駆動テストにする。全ての行で、送り手への応答が同じであることを確かめる。
- 性質ベーステスト（PROP-WLF-001）：任意のフォームの定義・FLS・送信の本文で、作ったリードに書かれた項目は「許可の一覧 ∩ 実行の利用者が編集できる項目 ∪ 固定の既定値」の中だけにある。
- 否定側のテスト（`LEAK-031`）：既存のリードと同じメールの送信と、新しいメールの送信で、応答の本文・状態・見出しが区別できない。組織のホストのクッキーが `forms.` のホストに送られない。
- 上限の試験：`alloc.web_form_submissions` のちょうどで受け付け、1 つ超えたら隔離に入る（送り手への応答は変わらない）。
