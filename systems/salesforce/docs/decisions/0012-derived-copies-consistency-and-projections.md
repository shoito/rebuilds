# ADR-0012: ピボットと射影は正本の写しとして同じトランザクションで書き、整合の検査で差を 0 に保つ。射影は S2 以降に大口の組織にだけ作る

詳細は [data-storage.md](../architecture/data-storage.md) の 3.4 節、6 節、7 節。

## Context

[ADR-0002](0002-custom-object-storage.md) は、ピボットの表を正本（`records`）の写しとし、ずれを検出して作り直す整合の検査を運用するとした。また、大口の組織のよく使うオブジェクトの読みが遅い時に、S2 以降で射影の表（組織・オブジェクトの専用の実テーブル）を検討し、この判断を data-storage の領域の ADR で行うとした。

本家は、よく使う項目を持つ skinny table を、元の表の変更と同期して持つ。200 列までで、他のオブジェクトの項目は持てず、サポートへの依頼で作る（[Best Practices for Deployments with Large Data Volumes](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_large_data_volumes_bp.pdf)、2026-09-28 に確認）。同期の方法（同じトランザクションか）は確かめられなかった（未検証）。

## Options

写しの作り方：

1. **写しを 1 つの純粋な関数（`derivePivotRows`）で決め、保存では同じトランザクションで差分を書き、整合の検査でも同じ関数で比べる**
2. 保存では写しを書かず、outbox から非同期に作る

射影：

- a. **S2 以降、運用の判断で大口の組織にだけ作る。同じトランザクションで書く。100 列まで**
- b. 利用者が自分で作れるようにする
- c. 射影を作らず、分析用の写し（reports-and-dashboards の領域）だけで受ける

## Decision

1 と a を採用する。

- 写しの行は、レコードとメタデータの部品から純粋な関数で決める。保存・型の変換・数式の作り直し・整合の検査は、同じ関数を使う。
- 整合の検査は、組織ごとに 7 日で全件を一周し（小さなオブジェクトは毎日）、ID の範囲ごとのハッシュで比べ、差のあるレコードだけを直す。差は保存の経路の不具合として警告する。
- 射影は、生きている行が 1,000 万件以上で、リストビュー・レポートの p95 が NFR-001 の 2 倍を 7 日続けて超えたオブジェクトに、Ops が作る。1 組織 3 つ、1 クラスタ 500 まで。
- 射影は同じトランザクションで書き、参照する全ての項目が射影にある時だけ計画が使う。射影に入った項目の型の変換・削除で `stale` にし、作り直すまで使わない。
- 射影の DDL は、専用の DB のロールを持つ Worker が、許可リストの形だけで行う。
- 2 は、書いた直後の問い合わせに出ない。一意の検査も非同期にできない。
- b は、利用者の設定で DDL が増え、ADR-0002 が避けた実テーブルの問題が戻る。c は、対話の経路のリストビューの遅さを解かない。

## Consequences

- 良くなること：
  - 写しの意味が 1 つの関数に閉じ、保存と検査で食い違わない。
  - 大口の組織の読みを、正本の形を変えずに速くできる。射影は捨てても正本は失われない。
- 引き受けるコスト：
  - 射影を持つオブジェクトは、保存のたびに射影の行も書く。S2 の前に、書き込みの速さへの影響を測る。
  - 射影の表の分だけ、マイグレーションの外の DDL を許す。許可リストと専用のロールで狭める。
  - 整合の検査が reader の読みを使い続ける。組織ごとの DB の時間に数える。

## Confirmation

- 性質ベーステスト：任意の操作の列で、保存で書いた写しが、`derivePivotRows` で全件を作り直したものと一致する。
- 結合テスト：射影を `stale` にしても、同じ問い合わせが同じ結果を返す。
- lint：`proj_` の許可リストの外の DDL を、マイグレーションの外で禁止する。
- 本番：整合の検査で直した件数を数え、0 を保つ。
