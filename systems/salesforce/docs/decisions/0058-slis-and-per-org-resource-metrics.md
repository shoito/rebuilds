# ADR-0058: SLI は経路ごとに合成監視とサーバーの計測で持ち、組織ごとの使用量は DB の表に全件、メトリクスには上位の組織だけを出す。ログとトレースには組織の ID を持たせ、個人データを入れない

詳細は [observability.md](../architecture/observability.md) の 2〜4 節。

## Context

- 各領域が、SLI の追加を Ops に依頼した（レコードのページ、問い合わせ、保存、フロー、レポート、検索、イベント、一括、デプロイ、共有、監査、上限）。
- [ADR-0042](0042-org-allocations-fair-queuing-and-limit-info.md) は、組織ごとの DB の時間を 1 分の桶で数え、`org_db_time_minutes` に書き、重い組織の状態を `org_db_time_heavy{org}` として渡すとした。
- 組織は S1 で 5,000、S3 で 50 万ある。組織の ID をメトリクスのラベルに全て載せると、系列の数が組織の数 × 指標の数になる。
- 問い合わせの文字列・検索の語・レコードの値は個人データを含みうる（[query-language-and-api.md](../architecture/query-language-and-api.md) の 8 節、[search.md](../architecture/search.md) の 9 節）。

## Options

組織ごとの計測：

1. **全ての組織の使用量は Aurora の表（1 分の桶）に持つ。メトリクスには、クラスタごとの上位 50 の組織と、「その他」だけをラベルにする**
2. 全ての組織をメトリクスのラベルにする
3. 組織ごとの使用量をログからだけ集計する

## Decision

1 を採用する。

- SLI は、利用者の経路ごとに持つ：レコードのページ、リストビュー、REST の読み書き、問い合わせ、保存（自動化の時間を除いた分と含む分）、レポートの同期、検索、変更のイベントの遅れ、Webhook の配信、一括の取り込み、メタデータの変更の反映（K2）、デプロイの止まり、ログイン。値と SLO は observability.md の 3 節。
- 可用性の SLI は、ALB の 5xx と合成監視の両方で数える。合成監視は、専用の監視の組織を東京と大阪に置き、1 分ごとに主な経路を通す。
- 組織ごとの使用量（DB の時間、要求の数、429 の数、上限に近いトランザクション、Worker の仕事の時間）は、全件を `org_*_minutes` の表に持ち、7 日で集計の粒度を落とす。メトリクスの `org` のラベルは、1 分ごとに上位 50（DB の時間）を選び、他は `org="_other"` にまとめる。選ばれた組織の ID はハッシュでなく ID のまま（運用者が特定するため）。
- ログは JSON で、`org_id`・`request_id`・`trace_id`・`user_id` を持つ。問い合わせは AST の形のハッシュ、検索の語はハッシュと長さだけ。レコードの値・項目の値・エラーの文言の値の差し込みを入れない（ログの型で禁止する）。保持は 30 日。
- トレースは OpenTelemetry で、`org_id` と `shard_no`・`cluster_id` を属性に持つ。標本は 1%、エラーと 1 秒を超える要求は全て残す。
- 2 は、S3 で系列が数千万になり、AMP の費用と問い合わせの速さが持たない（未検証）。3 は、騒がしい隣人の検知が分の単位で遅れる。

## Consequences

- 良くなること：
  - メトリクスの系列の数が、組織の数に依らず一定。
  - 全ての組織の使用量を、DB の表から後で調べられる。
  - ログとトレースから、組織と要求を結べる。
- 引き受けるコスト：
  - 上位 50 から外れた組織の急な変化は、メトリクスで見えない。表への問い合わせで見る。
  - 使用量の表の書き込みが、DB の負荷になる（組織 × 1 分の行）。7 日で粒度を落とす。

## Confirmation

- lint：ログの型に、レコードの値・問い合わせのリテラル・検索の語の生の値を入れる経路がない。
- 本番：秘密と個人データの出力の走査（ログの標本）で 0 件。
- 本番：メトリクスの `org` のラベルの異なる値の数が、1 時間で 500 を超えない。
