# ADR-0059: 騒がしい隣人は、アプリの DB の時間と、DB の側の実行中のセッションの標本の 2 つで見つけ、自動の対処は Worker の重みまでにし、対話の経路の絞りは人が決める

詳細は [observability.md](../architecture/observability.md) の 5 節。

## Context

- NFR-003 と K4 は、上限まで負荷をかけた組織があっても、他の組織の p95 の悪化を 10% 以内にすることを求める。
- [ADR-0042](0042-org-allocations-fair-queuing-and-limit-info.md) は、組織の DB の時間がクラスタの 20% を 5 分続けて超えたら「重い」とし、Worker の重みを半分にするとした。対話の経路は止めない。
- アプリの DB の時間は、データ層の計測器で数える。データ層を通らない経路（組織をまたぐ処理、保守、計測の漏れ）は数えられない。
- PostgreSQL の統計（`pg_stat_statements`）は文の形ごとで、組織を区別できない。共有の表なので、同じ文の形を全ての組織が使う。

## Options

1. **アプリの DB の時間を正にし、DB の側で 1 秒ごとに `pg_stat_activity` を標本にして、`application_name` に入れた組織の ID ごとの実行中のセッションの数を数え、2 つを突き合わせる**
2. アプリの DB の時間だけ
3. DB の側の計測だけ

## Decision

1 を採用する。

- データ層は、トランザクションの開始で `SET LOCAL application_name = 'o:<org_id>:<path>'` を設定する（UUID の 36 文字を入れても、PostgreSQL の名前の長さの上限 63 バイトに収まる）。組織をまたぐ処理は `x:<job>`、保守は `m:<job>`。
- 監視の Worker が、各クラスタの writer と reader で 1 秒ごとに `pg_stat_activity` の `state = 'active'` の行を読み、組織ごとの実行中のセッションの数（平均の実行中のセッション、AAS）を 1 分の桶に足す。
- 2 つの見方：
  - 「重い」：アプリの DB の時間がクラスタの 20% を 5 分（ADR-0042 のまま。Worker の重みを自動で半分に）。
  - 「漏れ」：DB の側の AAS の組織の割合が、アプリの DB の時間の割合より 2 倍以上大きい状態が 10 分続く。計測の漏れ（データ層の外の経路）の疑いとして警告する。
- 自動の対処は Worker の重みまで。対話の経路を絞る操作（組織の長い要求の同時実行の上限を一時的に下げる、組織の API の割り当てを下げる、特定の連携のクライアントを止める）は、runbook に従って人が決め、組織の監査に `support` として残す。
- 警告は、ほかの組織の SLI の悪化（クラスタの p95 がいつもより 10% 以上悪い）と重なった時だけ呼び出し（page）にする。重い組織がいても、他の組織が遅くなっていなければ、チケットにする。
- 2 は、計測の漏れに気づけない。3 は、reader のレポートや Worker の仕事の区別が粗く、トランザクションの上限の内側の多くの小さな要求を過小に見る。

## Consequences

- 良くなること：
  - 計測の漏れ（データ層を通らない経路）を、独立な計測で見つけられる。
  - 自動の対処が、利用者の画面を止めない範囲にとどまる。
  - 呼び出しが、実際に他の組織が遅い時に限られる。
- 引き受けるコスト：
  - 1 秒ごとの標本は、短い文を取りこぼす。平均の傾向だけを見る。
  - `application_name` を変える `SET LOCAL` が、トランザクションごとに 1 文増える。

## Confirmation

- 負荷試験（E12）：上限まで負荷をかける組織と、普通の組織 100 で、「重い」の検知が 5 分以内、他の組織の p95 の悪化が 10% 以内（NFR-003）。
- 障害の注入：データ層を通らない重い文を流すと、「漏れ」の警告が 10 分以内に出る。
- 結合テスト：全ての DB の接続の経路で、`application_name` が決めた形になっている。
