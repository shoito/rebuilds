# ADR-0030: ダッシュボードは見る人の権限で集計し、部下の視点は部下と見る人の権限の共通部分にする。指定した実行ユーザーの形は持たず、定期の配信は受け取る人ごとに実行する

詳細は [reports-and-dashboards.md](../architecture/reports-and-dashboards.md) の 7 節と 8 節。

## Context

ダッシュボードは、複数のレポートの集計をグラフで並べる。営業の管理職は、自分のチームの数字と、部下 1 人ずつの数字を見る。定期の配信は、レポートの結果をメールで決まった時刻に届ける。

本家（2026-09-28 に確認）：ダッシュボードの見え方は 3 つある。指定した実行ユーザー（全員がその人の権限で見る）、ログインしている利用者（動的なダッシュボード）、自分のチームの利用者（上司が部下の視点で見る）（[Metadata API Developer Guide](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/api_meta.pdf)、Winter '27 版の Dashboard）。組織で 1 時間にダッシュボードの更新 200、結果の取得 5,000。1 人が購読できるレポートは 5（[Reports and Dashboards REST API Developer Guide](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_analytics_rest_api.pdf)）。動的なダッシュボードは Enterprise 5、Unlimited・Performance 10、Developer 3 まで。動的なダッシュボードは定期の更新と購読ができない（[Dynamic Dashboards](https://help.salesforce.com/s/articleView?id=analytics.dashboards_dynamic_overview.htm&type=5)、2026-09-28 に確認）。他の人を実行ユーザーにするには「自分のチームのダッシュボードの参照」か「すべてのデータの参照」が要る（[Configure Dashboard Data Visibility in Salesforce Classic](https://help.salesforce.com/s/articleView?id=analytics.dashboards_select_running_user.htm&type=5)、2026-09-28 に確認）。

intent は「利用者が見られないレコードは、レポートの集計に現れない」とする。指定した実行ユーザーの形では、見る人が見られない行が、実行ユーザーの権限で集計に入る。

## Options

1. **見る人の形を既定にし、部下の視点は「部下の権限 ∩ 見る人の権限」で集計する。指定した実行ユーザーの形は持たない。定期の配信は受け取る人ごとに実行する**
2. 本家と同じ 3 つの形を持つ。指定した実行ユーザーの形は、結果を全員で共有するスナップショットにする
3. 指定した実行ユーザーの形を、`view_all_data` を持つ人が作ったものに限って持つ

## Decision

1 を採用する。

- ダッシュボードの `view_mode` は `viewer`（既定）と `team_member`。見え方は `DT-DSH-001` で決める。
- 部下の視点 S を選ぶには `view_my_team_dashboards`（ロール階層の部下）か `view_all_data`（組織の任意の利用者）が要る。集計は、S の共有の条件と見る人の共有の条件の `AND`、FLS は 2 つの権限の形の共通部分にする。見る人が見られない行・項目は決して入らない。
- ドリルダウンも同じ権限（見る人、または共通部分）でレポートを開く。
- 部品は 20、条件は 5（各 50 の値）。部品の実行はレポートの実行と同じ経路・予算。結果は見る人ごと（視点ごと）に 10 分キャッシュし、更新は 1 人 1 分に 1 回まで。組織で 1 時間に更新 200、結果の取得 5,000。
- 全てのダッシュボードが見る人ごとの集計なので、動的なダッシュボードの数の上限は持たない。
- 定期の配信は、受け取る人ごとにその人の権限で実行する。フォルダを見られない人には送らない。他の人を受け取る人にするには `schedule_reports_for_others` が要る。組織の外のアドレスには送らない。1 人の購読 5、受け取る人 50。
- 2 は、見る人が見られない行が集計に入り、intent の約束に反する。スナップショットの共有は、見る人の権限と無関係に集計の値を配ることになる。3 は、`view_all_data` の人の権限で集計した値を、見る人の権限に関わらず見せる点で 2 と同じ。
- 全員に同じ数字を見せたい需要には、MVP の後に、集計の値を別のオブジェクトに保存するスケジュールのフローで応える案を検討する。値の共有は通常の共有で決まる。PM に intent との関係を確認する。

## Consequences

- 良くなること：
  - どの見え方でも、見る人が見られない行・読めない項目が集計に入らない。
  - 部下の視点が「絞る」道具になり、「広げる」道具にならない。
  - 定期の配信で、購読した人の権限の数字が他の人に届かない。
- 引き受けるコスト：
  - 本家から移る組織で、指定した実行ユーザーのダッシュボード（全員が同じ経営の数字を見る）が作れない。移行の文書に書き、代わりの案を示す。
  - 見る人ごとの集計なので、多くの人が開くダッシュボードの費用が大きい。キャッシュと 1 時間の割り当てで抑える。
  - 定期の配信は受け取る人の数だけ実行する。受け取る人を 50 に限る。

## Confirmation

- 決定表：`DT-DSH-001` を表駆動テストにする。
- 性質ベーステスト：`PROP-RPT-002`（任意の見る人 U と視点 S で、結果が `evaluate(R, restrict(restrict(S_db, S), U))` と一致し、U の結果に入らない行が入らない）。
- 否定側のテスト：定期の配信で、受け取る人ごとの結果が、その人の見られる行だけで作られる。フォルダを見られない人に送られない。
- 上限の試験：部品 20、条件 5、購読 5、受け取る人 50、1 時間の更新 200。
