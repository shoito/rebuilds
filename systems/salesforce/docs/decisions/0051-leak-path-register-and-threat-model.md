# ADR-0051: 組織をまたぐ漏えいと、見えないデータの漏えいの経路を 1 つの登録簿にし、経路ごとに否定側のテストと本番の検査を必須にする

詳細は [security.md](../architecture/security.md) の 3 節と 4 節。

## Context

この題材で最も重い事故は、他の組織のデータが見えること（NFR-009）と、同じ組織の中で見せてはならないレコード・項目が見えること（intent の「守るべき振る舞い」）である。

各領域は、それぞれの経路で判定を 1 か所に集める設計をした。

- 問い合わせ・リストビュー・レポート・検索は、コンパイラの段 3・4 の 1 か所で権限と共有の条件を付ける（[ADR-0003](0003-metadata-driven-runtime.md)、[ADR-0024](0024-list-views-as-filter-ast.md)、[ADR-0029](0029-report-execution-on-reader-per-viewer.md)、[ADR-0032](0032-search-permission-post-filter.md)）。
- 変更のイベントは `view_all` を要し、FLS を配信の時にかける（[ADR-0034](0034-event-subscription-access-and-org-events.md)）。
- Sandbox は複製の経路で伏せる（[ADR-0038](0038-sandbox-types-and-masked-copy.md)）。

一方で、経路は増え続ける（ピボットの表、キャッシュ、カーソル、S3 の結果のファイル、ログ、エラーの文言、統計、応答の時間）。経路ごとの守りが各領域の文書に散ると、新しい経路を足した時に、否定側のテストと本番の検査を付け忘れる。

## Options

1. **経路の登録簿（`LEAK-*`）を security.md に持ち、各行に「守り」「否定側のテスト」「本番の検査」を必須にする。CI で、全ての行にテストの ID があることを確かめる**
2. 各領域の文書のセキュリティの節に任せる
3. 外部のペンテストだけで確かめる

## Decision

1 を採用する。

- 登録簿の 1 行は、経路（どこから、何が漏れうるか）、種類（`cross_org`：組織をまたぐ、`in_org`：組織の中の見えないレコード・項目、`existence`：存在や件数の 1 ビット）、守り（ADR）、否定側のテストの ID、本番の検査、持ち主の領域を持つ。
- 初期の行は security.md の 4 節に置く（records、ピボット、検索、変更のイベント、レポート、Sandbox、一括、キャッシュ、カーソル、エラーと統計など 30 行）。
- 新しい経路（新しい API、新しい写し、新しいキャッシュ）を足す変更は、登録簿の行を足す。`security:sensitive` の PR のテンプレートで問う（[ADR-0062](0062-security-sensitive-change-flow.md)）。
- CI は、登録簿の全ての行のテストの ID が、テストのコードから参照されていることを確かめる（要件 ID の追跡と同じ仕組み）。
- 脅威は STRIDE で部品ごとに整理し、登録簿は情報の漏えい（I）の細目とする。
- 2 は、同じ種類の漏えい（例：件数から存在を推し量る）への対策が領域ごとにずれる。3 は、ペンテストが見る範囲は時点の標本で、回帰を止められない。

## Consequences

- 良くなること：
  - 漏えいの経路が 1 か所で見え、否定側のテストの抜けを機械的に見つけられる。
  - 領域の間で、同じ種類の漏えいに同じ守りを使える。
- 引き受けるコスト：
  - 登録簿の保守。持ち主はセキュリティの担当と、各領域の Dev。
  - 行を足すまで、新しい経路のテストは CI で求められない。PR のテンプレートとレビューに頼る部分が残る。

## Confirmation

- CI：`LEAK-*` の全ての行に、テストのコードから参照される ID がある。
- 性質ベーステスト：任意の 2 組織で、一方のコンテキストから他方の行・文書・イベント・ファイルが返らない（全ての経路の API を生成の対象にする）。
- 外部のペンテスト（E12）：登録簿を渡し、登録簿にない経路を探してもらう。見つかった経路は行として足す。
