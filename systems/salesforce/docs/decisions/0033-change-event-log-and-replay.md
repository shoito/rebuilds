# ADR-0033: 変更のイベントは outbox からイベントの専用の Aurora に書き、論理シャードの唯一の書き手が確定の順の replay_id を付けて 3 日保つ

詳細は [events-and-integrations.md](../architecture/events-and-integrations.md) の 3 節。

## Context

NFR-010 は、変更のイベントを確定から購読者まで p95 5 秒で、少なくとも 1 回、レコードごとの順序を守って届け、3 日は再生できることを求める。[ADR-0008](0008-dml-order-of-execution.md) は、変更のイベントを保存の手順 11 で outbox に 1 回だけ書くとした。architecture の README は、再生の置き場所（Aurora の分割の表、Kinesis Data Streams など）を E8 の着手前に決めるとした。

本家（[Change Data Capture Developer Guide](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_change_data_capture.pdf)、Winter '27 版、2026-09-28 に確認）：

- 変更のイベントは最大 3 日保ち、購読者は過去のイベントを取り直せる。
- 見出しに、オブジェクト、レコードの ID、変更の種類、変わった項目、トランザクションの ID とその中の順、確定の時刻、確定した利用者を持つ。
- イベントを作れない時は、値のない隙間のイベントを送る。1 つのトランザクションの 10 万の変更を超えた分は、あふれのイベントにまとめる。

## Options

1. **イベントの専用の Aurora のクラスタの日ごとの分割の表。Relay が論理シャードごとに 1 つの書き手で、組織の中で確定の順に増える `replay_id` を付ける**
2. Kinesis Data Streams（組織の ID で分けたシャード）に書き、購読者ごとのカーソルを別に持つ
3. 主の Aurora の outbox をそのまま 3 日保ち、購読者が outbox を読む

## Decision

1 を採用する。

- Relay は、論理シャードごとに advisory lock を持つ Worker のタスクで、outbox の未送の行を `id` の順に読み、組織ごとに `replay_id`（確定の時刻 48 ビット｜シャードの中の連番 16 ビット）を付けて `change_events` に書く。`event_id` の一意の制約で二重の送信を捨てる。
- 同じレコードの保存は行ロックで順番になり、後の保存の outbox の行は前の確定の後に入るので、`id` の順に送ればレコードごとの順序が守られる。1 つのトランザクションの行は分けずに送り、`tx_key`・`tx_seq` で境目を示す。
- 1 レコード 1 件のイベントにする。長いテキストは 32KB、1 件は 256KB まで。超えたら隙間のイベント。
- 保存の手順を通らない変更（型の変換、整合の検査の直し、消去）は、隙間のイベント（`GAP_*`）を outbox に書く。1 つのトランザクションの DML の行は 1 万までなので、あふれのイベントは持たない。
- 保持は 3 日。4 日目の分割を `DROP` する。保持の外の `replay_id` は 410 `REPLAY_ID_EXPIRED`。
- 読みは SSE（`Last-Event-ID`）と取り出しの API（`after`、1,000 件まで）。gRPC は MVP の後。
- 対象のオブジェクト（エディションの割り当て）の変更だけを outbox に書く。
- 2 は、組織ごとの確定の順の番号を Kinesis の外で持つ必要があり、組織の数が多いとシャードへの振り分けで順と費用の扱いが難しい。3 日の中の時刻からの開始も、別に索引が要る。
- 3 は、購読者の追いつき・再生の読みが、レコードの保存の DB に及ぶ。outbox の行が 3 日分たまり、保存の経路の表が大きくなる。

## Consequences

- 良くなること：
  - 組織の中で確定の順の番号が付き、レコードごとの順序と、トランザクションの境目を受け手が扱える。
  - 再生の読みが、保存の DB に及ばない。
  - 開始の位置（番号・時刻・最も古い）を、同じ表の索引で扱える。
- 引き受けるコスト：
  - イベントのための Aurora のクラスタを 1 つ運用する（S1 で 3 日 約 130GB）。
  - Relay の書き手が論理シャードごとに 1 つなので、1 つの論理シャードの量に上限がある（大口の組織は S2 で専用のシャード）。
  - 1 レコード 1 件なので、一括の取り込みでイベントが多い。

## Confirmation

- 性質ベーステスト：任意の保存の列（並行、巻き戻り、部分の成功）で、確定した保存ごとにちょうど 1 つのイベントがあり、同じレコードの順が確定の順と一致する。巻き戻った保存のイベントはない。
- 障害の注入：Relay の書き込みの後、outbox の印の前に落としても、重複は `event_id` で捨てられる。
- 結合テスト：3 日を過ぎた `replay_id` が 410。SSE の続き。
- 合成監視：確定から購読者まで p95 5 秒（NFR-010）。
