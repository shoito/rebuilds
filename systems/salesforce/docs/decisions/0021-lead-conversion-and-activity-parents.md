# ADR-0021: リードの変換は 1 つのトランザクションの合成の DML にする。活動は主の親 1 つと割り当てられた本人で共有を決める

詳細は [sales-objects.md](../architecture/sales-objects.md) の 4 節と 5 節。

## Context

営業の標準オブジェクトのうち、次の 2 つは、保存の手順（[ADR-0008](0008-dml-order-of-execution.md)）と共有（[ADR-0004](0004-record-access-model.md)、[ADR-0015](0015-sharing-reasons-and-where-they-live.md)）の両方に関わる。

- **リードの変換**：1 件のリードから、取引先・取引先責任者・商談を作り（または既存のものに合わせ）、活動を付け替え、リードを変換済みにする。途中で失敗すると、取引先だけができた半端な状態が残りうる。
- **活動**：ToDo・行動は、誰と（取引先責任者かリード）・何と（取引先、商談など）の多態の参照を持ち、追加の関係者を 50 件まで持てる。ADR-0004 は「活動は親のレコードの判定に従う」としたが、親が多態で複数ありうる時の規則を決めていなかった。

本家（2026-09-28 に確認）：

- 変換は取引先・取引先責任者・任意で商談を作る。変換済みの状態は、状態の値を書き換えるだけでは作れない。キューが所有するリードは所有者の指定が要る。変換したリードは、専用の権限を持つ人だけが更新できる（[Apex Developer Guide](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_apex_developer_guide.pdf)、[Object Reference](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/object_reference.pdf)、Winter '27 版）。
- 既存の取引先・取引先責任者には空の項目だけを入れる（ヘルプの要約。本文は未検証）。
- 活動は、リード 1 件か取引先責任者 50 件までに関連付けられ、自分の共有の表を持たない（Object Reference、[Record-Level Access: Under the Hood](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_record_access_under_the_hood.pdf)）。活動を見られる人の細部は未検証。

## Options

リードの変換：

1. **サーバーの 1 つの API で、1 件の変換を 1 つの単位（全部か無しか）にする。中の作成・更新は全て通常の DML の手順を通す**
2. 画面が複数の API（作成・更新）を順に呼ぶ
3. 変換を、システムが持つ画面のフローとして作る

活動の共有：

- a. **主の親（何と、なければ誰と）1 つの水準と、割り当てられた本人（と上司）の水準の強い方にする。追加の関係者は広げない**
- b. 関係者の全て（誰と・何と・追加の関係者）のどれかを見られれば見られる
- c. 関係者の全てを見られる時だけ見られる

## Decision

1 と a を採用する。

- 変換の API は 1 回 50 件まで。1 件の変換は 1 つのセーブポイントの単位にし、`all_or_none` で要求の全体を 1 つにもできる。
- リードを `FOR UPDATE` で読み、`is_converted` が真なら 409 `LEAD_ALREADY_CONVERTED` にする。同じ変換の再送で 2 回作らない。
- 作成・更新は通常の DML の手順（入力規則、重複の規則、フロー、積み上げ集計）を通し、共有の評価と outbox は最上位の最後に 1 回だけ行う（ADR-0008）。
- 項目の対応は、標準は固定の表、カスタムはメタデータ（`lead_convert_mappings`）。変換する人が元を読めない・先を編集できない項目は、黙って写さず、名前だけを応答に返す。
- 変換済みのリードは読むだけにし、`edit_converted_leads` の権限で直せる。
- 活動の主の親の ID を `records.parent_id` に写し、「親に連動」の判定に使う。割り当てられた本人と上司は `full`。
- 2 は、途中で失敗すると半端な状態が残る。3 は、変換の規則（重複の扱い、FLS、項目の対応）をフローの要素で表すことになり、テストと上限の見通しが悪い。
- b は、取引先責任者を 1 人見られるだけで、その人に関する他人の活動（商談の交渉の記録など）が見える。c は、関係者が増えるほど見えなくなり、割り当てられた本人すら自分の ToDo を見られないことがある。

## Consequences

- 良くなること：
  - 変換は全部か無しかで、再送でも重複しない。
  - 変換でも、入力規則・重複の規則・フローが通常の保存と同じく効く。
  - 活動の共有は行を持たず、主の親と所有者の変更で書き直しがない。
- 引き受けるコスト：
  - 共有の領域の DT-SHR-001 の行 3 に、活動の割り当ての行を足す必要がある。
    > 2026-09-28 の注記：統合の工程で足した。DT-SHR-001 の行 3 が「活動の割り当て（本人と上司は `full`）」になり、起票の時の行 3（`controlled_by_parent`）は行 4 に繰り下がった。
  - 多態の主の親の条件は、親のオブジェクトの種類ごとの `OR` になり、問い合わせが重くなる。E4 の PoC で測る。
  - 本家の活動の共有の規則が未検証で、本家から移る組織で見え方が違いうる。
  - FLS で写さない項目は黙って落ちるので、管理者が気づきにくい。応答と変換の記録に名前を残す。

## Confirmation

- 決定表：`DT-ACT-001`（活動の水準）と、変換の失敗の表を表駆動テストにする。
- 性質ベーステスト：任意のリードと変換の指定で、変換は全部か無しか。任意の活動・親・所有者・共有の操作の列で、活動の水準が参照の評価器と一致する。
- 上限の試験：変換 50 件で通り、51 件で拒否する。
