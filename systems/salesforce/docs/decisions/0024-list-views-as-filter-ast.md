# ADR-0024: リストビューを条件の AST で保存し、見る人の権限で毎回コンパイルする。共有は定義だけで、読めない項目を条件に持つビューは開けない

詳細は [ui-layouts-and-list-views.md](../architecture/ui-layouts-and-list-views.md) の 5 節。

## Context

リストビューは、営業の担当者が毎日使う画面である。管理者や担当者が作り、チームに共有する。intent は「利用者が見られないレコードは、リストビューの件数に現れない」とする。

- リストビューを作った人と見る人の権限は違う。作った人は読めるが、見る人は読めない項目で絞った共有のリストビューがありうる。
- 項目の名前は変わり、項目は消える。条件を文字列で持つと壊れる。
- 20 万件を超えるオブジェクトでは、選択的でない条件を断る（[ADR-0019](0019-selectivity-statistics-and-planning.md)）。

本家（2026-09-28 に確認）：リストビューは列、条件の行、条件の論理、範囲（すべて・自分の・キューなど）、共有先を持つ。「自分だけ」のリストビューはメタデータとして扱えない（[Metadata API Developer Guide](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/api_meta.pdf)、Winter '27 版の ListView）。リストビュー・レポート・問い合わせは同じ最適化器で選択性を判定する（[Best Practices for Deployments with Large Data Volumes](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_large_data_volumes_bp.pdf)）。見る人が読めない条件の項目の扱いは、公開の資料に書かれていない（未検証。E5 の `list-views` で試用の組織で確かめる）。

## Options

保存の形：

1. **問い合わせの言語の AST の部分集合を JSON で、項目は `field_id` で持つ**
2. 問い合わせの言語の文字列で持つ
3. 結果（レコードの ID の一覧）を定期的に作って持つ

読めない項目の扱い：

- a. **条件・並べ替えに読めない項目があれば、その人には開けない。列だけなら列を落とす**
- b. 読めない項目の条件を落として開く
- c. 作った人の権限で条件を評価し、見る人の共有で絞る

## Decision

1 と a を採用する。

- 条件は `filters`（10 行まで）と `logic`、列は 15、並べ替えは 2、範囲（`scope`）は `all`・`mine`・`team`・`queues`・`mine_and_queues`。範囲は共有の条件に加えて絞るだけで広げない（[ADR-0018](0018-record-query-language.md)）。
- 毎回、見る人の版・権限の形でコンパイルする。コンパイル結果は同じ権限の形の利用者で共有するが、結果は共有しない。
- 件数は、画面が求めた時だけ、見る人の共有の条件をかけた `COUNT` を 1 万件で打ち切って返す。組織の統計から件数を出さない。
- 公開のリストビューはメタデータ（版を上げる）、自分だけのものはデータにする。
- 保存の時に計画の説明で選択性を確かめて警告する。見積もりの数は管理者にだけ出す。
- 2 は、名前の変更で壊れる。画面のビルダーが文字列を作り直すことになる。3 は、見る人ごとの共有に合わせられず、古い結果を返す。
- b は、結果が広がって意図しないレコードが並び、条件の有無の差から読めない値を推し量れる。c は、作った人の権限で見る人に値を推し量らせることになる（[ADR-0013](0013-permission-sets-and-field-level-security.md) の趣旨に反する）。

## Consequences

- 良くなること：
  - リストビューを共有しても、見えないレコード・読めない項目が漏れない。
  - 項目の名前の変更でリストビューが壊れない。
  - 問い合わせと同じコンパイラと計画を通るので、判定が 1 か所にまとまる。
- 引き受けるコスト：
  - 権限の違う人には開けない共有のリストビューが生まれる。保存の時に作った人へ警告する。
  - 件数は打ち切りで、正確な大きな件数は出ない。レポートを案内する。
  - 本家の上限（条件・列の数）は公開のヘルプに見当たらない（未検証。E5 の `list-views` で確かめる）。足りない組織がありうる。

## Confirmation

- 決定表：`DT-LV-001` を表駆動テストにする。
- 性質ベーステスト：任意の定義と権限・共有の設定で、結果が参照の評価器と一致する。`scope` 付きの結果は付けない結果の部分集合になる。
- 否定側のテスト：読めない項目を条件に持つ共有のリストビューが開けない。件数に見えない行が数えられない。
- 上限の試験：条件 10、列 15、並べ替え 2。
