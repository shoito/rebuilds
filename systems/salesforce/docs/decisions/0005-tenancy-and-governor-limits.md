# ADR-0005: 組織を共有スキーマと RLS で分け、論理シャードとセルで広げる。上限は実行基盤のデータ層で強制する

## Context

組織（org）は、メタデータ・レコード・利用者・設定の単位である。Sandbox も別の組織として作る。S1 で 5,000、S3 で 50 万の組織を、共有の基盤で動かす（[architecture/README.md](../architecture/README.md) の「規模の段階」）。

組織の分離が破れると、他の会社の顧客の情報が見える。分離は守れても、1 つの組織の重い処理（大量の問い合わせ、無限に続くフロー、大きな一括の処理）が共有の DB を占めると、他の組織が遅くなる。

本家は、全てのデータとメタデータに組織の ID を持たせ、組織の ID で物理的に分割している（[Platform Multitenant Architecture](https://architect.salesforce.com/docs/architect/fundamentals/guide/platform-multitenant-architecture.html)、2026-09-28 に確認）。共有の資源を守るために、トランザクションごとの上限（ガバナ制限）を実行系で厳しく強制し、超えたら捕まえられない例外でトランザクションを巻き戻す。同期の処理での値は、問い合わせ 100 回、問い合わせで取得する行 50,000、DML 150 回、DML の行 10,000、CPU 時間 10,000ms、ヒープ 10MB である（非同期は問い合わせ 200 回、CPU 60,000ms、ヒープ 25MB）（[Apex Developer Guide](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_apex_developer_guide.pdf)、Winter '27 版、2026-09-28 に確認）。組織ごとには、24 時間の API の割り当てと、長い要求（20 秒以上）の同時実行の上限（本番で 25）を持つ（[Developer Limits and Allocations Quick Reference](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_app_limits_cheatsheet.pdf)、2026-09-28 に確認）。

## Options

組織の分け方について：

1. **共有スキーマ＋RLS。** 全ての組織のテーブルに `org_id` を持たせる。論理シャードで物理のクラスタへ広げ、S3 でセルにする
2. **組織ごとのスキーマ**
3. **組織ごとの DB（silo）**

上限の強制について：

- a. **実行基盤のデータ層で、トランザクションごとの上限と組織ごとの割り当てを強制する**
- b. **DB の機能（`statement_timeout`、接続の数、資源のグループ）だけで抑える**
- c. **組織ごとの API のレート制限だけにする**

## Decision

1 と a を採用する。

### 組織の分離

- **テナントの分け方は、他の題材（Slack の ADR-0009、Notion の ADR-0003、Auth0 の ADR-0002）に倣う。**
  - 全ての組織のテーブルに `org_id` を持たせ、主キーとインデックスの先頭に置く。ID は UUIDv7。
  - `FORCE ROW LEVEL SECURITY` を設定し、トランザクションごとに `SET LOCAL app.org_id` を設定する。
  - RLS を外すのは、組織をまたぐ管理の処理（組織の作成、課金の集計、組織の移動、Sandbox の複製）だけにし、別の DB のロールで行う。
- **組織の解決を、DB を読む前に行う。** ホスト名（`<org>.my.<brand>.<domain>`）か、API のトークンから `org_id` を決める。解決できない要求は、どの組織のデータにも触れずに 404 を返す。
- **Sandbox は、本番とは別の `org_id` を持つ組織にする。** 本番の組織との関係（元の組織）は属性で持つ。Sandbox から本番の組織のデータは読めない。Sandbox へのデータの複製は、組織をまたぐ管理の処理として Worker が行う（sandboxes-and-deploy の領域。法務の L3）。
- **組織はリージョンに固定する。** S1 は東京（DR は大阪）だけにする。

### 広げ方

- **論理シャードは 256 に固定する。** `org_id` のハッシュで論理シャードを決め、論理シャードを物理のクラスタに割り当てる表を持つ。S1 は物理 1 つに全ての論理シャードを置く。
- **1 つのトランザクションは、1 つの組織で閉じる。** 組織をまたぐ機能は、非同期のジョブにする。
- **S2 で、Sandbox と試用の組織を本番とは別のクラスタへ置く。** 開発・試験の負荷を、本番の組織から切り離す。
- **S3 でセルにする。** セルは、物理のクラスタと、Runtime・Worker のサービスの組である。組織をセルに固定し、入口で組織からセルへ振り分ける。大口の組織には専用のセルを用意する。組織をセルの間で動かす手順を、infrastructure の領域で決める。
- 2 は、S3 の 50 万の組織でスキーマの数とマイグレーションが重い（[ADR-0002](0002-custom-object-storage.md) の実テーブルと同じ問題）。
- 3 は、S1 の 5,000 の組織でも運用が重い。大口の分離は、専用のセルで行う。

### トランザクションの上限（ガバナ制限）

- **全てのデータの読み書きは、実行基盤のデータ層を通る**（[ADR-0003](0003-metadata-driven-runtime.md)）。データ層が、トランザクションごとの計測器を持ち、問い合わせ・DML・フロー・イベントの発行のたびに数える。
- 上限の初期値は次のとおり。本家の値を目安にした本システムの値で、E12 の負荷試験で決める。

| 上限 | 同期 | 非同期 |
| --- | --- | --- |
| 問い合わせの数 | 100 | 200 |
| 問い合わせで取得する行の合計 | 50,000 | 50,000 |
| DML の数 | 150 | 150 |
| DML で処理する行の合計 | 10,000 | 10,000 |
| 実行基盤の CPU 時間（DB の待ちを除く） | 10 秒 | 60 秒 |
| 結果とトランザクションの状態が使うメモリー | 10MB | 25MB |
| フローの要素の実行の数 | 2,000 | 2,000 |
| 保存で起きる自動化の入れ子の深さ | 16 | 16 |
| 変更のイベント以外のイベントの発行の数 | 150 | 150 |
| トランザクションの時間 | 2 分 | 10 分 |

- **上限を超えたら、トランザクション全体を巻き戻す。** 超えたことは、フローからも（MVP の後の）利用者のコードからも捕まえられない。エラーは、どの上限を、どこで超えたかを返す。
- **上限の値は、エディションで変えない。** 公平のための上限は全ての組織で同じにする。エディションで変えるのは、組織ごとの割り当て（下の表）だけにする。
- DB の側にも、`statement_timeout` と、トランザクションごとの `idle_in_transaction_session_timeout` を置く。これは実行基盤の計測が漏れた時の最後の守りで、上限の本体ではない。
- 一括の API での 1 回の処理（チャンク）は、非同期の上限を使う。チャンクの大きさは、上限に収まるよう実行基盤が決める（bulk-and-import の領域）。

### 組織ごとの割り当て

| 割り当て | 初期の方針 |
| --- | --- |
| API の要求 | 24 時間の総量。エディションとライセンスの数で決める。値は governor-limits の領域で決める |
| 長い要求の同時実行 | 20 秒以上続く要求を、組織ごとに同時に 25 まで |
| 一括のジョブ | 24 時間の処理の行数と、同時に動くジョブの数 |
| Worker の順番 | 組織ごとの重み付きの公平なキュー。1 つの組織が Worker を占めない |
| DB の時間 | 組織ごとに DB の時間を計測し、しきい値を超えた組織の非同期の処理を後回しにする |
| ストレージ | データとファイルの容量。エディションとライセンスの数で決める |

- 上限と割り当ての残りは、応答のヘッダー `<Brand>-Limit-Info` と、上限の API で返す（[リポジトリ共通の ADR-0006](../../../../docs/decisions/0006-brand-neutral-identifiers.md)）。

## Consequences

- 良くなること：
  - 組織の分離を、アプリのコードだけに頼らない。
  - 1 つの組織の暴走した自動化が、トランザクションの上限で止まり、共有の DB を占めない。
  - 論理シャードとセルで、組織を動かしながら段階的に広げられる。
- 引き受けるコスト：
  - 上限は利用者に見える制約になる。業務の設定（フロー、一括の処理）を、上限の中で書く工夫を利用者に求める。上限に近づいたことを知らせる道具が要る（governor-limits の領域）。
  - 全てのデータの読み書きをデータ層に通すので、直接の SQL で速くしたい場面でも使えない。例外は、組織をまたぐ管理の処理だけにする。
  - CPU 時間の計測は、Node.js のイベントループの上で、トランザクションごとに正確に分けにくい。MVP は宣言的な処理だけなので、要素の実行の数と経過時間で近似する。利用者のコードは、WASM の燃料で数える（[ADR-0001](0001-platform-and-stack.md)）。
  - 大きな組織が 1 つの論理シャードに収まる前提になる。S3 の 50 億件の組織が収まるかは、S3 の前に確かめる。

## Confirmation

- 性質ベーステスト：任意の 2 組織で、一方のコンテキストで他方の行が読めない。Sandbox の組織のコンテキストで、元の本番の組織の行が読めない。
- 結合テスト：未知のホスト名・トークンの要求が、DB に問い合わせずに 404 になる。
- 上限の試験：上の表の全ての上限で、ちょうど上限で通り、1 つ超えたらトランザクション全体が巻き戻る（records・ピボットの表・共有の行・outbox のどれにも残らない）。
- 上限の試験：上限を超えた例外を、フローの失敗の経路で捕まえても、巻き戻りが起きる。
- CI：新しいテーブルに `org_id` と RLS のポリシーがないマイグレーションを失敗させる（例外は許可リストで管理する）。
- 負荷試験（E12）：上限まで負荷をかけた組織があっても、他の組織の p95 の悪化が 10% 以内（NFR-003）。
