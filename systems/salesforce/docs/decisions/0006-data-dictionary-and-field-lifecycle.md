# ADR-0006: データ辞書は field_id と再利用しない field_no を分けて持ち、型の変換は新しい field_no へ写して切り替え、削除は 15 日保つ

詳細は [metadata-and-runtime.md](../architecture/metadata-and-runtime.md) の 3 節と 5 節。

## Context

[ADR-0002](0002-custom-object-storage.md) は、レコードの値を `records.data`（JSONB）に「項目の ID をキーにして」入れるとした。名前の変更をメタデータだけで済ませるためである。一方で、次のことが決まっていなかった。

- 項目の ID（UUIDv7、36 文字）をそのまま JSONB のキーにすると、500 項目のオブジェクトでキーだけで 1 行 18KB になる。PostgreSQL は 1 行の更新で JSONB を書き直すので、行の大きさがそのまま書き込みの費用になる。
- 型の変換（テキストから数値など）の間に、読み書きをどう扱うか。
- 項目・オブジェクトの削除から、値を実際に消すまでの期間と手順。
- カスタムの名前の付け方。本家の `__c` の接尾辞は本家の識別子である（[リポジトリ共通の ADR-0006](../../../../docs/decisions/0006-brand-neutral-identifiers.md)）。

本家は、型の変更で値のために新しい列を割り当て、既存の値を一括で写し、メタデータの指す先を切り替える。変換の間も読める。消した項目と値は、確定するか期間が過ぎるまで戻せる。レコードのごみ箱は 15 日である（[Platform Multitenant Architecture](https://architect.salesforce.com/docs/architect/fundamentals/guide/platform-multitenant-architecture.html)、[Best Practices for Deployments with Large Data Volumes](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_large_data_volumes_bp.pdf)、2026-09-28 に確認）。項目の削除の保持の日数は確かめられなかった（未検証）。

## Options

JSONB のキーについて：

1. `field_id`（UUIDv7）をキーにする
2. **オブジェクトの中で再利用しない短い番号 `field_no` をキーにし、`field_id` と分けて持つ**
3. API の名前をキーにする

型の変換について：

- a. **新しい `field_no` を割り当てて写し、終わったら指す先を切り替える。変換の間はその項目を書けない**
- b. 同じキーの値をその場で書き換える
- c. 新しいキーへ写しつつ、変換の間は両方のキーに書く

## Decision

2 と a を採用する。

- `field_id` はメタデータ・デプロイ・監査で項目を指す。`field_no` はオブジェクトの中の連番で、欠番にして再利用しない。JSONB のキーは `field_no` の 10 進の文字列にする。
  > 2026-09-28 の注記：起票の時は、`field_id` を「全組織で一意の UUIDv7」としていた。Sandbox は元の組織の ID をそのまま使う（[ADR-0038](0038-sandbox-types-and-masked-copy.md)）ので、`field_id` の一意の範囲を「**組織の系統（本番の組織と、その Sandbox）の中で一意**」に改めた。別の系統の組織の間では重ならない（UUIDv7 で新しく作るため）。全ての表の主キーの先頭は `org_id` なので、同じ `field_id` が系統の中の別の組織にあっても衝突しない。組織の間のデプロイは ID でなく API の名前で当てる（[ADR-0039](0039-metadata-package-format.md)）。
- 標準の API の名前は接頭辞なしの小文字のスネーク、カスタムは `x_` の接頭辞にする。標準に後から項目を足しても、カスタムの名前とぶつからない。
- 型の変換は、下見（変換できない値の件数と依存の検査）→ 承認 → 新しい `field_no` へ Worker が範囲ごとに写す → 1 つの版で切り替え、の順にする。変換の間、読みは新しいキーを優先し、なければ古い値を同じ変換関数で変換して返す。その項目の書き込みは 409 `FIELD_CONVERTING` で断る。
  > 2026-09-28 の注記：切り替えの後も、古い `field_no` の値を 15 日残してから消す。デプロイの戻しで古い型へ切り替え直せるようにするため（[ADR-0040](0040-deploy-validation-and-rollback.md)）。
- 削除は印を付けるだけにし、15 日は戻せる。確定（15 日の後か管理者の操作）から 7 日以内に、Worker が値とピボットの行を消す。依存のある項目は削除できない。
- 3 は、名前の変更で全ての行を書き換えることになる。1 は、行が大きくなる。
- b は、変換の途中で失敗すると、古い型の値と新しい型の値が混ざり、戻せない。c は、全ての保存が変換の状態を見て 2 か所に書くことになり、保存の経路が複雑になる。書けない時間が長すぎると分かったら c を検討する。

## Consequences

- 良くなること：
  - 名前の変更・削除・復元がメタデータの変更だけで済み、行が小さい。
  - 型の変換は、途中で中止しても古い値が残る。
  - 削除した値の消去の期限が決まり、個人データを長く残さない。
- 引き受けるコスト：
  - 1 つの項目が、変換の間 2 つの `field_no` を持つ。読みの経路に変換関数が入る。
  - 変換の間、その項目を書けない。大きなオブジェクトでは数十分かかりうる。
  - 項目の上限に、削除中の項目も数える。

## Confirmation

- 性質ベーステスト：任意の型の変換の列（中止を含む）で、変換の間の読みと、変換の後の読みが一致する。
- 性質ベーステスト：任意の削除・復元・確定の列で、確定の前は値が失われない。
- 結合テスト：変換の間の項目への書き込みが 409 になり、他の項目は書ける。
- 本番：確定から 7 日を超えた消去の件数を数え、0 を保つ。
