# ADR-0003: メタデータを版の付いた不変のスナップショットにコンパイルし、要求を 1 つの版に固定して AST から SQL を作る

## Context

組織ごとのオブジェクト・項目・画面・自動化・権限は、メタデータで決まる（[ADR-0002](0002-custom-object-storage.md)）。全ての要求は、そのメタデータを読んで解釈する必要がある。

- 1 件の要求で、オブジェクト、項目、レイアウト、FLS、入力規則、フローなど、多くのメタデータを使う。毎回 DB から読むと遅い。
- 管理者やデプロイがメタデータを変えている最中に、要求が古い定義と新しい定義を混ぜて使うと、壊れたデータを書きうる。例：項目の型の変更の途中で、古い型で検証して新しい型で保存する。
- 本家は、よく使うメタデータを大きなメタデータのキャッシュに載せ、DB の読みと再コンパイルを避けている（[Platform Multitenant Architecture](https://architect.salesforce.com/docs/architect/fundamentals/guide/platform-multitenant-architecture.html)、2026-09-28 に確認）。
- 問い合わせの言語、数式、フローは独自のものにする（[ADR-0001](0001-platform-and-stack.md)）。どこかで名前を ID に解決し、権限と共有の条件を足し、SQL にする必要がある。

## Options

キャッシュと一貫性について：

1. **版の付いた不変のスナップショット。** メタデータの変更ごとに組織の版を 1 つ上げ、版ごとのコンパイル結果を不変にしてキャッシュする。要求は開始時の版に固定する
2. **項目・オブジェクトの単位のキャッシュを、変更の通知で消す**
3. **キャッシュせず、毎回 DB から読む**

要求の処理について：

- a. **問い合わせと DML を AST にし、メタデータに対して束縛・検査・書き換えをしてから SQL にする**
- b. **問い合わせの言語を、テンプレートで直接 SQL の文字列にする**
- c. **レコードをアプリに全て読み、アプリで絞り込む**

## Decision

1 と a を採用する。

### メタデータの版

- メタデータ（オブジェクト、項目、関係、選択リスト、レコードタイプ、レイアウト、リストビュー、入力規則、フロー、承認、権限セット、共有の設定）は Aurora の表に持ち、組織に 1 つの `metadata_version`（単調に増える整数）を持つ。
- メタデータの変更は、Setup の画面の 1 回の保存も、デプロイも、**1 つのトランザクションで版を 1 つ上げる**。1 つの版の中の変更は、全部か無しかで見える（NFR-004）。
- 版ごとに、変更の差分（何を足し、変え、消したか）を残す。直前の版へ戻すデプロイは、差分を逆に当てる新しい版として作る。版を巻き戻さない。

### コンパイル済みのスナップショット

- `(org_id, metadata_version)` をキーに、メタデータを 1 つのスナップショットにコンパイルする。中身は、オブジェクトと項目の記述（API の名前 → ID の表を含む）、型の検証器、数式の AST と型、入力規則、フローの呼び出しの表、権限セットから作った「利用者の権限の形」ごとの FLS とオブジェクトの権限の表。
- スナップショットは**不変**にする。版が上がったら新しいスナップショットを作り、古いものは使われなくなってから捨てる。キャッシュの無効化は「組織の今の版」を指す小さな値だけで済む。
- キャッシュは 3 層にする。
  - L1：Runtime のプロセスの中の LRU。
  - L2：Valkey に、シリアライズしたスナップショット。
  - L3：Aurora のメタデータの表から、コンパイルし直す。
- 組織の今の版は、Valkey の値と、変更の通知（Pub/Sub）で配る。通知が届かなくても、短い TTL（初期値 5 秒）で DB を読み直す。K2 の「5 秒以内」はこの値に依る。

### 要求を 1 つの版に固定する

- 要求（またはトランザクション）の開始時に、組織の今の版を読み、その版のスナップショットで最後まで処理する。
- データを書くトランザクションは、組織のメタデータの鍵に対する共有のアドバイザリロック（`pg_advisory_xact_lock_shared`）を取り、版がまだ今の版であることを確かめる。違っていたら、新しい版でやり直す（1 回まで）。
- メタデータの変更は、同じ鍵の排他のロックを取って版を上げる。変更の確定はメタデータの行を書くだけにし、時間のかかる処理（項目の型の変換、索引の作り直し、共有の再計算）は、確定の後に Worker で行う。確定の間のデータの書き込みの止まりを、p99 1 秒以内にする（NFR-004）。

### 要求のコンパイル

- 画面・REST API・一括の API・フロー・レポートの読み書きは、全て**問い合わせの AST と DML の AST** にする。問い合わせの言語の文字列は、パーサーで AST にしてから扱う。
- AST は次の順で処理する。
  1. **束縛**：API の名前を、スナップショットで項目の ID と型に解決する。無い名前はここで失敗する。
  2. **型の検査**：比較・関数・集計の型を確かめる。
  3. **権限**：オブジェクトの権限と FLS を確かめる。読めない項目は、既定では要求の失敗にする。画面用の要求は、読めない項目を落として返す選択肢を持つ。
  4. **共有の条件の付加**：OWD とアクセスの表から作る条件を足す（[ADR-0004](0004-record-access-model.md)）。
  5. **計画**：組織・オブジェクト・項目の値の分布から、ピボットの表を使うかを選ぶ（[ADR-0002](0002-custom-object-storage.md)）。
  6. **SQL の生成と実行**：値は全てバインド変数にする。実行はガバナ制限の計測の下で行う（[ADR-0005](0005-tenancy-and-governor-limits.md)）。
- コンパイル結果は、`(org_id, metadata_version, AST のハッシュ, 利用者の権限の形)` をキーにキャッシュする。
- DML は、決まった順序で処理する：型と必須の検証 → 保存の前のフロー → 入力規則 → 一意の確認 → 書き込み（records とピボットの表）→ 共有の行の更新 → 保存の後のフロー → 積み上げ集計 → 確定 → outbox から変更のイベント。順序の詳細は metadata-and-runtime と automation-flows の領域で決める。

### 独自の言語と参照の評価器

- 問い合わせの言語と数式の言語は、独自の文法を持つ。構文は SQL と表計算の関数に寄せ、学びやすくするが、本家の SOQL・数式との互換は目標にしない（[ADR-0001](0001-platform-and-stack.md)）。
- 数式と問い合わせの条件には、**TypeScript の参照の評価器**を 1 つ持つ。SQL にできない式は評価器で判定し、SQL にできる式でも、テストで SQL の結果と評価器の結果を比べる。
- b は、名前の解決・権限・共有の条件を文字列の組み立てで足すことになり、注入と判定漏れの危険が高い。c は、大きな組織で読みの量が上限を超える。

## Consequences

- 良くなること：
  - 1 つの要求が、ちょうど 1 つの版のメタデータで処理され、途中の変更と混ざらない。
  - キャッシュの無効化が「今の版」の値だけで済み、無効化の漏れで古い定義を使う事故が起きにくい。
  - 権限と共有の条件の付加が、コンパイラの 1 か所にまとまる。
- 引き受けるコスト：
  - 変更のたびにスナップショットを作り直す。大きな組織（オブジェクト数百、項目数万）でのコンパイルの時間を、E3 で測る。差分のコンパイルが要るかもしれない。
  - データの書き込みが、メタデータの鍵の共有のロックを取る。デプロイの確定が長いと、書き込みが待つ。確定を短く保つ規則（重い処理は確定の後）を守る。
  - 問い合わせの言語・数式の言語のパーサー、型の検査、SQL の生成、評価器を自前で保守する。

## Confirmation

- 性質ベーステスト：任意のメタデータの変更の列と、並行するレコードの書き込みの列で、各書き込みが、開始時の版の定義だけで検証・保存されている。
- 性質ベーステスト：任意の数式と問い合わせの条件で、SQL にコンパイルした結果と、参照の評価器の結果が一致する。
- lint：`records` とピボットの表への SQL を、コンパイラのパッケージの外で書くことを禁止する。
- 結合テスト：メタデータの変更の確定の間に止まった書き込みの時間を測り、p99 1 秒を超えたら失敗にする。
- 結合テスト：カスタム項目の追加から、別の Runtime のタスクで使えるまでが 5 秒以内。
