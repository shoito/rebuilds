# ADR-0065: 本家からの移行の経路

## Context

- 主な利用者のうち、本家から移る組織は、取引先・取引先責任者・リード・商談・活動のデータと、カスタムオブジェクト・項目・画面・フロー・権限の設定を持っている。
- 本家のメタデータの XML、`package.xml`、Apex・SOQL との互換は持たない（[ADR-0001](0001-platform-and-stack.md)、AGENTS.md）。[intent.md](../intent.md) の Non-goals は「本家からの移行の道具が要れば、別の Epic で変換の道具として扱う」と書き、[roadmap.md](../roadmap.md) の「後回しにしたもの」に変換の道具がある。
- 一方で、各領域は本家との違いを「移行の文書に書く」と決めてきた（[ADR-0001](0001-platform-and-stack.md)、[ADR-0030](0030-dashboards-viewer-intersection-and-subscriptions.md)、[ADR-0034](0034-event-subscription-access-and-org-events.md)、数式の FLS、活動の共有、フローの要素の数え方など）。その文書はまだない。
- データの取り込みの部品はそろっている：一括の取り込みのジョブ、外部 ID での upsert、親の外部 ID での参照、ウィザードの CP932 の判定と和暦、照合の規則での既存の更新（[ADR-0036](0036-bulk-jobs-chunking-and-partial-success.md)、[ADR-0037](0037-import-wizard-upsert-and-duplicate-matching.md)）。
- 移行で失いやすいのは、レコードの間の参照（本家の ID で結ばれている）、所有者、作成日・更新日、選択リストの値、項目の変更の履歴である。
- 移行の道具の Epic を作るか、いつ作るかは PM の判断である（[intent.md](../intent.md) の「PM の判断待ち」）。

## Options

1. **MVP は「移行の文書」と CSV の取り込みの決まった手順にする。本家の ID を外部 ID の項目に入れ、親の外部 ID で参照をつなぎ、決まった順で取り込む。メタデータは管理者が作り直す。変換の道具は後の Epic で、利用者が上げた書き出しのファイルを読む形で作る**
2. 本家の組織に OAuth でつなぎ、API でメタデータとデータを読んで変換して書く道具を MVP で作る
3. 移行を支援しない。一般の CSV の取り込みだけを案内する

## Decision

1 を採用する。詳細は [bulk-and-import.md](../architecture/bulk-and-import.md) の 15 節。

> 2026-10-25 の注記：PM が範囲を決めた。MVP（E9 の `migration-import`）は移行の文書と、`legacy_id` での CSV の取り込みの手順にする。メタデータの変換の道具は MVP の後の Epic にする（法務の L13 の後）。

- **移行の文書**：本家との違い（各領域で「移行の文書に書く」と決めたもの）を 1 か所に集め、本家の機能 → 本システムの対応・代わりの案・違いの理由の表にする。正本は bulk-and-import.md の 15.4 節に置き、各領域の文書はそこへの行を足す。
- **本家の ID を外部 ID にする**：移す各オブジェクトに、`legacy_id`（`text`、18、`external_id`・`unique`）を足す。本家の 15 文字の ID は大文字と小文字を区別し、18 文字の形は区別しなくても一意になるとされる（未検証。E9 の着手の時に公開の資料で確かめる）ので、18 文字の形だけを受け、15 文字の値は `INVALID_LEGACY_ID` で断る。参照の列は、親の外部 ID（`account.legacy_id` の形。[bulk-and-import.md](../architecture/bulk-and-import.md) の 4.2 節）で結ぶ。
- **取り込みの順**：利用者 → 取引先（親の取引先は 2 回目の更新で結ぶ）→ 取引先責任者 → リード → 商談 → 商談の取引先責任者の役割 → 活動 → カスタムオブジェクト（主従の親から）。所有者は、利用者の `legacy_id` で引く。各段は upsert なので、途中で止まってもやり直せる。
- **監査の項目**：作成日・更新日・作成者・更新者は、移行の時だけ書ける。新しいシステムの権限 `set_audit_fields_on_import`（既定はどの権限セットにもない）を持つ人の一括のジョブだけが、`created_at`・`created_by` などを列で指定できる。使ったジョブは監査に残す。
- **持ってこないもの**：項目の変更の履歴、設定の変更の履歴、ログインの履歴（新しい組織の監査の鎖の前に、確かめられない記録を混ぜない）、本家のメタデータ・コード。履歴が要る組織には、本家から書き出したファイルを組織の側で保管するよう案内する。
- **CSV の対応の型**：本家のデータの書き出しの見出しから本システムの項目への、標準オブジェクトごとの対応の型を、ウィザードの既定の対応の型（[bulk-and-import.md](../architecture/bulk-and-import.md) の 5.1 節）に足す。見出しの名前は本家の公開の資料から作り、本家のファイルをテストに使わない。
- **変換の道具（後の Epic）**：利用者が上げた本家のメタデータの書き出しを読み、オブジェクト・項目・選択リスト・レコードタイプ・ページレイアウトを本システムのメタデータの形式（[ADR-0039](0039-metadata-package-format.md)）の下書きに変換し、変換できないもの（Apex、数式の関数の違い、Visualforce）を報告する。デプロイは通常の検証と適用を通す。本家のメタデータの形式を読む道具の扱いは法務の確認待ち（L13）。
- 2 を採らない理由：本家の組織の資格を預かることになり、本家の API の割り当てと規約の制約を受ける。MVP の作業が大きい。
- 3 を採らない理由：参照と所有者を一般の CSV の手順でつなぐのは、管理者にとって誤りやすい。各領域で決めた違いが散らばったままになる。

## Consequences

- 移行の文書の表は、本家との違いを決めるたびに 1 行足す運用が要る。足し忘れを、ADR の雛形の Consequences で問う。
- `legacy_id` は移行の後も残る。消すかは組織が決める（項目の削除は 15 日で戻せる）。
- 監査の項目を書ける権限は、記録を偽る手段にもなる。移行の期間だけ付け、外したことを監査で確かめるよう案内する。
- メタデータの作り直しは、変換の道具ができるまで管理者の手作業になる。intent の K8（導入の速さ）は、データの取り込みだけで測る。

## Confirmation

- 結合テスト：生成した本家の形の CSV（公開の資料の見出しから作る）を、決まった順で取り込むと、参照・所有者・監査の項目が元の関係と一致する。途中の段で止めて再開しても、レコードが重ならない。
- 表駆動テスト：`legacy_id` の検査（18 文字、15 文字、空、重複）。`set_audit_fields_on_import` のない人のジョブが、監査の項目の列を `INSUFFICIENT_ACCESS` で断る。
- 移行の文書の表の各行が、根拠の ADR か領域の文書の節を指していることを、文書の lint で確かめる。
