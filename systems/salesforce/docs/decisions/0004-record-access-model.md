# ADR-0004: 共有を事前計算し、所有者とロール階層は閉包の表と結ぶ。設定の変更の再計算は影の世代で切り替える

## Context

利用者がレコードを見て変えられるかは、次の組み合わせで決まる（[intent.md](../intent.md) の MVP の範囲）。

- オブジェクトの権限（参照・作成・編集・削除、「すべて参照」「すべて変更」）と FLS。プロファイルと権限セットで与える。
- レコードの単位の共有：組織の共有設定（OWD）、ロール階層、共有ルール（所有者の条件・レコードの条件）、手動の共有、チーム、親に連動する共有、暗黙の共有（子の商談が見えれば親の取引先も見える、など）。

画面・API・レポート・リストビュー・検索の全てで、この判定を毎回かける。大きな組織では、ロール階層が数千、共有ルールが数百、レコードが数千万ある。

本家は、判定を読む時に全て計算すると、ページの表示の目安の 300ms に収まらないとして、**設定が変わった時にアクセスを計算して保存する**。オブジェクトごとの共有の表（レコード、利用者かグループ、アクセスの水準、理由（row cause）の行）と、グループの所属の表（ロール、ロールと部下、公開グループ、キューの所属を展開したもの）を持ち、問い合わせでレコードの表・共有の表・グループの所属の表を結ぶ。ロールの移動のような一見小さな操作が、大量の共有の行とグループの所属の書き換えになる（[Record-Level Access: Under the Hood](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_record_access_under_the_hood.pdf)、Winter '27 版、2026-09-28 に確認）。本家は、大量の変更のために共有の計算を後回しにする機能も持つ（[Best Practices for Deployments with Large Data Volumes](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_large_data_volumes_bp.pdf)、2026-09-28 に確認）。

## Options

1. **全て事前計算する。** 所有者を含む全ての理由を、レコードごとの共有の行にする（本家に近い）
2. **全て問い合わせの時に評価する。** ロール階層・共有ルールの条件を、問い合わせのたびに SQL の条件にする
3. **事前計算を基本にし、所有者に由来するものだけ問い合わせの時に結ぶ。** グループの閉包（利用者 → 属する全てのグループ）とロール階層の閉包は事前計算する。レコードごとの共有の行は、所有者に由来しない理由（手動、チーム、レコードの条件の共有ルール、暗黙の共有）だけに持つ。所有者と、所有者の条件の共有ルールは、`records.owner_id` と閉包の表を問い合わせの時に結ぶ

## Decision

3 を採用する。

### 判定の順序

判定は次の順で行う。上から順に評価し、最初に決まったものを採る。詳しい決定表は sharing-and-record-access の領域の spec で `DT-*` として書く。

1. オブジェクトの権限がない → 拒否。
2. 「すべて参照」「すべて変更」がある → 許可（その水準で）。
3. OWD が「公開・参照・更新」→ 許可。「公開・参照のみ」→ 参照を許可し、編集は 4 以降で決める。
4. レコードの単位の共有 → 次のどれかで許可。複数あれば最も強い水準を採る（本家も同じ。[Record-Level Access: Under the Hood](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_record_access_under_the_hood.pdf)）。
5. どれにも当たらない → 拒否。
6. 許可したレコードでも、FLS で読めない項目は返さない。

### 表

- **`group_members_closure`**：利用者 → 利用者が属する全てのグループ（ロールのグループ、公開グループ、キュー。入れ子を展開したもの）。
- **`role_subordinates_closure`**：利用者 → その利用者のロールの下にいる全ての利用者。ロール階層での「上司は部下のレコードを見る」に使う。
  > 2026-09-28 の注記：`group_members_closure` と `role_subordinates_closure` を 1 つの閉包の表にまとめた。利用者本人とキューもグループにし、上司は部下の `user` のグループに `via_hierarchy = true` で属する（[ADR-0014](0014-owd-roles-groups-and-closure.md)）。閉包は世代の番号を持つ（[ADR-0016](0016-recalculation-rule-versions-and-skew.md)）。暗黙の親は `record_shares` ではなく `implicit_parent_grants` に子ごとに持つ（[ADR-0015](0015-sharing-reasons-and-where-they-live.md)）。
- **`owner_rule_grants`**：所有者の条件の共有ルールを、「所有者のグループ → 共有先のグループ、水準」として持つ。レコードごとに展開しない。
- **`record_shares`**：`(org_id, object_id, record_id, grantee_group_id, access_level, row_cause, generation)`。所有者に由来しない理由（手動、チーム、レコードの条件の共有ルール、暗黙の共有）だけを持つ。
- 利用者も「本人だけのグループ」を持ち、手動の共有の相手が利用者でも、グループとして同じ形で扱う。

### 問い合わせの時の条件

非公開の OWD のオブジェクトでは、コンパイラ（[ADR-0003](0003-metadata-driven-runtime.md)）が次のどれかを満たす条件を足す。

- `owner_id` が本人。
- `owner_id` が `role_subordinates_closure` で本人の部下。
- `owner_id` が属するグループから、本人が属するグループへの `owner_rule_grants` がある。
- `record_shares` に、本人が属するグループへの、現在の世代の行がある。

主従の従のオブジェクトと活動は、親のレコードの判定に従う（共有の行を持たない）。本家も、主従の従と活動は自分の共有の表を持たない（[Record-Level Access: Under the Hood](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_record_access_under_the_hood.pdf)）。

### 再計算

- **レコードの保存**：同じトランザクションで直す。所有者の変更は行を書き換えずに済む（`owner_id` を結ぶため）。レコードの条件の共有ルールは、そのレコードについてだけ評価し直して、`record_shares` を足し引きする。暗黙の共有は、親子の関係の変更で足し引きする。本家に倣い、所有者の変更では手動の共有を消す。
- **グループの所属・ロールの変更**：1 人の利用者の所属の変更は、閉包の表を同じトランザクションで直す（影響は利用者と、そのロールの上下の数に比例し、レコードの数に依らない）。ロールの木の移動のような大きな変更は、非同期のジョブにする。
- **設定の変更（OWD、共有ルールの追加・変更・削除）**：非同期のジョブで、**影の世代**を作る。
  - オブジェクトごとに `active_generation` を持つ。ジョブは新しい世代の `record_shares` を、レコードの ID の範囲ごとに作る。
  - 全て作り終えたら、1 つのトランザクションで `active_generation` と設定を同時に切り替える。古い世代の行は後で消す。
  - 再計算の間は、古い設定と古い世代で判定し続ける。新旧が混ざった判定をしない（intent.md の「守るべき振る舞い」）。
  - ジョブは途中で止まっても、同じ範囲をやり直せる（冪等）。同じオブジェクトの再計算は、組織の中で 1 本ずつにする。
  - 組織ごとの一時的な保存の量が増える（その世代の行が 2 倍になる）ことを受け入れる。
  > 2026-09-28 の注記：オブジェクトごとの `active_generation` による影の世代は採らなかった。OWD・`grant_via_hierarchy`・所有者の条件の共有ルールの変更は、メタデータの版を上げて問い合わせの条件を切り替えるだけにし、行を書き直さない（[ADR-0014](0014-owd-roles-groups-and-closure.md)）。影で作るのは、レコードの条件の共有ルールの版（`rule_id`）の行と、閉包の新しい世代だけにした（[ADR-0016](0016-recalculation-rule-versions-and-skew.md)）。「古い構成か新しい構成のどちらか一方で判定する」性質は変わらない。
- **参照の評価器**：設定・所属・レコードから、利用者のアクセスを毎回計算し直す TypeScript の純粋な関数を持つ。テストのオラクルにし、本番では標本のレコードで事前計算の結果と照合する（K3）。

### 選ばなかった理由

- **1（全て事前計算）**：所有者の変更と、所有者の条件の共有ルールの変更が、レコードの数に比例した共有の行の書き換えになる。営業の担当替え（所有者の一括の変更）はよくある操作で、これが重いのは困る。
- **2（全て問い合わせの時）**：ロール階層・入れ子のグループ・レコードの条件の共有ルールを毎回 SQL で評価すると、条件が大きくなり、リストビューとレポートが NFR-001 に収まらない。レコードの条件の共有ルールは、ルールの数だけ OR が増える。

## Consequences

- 良くなること：
  - 担当替えとロールの変更が、レコードの数に比例した書き換えにならない。
  - 設定の変更の途中でも、判定は常にどちらか一方の世代で一貫する。
  - 参照の評価器があるので、事前計算の正しさを機械的に確かめられる。
- 引き受けるコスト：
  - 問い合わせの条件が、本家より 1〜2 個多い結合になる。所有者のグループと `owner_rule_grants` の結合の速さを、E4 の PoC で測る。
  - 影の世代のために、再計算の間は共有の行が一時的に 2 倍になる。
  - 閉包の表は、ロール階層が深く、部下が多いほど大きくなる（利用者の数 × 平均の深さ）。S1 の最大の組織（5,000 人）では小さいが、S3 の 10 万人の組織で測る。
  - 1 人の所有者・1 つの親に多くのレコードが集まるスキューで、暗黙の共有の更新とロックが重くなる。閾値と警告を sharing-and-record-access の領域で決める。

## Confirmation

- 決定表：判定の順序を `DT-*` として spec に書き、表駆動テストを spec から直接読み込んで回す。
- 性質ベーステスト：任意の設定（OWD、ロール階層、グループ、共有ルール）、レコード、操作（保存、所有者の変更、所属の変更、ルールの変更、再計算）の列の後で、事前計算の表による判定が、参照の評価器の判定と全ての（利用者、レコード）で一致する。
- 性質ベーステスト：再計算の途中のどの時点で判定しても、結果は古い世代か新しい世代のどちらか一方の判定と一致する。
- 結合テスト：画面・REST API・一括の API・レポート・リストビュー・検索・変更のイベントの購読の全ての経路で、見えないレコードが返らない（経路ごとの否定側のテスト）。
- 本番：標本のレコードでの照合の食い違いを数え、1 件でもあれば警告にする。
- 性能テスト（E12）：100 万件・1,000 人の組織で、OWD の変更の再計算が 15 分以内（NFR-005）。
  > 2026-09-28 の注記：OWD の変更は述語の切り替えなので、再計算がない（上の注記）。NFR-005 の目標を「OWD の変更は版の切り替え（p95 5 秒）、レコードの条件の共有ルールの追加・変更の再計算は 100 万件・1,000 人の組織で 15 分以内」に改めた（[architecture/README.md](../architecture/README.md) の 3 節）。この性能テストも、ルールの追加で測る。
