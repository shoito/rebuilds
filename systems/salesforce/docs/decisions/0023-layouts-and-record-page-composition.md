# ADR-0023: レイアウトを部品にコンパイルし、レコードのページを 1 回の要求で組み立てる。レイアウトは狭めるだけで、画面の保存にだけ効く

詳細は [ui-layouts-and-list-views.md](../architecture/ui-layouts-and-list-views.md) の 3 節と 4 節。

## Context

レコードの詳細の画面は、レイアウト（区画・項目・関連リスト）、レコードの値、関連リストの最初のページ、使える操作を必要とする。NFR-001 は、これを返す API の p95 を 300ms とした。

- 画面が、記述・レコード・関連リストごとに別々の API を呼ぶと、往復が増え、NFR-001 に収まらない。
- レイアウトは組織・プロファイル・レコードタイプごとに違い、メタデータの版で変わる（[ADR-0003](0003-metadata-driven-runtime.md)、[ADR-0007](0007-segmented-metadata-snapshots.md) の `layouts:<object_id>` の部品）。
- レイアウトの「読むだけ」「必須」を、アクセス制御と取り違えると、API から書き換えられる穴になる。

本家（2026-09-28 に確認）：画面の API は、レイアウトの種類（`Full`・`Compact`）とモード（作成・編集・表示）でレイアウトと値を返し、FLS・共有・権限を確かめる（[User Interface API Developer Guide](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/api_ui.pdf)、Winter '27 版）。250 項目を超えるレイアウトは、自動で作る問い合わせが大きくなりすぎて失敗しうる（[Developer Limits and Allocations Quick Reference](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_app_limits_cheatsheet.pdf)）。レイアウトの必須が API の保存に効くかは、公開の資料に書かれていない（未検証。E4 の `layout-access-dt-ui` で試用の組織で確かめる）。

## Options

組み立て：

1. **サーバーの 1 つの API（レコードのページ）で、レイアウト・値・関連リストの最初のページ・操作をまとめて返す。関連リストは予算を超えたら遅らせる**
2. 画面が、記述・レコード・関連リストの API を並行で呼ぶ
3. サーバーで HTML を描いて返す

レイアウトの効き方：

- a. **レイアウトは狭めるだけ。`readonly`・`required` は、要求に `layout_id` を付けた画面の保存にだけ効く**
- b. レイアウトの `readonly`・`required` を、全ての保存に効かせる
- c. レイアウトは表示だけに使い、保存では何も確かめない

## Decision

1 と a を採用する。

- レイアウトは `md_layouts` に持ち、プロファイル × レコードタイプで割り当て、`layouts:<object_id>` の部品にコンパイルする。
- `GET /api/v1/ui/records/{id}` は、版を固定し、レイアウトを決め、読める項目だけを読み（FLS で落として返す画面用の要求）、関連リストの最初のページを並行で読み、操作を決めて返す。
- 予算：最初に読む関連リスト 6、1 回の要求の問い合わせ 10、1 レイアウトの項目 200・関連リスト 20。予算を超えた関連リストは `deferred` で返す。
- 項目の見え方・書け方は `DT-UI-001` で決める。FLS で読めない項目はレイアウトにあっても出さない。
- 画面の保存は `layout_id` を付け、保存の手順 2 で `readonly` の変更と `required` の空を断る。`layout_id` のない保存には効かない。
- レコードタイプで使えない選択リストの値は、画面・API とも断る。
- 2 は往復が増える。記述と値の版がずれると、消えた項目を画面が描きうる。3 は、インライン編集と部分の更新が重く、API と画面で判定が 2 つになる。
- b は、同じオブジェクトをレイアウトの違うプロファイルの連携の利用者が書く時に、どのレイアウトで確かめるかが決まらない。c は、画面で読むだけにした項目を、同じ画面の保存の要求で書き換えられる。

## Consequences

- 良くなること：
  - レコードの画面が 1 往復で描ける。
  - 1 つの要求が 1 つの版で組み立てられ、記述と値がずれない。
  - レイアウトがアクセス制御を広げない。
- 引き受けるコスト：
  - どの経路でも守る規則は、レイアウトではなく項目の `required` や入力規則で書く必要がある。管理者への案内が要る。
  - レコードのページの API は、画面の都合の形を持つ。版は `/api/v1` の中で足す変更だけにする。
  - 関連リストの件数を出さない。

## Confirmation

- 決定表：`DT-UI-001` を表駆動テストにする。
- 性質ベーステスト：任意の権限の形とレイアウトで、応答に FLS で読めない項目の値が出ない。
- 上限の試験：レイアウトの項目 200・関連リスト 20、問い合わせ 10。
- 性能テスト：関連リスト 6、項目 100 のレイアウトで p95 300ms。
