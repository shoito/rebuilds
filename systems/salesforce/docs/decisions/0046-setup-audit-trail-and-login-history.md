# ADR-0046: 監査のイベントは変更と同じトランザクションで追記だけの表に書き、組織ごとのハッシュの鎖と毎日の Object Lock の錨で改ざんを見つける。画面は 180 日、ログインの履歴は 180 日

詳細は [audit-and-field-history.md](../architecture/audit-and-field-history.md) の 3 節と 4 節。

## Context

intent は、設定の変更、権限の変更、データの一括の削除が監査のログに残ることを守るべき振る舞いにし、法務の L5 で監査のログの保持の期間と本人の請求の関係を問う（E11 の spec を止めている）。[ADR-0003](0003-metadata-driven-runtime.md) は、メタデータの版ごとの差分（`md_changes`）を残すとした。ただし、権限セットの割り当て・利用者の管理・認証と連携の設定・データの大きな操作は、メタデータの版を上げないか、版の外の操作である。

各領域は、監査に残す操作を依頼している（承認のロックを越えた更新、重複の規則の `bypass`、エクスポート、完全な削除、Webhook の宛先の変更、デプロイ、Sandbox）。

監査のログは、DB の特権を持つ人（運用、侵入者）にも書き換えられないことが求められる。

本家（[Object Reference](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/object_reference.pdf)、Winter '27 版、2026-09-28 に確認）：Setup の変更を少なくとも直近 180 日表す（`SetupAuditTrail`）。組織の全ての成功・失敗のログインの試みを表す（`LoginHistory`）。ログインの履歴の保持は 6 か月と広く紹介されている（未検証）。

## Options

書き方：

1. **変更と同じトランザクションで書く（保存の経路からのものは `audit_pending` を経て 1 秒で移す）**
2. outbox から非同期に書く

改ざんの防止：

- a. **追記だけの権限、組織ごとのハッシュの鎖、毎日の鎖の先頭を別のアカウントの S3 の Object Lock に書く**
- b. 追記だけの権限だけ
- c. 監査を最初から S3 の Object Lock にだけ書く

## Decision

1 と a を採用する。

- 記録の分類は `metadata`・`permission`・`user`・`sharing`・`auth`・`integration`・`deploy`・`data_bulk`・`data_override`・`org`・`support`。`details` は種類ごとの許可リストのスキーマで作り、秘密とレコードの値を入れない。メタデータの差分は版の番号で指す。
- 組織の中で欠番のない `seq` と `hash = SHA-256(prev_hash || 正規化した行)` を持つ。設定の変更は `audit_heads` の行で採番し、保存の経路から書くもの（`data_override` など）は同じトランザクションで `audit_pending` に入れ、Worker が 1 秒ごとに採番して移す。
- アプリのロールには `INSERT`・`SELECT` だけを許す。毎日、全ての組織の鎖の先頭を、監査のアカウントの S3（Object Lock、コンプライアンスのモード）に書く。組織の管理者も本システムも、鎖を計算し直して錨と比べられる。
- 保持は、Aurora（画面と API）で 180 日、外部の保管（組織ごとの鍵で暗号化した JSON Lines、Object Lock）で 1 年。どちらも法務の L5 の結論で決める。組織の削除では、外部の保管の分を鍵の破棄で読めなくする。
- ログインの履歴は、ログインの画面の全ての試みと OAuth のトークンの発行を、outbox から別の表に書く（ログインを止めない）。利用者の決まらない失敗は、打った文字列を残さず HMAC だけを残す。保持は 180 日。
- 読みは `view_audit_trail`。書き出しも記録する。
- 2 は、変更が確定して監査が書けない時間ができ、落ちると監査が漏れる。
- b は、DB の特権を持つ人の書き換えに気づけない。
- c は、画面の検索・絞り込みが遅く、同じトランザクションで書けない。

## Consequences

- 良くなること：
  - 確定した管理の操作は必ず記録され、巻き戻った操作は記録されない。
  - 行の書き換え・消去を、錨との比べで見つけられる。
  - ログインの試みの調査ができ、ログインの経路を止めない。
- 引き受けるコスト：
  - 監査の書き込みの失敗で、管理の操作も失敗する。
  - 組織の 1 行での採番が、設定の変更の多い組織で待ちになりうる。
  - Object Lock の保管は期限まで消せない。組織の削除は鍵の破棄に頼る（法務の L5・L7 で確認）。

## Confirmation

- 決定表：`DT-AUD-001`（操作 → 記録の分類）を表駆動テストにする。
- 性質ベーステスト：任意の管理の操作の列（巻き戻りを含む）で、確定した操作ごとにちょうど 1 件の記録があり、`seq` に欠番がなく、鎖が一致する。
- 網羅のテスト：全ての管理の API が記録を書くことを、API の一覧から機械的に確かめる。
- 結合テスト：保守のロールで行を書き換えると、鎖の確かめが食い違いを出す。
- 否定側のテスト：`details` に秘密がない。ログインの履歴に打った文字列がない。
