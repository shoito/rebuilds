# ADR-0042: 割り当ては 24 時間の移動の窓で数えて有料の本番だけ 110% まで通し、Worker は組織の仮想時刻で公平に回し、上限の情報は見出しと /limits で返す

詳細は [governor-limits.md](../architecture/governor-limits.md) の 7〜9 節。

## Context

[ADR-0005](0005-tenancy-and-governor-limits.md) は、組織ごとの割り当て（API、長い要求の同時実行、一括、Worker の順番、DB の時間、ストレージ）の方針を置き、値と仕組みを governor-limits の領域で決めるとした。[ADR-0020](0020-rest-api-shape-and-versioning.md) は `<Brand>-Limit-Info: api-usage=…/…; long-running=…/…` の形を決め、トランザクションの使用量の返し方をこの領域に任せた。

本家（[Developer Limits and Allocations Quick Reference](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_app_limits_cheatsheet.pdf)、2026-09-28 に確認）：

- Enterprise の API は 24 時間で 100,000＋ライセンス × 1,000。組織の全体で数える。
- 有料で有効な組織は、急な増加に備えて一定の量だけ超えて動き、超えられる量に上限がある。試用・Developer・Sandbox には効かない。量は公開されていない（未検証）。
- 使用量を `Sforce-Limit-Info` と `/limits` で返し、割合を超えたらメールで知らせられる。
- 長い要求（20 秒以上）の同時実行は 25。

Worker は、一括の取り込み、レポート、共有の再計算、フローの非同期の処理を、全ての組織で共有する。SQS は組織ごとの公平な取り出しを持たない。

## Options

割り当ての数え方：

1. **24 時間の移動の窓（1 分の桶）。有料の本番は 110% まで通し、他は 100% で止める**
2. 暦の日で数えて 0 時に戻す
3. トークンバケット（秒ごとの補充）

Worker の順番：

- a. **仕事の種類ごとに、組織の仮想時刻（費用 ÷ 重み）が最も小さい組織から取る。組織ごとの同時の上限を置く**
- b. 組織ごとの SQS のキューを順番に回す
- c. 先着順（1 つの SQS）

トランザクションの使用量：

- x. **求めた時だけ `<Brand>-Tx-Usage` の見出しで返す**
- y. 全ての応答に返す

## Decision

1、a、x を採用する。

- 割り当ては Valkey の 1 分の桶（1,440）で数え、Aurora の `org_usage_minutes` にも書く。Valkey を失ったら、検査を通す側に倒し（fail open）、DB で後から数える。
- 有料の本番の組織は 110% まで通し、そこで 429 `REQUEST_LIMIT_EXCEEDED` と `Retry-After`。試用・Developer・Sandbox は 100%。80%・100% で管理者に知らせる。
- 長い要求の同時実行は、組織ごとの実行中の要求の開始の時刻の集合で数え、20 秒を超えた要求が 25 以上の間は新しい同期の要求を 429 `CONCURRENT_LIMIT_EXCEEDED` で断る。
- Worker は `jobs` の表（Aurora、`FOR UPDATE SKIP LOCKED`）と `org_vtime` で、class ごとに仮想時刻の最も小さい組織の仕事を取る。仮想時刻は実際の DB の時間 ÷ 重みで進める。重みはライセンスの数で決め（上限 8）、DB の時間がクラスタの 20% を 5 分超えた組織は半分にする。SQS は到着の通知だけに使う。
- `<Brand>-Limit-Info` は ADR-0020 の形のまま。`<Brand>-Tx-Usage` は、要求の見出しで求めた時だけ返す。`/api/v1/limits` は割り当て・同時実行・容量を返し、割り当てに数えない。
- 2 は、0 時の前後に使用量が集中し、0 時に全ての組織の連携が一斉に再開する。
- 3 は、瞬間の速さを抑えるには良いが、本家の 24 時間の割り当ての考え方と、利用者が見る使用量の意味がずれる。瞬間の速さは長い要求の同時実行と WAF で抑える。
- b は、組織の数（S3 で 50 万）だけキューを持つことになる。仕事の大きさのばらつきも考えない。
- c は、1 つの組織の大きな一括の取り込みが、他の全ての組織を待たせる。
- y は、使わない利用者の応答の見出しを大きくする。

## Consequences

- 良くなること：
  - 割り当ての使用量が 0 時で跳ねず、利用者が見る値が本家の感覚に近い。
  - 急な増加で有料の組織の連携が止まりにくい。
  - 大きな仕事を持つ組織があっても、小さな組織の仕事が待たされ続けない。
- 引き受けるコスト：
  - Valkey の障害の間は、割り当てを守らない（fail open）。
  - `jobs` の表の取り出しが Aurora の負荷になる。S2 の前に測る。
  - 110% の超過の量は本家と違いうる（未検証）。

## Confirmation

- 結合テスト：100%・110% の境目、`Retry-After` の値、Valkey の停止での fail open と、DB からの数の作り直し。
- 結合テスト：20 秒を超える要求 25 本の後の 429 と、要求の終わりでの回復。
- 性質ベーステスト：任意の仕事の到着の列で、各組織の取り出しの割合が重みの比から一定の幅に収まる。
- 負荷試験（E12）：NFR-003（上限まで負荷をかけた組織があっても、他の組織の p95 の悪化が 10% 以内）。
- 契約テスト：見出しと `/limits` の形。
