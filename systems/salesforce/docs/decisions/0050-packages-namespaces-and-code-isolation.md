# ADR-0050: パッケージは名前空間の接頭辞と署名を持つメタデータの束にし、上限は組織と共有して名前空間ごとに計測する。コードの秘密は宛先の登録だけで渡す

詳細は [extensibility.md](../architecture/extensibility.md) の 8 節と 9 節。

## Context

intent は、パッケージ（配布、名前空間、版の管理、インストール先での上書き）を MVP の後の Epic にし、メタデータのデプロイ（E10）の上に作り、名前空間と上限の分け方が要るとした。[ADR-0039](0039-metadata-package-format.md) は、組織の間のデプロイの形（部品ごとの YAML と目録の zip、参照は API の名前）を決めた。[ADR-0006](0006-data-dictionary-and-field-lifecycle.md) は、カスタムの名前を `x_` の接頭辞にした。

決めること：

- 名前空間の書き方と、インストール先の部品との名前の衝突。
- 上限を、パッケージごとに別に持つか、組織と共有するか。
- パッケージの改ざんと、配布者のなりすましを防ぐ方法。
- パッケージのコードが秘密（API のキー）を要る時の渡し方。

本家は、名前空間の接頭辞と `__` の区切りを持つ管理パッケージを持つ。セキュリティのレビューを通った認定の管理パッケージは、1 トランザクションの上限の多くを名前空間ごとに別に持ち（例：問い合わせ 100 を名前空間ごとに）、全ての名前空間の合計は 1 つの名前空間の上限の 11 倍まで。CPU 時間のように全体で共有する上限もある。認定でないパッケージは組織の上限を分け合う（[Apex Developer Guide](https://resources.docs.salesforce.com/latest/latest/en-us/sfdc/pdf/salesforce_apex_developer_guide.pdf)、Winter '27 版の「Per-Transaction Certified Managed Package Limits」、2026-09-28 に確認）。

## Options

上限：

1. **組織と共有する。名前空間ごとの使用量を計測して見せる**
2. 名前空間ごとに別の上限を持つ

配布：

- a. **配布者の署名（Ed25519）を目録に付け、インストールの時に確かめる。公開の一覧（マーケットプレイス）は MVP の後**
- b. 署名を持たず、配布の URL の信頼だけにする

秘密：

- x. **コードは秘密を読めない。秘密は外向きの呼び出しの宛先（[ADR-0035](0035-webhooks-outbound-calls-and-ssrf-guard.md) の `outbound_endpoints`）に登録し、送信の時に本体が付ける**
- y. コードが秘密の値を読める API を持つ

## Decision

1、a、x を採用する。

- 名前空間は、配布者の組織が 1 つ登録する英小文字 2〜15 文字。全ての組織で一意にする。パッケージの部品の API の名前は `<ns>__<name>`（例：`acme__x_score`、`acme__sync_trigger`）。インストール先の部品は名前空間なしのままなので、衝突しない。
- パッケージは ADR-0039 の形に `package.yaml` の `namespace`・`version`（semver）・`signature` を足したもの。コード（トリガー）の部品は、TypeScript の元と、ビルドの結果（バイトコード）のハッシュを持つ。インストール先はバイトコードを自分でビルドし直してハッシュを比べ、合わなければ断る。
- 版の上げは、インストール先の組織への通常のデプロイ（[ADR-0040](0040-deploy-validation-and-rollback.md)）として当てる。インストール先の管理者は、パッケージのコードと、パッケージが「変えてはならない」と宣言した部品を変えられない。レイアウト・リストビュー・権限セットの割り当ては変えられる。
- 上限は組織の上限と共有する。1 つのトランザクションで、組織の設定とパッケージのコードが同じ上限を使う。`tx_limit_peak_ratio` と `<Brand>-Tx-Usage` に名前空間ごとの内訳を足す。
- パッケージのトリガーの実行の文脈は、既定の `user` か、インストールの時に管理者が承認した `system_with_sharing`（[ADR-0049](0049-triggers-in-dml-order-and-platform-api.md)）。パッケージが求める権限（オブジェクト、システムの権限、宛先）は目録に宣言し、インストールの画面で全て見せる。
- 配布者の鍵は配布者の組織で作り、公開鍵を本システムに登録する。秘密鍵は本システムに預けない。鍵の失効で、その鍵で署名した版の新しいインストールを止める。
- 2 は、パッケージを多く入れた組織が、共有の DB を他より多く使える。[ADR-0005](0005-tenancy-and-governor-limits.md) の「公平のための上限は全ての組織で同じ」に反する。
- b は、配布の経路の改ざんに気づけない。
- y は、秘密がコードのログ・例外・外向きの本文へ流れる経路を作る。

## Consequences

- 良くなること：
  - 名前空間で、パッケージとインストール先の部品が衝突しない。
  - 上限の公平が、パッケージがあっても保たれる。
  - 署名とビルドのし直しで、改ざんしたコードを入れない。
  - 秘密がコードの中に入らない。
- 引き受けるコスト：
  - パッケージの書き手は、インストール先の組織の設定と上限を分け合う前提で書く必要がある。
  - インストールの時にビルドし直すので、インストールが遅い。ビルドの道具の版をパッケージの目録に固定する。
  - 本家の認定の管理パッケージは上限を名前空間ごとに別に持つので、本家から移るパッケージは上限に当たりやすい。移行の文書に書く。

## Confirmation

- 決定表：`DT-PKG-001`（部品の種類 × 宣言 × 操作する人 → インストール先で変えられるか）を表駆動テストにする。
- 結合テスト：署名が合わない・ハッシュが合わない・失効した鍵のパッケージのインストールを断る。
- 性質ベーステスト：任意のパッケージとインストール先の部品の組で、名前の解決が衝突しない。
- 否定側のテスト：コードのホストの API から、宛先の秘密・Webhook の秘密・OAuth の秘密を読めない。
