# Runbook: インシデント対応

- Owner: Ops
- 対応するアラート: 全ての呼び出し（page）のアラート（[observability.md](../architecture/observability.md) の 7 節）。個別の場面は「CRM の基盤に固有の場面」の節
- 最終確認日: 2026-09-28

個別の手順（[deploy-and-rollback.md](deploy-and-rollback.md)、[disaster-recovery.md](disaster-recovery.md)）の上に立つ、共通の進め方と、この題材に固有の 4 つの場面（参照の評価器の食い違いによる共有の漏えい、騒がしい隣人、Sandbox のマスキングの事故、組織のデータの漏えい）。進め方の骨格は他の題材（[auth0 の incident-response.md](../../../auth0/docs/runbooks/incident-response.md)）と同じ。

## 症状

次のどれかのときに、インシデントを宣言する。迷ったら宣言し、後で重さを下げる。

- 呼び出しのアラートが鳴った
- 組織や社内から、障害・遅さ・データの漏えい（見えてはならないレコード・項目が見えた、他の会社のデータが見えた）の報告が来た
- `access_oracle_mismatch_total{direction="over"}`、影の実行の `over`、監査の鎖の食い違い、出力の走査の検出、マスキングの警告、GuardDuty の重大な検出

## 影響

### 重さ（severity）

| 重さ | 基準 | 例 | 最初の応答 | 告知 |
| --- | --- | --- | --- | --- |
| SEV1 | 全体で画面・API が使えない。**他の組織のデータが見えた**（NFR-009）。組織の全データの持ち出しの疑い。本番の個人データが組織の外（Sandbox の利用者を含む第三者）へ大量に出た | リージョンの障害、組織をまたぐ漏えい | 5 分以内 | 30 分以内に影響した組織へ。以後 30 分ごと |
| SEV2 | 一部の機能・組織が使えない。**組織の中の見えないデータの漏えい**（参照の評価器の `over`）。Sandbox に伏せていない個人データが入った。SLO の速い燃え方。騒がしい隣人で他の組織が遅い | 共有の判定の誤り、マスキングの事故、1 つのクラスタの飽和 | 15 分以内 | 1 時間以内に影響した組織へ（影響があれば） |
| SEV3 | 劣化しているが、回避できる | 検索の `degraded`、索引の遅れ、1 つの組織の自動化の失敗 | 営業時間内 | 必要なら |
| SEV4 | 組織への影響がない | 1 つの Worker の class の失敗の増加 | 営業時間内 | なし |

**アクセスの判定、組織の分離、Sandbox の個人データ、秘密に関わるものは、範囲が 1 件でも SEV2 以上にする。**

## 確認

1. どのアラート・報告から始まったかを記録する。
2. 影響の範囲を見る：全体か、特定のセル・クラスタ・組織・オブジェクト・経路（画面、REST、レポート、検索、イベント、一括）か。本番の組織か、Sandbox・試用か。
3. 直近の変更を見る：デプロイ、フラグの段、マイグレーション、組織の移動、組織のメタデータのデプロイ・共有のルールの変更、Terraform。
4. セキュリティへの影響を見る：参照の評価器の食い違い、影の実行、出力の走査、監査の鎖、CloudTrail（KMS、`admin_cross_org` の資格情報）、GuardDuty。

## 対処

### 役割

| 役割 | 担う人 | 責任 |
| --- | --- | --- |
| 指揮者（IC） | 最初に応答したオンコール。SEV1 では Ops の責任者に引き継いでよい | 重さ、方針、大きな判断（安全の設定、組織の読むだけの状態、リージョンの切り替え） |
| 作業者 | オンコールの Ops、呼ばれた Dev | 調査と復旧 |
| セキュリティの担当 | セキュリティの当番 | 漏えい・分離・個人データに関わる判断、証拠の保全、法務への連絡 |
| 連絡係 | IC が指名する（PM が望ましい） | 組織、社内、AWS への連絡 |
| 記録係 | IC が指名する | 時刻付きの記録 |

SEV1 では、指揮者は手を動かさない。

### 進め方

1. **宣言する。** インシデント用の場を、このシステムと別の道具に作る。
2. **被害を止めることを、原因の特定より優先する。** 順番：
   - 直近の変更のフラグを前の段に戻す
   - 直近のデプロイを戻す（[deploy-and-rollback.md](deploy-and-rollback.md)）
   - 安全の設定をかける（下の「共有の漏えい」）
   - 問題の組織・連携を絞る（下の「騒がしい隣人」）
   - 問題の Sandbox を止める（下の「Sandbox のマスキングの事故」）
3. **証拠を消さない。** 監査のログ、`access_oracle_samples`、`shadow_eval_results`、トレース、Sandbox の複製の記録は、調査の材料である。**レコードの値・個人データ・秘密を、チケット・チャット・この記録に写さない。** 組織の ID、オブジェクト、レコードの ID、件数だけを書く。
4. **告知する。** 何が起きているか、どの機能に影響するか、利用者に頼むこと（あれば）、次の更新はいつか。原因の推測は書かない。
5. **収束を確かめる。** SLO の指標が戻り、合成監視が成功し、15 分たってから解決とする。セキュリティの調査（範囲の特定、組織への報告、法務の判断）が残るときは、インシデントを閉じず、SEV を下げて続ける。

### CRM の基盤に固有の場面

#### 共有の漏えい（参照の評価器の食い違い）

アラート：`access_oracle_mismatch_total{direction="over"}` が 1 件（本番の標本の照合、[ADR-0017](../decisions/0017-reference-access-evaluator.md)）、影の実行の `new_correct` の `over`、組織からの「見えないはずのレコードが見えた」の報告。背景は [sharing-and-record-access.md](../architecture/sharing-and-record-access.md) の 9 節と 10 節。

1. SEV2 で宣言し、セキュリティの担当を呼ぶ。複数の組織に出ていれば SEV1 を考える。
2. **食い違いを確かめる。** `access_oracle_samples` の行（組織、利用者、レコード、判定した水準、評価器の水準、メタデータの版、閉包の世代）を見る。2 回の判定で食い違っている（競合ではない）ことは Worker が確かめ済み。
3. **範囲を決める。** 同じ組織・同じオブジェクトで、同じ理由の判定（所有者、閉包、ルールの行、暗黙の共有、FLS）で他にも起きうるかを見る。
   - 直近のデプロイ・フラグの段の変更と、食い違いの始まりの時刻を比べる。
   - 組織の直近の共有の変更（ルールの版の切り替え、閉包の世代、ロールの木の移動、保留の再開）を監査で見る。
   - `pivot_drift_repaired_total`、共有のジョブの状態を見る。
4. **1 時間以内に判断する**（sharing-and-record-access の 15 節の決定）。
   - 原因がデプロイ・フラグなら、戻す。
   - 原因が組織のデータ（閉包の行の漏れ、ルールの行の漏れ）なら、該当の組織のオブジェクトに**安全の設定**をかける：機能フラグで、そのオブジェクトの読みの結果を参照の評価器でも絞る（遅くなるが、多く見せない）。
   - 1 時間以内に原因が決まらなければ、安全の設定をかける。
5. **直す。** 食い違いを自動で直さない。原因の層（閉包、共有の行、条件の生成）を特定してから、閉包の世代・ルールの版を作り直すジョブ（照合を経て切り替える。[ADR-0016](../decisions/0016-recalculation-rule-versions-and-skew.md)）か、コードの修正で直す。
6. **漏れた範囲を調べる。** 食い違いの始まりから安全の設定まで、該当の利用者が該当のレコードを読んだか（アクセスのログの `request_id`・レコードの ID、レポート・検索・一括の問い合わせの実行の記録）を調べる。値は写さない。
7. **組織へ知らせる。** 漏れた可能性のある範囲（利用者、オブジェクト、件数、期間）を組織の管理者へ知らせる。個人データの漏えい等に当たるか、報告の主体、本人への通知は、法務が判断する（[security.md](../architecture/security.md) の 10 節・11 節の L1）。
8. 安全の設定は、原因を直し、照合の食い違いが 24 時間 0 になってから外す。

`direction="under"`（少なく見せた）は、SEV3（翌営業日）。利用者が見られるはずのものを見られない。同じ手順の 2・3・5 で調べる。

#### 騒がしい隣人

アラート：重い組織（アプリの DB の時間がクラスタの 20% を 5 分）と、他の組織の SLI の悪化（クラスタの p95 がいつもより 10% 以上悪い）の重なり、クラスタの飽和（writer の CPU 80%、AAS が vCPU の数を超える）。検知の仕組みは [observability.md](../architecture/observability.md) の 5 節と [ADR-0059](../decisions/0059-noisy-neighbor-detection-two-sources.md)。

1. SEV2 で宣言する（他の組織が遅いため）。
2. **組織と経路を特定する。** 「騒がしい隣人」のダッシュボードで、上位の組織の DB の時間の経路（`runtime`・`worker`・`reader`）、`org_aas_minutes`、重い文の形（`pg_stat_statements`）、その組織の要求の内訳（連携のクライアント、API、一括、レポート、フロー）を見る。
3. **自動の対処を確かめる。** その組織の Worker の重みが半分になっているか（`org_vtime`）。
4. **人の対処を、小さい順に行う**（全て組織の監査に `support` で残し、組織の管理者に知らせる）。
   1. 組織の長い要求の同時実行の上限を一時的に下げる（25 → 5）。
   2. 原因の連携のクライアント（OAuth のクライアント）を一時的に止める。
   3. 組織の API の割り当てを一時的に下げる（`org_allocations` の上書き。Ops だけ）。
   4. 組織の非同期の仕事（一括の取り込み、レポートの非同期、共有のジョブ）の `org_cap` を 1 にする、または止める。
   5. reader が詰まっているなら、レポートの同期を非同期に回す設定を組織にかける。
5. **重い文の形が特定の組織の設定（選択的でない問い合わせ、重いフロー、子の多い親の積み上げ集計）に依るなら**、組織の管理者に具体的な直し方を知らせる（`report-heavy-org`、`list-view-non-selective`、`data-skew-warning`）。
6. **「漏れ」（AAS がアプリの DB の時間より大きい）なら**、データ層を通らない経路（組織をまたぐ処理、保守、計測の漏れ）を疑い、Dev を呼ぶ。
7. クラスタ全体の飽和が組織の絞りで戻らない時は、reader を足す・writer を大きくする（数十分）。常に続くなら、組織の移動（`org-migration`）で専用のクラスタへ動かす（[ADR-0055](../decisions/0055-shard-placement-and-stage-criteria.md) の段階の基準）。
8. 他の組織の SLI が戻ってから 1 時間で、一時的な絞りを段階的に戻す。戻す時も組織の監査に残す。

#### Sandbox のマスキングの事故

アラート：マスキングの警告（複製の後の検査で、`personal`・`sensitive` の元の値の形が Sandbox の DB に見つかった）、分類の漏れた項目の検出、組織からの報告。背景は [sandboxes-and-deploy.md](../architecture/sandboxes-and-deploy.md) の 4.3 節と [ADR-0038](../decisions/0038-sandbox-types-and-masked-copy.md)。

1. SEV2 で宣言し、セキュリティの担当と法務を呼ぶ（法務の L3）。
2. **Sandbox を止める。** 該当の Sandbox の組織を `suspended` にし、ログインと API を止める。進行中の複製を止める。同じマスキングの設定・同じ版の複製の Worker で作った他の Sandbox も洗い出し、同じく止めるかを決める。
3. **証拠を保全する。** 複製の記録（`sandbox_requests`、テンプレート、マスキングの設定、複製の Worker の版）、Sandbox の監査・ログインの履歴（誰が入り、何を読み、書き出したか）を残す。値は写さない。
4. **原因を分ける。**
   - 組織の分類の漏れ（カスタム項目が `none` のまま）：組織の設定の問題。複製の前の警告が出ていたかを確かめる。
   - 複製の Worker の不具合（伏せる前の値を書いた、伏せの関数の誤り）：本システムの問題。複製を全体で止め（フラグ）、`security:sensitive` の修正を出す。
5. **Sandbox を消す。** 組織の管理者に知らせた後、Sandbox の組織を消す（組織の削除の順。[security.md](../architecture/security.md) の 7.1 節。猶予を置かない）。S3 の組織のファイルと検索の文書も消す。消し終えたことを確かめる。
6. **読まれた範囲を調べる。** Sandbox の利用者（開発者、外部の委託先を含みうる）が、該当の項目を画面・API・一括の問い合わせ・レポート・エクスポートで読んだかを、Sandbox の監査とアクセスのログで調べる。
7. **組織へ知らせる。** 本番の組織の管理者へ、入った項目、件数、期間、Sandbox の利用者と読まれた範囲を知らせる。報告の要否と主体は法務が判断する。
8. 分類の漏れが原因なら、組織の管理者と、分類を直してから作り直す。本システムの不具合が原因なら、修正と、同じ版で作った全ての Sandbox の検査が済むまで、データを含む複製を止める。

#### 組織のデータの漏えい（組織をまたぐ、または外への持ち出し）

アラート：他の組織のデータが見えたという報告、組織の分離の性質の検査・合成監視の失敗、出力の走査の検出、Webhook の宛先の不審な変更の後の大量の配信、一括の問い合わせ・エクスポートの急増、GuardDuty・CloudTrail の異常（`admin_cross_org` の資格情報の読み、KMS の異常な `Decrypt`）。

1. **組織をまたぐ漏えいの疑いは SEV1。** 組織の中の持ち出し（乗っ取られた管理者・連携）は SEV2。セキュリティの担当、Dev のテックリード、法務を呼ぶ。
2. **経路を特定する。** [security.md](../architecture/security.md) の 4 節の `LEAK-*` のどの行か。当たる行がなければ、新しい経路として扱う。
   - 組織をまたぐ：組織の解決（ホスト名・トークン）、RLS、キャッシュの鍵（メタデータの部品、レポートの結果）、カーソル、検索の組織の条件、S3 の組織の接頭辞と DEK、組織の移動・Sandbox の複製（`admin_cross_org`）。
   - 外への持ち出し：Webhook の宛先の変更（監査の `integration`）、OAuth のクライアントの作成、一括の問い合わせ・エクスポート（監査の `data_bulk`）、`view_all_data` の割り当ての変更（監査の `permission`）。
3. **被害を止める。**
   - 組織をまたぐ：直近の変更を戻す。キャッシュ（Valkey のメタデータの部品、レポートの結果のキャッシュ）を消す。原因の経路の API をフラグで止める。止められなければ、影響するセル・クラスタの対話の経路を止めることを IC が決める。
   - 持ち出し：組織の管理者と連絡をとり、乗っ取られた利用者を凍結し、セッションとトークンを失効させる（組織の管理者が行う。応答がなければ break-glass で運用者が行い、事後に知らせる。[ADR-0053](../decisions/0053-operator-access-and-data-lifecycle.md)）。不審な Webhook の宛先・外向きの呼び出しの宛先を `disabled` にする。不審な OAuth のクライアントを止める。
4. **証拠を保全する。** 監査の鎖を確かめる（`POST /api/v1/audit/verify`、錨との比べ）。CloudTrail、ALB のログ、アクセスのログ、Webhook の配信の記録（`webhook_deliveries`）、一括・エクスポートの記録を、調査のアカウントへ写す。
5. **範囲を決める。** どの組織の、どのデータが、どの組織・宛先・利用者へ、いつからいつまで出たか。件数と種類（個人データを含むか）。値は写さない。
6. **組織へ知らせる。** 影響した組織の管理者へ。組織をまたぐ場合は、データの持ち主の組織と、見えてしまった組織の両方。見えてしまった組織には、データの削除への協力を頼む。報告の要否（個人情報保護委員会、本人）と主体は法務が判断する（法務の L1）。
7. **直す。** 原因の修正は `security:sensitive`。`LEAK-*` の行と、否定側のテストを足す（[ADR-0051](../decisions/0051-leak-path-register-and-threat-model.md)）。組織をまたぐ漏えいは、外部の専門家のレビューを考える。

### 依存先の障害

| 依存先 | 見え方 | 対処 |
| --- | --- | --- |
| Aurora の主の writer | 書き込みが 503 | 自動の切り替えを待つ。10 分で戻らなければ [disaster-recovery.md](disaster-recovery.md) の B を考える |
| `events` のクラスタ | 変更のイベント・Webhook が遅れる。保存は続く | Relay は outbox に残して待つ（`events-cluster-degraded`） |
| `history` のクラスタ | 項目の変更の履歴の画面・API・レポートが 503。保存は続く | Relay は outbox に残して待つ（`history-cluster-degraded`） |
| prod-egress（`sender`・SQS・NAT） | Webhook・外向きの呼び出しが遅れる。保存は続く | 送信は SQS に残って再試行される。72 時間で宛先が `disabled` になる前に復旧させる（`webhook-endpoint-disabled`） |
| OpenSearch | 検索が `degraded` | 名前の前方一致で続く（`search-degraded`） |
| Valkey | メタデータの読みが遅い、割り当ては fail open | L3 から作る（`metadata-cache-degraded`）。fail open の間の割り当ての超過は後で数える |
| KMS | 組織のファイル・秘密を使う操作が 503 | DEK のキャッシュ（5 分）で続け、切れたら縮退（`kms-outage`） |
| SES | メールが遅れる | outbox に残して再試行 |
| 組織の IdP | その組織の SSO のログインが失敗 | `sso_bypass` の管理者の案内（`org-idp-outage`） |

## エスカレーション

- 組織をまたぐ漏えいの疑い → SEV1。セキュリティの担当、Dev のテックリード、法務、経営の責任者。
- 組織の中の漏えい・Sandbox の個人データ → SEV2。セキュリティの担当、法務。
- 1 時間で被害が止まらない → Ops の責任者。
- AWS の障害 → AWS のサポートに起票（重要度の最も高いもの）。
