# Runbook: 災害復旧（AZ の障害、リージョンの障害、論理的な破損、訓練）

- Owner: Ops
- 対応するアラート: AZ の障害（複数のサービスで 1 つの AZ のターゲットが不健全）、大阪からの合成監視の全失敗、`AuroraGlobalDBRPOLag` の超過、訓練（staging は四半期に 1 回、本番の switchover は年 1 回）
- 最終確認日: 2026-09-28

構成と目標は [infrastructure.md](../architecture/infrastructure.md) の 7 節、方針は [ADR-0057](../decisions/0057-disaster-recovery-osaka-warm-standby.md) にある。目標は NFR-007（AZ：RPO 0、RTO 5 分）と NFR-008（リージョン：RPO 1 分以内、RTO 1 時間以内）。

## 症状

| 場面 | 見え方 |
| --- | --- |
| A. AZ の障害 | 1 つの AZ のタスク・Aurora のインスタンス・Valkey のノード・OpenSearch のノードが不健全。AWS Health Dashboard に東京の 1 つの AZ のイベント |
| B. リージョンの障害 | 東京の対話の経路が応答しない。大阪からの合成監視が全て失敗。CloudFront の 502・504 が増える |
| C. 複製の遅れ | `AuroraGlobalDBRPOLag` が 10 秒を超え続ける（東京は正常） |
| D. 論理的な破損 | 誤ったマイグレーション・操作・Worker の不具合で、組織のレコード・メタデータ・共有の行が消えた・壊れた |
| E. 訓練 | staging の failover（四半期に 1 回）、本番の switchover（年 1 回） |

## 影響

- A：数十秒、書き込みが 503（`Retry-After`）になる。確定したデータは失わない。
- B：切り替えまで（目標 1 時間以内）、画面と API が使えない。切り替えの後、複製の遅れの分の書き込みを失う（下の表）。検索は作り直しが済むまで `degraded`（名前の前方一致）。
- C：この状態でリージョンの障害が起きると、失う範囲が広がる。
- D：影響した組織の業務が止まる・誤ったデータで動く。

| 失った書き込み（B） | 切り替えの後に起きること | 回復 |
| --- | --- | --- |
| レコードの作成・更新 | そのレコードが古い状態・存在しない | 組織へ知らせ、組織が入れ直す（下の「失った範囲の取り出し」） |
| レコードの削除 | 削除したレコードが戻る | 同上 |
| メタデータの変更（版） | 項目・フロー・権限の変更が古い版に戻る | 組織の管理者がやり直す。デプロイは再適用 |
| 共有・権限の変更（割り当て、ルール、手動の共有） | **外した権限・共有が有効に戻る** | 失った範囲の取り出しで最優先に組織へ知らせる |
| 利用者の無効化・凍結・パスワードの変更 | **無効にした利用者が有効に戻る** | 同上。該当の利用者を運用者が無効にし直す（組織の許可を得て） |
| 変更のイベント | 失った保存のイベントは元から存在しない（正本と一致） | なし |
| 一括のジョブの確定した塊 | 最後の塊の数個が消えうる | ジョブの結果と `records` を突き合わせ、組織が再実行 |

## 確認

1. AWS Health Dashboard と Grafana の AZ ごとの内訳で、1 つの AZ か、リージョン全体かを見分ける。
2. Aurora（主・`events`・`history`）のクラスタのイベントで、フェイルオーバーの有無と、現在の writer の AZ を確かめる。
3. リージョンの障害を疑うときは、大阪の合成監視と、別の回線からの到達性の両方で確かめる。
4. **`AuroraGlobalDBRPOLag` の直近の値と、東京が応答しなくなった時刻を記録する。** 失った範囲の目安になる（B で使う）。
5. KMS（東京）の到達性を確かめる。KMS だけの障害なら、リージョンの切り替えではなく、DEK のキャッシュでの縮退で対処する（`kms-outage`）。
6. D では、破損の始まりの時刻、原因の操作（デプロイ、マイグレーション、Worker のジョブ、運用者の操作）、影響した組織・表・ID の範囲を、監査・`md_versions`・ログで特定する。

## 対処

### A. AZ の障害

1. 自動の復旧を待つ（Aurora の writer の切り替え、ECS のタスクの作り直し、ALB の健全性の検査）。5 分で戻らなければ B の準備を始める。
2. 残る 2 AZ の ECS のタスクの数が、最大の負荷に足りているか見る。足りなければ最小の台数を上げる。
3. OpenSearch のノードの喪失で `degraded` が出ていれば、ドメインの復旧を待つ（検索は名前の前方一致で続く）。
4. Worker の仕事は、確定した塊・範囲から再開する（冪等）。止まったままの class があれば `worker-queue-backlog`。

### B. リージョンの障害（大阪への切り替え）

切り替えは IC が決める。条件：東京の Aurora の writer が 10 分応答せず、AWS の障害の告知か、大阪からの合成監視の失敗が続く（ADR-0057）。

1. **宣言する**（[incident-response.md](incident-response.md)、SEV1）。組織への告知：「東京の障害。大阪へ切り替える。切り替えの直前の数秒〜数十秒の変更が失われうる」。
2. **東京への書き込みを止める。** 東京の ECS の `runtime`・`worker`・`relay` の台数を 0 にする（届く限り）。CloudFront のオリジンを東京から外す（メンテナンスの応答）。
3. **Aurora の切り替え。** 主・`events`・`history` の Global Database で、大阪の副を managed failover（`failover-global-cluster --allow-data-loss`）で主にする。`control` の Global Database も同じ。書き込みの囲い（write fencing）の RDS のイベントを確かめる。
4. **大阪の ECS を広げる。** 各サービスの最小の台数を東京と同じにする。`runtime` が新しい writer に接続できることを確かめる。
5. **Valkey は空で始める。** メタデータの部品は L3 から作り直す（最初の数分は DB の読みが増える）。割り当ては fail open。
6. **OpenSearch を作り直す。** 大阪のドメインを広げ、`search_reindex_jobs` を全ての組織に積む（有料の本番・ライセンスの多い順）。済むまで検索は `degraded`。
7. **prod-egress**：大阪の `sender` を広げる。送信元の IP は大阪の分（公開済み）。
8. **CloudFront のオリジンを大阪へ。** 合成監視（ログイン → 保存 → 読み → 問い合わせ → 変更のイベント）を大阪で通す。
9. **失った範囲を記録する。** 手順「確認」の 4 の値を、インシデントの記録に書く。組織へ告知する（失った時間の幅と、見直してほしい操作：権限・共有・利用者の無効化を最優先）。
10. 目標：宣言から 8 まで 1 時間以内。

### 失った範囲の取り出し（B の後、東京が戻ってから）

1. Aurora が作る古い主のスナップショット（`rds:unplanned-global-failover-...`）を、別のクラスタとして東京に復元する（本番の書き込みの経路に入れない）。
2. 復元したクラスタの、切り替えの時刻の前後の `md_versions`、`audit_events`（同じトランザクションで書いているので、失った管理の操作の一覧になる）、`records.updated_at` を読み、大阪の主にない行を組織ごとに一覧にする。
3. 一覧を組織の管理者へ渡す（`support-data` の許可の範囲で、または組織の管理者が自分で見られる書き出しの形で）。**自動で書き戻さない**（後の書き込みとぶつかるため）。
4. 権限・共有・利用者の無効化の失われた操作は、組織の管理者の確認を得て、運用者がやり直すのを手伝う（組織の監査に `support` で残る）。
5. 取り出しが済んだら、復元したクラスタを消す（35 日の中で。個人データを残さない）。

### 東京へ戻す（fail back）

1. 東京が健全になり、Aurora が東京を副として作り直すのを待つ（数分〜数時間）。
2. 平日の夜間に、switchover（RPO 0）で東京へ戻す。手順は B の 2〜8 を逆に、書き込みの止めを数分にして行う。
3. OpenSearch は、東京のドメインの索引を作り直してから切り替える（東京のドメインが残っていれば、整合の検査で差を直す）。

### C. 複製の遅れ

1. 東京の writer の書き込みの量（一括の取り込み、共有のジョブ、組織の移動の初期の同期）を見る。遅れの原因が特定の組織の大きな仕事なら、Worker の class の `org_cap` を一時的に下げる（組織の監査に残す）。
2. 30 分続けば、大阪の副のインスタンスを大きくする。
3. 遅れの間は、計画した作業（組織の移動、大きなマイグレーション）を止める。

### D. 論理的な破損

1. **被害を止める。** 原因のデプロイ・フラグ・Worker のジョブを止める（[deploy-and-rollback.md](deploy-and-rollback.md)）。影響した組織の書き込みを止める必要があれば、`orgs.status` を `read_only` にする（組織へ告知）。
2. **戻す時点を決める。** 破損の始まりの直前の時刻。
3. **PITR で別のクラスタに戻す**（本番の書き込みの経路に入れない）。
4. **戻す範囲を選ぶ。**
   - 行の範囲（組織・表・ID の範囲）なら、戻したクラスタから読み、`admin_cross_org` のロールで本番へ書き戻す。写し（ピボット・照合の鍵・共有の行）は正本から作り直す（`derivePivotRows` と整合の検査）。
   - 組織の全体なら、組織の移動の道具（[ADR-0056](../decisions/0056-org-migration-by-row-filtered-logical-replication.md)）で、戻したクラスタから本番の別のクラスタへ写し、書き込みの止めの間に置き場所を切り替える。破損の後の正しい書き込みは失われるので、組織の管理者の同意を得る。
5. 監査の鎖：書き戻した組織の `audit_events` の鎖を確かめる（`POST /api/v1/audit/verify`）。戻したことを `support` の記録として監査に足す。
6. 検索・イベント：影響した組織の検索を作り直す。変更のイベントには隙間のイベント（`GAP_*`）を出す（[ADR-0033](../decisions/0033-change-event-log-and-replay.md)）。

### E. 訓練

| 訓練 | 頻度 | 中身 | 記録 |
| --- | --- | --- | --- |
| staging の failover | 四半期に 1 回 | B の全て（書き込みを流しながら） | RTO、失った書き込みの数と `AuroraGlobalDBRPOLag` の比べ、検索の作り直しの時間 |
| 本番の switchover | 年 1 回 | B を switchover（RPO 0）で。平日の夜間、組織へ 14 日前に告知 | 止めの時間、SLO への影響 |
| 論理的な破損の復旧 | 半年に 1 回（staging） | D の 4 の行の範囲と組織の全体 | 所要時間 |
| 組織の移動 | 四半期に 1 回（staging） | 最大の組織の写しの移動 | 止めの時間、照合の結果 |

## エスカレーション

- B の判断に迷ったら、Ops の責任者と Dev のテックリードを呼ぶ。15 分以内に決める。
- 失った範囲に、権限・共有・利用者の無効化の操作がある → セキュリティの担当を呼ぶ（見えてはならない人に見える状態が戻っている）。
- D で、他の組織の行が混ざった疑い → SEV1。[incident-response.md](incident-response.md) の「組織のデータの漏えい」。
- 個人データを含む失った範囲・破損の組織への知らせの要否 → 法務（L1・L7）。

## 事後

- RTO・RPO の実測を記録し、NFR-007・008 と比べる。外れたら Intent の Issue を起票する。
- 失った範囲の取り出しで、組織から問い合わせの多かった操作を、次の訓練の確かめの項目に足す。
- この手順で足りなかったことを、ここに反映する。
