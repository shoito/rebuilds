## この題材に固有の規則（開発リポジトリで守る）

### 本家の実装と名前

- **MTA（受信・送信の配送）、選別のパイプライン、メールの保存、スレッド化、検索の索引、同期のプロトコルの設計を自前で作る。** 本家のコード、本家の内部の形式、本家のクライアントの解析の結果を、核にも依存にも使わない。汎用の MTA（Postfix、Exim、Haraka、Stalwart など）、汎用の検索のエンジン（OpenSearch など）を核に据えない（[リポジトリ共通の ADR-0007](../../docs/decisions/0007-no-reuse-of-original-implementation.md)、ADR-0001）。
- **汎用の部品は ADR に書いた範囲で使ってよい。** SMTP の構文の層、MIME の解析、署名の検査型のマルウェアの検出、暗号、DNS の解決、機械学習の推論の実行系は、ADR-0001 の一覧のものだけを使う。
- **公開の標準は実装してよい。** SMTP、MIME、SPF、DKIM、DMARC、ARC、MTA-STS、TLS-RPT、IMAP、JMAP、RFC 8058 の一括の配信停止は、標準として実装する。互換は振る舞いであって、実装の再利用ではない。
- **本家の名前を識別子に使わない。** ドメイン（`<brand>.<domain>`、`mx.<brand>.<domain>`、`smtp.<brand>.<domain>`）、ヘッダー（`X-<Brand>-...`）、IMAP の特別な箱の名前（`[<Brand>]/All Mail`）、トークンの接頭辞（`<brand>_at_`）、DKIM のセレクター、ARC の `d=` は `<Brand>`・`<brand>` で書く（[リポジトリ共通の ADR-0006](../../docs/decisions/0006-brand-neutral-identifiers.md)）。

### 受け付けたメールを失わない

- **250 を返すのは、メッセージが耐久の置き場所に確定してからにする。** SMTP の DATA の終わりに 250 を返す前に、生のメッセージを S3 のスプールに置き、配送の待ち行列に載せる。どちらかが確定しなければ 451 を返し、送り手に送り直させる（ADR-0002）。投稿（送信の API・submission）も同じで、確定の前に「送った」と返さない。
- **受け付けた後に迷惑メールとして送り返さない。** 迷惑メール・フィッシングの判定は、受け付けた後は「迷惑メールの箱」か「隔離」にする。受け付けた後に DSN（不達の通知）を作ってよいのは、配送の不能（宛先の消失、転送の先の恒久のエラー）だけにする（ADR-0002）。
- **配送は冪等にする。** 待ち行列の読み直しで同じメッセージが 2 回来ても、受け手のメールボックスには 1 通だけ入る。配送の鍵は `(spool_id, recipient)` にする（ADR-0002）。
- **blob は参照が 0 になってから消す。** 本文の blob は、メールボックスの行・保留（ホールド）・送信の待ちの参照がすべて 0 になり、猶予（7 日）を過ぎてから消す。参照を減らす処理は、メールボックスの変更の確定の後に outbox から行う（ADR-0003）。

### プライバシーと通信の秘密

- **メールの中身を人が読まない。** 選別・索引・スレッド化は機械だけで行う。本システムの運用者が、利用者のメールの本文・件名・添付を見る経路を作らない。例外は、利用者が明示の同意で提出した報告（迷惑メールの報告のサンプル）と、法務が承認した手続き（法務の確認待ちの L1・L4）だけにする（ADR-0008）。
- **中身をログに出さない。** 本文、件名、添付の名前、メールアドレス（ローカル部）、検索の語は、ログ・メトリクス・トレースの属性に書かない。ID、ドメイン、数、理由のコードだけを書く。宛先と差出人のドメインも、集計の外のログには書かない。
- **重複排除で他人の受信を漏らさない。** blob を共有するのは、同じ配送（1 つの SMTP のトランザクション、1 回の送信）の受け手の間だけにする。中身のハッシュでメッセージをまたいで重複を排除しない（ADR-0003）。
- **選別の学習に中身をそのまま使わない。** 学習に使うのは、中身から作った特徴（ハッシュ、URL のドメイン、規則の当たり）と、同意のある報告のサンプルだけにする（ADR-0008）。

### メールボックスの状態と同期

- **メールボックスの状態は `mailstore` だけが書く。** ラベル、既読、スター、スレッド、削除の変更は、`mailstore` の API を通し、同じトランザクションで `modseq` を進めて変更の記録（change log）と outbox を書く。JMAP・IMAP・Web・フィルター・保持の処理が、DB を直接書き換えない（ADR-0006）。
- **ラベルが正である。** メッセージは複数のラベルを持つ。フォルダーは「ラベルを 1 つだけ持つ」見せ方で、別のモデルを作らない。迷惑メールとゴミ箱だけは他のラベルの表示から外す（ADR-0004）。
- **スレッドは自動で分けない。** スレッドは合わせる（マージ）ことはあるが、一度同じスレッドに入れたメッセージを後から自動で別のスレッドに分けない。合わせは change log に載せる（ADR-0005）。
- **IMAP の UID は戻さない。** ラベルごとの UID は、その箱に入った順に増やし、再利用しない。`UIDVALIDITY` を変えるのは、箱を作り直したときだけにする（ADR-0006）。

### テナントと分離

- **メールボックスの表は FORCE RLS にする。** Aurora の表は `tenant_id`・`account_id` と `FORCE ROW LEVEL SECURITY`、`SET LOCAL app.tenant_id`・`app.account_id` で絞る。RLS の外の表は ADR-0007 の一覧だけにし、メールの中身・件名・アドレスを持たせない。
- **受け手の文脈で書く。** 受信の配送は、受け手のアカウントの文脈を設定して書く。差出人の文脈で他人のメールボックスに書く経路を作らない（ADR-0007）。
- **検索は自分の索引だけを引く。** 索引のファイル・キャッシュの鍵・検索の計画は `account_id` を先頭に持つ。eDiscovery の横断の検索は、専用の役割と監査の記録を通す（ADR-0009、retention-and-ediscovery の領域）。

### 送信の評判

- **送信は必ず評判の関門を通す。** 利用者の送信は、アカウントごとの送信の上限、送信の内容の選別、IP プールの選択を通してから MTA に渡す。関門を飛ばす送信の経路（管理の画面からの一括の送信を含む）を作らない（outbound-smtp-and-reputation の領域）。
- **乗っ取りの疑いがあれば、先に止める。** 送信の異常を検知したアカウントは、送信を保留にしてから本人に確かめる。疑いの間、共有の IP プールから送らない。

### 運用と入力

- **受け取ったメールを信用しない。** MIME の解析、文字コードの変換、添付の検査、画像の変換は、上限（大きさ、入れ子の深さ、パートの数、時間、メモリー）を付けて動かす。添付の検査は、ネットワークを持たない隔離したタスクで動かす。利用者の中身を返すのは `<brand>usercontent.<domain>` からだけにする。
- **判定・形式の規則をフラグにしない。** スレッド化の規則、件名の正規化、blob の形式、modseq の進め方はコードのバージョンとして出す。選別のモデルと規則は、モデルのバージョンとして段階的に出し、`release.*` のフラグで経路ごとに切り替えない。
- **フラグの名前**：`release.*` は kebab-case（`release.scheduled-send`）、`ops.*` は snake_case（`ops.inbound_accept_enabled`）。`release.*` は 100% の後 30 日で消す。
- **テストに本物のメールを使わない。** 実在の人のメール、本家から書き出したメール、実在の迷惑メールの本文を、テスト・フィクスチャー・シードに書かない。メールは生成器で作る。選別の評価の集まりは、quality.md の 2.4 節の規則で作ったものだけを使う。

## このリポジトリでの規則

- ADR を追加・更新したら、`docs/decisions/README.md` の一覧を生成し直す。
- 領域の文書で ADR を起票するときは、[architecture/README.md](docs/architecture/README.md) の 7 節で領域に割り当てた番号の範囲の中で採番する。
- 本家の振る舞い・数値を書くときは、出典と確認日を付ける。確かめられないものは「未検証」と書く。本家と違う振る舞いを選んだら、[architecture/README.md](docs/architecture/README.md) の 1.4 節の「本家との意図した違い」に行を足す。
- RFC と本家の振る舞いが違うときは、両方を書き、本システムがどちらに寄せるかを明記する。
