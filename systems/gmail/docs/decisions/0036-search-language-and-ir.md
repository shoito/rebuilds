# ADR-0036: 検索の文法は、空白の AND、大文字の `OR` と `{...}`、`-` の否定、かっこ、引用の語句、`AROUND n` と `name:value` の演算子から成る。IR は正規化した論理式の木で、構文解析は `search-lang` の 1 つの実装だけが行う。日付はアカウントの時間帯で解き、`after:` は以上・`before:` は未満、比べるのは受け付けの時刻。大きさの単位は 1024 の累乗。文字列は 1,024 文字、IR の節は 256 まで。フィルターは IR のうち配送の時に決まる部分だけを使う

詳細は [search.md](../architecture/search.md) の 5 節。

## Context

- 検索の文法は、Web・アプリ・JMAP の拡張（`Email/query` の文字列）・フィルター・eDiscovery で使う（[ADR-0006](0006-sync-protocol-jmap-imap-and-modseq.md)、[ADR-0001](0001-platform-and-stack.md)）。経路ごとに解釈が違うと、フィルターの条件で検索した結果と、フィルターが配送の時に当てた結果がずれる。
- 本家の演算子は公開されている（[Search operators](https://support.google.com/mail/answer/7190)、2026-10-10 に確認）が、日付の時間帯、`after:` が当日を含むか、大きさの単位は確かめられなかった（**未検証**）。文法をどこまで寄せてよいかは法務の L9（**法務の確認待ち**）。
- 検索の文字列は外からの入力で、長い `OR` と入れ子で計算を爆発させうる。

## Options

1. **本家に近い文法を 1 つの構文解析器（ネイティブと WASM）で解き、正規化した IR を全経路で使う**
2. JMAP の `FilterCondition`（RFC 8621 の 4.4.1 節）だけを使い、文字列の文法を持たない
3. 経路ごとに構文解析する（Web は TypeScript、サーバーは Rust）

## Decision

1 を採用する。

- 文法：`or_expr := and_expr ("OR" and_expr)*`、`and_expr := unary (WS unary)*`、`unary := "-" unary | primary`、`primary` はかっこ・`{}`・`AROUND`・演算子・語。結合の強さは `-` ＞ AND ＞ `OR`。
- 演算子は [search.md](../architecture/search.md) の 5.1 節の表。知らない演算子は誤りにし、黙って語として探さない。
- IR は否定を内側へ押し、AND・OR を平らにし、状態に依らない節と状態の節に印を付ける。既定の除外（`SPAM`・`TRASH`）を足す。
- 日付はアカウントの時間帯（既定 `Asia/Tokyo`）の 0 時に解き、`after:` は以上、`before:` は未満、受け付けの時刻と比べる。相対の日付は実行の時に解く。大きさは `K`=1,024、`M`=1,048,576、論理の大きさと比べる。
- 文字列 1,024 文字、IR の節 256、`OR` の枝 64。
- フィルターは、状態の節（ラベル、旗）と相対の日付を含まない IR だけを受ける。
- JMAP の標準の `FilterCondition` も受け、同じ IR に変える。

### 他の案を選ばなかった理由

- **2**：利用者が慣れた文字の検索を出せない。フィルターの条件を画面で書けない。
- **3**：2 つの実装の解釈のずれが、フィルターと検索のずれになる。

## Consequences

- 良くなること：
  - 検索とフィルターと eDiscovery が同じ意味で動く。
  - 計算の爆発を、IR の大きさで先に止められる。
- 引き受けるコスト：
  - 本家の文法と細部が違う可能性がある（日付の時間帯など、**未検証**）。
  - 法務の L9 の結論で演算子の名前を変えるときは、IR を保って文法だけを変える。

## Confirmation

- 性質ベーステスト：PROP-SRCH-004（ネイティブと WASM の IR の一致）。
- 表駆動テスト：DT-SRCH-001（日付の境界、時間帯、単位、否定だけの式）。
- ファジング：文法の解析器を夜間 1 時間。
