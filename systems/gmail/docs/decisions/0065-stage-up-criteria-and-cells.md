# ADR-0065: 段階を上げる準備は、上限の 60% で始める。S2 は東京の中でシャード・台・/24 を増やし、directory の書き込みの多い表（サインインの記録など）を別のクラスタに分ける。S3 はアカウントをリージョンのセル（directory の写し、シャードの組、MX、プール、検索）に固定し、全体の宛先の解決だけを全体の層に置く

詳細は [infrastructure.md](../architecture/infrastructure.md) の 8 節。

## Context

- 規模は S1（100 万）、S2（1,000 万）、S3（1 億）と広げる。S3 は複数のリージョン（アカウントをリージョンに固定）とセルの構成とした（[architecture/README.md](../architecture/README.md) の 2 節）。段階を上げる基準はこの領域で決める。
- メールボックスはアカウントで閉じ、シャードはアカウントの単位で増やせる（[ADR-0007](0007-tenancy-accounts-orgs-and-rls.md)）。directory は 1 つで、アドレスの解決・サインイン・監査が集まる。
- 受信の MX は、宛先のアカウントの置き場所を知らない送り手から来る。セルに分けても、受け口と宛先の解決は全体で要る。
- BYOIP の範囲は東京で S1 に 5 つを使い切る（[ADR-0063](0063-network-byoip-ranges-and-egress.md)）。準備（範囲の取得、上限の引き上げ、Aurora のクラスタの作成）に時間がかかる。

## Options

1. **指標ごとの上限の 60% で準備を始め、S2 は東京の中で増やし、S3 でセルにする**
2. S1 からセルの構成にする
3. 指標を決めず、遅れや誤りが出てから増やす

## Decision

1 を採用する。

- 指標と準備の開始：メールボックスのシャードの書き込みの CPU（50% が 4 週）、シャードの保存（2.5 TB）、directory の書き込みの CPU（50%）、`mx-edge` の使用（50%）、送信のプールの量（60%）、`search-node` の NVMe（60%）、Global Database の遅延（p99 10 秒が 4 週）、アカウントの数（120 万）。2 つが基準を超えたら、PM と Ops が次の段階の計画を始める。
- S2：東京の中でシャード 80、`mx-edge` 60、`mta-out` 80、`search-node` 140。directory の書き込みの多い表（`signin_events`、`audit_events`、`domain_checks`）を別のクラスタへ。BYOIP の範囲の数の上限を引き上げる。
- S3：セルは、メールボックスに関わる directory の表、シャードの組、`mx-edge`、送信のプール、`search-node` を持つ。アカウントはセルに固定する。全体の層は、宛先の解決（`domains`・`address_index` → セル）とサインインの入口を持ち、全体の MX が受けてセルのスプールへ渡す。詳しい設計は S2 の後に別の ADR で決める。

### 他の案を選ばなかった理由

- **2**：S1 で全体の層とセルの両方を作る費用と、セルをまたぐ配送の設計が、MVP の前に要る。S1 の量は 1 つの組（8 シャード）で収まる。
- **3**：Aurora のクラスタ、IP の範囲、NVMe の台は、要ってからでは間に合わない（準備に 1 四半期）。

## Consequences

- 良くなること：
  - 準備の始め時が数で決まり、月次のレビューで確かめられる。
  - S2 までは構成を変えずに数で広げられる。
- 引き受けるコスト：
  - S3 のセルの設計（セルをまたぐ配送、全体の宛先の解決の可用性）が残る。
  - 指標の計測と月次のレビューを運用する。

## Confirmation

- 監視：8 節の指標をダッシュボードにし、準備の基準を超えたらチケット（[observability.md](../architecture/observability.md)）。
- レビュー：月次のキャパシティのレビューの記録に、指標と判断を残す（[capacity.md](../architecture/capacity.md) の 10 節）。
