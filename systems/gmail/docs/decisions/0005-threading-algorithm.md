# ADR-0005: スレッドはアカウントごとに作る。`References`・`In-Reply-To` の Message-ID のつながり（届いていない親を仮の節にした素集合）と、正規化した件名の一致で合わせる。参照のないメールは同じ差出人・同じ件名・7 日の中で合わせる。100 通で新しいスレッドにする。合わせはあるが、自動で分けない

## Context

本家はメールを会話（スレッド）にまとめる。公式の説明では、件名が変わると新しい会話に分かれ、100 通を超えても分かれる。自動の通知は、受け手・差出人・件名の共有か参照のヘッダーの一致と、1 週間の中の到着でまとめることがある（[Group emails into conversations](https://support.google.com/mail/answer/5900)、2026-10-10 に確認）。内部の詳しい規則は公開されていない（**未検証**）。

公開の手法には、IMAP の `THREAD=REFERENCES`（RFC 5256）の基になった、Message-ID のつながりで木を作る方法がある。ただし、次の問題がある。

- **到着の順序**：返信が親より先に届く。メーリングリストや遅れた配送で、順序は保証されない。
- **欠け**：`References` を持たないアプリ、途中を落とすアプリがある。日本の携帯の事業者のメールや古いアプリでは、`In-Reply-To` だけのものもある（**未検証**）。
- **乗っ取り**：攻撃者は既存の会話の Message-ID を `References` に入れ、フィッシングを本物の会話の中に見せられる。
- **件名の正規化**：`Re:`、`RE:`、`Fwd:`、`FW:`、日本語のアプリの `返信:`、`転送:`、`Re[2]:`、メーリングリストの `[list-name]`、全角と半角、MIME の encoded-word の違いがある。
- **安定性**：スレッドの ID は、JMAP の `threadId`・IMAP の OBJECTID の `THREADID` として、クライアントに渡る。後から分かれると、クライアントの表示が崩れる。

## Options

1. **Message-ID のつながりと正規化した件名の一致で合わせ、合わせはするが分けない。参照のないメールは差出人・件名・時間の窓で合わせる**
2. RFC 5256 の `REFERENCES` の手順をそのまま使い、件名は見ない
3. 件名と参加者だけで合わせる（ヘッダーのつながりを見ない）

## Decision

1 を採用する。

### 入力

各メッセージから、配送の時に次を取る（`crates/threading` の純粋な関数）。

- `msgid`：`Message-ID` を正規化したもの（`<>` を外し、ドメインの部分を小文字）。ない場合や重複する場合は、本システムが作った仮の ID を使い、他から参照されない。
- `refs`：`References` の ID の列と `In-Reply-To` の ID（`In-Reply-To` が `References` の最後にない場合は足す）。最大 100 個（後ろから）。
- `subject_key`：件名を正規化したもの。encoded-word を復号し、NFKC にし、前後の空白を落とし、先頭の返信と転送の印（`re`、`fw`、`fwd`、`返信`、`転送`、`aw`、`sv` と、`[n]`・`(n)` の番号、`:`・`：`）とメーリングリストの `[...]` を、なくなるまで繰り返し外し、大文字小文字を畳み込む。空になった件名は「件名なし」の鍵にする。
- `from_addr`、`date`（受け付けの時刻を使う。`Date` ヘッダーは信用しない）、自動のメールの印（`Auto-Submitted`、`List-Id`、`Precedence: bulk`）。

### 合わせの規則

アカウントごとに、`msgid` を節とする素集合を持つ。届いていない親の ID も、仮の節として持つ（表 `thread_nodes(account_id, msgid, thread_id, is_placeholder)`）。新しいメッセージ m が届いたら、上から順に評価する。

| # | 条件 | 結果 |
| --- | --- | --- |
| 1 | m の `refs` のどれかが、既存のスレッド T の節（届いた節か仮の節）で、T の `subject_key` が m と同じ | m を T に入れる。`refs` の複数が別々のスレッドに当たり、どれも件名が同じなら、それらを 1 つに合わせる |
| 2 | m の `refs` が既存のスレッドに当たるが、件名が違う | 新しいスレッドを作る（件名が変わると分かれる） |
| 3 | m の `msgid` が、既存のスレッド T の仮の節（子が先に届いている）で、件名が同じ | m を T に入れる |
| 4 | `refs` がない。同じ `from_addr`・同じ `subject_key` のスレッドで、最後のメッセージが 7 日以内のものがある | そのスレッドに入れる |
| 5 | それ以外 | 新しいスレッドを作る |

- **件名なし**の鍵は、規則 1・3 では一致とみなし、規則 4 では一致とみなさない。
- **上限**：スレッドが 100 通に達したら、以後のメッセージは同じ規則で新しいスレッドを作る（本家に合わせる）。古いスレッドの節は、新しいスレッドへ移さない。
- **送信したメッセージ**も同じ規則で入る。本システムから返信を送るときは、`References` と `In-Reply-To` を必ず付ける。
- **乗っ取りの抑え**：規則 1 の件名の一致に加え、認証（DMARC か、DKIM の署名のドメインと From の揃い）に失敗したメッセージが、そのスレッドに一度も現れていない差出人のドメインから来た場合は、スレッドに入れたうえで、画面で「このメッセージは確かめられていない」の印を付ける（spam-and-abuse-filtering の領域）。

### 安定性と合わせ

- 一度スレッドに入れたメッセージを、後から自動で別のスレッドへ分けない。
- 規則 1 で 2 つのスレッドを合わせるときは、ID の小さいほう（UUIDv7 で古いほう）を残し、もう一方のメッセージの `thread_id` を書き換え、change log に「合わせ」として載せる。JMAP では、移ったメッセージの `threadId` の変更と、消えたスレッドの `destroyed` として届く。
- 利用者が手でスレッドから外す操作は MVP の後（mailbox-model-labels-and-threads の領域）。

### 収束

- 規則は、同じメッセージの集合なら、到着の順序に依らず同じスレッドの分け方になるように作る。ただし、上限（100 通）と規則 4 の 7 日の窓は到着の順序と時刻に依るので、収束の性質はこれらを除いて確かめる（[quality.md](../quality.md) の 2.2.1 節 D）。

### 他の案を選ばなかった理由

- **2（RFC 5256 のまま）**：件名を見ないので、古いメールに返信して別の話題を始めた場合や、乗っ取りで、関係のないメッセージが同じスレッドに入る。本家の「件名が変わると分かれる」とも違う。
- **3（件名と参加者だけ）**：「お問い合わせ」「ご確認」のような同じ件名の別の会話が混ざる。参照のヘッダーの情報を捨てる。

## Consequences

- 良くなること：
  - 到着の順序に強く、クライアントに渡すスレッドの ID が安定する。
  - 本家に近い分け方（件名の変化、100 通、自動の通知の 1 週間）になる。
  - 乗っ取りを、件名の条件と認証の印で抑える。
- 引き受けるコスト：
  - 仮の節の表が、届かない親の分だけ増える（期限を決めて消す。mailbox-model-labels-and-threads の領域）。
  - 合わせで `threadId` が変わる。クライアントは change log で追う必要がある。
  - 件名の正規化の規則は、言語ごとの返信の印を足すたびに、既存のスレッドに遡らない。

## Confirmation

- 性質ベーステスト：任意のメッセージの集合と到着の順序（上限と窓に当たらない範囲）で、スレッドの分け方が順序に依らない。合わせの後に、どのメッセージも 1 つのスレッドにだけ属する。一度同じスレッドだった 2 つのメッセージは、以後も同じスレッドにある。
- 表駆動テスト：上の合わせの規則の全行と、件名の正規化の試験のベクトル（日本語のアプリの返信の印、encoded-word、全角、メーリングリストの印）。
- 回帰：スレッド化の規則の変更は、試験のベクトルの期待する値の変更として QA が承認する。
