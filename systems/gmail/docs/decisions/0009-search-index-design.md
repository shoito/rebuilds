# ADR-0009: 検索の索引は自前で、アカウントごとの不変のセグメント（日本語は 2-gram、英語は語、NFKC と大文字小文字の畳み込み）を S3 に置き、`search-node` がアカウントの範囲を受け持って NVMe にキャッシュする。変わる状態（ラベル、既読）は索引に入れず、change log から追う状態のビットマップで当てる

## Context

検索は題材の主な論点の 1 つである（[intent.md](../intent.md)）。要件は次のとおり。

- **日本語の全文**：件名と本文の日本語を、部分の一致で見つける。人の名前、会社の名前、商品の型番、新しい言葉が多い。形態素の解析は辞書にない語で区切りを誤り、見つけ損ねる。
- **演算子**：`from:`、`to:`、`subject:`、`has:attachment`、`filename:`、`before:`・`after:`、`older_than:`、`larger:`、`label:`、`in:`、`is:unread` など（本家の演算子に寄せる。[Search operators](https://support.google.com/mail/answer/7190)、2026-10-10 に確認。文法の寄せ方は法務の L9）。
- **状態の頻繁な変更**：既読、ラベル、スター、アーカイブは、1 通に何度も起きる。全文の索引に入れると、索引の書き直しが増える。
- **アカウントの中だけ**：検索は自分のメールだけを対象にする。他人のメールの有無が、結果・件数・速さ・候補から漏れてはならない。
- **量**：S1 で 100 万アカウント、平均 2.7 万通、索引 100 TB を見込む。多くのアカウントは、まれにしか検索しない。
- **新しさ**：新しいメールは p95 10 秒で検索に出る（NFR-005）。
- 汎用の検索のエンジン（OpenSearch など）を核に据えない（[ADR-0001](0001-platform-and-stack.md)）。

## Options

索引の分け方：

1. **アカウントごとの不変のセグメント。`search-node` がアカウントの範囲を受け持つ**
2. 全員を共有の大きな索引に入れ、`account_id` で絞る
3. Aurora の全文の検索（PostgreSQL の `pg_trgm`・`tsvector`）

語の分け方：

- a. **日本語・中国語の文字は 2-gram、英数字は語。正規化（NFKC、大文字小文字の畳み込み、かなの揃え）**
- b. 形態素の解析（辞書による語の分け方）
- c. a と b の両方を索引に入れる

## Decision

1 と a を採用する。b を足す（c）かは、E10 の前の `search-index-poc` で、順位の質と索引の大きさを比べて決める。

### 索引の中身

- 文書はメッセージ（受け手ごとの行）。文書の番号は、アカウントの中の 32 ビットの連番（`doc_no`）で、`message_id` との対応表をセグメントに持つ。
- **全文の欄**：件名、本文（text/plain と、text/html から取り出した文字）、添付の名前。添付の中身（PDF、Office の文書）の文字は MVP の後（attachment-and-url-scanning の領域で抽出の隔離を決める）。
- **語の分け方**：NFKC、大文字小文字の畳み込み、ひらがなとカタカナは別のまま（`search-index-poc` で揃えるかを決める）。日本語・中国語の文字の連続は 2-gram（1 文字の語には 1-gram も）、英数字は語（記号で区切る）、メールアドレスと URL は、全体と部分（ローカル部、ドメイン、ドメインの各段）を入れる。
- **変わらない属性（doc values）**：差出人のアドレスと名前、宛先、Cc、日付（受け付けの時刻）、大きさ、添付の有無と種類、`List-Id`、`Message-ID`。
- **入れないもの**：ラベル、既読、スター、スレッドの所属（合わせで変わる）、迷惑メール・ゴミ箱の状態。

### 状態のビットマップ

- `search-node` は、受け持つアカウントごとに、ラベルごと・旗ごとの `doc_no` のビットマップ（圧縮したビットマップ）を持つ。
- change log（[ADR-0006](0006-sync-protocol-jmap-imap-and-modseq.md)）を、アカウントの `modseq` の順に当てて更新する。検索の要求は、クライアントの状態の `modseq` 以上まで追いついてから答える（追いつきの待ちは 1 秒まで。超えたら、`mailstore` から状態を引いて当てる遅い経路に落とす）。
- ビットマップはセグメントと一緒に S3 にスナップショットし、受け持ちが移ったら、スナップショットと change log から作り直す。

### セグメントと受け持ち

- `search-indexer` は、outbox から新しいメッセージを読み、アカウントごとの小さなセグメント（直近の数秒〜数分）を作る。小さなセグメントは、`search-node` のメモリーと S3 に置く。
- 小さなセグメントは段階的に合わせ（LSM の形）、アカウントあたりのセグメントの数を 10 以下に保つ。削除は墓標（`doc_no` の削除のビットマップ）で表し、合わせで落とす。
- `search-node` は、アカウントの範囲（`account_id` のハッシュの区間）を受け持ち、2 つの写しで持つ。直近 30 日に検索したアカウントのセグメントを NVMe に置き、他は検索の時に S3 から取る（最初の検索は遅い。NFR-005 の p99 1 秒は、NVMe にあるアカウントの値とし、冷えたアカウントは p99 3 秒を目標にする）。
- セグメントのパス、キャッシュの鍵、受け持ちの表は `account_id` を先頭に持つ。セグメントは、アカウントの鍵で包んだデータの鍵で暗号化する（[ADR-0003](0003-message-storage-layout-and-dedupe.md) と同じ形）。

### 検索の実行

1. 文法を IR に変換する（`search-lang`。フィルターと同じ IR）。
2. 全文の条件を、2-gram の転置の並び（位置つき）の交わりで候補にし、位置で連続を確かめる（語句の検索と `AROUND`）。
3. doc values の条件と、状態のビットマップの条件を当てる。`SPAM`・`TRASH` は、`in:spam`・`in:trash`・`in:anywhere` がない限り除く（[ADR-0004](0004-labels-as-primary-mailbox-model.md)）。
4. 日付の新しい順に並べ、ページの区切りは（日付、`doc_no`）のカーソルにする。件数は 1,000 までは正確、それより上は「1,000 以上」と示す。

### 他の案を選ばなかった理由

- **2（共有の大きな索引）**：まれにしか検索しないアカウントの索引も常に熱い場所に置くことになる。アカウントの消去と鍵の分離が難しい。1 つの絞り忘れで他人のメールが出る。
- **3（Aurora の全文の検索）**：メタデータのシャードに、索引の書き込みと検索の CPU を足すことになり、配送と同期の遅れに響く。日本語の部分の一致の質と速さも足りないと見込む（`search-index-poc` で確かめる）。
- **b（形態素だけ）**：辞書にない語（人名、会社名、型番）を見つけ損ねる。メールの検索では、見つからないことが最も困る。

## Consequences

- 良くなること：
  - 見つけ損ねの少ない日本語の検索になる。
  - 状態の変更が索引の書き直しにならない。
  - アカウントの単位で、置き場所・消去・鍵を閉じられる。
- 引き受けるコスト：
  - 2-gram の索引は、語の索引より大きい（`search-index-poc` で測る）。
  - 冷えたアカウントの最初の検索が遅い。
  - change log とビットマップの追いつきを運用する。

## Confirmation

- 性質ベーステスト：任意のメッセージの集まり（日本語、全角と半角、絵文字、記号、旧来の文字コードから変換したもの）と検索の文字列で、索引の結果が、すべてのメッセージを素直に走査した参照の実装の結果と一致する（見つけ損ね 0、余分 0）。
- 性質ベーステスト：任意の状態の変更の列の後、ビットマップを使った結果が、`mailstore` の状態で当てた結果と一致する。
- 漏れの経路の表（[quality.md](../quality.md) の 2.2.1 節 G）：検索・件数・候補・エラーの応答に、他のアカウントの情報が出ない。
- lint：索引とキャッシュの鍵を作る関数は `AccountId` を最初の引数に取る。
