# ADR-0003: 生のメッセージを不変の blob として S3 に置き、状態はメタデータに置く。blob は同じ配送の受け手の間でだけ共有し、受け手ごとのヘッダーは別に持つ。zstd のフレームで圧縮し、blob ごとのデータの鍵で暗号化する。小さな blob は 1 日後にパックへ詰め直す。消去は鍵の破棄と参照の数え

## Context

メールの保存は、題材の費用と正しさの中心である。

- S1 で 1 日 6,000 万通を受け付け、3 年後に論理 2 PB を見込む（[architecture/README.md](../architecture/README.md) の 2 節）。1 通の平均は 75 KB だが、中央値は数 KB で、小さなメッセージが多い。
- 受け取ったバイトを、そのまま返せる必要がある。DKIM の署名の検証、転送、IMAP の `BODY[]`、書き出し（EML）、eDiscovery は、受け取ったときと同じバイトを要る。
- 1 つの配送（SMTP の 1 つのトランザクション、1 回の送信）が、複数の受け手に同じ本文を届ける。組織の全員へのメール、メーリングリスト、送信者の「送信済み」と本システムの中の受け手。
- 一方、中身のハッシュでメッセージをまたいで重複を排除すると、「同じ中身のメッセージを誰かが持っている」ことが、容量・消去・鍵の分離のふるまいから漏れうる。Dropbox の題材でも同じ論点を扱った（[Dropbox の ADR-0003](../../../dropbox/docs/decisions/0003-dedupe-scope-and-privacy.md)）。
- 状態（ラベル、既読、スレッド）は頻繁に変わる。中身と同じ場所に置くと、変更のたびに大きなオブジェクトを書き換えることになる。
- S3 の 1 オブジェクトの PUT の費用と、低頻度の層の最小の大きさ（128 KiB）のため、小さなメッセージを 1 通 1 オブジェクトで長く持つと高い。
- 利用者の削除と、保留（ホールド）と、法務の消去の期限（法務の L6）を両立させる必要がある。

## Options

保存の単位：

1. **生のメッセージを不変の blob にし、状態はメタデータに分ける**
2. MIME のパートごとに分けて保存し、メッセージは組み立てる
3. メールボックスごとのファイル（mbox・Maildir の形）

重複排除の範囲：

- a. **同じ配送の受け手の間だけ**
- b. アカウント（またはテナント）の中で、中身のハッシュで
- c. 全体で、中身のハッシュで
- d. 重複排除をしない

## Decision

1 と a を採用する。

### blob の構成

- メッセージは **本文の blob** と **受け手ごとのヘッダーの前置き** に分ける。
  - 本文の blob：送り手から受け取ったバイト（ヘッダーと本文）そのもの。同じ配送の受け手で同じ。
  - 前置き：本システムが受け手ごとに足すヘッダー（`Received`、`Authentication-Results`、`Delivered-To`、`ARC-*`、`X-<Brand>-...`）。数百バイトで、メタデータの行に持つ。
  - 受け手に返すメッセージは、前置き＋本文の blob。DKIM の検証の対象（本文の blob）は変わらない。
- **blob の ID** は UUIDv7。中身のハッシュ（SHA-256）は、照合と破損の検出のために持つが、ID と探し方には使わない。
- **圧縮**：zstd で、256 KiB ごとの独立したフレームにする。フレームの索引（元の位置と圧縮後の位置）を blob の頭に持ち、IMAP の `BODY[]<部分>` や添付の取得で、必要なフレームだけを読む。圧縮が 0.9 倍より縮まないフレーム（画像、zip）は、圧縮せずに置く。
- **暗号化**：blob ごとにデータの鍵（256 ビット）を作り、AES-256-GCM でフレームごとに暗号化する。データの鍵は、参照するテナントごとに、テナントの鍵（KMS）で包んで blob の目録に持つ。S3 の SSE-KMS も重ねる。
- **MIME の構造の索引**：配送の時に MIME を解析し、パートの木（種類、文字コード、元の位置と長さ、添付の名前、大きさ、ハッシュ）を作ってメタデータに持つ。表示・添付の取得・検索の索引の作成は、この索引を使い、毎回の全体の解析をしない。

### 置き場所とパック

- 配送の時、blob を 1 つのオブジェクトとして `blobs/<shard>/<yyyy>/<mm>/<dd>/<blob_id>` に置く（直近の読み出しが多い期間は、個別の取得が速い）。
- `blob-packer` が、1 日を過ぎた 256 KiB 未満の blob を、64 MiB のパックのオブジェクトに詰め直す。パックは同じ時間帯の blob を集める（同じアカウントとは限らない）。256 KiB 以上の blob は個別のまま。
- blob の場所は **blob の目録**（Aurora、blob の ID で分けたシャード）に持つ：`blob_id`、場所（オブジェクトのキー、位置、長さ）、大きさ、ハッシュ、包んだデータの鍵（テナントごと）、参照の数。詰め直しは目録の場所だけを変え、メールボックスの行に触れない。
- 生きている blob の割合が 50% を下回ったパックは、詰め直す。

### 重複排除（同じ配送の中だけ）

- 1 つの配送の受け手（同じ SMTP のトランザクションの宛先、同じ送信の「送信済み」と本システムの中の宛先）は、同じ本文の blob を参照する。テナントをまたいでもよい（受け手は全員、その中身を正しく受け取っている）。
- 中身のハッシュで、別の配送のメッセージと blob を共有しない。転送、再送、同じ添付を別のメールで受けた場合は、別の blob になる。
- 組織が「保存を分ける」を選んだ場合（MVP の後の、組織ごとの暗号化の鍵を含む）は、その組織の受け手には別の blob を作る。
- 容量は、メッセージごとの論理の大きさ（前置き＋本文の blob の元の大きさ）で、受け手ごとに数える。共有で減った量を利用者に見せない。

### 参照と消去

- blob の参照の数は、メールボックスの行（受け手ごと）、保留、送信の待ち（送信の依頼）を数える。
- 参照を減らすのは、メールボックスの変更（完全な削除、ゴミ箱の期限、保持の期限、アカウントの消去）を確定した後に、outbox から blob の目録のシャードへ送る。目録の側は、同じ減らしの依頼の重複を、（メールボックスの行の ID、blob の ID）で 1 回にする。
- 参照が 0 になったら、目録から包んだデータの鍵を消す（**鍵の破棄**。24 時間以内、NFR-015）。この時点で、パックの中のバイトは読めない。
- 物理の消去は、猶予（7 日）の後に、個別のオブジェクトを消すか、パックの詰め直しで落とす。S3 のバージョニングと大阪の写しの消去の期限は、法務の L6 で決める（それまで 30 日を既定にする）。
- テナントの消去（解約）は、そのテナントの包んだ鍵をすべて消す。他のテナントが参照する blob は残る（他の受け手は正しく受け取っている）。

### 他の案を選ばなかった理由

- **2（パートごと）**：受け取ったバイトの組み立て直しが、DKIM の検証と書き出しで同じバイトにならない危険がある（ヘッダーの折り返し、境界の文字列、改行）。オブジェクトの数も増える。
- **3（mbox・Maildir）**：ラベル（複数の箱への所属）と、状態の頻繁な変更に合わない。S3 の上で追記できない。
- **b（アカウントの中で中身のハッシュ）**：同じアカウントの中では漏れは小さいが、保存の節約も小さい（同じ中身を別の配送で受けることは少ない）。転送や再送のメッセージの消去の数え方が複雑になる。
- **c（全体）**：ある中身のメッセージを誰かが持つことが、容量・消去の速さから推測されうる。テナントの消去と鍵の分離が複雑になる。
- **d（しない）**：組織の全員へのメール、メーリングリストで、保存が受け手の数だけ増える。組織の節約（20% の見込み）を失う。

## Consequences

- 良くなること：
  - 受け取ったバイトをそのまま返せる。状態の変更が blob に触れない。
  - 組織の全員へのメールなど、同じ配送の受け手の間で保存を節約できる。
  - 他人の受信の有無を、重複排除から推測させない。
  - 鍵の破棄で、物理の消去を待たずに読めなくできる。
- 引き受けるコスト：
  - blob の目録と参照の数えを、メールボックスのシャードとは別のシャードで持ち、outbox で整合させる。
  - パックの詰め直しの読み書きの費用を持つ。
  - 別の配送の同じ添付は、保存が重ならない。

## Confirmation

- 性質ベーステスト：任意の配送・削除・保留・解約の列で、(1) 参照のある blob は常に読める、(2) 参照 0 の blob の鍵は破棄される、(3) 受け手に返すバイトは、前置き＋受け取ったバイトに等しい。
- 試験のベクトル：blob とフレームの索引の形式を固定し、以後のすべてのバージョンで読めて同じバイトになる。
- 照合：毎週、blob の目録と S3 Inventory を突き合わせる（目録にあってオブジェクトがない行 0）。メールボックスの行と目録の参照の数を抜き取りで照合する。
- レビュー：中身のハッシュで blob を探すコードを入れない（lint で、ハッシュを鍵にした目録の照会を禁止する）。
