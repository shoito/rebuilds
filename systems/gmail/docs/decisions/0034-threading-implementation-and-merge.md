# ADR-0034: スレッド化は配送のトランザクションの中で行い、合わせるスレッドの行を ID の順でロックする。合わせは古い ID を残し、移ったメッセージは新しいオブジェクトの世代（JMAP の Email の ID・IMAP の EMAILID と UID を新しくする）にして、消えたスレッドと同じ `modseq` で change log に書く。仮の節はスレッドが生きている間持ち、1 スレッド 1,000 まで。100 通の上限の後のスレッドは `continued_from` で前を指す。件名の正規化は `threading_version` のコードのバージョンで出し、既存のスレッドに遡らない

詳細は [mailbox-model-labels-and-threads.md](../architecture/mailbox-model-labels-and-threads.md) の 6 節。

## Context

- [ADR-0005](0005-threading-algorithm.md) は合わせの規則（1〜5）、100 通の上限、合わせて分けないこと、合わせで古い ID を残すことを決めた。次は決めていない。
  - 同じアカウントへの同時の配送（組織の全員へのメールと返信が同時に届く）で、合わせが競合したときの扱い。
  - 仮の節をいつ消すか（[ADR-0005](0005-threading-algorithm.md) の Consequences は「期限を決めて消す」とした）。
  - 100 通の後のメッセージが、前のスレッドの節を参照するときの行き先。
  - 件名の正規化の規則を変えたとき、古いスレッドと新しいメッセージをどちらの規則で比べるか。
- 仮の節を期限で消すと、遅れて届いた親が別のスレッドになり、順序に依らない性質が崩れる。
- RFC 8621 の 3 節は `threadId` を変わらない性質とし、スレッドを合わせるときは、`threadId` の変わる Email を消して新しい Email の ID で入れ直すことを求める（MUST）。RFC 8474 の 5.2 節も、一度知らせた `THREADID` を変えてはならないとする。[ADR-0005](0005-threading-algorithm.md) の「JMAP では、移ったメッセージの `threadId` の変更として届く」は、この標準と合わない。

## Options

同時性：

1. **配送のトランザクションの中で行い、候補のスレッドの行を ID の順でロックする**
2. 配送の後に、アカウントごとの 1 つの作業者がスレッド化する（直列）

仮の節：

- a. **スレッドが生きている間持ち、1 スレッド 1,000 まで**
- b. 一定の期間（例：90 日）で消す

## Decision

1 と a を採用する。

- `mailstore.deliver` の中で `crates/threading` の純粋な関数を呼び、規則に当たったスレッドの行を `thread_id` の順に `FOR UPDATE` で取る。合わせは ID の小さいスレッドを残し、移るメッセージ・節・集計を書き換え、`thread_merged` と `thread_destroyed` を同じ `modseq` で change log に書く。
- 移るメッセージは `object_gen` を 1 つ進める。JMAP の Email の ID と IMAP の `EMAILID` は `(message_id, object_gen)` から作るので新しくなり、JMAP では古い ID の `destroyed` と新しい ID の `created` として届く（RFC 8621 の 3 節）。IMAP では、見える所属ごとに古い UID を `VANISHED` にし、新しい UID を振る（RFC 8474 の 5.2 節）。中の `message_id`、blob、ラベル、旗は変わらない。
- 合わせは上限（100 通）を見ない。上限は新しいメッセージを入れるときだけ見て、超えたら `continued_from` を持つ新しいスレッドを作る。前のスレッドの節を参照するメッセージは、`continued_from` の鎖の最後のスレッドに入れる。
- 仮の節はスレッドが生きている間持つ。1 スレッド 1,000 を超えたら古いものから捨てて数える。
- スレッドは作ったときの `subject_key` と `threading_version` を持ち、新しいメッセージは、比べる相手のスレッドの `threading_version` の規則で正規化し直して比べる。

### 他の案を選ばなかった理由

- **2**：配送の後にスレッドの ID が決まると、受信の時の通知と JMAP の `Email` に `threadId` が要る時点（RFC 8621 の 4.1.1 節は `threadId` を変わらない性質として扱う）に間に合わない。直列の作業者は、大きなアカウントで NFR-001 を満たしにくい。
- **b**：遅れて届いた親（メーリングリストの遅れ、数か月後の返信）が別のスレッドになり、PROP-THR-001 が成り立たない。

## Consequences

- 良くなること：
  - 配送と同じ時点でスレッドが決まり、`threadId` が最初から安定する。
  - 順序に依らない性質を、期限に影響されずに保てる。
- 引き受けるコスト：
  - 仮の節の行が、届かない親の分だけ残る（1 スレッド 1,000 まで）。
  - 合わせで 1 つのトランザクションが最大 1,200 行を書く。
  - 正規化の古い規則を、コードに残し続ける。
  - 合わせで移ったメッセージを、クライアントは消して取り直す（多くて数百通。合わせはまれ）。[ADR-0005](0005-threading-algorithm.md) の JMAP の見え方の 1 文は、この ADR で置き換える。

## Confirmation

- 性質ベーステスト：PROP-THR-001〜004（[quality.md](../quality.md) の 2.2.1 節 D）。
- 結合テスト：同じアカウントへの同時の配送で、行き詰まりと合わせの誤りがない。
- 監視：合わせの数、捨てた仮の節の数、`continued_from` の数。
