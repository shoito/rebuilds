# ADR-0046: アプリの手元の DB は SQLite で、受信箱と直近に開いたラベルの直近 30 日の見出しと、受信箱の直近 7 日の本文を持ち、添付は開いたときだけ取る。DB は OS の保護に加え端末の鍵（Keychain・Keystore）で暗号化する。端末は `<Brand>Device` で登録し、利用者と組織の管理者が遠くからサインアウトと手元の消去を命じられる

詳細は [mobile-and-push.md](../architecture/mobile-and-push.md) の 4・5 節。

## Context

- 本家の大きなアカウントは数万通を持つ（S1 の平均 2.7 万通、2 GB。[architecture/README.md](../architecture/README.md) の 2 節）。全部を端末に置くと、端末の容量と最初の同期の時間が足りない。
- 利用者はスマートフォンが主（[intent.md](../intent.md)）で、移動中のオフラインでも最近のメールを読みたい。
- 端末を失うと、手元のメールが他人の手に渡りうる。組織は、退職者や紛失の端末からデータを消したい。
- JMAP の `PushSubscription`（RFC 8620 の 7.2 節）は Web のプッシュの形で、APNs・FCM のトークンを持てない。

## Options

1. **範囲を限った手元の DB、端末の鍵での暗号化、拡張の端末の登録と遠くからの消去**
2. 全部を端末に同期する
3. 手元に保存しない（毎回サーバーから取る）

## Decision

1 を採用する。

- 範囲：見出しは受信箱と直近 30 日に開いたラベルの直近 30 日（スター 90 日）、本文は受信箱の直近 7 日と開いたもの（500 MB まで）、添付は開いたときだけ（7 日で捨てる）。範囲の外は開いたときに取る。
- 同期の手順は Web と同じ（[ADR-0043](0043-web-offline-cache-and-optimistic-updates.md)）。
- DB は SQLite を、OS の保護（iOS の Data Protection、Android のファイルの暗号化）に加え、端末で作った鍵（Keychain・Keystore）で暗号化する。iOS の Notification Service Extension と共有の置き場所に置く。
- 端末は拡張の `<Brand>Device/set` で登録する（20 台まで、90 日つながらなければ消す）。利用者と組織の管理者は、端末ごとにサインアウトと手元の消去を命じられ、次の接続で当てる。届かない端末は、セッションを無効にする。

### 他の案を選ばなかった理由

- **2**：端末の容量と最初の同期の時間（数 GB）が合わない。
- **3**：オフラインで読めず、通知から開くたびに待つ。

## Consequences

- 良くなること：
  - 最近のメールをオフラインで読め、最初の同期が短い。
  - 端末の紛失と退職で、手元のデータを消せる。
- 引き受けるコスト：
  - 範囲の外の古いメールは、オフラインで読めない。
  - 遠くからの消去は、端末が次につながるまで当たらない。
  - 2 つの OS で同じ同期の仕様を実装し、同じ性質ベーステストの模型で確かめる。

## Confirmation

- 性質ベーステスト：PROP-PUSH-001（プッシュを落としても収束）、同期の収束の模型にアプリの模型を足す。
- E2E：遠くからの消去、サインアウトで DB と鍵が消えること。
- 監視：最初の同期の時間、手元の DB の大きさの分布。
