# ADR-0008: 選別のパイプラインは、接続の情報・中身から作った特徴・中身そのものを分け、中身そのものは選別の処理の中だけで機械が読む。人が中身を見るのは同意のある報告だけ。学習は特徴と同意のある報告で行う。選別は利用者の同意の仕組みの上で既定で有効にし、範囲と変え方を示す（法務の L1 の結論で調整する）

## Context

迷惑メール・フィッシング・マルウェアの選別は、メールの中身を読まなければできない。分類器は本文を、URL の評判は本文の中の URL を、添付の検査は添付のバイトを読む。

一方、本システムはメールの事業者として、電気通信事業法の通信の秘密（第 4 条）を守る立場にあると見込む（結論は法務の L1）。通信の秘密は、中身だけでなく、宛先・日時・接続元のような通信の構成の要素にも及ぶと説明されることが多い（**法務の確認待ち**）。2006 年の総務省の懇談会は、利用者の同意があれば、サーバーでの選別は通信の秘密の侵害に当たらないとし、同意の条件を満たせば既定で有効にできると整理した、と報じられた（[intent.md](../intent.md) の出典。今の見解かは**未検証**）。

選別の質を上げるには、学習のデータが要る。本家は機械学習で 99.9% 超を止めると説明する（[Google Cloud Blog](https://cloud.google.com/blog/products/identity-security/protecting-against-cyber-threats-during-covid-19-and-beyond)、2020-04-16、2026-10-10 に確認）が、学習のデータの扱いは公開されていない（**未検証**）。

決めておく必要があるのは、法務の結論が出る前に作るパイプラインの形である。結論で範囲や同意の形が変わっても、作り直さずに済む境界が要る。

## Options

1. **データを 3 つの区分に分け、中身そのものは選別の処理の中だけで機械が読む。人が見るのは同意のある報告だけ。学習は特徴と同意のある報告で行う**
2. 中身を学習と調査に広く使う（受け取ったメールの抜き取りを人が確かめ、学習に使う）
3. 中身を読まない選別だけにする（接続の情報と認証だけ）

## Decision

1 を採用する。

### データの区分

| 区分 | 例 | 使ってよい処理 | 残してよい場所 |
| --- | --- | --- | --- |
| C1 接続の情報 | 送り元の IP、EHLO、TLS、MAIL FROM と宛先のドメイン、認証の結果、大きさ、時刻 | 評判の数え、速さの上限、選別、運用の監視 | 評判のストア、集計の指標（宛先のローカル部を持たない） |
| C2 中身から作った特徴 | URL のドメインとパスのハッシュ、添付のハッシュと種類、本文の指紋（局所に敏感なハッシュ）、規則の当たりの ID、分類器の点数 | 評判の数え、学習、外部との共有（法務の L10 の後） | 特徴のストア（中身に戻せない形に限る） |
| C3 中身そのもの | 件名、本文、添付のバイト、表示の名前、アドレスのローカル部 | 選別の処理のメモリーの中、受け手のメールボックス | 受け手のメールボックスと、同意のある報告のサンプルの置き場所だけ |

- C3 を、選別の処理のログ・トレース・エラーの報告・メトリクスの属性に出さない（`AGENTS.md`）。
- C2 は、中身に戻せない形にする。URL は、ドメインを平文で、パスと問い合わせはハッシュにする（パスに個人の識別子が入るため）。本文の指紋は、元の文を復元できない方式に限る。

### パイプラインの層

1. **規則**：ヘッダーの形の異常、認証の結果、既知の悪い URL・添付のハッシュ、組織の許可・拒否の一覧。
2. **評判**：送り元の IP、認証済みのドメイン（DKIM の `d=`、SPF の通ったドメイン、DMARC の揃った From のドメイン）、URL のドメイン、添付のハッシュの評判。利用者の報告と受け手の振る舞い（開いた、迷惑メールではないと報告した）から数える。
3. **内容の分類器**：C3 を入力に、選別の処理の中で推論する。モデルの入力の特徴の作り方はモデルのバージョンに結び付ける。
4. **添付と URL の検査**：隔離したタスクで、ハッシュ、署名、構造（マクロ、実行形式、入れ子の書庫、暗号化された書庫）を検査する（attachment-and-url-scanning の領域）。
5. **合わせ**：各層の点を合わせ、判定（受信箱、迷惑メール、隔離、添付を止める）と理由のコードを出す。理由のコードは利用者に見せる（「このメールは、よく似た迷惑メールが多く報告されているため…」）。
6. **利用者ごとの上書き**：連絡先、利用者のフィルター、迷惑メールではないの報告、組織の許可の一覧。ただし既知のマルウェアは上書きしない。

### 人が中身を見る経路

- 運用者が利用者のメールの中身を見る経路は作らない。
- 例外は 2 つだけ：
  - **報告のサンプル**：利用者が「迷惑メールを報告」「フィッシングを報告」「迷惑メールではない」で、別の同意（「サンプルを提出して改善に使うことに同意する」）をした場合、そのメッセージの写しを報告のサンプルの置き場所に写す。置き場所は別の AWS アカウント、操作する人を限り、操作をすべて監査に残し、保持は 1 年（法務の L1・L6 で確定）。
  - **法務が承認した手続き**（法務の L4）。
- 組織の隔離（組織の管理者が隔離したメールを確かめる）は、組織の中の管理者による組織のメールの扱いで、本システムの運用者は見ない（組織の契約で扱う。法務の L7）。

### 学習

- 学習のデータは、C2 と、報告のサンプル（同意のあるもの）と、生成した合成のメールだけにする。受け取ったメールの C3 を、同意なしに学習の置き場所へ写さない。
- 学習は、報告のサンプルの置き場所と同じ別のアカウントで行い、モデルの成果物だけを本番に出す。

### 同意と設定

- 選別は既定で有効にする。アカウントの作成の時と設定の画面で、選別の範囲（何を機械で読むか、結果をどう使うか、学習に何を使うか）を示し、利用者がいつでも変えられるようにする。
- 選別の範囲を設定で切り替えられる形にする：(a) 迷惑メールの選別を止める（すべて受信箱へ。迷惑メールの印だけを付ける）、(b) 内容の分類器を使わない（規則と評判と添付の検査だけ）。既知のマルウェアの添付を止める処理は、どの設定でも続けるかを法務の L1 で決める。
- 同意の有無で、他の提供の条件を変えない。
- 送信の側の選別（乗っ取りの検知のための送信の中身の判定）も同じ区分と経路で作り、範囲は法務の L1 で決める。

### 他の案を選ばなかった理由

- **2（中身を広く使う）**：通信の秘密と利用者の信頼に反するおそれが大きい。法務の結論が厳しかったときに、学習のデータと調査の手順を作り直すことになる。
- **3（中身を読まない）**：内容で見分けるフィッシング（正規のサービスの認証を通る送り元から送られる、乗っ取られたアカウントからの送信）を止められず、NFR-008 を満たせない。

## Consequences

- 良くなること：
  - 法務の結論が出る前に、区分と経路の形で作れる。結論で範囲と同意の形を調整しても、パイプラインの形は変わらない。
  - 運用者が中身を見ないことを、経路の不在として確かめられる。
- 引き受けるコスト：
  - 学習のデータが、受け取ったメール全体を使う場合より少ない。報告のサンプルの偏りと、合成のメールで補う。
  - 理由のコードと設定の画面を作り、保守する。
  - 特徴が中身に戻せないことを、方式ごとに確かめる。

## Confirmation

- 経路の検査：C3 の型（`MessageContent`）を、選別の処理と `mailstore` と報告のサンプルの書き込みの外で使えないようにする（型と lint）。ログ・トレースの属性に C3 の型を渡すと、コンパイルで失敗させる。
- 監査：報告のサンプルの置き場所の操作を、すべて監査に残し、毎月 QA と法務が抜き取りで確かめる。
- 試験：選別の設定（有効、選別を止める、内容の分類器なし）ごとに、決定表の全行を確かめる。
- レビュー：学習の置き場所への書き込みの経路が、報告のサンプルと C2 だけであることを、infrastructure の領域の IAM の方針で確かめる。
