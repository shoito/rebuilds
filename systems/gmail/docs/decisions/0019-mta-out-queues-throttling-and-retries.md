# ADR-0019: mta-out は宛先の MX の組ごとに並行と速さを AIMD で調整し、速さの数えを Valkey の GCRA でプールの全台で共有する。再試行は 1 分から 4 時間の間隔まで延ばして最大 5 日、24 時間で遅れの通知。MTA-STS の enforce の相手には方針と証明書が通らなければ送らない。TLS-RPT を公開する相手には日ごとに報告を送る

詳細は [outbound-smtp-and-reputation.md](../architecture/outbound-smtp-and-reputation.md) の 4.3・6・7 節。

## Context

- 相手の事業者は、送り元の IP と範囲ごとに速さを絞り、421・4.7.x で一時に断る。絞られても送り続けると、評判が落ちて迷惑メールの箱や拒否になる。
- 多くの宛先のドメインが、同じ事業者の MX を使う。ドメインごとに速さを数えると、同じ事業者への合計が多すぎる。
- NFR-002 は、窓の後から外部の MX への最初の試行まで p95 5 秒を求める。
- RFC 5321 の 4.5.4.1 節は、再試行の間隔を少なくとも 30 分、諦めるまで 4〜5 日を推奨する。一時の失敗の多く（相手の短い絞り、グレーリスト）は、数分で直る。
- SQS の可視の時間切れは最大 12 時間、保持は最大 14 日。
- MTA-STS を守ると決めた（[architecture/README.md](../architecture/README.md) の 6 節）。

## Options

速さ：

1. **MX の組ごとの AIMD と、Valkey の共有の GCRA**
2. 宛先のドメインごとの固定の上限
3. 台ごとの調整だけ（共有しない）

再試行：

- a. **1 分・5 分・15 分・30 分・1 時間・2 時間・以後 4 時間、5 日**
- b. 30 分の一定の間隔、5 日

## Decision

1 と a を採用する。

- MX の名前の登録ドメインで組を作り、大手の事業者は手の一覧で組を決める。
- 組ごと・プールごとに並行 `c` と速さ `r` を持つ。絞りの応答で半分、2 分で 3 回で 5 分止め、250 の 100 回の続きか 5 分の無事で `c + 1`・`r × 1.1`。既定 `c = 5`・`r = 300`、上限 `c = 20`・`r = 3,000`。
- 速さは Valkey の GCRA で全台が共有し、並行は台ごとに `c / 台数`。
- 再試行は a の間隔に ±20% の揺らぎ。組を止めている間の待ちは数えない。5 日で `expired` と DSN。24 時間で遅れの DSN を 1 回、画面の印は 1 時間から。
- 依頼は SQS の可視の時間切れで待つ。宛先ごとの状態の正本は `mailstore` の `submission_recipients` で、SQS を失ったら毎時の突き合わせで作り直す。
- TLS は機会主義。TLS 1.0・1.1 では送らない。MTA-STS の `enforce` では、方針の `mx` に合い、証明書が検証できる MX にだけ送り、満たさなければ待って 5 日で不達。
- TLS-RPT は、相手が `rua` を出していれば日ごとに送る。

### 他の案を選ばなかった理由

- **2**：同じ事業者への合計を抑えられず、事業者ごとの変化に追いつけない。
- **3**：台を足すと合計の速さが増え、相手の絞りを招く。
- **b**：短い一時の失敗で 30 分待ち、届くのが遅れる。RFC の推奨より短い間隔は、最初の数回だけに限り、後は長くする。

## Consequences

- 良くなること：
  - 相手の絞りに速く合わせ、評判を守る。
  - 一時の失敗の多くを数分で直して届ける。
- 引き受けるコスト：
  - 最初の数回の再試行が RFC の推奨より短い。相手の負荷にならないよう、組の速さの中で行う。
  - 手の一覧（大手の事業者の組と上限）の運用が要る。

## Confirmation

- 模型：`smtp-peer-sim` で、後退の間隔、期限、DSN、速さの調整、MTA-STS（[quality.md](../quality.md) の 2.2.1 節 J）。
- 性質ベーステスト：PROP-OUT-001、PROP-OUT-003。
- 監視：組ごとの絞りの率、待ちの深さ、最初の試行までの p95（NFR-002）。
