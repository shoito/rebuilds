# ADR-0007: テナントは組織、個人のアカウントは 1 人の個人のテナントとする。メールボックスの表はアカウントの単位で Aurora のシャードに置き、`tenant_id`・`account_id` で FORCE RLS にする。配送は受け手の文脈で書く。テナントをまたぐ経路は一覧にして専用のロールを通す

## Context

利用者は 2 種類いる。

- **個人**：1 人が 1 つのアカウントを持つ。他の個人とデータを共有しない。
- **組織**：独自のドメイン、利用者、組織の単位、別名、グループ、配送の規則、保持と保留を持つ。組織の管理者は、方針と監査を扱う。保留と eDiscovery の担当は、組織の中の複数のアカウントのメールを横断して検索する。

メールは、テナントの境界を越えるのが普通の仕事である。外部や他の組織から届いたメールを、受け手のメールボックスに書く。本システムの中の個人から組織へ、組織から個人へ送る。

量は、メッセージの行が S1 で 270 億、S3 で 2.7 兆を見込む（[architecture/README.md](../architecture/README.md) の 2 節）。1 つの Aurora のクラスタには入らない。メールボックスはアカウントの中で閉じた状態なので、アカウントの単位で分けやすい。

他の題材と同じく、データベースでの分離は FORCE RLS と `SET LOCAL` で行う。

## Options

テナントの形：

1. **テナントは組織。個人のアカウントは、1 人の個人のテナント**
2. テナントは組織。個人のアカウントは、すべて 1 つの共有のテナント
3. テナントを持たず、アカウントだけで分ける

メタデータの置き方：

- a. **directory（アカウント、組織、アドレス、規則）を 1 つのクラスタに、メールボックスの表をアカウントで分けた複数のクラスタ（シャード）に置く**
- b. すべてを 1 つのクラスタに置く
- c. メールボックスの表を DynamoDB に置く

## Decision

1 と a を採用する。

### テナントとアカウント

- `tenants(tenant_id, kind: org | personal, ...)`。個人のアカウントを作ると、その人だけの `personal` のテナントを作る。組織のテナントは、多くのアカウントを持つ。
- `accounts(tenant_id, account_id, primary_address, mailbox_shard, ...)`。ID は UUIDv7。
- 組織から個人へ、個人から組織へのアカウントの移し替えは、MVP では作らない（別の ADR で扱う）。

### directory とシャード

| クラスタ | 中身 | RLS |
| --- | --- | --- |
| directory（1 つ） | テナント、アカウント、ドメイン、アドレスと別名、グループ、配送の規則、保持の規則、保留、OAuth のクライアントと許可、監査ログ | `tenant_id` で FORCE RLS |
| メールボックスのシャード（S1 で 8） | メッセージ（受け手ごとの行）、ラベル、ラベルの所属と UID、スレッドと節、change log、下書き、送信の依頼、フィルター、不在の返信、outbox | `tenant_id` と `account_id` で FORCE RLS |
| blob の目録のシャード | blob の場所、包んだデータの鍵、参照の数（[ADR-0003](0003-message-storage-layout-and-dedupe.md)） | なし（下の一覧の X5。メールの中身・件名・アドレスを持たない） |

- アカウントは 1 つのシャードにだけ置く。シャードの割り当ては `accounts.mailbox_shard` が正で、`mailstore` は割り当てを Valkey にキャッシュする（変更の通知で消す）。
- シャードの移し替え（偏りの解消）は、アカウントの単位で、書き込みを止めずに写し、短い書き込みの停止で切り替える（infrastructure の領域）。
- メールボックスの表の主キーと索引の先頭は `account_id`。

### RLS

- メールボックスのシャードの要求は、`SET LOCAL app.tenant_id` と `SET LOCAL app.account_id` を設定する。ポリシーは両方が一致する行だけを通す。
- 委任（他の人のメールボックスを読む許可。MVP の後）と、組織の共有の受信箱は、`app.account_ids`（許された集合）で表し、`mailstore` が要求ごとに許可の表から決める。
- **RLS の外の表**は次だけにし、メールの中身・件名・アドレスのローカル部を持たせない。
  - `tenants` の公開の属性、`domains`（ドメイン → テナント。受信の宛先の解決の入口）
  - `address_index`（アドレスのハッシュ → アカウント・グループ。宛先の解決の入口。ローカル部を平文で持たない）
  - `sessions`、`oauth_tokens_index`（トークンのハッシュ → アカウント）
  - blob の目録
  - outbox の読み出しの位置、SLI の集計
- **テナントをまたぐ処理は、次の経路だけにし、専用の DB のロールを通す。** 一覧にない経路を足すときは、先にこの ADR を直す。
  - X1：受信の宛先の解決（`domains`、`address_index`）
  - X2：配送（`mailstore.deliver`）。受け手のアカウントの文脈を設定してから書く。差出人の文脈では書かない
  - X3：本システムの中の送信の配送（送信者の blob を受け手が参照する）
  - X4：システムの作業（保持の期限、ゴミ箱の期限、パック、GC）。アカウントを 1 つずつ文脈に設定して回す
  - X5：blob の目録の参照の増減（outbox から）
  - X6：relay の outbox の読み出し、SLI の集計
  - X7：eDiscovery の横断の検索と書き出し（組織の中だけ。担当の役割、保留の案件、監査の記録を要る。retention-and-ediscovery の領域）
  - X8：シャードの移し替え

### 他の案を選ばなかった理由

- **2（個人を 1 つのテナントに）**：個人どうしの分離を `account_id` だけで守ることになり、テナントの単位の操作（鍵、消去、監査）が個人に使えない。
- **3（テナントなし）**：組織の方針、保持、保留、監査をアカウントの外に持つ形がなくなる。
- **b（1 つのクラスタ）**：S1 のメッセージの行（16 TB）と書き込みの量で、1 つのクラスタの書き込みの上限と保守の時間に当たる。障害の範囲が全員になる。
- **c（DynamoDB）**：成り立つが、change log と `modseq` とラベルの所属を 1 つのトランザクションで書く形（[ADR-0006](0006-sync-protocol-jmap-imap-and-modseq.md)）と、RLS の分離の形が他の題材とそろわない。アカウントの単位のシャードで Aurora の上限に収まる。

## Consequences

- 良くなること：
  - 他の題材と同じ RLS の形で、アカウントとテナントの分離を DB で守れる。
  - アカウントの単位で、シャードを足し、移し、障害の範囲を限れる。
  - テナントをまたぐ経路が一覧になり、レビューと試験の対象が決まる。
- 引き受けるコスト：
  - Aurora のクラスタの数が段階とともに増える（S3 で 800）。作成・更新・監視の自動化が要る。
  - シャードをまたぐ一貫性（blob の目録、本システムの中の送信）を outbox で整える。
  - 大きなアカウント（組織の共有の受信箱、数百万通）の偏りを扱う。

## Confirmation

- 結合テスト：すべてのシャードと directory の表に `FORCE ROW LEVEL SECURITY` とポリシーがあることを、スキーマの検査で確かめる。RLS の外の表の一覧を CI が上の一覧と照らす。
- 性質ベーステスト：任意の 2 つのアカウントのメールと操作の列で、アカウント A の JMAP・IMAP・検索・プッシュ・通知の結果に、B のメッセージ・件名・有無が出ない（漏れの経路の表、[quality.md](../quality.md) の 2.2.1 節 G）。
- lint：S3 のキー・キャッシュの鍵・索引の鍵を作る関数は、`AccountId` の型を最初の引数に取るものだけにする。配送の関数は受け手の `AccountContext` を要る。
- 本番：応答の抜き取りを、アカウントの文脈に通し直して比べる（応答の監査）。
