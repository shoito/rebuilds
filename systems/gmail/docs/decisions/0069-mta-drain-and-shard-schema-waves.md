# ADR-0069: `mx-edge`・`mta-out` は台ごとの入れ替えで出し、EC2 の自動の拡大の群のライフサイクルフック（最大 15 分）で排出する。`mx-edge` は NLB から外した後、トランザクションの間の会話にだけ `421 4.3.2` を返して閉じ、確定の途中では止めない。`mta-out` は待ち行列から取るのを止め、送信中のトランザクションを終えてから IP を新しい台へ移す。IMAP・submission・プッシュの長い接続は、タスクごとに 60 秒に散らして閉じる。メールボックスのシャードのスキーマは、広げる段 → コード → 縮める段の順に、見張りのシャード → 1 日に全体の 4 分の 1 の波で当て、新しい列を使うコードは全シャードの `schema_version` を確かめてから動く

詳細は [delivery.md](../architecture/delivery.md) の 4.2・5.3 節。

## Context

- `mx-edge` と `mta-out` は 1 台ずつ入れ替え、NLB から外して新しい接続を断り、進行中の会話と配送を終えてから止める（最大 10 分）。送信の IP を持つ台は、その IP の送信を他の台へ移してから止める（[runbooks/README.md](../runbooks/README.md) の 3 節）。どの仕組みで待つかは決めていない。
- 250 を返す前の確定（[ADR-0011](0011-spool-commit-and-sweeper.md)）の途中で台を止めると、送り手は 250 を受けず送り直す（失わないが重複の抑えに頼る）。確定の後・250 の前に止めると同じ。
- IMAP の同時の接続は S1 で 20 万（設計 40 万）。一度に閉じると再接続が集まり、TLS の握手と QRESYNC の追いつきで負荷の山を作る。
- メールボックスのシャードは S1 で 8、S3 で 800 になる。シャードのマイグレーションは 1 つずつ、1 日に全シャードの 1/4 まで（[runbooks/README.md](../runbooks/README.md) の 3.1 節）。波の途中では、シャードごとにスキーマのバージョンが違う。
- メールボックスの状態は `mailstore` だけが書く（[ADR-0006](0006-sync-protocol-jmap-imap-and-modseq.md)）。

## Options

MTA の排出：

1. **自動の拡大の群のライフサイクルフックで、台ごとに排出を待つ**
2. ECS のタスクの停止の待ち（`stopTimeout`）だけで排出する
3. 2 つの群を作って一度に切り替える（ブルーグリーン）

スキーマ：

- a. **広げる・コード・縮めるの段と、見張りのシャードからの波、スキーマのバージョンによる切り替え**
- b. すべてのシャードに一度に当てる
- c. 新しい経路を `release.*` のフラグで切り替える

## Decision

1 と a を採用する。

- `mx-edge`：新しい台を足して健全を確かめ、古い台をライフサイクルフック（待ち 15 分）で終わらせる。NLB の登録を外し（遅れ 600 秒）、会話ごとに次のコマンドへ `421 4.3.2` を返して閉じる。`DATA` と確定の途中では止めず、確定と 250 を終えてから閉じる。10 分で残る会話は 421。AZ ごとに 1 台ずつ。
- `mta-out`：SQS から取るのを止め、送信中のトランザクションを 10 分まで終える。終わらないものは中断して待ち行列に戻す（重複しうる）。ENI の副の IP を新しい台に移す。1 つのプールの台を同時に 2 つ止めない。
- `imap-server`：`* BYE [UNAVAILABLE]` を 60 秒に散らし、実行中のコマンドを終える。1 回に全体の 10% のタスク。`submission` は `mx-edge` と同じ。`push-gateway` は `retry:` の乱数（5〜30 秒）と WebSocket の 1012。
- スキーマ：1 つの PR は 1 つの段。縮める段は広げる段の 14 日の後。波は見張りのシャード → 24 時間 → 1 日に全体の 4 分の 1。directory と blob の目録は 1 回。各シャードの `schema_versions` を directory の `mailbox_shards.schema_version` に写し、新しい列を使うコードは全シャードが要るバージョンになるまで古い経路で動く。埋め戻しは `mailstore` のマイグレーションの走り手がアカウントの文脈で 1,000 行ずつ。DDL は `lock_timeout` 2 秒と `CONCURRENTLY`。

### 他の案を選ばなかった理由

- **2**：Fargate の停止の待ちは最大 120 秒で、遅い送り元の会話（最大 30 分）と送信のトランザクションを待てない。EC2 の台の IP の移しの手順を挟めない。
- **3**：固定の IP（BYOIP の範囲）と NLB の登録を 2 つの群で持つことになり、IP が足りない。送信の IP の評判は台でなくプールに付くので、一度に切り替える利点が小さい。
- **b**：誤ったマイグレーションの影響が全員に及ぶ。全シャードの保守の時間が重なる。
- **c**：スキーマのバージョンはデータの事実で、フラグで先に有効にすると、列のないシャードで失敗する（`AGENTS.md` の形式の規則をフラグにしない、と同じ理由）。

## Consequences

- 良くなること：
  - デプロイで受け付け中のメールの確定を壊さない。送り手は 421 で別の台へ送り直す。
  - 長い接続の再接続の山を散らせる。
  - スキーマの誤りの影響を見張りのシャードで止められる。
- 引き受けるコスト：
  - `mx-edge` の 1 回のデプロイが、東京 9 台・大阪 4 台で数時間かかる。
  - `mta-out` の中断で、相手に重複が届きうる。
  - 新しい列を使う経路は、波が終わるまで（S1 で 5 日）動かない。

## Confirmation

- 性質ベーステスト：PROP-DLV-001（排出で確定を壊さない）、PROP-DLV-004（スキーマのバージョンの待ち）。
- 試験：検証の環境で、負荷をかけながら `mx-edge` の入れ替えを回し、確定の途中で閉じた会話 0 を確かめる。
- 監視：デプロイ中の 421 の数、IMAP の再接続の率、波ごとのマイグレーションの時間。
