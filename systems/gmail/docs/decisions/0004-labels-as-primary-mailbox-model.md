# ADR-0004: メールボックスのモデルはラベルを正とする。メッセージは複数のラベルを持ち、受信箱・送信済み・下書き・迷惑メール・ゴミ箱もシステムのラベルにする。迷惑メールとゴミ箱は他のラベルと排他にする。フォルダーは見せ方で、IMAP ではラベルを箱として見せる

## Context

メールの整理には 2 つの考え方がある。

- **フォルダー**：メッセージは 1 つのフォルダーにだけ入る。IMAP の箱、多くのメールのアプリ、組織の利用者の慣れた形。
- **ラベル**：メッセージは複数のラベルを持てる。本家はラベルを使い、フォルダーと違うと説明する（[Create labels](https://support.google.com/mail/answer/118708)、2026-10-10 に確認）。アーカイブは「受信箱のラベルを外す」ことになる。

本システムは、Web・アプリ（JMAP）と既存のアプリ（IMAP）の両方に同じ状態を見せる（[ADR-0006](0006-sync-protocol-jmap-imap-and-modseq.md)）。JMAP のメッセージは `mailboxIds` の集合を持ち、複数の箱への所属を表せる（RFC 8621 の 4.1.1 節）。IMAP はフォルダーの形だが、同じメッセージを複数の箱に置いて見せられる。

決める必要があるのは、正のモデル（DB の形と、変更の意味）である。正が 2 つあると、フォルダーの移動とラベルの付け外しの意味が経路ごとにずれる。

## Options

1. **ラベルを正にし、フォルダーは「ラベルを 1 つだけ持つ」見せ方にする**
2. フォルダーを正にし、ラベルはフォルダーの写し（同じメッセージの複製）で表す
3. 利用者ごとにラベルかフォルダーかを選ばせ、両方のモデルを持つ

## Decision

1 を採用する。

### ラベル

- メッセージ（受け手ごとのメールボックスの行）は、ラベルの集合を持つ。表は `message_labels(tenant_id, account_id, label_id, message_id, uid, added_modseq)`。
- **システムのラベル**：`INBOX`、`SENT`、`DRAFT`、`SPAM`、`TRASH`、`STARRED`、`IMPORTANT`、`SCHEDULED`、`SNOOZED`。`UNREAD` はラベルではなく、メッセージの旗（`seen`）で持つ（IMAP の `\Seen` と JMAP の `$seen` に合わせる）。
- **利用者のラベル**：名前（Unicode、NFC、`/` で入れ子を表す）、色、表示の設定。アカウントあたり 5,000 まで（本システムの既定。本家の上限は**未検証**）。
- **アーカイブ**は `INBOX` を外すこと。どのラベルもないメッセージは「すべてのメール」でだけ見える。
- **排他の規則**：`SPAM` と `TRASH` は互いに排他で、どちらかが付いたメッセージは、他のラベルの一覧と「すべてのメール」と検索の既定から外す（ラベルの所属は残し、戻したときに元に戻る）。`SPAM` か `TRASH` を付けると `INBOX` は外す。
- 規則は決定表（`DT-MBX-*`）で `spec.md` に書き、`mailstore` の 1 つの関数で当てる。

### スレッドとの関係

- ラベルはメッセージに付ける。スレッドのラベルは、スレッドのメッセージのラベルの和として求める（`TRASH`・`SPAM` のメッセージは除く）。
- スレッドへの操作（スレッドをアーカイブ、ラベルを付ける）は、そのスレッドのメッセージ（`TRASH`・`SPAM` を除く）に当てる。後から届いたメッセージには当てない。
- ミュートはスレッドの属性で、ミュートのスレッドに届いたメッセージには `INBOX` を付けない。

### フォルダーとしての見せ方

- Web の設定で「フォルダーの表示」を選んだ利用者には、移動（ラベルを付け替える）だけを見せる。モデルは同じで、移動は「元のラベルを外して新しいラベルを付ける」の 1 つの変更にする。
- IMAP では、各ラベルを箱として見せる（`INBOX`、`[<Brand>]/Sent Mail`、`[<Brand>]/All Mail`、`[<Brand>]/Spam`、`[<Brand>]/Trash` に `SPECIAL-USE` の属性を付ける）。IMAP の `COPY` はラベルを足し、`MOVE` はラベルを付け替え、`EXPUNGE` はその箱のラベルを外す。`[<Brand>]/Trash` での `EXPUNGE` は完全な削除にする（client-sync-and-protocols の領域）。

### 他の案を選ばなかった理由

- **2（フォルダーを正）**：ラベルの複製は、既読・スター・削除を複製の間でそろえる仕組みが要り、ずれの原因になる。保存も重複する。
- **3（両方）**：1 つのアカウントを JMAP と IMAP の両方で見るときに、2 つのモデルの対応が必要になる。変更の意味が経路ごとにずれる。

## Consequences

- 良くなること：
  - 1 つのメッセージを複数の観点で整理できる。JMAP にそのまま対応する。
  - フォルダーの利用者には移動だけを見せ、同じモデルで扱える。
- 引き受けるコスト：
  - IMAP のアプリでは、同じメッセージが複数の箱に見え、容量が多く見えることがある（`[<Brand>]/All Mail` を同期するアプリ）。利用者向けの説明が要る。
  - 排他の規則と、スレッドへの操作の意味を、決定表で厳密に決める必要がある。

## Confirmation

- 表駆動テスト：ラベルの付け外し・移動・アーカイブ・迷惑メール・ゴミ箱の決定表の全行。
- 性質ベーステスト：任意の操作の列（JMAP と IMAP を混ぜる）で、(1) `SPAM` と `TRASH` を同時に持つメッセージがない、(2) `SPAM`・`TRASH` を持つメッセージが他のラベルの一覧に出ない、(3) JMAP の `mailboxIds` と IMAP の各箱の中身が同じ所属を表す。
- lint：ラベルの所属の表を `mailstore` の外から書くコードを禁止する。
