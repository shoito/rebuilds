# ADR-0070: 永く残る形式（blob、スプールの封筒、セグメント、change log、展開の記録、プッシュの中身、監査の行、見張りのヘッダー）は形式の登録簿にバージョンと試験のベクトルを持つ。書く側の新しいバージョンは、東京と大阪のすべての読む側が新しいバージョンを読めることをデプロイの関門が確かめてから出す。読む側は、そのバージョンのデータが残る限り外さない（blob v1 は永く）。選別のモデルと規則は `filter_version` の成果物で、`spam-scorer` が今のバージョンと候補のバージョンを同時に読み込み、候補を影で全量に当て、アカウントのハッシュで決めた組で段を進める。段の進めと戻しは指標の関門で自動にし、固定は `ops.filter_model_pinned`

詳細は [delivery.md](../architecture/delivery.md) の 5.1・5.2 節。

## Context

- 形式の変更は、読む側を先に出し、全台に行き渡ってから書く側を出す。書く側を戻しても、読む側は新しい形式を読み続ける（[runbooks/README.md](../runbooks/README.md) の 3 節）。形式はコードのバージョンとして出し、フラグにしない（`AGENTS.md`）。「全台に行き渡った」をどう確かめるかは決めていない。
- 大阪の warm standby は切り替えの時に東京のデータを読む（[ADR-0064](0064-storage-classes-and-region-replication.md)）。大阪のバージョンが古いと、切り替えの直後に読めない。
- 形式ごとに残る期間が違う（blob は永く、スプールは 7 日、change log は 30 日）。
- 選別のモデルと規則は、評価の集まりの合否 → 影 7 日 → 1% → 10% → 50% → 100% で出し、外れたら `ops.filter_model_pinned` で戻して直近 24 時間を判定し直す（[ADR-0024](0024-feedback-training-data-and-model-release.md)）。影の判定の仕組みと、段の組の決め方は決めていない。
- 選別の誤りは数時間〜数日の利用者の報告で見える。同じ利用者・組織の判定が段の間でぶれると、報告の比べができない。

## Options

形式：

1. **登録簿と試験のベクトル、デプロイの関門で読む側の行き渡りを確かめる**
2. 読む側と書く側を同じリリースで出す
3. 書く側の新しいバージョンをフラグで段階に有効にする

選別の出し方：

- a. **同じプロセスで今と候補を当てる影と、アカウントのハッシュの組**
- b. 影を別の群（候補だけを動かす台）で、抜き取りのメッセージに当てる
- c. メッセージのハッシュで組を決める

## Decision

1 と a を採用する。

- 登録簿：開発リポジトリの `formats/` に、形式ごとのバージョン、試験のベクトル、読む側・書く側のコードの場所。形式の型を変えてバージョンと試験のベクトルを足さないと CI が失敗する。
- 出す順：読む側（東京、大阪の warm standby、関わるモバイルのアプリ）→ 関門（ECS の動いているダイジェストと AMI の一覧から、すべての読む側のバージョンを確かめる）→ 書く側。書く側の PR は、読む側の行き渡りの後でなければマージできない。
- 読む側を外す時：blob と監査の行は外さない。スプールと展開の記録は 8 日、change log は 30 日、セグメントは全アカウントの作り直しの後、プッシュの中身はアプリの 12 か月の後。
- 選別：`filter_version` は署名した成果物で、`spam-scorer` が今と候補を同じプロセスに読み込む。候補はすべてのメッセージに当て、判定に使わず `shadow_verdict` を特徴の記録に残す。候補の推論が予算を超えたら影の記録を落とし、判定を遅らせない。
- 組：`filter_version` の鍵つきのアカウントの ID のハッシュで 0〜9,999。組織のアカウントは組織の ID で決める。段は番号の範囲で広げ、同じアカウントは外れない。
- 関門：各段 24 時間以上、組ごとの報告の率・迷惑メールではないの率・隔離の解除の率・影の食い違いで、[ADR-0024](0024-feedback-training-data-and-model-release.md) の関門に外れたら自動で戻す。50% → 100% だけ QA と Dev の承認。危険度の点（`risk_version`）も同じ仕組み。

### 他の案を選ばなかった理由

- **2**：ローリングの途中で、新しい書く側と古い読む側が同時に動く。
- **3**：形式をフラグにすると、フラグを戻した後に新しい形式のデータが残り、戻したつもりで読めないデータができる。
- **b**：抜き取りでは、少ない種類（日本語のフィッシングの型ごと）の食い違いを 7 日で数えられない。別の群の費用と、同じメッセージを 2 回読む経路が増える。
- **c**：同じ利用者に届くメールの判定がバージョンでぶれ、報告の比べと説明ができない。

## Consequences

- 良くなること：
  - 読めないデータを作らないことが、関門で確かめられる。大阪の切り替えでも読める。
  - 選別の候補の振る舞いを全量で比べられ、段の間で判定がぶれない。
- 引き受けるコスト：
  - 形式の変更は 2 回のリリース（読む側、書く側）に分かれ、時間がかかる。
  - 影の推論で `spam-scorer` の CPU が増える（候補の分）。重ければ抜き取りに下げる判断が要る。
  - 組織の単位の組では、大きな組織が 1 つ入ると 1% の段の量が大きくなる。

## Confirmation

- 性質ベーステスト：PROP-DLV-002（組が外れない、組織で混ざらない）、PROP-DLV-003（読めないデータを作らない）。
- 試験：過去の全バージョンの試験のベクトルを今のコードで読む。
- 監視：段ごとの組の指標、自動の戻しの記録（[observability.md](../architecture/observability.md) の 6 節）。
