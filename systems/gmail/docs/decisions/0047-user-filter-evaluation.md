# ADR-0047: フィルターの条件は、検索の IR のうち配送の時に決まる節だけにする。配送の時に、組織の規則と選別の点の後、判定の上書きの前に、すべてのフィルターを作った順に評価し、当たったものの動作を決めた優先で合わせる。語の一致は検索と同じ語の分け方で 1 回だけ分ける。迷惑メールの箱のメッセージにはラベル・転送・不在の返信を当てない。Sieve を中の形式に使わない。1 アカウント 1,000 まで

詳細は [filters-forwarding-and-automation.md](../architecture/filters-forwarding-and-automation.md) の 4 節。

## Context

- [ADR-0001](0001-platform-and-stack.md) は、検索の文法と IR をフィルターと共有すると決めた。利用者は「この検索の結果にフィルターを作る」で条件を作る。検索の結果とフィルターの当たりがずれると、利用者は理由が分からない。
- 検索の IR には、配送の時には決まらない節（ラベル、既読、相対の日付）がある。
- 利用者のフィルターの「迷惑メールにしない」「迷惑メールにする」は、選別の上書きの決定表 DT-FLT-001 の入力になる（[ADR-0022](0022-verdict-score-composition-and-overrides.md)）。フィルターの評価は、選別の点の後で、上書きの前でなければならない。
- 本家のフィルターの数の上限と、複数が当たったときの順序は確かめられなかった（**未検証**）。
- Sieve（RFC 5228）は公開の標準のフィルターの言語だが、条件の意味が検索の文法と違う。

## Options

1. **検索の IR の配送の時の部分を条件にし、全部を評価して決めた優先で合わせる**
2. 作った順に評価し、最初に当たったもので止める
3. Sieve を中の形式にし、画面の条件を Sieve に変える

## Decision

1 を採用する。

- 条件は、`Text`・`Addr`・`subject:`・`filename:`・`has:attachment`・`larger:`・`smaller:`・`list:`・否定・AND・OR・`AROUND` だけ。状態と時刻の節は保存の時に拒む。
- 順序：組織の配送の規則 → 選別の点 → フィルター（全部）→ 上書き（DT-FLT-001）→ 最後の判定 → 動作。判定が `spam`・`spam_phish`・`quarantine` なら、フィルターの他の動作・転送・不在の返信を当てない。
- 合わせ（DT-FILT-001）：`trash` が最優先、`neverSpam` は `alwaysSpam` に勝つ、`neverImportant` は `markImportant` に勝つ、ラベルは全部、転送は 5 先まで。
- 語の一致は、配送の時にメッセージの語を検索と同じ `analyzer_version` で 1 回分け、手元の表で全部のフィルターを当てる。1 通の予算は CPU 20ms。
- 1 アカウント 1,000、IR の節 256。既存のメールへの適用は検索で行い、転送は当てない。

### 他の案を選ばなかった理由

- **2**：「請求書にスター」と「取引先にラベル」のような独立したフィルターが、両方当たらなくなる。順序の入れ替えで結果が変わり、利用者に分かりにくい。
- **3**：検索の文法との一致を保てない。Sieve の読み込みと書き出しは MVP の後に、IR との変換として足す。

## Consequences

- 良くなること：
  - フィルターの当たりが、同じ条件の検索の結果と一致する。
  - 迷惑メールが転送や不在の返信の引き金にならない。
- 引き受けるコスト：
  - 状態や時刻の条件のフィルター（「未読のまま 7 日」）を作れない。
  - フィルターが多いアカウントの配送の CPU が増える（予算で止める）。

- 表駆動テスト：DT-FILT-001。
- 監視：予算超えの数、評価の p99。
