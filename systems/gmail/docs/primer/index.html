メールのサービスは何をするか

Gmail は、メールを受け取って保存し、探しやすく見せ、利用者の代わりに外へ送るサービスです。個人の無料のアカウントと、組織向けの Google Workspace があります。メールは、他社のサーバーと標準のプロトコルでつながる、開いた網の上で動きます。相手を選べないことが、迷惑メールとなりすましの根にあります。

個人の利用者

スマートフォンが主です。通販・行政・金融のメールを受け、フィッシングに狙われます。

組織の利用者と管理者

自社のドメイン、別名とグループ、配送の規則、SSO、監査ログを使います。

法務・監査の担当

訴訟や監査のために、メールを保留し、横断して探し、書き出します。

外部の送信者と MTA

本システムへメールを送る事業者と、他社のメールのサーバーです。認証の設定を求められます。

設計の S1 は 100 万アカウント（個人 80 万、組織 2,000・20 万人）です。受け付けは 1 日 6,000 万通（ピーク 2,500 通/秒）で、申し出は 1.5 億通。その 6 割を SMTP の会話の中で断る見込みです。識別子は本家の名前を使わず、<brand>.<domain>・X-<Brand>-... のように書きます。

設計で効くところ：6 つの価値（失わない、すぐ届く、守る、届く、見つかる、どの端末でも同じ）と法務の確認待ち（L1〜L10）は intent.md、規模の段階と本家との意図した違いは architecture/README.md の 1.4・2 節。

メールの通り道と SMTP の会話

メールは、書く道具（MUA）から投稿の受け口（MSA）へ渡り、MTA から相手の MTA へ SMTP で運ばれ、MDA がメールボックスに入れます。送り手の MTA は、宛先のドメインの MX レコードを引いて、相手の受け口を知ります。

flowchart LR
  A["MUA 送り手のアプリ"] -- "submission 587 465" --> B["MSA と送信の MTA"]
  B -- "DNS で MX を引く" --> D[("DNS")]
  B -- "SMTP 25" --> C["受信の MTA mx1 優先度 10"]
  C --> E["MDA メールボックスへ"]
  E --> F["MUA 受け手のアプリ IMAP JMAP"]
  1. 送り手の MTA がポート 25 に TCP でつなぐ。受け手は 220 mx1.<brand>.<domain> ESMTP と挨拶する。
  2. EHLO で名乗る。受け手は 250 と、使える拡張（SIZE・STARTTLS・PIPELINING など）を返す。
  3. STARTTLS で TLS に切り替え、もう一度 EHLO する。
  4. MAIL FROM:<bounce@shop.example>：封筒の送り手。受け手はここで SPF の評価を始める。
  5. RCPT TO:<taro@<brand>.<domain>>：宛先ごとに 1 回。ない宛先は 550 5.1.1。
  6. DATA に 354。ヘッダーと本文を送り、<CRLF>.<CRLF> で終える。
  7. 受け手が 250 2.0.0 OK（受け付け）、4xx（後で送り直して）、5xx（恒久の拒否）のどれかを返す。QUIT で切る。

応答の先頭の数字は、2 が成功、4 が一時の失敗、5 が恒久の失敗です。5.1.1 のような拡張のコード（RFC 3463）が理由を細かく示します。

設計で効くところ：inbound-smtp.md の 4 節（mx1 と大阪の mx2）・5 節（ステートマシン、出す拡張、時間切れ）、主要な流れ A・B は architecture/README.md の 1.3 節。

封筒とヘッダー、受け付けと不達

メールには送り手が 2 つあります。SMTP の MAIL FROM（封筒）と、本文の頭の From: ヘッダーです。利用者の画面に出るのは From: で、不達の通知が返るのは MAIL FROM です。2 つは違ってよく、メールの配信の事業者を使うと普通に違います。

封筒（RFC 5321）

MAIL FROM:<bounce-8812@esp.example>
不達の返し先。受け手は Return-Path: として残す。SPF が確かめるのはこちら。

ヘッダー（RFC 5322）

From: お店 <news@shop.example>
画面に出る差出人。送り手が自由に書ける。DMARC が守るのはこちら。

受け付けた後：250 を返した受け手は、メールを届けるか、届けられないことを知らせる責任を負います（RFC 5321 の 6.1 節）。送り手の MTA は 4xx なら待ち行列に戻して間隔を広げて送り直し、5xx か期限切れなら DSN（不達の通知、RFC 3464）を MAIL FROM へ返します。DSN 自身は空の MAIL FROM:<> で送り、通知の通知の連鎖を防ぎます。

本システムの送信は、1 分・5 分・15 分・30 分・1 時間・2 時間、以後 4 時間ごとに送り直し、5 日で諦めます。24 時間で終わらなければ「遅れ」の DSN を 1 回出します。

相手の MX が 250 2.0.0 OK を返しました。これで分かることは？

250 は「受け付けた」の意味です。どの箱に入るかは、受け付けた後の選別で決まります。設計は、250 をスプール（S3）と配送の待ち行列（SQS）の両方に確定してからだけ返し、確定できなければ 451 を返して送り直させます（ADR-0002・ADR-0011）。

設計で効くところ：250 の意味と後方散乱の抑えは ADR-0002、再試行と DSN は outbound-smtp-and-reputation.md の 7・8 節、確定と掃除は ADR-0011。カレンダーの招待をメールで運ぶ話は Google カレンダーの資料。

経路の暗号化：STARTTLS・MTA-STS・TLS-RPT

MTA の間の SMTP は、平文で始まり、STARTTLS で TLS に上がります。公開の MX は、TLS を求めてはいけません（RFC 3207 の 4 節）。そのため、途中の攻撃者が STARTTLS の表示を消すと、送り手は気づかず平文で送ります（格下げの攻撃）。

MTA-STS（RFC 8461）は、受け手のドメインが「TLS で、この名前の MX にだけ送って」と宣言する仕組みです。_mta-sts.<domain> の TXT で方針のバージョンの id を出し、https://mta-sts.<domain>/.well-known/mta-sts.txt に mode（testing・enforce）、mx、max_age を置きます。送り手は方針を max_age の間覚え、enforce なら証明書の検証が通らない MX へ送りません。

TLS-RPT（RFC 8460）は、送り手が「TLS で送れなかった件数と理由」を毎日まとめて受け手へ報告する仕組みです。_smtp._tls.<domain> の TXT に送り先（rua）を書きます。enforce に上げる前に、testing で失敗がないことを確かめる材料になります。

受信は平文も受けます。本システムのドメインの MTA-STS は testing（max_age 1 日）から始め、TLS-RPT で失敗の率を見て enforce（7 日、14 日）へ上げます。MX を変えるときは、新しい MX を方針に足し、古い max_age が過ぎてから切り替えます。送信は相手の MTA-STS を守ります。DANE は MVP の後です。

設計で効くところ：ADR-0012、inbound-smtp.md の 7 節、送信の側は outbound-smtp-and-reputation.md の 6.3〜6.5 節。

送信者の認証 1：SPF と DKIM

SMTP には、送り手が本物かを確かめる仕組みがもともとありません。そこで DNS に送り手の情報を置き、受け手が照らします。SPF は「どの IP から送ってよいか」、DKIM は「このドメインが署名した内容が変わっていないか」を確かめます。

MAIL FROM のドメインの TXT（例：v=spf1 include:_spf.esp.example mx -all）に、送ってよい IP を書きます。受け手は接続元の IP を照らし、pass・fail・softfail・neutral・none・permerror・temperror を出します。

DNS を引く項（include・a・mx・ptr・exists・redirect）は合わせて 10 回までで、11 回目で permerror です（RFC 7208 の 4.6.4 節）。答えのない照会は 2 回までです。配信の事業者の include を重ねると、すぐ上限に当たります。

送り手の MTA が、ヘッダーと本文のハッシュに秘密の鍵で署名し、DKIM-Signature ヘッダーを足します。d= は署名したドメイン、s= はセレクター、h= は署名に含めたヘッダーの一覧です。受け手は <s>._domainkey.<d> の TXT から公開鍵を取って検証します（RFC 6376）。

経路の IP に依らないので、転送しても通ります。ただし件名や本文を書き換えると壊れます。l=（本文の長さ）付きの署名は、署名の外に文を足せるので、設計は DMARC の揃いに使いません。

SPF の結果だけで SMTP の時点で拒みません。DKIM は 1 通あたり 5 つの署名まで検証し、rsa-sha256 と ed25519-sha256 を受け、rsa-sha1 は fail にします。結果は Authentication-Results（RFC 8601）に書き、Web とアプリは本システムが付けたものだけを信じます。

設計で効くところ：sender-authentication.md の 4 節（評価の順）・5.1〜5.2 節（10 回の上限の例）・5.5 節、ADR-0014、署名の鍵の交換は ADR-0016。

送信者の認証 2：DMARC の揃いと方針

SPF も DKIM も、画面に出る From: を見ていません。DMARC は、SPF か DKIM で確かめたドメインが From のドメインと揃うことを求め、揃わないときの扱いを From のドメインの持ち主が _dmarc.<domain> の TXT で宣言します。

  • 揃い：SPF が pass で MAIL FROM のドメインが From と揃うか、DKIM が pass で d= が From と揃うか。どちらか 1 つで DMARC は pass。既定（r）は同じ組織のドメインなら揃い、s は名前の完全な一致。
  • 方針：p=none（見るだけ）、quarantine（迷惑メールへ）、reject（拒む）。設計は quarantine の失敗を迷惑メールの箱へ、reject の失敗を、ARC で救えなければ SMTP の時点で 550 5.7.26 にします（決定表 DT-AUTH-001）。
  • DMARCbis：設計の文書は、2026 年 5 月に RFC 9989 が出て RFC 7489 を置き換えたと確かめています（2026-10-10）。組織のドメインを公開接尾辞の一覧でなく DNS の木の歩き（最大 8 回の照会）で決め、pct を除き、t・np・psd を足しました。設計は t=y を 1 段弱く当て、古い pct=0 を t=y とみなし、一覧での結果を 90 日のあいだ影で比べます。

SPF が pass でした。画面の差出人（From:）は本物だと言えますか？

攻撃者は自分のドメインを MAIL FROM に使えば SPF を pass にでき、From には銀行の名前を書けます。From を守るのは、揃いを求める DMARC です。設計も、やりとりのある相手として甘く見るのは DMARC の pass のときだけです（ADR-0022）。

設計で効くところ：ADR-0015、sender-authentication.md の 3 節（標準の確認）・5.4 節（木の歩き、揃い、DT-AUTH-001）・8 節（集計の報告 RFC 9990 は法務の L1 の後に送る）。

転送と ARC：SPF が落ちても DMARC は通る

転送は、別の IP から送り直すので SPF を壊します。DMARC は SPF と DKIM のどちらかが揃えばよいので、本文が変わらなければ DKIM で通ります。次の例で確かめます。

  1. shop.example（DMARC p=reject）が hanako@univ.example へ送る。MAIL FROM:<bounce@shop.example>、From: info@shop.example、DKIM の d=shop.example。
  2. 大学のサーバーが、自分の IP 192.0.2.10 から本システムの hanako@<brand>.<domain> へ自動で転送する。本文と署名したヘッダーは変えない。
  3. SPF：shop.example の記録に 192.0.2.10 はない → fail。大学が SRS で MAIL FROM を自分のドメインに書き換えれば SPF は pass だが、univ.example は From と揃わない。
  4. DKIM：署名した中身は同じ → pass（d=shop.example）。
  5. DMARC：DKIM の d= が From と揃う → pass。普通に受信箱の候補になる（DT-AUTH-001 の 1 行）。
  6. もしメーリングリストが件名に [list] を足していたら、DKIM も壊れて DMARC は fail、p=reject で拒む候補になる。ここで ARC が効く。リストが受け取った時点の結果（dmarc=pass）を封印して渡し、本システムが信頼する封印者で連鎖が cv=pass なら、受け付けて「救い」の印を付ける（7 行）。
ARC は誰でも付けられる攻撃者も自分で封印できます。設計は、信頼の一覧（運用の一覧と組織ごとの一覧）の封印者の記録だけで救い、救ったメールが後で迷惑メールと報告される率が 30 日で 1% を超えた封印者は外す候補にします（ADR-0017）。

設計で効くところ：ADR-0017、sender-authentication.md の 5.3・7 節、本システムが外へ転送するときの SRS は outbound-smtp-and-reputation.md の 8.4 節、確認つきの転送は ADR-0048。

送信の評判：IP・ブロックリスト・苦情・一括の配信停止

受け手の事業者は、送り元の IP とドメインの過去の振る舞い（苦情、不達、迷惑メールの報告）から評判を付け、受け付けの速さと箱を決めます。評判の悪い IP からは、正規のメールも届かなくなります。だから本システムは、送信の IP と評判を自分で持ち、守ります。

ウォームアップ

新しい IP は実績がなく疑われます。設計は 1 日目 500 通から 14 日目 5 万通まで段で上げ、苦情 0.1% 未満・不達 2% 未満・絞りの応答 5% 未満を満たした日だけ進めます。

ブロックリスト

迷惑メールを出した IP を載せる公開の一覧（DNSBL）。多くの受け手が参照します。設計は送信のすべての IP を 5 分ごとに照会します。

フィードバックループ

受け手の利用者が「迷惑メール」を押すと、事業者が ARF（RFC 5965）の報告を送り手へ返します。苦情の率を、アカウント・組織・プール・IP ごとに数えます。

大量の送信者の要件

本家は 2024-02-01 から、全員に SPF か DKIM・逆引き・TLS・迷惑メールの率 0.3% 未満を、1 日 5,000 通を超える送信者に SPF と DKIM と DMARC・From の揃い・一括の配信停止を求めます。

一括の配信停止（RFC 8058）は、List-Unsubscribe: <https://…> と List-Unsubscribe-Post: List-Unsubscribe=One-Click を付け、両方を DKIM の署名に含めます。受け手のメールのアプリは、ボタン 1 つでその URL に POST します。設計は、署名の d= が From と揃うときだけボタンを出し、利用者の代わりに URL を叩くことは法務の確認待ち（L2 の (d)）なのでフラグの裏に置きます。

設計で効くところ：outbound-smtp-and-reputation.md の 5 節（プールとウォームアップ）・9 節（FBL とブロックリスト）・10〜11 節（送信の上限と乗っ取り）、ADR-0018・0020・0021、配信停止のボタンは sender-authentication.md の 10 節、運用は runbooks/ip-blocklisted.md。

迷惑メールの選別：層と対数オッズ

選別は 1 つの判定器ではなく、層の重ねです。規則（ヘッダーの形、認証の結果）、評判（IP・ドメイン・URL・添付のハッシュ）、内容の分類器、添付と URL の検査が、それぞれ証拠を出します。設計は各層の証拠を対数オッズの寄与 w にし、足して確率に戻します。

S = b + Σ w        （b は事前。迷惑メール −3.0、フィッシング −5.0）
p = 1 / (1 + e^(−S))

独立した証拠は、オッズの掛け算、つまり対数オッズの足し算で合わさります。設計の例 1（宅配の不在を装うメール）は、フィッシングの頭で −5.0 + 0.4 + 1.2 + 3.8 + 2.0 + 2.8 = 5.2、p ≈ 0.994 で、閾値 0.80 を超えて迷惑メールの箱へ入り、警告の帯が付きます。

偽陽性（誤判定）

取引先の請求書や本人の確認のメールが迷惑メールに入る。利用者は気づかず損をする。目標 0.05% 以下。

偽陰性（見逃し）

フィッシングが受信箱に届く。1 通開くだけで被害になる。捕捉の目標 99.9% 以上。

250 を返して受け付けた後、分類器が迷惑メールと判定しました。どうしますか？

迷惑メールの MAIL FROM の多くは偽で、DSN は無関係の第三者に届きます（後方散乱）。捨てると誤判定を利用者が取り戻せません。拒むなら、SMTP の会話の中で、安く確かなものだけを 5xx で拒みます（ADR-0002）。

設計で効くところ：spam-and-abuse-filtering.md の 4 節（層と予算）・5 節（寄与の表、閾値 DT-FLT-002、例）・6 節（評判の数え）、ADR-0022、添付と URL は attachment-and-url-scanning.md。投稿のモデレーションと比べるなら X の資料。

通信の秘密と、機械が中身を読むこと

電気通信事業法の第 4 条は通信の秘密を守ります。本システムはメールの事業者として、これを守る立場にあると見込みます。通信の秘密は中身だけでなく、宛先・日時・接続元のような通信の構成の要素にも及ぶと説明されることが多いです。選別・索引・スレッド化は、機械で中身を読まないとできません。

  • 総務省の「同意取得の在り方に関する参照文書」は、2006 年の懇談会の整理を引き、迷惑メール等のフィルタリングは 5 つの条件（いつでも設定を変えられる、同意の有無で他の提供の条件を変えない、内容を明確に限る、通常の利用者なら同意すると合理的に推定できる、事前に十分に説明する）を満たせば、約款等による同意でも有効と考えられるとします。
  • 総務省の「DMARC導入に関する法的な留意点」は、報告に本文と件名を含めないことなどを条件に挙げます。
  • 本システムへの当てはめは、どれも法務の確認待ち（L1）です。結論まで、選別の既定の有効化・送信の内容の選別・索引の spec を承認しません。
設計の境界（ADR-0008）データを C1（接続の情報）・C2（中身から作った戻せない特徴）・C3（中身そのもの）に分けます。C3 は選別の処理のメモリーの中だけで機械が読み、ログやメトリクスに出しません。人が中身を見るのは、利用者が同意して出した報告のサンプルだけです。学習は C2 と同意のあるサンプルで行い、選別を止める設定も持ちます。

設計で効くところ：ADR-0008、intent.md の「法務の確認待ち」（L1〜L10。特定電子メール法は L2、個人情報保護法は L3、捜査機関への対応は L4、消去の期限は L6）と出典、spam-and-abuse-filtering.md の 4.4 節（区分の型）、ADR-0067。

メッセージの形：RFC 5322・MIME・日本の文字コード

メッセージは、ヘッダーの行の並び、空行、本文です（RFC 5322）。添付や HTML は MIME で、本文をパートの木にして表します。日本のメールには、古い文字コードと encoded-word が今も多く残ります。

JVBERi0xLjcK...

  • multipart/mixed：本文と添付を並べる。boundary の行で区切る。
    • multipart/alternative：同じ内容の別の表し方。アプリは表示できる最後のもの（HTML）を選ぶ。
      • text/plain（ISO-2022-JP、7bit）
      • text/html（UTF-8、quoted-printable）
    • application/pdf：添付。名前は RFC 2231 の形で 見積書.pdf。

Content-Transfer-Encoding は、8 ビットのデータを 7 ビットの経路に通すための包み方です（base64・quoted-printable）。文字コード（charset）とは別の層です。

ヘッダーは ASCII が原則なので、日本語は =?文字コード?B か Q?中身?= の encoded-word にします（RFC 2047）。上の件名は base64 を戻すと ESC $ B … ESC ( B の ISO-2022-JP のバイトで、見積もりのご依頼 になります。

RFC 2047 は 1 つの encoded-word で文字を分けることを禁じますが、守らないアプリがあります。=?UTF-8?B?6KuL5g==?= =?UTF-8?B?sYLmm7g=?= は、1 つずつでは 求 のバイトが途中で切れています。設計は同じ文字コードの隣をバイトで繋いでから復号し、請求書 を得ます。

  • Shift_JIS は実際には Windows の CP932 で、丸数字（①）や拡張の漢字を含みます。ISO-2022-JP と宣言して CP932 の文字や 8 ビットのバイトを送るアプリもあります。
  • 波ダッシュ（〜 と ～）は、変換の表によって別の文字になります。検索では 1 つに畳みます。
  • 携帯の事業者の古いアドレスには taro..yamada@ のような RFC に合わないローカル部が残ります。捨てずに受け取った形のまま扱います。

設計で効くところ：message-parsing-and-storage.md の 5 節（解析の上限）・6 節（ラベルの表、推定、encoded-word の結合、RFC 2231、携帯のアドレス）、ADR-0029。HTML を安全に見せる話は ADR-0044。

保存：blob とメタデータ、同じ配送の中だけの共有

受け取ったバイトは、そのまま返せる必要があります。DKIM の検証、IMAP の BODY[]、EML の書き出し、eDiscovery が同じバイトを求めるからです。設計は、生のメッセージを変わらない blob（S3）に置き、頻繁に変わる状態（ラベル・既読・スレッド）をメタデータ（Aurora）に置きます。

blob（S3）

受け取ったヘッダーと本文。zstd で 256 KiB ごとに圧縮し、blob ごとの鍵で暗号化。1 日を過ぎた小さな blob は 64 MiB のパックに詰め直す。

メタデータ（Aurora）

受け手ごとの行。前置きのヘッダー（Received・Authentication-Results）、パートの木、件名、ラベル、旗、スレッド、modseq。

重複排除の範囲：組織の全員へのメールは、同じ本文が数千人に届きます。設計は、同じ配送（1 つの SMTP のトランザクション、1 回の送信）の受け手の間でだけ blob を共有します。中身のハッシュでメッセージをまたいで共有すると、容量や消去の振る舞いから「同じ中身を誰かが持っている」ことが漏れうるからです。この論点は Dropbox の資料と同じです。

消すとき：blob は、メールボックスの行・保留・送信の待ちの参照がすべて 0 になってから消します。鍵の破棄は 24 時間以内、物理の消去は 7 日の猶予の後です。

設計で効くところ：ADR-0003、message-parsing-and-storage.md の 4・7・8 節、形式は ADR-0030、参照と GC は ADR-0031、配る形は ADR-0032。

ラベルとフォルダー

多くのメールのアプリはフォルダーで整理します。メッセージは 1 つのフォルダーにだけ入ります。本家はラベルを使い、1 つのメッセージに複数のラベルを付けられます。設計はラベルを正のモデルにし、フォルダーは「ラベルを 1 つだけ持つ」見せ方にします。

操作ラベルのモデルでの意味
受信箱・送信済み・迷惑メール・ゴミ箱システムのラベル（INBOX・SENT・SPAM・TRASH など）。未読はラベルでなく旗
アーカイブINBOX を外す。ラベルのないメッセージは「すべてのメール」にだけ見える
迷惑メール・ゴミ箱へ互いに排他。付けると INBOX を外し、他のラベルの一覧から隠す
IMAP の COPY・MOVE・EXPUNGEラベルを足す・付け替える・その箱のラベルを外す

IMAP のアプリで、受信箱のメールを「仕事」の箱へ COPY しました。サーバーでは何が起きますか？

ラベルはフォルダーではありません。写しを作ると、既読・削除を写しの間でそろえる仕組みが要り、ずれの元になります。IMAP では同じメッセージが複数の箱に見えますが、EMAILID（RFC 8474）は同じです（ADR-0004）。

設計で効くところ：ADR-0004、操作の決定表は ADR-0033、mailbox-model-labels-and-threads.md、IMAP の箱の対応は ADR-0040。

スレッド化：参照のヘッダーと件名

返信のメールは、元のメールの Message-ID を In-Reply-To と References に入れます。これを辿れば会話の木ができます。ただし返信が親より先に届く、参照を落とすアプリがある、攻撃者が他人の会話の ID を入れる、という問題があります。設計は参照のつながりと、Re:・返信:・[list] を外した件名の一致で合わせます。

  1. m1 <a@x>「見積もりのご依頼」が届く。参照なし → 新しいスレッド T1。
  2. 返信の返信 m3 が先に届く。References: <a@x> <b@y>、件名「Re: 見積もりのご依頼」。<a@x> が T1 にあり件名が同じ → T1 へ。まだ届いていない <b@y> は仮の節として T1 に置く。
  3. 遅れて m2 <b@y>「RE: 見積もりのご依頼」が届く。T1 の仮の節で件名が同じ → T1 へ。届く順に依らず同じ形になる。
  4. m4 は <a@x> を参照するが、件名が「請求書の件」→ 新しいスレッド T2（件名が変わると分かれる）。
  5. 参照のない自動の通知は、同じ差出人・同じ件名・7 日以内なら同じスレッドへ。100 通に達したら新しいスレッドを始める。

一度同じスレッドにしたメッセージを、後から自動で分けることはしません。別々のスレッドが 1 つに合わさることはあります。認証に失敗し、そのスレッドに初めて出る差出人のドメインからのメッセージには「確かめられていない」の印を付け、会話の乗っ取りを見えるようにします。

設計で効くところ：合わせの規則の表は ADR-0005、合わせの実装は ADR-0034、収束の性質ベーステストは quality.md の 2.2.1 節 D。

同期：IMAP と JMAP

Web・アプリ・既存のメールのアプリが同じ状態を見るには、差分の取り方が要ります。手元の状態からの変化だけを取らないと、数万通の箱を毎回読み直すことになります。

IMAP（IMAP4rev2、RFC 9051）は箱ごとに UID を振ります。UID は箱の中で増える一方で、再利用しません。UIDVALIDITY が変わったら、手元の UID はすべて捨てます。

CONDSTORE・QRESYNC（RFC 7162）は各メッセージに MODSEQ を付けます。アプリが「UIDVALIDITY と、前に見た MODSEQ」を渡すと、サーバーは変わったメッセージと消えた UID（VANISHED）だけを返します。IDLE で変化を待ちます。

JMAP（RFC 8620・8621）は HTTP の上の JSON の API です。型ごとの状態の文字列を持ち、Email/changes に sinceState を渡すと、created・updated・destroyed と newState が返ります。古すぎる状態には cannotCalculateChanges を返し、取り直させます。変化の合図は EventSource か WebSocket で届きます。

メッセージは mailboxIds の集合を持つので、ラベルをそのまま表せます。

アカウントごとに 1 本の modseq を持ち、mailstore だけが、変更と同じトランザクションで 1 つ進めて change log に書きます。JMAP の状態の文字列も IMAP の MODSEQ もここから作ります。change log の保持は 30 日です。考え方は Linear の資料の 1 本の順序と同じです。

2 つのスレッドを 1 つに合わせます。移るメッセージの threadId はどう扱いますか？

RFC 8621 は threadId を変わらない性質とし、RFC 8474 も一度知らせた THREADID を変えないとします。クライアントは ID を鍵に手元を作るので、黙って変わると表示が崩れます。設計は object_gen を進めて作り直し、IMAP では古い UID の VANISHED と新しい UID で届けます（ADR-0005 の注記、ADR-0034）。

設計で効くところ：ADR-0006、client-sync-and-protocols.md の 5 節（Email/changes の例）・7.4 節（複数のラベルを持つメッセージの UID の例）、ADR-0039・0041。

検索：日本語の 2-gram

日本語は語の間に空白がないので、英語のように空白で語に分けられません。分け方は 2 つあります。辞書で語を切る形態素解析と、決まった長さの文字の並びで切る N-gram です。設計は、取りこぼしの少ない 2-gram を使います。

本文の「2026年9月分の請求書を送付します」索引に入る語（位置）
月分の請求書を送付します（日本語の連なり）月分(3)、分の(4)、の請(5)、請求(6)、求書(7)、…、ます(13)、最後の 1 文字 す(14)
検索の「請求書」請求(p) と 求書(p+1) が続けて現れる所 → 位置 6・7 で当たる
  • 2-gram は辞書にない新語や社名も拾えますが、索引が大きくなり、「京都」で「東京都」にも当たる、のような誤りの当たりが出ます。形態素との併用は search-index-poc で決めます。
  • 全角と半角は NFKC で揃え、波ダッシュの類は 1 つに畳みます。ひらがなとカタカナは揃えません。
  • 索引はアカウントごとの変わらないセグメントです。ラベルや既読のように変わる状態は索引に入れず、change log から作るビットマップで当てます。

設計で効くところ：search.md の 4 節（正規化と CJK の分け方）・5 節（演算子と IR、フィルターと共有）・7 節（状態のビットマップ）、ADR-0009。N-gram と形態素の比べは X の資料にもあります。

保持・保留・eDiscovery

組織は、法令や社内の規程のために、メールを決めた期間残し、期間の後に消す必要があります。訴訟や監査が始まると、関係する人のメールを消さずに守り（保留、リーガルホールド）、横断して探して書き出します（eDiscovery）。

保持の規則

範囲（組織・OU・アカウント）× ラベルの条件 × 受け付けからの日数。期間の後に消すか残すかを選ぶ。複数の規則は最も長いものが勝つ。

保留

案件（matter）の範囲で置く。規則より常に強い。利用者が完全に削除しても、保留が外れるまで消えない。利用者には見せない。

eDiscovery

担当は割り当てられた案件の範囲だけを検索する。閲覧と書き出しは別の権限で、すべての操作をハッシュの鎖の監査ログに残す。

設計は、保留を「消す時」に評価します。当たるメッセージは、メールボックスの行を preserved_messages に移し、blob に保留の参照を足します。保留を置く費用が範囲の大きさに依らない形です。消去の期限（L6）と捜査機関への対応（L4）は法務の確認待ちです。

設計で効くところ：retention-and-ediscovery.md の 4 節（規則と保留、決定表 DT-RET-001）・6〜7 節（案件、検索と書き出し）、ADR-0053・0054、鍵の破棄との関係は ADR-0060。

用語集

MUA
Mail User Agent。利用者がメールを書き、読むアプリ（Web、スマートフォンのアプリ、Thunderbird など）。
MSA
Mail Submission Agent。利用者の投稿を、認証してから受け付ける口。ポート 587（STARTTLS）か 465（最初から TLS）。
MTA
Mail Transfer Agent。SMTP でメールを次の MTA へ運ぶサーバー。
MDA
Mail Delivery Agent。受け取ったメールを利用者のメールボックスに入れる役。設計では mailstore.deliver に当たる。
MX レコード
ドメインのメールを受ける MTA の名前と優先度を示す DNS のレコード。数の小さいほうを先に試す。
SMTP
Simple Mail Transfer Protocol（RFC 5321）。MTA の間でメールを運ぶ、コマンドと応答のコードの会話。
封筒
SMTP の MAIL FROM と RCPT TO。ヘッダーの From・To とは別で、配送と不達の返し先に使う。
待ち行列
送れなかったメールを置き、時間を置いて送り直すための列。間隔を広げながら再試行し、期限で諦める。
DSN
Delivery Status Notification（RFC 3464）。届かなかった・遅れていることを送り手へ知らせるメール。空の MAIL FROM で送る。
後方散乱
偽の MAIL FROM へ返った不達の通知。無関係の第三者に届き、返した側が迷惑メールの送り手になる。
STARTTLS
平文で始めた SMTP の接続を、途中から TLS に切り替えるコマンド（RFC 3207）。
MTA-STS
受け手のドメインが、TLS と決めた MX への配送を求める方針を HTTPS で公開する仕組み（RFC 8461）。
TLS-RPT
送り手が TLS の失敗を受け手のドメインへ日ごとに報告する仕組み（RFC 8460）。
SPF
Sender Policy Framework（RFC 7208）。MAIL FROM のドメインが、送ってよい IP を DNS に書き、受け手が照らす。
DKIM
DomainKeys Identified Mail（RFC 6376）。ドメインがヘッダーと本文に署名し、受け手が DNS の公開鍵で検証する。
DMARC
From のドメインの持ち主が、SPF・DKIM との揃いと、揃わないときの扱いを宣言する仕組み。設計は RFC 9989 に従う。
揃い
alignment。SPF か DKIM で確かめたドメインが、From のドメインと同じ（または同じ組織のドメイン）であること。
組織のドメイン
mail.shop.example に対する shop.example のような、登録の単位のドメイン。RFC 9989 は DNS の木の歩きで決める。
ARC
Authenticated Received Chain（RFC 8617）。転送やメーリングリストが、受け取った時点の認証の結果を封印して次へ渡す仕組み。
SRS
Sender Rewriting Scheme。転送の時に MAIL FROM を転送する側のドメインに書き換え、転送の先の SPF を通す方式。
ウォームアップ
新しい送信の IP の量を、評判を見ながら日ごとに段で増やすこと。
ブロックリスト
迷惑メールを送った IP やドメインを載せる公開の一覧。多くの受け手が DNS で照会する（DNSBL）。
フィードバックループ
FBL。受け手の利用者の迷惑メールの報告を、事業者が ARF（RFC 5965）の形で送り手へ返す仕組み。
一括の配信停止
RFC 8058 の one-click unsubscribe。List-Unsubscribe-Post を付け、アプリのボタン 1 つで POST して配信を止める。
対数オッズ
確率 p を log(p / (1 − p)) に直した値。独立した証拠の重みを足し算で合わせられる。
偽陽性
正規のメールを迷惑メールと誤って判定すること。その逆の見逃しが偽陰性。
通信の秘密
電気通信事業法の第 4 条などが守る、通信の中身と構成の要素の秘密。本システムへの当てはめは法務の確認待ち（L1）。
MIME
Multipurpose Internet Mail Extensions（RFC 2045〜2049）。メールに文字コード・添付・HTML・パートの木を持たせる決まり。
encoded-word
ヘッダーに ASCII 以外の文字を入れる形 =?charset?B?…?=（RFC 2047）。
ISO-2022-JP
エスケープの列で ASCII と JIS の漢字を切り替える 7 ビットの文字コード（RFC 1468）。日本のメールの古い標準。
Shift_JIS
8 ビットの日本語の文字コード。メールで使われるのは多くが Windows の拡張の CP932。
blob
受け取ったメッセージのバイトをそのまま、変えずに置いたオブジェクト。状態は持たない。
ラベル
メッセージに複数付けられる印。受信箱や迷惑メールもシステムのラベルとして持つ。
Message-ID
メッセージを一意に指すヘッダーの値。返信は In-Reply-To・References でこれを指す。
IMAP
Internet Message Access Protocol。サーバーのメールボックスを箱の単位で読み書きするプロトコル。現行は IMAP4rev2（RFC 9051）。
UID
IMAP の箱の中でメッセージに振る、増える一方の番号。UIDVALIDITY と組で意味を持つ。
CONDSTORE・QRESYNC
IMAP の拡張（RFC 7162）。MODSEQ で変わったものだけを取り、消えた UID を VANISHED で返す。
MODSEQ
変更のたびに増える番号。設計ではアカウントごとの modseq を、IMAP と JMAP の両方の差分の基にする。
JMAP
JSON Meta Application Protocol（RFC 8620・8621）。HTTP の上で、メールの取得・変更・差分・送信・プッシュを扱う標準。
状態の文字列
JMAP のサーバーが型ごとに返す、今の状態を表す不透明な文字列。*/changes にこれを渡して差分を取る。
N-gram
文を決まった長さ N の文字の並びに切る方法。2-gram は隣り合う 2 文字ずつ。
保留
リーガルホールド。訴訟や調査のために、範囲のメールを利用者が消しても残すこと。
eDiscovery
訴訟や監査のために、電子のデータを探し、保全し、書き出すこと。
