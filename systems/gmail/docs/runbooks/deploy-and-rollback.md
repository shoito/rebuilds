# Runbook: デプロイとロールバック

- Owner: Ops
- 対応するアラート: デプロイ中の自動ロールバック、デプロイの直後の SLO の悪化
- 最終確認日: 2026-10-10

方式の正本は [delivery.md](../architecture/delivery.md)（[ADR-0069](../decisions/0069-mta-drain-and-shard-schema-waves.md)、[ADR-0070](../decisions/0070-format-versions-and-model-rollout.md)）、時間帯と凍結は [README.md](README.md) の 3 節。

## 症状

- パイプラインが自動ロールバックの条件（MX の 5xx・時間切れ、DATA の終わりの 250 の p99、受信の遅れの p95、見張りのメールの欠け、同期の通知の p99、選別の誤判定の代わりの指標）で止まった。
- デプロイの直後に、上の指標か、形式の照合（blob、change log）の誤りが増えた。

## 影響

部品による。`mx-edge` の誤りは受信の遅れ（送り手が再試行する）、`mailstore` の誤りは同期と配送の遅れ、形式の誤りは読めないデータになりうる。

## 確認

1. どの部品の、どのバージョンか。デプロイの記録とフラグの変更の記録を時刻で並べる。
2. 形式・スキーマに触れる変更か（`spool_version`、blob の形式、change log、スキーマの段）。触れていれば、読む側が全台に行き渡っていたかを確かめる。
3. MTA の台の入れ替えなら、排出（421 で閉じる、確定の途中で止めない）が効いていたか。

## 対処

1. **まずフラグで戻す**（`release.*` を 0% に）。
2. **1 つ前のイメージへ戻す**。マイグレーションは広げる段だけなので、前のバージョンが今の DB で動く。縮める段の後は前へ戻さない（前へ直す）。
3. **MTA**：`mx-edge`・`mta-out` は 1 台ずつ戻す。NLB から外し、進行中の会話と配送を終えてから止める（最大 10 分）。送信の IP を持つ台は、その IP の送信を他の台へ移してから止める。
4. **書く側の形式の変更**：書く側だけを戻す。読む側は新しい形式を読み続ける（書いた分を読めなくしない）。
5. **選別のモデル・規則**：`ops.filter_model_pinned` で前のバージョンに固定する。
6. **スキーマの波**：波を止め、進んだシャードは前へ直す。見張りのシャードで先に確かめる。

## エスカレーション

- 戻しても指標が戻らない、または形式の誤りで読めないデータがある：Dev のテックリードと [incident-response.md](incident-response.md) の SEV2 以上。
- 受け付けたメールの欠けの疑い：SEV1。

## 事後

- 戻した理由を、変更の `plan.md` と振り返りに残す。自動ロールバックの条件の過不足を見直す。
- 調査結果を `changes/` の新しい `intent.md` として起票する。
