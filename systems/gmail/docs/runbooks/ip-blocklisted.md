# Runbook: 送信の IP のブロックリストへの掲載

- Owner: Ops（到達性の担当）
- 対応するアラート: 送信の IP のブロックリストへの掲載（page）。外部の事業者への到達の低下（見張りが迷惑メールの箱・不達）の一部
- 最終確認日: 2026-10-10

検知の方法は [README.md](README.md) の 5.1 節、プールと IP の範囲は [outbound-smtp-and-reputation.md](../architecture/outbound-smtp-and-reputation.md) の 5 節（[ADR-0018](../decisions/0018-outbound-ip-pools-and-warmup.md)）と [infrastructure.md](../architecture/infrastructure.md) の 3.2 節（[ADR-0063](../decisions/0063-network-byoip-ranges-and-egress.md)）。目標は NFR-012（掲載から 4 時間以内に原因の止めと解除の申請）。

## 症状

- `blocklist-monitor` が、送信のプールの IP（IPv4 は /24 の単位も、IPv6 は /64）の掲載を検知した。
- 相手のドメインの 5xx・4.7.x の応答が、評判の理由を示す文で急に増えた。

## 影響

- 掲載された IP・範囲から送ったメールが、相手で拒まれるか迷惑メールの箱に入る。共有のプール（`personal`・`org-a`）なら多くの利用者に及ぶ。
- 送信の待ちが増える（最大 5 日で DSN）。

## 確認

1. どの IP・範囲・プールか、どのブロックリストか、いつからか。
2. 掲載の直前の送信を、アカウント・組織・プールの単位で調べる（ID と数で）。苦情の率（FBL）、`hard_invalid_recipient` の率、送信の点の高い送信の割合。
3. 乗っ取りの兆し（送信の点 0.5 以上の急増、新しい宛先の割合）があるか。あれば [account-takeover.md](account-takeover.md) も並べて行う。
4. 受信の MX の IP の誤った掲載（照会の誤り）でないか。

## 対処

1. **原因の送信を止める**：原因のアカウントの送信を保留にし、`suspect` のプールへ移す。乗っ取りなら [account-takeover.md](account-takeover.md)。
2. **影響を限る**：掲載された IP を、そのプールの送信から外す（`ops.outbound_delivery_enabled` で IP ごとに止める）。同じプールの他の IP に寄せるのは、評判を広げない量に限る。相手の事業者ごとの速さを下げる。
3. **送信の待ちを守る**：止めた間の送信は待ち行列に残る（最大 5 日）。利用者には、遅れていることを画面で示す。
4. **解除を申請する**：原因を止めたことを確かめてから、ブロックリストと相手の事業者の手順に従って申請する。申請の記録を残す。
5. **戻す**：解除の後、IP をウォームアップの計画の量（14 日の段）から戻す。
- 外部の事業者・ブロックリストとの連絡は Ops と到達性の担当だけ。エージェントは調査の要約の草案まで。

## エスカレーション

- 4 時間で原因を止められない、または `personal` の /24 の全体が掲載された：Ops の責任者と Dev のテックリード。SEV2。
- 迷惑な利用者（乗っ取りでない）の送信の停止の範囲は**法務の確認待ち**（L2・L7）。

## 事後

- 原因（送信の上限、乗っ取りの検知、プールの分け方の欠け）を `changes/` の新しい `intent.md` として起票する。
- 掲載の時間を NFR-012 の月の値に足す。
