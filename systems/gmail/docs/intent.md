# Intent: Gmail を AI エージェント主体で再構築する

- Author: shoito
- Status: draft
- Date: 2026-10-10

## Problem

メールは、日本の個人と組織の連絡の土台であり続けている。取引先との連絡、サービスの登録と本人の確認、請求書と通知、行政の手続きは、今もメールを前提にしている。それなのに、利用者と組織の管理者は次のところで困る。

- **迷惑メールとフィッシングが減らない。** 宅配の不在通知、カード会社・銀行・通販を装うフィッシングは、日本語で巧妙に作られる。受け手が見分けるのは難しく、1 通を開いただけで被害になる。逆に、選別が強すぎると、取引先のメールや本人の確認のメールが迷惑メールに入り、気づかない。
- **送ったメールが届かない。** 2024 年から大手のメールの事業者が、送信者に SPF・DKIM・DMARC と一括の配信停止を求めるようになった（出典は末尾）。組織の管理者は、自社のドメインの認証の設定と、送信の評判の管理を求められるが、その仕組みを持たない。
- **メールが多すぎて探せない。** 長年のメールが数万通たまり、日本語の件名と本文から目的のメールを探せない。旧来の文字コード（ISO-2022-JP、Shift_JIS）のメールや、携帯電話の事業者のアドレスの形が、検索とスレッドの表示を崩す。
- **端末がばらばらに見える。** Web、スマートフォンのアプリ、既存のメールのアプリ（IMAP）で、既読やラベルの状態がずれる。通知が遅い、または重なる。
- **組織の要件。** 自社のドメインでのメール、別名とグループ、配送の規則、退職者のメールの保持、訴訟や監査のための保全（ホールド）と検索、管理の操作の監査ログが要る。データを国内に置くことを求められる。
- **アカウントの乗っ取り。** 乗っ取られたアカウントは、本人の連絡先へフィッシングを送る踏み台になり、サービス全体の送信の評判を落とす。

本家 Gmail は、これらを大きな規模で解いている。ラベルとスレッド（会話）、強い迷惑メールの選別、検索の演算子、IMAP、元に戻す送信、予約の送信、組織向けの Google Workspace を提供する（出典は末尾）。この題材では、これを日本の市場を最初の対象に、小さなチームと AI エージェントでどこまで作り直せるかを確かめる。核（MTA、選別のパイプライン、メールの保存、スレッド化、検索の索引、同期のプロトコル）は自分で設計する（[リポジトリ共通の ADR-0007](../../../docs/decisions/0007-no-reuse-of-original-implementation.md)）。

## Proposed outcome

個人と組織が、安心して送受信でき、すぐ見つけられ、どの端末でも同じに見えるメールのサービスを作る。次の 6 つの価値を満たす。

1. **受け付けたメールを失わない**：MX が 250 を返したメール、利用者の送信を受け付けたメールは、1 通も失わない（NFR-004）。
2. **すぐ届く**：受信は、250 から受け手の受信箱に出るまで p95 10 秒（NFR-001）。送信は、元に戻す送信の窓の後、外部の MX への最初の試行まで p95 5 秒（NFR-002）。
3. **迷惑メールとフィッシングから守る**：迷惑メールの捕捉の率 99.9% 以上、正規のメールの誤判定 0.05% 以下（NFR-008、NFR-009）。フィッシングとマルウェアは、受信箱に届く前に止める。
4. **届く**：本システムから送ったメールが、外部の主な事業者の受信箱に届く。送信の評判を、乗っ取られたアカウントや迷惑な送信者から守る（NFR-012）。
5. **見つかる**：日本語の全文と演算子（`from:`、`has:attachment`、`before:` など）の検索が p99 1 秒で返り、新しいメールは p95 10 秒で検索に出る（NFR-005）。
6. **どの端末でも同じ**：Web・アプリ・IMAP の状態が、変更から p95 2 秒で揃う（NFR-006）。

### MVP（S1）に含める

- **受信の SMTP**：MX の層（IPv4・IPv6）、STARTTLS、MTA-STS の公開と TLS-RPT の受け取り、接続の評判と速さの上限、宛先の確かめ、SMTP の時点での拒否と、受け付けた後の選別、スプールと配送の待ち行列、DSN
- **送信者の認証**：SPF・DKIM・DMARC の検査、`Authentication-Results`、ARC の検査と封印（転送）、DMARC の集計の報告の送受、送信の DKIM の署名（本システムのドメインと組織のドメイン）
- **送信の SMTP**：投稿（Web・アプリ・JMAP、SMTP の submission）、IP プールとウォームアップ、宛先のドメインごとの速さの調整、再試行と後退、DSN、外部の事業者のフィードバックループの受け取り、MTA-STS の尊重、アカウントの送信の上限と乗っ取りの検知
- **迷惑メール・フィッシング・マルウェアの選別**：規則、送信元の評判（IP、ドメイン、認証済みの識別子）、内容の分類器、URL の評判、添付の静的な検査（署名とハッシュ、隔離したタスク）、利用者の報告（迷惑メール・迷惑メールではない）、組織の隔離
- **メールの保存**：RFC 5322・MIME の解析（日本の旧来の文字コードを含む）、blob（S3）とメタデータ（Aurora）、同じ配送の受け手の間の blob の共有、圧縮と暗号化、容量（既定 15 GB）
- **メールボックスのモデル**：ラベル（システムのラベル、利用者のラベル、入れ子）、アーカイブ、既読・スター・重要、スレッド、ゴミ箱と迷惑メール（30 日で消す）、ミュート、スヌーズ
- **検索**：日本語と英語の全文、演算子、ラベル・状態での絞り込み、候補の表示
- **同期とプロトコル**：JMAP（RFC 8620・8621）を Web とアプリの API にし、変更の記録と `modseq`、Web のプッシュ（EventSource）、モバイルのプッシュ（APNs・FCM）、IMAP4rev2（CONDSTORE・QRESYNC、OAuth での認証）
- **Web のクライアント**：受信箱、スレッドの表示、作成（返信・全員に返信・転送、署名、下書きの自動保存）、元に戻す送信、予約の送信、検索、ラベル、設定、外部の画像の代理の取得
- **モバイルのアプリ**：iOS・Android（オフラインの読み書き、プッシュ）
- **フィルターと自動化**：利用者のフィルター（検索と同じ条件）、確認つきの転送、不在の自動の返信、予約の送信、元に戻す送信
- **アカウントと安全**：作成、サインイン（パスキー、パスワードと 2 段階の確認）、セッション、乗っ取りの検知と回復、第三者のアプリの OAuth、アカウントの活動の表示
- **組織**：独自のドメイン（確かめ、MX・SPF・DKIM・DMARC の案内）、利用者と組織の単位、別名、グループ（配布）、配送の規則（分けた配送、送信のゲートウェイ）、管理の監査ログ、SSO（SAML・OIDC）
- **保持と eDiscovery**：保持の規則、保留（ホールド）、横断の検索と書き出し（担当の役割と監査つき）

### MVP の後の Epic で扱う

| 機能 | 理由 |
| --- | --- |
| POP3、他社のアカウントからのメールの取り込み | IMAP と JMAP で足りる利用者が多い。取り込みは外部の認証の情報を預かる設計が要る |
| S/MIME（組織） | 鍵と証明書の配布、Web での署名と復号の設計が要る（[architecture/](architecture/README.md) の 6 節の決定） |
| 添付の動的な解析（サンドボックスでの実行） | 静的な検査で MVP の大半を止める。実行の隔離と費用の設計が要る |
| BIMI のロゴの表示 | VMC・CMC の確かめと SVG の扱いの設計が要る。MVP は記録だけ |
| 送信の DANE（RFC 7672） | DNSSEC の検証の運用が要る。日本のドメインの採用は低いと見込む（未検証） |
| 機密モード | 受け手の画面の写しを防げず、利用者に誤った安心を与える。SMS の確認は法務の L3 に当たる |
| 外部の宛先の送信の確認と保留（誤送信の対策） | 日本の組織に多い要望。組織の配送の規則の上に作る |
| 公開の REST API（第三者のアプリ向けの Gmail API の相当） | MVP は JMAP と IMAP を第三者に開く |
| 送信者向けの評判の画面（Postmaster の相当） | 外部の送信者向けの製品で、受信の側の集計の公開の設計が要る |
| 海外のリージョン | 利用者をリージョンに固定する形で足す |

### 守るべき振る舞い

- 250 を返したメール、送信の受け付けを返したメールは、配送か、DSN による通知のどちらかで必ず終わる。黙って消えない。
- 受け付けた後の迷惑メール・フィッシングの判定で、送り手に DSN を返さない（第三者への後方散乱を作らない）。
- 同じメッセージが待ち行列の読み直しで 2 回処理されても、受け手のメールボックスには 1 通だけ入る。
- 利用者は、自分のアカウントのメールだけを見られる。委任とグループの共有の受信箱は、明示の許可の範囲だけ。検索・スレッド・候補の表示・通知を含め、どの経路でも他人のメールの有無が分からない。
- 迷惑メールの判定は、利用者の操作（迷惑メールではないの報告、連絡先、フィルターの「迷惑メールにしない」）で上書きできる。ただし既知のマルウェアの添付は、利用者の設定に関わらず開かせない。
- スレッドは、同じ利用者の同じ操作の列から、どの順序でメールが届いても同じ形に収束する（ADR-0005）。
- Web・アプリ・IMAP の状態は、すべての変更を受けた後に同じになる（ADR-0006）。
- 保留の対象のメールは、利用者が「完全に削除」しても、保留が外れるまで消えない。保留のないメールは、決めた期限の中で消える（法務の L6 で期限を決める）。
- 送信の上限を超えた送信、乗っ取りの疑いでの送信の保留は、利用者に理由を示す。黙って捨てない。

## Affected users and systems

- **個人の利用者**（主な利用者）：日本の個人。スマートフォンが主で、通販・行政・金融のメールを受ける。フィッシングの被害に遭いやすい。
- **組織の利用者**：中小企業から大企業の従業員、学校。取引先とのメールが業務の中心。
- **組織の管理者**：ドメイン、利用者、別名とグループ、配送の規則、保持と保留、監査ログ、SSO を管理する。
- **法務・監査の担当（組織）**：保留と横断の検索と書き出しを行う。
- **外部の送信者**：本システムの利用者へメールを送る事業者と個人。認証の設定と一括の配信停止を求められる。
- **外部のシステム**：外部の MTA（受信・送信の相手）、DNS、外部の評判のデータ（ブロックリスト）、APNs・FCM、第三者のメールのアプリ（IMAP、JMAP、OAuth）、IdP（Microsoft Entra ID、Okta など）、組織のオンプレミスのメールのサーバー（分けた配送）。
- **社内の運用**：到達性（送信の評判）の担当、乱用の対策（迷惑な送信者の停止）、サポート、開示の請求への対応。

## Constraints

- **核を自前で設計する。** MTA、選別のパイプライン、メールの保存、スレッド化、検索の索引、同期のプロトコルは、自分で作る。汎用の MTA と検索のエンジンを核に据えない。SMTP の構文の層、MIME の解析、署名の検査型のマルウェアの検出のような汎用の部品は、理由を ADR に書いて使う（[リポジトリ共通の ADR-0007](../../../docs/decisions/0007-no-reuse-of-original-implementation.md)、[ADR-0001](decisions/0001-platform-and-stack.md)）。
- 実行基盤と技術は、rebuilds の他の題材の決定（AWS 東京・大阪、TypeScript・Hono、Aurora PostgreSQL、Valkey、S3、SQS・SNS、ECS Fargate、Terraform、OpenTelemetry、AppConfig のフラグ、FORCE RLS と `SET LOCAL`、UUIDv7、outbox）を引き継ぐ。MTA、選別、保存、検索、IMAP は、量と接続の数が多いので Rust で書く。外れるところは [ADR-0001](decisions/0001-platform-and-stack.md) に理由を書く。
- **メールの送受信に Amazon SES を使わない。** Google Calendar の題材は iMIP の送受信に SES を使う（[invitations-and-itip.md](../../google-calendar/docs/architecture/invitations-and-itip.md) の 11 節）が、この題材はメールの事業そのもので、MTA の層を自前で持つ。送信の IP とその評判を自分で持つ（[ADR-0001](decisions/0001-platform-and-stack.md)）。
- 本家の名前は識別子に使わない。ドメインは `<brand>.<domain>`、ヘッダーは `X-<Brand>-...`、IMAP の特別な箱は `[<Brand>]/...` の形で書く（[リポジトリ共通の ADR-0006](../../../docs/decisions/0006-brand-neutral-identifiers.md)）。本家の API・IMAP の拡張とそのまま互換にすることは目標にしない。
- データは日本（東京、DR は大阪）に置く。
- 日本の法令（電気通信事業法と通信の秘密、特定電子メール法、個人情報保護法など）への対応は、法務の確認を前提に設計する。結論は出さない（下の「法務の確認待ち」）。
- 規模は段階的に広げる（[architecture/](architecture/README.md) の 2 節）。

## Non-goals

| 機能 | 理由 |
| --- | --- |
| 自前のホスト（オンプレミス）での提供 | 運用の形が別になる |
| 本家の API・IMAP の拡張（`X-GM-*`）・検索の文法との完全な互換 | 振る舞いは寄せるが、名前と識別子は独自にする（リポジトリ共通の ADR-0006）。IMAP は標準の拡張（OBJECTID など）で同じ働きを出す |
| ストレージ・文書・カレンダー・チャットとの一体の製品 | メールに絞る。容量はメールだけで数える |
| 汎用の大量配信のサービス（メールマガジンの配信の基盤） | 利用者の送信の上限の中の個人と組織の送信に絞る。大量の配信は、送信の評判を壊すので断る |
| 汎用の検索のエンジンを核に据えること（OpenSearch など） | 検索は題材の核。自前で作る（[ADR-0009](decisions/0009-search-index-design.md)） |
| メールの中身を使った広告 | 通信の秘密と利用者の信頼に反する |
| 添付のファイルの zip の暗号化とパスワードの別送（いわゆる PPAP） | 安全の効果が乏しく、検査を妨げる。必要な組織は送信のゲートウェイで外部の製品を使う |

### 選定・計測で決めるもの（法務以外）

- MIME の解析のライブラリ：候補を E4 の前の `mime-parser-poc` で、日本の旧来の文字コードの壊れたメール・巨大な入れ子・ファジングの耐性で比べる（[ADR-0001](decisions/0001-platform-and-stack.md)）。
- 受信の MX と送信の MTA の 1 台あたりの接続の数とメッセージの数、BYOIP の手続き：E2 の前の `mx-throughput-poc`（[ADR-0001](decisions/0001-platform-and-stack.md)）。
- blob のパックの大きさ、zstd の水準と辞書、S3 の要求の費用：E4 の前の `blob-pack-poc`（[ADR-0003](decisions/0003-message-storage-layout-and-dedupe.md)）。
- メールボックスのシャードの大きさ（1 つの Aurora のクラスタあたりのアカウントの数）：E4 の前の `mailbox-shard-poc`（[ADR-0007](decisions/0007-tenancy-accounts-orgs-and-rls.md)）。
- 日本語の索引の 2-gram と形態素の併用の効き、索引の大きさ：E10 の前の `search-index-poc`（[ADR-0009](decisions/0009-search-index-design.md)）。
- 内容の分類器の形（勾配ブースティングと小さな言語モデル）、推論の遅れ：E6 の前の `spam-classifier-poc`（[ADR-0008](decisions/0008-spam-pipeline-boundary-and-secrecy.md)）。
- 本家の内部の選別の仕組み、スレッド化の詳しい規則、受信のメールの大きさの上限、予約の送信の上限の数、迷惑メールの率の実際の値：公式の資料で確かめられなかった（**未検証**）。本システムの値は各領域の文書で決める。
