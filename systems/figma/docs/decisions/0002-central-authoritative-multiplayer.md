# ADR-0002: 同時編集は、ファイルごとの中央のサーバーが順序を決める。プロパティ単位の LWW、分数インデックス、循環の拒否

## Context

同じファイルを複数の人が同時に編集する。満たすべきことは次のとおり。

- 自分の入力は、サーバーを待たずに画面に出る（NFR-002）。
- 他の人の編集が 250ms 以内に見え、編集が止まれば全員の画面が同じ状態に収束する（NFR-001）。
- 親子の関係に循環ができず、ノードの親は 1 つだけ（intent の「守るべき振る舞い」）。
- 権限（閲覧だけの人は書けない）を、サーバーで守れる。

デザインのファイルは、テキストの文書と違い、ノードの木とそのプロパティ（位置、大きさ、色）でできている。テキストの長い同時編集は少なく、同じテキストのノードを 2 人が同時に打つことはまれである。

本家は、OT を「状態の組み合わせが爆発し、考えにくい」として避けた。CRDT の考え方を借りつつ、ファイルごとにサーバーのプロセスを 1 つ置き、それを中央の権威にした。変更の単位はオブジェクトのプロパティで、同じプロパティの競合は最後にサーバーへ届いた値が勝つ（LWW）。子の並びは 0 と 1 の間の分数の位置で持ち、親は子のプロパティとして持つ。循環を作る変更はサーバーが拒否する。クライアントは、未確定の自分の変更と同じプロパティへのサーバーの変更を、確定まで捨てて、ちらつきを防ぐ。オブジェクトの ID にクライアントの ID を含め、サーバーを待たずに作れる（[How Figma's multiplayer technology works](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)、2019-10-16、2026-09-27 に確認）。

rebuilds の Notion は、テキストをブロックごとの CRDT（Fugue＋Peritext）で統合し、構造とプロパティをサーバーの順序で決めた（[Notion の ADR-0010](../../../notion/docs/decisions/0010-text-crdt-with-server-ordered-structure.md)）。子の並びは分数インデックスを避け、前後の兄弟をアンカーにした（[Notion の ADR-0012](../../../notion/docs/decisions/0012-child-order-by-sibling-anchors.md)）。Notion はオフラインの長い編集と、文章の同時の入力を重く見たためである。

## Options

1. **OT**：中央のサーバーが版を進め、クライアントは確定していない操作を変換して載せ直す
2. **CRDT**：ファイル全体を CRDT（Yjs、Automerge、Loro）で持ち、どの順で届いても合わさる
3. **ファイルごとの中央のサーバー＋プロパティ単位の LWW**：サーバーが順序を決め、クライアントは楽観的に当てて、確定の後に合わせ直す（本家の方式）
4. **3 に、テキストのプロパティだけ列の CRDT を足す**（Notion に近い）

## Decision

3 を採用する。詳細は [multiplayer.md](../architecture/multiplayer.md) に書く。

- **ファイルごとに持ち主の Document Server を 1 つ置く。** 持ち主は、届いた変更に、ファイルごとに増える `seq` を振る。全員が `seq` の順に当てるので、結果は 1 つに決まる。
- **変更の単位は `(node_id, property)` の値の置き換え。** 同じ単位の競合は、サーバーに後から届いた値が勝つ（LWW）。違うプロパティへの変更は競合しない。
- **ノードの ID は `(session_id, local_id)`。** `session_id` はセッションごとにサーバーが振り、`local_id` はクライアントが数える。クライアントはサーバーを待たずにノードを作れる（振り方の細部は [ADR-0007](0007-node-ids-and-tree-invariants.md)）。
- **子の並びは分数インデックス**：各ノードは `parent_index = (parent_id, position)` を 1 つのプロパティとして持つ。`position` は、前後の兄弟の鍵の間の文字列の鍵（base-62 などの可変長）。親と位置を 1 つのプロパティにするのは、親の付け替えと並びの変更を分けて LWW にすると、「新しい親に古い位置」の組み合わせが生まれるため。
  - 同じ隙間への同時の挿入で鍵が重なったら、サーバーが後から届いた方の鍵を振り直し、変更として配る。
  - 鍵が長く伸びすぎたら（48 バイトを超えたら。上限は 64 バイト）、サーバーが兄弟の鍵をまとめて振り直す（[ADR-0010](0010-ordering-keys-and-cycle-rejection.md)）。
- **循環の拒否**：`parent_index` の変更で、ノードが自分の子孫の下に入る場合、サーバーはその変更を拒否し、送り手に拒否を返す。クライアントは自分の未確定の変更を取り消す。他のクライアントで一時的に循環が見えたとき（自分の未確定の変更とサーバーの変更の組み合わせ）は、確定まで該当のノードを木から外して描く（本家と同じ）。
- **クライアントの合わせ直し（rebase）**：クライアントは、確定した状態と、未確定の自分の変更の列を持つ。サーバーの変更が届いたら、確定した状態に当て、その上に未確定の変更を載せ直す。未確定の変更と同じ単位へのサーバーの変更は、画面に出さない（自分の変更が確定すれば、どのみちそれが勝つ）。
- **検証はサーバーで**：権限、プロパティの型と範囲、木の不変条件は、`doc-model` の同じコードで、クライアントとサーバーの両方が確かめる。サーバーの判定が正である（[ADR-0001](0001-platform-and-stack.md)）。
- **テキストのノードの中身も、1 つのプロパティとして LWW にする。** 同じテキストを 2 人が同時に打つと、後に届いた方が勝つ。デザインのファイルでは、同じテキストのノードの同時の入力がまれで、テキストの CRDT の費用（墓標、書式の統合）に見合わない。まれに起きる損失は、版の履歴と Undo で戻せる。
- **オフライン**：短い切断（数分）は、未確定の変更を持ったまま再接続し、送り直す。長いオフラインの編集は MVP で扱わない。
- **Undo**：Undo は、自分の変更を打ち消す新しい変更として送る。本家の原則「たくさん Undo して、コピーして、Redo で今に戻ったとき、文書は変わっていない」を守る（上の本家の記事）。詳細は [ADR-0012](0012-multiplayer-undo-redo.md)。
- 1 を採らない理由：本家と同じく、ノードの木とプロパティの変換関数の組み合わせが多く、正しさを確かめにくい。中央のサーバーがあるなら、プロパティ単位の LWW で足りる。
- 2 を採らない理由：CRDT は定義上どの変更も受け入れるので、サーバーが循環や権限に反する変更を拒否できない。分散した複製（P2P、長いオフライン）のための費用（墓標、メタデータ）を、中央のサーバーがある構成で払う意味が薄い。
- 4 を採らない理由：上の「テキストのノードの中身」のとおり、費用に見合わない。利用者の声でテキストの損失が問題になったら、テキストのプロパティだけ列の CRDT に替える ADR を書く。その場合も、構造とプロパティは 3 のままにする（Notion の形）。

### Notion との比較

| 項目 | Figma（この ADR） | Notion（ADR-0010〜0012） |
| --- | --- | --- |
| 中央の順序 | ファイルごとのプロセスがメモリで `seq` を振る | ページごとの `seq` を DB の行のロックで振る |
| テキスト | プロパティとして LWW | ブロックごとの CRDT（Fugue＋Peritext） |
| 子の並び | 分数インデックス。サーバーが重なりを振り直す | 前後の兄弟のアンカー。分数インデックスは使わない |
| オフライン | 短い切断だけ | 長いオフラインの編集を統合する |
| 変更の置き場所 | メモリ＋ジャーナル＋チェックポイント（[ADR-0003](0003-journal-and-checkpoints.md)） | Aurora の操作のログとブロックの表 |

分数インデックスを Notion が避けたのは、ブロックの並び（`content`）を正本として持つ形を変えないためである。Figma は並びを子のプロパティとして持つので、並びの変更が 1 つのプロパティの LWW で閉じ、分数インデックスが合う。

## Consequences

- 良くなること：
  - 規則が少なく、性質ベーステストで収束を示しやすい。
  - 権限と木の不変条件を、サーバーで確実に守れる。
  - 変更が小さい（1 プロパティの値）。
- 悪くなること、引き受けるコスト：
  - 同じプロパティへの同時の変更では、片方が消える。テキストのノードも同じ。
  - 長いオフラインの編集はできない。
  - 1 つのファイルの処理は 1 つの持ち主に集まる。人が多いファイルはホットスポットになる（[architecture/README.md](../architecture/README.md) の 7 節）。
  - 分数インデックスの鍵の振り直しの仕組みが要る。

## Confirmation

- 性質ベーステスト：任意のクライアントの数・変更・遅延・再送の列で、全クライアントの確定した状態が、サーバーの状態と一致する。
- 性質ベーステスト：任意の `parent_index` の変更の列で、サーバーの木に循環がなく、全ノードの親が 1 つである。
- 性質ベーステスト：任意の挿入の列で、分数インデックスの鍵が兄弟の中で一意で、長さが上限を超えない。
- 結合テスト：閲覧だけの権限の接続から送った変更を、サーバーが拒否する。
