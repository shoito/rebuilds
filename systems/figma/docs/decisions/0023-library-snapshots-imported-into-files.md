# ADR-0023: ライブラリは公開の時点の不変のスナップショットで配り、使う側のファイルに写しを取り込む。ファイルをまたぐ生の参照はしない

## Context

ライブラリ（MVP の後）は、あるファイルのコンポーネント・スタイル・変数を公開し、他のファイルで使えるようにする。本家では、公開には有料のプランと Full のシート、元のファイルの編集の権限が要る。更新は使う側のファイルに通知され、編集の権限を持つ人が受け入れるまで当たらない（[Publish a library](https://help.figma.com/hc/en-us/articles/360025508373-Publish-a-library)、[Review and accept library updates](https://help.figma.com/hc/en-us/articles/360039234193-Review-and-accept-library-updates)）。コンポーネントは一意の ID で、インスタンスとのつながりを保つ（[Move published components](https://help.figma.com/hc/en-us/articles/4404848314647-Move-published-components)）。いずれも 2026-09-27 に確認。

満たすべきことは次のとおり。

- ファイルは、他のファイルを読まずに開いて描ける。開く時間（NFR-003）に、ライブラリのファイルの読み込みを足さない。
- 更新を受け入れても、上書きが残る（[ADR-0021](0021-derived-instances-and-override-keys.md)）。
- 版の履歴で過去の版を開くと、その時点の部品の形で描ける。
- ライブラリへの権限と、使う側のファイルの権限を、描画のたびに組み合わせて判定しなくて済む。

## Options

1. **スナップショットと写し**：公開の時点で資産ごとに不変の blob を作り、使う側のファイルに写しとして取り込む。更新は受け入れで写しを置き換える
2. **生の参照**：使う側のインスタンスが、ライブラリのファイルの今のメインを直接指す。開くときにライブラリのファイルも読む
3. **公開した版を参照する**：使う側は `(asset_key, version)` だけを持ち、描くときに blob を読む（写しをファイルに入れない）

## Decision

1 を採用する。詳細は [components-and-libraries.md](../architecture/components-and-libraries.md) の 7 節。

- 公開は Worker の job で行う。`seq` の時点の木から資産ごとの部分木を直列化し、中身のハッシュが変わった資産だけ blob を作る。版と資産の一覧は Aurora に書く。
- 資産の鍵 `publish_key` は、最初の公開で元のコンポーネントに振る 128 ビットの乱数。移動・名前の変更で変わらない。
- 使う側は、資産の blob を API（判定を通す）から受け取り、ファイルの隠れた領域に写しとして取り込む。写しのノードの ID は `(asset_key, source_node_id)` から決定的に作る。版をまたいで ID が同じなので、上書きが残る。
- 更新は、Realtime で「更新あり」を知らせる。受け入れは、写しを新しい版に置き換える通常の変更として、マルチプレイヤーの経路で送る。
- ライブラリへの権限を失っても、取り込んだ写しは残る。
- 2 を採らない理由：
  - 開くたびに、ライブラリのファイル（大きなデザインシステムは数十 MB）を読む。複数のライブラリを使えば、さらに増える。
  - ライブラリの編集が、受け入れの前に使う側に当たる。本家の「受け入れるまで当たらない」と合わない。
  - 描くたびに、見る人がライブラリを読めるかの判定が要る。読めない人の画面で部品が欠ける。
  - 過去の版を開くと、今の部品で描かれる。
- 3 を採らない理由：開くときに blob の読み込みが要り、2 と同じく開く時間と判定が増える。写しに比べて得るのは、ファイルの大きさの節約だけである。

## Consequences

- 良くなること：
  - ファイルが自己完結する。開く・描く・書き出す・版の履歴を見る、のどれも、他のファイルを読まない。
  - 更新の受け入れが、Undo と版の履歴に残る。
  - Document Server は、ファイルをまたぐ読み込みを持たない（[ADR-0002](0002-central-authoritative-multiplayer.md) の「ファイルごとに持ち主は 1 つ」を崩さない）。
- 引き受けるコスト：
  - 使う側のファイルが、写しの分だけ大きくなる。ライブラリの Epic の前に、大きなデザインシステムで測る。
  - 公開した時点で、使う側へ中身を渡したことになる。権限を外しても写しは消えない。利用者への説明が要る（[permissions-and-sharing.md](../architecture/permissions-and-sharing.md) の漏洩の経路の表）。
  - 入れ子の依存の版を揃える規則（新しい方に揃える）が要る。本家の振る舞いは未検証。

## Confirmation

- 性質ベーステスト：任意のライブラリの版の列と受け入れの順で、元のノードが残る上書きは受け入れの後も残る。
- 結合テスト：ライブラリのファイルを消した後も、使う側のファイルが開けて、インスタンスが同じに描かれる。
- 結合テスト：ライブラリの公開先に入らない人に、資産の一覧と blob を返さない。
- 計測：写しの大きさがファイル全体に占める割合。
