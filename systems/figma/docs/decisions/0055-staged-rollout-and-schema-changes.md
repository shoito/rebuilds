# ADR-0055: クライアントのビルドは組織の割合で段階的に出し、適用の規則を変えるフラグはファイルごとに Document Server が決めて配る。プロパティの表の変更は「サーバー → クライアント → 書き込みの解禁」の 3 段で出す

## Context

- Slack は、フィーチャーフラグの割り当ての単位をワークスペースにし、評価済みの一覧をブートストラップで配る（[Slack の ADR-0026](../../../slack/docs/decisions/0026-feature-flags.md)）。この題材では、組織（`org_id`）が同じ単位になる。
- ただし、ファイルは組織の外の人（ゲスト、リンクを知っている人）とも共有する。**同じファイルを開いた 2 人が、違う適用の規則（検証、レイアウト、並びの鍵の振り直し）で動くと、画面が収束しない。** 利用者の組織でフラグを決めると、この組み合わせが起きる。
- UI だけのフラグ（パネル、ツール）は、人ごとに違ってもファイルの中身に影響しない。
- プロパティの表の変更は、サーバーを先に出す（[document-model.md](../architecture/document-model.md) の 8.4 節）。書き込みを始める時期は [ADR-0053](0053-client-server-version-skew.md) でフラグにした。
- クライアントのビルドは、配った後もタブに残る。戻すのは、配信を戻すだけでは済まない。

## Options

1. **フラグを 2 種類に分ける：UI のフラグ（利用者の組織で決める）と、文書のフラグ（ファイルを持つ組織とファイルで、Document Server が決めて配る）。ビルドは組織の割合で段階的に出す**
2. **すべてのフラグを利用者の組織で決める**
3. **すべてのフラグをファイルで決める**

## Decision

1 を採用する。詳細は [delivery.md](../architecture/delivery.md) の 5・6 節。

- **UI のフラグ**（`release.ui.*`）：Slack の ADR-0026 と同じ。割り当ては利用者の組織、評価はブートストラップの API。
- **文書のフラグ**（`release.doc.*`）：変更の適用・検証・レイアウト・描画の結果を変えるもの。
  - Document Server が、ファイルを開いたときに `hash(flag + file_id)` と、ファイルを持つ組織の許可の一覧で評価し、`Welcome.features` で全クライアントに配る。ファイルを開いている間は変えない（変えるときは `Kick(resync_required)` で開き直させる）。
  - Render Worker と file-read は、ジョブの `seq` の時点の `features` を、チェックポイントのマニフェストの付属の値から読む（マニフェストに `features` を記録する。document-model の領域への提案）。
  - クライアントは、`features` に従ってエンジンの規則を切り替える。知らないフラグを受けたら、強い再読み込み（ADR-0053）。
- **ビルドの段階的な配信**：静的な資産はハッシュの名前で不変にし、`index.html` だけが入口を決める。ブートストラップが、利用者の組織の割合（`hash(build_channel + org_id)`）で配るビルドを決める。段階は、社内の組織 → 1% → 10% → 50% → 100%。各段で 24 時間、[observability.md](../architecture/observability.md) の 3 節のクライアントの指標（panic の率、フレーム時間の p95、メモリの警告の率）を前のビルドと比べ、悪化がなければ次へ進む。同時に配るビルドは 2 つまで。
- **プロパティの表の変更の 3 段**：
  1. サーバー（Document Server、Render Worker、file-read、Worker）を出す。新しいプロパティを知り、既定値で扱い、書かれたら保つ。
  2. クライアントのビルドを段階的に出す。新しいプロパティを読んで描くが、書かない。
  3. アクティブな接続の 95% が新しい `schema_hash` になったら、`schema.<prop>.write` を有効にする（ADR-0053）。
  - 消すときは逆の順（書き込みを止める → クライアント → サーバー）で、`deprecated` にしてから 1 か月後に表から外す（document-model.md の 8.4 節）。
- **戻し方**：
  - UI のフラグと文書のフラグは、フラグで戻す。文書のフラグを戻すと、そのファイルは次に開いたときから古い規則になる（開いているファイルは `Kick(resync_required)` で開き直させる）。
  - ビルドは、配信の割合を 0 にし、`min_client_build` を上げて（ADR-0053）古いタブも読み込み直させる。
  - 書き込みを解禁したプロパティは、戻せない（ファイルに値が残る）。古いサーバーでも保てることを、1 の段の前に確かめる。
- 2 を採らない理由：共有したファイルで、違う規則の人が混ざる。
- 3 を採らない理由：UI の変更まで、ファイルを開き直すたびに変わり、利用者を混乱させる。

## Consequences

- 良くなること：
  - 1 つのファイルの中では、全員が同じ規則で動く。
  - クライアントのビルドの悪化を、1% の組織の段で止められる。
- 引き受けるコスト：
  - フラグの種類を、レビューで正しく選ぶ必要がある（文書に影響するのに UI のフラグにする誤り）。
  - マニフェストに `features` を持つ（document-model の領域への提案）。
  - 書き込みを解禁するまでの待ち（新しいビルドの普及）が、機能の公開を数日遅らせる。

## Confirmation

- lint：`doc-model`・`layout`・`scene` の crate から、UI のフラグを参照するコードを禁止する。これらの crate は `features` だけを読む。
- 結合テスト：同じファイルを違う組織の 2 人が開いたとき、2 人の `features` が同じ。
- 結合テスト：新しいプロパティを書いたファイルを、1 つ前の版の Document Server で開き、値が保たれる。
