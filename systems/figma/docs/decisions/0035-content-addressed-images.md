# ADR-0035: 画像は組織ごとに中身の SHA-256 で重複を除き、クライアントで正規化してから署名付き PUT で上げ、別ドメインの CDN から短命の署名付き URL で配る

## Context

画像の塗りは MVP に含む（[intent.md](../intent.md)）。ノードは画像を `image_hash`（中身の SHA-256）で参照し、画像そのものはファイルに入れない（[document-model.md](../architecture/document-model.md) の 9.5 節）。

満たすべきことは次のとおり。

- 画像を置いた本人の画面には、すぐ出る（NFR-002）。他の人の画面にも、上げ終わりしだい出る。
- 同じ画像を何度も貼っても、何度も上げない。
- 権限のない人に、画像を返さない（NFR-010）。組織をまたいで漏れない。
- 悪意のある画像（デコーダーの欠陥、展開の爆弾、マルウェア）と、利用者が上げたバイト列がアプリのオリジンで動くことを防ぐ。

本家は、長辺 4096 px を超える画像を縮め、その際にメタデータの一部が失われうる（[Add images and videos to designs](https://help.figma.com/hc/en-us/articles/360040028034-Add-images-and-videos-to-designs)）。画像の塗りは `imageRef` で参照し、API は 14 日以内に切れる URL を返す（[File endpoints](https://developers.figma.com/docs/rest-api/file-endpoints/)）。いずれも 2026-09-27 に確認。

rebuilds の Slack は、ファイルを署名付き PUT で上げ、GuardDuty で検査し、別ドメインの CloudFront の短命な署名付き URL で配る（[Slack の ADR-0015](../../../slack/docs/decisions/0015-file-upload-scan-and-delivery.md)）。

## Options

重複の除去の範囲：

1. **組織の中だけ**
2. **全体で 1 つ**（どの組織の同じ画像も 1 つのオブジェクト）
3. **除かない**（アップロードごとに ID を振る）

正規化（縮小・メタデータの除去）の場所：

- a. **クライアント**（ハッシュの前に行う）
- b. **サーバー**（上げた後に行い、ハッシュを付け直す）

配信：

- x. **別ドメインの CloudFront の短命の署名付き URL**（ハッシュのパスで不変のキャッシュ）
- y. **API が中継する**

## Decision

1・a・x を採用する。詳細は [export-and-assets.md](../architecture/export-and-assets.md) の 6 節。

- **組織ごとに、中身の SHA-256 で重複を除く。** S3 の鍵は `images/{org_id}/{sha256}`、表は `images` の主キー `(org_id, sha256)`。
  - 2 を採らない理由：「このハッシュはすでにある」という応答から、他の組織が特定の画像を持つことを当てられる。組織をまたぐ削除（権利の侵害の申し立て、組織の解約）の扱いも複雑になる。
  - 3 を採らない理由：同じ画像を貼るたびに上げ直し、容量と待ち時間が増える。ハッシュでの参照（document-model）と合わない。
- **正規化はクライアントで、ハッシュの前に行う。** 長辺 4096 px を超えたら縮め、EXIF・XMP（位置情報を含む）を、再符号化せずに除く。その後で SHA-256 を計算する。
  - b を採らない理由：サーバーで変えると、クライアントがすでにファイルに入れたハッシュと合わなくなる。ハッシュの付け直しを、ファイルの変更として配る仕組みが要る。
  - サーバーは、正規化が守られているか（大きさ、位置情報がない）を検査し、守られていなければ `rejected` にする。
- **アップロードは署名付き PUT で直接 S3 へ。** 署名に大きさ・種類・`x-amz-checksum-sha256` を含め、S3 にハッシュを検証させる。
- **画像を参照する変更の確定の経路では、`images` の表を引かない。** 確定の遅延（NFR-001）に Aurora を入れないため。組織にない画像は「読み込めない画像」として描くだけになる。
- **取り込みの検査は、Rust の検査器を子プロセスで動かす**（形式、大きさ、全体のデコード、位置情報）。加えて GuardDuty Malware Protection for S3 の結果を見る（Slack と同じ）。通ったら縮小版（長辺 2048・512・128 px の WebP）を作る。
- **配信は `assets.<brand>usercontent.<domain>` の CloudFront で、署名付き URL の期限は 15 分。** 署名の API は、閲覧の権限を判定関数で確かめ、ファイルを持つ組織の `images` の表にあるハッシュにだけ URL を出す。中身が不変なので、キャッシュは `immutable` にする。
  - y を採らない理由：画像の帯域と接続が API を占有する。キャッシュが効かない。
- **削除は週に 1 回の mark-and-sweep。** 残している全チェックポイントの `blob_refs_chunk` の和集合から外れ、作ってから 7 日を過ぎた画像を消す。

## Consequences

- 良くなること：
  - 同じ画像を貼り直しても上げない。上げた本人の画面には、アップロードを待たずに出る。
  - 組織をまたいで、画像の存在も中身も漏れない。
  - 画像がアプリのオリジンで動かない。
- 引き受けるコスト：
  - クライアントの正規化の不具合は、サーバーで `rejected` になり、画像が出ない。クライアントとサーバーで同じ Rust の検査のコードを使って、食い違いを減らす。
  - 組織をまたぐ複製では、S3 の中でのコピーが要る。
  - `pending` のまま上げ終わらない画像は、他の人の画面で「読み込めない画像」になる。
  - 端末に残ったブラウザのキャッシュは、権限を外しても消せない。

## Confirmation

- 性質ベーステスト：任意の画像のバイト列で、クライアントの正規化とハッシュと、サーバーの検査のハッシュが一致する。
- 性質ベーステスト：任意の 2 組織で、一方の組織の文脈で他方のハッシュの URL が返らない。
- 性質ベーステスト：任意のファイルと版の集合で、削除の後も、残したチェックポイントが参照する画像が残る。
- fuzzing：検査器（画像）。任意のバイト列で落ちず、上限を超える確保をしない。
- 結合テスト：権限を外した直後の利用者が、画像の新しい URL を得られない。
