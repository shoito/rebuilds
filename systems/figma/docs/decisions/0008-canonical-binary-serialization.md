# ADR-0008: 変更・チェックポイント・通信は、表から生成する自前のスキーマ付きバイナリ（タグ付き・正準形）で表し、ページ単位に分けて zstd で圧縮する

## Context

ファイルの中身は、3 つの場所で直列化する。

- 通信：クライアントと Document Server の間の変更（毎秒数十回、小さい）
- ジャーナル：確定した変更のまとまり（DynamoDB の項目。1 項目 400 KB まで。[Constraints in Amazon DynamoDB](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Constraints.html)、2026-09-27 に確認）
- チェックポイント：ファイル全体（10 万ノードで数十 MB）

満たすべきことは次のとおり。

- 小さく、速く読み書きできる（NFR-003 の開く時間、NFR-001 の反映の時間）。
- ページだけを読める（[ADR-0003](0003-journal-and-checkpoints.md)）。
- 同じ状態が同じバイト列になる。本家は、チェックポイントとジャーナルから作り直したファイルがバイト単位で一致することを確かめて、ジャーナルを出した（[Making multiplayer more reliable](https://www.figma.com/blog/making-multiplayer-more-reliable/)、2022-10-20、2026-09-27 に確認）。
- 新しいプロパティを足しても、古い読み手が壊れず、値を落とさない。

本家の CTO が作った Kiwi は、スキーマ付きのバイナリで、可変長の整数、省略できるフィールドの有無の判定、スキーマのバージョンの前後の互換を持つ（[evanw/kiwi](https://github.com/evanw/kiwi)、2026-09-27 に確認）。本家のファイルが Kiwi を使うかは公式の資料で確かめられなかった（**未検証**）。

## Options

1. **自前のスキーマ付きバイナリ。プロパティの表（[ADR-0006](0006-node-types-and-property-table.md)）から生成し、タグ付き・正準形にする**
2. **Protocol Buffers**
3. **FlatBuffers・Cap'n Proto（ゼロコピー）**
4. **CBOR・MessagePack（スキーマなし）**
5. **JSON**

## Decision

1 を採用する。詳細は [document-model.md](../architecture/document-model.md) の 8 節。

- 整数は LEB128、`f32` は 4 バイト、文字列は長さ＋UTF-8。ノードのプロパティは `(prop_id, len, value)` で並べ、知らない `prop_id` を読み飛ばせる。
- **正準形**：ノードは ID の昇順、プロパティは `prop_id` の昇順、既定値は書かない、`map` は鍵の昇順、`-0.0` は `0.0`。同じ状態は同じバイト列になる。
- **チェックポイント**：マニフェストと、ページごとのチャンク（4 MiB を超えたら分ける）。チャンクは zstd で圧縮し、SHA-256 で名付ける（[ADR-0025](0025-content-addressed-checkpoints-and-loading.md)）。
- 通信とジャーナルも同じ符号化を使う。通信のフレームは圧縮しない（小さいため）。ジャーナルの項目は zstd で圧縮する。
- 知らない `prop_id` を読んだら、値を保ったまま書き戻す（古い Worker が新しい値を消さない）。
- `format_version` は符号化の規則を変えたときだけ上げる。`schema_hash` で、接続時にクライアントとサーバーの表の一致を確かめる。
- 2 を採らない理由：フィールドが省略されたのか既定値なのかを区別しにくい（proto3）。正準形の符号化は仕様で保証されない。Rust と TypeScript の生成の道具が別々になる。
- 3 を採らない理由：ゼロコピーの利点は、読み込んだ後に `Doc`（HAMT）へ入れ直すので生きない。形が固定に近く、ページの分割と正準形を自前で足すことになる。
- 4 を採らない理由：フィールドの名前を毎回持つか、自前の番号の対応を持つことになり、1 と変わらない手間で型の検査がない。
- 5 を採らない理由：大きく遅い。`f32` の往復で値が変わりうる。

## Consequences

- 良くなること：
  - 1 つの形式で、通信・ジャーナル・チェックポイントを扱える。
  - 正準形で、回復の検証（バイト列の比較）と、WASM とネイティブの一致の検査ができる。
  - 変わっていないページのチャンクを再利用できる。
- 引き受けるコスト：
  - 符号化・復号の生成器を自前で持つ。fuzzing で守る。
  - 外部の道具（デバッガー、プロキシ）がそのまま読めない。開発用に、JSON へ変換する CLI を用意する。

## Confirmation

- 性質ベーステスト：`decode(encode(x)) == x`、`encode(decode(b)) == b`（正準形）。
- 性質ベーステスト：知らない `prop_id` を含むノードの往復で、値が残る。
- fuzzing：任意のバイト列で、復号が落ちず、上限を超える確保をしない。
- 計測：10 万ノードの参照ファイルのチェックポイントの大きさと、直列化・復号の時間を、CI で記録する。
