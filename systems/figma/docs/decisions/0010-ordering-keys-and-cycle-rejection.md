# ADR-0010: 並びの鍵は base-62 の可変長の文字列。重なりと長さはサーバーが振り直し、複数のノードの挿入には乱数の接頭辞を付け、循環を作る変更は `ChangeSet` ごと拒否する

## Context

[ADR-0002](0002-central-authoritative-multiplayer.md) で、子の並びを分数インデックスにし、親と位置を `parent_index` の 1 つのプロパティにすると決めた。重なりの振り直しと、長さの上限（例：64 文字）も方針として決めた。残る問いは次のとおり。

- 鍵の形式。Rust（サーバー、WASM）と TypeScript（UI の殻）で、同じ比較の結果になること。
- 同時に同じ隙間へ入れたときの扱い。重なり（同じ鍵）と、交ざり（2 つの列が 1 つずつ交互になる）。
- 鍵が伸びたときの扱い。
- 循環を作る変更の拒否の単位。

本家は、0 と 1 の間の分数を任意精度の文字列で持ち、同じ位置への同時の挿入はサーバーが後の方に一意の位置を振る。鍵の長さは、実際の使い方では問題にならないとしている（[Realtime editing of ordered sequences](https://www.figma.com/blog/realtime-editing-of-ordered-sequences/)、2017-03-06）。循環はサーバーが拒否する（[How Figma's multiplayer technology works](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)、2019-10-16）。分数インデックスの広く使われる実装は、base-62 で整数部の長さを先頭の文字で表す形で、同時に作ると鍵が重なりうることを認め、乱数を混ぜる派生を挙げている（[rocicorp/fractional-indexing](https://github.com/rocicorp/fractional-indexing)）。分数インデックスでは、同時に入れた列が交ざることが知られている（[Interleaving anomalies in collaborative text editors](https://martin.kleppmann.com/papers/interleaving-papoc19.pdf)、Kleppmann ほか、2019）。いずれも 2026-09-27 に確認。

## Options

鍵：

1. **base-62 の可変長の文字列（整数部の長さを先頭の文字で表す）。辞書順で比べる**
2. **`f64` の分数**
3. **任意精度の有理数（分子と分母）**
4. **前後の兄弟をアンカーにする（Notion の ADR-0012）**

同時の挿入：

- a. サーバーが重なりだけを振り直す
- b. すべての挿入に乱数を混ぜる
- c. 複数のノードをまとめて入れるときだけ、乱数の接頭辞を付ける。重なりはサーバーが振り直す

## Decision

1 と c を採用する。詳細は [multiplayer.md](../architecture/multiplayer.md) の 5・6 節。

- 鍵は ASCII の base-62。先頭の 1 文字で整数部の長さを表し、末尾を `0` にしない。バイトの比較がそのまま順序。上限 64 バイト。
- 1 つのノードの挿入・移動は、決定的な `key_between(前, 後)`。
- 複数のノードのまとめての挿入（貼り付け、複製、グループ化）は、乱数の接頭辞 `p`（前と後の間の、4 文字の乱数を持つ鍵）を作り、その後ろに鍵を並べる。2 人のまとまりが交ざらない。
- サーバーは、当てる鍵が兄弟と重なれば `key_between(重なった鍵, 次)` に書き換える。当てた後の鍵が 48 バイトを超えたら、その親の子すべての鍵を同じ `seq` の中で振り直す。書き換えは `session_id = 0` の操作として記録し、送り手には `Ack.server_ops` で返す。
- 循環：`parent_index` を当てる前に、新しい親から根までたどり、動かすノードが現れたら、その `ChangeSet` 全体を `Reject(cycle)` で拒否する。クライアントは、確定まで一時的な循環のノードを木から外して描く。
- 2 を採らない理由：53 ビットの精度は、同じ隙間への挿入を 50 回ほど繰り返すと尽きる。
- 3 を採らない理由：分母が育ち、比較の実装を Rust と TypeScript で揃える手間が増える。文字列で足りる。
- 4 を採らない理由：並びが 1 つのプロパティの LWW で閉じなくなる。アンカーの兄弟が消えたときの規則が要る。Figma は並びを子のプロパティとして持つので、分数インデックスが合う（ADR-0002 の比較）。
- a を採らない理由：2 人が同じ隙間へ同時に貼り付けると、まとまりが 1 つずつ交ざる。
- b を採らない理由：1 つのノードの挿入は、交ざりの問題がない。乱数で鍵が 4 文字ずつ長くなるのに見合わない。

## Consequences

- 良くなること：
  - 並びの変更が 1 つのプロパティの LWW で閉じ、収束を示しやすい。
  - まとまりの挿入が交ざらない。
  - 鍵の長さが上限で抑えられる。
- 引き受けるコスト：
  - まとめての振り直しは、子の多い親で大きな変更になる（1 万の子で数百 KB）。
  - 振り直しと同時に届いた他の人の移動は、古い間隔の鍵で当たり、並びが少しずれうる（重なりは再び振り直すので、一意は保つ）。

## Confirmation

- 性質ベーステスト（PROP-MP-003）：任意の挿入・移動の列で、兄弟の鍵が一意で 64 バイト以下。
- 性質ベーステスト（PROP-MP-008）：2 人が同じ隙間へ同時に n 個ずつ貼り付けても、各まとまりが連続する。
- 性質ベーステスト（PROP-MP-002）：任意の移動の列で、サーバーの木に循環がない。
- 差分テスト：Rust と TypeScript の `key_between` と比較が、同じ入力で同じ結果になる。
