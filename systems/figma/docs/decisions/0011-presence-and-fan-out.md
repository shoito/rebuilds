# ADR-0011: 在席とカーソルはジャーナルに書かず、Document Server がファイルごとにまとめて Gateway ごとに配る。1 ファイルの参加は 500 人、編集は 200 人まで

## Context

同時編集の画面には、他の人のカーソル、選択、在席（顔のアイコン）、視点を追う機能が要る（[intent.md](../intent.md) の MVP）。カーソルは 1 人あたり毎秒数十回動く。1 ファイルに N 人いると、そのまま配ると毎秒 N² に比例するメッセージになる。

[architecture/README.md](../architecture/README.md) の 7 節は、1 つのファイルに数百人が入るとき、閲覧だけの接続の配信を別のノードに分ける案の検討を、この領域に求めている。

本家は、1 ファイルに 500 人（編集と閲覧の合計）、編集 200 人、カーソルの表示 200 人を上限にしている。500 人に達すると、後から入った人は動かないバージョンを見て、カーソルは隠れる。閲覧で 500 人に達していても、編集の権限のある人は 20 人まで入れる（[How many people can be in a file at once?](https://help.figma.com/hc/en-us/articles/1500006775761-How-many-people-can-be-in-a-file-at-once)、2026-09-27 に確認）。本家の在席の送り方は公開されていない（**未検証**）。

## Options

在席の経路：

1. **Document Server のファイルごとの presence task が、一定の間隔でまとめて Gateway に配る**
2. **Gateway の間を Valkey の pub/sub でつなぎ、Document Server を通さない（Slack・Notion の在席と同じ形）**
3. **編集の変更と同じ経路（file actor とジャーナル）**

人が集まるファイル：

- a. **Gateway ごとに 1 回配り、Gateway が接続に分ける。参加の上限を置き、超えた人は動かないバージョン**
- b. **閲覧だけの接続を、別の配信のノード（木構造）から配る**
- c. **上限を置かない**

## Decision

1 と a を採用する。詳細は [multiplayer.md](../architecture/multiplayer.md) の 3・12 節。

- 在席・カーソル・選択・視点は一時的なデータで、ジャーナルにもチェックポイントにも書かない。file actor を通さず、ファイルごとの presence task が扱う。
- presence task は、50ms ごと（参加が 50 人を超えたら 100ms ごと）に、変わった項目だけを `PresenceBatch` にまとめて Gateway に送る。Gateway は、同じページを見ている接続にだけカーソルを送る。
- `session_id`・`user_id`・色はサーバーが付ける。
- 視点を追う（`Follow`）は、追われている人の視点を、追う人にだけ 20Hz まで送る。
- 編集の `Committed` も在席も、Document Server から Gateway のタスクごとに 1 回送る。
- 参加の上限は本家と同じ：500 人、編集 200 人、カーソルの表示 200 人、編集の権限の枠 20 人。超えて入った人は、最新のチェックポイントの動かないバージョンを見る。
- 2 を採らない理由：在席の対象（同じファイルの参加者の一覧、ページ）を、Document Server とは別に持つことになる。Document Server は既にファイルの接続の一覧を持つ。S2 で Gateway の間の配信の木を作るときに見直す。
- 3 を採らない理由：ジャーナルの書き込みと確定の遅延を、在席の量で悪化させる。
- b を採らない理由：S1 の上限（500 人）では、Gateway ごとに 1 回の配信で、Document Server の送信は毎秒 1 MB 未満に収まる見積もり（[multiplayer.md](../architecture/multiplayer.md) の 12.3 節）。配信の木は、上限を超える需要が出た S2 で ADR にする。
- c を採らない理由：1 ファイルの処理は 1 つの持ち主に集まるので、上限なしでは 1 人の大きな会議で全員の編集が遅れる。

## Consequences

- 良くなること：
  - 在席が編集の確定を遅らせない。
  - 送信の量が、参加の数の 2 乗ではなく、まとめの間隔と Gateway の数で決まる。
  - 上限が本家と同じなので、利用者の期待と合う。
- 引き受けるコスト：
  - カーソルの動きは、最大 100ms の段差で見える。受け手のクライアントが補間する。
  - 500 人を超えた人は、他の人の編集を即時には見られない。
  - Document Server の障害で、在席も一緒に途切れる（再接続で戻る）。

## Confirmation

- 負荷試験（E12）：1 ファイル 500 接続（編集 200）で、NFR-001 の p99、Document Server の CPU と送信の量、Gateway の 1 接続あたりの送信の量を計る。
- 結合テスト：501 人目が動かないバージョンになり、編集の権限のある人は 520 人目まで通常の参加になる。
- 結合テスト：クライアントが他人の `session_id` を名乗った `Presence` を送っても、配られる項目は自分の `session_id` になる。
