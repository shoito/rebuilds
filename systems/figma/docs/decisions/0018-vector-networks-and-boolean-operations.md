# ADR-0018: ベクターネットワークの編集は編集した人が計算して全体を書く。ブール演算の結果は保存せず、i_overlay の整数の演算で求め、平坦化だけ iCurve で曲線を残す

## Context

MVP は、ペンでのパスの編集（ベクターネットワーク）とブール演算を含む（[intent.md](../intent.md)）。

- 本家のベクターネットワークは、点と点を任意の線と 3 次ベジェで結び、囲まれた領域を自動で塗り、領域ごとに塗りと穴を切り替える（[Introducing Vector Networks](https://www.figma.com/blog/introducing-vector-networks/)、2016-02-09、2026-09-27 に確認）。
- `vector_network` は 1 つのプロパティで、全体が 1 つの競合の単位、1 MiB まで（[document-model.md](../architecture/document-model.md) の 4.2 節、11 節）。
- ブール演算は、子を残したまま結果を描く非破壊のノード（`BOOLEAN_OPERATION`）。結果の境界の箱は、レイアウトの結果（`derived_layout`）になり、WASM とネイティブでビットまで一致しなければならない（[ADR-0020](0020-deterministic-layout-arithmetic.md)）。
- 1 セッションの送信は毎秒 4 MiB まで（[multiplayer.md](../architecture/multiplayer.md) の 4.6 節）。

部品の事情（2026-09-27 に確認）：

- i_overlay（9.0.0）は、多角形の和・積・差・排他を、整数（i16・i32・i64）と浮動小数点の API で、自己交差・穴を含めて頑健に求める。geo の crate が使う（[iShape-Rust/iOverlay](https://github.com/iShape-Rust/iOverlay)）。曲線は扱わない（線分に平坦化してから渡す）。
- iCurve（0.2.0）は、線・2 次・3 次ベジェ・楕円の弧のまま和・積・差を求め、結果に曲線を残す。位相は i_overlay と同じエンジン（[iShape-Rust/iCurve](https://github.com/iShape-Rust/iCurve)）。版が若い。
- kurbo（0.13.1）は、線の展開と、曲線の当てはめ（`fit_to_bezpath`。`fit_to_bezpath_opt` は実験的）を持つ（[linebender/kurbo](https://github.com/linebender/kurbo)）。

## Options

ベクターネットワークの編集：

1. **編集した人のクライアントが計算し（点の追加、分割、曲げ、領域の作り直し）、`vector_network` 全体を書く**
2. 点・辺ごとの変更の操作にして、サーバーでも当てる

ブール演算の結果：

- a. **保存しない。i_overlay の整数の演算で、クライアントと Worker が求める**
- b. 保存しない。iCurve で曲線のまま求める
- c. 編集した人が計算して、結果のパスを保存する

## Decision

1 と a を採用する。

### ベクターネットワーク

- 形は `{ vertices, segments, regions }`。領域は辺の輪の集まりで、`winding_rule` と、領域ごとの塗り（なければノードの塗り）を持つ（[editor-and-tools.md](../architecture/editor-and-tools.md) の 7.1 節）。
- ペン・点の編集・辺の分割（de Casteljau）・曲げ・点の削除は、編集した人のクライアントだけで計算し、結果のネットワーク全体を `Set` で書く。他の人は描くだけなので、編集の計算に決定性は要らない（三角関数を使ってよい）。
- 辺を足す・消したら、各点で辺を接線の角度で並べて面を辿り、最小の輪で領域を作り直す。前の領域の塗りは、代表点を含む新しい領域に引き継ぐ。
- 直列化で 64 KiB を超えるネットワークは、ドラッグの途中は 4Hz で送り、離したときに最後の値を送る。

### ブール演算

1. 子の輪郭を、ドキュメントの座標で誤差 1/64 px 以内の線分にする。
2. 座標を 1/256 px の整数（i32）にする。
3. i_overlay の整数の演算で結果の多角形を求める。
4. 結果を描画のパスにし、境界の箱を `derived_layout` にする。

- 整数の演算なので、WASM とネイティブで結果が一致する。
- ズームが 16 倍を超える画面では、描画だけのために誤差を細かくして計算し直す。境界の箱には使わない。
- 計算の結果はノードごとにキャッシュする。1 回 20 ms を超えるなら、ドラッグの途中は前の結果を動かして見せる。
- **平坦化**（ブール演算を 1 つの `VECTOR` にする確定の操作）は、曲線を残すため iCurve で求める。失敗したら、i_overlay の結果を kurbo の `fit_to_bezpath` で曲線に直す。確定の結果は入力として書くので、決定性は要らない。
- **線のアウトライン化**：kurbo の線の展開 → i_overlay の和 → `VECTOR`。

### 採らない理由

- 2 を採らない理由：点・辺ごとの操作にすると、同時の編集で辺が消えた点を指すなど、ネットワークの整合を保つ規則がサーバーに要る。document-model は全体を 1 つの単位に決めている。同じパスを 2 人が同時に編集することはまれとみなす（ADR-0002 と同じ扱い）。
- b を採らない理由：iCurve は版が若く、浮動小数点の曲線の交点の計算が WASM とネイティブで一致するかを確かめていない（**未検証**。E4 の `boolean-operations` で一致の CI に載せて確かめる）。境界の箱がレイアウトの結果になるため、決定性を優先する。平坦化（確定）でだけ使う。
- c を採らない理由：子が変わるたびに結果を書くと、変更が大きくなる。同時の編集で、子と結果が食い違う（修復の規則が要る）。結果は子から決まるので、保存する意味が薄い。

## Consequences

- 良くなること：
  - ブール演算の結果が、全員の画面と Worker で一致し、境界の箱を決定的に求められる。
  - ベクターネットワークの編集の規則が、サーバーに要らない。
- 引き受けるコスト：
  - 画面のブール演算の結果は線分の多角形で、拡大すると角が見える（16 倍を超えたら描画だけ細かくする）。
  - 同じパスを 2 人が同時に編集すると、片方の編集が消える。
  - 大きなネットワークのドラッグの間、他の人の画面の更新が 4Hz になる。
  - 平坦化で、曲線の当てはめの品質が落ちうる（**未検証**。E4 の `boolean-operations` で参照の形と比べる）。

## Confirmation

- 性質ベーステスト：任意の多角形の組で、ブール演算の結果が WASM とネイティブで一致する。和は両方の子を含み、積はどちらにも含まれる（PROP-EDIT-004）。任意のネットワークの編集の後、添字が範囲の中にあり、領域の輪が閉じている（PROP-EDIT-003）。
- 参照画像のテスト：ブール演算の 4 種、自己交差、穴、曲線を含む形を、WebGPU・WebGL2・ネイティブで描く。
- 平坦化の品質：参照の形で、iCurve の結果と元の形の差（画素の差）を E4 の前に測る。
