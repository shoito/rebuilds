# ADR-0029: 階層は組織・チーム・プロジェクト・ファイル。水準は全順序で、上位で与えた水準を下位で下げない。ファイルの「招待した人だけ」は上位の一般アクセスを遮る。シートは上限として重ねる

## Context

ファイルは、組織の中のメンバー、組織の外のゲスト、リンクを知っている匿名の人と共有する（[intent.md](../intent.md) の MVP）。権限の規則は、判定のすべての経路（接続、一覧、サムネイル、コメント、通知、検索、書き出し）で同じでなければならない（NFR-010）。

本家の規則は次のとおり（いずれも 2026-09-27 に確認）。

- 階層は組織 → チーム → フォルダー（旧プロジェクト）→ ファイル。水準は所有者・編集・閲覧。フォルダーの役割はファイルに、チームの役割は最上位のフォルダーに届く。個人の役割は上位より上げられるが、下げられない。フォルダーの一般アクセスが「編集」でも、ファイルが「招待した人だけ」なら、一般アクセスで来た人は開けない（[File and folder permissions](https://help.figma.com/hc/en-us/articles/35361119554711-File-and-folder-permissions)）。
- 編集には、編集の権限と、その製品を含むシートの両方が要る。シートは Full・Dev・Collab・View（無料）（[Manage seats in Figma](https://help.figma.com/hc/en-us/articles/360039960434-Manage-seats-in-Figma)）。
- 一般アクセスは、招待した人だけ・組織の中・リンクを知っている全員。有料のプランで閲覧者の複製・共有・書き出しを止められる（[Share files and prototypes](https://help.figma.com/hc/en-us/articles/360040531773-Share-files-and-prototypes)）。リンクの期限は Enterprise で、期限が来ると最後の非公開の設定に戻る（[Set an expiration on public links in design files](https://help.figma.com/hc/en-us/articles/16142157359255-Set-an-expiration-on-public-links-in-design-files)）。

rebuilds の Notion は、ページの木に ACL を持たせ、設定したページで継承を置き換える方式にした（[Notion の ADR-0018](../../../notion/docs/decisions/0018-permission-levels-and-inheritance.md)）。Figma の階層は浅く（最大 3 段）、置き換えではなく「上げるだけ」である。

## Options

役割の継承：

1. **上げるだけ**：実効の役割は、ファイル・プロジェクト・チームの役割の最大
2. **置き換え**：下位に役割があれば、上位の役割を無視する（Notion の形）

一般アクセス：

- a. **最も近い設定を 1 つだけ使い、ファイルの「招待した人だけ」で上位を遮る**（本家の例と同じ）
- b. **すべての階層の一般アクセスの最大**

シート：

- x. **水準の上限として重ねる**：編集の水準があっても、Full のシートがなければ編集の操作を閲覧として扱う
- y. **シートを水準の一部にする**：役割を付けるときにシートを確かめ、足りなければ役割を下げて保存する

## Decision

1、a、x を採用する。詳細は [permissions-and-sharing.md](../architecture/permissions-and-sharing.md) の 3〜7 節。

- 水準は `none < view_prototype < view < edit < owner` の全順序。`view_prototype` は MVP の後。
- 役割は `resource_roles`（`team` / `project` / `file`）に置き、実効の役割はその最大。
- 一般アクセスは `general_access` に置き、最も近い設定を 1 つだけ使う。`scope = org` はゲストに届かない。`scope = anyone` は匿名に `view` まで。
- シートは組織ごとで、ゲストもファイルを持つ組織のシートを使う。編集の操作だけに効く上限にし、共有・移動・削除には効かせない。シートの承認は、本家の 3 つの設定（手動・空きがあれば自動・自動）を持つ。
- リンクの期限は、本家と違い、すべての有料のプランで付けられる。期限は判定の時点で確かめ、スケジューラーが設定を戻して `acl.changed` を流す。
- ファイルの URL には、128 ビットの乱数の鍵だけを入れ、名前を入れない（本家との差異）。
- 2 を採らない理由：本家の「上げるだけ」と違う振る舞いになる。浅い階層では、置き換えの利点（部分木ごとの非公開）より、「チームに入れたのに開けない」混乱の方が大きい。非公開にしたいファイルは、a の「招待した人だけ」で遮れる。
- b を採らない理由：ファイルを「招待した人だけ」にしても、プロジェクトの「組織の中」で開けてしまう。本家の例と逆になる。
- y を採らない理由：シートを後から足したとき（承認の後）に、役割を付け直す必要がある。シートを外したときに、役割の履歴が失われる。

## Consequences

- 良くなること：
  - 本家に慣れた利用者の期待と合う。
  - 実効の水準の計算が、3 つの役割の最大と、一般アクセスの 1 つの読み取りで済む。
  - シートの増減で、役割の行を書き換えない。
- 引き受けるコスト：
  - 下位で水準を下げられない。チームの編集者から特定のファイルの編集を外すには、ファイルを別のチームへ移す必要がある。
  - 「プロジェクト」の呼び名が、本家の改名（フォルダー）と違う。
  - URL に名前がないので、URL だけでは何のファイルか分からない。

## Confirmation

- 決定表のテスト：permissions-and-sharing.md の 4.2・4.4・5.3・6.2 節。
- 性質ベーステスト：下位の役割を足しても実効の水準が下がらない。ファイルの `invited_only` は上位の一般アクセスを遮る。
- 性質ベーステスト：期限を過ぎた `anyone` は、スケジューラーの前でも後でも届かない。
