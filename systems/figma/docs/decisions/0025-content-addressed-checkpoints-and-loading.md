# ADR-0025: チェックポイントはマニフェストと中身のハッシュで名付けたページのチャンクにし、変わったページだけを書く。クライアントは署名付き URL で CloudFront からチャンクを読んで端末にキャッシュし、その後の変更だけを Document Server から受け取る

## Context

[ADR-0003](0003-journal-and-checkpoints.md) で、Document Server は 60 秒か 5,000 件ごとに、ファイル全体を直列化して `files/{file_id}/checkpoints/{seq}` に書くと決めた。[architecture/README.md](../architecture/README.md) の 2.2 節は、クライアントが Document Server からページ単位でファイルを受け取るとした。次の問題がある。

- 10 万ノードのファイルは圧縮しても数十 MB になりうる。毎分ファイル全体を書くと、S3 の書き込みの量と費用、Document Server の CPU が大きい。多くの編集は 1 つのページに閉じる。
- 会議の始まりに数百人が同じ大きなファイルを開くと、Document Server がファイルの全体を各人に送ることになり、ホットスポットになる。
- 2 回目に開くとき（NFR-003 のキャッシュありの 2 秒）、変わっていない部分を取り直したくない。
- 版の履歴で多くのチェックポイントを残すと、同じ中身を何度も保存する。

本家は、ページとレイヤーを必要なときに読む（[Reduce memory usage in files](https://help.figma.com/hc/en-us/articles/360040528173-Reduce-memory-usage-in-files)、2026-09-27 に確認）。チェックポイントの内部の形と、クライアントへの配り方は公開されていない（**未検証**）。

## Options

チェックポイント：

1. **マニフェスト＋中身のハッシュで名付けたページのチャンク。変わったページだけを書く**
2. **毎回ファイル全体を 1 つのオブジェクトに書く**
3. **ページごとのオブジェクトを、`seq` で名付けて毎回すべて書く**

クライアントへの配り方：

- a. **判定の後に出す短い期限の署名付き URL で、CloudFront からチャンクを配る。Document Server はマニフェストと、その後の変更（tail）だけを送る**
- b. **Document Server が WebSocket でファイルの中身を送る**

## Decision

1 と a を採用する。詳細は [file-storage-and-history.md](../architecture/file-storage-and-history.md) の 5・6 節、形は [document-model.md](../architecture/document-model.md) の 8.2 節。

- マニフェストは `files/{file_id}/checkpoints/{seq:020}`（ADR-0003 のキー）。チャンクは `files/{file_id}/chunks/{sha256}` で、zstd で圧縮する。ページが 4 MiB を超えたら分ける。
- チェックポイントは、変わったページのチャンクだけを書く。写しは HAMT で O(1) に取り、別のスレッドで直列化する。マニフェストは `durable_seq` が写しの `seq` に追いついてから書く。
- 掃除は、残すマニフェストが参照しないチャンクを、最終更新から 7 日の猶予の後に消す。チャンクの名前はファイルの中で閉じる（ファイルをまたいで共有しない）。
- ファイルを開くと、Document Server は `LoadPlan`（マニフェストの内容、チャンクごとの署名付き URL、tail）を返す。URL は 5 分の期限で、判定を通ったセッションにだけ出す。
- クライアントは今のページのチャンクを先に読み、他のページを裏で読む。チャンクは IndexedDB にハッシュを鍵にしてキャッシュする（利用者ごと、500 MB、ログアウトで消す）。
- 2 を採らない理由：毎分ファイル全体の書き込みになる。版を残すほど、同じ中身が増える。
- 3 を採らない理由：変わっていないページも毎回書く。端末のキャッシュが `seq` ごとに外れる。
- b を採らない理由：数百人が同時に開くと、Document Server の送信がファイルの大きさ×人数になる。CloudFront で配れば、Document Server の送信は tail だけになる。
- チャンクをファイルをまたいで共有しない理由：共有すると、削除（完全な削除でのファイルごとの消去）と組織の分離が、参照の数え上げに頼ることになる。複製では S3 の中でコピーする。

## Consequences

- 良くなること：
  - チェックポイントの書き込みが、変わったページの大きさで済む。
  - 版を多く残しても、同じページの中身は 1 つだけ持つ。
  - 同時に開く人が多くても、Document Server に集中しない。
  - 2 回目に開くとき、変わったページだけを取る。
- 引き受けるコスト：
  - 掃除（参照の集合と猶予）の仕組みが要る。誤って消すと、そのチェックポイントが読めなくなる。性質ベーステストで守る。
  - 署名付き URL の発行と、CloudFront の構成が要る。
  - 端末のキャッシュに、ファイルの中身が残る。ログアウトで消し、共有の端末での扱いは security.md で決める。
  - [architecture/README.md](../architecture/README.md) の 2.2 節の「Document Server からページ単位で受け取る」を、「Document Server から計画と tail を受け取り、チャンクは CloudFront から読む」に読み替える。README の更新は統合の工程で行う。

## Confirmation

- 性質ベーステスト（PROP-FS-004）：残すマニフェストが参照するチャンクは、掃除で消えない。
- 性質ベーステスト（PROP-DM-003）：ページ単位のチャンクをすべて読んで作った状態が、元と一致する。
- 計測：10 万ノードの参照ファイルで、1 回のチェックポイントで書くバイト数、開く時間（キャッシュあり・なし。NFR-003）。
- 結合テスト：判定を通らない利用者に、署名付き URL が出ない。期限の切れた URL で読めない。
