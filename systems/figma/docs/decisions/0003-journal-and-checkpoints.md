# ADR-0003: ファイルはメモリに持ち、確定の前にジャーナルへ書き、定期的に S3 へチェックポイントを書く

## Context

[ADR-0002](0002-central-authoritative-multiplayer.md) で、ファイルごとの Document Server がメモリの上で変更の順序を決めると決めた。メモリの状態は、プロセスが落ちると失われる。満たすべきことは次のとおり。

- 確定を返した編集は失わない（NFR-006）。
- 他の人への反映は p99 250ms 以内（NFR-001）。永続化の時間もこの中に収める。
- 大きなファイルでも、開く時間と回復の時間が短い（NFR-003、NFR-007）。
- 過去の版を表示し、復元できる（intent の MVP）。

本家は、以前はファイル全体を 30〜60 秒ごとに S3 へ書くチェックポイントだけで、その間の変更はプロセスが落ちると失われえた。2022 年に、ファイルの変更に連番を振り、DynamoDB に追記するジャーナル（トランザクションのログ）を足した。回復は、最新のチェックポイントを読み、それより大きい番号の変更をジャーナルから当てる。書き込みはチェックポイントより 120 倍ほど頻繁（約 0.5 秒ごと）で、編集の 95% が 600ms 以内に保存される。目標は「失うのは 1 秒未満」（[Making multiplayer more reliable](https://www.figma.com/blog/making-multiplayer-more-reliable/)、2022-10-20、2026-09-27 に確認）。本家が、ジャーナルへの書き込みの前に送り手へ確定を返すかどうかは、記事に書かれていない（**未検証**）。

## Options

1. **チェックポイントだけ**（本家の 2022 年より前）
2. **ジャーナル＋チェックポイント。確定はジャーナルの書き込みの後**
3. **ジャーナル＋チェックポイント。確定はメモリへの適用の後、ジャーナルは非同期**（本家の記事の読み方の 1 つ）
4. **変更を Aurora の操作のログに書く**（Notion の形）

ジャーナルの置き場所の候補：

- a. DynamoDB（本家と同じ）
- b. Aurora PostgreSQL のテーブル
- c. Kinesis Data Streams や自前のログ（EBS の上）

## Decision

2 と a を採用する。

- **ジャーナル**：確定した変更を、DynamoDB のテーブルに追記する。パーティションキーは `file_id`、ソートキーは `seq`。
  - Document Server は約 20ms ごとに、たまった変更をまとめて書く（group commit）。1 回の書き込みは、`seq` の範囲を 1 つの項目にまとめたもの。
  - 書き込みは 2 つの条件を 1 つのトランザクション（`TransactWriteItems`）で確かめる：フェンスの項目（`seq = 0`）の `epoch` が自分の `epoch` と等しいことと、その `seq` の項目がまだないこと（[ADR-0024](0024-journal-items-and-fencing.md)）。どちらかの条件が失敗したら、別のプロセスがこのファイルを持っているとみなし、自分のメモリの状態を捨ててファイルを手放す。これが二重の持ち主への最後の防御になる（[ADR-0005](0005-tenancy-and-document-routing.md) と [ADR-0047](0047-router-task-liveness-and-file-assignment.md) の割り当てと組み合わせる）。
- **確定の順序**：ジャーナルに書けてから、送り手に確定を返し、他の人に配る。書く前の変更は、他の人にも見せない。持ち主が落ちたとき、他の人が見た変更が消える事態を避けるため。
- **チェックポイント**：Document Server は、最後のチェックポイントから 60 秒、または変更 5,000 件ごとに、ファイルを直列化して S3 に書く。マニフェストのキーは `files/{file_id}/checkpoints/{seq:020}`（大阪への切り替えの後の世代 `g ≥ 2` は `checkpoints/g{g}/{seq:020}`。[ADR-0048](0048-osaka-dr-with-journal-generations.md)）。書けたら、ファイルのメタデータ（Aurora）の `checkpoint_seq` を進める。
  - 直列化の形式はバイナリで、ページ単位に分ける（ページだけを読める）。形式は [document-model.md](../architecture/document-model.md) の 8 節（[ADR-0008](0008-canonical-binary-serialization.md)）、変わったページだけを書く形は [ADR-0025](0025-content-addressed-checkpoints-and-loading.md)。
- **ジャーナルの切り詰め**：項目には、書いた時点から 30 日の TTL を付ける（項目を書き直さないため。[ADR-0024](0024-journal-items-and-fencing.md)）。30 日は、チェックポイントの破損に気づいてから戻すための余裕である。手放さずに落ちたファイルのチェックポイントより後の項目が TTL で消えないよう、Router の回復のジョブが 5 分以内に回復させてチェックポイントを書かせる（[ADR-0047](0047-router-task-liveness-and-file-assignment.md)）。
- **回復**：新しい持ち主は、最新のチェックポイントを読み、`checkpoint_seq` より大きい項目をジャーナルから `seq` の順に当てる。
- **版の履歴**：
  - 自動の版は、チェックポイントから選んで残す（編集が続いた 30 分ごとに 1 つ）。残さないチェックポイントは、掃除のジョブで消す（[file-storage-and-history.md](../architecture/file-storage-and-history.md) の 5.4 節）。
  - 名前付きの版は、その時点でチェックポイントを書き、消さない。
  - 復元は、過去の版の中身を、今のファイルへの変更として当てる。過去の版から後の版は消さない。
  - 残す間隔と、無料のプランの日数は [ADR-0026](0026-version-history-restore-and-deletion.md) で決めた。
- **リージョンの災害**：ジャーナルは DynamoDB のグローバルテーブルで大阪へ、S3 はクロスリージョンのレプリケーションで大阪へ複製する。複製は非同期なので、リージョンの喪失では最大 1 分の損失を許す（NFR-009）。切り替えのたびに世代を上げてキーを分ける（[ADR-0048](0048-osaka-dr-with-journal-generations.md)）。
- 1 を採らない理由：最大 60 秒の編集を失い、NFR-006 を満たせない。
- 3 を採らない理由：確定を返した後に落ちると、その変更が消える。NFR-006 に反する。確定の時間は延びるが、group commit の 20ms と DynamoDB のトランザクションの書き込み（p99 40ms の予算。**未検証**、E3 の前の PoC で計測する。[multiplayer.md](../architecture/multiplayer.md) の 8 節）で NFR-001 に収まる見込み。
- 4 を採らない理由：変更の件数（段階 S3 で 1 日 50 億件）を、メタデータの Aurora に書くと、書き込みの負荷とテーブルの大きさで、メタデータの処理を圧迫する。ファイルの中身とメタデータを分ける原則（[architecture/README.md](../architecture/README.md) の 1 節）にも反する。
- b を採らない理由：4 と同じ。
- c を採らない理由：Kinesis は `seq` を条件にした書き込み（二重の持ち主の防御）ができない。自前のログは、複製と障害の扱いを自分で持つことになる。
- DynamoDB は他の題材の共通の基盤にない。条件付きの書き込み、Multi-AZ の耐久性、グローバルテーブル、TTL が、この用途に合うので足す。

## Consequences

- 良くなること：
  - 確定を返した編集は、プロセス・ホスト・AZ の障害で失われない。
  - 回復は、チェックポイント 1 つとジャーナルの 60 秒ぶんを読むだけで済む。
  - 条件付きの書き込みで、二重の持ち主が同時に確定することを防げる。
- 引き受けるコスト：
  - 永続化の基盤が 3 つ（Aurora、DynamoDB、S3）になる。バックアップと DR の手順が増える。
  - 確定の時間に、ジャーナルの書き込みが加わる。
  - チェックポイントの直列化は、大きなファイルで重い。Document Server の処理を止めないよう、スナップショットを取ってから別のスレッドで直列化する。

## Confirmation

- 障害注入のテスト：任意の時点で Document Server を強制終了しても、確定を返した変更がすべて、回復後の状態に含まれる。
- 性質ベーステスト：任意のチェックポイントの位置とジャーナルの列で、「チェックポイント＋後続のジャーナル」から戻した状態が、メモリの状態と一致する。
- 結合テスト：同じファイルを 2 つの Document Server に持たせたとき、確定できるのは片方だけで、もう片方はファイルを手放す。
- 計測：確定までの時間（ジャーナルの書き込みを含む）を、ファイルごとのメトリクスで出す。
