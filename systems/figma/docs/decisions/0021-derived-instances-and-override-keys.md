# ADR-0021: インスタンスの中身は保存せず導出する。上書きは元のノードの ID の経路 × プロパティをキーにし、1 項目ずつ LWW にする

## Context

コンポーネントのインスタンスは、メインコンポーネントの形を写し、一部のプロパティを上書き（override）する。満たすべきことは次のとおり。

- メインを編集すると、全インスタンスに反映される。
- メインで名前を変えても、並べ替えても、ノードを別の親へ移しても、インスタンスの上書きは残る。
- 同時編集で、別の人が同じインスタンスの別の上書きを書いても、両方が残る（[ADR-0002](0002-central-authoritative-multiplayer.md) のプロパティ単位の LWW）。
- 大きなデザインシステムで、インスタンスが多くても、ファイルの大きさとメモリが増えすぎない（NFR-003〜005）。

本家の上書きは、テキスト・塗り・線・エフェクト・入れ子のインスタンスの入れ替え・名前などに限られ、構造（順序、位置、制約）は変えられない。バリアントの切り替えでは、レイヤーの名前が一致し、元の値が同じ上書きだけを残す（[Apply changes to instances](https://help.figma.com/hc/en-us/articles/360039150733-Apply-changes-to-instances)、2026-09-27 に確認）。本家は 2026 年に、インスタンスの導出を、依存を自動で記録し押し出しで無効化する「Materializer」に作り直した（[How we rebuilt the foundations of component instances](https://www.figma.com/blog/how-we-rebuilt-the-foundations-of-component-instances/)、2026-03-17、2026-09-27 に確認）。上書きを何をキーにして保存しているかは、公開の文書で見つけられなかった（**未検証**）。

## Options

インスタンスの中身：

1. **導出する**：インスタンスは `main_component` と上書きだけを保存し、子はクライアントで導出する
2. **写して保存する**：インスタンスの子を通常のノードとして保存し、メインの変更のたびにサーバーが全インスタンスへ写す

上書きのキー：

- a. **元のノードの ID の経路**（入れ子のインスタンスを 1 段ずつたどった、メインの中のノードの ID の列）
- b. **レイヤーの名前の経路**
- c. **インスタンスの子のノードの ID**（2 のときの、写したノードの ID）

競合の単位：

- x. **上書きの 1 項目ずつ**（`(instance_id, path, property)`）
- y. **インスタンスの上書き全体を 1 つのプロパティ**

## Decision

1、a、x を採用する。詳細は [components-and-libraries.md](../architecture/components-and-libraries.md) の 3 節。

- インスタンスは、`main_component`、`overrides`（`(パス, prop_id) → value`）、`component_prop_values` を保存する。子は保存しない。
- 導出は `doc-model` の 1 つのコードで行い、ブラウザと Worker が使う。Document Server は導出しない。上書きのキーの形・上限と、コンポーネントの参照の循環だけを確かめる。
- 導出したノードの ID は `(instance_id, path)` で、決定的に決まる。選択・コメントの固定・他の人の選択の表示に使う。
- 導出したノードへの編集は、上書きの項目の書き込みに変える。上書きできるプロパティの表は `doc-model` に 1 つだけ置く。
- メインからノードが消えた上書きは、孤立として持ち続ける。ノードが戻れば効く。
- 名前の経路は、バリアントの切り替えとインスタンスの入れ替えで、上書きを新しいメインに引き継ぐときにだけ使う（[ADR-0022](0022-component-properties-and-variants-by-id.md)）。
- 2 を採らない理由：
  - メインの 1 回の編集が、インスタンスの数だけの変更になる。1 万のインスタンスなら 1 万の変更をジャーナルに書き、全員に配る。
  - 写したノードと上書きの区別を、別に持つ必要がある（どのプロパティが上書きで、どれがメインから写した値か）。
  - サーバーが写す間に、別の人がインスタンスを編集すると、写しと上書きの競合の規則が要る。
- b を採らない理由：メインで名前を変えると、上書きが外れる。同じ名前のレイヤーが複数あると、どれに当たるか決まらない。
- c は 2 を前提にする。
- y を採らない理由：2 人が同じインスタンスの別の上書き（1 人は文言、1 人は色）を同時に書くと、片方が消える。

## Consequences

- 良くなること：
  - メインの編集が、1 つの変更で済む。ファイルの大きさが、インスタンスの数に比例して増えない。
  - 名前の変更・並べ替え・移動で、上書きが外れない。
  - 別々の上書きの同時編集が、両方残る。
- 引き受けるコスト：
  - クライアントに導出と増分の再計算の仕組みが要る。導出したノードもメモリと描画の対象になるので、上限（1 ファイル 50 万、深さ 16）を置く。
  - 上書きの項目ごとの競合の単位は、document-model.md の `kind = map`（`MapSet`）に頼る。
  - 導出したノードは保存されないので、書き出し・サムネイル・検索の索引（中身の検索。[search.md](../architecture/search.md)）も導出を通す必要がある。
  - 孤立した上書きがファイルに残る。数を計測し、すべての取り消しとデタッチで消す。

## Confirmation

- 性質ベーステスト：任意のメインへの編集の列で、元のノードが残る限り上書きが効き続ける。
- 性質ベーステスト：増分の再導出の結果が、最初から導出した結果と一致する。WASM とネイティブで一致する。
- 決定表のテスト：上書きできるプロパティの表（components-and-libraries.md の 3.4 節）。
- 結合テスト：2 つのクライアントが同じインスタンスの別の上書きを同時に書き、両方が残る。
