# ADR-0012: Undo は自分の変更を打ち消す新しい変更として送る。他の人が後から上書きした値は戻さず、Redo の項目は Undo を実行した時点の値で作る

## Context

1 人で使うツールの Undo は、「前の状態に戻す」でよい。同時編集では、自分の変更の後に他の人が同じファイルを変えている。前の状態に丸ごと戻すと、他の人の変更まで消える。

[ADR-0002](0002-central-authoritative-multiplayer.md) で、Undo は自分の変更を打ち消す新しい変更として送り、本家の原則を守ると決め、詳細をこの領域に任せた。本家の原則は「たくさん Undo して、コピーして、Redo で今に戻ったとき、文書は変わっていない」で、Undo と Redo は実行の時点で逆の履歴を書き換える（[How Figma's multiplayer technology works](https://www.figma.com/blog/how-figmas-multiplayer-technology-works/)、2019-10-16、2026-09-27 に確認）。他の人が上書きした値を本家の Undo が戻すかは、記事に書かれていない（**未検証**）。

## Options

1. **自分が書いた値がまだ残っている鍵だけを戻す。他の人が上書きした鍵は戻さない**
2. **自分の変更の前の値に、無条件で戻す**
3. **サーバーでファイル全体の履歴を持ち、選択的に取り消す（変換を伴う）**

## Decision

1 を採用する。詳細は [multiplayer.md](../architecture/multiplayer.md) の 10 節。

- 履歴はクライアント・ファイルごと。自分の操作だけを積む。200 項目まで、タブを閉じたら消える。
- 項目は、1 つの利用者の操作（ドラッグの始まりから終わり、分けて送った大きな貼り付け）ごとに、触れた鍵の「前の値」と「自分が書いた値」を持つ。
- Undo：今の値が「自分が書いた値」と同じ鍵だけを「前の値」に戻す `ChangeSet` を送る。同時に、その時点の値で Redo の項目を作る。Redo も同じ規則で作る。
- ノードの削除の Undo は、同じ ID で作り直す。親が消えていたら、同じページの直下に元の絶対位置で作る。ノードの作成の Undo は、そのノードを消す（他の人の子があれば確認を出す）。
- Undo がサーバーに拒否されたら、その項目を捨て、理由を出す。
- 注記（2026-09-27、統合の工程で明記）：項目に記録するのは入力のプロパティだけで、`derived` のプロパティ（`derived_layout`）は記録しない。Undo の `ChangeSet` には、戻した入力から計算し直した `derived_layout` を入れる。レイアウトの修復の `Set` は Undo の項目にしない（[ADR-0019](0019-auto-layout-engine-and-layout-persistence.md)、[layout.md](../architecture/layout.md) の 4.2 節）。決定の中身は変えない。
- 2 を採らない理由：自分の Undo で、他の人の後からの編集が黙って消える。
- 3 を採らない理由：ADR-0002 で OT を採らない理由と同じく、変換の組み合わせが多く、正しさを確かめにくい。

## Consequences

- 良くなること：
  - Undo が他の人の作業を壊さない。
  - サーバーに Undo の仕組みが要らない。
- 引き受けるコスト：
  - 他の人が上書きした鍵が戻らないので、Undo の結果が「完全に前の状態」にならないことがある。画面に「一部は他の人が変更したため戻していません」を出す。
  - 削除の Undo のために、消したノードと子孫のプロパティをクライアントのメモリに持つ。

## Confirmation

- 性質ベーステスト（PROP-MP-006）：1 人の編集で、k 回 Undo、コピー、k 回 Redo の後、状態が元と一致する。
- 性質ベーステスト（PROP-MP-007）：他の人が上書きした鍵は、Undo で変わらない。
- E2E：2 つのブラウザで、A の移動・B の色の変更・A の Undo の後、B の色が残る。
