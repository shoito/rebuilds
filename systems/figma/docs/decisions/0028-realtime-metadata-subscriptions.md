# ADR-0028: メタデータのリアルタイムの更新は、トリガーで書く無効化の outbox と、単純な問い合わせへの分解・再取得の購読層で配る

## Context

コメント、通知、ファイルの一覧、共有の設定、版の一覧は、開いている全員の画面に、すぐに反映したい。これらは Aurora にある（[ADR-0005](0005-tenancy-and-document-routing.md)）。[architecture/README.md](../architecture/README.md) の 1.2 節は、Realtime のコンテナを「outbox から、メタデータの変更を購読で配る。本家の LiveGraph に相当」と置いた。

本家の LiveGraph は、Postgres の WAL を Kafka で配り、GraphQL に似た問い合わせを結合のない単純な SELECT に分解し、同じ問い合わせを共有・キャッシュした（[LiveGraph: real-time data fetching at Figma](https://www.figma.com/blog/livegraph-real-time-data-fetching-at-figma/)、2021-10-14）。2024 年の作り直し（LiveGraph 100x）では、edge・cache・invalidator の 3 つのサービスに分け、変更ではなく無効化を送り、問い合わせを「易しい式 AND 難しい式」に正規化して易しい式だけで無効化した。約 700 の問い合わせのうち難しい式は 11 だった（[Keeping it 100(x) with real-time data at scale](https://www.figma.com/blog/livegraph-real-time-data-at-scale/)、2024-05-17）。いずれも 2026-09-27 に確認。

## Options

変更の検知：

1. **トリガーで無効化のキーを outbox の表に書く**（同じトランザクション）
2. **アプリのコードで outbox を書く**（他の題材の transactional outbox と同じ）
3. **WAL の論理レプリケーションから無効化を作る**（本家の形）

配り方：

- a. **無効化と再取得**：変更の中身は送らず、影響する問い合わせを取り直し、ビューの差分を送る
- b. **変更の中身を送る**：行の変更をそのままクライアントへ送り、クライアントでビューに当てる

## Decision

1 と a を採用する。詳細は [comments-and-notifications.md](../architecture/comments-and-notifications.md) の 5 節。

- ビューは、1 つの表への等価の条件だけの問い合わせに分解する。無効化のキーは、等価の条件の列の値から機械的に決まる。
- 購読の対象の表に AFTER のトリガーを置き、変更された行の無効化のキーを `realtime_invalidations` に同じトランザクションで書く。invalidator がそれを読み、Valkey の pub/sub で edge に配る。
- edge は、問い合わせの結果を Valkey にキャッシュし、無効化を受けたら writer から取り直し、ビューの差分を送る。購読の開始と `acl.changed` で判定関数を通す。
- 取りこぼしは、60 秒の期限切れと、再接続での全取り直しで回収する。
- 2 を採らない理由：書き込みの経路ごとに outbox を書く必要があり、書き忘れが「画面が更新されない」不具合になる。トリガーなら、表に書く限り漏れない。
- 3 を採らない理由：S1 では、論理レプリケーションのスロットの運用（遅れで WAL が溜まる、フェイルオーバーでのスロットの扱い）と、WAL を配る基盤（本家は Kafka）の分だけ部品が増える。トリガーの負荷が問題になったら（S2）、3 へ移る。
- b を採らない理由：ビューごとに、行の変更をクライアントで当てる規則（並び、絞り込み、権限）が要る。権限で見えなくなった行の扱いも難しい。本家も、無効化の方が広がりが小さいとしている。

## Consequences

- 良くなること：
  - 書き込みの経路に手を入れずに、リアルタイムの更新が漏れない。
  - 同じ問い合わせを多くの購読者で共有できる（1 ファイルに 500 人）。
  - 権限の判定を、取り直しのたびに行える。
- 引き受けるコスト：
  - トリガーの分、Aurora の書き込みが重くなる。E8 の前に測る。
  - `realtime_invalidations` は組織をまたいで読むので、専用のスキーマとロールにし、RLS の例外にする（中身は ID のキーだけ）。
  - 範囲や結合が要るビューは、等価の問い合わせを組み合わせる形に書き直す必要がある。
  - 取り直しを writer から行うので、S2 で writer の読み取りが重くなりうる。

## Confirmation

- 性質ベーステスト：任意の購読の対象の表への書き込みで、その行を含む問い合わせの無効化のキーが出る。書き込みが止まれば、ビューが DB を直接読んだ結果と一致する。
- lint：購読の対象の表には、無効化のトリガーがある。ビューの問い合わせは、等価の条件だけを使う。
- 負荷テスト：コミットから購読者の画面まで p99 1 秒。トリガーによる書き込みの時間の増え方。
