# ADR-0051: Document Server は、ファイルごとのメモリを見積もって受け入れを決め、タスクのメモリの 75% を上限にする。大きなファイルは別の群れに置く

## Context

Document Server は、開いたファイルを丸ごとメモリに持つ（[ADR-0003](0003-journal-and-checkpoints.md)）。ファイルの大きさは、数 KB から数 GB まで、何桁も違う（[ADR-0005](0005-tenancy-and-document-routing.md)）。1 つのタスクがメモリを使い切ると、そのタスクの全ファイルが落ち、回復（NFR-007）が一度に集中する。

- 10 万ノードの `Doc` は 200 MiB 以内を目標にする（[document-model.md](../architecture/document-model.md) の 10 節）。1 ファイルの上限は 100 万ノード、チェックポイント全体で圧縮の前 2 GiB（同 11 節）。
- チェックポイントは、HAMT の写しを取り、変わったページだけを別のスレッドで直列化する（[file-storage-and-history.md](../architecture/file-storage-and-history.md) の 5.2 節）。直列化の間、写しの差分と出力の分だけメモリが一時的に増える。
- 直近の確定した変更（最大 1 万件か 60 秒）をメモリに持つ（[multiplayer.md](../architecture/multiplayer.md) の 9 節）。
- ECS のタスクには、メモリの硬い上限がある。超えれば、そのタスクは強制終了する。

## Options

1. **ファイルごとのメモリを見積もり、Router が受け入れの前に空きを確かめる。タスクの上限の 75% まで**
2. **ファイルの数だけで上限を決める**
3. **上限を決めず、メモリの圧迫でファイルを追い出す**

## Decision

1 を採用する。数値は [capacity.md](../architecture/capacity.md) の 3 節。

- **見積もり**：開く前は、Aurora の `files.size_bytes`（圧縮の前のチェックポイントの大きさ）× 係数（初期値 3。**未検証**。E7 の計測で置き換える）＋ 固定の 16 MiB（直近の変更、セッションの表、待ち行列）。開いた後は、Document Server が実際の使用量（HAMT の節の数×大きさ、直近の変更のバッファ）を 5 秒ごとに数え、`ds_liveness` の負荷に書く（[ADR-0047](0047-router-task-liveness-and-file-assignment.md)）。
- **受け入れ**：Router は、見積もりが「タスクのメモリ × 0.75 − 使用中」に収まるタスクだけを選ぶ。残りの 25% は、直列化の一時的な増加、Gateway との接続のバッファ、Rust の実行時に使う。
- **群れ**：見積もりが 1.5 GiB を超えるファイルは `ds-large`（120 GB）に置く（[ADR-0046](0046-multiplayer-compute-on-fargate-with-drain.md)）。`ds-standard`（60 GB）の 1 ファイルの上限は 1.5 GiB。
- **直列化の同時の数**：1 タスクで同時に直列化するチェックポイントは 4 つまで。大きなファイルは 1 つずつ。
- **圧迫のとき**：
  - 使用が 80% を超えたら、Router はそのタスクに新しいファイルを置かない（`ds_liveness` の `state = full`）。
  - 85% を超えたら、そのタスクは、編集者のいない（閲覧だけの）ファイルと、最近の変更のないファイルから、他のタスクへ渡す（`handoff`）。
  - 置ける場所がないときは、ECS のサービスの台数を増やし、開く要求を最大 10 秒待たせる。それでもなければ `Kick(overloaded, retry_after_ms)` を返す。
- **1 タスクのファイルの数**：5,000 まで（file actor の数とスケジューラーの公平さのため）。
- 2 を採らない理由：ファイルの大きさの差が大きすぎ、数では空きを表せない。
- 3 を採らない理由：追い出しは回復（読み込み直し）を伴い、編集中のファイルが止まる。圧迫の最中は、追い出しの直列化そのものがメモリを要する。

## Consequences

- 良くなること：
  - 1 つの大きなファイルが、同じタスクの他のファイルを巻き込んで落とすことを防ぐ。
  - 大きなファイルの置き場所が決まり、回復の時間を見積もれる。
- 引き受けるコスト：
  - タスクのメモリの 25% を、いつも空けておく。
  - 見積もりの係数がずれると、受け入れすぎか、台数の過剰になる。E7 と E12 の計測で直す。

## Confirmation

- 負荷試験（E12）：参照ファイル（1 万・10 万・30 万・100 万ノード）を混ぜて開き、どのタスクもメモリの 90% を超えない。
- 計測：見積もりと実際の使用量の比の分布（ファイルの大きさの区分ごと）。
- 障害注入：1 つのタスクに大きなファイルを集中させても、80% で受け入れが止まり、85% で渡しが始まる。
