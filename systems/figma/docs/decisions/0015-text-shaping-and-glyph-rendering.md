# ADR-0015: テキストは HarfRust・Skrifa・ICU4X で整形し、48 px 以下はグリフのアトラス、超えたらパスで描く。グリフのないときの和文のフォールバックはファイルの設定で決める

## Context

[ADR-0004](0004-gpu-rendering-in-wasm.md) で、フォントの読み込み・整形・改行はエンジンの中で行い、ブラウザのテキストの描画を使わないと決めた。グリフを輪郭のパスで描くかアトラスにするか、和文のフォールバックをどうするかは、この ADR で決める。

満たすべきこと：

- 同じファイルを開いた全員で、テキストの折り返しと大きさが一致する。オートレイアウトの結果がテキストの大きさで決まるため（[layout.md](../architecture/layout.md) の 6 節）。
- 画面と書き出し（PNG・PDF）で、同じ形になる。
- ズームは 1% 未満から数千% まで連続で変わる。小さな文字は速く、大きな文字は輪郭が崩れずに描く。
- 日本の市場を先に狙う。和文と欧文の混植、欧文のフォントに和文を打ったときの代わりのフォント、絵文字を扱う（[intent.md](../intent.md)）。

部品の事情（2026-09-27 に確認）：

- rustybuzz は開発を終えてアーカイブされ、HarfRust への移行を勧めている（[harfbuzz/rustybuzz](https://github.com/harfbuzz/rustybuzz)）。
- HarfRust（0.13.3）は HarfBuzz v14.3.1 に揃う。よく使うフォントで HarfBuzz より 25% 未満の遅さ。フォントの大きさを持たない。不正なフォントはエラーにし、Graphite に対応しない（[harfbuzz/harfrust](https://github.com/harfbuzz/harfrust)）。
- Skrifa（0.47）はフォントの解析とグリフの輪郭を持ち、read-fonts の上にある（[googlefonts/fontations](https://github.com/googlefonts/fontations)）。
- Parley（0.11）は、Fontique（システムのフォントの列挙とフォールバック）、HarfRust、Skrifa、ICU4X を組み合わせたリッチテキストのレイアウトである（[linebender/parley](https://github.com/linebender/parley)）。
- 本家のテキストの描画の方式と、和文のフォールバックの順序は、公開されていない（未検証）。

フォントの出どころ（同梱・組織・端末）、探す順、見つからないときの代わりのフォントは [ADR-0036](0036-font-sources-and-licensing.md) が決める。この ADR は、見つかったフォントで整形し、描き、グリフがない文字をどうするかを決める。

## Options

整形とレイアウト：

1. **HarfRust・Skrifa・ICU4X の上に、自前の薄いテキストのレイアウトを書く**
2. Parley を使う
3. ブラウザの Canvas 2D で測って描く

グリフの描き方：

- a. **小さい文字はアトラス、大きい文字はパス**
- b. すべてパス
- c. すべてアトラス（SDF を含む）

グリフのないときのフォールバック：

- x. **ファイルの設定で決めた順（指定のフォント → ファイルの和文のフォールバック → 絵文字 → `.notdef`）**
- y. 端末・ブラウザの既定のフォールバックに任せる

## Decision

1、a、x を採用する。

### 整形

- 文字列を、ICU4X で書記素・文字種・双方向に分け、フォールバック（下）で決めたフォントごとの走り（run）にする。走りを HarfRust で整形する。
- HarfRust の結果（UnitsPerEm の整数）を、f64 で文字の大きさに掛ける。改行と行の組み立ては [layout.md](../architecture/layout.md) の 5 節。
- 整形の結果は `(font_id, 走りの文字列, 大きさ, 機能の設定)` でキャッシュする。
- 整形は 1 つの trait の裏に置く。HarfRust の速度や互換性が足りなければ、HarfBuzz（C++）の WASM 版に替えられるようにする。

### フォントの識別

- ノードは `font_family`・`font_style` の名前でフォントを指す。名前からファイルを解決する順は ADR-0036 に従う。
- エンジンの中では、解決したファイルを中身の SHA-256（`font_blob_id`）で識別し、整形とアトラスのキャッシュの鍵にする。
- 同梱と組織のフォントは全員が同じバイト列を使うので、整形の結果が一致する。端末のフォントはその人の画面だけで使い、他の人は保存された `derived_layout` で行の位置を合わせる（[ADR-0019](0019-auto-layout-engine-and-layout-persistence.md)）。

### 和文のフォールバック

書記素クラスタごとに、すべての文字を `cmap` に持つ最初のフォントを使う。

1. ノードに指定したフォント
2. ファイルの設定の和文のフォールバックのフォント（`DOCUMENT` の `cjk_fallback_font`。既定は同梱の Noto Sans JP）
3. 記号・絵文字のフォント（COLRv1）
4. 指定したフォントの `.notdef`

- フォールバックの設定をファイルに持つのは、全員で同じフォントが選ばれるようにするため（端末ごとの既定に頼らない）。
- 太さは、指定の太さに最も近いものにする。

### グリフの描き方

- 画面の上の大きさが 48 px 以下：R8 のアトラス（2048×2048、最大 4 ページ）。鍵は `(font_id, glyph_id, 大きさ（1/4 px の刻み）, 横の端数の位置（4 段）, 可変の軸の値のハッシュ)`。ラスタライズは [ADR-0013](0013-scene-graph-and-tile-rendering.md) と同じ面積の被覆率を CPU で行う。
- 48 px を超える：グリフの輪郭を、ADR-0013 のパスとして描く。
- カラーのグリフ（COLRv1）：Skrifa の塗りの木を、パスとグラデーションの描画に変える。48 px 以下は RGBA8 のアトラス。
- ヒンティングはしない。

### 採らない理由

- 2 を採らない理由：Parley は有望だが、フォントの列挙とフォールバックを Fontique（端末のフォント）に寄せる作りで、全員で同じフォールバックにする（x）には置き換えが要る。和文の禁則の強さ、行の組み立ての細部（layout.md の 5 節）と、結果の決定性を自分で持つ必要がある。バージョンを固定し、整形の結果の差を比較するテストの対象（参照の実装）には使う。
- 3 を採らない理由：ブラウザと OS で測り方と描き方が違い、全員の結果が一致しない。本家も 2015 年にこれを避けた。
- b を採らない理由：小さな文字のパスの平坦化と振り分けは、1 画面に数万のグリフがあると CPU の予算を超える。アトラスなら同じグリフを使い回せる。
- c を採らない理由：大きな文字をアトラスにすると、ズームのたびにアトラスが溢れる。SDF は角が丸くなり、書き出しと形が変わる。
- y を採らない理由：OS とブラウザで既定のフォールバックが違い、同じ文字が人ごとに別のフォントで描かれ、テキストの幅とオートレイアウトの結果が変わる。

## Consequences

- 良くなること：
  - 全員の画面とサーバーの書き出しで、テキストの折り返しと形が一致する。
  - 和文と欧文の混植、フォールバックを、ファイルの設定で決められる。
- 引き受けるコスト：
  - ファイルの設定の和文のフォールバックが、同梱のフォントに限られる。
  - 和文のフォントは 1 書体で数 MB あり、開く時間（NFR-003）とメモリ（フォント 150 MB の予算）に効く。
  - ヒンティングをしないので、小さな文字が OS の文字より薄く見えうる。
  - テキストのレイアウトを自前で保守する。

## Confirmation

- 参照画像のテスト：欧文、和文、混植、フォールバック、絵文字、縦に長い段落を、WebGPU・WebGL2・ネイティブで描き、判定の値に収まる。
- 性質ベーステスト：任意の文字列とフォントの組で、WASM とネイティブの整形の結果（グリフの ID と位置の f64 のビット）が一致する。アトラスの経路とパスの経路の被覆率の差が、境目の 48 px で 1/255 以内。
- ベンチマーク：日本語の長文（1 万字）の整形が、HarfBuzz（ネイティブ）の 1.5 倍以内。超えたら整形の実装の差し替えを検討する。
- 本家との比較：欧文のフォントに和文を打った場合の見え方を、E4 で本家と比べる。
