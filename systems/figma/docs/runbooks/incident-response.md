# Runbook: インシデント対応

- Owner: Ops
- 対応するアラート: すべての呼び出し（page）のアラート（[observability.md](../architecture/observability.md) の 6 節）。個別の場面は「この題材に固有の場面」の節
- 最終確認日: 2026-09-27

個別の手順（[deploy-and-rollback.md](deploy-and-rollback.md)、[disaster-recovery.md](disaster-recovery.md)）の上に立つ、共通の進め方と、この題材に固有の場面（人が集まるファイル、再接続の殺到、ジャーナルの飛び、二重の持ち主、ファイルの状態の食い違い、テナントの分離の破れ）。進め方の骨格は Slack の [incident-response.md](../../../slack/docs/runbooks/incident-response.md) と同じ。

## 症状

次のどれかのときに、インシデントを宣言する。迷ったら宣言し、後で重さを下げる。

- 呼び出しのアラートが鳴った
- 利用者や社内から、「編集が保存されない」「他の人の変更が見えない」「ファイルが開けない」「他の組織のファイルが見えた」の報告が来た
- 漏洩のテスト・作り直しの検証・`parity` の抜き取りで不一致が出た

## 影響

### 重さ（severity）

| 重さ | 基準 | 例 | 最初の応答 | 告知 |
| --- | --- | --- | --- | --- |
| SEV1 | 他の組織のファイル・メタデータが見えた。確定を返した編集が失われた。全体でファイルを開けない・確定しない | テナントの分離の破れ、リージョンの障害、ジャーナルの書き込みの全停止 | 5 分以内 | 30 分以内に利用者へ。以後 30 分ごと |
| SEV2 | 一部のファイルが開けない・確定しない。ジャーナルの飛び。ファイルの状態の食い違い。編集の SLO の速いバーンレート | Document Server の群れの障害、AZ の障害、再接続の殺到 | 15 分以内 | 1 時間以内（影響があれば） |
| SEV3 | 劣化しているが、編集は失われない。回避できる | 1 つのファイルが遅い、書き出しの遅れ、通知の遅れ | 営業時間内 | 必要なら |
| SEV4 | 利用者への影響がない | 1 つの Worker の失敗の増加 | 営業時間内 | なし |

**確定した編集の損失の疑い、テナントの分離の破れの疑いは、範囲が 1 件でも SEV2 以上にする。**

## 確認

1. どのアラート・報告から始まったかを記録する。
2. 影響の範囲を見る：全体か、特定の AZ・Document Server のタスク・ファイル・組織・ブラウザ・ビルドか。
3. 直近の変更を見る：デプロイ（サーバー、クライアントのビルドの配信の段）、フラグ（UI・文書・書き込みの解禁）、マイグレーション、インフラ、AWS Health。
4. 編集の損失の有無を見る：`ds_fence_lost_total`、`ds_journal_gap_total`、作り直しの検証の不一致、クライアントの報告の `pending_count`。

## 対処

### 役割

| 役割 | 担う人 | 責任 |
| --- | --- | --- |
| 指揮者（IC） | 最初に応答したオンコール。SEV1 では Ops の責任者に引き継いでよい | 重さ、方針、大きな判断（読み取り専用、ファイルの編集の停止、リージョンの切り替え） |
| 作業者 | オンコールの Ops、呼ばれた Dev | 調査と復旧 |
| 文書の担当 | Dev のテックリード（`doc-model`・ジャーナルの持ち主） | 編集の損失・状態の食い違いの評価、修復の変更の承認 |
| 連絡係 | IC が指名する（PM が望ましい） | 利用者、社内への連絡 |
| 記録係 | IC が指名する | 時刻付きの記録 |

SEV1 では、指揮者は手を動かさない。

### 進め方

1. **宣言する。** インシデント用の場を、このシステムと別の道具に作る。
2. **被害を止めることを、原因の特定より優先する。** 順番：
   - 直近の変更のフラグを切る
   - 直近のデプロイ・ビルドの配信を戻す（[deploy-and-rollback.md](deploy-and-rollback.md)）
   - 問題のファイルの編集を止める（下の「ファイルの編集を止める」）
   - 全体の編集を止める（`ops.multiplayer_read_only`。閲覧は続く）
   - 容量を増やす
3. **ジャーナル・チェックポイント・ログを消さない、書き換えない。** 証拠であり、回復の材料である。修復は、新しい変更として当てる。
4. **ファイルの中身を見ない。** 調べるのは ID・数・大きさ・時刻だけ。中身を見る必要があれば、所有者の同意と Ops の責任者の承認を得て、監査の記録を残す（[security.md](../architecture/security.md) の 8 節）。
5. 30 分ごとに状況を更新する（SEV1・SEV2）。
6. 回復を確かめてから閉じる：SLO が戻る、合成のボットが成功する、`router_orphans` が 0 に戻る。

### ファイルの編集を止める

1 つのファイルだけを止めたいときの共通の操作。

1. 運用者の画面で、ファイルを `maintenance` にする（`files.state`。[data-model/organization.md](../architecture/data-model/organization.md) の `files`）。API は閲覧のチケットだけを出し、`acl.changed` で Gateway が開いている接続を読み取りに下げる。ジャーナルの飛び（`journal_gap`）のときは、Document Server も読み込まない。
2. 所有者に、アプリ内で「一時的に編集を止めています」を出す。
3. 解くときは `maintenance` を外す。

## この題材に固有の場面

### 人が集まるファイル

**症状**：`ds_write_budget_files{stage="100%"}` が続く、1 つの Document Server のタスクの CPU が高い、そのファイルの利用者から「反映が遅い」の報告。全社の発表や会議の始まりに多い。

1. Grafana の「人が集まるファイル」（上位のファイルの記録。[observability.md](../architecture/observability.md) の 4.3 節）で、`file_id`、参加の数、確定の数、書き込みの単位、メモリを見る。
2. 書き込みの予算の段（[ADR-0052](../decisions/0052-journal-throughput-and-hot-file-budget.md)）が働いているか（クライアントのまとめの間隔が 100ms・200ms に広がっているか）を見る。
3. `journal` の `ThrottledRequests` が 0 か。0 でなければ、予算の値がパーティションの実際の上限に合っていない。そのファイルの予算を ops の設定で下げる（毎秒 400 → 250 単位）。
4. 同じタスクの他のファイルが巻き込まれていれば、router の「ファイルを渡す」で、人が集まるファイルを空いた `ds-large` のタスクへ移す（中断は 1〜2 秒）。
5. 参加が 500 人に近いときは、後から入る人が「動かないバージョン」になる（[multiplayer.md](../architecture/multiplayer.md) の 12.3 節）。所有者に、閲覧の人にはプロトタイプの表示や書き出しの画像を案内するよう伝える。
6. 収まらず、他のファイルの SLO に響くなら、そのファイルの在席の配信を 200ms にする ops の設定を入れる。

**エスカレーション**：同じファイルで毎週起きる → 1 ファイル 500 人を超える需要として PM に上げる（[multiplayer.md](../architecture/multiplayer.md) の 17 節の持ち越し）。

### 再接続の殺到

**症状**：`gw_reconnect_total` が平常の 10 倍、API の 429（チケットの発行）が続く、`edit_open` の悪いイベントが増える。Gateway の落ち、Document Server の群れの落ち、入口の障害の回復、強い再読み込みの後に起きる。

1. きっかけを特定する：Gateway のタスクの停止（ECS のイベント）、Document Server の停止、デプロイ、`min_client_build` の変更、入口（CloudFront・ALB）の障害。
2. **散らしが効いているかを見る。** 再接続の時刻の分布（`gw_open_total` の 1 秒ごと）が、0〜5 秒・`retry_after_ms` に散っているか。散っていなければ、クライアントのビルドの不具合を疑う。
3. **API のチケットの発行を守る。** 429 が続くなら、api のタスクを増やす（最大 24）。判定関数のキャッシュのヒットの率を見る（`acl_version` の変更が同時に大量に起きていないか）。
4. **Gateway を増やす。** 接続が偏っているなら、`Kick(overloaded, retry_after_ms)` で散らす（Gateway の設定で上限を下げる）。
5. **router を守る。** 割り当ての上限（毎秒 200）に張り付いていれば、Document Server の空きを増やす（割り当てがメモリの空きを待っていることが多い）。
6. デプロイがきっかけなら、入れ替えの割合を下げる（Gateway 10% → 5%、ドレインの波を小さく）。
7. 収まらないとき、`ops.multiplayer_read_only` で編集を止めると、再接続の後の送り直しの負荷が減る。最後の手段にする。

**エスカレーション**：チケットの発行が律速で、30 分たっても収まらない → Dev のテックリードを呼ぶ。再開のトークンが効いているか（`gw_reconnect_total` の `auth = resume_token` の割合、`Kick(ticket_required)` の数、Valkey の状態）を先に見る。Gateway の落ちなのにトークンが外れていれば、鍵（`kid`）の配布か Valkey の組織の `acl_version` を疑う（[capacity.md](../architecture/capacity.md) の 2.2 節、[permissions-and-sharing.md](../architecture/permissions-and-sharing.md) の 5.5 節）。

### ジャーナルの飛び

**症状**：`ds_journal_gap_total` が 1 以上。回復で、ジャーナルの項目の `seq` が続かない（[file-storage-and-history.md](../architecture/file-storage-and-history.md) の 4.4 節）。ファイルは「修復が要る」になり、編集できない。

大阪への切り替えの直後の最初の回復での飛びは、失った範囲であり、この場面ではない（[disaster-recovery.md](disaster-recovery.md) の B）。

1. SEV2 を宣言する（確定した編集の損失の疑い）。
2. 影響するファイルの ID、飛びの範囲（`seq` の前後）、そのファイルの最後の `epoch` と持ち主の記録を集める。
3. 原因を切り分ける：
   | 見えること | 疑う原因 |
   | --- | --- |
   | 飛びの範囲の項目が、DynamoDB に `blob_key` だけあり、S3 の本体がない | 大きな変更の S3 の書き込みの不整合、S3 の複製の遅れ（大阪）。本体が後から届くか、古いバージョンがあるかを見る |
   | 飛びの範囲の直前に `epoch` が変わっている | 二重の持ち主の書き込みの交ざり（フェンスの不具合）。「二重の持ち主」の場面も見る |
   | TTL の期限を過ぎた項目がない | 回復のジョブの漏れ（手放さずに 30 日）。`router_orphan_oldest_seconds` の履歴を見る |
   | 飛びの範囲が、PITR の時点では存在する | 誤った削除（掃除・完全な削除のジョブの不具合、運用の誤り） |
4. **項目を戻せるなら戻す**：DynamoDB の PITR（35 日）から、別の表へ復元し、飛びの範囲の項目だけを写す（`seq` の範囲で、そのファイルのパーティションだけ）。写した後、ファイルの `maintenance` を外して回復させる。
5. **戻せないなら**、`journal-gap-or-corruption.md`（[file-storage-and-history.md](../architecture/file-storage-and-history.md) の 17 節の提案）の手順で、飛びの手前までの状態をチェックポイントとして書き、バージョンの一覧に残し、所有者に失った範囲（時刻）を知らせる。Dev のテックリードの承認を得る。
6. 同じ原因のファイルが他にないか、回復の記録（`ds_journal_gap_total` のログの `file_id`）と、作り直しの検証の不一致を全体で見る。

**エスカレーション**：飛びが 2 ファイル以上、または原因が二重の持ち主・誤った削除 → SEV1。Dev のテックリードと Ops の責任者を呼ぶ。

### 二重の持ち主

**症状**：`ds_fence_lost_total` がデプロイの外で増える、`Kick(owner_changed)` が特定のファイルで繰り返す。

1. フェンスが働いているなら、ジャーナルは分かれない（[ADR-0024](../decisions/0024-journal-items-and-fencing.md)）。まず、ジャーナルの飛びと作り直しの検証の不一致がないことを確かめる。
2. 原因を見る：`ds_liveness` の延長の失敗（DynamoDB の遅延、タスクの CPU の張り付き）、時計のずれ、ネットワークの分断、router の割り当ての不具合。
3. 同じファイルが繰り返し取り合われているなら、そのファイルを「ファイルの編集を止める」で止め、原因のタスクを止めてから解く。

### ファイルの状態の食い違い

**症状**：作り直しの検証・`parity` の抜き取りの不一致、`layout_divergence`、不変条件の破れ、利用者の「人によって見え方が違う」。

1. SEV2 を宣言する。影響するファイル、ビルド、Document Server のバージョン、文書のフラグ（`Welcome.features`）を集める。
2. 直近に、`doc-model`・`layout`・`text` の変更、文書のフラグの変更、書き込みの解禁があれば、それを戻す（[deploy-and-rollback.md](deploy-and-rollback.md) の「悪化したとき」）。
3. ファイルを `Kick(resync_required)` で開き直させ、食い違いが消えるかを見る（クライアントの側だけの食い違いなら消える）。
4. サーバーの状態が壊れている（不変条件の破れ）なら、`document-invariant-violation.md`（[document-model.md](../architecture/document-model.md) の 17 節の提案）の手順で、修復の変更を当てる。

### テナントの分離の破れ

**症状**：他の組織のファイル・コメント・サムネイル・名前が見えたという報告、漏洩のテストの失敗。

1. **SEV1 を宣言する。** Ops の責任者、Dev のテックリード、セキュリティの担当、法務を呼ぶ。
2. 経路を特定する（[permissions-and-sharing.md](../architecture/permissions-and-sharing.md) の 11 節の経路の一覧）。直近のデプロイ・フラグ・ポリシーの変更を戻す。
3. 経路を止める：該当の API・機能を ops フラグで止める（書き出し、サムネイル、検索、公開 API、共有のリンク）。署名付き URL の鍵を入れ替えて、出した URL を無効にする（CloudFront の鍵のグループ）。
4. 影響の範囲を、判定のログ（規則の ID、主体と資源の ID）、監査ログ、CloudFront のアクセスログで調べる。中身は見ない。
5. 報告の要否と期限（個人情報保護委員会と本人）は、法務が判断する（**法務の確認待ち**。[intent.md](../intent.md) の L5）。記録を法務へ渡す。
6. 詳細は `tenant-isolation-breach.md`（[security.md](../architecture/security.md) の 14 節の提案）。

## エスカレーション

| 状況 | 連絡先 |
| --- | --- |
| SEV1 | Ops の責任者、Dev のテックリード、PM（告知） |
| 確定した編集の損失の疑い | Dev のテックリード（ジャーナルと回復の持ち主） |
| テナントの分離の破れ、個人情報の漏洩の疑い | セキュリティの担当、法務 |
| AWS のサービスの障害 | AWS のサポート（Business 以上のケース） |
| 1 時間たっても SEV1 が収まらない | 経営の責任者へ報告 |

## 事後

- SEV1・SEV2 は、5 営業日以内に事後の検討（責めない形）を行い、記録を残す。
- 調査結果と再発の防止を、`changes/` の新しい `intent.md` として起票する（Maintain 段）。
- 失った編集の範囲と、取り戻せた範囲を記録する。
- アラート・runbook で足りなかったことを、ここと [observability.md](../architecture/observability.md) の 6 節に反映する提案を出す。
