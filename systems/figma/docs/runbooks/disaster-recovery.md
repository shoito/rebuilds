# Runbook: 災害復旧（AZ の障害、リージョンの障害、取り戻し、戻し、訓練）

- Owner: Ops
- 対応するアラート: AZ の障害（複数のサービスで 1 つの AZ のターゲットが不健全）、大阪からの合成の監視の連続の失敗、`ReplicationLatency`（東京 → 大阪）の超過、S3 の RTC の 15 分超え、訓練（四半期に 1 回）
- 最終確認日: 2026-09-27

構成と目標は [infrastructure.md](../architecture/infrastructure.md) の 7 節、方針は [ADR-0048](../decisions/0048-osaka-dr-with-journal-generations.md) にある。目標は NFR-006（AZ の障害で確定した編集を失わない）と NFR-009（リージョン：RPO 1 分、RTO 1 時間）。

## 症状

| 場面 | 見え方 |
| --- | --- |
| A. AZ の障害 | 1 つの AZ の Gateway・Document Server・Aurora のインスタンスが不健全。AWS Health Dashboard に東京の 1 つの AZ のイベント。`owner_recovery` が一時的に増える |
| B. リージョンの障害 | 東京の入口（`app`・`mp`・`api`）が応答しない。大阪からの合成の監視がすべて失敗する |
| C. 複製の遅れ | `ReplicationLatency` が 10 秒を超え続ける、S3 の複製の待ちが増える（東京は正常） |
| D. 取り戻し | B の後、東京が戻った |
| E. 戻し | B の後、東京へ戻す計画作業 |
| F. 訓練 | 四半期に 1 回（staging）、年 1 回（本番の計画的な切り替え） |

## 影響

- A：その AZ にあったファイルが 15 秒ほど止まり、再接続する。確定した編集は失わない。
- B：切り替えまで（目標 1 時間以内）、ファイルを開けず、編集もできない。ジャーナルの複製の遅れの分（通常 1 秒以内、最大 1 分）の確定した編集が、大阪に届かない。それらは D でバージョンとして取り戻す。
- C：この状態で B が起きると、失う範囲が広がる。

## 確認

1. AWS Health Dashboard と Grafana の AZ ごとの内訳で、1 つの AZ か、リージョン全体かを見分ける。
2. DynamoDB のリージョンの状態（`SuccessfulRequestLatency`、エラー）、S3、Aurora のクラスタのイベントを見る。
3. リージョンの障害を疑うときは、大阪の合成の監視と、別の回線からの到達の両方で確かめる。
4. **`ReplicationLatency`（`journal`・`file_leases`）の直近の値と、S3 の複製の待ちを記録する。** 失う範囲の目安になる（B で使う）。
5. 今の世代（AppConfig の `region.gen`）と、書き込みを受けるリージョン（`region.writable`）を記録する。

## 対処

### A. AZ の障害

基本は自動で回復する。

1. インシデントを宣言する（SEV2 から。[incident-response.md](incident-response.md)）。
2. `router_owner_recovery_seconds` と `router_orphans` を見る。その AZ の Document Server の割り当てが、残る AZ へ移っていることを確かめる。
3. 残る AZ の `ds-standard`・`ds-large`・`gateway` の空きを見る。メモリの 80% を超えたタスクが多ければ、最小のタスク数を上げる（[ADR-0051](../decisions/0051-document-server-memory-admission.md)）。
4. Aurora が別の AZ へ切り替わったことを確かめる。5 分たっても writer がなければ、手動で切り替える。
5. Valkey がレプリカへ切り替わったことを確かめる。チケットの `jti` の記録が一部失われるが、チケットは 60 秒で切れるので、待つだけでよい。
6. AZ が回復したら、台数を平常に戻す。ファイルは、次のデプロイや空きの偏りの解消で自然に散る。急がない。

### B. リージョンの障害（東京 → 大阪）

**切り替えの判断は、インシデントの指揮者（IC）が行い、Ops の責任者が承認する。** AWS の見込みで 30 分以内に回復しそうなら、待つことも選ぶ（切り替えれば、複製の遅れの分が取り戻しの対象になり、利用者の手間が増える）。

1. SEV1 を宣言し、利用者へ告知する（ステータスページ）。
2. **東京の書き込みを止める。** 東京の API と Gateway に届くなら、ops フラグ `ops.multiplayer_read_only` を有効にする（Document Server は新しい `Changes` を `Reject` し、ファイルを手放す）。届かなくても次へ進む。世代で分けたキーが、東京の遅れた書き込みから大阪を守る（ADR-0048）。
3. **失う範囲を記録する。** 「確認」の 4 の値と、東京が応答しなくなった時刻を、インシデントの記録に書く。
4. **世代を上げる。** 大阪の AppConfig で `region.gen = 現在 + 1`、`region.writable = apne3`。
5. **Aurora を切り替える。** Global Database の大阪の二次を昇格させる。
   - 東京の writer が生きていれば、switchover（RPO 0）。
   - 応答しなければ、マネージドなフェイルオーバー（`aws rds failover-global-cluster --allow-data-loss`、大阪で実行）。
   - 大阪の reader を 1 台足す。
6. **アプリを広げる。** 「DR：大阪を有効化」のワークフローで、大阪の各サービスのタスク数を東京と同じにする（状態ファイルは大阪のバケットにある）。Valkey を平常の大きさにする。
7. **DynamoDB の東京のレプリカを外すことを試みる。** 大阪から `UpdateTable` でレプリカの削除を求める。障害中に外せるかは **未検証**（資料に記述がない。E12 の `dr-drill` で、AWS FIS のリージョンの切り離し（複製の停止）の中で確かめる。[How DynamoDB global tables work](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html)、2026-09-27 に確認）。外せなくても続ける。
8. **入口を切り替える。** Terraform の `edge` の変数 `active_region` を大阪にして apply する（`app`・`mp`・`rt`・`api`・`telemetry` の CloudFront のオリジン、`files`・`assets` のオリジンのバケット）。
9. **回復のジョブを見る。** router は、`file_leases` の `region_gen` が古い `owned`・`handoff` の項目を「持ち主なし」とみなす。利用者が開いたファイルから回復し、誰も開かないファイルは回復のジョブが 1 秒に 50 ずつ回復する。`router_orphans` が減ることを確かめる。
   - 回復は、世代をまたぐ読み方になる（大阪にある最新のマニフェスト → 元の世代のジャーナルを飛びの手前まで → 新しい世代に書く。ADR-0048）。
   - `ds_journal_gap_total` は、この場面では「失った範囲」を示す。`修復が要る` にはせず、飛びの手前から続ける（切り替えの後の世代の最初の回復に限る）。
10. **受け付けを段階的に再開する。**
    1. 合成のボット（反映・開く）が大阪で成功することを確かめる。
    2. 大阪の編集の読み取り専用を解く。レート制限を平常の 50% にして開き、15 分ごとに上げる。
11. 利用者へ、再開と影響（障害の直前の数秒の編集が、後から「障害で反映されなかった編集」のバージョンとして戻ること）を告知する。

### C. 複製の遅れ

1. `ReplicationLatency` が 10 秒を超えたら、AWS Health と DynamoDB のメトリクスで原因（リージョンの間の回線、大阪の書き込みのスロットリング）を見る。大阪のレプリカのスロットリングなら、大阪の表の warm throughput と上限を確かめる（グローバルテーブルは容量の設定を同期する）。
2. 30 秒を超えたら、呼び出し。東京が正常なら、切り替えはしない。大阪への複製が戻るのを待つ。
3. S3 の RTC の 15 分超えの事象が続くなら、複製の待ちの大きさと KMS のスロットリング（複製は KMS の要求を使う）を見る。

### D. 取り戻し（東京が戻った後）

1. 東京のリージョンが回復したことを、AWS Health で確かめる。**東京で受け付けは再開しない**（書き込みは大阪のまま）。
2. `dr-salvage` のジョブを流す（「DR：取り戻し」のワークフロー。範囲は切り替えの時刻の前後 10 分）。ジョブは、各ファイルについて、元の世代のジャーナルのうち `base_end_seq` より後の項目を探す。
3. 見つかったファイルごとに、`base_end_seq` の状態にそれらの項目を当てた状態をチェックポイントとして書き、バージョンの一覧に「障害で反映されなかった編集」として足す。今のファイルには混ぜない。
4. 取り戻したファイルの数と項目の数を、インシデントの記録に書く。所有者へ通知する（アプリ内）。
5. 東京で後から書かれたマニフェスト（元の世代のキー）が大阪へ複製されていても、今の世代の回復は使わない。掃除のジョブが、バージョンの印のないものを通常の規則で消す。

### E. 戻す（大阪 → 東京）

別の計画作業として行う。平日の夜に、事前に告知する。急がない。

1. 東京のリージョンと、東京の DynamoDB のレプリカ（外したなら加え直す）、S3 の大阪 → 東京の複製、Aurora の東京の二次が、追いついていることを確かめる。
2. `ops.multiplayer_read_only` を有効にし、大阪の全ファイルを `released`（チェックポイントを書いて手放す）にする。`router_drain_remaining_files` が 0 になるまで待つ。
3. `ReplicationLatency`（大阪 → 東京）と S3 の複製の待ちが 0 になるのを待つ。
4. Aurora を switchover（RPO 0）で東京へ戻す。
5. 東京の AppConfig で `region.gen = 現在 + 1`、`region.writable = apne1`。入口を東京へ戻す。
6. 読み取り専用を解く。大阪の台数を縮小したウォームスタンバイへ戻す。

### F. 訓練

| 訓練 | 頻度 | 中身 | 合格の基準 |
| --- | --- | --- | --- |
| 計画外の切り替え | 四半期に 1 回（staging） | `mp-loadbot` で負荷をかけ、AWS FIS でグローバルテーブルの複製を止め、30 秒後に B の手順で切り替える。その後 D と E | 失った範囲が 1 分以内、`dr-salvage` がすべてをバージョンとして残す、RTO 1 時間以内 |
| 計画的な切り替え | 年 1 回（本番） | E の手順で大阪へ移し、1 日運用して戻す | 失った範囲 0、RTO の実測 |
| AZ の障害 | 半年に 1 回（staging） | FIS で 1 つの AZ を切り離す | `owner_recovery` の p95 15 秒、確定の損失 0 |

- 訓練のたびに、RTO の内訳（判断、Aurora、ECS、入口、回復）を記録し、[infrastructure.md](../architecture/infrastructure.md) の 7.2 節の目安を置き換える。
- 訓練で「障害中に東京のレプリカを外せるか」（B の 7）を確かめる。

## エスカレーション

- B の判断：Ops の責任者（承認）、Dev のテックリード（ジャーナルと回復）、PM（利用者への告知）。
- B の 9 で回復が 30 分たっても進まない、`ds_journal_gap_total` が切り替えの直後の最初の回復の外でも増える → Dev のテックリードを呼ぶ。
- 取り戻しで、見つかった項目の数が「失う範囲の目安」（確認の 4）より大幅に多い → 東京で切り替えの後も書き込みが続いていた疑い。IC に上げ、東京の入口が本当に止まっているかを確かめる。
- 個人情報の漏洩や、組織をまたぐ混入の疑いが出たら → [incident-response.md](incident-response.md) の「テナントの分離の破れ」。

- RTO の内訳を、infrastructure.md の 7.2 節に反映する提案を Dev に出す。
