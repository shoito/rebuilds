Figma は何をするサービスか

Figma は、ブラウザで動く画面のデザインのツールです。デザインのファイルを 1 つだけ置き、全員が同じものを同時に見て編集することで、「どれが最新か分からない」「受け渡しで食い違う」をなくしました。

手元のアプリのように速い

大きなファイルでも、パン・ズーム・変形が 60fps。自分の入力は 1 フレームで画面に出る。

一緒に作れる

他の人の編集とカーソルが 0.25 秒以内に見え、競合しても全員の画面が同じ結果になる。

失わない

確定を返した編集は、サーバーが落ちても失わない。過去のバージョンに戻れる。

使う人は、デザイナー（編集）、開発者（寸法・色の確認と書き出し）、PM・レビュアー（閲覧とコメント）、チームの管理者です。規模の感覚は、S1 で月間 10 万人、同時に開かれたファイル 1 万、同時接続 5 万です。性能の目標は「10 万ノードの参照ファイル」で測ります。日本の市場を先に狙い、和文のフォントと IME の入力を MVP で扱います。

設計の文書で効くところintent.md の「Proposed outcome」と「守るべき振る舞い」、architecture/README.md の 3〜4 節（規模の段階と NFR）。

ファイルの中身はノードの木

デザインのファイルは、表の行ではなくノードの木です。根に 1 つの DOCUMENT、その子にページ（CANVAS）、その下にレイヤーが並びます。ノードは「ID と、プロパティの値の集まり」で、親は子が持つ parent_index のプロパティで指します。

flowchart TD
  D["DOCUMENT 0:0"] --> P1["CANVAS ページ1"]
  D --> P2["CANVAS ページ2"]
  P1 --> F["FRAME ログイン画面"]
  F --> T["TEXT 見出し"]
  F --> G["GROUP"]
  G --> R["RECTANGLE"]
  G --> V["VECTOR"]
  F --> I["INSTANCE ボタン"]

FRAME：画面や部品の枠。自分の大きさを持ち、中身を切り抜け、オートレイアウトを持てる。HTML の div に近い。

GROUP：子をまとめるだけ。自分の位置の入力を持たず、境界は子の和。子が 0 になるとサーバーが消す（T8）。

SECTION：キャンバスの上の区画。画面の流れや作業の段階を整理する。

RECTANGLE・ELLIPSE・VECTOR・TEXT など。子を持たない葉。種類は作った後に変えない。

設計の文書で効くところdocument-model.md の 3 節（ノードの種類と親子の表）・5 節（木の不変条件 T1〜T9）、ADR-0006。

ベクター・パス・ブール演算

ベクターは、点と曲線で形を表す方式です。画素で持たないので、拡大しても劣化しません。曲線は3 次ベジェ（端の点 2 つと、向きを決める接線 2 本）で表します。

ふつうのパス（SVG の path）

点を一筆書きでつないだ列。1 つの点から出る線は 2 本まで。

ベクターネットワーク

点と辺のグラフ。1 つの点から 3 本以上の辺が出てよい。閉じた輪が「領域」になり、領域ごとに塗れる。

塗りの内と外は塗りの規則（非ゼロ・偶奇）で決まり、穴の開き方が変わります。ブール演算（和・差・積・排他）は非破壊で、元の図形を子として残し、結果の形は保存せずに毎回計算します。計算は整数で行い、ブラウザとサーバーで結果が一致するようにします。

設計の文書で効くところeditor-and-tools.md の 7〜8 節、ADR-0018、rendering-engine.md の 7 節（パスの描画）。

制約とオートレイアウト

画面のデザインは、大きさが変わっても崩れないことが大事です。そのための仕組みが 2 つあります。

制約は、親のフレームの大きさを変えたときに子がどう動くかの指定です。

制約親の幅が Δ 広がると
min（左）動かない
max（右）右へ Δ 動く
stretch（左右）幅が Δ 広がる
centerΔ/2 動く
scale位置と幅が比で伸びる

オートレイアウトは、CSS の flexbox に近い仕組みです。フレームが縦か横の向き・間隔・余白・揃えを持ち、子を自動で並べます。子とフレームの大きさは 3 つの方式から選びます。

  • hug：中身に合わせて縮む
  • fill：親の残りを埋める
  • fixed：固定

計算の結果（derived_layout）はファイルに保存しますが、画面は各自が手元で計算した結果を出します。全員の画面とサーバーの書き出しが同じ位置になるには、計算がビットまで決定的でなければなりません。だから算術の種類と順序まで決めています。

設計の文書で効くところlayout.md の 3〜4 節（入力と、保存・修復）・6 節（決定性）・8 節（制約）、ADR-0019、ADR-0020。

コンポーネント・インスタンス・バリアント

ボタンのような部品を何十か所でも使えるのが、デザインシステムの要です。

  • コンポーネントは原本、インスタンスはその写しです。原本を直すと、全インスタンスに反映します。
  • インスタンスで変えた部分が上書きです。テキスト・塗り・線・エフェクト・表示・名前は上書きできます。並び・位置・子の追加のような構造は変えられず、デタッチが要ります。
  • バリアントは、Size=Large, State=Hover のようなプロパティの値の組で、同じ部品の形違いを 1 つのセット（COMPONENT_SET）にまとめたものです。
  • インスタンスの中身は保存しません。原本と上書きから、各自のエンジンが導出（materialize）します。

原本の中のアイコンのレイヤーの名前を変えました。あるインスタンスでそのアイコンの色を上書きしていました。上書きはどうなりますか？

上書きのキーは「元のノードの ID の経路 × プロパティ」です。名前の変更・並べ替え・移動では消えません。名前で対応を取るのは、バリアントの切り替えとインスタンスの入れ替えのときだけです。

設計の文書で効くところcomponents-and-libraries.md の 3〜5 節、ADR-0021、ADR-0022。

同時編集の 3 つの方式

複数の人が同じ文書を同時に変えると、変更がぶつかります。ぶつかりを解く方式は、大きく 3 つあります。

OT（操作変換）。相手の操作に合わせて、自分の操作の位置などを変換する。共同編集のテキストエディタで広く使われてきた。変換の規則の組み合わせが増え、正しさを確かめにくい。

CRDT。どの順で届いても同じ結果に収束するデータ構造。サーバーなしでも収束し、オフラインに強い。ただし「木に循環を作らない」のような全体の規則を保ちにくい。rebuilds の Notion はこちら。

ファイルごとに 1 つのサーバーが変更の順序を決め、全員にその順で配る。CRDT の考え方（プロパティごとの LWW）を借りつつ、最後の判定はサーバーが下す。全体の規則に反する変更をサーバーが拒否できる。代わりに、サーバーに届くまで確定しない。

この設計は、本家と同じ中央のサーバーです。デザインのファイルは、木の形（親は 1 つ、循環なし）を守ることが大事で、長いオフラインの編集はまれだからです。1 ファイルを 1 つの Document Server が持ちます。

設計の文書で効くところADR-0002、multiplayer.md の 2〜3 節。

プロパティ単位の LWW と「競合の単位」

文書は「ノードの ID → プロパティ → 値」の 2 段の対応です。2 人が同じノードの別のプロパティを変えれば、両方が残ります。同じプロパティなら、サーバーに後に届いた値が勝ちます（LWW）。だから「何を 1 つのプロパティにするか」が、そのまま競合の単位になります。

プロパティ単位の決め方
transform移動と回転は同じ単位
size幅と高さは同じ単位
padding_top など余白の四辺は別々の単位
fills塗りの配列全体で 1 つ
text_content文字と書式の範囲で 1 つ。同時のテキスト編集は合わさらない
overridesmap。要素（上書き 1 項目）ごと

A さんが矩形を右へ動かし、同時に B さんが同じ矩形を回転させました。確定した結果は？

移動と回転は同じ transform のプロパティなので、LWW で片方が勝ちます。別々に編集されうる値は別のプロパティか map に分ける、というのがこの設計の規則です。

設計の文書で効くところdocument-model.md の 4 節（プロパティの表）、systems/figma/AGENTS.md の競合の単位の規則。

並びの鍵と、木の循環

同じ親の子の並び（重なりの順）を 0, 1, 2… の番号で持つと、間に挿入するたびに後ろの全員の番号を書き換え、同時の挿入で衝突します。そこで分数インデックスを使います。

  • 並びは文字列の鍵の辞書順で決める。間に入れるときは、前後の鍵の「間」の鍵を新しく作る（例：a0 と a1 の間に a0V）。他の子は書き換えない。
  • 同じ隙間に同時に入れて鍵が重なったら、サーバーが後の方を書き換える。鍵が 48 バイトを超えたら、サーバーがその親の子をまとめて振り直す。
  • A を B の下へ、同時に B を A の下へ動かすと、それぞれは正しくても、両方を当てると循環になる。

上の「A を B の下へ」「B を A の下へ」が同時に送られました。サーバーはどうしますか？

当てる前に新しい親から根までたどり、自分が現れたら循環とみなして ChangeSet ごと拒否します。拒否されるまでの間、クライアントは循環したノードを木から外して描きます。

設計の文書で効くところADR-0010、multiplayer.md の 5〜6 節、data-model.md の 6.3 節（O-1〜O-4）。

編集が確定するまで

自分の入力はサーバーを待たずに画面に出し（楽観的な反映）、確定はサーバーが決めます。1 回の編集は次の順に進みます。

  1. クライアントが変更を自分のモデルに当て、すぐ描く。未確定（pending）として持つ。
  2. 変更のまとまり（ChangeSet）に client_seq を付け、WebSocket で送る。ドラッグのような続く操作は 20Hz（50ms）にまとめる。
  3. Document Server が権限と木の規則を確かめ、ファイルの中の連番 seq を振る。
  4. 約 20ms ごとに、たまった変更をまとめてジャーナルに書く（group commit）。
  5. 書けたら、送り手に Ack、他の人に Committed を配る。書けるまでは誰にも見せない。
  6. 他の人は、自分の未確定の変更と同じプロパティへの変更を、自分の分が確定するまで画面に出さない（ちらつきを防ぐ）。

切断の後は、確定していない自分の変更を送り直します。サーバーは (session_id, client_seq) で重複を除きます（冪等）。

Document Server が変更を検証してメモリに当てた直後、ジャーナルに書く前に落ちました。この変更は？

確定の前に永続化する、が原則です。ジャーナルに書く前の変更は外に出ていないので、送り手の pending に残っており、再接続で送り直されます。

設計の文書で効くところarchitecture/README.md の 2.1 節、multiplayer.md の 4.5・7・9 節、ADR-0009。

ジャーナル・チェックポイント・フェンス

考え方は、DB の WAL とスナップショットと同じです。チェックポイントはある seq の時点のファイル全体（S3）、ジャーナルはその後に確定した変更の追記のログ（DynamoDB）です。ファイルを開くときは、最新のチェックポイントにジャーナルの残りを当てます。チェックポイントは 60 秒か 5,000 件ごとに、変わったページだけを書きます。

難しいのは二重の持ち主です。落ちたと思った古いサーバーが、実は止まっていただけで後から書き込むかもしれません。そこでフェンスを使います。

sequenceDiagram
  participant O as 古い持ち主 epoch 3
  participant R as Router
  participant N as 新しい持ち主
  participant J as ジャーナル
  R->>N: 割り当て epoch 4
  N->>J: フェンスを epoch 4 に上げる
  N->>J: チェックポイント後の変更を読む
  O->>J: epoch 3 で書き込み
  J-->>O: 条件の失敗
  O->>O: ファイルを手放す

ジャーナルへの書き込みは「フェンスの epoch が自分と同じ」を条件にした 1 つのトランザクションです。だから、古い持ち主の書き込みは必ず失敗します。

設計の文書で効くところADR-0003、ADR-0024、ADR-0025、ADR-0047、file-storage-and-history.md の 4〜6 節。

ブラウザの中の描画エンジン

数万のノードを 60fps で動かし、どのブラウザでも同じ見た目にするため、DOM や SVG ではなく <canvas> に GPU で自前で描きます。エンジンは Rust で書いて WASM にし、同じコードをサーバーでネイティブに動かして書き出しにも使います。

WebGL2 と WebGPU

WebGL2 は広く使える必須の土台。WebGPU は新しい API で、使えるときに使い、失敗したら WebGL2 へ戻る。

シーングラフ

ドキュメントの木とは別の描画用の木。世界座標と境界の箱を持ち、見えない部分木を飛ばす。

タイル

画面を 256×256 の画素の区画に分けて描き、キャッシュする。変わった範囲のタイルだけを描き直す。

アンチエイリアス

パスを線分にし、各画素を覆う面積を GPU で求めて、縁を滑らかにする。

60fps なら 1 フレームは 16.7ms です。入力の適用・レイアウト・描画をこの中に収めます。メモリは WASM の 32 ビットの空間（最大 4GB）の中で、タブ 1.5GB を目標にします。

設計の文書で効くところADR-0004、ADR-0013、ADR-0014、rendering-engine.md の 3〜7 節・11 節。

テキスト・フォント・日本語の入力

キャンバスに自前で文字を描くので、ブラウザが普段やっている仕事を自分でします。

  • 整形：文字の列を、フォントのグリフとその位置の列に変える。合字や字詰めもここで決まる。
  • フォールバック：欧文のフォントに和文を打つと、グリフがない。代わりのフォントを、端末ごとの既定に頼らずファイルの設定（既定は Noto Sans JP）で決め、全員の見た目を揃える。
  • フォントの出どころ：同梱のオープンなフォント、組織が上げたフォント、端末のフォント。端末のフォントは本人の画面だけで使う。
  • IME：「にほんご」を変換している間の文字列は未確定。<canvas> には入力欄がないので、見えない textarea で受け、確定した文字だけをファイルに書く。
法務の確認待ちフォントのライセンス（L1）：サーバーでの描画と PDF への埋め込み、組織のフォントを全員に配ること。和文のフォントは条件が厳しいものが多く、結論が出るまで該当の Story の spec を承認しません。
設計の文書で効くところADR-0015、ADR-0017、ADR-0036、editor-and-tools.md の 9 節、export-and-assets.md の 7 節。

Undo・バージョンの履歴・削除

「元に戻す」には 2 つの層があります。混同すると設計が読めなくなります。

自分の操作だけを戻す。他の人が後から上書きした値は戻さない。戻す操作も「新しい変更」として送る。履歴は 200 項目までで、タブを閉じると消える。

ファイル全体の過去の状態。バージョンは、変更があれば 30 分ごとに自動で作る。名前付きのバージョンも作れる。無料のプランは 30 日、有料はすべて残す。

過去のバージョンとの差分を 1 つの変更として当てる。git の revert に近く、それまでのバージョンは消えない。復元の前と後の 2 つのバージョンが足される。

2 段。まずゴミ箱（所有者が戻せる）、次に完全な削除（戻せない。ジョブが S3・ジャーナル・バージョンを消す）。複製ではコメントと履歴は写らない。

法務の確認待ち削除したファイルとバージョンをいつまで残し、いつ消すか、利用規約への書き方（L4）。
設計の文書で効くところADR-0012、ADR-0026、file-storage-and-history.md の 8〜11 節、multiplayer.md の 10 節。

組織・チーム・プロジェクトと権限

資源は 組織 → チーム → プロジェクト → ファイル の階層です（ほかに、プロジェクトに属さない個人の下書き）。本家は 2026-08-03 から「プロジェクト」を「フォルダー」に改名していますが、この設計は「プロジェクト」のままです。

  • 水準は全順序：none < view_prototype < view < edit < owner。上位で与えた役割は下位に届き、下位で下げられない。
  • 一般アクセス：「招待した人だけ」「組織の中」「リンクを知っている全員」。プロジェクトとファイルに置く。
  • シート：使える製品を決める契約の枠。編集には、ファイルの edit の水準と Full のシートの両方が要る。
  • ゲスト：組織のドメインに合わないメールアドレスの人。招待された資源だけを使える。

プロジェクトの一般アクセスは「組織の中・編集」、その中のファイルは「招待した人だけ」です。招待されていない組織のメンバーは、このファイルを？

役割（招待）は上から届いて下げられませんが、一般アクセスは「最も近い設定」を 1 つだけ使います。ファイルが「招待した人だけ」の行を持てば、上位の一般アクセスは届きません。

設計の文書で効くところpermissions-and-sharing.md の 3〜4・7 節、ADR-0029〜0031。組織の分離は共通の資料へ。

在席・コメント・メタデータ：3 つの経路

エディタの画面に出る情報は、性質ごとに別の経路を通ります。

データ経路保存
ファイルの中身（ノード）WebSocket → Document Serverジャーナル＋チェックポイント
在席・カーソル・選択WebSocket → Document Server（編集とは別のタスク）保存しない
コメント・権限・ファイルの一覧API → Aurora、Realtime の購読で配るAurora（RLS）
  • 1 ファイルに入れるのは 500 人（編集は 200 人）まで。配信は Gateway ごとに 1 回にまとめる。
  • コメントはファイルの中身に入れず、最上位のフレームなどのノードの ID と、そこからの相対の位置で固定する。フレームを動かすとコメントもついてくる。ノードが消えたら、作ったときの絶対座標に出す。
  • 「リンクを知っている全員」で開いた匿名の人には、コメントを見せない。
設計の文書で効くところADR-0011、ADR-0027、ADR-0028、comments-and-notifications.md の 3・5 節。

    uuid id PK
    text file_key UK
    bigint checkpoint_seq
  }
  file_versions {
    uuid org_id PK
    uuid id PK
    text kind
    bigint seq
  }
  comment_threads {
    uuid org_id PK
    uuid id PK
    text anchor_node_id
  }
  journal {
    text part_key PK
    number seq PK
    number epoch
  }
  • テナントの表は、主キーの先頭に org_id を持ちます。
  • 外に見せるのは乱数の file_key で、内部の files.id は出しません。
  • files.checkpoint_seq が、最新のチェックポイントの位置です。ジャーナルはそれより後の seq を持ち、seq = 0 の項目がフェンスです。
  • ノードの ID は "{session_id}:{local_id}" の文字列で、コメントの anchor_node_id などから参照します。
  • 権限に効く変更は、orgs.acl_version を 1 上げます。

用語集

ノード
ファイルの中の 1 つの要素。ID とプロパティの値の集まり。親を 1 つだけ持つ。
ページ
CANVAS のノード。1 つのファイルに複数あり、読み込みもページ単位で行う。
レイヤー
DOCUMENT と CANVAS 以外のノード。レイヤーの一覧に出る。
フレーム
大きさを持つ枠のノード。中身の切り抜き・オートレイアウト・制約の基準になる。
グループ
子をまとめるだけのノード。境界は子の境界の和。
ベクター
点と曲線で形を表す方式。拡大しても劣化しない。
ベジェ曲線
端の点と制御点（接線）で決まる曲線。3 次ベジェは制御点を 2 つ持つ。
ベクターネットワーク
点と辺のグラフで形を表す Figma の方式。1 点から 3 本以上の辺を出せる。
塗りの規則
パスの内と外を決める規則。非ゼロ（nonzero）と偶奇（even-odd）があり、穴の扱いが違う。
ブール演算
図形の和・差・積・排他をとる操作。元の図形を残す非破壊の形で持つ。
制約
親のフレームの大きさを変えたときの、子の位置と大きさの変え方の指定。
オートレイアウト
フレームの子を、向き・間隔・余白・揃えの指定で自動で並べる仕組み。CSS の flexbox に近い。
hug / fill / fixed
オートレイアウトの大きさの方式。中身に合わせる・親の残りを埋める・固定。
コンポーネント
再利用する部品の原本（メインコンポーネント）。
インスタンス
コンポーネントの写し。中身は原本と上書きから導出する。
上書き
override。インスタンスで原本と違う値にしたプロパティ。原本を直しても残る。
バリアント
プロパティの値の組で区別する、同じ部品の形違い。コンポーネントセットにまとめる。
デタッチ
インスタンスと原本のつながりを切り、ふつうのフレームに変える操作。
OT
Operational Transformation。相手の操作に合わせて自分の操作を変換し、同時編集を合わせる方式。
CRDT
Conflict-free Replicated Data Type。どの順で変更が届いても同じ状態に収束するデータ構造。
LWW
Last Writer Wins。同じ値への同時の書き込みで、最後の書き込みを勝たせる規則。ここでは「サーバーに後に届いた方」。
競合の単位
LWW で丸ごと置き換わる値のまとまり。この設計では 1 つのプロパティ、または map の 1 要素。
分数インデックス
並びを、前後の値の「間」をいつでも作れる鍵で表す方法。挿入で他の要素の鍵を変えない。
ChangeSet
1 つの利用者の操作に当たる変更のまとまり。全部当たるか、全部拒否されるか（原子的）。
Document Server
1 つのファイルをメモリに持ち、変更の順序を決め、検証し、ジャーナルに書いて配る Rust のサーバー。
Gateway
WebSocket の接続を終端し、Document Server へ中継し、配信を各接続へ分けるサーバー。
ジャーナル
チェックポイントより後に確定した変更の追記のログ。DynamoDB に置く。
group commit
短い間にたまった複数の変更を、1 回の書き込みにまとめて永続化すること。
チェックポイント
ある seq の時点のファイル全体の写し。ページごとのチャンクを中身のハッシュで名付けて S3 に置く。
フェンス
持ち主の世代番号（epoch）を記録し、古い持ち主の書き込みを条件で止める仕組み。分散システムの fencing token と同じ考え方。
WASM
WebAssembly。ブラウザで高速に動く実行形式。Rust や C++ からコンパイルできる。
WebGL2
ブラウザから GPU で描くための、広く使える API。OpenGL ES 3.0 に基づく。
WebGPU
ブラウザから GPU を使う新しい API。compute shader などを使える。
シーングラフ
描画のための木。座標の変換・境界の箱・描画の命令を持つ。
タイル
画面を一定の大きさの区画に分けた単位。区画ごとに描いてキャッシュする。
アンチエイリアス
図形の縁の画素を、覆う面積に応じた中間の色にして、ギザギザを目立たなくすること。
整形
shaping。文字の列を、フォントのグリフの列と位置に変える処理。HarfBuzz・HarfRust など。
グリフ
フォントの中の 1 つの字形。1 文字が複数のグリフになることも、その逆もある。
フォールバック
指定のフォントにグリフがないとき、別のフォントで描くこと。どれにもなければ豆腐（□）になる。
IME
Input Method Editor。かなを漢字に変換するなど、キーの入力から文字を組み立てる仕組み。変換中の文字は未確定。
バージョン
ファイルの過去の時点の状態。チェックポイントに印を付けたもの。自動と名前付きがある。
一般アクセス
個人への招待とは別の、範囲を指定した共有の設定（招待した人だけ・組織の中・リンクを知っている全員）。
シート
組織と結ぶ利用の枠。Full・Dev・Collab・View があり、使える製品を決める。
ゲスト
組織のドメインに合わないメールアドレスの人。招待された資源だけを使える。
在席
presence。誰がファイルを開いていて、どこを見て何を選んでいるか。保存しない。
Realtime
ファイルの外のメタデータ（コメント、権限、ファイルの一覧）の変更を、購読で配る仕組み。本家の LiveGraph に当たる。
