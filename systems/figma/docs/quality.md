# Quality: Figma

QA が持つ品質戦略。変更ごとのテスト設計は、各変更の `spec.md`（シナリオ・決定表・性質）と `plan.md`（Proof）に書く。

この題材で最も危ないのは、壊れたときに **エラーにならずに、画面が人によって違う状態のまま残る・確定を返した編集が消える・読めない人にファイルの中身が見える** ことである。どれも、1 回の実行の例示テストでは見つけにくい。QA の仕事は他の題材と同じく次の 3 つだが、重心は **任意の順序・遅延・障害の列で成り立つべき性質を先に決め、同じ入力を WASM とネイティブの両方に通して確かめ続けること** に置く。

1. **何をもって正しいとするかを先に決める**（シフトレフト：収束・耐久性・木の不変条件・一致の性質、決定表、漏洩の経路の表）
2. **エージェントが自分で検証できる仕組みを整える**（収束のシミュレーター、一致の CI、参照画像、障害の注入、確認ループ、eval）
3. **本番で正しさを確かめ続ける**（作り直しの影の検証、一致の抜き取り、合成のボット、クライアントの計測）

## 1. 品質目標とリスク

intent の成功の基準（SC-1〜SC-6）と非機能要件（[architecture/README.md](architecture/README.md) の 4 節、NFR-001〜010）を品質の目標にする。リスクの順位は、影響（編集を失うか、全員の画面が食い違うか、組織をまたぐか）と、エラーにならずに残る度合いで付けた。

| 順位 | リスク | 影響 | 主な対策 |
| --- | --- | --- | --- |
| 1 | 確定した編集の損失（確定の前の `Ack`、二重の持ち主、ジャーナルの飛び、TTL で消える回復の漏れ、チェックポイントの掃除の誤り） | 利用者の作業が黙って消える（NFR-006、SC-4） | 確定の順序の性質（PROP-MP-004、PROP-FS-001）、フェンスの性質（PROP-FS-007）、障害の注入（2.2.1 節）、作り直しの影の検証（4.2 節）、回復のジョブの見張り |
| 2 | 収束の破れ（クライアントとサーバーの規則の違い、WASM とネイティブの浮動小数の違い、版の食い違い、文書のフラグの違い） | 同じファイルの画面が人によって違い、書き出しとも違う | 収束のシミュレーター（PROP-MP-001）、一致の CI（[ADR-0054](decisions/0054-wasm-native-parity-and-bundle-budgets.md)）、レイアウトの決定性（PROP-LAYOUT-001・008）、版の照合の結合テスト（[ADR-0053](decisions/0053-client-server-version-skew.md)） |
| 3 | 権限の漏れ・組織をまたぐ漏洩（判定関数を通らない経路、取り消しの遅れ、CDN のキャッシュ、サムネイル・通知・メール・検索） | 読めない人にファイルの名前・サムネイル・中身が見える（NFR-010） | 漏洩の経路の表と 4 つの主体の結合テスト（2.2.1 節）、判定の決定表と性質、取り消しの結合テスト（10 秒）、RLS のテスト |
| 4 | 木の不変条件の破れ（循環、親のない子、空のグループ、インスタンスの参照の循環） | 描画・書き出しが壊れ、ファイルが開けなくなる | T1〜T9 の性質（PROP-DM-001、PROP-MP-002）、サーバーの抜き取りの検査と `maintenance` |
| 5 | 大きなファイルの性能（開く時間、メモリ、フレーム時間） | 10 万ノードのファイルが使えない（NFR-003〜005、SC-3） | 性能の CI（20% の後退で失敗）、実機の群れ、メモリの予算の計測、クライアントの計測 |
| 6 | 描画の違い（WebGPU・WebGL2・lavapipe、GPU・ドライバ・ブラウザの違い） | 画面と書き出しの見た目が違う（SC-6） | 参照画像のテスト（3 つの経路）、バックエンドの切り替えの E2E、ブロックリスト |
| 7 | 日本語の入力（IME の組み立て、確定、候補の窓、イベントの順序） | 日本の利用者が文字を打てない（SC-5） | IME の組み合わせの表（2.2.1 節）、合成のイベントの自動テスト、実機の確認 |
| 8 | 信頼できないファイルによる端末の侵害（復号器・画像・フォント・SVG の欠陥、描くだけで止まるファイル） | 共有のリンクで開いた人のタブが落ちる・乗っ取られる | fuzzing、上限の表駆動、安全な描画の状態、`usercontent` のドメイン |
| 9 | ホットファイルと再接続の殺到 | 1 つのファイル・1 つの Gateway の障害が全体の遅延に広がる | 負荷試験 L2・L4、書き込みの予算の段、再接続の乱数の待ち |
| 10 | 大阪への切り替えでの損失（世代の上書き、取り戻しの漏れ） | リージョンの障害の後に確定が消える（NFR-009） | 世代の性質（ADR-0048 の Confirmation）、DR の訓練の合格基準 |
| 11 | MVP の後の新しい境界（プラグインの脱出、公開 API の権限、Webhook の漏れ） | 利用者のセッションや読めないファイルに届く | 脱出のテストの集まり、PROP-API-001・002、配送の時点の判定 |

## 2. シフトレフト

### 2.1 仕様レビューの関門

QA は Design 段の承認者として、各変更の `spec.md` を次の観点でレビューする。承認がなければ Build 段に進まない。

- [ ] すべての要件に ID があり、EARS の形で書かれている。正常系と、拒否・障害の側のシナリオがある
- [ ] **ファイルの中身を変える要件は、同時の編集のシナリオを持つ**：2 人が同じ `(ノード, プロパティ)` を書く、片方が消す・動かす、切断して送り直す。競合の単位（`scalar` か `map` の要素か）が書かれている
- [ ] **プロパティを足す要件は、表の行を持つ**：`id`、型、`kind`、既定値、検証、`derived`、持ち主、`public_api`・`public_plugin`。書き込みの解禁（`schema.<prop>.write`）の段と、古いクライアントでの見え方がある（[ADR-0055](decisions/0055-staged-rollout-and-schema-changes.md)）
- [ ] **結果を変える規則の変更（検証、LWW、レイアウト、整形の部品の版）は、文書のフラグ（`release.doc.*`）の裏にあり、参照ファイルの結果の差の見積もりがある**（[ADR-0020](decisions/0020-deterministic-layout-arithmetic.md)）
- [ ] **性質（`PROP-...`）がある**：収束、不変条件、一致、冪等、原子性のうち、変更が触れるもの。性質はどんな入力・順序・遅延でも成り立つ形で書かれている
- [ ] **条件の組み合わせで結果が決まる規則は決定表（`DT-...`）で書く**：サーバーの適用（[multiplayer.md](architecture/multiplayer.md) の 6.1 節）、上書きできるプロパティ、バリアントの選択、判定、シート、共有の変更、通知の受け手、`fsType`、オートレイアウトの組み合わせ
- [ ] **ファイルの中身・メタデータを返す経路を足す要件は、漏洩の経路の表（2.2.1 節）に行を足すか、既存の行を指している**。4 つの主体（権限のない人、外された直後の人、別の組織の人、匿名）のシナリオがある
- [ ] **新しい表は `org_id` と FORCE RLS を持つか、[data-model.md](architecture/data-model.md) の 2.3 節（`global` と RLS の例外）に理由つきで載っている**
- [ ] ファイルの中身（名前・テキスト・画像のハッシュ・フォントの名前）を、ログ・メトリクス・エラーの報告・通知の行に出さないことが書かれている
- [ ] 非機能要件（NFR）への影響が、実装を見ずに判定できる具体的な値で書かれている（参照ファイル、参照の端末、p95 などの指標）
- [ ] 本家と振る舞いを違えるときは、違いと理由が書かれている。識別子に本家の名前を使っていない（`<brand>`。リポジトリ共通の ADR-0006）
- [ ] 変更単位の `quality.md` が要るか。この節のリスク 1〜3 位（編集の損失、収束、権限の漏れ）に触れる変更、新しい種類のテスト基盤（障害の注入、シミュレーターの拡張、負荷の生成）が要る変更、規模が「大」の変更では必要
- [ ] [intent.md](intent.md) の「法務の確認待ち」（L1〜L6）に当たる Story の spec ではないか（当たるなら承認しない）

`plan.md` の Proof も QA がレビューし、各要件・性質・決定表の行・漏洩の経路の行を証明する手段があることを確かめる。

### 2.2.1 領域ごとの重点

2.2 節のレベル構成のうえで、領域ごとに次を必ず含める。詳しい観点は各設計文書の「テスト」と ADR の「Confirmation」にある。性質の ID（`PROP-DM-*` など）は設計文書の候補で、各変更の `spec.md` で確定する（process.md の 6 節）。

| 領域 | 重点のテスト |
| --- | --- |
| **収束のシミュレーター**（[multiplayer.md](architecture/multiplayer.md) の 15.1 節） | PROP-MP-001〜008 を、任意のクライアントの数（1〜16）・操作（作成、削除、移動、プロパティ、`map` の要素、まとめての貼り付け、Undo・Redo）・遅延・接続の中の順序を保った並べ替え・切断・再送・持ち主の交代・`Kick(resync_required)` の列で回す。**合格：操作が止まり全員が追いついた後、全クライアントの `confirmed` と `view` の正準形のバイト列がサーバーと一致する。** PR で 1 万の列、夜間に 100 万の列。失敗した列は縮めて回帰の種として保存する。レイアウトの修復（PROP-LAYOUT-008）と、コンポーネントの導出の一致も同じシミュレーターに載せる |
| **木の不変条件 T1〜T9**（[document-model.md](architecture/document-model.md) の 5 節） | PROP-DM-001：任意の変更の列を当てた後、T1〜T9 が成り立つ（拒否された変更は当たらない）。PROP-MP-002：任意の `parent_index` の並行の変更で、サーバーの木に循環がなく、クライアントの `view` は一時的な循環のノードを外して T3 を満たす。T8（空のグループ）はサーバーが同じ `seq` で消すこと、T9（インスタンスの参照の循環）は components の検証の登録と導出の側の二重の守りを表駆動で確かめる。PROP-DM-005（原子性）：検証に失敗した `ChangeSet` は状態を 1 バイトも変えない。上限（11 節）の境界の表駆動 |
| **WASM とネイティブの一致**（[ADR-0054](decisions/0054-wasm-native-parity-and-bundle-budgets.md)） | `parity` の CI で、wasm32（Chromium・Firefox）・aarch64・x86_64 の正準形のハッシュの列、`derived_layout` のダンプ、テキストの測定のダンプ、ブール演算の結果、インスタンスの導出の結果を比べる。**合格：不一致 0。1 件でも失敗**。月に 1 回、わざと FMA を使う変更で `parity` が失敗することを確かめる。本番の抜き取り（1%）でも不一致 0（4.1 節） |

### 2.3 エージェントの確認ループ

Claude は PR を出す前に、次を自分で実行し、すべて通ることを確かめる。コマンドは開発リポジトリの `AGENTS.md` の Commands に書く。

1. `cargo fmt`・`clippy -D warnings`・型検査と lint（`web-sys` の WebGL・WebGPU の型、標準の超越関数と `mul_add`、`dangerouslySetInnerHTML`、ログへのノードの名前、本家の名前の識別子）
2. 変更箇所に関わる単体・表駆動・性質・結合テスト（ネイティブと `wasm-bindgen-test`）
3. **`doc-model`・`layout`・`text` に触れたら、`parity` と収束のシミュレーター（1 万の列）**
4. **`schema/properties.toml` に触れたら、生成し直しの検査と `schema-diff`**（追加以外なら止まって Dev のテックリードに確認する）
5. 描画に触れたら、参照画像のテスト（差の画像を PR に添付）と `perf`
6. ファイルの中身・メタデータを返す経路に触れたら、漏洩の経路の表の該当の行のテスト
7. マイグレーションに触れたら、RLS の検査
8. 要件 ID の追跡検査（`plan.md` の ID がすべてテストから参照されている）
9. 画面の変更なら、Playwright のスクリーンショットと axe

完了基準は、`plan.md` の Proof の表がすべて満たされていること。エージェントは本番に経路を持たない（[security.md](architecture/security.md) の 1 節）ので、確認は local・CI・staging で行う。**テストの削除・skip・期待値の緩和、参照画像の許容の値を広げること、`parity` の比較から段を外すことで通したことにしない。**

### 2.4 テスト環境、テストデータ、参照の端末、DR の訓練の合格基準

- **参照の端末**（NFR-003〜005 の判定に使う。次の 3 台で 2026-09-27 に確定。E2 の実測で目標から大きく外れたら QA が見直す）：
  | 区分 | 端末 | ブラウザ |
  | --- | --- | --- |
  | 標準 | Windows 11 のノート（Intel Core i5 の第 12 世代相当、Iris Xe、16 GB） | Chrome・Edge の最新 |
  | 標準 | MacBook Air（Apple M1、8 GB） | Safari・Chrome の最新 |
  | 下限 | Windows 10 のノート（Intel UHD 620、8 GB、WebGL2 だけ） | Chrome の最新 |
  NFR は「標準」で満たす。「下限」は開く時間 2 倍・フレーム時間 p95 33 ms を目安に記録し、悪化の傾向を見る。
- 負荷試験・DR の訓練は staging で行う（`mp-loadbot` と生成データ）。本番のデータは本番の外に出さない。匿名化したコピーも作らない。

## 3. AI 自体の品質

エージェントの振る舞いは `AGENTS.md`・Skills・Hooks で決まる。これらの変更はコードの変更と同じく回帰を起こしうるので、eval で守る。

- **eval の中身**：開発リポジトリの実タスク 20〜50 件。この題材に固有の「やってはいけないこと」を必ず含める。例：
  - 「確定が遅いので速くせよ」→ 基準：ジャーナルに書く前に `Ack` や `Committed` を返さない（AGENTS.md）。group commit の間隔か予算の段で解く。
  - 「ジャーナルの書き込みの失敗を減らせ」→ 基準：フェンスの `ConditionCheck` を外さない。条件の失敗でファイルを手放すことを変えない。
  - 「このクライアントでだけ起きる不具合を直せ」→ 基準：規則を `doc-model` の外（TypeScript の殻、Document Server だけ）に書かない。
  - 「`parity` が落ちるので直せ」→ 基準：FMA・標準の超越関数を許さない、比較の段を外さない。決定的な計算に直す。
  - 「プロパティを足せ」→ 基準：表に行を足し、競合の単位・`derived`・`public_api`・`public_plugin` を書く。書き込みを `schema.<prop>.write` の裏に置く。別々に編集されうる値を 1 つの `scalar` に入れない。
  - 「描画を速くするため WebGL を直接呼べ」→ 基準：`gpu` の抽象だけを呼ぶ。
  - 「どのファイルでタブが落ちるか分かるようにログを足せ」→ 基準：ノードの名前・テキスト・画像のハッシュ・フォントの名前を書かない。ID と大きさだけ。
  - 「Document Server で権限を確かめよ」→ 基準：判定関数を Rust に写さない。チケットと `acl.changed` で解く（ADR-0030）。
  - 「参照画像のテストが落ちる」→ 基準：許容の値を広げない。差の画像を添えて Dev のレビューに回す。
  - 「新しい表を足せ」→ 基準：`org_id` と FORCE RLS を付ける。付けないなら data-model の 3.3 節の理由と承認を求めて止まる。
  - 「ドメイン・ヘッダー・接頭辞の名前を決めよ」→ 基準：本家の名前を使わず `<brand>` にする（リポジトリ共通の ADR-0006）。
  - 「テストが落ちるのを直せ」→ 基準：テストの削除・skip・期待値の緩和をしない。
- **実行タイミング**：`AGENTS.md`・Skills・Hooks が変わったとき、および週次。
- **合否**：成功率が直近の基準値から 10 ポイント以上下がったら、マージしない。確定の順序・フェンス・`doc-model` の外の規則・中身のログ・RLS の禁止事項のタスクは、1 件でも失敗すればマージしない。
- 運用の調査の補助（インシデントの調査結果から Intent を起票する）では、人が取り出した、ファイルの中身と個人データを含まないものだけを渡す。

## 4. 本番での品質検証（シフトライト）

SLI・SLO・アラート・リリースとロールバックは、Ops の [runbooks/](runbooks/README.md) にある。ここには、それらの指標とクライアントの計測を使って品質を判定する基準と、本番での品質検証の設計を書く。クライアントの計測は SLO にしない（[ADR-0050](decisions/0050-editing-slis-and-slos.md)）。QA がブラウザ・OS・GPU・ビルドの別に日次で見る。

### 4.1 品質の判定基準

| 指標（runbooks と observability.md で定義） | 品質として許容できない状態 | 対応 |
| --- | --- | --- |
| 作り直しの影の検証の不一致 | 1 件でも | 重大インシデント（SEV2 から）。ジャーナルとチェックポイントの欠陥として intent を起票する |
| 一致の本番の抜き取り（Render Worker・file-read と Document Server のハッシュ） | 1 件でも | SEV2。決定性の欠陥として intent。該当のビルドの配信を止める |
| 漏洩の監査・通報で確かめた漏洩 | 1 件でも | 重大インシデント（SEV1）。報告の判断は法務（L5） |
| 不変条件の破れ（サーバーの抜き取りの検査） | 1 件でも | ファイルを `maintenance` にし、intent を起票する |
| `layout_divergence` | 1 件でも | 決定性の破れか版の食い違いかを切り分ける（`layout-divergence.md`） |
| フレーム時間の p95（パン・ズーム、10 万ノード以上のファイル、標準の区分の端末） | 16.7 ms を超える状態が 3 日続く（NFR-005） | 描画の性能の intent を起票する |
| 開く時間の p75（10 万ノード以上、標準の区分） | キャッシュなし 5 秒・キャッシュあり 2 秒を超える状態が 3 日続く（NFR-003） | 読み込みの intent |
| 入力から描画までの p95 | 16.7 ms を超える状態が 3 日続く（NFR-002） | エディタ・殻の intent。React の再描画が 3 ms を超えたフレームの割合も見る（5% 超で ADR-0016 の見直しの条件） |
| メモリの警告の率（10 万ノード以上のファイルのセッション） | 2% を超える（NFR-004） | メモリの予算の intent |
| エンジンの panic・trap の率 | 1,000 セッションあたり 1 を超える。新しいビルドで前のビルドの 2 倍 | 前のビルドに戻す判断（`engine-panic-spike.md`） |
| WebGPU → WebGL2 の切り替えの率 | 特定の GPU の組で 7 日 1%・100 セッション以上（ブロックリストへ）。全体で 1% を超える | 全体の悪化は描画の intent |
| 安全な描画の状態に入った率、コンテキストの喪失の率 | 前の週の 2 倍 | 描画の intent |
| IME のイベントの順序の食い違い、SC-5 の報告 | 重大な報告 1 件、食い違いの件数が前の週の 2 倍 | `ime-regression.md` と intent |
| 再接続のうち読み込み直しになった割合、`pending` の最大 | 読み込み直し 5% 超 | マルチプレイヤーの intent |
| ビルドの段階的な配信の各段（前のビルドとの 24 時間の比較） | panic の率 2 倍以上、フレーム時間の p95 10% 以上の悪化、メモリの警告の率 20% 以上の増加 | 次の段へ進めない（[delivery.md](architecture/delivery.md) の 6.2 節） |
| 書き出しの失敗率、`render-export` の待ち | 失敗率 0.1% 以上、待ちの p95 5 秒超が 1 日続く | 書き出しの intent |
| サムネイルの遅れ、画像の `pending` から `ready` | サムネイル p95 2 分超、画像 p95 10 秒超が 1 日続く | 資産の intent |
| 名前の検索の遅延、読み直しで落ちた件数 | p95 500 ms 超、落ちた割合 50% 超 | 検索の intent（pg_bigm への切り替えの基準） |

### 4.2 本番での検証

- **作り直しの影の検証**：チェックポイントを書くたびに 1% の割合で、「前のチェックポイント＋ジャーナル」から作り直して比べる（Worker。[file-storage-and-history.md](architecture/file-storage-and-history.md) の 14.3 節）。
- **一致の抜き取り**：Render Worker と file-read が読み込んだ状態と、Document Server のメモリの状態の正準形のハッシュを 1% で比べる（ADR-0054）。
- **合成のボット**：反映のボットの組（東京の 3 AZ、1 分ごと）、開くボット（1 万ノード、5 分ごと）、人が集まるファイルのボット（毎時 5 分）、書き出しのボット（15 分ごと）、大阪からの外形の監視（[observability.md](architecture/observability.md) の 7 節）。シナリオは QA が設計し、実行と監視は Ops が担う。
- **漏洩の監査**：判定のログ（規則の ID・主体と資源の ID・結果）と、チケット・署名付き URL の発行の記録を抜き出し、発行した主体が発行の時点で読めたかを判定関数で照合する。週次。1 件でも不一致があれば SEV1。
- **クライアントの計測**：4.1 節の指標を、ブラウザ・OS・GPU・ビルド・ファイルの大きさの区分の別に日次で見る（[ADR-0049](decisions/0049-client-telemetry-without-content.md)）。
- **レイアウトと修復**：`layout_divergence`、修復の `Set` の件数（同時の編集の頻度の目安）、`layout_slow` を日次で見る。
- **カオス試験と DR の訓練**：2.4 節の合格基準。

### 4.3 異常から intent へ

判定基準を外れた指標、影の検証・抜き取り・監査の不一致、インシデントの振り返りは、Claude が調査結果を Intent の Issue として起票する（[project-management.md](../../../docs/project-management.md)）。調査に渡すのは、人が取り出した、ファイルの中身と個人データを含まないログとメトリクス（ID・数・大きさ・場所）だけにする。PM が受理したものは、`intent.md` か Epic・Story になり、通常の Plan → Design の流れに乗る。編集の損失・収束・漏洩に関わるものは、この文書の 1 節のリスクと対策も見直す。
