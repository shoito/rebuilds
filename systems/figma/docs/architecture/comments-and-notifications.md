# Comments and notifications: Figma

キャンバスに固定するコメント、スレッド、メンション、解決、通知（アプリ内とメール）と、メタデータ（コメント、ファイルの一覧、通知、権限）をリアルタイムに配る購読の層（Realtime）の設計。

コメントはメタデータで、Aurora に置く（[architecture/README.md](README.md) の 1 節「ファイルの中身とメタデータを分ける」、[ADR-0005](../decisions/0005-tenancy-and-document-routing.md)）。判定は [permissions-and-sharing.md](permissions-and-sharing.md) の判定関数を通す。この文書で決めたことは次の ADR にある。

| ADR | 決定 |
| --- | --- |
| [0027](../decisions/0027-comments-anchored-to-nodes-in-metadata.md) | コメントは Aurora に置き、ノードの ID と相対の位置で固定する。通知は送る時点で受け手を判定し直し、メールは受け手とファイルごとにまとめる |
| [0028](../decisions/0028-realtime-metadata-subscriptions.md) | メタデータのリアルタイムの更新は、トリガーで書く無効化の outbox と、単純なクエリへの分解・再取得の購読層で配る |

本家の振る舞いは、2026-09-27 に Figma のヘルプセンターと Figma のブログで確かめた。確かめられなかったものは「未検証」と書く。

## 1. 目的と範囲

| 範囲 | MVP | MVP の後 |
| --- | --- | --- |
| キャンバスの位置・領域へのコメント、フレームへの固定 | ○ | |
| スレッド、返信、編集、削除、解決・再開、リアクション、画像の添付 | ○ | |
| 人へのメンション | ○ | ユーザーグループへのメンション |
| 既読・未読、並べ替えと絞り込み | ○ | |
| アプリ内の通知、メールの通知、ファイルごとの通知の設定 | ○ | モバイルの push、チャットの連携 |
| 招待・アクセスの申請・シートの申請の通知 | ○ | |
| ライブラリの更新の通知 | | ○（ライブラリと一緒に） |
| Realtime（メタデータの購読） | ○ | S2 での WAL からの無効化 |
| プロトタイプへのコメント | | ○（プロトタイピングと一緒に） |

守ること：

- 読めない人に、コメントの本文・添付・ファイルの名前・デザインのプレビューを、通知・メールを含むどの経路でも出さない。
- コメントは、固定したフレームが動けば一緒に動く。フレームが消えても、コメントは消えない。

- 本家のメールの送信の遅らせ方・まとめ方は **未検証**。

## 3. コメント

### 3.1 データ

[ADR-0027](../decisions/0027-comments-anchored-to-nodes-in-metadata.md) による。すべて `org_id` を持ち、FORCE RLS を付ける。

| 表 | 主な列 |
| --- | --- |
| `comment_threads` | `org_id`、`id`（UUIDv7）、`file_id`、`page_id`（ノードの ID の文字列 `"{session_id}:{local_id}"`）、`anchor_kind`（`point` / `region`）、`anchor_node_id`（最上位のフレーム・コンポーネント・グループ、なければ null）、`offset_x`・`offset_y`（ノードの座標系での位置）、`region_w`・`region_h`、`abs_x`・`abs_y`（作成時のキャンバスの絶対座標）、`resolved_at`、`resolved_by`、`created_by`、`created_at`、`last_activity_at`、`deleted_at` |
| `comments` | `org_id`、`id`、`thread_id`、`file_id`、`author_id`、`body`（リッチテキストの JSON）、`edited_at`、`deleted_at`、`created_at` |
| `comment_attachments` | `org_id`、`comment_id`、`asset_id`（S3 のキー）、`file_id`、`mime`、大きさ。1 コメント 5 つまで |
| `comment_reactions` | `org_id`、`comment_id`、`account_id`、`emoji`、`file_id` |
| `comment_mentions` | `org_id`、`comment_id`、`mentioned_account_id`、`file_id` |
| `comment_read_states` | `org_id`、`account_id`、`thread_id`、`file_id`、`last_read_comment_id` |
| `file_comment_subscriptions` | `org_id`、`account_id`、`file_id`、`level`（`all` / `mentions_replies` / `none`）、`source`（`owner_default` / `auto_two_comments` / `explicit`） |

- コメントは、ファイルの中身（ノードの木、ジャーナル、チェックポイント）に入れない。バージョンの履歴で過去のバージョンを開いても、コメントは今のものを出す。
- 本文は、書いた時点の文字列をそのまま保存する。メンションは `{type: "mention", account_id}` の要素で持ち、表示のたびに名前を解決する。
- Realtime の問い合わせは 1 つの表への等価の条件だけなので、`file_id` で絞る表（リアクション・既読など）は `file_id` を自分で持つ（非正規化）。削除は墓標（`deleted_at` を設定し、本文を空にする）。列の定義は [data-model/comments-and-notifications.md](data-model/comments-and-notifications.md)。

### 3.2 固定と位置の解決

```
作成（クライアント）：
  hit = クリックした位置を含む、最上位のフレーム・コンポーネント・グループ（入れ子は見ない）
  anchor_node_id = hit?.id
  offset = hit があれば hit の座標系での位置、なければ null
  abs    = キャンバスの絶対座標（いつも持つ）

表示（クライアント）：
  if anchor_node_id がモデルにあり、同じページにある:
      位置 = anchor_node の変換 × offset             // フレームと一緒に動く
  elif anchor_node_id がモデルにあり、別のページへ移った:
      位置 = 移動先のページで同じ計算。スレッドの page_id はそのまま（一覧では元のページに出す）
  else:                                                // 消えた、または導出したノードで見つからない
      位置 = abs。「固定先が消えた」印を付ける
```

- サーバーは、ノードの移動を追わない。位置はクライアントがファイルの中身から計算する。Undo やバージョンの復元でノードが戻れば、コメントも元の位置に戻る。
- インスタンスの中の導出したノードには固定しない。最上位のノード（インスタンスの根を含む）にだけ固定する（本家の「入れ子には付かない」と同じ）。
- メールのプレビューと通知の画面の位置は、Worker が最新のチェックポイント（とジャーナル）から同じ計算をする。

### 3.3 操作と権限

| 操作 | 必要な水準（ファイルに対して） | 追加の条件 |
| --- | --- | --- |
| コメントを読む・購読する | `view` 以上 | ログインが要る。匿名の閲覧者には出さない |
| スレッドを始める・返信する・リアクション | `view` 以上 | ログイン。上限（3.4 節） |
| 自分のコメントを編集する | `view` 以上 | 書いた本人 |
| 自分のコメントを削除する | `view` 以上 | 書いた本人。元に戻せない（本家と同じ） |
| 他人のコメントを削除する | —（本家と同じく持たない） | 濫用への対応は運用者の経路（監査付き） |
| 解決・再開 | `view` 以上 | 本家と同じく誰でも |
| 既読・未読にする | `view` 以上 | 自分の状態だけ |
| 通知の設定を変える | `view` 以上 | 自分の設定だけ |

- 匿名の閲覧者にコメントを出さないのは、「リンクを知っている全員」のファイルで、社内のやり取りを外に出さないため。本家の振る舞いは **未検証** だが、本システムの決定として確定した（2026-09-27）。
- スレッドの最初のコメントを削除すると、スレッドごと消す。返信の削除は、その 1 件だけを消す。
- ファイルをゴミ箱へ入れても、コメントは消さない。ファイルの完全な削除で消す（security.md のデータのライフサイクル）。

### 3.4 上限

| 項目 | 値 | 出どころ |
| --- | --- | --- |
| 1 人が書けるコメント | 1 時間に 100 件（全ファイル合計） | 本家と同じ |
| 本文 | 10,000 文字 | 本システムの値 |
| 添付 | 1 コメント 5 つ。PNG・JPEG・GIF。1 つ 10 MB | 数は本家と同じ。大きさは本システムの値 |
| 1 コメントのメンション | 50 人 | 本システムの値 |
| 1 ファイルのスレッド | 10,000（超えたら、解決済みの古いものから一覧の読み込みを遅らせる） | 本システムの値 |

## 4. メンションと通知

### 4.1 メンション

| 項目 | 規則 |
| --- | --- |
| 候補 | ファイルを読める人（役割を持つ人と、最近コメントした人）から出す。組織のメンバーの名前を、ファイルを読めるかに関わらず候補に出すのは、組織のメンバー（ゲストでない）が書くときだけ |
| 読めない人 | 本家と同じく、送信の前に「この人はファイルを開けない。招待しますか」を示す。招待するかは書いた人が決める。自動では共有しない。招待しないで送った場合、その人には通知しない |
| ゲストが書くとき | 候補は、ファイルを読める人だけ。組織のメンバーの一覧を見せない |
| 編集での変化 | 編集で新しく増えたメンションにだけ通知する。消えたメンションの未読の通知は取り消す |

### 4.2 受け手の決め方

`comment.created` の出来事ごとに、Worker が受け手を決める。

| # | 条件 | アプリ内 | メール |
| --- | --- | --- | --- |
| 1 | 書いた本人 | — | — |
| 2 | 送る時点でファイルを読めない（判定関数） | — | — |
| 3 | メンションされた | ○ | ○（設定が `none` でも送る。本家と同じ） |
| 4 | 自分が始めた・返信したスレッドへの返信・リアクション | ○ | 設定が `all` か `mentions_replies` のとき |
| 5 | 購読の設定が `all`（所有者の既定、2 件以上コメントした人） | ○ | ○ |
| 6 | それ以外 | — | — |

- 購読の自動の設定：ファイルの所有者は `all`（`owner_default`）。所有者でない人は、そのファイルで 2 件目のコメントを書いたときに `all`（`auto_two_comments`）。本人が変えた設定（`explicit`）は、自動で上書きしない。
- アプリ内の通知は、本家と同じく切れない。
- 同じコメントで複数の行に当たったら、1 つにまとめる（メンションを優先して表示する）。

### 4.3 パイプライン

```
コメントの書き込み（1 つのトランザクション）
  ├─ comments / comment_mentions / file_comment_subscriptions（2 件目の自動）
  ├─ realtime_invalidations（トリガー。5 節）
  └─ outbox: comment.created { org_id, file_id, thread_id, comment_id }
        ▼ SQS（notify）
Worker：受け手を決める（4.2 節。判定関数で読めるかを確かめる）
  ├─ notifications に行を書く（アプリ内）→ トリガーで Realtime に無効化
  └─ email_digest_queue に (account_id, file_id, comment_id, due_at) を書く
        ▼ 1 分ごと
Worker：due_at を過ぎた (account_id, file_id) をまとめる
  ├─ 送る直前に、受け手がファイルを読めるかを判定し直す
  ├─ 既に読んだコメント（comment_read_states）を除く。残りがなければ送らない
  ├─ プレビューの画像を作る（5.5 節）
  └─ メールを送る（SES）
```

- **メールのまとめ**：最初のコメントから 2 分待ち、その間に来た同じファイルのコメントを 1 通にまとめる。メンションは待たずに送る（遅れは最大 1 分のスケジューラーの間隔だけ）。
- **読んだものを送らない**：まとめの待ちの間にアプリで読んだコメントは、メールに入れない。本家の振る舞いは未検証で、本システムの決定（メールの数を減らす。2026-09-27 に確定）。
- 目標：コメントの確定から、メンションの受け手のアプリ内の通知まで p99 2 秒、メールの送信まで p99 3 分。

### 4.4 アプリ内の通知

| 表 | 主な列 |
| --- | --- |
| `notifications` | `org_id`、`id`、`account_id`、`kind`（`comment_mention` / `comment_reply` / `comment_on_file` / `invite` / `access_request` / `seat_request` / `library_update`）、`file_id`、`subject_id`、`created_at`、`read_at`、`revoked_at` |

- 通知の行は、ファイルの名前やコメントの本文を持たない。表示のたびに、判定関数を通して読み直す。読めなくなったファイルの通知は、一覧から省く。
- 組織をまたぐ通知（ゲストとして招かれた組織の通知）は、アカウントの通知の画面で組織ごとに分けて出す。行は、ファイルを持つ組織の `org_id` で持つ。
- 90 日を過ぎた通知は消す（本システムの値）。

### 4.5 メールの中身

| 項目 | 規則 |
| --- | --- |
| 本文 | コメントの本文（最大 500 文字で切る）、書いた人の名前、ファイルの名前、ファイルへのリンク（ファイルの鍵の URL） |
| プレビュー | 固定した位置の周り（フレームがあればそのフレーム）を Worker で描いた PNG を、メールに埋め込む（外部の URL で配らない） |
| 組織の設定 | 「メールにデザインのプレビューを入れない」「メールに本文を入れない（通知だけ）」を組織の管理者が選べる |
| 受け手 | 送る直前に判定し直した人だけ |
| リンク | ログインの後に判定を通して開く。メールのリンクに能力やトークンを入れない |

- プレビューをメールに埋め込むと、メールの転送で、ファイルを読めない人に絵が届きうる。本家もプレビューを送る。組織の設定で切れるようにして、既定は入れる（未解決の問い 2）。

## 5. Realtime（メタデータの購読）

[ADR-0028](../decisions/0028-realtime-metadata-subscriptions.md) による。本家の LiveGraph に相当する。

### 5.1 使いどころ

| 画面 | 購読するビュー |
| --- | --- |
| エディタのコメントの一覧・キャンバスの吹き出し | `fileComments(file_id)`：スレッド、コメント、リアクション、自分の既読 |
| 通知の一覧・未読の数 | `myNotifications(org_id)` |
| ファイルブラウザ（最近・プロジェクト・チーム） | `projectFiles(project_id)`、`recentFiles()`、`teamProjects(team_id)` |
| 共有の画面 | `fileAccess(file_id)`：役割、一般アクセス、申請 |
| バージョンの一覧 | `fileVersions(file_id)` |
| ライブラリの更新の印（MVP の後） | `fileLibraryUpdates(file_id)` |

ファイルの中身（ノード）と在席は、Realtime ではなくマルチプレイヤーの経路で配る（[multiplayer.md](multiplayer.md)）。

### 5.2 構成

```
ブラウザ（useSubscription）
   │ WebSocket（メタデータ用。マルチプレイヤーの接続とは別）
   ▼
Realtime edge（TypeScript。ECS）
   ├─ ビューを「単純な問い合わせ」に分解する
   │     例：fileComments(f) =
   │         Q1: comment_threads WHERE org_id=? AND file_id=?
   │         Q2: comments        WHERE org_id=? AND file_id=?
   │         Q3: comment_reactions WHERE org_id=? AND file_id=?
   │         Q4: comment_read_states WHERE org_id=? AND account_id=? AND file_id=?
   ├─ 問い合わせの結果を Valkey にキャッシュ（キー＝問い合わせの正規形のハッシュ）
   ├─ 購読の判定（判定関数。acl_version でキャッシュ）
   └─ 無効化を受けたら、該当の問い合わせを取り直し、ビューの差分をクライアントへ送る
   ▲
   │ Valkey pub/sub（channel = 無効化のキー）
Realtime invalidator（TypeScript）
   └─ realtime_invalidations（outbox の表）を読み、無効化のキーを publish する
   ▲
Aurora：購読の対象の表に AFTER INSERT/UPDATE/DELETE のトリガー
        → realtime_invalidations (org_id, table_name, key, txid, created_at) を同じトランザクションで書く
```

- **問い合わせは、1 つの表への、等価の条件だけの SELECT**（本家の「易しい式」）に限る。範囲や結合が要るビューは、等価の問い合わせを組み合わせて edge で組み立てる。これで、行の変更から無効化のキー（`table:org_id:file_id` など、等価の条件の列の値）が機械的に決まる。
- **トリガーで無効化を書く**：アプリのコードが outbox を書き忘れても、無効化が漏れない。変更の中身ではなく、キーだけを書く（本家の「変更ではなく無効化を送る」と同じ考え方）。
- **取り直しは writer から**（S1）。無効化の後に reader の遅れで古い値を読む行き違いを避けるため。S2 で読み取りが重くなったら、reader の複製の位置を確かめて読む形を検討する（Aurora でその位置を読めるかは **未検証**）。
- **購読の判定**：購読の開始で判定関数を通す。`acl.changed`（[permissions-and-sharing.md](permissions-and-sharing.md) の 9.2 節）を受けたら、その組織の購読を判定し直し、読めなくなった購読に `revoked` を送って閉じる。行ごとの判定が要るビュー（ファイルの一覧）は、取り直しのたびに行ごとに判定する。

### 5.3 保証

| 項目 | 保証 |
| --- | --- |
| 順序 | 1 つの購読の中では、ビューのバージョン（単調に増える番号）の順に届く。古いバージョンの差分は捨てる |
| 取りこぼし | 無効化を取りこぼしても、edge は 60 秒ごとに購読中の問い合わせのキャッシュを期限切れにし、取り直す。切断の後の再接続では、ビューを全部取り直す |
| 一貫性 | 結果整合。書いた本人の画面は、API の応答で先に反映する（楽観的な更新） |
| 遅れ | 目標：コミットから購読者の画面まで p99 1 秒（同じリージョン） |

### 5.4 規模

- S1：同時接続 5 万（[architecture/README.md](README.md) の 3 節）のうち、Realtime の接続は開いているタブの数と同じ見込み。購読中の問い合わせは、同じ正規形をまとめて数える。数は capacity.md で見積もる。
- `realtime_invalidations` は、1 分より古い行を消す。無効化の数は、購読の対象の表の書き込みの数と同じ。
- S2 で、Aurora の書き込みの負荷にトリガーの分が効くなら、本家と同じく WAL の論理レプリケーションから無効化を作る形に移る（ADR-0028 の再検討の条件）。

### 5.5 プレビューの画像

- メールのプレビューと、通知の画面のサムネイルは、Render Worker（export-and-assets.md）が描く（[ADR-0004](../decisions/0004-gpu-rendering-in-wasm.md)）。
- 描く直前に、受け手（メール）か見る人（画面）の判定を通す。画面のサムネイルは、判定の後の短い期限の署名付き URL で配る。

## 6. 失敗のしかた

| 事象 | 影響 | 対処 |
| --- | --- | --- |
| Realtime の edge が止まる | コメント・一覧がリアルタイムに更新されない | クライアントは再接続し、ビューを取り直す。API の書き込みは影響を受けない |
| 無効化の取りこぼし | 画面が古いまま | 60 秒の期限切れで取り直す |
| トリガーの負荷 | Aurora の書き込みが遅くなる | トリガーはキーだけを書く。負荷を計測し、S2 の前に WAL の方式を判断する |
| 通知の Worker の遅れ | 通知・メールが遅れる | SQS の滞留のアラート。メールは送る直前に判定するので、遅れても漏洩しない |
| メールの送信の失敗 | メールが届かない | 3 回まで再試行し、失敗は捨てる（アプリ内の通知は残る）。バウンスした宛先は送信を止める |
| 固定先のノードが消えた | コメントの位置が合わない | 絶対座標で表示し、印を付ける |
| 濫用（大量のコメント・メンション） | 通知の嵐 | 3.4 節の上限。メンションの通知は、同じ書き手から同じ受け手へ 1 時間に 20 件まで |

## 7. セキュリティ：権限の漏れ

| 経路 | 規則 |
| --- | --- |
| コメントの一覧・API | 判定関数を通す。匿名の閲覧者には出さない |
| Realtime の購読 | 開始時と `acl.changed` で判定。行ごとの判定が要るビューは取り直しのたびに判定 |
| 通知の一覧 | 行は ID だけ。表示のたびに判定して読み直す |
| メール | 送る直前に判定し直す。組織の設定で本文・プレビューを外せる。リンクに能力を入れない |
| メンションの候補 | ファイルを読める人から出す。ゲストに組織のメンバーの一覧を見せない |
| 添付の画像 | S3 に `org_id` と `file_id` を含むキーで置く。判定の後の短い期限の署名付き URL で配る |
| 解決・削除 | 3.3 節の表。他人のコメントは消せない |
| ログ | コメントの本文・ファイルの名前を書かない。ID と数だけ |
| 組織の分離 | 全表に `org_id` と FORCE RLS。ゲストの通知も、ファイルを持つ組織の行 |

### 8.2 性質ベーステスト

| 性質 | 内容 |
| --- | --- |
| 漏洩しない | 任意の権限の変更と通知の送信の順で、送った時点でファイルを読めない人に、メール・アプリ内の通知の本文が出ない |
| 1 回だけ | 任意の Worker の再試行の列で、同じ受け手に同じコメントのメールは 1 回まで（`email_digest_queue` の一意のキー） |
| 無効化の網羅 | 任意の購読の対象の表への書き込みで、その行を含むビューの問い合わせの無効化のキーが、少なくとも 1 つ出る |
| 収束 | 任意の書き込みと購読の順で、書き込みが止まれば、購読者のビューが DB を直接読んだ結果と一致する |
| 位置の追従 | 任意のノードの移動の列で、コメントの表示の位置 = ノードの変換 × offset |

- 結合テスト：ファイルの共有を外した後、10 秒以内に Realtime の購読が閉じ、以後の通知が届かない。
- 負荷テスト：1 ファイルに 500 人が購読し、コメントが毎秒 10 件のとき、p99 1 秒で届く。

## 10. 未解決の問い

1. 匿名の閲覧者にコメントを見せるか（本家の振る舞いは未検証）。
2. メールにデザインのプレビューを入れる既定。
3. アプリで読んだコメントをメールから除く（本家は未検証）ことが、利用者の期待に合うか。
4. トリガーによる無効化の、Aurora の書き込みへの負荷。
5. Realtime の接続を、マルチプレイヤーの接続とまとめるか（接続の数を減らせるが、障害の範囲が広がる）。

### 決定

2026-09-27 に、次のとおり決めた。1 と 3 は、推奨案で確定した。4 は計測で決める。

| 問い | 決定 |
| --- | --- |
| 1 | 見せない。ログインした `view` 以上の人だけに見せる |
| 2 | 入れる。組織の管理者が切れる |
| 3 | 除く。まとめの待ち（2 分）の間に読んだものだけ |
| 4 | E8 の前の負荷試験で測る。書き込みの p99 が 20% 以上悪くなれば、WAL の方式を前倒しにする |
| 5 | 分ける。Realtime の障害で編集を止めないため |

### runbooks

- 通知・メールが届かない問い合わせ：SQS の滞留、`email_digest_queue`、SES のバウンス、送る直前の判定での除外の数。
- Realtime の edge の再起動と、再接続の集中（thundering herd）の抑え方（再接続の待ちに揺らぎを入れる）。
- トリガーの負荷が高いときの、購読の対象の表の見直し。
- 濫用のコメントの取り下げ（運用者の経路、監査付き）。
