# Components and libraries: Figma

コンポーネント、インスタンスと上書き（override）、バリアントとコンポーネントのプロパティの設計。MVP の後に作る、ライブラリの公開・更新・ファイルをまたぐ参照の目標の形も書く。

ドキュメントのモデル（ノードの種類、プロパティの表、ID）は [document-model.md](document-model.md)、変更の送受信と LWW は [multiplayer.md](multiplayer.md)、レイアウトの計算は [layout.md](layout.md) にある。この文書は、その上に載る「コンポーネントの参照と導出」だけを扱う。

この文書で決めたことは次の ADR にある。

| ADR | 決定 |
| --- | --- |
| [0021](../decisions/0021-derived-instances-and-override-keys.md) | インスタンスの中身は保存せず、メインコンポーネントと上書きから導出する。上書きは「元のノードの ID の経路 × プロパティ」をキーにし、1 項目ずつ LWW にする |
| [0022](../decisions/0022-component-properties-and-variants-by-id.md) | コンポーネントのプロパティとバリアントは ID で束ねる。名前での対応は、バリアントの切り替えとインスタンスの入れ替えのときの上書きの引き継ぎにだけ使う |
| [0023](../decisions/0023-library-snapshots-imported-into-files.md) | ライブラリは公開の時点の不変のスナップショットで配り、使う側のファイルに写しを取り込む。ファイルをまたぐ生の参照はしない（MVP の後） |

本家の振る舞いは、2026-09-27 に Figma のヘルプセンターと Figma のブログで確かめた。確かめられなかったものは「未検証」と書く。

## 1. 目的と範囲

| 範囲 | MVP | MVP の後 |
| --- | --- | --- |
| ファイルの中のコンポーネント、インスタンス、上書き、上書きの取り消し | ○ | |
| 入れ子のインスタンス、インスタンスの入れ替え（swap） | ○ | |
| バリアント（コンポーネントセット）、バリアントのプロパティ | ○ | |
| コンポーネントのプロパティ（真偽・テキスト・インスタンスの入れ替え） | ○ | |
| デタッチ、メインコンポーネントへの上書きの反映（push） | ○ | |
| スロットのプロパティ | | ○（本家の新しい機能。要否を利用者の声で決める） |
| ライブラリの公開、ファイルでの有効化、更新の通知と受け入れ | | ○（MVP の後） |
| スタイル・変数のライブラリ | | ○（変数は intent.md の「MVP の後」） |
| 公開したコンポーネントの別のファイルへの移動 | | ○ |

守ること：

- メインコンポーネントを編集しても、インスタンスの上書きは残る（名前の変更、並べ替え、移動、入れ子の追加で消えない）。
- 同じファイルを開いた全員で、インスタンスの導出の結果が同じになる（`doc-model` の同じコードで導出する。[ADR-0001](../decisions/0001-platform-and-stack.md)）。
- コンポーネントの参照に循環ができない（インスタンスが自分自身を含まない）。
- ファイルは、他のファイルを読まずに開いて描ける（ライブラリを使っていても）。

- 本家が上書きを何をキーに保存しているか（元のノードの ID か、名前の経路か）は、公開の文書で見つけられなかった（**未検証**）。本システムの選択は 3.2 節と ADR-0021 にある。
- ライブラリへの読み取りの権限を失った人のファイルで、インスタンスが描かれ続けるかは **未検証**。本システムでは描かれる（6 節）。

## 3. インスタンスと上書き

### 3.1 ノードの種類と主なプロパティ

ノードの種類とプロパティの表は [document-model.md](document-model.md) に登録する。この領域が使うものは次のとおり。

| ノードの種類 | プロパティ | 型 | 競合の単位 |
| --- | --- | --- | --- |
| `COMPONENT` | 通常のフレームのプロパティ一式 | - | プロパティごと |
| `COMPONENT` | `component_props` | `PropKey → PropDef`（4 節） | 定義ごと（キーごとの LWW） |
| `COMPONENT` | `variant_props`（セットの子のとき） | `PropKey → String` | キーごと |
| `COMPONENT` | `publish_key`、`publish_hidden` | 128 ビットの乱数の文字列、真偽 | それぞれ 1 つ |
| `COMPONENT` | `removed_at` | 時刻 | 1 つ |
| `COMPONENT_SET` | `component_props`（バリアントのプロパティを含む） | 同上 | 定義ごと |
| `INSTANCE` | `main_component` | `NodeId` | 1 つ |
| `INSTANCE` | `overrides` | `OverrideKey → Value` | **項目ごと** |
| `INSTANCE` | `component_prop_values` | `PropKey → Value` | キーごと |
| `INSTANCE` | 位置・大きさ・回転・親と並び（`parent_index`） | 通常のノードと同じ | プロパティごと |
| レイヤー（コンポーネントの中） | `component_prop_refs` | `{ visible?: PropKey, characters?: PropKey, main_component?: PropKey }` | キーごと |

- `overrides`・`component_prop_values`・`component_props`・`variant_props`・`component_prop_refs` は、document-model.md の 4.1 節の `kind = map`（要素の鍵ごとが競合の単位。操作は `MapSet`）である。「1 つのプロパティに別々に編集されうる値を詰め込まない」（[AGENTS.md](../../AGENTS.md)）を守るための形。
- `component_props`（60）・`main_component`（61）・`overrides`（62）・`variant_props`（63）は document-model.md の 4.2 節の表にある。`component_prop_values`（64）・`component_prop_refs`（65）・`publish_key`・`publish_hidden`・`removed_at`（66〜68）も、統合の工程で表に登録した（持ち主は components）。
- インスタンスは、自分の子のノードを保存しない。子は導出する（3.3 節）。

### 3.2 上書きのキー

```
OverrideKey = (path: [SourceNodeId], property: PropertyName)
  path  : インスタンスのメインコンポーネントの中のノードの ID から、
          入れ子のインスタンスを 1 段ずつたどった、元のノードの ID の列
  例    : Button の中の Icon（入れ子のインスタンス）の中の Path の塗り
          → ([icon_instance_in_button, path_in_icon_component], "fills")
```

- **キーは元のノードの ID で、名前ではない**（[ADR-0021](../decisions/0021-derived-instances-and-override-keys.md)）。メインで名前を変えても、並べ替えても、別の親へ移しても、上書きは同じノードに当たり続ける。
- ライブラリから取り込んだコンポーネントも、元のファイルのノードの ID をそのまま保つ（7.4 節）。ライブラリの更新でも上書きが残る。
- メインからノードが消えると、そのキーの上書きは「孤立」になる。消さずに持ち、描画にも使わない。メインでノードが戻れば（Undo、版の復元）、上書きも戻る。孤立した上書きは、インスタンスの上書きの取り消しか、デタッチのときにだけ消す。
- 1 インスタンスの上書きの項目は 5,000 まで（本システムの値）。超える変更はサーバーが拒否する。

### 3.3 導出（実体化）

インスタンスの子は、描画・ヒットテスト・選択・レイアウトのために、クライアントのエンジンの中で導出する。

```
materialize(instance):
  main = resolve(instance.main_component)        // 7 節の取り込んだ写しを含む
  for src in main の部分木（main 自身を除く）:
      vnode = VirtualNode(id = (instance.id, path(src)))
      vnode.props = src.props
      for binding in src.component_prop_refs:          // 4 節
          vnode.props[binding.target] = instance.component_prop_values[binding.prop] ?? defs[binding.prop].default
      for (key, value) in instance.overrides where key.path == path(src):
          if overridable(src.kind, key.property):   // 3.4 節の表
              vnode.props[key.property] = value
      if src が INSTANCE:
          入れ替えの上書き（main_component の上書き）を当て、再帰的に materialize する
  レイアウト（layout.md）は、導出した木を入力として別に計算する
```

- **導出したノードの ID** は `(instance_id, path)`（document-model.md の 9.3 節の `InstanceSubId`）。保存しないが、決定的なので、選択・コメントの固定（[comments-and-notifications.md](comments-and-notifications.md)）・他の人の選択の表示で、全員が同じノードを指せる。
- **導出したノードへの編集は、上書きの書き込みに変換する。** 選択したレイヤーの塗りを変えると、`overrides[(path, "fills")]` を書く変更になる。
- **増分の再計算**：メインコンポーネントから、それを使うインスタンスへの逆引きの索引を持つ。メインの部分木のノードが変わったら、そのノードに対応する導出ノードだけを作り直す。読み取りから依存を記録する方式は、本家の Materializer に倣う。導出はレイアウトと分け、導出の後にレイアウトの無効化を伝える。
- **Document Server は導出しない。** サーバーが持つのは、保存されたノードとプロパティだけで、上書きのキーの形・上限・循環（3.5 節）だけを確かめる。メモリと CPU を抑えるため。書き出しとサムネイルの Worker は、同じ `doc-model` の導出を使う。
- **導出の上限**：導出したノードも、ファイルのノードの数（NFR-003〜005 の 10 万ノード）に数える。1 ファイルで導出したノードが 50 万を超えたら、超えた分のインスタンスを「大きすぎて描けない」印の枠で描き、警告を出す（入れ子のインスタンスの掛け算で、数が爆発するのを防ぐ）。入れ子の深さは 16 まで。どちらも本システムの値で、E6 の前の PoC で見直す。

### 3.4 上書きできるプロパティの決定表

上から評価し、最初に一致した行を採る。

| # | 対象 | プロパティ | 結果 |
| --- | --- | --- | --- |
| 1 | インスタンスの根 | 位置、大きさ、回転、`parent_index`、制約 | 上書きではなく、インスタンスのノード自身のプロパティとして書く |
| 2 | 導出ノード | `parent_index`（順序・親）、x・y、制約 | 拒否（構造は変えられない。本家と同じ） |
| 3 | 導出ノード（テキスト） | テキストの枠の大きさ | 拒否（本家と同じ） |
| 4 | 導出ノード（オートレイアウトの子） | 大きさの方式（hug / fill / fixed） | 許可（2026-09-27 に推奨案で確定。本家の振る舞いは **未検証** で、E6 の `edit-derived-nodes` で本家と比べる） |
| 5 | 導出ノード | 名前、表示・非表示、不透明度、塗り、線、エフェクト、ブレンドモード、レイアウトグリッド、書き出しの設定 | 許可 |
| 6 | 導出ノード（テキスト） | 中身（`characters`）、書体、太さ、大きさ、行の高さ、字間、リサイズの方式 | 許可 |
| 7 | 導出ノード（入れ子のインスタンス） | `main_component`（入れ替え） | 許可。ただし 3.5 節の循環の検査を通す |
| 8 | 導出ノード（入れ子のインスタンス） | `component_prop_values` | 許可 |
| 9 | 導出ノード | 子の追加・削除 | 拒否（デタッチを促す） |
| 10 | それ以外 | - | 拒否 |

- 表は `doc-model` の `overridable(kind, property)` の 1 つの関数で持ち、クライアントとサーバーが同じ表を使う。

### 3.5 コンポーネントの参照の循環

コンポーネント C の部分木に、D のインスタンスがあるとき、辺 `C → D` を持つ有向グラフを考える。このグラフに循環を作る変更は、サーバーが拒否する。

| # | 変更 | 辺の増え方 | 検査 |
| --- | --- | --- | --- |
| 1 | インスタンスを C の部分木へ移す（`parent_index`） | `C → main(instance)` | 追加の後に C へ戻る経路がないか |
| 2 | C の中のインスタンスの `main_component` を変える | `C → 新しい main` | 同上 |
| 3 | C の中のインスタンスに入れ替えの上書き・プロパティの値を書く | `C → 入れ替え先` | 同上 |
| 4 | インスタンスの入れ替えのプロパティの既定値を変える | `C → 既定値` | 同上 |
| 5 | コンポーネントを C の中に作る（入れ子のコンポーネント） | 拒否（コンポーネントの中にコンポーネントは置かない。セットの子を除く） | - |

- Document Server は、このグラフをメモリに持ち、変更のたびに増分で更新する。2 つの変更が別々には安全で、合わせると循環になる場合も、`seq` の順に検査するので後の方が拒否される（[ADR-0002](../decisions/0002-central-authoritative-multiplayer.md) の親子の循環と同じ考え方）。
- 取り込んだライブラリの写し（7 節）の辺も同じグラフに入る。

### 3.6 操作

| 操作 | 変更 | 必要な権限 |
| --- | --- | --- |
| コンポーネントを作る | フレームの種類を `COMPONENT` に変える、または選択を包む | 編集 |
| インスタンスを置く | `INSTANCE` を作る（`main_component`） | 編集 |
| 上書きを書く | `overrides` の項目 | 編集 |
| 上書きを取り消す（1 つ・すべて） | 項目を消す。すべての取り消しは孤立した上書きも消す | 編集 |
| デタッチ | インスタンスを `FRAME` に変え、導出した木を新しい ID の通常のノードとして作り、上書きを焼き込む。1 つの変更のまとまりで送る | 編集 |
| メインへの反映（push） | インスタンスの上書きを、メインの対応するノードのプロパティに書き、インスタンスの項目を消す。メインが同じファイルにあるときだけ（本家と同じ） | 編集 |
| メインコンポーネントを消す | `removed_at` を立て、キャンバスに描かない。インスタンスは導出を続ける。参照が 0 になったら、チェックポイントの時に完全に消す | 編集 |
| 消したメインを戻す | `removed_at` を外す | 編集 |

- 「1 つの変更のまとまり」は、document-model.md の 7 節の `ChangeSet`（原子的に当たり、1 つでも検証に失敗すれば全体を拒否）である。直列化で 4 MiB を超える大きなデタッチ・受け入れは、各 `ChangeSet` が単独で不変条件を満たす形に分ける。
- コンポーネントを消しても、使っているインスタンスは壊れない。本家も、メインコンポーネントを消してもインスタンスは残り、インスタンスから「Restore component」で戻せる（[Create components to reuse in designs](https://help.figma.com/hc/en-us/articles/360038663154-Create-components-to-reuse-in-designs)、2026-09-27 に確認）。

## 4. コンポーネントのプロパティ

### 4.1 定義

```
PropDef = {
  id:      PropKey          // 作成時にクライアントが振る。NodeId と同じ形 (session_id, local_id)
  name:    String           // 表示名。変えても束縛は切れない
  kind:    VARIANT | BOOLEAN | TEXT | INSTANCE_SWAP
  default: Value            // VARIANT は既定のバリアントの値
  variant_options: [String] // VARIANT だけ。表示の順
  preferred: [ComponentRef] // INSTANCE_SWAP だけ。優先の候補
  order:   FractionalKey    // パネルでの並び
}
```

- **束縛は ID で行う**（[ADR-0022](../decisions/0022-component-properties-and-variants-by-id.md)）。レイヤーの `component_prop_refs.visible = PropKey` のように持つ。名前の変更で束縛は切れない。
- 定義を消すと、インスタンスの `component_prop_values` のその項目は孤立する（使わない。戻せば効く）。束縛しているレイヤーは既定の値に戻る。
- 1 つのコンポーネント（セット）の定義は 64 まで（本システムの値）。
- スロットのプロパティは MVP の後に扱う。

### 4.2 インスタンスでの値の決まり方

レイヤーのプロパティの値は、次の優先の順で決まる。

| 順 | 値の出どころ |
| --- | --- |
| 1 | インスタンスの `overrides`（そのレイヤーの、そのプロパティ） |
| 2 | インスタンスの `component_prop_values`（束縛しているプロパティ） |
| 3 | メインの定義の `default`（束縛しているプロパティ） |
| 4 | メインのレイヤーのプロパティの値 |

- テキストのプロパティに束縛したテキストのレイヤーに、直接の上書き（1）も書ける。本家のパネルでの見え方と合うかは **未検証**（E6 の `component-properties` で本家と比べる）。1 を優先にするのは、「直接変えたものが見える」を守るため。

## 5. バリアント

### 5.1 保存

- `COMPONENT_SET` は、子に `COMPONENT` だけを持つ（本家と同じ）。セットの `component_props` に `VARIANT` の定義を持つ。
- 各バリアント（子の `COMPONENT`）は `variant_props: PropKey → String` を持つ。表示名（`Size=Large, State=Hover`）はここから作り、名前として保存しない。
- **組の一意は、サーバーで強制しない。** 同時の編集で一時的に同じ組ができうる（LWW の単位が違うため）。クライアントが衝突を表示し、どちらかを直すよう促す（本家も衝突を知らせるだけ）。
- **既定のバリアント**：子の並び（分数インデックス）の先頭。本家はキャンバスの左上を既定にする。本システムが並びの先頭にするのは、レイアウトの計算の結果に依存させず、導出を決定的に保つため（本家との差異）。
- 1 セットのバリアントは 1,000 まで（本システムの値。本家も、大きなセットは遅くなると注意している）。

### 5.2 バリアントの選択

インスタンスでバリアントのプロパティを変えたとき、使うバリアントを次で決める。

| # | 条件 | 結果 |
| --- | --- | --- |
| 1 | 全プロパティの値が一致するバリアントが 1 つ | それを使う |
| 2 | 一致が 2 つ以上（衝突） | 並びの先頭を使う |
| 3 | 一致なし | 変えたプロパティの値が一致するもののうち、他のプロパティの一致が最も多いもの。同数なら並びの先頭 |
| 4 | 変えたプロパティの値のバリアントがない | 変更を受け付けない（パネルで選べない） |

### 5.3 切り替え・入れ替えでの上書きの引き継ぎ

バリアントの切り替えと、インスタンスの入れ替えでは、`main_component` が別のコンポーネントに変わり、元のノードの ID が合わなくなる。このときだけ、名前で対応を取る（本家と同じ規則）。

```
remap(overrides, old_main, new_main):
  for (key, value) in overrides:
      old_src = old_main の中の key.path のノード
      new_src = new_main の中で、old_src と「根からの名前の経路」が同じノード（最初の 1 つ）
      if new_src がない: 捨てる
      elif key.property がテキストの中身・書体: 引き継ぐ（名前の一致だけでよい）
      elif old_src[key.property] == new_src[key.property]: 引き継ぐ（元の値が同じ）
      else: 捨てる
      引き継ぐときは、キーを new_src の経路に書き換える
```

- クライアントが `remap` を計算し、`main_component` の変更と、`overrides` の項目の追加・削除を、1 つの変更のまとまりで送る。
- 切り替えと同時に、別の人が同じインスタンスの上書きを書くと、古い経路の項目が残りうる。孤立した上書き（3.2 節）として無害に残る。

## 6. 失敗のしかた

| 事象 | 影響 | 対処 |
| --- | --- | --- |
| メインコンポーネントが消えた | インスタンスが描けなくなる | 3.6 節のとおり、参照がある間は消さない。万一見つからなければ、インスタンスは最後に導出した大きさの「見つからないコンポーネント」の枠で描き、パネルでデタッチか入れ替えを促す |
| 取り込んだライブラリの写しが壊れている | 同上 | 写しはファイルの中にあるので、版の履歴から戻せる。ライブラリから取り込み直す操作を用意する（MVP の後） |
| 上書きの経路が存在しない | 何も起きない（孤立） | 取り消しの操作で消せる。孤立した項目の数を計測する |
| 導出の爆発（入れ子の掛け算） | タブのメモリ（NFR-004）とフレームレート（NFR-005） | 3.3 節の上限。上限に近いファイルをサムネイルの Worker で数え、計測する |
| 循環の拒否の漏れ | 導出が終わらない | サーバーの検査に加え、導出の側でも訪問中のコンポーネントを記録し、循環を見つけたら枠で描く（二重の守り） |
| クライアントとサーバーの `overridable` の表の食い違い | 書いた上書きが拒否される、または画面だけで効く | 表は `doc-model` の 1 つの関数。接続時の版の確認（delivery.md）で古いクライアントを止める |
| 大きなコンポーネントの編集 | 多くのインスタンスの再導出でフレームが落ちる | 見えているインスタンスを先に導出し、見えないものは描くときまで遅らせる |
| ライブラリの更新の受け入れが途中で切れた | 一部の資産だけ新しい版になる | 受け入れは資産ごとに 1 つの変更のまとまり。途中で切れても、資産ごとに一貫する。版の不一致は更新の画面に残るので、やり直せる |

## 7. ライブラリ（MVP の後）

[ADR-0023](../decisions/0023-library-snapshots-imported-into-files.md) による。MVP の後の E13（ライブラリ）で作る。目標の形だけを書く。

### 7.1 全体の流れ

```
ライブラリのファイル（編集者）
   │ 公開（資産を選ぶ、説明を書く）
   ▼
API ── 判定（編集の権限 × Full のシート × 有料のプラン）
   │ job: library.publish { library_file_id, seq }
   ▼
Worker（ネイティブの doc-model）
   ├ チェックポイント＋ジャーナルで seq の時点の木を作る
   ├ 資産ごとに、部分木と依存（入れ子のコンポーネント）を直列化
   ├ 前の版と中身のハッシュが同じ資産は、blob を作らない
   ├ S3 に blob を書く
   └ Aurora：library_versions、library_assets を 1 つのトランザクションで書く
           outbox：library.version_published
   ▼
Realtime ──▶ そのライブラリを有効にしたファイルを開いている人に「更新あり」の印
```

### 7.2 取り込みと参照

- ファイルでライブラリを有効にすると、`file_library_links` に行を作る。資産の一覧は API で読む（判定を通す）。
- ライブラリの資産のインスタンスを置くと、クライアントは資産の blob を API から受け取り、ファイルの隠れた領域（`imported` の根）に、**取り込んだ写し**として `COMPONENT` の部分木を作る。写しは `library_asset_key` と `library_version` を持つ。
- インスタンスの `main_component` は、この写しを指す。**描画・導出は、ファイルの中の写しだけを読む。** ファイルを開くときに、ライブラリのファイルや S3 の blob を読まない。
- 写しのノードの ID は、ライブラリのファイルの元のノードの ID から決定的に作る（`(asset_key, source_node_id)`）。版をまたいで同じ ID になるので、上書きのキー（3.2 節）が更新の後も当たる。
- 1 つのファイルには、同じ `asset_key` の写しを 1 つだけ持つ。入れ子の依存（ライブラリ A の部品がライブラリ B の部品を使う）も、ファイルの中の B の写しに解決する。版が違う依存を持ち込むと、新しい方に揃える（本家の振る舞いは **未検証**。E13 の `library-import` で本家と比べる）。

### 7.3 更新の受け入れ

| # | 状態 | 画面 | 受け入れの結果 |
| --- | --- | --- | --- |
| 1 | 写しの版 = 最新 | 印なし | - |
| 2 | 写しの版 < 最新、中身のハッシュが違う | 「更新あり」。並べて・重ねて見比べる | 写しの部分木を新しい版に置き換える変更を送る。ノードの ID が同じものはプロパティの差分だけ、消えたノードは消し、増えたノードは作る |
| 3 | 最新で資産が公開から外れた | 「ライブラリから外れた」 | 写しはそのまま残す。インスタンスは描け続ける |
| 4 | ライブラリのファイルが消えた、または読む権限を失った | 「ライブラリを使えない」 | 写しはそのまま。更新は受け取れない |
| 5 | 受け入れる人の権限が閲覧 | 印は出す | 受け入れられない（本家と同じ。編集の権限が要る） |

- 受け入れは、ファイルへの通常の変更としてマルチプレイヤーの経路を通る。版の履歴に残り、Undo できる。
- 2 人が同時に受け入れても、同じ版の同じ中身を書くので、結果は同じになる。

### 7.4 公開の規則

| 項目 | 規則 |
| --- | --- |
| `publish_key` | 最初の公開のときに、元のコンポーネントに 128 ビットの乱数で振る。ファイルの中での移動・名前の変更で変わらない。複製したコンポーネントには新しい鍵を振る |
| 別のファイルへの移動 | 公開の画面で「このファイルへ移す」を選ぶと、元のファイルの資産の `publish_key` を移動先に付け替える。元に戻せない（本家と同じ） |
| 公開しない資産 | `publish_hidden` を立てる |
| 公開先 | 組織のプランでは、チームか組織全体。公開先の人は、ライブラリのファイルを開けなくても資産を使える（[permissions-and-sharing.md](permissions-and-sharing.md) の 7 節） |
| 上限 | 1 ライブラリの資産 10,000、1 資産の blob 5 MB（本システムの値） |

## 8. セキュリティ：権限の漏れ

| 経路 | 規則 |
| --- | --- |
| 取り込んだ写し | ファイルを読める人は、写しの中身（ライブラリの部品の形・名前・説明）を読める。ライブラリへの権限を失っても、既に取り込んだ写しは消えない。**設計上の性質**として利用者に示す（公開した時点で、使う側へ中身を渡したことになる） |
| 資産の一覧と blob | API で、ライブラリの公開先に入るか、ライブラリのファイルを読めるかを判定関数で確かめてから返す。blob の URL は短い期限の署名付き URL にする |
| インスタンスの入れ替えの候補（`preferred`） | 候補が、見る人の読めないライブラリの資産なら、名前もサムネイルも出さず「利用できない部品」とだけ出す |
| 組織の外 | ゲストは組織のライブラリを使えない（本家と同じ。[Members, guests, and limited access](https://help.figma.com/hc/en-us/articles/4420557314967-Members-versus-guests)）。組織をまたぐライブラリは作らない |
| 更新の通知 | Realtime の購読で、ファイルを読める人にだけ配る。通知の中身は「更新がある」と資産の数だけ |
| 導出したノードの名前・テキスト | ファイルの中身なので、ログ・メトリクスに出さない（[AGENTS.md](../../AGENTS.md)）。孤立の数・導出のノード数など、数だけを出す |
| 閲覧だけの人 | 上書き・デタッチ・受け入れの変更は、Document Server が拒否する（[ADR-0002](../decisions/0002-central-authoritative-multiplayer.md) の結合テスト） |

### 9.2 性質ベーステスト

| 性質 | 内容 |
| --- | --- |
| 上書きの保存 | 任意のメインへの編集の列（名前の変更、並べ替え、親の付け替え、ノードの追加）で、元のノードが残っている限り、その上書きは導出の結果に効き続ける |
| 孤立の可逆 | ノードを消してから戻す（Undo）と、上書きの効き方が消す前と同じになる |
| 導出の決定性 | 任意のファイルで、WASM とネイティブの導出の結果（導出ノードの ID とプロパティ）が一致する |
| 増分と全体の一致 | 任意の変更の列で、増分の再導出の結果が、最初から導出した結果と一致する |
| 循環がない | 任意の変更の列（並行を含む）で、サーバーが受け付けた後のコンポーネントの参照のグラフに循環がない |
| 収束 | 任意のクライアントの数と変更の順で、全員の導出の結果が一致する（ADR-0002 の性質の拡張） |
| 更新の後の上書き | 任意のライブラリの版の列で、元のノードが残る上書きは、受け入れの後も残る（MVP の後） |

### 9.3 その他
