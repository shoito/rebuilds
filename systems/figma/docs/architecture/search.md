# Search: Figma

ファイルブラウザの検索の設計。MVP は、ファイル・プロジェクト・チーム・人の名前の検索。MVP の後に、ファイルの中のノードの名前とテキストの検索を足す。どちらも、権限は「候補を絞る段」と「判定関数での読み直し」の二重で効かせる。

この文書で決めたことは次の ADR にある。

| ADR | 決定 |
| --- | --- |
| [0032](../decisions/0032-name-search-in-aurora.md) | MVP の名前の検索は Aurora の中で行う。組織の行を部分一致で絞り、候補を「読めうる資源の集合」で絞り、判定関数で読み直す。別の検索の基盤を持たない |
| [0033](../decisions/0033-content-search-from-checkpoints.md) | MVP の後の中身の検索は、Worker がチェックポイントからノードの名前とテキストを取り出し、OpenSearch に索引する。権限は資源の連鎖を文書に持たせて問い合わせの時点で絞り、判定関数で読み直す |

本家の振る舞いは、2026-09-27 に Figma のヘルプセンターと Figma のブログで確かめた。確かめられなかったものは「未検証」と書く。

## 1. 目的と範囲

| 対象 | MVP | MVP の後 |
| --- | --- | --- |
| ファイルの名前 | ○ | |
| プロジェクト・チームの名前 | ○ | |
| 人（名前・メールアドレス） | ○（組織のメンバーだけ） | |
| 最近開いたファイル（検索の前の候補） | ○ | |
| ファイルの中のノードの名前（フレーム、コンポーネント、レイヤー） | | ○ |
| ファイルの中のテキスト | | ○ |
| ファイルの中の検索（開いたファイルの中で探す） | エディタの機能（エンジンの中で探す。editor-and-tools の領域） | |
| 画像・見た目での検索（本家の AI の検索） | | 範囲の外（[intent.md](../intent.md) の「やらないこと」の AI） |
| ライブラリの資産の検索 | | ○（ライブラリと一緒に。[components-and-libraries.md](components-and-libraries.md)） |

守ること：

- 検索した人がその時点で読めないファイル・プロジェクト・チームを、結果・件数・候補・抜粋のどこにも出さない（NFR-010）。
- 組織をまたいで検索しない。検索は、画面で選んでいる組織の中だけ。

## 3. 名前の検索（MVP）

[ADR-0032](../decisions/0032-name-search-in-aurora.md) による。

### 3.1 保存

| 表 | 追加する列・索引 |
| --- | --- |
| `files` | `name_norm`（`normalizeForSearch(name)`）。索引 `(org_id, last_edited_at DESC)` |
| `projects`、`teams` | `name_norm` |
| `org_members` の表示の名前 | `display_name_norm`、`email_norm` |
| `file_visits` | `org_id`、`account_id`、`file_id`、`visited_at`。最近のファイル。1 人 500 件まで |

- `normalizeForSearch`：NFKC、小文字化、前後と連続の空白を 1 つに。ひらがなとカタカナは同一視しない（rebuilds の Slack・Notion と同じ判断。[Notion の search.md](../../../notion/docs/architecture/search.md) の 4 節）。
- 部分一致（`LIKE '%語%'`）で探す。日本語でも語の区切りが要らない。
- S1 は、pg_bigm・pg_trgm の索引を置かない。RLS の下では `LIKE` が索引を使えず（rebuilds の Slack の [ADR-0027](../../../slack/docs/decisions/0027-search-table-rls-exception.md)）、名前の数（1 組織で最大数十万）なら、`org_id` の索引で組織の行に絞ってから走査すれば足りるため。

### 3.2 問い合わせ

```
searchNames(actor, org, q):
  q_norm = normalizeForSearch(q)                          // 1〜100 文字
  S = readableScopes(actor, org)                          // 3.3 節。候補を絞る資源の集合
  candidates = SELECT id, kind FROM (files ∪ projects ∪ teams)
               WHERE org_id = :org AND name_norm LIKE '%' || :q_norm || '%'
                 AND (team_id = ANY(S.teams) OR project_id = ANY(S.projects)
                      OR id = ANY(S.files) OR owner_account_id = :actor AND project_id IS NULL)
                 AND state = 'active'
               ORDER BY 前方一致を先、次に last_edited_at DESC
               LIMIT 500
  results = []
  for c in candidates:                                     // 読み直し
      if can(actor, read, c): results.append(RLS の下で読み直した行)
      if len(results) == 50: break
  return results                                           // 合計の件数は返さない
```

- **結果の名前・サムネイルは、読み直した行から作る。** 候補の段の値を画面に出さない。
- 候補 500 件を使い切っても 50 件に満たなければ、そこで打ち切る。件数が少なく出ることは許容する。
- 人の検索は、組織のメンバー（ゲストでない人）だけが使える。対象は組織のメンバーの名前とメールアドレス。ゲストの人の検索は、MVP では持たない（ゲストに組織のメンバーの一覧を見せない）。

### 3.3 読めうる資源の集合

`readableScopes` は、判定関数（[permissions-and-sharing.md](permissions-and-sharing.md) の 4.3 節）の**上位集合**を、資源の ID の集合として返す。候補の段が狭すぎると結果が欠け、広すぎると読み直しが増える。広い側に倒す。

| 主体 | `teams` | `projects` | `files` |
| --- | --- | --- | --- |
| 組織のメンバー | 名前の結果：参加しているチーム ＋ open のチーム。中身の候補：役割を持つチーム | 役割を持つプロジェクト ＋ 一般アクセスが `org` のプロジェクト | 役割を持つファイル ＋ 一般アクセスが `org` のファイル |
| ゲスト | 名前の結果：参加しているチーム。中身の候補：役割を持つチーム | 役割を持つプロジェクト | 役割を持つファイル |

- 集合は `(account_id, org_id, acl_version)` をキーにキャッシュする（permissions-and-sharing.md の 9.1 節）。
- チームの中で「招待した人だけ」にしたファイルは、候補に入るが、読み直しで落ちる。
- チームへの参加と可視性は、チームの中身に届かない（[permissions-and-sharing.md](permissions-and-sharing.md) の 3.3 節）。プロジェクト・ファイルの候補は、`teams` の列の「中身の候補」で絞る。
- 「リンクを知っている全員」のファイルは、候補に入れない。役割も一般アクセスの `org` もない人には、最近のファイル（`file_visits`）からだけ出る。

### 3.4 目標と上限

| 項目 | 値 |
| --- | --- |
| 応答の時間 | p95 500ms（10 万ファイルの組織） |
| 語の長さ | 1〜100 文字 |
| 1 回の結果 | 50 件 |
| 候補の上限 | 500 件 |
| 1 人の検索 | 1 分に 60 回 |

- 最大の組織のファイルが 20 万を超えるか、p95 が 500ms を超えたら、Slack の ADR-0027 と同じ形（検索用の表だけ RLS を外し、関数を経由して読む）で pg_bigm の索引を足す。それでも足りなければ、4 節の OpenSearch に名前も載せる。

## 4. 中身の検索（MVP の後）

[ADR-0033](../decisions/0033-content-search-from-checkpoints.md) による。MVP の後に作る（roadmap.md の延期の一覧）。目標の形だけを書く。

### 4.1 取り出し

```
Document Server がチェックポイントを書く（ADR-0003）
  └─ Aurora の files.checkpoint_seq を進める ──▶ outbox: file.checkpointed { org_id, file_id, seq }
        ▼ SQS（search-index）。file_id で間引く
Worker（ネイティブの doc-model）
  ├─ S3 から、その seq のチェックポイントを読む（ページ単位）
  ├─ インスタンスを導出する（components-and-libraries.md の 3.3 節）
  ├─ ページごとに、ノードの名前とテキストの中身を集める。同じページの同じ文字列はまとめる
  └─ OpenSearch に、(file_id, page_id) の文書として書く（外部のバージョン = seq）
```

- **間引き**：同じファイルの索引は、最後の索引から 30 分に 1 回まで。ファイルを閉じて Document Server が手放したときに、最後の 1 回を行う。本家の AI の検索の 4 時間（処理するデータが 12%）より短くするのは、文字の検索は「さっき書いた文言」を探す使い方が多いと見るため（未解決の問い 2）。
- ジャーナルは読まない。チェックポイントの `seq` の時点で索引する。チェックポイントの後の 60 秒以内の変更は、次の索引まで検索にかからない。
- バージョンの履歴の過去のバージョンは索引しない。最新だけ。
- ゴミ箱のファイルは、`in_trash` を立てる。完全な削除で、`file_id` の文書を消す。

### 4.2 文書

| フィールド | 型 | 中身 |
| --- | --- | --- |
| `org_id`、`team_id`、`project_id`、`file_id`、`page_id` | keyword | 資源の連鎖（権限の絞り込みに使う） |
| `drafts_owner_id` | keyword | 下書きなら所有者 |
| `general_access_org` | boolean | ファイル（またはその上位）の一般アクセスが `org` か |
| `in_trash` | boolean | ゴミ箱 |
| `node_names` | text | ノードの名前（フレーム、コンポーネント、レイヤー）。1 ページ 1 MB まで |
| `texts` | text | テキストのノードの中身。1 ページ 1 MB まで |
| `seq`、`indexed_at` | long / date | 外部のバージョン、索引の日時 |

- ファイルの名前・ページの名前は、文書に持たない。結果は読み直しで DB から出す。
- 解析は、rebuilds の Notion の search.md の 4 節（1〜2 文字の N-gram で一致、Sudachi で関連度）をそのまま使う。
- ノードの ID は持たない。結果から開いたファイルの中で、エディタの中の検索で同じ語を探して選ぶ。

### 4.3 権限の適用

| 層 | 何をするか | 何を防ぐか |
| --- | --- | --- |
| 1. 問い合わせの条件 | `org_id` と、3.3 節の集合（`team_id`・`project_id`・`file_id` の `terms`）と `general_access_org`（メンバーのとき）と `in_trash: false` を必ず `filter` に入れる | 件数・並べ替えから、読めないファイルの存在が漏れること |
| 2. 読み直し | 結果の `file_id` を判定関数と RLS の下で読み直す | 文書の資源の連鎖が古い間（移動の直後）の漏洩 |

- 役割の変更で、文書を書き換えない。役割は問い合わせの時点の集合で効く。
- ファイル・プロジェクトの移動と、一般アクセスの変更は、`file.moved`・`acl.changed` の出来事から、該当の文書の連鎖のフィールドを `update_by_query` で書き換える。目標：p99 10 秒。それまでの間は読み直しで守る。
- 抜粋（一致した文字列の前後）は、読み直しで読めると確かめた結果にだけ付ける。抜粋は索引の値（最大 30 分古い）から作るので、既に消した文言が出うる。これは権限の漏れではない（そのファイルを今読める人にだけ出る）が、利用者に「最新でない場合がある」と示す。
- 問い合わせは 1 つの関数 `buildSearchRequest` だけで作り、OpenSearch のクライアントを他の場所から使うことを lint で禁止する（rebuilds の Slack・Notion と同じ）。

## 5. 失敗のしかた

| 事象 | 影響 | 対処 |
| --- | --- | --- |
| Aurora の名前の検索が遅い | 検索が遅い | 3.4 節の上限と、pg_bigm への切り替えの基準 |
| 候補の段が狭すぎる（`readableScopes` の漏れ） | 読めるファイルが結果に出ない | 性質ベーステストで「判定関数で読める ⊆ 候補」を確かめる（6 節） |
| 候補の段が広すぎる | 読み直しが増えて遅い | 読み直しで落ちた件数（`search_hydration_permission_drop`）を計測する |
| 索引の遅れ（MVP の後） | 新しい文言が見つからない | 30 分の間引きの範囲。SQS の滞留のアラート |
| OpenSearch が止まる（MVP の後） | 中身の検索が使えない | 名前の検索（Aurora）だけで結果を返し、画面に「中身の検索は一時的に使えない」と出す |
| 移動の後の連鎖が古い | 読めないファイルが候補に入る | 読み直しで落とす |

## 6. セキュリティ：権限の漏れ

| 経路 | 規則 |
| --- | --- |
| 結果の一覧 | 読み直した行だけを出す。候補の段の値を出さない |
| 件数 | 合計の件数を返さない |
| 入力中の候補（プレビュー） | 同じ関数を通す。最近のファイルの一覧も、表示のたびに判定する |
| 最近のファイル | `file_visits` の行があっても、今読めなければ出さない。権限を失ったファイルの行は、見つけたときに消す |
| 人の検索 | 組織のメンバーだけが使える。ゲストは使えない |
| 組織をまたぐ | 検索は選んでいる組織の中だけ。問い合わせの `org_id` は、要求の組織の文脈（`SET LOCAL app.org_id`）から取り、引数で受け取らない |
| 抜粋（MVP の後） | 読み直しを通った結果にだけ付ける |
| 索引の中身（MVP の後） | OpenSearch の中身は、`buildSearchRequest` だけから読む。運用者の直接の問い合わせは監査付き |
| ログ | 検索の語・結果の名前を書かない。語の長さと件数だけ |

### 7.2 性質ベーステスト

| 性質 | 内容 |
| --- | --- |
| 漏洩しない | 任意の組織・役割・一般アクセス・検索の語で、結果のすべてを、検索した人が判定関数で読める |
| 欠けない | 任意の入力で、判定関数で読めて名前が一致するファイルは、候補の段（`readableScopes` の条件）に入る |
| 組織の分離 | 任意の 2 組織で、一方の組織の文脈の検索が、他方の資源を返さない |
| 取り消しの即時 | 権限を外した直後の検索に、そのファイルが出ない（読み直しで落ちる） |
| 正規化 | `normalizeForSearch` が冪等で、索引と問い合わせで同じ結果になる |

## 9. 未解決の問い

1. MVP で、ファイルの中のテキストまで検索するか（本家はする。intent.md の MVP は「ファイル名での検索」）。
2. 中身の索引の間引きの間隔（30 分）。
3. 最近のファイルの一覧に、組織の外で「リンクを知っている全員」で開いたファイルを出すか。
4. 名前の検索で、ひらがなとカタカナ・全角と半角の揺れをどこまで同一視するか。

### 決定

2026-09-27 に、次の既定で進める。

| 問い | 決定 |
| --- | --- |
| 1 | MVP は名前だけ（intent.md のとおり）。中身の検索は MVP の後の Epic に置く |
| 2 | 30 分で始め、索引の費用と「見つからない」問い合わせで見直す |
| 3 | 出す。ただし、その組織の画面ではなく、アカウントの「最近」の画面に、組織ごとに分けて出す。表示のたびに判定する |
| 4 | NFKC と小文字化だけ（全角と半角は NFKC で揃う）。ひらがなとカタカナは同一視しない |

## 10. quality.md・runbooks・data-model への項目

### quality.md

- 7 節の決定表・性質を、E11 の `spec.md` の `DT-*`・`PROP-*` に移す。
- 「欠けない」の性質（候補の段 ⊇ 判定関数で読める）を、判定関数の変更のたびに走らせる。
- 名前の検索の性能の基準（p95 500ms、10 万ファイル）。
