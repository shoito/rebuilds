# ADR-0029: 更新は Omaha 4 互換のプロトコルと二重の署名で行い、指標で自動に止める

## Context

ADR-0004 で、4 つのチャンネルと段階的な自動更新を決めた。この ADR では、更新の仕組みを決める。条件は次のとおり。

- 重大な脆弱性の修正を、48 時間で Stable の 90% に届ける（NFR-006）。
- 更新の経路は、端末で最も強い権限で動くコードを入れ替える。サーバーの侵害が、全端末の侵害にならないようにしたい。
- 悪い版を、広がる前に止めたい。ただし、クラッシュの報告とテレメトリは同意した人だけが送る（ADR-0005）。
- 端末の識別子を送らない。

## Options

1. **Omaha のプロトコル 4 と互換の形を自作し、CUP とリリースの署名の二重で守る**
2. **OS の仕組みに任せる**（Windows は MSIX とストア、macOS は Sparkle などの既製の更新の部品、Linux はパッケージ管理）
3. **独自の単純な方式**（静的な JSON のマニフェストを取り、署名を確かめる）

## Decision

1 を採用する。詳細は [update-and-release.md](../architecture/update-and-release.md) の 3〜7 節。

- **プロトコル**：Omaha のプロトコル 4（JSON、CUP での応答の署名、`download`・`zucc`・`puff` などのパイプライン、`cached_items` による差分の選択、ID なしで活動中の端末を数える方式）と互換の形にする（[Omaha プロトコル 4](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/updater/protocol_4.md)）。
- **アップデータ**：ブラウザと別のプログラムにし、Windows はサービスとタスクスケジューラ、macOS は LaunchDaemon・LaunchAgent で動かし、約 5 時間ごとに確かめる。本家の Chromium updater の設計に倣う（[Chromium updater の設計](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/updater/design_doc.md)）。Linux は、本家と同じくパッケージのリポジトリで配る。
- **二重の署名**：応答は update-server の CUP の鍵で、リリースの中身（版、成果物のハッシュ、チャンネル）は release-signing アカウントの KMS の鍵で署名する。端末は両方と OS のコード署名を確かめる。update-server の侵害だけでは、署名のない版を入れられない。
- **差分**：Zucchini（実行ファイル）と Puffin（圧縮されたファイル）で作り、失敗したら全体に戻る。
- **段階と自動の停止**：端末で作る 0〜999 の区画で段階を決める。rollout-guard が 5 分ごとに、同意した端末のクラッシュ率・起動の時間と、全端末の更新の失敗率を前の版と比べ、閾値を超えたら段階を凍結する。再開は人が行う。
- **予備の経路**：update-server が止まっても、静的な予備のマニフェスト（GET、別の CDN）で 100% に達した版を取れる。
- 2 は、OS ごとに更新の速さ・段階の制御・差分の有無がばらばらで、NFR-006 を一様に測れない。段階的な配信と自動の停止を自分たちで持てない。
- 3 は単純だが、差分の選択、段階の区画、活動中の端末の数え方、応答の鮮度の保証（古いマニフェストの再送への対策）を後から足すことになり、結局 1 に近づく。

## Consequences

- 良くなること：
  - 公開された仕様と、本家の長い運用の実績に沿える。
  - サーバーの侵害への耐性が、署名の鍵の分離で上がる。
  - 悪い版の広がりを、人の反応を待たずに止められる。
- 引き受けるコスト：
  - アップデータ（OS ごとの常駐、権限の昇格、自己更新）を自作・保守する。
  - S1 では同意した端末が少なく、自動の停止の判定に必要な標本が集まるまで段階を進められない。
  - Linux は、パッケージ管理の更新の設定に依存し、NFR-006 が遅れうる。
  - CUP の鍵とリリースの鍵の 2 つを運用し、交換の手順を持つ。

## Confirmation

- 結合テスト：CUP の署名が合わない応答、リリースの署名が合わない成果物、ハッシュが合わない差分を、アップデータが拒否すること。
- 結合テスト：update-server を止めた状態で、アップデータが予備のマニフェストから 100% の版を取ること。
- 年 1 回、staging で、rollout-guard が意図的に悪くした版を凍結することを確かめる。
- 緊急の修正のたびに、48 時間での普及の割合を記録する（ADR-0004）。
