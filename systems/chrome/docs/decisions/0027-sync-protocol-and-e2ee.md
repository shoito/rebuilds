# ADR-0027: 同期は版の番号による楽観的な排他のプロトコルにし、すべてのデータ型を利用者の鍵で暗号化する

## Context

[ADR-0005](0005-privacy-first-services.md) で、同期はパスワードを必ず、その他のデータも既定でエンドツーエンドで暗号化すると決めた。同期のプロトコル（取得と送信、版、衝突）と、鍵の作り方・配り方・回復の方法を決める。

確かめたこと（2026-09-26）：

- 本家の同期は、`GetUpdates` と `Commit` の 2 つの要求と、データ型ごとの橋で組み立てる（[components/sync](https://chromium.googlesource.com/chromium/src/+/master/components/sync/README.md)）。
- 本家の暗号化（Nigori）は、鍵の種類として、サーバーが渡す鍵（keystore）、利用者のパスフレーズ（custom passphrase）、trusted vault を持つ。パスフレーズの鍵の導出は、M70 から scrypt（N=2^13、r=8、p=11、無作為の塩）、それ以前は PBKDF2-HMAC-SHA1 の 1,003 回・固定の塩（[nigori_specifics.proto](https://chromium.googlesource.com/chromium/src/+/HEAD/components/sync/protocol/nigori_specifics.proto)）。既定の keystore では、サービスの運営者が鍵を持つ。

## Options

プロトコル：

1. **データ型×アカウントごとの版の番号と、元にした版による楽観的な排他。衝突は端末が型ごとの規則で解く**
2. **CRDT で、衝突を自動で合わせる**

暗号化：

- A. **すべての型を、アカウントごとの根の鍵（SRK）で暗号化する。SRK は端末の鍵・回復用のコード・任意のパスフレーズで包んでサービスに置く**
- B. **本家と同じく、既定はサーバーの鍵、希望者だけ利用者のパスフレーズ**
- C. **パスワードだけを利用者の鍵、他はサーバーの鍵**

## Decision

1 と A を採用する。詳細は [sync-and-accounts.md](../architecture/sync-and-accounts.md) の 3〜6 節。

- 版の番号はサービスが Commit のときに振る。取得は進み具合の印（最後の版）から、送信は元にした版を付け、違えば衝突として返す。
- 衝突は端末で解く。規則はデータ型ごとに決める（項目ごとに新しい方、追加だけの和集合、端末ごとの所有）。サービスは中身を読めないので、合わせ方を持たない。
- SRK から HKDF でデータ型ごとの鍵を導き、XChaCha20-Poly1305 で暗号化する。AAD にアカウント ID・データ型・エンティティ ID・鍵の版を入れる。エンティティ ID は鍵付きハッシュにし、URL などを ID から推測させない。
- SRK は端末の X25519 の鍵で HPKE（RFC 9180）で包む。新しい端末は、既存の端末での承認（両方に同じ確認の数字）、回復用のコード（128 bit）、任意のパスフレーズ（Argon2id）のどれかで SRK を得る。
- 端末を外したら SRK を回転し、残る端末が背景で書き直す。
- 利用者の選択で暗号化を外す設定は、MVP では持たない（ADR-0005 の「既定で」を、MVP では「常に」とする）。
- 2 を採らない理由：ブックマークの木・パスワードのような型では、自動の合わせ込みの結果が利用者の期待とずれやすく、型ごとに規則を書く量は 1 と変わらない。CRDT の操作の履歴を暗号化して持つと、保存の量も増える。
- B・C を採らない理由：ADR-0005 に反し、履歴やブックマークがサービスの運営者に読める。

## Consequences

- 良くなること：
  - サービスの DB・バックアップが漏れても、同期のデータは読まれない。運営者も読めない。
  - サービスは中身を解釈しないため、単純な保存と版の管理になり、規模を広げやすい。
- 悪くなること、引き受けるコスト：
  - すべての端末と回復用のコード・パスフレーズを失うと、データは戻らない。運用者は助けられない。
  - サーバー側での検索・集計・重複の除去・不正な値の修正ができない。不具合の直しは端末の更新で行う。
  - データ型・大きさ・時刻などのメタデータは見える。
  - 端末の時計に依存する「新しい方」の判定で、まれに古い変更が勝つ。
  - Argon2id の引数と、Linux での鍵の保管（Secret Service が無い環境）は **未検証**。E8 で基準の端末で測る。

## Confirmation

> 2026-09-27 の注記：Argon2id の引数は、RFC 9106 の 4 節の推奨（1 つ目：t=1、p=4、m=2 GiB。2 つ目：t=3、p=4、m=64 MiB）を出発点にする。基準の端末で 1 秒以内に終わる値を、E8 で測って決める（[RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html#section-4)、2026-09-27 に確認）。Linux の Secret Service が無い環境での鍵の保管は、未検証のまま E8 で確かめる。

- 同期のサービスの DB の定期の検査で、暗号文でない値（URL、JSON、protobuf の平文）が無いことを確かめる（ADR-0005）。
- 衝突の規則を、データ型ごとの性質ベースのテスト（任意の順序で届いた変更が、すべての端末で同じ結果に収束する）で確かめる。
- 端末の追加の確認の数字が、公開鍵のすり替えで一致しなくなることを、テストで確かめる。
- 暗号の設計と実装に、E8 の完了の前に外部の暗号のレビューを受ける。
