# ADR-0026: 拡張機能のストアは自動と人の審査を組み合わせ、停止の一覧で公開後の拡張機能も止められるようにする

## Context

拡張機能は、ホストの権限を持つと、利用者の閲覧の内容を読み書きできる。悪意のある拡張機能や、買収の後に悪意のある更新を出す拡張機能は、ブラウザの安全の大きな穴になる。ストアでどう審査し、公開の後に見つかった悪い拡張機能をどう止めるかを決める。

確かめたこと（2026-09-26）：

- 本家の Chrome Web Store は、自動と人の仕組みを組み合わせ、開発者の実績や利用者の数にかかわらず、すべての提出を同じ審査にかける。大半は数日、長いと数週間。広いホストの権限と大量のコードは審査を長くし、難読化は禁止される。措置は却下・警告（7〜30 日の猶予）・取り下げで、マルウェアや審査の回避は通知なしで取り下げ、アカウントを停止する（[Chrome Web Store review process](https://developer.chrome.com/docs/webstore/review-process)）。
- 本家のストアは、公開・更新の前に開発者に 2 段階認証を求める（[2-Step Verification](https://developer.chrome.com/docs/webstore/program-policies/two-step-verification)）。
- 本家は、マルウェアと判定した拡張機能を利用者の端末で自動で無効にし、ストアから消えた拡張機能を安全確認で知らせる。

## Options

1. **すべての提出に自動の審査をかけ、リスクの点数の高いものを人が審査する。公開後は停止の一覧で止める**
2. **すべての提出を人が審査する**
3. **自動の審査だけにし、公開後の通報で対応する**

## Decision

1 を採用する。詳細は [extensions.md](../architecture/extensions.md) の 7〜9 節。

- 自動の審査：形式、遠隔のコード、難読化、マルウェアの検査、隔離した環境での動的解析、更新の差分の検査。結果からリスクの点数を付ける。
- 人の審査：点数が閾値を超えたもの、疑いのあるもの、利用者の多い拡張機能の権限の増加。目標は p90 で 3 営業日以内。
- 開発者は、公開にパスキーか TOTP の 2 段階認証を必須にする。
- 利用者の多い拡張機能の更新は段階的に配り、その間の指標で止められるようにする。
- 停止の一覧（`malware`・`policy_violation`・`potentially_unwanted`・`unpublished`）を、Safe Browsing のリストと同じ経路・署名で配り、端末は 30 分以内に反映する（NFR-009 と同じ）。`malware` は利用者も企業のポリシーも上書きできない。端末は拡張機能のデータを消さず、誤って止めたときは一覧から外せば戻る。
- 2 を採らない理由：提出の量に比例して人手が要り、審査の待ちが長くなる。人は、自動の審査が絞り込んだ高リスクのものに集中させる方が、見落としが減る。
- 3 を採らない理由：公開から通報までの間に、利用者のデータが漏れる。

## Consequences

- 良くなること：
  - 大半の提出を速く公開でき、高リスクのものを人が見る。
  - 公開後に悪意が見つかっても、端末で 30 分以内に止められる。
- 悪くなること、引き受けるコスト：
  - 動的解析の環境、審査の担当者、異議の申し立ての対応を運用し続ける。
  - 自動の審査の誤検知で、正当な拡張機能の公開が遅れる。点数の閾値を定期に見直す。
  - 停止の一覧は強い力を持つ。誤った追加は多くの利用者の拡張機能を止めるため、追加は人が根拠を付けて行い、二人目の確認を経る（緊急時の手順は runbook）。

## Confirmation

- 既知の悪い拡張機能の標本（公開の研究と、自分たちの試験用の標本）を、自動の審査が高リスクと判定することを、審査の仕組みの回帰テストにする。
- 停止の一覧への追加から、端末での無効化までの時間を、合成の端末で継続的に測る（目標 30 分以内）。
- 審査の待ちの時間（p50・p90）と、異議で覆った判定の割合を、ストアの指標として公開する。
