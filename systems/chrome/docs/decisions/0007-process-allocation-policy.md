# ADR-0007: デスクトップでは常にサイトごとにプロセスを分け、上限を超えても異なるサイトを混ぜない

## Context

[ADR-0003](0003-multi-process-site-isolation.md) で、サイトごとのプロセスを前提にした。具体的に、何を「サイト」とし、プロセスの数が増えたときにどうするかを決める必要がある。

本家は、デスクトップで全サイトを隔離（site-per-process）し、メモリに応じた soft limit を置く。上限を超えたら同じサイトのプロセスを再利用し、異なるサイトは混ぜない。Android では、メモリの少ない端末で、ログインのあるサイトなどに隔離を絞る（[Process Model and Site Isolation](https://chromium.googlesource.com/chromium/src/+/main/docs/process_model_and_site_isolation.md)、[Site Isolation](https://www.chromium.org/developers/design-documents/site-isolation/)）。この題材の MVP はデスクトップだけである。

## Options

1. **常にサイトごと。上限は目安で、超えたら同じサイトだけを再利用し、異なるサイトは混ぜない**（本家のデスクトップと同じ）
2. **上限を超えたら、異なるサイトも同じプロセスに入れる**（Site Isolation 以前の本家）
3. **オリジンごとに分ける**
4. **一部のサイトだけ隔離する**（本家の Android）

## Decision

1 を採用する。詳細は [process-model.md](../architecture/process-model.md) の 3 節。

- サイトは、スキーム＋登録可能ドメイン（eTLD+1、Public Suffix List）とする。
- プロセスの鍵（そのプロセスに置いてよいもの）には、サイトのほか、クロスオリジン隔離の有無、サンドボックス化した iframe か、プロファイル（通常かシークレットか）を含める。鍵は最初の文書を入れる前に決め、変えない。
- 同じ閲覧のグループの同じサイトの文書は、必ず同じプロセスに置く。
- 上限は、端末のメモリから計算する目安とする。上限を超えたら、同じ鍵のプロセスを再利用する。同じ鍵のプロセスがなければ、上限を超えて新しく起動する。同じサイトの iframe は、上限の前でも既存のプロセスを再利用する。
- 起動の待ち時間を隠すため、鍵を掛けていない予備の Renderer を 1 つ持つ。メモリの圧迫の中以上では持たない。
- オリジン単位の分離は、`Origin-Agent-Cluster` の既定の有効化と同じく論理的な分離にとどめ、プロセスはサイト単位のままにする。明示的に求めたオリジンのプロセスを分けるのは S2 で検討する。
- 2 は、侵害された Renderer や Spectre の類で、同居した別のサイトのデータが読める。ADR-0003 の目的に反する。
- 3 は、同じサイトの別のオリジン（`a.example.com` と `b.example.com`）が `document.domain` などで同期的に触れ合う互換性を壊し、プロセスの数も大きく増える。
- 4 は、メモリの少ない携帯端末のための妥協で、デスクトップには要らない。

## Consequences

- 良くなること：
  - 侵害されたプロセスの被害が、常に 1 つのサイト（と、同じプロファイル）に閉じる。上限の状態に関わらず、安全の性質が変わらない。
- 引き受けるコスト：
  - タブの多い利用者で、プロセスの数とメモリが増える。予備の Renderer、bfcache、タブの破棄（メモリの圧迫の対応）と組み合わせて、NFR-004 に収める。
  - 上限の式は、E3 で測って決め直す必要がある。

## Confirmation

- 性質のテスト：任意のナビゲーションとタブの操作の列の後、どのプロセスにも、異なるサイトの文書（と、異なる鍵の文書）が同居していない。
- プロセスの数を上限の数倍に増やす負荷のテストで、上の性質が保たれることを確かめる。
- NFR-004 の計測に、プロセスの数と上限の超過の時間を並べて記録する。
