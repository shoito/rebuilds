# Runbook: 緊急のセキュリティ修正の配信

- Owner: Ops
- 対応するアラート: 緊急の修正の普及の遅れ、署名の工程の失敗（緊急の修正の最中）、セキュリティの担当からの依頼
- 最終確認日: 2026-09-26

方針は [update-and-release.md](../architecture/update-and-release.md) の 6 節（NFR-006）、署名は同じく 5 節、脆弱性の扱いは [sandbox-and-security.md](../architecture/sandbox-and-security.md) にある。

## 症状

次のときに使う。

- 重大度が Critical・High の脆弱性で、悪用が確認されたか、公表が迫っている（自作のコード、部品のどちらでも）
- 部品（V8 など）の上流が、悪用の確認された脆弱性の修正を出した

## 影響

- 修正が届くまで、利用者が攻撃にさらされる。
- NFR-006：修正の版の Stable への配信の開始から 48 時間以内に、直近 48 時間に活動した Stable の端末の 90% に届ける。

## 確認

1. セキュリティの担当が、重大度・悪用の有無・影響する版とチャンネル・公表の予定を記録する。Issue は非公開にする。
2. 修正が `main` に入っているか。部品の修正なら、部品の成果物が作り直されているか（[build-and-test.md](../architecture/build-and-test.md) の 4.5 節）。
3. 影響するリリースのブランチ（Stable、Beta。企業の固定の版があればそれも）を決める。
4. 署名の工程が使えるか（release-signing の KMS・CloudHSM・署名専用の EC2 Mac の状態）。

## 対処

時間の予算は、配信の開始（T0）までを 8 時間以内とする。

1. **修正を入れる（T−8h）。** 修正の PR を `main` へ入れる。コミットのメッセージは中立に書き、脆弱性の内容を書かない。承認は作成者と別の 1 人でよい。
2. **ブランチへ入れる（T−6h）。** Stable と Beta の `release/M` へ cherry-pick する。release owner が承認する。
3. **緊急の CI（T−6h〜T−2h）。** ブランチで緊急の CI を起動する：3 OS のビルド、再現性の比較、スモーク（起動、ナビゲーション、サイトの隔離のテスト、更新の適用）。可能なら、脆弱性の再現のテストを非公開のテストとして足す。
4. **署名（T−2h）。** release-signing で OS の署名・公証とリリースの署名を行う。公証が遅れたら、Windows・Linux を先に進め、macOS は届き次第配る（OS ごとに配信を分けてよい）。
5. **Beta に配る（T−1h）。** Beta に 100% で出し、1 時間、起動直後のクラッシュを見る。
6. **Stable に配る（T0）。** `urgency=critical` で、Stable の 10% に 1 時間。自動の停止の条件は「起動直後のクラッシュ率が前の版の 3 倍」だけにする。
7. **100%（T+1h）。** 問題がなければ 100% にする。予備のマニフェスト（[update-and-release.md](../architecture/update-and-release.md) の 4.4 節）にも載せる。
8. **普及を見る（T+6h、T+24h、T+48h）。** 普及の割合を OS ごとに記録する。24 時間で 60% に届かなければ、原因を見る：
   - 再起動の待ち（再起動の促しが効いているか）
   - 更新の失敗（エラーの種類）
   - Linux のパッケージ管理の遅れ（OS ごとに分けて報告する）
9. **公表する。** 普及が 90% に達するか、公表の期限が来たら、セキュリティの担当がリリースノートと勧告を出す。Issue の非公開は、Stable の普及を見て解く時期を決める。

### 署名の工程が使えないとき

- KMS・CloudHSM が東京で使えなければ、大阪の複製で署名する（[infrastructure.md](../architecture/infrastructure.md) の 5.1 節）。
- macOS の署名専用の機械が使えなければ、予備の機械を用意する。予備もなければ macOS を後回しにし、他の OS を先に配る。

## エスカレーション

| 状況 | 連絡先 |
| --- | --- |
| 開始の判断 | セキュリティの担当と release owner の 2 人 |
| T0 が 8 時間の予算を超えそう | Dev（テックリード）、PM |
| 修正の版で重大な回帰が出た | [bad-release-rollback.md](bad-release-rollback.md) に進む。止めるか、回帰の修正を同じ流れで出すかを、セキュリティの担当と決める |
| 48 時間で 90% に届かない見込み | Ops の責任者、PM（企業の管理者への告知を含む） |

## 事後

- NFR-006 の達成（48 時間の普及の割合、OS ごと）を記録する（ADR-0004 の Confirmation）。
- T0 までの各段の所要時間を記録し、8 時間を超えた段を短くする対策を Intent として起票する。
- 部品の脆弱性なら、部品の追従の時間（上流の公開から T0 まで）も記録する。
- この手順で足りなかったことを、ここに反映する。
