# Browser UI: Chrome

ブラウザの UI（ウィンドウ、タブ、アドレスバー、設定、プロファイル、ダウンロード）と、アクセシビリティ・国際化・UI の性能の設計。UI の作り方（ツールキット）は [ADR-0024](../decisions/0024-ui-toolkit.md) に従う。Web のコンテンツの描画は [rendering.md](rendering.md)、プロセスの構成は [process-model.md](process-model.md)、権限の確認とパスワードマネージャは [safe-browsing-and-permissions.md](safe-browsing-and-permissions.md) にある。

この文書の値（予算、件数）は初期値である。E6 の各変更の `spec.md` で要件にするときに確定する。

## 1. 全体像

本家 Chrome は、ウィンドウの枠・タブ・ツールバー・ダイアログを、自前の UI ツールキット（Views）で描き、設定や履歴などの内部ページ（`chrome://`）を、エンジンで描く Web の技術（WebUI）で作る。macOS も、以前の Cocoa から Views へ移った（[Chromium の glossary](https://chromium.googlesource.com/chromium/src/+/main/docs/ui/learn/glossary.md)、[MacViews の release plan](https://chromium.googlesource.com/chromium/src/+/0e94f26e8/docs/ui/views/macviews_release.md)）。本システムも同じ 2 層に分ける（ADR-0024）。

```
┌──────────────────────── Browser プロセス ─────────────────────────┐
│ 枠の UI（Rust の自前の UI 層）                                     │
│   ウィンドウ・タブの帯・ツールバー・アドレスバー・候補・ダイアログ │
│   ・ダウンロードの吹き出し・権限の確認                             │
│   描画：GPU プロセスの合成器へ（Web のコンテンツと同じ経路）       │
│   アクセシビリティ：AccessKit → UIA / NSAccessibility / AT-SPI     │
│ OS の薄い層（ウィンドウ、メニューバー、IME、ドラッグ、通知）       │
└───────────────┬───────────────────────────────────────────────────┘
                │ IPC（型付きのメッセージ。Web のページとは別の許可リスト）
┌───────────────▼──────────────┐   ┌──────────────────────────────┐
│ 内部ページの Renderer          │   │ Web の Renderer（サイトごと）  │
│ <brand>://settings, history,  │   │ サンドボックス。Web の権限だけ │
│ downloads, bookmarks,         │   └──────────────────────────────┘
│ extensions, newtab            │
│ サンドボックス。専用のプロセス │
└──────────────────────────────┘
```

- **枠の UI は Browser プロセスで動くが、スクリプトを実行しない。** Rust のコードだけで描く。最も権限の高いプロセスに、JavaScript の実行環境を持ち込まない。
- **内部ページは、Web のページと同じエンジンで描き、専用の Renderer に隔離する。** 内部ページは Web のページと同じプロセスに載せない（[ADR-0003](../decisions/0003-multi-process-site-isolation.md)）。内部ページから Browser への要求は、ページごとの許可リスト（設定のページは設定の読み書きだけ、など）で検査する。
- 内部ページのスキームは `<brand>://`（[リポジトリ共通の ADR-0006](../../../../docs/decisions/0006-brand-neutral-identifiers.md)）。

### 1.1 OS の薄い層

| OS | ウィンドウ・入力 | IME | 備考 |
| --- | --- | --- | --- |
| Windows 10/11 | Win32（`HWND`）、DirectComposition | TSF | 枠の独自の描画（タイトルバーにタブを置く）。Snap Layouts に対応する |
| macOS 13 以降 | AppKit（`NSWindow`）、Core Animation | `NSTextInputClient` | メニューバーはネイティブ。フルスクリーン・Spaces に対応する |
| Linux | Wayland を先に、X11 も対応 | Wayland の `text-input-v3`、X11 は XIM / IBus | クライアント側の枠（CSD）。`xdg-desktop-portal` でファイル選択 |

- この層は OS ごとに書く。汎用のウィンドウのライブラリ（winit など）は、日本語の IME の変換中の表示・候補の窓の位置を細かく制御しにくいため、使わない。winit も IME のイベント（変換中の文字列、確定）と候補の窓の位置の指定（`set_ime_cursor_area`）を持つが、次の版でこの API を `request_ime_update` に置き換えつつある（[winit](https://github.com/rust-windowing/winit)、2026-09-27 に確認）。API が落ち着いていないことも、使わない理由に加える。E6 の初めに、3 OS の IME で自前の層と比べて確定する。

## 2. ウィンドウとタブ

### 2.1 モデル

```
Profile ─┬─ Window ─┬─ TabStrip ─┬─ Tab（WebContents 1 つ）
         │          │            └─ TabGroup（名前、色、折りたたみ）
         │          └─ 固定したタブ
         └─ Window …
```

- タブは 1 つの `WebContents`（ナビゲーションの履歴と、表示中のフレームの木）を持つ。Renderer の割り当てはタブではなくサイトで決まる（[process-model.md](process-model.md)）。
- タブの帯の操作：開く・閉じる・並べ替え・ウィンドウ間の移動（ドラッグで新しいウィンドウ）・固定・ミュート・グループ化・複製・閉じたタブを開き直す（直近 25 件）。
- 閉じたときの状態の保存：ウィンドウ・タブ・ナビゲーションの履歴を、プロファイルの中に数秒ごとに書く。起動時に「前回のタブを開く」を選べる。シークレットのウィンドウは書かない。

### 2.2 メモリの節約

- 背景のタブを破棄する（Renderer を解放し、タブの帯には残す）。条件と優先度は [process-model.md](process-model.md) の「プロセスの上限」と合わせる。
- 破棄の対象から外すもの：音声を再生中、フォームに入力中、固定したタブ（設定による）、利用者が除外したサイト。
- 破棄したタブは、選ぶと読み込み直す。bfcache と区別して表示する（破棄したことをタブに小さく示す）。

## 3. アドレスバー（オムニボックス）

### 3.1 候補の構成

本家は、複数の提供元（履歴、ブックマーク、検索の候補、ショートカット）の候補を、関連度の点数で並べる（`components/omnibox` の `AutocompleteController`）。本システムも同じ形にする。

| 提供元 | 元のデータ | 実行する場所 | 送信 |
| --- | --- | --- | --- |
| 入力そのもの | URL か検索語かの判定 | Browser | なし |
| 履歴 | 訪問の回数・入力の回数・最終訪問 | Browser（メモリの索引） | なし |
| ブックマーク | タイトル・URL | Browser（メモリの索引） | なし |
| 開いているタブ | 同じプロファイルのタブ | Browser | なし |
| ショートカット | 過去に入力した語と選んだ候補の組 | Browser | なし |
| 検索の候補 | 選んだ検索エンジンの候補の API | Network サービス経由 | **入力を検索エンジンへ送る。既定で無効**（3.3） |
| 内部ページ・拡張機能 | `<brand>://` のページ、拡張機能のキーワード（`omnibox` API） | Browser | 拡張機能へは、キーワードの後の入力だけ |

- 手元の提供元は、入力のたびに同期的に 1 回目の結果を返し、検索の候補は非同期に追加する。候補の並びが入力の途中で大きく入れ替わらないよう、上位の候補を固定する。
- 履歴・ブックマークの索引は、起動後に背景で作り、プロファイルの DB（[storage.md](storage.md) の対象外。ブラウザ自身のデータ。[data-model.md](data-model.md)）から読む。
- 貼り付けた文字列・IDN（国際化ドメイン名）は、表示の段階で紛らわしい文字を Punycode で表示する（本家の IDN の表示規則に寄せる）。

### 3.2 検索エンジンの選択（既定を置かない）

- **既定の検索エンジンを置かない。** 初回の起動で選択の画面を出し、利用者が選ぶまで、アドレスバーの入力は「URL として開く」か「検索エンジンを選ぶ」の案内にする。
  - 本家は EEA で、DMA に基づく選択の画面を、主要な検索エンジンを無作為の順で並べて出す（[About search engine choice screens in Chrome](https://support.google.com/chrome/answer/15290248?hl=en)）。本システムは、地域を問わず全員に出す。
- 選択肢は、国ごとの一覧（名前、候補の API の URL、検索の URL、アイコン）を、更新の配信（[update-and-release.md](update-and-release.md)）で届ける。表示の順は端末ごとに無作為にする。検索エンジンとの商業的な契約は持たない（持つ場合は別の ADR にする）。
- 利用者は、設定で検索エンジンを足し・消し・既定を変えられる。OpenSearch の記述を持つサイトは、候補として追加を提案する（自動では足さない）。
- 企業のポリシーで固定できる（5 節）。

### 3.3 検索の候補と送信

- 検索の候補を有効にすると、入力の途中の文字列を、選んだ検索エンジンへ送る。これは閲覧の内容の送信にあたるため、選択の画面で別に選ばせ、**既定は無効** にする（[ADR-0005](../decisions/0005-privacy-first-services.md)）。
- 次のときは、有効でも送らない：シークレットのウィンドウ（利用者が別に許可した場合を除く）、入力が URL・ファイルのパス・内部ページに見えるとき、パスワードの入力欄から貼り付けた直後。

## 4. 設定

- 設定は内部ページ（`<brand>://settings`）で作る。項目の値の正本は Browser プロセスの設定の記憶（プロファイルごとの `Preferences`）で、内部ページは許可された項目だけを読み書きする。
- 各項目は、値の出どころ（利用者、企業のポリシー、既定）を持つ。ポリシーで決まった項目は、変更できない表示（管理されていることを示すアイコンと説明）にする。
- 同期する設定と、端末に閉じる設定を、項目ごとに決める（同期の対象は [sync-and-accounts.md](sync-and-accounts.md) の 3 節）。

## 5. 企業のポリシー（基本）

本家は、Windows のグループポリシー（ADMX）、macOS の構成プロファイル、Linux の JSON ファイルでポリシーを受ける。本システムも同じ 3 つの経路にする。

| OS | 経路 | 置き場所 |
| --- | --- | --- |
| Windows | レジストリ（GPO・Intune） | `HKLM\Software\Policies\<Brand>\<Product>`、ADMX を配布する |
| macOS | 構成プロファイル（管理された設定） | ドメイン `com.<brand>.<product>` |
| Linux | JSON | `/etc/<brand>/policies/managed/*.json` |

- ポリシーの定義（名前、型、対応する版、既定、説明）は 1 か所の定義ファイルに置き、ADMX・プロファイルの雛形・文書を生成する。名前は本家と同じ意味のものは同じ語を使ってよい（例：`ExtensionSettings`、`DefaultSearchProviderEnabled`。名前は機能の説明であって商標ではない）。
- MVP のポリシー：検索エンジンの固定、拡張機能の設定（強制インストール・禁止・許可。[extensions.md](extensions.md) の 8 節）、更新の方針、テレメトリ・クラッシュの報告、同期の無効化、パスワードマネージャの無効化、シークレットモードの可否、プロキシ・DNS over HTTPS、起動時のページ、UIA の提供の可否（6 節）。
- ポリシーは起動時と、変更の通知（Windows のレジストリの監視、macOS の設定の変更通知、Linux のファイルの監視）で読み直す。クラウドでの管理（管理コンソール）は S2 で扱う。
- `<brand>://policy` で、適用中のポリシーと出どころを表示する。

## 6. プロファイルとシークレットモード

### 6.1 プロファイル

- プロファイルは、ディスクの上の 1 つのディレクトリで、履歴・Cookie・保存領域・拡張機能・設定・同期のアカウントを、他のプロファイルと共有しない。
- 各プロファイルに、別のアカウントで同期を設定できる（[sync-and-accounts.md](sync-and-accounts.md)）。アカウントなしでも使える。
- ゲスト：一時的なプロファイル。最後のウィンドウを閉じると、ディレクトリごと消す。

### 6.2 シークレットモード

| 項目 | 振る舞い |
| --- | --- |
| 保存領域・Cookie・キャッシュ | 元のプロファイルと別の、メモリの上の保存領域（off-the-record）。最後のシークレットのウィンドウを閉じると破棄する |
| 履歴・検索の候補・入力の記録 | 書かない |
| ブックマーク・ダウンロード | ブックマークの追加と、ダウンロードしたファイルは残る（その旨を最初のページに示す） |
| 拡張機能 | 既定で無効。利用者が拡張機能ごとに許可したものだけ動く |
| サードパーティ Cookie | 常に遮断（[networking.md](networking.md)） |
| 同期 | 行わない |

- シークレットのページも、Renderer の分け方・サンドボックスは同じにする。元のプロファイルのページと同じ Renderer に載せない。
- シークレットモードは、ネットワークの上の相手（勤務先、ISP、訪問先のサイト）からは隠さないことを、最初のページに書く。

## 7. ダウンロードの UI

- ツールバーの吹き出しで、進行中・完了・危険の判定を示す。一覧は `<brand>://downloads`。
- 判定の流れ（保存の前）：
  1. ファイルの種類の危険度（実行形式・スクリプトなど）を、手元の表で決める。
  2. Safe Browsing のダウンロードの確認（ハッシュでの照会。[safe-browsing-and-permissions.md](safe-browsing-and-permissions.md)）。
  3. 結果に応じて、そのまま保存・警告して利用者に選ばせる・遮断する。遮断したものも一覧に残し、理由を示す。
- 保存したファイルに OS の出どころの印を付ける：Windows は `Zone.Identifier` の代替データストリーム（Mark of the Web）、macOS は `com.apple.quarantine` の拡張属性、Linux は `user.xdg.origin.url`・`user.xdg.referrer.url` の拡張属性（本家と同じ。[README.md](README.md) の「決定」）。
- HTTPS のページから HTTP でのダウンロード（混在のダウンロード）は警告する。

## 8. アクセシビリティ

### 8.1 OS の支援技術への橋

| OS | API | 支援技術の例 |
| --- | --- | --- |
| Windows | UI Automation（UIA） | ナレーター、NVDA、JAWS、音声アクセス |
| macOS | NSAccessibility | VoiceOver |
| Linux | AT-SPI2（D-Bus） | Orca |

- 枠の UI と Web のコンテンツは、1 つのアクセシビリティの木として OS に見せる。Web のコンテンツの木は Renderer が作り、Browser プロセスへ送り、そこで枠の UI の木とつなぐ（本家と同じ構成）。
- OS への橋は AccessKit（Rust。UIA・NSAccessibility・AT-SPI の橋を持ち、一部は Chromium のコードに由来する。[AccessKit](https://github.com/AccessKit/accesskit)）を使う（ADR-0024）。
- **Windows の MSAA・IAccessible2 は MVP で提供しない。** 本家は UIA を Chrome 126 から段階的に有効にしつつ、MSAA・IA2 も支え続けている（[Introducing UIA support on Windows](https://developer.chrome.com/blog/windows-uia-support)）。NVDA・JAWS の Web の閲覧は IA2 に依存してきたため、UIA だけで十分に使えるかは **未検証** である（実機の支援技術での確認が要る）。AccessKit は IA2 を実装していない（[ADR-0024](../decisions/0024-ui-toolkit.md) の注記）ので、IA2 が要れば橋は自前で書く。E6 の初めに、NVDA・JAWS・ナレーターで主要な操作（タブの移動、アドレスバー、見出しとリンクの一覧、フォームの入力）を試し、足りなければ IA2 の橋を S2 の前に足す。
- 企業のポリシーで UIA の提供を止められるようにする（本家の `UiAutomationProviderEnabled` と同じ目的）。

### 8.2 UI の規則

- すべての操作をキーボードで行える。本家のショートカット（`Ctrl/Cmd+T`、`Ctrl/Cmd+L`、`Ctrl+Tab`、`F6` でのペインの移動など）に合わせる。
- 各 OS の高コントラスト・文字の大きさ・視差効果を減らす設定・ダークモードに従う。
- 文字とアイコンのコントラストは WCAG 2.2 の AA を満たす。内部ページも同じ基準で、CI で axe 相当の検査を回す。

## 9. 国際化

- MVP の UI の言語は日本語と英語。UI の文字列は Project Fluent の形式（`fluent-rs`）で持ち、枠の UI と内部ページで同じ文字列の束を使う。
- 日付・数値・並べ替え・複数形は ICU4X（[ADR-0002](../decisions/0002-engine-build-vs-reuse.md) の部品）。
- 日本語の入力：アドレスバー・検索の欄・内部ページの入力で、IME の変換中の文字列（下線、変換の区切り）を正しく描き、変換の確定前に候補の検索を走らせない（変換中の文字列で候補を更新するかは、本家に合わせて確定前の文字列で更新する。未検証：E6 で本家の振る舞いを確かめる）。
- 右から左の言語（アラビア語など）は MVP の UI の言語に含めないが、枠の UI の配置を左右反転できる作りにしておく（後から足すと直しが大きいため）。Web のコンテンツの双方向テキストはエンジンの側（[rendering.md](rendering.md)）で扱う。
- 翻訳は、英語を正本とし、日本語は人がレビューする。文字列の追加は CI で両言語がそろっていることを検査する。

## 10. UI の性能の予算

基準の端末（[build-and-test.md](build-and-test.md) の 4.4 節の専用の機械）での値。枠の UI は Browser プロセスの UI スレッドで動くため、UI スレッドを止める処理（ディスク・ネットワーク・重い計算）を置かない。

| 項目 | 予算 | 測り方 |
| --- | --- | --- |
| 起動してから、枠の UI（タブの帯・ツールバー）の最初の描画 | p75 500 ms（ウォーム）。NFR-001 の 1 秒の内側 | 起動のトレース |
| キー入力から、アドレスバーへの文字の表示 | p95 16 ms（60 Hz で 1 フレーム） | 入力から表示までのトレース |
| キー入力から、手元の提供元の候補の表示 | p95 50 ms | 同上 |
| 新しいタブを開く操作から、タブの帯への表示 | p95 50 ms | 同上 |
| タブの切り替えから、内容の表示（Renderer が生きている場合） | p95 100 ms | 同上 |
| 内部ページ（設定）を開いてから、操作できるまで | p75 300 ms | 内部ページの INP・LCP |
| UI スレッドの長い処理（50 ms 超） | Stable で 1 セッションあたり中央値 0 件 | テレメトリ（同意した利用者だけ） |
| 枠の UI のメモリ（Browser プロセスのうち UI の分） | ウィンドウ 1 つ・タブ 20 枚で 60 MB 以内 | メモリの計測のテスト |

- CI で、起動・入力・タブの切り替えの性能のテストを回し、予算を 10% 超えたら失敗にする（[build-and-test.md](build-and-test.md)）。

## 11. リスクと未解決事項

- **Windows のスクリーンリーダーの対応**：UIA だけで NVDA・JAWS の Web の閲覧が実用になるか（8.1）。
- **検索の候補の既定**：既定で無効にすると、本家と比べて使い勝手が落ちる。選択の画面で有効にする割合を見て、PM が見直す。
- **Linux の多様さ**：Wayland の合成器ごとの差（CSD、IME、ドラッグ）。MVP は GNOME と KDE の最新版に絞って検証する。
- **自前の UI 層の作り込み**：枠の UI のウィジェット（テキストの編集、メニュー、ドラッグ）を自作する量が多い（ADR-0024 の Consequences）。
