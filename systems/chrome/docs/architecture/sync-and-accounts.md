# Sync and accounts: Chrome

アカウントのサービス（登録、ログイン、ブラウザのサインイン）と、同期（データ型、プロトコル、衝突の解決、エンドツーエンドの暗号化、複数の端末、削除）の設計。アカウントは [ADR-0028](../decisions/0028-account-service.md)、同期のプロトコルと暗号化は [ADR-0027](../decisions/0027-sync-protocol-and-e2ee.md)、送るデータの方針は [ADR-0005](../decisions/0005-privacy-first-services.md) に従う。

この文書の値（期間、件数、暗号の引数）は初期値である。E8 の各変更の `spec.md` で要件にするときに確定する。

## 1. 全体像

```
ブラウザ（プロファイルごと）
 ├─ 同期のエンジン（Browser プロセスの専用スレッド）
 │    データ型ごとの橋 ─ 手元の DB（ブックマーク、履歴、パスワード…）
 │    暗号化の層（鍵束、端末の鍵は OS の鍵の保管庫）
 │
 │ HTTPS（アクセストークン）          WebSocket（変更の通知だけ）
 ▼                                     ▼
┌──────────── クラウドのサービス（AWS、東京） ────────────┐
│ アカウント（Better Auth）  accounts.<brand>.<domain>       │
│   パスキー、メールの OTP、セッション、OAuth 2.1 の発行    │
│ 同期の API（Hono）         sync.<brand>.<domain>           │
│   GetUpdates / Commit / 鍵束 / 端末                        │
│ 通知（WebSocket）          変更があった型だけを知らせる    │
│ Aurora PostgreSQL（暗号文とメタデータ）、Valkey（通知）    │
└────────────────────────────────────────────────────────────┘
```

- **サービスは暗号文だけを持つ。** 同期するすべてのデータ型を、端末で暗号化してから送る。サービスが読めるのは、2.4 節のメタデータだけである。
- **衝突の解決は端末で行う。** サービスは中身を読めないため、版の番号による楽観的な排他だけを行い、合わせ方はデータ型ごとに端末が決める。
- 本家の同期は、`GetUpdates`（取得）と `Commit`（送信）の 2 つの要求と、データ型ごとの橋（`DataTypeSyncBridge`）で組み立てる（[Chromium の components/sync](https://chromium.googlesource.com/chromium/src/+/master/components/sync/README.md)）。本システムも同じ形にする。違いは、本家が既定でサーバーの鍵（keystore）で暗号化し、利用者のパスフレーズを選んだときだけ全体を利用者の鍵にするのに対し、本システムは常に利用者の鍵にすること（4 節）。

## 2. アカウントのサービス

### 2.1 ログインの手段

Slack の設計（[identity-and-access.md](../../../slack/docs/architecture/identity-and-access.md)、Slack の ADR-0012）と同じく Better Auth で自前でホストし、パスワードを持たない。

| 手段 | MVP | 備考 |
| --- | --- | --- |
| パスキー（WebAuthn） | ○ | 主な手段。登録を初回の設定で勧める |
| メールの OTP（6 桁） | ○ | サインアップと、パスキーのない端末での回復。10 分で失効、5 回の誤りで無効 |
| TOTP | ○（任意） | メールの OTP だけのアカウントの 2 段階目。拡張機能の開発者は、パスキーか TOTP が必須（[extensions.md](extensions.md) の 7 節） |
| パスワード | × | 保存しない |
| Google などのソーシャルログイン | × | Google のサービスとの統合は Non-goals（[intent.md](../intent.md)） |

- パスキーでのログインには、ブラウザ自身の WebAuthn の実装が要る。Windows は Windows Hello、macOS は AuthenticationServices のパスキー、Linux はセキュリティキーを使う。スマートフォンでの認証（hybrid）は MVP の後で、それまではメールの OTP で補う（[safe-browsing-and-permissions.md](safe-browsing-and-permissions.md) の 7 節。Linux の本家は hybrid に対応し、BLE は BlueZ を使う。[Passkeys の対応環境](https://developers.google.com/identity/passkeys/supported-environments)、2026-09-27 に確認。BlueZ に起因する不安定さの報告があるので、品質は E8 の初めに実機で確かめる）。WebAuthn の実装は [safe-browsing-and-permissions.md](safe-browsing-and-permissions.md) の権限と合わせて扱う。
- 応答は、アカウントが存在するかどうかで変えない（メールアドレスの列挙を防ぐ）。

### 2.2 ブラウザのサインイン

ブラウザは、アカウントのサービスに対する OAuth 2.1 の公開クライアント（第一者）である。Better Auth の OAuth 2.1 Provider プラグイン（`@better-auth/oauth-provider`。公開クライアントでの PKCE、リダイレクト URI の完全一致が既定。[OAuth 2.1 Provider](https://better-auth.com/docs/plugins/oauth-provider)）で発行する。

1. 利用者が「同期を有効にする」を選ぶと、Browser プロセスが専用のタブで `accounts.<brand>.<domain>` の認可のページを開く（PKCE の `code_verifier` は Browser プロセスだけが持つ）。
2. ログインが済むと、認可のページは予約したリダイレクト URI（`<brand>://oauth-callback`）へ移る。Browser プロセスがこの遷移を横取りし、Renderer には渡さない。
3. Browser プロセスが認可コードをトークンに交換する。

| トークン | 有効期間 | 保存 |
| --- | --- | --- |
| アクセストークン（JWT、`aud` は同期の API） | 10 分 | メモリだけ |
| リフレッシュトークン | 使うたびに回転。90 日使わなければ失効 | OS の鍵の保管庫（Windows は DPAPI、macOS は Keychain、Linux は Secret Service）。プロファイルごと |

- リフレッシュトークンは、端末（プロファイル）の登録（`devices` の行）に結びつける。端末を外すと、その端末のリフレッシュトークンを失効させる。
- ログイン・端末の一覧・端末の削除・アカウントの削除は、アカウントの Web のページ（ブラウザの中で開く）で行う。
- 本家では、Google アカウントへのログインとブラウザのサインインが結びついているが、本システムは Web のサイトのログインとブラウザのサインインを結びつけない（アカウントの Web のページでログインしても、同期は自動で有効にならない）。

### 2.3 テーブル（アカウント）

Slack と同じく、Better Auth のモデル名を変えて使う。

| テーブル | 中身 |
| --- | --- |
| `accounts` | メールアドレス、確認済みか、作成日時、削除の予定日時 |
| `sessions` | Web のセッション（アカウントのページ用） |
| `passkeys` | WebAuthn の公開鍵 |
| `two_factors` | TOTP の秘密（暗号化） |
| `verifications` | OTP のハッシュ |
| `oauth_clients`、`oauth_tokens` | ブラウザ（第一者のクライアント）、リフレッシュトークンのハッシュ |
| `devices` | 端末 ID、プロファイルの表示名（暗号化。4.4）、OS・版、登録日時、最終同期日時、失効日時 |

### 2.4 同期のサービスが見えるメタデータ

| 見える | 見えない（暗号文の中） |
| --- | --- |
| アカウント ID、端末 ID、データ型、エンティティ ID（無作為か、鍵付きハッシュ）、版、削除の印、更新日時、暗号文の大きさ、鍵の版 | URL、タイトル、パスワード、ユーザー名、フォルダの構造、並び順、履歴の訪問の時刻、拡張機能の ID、設定の値、端末の表示名 |

- データ型と大きさと時刻は見えるため、「いつ・どれだけ閲覧したか」の傾向は推測できる。これは引き受ける（ADR-0027 の Consequences）。

## 3. データ型

| データ型 | MVP | 衝突の解決 | 上限（初期値） | 備考 |
| --- | --- | --- | --- | --- |
| `keys`（鍵束） | ○ | 4.3（版の番号で直列化） | ― | 本家の Nigori にあたる |
| `devices`（端末の情報） | ○ | 端末ごとに所有。衝突しない | 20 台 | |
| `bookmarks` | ○ | 項目ごとに新しい方。親と並び順は項目の属性（分数の位置）として持ち、木の矛盾（循環、親の消失）は端末で直す | 10 万件 | 本家の `UniquePosition` と同じ考え方 |
| `passwords` | ○ | 項目ごとに新しい方。パスワードの変更の履歴（直前の 1 件）を暗号文の中に残す | 1 万件 | 端末での保存と漏洩の確認は [ADR-0023](../decisions/0023-password-manager-encryption.md) |
| `preferences` | ○ | 項目（設定の名前）ごとに新しい方 | 同期の対象に選んだ設定だけ | 端末に閉じる設定は送らない |
| `history` | ○ | 訪問は追加だけ（和集合） | 90 日 | 本家の履歴の同期と同じく、期間を限る |
| `history_delete_directives` | ○ | 追加だけ | 90 日 | 履歴の削除（期間・URL）を他の端末に伝える |
| `open_tabs` | ○ | 端末ごとに所有 | 端末あたり 500 タブ | 他の端末のタブの一覧 |
| `reading_list` | ○ | 項目ごとに新しい方 | 1 万件 | |
| `extensions` | ○ | インストール・削除は項目ごとに新しい方 | 500 件 | 拡張機能の ID と有効・無効だけ。パッケージはストアから取る |
| `extension_settings` | ○ | 拡張機能の `storage.sync` のキーごとに新しい方 | 本家の `storage.sync` の上限に合わせる | |
| `search_engines` | ○ | 項目ごとに新しい方 | 500 件 | 既定の検索エンジンの選択を含む |
| `autofill_profiles` | ○ | 項目ごとに新しい方 | 1,000 件 | 住所など。支払いのカードは MVP の外 |
| `themes`、`send_tab`、`payment_cards` | MVP の後 | | | |

- 「新しい方」は、暗号文の中の更新の時刻（端末の時計）と、端末 ID の辞書順で決める。時計のずれで古い変更が勝つことがあるため、サービスは応答にサーバーの時刻を入れ、端末は大きくずれた時計（初期値 ±10 分）を補正する。
- アカウントあたりの保存の上限は、暗号文の合計で 200 MB（初期値）。超えたら、履歴から古い順に送らなくなる。

## 4. エンドツーエンドの暗号化

### 4.1 鍵の構成

```
同期の根の鍵（SRK。256 bit の乱数。アカウントに 1 つ。版を持つ）
 ├─ HKDF ─▶ データ型ごとの暗号化の鍵（AEAD）
 ├─ HKDF ─▶ エンティティ ID の鍵付きハッシュの鍵（HMAC）
 └─ HKDF ─▶ 端末の表示名などの鍵

SRK を包んだもの（サービスに置く。サービスは開けない）
 ├─ 端末の公開鍵で包む（HPKE。端末ごと）
 ├─ 回復用のコードから作った鍵で包む
 └─ （任意）利用者のパスフレーズから作った鍵で包む
```

| 用途 | 方式 |
| --- | --- |
| エンティティの暗号化 | XChaCha20-Poly1305。追加の認証データ（AAD）にアカウント ID・データ型・エンティティ ID・鍵の版を入れ、暗号文の入れ替えを検出する |
| エンティティ ID | 手元の一意な名前（例：パスワードならオリジンとユーザー名）がある型は、HMAC-SHA256 の値。無い型は乱数 |
| 端末の鍵 | X25519 の鍵の組を端末で作り、秘密鍵は OS の鍵の保管庫に置く。SRK は HPKE（RFC 9180、X25519・HKDF-SHA256・ChaCha20-Poly1305）で包む |
| 回復用のコード | 128 bit の乱数を、区切り付きの 26 文字（Crockford の Base32）で表示する。鍵は Argon2id（m=64 MiB、t=3、p=1）で作る |
| パスフレーズ（任意） | 12 文字以上。鍵は Argon2id（m=256 MiB、t=3、p=1）。塩は無作為 |

- 本家の利用者のパスフレーズの鍵の導出は、M70 から scrypt（N=2^13、r=8、p=11、無作為の塩）で、それ以前は PBKDF2-HMAC-SHA1 の 1,003 回（固定の塩）だった（[nigori_specifics.proto](https://chromium.googlesource.com/chromium/src/+/HEAD/components/sync/protocol/nigori_specifics.proto)）。本システムは、メモリを多く使う Argon2id（RFC 9106）を選ぶ。引数は、RFC 9106 の 4 節の 2 つ目の推奨（t=3、p=4、m=64 MiB）を出発点にし、基準の端末で 1 秒以内に終わる値を E8 で測って確定する（[RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html#section-4)、2026-09-27 に確認。値は **未検証**）。
- 暗号の実装は、監査済みのライブラリ（RustCrypto の各クレート、HPKE は `hpke` クレートなど）を使い、自分たちで暗号の基本の部品を書かない（[ADR-0002](../decisions/0002-engine-build-vs-reuse.md)）。

### 4.2 端末を足す

| 経路 | 流れ |
| --- | --- |
| 既存の端末で承認（既定） | 新しい端末が公開鍵をサービスに登録する → 既存の端末に通知 → 両方の端末に同じ 6 桁の確認の数字を表示し、利用者が一致を確かめて承認 → 既存の端末が SRK を新しい端末の公開鍵で包んで置く |
| 回復用のコード | 利用者がコードを入力 → 包んだ SRK を開く → 自分の公開鍵で包み直して置く |
| パスフレーズ | 同上 |

- 確認の数字は、両方の端末の公開鍵と、サービスが渡した乱数から作る。サービスが別の公開鍵にすり替えると、数字が一致しない。
- 最初の端末：SRK を作り、回復用のコードを表示し、控えたことを確かめる（コードの一部の入力）までは同期を始めない。

### 4.3 鍵の回転

- 端末を外したとき、回復用のコードを作り直したとき、利用者が求めたとき、SRK を新しい版にする。
  1. 信頼できる端末（外していない端末）が新しい SRK を作り、残る端末の公開鍵・回復用のコードで包んで置く。
  2. 以後の書き込みは新しい版で暗号化する。古い版のエンティティは、その端末が背景で読み直して、新しい版で書き直す。
  3. 古い版の鍵は、鍵束（新しい SRK で暗号化）の中に残し、書き直しが済むまで読めるようにする。
- 鍵束の更新は、`keys` 型の版の番号で直列化する（2 台が同時に回転しても、片方の Commit は衝突で失敗し、やり直す）。
- 外した端末は、回転の前に取得したデータは読める。これは暗号化では防げないので、端末の削除はリフレッシュトークンの失効（取得を止める）と組み合わせる。

### 4.4 鍵を失ったとき

- すべての端末と、回復用のコード・パスフレーズを失うと、同期のデータは誰も戻せない（[ADR-0005](../decisions/0005-privacy-first-services.md) の Consequences）。
- その場合、利用者は「同期をやり直す」を選び、サービス上のデータを消して新しい SRK で始める（手元の端末に残ったデータは、新しい同期で送り直される）。
- 鍵の問題（開けない、版が合わない）の調べ方は、runbook（同期の鍵の問題）に書く。サービスの運用者が鍵を戻す手段はない。

### 4.5 暗号化されていないことの検査

- サービスは、Commit で受けたエンティティの形（封筒の版、鍵の版、ノンスの長さ、AEAD のタグの長さ）を検査し、合わないものは拒む。
- 定期の検査で、DB の暗号文から標本を取り、既知の平文の形（URL、JSON、protobuf の先頭）に見えるものが無いことを確かめる（ADR-0005 の Confirmation）。

## 5. 同期のプロトコル

### 5.1 要求

| 要求 | 中身 |
| --- | --- |
| `GetUpdates` | データ型ごとの進み具合の印（最後に受けた版）。応答は、それより新しい版のエンティティ（1 ページ 500 件）と、新しい印 |
| `Commit` | エンティティの一覧。各エンティティは、元にした版（新規は 0）を持つ。版が今のものと違えば、そのエンティティは `conflict` で拒み、今の版を返す |
| `GetKeys` / `PutKeys` | 鍵束、包んだ SRK、端末の公開鍵 |
| 通知 | WebSocket で、変更のあったデータ型の名前だけを送る。中身は送らない |

- 形式は HTTPS の上の protobuf。エンティティの中身（暗号文の中）も protobuf で、知らないフィールドを保つ（古い端末が読み書きしても、新しい端末が足したフィールドを消さない）。本家も同じ方針である。
- 版の番号は、アカウント×データ型ごとに単調に増える整数で、サービスが Commit のときに振る。進み具合の印はこの番号である。
- 通知の WebSocket が切れているときは、5 分ごとに `GetUpdates` を送る。NFR-008（別の端末への反映 p95 10 秒）は、通知で満たす。
- サービスは、応答で `retry_after` と、データ型ごとの一時停止（ある版の端末で不具合が出たとき、その型の同期を止める）を指示できる。

### 5.2 衝突の流れ

1. 端末 A と B が、同じエンティティ（版 7）を変える。
2. A の Commit が先に着き、版 8 になる。
3. B の Commit は、元の版 7 が今の版 8 と違うため `conflict` になり、版 8 の暗号文が返る。
4. B は復号して、データ型の規則（3 節）で合わせ、元の版 8 として Commit し直す。
5. 合わせた結果が A の版と同じなら、B は何も送らない。

- 本家の既定の衝突の解決は、橋が上書きしなければサーバーの側を採る。ただし、サーバーの側が削除なら手元の側を採る（`DataTypeSyncBridge::ResolveConflict`。[data_type_sync_bridge.cc](https://source.chromium.org/chromium/chromium/src/+/main:components/sync/model/data_type_sync_bridge.cc)、2026-09-27 に確認）。3 節の規則がないデータ型は、この既定に揃える。

### 5.3 初回の合わせ込み

- 手元にデータがある端末で同期を始めると、サービスのデータを全部取ってから、データ型ごとに合わせる。
  - ブックマーク：同じフォルダの中で、URL とタイトルが同じものを同じ項目とみなす。
  - パスワード：オリジンとユーザー名が同じものは、新しい方を採り、もう一方を変更の履歴に残す。
  - 履歴：和集合。
- 合わせ込みの結果を送る前に、ブックマークとパスワードの件数の変化を利用者に示す（件数が大きく減る合わせ込みは、確認してから送る）。

### 5.4 削除の印

- 削除は、暗号文を持たない削除の印として版を進める。削除の印は 60 日残し、それより後に消す。
- 60 日を超えて同期していない端末は、進み具合の印を捨て、全体を取り直す（5.3 の合わせ込みを経る）。

## 6. サーバーの保存

| テーブル | キー | 中身 |
| --- | --- | --- |
| `sync_entities` | (`account_id`, `data_type`, `entity_id`) | 版、暗号文、鍵の版、削除の印、更新日時、大きさ |
| `sync_type_state` | (`account_id`, `data_type`) | 次の版の番号、合計の大きさ |
| `sync_key_bags` | `account_id` | 鍵束（暗号文）、鍵の版、版の番号 |
| `sync_wrapped_keys` | (`account_id`, 包んだ相手) | 端末ごと・回復用のコード・パスフレーズごとに包んだ SRK、KDF の引数、塩 |
| `sync_device_keys` | (`account_id`, `device_id`) | 端末の公開鍵、登録の状態 |

- S1 は Aurora PostgreSQL の 1 つのクラスタ（東京）。`sync_entities` は `account_id` のハッシュで分割（パーティション）する。
- S2 では、`account_id` のハッシュでクラスタを分ける（シャード）。アカウントのサービスは分けない。
- S3 では、アカウントごとに本拠のリージョンを持ち、同期のデータはそのリージョンだけに置く。
- 通知は Valkey の pub/sub で、通知の WebSocket を持つタスクへ流す。Valkey は失われてもよい（端末は 5 分ごとの取得で追いつく）。
- 平文の閲覧のデータは、ログにもトレースにも出さない。出すのはアカウント ID・データ型・件数・大きさだけ（[observability.md](observability.md)）。

## 7. 複数の端末

- 設定の「端末」で、同期している端末の一覧（表示名、OS、最終同期）を見て、外せる。外すと、リフレッシュトークンの失効と鍵の回転（4.3）を行う。
- 他の端末の開いているタブを、履歴のページと新しいタブのページに示す（`open_tabs`）。
- データ型ごとに、その端末で同期するかを選べる。選ばなかった型は、その端末では送りも受けもしないが、サービスのデータは消さない。
- 企業のポリシー：同期の無効化（`SyncDisabled` と同じ意味）、データ型ごとの無効化（`SyncTypesListDisabled` と同じ意味）。

## 8. 削除

| 操作 | サービスの振る舞い | 期限 |
| --- | --- | --- |
| データ型のデータを消す（例：履歴を同期から消す） | その型のエンティティを削除の印に変え、他の端末に伝える | 即時。暗号文の物理的な削除は 24 時間以内 |
| 同期をやり直す | `sync_*` のすべての行（鍵束、包んだ鍵を含む）を消す。全端末の同期を止め、設定し直しを求める | 即時。物理的な削除は 24 時間以内 |
| 端末を外す | 端末の公開鍵・包んだ SRK・リフレッシュトークンを消し、鍵を回転する | 即時 |
| アカウントを消す | ログインを止め、14 日の取り消し期間の後に、アカウントと同期のすべての行を消す | 14 日＋物理的な削除 24 時間以内 |
| バックアップ | Aurora の特定時点への復元の保持期間（35 日）が過ぎると消える | 35 日 |

- 削除の後も、バックアップには 35 日まで暗号文が残る。サービスは鍵を持たないため、読めない。これを利用者への説明に書く。
- 削除の記録（いつ、どの操作）は、アカウント ID を仮名化して 1 年残す（`deletion_events`。[data-model.md](data-model.md) の 2.3 節）。

## 10. リスクと未解決事項

- **鍵の喪失**：回復用のコードを控えない利用者は、端末を失うとデータを失う。初回の設定で控えたことを確かめ、定期的に再確認を促す。
- **メタデータ**：データ型・大きさ・時刻から、閲覧の量の傾向が見える。パディング（大きさの丸め）を S2 で検討する。
- **時計のずれ**：「新しい方」の判定が端末の時計に依存する。
- **パスキーでの鍵の保護**：WebAuthn の PRF 拡張で SRK を包めば、パスキーだけで新しい端末を足せる。対応する認証器・OS の範囲が **未検証** のため（2026-09-27 の検証でも、Windows Hello などの各 OS の対応を公式の文書で確かめられなかった）、MVP に含めず、S2 の前に検討する。
- **本家からの移行**：本家の同期のデータは読めない（Google の鍵）。本家からの取り込みは、エクスポートしたファイル（ブックマークの HTML、パスワードの CSV）から行う。
